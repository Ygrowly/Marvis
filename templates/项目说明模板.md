# 项目说明模板

> **这份模板解决什么**：项目说明最容易写成「我做了个平台」——技术很全，但读者读完不知道**这东西到底给谁、怎么用、交付到哪一步**。RuleArena 的第一版就是这个病，面试时被连着三个问题打穿（「别人怎么用？」「需要上报吗？」「损失指什么？」）。
>
> **核心判据**：**写每一节前先问——这一节在回答读者的哪个问题。** 回答不了就别写。
> **产出物**：一份 `{项目}-项目说明.md`，作为该项目的**唯一正本**（叙事、口径、面试话术都从这里派生）。

---

## 总原则（先读这条，再动笔）

**按别人会怎么问来写，不按你有什么可写来写。**

| 写坏的样子 | 该有的样子 |
|---|---|
| 从「我做了个平台」开始，罗列组件与技术选型 | 从「**谁在什么情况下遇到什么问题**」开始，技术是解法 |
| 把「验证系统」当「平台」写——堆功能、堆模块 | 说清**它验证谁、拦住什么、给出什么判定** |
| 把自建靶场说成「客户的真实系统」 | 说清它是**替身**：替代客户系统让验证成立，同时把危险关在笼子里 |
| 数字只报对自己有利的那半 | **成对陈述**：机制达标与能力短板一起说 |

## 第零阶段：立意闸门（**动笔写正文之前，先过这一关**）

> **这一节解决什么**：项目说明写不下去、写完了被问穿，九成不是表达问题，是**立意没过闸**——说不出「给谁省了什么」，或者「在哪一格上比别人钻得深」。
>
> **判据（2026-10-02 定，从两个 idea 的讨论里反推）**：**项目要么有价值，要么在某个业务上很垂直。** 展开成三条，逐条打分，缺一条就在正文里补，补不上就别写这个项目。
>
> **本节的正文下游**：`output/resume/简历写作方法论.md` §1.6（选条与价值叙事）、`wiki/interview/个人项目含金量表达铁律.md` §0 铁律三与 §0.5（画饼公式）——**两处只引用不复制**。

### 0.1 三条判据（V × H × P）

| 判据 | 一句话 | 检验问句（答不出 = 没过闸） | 典型反例 |
|---|---|---|---|
| **V 有价值** | 有人因为它少花钱 / 少踩坑 / 多做成一件事 | 谁？原来怎么做？代价是多少（钱 / 时间 / 事故）？**它改变了谁的哪个决定？** | 「提升研发效率」——谁的、多少、怎么算 |
| **H 垂直** | 在一个具体业务 / 具体失败模式上钻到别人钻不进去 | 能不能说出「**同一份代码跑两次**」的对照场景？失败模式能不能**点名**？裁决依据是不是**能算的数**？ | 「通用 Agent 平台」——每句话换个项目也能说 |
| **P 可证明** | 价值与深度都能被跑出来的数字支撑 | 有没有对照实验 / 固定评测集 / 可复现命令？能不能**成对陈述**（好的一半与坏的一半一起说）？ | 「效果显著」、只有 demo 没有数字 |

**三条是乘积不是加和**（缺一条，整体就不成立）：

- **V 强 · H 弱** = 人人都在做的通用能力（例如「做一个外挂记忆系统」）——**讲得出价值，讲不出差异**；
- **H 强 · V 弱** = 技术炫技，第一句「谁会为这个付钱」就倒；
- **V·H 都强 · P 弱** = 只能在嘴上成立，**进不了简历**（与「E3 不进简历」是同一条规矩）。

**四象限速判**：

|  | 垂直 | 不垂直 |
|---|---|---|
| **有价值** | **立项优先**（RuleArena：资损 + 非原子工具调用这一格） | 通用能力 → **先切一格**再讲（记忆系统 → 可验证的记忆） |
| **价值不清** | 技术 demo，先补价值落点 | 不写 |

### 0.2 立意的两步动作

1. **先找价值落点**：写「因为有了它，【谁】在【什么时刻】不用再做【什么事】/ 不再损失【多少钱】」——**写不出这句，先别画架构**。
2. **再切垂直一格**：在通用能力里挑**一个具体失败模式**，做到「同样的话别人说不出口」。
   - 不做「记忆系统」，做「**记忆写入的幂等与冲突裁决**」；
   - 不做「E2E 平台」，做「**LLM 采集用例 + 确定性断言的分离**」；
   - 不做「多 Agent 平台」，做「**任务依赖与计划变更下的结果失效**」。

> **判据**：切完之后，能不能用一句「**A ≠ B**」点名这一格（如「SQL 能执行 ≠ 业务答案正确」「工具返回 ACK ≠ 业务成功」）？**能，就切对了**；只能用形容词描述，就还没切到。

### 0.3 上价值公式（画饼）的五层与降维

| 层 | 说什么 | 纪律 |
|---|---|---|
| **L1 我能做** | 已有证据的机制 | **必须有实测数字**，否则后面四层全是空的 |
| **L2 对公司多个产品有用** | 复用 / 打通 | 要答得出**障碍**（schema 不一致 / 权限边界 / 裁决规则谁定），答不出就别讲这层 |
| **L3 变成业务指标** | 成本 / 留存 / 客诉 / 发布信心 | 说清转化链；**「更了解客户」不是指标**，它下面是留存还是客诉要能点名 |
| **L4 开源反哺** | 参考实现 | 说「开源一份参考实现」，**不说「建立行业标准」** |
| **L5 标准 / 影响力** | 只在 L1–L4 都站住时提 | 用假设语气（「如果跑通，可以再往外推一步」）；**对应届生是雷区** |

> **画饼纪律（一句话）**：**饼只能画在已做出来的证据的延长线上。** 面试问「你打算为公司做什么」讲到 L3 就够，L4 一句带过；老板 / 创始人问，可以讲到 L4，但必须带「先跑通一个产品」的前置。逐层用法见 [[个人项目含金量表达铁律]] §0.5。

## 第一阶段：先定读者与用法（**跳过这步必踩坑**）

### 1.1 这份说明是给谁看的？

| 读者 | 他关心 | 对应要写透的节 |
|---|---|---|
| **面试官（主）** | 这东西解决什么真问题、你负责了哪部分、有什么证据 | 设计哲学 · 行业位置 · 黄金场景 · 实测结果 · 面试话术 |
| 你自己（三个月后） | 当时为什么这么决策、口径在哪 | 全文 |
| 未来协作者 | 怎么跑起来、边界在哪 | 系统架构 · 交付物 · 边界与诚实口径 |

### 1.2 用户是谁、他拿它做什么（**必答，不能含糊**）

> 三栏缺一不可：**用户是谁 / 他什么时候用 / 他拿到什么结果**。

- 主用户：______（**写具体角色**，不要写「开发者」）
- 使用时机：______
- 拿到什么：______

### 1.3 一句话的 Job to Be Done

> 当【**什么情况下**】，用户要【**完成什么**】，现在【**为什么做不到**】，所以我做了这个。

**判据**：这句话里如果出现「平台」「框架」「系统」这类词，说明还没想清楚——换成动作和结果。

### 1.4 用户到底怎么用（**B4 式追问的正面回答**）

> 这节专治「你做了个东西，但别人怎么用？」

- **主路径**：从输入到结果的完整流程，**逐步骤写清楚谁在动**
- **有没有集成**：用户需不需要接自己的东西？接什么？不接能不能用？
- **会不会影响别人的生产环境**：如果会，机制是什么；如果不会，为什么
- **理想形态 vs 已实现形态**：诚实分开（见「交付物与完成度边界」节）

## 第二阶段：正文骨架

### ① 一句话定义

三段固定结构，**缺一段就是不完整**：

```text
1. 是什么：它是【面向谁的什么场景】的【什么东西】
2. 核心矛盾：它要解决的**根本矛盾**是什么（一句话，能背）
3. 最小价值单位：用户拿到的最小成果是什么——**不是报告，是判断/证据/判定**
```

**判据**：第 3 段如果是「一份报告 / 一份分析」，回去重想——报告不是价值，**能被使用的东西才是**。

### ② 设计哲学（两条腿）

> 结构必须是：**【谁】负责【什么】，【谁】负责【什么】**。

示范：*「让 LLM 去搜人想不到的路径，让确定性程序去证明路径是不是真的有问题。」*

**判据**：这句话要能一句话说清「哪部分交给概率、哪部分交给确定性」——这是 AI 应用类项目的核心取舍，面试官必问。

### ③ 设计原则（3–6 条，每条都能被追问）

每条格式：**短句断言 + 为什么**。

必须覆盖的几条（按项目改词）：
- 什么东西必须先冻结/确认，才能往下走；
- **信任必须来自被测对象之外**（防自证）；
- 什么由确定性程序负责，模型不碰；
- 完成由什么证据证明（**不接受自述**）；
- 不确定时的默认行为（**fail closed**）。

### ④ 行业位置（**必须有，配置不到位会被击穿**）

> **这一节的目标不是「我很新」，是「我知道我在哪」。**

1. **先查有没有人做过**：论文、开源、产品。查到就**引用**，别装不知道
2. **分级**：问题已被正式提出 / 解法已被验证有效 / 工程侧已有共识
3. **划清差异**：表格三列——「他们做什么 / 我在哪一层 / 我的产物有什么不同」
4. **一句话定位**：承认共识 + 说清自己占的那一格

> **⛔ 禁止**：声称首创、说「没有主流项目做这件事」。正确的姿态是「**在已经成立的共识上往前接了一段**」。

### ⑤ 黄金场景（**一个，别贪多**）

- **必须是对照**：同一份代码跑两次，差别只有「有没有它」——**不是好版本打坏版本**
- 说清：**失败是怎么发生的**（真实失败模式，不是构造的刁难）
- 说清：**拦住之后发生什么**
- 一条主场景讲透 + 一条备用（证明能力不只一种）

### ⑥ 实测结果（**最优先的面试弹药**）

> 面试口径第一优先级：**先讲结果，再讲机制**。

1. **数字必须可复现**：给命令
2. **成对陈述**：好的那半与坏的那半一起说——**只报一半等于选择性陈述**
3. **两组指标宁可不合并**：比如「任务完成度」与「代价/风险」是两个维度，**合并会掩盖失败**
4. **口径写死**：样本构成、重复次数、对照组定义、环境
5. **诚实区间的写法**：能报稳定性的别只报上限

> **版式建议**：把这组数字放在**文档正文最前面**（在「一句话定义」之后立刻出现），
> 而不是埋在评测章节里——面试前自己复习时，第一眼要看到的就是它。
>
> **加分项（比数字更值钱）**：**执行中打出来的真实缺陷**。每条写清「现象 → 为什么会漏掉 → 怎么修 → 补了什么回归」。**「我怎么发现自己做错了」比「我设计得多对」可信得多。**

### ⑦ 系统架构与模块职责

> 上承设计原则（为什么这么分），下接评测（分得对不对）。**不是画组件图的节，是写清边界的节。**

给一张主链路图（谁调谁、数据往哪走），再给一张**职责表**：

| 模块 | 负责 | **不负责** |
|---|---|---|
| ______ | ______ | ______ |

**判据**：**「不负责」那一列必须写满。** 只写负责什么，读者会自己脑补出你没做的能力；
写明「不负责什么」，边界才是你划的，不是别人替你划的。

主链路要能回答：**一条输入从进来到出去，中间经过了谁、每一步谁在动。**

### ⑧ 交付物与完成度边界

- **用户拿到什么**：成功路径给什么、失败路径给什么（都要有）
- **使用形态**：有几种、分别是什么
- **完成度表（**面试必须主动说**）**：

| 已实现（有代码与实测） | 尚未做 / 为什么不做 |
|---|---|
| …… | …… |

> **口径纪律**：设计中的东西**永远是 E3**；**只有跑出真实数字，才能从右列移到左列**。

### ⑨ 边界与诚实口径

- **负责**：______
- **不负责**：______
- **只能声明**：在【版本 + 环境 + seed + 预算】内发现或未发现
- **不能声明**：绝对安全 / 已解决
- **真实性分层**：业务真实性 / 执行真实性 / 验证真实性 / 运行真实性各是什么；**别把替身说成客户系统**

### ⑩ 面试话术（从真实受击点倒推）

| 层级 | 内容 | 要求 |
|---|---|---|
| **开场第一句** | 一句话把面试官拉成同行 | 自带反转、能记住 |
| **20 秒** | 是什么 + 最硬的一组数字 | 数字带对比 |
| **90 秒** | 问题 → 但书 → 解法 → 证据 → 诚实边界 | 能一口气说完 |
| **高频追问表** | `面试官问 \| 应答要点` | **每一条都来自真实被问懵的地方** |

- [ ] §1.4 能**逐步骤**说清用户怎么用；能回答「会不会影响别人的生产环境」
- [ ] §④ 引用得出具体论文/产品名；**没有**任何「首创」表述
- [ ] §⑤ 对照组是**同一份代码跑两次**

- [ ] §⑧ 完成度表左右分得清；**设计中的没写成已达成**

## 三个反复出现的错误（写的时候对照）

| 错误 | 症状 | 修法 |
|---|---|---|
| **把「验证系统」写成「平台」** | 堆功能清单，读者不知道它拦住了什么 | 说清**它验证谁、给出什么判定、改变什么决策** |
| **立意没过闸就开始写正文** | 价值说不出「谁省了多少」，深度说不出「A ≠ B」；面试官第一问「谁会用这个」就倒 | 回 §0.1 三条判据逐条打分；**先切垂直一格再动笔**（§0.2） |
| **把自建靶场说成客户的系统** | 一说就自相矛盾（「自建的怎么能是客户的？」） | 讲成**替身**：替代客户系统让验证成立，同时把危险关在笼子里；真接外部要走适配层接测试环境 |
| **口径改了只改一处** | 同一份文档里前后打架；简历与仓库对不上 | 改口径**必须全库 grep**；列表登记口径正本，其余引用不复制正文 |
