# 系统设计题 · 澄清 → 拆解 → 估算 → 方案 的四段法

> **这份文档解决什么**：系统设计题不是"想出一个架构"，而是**在信息不全、约束不清的情况下，把一个大问题切成能回答的小问题**。它有一套几乎固定的动作顺序，缺任何一个动作都会被看出来。
> **与相邻正本的分工（只引用、不复制）**：
> - **本卡是方法论**（怎么想、按什么顺序说、每一步要产出什么）
> - `wiki/interview/场景设计题库-十道母题.md` 是**题目与口述稿**（具体的题、具体的答案）
> - `wiki/interview/面试准备第一性原理.md` 是**面试域总操作系统**（面试=证据采集）
> - `wiki/interview/乐元素-服务端一二面复盘报告.md` 是**实测校准**（9.9 场景设计 10 分，缺口在哪）
>
> **本卡只回答"过程"，不回答"这道题的答案是啥"** —— 答案在题库与母题卡里。

---

## 一、面试官在这道题里到底在看什么

【事实】**系统设计题没有标准答案**，所以它一定在考过程。四个观察点，对应四段：

| # | 观察点 | 他在看什么 | 对应动作 |
|---|---|---|---|
| **1** | **会不会问** | 拿到模糊需求时，你是先问还是先编 | **澄清** |
| **2** | **能不能拆** | 把大问题切成分得清职责的几块 | **拆解** |
| **3** | **能不能算** | 你给的方案有没有量级支撑，还是全凭感觉 | **估算** |
| **4** | **会不会取舍** | 每个选择你能不能说出"为什么不选另一个"、代价是什么 | **方案** |

【推导】**这四个点的性质不同**：**前两个是"合格线"，后两个是"分水岭"。**

```
不问就答     → 直接失分（暴露"拿到题就编码"的习惯）
拆不出层次   → 后面全乱（说不清哪个组件负责什么）
不算量级     → 方案无法评价（"加缓存"是万能的，也是无用的）
不说取舍     → 听起来像背了一个架构，而不是设计了它
```

【事实】**9.9 实测的校准**：那一场**项目题 18–21 分、场景设计 10 分**——项目讲得好是因为真做过，场景设计低是因为**缺上面这套过程**（`wiki/interview/乐元素-服务端一二面复盘报告.md`）。**所以本卡是直接对着那 10 分写的。**

## 二、第一段：澄清（先问，别先答）

### 2.1 必须问清的五件事【事实】

【事实】**五类信息，缺哪类都会让后面的方案失焦**：

| # | 问什么 | 不问会怎样 |
|---|---|---|
| **① 功能范围** | **做哪些、明确不做哪些** | 面面俱到 → 每个都讲不深；**而且面试官会以为你没意识到范围问题** |
| **② 量级** | 用户规模 / 峰值 QPS / 数据量 / 读写比 | 无法估容量，无法选型（100 QPS 和 10 万 QPS 是两套系统） |
| **③ 一致性要求** | 哪部分必须强一致、哪部分能最终一致 | 全都强一致 → 又慢又复杂；全都最终一致 → **涉及钱的部分就出错了** |
| **④ 延迟与可用性** | 哪些路径要低延迟、能容忍多慢；允许多久不可用 | 无法做降级与超时设计 |
| **⑤ 边界与前提** | 单机还是分布式、能不能引第三方、已有技术栈是什么 | 方案可能"理论上对、实际上做不了" |

【推导】**问的时候要"带着假设问"，不是"空白地问"**：

```
❌ 空白地问："你们 QPS 多少？"          → 像在等答案
✅ 带假设地问："我假设峰值在几千 QPS 这个量级，
              如果实际是十万级，架构会有几处要改，我们先按几千走？"
              → 展示了估算能力，也把决定权还给面试官
```

【取舍】**问几个？** **不超过 5 个**，每个都要"问了就能改变方案"。**问那些问了不改变方案的，是浪费时间**（比如问"你们用什么语言"——除非它真的影响选型）。

### 2.2 澄清的产出【推导】

【推导】**问完之后，你要用一句话把需求复述回去**：

> "所以我们要做的是：**{功能范围}**，规模在 **{量级}**，**{哪部分}**必须强一致、**{哪部分}**可以最终一致，**{哪条路径}**的延迟要控制在 **{多少}** 以内。"

【推导】**这句话有双重作用**：① **确认没跑偏**；② **它天然就是"拆解"这一段的输入**——你会发现"强一致"和"可以最终一致"这两个词已经把系统切成两半了。

**到这里你应该能回答**：为什么"先问"不是礼貌问题，而是能力问题？

## 三、第二段：拆解（把大问题切成职责清楚的几块）

### 3.1 按请求链路拆【事实】

【推导】**最通用的一刀是"沿请求走一遍"**：

```
客户端 → 接入层（网关 / 鉴权 / 限流）
       → 应用层（业务逻辑 / 编排）
       → 数据层（缓存 / 关系库 / 搜索 / 对象存储）
       → 异步层（队列 / Worker / 定时任务）
       → 外部依赖（第三方 API / 消息推送）
```

【推导】**每一层你只需要回答三个问题**：

```
① 这一层的职责是什么（它唯一必须做对的事）
② 它可能怎么坏（超时 / 满了 / 挂了）
③ 坏了之后上游看到什么（这一步决定降级怎么设计）
```

**【第 ③ 问是分水岭】** ——大多数人能说清 ①，**少数人能说清 ③**。而"坏了之后上游看到什么"正好是 [[母题-N1-一次请求的完整路径]] 里"先分清卡在哪一层"的另一面。

### 3.2 按数据流拆（不是所有题都从请求开始）【事实】

【推导】**如果题目里有"数据从哪来、怎么变成结论"，就换成这条轴**：

```
数据源（埋点 / 日志 / 业务库）
  → 采集 → 加工（清洗 / 聚合 / 特征）
  → 存储（原始 / 明细 / 聚合层）
  → 服务（查询 / 报表 / 模型）
```

【事实】**这条轴在 AI 类题目里更常见**：RAG（文档 → 切分 → 索引 → 检索 → 生成）、评测（样本 → 跑批 → 打分 → 门禁）都属于这个形态——**对应的母题卡分别在 [[母题-G1-切分策略与索引粒度]] 与 [[母题-E1-评测集设计与pass^k]]。**

### 3.3 拆完要能画出来【取舍】

【取舍】**能画一张 3–5 个方块的图就够了**，别画 20 个（画得越多越说不清主次）。**判据**：

> **如果一张图里有哪个方块"不知道该说它什么"，那个方块就不该出现。**

**到这里你应该能回答**：为什么"拆解"的重点不在拆得多细，而在每块职责唯一？

## 四、第三段：估算（把"感觉"变成"数"）

### 4.1 三个万能算式【事实】

【事实】**几乎所有的容量估算都是这三个式子的组合**：

```
① 吞吐：QPS = 用户数 × 人均请求数 ÷ 86400 × 峰值系数
② 存储：容量 = 记录条数 × 单条大小 × 保留期
③ 带宽：带宽 = QPS × 单次数据大小
```

【推导】**再加两个"派生式子"**：

```
④ 缓存回源放大 = 1 ÷ (1 − 命中率)          ← 判断"缓存挂了能不能扛"
⑤ 连接/并发数 ≈ QPS × 平均处理时间          （Little 定律，见 [[母题-N1-一次请求的完整路径]]）
```

【事实】**分母那个 86400 是"一天有多少秒"**——记住它，大量估算的第一步都是它（**约 10 万秒，所以"日均 100 万次"≈ 每秒 10 次**）。

【推导】**峰值系数**是把"平均"变成"峰值"的乘数：**一般取 2–5 倍，有明显潮汐的业务（外卖、打卡、抢购）可以取 10 倍甚至更高**——**这个数要问面试官，而不是自己拍**。

### 4.2 常用数量级速查（⚠️ 全是经验值，随硬件与版本变化）

> 【事实】**下表只用来做"量级判断"，不要当规格书用**。真实容量取决于查询复杂度、数据分布、硬件与并发模型——**面试里说"量级在 X，具体要压测"比报一个精确数字更专业。**

| 项目 | 量级参考 |
|---|---|
| 单机应用服务（简单接口） | 数千 QPS |
| 单个关系数据库实例（简单主键查） | 数千 QPS；复杂查询可能只有几十 |
| 单个 Redis 实例 | 十万级 QPS（单线程，命令都极短） |
| 单个 MQ 分区 | 数千~万级 条/秒 |
| 一块 SSD 顺序读 | 数百 MB/s |
| 一块网卡（1 Gbps） | 约 125 MB/s |
| 单条业务记录 | 几百字节 ~ 几 KB |
| 内存带宽 | 数十 GB/s |
| 一次内存访问 / 一次上下文切换 / 一次系统调用 | 约 100 ns / 约 1 μs / 约 100 ns（[[母题-O1-上下文切换与死锁]]） |
| 一次跨机网络往返（同机房） | 约 0.1–1 ms |
| 一次磁盘随机读 | 约 0.1 ms（SSD）/ 约 10 ms（机械） |

【推导】**这张表最实用的用法是"反过来用"**：**先算出需要的量级，再查表看"单个组件够不够、要不要拆"**：

```
算出 5 万 QPS 的读 → 单 Redis 十万级够用，单 MySQL 不够 → 结论：加缓存
算出 2000 QPS 的写 → 单 MySQL 实例够用 → 结论：不需要分库分表【并且主动说出这一点】
```

**【主动说出"不需要"是加分项】** ——它证明你**按量级做了判断**，而不是"因为大厂都这么做所以我也这么做"。

### 4.3 估算的产出【推导】

【推导】**估算完要有三个数落地**：

```
① 峰值 QPS（读 / 写分开）
② 数据总量与增长速度（决定存储选型与分区策略）
③ 瓶颈在哪一层（这才是估算真正想要的东西）
```

**到这里你应该能回答**：为什么"估算"的真正目的不是算数字，而是找出瓶颈？

## 五、第四段：给方案（骨架 → 取舍 → 风险 → 指标）

### 5.1 顺序不能乱【推导】

【推导】**四步递进，每一步都在前一步的基础上加一层**：

| 步 | 说什么 | 一句话模板 |
|---|---|---|
| **① 骨架** | 先给一个**能跑通**的最小架构 | "我先把链路走通：接入 → 应用 → 库 + 缓存 → 队列异步。" |
| **② 取舍** | 每个关键选择说"为什么不选另一个" | "缓存用 Redis 不选本地缓存的理由是……；而代价是……" |
| **③ 风险** | **主动交代**会怎么坏、怎么兜 | "缓存全挂时回源放大 20 倍，所以要限流 + 降级。" |
| **④ 指标** | 怎么知道它是对的 | "看 P99、缓存命中率、队列 lag、错误率这四个。" |

【推导】**③ 和 ④ 是区分"设计过"和"背过"的分界线**：

```
只讲 ①② → 听起来像在复述一个经典架构
加上 ③④ → 听起来像真的想过它上线以后会怎样
```

### 5.2 "取舍"怎么说得不空【推导】

【推导】**取舍的模板永远是同一套**（这个模板在本库的每个模块卡里都在用）：

```
① 说清**比的是什么**（用同一个指标）
② 给两边的**代价**
③ 说**你的选择与它成立的前提**

例：
"缓存和数据库的一致性，本质是比'能容忍多久不一致'。
  只配 TTL 的代价是最多旧一个 TTL（比如 60 秒）；
  写时失效能把窗口压到毫秒级，代价是要处理删失败。
  我选写时失效 + TTL 兜底，前提是这份数据【只用于展示】——
  如果它参与判断（比如余额），那就不能进缓存，判断要下沉到数据库。"
```

【推导】**注意最后那句"前提"** ——**它把"选择"变成了"有条件的选择"，这才是设计**。**没有前提的选择，都会被追问打穿。**

## 六、常见扣分点（对着 9.9 的实测写的）

> 【事实】以下每条都在实测或复盘里出现过。**面试前 5 分钟扫一遍这张表，比再过一遍架构更有用。**

| # | 扣分点 | 表现 | 纠正 |
|---|---|---|---|
| 1 | **不问就答** | 听到题就开始画架构 | 先问 3–5 个"会改变方案"的问题 |
| 2 | **只讲优点不讲代价** | "加缓存提升性能" | 每个选择都说代价（不一致、故障点、内存成本） |
| 3 | **估算缺席** | 全程没有数 | 至少算峰值 QPS + 数据量 + 瓶颈层 |
| 4 | **面面俱到但都很浅** | 一次讲八个组件 | 主动划范围：**先做这三个，其余明确不做** |
| 5 | **一致性口径含混** | "保证强一致" 一句话带过 | **逐路径说**：这条强一致、那条最终一致（并给秒数） |
| 6 | **不提故障** | 假设一切可用 | 说清"某层挂了上游看到什么"+ 降级方案 |
| 7 | **没有指标** | 方案无法评价 | 给 3–4 个可观测指标 |
| 8 | **过度设计** | 1000 QPS 上分库分表 | **按量级判断，并主动说"这里不需要 XX"** |
| 9 | **术语堆砌但说不清机制** | "用 MVCC 解决" 却说不清解决什么 | 术语后面必须跟"它解决哪一个具体问题" |
| 10 | **被打断就慌** | 面试官插一句就丢掉主线 | 记下他的问题、**答完继续按原顺序讲** |

【取舍】**第 8 条值得单独说**：**"过度设计"和"设计不足"扣分的性质不同**——

```
设计不足 → 面试官追问一句就能补上（他看的是过程）
过度设计 → 他会认为你【没有按量级判断】的能力
         → 而这个能力恰恰是这一题最想考的
```

## 七、怎么练（用现成的题，别新建材料）

【推导】**练法只有一条：计时 + 闭卷 + 复盘**：

```
① 从 `wiki/interview/场景设计题库-十道母题.md` 抽一题
② 计时 10 分钟，**闭卷**按四段走一遍（口述、录音）
   澄清 2 分钟 → 拆解 3 分钟 → 估算 2 分钟 → 方案 3 分钟
③ 回听，对着第六节的扣分表打分
④ 只补断点：哪一段卡了，就去对应的母题卡补那一段
```

【取舍】**注意这条与全库纪律的关系**：**系统设计题的"练"不能替代母题卡的"练"** ——

```
系统设计题 = 【组装演练】（把已学的零件按顺序装起来）
母题卡     = 【零件制造】（每个零件本身的正确性）

零件不对，组装只会更快地暴露错误。
→ 所以顺序是：先把高相关的母题卡练到 integrated，再用这道题当"总装测试"。
```

【事实】**对应到 `questions.md`**：本卡由 **Q-2026-016** 驱动（见该条的状态）。**它不产生新的母题卡**——因为它的作用是把已有的卡串起来，而不是再加一张卡。
