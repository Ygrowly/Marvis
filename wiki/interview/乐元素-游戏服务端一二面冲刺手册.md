#### D · 八股恢复关键词（★ 9.9 考过且答砸的，必须能背）

| 题 | 恢复关键词 |
|---|---|
| ★ Linux 命令 | 四类：文件 `ls/find/grep -rn/tail -f`｜进程 `ps/top/kill/nohup`｜网络 `ss -lntp/curl/lsof -i`｜资源 `df -h/du -sh/free -m`；**排查一条线：top→ps→栈** |
| ★ Redis 数据结构 | String 计数锁｜Hash 对象属性｜List 队列栈｜Set 去重交集｜**ZSet 排行榜延迟队列（跳表+哈希）**｜另：Bitmap / HyperLogLog / Geo / Stream |
| ★ 乐观锁 vs 悲观锁 | 悲观：先加锁 `FOR UPDATE`/`synchronized`，写多冲突多｜乐观：不加锁，提交校验 **version / CAS**，行数为 0 即冲突｜**ABA → 版本号**｜取舍：重试成本 > 加锁成本时改悲观 |
| ★ HTTP 状态码 | **502 = 网关收到上游无效响应｜504 = 网关等上游超时｜503 = 服务不可用（过载/熔断/发布中），带 Retry-After**｜401 未认证 403 无权限 429 限流 |
| ★ SSE | **是长连接**（HTTP 持久连接，text/event-stream 单向推）｜vs WebSocket 双向｜自带重连（Last-Event-ID）｜坑：Nginx 关缓冲、发心跳 |
| 打开网页过程 | 四层：寻址 DNS → 建连 TCP + TLS 证书校验 → 请求（CDN/网关/缓存 304）→ 渲染（DOM+CSSOM→渲染树→布局→绘制） |
| MySQL 索引 | **B+ 树**（矮胖、叶子链表、范围扫快）｜聚簇索引 vs 二级索引回表｜最左前缀｜覆盖索引 `Using index`｜失效：函数/隐式转换/like %/or/不等 |
| MySQL 事务 | 隔离级别｜**MVCC = undo 版本链 + ReadView**｜RR 默认、RC 生成 ReadView 更频繁｜幻读 = 快照读 MVCC + 当前读 next-key lock |
| 项目栈是 PG 不是 MySQL | 说法：「项目里是 PG，堆表 + xmin/xmax + vacuum；MySQL 是索引组织表 + undo 版本链。原理同构，实现不同」 |
| Java | 「主力 Python，Java 写过 X 没上过生产；语言切换成本在生态不在语言本身」——**不说"有 AI 学得快"** |

#### E · 决策链 D1–D8（一行一条，只记关键词 + 复盘句）

| | 关键词 | 复盘句 |
|---|---|---|
| D1 | 幂等：四层唯一键 + **条件更新抢占** `WHERE status='pending'` | 幂等键选错，后面重试全是补丁 |
| D2 | 7 天回补：应到 vs 实到差集，走幂等通道 | 只补缺口，不全量重跑 |
| D3 | 优化：消重复 JOIN → 组合索引 → **预聚合** | 缓存是把慢结果暂存，预聚合是把计算提前 |
| D4 | 六阶段：①②⑥ 模型自主，③④⑤ 代码守不变量 | 边界划在"下个产出可独立验证"处 |
| D5 | 五层校验：入口→能力→调用→执行(只读账号+AST)→输出 | 便宜的在前，纵深收窄 |
| D6 | 证据绑定：`call_id + fingerprint + result_hash` | 回答的不是"对不对"，是"能不能被证明" |
| D7 | 确定性重放 + Oracle 独立裁决 | **声称者不能兼任裁判** |
| D8 | FSM + 业务身份幂等键 + 事件只追加 | 超时不换 key 盲重试 = 二次扣款 |

#### F · 游戏服务端 10 题（关键词 → 挂载句）

1. **排行榜**★：Redis ZSet｜复合分 `分×1e10+(MAX_TS-时间)`｜周期 key｜大榜分桶｜TopN 裁剪｜**防作弊**｜挂载：预聚合=排行榜快照
2. **体力**：惰性恢复（当前值 + 上次时间戳，用时算）｜按 uid 串行
3. **抽卡**：**服务端掷骰子**，配置表 + 保底计数器，客户端只做表现
4. **配置热更**：版本号 + 灰度 + 回滚｜挂载：EnergyOps dry-run 准入
5. **全服邮件**：模板 + 领取记录唯一键，靠唯一约束幂等｜错发走对冲 + 留痕
6. **签到防重**：条件更新 `WHERE day=N AND claimed=0`，行数=1 才发
7. **赠体力**：唯一键（赠者+收者+日期）防超次
8. **防作弊总纲**：规则校验(全量便宜) → 抽样重放 → 资产对账｜**目标是让作弊期望收益 < 成本**｜挂载：RuleArena 就是第②层
9. **断线重连**：token + 本地序号 + **写请求幂等**｜挂载：ACTION_UNKNOWN 超时语义
10. **分服架构**：无状态网关 → uid 哈希按区服路由 → 逻辑服分模块 → 热数据 Redis + 脏标记批量回写 + 关键操作实时落库

#### 1.2 三个事实与三句话策略

事实：①「java 优先」= 优先不等于必须，校招看的是基础与潜力；②JD 第 5 条把 AI 工具写进要求，全库只有我的简历天然命中；③这场面试 70% 的分数在**基础题 + 项目深挖 + 算法题**，都不依赖游戏经验。

策略三句话：

1. **基础不丢分**：网络、数据结构、OS、DB 的显性门槛题全部准备到「60 秒说清 + 能被追问一层」。
2. **项目换叙事**：三个项目的**事实一个不改**，把叙事重心从「Agent 治理」平移到「服务端工程」——幂等、状态机、定时任务、性能优化、安全校验本来就是服务端语言（第 4.2 节映射表）。
3. **Java 不装熟**：主动定位「主力 Python，Java 概念层扎实、语法可查」，用迁移故事收尾；概念题答对比装熟答穿强得多。
4. **痕迹 > 背诵**（2026-09-08 按 [[面试准备第一性原理]] 增补）：面试是证据采集，第 4.6 节决策链的「还想过什么 / 为什么放弃 / 重做改什么」比多背十道八股更值钱。八股的目标定在「60 秒说清 + 追问一层不塌」，不追求完美；省下的时间全部投给决策链挖写说和口述录音。

### 3. 消消乐业务专项（区分度最高，先建立全局）

#### 3.1 业务图景：先说对「这是什么形态的服务端」

开场就可能问「你了解开心消消乐吗 / 你觉得消消乐的服务端要做什么」。这段是地基：

> 乐元素 2009 年成立，北京总部，开心消消乐 2014 年上线、长线运营超十年的国民级三消手游，海外版 Anipop。它是**单机核心玩法 + 强联网运营**的休闲游戏：消除关卡本身客户端本地跑，服务端负责**进度结算与校验、体力、金币等资产、排行榜、好友、活动运营、支付**。所以它是**请求-响应式（短连接/HTTP 为主 + 少量推送）**，不是 MMO——**不需要帧同步**，并发压力来自海量玩家同时做简单请求（DAU 千万级），而不是单局内高频同步。

这句话的价值：一个没有游戏经验的候选人，上来就能做对「品类 → 架构形态」的判断，直接和对背八股的人拉开差距。追问「为什么不用长连接帧同步」→ 三消没有实时对战；帧同步/状态同步的适用边界见第 5 节第 1 题。

#### 3.2 消除核心算法（大概率手写/口述，第 9 节对应练习）

**本轮消除检测**（棋盘 `board[m][n]`，颜色 1-6，空=0）：

```text
marks = set()
对每个格子 (i,j)，若非空：
  向右统计连续同色数 run → 若 run>=3，把这段全部加入 marks
  向下统计连续同色数 run → 若 run>=3，把这段全部加入 marks
（横向纵向分开扫，交叉消除用 set 自动去重；特殊元素如直线特效/炸弹
 可建模为「消除后触发额外波及」，用队列做连锁触发）
```

**下落填充**：逐列处理，每列用双指针——写指针 `w` 从列底向上找第一个空位，读指针 `r` 在其上方找第一个非空元素，搬到 `w`；列顶剩余空位补新随机元素（或关卡预设）。

**连锁反应（cascade）**：`while true { if 检测为空 break; 消除→计分→下落 }`，连消次数影响分数倍率。

**死局检测与洗牌**：枚举每个格子与「右邻、下邻」交换一次，交换后跑一次检测，存在任何可消交换 → 可解；否则洗牌，洗后需保证「可解且不会立即自动消除」。一次检测 O(mn)，死局检测 O(mn×2) 次交换 × O(mn)，休闲棋盘规模完全可接受。

**步数与结算**：步数是资源，用尽或达成目标（收集 X 个某元素）结束；结算要区分「客户端表现动画」与「服务端权威数值」（见第 5 节第 6 题）。

#### 3.4 高并发与稳定性（开心消消乐体量下的追问链）

- **入口**：无状态接入层/网关 → 按分服（区服）路由到逻辑服；逻辑服内部再按玩法/模块拆服务。**分服是休闲游戏最常用的水平扩展手段**：uid 哈希到区服，天然隔离故障与热点。
- **缓存三问**（必考）：穿透（不存在 key → 空值缓存/布隆过滤器）、击穿（热 key 过期 → 互斥重建/逻辑过期）、雪崩（批量过期/缓存宕机 → 过期加随机、多级缓存、限流降级）。
- **热 key**：某活动瞬间全服读 → 本地缓存 + 随机副本 key + 限流。
- **落库策略**：玩家数据写 Redis/内存（脏标记），定时批量回写 + 关键操作（支付、通关）实时落 MySQL；停服维护时全量落地。
- **大表**：玩家数据按 uid 分库分表；排行榜等热数据外置 Redis。
- **限流与降级**：入口令牌桶/漏桶；活动高峰降级非核心功能（如排行查询走缓存快照）。
- **可观测**：请求量、耗时 P95、错误率、队列积压——直接迁移 EnergyOps 的 SLO 语言。

#### 4.3 每个项目的 60 秒服务端版开场（细节仍回原项目说明）

**EnergyOps（主推，最像游戏服务端日常）**：
> 我讲讲它的服务端部分。这是一个对接 604 台水电表的数据平台，核心是**按 15 分钟周期的定时聚合**，类似游戏里的周期结算。三个工程问题我各做了一个机制：一是**幂等**，任务重跑不能重复聚合，用幂等窗口约束；二是**恢复**，服务重启会漏任务，我把任务状态持久化，启动时自动回补 7 天，聚合成功率从 96.9% 到 99.6%；三是**性能**，统计接口一开始 20 秒，我把重复 JOIN 和全表扫描消掉、加了组合索引和预聚合，P95 到 2.8 秒。这套「周期任务 + 幂等 + 恢复 + 预聚合」的组合，我认为就是游戏服务端运营侧的日常。

**数驭穹图（协议与安全）**：
> 它的服务端链路分六个阶段，每阶段有明确契约，出了错能归因到具体层。我印象最深的是安全层设计：客户端传来的任何输入都不被信任，从权限、参数 Schema 到只读 AST 审查共五层校验，300 条对抗请求全部拦截、正常误拦只有 2.7%。这和游戏服务端校验客户端请求是同一件事——**协议要分层，校验要闭环，错误码要可区分**。

**RuleArena（与防作弊同构，二面杀手锏）**：
> 这个项目解决一个问题：**一个行为的声称者不能同时是它的裁判**。Agent 声称发现了漏洞，必须拿到干净的确定性环境里真实重放、由独立裁决程序判定才算数。映射到游戏：客户端上报「我这局得了 3 万分」，服务端不能直接信，要么用规则校验合理性，要么对关键操作做重放验证。我做的正是后者的工程化版本：状态机、幂等键、事件只追加、确定性裁决。

### 5. 游戏服务端专题 60 秒答案（8 题）

**Q1 帧同步 vs 状态同步？**
L0：确定性模拟 vs 权威状态广播。60 秒：状态同步由服务端跑权威逻辑，广播结果状态，客户端表现，安全但流量大；帧同步服务端/玩家只广播输入指令，各端跑确定性模拟，流量小、利于回放观战，但要求浮点/随机一致性且防作弊弱。**选型**：强实时对战（MOBA/射击）用帧同步或权威帧同步；回合制、卡牌、三消这类**请求-响应式玩法用状态同步甚至纯 HTTP 结算**。消消乐：单机玩法本地跑，服务端做结果校验与资产结算。

**Q2 消消乐选长连接还是短连接？**
L0：短连接为主 + 少量推送。60 秒：三消没有局内实时同步需求，交互是「进关卡→打完→上报→领结算」的低频请求-响应，HTTP(S) 短连接足够，运维简单、天然过网关和负载均衡；需要服务端主动推的少数场景（好友赠体力提醒、活动推送）用长连接推送或客户端轮询/厂商推送通道兜底。若追问「为什么不干脆全长连接」：海量大 DAU（ **每日活跃用户数量**） 下长连接的维持成本（心跳、网关内存、断线重连）远大于收益。

**Q3 TCP 粘包拆包怎么办？**
L0：TCP 是字节流，无消息边界。60 秒：应用层自己定界，四种方案——固定长度、分隔符、**长度前缀（header 带 body 长度，最常用）**、协议自带（如 HTTP 的 chunked）。游戏里自定义二进制协议一般是 `len + msgId + version + body(protobuf)`。收到半个包先缓存，凑齐再解。

**Q4 心跳与断线重连怎么设计？**
L0：心跳探活 + 幂等重连。60 秒：客户端定时发心跳，服务端超时未收到则判离线并释放资源；重连时客户端带会话 token 和本地已处理的指令序号，服务端校验身份后补发增量状态；**所有写请求必须幂等**（请求唯一键），因为重连前最后一条请求是否到达服务端是不确定的——这正是我在 EnergyOps 做的幂等窗口 + 状态持久化 + 回补。

**Q5 Protobuf vs JSON？**
L0：二进制 vs 文本。60 秒：Protobuf 体积小（varint【可变长度整数-用于压缩整型数值的编码】、字段号）、编解码快、schema 强约束多端一致，适合高频游戏协议；JSON 可读性好、调试方便，适合运营后台和管理接口。游戏内协议 Protobuf、对外/后台接口 JSON 是常见组合。

**Q6 防作弊：客户端上报的分数能信吗？**
L0：不信任，服务端权威。60 秒：三道防线——①**规则校验**：分数/步数/用时是否超出该关卡的物理上限；②**关键步骤校验**：消除操作序列服务端可重算或抽样重放；③**资产一致性**：奖励发放走服务端结算并留流水。高级方案是把核心逻辑做成服务端确定性模拟（RuleArena 思路：声称者不能兼任裁判）。同时说边界：三消单机玩法全量重放成本高，业界常做抽样 + 举报驱动的深查。

**Q7 游戏服务器里的定时任务怎么做？**
L0：时间轮/优先队列 + 持久化。60 秒：大量玩家定时器（体力恢复）用**惰性计算**（读取时按时间戳算，不真起定时器）；全局定时任务（日结算、赛季）用调度中心 + 分布式锁；海量短期定时器用时间轮。关键都是：任务状态要持久化、执行要幂等、错过要能补——我在金山做的就是这套。

**Q8 消息推送/全服广播怎么扛量？**
L0：分批 + 队列削峰。60 秒：全服邮件/公告不逐个写玩家库，用「模板 + 领取记录」；在线推送按分区分批；用 MQ 削峰，消费端幂等。高峰期降级非核心链路。

### 6. 网络与 TCP/IP 必答题（一面基本盘，12 题）

> 每题先背 L0 关键词，再用 60 秒展开。来源建议：小林 coding《图解网络》对应章节（第 11 节）。

1. **三次握手**：SYN→SYN+ACK→ACK。为什么三次：确认双方收发能力 + 同步初始序号 + 防止历史重复连接初始化。
2. **四次挥手**：FIN→ACK→FIN→ACK。为什么四次：TCP 全双工，两个方向分别关闭；主动方收到 FIN 后进 TIME_WAIT 等 2MSL（最大报文生存时间）——保证最后 ACK 可达 + 让旧报文消亡。
3. **TIME_WAIT 过多**：端口耗尽/内存；解法：连接复用（keep-alive、连接池）、`SO_REUSEADDR`、调大端口范围。
4. **TCP 怎么保证可靠**：序号+确认应答、超时重传/快速重传、滑动窗口流量控制、拥塞控制（慢启动、拥塞避免、快恢复）、校验和去重排序。
5. **TCP vs UDP + 游戏选型**：TCP 面向连接可靠有序、拥塞控制；UDP 无连接、开销小、实时性好、可自定义可靠性（KCP/QUIC）。对战同步选 UDP，请求-响应和资产操作选 TCP/HTTP。消消乐用 HTTP(TCP) 足够。
6. **HTTP 报文与方法**：请求行/头部/体；GET 幂等取资源、POST 提交；PUT/DELETE 语义；游戏接口一般 POST + 签名。
7. **HTTPS 握手**：TCP 后协商（TLS：交换随机数与证书、验签、算出对称密钥）→ 之后对称加密通信；防窃听/篡改/冒充。
8. **常见状态码**：200/301/302/400（参数错）/401（未认证）/403/404/429（限流）/500/502（网关到上游失败）/504（上游超时）。游戏接口常自定义业务错误码 + HTTP 200，要能说取舍。
9. **长连接心跳**：应用层心跳包定时保活，检测半开连接（对端异常掉线 TCP 本身感知不到）；Nginx/网关 idle timeout 要大于心跳间隔。
10. **select/poll/epoll**：IO 多路复用让单线程管理大量连接；epoll 红黑树+就绪链表，事件驱动，避免每次全量扫描——高并发网关（Netty/Redis/Nginx）的地基。
11. **从输入 URL 到页面显示**（串联题）：DNS→TCP 握手→TLS→HTTP 请求→网关→服务端→DB/缓存→响应渲染。用这条线把上面所有点串成 2 分钟叙述。
12. **签名与防重放**：参数排序 + 时间戳 + nonce + 密钥 HMAC；服务端校验时间窗与 nonce 去重——游戏接口防改包基本功。

#### 7.2 概念级必答题（答出机制 + 一句对比即可）

1. **OOP 三大特性**：封装（隐藏内部状态）、继承（复用与扩展）、多态（父类引用指向子类实现，运行期动态绑定）；再加接口与抽象类区别（接口多继承行为契约，抽象类单继承共享实现）。
2. **HashMap 原理（1.8）**：数组 + 链表 + 红黑树；put 对 key 取 hash 定位桶，冲突挂链，链长 ≥8 且容量 ≥64 树化；负载因子 0.75、扩容翻倍 rehash；1.8 改点：尾插法（防环）、树化。线程不安全 → 并发用 ConcurrentHashMap。
3. **ConcurrentHashMap（1.8）**：放弃分段锁，Node 数组 + CAS + synchronized 锁单个桶头；读不加锁；size 用计数。
4. **ArrayList vs LinkedList**：动态数组随机访问 O(1)、尾插均摊 O(1)、中间插删 O(n)；LinkedList 双向链表头尾插删 O(1)、随机访问 O(n)；实际几乎总选 ArrayList（缓存友好）。
5. **String 为什么不可变**：final char/value 数组不暴露；好处：字符串常量池复用、hashCode 缓存、线程安全、作为 map key 稳定。
6. **equals 与 hashCode**：契约——equals 相等则 hashCode 必须相等；不重写 hashCode 会导致 HashMap 行为错误。
7. **异常体系**：Throwable→Error（不捕获）/Exception；Exception 分受检（编译强制处理，IOException）与运行时（RuntimeException，NPE/越界）；try-with-resources 自动关闭资源。
8. **JVM 内存区域**：堆（对象，GC 主战场，分新生代/老年代）、虚拟机栈（栈帧、局部变量）、方法区/元空间（类信息）、程序计数器、本地方法栈。线程私有 vs 共享要能分清。
9. **GC 一句话版**：可达性分析判活；分代假设→新生代复制算法（Eden+S0/S1，Minor GC），老年代标记整理/清除（Major/Full GC）；收集器认识名字即可（CMS、G1、ZGC：G1 分 Region 可预测停顿，ZGC 低停顿）。对象晋升：年龄阈值、大对象直入老年代。
10. **volatile vs synchronized**：volatile 保证可见性 + 禁止指令重排、**不保证原子性**（i++ 仍不安全），适合状态标志；synchronized 互斥 + 可见性，锁对象/方法/类。扩展：CAS 与 ABA 一句话。
11. **线程池参数**：corePoolSize、maximumPoolSize、keepAliveTime、workQueue、拒绝策略；执行顺序（核心→队列→扩到 max→拒绝）；为什么不用 Executors 默认工厂（无界队列/无限线程风险）。
12. **ThreadLocal**：线程私有副本，底层 ThreadLocalMap，key 弱引用；用完必须 remove，防止线程池复用导致脏数据与内存泄漏。

### 8. 数据库 / Redis / OS 必答题（8 题）

### 第 1 节三项目「去 Agent 主语」服务端叙事（每个 60 秒）

> 用法：面试官问「你做的事跟我们的服务端有什么关系」时，直接背这段，不要临场翻译。

#### 1.1 EnergyOps = 定时聚合系统 + 数据治理链路

> 把它当成服务端看就三个问题。
>
> 第一，进来的数据不可信。604 台表三种脏数据最常见：某台表掉线导致整个窗口缺失、读数倒转或突跳、换表或变更倍率导致量纲突变。我定义了 7 类质量状态，每个采集点进聚合前先判定，只有可信的才参与计算，脏数据标记但不删、留着溯源。
>
> 第二，定时任务不可靠。15 分钟一个窗口，任何一次重跑、重启、多 worker 并发都会算重或漏。我用「设备 ID + 聚合窗口」做唯一键走 upsert，重跑一百次也只有一行；任务领取用一条条件更新抢占，UPDATE 加 WHERE status 等于 pending，谁改到那行谁执行，数据库的行级约束替我解决并发，不需要分布式锁。
>
> 第三，查询太慢。原来是每次查询都从明细现算，还重复 JOIN 设备维表。做完三件事：去掉重复 JOIN、加组合索引（等值列在前、范围列在后）、小时和日的结果预聚合落表，查询只读结果表。P95 从 20.4 秒到 2.8 秒，降了 86%。
>
> 还有一块我自己认为最关键的：启动时的 7 天自动回补。调度器重启只会接着跑未来的任务，宕机期间错过的历史窗口会永久缺失，这在结算类系统里是不能接受的。我对账最近 7 天应该产生而实际没有的窗口，差集就是缺口，按低优先级补算，走同一套幂等通道所以不会重复聚合。
>
> 复盘句：这套东西放到游戏里就是日结算和周期榜，定时、幂等、可恢复，三个词一个都不能少。

#### 1.2 数驭穹图 = 多租户查询网关 + 只读执行引擎

> 剥掉 AI 的外壳，这是一个多租户的查询网关：上游接 MySQL、PostgreSQL、MongoDB、飞书表格等 6 类数据源，中间一层查询引擎，出口管权限、限流和脱敏。三个工程难点。
>
> 一是方言收敛。不同源在分页、时间函数、类型转换上都不一样，我没有让上层去写方言分支，而是把差异收到一层统一的中间计划里，执行前再翻译成目标方言，差异只有一处，不散落在业务代码里。
>
> 二是不能拖垮客户的生产库。客户库有的就是正在跑业务的生产库。我做的是：优先查本地 Parquet 副本；必须直查时用只读账号；执行前先 EXPLAIN 估算代价，超阈值直接拒绝；再加超时和行数上限熔断。这跟只读从库扛查询流量是一个思路。
>
> 三是权限不能靠口头约定。租户 ID 由服务端注入，不是从上层传进来；执行层只给只读账号，再用 SQL AST 审查做兜底，就算前面全漏了，到这一层也写不了库。输出按行列权限裁剪后再脱敏出来。
>
> 数字：端到端查询成功率 78% 提到 91%，300 条对抗危险语句拦截 100%，正常查询误拦 2.7%。
>
> 复盘句：服务端永远不信任上游给的身份，权限必须由服务端自己写入，这条在游戏里同样成立。

#### 1.3 RuleArena = 确定性重放引擎 + 不变量裁决器

> 这个项目剥掉 AI，剩下的是一个确定性重放引擎加不变量裁决器。
>
> 背景是电商规则变更：很多事故不是单条规则错，而是优惠券、退款、积分在特殊顺序下组合出错，单测只覆盖你想到的路径。
>
> 做法是：先把规则编译成一份不可变的执行契约，然后让程序去搜动作序列，搜到的候选不能自己说了算，必须拿到一个干净环境里用真实 HTTP API 重放一遍，由一个独立的裁决器按资金守恒、状态生命周期、幂等这三类不变量来判。
>
> 两个服务端关键点。一是写操作必须有幂等键，我用业务身份合成：run_id 加动作类型加目标对象加归一化参数加规则版本加步骤号，配数据库唯一约束。一开始用调用 ID 当键是错的，重规划和超时重试都会生成新 ID，同一个动作就有了好几个身份。二是超时语义，写操作超时后你分不清是没送达、失败、还是成功但响应丢了，做法是拿同一个幂等键去查回执，查不到才敢重试，绝不能换 key 盲重试，因为请求可能已经生效。
>
> 复盘句：这条在游戏里就是防作弊的最高形态，声称者不能兼任裁判。玩家上报「我这局 3 万分」，你要么做合理性校验，要么确定性重放，不能直接信。

### 第 2 节十二条新增追问标答（D1-D8 没写的，按星级背）

> 三星必背，大概率被问；二星备着。

#### E-A 三星 · 数据是累计读数，表倒转、换表、改倍率怎么处理？

> 因为源头是累计读数不是区间用量，所以第一步必须做差分：用「本次读数减上次读数」得到这个窗口的实际用量，再做三类校验。
>
> 一、回退：差值小于 0，说明抄错或者表被拆装过，判为回退类脏数据，不进聚合。
>
> 二、长间隔：两个相邻读数的时间跨度超过窗口上限，这份差值不能算作某一个 15 分钟窗口的用量，要做分摊或者直接标不可信。
>
> 三、倍率变更：换表或者变更 CT 变比之后，读数会出现一次量纲级跳变，如果不处理，聚合出来的能耗会凭空涨几十倍。我的做法是给设备维护一个「有效倍率区间」，检测到疑似跳变就判为质量状态里的倍率变更类、先不进聚合，等人工确认后开启一个新的有效区间继续算，历史数据不回改。
>
> 复盘句：累计读数的系统一定要做分段，只要设备的物理属性变了，之前的数据和之后的数据就必须属于不同的有效区间，不能用一个公式算全场。

【核对】以上判定细节是按简历里「7 类质量状态（缺失、回退、长间隔、倍率变更、异常跳变等）」重建的合理版。考前核对真实的字段名和判定方式，阈值记不准就说「具体阈值是跟业务对齐过的」，不要现编数字。

#### E-B 三星 · 15 分钟周期，数据迟到、乱序怎么办？

> 第三方平台补数是常态，所以不能假设数据按时间顺序到达。我的处理是容错窗口加幂等覆盖：聚合结果落地后不是终态，允许一定窗口内的迟到数据回流并重算；因为写入是「设备 ID + 聚合窗口」唯一键的 upsert，迟到数据修正旧值不会产生第二条记录，天然幂等。超过容错窗口的数据就不再按小时粒度回溯了，标记不可信走人工补录，或者并入下一次的日粒度重算。
>
> 复盘句：乱序系统的原则是，修正的路径必须和写入的路径是同一条。你只要为补数据单开一条更新逻辑，重复计算只是时间问题。

#### E-C 二星 · 604 台设备同时上报，写入怎么扛？

> 这个量级其实不大：604 台乘以 15 分钟一次，峰值每分钟几百条写入，单机 PostgreSQL 完全够。真正要注意的不是吞吐，是事务粒度和连接管理，批量 upsert、单事务提交，避免一条一个事务；连接走池化，不让每个采集任务新建连接。批次本身也是幂等的，重试不会产生重复行。
>
> 复盘句：教训是别一上来就上消息队列和分库分表，先把写入粒度、事务边界、连接池这三件事做对，量没到之前，多引一个组件就多一个故障点。

#### E-D 二星 · 7 类质量状态怎么定的？为什么不是 3 类或 20 类？

> 不是拍脑袋，是对着真实脏数据倒推的：把历史数据跑一遍，所有导致聚合结果偏离的样本拿出来归类，归到「同一类问题、同一种处理方式」才合并，处理方式不同的就拆开。比如缺失和长间隔虽然都是没数，但缺失是确定没有任何数据、长间隔是有头尾但跨度超限，处理动作完全不同，就必须是两类。所以 7 类的划分标准是：处理动作不同才配成为一类。这也是我不再往下加的原因，加一类就意味着多维护一套补偿逻辑。
>
> 复盘句：状态码的价值不在数量，在于每一类都对应一个确定的处置动作。如果一个状态只有人看、机器不知道怎么办，那它就不该存在。

#### S-A 三星 · 慢查询会把客户生产库拖垮，你怎么防？

> 四道防线，从便宜到贵。
>
> 一、优先本地副本：数据有 Parquet 落盘，绝大多数分析查询打本地引擎 DuckDB，根本不碰客户库。
>
> 二、必须直查时先 EXPLAIN 估算：扫描量或预估代价超阈值直接拒绝，不让重查询进入执行。
>
> 三、只读账号加执行超时加行数上限：就算放行了，也写不了库、有执行时间天花板、结果集有上限。
>
> 四、熔断与配额：单租户连续慢查询触发降级，后续查询走副本或排队；不同客户独立配额，一个打满不影响别人。
>
> 复盘句：原则是把保护放在离资源最近的地方，外层的权限和校验再全，也不如一个只读账号加一句执行超时来得踏实。

#### S-B 二星 · 6 类数据源的方言差异怎么收敛？

> 不是在业务代码里写 if mysql else postgres，那样改一个方言要动十个地方。做法是把差异收进一层中间表示：上层产出的是跟方言无关的中间计划，到执行前的最后一环才翻译成目标方言，方言适配是配置不是代码分支。最难处理的三类：时间函数和时区、分页语法、类型转换和 NULL 语义。真遇到翻译不了的能力，就明确报错而不是退化成差不多的 SQL，错误的查询不如拒绝执行。
>
> 复盘句：跨源系统的取舍只有两个答案，差异要么收在一处，要么散在十处，没有中间地带。

#### S-C 二星 · 大结果为什么不能直接放进上下文？

> 两个原因。一是成本：几万行的结果塞进去既贵又慢，处理质量还会下降。二是正确性：大结果进入上下文之后，模型看到的只是其中一段，很可能拿局部数据下全局结论。我的做法是把大结果外置成一个产物，有热、温、冷三级生命周期，上层只拿到口径摘要和聚合统计（行数、时间范围、总量、Top 分布），要看明细按引用取。同时给结果做哈希绑定，证明这段数据确实来自某次真实执行。
>
> 复盘句：一条通用规则是，任何展示给用户的数据，都必须能追溯到一次真实执行，而不是追溯到一段文本。

#### S-D 二星 · 权限撤销了，之前生成的快照和导出怎么办？

> 分两类。在线内容（还在有效期的数据产物）撤销即时生效，下次访问重新走一次权限校验，而不是查缓存下来的结论。已经外发的静态文件（导出的表格、分享链接）从设计上就带有效期并绑定策略版本，到期自动失效；期间发现误发就吊销引用，而不是去删数据。核心原则是：权限检查的结果不要持久化成「这个人能看」的结论，每次访问都要重新判。
>
> 复盘句：权限这件事上，缓存校验结果是收益最小、风险最大的优化。

#### R-A 三星 · 重放怎么保证确定性？随机、时间、外部依赖怎么办？

> 确定性不是靠运气，是把所有不确定源都变成输入。三条措施：
>
> 一、所有随机必须有种子。概率、随机策略都走同一条伪随机序列，种子记录在运行元数据里，重放时序列完全一致。
>
> 二、时间不能被直接读取。业务代码取的是一个可注入的逻辑时钟，每次运行有自己的时间轴，不依赖墙钟。
>
> 三、外部依赖全部打桩。第三方调用、网络响应都在环境内做确定性实现，同样输入必然得到同样输出。
>
> 另外每个环境用完就销毁，两次运行之间不共享残留状态。
>
> 复盘句：判断一个系统能不能被重放，就看三件事，随机数从哪来、时间从哪来、外部调用有没有打桩。这三个口子没堵上，重放结果就不可信。

#### R-B 三星 · 24 个 Case 会不会过拟合？怎么说明机制可信而不是记住答案？

> 单看 24 个 Case 确实不够，所以我做了三件事。
>
> 一、双集隔离：开发集 16 个开发期可用，隐藏集 8 个与运行时物理隔离，开发侧根本读不到，防止对着考纲训练。
>
> 二、归一化预算的消融：不同策略（随机、广度优先、单策略、多策略）在同一个动作预算下比，比的不是谁答得对而是同等代价下谁找得到，预算不公平的对比没有意义。
>
> 三、多次独立重放：同一个样本重跑 3 次结果必须一致，证明发现不是靠运气。
>
> 但我也要说清边界：发布门禁承诺的是「预算内未发现」，不是「规则必然安全」。通过门禁只代表在这个预算、这些策略、这组不变量下没有找到违规而已。这一点我在文档里写得很明确。
>
> 复盘句：评测集的价值不在通过率，在于它能区分策略之间的优劣。如果所有策略都是满分，那说明题太简单或者漏题了。

#### R-C 二星 · 确认有问题之后，怎么把报告压到最小？

> 用删除式 Delta Debugging：对找到的违规动作序列，逐步删除其中的步骤，每删一次重跑一次裁决，只要违规还成立就保留这次删除，删到再多删任意一步违规就消失为止，最后得到的是最小复现路径。这个过程能自动化，前提是重放和裁决都是确定性的，删一步重跑的代价可控。反例沉淀成回归用例，修复版本自动重放历史反例。
>
> 复盘句：缺陷报告的价值和它的长度成反比。一个要十步才能复现的问题，报上去很可能没人读；压到三步，修的人当天就能动手。

#### R-D 二星 · FSM 里的 Checkpoint 到底存什么？恢复后会不会重复扣款？

> Checkpoint 存的是执行进度（当前在哪个节点、已经规划了哪些动作、预算用了多少），不是业务状态，业务状态一直在服务端的权威数据库里。所以恢复时不需要拿状态去补偿，而是重新读权威状态。防重复副作用的防线是幂等键加数据库唯一约束：同一个业务动作第二次执行会撞键冲突，直接返回上一次的结果。
>
> 这就引出超时语义：超时不等于失败，可能已经成功了只是响应丢了。正确做法是拿同一个幂等键去查回执，查到已完成就接受，查到被拒就按错误处理，查不到才敢重试，查不了就标记未知并停掉这个分支，绝不会换个 key 重发。
>
> 复盘句：状态机和业务数据要分开管的是，状态机存的是进度，业务结果存在权威数据里。前者丢了可以重跑，后者丢了就是事故。

### 1. 决策链口述稿 D1–D8

#### D1 · EnergyOps：定时聚合的幂等设计

**面试官问法**：定时任务重跑/漏跑怎么兜？幂等具体怎么做的？

**口述稿（90 秒）**：

> 能耗数据是 15 分钟一个采集点，聚合按小时/日做，天然会有三类重复风险：任务重跑、服务重启恢复、多 Worker 并发抢任务。我的做法是**分层幂等**：Raw、Hourly、Daily、Task 四层，每层都有唯一业务键——比如小时聚合的键就是"设备 ID + 聚合窗口"，写入用确定性 upsert，重跑一百次也只有一行。这里有个真实踩坑：一开始防并发是"先查有没有 pending 再插入"，结果两个 Worker 同时发现同一个小时缺口，都查到没有、都去插，任务执行了两遍。**后来改成一条带条件更新抢占：`UPDATE ... WHERE status='pending'`，受影响行数等于 1 的 Worker 才有执行权**，数据库的行级约束替我解决并发，也就不需要引分布式锁。还有一个坑是"只成功一半"：小时表更新了、任务状态没更新，重启后就重复执行；反过来 Daily 成功了、Hourly 回滚了，上下游数据版本就不一致。**最后把本地多表写全部收进一个事务，并给聚合结果带版本号**——原子性和一致性是两个问题，得分别兜住。（复盘）重做一次我会把幂等键的设计放到最前面：键选错了，后面所有重试逻辑都是补丁。

**追问兜底**：为什么不用分布式锁？——数据库唯一约束 + 条件更新在单库场景下更简单可靠，锁是跨服务才需要的。

#### D2 · EnergyOps：启动 7 天自动回补

**面试官问法**：为什么是 7 天？回补时上游数据变了怎么办？会不会重复聚合？

**口述稿（90 秒）**：

> 背景：普通调度器重启后只会"接着跑未来的任务"，**服务宕机期间错过的历史窗口会永久缺失**——这在结算类系统里是不可接受的，游戏里的日结算、赛季榜同理。所以我在服务启动时做一次对账：扫描"最近 7 天每一个应该产生的聚合窗口 vs 实际已完成的窗口"，差集就是缺口，按低优先级排队补算。两个设计点：一是**回补走幂等通道**，用的就是 D1 那套唯一键 upsert，所以补算天然不会重复聚合；二是**只补缺口不全量重跑**，全量重跑会争抢实时写入库的资源、还会重复触发下游通知。（对比）当时考虑过全量重算，放弃的原因就是成本和副作用；也考虑过上游给变更流，但外采数据源不支持。（复盘）完整率从 96.8% 提到 99.7%，这 3 个点基本就是回补和质量白名单挣回来的。【核对：7 天这个数字的原始依据——建议说法："取的是覆盖最长一次真实停机加上游补数周期的保守值"】

#### D3 · EnergyOps：P95 20.4s → 2.8s 的优化

**面试官问法**：一开始为什么慢？怎么定位的？为什么选预聚合不选缓存？

**口述稿（90 秒）**：

> 定位靠 EXPLAIN：两个元凶，一是**查询里重复 JOIN**——同一批设备维表被 JOIN 了多次；二是**大范围全表扫描**——每次查询都对原始明细从零聚合。解法三层：消掉重复 JOIN、先过滤再聚合缩小扫描面、加组合索引把过滤条件排前面（等值列在前、范围列在后）；最关键的是**预聚合**——小时/日粒度的结果提前算好落表，查询时只查聚合结果，P95 从 20.4 秒到 2.8 秒。【核对：定位过程建议补一句你真实的第一步，比如"先看慢查询日志排序"】（对比）为什么不加缓存？缓存解决的是"同一个查询反复查"，但我们的慢根因是"每次都从明细现算"——缓存只是把慢查询的结果暂存，预聚合是把计算提前；而且统计场景数据更新频繁，缓存失效逻辑会很复杂。预聚合表本质上是拿写入侧一点成本换读取侧确定性性能，这个取舍和游戏排行榜做快照是同构的。（复盘）重做会先做完整的慢查询画像再动手，不凭直觉优化。

#### D4 · 数驭穹图：为什么六阶段，不端到端

**面试官问法**：一个大 prompt 端到端不行吗？为什么拆六阶段？

**口述稿（90 秒）**：

> 我们试过两个极端，都被否了。**完全固定 Pipeline**：应对不了自然语言的变化，问法一换流程就断；**完全自主 Agent Loop**：路径不稳定、成本不可控、该守的前置条件容易被绕过。最后是混合 Runtime：链路拆成六个阶段——意图路由、域内检索、计划确认、SQL 静态校验、受控执行、解释与证据绑定。**①②⑥ 让模型自主，③④⑤ 由确定性代码主导**——代码守住不变量（SQL 只读、资源限额），模型处理局部语义决策。拆段的核心理由是**可归因**：端到端方案失败了，你只知道"答案错了"，不知道错在理解、检索还是 SQL；六阶段每一层有独立契约和错误码，一次失败精确定位到层，Bad Case 定位从 30 分钟降到 8 分钟。本质上把"业务理解对不对"和"SQL 写得对不对"拆成了两个独立可验证的问题——这和游戏服务端把协议分层、每层有自己的错误码是同一个道理。（复盘）段数不是拍脑袋说越细越好，边界划在"下一个产出可以独立验证"的地方。

#### D5 · 数驭穹图：五层安全校验

**面试官问法**：五层各拦什么？去掉一层会怎样？为什么这个顺序？

**口述稿（90 秒）**：

> 原则是**纵深防御，由外向内逐层收窄，便宜的在前**。入口层：身份、租户、配额——不是合法用户直接出局，成本最低；能力层：Agent 只能调注册过的工具，能力边界是白名单不是模型自觉；调用层：把 Tool Call 当不可信输入，Schema 校验 + Validator，tenant_id 由服务端注入而不是信模型传的；执行层：数据库用只读账号 + SQL AST 审查 + 超时/行数/扫描量限制——就算前面全漏了，到这里也写不了库、拖不垮库；输出层：敏感字段脱敏 + 证据绑定。300 条对抗用例全部拦截，误拦率 2.7%。【核对：去掉一层会怎样——建议准备两层：去"执行层"则一条变形 SQL 就打到生产库（我们真实遇到过慢 SQL 拖库风险，靠只读副本 + statement timeout 熔断兜的）；去"调用层"则越权工具调用没有闸门】（复盘）顺序的依据是"越往内、单次校验越贵、但拦的威胁越致命"，所以外层先用便宜规则过滤绝大部分流量。

#### D6 · 数驭穹图：证据绑定（call_id + query_fingerprint + result_hash）

**面试官问法**：为什么三重绑定？只存 SQL 或只存结果不行吗？

**口述稿（60 秒）**：

> 动机是一句话：**合法 JSON 不等于可信图表**。模型的结构化输出只保证字段存在，不保证这个数值真的来自一次真实查询、没被模型脑补、结果是完整的。所以做了三重绑定：call_id 证明来自哪次调用，query_fingerprint 证明是哪个查询，result_hash 证明数据没被改写——三者一致才渲染图表，任一失败降级成占位块，绝不假装有数。（对比）只存 SQL 不行，因为同样的 SQL 执行两次结果可以不同；只存结果不行，因为你不知道它是怎么来的。（复盘）100 条抽检复现一致率 100%，这个机制后来成了整个平台"结果可信"的底线——它回答的不是"答案对不对"，而是"这个答案能不能被证明"。

#### D7 · RuleArena：确定性重放，不让 LLM 自己判

**面试官问法**：为什么不让 LLM 评判对错？重放环境怎么保证确定性？

**口述稿（90 秒）**：

> 核心原则一句话：**声称者不能兼任裁判**。Agent 说"我发现了漏洞"，这个声称本身不可信——模型会错误推理，也会犯错。LLM Judge 适合评语义质量（这段文案好不好），但裁决资金安全这种事，判例必须可复现，概率性判定不行。所以我的架构是：被测 Agent 在 Sandbox 里执行，Oracle 裁决器**独立部署**、以冻结版本的 RuleSpec 为基准做确定性判定，裁决依据只认四样东西：Sandbox 返回的 ActionReceipt、数据库权威状态、BusinessEvent 事件、同版本独立重放结果——完全绕开模型的自我评价。有个真实案例很典型：第一版黄金用例里，退款恢复了优惠券但**没有撤销订单赠送的积分**，用户拿回全部实付还白拿了权益，违反奖励守恒；第二版在退款事务里补上积分撤销，按冻结的规则版本处理券恢复。这个案例就是我整个项目的演示主线：**模型猜出来的 ≠ 确定性证明出来的**。（映射）这和游戏防作弊同构：客户端上报"我这局 3 万分"，服务端要么规则校验合理性，要么确定性重放验证，不能直接信。

#### D8 · RuleArena：FSM + 幂等键 + 事件只追加

**面试官问法**：为什么用显式状态机？幂等键怎么设计？ACTION_UNKNOWN 是什么？

**口述稿（90 秒）**：

> 三个设计，一个主题：**写操作的可靠性**。第一，主流程用显式 FSM 而不是自由 Agent 流——因为写资金的生命周期有限，状态和失败语义必须清晰，出问题知道卡在哪一步、能从 Checkpoint 恢复；自由流程调试是噩梦。第二，幂等键踩过一个真实的坑：**一开始用 ToolCallID 当幂等键，发现不行**——重规划、重启、超时重试都会产生新的调用 ID，同一个业务动作就有了好几个"身份"。正确做法是基于业务身份合成键：run_id + 动作类型 + 目标对象 + 归一化参数 + 规则版本 + 逻辑步骤号，配合数据库唯一约束防并发穿透，同一事务里写聚合、账本、回执、事件四张表。第三，超时语义：写操作超时后无法区分"没送达、失败、还是成功了但响应丢了"——**用同一个幂等键去查回执**：已完成读快照继续、被拒按错误重试、查不到才敢用同 key 重试、查不了就标记 ACTION_UNKNOWN 停止分支，绝不能换 key 盲重试，因为请求可能已经生效，重试就是第二次扣款。事件只追加是为了审计：历史不可改，错了写补偿事件。（复盘）重做会先定事件 schema 和幂等键规范，再写业务代码。

### 3. 游戏服务端通用模块面试问答（第 3.3 节的问答版）

> 每题结构：60–90 秒答案 + 常见追问。通用模块题的加分动作：**能挂到自己项目的挂一句**。

#### Q1 排行榜怎么设计？

> 常规榜用 Redis ZSet：ZINCRBY 加分、ZREVRANGE 查名次，天然 O(logN)。三个细节：①**同分排序**——用复合分数 `score * 1e10 + (MAX_TS - 达成时间)`，先到者排前；②**周期榜**——key 里带周期号（周榜/赛季榜），到期新 key，旧 key 归档；③**大榜分片**——DAU 千万级单 ZSet 内存和热度都吃紧，按分数段或 uid 哈希分桶，TopN 汇总层合并。我的 EnergyOps 里预聚合表本质上就是"排行榜快照"思路——预计算换查询性能。
> 追问：好友榜？——好友 uid 集合存 Set，查询时 ZSet 里对这些 uid 批量取 rank。实时性？——前端展示可接受秒级延迟的话，本地缓存 + 定时刷。

#### Q2 体力系统怎么设计？

> **惰性恢复**：只存两个字段——当前体力 + 上次恢复时间戳。玩家请求时算 `min(上限, 当前 + (now - 上次时间)/恢复间隔)`，把结果和新的时间戳写回去。不需要起定时器，几百万玩家也不怕。离线恢复天然正确，因为算的是时间差。
> 追问：买体力/上限随等级？——上限查配置表，恢复只在没满时累计。并发领体力？——单玩家请求串行化（按 uid 路由），天然无并发问题。

#### Q3 掉落/抽卡怎么设计？客户端能不能自己掷骰子？

> **服务端掷骰子，客户端只做表现**。配置表驱动概率表，服务端按权重随机。保底用计数器（第 N 抽必出）。伪随机（连续不出概率递增）体验更稳，看产品取舍。客户端掷骰子等于把游戏经济交给外挂。
> 追问：概率怎么调？——配置表 + 版本号 + 灰度，改概率不用发版。

#### Q4 策划配置表怎么管理？热更怎么做？

> 策划 Excel/JSON → 构建管线校验 → 推送到配置中心，服务端按版本号加载。**热更三件套：版本号 + 灰度 + 回滚**。风险控制：新配置先灰度一部分区服，观察错误率和玩家反馈，异常秒回滚。这个我熟的——EnergyOps 里聚合规则变更我做过 dry-run 准入：先在影子流量上跑一遍看结果差异，才允许上线。
> 追问：配置错了怎么办？——回滚版本；数据层面错发奖励走补偿流程（幂等发放）。

#### Q5 全服邮件/活动补偿怎么发？怎么保证不重复发？

> **模板 + 领取记录**：全服邮件只存一份模板 + 一条公告记录，玩家登录时拉取，领取时在"玩家领取记录"表插入唯一键（活动 ID + 玩家 ID），靠唯一约束幂等——领过就插不进去。补偿发放同理，绝不逐个 UPDATE 几百万玩家行。大量推送走 MQ 削峰，分区分批。
> 追问：错发了怎么办？——不物理删除，发对冲邮件（回收道具），全程留痕可审计。

#### Q6 签到/每日任务怎么防重复领取？

> 日历型状态机：玩家的签到状态是"第 N 天已领"，领取接口带条件更新（WHERE day=N AND claimed=0），受影响行数=1 才发奖。和任务状态持久化一个思路——**状态收敛到数据库，应用层不做判断**。

#### Q7 好友赠体力怎么设计？

> 赠送记录表唯一键（赠送者 + 接收者 + 日期）防超次数；接收方体力走惰性恢复的加值通道，幂等；陌生人限制：只能赠好友 + 拉黑名单。

#### Q8 防作弊总纲？（重点，主动往项目引）

> 三层，按成本从低到高：①**规则校验**（全量、便宜）：分数/步数/用时是否超出该关卡物理上限；②**关键步骤校验**（抽样）：对上报的操作序列做服务端重算或重放；③**资产一致性**（审计）：奖励发放走服务端结算 + 流水守恒对账。设计哲学是**经济学目标**：让作弊期望收益低于期望成本，不是追求拦截率 100%。我做的 RuleArena 就是第②层的工程化极致：声称者不能兼任裁判，声称结果必须能被独立确定性重放验证——这个思路直接可以用于游戏的关键操作验证。
> 追问：全量重放成本高？——三消单机玩法确实全量不划算，业界做抽样 + 举报驱动深查 + 大额/上榜行为全查。

#### Q9 断线重连怎么设计？

> 会话 token 认身份 + 客户端本地指令序号定增量 + **所有写请求幂等**（请求唯一键）。重连后先查会话，再补发序号之后的增量状态。为什么必须幂等：重连瞬间最后一条请求是否到达服务端是不确定的——这正是我在 EnergyOps 做的"状态持久化 + 条件抢占 + 回补"那套，也是 RuleArena ACTION_UNKNOWN 超时语义处理的问题：**不确定时用同一个幂等键去查结果，而不是盲重试**。

#### Q10 分服/高并发架构总览？（收尾大题）

> 休闲游戏标配：无状态网关 → **按区服路由**（uid 哈希，分服是休闲游戏最常用的水平扩展：天然隔离故障和热点）→ 逻辑服按玩法拆模块。数据侧：玩家数据按 uid 分库分表，热数据（排行榜、会话）外置 Redis，落库用"内存脏标记 + 定时批量回写 + 关键操作（支付/通关）实时落库"。稳定性：入口限流（令牌桶）、活动高峰降级非核心（排行查询走快照）、可观测四件套（请求量/P95/错误率/队列积压）。我的能耗平台是同构的小版本：分设备路由、分层数据模型、聚合任务调度加监控。

### 二、主讲项目：EnergyOps（完整版，约 3 分钟）

> 我把金山这个项目展开讲。业务背景是：园区原本只有第三方平台的原始累计读数，质量很差，行政每个月把数据导进 Excel 手工对账；告警一天几十条，真问题被淹没。我做的是把这条链路工程化。
>
> **第一块是数据可信。** 数据是每 15 分钟一个采集点，我设计了原始层、区间层、小时层、日层四层模型。关键是进聚合之前必须先过质量判定——我定义了七类质量状态：缺失、回退、长间隔、倍率变更、异常跳变等等，只有进了可信白名单的数据才允许往下走聚合，脏数据标记但不删，留着溯源。因为源头是累计读数，差分之后最麻烦的是换表和改倍率，这类跳变如果不拦，聚合出来的能耗会凭空涨几十倍。结果是**可信聚合完整率从 96.8% 提到 99.7%**。
>
> **第二块是定时任务的可靠性。** 15 分钟一个窗口，任何一次重跑、重启或者多 worker 并发，都会算重或者漏。我用「设备 ID 加聚合窗口」做唯一键走 upsert，重跑一百次也只有一行；任务领取用一条条件更新去抢占，谁改到那行谁执行，靠数据库的行级约束解决并发，不需要分布式锁。另外调度器重启只会接着跑未来的任务，宕机期间的历史窗口会永久缺失，所以我加了**启动时对账最近七天、把缺失窗口补算回来**，补算走同一套幂等通道。这块的结果是**定时聚合成功率 96.9% 提到 99.6%，人工补数次数降了 72%**。
>
> **第三块是查询性能。** 原来统计接口 P95 是 20.4 秒，定位下来是两个原因：设备维表被重复 JOIN，以及每次查询都从明细现算。我做了三件事：消掉重复 JOIN、加组合索引、把小时和日的聚合结果提前算好落表，查询只读结果表。**P95 从 20.4 秒降到 2.8 秒**。这里我没有选缓存，因为根因是每次从明细现算，缓存只是把慢结果暂存，预聚合才是把计算提前。
>
> **第四块是我认为最能体现服务端设计能力的操作治理。** 上层要调用系统能力，我不可能把数据库操作直接暴露出去，所以把查询、设备管理、规则配置、告警处置、导出、结算这些能力拆成了三十个受控工具，再收敛成六大类能力包，上层只能调注册过的工具，能力边界是白名单而不是调用方的自觉。  
> 然后按风险分三级：**R0 是只读，可以直接执行；R1 是可回滚的写入，执行但留痕；R2 是高风险写入，比如结算确认、批量处置这类，必须先生成预览、经过人工确认才允许真正执行。**  
> 落地方式是**在工具执行的入口做统一的 Hook 切面**：调用前校验参数格式、校验权限、校验操作范围有没有越界，调用后做结果裁剪和上下文控制，避免大结果把上下文撑爆。违规不是抛一个笼统的异常，而是分级返回——需要确认、部分成功、工具超时，各有各的处理路径。  
> 结果是**八十条越权用例拦截率 100%，上层任务完成率从 83.3% 提到 95.8%**——完成率提升不是因为模型变强了，是因为失败路径变清晰了，能重试的知道怎么重试。
>
> **复盘句：这一套的核心就是服务端那句老话——永远不信任上游传进来的东西，身份和范围必须由服务端自己写入。放在游戏里就是客户端上报的任何数据都要在服务端校验，重要操作要服务端二次确认。**

#### 操作治理的三层递进（被追问「再讲细一点」时用）

> 可以从三个层次去看：  
> **机制层**是三个插桩点——调用前、调用后、以及进入模型之前。调用前管越权和参数，调用后管结果体积，进入模型前管上下文。风险分级是挂在 Hook 上的策略配置，不是另一套独立机制，所以业务只需要声明「哪个能力是什么风险级、要不要确认」，核心流程不随业务改。  
> **取舍层**是我为什么不用大而全的权限框架：这里的诉求不是通用的账号体系，而是「能力级的、可声明的、能跟着能力一起演进」的管控，所以做成可插拔的策略比接一套权限中台更轻，也更符合只有一个后端在维护的实际情况。  
> **边界层**是这套治理不承诺什么：它拦的是越权和参数非法，拦不了业务上"合法但错误"的操作，那类问题靠的是第二块的数据可信和质量门禁。

### 三、另两个项目（各 40 秒，被问到才讲）

#### 数驭穹图

> 这是一个多租户的查询网关：上游接 MySQL、PostgreSQL、MongoDB、飞书表格等六类数据源，中间一层查询引擎，出口管权限。  
> 我做的核心决策是**把链路拆成六个阶段**，而不是一个端到端的大调用。原因是可归因：端到端失败了只知道答案错了，不知道错在理解、检索还是生成；拆开之后每层有独立契约和错误码，定位问题的时间从三十分钟降到八分钟。  
> 安全上做了五层纵深，最内层是只读账号加 SQL 结构审查加执行超时——就算前面全漏了，到这一层也写不了库、拖不垮库。结果是**查询成功率 78% 提到 91%，三百条对抗请求危险语句拦截 100%，正常查询误拦率 2.7%**。  
> **（复盘句）跨源系统的取舍只有两个答案：差异要么收在一处，要么散在十处。**

#### RuleArena

> 这个项目的出发点是一个判断：**声称者不能兼任裁判。** 让程序去找规则的漏洞，它说"我找到了"这句话本身不可信。  
> 所以架构是三分离的：程序只负责提议动作序列，拿到一个干净的隔离环境里用真实 HTTP 接口重放，再由一个独立部署的裁决器按资金守恒、状态生命周期、幂等这三类不变量来判。  
> 服务端上最关键的是写操作的可靠性：幂等键用业务身份合成，配数据库唯一约束；超时之后不能盲重试，而是拿同一个幂等键去查回执，查不到才敢重发。  
> **（复盘句）这条在游戏里就是防作弊的最高形态：玩家上报这局三万分，你要么做合理性校验，要么确定性重放，不能直接信。**

### 四、面试问答（短标答，30-60 秒，照念即可）

#### A 组 · 操作治理专项（你最该拿分的地方）

**A1 三十个工具为什么收敛成六类能力包？**

> 不是分类强迫症。上层如果面对三十个细粒度工具，调用成本高、容易选错，而且同类操作的权限策略会各写一遍。收敛成六类之后，**权限策略、风险等级、确认流程都挂在能力包这一层**，新增一个工具只需要声明它属于哪一类，不用重新配一遍策略。本质是让治理的配置维度从三十降到六。

**A2 R0/R1/R2 怎么划的？会不会有人为了省事把高风险标成低风险？**

> 划分标准是**副作用是否可逆、影响面是否跨主体**：只读是 R0；只影响单条记录、且有反向操作的是 R1；涉及结算确认、批量变更、会影响财务结果的是 R2。标低风险的动机确实存在，所以分级不是靠自觉，而是**分级和 Hook 绑定**——标成 R0 就走 R0 的校验路径，越权会在调用前被拦；而且分级变更本身要进版本记录，改了要重新过一遍用例。

**A3 去掉 Hook 会怎样？能不能只在业务代码里写判断？**

> 能跑，但会散。三十个工具每个都自己写一遍参数校验和权限判断，一定会有漏的，而且漏了之后你不知道漏在哪。做成统一切面的好处是**漏不掉**——新加一个工具，默认就在管控里，不需要开发者想起来才加。这也是我做完之后任务完成率能提上去的原因：失败变得可预期了。

**A4 拦截 100% 是怎么测的？这个数字可信吗？**

> 我构造了八十条越权用例，覆盖几类典型越权：跨租户访问、越级调用高风险能力、参数里伪造身份、操作范围超出授权。**要说明的是，这个 100% 的意思是"这八十条用例全部被拦"，不是说系统不存在任何越权可能**——它证明的是机制生效，不是证明完备。这点我会说清楚，不想把验证结果说成安全承诺。

**A5 Hook 会不会拖慢调用？**

> 校验本身很轻，主要是参数格式和范围判断，没有重查询。真正有成本的是 R2 的人工确认，但那是业务上必须付的代价。另外调用后做结果裁剪，反而**降低了整体开销**——大结果被截断之后，后续处理的成本是下降的。

#### B 组 · 项目与服务端

**B1 你做的这些跟游戏服务端有什么关系？**

**B4 为什么用 Python 不用 Java？**

**B5 你平时怎么用 AI 编程工具？**

### 1. 场景题一：移动端 2D 渲染引擎

#### 1.1 60 秒核心判断

> 这道题的本质约束是每帧 16.67ms 和运行时 350MB。2000 个精灵不是问题，2000 次 draw call 才是问题；1.5GB 资源不是问题，运行时纹理怎么放才是问题。所以我的核心判断是三点：**渲染能力靠合批**（图集 + 按材质排序批量提交，粒子走 GPU instancing）；**内存靠纹理压缩与生命周期管理**（ASTC/ETC2 硬件压缩占 1/4~1/8 内存 + 引用计数装卸）；**进关卡不卡靠异步预载 + 分帧加载 + 对象池**。可扩展性走组件化和数据驱动，兼容性的正确形态是**自动画质分级降级**而不是「能跑就行」。

#### 1.2 复盘后的 3 分钟框架（大纲）

1. **目标与预算**：帧预算表（逻辑/动画/合批/提交/GPU 各几 ms）+ 内存账本（一张 2048×2048 RGBA=16MB，350MB 倒推图集与压缩策略）。
2. **架构分层**：场景图与组件 → 渲染管线（收集→剔除→排序→合批→提交）→ 动画系统 → 粒子系统（GPU 粒子/池化）→ UI（层级与合批断裂治理）→ 文字（SDF 字体 + 动态字库）→ 多分辨率适配（设计分辨率 + 缩放策略 + safe area）。
3. **资源系统**：图集、压缩格式矩阵（iOS ASTC / Android ETC2 兜底 ETC1+alpha）、异步分帧加载（每帧时间片）、引用计数 + 对象池、热更与版本号。
4. **性能与兼容**：启动时特性检测 → 画质档位（粒子数/分辨率缩放/后处理开关）自动降级；旧关卡兼容 = 数据版本号 + 迁移层，只加字段不改旧格式。
5. **可扩展性**：组件化、渲染管线可插拔（后处理栈）、材质/Shader 变体管理、数据驱动配置。
6. **验证**：性能预算测试、中低端机型矩阵自动化、FPS/内存/DC 基线与门禁。

#### 1.3 高频追问 10 连 + 答案要点

| #   | 追问                           | 答案要点                                                                    |
| --- | ---------------------------- | ----------------------------------------------------------------------- |

### 2. 场景题二：休闲关卡游戏防作弊体系

#### 2.1 60 秒核心判断

> 题目最后说「不要求消灭所有作弊」，这提示目标函数是**经济学目标**——让作弊的期望收益低于期望成本——而不是拦截率 100%。第一性原理：客户端在玩家手里，一切客户端数据不可信；业务又要求离线 24 小时，信任缺口必然存在。所以问题转化为：**在缺口确定存在的前提下，用对账、合理性校验和分级结算把损失压到可接受**。我从作弊者视角排攻击面收益（排行榜/稀缺奖励、付费货币、广告奖励、批量小号），防御资源按收益倒序投放；每层防御用边际思维看拦截率增益对误伤率和服务端成本的拐点，在拐点处停手。

#### 2.2 复盘后的 3 分钟框架（大纲）

1. **目标与不可接受风险清单**：付费资产、稀缺活动奖励、排行榜公平——先和运营对齐「损失多少钱/多少口碑算不可接受」。
2. **威胁建模**：攻击面 × 收益排序；作弊者成本（封号、设备、技术）是我们的杠杆——抬高他们的边际成本。
3. **分层架构**：端侧加固（完整性校验、越狱检测只作信号不作一票否决）→ 协议校验（签名、时间戳+nonce 防重放）→ 服务端审计（对账守恒、合理性校验、抽样重放）→ 账号画像（设备指纹、批量聚类、速率限制）→ 运营处置（渐进、可回滚、申诉）。
4. **离线同步专项（题眼）**：货币/体力/道具全服务端记账，离线变化事后对账（体力可按时间戳重算，消耗与获得必须闭合）；上报带上下文，按物理上限校验；小额先发保体验、大额稀缺延迟结算进风控窗口。
5. **误伤与体验保护**：99% 正常玩家无感；friction 只加在高温区（大额、上榜）；渐进处置可回滚；申诉通道 + 误报率监控告警。
6. **隐私合规**：最小化采集、告知同意、匿名化、指纹不作唯一身份。

### 3. 场景题三：玩家状态重建与问题复现系统

#### 3.1 60 秒核心判断

> 第一性原理：状态 = f(初始状态, 事件序列)。要在任意变更点重建状态，数学上要求三件事：**事件可回放且有序、重放函数确定、重放用的是事件发生时刻的逻辑与配置**——第三条是最深的坑。逆向思维：研发/测试/客服要的不是一坨终态，而是「这个状态为什么是这样、谁改的、依据什么配置」，所以系统本质是**可解释的变更历史**，不是备份系统。边际思维：10 亿事件/天不能全量物化，但单玩家一天才 100 条事件、重放毫秒级——所以正确解是**周期快照 + 按需重放增量**，存储分层，查询时才算。

### 5. 算法 T1：广告排期（带权区间调度 + 最多 K 个 + 最少广告数）

> 你可能「没做完」的题——现在必须能白板完整写出并通过示例。

**建模**：经典加权区间调度的 DP 变体。按 endTime 排序；闭区间冲突规则（end\==start 也冲突）⇒ 与广告 i 兼容的前缀是「end 严格小于 start_i」的所有广告，排序后是前缀，二分求出。

**双目标的优雅解法**：DP 值存 pair `(收益, 广告数)`，比较规则 = 收益最大优先、同收益广告数最少——一次 DP 同时优化两个目标，不需要二分答案。

**转移**：`dp[i][j] = max( dp[i-1][j], dp[p(i)][j-1] + (rev_i, 1) )`，`dp[i][j]` = 前 i 个广告、最多选 j 个的最优 pair。
**复杂度**：O(n log n + nK)，n=2e4、K≤50 → 约 10⁶，轻松通过。收益总和最大 5×10¹⁰ → 64 位（题目 IO 标 %lld 就是提示）。

**示例自验**：排序后选广告 1、3、5 → 50+70+80=200，3 条；广告 6 [1,10] 收益 180 与所有冲突 ⇒ 200 正确。

```python
from bisect import bisect_left
import sys

def solve(n, k, ads):
    # ads: (adId, advertiserId, start, end, revenue)，按结束时间排序
    items = sorted(ads, key=lambda x: x[3])
    ends = [it[3] for it in items]
    # dp[i][j] = 前 i 个广告、最多选 j 个的最优 (收益, 广告数)
    dp = [[(0, 0)] * (k + 1) for _ in range(n + 1)]
    for i in range(1, n + 1):
        _, _, s, _, r = items[i - 1]
        p = bisect_left(ends, s)          # end 严格小于 s 的前缀长度（闭区间冲突）
        for j in range(1, k + 1):
            skip = dp[i - 1][j]
            pv = dp[p][j - 1]
            take = (pv[0] + r, pv[1] + 1)
            if take[0] > skip[0] or (take[0] == skip[0] and take[1] < skip[1]):
                dp[i][j] = take
            else:
                dp[i][j] = skip
    return dp[n][k]

if __name__ == "__main__":
    data = sys.stdin.read().split()
    it = iter(data)
    n, k = int(next(it)), int(next(it))
    ads = []
    for _ in range(n):
        ad_id = int(next(it)); adv = int(next(it))
        s = int(next(it)); e = int(next(it)); r = int(next(it))
        ads.append((ad_id, adv, s, e, r))
    rev, cnt = solve(n, k, ads)
    print(rev, cnt)                       # 示例输入输出 200 3
```

import java.util.*;

public class Main {
    static long[] solve(int n, int k, long[][] ads) {   // ads[i] = {s, e, r}
        Arrays.sort(ads, (a, b) -> Long.compare(a[1], b[1]));
        long[] ends = new long[n];
        for (int i = 0; i < n; i++) ends[i] = ads[i][1];
        long[][] rev = new long[n + 1][k + 1];
        int[][] cnt = new int[n + 1][k + 1];
        for (int i = 1; i <= n; i++) {
            long s = ads[i - 1][0], r = ads[i - 1][2];
            int p = lowerBound(ends, s);                 // end < s 的个数
            for (int j = 1; j <= k; j++) {
                long sr = rev[i - 1][j]; int sc = cnt[i - 1][j];
                long tr = rev[p][j - 1] + r; int tc = cnt[p][j - 1] + 1;
                if (tr > sr || (tr == sr && tc < sc)) { rev[i][j] = tr; cnt[i][j] = tc; }
                else { rev[i][j] = sr; cnt[i][j] = sc; }
            }
        }
        return new long[]{rev[n][k], cnt[n][k]};
    }
    static int lowerBound(long[] a, long t) {            // 第一个 >= t 的下标
        int lo = 0, hi = a.length;
        while (lo < hi) { int mid = (lo + hi) >>> 1;
            if (a[mid] < t) lo = mid + 1; else hi = mid; }
        return lo;
    }
    public static void main(String[] args) {
        Scanner sc = new Scanner(System.in);
        int n = sc.nextInt(), k = sc.nextInt();
        long[][] ads = new long[n][3];
        for (int i = 0; i < n; i++) {
            sc.nextLong(); sc.nextLong();                // adId, advertiserId
            ads[i][0] = sc.nextLong(); ads[i][1] = sc.nextLong(); ads[i][2] = sc.nextLong();
        }
        long[] ans = solve(n, k, ads);
        System.out.println(ans[0] + " " + ans[1]);       // 示例 → 200 3
    }
}

**追问预案**：①为什么按结束时间排序（保证兼容前缀是前缀、可二分）；②闭区间冲突在代码哪里体现（`bisect_left(ends, s)` 严格小于，end\==start 不会被算进 p）；③为什么 pair DP 能同时优化两个目标（两目标都可加，字典序比较在相同 DP 结构上仍然最优子结构）；④K 更大/n 更大怎么办（nK 超限时按收益上界剪枝或改堆贪心，但要说明贪心对带权区间不最优）。

### 6. 算法 T2：完全二叉树补全

**你当时的坑**：自测输出 {1,#,1,1} = 原样返回了树，没有真正重建。复盘时直接承认，然后给正确解法。

**题意**（示例钉死）：{1,#,1,1} → 树 = 根、根右、根右左；输出 {1,1,1,1,1,1} 共 6 节点 = 补全为 3 层完全二叉树：第 2 层补满（补根左），第 3 层「集中在最左」= 补到最深真实节点的编号为止。

**算法（完全二叉树编号系统）**：
1. DFS 给每个真实节点标编号（根=1，孩子=2p/2p+1），求树高 h（层数）与最深层最大编号 k。
2. 原地补全：深度 < h-1 的层必须全满（缺则 new 权值 1）；最深层（深度 h-1）只保留编号 1..k（缺则补、超出的跳过）。
3. 层序输出，尾部 # 截断。
4. 复杂度 O(节点数 + 补全数)，h≤20 → 轻松。

```python
from collections import deque

class TreeNode:
    def __init__(self, val=1):
        self.val = val
        self.left = None
        self.right = None

def complete_tree(root):
    """把二叉树补全为完全二叉树（只新增权值 1 的节点，保留原节点与结构）"""
    info = {}                                  # node -> (完全树编号, 深度)
    h = 0
    def dfs(node, ci, d):
        nonlocal h
        if not node: return
        info[node] = (ci, d)
        h = max(h, d + 1)
        dfs(node.left, 2 * ci, d + 1)
        dfs(node.right, 2 * ci + 1, d + 1)
    dfs(root, 1, 0)
    k = max(ci for ci, d in info.values() if d == h - 1)   # 最深层最右编号
    hidx = {ci: node for node, (ci, _) in info.items()}
    q = deque([(hidx[1], 1, 0)])
    while q:
        node, ci, d = q.popleft()
        for pos, attr in ((2 * ci, 'left'), (2 * ci + 1, 'right')):
            cd = d + 1
            if cd >= h: continue                     # 超出树高
            if cd == h - 1 and pos > k: continue     # 最深层只保留 1..k
            child = hidx.get(pos)
            if child is None:
                child = TreeNode(1)
                hidx[pos] = child
            setattr(node, attr, child)
            q.append((child, pos, cd))
    return root

def serialize(root):
    out, q = [], deque([root])
    while q:
        node = q.popleft()
        if node is None: out.append('#')
        else:
            out.append(str(node.val))
            q.append(node.left); q.append(node.right)
    while out and out[-1] == '#': out.pop()
    return '{' + ','.join(out) + '}'

def parse(s):
    toks = s.strip().strip('{}').split(',')
    root = TreeNode(1)
    q, i = deque([root]), 1
    while q and i < len(toks):
        node = q.popleft()
        for attr in ('left', 'right'):
            if i < len(toks):
                t = toks[i]; i += 1
                if t != '#':
                    ch = TreeNode(1); setattr(node, attr, ch); q.append(ch)
    return root

if __name__ == "__main__":
    print(serialize(complete_tree(parse("{1,#,1,1}"))))   # {1,1,1,1,1,1}
```

> 注：笔试是牛客「核心模式」，参数绑定格式特殊（给的是节点数组），复盘讲思路时与输入格式无关——**编号 + 按编号重建**才是考点。

**追问预案**：①怎么定义「补全后第 h 层到哪」（k = 最深层最大真实编号）；②为什么任意输入都能这样补全（填满所有祖先 + 最深层补到 k，原节点全部被保留且结构合法）；③用 BFS 队列逐槽位补全的写法（上面代码）；④如果要输出「新增了哪些节点」（对比编号集合的差集）。

### 7. 算法 T3：最长特殊子序列（LeetCode 522，你输出 1 的题）

**逆向洞察（这题的灵魂）**：

> 若串 s 的某个子序列是特殊的，那么 **s 整串本身也必然特殊**——s 是它的超序列，「小的不是任何人的子序列 ⇒ 大的更不是」。所以候选只有 n 个整串，**不需要枚举任何真子序列**，问题从指数空间塌缩到 O(n²·len)。

**解法**：对每个串 s，用双指针检查它是否是其他任何一个串的子序列（O(len)）；都不是 → 候选；答案 = 最长候选长度，无则 -1（按题面）。重复串天然被处理（相同串互为子序列 → 都不特殊）。

你输出 1 的常见原因：往「和别人的 LCS 差集」或贪心逐字符对抗方向做了。复盘话术：「我后来发现了『答案只需整串』这个逆向洞察，问题瞬间简化」。

Python：

```python
def is_subseq(s, t):
    it = iter(t)
    return all(c in it for c in s)

def find_lus_length(strs):
    ans = -1
    for i, s in enumerate(strs):
        if not any(j != i and is_subseq(s, t) for j, t in enumerate(strs)):
            ans = max(ans, len(s))
    return ans

if __name__ == "__main__":
    print(find_lus_length(["aba", "bbb", "eae"]))       # 3
    print(find_lus_length(["nowcoder", "nowcoderr"]))   # 9
    print(find_lus_length(["abc", "abc"]))              # -1
```

Java：

```java
class Solution {
    public int findLUSlength(String[] strs) {
        int ans = -1;
        for (int i = 0; i < strs.length; i++) {
            boolean uncommon = true;
            for (int j = 0; j < strs.length && uncommon; j++) {
                if (i != j && isSubseq(strs[i], strs[j])) uncommon = false;
            }
            if (uncommon) ans = Math.max(ans, strs[i].length());
        }
        return ans;
    }
    private boolean isSubseq(String s, String t) {
        int i = 0;
        for (char c : t.toCharArray()) {
            if (i < s.length() && s.charAt(i) == c) i++;
        }
        return i == s.length();
    }
}
```

**追问预案**：①为什么只需检查整串（超序列论证，上面引号那段必须能脱口而出）；②重复串为什么天然处理（相同串互为子序列）；③isSubseq 双指针为什么正确（贪心匹配：t 的字符按序喂给 s 的指针，能走完即存在）；④如果题目改成「统计特殊子序列数量」会怎样（那才是真指数题，需要 Trie/AC 自动机等——说出方向即可）。
