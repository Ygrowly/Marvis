### 1.2 三个事实与三句话策略

事实：①「java 优先」= 优先不等于必须，校招看的是基础与潜力；②JD 第 5 条把 AI 工具写进要求，全库只有我的简历天然命中；③这场面试 70% 的分数在**基础题 + 项目深挖 + 算法题**，都不依赖游戏经验。

策略三句话：

1. **基础不丢分**：网络、数据结构、OS、DB 的显性门槛题全部准备到「60 秒说清 + 能被追问一层」。
2. **项目换叙事**：三个项目的**事实一个不改**，把叙事重心从「Agent 治理」平移到「服务端工程」——幂等、状态机、定时任务、性能优化、安全校验本来就是服务端语言（§4.2 映射表）。
3. **Java 不装熟**：主动定位「主力 Python，Java 概念层扎实、语法可查」，用迁移故事收尾；概念题答对比装熟答穿强得多。
4. **痕迹 > 背诵**（2026-09-08 按 [[面试准备第一性原理]] 增补）：面试是证据采集，§4.6 决策链的「还想过什么 / 为什么放弃 / 重做改什么」比多背十道八股更值钱。八股的目标定在「60 秒说清 + 追问一层不塌」，不追求完美；省下的时间全部投给决策链挖写说和口述录音。

## 3. 消消乐业务专项（区分度最高，先建立全局）

### 3.1 业务图景：先说对「这是什么形态的服务端」

开场就可能问「你了解开心消消乐吗 / 你觉得消消乐的服务端要做什么」。这段是地基：

> 乐元素 2009 年成立，北京总部，开心消消乐 2014 年上线、长线运营超十年的国民级三消手游，海外版 Anipop。它是**单机核心玩法 + 强联网运营**的休闲游戏：消除关卡本身客户端本地跑，服务端负责**进度结算与校验、体力、金币等资产、排行榜、好友、活动运营、支付**。所以它是**请求-响应式（短连接/HTTP 为主 + 少量推送）**，不是 MMO——**不需要帧同步**，并发压力来自海量玩家同时做简单请求（DAU 千万级），而不是单局内高频同步。

这句话的价值：一个没有游戏经验的候选人，上来就能做对「品类 → 架构形态」的判断，直接和对背八股的人拉开差距。追问「为什么不用长连接帧同步」→ 三消没有实时对战；帧同步/状态同步的适用边界见 §5 第 1 题。

### 3.2 消除核心算法（大概率手写/口述，§9 对应练习）

**本轮消除检测**（棋盘 `board[m][n]`，颜色 1-6，空=0）：

```text
marks = set()
对每个格子 (i,j)，若非空：
  向右统计连续同色数 run → 若 run>=3，把这段全部加入 marks
  向下统计连续同色数 run → 若 run>=3，把这段全部加入 marks
（横向纵向分开扫，交叉消除用 set 自动去重；特殊元素如直线特效/炸弹
 可建模为「消除后触发额外波及」，用队列做连锁触发）
```

**下落填充**：逐列处理，每列用双指针——写指针 `w` 从列底向上找第一个空位，读指针 `r` 在其上方找第一个非空元素，搬到 `w`；列顶剩余空位补新随机元素（或关卡预设）。

**连锁反应（cascade）**：`while true { if 检测为空 break; 消除→计分→下落 }`，连消次数影响分数倍率。

**死局检测与洗牌**：枚举每个格子与「右邻、下邻」交换一次，交换后跑一次检测，存在任何可消交换 → 可解；否则洗牌，洗后需保证「可解且不会立即自动消除」。一次检测 O(mn)，死局检测 O(mn×2) 次交换 × O(mn)，休闲棋盘规模完全可接受。

**步数与结算**：步数是资源，用尽或达成目标（收集 X 个某元素）结束；结算要区分「客户端表现动画」与「服务端权威数值」（见 §5 第 6 题）。

### 3.3 游戏服务端通用模块 → 考点映射（每行都要能展开 1 分钟）

| 模块       | 设计要点                                                                                                    | 延伸考点                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |

### 3.4 高并发与稳定性（开心消消乐体量下的追问链）

- **入口**：无状态接入层/网关 → 按分服（区服）路由到逻辑服；逻辑服内部再按玩法/模块拆服务。**分服是休闲游戏最常用的水平扩展手段**：uid 哈希到区服，天然隔离故障与热点。
- **缓存三问**（必考）：穿透（不存在 key → 空值缓存/布隆过滤器）、击穿（热 key 过期 → 互斥重建/逻辑过期）、雪崩（批量过期/缓存宕机 → 过期加随机、多级缓存、限流降级）。
- **热 key**：某活动瞬间全服读 → 本地缓存 + 随机副本 key + 限流。
- **落库策略**：玩家数据写 Redis/内存（脏标记），定时批量回写 + 关键操作（支付、通关）实时落 MySQL；停服维护时全量落地。
- **大表**：玩家数据按 uid 分库分表；排行榜等热数据外置 Redis。
- **限流与降级**：入口令牌桶/漏桶；活动高峰降级非核心功能（如排行查询走缓存快照）。
- **可观测**：请求量、耗时 P95、错误率、队列积压——直接迁移 EnergyOps 的 SLO 语言。

## 5. 游戏服务端专题 60 秒答案（8 题）

**Q1 帧同步 vs 状态同步？**
L0：确定性模拟 vs 权威状态广播。60 秒：状态同步由服务端跑权威逻辑，广播结果状态，客户端表现，安全但流量大；帧同步服务端/玩家只广播输入指令，各端跑确定性模拟，流量小、利于回放观战，但要求浮点/随机一致性且防作弊弱。**选型**：强实时对战（MOBA/射击）用帧同步或权威帧同步；回合制、卡牌、三消这类**请求-响应式玩法用状态同步甚至纯 HTTP 结算**。消消乐：单机玩法本地跑，服务端做结果校验与资产结算。

**Q2 消消乐选长连接还是短连接？**
L0：短连接为主 + 少量推送。60 秒：三消没有局内实时同步需求，交互是「进关卡→打完→上报→领结算」的低频请求-响应，HTTP(S) 短连接足够，运维简单、天然过网关和负载均衡；需要服务端主动推的少数场景（好友赠体力提醒、活动推送）用长连接推送或客户端轮询/厂商推送通道兜底。若追问「为什么不干脆全长连接」：海量大 DAU（ **每日活跃用户数量**） 下长连接的维持成本（心跳、网关内存、断线重连）远大于收益。

**Q3 TCP 粘包拆包怎么办？**
L0：TCP 是字节流，无消息边界。60 秒：应用层自己定界，四种方案——固定长度、分隔符、**长度前缀（header 带 body 长度，最常用）**、协议自带（如 HTTP 的 chunked）。游戏里自定义二进制协议一般是 `len + msgId + version + body(protobuf)`。收到半个包先缓存，凑齐再解。

**Q4 心跳与断线重连怎么设计？**
L0：心跳探活 + 幂等重连。60 秒：客户端定时发心跳，服务端超时未收到则判离线并释放资源；重连时客户端带会话 token 和本地已处理的指令序号，服务端校验身份后补发增量状态；**所有写请求必须幂等**（请求唯一键），因为重连前最后一条请求是否到达服务端是不确定的——这正是我在 EnergyOps 做的幂等窗口 + 状态持久化 + 回补。

**Q5 Protobuf vs JSON？**
L0：二进制 vs 文本。60 秒：Protobuf 体积小（varint【可变长度整数-用于压缩整型数值的编码】、字段号）、编解码快、schema 强约束多端一致，适合高频游戏协议；JSON 可读性好、调试方便，适合运营后台和管理接口。游戏内协议 Protobuf、对外/后台接口 JSON 是常见组合。

**Q6 防作弊：客户端上报的分数能信吗？**
L0：不信任，服务端权威。60 秒：三道防线——①**规则校验**：分数/步数/用时是否超出该关卡的物理上限；②**关键步骤校验**：消除操作序列服务端可重算或抽样重放；③**资产一致性**：奖励发放走服务端结算并留流水。高级方案是把核心逻辑做成服务端确定性模拟（RuleArena 思路：声称者不能兼任裁判）。同时说边界：三消单机玩法全量重放成本高，业界常做抽样 + 举报驱动的深查。

**Q7 游戏服务器里的定时任务怎么做？**
L0：时间轮/优先队列 + 持久化。60 秒：大量玩家定时器（体力恢复）用**惰性计算**（读取时按时间戳算，不真起定时器）；全局定时任务（日结算、赛季）用调度中心 + 分布式锁；海量短期定时器用时间轮。关键都是：任务状态要持久化、执行要幂等、错过要能补——我在金山做的就是这套。

**Q8 消息推送/全服广播怎么扛量？**
L0：分批 + 队列削峰。60 秒：全服邮件/公告不逐个写玩家库，用「模板 + 领取记录」；在线推送按分区分批；用 MQ 削峰，消费端幂等。高峰期降级非核心链路。

## 6. 网络与 TCP/IP 必答题（一面基本盘，12 题）

> 每题先背 L0 关键词，再用 60 秒展开。来源建议：小林 coding《图解网络》对应章节（§11）。

1. **三次握手**：SYN→SYN+ACK→ACK。为什么三次：确认双方收发能力 + 同步初始序号 + 防止历史重复连接初始化。
2. **四次挥手**：FIN→ACK→FIN→ACK。为什么四次：TCP 全双工，两个方向分别关闭；主动方收到 FIN 后进 TIME_WAIT 等 2MSL（最大报文生存时间）——保证最后 ACK 可达 + 让旧报文消亡。
3. **TIME_WAIT 过多**：端口耗尽/内存；解法：连接复用（keep-alive、连接池）、`SO_REUSEADDR`、调大端口范围。
4. **TCP 怎么保证可靠**：序号+确认应答、超时重传/快速重传、滑动窗口流量控制、拥塞控制（慢启动、拥塞避免、快恢复）、校验和去重排序。
5. **TCP vs UDP + 游戏选型**：TCP 面向连接可靠有序、拥塞控制；UDP 无连接、开销小、实时性好、可自定义可靠性（KCP/QUIC）。对战同步选 UDP，请求-响应和资产操作选 TCP/HTTP。消消乐用 HTTP(TCP) 足够。
6. **HTTP 报文与方法**：请求行/头部/体；GET 幂等取资源、POST 提交；PUT/DELETE 语义；游戏接口一般 POST + 签名。
7. **HTTPS 握手**：TCP 后协商（TLS：交换随机数与证书、验签、算出对称密钥）→ 之后对称加密通信；防窃听/篡改/冒充。
8. **常见状态码**：200/301/302/400（参数错）/401（未认证）/403/404/429（限流）/500/502（网关到上游失败）/504（上游超时）。游戏接口常自定义业务错误码 + HTTP 200，要能说取舍。
9. **长连接心跳**：应用层心跳包定时保活，检测半开连接（对端异常掉线 TCP 本身感知不到）；Nginx/网关 idle timeout 要大于心跳间隔。
10. **select/poll/epoll**：IO 多路复用让单线程管理大量连接；epoll 红黑树+就绪链表，事件驱动，避免每次全量扫描——高并发网关（Netty/Redis/Nginx）的地基。
11. **从输入 URL 到页面显示**（串联题）：DNS→TCP 握手→TLS→HTTP 请求→网关→服务端→DB/缓存→响应渲染。用这条线把上面所有点串成 2 分钟叙述。
12. **签名与防重放**：参数排序 + 时间戳 + nonce + 密钥 HMAC；服务端校验时间窗与 nonce 去重——游戏接口防改包基本功。

### 7.2 概念级必答题（答出机制 + 一句对比即可）

1. **OOP 三大特性**：封装（隐藏内部状态）、继承（复用与扩展）、多态（父类引用指向子类实现，运行期动态绑定）；再加接口与抽象类区别（接口多继承行为契约，抽象类单继承共享实现）。
2. **HashMap 原理（1.8）**：数组 + 链表 + 红黑树；put 对 key 取 hash 定位桶，冲突挂链，链长 ≥8 且容量 ≥64 树化；负载因子 0.75、扩容翻倍 rehash；1.8 改点：尾插法（防环）、树化。线程不安全 → 并发用 ConcurrentHashMap。
3. **ConcurrentHashMap（1.8）**：放弃分段锁，Node 数组 + CAS + synchronized 锁单个桶头；读不加锁；size 用计数。
4. **ArrayList vs LinkedList**：动态数组随机访问 O(1)、尾插均摊 O(1)、中间插删 O(n)；LinkedList 双向链表头尾插删 O(1)、随机访问 O(n)；实际几乎总选 ArrayList（缓存友好）。
5. **String 为什么不可变**：final char/value 数组不暴露；好处：字符串常量池复用、hashCode 缓存、线程安全、作为 map key 稳定。
6. **equals 与 hashCode**：契约——equals 相等则 hashCode 必须相等；不重写 hashCode 会导致 HashMap 行为错误。
7. **异常体系**：Throwable→Error（不捕获）/Exception；Exception 分受检（编译强制处理，IOException）与运行时（RuntimeException，NPE/越界）；try-with-resources 自动关闭资源。
8. **JVM 内存区域**：堆（对象，GC 主战场，分新生代/老年代）、虚拟机栈（栈帧、局部变量）、方法区/元空间（类信息）、程序计数器、本地方法栈。线程私有 vs 共享要能分清。
9. **GC 一句话版**：可达性分析判活；分代假设→新生代复制算法（Eden+S0/S1，Minor GC），老年代标记整理/清除（Major/Full GC）；收集器认识名字即可（CMS、G1、ZGC：G1 分 Region 可预测停顿，ZGC 低停顿）。对象晋升：年龄阈值、大对象直入老年代。
10. **volatile vs synchronized**：volatile 保证可见性 + 禁止指令重排、**不保证原子性**（i++ 仍不安全），适合状态标志；synchronized 互斥 + 可见性，锁对象/方法/类。扩展：CAS 与 ABA 一句话。
11. **线程池参数**：corePoolSize、maximumPoolSize、keepAliveTime、workQueue、拒绝策略；执行顺序（核心→队列→扩到 max→拒绝）；为什么不用 Executors 默认工厂（无界队列/无限线程风险）。
12. **ThreadLocal**：线程私有副本，底层 ThreadLocalMap，key 弱引用；用完必须 remove，防止线程池复用导致脏数据与内存泄漏。

## 8. 数据库 / Redis / OS 必答题（8 题）

1. **MySQL 索引为什么用 B+ 树**：矮胖少 IO、叶子链表利于范围查询；对比哈希（无序）、二叉树（可能退化）、B 树（非叶存数据，扇出小）。加一句：最左前缀、覆盖索引、回表。
2. **事务 ACID 与隔离级别**：原子/一致/隔离/持久；读未提交/读已提交/可重复读（MySQL 默认）/串行化；脏读、不可重复读、幻读一句话各配一个例子。
3. **慢查询怎么排查**：`EXPLAIN` 看扫描行数与索引使用 → 加/改索引、改写 SQL、预聚合（直接接 EnergyOps P95 优化证据）。
4. **Redis 常用结构与游戏用途**：String（资产计数）、Hash（玩家属性）、ZSet（排行榜！）、List（消息）、Set（好友去重）；过期策略与内存淘汰（LRU/LFU）一句话。
5. **Redis 持久化**：RDB 快照（快恢复、可能丢数据）vs AOF 日志（更安全、文件大），混合持久化。
6. **缓存三问**：见 §3.4，必背，这是排行榜/玩家数据话题的固定追问。
7. **进程/线程/协程**：进程隔离资源、线程共享内存切换由 OS 调度、协程用户态调度轻量（Python asyncio 我天天用 → 顺势迁移到「海量玩家连接用协程/虚拟线程处理」）。
8. **死锁四条件**：互斥、持有等待、不可剥夺、循环等待；破坏任一条即可预防（统一加锁顺序最常用）。
