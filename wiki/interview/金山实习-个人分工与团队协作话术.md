# 金山实习——个人分工与团队协作面试话术

> 目标：回答大厂面试官必问的「这个项目是你一个人做的吗」「具体说说你的分工」「你们团队怎么协作」。核心是**诚实 + 突出主导 + 边界清晰**。
> 所有【】内容为真实信息占位，请按实际情况填写后再使用。

## 0. 总原则

一句话公式：

> **背景（项目多大、多少人参与）→ 我的边界（我主导什么 / 我参与什么）→ 我的推动（如何对齐、如何落地）→ 结果（量化价值）**

三条铁律：
1. **不否认团队存在**——大厂会交叉验证，虚报团队规模比说"我负责了更多"更危险。
2. **用「主导提出并实现」替代「独立完成」**——既能讲贡献，又不越界。
3. **把量化结果绑定到「我主导的部分」**——数字是护城河，但要归位到你能负责的模块。

## 2. 三个必答题

### Q1：这个项目是你一个人做的吗？

**应答（诚实 + 主导）：**

> 不是一个人，项目是团队一起推进的。但里面的【数据模型、工具拆分、Hook 链治理、安全分级】这几块核心架构是我主导提出并实现的。其他同学主要负责【结算业务口径、前端工作台】。我负责的模块都有线上结果：比如 Agent 任务完成率从 83.3% 提到 95.8%、可信聚合完整率 96.8%→99.7%、越权用例拦截 100%。

**要点：**
- 第一句先给团队，不回避。
- 第二句用「主导提出并实现」锁定贡献。
- 第三句用数字证明——数字属于你主导的模块，站得住。

### Q2：具体说说你的分工？

用「主导 / 参与」清单，边说边分类：

**我主导（可讲深，面试官深挖都在这）：**
1. 四层能耗数据模型 + 7 类质量状态 + 可信白名单
2. 25 个 MCP 工具拆分 + 6 类 Capability Bundle
3. R0/R1/R2 风险分级 + Before/After Tool Hook 链治理
4. 告警指纹去重 + dry-run 准入（告警量 -43%）
5. 聚合查询性能优化（P95 20.4s→2.8s）

**我参与 / 对齐（主动说明边界，防追问）：**
1. 月度结算业务口径——与财务团队对齐，不是我单独定的
2. 设备归属与园区组织——与业务方确认
3. 前端工作台——团队其他成员实现，我提供接口与状态协议

### Q3：你们团队怎么协作的？

> 我【远程/在办公室】跟【导师】和【同学】配合。复杂设计我会先写设计文档给团队评审，再动手实现；改动的模块有【单元测试 + 回归测试】兜底。Agent 这块当时是新方向，我会主动把架构决策讲清楚，帮助团队理解为什么这么设计，而不是只交代码。

## 3. 针对「你只是实习生，怎么会主导架构设计？」

**最常见的灵魂拷问，重点是讲"为什么能"，不是辩解。**

> 因为 Agent 当时对团队来说是新方向，大家还在探索，没有现成答案。我把这块当成主攻方向，先做了行业方案调研和对比，用【内部评测/实验数据】验证了方案可行，再说服团队采用，之后独立实现并拿到量化结果。所以不是团队让我去主导，而是我用方案和数据挣来的主导权——这个从调研到落地到量化的过程，恰恰是我最想展示的能力。

**要点：**
- 用「新方向、无现成答案」解释实习生主导的合理性。
- 用「数据/评测建立信任」替代「职权」，体现工程判断力。
- 收尾把话题落到"过程"而非"职位"。

## 4. 追问应对

| 可能追问 | 应答要点 |
|---|---|
| 「你写了多少代码？」 | 我主导的模块对应的质量保障：92 项单元测试 + 30 项回归测试，核心链路通过率 98.4%；代码量可以按模块描述，不虚报总量 |
| 「团队其他人为什么不反对你的方案？」 | 方案先过设计评审，且有评测/数据支撑，改动带量化回退，不是拍脑袋 |

| 「协作中最难的一件事？」 | 准备 1 个真实案例：例如"把结算业务口径从业务方讲清楚并落到规则里"，体现沟通与对齐 |

## 5. 表述边界清单

**不说的（越界风险）：**
- 编造团队人数、导师头衔、他人职责
- 「整个项目都是我一个人做的」
- 「结算业务口径是我全权定的」——这是业务方责任，不是你冒领的地方
- 未经证实的线上长期监控数据（按口径文档表述为日志抽样/固定回放集）

**要说的：**
- 我主导的模块 + 该模块的量化结果
- 协作对象明确（与财务对齐、与前端配合、导师评审）
- 设计决策的理由与备选方案（体现真正的 Owner 感）

## 8. 候选素材库（协作难点 + 技术反思）

> 以下候选均基于 EnergyOps 文档中的真实设计推导。**请只选择真实发生过的**，未发生的不要采用——面试官会追问细节。

### 协作难点候选

**候选 A：把「结算业务口径」从业务方讲清楚并落到代码里**
- **S**：月度结算涉及真金白银，分摊规则、口径、责任人确认牵扯行政和财务。一开始靠口头对齐，规则容易漏、口径容易变。
- **T**：把结算流程固化成可验证、可审计的规则，同时不能剥夺财务的最终裁决权。
- **A**：设计三道质量门（事实源门 → 预演门 → 责任门），把"哪些自动校验、哪些人工确认"用代码固化，和财务团队逐条对齐分摊口径。
- **R**：结算从"人工 Excel 对账"变成"带规则版本和差异检查的可核验流程"，正式分发版必须经行政 + 财务两道确认。
- **体现能力**：业务理解、跨职能协作、把模糊业务规则工程化的能力。

**候选 B：让团队接受「Prompt 不是安全边界」这个新思路**
- **S**：Agent 是新方向，团队一开始倾向用 Prompt 约束模型行为，觉得够用。
- **T**：把"能由代码确定性保证的，不交给模型"落实到架构。
- **A**：先用 80 条越权用例证明 Prompt 约束会漏，再实现 Before Tool Hook 参数校验 + R0/R1/R2 分级，给团队做演示。
- **R**：越权拦截 100%，团队接受 Hook 链治理方案。
- **体现能力**：技术判断、说服力、用证据推动架构决策。

**候选 C：远程协作下的接口与状态协议对齐**
- **S**：前端工作台同学要消费 Agent 长任务状态，但最初接口和状态字段是两边各写各的，联调反复返工。
- **T**：让"进度推送 + 状态机"成为前后端都遵守的约定。
- **A**：我定义统一的任务状态机与 SSE 事件格式，先出协议文档，双方按文档实现，再加 E2E 回归兜底。
- **R**：SSE 进度推送 + 30 次断线演练状态恢复率 100%，联调返工明显减少。
- **体现能力**：接口设计、协作规范、以约定代替口头沟通。

### 技术反思点候选

**候选 A：质量状态分类最初低估了「倍率变更」这类边界情况**
- 一开始 7 类质量状态里"倍率变更"只做了简单标记，没考虑它需要结合历史上下文判断，导致早期部分读数异常漏检。
- 后来靠"历史回放 + dry-run 准入"在历史数据上把规则跑一遍，才发现并补齐。
- **反思**：定义规则时不能只看单点，要考虑需要历史上下文的边界情况；凡是规则都先回放验证再上线，而不是直接生效。

**候选 B：告警规则一开始直接上线，噪声大**
- 最初规则直接上线，一天几十条告警，运营产生疲劳，真问题被淹没。
- 后来引入"历史 dry-run 准入 + 告警指纹去重 + 三层分离（基线→候选→通知）"，告警量降 43%。
- **反思**：告警类系统要先把"候选"和"通知"分离，先用历史数据证明规则有效再上线，而不是边发边调。

**候选 C：长内容治理最初只做了读侧 Offload，写侧 Onload 是后补的**
- 一开始只解决"大结果进上下文"的读侧问题（Offload 到 Artifact）。
- 后来才补上写侧 Onload（模型传 filePath → 校验白名单 → 读文件），并明确了"读侧降级、写侧阻断"的失败语义。
- **反思**：Agent 工程的失败语义要按操作代价区分——越接近生产写入，自动化越要转向可验证、可阻断；读侧可以降级，写侧必须阻断。
