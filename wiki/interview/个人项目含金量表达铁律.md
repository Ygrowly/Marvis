# 个人项目含金量表达铁律

## 0. 三条铁律（第三条 2026-10-02 补入）

| #   | 铁律                  | 一句话                                             |
| --- | ------------------- | ----------------------------------------------- |
| 1   | **简历不是功能清单，是决策链**   | 每条 bullet 写成「**具体问题 → 技术取舍 → 验证结果**」，让面试官有东西可追问 |
| 2   | **价值被降格时，接住但不全盘接受** | 三段接法：① 承认对方对的那部分 ② 用你独有的技术点划清边界 ③ 主动暴露局限，拿回叙事权  |
| 3   | **立意先于表达** | 说不出「谁省了什么」，或用一句「A ≠ B」点名这一格之前，**不要在措辞上补救**——回 `templates/项目说明模板.md` 第零阶段过闸（有价值 V × 垂直 H × 可证明 P） |

**为什么这三条是一件事**：写不出取舍，是因为你没在简历里留下"值得追问的点"；讲不出边界，是因为你没在心里划清"我和现成工具的区别"；**而取舍和边界都划不清，八成是立意这一格没切到位**——你讲的是一整块通用能力（垂直度不够），自然说不出「别人做不到、我做得到」的那一句。取舍、边界、立意是同一个东西的三面。

**第三条的用法（最重要）**：遇到「这不就是 X 吗 / 现成的 Y 不就够了」这类追问，先别接话，先在心里问一句：**我这一格切得够不够细？** 切对了，边界句自动就在嘴边；切错了，再怎么组织语言都是辩解。

**心理前提（别再犯错）**：个人项目不需要独一无二、不需要创新或革命。**有思考、有考量就够了**。面试官问"为什么不直接用现成工具"，不是在为难你，是在给你递话筒。

## 0.5 上价值公式（画饼）的逐层用法

> **判据正本** = `templates/项目说明模板.md` §0.3（五层表与降维纪律）。**本节只放面试 / 汇报场景的逐层用法与话术示范，不复制判据正文。**

**一句话纪律**：**饼只能画在已做出来的证据的延长线上**（先讲实测数字，再讲「这套机制推广开还能……」）。

**逐层怎么用**：

| 场景 | 讲到第几层 | 理由 |
|---|---|---|
| 面试官问「你打算为我们做什么」 | **L3 为止**（已有证据 → 团队内复用 → 业务指标），L4 一句带过 | 讲 L5「建立行业标准」会被追问「你凭什么」，答不动即减分 |
| 老板 / 创始人问 | 可到 L4（开源参考实现），**必须带「先跑通一个产品」的前置** | 画饼的价值在路径，不在终点 |
| 简历书面 | **只到 L1 / L2**，不写开源与标准 | 写上去而仓库是空的 = 现场打穿风险（见 `简历写作方法论.md` §1.6） |

**每一层都要能接住一层追问**：讲 L2「帮 N 个产品打通记忆」，就要答得出**打通的障碍**（各家记忆 schema 不同 / 读写权限边界 / 冲突由谁裁决）；讲 L3「业务更了解客户」，要点名它下面是**留存还是客诉**，而不是停在这四个字上。

### 两个 idea 的「切一格」示范（同一套动作，两个域）

| 原说法（不垂直） | 切成的一格 | 点名用的「A ≠ B」 | 为什么别人说不出口 |
|---|---|---|---|
| 做一个外挂记忆系统 | **记忆的可信性**：每条记忆带来源与证据等级、写入幂等、冲突有裁决规则 | **「记得住 ≠ 记得对」** | 现有开源都在卷检索（记得全、召回准），**没人卷写入侧的事务性** |
| 做一个智能 E2E 平台 | **用例采集与用例验证的分离**：离线大模型生成用例，在线只跑 AX Tree + 确定性断言 | **「用例生成难 ≠ 用例判定难」** | 在线每步过大模型不可接受（贵 + 脆弱），**贵的跑一次、便宜的跑一万次** |

**这两句的复用方式**：它们最值钱的场合不是立项，而是**面试里展示判断力**——「如果我来做 X，我不会做 X 的整体，我会切这一格，理由是……」。一句就能证明你会选题，而不只是会写代码。（两个 idea 的完整分析见 `wiki/sources/2026-09-30-外挂记忆系统与现代E2E-项目idea分析.md`）

## 1. 铁律一：具体问题 → 技术取舍 → 验证结果

### 1.1 写法对照（用多 Agent 平台举例，通用模板）

❌ 弱（功能清单，看不出哪里需要思考）：
> 开发多 Agent 协作平台，支持群聊、任务拆解、角色管理和长期记忆。

✅ 强（问题→取舍→验证，每段都能引出追问）：
> 针对多 Agent 并行开发中**任务依赖、重复派发与计划变更导致的结果失效**问题，将**模型规划与确定性调度分离**，设计基于 DAG 的任务调度与**计划版本校验**机制，并通过**掉线、重复回报、执行中重规划**等场景验证恢复能力。

强在哪：说出"原方案会出什么问题"（结果失效）→ 说出"我选了什么、放弃了什么"（规划与调度分离，而不是让模型全权决定）→ 说出"怎么证明"（掉线/重复回报/重规划三个失败场景）。

### 1.2 通用句式模板（写 bullet 时逐格填）

```
面向【谁的什么问题：原来怎么做的，代价是什么】
→ 我选择【方案A】而不是【现成方案B / 更简单方案C】，因为【约束：成本/确定性/权限/可复现…】
→ 结果是【可验证数字 or 边界声明】，代价是【我接受的 trade-off】
```

三条自检（写完逐条过）：
1. **能不能被追问？** 读完让人想问"为什么分离？版本怎么校验？掉线怎么恢复？"—— 能问就是好 bullet。
2. **有没有回答"为什么不用现成的"？** 没写清楚就是默认"其实可以直接用"。
3. **数字是不是能复算的？** 没有测量就写"设计目标/门禁口径"，不写"显著提高效率"。

### 1.3 面试官判断含金量的五个角度（按这五个备弹药）

| 角度              | 他在问什么                       | 你的弹药                 |
| --------------- | --------------------------- | -------------------- |
| **① 是否解决真实问题**  | 谁会用？原来怎么做？减少什么麻烦？           | 见第 2 节每个项目的「问题」段     |
| **② 是否理解关键设计**  | 为什么这样拆，不那样拆？复杂度换来什么？        | 见第 2 节每个项目的「取舍」段     |
| **③ 是否处理过失败情况** | 超时、重复消息、重启、冲突怎么办？           | 见第 2 节每个项目的「失败」段     |
| **④ 是否有可信结果**   | 同任务、同模型、同工具条件下的对比？          | 只报能复算的数字，见第 2 节「验证」段 |
| **⑤ 是否真是你做的**   | 能不能沿一次真实任务讲完输入→调度→执行→恢复→验收？ | 准备一条端到端真实任务流水（第 4 节） |

> 吸引面试官的不是名词多，是**留下一个你确实讲得透的技术点**。
> 例：RuleArena 最该突出的是「动态计划下如何可靠执行和验收」，不是"用了几个 Agent"。

## 2. 三个项目的口述改写稿（90 秒深挖版，不是简历 bullet）

> **定位（2026-10-03 修订，原标「可直接贴简历 / 可直接念」）**：本节按「讲透、能被追问」写，是**口述量级**。简历 bullet 不从这里贴——按 `output/resume/简历写作方法论.md` §3 与 `简历版面规划.md` §2 的预算压缩（一页版：实习 5 条、项目 ≤4~5 条、每条 ≤2 行），从 `output/resume/刘宇广-网申-公共层.md` 取用；**一页版压掉的条目正好落回本节当追问弹药**。两版冲突时：简历归版面规划管，本节负责深挖。

> 事实口径：**只用真实做过的事**。**数字分两种，绝不混用**：**实测**（写清版本 + 命令，如 RuleArena 的 golden-v4，可用 `uv run rulearena benchmark verify --latest` 复核）与**设计目标/门禁阈值**（如 hidden 发现率 ≥75%，属 E3，**不得进简历**）。等级定义见 `output/主张-证据账本-刘宇广.md` 第 5 节。

### 2.1 RuleArena（个人项目，最需要改）

**现在的写法偏弱在哪**：开头是"把自然语言规则编译为可执行契约…"——在描述机制，没有先说"不出这个系统会出什么事"，也没说"为什么不能用现成的混沌工程/LLM 审文档"。

**改写版（问题 → 取舍 → 验证）**：

> **问题**：电商资损事故大多不是单条规则错，而是**订单/优惠券/积分/退款在特殊顺序下组合出错**——单测只覆盖想到的路径，LLM 审 PRD 只能给风险提示，都不能证明"真实系统里这条路径真的能走通"。
>
> **取舍**：
> - 规则不直接给模型执行，先编译成经人工确认的 **RuleSpec**（只允许固定原语、禁止动态求值、冻结 RuleVersion）——代价是多一次人工确认，换来歧义可归因、结论可绑定到版本。
> - **模型只提议，不裁决**：候选路径先在 Reference Simulator 快速剪枝，晋升到独立 Commerce Sandbox 用**真实 HTTP API 重放**，由独立 Oracle 按**资金守恒、状态生命周期、幂等不变量**裁决——代价是全流程慢（多了模拟器和重放两层），换来"不自己验证自己"（Agent 全程触达不到 Ground Truth）。
> - 主流程用**显式 FSM**而不是 Agent 自由编排——代价是灵活性，换来失败语义清晰、可 Checkpoint 恢复。
>
> **验证**：
> - **已实测**（**golden-v4 / deepseek-v4.1-flash / seed 20260831**）：21 + 17 双评测集（hidden 物理隔离、Runtime 不可读），四基线归一化预算消融——dev 集 **Multi-strategy 5/14 高于确定性 BFS 2/14**（Random 0/14、Single 4/14）；但 hidden 集**连续重复 3 次**暴露 **`pass@3 = 8/14`（57%）而 `pass^3 = 1/14`（7%）**——**单次成绩掩盖了搜索不可复现**，这条比任何单次发现率都重要。据此 **Release Gate 如实拒绝放行**（hidden 8/14 = 57% < 75% 门槛，9 项检查过 8 项）。
> - **机制层全部达标**（必须与上一句**成对说**）：零误报（dev 0/7、hidden 0/3）、零 Ground Truth 泄漏、稳定重放 **42/42**。
> - **`hidden 发现率 ≥75%` 是门禁阈值（E3 目标），不是成绩**——简历上不得出现，只有 BenchmarkRun 跑完才可能变实测值。
> - 确认违规经**删除式 Delta Debugging** 压成 1-minimal 反例，绑定完整证据链（请求序列 + 回执 + 事件 + 状态 Diff + 违反的不变量）；修复版本自动重放历史反例
> - 写动作带**幂等键 + ActionReceipt + `ACTION_UNKNOWN`**，覆盖掉线、重复回报、超时后重查权威状态三类失败场景
>
> **边界（主动说）**：被测对象是独立 Sandbox（真实业务系统的**替身**），不是真实线上流量，更不是客户的生产系统；门禁只能声明"预算内未发现"，不能声明"规则安全"。

**这条 bullet 会引出的追问**（每个都要能答）：为什么分离规划与裁决？版本怎么校验？掉线/超时后怎么恢复？Oracle 不变量哪来的、会不会自证？多策略消融结果如果不占优怎么办？

**最该突出的唯一技术点**：**动态计划下如何可靠执行与验收**（幂等 + 权威状态重查 + 确定性裁决 + 回归门禁），不是"用了几个 Agent"。

**一页版裁掉的条目（2026-10-03 压缩 7→5，口述弹药，正本 = RuleArena 项目说明 §0.7）**：
1. **NL→RuleSpec 编译链路**（固定原语 / 禁动态求值 / 歧义人工确认冻结 / 未确认不进攻击）——summary「类型化工具契约」层的第一展开，作战地图 4.1 有完整追问链；
2. **SSE 前后端一致性**（SSE 只做通知，加载 / 重连 / 刷新一律 GET 权威状态对账，消除「断线后 UI 假完成」）——被问「前端怎么做的」用它接，一句带过；技能行「前端 & 实时」仍保留该关键词。

### 2.2 金山 EnergyOps（实习，主投游戏服务端岗时主讲）

**问题**：园区只有第三方平台的原始累计读数，**质量差、缺口不可见**，行政按月手工对账、告警一天几十条真问题被淹没；给行政一个对话入口很容易，难的是**让 Agent 的写操作可控**。

**取舍**（挑一个讲透，别全讲）：
- 30 个工具收敛为 6 类 Capability Bundle + **R0/R1/R2 三级风险**，在 Before Tool Hook 统一拦截 —— 代价是业务每加一个能力都要声明风险级，换来治理策略可插拔、核心 Loop 不随业务改。
- 数据分四层（raw→interval→hourly→daily）+ **7 类质量状态与可信白名单**，只有可信区间能进聚合 —— 代价是要维护质量状态机，换来聚合结果可解释、缺口可定位。
- 权威状态放 PostgreSQL、Redis 只做队列 —— 代价是延迟，换来事实源不漂移、可审计。

**验证**（都能复算，直接用）：
- 604 台设备、15 分钟周期、日均 5.8 万条读数，可信聚合完整率 96.8% → 99.7%（口径：有效区间 ÷ 应产生区间）
- 72 条任务评测集任务完成率 83.3% → 95.8%；80 条越权用例拦截率 100%
- 固定查询集核心统计接口 P95 20.4s → 2.8s
- 幂等窗口 + 任务状态持久化 + 启动 7 天回补：定时聚合成功率 96.9% → 99.6%，人工补数次数降 72%
- 4 类异常规则历史 dry-run 准入 + 告警指纹去重：告警量降 43%，研判 18min → 6min

**失败处理（主动讲，最见功力）**：第三方服务中断 → 缺失标记 + 自动回补；服务重启/乱序补数 → 幂等窗口去重；重复消息/重复派单 → 指纹去重；R2 未确认 → 直接阻断不给执行。

**画饼 30 秒（2026-10-03 补，正本 = EnergyOps-项目说明 §0.7.3；纪律见 §0.5——饼只画在证据延长线上，面试停 L3）**：

- **面试官版**（问「你打算为我们做什么」）：「这套东西的内核是两件可复用的事：**第三方参差数据的可信化流水线**（分层建模 + 质量状态机 + 白名单准入）和 **Agent 写操作的分级治理框架**（Capability Bundle + R0/R1/R2 + Hook 链，策略可插拔）。贵司凡是『要接外部数据』或『要给 Agent 开写权限』的场景，这两层可以直接搬——换的只是质量规则和风险分级配置，核心 Loop 不改。我会先挑一个真实场景把框架落进去，跑出对比数字再横向推。」
- **被追问「怎么打通」的障碍答案**：每个新场景沉淀一张「三件套」配置——字段/点位映射 + 质量规则（7 类状态的领域变体）+ 风险分级表；责任门涉及业务责任体系要重定、费用分摊规则是领域知识，这两块不能直接搬，如实说。
- **老板版**（可到 L4）：面试官版结尾加一句「框架稳定后可抽成公司内部的 Agent 操作治理中间件，新 Agent 项目开箱即用」——参考实现量级，不说「行业标准」。

### 2.3 数驭穹图（实习，主投 AI/Agent 岗时主讲）

**问题**：中小企业业务人员想用数据，被"找数据同学 → 写 SQL → 等排期"卡住；更麻烦的是**同一个"销售额"在不同行业口径完全不同**，模型直接写 SQL 大概率答非所问，而且**"SQL 能跑通"不等于"业务答案对"**。

**取舍**：
- 先建**语义层**（3 套 Domain Pack：65 指标 + 120 别名 + 口径 + 表关联约束）再谈查询 —— 代价是每进一个新行业要沉淀 Domain Pack，换来口径统一、歧义可枚举澄清（澄清选项来自 Domain Pack，不是模型现编）。
- 链路拆 6 阶段（意图路由 → 域内检索 → SemQL → SQL → 安全校验 → 执行）——代价是链路长，换来**错误可独立归因**：业务理解错 vs SQL 写错 vs 权限拒绝，各归各层。
- 五层安全边界，只读 SQL AST 审查 + 服务端注入 tenant_id —— 代价是部分复杂查询被拦（误拦 2.7%），换来危险语句 100% 拦截。
- 大结果外置 Artifact、模型只收口径摘要与聚合统计 —— 代价是多一次外置/引用，换来上下文 18.4K → 3.6K。

**验证**：150 条评测集 Top-K Schema 召回 81% → 95%，查询成功率（**口径：最终 SQL 可执行且结果口径正确——不是端到端**）78% → 91%；300 条对抗请求危险语句拦截 100%、正常误拦 2.7%；100 条抽检复现一致率 100%（call_id + query_fingerprint + result_hash 三重绑定）。

**失败处理**：错误回灌限次修复并区分四类（语法/字段缺失/方言差异/权限拒绝）；慢查询 EXPLAIN 预估拒绝 + 副本优先；权限撤销对下次查询即时生效。

**画饼 30 秒（2026-10-03 补，正本 = 数驭穹图项目说明 §0.7.3；纪律见 §0.5——面试停 L3）**：

- **面试官版**（问「你打算为我们做什么」）：「这项目的内核是两件可复用的事：**企业语义层方法论**（Domain Pack：指标口径 + 别名 + 关联约束 + 健康度评分与一票否决）和**『SQL 能执行 ≠ 业务答案正确』的可信问数链路**（六阶段可归因 + 固定评测集 + 证据绑定）。贵司凡是『业务术语和数据对不上』或『模型生成的数字要被当真』的场景——经营分析、报表自动化、内部 ChatBI 升级——这两层直接搬。我会先接一个业务域沉淀 Domain Pack、跑出对比数字，再横向推。」
- **行业位置现成弹药**（项目说明 §10，2026-10-03 核对修正）：Snowflake Cortex Analyst / Databricks Genie 验证「语义层 + LLM 问数」是企业级方向，但绑定自家数仓、面向大客户；**语义层本身已是国内共识（SuperSonic / Wren AI / Kyligence）——差异别放在「有语义层」**，放在语义层之上的口径治理（一票否决、fail-closed）与证据闭环（三重绑定 + 结果沉淀回写），叠加不绑定数仓的轻量湖仓。
- **障碍答案**：每个新行业的 Domain Pack 人工沉淀是最重的一块成本；口径一票否决依赖业务方参与裁决——如实说，这是机制不是缺陷（过期语义不能冒充当前口径）。
- **老板版**（可到 L4）：加一句「语义层抽象稳定后可抽成公司统一的指标口径中间件，新数据产品开箱即用」——参考实现量级，不说「行业标准」。

## 3. 铁律二：被降格时的三段接法

**模板**：
1. **接住但不全盘接受**：「您的说法对了一半——[承认对方对的那部分]」
2. **用独有技术点划边界**：「但目标/机制不一样：[一句话差别]，具体差别在 [你的独有机制]」
3. **主动暴露局限，拿回叙事权**：「您说的对的一点是，目前我确实还没做 [X]，这是它现在最大的局限；理想形态是 [Y]」

> 关键动作：**不等他问，自己先说局限**。先说缺点的人掌握叙事权；被问出来的缺点才叫减分。

### 3.1 卡 A（已实战，乐元素二面 B6）：「不就是 API 测试 / 故障注入」

> 「故障注入是手段之一，但目标不一样：故障注入验证系统在故障下**不崩**，我这个要在促销规则上线之前**主动搜索会导致资损的规则组合**——面向业务正确性的对抗验证，不是面向可用性。
> 具体差别在裁决器：我会做**资金守恒校验**（用户多得的优惠 = 平台多付的成本），这是纯故障注入工具不会做的。
> 您说的对的一点是，目前我确实只跑了本地构造的用例、没接真实线上流量，这是它现在最大的局限；理想形态是接灰度环境真实流量做影子重放。」

**改了什么**：① 接住不全盘接受 ② 用「资金守恒」划边界 ③ 主动暴露局限。

### 3.2 卡 B：EnergyOps「不就是 CRUD + BI 看板 / 数据搬运」

> 「存储和看板是其中一层，但真正的难点在数据**可信**和执行**受控**这两件事上。
> 不信的部分：第三方累计读数有缺失、回退、倍率变更，我先判 7 类质量状态再决定它能不能进聚合，聚合完整率 96.8 → 99.7 就是这么来的——直接展示原始读数会得出错误的能耗账。
> 受控的部分：这是给行政用的 Agent，写操作按 R0/R1/R2 分级、高风险必须预览确认，80 条越权用例 100% 拦在工具执行前。
> 局限我也说清楚：第三方平台一旦中断我只能标记缺失再回补，做不到实时；月度结算口径仍然以人工抄表底稿为准，自动聚合只做交叉核对。」

### 3.3 卡 C：数驭穹图「不就是 NL2SQL / ChatBI，套个壳」

> 「NL2SQL 是其中一步，但光有它答不对。同一句"销售额"，出海电商和医美的口径完全不同，所以先有语义层（指标口径 + 别名 + 合法关联）再谈查询；
> 更难的是**"SQL 跑通"不等于"业务答案对"**——所以链路拆 6 阶段让错误可归因，结果绑定证据（SQL + 数据快照 + 结果 hash）可复现，100 条抽检复现一致率 100%。
> 边界：目前只覆盖结构化查询场景，跨源复杂建模和口径自动发现还没做，Domain Pack 仍是人工沉淀，这是它现在最重的一块成本。」

### 3.4 卡 D（通用，一定会遇到）：「这是 AI 写的吧？你做了什么？」

> 「用 AI 写代码是事实，我重度用 Claude Code/Codex。但**架构决策、取舍和不变量定义是我定的**：[举一个具体决策，如"Agent 只提议不裁决、Oracle 独立部署" / "工具按 R0/R1/R2 分级"]。
> AI 能帮我把实现写出来，但它不会替我回答"为什么这两个组件必须分离"、"预算怎么给才公平"——这些写在文档第 9 节架构取舍表里，每一条都有被放弃的替代方案和代价。」

> 原则：**不否认用 AI**（会被追问细节戳穿），把话题拉到"决策是我的"。

## 5. 事实安全红线（写在最前面也写在最后面）

1. **没跑过的写"设计目标 / 门禁口径"，跑过的写"实测 + 版本 + 命令"**，两者绝不混用。
2. **没有测量就不写数字**，不写"显著提高/大幅降低"。
3. **不能用局部结果冒充整体结论**：24-Case 平台基准证明"机制可信度"，不等于"某条规则安全"；门禁只能声明"预算内未发现"。
4. **不抢别人的活**：结算财务口径、前端表格引擎、产品定位 —— 明确说"这部分不是我做的"反而加分。
5. **概念不能错**：SSE 是长连接；502 vs 504 vs 503 语义不同；乐观锁/悲观锁的差别在冲突假设。说错一次，整场可信度打折。

## 6. 60 秒项目介绍骨架（任何项目通用）

```
① 一句话定位（10s）：这是什么、给谁用
② 问题（15s）：原来怎么做、代价是什么、不出这个系统会出什么事
③ 取舍（20s）：我选了 A 而不是 B，因为 [约束]；代价是 [X]
④ 验证（10s）：可复算的数字 + 口径
⑤ 边界（5s）：现在最大的局限是什么、理想形态是什么
```

收尾句（三个项目通用）：**「Agent 生产化的瓶颈在可靠性工程，不在模型。」**

证据版收尾（2026-10-03 起，被追问「凭什么这么说」时用）：**「模型能力已经是商品，瓶颈在模型之外的信任工程——数据侧治理、执行侧分级、发布侧门禁。这三块恰好是生态自己在补的课：语义层成了 ChatBI 共识（SuperSonic / Wren AI / Kyligence）、运行时 guardrails 在起势、τ-bench 把一致性变成标准度量——我三段经历各占一格。」**
