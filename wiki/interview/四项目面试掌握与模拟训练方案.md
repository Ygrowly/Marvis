## 1. 核心结论

不要按四份完整项目说明逐章背诵。四份说明合计约 3700 行，逐篇背会造成输入超载、项目互混、追问时无法调用。

新版项目说明的最大变化是：每份文档新增了**「设计哲学与核心范式」**章节，从第一性原理推导出工程决策。这意味着面试时最有力的差异化不再是"我做了 X 功能"，而是"我为什么选择 Hook 链而不是 Prompt 约束""为什么支付回调要阻断而不是降级"。

正确训练单位是：

> **8 条共性能力轴（含 1 条范式轴）+ 约 36 个项目母题（含范式对比题）+ 45 组量化口径 + 三层递进追问 + 模拟面试。**

四个项目的面试优先级不变：

| 优先级 | 项目 | 面试定位 | 首轮投入 |
|---|---|---|---:|
| P0 | EnergyOps Agent | 当前实习、真实业务、数据/后端/Agent 综合证据 | 3 天 |
| P0 | PayTrace | 个人主导、Agent Harness、证据契约与 Eval 差异化 | 3 天 |
| P1 | 数驭穹图 | Data Agent、语义层、NL2SQL、安全执行与协作闭环 | 2 天 |
| P1 | Ovanta | 真实上线产品、支付权益、异步埋点、区域化后端基本盘 | 2 天 |

优先级只决定训练顺序，不代表可以放弃后两个项目。

## 2. 面试官到底在问什么（新增）

在启动训练之前，先理解面试官的底层逻辑。综合大厂面经和面试官自述，核心只有一句话：

> **面试官不关心你的代码细节。他们关心的是：这件事你是不是真的做过、你是不是知道它为什么要做、以及你有没有形成可迁移的判断力。**

### 2.1 面试官的三类底层追问

| 追问目标 | 典型问法 | 考察什么 |
|---|---|---|
| 验证真实性 | "具体哪个时间节点？""数据怎么算出来的？""你写的还是别人写的？" | 你是否真的参与，而非旁观或编造 |
| 验证理解深度 | "为什么选这个方案？""还有什么替代方案？""如果重新做，你会怎么改？" | 你是否理解背后的 tradeoff，而非照搬执行 |
| 验证可迁移性 | "如果你去另一个业务线，你会怎么做？""这个设计能复用到什么场景？" | 你是掌握了方法论，还是只能背一个项目 |

### 2.2 三个核心问题

几乎所有面试都会围绕这三个问题展开：

**问题一："介绍一下你的实习/项目吧。""**

回答骨架：**大部门/项目业务 → 你的服务在整体中的作用 → 举一个具体例子 → 你做了什么、有什么量化收益。** 控制在 90 秒以内，不要讲代码细节，把细节留给面试官追问。

**问题二："能介绍一下你们服务的业务架构吗？""**

回答骨架：**上下游依赖关系 → 服务内部模块划分 → 关键数据存储和读写链路。** 不需要画出完整架构图，但要能说清楚"谁调你、你调谁、数据怎么流"。

**问题三："讲一个你实习/项目中的难点吧。""**

回答骨架：**需求背景（1-2 句）→ 快速讲清链路 → 指出难点在哪里 → 都想了哪些方案 → 选了哪一个 → 为什么这样选。** 这是拉开差距的核心问题。

> 核心原则：**不要过度陷入代码细节。快速讲清整体逻辑后直接进入难点，不要又臭又长。**

### 2.3 难点讲完后，面试官的追杀方向

| 追问方向 | 典型问法 | 准备要点 |
|---|---|---|
| 继续优化 | "还能进一步优化吗？""瓶颈在哪？" | 提前想好方案的容量上限和下一步改进方向 |
| 极端场景 | "更极端的流量/数据量下怎么办？" | 想清楚单机→分布式的扩展路径 |
| 横向迁移 | "换成售后业务你怎么做？""如果数据源变了呢？" | 把方法论抽象出来，证明换个场景也能用 |
| 失败复盘 | "你项目中最大的失败是什么？""学到了什么？" | 准备一个真实的失败案例，讲清楚根因和收获 |

### 2.4 三层追问模型

网上高质量面经将面试考点分为三层，这恰好对应我们训练的三个深度：

| 层次 | 覆盖面 | 内容 | 训练要求 |
|---|---|---|---|
| **基础必问层** | 90% 面试 | 项目背景、个人职责、核心链路、量化结果 | 脱口而出，不能卡壳 |
| **进阶深挖层** | 70% 面试 | 技术选型原因、方案对比、优化链路、Bad Case 处理 | 有结构、有逻辑、有数据 |
| **死亡追问层** | 大厂/核心岗 | 架构重构、极端场景、跨领域迁移、失败复盘、底层原理 | 展现方法论和判断力 |

### 2.5 对你的直接影响

基于上述面试逻辑，你的训练必须做到：

1. **每个项目先练三个核心问题**（介绍、架构、难点），而不是先背细节。
2. **每个回答按"业务问题 → 约束 → 方案 → 验证 → 边界"结构组织**，避免变成代码细节堆砌。
3. **所有量化数字必须能现场解释公式、样本、改动和证据边界。**
4. **范式层训练**解决"为什么要这样做"和"换一个场景怎么做"的追问。

## 4. 四个项目的最小恢复地图（更新）

### 4.1 EnergyOps Agent

一句话：

> 把不稳定的水电表累计读数转化为可信用能账、异常事件账和财务结算账，再通过受控 Agent 统一查询和操作入口。

**核心范式：**
- **Hook 链治理**：Before Tool 阻断写操作（R0/R1/R2），After Tool 登记 Evidence + Artifact，Before Model 注入副作用。核心原则：能由代码确定性保证的，不交给模型。
- **三账一体**：用能账（物理事实）→ 事件账（异常与处置）→ 结算账（费用归属），通过设备、区域、时间窗口关联。
- **三道质量门**：事实源门 → 预演门 → 责任门。越接近生产写入，自动化越转向可验证和可审计。
- **Offload/Onload**：读侧降级（Artifact 落盘失败透传原文），写侧阻断（路径不在白名单拒绝执行）。失败语义与操作代价匹配。

恢复关键词：

> 累计读数、区间用量、七类质量、分层聚合、三账、Capability Bundle、R0/R1/R2、Hook 链、三道质量门、Offload/Onload

主链路：

```text
同方累计读数
→ 标准化与质量判断
→ raw / interval / hourly / daily
→ 查询与异常检测
→ Incident、证据与处置
→ 月度结算与财务核验（三道质量门）
→ WPS Comate 受控操作（Hook 链治理）
```

### 4.2 PayTrace

一句话：

> 用确定性代码计算支付损失，用 Agent 调查原因，用证据契约阻止无依据归因，再用隔离 Ground Truth 的故障注入持续评测。

**核心范式：**
- **确定性系统计算事实，模型负责组织调查**：损失数值精确可复算，根因假设在不确定信息中逐步收敛。
- **Hook 链治理**：Before Tool 校验参数/范围/权限，After Tool 登记 Evidence + 更新 Hypothesis Ledger。
- **证据契约**：Claim → Evidence → 自动校验（十道门禁），"没有 evidence 的 done 只能视为口头完成"。
- **Hypothesis Ledger（DAG 化）**：每个根因假设变为 DAG 节点，记录支持证据、冲突证据、替代解释、状态流转。
- **评测闭环**：Response + Trajectory 双评测，Ground Truth 隔离，pass^k 衡量生产可靠性。
- **模拟数据的诚实边界**：明确声明能证明什么、不能证明什么。

恢复关键词：

> 九阶段、Purchase Intent、损失账本、Harness、Before/After Tool Hook、Hypothesis Ledger、Evidence Contract、十道门禁、Ground Truth 隔离、pass^3、诚实边界

主链路：

```text
支付转化异常
→ Incident 与九阶段定位
→ Purchase Intent 损失去重
→ Harness（Hook 链）调用七类只读工具
→ Hypothesis Ledger 推进调查
→ Claim 绑定 Evidence（十道门禁校验）
→ 人工复核
→ Ground Truth 隔离评测
```

### 4.3 数驭穹图

一句话：

> 统一接入企业多源数据，通过语义层与 NL2SemQL2SQL 完成可信问数，并把结果沉淀为协同表格、报告和动态看板。

**核心范式：**
- **业务事实层先于 Agent**：Agent 不得成为第二套事实链。AI 查询必须读取与后台一致的当前态数据。数据过期时 fail closed。
- **SQL 能执行 ≠ 业务答案正确**：五层保障（语义层 → 权限贯穿 → 只读安全执行 → 结果验证 → 证据绑定）。
- **Workflow 管主流程，Agent 处理局部决策**：能画成有限状态机的优先用 Workflow；模型只在受限能力包内做局部决策。
- **Tool 是业务契约**：每个 Tool 必须回答：解决什么业务任务、合法参数、返回什么事实、失败如何区分。
- **ChartSpec 证据绑定**：合法 JSON ≠ 可信图表。图表渲染必须绑定 call_id + query_fingerprint + result_hash。
- **语义资产健康度**：六维评分，指标口径一票否决。

恢复关键词：

> Domain Pack、语义层、AnalysisIntent、NL2SemQL2SQL、只读安全、混合 Runtime、ChartSpec 证据绑定、语义资产健康度、Session Ledger、Atomic Turn

主链路：

```text
数据库、文件、飞书、协同表格
→ 数据目录与权限
→ 业务域和语义资产（健康度评分）
→ AnalysisIntent
→ SemQL 与 SQL（安全校验）
→ 执行和结果验证
→ ChartSpec 证据绑定
→ 表格/图表/报告
→ 反馈与评测回流
```

### 4.4 Ovanta

一句话：

> 把持续变化的签证与身份政策组织成结构化申请产品，用共享核心代码支持国内外站点，并以支付、权益与顾问服务完成商业化交付。

**核心范式：**
- **支付回调 Hook 链**：Webhook 到达 → 验证签名 → 定位订单 → 核对金额 → 状态机校验 → 幂等检查 → 发放权益。每一步失败直接阻断，失败语义与操作代价匹配。
- **运营 AI 的决策边界**：候选 → 洞察 → 结论三层分离，AI 不直接修改 Strapi 内容、价格、套餐、权益或支付配置。
- **内容质量门禁**：来源完整度、时效性、风险说明一票否决式阻断。
- **行为数据质量治理**：前端埋点 ≠ 业务事实。支付、权益、退款指标只使用后端权威事件。
- **E2E 回归覆盖业务不变式**：BDD 模式，Spec 里写的就是后面测的。覆盖支付权益一致性、咨询配额原子性、跨区域身份隔离。

恢复关键词：

> Headless CMS、结构化内容、区域配置、统一用户、订单快照、支付 Hook 链、权益一致性、行为事件 vs 业务事件、E2E 业务不变式

主链路：

```text
公开内容与资格初筛
→ 注册和区域化账户
→ 套餐与服务端订单快照
→ 多渠道支付与 Webhook（Hook 链校验）
→ 权益/咨询/服务履约
→ 行为事件（前端）与业务事件（后端权威）
→ 运营 AI 分析（候选→洞察→结论，不直接修改配置）
```

### 5.2 第八条能力轴：设计范式与工程判断（新增）

这是 v2 方案的核心新增。四个项目的范式高度呼应，面试官追问"你在三个项目里都用了 Hook 链，区别是什么"时，必须能跨项目对比。

| 范式 | EnergyOps | PayTrace | 数驭穹图 | Ovanta |
|---|---|---|---|---|
| **Hook 链治理** | Before/After Tool + Before Model 三层。R0/R1/R2 是 Hook 参数 | Before/After Tool 两层。重点在 Hypothesis Ledger 更新和 Early-Exit | 混合 Runtime：代码控制护栏，模型处理局部决策，有限状态机建模跨域分析 | Before Tool 链式阻断在支付回调链路，每一步失败直接阻断 |
| **读侧降级、写侧阻断** | Offload 失败透传原文；Onload 失败阻断执行 | Artifact 落盘失败透传；参数非法/权限不足阻断 | 相同原则；数据过期 fail closed | Webhook 签名/金额/状态机校验失败阻断 |
| **证据与事实绑定** | Evidence + Artifact + Trace | 证据契约十道门禁，Claim→Evidence→自动校验 | ChartSpec 证据绑定（call_id + fingerprint + hash） | 支付/权益只以后端权威事件为准 |
| **质量门/门禁** | 三道质量门（事实源→预演→责任） | 十道证据门禁 + 四条发布硬门禁 | 语义资产健康度六维评分 + 指标口径一票否决 | 内容质量门禁（来源/时效/风险） |
| **评测闭环** | 六层评测 + 确定性规则评分优先 | Response + Trajectory + pass^k + Ground Truth 隔离 | 五层评测（Contract/Oracle/Evidence/Rubric/Cost） | E2E 回归覆盖业务不变式（BDD） |
| **AI 的决策边界** | AI 可编排但不直接修改读数/费用 | AI 可调查但不能绕过证据契约 | AI 可理解意图但不能绕过权限和只读约束 | AI 仅做运营分析，不修改内容/价格/权益/支付配置 |

### 8.3 全指标覆盖法

建立"指标证据账本"，强化母稿中的每个数字占一行：

```text
项目｜简历原句｜公式/分母｜样本与环境｜Baseline｜Candidate｜主要改动｜证据等级｜高风险追问
```

训练状态只使用四种：

- `UNSEEN`：尚未闭卷解释；
- `LEARNING`：需要提示；
- `PASSED`：可在 45 秒内完整解释；
- `STABLE`：间隔 7 天后仍能解释并回答一个质疑。

"掌握母稿所有内容"的验收不是把文档背完，而是强化母稿所有 bullet 和指标都达到 `PASSED`，P0 项目核心指标达到 `STABLE`。

## 9. 15 天首轮冲刺（重新设计）

原来 14 天方案在项目天数分配上合理，但存在一个问题：每天混合训练多个板块（闭卷 → 回看 → 母题卡 → 语音 → 指标），对新手的认知负荷太高。

v2 将每天结构调整为**"三个核心问题优先"**——每个项目先用三个核心问题建立骨架，再填充母题细节。

### 9.1 三阶段框架

```text
阶段一：项目内化（D1-D10）
  目标：能清晰讲清每个项目的核心范式和依据
  方法：三个核心问题 → 范式理解 → 母题深挖 → 指标防守
  
阶段二：跨项目合成（D11-D13）
  目标：能在四个项目间自由迁移、对比和抽象
  方法：范式轴对比 → 随机跨项目追问 → 指标专场 → 引导式模拟
  
阶段三：压力验收（D14-D15 + 持续）
  目标：能在不提示的情况下承受三层追问
  方法：严格模拟 → 评分 → 修复断点 → 复训
```

### 9.2 每日训练结构

每天 90 分钟，拆成：

```text
15 分钟：三个核心问题闭卷口述（介绍→架构→难点），暴露断点
20 分钟：定向回看对应项目说明和范式章节，只补断点
20 分钟：完成 2 道母题的三层追问卡（基础→进阶→死亡）
15 分钟：范式层专项（设计哲学、Hook 链、证据绑定等）
10 分钟：随机防守 2～3 个量化指标
10 分钟：语音一问一答，连续追问 2 层；记录错因和复训日期
```

## 11. 间隔复训与长期维护（更新）

每个母题首次通过后，在 `+1、+3、+7、+14、+30` 天闭卷复训。范式对比题和跨项目迁移题从 D11 开始单独建立复训池。

1. 不看材料说出一句话、关键词和主线；

## 12. 最终验收标准（更新）

一个项目达到"可面试"必须同时满足：

- 20 秒说出一句话定义；
- 90 秒完成项目介绍；
- 3 分钟回答三个核心问题（介绍、架构、难点）；
- 8 个业务与工程母题全部达到 `PASSED`；
- 2 个范式深挖母题全部达到 `PASSED`；
- 任意核心母题能承受三层追问（基础→进阶→死亡）；
- 强化母稿中该项目所有指标均能解释公式、样本、改动和证据边界；
- 能明确个人完成了什么、团队完成了什么、哪些只是设计；
- 能讲一个失败案例、一个取舍和一个下一步；
- **能用自己的话解释该项目的设计哲学和核心范式，并回答"为什么这样设计"**（新增）；
- 与另外三个项目做一次范式迁移对比；
- 7 天后严格复训仍能独立输出。
