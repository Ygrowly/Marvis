## §0 开场 90 秒（逐句背，含为什么挑这个项目）

> 面试官好，我叫刘宇广，南华大学 27 届，数据科学专业。简历上有两段实习和一个个人项目，方向都写着 AI，但我今天想讲的那段工作，本质是一个服务端工程问题。
>
> 我挑金山那段，园区能耗运营平台。业务问题是：园区 604 台水电表每 15 分钟上报一次累计读数，日均 5.8 万条，但第三方平台给的数据质量很差，掉线缺失、读数倒转跳变、换表换倍率都有。原来的做法是行政导出 Excel 手工对账，一个月一次，错了也不知道错在哪。
>
> 我负责的是从原始读数到可用账目的这条服务端链路，三块：一是入库前的可信判定，定义了 7 类数据质量状态，只有进白名单的数据才允许往下走聚合；二是定时聚合的可靠性，解决任务重跑、宕机漏算、多 worker 并发抢同一个窗口的问题；三是查询性能，核心统计接口 P95 从 20.4 秒压到 2.8 秒。
>
> 结果三条线：可信聚合完整率 96.8% 提到 99.7%，定时聚合成功率 96.9% 提到 99.6%，人工补数次数降了 72%。
>
> 我挑它，是因为它跟游戏服务端是同一类问题：周期触发、必须幂等、结果要能算准账，这三件事我在真实生产里踩过完整的坑。Agent 只是它的入口，不是重点。

**为什么挑 EnergyOps（被追问时才答）**：另外两个我也熟，但数驭穹图偏查询引擎、RuleArena 偏验证方法论，最能证明「我能写可靠的定时任务和数据链路」的是这一个，而这正是 JD 第一条「服务器端通讯系统、逻辑系统的设计及开发」。

## §1 三项目「去 Agent 主语」服务端叙事（每个 60 秒）

> 用法：面试官问「你做的事跟我们的服务端有什么关系」时，直接背这段，不要临场翻译。

### 1.1 EnergyOps = 定时聚合系统 + 数据治理链路

> 把它当成服务端看就三个问题。
>
> 第一，进来的数据不可信。604 台表三种脏数据最常见：某台表掉线导致整个窗口缺失、读数倒转或突跳、换表或变更倍率导致量纲突变。我定义了 7 类质量状态，每个采集点进聚合前先判定，只有可信的才参与计算，脏数据标记但不删、留着溯源。
>
> 第二，定时任务不可靠。15 分钟一个窗口，任何一次重跑、重启、多 worker 并发都会算重或漏。我用「设备 ID + 聚合窗口」做唯一键走 upsert，重跑一百次也只有一行；任务领取用一条条件更新抢占，UPDATE 加 WHERE status 等于 pending，谁改到那行谁执行，数据库的行级约束替我解决并发，不需要分布式锁。
>
> 第三，查询太慢。原来是每次查询都从明细现算，还重复 JOIN 设备维表。做完三件事：去掉重复 JOIN、加组合索引（等值列在前、范围列在后）、小时和日的结果预聚合落表，查询只读结果表。P95 从 20.4 秒到 2.8 秒，降了 86%。
>
> 还有一块我自己认为最关键的：启动时的 7 天自动回补。调度器重启只会接着跑未来的任务，宕机期间错过的历史窗口会永久缺失，这在结算类系统里是不能接受的。我对账最近 7 天应该产生而实际没有的窗口，差集就是缺口，按低优先级补算，走同一套幂等通道所以不会重复聚合。
>
> 复盘句：这套东西放到游戏里就是日结算和周期榜，定时、幂等、可恢复，三个词一个都不能少。

### 1.2 数驭穹图 = 多租户查询网关 + 只读执行引擎

> 剥掉 AI 的外壳，这是一个多租户的查询网关：上游接 MySQL、PostgreSQL、MongoDB、飞书表格等 6 类数据源，中间一层查询引擎，出口管权限、限流和脱敏。三个工程难点。
>
> 一是方言收敛。不同源在分页、时间函数、类型转换上都不一样，我没有让上层去写方言分支，而是把差异收到一层统一的中间计划里，执行前再翻译成目标方言，差异只有一处，不散落在业务代码里。
>
> 二是不能拖垮客户的生产库。客户库有的就是正在跑业务的生产库。我做的是：优先查本地 Parquet 副本；必须直查时用只读账号；执行前先 EXPLAIN 估算代价，超阈值直接拒绝；再加超时和行数上限熔断。这跟只读从库扛查询流量是一个思路。
>
> 三是权限不能靠口头约定。租户 ID 由服务端注入，不是从上层传进来；执行层只给只读账号，再用 SQL AST 审查做兜底，就算前面全漏了，到这一层也写不了库。输出按行列权限裁剪后再脱敏出来。
>
> 数字：端到端查询成功率 78% 提到 91%，300 条对抗危险语句拦截 100%，正常查询误拦 2.7%。
>
> 复盘句：服务端永远不信任上游给的身份，权限必须由服务端自己写入，这条在游戏里同样成立。

### 1.3 RuleArena = 确定性重放引擎 + 不变量裁决器

> 这个项目剥掉 AI，剩下的是一个确定性重放引擎加不变量裁决器。
>
> 背景是电商规则变更：很多事故不是单条规则错，而是优惠券、退款、积分在特殊顺序下组合出错，单测只覆盖你想到的路径。
>
> 做法是：先把规则编译成一份不可变的执行契约，然后让程序去搜动作序列，搜到的候选不能自己说了算，必须拿到一个干净环境里用真实 HTTP API 重放一遍，由一个独立的裁决器按资金守恒、状态生命周期、幂等这三类不变量来判。
>
> 两个服务端关键点。一是写操作必须有幂等键，我用业务身份合成：run_id 加动作类型加目标对象加归一化参数加规则版本加步骤号，配数据库唯一约束。一开始用调用 ID 当键是错的，重规划和超时重试都会生成新 ID，同一个动作就有了好几个身份。二是超时语义，写操作超时后你分不清是没送达、失败、还是成功但响应丢了，做法是拿同一个幂等键去查回执，查不到才敢重试，绝不能换 key 盲重试，因为请求可能已经生效。
>
> 复盘句：这条在游戏里就是防作弊的最高形态，声称者不能兼任裁判。玩家上报「我这局 3 万分」，你要么做合理性校验，要么确定性重放，不能直接信。

## §2 十二条新增追问标答（D1-D8 没写的，按星级背）

> 三星必背，大概率被问；二星备着。

### E-A 三星 · 数据是累计读数，表倒转、换表、改倍率怎么处理？

> 因为源头是累计读数不是区间用量，所以第一步必须做差分：用「本次读数减上次读数」得到这个窗口的实际用量，再做三类校验。
>
> 一、回退：差值小于 0，说明抄错或者表被拆装过，判为回退类脏数据，不进聚合。
>
> 二、长间隔：两个相邻读数的时间跨度超过窗口上限，这份差值不能算作某一个 15 分钟窗口的用量，要做分摊或者直接标不可信。
>
> 三、倍率变更：换表或者变更 CT 变比之后，读数会出现一次量纲级跳变，如果不处理，聚合出来的能耗会凭空涨几十倍。我的做法是给设备维护一个「有效倍率区间」，检测到疑似跳变就判为质量状态里的倍率变更类、先不进聚合，等人工确认后开启一个新的有效区间继续算，历史数据不回改。
>
> 复盘句：累计读数的系统一定要做分段，只要设备的物理属性变了，之前的数据和之后的数据就必须属于不同的有效区间，不能用一个公式算全场。

【核对】以上判定细节是按简历里「7 类质量状态（缺失、回退、长间隔、倍率变更、异常跳变等）」重建的合理版。考前核对真实的字段名和判定方式，阈值记不准就说「具体阈值是跟业务对齐过的」，不要现编数字。

### E-B 三星 · 15 分钟周期，数据迟到、乱序怎么办？

> 第三方平台补数是常态，所以不能假设数据按时间顺序到达。我的处理是容错窗口加幂等覆盖：聚合结果落地后不是终态，允许一定窗口内的迟到数据回流并重算；因为写入是「设备 ID + 聚合窗口」唯一键的 upsert，迟到数据修正旧值不会产生第二条记录，天然幂等。超过容错窗口的数据就不再按小时粒度回溯了，标记不可信走人工补录，或者并入下一次的日粒度重算。
>
> 复盘句：乱序系统的原则是，修正的路径必须和写入的路径是同一条。你只要为补数据单开一条更新逻辑，重复计算只是时间问题。

### E-C 二星 · 604 台设备同时上报，写入怎么扛？

> 这个量级其实不大：604 台乘以 15 分钟一次，峰值每分钟几百条写入，单机 PostgreSQL 完全够。真正要注意的不是吞吐，是事务粒度和连接管理，批量 upsert、单事务提交，避免一条一个事务；连接走池化，不让每个采集任务新建连接。批次本身也是幂等的，重试不会产生重复行。
>
> 复盘句：教训是别一上来就上消息队列和分库分表，先把写入粒度、事务边界、连接池这三件事做对，量没到之前，多引一个组件就多一个故障点。

### E-D 二星 · 7 类质量状态怎么定的？为什么不是 3 类或 20 类？

> 不是拍脑袋，是对着真实脏数据倒推的：把历史数据跑一遍，所有导致聚合结果偏离的样本拿出来归类，归到「同一类问题、同一种处理方式」才合并，处理方式不同的就拆开。比如缺失和长间隔虽然都是没数，但缺失是确定没有任何数据、长间隔是有头尾但跨度超限，处理动作完全不同，就必须是两类。所以 7 类的划分标准是：处理动作不同才配成为一类。这也是我不再往下加的原因，加一类就意味着多维护一套补偿逻辑。
>
> 复盘句：状态码的价值不在数量，在于每一类都对应一个确定的处置动作。如果一个状态只有人看、机器不知道怎么办，那它就不该存在。

### S-A 三星 · 慢查询会把客户生产库拖垮，你怎么防？

> 四道防线，从便宜到贵。
>
> 一、优先本地副本：数据有 Parquet 落盘，绝大多数分析查询打本地引擎 DuckDB，根本不碰客户库。
>
> 二、必须直查时先 EXPLAIN 估算：扫描量或预估代价超阈值直接拒绝，不让重查询进入执行。
>
> 三、只读账号加执行超时加行数上限：就算放行了，也写不了库、有执行时间天花板、结果集有上限。
>
> 四、熔断与配额：单租户连续慢查询触发降级，后续查询走副本或排队；不同客户独立配额，一个打满不影响别人。
>
> 复盘句：原则是把保护放在离资源最近的地方，外层的权限和校验再全，也不如一个只读账号加一句执行超时来得踏实。

### S-B 二星 · 6 类数据源的方言差异怎么收敛？

> 不是在业务代码里写 if mysql else postgres，那样改一个方言要动十个地方。做法是把差异收进一层中间表示：上层产出的是跟方言无关的中间计划，到执行前的最后一环才翻译成目标方言，方言适配是配置不是代码分支。最难处理的三类：时间函数和时区、分页语法、类型转换和 NULL 语义。真遇到翻译不了的能力，就明确报错而不是退化成差不多的 SQL，错误的查询不如拒绝执行。
>
> 复盘句：跨源系统的取舍只有两个答案，差异要么收在一处，要么散在十处，没有中间地带。

### S-C 二星 · 大结果为什么不能直接放进上下文？

> 两个原因。一是成本：几万行的结果塞进去既贵又慢，处理质量还会下降。二是正确性：大结果进入上下文之后，模型看到的只是其中一段，很可能拿局部数据下全局结论。我的做法是把大结果外置成一个产物，有热、温、冷三级生命周期，上层只拿到口径摘要和聚合统计（行数、时间范围、总量、Top 分布），要看明细按引用取。同时给结果做哈希绑定，证明这段数据确实来自某次真实执行。
>
> 复盘句：一条通用规则是，任何展示给用户的数据，都必须能追溯到一次真实执行，而不是追溯到一段文本。

### S-D 二星 · 权限撤销了，之前生成的快照和导出怎么办？

> 分两类。在线内容（还在有效期的数据产物）撤销即时生效，下次访问重新走一次权限校验，而不是查缓存下来的结论。已经外发的静态文件（导出的表格、分享链接）从设计上就带有效期并绑定策略版本，到期自动失效；期间发现误发就吊销引用，而不是去删数据。核心原则是：权限检查的结果不要持久化成「这个人能看」的结论，每次访问都要重新判。
>
> 复盘句：权限这件事上，缓存校验结果是收益最小、风险最大的优化。

### R-A 三星 · 重放怎么保证确定性？随机、时间、外部依赖怎么办？

> 确定性不是靠运气，是把所有不确定源都变成输入。三条措施：
>
> 一、所有随机必须有种子。概率、随机策略都走同一条伪随机序列，种子记录在运行元数据里，重放时序列完全一致。
>
> 二、时间不能被直接读取。业务代码取的是一个可注入的逻辑时钟，每次运行有自己的时间轴，不依赖墙钟。
>
> 三、外部依赖全部打桩。第三方调用、网络响应都在环境内做确定性实现，同样输入必然得到同样输出。
>
> 另外每个环境用完就销毁，两次运行之间不共享残留状态。
>
> 复盘句：判断一个系统能不能被重放，就看三件事，随机数从哪来、时间从哪来、外部调用有没有打桩。这三个口子没堵上，重放结果就不可信。

### R-B 三星 · 24 个 Case 会不会过拟合？怎么说明机制可信而不是记住答案？

> 单看 24 个 Case 确实不够，所以我做了三件事。
>
> 一、双集隔离：开发集 16 个开发期可用，隐藏集 8 个与运行时物理隔离，开发侧根本读不到，防止对着考纲训练。
>
> 二、归一化预算的消融：不同策略（随机、广度优先、单策略、多策略）在同一个动作预算下比，比的不是谁答得对而是同等代价下谁找得到，预算不公平的对比没有意义。
>
> 三、多次独立重放：同一个样本重跑 3 次结果必须一致，证明发现不是靠运气。
>
> 但我也要说清边界：发布门禁承诺的是「预算内未发现」，不是「规则必然安全」。通过门禁只代表在这个预算、这些策略、这组不变量下没有找到违规而已。这一点我在文档里写得很明确。
>
> 复盘句：评测集的价值不在通过率，在于它能区分策略之间的优劣。如果所有策略都是满分，那说明题太简单或者漏题了。

### R-C 二星 · 确认有问题之后，怎么把报告压到最小？

> 用删除式 Delta Debugging：对找到的违规动作序列，逐步删除其中的步骤，每删一次重跑一次裁决，只要违规还成立就保留这次删除，删到再多删任意一步违规就消失为止，最后得到的是最小复现路径。这个过程能自动化，前提是重放和裁决都是确定性的，删一步重跑的代价可控。反例沉淀成回归用例，修复版本自动重放历史反例。
>
> 复盘句：缺陷报告的价值和它的长度成反比。一个要十步才能复现的问题，报上去很可能没人读；压到三步，修的人当天就能动手。

### R-D 二星 · FSM 里的 Checkpoint 到底存什么？恢复后会不会重复扣款？

> Checkpoint 存的是执行进度（当前在哪个节点、已经规划了哪些动作、预算用了多少），不是业务状态，业务状态一直在服务端的权威数据库里。所以恢复时不需要拿状态去补偿，而是重新读权威状态。防重复副作用的防线是幂等键加数据库唯一约束：同一个业务动作第二次执行会撞键冲突，直接返回上一次的结果。
>
> 这就引出超时语义：超时不等于失败，可能已经成功了只是响应丢了。正确做法是拿同一个幂等键去查回执，查到已完成就接受，查到被拒就按错误处理，查不到才敢重试，查不了就标记未知并停掉这个分支，绝不会换个 key 重发。
>
> 复盘句：状态机和业务数据要分开管的是，状态机存的是进度，业务结果存在权威数据里。前者丢了可以重跑，后者丢了就是事故。

## §3 硬题兜底十句（不会就这么说，别编）

1. **没做过游戏**：游戏经验我确实没有。但我理解休闲游戏服务端的骨架是：无状态网关到按区服路由（uid 哈希）到逻辑服按玩法分模块到冷热数据分层。这套东西我在能耗平台里做过一个等比缩小的版本，设备路由、分层数据模型、定时任务加监控。缺的是业务语义，这个我看两周能补上。
2. **Python 对 Java**：我主力是 Python，Java 写过项目但没上过生产（按真实情况说）。我认为语言切换的成本主要在生态和开发习惯，不在语言本身，服务端真正的题目是状态放哪、失败怎么兜、量怎么扛，这些是可迁移的。
3. **想不起来就用这句兜底**：我的判断是 X，理由是 Y，我不确定的部分是 Z，这一块我没在生产上验证过，所以不下结论。面试官对「他知道边界」的评价高于「他全会」。
4. **算法题卡住**：先说暴力解和复杂度，再说优化方向（空间换时间、有序性、单调性），主动请面试官给提示。沉默在那里是零分，讲思路是 60 分。
5. **为什么来乐元素**：休闲游戏日活量级大、交互是请求响应式，服务端的问题会做得很深；我两段经历都在做业务系统的可靠性，希望在一个高并发的业务上把服务端底子扎稳。
6. **AI Agent 工具（JD 明确加分项，必须主动说）**：我日常重度用 Claude Code 和 Codex，但不是让它写完我看都不看。我的用法是管它的上下文成本和安全边界：Skills 定能力边界、Hooks 在工具调用前后做校验、仓库级开发规范写进配置。核心原则是能由代码确定性保证的不交给模型，这也是我做服务端的习惯。
7. **TCP/IP 被问住时**：回到三次握手、粘包拆包、连接队列、TCP 与 UDP 取舍这四件事说，不要硬扯拥塞控制细节。
8. **问到简历上没有的东西**：答不上就说没做过，「这个我项目里没用到，我的了解停留在 X」。硬编扣分远大于诚实。
9. **被追问失误或弱点**：先认事实，再说纠正动作。「这块我当初做得不好的地方是 XXX，后来我改成 YYY。如果重做一次，我会 ZZZ。」
10. **反问环节（至少问一个）**：团队现在消消乐的服务端主要是 Java 栈还是混合栈？新人入职半年会落在哪个模块？
