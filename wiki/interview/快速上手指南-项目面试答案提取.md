# 快速上手指南：如何把项目文档拆成面试答案

这份指南不替代项目文档，而是教你怎么"读"文档。花 20 分钟看完 EnergyOps 的示例，你就能用同一套方法处理另外三个项目。

---

## 0. 先记住三条铁律

**铁律一：面试官不关心你的代码细节。** 你不需要背表结构、字段名、函数签名。你需要的是"为什么这样做"和"如果不这样做会出什么问题"。

**铁律二：先骨架，后血肉。** 先练三个核心问题（介绍 → 架构 → 难点），再填充母题细节。骨架没立住之前不要背细节。

**铁律三：永远准备三层答案。** 每个知识点至少准备到第二层追问。你讲的每一句话都可能被面试官抓着往下挖。

---

## 1. 三个核心问题的万能模板

### 问题一："介绍一下你的项目"（90 秒）

用飞书文档里的骨架，直接套你自己的项目：

> **大部门/项目业务**（15s）：一句话说清这个项目解决了什么业务问题。
>
> **我的角色与负责范围**（15s）：我负责/独立完成了哪几个模块。
>
> **核心链路**（25s）：数据从哪来，经过什么处理，到哪里去。不要说技术名词，说业务动作。
>
> **我解决的两个最难问题**（20s）：一个业务难点 + 一个技术难点，每句带一个量化结果。
>
> **系统边界或差异点**（5s）：一句话收尾。

### 问题二："能介绍一下业务架构吗？"（2 分钟）

> **上下游**：谁调你、你调谁。（上游是 X 平台，下游是 Y 服务）
>
> **内部模块**：接入层 → 处理层 → 存储层。（3-5 个模块，每个一句话）
>
> **数据怎么流**：从 A 进来到 B 出去的读写链路。

### 问题三："讲一个难点"（3 分钟）

这是拉开差距的核心问题。用飞书文档里的结构：

> **需求背景**（1-2 句）→ **快速讲清链路**（5-6 句，不要超过半分钟）→ **难点在哪里** → **都想出了哪些方案** → **选了哪一个** → **为什么这样选（方案对比，关键）**

重点在"为什么选"——这展示的是你的工程判断力，不是代码能力。

## 2. 实战拆解：EnergyOps 三个核心问题

下面以 EnergyOps 为例，演示怎么从项目文档中提取答案。

### 2.1 90 秒项目介绍（拆解过程）

**第一步：从文档中提取"业务问题"。**

打开 `projects/EnergyOps/EnergyOps-项目说明.md`，找 `## 1. 业务背景`。

文档原句（1.4）：
> 如何把分散且不稳定的表计读数，转化为可信、可追溯、可处置、可结算的园区能源运营结果。

这就够了。不需要把七类质量状态、三本账、五层能力都讲一遍。

**你的回答（15s）：**

> 金山武汉园区有 604 台智能水电表，同方平台每天产生 17.4 万条累计读数。但这些读数存在缺失、回退、乱序等问题，不能直接用来统计用电量、发现异常和做月度费用结算。EnergyOps 要解决的就是把这些不稳定的读数变成行政人员可以查询、财务可以核验、异常可以处置的可信运营数据。

**第二步：提取"你的角色"。**

强化母稿中原文：
> 重构 `raw → interval → hourly → daily` 数据链路……定义 7 类质量状态……统一页面、API、导出与月度账单……建设任务恢复机制……封装 Agent 业务能力……约束高风险操作……

选 3 个最有代表性的，不要罗列全部。

**你的回答（15s）：**

> 我负责能耗数据链路的建模与治理、Agent 业务能力的封装，以及高风险操作的安全约束。我的工作需要让数据工程和后端 Agent 工程共用一套业务口径。

**第三步：提取"核心链路"。**

文档 6.1 有 mermaid 图，但面试时不能画图。用文字描述业务动作：

**你的回答（25s）：**

> 链路从同方平台的累计读数开始，先经过质量判断和标准化，计算出每个时间区间内的实际用量；然后按小时、天、月逐层聚合。在这之上有三条业务线：用能分析让行政查询统计，异常运营让设备告警被追踪处置，费用结算让财务拿到可核验的月度账单。Agent 通过 WPS Comate 提供统一的查询和操作入口，但所有写操作都必须经过人工确认。

**第四步：提取"两个最难问题"。**

直接从母稿的量化指标中挑两个最有把握的：

**你的回答（25s）：**

> 第一个是统计口径的一致性问题——页面、API、导出和账单因为时间边界和设备归属不同，结果对不上。我统一了四端的设备范围、覆盖率和归属规则，30 组样本从 26 组一致提升到全部一致。
>
> 第二个是聚合查询性能问题。核心统计 P95 从 20.4 秒降到 2.8 秒，主要砍掉了重复 Join 和补充了预聚合。

**第五步：收尾（5s）：**

> 这个项目的核心差异在于它不是能耗看板，而是从原始读数到财务结算的完整运营系统，Agent 只是入口。

**完整版对照：**

把上面五段连起来就是 90 秒。你自己练习时录音，超了就砍。宁可少说一个点，也不要把细节塞进去。

### 2.2 业务架构（拆解过程）

三个必答子问题：

**上下游是谁？**

> 上游：同方能耗平台，通过接口产生累计读数。偶尔也接收行政上传的人工抄表和分摊规则。
>
> 下游：WPS Comate（Agent 入口）、管理页面（后台操作）、财务接收月度结算结果。

**内部模块？**

> 五个核心模块——
> 数据接入层负责拉取读数和标准化；
> 聚合层负责从 interval 到 monthly 的分层计算；
> 查询分析层提供用能统计和趋势；
> 异常运营层管理规则、告警和处置；
> 结算层处理月度费用分摊和三道质量门校验。

**数据怎么流？**

> 读数从同方拉进来之后经过质量判断，进入分层聚合表。查询、告警和结算都读这些聚合结果，页面和 API 共用同一套统计服务，不会出现两边看到不同数字的情况。

### 2.3 难点（拆解过程）

选一个最能展示"工程判断力"的难点。推荐用"统一统计口径"或"查询性能优化"，因为这两个最能体现你同时考虑了业务正确性和技术实现。

以"统一统计口径"为例：

**需求背景（2 句）：**

> 行政在页面看到的数据、导出的 Excel、API 返回的结果和月度账单经常对不上。同一个设备同一个月，四个地方能出四个数。

**快速讲清链路（5 句）：**

> 根因不在计算错误，而在四端使用了不同的边界条件。页面默认当前设备归属，导出取的是查询时的归属，账单用的是历史归属版本。时间边界的处理也不一致——有的用自然月，有的用采集周期。

**难点：**

> 难点在于不能简单地让所有端都读同一张表。因为账单需要用历史归属版本（设备可能在月中调拨过），但页面需要显示当前归属。同一个设备在不同端需要用不同的归属逻辑，但又要保证总量一致。

**都想了哪些方案：**

> 方案 A：统一只读当前归属，账单额外加调拨明细——但财务不接受"账单和当月页面不一样"。
>
> 方案 B：四端都用历史归属版本——但行政日常查询只看当前归属，用历史版本反而看错。
>
> 最终方案：区分"查询口径"和"结算口径"。查询口径用当前归属，结算口径用事件发生时的归属版本。总量通过归属版本表关联验证。

**为什么选：**

> 这个方案的核心洞察是：查询和结算对"归属"的需求本来就不一样，强行统一反而会产生新的问题。正确的做法是让它们共存，但用版本表保证可以互相验证。

## 3. 范式类问题的回答公式（新增，v2 核心）

如果说三个核心问题考的是"你做了什么"，范式问题考的就是"你为什么这样做"和"换一个场景还能不能这样做"。

回答公式：

```text
这个设计解决什么问题（根因，不是表面）
→ 为什么用 Prompt/文档/流程解决不了
→ 用什么机制保证（Hook/合约/校验器/状态机）
→ 失败边界（什么情况下这个机制本身会失效）
→ 跨项目对照（另三个项目有没有相同思想，怎么实现的）
```

### 实战示例：EnergyOps 的 Hook 链

**问题："为什么 EnergyOps 要设计三层 Hook 链，而不是把工具给 Agent 让它自由调用？"**

**根因（2 句）：**

> Agent 天然存在三个固有问题：它不理解操作的真实代价——对模型来说，查询一个设备和发布一份账单只是不同的工具名；它受 Token 预算限制，长结果会被截断；它倾向于最短路径完成任务，额外的校验意味着更多 Token 消耗。

**为什么 Prompt 解决不了（1 句）：**

> Prompt 只是软约束。你可以写"不要越权操作"，但模型不知道什么是"越权"——它不知道 R2 级操作意味着真金白银的财务影响。

**机制（3 句）：**

> Before Tool Hook 在工具执行前校验参数、权限和风险等级。R2 级操作检查人工确认状态，不满足直接阻断。After Tool Hook 在工具执行后登记 Evidence、外置大结果、更新任务状态。Before Model Hook 在下一轮调用前注入副作用信息。
>
> 三层共用一个原则：能由代码确定性保证的，不交给模型自行判断。

**失败边界（1 句）：**

> Hook 链本身不防 Hook 实现 Bug——如果 After Tool 的落盘逻辑写错了，Artifact 还是会丢。所以读侧降级（透传原文），写侧阻断（路径不在白名单拒绝执行），失败语义与操作代价匹配。

**跨项目对照（1 句）：**

> PayTrace 用同样的思想，但只做了两层——Before Tool 校验参数和范围，After Tool 更新 Hypothesis Ledger。数驭穹图没有显式叫 Hook 链，但它的混合 Runtime 本质上也是代码守住边界、模型处理局部决策。

## 4. 30 分钟快速入门流程

### 步骤一：通读 EnergyOps 的设计哲学（5 分钟）

打开 `projects/EnergyOps/EnergyOps-项目说明.md`，只读 `## 设计哲学与核心范式` 和 `## 6. 系统架构与核心机制`。读完后合上文档，口述：

- 四个范式分别解决什么核心问题？
- 每个范式的关键机制是什么？（不用背术语，用自己的话）

### 步骤二：用模板写出 EnergyOps 三个核心问题（10 分钟）

对每个问题，先不查资料，闭卷写下来。然后对照上面的示例检查遗漏。

### 步骤三：练范式第一问（5 分钟）

不看材料，回答"What is Hook 链 and why not Prompt?"录下来，听一遍，标记所有卡壳点。然后对照 `设计哲学与核心范式` 章节核对自己漏了什么。

### 步骤四：防守两个指标（5 分钟）

- `17.4 万条/日`：`604 × 24 × 12 = 173,952`
- `P95 20.4s → 2.8s`：`(20.4 - 2.8) / 20.4 = 86.3%`，固定查询集多轮执行取 P95

**面试官可能追问："这个 P95 是在什么环境下测的？多少人同时访问？"'**

如果不知道，诚实说"在固定查询集上单轮执行，没有构造并发场景"。记下来作为待确认点。宁可说不知道，不要编。

### 步骤五：自我评分（5 分钟）

| 验收项 | 自评 |
|---|---|
| 20 秒说出一句话定义 | |
| 90 秒完成项目介绍（不超时） | |
| 画出主链路并讲清端到端 | |
| 讲清上下游 + 内部模块 | |
| 讲一个难点（背景→链路→难点→方案→选型） | |

每项 1-3 分。低于 2 分的项就是你的第一批断点，直接回看对应的文档章节。

## 6. 常见翻车点

1. **90 秒介绍超时到 3 分钟** → 面试官会打断你，第一印象很差。解决办法：录音，听到超过 95 秒就重录。有量化结果的选择性分享，不要全堆。

2. **讲架构时开始描述数据库表结构** → 面试官想听的是"上游是谁、下游是谁、数据怎么流"，不是字段名。每次讲到技术细节就问自己："这句话能帮面试官理解业务吗？"

3. **讲难点时 2 分钟了还没进入难点本身** → 前奏控制在一分钟以内。用"难点在于……"明确标记边界。

4. **被追问数字时卡住** → 任何数字说不清时，先诚实说"这个数据来自固定回放集/日志抽样"，补上"如果面试官需要，我可以解释计算方式"。比硬编强得多。

5. **范式中把"设计目标"说成"已完成结果"** → E3 内容不能伪装成 E1。面试官会继续追问"你怎么验证的"，你接不住就是扣分项。
