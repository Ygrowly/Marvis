# 外挂记忆系统与现代 E2E 工程——两个项目 idea 的全面分析

> **缘起**：2026-09-30 深夜讨论。两份材料：① 一张 DeepSeek 对话截图（「标准外挂记忆系统」的协议与开源实现盘点）；② 主人自己画的「现代 E2E 工程」架构图（用例采集离线自动 / 用例验证在线实时 / 三座大山）。目的：**先探讨落库，不动简历**——简历母版余量仅 +3.0pt，任何进简历的动作都要过版面与事实两道闸。
>
> **⚠️ 2026-10-02 定位修订（重要，先读这条）**：本文初版把两个 idea 当成「要不要立项」来写（含 10/15 数据决定立项之类的判断）。**主人已澄清：不做外挂记忆系统，是学这两个 idea 的「项目立意」**——即「项目都要有价值，或者在某个业务上很垂直」这条判据是怎么成立的、怎么用。
> 因此：**「做不做」这一问已被消解**，本文 §1–§3 保留为立意素材与行业坐标，**判据正本迁至 `templates/项目说明模板.md` 第零阶段（V 有价值 × H 垂直 × P 可证明）**，本文 §7 是按该判据重做的两个 idea 打分。**不立项 = 不占派单、不改简历、不进必做区**；它的用途是面试里「如果我来做 X，我会切哪一格」的判断力展示。
>
> **一句话结论（2026-10-02 按立意判据重写）**：
> 1. **两个 idea 的真正收获不是「做什么」，是「怎么立意」**：价值落点 + 垂直切分，这套动作可以套在任何一个 idea 上（判据正本：`templates/项目说明模板.md` 第零阶段）。
> 2. **按 V × H × P 打分**：E2E 三格全强（价值落在「敢不敢发布」的决策上、垂直在「用例采集 / 验证分离」、可证明 = 断言通过率可测）；记忆系统 **V 强 H 弱**——整体是通用能力，必须**切一格**（切成「可验证的记忆」，§7.2）才讲得出差异。
> 3. **E2E idea 与 RuleArena 同构**（离线出题 / 在线门禁的第二应用域），所以它现在的价值是**话术与判断力**，不是新代码；记忆系统的价值是**「切一格」的示范样本**。

## 1. Idea A：标准外挂记忆系统

### 1.1 idea 本体（图 1 解读）

截图是一段 AI 对话，讨论「像 MCP 那样的标准记忆层」：各 Agent 产品接入统一的外挂记忆服务，厂家不用自研记忆功能、还能更了解客户；用户在一处读写自己的全部记忆，双向利好。对话里列了一批协议与实现（MCP Memory Protocol / Agent Memory Protocol / A2M / Memary / mem0 / memobase / memory-mcp-server / agentmemory 等），并讨论了「标准之争的时机窗口」。**（2026-10-03 联网核查：mem0 / memobase 证实为真实主流项目，Letta / Zep 同为主流代表；清单其余项仍未逐个核实，见 §8.6③）**

**信源性质标注（最重要的一条纪律）**：这张截图是**二手信源**——AI 对话里列举的协议名、项目名、能力描述，一条都没有经过一手核实。按「行业惯例式阶梯数字先当无出处」的同一原则：**这份清单在面试引用前必须逐个对一手 repo / 文档核实，核实前只能当「存在这样一个方向」的印象，不能当「存在这些具体协议」的事实。**

### 1.2 三个冷静判断

1. **「标准」轮不到个人定。** 协议标准化是平台方和基金会的游戏（MCP 之于 Anthropic 是先例：先有自家实现、后有生态）。应届生开源一份「自定义记忆协议」并宣称行业标准，面试官第一反应是不接地气。个人的可占位置有两个：
   - **做实现**：选一个已有共识的接口形态（MCP tool 是目前最接近共识的），开源一份自己的记忆服务实现；
   - **做评测**：对几套开源记忆系统做横向评测、出一个 benchmark 报告——**评测恰恰是全库最强的牌**（E1 母题、`pass@k`/`pass^k` 成对陈述、RuleArena 评测框架全是现成的）。
2. **竞争格局：记忆层已是红海。** mem0 / Zep / Letta（原 MemGPT）/ Memobase 等开源实现已成型并有融资，大模型厂商也在把记忆内建进平台。**差异空间不在「我做了一个记忆系统」，而在具体的失败模式上**——这正是 RuleArena 的方法论：不抢「记忆让 Agent 更聪明」这个大叙事，找「现有实现都会踩的具体坑」。
3. **「更了解客户」是真的，「更懂用户」要打个折。** 对企业（B 端）：跨产品共享用户记忆 → 个性化 → 留存，这条价值链成立，是「能讲」的部分。对用户（C 端）：把全部记忆交给一个中心化服务，隐私和可携权是硬问题——面试里主动提这一层反而加分（说明想过边界）。

### 1.3 技术内核 ↔ 已教材化模块对照（这是本 idea 最大的杠杆）

| 记忆系统要做的事 | 已有的母题卡 | 状态 |
| --- | --- | --- |
| 记忆检索（向量 + 关键词 + 图混合） | G2 混合检索 | 已教材化 |
| 记忆整固（ episodic → semantic 提炼） | A5 上下文压缩与记忆 | 已教材化 |
| 写入冲突消解（新旧记忆矛盾） | A5 + C1 上下文组装与预算 | 已教材化 |
| 记忆评测（长期对话一致性 benchmark） | G5 评测 / E1 评测集设计与 pass^k | 已教材化 |
| 记忆增量更新与失效 | G6 增量更新 | 已教材化 |
| 记忆写入的幂等（同一事件重复写入不产生两条记忆） | A3 失败恢复与幂等 + RuleArena 三段拦截 | 已教材化 + 有实测 |
| 多租户隔离与权限 | 数驭穹图五层安全 | 有项目支撑 |

**结论：做这个项目，约七成技术内核是「练过的卡」，剩下的三成（记忆生命周期管理、衰减与遗忘、PII 处理）才是真正的新学习量。** 这是两个 idea 里「学习成本 / 叙事收益」比最好的一张。

### 1.4 独家角度：可验证的记忆（把 RuleArena 的哲学带进来）

现有记忆系统叙事都在卷「记得更全、召回更准」。没人卷的是**记忆的可信性**：

- 记忆条目带**证据等级与来源**（这条记忆是从哪次对话提炼的？原文可回溯吗？）——对应证据等级 E1/E2/E3 的思路；
- 记忆写入**幂等与事务性**（同一次对话重复提炼不产生两条矛盾记忆）——RuleArena 门禁三段拦截的直接迁移；
- 记忆**过期与失效是机制不是脏数据**（带 TTL / 置信衰减，冲突时保留哪个有裁决规则）；
- **「Agent 自述学到的」和「用户明确说的」分开存**——不信 Agent 自述，同 Oracle 不信 ACK 的哲学同源。

这一层是**「能做能讲」重合度最高**的部分：做了就是面试里「我和 mem0 的差异」的答案，而且每一句背后都有 RuleArena 的实测故事撑腰。

### 1.5 画饼话术降维

原版：「帮助公司 N 个 Agent 产品打通用户记忆 → 业务更了解客户 → 内部做成熟后开源反哺社区甚至建立行业标准」。

逐段处理：

| 原话 | 处理 | 理由 |
| --- | --- | --- |
| 帮 N 个 Agent 产品打通记忆 | **保留**，但要能答「怎么打通」：统一 MCP 接口 + 记忆 schema 版本化 + 按产品配读写权限 | 这是工程价值，可落地 |
| 业务更了解客户 | 保留，但接在「打通」后面说，并补隐私边界一句 | 双向利好的另一半 |
| 内部成熟后开源 | 降为「接口抽象稳定后开源一份参考实现」 | 开源参考实现是应届生说得出口的量级 |
| 建立行业标准 | **删掉或改成「把接口抽象沉淀成内部规范」** | 面试官会追问「你凭什么定标准」，答不动就是减分项 |

### 1.6 风险

1. **必考题「和 mem0 有什么区别 / 为什么不用现成的」**——没部署用过 2~3 套现成品，这题必死。最小切片里必须含横评环节。
2. **记忆质量评测没有公认基准**——LoCoMo 类长对话基准也要一手核实其适用性，不能拿二手评价当成绩。
3. **工程黑洞**：记忆系统要做到「演示得体面」，检索、存储、接口、评测四面都要有——两周切片必须砍到只剩「接口 + 检索 + 评测」三面。

### 1.7 最小切片（两周量级）

1. 一个 MCP 记忆 server：三层结构（working / episodic / semantic）+ 混合检索，接口对齐 MCP tool 形态；
2. 把自己的某个真实工作流（比如母题复训记录）当记忆源跑两周，**攒真实使用证据**；
3. 对 mem0 / Zep 各做一次接入对比，出一个 3~5 页横评笔记（这就是评测牌的第一张）；
4. 写一篇「可验证的记忆」设计笔记（不实现，只设计）——面试深水区弹药。

## 2. Idea B：现代 E2E 工程（主人自画图）

### 2.1 图 2 解读与最值钱的洞察

图的结构：左侧「用例采集（离线自动）」——Browser/Computer Use + LLM 在混沌的业务系统里跑，产出结构化 case（如「点击删除按钮弹出确认对话框」）沉淀进 E2E 用例库（周期更新）；右侧「用例验证（在线实时）」——埋点数据采集 + Browser/Computer Use，Context 用 AX Tree（找到删除按钮 / 找到对话框），由 SoM（Jev like）感知引擎执行断言（click#button → 已找到 = 通过 / 未找到 = 失败），输出报告和基线。三座大山标注为：环境的不确定、用例的丰富度、执行的效率。

> **原件归档（2026-10-03）**：架构图原件已拷入本目录 `assets/2026-09-30-现代E2E工程架构图.png`（微信临时目录会被清理，此为库内唯一副本）；图 1（DeepSeek 记忆协议对话截图 `42b0f798….png`）原始文件已丢失，仅存 §1.1 文字解读。

**这张图最值钱、也是最该在面试里讲出来的洞察：把「贵的模型的一次」和「便宜的一万次」分开。**

- 离线采集用大模型：慢、贵、但一次性的产物（用例）可以复用成千上万次；
- 在线验证用小模型 / 确定性程序：快、便宜、高频执行。

这和「编译器贵一次、二进制便宜一万次」是同一条经济学。在线环节如果跑完整 Computer Use Agent（每步都过大模型），成本和脆弱性都不可接受——图上把在线验证限定为「AX Tree + 感知引擎 + 确定性断言」，方向是对的。

### 2.2 与 RuleArena 的同构对照（这是本 idea 的真正归宿）

| | RuleArena（已实现已实测） | 现代 E2E（图中设想） |
| --- | --- | --- |
| 离线层 | 规则引擎自动出题（对抗工单） | LLM + Computer Use 自动采集用例 |
| 在线层 | 运行时门禁三段拦截 | 感知引擎 + 确定性断言 |
| 裁决 | 独立 Oracle 按业务不变量算，不信 Agent 自述 | 按用例期望断言，不信「页面看起来正常」 |
| 核心哲学 | **LLM 负责提议探索，确定性代码负责裁决** | **LLM 负责生成用例，确定性断言负责判定** |
| 产物 | 可复现失败证据 + 回归资产 + 发布判定 | 报告和基线 + 回归用例库 |

**同一条设计哲学的两个应用域**：RuleArena 管「Agent 调工具的业务终态」，E2E 管「前端改版后交互还在不在」。这不是巧合——是主人的方法论（模型提议 / 程序裁决、自动出题、独立验证）在两个域的自然展开。

**因此结论：E2E idea 不立项为独立项目，作为 RuleArena 的延伸叙事。** 两个理由：
1. RuleArena 口径已冻结、实测数字已成对陈述，再往上叠一个前端域会稀释主线、增加记忆负担；
2. 面试官问「这项目接下来怎么做」时，E2E 恰好是完美的答案素材（见 §4）。

### 2.3 三座大山逐个拆 + 对应已有武器

| 大山 | 拆解 | 已有武器 |
| --- | --- | --- |
| 环境的不确定 | 前端环境混沌（数据、状态、时机都在变），用例输入不稳定 → 解法是**把混沌环境变成可构造环境**：埋点 + 契约固定输入，断言读 AX Tree 而非像素 | Commerce Sandbox 思路直接迁移：可注入缺陷轴、可重置、状态可重算 |
| 用例的丰富度 | 人工写用例跟不上迭代，长尾覆盖不到 → **LLM 自动出题** | RuleArena 自动出题器的同款逻辑，且实测过它的诚实结论（出题不稳定 → 门禁兜底）——**这段实测经验直接就是 E2E 自动出题的回答** |
| 执行的效率 | 在线每步过大模型不可接受 → 分层：能断言 DOM/AX Tree 的不上模型，模型只处理感知层 | C5 模型选型 / C6 成本与缓存；数驭穹图 Token 18.4K→3.6K 的成本工程经验 |

### 2.4 价值叙事链（前端敏捷 → 自动化 E2E）

前端回归敏捷开发、快改快上 → 每次改版都需要 E2E 兜底 → 传统 E2E 死在「写用例慢、维护用例更慢」→ 用例自动采集把**写**的成本打掉、AX Tree + 感知引擎把**维护**的成本打掉 → 「敢不敢发布」从拍脑袋变成基线对比的数据决策。

这条链直接对口**四份简历成品里的「AI 评测与测试开发」方向**——投测试 / 质量序列时，这段叙事就是面试里「你为什么投测试开发」的最佳答案：不是「测试缺人」，是「我知道评测与门禁怎么做得可信」。

### 2.5 风险与边界

1. **「Jev 模型」未核实**——图上写「SoM (Jev Like)」，这个模型名目前只存在于二手对话中，面试引用前必须一手核实（§5）；**（2026-10-03 已核实：TypeSafe AI 的 System One 快判断模型，见 §8.6①；引用建议改为「说形态不点名」）**
2. **别吹「取代手工测试」**——用例自动生成覆盖不了业务语义正确性（哪些该有确认弹窗是产品决策），叙事要收在「回归兜底 + 覆盖增长」；
3. **Computer Use 的脆弱性是真实工程成本**——这恰恰是在线环节不用它的理由，讲出来是理解深度的证明，藏起来反而被追问打穿；
4. 若真要动手，被测对象就用**自己的 site/**（progress.html 的派单引擎已有三个回归测试，天然是「确定性断言」的现成标的）——但同样排在 10/15 之后。

## 3. 两个 idea 的横向比较与优先级

| 维度 | 记忆系统 | 现代 E2E |
| --- | --- | --- |
| 新项目空间 | **有**（三项目里没有纯 Agent 基建位） | 无（与 RuleArena 同构，作延伸） |
| 对口方向 | AI 应用开发 / Agent 后端（主方向①） | AI 评测与测试（方向③） |
| 技术储备 | ~七成已教材化 | 哲学全通，实现层（Computer Use/AX Tree）全新 |
| 两周切片可行性 | 可（server + 横评 + 设计笔记） | 勉强（只够跑通自己站点的小闭环） |
| 最大风险 | 「和 mem0 差异」必考题 | 工程量大、演示体面难 |

**优先级建议（按库内既有判据推，不新造规则）**：

1. **今晚到 10/15：两个都不动手。** 唯一指标是 `questions.md` 每周闭环 ≥1 问；硬窗口压着（五大行 10/7–10/9、英特尔中国约 10 月中旬）；止损线 10/15（前场次 <3 = 过筛问题）必须先看数据。开新项目要过 `wiki/thinking/行动规则.md` A-7 机会成本门。
2. **但话术今晚就能用**（零成本、不动简历）：
   - E2E idea → 织进 RuleArena 的「下一步」答法（§4.1）；
   - 记忆系统 → 织进「如果加入贵司你打算做什么」的答法（§4.2）。
3. **10/15 数据 ≥5 场、面试节奏起来之后**：二选一立项的话，**记忆系统优先**——它是主方向的新牌、七成内核已练过、能接 RuleArena 的幂等与评测故事。E2E 在任何情况下都保持为 RuleArena 的延伸章节，不独立立项。
4. **母题/派单不减量是立项前置条件**：新项目的 slices 只能从「加餐」位走，不进必做区，命功三件事不可被挤。

## 4. 面试话术：上价值公式的可用版本

### 4.1 RuleArena「这个项目接下来怎么做」（30 秒答法）

> 「下一步是把门禁从 CLI 推到 CI 形态——提 PR 自动跑回归工单、门禁报告挂到 PR 上。再往外一层，我最近在想的等价问题是前端侧的：前端回归敏捷开发，E2E 兜底一直做不起来的原因是写用例和维护用例太贵。我的解法是同一套哲学——离线让大模型采集用例沉淀成用例库，在线验证只跑 AX Tree 加轻量感知和确定性断言，把贵的一次和便宜的一万次分开。出题不稳定怎么办我在 RuleArena 里实测过：不能指望生成器保证覆盖，必须由运行时断言兜底。」

这段话同时回答了三个问题：项目有规划、方法论可迁移、实测经验能跨域复用。

### 4.2 「如果加入贵司，你打算做什么」（30 秒答法，记忆系统版）

> 「贵司有多条 Agent 产品线，每条都在各自维护用户上下文，用户记忆其实是割裂的。我做过一个可验证记忆的设计：统一 MCP 记忆接口 + 三层记忆结构，关键是每条记忆带证据等级和来源、写入幂等、冲突有裁决规则——这些机制我在上一个项目里用确定性门禁实测过（多退一笔钱 vs 零资损那组数字）。先在一个产品里跑通，接口抽象稳定后开源一份参考实现，再横向推到其他产品线。」

注意结尾是「先跑通一个产品 → 开源参考实现 → 横向推广」，不是「建立行业标准」——饼画在证据延长线上（0713 那份的原则：不比量级比方向）。

## 7. 立意判据视角下的两个 idea（2026-10-02 补）

> 判据正本 = `templates/项目说明模板.md` 第零阶段（**V 有价值 × H 垂直 × P 可证明**）。本节只做打分与反向校验，不复制判据正文。

### 7.1 打分

| idea | V 有价值 | H 垂直 | P 可证明 | 结论 |
|---|---|---|---|---|
| **外挂记忆系统（整体）** | **强**：企业愿为「跨产品打通用户记忆」付钱；弱点在「更了解客户」本身不是指标，要落到留存 / 客诉才算数 | **弱**：通用能力，换个团队也能讲同样的话 | 中：检索指标可测，**「可信性」要自建评测** | **必须切一格才有讲头** |
| **智能 E2E（整体）** | **强**：前端快改快上的兜底，价值落在「**敢不敢发布**」这个决策上 | 中偏强：三座大山点名了（环境 / 用例 / 断言），但「平台」形态仍偏通用 | **强**：断言通过率、漏测数、维护工时都可测 | 切一格后成立 |

### 7.2 切一格之后，P 也跟着变

「切一格」不只是修辞动作，它同时救了可证明性：

- 记忆系统整体 → 只能用「召回率 / 延迟」这类别人也有的指标（P 中）；
- 切成**「可验证的记忆」** → 写入幂等能用**重放**验证（同一段对话重复提炼不产生两条矛盾记忆），冲突裁决能用**规则用例**验证——**这两条验证方式 RuleArena 里已经跑过一遍**（P 变强）。

> 这也是「垂直」和「可证明」常常一起出现的原因：**切得越具体，越容易设计对照实验。**

### 7.3 用同一判据反向校验三个已有项目（判据不是新造的）

| 项目 | V 价值落点 | H 垂直的那一格 | P 可证明 |
|---|---|---|---|
| **EnergyOps** | 行政手工对账 + 告警研判 | 第三方累计读数的 **7 类质量状态** | 聚合完整率 96.8%→99.7%、告警量降 43% |
| **数驭穹图** | 取数排期（找数据同学 → 等） | **语义层口径**（同一句「销售额」不同行业不同口径） | 查询成功率 78%→91%、Top-K Schema 95% |
| **RuleArena** | 资损 + 发布决策 | **非原子工具调用 → 换幂等键重试 → 重复退款** | 资损 6 笔→0 笔、终态正确率 60%→100% |

**两条结论**：

1. 这三个项目讲得动，是因为**三格全占**；反过来，「多 Agent 平台」这类讲不动，是因为 **V 有、H 无**——同一套判据两头都验得住。
2. 因此这条判据**不是从理论推出来的，是从「哪些讲得动、哪些讲不动」的样本里反推的**，可信度高于任何写作技巧。

### 7.4 面试用法：用 30 秒证明「我会选题」

> 「我不会去做『又一个记忆系统』——那是通用能力，讲不出差异。我会切**记忆的可信性**：每条记忆带来源和证据等级、写入幂等、冲突有裁决规则。这个坑现在的开源实现都还没解决，因为它不是检索问题，是**写入侧的事务问题**。同样的思路我用过一次：RuleArena 我没做『Agent 测试平台』，我做的是『**工具返回 ACK ≠ 业务成功**』这一格。」

这 30 秒同时证明三件事：**会选题**（不贪整体）、**有方法论**（切一格 + A≠B 点名）、**方法论是从真实项目里长出来的**（不是背的话术）。

### 8.1 「三个核心 × 三座大山」的两套命名（同一件事）

对话口头版与图上标注版的映射：

| 对话口头版（三核心 → 三大山） | 图上标注版 | 本质 |
|---|---|---|
| **输入的稳定性** | 大山一：环境的不确定 | 业务系统是混沌环境（数据 / 状态 / 时机都在变），输入不稳定 |
| **用例的丰富度** | 大山二：用例的丰富度 | 人工写用例跟不上迭代，长尾覆盖不到 → LLM 自动出题 |
| **断言的性能** | 大山三：执行的效率 | 在线验证要高频跑，每步过大模型不可接受 |

对应关系是干净的 **一核心扛一山**：用例→丰富度、输入→稳定性、断言→性能。这是这个 idea 概念框架最值钱的地方——**一个 idea 的骨架能被三个词扛住，说明它真的立住了**。

**面试用法**：同一座山有两套词——对工程听众说「输入稳定 / 断言性能」，对业务听众说「环境不确定 / 执行效率」。主动把映射说破（「图上写的执行效率，聊起来就是断言的性能问题」）反而显出概念清楚，比背一个版本强。

### 8.2 GitHub Issue/PR 派任务实验：自动化程度低于预期的根因（独家素材，主人亲测）

对话原文：「直接用 GitHub 的 Issue 和 PR 给 Agent 派任务和验收，但是试下来自动化程度好像没有想象中的高。」

按三核心拆根因：

- **输入（派活）**：Issue 做到了——目标、上下文、约束可以写清楚；
- **用例**：缺——Issue 里没有可执行用例，Agent 自由发挥；
- **断言（验收）**：**最弱**——PR 回来了，验收靠人看，「完成」没有确定性定义。

**这是三核心框架的一个真实反证：三座山里最先断掉的是断言。** 由此得到一条**从自己实验里长出来的 A≠B 句式**（比借来的硬）：

> **「Issue 描述了目标 ≠ Issue 定义了完成」**（派活 ≠ 验收）

它和 RuleArena 设计原则第 4 条「完成由什么证据证明（不接受自述）」是**同一条原则的第三个应用域**：

| 域 | 「完成」的确定性定义靠什么 |
|---|---|
| Agent 执行工具（RuleArena） | 独立 Oracle 按业务不变量裁决，不信 ACK |
| 前端回归（现代 E2E） | AX Tree + 确定性断言，不信「页面看起来正常」 |
| 开发流程（Issue/PR 派活） | PR 挂可执行验收标准（用例 + 断言先行），不信 PR 描述 |

**追问链备好**：为什么 PR 验收自动化低 → 缺确定性断言 → 怎么补 → 验收标准进 Issue 模板 + CI 跑 → 这正是 RuleArena 门禁 / 现代 E2E 在做的事。这个实验讲 30 秒，比任何「我方法论很强」的自述都有效。

### 8.3 「分三层」表达法（主人自己的开放题结构）

对话原文：「我会分三层：现象描述，目标描述，个人倾向性方案。」

- **现象描述**：现在是什么样、问题出在哪（不夹私货）；
- **目标描述**：理想态是什么、用什么标准判断；
- **个人倾向性方案**：我会怎么做、**代价是什么**。

**定位**：这是接**开放性问题**的结构（「拿到一个页面让你做优化，有比较好的工具吗」这类没有标准答案的题）。与铁律 §6 的 60 秒项目骨架互补：**讲既有项目用五段骨架，接开放题用三层法**。它天然带出取舍感——第三层永远连着代价，讲不成方案吹嘘；而且第三层「倾向性」三个字自带可追问性（为什么倾向它、放弃的是什么）。

### 8.4 页面优化探索类问题的归属：探索归离线，验证归在线

对话原文：「如果拿到一个页面让你做优化，现在有比较好的工具吗，这种是不是就比较侧重让 AI 的探索？」

直觉是对的，且正好是采集/验证分离的另一半：**探索题（找什么可以改）和验证题（改了有没有坏）是两类题**——

- 探索归**离线**：让 LLM / Computer Use 慢慢逛页面找问题、产出结构化用例（贵、慢、一次性）；
- 验证归**在线**：优化是否生效交给确定性断言跑回归（快、便宜、一万次）。

面试里被问「给我个好工具」时，先拆题（探索还是验证）再答工具，比直接报工具名高一层。

### 8.5 记忆侧新信号：「AI 都能导出全部记忆了，不过处理挺慢的」

三个推论：

1. **导出已不是壁垒**：记忆可携从「能不能」变成「好不好用」——现在是全量一次性 dump，不是结构化、增量的管道；
2. **工程机会在导入 / 整固侧**：导出的记忆如何去重、冲突消解、分层（episodic → semantic）、带证据等级入库——恰好是 §1.4「可验证的记忆」说的**写入侧事务问题**，痛点真实存在（「处理挺慢」= 没人做增量与整固）；
3. **给 §1.7 最小切片补了真实数据源锚点**：导出主人自己的 AI 记忆当数据源跑「结构化管道」，比构造数据有说服力，攒下的还是真实使用证据。
