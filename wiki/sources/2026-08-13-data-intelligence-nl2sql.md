# 主题：数据智能 Agent：NL2SQL、NL2BI 与意图识别

## 一句话结论

「模型处理语言不确定性，确定性系统守住业务确定性」——从 NL2SQL 到 NL2BI 再到意图识别，生产级数据智能 Agent 的上限不取决于模型，而取决于知识工程（口径、路由、权限、证据）和评测闭环。

## 共同结论

1. **LLM 与确定性系统的分工是共识**：路由、口径、权限、证据由规则/代码收口，模型只处理语言不确定性。NL2SQL、NL2BI、意图识别三篇文章从不同截面得出同一结论。
2. **知识工程决定上限**：NL2SQL 的天花板在知识质量不在模型——3 万行知识按需加载（单次 200-400 行），6 节表知识卡片 + 半自动元数据 Pipeline。
3. **评测驱动是质量基线**：评测集先行、自动化闭环、DDL 一致性监控、AB 实验收敛，无一例外。
4. **权限与治理 fail-closed 是生产门槛**：受权限、语义、证据约束的查询流水线，而不是「裸调 LLM 写 SQL」。

## 真正的分歧

- **检索 vs 确定性路由**：高德在 V1 用多 Skill + RAG 选表失败后，V2 放弃 RAG 改用确定性两级路由（域路由表 + 域内 DOMAIN.md 映射）；而 RAG 科普文主张多路召回 + 精排。分歧点其实是适用条件：表规模、口径歧义度、知识维护成本。
- **模型大小的选择**：618 在成本约束下选小模型 Qwen3-8B + 强评测闭环，效果收敛到 90+；多数文章默认大模型。隐含判断：小模型 + 强评测可以打赢大模型 + 弱评测。
- **多 Skill 还是单 Skill**：高德 V1 多 Skill 因路由失控失败 → V2 统一 Skill + 内部确定性路由；与部分「每个场景一个 Skill」的流行做法相反。

## 新增或修正的知识

- **确定性两级路由**：域路由表 + 域内 DOMAIN.md 选表映射，放弃 RAG 选表——这是一个有真实失败案例支撑的反直觉结论。
- **Evidence Binding**：call_id / 查询指纹 / 结果 Hash 绑定 ChartSpec，防止图表与底层数据脱节，是 NL2BI 独有的设计。
- **Prompt 自进化框架**：自动化闭环 + train/test split 防过拟合 + 规则/LLM 双轨评分，是「评测集怎么持续变好」的可复制答案。
- **评测五层**：Tool Contract / Oracle / 证据 / Judge / 成本，比「准确率」单一的评测观完整。
- **知识卡片化**：6 节表知识卡片 + 半自动元数据 Pipeline，是「知识工程」的可操作形态。

## 可信度

- 有数据、代码或案例支持：
  - 高德 NL2SQL：准确率 >95%、取数效率提升 30 倍以上、900 道测试题、生产案例。
  - 618 意图识别：80.8 分 → 90+、自定义对话 CTR 3.7 倍、AB 实验。

  - Redis：告警噪音降 90% 以上。
- 只有观点或二手转述：
  - RAG 核心概念是科普综述，无生产数据，适合建立词汇表。
  - K8s + Ray 有腾讯 TEG 实践但量化数据少。
- 需要进一步验证：
  - NL2BI 无量化效果数据，设计细节虽全，但个人项目是否值得全套复制 Evidence Binding 需要权衡。
  - 确定性路由在表数量更小、口径更少的个人项目中是否仍然优于 RAG。
