# AI Coding 驱动工作流

> **状态说明**：本文是 AI 依据官方一手资料整理的 `candidate`，**不代表已掌握**。按 [[母题驱动证据闭环学习法]]，需闭卷复述 + 两层追问 + 迁移到自己项目后才算沉淀。见文末〈验收〉。
> **性质**：方法 / 行动规则。能力项定义与掌握度见 [[AI应用开发能力地图]] F10；JD 侧要求见 [[六家公司AI应用开发岗位-横向对比总览]] CORE-28。

## 触发问题

我的 AI Coding 一直是三步法：**拆需求写提示词 → 让它全面审查 → 手动测试再迭代**。这套流程跑得动，但 JD 把 AI Coding 列为 CORE-28（`需求→计划→实现→测试→Review→验证`），面试会考察它，我想知道这套流程缺什么。

## 我的原始判断（2026-09-14 之前）

1. 拿到业务需求 → 自己拆解出提示词（要做什么、要考虑什么、要达到什么结果）→ 让 AI 实现。
2. 实现完 → 补一句提示词，让 AI 针对关键模块再全面审查一遍，确保没 bug、逻辑正确。
3. 自己手动真实测试 → 和预期有出入就让它迭代修复。

## 三个结构性缺口

诊断结论：**缺的不是"更好的提示词"，而是三个环节的缺失。**

| 缺口 | 原做法 | 问题 |
|---|---|---|
| **澄清** | 拆解*我已知*的需求 | 只覆盖 Known Knowns，漏掉 unknown knowns 和 unknown unknowns |
| **验证** | 同一会话里让它自审 | 做事的 agent 给自己评分，是最弱的验证形式；且第 3 步把验证放到最后，我自己成了验证循环 |
| **沉淀** | 每次从零组织提示词 | 经验易失，不跨会话累积 |

## 支持证据（官方一手）

### 证据 1 · 没有可执行的检查，你就是验证循环

Claude Code 官方最佳实践把「给 Claude 一种验证其工作的方式」列为第一条：

> 当工作*看起来*完成时，Claude 会停下。没有它能跑的检查，"看起来完成"就是唯一可用的信号，**而你就成了验证循环——每个错误都在等你发现它**。

给一个能产出 pass/fail 的东西（测试套件、构建退出码、linter、截图对比脚本），循环才自动闭合。这是"你盯着看的会话"和"你可以走开的会话"之间的区别。

### 证据 2 · 真正的瓶颈是澄清未知的能力

Anthropic 的 Thariq 在 *Finding your unknowns* 里给出核心判断：**在 Claude 5 代模型上，工作质量已经不再被模型能力卡住，而是被"你澄清未知的能力"卡住。** 四类未知：

- **Known Knowns** —— 写进 prompt 的（我的第 1 步只覆盖了这类）
- **Known Unknowns** —— 知道自己没搞清楚的
- **Unknown Knowns** —— 看到才知道自己要什么（视觉、手感、API 手感）
- **Unknown Unknowns** —— 压根没考虑过的

> The better models get, the more you can achieve with the right approach.

模型越强，越要求你先把未知挖出来；否则它只能用行业默认最佳实践去猜，而那未必是你的场景。

### 证据 3 · 做事的 agent 不该给它评分

官方明确：对抗性审查要放在**新鲜上下文**里跑——审查者只看到 diff 和你给的标准，看不到产生这些改动的推理过程，所以它按自己的条件评估结果。同时有一条关键警告：

> 被要求找缺陷的审查者**总会找到一些**，即使工作是健全的，因为那是它被要求做的。追逐每个发现会导致**过度工程化**：额外的抽象层、防御性代码、针对无法发生的情况的测试。

所以必须把标准收紧到"只标影响**正确性或明确需求**的缺陷"，其余算可选。

### 证据 4 · 七种指令方式的取舍是"上下文成本 × 权威性"

来源：*Steering Claude Code*。核心结论——

| 机制 | 何时加载 | 放什么 |
|---|---|---|
| CLAUDE.md | 每次会话，全程常驻 | Claude 猜不到的：构建命令、非默认风格、项目特有的坑 |
| Rules（带 `paths:`） | 只在碰相关路径时 | 跨切面的局部约束 |
| Skills | 按需，只加载 name + description | 流程性知识：部署清单、审查流程、验证步骤 |
| Subagents | 被调用时，跑在独立窗口 | 会污染主上下文的调查（深搜、日志分析） |
| Hooks | 生命周期事件，绕过压缩 | 必须**确定性**发生的事 |

三条反直觉结论：

1. **膨胀的 CLAUDE.md 会让 Claude 忽略你真正的指令**——重要规则淹没在噪音里。官方建议 < 200 行，每行问："删掉它 Claude 会犯错吗？"
2. **"每次 X 都要做 Y"不是 CLAUDE.md 的内容，是 hook**。"模型选择去跑 formatter"和"formatter 自动跑了"是两回事。
3. **"绝对不要做 X"提示词保证不了**。长会话、压力下、或文件里被塞了提示注入时，模型会违背。真正的护栏是 hooks 和 permissions（`PreToolUse` hook 检查后 exit code 2 可拦截）。

### 证据 5 · 上下文是最重要的资源

官方最佳实践的总纲：Claude 的上下文窗口填充很快，**填充时性能下降**。两个典型失败模式：

- **厨房水槽会话**：一个任务里穿插问无关的事 → 修复：不相关任务之间 `/clear`
- **反复纠正**：同一问题上纠正 2 次以上，上下文已被失败方案污染 → 修复：**纠正两次就 `/clear`，用更具体的提示重开**。干净的会话 + 更好的提示，几乎总是胜过积累了一堆纠正的长会话。

## 三个转变

### 转变一：从"写提示词"到"发现未知"

**① Blind spot pass**（做不熟的模块前，直接用它给的原话）：
```
我对这个 codebase 的 X 模块一无所知。先做一次 blind spot pass，
把我相关的 unknown unknowns 找出来，然后帮我更好地 prompt 你。
```
关键：**告诉它你的起点**（你是谁、懂什么、不懂什么）。

**② 让 Claude 采访你**（官方最佳实践推荐）：
```
我想做 [简述]。用 AskUserQuestion 详细采访我，
问技术实现、UI/UX、边界情况、权衡取舍。
不要问显而易见的，往我没考虑到的硬骨头里挖。
一直问到覆盖完整，然后把 spec 写到 SPEC.md。
```
spec 完成后**开新会话执行**——干净上下文专注实现，且你手上有一份可引用的书面规格。

**③ 原型先行**（治 Unknown Knowns）：
> "在接任何真实数据前，先做一个单文件 HTML，用假数据把新工具栏 mock 出来。我想先对布局有反应，再让你碰真代码。"

先做 3–4 个**完全不同的方向**给你反应，比让它猜一个再改 5 轮便宜得多。

**④ 参考资料优先用代码**：官方明确 **HTML mockup > 设计稿描述 > 截图**。有现成实现（哪怕别的语言）直接指过去：
```
vendor/rate-limiter 这个 Rust crate 实现了我想要的确切退避语义。
读它，在我们的 TypeScript client 里重实现同样的语义。
```

### 转变二：从"让它自审"到"独立上下文 + 可执行检查"

替换原第 2 步。按可靠性递增：

1. **同提示内**：让它在同一条消息里跑检查并迭代（`"实现后运行测试"`）。
2. **独立子代理审查**：
```
用子代理按 PLAN.md 审查这个 diff。检查每条需求是否落地、
列出的边界情况是否有测试、有没有超出任务范围的改动。
只报正确性缺陷，不报风格偏好。
```
现成的还有 `/code-review`——在全新子代理里审当前 diff。
3. **确定性护栏**：Stop hook，检查不过就不让结束轮次。这是唯一真正"确定"的层级。
4. **对抗性审查**：新鲜上下文里独立评估，不看产生改动的推理过程。

同时改造原第 1 步的提示词，把验收标准前置：

| 之前 | 之后 |
|---|---|
| "实现一个校验邮箱的函数" | "写 validateEmail。用例：`user@example.com` 真、`invalid` 假、`user@.com` 假。**实现后运行测试**" |
| "让页面好看点" | "[贴截图] 实现这个设计。**对结果截图与原设计对比，列出差异并修复**" |
| "构建失败了" | "构建失败，报错：[贴]。修复并验证构建成功。**解决根因，不要抑制错误**" |

### 转变三：从"每次现编"到"沉淀环境"

把重复的组织工作沉淀成环境资产（对应证据 4 的表）：

- **CLAUDE.md** —— 起手 `/init`，然后按"删了会犯错吗"逐行修剪到 200 行内。
- **Rules** —— `.claude/rules/`，带 `paths:` frontmatter，只在碰相关文件时加载。
- **Skills** —— 流程性知识（"怎么验证这个项目"应当写成 skill，从 CLAUDE.md 引用）。
- **Hooks** —— 必须每次都发生的，以及所有"绝对不要"的护栏。
- **Subagents** —— `.claude/agents/`，会污染主上下文的一次性调查。

## 反例与适用边界

- **不是所有任务都要规划**。官方：如果你能用一句话描述这个 diff，跳过计划。修 typo、加日志行、重命名变量，别上 Plan Mode。
- **模糊提示有时是对的**。探索阶段问 `"你会改进这个文件的什么？"` 反而能问出你不会想到要问的东西。具体 vs 开放，取决于你在探索还是在执行。
- **不要无脑追审查发现**。见证据 3：会导致过度工程化。审查者必须被限定"只报正确性缺陷"。
- **不要为每个发现都建文档**。官方新规则明确：不要为每个普通收藏/发现建独立页面，用渐进式披露。
- **过度指定的 CLAUDE.md 是负资产**。长文件会导致 Claude 忽略一半指令。
- 本方法主要针对 Claude Code。转 Codex / Cursor 时机制名不同（AGENTS.md 等），但**三个转变的内核与工具无关**。

## 讨论后的判断

1. 原三步法的**顺序基本对，但三个环节的性质要换**：澄清从"我已知"扩到"我发现我不知道的"；审查从"自我审查"换成"独立上下文 + 可执行检查"；测试从"最后的兜底"前移成"提示词里就写好的验收标准"。
2. **最高杠杆的单点改动**是给 Claude 一个它能自己跑的检查。这一条同时解决了"我是验证循环"和"审查流于形式"两个问题。
3. 面试考察的不是"会不会调工具"——CodeSignal 2026-03 的 Agentic Interviewing 说明已明确允许用 Claude Code / Codex / Cursor，**会用工具本身不是信号**。见下节。

## 面试侧：被追问的五个维度

| 维度 | 强信号 | 弱信号 |
|---|---|---|
| 任务拆解 | 先拆任务、定约束、定第一步，主导工作流 | 一股脑丢给工具，被模型输出推着走 |
| 上下文选择 | 主动收 working set，始终能解释清楚 | 能给的全给，最后自己 review 不过来 |
| 权限判断 | 讲清何时要更大的能力边界、何时只是制造风险 | 默认全开，祈祷别出事 |
| 审查验证 | 像审 teammate 的 PR 一样查复杂度、边界、数据流、失败场景 | 只能接住"生成代码"，接不住"为什么值得信任" |
| 追问深度 | 说清为什么选这个方案、为什么放这层边界 | 一追问就暴露真正思考的不是自己 |

**最致命的一条**：*vibe coding 会让 debug 叙事变弱*——代码一坏就继续重试 prompt，而不是自己先推理。"前 30 秒看起来很快，后 10 分钟看起来很空。"

**反直觉但官方推荐的训练**——让它考你：
```
我想要确认我完全理解了这次变更。给我一份 HTML 报告
（改动内容、上下文、直觉、做了什么），底下附一份
关于这次改动的测验，我必须满分通过。
```
长会话后 Claude 做的事往往远超你的理解，读 diff 只给浅层认知。**考过才 merge。** 这同时是理解手段和"我能解释我交付的每一行"的面试训练。

## 行动规则

> 下一次遇到什么情况，我具体怎么做？

1. **不平凡的任务开始前**，先加一句 blind spot pass 或"采访我"，产出 spec 再动手。
2. **审查一律换成独立子代理**，并固定附上"只报正确性缺陷，不报风格偏好"。
3. **任何任务开始前先问：这个任务的 pass/fail 检查是什么？** 没有就想办法造一个（测试 / 构建 / 截图对比 / 脚本）。造不出来就先别开工。
4. **同一问题纠正满 2 次** → `/clear`，带上已学到的信息重写提示，不在烂上下文里继续。
5. **任务之间 `/clear`**，不做厨房水槽会话。
6. **每次会话结束后问**：这次的什么东西值得沉淀进 CLAUDE.md / rules / skills / hooks？只沉淀"下次还会用到"的。
7. **每周**：把一条重复了 3 次的口头指令升级成 hook 或 skill。
8. **交付前**：让它出测验，考过再收。

## 验收（按母题法，未过不算沉淀）

- [ ] **闭卷 3 分钟**：讲清"为什么给 Claude 可执行的检查比让它自审更重要"，并说出四类未知的差别。
- [ ] **两层追问**：① 什么情况下**不该**用子代理审查？② 为什么"绝对不要做 X"不能写成提示词？
- [ ] **项目迁移**：在 RuleArena 或 EnergyOps 上真实跑一次完整流程（blind spot → spec → 实现 → 独立审查 → 检查通过），并留下可复述的对照记录。
