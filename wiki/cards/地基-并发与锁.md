## ground ground-lock · 并发与锁地基包

**定位**：从单机锁到分布式锁的完整决策线——Agent 后端的多任务、多实例场景天天在用；与 MySQL 事务/业务并发两主线、Redis 主线联动。不含语言级并发包的 API 细节。

**心智模型**：锁的每一步都是**花性能买正确性**，所以每个决策都是判据题：冲突率决定**要不要**锁（乐观 vs 悲观），共享范围决定锁**画多大**（粒度、临界区、读写），机器边界决定锁**放哪里**（单机内存 → 分布式）。分布式锁的根问题是：**锁服务和真相分离了**——持锁者可能已经死了但锁还在，所以无论哪种实现，最终都要配 fencing token（一次单调递增的凭据）兜底。

**必会清单**：
- 乐观锁判据 = 冲突率：成本约单次 ÷(1−p)，高冲突下总工作量约 N²；悲观锁约 N [@并发与锁-1]
- 两种锁的实体：version 字段 / SELECT FOR UPDATE / 语言级锁，各自的适用层 [@并发与锁-1]
- 锁数据不锁代码：粒度与临界区尽量小；自旋还是睡眠看持有时长 [@并发与锁-2]
- 读写锁的退化场景、CAS 与 ABA：无锁不是没代价 [@并发与锁-2]
- 分布式锁三实现（DB / Redis / ZK）与各自失效场景；为什么「锁本身」还要配 fencing token [@并发与锁-3]

**学习路径**：
1. 先学「要不要加锁」：所有题的第一步是算冲突账 [@并发与锁-1]
2. 再学「锁画多大」：单机内的粒度与临界区 [@并发与锁-2]
3. 最后分布式锁：单机直觉直接搬到多机会失效，失效点就是考点 [@并发与锁-3]

**验收门**：
- 给抢库存场景选锁型并把成本账算出来 [@并发与锁-1]
- 讲清「Redis 锁为什么会失效、fencing token 怎么补」 [@并发与锁-3]
