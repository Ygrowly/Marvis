## ground ground-mysql · MySQL 地基包

**定位**：MySQL 8.0 / InnoDB 的索引、事务锁、SQL 优化、日志恢复、复制高可用与业务并发场景——每家公司都会问的通用底盘。不含源码、DBA 调优、PostgreSQL 与 NoSQL。

**心智模型**：七条主线分两组——一、二回答「怎么读得快」，三至六回答「怎么写得稳」，七是真实业务落地。全部机制的根判据是同一条：**磁盘随机 IO 比内存慢约 5 个数量级**，所以 B+ 树三层（扇出约 1170）覆盖约 2000 万行只要 3 次 IO；所有设计都在做两件事之一：**换 IO 次数**，或**把随机写换成顺序写**（WAL）。抓住这条根，每个机制都能从它推出来。

**必会清单**：
- B+ 树选型判据 = 磁盘 IO 次数：三层覆盖约 2000 万行只花 3 次 IO [@MySQL-1]
- 联合索引按字典序排列，只有连续前缀能切出定位区间；「用不上」= 扫描量约等于全表 [@MySQL-1]
- 二级索引叶子只存「索引列 + 主键值」，回表是随机 IO，代价随命中行数线性增长 [@MySQL-1]
- ACID 的机制拆解：A 靠 undo、D 靠 redo、I 分锁与 MVCC 两路，C 是结果不是机制 [@MySQL-3]
- RC 与 RR 的唯一差别是 ReadView 的生成时机 [@MySQL-3]
- 两阶段提交的唯一理由是 redo 与 binlog 的逻辑一致，崩溃后由 binlog 完整性裁决 [@MySQL-4]
- 长事务只读也危险：MVCC 链的回收看 ReadView，不是看你做了什么 [@MySQL-5]
- 乐观锁的判据只有冲突频率：成本约单次 ÷(1−p)，高冲突下总工作量约 N²，悲观锁约 N [@MySQL-7]

**学习路径**：
1. 先学「索引与表设计」：索引的有序性是后面执行计划、回表、覆盖索引的共同前提 [@MySQL-1]
2. 再学「SQL 执行与优化」：五层链路里只有优化器做决定，慢的第一嫌疑人是它估算错 [@MySQL-2]
3. 然后「事务与锁」「日志与持久化」互为因果：并发正确性与崩溃不丢，一起学才通 [@MySQL-3]
4. 「长事务」「数据增长与高可用」是稳定性延伸：先归档再谈分库分表 [@MySQL-5]
5. 最后「业务并发场景」：前六条在抢库存、排行榜上的综合应用 [@MySQL-7]

**验收门**：
- 合上资料，按「读得快 → 写得稳 → 业务落地」两组讲出七条主线各自回答什么问题 [@MySQL-1]
- 能从「磁盘随机 IO 慢 5 个数量级」这条根判据推出 B+ 树、WAL、回表代价中的任意两个 [@MySQL-4]
