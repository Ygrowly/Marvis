## ground ground-mq · 消息队列地基包

**定位**：异步与削峰的底盘——MQ 三问（丢 / 重 / 积压）是后端面试标配，也直接对应 Agent 任务队列场景。不含具体 MQ 的运维与调参。

**心智模型**：MQ 的全部保证从一条推出：**跨进程跨网络的传递是会失败的，所以只敢承诺「至少一次」**。不丢靠每一段的确认（生产确认 → Broker 持久化 → 消费 ACK）——少一段就有一个丢失点；「重复」是至少一次的必然代价，用幂等消费接住；「乱序」是分区的代价，按业务 key 路由换局部有序。积压不是事故是常态，消费速度怎么扩要在设计时想好。

**必会清单**：
- 三段丢失点与兜法：生产者确认机制、Broker 持久化（刷盘策略）、消费者手动 ACK [@消息队列-1]
- 至少一次 → 只生效一次：幂等消费（唯一业务键 / 去重表 / 版本号），业务层接住重投 [@消息队列-2]
- 乱序的来源与对策：多分区并行必然乱序；按 key 路由保「同一实体局部有序」 [@消息队列-2]
- 积压治理：加消费者受分区数上限时，换思路（批处理 / 跳过 / 临时转储队列）[@消息队列-3]
- 选型到底在选什么：吞吐 / 延迟 / 顺序 / 语义保证的组合，没有全能冠军 [@消息队列-3]

**学习路径**：
1. 先学「怎么不丢」：三段丢失点是后面一切的地基 [@消息队列-1]
2. 再学「为什么必然重复」：懂了至少一次，幂等才不是背诵 [@消息队列-2]
3. 最后「撑不住」：积压与选型，回到业务负载谈 [@消息队列-3]

**验收门**：
- 画出一条消息从生产到消费的三个丢失点及各自的兜法 [@消息队列-1]
- 一句话讲清「至少一次怎么变成只生效一次」 [@消息队列-2]
