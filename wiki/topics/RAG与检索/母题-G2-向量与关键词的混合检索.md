**题目**：面试官问——"你们的检索是怎么做的？为什么既要用向量又要用关键词？"

**母题**：**语义检索和关键词检索各自强在哪、弱在哪——为什么企业知识库通常两路都要？两路结果怎么合，权限又该在哪一步生效？**

**为什么重要**：这是 RAG 面试的**必答题**，也是最能区分"用过"和"照文档搭过"的一题。答"我们用向量库"会被追问到崩；**答出"两路各有盲区、融合要处理量纲不可比、权限必须在召回前生效"才算过关**。

## 一、教材

### 1. 前提：两路检索的盲区正好互补

| | 强项 | 弱项 |
|---|---|---|
| **BM25 / 关键词** | **专有名词、编号、精确短语**、可解释 | **同义表达与语义泛化弱** |
| **Dense Vector** | **语义相似、自然语言改写** | **编号 / 罕见词弱**，且受 Embedding 版本影响 |
| **Hybrid** | 同时覆盖精确与语义 | **需要融合、去重和调参** |

【事实】**得物文章给的那个反例最直观**：

```text
搜 "SLB-20250101-abc" 这种 trace ID
→ Embedding 模型无能为力（语义向量对专有编码不敏感）
→ BM25 倒排索引才是正解
```

反过来：

```text
搜 "数据库连接池"
→ 应该命中 "DB connection pool 配置"
→ 文字完全不同、意思一样 → 这是 Dense 的强项，BM25 匹配不上
```

【推论】**所以"用哪个"这个问题的正确答案是"两个都用"**——**不是因为混合更先进，是因为它们的盲区不重叠**。而两者都覆盖不到的（比如需要多跳推理的关系），才是 GraphRAG 要解决的问题（见第 5 节）。

**到这里你应该能回答**：为什么"我们的检索用的是向量库"这个回答不完整？

### 2. 向量这一路的基础：相似度怎么量

#### 2.1 余弦相似度是默认选择【事实】

```text
余弦相似度 = cos(θ) = (A·B) / (|A| × |B|)
值域 [-1, 1]；实践中 Embedding 产出的向量通常落在 [0, 1]，负值极少
1 = 方向完全一致，0 = 正交（无关）
```

【推导】**为什么是余弦而不是别的**——**因为 Embedding 模型在训练时就是用余弦相似度优化的**。

> 得物文章的原话：**"你用别的度量去比，相当于考试的评分标准都换了，成绩自然不准。"**

| 度量 | 什么时候用 |
|---|---|
| **余弦相似度** | **默认选它** |
| **欧氏距离** | 衡量空间直线距离，**受向量长度影响大**（两个意思相同但长度不同的向量，欧氏距离可能很大而余弦很高）——通常不优先 |
| **点积** | **当向量已做 L2 归一化（长度为 1）时，点积 = 余弦**，而且更快 |

#### 2.2 维度是模型定的，不是你能调优的【事实】

```text
主流 Embedding 模型的维度：768 / 1024 / 1536
比如「用户喜欢川菜」 → [0.21, -0.43, 0.07, 0.85, ..., -0.12]  ← 1536 个数字
```

【推论】**维度不是"越大越好"的调优项**——它由模型决定，**换模型就换维度，整个索引必须重建**。

【取舍】**这也是"Embedding 版本"必须进版本管理的原因**：**新旧向量混在同一个索引里是不可比的**，所以换模型 = 全量重嵌入 + 双写切换（[[母题-G6-知识更新与增量索引]]）。

### 3. 为什么必须用 ANN：算力账

#### 3.1 精确 KNN 算不动【推导】

```text
精确 KNN = 逐条遍历所有向量，逐一算相似度，排序取 Top-K
复杂度 O(N × D)

100 万条向量 × 1536 维：
  100万 × 1536 = 15.36 亿次浮点运算

即使每次运算只要 1 纳秒：
  15.36 亿 × 1ns ≈ 1.5 秒 / 次查询
```

【结论】**单次查询 1.5 秒，这在任何在线系统里都不可接受。** 而这是**单条**的代价——并发一来直接崩。

【推论】**ANN（近似最近邻）不是"精度优化"，是"算力逼出来的"**：**牺牲一点召回精度，换数量级的性能提升**。这是所有 ANN 算法共同的设计取舍。

#### 3.2 HNSW 怎么做到【推导】

【事实】**回顾跳表**（[[母题-R1-Redis数据结构与选型]]）：有序链表加多级索引，上层稀疏、下层稠密，查找时从上层快速跳。

**HNSW 把分层思想搬到了图上**——但这里有个关键问题：

```text
跳表能工作，是因为链表是有序的，
比一下大小就知道往左还是往右。

但向量没有「大小」概念——向量 (1,3) 和 (-2,5) 谁大？没法比。
→ 光有分层不够，还得解决「图上怎么导航」
```

【事实】**HNSW 的解法**：

```text
① 分层：每个节点按概率随机分配到若干层，同时存在于所属层及以下所有层
   （层间只有同一节点的纵向连接，没有跨节点连线）
② 贪心导航：上层节点少、边长跨度大 → 先粗定位
             顺着纵向连接降到下一层 → 逐层下沉
             到第 0 层做精细搜索
```

**层数能算出来**：

```text
100 万节点，晋升概率按 1/M（M = 16）：
  第 1 层 ≈ 100万 / 16 = 6.25 万
  第 2 层 ≈ 3,906
  第 3 层 ≈ 244
  第 4 层 ≈ 15
  第 5 层 ≈ 1
  → 最高约 5 层
```

【事实】得物文章给的实测口径：**"100 万节点，图的最高层大概 5–6 层"**。论文里第 L 层的节点占比是 **`exp(−L/mL)`**，论文推荐的归一化因子是 **`mL = 1/ln(M)`**（M=16 时约 0.36）。

【纠正常见误解】**注意 `mL = 1/ln(M)` 这个取值【恰好复现】简化的 `(1/M)^L`，不是"更胖"**：

```text
exp(−L / mL) = exp(−L · ln M) = exp(ln(M^−L)) = M^−L = (1/M)^L
```

**两者是同一个分布**（M=16、L=1..5 逐层验算完全相同）。**要让分布变"胖"（高层节点更多），得把 mL 调【大】**——`mL` 越大，衰减越慢。**说成"论文的分布比 1/M 更胖"是错的**：论文的推荐值恰恰是让两者相等的那一个。**而不论用哪个 mL，"层级越高节点越少"的指数衰减规律都成立。**

【推论】**上层的长距离边还有一个作用**：帮搜索在早期跳过"看起来近但其实不对"的区域，避免卡在局部最优里。

【事实】**选型分档**（得物的口径）：**百万级以内用 HNSW，千万级用 IVF，亿级考虑 DiskANN 或分片**。ES、Faiss、Milvus 都默认支持 HNSW。

**到这里你应该能回答**：为什么"向量库慢"通常不是硬件问题，而是索引选型问题？

### 4. 两路怎么合：RRF

#### 4.1 为什么不能直接加分数【推导】

```text
向量路：doc_A 得分 0.92   ← 余弦相似度，值域 [0, 1]
关键词路：doc_B 得分 8.7  ← BM25 相关度，无上界

0.92 和 8.7 谁更相关？没法比。
```

【推论】**量纲不可比 → 加权求和需要调参，而且换个数据集就失效。**

#### 4.2 RRF 的做法：扔掉分数，只看排名【事实】

```text
score(d) = Σ 1 / (k + rank_i(d))       k 通常取 60
```

**规则**：**某一路排得越前贡献越大；在越多路里靠前，总分越高（各路独立贡献、自然叠加）**。得物原文的说法是"**不偏向任何一路，只看综合排名**"，实现只要约 30 行代码。

#### 4.3 把融合结果算出来【推导】

```text
doc_A：ANN 第 1，BM25 第 10
  RRF = 1/(60+1) + 1/(60+10) = 0.0164 + 0.0143 = 0.0307

doc_B：两路都第 5
  RRF = 1/(60+5) + 1/(60+5) = 0.0154 + 0.0154 = 0.0308
```

【结论】**doc_B 略胜**——它一路第一、另一路第十，**却输给了"两路都在前列"的 doc_B**。

【推论】**这就是 RRF 的设计意图：奖励"多路共识"，而不是"单路极端强"。** 只在一路出现、另一路没出现的文档，自然排后面。

::figure rrf-fusion.svg | RRF：为什么不拼分数拼排名 | 两路分数量纲不可比；RRF 每路贡献 1/(k+排名)，各路独立叠加；例子说明它奖励"多路都在前列"

**到这里你应该能回答**：为什么"一路第一、另一路第十"的文档，可能排不过"两路都第五"的？

### 5. 融合之外的几件事

#### 5.1 权限必须在检索前生效【事实】

**错误做法**：先检索全部文档，再让模型"不要泄露"。

**正确做法**：

```text
身份 / 租户 / 角色  →  策略决策  →  生成 ACL Filter  →  受权召回  →  生成与引用
```

【推论】**为什么必须在召回前**：

```text
① 未授权内容一旦进入上下文，就已经"泄露"了——
   模型是否说出来是概率问题，不是权限控制
② 未授权内容还会挤占上下文预算，降低有用证据的质量
③ 日志、Trace、缓存都可能把未授权内容带出去
```

【事实】**还要测的场景**（这些都是真实事故形态）：**跨租户、已撤权、共享链接、继承权限、删除传播、缓存污染**。

#### 5.2 其他几种召回增强【事实】

- **Query Rewrite / Decomposition**：多条件问题拆成子查询，再合并证据
- **Multi-hop**：第二轮检索由第一轮发现的实体驱动
- **Metadata Filter**：租户、ACL、时间、地区、文档类型

【取舍】**Filter 有一个反直觉的坑**：**过滤会缩小候选集，可能把正确答案滤掉**（比如 ACL 配置错了、或者时间字段本身标错）。所以**过滤条件本身也要进评测**——不能只测"过滤生效了没有"，还要测"过滤有没有误伤"。

#### 5.3 GraphRAG 什么时候值得【取舍】

**当问题依赖实体关系、多跳路径和全局结构，普通相似检索难覆盖时才考虑。**

【取舍】**代价是图谱构建、更新和评测成本都不低。** **如果只是品牌词查询或单文档问答，混合检索更简单**——不要为了技术先进性上图谱。

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "向量检索比 BM25 先进，全用向量就行" | **反例很硬**：搜 `SLB-20250101-abc` 这种 trace ID，**Embedding 模型无能为力**（语义向量对专有编码不敏感），BM25 才是正解。**两者盲区不重叠，所以企业库通常两路都要** |
| "直接给两路分数加权求和就行" | **量纲不可比**（余弦 ∈ [0,1]，BM25 无上界），加权要调参且换数据集就失效。**RRF 扔掉分数只看排名，不需要调参** |
| "RRF 就是取平均" | **不是**。它是 `Σ 1/(k+排名)`——**奖励"多路共识"**：一路第 1、另一路第 10 的文档（0.0307）**排不过两路都第 5 的**（0.0308） |
| "向量维度越高检索越准" | **维度由模型决定，不是调优项**。而且**换模型就换维度，整个索引必须重建**——所以 Embedding 版本必须进版本管理，新旧向量**不可比** |
| "向量库慢就加机器" | **多半是索引选型问题**。精确 KNN 是 O(N×D)（100 万 × 1536 维 ≈ 1.5 秒/次），**必须用 ANN**；百万级以内 HNSW、千万级 IVF、亿级 DiskANN 或分片 |
| "先把全部召回来，再让模型别说没权限的" | **这是明确的数据泄露**——未授权内容一旦进入上下文就已经出去了；而且它会挤占预算、还可能进日志和缓存。**权限必须在召回前生效** |
| "HNSW 保证找到最近的" | **它是近似算法，不保证命中全局最近邻**——这是所有 ANN 的共同取舍：**用可控的召回损失换数量级性能**。要 100% 精确就得回到 O(N×D) |

【取舍】读成一句话：**"用哪一路"不是先进性问题，是"你的查询里有多少是专有编码、有多少是自然语言"——所以要按查询类型分桶评测来定，而不是拍脑袋。**

## 二、自测

**Q1（计算）**：向量库里有 **100 万**条 **1536 维**向量。

问：**精确 KNN 一次查询要做多少次浮点运算？**假设每次运算 1 纳秒，单次查询要多久？

**A1**：

```text
精确 KNN 复杂度 = O(N × D)
= 1,000,000 × 1536
= 1,536,000,000 次浮点运算（约 15.36 亿次）

按每次 1ns：
= 15.36 亿 × 1ns = 1.536 秒 / 次查询
```

【结论】**单次查询约 1.5 秒**——而这还只是**单条**的代价，并发一来直接崩。

【推论】**ANN（近似最近邻）不是"精度优化"，是算力逼出来的**：用可控的召回损失换数量级的性能。**所有 ANN 算法共享这个取舍**，HNSW 只是其中平衡得最好的一个。

**Q2（计算）**：HNSW 有 **100 万**个节点，每层晋升概率约为 **1/M**（M = 16）。

问：**第 1 到第 5 层各有多少节点？**最高大约几层？这个衰减规律叫什么？

**A2**：

```text
第 1 层 ≈ 1,000,000 / 16 = 62,500
第 2 层 ≈ 3,906
第 3 层 ≈ 244
第 4 层 ≈ 15
第 5 层 ≈ 1

→ 最高约 5 层
```

【结论】**层级越高节点越少（指数衰减）**——**上层节点极少，但每个节点都要连 M 个邻居，所以这些边自然跨越很远**，正好用来"快速通道"式地粗定位。

【补充】这是**跳表思想的直接移植**（[[母题-R1-Redis数据结构与选型]]）。区别在于：**跳表靠"大小比较"导航，而向量没有大小概念，所以 HNSW 必须再加一个"贪心搜索"在图里导航**——**分层 + 贪心，两者合起来才是 HNSW 的全部核心。**

**Q3（计算）**：用 RRF 融合两路结果，`k` 取 60。

```text
doc_A：ANN 排第 1，BM25 排第 10
doc_B：两路都排第 5
```

问：**两篇文档的 RRF 分数分别是多少？谁更高？**这说明 RRF 在奖励什么？

**A3**：

```text
doc_A = 1/(60+1) + 1/(60+10)
      = 1/61 + 1/70
      = 0.01639 + 0.01429
      = 0.03068

doc_B = 1/(60+5) + 1/(60+5)
      = 1/65 + 1/65
      = 0.01538 × 2
      = 0.03077

doc_B 略高（0.03077 > 0.03068）
```

【结论】**一路第一、另一路第十的文档，排不过"两路都在前列"的文档。**

【推论】**RRF 奖励的是"多路共识"，不是"单路极端强"。** 这正好对应它的设计目标：**不偏向任何一路**——因为两路各自有盲区（Dense 不懂专有编码、BM25 不懂同义改写），**"两路都认为它相关"比"一路强烈认为它相关"更可信**。

**Q4（纠错）**：下面这段话哪里不准确？

> "我们用向量检索就够了，语义检索比关键词检索先进得多。"

**A4**：三处问题。

1. **两路的盲区不重叠，不是先进性问题**：**向量检索对专有编码（`SLB-20250101-abc` 这类 trace ID、订单号、错误码）无能为力**——语义向量在那里几乎没有信号。**而这恰恰是企业知识库里最常见的一类查询。**
2. **BM25 还有可解释性优势**：它能告诉你"命中了哪个词"，这在排查和给用户看依据时很有用。
3. **混合也不是免费的**：要用 **RRF 之类的方式融合**（不能直接加分数，量纲不可比），还要处理去重。

【准确说法】"**应该按查询类型分桶评测来决定权重**：专有名词、编号、错误码偏 BM25；自然语言同义改写偏向量；**企业知识通常混合检索后重排**。这是得物那篇文章和 study/03 的共同结论。"

**Q5（纠错）**：下面这段话哪里不准确？

> "权限控制放在生成阶段就行——把全部文档召回，然后让模型不要说出没权限的内容。"

**A5**：**这是明确的数据泄露，不是优化点。**

1. **未授权内容一旦进入上下文，就已经"出去"了**——模型是否说出来是**概率问题**，不是权限控制。**这等于把权限交给模型的自觉。**
2. **它会挤占上下文预算**：无关且未授权的内容占掉的位置，本该给真正有用的证据（[[母题-C1-上下文组装与窗口预算]]）。
3. **还可能从别的渠道漏出去**：日志、Trace、缓存都可能记录下召回的原文——**而"日志里不能有敏感原文"本身也是要求**。

【准确说法】"**身份 / 租户 / 角色 → 策略决策 → 生成 ACL Filter → 受权召回 → 生成与引用**。**权限必须在召回前生效。** 而且要专门测：**跨租户、已撤权、共享链接、继承权限、删除传播、缓存污染**。"

## 三、面试输出（学完再看）

**一句话结论**：**两路检索的盲区不重叠，所以企业知识库通常两路都要**——BM25 强在专有名词 / 编号 / 精确短语（搜 `SLB-20250101-abc` 这种 trace ID，**Embedding 无能为力**），Dense 强在语义改写真（搜"数据库连接池"能命中"DB connection pool 配置"）。向量这一路：**余弦相似度是默认**（因为模型训练时就用它优化），**维度由模型决定、换模型必须重建索引**。**精确 KNN 是 O(N×D)**——100 万 × 1536 维 = **15.36 亿次运算 ≈ 1.5 秒/次**，所以**必须用 ANN**；**HNSW = 跳表分层 + 图上贪心导航**（100 万节点约 5–6 层），**百万级以内 HNSW、千万级 IVF、亿级 DiskANN 或分片**。两路融合用 **RRF**：`Σ 1/(k+排名)`，**因为两路分数量纲不可比**（余弦 ∈ [0,1]，BM25 无上界），RRF **奖励多路共识**——一路第 1 另一路第 10（0.0307）排不过两路都第 5（0.0308）。最后一条最容易答错：**权限必须在召回前生效**，先召回再让模型"别说"是**已经泄露**。

**恢复关键词**：两路盲区互补（专有编码 vs 同义改写）/ 余弦 = 默认（模型就是这么训的）/ 点积 = 余弦（L2 归一化后）/ 维度由模型定，换模型必须重建 / 精确 KNN = O(N×D) ≈ 1.5 秒/次 / ANN 是算力逼的，不是精度优化 / HNSW = 分层图 + 贪心导航，100 万节点约 5–6 层 / 百万 HNSW · 千万 IVF · 亿级 DiskANN/分片 / **RRF `Σ1/(k+排名)`，k=60，奖励多路共识** / **权限在召回前生效**（跨租户·撤权·删除传播·缓存污染）/ GraphRAG 只在多跳与全局结构才值

**核心不变量 / 主线**：
**两路检索的盲区不重叠，所以"选哪一路"是个伪问题；真正的问题是"融合要怎么处理量纲不可比"，以及"权限要在哪一层拦"。**
前者用 **RRF 只排名不拼分**解决，后者用 **ACL Filter 前置**解决——**两个都是"不试图用错的方式解决错的问题"**。

**完整回答骨架**：两路各自强/弱（各给一个反例）→ 相似度度量怎么选（余弦 + 为什么）→ 精确 KNN 算不动 → ANN 与 HNSW（给算力账和层数）→ 融合用 RRF（给融合算式）→ **权限必须在召回前**（并说清"先召回再让模型别说"为什么是泄露）→ GraphRAG 的边界 → 收束到"按查询类型分桶评测来定权重"

**追问**（先说后看）

1. **向量检索和 BM25 怎么选？** —— **按查询类型分桶评测**：专有名词、编号、错误码偏 BM25；自然语言同义改写偏向量；**企业知识通常混合检索后重排**。**选择由数据决定，不由偏好决定。**
2. **RRF 的 k 是干什么的？** —— 它**平滑高排名的差距**：k 越大，第 1 名和第 2 名的贡献差距越小（`1/(k+1)` vs `1/(k+2)`）。**k=60 是社区默认值**，k 太小会让"某一路单独第一"过于强势。
3. **HNSW 为什么在精度和速度之间平衡得最好？** —— **分层给了"对数级"的搜索路径**（100 万节点约 5–6 层），**贪心导航在每层只需要局部比较**；而且它**实现成熟、生态完善**（ES、Faiss、Milvus 都默认支持）。
4. **多跳（multi-hop）问题怎么处理？** —— **第二轮检索由第一轮发现的实体驱动**。比如"某公司 CEO 的母校在哪"——先检索"公司 CEO"，再用找到的人名检索"母校"。**这不是检索算法的问题，是查询规划的问题**（见 [[母题-G3-重排与召回质量]]）。
5. **怎么防止 RAG 越权？** —— **身份进入检索层、ACL filter 先于召回**；**缓存按租户 / 权限分区**；**引用和下载再次鉴权**；**做跨租户与撤权测试**；**日志避免记录敏感原文**。

**同类变体**

- 「余弦相似度和欧氏距离怎么选？」——**默认余弦**（模型就是这么训的）；**欧氏距离受向量长度影响大**（意思相同但长度不同的向量，欧氏可能很大而余弦很高）；**点积在向量已 L2 归一化时等于余弦，且更快**。
- 「稀疏向量（SPLADE 之类）和 BM25 什么关系？」——**都是稀疏表示**，但稀疏向量是**学出来的**、能部分覆盖同义改写；**BM25 是统计出来的、完全不做语义泛化但绝对可解释**。**两者常作为"关键词这一路"的不同实现**。
