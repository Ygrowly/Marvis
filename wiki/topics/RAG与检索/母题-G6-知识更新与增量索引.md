**题目**：面试官问——"你们的文档更新了怎么办？删除和撤权呢？"

**母题**：**知识改了、删了、撤权了，索引怎么跟上——为什么"更新"这件事里最难的不是新增，而是删除？**

**为什么重要**：这是 RAG 面试里**最容易被忽略、但工程上最容易出事的一题**。多数人答得出"我们每天重建一次索引"，但答不出"**删除怎么传播**"。**而删除和撤权出事不是性能问题，是合规事故**——用户能搜到已经删除或本无权看的内容。

---

## 一、教材

### 1. 前提：索引是派生数据，源变了它就必须变

【推导】**索引（向量 + 倒排 + 元数据）不是事实来源，它只是源文档的派生视图。** 这直接推出一件事：

```text
源文档的三种变化，索引都必须跟着变：
  ① 新增 / 修改  → 内容变了，派生视图要重算
  ② 删除         → 源没了，派生副本不能留着
  ③ 撤权         → 内容还在，但"谁能看"变了
```

【推论】**新增最容易（多加一份），删除最难**——因为**删除要找全所有派生物**，而派生物是散开的（一个文档切成 N 个块，每块有向量、倒排项、元数据）。

::figure index-update.svg | 知识更新：三条路径都要走完，缺一条就出事 | 新增走增量链路；删除要按 ID 反查全部块；撤权还要连缓存一起清

**到这里你应该能回答**：为什么"我们每天全量重建一次索引"这个答案会让面试官追问删除和撤权？

---

### 2. 为什么值得做增量【推导】

```text
100 万块文档，每天只改 1%：

全量重建：
  每天重算 100 万次嵌入

增量更新：
  只重算变化的 1% = 1 万次嵌入

降到 1/100
```

【结论】**增量的收益是数量级的**——尤其在嵌入调用要花钱的时候（[[母题-C6-成本与长上下文截断]] 的成本口径）。

【取舍】**但增量不是免费的**，它换来两个新问题：

```text
① 要维护【版本】：哪一版索引对应哪一版源文档？
② 要保证【一致性】：增量跑失败一半怎么办？新旧混在一起怎么办？
```

【推论】**所以"全量重建"不是笨办法，是"数据量小、更新频率低"时的正确选择**——**它的简单性是真实的收益**。**判断该不该上增量，看的是"重建一次要多久、多久需要重建一次"，不是技术先进性。**

---

### 3. 删除：为什么它比新增难得多【推导】

【推导】**删除必须按文档 ID 反查它切出来的全部块**：

```text
一份文档 → 切成 100 个块 → 每块有：向量 + 倒排项 + 元数据

删除时必须清掉这 100 个块的全部派生物

漏掉 1 个块 → 用户还能搜到已删除内容
            → 在合规场景里，这就是事故
```

【推论】**新增漏了只是"少了一条"，删除漏了是"多了一条不该在的"**——**后者的性质完全不同**。

【事实】**所以删除需要一张反查表**：`doc_id → [chunk_id...]`。**这张表本身也是索引的一部分，也要维护、也要能容错**。这也是为什么"删除传播"在 study/03 里被单独列为一步。

---

### 4. 撤权：要清的地方比删除还多【推导】

【推导】**撤权时，内容没变，变的是"谁能看"**——所以要清的不只是索引：

```text
① 主索引里的元数据（ACL 字段）
② 向量索引里的对应项（如果按权限分区的话）
③ 倒排索引
④ 【缓存】——这一条最容易被漏掉
⑤ 任何派生的引用、摘要、Agent 的记忆
```

【推论】**第 ④ 条是关键**：**缓存会绕过 ACL 过滤**（[[母题-G2-向量与关键词的混合检索]] 里"权限必须在召回前生效"讲的是主链路，缓存是绕开主链路的另一条路）。

```text
如果缓存是按 query 文本做键的，那么：
  有权用户查过 → 结果进了缓存
  无权用户用同样的 query 查 → 直接命中缓存 → 拿到不该看的内容
```

【推论】**所以缓存必须按租户 / 权限分区**——**它不是优化，是权限模型的一部分。**

**到这里你应该能回答**：为什么"下次查询时 ACL 会过滤掉"这句话，挡不住缓存泄漏？

---

### 5. 新鲜度：必须可观测【事实】

【事实】study/03 的要求（这一节可以直接背）：

```text
① 文档带 effective_at、expires_at、source_version
② 索引延迟【可观测】
③ 已删除 / 过期内容可追踪传播
④ 回答【展示规则生效时间】
⑤ 冲突时优先权威级别和最新生效版本，并【显式说明】
```

【推导】**第 ② 条是最该盯的指标**：

```text
索引滞后 = 文档变更时刻 → 该内容可被检索到的时刻

如果增量任务每 5 分钟跑一次：
  平均滞后 ≈ 2.5 分钟
  最大滞后 ≈ 5 分钟（在两次跑之间提交的变更）

这个数必须是个可观测的指标，而不是"我们大概几分钟同步一次"
```

【推论】**为什么它必须是"指标"而不是"约数"**：**因为它决定"回答能不能引用刚改过的规则"**——**如果业务承诺"规则改了 10 分钟内生效"，那滞后指标超过 10 分钟就是故障。**

【取舍】**第 ④ 条第 ⑤ 条是同一个思路**：**冲突或过期时，不要偷偷选一个**——**把"这是哪一版、什么时候生效的"显式告诉用户**。这跟 [[母题-G4-引用绑定与证据可追溯]] 的"引用要能定位到版本"是同一条。

---

### 6. 双写 / 影子索引再切换【事实】

【推导】**直接原地覆盖索引有两个问题**：

```text
① 没有回滚路径（覆盖了就回不去）
② 重建期间旧索引已被破坏 → 出问题只能全量重来
```

【事实】**正确做法是双写 / 影子索引**：

```text
新建一份索引 → 双写（或先切流量的一小部分）→ 验证指标没问题 → 切换
                                                                  ↓
                                                            切错了能回滚
```

【推论】**这和 [[母题-M4-索引代价与大表变更]] 的"影子表方案（pt-osc / gh-ost）"是同一个模式**：

> **凡是要改"正在服务的派生结构"，都用"新建一份 + 双写 + 验证 + 切换"这套动作。**

**到这里你应该能回答**：为什么换 Embedding 模型必须走双写切换，而不能原地重跑？

### 7. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "删除就是把文档记录删掉" | **文档记录只是主记录，派生物散在 100 个块里**（向量 + 倒排 + 元数据）。**必须按 `doc_id` 反查全部 `chunk_id` 逐个清**——漏一个就是"已删内容还能被搜到"的合规事故 |
| "撤权了下一次查询会被 ACL 过滤掉" | **挡不住缓存**。如果缓存按 query 文本做键，有权用户查过的结果会直接命中给无权用户。**缓存必须按租户 / 权限分区**——它是权限模型的一部分，不是优化项 |
| "每天全量重建最省心" | **在数据量小、更新少时确实对**（简单性是真实收益）。但**重建一次要多久、多久要重建一次**才是判据——**100 万块每天改 1% 时，增量能省 99% 的嵌入调用** |
| "原地覆盖索引就行，反正内容一样" | **没有回滚路径**，而且重建期间旧索引已被破坏。**要新建一份 + 双写 + 验证 + 切换**——和影子表方案是同一个模式 |
| "索引滞后我们大概几分钟" | **"大概"不够**。它是个**必须可观测的指标**（变更时刻 → 可被检索时刻）。如果业务承诺"规则 10 分钟内生效"，那它超 10 分钟就是故障 |
| "旧版本新版本都一样，选一个返回就行" | **冲突时要显式说明**：优先权威级别和最新生效版本，**并把"这是哪一版、什么时候生效"告诉用户**。**偷偷选一个**会让用户以为那是唯一的答案 |
| "换 Embedding 模型只要重跑一遍" | **新旧向量不可比**（[[母题-G2-向量与关键词的混合检索]]），混在一起检索结果会错乱。**必须全量重嵌入 + 双写切换**——这意味着**换模型是一次成本很高的操作，要提前规划** |

【取舍】读成一句话：**增量省的是成本，删除与撤权保的是正确性——前者做不好是慢，后者做不好是事故。**

## 二、自测

**Q1（计算）**：某知识库有 **100 万**个块，每天约有 **1%** 的内容发生变化。

问：**全量重建和增量更新各要多少次嵌入调用？**差多少倍？

**A1**：

```text
全量重建：1,000,000 次嵌入
增量更新：1,000,000 × 1% = 10,000 次嵌入

倍数 = 100 倍
```

【结论】**增量省 99% 的嵌入调用**——在嵌入要花钱、要花时间的前提下，这是数量级的差别。

【补充】**但增量不是免费的**：它换来两个新问题——**版本管理**（哪一版索引对应哪一版源）和**一致性**（增量跑失败一半怎么办）。所以**"数据量小、更新频率低"时，全量重建反而是对的选择**：**它的简单性是真实收益**。

**Q2（计算）**：增量同步任务每 **5 分钟**跑一次。一份文档在**两次任务之间**被修改。

问：**这份文档的索引滞后最短和最长各是多少？**如果业务承诺"规则修改 10 分钟内生效"，够不够？

**A2**：

```text
最好情况：修改发生在任务开始前一刻 → 滞后 ≈ 0
最坏情况：修改发生在任务刚跑完之后 → 要等完整一轮 → 滞后 = 5 分钟
平均：   ≈ 2.5 分钟
```

【结论】**最大滞后 = 任务周期（5 分钟）**。业务承诺 10 分钟时**够用**——**因为有 2 倍余量**。

【推论】**但如果任务某次跑失败或超时，滞后就会突破 5 分钟**——所以：

```text
① 索引滞后必须是【被监控的指标】，而不是"我们大概几分钟"
② 要监控任务本身是否按时完成（失败了要告警，不能静默）
③ 承诺的时限要留余量（5 分钟周期对 10 分钟承诺 = 2 倍余量，是合理的）
```

**Q3（计算）**：一份文档切成 **100 个块**。删除时按 `doc_id` 反查并清理。

问：**如果清理逻辑漏掉了块的反查表（只删了主记录），会发生什么？**这个后果和"新增漏了一条"有什么本质区别？

**A3**：

```text
只删主记录、漏了反查表：
  → 那 100 个块还留在索引里
  → 它们仍会被检索到、仍会被引用
  → 用户能搜到【已经删除的内容】
```

【结论】**本质区别在"错误的方向"**：

| | 后果 | 性质 |
|---|---|---|
| **新增漏了** | 少了一条内容 | **功能缺失**（用户找不到） |
| **删除漏了** | **多了一条不该在的内容** | **正确性 / 合规事故**（用户看到了不该看的） |

【推论】**所以"删除传播"必须当成一条独立的、可验证的链路**——**要能回答"这份文档的 100 个块是不是都清了"，而不是"我调了删除接口"。**

【补充】这也解释了为什么 **study/03 把"删除传播"单独列为一个要测的场景**（和"跨租户、已撤权、共享链接、继承权限、缓存污染"并列）。

**Q4（纠错）**：下面这段话哪里不准确？

> "用户被撤权了没关系，下一次查询时 ACL 过滤会把他挡住的。"

**A4**：**挡不住缓存。**

1. **缓存绕过了 ACL 过滤**：如果缓存按 query 文本做键，**有权用户查过的结果会进缓存**；无权用户用同样的 query 查 → **直接命中缓存** → 拿到不该看的内容。**这条路径根本不经过 ACL 过滤。**
2. **派生物也要清**：撤权时要清的不只是主索引——**向量项、倒排项、元数据、以及任何派生的引用 / 摘要 / Agent 记忆**。
3. **所以"下一次查询会挡住"是一个不成立的假设**：它假设了所有访问都经过同一条过滤链路，而缓存不是。

【准确说法】"**缓存必须按租户 / 权限分区**——它不是优化项，**是权限模型的一部分**。撤权时要清主索引、向量、倒排、**缓存**和派生引用；而且要专门测**跨租户、已撤权、共享链接、继承权限、删除传播、缓存污染**这六类场景。"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们要换一个更好的 Embedding 模型，直接重跑一遍索引替换掉就行了。"

**A5**：三处问题。

1. **新旧向量不可比**：不同模型的向量空间完全不同，**混在同一个索引里检索结果会错乱**。所以必须**全量重嵌入**，不能增量替换。
2. **"直接替换"没有回滚路径**：重建期间旧索引已被破坏，**出问题只能全量重来**。正确做法是**新建一份索引 + 双写 + 验证 + 切换**（和 [[母题-M4-索引代价与大表变更]] 的影子表方案是同一个模式）。
3. **低估了成本**：全量重嵌入 = **一次全量的嵌入调用**（100 万块就是 100 万次），而且**切换期间要双写**。**换模型是一次成本很高的操作，要提前规划、留出双写窗口。**

【准确说法】"**换 Embedding 模型 = 全量重嵌入 + 双写切换 + 指标验证 + 可回滚**。所以 Embedding 版本必须进版本管理——**它和 Schema 版本、Prompt 版本一样，是决定输出的一部分**（[[母题-C3-Prompt版本管理与回归]]）。"

## 三、面试输出（学完再看）

**一句话结论**：**索引是派生数据，源变了它就必须变**——三种变化各自要处理：**新增 / 修改**走增量链路（只重跑变化的 1%，100 万块每天改 1% 时能省 **99%** 的嵌入调用）；**删除**最难，因为**要按 `doc_id` 反查它切出来的全部块**（一份文档 100 个块就要清 100 个），**漏一个就是"已删内容还能被搜到"的合规事故**；**撤权**要清的地方更多——**主索引、向量、倒排，以及缓存**，**因为缓存会绕过 ACL 过滤**（有权用户查过的结果会命中给无权用户），所以**缓存必须按租户 / 权限分区**。**新鲜度必须可观测**：文档带 `effective_at` / `expires_at` / `source_version`，**索引滞后**（变更时刻 → 可检索时刻）要是一个被监控的指标，回答要**展示规则生效时间**，冲突时**显式说明版本而不是偷偷选一个**。改索引结构（比如换 Embedding 模型）要走**双写 / 影子索引再切换**——**凡是要改正在服务的派生结构，都用"新建 + 双写 + 验证 + 切换"这套动作。**

**恢复关键词**：索引是派生数据 / 三种变化（新增修改 / 删除 / 撤权）/ 增量省 99% 嵌入 / **删除要按 doc_id 反查全部块**（漏一个 = 合规事故）/ **缓存绕过 ACL**，撤权要连缓存一起清 / 缓存按租户权限分区 / `effective_at` · `expires_at` · `source_version` / **索引滞后 = 变更时刻 → 可检索时刻**，要监控 / 最大滞后 = 任务周期 / 回答要展示生效时间 / 冲突时显式说明版本 / 双写 + 影子索引 + 切换（同影子表方案）/ 换 Embedding = 全量重嵌入 + 双写

**核心不变量 / 主线**：
**增量省的是成本，删除与撤权保的是正确性。**
前者做不好是"慢"，后者做不好是**事故**——所以**删除传播必须当成一条独立的、可验证的链路**，而不是"我调了删除接口"。

**完整回答骨架**：索引是派生数据（三种变化）→ 为什么值得增量（给 99% 的算式）+ 增量的代价 → **删除为什么最难**（反查表 + 漏删的性质）→ **撤权还要清缓存**（缓存绕过 ACL）→ 新鲜度可观测（滞后指标 + 展示生效时间 + 冲突显式说明）→ 双写切换模式 → 收束到"删除与撤权是正确性问题"

**追问**（先说后看）

1. **知识更新怎么做到增量且不返回失效内容？** —— **Source 事件触发增量解析与索引；新旧索引双轨验证；文档和 chunk 版本化；删除 / 撤权必须传播；回答记录知识版本；支持回滚，并监控索引滞后。** 这是 study/03 给的完整清单。
2. **删除与撤权怎么传播？缓存会不会污染？** —— **删除**：按 `doc_id` 反查全部 `chunk_id` 逐个清（向量 + 倒排 + 元数据）。**撤权**：还要清**缓存**和派生引用。**缓存会绕过 ACL 过滤**——所以**缓存按租户 / 权限分区不是优化，是权限模型的一部分**。
3. **索引滞后多少算正常？** —— **取决于业务承诺**：如果承诺"规则修改 10 分钟内生效"，那任务周期取 5 分钟（2 倍余量）就是合理的；**滞后指标超过承诺时限就是故障**。关键是**它必须是个指标，不是"大概几分钟"**。
4. **换 Embedding 模型要注意什么？** —— **新旧向量不可比，必须全量重嵌入**；**不能原地替换**（没有回滚路径），要走**双写 + 影子索引 + 验证 + 切换**；**切换期间要双写**，成本要提前规划。
5. **冲突的文档怎么处理？** —— **优先权威级别和最新生效版本，并显式说明**——**不要偷偷选一个**，否则用户会以为那是唯一的答案（[[母题-G4-引用绑定与证据可追溯]]）。

**同类变体**

- 「多租户的知识库怎么更新？」——**按租户分区**：索引分区、缓存分区、删除与撤权也要按租户生效。**跨租户的测试是必测项**（不属于"边界情况"，是"核心正确性"）。
- 「实时数据（比如设备状态）要不要进 RAG？」——**不要**。**实时事实走 Tool / 数据库，静态说明走 RAG**（EnergyOps 的做法）。**把实时数据塞进索引会同时毁掉两边**：索引追不上实时变化，而查询又会拿到过期的"事实"。
