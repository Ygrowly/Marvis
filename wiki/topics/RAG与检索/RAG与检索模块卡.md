# RAG 与检索模块卡

## 0. 模块边界（先写这个，防无限扩张）

**包含**：知识怎么进来（解析、切分、粒度、元数据、更新与删除传播）、怎么把对的证据捞回来（向量与关键词、ANN 索引、融合、权限过滤、重排）、捞回来之后怎么用与怎么证明（上下文组装、引用绑定、拒答、分层评测与失败归因）。

**明确不包含**：

- **向量库的部署运维**（集群、分片、副本、扩容）——只到"什么规模用什么索引"
- **Embedding 模型的训练与微调**——只到"维度、Dense/Sparse 的能力边界、模型版本会影响什么"
- **GraphRAG 的图谱构建细节**——只到"什么时候值得上"
- **多模态 RAG**（图片、视频检索）——只到"知道它存在，不是本模块主线"
- **具体的向量库产品横评**——只给选型判据，不给产品排名

**边界判据**：**本模块只回答"证据能不能被找回来、找回来之后能不能被证明"**。凡是"某个向量库怎么装"的，不进本卡。

## 5. 项目映射（三个简历项目逐个过）

### 5.1 数驭穹图（企业问数）· 主承载项目

- **锚点**：`projects/数驭穹图/`
- 用在哪：**把 Schema / 指标口径 / 样例查询视作不同知识类型**，关键词 + 向量混合召回表、字段和业务术语；**权限过滤先于 Schema Linking**
- 解决什么问题：**Top-K Schema 召回率 81% → 95% 的提升是靠什么拿到的？**——这条是本模块最值得在面试里讲的证据
- 踩过的坑：**砍掉的检索结果是「外置」不是「丢弃」**——大结果写 Artifact（Hot/Warm/Cold 三级生命周期），**上下文里只留口径摘要、聚合统计和 artifact_id**。需要下钻时按 id 取回。**说成「为了省 token 把数据扔了」就错了：扔的是常驻，不是数据。**
- 决策与取舍：**权限必须在检索前生效，因为「进上下文」就等于「已经泄露」**——模型说不说只是概率问题，不是控制手段；而且未授权内容还会挤占预算、可能进日志和缓存。**「让模型别说」是概率保证，「检索前过滤」才是权限控制**（[[母题-G2-向量与关键词的混合检索]] 5.1 的三条理由）。

- 对应母题：【G1】【G2】【G4】

### 5.2 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**条款按"条件 / 例外 / 生效时间"结构化切分**；召回规则后用**确定性状态模型验证**
- 解决什么问题：**冲突规则显式返回证据，不强行合成唯一答案**——这是"拒答"的正例
- 踩过的坑：**按字数切条款会把「条件」和「例外」切散**——一条规则的含义被拆到两个 chunk 里，召回任一半都不完整，模型只能猜。**语义被切碎比没召回更危险**：它给了你一个看起来有出处的错答案。
- 决策与取舍：**条款的语义边界是逻辑结构，不是长度**——按「条件 / 例外 / 生效时间」结构化切分，每个 chunk 才语义自足。**字数切分只适合叙述型文本**，对「条件-例外」型规则是破坏性的（[[母题-G1-切分策略与索引粒度]] 的「切分要按语义边界」）。

- 对应母题：【G1】【G4】

### 5.3 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**运维文档、设备数据和实时状态不混成一个索引**；实时事实走 Tool / 数据库，静态说明走 RAG
- 解决什么问题：**故障建议要引用日志 / 指标 Artifact 和操作手册**——"证据"有两种形态
- 踩过的坑：**把运维文档和设备实时状态混进同一个索引**——检索出来的「当前负荷」其实是**上次同步时的**，而模型会把它当作当下事实引用。**过期的实时数据比没有更危险**，因为它带着「这是事实」的外观。
- 决策与取舍：**证据有两种形态，不能混**——**日志/指标是运行时产生的、会变**，走 Artifact 引用（绑定运行 id）；**操作手册是静态的**，走 RAG。混在一个索引里会让「引用」失去意义：**你分不清引的是哪一次运行的日志**（[[母题-G4-引用绑定与证据可追溯]] 的可追溯性）。
- 对应母题：【G4】【G6】

## 8. 题级答案（「本主线的题」翻转卡背面 · 先说后翻）

> 题号与第 4 节题单一一对应。**必背**题写成能直接说出口的一段话；**理解 / 了解**题写 1–3 句。
> 翻转卡背面先给这道题的答案，再挂上「所属母题的完整回答（口述稿）」与单卡入口——两段合起来才是深挖。

### 1 （必背）
按链路分层答：① **切分**——按数据结构切（标题 / FAQ / 代码 / 表格各有切法），小块召回 + 父块返回（Child-Parent），或给每块补 50–100 token 定位说明再索引（Contextual Retrieval，索引只涨约 12.5%）；② **检索**——BM25 + 向量两路（盲区不重叠），向量侧用 HNSW 做 ANN，两路用 RRF 融合；③ **权限**——ACL 过滤**先于召回**，缓存按租户/权限分区；④ **重排**——交叉编码器精排（召回几百 → 重排 50–100 → 进上下文 5–20）；⑤ **生成与引用**——逐条绑定片段、可定位到版本，生成后回头验证，找不到支撑就撤稿，该拒答时拒答；⑥ **更新**——增量索引 + 删除/撤权传播 + 索引滞后可观测；⑦ **评测**——检索层（Recall@K / nDCG）与答案层（Correctness / Faithfulness / Citation completeness / Answerability）**分开**评，并保留 holdout。

### 2 （必背）
没有通用数字，要用**代表性问题集**测 Recall 与答案正确性来定。能给的是方向和判据：**太小**语义不自足（条款的例外被切走，单块意思可能是反的）；**太大**相关内容占比下降、相似度被稀释，**关键内容排不进 Top-K**（2000 字里只有 200 字相关时占比只剩 10%）。

按数据结构选：制度文档按标题层级（几百字量级）、FAQ 按问答、代码按函数边界、条款按"条件 + 例外 + 生效时间"；**表格必须表头与行绑定，不能拆掉口径**（拆开表头的行是无意义的数字）。

### 3 （必背）
因为它切的是**字符数**，不是**语义边界**。三种典型的坏：把条款的"条件"和"例外"切到两块（单块意思可能是反的）；把表格的表头和行拆开（剩下的行是无意义的数字）；把代码从函数中间切断。

而且固定字数让"块内相关占比"变得随机——大块塞进无关内容会稀释相似度，小块又丢上下文。正确做法是**按结构切 + 用评测定参数**，或者用 Child-Parent（小块召回保召回率、父块返回保完整）。

### 4 （理解）
索引时切**小块**、返回时给模型**父块**：小块保证语义集中、匹配准，父块保证喂给模型的上下文完整。解决的是"粒度两头都会坏"的矛盾——小块语义不自足，大块稀释相似度。

它改的是"**返回什么**"；Contextual Retrieval 改的是"**索引什么**"（给每块补定位说明）。**两者可以叠加**，叠加后正好覆盖"匹配准"和"信息全"两个需求。

### 5 （必背）
索引之前，先让模型给每个 chunk 补一段 **50–100 token 的定位说明**（这是哪份文档的哪一部分、在讲什么），再把"说明 + 原文"一起做嵌入和索引，**索引体积只涨约 12.5%**。

实测效果：单独用把检索失败率从 **5.7% 降到 2.9%（−49%）**，叠加重排后到 **1.88%（−67%）**。它解决的是"脱离文档的块不知道自己在说什么"——制度、条款、表格这类强依赖上下文的文档收益最大。

### 6 （必背）
**盲区不重叠，所以企业知识库通常两路都要**。BM25 强在专有名词、编号、精确短语（搜 `SLB-20250101-abc` 这种 trace ID，**Embedding 无能为力**）；向量强在语义改写真（搜"数据库连接池"能命中"DB connection pool 配置"）。

判据是**按查询类型分桶评测**：把问题集按类型分桶，看哪一路在哪个桶上赢，再由数据决定配比与融合方式。**选择由数据决定，不由偏好决定。**

### 7 （理解）
**默认余弦**——模型训练时通常就是按余弦（或归一化后的点积）优化的。三者的关系：向量**归一化之后**，余弦、点积、欧氏距离的**排序完全等价**（`‖a−b‖² = 2 − 2·cos`）；只有在**未归一化且要区分模长**时，点积才会给出不同排序。

实践结论：统一归一化 + 余弦；另外**维度由 Embedding 模型决定，换模型必须重建索引**。

### 8 （必背）
精确 KNN 要对全量算相似度，复杂度 **O(N×D)**：100 万 × 1536 维 = 15.36 亿次运算 ≈ **1.5 秒/次**，在线服务用不起，所以必须 **ANN**。

选索引按规模：**百万级以内 HNSW**（精度和速度平衡最好、生态成熟，ES / Faiss / Milvus 都默认支持）；**千万级 IVF**；**亿级 DiskANN 或分片**。代价是拿少量召回率换两个数量级的延迟。

### 9 （理解）
两件事叠加：**分层**给出对数级的搜索路径（100 万节点约 5–6 层，从最高层开始、走不动就下层）；**图上贪心导航**让每层只需和局部邻居比较。本质上是"**跳表的分层思想 + 图的近邻连接**"。

代价：构图时间与内存（邻居表）、以及它是**近似**的——召回率靠检索时的候选队列参数调。

### 10 （必背）
RRF（Reciprocal Rank Fusion）= 对每路结果的排名 r 取 `1/(k + r)` 再求和（k 常取 60）。

**为什么不直接加分数：两路分数量纲不可比**——余弦 ∈ [0,1]，BM25 无上界且随词频/文档长度浮动，直接相加等于让量纲大的那一路说了算；用排名就把这个变量消掉了。

k 的作用是**平滑高排名的差距**：k 越大，第 1 名和第 2 名的贡献差越小（`1/(k+1)` vs `1/(k+2)`）；k 太小会让"某一路单独第一"过于强势。

### 11 （必背）
**必须在检索层、先于召回**（ACL pre-filter），不能等召回到答案之后再过滤。五条：① 身份进入检索层、ACL 过滤先于召回；② **缓存按租户 / 权限分区**——缓存会绕过 ACL（有权用户查过的结果会命中给无权用户），所以分区不是优化，是**权限模型的一部分**；③ 引用和下载**再次鉴权**；④ 做**跨租户与撤权测试**；⑤ 日志避免记录敏感原文。

### 12 （必背）
收益要说清口径：Contextual Retrieval 的实验里，重排把检索失败率从 2.9% 降到 1.88%——**相对重排前降 35%，相对基线累计降 67%**，这两个数不能混。

代价是**延迟随候选数线性增长**（5 ms × N，重排 200 条就是 1 秒，比 ANN 召回慢两个数量级），所以常见折中是"召回几百 → 重排 50–100 → 进上下文 5–20"。而且**不一定值得**：精确编号、单跳事实这类查询召回本身已经排得很准，重排收益很小，**应通过 Eval 判断是否只在难题启用**。

原理：双塔把 query 和 doc 分别编码、编码时看不到对方，"除外""不适用"这类否定词被平均掉（结构性损失，换更大的双塔也补不回来）；交叉编码器把两者拼在一起，能看到逐词交互。

### 13 （理解）
**Recall@K**：正确证据有没有进前 K——回答"捞没捞到"，不关心顺序；**MRR**：第一个正确结果平均排在第几——回答"第一个对的来得多快"，适合单答案场景；**nDCG@K**：前 K 的排序质量——回答"排得准不准"，且支持分级相关性。

RAG 里检索层主要看 **Recall@K 和 nDCG@K**：召回阶段的目标是"不漏"，排序质量交给重排解决。

### 14 （必背）
按三个岔路口走：① 正确证据**进 TopK 了吗**（没进 → 召回问题）；② 进了 TopK 但**进最终 Context 了吗**（没进 → 重排 / 预算 / 去重 / 截断问题）；③ 都进了还是错 → **生成 / Prompt / 引用**问题。

前提是 **Trace 把候选、分数、重排位置、上下文版本都留下来了**，否则只能猜。另外要记住两层的损失是**相乘**的（Recall@20 95% × faithfulness 90% = 端到端上限 85.5%），所以端到端指标一定低于任何单层。

### 15 （必背）
三个动作：① **逐条绑定**——每句结论绑到具体片段，可定位到文档 / 章节 / **版本**；计算类结论还要绑定 SQL 或工具运行 ID，让用户能重跑；② **生成后回头验证**——把每条结论回原文找支撑，**找不到的直接撤掉**，因为"要求模型给引用"改的是概率，模型完全可以编一个看起来像引用的东西，**验证才是机制**；③ 代价要算——逐条验证让 token 成本接近翻倍（10 条结论约 8,500 token vs 生成 4,500 token），所以**只对高风险结论做**（金额、权限、生效时间）。

粗引用（文末列链接）的问题：把校验成本全推给读者，用户只能全信或全不信。

### 16 （必背）
五条：**没有召回足够证据**、**多个权威来源冲突**、**用户身份不足**、**超出知识库边界**、**时间 / 主体 / 口径不明确**。冲突时**不强行合成唯一答案**，而是显式返回证据（RuleArena 的做法）。

为什么拒答是设计的一部分：把"自信的错误"（代价 10 单位）换成"坦白的不知道"（1 单位），**总代价降到 1/10**——错误越贵，拒答越值钱。

### 17 （必背）
因为它们回答两个不同的问题——"证据有没有捞到" vs "答案对不对、有没有依据"，**混成一个数就两个都答不了**；分开之后才能算"提升哪一层更划算"。检索层看 Recall@K / nDCG@K；答案层看 Correctness / Faithfulness / Citation completeness / Answerability。

还有一条：**归因决定修复上限**——100 条失败里召回占 40、排序占 25、生成占 35，只换更强的模型最多修 35%。评测集要保留 holdout（真实案例：训练集打平、held-out 差 11.9 个点），规模按 `SE = √(p(1−p)/n)` 定：150 条约 ±3.4%，想分辨 2 个百分点需要约 900 条。

### 18 （理解）
因为**失败发生在三个不同地方**：① 证据没被捞到（召回）；② 捞到了没进上下文（重排 / 预算）；③ 进了还是答错（生成）。

检索失败率只覆盖①，而幻觉率主要是③的问题——证据就在上下文里，模型还是答错了或编了个引用。两者是**相乘关系**而不是同一个数（Recall 95% × faithfulness 90% = 端到端上限 85.5%），所以用检索指标冒充答案质量，会系统性地高估系统。

### 19 （必背）
六件套：**Source 事件触发增量解析与索引**（只重跑变化的 1%，100 万块每天改 1% 时省 **99%** 的嵌入调用）；**新旧索引双轨验证**；**文档和 chunk 版本化**；**删除 / 撤权必须传播**；**回答记录知识版本**；**支持回滚 + 监控索引滞后**。

文档要带 `effective_at` / `expires_at` / `source_version`，回答要展示规则生效时间，冲突时**显式说明版本而不是偷偷选一个**。索引滞后（变更时刻 → 可检索时刻）必须是一个被监控的指标，超过承诺时限就是故障。

### 20 （理解）
**删除最难**：要按 `doc_id` 反查它切出来的**全部块**逐个清（一份文档 100 个块就要清 100 个，漏一个就是"已删内容还能被搜到"的合规事故），而且**向量、倒排、元数据三处都要清**。

**撤权要清的地方更多**：主索引、向量、倒排，**还有缓存**——缓存会绕过 ACL 过滤（有权用户查过的结果会命中给无权用户），所以缓存按租户 / 权限分区不是优化，是权限模型的一部分。

换 Embedding 模型时：新旧向量不可比，必须全量重嵌入，且**不能原地替换**（没有回滚路径），要走**双写 + 影子索引 + 验证 + 切换**。

### 21 （理解）
**最新 / 私有 / 需要可引用的知识 → RAG**；**稳定的行为、格式、领域表达 → 可能微调**；**小而稳定的知识 → 长上下文可能更简单**（数据小、稳定、无权限差异、不需要溯源时，直接放长上下文更简单也可能更好）。

通常的顺序是：**先用 Prompt / RAG 建 Eval，再判断是否微调**——没有 Eval 就没法证明微调带来多少增益。决策由质量、成本、延迟、权限的评测驱动，不由架构偏好驱动。

### 22 （了解）
当问题必须靠**实体之间的关系**才能回答时（"A 公司的供应商里哪些同时是 B 的客户"这类多跳关联），纯向量检索拿不到这种结构信息，GraphRAG 才有增量。

代价是**构建与维护成本高**（抽实体、建图、图更新），而且它通常不是替代原有链路，而是作为**一路召回叠加**。所以判据是：先证明你的问题集里有相当比例是"关系型"的，再上；否则不值得。

### 23 （必背）
五条：① **身份进入检索层、ACL filter 先于召回**；② **缓存按租户 / 权限分区**（缓存会绕过 ACL）；③ **引用和下载再次鉴权**；④ 做**跨租户与撤权测试**（这两类测试是 RAG 特有的）；⑤ **日志避免记录敏感原文**。

再加一条工程习惯：评测集里要专门放**权限攻击样本**，否则你永远不知道越权到底有没有被拦住。

### 24 （理解）
**重排解决不了**——重排只是把已有候选重新排序，而多跳需要的候选**压根不在池子里**。

两条路：**Query Decomposition**（把一个多条件问题拆成多个子查询分别检索再合成）和 **Multi-hop 检索**（第二轮检索由第一轮发现的实体驱动——先检索"某公司 CEO"，再用找到的人名检索"母校"）。

本质上**这不是检索算法的问题，是查询规划的问题**。
