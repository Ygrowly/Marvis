**题目**：面试官问——"你们的 RAG 是怎么切块的？切多大？为什么是这么大？"

**母题**：**把文档切成检索单元时，粒度该多大——为什么这个问题无论怎么答都会被追问？**

**为什么重要**：这道题几乎每场 RAG 面试都会问，而且它是**最容易暴露"照搬经验数值"的一题**——答"我们切 500 字"和答"我们用小块召回 + 父块返回，因为这两个需求互相矛盾"是两个档次。**它也是唯一一个"在离线阶段就能决定线上质量上限"的环节**：切坏了，后面的重排和生成再强也救不回来。

---

## 一、教材

### 1. 前提：检索单元必须同时满足两个互相矛盾的需求

【推导】把"一块文档"当成检索单元，它要同时做到：

```text
① 能被准确匹配到  → 要求块里mostly 是相关内容
                     → 块越小越好（相关内容占比高，相似度信号强）

② 能被模型直接使用 → 要求块语义自足
                     → 块越大越好（前因后果、例外条件都在里面）
```

【推论】**这两个需求方向相反，所以"切多大"这个问题的正确答案不是某个数字，而是"承认它们矛盾、然后想办法解耦"。**

::figure chunk-granularity.svg | 切块粒度的两端都会坏，解耦才是解 | 太小则语义不完整、太大则相似度稀释；解耦用小块召回保召回率、父块返回保上下文完整；右侧是 Contextual Retrieval 的实测降幅

**到这里你应该能回答**：为什么"我们切 500 字"这种回答一定会被追问"为什么是 500"？

---

### 2. 两端各坏在哪

#### 2.1 太小：语义不完整【推导】

```text
一份退款规则切成「条件」「例外」「生效时间」三块

用户问：「7 天无理由退款适用哪些情况？」
召回命中「条件」那一块：「购买后 7 天内可无理由退款」
→ 模型照此回答

但「例外」块里写着：「拆封的数码产品除外」
→ 这一块没被召回，答案就是错的
```

【推论】**单个块的意思甚至可能是反的。** 小块的"高召回率"只说明**它容易被匹配到**，不说明**它能独立支撑一个答案**。

【事实】另外两个代价：**块数暴涨**（索引与检索成本上升）、**重叠切分时重复召回**（挤占上下文预算）。

#### 2.2 太大：相似度被稀释【推导】

```text
一段 2000 字的文档，其中只有 200 字与问题相关
  相关内容占比 = 200 / 2000 = 10%

如果整篇作为一个块：
  它的向量是整篇内容的「平均表示」
  → 与 query 的相似度被另外 90% 的无关内容拉低
  → 在 Top-K 排序里排不过那些「占比高」的小块
```

【推论】**块越大，单块的相似度信号越弱**——关键内容不是"没被切到"，是**被淹没在噪声里排不进 Top-K**。

【取舍】**这是"块大小"这个数字真正的含义**：它调节的是**"相关内容在块里的占比"**。500 字对制度文档可能合适，对表格或代码就是灾难——**因为它不取决于文档长度，取决于"相关内容通常有多长"**。

**到这里你应该能回答**：为什么"块大小"不能用文档平均长度来定？

---

### 3. 候选方案一：解耦——小块召回、大块返回【事实】

```text
索引时：把文档切成【小块】（child），每块记住自己的【父块】（parent / 整节 / 整篇）
检索时：用【小块】去匹配          → 粒度细，召回率高
返回时：把【父块】塞给模型        → 上下文完整，模型能理解全貌
```

【事实】得物那篇文章把它叫 **Child-Parent**，总结成一句很准的话：

> **"检索时用 Child 去搜——小块粒度细，召回率高；返回时把 Parent 塞给 LLM——大块上下文完整，LLM 能理解全貌。兼顾了召回率和上下文完整性。"**

【推论】**这个方案的通用价值在于：它把"检索用的表示"和"喂给模型的表示"拆成了两份。** 只要这两者可以不同，矛盾就消失了——**这也是后面所有 RAG 优化的同一个套路**（重排用小块、生成用大块；索引用补过上下文的块、展示用原文）。

---

### 4. 候选方案二：不改粒度，改"块自己知不知道自己在说什么"

【事实】**Contextual Retrieval** 的做法：切块之后，**先让模型给每块补一句"它在全文里是什么位置、指代谁"**（约 **50–100 token**），再把**补过上下文的块**拿去做向量和 BM25 索引。

原文给的例子：

```text
原始块：  "The company's revenue grew by 3% over the previous quarter."
          （哪家公司？哪个季度？单看这块无从判断 → 检不到）

补上下文："This chunk is from an SEC filing on ACME corp's performance in Q2 2023;
          the previous quarter's revenue was $314 million.
          The company's revenue grew by 3% over the previous quarter."
```

#### 4.1 收益与成本都能算【推导】

**收益**（实测的平均检索失败率，top-20 口径）：

```text
基线                              5.7%
+ Contextual Embeddings           3.7%   （−35%）
+ Contextual BM25                 2.9%   （−49%）
+ 再叠加 Rerank                   1.88%  （−67%）
```

换算成"每 1000 次查询失败几次"更直观：**57 次 → 37 次 → 29 次 → 19 次**。

**成本**：

```text
每个块多 50–100 token 的上下文
若块本身 800 token，加上 100 token 上下文：
  索引体积增加 100 / 800 = 12.5%
```

【结论】**用约 12.5% 的索引体积，换 49% 的检索失败率下降。** 这笔账很划算，而且它**不需要改切分策略**——是在现有切法上加一层。

【事实】**一次性成本**：Anthropic 给过一个测算——**用 prompt caching 做上下文增强，一次性成本约 $1.02 每百万文档 token**（前提是缓存复用参考文档，否则要为每个块都重传全文）。

**到这里你应该能回答**：Contextual Retrieval 和 Child-Parent 是两种什么思路？（一个改"返回什么"，一个改"索引什么"）

### 5. 三种切分策略的适用【事实】

| 数据 | 首选策略 | 为什么 |
|---|---|---|
| **Markdown / 制度文档** | 标题层级 + 段落，**保存父子关系** | 标题本身就是语义边界 |
| **FAQ** | **一个问答为基本单元** | 天然自足，不需要再切 |
| **代码** | 函数 / 类 / 模块边界 + 符号信息 | 半个函数无法被理解 |
| **表格** | **表头与行 / 分组绑定**，不拆掉口径 | 拆开表头的行是"无意义的数字" |
| **长报告** | **小块召回 + parent 扩展** | 典型的 Child-Parent 场景 |
| **规则条款** | **条款 / 条件 / 例外 / 生效时间结构化** | 例外与条件必须同行，否则意思会反 |

【取舍】**得物文章里的一句总结可以当通用判据**：

> **"Chunk 参数必须通过目标问题集评测，而不是照搬经验数值。"**

【推论】**这句话的落点是：切分策略的唯一验收标准是"在你的目标问题上召回率是多少"**，而不是"是否符合某个最佳实践"。**所以切分是一个需要 Eval 才能定的事**（[[母题-G5-RAG评测与幻觉率]]）。

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "固定切 500 字是行业标准" | **没有这个标准**。块大小调节的是"**相关内容在块里的占比**"，所以它取决于**你的文档里相关内容通常多长**，而不是一个全局数字。对表格和代码，固定字数切块是灾难 |
| "块越小召回率越高，所以越小越好" | **召回率高 ≠ 答案对**。块太小会让语义不自足（例外的条款被切走，单个块的意思可能是反的），而且块数暴涨、重复召回挤占预算。**正解是解耦，不是把块切小** |
| "Child-Parent 就是把块切小一点" | **不是**。它是**把"检索用的表示"和"喂给模型的表示"拆成两份**——这个概念可以推广到重排（重排用小块、生成用大块）和索引（索引用补过上下文的块） |
| "Contextual Retrieval 要重做切分" | **不用**。它是在现有切法上**加一层预处理**：切完再给每块补 50–100 token 的定位说明。**收益 49%，索引只涨约 12.5%** |
| "切分是一次性的离线工作" | 它**和更新绑在一起**：文档改了要重切、重嵌入。所以切分粒度的选择会直接影响增量更新的成本（[[母题-G6-知识更新与增量索引]]） |
| "切分没什么可优化的，重点是模型" | **反了**。切分决定的是**召回的质量上限**——**块没被召回，后面多强的模型都看不到它** |

【取舍】读成一句话：**"切多大"没有正确答案，只有"辨认出两个矛盾的需求，然后把它们在系统里拆开"——这才是这道题真正在考的东西。**

## 二、自测

**Q1（计算）**：一段 **2000 字**的文档，其中只有 **200 字**与用户问题相关。

问：**如果整篇作为一个块，相关内容的占比是多少？**这个占比会怎样影响它被召回的概率？如果切成 20 个 100 字的块、那 200 字正好落在 2 块里，这 2 块的占比是多少？

**A1**：

```text
整篇一个块：
  相关内容占比 = 200 / 2000 = 10%
  块向量是整篇内容的「平均表示」
  → 与 query 的相似度被另外 90% 的无关内容拉低
  → 在 Top-K 里排不过占比高的小块

切成 20 个 100 字的块：
  那 200 字落在 2 块里，每块 100 字且全部相关
  占比 = 100%  → 相似度信号最强
```

【结论】**这就是"块太大"的真实机制**：关键内容不是"没被切到"，是**被稀释到排不进 Top-K**。

【补充】这个例子也解释了**为什么"块大小"不能脱离内容来定**：块大小调节的是"**相关内容在块里的占比**"，而"相关内容通常多长"取决于文档类型——制度文档的一段可能 300 字，表格的一行可能 20 字。

**Q2（计算）**：某 RAG 系统的检索失败率基线是 **5.7%**（top-20 口径）。依次加上三种手段。

问：**每 1000 次查询的失败次数分别是多少？**每次相对基线的降幅是多少？

**A2**：

| 配置 | 失败率 | 每 1000 次失败 | 相对基线降幅 |
|---|---|---|---|
| 基线 | 5.7% | **57 次** | — |
| + Contextual Embeddings | 3.7% | **37 次** | −35% |
| + Contextual BM25 | 2.9% | **29 次** | −49% |
| + Rerank | 1.88% | **19 次** | −67% |

【结论】**三种手段是叠加的**，而且每一层治的东西不同：

- **Contextual Embeddings**：让"语义检索"能认出指代（治的是**块不知道自己在说什么**）
- **Contextual BM25**：让"关键词检索"也能用上补的上下文（治的是**精确匹配也缺上下文**）
- **Rerank**：把已经召回的候选重新排序（治的是**排序不够准**，[[母题-G3-重排与召回质量]]）

【补充】把它换算成"每 1000 次失败几次"而不是百分比，**在汇报时更有说服力**——因为它直接对应"会有多少次需要人工兜底"。

**Q3（计算）**：Contextual Retrieval 给每个块补约 **100 token** 的上下文。假设块本身是 **800 token**。

问：**索引体积增加多少？**这笔投入换来的收益是多少？如果块本身只有 200 token 呢？

**A3**：

```text
块 800 token + 上下文 100 token：
  索引体积增加 = 100 / 800 = 12.5%
  换来失败率下降 49%（Q2）

块 200 token + 上下文 100 token：
  索引体积增加 = 100 / 200 = 50%
  同样换来失败率下降 49%
```

【结论】**块越小，Contextual Retrieval 的相对成本越高。** 800 token 的块只涨 12.5%，200 token 的块要涨 50%——**收益一样，成本差 4 倍。**

【推论】**这是"切分策略"和"上下文增强"之间的一个真实耦合**：如果你把块切得很小（为了召回率），再上 Contextual Retrieval 就不太划算了。**两个决策要一起考虑，不能分开选。**

【事实】**一次性成本**：Anthropic 给的测算是**约 $1.02 每百万文档 token**——前提是**用 prompt caching 复用参考文档**，否则要为每个块都重传全文，成本会高一个数量级。

**Q4（纠错）**：下面这段话哪里不准确？

> "我们把文档统一切成 500 字一块，这是业界标准做法。"

**A4**：三处问题。

1. **不存在"500 字"这个业界标准**。块大小调节的是"**相关内容在块里的占比**"，所以它取决于**你的文档里相关内容通常多长**——制度文档的一段可能 300 字，表格的一行可能 20 字。
2. **对结构化内容，固定字数切块会破坏语义**：表格拆开表头就变成"无意义的数字"；条款把"例外"切到相邻块，**单块的意思可能是反的**。
3. **"切多大"没有普适答案，只有评测答案**：得物文章的结论就是"**Chunk 参数必须通过目标问题集评测，而不是照搬经验数值**"。

【准确说法】"先看**数据结构和问题粒度**（标题 / 条款 / 表格 / 代码优先），再用**代表性问题集**比较 Recall、答案正确性、Token 和 P95 延迟。**必要时用小块召回 + 父块扩展**——**把'检索的单位'和'喂给模型的单位'拆开**。"

**Q5（纠错）**：下面这段话哪里不准确？

> "既然小块召回率高，那我们就把块切得尽量小，这样召回肯定最好。"

**A5**：**"召回率高"和"答案对"是两件事。**

1. **语义不自足**：块太小会把"条件 / 例外 / 生效时间"拆散。**单个块可能被召回、但它的意思是残缺甚至相反的**（Q1 的退款规则例子）——**召回率指标看不出来这个问题**（它只关心"相关文档有没有进 Top-K"，不关心"进了之后够不够用"）。
2. **块数暴涨**：索引体积、检索开销、存储都上升。
3. **重复召回挤占预算**：重叠切分时同一个内容会被多块召回，**在有限的上下文预算里挤掉真正需要的内容**（[[母题-C1-上下文组装与窗口预算]]）。

【准确说法】"**正解是解耦，不是把块切小**：用**小块**去匹配（拿召回率），用**父块 / 整节**返回给模型（拿上下文完整）。**如果非要选一个粒度，那也要用评测来定**，而不是取极值。"

## 三、面试输出（学完再看）

**一句话结论**：切块粒度是一个**两头都会坏**的问题——**太小**语义不自足（条款的例外被切走，单块意思可能是反的）；**太大**相关内容占比下降、相似度被稀释，**关键内容排不进 Top-K**（2000 字里只有 200 字相关时占比只剩 10%）。所以答案不是某个数字，而是**把两个矛盾的需拆开**：**小块召回（保召回率）+ 父块返回（保上下文完整）**——这就是 Child-Parent。另一种思路是**不改粒度、改信息**：**Contextual Retrieval** 先给每块补 50–100 token 的定位说明再做索引，索引只涨约 **12.5%**，实测把检索失败率从 **5.7% 降到 2.9%（−49%）**，再叠加重排是 **1.88%（−67%）**。**切分策略必须按数据结构选**（标题 / FAQ / 代码 / 表格 / 条款各有首选），**并用目标问题集评测来定参数，不能照搬经验值。**

**恢复关键词**：两个矛盾需求（匹配准 vs 语义自足）/ 太大的机制是**稀释**（占比 10%）/ 太小的机制是**语义不自足**（例外被切走）/ **Child-Parent = 小块召回 + 父块返回** / 解耦可以推广（重排用小块、索引用补上下文的块）/ Contextual Retrieval：+50–100 token 定位说明，索引 +12.5% / 失败率 5.7% → 3.7% → 2.9% → 1.88% / 块越小，上下文增强的相对成本越高（200 token 时涨 50%）/ 切分按数据结构选，参数靠评测定

**核心不变量 / 主线**：
**"检索用的表示"和"喂给模型的表示"，不必是同一个东西。**
一旦这条被认出来，切分粒度的矛盾就消失了——**后面所有 RAG 优化用的都是同一个套路**（重排用小块、生成用大块；索引用补过上下文的块、展示用原文）。

**完整回答骨架**：先说两个矛盾需求 → 两端各坏在哪（各给一个机制）→ **解耦方案（Child-Parent）** → 另一种思路（Contextual Retrieval，给收益与成本的数）→ 按数据结构选策略 → 参数必须靠评测定 → 收束到"拆开两种表示"

**完整回答（口述稿）**：
切块粒度是一个**两头都会坏**的问题：**太小**语义不自足（条款的例外被切走，单块意思可能是反的）；**太大**相关内容占比下降、相似度被稀释，**关键内容排不进 Top-K**（2000 字里只有 200 字相关时占比只剩 10%）。所以答案不是某个数字，而是**把两个矛盾的需求拆开**。

两条思路：**Child-Parent**（**小块召回保召回率 + 父块返回保上下文完整**）改的是"返回什么"；**Contextual Retrieval**（先给每块补 **50–100 token 的定位说明**再做索引）改的是"索引什么"，索引只涨约 **12.5%**，实测把检索失败率从 **5.7% 降到 2.9%（−49%）**，再叠加重排是 **1.88%（−67%）**。两者可以叠加。

切分策略必须**按数据结构选**：制度文档按标题层级（几百字量级）、FAQ 按问答、代码按函数边界、条款按"条件 + 例外 + 生效时间"；**表格必须表头与行绑定，不能拆掉口径**（拆开表头的行是无意义的数字，指标表/口径表尤其明显）。参数要用**目标问题集评测**来定，不能照搬经验值。

**分层要点**：
- **结论**：粒度两头都会坏；小块召回 + 父块返回（Child-Parent）或补定位说明再索引（Contextual Retrieval）。
- **推导链**：太小→语义不自足；太大→相似度稀释、排不进 Top-K → 拆成"召回准"与"信息全" → 改返回 vs 改索引。
- **量化**：2000 字里 200 字相关 → 占比只剩 10%；Contextual Retrieval 索引涨约 12.5%，失败率 5.7% → 2.9%（−49%），叠重排 → 1.88%（−67%）。
- **边界与常见误解**：固定字数切块切的是字符数不是语义边界；表格拆掉表头是常见的坏切法；"多长的块最合适"没有通用答案，只能评测定。

**追问**（先说后看）

1. **Child-Parent 和 Contextual Retrieval 有什么区别？** —— **一个改"返回什么"，一个改"索引什么"**。Child-Parent 索引小块、返回父块；Contextual Retrieval 索引的是"补了定位说明的块"。**两者可以叠加**，而且叠加后正好覆盖了"匹配准"和"信息全"两个需求。
2. **表格怎么切？** —— **表头与行 / 分组绑定，不能拆掉口径**。拆开表头的行是"无意义的数字"——这在企业知识库里是最常见的坏切法之一（指标表、口径表尤其明显）。
3. **多长的块最合适？** —— **没有通用答案**。要先用代表性问题集测 Recall 与答案正确性。**能给的经验只有方向**：制度文档按标题层级（几百字量级）、FAQ 按问答、代码按函数边界、条款按"条件+例外+生效时间"。
4. **RAG、微调、长上下文怎么选？** —— **最新 / 私有 / 可引用的知识 → RAG**；**稳定的行为、格式、领域表达 → 可能微调**；**小而稳定的知识 → 长上下文可能更简单**。通常**先用 Prompt / RAG 建 Eval，再判断是否微调**。

**同类变体**

- 「小块召回父块返回，和"检索后扩展上下文窗口"有什么区别？」——**前者扩的是"同一文档内的父级"（结构关系），后者扩的是"相邻块"（位置关系）**。前者更准（父块是语义边界），后者更便宜（不需要维护父子关系）。
- 「代码库怎么做 RAG？」——**按函数 / 类 / 模块边界切 + 带上符号信息**（函数签名、所在文件路径、被谁调用）。**半个函数无法被理解**，而符号信息相当于代码版的"Contextual Retrieval"。
