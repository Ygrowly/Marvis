**母题**：什么数据该放缓存、什么不该，边界是怎么划出来的。

## 一、教材

### 1. 前提："缓存"这个词掩盖了两类东西

#### 1.1 派生数据 vs 权威状态【事实】

【推导】**"要不要加缓存"这个问题问错了**。正确的问法是：**这份数据的"权威来源"在哪？**

| | **派生数据**（可以缓存） | **权威状态**（不该只放缓存） |
|---|---|---|
| 定义 | **能从权威来源重新算/重新查出来的** | **丢了就真的没了，它就是事实本身** |
| 例子 | 榜单、统计结果、列表页、配置副本、搜索结果 | 订单、账本、库存、余额、状态机当前状态 |
| 丢了怎么办 | **重建**（慢一点，但正确） | **不可恢复**（或要人工核对） |
| 缓存挂了的影响 | 变慢 | **可能读错、写错** |

【推导】**关键区别在"它参不参与判断"**：

```
只用来【展示】的数据（榜单、详情页）→ 旧一点无所谓 → 可以缓存
用来【做决定】的数据（余额够不够、库存还有没有、状态能不能流转）
  → 旧值会导致【错误的决定】→ 不能只靠缓存
```

#### 1.2 判据：三问【推导】

【推导】**任何一份数据要不要进缓存，问三个问题就够**：

| # | 问题 | 答"是"才适合缓存 |
|---|---|---|
| **①** | **丢了能不能重建？** | 能（有权威来源） |
| **②** | **旧一段时间能忍吗？能忍多久？** | 能，且能给出具体秒数 |
| **③** | **会不会因为读到旧值而做错事？** | 不会 |

【推导】**三问里有任何一问不过，就不是"缓存策略该怎么调"的问题，而是"放错地方了"**：

```
①不过（是唯一一份）      → 它是权威状态，应该留在数据库里
②不过（完全不能旧）      → 只能读权威来源（或接受强一致的方案）
③不过（旧值会做错事）    → 同上 —— 这是最容易被忽略、也最危险的一问
```

**到这里你应该能回答**：为什么"余额"和"排行榜"虽然都是"用 Redis 存的数据"，但它们的性质完全不同？

### 2. 放错的代价：从"慢"升级成"错"

#### 2.1 典型的三类放错【事实】

【推导】**按"后果严重程度"排**：

| 类型 | 例子 | 后果 | 为什么 |
|---|---|---|---|
| **① 权威状态只放缓存** | 订单状态 / 账本 / 唯一一份配置 | **数据丢失** | Redis 的持久化是"尽力而为"（[[母题-R2-持久化与内存淘汰]]），**不能当唯一存储** |
| **② 参与判断的数据带旧值** | 余额、库存、状态机状态 | **业务错误**（超卖、状态乱跳） | 判断发生在应用层，**应用层相信了一个旧值** |
| **③ 大量冷数据 / 大对象** | 全量用户信息、整篇文档塞一个 String | **内存被打爆、淘汰把热数据挤出去** | 命中率极低却占着内存（[[母题-R4-大key与热key]]） |
| **④ 能本地算出来的东西** | 用 Redis 存"列表页的排序结果"，而排序本身很便宜 | **多了一个故障点，收益接近零** | 引入缓存的收益必须 > 它带来的可用性风险 |

【推导】**第 ② 类最难发现，因为它在低并发下完全正常**：

```
缓存里余额 = 100（TTL 60 秒）
用户在 60 秒窗口里扣了 90（数据库余额变成 10）
缓存还没过期 → 用户再读，看到 100 → 以为还能扣 → 下单
→ 数据库扣款失败（余额不足）
→ 【用户看到"我明明有钱"】
```

**这就是"缓存不一致"从"慢"变成"错"的那一刻**——**同一个不一致，用在展示上是"旧了 60 秒"，用在判断上是"业务做错了"。**

#### 2.2 缓存不可用：回源放大【推导】

【推导】**这是必须先算清楚的数**（自测 Q1）：

```
回源请求量 = 总请求 × (1 − 命中率)
回源放大倍数 = 1 / (1 − 命中率)
```

| 命中率 h | 正常回源 | **缓存全挂时回源** | 放大倍数 |
|---|---|---|---|
| 99% | 1% | 100% | **100 倍** |
| 95% | 5% | 100% | **20 倍** |
| 90% | 10% | 100% | **10 倍** |
| 50% | 50% | 100% | **2 倍** |

【推导】**这张表解释了"为什么缓存挂了等于数据库挂了"**：

- **命中率越高，缓存的价值越大，但它挂掉时的冲击也越大**
- 命中率 95% 的缓存挂掉 → **数据库要扛原来 20 倍的流量** → 大概率打穿
- **而"打穿"的标志是：数据库因为慢查询排队，响应变慢 → 上游重试 → 流量再翻倍**

【取舍】**所以"缓存挂了怎么办"必须提前设计**，三档：

| 档 | 做法 | 代价 |
|---|---|---|
| **限流** | 直接把入口流量压到数据库能扛的量（拒绝一部分请求） | **有损**：部分用户被拒 |
| **降级** | 返回兜底数据（默认值 / 上一次成功的快照 / 静态页） | **数据可能不准**，但服务活着 |
| **本地缓存兜底** | 实例内的本地缓存还能顶一会儿 | **最长顶一个 TTL**，且不适用于"写" |
| **不降级（fail open）** | 直接放行到数据库 | **通常就是压垮数据库的那个选项** |

【事实】**EnergyOps 与 RuleArena 的做法值得对照**：**权威状态全部落在 PostgreSQL，Redis 只承担队列、限流与短期进度**（`RuleArena 06`、`08`）——**这样"Redis 挂了"的影响是"任务排队变慢"，而不是"数据读错"**。**这是"把缓存放在不影响正确性的位置上"最直接的示范。**

**到这里你应该能回答**：为什么"缓存挂了大不了回源"这句话在命中率高的时候特别危险？

### 3. 一致性这件事，先说清"上限"再谈方案

#### 3.1 TTL 是"最多旧多久"，不是"不会不一致"【推导】

【推导】**缓存的一致性问题分两种时机，各自的上限不同**：

| 更新时机 | 不一致的上限 | 代价 |
|---|---|---|
| **只靠 TTL** | **最多旧一个 TTL**（比如 60 秒） | 极简单；但 60 秒内可能读到旧值 |
| **写时失效**（写完删缓存） | **旧到下一次读把它重建为止**（通常毫秒级） | 要处理"删缓存失败"（[[母题-R3-缓存一致性与三类事故]]） |
| **写时更新 + 双删** | 同上，且窗口更小 | 复杂度上升 |
| **不用缓存** | **0**（但读压力全在数据库） | 性能 |

【推导】**所以一致性的选择是一个"能容忍多久"的问题，而不是"有没有问题"的问题**：

```
能容忍 60 秒旧值       → 只配 TTL，最简单
能容忍几百毫秒旧值     → 写时删缓存 + TTL 兜底
一毫秒都不能旧         → 这份数据【不该进缓存】，或者要上"强一致"的读路径
```

【事实】**EnergyOps 里有一个必须讲清的点**：**"数据库提交"与"Redis 删除"无法组成一个普通的数据库事务**——所以它**不用"假装同一个事务"，而是用 Outbox（失效消息与业务同事务落库，再由 Worker 执行删除）**（`02-aggregation-and-recovery.md`、`03-query-and-performance.md`）。**这说明：缓存一致性最终是"最终一致"，不是"强一致"。**

#### 3.2 权威状态放在哪，决定了整个架构的骨架【取舍】

【推导】**RuleArena 的架构选择可以当成模板**：

```
PostgreSQL = 权威状态（唯一事实来源）
Redis      = 队列、限流、短期进度（都可以丢、可以重投）
→ 于是"Redis 挂了"是【可恢复】的：任务重投、状态从 PG 重建
→ 而如果反过来（Redis 存权威状态），"Redis 挂了"就是【数据事故】
```

【取舍】**一句话判据**：

> **能丢的东西放缓存，不能丢的东西放数据库；而"哪个组件挂了可以重来"这件事，应该在设计阶段就写下来。**

**到这里你应该能回答**：为什么"权威状态在哪"是一个架构问题，而不是一个缓存配置问题？

### 4. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "有 TTL 就不怕不一致" | 【推导】**TTL 只给"最多旧多久"这个上限**（60 秒 TTL = 最多旧 60 秒），**它不保证正确性**。**如果这份数据参与判断，那 60 秒里的错误决定照样发生** |
| "缓存挂了大不了回源" | 【推导】**回源压力会放大 `1/(1−命中率)` 倍**：命中率 95% 时全挂 → **数据库要扛 20 倍流量**，大概率打穿。**"缓存挂了怎么办"必须提前设计限流 / 降级** |
| "Redis 很可靠，可以当数据库用" | 【事实】**不可以**。它的持久化是"尽力而为"（AOF 默认每秒刷盘，最坏丢 1 秒；RDB 丢更多），**定位就是缓存**（[[母题-R2-持久化与内存淘汰]]）。**权威状态不能只放它** |
| "余额可以缓存，加个 TTL 就行" | 【推导】**不行**。余额是**参与判断**的数据（够不够扣），**旧值会导致业务做错**。这类数据要"读权威来源"，或者只缓存一个"肯定够用"的上界做快速失败（**不能用来放行**） |
| "什么都能缓存，只要 TTL 够短" | 【推导】**TTL 再短也有窗口**，而"窗口内做错事"这个后果不随 TTL 变短而消失，只是概率降低。**判据三问里第 ③ 问不过，就不该进缓存** |
| "缓存能提升性能，所以能加就加" | 【取舍】**加缓存同时引入**：一个**新的不一致来源**、一个**新的故障点**、一份**新的内存成本**。**收益必须大于这三样**——"能本地算出来的东西"就不值得（第 2.1 的第 ④ 类） |
| "用了缓存就是最终一致，没关系" | 【推导】**"最终一致"必须配一个数字**：最终是多久（TTL？几百毫秒？）。**说不出数字，就等于没设计** |
| "Redis 和数据库之间用事务保证一致" | 【事实】**做不到**——跨两个系统没有普通事务。**能做到的是**：Outbox / 失效消息（**与业务同事务落库**）→ 由 Worker 异步执行删除。**EnergyOps 用的就是这个** |

## 二、自测

**Q1（计算）**：某读接口 **5000 QPS**，缓存命中率 **95%**。数据库实测能扛 **8000 QPS** 的读。

问：① 正常时数据库承受多少？② 缓存全挂时呢？③ 会发生什么？④ 该怎么设计？

**A1**：

```
① 正常回源 = 5000 × (1 − 0.95) = 【250 QPS】→ 远在 8000 以内，很安全

② 缓存全挂 = 全部请求回源 = 【5000 QPS】
   ★ 看起来"5000 < 8000，还扛得住"？—— 但要看下一条

③ 会发生的连锁反应：
   5000 QPS 直接打数据库，而且【这些查询原本是被缓存挡住的"重查询"】
   （能被缓存挡住的往往就是慢查询：聚合、join、大范围扫描）
   → 数据库变慢 → 上游超时 → 上游重试 → 请求量再翻倍
   → 【8000 的上限很快被突破】→ 雪崩
```

【推导】**这里有一个容易算漏的地方**：**"缓存挡住的那部分请求"和"原来就在回源的请求"性质不同**——**能被缓存挡住的往往是更重的查询**（轻查询没必要缓存）。所以不能简单用 QPS 比较，**回源的"单位成本"更高**。

④ **设计（三档，要提前做）**：

| 档 | 做法 |
|---|---|
| **① 限流** | 入口把流量压到数据库能扛的量（比如 3000），**明确拒绝一部分**——"有损但可控" |
| **② 降级** | 返回兜底内容（默认值 / 静态页 / 上次快照），**保证服务不挂** |
| **③ 本地缓存兜底** | 实例内缓存能顶一个 TTL，给恢复争取时间 |
| **④ 关键点** | **绝不能让"缓存未命中"直接等于"打数据库"**——中间必须有闸门 |

【这一步在验证什么】验证 2.2 的判据：**缓存的价值与它的风险同源**——命中率越高，挂的时候越惨，所以闸门必须提前设计。

**Q2（计算）**：某服务把 **100 万个 key** 放进 Redis，每个约 **1 KB**（合计约 **1 GB**）。监控显示**只有 1% 的 key 被访问过**。

问：① 有多少内存是"白占"的？② 这会带来什么后果？③ 怎么改？

**A2**：

```
① 被访问过的：1% = 1 万 个 key ≈ 10 MB
   白占的：99% = 99 万 个 key ≈ 【990 MB】
   → 也就是【99% 的内存没有产生任何命中】

② 后果（不只是"浪费"）：
   · 【淘汰策略会把热数据挤出去】：内存有限时，那些从没被访问的 key
     和热 key 一起参与淘汰，可能导致【热 key 被淘汰、命中率反而下降】
   · 【成本】：内存是这个系统里最贵的资源之一
   · 【持久化与复制变慢】：数据量越大，RDB/AOF 与主从同步越重
   · 【启动恢复变慢】：重启后要重新加载大量无用数据
```

③ **改法（三步）**：

| 步 | 做法 |
|---|---|
| **1. 先测"该不该缓存"** | 用判据三问过一遍：这些 key 是派生数据吗？访问分布是不是长尾？**长尾冷数据本来就不该缓存** |
| **2. 改缓存策略** | **惰性加载**：只缓存**被访问过**的（读时未命中再回源并写入）——**别再"预加载全量"** |
| **3. 给内存设上界** | 配 `maxmemory` + 合理淘汰策略（[[母题-R2-持久化与内存淘汰]]）；**Redis 的内存必须有上界**（这与 [[母题-O2-虚拟内存与缺页]] 的"给每个会增长的东西设上界"是同一条原则） |

【这一步在验证什么】验证 2.1 的第 ③ 类：**冷数据放缓存不只是浪费，它会通过淘汰机制伤害真正的热数据。**

**Q3（判读）**：某服务用 Redis 缓存"用户余额"，TTL 60 秒，读路径直接读缓存。

问：① 这个设计的问题在哪？② 会看到什么现象？③ 如果一定要加速这个读，可以怎么做？

**A3**：

```
① 问题：余额是【参与判断】的数据（够不够扣），
   而缓存会给出【最多旧 60 秒】的值。
   → 判据三问的第 ③ 问不过（会因为旧值做错事）
```

② **现象**（低并发下完全不出现）：

```
用户看到的余额 = 100（缓存）
60 秒窗口内该用户已经扣了 90（库里是 10）
用户读缓存 → 还是 100 → 判断"够" → 发起下单
→ 数据库校验时发现不足 → 失败
→ 用户体验："我明明看到有钱，为什么下不了单"
```

**关键点**：**用户没有做错任何事，是系统给了一个旧值让他做了决定。** 这类 bug 在压测里通常不复现（因为压测用的是不同的用户 / 没有真实的 60 秒窗口）。

③ **要加速这个读，有三条路（都不包括"直接缓存余额"）**：

| 路 | 做法 | 说明 |
|---|---|---|
| **① 缓存"判断结果"而不是"余额"** | 缓存的是"该用户是否还有可用额度"的**带版本的判断**，**且写路径必须让缓存失效** | 复杂度高；**本质上还是在缓存"参与判断的数据"**，要非常小心 |
| **② 把判断下沉到数据库** | 读缓存只用于**展示**（显示余额可以旧），**扣减用条件更新**（`UPDATE ... WHERE balance >= ?`） | **这是标准答案**：展示可以旧，**判断由数据库在被保护和原子的地方做**（[[母题-L1-乐观锁与悲观锁]] 2.3） |
| **③ 不做缓存，优化查询本身** | 余额查询通常是主键查一行，**本来就该很快**；慢的话先查索引与连接池 | **先确认它真的需要缓存** |

【这一步在验证什么】验证 1.2 的判据：**"用来展示"和"用来判断"是同一条数据的两条不同路径，前者可以缓存、后者不能。** 这正是本卡开头两个问题里的第二个——**它的根因不是"缓存没配好"，而是"把参与判断的数据放进了缓存"。**

**Q4（纠错）**：下面这段话哪里错了？

> "缓存加个 TTL 就没什么一致性问题了——反正最多脏一会儿，业务能忍。"

**A4**：**"最多脏一会儿"这个判断本身不一定错，但"所以业务能忍"是未经检验的假设——而且它漏掉了两件事。**

**① "能忍多久"必须是一个具体的数，而且必须按最苛刻的用途来定**：

```
同一份数据，两条路径的容忍度完全不同：
  用来【展示】（列表页、详情页）→ 忍 60 秒没问题
  用来【判断】（够不够扣、能不能流转）→ 【一秒都不能忍】
→ 所以"业务能忍"必须落到"哪条路径 + 几秒"，而不是一句感觉
```

**② TTL 只覆盖"到期会自己更新"，不覆盖"到期时会发生什么"**：

```
TTL 到期的那一刻 → 缓存未命中 → 【回源】
如果这个 key 是热 key，且很多实例同时到期 →
  【同时回源】= 缓存击穿（[[母题-R3-缓存一致性与三类事故]]）
→ TTL 反而制造了一个尖峰
```
**所以 TTL 要加随机抖动**（避免同一时刻集体到期）。

**③ 还有一件被漏掉的事：删缓存失败怎么办**：

```
写路径"写完数据库 → 删缓存"里，如果【删缓存失败】，
那份旧值会一直留到 TTL 到期（这就是"回退到只靠 TTL"的兜底）
→ 所以 TTL 的真正角色是【兜底】，不是【主要机制】
→ 主要机制应该是"写时失效"，而它自己的失败要靠 TTL 兜住
→ 而"删缓存"这个动作本身还可能失败 —— 所以 EnergyOps 用 Outbox 来保证它最终会被执行
```

**准确说法**：*TTL 给的是"最多旧多久"的上限，要按最苛刻的用途定；它还要加随机抖动防集体到期；而它的角色是"给写时失效兜底"，不是主要机制。至于"业务能忍"，必须落到具体的路径与秒数上。*

**Q5（纠错）**：下面这段话哪里错了？

> "Redis 性能这么好，就让它当主存储吧——反正它也有持久化（RDB + AOF），数据丢不了。"

**A5**：**"数据丢不了"是错的，而且这正是"把缓存当数据库"这类事故的核心。**

**【事实】Redis 的持久化是"尽力而为"，不是"保证不丢"**：

| 方式 | 最坏会丢多少 |
|---|---|
| **RDB** | 两次快照之间的全部写入（按配置可能是几分钟） |
| **AOF（`everysec`，默认）** | **最坏约 1 秒**的写入 |
| **AOF（`always`）** | 理论上不丢，但**性能代价很大**（每条命令都要刷盘） |

**而且还有几件"持久化"解决不了的事**：

```
① 主从异步复制 → 主挂了、从还没同步 → 那部分数据丢（[[母题-R2-持久化与内存淘汰]]）
② 内存是有限的 → 【淘汰策略会主动删数据】（这是它的设计行为，不是故障）
③ 误操作（FLUSHALL / 错误覆盖）→ 会立刻复制到从库
④ 持久化文件损坏 / 磁盘满 → 恢复失败
```

**更根本的一句话**：**持久化解决的是"进程重启后数据还在"，不解决"数据是唯一一份、丢了不可恢复"。** 而"权威状态"的定义恰恰就是后者。

**正确的分工（RuleArena 的模板）**：

```
PostgreSQL = 权威状态（唯一事实来源，事务保证）
Redis      = 队列 / 限流 / 短期进度（丢了可以重投、可以重算）
→ 于是"Redis 挂了"= 可恢复事件
→ 反过来（Redis 存唯一一份）→ "Redis 挂了"= 数据事故
```

**准确说法**：*Redis 的持久化能保证"重启后数据大多还在"，但 AOF everysec 最坏丢约 1 秒、RDB 丢更多，加上异步复制、主动淘汰、误操作，它不能承担"唯一一份数据"。权威状态放数据库，缓存放可重建的派生数据——"哪个组件挂了可以重来"要在设计阶段就写下来。*

## 三、面试输出（学完再看）

**一句话结论**：判断"什么数据该放缓存"要问**三问**——**丢了能不能重建、旧一段时间能忍吗（几秒）、会不会因为读到旧值做错事**；任何一问不过就不是"缓存策略要调"，而是**放错地方了**。核心区分是**派生数据**（榜单、统计、配置副本 —— 可以缓存）与**权威状态**（订单、账本、余额、库存 —— 不能只放缓存）；而**同一份数据的"展示路径"和"判断路径"容忍度完全不同**：展示可以旧 60 秒，**判断一秒都不能旧**（所以余额的正确做法是"显示可以走缓存、扣减用条件更新下沉到数据库"）。另外两笔必须提前算的账：**缓存全挂时回源压力放大 `1/(1−命中率)` 倍**（命中率 95% 就是 20 倍，足以打穿数据库，所以**限流与降级必须提前设计**）；**TTL 给的是"最多旧多久"的上限，它的角色是给"写时失效"兜底**，不是主要机制，而且**要加随机抖动防集体到期**。至于 Redis 的持久化——**它保证"重启后数据大多还在"，不保证"数据是唯一一份"**（AOF everysec 最坏丢约 1 秒），**所以权威状态必须留在数据库里**（RuleArena 的 PG + Redis 分工就是这个模板）。

**恢复关键词**：派生数据 vs 权威状态 / **判据三问（能否重建 · 能忍多久 · 会不会做错事）** / **"展示路径"和"判断路径"容忍度不同** / 余额不能直接缓存（扣减下沉到数据库用条件更新）/ 冷数据放缓存会通过**淘汰**伤害热数据 / **回源放大 = 1/(1−命中率)**（95% → 20 倍）/ 缓存挂了要**限流 + 降级 + 本地兜底**，绝不能让未命中直连数据库 / **TTL 是上位上限、写时失效是主机制、抖动防集体到期** / 删缓存失败要靠 TTL 兜底（EnergyOps 用 Outbox 保证执行）/ **Redis 持久化 ≠ 不丢**（AOF everysec 最坏 1 秒）/ 权威状态在 PG、Redis 放可重投的东西 / "哪个组件挂了可以重来"要写下来

**核心不变量 / 主线**：
**缓存能解决的问题只有"快"，不能解决"可靠"和"正确"。** 所以边界只有一条：**能被重建的、不参与判断的、能容忍旧值的东西，才属于缓存**（能用 `1/(1−命中率)` 量化它的风险、能用 TTL 量化它的不一致）。**而"权威状态在哪"是一句架构级的话——它决定了"哪个组件挂了是事故、哪个挂了只是变慢"。**

**完整回答骨架**：把"缓存"拆成派生数据与权威状态 → 给判据三问 → 三类放错的后果（尤其"参与判断的数据带旧值"为什么会从慢变成错）→ **量化回源放大 `1/(1−h)` 与降级设计** → 一致性的上限（TTL vs 写时失效 vs 不用）→ 权威状态放哪决定架构骨架 → Redis 持久化 ≠ 不丢 → 边界与误解

**完整回答（口述稿）**：
判断"什么数据该放缓存"要问**三问**——**丢了能不能重建**、**旧一段时间（几秒）能忍吗**、**会不会因为读到旧值做错事**；任何一问不过，就不是"缓存策略要调"，而是**放错地方了**。

核心区分是**派生数据**（榜单、统计、配置副本——可以缓存）与**权威状态**（订单、账本、余额、库存——不能只放缓存）。而**同一份数据的"展示路径"和"判断路径"容忍度完全不同**：展示可以旧 60 秒，**判断一秒都不能旧**（所以余额的正确做法是"显示走缓存、扣减用 `UPDATE ... WHERE balance >= ?` 下沉到数据库"）。

两笔必须提前算的账：**缓存全挂时回源压力放大 `1/(1−命中率)` 倍**（命中率 95% 就是 20 倍，足以打穿数据库，所以**限流与降级必须提前设计**）；**TTL 给的是"最多旧多久"的上限，它的角色是给"写时失效"兜底**，不是主要机制，而且**要加随机抖动防集体到期**。

至于 Redis 当数据库：**不行**。AOF `everysec` 最坏丢约 1 秒、RDB 丢更多，加上异步复制、主动淘汰、误操作——**持久化保证的是"重启后数据大多还在"，不是"唯一一份"**。一致性要"不骗人"：说清上限多少、失败怎么办、哪些路径不能容忍。

**分层要点**：
- **结论**：三问定能不能缓存；派生数据可缓存，权威状态不行；展示可旧、判断不能旧。
- **推导链**：三问 → 派生 vs 权威 → 两条路径容忍度不同 → 回源放大与 TTL 定位 → Redis 不能当唯一数据源。
- **量化**：回源放大 `1/(1−命中率)`（95% → 20 倍）；展示可旧 60 秒、判断基本 0；AOF `everysec` 最坏丢约 1 秒。
- **边界与常见误解**："余额能不能缓存"要分路径答；"Redis 挂了业务能不能继续"必须提前设计限流→降级→本地缓存兜底，不能让"未命中"直接等于"打数据库"。

**追问**（先说后看）

1. **余额能不能缓存？** —— **看路径**：**展示**可以（旧一点无所谓）；**判断**不能（旧值会让用户做错决定）。**标准做法是"显示走缓存、扣减用 `UPDATE ... WHERE balance >= ?` 下沉到数据库"**（[[母题-L1-乐观锁与悲观锁]] 2.3）。
2. **缓存挂了怎么办？** —— 先算回源放大 **`1/(1−命中率)`**（95% → 20 倍）；然后按"**限流 → 降级 → 本地缓存兜底**"设计闸门。**绝不能让"未命中"直接等于"打数据库"。**
3. **TTL 设多少？** —— **按最苛刻的用途定**（展示路径可以长、判断路径基本是 0）；**加随机抖动防集体到期**；而且它的角色是**给写时失效兜底**，不是主要机制。
4. **Redis 能当数据库用吗？** —— **不能**。AOF `everysec` 最坏丢约 1 秒、RDB 丢更多，加上异步复制、主动淘汰、误操作——**持久化保证的是"重启后数据大多还在"，不是"唯一一份"**。
5. **缓存一致性怎么做到"不骗人"？** —— 说清三件事：**① 上限是多少**（TTL 几秒 / 写时失效几百毫秒）；**② 失败怎么办**（删缓存失败靠 TTL 兜底，用 Outbox 保证最终执行）；**③ 哪些路径不能容忍**（参与判断的那条走权威来源）。

**同类变体**

- 「本地缓存（进程内）和 Redis 缓存的边界怎么划？」——**本地缓存的 TTL 更短（几十毫秒）、容量更小、不一致更明显**，但**连 Redis 的网络往返都省了**。适合"极热 + 能容忍几十毫秒旧值"的数据（[[母题-R4-大key与热key]] 3.3）
- 「多级缓存怎么分层？」——常见三层：**本地 → Redis → 数据库**，每层**容忍度递增、延迟递增**；**关键是要给每层都定"命中率与回源放大"的目标**
- 「配置中心算缓存还是权威状态？」——**看它是不是唯一一份**。配置本身往往**有权威来源（Git / 数据库）**，缓存是派生数据；但如果配置只存在配置中心里，**它自己就必须高可用**（不能当"可丢的缓存"）
- 「为什么 RuleArena 敢把 Redis 只给 256~512MB？」——**因为放进去的是可重投的队列与短期进度**（`08-capacity-cost-and-facts.md`）——**规格小不是问题，放错东西才是问题**
