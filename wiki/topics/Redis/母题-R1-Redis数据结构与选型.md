## 一、教材

### 1. 前提：Redis 为什么快

#### 1.1 第一个原因：数据在内存里

【事实】把量级摆出来（[[母题-M1-为什么用B+树]] 用过同一张表）：

| 访问 | 典型延迟 |
|---|---|
| 内存随机访问 | 约 100 纳秒 |
| 机械盘随机读 | 约 10 毫秒 |

【推导】差 **5 个数量级**。**这一条推出一件很关键的事**：

> **磁盘系统里最重要的优化目标是"减少 IO 次数"（M1 的全部内容）；而 Redis 里没有磁盘 IO 可省——所以它优化的是别的东西。**

**记住这一条**：第 4 节讲"为什么用跳表不用 B+ 树"时，它就是唯一答案。

#### 1.2 第二个原因：单线程（但要先澄清"单"的是什么）

【事实】**Redis 的"单线程"指的是：命令的执行是单线程的。**

【推导】**为什么单线程反而快**——三个理由：

1. **没有锁竞争**：不用为每个键加锁解锁（对比多线程模型要处理并发修改）
2. **没有上下文切换**：避免线程切换的开销
3. **没有原子性问题**：一条命令天然原子（这也是它适合做计数器、分布式锁的基础）

【事实】**必须说清的边界（版本演进）**：

| 版本 | 变化 |
|---|---|
| 早期 | 网络 IO 与命令执行都在同一个线程 |
| **Redis 6+** | **网络 IO 用多线程**（读写 socket、解析协议），**命令执行仍然是单线程** |

**所以"Redis 是单线程还是多线程"的准确答案是**：**命令执行单线程，网络 IO 在 6.0 之后是多线程。** 只说"单线程"是旧答案，会被追问。

【推导】**单线程的代价，直接推出下一件事**：

> **一条慢命令会卡住所有人。** 因为是单线程，一条 `KEYS *` 或大 key 的 `DEL` 执行期间，**其他所有请求都在等**。
>
> 【联系】这正是 [[母题-N3-进程线程与协程]] 里"协作式的代价"——**一处阻塞，全体停摆**。**同一个道理，在进程、协程、Redis 三处重复出现。**

#### 1.3 第三个原因：IO 多路复用

【事实】Redis 用 `epoll` 这类机制，**一个线程一次系统调用就能问出"成千上万个连接里哪些有数据了"**（N3 第 3.1 节讲过同一个机制）。

**三个原因合起来**：内存（快）+ 单线程（无锁、无切换）+ 事件循环（一个线程管很多连接）。

### 2. 五种基础结构：各自是什么形状、解决什么

**理解的方式不是背名字，而是问"它是一份什么形状的数据"。**

| 结构 | 形状 | 典型场景 |
|---|---|---|
| **String** | 一个值（字符串/数字/二进制） | 计数（`INCR`）、缓存单值、**分布式锁**（`SET NX EX`）、限流计数器 |
| **List** | **有序、两端进出的线** | 队列 / 栈（`LPUSH`+`RPOP`）、简单消息流、最近 N 条 |
| **Hash** | **一个对象的一堆字段** | 对象属性（购物车 `key=cart:1, field=sku`）、部分字段更新 |
| **Set** | **不重复的集合，无序** | **去重**、交集并集（共同好友、抽奖去重）、标签 |
| **ZSet** | **不重复的集合，但每个成员带一个分数，按分数排序** | **排行榜**、延迟队列（score 存时间戳 + `ZRANGEBYSCORE` 捞到期任务）、带权重的去重 |

【推导】**五种结构的差别可以归纳成两个问题**：

1. **要不要"有序"**？ → 要排序用 **List**（按插入位置）或 **ZSet**（按分数）
2. **要不要"唯一"**？ → 要去重用 **Set** 或 **ZSet**

**所以选型就是这两问的组合**：

```
要唯一 + 要按分数排序 → ZSet
要唯一 + 不要顺序     → Set
不要唯一 + 要顺序     → List
要按字段取子集        → Hash
就是个值              → String
```

#### 2.1 Set 和 ZSet 的区别（9.9 漏掉的那一条）

【事实】**Set 只存成员，ZSet 存成员 + 分数**。

- `Set` 的操围绕"有没有 / 交并差"
- `ZSet` 的操围绕"排名 / 按分数范围取"

【推导】**ZSet 多出来的那个"分数"，是它一切能力的来源**：能排序、能取 Top N、能按分数区间捞。**所以排行榜必须用 ZSet，用 Set 做不到。**

### 3. 四种扩展结构（知道场景就够了）

| 结构 | 是什么 | 场景 | 关键代价 |
|---|---|---|---|
| **Bitmap** | 用位来表示"是/否" | 签到、日活打点、布尔标记 | 稀疏数据浪费空间 |
| **HyperLogLog** | **基数估算**（不存原始数据） | 大流量 UV 去重计数 | **有误差（约 0.81%）**，不能取回原始元素 |
| **Geo** | 存经纬度并做距离查询 | 附近的人 / 附近的门店 | 精度依赖底层 ZSet 编码 |
| **Stream** | **带消费组的消息流** | 中小规模事件流、任务分发 | 与 Kafka 的持久化/分区/生态差距明显 |

【取舍】**HyperLogLog 最值得记的一点**：**它用"接受误差"换"固定的小内存"**——统计 1 亿 UV，内存也就十几 KB。这是"用精度换空间"的典型取舍。

### 4. ZSet 的底层：跳表 + 哈希表，以及为什么不用 B+ 树

#### 4.1 为什么是"两个结构"

【事实】ZSet 内部同时用了两样东西：

| 组件 | 支撑什么操作 |
|---|---|
| **哈希表**（member → score） | **按成员 O(1) 查分数**（`ZSCORE`） |
| **跳表**（按 score 排序） | **按分数范围 / 排名 O(log N)**（`ZRANGE`、`ZRANGEBYSCORE`） |

【推导】**两个结构是为了支撑两类完全不同的查询**。这也解释了为什么"ZSet 既能查某个人的分数，又能取 Top 100"——**两件事走两条路径**。

#### 4.2 跳表是什么

::figure skiplist.svg | 跳表 = 有序链表 + 多层稀疏索引 | 从最高层开始，能往右就往右、不能就下降一层

**定义**：**跳表（Skip List）= 有序链表 + 多层稀疏索引**。查询从最上层开始：

```
能往右就往右（目标更大），不能往右就往下一层
→ 比较次数从 O(n) 降到期望 O(log n)
```

**关键设计**：**每一层是否出现是随机的**（约 1/2 概率向上）。

【推导】**这说明它不需要重平衡**——而平衡树（AVL / 红黑树）在插入删除后必须旋转来维持平衡。**这是跳表"实现简单"的根本原因。**

#### 4.3 为什么不用 B+ 树（本题的落点）

【推导】**用 M1 的判据反推**：

B+ 树的全部优势来自一句话——**"一次磁盘 IO 的成本几乎固定，所以让每次 IO 尽量多带数据回来"**（扇出大 → 树矮 → IO 少）。

**但这个前提在 Redis 里不成立**：

| | B+ 树的主场（MySQL） | Redis |
|---|---|---|
| 数据在哪 | 磁盘 | **内存** |
| 瓶颈是什么 | **磁盘 IO 次数** | **比较与内存访问** |
| 扇出的价值 | 极高（一次 IO 带回一页） | **几乎为零**（没有 IO 可省） |
| 代价 | 节点分裂/合并（重平衡） | 跳表用随机层数替代，**不需要重平衡** |

> 【推导】**内存里没有"IO 分摊"这回事，所以 B+ 树最大的优势失效了，只剩下"实现复杂"这个缺点。**

**那为什么不用红黑树 / AVL？**【取舍】它们能用，但：

- **平衡操作复杂**（旋转、维护颜色）
- **范围查询不如跳表自然**（跳表底层的链表天然支持顺序遍历）

**准确的说法**：**不是"跳表比 B+ 树快"，而是"B+ 树为磁盘设计，它的优势在内存里用不上；而跳表实现更简单、范围查询更自然"。** 这个分寸比"跳表更快"准确得多。

### 5. 怎么答才拿分：每个结构配一个你的场景

【取舍】**9.9 这道题丢分的关键不是"漏了哪个结构"，而是"没有给出任何一个自己用过的场景"**——听起来像背书。

**所以每个结构都要能挂上真实场景**（面试时挑 2–3 个讲，不要全报）：

| 结构 | 可以挂的场景 |
|---|---|
| **String** | 限流计数器（`INCR` + `EXPIRE`）、接口幂等键（`SET NX`）、短期去重标记 |
| **Hash** | 缓存一个对象的多个字段，**只更新其中一两个字段**（不用整对象重写） |
| **Set** | 短期去重（"这个请求处理过没有"）、标签集合 |
| **ZSet** | **延迟队列**（score = 到期时间戳，`ZRANGEBYSCORE` 捞到期任务）、按权重的优先级队列 |
| **Stream** | 中小规模的任务分发与消费组 |

**（面试话术的结构）**：先给"五种基础 + 四种扩展"的总览（一句话一个），**再挑 1–2 个展开讲你项目里怎么用的**。**总览证明覆盖面，展开证明真用过。**

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "Redis 是单线程的" | 【事实】**准确说法：命令执行单线程，网络 IO 在 6.0 后是多线程。** 只说"单线程"是旧答案 |
| "跳表比 B+ 树快" | 【推导】**不是快慢问题**：B+ 树为磁盘 IO 设计，**它的优势在内存里用不上**；而跳表实现更简单、范围查询更自然 |
| "单线程所以不会有并发问题" | 【推导】单条命令原子，**但多条命令的组合不原子**（`GET` 完再 `SET` 之间可能插进别的请求）→ 需要 `INCR`/Lua/`SET NX` 这类原子操作 |
| "Redis 什么都能缓存" | 【取舍】**它适合缓存"派生数据"，不适合当权威状态**（[[母题-R3-缓存一致性与三类事故]]） |
| "Hash 就是 ZSet 少了个排序" | 【事实】**两者形状完全不同**：Hash 是"字段→值"的映射（按字段取），ZSet 是"成员→分数"的**有序集合**（按分数取） |
| "HyperLogLog 能精确统计 UV" | 【事实】**它是估算**，标准误差约 0.81%，且**不能取回原始元素**。换来的是固定的小内存 |

## 二、自测

**Q1（计算）**：内存随机访问约 **100 纳秒**，一次磁盘随机 IO 约 **10 毫秒**。

问：两者相差几个数量级？**这个差距对"该选什么作为索引结构"意味着什么？**

**A1**：

- 10ms / 100ns = 10⁻² / 10⁻⁷ = **10⁵ → 相差 5 个数量级**

**意义**：

| 场景 | 第一优化目标 | 优选结构 |
|---|---|---|
| **磁盘**（MySQL） | **减少 IO 次数** | B+ 树（扇出大 → 树矮 → IO 少） |
| **内存**（Redis） | 没有 IO 可省 → 转向**实现简单 + 范围查询自然** | **跳表** |

【推论】**同一个问题（"该用什么索引结构"）在两处答案不同，不是因为哪个结构更好，而是因为约束变了。** 这是本卡最值钱的一条思路——**面试里能把"约束变了所以答案变了"讲出来，比记住"Redis 用跳表"有价值得多。**

**Q2（判读）**：下面五个需求分别该用哪个结构？

① 统计接口调用次数，用于限流
② 存一个订单的 20 个字段，通常只改其中一两个
③ 每天签到的用户去重，还要能查"今天有多少人签到"
④ 一个游戏关卡的前 100 名（按分数排序）
⑤ 一个任务要延迟 5 分钟执行

**A2**：

| 需求 | 结构 | 理由 |
|---|---|---|
| ① 调用计数 | **String** | `INCR` + `EXPIRE`，单条命令原子 |
| ② 订单多字段部分更新 | **Hash** | 按字段读写，不必整对象重写 |
| ③ 签到人数 | **Set**（人数少）或 **Bitmap**（按用户 ID 打点） | 要"精确人数 + 成员"用 Set；只关心"某用户是否签到"用 Bitmap 更省 |
| ④ 前 100 名 | **ZSet** | **按分数排序取范围**，Set 做不到 |
| ⑤ 延迟 5 分钟执行 | **ZSet** | score 存 **到期时间戳**，用 `ZRANGEBYSCORE` 捞到期任务 |

【补充】⑤是最容易被忽略的用法——**延迟队列就是"score 是时间戳的 ZSet"**。能说出这个，说明不只会背"ZSet 做排行榜"。

**Q3（计算）**：Redis 的哈希表要扩容。假设表里有 **100 万个键**，扩容需要把键重新分布到更大的表里。

问：为什么**不能一次性搬完**？Redis 用什么办法？

**A3**：

- **一次性搬完是 O(n) = 100 万次搬运**。因为 Redis 的命令执行是**单线程**，这一段时间里**所有其他请求都在等**（1.2 的代价）
- **Redis 用「渐进式 rehash」**：把搬运**分摊到后续的每一次操作上**（每次操作顺带搬一小批），把**一次 O(n) 的尖峰**摊成 **O(1) 的平摊开销**

【联系】**这又一次是"单线程下最怕一处阻塞、全体停摆"**（[[母题-N3-进程线程与协程]] 的协作式代价）。

**同一个约束，在三个地方给出了三种解法**：

| 场景 | 解法 |
|---|---|
| 协程里不能有阻塞调用 | 换异步库 / 丢线程池 |
| Redis 扩容会卡 | **渐进式 rehash**（把 O(n) 摊掉） |
| MySQL 加索引会卡 | **Online DDL / 影子表**（[[母题-M4-索引代价与大表变更]]） |

**能把这三处串起来讲，说明你理解的是"约束"而不是"三个孤立的知识点"。**

**Q4（纠错）**：下面这段话哪里不准确？

> "Redis 是单线程的，所以它跑不满多核 CPU，一份实例只能用一个核。"

**A4**：**"单线程"说得太笼统了。**

准确的说法是分层的：

| 部分 | 线程模型 |
|---|---|
| **命令执行** | **单线程**（这是"Redis 是单线程"这句话的真正含义） |
| **网络 IO**（Redis 6+） | **多线程**（读写 socket、解析协议） |
| 后台任务（持久化、异步删除等） | 另有后台线程 / 子进程 |

**所以"只用了一个核"也不准确**：网络 IO 和后台任务会用别的核，**但命令执行确实是单线程**——这也是为什么"慢命令会卡住所有人"。

【推论】**正确的答法是"命令执行单线程"，并主动补一句 6.0 之后网络 IO 多线程**——这一句能把"背旧资料"的印象变成"跟得上版本"。

**Q5（纠错）**：下面这段话哪里错了？

> "ZSet 用跳表实现，是因为跳表比 B+ 树和红黑树都快。"

**A5**：**"更快"这个归因是错的。准确的原因是"约束变了"。**

B+ 树的全部优势来自"**一次磁盘 IO 的成本固定，所以让每次 IO 多带数据回来**"（扇出大 → 树矮 → IO 少）。**而 Redis 的数据在内存里，根本没有磁盘 IO 可省** —— **B+ 树最大的优势失效了，只剩"节点分裂合并、需要重平衡"这个复杂度。**

跳表胜出的真实理由是两条：

1. **不需要重平衡**（层数随机，约 1/2 概率向上）
2. **范围查询更自然**（底层就是有序链表，顺序遍历天然支持）

【取舍】红黑树也能用，但它同样有"平衡操作复杂"的问题，而且**范围查询不如跳表顺**。

**准确说法**：**不是跳表更快，而是 B+ 树是为磁盘设计的结构，它的优势在这个场景里用不上；跳表是"约束更匹配"的那个选择。**

## 三、面试输出（学完再看）

**一句话结论**：Redis 快在三点——**数据在内存、命令执行单线程（无锁、无切换）、IO 多路复用**；注意 6.0 之后**网络 IO 是多线程**，只有命令执行仍是单线程。**五种基础结构按"要不要唯一 + 要不要顺序"选**：String / List / Hash / Set / ZSet；另有 Bitmap、HyperLogLog（估算 UV，有误差）、Geo、Stream 四种扩展。**ZSet 底层是"跳表 + 哈希表"**——哈希表支撑按成员查分数，跳表支撑按分数取范围与排名；**用跳表而不用 B+ 树，是因为 B+ 树的优势（减少磁盘 IO）在内存里用不上，而跳表不需要重平衡、范围查询更自然。**

**恢复关键词**：内存（差 5 个数量级）/ 命令执行单线程 + 网络 IO 多线程 / 单线程的代价是慢命令卡所有人 / 选型两问（唯一？有序？）/ ZSet = 跳表 + 哈希表 / 跳表的层数随机所以不需重平衡 / B+ 树为磁盘设计、内存里优势失效 / HyperLogLog 用误差换空间 / **每个结构都要挂一个自己的场景**

**核心不变量 / 主线**：
**"该用什么结构"由"数据是一份什么形状的内存数据"决定**，而不是由"哪个结构更高级"决定。同理，"该用什么索引结构"由"瓶颈是 IO 还是比较"决定——**约束变了，答案就变了**。

**完整回答骨架**：快的三个原因（内存 / 单线程 / 事件循环）+ 版本澄清 → 五种基础结构按"唯一 + 有序"两问选型 → 四种扩展结构及各自代价 → ZSet 为什么是两个结构 → 跳表是什么、为什么不需要重平衡 → **为什么不用 B+ 树（约束变了）** → 每个结构配一个自己的场景

**完整回答（口述稿）**：
Redis 快在三点：**数据在内存**、**命令执行单线程**（无锁竞争、无上下文切换、单条命令天然原子）、**IO 多路复用**（epoll 一次问出成千上万连接里哪些就绪）。注意 6.0 之后**网络 IO 是多线程**，**只有命令执行仍是单线程**；后台任务（bgsave、异步删）另有线程/子进程。

五种基础结构按"**要不要唯一 + 要不要顺序**"选：String（最通用）、List（有序可重复，队列/栈）、Hash（字段映射）、Set（无序唯一，去重与集合运算）、ZSet（按 score 有序唯一，排行榜/延迟队列）。四种扩展：Bitmap（二值标记）、HyperLogLog（估算 UV，**标准误差约 0.81%**，换固定小内存）、Geo（附近查询，底层 ZSet）、Stream（可持久化的消息流）。

**ZSet 底层是"跳表 + 哈希表"**——哈希表支撑按成员查分数，跳表支撑按分数取范围与排名。**用跳表而不用 B+ 树，不是快慢，是约束**：B+ 树的优势（减少磁盘 IO）在内存里用不上，而跳表不需要重平衡、范围查询顺着底层链表扫就行。

单线程的代价必须一起说：**一条慢命令卡住所有人**（`KEYS *`、大 key 的 `DEL`），所以才有慢命令禁用清单和大 key 治理。

**分层要点**：
- **结论**：内存 + 命令单线程 + IO 多路复用；结构按"唯一 + 顺序"选；ZSet = 跳表 + 哈希表。
- **推导链**：为什么快 → 单线程的代价 → 结构选型 → ZSet 为什么两个结构都要 → 跳表 vs B+ 树是约束差异。
- **量化**：6.0 后网络 IO 多线程；HyperLogLog 标准误差约 0.81%；30 个工具/大结构场景的上下文类比不适用（那是 Agent 侧）。
- **边界与常见误解**：6.0 之后"Redis 是单线程"已经不准确；单条命令原子 ≠ 一组命令原子；HyperLogLog 取不出单条成员。

**追问**（先说后看）

1. **Redis 是单线程还是多线程？** —— **命令执行单线程，网络 IO 在 6.0 之后是多线程。** 后台任务另有线程/子进程。
2. **单线程为什么还快？** —— 无锁竞争、无上下文切换、单条命令天然原子；加上内存访问快、epoll 一次管很多连接。
3. **单线程有什么代价？** —— **一条慢命令卡住所有人**（`KEYS *`、大 key 的 `DEL`）。所以有"慢命令禁用清单"和"大 key 治理"。
4. **ZSet 为什么用跳表不用 B+ 树？** —— 见 Q5：**不是快慢，是约束**。
5. **HyperLogLog 精确吗？** —— 不精确，标准误差约 0.81%，**用它换的是固定的小内存**。
6. **Redis 能当消息队列吗？** —— 能用 List / Stream 做**中小规模**；但**持久化、分区、重放、生态**与 Kafka 差距明显，**不能因为"已经用了 Redis"就默认替代**（[[母题-R3-缓存一致性与三类事故]]）。

**同类变体**

- 「ZSet 还能做什么？」——**延迟队列**（score = 到期时间戳）、带权重的优先级队列、滑动窗口限流（score 存时间戳 + `ZREMRANGEBYSCORE` 清窗口外）
- 「Hash 和 String 存对象哪个好？」——**只改部分字段用 Hash**（避免整对象序列化重写）；**整个对象一起读写用 String**（更省内存、少一次 field 开销）
- 「怎么发现大 key / 热 key？」——`redis-cli --bigkeys`、`SCAN` 采样、监控命令耗时；**线上更可靠的是慢日志 + 代理层统计**
