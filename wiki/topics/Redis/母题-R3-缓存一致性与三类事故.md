## 一、教材

### 1. 前提：先定"谁是权威"

#### 1.1 缓存是派生数据【事实】

**这句话是本卡的地基**：

> **数据库是权威状态，缓存只是它的一份派生副本。**

【推导】**这个定位直接推出三件事**：

1. **不一致时以 DB 为准** —— 不是"谁新信谁"，而是**结构上就规定了 DB 是真相**
2. **缓存可以丢** —— 缓存挂了要能从 DB 重建（所以缓存**不是**可用性的单点，**但**它会变成"性能的单点"）
3. **不必追求强一致** —— 派生副本追求强一致，等于给系统加一条永远达不成的目标

#### 1.2 为什么做不到强一致【推导】

【推导】要强一致，就得让"改 DB"和"改缓存"**一起成功或一起失败**——也就是一个事务。

**但它们是两个独立的系统**：

| | DB | Redis |
|---|---|---|
| 事务范围 | 自己的事务 | 自己的原子操作 |
| 跨系统事务 | **没有**（除非上分布式事务，代价极高） | 同左 |

**所以你只能做到"最终一致"**——问题不是"能不能做到强一致"，而是：

> 【取舍】**你允许多大的不一致窗口？窗口里读到旧数据，会不会造成业务事故？**

**这句话是本卡唯一真正需要判断的地方**——技术手段都是现成的，**难的是定口径**。

**到这里你应该能回答**：为什么"缓存和数据库保证强一致"这个目标本身就是不成立的？

### 2. 写路径的几种写法（先各自介绍，再比较）

#### 2.1 写法 A：先删缓存，再写 DB【事实】

```
① DEL cache
② UPDATE db
```

**问题**：① 和 ② 之间有窗口，此时**另一个请求读缓存未命中 → 从 DB 读到旧值 → 写回缓存**。结果：**缓存里是旧值，而且可能长期留着。**

**所以这个顺序是错的。**

#### 2.2 写法 B：先写 DB，再删缓存（Cache Aside）【事实】

```
① UPDATE db
② DEL cache
```

**这是主流做法。** 【推导】**为什么它比 A 好**：把"写 DB"放在前面，**并发读最坏也只是读到旧值一次**，而不是把旧值**写进缓存长期保留**。

**它唯一的缺口**：② 失败了（Redis 抖动、网络超时）→ **缓存里是旧值，直到 TTL 到期**。

【取舍】**所以必须配一条兜底**：要么**给 TTL**（让脏数据自己过期），要么**有重试/对账**（发现不一致能修回来）。**没有 TTL 又没有对账的 Cache Aside，就是埋雷。**

#### 2.3 更新缓存 vs 删除缓存

【推导】**为什么"删"比"更新"好**：

- **更新**：每次都要算新值并写缓存；如果这个值是聚合出来的（比如榜单），**算出来的新值可能马上又过期**，白算
- **删除**：不动缓存内容，**下次谁读谁来重建**（懒加载）—— **只在真有人读的时候才付重建成本**

**代价**：删除后紧跟一次读取会"未命中 → 查 DB"（这就是击穿的成因之一）。

#### 2.4 延迟双删 / Outbox / CDC【取舍】

| 做法 | 做法 | 适用 |
|---|---|---|
| **延迟双删** | 写 DB 前后各删一次（第二次延迟几百毫秒） | 缓解 A 的窗口，**但延迟时间靠猜**，不解决根本 |
| **Outbox** | 把"要失效缓存"这件事**和业务改动写在同一个 DB 事务里**，再由后台任务去执行失效 | **要可靠性时用这个** |
| **CDC** | 订阅 DB 的变更日志（binlog / WAL）驱动失效 | 链路复杂，但**完全不侵入业务** |

【推导】**Outbox 的想法值得记牢**：

> **"改 DB"和"删缓存"做不到同一个事务，那就把"删缓存"这件事变成一条 DB 记录——它先和业务改动同一个事务落库，再异步执行。**

**这把"跨系统原子性"问题转化成了"我自己的事一定要做"的问题**，而后者是可以用本地事务保证的。

【事实】**EnergyOps 用的就是这个思路**——**不用"提交完顺手删 Redis"，因为 PG 的提交和 Redis 的删除不可能构成同一个 ACID 事务**。

### 3. 三类经典事故

::figure cache-problems.svg | 穿透 击穿 雪崩的区别与对策 | 三者都是"缓存没挡住请求"，区别在为什么没挡住

#### 3.1 各自的定义【事实】

| 事故 | 根因 | 现象 |
|---|---|---|
| **穿透** | 查的键**根本不存在**，缓存和 DB 都没有 | 每个请求都落到 DB，**且永远不命中** |
| **击穿** | **一个**热点键刚好过期 | 大量并发**同时**发现未命中 → 同时查 DB |
| **雪崩** | **一大批**键同一时刻过期，或 Redis 整体故障 | **全量**请求打到 DB |

**最简记法**：

```
穿透 = 不存在
击穿 = 一个热点没了
雪崩 = 一大批同时没了
```

#### 3.2 对策（每条都对应根因）

| 事故 | 对策 | 为什么有效 |
|---|---|---|
| **穿透** | **空值也缓存**（短 TTL） | 让"不存在"也有缓存命中，不再落到 DB |
| | **布隆过滤器前置** | **在缓存之前**就判断"这个键一定不存在"，直接挡掉 |
| **击穿** | **互斥重建**（single-flight）：只放一个请求去查 DB，其他等待或读旧值 | 把 N 个并发压成 1 个 |
| | **逻辑过期**：缓存不设真实 TTL，值里带过期时间；发现过期就**异步重建**，期间返回旧值 | 用"短暂返回旧值"换"DB 不被冲" |
| **雪崩** | **TTL 加随机抖动** | 把"同一秒过期"摊成"一段时间内陆续过期" |
| | **多级缓存**（本地 + Redis） | 减少 Redis 整体故障的影响面 |
| | **限流降级** | DB 是最后一道防线，**必须能扛住"缓存全挂"的流量**（或直接拒绝） |

【推导】**三类事故的共同根因是一句话**：

> **"缓存没挡住请求，于是请求全落到 DB。"**

**而 DB 的容量是有限的**——所以对策的本质都是**"控制落到 DB 的请求量"**，而不是"把缓存修好"。

### 4. 还有三个容易被忘掉的工程问题

| 问题 | 是什么 | 处理 |
|---|---|---|
| **热 key** | 单个键的访问量极大，**集中在一个分片上** | 本地缓存、key 打散（加随机后缀分片）、读写分离 |
| **big value** | 单个值太大（几十 KB 到几 MB） | 拆分成多个键、压缩、改用 Hash 分字段取；**大 key 的 `DEL` 会卡住单线程**（[[母题-R1-Redis数据结构与选型]]） |
| **跨租户 key 设计** | 多租户共用一套 Redis | key 带租户前缀、**权限隔离**、避免同名前缀互相淘汰 |

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "先删缓存再写 DB 可以保证一致" | 【推导】**错的，而且比反过来更糟**：中间的读会把旧值**写回缓存长期保留**（2.1） |
| "缓存和 DB 可以用事务保证强一致" | 【推导】**不可能**——两个独立系统没有共同事务。**目标是"最终一致 + 可接受的不一致窗口"** |
| "有了缓存就不怕 DB 挂了" | 【取舍】缓存平时**替你挡住了流量**；一旦缓存整体故障，**全部流量会瞬间倒向 DB** —— 这正是雪崩的第二种成因。**所以必须准备限流降级** |
| "给所有 key 设一样的 TTL 最省事" | 【推导】**这正是雪崩的成因**。TTL 要加**随机抖动** |
| "缓存永不过期就没事了" | 【取舍】永不过期意味着**永远不会自愈**——一旦写入不一致，脏数据留到永远。**TTL 是兜底，不是可选项** |
| "空值缓存会浪费内存，不如不做" | 【取舍】短 TTL 的空值缓存**正是为了防穿透**；成本是一个短命的小 key，收益是 DB 不被无效请求打 |

## 二、自测

**Q1（计算）**：10 万个 key 在同一时刻被创建，TTL 都设 **3600 秒**。

问：它们会在什么时候过期？如果给 TTL 加 **0–600 秒的随机抖动**，过期请求的峰值从多少降到多少？

**A1**：

- **不加抖动**：10 万个 key **在同一秒过期** → 那一秒 DB 突然收到 **约 10 万 QPS**（如果这些 key 都有人在读）
- **加 0–600 秒抖动**：过期时间散布在 600 秒的窗口里 → 峰值 = 100,000 / 600 ≈ **167 QPS**

**峰值降低约 600 倍。**

【推论】**加抖动是一行代码的事，但不做就是一次事故。** 这就是"雪崩"最典型的成因——**不是有人攻击，而是自己的代码把过期时间对齐了**。

**波动提醒**：如果这 10 万个 key 是"每天凌晨批量预热"生成的，那它们**天然会在同一秒过期**——这种场景**必须**加抖动。

**Q2（判读）**：下面三个现象分别属于穿透、击穿还是雪崩？各自的直接对策是什么？

① 有人用 `id=-1`、`id=99999999` 这类不存在的 ID 高频请求接口
② 首页那一个商品缓存刚过期，一瞬间数据库 CPU 打满
③ 服务重启后批量预热了缓存，2 小时后数据库周期性挨打

**A2**：

| 现象 | 类型 | 对策 |
|---|---|---|
| ① 不存在的 ID | **穿透**（键根本不存在） | 空值缓存（短 TTL）+ 布隆过滤器前置 |
| ② 单个热 key 刚过期 | **击穿** | **互斥重建**（只放一个请求去查 DB）/ 逻辑过期 |
| ③ 批量预热的 key 同时到期 | **雪崩** | **TTL 加随机抖动** + 多级缓存 + 限流降级 |

【注意③】它暴露了一条容易忽略的规律：**批量预热 = 批量同时过期**。**所以"批量写入缓存"的代码，必须同时"批量加抖动"。**

**Q3（计算）**：一个热点 key 承载 **10 万 QPS**。某时刻它过期了，此时并发请求全部未命中。后端 DB 的上限是 **5000 QPS**。

问：不用保护会发生什么？加了"互斥重建"之后，DB 收到多少请求？

**A3**：

- **不保护**：10 万 QPS 全部落到 DB → **是 DB 上限的 20 倍** → 大概率把 DB 打挂（而 DB 一旦挂了，**所有**接口都受影响，不只是这个 key）
- **加互斥重建**：只有**一个**请求被放行去查 DB，其他请求**等待它重建完成或直接读旧值** → DB 压力从 10 万降到 **约 1**

【推论】**这就是"单个热点键能打挂整个系统"的机制**——**它不是因为请求多，而是因为"同时发现未命中"。** 加锁/互斥的成本，远低于 DB 挂掉的成本。

**Q4（纠错）**：下面这段话哪里错了？

> "缓存一致性很好解决：写数据的时候先删缓存、再更新数据库，这样读请求就会去数据库拿最新的。"

**A4**：**这个顺序是错的，而且比反过来更糟。**

**问题出在 ① 和 ② 之间的窗口**：

```
T1: 线程 A 删除缓存
T2: 线程 B 读缓存 → 未命中 → 从 DB 读到【旧值】
T3: 线程 A 更新 DB（现在 DB 是新值了）
T4: 线程 B 把【旧值】写回缓存     ← 脏数据被写进缓存
```

**结果**：缓存里留着旧值，**而且可能长期留着**（如果没设 TTL）。

**正确做法是反过来（Cache Aside）**：

```
① UPDATE db
② DEL cache
```

这样并发读**最坏只是读到一次旧值**，而**不会把旧值写进缓存长期保留**。

【补充】**即便用了正确顺序，仍有缺口**：② 失败时缓存就是脏的。**所以必须配 TTL 兜底，或者上 Outbox 保证"删缓存"这件事一定会被执行。**（EnergyOps 用的就是后者。）

**Q5（纠错）**：下面这段话哪里错了？

> "只要引入 Redis，系统的可用性就更好了，因为数据库挂的时候缓存还能扛。"

**A5**：**这句话把"平时"和"故障时"搞反了——引入缓存反而增加了一个故障面。**

**平时**：缓存**替你挡住了大部分读流量**，DB 很轻松。✅

**缓存整体故障时**：**被挡住的那部分流量会瞬间全部倒向 DB**。假设原本 10 万 QPS 里 95% 由缓存承接，缓存一挂 → DB 瞬间要接 **10 万 QPS**（原来只接 5000）。**结果往往不是"降级仍可用"，而是"DB 被连锁打挂"。**

【推论】**所以必须准备两件事**：

1. **限流降级**：DB 是最后一道防线，**要能主动拒绝请求**（宁可拒绝一部分，也不要全挂）
2. **多级缓存 / 本地缓存**：Redis 挂了还有一层本地缓存顶着

**准确说法**：**缓存提升的是"平时的吞吐"，它把故障风险从"缓存的可用性"转嫁成了"DB 的抗冲击能力"——所以缓存故障必须专门演练。**

## 三、面试输出（学完再看）

**一句话结论**：**数据库是权威状态，缓存是它的派生副本**——两个独立系统**没有共同事务**，所以只能追求"最终一致 + 可接受的不一致窗口"。写路径用 **Cache Aside（先写 DB 再删缓存）**，删除失败要靠 **TTL 兜底或 Outbox 保证**（EnergyOps 用 Outbox，因为 **PG 提交与 Redis 删除不可能构成同一个事务**）。三类事故的共同根因是"**缓存没挡住请求**"：**穿透 = 键不存在**（空值缓存 / 布隆过滤器）、**击穿 = 一个热点过期**（互斥重建 / 逻辑过期）、**雪崩 = 一大批同时过期**（**TTL 加抖动** / 多级缓存 / 限流降级）。

**恢复关键词**：缓存是派生数据 / DB 权威 / 没有跨系统事务所以做不到强一致 / 判据是"允许多大的不一致窗口" / 先写 DB 再删缓存 / **删缓存失败要有兜底（TTL 或 Outbox）** / 删比更新好（懒加载） / 穿透=不存在、击穿=一个热点、雪崩=一大批 / 空值缓存 + 布隆 / 互斥重建 / **TTL 加抖动** / DB 是最后一道防线要能限流 / 缓存故障会把流量倒给 DB

**核心不变量 / 主线**：
**缓存的价值是"用可接受的不一致，换吞吐与延迟"。** 一旦把缓存当权威状态、或追求强一致，就同时失去了它的价值和它的安全边界。所以判断任何一个缓存方案，先问两件事：**这是派生数据吗？能容忍多大的不一致窗口？**

**完整回答骨架**：缓存是派生数据、DB 是权威 → 为什么做不到强一致（没有跨系统事务）→ 四种写路径的对比（先删的坑 / Cache Aside / 删 vs 更新 / Outbox 与 CDC）→ 三类事故的定义与对策（按根因配药）→ 热 key / big value / 跨租户 key → 缓存故障时 DB 要能限流降级

**完整回答（口述稿）**：
先认前提：**数据库是权威状态，缓存是它的派生副本**，两个独立系统**没有共同事务**，所以只能追求"最终一致 + 可接受的不一致窗口"。

写路径用 **Cache Aside：先写 DB，再删缓存**——反过来会让并发读把旧值写回缓存并长期保留。为什么是删除而不是更新：**懒加载**，只在真有人读时才付重建成本，聚合值（如榜单）尤其不该每次写都重算。删除失败靠 **TTL 兜底 + 重试/对账**；要可靠性就上 **Outbox**（把"删缓存"变成一条 DB 记录，用本地事务保证一定会做——因为 **PG 的提交和 Redis 的删除不可能构成同一个 ACID 事务**，EnergyOps 用的就是 Outbox）。

三类事故的共同根因是"**缓存没挡住请求**"：**穿透 = 键不存在**（空值缓存 / 布隆过滤器）、**击穿 = 一个热点过期**（互斥重建 / 逻辑过期）、**雪崩 = 一大批同时过期**（**TTL 加抖动** / 多级缓存 / 限流降级）。击穿和雪崩的区别：前者是"一个热 key"，后者是"一大批"，对策也因此不同。

**分层要点**：
- **结论**：DB 是权威、缓存是派生；先写 DB 再删缓存；三类事故根因都是"缓存没挡住请求"。
- **推导链**：两系统无共同事务 → 只能最终一致 → Cache Aside 顺序 → 删而非更（懒加载）→ 失败靠 TTL/Outbox → 三类事故分类。
- **量化**：没有共同事务，所以强一致做不到；Outbox 把"一定会做"交给本地事务。
- **边界与常见误解**：先删缓存再写 DB 是错的（并发读会把旧值写回并长期保留）；预热也要加 TTL 抖动（否则预热即埋雷）；Redis Stream 有持久化但不能简单替代 Kafka。

**追问**（先说后看）

1. **先删缓存还是先写 DB？** —— **先写 DB 再删缓存**。反过来会让"并发读把旧值写回缓存并长期保留"。
2. **删缓存失败了怎么办？** —— **TTL 兜底**（让脏数据自己过期）+ **重试/对账**；要可靠性就上 **Outbox**（把"删缓存"和业务改动写进同一个本地事务）。
3. **为什么删除缓存而不是更新缓存？** —— **懒加载**：只在真有人读时才付重建成本；聚合值（如榜单）尤其不该每次写都重算。
4. **击穿和雪崩怎么区分？** —— **击穿是"一个热点键"，雪崩是"一大批同时失效"**。对策也因此不同：击穿靠**互斥重建**，雪崩靠**TTL 抖动**。
5. **缓存和 DB 能强一致吗？** —— **不能**（没有共同事务）。能做的是"最终一致 + 明确的不一致窗口 + 对账"。
6. **为什么项目里用 Outbox 而不是顺手删缓存？** —— **因为 PG 的提交和 Redis 的删除不可能构成同一个 ACID 事务**。把"删缓存"变成一条 DB 记录，才能用本地事务保证"这件事一定会做"。

**同类变体**

- 「什么时候不该加缓存？」——写多读少、强一致要求高（如余额扣减）、数据量小且 DB 本来就快
- 「缓存预热怎么做才不出事故？」——**预热就要加 TTL 抖动**（Q2 的 ③），否则预热即埋雷
- 「多级缓存怎么保持一致？」——**逐级 TTL 递减 + 失效从最上层开始广播**；或者接受"本地缓存有更长的窗口"
