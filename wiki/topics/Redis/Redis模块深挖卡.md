## 0. 模块边界（先写这个，防无限扩张）

**包含**：五种基础结构 + 四种扩展结构各自的场景与底层实现、为什么快（内存 + 单线程 + IO 多路复用）、数据怎么不丢（持久化 / 过期删除 / 内存淘汰）、缓存怎么用不出事故（一致性策略 + 穿透 / 击穿 / 雪崩 + 热 key / big value）。

**明确不包含**：

- **集群运维细节**（分片迁移、槽位重分配、哨兵选主细节）——只到"知道主从是异步复制、所以不保证强一致"

**边界判据**：**本卡只回答"该用哪个结构 / 为什么不能这么用 / 出了事故怎么定位"**。凡是"某参数具体取值调优"的，不进本卡。

## 5. 项目映射（三个项目逐个过）

### 5.1 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**缓存加速读取**（园区/表/指标的元数据）；**写路径用 Outbox 而不是"提交完顺手删 Redis"**
- 解决什么问题：**缓存是派生数据，DB 才是权威** —— 这条定位决定了"不一致时以谁为准"
- 踩过的坑：**把聚合结果当缓存读**——缓存里该放的是**元数据**（园区/表/指标定义），不是**业务事实**（用量、账单）。元数据陈旧最多是查询慢一点；业务事实陈旧会让**页面和月账单出现两套数字**，而结算必须只有一个权威口径
- 决策与取舍：**为什么用 Outbox 而不是「提交完顺手删 Redis」**——因为 **PG 提交与 Redis 删除不可能构成同一个 ACID 事务**。先删缓存再提交，提交失败就留下脏缓存；先提交再删，删除失败就留下更久的脏缓存。**Outbox 把「删除」变成事务内可提交的一条事实**，再由异步消费者执行，失败可重试、可审计

- 对应母题：【R3】

### 5.2 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**权限与语义层的缓存**（口径、指标、粒度这类读多写少的数据）；**限流与短期去重**
- 解决什么问题：**权限相关的数据能不能缓存？** —— 能，但**必须有明确的失效路径**（权限变了要能立刻失效，否则是安全问题不是性能问题）
- 踩过的坑：**权限数据一进缓存，撤权就不再是即时的**——TTL 没到期前，已经失去权限的人照样能命中。**这是安全问题，不是性能问题**，不能用「缓存总会过期」搪塞
- 决策与取舍：**分界线是「陈旧的后果是慢还是错」**。口径、粒度、常用指标这类，陈旧几分钟只是体验问题 → 可缓存；**行级权限、租户归属、字段可见性一秒都不能陈旧** → 所以它们**不作为缓存值**，而是作为**召回前的过滤条件每次重新求值**（[[母题-G2-向量与关键词的混合检索]] 的「权限必须在召回前生效」在缓存侧的同一件事）

- 对应母题：【R3】

### 5.3 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**短期去重 / 限流 / lease 归属**（`archive/study-courses/09` 明确写了"Redis 用 Cache Aside、限流或短期去重，但不把缓存当最终事实"）
- 解决什么问题：**动作有副作用，所以 Redis 只能做"辅助判断"，不能做"最终裁决"** —— 最终裁决必须是 DB 的约束或条件更新
- 踩过的坑：**用 Redis 判断「这笔动作做过没有」**——Redis 重启、主从切换、或单纯的过期，都会让同一个幂等键被判成「没做过」→ **重复执行副作用**。而超时重投在 Agent 场景里是常态，不是异常
- 决策与取舍：**区别在「丢了会怎样」**。**短期状态**（限流计数、去重窗口、Worker lease）丢了最多是多做一次检查，可恢复、可重来 → 放 Redis 划算；**任务状态与幂等判断**丢了就不知道「做过没有」，这是**正确性问题** → 必须落 PG 的唯一约束（[[母题-P19-唯一约束与UPSERT]]）。**Redis 只能做辅助判断，不能做最终裁决**

- 对应母题：【R3】

## 8. 题级答案（「本主线的题」翻转卡背面 · 先说后翻）

> 题号与第 4 节题单一一对应。**必背**题写成能直接说出口的一段话；**理解 / 了解**题写 1–3 句。
> 翻转卡背面先给这道题的答案，再挂上「所属母题的完整回答（口述稿）」与单卡入口——两段合起来才是深挖。

### 1 （必背）
五种基础结构按"**要不要唯一 + 要不要顺序**"选：**String**（字符串/整数/位图，最通用）、**List**（有序可重复，队列/栈）、**Hash**（字段映射，对象）、**Set**（无序唯一，去重与集合运算）、**ZSet**（按 score 有序唯一，排行榜/延迟队列）。

四种扩展：**Bitmap**（二值标记，签到/活跃位）、**HyperLogLog**（估算 UV，标准误差约 0.81%，换的是固定小内存）、**Geo**（经纬度附近查询，底层是 ZSet）、**Stream**（可持久化的消息流，带消费组）。

### 2 （必背）
Set 无序、成员唯一，能做去重和交并差；ZSet 每个成员带一个 **score**，**按 score 有序且成员仍唯一**。多出来的能力是"按分数取范围、取排名"——排行榜、延迟队列（score 存到期时间戳）、滑动窗口限流（score 存时间戳 + `ZREMRANGEBYSCORE` 清窗口外）都是这条能力的变形。

底层也因此不同：ZSet 是"**跳表 + 哈希表**"——哈希表支撑按成员查分数，跳表支撑按分数取范围与排名。

### 3 （必背）
**跳表 + 哈希表双结构**：哈希表做 member → score 的 O(1) 查找，跳表做按 score 的范围查询与排名。为什么两个都要——单靠哈希表拿不到有序性，单靠跳表按成员查分数要遍历。

跳表本身是"**多层有序链表 + 随机层高**"：层高在插入时随机决定，不需要像平衡树那样重平衡，范围查询顺着最底层链表顺序扫就行。

### 4 （理解）
跳表是在有序链表上**加多层索引**：第 0 层是全量有序链表，上层是下层的抽样；查找从最高层开始向右、走不动就下降一层，等效于二分。

层高是**插入时随机决定**的（按 p 的几何分布、Redis 有最大层数上限），不需要重平衡——这正是它相对平衡树的工程优势。代价是每个节点平均多占几个指针，用空间换"不重平衡"。

### 5 （必背）
**不是快慢，是约束变了。** B+ 树的核心优势是"把定位的 IO 次数从行数降到树高"——这个优势只在**磁盘**上成立；Redis 数据在内存里，没有"一次 IO 读一页"这个约束，扇出与页对齐这些设计就白付了。

跳表在内存里更合适：不需要重平衡、范围查询顺着底层链表顺序扫（天然有序）、实现简单。一句话：**B+ 树是为磁盘设计的，跳表是为内存设计的**；再加一条 Redis 特有的约束——单线程，常数和实现复杂度都要尽量小。

### 6 （理解）
C 字符串三个问题：① **O(n) 求长度**（每次 strlen 都要遍历）；② **二进制不安全**（遇 `\0` 截断，存不了 protobuf / 图片）；③ **拼接容易缓冲区溢出**。

Redis 的 SDS 自带 `len` 和 `free` 字段：O(1) 取长度、二进制安全，并用**空间预分配 + 惰性释放**减少内存重分配次数；同时保留 `\0` 结尾以兼容部分 C 字符串函数。

### 7 （理解）
字典有**两张哈希表 + 一个 rehash 下标**，扩容不是一次性搬完，而是**渐进式 rehash**：每次增删改查顺手把下标指向的桶搬过去，新写入直接落到新表。

所以**读请求会同时查两张表**（先旧后新），单次查找成本略增，但不会被一次性阻塞——这是"Redis 单线程，所有设计都在避免长时间阻塞主线程"这条约束的直接后果。

### 8 （必背）
快在三点：**数据在内存**、**命令执行单线程**（无锁竞争、无上下文切换、单条命令天然原子）、**IO 多路复用**（epoll 一次问出成千上万连接里哪些就绪）。

**是单线程还是多线程**：6.0 之后**网络 IO 是多线程**，**只有命令执行仍是单线程**；后台任务（bgsave、异步删）另有线程/子进程。

单线程的代价必须一起说：**一条慢命令卡住所有人**（`KEYS *`、大 key 的 `DEL`），所以才有慢命令禁用清单和大 key 治理。

### 9 （理解）
**Bitmap**：单个用户的二值标记（签到、活跃位），极省空间。**HyperLogLog**：估算 UV，**标准误差约 0.81%**，换的是固定小内存，且取不出单条成员。**Geo**：附近的人/网点，底层是 ZSet。**Stream**：可持久化的消息流，支持消费组与确认，适合**中小规模**消息——保留策略、分区、重放、运维生态与专业 MQ 差距明显，不能因为"已经用了 Redis"就默认替代 Kafka。

### 10 （必背）
**RDB**：定时快照，记的是"结果"——文件小、恢复快，但**两次快照之间宕机会丢**。**AOF**：追加每条写命令，记的是"过程"——`everysec` 最多丢约 1 秒，但文件大、恢复慢，所以有 **AOF 重写**把历史压成当前结果。生产通常**两者都开**：RDB 做冷备与快速恢复，AOF 保最多丢 1 秒（4.0 后还有混合持久化）。

两条必须说清：`bgsave` 并非无代价（fork 复制页表时的短暂停顿 + COW 让快照期间内存上涨）；而且**持久化不是备份**——误删、误 `FLUSHALL` 同样会被记进 AOF，所以要另有备份策略。

### 11 （必背）
两件不同的事：**过期删除**是"这个 key 到点了怎么处理"——**惰性（访问时判）+ 定期抽样**，不是立即删；**内存淘汰**是"内存不够了踢谁"——8 种策略，按"在哪个池子挑（allkeys / volatile）× 用什么算法（LRU / LFU / random / 不淘汰）"组合。

`noeviction` 是写报错；注意 `volatile-*` 在**没有 TTL 的 key** 时等同 `noeviction`。为什么不做精确 LRU：精确 LRU 要维护全量链表、每次访问都移动节点，开销大；采样近似效果接近而代价小得多。

### 12 （理解）
不会。两种策略配合：**惰性删除**（访问这个 key 时才判过期并删）+ **定期抽样删除**（每隔一段时间随机抽一部分 key 检查清理）。

不立即删的原因还是那条约束——Redis 单线程，不能为了清理去扫全表或给每个 key 起定时器，那会阻塞主线程。所以**实际内存占用可能高于"所有未过期 key 的大小"**，这也是要看 `used_memory` 而不是只算逻辑数据量的原因。

### 13 （了解）
不能保证强一致：主从复制是**异步**的，主库写入后不等从库确认就返回，所以主库宕机时可能丢最后一段未同步的写；集群（分片）解决的是容量与吞吐的横向扩展，同样不提供跨节点强一致。

直接后果：在 Redis 上做锁要额外处理——这正是"Redis 分布式锁在主从切换时会丢锁"的根因。

### 14 （必背）
先认前提：**数据库是权威状态，缓存是它的派生副本**，两个独立系统**没有共同事务**，所以只能追求"最终一致 + 可接受的不一致窗口"。

写路径用 **Cache Aside：先写 DB，再删缓存**——反过来会让并发读把旧值写回缓存并长期保留。删除失败靠 **TTL 兜底 + 重试/对账**；要可靠性就上 **Outbox**（把"删缓存"变成一条 DB 记录，用本地事务保证一定会做——因为 PG 的提交和 Redis 的删除不可能构成同一个 ACID 事务）。

为什么是删而不是更新：**懒加载**，只在真有人读时才付重建成本，聚合值（如榜单）尤其不该每次写都重算。

### 15 （必背）
共同根因是"**缓存没挡住请求**"，但形态不同：**穿透** = 键根本不存在，每次都打穿 → 空值缓存 + 布隆过滤器；**击穿** = 一个热点键刚好过期，瞬间全打到 DB → 互斥重建（单飞）或逻辑过期；**雪崩** = 一大批 key 同时过期 → **TTL 加随机抖动** + 多级缓存 + 限流降级。

击穿和雪崩的区分：**前者是"一个热 key"，后者是"一大批"**，对策也因此不同。

### 16 （理解）
该设，但要认清 **TTL 的角色是给"写时失效"兜底**，不是主要机制——它给的是"最多旧多久"的上限。

设多少按**最苛刻的用途**定：展示路径可以长（旧 60 秒无所谓），判断路径基本是 0（余额、库存一秒都不能旧）。另外**必须加随机抖动**，否则一批 key 会集体到期——**预热尤其要加抖动，否则预热即埋雷**。

### 17 （必背）
**大 key 是体积问题**：危害来自"命令执行单线程"——删一个 200 万 field 的 Hash 会阻塞约 200 ms，这期间所有请求延迟都 +200 ms。发现用 `--bigkeys` / `MEMORY USAGE`（采样估算 + 逐个确认）；处理用 **`UNLINK`**（异步回收，内存是逐步释放的）或 **`HSCAN` / `SSCAN` 分批删**。

**热 key 是频率问题**：危害来自"集群里一个 key 只属于一个分片"，**加节点完全无效**；"单分片打满、其他分片闲置"就是它的签名。发现靠客户端/代理层统计。处理要**先分读热还是写热**：读热用本地缓存（命中 95% 能把 3 万 QPS 降到 1500）或打散成多个副本 key；**写热打散无效**（一次写变 N 份），只能本地聚合 / 队列串行 / 换结构。

一箭双雕的动作：**按业务维度把大 key 拆成一堆小 key**。

### 18 （理解）
**限流**：固定窗口/滑动窗口计数（`INCR` + `EXPIRE`，或用 ZSet 存时间戳、`ZREMRANGEBYSCORE` 清窗口外实现滑动窗口），以及令牌桶；要在边界上做，失败要有明确的 429 语义。

**幂等去重**：请求带唯一键，`SET key NX EX` 成功即首次、失败即重复（这是幂等不是锁）；去重键要有 TTL。注意：参与判断的场景（余额、库存）要回到**数据库的唯一约束**——Redis 的幂等是尽力而为，不是事务保证。

### 19 （必背）
三个坑：① **主从异步复制会丢锁**——主库加了锁还没同步就宕机，切主后另一个客户端又能加上；② **释放锁不能裸 `DEL`**——你过期后别人拿到了锁，你这时 `DEL` 删的是别人的，等于一次删锁动作制造了双重执行，**必须校验值**（GET 比对 + DEL，用 Lua 保证原子）；③ **TTL 没有安全值**——业务因 GC 停顿 / 时钟漂移 / 网络分区还没跑完，锁就过期了，出现两个持有者。

真正的解法是把安全性搬到**资源侧**：**fencing token**（发锁时给单调递增号，写入由存储校验"只接受更大的号"）。但更该先问：**我要的是"不同时跑"还是"不重复执行"？** 后者用**幂等键 + 唯一约束**就够了——更便宜、不引入新依赖，RuleArena 连锁都没用。

### 20 （了解）
不能简单替代。Stream 有持久化（走 AOF/RDB）、消费组和确认，支撑**中小规模**没问题；但**保留策略、分区、重放、运维生态**与专业 MQ 差距明显。

判据是按可靠性需求选：要多副本分区、长期保留、高吞吐重放就上 Kafka；只是需要一个轻量的、已经在 Redis 里的流，Stream 够用。**不能因为"已经用了 Redis"就默认替代。**

### 21 （必背）
判据三问：**丢了能不能重建**、**旧一段时间（几秒）能忍吗**、**会不会因为读到旧值做错事**。任何一问不过，就不是"缓存策略要调"，而是**放错地方了**。

核心区分：**派生数据**（榜单、统计、配置副本）可以缓存；**权威状态**（订单、账本、余额、库存）不能只放缓存。而且同一份数据的两条路径容忍度不同：**展示可以旧 60 秒，判断一秒都不能旧**——余额的正确做法是"显示走缓存、扣减用 `UPDATE ... WHERE balance >= ?` 下沉到数据库"。

### 22 （必背）
不行，三条理由：AOF `everysec` 最坏丢约 1 秒、RDB 窗口更大；**异步复制**会让主库宕机时丢最后一段；还有**主动淘汰**（内存满时按策略踢数据）和误操作（`FLUSHALL` 也会被记进 AOF）。

一句话：**持久化保证的是"重启后数据大多还在"，不是"它是唯一一份"。** 权威状态必须在数据库，Redis 只放可重建的派生数据与有 TTL 的临时状态。

### 23 （必背）
只放**派生数据**。因为缓存与数据库**没有共同事务**，放进缓存的那一刻它就可能变旧——派生数据旧一点可以重建，权威状态旧一点就会让人做错决定。

配套两笔账：① **缓存全挂时回源压力放大 `1/(1−命中率)` 倍**（命中率 95% 就是 20 倍，足以打穿数据库，所以限流与降级必须提前设计）；② **TTL 是给写时失效兜底，不是主要机制**，且要加抖动。

一致性要"不骗人"，说清三件事：上限是多少、失败怎么办、哪些路径不能容忍。

### 24 （理解）
能继续，但必须**提前设计**，不是临场发挥。先算回源放大 `1/(1−命中率)`（95% → 20 倍），再按"**限流 → 降级 → 本地缓存兜底**"设计闸门——绝不能让"未命中"直接等于"打数据库"。

降级的目标要明确：**保住可用性，不是保住质量**；而且要**可观测**（降级本身要打点报警，不知道自己在降级比降级更危险）。本地缓存（进程内）可以用，一致性可量化——TTL 50 ms 就意味着"最多旧 50 ms"，判据仍是那三问。
