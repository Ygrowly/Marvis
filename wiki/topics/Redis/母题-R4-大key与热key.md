# 母题 R4 · 大 key 与热 key：怎么发现、怎么拆、为什么会同时打穿三样东西

**题目**：某天 Redis 出现周期性卡顿，`SLOWLOG` 里出现一条"命令耗时 300 ms"，但那条命令只是 `DEL`。另一次，集群扩容到 10 个分片之后，整体 QPS 上不去——监控显示**只有一个分片的 CPU 打满**。这两件事的根因分别是什么？

**母题**：大 key 与热 key 各是什么、为什么危险、怎么发现和拆。

## 一、教材

### 1. 前提：两个维度，两种打法

#### 1.1 先把两个概念分开【事实】

| | **大 key** | **热 key** |
|---|---|---|
| 维度 | **体积 / 元素个数** | **访问频率** |
| 典型形态 | 一个 Hash 里有几百万元素；一个 String 有几 MB | 一个 key 每秒被读几十万次 |
| 危险在哪 | **一次性操作要耗很多时间/带宽** | **单点压力集中** |
| 打穿什么 | **内存、网络带宽、主从复制、集群迁移** | **单个分片 / 单个实例的 CPU** |
| 救法 | **拆开 + 分批操作** | **打散 + 本地挡** |

【推导】**这两个问题经常被混着讲，但它们的解法完全不同**：

```
大 key  → 问题是"一次操作太大"，解法是【把大操作变小操作】
热 key  → 问题是"所有请求都找同一个点"，解法是【让请求分散到多个点】
```

#### 1.2 两个共同前提：单线程 + 单分片【推导】

【推导】**为什么这两个问题在 Redis 里特别严重**，取决于两个结构性事实：

```
① Redis 的【命令执行是单线程】的
   → 一条慢命令会挡住后面所有命令（不是"这一条慢"，是"全体排队"）
   → 所以"一条 300ms 的 DEL"= 这 300ms 内所有请求的延迟都 +300ms

② 集群里【一个 key 只属于一个分片】
   → 热 key 的压力无法被自动摊到其他分片
   → 所以"加节点"对热 key 是无效的（自测 Q2 会算）
```

【推导】**这两条合起来就是本卡的全部逻辑**：

> **大 key 的危险来自 ①（单线程被一条大命令挡住）；热 key 的危险来自 ②（单分片被打满）。**

**到这里你应该能回答**：为什么"Redis 单线程"这个前提，是理解大 key 危害的关键？

### 2. 大 key：把大操作拆成小操作

#### 2.1 危害的四个面【事实】

::figure redis-bigkey-hotkey.svg | 大 key 与热 key 的两个维度、危害与解法 | 左：单线程被一条大命令挡住；右：热 key 在集群里打不散，加节点无效

【事实】**大 key 不止"占内存"这一个问题**：

| 面 | 机制 |
|---|---|
| **① 操作阻塞** | `DEL` 一个几百万元素的 Hash 要**同步释放所有元素**——期间单线程被占住 |
| **② 网络带宽** | 一次 `GET` 一个 5MB 的 String → 5MB 走一遍网络（还会打满网卡） |
| **③ 主从复制** | 大 key 的每次修改都要复制给从库 → **复制延迟被拉长**（[[母题-M14-主从复制与延迟]] 是同一问题） |
| **④ 集群迁移** | 槽位迁移时按 key 搬，**大 key 会让单个迁移卡住** |

【推导】**第 ① 条最能说明"单线程"的代价**：

```
假设一个 Hash 有 200 万个 field
  删除一个 field 约 100 ns 级（释放对象 + 更新结构）
  逐个释放：200 万 × 100 ns ≈ 【200 ms】
→ 这 200 ms 里，Redis 处理不了任何其他命令
→ 而这期间到达的所有请求，延迟都至少 +200 ms
```

**【注意：这 200 ms 不是"那一个请求慢"，而是"所有人都慢"】** ——这正是 1.2 ① 的后果。

#### 2.2 怎么发现【事实】

【事实】**三种手段，按成本从低到高**：

| 手段 | 做什么 | 注意 |
|---|---|---|
| **`redis-cli --bigkeys`** | 用 `SCAN` 采样扫描，报告各类型最大的 key | ⚠️ **它是采样估算，不是精确值**；对生产有压力，低峰期跑 |
| **`MEMORY USAGE <key>`** | 精确看单个 key 占多少内存 | 需要对可疑 key 逐个查 |
| **监控侧采样 + 慢日志** | 定期按比例扫一批 key 统计大小分布；看 `SLOWLOG` | **长期、低开销**，适合常态化 |

【事实】**判断"多大算大"没有统一阈值**，要按你的集群规格来定，常见的经验线：

```
String  > 10 KB 就要关注（单条命令的网络与延迟成本）
集合类  > 5000 个元素就要关注（一次全量操作的耗时）
集合类  > 1 MB 基本必须拆
```

#### 2.3 怎么拆【推导】

【推导】**两类处理，别混**：

| 场景 | 做法 | 关键 |
|---|---|---|
| **要删一个大 key** | **用 `UNLINK` 而不是 `DEL`** | 【事实】`DEL` 是**同步**释放（阻塞主线程）；**`UNLINK` 只把 key 从键空间摘掉，真正的内存回收交给后台线程** |
| **要慢慢清一个大的集合** | **`HSCAN` / `SSCAN` + 分批 `HDEL`** | 每次删一小批，让单线程有机会处理别的命令 |
| **要长期保留这份数据** | **按业务维度拆成多个 key** | 例如把"某设备全年数据"拆成"每天一个 key"——**把大 key 变成一堆小 key，顺带让访问也分散了** |

【推导】**"拆"这个动作有双重收益**（这一点最能体现设计感）：

```
拆之前：一个大 Hash，200 万 field
  删除 → 200 ms 阻塞；而且这个 key 落在【一个分片】上

拆成按天 365 个 key：
  删除 → 每个 key 只有 5000 field（几毫秒）；且 365 个 key 分到不同分片
  → 【既解决了大 key，也顺便缓解了单分片压力】
```

**到这里你应该能回答**：为什么"把大 key 按业务维度拆成小 key"比"优化删除方式"更根本？

### 3. 热 key：让请求分散到多个点

#### 3.1 危害：单分片打满，而且加节点无效【推导】

【推导】**热 key 的危害只有一个，但很硬**：

```
集群有 10 个分片，总容量 10 万 QPS，平均每分片 1 万
某个 key 独占 3 万 QPS
→ 它落到的那 1 个分片要承担 3 万 + 其它 key 的流量
→ 【那一个分片打满】，其余 9 个还有余量
→ 而扩容到 20 个分片？那个 key 还是只在一个分片上
→ 【加节点对这个 key 完全无效】
```

【事实】**这就是热 key 与"普通高负载"的本质区别**：**普通高负载靠水平扩展能解决，热 key 不能**——因为它违背了"水平扩展假设请求能均匀分布"这个前提。

#### 3.2 怎么发现【事实】

| 手段 | 说明 |
|---|---|
| **客户端埋点统计** | 在客户端记录 key 的访问频次（最直接，但要改代码） |
| **代理层 / SDK 中间件统计** | 如果有统一的数据访问层，在这里统计最自然 |
| **`MONITOR`（**高成本，别在生产常开**）** | 能看到实时命令流，但**会显著影响性能** |
| **采样分析** | 按比例采样命令流，估算 top key |
| **监控指标的"倾斜"** | 集群里**某个分片的 QPS/CPU 显著高于其他** —— 这本身就是热 key 的信号 |

#### 3.3 怎么解（三种，按成本递增）【取舍】

【取舍】

| 解法 | 做法 | 代价 |
|---|---|---|
| **① 本地缓存（多级缓存）** | 在应用进程内缓存这份数据（几十毫秒 TTL），**请求根本不落到 Redis** | **一致性变差**：各实例的值可能不同，且更新要广播或等 TTL 过期 |
| **② 打散成多个副本 key** | 把 `hot:key` 变成 `hot:key:0` … `hot:key:9`，**读时随机取一个**，把读压力摊到 10 个分片 | **写要写 10 份**（或缩短 TTL）；**读到的可能不一致**；key 数量变多 |
| **③ 只读副本 / 多副本读** | 读请求走多个副本实例 | 要额外的路由逻辑；主从延迟带来不一致 |

【推导】**选哪个看是"读热"还是"写热"**：

```
读热（绝大多数情况）→ ① 本地缓存最划算：连 Redis 都不用打
                   → ② 打散是退而求其次（不想引入本地缓存时）
写热（同一个 key 被高频写）→ 打散【没用】（写要写 N 份，压力不减）
                        → 只能：本地聚合（攒批） / 队列串行 / 换数据结构
```

【推导】**"写热"这一点值得单独记住**：**热 key 的"打散"只对读有效**，因为一次写会变成 N 次写。**写热要靠"聚合"或"串行"，和 [[母题-L2-锁的粒度与临界区]] 里"热键分段救不了、要换方案"是同一个结论。**

【事实】**RuleArena 的容量文档里给 Redis 只留 256~512MB**——**这种小规格下，"放到 Redis 里的东西必须是有选择的"**，这正是 [[母题-R5-缓存的边界]] 要回答的问题。

**到这里你应该能回答**：为什么"热 key 打散"只对读有效，对写无效？

### 4. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "删一个大 key 和删小 key 一样" | 【事实】**不一样**。`DEL` 是**同步**释放——删一个 200 万元素的 Hash 会让**整个实例阻塞约 200 ms**。**要用 `UNLINK`（异步回收）或 `HSCAN` 分批删** |
| "集群加节点就能解决热 key" | 【推导】**不能**。集群里一个 key 只属于一个分片，**热 key 的压力不会因为加节点而摊开**——这正是热 key 与普通高负载的本质区别 |
| "热 key 打散一下就行了" | 【推导】**只对读有效**。一次写会变成 N 份写，**写热打散反而更糟**；写热要靠"本地聚合 / 队列串行 / 换结构" |
| "大 key 的问题就是占内存" | 【事实】占内存只是其中之一。**更要紧的是单线程被阻塞、网络带宽、主从复制延迟、集群迁移卡住**这四样 |
| "用 `--bigkeys` 扫一遍就知道所有大 key" | 【事实】**它是采样估算**，可能漏；而且**对生产有压力**，应该在低峰跑。要精确得用 `MEMORY USAGE` 逐个看 |
| "`MONITOR` 能直接找出热 key" | 【事实】**能看，但代价大**——它会把每条命令都推给客户端，**生产常开等于自伤**。热 key 更适合在客户端/代理层统计，或用"分片倾斜"这个信号去发现 |
| "本地缓存会有一致性问题，所以不能用" | 【取舍】**一致性可以量化**：本地缓存放 50 ms TTL，就意味着"最多旧 50 ms"。**对于那些本来就能容忍几秒延迟的数据，这 50 ms 根本不算问题**——**不要用"有一致性问题"一票否决** |
| "大 key 拆分之后就没问题了" | 【推导】拆完要检查两件事：**① 会不会把一个 key 的请求集中到多个 key 上造成新的热点 ② 跨 key 的原子操作是否还需要**（拆开之后原来"一个命令搞定"的可能要多个命令 + 事务） |

## 二、自测

**Q1（计算）**：某 Redis 里有一个 Hash，包含 **200 万个 field**。运维执行 `DEL` 删它。已知**逐个释放 field 的成本约 100 ns**。

问：① 这次 `DEL` 会让实例阻塞多久？② 如果当时 QPS 是 5000、每个请求平均耗时 0.2 ms，这期间会积压多少请求？③ 换成 `UNLINK` 会怎样？

**A1**：

```
① 阻塞时间 ≈ 200 万 × 100 ns = 0.2 s = 【约 200 ms】
   ★ 注意：这是【同步】释放所有元素的时间，单线程期间处理不了别的命令

② 该 200 ms 内到达的请求量：
   5000 QPS × 0.2 s = 【1000 个请求】
   而这 1000 个请求的延迟都会【至少 +200 ms】
   → 表现：一个 P99 尖刺；如果是核心接口，就是一次告警
```

③ **换成 `UNLINK`**：

```
UNLINK 只把 key 从键空间摘掉（O(1) 级操作），
真正的内存回收交给【后台线程】
→ 主线程几乎不阻塞
→ 这 1000 个请求不受影响
```

【这一步在验证什么】验证 2.3：**大 key 的删除必须避开"同步释放"**——`UNLINK` 就是为这个场景提供的（Redis 4.0+）。

**这里有一个可以加分的追问答案**：*"那 `UNLINK` 之后内存是不是立刻降下来？"* —— **不是立刻**。它只是把回收挪到后台，**内存会在随后的几百毫秒内逐步释放**。所以监控上会看到"删除成功但内存缓慢下降"——**这是正常现象，不是没删掉**。

**Q2（计算）**：集群有 **10 个分片**，单分片能扛 **1 万 QPS**。总请求 **10 万 QPS**，其中**一个 key 独占 3 万 QPS**。

问：① 会发生什么？② 扩容到 20 个分片能解决吗？③ 打散成 10 个副本 key 呢？④ 如果这是"写"热（同一个 key 每秒被写 3 万次）呢？

**A2**：

```
① 其他 9 个分片：平分剩下 7 万 → 每个约 7.8 千（接近上限但没满）
   热 key 所在的分片：3 万 + 分摊到的量 ≈ 3.8 万
   → 单分片上限 1 万 → 【这一个分片被打爆】，其余分片闲置
   → 表现：整体 QPS 上不去 + 单个分片 CPU 100%
```

② **扩容到 20 分片：解决不了**。那个 key 还是只落在一个分片上，**该分片仍然是 3.8 万 > 1 万**。**加节点只摊薄了其他 key，没动热点。**

③ **打散成 10 个副本 key（读时随机取一个）**：

```
每个副本承担 3 万 / 10 = 3000 QPS
如果这 10 个副本被哈希到不同分片 → 每片只多 3000 → 【全部在容量内】
→ 有效
```

④ **如果是写热，打散无效**：

```
3 万 QPS 的写 → 打散成 10 份意味着【写 10 次】= 30 万次写
→ 总压力反而涨了 10 倍
→ 正确解法：① 本地聚合（在应用内攒批，每 N 次汇总写一次）
            ② 队列串行（收进队列单消费者处理）
            ③ 换结构：能累加的用 INCR 类操作；能 Hash 分片的按业务维度拆
```

【这一步在验证什么】验证 3.1 与 3.3：**热 key 不能靠扩容解决；打散只对读有效，写热要靠聚合或串行。**

**Q3（判读）**：某服务在应用进程内加了一层"本地缓存"（TTL 50 ms）来挡一个热 key。

问：① 它能把 Redis 的读压力降多少（假设本地命中率 95%）？② 代价是什么？③ 什么数据可以这样放、什么不可以？

**A3**：

```
① 本地命中率 95% → Redis 只承接 5% 的请求
   原来 3 万 QPS 打 Redis → 现在【1500 QPS】
   → 降了 【20 倍】，热 key 问题基本消失
```

② **代价是"一致性上限"**：

| 代价 | 具体 |
|---|---|
| **读到的值最多旧 50 ms** | 这是可量化的——不是"有一致性问题"，是"旧不超过 50 ms" |
| **不同实例可能读到不同的值** | 各自独立缓存，更新时刻不同 |
| **更新后不会立刻生效** | 要等 TTL 过期或做广播失效（增量复杂度） |
| **内存占用分散到每个实例** | 每台机器都要留这块内存 |

③ **判据（三问）**：

| 问题 | 能放本地缓存 | 不能放 |
|---|---|---|
| 丢了能不能重建？ | 能（是派生数据） | **不能（是权威状态）** |
| 旧 50 ms 能忍吗？ | 能（配置、字典、榜单、商品详情） | **不能（余额、库存、订单状态）** |
| 会不会因为旧值做错事？ | 不会（只用于展示） | **不会** ← **只要它参与判断，就不能容忍旧值 |

【这一步在验证什么】验证 3.3 与 4 的最后一条：**本地缓存的代价可以量化（旧不超过 TTL），所以决策不是"有没有一致性问题"，而是"能容忍多少延迟"**——这个口径同样适用于 [[母题-R5-缓存的边界]]。

**Q4（纠错）**：下面这段话哪里错了？

> "Redis 集群扩容之后 QPS 上不去，就是节点不够，再加几台就好了。热 key 也能一起解决。"

**A4**：**"再加几台就好了"和"热 key 也能一起解决"都错——而且后一句是方向性错误。**

**为什么加节点解决不了热 key**：

```
集群的分片规则是「key → slot → 节点」
→ 一个 key 永远只在一个 slot 上、只落在一个节点上
→ 你说这个 key 有 3 万 QPS，加多少个节点，它还是【只压在那一个节点】
→ 加节点只能摊薄【其他】key 的流量
```

**所以"单分片 CPU 打满、其他分片闲置"这个画面本身就是热 key 的签名**——看到它就该去找热点 key，而不是点"扩容"。

**热 key 的正确动作（三档）**：

| 档 | 做法 | 适用 |
|---|---|---|
| **① 本地缓存** | 进程内缓存 + 短 TTL，请求根本不落 Redis | **读热**（首选） |
| **② 打散副本** | `key:i` 随机取，摊到多个分片 | **读热**（不想改太多代码时） |
| **③ 聚合 / 串行** | 本地攒批、队列单消费者 | **写热**（打散无效） |

**另外要补一句限定**：**"扩容上不去"也可能是别的原因**——比如**单条命令本身很慢**（大 key 问题，不是热 key 问题）、**连接数/带宽打满**、**客户端侧瓶颈**。**先看"倾斜"还是"全体"**：全体高才是容量问题，单点高才是热 key——**这正是本卡把两个维度分开讲的原因。**

**准确说法**：*热 key 违背了"请求能均匀分布"这个水平扩展的前提，所以加节点无效。要看是读热还是写热：读热用本地缓存或打散副本，写热只能用聚合或串行。*

**Q5（纠错）**：下面这段话哪里错了？

> "delete 一个 key 很快的，`DEL` 和 `UNLINK` 只是写法不同，用哪个都一样。"

**A5**：**"很快"和"都一样"都错——`DEL` 和 `UNLINK` 的区别正好在于"快不快"。**

**【事实】两者的行为完全不同**：

| | `DEL` | `UNLINK` |
|---|---|---|
| 摘掉 key | 是 | 是 |
| **释放内存** | **同步**：在主线程里逐个释放元素 | **异步**：交给**后台线程**回收 |
| 大 key 的后果 | **阻塞整个实例**（Q1 算的 200 ms） | 主线程几乎不阻塞 |
| 成本 | O(元素个数) | **O(1) 级删除 + 后台 O(n) 回收** |

**为什么这件事在大 key 上特别重要**：**Redis 命令执行是单线程的**——**"释放 200 万个 field"这段时间里，别的命令一个都执行不了**。所以那 200 ms 不是"删得慢"，是"**整个实例停了 200 ms**"。

**还要纠正一个隐含误解**：**`UNLINK` 之后内存不是立刻降**——因为回收发生在后台，**内存会在随后一段时间内逐步释放**。**监控上看到"删了但内存没马上掉"是正常的。**

**准确说法**：*`DEL` 是同步释放（会阻塞单线程，大 key 上能到几百毫秒）；`UNLINK` 只摘 key、把内存回收交给后台线程，但内存是逐步释放的。删大 key 应该用 `UNLINK`，或者用 `HSCAN` 分批删。*

## 三、面试输出（学完再看）

**一句话结论**：**大 key 与热 key 是两个维度的问题**——大 key 是**体积**（危害来自"Redis 命令执行单线程"，一条大命令会把所有人一起挡住；删一个 200 万 field 的 Hash 能阻塞约 200 ms，**所以要用 `UNLINK` 或 `HSCAN` 分批**）；热 key 是**频率**（危害来自"集群里一个 key 只属于一个分片"，**加节点完全无效**，只对读有效——**读热用本地缓存（命中 95% 就把 3 万 QPS 降到 1500）或打散成多个副本 key；写热只能靠本地聚合、队列串行或换结构**）。**发现手段分别是 `--bigkeys`/`MEMORY USAGE`（采样估算 + 逐个确认）和客户端/代理层统计 + "单分片倾斜"这个信号**；`MONITOR` 能看但代价大，别在生产常开。**而"按业务维度拆成大堆小 key"是一箭双雕的动作**：既解决了大 key，也顺带分散了访问。

**恢复关键词**：大 key = 体积 / 热 key = 频率 / **单线程 → 一条慢命令挡住全体** / **一个 key 只在一个分片 → 加节点对热 key 无效** / `DEL` 同步阻塞 vs **`UNLINK` 后台回收** / `HSCAN` 分批删 / `--bigkeys` 是采样估算 / `MEMORY USAGE` 精确 / 热 key 发现靠客户端统计 + **分片倾斜** / `MONITOR` 代价大 / **读热：本地缓存 > 打散副本** / **写热：聚合 / 串行（打散无效）** / 按业务维度拆 key 一箭双雕 / 本地缓存的代价 = **最多旧一个 TTL**

**核心不变量 / 主线**：
**大 key 的危险来自"单线程"（一条大命令挡住全体），热 key 的危险来自"单分片"（一个 key 打不散）。** 想清楚这两个前提，就能自己推出所有解法：**大 key 要把一次大操作拆成多次小操作，热 key 要把一个点变成多个点（读）或把多次写变成一次写（写）。**

**完整回答骨架**：先把两个维度分开（体积 vs 频率）→ 给两个共同前提（单线程、单分片）→ 大 key 的四个危害面 → 发现（三种手段与注意事项）→ 拆（`UNLINK` / 分批 / 按业务维度拆）→ 热 key 为什么加节点无效（算一遍）→ 发现（客户端统计 + 分片倾斜）→ 解（读热 vs 写热分开）→ 本地缓存的代价要量化 → 边界与误解

**完整回答（口述稿）**：
**大 key 与热 key 是两个维度**：大 key 是**体积**，热 key 是**频率**，对策完全不同。

**大 key**：危害来自"**Redis 命令执行单线程**"——删一个 200 万 field 的 Hash 会在主线程里同步释放所有元素（约 200 ms），这期间**所有请求的延迟都 +200 ms**；还有网络带宽、主从复制延迟、集群迁移卡住三个面。发现用 `--bigkeys` / `MEMORY USAGE`（采样估算 + 逐个确认）；处理用 **`UNLINK`**（异步回收，内存逐步释放）或 **`HSCAN`/`SSCAN` + 分批删**。

**热 key**：危害来自"**集群里一个 key 只属于一个分片**"，**加节点完全无效**——"单分片打满、其他分片闲置"就是它的签名。发现靠客户端/代理层统计（`MONITOR` 能看但代价大，别常开）。处理要**先分读热还是写热**：读热用本地缓存（命中 95% 能把 3 万 QPS 降到 1500）或打散成多个副本 key；**写热打散无效**（一次写变 N 份），只能本地聚合 / 队列串行 / 换结构。

一箭双雕的动作：**按业务维度把大 key 拆成一堆小 key**——既解决体积也分散访问。本地缓存能用，一致性可量化：TTL 50 ms 就是"最多旧 50 ms"；判据是"丢了能不能重建、旧 50 ms 能不能忍、会不会因为旧值做错事"——**只要它参与判断（余额、库存），就不能用**。

**分层要点**：
- **结论**：大 key 管体积（单线程阻塞），热 key 管频率（分片归属），对策不同。
- **推导链**：单线程 → 一条大命令挡住所有人 → UNLINK/分批；一个 key 只属一个分片 → 扩容无效 → 读热/写热分治。
- **量化**：删 200 万 field 的 Hash ≈ 阻塞 200 ms；本地缓存命中 95% 把 3 万 QPS 降到 1500；TTL 50 ms = 最多旧 50 ms。
- **边界与常见误解**：扩容治不了热 key（`MONITOR` 别生产常开）；写热打散会变成 N 份写，反而更糟；`UNLINK` 后内存是逐步释放的，监控不会立刻掉。

**追问**（先说后看）

1. **大 key 为什么危险？** —— **因为 Redis 命令执行是单线程的**：一条 `DEL` 大 key 会在主线程里同步释放所有元素（200 万 field 约 200 ms），**这期间所有请求的延迟都 +200 ms**。另外还有网络带宽、主从复制延迟、集群迁移卡住三个面。
2. **删大 key 该怎么做？** —— **`UNLINK`**（异步回收）或 **`HSCAN`/`SSCAN` + 分批删**。注意 `UNLINK` 之后内存是**逐步释放**的，监控上不会立刻掉。
3. **热 key 为什么扩容没用？** —— **集群里一个 key 只落在一个分片**，压力不会因为加节点而摊开。**"单分片打满、其他分片闲置"就是热 key 的签名。**
4. **热 key 怎么解决？** —— **先分清读热还是写热**：**读热**用本地缓存（首选，命中率高时直接把 Redis 的流量砍掉一个数量级）或打散成多个副本 key；**写热**打散无效（一次写变 N 份），要靠**本地聚合 / 队列串行 / 换数据结构**。
5. **本地缓存能用吗？有没有一致性问题？** —— **能，而且一致性可以量化**：TTL 50 ms 就意味着"最多旧 50 ms"。**判据是三问**：丢了能不能重建、旧 50 ms 能不能忍、会不会因为旧值做错事。**只要它参与判断（余额、库存），就不能用。**

**同类变体**

- 「缓存击穿和热 key 是什么关系？」——**同一个压力来源的不同表现**：击穿是"单个热 key 失效瞬间全部回源"，热 key 是"单个 key 长期打满分片"。**解法都指向"别让请求集中到一个点"**（[[母题-R3-缓存一致性与三类事故]]）
- 「大 key 和数据倾斜是什么关系？」——**大 key 常常就是数据倾斜的成因**：按用户 ID 分片时，某个超大用户的 key 会固定落在某一片上
- 「热 key 和锁的热键问题是同一件事吗？」——**是同一件**：**分段救不了热键**，都要换方案（聚合/串行/本地化），见 [[母题-L2-锁的粒度与临界区]] 2.1
- 「Redis Cluster 的槽位迁移为什么怕大 key？」——迁移是**按 key 搬**的，大 key 会让单次迁移卡住，**这是大 key 危害的第四个面**
