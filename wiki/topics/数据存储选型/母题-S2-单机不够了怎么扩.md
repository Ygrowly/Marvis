**导读**：必懂 3 件事（① 三条路解决的是**同一件事的两个部分**：读的压力、写的压力 ② 分片买到的是容量与并发，付出的是**"跨片操作全都变难"** ③ **CAP 不是一个"三选二"的按钮**，它要按"分区时选什么"来讲）· 读完约 13 分钟 · 需要先懂：[[母题-S1-OLTP与OLAP的分野与选型]]

**题目**：某业务库单表 **4 亿行**，QPS **8000**（读写比 9:1）。现在两个症状：**① 主库 CPU 常年在 70% 以上，写延迟偶尔飙升；② 每次加索引、改字段都要停机维护窗口，业务方已经拒绝再给窗口了。** 团队提了四条路：

- **A**：加两个从库，读走从库
- **B**：按 `user_id` 水平拆成 16 张表，放在同一个实例里
- **C**：按 `user_id` 拆到 4 个实例，每个实例 4 张表
- **D**：迁移到 OceanBase / TiDB

选哪个？第二个问题：**CAP 定理说分布式系统只能三选二，那是不是意味着"强一致"和"高可用"不可能同时要？**

**母题**：单机数据库的瓶颈在哪里、三条扩展路线各自买到什么付出什么，以及"一致性"在分布式系统里到底是怎么被取舍的。

## 一、教材

### 1. 前提：单机到底卡在哪——先分清"不够用"是哪一种不够用

#### 1.1 单机的四类上限【事实】

【事实】**"单机到顶了"这句话必须先拆开，因为四类上限的解法完全不同**：

| 上限 | 卡在哪 | 症状 | 解法 |
|---|---|---|---|
| **容量** | 单表/单库数据量增长 → 备份、DDL、索引维护的时间都在涨 | **加索引要几小时、DDL 要停机** | 归档 / 分区（[[母题-M15-数据增长治理]]）→ 再考虑分片 |
| **写并发** | 单实例的写入必须**串行化到同一份日志与同一批页**上 | 写延迟抖动、锁等待上升 | **分片**（把一个写入口变成 N 个） |
| **读并发** | 连接数与会话内存（**每个连接都有代价**，见 [[母题-O1-上下文切换与死锁]]） | 连接打满、`too many connections` | **加从库**（读天然可以复制） |
| **分析干扰** | 重查询与事务争抢 CPU / IO / 缓存 | 报表一跑，线上接口就变慢 | **隔离**（从库 / 列存引擎，见 [[母题-S1-OLTP与OLAP的分野与选型]]） |

【推导】**这张表决定了后面所有讨论的顺序**：

```
读并发高       → 读写分离（最便宜，先做）
分析干扰线上   → 隔离到从库或列存（次便宜）
容量增长       → 先归档分区，再谈分片
写并发高       → 只有分片这一条路（写在单机上无法被复制解决）
```

【事实】**关键判断：写入压力无法用"加从库"解决。** 从库是复制的**副本**，写入还是只有主库在承担——**加从库只增加"能同时读的人"，不增加"能同时写的人"**。这是很多"加了从库还是慢"的根因。

#### 1.2 一个必须先破除的误解【推导】

【推导】**"单表多少行就必须分表"这个说法是假的。** 数据库里没有"表超过 N 行就不行"的硬限制。**真正随时间增长的是"维护成本"**：

```
数据量增长 → B+ 树变高 → 点查多一次 IO        （慢一点，但不致命）
           → 索引变大 → 加字段/加索引要重建更久 （致命：要停机窗口）
           → 备份/恢复时间线性增长              （致命：RTO 不可接受）
           → 缓存命中率下降                     （致命：缓冲池装不下热数据）
```

【推导】**所以"该不该分"的判据不是"多少行"，而是**：

> **你是否已经付不起"维护一次这张表的代价"了？**（DDL 要多久、备份要多久、热数据还装不装得进内存）

【取舍】**这也是为什么"归档 + 分区"要先于分片**：如果 4 亿行里有 **3 亿行是两年前的历史数据**，那么**归档掉历史数据 + 对当前表做分区**，可能让维护成本直接回到可接受范围——**而这比引入分片中间件的成本低一个数量级**。

**到这里你应该能回答**：为什么"读取慢"和"写入慢"不能用同一招解决？

::figure data-growth-ladder.svg | 数据增长的治理阶梯 | 便宜且可逆的先做，贵且难回头的后做——分库分表恰好是最后一步

### 2. 三条路，先各自介绍

#### 2.1 A · 读写分离【事实】

【事实】**做法**：一个主库接收写，N 个从库通过复制协议（binlog / WAL）同步，应用层把读请求路由到从库。

**它买到什么**：**读的并发能力**（读可以水平复制，因为副本之间互不影响）。

**它付出什么**：

```
① 主从延迟 —— 从库是【异步或半同步】复制的，所以从库上的数据可能比主库旧
   → 直接的业务后果：「写后立刻读」可能读不到自己刚写的东西（read-your-write 被破坏）
② 路由复杂度 —— 应用要区分哪些读能走从库（容忍延迟）、哪些必须走主库
③ 一致性窗口 —— 报表与实时数据对不上，必须有对账或"数据截止时间"标注
```

【事实】**数驭穹图的 `LIVE_READ` 走的就是这条路**：`02` 写明实时模式*"优先连接只读副本或分析库"*，且*"若客户只有生产主库，默认不开放复杂即席查询"*——**把"不许打到主库"写成了产品规则**。

#### 2.2 B / C · 分库分表【事实】

【事实】**两个维度，不要混**：

| | 垂直拆 | 水平拆 |
|---|---|---|
| 拆什么 | **按业务/字段拆**（订单库、用户库；把大字段挪到附表） | **按行拆**（`user_id % 16`） |
| 解决 | 耦合与"热点表"问题 | **容量与写并发** |
| 典型形态 | 微服务化后的自然结果 | 分片键 + 路由规则 |

**它买到什么**：**写并发能力**（N 个实例各自有独立的日志、锁、缓冲池）+ 单表容量回到可控范围。

**它付出什么**（**这张清单是本节的重点**）：

```
① 跨片 join 消失 —— 要么在应用层拼装，要么建冗余宽表
② 跨片分页与排序变难 —— 原来一个 ORDER BY + LIMIT 能做的事，
   现在要【每个分片各取前 N 条再归并】
③ 跨片事务消失 —— 必须换成分布式事务方案（见第 4 节）
④ 全局唯一 ID —— 自增主键不能再用了（见第 4 节）
⑤ 二级索引变成"全局索引"问题 —— 非分片键的查询要么广播、要么自建索引表
⑥ 扩容迁移 —— 分片数一变，数据要重新分布（一致性哈希能减轻但解决不了全部）
⑦ 【选错分片键是灾难】—— 数据倾斜（热点分片）、或者大多数查询都要广播
```

【取舍】**第 ⑦ 条最容易出事**：**分片键决定了"哪些查询变成广播"**。按 `user_id` 分片，那么"按城市统计"这类查询就要打到所有分片。**所以分片键的选择不是看数据怎么分布，而是看"最高频的查询按什么维度来"。**

#### 2.3 D · 分布式数据库（OceanBase / TiDB）【事实】

【事实】**它把上面所有"应用层要自己做的事"下沉到数据库内部**：自动分片、自动扩容、分布式事务、全局索引。

**两条技术路线的架构差别**（这是本题最容易被追问的地方）：

| | **TiDB** | **OceanBase** |
|---|---|---|
| 整体形态 | **计算与存储分离**（三层） | **一体化**（单机与分布式同一套代码） |
| 计算层 | TiDB Server（无状态 SQL 层，可任意加） | OBServer（每个节点都同时是 SQL 与存储） |
| 存储层 | TiKV（**行存**，按 Range 分片成 Region） | 分区表 + 底层 LSM 存储 |
| 分析副本 | TiFlash（**列存**，以 Raft learner 从 TiKV 同步） | 列存副本 |
| 调度 | **PD**（独立组件，管 Region 分布与负载均衡） | 内建于集群管理 |
| 多副本一致性 | **Raft**（TiKV 内部按 Region 做 Raft 组） | **Paxos**（多副本日志同步） |
| 部署重心 | 组件多、依赖 PD，规模弹性好 | 单机即可跑出分布式架构，**对运维更友好**（这是它在国内金融/政企吃香的一个原因） |

【事实】**两者的共同点更重要**：**都是"用多副本一致性协议（Raft / Paxos）把复制做对，用自动分片把容量做开，用快照隔离 + 两阶段提交把分布式事务做出来"**。**它们解决的是同一个问题，差别主要在"组件怎么摆"和"对单机场景的友好度"。**

【取舍】**选它而不选分库分表的理由**：**把复杂度从"每个业务团队都要懂"变成"数据库团队管一次"。** 分库分表是**应用层方案**（每个写代码的人都要知道分片规则、都要处理跨片查询），分布式数据库是**基础设施方案**（应用写普通 SQL）。

**代价**：**产品锁定更深**（换回来极难）、**资源开销更高**（多副本意味着至少 3 份存储）、**学习与调优门槛在数据库侧**。

**到这里你应该能回答**：分库分表与分布式数据库，本质上是"把复杂度放在应用层还是放在基础设施层"的选择？

### 3. 逐个淘汰：统一指标是"新增了多少个失败点"

> **统一指标：新增的失败点数量 + 新增的不一致窗口。** 扩展的本质是**用复杂度换能力**，所以要比的是"换来的能力"与"付出的复杂度"。

【推导】把开头的四个方案放进同一把尺子：

| 方案 | 新增能力 | 新增失败点 / 不一致窗口 | 结论 |
|---|---|---|---|
| **A** 加两个从库 | 读并发 | +2 个实例（故障面）+ **主从延迟窗口** | **该做，但它解决不了"写延迟飙升"**（1.1 的判据） |
| **B** 同实例拆 16 表 | 单表维护成本下降 | **几乎为零**（还是同一个实例，事务与 join 都还在） | **性价比最高的一步**，但**不解决写并发**（还是同一个实例的日志与锁） |
| **C** 拆到 4 实例 | **写并发 ×4** | +4 个实例；**跨片事务、跨片 join、跨片分页全部变成应用层问题**；分片键选错 = 灾难 | **真能解决写并发**，但要吃下整张代价清单（2.2） |
| **D** 迁分布式数据库 | 写并发 + 容量 + 自动扩容 | 锁定、资源开销；但**应用层复杂度大幅下降** | 团队规模小、不想长期维护分片中间件时最优 |

【推导】**用题面给的两个症状来判**：

```
症状① 写延迟偶尔飙升 → 这是【写并发】问题
   → 加从库（A）无效：从库不承担写（1.1）
   → B 无效：同实例内拆表不增加写入并行度（日志、锁、页仍是同一份）
   → 只有 C 或 D 能解决

症状② 加索引要停机窗口 → 这是【容量/维护成本】问题
   → A 完全无效
   → B 有效（单表变小，DDL 更快），但表还会继续长大
   → C / D 有效（单表规模回到可控范围；D 还能在线 DDL）

★ 所以 A 和 B 都该做（成本低、解决部分问题），
  但题面里最痛的两个症状，需要 C 或 D 才能根治。
  选 C 还是 D，看"团队愿不愿意长期维护分片中间件与那套应用层规则"。
```

【取舍】**"先做 A 和 B、同时评估 C 或 D"不是和稀泥，而是成本顺序**：A 与 B 便宜且不排他，**先用它们买到喘息时间，再决定要不要吃下 C/D 的长期复杂度**——**这也是得物那个案例的实际路径**（`summaries/oceanBase.md`：*"低风险业务迁移 → TP/AP 一体化重构"*，**先小步验证，再动核心**）。

### 4. 分布式事务与全局 ID：为什么"没有全局时钟"是根本困难

#### 4.1 分布式事务的五个方案【事实】

【事实】

| 方案 | 思路 | 代价 |
|---|---|---|
| **2PC**（两阶段提交） | 协调者先问所有参与者"能不能提交"，都答应再统一提交 | **阻塞**（参与者要一直占着资源等结论）+ 协调者单点 |
| **TCC**（Try-Confirm-Cancel） | 每个服务自己实现"预留 / 确认 / 取消"三个操作 | 业务侵入极大，**要为每个操作写三个反向逻辑** |
| **Saga** | 一串本地事务，失败时按反序执行补偿 | 补偿逻辑要写；**中间态对外可见** |
| **本地消息表 / 事务消息** | 本地事务和"要发的消息"写在同一库，靠投递保证最终一致 | **只是最终一致**；要有幂等与对账 |
| **分布式数据库内建** | 快照隔离 + 两阶段提交，由数据库自己做 | 依赖产品；跨库（跨产品）仍然做不到 |

【推导】**所有方案的困难来自同一个地方**：

```
单机事务能原子提交，靠的是【共享的日志 + 一个本地的锁 + 一个提交点】。
分布式之后：没有共享日志、没有全局锁、【没有统一的时间（各机器时钟有偏差）】
→ 于是只剩两条路：
   ① 用协议（2PC / Raft 日志）把"一个提交点"造出来 → 慢、有阻塞
   ② 放弃原子性，用"补偿 + 幂等 + 对账"逼近最终一致 → 复杂但有弹性
```

【取舍】**工程上的主流选择是 ②**，**而它的核心不是事务本身，是幂等与对账**——这正是 [[母题-A3-失败恢复与幂等]] 与 [[母题-L3-分布式锁与fencing-token]] 要解决的问题：**"用最终一致"这句话只有在"重复执行不出错"和"能对账发现差异"都成立时才是安全的。**

#### 4.2 全局唯一 ID【事实】

【事实】**自增主键在分片后失效**（每个分片都会从 1 开始）。可选方案：

```
① UUID          → 全局唯一，但无序 → 【B+ 树索引插入变成随机写】，且体积大
② 号段模式      → 数据库批量发号（一次领 1000 个），本地自增
                  → 高性能，但重启/多实例要考虑浪费与重复
③ 雪花算法（Snowflake） → 时间戳 + 机器 ID + 序列号
                  → 趋势递增，但【依赖机器时钟】—— 时钟回拨会产生重复 ID
④ 数据库序列 / 分布式协调服务 → 简单但引入额外依赖
```

【推导】**选型的判据是"这个 ID 要不要参与索引和排序"**：**要按时间排序、要作为主键插入 → 必须趋势递增**（这直接关系到 [[母题-M1-为什么用B+树]] 的插入代价）；**纯业务标识、不参与排序 → UUID 的随机性无所谓**。

### 5. CAP 到底该怎么讲

#### 5.1 为什么"C 和 A 二选一"是个过度简化【推导】

【推导】**CAP 的准确含义**：

```
C（一致性）：线性一致性——所有节点看到同一个最新值
A（可用性）  ：每个请求都能在有限时间内得到【非错误】响应
P（分区容错）：网络分区（节点之间消息丢失/延迟）时系统仍能继续运行
```

【推导】**问题出在"三选二"这个说法上**：

```
① 网络分区在分布式系统里【不是可选项】——只要跨机器通信，
   分区迟早会发生。所以 P 不是"要不要"，是"必须接受"。
   → 于是真正的选择只剩：【分区发生的时候，选 C 还是选 A】

② 而"分区发生的时候"是一个【很短的窗口】。
   绝大多数时间里网络是好的，系统可以【同时】提供一致性与可用性。
   → 所以 CAP 描述的是"极端情况下的行为"，不是"日常的取舍"
```

【取舍】**更实用的框架是 PACELC**：

```
P（分区时）：在 A（可用）和 C（一致）之间选
E（否则 Else，即正常运行时）：在 L（低延迟）和 C（一致）之间选
→ 后半句才是日常真正在做的权衡：
  想要强一致的多副本写入，就必须等多数派确认 → 【延迟必然更高】
```

【推导】**所以面对"强一致和高可用能不能同时要"，准确的回答是**：

> **可以，在正常情况下两者都能得到。CAP 描述的是"网络分区发生的那一刻，你预先选了哪一个"**——**而这个选择应该由业务来定，不是由技术来定**（涉及钱和账的，选 C；可以被降级和缓存的，选 A）。

#### 5.2 一致性不是布尔值【事实】

【事实】**"一致"是个谱系，不是开关**：

```
线性一致（最强）：所有操作看起来像在单一副本上按时间顺序发生
    ↓
顺序一致 / 因果一致：至少保证有因果关系的操作间的顺序
    ↓
快照隔离：每个事务看到某个一致的快照（大多数分布式数据库的默认档）
    ↓
读己之写（read-your-writes）：至少能看到自己刚写的东西
    ↓
最终一致（最弱）：不保证多久，只保证最终会一致
```

【取舍】**工程上的常见落法**：**数据库内部用强一致（Raft / Paxos 多副本）保证"这份数据不会丢也不会分裂"，而业务层接受"跨系统的最终一致"**。**这是两个不同层次的一致，不要混着说**——把它们混成"你们系统是最终一致的吗"这种问法，就没法讨论了。

**到这里你应该能回答**：为什么"你们系统选 CP 还是 AP"这个问题，问法本身就有问题？

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "单表超过 1000 万行就要分表" | 【事实】**没有这个硬限制**。真正随时间增长的是**维护成本**（DDL 与备份耗时、缓冲池装不下热数据）。**判据是"你还付不付得起维护这张表的代价"，不是行数**（1.2） |
| "加几个从库就能扛住" | 【推导】**从库只分担读**（1.1）。**写入压力加从库无效**——这是"加了从库还是慢"的最常见根因 |
| "分库分表能提升性能" | 【取舍】**它提升的是"能承受的写并发与容量"，代价是"跨片操作全都变难"**（2.2 的七条）。**在数据量没到时做这件事，是纯负债** |
| "CAP 就是三选二，所以强一致必然牺牲可用性" | 【推导】**过度简化**（5.1）：P 是必须接受的，真实选择是"**分区时**选 C 还是 A"；而且正常运行时两者都能得到。**描述日常权衡的是 PACELC 的后半句：一致性与延迟之间的取舍** |
| "上了分布式数据库就不用管分片键了" | 【事实】**分片（分区）键仍然存在**，只是由数据库来管理。**选错分区键照样热点**——这是把"运维复杂度"下沉了，不是把"设计决策"取消了 |
| "分布式事务用 2PC 就行" | 【取舍】**2PC 会阻塞**（参与者要占着资源等结论），且协调者是单点。**它适合短小的事务，不适合跨服务的长业务流程**——后者要用 Saga / 本地消息表 + 幂等 + 对账 |
| "用最终一致就够了，业务能接受" | 【取舍】**要问三个问题**：重复执行安全吗（幂等）？差异怎么发现（对账）？不一致窗口里业务能接受吗？**三个都答得上来，最终一致才是安全的选项** |
| "分库分表以后再拆，先上业务" | 【取舍】**这是最常见的技术债来源**：分片键一旦选错，迁移成本极高（要重分布全量数据 + 改所有查询）。**所以"以后再拆"这个决定本身，也要在表设计阶段想清楚分片键会是什么** |

## 二、自测

**Q1（计算）**：某表写 QPS **2000**，平均每行写入（含索引维护）耗时 **0.15 ms**。单实例的写入能力受"日志与页的串行化"限制，实测该实例的写入上限约 **1500 QPS**。

问：① 现在会不会有问题？② 如果水平拆成 4 个实例，每个承担多少？③ 拆成 4 个实例后总写入能力大约是多少？④ 加 3 个从库能解决吗？

**A1**：

```
① 2000 > 1500 → 【已经超出单实例写入能力】
   → 表现为：写延迟抬升、锁等待上升、队列堆积（题面"写延迟偶尔飙升"正是这个）

② 均分的话：2000 / 4 = 【500 QPS/实例】
   → 只有上限的 1/3 → 有余量

③ 总能力 ≈ 1500 × 4 = 【6000 QPS】
   ★ 注意：这是【理论上界】，实际要打折——
     ① 跨片事务/查询的开销会回来吃掉一部分
     ② 数据倾斜会让某个分片先顶到上限（所以分片键要选高频查询维度）

④ 【不能】。从库不承担写（1.1）——加从库只增加读的并行度，
   写入仍然全部落在主库上，2000 QPS 一秒不少
```

【这一步在验证什么】验证 1.1 与 2.2：**"读的压力"和"写的压力"是两种资源，从库只解决前者，分片才解决后者。**

**Q2（计算）**：某表按 `user_id % 4` 分成 4 片。现在有两类查询：

- **甲**：`WHERE user_id = ? AND dt >= ?` —— 占总查询量 **85%**
- **乙**：`SELECT city, count(*) FROM orders WHERE dt >= ? GROUP BY city` —— 占 **15%**

问：① 甲查询要打到几个分片？② 乙查询呢？③ 如果把这个分片键改成按 `city` 分片，会怎样？④ 由此得出什么结论？

**A2**：

```
① 甲：`user_id` 就是分片键 → 能【精确定位单分片】→ 1 个分片，最高效

② 乙：查询条件里没有 user_id → 【无法裁剪】
   → 必须打到全部 4 个分片，各自算一遍，再在应用层归并
   → 代价：4 倍的计算量 + 一次归并

③ 若改成按 city 分片：
   甲：85% 的查询【全部变成广播】—— 灾难性的倒退
   乙：变成单分片，快了
   → 用 85% 换 15%，严重不划算

④ 结论：【分片键的选择不看数据怎么分布，看"最高频的查询按什么维度来"】
   （2.2 第 ⑦ 条）
   → 而 ② 这种情况的正解不是改分片键，是【另建一份按 city 聚合的宽表/物化视图】
     （回到 [[母题-S1-OLTP与OLAP的分野与选型]]：聚合类查询本来就该走列存）
```

【这一步在验证什么】验证 2.2 的第 ⑦ 条与第 ⑤ 条：**分片键按"高频访问维度"选；非分片键的聚合查询，应该用另一份数据（物化视图 / 列存）解决，而不是靠改分片键。**

**Q3（判读）**：团队报了一个方案：

> "我们库 3000 万行，主从延迟偶尔到 3 秒。为了解决这个问题，我们打算上分库分表，按 user_id 拆 8 片。"

问：这个方案的问题在哪？

**A3**：

```
问题一：【诊断错了】"主从延迟 3 秒"是【复制链路的容量问题】，不是分片能解决的
   → 分片解决的是"单实例写并发与容量"（2.2）
   → 主从延迟的可能原因：从库回放单线程/并行度不足、大事务、从库规格偏低、
     从库上还跑了别的查询（抢资源）
   → 应该先查：是不是有大事务（[[母题-M13-长事务为什么危险]]）、
     并行复制是否开启、从库有没有被别的负载占用

问题二：【3000 万行远远没到必须分片的量级】
   3000 万行 → 先做归档 + 分区 + 索引优化（[[母题-M15-数据增长治理]]）
   → 分库分表要吃下【七条代价清单】（2.2），在这个量级上纯亏

问题三：【即使真要分片，目标也不对】
   分片解决的是写与容量；而这里的症状是【复制延迟】——
   分片之后如果每个分片都有自己的从库，延迟问题一模一样地存在

【准确说法】先定位主从延迟的真因（大事务/并行复制/从库负载），
          同期做归档与分区；分库分表放到"确认是写并发或容量上限"之后再说。
```

**Q4（纠错）**：下面这段话哪里错了？

> "CAP 定理说分布式系统只能在一致性、可用性、分区容错里三选二。我们系统对可用性要求高，所以选了 AP，放弃一致性，用最终一致。"

**A4**：**三处错。**

1. **"三选二"是过度简化**：**P（分区容错）在网络分布式系统里不是可选项**——只要跨机器通信，分区迟早发生。**所以真实的选择是"分区发生的那一刻，选 C 还是 A"**（5.1）。把它说成"三选二"会让人以为"可以不要 P"。

2. **"放弃一致性"这个说法不准确**：**一致性是谱系不是开关**（5.2）。**"用最终一致"具体落在哪一档要问清楚**——是"读己之写"？是"因果一致"？还是"随便多久最终会一致"？**大部分自称"最终一致"的系统里，核心数据仍然需要强一致**（账、库存），**只有派生数据可以最终一致**。

3. **最关键的：CAP 描述的是极端情况，日常的权衡在别处**。按 **PACELC**，**运行正常时你在"一致性"和"延迟"之间选**：**想要强一致的多副本写入，就必须等多数派确认，延迟必然更高**。**这才是每天在做的取舍，而不是"要不要放弃一致性"。**

**准确说法**：*P 是分布式的前提而非选项，CAP 说的是"分区发生时预先选 C 还是 A"；一致性是个谱系而不是开关，多数系统是"核心数据强一致、派生数据最终一致"；而正常运行时的真正取舍在"一致性 vs 延迟"（PACELC 的后半句）。*

**Q5（纠错）**：下面这段话哪里错了？

> "我们上了分库分表之后性能提升很大，QPS 从 3000 涨到 12000，所以分库分表就是用来提升性能的。所有数据量大的系统都应该尽早分库分表。"

**A5**：**三处错。**

1. **"提升性能"这个归因不准确**：分库分表提升的是**"能承受的写并发与单表规模"**（2.2），**不是让单个查询更快**——**单个查询在分片后往往更慢**（非分片键要广播、要归并、跨片分页要各取 N 条再合并）。**准确的表述是"总吞吐能力提升，单次跨片查询的代价上升"。**

2. **"QPS 从 3000 到 12000"要给出前提**：这个数字**只有在"QPS 增长来自分片键命中的请求"时才成立**。如果新增请求大量是非分片键查询（广播），**总吞吐可能反而下降**——因为一个请求变成了 N 个。**报数字必须自带口径**（← 库内的硬规矩）。

3. **"尽早分库分表"是危险的建议**：**分片键选错之后迁移成本极高**（要重分布全量数据 + 改所有查询），而**分片键该怎么选，取决于"未来最高频的查询"，这在业务早期恰恰最不确定**。所以正确顺序是：**归档 → 分区 → 索引优化 → 读写分离 → 确认是写并发/容量上限 → 分片**（1.1 的顺序）；**并且真正的选择是在"应用层分片"与"分布式数据库"之间做**（2.3）。

**准确说法**：*分库分表买到的是"能承受的总写入与容量"，付出的是"跨片操作全都变难"；它不该被当作性能优化手段，而是"单实例确认到顶之后"的结构性选择。而且这个选择要在"应用层自己分片"和"换分布式数据库把复杂度下沉"之间做——后者在团队规模有限时往往更划算。*

## 三、面试输出（学完再看）

**一句话结论**：**扩展的第一步是分清"哪一种不够用"**——读并发高就加从库（**最便宜，但绝不解决写**）；分析干扰线上就隔离到从库或列存；容量与维护成本高就先归档 + 分区；**只有写并发高才需要分片**。分片买到的是**总写入能力与容量**，付出的是**七条代价**（跨片 join / 分页 / 事务 / 全局 ID / 全局二级索引 / 扩容迁移 / 分片键选错），**所以它的判据不是"多少行"，而是"你还付不付得起维护这张表的代价"**。而"应用层分片"与"换分布式数据库（OceanBase / TiDB）"的区别是**把复杂度放在应用层还是下沉到基础设施**——后者把跨片事务、自动扩容、全局索引都做进数据库，代价是产品锁定更深、资源开销更高。**OceanBase 与 TiDB 的共同点是"多副本一致性协议（Paxos / Raft）+ 自动分片 + 分布式事务"**，差别主要在组件摆法（TiDB 是计算存储分离 + PD 调度；OceanBase 是一体化、单机也能跑）。最后 **CAP 不是三选二**：P 是前提，真实选择是"分区时选 C 还是 A"，而日常的取舍是 PACELC 的后半句——**一致性与延迟**。

**恢复关键词**：**先分清哪一种不够用**（读 / 写 / 容量 / 分析干扰）/ **从库只分担读，写压力加从库无效** / 判据不是行数而是**维护成本** / 归档+分区 → 读写分离 → 分片 / **分片七条代价** / **分片键按高频查询维度选**（选错=灾难）/ 应用层分片 vs 分布式数据库 = **复杂度放哪层** / OceanBase 一体化 · TiDB 计算存储分离 / 共同点 = PAC**多副本 + 自动分片 + 分布式事务** / 2PC 阻塞 · TCC 侵入 · Saga 补偿 · 本地消息表最终一致 / 全局 ID 要**趋势递增**（B+ 树插入）/ **CAP 不是三选二：P 是前提** / **PACELC：日常权衡是一致性 vs 延迟** / 一致性是谱系不是开关

**核心不变量 / 主线**：
**扩展的一切手段都在"用复杂度换能力"**，而复杂度的落点是**"新增了多少个失败点 + 新增了多长的不一致窗口"**。**所以每一个扩展方案都要能回答：我新增了几个要监控、要处理故障、要对账的东西？** 分库分表把这件事放在应用层（每个开发者都要懂），分布式数据库把它放到基础设施层（数据库团队管一次）——**这个"放哪层"才是真正的选型分界，而不是"哪个更快"。**

**完整回答骨架**：先拆"不够用是哪一种"（四类上限表）→ 破除"多少行就要分表"的误解（判据是维护成本）→ 三条路各自买到什么、付出什么 → 分片的七条代价（重点讲分片键与跨片查询）→ OceanBase vs TiDB 的架构对照与共同点 → 分布式事务为什么难（没有全局时钟）+ 五种方案 → 全局 ID → CAP 的准确讲法 + PACELC → 边界

**完整回答（口述稿）**：
**扩展的第一步是分清"哪一种不够用"**：读并发高 → 加从库（**最便宜，但绝不解决写**）；分析干扰线上 → 隔离到从库或列存；容量与维护成本高 → **先归档 + 分区**；**只有写并发高才需要分片**。

**分片买到的是总写入能力与容量，付出的是七条代价**：跨片 join、跨片分页、跨片事务、全局 ID、全局二级索引、扩容迁移（约 50% 数据）、分片键选错。**所以判据不是"多少行"，而是"你还付不付得起维护这张表的代价"**——和 MySQL 侧"分库分表是最后一步"完全一致。

**分片键是查询形状的属性**，不是数据本身的属性；选错会导致大量查询广播到所有分片，而且它是**最难改的决定**。

"应用层分片" vs "换分布式数据库（OceanBase / TiDB）"的区别：前者把复杂度放在应用层，后者**下沉到基础设施**（跨片事务、自动扩容、全局索引由它承担）——**代价是引入一个新组件和它的运维与排障成本**。

**分层要点**：
- **结论**：先分清楚哪一种不够用；分片只解决写与容量，代价七条；判据不是行数。
- **推导链**：四类瓶颈 → 各自的解法 → 分片的收益与七条代价 → 判据 → 分片键性质 → 自建分片 vs 分布式库。
- **量化**：扩容迁移约 50% 数据；分片把"单机写上限"横向扩展。
- **边界与常见误解**：加从库不解决写瓶颈；分片键选错 = 大量广播（等于没分）。

**追问**（先说后看）

1. **加了从库为什么还是慢？** —— **因为从库只分担读**（1.1）。**写入压力无法用复制解决**——副本不进写路径。要先确认瓶颈是读还是写，再选手段。
2. **分片键怎么选？** —— **按"最高频的查询维度"选**（2.2 第 ⑦ 条），不是按数据分布选。**选错的后果是：高频查询全部变成广播，或者数据倾斜导致热点分片。** 而低频的非分片键查询，应该另建一份聚合数据（物化视图 / 列存）来解决。
3. **OceanBase 和 TiDB 最大的差别是什么？** —— **组件摆法**：TiDB 是**计算存储分离**（TiDB Server 无状态 + TiKV 行存 + TiFlash 列存 + PD 调度，依赖 Raft）；OceanBase 是**一体化**（每个节点同时是 SQL 与存储层，用 Paxos 多副本，**单机也能跑出分布式架构**，对运维更友好）。**共同点是"多副本一致性 + 自动分片 + 分布式事务"**——它们解决的是同一个问题。
4. **分布式事务为什么难？** —— **因为没有全局时钟、没有共享日志、没有全局锁**，原子提交的"一个提交点"不存在（4.1）。要么用协议造一个（2PC / Raft，慢且有阻塞），要么放弃原子性用**补偿 + 幂等 + 对账**逼近最终一致——**后者的关键不是事务，是幂等与对账。**
5. **什么情况下不该分库分表？** —— 数据量没到（归档 + 分区能解决）、瓶颈在别处（慢查询 / 主从延迟 / 缺索引）、**以及"分片键还没想清楚"的时候**——**分片键选错的迁移成本极高，所以宁可晚分也别乱分**。
6. **HTAP 的分布式数据库是不是就不用分库分表了？** —— **是的，它把分片内化了**——但**分区键仍然存在且要选对**（只是由数据库管理）。**它取消的是"应用层要知道分片规则"这件事，不是取消"设计决策"。**

**同类变体**

- 「读写分离为什么会有主从延迟？」——**复制是异步或半同步的**（[[母题-M14-主从复制与延迟]]）。直接的业务后果是 **read-your-write 被破坏**——所以"写后立刻读"的场景必须走主库
- 「一致性哈希为什么能减轻扩容迁移？」——它让**"增加一个节点时只影响相邻的一段数据"**，而不是全量重分布。**但它解决不了数据倾斜，也解决不了跨片查询**
- 「为什么分布式数据库至少三副本？」——**多数派协议（Raft / Paxos）需要"多数派存活才能提交"**。三副本能容忍 1 个节点故障；两副本没有容错能力（任何一台挂了都凑不齐多数派）
- 「分库分表中间件（ShardingSphere 这类）解决什么？」——**在应用层把"分片规则"变成透明的**（改写 SQL、路由、归并结果）。**这正是"复杂度放在哪层"的中间态**——比纯应用层改造轻，比换数据库重

**得物案例（`summaries/oceanBase.md`）** —— 它的起点正是本卡第 0 节那个"多引擎隐性成本"：**MySQL + TiDB + MongoDB + HBase + DuckDB + ClickHouse + StarRocks + 向量库 并存**，导致*"运维复杂、研发选型困难、架构链路复杂、数据一致性风险、资源利用率低"*。**它的解法是"一体化"**（用一套 HTAP 数据库收掉部分引擎），**但路径是"低风险业务先迁移 → POC 验证 → 再动核心"**——**这正是本卡第 3 节"先做便宜的、再决定要不要吃长期复杂度"的现场版。**

**方言差异**：

| 同一件事 | 单机 MySQL / PG（本卡之前的默认） | 分布式数据库（OceanBase / TiDB） |
|---|---|---|
| 分片 | 靠中间件或应用层 | **数据库内部自动**（Region / 分区） |
| 跨片事务 | 应用层解决（2PC / Saga / 消息表） | **数据库内建**（快照隔离 + 两阶段提交） |
| 扩容 | 需要人工重分布 + 改路由规则 | **自动调度**（PD 或内建均衡） |
| 二级索引 | 本地索引 | **全局索引**（跨分片维护，写入代价更高） |
| 自增主键 | 原生支持 | 需要全局 ID 方案（趋势递增） |
| 故障单元 | 单机（挂了就没了，靠主从切换） | **多副本**（多数派存活即可用） |
