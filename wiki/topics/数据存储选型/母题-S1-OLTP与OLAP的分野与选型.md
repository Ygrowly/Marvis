**导读**：必懂 3 件事（① 分水岭不是"功能多少"，而是**数据在磁盘上怎么排** ② **一次查询要读多少字节**是所有选型讨论的唯一可比指标 ③ 大多数业务数据量下，**引入第二个引擎是负债而不是升级**）· 读完约 12 分钟 · 需要先懂：无

**题目**：某业务库 MySQL 里有一张 **1 亿行的订单明细表**（约 **100 个字段**）。分析师要跑一句"按城市统计近一年客单价"的报表：`SELECT city, sum(amount)/count(distinct user_id) FROM orders WHERE dt >= ... GROUP BY city`。这句 SQL 在 MySQL 上要跑 **几分钟**，而且跑的时候线上接口开始变慢。团队提了三个方案：

- **A**：给 MySQL 加上 `city`、`dt`、`amount` 的联合索引
- **B**：主库不动，加一个从库专门跑报表
- **C**：把这批数据同步到 ClickHouse，报表查 ClickHouse

选哪个？还有第二个问题：另一个团队只有 **500 万行** 的数据，也想上 ClickHouse，该不该拦？

**母题**：OLTP 与 OLAP 的本质差别是什么，凭什么它俩不能被一个引擎同时做好，什么信号出现时才真的该上第二个引擎。

## 一、教材

### 1. 前提：所有的差别只来自一件事——数据在磁盘上怎么排

#### 1.1 先把两类负载说清楚【事实】

【事实】**这不是两个技术名词，这是两类负载。** 先用"一次操作碰多少数据"把它们分开：

| | **OLTP**（联机事务处理） | **OLAP**（联机分析处理） |
|---|---|---|
| 全称 | Online **Transaction** Processing | Online **Analytical** Processing |
| 一次操作碰多少 | **几行到几十行** | **百万行到亿行** |
| 典型动作 | 下单、扣库存、改状态、按主键查详情 | 按维度聚合、算比值、多表关联、下钻 |
| 并发 | **高**（每笔都很小） | **低**（每条都很重） |
| 延迟预期 | **毫秒** | 亚秒到分钟都可接受 |
| 数据新鲜度 | **必须是当前最新** | 允许有窗口（T+1 或分钟级） |
| 失败代价 | **不可接受**（钱和账不能错） | 可重跑 |

【推导】**这张表已经决定了一件事**：**这两类负载对"读取效率"的定义是相反的**——OLTP 希望"给我一行时一次把这一行拿全"，OLAP 希望"给我一列时别把别的列也读进来"。**同一个物理排布不可能同时满足这两个愿望**，这就是整个分野的起点。

#### 1.2 两种物理排布【事实】

【事实】**行式存储（row store）**：**同一行的字段连续存放**，一行接一行。
【事实】**列式存储（column store）**：**同一列的字段连续存放**，一列接一列。

::figure row-vs-column-store.svg | 同一张表的两种物理排布 | 逻辑上是同一张表，物理上顺序完全不同：行存按行连续，列存按列连续

**别把这张图当成"两种索引"**——它不是索引层面的差异，是**数据文件本身的组织方式**。索引再花哨，底层读的还是这些块。

**到这里你应该能回答**：为什么"OLTP 和 OLAP 的区别"这个问题，不能从"功能列表"回答，只能从"物理排布"回答？

### 2. 用同一个指标把两种排布算一遍

> **统一指标：扫一次全表，要从磁盘读多少字节。** 这是唯一能公平比较的尺子——**别的指标（QPS、响应时间）都受硬件和实现影响，只有"读多少字节"是由排布直接决定的**。

#### 2.1 场景一：按主键查一行【推导】

【推导】假设表宽 **100 个字段、行宽约 1 KB**：

```
行存：读一行 = 找到这 1 KB 连续数据 → 1 次 IO 拿回整行（全部 100 个字段都在）
列存：要拼出一行 = 需要从【100 个不同的列段】各取一个值 → 100 次定位
      （而且这 100 个值在磁盘上彼此相距很远，因为列与列之间隔着一整列的数据）
```

**结论：点查场景行存赢，而且赢的不是一点。**

#### 2.2 场景二：扫全表算一列的聚合【推导】

【推导】还是那张表，现在只算 **3 个数值列**（每列 8 字节）：

```
行存：必须把每一行整行读进来，再扔掉其中 97 个字段
   1 亿行 × 1 KB = 【约 100 GB】要读

列存：只读这 3 列
   1 亿行 × 3 列 × 8 B = 【2.4 GB】要读
   → 而且同列数据同构、取值域窄，可压缩 → 实际读的更少（倍数取决于数据基数，属【经验值】，必须按自己的数据实测）
```

**同一个查询，IO 量差 40 倍以上。** 这就是"为什么列存快"的全部秘密——**不是它算得快，是它要读的东西少。**

【推导】**附带还有两个加成，都来自同一件事**：

| 加成 | 为什么 | 来源 |
|---|---|---|
| **压缩率高** | 同一列的数据类型相同、相邻、取值域窄（城市名、状态码、日期），列式排列让"相似的东西挨在一起"，通用压缩算法能吃到更多重复 | 同列同构 |
| **能用向量化执行** | 连续内存 + 同构类型 → 可以一次处理一批值，而不是一行一行循环（SIMD 指令的前提） | 数据连续 |

#### 2.3 场景三：改一行【推导】

【推导】**这一条最容易被忽略，但它决定了 OLAP 引擎的"功能边界"**：

```
行存：改一行 = 在那一行 1 KB 上原地改（或追加新版本，见 MVCC）
列存：改一行 = 要改 100 个列段里的各一个值
      → 逻辑上的"一行"，物理上散落在 100 个地方
      → 所以列存引擎普遍把"更新"实现成【异步重写整块数据】（先标记，后台合并）
```

【事实】**这就是为什么列存引擎的"UPDATE"普遍是异步的、按批的、代价高的**（ClickHouse 的 mutation 走这条路径；Doris / StarRocks 用 Unique Key 模型 + 后台合并来缓解，但语义上仍是"最终一致"）。**"它能做点更新"和"它划得来做高频点更新"是两句话。**

::figure storage-selection-tree.svg | 三步把负载归到引擎族 | 第一问访问模式定大类，后两问在组内收敛

### 3. 从物理排布推出的全部差异

【推导】下面是**同一张表的两种排布**推导出来的完整差异表——**每一条都能追到 2.1 / 2.2 / 2.3**：

| 维度 | OLTP（行存） | OLAP（列存） |
|---|---|---|
| 单次数据量 | 几行 ~ 几十行 | 百万 ~ 亿行 |
| 并发 / QPS | 高（每笔小） | 低（每条重） |
| 延迟预期 | 毫秒级 | 亚秒 ~ 分钟 |
| 索引 | B+ 树主键 + 少量二级索引（更新时维护代价高） | 稀疏索引 / 排序键 / min-max / 布隆过滤器（**不要求唯一，维护便宜**） |
| 事务 | 强 ACID、细粒度锁 / MVCC | 多数没有跨行事务；批量导入有原子性；点更新昂贵 |
| 写入模式 | 高频点更新 / 删除 | 大批量追加（append） |
| 数据新鲜度 | 当前最新状态 | 通常有窗口（要最新就得付同步代价） |
| 表设计 | **规范化（3NF）**：避免冗余、避免更新异常 | **反规范化 / 宽表 / 星型模型**：少 join、少扫描；用冗余换查询速度 |
| 瓶颈所在 | 随机 IO、锁竞争、写放大 | 扫描量、shuffle、join 内存、数据倾斜 |

【取舍】**最后两行是真正的哲学分歧，值得单独记**：

> **规范化是为了"一份事实只存在一个地方"（保证更新不出错）；反规范化是为了"一次查询少碰几个地方"（保证读得快）。** 两者的代价正好是对方的目标。

【推导】由此还能推出一件工程事实：**既然两边的表设计不一样，数据就不能"同一张表两边共用"**——必须经过 ETL / CDC 同步，**于是必然带来延迟和一致性窗口**。**"要不要上 OLAP 引擎"这个问题，一半的答案其实是在问"你受得了这个延迟窗口吗"。**

**到这里你应该能回答**：为什么说"OLAP 引擎快"这个说法不准确，准确说法应该是"它要读的字节少"？

### 4. 选型：三个问题，依次收敛

【取舍】选型不要从"哪个引擎先进"开始。**按顺序问三个问题，任何一个能定死答案，后面的就不用问了。**

**第一问：访问模式是什么？**

```
点查 / 小事务 / 要求强一致  → 行存（OLTP）
大范围扫描 / 聚合 / 多表关联 → 列存（OLAP），继续问第二问
```

**第二问：数据量到底多大？**

【取舍】**这一问是"拦住过度设计"的那一关。**

```
千万行以内、查询不复杂 → 【先用现有的关系库】加索引 / 物化视图 / 分区
                     → 上第二个引擎的收益小于它的代价（见第三问）
亿级以上、宽表聚合、要压缩率 → 列存引擎
```

【事实】**关系型数据库本身也能做分析**（PostgreSQL 的并行扫描、物化视图、分区表；MySQL 8 的窗口函数与 CTE）。**"能不能做"和"划不划得来"是两件事**——**数据量没到那个量级时，多一套引擎带来的同步链路、一致性窗口、运维面、以及"两份数据谁是准的"这一串问题，代价远大于省下的那几秒查询时间。**

**第三问：更新与并发怎么分布？**

```
高频单行 UPDATE / DELETE   → 【留在行存那边】，或者用支持 Unique Key 的列存引擎
                        → 高频点更新打到 ClickHouse 这类引擎上，是最常见的误用
大批量 append（日志、埋点、流水归档）→ 列存引擎最舒服
交互式 BI、几百人同时点报表 → 需要强并发能力的列存引擎（Doris / StarRocks 这类）
单条重查询跑到底、并发不高 → ClickHouse 这类擅长单表扫描的引擎
```

#### 4.1 回到开头那道题【推导】

【推导】**三个方案，逐个用指标算**：

| 方案 | 会发生什么 |
|---|---|
| **A** 加联合索引 | **改善有限**。这个查询要的是"近一年全部明细的和与去重计数"，**它天然要扫掉那一年的大量数据**——索引能帮 `WHERE dt >= ...` 做范围裁剪，**但聚合本身躲不掉全量读**。而且**1 亿行的宽表加索引，写入代价也要算**（见 [[母题-M4-索引代价与大表变更]]） |
| **B** 加一个从库跑报表 | **解决了"干扰线上"这一半，没解决"慢"这一半**。它把负载隔离出去（这是对的，也是数驭穹图 `SNAPSHOT / LIVE_READ` 分流想干的事），但**行存扫宽表这件事本身还是那么贵** |
| **C** 同步到 ClickHouse | **两条都解决**：扫描只读需要的那几列（2.2 的 40 倍），而且**和线上库物理隔离**。**代价是**：新增一条同步链路、新增一个要对齐的存储、新增一个口径可能不一致的地方 |

【取舍】**正确答案是 C，但理由要说完整**：**C 赢在两个地方——IO 量、负载隔离；C 的成本也在这两个地方——多一份数据、多一个"谁是准的"的问题。** 只答"因为 ClickHouse 快"是没答到点的（那是方案说明，不是选型理由）。

#### 4.2 第二个问题：500 万行该不该上 ClickHouse【推导】

【推导】**该拦。** 按第二问：

```
500 万行 × 假设行宽 1 KB ≈ 5 GB 原始数据
→ 单机关系库加好索引 / 物化视图，这类量级的聚合是【秒级】能给出的
→ 而引入 ClickHouse 的固定成本是【不变的】：
   一条同步链路 + 一个引擎的运维 + 一份口径对齐 + 一条"数据延迟了怎么办"的处理路径
→ 固定成本不变、收益随数据量增长 → 数据量小的时候，收益 < 固定成本
```

【取舍】**这里有一个反直觉但重要的判断**：**"要不要上 OLAP 引擎"的主要变量是"团队能不能承受多一份数据的复杂度"，不是"数据量到了哪个数"。** 数据量只是让它变得划算的快慢问题。**一个有专职数据团队的公司，500 万行上实时数仓也可能合理；一个三人的小团队，5 亿行也未必该上——因为上了没人能维护。**

**到这里你应该能回答**：为什么"我们数据量很大"这句话本身，不足以支撑选型决策？

### 5. HTAP 与那几个容易被说错的边界

#### 5.1 HTAP 是折中，不是全面胜出【事实】

【事实】**HTAP（Hybrid Transactional/Analytical Processing）** 指一套系统同时承担两类负载。主流实现方式有两条路线：

| 路线 | 做法 | 代表 |
|---|---|---|
| **一份数据 + 两种副本** | 行存副本负责事务，列存副本负责分析，通过复制协议同步 | TiDB（TiKV 行存 + TiFlash 列存）· OceanBase（行存 + 列存副本） |
| **单一引擎兼顾** | 内存列存 / 向量化 + 事务能力共存 | MySQL HeatWave · 部分单机分布式一体化产品 |

【取舍】**它的价值是明确的**：**省掉"再搭一套同步链路"**，并且把分析拉近实时（这是多库架构最主要的痛点，`summaries/oceanBase.md` 里得物的实践正是从"多库并存"走向"一体化"）。

【取舍】**但它不是免费的，也不是终点**：

```
好处：少一条同步链路、少一份口径分歧、实时性更好、运维面收敛
代价：① 分析负载与事务负载仍会争抢同一套底层资源（要靠资源隔离去管）
      ② 极重的分析场景下，专用 OLAP 引擎的性价比仍可能更高
      ③ 单产品锁定更深——迁移成本比"多个独立引擎"更高
```

【推导】**准确的表述**：**HTAP 把"同步链路"这个成本换成了"资源隔离 + 产品锁定"这两个成本。** 它在中大数据量 + 强实时性 + 团队规模有限时最优；数据量极大、查询极重时，专用引擎分工仍更划算。

#### 5.2 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "OLAP 引擎也支持 UPDATE，所以一个引擎就够了" | 【事实】**它支持，但那是异步、按批、代价高的路径**（列存的"改一行"物理上要碰 N 个列段，见 2.3）。**能做的语义 ≈ 最终一致的批量重写，不是 ACID 事务**——面试里把这两者混着说，是硬伤 |
| "列存快是因为它算得快" | 【推导】**错在归因**。列存快的根本原因是**它要读的字节少**（只读用到的列 + 压缩率更高），**执行层的向量化是"数据连续"这个前提带来的附加收益**，不是原因 |
| "MySQL 上跑得慢，加个索引就好了" | 【推导】**要看慢在哪**。索引解决的是"定位"（`WHERE` 挑出少数行）；**如果查询本身就要聚合掉大量数据，索引帮不上忙**——那是扫描量的问题，属于"选错引擎族"而不是"缺索引" |
| "我们数据量大，必须上大数据方案" | 【取舍】**"大"要有量级**。千万行以内先算账（4.2）：**固定成本不变的条件下，收益必须随量级增长才划算** |
| "HTAP 是最终答案，两套系统迟早要合并" | 【取舍】**它是折中**（5.1）：省掉同步链路，换来资源争抢与产品锁定。**在什么规模上哪种更优，取决于数据量、实时性要求和团队规模三个变量，没有普适答案** |
| "ClickHouse 是 OLAP，所以它=分析" | 【事实】**OLAP 是一类负载，不是一类产品**。同样叫 OLAP 引擎，有的擅长单表大扫描（压缩与扫描速度优先），有的擅长多表 join 与高并发短查询（**这与它们的存储与执行设计有关**）。**"OLAP 引擎"这个词不能替代具体选型** |
| "从库跑报表就不影响线上了" | 【事实】**只搬走了负载，没搬走成本**。从库仍要承担复制开销，而且**报表如果扫的是同一份行存数据，慢的根源一点没变**（4.1 方案 B） |
| "报表慢一点没关系，反正不影响交易" | 【取舍】**要区分"慢"和"把线上拖慢"**。这两件事的解法不同：**前者是引擎族选型问题（本卡），后者是资源隔离问题**（[[母题-X1-容器是什么]] 的同一个原则：**给资源设上界**）。数驭穹图 `07`/`08` 对"扫描量、超时、行数、并发"的限制，正是把这两件事分开处理 |

## 二、自测

**Q1（计算）**：一张宽表，**100 个字段，行宽 1 KB，共 1 亿行**。现在只查询其中 **2 个数值列**（每列 8 字节）：`SELECT sum(a), avg(b) FROM t`。

问：① 行存要读多少字节？② 列存要读多少字节（不考虑压缩）？③ 倍数是多少？④ 如果这 2 列是"订单状态"（取值只有 5 种）和"城市"（取值约 300 种），压缩之后会怎样？

**A1**：

```
① 行存：必须整行读进来再扔掉 98 个字段
   1 亿 × 1 KB = 【100 GB】

② 列存：只读 2 列
   1 亿 × 2 × 8 B = 16 亿 B = 【1.6 GB】

③ 倍数 = 100 GB / 1.6 GB = 【62.5 倍】
   → 这就是"列存快"的全部来源：要读的字节少 62 倍

④ 压缩：这两个列的取值域都很窄（状态 5 种、城市 300 种）
   → 同列相邻、类型相同、重复度高 → 通用压缩能吃到大量重复
   → 实际落盘远小于 1.6 GB
   ★ 但【具体倍数取决于数据基数，属经验值】——必须拿自己的数据实测，
     不许把任何一个"列存能压 N 倍"的说法当结论背（库内规矩：区间 + 来源性质）
```

【这一步在验证什么】验证 2.2：**列存的收益主要是"少读"**，压缩是叠加在"少读"之上的第二层收益。**两个收益都来自同一个原因——同列的数据挨在一起。**

**Q2（计算）**：还是这张表。现在有两个写入场景：

- **场景甲**：每秒 **500 笔**订单状态更新，每笔改 **1 行**
- **场景乙**：每小时追加 **200 万行**新流水

问：① 两个场景在行存上的代价？② 在列存上呢？③ 结论是什么？

**A2**：

```
① 行存：
   甲：500 行/秒 × 1 KB = 500 KB/秒 的随机写 —— 量很小，但每个事务要维护
       主键索引与二级索引 → 代价在【索引维护与锁】上，不在数据量上
   乙：200 万行追加 = 顺序写 + 批量提交 → 行存完全能承受

② 列存：
   甲：每改 1 行要碰 100 个列段 → 500 行/秒 = 每秒要改【5 万处】
       逻辑一行、物理散落 100 处（2.3）→ 只能走异步重写整块（mutation）
       → 后台合并（merge）会持续被压住，是【典型的误用】
   乙：追加正是列存最擅长的——顺序写入、按块组织、后台合并
       → 每小时 200 万行是很轻松的批量导入

③ 结论：同样一句"我们要写数据"，
   甲该给行存，乙该给列存。
   → 【写入模式比写入量更重要】：高频小写的杀手是"改一行要碰几处"，
     不是"每秒多少行"
```

【这一步在验证什么】验证 2.3 与第三问：**"写入量大"不是判断依据，"点更新还是批量追加"才是。**

**Q3（判读）**：某团队说："我们的库有 **8000 万行**，报表要跑 40 秒。我们打算 MySQL 和 ClickHouse 双写，以后所有查询都走 ClickHouse，MySQL 只做写入。"

问：这个方案的问题在哪？

**A3**：

```
问题一：【"所有查询"包含了点查】
   ClickHouse 做按主键查单行是它的弱项（2.1 反向）
   → 点查必须留在行存那边。"以后都走 ClickHouse"是把两类负载混为一谈

问题二：【双写的成本被低估了】
   双写 = 两个写入口 → 必须处理：
     · 一边成功一边失败怎么办（分布式事务问题，见 [[母题-Q1-消息为什么会丢怎么才不丢]]）
     · 写顺序与幂等（见 [[母题-L3-分布式锁与fencing-token]]）
   主流做法是【单写 + CDC 同步】而不是应用层双写，就是为了避开这个坑

问题三：【口径分歧没人管】
   两份数据必然出现"报表和明细对不上"
   → 必须有对账机制与"以哪边为准"的明确规则

问题四：【量级需要复核】
   8000 万行、40 秒——先确认慢在哪（Q1 的算法）：
   如果只是缺索引或写法问题（[[母题-M7-慢查询与SQL优化手段]]），
   加引擎是"用大炮打蚊子"；如果确实是宽表全量聚合，那 C 方案成立

【准确说法】保留"同步到 ClickHouse 供分析"这个方向，
          但必须补三条：① 点查留在行存 ② 用 CDC 而不是双写
          ③ 明确哪边是准的 + 对账机制
```

**Q4（纠错）**：下面这段话哪里错了？

> "列式存储比行式存储先进，所以新系统都应该用列存。而且列存的压缩率高，占的磁盘少，连存储成本都更低。"

**A4**：**三处错。**

1. **"先进"错了，错在把"针对某类负载更优"说成"总体更先进"**。行存与列存是**针对两类相反负载的两个最优解**（2.1 与 2.2 是同一个计算的两面）。**点查场景行存赢；聚合场景列存赢。** 没有先进与落后，只有匹配与不匹配。

2. **"都应该用列存"错了**：**绝大多数业务系统的核心负载是 OLTP**（下单、支付、改状态、按主键查详情），**而且要强一致**。列存在这类负载上会同时输在"点查"和"点更新"两件事上（2.1、2.3）。

3. **"连存储成本都更低"错在只算了一边**：**持有一份列存数据，你要付的不只是磁盘钱**——还有：
   - 一条同步链路的开发与维护
   - 一个引擎的运维
   - "两份数据口径不一致怎么处理"
   - 数据延迟窗口带来的业务处理（报表要不要标注"数据截止时间"）

   **磁盘便宜，人不便宜。** 在小数据量下，这些固定成本远大于省下的磁盘与查询时间（4.2）。

**准确说法**：*行存与列存是两类负载各自的最优解，不是新旧关系。判断该用哪个，先算"一次查询要读多少字节"（点查看行存、聚合看列存），再算"多一份数据的固定成本划不划算"。列存确实压缩率高、占盘少，但那只是它众多差异里的一项，不足以单独支撑选型。*

**Q5（纠错）**：下面这段话哪里错了？

> "HTAP 把 OLTP 和 OLAP 合并到一个系统里，所以以后就不需要数据同步、不需要数仓了，一个数据库全搞定。"

**A5**：**两处错。**

1. **"不需要数据同步"只在同源数据上没有错**：HTAP 的价值确实是**省掉"再搭一套同步链路"**（5.1）。**但这句话的隐含前提是"所有数据都在这个 HTAP 系统里"**——而现实里数据分散在十几个系统（`summaries/oceanBase.md` 里得物的清单就是：MySQL、TiDB、MongoDB、HBase、DuckDB、ClickHouse、StarRocks、向量库）。**跨系统的同步该有还是有**，HTAP 只解决了"这一份数据内部分析与事务"的那一段。

2. **"一个数据库全搞定"错在无视了折中的代价**：
   - **资源争抢仍在**：分析和事务共用一套底层，重分析会与事务抢 CPU / IO / 内存 → 靠资源隔离去管，不是自动消失
   - **产品锁定更深**：单产品越重，迁移成本越高
   - **专用引擎并非无意义**：极重分析场景下专用列存引擎的性价比仍可能更高

**准确说法**：*HTAP 是把"再搭一套同步链路 + 维护两份数据"这个成本，换成了"资源隔离 + 更深的产品锁定"这两个成本。它在数据量中等、实时性要求高、团队人手有限时最优；不是"以后不需要其他东西"，而是"这几个约束下的更好折中"。*

## 三、面试输出（学完再看）

**一句话结论**：**OLTP 与 OLAP 的差别只有一个根因——数据在磁盘上怎么排。** 行存把同一行的字段放在一起，所以**点查一次 IO 拿回整行、改写一行只碰一处**，但它做聚合时**必须整行读进来再扔掉大部分字段**；列存把同一列的放在一起，所以**聚合只读用到的列**（一张 100 列的表只取 2 列时，IO 差 60 倍以上），而且**同列同构所以压缩率高、数据连续所以能用向量化**，但它**点查要拼 N 个列段、改一行要碰 N 个列段**——**这就是列存引擎的 UPDATE 普遍是异步按批的根本原因**。由此推出选型三步：**先问访问模式**（点查→行存，聚合→列存）；**再问数据量**（千万行以内先别加引擎，因为同步链路与运维的固定成本不随数据量缩小）；**最后问更新模式**（高频点更新别给列存，大批量追加才是列存的地盘）。**HTAP 是折中不是终点**：它把"同步链路"的成本换成"资源隔离 + 产品锁定"的成本。

**恢复关键词**：**根因只有一个——数据在磁盘上怎么排** / 行存=同一行连续 / 列存=同一列连续 / **统一指标：扫全表要读多少字节** / 点查看行存 · 聚合看列存 · 点更新看行存 / 列存快的真因是**读得少**（压缩与向量化是附加）/ **改一行要碰 N 个列段** → UPDATE 异步按批 / 规范化 vs 反规范化 / **选型三问：访问模式 → 数据量 → 更新模式** / 千万行以内先算账 / **HTAP = 折中（省同步链路，换资源隔离与锁定）** / OLAP 是一类负载不是一类产品

**核心不变量 / 主线**：
**一切差异都能从"一次读多少字节"和"改一行要碰几处"这两个算术题推出来。** 面试里被追问任何 OLAP / OLTP 细节（为什么压缩率高、为什么不支持高频更新、为什么要有同步链路、为什么列存不适合点查），**都可以回到这两个问题现推**——**不需要背，需要会算。**

**完整回答骨架**：先给根因（磁盘排布）→ 用一个可算的场景把差距算出来（100 列宽表只取 2 列，60 倍）→ 从根因推出四种差异（点查 / 聚合 / 写入 / 压缩）→ 推出两条工程后果（表设计规范 vs 反规范、必须有同步链路）→ 给选型三问 → 用三问回答"该不该上第二个引擎" → 补 HTAP 是折中 → 边界（OLAP 引擎的"事务"不是 ACID 事务）

**完整回答（口述稿）**：
**OLTP 与 OLAP 的差别只有一个根因——数据在磁盘上怎么排。** **行存**把同一行的字段放在一起：**点查一次 IO 拿回整行、改写一行只碰一处**；但做聚合时**必须整行读进来再扔掉大部分字段**。**列存**把同一列的放在一起：**聚合只读用到的列**（100 列的表只取 2 列时 IO 差 60 倍以上），而且**同列同构所以压缩率高、数据连续所以能用向量化**；代价是**点查要拼 N 个列段、改一行要碰 N 个列段**——**这就是列存引擎的 UPDATE 普遍是异步按批的根本原因**。

选型三步：**① 先问访问模式**（点查 → 行存，聚合 → 列存）；**② 再问数据量**（千亿以下的行存大多够用，别一上来就上列存）；**③ 最后问维护成本**（两套存储 = 两套运维 + 一条同步链路）。

和 MySQL 侧呼应：冷热分离/归档解决的是"热查询背着冷数据跑"，而**分析型查询要隔离到列存或从库**，不能让它在主库上跑全表聚合。

**分层要点**：
- **结论**：根因是存储布局；行存利点查与改写，列存利聚合。
- **推导链**：布局 → 点查 vs 聚合的 IO 差异 → 列存 UPDATE 为什么按批 → 选型三步。
- **量化**：100 列取 2 列时 IO 差 60 倍以上。
- **边界与常见误解**："列存全面更好"×（点查和单行改写是它的短板）；数据量不大时用不上列存。

**追问**（先说后看）

1. **为什么列存的压缩率高？** —— **因为同列的数据类型相同、取值域窄、物理相邻**，"相似的东西挨在一起"让通用压缩算法能吃到大量重复。**注意：具体倍数取决于数据基数，是经验值**——正确说法是"取决于基数，要按自己的数据实测"，而不是给一个倍数。
2. **为什么 ClickHouse 这类引擎不适合高频单行更新？** —— **列存的物理结构决定的**：改一行要碰 N 个列段（100 列就是 100 处），只能实现成**异步重写整块数据**。所以它的更新语义是"最终一致的批量重写"，不是 ACID 事务。**要高频点更新就留在行存。**
3. **一张 100 列的表，MySQL 上跑聚合很慢，加索引能解决吗？** —— **不能根治**。索引解决的是"定位少数行"；**如果查询本来就要聚合掉大量数据，索引帮不上忙**——那是扫描量问题，属于"选错引擎族"。**先确认慢在哪**（是缺索引、写法问题，还是要扫的数据本来就多），再决定加索引还是换引擎。
4. **HTAP 是不是就不需要数仓了？** —— **不是**。它解决的是"同一份数据里分析与事务共存"，**跨系统的同步该有还是有**；而且它把成本从"同步链路"换成了"资源隔离 + 产品锁定"。**它是折中，不是终点。**
5. **为什么 OLAP 要有反规范化的宽表？** —— 因为**规范化是为了"更新不出错"，反规范化是为了"读得少"**——两者的代价正好是对方的目标。OLAP 允许冗余，是因为它的负载是"大量读、极少更新"，**规范化的更新保护在它这里换不到好处**。
6. **数据同步（ETL / CDC）会带来什么？** —— **一个必然的一致性窗口**。所以真正的选型问题不只是"分析要不要更快"，还有"**业务受不受得了这个窗口**"（报表要标注数据截止时间、实时决策类需求要另想办法）。

**同类变体**

- 「为什么大宽表在 OLAP 里反而好？」——**列存 + 宽表是配套的**：列存让"多列"不成为负担（只读用到的列），宽表让查询不用 join。**两者是同一个"少碰数据"的目标**
- 「DuckDB 为什么能嵌进进程里，还能很快？」——**它是列存 + 向量化执行 + 面向单机分析**（数驭穹图正是这么用的：`02` 写"PostgreSQL 只保存目录与状态，DuckDB 负责分析执行"）。**它证明"列存"这件事不依赖分布式**
- 「数据湖 / 湖仓是什么？」——**把数据以开放格式（如 Parquet）放在对象存储上，再由计算引擎去读**。数驭穹图的"轻量湖仓"就是这个思路的小型版：**存储与计算分开，算的时候才把列读进来**
- 「向量数据库算 OLAP 吗？」——**都不算**，它是第三类负载（近邻检索）。**但"按查询形状选结构"这条判据是同一条**（见 [[母题-G2-向量与关键词的混合检索]]）

**EnergyOps** —— 能耗数据是"写多、按时间窗聚合读"的形态，**天然偏分析类存储，但当前规模下选择"用现有库 + 受控并发 + 低优先级回补"顶住**：这是 4.2 那条算术的现场版——**"能不能不上，先算账"**。

**方言差异**：

| 同一件事 | 行存（MySQL / PG） | 列存（ClickHouse / Doris / DuckDB） |
|---|---|---|
| "改一行" | 原地改 / 版本链（MVCC） | **异步重写整块**（mutation / 合并） |
| "事务" | 强 ACID、跨行、可回滚 | 批量导入原子性；**无跨行事务** |
| 索引的用途 | **定位**（挑出少数行） | **裁剪**（跳过整块数据：min-max / 排序键） |
| 唯一性约束 | 主键 / 唯一索引，强制保证 | 通常不强制（**去重要在写入或查询时另做**） |
| 一条查询能吞多少行 | 要控制（会拖垮线上） | 上亿行是常态 |
