**题目**：某企业的数仓里有一张 `orders` 表，其中有三个金额字段：`order_amount`（下单金额）、`pay_amount`（实付金额）、`refund_amount`（退款金额）。

业务方问：**"上个月华东区的 GMV 是多少？"**

三个分析师给了三个答案：**A 说 `sum(order_amount)`，B 说 `sum(pay_amount)`，C 说 `sum(pay_amount) - sum(refund_amount)`**。而且还有第四个问题：**"上个月"是指下单时间还是支付时间？跨月的退款算哪个月？**

第二个问题：团队为了让 LLM 答对这个，给提示词里塞了 3000 字的"指标说明"。**这样做的问题在哪，正确的做法是什么？**

**母题**：自然语言问数的准确率上限到底卡在哪里，业务语义应该存在系统里还是提示词里，以及 Ontology 在 Agent 语境下指的是什么。

## 一、教材

### 1. 前提：模型没有业务先验，而业务事实是"人为确权"的结果

#### 1.1 一道题暴露的全部问题【事实】

【事实】回到开头那道题。**三个答案都能写出正确的 SQL 语法，但结果不同**——而这**不是模型的错，也不是 SQL 的错**：

```
"GMV" 这个词在企业里【没有唯一的技术对应】：
  · 口径一：下单金额 → sum(order_amount)          （含未支付、含已退款）
  · 口径二：实付金额 → sum(pay_amount)             （不含退款）
  · 口径三：净额     → sum(pay_amount) - sum(refund_amount)（扣退款）
  · 还有：口径四（含税/不含税）、口径五（含运费/不含运费）…

"上个月" 也没有唯一对应：
  · 按【下单时间】筛，还是按【支付时间】筛？
  · 上月下单但本月支付 → 算哪个月？
  · 上月支付但本月退款 → 是否回冲上月的数？

→ 这 3 × 2 = 6 种组合，都是"语法正确的 SQL"，
  只有【业务负责人】能说清哪个是对的。
```

【事实】**`projects/数驭穹图/03-数据目录与语义资产.md` 把这件事写成了一句话**：

> ***"模型看到 `pay_amount` 并不知道它是下单金额、实付金额还是退款后净额。企业分析中的大多数错误不是 SQL 语法错误，而是业务定义错误。因此，业务事实必须由数据管理员和业务负责人确权，模型只能映射和使用，不能自行创造。"***

【推导】**这条判断推出了本卡的全部结论**：

```
模型的能力边界不在"写 SQL"，在"不知道业务怎么定义"
→ 所以：让模型【猜】口径 = 必然时对时错，而且【错了看不出来】（语法全对）
→ 所以：正确形态是让模型【检索并应用已被确权的口径】
→ 所以：需要有一个地方【存放被确权的含义】，并让它可被检索、可版本化、可审计
→ 那个地方就是【语义层】
```

**到这里你应该能回答**：为什么"换一个更强的模型"解决不了这道题？

#### 1.2 语义的三种存放位置【取舍】

【取舍】**同一份业务含义，可以放在三个地方——它们的差别在于"谁能改、怎么验证、能不能审计"**：

| 放在哪 | 接入速度 | 可版本化 | 可评测 | 可审计 | 主要问题 |
|---|---|---|---|---|---|
| **① 人脑里**（分析师知道） | — | ✗ | ✗ | ✗ | **这就是"问数依赖分析师"的根源** |
| **② 提示词里** | **快** | ✗（改了就覆盖） | 弱 | ✗ | **上下文有限、易漂移、无法对账** |
| **③ 系统里**（语义层） | **慢**（要治理） | **✓** | **✓** | **✓** | **建设成本高，且需要业务方参与确权** |

【取舍】**"放进提示词"是最常见的偷懒解法**（第二个问题问的就是它）。**它的三个硬伤**：

```
① 上下文有限：企业核心指标几十上百个，全塞提示词会挤爆预算
   （[[母题-C1-上下文组装与窗口预算]]）
② 无法版本化：改了提示词就是覆盖，【"上周那个答案是按什么口径算的"无法回答】
③ 无法对账：发现某个数不对时，你无法确定是【口径写错了】还是【模型没遵守】
④ 无法评测：口径和提示词混在一起，指标回归测试就没有稳定的对象
⑤ 无法确权：谁批准的？什么时候生效的？什么条件下失效？
```

【推导】**语义层的价值不是"让模型更聪明"，而是"把含义变成一个有生命周期、可验证、可追责的对象"**——**它把"猜"变成"查"。**

### 2. 语义层是什么：三层知识 + 生命周期

#### 2.1 三层知识【事实】

【事实】**`03` 把语义资产分成三层，这个分层很干净**：

| 层 | 内容 | 更新方式 | 谁来负责 |
|---|---|---|---|
| **技术元数据** | 表、字段、类型、主键、分区、更新时间 | **自动抽取**（DDL diff） | 系统 |
| **业务语义** | 指标、维度、同义词、**口径**、关联、场景 | **人工确权 + 版本化** | 数据管理员 / 业务负责人 |
| **公共规则** | 日期、权限、单位、查询限制 | 平台统一维护 | 平台 |

【推导】**这个分层的意义在于"分工是由可信度决定的"**：

```
技术元数据：机器能读出来的 → 自动抽取，成本低、不会错
业务语义：  【机器读不出来】的 → 必须人来确权，成本高、是稀缺资源
公共规则：  横切所有查询的 → 平台一次定义，处处生效
→ 所以治理的精力应该【集中在中间那层】
→ 而"人力稀缺"这一点决定了：不可能把所有字段一次治完（见 2.4）
```

#### 2.2 一个指标要写清楚哪些东西【事实】

【事实】`03` 的"六节知识卡片"给出了**一个核心表的语义卡片该包含什么**：

```
① 元数据：来源、粒度、分区、更新频率、负责人
② 字段语义：主键、维度、指标、单位和限制
③ 场景映射：适合回答什么、不适合回答什么
④ 关联约束：合法的 JOIN、基数、一对多风险
⑤ 【指标口径：公式、过滤、去重、退款和时间定义】← 开头那道题的答案就写在这里
⑥ 高质量查询：已确认的示例 SQL 和边界案例
```

【推导】**值得注意第 ③ 和第 ⑥ 节**——**它们不是"描述数据"，而是"描述怎么用数据"**：

```
③ "不适合回答什么" —— 这个信息【防止模型在能力边界外硬答】
   （例：这张表没有实时数据 → 不要用它回答"现在有多少人下单"）
⑥ "已确认的示例" —— 这是【few-shot 的正确来源】：
   示例来自确权过的资产，而不是从历史查询里随便捞
   → 否则会【被污染的示例反复召回】，让错误 SQL 变成"标准答案"
     （`03` 的失败表里明确列了这条："示例污染 → 错误 SQL 被反复召回"）
```

#### 2.3 语义资产也需要生命周期【事实】

【事实】`03` 给语义资制定了状态机：

```
DRAFT → REVIEWED → PUBLISHED → DEPRECATED
```

【推导】**这个状态机解决的是"语义会过期"这个问题**：

```
表结构变了 → 指标口径失效
业务规则变了（例如"退款"的定义改了）→ 口径失效
负责部门调整 → 归属失效
→ 如果没有 DEPRECATED 这个状态，【旧口径会一直假装有效】
→ 而模型无法分辨"这条是现行口径还是三年前的"——它会一视同仁地用
```

【事实】**所以 `03` 的规则是**：*"查询只使用已发布且健康的数据集版本，并把语义版本写入查询 Provenance"*。

【推导】**"把语义版本写进查询溯源"这一条是整套设计的落点**：**它让"这个数字是按哪版口径算出来的"变成可回答的问题。** 没有它，事后对账只能靠猜。**这也是"权威状态"和"可审计"的落地方式。**

#### 2.4 语义资产也要有健康度【取舍】

【事实】`03` 监控这些信号：**字段覆盖率、核心指标口径完整度、JOIN 标注率、示例覆盖率、最近核验时间、回归通过率**。

【取舍】**这条最容易被忽略，但它决定了"治理到什么程度算够"**：

```
不可能一次性把所有字段都治完（人力稀缺）
→ 所以优先级是"核心指标先行"
→ 而且要有明确的【降级规则】：
   核心指标缺少正式定义时 → 【暂停该指标的自动问数】，而不是让模型猜
   （`03` 原文）
```

【取舍】**这一条是整个语义层设计里最有价值的判断**：**在"答得快"和"答得对"之间，它选择了"不确定就不答"**——**这与 [[母题-X1-容器是什么]] 里"权限不确定就 fail closed"是同一条原则。** 因为**在企业问数场景里，一个错误的数字比"我暂时查不了"的代价高得多**（数字会被拿去做决策、会被贴进汇报材料）。

### 3. 语义层与检索层是两件事

#### 3.1 分工：检索找候选，语义层做确权与约束【推导】

【推导】**这是本卡最容易被混淆的一处，值得单独说清**：

```
用户的自然语言问题："上个月华东区的 GMV 是多少"
        ↓
【检索层】找【候选】——哪几张表、哪些字段、哪些指标可能相关
   （向量检索按语义相似度找，关键词检索按字面命中找，两者互补
     → 见 [[母题-G2-向量与关键词的混合检索]]）
        ↓
【语义层】做【确权与约束】——GMV 的正式口径是什么、必须用哪个字段、
   必须加什么过滤（排除测试单？只算已支付？）、时间按哪个字段切、
   哪些 JOIN 是合法的（含基数约束，防金额膨胀）
        ↓
【生成层】按固定下来的语义生成结构化查询（SemQL → SQL）
        ↓
【验证层】结果对不对（粒度、总分、完整性、业务规则）→ 绑定证据
```

【推导】**两者的差别是**：

| | 检索层 | 语义层 |
|---|---|---|
| 回答的问题 | **"可能相关的是什么"** | **"正确的定义是什么"** |
| 结果性质 | **候选集**（可以有多个，可以排序） | **唯一判定**（必须有一个权威答案） |
| 出错的表现 | 召回不全（漏了相关的表） | **口径错**（用了错的定义） |
| 能不能用相似度 | **就是靠相似度** | **不能**——口径是"对/错"的问题，不是"像不像"的问题 |

【推导】**"不能用相似度解决口径问题"这一条很关键**：**如果你把"GMV = 实付金额"这句话塞进向量库，检索到它只是"找到了这个说法"，不代表它是现行有效的口径。** **确权必须有状态机与版本（2.3），这是检索做不到的。**

#### 3.2 所以"更好的提示词"为什么不够【推导】

【推导】回到第二个问题——**团队往提示词里塞 3000 字指标说明**：

```
它解决了什么：模型这次知道 GMV 的定义了
它没解决什么：
  ① 上下文预算：核心指标几十上百个，3000 字只是冰山一角
     （[[母题-C1-上下文组装与窗口预算]]：预算是有上界的，塞这个就挤掉别的）
  ② 无法按问题裁剪：每次都要塞全部，而不是"这个问题只涉及 3 个指标"
  ③ 改了没记录：口径变更后，无法回答"上周的报表按哪版算的"
  ④ 无法评测：口径和提示词耦合，指标回归测试没有稳定对象
  ⑤ 无法确权：谁批准、何时生效、什么条件失效——都不存在
  ⑥ 会漂移：模型对长提示词里中段的约束遵守度下降（长上下文的位置效应）
     → 表现是"有时遵守有时不遵守"，且难以复现
  ⑦ 无法对账：数字不对时，分不清是"提示词写错了"还是"模型没照做"

→ 正确的做法：
   ① 把口径放进【有状态机的语义资产】里（唯一正本）
   ② 【按问题先做 Schema/指标检索】，只把相关的少量定义注入上下文
      ← 这正是数驭穹图的链路：领域路由 → Schema Linking → SemQL
   ③ 把语义版本写进查询溯源（可对账）
   ④ 对核心指标建立回归集（可评测）
```

**到这里你应该能回答**：语义层解决的是"模型知不知道"，那它为什么还必须"可版本化、可审计"？

### 4. Ontology：一个被两种意思共用的词

> **这一节必须先分清词义，否则会答非所问。** 这是本卡最容易翻车的地方。

#### 4.1 两种用法【事实】

【事实】**"Ontology（本体）"在两个语境里指的是不同的东西**：

| | **① 学术/语义网传统** | **② 企业软件/Agent 语境（如 Palantir 的 Ontology）** |
|---|---|---|
| 指什么 | **对某个领域的概念体系做形式化描述**：概念、属性、关系、约束、公理 | **把企业数据组织成"可操作的对象层"**：对象（Object）、属性（Property）、关联（Link）、**动作（Action）** + 逻辑（Logic） |
| 关键技术 | RDF / OWL / SPARQL 这类标准与推理机 | 由厂商产品实现（**不是某个标准**） |
| 关注点 | **"如何无歧义地表达知识、并支持推理"** | **"如何让业务数据变成可被人与 AI 操作的东西"** |
| 和数据库的关系 | 往往自带三元组存储 | **底层还是企业原有数据源**，Ontology 是上面的一层建模 |
| 主要场景 | 知识工程、语义检索、专业领域建模 | **数据平台 / 数字孪生 / AI Agent 的操作层** |

【事实】**"知识图谱"与这两者的关系也要分清**：

```
Ontology（学术义）= 【概念层的定义】（有哪些类型、它们之间允许什么关系、有什么约束）
知识图谱          = 【实例化的数据】（具体有哪些实体、它们之间实际是什么关系）
→ 关系类似"类定义"与"对象集合"；知识图谱通常是某个 Ontology 的实例
而【厂商语境】的 Ontology 把这两者与"动作"揉在了一起，更接近"可操作的数据孪生"
```

【取舍】**面试里怎么用**：

```
如果对方问"你了解 Ontology 吗"，【先反问一句是在哪个语境】是安全的做法：
  "您指的是语义网里那套形式化本体（OWL/RDF），还是 Palantir 那种
   把数据+逻辑+动作打包的 Ontology 图层？"
→ 这两者的共同内核是【都强调"显式地表达含义，而不是让它隐含在代码里"】
→ 而这个内核，正是本卡第 1 节说的那件事
```

#### 4.2 为什么它在 Agent 时代变热了【推导】

【推导】**因为 Agent 与"只看不写"的 BI 有一个根本差别**：

```
BI / 报表：只【读】数据 → 只要口径对、SQL 对，就够了
Agent    ：还要【写】——下单、退款、发券、改状态、发起审批
→ 光知道"GMV 是什么"不够了，还要知道：
   · 一个"订单"对象上允许做哪些动作？
   · 什么状态下允许（"已发货"不能取消）？谁有权做？
   · 做完之后状态怎么变、要不要通知下游？
→ 这些"动作及其前置条件与后果"必须有地方声明
→ 这就是厂商语境 Ontology 里 Action / Logic 那一层的意思
```

【推导】**这与库里已有的两条线直接接上**：

```
· Ontology 的"动作"层 ≈ 【工具（Tool）的边界与契约】
  → [[母题-A2-工具调用与MCP边界]]：工具要声明严格的输入 schema、
    要服务端注入租户与身份（不信任模型传参）
  → 数驭穹图 `07` 的写法就是范例：SQL 执行前过 AST 检查、
    租户过滤由服务端施加、任何不确定就 fail closed
· Ontology 的"对象"层 ≈ 【语义层】
  → 只是范围从"分析可用的指标"扩展到"可被操作的业务实体"
```

【取舍】**一句话概括这个趋势**：**数据平台从"存事实"走向"存事实的含义"，再走向"存含义 + 可执行的动作"**——**因为有了 Agent，系统必须对"什么动作是允许的"给出显式答案，而不能指望调用方自己判断。**

#### 4.3 但要注意边界【取舍】

【取舍】**这一块要避免两种过度反应**：

```
① 不要为了"有个 Ontology"而建本体
   → 数驭穹图 `03` 的"钢人比较"写得很清楚：
     *"只使用 DDL 和模型推理接入快、维护少，适合结构简单的 Demo；
       完整语义层建设成本高"*
   → 它的选择是【自动生成技术部分 + 人工确认高价值业务部分】，
     【不追求所有字段一次性治理】
   → 这才是务实的形态：不是"建一套完整本体"，而是"按核心指标逐步确权"（2.4）

② 不要把厂商概念当标准来答
   → Ontology 在厂商语境里【不是一个通用标准】，而是产品设计理念
   → 面试里说"我们用了 Ontology"而不解释具体机制 = 空话
   → 有说服力的说法是描述机制：
     "我们维护了一份带状态机与版本的指标语义资产，
      按问题检索后注入，并把语义版本写进查询溯源"
```

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "换个更强的模型就能解决 NL2SQL 的准确率问题" | 【推导】**换模型解决不了"模型不知道业务怎么定义"**（1.1）。**语法错误模型很少犯，业务定义错误才是主要来源**——而后者要靠**确权过的语义资产**解决，不是靠模型能力 |
| "把指标说明写进提示词就行了" | 【取舍】**它解决"这次知道"，不解决"可版本化、可评测、可对账、可确权"**（3.2 的七条）。而且**长提示词会漂移**，表现是"有时遵守有时不遵守" |
| "Ontology 就是知识图谱" | 【事实】**两者不是一回事**（4.1）：**Ontology 是概念层的定义（有哪些类型、允许什么关系与约束），知识图谱是实例化的数据（具体有哪些实体与关系）**。而**厂商语境的 Ontology 是第三个东西**——它把数据、逻辑、动作打包成可操作层 |
| "语义层就是给字段加中文注释" | 【取舍】**注释是"人能看懂"，语义层是"机器能执行"**（2.2）：注释里写"这是 GMV"没有用，**必须有公式、过滤条件、去重规则、时间字段定义**——**要被生成成 SQL**，而不只是被读 |
| "相似度检索能找到相关的指标定义，就够了" | 【推导】**检索解决"找到"，不解决"哪个是现行有效的"**（3.1）。**口径是"对/错"问题而不是"像不像"问题**——必须有权威状态与版本，才能回答"这条定义还生效吗" |
| "有了语义层就不需要业务方参与了" | 【事实】**恰好相反**：`03` 明确*"业务事实必须由数据管理员和业务负责人确权，模型只能映射和使用，不能自行创造"*。**语义层是把"业务方参与"这件事变成一次性投入（确权一次，处处复用），不是取消它** |
| "指标口径错了改一下就行，反正报表每天刷新" | 【取舍】**要算代价**：一个错的口径会**进入决策、汇报材料、对外口径**，而这些**不会随报表刷新而自动纠正**。**这也是为什么"核心指标缺定义时应暂停自动问数"比"先给个数"更划算**（2.4） |
| "语义资产建好就不用管了" | 【事实】**它有生命周期**（2.3）：表结构变、业务规则变、归属调整都会让它失效。**没有 DEPRECATED 状态，旧口径会一直假装有效**，而模型分不出来 |
| "Agent 只需要读数据的能力" | 【推导】**那就只是 BI**（4.2）。**Agent 要"做事"就必须知道"什么动作在什么状态下允许"**——这正是工具契约与 Ontology 的 Action 层要解决的问题 |

## 二、自测

**Q1（判读）**：业务方问：**"为什么上周的转化率掉了？"** 系统里有三张表：`orders`（下单）、`payments`（支付）、`visits`（访问）。已知：

- `visits` 表**只统计了 App 端**，Web 端的数据在两年前就停止接入了
- "转化率"在不同部门的定义不同：**市场部**用"下单数 / 访问数"，**财务部**用"支付数 / 访问数"
- 数据**同步延迟 4 小时**

问：如果没有语义层，模型最可能怎么答？错在哪？

**A1**：

```
模型最可能做的事：
  ① 搜到 visits 表有数据 → 用它算访问数
  ② 搜到 orders 和 payments → 【自己选一个】当分子
  ③ 生成一个【语法完全正确】的 SQL → 给出一个数字
  ④ 顺便可能编一个"可能原因"（这是更危险的部分）

四处错：
  ① 【数据范围错】：visits 只有 App 端 → 这个"转化率"的覆盖面是残缺的
     → 正确做法是【在语义层里声明"visits 表只含 App 端"】，
       并让系统在回答时【主动声明口径范围】，而不是默认它代表全量
  ② 【口径歧义未澄清】：市场部和财务部定义不同 → 应该【触发澄清】
     （数驭穹图 `04-意图识别与歧义澄清.md` 正是处理这个：
       "同名指标跨域 → 选错口径 → 领域路由 + 限定选项澄清"）
  ③ 【新鲜度未声明】：同步延迟 4 小时 → 回答必须带上"数据截止时间"
     （否则用户以为这是实时数据）
  ④ 【因果推断越界】：从"转化率掉了"直接给原因 = 幻觉
     （[[母题-C4-幻觉的成因与可控性]]）

★ 关键：这四处错【没有一处是 SQL 语法问题】——
  全是"业务定义与数据边界"的问题。
  → 这正是 1.1 那条判断的完整展开：
    "企业分析中的大多数错误不是 SQL 语法错误，而是业务定义错误"
```

**Q2（计算）**：某企业有 **120 个核心指标**，每个指标的完整口径说明（公式 + 过滤 + 去重规则 + 时间定义 + 边界案例）平均约 **150 字**。

问：① 全部塞进提示词需要多少字？② 如果模型上下文是 128K token（按中文约 1 字 ≈ 1 token 估），占总预算的多少（假设系统提示 + 工具定义 + 对话历史已占 20K token）？③ 实际该怎么注入？④ 这样省下了什么？

**A2**：

```
① 120 个 × 150 字 = 【18000 字】≈ 18000 token

② 可用预算 = 128K - 20K = 108K token
   占比 = 18000 / 108000 ≈ 【16.7%】
   ★ 看起来"还能塞"——但这只是【口径】这一项，
     还没算：表结构、字段说明、示例 SQL、关联约束、权限规则
   → 真实情况是这个数会迅速膨胀到吃掉大部分预算
   → 而且【每次请求都付这个成本】：token 是钱，延迟也是钱
     （[[母题-C6-成本与长上下文截断]]）

③ 正确做法：【按问题检索后再注入】
   用户问题 → 领域路由 / 意图澄清 → Schema Linking（检索相关表与指标）
   → 只注入【这次真正用到的 3–5 个指标定义】+ 相关表结构
   → 约 5 × 150 = 750 字 ≈ 1000 token
   → 从 16.7% 降到 【不到 1%】

④ 省下的不只是钱：
   · 上下文预算（给对话历史、工具结果、错误重试留出空间）
   · 【遵守度】：短而精准的约束比长提示词更容易被遵守
     （长上下文里中段的约束遵守度会下降）
   · 【可评测性】：注入的是"哪个指标的哪一版"，回归测试有稳定对象
   · 【可解释性】：出问题时能回答"当时注入了哪几个指标定义"
```

【这一步在验证什么】验证 3.2：**"放进提示词"不只是"不够好"，它在成本和可靠性上都是不可行的**——**语义层 + 按需检索是唯一能规模化的形态。**

**Q3（判读）**：一位面试官问：**"你们项目里用 Ontology 了吗？"**

问：直接回答"用了"或"没用"分别有什么问题？该怎么回答？

**A3**：

```
直接说"用了"的问题：
  Ontology 有两种以上常见含义（4.1），
  → 你不知道对方问的是【语义网那套形式化本体】还是【Palantir 那种对象+动作层】
  → 贸然说"用了"，后面被追问"你们用什么推理机 / 三元组存哪"就会露馅

直接说"没用"的问题：
  → 如果你是做 NL2SQL 的，这个回答【明显不完整】——
    你的项目【必然】处理了"业务语义存在哪"这个问题，
    只是不一定叫 Ontology
  → 会错过一次展示架构能力的机会

正确的回答（三步）：
  ① 【先澄清词义】：
     "Ontology 这个词我看过两种用法——一种指语义网里的形式化本体
      （OWL/RDF 那套，重点在推理），另一种指把数据、逻辑、动作
      打包成可操作层的那种（比如 Palantir 的 Ontology）。
      您指的是哪一个？"
  ② 【再给共同内核】：
     "两者的共同内核都是【显式地表达业务含义，而不是让它隐含在代码里】。
      这一点我们的项目里是有的。"
  ③ 【最后用机制描述代替名词】：
     "我们维护了一份带状态机与版本的指标语义资产——
      三层：技术元数据自动抽取、业务语义人工确权、公共规则平台统一；
      核心表有六节知识卡片（口径、关联约束、适用场景、示例查询）；
      状态是 DRAFT → REVIEWED → PUBLISHED → DEPRECATED，
      查询只使用已发布版本，并把语义版本写进查询溯源。
      如果按您的第一种定义，我们没做形式化推理；
      按第二种定义，我们的语义资产就是它的对象层，
      只是还没有'动作'那一层——因为我们目前只读不写。"

★ 这个回答的价值：把"一个名词对不对得上"变成
  "我的系统里这件事是怎么解决的"——这才是面试官想听的。
```

**Q4（纠错）**：下面这段话哪里错了？

> "我们把公司所有的指标定义、表结构说明、业务规则都整理成文档，然后全部塞进系统提示词里。这样模型就具备了完整的业务知识，NL2SQL 的准确率应该能大幅提升。"

**A4**：**三处错。**

1. **"全部塞进系统提示词"在工程上不可行**：**上下文预算是有上界的**（[[母题-C1-上下文组装与窗口预算]]）。企业级的表结构 + 指标 + 规则会远超预算（Q2 算过：**只算 120 个核心指标就吃掉 16.7%**，还没算表结构与示例）。**正确形态是按问题检索后只注入相关部分。**

2. **"具备完整的业务知识"这个说法不准确，而且掩盖了最大的风险**：**模型拿到定义，不等于会稳定遵守**。长提示词有位置效应——**中段的约束遵守度会下降**，表现为"有时遵守有时不遵守"，**而这类问题极难复现和定位**。

3. **最关键的一处：它把"文档"当成了"语义资产"**。**两者的差别，正是语义层存在的理由**：

```
文档：给人看的 —— 没有状态、没有版本、没有生效条件、没有权威性判定
语义资产：给机器执行的 ——
   有状态机（DRAFT → REVIEWED → PUBLISHED → DEPRECATED）
   有版本与生效条件
   有公式与过滤（能被生成成 SQL，不只是能被读）
   有溯源（语义版本写进查询记录 → 可对账）
→ "整理成文档"解决的是【人能看懂】，
  而系统需要的是【机器能执行 + 能验证 + 能追责】
```

**准确说法**：*把口径整理出来是必要的第一步，但把文档塞进提示词只是把问题搬了个位置。正确的做法是把它们做成有状态机、有版本、有溯源的语义资产，再按问题检索后只注入相关的那几条，并把语义版本写进查询溯源——这样才同时得到成本、可靠性和可审计性。*

**Q5（纠错）**：下面这段话哪里错了？

> "语义层的本质就是给数据库字段加注释、给表加中文名，让模型更容易理解。所以这事主要是文档工作，写清楚就行了。"

**A5**：**两处错，而且第二处错得比较关键。**

1. **"给字段加注释"完全不够**：**注释是"描述性"的，语义层需要的是"可执行性"的**（2.2）：

```
注释能写："pay_amount 是实付金额"
语义资产要写：
   · 公式：GMV = sum(pay_amount) - sum(refund_amount)
   · 过滤：排除测试单 / 只算已支付 / 是否含税
   · 去重：是否按 order_id 去重（防 JOIN 膨胀导致重复计和）
   · 时间：口径按【支付时间】切分；跨月退款【回冲当月】
   · 关联约束：与会员表的合法 JOIN、基数（一对多会让金额膨胀）
   · 适用场景：不适合回答实时问题（同步延迟 4 小时）
→ 注释能被人读懂就够了；语义资产【要能被生成成正确的 SQL】
```

2. **"主要是文档工作"错在低估了它的系统属性**：**语义资产的难点不在"写"，在"管"**：

```
· 生命周期：表结构变了、业务规则变了 → 谁负责更新？（状态机 + 负责人）
· 权威性：谁批准的？什么时候生效？—— 需要【确权流程】而不是"谁写的算谁的"
· 可发现：几十上百个指标，怎么在提问时【找到相关的那几个】？（检索层）
· 可验证：怎么知道它是对的？（回归集 + 健康度指标）
· 可追溯：这个数字是按哪版口径算的？（语义版本写进 Provenance）
→ 这些是【系统设计问题】，不是写作问题
```

**准确说法**：*语义层的核心不是"写文档"，而是"把业务含义变成一个有生命周期、可确权、可检索、可追溯到具体版本的资产"。注释只能让人看懂；语义资产要能被生成成 SQL、能被回归测试、能在事后回答"这个数按哪版口径算的"。*

## 三、面试输出（学完再看）

**一句话结论**：**NL2SQL 的准确率上限不在模型，在"业务定义"**——**模型没有业务先验**，它看到 `pay_amount` 不知道这是下单金额、实付还是净额；而**企业分析中的大多数错误不是 SQL 语法错误，而是业务定义错误**（语法全对但口径错，而且**错了看不出来**）。所以正确形态不是"让模型猜口径"，而是**把口径做成可检索、可版本化、可审计的语义资产**：**三层知识**（技术元数据自动抽取 / 业务语义人工确权 / 公共规则平台统一）、**状态机**（DRAFT → REVIEWED → PUBLISHED → DEPRECATED）、**查询只用已发布版本并把语义版本写进溯源**。**把口径塞进提示词是最常见的偷懒解法**，它的硬伤是上下文有上界、改了没记录、无法对账、无法评测、会漂移——**正确做法是按问题检索后只注入相关的那几条**。**Ontology 这个词有两种用法**：学术义指**概念层的形式化定义**（与"实例化的知识图谱"是"类定义 vs 对象集合"的关系），厂商语境指**把数据、逻辑、动作打包成可操作层**——**两者的共同内核都是"显式表达含义，而不是让它隐含在代码里"，而这个内核在 Agent 时代变重要，是因为 Agent 还要"做事"，必须知道什么动作在什么状态下允许。**

**恢复关键词**：**模型没有业务先验** / 错误主要来自**业务定义**而不是语法 / 同一个词 3 口径 × 2 时间维度 = 6 个"语法正确的答案" / 语义的三种位置（人脑 / 提示词 / 系统）/ **提示词的五个硬伤**（预算、无版本、无法对账、无法评测、会漂移）/ **三层知识**（技术元数据 / 业务语义 / 公共规则）/ 六节知识卡片（**口径与关联约束是核心**）/ **状态机 + 语义版本进溯源** / **检索找候选，语义层做确权**（相似度解决不了"哪个现行有效"）/ **Ontology 两种用法**：形式化本体 vs **数据+逻辑+动作的可操作层** / Ontology 的 Action 层 ≈ **工具契约**（[[母题-A2-工具调用与MCP边界]]）/ **核心指标没定义时暂停自动问数**（fail closed）

**核心不变量 / 主线**：
**"含义"必须是一个可以被系统管理的东西，而不是散在人脑、代码和提示词里的隐式约定。** 这条主线能解释语义层的全部设计：**为什么要有状态机**（含义会过期）、**为什么要确权**（含义必须唯一且被授权）、**为什么要检索**（含义太多，上下文装不下）、**为什么要写进溯源**（含义有多版本，事后要对账）。**把"含义"从隐式变成显式，就是这一整层的意义。**

**完整回答骨架**：先用一道口径题暴露问题（同一句话 6 个"正确"答案）→ 给根因（**模型没有业务先验 / 错误主要来自业务定义**）→ 语义的三种存放位置对比 → 语义层是什么（三层知识 + 六节卡片 + 状态机 + 健康度 + fail closed）→ 区分检索层与语义层 → 拆"塞提示词"为什么不够 → Ontology 的两种用法与为什么现在热（**因为 Agent 要做事**）→ 边界（不要为了建本体而建本体）

**完整回答（口述稿）**：
**NL2SQL 的准确率上限不在模型，在"业务定义"**——**模型没有业务先验**，它看到 `pay_amount` 不知道这是下单金额、实付还是净额。而**企业分析中的大多数错误不是 SQL 语法错误，而是业务定义错误**（语法全对但口径错，**而且错了看不出来**）。

所以正确形态不是"让模型猜口径"，而是**把口径做成可检索、可版本化、可审计的语义资产**：**三层知识**（技术元数据自动抽取 / 业务语义人工确权 / 公共规则平台统一）、**状态机**（DRAFT → REVIEWED → PUBLISHED → DEPRECATED）、**查询只用已发布版本，并把语义版本写进溯源**。

失败时怎么答：**口径不确定就返回候选口径让人确认，而不是硬选一个**——这和其他地方的"拒答"是同一条原则：**把自信的错误换成坦白的不确定，错误越贵越值钱**。

和数驭穹图的落点一致：上下文里只装**当前领域 Schema + 权限过滤后的候选表 + 关键样例**，且 Schema 版本、Prompt 版本与结果绑定。

**分层要点**：
- **结论**：瓶颈在业务定义不在模型；口径要做成版本化的语义资产，语义版本进溯源。
- **推导链**：模型无业务先验 → 错误形态是口径错且看不出来 → 三层知识 + 状态机 → 只用已发布 → 不确定就让人确认。
- **量化**：无（工程形态为主）。
- **边界与常见误解**："再换个更强的模型就能提高 NL2SQL 准确率"×；口径冲突时不能偷偷选一个。

**追问**（先说后看）

1. **为什么说 NL2SQL 的瓶颈是"口径"而不是模型能力？** —— **因为模型没有业务先验**（1.1）。同一个词在不同部门有不同定义，同样的 SQL 语法正确但结果不同，**而且错了看不出来**。**模型能做的是"映射与使用"，不能是"创造定义"**——后者必须由业务负责人确权。
2. **语义层和知识图谱什么关系？** —— **要分清三层**（4.1）：**Ontology（学术义）= 概念层的定义**（有哪些类型、允许什么关系与约束）；**知识图谱 = 实例化的数据**（具体有哪些实体与关系）；**厂商语境的 Ontology = 数据 + 逻辑 + 动作的可操作层**。**"类定义 vs 对象集合"是理解前两者的关键。**
3. **为什么不把所有指标定义写进系统提示词？** —— **四件事同时不成立**（3.2）：上下文有上界（Q2：只算 120 个核心指标就吃掉 16.7%）、无法版本化、无法对账、长提示词会漂移。**正确做法是按问题检索后只注入相关的那几条，并把语义版本写进溯源。**
4. **语义资产为什么需要状态机？** —— **因为含义会过期**（2.3）：表结构变了、业务规则变了、负责部门调整了——**没有 DEPRECATED，旧口径会一直假装有效，而模型分不出来**。配合"语义版本写进溯源"，才能事后回答"这个数按哪版算的"。
5. **Agent 场景下，语义层要多做什么？** —— **多一层"动作"**（4.2）：BI 只要读，Agent 要写（下单、退款、改状态）——**系统必须显式声明"什么动作在什么状态下允许、谁有权做"**，这就是工具契约（[[母题-A2-工具调用与MCP边界]]）与厂商语境 Ontology 的 Action 层。
6. **什么情况下不该建完整语义层？** —— **看数据复杂度与团队规模**（4.3）：数驭穹图的"钢人比较"写得很清楚——**只用 DDL + 模型推理接入快、维护少，适合结构简单的场景；完整语义层建设成本高。** 它的选择是**"自动生成技术部分 + 人工确认高价值业务部分，不追求所有字段一次性治理"**——**按核心指标逐步确权才是务实形态。**

**同类变体**

- 「Schema Linking 是什么？」——**在提问时找出"哪几张表、哪些字段相关"**（数驭穹图 `05`）。**它是检索层的工作，是语义层的前置步骤**
- 「为什么 NL2SQL 要中间加一层 SemQL？」——**把"自然语言的理解结果"固化成结构化中间表示**（数驭穹图 `06`）：这样**意图澄清、语义校验、权限检查、成本估算都可以在生成 SQL 之前做**，而不是等 SQL 出来再改
- 「结果验证怎么做？」——数驭穹图 `09` 的粒度、总分、完整性、业务规则四类验证 + **证据绑定**（查询指纹、数据快照、语义版本）——**这是"语义层可追溯"在结果侧的落地**
- 「这和 RAG 什么关系？」——**同一套思路的两个应用**：RAG 是把"文档知识"从模型参数搬到可检索的外部资产；**语义层是把"业务定义"从人脑/提示词搬到可管理的外部资产**。**两者都基于同一个判断：模型内部没有可靠的知识与口径，必须外置。**
