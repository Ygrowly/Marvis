## 一、教材

### 1. 前提：一个存储的能力边界，由它的"索引结构"决定

#### 1.1 关系库的强项到底是什么【事实】

【事实】**关系数据库最强的是"按值精确定位"与"自由组合的过滤与关联"**：

```
B+ 树索引擅长：等值查询（=）、范围查询（> < BETWEEN）、前缀匹配（LIKE 'abc%'）
              排序（ORDER BY 走索引）、多条件组合（联合索引）
JOIN 擅长    ：按声明的关联关系把多张表拼起来，且有约束保证正确性
事务擅长     ：跨行跨表地保证"要么全成要么全不成"
```

【推导】**这些强项的反面就是它的边界**：

| 查询形状 | 为什么关系库做不好 |
|---|---|
| **全文模糊匹配**（`LIKE '%关键词%'`） | **前置通配符用不上 B+ 树**——跳过不了任何数据，只能全表扫。**而且没有"相关性排序"这个概念**（"哪个更相关"是检索问题，不是过滤问题） |
| **按几何距离找最近邻** | B+ 树按"值的大小"排序，**而"相似度"不是可排序的一维标量**——它要靠专门的索引结构（HNSW / IVF 这类） |
| **多跳关系遍历**（"朋友的朋友里买过 X 的人"） | 关系库要靠**反复 JOIN**，每多一跳就多一次关联；而**图结构在多跳时的代价是线性的、而且是随深度组合爆炸的** |
| **结构频繁变化** | 关系库的 schema 是**强约束的**（要改字段就得 DDL）；**字段经常变意味着 DDL 经常变**——在这张表还大的时候直接撞上维护成本（[[母题-S2-单机不够了怎么扩]] 1.2） |
| **纯键值的超高频读写** | 关系库有事务、有 WAL、有约束——**这些在"只按 key 取一个 value"的场景里全是纯开销** |

【推导】**所以判断标准只有一句话**：

> **看这次查询的"入口"是什么。** 入口是**主键/范围** → 关系库；是**关键词** → 检索库；是**向量距离** → 向量索引；是**关系路径** → 图；是**纯 key** → 键值库。

**入口决定结构，结构决定引擎。** 这是本卡的唯一判据。

#### 1.2 那不是"关系库做不到"，是"不划算"【取舍】

【事实】**上面五件事，关系库其实都能做**（`LIKE`、递归 CTE、JSONB 字段、`pg_trgm` 扩展…）。

【取舍】**但能不能做与划不划得来，是两件事**：

```
能做 ≠ 划得来
① 全表扫描式模糊匹配：数据量小时没事，量一大就是拖垮线上（[[母题-S2-单机不够了怎么扩]] 1.1 的"分析干扰"）
② 相似度检索：就算算出来，也无法用索引加速 → 每次都要全量算距离
③ 多跳遍历：深度一上来，JOIN 的组合数就爆炸（同样能写出来，但跑不动）
④ JSONB 存灵活字段：能存，但【按 JSON 内部字段过滤与聚合的代价远高于普通列】，
   而且失去了类型约束与统计信息
```

**到这里你应该能回答**：为什么"MySQL 加个索引"这句话，在这四个需求上都答不到点上？

### 2. 五类专有存储：各自为哪种"查询形状"而生

> **先各自介绍，不比较。** 每一条都按"它擅长什么 → 这个擅长来自什么结构 → 它牺牲了什么"三段说。

#### 2.1 键值 / 缓存（Redis 为代表）【事实】

- **擅长的入口**：**key**（单 key 读写、计数、过期）
- **结构来源**：数据放内存 + 哈希表定位 → **"按 key 找到值"这件事是 O(1) 的内存访问**
- **它牺牲了什么**：

```
① 内存成本远高于磁盘（所以容量必须靠"哪些数据值得放内存"来筛）
② 事务与持久化的强度通常远低于关系库
③ 查询能力极弱：没有 SQL、没有 join、复杂条件过滤要在客户端做
④ 【易失性】：无论是淘汰策略（内存满了要淘汰）还是部署形态（进程可能被拿走、
   容器内存有上限，见 [[母题-X1-容器是什么]]），它都不是"存了就不会丢"的地方
```

【取舍】**所以它的正确定位是"加速层"，不是"权威层"**——**能重新算出来的东西（缓存、计数器、队列进度）放它，丢了算不出来的东西（订单、余额、账）不放它。** 这条判断在 [[母题-R5-缓存的边界]] 已完整展开。

#### 2.2 文档（MongoDB 为代表）【事实】

- **擅长的入口**：**文档 ID**，以及"整取整存一个结构不固定的对象"
- **结构来源**：**一个对象（及其嵌套结构）作为整体存储** → 读一个文档通常一次拿到全部；**schema 灵活**（同一集合里的文档字段可以不同）
- **它牺牲了什么**：

```
① 多文档事务：能力与成熟度通常弱于关系库（跨文档一致要靠事务支持，且有代价）
② 多表关联：本来就不鼓励 join（鼓励把数据嵌进同一个文档）
   → 代价是【数据冗余】与【更新时要改多处】
③ 复杂聚合：能做，但代价与可维护性不如 SQL
④ 约束：schema 灵活的另一面是【没有编译期/约束期的类型保护】
```

【取舍】**它的甜点区是"以对象为单位读写、结构会变、不需要跨对象事务"**——例如用户档案、配置、内容快照、事件原文。**它的雷区是"需要跨对象强一致的账务类数据"。**

#### 2.3 搜索引擎（Elasticsearch 为代表）【事实】

- **擅长的入口**：**关键词 / 全文**，以及"按相关性排序地取回一批文档"
- **结构来源**：**倒排索引**——`词 → 出现过这个词的文档列表`。**这与 B+ 树是相反的组织方式**：B+ 树按"值的顺序"排，倒排索引按"词"反查文档集合
- **它牺牲了什么**：

```
① 它不是为"事务"设计的：通常没有跨文档 ACID 事务
② 它不是为了"权威存储"设计的：默认的写入可见性与刷新周期是【近实时】而非实时
   → 写进去的数据不保证立刻可搜到（这是设计选择，不是 bug）
③ 数据量大时索引本身的成本很高（倒排索引要占额外空间、合并要资源）
④ 更新语义通常是"重写文档"，不是"改字段"
```

【取舍】**所以它正确的角色是"检索层"，权威数据在别处，它是一份为检索优化的副本。** **"用 ES 当唯一数据源"是经典事故**——因为它的持久性与事务语义不是为承担这个责任设计的。

#### 2.4 向量索引（Milvus / Qdrant / pgvector 等）【事实】

- **擅长的入口**：**一个向量**，要"找出与它最相似的 Top-K"
- **结构来源**：**近似最近邻索引（如 HNSW、IVF 这类）**——**接受"近似的"结果，换来从"全量算距离"变成"只算一小部分"**（详细取舍见 [[母题-G2-向量与关键词的混合检索]]）
- **它牺牲了什么**：

```
① 【近似】：不保证找到真正最近的 K 个（这是它的核心取舍，不是缺陷）
② 向量不是人类可解释的检索条件 —— 无法精确约束（"必须有这个词"要靠关键词检索补）
③ 更新与过滤的代价：向量索引的增量插入/删除有额外开销，
   而"先按元数据过滤再检索"的策略会影响召回率
④ 运维与容量独立于主数据库（除非用 pgvector 这类"嵌入关系库"的形态）
```

【取舍】**它的选型分岔很清晰**：

```
数据量小 / 已有 PostgreSQL / 想要"一份数据一个事务"  → pgvector（嵌进关系库）
数据量大 / 独立运维 / 需要专门的向量能力（多路召回、混合检索） → 独立向量库
```

**pgvector 的价值是"少引入一个引擎"**（第 4 节的账）；**独立向量库的价值是"把向量检索做到专业水平"**。**两者不是先进与落后，是同一道账的两端。**

#### 2.5 图（Neo4j 等）【事实】

- **擅长的入口**：**一个节点**，要"沿关系走 N 跳"
- **结构来源**：**把关系本身当作一等公民存储**（邻接关系是物理上的直接引用）→ **走一跳的代价与"这个节点的度数"有关，与"全图有多少节点"无关**
- **它牺牲了什么**：

```
① 全量扫描与聚合类查询通常弱于关系库（它不为此优化）
② 生态与人才池比关系库小得多
③ 分片很难（图天然是"高度关联"的，切开关系就要跨网络）
④ 大多数业务场景其实用不上——【"有外键"不等于"需要图数据库"】
```

【取舍】**它的真实适用面比宣传中窄**：**只有当查询形状是"深度多跳 + 实时"时才有明显优势**（反欺诈链路、推荐的关系传导、知识图谱推理）。**两三层关联的查询，关系库的 JOIN 完全够用。**

**到这里你应该能回答**：这五类存储，能不能用一句"它的入口是什么"各自概括？

### 3. 回到题目：四个需求各自该去哪

【推导】

| 需求 | 查询入口 | 该去哪 | 为什么 |
|---|---|---|---|
| **① 标题模糊搜索 + 拼音 + 同义词** | **关键词** | **搜索引擎** | 倒排索引 + 分词 + 相关性排序是它的本职工作；`LIKE '%x%'` 用不上 B+ 树且无法按相关性排序 |
| **② token 毫秒级读写 + 自动过期** | **key** | **Redis** | 内存 + key 过期是它的本职；关系库做这件事要付事务与 WAL 的纯开销 |
| **③ 语义相似检索** | **向量** | **向量索引**（独立库或 pgvector） | 相似度不是可排序标量，B+ 树帮不上忙 |
| **④ 字段结构经常变** | **对象 ID**（整取整存） | **文档库**（若确实需要）**或者 JSONB 字段** | 关键判断：**是"整取整存、不需要对这些字段做复杂查询"，还是"要对这些字段频繁过滤聚合"** |

【取舍】**④ 是本卡最重要的一个"不急着加引擎"的例子**：

```
要问三件事：
  ① 这些灵活字段的【读写模式】是什么？
     整取整存（读一个对象就要全部字段）→ 文档库确实合适
     要按这些字段过滤/聚合/排序        → 关系库的 JSONB 会很难受，但【先看数据量与频率】
  ② 现在有几张表需要这样？1–2 张 → 用 JSONB 顶住；到处都是 → 才考虑文档库
  ③ 引入文档库后，这些数据和主库的关系是什么？
     如果它要跟主库的数据做关联 → 又多了一份要对齐的数据（第 4 节）
```

**结论：① 该上检索库；② 该用 Redis；③ 该上向量能力（优先考虑 pgvector，如果规模和能力要求没到独立库的必要）；④ 先别急着加引擎，用 JSONB 顶住，同时明确"什么信号出现时再换"。**

### 4. 多引入一个引擎要付什么账

> **这一节是本卡的落点。** 五类存储的差异是知识，**"该不该引入"是判断**——而判断的依据是这张清单。

【事实】**`summaries/oceanBase.md` 里得物的现状就是这张清单的实证**：它的在线体系里同时有 **MySQL、TiDB、MongoDB、HBase、DuckDB、ClickHouse、StarRocks、向量库**，而这份材料把它带来的问题列得很清楚：

```
运维复杂   —— 不同数据库需要不同的监控、备份、迁移和故障处理方法
研发选型困难 —— 业务需要判断什么数据放在哪类数据库里
架构链路复杂 —— 主库、异构从库、同步工具、应用层分流相互依赖
数据一致性风险 —— 不同系统之间通常是异步同步，存在延迟
资源利用率低 —— 低 QPS 实例仍需维持最低资源配置
TP 与 AP 互相影响 —— 在线事务和复杂分析查询争夺 CPU、IO、锁和缓存
```

【推导】**把它压缩成"引入一个新引擎的固定成本"（注意：**这份成本不随数据量缩小**）：

| 成本 | 具体是什么 |
|---|---|
| **① 新增一条同步链路** | 数据怎么进去？双写（要处理一边成功一边失败）还是 CDC（要维护同步组件）？**这是最容易低估的一项** |
| **② 新增一个"谁是准的"问题** | 两份数据必然出现对不上的时候。**必须提前定好：以哪边为准、怎么对账、不一致时怎么办** |
| **③ 新增一个失败点** | 它挂了业务怎么办？降级还是阻塞？**降级路径要提前设计**（不是故障时现想） |
| **④ 新增一套运维与监控** | 备份、扩容、版本升级、慢请求排查、容量规划——**每一项都要有人会** |
| **⑤ 新增一层学习与协作成本** | 每个改这块代码的人都要知道"这个数据在哪个引擎、要不要两边写" |
| **⑥ 新增一份存储与资源** | 副本意味着至少多一份数据；专用引擎往往还要求独立的实例规格（**低负载也要占最小资源**） |

【取舍】**所以引入判据是**：

```
引入新引擎 = 划算，当且仅当：
  【它解决的问题】的收益  >  【上面六条】的固定成本
而六条固定成本【不随数据量缩小】
→ 所以：数据量越小越不该引入；团队越小越不该引入
→ 也所以：能用现有引擎顶住的，先顶住，并明确写清"什么信号出现时才换"
```

【事实】**RuleArena 的选型卡正是这条规矩的正面样本**（`06` 第 8 节）：

```
正选：PostgreSQL 保存权威状态；Redis + ARQ 负责队列、限流和短期进度
理由：PostgreSQL 已承担领域数据和事务；Redis 简单满足 MVP 异步任务
被淘汰的反方案：【Redis 同时做权威状态】——"持久和事务不足"
风险与验证：Redis 丢任务、重复投递 → 用 PostgreSQL 的 expected status 做校验，
           并验证"任务重投 / Worker 重启 / 队列恢复"三条路径
升级条件：需要复杂路由、优先级、跨区域或高吞吐任务时评估 RabbitMQ/Kafka，
         但【仍不改变 PostgreSQL 的权威状态地位】
```

【推导】**这段结构值得学的是它的形状**：**每个引擎的角色被明确写成"负责什么、不负责什么"，并且写了升级条件。** 这比"我们用了 Redis"这样的描述有用得多——**它把"什么时候该换"变成了一个可观测的条件，而不是一个感觉。**

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "Redis 能做持久化（AOF / RDB），所以可以当数据库" | 【取舍】**持久化能力 ≠ 权威存储能力**。它缺的不只是"会不会丢"，还有：**事务强度、容量上界（内存）、查询能力、以及"内存满了要淘汰"这个机制本身**。**能重新算出来的放它，算不出来的不放它**（2.1）——RuleArena 把这一点直接写进了选型卡 |
| "全文检索用 `LIKE '%关键词%'` 就行" | 【推导】**两处不成立**：① **前置通配符用不上 B+ 树索引**，只能全表扫；② **它没有"相关性"概念**——检索要回答的是"哪几条最相关、按相关度排序"，这是检索问题不是过滤问题 |
| "有外键关联就应该上图数据库" | 【取舍】**两三层 JOIN 完全够用**（2.5）。**图数据库的优势只在"深度多跳 + 实时"时才明显**——**"数据有关系"是所有业务数据的共性，不构成选型依据** |
| "向量库是 RAG 标配，做 RAG 就得上 Milvus" | 【取舍】**数据量与能力要求决定**（2.4）：**小规模 + 已有 PostgreSQL → pgvector 更划算**（少一个引擎就是少六条成本）。**"标配"这个说法跳过了算账这一步** |
| "用 ES 当唯一数据源，就不用维护两份数据了" | 【事实】**ES 的写入是近实时的（默认有刷新周期），且通常没有跨文档 ACID 事务**——**它不是为权威存储设计的**。正确形态是"权威在关系库，ES 是检索副本"（2.3） |
| "多一个引擎就是多一份运维，忍忍就过去了" | 【取舍】**清单里最容易被忽略的是第 ②、⑤ 条**：**"谁是准的"这个问题会以"报表和明细对不上"的形式反复出现**，而**"每个改代码的人都要知道数据在哪"是长期的人力成本**——**这两条不会因为习惯了就消失** |
| "用 MongoDB 就不用改 schema 了，省事" | 【取舍】**schema 灵活不等于没有设计**：约束缺失意味着**错误数据能写进去、要靠应用层自己防**；而且**"灵活"的代价是"不能对灵活字段做高效查询"**（2.2）。**选它是对"整取整存 + 结构会变"的匹配，不是对"不想设计"的妥协** |
| "关系库什么都能做，就不该引入别的" | 【推导】**这句在方向上对，但过头了**。1.2 已说：**能不能做 ≠ 划不划得来**——**当查询形状与引擎的根本结构冲突时（全文检索、相似度、深度遍历），不引入的代价是"线上被拖垮"**，比引入的代价高。**判据仍是算账，不是守着一套栈** |

## 二、自测

**Q1（计算）**：某团队准备为"全文搜索"引入 Elasticsearch。已知：

- 需要检索的数据：**500 万条商品**，原始数据约 **5 GB**
- 这条链路要新增：**1 个同步组件**（CDC，需要有人维护与排障）+ **1 个 ES 集群**（要求至少 3 节点才能容忍故障）+ **1 套监控告警**
- 团队规模：**3 人**，其中**只有 1 人**有 ES 经验
- 当前痛点：MySQL 上的模糊查询平均 **2 秒**，每天约 **200 次**调用，**不在业务关键路径上**

问：① 引入的固定成本有几项？② 收益有多大？③ 该不该引入？④ 如果"必须 200 ms 内返回、且每天 200 万次"，结论会变吗？

**A1**：

```
① 固定成本（按第 4 节清单）：
   ① 同步链路（CDC 组件 + 维护）        —— 新增
   ② "谁是准的"问题（两份数据要对账）    —— 新增
   ③ 新增失败点（ES 挂了，降级路径要设计）—— 新增
   ④ 运维与监控（3 节点集群 + 告警）     —— 新增
   ⑤ 学习成本（3 人里只有 1 人会）       —— 新增，且【只有一个人会 = 单点】
   ⑥ 存储与资源（5 GB 数据的副本 + 3 节点最小规格）—— 新增
   → 【6 项全中】

② 收益：
   把 2 秒变成"假设 100 ms" → 每次省 1.9 秒
   每天 200 次 → 每天省 380 秒 ≈ 6.3 分钟
   而且它【不在关键路径上】（用户不会因此流失）

③ 【不该引入】。用第 4 节的判据：
   收益 = 每天 6 分钟的非关键路径耗时
   成本 = 6 项固定成本（其中"3 人团队里只有 1 人会"这一项会长期占用稀缺人力）
   → 收益 << 成本

   替代方案（按成本从低到高）：
   ① 加合适的索引 + 收紧查询（可能是写法问题，见 [[母题-M7-慢查询与SQL优化手段]]）
   ② 数据量不大（500 万条）→ 用数据库自带的全文能力
      （PostgreSQL 的全文检索 / MySQL 的全文索引）先顶住
   ③ 明确写下升级条件："当搜索进入关键路径，或数据量/调用量增长到 X 时再评估"

④ 【结论会变，而且是彻底反转】：
   变成关键路径（200 ms 是硬要求）→ 收益 = 保住核心体验，不再是"省 6 分钟"
   调用量涨到 200 万次/天 → 2 秒 × 200 万 = 每次请求都不可接受，
      而且这么大的量会把主库拖垮（[[母题-S2-单机不够了怎么扩]] 1.1）
   → 此时 6 项固定成本【相对于收益是可接受的】
   → 该引入，而且"只有 1 人会"这件事必须同步解决（培训或招人）

★ 关键：同一个技术需求，"该不该引入"的答案【随使用场景与规模完全反转】——
  这就是本卡要练的判断力。
```

【这一步在验证什么】验证第 4 节：**引入判据是"收益 > 六项固定成本"，而六项固定成本不随数据量缩小。**

**Q2（计算）**：某系统用 Redis 存了 **3 类数据**：

- **甲**：用户会话 token（1 小时过期，丢了要重新登录）
- **乙**：限流计数器（每分钟重置）
- **丙**：订单的支付状态（丢了要联系用户退款）

Redis 配置了 **256 MB** 上限，淘汰策略是 **`allkeys-lru`**（内存满时淘汰最久未用的 key）。

问：① 三类数据各自丢了会怎样？② `allkeys-lru` 会给哪一类带来风险？③ 该怎么改？

**A2**：

```
① 丢失后果：
   甲：用户要重新登录 → 【可接受】（能重新生成）
   乙：限流计数丢失 → 短暂放宽限流 → 【可接受】（能重新算）
   丙：支付状态丢失 → 【不可接受的灾难】
      （钱已经收了但系统不知道；且这不是"能重新算出来"的数据）

② `allkeys-lru` 的风险：
   【allkeys 意味着所有 key 都可能是淘汰候选】，包括"丙"
   → 当内存打满且丙这条 key 恰好最久没被访问（例如那笔订单支付后
     用户没再操作），它【会被直接删掉】
   → 更糟的是：这个删除【不会有任何报错】，业务只会看到"状态查不到"

③ 该怎么改（两层）：
   【第一层：把丙搬出 Redis】
     权威状态必须放到有事务与持久化保证的地方（PostgreSQL）
     → 这正是 RuleArena 的选型结论：PostgreSQL 存权威状态，
       Redis 只做队列/限流/短期进度
   【第二层：如果确实需要缓存丙】
     · 用 Redis 存【丙的缓存】而不是【丙本身】，主数据在 PG
     · 淘汰策略改 volatile-lru / volatile-ttl（只淘汰设了过期时间的 key），
       并给"甲、乙"显式设置 TTL、不给"丙的缓存"设 TTL
     · 缓存未命中时回源到 PG
   【另注】256 MB 这个上限本身就是 [[母题-X1-容器是什么]] 的 cgroup 场景——
     超了是 OOM 或大规模淘汰，与宿主机剩多少内存无关
```

【这一步在验证什么】验证 2.1："Redis 是加速层不是权威层"这条判断，**要用"这类数据丢了会怎样"来落地**——而不是用"它支不支持持久化"。

**Q3（判读）**：某团队的需求描述是：

> "我们的商品数据字段经常变，今天加三个属性、下周下掉两个。所以我们准备把商品主数据从 MySQL 迁到 MongoDB，MySQL 只保留订单。"

问：这个判断完整吗？该补问什么？

**A3**：

```
【判断不完整】。它只问了"结构变不变"，没问"这些灵活字段怎么被查询"。

必须补问三个问题：
① 【读写模式】：这些灵活字段是"整取整存"（读商品详情一次要全部）
   还是"要按它们过滤/聚合/排序"（例如"找出所有 color=red 且 size=XL 的商品"）？
   · 整取整存 → 文档库确实是甜点区（2.2）
   · 要频繁过滤聚合 → 文档库也会难受，而且失去约束与统计信息
     → 关系库的 JSONB 也可能够用（先看频率与数据量）

② 【范围】：有多少张表需要这样？
   1–2 张 → 用 JSONB 顶住，不必为此换掉主数据库
   到处都是 → 才构成"引入"的理由

③ 【代价】：迁到 MongoDB 之后
   · 商品与订单的关联查询怎么办？（跨引擎关联是最难的）
   · 两份数据谁是准的？（商品状态在订单流程里被引用时）
   · 现有多少代码要改？
   【特别是"MySQL 只保留订单"这一句】——
     它把一份业务数据切成了两个引擎，
     → 直接产生第 4 节清单里的第 ①②⑤ 三条成本

【另外要问的一个元问题】
"字段经常变"是【业务本来就不确定】，还是【当初没人设计】？
· 前者是真实需求（确实要灵活 schema）
· 后者是设计债（先把字段想清楚，比换数据库便宜得多）
```

**Q4（纠错）**：下面这段话哪里错了？

> "我们的 RAG 系统用 Elasticsearch 存知识库文档，同时用它的向量能力做语义检索，所以一套 ES 就够了，不用引入向量数据库。"

**A4**：**这句话有两处需要修正——第一处是事实，第二处是判断。**

1. **"用 ES 的向量能力"这件事本身是可以的**（ES 确实支持向量检索），**但要注意它的定位**：ES 的向量检索能力在"数据量、召回质量、专门的混合检索策略"上与专业向量库有差距，**而具体差距必须按自己的评测集实测**（**不许照搬厂商对比数字**）。**"能用"和"在这个规模上够用"是两件事。**

2. **真正的问题在"一套 ES 就够了"这个推理**——它**跳过了一个更重要的问题：权威数据在哪。**

```
如果 ES 是这个知识库的【唯一存储】：
   → 它承担了"权威存储"的角色
   → 而它不是为了这个角色设计的（2.3）：
     · 写入近实时（不保证写完立刻可搜）
     · 通常没有跨文档 ACID 事务
     · 更新语义是重写文档
   → 一旦索引损坏或需要重建，【源数据在哪】？
```

**准确说法**：*用 ES 同时做全文与向量检索，在数据量不大时是"少引入一个引擎"的合理取舍（第 4 节的账）；但必须明确"权威原文存在哪里"——通常是对象存储或关系库存原始文档，ES 只是检索副本。判断顺序应该是：① 权威数据在哪 ② 检索用一套还是两套 ③ 如果用一套，它的向量能力在我们这个规模上够不够（实测）。*

**Q5（纠错）**：下面这段话哪里错了？

> "我们的架构很先进：MySQL 存订单、MongoDB 存商品、Redis 存会话、ES 做搜索、ClickHouse 做报表、还接了向量库做推荐。每种数据都用了最合适的存储。"

**A5**：**"每种数据都用了最合适的存储"这个说法，把"单点最优"当成了"全局最优"。**

**问题一：它只算了"每个引擎各自的收益"，没算"引擎之间的成本"**（第 4 节的六条）：

```
① 六条同步链路（每个引擎都要有数据进去的路径）
② 五个"谁是准的"问题
③ 六个失败点（任一个挂了都要有降级路径）
④ 六套运维与监控
⑤ 每个改代码的人都要知道"这份数据在哪个引擎"
⑥ 六份存储与最小实例规格
→ 这正是 summaries/oceanBase.md 里得物【改造前】的状态，以及它列出的那些问题
```

**问题二：它没有回答"这些数据之间要不要关联"**：

```
订单要引用商品（MySQL ↔ MongoDB）
报表要关联订单与商品（ClickHouse ↔ 两个库）
推荐要用订单行为（向量库 ↔ MySQL）
→ 每一条跨引擎关联，都要变成"应用层拼装"或"宽表冗余"
→ 而只要有冗余，就有"哪份是准的"的问题
```

**问题三：它把"用了某种存储"当成了架构水平的证明**：

```
【真正的成熟标志是相反的】：能说清"我们【主动删掉】了什么，为什么"
← RuleArena 的"秒级删除清单"（K8s / RabbitMQ / 通用 DAG）就是这个形状
← 得物的案例也是从"多库并存"走向"收敛"
```

**准确说法**：*选型的正确姿势不是"每种数据配一个最合适的引擎"，而是"在满足负载要求的前提下，用尽可能少的引擎，并且每个引擎的角色边界与升级条件都写明"。引擎数量本身是一个成本项，不是能力项。*

## 三、面试输出（学完再看）

**一句话结论**：**判断该不该用关系库，只看一件事——这次查询的"入口"是什么。** 入口是**主键/范围** → 关系库（B+ 树就是为等值、范围、前缀、排序设计的）；入口是**关键词** → 检索库（**倒排索引**，`LIKE '%x%'` 用不上 B+ 树而且没有"相关性"这个概念）；入口是**向量距离** → 向量索引（**相似度不是可排序的一维标量**）；入口是**关系路径** → 图（**多跳时 JOIN 会组合爆炸**）；入口是**纯 key** → 键值库。**但"能做 ≠ 划得来"**：关系库靠 JSONB、递归 CTE、`pg_trgm` 这些也能做，**所以真正的判断是算账**——引入任何新引擎都要付**六项固定成本**（同步链路、谁是准的、失败点、运维监控、学习协作、存储资源），**而这六项不随数据量缩小**，**所以数据量越小、团队越小，越不该引入**。落到项目上：**RuleArena 的选型卡就是正面样本——PostgreSQL 存权威状态，Redis 只做队列与限流，并明确写下"Redis 不能做权威状态"和升级条件。**

**恢复关键词**：**入口决定结构**（主键 / 关键词 / 向量 / 关系路径 / key）/ 倒排索引 vs B+ 树是相反的组织方式 / `LIKE '%x%'` 用不上索引且无相关性 / 相似度不是可排序标量 / 图只在**深度多跳**时有优势 / **能做 ≠ 划得来** / Redis 与 ES 都**不是权威存储**（一个易失、一个近实时无事务）/ pgvector = 少一个引擎 / **引入六项固定成本，不随数据量缩小** / RuleArena：PG 权威 + Redis 队列 + **写清升级条件** / **引擎数量是成本项，不是能力项**

**核心不变量 / 主线**：
**存储选型的顺序是：先问"查询的入口"，再问"能不能用现有的顶住"，最后才问"引入哪个"。** 大多数选型失误不是因为选错了引擎，而是因为**跳过了第二步**——**没有回答"用现有引擎顶住会付出什么代价"，就直接跳到了"引入新的"**。所以每条引入决策都应该配一句**升级条件**（什么信号出现时才换），**这一句是把"感觉"变成"判据"的关键。**

**完整回答骨架**：先给唯一判据（查询的入口）→ 关系库的强项与它的反面（五类做不好的查询形状）→ 澄清"能做 ≠ 划得来" → 五类专有存储各一段（擅长 / 结构来源 / 牺牲了什么）→ 用四个需求演练一遍 → **引入六项固定成本**（本卡落点）→ RuleArena 的正面样本 → 边界（Redis 不能当数据库、ES 不能当唯一数据源、图被高估、向量库不是必需品）

**完整回答（口述稿）**：
**判断该不该用关系库，只看一件事——这次查询的"入口"是什么。**

入口是**主键 / 范围** → 关系库（B+ 树就是为等值、范围、前缀、排序设计的）；入口是**关键词** → 检索库（**倒排索引**；`LIKE '%x%'` 用不上 B+ 树，而且没有"相关性"这个概念）；入口是**向量距离** → 向量索引（**相似度不是可排序的一维标量**）；入口是**关系路径** → 图（**多跳时 JOIN 会组合爆炸**）；入口是**纯 key** → 键值库。

**但"能做 ≠ 划得来"**：关系库靠 JSONB、递归 CTE、`pg_trgm` 也能做这些事，**所以真正的判断是算账**——引入一个新组件，要付同步链路、运维、一致性、排障四笔成本；只有算下来更便宜才换。

和 RAG 侧呼应：关键词检索（BM25）与向量检索的盲区不重叠，正是"入口不同"这条判据在检索层的体现。

**分层要点**：
- **结论**：按查询入口选型；能做不等于划得来，要算引入新组件的四笔成本。
- **推导链**：入口类型 → 各自适配的存储（B+ 树/倒排/向量/图/KV）→ 关系库能勉强替代 → 判据变成算账。
- **量化**：无（判据为主）。
- **边界与常见误解**：`LIKE '%x%'` 用不上 B+ 树；多跳关系用 JOIN 会组合爆炸。

**追问**（先说后看）

1. **Redis 能做持久化，为什么不能当数据库？** —— **它缺的不只是持久化**：还有事务强度、容量上界（内存 + 淘汰机制）、查询能力。**判断依据是"这类数据丢了会怎样"**——能重新算出来的（会话、计数、队列进度）可以放；算不出来的（订单、账）不行。**RuleArena 把这条直接写进了选型卡：Redis 同时做权威状态 → "持久和事务不足"，淘汰。**
2. **为什么 `LIKE '%关键词%'` 加索引也没用？** —— **前置通配符让 B+ 树无法做任何裁剪**（B+ 树是按值得顺序排的，从中间开始匹配就跳不过任何数据）。**而且检索要的是"相关性排序"，关系库没有这个概念。**
3. **做 RAG 一定要上独立向量库吗？** —— **不一定**。判据是规模与能力要求：**小规模 + 已有 PostgreSQL → pgvector 更划算**（少一个引擎就是少六项成本）；**数据量大或需要专门的混合检索、多路召回能力 → 独立向量库**。**"标配"这个说法跳过了算账。**
4. **ES 能当主库用吗？** —— **不建议**。它的写入是**近实时的**（有刷新周期），而且**通常不提供跨文档 ACID 事务**——**它不是为权威存储设计的**。正确形态是：权威数据在关系库/对象存储，**ES 是为检索优化的一份副本**。
5. **怎么判断"该不该引入一个新引擎"？** —— 三步：**① 这个负载的查询入口是什么（现有引擎真的做不好吗）② 用现有引擎顶住会付出什么代价（能不能接受）③ 引入要付六项固定成本，收益是否大于它**。**并且无论结论如何，都写下升级条件。**
6. **多引擎架构最大的隐性成本是什么？** —— **不是钱，是"谁是准的"**。两份数据必然出现对不上的时候（`summaries/oceanBase.md` 把这条列为"数据一致性风险"），**而这个问题会以"报表和明细对不上"的形式反复出现**，且**对账机制必须提前设计，不能事后补**。

**同类变体**

- 「什么时候用 MongoDB？」——**"以对象为单位读写 + 结构会变 + 不需要跨对象事务"**（2.2）。**它的雷区是账务类数据**（需要跨对象强一致）
- 「图数据库适合什么？」——**深度多跳 + 实时**（2.5）。**"有外键"不是理由。**
- 「缓存和数据库怎么保证一致？」——见 [[母题-R3-缓存一致性与三类事故]]：**没有完美的强一致方案，只有"延迟可接受 + 能对账"**——**这与本卡第 4 节的第 ② 条是同一个问题**
- 「消息队列算存储吗，怎么选型？」——**算，而且是"有状态的"**——它的选型（Kafka / RocketMQ / RabbitMQ）同样按"队列形态与投递语义"的入口来判断，正本在 [[消息队列模块卡]]

**方言差异**：

| 同一件事 | 关系库（MySQL / PG） | 专有存储 |
|---|---|---|
| "查一个东西" | `WHERE` + 索引，入口是**值** | 入口是**key**（Redis）/ **词**（ES）/ **向量**（向量库）/ **节点**（图） |
| "更新" | 原地更新 + 事务 | Redis 覆盖 key · ES **重写文档** · 向量库**重算并重建索引** |
| "一致性" | 强 ACID | 各自不同（**多数弱于关系库，这是设计取舍不是缺陷**） |
| "数据会不会丢" | 不会（WAL + 事务） | **默认会**（淘汰 / 近实时 / 索引重建）→ **所以不能当权威层** |
| 该放什么 | **不可重新计算的东西** | **可重新计算的东西**（缓存、索引、队列进度） |
