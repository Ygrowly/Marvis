# 数据存储选型模块深挖卡

> 本卡是 [[模块深挖卡模板]] 的实战卡。**主线优先**：先看四条线，再落母题，题单只用来查漏。
>
> **定位**：这是后端基本盘里**唯一一层"选型"视角**——它不解释某个库的内部机制（那是 [[MySQL模块深挖卡|MySQL]] / [[PostgreSQL模块深挖卡|PostgreSQL]] / [[Redis模块深挖卡|Redis]] 的活），它回答**"这段负载该交给哪一类存储，以及为什么不交给另一类"**。
>
> **与相邻模块的分工（三处，别串台）**：
> - [[MySQL模块深挖卡|MySQL]] / [[PostgreSQL模块深挖卡|PostgreSQL]] 讲**机制**：索引为什么是 B+ 树、MVCC 怎么实现、WAL 怎么写
> - [[Redis模块深挖卡|Redis]] 讲**缓存语义**：数据结构、持久化、一致性事故
> - [[母题-M15-数据增长治理]] 讲**单个库内部**怎么应对增长（归档 / 分区 / 加索引）
> - **本卡讲"跨引擎"的那一层**：什么负载配什么引擎、多个引擎并存要付什么代价
>
> **本轮落 4 张母题**（分野 / 扩展 / 边界 / 语义），题单里其余排期。

## 0. 模块边界（先写这个，防无限扩张）

**包含**：**分野**（OLTP 与 OLAP 为什么是两类东西，行存与列存的分水岭）、**扩展**（单机扛不住之后的三条路：读写分离 / 分片 / 换分布式数据库，各自买到什么、付出什么）、**边界**（什么需求不该用关系库解决：缓存、文档、搜索、向量、图，以及多引擎并存的隐性成本）、**语义**（数据仓库存事实，语义层/Ontology 存"含义与动作"——NL2SQL 与 Agent 真正依赖的是什么）。

**明确不包含**：

- **任何单一引擎的内部机制**（B+ 树、MVCC、WAL、LSM、跳表…）——各有正本，本卡只引用不复制
- **部署、参数调优、集群运维命令**——归 [[Linux与部署模块卡|Linux 与部署]]；本卡只到"这个引擎的架构决定了它的取舍"
- **厂商产品横评与价格对比**（各家云数据库的规格与计费）——属于现场决策，且**厂商自述的性能数字一律不采信**
- **分库分表的实施细节**（路由算法、扩容迁移、分布式 ID 的具体方案）——只到"什么时候该拆、拆的代价是什么"
- **数据仓库建模方法论**（维度建模、拉链表、数仓分层）——本卡只到"为什么 OLAP 要反规范化"，不教建模

**边界判据**：**凡是"这个引擎内部怎么做到"的，归它自己的模块卡；凡是"该用哪一个、为什么不换一个"的，进本卡。**

**一条必须先立的认知**：**选型的起点不是"哪个引擎先进"，而是"这段负载长什么样"。**

```
❌ 先看技术榜单，再找机会用它
✅ 先问负载三件事：一次查多少行、写得多频、要多久看到结果
   —— 三个答案出来，引擎族基本就定了，剩下的才是细节
```

**"为什么选 X 不选 Y" 的标准答法，是一个可算的判据，不是一句偏好。** 这是本模块最核心的立场。

## 2. 主线拆解（骨架：这个域在回答哪几个问题）

> 主线从**问题**出发，不从**名词**出发。

| # | 主线（它在回答什么问题） | 这条线的关键取舍 | 落几个母题 |
|---|---|---|---|
| 一 | **分野**：OLTP 与 OLAP 为什么是两类东西，凭什么它们不能合成一个 | 行存（点查与写入快）vs 列存（扫描与聚合快）；规范化（更新不异常）vs 反规范化（少 join 少扫描） | 1 |
| 二 | **扩展**：单机扛不住以后，加机器为什么不是免费的，三条路各买到什么 | 强一致（不敢出错）vs 可用性与延迟（不能停）；共享存储（省事）vs 分片（可控）；换数据库 vs 改应用 | 1 |
| 三 | **边界**：什么需求不该用关系库解决，多引入一个引擎要付什么账 | 通用（灵活但慢）vs 专用（快但能力窄）；省下的查询时间 vs 新增的同步链路与运维面 | 1 |
| 四 | **语义**：数据仓库存的是事实，那"事实的含义"存在哪——NL2SQL 与 Agent 依赖的是什么 | 把语义放进模型提示（接入快、易漂移）vs 放进系统（成本高、可版本化）；仓（存数）vs 语义层/本体（存含义与动作） | 1 |

**四条线的关系**：一是"**两种负载天生不同**"，二是"**一种负载自己扛不住时怎么办**"，三是"**不用关系库的那些负载去哪**"，四是"**数据之上那层含义放在哪**"。**前三条是选型，第四条是选型在 AI 时代的延伸——也正是主人两个项目的核心议题。**

**这四条线共享同一个前提**：**存储的能力边界是由它的物理布局与一致性模型决定的，不是由它的功能列表决定的。** 功能列表谁都能加（Doris 也能做点更新、MongoDB 也能做事务），**但物理布局决定的"擅长什么"改不了**——它能做，不等于它划得来。**判断一个引擎适不适合，永远看它的物理布局，不看它的功能页。**

## 5. 项目映射（三个项目逐个过）

> 素材来源：`projects/` 下的项目说明与编号手册。**这里每一句都要能指回原文**，不许编。

### 5.1 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/03-query-and-performance.md`、`02-aggregation-and-recovery.md`
- 用在哪：**"受控并发 + 低优先级回补"是本模块在应用层的一次选型**——不引入 MQ、不引入分析引擎，用**调度 + 批量 + 幂等**把负载压在单库能承受的范围里。
- 解决什么问题：**能耗数据是"写多、按时间窗聚合读"的形态**——这本来偏向时序/分析类存储，但**当前规模下"加一套引擎"的代价大于收益**，所以选择"用现有库 + 受控并发"顶住。
- 踩过的坑：**Checkpoint 被当成"业务完成证明"**——恢复线索不等于完成证明（对应 S1 的"数据同步有窗口"同一类问题：**两边不一致时，以哪边为准**）。
- 决策与取舍：**"达到升级条件才引入"**——这是本模块第 0 节那条判据（先算账，再换引擎）的现场版。
- 对应母题：【S1、S3】

### 5.2 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/02-数据接入与轻量湖仓.md`、`03-数据目录与语义资产.md`、`14-系统架构部署与故障处理.md`
- 用在哪：**这是本模块最完整的实例，三条线都命中**：
  - **S1 分野**：**PostgreSQL 管控制面（租户、权限、目录、任务——典型 OLTP），Parquet + 对象存储存分析数据，DuckDB Worker 做隔离分析（列存 + 进程内）**。`02` 写得很直白：*"PostgreSQL 只保存目录、Schema、同步状态和版本，DuckDB 负责分析执行"*。**这就是"两种负载交给两种引擎"的标准做法。**
  - **S2 扩展**：**快照（`SNAPSHOT`）与实时（`LIVE_READ`）双模式**——实时模式**优先只读副本或分析库**，且*"若客户只有生产主库，默认不开放复杂即席查询"*。**这就是"不许分析负载打到生产主库"这条硬规矩。**
  - **S4 语义**：`03` 的三层知识（技术元数据 / 业务语义 / 公共规则）与"**模型只能映射和使用，不能自行创造**"——**这是 S4 的项目正本**。
- 解决什么问题：**同一份数据，控制面要强一致（权限不能错），数据面要扫描快（分析不能慢）**——一个引擎同时满足两者的代价，比分成两层更高。
- 踩过的坑：**扫描量、超时、行数、并发都必须有上界**（`07`、`08`）——**"单个请求没有上界"是这类事故的共同根因**（同 [[母题-X1-容器是什么]] 的结论）。
- 决策与取舍：**不做全量复制**（成本与合规），**只同步"选定数据集"**；`02` 的钢人比较写明：*"完全直连无需同步、数据最新，适合已经有成熟分析库的企业；全量复制查询自由，但成本和合规压力大。"*
- 对应母题：【S1、S2、S4】

### 5.3 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/06-architecture-and-scenarios.md`、`08-capacity-cost-and-facts.md`、`04-idempotency-and-recovery.md`
- 用在哪：**"权威状态放关系库，易失状态与队列放 Redis"的经典二分**——PostgreSQL 存 `AttackRun` 与 `Receipt`，Redis/ARQ 负责队列、限流与短期进度。
- 解决什么问题：**崩溃后能重建**——*"起来先读 AttackRun 和最后一个 Receipt，再校准 Checkpoint"*。**这直接回答 S3 的第一问：Redis 能替代数据库吗？不能，因为它的权威性不在这里。**
- 踩过的坑：**Redis 只配 256~512MB**（`08`）——一个"进程随时可能被拿走"的存储，**不能承载不可再生的状态**（同 [[母题-X1-容器是什么]] 2.2）。
- 决策与取舍：**K8s、RabbitMQ、通用 DAG 都进了"主动删除"清单**（`06` §秒级删除清单）——**明确不做的比做的更能说明取舍**；这正是 S3 要练的"多引入一个引擎要付什么账"。
- 对应母题：【S3】
