**题目**：面试官问——"Agent 跑久了上下文满了怎么办？记忆该存什么？"

**母题**：**Agent 的上下文满了要压缩、跨会话要记东西——但"压缩什么、记什么"的判据是什么？为什么记忆不是越多越好？**

**为什么重要**：这道题**看起来是"内存管理"，实际是"权威性管理"**。答"我们做了摘要压缩"是及格线；**能说清"摘要里必须留哪些指针、长期记忆的写入门槛是什么"才算过关**——因为**这两件事做错，前者会导致重复执行副作用，后者会让检索被噪声淹没**。

## 一、教材

### 1. 前提：记忆分三层，权威性完全不同

::figure memory-layers.svg | 记忆分三层：每层的作用域、寿命和写入门槛都不同 | 运行状态（Checkpointer）→ 长期记忆（Store）→ 业务权威状态；混在一起的后果是拿模型自己的摘要当事实

| 层 | 作用域 | 寿命 | 写入方式 | 权威性 |
|---|---|---|---|---|
| **① 运行状态** | **单个 thread** | 一次 run | **自动**（每一步） | 运行权威 |
| **② 长期记忆** | **跨 thread** | 用户 / 组织级 | **有门槛** | **派生**（需治理） |
| **③ 业务权威状态** | 业务系统 | 长期 | 业务系统自己 | **最高** |

【推导】**这个分层的判据是"权威性"，不是"存哪"**：

```text
① 运行状态：是"我做到哪了" —— 权威，但只对本次 run 有效
② 长期记忆：是"我记住了什么" —— 【派生】，可能过期、可能被推断污染
③ 业务状态：是"事情到底是什么样" —— 【唯一权威】
```

【推论】**混在一起的后果很具体**：**拿模型自己总结的"已执行"当成工具真的执行成功了**。**这正是 [[母题-C1-上下文组装与窗口预算]] 里那句"不把模型自己总结的已执行当作工具执行成功"的机制版本。**

【事实】**LangGraph 的划分和这个同构**（[[母题-A4-长任务状态与Checkpoint]] 引过）：

```text
Checkpointer = 单 thread、短期、thread 级  → 对应 ①
Store        = 跨 thread、长期、需治理    → 对应 ②
```

【事实】**OpenAI 那篇 Harness 工程给了一个更狠的说法**：

> **"From the agent's point of view, anything it can't access in-context while running effectively doesn't exist."**

【推论】**这句话反过来推出一件重要的事**：**"我告诉过模型"不等于"模型知道"**——**知识必须落在 agent 能访问的地方（仓库里、可检索的存储里），而不是留在人的脑子里或聊天记录里。**

**到这里你应该能回答**：为什么"用户上周说过他偏好 A 方案"这句话，如果只留在聊天记录里，第二周就不算数了？

### 2. 压缩：Agent 里和纯对话里的区别【推导】

【事实】**共同的原理**（[[母题-C1-上下文组装与窗口预算]]）：

```text
压缩 = 把历史摘要掉，用摘要 + 最近若干条重新开始
调法 = 先保 recall（不漏），再提 precision（删冗余）
摘要必须有可回溯的指针，原始内容外部持久化
触发阈值：Claude 平台默认 150,000 输入 token
```

【推导】**Agent 里多出来的是"压缩时机的判据"**：

```text
纯对话：什么时候压，主要看【窗口快满了】
Agent ：什么时候压，还要看【当前处在哪个业务节点】

因为压缩在 Agent 里是【有状态语义的】：
  在一个工具调用序列中间压缩 → 可能丢掉"这一步还没做完"的标记
  在副作用之后压缩           → 正好，因为结果已经落盘了（[[母题-A4-长任务状态与Checkpoint]]）
```

【推论】**所以 Agent 的压缩点应该和 checkpoint 点对齐**——**archive/study-courses/04 把"Context 压缩或分支合并后"列为 checkpoint 时机之一**，正是这个道理：**压缩和 checkpoint 是同一个动作的两面，一个改上下文，一个存状态。**

#### 2.1 压缩能省多少【推导】

```text
50 步任务，每步新增 2.5K token，每 20 步压缩一次（压到 10K）

不压缩：
  累计输入 = 2.5K × (1 + … + 50) = 2.5K × 1,275 = 3.19M

压缩（分三段）：
  段 1（1–20）：prompt 从 2.5K 涨到 50K
               累计 = 2.5K × 210 = 525K
               段末压到 10K
  段 2（21–40）：prompt 从 10K 涨到 60K
               累计 = 20 × 10K + 2.5K × 210 = 200K + 525K = 725K
               段末压到 10K
  段 3（41–50）：prompt 从 10K 涨到 35K
               累计 = 10 × 10K + 2.5K × 55 = 100K + 137.5K = 237.5K

  合计 ≈ 1,487.5K ≈ 1.49M
```

【结论】**压缩把累计输入从 3.19M 降到 1.49M，约一半（47%）。**

【推论】**而且压缩的收益随任务变长而变大**：**不压缩是"整段平方"，压缩是"分段平方"**——**段数越多，省得越多**。（[[母题-C6-成本与长上下文截断]] 里那句"缓存改价格、压缩改占用"在这里同样成立，但 Agent 场景下压缩的触发点还要和状态对齐。）

**到这里你应该能回答**：为什么 Agent 的压缩不能只看"窗口还剩多少"？

### 3. 摘要里必须留下什么【推导】

【推导】**压缩是有损的，所以"留什么"是设计出来的，不是概括出来的**。三类必须留：

```text
① 与副作用相关的：已完成的操作 + 幂等键
   → 丢了会导致恢复时【重复执行】（[[母题-A3-失败恢复与幂等]]）

② 与证据相关的：来源 ID / Artifact 引用
   → 丢了会导致结论无法追溯（[[母题-G4-引用绑定与证据可追溯]]）

③ 与进度相关的：未决问题、剩余预算、当前节点
   → 丢了会导致恢复时不知道该从哪继续（[[母题-A4-长任务状态与Checkpoint]]）
```

【推导】**算一下"多留这几个字段"的成本**：

```text
在摘要里多保留约 200 token 的指针信息
成本 = 200 × $5 / 1M = $0.001           （Opus 5 输入价）

而丢掉"已完成副作用记录"的代价：
  一次重复扣款 / 重复建单 → 对账、退款、客诉 → 【远大于 $0.001】
```

【结论】**在摘要里保留指针的成本可以忽略，而丢掉的代价是事故。**

【推论】**这就是"摘要不是审计记录"这句话的正确理解**：**它不是"摘要可以随便写"，而是"摘要不该承担记录真相的责任"**——**真相要外部持久化，摘要只留指针。**

**到这里你应该能回答**：为什么"摘要写得好不好"这件事，不能用"读起来通不通顺"来判断？

### 4. 长期记忆的写入门槛【推导】

【事实】**门槛是三条同时成立**（[[母题-C1-上下文组装与窗口预算]] 给过）：

```text
跨任务稳定 + 对未来有用 + 经过授权（能治理）
```

【事实】**不该自动写入的**：**临时推理、模型猜测、敏感数据**。

【推导】**算一下"不设门槛"的代价**：

```text
什么都写（每次 run 写 10 条）：
  每天 10,000 run → 100,000 条/天
  一年 ≈ 3,650 万条

只写"跨任务稳定 + 已验证"的（每天约 50 条）：
  一年 ≈ 18,250 条

差约 2,000 倍
```

【结论】**写入门槛决定长期记忆是"资产"还是"噪声"。**

【推论】**这个差别不是存储成本的问题，是检索质量的问题**——**当记忆里有 3,650 万条时，"回忆相关偏好"这件事本身就变成了一次低质量检索**：**大部分条目是噪声，真正有用的被淹没**（和 [[母题-G1-切分策略与索引粒度]] 里"块太大导致信号被稀释"是同一个机制）。

【事实】**每条记忆应有的元数据**：**来源、主体、作用域、置信度、更新时间、TTL、删除机制**。

【推论】**"删除机制"这一条是硬要求，不是可选项**——**因为记忆里可能有敏感信息，也可能有已经被推翻的结论**（[[母题-G6-知识更新与增量索引]] 的删除传播在记忆上的版本）。

**到这里你应该能回答**：为什么"模型觉得重要就自动记下来"这个设计是危险的？

### 5. 记忆的三种失效【事实】

【推导】**长期记忆会以三种方式变坏，各要一种对策**：

| 失效方式 | 表现 | 对策 |
|---|---|---|
| **过期** | 用户偏好变了，记忆还是旧的 | **TTL + 更新时间**；关键事实回权威源重查 |
| **污染** | 模型推断被当成事实写进去 | **写入门槛**（只写验证过的）+ **标注置信度与来源** |
| **过载** | 条目太多，检索不出有用的 | **写入门槛**（Q2）+ 定期清理 |

【推论】**第二类最隐蔽**：**模型推断被写进记忆后，下一轮它就不再有"这是推断"的标记了**——**它变成了一条"事实"**。**所以记忆条目必须自带来源与置信度**，否则**系统会逐渐把"自己猜的"当成"知道的"**。

【推论】**这和 [[母题-C4-幻觉的成因与可控性]] 的"多轮对话里幻觉会累积"是同一个机制**：**上一轮的错误结论进了下一轮上下文，就变成了"已确认事实"。**

**到这里你应该能回答**：为什么记忆条目必须自带来源和置信度？

### 5.5 记忆三段：写入 / 读取 / 遗忘（面试要能一把说出）【推导】

【事实】第 4 节讲了**写入门槛**，第 5 节讲了**三种失效**，内容都在，但**散着**。面试官问"Memory 怎么设计"要的是一把说出的三段：

```text
写入：什么能写（门槛三条）+ 写成什么（元数据七项，含 TTL 与删除机制）
读取：什么时候读、读多少、按什么排序
遗忘：什么时候删（TTL / 被推翻 / 过载清理）+ 删掉的影响怎么传播
```

【推导】**三段的控制手段完全不同，别混成一个答案**：

| 段 | 主要风险 | 控制手段 | 出处 |
|---|---|---|---|
| **写入** | 噪声淹没信号（第 4 节的 2000 倍） | 门槛三条 + 置信度与来源标注 | 本卡 §4 |
| **读取** | 读多打穿 prefix cache，读少丢证据 | 召回后重排 + 数量上限 + 位置固定 | 本卡 §5.5 ↓ |
| **遗忘** | 过期记忆被当成事实复用 | TTL + 更新时间 + 回权威源重查 | 本卡 §5「过期」那一行 |

【事实】**读取段排序的三个因子，直接来自第 4 节的元数据**：**相关度（召回给的）× 新鲜度（更新时间 / TTL 给的）× 置信度（来源给的）**。**没有元数据就没法排序**——这就是为什么"元数据七项"不是形式主义。

【推导】**读取位置和遗忘频率是一对矛盾（被追问最多的地方）**：

```text
记忆更新越频繁 → 若放在 prompt 最前面，每次更新都打穿整段 prefix cache → 成本飙升
想命中 prefix cache → 必须把记忆放在最前面、且尽量不变
```

【结论】**顺序原则：变化最少的内容放最前**：

```text
system prompt → 长期记忆 → 工具描述 → 历史会话 → 当前 query
```

（完整推导与成本账在 [[母题-C6-成本与长上下文截断]]，本卡不重复）

【推论】**所以"记忆多久更新一次"不是产品问题，是成本问题**：高频变动的记忆要么**单独放尾部**（放弃这段 cache），要么做成**版本号 + 只追加不改**——**追加写在尾部，不影响头部前缀**。

**到这里你应该能回答**：长期记忆为什么要放最前面？它和"记忆多久更新一次"有什么关系？

### 6. 项目落点：数驭穹图把「分三层」做成了五层状态【事实】

【事实】`projects/数驭穹图/12-多轮上下文与任务恢复.md` 的原话（**这句可以直接背**）：

> **"历史上下文负责记住'刚才在讨论什么'，当前事实必须重新查询；会话、执行轨迹、大结果和证据分别管理，不能混成一个无限增长的 messages 数组。"**

【事实】它把状态拆成五层——**比本卡的三层更细，而且落到了工程实体上**：

| 层 | 作用 | 对应本卡 |
|---|---|---|
| **Visible Memory** | 用户看到的问题和最终结果 | —（展示层） |
| **Trajectory** | 模型、Tool、重试、错误和事件 | ① 运行状态 |
| **Working Context** | 本轮真正提供给模型的高信号内容 | Context（投影） |
| **Evidence Memory** | 历史结论对应的查询和版本引用 | ② 长期记忆（带来源与版本） |
| **Current Business Truth** | 本轮重新查询获得的事实 | ③ 业务权威状态 |

【推论】**"当前事实必须重新查询"就是本卡那条"权威性分三层"在产品上的判据**：上一轮查出的销售额可能已经更新，**语义可以继承（指标、时间、分析方式），带「当前」含义的业务事实不能无条件复用。** 用户说"那华南呢"，继承的是指标和时间，替换的是区域过滤，**销售额必须重查**。

【事实】三个可以直接讲的工程动作：

```text
① Session Ledger：每回合原子记账
   User → Intent → Tool Call → Tool Result → Evidence → Final → Turn Committed
   （Tool Call 没有 Tool Result 时，不能作为完整历史重放）

② Artifact：大结果外置
   上下文只留：参数、口径、聚合事实、完整性、少量样例、artifact_id、Hash
   要再分析时通过受控工具按权限读回

③ 结构化 Checkpoint（不是聊天摘要）
   =「较早状态快照 + 最近增量」
   压缩优先保证【关键约束和证据召回】，再删旧 Tool Result
```

【推论】第 ③ 条正好印证本卡 §3 的"摘要必须留三类指针"——**项目里的说法是「约束、未决项、证据引用、版本」，是同一件事的两套叫法。** 面试里把两边对上，说明你不是背的。

【事实】**逆向检查**（这条是加分点，也是"压缩不能只看摘要流不流畅"的项目版）：

```text
即使 Checkpoint 保存成功，也可能
  ① 压掉未决问题
  ② 使用旧 Schema 版本
  ③ 留下孤立 Tool Call
→ 所以压缩必须通过【恢复测试 + 长对话 Eval】验证，而不是只看摘要是否流畅
```

【取舍】**边际决策**（别过度设计，这句能挡掉"你们压缩做得好复杂"的质疑）：

```text
第一版只做：原子回合 + 近期窗口 + 大结果外置
只有真实长对话达到预算时，才引入 Token-aware 召回和自动 Compaction
```

【事实】同源的第二处证据：`05-领域路由与Schema-Linking.md`——**不把全库 DDL 塞进上下文，只给模型当前任务所需的最小语义包**（先路由，再按需加载少量高信号 Schema）。**这是"减少新增"而不是"压缩历史"**，与 EnergyOps 那条"日志和大表先检索聚合再进上下文"是同一类动作——**两类动作要配合用，只做一边都会漏。**

**到这里你应该能回答**：为什么"我们做了上下文压缩"还不够，还必须要有 Artifact 和结构化 Checkpoint？

### 7. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "记忆越多越聪明，都存下来" | **写入门槛决定它是资产还是噪声**：什么都写是每年 3,650 万条，只写稳定已验证的约 1.8 万条——**差 2,000 倍**。**条目多了之后，"回忆相关偏好"本身就退化成一次低质量检索** |
| "模型自己总结的'已执行'可以当状态用" | **这是最危险的混淆**。**运行状态（①）是权威的，长期记忆（②）是派生的**——**拿模型自己的摘要当业务事实，就是 [[母题-C1-上下文组装与窗口预算]] 里点名的反例** |

| "压缩什么时候做，看窗口快满了就行" | **Agent 里还要看当前处在哪个业务节点**。**在工具调用序列中间压缩可能丢掉"这一步还没做完"的标记**；**在副作用之后压缩才是安全的**。所以压缩点应该和 checkpoint 点对齐 |
| "长期记忆写进去就不用管了" | **记忆会以三种方式变坏**：过期、污染、过载。所以要 **TTL + 更新时间 + 来源 + 置信度 + 删除机制**——**"删除机制"是硬要求**（可能有敏感信息，也可能有被推翻的结论） |
| "提示里告诉过模型就行" | **OpenAI 的原话是"agent 访问不到的东西，等于不存在"**。知识必须落在**可访问、版本化、可检索**的地方——留在聊天记录和人的脑子里都不算 |
| "压缩和 checkpoint 是两件事" | **它们是同一个动作的两面**：**一个改上下文、一个存状态**，而且**压缩后必须 checkpoint**——**否则压缩后崩溃又回到压缩前，等于白压一次** |

【取舍】读成一句话：**记忆的核心问题是"权威性"，不是"容量"——分不清"我记住的"和"事情本来的样子"，压缩和记忆都会变成事故来源。**

## 二、自测

**Q1（计算）**：一个 **50 步**的 Agent 任务，每步新增 **2.5K token**，每 **20 步**压缩一次（压到 **10K**）。模型 Opus 5（输入 $5/MTok）。

问：**不压缩和压缩的累计输入各是多少？**压缩省了多少？

**A1**：

```text
不压缩：
  累计 = 2.5K × (1 + … + 50) = 2.5K × 1,275 = 3,190K = 3.19M

压缩（分三段）：
  段 1（1–20）：2.5K × 210 = 525K，段末压到 10K
  段 2（21–40）：20 × 10K + 2.5K × 210 = 200K + 525K = 725K，段末压到 10K
  段 3（41–50）：10 × 10K + 2.5K × 55 = 100K + 137.5K = 237.5K
  合计 ≈ 1,487.5K ≈ 1.49M
```

【结论】**降到约 47%**（3.19M → 1.49M）。

【推论】**压缩的收益随任务变长而变大**：**不压缩是"整段平方"，压缩是"分段平方"**。50 步分成 3 段能省一半；**100 步分成 5 段省得更多**。

【补充】**但压缩点的选择不能只看步数**——**要和业务节点对齐**（第 2 节）：**在工具调用序列中间压缩可能丢掉"这一步还没做完"的标记。**

**Q2（计算）**：某系统把每次 run 的所有中间信息都写进长期记忆，平均每次 **10 条**，每天 **10,000** 个 run。

问：**一年会积累多少条记忆？**如果改成只写"跨任务稳定 + 经过验证"的（每天约 50 条），差多少倍？

**A2**：

```text
什么都写：
  100,000 条/天 × 365 = 36,500,000 条/年 ≈ 3,650 万条

只写稳定已验证的：
  50 条/天 × 365 = 18,250 条/年

差约 2,000 倍
```

【结论】**差 2,000 倍。**

【推论】**这个差别不是存储成本的问题，是检索质量的问题**：**当记忆里有 3,650 万条时，"回忆相关偏好"退化成一次低质量检索——大部分是噪声，有用的被淹没。** 这和 [[母题-G1-切分策略与索引粒度]] 里"块太大导致相似度信号被稀释"是同一个机制。

【推论】**而且噪声会自我强化**：**模型从记忆里读到一堆自己的旧推断，会更倾向于继续沿用它们**——**越写越多、越多越乱。**

**Q3（计算）**：在摘要里多保留 **200 token** 的指针信息（已完成副作用 + 幂等键 + Artifact 引用）。模型 Opus 5（输入 $5/MTok）。

问：**这个额外成本是多少？**和"丢掉副作用记录导致一次重复扣款"相比，量级如何？

**A3**：

```text
额外成本 = 200 token × $5 / 1M = $0.001
```

【结论】**保留这些指针的成本是千分之一美元量级。**

【对比】**一次重复扣款 / 重复建单的后果**：对账、退款、客诉、可能的信任损失——**任何一个都远大于 $0.001**。

【推论】**所以"摘要里要不要留副作用记录"根本不是成本问题，是意识问题**：

> **摘要不是审计记录——它的意思是"真相要外部持久化、摘要只留指针"，不是"摘要可以随便写"。**

【补充】**同一笔账也适用于"证据 ID / Artifact 引用"和"未决问题"**——**它们都只占几十个 token，但丢了就找不回来**（[[母题-G4-引用绑定与证据可追溯]]）。

**Q4（纠错）**：下面这段话哪里不准确？

> "我们的 Agent 会把模型每轮总结的内容存进长期记忆，这样它下次就记得了。"

**A4**：三处问题。

1. **"模型每轮总结的内容"不是可信信息源**。**长期记忆是派生的、需要治理的**；**模型自己的推断没经过验证就写进去，会变成一条"事实"**——**而下一轮它读到这条时，已经看不到"这是推断"的标记了**。这就是**记忆污染**。
2. **没有写入门槛**：什么都写会以 **2,000 倍**的量级累积噪声（Q2），**让"回忆相关偏好"退化成低质量检索**。
3. **缺少治理字段**：每条记忆应该有**来源、主体、作用域、置信度、更新时间、TTL、删除机制**——**"删除机制"是硬要求**（可能有敏感信息、也可能是被推翻的结论）。

【准确说法】"**长期记忆只存跨任务稳定、对未来有用、经过授权、能治理的信息**；**临时推理、模型猜测、敏感数据不自动写入**。每条记忆要带来源与置信度，**这样才不会把'自己猜的'逐渐当成'知道的'**。"

**Q5（纠错）**：下面这段话哪里不准确？

> "上下文快满了就压缩一下，把历史总结成一段话接着跑。"

**A5**：三处问题。

1. **触发条件不完整**：**Agent 里除了看窗口，还要看当前处在哪个业务节点**。**在工具调用序列中间压缩，可能丢掉"这一步还没做完"的标记**；**在副作用之后压缩才安全**（[[母题-A4-长任务状态与Checkpoint]]）。
2. **"总结成一段话"会丢掉必须留的指针**：**已完成副作用 + 幂等键、证据 ID / Artifact 引用、未决问题与剩余预算**——**丢了前者会导致恢复时重复执行副作用**（Q3：多留这些只要 $0.001）。
3. **压缩后必须 checkpoint**：**否则压缩后崩溃又回到压缩前，等于白压一次**。archive/study-courses/04 把"Context 压缩或分支合并后"明确列为 checkpoint 时机之一。

【准确说法】"**压缩点要和业务节点、checkpoint 点对齐**；**摘要要留三类指针**；**压缩完立刻 checkpoint**。而且摘要**不是审计记录**——**原始消息与工具结果要外部持久化，摘要只留引用。**"

---

**Q6（口述）**：面试官问「Memory 怎么设计」。请用**不超过 40 秒**把**写入 / 读取 / 遗忘**三段说完，并接住两个追问：**记忆为什么要放最前面？那多久更新一次？**

**A6**：

```text
三段：
  写入 —— 门槛三条（跨任务稳定 + 对未来有用 + 经过授权）；
          每条带七项元数据（来源/主体/作用域/置信度/更新时间/TTL/删除机制）
  读取 —— 召回后重排，排序因子 = 相关度 × 新鲜度 × 置信度；有数量上限
  遗忘 —— TTL 到期删、被权威源推翻的删、过载清理；删除要传播（下游引用一起失效）

追问①（为什么放最前面）：
  顺序原则 = 变化最少的内容放最前
  system → 长期记忆 → 工具描述 → 历史会话 → 当前 query
  放最后 → 每次记忆更新都打穿整段 prefix cache → 成本飙升

追问②（多久更新一次）：
  这是成本问题，不是产品问题。
  高频变动的记忆要么放尾部（放弃这段 cache），
  要么版本号 + 只追加不改（追加在尾部，不动头部前缀）
```

【验收】三段各 2 句内能说完，且第二问不卡壳——**卡壳就说明只背了"放最前"，没懂代价**。

**完整回答骨架**：三层记忆与权威性 → Agent 的压缩为什么要看业务节点 → 压缩收益算式 → **摘要必须留的三类指针**（给成本对比）→ 长期记忆的写入门槛（给 2,000 倍）→ 记忆的三种失效 → 收束到"权威性不是容量"

**完整回答（口述稿）**：
记忆要**分三层，判据是权威性不是容量**：**运行状态**（Checkpointer，单 thread、短期、自动写入）→ **长期记忆**（Store，跨 thread、需治理、**有写入门槛**）→ **业务权威状态**（最高权威，任何恢复动作都要先查它）。混在一起的后果很具体：**拿模型自己总结的"已执行"当成工具真的执行成功了**。

压缩在 Agent 里比对话里多一条判据：**除了看窗口，还要看当前处在哪个业务节点**——工具调用序列中间压缩可能丢掉"这一步还没做完"，**副作用之后压缩才安全**；而且**压缩点要和 checkpoint 点对齐，压缩后必须 checkpoint**（否则压缩后崩溃又回到压缩前，等于白压一次）。收益能算：50 步每 20 步压一次，累计输入从 **3.19M 降到 1.49M（约一半）**，任务越长省得越多。摘要必须留三类指针：**已完成副作用 + 其幂等键、来源 ID、未决问题**。

防污染两道：**写入门槛**（只写验证过的）+ **条目自带来源与置信度**——最危险的是"模型推断写进去后，下一轮就看不到推断标记了"。

**分层要点**：
- **结论**：三层按权威性分；压缩要看业务节点，且与 checkpoint 对齐。
- **推导链**：State/Context/Memory 权威性不同 → 混用导致"模型摘要当事实" → 压缩点选择 → 压缩后必须 checkpoint → 写入门槛 + 置信度防污染。
- **量化**：50 步每 20 步压一次 → 累计输入 3.19M → 1.49M（约一半）。
- **边界与常见误解**：多轮对话里幻觉会累积（上一轮的错误结论进了下一轮就变成"已确认事实"）；长文档要先逐字摘录再作答，引用在生成时就产生。

**追问**（先说后看）

1. **Agent State、Context、Memory 有何区别？** —— **State 是运行时结构化事实；Context 是某一次模型调用看到的投影；Memory 是跨步骤 / 会话复用的信息**。**业务状态仍由数据库权威维护**。**恢复时从 State 和业务状态重新装配 Context。**
2. **Memory 应该存什么？** —— **只存跨任务稳定、对未来有用、经过授权、能治理的信息**。临时推理、模型猜测、敏感数据不自动写入。每条有**来源、主体、作用域、置信度、更新时间、TTL 和删除机制**。
3. **怎么防止记忆污染？** —— **两道**：**写入门槛**（只写验证过的）+ **条目自带来源与置信度**（这样模型读到它时知道这是"推断"还是"事实"）。**最危险的是"模型推断写进去后，下一轮就看不到推断标记了"。**
4. **压缩和 checkpoint 什么关系？** —— **同一个动作的两面**：一个改上下文、一个存状态。**压缩后必须 checkpoint**，否则压缩后崩溃又回到压缩前，**等于白压一次**。
5. **长文档场景怎么保证 grounding？** —— 对超过 20k token 的文档，**先要求逐字摘出相关原文（找不到就明说"没找到"），再基于摘录作答**——这样引用在生成时就产生了，而且**摘要里天然带着可回溯的指针**（[[母题-G4-引用绑定与证据可追溯]]）。

**同类变体**

- 「多轮对话里幻觉会累积吗？」——**会**。上一轮的错误结论进了下一轮上下文，就变成"已确认事实"。**所以摘要必须标注哪些是已验证事实、哪些是模型推断**，关键状态要回权威源重查。
- 「子 Agent 的上下文怎么和主 Agent 交互？」——**子 Agent 在自己的干净窗口里探索，只回传 1,000–2,000 token 的浓缩结论**——**这本质上是"压缩"的一种实现，而且它天然地只回传了结论、不带过程的噪声**（[[母题-A7-多Agent拆分与协作]]）。
