**题目**：面试官问——"工具调用超时了怎么办？如果重试，怎么保证不会重复扣款、重复建单？"

**母题**：**失败之后重试是本能——但"重试一次"和"多扣一次款"之间的距离，靠什么堵住？**

**为什么重要**：这是**Agent 从 Demo 到生产的分界线**。Demo 里工具调用几乎不会失败；生产里超时、限流、进程重启天天发生。**而这题有一个非常具体的反例——用 `ToolCallID` 当幂等键**——**它看起来天经地义，实际永远失效**。能说出这个反例，基本就能证明你真的处理过线上重复。

## 一、教材

### 1. 前提：先分清什么是"副作用"

【推导】**不是所有的工具调用都需要幂等保护**——先分类：

```text
① 只读工具（查询、检索、读文件）
   → 重试天然安全，不需要幂等键

② 幂等的写（"把状态设为 X"）
   → 重试安全（重复执行结果一样），但要注意"覆盖"语义

③ 非幂等的写（"余额减 1"、"追加一条记录"、"发一条消息"）
   → 【必须】有幂等保护，否则重试就是重复执行
```

【推论】**"重试安不安全"不是由"这个工具重不重要"决定的，是由"重复执行会不会产生第二次效果"决定的。** 所以**分类要在设计工具时就做**，而不是出事之后再补。

【事实】**Agent 场景的特殊性**：**模型会自己重试**。它看到工具报错，可能换一种参数再调一次——**这相当于一个"没有退避、没有上限、没有幂等键"的自动重试**（[[母题-A1-计划执行循环与停止条件]] 的无进展检测也治这个）。

::figure idempotency-key.svg | 幂等键必须是「业务身份」，不是「调用身份」 | 用 ToolCallID 时重试换钥匙、约束永不生效；用业务键时重试键不变、第二次被拒；底部是三层各重试 3 次的 27 倍放大

**到这里你应该能回答**：为什么"我们的工具调用基本不会失败"不能作为不做幂等的理由？

---

### 2. 幂等键：必须用业务身份【推导】

【事实】RuleArena 的真实设计：

```sql
UNIQUE(run_id, action_type, idempotency_key)
```

【推导】**为什么不能用 `ToolCallID`**：

```text
第一次调用：call_abc  → 插入成功
超时（其实已执行）→ 重试
第二次调用：call_def  → 【键变了】→ 唯一约束认为这是新记录 → 插入成功
→ 同一个副作用被执行了两次
```

【结论】**幂等键必须是"业务身份"（这笔操作在业务上是什么），不是"调用身份"（这次调用长什么样）。**

【取舍】**幂等键的选法**：

```text
✓ run_id + action_type + 业务键（订单号、工单号、窗口标识）
✓ 天然的业务唯一标识（同一窗口的采集记录）
✗ ToolCallID（重试会换）
✗ 时间戳（重试会换）
✗ 随机 UUID（重试会换）
```

【推论】**判据是一句话**：**"同一个业务意图重试时，这个键会不会变？"** **会变就不能用。**

**到这里你应该能回答**：为什么"我们每次调用都生成了一个唯一 ID 做幂等"反而更危险？

### 3. 重试放大【推导】

```text
客户端重试 3 次 × 网关重试 3 次 × 服务内部重试 3 次
= 最坏 3 × 3 × 3 = 27 倍请求打到下游
```

【结论】**每层都"好心"地重试，合起来就是一次流量放大 27 倍的风暴。**

【事实】**raw 里的真实事故形态**：**"队列积压 8 万，直接把副本从 20 扩到 100，情况反而更糟"**——因为**多层重试把一次故障放大成了任务风暴**（LLM 429、连接池打满、超时任务重新入队）。

【取舍】**所以重试必须分层设计，要一起定三件事**：

```text
① 哪一层负责重试（只让一层重试，其余快速失败）
② 重试几次 + 退避 + 抖动（[[母题-M16-乐观锁与悲观锁]] 的重试三件套）
③ 哪些错误可重试（见下）
```

【事实】**重试分类**（哪些能重试）：

| 类别 | 例子 | 处理 |
|---|---|---|
| **可重试** | 网络抖动、限流、下游 5xx、死锁回滚（40001） | 退避后重试，**带上限** |
| **不可重试** | 参数校验失败、权限拒绝、约束冲突（23505） | **立即失败**，走业务分支 |
| **不确定** | **超时**、连接中断、进程被杀 | **先查权威状态**（见第 4 节） |

【推论】**把"不确定"混进"可重试"是最危险的**——**因为超时的真实含义是"我不知道做没做成"，而不是"没做成"。**

### 4. 不确定状态：先查，不要赌【推导】

【推导】**工具调用超时，系统处于"未知"状态**。两个选择：

```text
选择 A：直接重试
  如果第一次其实成功了 → 重复执行 → 重复扣款

选择 B：先查权威状态
  用业务键查一次："这笔操作做了吗？"
  → 做了 → 补记结果，跳过
  → 没做 → 重试
```

【推导】**算一下这笔账**：

```text
设 P(第一次其实已执行) = 50%
重复执行的事故代价 = 100 单位（对账、退款、客诉）
查询一次的成本 = 1 单位

选择 A 的期望损失 = 0.5 × 100 = 50 单位
选择 B 的成本     = 1 单位

差 50 倍
```

【结论】**"先查权威状态"的成本几乎可以忽略，而它能消掉一整类事故。**

【事实】**原始素材的表述**（study/04 的恢复协议）：

```text
读取 Checkpoint → 校验版本 → 【查询业务权威状态】
  → 副作用已发生？ → 是：补记结果 / 跳过重复
                   → 否：按策略重试或人工
  → 重建最小 Context → 从安全节点恢复
```

【推论】**注意"查询业务权威状态"这一步是独立的一步**——**它不是"顺手查一下"，是恢复协议的必要环节**。**因为 checkpoint 记录的是"意图"，不是"事实"**（第 5 节会展开）。

**到这里你应该能回答**：为什么"超时后重试"和"失败后重试"必须区别对待？

### 5. Checkpoint 与副作用：记录的是"意图"还是"事实"【推导】

【事实】study/04 给的 checkpoint 时机（**这几条要能背**）：

```text
① 进入 / 离开每个有业务意义的节点
② 【外部副作用之前】记录 intent
③ 【副作用完成后】记录结果与业务幂等键
④ 人工中断前
⑤ 大型子任务完成后
⑥ Context 压缩或分支合并后
```

【推导】**为什么要"前后各记一次"**：

```text
② 之前记 intent：崩溃在调用中间时，系统知道"这一步本来要做 X"
③ 之后记结果：崩溃在调用之后时，系统知道"X 已经做了"

只记 ②（无 ③）：恢复时不知道做没做 → 只能先查权威状态（第 4 节）
只记 ③（无 ②）：崩溃在中间时，连"本来要做什么"都不知道 → 无从恢复
```

【推论】**checkpoint 记录的是"意图 + 事实"两份，而它们之间正好夹着那个"不确定窗口"。** **这就是为什么原始素材说"Checkpoint 不是简单序列化内存"**——**它必须与工具版本、业务状态和幂等记录协调。**

**到这里你应该能回答**：为什么"把内存序列化下来"不等于做了一个可用的 checkpoint？

---

### 6. 四种操作要分清：Resume / Replay / Retry / Fork【事实】

【事实】study/04 给的对照（**这张表是这一题的高分点**）：

| 操作 | 目标 | 对副作用的处理 |
|---|---|---|
| **Resume** | 完成原任务 | **查询状态**，必要时继续执行 |
| **Replay** | 复现 / 评估轨迹 | **默认使用记录结果或沙盒，不重做真实副作用** |
| **Retry** | 重做一个失败步骤 | **仅对可重试错误且有幂等保障** |
| **Fork** | 从历史节点探索新方案 | **新 branch，继承只读事实，不继承未批准写权限** |

【推导】**这四个最容易混的是 Replay 和 Resume**：

```text
Resume：我要把这件事做完 → 该做的副作用要真做
Replay：我要看看当时到底发生了什么 → 【不能真做副作用】
```

【推论】**Replay 如果重做真实副作用，那它就不是 Replay，是"重放事故"**——**这是评测和调试场景里最容易踩的坑**（比如你想复现一次失败，结果又扣了一次款）。

【推论】**Fork 那条"不继承未批准写权限"设计得很细**：**你可以继承"当时读到的事实"，但不能继承"当时被批准的写权限"**——**因为权限的批准是针对具体动作的**（[[母题-A6-沙箱权限与可信执行]] 的"批准必须绑定具体动作摘要和版本"）。

**到这里你应该能回答**：为什么 Replay 默认不能重做真实副作用？

### 7. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "用 `ToolCallID` 做幂等键最自然" | **它永远失效**。重试会产生**新的调用 ID**，唯一约束认为这是新记录 → **同一个副作用被执行两次**。**必须用业务身份**（`run_id + action_type + 业务键`） |
| "超时了就重试" | **超时的含义是"不知道做没做成"**，不是"没做成"。**直接重试可能重复执行**；正确动作是**先按业务键查权威状态**（期望损失 50 vs 成本 1，差 50 倍） |
| "每一层都加个重试更保险" | **三层各重试 3 次 = 最坏 27 倍放大**。raw 里的真实事故：**队列积压时扩副本反而更糟，因为多层重试把一次故障放大成了任务风暴**。**只让一层重试，其余快速失败** |
| "约束冲突和网络错误一样，重试就行" | **完全不同**。**约束冲突（23505）是确定性失败，重试一万次也不会成功**——要走业务分支。**只有可重试错误才重试**（网络抖动、限流、死锁回滚） |
| "幂等靠应用层判断就够了" | **应用层幂等是优化，数据库约束才是正确性**（[[母题-P19-唯一约束与UPSERT]]）。**锁会失效（超时、网络分区），唯一约束不会**。而且应用层的"先查再写"在并发下有窗口 |
| "Replay 就是把当时的操作再做一遍" | **那就成了"重放事故"**。**Replay 的目标是复现 / 评估轨迹，默认使用记录结果或沙盒，不重做真实副作用**。Resume 才是"把事做完" |
| "Checkpoint 就是把内存序列化下来" | **不是**。它必须**与工具版本、业务状态和幂等记录协调**——而且要在**副作用之前记 intent、之后记结果**，两份合起来才能恢复 |

【取舍】读成一句话：**幂等不是"让操作不重复执行"，是"让重复执行不产生第二次效果"——前者做不到（网络就是会重发），后者可以。**

## 二、自测

**Q1（计算）**：客户端重试 **3 次**、网关重试 **3 次**、服务内部重试 **3 次**，三层各自独立。

问：**最坏情况下，一个原始请求会变成多少个请求打到下游？**这个数字对系统意味着什么？

**A1**：

```text
最坏放大 = 3 × 3 × 3 = 27 倍
```

【结论】**一次"保险起见"的三层重试，最坏会把请求放大 27 倍。**

【推论】**在正常负载下这没问题；在故障时它会要命**——raw 里的真实事故形态就是：

```text
队列积压 8 万 → 把副本从 20 扩到 100 → 情况反而更糟
  因为：副本多了 → 每个副本都在重试 → LLM 429 + 连接池打满
       → 超时任务重新入队 → Retry Queue 翻倍
```

【取舍】**所以重试必须分层设计**：**只让一层负责重试，其余快速失败**；而且要配套**退避 + 抖动 + 上限**（[[母题-M16-乐观锁与悲观锁]]）和 `max_retries` 预算（[[母题-A1-计划执行循环与停止条件]]）。

**Q2（判读）**：下面两种幂等键设计，**哪种能真正拦住重复执行？为什么？**

```text
方案 A：UNIQUE(tool_call_id)              ← 每次调用生成的 ID
方案 B：UNIQUE(run_id, action_type, idempotency_key)
```

**A2**：

**只有方案 B 能拦住。**

```text
方案 A 的执行过程：
  第一次调用：tool_call_id = call_abc  → 插入成功
  超时（其实已执行）→ 重试
  第二次调用：tool_call_id = call_def  → 【键变了】
  → 唯一约束认为这是【新记录】→ 插入成功
  → 同一个副作用被执行了两次

方案 B 的执行过程：
  第一次：run_1 / refund / order_42  → 插入成功
  超时（其实已执行）→ 重试
  第二次：run_1 / refund / order_42  → 【键没变】→ 唯一约束拒绝
```

【结论】**幂等键必须是"业务身份"（这笔操作在业务上是什么），不是"调用身份"（这次调用长什么样）。**

【判据】**一句话**：**"同一个业务意图重试时，这个键会不会变？"** 会变就不能用。所以 **`ToolCallID`、时间戳、随机 UUID 都不能用**。

【补充】RuleArena 的真实设计就是 `UNIQUE(run_id, action_type, idempotency_key)`——**这三段分别回答"哪一次运行、什么动作、针对哪个业务对象"。**

**Q3（计算）**：一次工具调用**超时了**，系统不知道它到底执行成功没有。

```text
方案 A：直接重试
方案 B：先按业务键查一次权威状态，再决定
```

设 **P(第一次其实已执行) = 50%**，重复执行的事故代价 **100 单位**，查询一次的成本 **1 单位**。

问：**两种方案的期望代价各是多少？**

**A3**：

```text
方案 A（直接重试）：
  期望损失 = P(已执行) × 事故代价
          = 0.5 × 100 = 50 单位

方案 B（先查）：
  成本 = 1 单位（无论查出来是哪种结果，都是一次查询）
  → 拿到权威状态后：做过就跳过，没做就重试，【不会重复执行】
```

【结论】**差 50 倍。**

【推论】**"先查权威状态"的成本几乎可以忽略，而它能消掉一整类事故。** 这也是 study/04 恢复协议里**把"查询业务权威状态"单独列一步**的原因——**它不是"顺手查一下"，是必要环节**。

【补充】**如果查询本身也可能超时或失败**，要有**兜底策略**（比如转人工）——但**这不构成"不如直接重试"的理由**：**不确定时转人工的成本，仍然远低于重复扣款的成本。**

**Q4（纠错）**：下面这段话哪里不准确？

> "工具调用失败我们就重试三次，最多重试三次很安全。"

**A4**：三处问题。

1. **"失败"和"超时"不是一回事**。**超时的含义是"不知道做没做成"**——直接重试可能**重复执行**。**不确定状态必须先查权威状态**（Q3：期望损失 50 vs 成本 1）。
2. **"重试三次"没说清哪些错误可重试**。**约束冲突（23505）、参数校验失败、权限拒绝都是确定性失败，重试一万次也不会成功**——它们应该**立即失败走业务分支**。
3. **"很安全"缺少幂等保障**。**没有幂等键的重试只是在赌**——赌"业务上重复执行不会出事"。而**幂等键还必须用业务身份，不能用 `ToolCallID`**（Q2）。

【准确说法】"重试的正确形态是**三个条件同时成立**：**① 只对可重试错误重试**（网络抖动、限流、死锁回滚）；**② 带退避 + 抖动 + 上限**；**③ 有业务身份的幂等键兜底**。**缺任何一条都不安全。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们要复现昨天那次失败的轨迹，直接按记录重放一遍操作就行。"

**A5**：**那会把事故重放一遍。**

1. **Replay 的目标是"复现 / 评估轨迹"，不是"把事做完"**。study/04 明确写了：**Replay 默认使用记录结果或沙盒，不重做真实副作用**。
2. **如果重做真实副作用，你会在调试的同时又扣一次款**——**而调试通常要跑很多次**。
3. **要"把这件事做完"的是 Resume，不是 Replay**——**两者的目标不同，对副作用的处理也完全不同**：

| 操作 | 目标 | 副作用 |
|---|---|---|
| **Resume** | 完成原任务 | **查询状态**，必要时继续执行 |
| **Replay** | 复现 / 评估轨迹 | **不重做真实副作用** |
| **Retry** | 重做一个失败步骤 | 仅对可重试错误且有幂等保障 |
| **Fork** | 从历史节点探索新方案 | 新 branch，**不继承未批准写权限** |

【准确说法】"**Replay 默认用记录下来的工具结果**——这样重放是确定的、可重复的、零副作用。**要真执行的是 Resume**，而且它也要先查权威状态。"

## 三、面试输出（学完再看）

**一句话结论**：**幂等不是"让操作不重复执行"（做不到，网络就是会重发），是"让重复执行不产生第二次效果"。** 核心是**幂等键必须用业务身份**——RuleArena 的真实设计是 `UNIQUE(run_id, action_type, idempotency_key)`；**用 `ToolCallID` 当键会永远失效**，因为**重试会产生新的调用 ID**，唯一约束认为那是新记录。**第二件事是重试分类**：可重试（网络抖动、限流、死锁回滚）、不可重试（约束冲突、参数校验、权限拒绝——**确定性失败**）、**不确定（超时、连接中断）**。**第三件事：不确定状态必须先查权威状态，不要赌**——P(已执行) 50%、事故代价 100 单位时，**直接重试的期望损失 50 单位 vs 查询成本 1 单位，差 50 倍**。**第四：重试要分层**——三层各重试 3 次 = 最坏 **27 倍放大**，raw 里的真实事故就是"队列积压时扩副本反而更糟"。最后，**Resume / Replay / Retry / Fork 四个操作对副作用的处理完全不同**——**Replay 默认不重做真实副作用**，否则就是在重放事故。

**恢复关键词**：副作用三分类（只读 / 幂等写 / 非幂等写）/ **幂等键 = 业务身份**（`run_id + action_type + 业务键`），**不能用 ToolCallID** / 重试放大 3×3×3 = 27 / 重试三件套（可重试分类 + 退避抖动 + 上限）/ **超时 ≠ 失败**，先查权威状态 / 期望损失 50 vs 1 / checkpoint 前记 intent、后记结果 / **应用层幂等是优化，数据库约束才是正确性** / Resume · Replay · Retry · Fork 四分工 / Replay 不重做副作用

**核心不变量 / 主线**：
**幂等的实现位置决定了它的可靠性：应用层是优化，数据库约束才是正确性。**
应用层的"先查再写"在并发下有窗口、在崩溃后会失效；**唯一约束是唯一一个"无论如何都拦得住"的位置**（[[母题-P19-唯一约束与UPSERT]]）。

**完整回答骨架**：先分副作用三类 → **幂等键必须用业务身份（ToolCallID 反例）** → 重试分类（可重试 / 不可重试 / **不确定**）→ **不确定时先查权威状态（给期望损失算式）** → 重试放大 27 倍与分层设计 → checkpoint 前 intent 后结果 → Resume/Replay/Retry/Fork 四分工 → 收束到"约束才是正确性"

**追问**（先说后看）

1. **中断恢复时如何避免重复扣款 / 建单？** —— **副作用前记录 intent 和业务幂等键；调用端和服务端共同支持幂等；超时不确定时先按业务键查询状态；结果落库后 checkpoint；Resume 跳过已完成动作**。必要时补偿或人工。
2. **哪些错误可以重试，哪些不能？** —— **可重试**：网络抖动、限流、下游 5xx、死锁回滚（40001）。**不可重试**：参数校验失败、权限拒绝、约束冲突（**确定性失败，重试也没用**）。**不确定**：超时、连接中断——**先查权威状态**。
3. **幂等键怎么设计？** —— **用业务身份**：`run_id + action_type + 业务键`。**判据是"同一个业务意图重试时这个键会不会变"**。**不能用 `ToolCallID`、时间戳、随机 UUID**（重试都会变）。
4. **为什么"应用层判断是否已执行"不够？** —— **两个漏洞**：① **并发下有窗口**（两个请求同时查到"没执行"）；② **崩溃后失效**（应用层的记录可能比业务写入更晚落盘）。**数据库唯一约束是唯一"无论如何都拦得住"的位置。**
5. **Replay 和 Resume 有什么区别？** —— **Resume 要把事做完**（该做的副作用要真做，且要先查状态）；**Replay 要复现轨迹**（**默认用记录结果或沙盒，不重做真实副作用**）。**混用会把调试变成事故重放。**

**同类变体**

- 「Agent 有副作用，和普通后端服务的幂等有什么不同？」——**本质相同，但多了一个来源：模型会自己重试**。它看到报错可能换个参数再调一次——**这相当于一个没有退避、没有上限、没有幂等键的自动重试**。所以 Agent 里的重试要求**更严**。
- 「怎么验证幂等真的生效了？」——**做故障注入**：**在"副作用已执行但结果未落盘"这个窗口里杀掉进程**，然后恢复，检查是否重复执行（[[母题-A4-长任务状态与Checkpoint]] 的验收项就是这个）。
