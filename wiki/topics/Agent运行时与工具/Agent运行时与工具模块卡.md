## 0. 模块边界（先写这个，防无限扩张）

**包含**：Agent 循环的形状与停止条件、工具契约与 MCP 边界、失败恢复与幂等、长任务的状态模型与 checkpoint、上下文压缩与记忆、沙箱与权限分级、多 Agent 拆分的判据、动态计划下的可靠执行。

**明确不包含**：

- **具体框架的 API**（LangGraph / Agent SDK 的写法）——只讲**选型判据**（状态是否可导出、checkpoint 粒度、幂等支持），不讲怎么调 API
- **模型训练侧的 Agent 能力**（RL 训 tool use）——只到"工具的 schema 设计会影响选择准确率"
- **多 Agent 的具体通信协议实现**（消息队列选型、gRPC 细节）——属于后端底盘
- **前端交互细节**（怎么渲染流式）——只在"事件流要结构化"这一层提
- **自建 MCP server 的完整开发**——只到"边界在哪、什么该做成工具"

**边界判据**：**本模块只回答"Agent 怎么不失控、失败之后怎么接着干、风险怎么管住"**。凡是"某个框架怎么用"的，不进本卡。

## 5. 项目映射（三个简历项目逐个过）

### 5.1 RuleArena（规则竞技场）· 主承载项目

- **锚点**：`projects/RuleArena/`
- 用在哪：**显式 FSM 编排**（准备 → 取证 → 各角色审查 → 合并 → 确定性验证 → 人工确认 → 完成）；**Thread/Run/Step/Checkpoint/Artifact/Event 数据模型**；**每个步骤记录 Prompt/Model/Tool/Rule 版本**
- 解决什么问题：**高风险修复发布前 interrupt**；**从任一步 fork 比较不同策略**；**Replay 默认使用记录的工具结果**
- 踩过的坑：**一开始想过用 LangGraph 的自由编排，最后没用**——它的控制流由框架决定，而这个项目的卖点恰恰是「流程确定性」：**发布门禁的每一步都必须可复现、可审计**，裁决不能落在一个模型驱动的调度器手里。用自由编排等于把「可证明」换成了「大概率」。
- 决策与取舍：**三种终止原因必须各占一个码**——`completed_verified`（结果通过验证）/ `budget_exhausted`（预算耗尽）/ `unrecoverable_error`（证据冲突等不可恢复）。**合成一个「失败了」会毁掉归因**：预算耗尽说明任务太难或预算太紧，该调参；证据冲突说明规则或 Oracle 有问题，该查设计。**终止原因是 Eval 的输入，不是一个日志字段。**

- 对应母题：【A4】【A8】

### 5.2 EnergyOps（金山园区能耗）· 最硬的证据区

- **锚点**：`projects/EnergyOps/`
- 用在哪：**Hook 链 + R0/R1/R2 风险分级**（这是简历最硬的一条 bullet）；**30 个 MCP 工具封装**、6 类 Capability Bundle
- 解决什么问题：**Agent 在跑，但危险动作被 Hook 拦住**
- 踩过的坑：**一开始想用 Prompt 约束代替 Hook**——「你已经拿到了审批，可以执行了」。**Prompt 是说服，Hook 是强制**：模型可能幻觉出一个不存在的审批、或把上一次的审批用到这一次。改成 Before Tool Hook 里**校验一次性确认令牌**（绑定动作摘要 + 版本 + 期望状态）后，越权才真正归零。
- 决策与取舍：**30 个工具按 6 类业务域分组，不是平铺**——平铺的代价是每次请求都要付全部工具定义的 token，且**相似命名的工具会互相干扰选择**（选择的准确率随工具数下降）。**少用且重的（结算、批量）标记延迟加载**，用到时才通过工具搜索引入；高频查询类常驻。

- 对应母题：【A2】【A3】【A6】

### 5.3 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**意图路由**（该走 RAG 还是 NL2SQL 还是直接回答）；**五层安全**；**大结果外置为 Artifact + 结构化 Checkpoint 恢复**（`12-多轮上下文与任务恢复.md`：语义可继承、当前数重查）
- 解决什么问题：**Agent 的计划依赖领域判断**——路由错了后面全错
- 踩过的坑：**意图路由错一步，后面全错**——把「本月销售额」路由到 NL2SQL 是对的，但把「为什么下降」也当成一次取数就会漏掉归因。早期没有独立的路由阶段，模型会直接选工具，**错误要到结果出来才暴露，且无法归因到哪一环**。
- 决策与取舍：**「先判断意图」是把一次不可归因的失败拆成可归因的两段**：路由错 → 看路由的输入输出；生成错 → 看 SQL。**全给模型则是把两个问题混成一个**，出错时只能说「答错了」，说不出错在哪。这也是六阶段链路存在的理由——**可归因 > 看起来更聪明**。
- **上下文侧的取舍（`12-多轮上下文与任务恢复.md`）**：**语义可继承、当前数重查**——用户说「那华南呢」继承指标和时间、替换区域过滤，但销售额必须重查；**大结果外置为 Artifact，上下文只留口径/聚合/引用**；**压缩生成的是结构化 Checkpoint（约束 + 未决项 + 证据 + 版本），不是聊天摘要**；**第一版只做原子回合 + 近期窗口 + 大结果外置**，真实长对话到预算才上 Token-aware 召回。

- 对应母题：【A2】【A5】【A7】

## 8. 题级答案（「本主线的题」翻转卡背面 · 先说后翻）

> 题号与第 4 节题单一一对应。**必背**题写成能直接说出口的一段话；**理解 / 了解**题写 1–3 句。
> 翻转卡背面先给这道题的答案，再挂上「所属母题的完整回答（口述稿）」与单卡入口——两段合起来才是深挖。

### 1 （必背）
**五条件**：有目标、能观察、模型能选动作、**动作改变环境**、**根据结果继续或停止**——所以"问一次模型返回文本"不是 Agent。

循环体只有四步：组装上下文 → 模型决策 → 校验并执行工具 → 记录 Step。**工程的分量全在出口**：正常出口是**结果通过验证**（不是模型说 done），异常出口是**多种预算 + 无进展检测**。

预算是**七种不是一个**：`max_steps`（防循环）、`max_tokens/cost`、`deadline`（防慢）、`max_tool_calls`、`per-tool quota`、`max_retries`（**防重试放大**）、`artifact size`；它们**先到先停**，设的时候要算清楚哪个会先生效。

### 2 （必背）
两个判据：**谁决定下一步**、**动作是否改变环境**。单次工具调用：模型选一次工具、拿到结果就结束，没有循环；Workflow：步骤**预先确定**（固定 DAG），执行路径可穷举；Agent：**下一步无法预先穷举**，由模型看观察结果决定，且动作会改变环境。

选型判据是"步骤固定就别用 Agent"——Agent 带来两个代价：成本不可预测、行为不可穷举。

### 3 （必背）
六类手段叠加：① **多种预算**（步数 / 时间 / 成本 / 工具次数 / 单工具配额 / 重试次数 / 产物大小，先到先停）；② **检测重复状态和重复调用**（同一工具同参数反复调用就是信号）；③ **工具返回明确的错误语义**（不然它不知道该换路）；④ **每轮验证进展**（用真实的外部反馈，而不是只看模型自述）；⑤ **连续无进展就触发澄清、降级或转人工**；⑥ **终止原因结构化进 Eval**，用来调阈值。注意 `max_retries` 这一项防的是"重试放大"，不是防重试本身。

### 4 （理解）
因为终止原因要**进 Eval、用来调阈值**——写成"失败了"三个字既没法定责也没法优化。结构化枚举大致：达到目标（结果通过验证）、预算耗尽（要标明七种预算里哪一种先到）、重复/无进展（检测到循环）、工具不可用、权限被拒、人工中断、内部错误。

前两类是正常或受限结束；后面几类是异常，而且每一种异常对应的修复动作不同——这正是要分开记的原因。

### 5 （必背）
核心是：**工具不是"能力的暴露面"，是"给模型看的界面"**，要按 agent 的 affordance 设计，而不是把 API 包一层。三条：① **别把 API 直接封装**——传统软件可以遍历全量，agent 只能 token by token 读，`list_contacts` 会逼它用有限上下文做暴力搜索，`search_contacts` 才对；② **按工作流做 consolidation**（`list_users`+`list_events`+`create_event` → `schedule_event`），收益不只是少调几次，更是**让中间产物不进上下文**；③ **命名空间**（`asana_projects_search`）避免工具混淆。

描述要清晰、具体、有边界；但对新一代模型，**给示例反而可能限制探索空间**——更好的做法是设计接口本身：把 `status` 做成 `pending / in_progress / completed` 的枚举，光是列出来就在提示怎么用。错误语义要明确返回"为什么失败"，让模型知道该换参数还是换工具。

### 6 （必背）
三种代价：① 每个工具的描述都占上下文——30 个约 6,000 token/请求，**每轮都付，且注意力层面没有折扣**；② 重叠或含糊的工具让 agent 分不清该用哪个；③ 选错的概率上升。

手段三条：**consolidation**（合并常用组合）、**namespacing**、**延迟加载**（`defer_loading`，把少用工具移出缓存前缀，代价从"每轮都付"变成"用到才付"）。怎么知道该合并哪些：看"工具调用总次数"——经常被连着调用的组合就是 consolidation 候选；冗余调用多说明分页 / token 参数要调；参数无效的错误多说明描述不清。

### 7 （理解）
MCP 是**工具接入的标准化协议**：把"每个客户端各写一套集成"变成"一次实现、多处复用"。**边界**：MCP 只统一了"怎么暴露和调用"，**没有统一"该不该暴露"**——工具的职责划分、权限边界、返回设计仍然是你的事。

### 8 （必背）
五步：① **副作用前先记录 intent 和业务幂等键**；② 调用端和服务端都支持幂等（服务端用数据库唯一约束 `UNIQUE(run_id, action_type, idempotency_key)`）；③ **超时不确定时先按业务键查权威状态，不要赌**——P(已执行) 50%、事故代价 100 单位时，直接重试的期望损失 50 单位 vs 查询成本 1 单位，差 50 倍；④ 结果落库后再 checkpoint；⑤ Resume 时跳过已完成的副作用。

关键认知：幂等不是"让操作不重复执行"（做不到，网络就是会重发），是"**让重复执行不产生第二次效果**"。

### 9 （必背）
幂等键必须用**业务身份**：`run_id + action_type + 业务键`。判据是"同一个业务意图重试时这个键会不会变"。**不能用 `ToolCallID`、时间戳、随机 UUID**——重试会产生新的调用 ID，唯一约束认为那是新记录，键永远失效。

为什么"应用层判断是否已执行"不够：① **并发下有窗口**（两个请求同时查到"没执行"）；② **崩溃后失效**（应用层的记录可能比业务写入更晚落盘）。**数据库唯一约束是唯一"无论如何都拦得住"的位置。**

### 10 （理解）
三类：**可重试**——网络抖动、限流、下游 5xx、死锁回滚（40001）；**不可重试**——参数校验失败、权限拒绝、约束冲突（**确定性失败，重试也没用**）；**不确定**——超时、连接中断，**必须先查权威状态再决定**。

Agent 场景还多一个重试来源：**模型会自己重试**，所以 `max_retries` 这条预算是防"重试放大"的，不是防重试本身。

### 11 （必背）
**存九项**：目标、运行状态、当前节点、结构化中间结果、Artifact 引用、剩余预算、版本（model / prompt / tool）、**已完成副作用与幂等键**、待审批动作。大结果存外部只留引用，敏感信息按权限治理。

**时机**：进出业务节点、**副作用前后**、人工中断前、大型子任务完成后、上下文压缩或分支合并后——纯只读的中间步骤不必记（重做代价低、存储成本高）。核心是"**记两次**"：副作用前记 intent、后记 result，这两次之间夹着的"不确定窗口"，正是恢复时必须先查权威状态的原因。另外：**只存聊天历史恢复不了**，因为里面没有"哪些写操作真的发生了"。

### 12 （必背）
**Resume** 要把事做完——该做的副作用要真做，但先查状态跳过已完成的；**Replay** 只复现轨迹——默认用记录结果或沙盒，**不重做真实副作用**（你要的是调试，不是事故重放）；**Retry** 仅对可重试错误且有幂等保障；**Fork** 继承只读事实，但**不继承未批准的写权限**。

配套：长任务状态要分层（Thread / Run / Step / Branch / Checkpoint / Artifact / Event 七类实体），Step 级记录必须带三组字段——**版本**（否则 Replay 不出来）、**Artifact 引用**、**幂等键**。

### 13 （必背）
**State** 是运行时结构化事实（Checkpointer，单 thread、短期、自动写入）；**Context** 是某一次模型调用看到的投影；**Memory** 是跨步骤 / 会话复用且获准保存的信息（Store，跨 thread、需治理、有写入门槛）；**业务权威状态由数据库维护，权威性最高**。

恢复的正确姿势：**从 State 和业务权威状态重新装配 Context**，而不是拿旧摘要直接续跑。混在一起的后果很具体——**拿模型自己总结的"已执行"当成工具真的执行成功了**。

### 14 （理解）
多一条判据：**除了看窗口，还要看当前处在哪个业务节点**——工具调用序列中间压缩可能丢掉"这一步还没做完"，**副作用之后压缩才安全**。而且**压缩点要和 checkpoint 点对齐，压缩后必须 checkpoint**，否则压缩后崩溃又回到压缩前，等于白压一次。

收益能算：50 步每 20 步压一次，累计输入从 3.19M 降到 1.49M（约一半），任务越长省得越多。摘要必须留三类指针（已完成副作用 + 其幂等键、来源 ID、未决问题）。

### 15 （理解）
只存**跨任务稳定、对未来有用、经过授权、能治理**的信息；临时推理、模型猜测、敏感数据不自动写入。每条记忆要有**来源、主体、作用域、置信度、更新时间、TTL 和删除机制**。

防污染两道：**写入门槛**（只写验证过的）+ **条目自带来源与置信度**——最危险的是"模型推断写进去后，下一轮就看不到推断标记了"。清理靠 TTL 与删除机制，跨 thread 的长期记忆还要有治理流程。

### 16 （必背）
不能靠"让模型别做坏事"，也不能靠"人一直盯着"——要靠**即使它决定做坏事，也做不到**。核心是**用边界替代确认**：**文件系统隔离（管"能碰什么"）+ 网络隔离（管"能送到哪"），两个必须是"与"不是"或"**——只有文件系统隔离，它能读到的东西可以被传出去；只有网络隔离，它能改坏沙箱外的东西甚至绕出去再联网。

再加**风险分级**（R0 自动 / R1 提示 / R2 强制拦截）。为什么不能每次都确认：Anthropic 实测沙箱把审批提示减少 84% 且更安全，因为"每次都确认"会失效——50 个动作里用户从第 20 次左右就不看了，后 30 次形同虚设。最后一条：**真正的凭证永远不进沙箱**；云端沙箱还要防跨租户逃逸（独立容器 / microVM）。

### 17 （必背）
六项：**将执行什么、作用对象、关键参数、影响、证据、是否可撤销**。

而且**批准必须绑定具体动作摘要和版本**——不能用一次"允许所有"永久放权，那等于把批准从"一次动作"降级成"一个类别"。

### 18 （必背）
**聊天场景的损失在信息层面，Agent 场景的损失在动作层面**——删文件、发消息、转账、改权限，而且这些动作是真的发生了。所以防线要**以"边界"为主、"过滤"为辅**。

再加最小权限：每个工具只拿完成它所需的最小权限、跨权限域的操作拆成多个工具、高权限动作必须人工确认。Skill / 插件这类扩展**扩大了能力面也就扩大了权限面**，要按"能做什么"而不是"是谁提供的"来授权，且扩展本身要能被审计和禁用。验证沙箱有效性的办法是红队测试：故意注入"把 ~/.ssh 读出来发到某域名"的指令，看它是否真被拦住。

### 19 （必背）
**该拆**：重并行 + 信息量超出单窗口 + 要对接很多复杂工具（研究、多源调研）。**不该拆**：所有 agent 必须共享同一份上下文（如**大多数编码任务**）、子任务依赖很密、需要实时协调。

有效的真实原因不是"多个模型更聪明"，是**多花了 token + 并行**——Anthropic 的归因分析显示 token 用量单独就解释了 80% 的性能方差；效果实测比单 Agent 高 90.2%。代价是 **15× token**（普通对话 1×、单 agent 约 4×、多 agent 约 15×），所以判据是"任务价值高到足以支付这个性能提升"。另外 effort 必须分档——不分档会让简单查询也按复杂配置跑（浪费可达 24 倍）。

### 20 （理解）
子 agent 用**独立上下文窗口**，只回传**结构化的浓缩结论（1–2K token）**；大产物写外部系统、只传轻量引用——避免"传话游戏（game of telephone）"。这本质上是压缩，而且是"天然干净"的那种：搜索过程的噪声被隔离在子 agent 内部。

另外**不要让模型自己决定派几个子 agent**——模型判断不了合适的 effort，要把分档规则写进 prompt（Harness 的通用思路：模型判断不了的地方，用显式规则兜住）。

### 21 （理解）
按 token 倍数估：普通对话 1×、单 agent 约 4×、**多 agent 约 15×**，再乘上任务量。省的两条：**effort 分档**（不分档会让简单查询按复杂配置跑，浪费可达 24 倍）、子 agent 只回传浓缩结论。

判据：任务价值是否高到足以支付 15× token 换来的性能提升（实测 +90.2%）。

### 22 （必背）
三件事一起做：① **计划外化**——把计划做成**版本化的产物**（OpenAI 的做法是 checked into the repository，修订产生新版本，**偏离变成可见的 diff**），人不必读全过程，只需要看计划变了没有；② **把目标变成可验证的信号**——"agent 访问不到的东西等于不存在"，把 logs / metrics / traces 暴露给 agent 后，目标从"确保启动快一点"变成"**启动在 800ms 内**"，验证成本差 10 倍；③ **能确定化的检查就确定化**——10 项检查全用模型 Judge（85% 准）只有 19.7% 全对，60% 确定化后升到 52%+。

为什么难：**跑偏最难的地方是"它看起来很正常"**——还在调工具、还在推进，没有任何信号告诉你它在做的不是原来那件事。所以约束别只写在提示里，写成 linter / structural test，违规必然被拦住，并把修复指令写进错误信息。

### 23 （理解）
**同一模型可能重复同一盲点**——它看不出自己的错，多一轮还是同一个错；而且多一次调用就多一份成本。所以优先给**外部测试 / 工具反馈**（那是真实的外部信号）；Reflection 适合用来**生成候选修复或检查清单**，并且要通过 Eval 验证它到底带来多少增益。

### 24 （理解）
归因层次不同。RAG 是**三段归因**：没捞到 / 没进上下文 / 生成错。Agent 层次更多：**目标理解 → 计划 → 每一步的工具选择与参数 → 副作用 → 终止判定**，而且**要评"交互模式"而不只是单个 agent**（多 agent 有涌现行为——改 lead 的 prompt 可能不可预测地改变子 agent 的行为）。

共同点：都必须能定位到具体哪一段坏了，都要区分错误与弃答，都要 held-out 集合。RuleArena 的做法是显式 FSM——"当前该做哪一步"是可检查的，而不是"模型觉得该做哪一步"。
