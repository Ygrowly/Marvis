# 母题 A1 · 计划执行循环与停止条件

> **模块**：Agent 运行时与工具 / Runtime 骨架
> **所属主线**：一 · 循环怎么转、什么时候停（正常路径）
> **层级**：A · 教材级（"为什么需要多种预算"能从"每种失控方式的形状不同"推出来；失控成本与无进展检测的收益都能算）
> **关联母题**：[[母题-A2-工具调用与MCP边界]]（循环里的"行动"这一环）· [[母题-A4-长任务状态与Checkpoint]]（状态模型是循环的载体）· [[母题-C1-上下文组装与窗口预算]]（每转一圈都在生成新上下文，平方计费）
> **素材来源**：`study/04-Agent-Runtime与Harness.md` 第 1–4 节 + raw 的 Harness 实践系列（含 Claude Code 的 compaction 与停止条件）。**失控成本、无进展检测收益、多预算先到先停三组算式为本次新增（待你核对）**

**导读**：必懂 3 件事（① 循环体很短，工程在出口 ② 预算有七种，因为失控有七种形状 ③ "模型说 done"不算终止原因）· 读完约 11 分钟 · 需要先懂：无

**题目**：面试官问——"请解释一下 Agent Loop。你们的 Agent 怎么保证不会一直转下去？"

**母题**：**一个 Agent 循环长什么样——以及凭什么判定它"做完了"、又怎么防它转不停？**

**为什么重要**：**这是 Agent 方向的第一道门**。它看起来简单（画个循环谁都会），但**"怎么停"才是真问题**——raw 里那句 **"只保存消息历史，进程重启后不知道哪些写操作已完成"** 和 **"无限 `while` 等模型说 done"** 就是两个反例。**能说清终止原因的粒度，比能画出循环体更能证明你跑过线上。**

## 一、教材

### 1. 前提：Agent 的必要条件

【事实】Agent 的五个必要条件：

```text
① 有目标
② 能观察环境
③ 模型能选择下一动作
④ 动作改变信息或环境
⑤ 根据结果继续或停止
```

【推论】**"问模型一次、返回一段文本"不是 Agent**——它缺 ④ 和 ⑤（动作不改变环境、也没有"根据结果继续"）。**固定 DAG 即便用了 LLM，也更准确地称为 Workflow**（[[母题-C1-上下文组装与窗口预算]] 里那句"workflow vs agent 的分界判据"）。

【取舍】**这个区分不是术语洁癖**：Agent 的自主性带来两个必须付的代价——**成本不可预测**（步数不定）、**行为不可穷举**（路径不定）。所以选 Agent 之前要先确认：**任务真的需要模型现场决定下一步吗？** 如果步骤是固定的，Workflow 更便宜也更可控。

**到这里你应该能回答**：为什么"我们的系统会调用 LLM 来选工具"还不足以称为 Agent？

---

### 2. 循环体：四步，很短

::figure agent-loop.svg | Agent 循环：一个入口，三个出口 | 循环体只有四步；真正的工程在三个出口（正常 / 预算耗尽 / 无进展）与结构化的终止原因

```text
while not state.is_terminal:
    ① 组装上下文（State → Context 投影）
    ② 模型决策：给最终答案，还是调工具
    ③ 校验工具调用 → 执行 → 拿结果
    ④ 记录 Step（版本、幂等键、耗时、错误码）
```

【事实】原始素材给的关键原则很准：

> **"Loop 很短，复杂度应集中在可测试的边界组件，而不是一个巨大的 Prompt。"**

【推论】**这句话有一个直接的工程含义**：如果你发现自己在往系统提示里堆"遇到 X 要 Y"的规则，**那多半是缺一个边界组件**（校验器、预算检查、重试分类），而不是提示写得不细。**提示里堆的规则无法被测试，边界组件可以。**

【事实】**最小 Loop 之外还需要什么**（study/04 列全了）：**超时、取消、重试分类、HITL、流式事件、并发控制、checkpoint、版本和 trace**。

**到这里你应该能回答**：为什么"把规则写进 Prompt"解决不了 Agent 的失控问题？

### 3. 预算不是一个数，是七种

【事实】**因为"失控"有不同的形状**，每种形状要一个对应的预算：

| 预算 | 防的是什么 |
|---|---|
| `max_steps` | 防无限循环 |
| `max_tokens` / `cost` | 控模型成本 |
| `deadline` | 控端到端时间 |
| `max_tool_calls` | 控外部系统负载 |
| `per-tool quota` | 限制昂贵 / 危险工具 |
| `max_retries` | **防重试放大**（[[母题-A3-失败恢复与幂等]]） |
| `artifact size` | 防日志和结果爆炸 |

【推导】**为什么一个 `max_steps` 不够**：

```text
只设 max_steps = 50，但每步特别慢（模型 2 秒 + 工具 1 秒 = 3 秒）
  最坏耗时 = 50 × 3 = 150 秒
  → 用户等不了，而且这 150 秒里连接、内存、锁都被占着

如果同时设 deadline = 60 秒：
  60 / 3 = 20 步
  → deadline 会在第 20 步先生效
```

【推论】**多个预算之间是"先到先停"**——所以设预算时**要算清楚哪个会先生效**，否则你以为在防 A，实际被 B 拦住了，而 B 的终止原因又会误导排查方向。

【取舍】**第 ⑥ 条最容易漏**：`max_retries` 防的是**重试放大**——一次故障触发重试，重试又失败触发更多重试，把一次故障放大成任务风暴（raw 里的真实事故形态）。

#### 3.1 失控要花多少钱【推导】

```text
max_steps = 50，每步新增约 2.5K token（模型决策 + 工具结果）
累计输入 = 2.5K × (1 + 2 + … + 50)      ← 历史每轮都要重发（[[母题-C1-上下文组装与窗口预算]]）
        = 2.5K × 50 × 51 / 2
        = 2.5K × 1,275
        = 3,187.5K ≈ 3.19M token

成本（Opus 5，输入 $5/MTok）= 3.19M × $5 / 1M ≈ $15.9
```

【结论】**一个失控的 50 步 Agent，单次就要约 16 美元**——而这还只是**一个** run。并发一来，账单是乘出来的。

【推论】**这是"必须有多层预算"最直接的理由**：**不是"防死循环"这种概念问题，是每一分钟都在烧钱。**

**到这里你应该能回答**：为什么"我们设了 max_steps"这句话还不够？

### 4. 第三个出口：无进展检测【推导】

【事实】**连续无进展**是比"步数耗尽"更早、更准的停止信号。两个可判定的信号：

```text
① 状态没变（这一步没有产生新的信息或新的副作用）
② 重复调用同一个工具 + 同样的参数
```

【推导】**它能把浪费压下来**：

```text
场景：第 10 步进入循环，max_steps = 50

不做无进展检测：
  跑满 50 步 → 累计输入 = 2.5K × 1,275 = 3.19M → 约 $15.9

做检测（连续 3 步无进展就停）：
  第 13 步停下 → 累计输入 = 2.5K × (13 × 14 / 2) = 2.5K × 91 = 227.5K
  → 约 $1.14

降到约 1/14
```

【结论】**无进展检测把"跑到预算耗尽"变成"确认卡住就停"**——**它比调小 `max_steps` 更准**，因为正常的复杂任务确实需要很多步，**卡住和"在认真干活"长得很像，只有"状态有没有变"能区分。**

【取舍】**检测到无进展之后做什么**，比检测本身更重要：

```text
① 触发澄清（缺输入 → needs_clarification）
② 降级（换更简单的手段）
③ 转人工（unrecoverable_error）
```

【推论】**直接报错退出是最差的选择**——**它丢掉了"卡在哪"这个最有价值的信息。**

**到这里你应该能回答**：为什么"步数少"不等于"没失控"，而"步数多"也不等于"失控"？

### 5. 终止原因必须结构化【推导】

【事实】**八种终止原因**（study/04 的清单）：

```text
completed_verified     结果通过验证
needs_clarification    缺少必要输入
waiting_approval       高风险步骤待确认
budget_exhausted       步骤 / Token / 时间耗尽
tool_unavailable       关键依赖失败
policy_blocked         权限或安全策略拒绝
cancelled_by_user      用户取消
unrecoverable_error    不可恢复错误
```

【推导】**为什么粒度重要——它直接决定可观测性的粒度**：

```text
只有 success / fail 两种：
  「失败率从 3% 涨到 12%」—— 看不出发生了什么，也不知道该动哪

有八种：
  「budget_exhausted 占比从 2% 涨到 15%」→ 该看预算与循环检测
  「tool_unavailable 涨了」              → 该看外部依赖
  「policy_blocked 涨了」                → 该看权限策略是否过严
```

【推论】**"模型停了"不是工程可用的终止原因**——**它把四类完全不同的失败压成了一句话，等于放弃了排查的入口。**

【推论】**终止原因还要进 Eval**（[[母题-G5-RAG评测与幻觉率]] 的归因思路在这里同样成立）：**不同终止原因的占比变化，是 Agent 系统最重要的健康指标之一。**

**到这里你应该能回答**：为什么"终止原因"这种看起来是日志细节的东西，值得在面试里专门讲？

### 6. 验证：Agent 必须能检查自己的工作【事实】

【事实】**验证的优先级**（study/04 的排序，从强到弱）：

```text
① 确定性测试、Schema、规则、编译器、SQL AST
② 工具返回和权威状态查询
③ 多源交叉证据
④ 模型 Judge
⑤ 人工复核
```

【事实】原始素材给了一句很硬的话：

> **"模型'自我反思'不能替代外部 oracle。最强的 Harness 通常给 Agent 可执行测试、浏览器、终端、数据库只读查询等真实反馈。"**

【推论】**这解释了为什么"Reflection"类技巧效果有限**：**同一模型重复同一盲点**——它反思时用的是同一个"坏掉的尺子"（[[母题-A8-动态计划下的可靠执行]] 会展开）。**真正有效的是给它一个外部的、可执行的判据。**

**到这里你应该能回答**：为什么"让模型自己检查一遍"不能替代"让它跑一遍测试"？

### 7. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "Agent 就是一个 while 循环调模型" | **循环体确实很短**（四步），但**工程全在出口**：正常终止要靠**验证**、异常终止要靠**多种预算 + 无进展检测**，而终止原因必须**结构化**。**只写循环体不写出口，就是 raw 里那个反例："无限 while 等模型说 done"** |
| "模型说 done 就说明做完了" | **不算**。**只有"结果通过验证"才算完成**（`completed_verified`）。模型说 done 是它的**判断**，不是**事实**——而且它可能只是"觉得自己做完了" |
| "设一个 max_steps 就够了" | **不够**。失控有不同形状：步数多、**每步慢**（要 `deadline`）、**工具调得多**（要 `max_tool_calls`）、**重试放大**（要 `max_retries`）。而且多个预算**先到先停**——要算清楚哪个会先生效 |
| "只保存消息历史就能恢复" | **这是 raw 里点名的反例**。消息历史里**没有"哪些写操作已经完成"**——重启后不知道要不要重做，要么重复扣款，要么漏做。**必须记录 Step 级别的副作用与幂等键** |
| "Agent 步数多就是失控" | **不一定**。复杂任务确实需要很多步。**判据是"状态有没有变"**——认真干活和无意义循环的区别在**进展**，不在步数 |
| "把规则写进系统提示就能防失控" | **防不住，而且不可测试**。原始的判断是"**复杂度应集中在可测试的边界组件，而不是一个巨大的 Prompt**"——预算检查、校验器、重试分类都是可测试的组件，提示里的规则不是 |
| "让模型自己反思一遍就能纠错" | **不能替代外部 oracle**。同一模型会**重复同一盲点**。优先给**可执行的反馈**（测试、编译器、只读查询），Reflection 只适合生成候选修复，且要通过 Eval 验证增益 |

【取舍】读成一句话：**循环体谁都会写，工程的分量全在"什么情况下必须停下来"——以及停下来之后，你知不知道是为什么停的。**

## 二、自测

**Q1（计算）**：某 Agent 的 `max_steps = 50`，每一步新增约 **2.5K token**（模型决策 + 工具结果）。模型是 Opus 5（输入 $5/MTok）。

问：**如果它一路跑满 50 步，累计输入 token 是多少？成本大约多少？**

**A1**：

```text
历史每轮都要重发（[[母题-C1-上下文组装与窗口预算]]）
累计输入 = 2.5K × (1 + 2 + … + 50)
        = 2.5K × 50 × 51 / 2
        = 2.5K × 1,275
        = 3,187.5K ≈ 3.19M token

成本 = 3.19M × $5 / 1M ≈ $15.9
```

【结论】**一个失控的 50 步 Agent，单次约 16 美元。**

【补充】注意这里用的是**平方累计**而不是 50 × 2.5K = 125K——**因为每一步都要把之前的历史重发一遍**。**"步数多"的代价不是线性的，这也是"为什么必须设预算"的量化答案。**

**Q2（计算）**：同上场景，第 **10 步**开始进入无意义循环。加了"连续 3 步无进展就停"的检测。

问：**它在第几步停下？省了多少成本？**

**A2**：

```text
检测生效：第 10、11、12 步都无进展 → 第 13 步停下

累计输入 = 2.5K × (13 × 14 / 2) = 2.5K × 91 = 227.5K token
成本 = 227.5K × $5 / 1M ≈ $1.14

对比不做检测的 $15.9：降到约 1/14
```

【结论】**无进展检测把"跑到预算耗尽"变成"确认卡住就停"**，单次省约 **14.8 美元**。

【推论】**它比"调小 `max_steps`"更准**：调小 `max_steps` 会**误杀正常的复杂任务**；而无进展检测判的是**进展**，不是步数。**卡住和"在认真干活"长得很像，只有"状态有没有变"能区分。**

【补充】**检测到之后做什么更重要**：触发澄清 / 降级 / 转人工——**直接报错退出是最差的选择**，因为它丢掉了"卡在哪"这个最有价值的信息。

**Q3（计算）**：某 Agent 单步平均耗时 **3 秒**（模型 2 秒 + 工具 1 秒）。它设了两个预算：`max_steps = 50` 和 `deadline = 60 秒`。

问：**哪个先生效？实际能跑多少步？**这对设预算意味着什么？

**A3**：

```text
deadline 允许的步数 = 60 / 3 = 20 步
max_steps 允许的步数 = 50 步

→ 【deadline 先生效】，实际只能跑约 20 步
```

【结论】**多个预算之间是"先到先停"**——所以设预算时**要算清楚哪个会先生效**。

【推论】**不算清楚的后果是排查被误导**：

```text
你以为在防"无限循环"（所以设了 max_steps = 50）
实际拦住的是 deadline
终止原因会报 budget_exhausted，但到底是哪个预算？
  → 所以终止原因要能细分到【具体是哪个预算耗尽】

否则你会去调 max_steps（一个根本没生效的预算），而真正该调的是 deadline 或单步耗时
```

【取舍】**单步 3 秒这个数本身也值得看**：**如果模型 2 秒、工具 1 秒，那 60 秒只能跑 20 步——说明这个任务的"步数预算"实际是被时间卡住的。要跑更多步，得先降单步耗时（比如并行工具调用），而不是调大 max_steps。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们的 Agent 循环是 while 循环，模型返回 done 就结束。"

**A4**：三处问题。

1. **"模型返回 done"不是终止原因**。模型说 done 是它的**判断**，不是**事实**——**只有"结果通过验证"才算完成**（`completed_verified`）。而且模型可能只是"觉得自己做完了"。
2. **缺了异常出口**。循环必须有**预算耗尽**和**无进展**两个出口——raw 里的反例就是"**无限 `while` 等模型说 done，没有预算、进展检测或终止原因**"。
3. **终止原因没有结构化**。「done / 没 done」这个二分把四类完全不同的失败压成了一句话，**监控上看不出该动哪**。

【准确说法】"循环的四步只是骨架；**工程全在出口**——正常出口是**验证通过**，异常出口是**多种预算 + 无进展检测**，而**终止原因要分八类并进 Eval**。"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们 Agent 设了 max_steps = 50，所以不会失控。"

**A5**：三处问题。

1. **`max_steps` 只防"步数多"这一种形状**。还有：**每步很慢**（要 `deadline`）、**工具调用过多打爆下游**（要 `max_tool_calls`）、**重试放大**（要 `max_retries`）、**结果爆炸**（要 `artifact size`）。
2. **多个预算"先到先停"**（Q3）——**实际生效的往往不是 `max_steps`**。所以设预算要算清楚，而且终止原因要**细分到具体是哪个预算**。
3. **"不会失控"这个目标定错了**。预算只能保证**停下来**，保证不了**停得对**——**要停得早、停得准，靠的是无进展检测**（Q2 里省 14 倍）。

【准确说法】"**预算是"止损"，无进展检测是"早停"，验证是"确认完成"——三件事都要有。** 而且终止原因必须结构化，否则你只知道它停了，不知道为什么停。"

## 三、面试输出（学完再看）

**一句话结论**：**Agent 的五条件**是有目标、能观察、模型能选动作、**动作改变环境**、**根据结果继续或停止**——所以"问一次模型返回文本"不是 Agent，固定 DAG 是 Workflow。**循环体只有四步**（组装上下文 → 模型决策 → 校验并执行工具 → 记录 Step），**工程的分量全在出口**：正常出口是**结果通过验证**（而不是模型说 done），异常出口是**多种预算 + 无进展检测**。**预算是七种不是一个**——`max_steps`（防循环）、`max_tokens/cost`、`deadline`（防慢）、`max_tool_calls`、`per-tool quota`、`max_retries`（**防重试放大**）、`artifact size`；而且它们**先到先停**，设的时候要算清楚哪个会先生效。**为什么必须设**：50 步每步 2.5K token 的失控 run，**累计输入 3.19M、成本约 $16**（平方累计，不是线性）。**无进展检测比调小 max_steps 更准**——判的是"状态有没有变"，能把浪费降到 1/14。最后，**终止原因必须分八类**（completed_verified / needs_clarification / waiting_approval / budget_exhausted / tool_unavailable / policy_blocked / cancelled_by_user / unrecoverable_error）——**"模型停了"不是工程可用的终止原因**。

**恢复关键词**：五条件（动作改变环境 + 根据结果停止）/ Workflow vs Agent / 循环四步 / **复杂度放可测试的边界组件，不放巨大 Prompt** / 七种预算 + 先到先停 / 平方累计的失控成本（50 步 = 3.19M ≈ $16）/ **无进展检测（状态没变 / 重复同参数调用）** / 八种终止原因 / 验证优先级（确定性测试 > 权威状态 > 交叉证据 > 模型 Judge > 人工）/ **模型自我反思不能替代外部 oracle**

**核心不变量 / 主线**：
**循环体很短，工程全在出口。**
而出口的设计决定了两件事：**花多少钱停下来**（预算 + 无进展检测），以及**停下来之后你知不知道为什么**（结构化的终止原因）。

**完整回答骨架**：五条件与 Workflow 之分 → 循环四步（点明"复杂度放边界组件"）→ **七种预算与"先到先停"** → 失控成本算式 → **无进展检测（比调 max_steps 更准）** → 八种终止原因与可观测性 → 验证优先级与"反思不能替代 oracle" → 收束到"三个出口"

**完整回答（口述稿）**：
先说清什么是 Agent：**有目标、能观察、模型能选动作、动作改变环境、根据结果继续或停止**——五条同时成立。所以"问一次模型返回文本"不是 Agent；步骤固定的固定 DAG 是 Workflow。

循环体只有四步：组装上下文 → 模型决策 → 校验并执行工具 → 记录 Step。**工程的分量全在出口**：正常出口是**结果通过验证**（而不是模型说 done），异常出口是**多种预算 + 无进展检测**。

预算是**七种不是一个**：`max_steps`（防循环）、`max_tokens/cost`、`deadline`（防慢）、`max_tool_calls`、`per-tool quota`、`max_retries`（**防重试放大**）、`artifact size`；它们**先到先停**，设的时候要算清楚哪个会先生效。

防止无限循环是六条叠加：多种预算、检测重复状态与重复调用、工具返回明确错误语义、每轮验证进展、连续无进展就触发澄清/降级/转人工、终止原因结构化进 Eval 用来调阈值。

**分层要点**：
- **结论**：五条件定义 Agent；循环体四步，分量全在出口（结果通过验证 + 多种预算 + 无进展检测）。
- **推导链**：谁决定下一步 → 动作是否改变环境 → 与 Workflow 分界 → 七种预算先到先停 → 六条防循环手段。
- **量化**：七种预算（步数/token/成本/时间/工具次数/单工具配额/重试次数/产物大小）；`max_retries` 防的是重试放大。
- **边界与常见误解**："模型说 done 就结束"×（要结果通过验证）；"一个 max_steps 就够了"×（七种先到先停，得算清哪个先到）；终止原因要结构化才进得了 Eval。

**追问**（先说后看）

1. **Agent State、Context、Memory 有何区别？** —— **State 是运行时结构化事实；Context 是某一次模型调用看到的投影；Memory 是跨步骤 / 会话复用的信息**。**业务状态仍由数据库权威维护**。恢复时从 State 和业务状态**重新装配** Context（[[母题-A5-上下文压缩与记忆]]）。
2. **怎么防止 Agent 无限循环？** —— **最大步数 / 时间 / 成本 / 工具次数；检测重复状态和重复调用；工具返回明确错误语义；每轮验证进展；连续无进展触发澄清、降级或人工；终止原因进 Eval**。
3. **Checkpoint 存什么？** —— **目标、运行状态、当前节点、结构化中间结果、Artifact 引用、剩余预算、版本、已完成副作用与幂等键、待审批动作**（[[母题-A4-长任务状态与Checkpoint]]）。
4. **Reflection 有什么局限？** —— **同一模型可能重复同一盲点**，而且多一次调用增加成本。**优先给外部测试 / 工具反馈**；Reflection 适合生成候选修复或检查清单，并**通过 Eval 验证增益**。
5. **什么时候该用 Agent 而不是 Workflow？** —— **当"下一步做什么"无法预先穷举、需要模型看情况决定**时。**步骤固定就别用 Agent**——它带来成本不可预测和行为不可穷举两个代价（[[母题-A7-多Agent拆分与协作]] 会从"多 Agent"的角度再讲一遍这个判据）。

**同类变体**

- 「Agent 的"步"（Step）具体指什么？」——**一次模型调用或一次工具调用都算一步**。Step 要记录 `kind`（model / tool）、版本、耗时、错误码、**幂等键**——**只存最终聊天文本就没法 Replay 和归因**。
- 「怎么判断一个任务该给多少预算？」——**先跑一批真实任务，统计步数与耗时的 P95**，再**按 P95 的 1.5–2 倍设预算**。**拍脑袋设的数字要么误杀正常任务，要么拦不住失控。**
