**题目**：面试官问——"你们的 Agent 有多少个工具？怎么定的？工具描述怎么写？"

**母题**：**该给 Agent 做什么工具、做多少个——为什么"把现有 API 包一层"是错的？**

**为什么重要**：这道题**直接对应你 EnergyOps 的 30 个 MCP 工具**——面试官问"30 个工具会不会太多"，答"我们分成了 6 类 Capability Bundle"只是**结果**，**说不出判据就还是背的**。Anthropic 这篇原文里有一句很硬的话：**"More tools don't always lead to better outcomes"**，而且给了具体例子说明**为什么**。

## 一、教材

### 1. 前提：Agent 的 affordance 和传统软件不一样

【事实】Anthropic 原文点出的最常见错误：

> **"A common error we've observed is tools that merely wrap existing software functionality or API endpoints—whether or not the tools are appropriate for agents."**

【推导】**差别在哪**：

```text
传统软件程序：内存便宜且充足
  → 可以一次取出全部数据，再在程序里逐条处理

LLM Agent：上下文有限且昂贵
  → 如果工具返回全部联系人，它只能【token by token 读过去】
  → 等于拿有限的上下文做【暴力搜索】
```

【事实】原文给了一个很直观的类比：

> **"imagine searching for a contact in your address book by reading each page from top-to-bottom—that is, via brute-force search"**

【推论】**人找通讯录不会从头读到尾**——会先翻到那一页。**所以工具设计的目标不是"暴露能力"，是"让 agent 用接近人的方式完成任务"。**

::figure tool-design.svg | 工具设计：把 API endpoint 直接包一层，是把检索工作推给了模型 | 左边是错误做法（返回全部、让模型暴力搜索）；右边是按工作流做 consolidation；底部是同一响应的 206 vs 72 token

**到这里你应该能回答**：为什么"我们能调的通路都封装成工具了"不是一句好话？

### 2. 原则一：按工作流做，不按 API 做【事实】

【事实】原文给的三组对照（**这三组可以直接背**）：

```text
✗ list_users + list_events + create_event
✓ schedule_event        （自己找可用时间并排期）

✗ read_logs
✓ search_logs           （只返回相关行 + 一点上下文）

✗ get_customer_by_id + list_transactions + list_notes
✓ get_customer_context  （把该客户的近期相关信息一次性汇总）
```

【推导】**consolidation 的收益有两层**：

```text
① 减少调用次数   → 少几步、少几轮上下文累积
② 把中间产物搬回工具内部 → 【这些中间产物本来会进 agent 的上下文，现在不进了】
```

【推论】**第 ② 条才是关键**：**一次 `list_transactions` 返回的 100 条流水，如果只是为了让 agent 数个数，那这 100 条就白占了上下文。** 把它合进 `get_customer_context`，计数在工具内部完成。

【事实】**原文对判据的表述**：

> **"Make sure each tool you build has a clear, distinct purpose. Tools should enable agents to subdivide and solve tasks in much the same way that a human would, given access to the same underlying resources, and simultaneously reduce the context that would have otherwise been consumed by intermediate outputs."**

#### 2.1 工具响应会被平方放大【推导】

```text
一个工具返回 5,000 token 的原始日志，40 轮会话里有 10 次这样的调用

这 10 × 5,000 = 50,000 token 会【留在历史里】
之后的每一轮都要把它重发一遍（[[母题-C1-上下文组装与窗口预算]]）

在剩余 30 轮里被重发：50,000 × 30 = 1,500,000 token 的额外输入
成本（Opus 5，$5/MTok）= 1.5M × $5 / 1M = $7.5
```

【结论】**工具响应的代价不是"这一次调用花了多少 token"，而是"它进了历史之后，被重发了多少次"。**

【推论】**改成 `search_logs` 只返回 500 token（1/10），就能省下约 $6.75。**

【事实】**所以原文建议对任何可能吃上下文的响应实现**：**分页、范围选择、过滤、截断**，并给**合理的默认值**。**Claude Code 把工具响应默认限制在 25,000 token。**

**到这里你应该能回答**：为什么"工具返回得多一点，信息更全"在 Agent 里反而更差？

### 3. 原则二：命名空间【事实】

【事实】原文的观察：

> **"Your AI agents will potentially gain access to dozens of MCP servers and hundreds of different tools… When tools overlap in function or have a vague purpose, agents can get confused about which ones to use."**

【事实】**两种命名空间方式**：

```text
按服务：asana_search、jira_search
按资源：asana_projects_search、asana_users_search
```

【事实】**一个反直觉的实测结论**：

> **"We have found selecting between prefix- and suffix-based namespacing to have non-trivial effects on our tool-use evaluations. Effects vary by LLM."**

【推论】**前缀还是后缀，对评测有实质影响，而且因模型而异——所以这个选择要靠自己的评测定，不能照搬。**

【事实】**原文还列了四种工具调用失败**（**这四种可以直接当追问的答案**）：

```text
① 调错工具
② 调对了工具但参数错
③ 工具调用太少（没查够就下结论）
④ 工具响应处理错误
```

【推论】**命名反映任务的天然切分，能同时降低四类失败**——**因为它减少了加载进上下文的工具数与描述长度**，把计算从"agent 的上下文"搬回"工具调用本身"。

### 4. 原则三：返回什么，取决于"接下来还需不需要它"【推导】

【事实】原文给的同一份数据的两种响应（Slack 线程）：

```text
详细版（206 token）：含 thread_ts / channel_id / user_id
  → 这些 ID 是【发起后续调用所必需的】

精简版（72 token）：只有线程内容，不含 ID
  → 省了约 2/3 的 token
```

【推导】**所以"该返回什么"的判据不是"信息全不全"，是**：

```text
模型接下来还需不需要用这些字段发起新调用？
  需要 → 返回 ID 类字段（详细版）
  不需要 → 只返回内容（精简版）
```

【事实】**还有一条容易被忽略的**：**响应的结构（XML / JSON / Markdown）本身会影响评测表现**——原文说**没有万能解**，**因为模型是按 next-token prediction 训练的，对匹配训练数据的格式表现更好**，**要按自己的评测选**。

【事实】**错误响应也要"可行动"**：

> **"…prompt-engineer your error responses to clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks."**

【事实】**一个真实的例子**：Claude 的 web search 工具上线时，**它会在 `query` 参数里无意义地加上 "2025"，影响搜索结果**——**修法是改工具描述，不是改模型。**

【推论】**这两条合起来说明一件事**：**工具的描述、参数、返回、错误，全都是"给模型看的界面"**——**它们不是文档，是可调优的输入。**

**到这里你应该能回答**：为什么"工具报错返回一个错误码"是不合格的？

### 5. 原则四：怎么知道工具做得好不好——用 Agent 评估 Agent【事实】

【事实】原文的流程：

```text
① 先做一个 prototype（别一上来设计完美工具集）
② 跑评测
③ 和 agent 一起打磨工具（"with agents"）
```

【事实】**要收集的指标**：

```text
顶层准确率
单个工具调用的耗时
任务总耗时
工具调用总次数
总 token 消耗
工具错误
```

【推导】**每个指标对应一类可行动的诊断**：

```text
冗余调用多      → 分页或 token 上限的参数需要调整
参数无效的错误多 → 描述不清或缺少示例
工具调用次数异常 → 可能有一批工具总是连着用 → 【合并的机会】
```

【推论】**最后一条特别值**：**"工具调用总次数"这个指标能暴露出"经常被连起来调用的工具组合"，那就是 consolidation 的候选。**

**到这里你应该能回答**：为什么"重新设计工具"这件事不能靠拍脑袋，而要先跑评测？

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "工具越多能力越强" | **反了**。原文原话：**"More tools don't always lead to better outcomes"**。**重叠或用途含糊的工具会分散 agent 的注意力**，而且**每个工具的描述都占上下文** |
| "把现有 API 全部封装成工具就行" | **这是最常见的错误**（原文点名）。传统软件内存充足、可以遍历全部数据；**agent 只能 token by token 读**。**`list_contacts` 会逼 agent 暴力搜索，`search_contacts` 才是对的** |
| "工具返回的信息越多越好" | **响应会被平方放大**：5,000 token 的日志在 40 轮里被重发 30 次 = 1.5M token ≈ $7.5。**要分页 / 过滤 / 截断 + 合理默认值**（Claude Code 默认上限 25,000 token） |
| "报错就返回错误码" | **要"可行动"**：原文明确要求**清楚地传达具体的、可改进的信息**，而不是不透明的错误码或堆栈。**错误响应也是给模型看的界面** |
| "命名前缀还是后缀无所谓" | **有非平凡的影响**，而且**因模型而异**（原文实测）。**要按自己的评测选**，不能照搬别人的命名方案 |
| "工具描述写清楚就行，不用给示例" | **对新一代模型，示例反而会限制探索空间**（[[母题-C3-Prompt版本管理与回归]]）——**更好的做法是设计接口本身**（枚举值、参数命名、默认值）。**"光是列出枚举值就在提示怎么用"** |
| "工具集设计是一次性的" | **原文的流程是"prototype → 评测 → 和 agent 一起打磨"**。**"工具调用总次数"这个指标能暴露"总被连着调用的组合"——那就是下一次 consolidation 的候选** |

【取舍】读成一句话：**工具不是"能力的暴露面"，是"给模型看的界面"——它的描述、参数、返回、错误都要按 agent 的 affordance 设计，而不是按 API 的形状包装。**

## 二、自测

**Q1（计算）**：某工具返回 **5,000 token** 的原始日志。一个 40 轮的 Agent 会话里有 **10 次**这样的调用。模型 Opus 5（输入 $5/MTok）。

问：**这些响应最终让总输入多了多少 token？多花多少钱？**

**A1**：

```text
这 10 次调用的结果会【留在历史里】：
  10 × 5,000 = 50,000 token

之后的每一轮都要重发这段历史（[[母题-C1-上下文组装与窗口预算]]）：
  在剩余约 30 轮里被重发 → 50,000 × 30 = 1,500,000 token 的额外输入

成本 = 1.5M × $5 / 1M = $7.5
```

【结论】**工具响应的真实代价不是"这一次花了 5,000 token"，而是"它进了历史之后被重发了多少次"。**

【补充】改成 `search_logs` 只返回 **500 token**（1/10），额外输入降到 150,000 token、成本降到 **$0.75**——**省约 $6.75**。

【推论】**这就是原文为什么建议对任何可能吃上下文的响应都实现分页 / 范围选择 / 过滤 / 截断**，并给**合理的默认值**。**"返回全量、让模型自己挑"在 Agent 里是最贵的做法。**

**Q2（计算）**：某 Agent 加载了 **30 个工具**，每个工具的定义（名称 + 描述 + 参数 schema）平均约 **200 token**。

问：**这些定义每次请求占多少 token？**它与"最常用的只有 8 个"相比差多少？这带来什么工程手段？

**A2**：

```text
全部加载：30 × 200 = 6,000 token / 请求
只留常用的 8 个：8 × 200 = 1,600 token / 请求

差 4,400 token / 请求
```

【结论】**工具定义是"每一轮都在付"的固定成本**——而且**成本有两层**：

```text
① 钱的层面：这 6,000 token 每轮都要重发
   （如果在前缀里且缓存命中，按 0.1× 计——[[母题-C6-成本与长上下文截断]]）
② 注意力层面：它每轮都占着 attention budget，而且【没有折扣】
   （[[母题-C1-上下文组装与窗口预算]]）
```

【推论】**所以工程上有一个直接手段**：**把少用的工具标记为延迟加载**（`defer_loading`）——**它们留在缓存前缀之外，用到时再通过工具搜索加载进来**。**代价从"每轮都付"变成"用到才付"。**

【补充】**这也解释了 EnergyOps 的"6 类 Capability Bundle"在做什么**：**它不是分组展示，是控制"每次请求加载哪些工具定义"**。**能说出这一层，比说"我们分了 6 类"更像设计过。**

**Q3（判读）**：某团队的工具集里有这三个：`list_users`、`list_events`、`create_event`。评测数据显示：**这三个工具经常被连着调用**（同一个任务里平均连着调 3 次），而且**总 token 消耗偏高**。

问：**这三个指标说明了什么？该怎么办？**

**A3**：

- **"经常被连着调用"** → 说明它们其实是**同一个工作流的三个步骤**，而 agent 每次都要自己把它们串起来。
- **"总 token 消耗偏高"** → 说明**中间产物（用户列表、事件列表）都进了 agent 的上下文**，而这些中间结果**只是为了让 agent 挑一个时间**。

【结论】**这是 consolidation 的典型信号。** 应该合并成一个 **`schedule_event`**：**自己找可用时间并排期**。

【收益有两层】：

```text
① 调用次数从 3 次降到 1 次 → 少几轮上下文累积
② 中间产物（两个列表）不再进 agent 的上下文 → 直接省掉
```

【推论】**原文的判据可以直接背**：

> **"Tools should enable agents to subdivide and solve tasks in much the same way that a human would… and simultaneously reduce the context that would have otherwise been consumed by intermediate outputs."**

**关键在最后半句**：**合并的目的不只是"少调几次"，是"让中间产物不进上下文"。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们把系统里所有的 API 都封装成了工具，一共 80 个，能力覆盖很全。"

**A4**：三处问题。

1. **"包装 API"是原文点名的常见错误**：**传统软件内存充足、可以一次取出全部数据再逐条处理；agent 只能 token by token 读**。把 `list_contacts` 这样的一次性返回全部，等于**逼 agent 用有限的上下文做暴力搜索**。
2. **"能力覆盖全"不等于"好用"**：原文原话是 **"More tools don't always lead to better outcomes"**。**重叠或用途含糊的工具会让 agent 分不清该用哪个**，而且**每个工具的描述都占上下文**（Q2 的 6,000 token/请求）。
3. **80 个工具的定义开销很可观**：按 200 token 一个算就是 **16,000 token/请求**，**每轮都付**——而且**注意力层面没有折扣**。

【准确说法】"**按 agent 的高频工作流设计少量工具**（原文建议"a few thoughtful tools targeting specific high-impact workflows"），**并把经常被连着调用的组合合并**（`list_users`+`list_events`+`create_event` → `schedule_event`）。**判据是"能不能减少中间产物占用的上下文"，不是"覆盖了多少 API"。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "工具调用失败时我们返回标准的错误码，模型看到就知道怎么回事了。"

**A5**：**原文明确反对这个做法。**

> **"…prompt-engineer your error responses to clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks."**

三处问题：

1. **不透明的错误码对模型没有信息量**：模型不知道"该怎么改"。**要给出具体的、可改进的信息**（哪个参数不合法、期望什么格式、可以试什么）。
2. **错误响应本身就是一次"提示机会"**：原文说，**工具截断和错误响应可以用来引导 agent 采用更省 token 的策略**（用过滤或分页），或者**示范正确的参数格式**。
3. **真实案例**：Claude 的 web search 工具上线时**会在 query 里无意义地加上 "2025"**，**修法是改进工具描述**——说明**工具界面（描述 / 参数 / 错误）是可调优的输入，不是一次写死的文档**。

【准确说法】"**工具的错误响应要像"给同事的错误提示"一样写**：哪里错了、期望什么、可以怎么改。**它和工具描述一样，都是给模型看的界面。**"

## 三、面试输出（学完再看）

**一句话结论**：**工具不是"能力的暴露面"，是"给模型看的界面"**——所以要**按 agent 的 affordance 设计，而不是把 API 包一层**。第一条原则：**别把 API 直接封装**——传统软件内存充足可以遍历全量，**agent 只能 token by token 读**，`list_contacts` 会逼它用有限上下文做暴力搜索，`search_contacts` 才是对的。第二条：**按工作流做 consolidation**（`list_users`+`list_events`+`create_event` → `schedule_event`；`read_logs` → `search_logs`），**收益不只是少调几次，更是让中间产物不进上下文**。第三条：**命名空间**（`asana_projects_search`），而且**前缀还是后缀对评测有实质影响、因模型而异**。第四条：**返回什么取决于"接下来还需不需要它发起调用"**——同一份数据详细版 **206 token**、精简版 **72 token**，差约 2/3。第五条：**错误响应要"可行动"**，不是不透明错误码。最后，**工具的真实代价会被平方放大**：5,000 token 的响应在 40 轮里能被重发 30 次 = **1.5M token ≈ $7.5**；Claude Code 因此**把工具响应默认限制在 25,000 token**。

**恢复关键词**：别包装 API（agent 的 affordance 不同）/ `list_contacts` → `search_contacts` / **consolidation 的收益是"中间产物不进上下文"** / namespacing（按服务 / 按资源；前后缀因模型而异）/ **响应 206 vs 72 token**，判据是"接下来还需不需要它" / 分页 · 范围 · 过滤 · 截断 + 合理默认值 / **Claude Code 默认 25,000 token 上限** / 错误响应要可行动 / 四种失败（调错工具 · 参数错 · 调太少 · 响应处理错）/ 评测指标（准确率 · 耗时 · 调用次数 · token · 错误）/ **"调用次数异常"暴露 consolidation 机会** / web search 的 "2025" 案例

**核心不变量 / 主线**：
**工具的每一个面（描述、参数、返回、错误）都是"给模型看的界面"。**
所以设计判据不是"API 长什么样"，是"**模型要分几步、中间产物占多少上下文**"——**能一步做完、中间结果不外露的工具，比功能更全的工具更好。**

**完整回答骨架**：先破"包装 API"（给 affordance 的差别）→ consolidation 三组例子 + 收益的两层 → 命名空间 → 响应设计（206 vs 72 + 判据）→ 错误响应要可行动 → 平方放大的成本算式 → 评测指标与"调次数暴露合并机会" → 收束到"工具是界面"

**追问**（先说后看）

1. **工具数量多了会怎样？** —— **三种代价**：① 每个工具的描述都占上下文（30 个 ≈ 6,000 token/请求，**每轮都付，且注意力层面没有折扣**）；② **重叠或含糊的工具让 agent 分不清该用哪个**；③ **选错的概率上升**。**手段**：consolidation + namespacing + **延迟加载**（`defer_loading`，把少用工具移出缓存前缀）。
2. **MCP 解决什么问题，边界在哪？** —— MCP 是**工具接入的标准化协议**（把"每个客户端各写一套集成"变成"一次实现、多处复用"）。**边界**：**MCP 只统一了"怎么暴露和调用"，没有统一"该不该暴露"**——**工具的职责划分、权限边界、返回设计仍然是你的事**（[[母题-A6-沙箱权限与可信执行]]）。
3. **工具描述该怎么写？** —— **清晰、具体、有边界**。但对**新一代模型**，**给示例反而可能限制探索空间**（[[母题-C3-Prompt版本管理与回归]]）——**更好的做法是设计接口本身**：把 `status` 做成 `pending / in_progress / completed` 的**枚举**，**光是列出来就在提示怎么用**。
4. **怎么知道该合并哪些工具？** —— **看"工具调用总次数"这个指标**：**经常被连着调用的工具组合，就是 consolidation 的候选**；**冗余调用多**说明分页/token 参数要调；**参数无效的错误多**说明描述不清或缺示例。

**同类变体**

- 「工具返回的结果要不要缓存？」——**要区分"确定性工具"和"有副作用的工具"**。只读且参数相同 → 可以缓存；**有副作用的工具缓存等于跳过执行**（[[母题-A3-失败恢复与幂等]]）。而且缓存要**按租户 / 权限分区**（[[母题-G6-知识更新与增量索引]]）。
- 「工具太多，全给模型 vs 按意图路由给一部分，怎么选？」——**按评测定**，但**先天的判据是"意图能否可靠地判断"**。数驭穹图的意图路由就是这个思路：**先判断意图（RAG / NL2SQL / 直接回答），再给对应的工具子集**。**路由错了后面全错，所以路由本身的准确率要单独评测。**
