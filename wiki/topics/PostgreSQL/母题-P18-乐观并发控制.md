# 母题 P18 · 乐观并发控制

> **模块**：PostgreSQL / 业务并发场景
> **所属主线**：七 · 业务并发场景（抢库存、冲排行榜怎么不出错）
> **层级**：B · 标准级（期望尝试次数与串行化上限能算；但「用乐观还是悲观」是取舍题，取决于冲突频率，不是推导题）
> **关联母题**：[[母题-P10-无间隙锁与锁变体]]（为什么不用 FOR UPDATE）· [[母题-P19-唯一约束与UPSERT]]（乐观的最终防线）· [[母题-P8-隔离级别与读一致性]]（RC 下 UPDATE 为什么可能改错）· [[母题-P9-序列化失败与重试]]（重试的期望次数是同一个公式）· [[母题-M16-乐观锁与悲观锁]]（MySQL 侧对照）
> **素材来源**：**RuleArena 真实设计**（`projects/RuleArena/02-rulespec-runtime-harness.md` §5 的 `UPDATE attack_run ... WHERE status = :expected`、`04-idempotency-and-recovery.md` §12 的退款条件更新与 §15 的取舍原话）+ `study/09-数据缓存队列与一致性` 第 2 节 + **PostgreSQL 官方文档 UPDATE / Explicit Locking**（2026-09-13 联网核实）。**三组算式为本次新增（待你核对）**

**导读**：必懂 3 件事（① 「先查再写」**必然**有竞态——两个请求都读到合法状态，所以都认为自己有资格改 ② 条件更新把「判断」和「写入」压进**一条原子语句**，**影响行数 0 是一个正常业务分支，不是错误** ③ **`FOR UPDATE` 把临界区串行化了**——它的吞吐上限 = 1 ÷ 持锁时长，这是一个可以算出来的硬天花板）· 读完约 12 分钟 · 需要先懂：[[母题-P10-无间隙锁与锁变体]]

**题目**：两个 Worker 同时认领同一个任务。用 `SELECT ... FOR UPDATE` 锁住再改，有什么问题？不用锁怎么写？

**母题**：乐观并发控制在 PG 里怎么写？条件更新和 `FOR UPDATE` 怎么选？

**为什么重要**：这是**「业务并发」这条线上最直接能落到代码的一题**——**它不是"选个模式"，而是"你的判据和写入必须在同一个原子操作里"。** 而且它承接 [[母题-P10-无间隙锁与锁变体]]：**PG 没有间隙锁，所以"锁住一个范围"根本做不到——这直接决定了有些场景只能用条件更新或约束。**

**一句话结论**：**「先查再写」必然有竞态**（两个请求都读到合法状态），唯一解法是让**判断和写入不可分割**。**条件更新**就是把判断条件搬进 `WHERE`——**影响 1 行 = 成功，影响 0 行 = 别人先改了**，**0 行是一个正常业务分支，不是异常**。它相对 `FOR UPDATE` 的好处是三条：**冲突时不排队（立即返回 0 行）、基本无死锁、天然幂等（重复执行第二次影响 0 行）**。**判据是冲突频率**：**冲突低 → 条件更新；冲突高到重试成本超过加锁成本 → 才用悲观锁。**

**恢复关键词**：先查再写有竞态 / **判断与写入压进一条语句** / **影响行数 0 是正常分支** / `RETURNING` 省一次往返 / 版本号还是状态 / **乐观天然幂等** / **`FOR UPDATE` 的吞吐上限 = 1 ÷ 持锁时长** / 冲突高才用悲观

**核心不变量 / 主线**：
**并发正确性的单位是「一次原子操作」，不是「一段代码」。**
**任何跨越语句边界的「读—判断—写」，在多进程/多副本下都有窗口**——**条件更新的全部价值，就是把这三步压进一条语句。**

**完整回答骨架**：为什么「先查再写」必然有竞态 → 三条出路 → **条件更新的完整形态（含影响行数的语义）** → **为什么不用 `FOR UPDATE`（算吞吐上限）** → 它覆盖不了什么 → 落到项目

## 一、教材

### 1. 先讲清楚「先查再写」为什么必然有竞态

::figure pg-optimistic-update.svg | 条件更新：把判断与写入压进一条原子语句 | 先查再写的竞态窗口、条件更新的完整形态与影响行数语义、与 FOR UPDATE 的吞吐对比、它覆盖不了的三类场景

```
Worker A: SELECT ... WHERE id=1 AND status='READY'   → 查到
Worker B: SELECT ... WHERE id=1 AND status='READY'   → 也查到
Worker A: UPDATE ... SET status='SEARCHING' WHERE id=1  → 成功
Worker B: UPDATE ... SET status='SEARCHING' WHERE id=1  → 也成功 ← 重复认领
```

**两个请求都"读到了合法状态"，所以都认为自己有资格改。**

【事实】**为什么这在 PG 默认级别下完全可能**（[[母题-P8-隔离级别与读一致性]]）：**RC 下两条语句各自取快照，中间没有任何东西阻止另一个事务提交。**

【事实】**而且更微妙的是**：**即使两条 `UPDATE` 真的撞上了，RC 下的行为也不是报错**——**官方说：第二个更新者会等第一个提交，然后【对更新后的版本施加自己的操作】，并且【把 `WHERE` 条件重新求值】。** **所以 `WHERE id=1` 会匹配，操作照样生效**——**这就是"重复认领"发生的完整路径。**

**唯一能救的办法是让「判断」和「写入」不可分割。** 三条路：

1. **加锁**（`SELECT ... FOR UPDATE`）——把中间窗口锁住；
2. **数据库约束**（唯一约束）——让重复的那次直接失败（[[母题-P19-唯一约束与UPSERT]]）；
3. **条件更新**——把判断条件搬进 `WHERE`，让数据库在一次原子操作里同时判断和写入。

**第 3 条就是本题答案**，也是 PG 项目里最常用的那条。

### 2. 条件更新的完整形态

```sql
-- ① RuleArena 认领 Run：项目文档 02 §5 给的就是这个形状（表叫 attack_run）
UPDATE attack_run
SET status = 'SEARCHING',
    worker_id  = :worker_id,
    started_at = now()
WHERE id = :run_id
  AND status = 'READY'          -- 只有还是 READY 才抢得到
RETURNING id, status;

-- ② 改「聚合」时再加版本号——防的是「基于旧值做的判断」
--    （项目文档 04 §12 的退款例子：版本 + 业务不变量一起进 WHERE）
UPDATE orders
SET refunded_amount = refunded_amount + :amount,
    version         = version + 1
WHERE id = :id
  AND version = :expected_version
  AND refunded_amount + :amount <= paid_amount;
```

【推论】**两段的差别在于「要不要防旧值」**：

```text
认领 Run：判断依据是【状态本身】，状态变了条件自然不成立
          → 状态这一个条件就够
改聚合  ：判断依据是【读到的那个旧值】（剩余可退 = 已付 − 已退）
          → 必须把版本号也进 WHERE，否则"读到 100、要退 80"这个前提会失效
```

**三个要点：**

**① 判断依据可以是「状态」也可以是「版本号」，看你在防什么**：

```text
状态：管业务语义（必须是 READY 才能认领）
版本：管并发冲突（即便状态刚好又变回 READY，版本也不会重复）
```

【推论】**为什么「状态」单独不够——当状态会回流时**：**如果一行能从 `READY → SEARCHING → READY`（比如失败后重置），那么"状态是 READY"这个判断对两次不同的认领都成立**——**版本号能区分"这一轮的 READY"和"上一轮的 READY"。**

**② `RETURNING` 让这件事变成一次往返**：认领成功时直接拿到更新后的行，不用再去 `SELECT` 一次。**减少一次往返对连接占用和延迟都有意义**（[[母题-P17-连接模型与连接池]]）。

**③ 用「影响行数」判断结果，不要用异常**：

| 影响行数 | 含义 | 处理 |
|---|---|---|
| **1** | 认领成功 | 继续执行 |
| **0** | 别人先改了 / 状态不匹配 / 版本不匹配 | **先读出权威状态再决定**（继续跳过、或重试、或报冲突） |

【推论】**「影响行数 0 不是错误」这个认知很关键**——**它是一个正常的业务分支**，不需要抛异常、不需要重试循环。

【事实】**为什么 0 行有多个可能的原因，直接影响处理方式**：

```text
0 行可能是：
  ① id 不存在            → 业务上应该报"任务不存在"
  ② status 不是 READY   → 【正常分支】，跳过就行
  ③ version 不匹配       → 【并发冲突】，可以重试

→ 这三者的区别只能靠【再读一次权威状态】来分辨
→ 所以正确做法是：影响 0 行 → SELECT 读权威状态 → 按状态决定
```

【推论】**这也是 [[母题-P10-无间隙锁与锁变体]] 里那条原则的又一次出现**：**「用一次权威读取替代对原因的猜测」。** **不要去猜"0 行是为啥"，去读。**

**到这里你应该能回答**：为什么「更新影响 0 行」这件事，不能简单地当成"失败"？

### 3. 为什么不用 `FOR UPDATE`

`FOR UPDATE` 是可行的（而且更"直观"），但在这个场景下有三处不划算：

| 维度 | `FOR UPDATE` | 条件更新 |
|---|---|---|
| 冲突时行为 | **排队等待**（可能超时/死锁） | **立即返回 0 行**（无等待） |
| 死锁风险 | 有（多行多路径加锁顺序不一致） | **基本没有**（无长持锁） |
| 幂等性 | 需要自己保证 | **天然幂等**（重复执行第二次影响 0 行） |
| 连接占用 | **事务持续到业务处理完** | **一条语句就结束** |

【推导】**把「排队等待」的代价算出来——这是 `FOR UPDATE` 的硬天花板**：

```text
FOR UPDATE 把临界区【串行化】了：
  同一行上的并发操作，同一时刻只有一个能进行

吞吐上限 = 1 ÷ 持锁时长

如果持锁 20 ms（比如要在锁里做业务处理）：
  → 这一行的吞吐上限 = 1 ÷ 0.02 s = 【50 TPS】
  → 加再多并发也没用，多出来的都在排队

而条件更新：
  每次尝试 2 ms，冲突率 p = 5%
  → 期望耗时 = 2 ms ÷ 0.95 ≈ 2.1 ms
  → 【不排队】，只是偶尔多跑一次
```

【结论】**`FOR UPDATE` 的吞吐上限是「1 ÷ 持锁时长」，与并发数无关；条件更新的成本是「期望尝试次数」，与冲突率相关。**

【推论】**这就是判据的量化版本**：

> **冲突低 → 条件更新（期望尝试 ≈ 1 次，几乎无额外成本）**
> **冲突高 → 条件更新的期望尝试次数会上去（1/(1−p)，见 Q1）**，**但即使 p = 50% 也才 2 次尝试**——**而 `FOR UPDATE` 在同样的冲突下会变成一条队列。**

【结论】**所以真正让 `FOR UPDATE` 变得必要的不是"冲突高"，而是「临界区里有不可重试的东西」**——**比如跨行不变量（[[母题-P9-序列化失败与重试]]）、或者临界区里有外部副作用。**

【补充】**再加上 PG 的一个特殊性**（[[母题-P10-无间隙锁与锁变体]]）：**PG 没有间隙锁**，所以「锁住一个范围以防别人插入」这件事本身做不到——**即使你用了 `FOR UPDATE`，它也只保护「已存在的行」。** **在任务认领这种场景里，要保护的是"这一行的状态"，条件更新正好够用；而在需要跨行不变量的场景里，`FOR UPDATE` 也未必够——那要用约束或 SSI。**

### 4. 它覆盖不了什么（必须主动说出边界）

| 场景 | 为什么条件更新不行 | 该用什么 |
|---|---|---|
| **跨行不变量**（比如「租户至少一个管理员」） | **一条 `UPDATE` 只能守一行**——**多行之间的约束它表达不了** | **SSI**（[[母题-P9-序列化失败与重试]]）或**把不变量收敛到一行上** |
| **必须跨多步操作**（读外部数据 → 判断 → 写） | **判断依据来自数据库之外，没法搬进 `WHERE`** | 悲观锁 / SSI / 把判断依据也落到数据库 |
| **插入语义**（"不存在才插入"） | **条件是"不存在"，`UPDATE` 天然表达不了** | **唯一约束 + `ON CONFLICT`**（[[母题-P19-唯一约束与UPSERT]]） |
| **临界区里有不可重试的副作用** | 条件更新天然鼓励重试，但副作用重试会重复 | **必须先把副作用做成幂等的**（P19） |

【推论】**第四行是这条主线反复出现的那个前提**：**「能不能重试」取决于「副作用可不可幂等」**——**所以「用不用乐观并发」最终是一个幂等设计问题**（和 [[母题-P9-序列化失败与重试]] 的结论是同一句）。

### 5. 落到项目：RuleArena 的认领与扣退款

【事实】**项目里的真实形态**（表格与状态名以项目正本为准）：

```text
认领 Run（表 attack_run；状态机 DRAFT→NEEDS_CONFIRMATION→READY→SEARCHING→REPLAYING→COMPLETED）
  UPDATE attack_run SET status='SEARCHING', worker_id=:w, started_at=now()
  WHERE id = :run_id AND status = 'READY'          ← 项目文档 02 §5 的原示例
  → 影响 1 行 = 我抢到了；影响 0 行 = 别人抢到了

扣退款 / 记账（改的是聚合，要防"基于旧值做的判断"）
  幂等键走唯一约束（UNIQUE(run_id, action_type, idempotency_key)）
  业务不变量进 WHERE（refunded_amount + :amount <= paid_amount），还要带 version
  → 应用层的条件判断只是【优化】，正确性由约束 + 事务保证
```

【推论】**两段的配合关系要说清**：

> **条件更新管「同一行的状态转移」**——**它保证「READY → SEARCHING 只发生一次」。**
> **唯一约束管「同一笔业务动作只落一次账」**——**它保证「重复投递不产生第二次副作用」。**
> **前者是「并发控制」，后者是「幂等防线」——两个问题，两个机制。**

【取舍】**项目为什么优先条件更新而不是加锁**——**项目文档给的理由是「权威性」不是「频率」**：

```text
项目文档 15 节原话：MVP 优先业务唯一键 + 条件更新
项目文档 Q7 原话：锁可以降低竞争，但不能成为资金正确性的唯一保证。
                 数据库事务、条件更新和唯一约束更接近权威状态；
                 只有真实高竞争时再评估锁。
```

【事实】**而且项目文档明确划了边界，不能把设计说满**——**04 §12 结尾原话**：

> **「MVP 当前主要覆盖重复和顺序动作；真正并发需要后续加入 barrier 和并发测试，不能把设计说明成已完整实现。」**

【取舍】**同时要知道文档给的是一个「或」**：**04 §12 的退款保守方案写的是「在事务中锁定订单行，**或**使用乐观版本条件更新」**——**所以"我项目里完全不用锁"是**说满了**；准确的说法是「优先条件更新，锁留到真实高竞争时再评估」。**

### 6. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「先查再写，查到了就改，没问题」 | **必然有竞态**——**两个请求都读到合法状态，都会认为自己有资格改** |
| 「影响 0 行说明出错了」 | **它是正常业务分支**——**而且有多个可能原因，要靠权威读取分辨，不能猜** |
| 「条件更新失败要重试」 | **多数情况下不该无条件重试**——**要先读出权威状态，判断是"正常跳过"还是"并发冲突"** |
| 「`FOR UPDATE` 更直观，用它更保险」 | **它把临界区串行化**——**吞吐上限 = 1 ÷ 持锁时长，与并发数无关** |
| 「有了乐观锁就不需要唯一约束了」 | **它守的是「行的状态转移」**，**守不住「不存在才插入」**——**那是唯一约束的活** |
| 「版本号可有可无，看状态就行」 | **状态能从 A→B→A 时，两次不同的操作都能通过状态判断**——**版本号才能区分轮次** |

## 二、自测

**Q1（计算）**：某认领接口，两个 Worker 撞上同一行的概率是 **20%**。条件更新单次尝试耗时 **2 ms**。

问：**期望要尝试几次？期望耗时多少？把冲突率提到 80% 呢？**

**A1**：

```text
每次尝试失败的概率 = p，成功概率 = 1 − p
期望尝试次数 = 1 ÷ (1 − p)     ← 与 P8 的 40001 重试是同一个公式

p = 20% → 1 ÷ 0.8 = 【1.25 次】
  期望耗时 = 2 ms × 1.25 = 【2.5 ms】

p = 80% → 1 ÷ 0.2 = 【5 次】
  期望耗时 = 2 ms × 5 = 【10 ms】
```

【结论】**即使冲突率高达 80%，条件更新的期望耗时也只有 10 ms**——**它没有排队，只是偶尔多跑几次。**

【推论】**所以"冲突高就该用悲观锁"这个说法需要修正**：

> **真正的判据是「重试的期望成本」vs「排队的等待成本」**，
> **而重试的期望成本是【线性的、有上界的】（1/(1−p)），排队是【无上界的】（队列可以无限长）。**

【补充】**但有一个例外让悲观锁重新变得必要**：**如果每次尝试之间还有别的代价**（比如重试会重新读外部数据、重新调接口），**那么 5 次尝试的成本就不只是 10 ms 了**——**这时要先把那些代价挪出临界区。**

**Q2（计算）**：同一行上，`FOR UPDATE` 被持有 **20 ms**（因为在锁里做了业务处理）。

问：**这一行的吞吐上限是多少？加并发能突破吗？为什么？**

**A2**：

```text
FOR UPDATE 把临界区【串行化】了：
  同一行上，同一时刻只有一个事务能持有锁

吞吐上限 = 1 ÷ 持锁时长 = 1 ÷ 0.02 s = 【50 TPS】

加并发能突破吗？【不能】
  并发只是让更多事务【排在队列里】
  → 吞吐不变，等待时间变长
  → 而且 PG 默认【无限期等锁】（P10）→ 队列会一直长
```

【结论】**`FOR UPDATE` 的吞吐是「1 ÷ 持锁时长」，与并发数无关。**

【推论】**这条给出了一个非常明确的优化方向**：

```text
要让这一行更快，只有两条路：
  ① 缩短持锁时长（把业务处理挪出临界区）
  ② 【不锁】，改用条件更新

而 ① 往往要求 ②：
  因为"在锁里做业务处理"通常意味着"读了才知道要写什么"，
  而这正是条件更新要解决的问题
```

【取舍】**所以「把外部调用移出事务」这条建议，在并发场景里还有第二层意义**：**它不只是缩短事务（P14），也是把 `FOR UPDATE` 的持锁时长压下来**——**两个收益是同一件事。**

**Q3（判读 + 计算）**：下面这段代码，问题在哪？

```sql
-- 认领接口
SELECT * FROM attack_run WHERE id = 1 AND status = 'READY';
-- （应用判断：查到了，可以认领）
UPDATE attack_run SET status = 'SEARCHING', worker_id = 'W1' WHERE id = 1;
-- （应用判断：影响 1 行，成功）
```

问：**两个 Worker 并发跑这段代码会怎样？改成条件更新后，影响行数的语义是什么？**

**A3**：

```text
并发跑会发生什么：
  A: SELECT → 查到（READY）
  B: SELECT → 也查到（READY）
  A: UPDATE WHERE id=1 → 影响 1 行 → 认为成功
  B: UPDATE WHERE id=1 → 影响 1 行 → 【也认为成功】
  → 两个 Worker 都在跑同一个任务

为什么 B 也能"成功"：
  UPDATE 的 WHERE 只有 id=1，【没有任何状态判断】
  → RC 下它会对更新后的版本施加操作（官方口径）
  → 照样影响 1 行
```

【改成条件更新】：

```sql
UPDATE attack_run
SET status = 'SEARCHING', worker_id = :w, version = version + 1
WHERE id = 1 AND status = 'READY'
RETURNING id, status, version;

影响行数语义：
  1 行 → 【我抢到了】（并且 RETURNING 直接拿到新状态，不用再查）
  0 行 → 【别人抢到了，或状态已变】
       → 再读一次权威状态，决定是跳过还是报"任务不存在"
```

【结论】**原代码的问题不是"没加锁"，是【判断和写入不在同一个原子操作里】。** **加锁能解决，但条件更新更轻——而且它天然幂等。**

【推论】**这个改法的收益，恰好是第 3 节那张表的四行**：**不排队、不死锁、天然幂等、一条语句就结束事务。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们用乐观锁，每次更新失败就重试三次，三次都失败就报错。"

**A4**：三处问题。

1. **「失败」这个词用错了**：**影响 0 行有三种可能**——**id 不存在（业务错误）、状态不匹配（正常分支）、版本不匹配（并发冲突）**。**把它们都当成"失败并重试"是错的**：**前两种重试一万次也还是 0 行。**
2. **正确动作是「先读权威状态再决定」**：**0 行之后应该 `SELECT` 一次看当前是什么状态**——**该跳过就跳过，该报"不存在"就报，只有确认是并发冲突才重试。**
3. **「重试三次」是一个没算过的数**：**期望尝试次数是 1/(1−p)**（Q1）——**p = 20% 时 1.25 次就够，p 很高时三次也不够。** **次数应该从冲突率的量级推出来，而不是拍一个。**

【准确说法】"**0 行不是失败，是一个需要【读一次权威状态】才能解释的信号。** **而重试只针对其中一种原因（并发冲突），次数上界按冲突率定。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们把乐观锁加上了，所以不会有重复执行的问题了。"

**A5**：三处问题。

1. **它守的是「行的状态转移」，不是「业务动作只发生一次」**：**条件更新能保证「READY → SEARCHING 只发生一次」，但保证不了「这笔退款只退一次」**——**那是**幂等键 + 唯一约束**的活**（[[母题-P19-唯一约束与UPSERT]]）。
2. **它覆盖不了「不存在才插入」**：**条件是"不存在"，`UPDATE` 天然表达不了**——**两笔并发的"首次插入"都会成功。**
3. **它覆盖不了跨行不变量**（第 4 节）：**一条 `UPDATE` 只守一行。**

【准确说法】"**并发控制管「谁先谁后」，幂等管「做没做过」——两件事。** **项目的正确姿势是两层：条件更新守状态转移，唯一约束守幂等。** **只有其中一层，另一边一定会漏。**"

## 三、面试输出（学完再看）

**一句话结论**：**「先查再写」必然有竞态**——**两个请求都读到合法状态，所以都认为自己有资格改**。**而在 PG 的默认级别下，两条 `UPDATE` 真的撞上时官方行为也不是报错**：**第二个更新者会等第一个提交，然后对更新后的版本施加操作，并重新求值 `WHERE`**——**所以重复执行照样成功。** **解法是让判断和写入不可分割，条件更新就是把判断条件搬进 `WHERE`**：**影响 1 行 = 成功，影响 0 行 = 别人先改了**。**关键认知是「0 行不是错误，是一个正常业务分支」**——**而且它有多个可能原因（id 不存在 / 状态不匹配 / 版本不匹配），要靠再读一次权威状态去分辨，不能猜。** **判断依据通常状态和版本一起用**：**状态管业务语义，版本管并发冲突**——**因为一行可能从 `READY → SEARCHING → READY`，光看状态区分不了轮次。** **为什么不用 `FOR UPDATE`，可以算出来**：**它把临界区串行化，吞吐上限 = 1 ÷ 持锁时长**——**持锁 20 ms 就是 50 TPS，加并发也突破不了，只会让队列变长**（**而 PG 默认无限期等锁**）。**条件更新没有这个天花板**：**每次尝试 2 ms，p = 20% 时期望耗时 2.5 ms，p = 80% 时也才 10 ms**——**它不排队，只是偶尔多跑几次。** **但乐观锁有三件覆盖不了的事**：**跨行不变量**（要 SSI 或把不变量收敛到一行）、**「不存在才插入」**（要唯一约束 + `ON CONFLICT`）、**临界区里有不可重试的副作用**（要先把副作用做成幂等的）。**所以项目里的正确姿势是两层**：**条件更新守「行的状态转移」，唯一约束守「业务动作只落一次账」——前者是并发控制，后者是幂等防线。**

**恢复关键词**：先查再写有竞态 / **RC 下 UPDATE 会对新版本重新求值 `WHERE`** / **判断与写入压进一条语句** / **影响行数 0 是正常分支且有三种原因** / **先读权威状态，不要猜** / 状态 + 版本各管一半 / `RETURNING` 省一次往返 / **`FOR UPDATE` 的吞吐上限 = 1 ÷ 持锁时长** / 乐观天然幂等 / **乐观守状态转移、唯一约束守幂等** / 1/(1−p)

**核心不变量 / 主线**：
**并发正确性的单位是「一次原子操作」，不是「一段代码」。**
**任何跨越语句边界的「读—判断—写」，在多进程/多副本下都有窗口。**

**完整回答骨架**：竞态为什么必然（含 RC 下 UPDATE 的实际行为）→ 三条出路 → **条件更新的完整形态与 0 行的三种原因** → **为什么不用 FOR UPDATE（算 50 TPS 的天花板）** → **乐观覆盖不了的四类场景** → 项目的两层结构 → 收束到「原子操作」

**追问**（先说后看）

1. **冲突高的时候该不该换成悲观锁？** —— **先别急**：**条件更新的期望尝试是 1/(1−p)、有上界（p = 80% 也才 5 次）**；**而悲观锁的队列是无上界的**。**只有一种情况必须换**：**临界区里有不可重试的东西**（跨行不变量、外部副作用）——**那时要先把那些东西挪出去，再决定。**
2. **版本号怎么设计？** —— **单调递增的整数**（`version = version + 1`），**由数据库在同一条 `UPDATE` 里自增**——**不要在应用里算**。**而且要让版本号对所有会改这一行的路径都生效**——**漏一条路径，乐观锁就有个洞。**
3. **影响 0 行之后到底该怎么处理？** —— **读一次权威状态**，按状态分三类：**不存在 → 业务错误**；**状态不匹配 → 正常跳过**（比如任务已被别人做完，直接返回）；**版本不匹配 → 并发冲突**（可以重试，重试次数按冲突率定）。**「用一次权威读取替代对原因的猜测」是一条可以迁移到所有并发场景的原则**（[[母题-P10-无间隙锁与锁变体]]）。
4. **乐观并发下能不能批量更新？** —— **能，但要小心**：**一次 `UPDATE ... WHERE ...` 影响多行时，"影响行数"就不再是"我抢到了一行"那么简单**——**它变成了"我抢到了 N 行"。** **判断逻辑要按 N 处理**（比如抢批任务时 N > 0 就算抢到）。**而 `RETURNING` 在多行时会把每行都返回**——**这是批量认领的正确姿势。**
5. **这套和 MySQL 那边一样吗？** —— **核心思想一样（判断与写入合并），但有两处不同**：**① MySQL 的 `UPDATE` 撞上时会【等锁】而不是"对更新后的版本重新求值"**——**等待超时是 `innodb_lock_wait_timeout`**；**② PG 的 `UPDATE` 拿的是 `FOR NO KEY UPDATE`，改键列会升级成 `FOR UPDATE`**（[[母题-P10-无间隙锁与锁变体]]）——**这会影响"会不会阻塞子表插入"**（[[母题-M16-乐观锁与悲观锁]]）。

**同类变体**

- 「条件更新和 `ON CONFLICT DO UPDATE` 是一回事吗？」—— **不是**。**条件更新是 `UPDATE` 加条件**（守「已存在行的状态转移」）；**`ON CONFLICT DO UPDATE` 是 `INSERT` 加冲突处理**（守「不存在才插入 / 存在就更新」）。**两者都做到了"判断与写入原子化"，但保护的语义不同。** **需要"插入语义"时只能用后者**（[[母题-P19-唯一约束与UPSERT]]）。
- 「为什么不用一个 `SELECT ... FOR UPDATE` + `UPDATE` 的两步写法？」—— **因为它把两步变成了"在锁里做两步"**，**持锁时长翻倍**——**而吞吐上限是 1 ÷ 持锁时长**（Q2）。**如果能用一条语句表达，就不要用两条。**
