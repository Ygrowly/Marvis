# 母题 P18 · 乐观并发控制

> **模块**：PostgreSQL / 业务并发场景
> **所属主线**：七 · 业务并发场景（抢库存、冲排行榜怎么不出错）
> **关联母题**：[[母题-P19-唯一约束与UPSERT]] · [[母题-P10-无间隙锁与锁变体]] · [[母题-P8-隔离级别与读一致性]]
> **素材来源**：**RuleArena 真实设计**（`projects/RuleArena/04-idempotency-and-recovery.md` 的条件更新 SQL 与取舍理由）· `study/09` 第 2.3 节

**题目**：两个 Worker 同时认领同一个任务，怎么保证只有一个成功、而且不靠加锁？

**母题**：乐观并发控制在 PG 里怎么做？为什么你项目里选它而不选 `FOR UPDATE`？

**为什么重要**：这是**你的项目最硬的一段技术证据**，也是**主线七唯一的落点**——而且它和前面五条主线全都接上了：**无间隙锁（P10）让它成为必要、RC 下 `UPDATE` 会重新判定（P8）让它能安全工作、短事务（P17）让它省连接、唯一约束（P19）给它兜底。** **能把这条链讲通，说明你不是"知道一个技巧"，而是有一致的技术判断。**

**一句话结论**：**条件更新**——把「我期望的状态」写进 `WHERE`：

```sql
UPDATE tasks
SET status = 'RUNNING', version = version + 1
WHERE id = :id AND status = 'QUEUED' AND version = :expected_version;
```

**受影响行数为 0 → 说明别人先改了**，读出权威状态再决定重试还是放弃。**选它而不选 `FOR UPDATE` 的理由**：① 认领/扣减是**低频写、读多写少**，加锁只会引入锁等待与死锁风险；② **它是「一次原子写」，天然幂等**——重复执行第二次影响 0 行；③ 它把「判断」和「写入」合并进一条语句，**从根上消除了「先查再写」的竞态**。

**恢复关键词**：条件更新 / 期望状态进 WHERE / version 或状态机做期望 / **影响行数 0 = 冲突** / 与 `FOR UPDATE` 取舍 / 无锁可重试 / 跨行不变量要靠约束 / `RETURNING`

**核心不变量 / 主线**：
**乐观并发控制的正确性不来自「不加锁」，而来自「把判断和写入合并成一条语句」。** 只要判断和写入是两个步骤，中间就一定有窗口——**这不是概率问题，是结构问题。**

**完整回答骨架**：先讲「先查再写」为什么必然有竞态 → 条件更新怎么消除它 → 影响行数为 0 之后怎么办 → 为什么不用 `FOR UPDATE` → 它覆盖不了什么（跨行不变量 → 交给 P19）→ 冲突频繁时怎么办

## 原理分解

### 一、先讲清楚「先查再写」为什么必然有竞态

```
Worker A: SELECT ... WHERE id=1 AND status='QUEUED'   → 查到
Worker B: SELECT ... WHERE id=1 AND status='QUEUED'   → 也查到
Worker A: UPDATE ... SET status='RUNNING' WHERE id=1  → 成功
Worker B: UPDATE ... SET status='RUNNING' WHERE id=1  → 也成功 ← 重复认领
```

**两个请求都"读到了合法状态"，所以都认为自己有资格改。** 在 RC（PG 默认，P8）下这完全可能，因为**两条语句各自取快照，中间没有任何东西阻止另一个事务提交**。

**唯一能救的办法是让「判断」和「写入」不可分割。** 三条路：

1. **加锁**（`SELECT ... FOR UPDATE`）——把中间窗口锁住；
2. **数据库约束**（唯一约束）——让重复的那次直接失败（P19）；
3. **条件更新**——把判断条件搬进 `WHERE`，让数据库在一次原子操作里同时判断和写入。

**第 3 条就是本题答案**，也是 PG 项目里最常用的那条。

### 二、条件更新的完整形态

```sql
-- 认领任务：只有当前状态还是 QUEUED、且版本没变，才改成 RUNNING
UPDATE tasks
SET status = 'RUNNING',
    worker_id = :worker_id,
    started_at = now(),
    version = version + 1
WHERE id = :id
  AND status = 'QUEUED'
  AND version = :expected_version
RETURNING id, status, version;
```

三个要点：

**① 判断依据可以是「状态」也可以是「版本号」**，通常两个一起用：**状态管业务语义**（必须是 `QUEUED` 才能认领），**版本管并发冲突**（即便状态刚好又变回 `QUEUED`，版本也不会重复）。

**② `RETURNING` 让这件事变成一次往返**：认领成功时直接拿到更新后的行，不用再去 `SELECT` 一次。**减少一次往返对连接占用和延迟都有意义（P17）。**

**③ 用「影响行数」判断结果，不要用异常**：

| 影响行数 | 含义 | 处理 |
|---|---|---|
| **1** | 认领成功 | 继续执行 |
| **0** | 别人先改了 / 状态不匹配 / 版本不匹配 | **读出权威状态再决定**（继续跳过、或重试、或报冲突） |

**「影响行数 0 不是错误」这个认知很关键**——**它是一个正常的业务分支**，不需要抛异常、不需要重试循环。

### 三、为什么不用 `FOR UPDATE`

`FOR UPDATE` 是可行的（而且更"直观"），但在这个场景下有三处不划算：

| 维度 | `FOR UPDATE` | 条件更新 |
|---|---|---|
| 冲突时行为 | **排队等待**（可能超时/死锁） | **立即返回 0 行**（无等待） |
| 死锁风险 | 有（多行多路径加锁顺序不一致） | **基本没有**（无长持锁） |
| 幂等性 | 需要自己保证 | **天然幂等**（重复执行第二次影响 0 行） |
| 连接占用 | 事务持续到业务处理完 | **一条语句就结束** |

**再加上 PG 的一个特殊性（P10）**：**PG 没有间隙锁**，所以「锁住一个范围以防别人插入」这件事本身做不到——**也就是说，即使你用了 `FOR UPDATE`，它也只保护「已存在的行」，不会保护「还没出现的行」**。**在任务认领这种场景里，要保护的是"这一行的状态"，条件更新正好够用；而在需要跨行不变量的场景里，`FOR UPDATE` 也未必够——那要用约束或 SSI（P9）。**

**所以取舍判据是**：**冲突频率 × 锁等待成本 vs 重试成本。** 冲突低 → 条件更新（乐观）；冲突高到重试成本超过加锁成本 → 才用悲观锁。

### 四、它覆盖不了什么（必须主动说出边界）

条件更新保护的是**「同一行的状态转换」**。它**不能直接保护跨行不变量**，比如：

```
已退款金额 + 本次退款 <= 已付金额        ← 跨列，但可以在同一个 UPDATE 里带上条件
用户多得的优惠 == 平台多付的成本          ← 跨表/跨行，条件更新做不到
```

**处理方式分三层**：

1. **能在同一条 SQL 里表达的条件，就写进 `WHERE`**（RuleArena 的实际做法）：

```sql
UPDATE orders
SET refunded_amount = refunded_amount + :amount,
    version = version + 1
WHERE id = :id
  AND version = :expected_version
  AND refunded_amount + :amount <= paid_amount;
```

**这条 SQL 一次性守住了三件事**：版本没变（没被别人改过）、**金额上限没被突破**（超额时影响 0 行）、以及幂等（重复执行第二次失败）。**这是"把不变量压进原子操作"的典范。**

2. **跨行的重复性** → **唯一约束兜底**（P19）；
3. **真正需要的跨行可串行化** → **SSI（P9）** 或显式加锁 + 统一顺序（P10）。

**说清第 4 节这段，就把「乐观并发控制」从一个技巧升级成了一套有边界的方案。**

### 五、冲突频繁时怎么办

条件更新在**高冲突**下会表现为「大量 0 行」——**这不是错，但要处理**：

- **有界重试 + 退避 + 抖动**（和 P9 的重试要求一样，**但这里重试的是一条语句，不是整个事务**，成本低得多）；
- **限流 / 排队**：把并发收敛到可接受范围（比如按任务分区，不同分区不互相冲突）；
- **换模式**：如果某个热点行必然被高频争抢（计数器、库存），**考虑把它改成"队列串行化"**（单一写入者）或挪到内存侧（Redis 的原子操作）——**这是"改结构"而不是"调参数"。**

## 二、扩展：类似题与追问

**类似题**

1. 「乐观锁和悲观锁怎么选？」——**一条判据**：**冲突频率高到「重试成本 > 加锁成本」时用悲观锁，否则用乐观。** 其余都是这条的展开。（这也是 MySQL 那边 M14 的同一道题，**两边答案一致——说明这是通用原理，不是某个数据库的特性。**）
2. 「乐观锁一定要 version 字段吗？」——不一定：**状态机本身就能当"期望值"**（`WHERE status = 'QUEUED'`）；但如果有「状态可能回到原值」的路径（往复状态机），**就必须加 version 才能区分"没变过"和"变了又变回来"**（这就是 CAS 的 ABA 问题在数据库里的体现）。
3. 「CAS 在数据库里是什么？」——**就是条件更新**：`UPDATE ... WHERE version = :expected` 与 CPU 的 compare-and-swap 是同一个模式；**数据库版本多了「持久化 + 事务 + 可跨机器」三件事。**

**追问链**

- 追问一层：**「影响行数 0 之后，怎么区分"别人抢先了"和"条件本来就不满足"？」**——**分不出来，也不需要分**：正确的做法是**统一走「读权威状态 → 判定 → 决定」**这条路。**这也是 RuleArena 里「Receipt / Snapshot 权威查询」的位置**（`projects/RuleArena/04-idempotency-and-recovery.md` 的「超时后的恢复决策」）。**「用一次权威读取替代对原因的猜测」是一个可以迁移到所有并发场景的原则。**
- 追问二层：**「条件更新和 RR/Serializable 一起用会不会出问题？」**——会多出一种失败：**在 RR/Serializable 下，如果目标行被并发改过，你可能直接拿到 `40001`（P8/P9），而不是"0 行"。** 所以**应用要同时处理两种信号**：`0 行`（业务冲突）与 `40001`（快照冲突，可重试）。**很多项目的重试框架只处理一种，另一种就变成了线上偶发错误。** **能说出这一条，说明真的在 PG 上跑过并发。**
