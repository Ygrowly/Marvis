# 母题 P3 · 部分索引与表达式索引

> **模块**：PostgreSQL / 索引与表设计
> **所属主线**：一 · 索引与表设计（怎么让查询不用扫全表，表怎么建才不埋雷）
> **层级**：B · 标准级（体积与写入收益能算；谓词蕴含与 IMMUTABLE 是规则型的，所以不是 A）
> **关联母题**：[[母题-P1-索引类型选型]]（选哪种索引）· [[母题-P2-堆表与回表]]（索引拿到位置之后）· [[母题-P4-索引代价与在线建索引]]（索引的第三项代价就是 VACUUM 压力）· [[母题-P15-VACUUM与事务ID回卷]]（清理负担的底部原因）
> **素材来源**：`archive/study-courses/09-数据缓存队列与一致性` 第 3.3 节（Partial Index 与真实 SQL）+ **PostgreSQL 官方文档 Partial Indexes**（2026-09-12 联网核实）+ 通用知识。**三组算式为本次新增（待你核对）**

**导读**：必懂 3 件事（① 只用得上 1% 的行，就不该为 100% 的行付维护成本 ② 谓词必须能被**证明蕴含** ③ 它会**静默失效**）· 读完约 11 分钟 · 需要先懂：[[母题-P2-堆表与回表]]

**题目**：`attack_run` 表里 **99%** 的行都是终态（`COMPLETED` / `CANCELLED`），只有少量是活跃态（`READY` / `SEARCHING` / `REPLAYING`）——但调度器**每秒都在查这些活跃行**。给 `status` 建一个全表索引，浪费在哪？

**母题**：**部分索引与表达式索引各解决什么问题——它们省的那一大截，代价是什么？**

**为什么重要**：这是 **PG 相对 MySQL 的一个实打实的优势**，也是「索引设计」和「索引堆砌」的分界线。它同时回答了另外两个高频追问——「索引是不是越多越好」（不是，所以要把索引做小）和「函数为什么导致索引失效」（PG 有解）。**能主动提这一条，说明你真的是在 PG 上做过优化。**

## 一、教材

### 1. 前提：全表索引的浪费在哪

::figure pg-partial-index.svg | 部分索引：只给热子集建索引，体积与服务范围成正比 | 全表索引 vs 部分索引的对比、谓词匹配三条判据、静默失效的风险

【推导】**调度器只查活跃态，但全表索引包含所有行**，于是有**四种浪费**：

| 浪费维度 | 具体表现 |
|---|---|
| **体积** | **99% 的索引项永远不会被这条查询用到**，却一直占空间、占缓存 |
| **写入** | **每次「终态化」的更新都要维护这个索引项——而它永远不会被那条查询用到** |
| **VACUUM 负担** | 索引项越多，autovacuum 要清理的索引页越多（**这是 PG 特有的第三项**，[[母题-P4-索引代价与在线建索引]]） |
| **统计信息** | 选择性估算被大量无用值稀释 |

【推论】**这条可以收成一句判据**：

> **索引的价值 = 它服务的那部分查询的频率 × 被索引集合的大小。**

**部分索引直接砍掉第二个因子。**

**到这里你应该能回答**：为什么"给 status 建个索引"这个动作，在有明确热子集的表上是不经济的？

### 2. 部分索引：把索引做小【事实】

```sql
CREATE INDEX idx_runs_active
ON attack_run (updated_at)
WHERE status IN ('READY', 'SEARCHING', 'REPLAYING');
```

【推导】**效果能算**：

```text
99% 终态 / 1% 活跃

体积：索引只含活跃行 → 约为全表索引的 1/100
写入：终态化那一步【完全不碰这个索引】
      （假设 95% 的更新是「变成终态」→ 这部分写入的索引维护省掉）
VACUUM：要清理的索引页同步下降
```

【结论】**体积约降到 1/100，而写入与 VACUUM 负担同步下降。**

【事实】**这就是"调度器扫活跃任务"这类场景的标准做法**——用「状态 + 时间」的队列式捞取，**索引只覆盖队内元素**。

#### 2.1 唯一的关键规则：谓词必须匹配【事实】

| 查询 | 能否用上面的索引 |
|---|---|
| `WHERE status = 'SEARCHING'` | ✅ 能——`SEARCHING` **蕴含在** `IN (...)` 里 |
| `WHERE status IN ('READY','SEARCHING')` | ✅ 能 |
| `WHERE status = 'COMPLETED'` | ❌ 不能 |
| `WHERE updated_at > ?`（**不带 status**） | ❌ **不能——谓词缺失，PG 无法证明蕴含** |

【推导】**最后一行是最容易踩的**：

```text
"我明明有索引，为什么不走？"
→ 因为查询条件里没有那句 WHERE 谓词
→ PG 不敢用（用了会漏掉终态行）
→ 【这时只能改写查询条件，不能靠加索引解决】
```

【推论】**"证明蕴含"这个词可以背**：**PG 不会去推断"这个查询大概只关心活跃行"，它要的是一个能机械验证的包含关系。**

**到这里你应该能回答**：为什么"我有索引但没用上"这件事，在部分索引上比在普通索引上更常见？

### 3. 表达式索引：让函数也能走索引【事实】

```sql
CREATE UNIQUE INDEX idx_users_email_lower ON users (lower(email));
```

【推导】**问题是什么**：

```text
WHERE lower(email) = ?
  普通索引里存的是【原始值】，不是 lower() 之后的值
  → 索引完全用不上
```

【事实】**PG 的解法**：**把 `lower(email)` 的结果本身作为索引键**。

【推论】**于是"函数导致索引失效"这件事在 PG 里是可以修的**——**不是"必须避免写函数"，而是"要么避免，要么为它建表达式索引"。**

【事实】**两个硬约束**：

```text
① 函数必须是 IMMUTABLE（确定性）
   lower() 是；now() 不是（每次结果不同）
   → 【这是选型前必须查的一件事】

② 查询必须写【完全一样】的表达式
   lower(email) 的索引，upper(email) 或 email ILIKE ? 都用不上
   → 所以表达式索引某种程度上是「给某一条 SQL 定制的」
```

【推导】**为什么 `now()` 不能建表达式索引**：

```text
表达式索引的键是【求值那一刻的结果】
若表达式每次求值都不同
→ 索引里的条目在下一次查询时就对不上了
→ 【索引形同虚设，而且你不会有任何察觉】
```

【取舍】**所以"函数写在条件里索引失效"有两条路**：

```text
① 改写成 col >= ? AND col < ?（去掉函数）—— 不付额外代价
② 建表达式索引 —— 只在【改不动 SQL】时用
```

**到这里你应该能回答**：为什么"给 `lower(email)` 建索引"这件事，要先确认 `lower` 是不是 IMMUTABLE？

### 4. 两者组合：部分唯一索引（软删除的经典解）【事实】

【事实】

```sql
CREATE UNIQUE INDEX idx_users_email_active
ON users (lower(email))
WHERE deleted_at IS NULL;
```

【推导】**一条语句同时用了三样东西**：

```text
部分（WHERE deleted_at IS NULL）
+ 唯一（UNIQUE）
+ 表达式（lower(email)）

→ 只对「未删除」的行保证 `lower(email)` 唯一
→ 软删除后【允许同邮箱重新注册】
```

【推论】**这是最能体现"索引是为业务规则服务"的一个例子**——**业务说的是"未删除的邮箱唯一"，索引就应该只约束那部分行**。

**到这里你应该能回答**：为什么"邮箱唯一"这个需求，在有软删除的系统里不能直接建成普通唯一索引？

### 5. 最大的风险：静默失效【推导】

【推导】**部分索引的失效方式是静默的**：

```text
只要查询条件与谓词不再匹配
（比如以后加了「查终态任务」的需求）
→ 新查询就自动用不上、走全表扫
→ 【而你不会收到任何通知】
```

【推导】**这个代价能算**：

```text
一张 1000 万行的表（每页 16 行 → 62.5 万页）

走部分索引：3 次树查找 + 命中 100 行的回表
全表扫    ：62.5 万页顺序读

【差几个数量级】
```

【推论】**所以部分索引必须配一句"它的服务范围是什么"写在注释或文档里**——**这是它和普通索引最大的不同：普通索引失效通常是"条件不匹配"，你改改 SQL 就能用；部分索引失效可能是"需求变了"，而索引本身没错。**

【取舍】**这条在面试里很值钱**：**主动说出"部分索引最大的风险是静默失效"，比只说它省空间更像运维过的人。**

**到这里你应该能回答**：为什么"加个部分索引"这个动作，需要配一条注释？

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "索引当然是覆盖的行越多越好" | **反了**。**索引的价值 = 服务的那部分查询的频率 × 被索引集合的大小**——**只用得上 1% 的行，就不该为 100% 的行付维护成本**（体积约 1/100，且终态化那步完全不碰它） |
| "有索引就应该能用上" | **部分索引要求"查询条件能被证明蕴含在谓词里"**。**`WHERE updated_at > ?`（不带 status）用不上**——**因为谓词缺失，PG 不敢用（用了会漏掉终态行）**。**这时只能改写查询，不能靠加索引解决。** |
| "函数写在条件里索引必然失效" | **PG 有解：表达式索引**（把 `lower(email)` 的结果作为索引键）。**但有两个硬约束：函数必须 IMMUTABLE，且查询要写一模一样的表达式。** |
| "`now()` 也可以建表达式索引" | **不行**。**它每次求值都不同 → 索引条目下一次查询就对不上 → 索引形同虚设，而且你不会有任何察觉。** **选型前必须查函数是不是 IMMUTABLE。** |
| "部分索引加了就一劳永逸" | **它会【静默失效】**：**以后新增一条不匹配谓词的查询，就自动走全表扫，而你不会收到通知**。**必须把"服务范围"写进注释或文档。** |
| "索引多了只是写入慢一点" | **在 PG 里还有第三项代价：VACUUM 负担**——**每多一个索引，autovacuum 清理死元组就要多处理一棵索引树**。**所以"索引不是越多越好"在 PG 里的后半句是"索引越多，表膨胀越难被自动控制住"。** |
| "MySQL 也能这么干" | **MySQL 没有部分索引**。同需求要么靠前置过滤 + 组合索引（**索引里仍然包含终态行**），要么靠业务层改写。**"PG 用部分索引 + 表达式索引；MySQL 用 (status, updated_at) 联合索引靠最左列过滤，但索引仍含全量行"——这个对照要能说出来。** |

【取舍】读成一句话：**部分索引省的那一大截，代价是"它只为一部分查询服务"——所以用它就必须说清"这部分"是谁。**

## 二、自测

**Q1（计算）**：`attack_run` 表里 **99%** 是终态行、**1%** 是活跃行。调度器只查活跃行。

问：**全表索引与部分索引的体积比是多少？**在写入上，部分索引省掉了哪一部分？

**A1**：

```text
体积：部分索引只含活跃行
  ≈ 1% / 100% = 【1/100】

写入：
  终态化那一步【完全不碰这个索引】
  （假设 95% 的更新是"变成终态"）
  → 这部分更新的索引维护被完整省掉
```

【结论】**体积约降到 1/100，而写入与 VACUUM 负担同步下降。**

【推论】**判据**：

> **索引的价值 = 它服务的那部分查询的频率 × 被索引集合的大小。**

**部分索引直接砍掉第二个因子。**

【补充】**第三项收益（VACUUM）是 PG 特有的**：**每多一个索引，autovacuum 清理死元组就要多处理一棵索引树**——所以部分索引在 PG 里的价值比在"只有写放大"的模型下更大。

**Q2（判读）**：索引是：

```sql
CREATE INDEX idx_active ON attack_run (updated_at)
WHERE status IN ('READY','SEARCHING','REPLAYING');
```

下面三个查询，**哪些能用上这个索引？为什么？**

```sql
-- ①
SELECT * FROM attack_run WHERE status = 'SEARCHING';
-- ②
SELECT * FROM attack_run WHERE status = 'COMPLETED';
-- ③
SELECT * FROM attack_run WHERE updated_at > now() - interval '1 hour';
```

**A2**：

| | 能否用上 | 为什么 |
|---|---|---|
| **①** | ✅ | **`SEARCHING` 蕴含在 `IN (...)` 里**——能被机械验证 |
| **②** | ❌ | **`COMPLETED` 不在子集里** |
| **③** | ❌ | **谓词缺失——PG 无法证明蕴含**（用它就会漏掉终态行） |

【结论】**③ 是最容易踩的**："我明明有索引，为什么不走？"——**因为查询条件里没有那句 `WHERE` 谓词**。

【推论】**这时只能改写查询条件，不能靠加索引解决**。而且要注意：**改写成带 `status IN (...)` 的形式，语义必须真的等价**——如果业务上确实要查所有状态，那就该另建一个索引。

【补充】**"证明蕴含"这个说法可以背**：**PG 不去推断"这个查询大概只关心活跃行"，它要的是一个能机械验证的包含关系。**

**Q3（判读）**：下面两个建索引的尝试，**哪个能成功？为什么？**

```sql
-- A
CREATE INDEX idx_a ON users (lower(email));

-- B
CREATE INDEX idx_b ON users (now());
```

**A3**：**A 能，B 不能。**

```text
A（lower）：lower 是 IMMUTABLE（确定性）
  → 同一个输入永远得到同一个输出
  → 索引键是稳定的 → 索引有效

B（now）：now 不是 IMMUTABLE
  → 【每次求值都不同】
  → 索引里的条目在下一次查询时就对不上
  → 索引形同虚设，而且【你不会有任何察觉】
```

【结论】**表达式索引的第一个硬约束是"函数必须 IMMUTABLE"——这是选型前必须查的一件事。**

【第二个约束】**查询必须写完全一样的表达式**：

```text
lower(email) 的索引：
  ✓ WHERE lower(email) = ?
  ✗ WHERE upper(email) = ?
  ✗ WHERE email ILIKE ?
```

【推论】**所以表达式索引某种程度上是"给某一条 SQL 定制的"**——**这一点要在设计时就接受**。

**Q4（纠错）**：下面这段话哪里不准确？

> "我给 status 建了个索引，调度器查活跃任务的性能问题就解决了。"

**A4**：三处问题。

1. **全表索引为 100% 的行维护，而调度器只用 1%**（Q1）——**99% 的索引项永远不会被这条查询用到，却一直占空间、占缓存、拖慢写入**。
2. **更好的做法是部分索引**：`WHERE status IN ('READY','SEARCHING','REPLAYING')`——**体积约 1/100，而且终态化那一步完全不碰它**。
3. **而且"建了索引"不等于"用上了"**：**查询条件必须能被证明蕴含在谓词里**（Q2）——**最终要看 `EXPLAIN`**。

【准确说法】"**先用部分索引把索引做小**（只覆盖热子集），**再确认查询条件与谓词匹配**。**如果业务上确实要查所有状态，那才需要全量索引**——但那是一个不同的需求，不是"顺手建一个"。"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们加了部分索引，以后就不用管了。"

**A5**：三处问题。

1. **部分索引会【静默失效】**：**只要以后新增一条不匹配谓词的查询（比如"查今天完成的任务"），它就自动走全表扫，而你不会收到任何通知。**
2. **所以必须把"服务范围"写进注释或文档**——**这是它和普通索引最大的不同**：**普通索引用不上，通常是"SQL 没写好"；部分索引用不上，可能是"需求变了"，而索引本身没错。**
3. **代价也不小**（Q2 的量级对比）：**一张 1000 万行的表，全表扫 62.5 万页 vs 走索引 3 次树查找 + 100 次回表——差几个数量级**。

【准确说法】"**部分索引必须配一句"它服务哪些查询"**，而且要定期检查**新增查询有没有落在它的服务范围内**。**它不是"加完就忘"的索引，是需要维护文档的索引。**"

## 三、面试输出（学完再看）

**一句话结论**：**索引的价值 = 它服务的那部分查询的频率 × 被索引集合的大小**——**只用得上 1% 的行，就不该为 100% 的行付维护成本**。**部分索引只给满足谓词的行建索引**，体积与服务范围成正比（**本例约 1/100**），而且**终态化那一步完全不碰它**；它还有 PG 特有的第三项收益：**VACUUM 负担同步下降**。**唯一的关键规则是"谓词必须匹配（可证明蕴含）"**——`WHERE updated_at > ?`（不带 status）**用不上，因为谓词缺失，PG 不敢用（用了会漏终态行）**，**这时只能改写查询，不能靠加索引解决**。**表达式索引把计算结果作为索引键**，让 `lower(email)` 这类条件也能走索引——**两个硬约束是：函数必须 IMMUTABLE（`now()` 不行），且查询要写一模一样的表达式**。**两者组合就是部分唯一索引**（`UNIQUE (lower(email)) WHERE deleted_at IS NULL`），**这是软删除场景的经典解，也最能体现"索引是为业务规则服务"**。**最大的风险是静默失效**——**以后新增一条不匹配谓词的查询就自动走全表扫，而你不会收到通知**，所以**必须把服务范围写进注释**。

**恢复关键词**：**价值 = 频率 × 集合大小** / 全表索引的四项浪费（体积·写入·VACUUM·统计） / 部分索引体积 ≈ 1/100 / **谓词必须可证明蕴含** / 缺谓词 = 用不上（只能改写查询）/ **静默失效**是最大风险 → 服务范围要写注释 / 表达式索引：把结果作为键 / **两个约束：IMMUTABLE + 表达式一模一样** / `now()` 不行 / **部分唯一索引 = 软删除的经典解** / MySQL 没有部分索引（用 `(status, updated_at)` 但索引仍含全量行）

**核心不变量 / 主线**：
**索引的价值 = 它服务的那部分查询的频率 × 被索引集合的大小。**
**部分索引直接砍掉第二个因子**——但代价是**它只为一部分查询服务**，所以**用它就必须说清"这部分"是谁**。

**完整回答骨架**：全表索引浪费在哪（四项）→ **部分索引的机制与收益算式** → **谓词必须匹配（含"缺谓词"那一行）** → **表达式索引与两个硬约束** → **部分唯一索引（软删除）** → **静默失效的风险** → 收束到"索引是为业务规则服务"

**完整回答（口述稿）**：
**索引的价值 = 它服务的那部分查询的频率 × 被索引集合的大小**——**只用得上 1% 的行，就不该为 100% 的行付维护成本**。

**部分索引**只给满足谓词的行建索引：体积与服务范围成正比（**本例约 1/100**），终态化那一步完全不碰它；还有 PG 特有的第三项收益——**VACUUM 负担同步下降**。

**唯一的关键规则是"谓词必须匹配（可证明蕴含）"**：`WHERE updated_at > ?`（不带 status）用不上，因为谓词缺失时 PG 不敢用（用了会漏终态行）——**这时只能改写查询，不能靠加索引解决**。

**表达式索引**把计算结果作为索引键，让 `lower(email)` 这类条件也能走索引；代价是写入时要维护这个表达式的结果，且查询必须写成同样的表达式才能命中。

**分层要点**：
- **结论**：只给需要的那部分行建索引；谓词必须可证明蕴含，否则只能改查询。
- **推导链**：价值 = 频率 × 集合大小 → 部分索引 → 体积与 VACUUN 负担同步降 → 谓词蕴含规则 → 表达式索引。
- **量化**：本例部分索引体积约 1/100。
- **边界与常见误解**：谓词不匹配时加索引没用（PG 不敢用）；表达式索引要求查询写成同样的表达式。

**追问**（先说后看）

1. **PG 怎么做软删除的唯一约束？** —— **部分唯一索引**：`CREATE UNIQUE INDEX ... ON users (lower(email)) WHERE deleted_at IS NULL`。**删掉的行不参与唯一性，所以可以重新注册同一个邮箱。**
2. **`LIKE '%xx'` 能走索引吗？** —— **普通 B-tree 不行**（前缀无序）；**PG 的常规解法是 `pg_trgm` + GIN / GiST**。**答这题能顺手展示你知道"扩展"而不是只会内置类型。**
3. **函数写在条件里索引失效，怎么办？** —— **两条路**：**改写成 `col >= ? AND col < ?`（去掉函数）**，或**建表达式索引**。**前者不付额外代价，后者只在改不动 SQL 时用。**
4. **部分索引会不会失效？** —— **会，而且是静默的**：**查询条件与谓词不再匹配时，新查询自动用不上、走全表扫，而你收不到通知**。**所以必须把服务范围写进注释或文档——这是它最大的运维风险。**
5. **索引多了对 VACUUM 有什么影响？** —— **每多一个索引，autovacuum 清理死元组要多处理一棵索引树**，**代价从"写放大"延伸到"清理负担"**。**所以"索引不是越多越好"在 PG 里的后半句是："索引越多，表膨胀越难被自动控制住"**（[[母题-P15-VACUUM与事务ID回卷]]）。

**同类变体**

- 「PG 和 MySQL 在"把索引做小"上的能力差多少？」——**MySQL 只能靠组合索引的"最左列过滤"间接缩小有效范围，但索引里仍然包含全量行**；**PG 的部分索引是真正只存子集**。**这是两者在索引设计上的一个结构性差异**（[[母题-M2-联合索引与最左前缀]]）。
- 「表达式索引和生成列（generated column）该选哪个？」——**生成列是"把计算物化到行里"，表达式索引是"把计算物化到索引里"**。**前者能被更多查询用到（任何引用该列的查询），代价是每行多存一份；后者只服务匹配那个表达式的查询，但只占索引空间。**
