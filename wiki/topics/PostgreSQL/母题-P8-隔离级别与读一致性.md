# 母题 P8 · 隔离级别与读一致性

> **模块**：PostgreSQL / 事务与锁
> **所属主线**：三 · 事务与锁（并发改同一份数据，为什么不会乱）
> **关联母题**：[[母题-P9-序列化失败与重试]] · [[母题-P10-无间隙锁与锁变体]]
> **素材来源**：`study/09-数据缓存队列与一致性` 第 2.2 节（隔离级别）+ 通用知识（**RC 下 UPDATE 的重新检查细节待你核对**）

**题目**：同一个事务里，两条完全一样的 `SELECT` 返回了不同的行。这算 bug 吗？

**母题**：PG 默认是 RC 还是 RR？同一事务内两次查询为什么会看到不同结果？

**为什么重要**：这是**「PG 与 MySQL 最容易说错的七处」里的第一条**——**MySQL 默认 RR，PG 默认 RC**。而且它的反直觉程度最高：**「同一事务内读到不一样的结果」在 PG 的默认级别下不算 bug，是规范行为。** 如果这条说错，后面 MVCC、锁、膨胀全都跟着错。

**一句话结论**：PG 默认 **READ COMMITTED**。RC 下**每条语句开始时取一次快照**，所以同一事务里的两条 `SELECT` 之间如果有别的事务提交，你就会看到不同的结果——**这是规范允许的不可重复读**。要事务内一致就提到 **REPEATABLE READ**（PG 的 RR 是快照隔离，整个事务一个快照）；**但 PG 的 RR 遇到写冲突会直接报错让你重试**，它不靠间隙锁把冲突挡住（那是 MySQL 的做法，见 P10）。

**恢复关键词**：默认 RC / 每条语句一个快照 vs 每事务一个快照 / 快照隔离 SI / 写冲突要重试 / RC 下 UPDATE 会重新检查最新版本 / 快照基于事务开始时间

**核心不变量 / 主线**：
**隔离级别在 PG 里承诺的是「你能看到什么」，不是「你不会失败」。** 级别越高，看到的越一致，但**越可能被要求重试**——这是 PG 与 MySQL 的哲学差异：**PG 用「快照 + 报错重试」换掉了「加锁等待」。**

**完整回答骨架**：PG 默认 RC（对比 MySQL 的 RR）→ 快照粒度差异（语句 vs 事务）→ 所以「两次查询不同」是规范行为 → RR 的代价是写冲突要报错 → RC 下 UPDATE 的特殊行为 → 怎么选

## 原理分解

### 一、默认值：第一处必须说对的差异

| | MySQL（InnoDB） | PostgreSQL |
|---|---|---|
| 默认隔离级别 | **REPEATABLE READ** | **READ COMMITTED** |
| 幻读防护 | next-key lock（间隙锁） | **无间隙锁**，靠快照 / SSI |
| 写冲突表现 | **等待锁**（可能超时/死锁） | **报 `40001`，让应用重试** |

**为什么这个默认值差异重要**：MySQL 的 RR 让很多「本来会出现的读不一致」被默认挡住，所以从 MySQL 过来的人**习惯性地假设「事务内读是一致的」**；而 PG 默认不保证这一点。**面试里只要开口说「PG 默认也是 RR」，后面所有关于并发行为的判断都会被怀疑。**

### 二、快照粒度：理解一切的关键

| 级别 | 快照什么时候取 |
|---|---|
| **READ COMMITTED（默认）** | **每条语句开始时**各取一次 |
| **REPEATABLE READ（PG 的快照隔离）** | **事务开始时**取一次，整个事务都用它 |

**所以 RC 下**：

```
事务 A                                    事务 B
BEGIN
SELECT balance  → 100
                                          UPDATE ... COMMIT（改成 80）
SELECT balance  → 80     ← 同一事务，结果变了
```

**这不是 bug**——两条语句各自取了自己的快照，各自看到了当时已提交的最新数据。

**RR 下**这两条都会返回 100（整个事务用同一快照）——**这才叫「可重复读」。**

### 三、RC 下一个必须知道的细节：`UPDATE` 会看到「最新的那一行」

RC 下，当你 `UPDATE` 一行时，如果这一行在语句执行期间被别人改过，PG 的规则是：

**重新读取该行的最新已提交版本，重新判定 `WHERE` 条件是否仍成立**，成立才更新；不成立就跳过（受影响的可能比你以为的少）。

**为什么这条重要**：它解释了两件常见现象——

- **`UPDATE ... WHERE status = 'QUEUED'` 在 RC 下是「相对安全」的**：因为重新判定时会发现 `status` 已经不是 `QUEUED` 了，于是跳过。**这正好是 P18 条件更新能成立的基础。**
- 反面：**它也可能让你「以为改了一行、实际没改」**，所以必须**用影响行数判断结果**，不能假定一定成功。

### 四、RR 的代价：写冲突会报错

PG 的 REPEATABLE READ 是**快照隔离**。当两个事务基于同一个旧快照去改同一行时，第二个会拿到：

```
ERROR: could not serialize access due to concurrent update (SQLSTATE 40001)
```

**这不是故障，是设计**：**要么让你看到一致快照、要么明确告诉你没改成功，二者不能都要。** 所以 PG 的做法是「报错 + 应用重试」，而不是 MySQL 那样「加锁等待」。

**所以把级别提到 RR 的那一刻，你的应用就必须能重试事务**（见 P9）。

### 五、怎么选（面试收尾）

| 场景 | 选择 |
|---|---|
| 绝大多数业务读写 | **RC（默认）**——每条语句看最新已提交数据，最接近直觉，并发冲突最少 |
| 一条事务里需要多次读同一批数据保持一致（对账、汇总计算） | **RR**，并且**整套写路径要能处理 40001 重试** |
| 有跨行不变量、写偏斜风险 | **Serializable（SSI）**，同样要能重试（P9） |
| 只读报表 | RC 或 RR 都行，但**注意长事务对膨胀的影响**（P14） |

**一句判据**：**能接受「读到别人刚提交的数据」就用 RC；需要「整段计算基于同一时刻」就往上提，同时接受重试。**

## 二、扩展：类似题与追问

**类似题**

1. 「RC 下会不会有幻读？」——会（范围查询两次结果可能不同），**但 PG 不会因此加锁**；要挡住就提到 RR/Serializable 或显式加锁。
2. 「`BEGIN; INSERT ...; SELECT ...; COMMIT;` 里 `SELECT` 能看到自己没提交的改动吗？」——**能看到，事务能看到自己的改动**（这是所有隔离级别都成立的）。
3. 「只读事务也有快照吗？」——有，而且**PG 的只读事务在 RR 下同样持有快照**，因此**同样会阻塞 VACUUM、导致膨胀**——这是 P14 那个反直觉结论的来源。

**追问链**

- 追问一层：**「RC 下 `UPDATE` 重新检查的行为，会不会导致死锁？」**——会，而且这是 PG 里一种常见的死锁来源：**两个事务以不同顺序更新同一批行**。处理办法是所有写路径**统一加锁/更新顺序**（比如总是按主键升序），或者用条件更新把冲突变成「0 行受影响」而不是「互相等待」。
- 追问二层：**「怎么知道线上到底是哪个隔离级别在跑？」**——查 `SHOW default_transaction_isolation`（会话/默认值），**并且要注意应用可能自己设了**（连接池、ORM、`SET TRANSACTION ISOLATION LEVEL`）。**面试里的正确表述是「我先确认当前默认值和连接池是否覆盖」，而不是假定「PG 就是 X」。** 这一点和 P5 里那条「我项目默认 RC，所以你们库里的 RR 行为我要先确认」是同一个纪律。
