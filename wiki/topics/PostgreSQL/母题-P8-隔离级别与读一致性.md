# 母题 P8 · 隔离级别与读一致性

> **模块**：PostgreSQL / 事务与锁
> **所属主线**：三 · 事务与锁（并发改同一份数据，为什么不会乱）
> **层级**：A · 教材级（三种级别的行为都能从「快照什么时候取」推出来；40001 的处置与重试次数能算）
> **关联母题**：[[母题-P9-序列化失败与重试]]（40001 怎么处理）· [[母题-P10-无间隙锁与锁变体]]（PG 为什么不用间隙锁）· [[母题-P13-MVCC与可见性]]（快照的底层）· [[母题-P14-长事务与表膨胀]]（快照留得越久，回收越难）· [[母题-M8-隔离级别与ACID]]（MySQL 侧对照）
> **素材来源**：`study/09-数据缓存队列与一致性` + **PostgreSQL 官方文档 Transaction Isolation**（2026-09-13 联网核实）+ 三个项目真实用法。**三组算式与 RR 的 40001 那一段为本次新增（待你核对）**

**导读**：必懂 3 件事（① **PG 默认是 READ COMMITTED**，不是 MySQL 的 RR——这是最容易说错的一条 ② 级别在 PG 里承诺的是「你能看到什么」，不是「你不会失败」——**级别越高，越可能被要求重试** ③ PG 用「快照 + 报错重试」换掉了 MySQL 的「加锁等待」）· 读完约 12 分钟 · 需要先懂：[[母题-P13-MVCC与可见性]]

**题目**：同一个事务里执行两次 `SELECT`，结果不一样。这是 bug 吗？该把级别调高吗？

**母题**：PG 默认是 RC 还是 RR？同一事务内两次查询为什么会看到不同结果？

**为什么重要**：这是**「PG 与 MySQL 最容易说错的七处」里的第一条**——**MySQL 默认 RR，PG 默认 RC**。而且它的反直觉程度最高：**「同一事务内读到不一样的结果」在 PG 的默认级别下不算 bug，是规范行为。** 如果这条说错，后面 MVCC、锁、膨胀全都跟着错。

**一句话结论**：PG 默认 **READ COMMITTED**。RC 下**每条语句开始时取一次快照**，所以同一事务里的两条 `SELECT` 之间如果有别的事务提交，你就会看到不同的结果——**这是规范允许的不可重复读**。要事务内一致就提到 **REPEATABLE READ**（PG 的 RR 是快照隔离，整个事务一个快照，**而且连幻读也一并挡住了**）；**但 PG 的 RR 遇到写冲突会直接报 `40001` 让你重试**，它不靠间隙锁把冲突挡住（那是 MySQL 的做法，见 [[母题-P10-无间隙锁与锁变体]]）。

**恢复关键词**：默认 RC / 每条语句一个快照 vs 每事务一个快照 / **RR = 快照隔离且挡幻读** / **RR 写冲突报 40001** / Serializable = 不额外阻塞、只检测中止 / 快照留久 = 挡住 VACUUM / 必须准备重试

**核心不变量 / 主线**：
**隔离级别在 PG 里承诺的是「你能看到什么」，不是「你不会失败」。** 级别越高，看到的越一致，但**越可能被要求重试**——这是 PG 与 MySQL 的哲学差异：**PG 用「快照 + 报错重试」换掉了「加锁等待」。**
**推论：把级别调高不是「更安全」，而是把「静默的读不一致」换成了「显式的、可重试的失败」。** **这两者的成本差别，是这道题真正要算的东西。**

**完整回答骨架**：PG 默认 RC（对比 MySQL 的 RR）→ 快照粒度差异（语句 vs 事务）→ 所以「两次查询不同」是规范行为 → RR 的代价是写冲突要报 40001 → RC 下 UPDATE 的特殊行为 → Serializable 做了什么 → 快照的隐藏成本 → 怎么选

**完整回答（口述稿）**：
**PG 默认 READ COMMITTED**（注意：**MySQL 默认是 RR，这是最容易被抓住的方言错误**）。RC 下**每条语句开始时取一次快照**，所以同一事务里两条 `SELECT` 之间如果有别的事务提交，你会看到不同结果——**这是规范允许的不可重复读**。

要事务内一致就提到 **REPEATABLE READ**：**PG 的 RR 是快照隔离**（整个事务一个快照），**而且连幻读也一并挡住了**——这一点和 MySQL 的 RR 不同（MySQL 靠 MVCC 挡快照读的幻读、靠间隙锁挡当前读的幻读）。

**但 PG 的 RR 遇到写冲突会直接报 `40001` 让你重试**——它不靠间隙锁把冲突挡住（**PG 没有间隙锁**，见 P10）。所以两边的哲学差异要说清：**MySQL 是排队等锁，PG 在 RR 及以上是报错让你重试**。

**分层要点**：
- **结论**：PG 默认 RC（MySQL 默认 RR）；PG 的 RR 是快照隔离，连幻读一并挡住，冲突时报 40001。
- **推导链**：默认 RC → 每语句取快照 → 允许不可重复读 → 提到 RR 得快照隔离 → 冲突处理是报错重试而非排队。
- **量化**：错误码 SQLSTATE 40001（序列化失败）。
- **边界与常见误解**："MySQL 和 PG 默认级别一样"×；"PG 的 RR 靠间隙锁"×（PG 没有间隙锁）。

## 一、教材

### 1. 默认值：第一处必须说对的差异

::figure pg-isolation-and-retry.svg | 三种隔离级别的快照粒度与失败方式 | 快照在语句级还是事务级、四种标准级别在 PG 里的实际行为、RR 写冲突报四千零一、级别越高越可能被要求重试

| | MySQL（InnoDB） | PostgreSQL |
|---|---|---|
| 默认隔离级别 | **REPEATABLE READ** | **READ COMMITTED** |
| 幻读防护 | next-key lock（间隙锁） | **无间隙锁**，靠快照 / SSI |
| 写冲突表现 | **等待锁**（可能超时/死锁） | **报 `40001`，让应用重试** |
| RR 下的写冲突 | 等待 / 死锁 | **直接报错中止** |

**为什么这个默认值差异重要**：MySQL 的 RR 让很多「本来会出现的读不一致」被默认挡住，所以从 MySQL 过来的人**习惯性地假设「事务内读是一致的」**；而 PG 默认不保证这一点。**面试里只要开口说「PG 默认也是 RR」，后面所有关于并发行为的判断都会被怀疑。**

【事实】**PG 其实只实现了三种级别**——官方原话：

> **在 PostgreSQL 里你可以请求四种标准级别，但内部只实现了三种不同的隔离级别——PG 的 Read Uncommitted 模式的行为等同于 Read Committed。**
> （因为这是把标准级别映射到 PG 的 MVCC 架构上唯一合理的做法。）

**所以「PG 支持四种级别」这句话是错的**：**你写 `READ UNCOMMITTED` 也不会读到脏数据，它被静默升成了 RC。**

### 2. 快照粒度：理解一切的关键

| 级别 | 快照什么时候取 |
|---|---|
| **READ COMMITTED（默认）** | **每条语句开始时**各取一次 |
| **REPEATABLE READ（PG 的快照隔离）** | **事务里第一条非事务控制语句开始时**取一次，整个事务都用它 |
| **SERIALIZABLE** | 同上，**外加一层序列化异常检测** |

【事实】**官方对 RC 的措辞把三件事一次说清**：

> **一个 `SELECT`（不带 `FOR UPDATE/SHARE`）只看到【查询开始之前】已提交的数据**，它既看不到未提交的数据，也看不到**在本查询执行期间**被其他事务提交的改动。
> **而且要注意：即使在一个事务里，两条相继的 `SELECT` 也可能看到不同的数据**——只要在第一条开始之后、第二条开始之前有别的事务提交了改动。

**所以 RC 下**：

```
事务 A                                    事务 B
BEGIN
SELECT balance  → 100
                                          UPDATE ... COMMIT（改成 80）
SELECT balance  → 80     ← 同一事务，结果变了
```

**这不是 bug**——两条语句各自取了自己的快照，各自看到了当时已提交的最新数据。

**RR 下**这两条都会返回 100（整个事务用同一快照）——**这才叫「可重复读」。**

【事实】**PG 的 RR 比 SQL 标准更强**——官方原话：

> **这是一个比 SQL 标准对该级别的要求【更强】的保证**，它阻止了表 13.1 里描述的所有现象，**除了序列化异常**。**标准只描述每个级别必须提供的【最低】保护，所以更强的保证是被允许的。**

【推导】**强在哪，用官方那张表看最清楚**：

| 级别 | 脏读 | 不可重复读 | 幻读 | 序列化异常 |
|---|---|---|---|---|
| Read uncommitted | **标准允许，但 PG 里不会** | 可能 | 可能 | 可能 |
| Read committed | 不会 | **可能** | **可能** | 可能 |
| Repeatable read | 不会 | 不会 | **标准允许，但 PG 里不会** | 可能 |
| Serializable | 不会 | 不会 | 不会 | 不会 |

【结论】**PG 的 RR 是「快照隔离」——它挡住幻读靠的是「整事务一个快照」，不是靠锁。** **这就是为什么 PG 不需要间隙锁**（[[母题-P10-无间隙锁与锁变体]]）。

**到这里你应该能回答**：为什么「PG 的 RR 和 MySQL 的 RR 都叫 Repeatable Read，但机制完全不同」？

### 3. RR 的代价：写冲突直接报错【事实】

这是 PG 最反直觉、也最能体现「快照 + 报错重试」哲学的一段。**官方原文**：

> `UPDATE` / `DELETE` / `MERGE` / `SELECT FOR UPDATE` / `SELECT FOR SHARE` 和 `SELECT` 一样**只找【事务开始时刻】已提交的目标行**。但这样一行**可能已经被另一个并发事务改过或锁住了**。这时 RR 事务会等第一个更新者提交或回滚。
> **如果第一个更新者提交了（并且真的改过或删除了该行，而不只是加锁），那么 RR 事务会被回滚，报：**
> ```
> ERROR:  could not serialize access due to concurrent update
> ```
> **因为 RR 事务不能修改或锁住那些【在它开始之后】被其他事务改过的行。**
> **应用收到这条错误时，应该中止当前事务并从头重试整个事务。**

【推导】**两种级别的同一个场景，结果完全不一样**：

```text
场景：事务 A 在 RR 下 UPDATE 一行，这一行已被事务 B 改过并提交

【RR】
  → A 报 40001，整个事务作废
  → 应用必须从头重试
  → 但 A 看到的数据从头到尾是一致的

【RC】
  → 官方原话：A 会【忽略被删的行】，否则【对更新后的版本施加自己的操作】
  → 而且命令的 WHERE 条件会被【重新求值】，看新版本是否仍匹配
  → A 不报错，但 A 的视角【变了】
```

【推论】**这就是那道题的答案**：

> **PG 把「数据可能已经变了」这个事实，在 RC 下处理成「重新读最新的」，在 RR 下处理成「报错让你重来」。**
> **前者静默、不中断；后者显式、要重试。**

**没有哪个更"好"——RC 的代价是可能产生业务层面的不一致，RR 的代价是可能失败。** **选级别，本质上是在选「你想要哪种代价」。**

【事实】**那为什么 PostgreSQL 官方建议应用"必须准备重试"？** 因为官方对 RC 之外的级别有一句明确的提醒：

> **使用这个级别的应用【必须准备好因为序列化失败而重试事务】。**

【纠正常见误解】**这条同样适用于 RC**——**RC 下 `UPDATE` 冲突不报错，但它"重新读最新版本再改"这件事本身，就可能让业务逻辑的前提失效**（你基于旧值做的判断，被应用到了新值上）。**所以"RC 不会失败"是错觉：它只是把失败从【数据库报错】挪到了【业务结果不对】。**

**到这里你应该能回答**：为什么「把隔离级别调高」不是免费的——它把什么换成了什么？

### 4. Serializable：不额外阻塞，只检测并中止【事实】

**官方原文**：

> **这个级别的工作方式和 Repeatable Read 完全一样，【除了】它还会监控那些可能让并发执行的结果与任何串行顺序都不一致的条件。**
> **这种监控除了 RR 本来就有的阻塞之外，【不引入任何额外的阻塞】**——但监控本身有开销，而且**一旦检测到可能造成序列化异常的条件，就会触发一次序列化失败。**

【推导】**用官方那个例子把 SSI 在防什么讲清**：

```text
初始：class=1 有 (10, 20)，class=2 有 (100, 200)

事务 A（Serializable）：SELECT SUM(value) WHERE class=1  → 30
                      INSERT (class=2, 30)
事务 B（Serializable）：SELECT SUM(value) WHERE class=2  → 300
                      INSERT (class=1, 300)

两边都提交时：
  如果是 RR → 【两个都被允许提交】
  但没有任何串行顺序能产生这个结果：
    若 A 先执行，B 会算出 330
    若 B 先执行，A 会算出 330
  → Serializable 会让其中一个提交、另一个回滚并报：
     ERROR:  could not serialize access due to read/write dependencies among transactions
```

【结论】**SSI 防的是「单独看每个事务都没问题、但合起来没有任何串行顺序能解释」这件事**——**这叫写偏斜（write skew），RR 挡不住它。**

【推论】**判据**：

> **RR 保证「你看到的一致」，Serializable 保证「结果能解释成某种串行顺序」。** **后者更强，但失败率也更高**——**因为它检测的范围更大。**

【事实】**一个很实用的特例**：**可延迟的只读事务**（`SERIALIZABLE READ ONLY DEFERRABLE`）**读到的数据在读到的那一刻就是有效的**——因为它会**等到能拿到一个保证没有这类问题的快照之后才开始读**。**做长报表、一致性快照导出时，这是最干净的做法。**

### 5. 一个连带的坑：序列不是事务性的【事实】

**官方专门用一段 "Important" 提醒**：

> **有些 PostgreSQL 数据类型和函数在事务行为上有特殊规则。特别是：对序列的改动（因此也包括 `serial` 声明列的那个计数器）【对其他所有事务立即可见】，而且【即使改动它的事务中止了也不会回滚】。**

【推论】**这是「自增主键为什么一定有洞」的第二个原因**（第一个是「分配出去就算用过」）——**它是事务可见性模型的一个明确例外**。**在 RR 事务里，你可能看不到别人刚提交的行，但你一定能看到自增值已经跳过去了。** **面试里能主动说出这条，说明你读的是文档而不是二手总结。**

**到这里你应该能回答**：为什么「事务里回滚了，自增值也该回退」这个期待是错的？

### 6. 快照的隐藏成本：它挡住了 VACUUM

【推导】**隔离级别选得越高，持有的快照越旧、越久——而旧快照是 VACUUM 的天敌**：

```text
一张表写 500 TPS
一个 RR / Serializable 事务跑了 10 分钟

这个事务的快照固定在开始那一刻
  → 它【之后产生的所有死元组都不能被回收】
  → 10 × 60 × 500 = 【30 万个死元组被压住】

后果：表膨胀、索引膨胀、查询越来越慢
（这正是主线五的主题，见 P14 / P15）
```

【结论】**「把级别调高更安全」这句话，在 PG 里还有一个反向代价：它让表膨胀得更快。**

【取舍】**所以正确的动作是**：

- **默认保持 RC**——绝大多数业务读不需要事务级一致性；
- **只在真正需要「事务内一致读」的地方**（对账、生成报表、跨表一致性校验）**提升到 RR，而且把事务做得尽量短**；
- **不要"为了安全"把全局默认调成 RR**——**那是把全局的事务时长都变成了膨胀源。**

**到这里你应该能回答**：为什么「全局调高隔离级别」在 PG 里是一个会反噬的决定？

### 7. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「PG 默认也是 RR」 | **PG 默认是 READ COMMITTED**；MySQL 才是 RR |
| 「PG 支持四种隔离级别」 | **内部只实现三种**——`READ UNCOMMITTED` 被静默当成 RC |
| 「同一事务两次读不同是 bug」 | **RC 下是规范行为**——每条语句各取一次快照 |
| 「调高到 RR 就没有并发问题了」 | **RR 挡不住写偏斜**（那是 Serializable 的活），**而且写冲突会变成 40001** |
| 「40001 是数据库出故障了」 | **是隔离级别的正常输出**——应用的正确答案是**重试整个事务**，不是加锁 |
| 「Serializable 会让并发变慢（到处加锁）」 | **官方明确：除了 RR 本来就有的阻塞，它不引入额外阻塞**；代价是**监控开销 + 更高的中止率** |
| 「事务回滚了，自增值也要回退」 | **序列不是事务性的**——**立即可见、不回滚** |

## 二、自测

**Q1（计算）**：某业务在 RR 下跑，两个事务争抢同一行的概率是 **5%**（也就是说，有 5% 的事务会在提交前遇到「这行已被别人改过并提交」）。

问：**一个事务平均要执行几次才能成功？如果把冲突概率提高到 30% 呢？**

**A1**：

```text
每次尝试失败的概率 = p（遇到写冲突 → 40001）
成功的概率 = 1 − p
期望尝试次数 = 1 / (1 − p)     ← 与乐观锁同源的公式

p = 5%  → 1 / 0.95 ≈ 【1.05 次】
p = 30% → 1 / 0.70 ≈ 【1.43 次】
p = 90% → 1 / 0.10 = 【10 次】
p → 100% → 【发散】——事务永远成功不了
```

【结论】**低冲突时重试几乎不要钱（5% 时多跑 5% 的次数）；高冲突时会雪崩**——**90% 冲突时平均要跑 10 次，等于把数据库负载放大 10 倍，而负载越高冲突越高——这是正反馈。**

【推论】**判据**：

> **重试策略的适用边界是【低冲突】。** **一旦冲突率上去，正确动作是改变访问模式（缩短事务、拆分热点、串行化那一小段），而不是加大重试次数。**

【补充】**重试必须带退避与次数上限**——**固定间隔的立即重试，在冲突期只会把冲突推得更高**（[[母题-M16-乐观锁与悲观锁]] 里算过同一件事）。

**Q2（计算）**：一张表 500 TPS 写入。一个 RR 事务持续了 10 分钟才提交。

问：**这个事务让多少死元组无法被回收？这对系统意味着什么？**

**A2**：

```text
RR 事务的快照固定在它开始的那一刻
  → 它开始之后产生的死元组，在它结束前【都不能被 VACUUM 回收】

压住的死元组 ≈ 10 × 60 × 500 = 【30 万个】
```

【结论】**30 万个死元组，占了这段时间写入的全部**——**它们会被复制到所有索引里，而不只是表里。**

【推论】**判据**：

> **在 PG 里，一个事务的【时长】直接等于它给整张表造成的膨胀量。** **所以「事务要短」在 PG 里不是风格建议，是有明确数量关系的运行要求**（[[母题-P14-长事务与表膨胀]]）。

【补充】**这里有个反直觉的连锁**：**为了「更安全」把级别调高 → 事务因为要重试而变长 → 快照留得更久 → 膨胀更快 → 查询更慢 → 事务更慢。** **这是一个正反馈环，也是"全局调高隔离级别"最危险的后果。**

**Q3（判读 + 计算）**：同一段业务代码，两种方案：

- **方案 A**：RC，实测有 **1%** 的请求因为「读到的两份数据来自不同时刻」而产生业务错误，**这些错误是静默的**（用户看到一笔错账）。
- **方案 B**：RR，实测有 **5%** 的事务报 `40001`，**应用会自动重试**（平均重试 1/0.95 ≈ 1.05 次）。

问：**哪一个更"安全"？判断的依据是什么？**

**A3**：

```text
方案 A 的代价：
  1% 的请求 → 业务错误
  → 【静默】：没有任何信号、没有日志、没有重试
  → 发现方式：用户投诉 / 对账不平

方案 B 的代价：
  5% 的事务 → 40001
  → 【显式】：有错误码、能监控、能重试
  → 重试成本：总尝试次数 ×1.05，即数据库负载 +5%
  → 发现方式：错误率仪表盘
```

【结论】**方案 B 更安全——不是因为它的失败率更低（5% > 1%），而是因为它的失败是【显式的、可自愈的】。**

【推论】**判据（这条可以直接当面试答案用）**：

> **「静默的错」和「响亮的错」不是一个量级的问题。**
> **静默的错会一路走到用户那里；响亮的错会在监控上停住，并且能被自动重试消化掉。**
> **所以在一致性敏感的场景，正确的方向是「宁可失败，不要读错」。**

【取舍】**但这不是「一律用 RR」**——**如果那 1% 的业务错误本来就无关紧要**（比如展示用的推荐位），**RR 那 5% 的重试与更长的事务反而是纯成本。** **判断标准是：这份数据读错了，代价由谁承担。**

【补充】**方案 B 还需要一个前提才成立**：**应用必须真的实现了幂等重试**。**如果重试逻辑不幂等，5% 的 40001 会变成 5% 的重复扣款**——**那它就从"更安全"变成了"更危险"**（[[母题-P19-唯一约束与UPSERT]] 里的幂等键正是为此）。

**Q4（纠错）**：下面这段话哪里不准确？

> "我们线上用 PostgreSQL，默认应该是 RR，和 MySQL 一样，所以不需要特别设隔离级别。"

**A4**：三处问题。

1. **PG 的默认是 READ COMMITTED**——**这是 PG 与 MySQL 最容易说错的一条**。**PG 的 RR 需要显式 `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ`。**
2. **「PG 支持四种级别」也不对**：**内部只实现三种**——**`READ UNCOMMITTED` 被静默当成 RC**，所以你写它也不会读到脏数据（官方原话：这是映射到 MVCC 架构唯一合理的做法）。
3. **两边同名的 RR 机制完全不同**：**PG 的 RR 是快照隔离，不用间隙锁、挡幻读靠快照、写冲突直接报 40001**；**MySQL 的 RR 用 next-key lock，写冲突表现为等待锁**（[[母题-P10-无间隙锁与锁变体]]）。

【准确说法】"**PG 默认 READ COMMITTED，所以「同一事务里两次 `SELECT` 结果不同」在默认配置下是【规范行为】。** **要事务内一致，显式提到 REPEATABLE READ，并且应用要准备好重试 40001。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "线上偶尔报 `could not serialize access due to concurrent update`，这是数据库有问题，我们打算给那些行加显式锁来避免它。"

**A5**：四处问题。

1. **这不是故障，是隔离级别的正常输出**：**它是 PG 明确设计出来**用来在快照隔离下保护一致性的**（官方原文就写了这条错误的完整含义）。
2. **它的标准处理是重试整个事务，不是加锁**：**官方原文：「应用收到这条错误时，应该中止当前事务并从头重试整个事务。」** **加锁是把"报错"改回"等待"——**也就是**把 PG 的哲学换成 MySQL 的哲学**，**但 PG 没有为此优化的锁机制**。
3. **加锁会引入新的失败模式**：**等待 → 锁超时 / 死锁**，**而这两样比 40001 更难处理**（**40001 有明确的重试语义，锁超时没有**）。
4. **如果它发生得太频繁，问题在别处**：**Q1 的算式说明冲突率一高，重试就会雪崩**——**那时该改的是事务的粒度与热点分布，不是加锁。**

【准确说法】"**40001 是「让你重来一次」的信号，标准动作是幂等重试。** **如果重试率超过可接受范围，说明事务太长或热点太集中——要改的是访问模式，不是把快照隔离换回锁等待。**"

## 三、面试输出（学完再看）

**一句话结论**：**PG 默认是 READ COMMITTED**，这是它与 MySQL（默认 RR）最容易被说错的一条差异；而且 **PG 内部只实现三种级别**——`READ UNCOMMITTED` 被静默当成 RC。**RC 下每条语句开始时取一次快照**，所以**同一事务里两条 `SELECT` 结果不同是规范行为**（不可重复读）。**PG 的 RR 是快照隔离**：整个事务一个快照，**顺带把幻读也挡掉了（比 SQL 标准的 RR 更强，标准只规定最低保护）**——**所以 PG 不需要间隙锁**。**代价是写冲突的表现完全不同**：RR 下如果目标行在事务开始后被别人改过并提交，**PG 会直接回滚该事务并报 `could not serialize access due to concurrent update`**，**官方要求应用从头重试整个事务**；而 RC 下同样场景是**对更新后的版本重新求值 `WHERE` 并继续**——**一个静默、一个显式**。**Serializable 用 SSI：除了 RR 本来就有的阻塞，不引入任何额外阻塞**，代价是监控开销与更高的中止率，**它防的是 RR 挡不住的写偏斜**。**隔离级别的真正含义是：PG 承诺的从来不是「你不会失败」，而是「你能看到什么」——级别越高，静默的读不一致越少，但显式失败越多。** 顺带记住：**序列不是事务性的**（立即可见、不回滚，这是自增有洞的第二个原因），**而长事务的快照会挡住 VACUUM**——**一张 500 TPS 的表上跑 10 分钟的 RR 事务，就是 30 万个死元组被压住。**

**恢复关键词**：**PG 默认 RC**（MySQL 是 RR）/ **内部只实现三种**（RU 当成 RC）/ 每条语句一个快照 vs 每事务一个快照 / **PG 的 RR 挡幻读**（比标准强）/ **RR 写冲突 → 40001 → 重试整个事务** / RC 下 UPDATE 重新求值 WHERE / **Serializable = 不额外阻塞 + 检测中止** / SSI 防写偏斜 / `SERIALIZABLE READ ONLY DEFERRABLE` / **序列不是事务性的** / 快照留久 → 30 万死元组

**核心不变量 / 主线**：
**隔离级别在 PG 里承诺的是「你能看到什么」，不是「你不会失败」。**
**级别越高，看到的越一致，但越可能被要求重试**——**PG 用「快照 + 报错重试」换掉了「加锁等待」。**

**完整回答骨架**：默认 RC（不是 RR）→ 快照粒度（语句 vs 事务）→ 「两次读不同」是规范行为 → **PG 的 RR 比标准强（挡幻读）** → **代价是写冲突报 40001，要重试** → RC 与 RR 在同一场景下的两种处理（静默 vs 显式）→ Serializable = SSI（不额外阻塞）→ **序列不是事务性 + 快照挡住 VACUUM** → 收束到「选级别 = 选哪种代价」

**追问**（先说后看）

1. **PG 为什么不加间隙锁？** —— **因为它用快照隔离，幻读已经被快照挡住了，不需要用锁挡。** **加间隙锁会让并发插入互相阻塞**（MySQL 的死锁大头就来自这里）。**这是 PG 用「快照 + 报错」换「锁 + 等待」的一个具体体现**（[[母题-P10-无间隙锁与锁变体]]）。
2. **Serializable 是不是就万无一失了？** —— **一致性上万无一失，可用性上更容易失败**：**它连写偏斜都检测，所以中止率更高**。**而且它要求「读到的数据在事务成功提交前都不算数」**——**包括只读事务**（除非用 `READ ONLY DEFERRABLE`）。**所以它适合"正确性压倒一切"的场景，不适合高并发写入的常规业务。**
3. **40001 和死锁（40P01）有什么区别？** —— **40001 是「你的快照过期了，重来一次就好」，没有等待、没有资源占用**；**死锁是「两个事务互相等对方的锁」，需要一个被牺牲掉**。**前者是快照隔离的正常输出，后者是加锁模型的固有代价**——**PG 两种都有，但 40001 是它主动选择的。**
4. **`FOR UPDATE` 能不能替代提高隔离级别？** —— **能替代一部分**。**`SELECT ... FOR UPDATE` 在 RC 下也会锁住读到的行，所以"读-改-写"这种最常见的竞态可以直接用它防住**，不必升到 RR。**PG 还有四种变体**（`FOR UPDATE` / `FOR NO KEY UPDATE` / `FOR SHARE` / `FOR KEY SHARE`），**选最弱的那一个能显著减少锁冲突**（[[母题-P10-无间隙锁与锁变体]]）。
5. **只读副本上的读一致性怎么办？** —— **副本上的默认也是 RC，但副本有额外一层：复制延迟**。**要在副本上做「事务内一致读」，RR 只保证副本自身快照一致，不保证读到主库最新**——**要读最新得走主库，或者用复制槽 / `pg_last_wal_replay_lsn()` 做等待**（[[母题-P12-流复制与逻辑复制]]）。

**同类变体**

- 「MySQL 的 RR 和 PG 的 RR 差多少？」—— **三处**：① **MySQL RR 用 next-key lock 挡幻读，PG 用快照挡**；② **MySQL RR 写冲突是等待（可超时/死锁），PG RR 写冲突是报 40001**；③ **MySQL RR 事务内的一致性读更"重"（因为要维护锁），PG 更轻但要处理重试**。**两边同名的级别不是同一件东西**（[[母题-M8-隔离级别与ACID]]）。
- 「为什么 PG 文档反复强调"应用必须准备重试"？」—— **因为 PG 的一致性模型把失败【暴露】给应用了**：**RC 下它把失败藏进业务结果里，RR/Serializable 下它明确报错。** **这条提醒本身，就是「PG 把选择权交给应用」的体现。**
