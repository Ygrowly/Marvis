**题目**：一条 `WHERE device_id = ? AND stat_date >= ?` 只返回 `device_id, stat_date` 的查询，同样的表结构在 MySQL 里可以做到「不回表」，在 PG 里为什么不一定？

## 一、教材

### 1. 前提：索引只记录"值 → 位置"

::figure pg-heap-and-ctid.svg | PG 的索引只是路标：索引给位置，取行要回堆 | 堆是无序数据页；B-tree 叶子存 (键值, ctid)；取行默认要回堆，只有可见性映射干净时才跳过

【事实】

```text
表（堆）      ：一堆数据页（8KB），行按写入顺序散落，【行与行之间无任何顺序保证】
索引（B-tree）：另一套文件，有序，叶子存 (键值, ctid)
ctid          ：(页号, 页内偏移) —— 【物理位置】
```

【推导】**对比 InnoDB**：

```text
InnoDB：主键索引的叶子【就是整行数据】（索引组织表）
        → 按主键查一次树查找就拿到数据

PG    ：没有这种结构
        → 一次索引查找【永远只能拿到位置】
```

【结论】**所以回表不是"PG 没做好"，是"PG 的表结构和索引结构决定了它必须回"。**

【推论】**这一条决定了后面所有差异**：回表、主键选型、页分裂、覆盖索引的可行性——**全都能从"索引组织表 vs 堆表"推出来。**

**到这里你应该能回答**：为什么说"PG 的主键索引就是数据"是错的？

---

### 2. 回表是必然的，而且成本随命中行数线性增长【推导】

```text
走索引：B-tree 查找 → 拿到 ctid（可能几十上百个）
回表  ：按 ctid 逐个读堆页 → 拿到真正的行
```

【推导】**算一下代价**：

```text
树查找是 O(log N)——命中 100 万行和命中 10 行，树查找的深度差不多

但回表次数 = 命中行数，而且是【随机 IO】（ctid 指向的位置不一定连续）

命中 10 行   → 约 10 次随机 IO  ≈ 1 ms（按 SSD 每次 0.1ms）
命中 1000 行 → 约 1000 次随机 IO ≈ 100 ms
```

【结论】**"命中 1000 行"比"命中 10 行"危险得多**——**因为树查找的深度几乎不变，而回表次数是线性增长的。**

【推论】**这和 MySQL 是同一个道理，但 PG 里没有主键这条路可以绕过**——**InnoDB 至少主键查询不用回表**（[[母题-M3-聚簇索引与回表]]）。

**到这里你应该能回答**：为什么"加个索引"对大范围查询不一定有效？

### 3. Index Only Scan：判据是"可见性"，不是"列齐了"

【推导】**这是最容易讲错的一处。** PG 的"不回表扫描"**不是**因为索引里含了所有需要的列：

```text
即使列齐了，PG 也【必须确认这一行的这个版本对当前事务可见】
而这个信息存在【堆页头部】，不在索引里
```

【事实】**解决办法是 visibility map（可见性映射）**：

```text
visibility map 说该页全可见    → 可以直接用索引里的值，跳过堆  ← Index Only Scan
该页有不可见版本（刚更新过）    → 必须去堆确认可见性            ← 退化成普通 Index Scan
```

【结论】**所以 Index Only Scan 的隐含条件是"你一直在 VACUUM"**——**更新/删除产生的死元组没被清理前，对应的页就不是"全可见"。**

【事实】**被追问"为什么计划里明明是 Index Only Scan 但还是很慢"时**，答案就是 **`Heap Fetches` 很多**——**`EXPLAIN ANALYZE` 会直接显示这一项**。

【推论】**`Heap Fetches` 是判断"真假覆盖索引"的唯一依据**：

```text
Heap Fetches = 0            → 真的没回堆
Heap Fetches ≈ 返回行数     → 等于每行都回了堆 —— 【省了个寂寞】
```

【推论】**只看节点名（是不是 `Index Only Scan`）不看 `Heap Fetches`，是典型的假优化。**

**到这里你应该能回答**：为什么"索引里包含了我需要的所有列"不保证不回表？

### 4. 最左前缀在 PG 依然成立（但语义要讲清）

【事实】PG 的 B-tree 索引是**有序结构**，所以 `(a, b, c)` 依旧只能从最左列开始连续使用——**这和 MySQL 是同一个道理，因为原因是同一个（有序性）**。

【事实】**两处 PG 特有的差异**：

| | MySQL | PostgreSQL |
|---|---|---|
| 联合索引叶子存什么 | **索引列 + 主键** | **索引列 + ctid**（堆表要存物理位置） |
| 后果 | 覆盖索引要**凑巧包含主键** | **更容易做到 Index Only Scan**（叶子有各列的值），**但仍受可见性限制** |
| 额外列 | 只能靠扩展索引键 | **`INCLUDE` 列** |

【事实】**`INCLUDE` 是 PG 一个很实用的点**：

```sql
CREATE INDEX idx ON t (a, b) INCLUDE (c);
-- 排序与定位只用 (a, b)
-- c 只放在叶子里供 Index Only Scan 取用
-- 【c 不参与最左前缀规则】
```

【推导】**它和"把 c 直接加进索引键"的差别**：

```text
(a, b, c) ：
  c 参与最左前缀
  → 查询 WHERE a = ? AND c = ? 里，c 【用不上】（被 b 截断，[[母题-M2-联合索引与最左前缀]]）

(a, b) INCLUDE (c) ：
  索引的【可用形状】和 (a, b) 一样（c 不参与定位）
  但叶子多带了 c 的值 → 满足 Index Only Scan 的列条件
```

【结论】**INCLUDE 的收益是"不改索引的可用形状，只加覆盖能力"。** 被问"怎么既保持索引键简洁又能覆盖"时，这就是答案。

**到这里你应该能回答**：为什么 `INCLUDE` 列的收益不是"让索引更快"，而是"让索引多一种用途"？

### 5. 落到项目查询

【事实】EnergyOps 的四层事实表按 `(device_id, energy_type, stat_date)` 建索引（**等值在前、范围在后**）。

【推导】**这条查询理论上可以走 Index Only Scan**，但成立的前提是**这张表被正常 VACUUM**：

```text
聚合表更新频繁
→ 持续产生旧版本
→ 可见性映射常年不干净
→ 实际上拿不到 Index Only Scan
```

【取舍】**所以优化重心应该放在"减少扫描与回表行数"，而不是"凑成覆盖索引"**——**这是一个可以主动讲出来的取舍**，而且它体现了"先看机制再定手段"的思维方式。

【推论】**"回表慢"在 PG 里经常要先治膨胀（VACUUM），而不是先加索引**——**这条正好接到主线五**（[[母题-P14-长事务与表膨胀]]、[[母题-P15-VACUUM与事务ID回卷]]）。

**到这里你应该能回答**：为什么在 PG 里，"优化一个慢查询"的第一步可能不是看索引？

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "PG 的主键索引就是数据" | **这是 MySQL 语义**。**PG 的表是堆，主键只是"唯一且非空的 B-tree 索引"，数据仍然是堆，仍然要回表**。**这是最容易被污染的一题** |
| "索引里包含了需要的列就不会回表" | **判据不是"列齐了"，是"可见性映射说这一页全可见"**。**因为可见性信息存在堆页头部，不在索引里**。**所以 Index Only Scan 依赖 VACUUM 的维护** |
| "计划里写了 Index Only Scan 就是没回表" | **要看 `Heap Fetches`**：**不是 0 就说明还在回堆**——**`Heap Fetches ≈ 返回行数`时，等于每行都回了堆，省了个寂寞**。**只看节点名是典型的假优化。** |
| "PG 有 CLUSTER 就是聚簇索引" | **`CLUSTER` 是一次性重排**（按某个索引把堆重写一遍），**之后新写入的行不会再维持顺序**——**所以它不是持续的聚簇索引**。知道它存在、也知道它不持久，就够了 |
| "PG 的索引比 MySQL 少一层开销" | **反了**。**PG 每次写要在堆里插行（更新 = 插入新版本 + 标记旧版本），同时更新每一个索引**——**写放大比 MySQL 更重** |
| "PG 里主键查询更快，因为有聚簇" | **没有聚簇**。**PG 的主键查询同样要回表**（除非能走 Index Only Scan，而那要可见性映射干净）。**"主键快"是 InnoDB 的性质** |
| "最左前缀是 MySQL 的概念" | **PG 也有，原因相同（B 树有序）**。**差别在叶子存什么**：MySQL 存主键、PG 存 ctid（外加各列的值），**所以 PG 更容易做到覆盖，但仍受可见性限制** |

【取舍】读成一句话：**MySQL 的主键就是数据本身，PG 的索引只是"指向数据的路标"——这一条决定了两边索引的一切行为差异。**

## 二、自测

**Q1（计算）**：某查询走索引后命中 **1000 行**，每行都要回表。设 SSD 上一次随机 IO 约 **0.1 ms**。

问：**回表部分的耗时大约是多少？**如果只命中 10 行呢？这说明什么？

**A1**：

```text
命中 1000 行：1000 × 0.1ms = 100 ms
命中 10 行：  10 × 0.1ms  = 1 ms
```

【结论】**回表耗时随命中行数【线性增长】。**

【推论】**而树查找是 O(log N)**——**命中 100 万行和命中 10 行，树查找的深度差不多**。所以：

```text
"加个索引让查询走树查找" 这件事
只解决了【找到位置】的成本
没有解决【按位置逐个取行】的成本
```

**这就是"命中行数"比"树查找深度"重要得多的原因**——**也是"加索引不总是有效"的数学依据。**

【补充】而这还是**纯回表**的成本，没算 buffer pool 未命中、以及膨胀导致的堆页稀疏（[[母题-P14-长事务与表膨胀]] 会讲"回表慢"经常要先治膨胀）。

**Q2（判读）**：某查询的 `EXPLAIN ANALYZE` 显示：

```text
Index Only Scan using idx_xxx on t
  Heap Fetches: 9850
  rows: 10000
```

问：**这个 Index Only Scan 真的省掉回表了吗？**该怎么解读？

**A2**：**没有省掉，几乎是每行都回了堆。**

```text
Heap Fetches: 9850 / rows: 10000
→ 回表比例 = 98.5%
→ 只有 150 行（1.5%）真的用了索引里的值
```

【结论】**节点名写了 `Index Only Scan`，但实际退化成了普通 Index Scan**——**因为它想跳过的"读堆"这一步，98.5% 的情况下还是发生了。**

【为什么】**可见性映射不干净**：**这一页里有还没被 VACUUM 清理的死元组**，所以 PG 必须回堆确认可见性（Q2 的机制）。

【正确解读】**`Heap Fetches` 是"真假覆盖索引"的唯一依据**：

```text
Heap Fetches = 0            → 真的没回堆
Heap Fetches ≈ 返回行数     → 省了个寂寞
```

【补充】**只看节点名不看 `Heap Fetches`，是典型的假优化**——**这也是"我加了覆盖索引怎么没变快"最常见的答案。**

**Q3（判读）**：下面两个建索引的方案，**哪个更好？为什么？**

```sql
-- 方案 A
CREATE INDEX idx_a ON t (a, b, c);

-- 方案 B
CREATE INDEX idx_b ON t (a, b) INCLUDE (c);
```

**A3**：**取决于查询形状，但方案 B 的适用范围更宽。**

```text
方案 A（c 参与索引键）：
  索引可用形状 = (a, b, c)
  ✓ 能服务：a / a,b / a,b,c
  ✗ 不能服务：WHERE a=? AND c=?（c 被 b 截断，用不上）
  ✓ 叶子带了 c，可覆盖

方案 B（c 只是 INCLUDE）：
  索引【可用形状】= (a, b)（c 不参与定位）
  ✓ 能服务：a / a,b
  ✓ 叶子同样带了 c → 也能覆盖
  → 【可用形状和 (a,b) 一样，但多了覆盖能力】
```

【结论】**INCLUDE 的收益是"不改索引的可用形状，只加覆盖能力"。**

【取舍】**怎么选**：

```text
如果查询里 【c 经常作为过滤条件】→ 用方案 A（让 c 参与定位）
如果 c 【只是被 SELECT 出来】    → 用方案 B（不破坏 (a,b) 的形状）
```

【补充】**注意两者都要看 `Heap Fetches`**——**即使列齐了，可见性映射不干净照样回堆**（Q2）。

**Q4（纠错）**：下面这段话哪里不准确？

> "PG 的主键索引就是数据，所以按主键查是最快的。"

**A4**：三处问题。

1. **"主键索引就是数据"是 MySQL 的语义**。**PG 的表是堆**，**主键只是"唯一且非空的 B-tree 索引"**，叶子存的是 `ctid`（物理位置），**数据仍在堆里**。
2. **所以按主键查【同样要回表】**——除非能走 Index Only Scan，**而那需要可见性映射干净**（Q2）。
3. **"最快"要看具体查询**：**按主键查一行确实快**（回表 1 次），**但这是"命中行数少"带来的，不是"有聚簇"带来的**（Q1：回表成本随命中行数线性增长）。

【准确说法】"**PG 里所有索引都是二级索引**，主键也不例外。**按主键查快，是因为它命中一行、回表一次**——**换一个高选择性的二级索引，效果一样。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "我给查询需要的三列建了联合索引，这样就不用回表了。"

**A5**：三处问题。

1. **"列齐了"不是 Index Only Scan 的判据**：**可见性信息存在堆页头部，不在索引里**——**即使列齐，也要先确认"这一页所有版本都可见"**（Q2 的机制）。
2. **而"可见性映射干净"依赖 VACUUM**：**更新/删除产生的死元组没清理前，对应的页就不干净**。**所以这是一个【运行时状态】，不是建索引时能决定的。**
3. **必须用 `Heap Fetches` 验证**：**不是 0 就说明还在回堆**。**"我建了覆盖索引"和"它真的覆盖了"是两件事。**

【准确说法】"**建对的索引是必要条件，可见性映射干净是另一个必要条件。** 而后者靠 VACUUM 维护——**所以聚合表、更新频繁的表，实际上很难拿到 Index Only Scan。**"

## 三、面试输出（学完再看）

**一句话结论**：**MySQL 的主键就是数据本身（索引组织表），PG 的索引只是"指向数据的路标"**——**PG 的表是堆，所有索引都是二级索引，叶子存 `ctid`（物理位置）**，所以**走索引只能拿到"行在哪"，取行必须再读堆，这就是回表**。而且**回表成本随命中行数线性增长**（命中 1000 行 ≈ 100ms，命中 10 行 ≈ 1ms），**树查找却是 O(log N)**——**所以"命中行数"比"树查找深度"重要得多**。**Index Only Scan 的判据不是"列齐了"，而是"可见性映射说这一页所有版本都可见"**——因为**可见性信息存在堆页头部**。**所以它依赖 VACUUM 的维护**，而**验证的唯一依据是 `EXPLAIN ANALYZE` 里的 `Heap Fetches`（不是 0 就还在回堆）**。**最左前缀在 PG 依然成立**（原因相同：B 树有序），**差别在叶子存什么**——PG 存 ctid + 各列值，**所以更容易做到覆盖，但仍受可见性限制**；而 **`INCLUDE` 列**是"不改索引的可用形状，只加覆盖能力"。

**恢复关键词**：**堆 / 所有索引都是二级索引 / ctid = (页号, 页内偏移)** / 回表必然 / **回表成本线性增长**（1000 行 ≈ 100ms）/ 树查找 O(log N) 不是瓶颈 / **Index Only Scan 的判据是可见性映射**（不是列齐）/ 可见性信息在堆页头部 / **依赖 VACUUM** / **`Heap Fetches` 判断真假**（≈ 返回行数 = 省了个寂寞）/ 最左前缀成立（B 树有序）/ PG 叶子存 ctid + 各列值 / **`INCLUDE` 列不参与最左前缀** / `CLUSTER` 是一次性重排、不持久

**核心不变量 / 主线**：
**MySQL 的主键就是数据本身（索引组织表），PG 的索引只是「指向数据的路标」。**
这一条决定了**两边索引的一切行为差异**：回表、主键选型、页分裂、覆盖索引的可行性。

**完整回答骨架**：堆表长什么样 → **索引只给位置，所以回表必然** → 回表成本的算式 → **Index Only Scan 的判据是可见性映射**（不是列齐）+ Heap Fetches 怎么验 → 最左前缀依然成立但叶子语义不同 → **INCLUDE 列** → 落到项目查询（聚合表拿不到 IOS，重心转向减少扫描）

**完整回答（口述稿）**：
**MySQL 的主键就是数据本身（索引组织表），PG 的索引只是"指向数据的路标"**——**PG 的表是堆，所有索引都是二级索引，叶子存 `ctid`（物理位置）**。所以走索引只能拿到"行在哪"，取行必须再读堆，**这就是回表**——**PG 里任何索引查询都要回表**（`CLUSTER` 只是一次性重排，不持久）。

成本结构要会算：**回表成本随命中行数线性增长**（命中 1000 行 ≈ 100 ms，命中 10 行 ≈ 1 ms），而**树查找是 O(log N)**——所以**"命中行数"比"树查找深度"重要得多**，这也是"加了索引还是慢"的常见原因。

**Index Only Scan 的判据不是"列齐了"，而是"可见性映射说这一页所有版本都可见"**——因为**可见性信息存在堆页头部**。所以它**依赖 VACUUM 的维护**，验证的唯一依据是 `EXPLAIN` 里出现 `Heap Fetches: 0`。

**分层要点**：
- **结论**：PG 是堆表，索引一律二级、一律回表；Index Only Scan 靠可见性映射，依赖 VACUUM。
- **推导链**：索引组织表 vs 堆表 → 叶子存 ctid → 必然回表 → 成本随命中行数增长 → 免回表的条件是可见性映射。
- **量化**：回表 1000 行 ≈ 100 ms、10 行 ≈ 1 ms；树查找 O(log N)。
- **边界与常见误解**："列齐了就是 Index Only Scan"×；`CLUSTER` 不是持久的聚簇；与 MySQL 对照时要说"PG 一律回表"。

**追问**（先说后看）

1. **PG 的主键一定是聚簇索引吗？** —— **不是**。**PG 的主键只是"唯一且非空的 B-tree 索引"，数据仍然是堆**。**这是最容易被 MySQL 语义污染的一题。**
2. **PG 有聚簇吗？** —— **有 `CLUSTER` 命令，但它是一次性重排**（按某个索引把堆重写一遍），**之后新写入的行不会再维持顺序**——**所以不是持续的"聚簇索引"**。知道它存在、也知道它不持久，就够了。
3. **为什么 PG 的索引个数对写入影响大？** —— **每次写要在堆里插行，同时更新每一个索引**；而且 **PG 的 MVCC 让更新等于"插入新版本 + 标记旧版本"**，**写放大被进一步放大**。
4. **怎么判断有没有真的省掉回表？** —— **`EXPLAIN ANALYZE` 看三点**：节点是不是 `Index Only Scan`；**`Heap Fetches` 是多少（不是 0 就说明还是回了堆）**；实际行数与 buffered read 的关系。**只看节点名不看 Heap Fetches，是典型的假优化。**
5. **表膨胀会让回表更慢吗？** —— **会，而且是双重影响**：① **堆页更稀疏**，同样的行数分布在更多页上，**回表的随机 IO 次数上升**；② **索引的 ctid 指向的旧位置让局部性更差**。**所以"回表慢"在 PG 里经常要先治膨胀（VACUUM），而不是先加索引。**

**同类变体**

- 「为什么 PG 的索引更容易做大？」——**因为叶子要存 ctid（物理位置）**，而 **ctid 会随行的移动而失效**（更新 = 新版本 + 新位置）——**所以 PG 的索引项更新更频繁**，也更容易膨胀。
- 「覆盖索引在 PG 里还值得做吗？」——**值得，但要先确认可见性映射干净**（Q2）。**对更新频繁的表（比如聚合成事实表），实际拿不到 Index Only Scan**——**这时候"减少扫描行数"比"凑覆盖"更实在。**
