# 母题 P2 · 堆表与回表

> **模块**：PostgreSQL / 索引与表设计
> **所属主线**：一 · 索引与表设计（怎么让查询不用扫全表，表怎么建才不埋雷）
> **关联母题**：[[母题-P1-索引类型选型]] · [[母题-P3-部分索引与表达式索引]]
> **素材来源**：三个项目真实查询（EnergyOps 四层事实表）+ 通用知识（**待你核对**）

**题目**：一条 `WHERE device_id = ? AND stat_date >= ?` 只返回 `device_id, stat_date` 的查询，同样的表结构在 MySQL 里可以做到「不回表」，在 PG 里为什么不一定？

**母题**：PG 是堆表，为什么索引查询要回表？Index Only Scan 靠什么成立？联合索引在 PG 也有最左前缀吗？

**为什么重要**：这是**整个 PG 索引体系的起点**，也是 MySQL 与 PG 最容易说反的地方。你三个项目全在 PG，如果讲不清「PG 表是堆、所有索引都是二级索引」，那么后面讲覆盖索引、讲索引代价、讲主键选型全都会带着 MySQL 的语义往下走——**面试官一听就知道你在背另一本书**。

**一句话结论**：PG 的表是**堆**（一堆无序的数据页），**所有索引都是二级索引**，叶子存的是 `ctid`（指向物理位置），所以走索引只能拿到「行在哪」，取行必须再读堆——这就是回表。**Index Only Scan 成立的条件不是「索引里有这些列」，而是「这些页的可见性映射说这些版本全可见」**，因此它**依赖 VACUUM 的维护**。最左前缀在 PG 依然成立（B-tree 是有序结构），但联合索引叶子存的是所有列的值，所以它才可能不走堆。

**恢复关键词**：堆 / 无序数据页 / 所有索引都是二级索引 / ctid / 回表 / visibility map + VACUUM / 最左前缀 / INCLUDE 列

**核心不变量 / 主线**：
**MySQL 的主键就是数据本身（索引组织表），PG 的索引只是「指向数据的路标」。** 这一条决定了两边索引的一切行为差异：回表、主键选型、页分裂、覆盖索引的可行性。

**完整回答骨架**：堆表长什么样 → 索引只能给位置，所以回表必然 → Index Only Scan 的判据是可见性映射 → 最左前缀依然成立但语义不同 → INCLUDE 列怎么用 → 落到项目查询

## 原理分解

### 一、堆表：数据本身没有顺序

PG 的表由一堆**数据页（8KB）**组成，行按写入顺序散落在页里，**行与行之间没有任何顺序保证**。索引是**另外一套文件**，它把「某个值 → 行在哪」记录下来。

```
表（堆）        ：一堆数据页，无序
索引（B-tree）  ：有序，叶子存 (键值, ctid)
ctid            ：(页号, 页内偏移) —— 物理位置
```

对比 InnoDB：InnoDB 的主键索引**叶子就是整行数据**（索引组织表），所以「按主键查」一次树查找就拿到数据。**PG 没有这种结构，一次索引查找永远只能拿到位置。**

### 二、所以回表是必然的

```
走索引：B-tree 查找 → 拿到 ctid（可能几十上百个）
回表  ：按 ctid 逐个读堆页 → 拿到真正的行
```

**成本模型的关键**：树查找是 O(log N)，**回表次数随命中行数线性增长**，而且是随机 IO（ctid 不一定连续）。所以「命中 1000 行」比「命中 10 行」危险得多——**这和 MySQL 是同一个道理，但 PG 里没有主键这条路可以绕过**（InnoDB 至少主键查询不用回表）。

### 三、Index Only Scan：判据是「可见性」，不是「列齐了」

这是最容易讲错的一处。PG 的「不回表扫描」**不是**因为索引里含了所有需要的列——即使列齐了，PG 也**必须确认这一行的这个版本对当前事务可见**，而这个信息存在堆页头部，不在索引里。

解决办法是 **visibility map**：PG 用一个位图记录「这一页里的所有行对所有事务都可见」。

```
visibility map 说该页全可见  →  可以直接用索引里的值，跳过堆   ← Index Only Scan
该页有不可见版本（刚更新过） →  必须去堆确认可见性           ← 退化成普通 Index Scan
```

**所以 Index Only Scan 的隐含条件是你一直在 VACUUM**：更新/删除产生的死元组没被清理前，对应的页就不是「全可见」，Index Only Scan 会退化。**被追问「为什么计划里明明是 Index Only Scan 但还是很慢」时，答案就是 Heap Fetches 很多**（`EXPLAIN ANALYZE` 会直接显示这一项）。

### 四、最左前缀在 PG 依然成立（但语义要讲清）

PG 的 B-tree 索引是**有序结构**，所以 `(a, b, c)` 依旧只能从最左列开始连续使用——**这和 MySQL 是同一个道理，因为原因是同一个（有序性）**。

两处 PG 特有的差异：

| | MySQL | PostgreSQL |
|---|---|---|
| 联合索引叶子存什么 | **索引列 + 主键** | **索引列 + 全部索引列的值 + ctid** |
| 后果 | 覆盖索引要凑巧包含主键 | **更容易做到 Index Only Scan**（叶子本来就有各列的值），但仍受可见性限制 |
| 额外列 | 只能靠扩展索引 | **`INCLUDE` 列**：把「只为覆盖而加」的列挂在叶子，不参与排序 |

**`INCLUDE` 是 PG 一个很实用的点**：`CREATE INDEX ... ON t (a, b) INCLUDE (c)` —— 排序与定位只用 `(a,b)`，`c` 只放在叶子里供 Index Only Scan 取用，**不参与最左前缀规则**。被问「怎么既保持索引键简洁又能覆盖」时这就是答案。

### 五、落到你的项目查询

EnergyOps 的四层事实表按 `(device_id, energy_type, stat_date)` 建索引（等值在前、范围在后）。这条查询**只返回 device_id / energy_type / stat_date，理论上可以走 Index Only Scan**——但要成立，前提是这张表**被正常 VACUUM**（批量聚合会持续产生旧版本）。**这是一个可以主动讲出来的取舍**：聚合表更新频繁 → 可见性映射常年不干净 → 实际上拿不到 Index Only Scan，于是优化重心应该放在「减少扫描与回表行数」而不是「凑成覆盖索引」。

## 二、扩展：类似题与追问

**类似题**

1. 「PG 的主键一定是聚簇索引吗？」——**不是**。PG 的主键只是「唯一且非空的 B-tree 索引」，数据仍然是堆。**这是最容易被 MySQL 语义污染的一题。**
2. 「PG 有聚簇吗？」——有 `CLUSTER` 命令，但它是一次性重排（按某个索引把堆重写一遍），**之后新写入的行不会再维持顺序**，所以不是持续的「聚簇索引」。**知道它存在，也知道它不持久，就够了。**
3. 「为什么 PG 的索引个数对写入影响大？」——每次写要在**堆**里插行，同时更新**每一个**索引；PG 的 MVCC 还让更新等于「插入新版本 + 标记旧版本」，写放大被进一步放大。

**追问链**

- 追问一层：**「那怎么判断有没有真的省掉回表？」**——`EXPLAIN ANALYZE` 看三点：节点是不是 `Index Only Scan`；**`Heap Fetches` 是多少**（不是 0 就说明还是回了堆）；实际行数与 buffered read 的关系。**只看节点名不看 Heap Fetches，是典型的假优化。**
- 追问二层：**「表膨胀会让回表更慢吗？」**——会，而且是双重影响：① 堆页更稀疏，同样的行数分布在更多页上，回表的随机 IO 次数上升；② 索引的 ctid 指向的旧位置让局部性更差。**所以「回表慢」在 PG 里经常要先治膨胀（VACUUM），而不是先加索引**——这条正好接到主线五。
