> **素材来源**：`study/09-数据缓存队列与一致性` 第 7 节（Agent 长任务数据模型）+ 三个项目真实建表 + **PostgreSQL 官方文档 Character Types / JSON Types / Date-Time Types / Numeric Types / Identity Columns**（2026-09-13 联网核实）。**三组算式与「UUID 代价落在哪」那一段为本次新增（待你核对）**

**导读**：必懂 3 件事（① PG 的类型选择**几乎不看性能**，只看语义——因为性能差异是被算过的，小到排不上第一理由 ② 唯一有真实性能后果的是 `char(n)` 与 JSON 选型 ③ UUID 在 PG 的代价**在索引不在堆**，和 InnoDB 不一样）· 读完约 11 分钟 · 需要先懂：[[母题-P2-堆表与回表]]

**题目**：给一张新的业务表定字段：一个存放用户输入的文本字段、一个结构不固定的配置项、一个主键、两个时间戳。每项怎么选，为什么？

**母题**：PG 里 text 与 varchar、jsonb 与 json、serial 与 identity、timestamptz 怎么选？

**为什么重要**：这是**最不起眼但最容易被追问到底**的一类题。它不难，但**PG 的答案和 MySQL 的答案在四个点上都不一样**（varchar 的性能差异、JSON 的两种类型、自增的实现、时间的时区语义）。**答成 MySQL 那一套，等于白做三个 PG 项目。**

**一句话结论**：PG 里 **text 与 varchar(n) 性能没有差别**（同一套变长存储），所以选哪个是**语义选择**——要长度约束才用 `varchar(n)`；**jsonb 存解析后的二进制、可建 GIN 索引，json 存原始文本、保留格式与键序**，要查就用 jsonb；主键用 **`GENERATED ... AS IDENTITY`**（SQL 标准，序列是隐式的，随表走），`serial` 是历史写法；**时间一律 `timestamptz`**（存 UTC 瞬时点、会话时区显示），`timestamp` 只用于「就是本地墙上时间」的语义。

**恢复关键词**：text = varchar（无性能差）/ varchar(n) 只做校验 / 1 字节头 ≤126 字符 / `char(n)` 最慢 / jsonb 可索引 vs json 保原文 / identity（自动 NOT NULL，但不保证唯一）vs serial / UUID 的索引代价在索引不在堆 / timestamptz 存 UTC、不保留原时区

**核心不变量 / 主线**：
**类型选择不是「哪个性能好」，而是「哪个语义对」。** 长度约束、时区语义、结构固定性、唯一性来源——**先把语义说清，性能差异在 PG 里往往小到不值得作为第一理由。**
**唯一的例外是 `char(n)` 与 JSON 选型**：前者有实打实的空间与 CPU 代价，后者直接决定「能不能建索引」。

**完整回答骨架**：文本类型（无性能差，只有语义差）→ JSON 两种类型的选择判据 → 主键（identity / UUID 的真实代价落在哪）→ 时间（时区语义）→ 回到建表给完整 DDL

## 一、教材

### 1. text vs varchar vs char：把「没有性能差别」算出来

::figure pg-types-choice.svg | 四种类型选择的判据：先问语义，再问代价 | 文本三选一的存储算式、json 与 jsonb 的判据、identity 与 serial 的差别、时间类型的时区语义

【事实】**官方口径第一句就很硬**：

> **这三种类型之间没有性能差别**——除了定长（blank-padded）类型会多占存储空间，以及往有长度约束的列写入时多花几个 CPU 周期去检查长度。
> **`character(n)` 在别的数据库里可能有优势，在 PostgreSQL 里没有；事实上它通常是三者中最慢的**，因为存储开销更大。**大多数情况下应该用 `text` 或 `character varying`。**

【推导】**「没有性能差别」不是一句感觉，是可以算的**：

```text
变长字符串的存储开销（官方给出）：
  长度 ≤ 126 字节 → 1 字节头 + 实际内容
  长度 >  126 字节 → 4 字节头 + 实际内容

存一个 20 字符的短字符串：
  text        = 1 + 20 = 21 字节
  varchar(255)= 1 + 20 = 21 字节   ← 完全相同

  → 两者的存储与拷贝成本一模一样
  → varchar(n) 唯一多做的事，是写入时比一下 n
```

【推导】**而 `char(n)` 的代价是真实的**：

```text
char(200) 存 "abc"：
  定长补空格 → 200 字节（补了 197 个空格）
text 存 "abc"：
  1 + 3 = 4 字节

  → 50 倍空间
  → 而且读出/比较时还要处理补上的空格（官方说它「通常最慢」的原因）
```

【取舍】**所以选择标准是纯语义的**：

- 业务上确实有上限（比如「手机号最多 20 字符」）→ `varchar(n)`，**让数据库替你守住这个约束**；
- 只是「文本」→ `text`；
- **`char(n)` 在 PG 里没有正当用途**——定长带来的那点「对齐」想法在 PG 里不成立。

【推论】**「为什么 PG 圈里很多人直接用 text」的准确答案**：**不是图省事，是因为在没有约束需求时，加一个长度限制只会带来「以后要放宽还得改 DDL」的麻烦，而换不来任何性能。** ——注意这是**在 PG 里**成立的推论；**MySQL 那边不完全成立**（见第四节方言差异），**别混着讲**。

**到这里你应该能回答**：为什么「`varchar` 比 `text` 快」这句话在 PG 里是错的，而它错在哪一步？

### 2. json vs jsonb：判据是「要不要查」

【事实】**官方口径**：

> **`json` 存输入的精确副本**，处理函数每次执行都要**重新解析**；
> **`jsonb` 存分解后的二进制格式**，**写入稍慢**（多一次转换开销），但**处理显著更快**（不用重新解析），而且 **`jsonb` 支持索引，这是它的一个重要优势**。

| | `json` | `jsonb` |
|---|---|---|
| 存储 | **原始文本** | **解析后的二进制结构** |
| 保留 | 语义上无关紧要的空格、**键的顺序**、**重复键全部保留**（函数取最后一个） | 规范化：不留空白、**键序不保证**、去重复键 |
| 写入 | 快（只存字符串） | 稍慢（要解析） |
| 查询 / 索引 | **不能建 GIN 索引**，取字段要现场解析 | **可建 GIN**，支持 `@>`、`?`、`->` 等操作符 |
| 典型用途 | 审计、留痕、**原样回传** | **要按内部字段过滤/检索** |

**一句话判据**：**只要会被「查」，就用 jsonb。** 只有当「原样保存、原样取出」是需求本身（司法级留痕、要把用户原始请求原封不动还回去）时才用 json。

【推论】**这是一条会连锁的选择**：选 jsonb → 可以建 GIN（[[母题-P1-索引类型选型]]）；选 json → 只能整列全表扫。**这个字段类型的选择，直接决定索引能不能做。**

【取舍】**jsonb 的两个真实代价**：① 写入时多一次解析；② **重复键会被丢掉、键序会变**——**如果有任何一个下游在依赖「原样」的 JSON 字符串（比如做签名校验、做 hash 比对），jsonb 会悄悄改变它。** 这个坑不报错，只会让签名对不上。

**到这里你应该能回答**：为什么「审计表用 jsonb 省事」可能是一个错误决定？

### 3. 主键：identity vs serial，以及 UUID 的真实代价

【事实】**`serial` 不是类型，是语法糖**——官方给的展开是三条语句：

```sql
-- 写这个：
CREATE TABLE tablename (colname SERIAL);
-- 等价于：
CREATE SEQUENCE tablename_colname_seq AS integer;
CREATE TABLE tablename (colname integer NOT NULL DEFAULT nextval('tablename_colname_seq'));
ALTER SEQUENCE tablename_colname_seq OWNED BY tablename.colname;
```

【事实】**identity 是 SQL 标准写法**，序列是**隐式**的：

```sql
CREATE TABLE people (
  id bigint GENERATED ALWAYS AS IDENTITY   -- 或 GENERATED BY DEFAULT
);
```

| | `serial` / `bigserial` | `GENERATED ... AS IDENTITY` |
|---|---|---|
| 本质 | **语法糖**：显式建 sequence + 设默认值 + `OWNED BY` | SQL 标准，**隐式序列**，随表走 |
| 防误插 | **无**。任何人可以显式写一个值进去 | **`ALWAYS` 模式下，显式值必须写 `OVERRIDING SYSTEM VALUE` 才被接受**；`BY DEFAULT` 则允许覆盖 |
| 改自增属性 | 要去动那个 sequence 对象 | `ALTER TABLE ... ALTER COLUMN ... RESTART / SET GENERATED` |
| 结论 | 能用，属于**历史写法** | **新表用这个** |

【纠正常见误解】**identity 不等于唯一**——官方原文：

> **identity 列会自动标记为 `NOT NULL`。但 identity 列不保证唯一。**
> （序列通常返回唯一值，但序列可以被重置，值也可以被手工插入。）

**所以 `PRIMARY KEY` / `UNIQUE` 还是必须写。**「用了 identity 就有唯一主键」是错的。

【纠正常见误解】**自增列会有洞，删了行也不影响这个结论**——官方原文：

> **因为 `smallserial` / `serial` / `bigserial` 是用序列实现的，即使一行都没删，列里的值也可能出现「空洞」**：**一个从序列分配出去的值，即使包含它的行从未成功插入，也已经被用掉了**——比如插入事务回滚。

**所以「主键不连续」不是 bug，是设计。** identity 用的也是序列，同样有洞。

【推导】**UUID 主键的代价落点，PG 和 MySQL 完全不同——这是最值钱的一段**

```text
InnoDB（MySQL）：二级索引的叶子存【主键】
  → 主键越宽，【每一个二级索引】都跟着变宽
  → 例：表有 6 个二级索引，UUID 主键让 6 个索引全部变胖

PostgreSQL：二级索引的叶子存【ctid】（6 字节定长）
  → 主键宽度【只影响主键索引自己】
  → 除非你把这个 UUID 也放进别的索引（那才按个数重复）

再算宽度（索引项 = 8B header + 键 + 6B ctid）：
  bigint 键：8 + 8 + 6 = 22 → 对齐 24B → 8000 万行 ≈ 1.92 GB
  UUID  键：8 + 16 + 6 = 30 → 对齐 32B → 8000 万行 ≈ 2.56 GB
  → 单个索引多约 33%
```

【结论】**PG 里 UUID 主键的代价是两条，且都不在堆上**：

1. **索引宽度的代价**（上面算的 33%）——**但它不摊到别的索引上**（这与 InnoDB 相反）；
2. **索引插入变随机**——**堆本身无序，插入永远是追加，所以没有「页分裂」这个问题**；**但索引是有序结构**，随机 UUID 会让索引插入变成随机写、页分裂与缓存局部性差。**代价转移到索引上。**

**所以正确说法是**：「**PG 里 UUID 的代价不在堆、在索引；而且宽度代价不会像 InnoDB 那样摊到每个二级索引上。**」**能说出这个区别，就是真的理解了两边的存储结构**（[[母题-P2-堆表与回表]]）。

【取舍】**如果确实需要分布式唯一 ID**：**有序化**的 UUID（时间有序的版本）能把「索引随机写」这一条压下去——**这是当下比较主流的折中**；**但它压不掉宽度那一条**。

**到这里你应该能回答**：为什么「UUID 主键会让所有索引都变大」这句话，在 MySQL 里对、在 PG 里不对？

### 4. 时间：timestamptz 是默认答案

【事实】**官方口径**：

> **带时区的值在内部一律按 UTC 存储，原来声明的或假定的那个时区【不会被保留】。**

| | `timestamp`（不带时区） | `timestamptz`（带时区） |
|---|---|---|
| 存什么 | 字面的日期时间，**没有时区语义** | **UTC 瞬时点**（8 字节，微秒精度） |
| 显示 | 原样返回 | 按当前会话的时区**换算显示** |
| 写入 | 不做换算 | 按会话时区换算成 UTC 存储 |

**为什么 PG 建议 `timestamptz`**：因为绝大多数业务时间是**瞬时点**（这条记录什么时候发生的），瞬时点必须有一个明确的时区基准才能比较、排序、跨地区展示正确。**用 `timestamp` 存瞬时点，等于把「解释权」留给读它的人——同一个值在不同时区看到不同的「现在」。**

【纠正常见误解】**「带时区」不是「记住它是哪个时区的」**——**它存的就是 UTC 时刻，只是读写时自动做会话时区换算。** **被追问时能说这一句，会显得非常扎实。**

【推导】**`timestamp` 在夏令时切换时会真的坏掉**：

```text
夏令时回拨的那一小时里，同一个【本地墙上时间】会出现两次：
  01:30（夏令时）和 01:30（标准时）—— 相差一小时，是【两个不同的瞬时点】

timestamp（不带时区）只存字面值：
  两条记录的 01:30 一模一样
  → 无法区分先后 → 【排序会错、去重会误合并、时长会算成 0】
```

**这不是 PG 的缺陷，是「不带时区的时间戳」这个语义本身表达不了这件事。** 所以周期性运维时间表（夜班交接、跨园区巡检）必须落在 `timestamptz` 上。

【取舍】**什么时候用 `timestamp`**：语义确实是「本地墙上时间」，**且那个本地无关时区**——比如「每天 09:00 开门」这种排班规则（它描述的是钟表读数，不是时刻）。**一旦要问「这两件事谁先发生」，就必须是 `timestamptz`。**

**到这里你应该能回答**：为什么「我们只在国内，不用管时区」不足以成为用 `timestamp` 的理由？

### 5. 回到题目：完整 DDL 与逐字段理由

```sql
CREATE TABLE agent_inputs (
  id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id    bigint NOT NULL,
  user_input   text   NOT NULL,                       -- 纯文本：无上限就用 text
  config       jsonb  NOT NULL DEFAULT '{}'::jsonb,   -- 要被查 → jsonb + 可选 GIN
  created_at   timestamptz NOT NULL DEFAULT now(),    -- 瞬时点 → timestamptz
  updated_at   timestamptz NOT NULL DEFAULT now()
) WITH (fillfactor = 90);                             -- 高频更新 → 给 HOT 留空间（P4）
```

| 字段 | 选择 | 理由（一句） |
|---|---|---|
| `user_input` | `text` | 没有业务长度上限时，加限制只换来「以后要改 DDL」 |
| `config` | `jsonb` | **它会被查**；同时接受「键序不保证、重复键被去掉」这个规范化 |
| `id` | `identity` | SQL 标准；而且 `ALWAYS` 能挡住手写主键 |
| 时间戳 | `timestamptz` | **时间戳是瞬时点**；跨时区、夏令时都不会坏 |
| `fillfactor` | 90 | `updated_at` 会被频繁改；**若它不进任何索引，就有机会走 HOT** |

【取舍】**这张表里唯一需要慎重的是 `fillfactor`**：**它只在「高频更新 + 更新的列不在索引里」时才划算**（[[母题-P4-索引代价与在线建索引]]）；**只读表填满（100）才对。**

### 6. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「`varchar` 比 `text` 快」 | **PG 里两者存储与开销完全相同**；`varchar(n)` 只是多一次长度检查 |
| 「`char(n)` 定长所以更快」 | **反了**，官方说它**通常是三者中最慢的** |
| 「用了 identity 就有唯一主键」 | **identity 只保证 NOT NULL，不保证唯一**，PK/UNIQUE 还得写 |
| 「主键不连续是 bug」 | **自增用序列实现，回滚也消耗值**；有洞是设计，不是故障 |
| 「UUID 会让所有索引变大」 | **那是 InnoDB 的行为**（二级索引叶存主键）；**PG 的二级索引叶存 ctid**，不摊开 |
| 「timestamptz 会记住原来的时区」 | **不保留**，只存 UTC；「带时区」= 自动做会话时区换算 |
| 「`enum` 加值要重建表」 | **PG 12+ 后 `ALTER TYPE ... ADD VALUE` 已经是轻量操作**（见追问 5） |

## 二、自测

**Q1（计算）**：某表有一个 `char(200)` 字段，实际存的内容平均 3 个字符。表 2000 万行。

问：**这个字段比用 `text` 多占多少空间？**为什么官方说 `char(n)`「通常是最慢的」？

**A1**：

```text
char(200)：定长补空格 → 每行 200 字节
text     ：1 字节头 + 3 字节内容 = 每行 4 字节

倍率：200 ÷ 4 = 【50 倍】
总量：2000 万 × (200 − 4) ≈ 【3.7 GB】的纯浪费
```

【结论】**50 倍，而且这 50 倍要付两次**：**一次付在磁盘与缓冲区上**（IO 更多），**一次付在每次读写的空格补齐/裁剪上**（CPU）——**官方那句「通常是最慢的」就是这两笔账的结论。**

【推论】**判据**：

> **在 PG 里，定长不是优化，是负债。** 任何「用 `char(n)` 让存储对齐」的想法，在 PG 的变长存储实现下都不成立。

**Q2（计算）**：`varchar(255)` 与 `text` 两列，都存一个 20 字符的字符串，各占多少字节？这个数字能说明什么？

**A2**：

```text
官方给出的头部开销：
  长度 ≤ 126 字节 → 1 字节头
  长度 >  126 字节 → 4 字节头

存 20 字符：
  varchar(255) = 1 + 20 = 【21 字节】
  text         = 1 + 20 = 【21 字节】
```

【结论】**完全相同。** ——这就是「PG 里 text 与 varchar 没有性能差别」这句话的算术版本。**它俩的存储、拷贝、比较成本一模一样，`varchar(n)` 只多做一件事：写入时比一下 n。**

【推论】**所以 `varchar(n)` 是一个【纯约束】，不是一个【优化】。** ——**要用它，理由必须是「业务上确实有上限」，不能是「感觉更规范」或「听说更快」。**

【补充】**阈值 126 是同一套实现里的分界**：**两者都跨过这条线时一起变成 4 字节头**——**所以「长度超过 126 后 varchar 会比 text 多花钱」也是错的。**

**Q3（计算）**：8000 万行的表，主键从 `bigint` 换成 `uuid`。

问：**主键索引大约变胖多少？在 PG 里，其他二级索引会跟着变胖吗？为什么？**

**A3**：

```text
索引项 = 8B 元组头 + 键 + 6B ctid

bigint 键：8 + 8 + 6 = 22 → 对齐 24 字节
  → 8000 万 × 24 B ≈ 【1.92 GB】
uuid   键：8 + 16 + 6 = 30 → 对齐 32 字节
  → 8000 万 × 32 B ≈ 【2.56 GB】
  → 单个索引多约 【33%】（+640 MB）
```

【关键在第二问】**PG 的二级索引叶子存的是 `ctid`（6 字节定长），不是主键。所以主键变宽【不会】摊到其他二级索引上。**

```text
对照 InnoDB：二级索引叶存【主键】
  → 主键 16 字节时，6 个二级索引各多 8 字节/行
  → 代价是【乘索引个数】的

PG：二级索引叶存【ctid】
  → 代价只落在【主键索引自己】身上
  → 除非你把这个 UUID 也放进了别的索引（那才按个数重复）
```

【结论】**PG 里 UUID 的宽度代价是一次性的，不是乘法的。**

【推论】**但 UUID 主键在 PG 里仍有另一笔更大的代价**：**索引是有序结构，随机 UUID 让索引插入变成随机写**——**而堆是无序的，插入一直是追加，所以没有「页分裂」问题**。**代价从堆转移到了索引。**

【取舍】**时间有序的 UUID 能压掉「随机写」这一条，压不掉「宽度」这一条。** **两笔账要分开说，不要混成一句「UUID 慢」。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们主键用了 `bigserial`，所以自增、唯一、非空都有了，不用再写约束。"

**A4**：三处问题。

1. **`serial` / `bigserial` 不是类型，是语法糖**：官方展开是 `CREATE SEQUENCE` + `DEFAULT nextval(...)` + `OWNED BY`。**它只做了一件事：给一个默认值。**
2. **唯一性它一点都没给**：**`serial` 展开里只有 `NOT NULL`，没有 `UNIQUE`**（官方原文明确说「大多数情况下你还会想加 `UNIQUE` 或 `PRIMARY KEY`，但这不是自动的」）。**identity 也一样——官方原文：「identity 列不保证唯一」。**
3. **主键还会不连续**：**序列分配出去的值，即使插入回滚也已经被用掉了**——**有洞是设计，不是 bug。**

【准确说法】"**自增、非空、唯一是三件事，`serial` 只给了前两件。** **新表我会写 `bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`——`identity` 是 SQL 标准写法、序列隐式随表走，`ALWAYS` 还能挡住手工写主键；但 `PRIMARY KEY` 那四个字仍然必须写。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "时间字段统一用 `timestamp` 就行。我们业务只在国内，没有时区问题，用了 `timestamptz` 反而要在应用层转来转去。"

**A5**：三处问题。

1. **「只在国内」挡不住两类问题**：**跨时区的部署与客户端**（容器时区、CI、运维终端、海外用户）**和夏令时**（**中国现在不用夏令时，但「服务器时区」不一定设成 `Asia/Shanghai`**）。**时区问题不是「你在哪」，是「谁在读这个值」。**
2. **`timestamp` 在语义上就表达不了「瞬时点」**：它存的是字面值，**没有任何东西告诉你这个字面值是按哪个时区写的**。**读的人只能靠默契。**
3. **「应用层转来转去」恰恰是 `timestamptz` 帮你省掉的**：**`timestamptz` 存 UTC、按会话时区自动显示**——应用不需要自己算偏移；**反而是 `timestamp` 逼着应用层去猜。**

【准确说法】"**判据是「这个字段是瞬时点还是墙上时间」**：**是瞬时点（什么时候发生）→ `timestamptz`；确实是墙上时间（每天 09:00 开门，与时区无关）→ `timestamp`。** **绝大多数业务时间字段是前者，所以默认答案就是 `timestamptz`。**"

## 三、面试输出（学完再看）

**一句话结论**：PG 里**类型选择的第一原则是语义，不是性能**——**因为「性能」那一项是可以算的，而且算出来往往一样**：**`text` 与 `varchar(n)` 的存储完全相同**（≤126 字节时都是 1 字节头，20 字符的字符串各占 21 字节），**`varchar(n)` 唯一多做的是写入时比一下 n，所以它是【纯约束】不是【优化】**；**而 `char(n)` 是三者中最慢的**（定长补空格，`char(200)` 存 3 个字符要 200 字节，是 `text` 的 **50 倍**）。**JSON 的判据是一句话：会被查就用 `jsonb`**（二进制、可建 GIN、但要接受键序不保证、重复键被去掉），**只有「原样保存原样取出」是需求本身时才用 `json`**。**主键写 `bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY`**——**identity 是 SQL 标准、序列隐式随表走，`ALWAYS` 能挡住手写主键**；**但要注意 identity 只保证 NOT NULL、不保证唯一**，而且**自增列一定会有洞**（序列分配出去的值回滚了也已经被用掉）。**UUID 的代价在 PG 里落在索引、不在堆**：堆是无序的、插入永远是追加，**代价是索引插入变随机 + 索引宽 33%（1.92 GB → 2.56 GB）**；**而且因为 PG 的二级索引叶存的是 `ctid` 而不是主键，这个宽度代价不会摊到其他索引上——这一点和 InnoDB 正好相反**。**时间一律 `timestamptz`**：**它内部一律存 UTC、原来那个时区不会被保留**，「带时区」的准确含义是**自动做会话时区换算**。

**恢复关键词**：**没有性能差别**（官方口径）/ 1 字节头 ≤126 字节 / 20 字符 = 21 字节（两者相同）/ **`varchar(n)` 是纯约束** / `char(n)` 最慢（50 倍）/ **会被查就用 jsonb** / json 保原文·键序·重复键 / **identity：自动 NOT NULL、【不保证唯一】** / serial 展开三条语句 / **自增有洞是设计** / **UUID：代价在索引不在堆** / 索引宽 33%（1.92→2.56 GB）/ **PG 二级索引叶存 ctid → 宽度不摊开（与 InnoDB 相反）** / **timestamptz 存 UTC、不保留原时区** / `timestamp` 表达不了瞬时点

**核心不变量 / 主线**：
**类型选择不是「哪个性能好」，而是「哪个语义对」。**
**唯一的例外是 `char(n)` 与 JSON 选型**：前者有实打实的空间与 CPU 代价，后者直接决定「能不能建索引」。

**完整回答骨架**：文本类型（算 21 vs 21、算 50 倍）→ **JSON 两种类型的选择判据** → **主键：identity 与它不保证的两件事（唯一、连续）** → **UUID 代价落在哪（算 1.92 → 2.56 GB，并说清为什么不摊开）** → 时间的时区语义 → 回到建表给完整 DDL → 收束到「先问语义」

**追问**（先说后看）

1. **jsonb 存的配置项想做范围查询怎么办？** —— 两条路：① **表达式索引**把某个内部字段抽出来（`(data->>'priority')`）建 B-tree；② **如果被查询字段是核心业务字段，就把它提升成独立列**——**「能被高频查询的字段不该藏在 JSON 里」**，**这是比建索引更根本的建议**。
2. **改了字段类型会不会锁表？** —— `ALTER COLUMN TYPE` **通常会重写整表**（危险）；但**扩大长度、加/去掉 varchar 的长度限制在 PG 里是不重写的**。所以「想加长字段」不需要紧张，**而「改存的是什么」必须排窗口**——**这条又回到 P4 的「区分加列与改列」。**
3. **PG 用 `numeric` 还是 `float` 存金额？** —— **`numeric`**。官方定义里 **`numeric` 是「用户指定精度、精确」**，而 **`real` / `double precision` 是「变精度、不精确」**（分别约 6 / 15 位十进制有效数字）。**浮点是二进制近似，金额会出现比较与累加误差。** **这条在 MySQL 里也是同一答案，属于跨栈通用。**
4. **`NULL` 在唯一约束里怎么算？** —— **PG 里 `NULL` 彼此不相等**，所以 `UNIQUE` 列允许多行 `NULL`。**这正是 P19「唯一约束做幂等防线」要注意的地方**：**作为幂等键的列必须 `NOT NULL`**（[[母题-P19-唯一约束与UPSERT]]）。
5. **枚举用 `enum` 还是 `varchar` + `CHECK`？** —— `enum` 紧凑、约束强、**而且有序**（枚举值的顺序就是定义顺序，可以直接比较大小）；`varchar + CHECK` 更灵活。**关键事实：PG 12+ 之后 `ALTER TYPE ... ADD VALUE` 已经是轻量操作**（还能指定 `BEFORE` / `AFTER` 插到中间），**「加值要重建表」是过时说法**。

**同类变体**

- 「PG 的表设计和 MySQL 差在哪？」——**四个点**：① `varchar` 无性能优势（MySQL 有定长/变长差别）；② JSON 有 `json` / `jsonb` 两种（MySQL 只有一种原生 JSON）；③ 自增有 identity 这个 SQL 标准写法；④ `timestamptz` 的时区语义（**MySQL 的 `TIMESTAMP` 还有 2038 上限，PG 的 `timestamptz` 没有**——[[母题-M5-引擎与表设计基本盘]]）。
- 「主键用自增还是 UUID？」——**先问「这个 ID 会不会出现在 URL 里」**（自增会泄露业务量与增长节奏）**和「要不要跨库合并」**；**两个都否，就用 identity**（宽度减半、索引顺序写）；**要跨库，再考虑时间有序的 UUID**。
