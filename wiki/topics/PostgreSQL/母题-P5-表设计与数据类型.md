# 母题 P5 · 表设计与数据类型

> **模块**：PostgreSQL / 索引与表设计
> **所属主线**：一 · 索引与表设计（怎么让查询不用扫全表，表怎么建才不埋雷）
> **关联母题**：[[母题-P1-索引类型选型]]（jsonb 为什么能建 GIN）· [[母题-P17-乐观并发控制]]（version 列的类型）
> **素材来源**：`study/09-数据缓存队列与一致性` 第 7 节（Agent 长任务数据模型）+ 三个项目真实建表 + 通用知识（**类型细节待你核对**）

**题目**：给一张新的业务表定字段：一个存放用户输入的文本字段、一个结构不固定的配置项、一个主键、两个时间戳。每项怎么选，为什么？

**母题**：PG 里 text 与 varchar、jsonb 与 json、serial 与 identity、timestamptz 怎么选？

**为什么重要**：这是**最不起眼但最容易被追问到底**的一类题。它不难，但**PG 的答案和 MySQL 的答案在四个点上都不一样**（varchar 的性能差异、JSON 的两种类型、自增的实现、时间的时区语义）。**答成 MySQL 那一套，等于白做三个 PG 项目。**

**一句话结论**：PG 里 **text 与 varchar(n) 性能没有差别**（同一套变长存储），所以选哪个是**语义选择**——要长度约束才用 `varchar(n)`；**jsonb 存解析后的二进制、可建 GIN 索引，json 存原始文本、保留格式与键序**，要查就用 jsonb；主键用 **`GENERATED ... AS IDENTITY`**（SQL 标准，权限与归属清楚），`serial` 是历史写法；**时间一律 `timestamptz`**（存 UTC 瞬时点，按会话时区显示），`timestamp` 只用于「就是本地墙上时间」的语义。

**恢复关键词**：text = varchar（无性能差）/ varchar(n) 只做校验 / jsonb 可索引 vs json 保原文 / identity vs serial / timestamptz 存瞬时点 / UUID 的索引代价在索引不在堆

**核心不变量 / 主线**：
**类型选择不是「哪个性能好」，而是「哪个语义对」。** 长度约束、时区语义、结构固定性、唯一性来源——**先把语义说清，性能差异在 PG 里往往小到不值得作为第一理由。**

**完整回答骨架**：文本类型（无性能差，只有语义差）→ JSON 两种类型的选择判据 → 主键（identity / UUID 的真实代价）→ 时间（时区语义）→ 回到建表给完整 DDL

## 原理分解

### 一、text vs varchar vs char

| 类型 | 存储 | 约束 |
|---|---|---|
| `text` | 变长，超长自动 TOAST 外置 | 无长度限制 |
| `varchar(n)` | **同一套变长机制** | 超过 n 报错 |
| `char(n)` | 定长补空格 | 定长，**在 PG 里几乎没有理由用** |

**关键结论**：**`text` 和 `varchar` 在 PG 里性能相同**——底层是同一套变长实现，长度前缀的开销一样。

**所以选择标准是语义**：

- 业务上确实有长度上限（比如「手机号最多 20 字符」）→ 用 `varchar(n)`，**让数据库替你守住这个约束**；
- 只是「文本」→ 用 `text`。

**这正是「为什么 PG 圈里很多人直接用 text」的原因**——不是图省事，而是**没有约束需求时，加一个长度限制只会带来「以后要放宽还得改 DDL」的麻烦**。

> MySQL 那边 `varchar` 与 `char` 有明确的定长/变长性能差别，`varchar` 还有额外的长度字节；**PG 里这套说法不成立**，别混着讲。

### 二、json vs jsonb：判据是「要不要查」

| | `json` | `jsonb` |
|---|---|---|
| 存储 | **原始文本** | **解析后的二进制结构** |
| 保留 | 格式、空格、**键的顺序**、重复键 | 规范化：去掉空格、**键序不保证**、去重复键 |
| 写入 | 快（只存字符串） | 稍慢（要解析） |
| 查询 / 索引 | **不能建 GIN 索引**，取字段要现场解析 | **可建 GIN**，支持 `@>`、`?`、`->` 等操作符 |
| 典型用途 | 审计、留痕、**原样回传** | **要按内部字段过滤/检索** |

**一句话判据**：**只要会被「查」，就用 jsonb。** 只有当「原样保存、原样取出」是需求本身（比如司法级留痕、要把用户原始请求原封不动还回去）时才用 json。

**注意它的连锁效应**：选 jsonb → 可以建 GIN（见 P1）；选 json → 只能整列全表扫。**所以这个字段类型的选择直接决定索引能不能做。**

### 三、主键：identity vs serial，以及 UUID 的真实代价

| | `serial` / `bigserial` | `GENERATED ... AS IDENTITY` |
|---|---|---|
| 本质 | **语法糖**：隐式创建 sequence 并设为默认值 | SQL 标准写法 |
| 权限 | **序列的 owner 是建表者**，权限模型容易出问题（换 owner、迁移时常见坑） | 序列归表所有，**随表权限走** |
| 等价写法 | `id bigserial` | `id bigint GENERATED ALWAYS AS IDENTITY` |
| 结论 | 能用，但属于**历史写法** | **新表用这个** |

**UUID 主键的代价，PG 版和 MySQL 版不一样，这点必须讲清：**

- **MySQL（InnoDB）**：主键即数据，随机主键会插到 B+ 树中间 → **页分裂 + 顺序写变随机写**。
- **PG（堆表）**：**堆本身无序，插入永远是追加**，所以**没有「页分裂」这个问题**；但代价转移到两处——① **索引仍然是 B-tree（有序结构）**，随机主键让索引插入变成随机写、页分裂与缓存局部性差；② **UUID 是 16 字节，`bigint` 是 8 字节**，而 PG 的联合索引叶子会重复存键值，**宽度会摊到每个索引上**。

**所以正确说法是**：「PG 里 UUID 的代价不在堆、在索引，另外就是宽度。」**能说出这个区别，就是真的理解了两边的存储结构。**

> 如果确实需要分布式唯一 ID，**有序化**的 UUID（UUIDv7 这类时间有序版本）能把索引随机写的问题压下去——这是当下比较主流的折中。

### 四、时间：timestamptz 是默认答案

| | `timestamp`（不带时区） | `timestamptz`（带时区） |
|---|---|---|
| 存什么 | 字面的日期时间，**没有时区语义** | **UTC 瞬时点** |
| 显示 | 原样返回 | 按当前会话的时区**换算显示** |
| 写入 | 不做换算 | 按会话时区换算成 UTC 存储 |

**为什么 PG 建议 `timestamptz`**：因为绝大多数业务时间是**瞬时点**（这条记录什么时候发生的），瞬时点必须有一个明确的时区基准才能比较、排序、跨地区展示正确。**用 `timestamp` 存瞬时点，等于把「解释权」留给读它的人——同一个值在不同时区看到不同的「现在」。**

**什么时候用 `timestamp`**：语义确实是「本地墙上时间」，比如「每天 09:00 开门」这种**与时区无关的排班**。

**一个实用细节**：`timestamptz` 也不存时区名，它存的就是 UTC 时刻；**「带时区」的准确含义是「自动做会话时区换算」**，而不是「记住它是哪个时区的」。**被追问时能说这一句，会显得非常扎实。**

## 二、扩展：类似题与追问

**类似题**

1. 「PG 用 `numeric` 还是 `float` 存金额？」——**`numeric`**。浮点是二进制近似，金额会出现比较与累加误差。**这条在 MySQL 里也是同一答案，属于跨栈通用。**
2. 「枚举用 `enum` 还是 `varchar` + `CHECK`？」——`enum` 紧凑、约束强，但**加值要改类型**（历史上有重建表的代价）；`varchar + CHECK` 更灵活。**PG 12+ 后加 enum 值已经是轻量操作**，可以据此选。
3. 「`NULL` 在唯一约束里怎么算？」——**PG 里 `NULL` 彼此不相等**，所以 `UNIQUE` 列允许多行 `NULL`。**这正是 P18「唯一约束做幂等防线」要注意的地方**：作为幂等键的列必须 `NOT NULL`。

**追问链**

- 追问一层：**「jsonb 存的配置项想做范围查询怎么办？」**——两条路：① 表达式索引把某个内部字段抽出来（`(data->>'priority')`）建 B-tree；② 如果被查询字段是**核心业务字段**，就**把它提升成独立列**——**「能被高频查询的字段不该藏在 JSON 里」**，这是比建索引更根本的建议。
- 追问二层：**「改了字段类型会不会锁表？」**——`ALTER COLUMN TYPE` 通常会**重写整表**（危险）；但**扩大长度、加/去掉 varchar 的长度限制在 PG 里是不重写的**。所以「想加长字段」不需要紧张，而「改存的是什么」必须排窗口。**这条又回到 P4 的「区分加列与改列」。**
