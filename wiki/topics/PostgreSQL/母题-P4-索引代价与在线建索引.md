# 母题 P4 · 索引代价与在线建索引

> **模块**：PostgreSQL / 索引与表设计
> **所属主线**：一 · 索引与表设计（怎么让查询不用扫全表，表怎么建才不埋雷）
> **层级**：B · 标准级（三项代价与阻塞时长能算；但 CONCURRENTLY 的等待条件、INVALID 的处置是规则型的，所以不是 A）
> **关联母题**：[[母题-P3-部分索引与表达式索引]]（把索引做小是减负的第一手段）· [[母题-P14-长事务与表膨胀]]（长事务会让 CONCURRENTLY 一直等）· [[母题-P15-VACUUM与事务ID回卷]]（第三项代价的底部原因）· [[母题-P5-表设计与数据类型]]（HOT 要给页留空间）
> **素材来源**：`study/09-数据缓存队列与一致性` 第 3.1 节（索引代价含 vacuum 压力）+ **PostgreSQL 官方文档 CREATE INDEX / HOT**（2026-09-13 联网核实）+ 通用知识。**三组算式与 HOT 那一段为本次新增（待你核对）**

**导读**：必懂 3 件事（① PG 的索引代价比 MySQL 多一项：VACUUM 压力 ② `CONCURRENTLY` 不是「更聪明的锁」，是「换了一套做法」 ③ 它失败会留下**不报错但纯负债**的 INVALID 索引）· 读完约 12 分钟 · 需要先懂：[[母题-P2-堆表与回表]]

**题目**：线上 8000 万行的表要加一个索引。你直接执行 `CREATE INDEX idx_x ON big_table (col)`。会发生什么？换成 `CREATE INDEX CONCURRENTLY` 就安全了吗？

**母题**：索引的代价是什么（PG 版）？`CREATE INDEX CONCURRENTLY` 有什么坑，失败了怎么办？

**为什么重要**：MySQL 那边这条主线的关键词是「MDL 连锁」；**PG 这边换成了另一套机制**——不阻塞写、但会留下**静默的 INVALID 索引**。这是同一个问题的两种形态，**能不能分别讲清，是判断你有没有真的在两套库上操作过的分水岭**。而且它承接 P3：**索引不是越多越好，PG 里还多一条理由。**

**一句话结论**：PG 里索引的代价有三项——**写放大 / 空间 / VACUUM 与缓存压力**（第三项是 PG 特有的，也是它在索引数量上比 MySQL 更保守的原因）；`CREATE INDEX CONCURRENTLY` 做到了**不长时间阻塞写入**，代价是**不能在事务里跑、要扫两遍表所以更慢、失败会留下 INVALID 索引**——那个索引**不报错、但照样占空间并拖慢写入，必须手动 DROP 再重建**。

**恢复关键词**：写放大 / 空间 / vacuum 压力 / HOT 与 fillfactor / CONCURRENTLY 不能在事务内 / 两遍扫描 / INVALID 索引 / 幂等重建脚本

**核心不变量 / 主线**：
**在线变更安全的判据不是「它快不快」，而是「失败之后系统停在一个什么状态、以及这个状态是否可见」。** MySQL 的答案是「看不见的队列堵住一切」，PG 的答案是「看得见但不报错的无效索引」——**两次都是「静默」最危险。**

**完整回答骨架**：索引的三项代价（PG 版）→ 直接建索引会堵什么 → CONCURRENTLY 的机制 → 三个坑 → 失败后的正确处理 → 工程流程

## 一、教材

### 1. 索引的三项代价（PG 版，第三项是重点）

::figure pg-online-index.svg | 在线建索引：两遍扫描换掉长锁，代价是失败会留下静默的无效索引 | 直接建索引的锁与阻塞、CONCURRENTLY 的两遍扫描状态机、失败留下的 INVALID 索引、以及 HOT 与索引数量的关系

| 代价 | 表现 |
|---|---|
| **写放大** | 每次 `INSERT` 要在堆里插行并更新**每一个**索引；PG 的 MVCC 让 `UPDATE` = 插入新版本 + 标记旧版本，**所以一次更新会同时写堆和所有索引** |
| **空间** | 索引独立文件，叶子存键值 + ctid；联合索引叶子存**所有索引列的值**（比 InnoDB 只存主键更大） |
| **VACUUM 与缓存压力** | 每个索引都是一棵要清理的树：**autovacuum 要遍历的索引页变多、清理变慢、膨胀更难被自动控制**；同时索引页争抢 shared_buffers |

**第三项是回答「PG 里索引是不是越多越好」的关键**。MySQL 的答案通常停在「写放大 + 空间」；**PG 必须多一句「它让 VACUUM 更难跟上」**——这句话直接连到 [[母题-P15-VACUUM与事务ID回卷]]。

【推导】**把写放大算成数字**：设表上有 k 个索引，某次 `UPDATE` 改了至少一个被索引引用的列——

```text
写元组数 = 1（堆里的新版本）+ k（每个索引各一条新项）
```

k = 6 时是 **7 次元组写**，其中 **6/7 ≈ 86% 花在索引上**。**索引不是"附带的"成本，它是写路径上的主要成本。**

**到这里你应该能回答**：为什么「加个索引又不占多少空间」这个说法，在写入密集的表上是站不住的？

### 2. HOT：PG 给写放大留的一条免费通道【事实】

PG 有一个 MySQL 没有的优化——**HOT（Heap-Only Tuple）**：

> **如果这次 `UPDATE` 改的列【不在任何索引里】，而且新版本能放进【同一张页】，PG 就直接在页内链一个新版本，一个索引都不用碰。**

（严格说：排除 BRIN 这类「摘要索引」——核心发行版里唯一的摘要索引就是 BRIN。）

【事实】**HOT 给两样东西，第二样常被漏掉**（官方文档原文的两条）：

| 收益 | 说明 |
|---|---|
| **不写新索引项** | 更新后的行不需要新的索引条目（摘要索引仍可能要更新） |
| **中间版本可以就地清理** | **一行被更新多次时，除最旧和最新之外的中间版本，可以在【正常运行期间（包括 `SELECT`）】被直接移除**，不必等 VACUUM——索引永远指向原始行版本的页内位置，那条规定被改成一个指向"仍可能可见的最旧版本"的重定向 |

**第二条直接连着主线五**：**HOT 越多，VACUUM 的欠账越少，表膨胀越慢**（[[母题-P14-长事务与表膨胀]]）。

【推导】**这直接改变了「该不该把某列放进索引」的判断**：

```text
updated_at 被 3 个索引引用：
  每次更新 → 写 1 个堆元组 + 3 个索引项 = 4 次元组写

updated_at 不被任何索引引用 + 页内有空间：
  每次更新 → 走 HOT → 写 1 个堆元组 + 0 个索引项 = 1 次元组写
```

**4 倍差距。** 这也解释了为什么 PG 里**把「经常被更新的列」放进索引是一个要慎重权衡的动作**——它不是多占一点空间，而是**永久关掉了这条更新路径的 HOT**。

【事实】**第二个条件（页内有空间）可以手动提高概率**：

```sql
CREATE TABLE attack_run (...) WITH (fillfactor = 90);
```

**`fillfactor` 默认 100（完全填满）**，取值 10–100。调小它 = **`INSERT` 只把页填到指定比例，剩下的空间专门留给「在本页更新行」**。

【纠正常见误解】**不调 fillfactor 不等于没有 HOT**——官方文档明确说：**新版本会自然地流向新页、已有页空出来时也会接纳新版本，所以 HOT 仍会发生**。**`fillfactor` 是「提高概率」，不是「开关」。**

【取舍】**HOT 也有代价**：页只填 90% → 同样的行数要多占约 **11%** 的页（1/0.9）→ 表更大、顺序扫描要读更多页。**官方给的口径很清楚：从不更新的表，填满才是最优；只有【高频更新】的表才该调小 fillfactor。** 所以它是「用顺序读换随机写」的交易。

【事实】**能不能验证？能**——`pg_stat_all_tables` 里可以同时看到 **HOT 更新与非 HOT 更新的次数**：

```sql
SELECT relname, n_tup_upd, n_tup_hot_upd,
       round(100.0 * n_tup_hot_upd / nullif(n_tup_upd, 0), 1) AS hot_pct
FROM pg_stat_all_tables WHERE relname = 'attack_run';
```

**「该不该为这张表调 fillfactor」这个问题，不需要猜——查一下 hot_pct 就有答案。**

**到这里你应该能回答**：为什么「多建一个索引」的影响，会比它的体积看起来大得多？

### 3. 直接建索引会堵什么

普通 `CREATE INDEX` 会**在整张表上持有一个较轻的锁（SHARE）**：它允许其他会话**读**，但**阻塞所有写入**（`INSERT` / `UPDATE` / `DELETE`）。

对 8000 万行的表，这意味着：

```
建索引耗时（分钟级到小时级）
  ↓
这段时间内所有写请求排队等待
  ↓
连接池被占满
  ↓
上层接口开始超时 → 雪崩
```

**机制和 MySQL 完全不同（PG 没有 MDL 那套连锁，这里是直接的写锁），但后果一样：不是 DDL 本身慢，是它把后面的写入堵成一条越来越长的队。**

【推导】**把堵塞算成数字**（口径写在算式里）：

```text
表：8000 万行 × 200 字节 = 16 GB
页：16 GB ÷ 8 KB ≈ 200 万页

建索引要扫一遍全表 + 排序 + 写索引，15 分钟量级（含 WAL，非纯 IO 时间）
写流量：500 TPS
  → 阻塞期间积压写入 = 15 × 60 × 500 = 【45 万次】

这 45 万次不是「慢一点」，是【全部排队】
连接池 100 条连接被写请求占满
  → 读请求也拿不到连接 → 故障从「写变慢」升级成【整站不可用】
```

**真正致命的从来不是 15 分钟，是从「写排队」到「连接池耗尽」这一步。**

### 4. CONCURRENTLY 怎么做到不阻塞

**先把对照组说准**：普通 `CREATE INDEX` 是**「在整张表上挡住写，然后【一次扫描】把索引建完」**。CONCURRENTLY **要扫【两次】**表，而且**每次扫描前后都要等**——这才是它的机制。

**精确的三段式**（官方文档口径）：

```text
① 在系统表里，把索引以一个【invalid（无效）】的身份登记进去   ← 一个事务
② 第一次全表扫描：【建索引】                                  ← 一个事务
     开始前：等所有【改过这张表】的事务结束
③ 第二次全表扫描：【把构建期间新增/修改的行补进来】            ← 一个事务
     开始前：同样等改过这张表的事务结束
     结束后：再等所有【快照早于第二次扫描】的事务结束
④ 标记为 valid（有效），命令结束
```

【推论】**注意 ①——它一开始就是「无效索引」**。这解释了后面那个最危险的坑：**失败时不需要"制造"一个无效索引，它本来就在那儿，只是没被改回有效。**

| 坑 | 说明 |
|---|---|
| **不能在事务块里执行** | 它需要跨多个事务/多遍扫描，所以 `BEGIN ... CREATE INDEX CONCURRENTLY ... COMMIT` 会直接报错。**迁移脚本里最常见的翻车点。** |
| **更慢、占用更多资源** | 扫两遍表、等待所有并发事务结束；期间 CPU / IO / WAL 压力显著上升，**必须避开业务高峰**。 |
| **失败会留下 INVALID 索引** | 这一步没有回滚——**失败后索引对象仍然存在，只是停留在 invalid 状态**。 |
| **等待期可能很长** | 它要等所有可能看到这张表的旧事务结束；**有长事务在跑时会一直等**（长事务在这条主线里又以另一种方式出现）。 |
| **「标记有效」不等于「马上能用」** | **最坏情况下，只要还有早于建索引开始的事务在跑，优化器就一直用不上它**——索引是有效的，但查询还是走全表扫。 |

【推导】**「更慢」是多少？** 口径：

```text
普通 CREATE INDEX：扫 1 遍表
CONCURRENTLY：      扫 2 遍表 + 每遍前后都要等事务结束
  → 纯扫描时间约 2 倍
  → 实际耗时通常 2–3 倍（还要叠加等待与两次索引维护）
```

**所以它换来的不是「更快」，是「不在同一时刻堵住所有人」**——**把 15 分钟的硬停，摊成 40 分钟的慢**。这是一笔明确的交易，不是免费的午餐。

【事实】**另外两条容易漏的约束**：

- **同一张表同时只能有一个 CONCURRENTLY 在跑**（普通建索引则可以多个并行）。**迁移脚本里连续建两个索引时，这条会咬人。**
- **建索引期间不允许改这张表的结构**。所以它天然不适合和别的 DDL 打包在一个迁移里。
- **只有第一次扫描能并行**（`CONCURRENTLY` 支持并行构建，但并行只作用在第一遍）。

### 5. INVALID 索引：为什么它不是「无害的垃圾」

这是这一题最值得讲透的地方，因为它**静默**：

- 它**不会被查询使用**——优化器忽略它，理由是**它可能不完整**；
- 但**它仍然被写入维护**——每次 `INSERT` / `UPDATE` 都要更新它 → **纯负债**；
- 而且它会**占用空间**、拖慢 VACUUM、**并且挡住后续同名的重建**。

【纠正一个想当然的结论】**「无效」不等于「约束失效」**——这条最容易讲错：

> **一个用 CONCURRENTLY 建的【唯一】索引，在第二次扫描开始的那一刻起就已经在【强制唯一性】了。**
> **所以即使它最终构建失败、停在 invalid 状态，它【之后仍然继续强制唯一性】。**

【推论】**这带来两个反直觉的后果**：

```text
① 约束可能【提前生效】：
   索引还没"可用"，违反唯一性的写入就已经被拒绝了
   → 报错出现在别的业务代码里，而不是在建索引这条命令上

② 约束可能【永久生效】但查询【永远用不上】：
   失败后的 invalid 唯一索引——
     写入侧：继续拦住重复值（像个约束）
     读取侧：优化器忽略它（不像个索引）
   → 你以为"失败了就没事了"，其实约束已经上线了
```

【推导】**把「纯负债」算成数字**：

```text
索引项大小（bigint 键）：
  index tuple header 8B + 键 8B + ctid 6B ≈ 22B → 对齐后 24B

8000 万行 × 24B ≈ 1.9 GB
  → 约 24 万页（8 KB/页）
  → 每轮 autovacuum 都要多处理这 24 万页
  → 每次写入都要多维护一条索引项
  → 而它【永远不会被任何查询用到】
```

**2 GB 不是重点，「每次写都付、永不回收」才是。**

【事实】**所以「失败了怎么办」的标准答案是**：先查有没有 invalid 索引（`pg_index.indisvalid = false`），然后**两条路**——**官方推荐的是删掉重建**：

```sql
-- 找出无效索引（顺手把大小一起查出来）
SELECT c.relname, pg_size_pretty(pg_relation_size(c.oid))
FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
WHERE NOT i.indisvalid;
```

```sql
-- 路一（官方推荐）：删掉重来——也要带 CONCURRENTLY，否则 DROP 本身要拿锁
DROP INDEX CONCURRENTLY idx_x;
CREATE INDEX CONCURRENTLY idx_x ON big_table (col);

-- 路二：原地重建，不用先删
REINDEX INDEX CONCURRENTLY idx_x;
```

【取舍】**两条路怎么选**：**重建（REINDEX）少一步、少一次窗口风险**，**但要求那个索引对象本身是对的**；**如果失败原因是你想改索引定义（换列、加谓词、改 opclass），那就必须走"删掉重建"。**

【事实】**进度看得见**：`pg_stat_progress_create_index` 会报告每个后端正在跑的建索引进度——**长任务要能被观测，不然只能靠猜。**

【补充】**一条容易被忽略的连带影响**（官方"Tip"里写的）：**`CREATE INDEX` 本身也是一个长事务**——**它会挡住【其他表】上并发 `VACUUM` 能回收的元组**。**所以在 PG 里，"我在小表上建个索引"也可能影响到别处**。

### 6. 工程流程（说这段才像做过线上）

```
① 先在低峰窗口确认没有长事务（有就跑不了/要等很久）
② 检查是否有同类索引已经存在（避免重复）；同表不要连开两个 CONCURRENTLY
③ 用 CONCURRENTLY 建，脚本里带超时与重试
④ 建完立刻校验 indisvalid，无效就 DROP CONCURRENTLY + 重建（幂等）
⑤ 建完后【过一会儿再确认优化器真的用上了】（标记有效 ≠ 马上可用）
⑥ 确认生效后再考虑删掉被它替代的旧索引
⑦ 若业务写量大：用部分索引缩小索引集合（见 P3），比省这一步更划算
```

**第 ① 步和主线五呼应**：长事务在 PG 里会同时阻塞 VACUUM、加剧膨胀、拖慢在线建索引——**一条长事务能同时踩三个坑。**

### 7. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「CONCURRENTLY 不锁表」 | 它**仍然要拿短暂的锁**（开始与结束各有一次），只是**不长时间持有**。所以它**不能在事务里**，也不能和别的 DDL 放在一个迁移里 |
| 「失败会自动回滚」 | **不。** 留下 INVALID 索引，必须手工查、手工处理 |
| 「无效索引的约束也没生效」 | **反了。** 失败的**唯一**索引**之后仍然继续强制唯一性**（[[母题-P19-唯一约束与UPSERT]]），只是**查询用不上它** |
| 「索引标记有效就万事大吉」 | **最坏情况下，只要还有早于建索引开始的事务在跑，优化器就用不上它** |
| 「加字段都会重写表」 | `ADD COLUMN` 带**常量默认值**在 PG 11+ 是元数据操作、不重写；**改类型、加约束**才重写表——**要区分「加列」和「改列」** |
| 「不调 fillfactor 就没有 HOT」 | **HOT 仍会自然发生**（新行流向新页、页内空位接纳新版本）；调小 fillfactor 是**提高概率**。官方口径：**从不更新的表填满最优，高频更新的表才调小** |
| 「索引建好了就一定用得上」 | 优化器还看统计信息与选择率估算（[[母题-P7-统计信息与慢查询定位]]） |

## 二、自测

**Q1（计算）**：表 8000 万行、平均每行 200 字节。现在给一个 `bigint` 列建一个普通 B-tree 索引。

问：**索引大约多大？占表的多大比例？**每轮 autovacuum 要多处理多少页？

**A1**：

```text
表：8000 万 × 200 B = 16 GB → 16 GB ÷ 8 KB ≈ 【200 万页】

索引项：header 8B + bigint 键 8B + ctid 6B ≈ 22 B → 对齐 24 B
索引：8000 万 × 24 B = 1.92 GB ≈ 【2 GB】
  → 2 GB ÷ 8 KB ≈ 【24 万页】
  → 占表的体积比 = 1.92 / 16 ≈ 【12%】
```

【推论】**索引的体积通常只是表的 10% 量级，所以「空间」几乎从来不是拒绝索引的理由**——**真正的理由是写入与 VACUUM**（Q3）。

【补充】**这一条要主动说**：能被体积劝退的场景只有一种——**部分索引把 12% 压到 0.12%**（[[母题-P3-部分索引与表达式索引]]）。**那才是空间真正值钱的地方。**

**Q2（计算）**：接上题。直接 `CREATE INDEX` 耗时约 15 分钟，期间写入 500 TPS、连接池 100 条连接、平均请求 50 ms。

问：**阻塞期间积压多少次写？为什么故障会从「写变慢」升级成「整站不可用」？**

**A2**：

```text
积压写入 = 15 × 60 × 500 = 【45 万次】

连接池被写请求占满：100 条连接全部卡在建索引的等待上
  → 读请求也拿不到连接
  → 正常能扛 100 ÷ 0.05 s = 2000 QPS 的读，此刻【归零】

→ 故障形态：不是"写慢"，是【所有接口一起超时】
```

【结论】**这就是「DDL 本身慢」和「DDL 把系统拖下水」的区别**——**15 分钟是 DDL 的耗时，45 万次积压是它的代价。**

【推论】**判据**：

> **危险的不是锁有多重，是锁【被持有的时间】× 【锁后面的流量】。**

**所以同一个 DDL，在凌晨 3 点做和在早高峰做，完全是两件事。**

**Q3（计算）**：表上有 6 个二级索引，其中 **3 个引用了 `updated_at`**。业务每次处理任务都会 `UPDATE ... SET updated_at = now()`。

问：**这次 UPDATE 要写几个元组？如果把 `updated_at` 从这 3 个索引里拿掉（并建表时留了 fillfactor），能降到几个？**

**A3**：

```text
现状（updated_at 被 3 个索引引用）：
  改的列在索引里 → 永远无法 HOT
  写元组 = 1（堆新版本）+ 3（被引用的索引）= 【4 个】

拿掉引用 + fillfactor 90（页内有空间）：
  改的列不在任何索引里 → 走 HOT
  写元组 = 1（堆新版本）+ 0（索引一个都不碰）= 【1 个】
```

【结论】**4 → 1，写路径上的元组数降到 1/4。**

【推论】**判据**：

> **在 PG 里，把一个「高频更新的列」放进索引，代价不只是多一个索引项，而是【永久关掉这条更新路径的 HOT】。**

【补充】**HOT 省的不止索引写，还省 VACUUM**：**一行被更新多次时，HOT 链上的中间版本可以在正常运行（包括 `SELECT`）中被就地移除**，不必等 autovacuum。**所以「高频更新列不进索引」这条规则，同时减轻了写路径和清理路径**——**这是它连到主线五（表膨胀）的那根线。**

【补充】**这条规则可验证**：`pg_stat_all_tables` 里的 `n_tup_hot_upd / n_tup_upd` 就是 HOT 占比。**调 fillfactor 之前先查这个数，不用猜。**

【取舍】**但这不是「updated_at 一律不进索引」**——**调度器要按 `updated_at` 排序取任务时，这个索引就是必需的**（而且那时它往往该是部分索引）。**正确的动作是：先问「这个索引服务哪条查询」，再问「它会不会关掉一条高频更新路径的 HOT」。两个问题都答得上来，才动手。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们用了 `CREATE INDEX CONCURRENTLY`，它不锁表，所以可以随时在业务高峰跑。"

**A4**：三处问题。

1. **它不是「不锁」，是「不长时间锁」**：开始和结束各要拿一次短暂的锁，中间靠两遍扫描避开长锁——**语义是「换了一套做法」，不是「更聪明的锁」**。
2. **它更慢、资源占用更高**：扫两遍表，纯扫描时间就是普通建索引的约 2 倍，实际 2–3 倍。**高峰跑等于把「15 分钟硬停」换成「40 分钟的高 IO/高 WAL 慢」**——对已经有流量压力的系统，这未必更好。
3. **它要等所有并发事务结束**：**有长事务在跑时会一直等**（[[母题-P14-长事务与表膨胀]]），**在高峰做，等待时间不可控**。

【准确说法】"**`CONCURRENTLY` 换掉的是「长锁」，不是「资源代价」**。**所以它仍然该放在低峰做**，而且**做之前要先确认没有长事务在跑**——**否则它会一直等，比普通建索引还难收场。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "建索引那条命令报错失败了，PG 会回滚，表就回到原来的样子，我们重试一下就行。"

**A5**：三处问题。

1. **失败不回滚索引对象**：`CONCURRENTLY` 出错后 **索引对象仍然存在，只是停留在 invalid 状态**——**它跨了三个事务，本来就没有一个"整体事务"可以回滚它**。
2. **它是纯负债而且静默**：不会被查询使用，**但每次写入都要维护、每轮 VACUUM 都要处理**——而**你不查就不会知道**。
3. **如果它是唯一索引，后果比"纯负债"更重**：**第二次扫描一开始，唯一性就已经在强制生效了；构建失败之后，这个 invalid 索引【仍然继续强制唯一性】**。**所以"失败了 = 什么都没发生"是错的——约束可能已经上线，只是没有任何查询能用到它**（[[母题-P19-唯一约束与UPSERT]]）。
4. **重试不是"再跑一次"**：同名索引已存在，直接重跑会失败——**要么 `DROP INDEX CONCURRENTLY` 再建，要么 `REINDEX INDEX CONCURRENTLY`**，**脚本必须幂等**（先查 `indisvalid`）。

【准确说法】"**`CONCURRENTLY` 的失败是一个需要人工收尾的状态，不是一个异常**。**脚本要对它做两件事：建完立刻校验 `indisvalid`，无效就 DROP CONCURRENTLY 再重建（或 REINDEX CONCURRENTLY）。** **唯一索引还要多确认一件事：约束是不是已经生效了。** **这就是为什么这条 DDL 要写成幂等脚本，而不是在客户端手敲一遍。**"

## 三、面试输出（学完再看）

**一句话结论**：PG 里索引的代价要讲**三项**——**写放大（1 个堆元组 + k 个索引项）/ 空间（通常是表的 10% 量级）/ VACUUM 与缓存压力**，**第三项是 PG 特有的，也是它在索引数量上比 MySQL 更保守的原因**。**能不能走 HOT 是 PG 独有的一条免费通道**：只要更新的列不在任何索引里、且页内有空间，**索引一个都不用碰**（4 次元组写 → 1 次），**而且中间版本还能在正常运行时被就地清掉、不必等 VACUUM**；**所以把高频更新的列放进索引，代价是永久关掉这条路径的 HOT**。**直接 `CREATE INDEX` 会在一次全表扫描里挡住所有写入**，**真正的危险不是它慢，是它在 15 分钟里积压几十万次写、把连接池占满，让整站一起超时**。**`CONCURRENTLY` 不是「更聪明的锁」，是换了一套做法**——**先以 invalid 身份登记，再扫两遍、每遍前后都等事务结束，最后标记 valid**，**代价是不能放在事务里、慢 2–3 倍、要等长事务结束，而且「标记有效」不等于「马上能用」**。**最危险的是失败：它不回滚，索引会停在 INVALID——不被查询用、但每次写都要维护、每轮 VACUUM 都要处理，是纯负债**；**如果它是唯一索引，那第二条扫描一开始约束就已经生效，失败之后【仍然继续强制唯一性】**。**处置方式两条：`DROP INDEX CONCURRENTLY` 重建，或 `REINDEX INDEX CONCURRENTLY`**——**所以这条 DDL 必须写成幂等脚本。**

**恢复关键词**：三项代价（写放大·空间·VACUUM）/ 写元组 = 1 + k / **HOT：更新的列不在索引里 + 页内有空间 → 索引全不碰** / **HOT 第二个收益：中间版本不用等 VACUUM** / `fillfactor = 90`（默认 100）/ `pg_stat_all_tables` 看 HOT 占比 / 索引≈表的 12% / 标准建索引 = 单次扫描 + 挡写 / **45 万次积压 → 连接池耗尽** / **危险 = 锁持有时间 × 背后流量** / **CONCURRENTLY：invalid 登记 → 两次扫描 → 标记 valid** / **不能在事务里** / 标记有效 ≠ 马上能用 / **INVALID 索引：静默纯负债** / **失败的唯一索引仍然强制唯一性** / `DROP INDEX CONCURRENTLY` · `REINDEX INDEX CONCURRENTLY`

**核心不变量 / 主线**：
**在线变更安全的判据不是「它快不快」，而是「失败之后系统停在一个什么状态、以及这个状态是否可见」。**
MySQL 的答案是「看不见的 MDL 队列堵住一切」，PG 的答案是「不报错、却仍在收租的 INVALID 索引」——**两次都是「静默」最危险。**

**完整回答骨架**：索引的三项代价（算一笔写元组 = 1 + k）→ **HOT 这条免费通道与它的两个条件、两样收益** → 直接建索引堵什么（算 45 万次积压 → 连接池耗尽）→ **CONCURRENTLY 的三段式：invalid 登记 → 两次扫描 → 标记 valid** → 四个坑 → **INVALID 索引为什么是纯负债（算 1.9 GB / 24 万页）+ 失败的唯一索引仍强制唯一性** → 失败后的幂等处置 → 收束到「静默最危险」

**追问**（先说后看）

1. **为什么不能放在事务里，机制上是什么？** —— 因为它**需要跨多个事务、让并发事务持续提交**才能收集到完整数据；被放进一个事务里，就变成「持锁等待」，反而退化成普通 `CREATE INDEX` 的语义，所以 PG 直接禁止。**它不是更聪明的锁，而是换了一套做法。**
2. **如果建到一半应用在写，会不会丢行？** —— 不会。第二次全表扫描就是为这件事存在的：它补齐构建期间新增/更新的行；**两遍覆盖完整之后才把索引标记为 valid，中途出问题就停在 invalid**。所以**正确性靠「补扫 + 校验」，不靠「停写」**——这和 MySQL 影子表方案（pt-osc / gh-ost）的「先建后换」是两种哲学，可以对比着讲。
3. **HOT 和加索引是怎么互相影响的？** —— **HOT 的前提之一就是「更新的列不在任何索引里」**，所以**每多一个索引，就多一批更新被判出 HOT 通道**。**这是 PG 里「索引数量」这件事比 MySQL 更贵的一条具体机制**（不只是抽象的「写放大」）。**顺带还能说出第二样收益：HOT 链上的中间版本能在正常运行时被就地清掉，所以它同时减轻 VACUUM 负担。**
4. **唯一索引用 CONCURRENTLY 建失败了，约束到底生效没有？** —— **生效了。** 第二次扫描一开始，唯一性就已经在强制；**构建失败之后，那个 invalid 索引【仍然继续强制唯一性】**。所以它的状态是「**约束在，索引不在**」——**写入侧像个约束，读取侧不像个索引。** **这条最能说明"失败不是回到原点"**（[[母题-P19-唯一约束与UPSERT]]）。
5. **PG 加字段会不会锁表？** —— `ADD COLUMN` 只有**默认值**在 PG 11+ 后是元数据操作、不重写表（很轻）；但**改类型 / 加约束要重写表**，那才是真正危险的。**要区分「加列」和「改列」。**
6. **怎么发现线上有无效索引？** —— `pg_index.indisvalid = false`；顺手还能查**重复/冗余索引**（同一前缀的多个索引）与**从未被用过的索引**（`pg_stat_user_indexes.idx_scan = 0`）。**「该删的索引」和「该补的索引」一样值钱。**

**同类变体**

- 「PG 和 MySQL 做在线 DDL 的能力差多少？」——**MySQL** 有 `ALGORITHM=INPLACE, LOCK=NONE`，但**它做不到的事要交给 pt-osc / gh-ost 影子表**，而 MySQL 的 **MDL 队列**会让「慢」升级成「全表不可访问」；**PG** 用 `CONCURRENTLY`，**不需要外部工具**，但**失败会留 INVALID 索引**。**两边共同的坑是「失败留下的中间态」——MySQL 是排队，PG 是无效索引。**
- 「索引建多了会怎样？」——见上面三项代价；**回答里带上 VACUUM 压力与 HOT，就把 PG 的答案和 MySQL 的答案区分开了**（[[母题-M4-索引代价与大表变更]]）。
