# 母题 P4 · 索引代价与在线建索引

> **模块**：PostgreSQL / 索引与表设计
> **所属主线**：一 · 索引与表设计（怎么让查询不用扫全表，表怎么建才不埋雷）
> **关联母题**：[[母题-P3-部分索引与表达式索引]] · [[母题-P15-VACUUM与事务ID回卷]]
> **素材来源**：`study/09-数据缓存队列与一致性` 第 3.1 节（索引代价含 vacuum 压力）+ 通用知识（**CONCURRENTLY 细节待你核对**）

**题目**：线上 8000 万行的表要加一个索引。你直接执行 `CREATE INDEX idx_x ON big_table (col)`。会发生什么？换成 `CREATE INDEX CONCURRENTLY` 就安全了吗？

**母题**：索引的代价是什么（PG 版）？`CREATE INDEX CONCURRENTLY` 有什么坑，失败了怎么办？

**为什么重要**：MySQL 那边这条主线的关键词是「MDL 连锁」；**PG 这边换成了另一套机制**——不阻塞写、但会留下**静默的 INVALID 索引**。这是同一个问题的两种形态，**能不能分别讲清，是判断你有没有真的在两套库上操作过的分水岭**。而且它承接 P3：**索引不是越多越好，PG 里还多一条理由。**

**一句话结论**：PG 里索引的代价有三项——**写放大 / 空间 / VACUUM 与缓存压力**（第三项是 PG 特有的，也是它在索引数量上比 MySQL 更保守的原因）；`CREATE INDEX CONCURRENTLY` 做到了**不长时间阻塞写入**，代价是**不能在事务里跑、要扫两遍表所以更慢、失败会留下 INVALID 索引**——那个索引**不报错、但照样占空间并拖慢写入，必须手动 DROP 再重建**。

**恢复关键词**：写放大 / 空间 / vacuum 压力 / CONCURRENTLY 不能在事务内 / 两遍扫描 / INVALID 索引 / 幂等重建脚本

**核心不变量 / 主线**：
**在线变更安全的判据不是「它快不快」，而是「失败之后系统停在一个什么状态、以及这个状态是否可见」。** MySQL 的答案是「看不见的队列堵住一切」，PG 的答案是「看得见但不报错的无效索引」——**两次都是「静默」最危险。**

**完整回答骨架**：索引的三项代价（PG 版）→ 直接建索引会堵什么 → CONCURRENTLY 的机制 → 三个坑 → 失败后的正确处理 → 工程流程

## 原理分解

### 一、索引的三项代价（PG 版，第三项是重点）

| 代价 | 表现 |
|---|---|
| **写放大** | 每次 `INSERT` 要在堆里插行并更新**每一个**索引；PG 的 MVCC 让 `UPDATE` = 插入新版本 + 标记旧版本，**所以一次更新会同时写堆和所有索引** |
| **空间** | 索引独立文件，叶子存键值 + ctid；联合索引叶子存**所有索引列的值**（比 InnoDB 只存主键更大） |
| **VACUUM 与缓存压力** | 每个索引都是一棵要清理的树：**autovacuum 要遍历的索引页变多、清理变慢、膨胀更难被自动控制**；同时索引页争抢 shared_buffers |

**第三项是回答「PG 里索引是不是越多越好」的关键**。MySQL 的答案通常停在「写放大 + 空间」；**PG 必须多一句「它让 VACUUM 更难跟上」**——这句话直接连到 P15（表膨胀）。

### 二、直接建索引会堵什么

普通 `CREATE INDEX` 会**在整张表上持有一个较轻的锁（SHARE）**：它允许其他会话**读**，但**阻塞所有写入**（`INSERT` / `UPDATE` / `DELETE`）。

对 8000 万行的表，这意味着：

```
建索引耗时（分钟级到小时级）
  ↓
这段时间内所有写请求排队等待
  ↓
连接池被占满
  ↓
上层接口开始超时 → 雪崩
```

**机制和 MySQL 完全不同（PG 没有 MDL 那套连锁，这里是直接的写锁），但后果一样：不是 DDL 本身慢，是它把后面的写入堵成一条越来越长的队。**

### 三、CONCURRENTLY 怎么做到不阻塞

它把建索引拆成**多遍扫描 + 状态机**，中间不持长锁：

1. 第一遍：登记一个「待构建」的索引（很快，短锁）；
2. 扫描已有数据、填充索引；
3. 第二遍扫描：把构建期间新产生/修改的行补进去；
4. 校验并标记为有效。

**代价与坑，全在这套流程里：**

| 坑 | 说明 |
|---|---|
| **不能在事务块里执行** | 它需要跨多个事务/多遍扫描，所以 `BEGIN ... CREATE INDEX CONCURRENTLY ... COMMIT` 会直接报错。**迁移脚本里最常见的翻车点。** |
| **更慢、占用更多资源** | 扫两遍表、等待所有并发事务结束；期间 CPU / IO / WAL 压力显著上升，**必须避开业务高峰**。 |
| **失败会留下 INVALID 索引** | 这一步没有回滚——**失败后索引对象仍然存在，只是标记为 invalid**。 |
| **等待期可能很长** | 它要等所有可能看到这张表的旧事务结束；**有长事务在跑时会一直等**（长事务在这条主线里又以另一种方式出现）。 |

### 四、INVALID 索引：为什么它不是「无害的垃圾」

这是这一题最值得讲透的地方，因为它**静默**：

- 它**不满足唯一性/约束**（`UNIQUE` 用 CONCURRENTLY 建失败后，唯一性其实没有生效）；
- 它**不会被查询使用**（优化器忽略 invalid 索引）；
- 但它**仍然被写入维护**——每次 `INSERT` / `UPDATE` 都要更新它 → **纯负债**；
- 而且它会**占用空间**、拖慢 VACUUM。

**所以「失败了怎么办」的标准答案是**：先查有没有 invalid 索引（`pg_index.indisvalid = false`），然后 `DROP INDEX CONCURRENTLY`（**也要带 CONCURRENTLY，否则 DROP 本身要拿锁**）再重建。

```sql
-- 找出无效索引
SELECT c.relname FROM pg_index i JOIN pg_class c ON c.oid = i.indexrelid
WHERE NOT i.indisvalid;
```

### 五、工程流程（说这段才像做过线上）

```
① 先在低峰窗口确认没有长事务（有就跑不了/要等很久）
② 检查是否有同类索引已经存在（避免重复）
③ 用 CONCURRENTLY 建，脚本里带超时与重试
④ 建完立刻校验 indisvalid，无效就 DROP CONCURRENTLY + 重建（幂等）
⑤ 确认生效后再考虑删掉被它替代的旧索引
⑥ 若业务写量大：用部分索引缩小索引集合（见 P3），比省这一步更划算
```

**第 ① 步和主线五呼应**：长事务在 PG 里会同时阻塞 VACUUM、加剧膨胀、拖慢在线建索引——**一条长事务能同时踩三个坑。**

## 二、扩展：类似题与追问

**类似题**

1. 「PG 加字段会不会锁表？」——`ADD COLUMN` 只有**默认值**在 PG 11+ 后是元数据操作、不重写表（很轻）；但**改类型 / 加约束要重写表**，那才是真正危险的。**要区分「加列」和「改列」。**
2. 「索引建多了会怎样？」——见上面三项代价；**回答里带上 VACUUM 压力，就把 PG 和 MySQL 的答案区分开了。**
3. 「怎么发现线上有无效索引？」——`pg_index.indisvalid`；同理还有「重复/冗余索引」（同一前缀的多个索引）可以一起查。

**追问链**

- 追问一层：**「为什么不能放在事务里，机制上是什么？」**——因为它**需要跨多个事务、让并发事务持续提交**才能收集到完整数据；被放进一个事务里，就变成「持锁等待」，反而退化成普通 `CREATE INDEX` 的语义，所以 PG 直接禁止。**「它不是更聪明的锁，而是换了一套做法」。**
- 追问二层：**「如果建到一半应用在写，会不会丢行？」**——不会。第二遍扫描就是为这件事存在的：它补齐构建期间新增/更新的行；**校验阶段会确认覆盖完整，不完整就标记 invalid**。所以**正确性靠「补扫 + 校验」，不靠「停写」**——这和 MySQL 影子表方案（pt-osc / gh-ost）的「先建后换」是两种哲学，可以对比着讲。
