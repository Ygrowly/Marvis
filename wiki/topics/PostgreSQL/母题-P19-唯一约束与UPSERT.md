# 母题 P19 · 唯一约束与 UPSERT

> **模块**：PostgreSQL / 业务并发场景
> **所属主线**：七 · 业务并发场景（抢库存、冲排行榜怎么不出错）
> **关联母题**：[[母题-P18-乐观并发控制]] · [[母题-P5-表设计与数据类型]] · [[母题-P9-序列化失败与重试]]
> **素材来源**：**RuleArena 真实设计**（`projects/RuleArena/04-idempotency-and-recovery.md`：`UNIQUE(run_id, action_type, idempotency_key)`、Receipt 与同一事务提交）· `study/09` 第 5 节

**题目**：消息队列按「至少一次」投递，同一个业务动作可能被投递两次。你怎么保证业务效果只有一次？

**母题**：唯一约束为什么是幂等的最终防线？`UPSERT`（`ON CONFLICT`）怎么用、有哪些坑？

**为什么重要**：这是**幂等设计的地基**，而且它有一个非常有说服力的论证结构——**「应用层幂等是优化，数据库约束才是正确性」**。它还接住了你的项目里最核心的一段：**RuleArena 的 ActionReceipt 与唯一约束**（`projects/RuleArena/04-idempotency-and-recovery.md`）。**能把"为什么必须在数据库层兜底"讲成一条必然性论证，而不是一句结论，这道题就到位了。**

**一句话结论**：**因为它是数据库级别、原子、且对所有并发路径都生效的**——应用层的「先查再插」有竞态（P18 讲过），而唯一约束让**第二次插入直接失败**，从结构上堵住了。**前提是幂等键要基于业务身份构造**（`run_id + 动作类型 + 目标 + 参数 + 规则版本 + 逻辑步骤`），**并且参与约束的列必须 `NOT NULL`**（PG 里 `NULL` 彼此不相等，否则约束会漏）。`UPSERT` 用 `INSERT ... ON CONFLICT ... DO NOTHING / DO UPDATE`。

**恢复关键词**：唯一约束是原子防线 / 应用层幂等是优化 / 先查再插有竞态 / 幂等键基于业务身份（**不能用 ToolCallID 这类技术 ID**）/ 约束列必须 NOT NULL / `ON CONFLICT DO NOTHING` vs `DO UPDATE` / `excluded` 与条件覆盖 / 冲突也消耗序列值

**核心不变量 / 主线**：
**幂等的最终责任必须落在数据库约束上。** 应用层做幂等只能**减少无效尝试**（省资源），**不能提供正确性保证**——因为任何「查—判断—写」在多进程/多副本下都有窗口。**唯一约束是唯一一个"无论如何都拦得住"的位置。**

**完整回答骨架**：为什么应用层幂等不够（竞态）→ 唯一约束为什么是最终防线 → 幂等键怎么构造（含反例）→ `NOT NULL` 这个坑 → UPSERT 两种形态与坑 → 落到项目的 Receipt 设计

## 原理分解

### 一、为什么应用层幂等「不够」

**幂等的常见应用层实现**：

```
查：这个 idempotency_key 有没有处理过？
  没有 → 处理 → 记录
  有   → 直接返回上次结果
```

**问题就在「查」和「记录」之间**（和 P18 是同一个结构缺陷）：

```
实例 A: 查 → 不存在
实例 B: 查 → 不存在          ← 两个实例拿到同一个答案
实例 A: 处理 → 记录
实例 B: 处理 → 记录           ← 副作用发生了两次
```

**读者会问：「那加锁不就行了？」**——加锁可以，但有两个代价：① **锁是应用层的，一旦有第二台机器/第二个进程就失效**（除非用分布式锁，那又引入新依赖和新的失效模式）；② **锁的获取本身可能失败/超时**，于是又回到"要么重试要么放弃"的老问题。

**所以判断是**：**应用层幂等能挡掉绝大多数重复（这是有价值的优化——省掉了重复的昂贵操作），但不能作为正确性保证。**

### 二、唯一约束为什么是「最终防线」

它同时满足四个条件，缺一不可：

| 条件 | 说明 |
|---|---|
| **原子** | 插入与唯一性检查在数据库内部是一次操作，**不存在「查—写」窗口** |
| **对所有路径生效** | 不管来自哪个实例、哪个进程、哪条代码路径、甚至是运维手工插入，**都拦得住** |
| **由持久状态保证** | 约束建立在索引/数据上，**不是内存状态**（重启不丢） |
| **失败是确定的** | 第二次插入报 `23505`，**语义明确，不会"有时成功有时失败"** |

**所以正确的分工是**：

```
应用层幂等：优化（减少无效的昂贵操作）
数据库约束：正确性（唯一一个"无论如何都拦得住"的位置）
权威查询：判定（Receipt/Snapshot 告诉你"它到底成没成"，P18 追问）
```

**这三层合起来才是完整的幂等方案**——**只说其中一层都是不完整的。**

### 三、幂等键怎么构造（含反例）

**规则：基于业务身份构造，不依赖任何一次技术调用。**

RuleArena 的组成（`projects/RuleArena/04-idempotency-and-recovery.md`）：

```
run_id + action_type + target_id + normalized_arguments + rule_version + logical_step
```

**要能说出每一项挡的是什么**：

| 组成 | 挡什么 |
|---|---|
| `run_id` | 不同运行的相同动作不能混为一谈 |
| `action_type` | 同一目标的不同动作（退款 vs 发券）要分开 |
| `target_id` | 同一动作作用在不同对象上要分开 |
| `normalized_arguments` | **参数要归一化**（顺序、大小写、数值表示），否则「同一个业务意图」会因为参数写法不同而被当成两次 |
| `rule_version` | 规则变了之后，同一个动作是**新的业务意图**，不该复用旧结果 |
| **`logical_step`** | **同一意图可能被合法地重复执行多次**（比如重试策略的第 3 步），逻辑步骤要区分开 |

**明确的反例（这是这道题最值钱的部分）**：

**不能用 `ToolCallID` 当幂等键。** 因为它是**由模型/运行时为"这一次调用"生成的**，而同一个业务意图在这些情况下会产生不同的 `ToolCallID`：

- 模型**重新规划**（换了调用方式）；
- **Worker 重启**后恢复；
- **会话恢复**；
- **HTTP 超时后重新发起**；
- 两个策略**恰好提出相同动作**（各自生成自己的 ID）。

**所以用 `ToolCallID` 做幂等键，等于"每次重试都换一把新钥匙"——约束永远不生效，重复副作用照样发生。** **这条是"幂等设计里最典型的错误"，能讲出来直接体现项目深度。**

### 四、`NOT NULL`：一个容易漏的坑

**PG 里 `NULL` 彼此不相等**（P5 提过），所以唯一约束**允许多行 `NULL`**。

后果：如果幂等键的某一列可为 `NULL`，那么「同一业务意图」可能因为该列为 `NULL` 而**不被判定为重复**，约束形同虚设。

**所以规则是**：**参与唯一约束的列一律 `NOT NULL`**；确实有可选维度时，**用空字符串 / 哨兵值而不是 `NULL`**（或者把可选维度塞进归一化后的参数哈希里）。

**「设计唯一约束时必须检查 `NOT NULL`」——这是一个可以在 5 秒内检查完、但漏掉会致命的检查项。**

### 五、`UPSERT`：两种形态与三个坑

```sql
-- 形态一：重复就跳过（幂等写入的默认选择）
INSERT INTO action_receipts (idempotency_key, run_id, action_type, status)
VALUES (:key, :run_id, :type, 'ACCEPTED')
ON CONFLICT (idempotency_key) DO NOTHING;

-- 形态二：重复就更新（"取最新"，要小心）
INSERT INTO counters (id, value)
VALUES (:id, 1)
ON CONFLICT (id) DO UPDATE
  SET value = counters.value + 1;
```

**三个坑**：

| 坑 | 说明 |
|---|---|
| **`DO UPDATE` 可能把更新的旧值写回去** | 如果目标是「保留最新」，必须加条件：`... DO UPDATE SET ... WHERE excluded.updated_at > t.updated_at`（`excluded` 指"本次想插入的那行"）。**不加条件，一个延迟到达的旧请求就能覆盖掉新数据。** |
| **冲突也会消耗序列值** | `INSERT ... ON CONFLICT` **先尝试插入**，所以自增序列**会前进**——于是**主键会出现"空洞"**。**这是正常现象，不要试图修它。** |
| **并发下仍可能报错** | `DO UPDATE` 涉及行锁，**同键高并发可能出现序列化失败或死锁**（P9 / P10），**所以重试逻辑依然需要**。 |

**还有一个语义选择**：`DO NOTHING` 有一个副作用——**它不告诉你是"真的插入了"还是"跳过了"**（`RETURNING` 在这种情况下不返回行）。**如果你需要区分，就得靠"有没有返回行"来判断**：

```
有返回行 → 本次是新插入（首次执行）
无返回行 → 已有记录（重复执行）  ← 正是幂等判断需要的信号
```

**这个技巧很实用**：**一条 `INSERT ... ON CONFLICT DO NOTHING RETURNING` 同时完成了「写入 + 幂等判定」**——**不需要先 SELECT，也不存在竞态。**

### 六、落到项目（RuleArena 的真实设计）

`projects/RuleArena/04-idempotency-and-recovery.md` 里的做法值得逐条对照：

1. **唯一约束**：`UNIQUE(run_id, action_type, idempotency_key)` —— **约束带上了业务身份前缀**（不只是幂等键本身）；
2. **同一事务提交**：业务效果 + 账本 + BusinessEvent + Receipt **在同一个事务里**——**否则会出现"业务成功但没有 Receipt"（无法判定）或"Receipt 成功但业务回滚"（假成功）**；
3. **Receipt 状态机**：`ACCEPTED` / `COMPLETED` / `REJECTED` / `UNKNOWN`——**把"不知道"变成一个显式状态**（`ACTION_UNKNOWN`），**而不是硬塞进成功或失败**；
4. **超时后不换 key**：**重试仍用同一个幂等键**，因为换了 key 就等于放弃幂等保护；
5. **业务校验 + 数据库约束都要有**：**业务校验给出清晰的错误信息，唯一约束防并发穿透**——**两者职责不同，不能互相替代。**

**第 5 条是这道题最好的收尾**：**"清晰错误"是给人和业务看的，"原子约束"是给正确性看的**——**一个负责体验，一个负责不出错。**

## 二、扩展：类似题与追问

**类似题**

1. 「幂等和去重有什么区别？」——**幂等是"同一个业务意图重复请求只产生一次效果"**（语义层面）；**去重是"识别出重复的请求"**（实现手段）。**幂等是目标，去重是方法之一。**
2. 「`ON CONFLICT` 和 `MERGE` 什么关系？」——`MERGE` 是更通用的"匹配则更新、否则插入"语句（PG 15+），**但它在并发下的行为与 `ON CONFLICT` 不同**（`ON CONFLICT` 是真正基于唯一索引的原子冲突处理）。**幂等场景首选 `ON CONFLICT`。**
3. 「Redis 的 `SETNX` 能替代唯一约束吗？」——**不能作为最终防线**：① Redis 不是权威状态（可能丢、可能被清）；② 分布式锁的失效是常见故障模式。**它可以是第一层快速拦截（省数据库往返），但正确性必须落回数据库。**

**追问链**

- 追问一层：**「唯一约束冲突了，怎么知道是该返回上次结果还是报错？」**——**先看 Receipt 的状态**（`COMPLETED` → 读权威 Snapshot 复用结果；`REJECTED` → 返回确定失败；`ACCEPTED` → 还在处理中，短暂等待或返回"处理中"；不存在 → 才考虑重试）。**这就是 RuleArena 的「超时后的恢复决策」那张判定表**——**它把"重复请求"从一个错误变成了一个有明确分支的状态机。**
- 追问二层：**「如果一条 SQL 里既要插 Receipt 又要改业务表，怎么保证原子？」**——**放在同一个事务里**（RuleArena 的做法），**并且唯一约束是这个事务的一部分**。**如果跨了服务/库**，就要走 Outbox（Study 09 第 6 节）：**事务内写业务 + OutboxEvent，提交后由异步 Publisher 至少一次发布，消费端幂等**——**注意这里"消费端幂等"又回到了本母题，所以 Outbox 不能免除幂等，只能把"跨系统"拆成"本地原子 + 远端幂等"。**
