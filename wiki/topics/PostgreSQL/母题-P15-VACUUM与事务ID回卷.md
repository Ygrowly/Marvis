# 母题 P15 · VACUUM 与事务 ID 回卷

> **模块**：PostgreSQL / 长事务
> **所属主线**：五 · 长事务（它为什么危险，为什么拖系统下水）
> **层级**：A · 教材级（冻结的阶梯、激进 VACUUM 的扫描放大、回卷倒计时都能算；能推出「为什么宁可停机」）
> **关联母题**：[[母题-P13-MVCC与可见性]]（32 位事务 ID）· [[母题-P14-长事务与表膨胀]]（清理边界）· [[母题-P4-索引代价与在线建索引]]（VACUUM 压力的来源）· [[母题-P12-流复制与逻辑复制]]（离线复制槽阻塞回收）· [[母题-M13-长事务为什么危险]]（MySQL 侧对照）
> **素材来源**：`study/09-数据缓存队列与一致性` + **PostgreSQL 官方文档 Routine Vacuuming / Autovacuum 配置**（2026-09-13 联网核实）+ 通用知识。**三组算式与 `pg_xact` 那个理由为本次新增（待你核对）**

**导读**：必懂 3 件事（① **普通 VACUUM 只把空间标记为「可复用」，不还给操作系统**——「跑完还是 10 GB」是正常的 ② **冻结是一条阶梯**：5000 万开始冻、1.5 亿转激进扫描、2 亿强制防回卷 ③ **回卷是一个有倒计时的硬约束**——500 TPS 下冻结停摆约 48.6 天逼近红线，而官方的说法是超过就可能**丢数据**）· 读完约 12 分钟 · 需要先懂：[[母题-P14-长事务与表膨胀]]

**题目**：`VACUUM` 跑完，表还是 10 GB。正常吗？为什么 PG 会宁可拒绝服务也不让事务 ID 用完？

**母题**：`VACUUM` 到底做了什么？事务 ID 回卷是什么，PG 怎么应对？

**为什么重要**：这是**唯一一处「运维不到位会真的丢数据」的 PG 机制**——**其他问题最多是变慢，这个会丢数据。** 而且它把主线的所有线索收在了一起：**P13 的 32 位 ID、P14 的回收边界、P4 的 VACUUM 压力，最后都落到这条线上。**

**一句话结论**：`VACUUM` 做三件事——**把死元组的空间标记为「可复用」（不是还给操作系统）**、**清理索引里指向死元组的条目**、**推进冻结**。所以**「跑完 VACUUM 表还是 10 GB」完全正常**，它只是不再继续长。要真正缩小只能 `VACUUM FULL` / `CLUSTER`（**排他锁 + 等量磁盘空间**）或 `pg_repack`（在线重建）。而**事务 ID 是 32 位、循环使用**，所以必须**在 ID 绕回来之前把老行「冻结」成"永远可见"**——**清理长期跟不上（长事务、离线复制槽）→ 冻不住 → 逼近回卷红线。PG 的应对是渐进升级，最后宁可拒绝新事务——「宁可停机也不出错数据」。**

**恢复关键词**：标记可复用 ≠ 还空间 / 清理索引条目 / 推进冻结 / `VACUUM FULL` 要排他锁 / `pg_repack` / **32 位事务 ID 循环** / **冻结阶梯：5000 万 → 1.5 亿 → 2 亿** / 激进 VACUUM / **「20 亿事务不被 VACUUM 就可能丢数据」** / 渐进升级与拒绝服务

**核心不变量 / 主线**：
**「回收」要拆成两个动作：把空间标记为可复用（普通 VACUUM）≠ 把空间还给操作系统（VACUUM FULL）。**
**而「冻结」是另一条独立的时间线：它不是为了让表变小，是为了让事务 ID 能安全地绕回来。**

**完整回答骨架**：`VACUUM` 做的三件事 → `VACUUM` vs `VACUUM FULL` vs `pg_repack` → **autovacuum 的两道门槛（回顾）** → **冻结的三级阶梯与激进 VACUUM 的代价** → **事务 ID 回卷的机制与 PG 的渐进升级** → 膨胀已经发生了怎么处理 → 预防清单

## 一、教材

### 1. `VACUUM` 做的三件事

1. **回收死元组占用的空间 → 标记为「可复用」**（注意：**不是还给操作系统**）；
2. **清理索引里指向死元组的条目**（[[母题-P13-MVCC与可见性]] 里那条：索引也要清）；
3. **更新统计信息**（`VACUUM ANALYZE`）并**推进冻结**（下面讲）。

【事实】**官方原话把第 1 条说得很死**：

> **标准形式的 `VACUUM` 会移除表和索引里的死行版本，并把空间标记为【可供将来复用】。**
> **然而，它【不会把空间还给操作系统】——除非出现特殊情况：表末尾的一个或多个页完全空闲，而且能轻易拿到排他表锁。**

【推论】**「可复用」的含义要讲准**：**空间留在表文件里，后续插入/更新可以填进去。** **所以表文件大小不会下降，只是「不再继续长」。** **「跑完 `VACUUM` 表还是 10 GB」完全是正常现象**——**很多人的困惑就来自这一步。**

---

### 2. 三种「重建」手段的分工

::figure pg-vacuum-and-wraparound.svg | VACUUM 的两条时间线：空间回收与冻结防回卷 | 标记可复用与真正还空间的区别、三种重建手段的锁与代价、冻结的三级阶梯、回卷倒计时与渐进升级

| | `VACUUM` | `VACUUM FULL` | `pg_repack` |
|---|---|---|---|
| 做什么 | **标记空间可复用** | **重写整张表**（新文件 + 拷贝有效行） | **在线重建**（类似在线建索引的思路） |
| 锁 | **轻锁**，业务基本不受影响 | **排他锁**，**期间该表不可读写** | **不长时间持锁** |
| 空间 | **不缩小文件** | **真正缩小** | **真正缩小** |
| 额外空间 | 不需要 | **需要等量额外空间** | **需要额外空间** |
| 额外代价 | — | **产生大量 WAL** | **过程更复杂、要装扩展** |
| 适用 | **日常、autovacuum 自动做** | **小表或可停机窗口** | **大表在线** |

【取舍】**判据**：

> **小表或可停机窗口 → `VACUUM FULL`；大表在线 → `pg_repack`；根本解法 → 治因（[[母题-P14-长事务与表膨胀]]）。**

【推论】**「表膨胀了跑一次 `VACUUM FULL`」在生产上通常不可接受**——**它要排他锁（业务中断）、要等量磁盘、还要产生大量 WAL**——**在一个已经很忙的实例上，这可能比"表大"本身更麻烦。**

---

### 3. autovacuum 为什么经常跟不上（回顾 P14）

autovacuum 是**按比例触发**的——**官方默认：过期的元组数 > `50 + 0.2 × 表行数`**（**8000 万行的表要 1600 万个过期元组**）。两类问题：

| 问题 | 说明 |
|---|---|
| **大表触发太晚** | **比例阈值对大表意味着「要变更多少行」才触发**——**偏偏大表最经不起堆积**。所以大表**需要单独调低阈值**（按表调，不全局调）。 |
| **被长事务/复制槽顶住** | **有长事务时，回收边界推不动**，**autovacuum 跑上去也清不掉东西**（[[母题-P14-长事务与表膨胀]]）；**有离线复制槽时 WAL 不回收**（[[母题-P12-流复制与逻辑复制]]）。**这两个是"看起来在跑但没效果"的典型。** |

【事实】**还有一个容易被忽略的限制**：**`autovacuum_max_workers` 默认只有 3**——**同一时间最多 3 张表在被清理**，**表多的时候会排队**。**而加大 workers 的代价是它们争抢 IO。**

**所以「调 autovacuum」不是万能的**：**它先要能被放开回收边界。** **判断顺序应该是「有没有东西按住边界」→ 再「阈值够不够激进」。**

---

### 4. 冻结：一条独立的时间线

【事实】**为什么需要冻结**（[[母题-P13-MVCC与可见性]]）：

- 事务 ID 是 **32 位、循环使用**；
- 一个行版本靠 `xmin`/`xmax` 判定可见性——**如果 ID 用完一圈绕回来，同一个 ID 既可能表示「很久以前的已提交」又可能表示「很新的事务」，比较就会彻底错乱**——**老数据可能被判定成"未来才可见"，于是凭空消失。**
- 解决办法是**冻结（freeze）**：**把足够老的行标记为「无论 ID 怎么变，它都是可见的」。** **冻结必须在 ID 循环到它之前完成。**

【事实】**冻结不是一件事，是一条三级阶梯**（官方默认值）：

| 参数 | 默认 | 触发什么 |
|---|---|---|
| `vacuum_freeze_min_age` | **5000 万事务** | **超过这个年龄的行版本【才值得】被冻结** |
| `vacuum_freeze_table_age` | **1.5 亿事务** | **`relfrozenxid` 到这个年龄 → 转【激进扫描】** |
| `autovacuum_freeze_max_age` | **2 亿事务** | **到这个年龄 → 【强制】防回卷 autovacuum（即使 autovacuum 被关掉也会启动）** |

【事实】**「激进扫描」的区别，官方说得很清楚**：

> **激进扫描与常规 `VACUUM` 的区别是：它会访问【每一个可能包含未冻结 XID 或 MXID 的页】，而不只是那些可能包含死元组的页。**

【推导】**算一下激进扫描的代价**：

```text
表 200 万页
常规 VACUUM：只有 5% 的页有死元组 → 扫【10 万页】
激进扫描：  扫【全部 200 万页】

→ IO 放大 【20 倍】
```

【结论】**这就是为什么官方反复强调「`vacuum_freeze_table_age` 应该设得比 `autovacuum_freeze_max_age` 低一些、留出余量」**——**留余量的意思是：让常规清理有机会顺手把冻结做掉，而不是被迫做一次 20 倍 IO 的激进扫描。**

【事实】**两个上限关系也要记住**：**`vacuum_freeze_table_age` 的有效上限是 `0.95 × autovacuum_freeze_max_age`**；**`vacuum_freeze_min_age` 的有效值会被静默限制为 `autovacuum_freeze_max_age` 的一半。**

【事实】**为什么默认是 2 亿这么"低"？官方给了理由**：

> **`VACUUM` 还允许从 `pg_xact` 子目录里移除旧文件，【这就是为什么默认值是一个相对低的 2 亿事务】。**

【推论】**这条把「冻结」和「磁盘上的其他东西」连起来了**：**事务 ID 用得越久，`pg_xact`（以及 `pg_commit_ts`）要保留的文件越多。** **所以官方还给了另一半建议：如果这些目录相对你的总库容很小，可以把 `autovacuum_freeze_max_age` 调到允许的最大值；否则就按你愿意为它们付出多少空间来定。**

---

### 5. 事务 ID 回卷：为什么 PG 宁肯拒绝服务

【事实】**官方给的那个"硬上限"，值得逐字读**：

> **一张表可以不被 `VACUUM` 的最长时间，是【20 亿个事务】减去上次激进 `VACUUM` 时的 `vacuum_freeze_min_age`。**
> **如果超过这个时间还没有被 `VACUUM`，就可能造成【数据丢失】。**

【推导】**把倒计时算出来**：

```text
事务 ID 可用范围约 2^31 ≈ 21 亿
某实例 500 TPS，且冻结完全停摆：

21 亿 ÷ 500 = 4.2 × 10⁶ 秒 ≈ 【48.6 天】  ← 撞上回卷红线

按三级阶梯拆开看：
  2 亿 ÷ 500 = 40 万秒 ≈ 4.6 天   ← autovacuum 被【强制】启动
  1.5 亿 ÷ 500 = 30 万秒 ≈ 3.5 天  ← 转激进扫描
  5000 万 ÷ 500 = 10 万秒 ≈ 1.2 天 ← 开始冻结
```

【结论】**「事务 ID 用完」在 500 TPS 下是一个以【周】计、逼近时以【天】计的量级**——**它不是理论问题，是有具体倒计时的运维约束。**

【事实】**PG 的应对是渐进升级的**：

```text
① 远未到期：正常
② 接近阈值：日志/监控告警
③ 非常接近：强制 autovacuum、可能拒绝新事务
④ 超过安全线：进入只允许维护操作的状态（业务写不进来）
```

【事实】**一个说明它有多严肃的细节**：**防回卷的 autovacuum 即使在其他情况下被关掉，系统也会启动它。**

【推论】**为什么这样设计**：**它宁可付出「短时间不可用」的代价，也不接受「静默丢数据/读错数据」。** **这个取舍本身是 PG 的一条设计哲学**（和 [[母题-P9-序列化失败与重试]] 的「宁可报错让你重试」是同一种态度）——**能把这个共性说出来，说明你理解了 PG 的价值观，而不只是记住了一个现象。**

【推论】**而且「拒绝服务」这个动作必须能被观测到才有意义**——**所以生产上必须监控 `age(relfrozenxid)` 与 `age(datfrozenxid)`，并设告警阈值**（**不是等它自己升级**）。

---

### 6. 膨胀已经发生了：三步处理（顺序不能反）

```
① 先切断长事务 / 离线复制槽（否则后面做什么都白做）
     → 设 idle_in_transaction_session_timeout、处理不活跃的复制槽
② 需要在线重建时用 pg_repack（而不是 VACUUM FULL）
     → VACUUM FULL 要排他锁 + 等量磁盘 + 大量 WAL
③ 最后才调 autovacuum 的阈值（大表按表调）
```

【推论】**第 ① 步排在最前面是有道理的**：**边界被按住时，第 ② 步的重建会被同样的长事务阻塞**，**第 ③ 步的清理会被同样的长事务清空**——**不先切断源头，后面两步都是无效工作。**

---

### 7. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「跑完 `VACUUM` 表就小了」 | **不缩小文件**——**它只把空间标记为可复用**；**要变小得 `VACUUM FULL` / `CLUSTER` / `pg_repack`** |
| 「`VACUUM FULL` 比 `VACUUM` 强，能用就用」 | **它要排他锁（业务中断）+ 等量磁盘 + 大量 WAL**——**大表上基本不可接受** |
| 「关掉 autovacuum 就没那些后台开销了」 | **防回卷的 autovacuum 即使被关掉也会启动**——**它绕不过去** |
| 「事务 ID 用完是个理论问题」 | **500 TPS 下是 48.6 天**——**有具体倒计时，而且官方的说法是超过就可能【丢数据】** |
| 「冻结就是把行锁住」 | **冻结是【改写行头上的事务 ID】为"永远可见"的标记**，**不是锁** |
| 「冻结越早做越好」 | **太早冻会白做功**——官方原话：**冻结一个很快又会被修改的行是浪费时间**（它一改就又拿到新 XID） |
| 「激进 VACUUM 和普通 VACUUM 差不多」 | **激进扫描要访问每一个可能含未冻结 XID 的页**——**本例是 20 倍 IO** |

## 二、自测

**Q1（计算）**：某实例 **500 TPS**。表 **200 万页**，其中 **5%** 的页有死元组。

问：**常规 VACUUM 扫多少页？激进 VACUUM 呢？为什么官方建议让 `vacuum_freeze_table_age` 留出余量？**

**A1**：

```text
常规 VACUUM：
  只扫可能含死元组的页 → 200 万 × 5% = 【10 万页】

激进扫描（官方口径：访问【每一个可能包含未冻结 XID 或 MXID 的页】）：
  → 【200 万页】

IO 放大 = 200 万 ÷ 10 万 = 【20 倍】
```

【结论】**被迫做一次激进 VACUUM = 一次 20 倍 IO 的扫描。**

【推论】**为什么官方要留余量**：

```text
vacuum_freeze_table_age（1.5 亿）比 autovacuum_freeze_max_age（2 亿）低
  → 常规/自动清理有机会在到达 2 亿【之前】顺手把冻结做掉
  → 于是不需要一次 20 倍 IO 的激进扫描

如果两者设得太近：
  → 表刚常规清理过，还没冻干净就撞上 2 亿
  → 被迫激进扫描——即使刚刚才 VACUUM 过
  （官方原话：这会导致"即使表最近为回收空间被清理过，
    仍然触发防回卷的 autovacuum"）
```

【取舍】**所以这三个数字是一组配合，不是三个独立旋钮**：

> **`vacuum_freeze_min_age`（什么时候开始冻）< `vacuum_freeze_table_age`（什么时候转激进）< `autovacuum_freeze_max_age`（什么时候强制）。**
> **它们之间的间距，就是"从容清理"和"被迫激进"之间的缓冲。**

**Q2（计算）**：某实例稳定 **500 TPS**，冻结完全停摆。

问：**大约多久会撞上回卷红线？按三级阶梯拆开，各在什么时候触发？**

**A2**：

```text
事务 ID 可用范围约 2^31 ≈ 【21 亿】

21 亿 ÷ 500 TPS = 4.2 × 10⁶ 秒 ≈ 【48.6 天】   ← 回卷红线

三级阶梯（都按 500 TPS 折算）：
  5000 万 ÷ 500 = 10 万秒 ≈ 【1.2 天】  ← 开始冻结
  1.5 亿 ÷ 500 = 30 万秒 ≈ 【3.5 天】   ← 转激进扫描
  2 亿 ÷ 500 = 40 万秒 ≈ 【4.6 天】     ← 强制 autovacuum（关掉也会启动）
```

【结论】**在 500 TPS 下，「一切正常」和「灾难」之间只有约 48.6 天**——**而告警窗口在第 4.6 天就开始了。**

【推论】**这意味着两件事**：

```text
① 冻结这件事【不能靠人盯】——48 天太久，没人会记得
   → 必须靠监控 age(relfrozenxid) 并设告警

② 但在高 TPS 的实例上，这个窗口会【急剧缩短】
   例：5000 TPS 时，21 亿 ÷ 5000 = 42 万秒 ≈ 【4.9 天】
   → 一个长周末没人管，就可能逼近红线
```

【补充】**这也解释了为什么「离线复制槽」和「长事务」这两件事必须被当作 P0 处理**——**它们不是"性能问题"，是"倒计时被按住了"。** **而 `pg_stat_activity` 里最老的 `backend_xmin` 就是那个倒计时的指针。**

**Q3（计算 + 判读）**：某表的行平均每天被修改一次。`vacuum_freeze_min_age` 目前是 5000 万。

问：**如果把它调到 100 万，会不会更安全？为什么官方说"冻结一个很快又会被修改的行是浪费时间"？**

**A3**：

```text
冻结一个行版本 = 改写它头上的事务 ID 为"永远可见"标记
  代价：一次页写入 + WAL

如果这行之后很快又被 UPDATE：
  → 它拿到【新的事务 ID】
  → 刚才那次冻结【作废】
  → 白做

某表行平均 1 天改一次：
  5000 万事务 ≈ 1.2 天（按 500 TPS）→ 刚过"平均修改间隔"就冻结
    → 有一部分行会白冻
  100 万事务 ≈ 33 分钟 → 【远小于 1 天】
    → 绝大多数被冻结的行，很快就会再被改
    → 【绝大部分冻结都是白做】
```

【结论】**调小 `vacuum_freeze_min_age` 会让 VACUUM 做大量无用功**——**它不提高安全性，只是让每一轮 VACUUM 更慢。**

【推论】**官方给的口径是**：

> **`vacuum_freeze_min_age` 应该设得足够大，使得行【在不太可能再被修改之后】才被冻结。**

【取舍】**所以三个数字各有各的作用**：

```text
vacuum_freeze_min_age    ：控制"哪些行值得冻"——太小会白做工
vacuum_freeze_table_age  ：控制"什么时候转激进扫描"——与 2 亿留出间距
autovacuum_freeze_max_age：控制"什么时候强制"——同时受 pg_xact 体积约束
```

【补充】**「白做功」这件事在监控上是有信号的**：**VACUUM 耗时变长但 `n_dead_tup` 降不下来**——**这时要查的不是阈值，是这两个 freeze 参数。**

**Q4（纠错）**：下面这段话哪里不准确？

> "表膨胀了，安排一个维护窗口做 `VACUUM FULL` 就行。"

**A4**：三处问题。

1. **`VACUUM FULL` 的代价比"一个窗口"大**：**它要【排他锁】（期间这张表完全不可读写）、要【等量额外磁盘空间】（新旧表同时存在）、还要【产生大量 WAL】**——**在一个已经很忙的实例上，WAL 量本身可能成为新问题。**
2. **大表上它可能跑不完那个窗口**：**重写 100 GB 的表不是几分钟的事**——**窗口估算错了会变成事故。**
3. **它治的是症状，不是病因**：**如果长事务还在，做完 `VACUUM FULL` 之后表会【继续胖回去】。**

【准确说法】"**先切病因，再谈重建**：**① 先把长事务 / 离线复制槽清掉；② 大表在线重建用 `pg_repack`（不长时间持锁）；③ `VACUUM FULL` 留给小表或真有窗口的场景。** **不做第 ① 步，第 ② ③ 步都是白做。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们关掉了 autovacuum，因为它太占资源；事务 ID 回卷那个问题，我们定期手动跑一次 VACUUM 就行。"

**A5**：四处问题。

1. **防回卷的 autovacuum 关不掉**：**官方原话是「即使 autovacuum 在其他情况下被禁用，系统也会启动 autovacuum 进程来防止回卷」**——**所以「关掉 autovacuum」只是关掉了常规清理，防回卷这一路照样会来。**
2. **「定期手动跑」在时间上算不过来**：**500 TPS 下红线是 48.6 天**（Q2），**但你无法预知未来的写入速率**——**一次批量导入就可能把倒计时从几周缩到几天。**
3. **手动跑的 VACUUM 不一定是「激进」的**：**只有 `relfrozenxid` 到 `vacuum_freeze_table_age` 才会转激进扫描**；**普通 VACUUM 可能只扫含死元组的页，冻不了几张页。**
4. **这治不了根因**：**如果长事务在，手动 VACUUM 一样推不动冻结。**

【准确说法】"**autovacuum 不该关**——**它对资源的影响应该靠【按表调参数】来控制**（比如 `autovacuum_vacuum_cost_delay`、每表的阈值），**而不是关掉整个机制。** **而防回卷这件事，唯一可靠的做法是监控 `age(relfrozenxid)` 并让它自然推进。**"

## 三、面试输出（学完再看）

**一句话结论**：**`VACUUM` 做三件事**：**把死元组的空间标记为「可复用」**（官方原话：**不会把空间还给操作系统**，除非表末尾整页空闲且能拿到排他锁）、**清理索引里指向死元组的条目**、**推进冻结**。**所以「跑完 VACUUM 表还是 10 GB」完全正常**——**它只是不再继续长。** **要真正变小只有三条路**：`VACUUM FULL`（**排他锁 + 等量磁盘 + 大量 WAL**）、`CLUSTER`、或 `pg_repack`（**在线重建，大表的正确答案**）。**而冻结是另一条独立的时间线**：**事务 ID 只有 32 位、循环使用，所以必须在 ID 绕回来之前把老行冻成"永远可见"**——**这是一条三级阶梯：`vacuum_freeze_min_age` 默认 5000 万（开始冻）、`vacuum_freeze_table_age` 默认 1.5 亿（转激进扫描）、`autovacuum_freeze_max_age` 默认 2 亿（强制防回卷，关了 autovacuum 也会启动）。** **激进扫描的代价是它会访问每一个可能含未冻结 XID 的页**——**本例是 20 倍 IO**，**所以这些参数之间要留间距，让从容清理有机会把冻结做掉。** **回卷是有倒计时的**：**500 TPS 下 48.6 天**（**5000 TPS 时就只剩 4.9 天**），而**官方的说法是「一张表最多可以 20 亿个事务不被 VACUUM，超过就可能造成数据丢失」**——**这是 PG 里唯一一处「运维不到位会真的丢数据」的机制。** 所以 **PG 的应对是渐进升级，最后宁可拒绝新事务**——**「宁可停机也不出错数据」，这和它宁可报 40001 让你重试是同一种态度。**

**恢复关键词**：三件事（标记可复用 · 清索引条目 · 推进冻结）/ **不还空间给操作系统** / `VACUUM FULL` 的三种代价 / `pg_repack` / **`50 + 20% × N`** / `autovacuum_max_workers` 3 / **冻结三级阶梯 5000 万 → 1.5 亿 → 2 亿** / **激进扫描 = 每页都访问（20 倍 IO）** / **`pg_xact` 体积是 2 亿这个默认值的理由** / **20 亿事务不 VACUUM 就可能丢数据** / **48.6 天（500 TPS）/ 4.9 天（5000 TPS）** / 关了 autovacuum 防回卷那路照样启动 / 太早冻结是白做功

**核心不变量 / 主线**：
**「回收」要拆成两个动作：把空间标记为可复用（普通 VACUUM）≠ 把空间还给操作系统（VACUUM FULL）。**
**而「冻结」是另一条独立的时间线：它不是为了让表变小，是为了让事务 ID 能安全地绕回来。**

**完整回答骨架**：`VACUUM` 三件事（不还空间）→ 三种重建手段的分工 → autovacuum 两道门槛（回顾）→ **冻结的三级阶梯** → **激进扫描的 20 倍代价与留间距的理由** → **回卷倒计时与渐进升级** → **「20 亿事务不 VACUUM 就可能丢数据」** → 处理三步（顺序不能反）→ 收束到「宁可停机也不出错数据」

**追问**（先说后看）

1. **为什么 `VACUUM FULL` 不能天天跑？** —— **它要排他锁（业务中断）、要等量额外磁盘、还要产生大量 WAL**。**小表可以，大表上等于一次业务中断。** **大表在线重建的正确工具是 `pg_repack`。**
2. **「冻结」这个词容易误解成什么？** —— **它不是"锁住"，是【改写行头上的事务 ID 为"永远可见"的标记】**。**而且它要付出一次页写入 + WAL**——**所以太早冻是浪费**（官方原话：冻结一个很快又会被修改的行是浪费时间）。
3. **为什么 `autovacuum_freeze_max_age` 默认只有 2 亿，不设大一点？** —— **官方给了理由：`VACUUM` 还允许从 `pg_xact` 子目录里移除旧文件，这就是为什么默认是一个相对低的值。** **官方还给了另一半建议：如果 `pg_xact` / `pg_commit_ts` 相对总库容很小，可以调到允许的最大值；否则按你愿意为它们付出多少空间来定。**
4. **关了 autovacuum 会怎样？** —— **常规清理没了，但【防回卷那一路照样会启动】**（官方原话）。**所以"关掉 autovacuum"只是把问题从"定期小清理"变成"突然一次激进扫描 + 业务被拒绝"**——**更糟。**
5. **怎么监控回卷风险？** —— **看 `age(relfrozenxid)`（每张表）和 `age(datfrozenxid)`（整个库）**，**设多级告警（比如 60% / 80% 各一档）**。**同时盯 `pg_stat_activity` 里最老的 `backend_xmin`——那是"倒计时有没有被按住"的直接指针**（[[母题-P14-长事务与表膨胀]]）。

**同类变体**

- 「PG 和 MySQL 在这条线上差多少？」—— **MySQL 完全没有"回卷"这个问题**（**它的 purge 是自动的，事务 ID 是 64 位且用法不同**）；**PG 有 VACUUM、冻结、回卷这三件 MySQL 没有的事**。**所以「PG 的 DBA 一半时间在跟膨胀打交道」不是夸张**——**这是版本留在堆里的直接后果**（[[母题-P13-MVCC与可见性]]）。
- 「`VACUUM FULL` 产生的 WAL 为什么值得单独一提？」—— **因为它把整张表重写到新文件**——**在流复制场景下，这些 WAL 还要传到所有备库并由它们重放**（[[母题-P12-流复制与逻辑复制]]）。**所以一次 `VACUUM FULL` 的影响是跨实例的。**
