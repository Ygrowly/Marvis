**导读**：必懂 3 件事（① **PG 没有间隙锁**——它不会因为「锁了一个范围」而阻止别人往这个范围里插入 ② 四种行锁的强弱关系，**选错要么挡不住、要么挡太多**，而选对能直接换回吞吐 ③ **PG 默认会无限等锁**——这和 MySQL 的锁等待超时是两回事）· 读完约 12 分钟 · 需要先懂：[[母题-P8-隔离级别与读一致性]]

**题目**：一个只用过 MySQL 的候选人说「RR 靠间隙锁防幻读」。这句话在 PG 里哪里不成立？

**母题**：PG 没有间隙锁，幻读和写偏斜靠什么防？`FOR UPDATE` 的四个变体怎么选？

**为什么重要**：这是**「最容易说反的一处」**——因为它不是「PG 也有类似的东西只是名字不同」，而是**PG 从根本上换了一套机制**。而且它接得很实：**为什么你的项目选条件更新而不选 `FOR UPDATE`（P18），答案就在这里**——PG 的显式锁有四种强度，选错要么挡不住、要么挡太多。

**一句话结论**：**PG 没有间隙锁**——它不会因为「锁了一个范围」而阻止别人往这个范围里插入（MySQL 的 next-key lock 会）。所以防幻读只有两条路：**提高隔离级别靠快照（RR / Serializable，冲突时报错重试）**，或者**用显式锁 / 谓词式约束（唯一约束、条件更新）自己把不变量守住**。四种行锁从强到弱：`FOR UPDATE` → `FOR NO KEY UPDATE` → `FOR SHARE` → `FOR KEY SHARE`。

**恢复关键词**：**无间隙锁** / 不阻塞插入 / FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE / **外键用最弱的 KEY SHARE** / **普通 UPDATE 对应 NO KEY UPDATE，但改被外键引用的键列会升到 UPDATE** / **PG 默认无限等锁** / advisory lock

**核心不变量 / 主线**：
**MySQL 用「范围锁」把幻读挡在门外；PG 用「多版本快照」让幻读不产生错误结果，代价是冲突时要报错重试。** 一个靠「不许发生」，一个靠「发生但可检测」——**理解这个分歧，后面的锁与隔离全都能推出来。**
**而 PG 把「锁的强度」做成了四档可选**——**这不是细节，这是它把并发控制的成本交还给应用的一种方式。**

**完整回答骨架**：PG 为什么没有间隙锁 → 那幻读怎么防（两条路）→ **四种行锁的冲突矩阵与选档位** → 外键为什么用最弱的那个 → **PG 默认无限等锁（与 MySQL 的对比）** → 写偏斜为什么更麻烦 → 工程上怎么选

**完整回答（口述稿）**：
**PG 没有间隙锁**——它不会因为"锁了一个范围"而阻止别人往这个范围里插入（**MySQL 的 next-key lock 会**）。所以防幻读只有两条路：**提高隔离级别靠快照**（RR / Serializable，冲突时报错重试），或者**用显式锁 / 谓词式约束（唯一约束、条件更新）自己把不变量守住**。

四种行锁从强到弱：**`FOR UPDATE` → `FOR NO KEY UPDATE` → `FOR SHARE` → `FOR KEY SHARE`**——前两种是写意图，后两种是读锁；`FOR KEY SHARE` 最弱（只挡删改主键，允许改非键列），是外键检查用的。

面试安全底线：**"PG 也有间隙锁"和"MySQL 不需要间隙锁"都是明确错误**。死锁排查工具也不同（MySQL 是 `SHOW ENGINE INNODB STATUS`，PG 是查锁等待视图）。

**分层要点**：
- **结论**：PG 无间隙锁；防幻读靠快照或自己守不变量；四种行锁强度有序。
- **推导链**：无间隙锁 → 插不进去拦不住 → 只能靠快照或谓词式约束 → 四种行锁各自的强度与用途。
- **量化**：四种行锁（FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE）。
- **边界与常见误解**：把 MySQL 的 next-key lock 套到 PG 上是错的；外键检查用最弱的 FOR KEY SHARE。

## 一、教材

### 1. PG 为什么没有间隙锁

MySQL 的 next-key lock = **记录锁 + 间隙锁**：锁定「某个范围」，从而**阻止别人在这个范围内插入新行**，这样「第二次查询不会多出几行」（防幻读）。

PG 的做法完全不同：**读操作完全不加锁**，靠**快照**保证「你看到的数据是某个一致时刻的」。所以：

- 「幻读」在 PG 里表现为：**你换了快照就会看到新行（RC 下每条语句一次快照，[[母题-P8-隔离级别与读一致性]]），或看到旧快照（RR/Serializable 下）**；
- **PG 不会为此阻塞插入**——所以**插入和范围查询几乎不互相干扰，并发度更高**。

【推论】**「无间隙锁」有一个必须记住的后果**：

> **你锁不住「还不存在的行」。** 一个范围查询锁到的只是**当下匹配的那些行**——**别人仍然可以在你锁住的范围内插入新行。**

【结论】**这就是为什么「先查一遍有没有，再插入」这个动作在 PG 里天然有竞态**——**必须靠唯一约束兜底，不能靠锁**（[[母题-P19-唯一约束与UPSERT]]）。

**这就是为什么「PG 没有间隙锁」不是缺陷，而是另一条设计路线。**

---

### 2. 幻读和不变量：两条路

| 需求 | 路径 |
|---|---|
| 「我这段计算要基于同一时刻的数据」 | **提隔离级别**（RR / Serializable），接受 `40001` 重试（[[母题-P9-序列化失败与重试]]） |
| 「某个跨行不变量绝不能破」 | **用锁或约束显式守住**：`FOR UPDATE` 锁住涉及行、**唯一约束**堵住重复、**条件更新**把判断与写入合并（P18/P19） |

【推论】**关键判断**：**PG 不会自动帮你把不变量守住**（不像 MySQL 会用间隙锁顺手挡住一部分幻读），所以**PG 的业务正确性更依赖「显式约束 + 显式锁」，而不是「依赖默认隔离级别」。** **这句话说出来，对 PG 的理解层次就到位了。**

### 3. 四种行锁：一个冲突矩阵定强弱

::figure pg-row-locks.svg | 四种行锁的冲突矩阵与选档位的收益 | 四种行锁两两是否冲突、外键为什么用最弱的那档、普通更新真正拿的是哪一档、无间隙锁带来的后果

【事实】**官方原文**：**「行级锁不影响数据查询，它们只阻塞对同一行的【写者与加锁者】。」**

| 模式 | 官方定义（要点） |
|---|---|
| `FOR UPDATE` | **最强**：**阻止**其他事务对这行做 `UPDATE` / `DELETE` / `FOR UPDATE` / `FOR NO KEY UPDATE` / `FOR SHARE` / `FOR KEY SHARE` |
| `FOR NO KEY UPDATE` | 比它弱：**不阻塞 `FOR KEY SHARE`** |
| `FOR SHARE` | 共享锁：**阻塞** `UPDATE` / `DELETE` / `FOR UPDATE` / `FOR NO KEY UPDATE`，**不阻塞** `FOR SHARE` / `FOR KEY SHARE` |
| `FOR KEY SHARE` | **最弱**：**阻塞 `FOR UPDATE`**，**但不阻塞 `FOR NO KEY UPDATE`** |

【事实】**官方给出的冲突矩阵（表 13.3）**——**这是判断一切锁问题的唯一依据**：

| 请求的锁 ↓ ／ 已持有的锁 → | FOR KEY SHARE | FOR SHARE | FOR NO KEY UPDATE | FOR UPDATE |
|---|---|---|---|---|
| **FOR KEY SHARE** | | | | **✗** |
| **FOR SHARE** | | | **✗** | **✗** |
| **FOR NO KEY UPDATE** | | **✗** | **✗** | **✗** |
| **FOR UPDATE** | **✗** | **✗** | **✗** | **✗** |

【推论】**从矩阵里能读出两件反直觉的事**：

1. **`FOR KEY SHARE` 和 `FOR SHARE` 之间完全不冲突，和 `FOR NO KEY UPDATE` 也不冲突**——**这就是「弱档位能大幅减少阻塞」的来源**；
2. **只有 `FOR UPDATE` 是「和谁都冲突」的**——**所以它是最后手段，不是默认选择**。

【纠正常见误解】**普通 `UPDATE` 拿的是哪一档？** 官方原话：

> **`FOR NO KEY UPDATE` …这个锁模式也被任何【没有拿到 `FOR UPDATE` 锁】的 `UPDATE` 获取。**
> **而 `FOR UPDATE` 锁模式也被任何 `DELETE` 获取，以及任何【修改了某些列的】`UPDATE` 获取。目前被考虑的那组列，是那些【上面有可用于外键的唯一索引】的列**（所以部分索引和表达式索引不算）。

【推论】**这条把「改哪一列」和「阻塞谁」连起来了**：

```text
UPDATE t SET note = ? WHERE id = ?        → FOR NO KEY UPDATE（弱）
  → 不阻塞子表的 FOR KEY SHARE 插入  ✔

UPDATE t SET id = ? WHERE ...             → FOR UPDATE（强）
  → 阻塞所有 FOR KEY SHARE（包括外键检查）
  → 也阻塞其他一切
```

【结论】**「改一个被外键引用的键值」是一个远比「改一个普通字段」重的动作**——**这是很多 ORM 无脑 `SET` 全字段时踩的坑**：**它可能顺手把一个本该是弱锁的更新升级成了 `FOR UPDATE`。** **「更新时只 SET 你真正改的字段」这条建议，在 PG 里有一个具体的并发收益。**

**到这里你应该能回答**：为什么「`FOR UPDATE` 是最强的所以最安全」这个直觉在 PG 里是错的？

### 4. 外键用最弱的 `FOR KEY SHARE`【事实】

【推导】**为什么外键只需要最弱的那一档**：

```text
外键约束需要保证的事情，只有一件：
  「被引用的那个键【还在】」

它不需要：
  ✗ 阻止别人改被引用行的【其他字段】
  ✗ 阻止别人读它

它需要：
  ✔ 没人删这一行
  ✔ 没人改【键值】本身

→ 这正好就是 FOR KEY SHARE 的定义
```

【结论】**所以「向子表插入一行」通常不会和被引用行的普通更新互相阻塞**——**因为普通更新拿的是 `FOR NO KEY UPDATE`，而它和 `FOR KEY SHARE` 不冲突**（看矩阵）。

【取舍】**官方对它的定位是一句实用的建议**：

> **应该确保一个事务中在某个对象上获取的【第一个锁】，是该对象后续需要的【最严格的】模式。**
> **最好的防死锁办法是避免死锁：确保所有应用都以【一致的顺序】在多个对象上获取锁。**

【推论】**这两句话合起来是一条设计规则**：**要么一开始就拿最强的锁（避免中途升级），要么始终按同一个顺序拿（避免交叉等待）。** **最糟的是"先拿弱的、中途想升级"**——**因为锁升级在 PG 里会互相等待。**

**到这里你应该能回答**：为什么「给表加个外键会让写入变慢」这个担心，在 PG 里通常不成立？

### 5. 一个必须知道的默认值：PG 会【无限】等锁【事实】

**官方原文**：

> **只要没有检测到死锁，一个寻求表级或行级锁的事务会【无限期地等待】冲突锁被释放。**
> **这意味着让应用长时间持有事务是个坏主意**（比如在等用户输入的时候）。

【事实】**死锁检测的机制与默认值**：

> **PostgreSQL 会自动检测死锁并解决它们——牺牲掉其中一个事务，让其余的完成。**（**具体牺牲哪一个难以预测，不应该依赖它。**）
> `deadlock_timeout`（默认 **1 秒**）：**在锁上等待多久之后去检查是否存在死锁。** 死锁检查相对昂贵，所以服务器不是每次等锁都查——**它乐观地假设生产应用里死锁不常见，先等一会儿再说。**

【推导】**把「无限等锁」的后果算出来**：

```text
某个事务因为写了外部 API / 等人工确认，持锁 30 秒
  → 后续所有要碰这一行的请求【全部排队】
  → 连接池 100 条连接在 30 秒内被这个队列占满
  → 正常能扛 100 ÷ 0.05s = 2000 QPS，此刻读请求也拿不到连接
  → 故障形态：不是"某个接口慢"，是【整站超时】
```

【推论】**判据**：

> **PG 的「无限等锁」意味着：一个失控的事务不只是自己慢，它会把整个连接池变成它的等待队列。**
> **所以 `lock_timeout` / `statement_timeout` / `idle_in_transaction_session_timeout` 这三个参数在生产上是必须设的——它们是给"失控事务"准备的保险丝。**

【方言差异】**这是与 MySQL 最容易混淆的一处**：**MySQL 有 `innodb_lock_wait_timeout`（默认 50 秒），等不到就报错**；**PG 默认【无限等】，只靠死锁检测兜底**。**所以「MySQL 里这行代码会报超时」和「PG 里这行代码会一直挂着」是两个不同的现象。**

**到这里你应该能回答**：为什么「我们的事务里调了一下第三方接口」这件事，在 PG 里比在 MySQL 里更危险？

### 6. advisory lock：不写表也能加锁【事实】

**官方定义**：

> **PostgreSQL 提供了创建【应用自定义含义】的锁的手段，叫 advisory lock（咨询锁）——因为【系统不强制它的使用】，用对用错取决于应用自己。**
> **它适合那些不太契合 MVCC 模型的加锁策略。** 一个常见用法是**模拟那种「扁平文件」数据管理系统的悲观锁策略**。

【推导】**为什么它比「在表里插一个标志位」更好——官方给了三条**：

```text
在表里插标志位（自己实现锁）        用 advisory lock
  → 多一次写                    → 只在内存里
  → 产生死元组 → 表膨胀（P14）    → 【避免表膨胀】
  → 崩溃后标志位残留             → 【会话结束自动清理】
  → 要自己写清理逻辑             → 不用
```

【事实】**两个级别，区别在「回滚时会不会释放」**：

| 级别 | 何时释放 | 是否遵守事务语义 |
|---|---|---|
| **会话级**（`pg_advisory_lock`） | **显式解锁或会话结束** | **不遵守**——**事务回滚后锁仍然被持有**；同一个进程可以重复获取，每次都要配对解锁 |
| **事务级**（`pg_advisory_xact_lock`） | **事务结束时自动释放** | 遵守；没有显式解锁操作 |

【取舍】**官方明确说：短期使用 advisory lock，事务级往往比会话级更方便。** **而会话级那个「回滚后仍然持有」的行为，是最容易踩的坑**——**它和普通锁的直觉相反。**

【事实】**它的存储与上限**：**advisory lock 和普通锁共用同一个共享内存池，大小由 `max_locks_per_transaction` 和 `max_connections` 决定。** **必须小心不要耗尽它——否则服务器将【完全无法授予任何锁】。** **典型上限是几万到几十万个。**

【结论】**所以 advisory lock 不是免费的**：**它是一个有全局上限的共享资源，用得失控会波及整个实例。**

【事实】**排查工具**：**所有 advisory lock 都能在 `pg_locks` 里查到。**

### 7. 写偏斜：比幻读更麻烦的东西

【事实】**定义**：两个事务**读的集合和写的集合都不重叠**，但合起来破坏了一个跨行不变量。

【推导】**经典例子**：约束是「至少有一名医生值班」。

```text
事务 A：SELECT count(*) WHERE on_call = true  → 2（够）
        把其中一人设为不值班
事务 B：SELECT count(*) WHERE on_call = true  → 2（够）
        把【另一人】设为不值班

结果：0 人值班 —— 不变量破了
```

【结论】**A 的读集不包含 B 要写的行，写集也不重叠**——**所以 RC 和 RR 都拦不住**。

【推论】**为什么 RC/RR 拦不住**：**快照隔离只保证「你看到的是一致的」，它不保证「你的读和你的写之间没有别人插进来」。**

**三条解法**：

1. **Serializable（SSI）**：它能检测出这种依赖环 → 报错重试（[[母题-P9-序列化失败与重试]]）——**这是最省心的解法**；
2. **显式锁**：**把「读」也加锁**（`FOR UPDATE` 锁住所有涉及行），退化成悲观并发的写法；
3. **改成约束 / 单行聚合**：**把跨行不变量收敛成一个能被数据库原子保护的东西**（比如在一行里维护计数并用条件更新守护）。

【推论】**第 3 条最值钱**：**工程上最好的做法不是「加锁保护不变量」，而是「把不变量设计成不需要跨行保护」**——**这是设计层面的解法，比机制层面的更根本。**

### 8. 死锁：PG 里怎么来、怎么减少

- **来**：两个事务以不同顺序锁同一批行（`UPDATE` 顺序不一致、`FOR UPDATE` 顺序不一致），或者 **RC 下 `UPDATE` 重新检查最新版本**（P8）造成的互相等待；
- **减少**（前两条是官方原话）：
  1. **统一加锁/更新顺序**（例如总是按主键升序更新）；
  2. **对象上拿的第一个锁就是后续需要的最强那一档**（避免中途升级）；
  3. **缩短事务**、别在事务里做网络 IO 或等人工确认（官方明确点名这个场景）；
  4. **能不用锁就不用锁**——条件更新把「等待」变成「0 行受影响」，**根本不产生锁等待，也就没有死锁**。

【推论】**第 4 条接到 P18**：**PG 里减少死锁最有效的手段不是调参，而是换并发控制方式。**

### 9. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「PG 也靠间隙锁防幻读」 | **PG 没有间隙锁**——它靠快照挡幻读，**代价是串行化冲突时重试** |
| 「`FOR UPDATE` 最强所以最安全」 | **它是唯一和一切都冲突的那一档**——**不该阻塞的也阻塞了** |
| 「外键会阻塞被引用行的所有更新」 | **只要没改键值**，外键的 `FOR KEY SHARE` 和普通更新的 `FOR NO KEY UPDATE` **不冲突** |
| 「普通更新都是 `FOR NO KEY UPDATE`」 | **改被外键引用的键列时，UPDATE 会升到 `FOR UPDATE`** |
| 「PG 的锁等不到会像 MySQL 一样超时」 | **PG 默认【无限等】**——只有死锁检测会救你 |
| 「advisory lock 是内存里的，所以随便用」 | **和普通锁共用同一个内存池**——**耗尽它会让服务器完全无法授予任何锁** |
| 「advisory lock 也会被回滚掉」 | **会话级 advisory lock 不遵守事务语义**——**回滚后仍然持有** |

## 二、自测

**Q1（判读 + 计算）**：一张主表被一张子表用外键引用。主表上每秒有 **100 次更新**，每次更新持锁约 **5ms**；子表每秒有 **200 次插入**。

问：**如果主表那些更新改的是普通字段，子表插入会被阻塞多少？如果改的是被外键引用的键值呢？**

**A1**：

```text
情况一：改【普通字段】
  UPDATE 拿 FOR NO KEY UPDATE
  子表插入的外键检查拿 FOR KEY SHARE
  查矩阵：FOR NO KEY UPDATE × FOR KEY SHARE = 【不冲突】
  → 阻塞时间 = 【0】

情况二：改【被外键引用的键值】
  UPDATE 升级为 FOR UPDATE
  查矩阵：FOR UPDATE × FOR KEY SHARE = 【冲突】
  → 每次更新都会挡住子表插入
  → 阻塞占比 = 100 × 5ms = 500ms/秒 = 【50% 的时间】
```

【结论】**同一个 `UPDATE` 语句，改的列不同，对子表的阻塞从 0 变成一半时间。**

【推论】**判据**：

> **在 PG 里，「你改的是哪一列」决定了你拿的是哪一档锁，而拿哪一档锁直接决定了阻塞面。**
> **所以「更新时只 SET 真正需要改的字段」这条建议，在 PG 里不只是减少 WAL 与索引维护——它还有一个直接的并发收益。**

【补充】**这条也解释了 ORM 的一个隐蔽问题**：**「查出整行 → 改一个字段 → 存回整行」这种写法，会把所有列都写一遍**——**只要其中碰巧包含被外键引用的键列，锁就升级了。** **这是「看不见的性能问题」的典型来源。**

**Q2（判读 + 计算）**：一个事务因为要调外部支付接口，**持锁 30 秒**才提交。同一行上还有持续到达的写请求。连接池 100 条，正常一个请求 50ms。

问：**这 30 秒里会发生什么？为什么说 PG 的「无限等锁」让这件事比 MySQL 更危险？**

**A2**：

```text
PG 默认「无限期等待冲突锁被释放」
  → 后续所有碰这一行的请求【不是报错，而是挂住】
  → 每个请求占住一条连接不放
  → 30 秒内，100 条连接被占满

正常吞吐：100 ÷ 0.05s = 2000 QPS
此刻吞吐：【0】（读请求也拿不到连接）

→ 故障形态：不是"某个接口慢"，是【整站超时】
```

【结论】**一个失控事务 = 一个把整个连接池变成自己等待队列的队列头。**

【推论】**对比 MySQL**：**MySQL 有 `innodb_lock_wait_timeout`（默认 50 秒），等不到会报错释放连接**；**PG 默认无限等**——**所以同样一行代码，在 MySQL 里会"报个超时错误、连接归还"，在 PG 里会"一直挂着、连接不归还"。** **故障形态完全不同。**

【判据与动作】：

> **PG 的生产环境必须设三根保险丝**：`lock_timeout`（单次等锁上限）、`statement_timeout`（单条语句上限）、`idle_in_transaction_session_timeout`（空事务上限）。
> **没有它们，一个忘记提交的事务就能拖垮整个实例。**

【补充】**官方也点名了这个场景**：**「让应用长时间持有事务是个坏主意（比如在等用户输入的时候）。」** **把外部 IO 放进事务里，正是在制造这种事务。**

**Q3（判读 + 计算）**：约束是「一个租户必须至少有一个管理员」。表里有 `tenant_id`、`role`、`user_id`。

问：**这个不变量能不能靠 `FOR UPDATE` 守住？为什么它比单行不变量更难？**

**A3**：

```text
不安全的两步操作：
  ① SELECT count(*) FROM members
     WHERE tenant_id = 1 AND role = 'admin'    → 2
  ② UPDATE members SET role = 'member'
     WHERE tenant_id = 1 AND user_id = 7
  → 提交后可能只剩 1 个 → 另一个并发事务同样做，剩 0 个

能不能靠 FOR UPDATE？
  ① 改成 SELECT ... FOR UPDATE 锁住查到的行 → 【可以】，
     但前提是【所有】改这个不变量的路径都这么做
  ② 而且它把「读」也变成了加锁 → 退化成悲观并发
  ③ 更麻烦的是：如果租户【一个管理员都没有】，
     第一步查出来是 0 行 → 【锁不住任何东西】
     → 这正是「无间隙锁」的直接后果
```

【结论】**跨行不变量在 PG 里更难的三个原因**：① **要锁住"读到的行"，就必须所有路径都记得加锁**（漏一条就有竞态）；② **锁住了就没法并发**；③ **要防"不存在"的情况时，`FOR UPDATE` 锁不住空集**（**因为没有间隙锁**）。

【推论】**三条解法按推荐度排序**：

```text
最好：把不变量收敛到【一行】上
  → 比如 members 表里每个租户有一行 admin_count
  → 用条件更新守护：UPDATE ... SET admin_count = admin_count - 1
                    WHERE tenant_id = ? AND admin_count > 1
  → 影响 0 行 = 不变量会被破坏 = 【业务冲突，拒绝】
  → 不产生锁等待，天然幂等（P18）

次好：Serializable（SSI）
  → 它能自动检测这种依赖环（P9）→ 报 40001 重试

最差：显式锁 + 全体路径统一纪律
  → 任何一条路径忘了加锁，不变量就破了
```

【结论】**判据**：

> **最好的做法不是「加锁保护不变量」，而是「把不变量设计成不需要跨行保护」。**
> ——**这是设计层面的解法，比机制层面的更根本。**

**Q4（纠错）**：下面这段话哪里不准确？

> "MySQL 的 RR 靠 next-key lock 防幻读，PostgreSQL 也是一样的思路，只是锁的名字不同。"

**A4**：三处问题。

1. **PG 根本没有间隙锁**：**它的读操作完全不加锁，靠快照保证一致性**。**「PG 也靠间隙锁」是明确的概念性错误**——和「SSE 是短连接」同一级别。
2. **幻读在 PG 里不是"被锁挡住"，而是"被快照定义"**：**RC 下它本来就会发生（每条语句一个快照），RR/Serializable 下它不会发生（整个事务一个快照）**——**但代价是冲突时报 `40001` 重试**，**不是阻塞插入**。
3. **两者的并发行为是相反的**：**MySQL 会【阻止别人插入】（表现为插入被阻塞）；PG 【不会】，它要么让你看到旧快照、要么在冲突时报错。**

【准确说法】"**MySQL 用范围锁把幻读挡在门外；PG 用快照让幻读不产生错误结果——一个靠"不许发生"，一个靠"发生但可检测"。** **所以 PG 里守住不变量的正确姿势是显式约束 + 显式锁，而不是依赖默认隔离级别。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们用了 `SELECT ... FOR UPDATE`，而且只锁了查到的行，所以不会有并发问题。"

**A5**：三处问题。

1. **它锁不住"还不存在的行"**（Q3 的第 ③ 点）：**如果查询返回 0 行，`FOR UPDATE` 锁了个空**——**别人照样可以在你这个范围里插入。** **这正是「无间隙锁」的直接后果。**
2. **它需要「读的时候也用它」**：**只要有一条路径是普通 `SELECT` 然后 `UPDATE`，竞态就回来了**——**而「所有路径统一纪律」在多人协作的项目里非常脆弱。**
3. **它把并发冲突从「报错重试」换成了「排队等待」**：**而 PG 默认会【无限等】**（第 5 节）——**高并发下这会把连接池变成等待队列**。

【准确说法】"**`FOR UPDATE` 能守住「存在行」上的不变量，守不住「不存在」的不变量。** **要把不变量收敛成一行上的条件更新（或者上 Serializable），而不是靠一把锁挡在流程中间。**"

## 三、面试输出（学完再看）

**一句话结论**：**PG 没有间隙锁**——**读不加锁，它靠多版本快照保证一致性**。所以「幻读」在 PG 里不是被锁挡住的，而是**被快照定义的**：**RC 下它本来就会发生（每条语句一个快照），RR/Serializable 下它不会发生（整个事务一个快照），代价是串行化冲突时报 `40001` 重试**。**直接后果是：你锁不住「还不存在的行」，所以「先查再插」在 PG 里天然有竞态，必须靠唯一约束兜底，不能靠锁。** **四种行锁的强弱由一个冲突矩阵决定**：`FOR UPDATE`（**唯一和一切都冲突的，所以是最后手段**）→ `FOR NO KEY UPDATE`（**普通 `UPDATE` 拿的就是这一档**）→ `FOR SHARE` → `FOR KEY SHARE`（**最弱，外键检查用的就是它**）。**外键用最弱的那档是因为它只需要保证"键还在"**——**所以「向子表插入」通常不会和「对被引用行的普通更新」互相阻塞**。**但有一个隐蔽的升级**：**如果 `UPDATE` 改的是「有可用外键的唯一索引」的列，它会升级成 `FOR UPDATE`**——**所以"更新时只 SET 真正改的字段"在 PG 里有一个直接的并发收益**。**最后一条最容易被忽略**：**PG 默认【无限期等锁】**（官方原话），只有 `deadlock_timeout`（默认 1 秒）会去检测死锁——**这和 MySQL 的 `innodb_lock_wait_timeout`（默认 50 秒）完全不同**：**同样一行代码，MySQL 会报超时归还连接，PG 会一直挂着不归还**。**所以生产上 `lock_timeout` / `statement_timeout` / `idle_in_transaction_session_timeout` 是必须设的保险丝。**

**恢复关键词**：**无间隙锁**（读不加锁）/ 幻读靠快照定义而非锁 / **锁不住不存在的行** / 冲突矩阵（FOR UPDATE 和一切都冲突）/ **普通 UPDATE = FOR NO KEY UPDATE** / **改外键引用的键列 → 升到 FOR UPDATE** / 外键 = FOR KEY SHARE / **PG 默认无限等锁** / `deadlock_timeout` 1 秒 / 三根保险丝 / advisory lock（会话级不遵守事务语义 · 共用锁内存池）/ 写偏斜

**核心不变量 / 主线**：
**MySQL 用「范围锁」把幻读挡在门外；PG 用「多版本快照」让幻读不产生错误结果，代价是冲突时要报错重试。**
**推论：PG 里守住不变量的正确姿势是「显式约束 + 显式锁」，而不是依赖默认隔离级别。**

**完整回答骨架**：无间隙锁（读不加锁、锁不住不存在的行）→ 这两条路（提级别 / 显式约束）→ **四种行锁的冲突矩阵与选档位** → **外键为什么用最弱的，以及那个隐蔽的锁升级** → **PG 默认无限等锁（与 MySQL 的对比）** → advisory lock → 写偏斜与「把不变量收敛到一行」→ 收束到「PG 把并发控制的成本交还给应用」

**追问**（先说后看）

1. **`FOR UPDATE` 是不是就万无一失了？** —— 不是。① **它只锁匹配到的行**，如果范围里还没有行（还没插入），照样锁不住——**这正是「无间隙锁」的直接后果**；② 它需要**读的时候也用它**，一旦某条路径忘了加锁就出现竞态；③ **它会把并发冲突从「报错重试」变成「排队等待」**，而 **PG 默认无限等**，高并发下可能拖垮吞吐。
2. **那 RuleArena 为什么优先条件更新？** —— **项目文档给的理由是「权威性」不是「频率」**：**04 §15 原话「MVP 优先业务唯一键 + 条件更新」**，**Q7 原话「锁可以降低竞争，但不能成为资金正确性的唯一保证……只有真实高竞争时再评估锁」**——**注意文档 04 §12 同时给了「锁定订单行【或】乐观版本条件更新」，所以不要说成「完全不用锁」**；**准确说法是「优先条件更新，锁留到真实高竞争时再评估」**。**而且条件更新天然幂等**（重复执行第二次影响 0 行），**唯一约束负责最终防线**（[[母题-P18-乐观并发控制]]）。
3. **`SELECT ... FOR UPDATE` 和 `UPDATE` 自己差在哪？** —— **`UPDATE` 会自动加行锁**（普通更新对应 `FOR NO KEY UPDATE`，改键列则升到 `FOR UPDATE`）；**`FOR UPDATE` 是先把行锁住再去判断/计算**，用于「读—判断—写」跨越多次交互的场景。**另外官方提醒：`SELECT FOR UPDATE` 会因为"标记行已锁"而产生磁盘写。**
4. **PG 的表锁呢？** —— **PG 有一套 8 种表级锁**（`ACCESS SHARE` 到 `ACCESS EXCLUSIVE`），**日常业务基本不用**；**要被提醒的是 `ALTER TABLE` 会拿较重的表锁**——那才是真正会堵住整张表的（[[母题-P4-索引代价与在线建索引]]）。
5. **advisory lock 适合做什么？** —— **适合那些"不适合用表里的标志位"的锁**：**官方说它比标志位更快、避免表膨胀、而且会话结束时服务器自动清理。** **典型场景是调度器选主、单例任务互斥。** **但要注意两个坑：会话级的不遵守事务语义（回滚后仍持有），以及它和普通锁共用同一个内存池——耗尽它会让服务器无法授予任何锁。**

**同类变体**

- 「PG 和 MySQL 的锁模型差多少？」—— **① PG 无间隙锁，MySQL 有**（next-key lock）；**② PG 行锁有四档，MySQL 只有两档**（`FOR UPDATE` / `LOCK IN SHARE MODE`）；**③ PG 默认无限等锁，MySQL 有 50 秒超时**；**④ PG 有 advisory lock、MySQL 靠 `GET_LOCK()`**。**四条说清，这道题就满分。**
- 「怎么知道是谁在等锁？」—— **`pg_locks`（含 `SIReadLock` 与 advisory lock）+ `pg_stat_activity.wait_event_type = 'Lock'`**。**能说出 `wait_event_type` 就说明你真的排过线上锁问题。**
