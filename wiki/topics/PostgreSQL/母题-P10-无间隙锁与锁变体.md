# 母题 P10 · 无间隙锁与锁变体

> **模块**：PostgreSQL / 事务与锁
> **所属主线**：三 · 事务与锁（并发改同一份数据，为什么不会乱）
> **关联母题**：[[母题-P8-隔离级别与读一致性]] · [[母题-P9-序列化失败与重试]] · [[母题-P18-乐观并发控制]]
> **素材来源**：`study/09-数据缓存队列与一致性` 第 2.4 节 + 通用知识（**四种行锁的细节待你核对**）

**题目**：一个只用过 MySQL 的候选人说「RR 靠间隙锁防幻读」。这句话在 PG 里哪里不成立？

**母题**：PG 没有间隙锁，幻读和写偏斜靠什么防？`FOR UPDATE` 的四个变体怎么选？

**为什么重要**：这是**「最容易说反的一处」**——因为它不是「PG 也有类似的东西只是名字不同」，而是**PG 从根本上换了一套机制**。而且它接得很实：**为什么你的项目选条件更新而不选 `FOR UPDATE`（P18），答案就在这里**——PG 的显式锁有四种强度，选错要么挡不住、要么挡太多。

**一句话结论**：**PG 没有间隙锁**——它不会因为「锁了一个范围」而阻止别人往这个范围里插入（MySQL 的 next-key lock 会）。所以防幻读只有两条路：**提高隔离级别靠快照（RR / Serializable，冲突时报错重试）**，或者**用显式锁 / 谓词式约束（唯一约束、条件更新）自己把不变量守住**。四种行锁从强到弱：`FOR UPDATE` → `FOR NO KEY UPDATE` → `FOR SHARE` → `FOR KEY SHARE`。

**恢复关键词**：**无间隙锁** / 不阻塞插入 / FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE / 外键用最弱的 KEY SHARE / 写偏斜

**核心不变量 / 主线**：
**MySQL 用「范围锁」把幻读挡在门外；PG 用「多版本快照」让幻读不产生错误结果，代价是冲突时要报错重试。** 一个靠「不许发生」，一个靠「发生但可检测」——**理解这个分歧，后面的锁与隔离全都能推出来。**

**完整回答骨架**：PG 为什么没有间隙锁 → 那幻读怎么防（两条路）→ 四种行锁强度与用途 → 外键为什么用最弱的那个 → 写偏斜为什么更麻烦 → 工程上怎么选

## 原理分解

### 一、PG 为什么没有间隙锁

MySQL 的 next-key lock = **记录锁 + 间隙锁**：锁定「某个范围」，从而**阻止别人在这个范围内插入新行**，这样「第二次查询不会多出几行」（防幻读）。

PG 的做法完全不同：**读操作完全不加锁**，靠**快照**保证「你看到的数据是某个一致时刻的」。所以：

- 「幻读」在 PG 里表现为：**你换了快照就会看到新行（RC 下每条语句一次快照，P8），或看到旧快照（RR/Serializable 下）**；
- **PG 不会为此阻塞插入**——所以**插入和范围查询几乎不互相干扰，并发度更高**。

**这就是为什么「PG 没有间隙锁」不是缺陷，而是另一条设计路线。**

### 二、幻读和不变量：两条路

| 需求 | 路径 |
|---|---|
| 「我这段计算要基于同一时刻的数据」 | **提隔离级别**（RR / Serializable），接受 `40001` 重试（P8 / P9） |
| 「某个跨行不变量绝不能破」 | **用锁或约束显式守住**：`FOR UPDATE` 锁住涉及行、**唯一约束**堵住重复、**条件更新**把判断与写入合并（P18/P19） |

**关键判断**：**PG 不会自动帮你把不变量守住**（不像 MySQL 会用间隙锁顺手挡住一部分幻读），所以**PG 的业务正确性更依赖「显式约束 + 显式锁」，而不是「依赖默认隔离级别」**。这句话说出来，对 PG 的理解层次就到位了。

### 三、四种行锁：从强到弱

| 变体 | 它阻止什么 | 什么时候用 |
|---|---|---|
| `FOR UPDATE` | **最强**：阻止其他事务对这行做 `UPDATE` / `DELETE` / `SELECT FOR UPDATE` / `FOR NO KEY UPDATE` | 你马上要改这一行，且不希望任何人插队（**注意：它虽然强，但默认不阻止对「非键列」的某些并发路径**——见追问） |
| `FOR NO KEY UPDATE` | 弱一点：**允许**其他事务对同一行做不涉及唯一键的更新 | 更新非键字段的常规写路径（PG 的普通 `UPDATE` 实际对应这一档） |
| `FOR SHARE` | 共享锁：**阻止别人改这行**，但允许多人同时读锁 | 「我要基于这行做判断，先别动它」 |
| `FOR KEY SHARE` | **最弱**：只阻止「删行」和「改键值」 | **外键检查用的就是它** |

**为什么外键用最弱的 `FOR KEY SHARE`**：外键只需要保证「被引用的键还在」——**只要没人删它、没人改它的键值就够了**，不需要阻止别人改它的其他字段。**所以「向子表插入一行」通常不会和被引用行的普通更新互相阻塞。** 这是 PG 在外键上的一个精细优化，**能主动说出来很加分**。

### 四、写偏斜：比幻读更麻烦的东西

**定义**：两个事务**读的集合和写的集合都不重叠**，但合起来破坏了一个跨行不变量。

经典例子：约束是「至少有一名医生值班」。两个事务各自看到「有 2 人值班」，各自把其中一人设为「不值班」——各自的读集不包含对方要写的行，**所以 RC 和 RR 都拦不住**，最后 0 人值班。

**为什么 RC/RR 拦不住**：快照隔离只保证「你看到的是一致的」，**它不保证「你的读和你的写之间没有别人插进来」**。

**三条解法**：

1. **Serializable（SSI）**：它能检测出这种依赖环 → 报错重试（P9）——**这是最省心的解法**；
2. **显式锁**：把「读」也加锁（`FOR UPDATE` 锁住所有涉及行），退化成悲观并发的写法；
3. **改成约束 / 单行聚合**：把跨行不变量收敛成一个能被数据库原子保护的东西（比如在一行里维护计数并用条件更新守护）。

**第 3 条最值钱**：**工程上最好的做法不是「加锁保护不变量」，而是「把不变量设计成不需要跨行保护」**——这是设计层面的解法，比机制层面的更根本。

### 五、死锁：PG 里怎么来、怎么减少

- **来**：两个事务以不同顺序锁同一批行（`UPDATE` 顺序不一致、`FOR UPDATE` 顺序不一致），或者**RC 下 `UPDATE` 重新检查最新版本**（P8）造成的互相等待；
- **减少**：
  1. **统一加锁/更新顺序**（例如总是按主键升序更新）；
  2. **缩短事务**、别在事务里做网络 IO 或等人工确认；
  3. **能不用锁就不用锁**——条件更新把「等待」变成「0 行受影响」，**根本不产生锁等待，也就没有死锁**；
  4. 批量按固定顺序、分批提交。

**第 3 条接到 P18**：**PG 里减少死锁最有效的手段不是调参，而是换并发控制方式。**

## 二、扩展：类似题与追问

**类似题**

1. 「`SELECT ... FOR UPDATE` 和 `UPDATE` 自己差在哪？」——`UPDATE` 会自动加行锁（且权限更细，PG 里普通更新对应 `FOR NO KEY UPDATE`），`FOR UPDATE` 是**先把行锁住再去判断/计算**，用于「读—判断—写」跨越多次交互的场景。
2. 「表锁呢？」——PG 还有表级锁（`LOCK TABLE ... IN ... MODE`），日常业务基本不用；**要提醒的是 `ALTER TABLE` 会拿较重的表锁**（对应 P4「改类型要排窗口」）。
3. 「PostgreSQL 有没有 `SELECT ... LOCK IN SHARE MODE`？」——那是 MySQL 语法；PG 是 `FOR SHARE` / `FOR KEY SHARE`。**语法别串。**

**追问链**

- 追问一层：**「`FOR UPDATE` 是不是就万无一失了？」**——不是。① 它**只锁匹配到的行**，如果范围里还没有行（还没插入），照样锁不住——**这正是「无间隙锁」的直接后果**；② 它需要**读的时候也用它**，一旦某条路径忘了加锁就出现竞态；③ 它会把并发冲突从「报错重试」变成「排队等待」，**高并发下可能拖垮吞吐**。
- 追问二层：**「那 RuleArena 为什么不用它？」**——因为扣退款/认领任务是**低频写、读多写少**：加锁引入锁等待与死锁风险，而收益几乎没有；**条件更新（乐观）在这里更合适**，而且它天然幂等（重复执行第二次影响 0 行）。**唯一约束负责最终防线，而不是靠锁。** 这条直接呼应 [[母题-P18-乐观并发控制]]。
