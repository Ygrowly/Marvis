# 母题 P14 · 长事务与表膨胀

> **模块**：PostgreSQL / 长事务
> **所属主线**：五 · 长事务（它为什么危险，为什么拖系统下水）
> **关联母题**：[[母题-P13-MVCC与可见性]] · [[母题-P15-VACUUM与事务ID回卷]] · [[母题-P2-堆表与回表]]
> **素材来源**：`study/09-数据缓存队列与一致性` + 通用知识（**回收边界与监控视图细节待你核对**）

**题目**：一个开了两小时、只做 `SELECT`、一行都没改过的事务，会让表变大吗？

**母题**：长事务为什么会造成表膨胀？机制是什么？

**为什么重要**：这是 **PG 里最反直觉、也最容易在生产上踩的一题**——**「只读事务无害」是错的**。而且它是主线五的核心：**膨胀不是一个独立现象，它是「长事务按住了回收边界」的必然结果。** 答得出这条链，P13（MVCC）和 P15（VACUUM）就串成了一条线；答不出，那两道题也只是两个孤立的知识点。

**一句话结论**：**会。** 膨胀的机制是「**旧的死元组不能被回收**」：VACUUM 只能回收「对**所有活跃快照**都不可见」的死元组——**长事务持有的快照还需要看到旧版本，于是 VACUUM 不敢删**，死元组一直堆积 → 表页越来越多 → **扫描同样的行要读更多页、回表更贵、缓存命中率下降**。所以长事务的危害不是「持锁久」，而是**它按住了一个旧快照，让空间回收停摆**。

**恢复关键词**：活跃快照按住回收 / 回收的判据是「对所有人不可见」/ 死元组积压 → 表与索引一起膨胀 / `idle in transaction` / **只读长事务同样有害** / 监控最老事务

**核心不变量 / 主线**：
**回收的判据是「对所有人都不可见」，不是「对当前事务不可见」。** 换句话说——**表能不能瘦，由「最老的那个活跃快照」决定，不由「现在有多少死数据」决定。**

**完整回答骨架**：膨胀的机制（回收边界）→ 为什么只读事务也有害 → 膨胀的连锁代价（扫描 / 回表 / 缓存）→ 怎么发现（监控哪几个视图）→ 怎么防（超时 + 拆批 + 别在事务里等外部）

## 原理分解

### 一、机制：回收边界由最老快照决定

结合 P13 的版本模型：

```
一个行版本被删/被更新后 → 变成「死元组」，但它还物理存在
VACUUM 判断「这个死元组能不能清掉」的唯一问题：
   还有没有活跃事务能看到它？
     有 → 不能删（删了那个事务就读不到了）
     没有 → 可以标记为可复用
```

**所以 VACUUM 的清理边界 = 所有活跃快照里最老的那一个。**

一个两小时前开始的事务 → **它的快照就是两小时前** → **这两小时内产生的所有死元组都不能回收**。**两小时的写入量全部变成"不能动的垃圾"。**

**这就是「长事务拖系统下水」的真实路径**——不是它占了多少 CPU，而是**它让整张表的回收停摆了两小时**。

### 二、为什么「只读」也有害（最反直觉的一点）

**因为回收看的是「快照」，不是「这个事务做了什么」。**

- 一个只读事务**不做任何修改**，看上去"人畜无害"；
- 但它**持有快照**，而快照决定了回收边界；
- **所以只要它开着，膨胀就在积累。**

**三种常见的「无害长事务」**：

| 形态 | 为什么出现 | 危害 |
|---|---|---|
| `idle in transaction`（开了事务但没提交、连接挂着） | 应用逻辑里 `BEGIN` 之后做了网络请求 / 等用户输入 / 调了慢接口 | **最坏的形态**：不干活但一直按住快照 |
| 长只读事务（报表、导出、全量扫描） | 一次性拉大量数据分析 | 按快照 + 占备库回放 |
| 批处理事务（几千行一提交） | 「为了原子性把一批包在一个事务里」 | 事务内的写入量本身就是膨胀源 |

### 三、膨胀的连锁代价

膨胀不只是"占空间"，它会**污染整条查询链路**：

```
表页变多
  → 同样的行数分布在更多页上
  → Seq Scan 要读更多页（同样的数据，更多 IO）
  → 索引查询的回表随机 IO 次数上升（P2：ctid 指向更多稀疏页）
  → 缓存命中率下降（shared_buffers 装不下有用的数据）
  → 于是查询整体变慢 → 更慢的查询又延长事务 → 环路加剧
```

**这个环路值得记住**：**膨胀 → 查询变慢 → 事务变长 → 回收继续停摆 → 膨胀更严重**。**这就是为什么「PG 表膨胀」经常是性能事故的起点，而不是结果。**

### 四、怎么发现（要能说出监控哪一个）

| 看什么 | 用途 |
|---|---|
| `pg_stat_activity` 里**最老的活动事务 / 其 `xmin`（或 `backend_xmin`）** | **回收边界**——这是最直接的指标 |
| 「运行时间最长的事务」+「处于 `idle in transaction` 的连接」 | 找出真正的肇事者 |
| 表的死元组数量 / 上次 VACUUM 时间（表级统计） | 判断哪张表在积累死元组 |
| 表与索引的实际大小 vs 有效数据量 | 判断膨胀程度 |

**面试里能说出「我盯的是最老事务的 xmin，也就是回收边界」这一句，就说明你真的理解了机制**——因为大部分人只会说「看有没有长事务」。

### 五、怎么防（按有效性排序）

1. **设超时**：`idle_in_transaction_session_timeout`（**这条最有效**，直接干掉"挂着不干活"的连接）、`statement_timeout`；
2. **拆批**：大批处理拆成小事务分批提交（**不要为了"原子性"把几万行包进一个事务**）；
3. **别在事务里做外部 IO**：网络调用、调外部服务、等人工确认——**事务边界应该只包住数据库操作**；
4. **调 autovacuum**：对大表/高更新表单独设更激进的触发阈值（**`pg_stat_bgwriter` 与表级统计是依据**）；
5. **设计层**：把「高频更新的列」排除出索引（利用 HOT，见 P13）、用状态表 / 追加式日志代替就地更新。

**第 3 条是最容易被忽略的工程纪律**：**「事务里不调外部服务」和「事务里等用户输入」是同一类错误**——它们都把「数据库锁与快照的持有时间」绑到了「外部系统的响应时间」上。

## 二、扩展：类似题与追问

**类似题**

1. 「`VACUUM` 手工跑一次能救回来吗？」——**能缓解，但救不回已经变大的文件**（VACUUM 只标记可复用，见 P15）。要真正变小得用 `VACUUM FULL` 或 `pg_repack`。
2. 「备库上的长查询有危害吗？」——有，而且**双份**：① 备库自己也会膨胀（备库也在回收）；② **它会阻塞 WAL 回放**（进而放大主从延迟，P12）。
3. 「删掉大量历史数据能瘦身吗？」——**`DELETE` 不瘦身**（只是把行变成死元组，等 VACUUM 标记复用）；**要真瘦身用分区 + 丢弃分区**（P16，几乎瞬时且不产生大批死元组）。

**追问链**

- 追问一层：**「为什么『对所有人不可见』不能放宽成『对当前查询不可见』？」**——因为**并发事务的快照可能还需要那些版本**：如果 VACUUM 删掉了一个老事务还要读的版本，那个事务就会读到"数据凭空消失"。**所以回收必须先确认"全网都没人需要它"**——这也是**为什么 PG 的事务 ID 回卷危险（P15）**：一旦 ID 循环复用，同一个 ID 可能既表示"很老的已提交"又表示"很新的事务"，判定就乱了。
- 追问二层：**「膨胀已经发生了怎么办？」**——分三步：**① 先治因**（干掉长事务/调整 autovacuum），否则重建完还会再膨胀；**② 再回收空间**（`pg_repack` 在线重建，或选低峰做 `VACUUM FULL`——**注意 `VACUUM FULL` 要排他锁 + 等量额外空间**）；**③ 最后做结构性改造**（分区 + 丢弃旧分区，把"持续删除"变成"周期丢弃"）。**顺序不能颠倒——先重建再治因，等于白干。**
