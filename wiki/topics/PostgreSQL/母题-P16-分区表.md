# 母题 P16 · 分区表

> **模块**：PostgreSQL / 数据增长与高可用
> **所属主线**：六 · 数据增长与高可用（数据多了怎么不被拖垮）
> **关联母题**：[[母题-P15-VACUUM与事务ID回卷]] · [[母题-P14-长事务与表膨胀]] · [[母题-P2-堆表与回表]]
> **素材来源**：`study/09-数据缓存队列与一致性` 第 7 节（长任务数据模型）+ EnergyOps 四层事实表 + 通用知识（**分区限制细节待你核对**）

**题目**：一张 5 亿行的表，查询永远带时间范围，而且每月要清掉两年前的数据。该不该分区？

**母题**：PG 的分区表有哪几种？什么规模才值得分？

**为什么重要**：这是**「数据增长」这条主线里唯一真正改变架构形状的手段**——加索引、加缓存都还在「同一张表」里打转，**分区改变的是「表的数量和管理粒度」**。而且它和主线五直接合流：**「按月丢弃分区」同时解决了膨胀问题**（P14/P15 的根治方案就是它）。**能看出这两个事是同一件事，是这条线的价值。**

**一句话结论**：PG 是**声明式分区**——`PARTITION BY RANGE / LIST / HASH`。它的主要收益有两个：**① 分区裁剪**（查询带分区键时只扫相关分区）；**② 批量删除变成 `DROP`/`DETACH` 分区**（比 `DELETE` 便宜得多，且**不产生大批死元组**）。**代价**：分区键必须进大部分查询条件、分区太多会有规划开销、**跨分区唯一约束做不了**（除非约束里带上分区键）、运维更复杂。**所以判据不是「数据大」，而是「数据大 + 天然有分区键 + 有批量清理需求」。**

**恢复关键词**：声明式分区 / RANGE LIST HASH / 分区裁剪（partition pruning）/ 分区即批量删除 / 分区多=规划开销 / 唯一约束要带分区键 / 与归档、索引、统计信息配合

**核心不变量 / 主线**：
**分区不是「把大表变小表」，而是「把一张表的管理粒度变细」。** 它的收益全部来自「**能只碰一部分**」——**只扫一部分（裁剪）、只丢一部分（DROP 分区）**。**没有这两类操作的场景，分区只会增加复杂度。**

**完整回答骨架**：分区的三种方式 → 收益一：分区裁剪 → 收益二：丢弃即归档 → 代价与限制（尤其是唯一约束）→ 回到题目做判断 → 与膨胀治理合流

## 原理分解

### 一、三种分区方式

| 方式 | 按什么分 | 典型场景 |
|---|---|---|
| **RANGE** | 值区间 | **时间**（按月 / 按季）、ID 段 |
| **LIST** | 枚举值集合 | 租户 / 区域 / 类别 |
| **HASH** | 哈希取模，均匀打散 | **没有天然分区键**、只想把单表压力摊开 |

**PG 的分区是「声明式的」**：建表时就声明分区键和分区子表，**插入时由数据库路由**（早年的继承 + 触发器手工方案已经是历史）。**并且支持默认分区**（捕获不匹配任何分区的行）——**没有默认分区时，插入一个落在所有分区之外的值会直接报错**，这是第一个常见坑。

### 二、收益一：分区裁剪（查询变快）

当查询条件**明确落在某个/某些分区**上时，规划器**根本不去碰其他分区**：

```
查询：WHERE stat_date >= '2026-01-01' AND stat_date < '2026-02-01'
  ↓ 分区裁剪
只扫描 2026-01 那一个分区 → 扫描量从 5 亿行降到 1400 万行
```

**关键前提：分区键必须出现在查询条件里。** 如果查询经常不带分区键（比如只按 `device_id` 查），**裁剪失效，等于在 24 张分区表上做 24 次扫描**——**比不分区分区还慢**。**这是评估分区是否值得的第一道门槛。**

**第二个要求**：**条件要与分区边界"可推断"**。用 `date_trunc` / 表达式包住分区键，规划器可能无法裁剪（和索引谓词匹配是同一类问题，P3）。

### 三、收益二：丢弃即归档（这是更值钱的那个）

**不分区的表**，清理两年前数据只能 `DELETE`：

```
DELETE FROM facts WHERE stat_date < '2024-09-01';
  ↓
逐行标死 → 产生海量死元组 → 表与索引一起膨胀 → 要等 VACUUM 回收（P14/P15）
  ↓
而且回收后文件也不变小（P15）
```

**分区表**：

```sql
ALTER TABLE facts DETACH PARTITION facts_2024_08;   -- 摘掉（几乎瞬时）
DROP TABLE facts_2024_08;                            -- 或直接丢弃
```

**代价对比是数量级的**：**不产生死元组、不触发膨胀、不占用 VACUUM 资源、可以随时取消（DETACH 后可再挂回来）。**

> **所以「有持续清理需求的大表」应该在设计阶段就分区**——这不是优化，是**避免了后面必然出现的膨胀问题**。这条把主线五和主线六合成了一条线。

### 四、代价与限制（不说这段就等于没评估）

| 限制 | 说明 |
|---|---|
| **唯一约束 / 主键要带分区键** | 跨分区的唯一性**无法用普通唯一索引保证**（每个分区是独立索引）。所以唯一键必须包含分区键，或者用别的机制兜底。**这是最常被忽略、也最容易在业务上炸的一条。** |
| **分区数量影响规划时间** | 分区越多，规划器要枚举的候选越多 → **规划耗时上升**（不是执行慢，是"想"得久）。**几百上千个分区会明显拖慢短查询。** |
| **跨分区查询没有并行优势** | 不裁剪时，多个分区是各自扫描，聚合要合并（有并行改善，但不能指望它抵消设计问题）。 |
| **外键、约束、触发器的行为更复杂** | 子表独立管理，迁移/变更脚本更啰嗦。 |
| **统计信息按分区维护** | 分区多了 autovacuum/ANALYZE 的对象也变多（**又回到 VACUUM 负担**）。 |

### 五、回到题目做判断

条件是：**① 数据大（5 亿行）② 查询永远带时间（有天然分区键，可裁剪）③ 每月要清两年前数据（有批量清理需求）**。

**三条全中 → 该分区，按 `stat_date` 做 RANGE 分区（按月或按季）。**

**反过来，什么情况不该分**：

- **查询不带分区键**（裁剪失效）；
- **数据量其实不大**（几千万行、索引够用）——**先加索引、先优化查询**（P6/P7）；
- **没有清理需求**（那就只是增加复杂度）；
- **需要跨分区的强唯一约束**（成本和复杂度会显著上升）。

**一句判据**：**「我能不能只碰一部分」——能，就分；不能，先别分。**

## 二、扩展：类似题与追问

**类似题**

1. 「分区和分表有什么区别？」——**分区是「一张逻辑表 + 多个物理分区」**（由数据库管理、对外是一张表）；**分表是「多张独立表」**（由应用管理路由）。**分区是数据库能力，分表是架构手段**——这个区分要讲清。
2. 「HASH 分区有什么用？」——**没有天然分区键**时，用一个稳定的高基数列（如租户 ID / 实体 ID）把写入与查询摊开；**放弃裁剪能力，换并发分摊**。**这是「用分区做水平分散」而不是做裁剪。**
3. 「索引要不要建在分区上？」——**分区表上的索引默认是"每个分区各一个"（local index）**；查询时如果裁剪生效，只用对应分区的索引。**所以索引设计要跟着分区键走**——**分区键通常是索引的最左列。**

**追问链**

- 追问一层：**「分区表的主键怎么设计？」**——因为唯一约束必须带分区键，**如果业务主键是「业务 ID」而分区键是「时间」，就不能只对业务 ID 建主键**。常见处理：**主键改成「业务 ID + 时间」的复合**，或者**放弃数据库级唯一约束、改用「全局 ID 生成 + 幂等写入」来保证唯一**（把唯一性交到上游或应用层）。**这是一个"分区代价"落到具体 DDL 上的例子——能讲出来说明真设计过。**
- 追问二层：**「分区真的能让 5 亿行的查询变快吗？」**——**只在裁剪生效时**。裁剪后扫描量下降到单分区，**本质收益和「加索引」是一样的（少扫数据）**，区别在于：**索引解决"行级过滤"，分区解决"整块数据根本不用碰"**。当条件本身能排除大量整块数据（时间范围）时，**分区比索引更彻底**——因为它连索引都不用读。**但如果查询本来就命中很少的行，单表加索引可能更划算**（改动更小、不用承担分区代价）。
