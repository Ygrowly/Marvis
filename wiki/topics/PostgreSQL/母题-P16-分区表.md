# 母题 P16 · 分区表

> **模块**：PostgreSQL / 数据增长与高可用
> **所属主线**：六 · 数据增长与高可用（数据多了怎么不被拖垮）
> **层级**：B · 标准级（裁剪与丢弃的收益能算；但「多少分区才值得分」「哪天该重新分区」是取舍题，不是推导题）

> **素材来源**：`archive/study-courses/09-数据缓存队列与一致性` 第 7 节（长任务数据模型）+ EnergyOps 四层事实表 + **PostgreSQL 官方文档 Table Partitioning**（2026-09-13 联网核实）。**三组算式与「唯一约束为什么必须带分区键」那一段为本次新增（待你核对）**

**导读**：必懂 3 件事（① 分区的收益全部来自**「能只碰一部分」**——只扫一部分（裁剪）、只丢一部分（DROP 分区） ② **唯一约束必须包含分区键**，因为每个分区是独立索引，**跨分区唯一性它管不了** ③ 分区多了**规划时间和内存**都会涨——**它不是免费的把大表变小表**）· 读完约 11 分钟 · 需要先懂：[[母题-P14-长事务与表膨胀]]

**题目**：一张 5 亿行的表，查询永远带时间范围，而且每月要清掉两年前的数据。该不该分区？

**母题**：PG 的分区表有哪几种？什么规模才值得分？

**为什么重要**：这是**「数据增长」这条主线里唯一真正改变架构形状的手段**——加索引、加缓存都还在「同一张表」里打转，**分区改变的是「表的数量和管理粒度」**。而且它和主线五直接合流：**「按月丢弃分区」同时解决了膨胀问题**（P14/P15 的根治方案就是它）。**能看出这两个事是同一件事，是这条线的价值。**

**一句话结论**：PG 是**声明式分区**——`PARTITION BY RANGE / LIST / HASH`。它的主要收益有两个：**① 分区裁剪**（查询带分区键时只扫相关分区）；**② 批量删除变成 `DROP`/`DETACH` 分区**（比 `DELETE` 便宜得多，而且**官方明确说它完全避免了 `DELETE` 带来的 VACUUM 开销**）。**代价**：分区键必须进大部分查询条件、分区太多会有规划开销、**跨分区唯一约束做不了**（除非约束里带上分区键）、运维更复杂。**所以判据不是「数据大」，而是「数据大 + 天然有分区键 + 有批量清理需求」。**

**恢复关键词**：声明式分区 / RANGE LIST HASH / 分区裁剪（规划时 + 执行时）/ **裁剪只由分区键驱动，与索引无关** / 分区即批量删除（**绕开 VACUUM**）/ **唯一约束必须包含分区键** / **分区上建索引不能直接 CONCURRENTLY** / 分区多 = 规划时间 + 内存

**核心不变量 / 主线**：
**分区不是「把大表变小表」，而是「把一张表的管理粒度变细」。** 它的收益全部来自「**能只碰一部分**」——**只扫一部分（裁剪）、只丢一部分（DROP 分区）**。**没有这两类操作的场景，分区只会增加复杂度。**

**完整回答骨架**：分区的三种方式 → **收益一：分区裁剪（含"条件必须带分区键"）** → **收益二：丢弃即归档（绕开 VACUUM，算一笔对比）** → **代价与限制（唯一约束那一条最致命）** → **分区上建索引的那个麻烦（ONLY + ATTACH）** → 回到题目做判断 → 与膨胀治理合流

**完整回答（口述稿）**：
PG 是**声明式分区**——`PARTITION BY RANGE / LIST / HASH`。主要收益两个：**① 分区裁剪**（查询带分区键时只扫相关分区）；**② 批量删除变成 `DROP` / `DETACH` 分区**（比 `DELETE` 便宜得多，而且**官方明确说它完全避免了 `DELETE` 带来的 VACUUM 开销**——这一条在 PG 里特别值钱）。

**代价**：分区键必须进大部分查询条件、分区太多会有规划开销、**跨分区唯一约束做不了**（除非约束里带上分区键）、运维更复杂。

**所以判据不是"数据大"，而是"数据大 + 天然有分区键 + 有批量清理需求"**——和 MySQL 侧「分库分表是最后一步」的结论一致：行数本身不是拆分的理由，真正的信号是"前三步做完仍然扛不住 + 有天然分片键"。

**分层要点**：
- **结论**：收益是裁剪与批量删（避 VACUUM 开销）；代价是分区键约束与运维；判据不是数据大。
- **推导链**：声明式分区 → 两种收益 → 四项代价 → 判据：数据大 + 天然分区键 + 批量清理。
- **量化**：`DROP` 分区 vs `DELETE` 行的成本差（官方明确后者带来 VACUUM 开销）。
- **边界与常见误解**：跨分区唯一约束做不了（除非带分区键）；分区太多会有规划开销。

## 一、教材

### 1. 三种分区方式

::figure pg-partitioning.svg | 分区的两类收益与它的硬限制 | 三种分区方式的适用场景、裁剪的两条前提、丢弃分区与批量删除的代价对比、唯一约束必须带分区键的原因

| 方式 | 按什么分 | 典型场景 |
|---|---|---|
| **RANGE** | 值区间 | **时间**（按月 / 按季）、ID 段 |
| **LIST** | 枚举值集合 | 租户 / 区域 / 类别 |
| **HASH** | 哈希取模，均匀打散 | **没有天然分区键**、只想把单表压力摊开 |

**PG 的分区是「声明式的」**：建表时就声明分区键和分区子表，**插入时由数据库路由**（早年的继承 + 触发器手工方案已经是历史）。

【事实】**官方给的收益清单里，有一条常被忽略**：

> **分区有效地【替代了索引的上层树节点】，让被频繁使用的那些索引部分更有可能放进内存。**

【推论】**这条独立于「裁剪」，值得单独说**：**即使查询不裁剪，一个按时间分区的表，它的「热分区」的索引更小、更容易常驻内存**——**这是 B-tree 深度之外的另一层收益**（[[母题-P2-堆表与回表]]）。

【事实】**默认分区**：**没有默认分区时，插入一个落在所有分区之外的值会直接报错**——**这是第一个常见坑**（也是"分区键选错"的最早信号）。

### 2. 收益一：分区裁剪（查询变快）

【事实】**官方对裁剪机制的描述**：

> **规划器会检查每一个分区的定义，并【证明该分区不需要被扫描】——因为它不可能含有满足 `WHERE` 条件的行。**

【推导】**算一下裁剪的收益**：

```text
表 5 亿行，按月分成 24 个分区（约 2 年）

查询：WHERE stat_date >= '2026-01-01' AND stat_date < '2026-02-01'
  → 只扫 2026-01 那一个分区
  → 扫描量：5 亿 → 【约 2100 万行】（5 亿 ÷ 24）
  → 降到 【1/24 ≈ 4.2%】

如果查询不带分区键（比如只按 device_id 查）：
  → 裁剪失效，24 个分区【每个都要扫】
  → 5 亿行全扫 + 结果合并
  → 【比不分区还慢】（多了 24 次扫描的固定开销与合并）
```

【判据】**这是评估分区是否值得的第一道门槛**：

> **分区键必须出现在大部分查询条件里。**
> **如果查询经常不带分区键，分区是负收益——不是"没效果"，是"更慢"。**

【纠正常见误解】**一个反直觉的官方说明**：

> **分区裁剪【只由分区键隐式定义的约束驱动，与索引是否存在无关】。因此不需要在分区键列上定义索引。**

【推论】**这句话解释了一个常见困惑**：**「我在分区键上建了索引，为什么还是没裁剪？」**——**因为裁剪看的是【分区的边界定义】，不是索引。** **索引影响的是"分区内部怎么扫"，裁剪影响的是"要不要碰这个分区"——两件事。**

【事实】**第二类前提：条件要与分区边界「可推断」**。**用 `date_trunc` / 表达式包住分区键，规划器可能无法裁剪**——**这和 [[母题-P3-部分索引与表达式索引]] 里的「谓词必须可证明蕴含」是同一类问题。**

【事实】**裁剪发生在两个时刻，第二个时刻容易被忽略**：

| 时刻 | 什么时候能裁 | 在哪看 |
|---|---|---|
| **规划时** | 条件里的值是常量 | `EXPLAIN` 的分区列表 |
| **执行时** | 值来自**预处理语句的参数、子查询、嵌套循环的内侧** | **`EXPLAIN ANALYZE` 的 `loops`**（官方原话：**要仔细检查 `loops` 属性**） |

【推论】**这里有两个坑，官方都点出来了**：

```text
① 执行时才被裁掉的分区，【不会出现在 EXPLAIN 或 EXPLAIN ANALYZE 里】
   → 你以为没裁，其实裁了；或者反过来
② 但在执行初始阶段被裁掉的分区，【仍然会在执行开始时被加锁】
   → 所以"裁剪了"不等于"完全没碰到它"
```

【补充】**裁剪可以用 `enable_partition_pruning` 关掉**——**这是排查"到底裁了没有"的一个开关。**

**到这里你应该能回答**：为什么「我在分区键上建了索引」并不等于「查询会被裁剪」？

### 3. 收益二：丢弃即归档（这是更值钱的那个）

**不分区的表**，清理两年前数据只能 `DELETE`：

```
DELETE FROM facts WHERE stat_date < '2024-09-01';
  ↓
逐行标死 → 产生海量死元组 → 表与索引一起膨胀 → 要等 VACUUM 回收（P14/P15）
  ↓
而且回收后文件也不变小（P15）
```

**分区表**：

```sql
ALTER TABLE facts DETACH PARTITION facts_2024_08;   -- 摘掉
DROP TABLE facts_2024_08;                            -- 或直接丢弃
```

【事实】**官方的措辞把两边的差距说得非常直接**：

> **用 `DROP TABLE` 丢掉单个分区、或者做 `ALTER TABLE DETACH PARTITION`，【比批量操作快得多】。**
> **这些命令还【完全避免了】批量 `DELETE` 带来的 `VACUUM` 开销。**

【推导】**把代价算出来**：

```text
删掉一个月的数据 = 2100 万行

DELETE 路线：
  2100 万个死元组（堆）
  × 每个索引各 2100 万个死条目
  → 表与【所有索引】一起膨胀
  → 触发一轮大清理（要读这些页）
  → 而且文件不会变小（P15）
  → 还占了 WAL、还要传去备库

DROP / DETACH 路线：
  → 元数据操作
  → 【零死元组、零膨胀、几乎零 WAL】
  → 瞬时完成
  → 而且 DETACH 之后还能再挂回来（可回滚）
```

【结论】**差的不是几倍，是「一次大清理」和「一次元数据操作」的区别。**

> **所以「有持续清理需求的大表」应该在设计阶段就分区**——**这不是优化，是避免了后面必然出现的膨胀问题。** **这条把主线五和主线六合成了一条线。**

【事实】**`DETACH` 还有一个在线版本**：`ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY`——**它需要额外一次表扫描，但拿的锁更轻**。**这一点很重要：默认的 `DETACH` 会拿一个较强的锁，在热表上会阻塞写入。**

### 4. 代价与限制（不说这段就等于没评估）

| 限制 | 说明 |
|---|---|
| **唯一约束 / 主键要带分区键** | **跨分区的唯一性无法用普通唯一索引保证**。所以唯一键必须包含分区键，或者用别的机制兜底。**这是最常被忽略、也最容易在业务上炸的一条。** |
| **分区上建索引不能用 `CONCURRENTLY`** | 只能在父表建「无效索引」再逐个分区 `CONCURRENTLY` 建、再 `ATTACH`（见下） |
| **分区数量影响规划时间与内存** | 分区越多，规划器要枚举的候选越多 → **规划耗时上升**；**而且官方警告：服务器内存消耗可能随时间显著增长，尤其是很多会话都碰到大量分区时** |
| **跨分区查询没有并行优势** | 不裁剪时，多个分区各自扫描，聚合要合并（有并行改善，但**不能指望它抵消设计问题**）。 |
| **外键、约束、触发器的行为更复杂** | 子表独立管理，迁移/变更脚本更啰嗦。 |
| **统计信息按分区维护** | 分区多了 autovacuum/ANALYZE 的对象也变多（**又回到 VACUUM 负担**）。 |

【事实】**「唯一约束要带分区键」的机制，官方说得很清楚**：

> **要在分区表上创建唯一约束或主键约束，分区键不能包含表达式或函数调用，而且【约束的列必须包含所有分区键列】。**
> **这个限制存在的原因是：【组成约束的那些独立索引只能在各自的分区内直接强制唯一性】；因此，必须由【分区结构本身】来保证不同分区之间没有重复。**

【推导】**这句话把「为什么」讲透了**：

```text
分区表上的索引是「虚拟」的——真正的数据在【各个分区的子索引】里

所以唯一性只能被拆成两半保证：
  分区内部   → 由该分区的唯一索引保证  ✔
  分区之间   → 索引管不了  ✗ 只能靠【分区键本身在逻辑上排他】

如果约束包含分区键：
  → 两条"重复"的行只要分区键不同，它们本来就不该算重复
  → 而如果分区键相同，它们必然落在【同一个分区】→ 那个分区的唯一索引能管
  → 逻辑闭合 ✔

如果约束不包含分区键：
  → 同样的键值可能落在不同分区 → 谁都不知道被谁重复了
  → 没有任何一个索引能拦得住
```

【结论】**这不是 PG 的实现缺陷，是「分区」这个结构的数学后果。**

【推论】**它在业务上的表现是**：**「我想按时间分区，但业务主键是 `order_id` 全局唯一」——这两个需求直接冲突。** **可选的三条路**：**① 把分区键加进唯一键（`UNIQUE (order_id, stat_date)`，代价是同一 `order_id` 在不同分区可以重复，通常不可接受）**；**② 不分区（改用别的增长手段）**；**③ 用应用层的全局唯一机制兜底**（比如另一个不分区的小表做注册表，或者用分布式 ID 保证出生即唯一）。**第 ③ 条在生产上最常见。**

**到这里你应该能回答**：为什么「按时间分区的订单表 + 订单号全局唯一」这两个需求会打架？

### 5. 分区上建索引的那个麻烦（P4 的后续）

【事实】**官方的说明与绕过方式**：

> **分区表的一个限制是【不能使用 `CONCURRENTLY` 限定符】，这可能带来很长的锁时间。**
> **为了避免这一点，可以先用 `CREATE INDEX ON ONLY` 在分区表上创建索引——它会把这个新索引标记为【无效】，从而阻止它被自动应用到已有分区。**
> 然后**在每个分区上分别用 `CONCURRENTLY` 建索引**，再用 `ALTER INDEX ... ATTACH PARTITION` **挂到父索引上**。
> **当所有分区的索引都挂上去之后，父索引会自动被标记为有效。**

```sql
CREATE INDEX measurement_usls_idx ON ONLY measurement (unitsales);
CREATE INDEX CONCURRENTLY measurement_usls_200602_idx
    ON measurement_y2006m02 (unitsales);
ALTER INDEX measurement_usls_idx ATTACH PARTITION measurement_usls_200602_idx;
-- …对每个分区重复…
```

【推论】**这段和 P4 直接接上，而且多了一层**：**在分区表上做在线建索引，不是"一条 CONCURRENTLY"，是一套【父表建空壳 → 各分区并发建 → 逐个挂接】的流程。** **而它恰好也用到 P4 里的那个状态：无效索引**——**只不过这里的"无效"是**故意**的、是流程的一部分。**

【取舍】**`UNIQUE` / `PRIMARY KEY` 也能用同样的手法**，**但代价更大**：**约束的索引是隐式创建的**——**所以要先把约束加在父表上（`ALTER TABLE ONLY ... ADD UNIQUE`），再逐分区加、再 `ATTACH`。**

### 6. 回到题目做判断

条件是：**① 数据大（5 亿行）② 查询永远带时间（有天然分区键，可裁剪）③ 每月要清两年前数据（有批量清理需求）**。

**三条全中 → 该分区，按 `stat_date` 做 RANGE 分区（按月或按季）。**

【推论】**判据要能反向使用**——**下面任何一种情况就不该分区**：

```text
✗ 查询不带分区键（裁不掉，反而更慢）
✗ 没有批量清理需求（只用到一半收益）
✗ 数据量不大（几百万行以内，普通索引就够了）
✗ 业务要求跨分区的唯一约束，而分区键进不了唯一键，也没有应用层兜底
  → 这一条最硬，往往是"不能分区"的决定性理由
```

【取舍】**还有一个判断维度是"分多少个"**：

```text
太少（比如按年分）：裁剪粒度粗，收益有限
太多（比如按天分，几年就上千个）：
  → 规划时间与内存上升（官方明确警告）
  → autovacuum / ANALYZE 的对象变多

经验区间：按【月】或【季】，把总数控制在【几十到几百】这个量级
  → 也就是官方那句「保持分区数量适中」的具体化
```

### 7. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「分区就是把大表拆成小表，一定更快」 | **不带分区键的查询会更慢**（24 个分区各扫一遍 + 合并） |
| 「在分区键上建索引就能裁剪」 | **裁剪只由分区边界驱动，与索引无关**（官方原话） |
| 「分区表的唯一约束和普通表一样」 | **必须包含所有分区键列**，否则**跨分区唯一性无人保证** |
| 「`DELETE` 掉旧数据和 `DROP` 分区差不多」 | **差一个量级**：官方说 DROP/DETACH **完全避免**了批量 DELETE 的 VACUUM 开销 |
| 「分区多了只是慢一点」 | **官方警告：规划时间与内存消耗都会上升，而且内存可能【随时间持续增长】** |
| 「`DETACH` 是瞬时且不阻塞的」 | **默认 `DETACH` 会拿较强的锁**——**热表上要用 `DETACH PARTITION ... CONCURRENTLY`** |
| 「分区表上的索引可以直接 `CONCURRENTLY`」 | **不能**——**要用「父表建空壳 + 逐分区 CONCURRENTLY + ATTACH」那套流程** |

## 二、自测

**Q1（计算）**：一张 5 亿行的表按月分成 24 个分区。查询一个月的数据。

问：**裁剪把扫描量降到多少？如果查询只按 `device_id`（不带时间），会变成什么样？**

**A1**：

```text
带时间条件：
  只扫 1 个分区 = 5 亿 ÷ 24 ≈ 【2100 万行】
  降到 【1/24 ≈ 4.2%】

不带分区键（只按 device_id）：
  → 裁剪失效，24 个分区【每个都要扫】
  → 5 亿行全扫 + 【24 次扫描的固定开销】+ 结果合并
  → 【比不分区还慢】
```

【结论】**分区键在不在查询条件里，决定了分区是「快 24 倍」还是「更慢」。**

【推论】**判据**：

> **评估分区是否值得的第一道门槛不是「数据有多大」，是「大部分查询带不带分区键」。**
> **不带 → 分区是负收益，不是"没效果"。**

【补充】**而且「带没带」还要看**能不能裁****：**用 `date_trunc(stat_date)` 这类表达式包住分区键，规划器可能证不出裁剪。**

**Q2（计算）**：接上题。现在要清掉两年前的那一个月（2100 万行），表上有 **3 个索引**。

问：**`DELETE` 和 `DROP PARTITION` 各产生什么代价？**

**A2**：

```text
DELETE 路线：
  堆：2100 万个死元组
  索引：3 个索引各 2100 万个死条目
  → 表与 3 个索引【一起膨胀】
  → 触发一轮大清理（要读这些页）
  → 文件不会变小（P15）
  → 还要写 WAL、还要传给所有备库

DROP / DETACH 路线：
  → 元数据操作
  → 【零死元组、零膨胀、几乎零 WAL】
  → 瞬时完成
  → DETACH 后可再挂回来（可回滚）
```

【结论】**官方原话：这些命令【完全避免了】批量 `DELETE` 带来的 `VACUUM` 开销。**

【推论】**这就是「分区把膨胀问题从根上绕过」的意思**——**注意是"绕过"不是"解决"**：

> **不是分区的清理更高效，是分区让"清理"这个动作根本不需要发生。**
> **数据不是被删除的，是整块被摘掉的。**

【补充】**这一条决定了「该不该分区」的第二道门槛**：**有没有【持续的、按分区键的】批量清理需求。** **没有的话，你只拿到了一半收益（裁剪），却付了全部复杂度。**

**Q3（判读 + 计算）**：某系统按天分区，3 年下来有 **1000 个分区**。一条典型的短查询（单条主键查，执行约 1 ms）。

问：**分区数量会带来什么代价？为什么官方说这是「保持分区数量适中」的理由？**

**A3**：

```text
官方明确两点：
  ① 规划时间随分区数上升
  ② 内存消耗上升，而且【可能随时间显著增长】，
     尤其是【很多会话都碰到大量分区】时

估算（口径写在算式里）：
  假设每个候选分区的枚举开销约 0.05 ms
  1000 个分区 → 规划耗时 ≈ 50 ms
  而查询本身只要 1 ms
  → 【规划占了总耗时的 98%】
```

【结论】**在短查询上，规划时间可以压倒执行时间**——**这是分区数量真正的天花板。**

【推论】**官方那句「内存可能随时间显著增长」还有第二层意思**：**它是【每个会话】的内存**——**100 个会话各自持有大量分区的规划缓存，乘起来就是实例级的压力。**

【取舍】**所以分区数量的设计原则是**：

```text
按【月】或【季】分（而不是按天）
  → 三年 = 36 个或 12 个分区，而不是 1000 个
  → 裁剪粒度对「查一个月/一个季度」的场景足够

按【天】分只在两种情况下值得：
  ① 清理需求本身就是按天的（比如只保留 30 天）
  ② 单天数据量已经大到"一个月一个分区"仍然过大
```

【补充】**这条也解释了「为什么要按业务查询的粒度设计分区，而不是按数据产生的粒度」**——**分区的客户是查询和清理，不是写入。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们要按 `stat_date` 给订单表分区，顺便把 `order_id` 设成主键，这样既有分区又有全局唯一。"

**A4**：四处问题。

1. **这两个需求直接冲突**：**官方原话是「约束的列必须包含所有分区键列」**——**因为组成约束的那些独立索引只能在各自分区内强制唯一性。** **所以 `PRIMARY KEY (order_id)` 在按 `stat_date` 分区的表上建不出来。**
2. **加进分区键会让语义变错**：**`PRIMARY KEY (order_id, stat_date)` 意味着「同一个 `order_id` 在不同分区可以重复」**——**对一个订单号来说，这通常是不可接受的。**
3. **机制上的原因值得说清**：**同一个 `order_id` 如果落在不同分区，没有任何一个分区的索引能看到另一边的重复**——**"谁重复了谁"这件事在分区结构里根本没有答案。**
4. **可选的三条路**：**① 不分区（换别的增长手段）；② 换一个能进唯一键的分区键；③ 用应用层/外部的全局唯一机制兜底**（分布式 ID、或者一张不分区的小注册表）。**第 ③ 条在生产上最常见。**

【准确说法】"**分区键是「管理粒度」的声明，也是「唯一性边界」的声明。** **想按时间分区又想全局唯一，就得接受唯一性由分区之外的机制保证——这不是 PG 的限制，是分区这个结构的数学后果。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "表大了，我按 `stat_date` 分个区，以后查询就都快了。"

**A5**：三处问题。

1. **只有「带分区键的查询」会快**：**不带分区键的查询要扫所有分区**（Q1）——**比不分区还慢。**
2. **还要看「能不能裁」**：**用表达式包住分区键（`date_trunc(stat_date) = ?`）可能裁不掉**，**这和部分索引的「谓词必须可证明蕴含」是同一类问题**（[[母题-P3-部分索引与表达式索引]]）。
3. **分区的另一半收益是清理，不是查询**：**如果只有查询变快这一个目标，先试索引**——**分区真正的独特价值在「`DROP` 分区 = 瞬时清理」那一条**（Q2）。

【准确说法】"**分区的判据不是「数据大」，是「数据大 + 大部分查询带分区键 + 有按分区键的批量清理需求」。** **三条不齐，分区只会增加复杂度。**"

## 三、面试输出（学完再看）

**一句话结论**：**分区不是「把大表变小表」，是「把一张表的管理粒度变细」**——**收益全部来自「能只碰一部分」。** **收益一是分区裁剪**：**规划器检查每个分区的定义，证明它不可能含有满足 `WHERE` 的行**，**于是根本不去碰它**——**5 亿行按 24 个月分区，查一个月只扫约 2100 万行（1/24）**。**但前提是分区键必须出现在查询条件里，而且可推断**——**不带分区键的查询要扫全部 24 个分区，比不分区还慢**；**而且官方有一句反直觉的话：裁剪只由分区边界驱动，【与索引是否存在无关】——所以在分区键上建索引并不带来裁剪。** **收益二是丢弃即归档**，这也是**更值钱**的那一条：**官方说 `DROP TABLE` 单个分区或 `ALTER TABLE DETACH PARTITION` 比批量操作快得多，而且【完全避免了批量 `DELETE` 带来的 `VACUUM` 开销】**——**删 2100 万行会产生堆 + 每个索引各 2100 万个死元组，而摘分区是一次元数据操作、零死元组、几乎零 WAL，而且 DETACH 还能挂回来。** **所以这条把主线五和主线六合成了一条线：分区在设计的层面绕开了膨胀问题。** **代价里最致命的一条是唯一约束**：**官方原话是「约束的列必须包含所有分区键列」，原因是【组成约束的独立索引只能在各自分区内强制唯一性】——跨分区唯一性在分区结构里没有答案。** **所以「按时间分区的订单表 + 订单号全局唯一」这两个需求直接打架**，出路只有不分区、换分区键、或用应用层的全局唯一机制兜底。**其他代价**：**分区上建索引不能用 `CONCURRENTLY`**（要用「父表建空壳 → 逐分区 CONCURRENTLY → `ATTACH`」那套流程）；**分区数量上升会推高规划时间与内存**（官方警告内存可能随时间显著增长），所以**按天分几年变上千个分区是自找麻烦**——**经验上按「月」或「季」，总数控制在几十到几百。**

**恢复关键词**：RANGE / LIST / HASH / **裁剪 = 证明该分区不需要被扫** / **裁剪只由分区边界驱动，与索引无关** / 裁剪可发生在规划时与执行时（执行时的看 `loops`）/ **`DROP`/`DETACH` 完全避免 VACUUM 开销** / `DETACH ... CONCURRENTLY` / **唯一约束必须包含所有分区键列** / 分区上不能直接 `CONCURRENTLY`（`ONLY` + `ATTACH`）/ 分区多 → 规划时间 + 内存 / 1/24 vs 24 次扫描

**核心不变量 / 主线**：
**分区不是「把大表变小表」，而是「把一张表的管理粒度变细」。**
**它的收益全部来自「能只碰一部分」——只扫一部分（裁剪）、只丢一部分（DROP 分区）。没有这两类操作的场景，分区只会增加复杂度。**

**完整回答骨架**：三种分区方式 → **裁剪（算 1/24 与"不带键会更慢"）** → **丢弃即归档（算 DELETE vs DROP）** → **唯一约束必须带分区键（讲清机制，不是实现缺陷）** → **建索引的那套绕法** → 分区数量的天花板 → 收束到「管理粒度」

**追问**（先说后看）

1. **分区数量和性能是什么关系？** —— **不是线性变好，是先好后坏**：**裁剪的收益随分区数上升，但规划时间与内存也上升**。**官方明确警告内存可能随时间显著增长，尤其是很多会话都碰到大量分区时。** **所以按「月/季」分、总数几十到几百，是把两条曲线折中的经验值。**
2. **`DETACH` 会不会阻塞写入？** —— **默认的 `DETACH` 会拿较强的锁**；**热表上要用 `ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY`**——**它需要额外一次表扫描，但锁更轻。** **这条如果不知道，会在生产上直接把写入卡住。**
3. **分区表上怎么做在线建索引？** —— **不能用一条 `CONCURRENTLY`**。**要先用 `CREATE INDEX ON ONLY` 在父表建一个【无效】索引（阻止它自动应用到已有分区），再在每个分区上分别 `CONCURRENTLY` 建，最后逐个 `ALTER INDEX ... ATTACH PARTITION`**；**全部挂上后父索引会自动变为有效。** **注意这里的"无效"是【故意】的、是流程的一部分**——**和 P4 里那个"失败留下的无效索引"是同一个状态、完全不同的含义。**
4. **默认分区为什么必须建？** —— **没有默认分区时，插入一个落在所有分区之外的值会直接报错**。**这在生产上意味着"某天凌晨的写入突然全部失败"**——**所以设计时要么建默认分区兜底，要么保证有自动建分区的任务。** **两者选一个，不能不选。**
5. **`enable_partition_pruning` 是干什么的？** —— **它是裁剪的开关**。**排查"到底裁了没有"的时候，可以关掉它做对比**；**而执行时才被裁掉的分区不会出现在 `EXPLAIN` 里，要看 `EXPLAIN ANALYZE` 的 `loops`**（官方原话）。

**同类变体**

- 「`HASH` 分区什么时候用？」—— **当没有天然分区键、只想把单表压力摊开时**（比如高并发的队列表）。**它拿不到"裁剪"的收益（哈希没法按范围裁），但能拿到"每张子表更小、索引更容易常驻内存"的收益**——**这一点和 RANGE 分区共享。** **所以 HASH 分区的定位是"摊开写入压力"，不是"加快范围查询"。**
- 「分区和分表（应用层）该选哪个？」—— **PG 的声明式分区由数据库保证路由与约束，应用不需要知道分区存在**；**应用层分表要自己维护路由、跨表查询、聚合**。**所以能用声明式分区就别自己分表**；**只有"要分到不同实例"时才必须应用层分。**
