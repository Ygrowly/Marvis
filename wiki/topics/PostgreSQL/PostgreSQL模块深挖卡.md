**PG 与 MySQL 最容易说错的七处**（面试安全底线）：

| 点 | MySQL | PostgreSQL |
|---|---|---|
| 默认隔离级别 | REPEATABLE READ | **READ COMMITTED** |
| MVCC 实现 | undo log 版本链 + ReadView | **元组多版本留在堆里 + xmin/xmax** |
| 旧版本回收 | purge 线程自动 | **VACUUM / autovacuum（可能跟不上）** |
| 幻读防护 | next-key lock（间隙锁） | **无间隙锁，靠 SSI 做可串行化** |
| 索引组织 | 聚簇索引（主键即数据） | **堆表，所有索引都要回表** |
| 日志 | redo + undo + binlog | **WAL（单一）** |
| 连接 | 线程池 | **进程模型，连接很贵** |

## 5. 项目映射（**本模块的核心价值**：三个项目全是 PG）

> 这一节比 MySQL 模块的同类章节更重要——**PG 是你真用过的**，所以每个母题都应该能挂上项目证据。填不出来的，说明那块只停留在概念层。

### 5.1 EnergyOps（金山园区能耗 · PostgreSQL）

**锚点**：`projects/EnergyOps/03-query-and-performance.md`（四层事实表、联合索引、explain、消除重复 join）、`02-aggregation-and-recovery.md`（15 分钟窗口、幂等与补数）

- **用在哪**：604 台电表的 15 分钟累计读数经采集与治理后落四层事实表（原始 → 可信聚合区间 → hourly → daily）；查询按粒度直接命中 daily / hourly，**不回到 Raw 现算差分**；`EXPLAIN ANALYZE` 是索引设计的唯一依据。
- **实际用的索引与分区**：事实表按**等值条件在前、时间范围在后**组织联合索引，可考虑 `(device_id, energy_type, stat_date)`；若事实表合法冗余了园区快照，也可考虑 `(campus_id, energy_type, stat_date)`。**最终以选择性和执行计划为准，不机械套最左前缀。** 当前设备规模下**未做分区**——分区被列为「暂缓」项，等容量与 SLO 证明不足时才升级。
- **踩过的坑**：① 估计行数与实际行数偏差大（JOIN 后行数膨胀），导致优化器选错方案；② 把「看到 Index Scan」当成优化成功的标准，结果接口仍然慢——**真正要看的是实际 rows / loops / 过滤行数 + 分段计时**（数据库、应用处理、序列化、缓存、接口总耗时分别测）。
- **决策与取舍**：缓存一致性没有用「事务里顺手删 Redis」，而是**事务内写 CacheInvalidation Outbox → 提交 → 异步 worker 幂等删缓存**，或**把聚合版本放进缓存键**（新版本提交后自然不再命中旧键，再配 TTL 清理）。理由：**PG 事务提交与 Redis 删除不可能构成同一个 ACID 事务**，靠"提交完立刻删"是有窗口的。没有换 OLAP：设备规模下 PG 事实表 + 索引 + 预聚合够用，额外系统的运维成本高于收益。
- **对应母题**：【P2、P5、P6、P7、P18】
- **口径提醒**：`P95 20.4s → 2.8s` 属**待验证数字**（手册未关联原始报告）。必须能补齐查询范围、样本数、并发、硬件、缓存冷热、统计窗口和 P95 算法，否则不要主动报这个数。

### 5.2 数驭穹图（企业问数 · PG 存元数据 + 接入多个数据源）

**锚点**：`projects/数驭穹图/02-数据接入与轻量湖仓.md`（PG 用逻辑复制 / WAL；只读账号与可恢复快照）、`07-权限安全与生产隔离.md`、`08-查询性能与成本控制.md`

- **用在哪**：PostgreSQL 保存租户、数据目录、Schema、同步任务和文件索引；对象存储按租户 / 数据集 / 分区存 Parquet，DuckDB 读 Parquet 完成分析查询。**增量同步路径：MySQL 源优先用 Binlog，PostgreSQL 源优先用逻辑复制 / WAL**，都不支持 CDC 时才退回 `updated_at` 或递增主键轮询。
- **只读账号与权限隔离怎么做的**：接入服务先验证网络、数据库版本和**只读权限**，凭据加密保存、**不进模型上下文**；`LIVE_READ` 路径必须有只读事务、允许表清单、超时、扫描量、并发、行数和取消能力，客户只有生产主库时**默认不开放复杂即席查询**。
- **踩过的坑**：① 多租户数据源方言差异（同一条 SQL 在不同源上行为不同）；② **删除行没有 tombstone / 变更日志就会静默漏数**——所以发布前要校验行数、主键重复、字段类型、分区完整性、Schema 漂移、同步位点和新鲜度，关键校验失败就停在 `INVALID` / `STALE`；③ 长事务会阻塞 VACUUM、加剧表膨胀，也拉长快照持有时间。
- **决策与取舍**：逻辑复制（按表、可跨版本、可选择性复制）vs 物理复制（整实例、字节级、备库只读）——我们只需要**授权的分析数据集**，所以走逻辑路径。第一版**只做可恢复快照 + 轮询增量**，不上完整 CDC：CDC 要求源端开启 binlog / 逻辑复制并承担权限与稳定性风险，而分析场景容忍分钟级新鲜度，**用「快照 + 位点 + 校验」换来生产隔离与可复现性更值**。
- **对应母题**：【P8、P11、P12、P14】

### 5.3 RuleArena（规则竞技场 · PostgreSQL）

**锚点**：`projects/RuleArena/04-idempotency-and-recovery.md`（条件更新、Checkpoint、Worker 重启恢复）、`03-executable-world-and-oracle.md`（PG 事务、Sandbox 副本环境）

- **用在哪**：PostgreSQL 是所有**权威状态**的落点——AttackRun / StrategyStep / ActionReceipt / Ledger / BusinessEvent 在同一事务内提交；沙箱用**数据库副本**环境重放高风险操作组合，绝不在生产库上跑。
- **并发控制怎么做的**：**条件更新（乐观并发）+ 唯一约束兜底**，不用 `FOR UPDATE`：

  ```sql
  UPDATE orders
  SET refunded_amount = refunded_amount + :amount,
      version = version + 1
  WHERE id = :id
    AND version = :expected_version
    AND refunded_amount + :amount <= paid_amount;
  ```

  影响行数为 0 → 版本冲突或超额，**读出权威 Snapshot 后返回冲突，不盲目重试业务动作**。为什么优先条件更新而不是 `FOR UPDATE`：项目文档 `04 §15` 给的是**「MVP 优先业务唯一键 + 条件更新」**，`Q7` 给的是**「锁可以降低竞争，但不能成为资金正确性的唯一保证」**——**理由是权威性，不是「低频写」**；而且文档 `04 §12` 同时给了**「锁定订单行 **或** 乐观版本条件更新」**，所以别说成「完全不用锁」。正确性最终靠 `UNIQUE(run_id, action_type, idempotency_key)` 兜底，而不是内存锁或 Redis 锁。
- **踩过的坑**：① 沙箱若直接在生产库重放，**长事务 + 锁等待 + 高风险组合会把生产拖下水**（现实版本就是长事务阻塞 VACUUM、加剧表膨胀）→ 必须用副本；② 曾把 **ToolCallID 当幂等键**——模型重新规划、Worker 重启、超时重发都会产生不同的 ToolCallID，业务幂等键必须基于业务身份构造（`run_id + action_type + target_id + 参数 + 规则版本 + 逻辑步骤`）；③ PG **没有间隙锁**，跨行不变量（`refunded + amount <= paid`）不能靠「我先查一遍」，只能靠条件更新或约束。
- **决策与取舍**：Checkpoint 存**执行位置**（frontier / 已用预算 / 版本元组），**不存业务结论**；业务事实靠 Receipt + Snapshot 查询。理由：**「动作」与「Checkpoint」之间永远存在崩溃窗口，不存在完美的保存顺序**——所以不追求完美顺序，而是让每个中断点都能根据权威事实判断该继续、跳过、重试还是停止。
- **对应母题**：【P10、P13、P18、P19】

> 规则：**没有真实使用就写「未使用」，不要编**。写了「未使用」反而是诚实资产。
