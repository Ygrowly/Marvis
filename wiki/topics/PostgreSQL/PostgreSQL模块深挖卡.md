# PostgreSQL 模块深挖卡

> **与 [[MySQL模块深挖卡]] 的关系**：**主线结构一致，内容各自成体系**。MySQL 是「岗位会问的」，PG 是「我项目里实际用的」。
> 两条线共用七条主线的骨架，但每条线的重点不同——PG 的头号考点是 **MVCC / VACUUM / 表膨胀**，这是 MySQL 不会问的。
> 素材来源：`study/09-数据缓存队列与一致性`（PG 事务与索引视角）+ 三个项目的真实设计 + 公开面试题汇总（**内容待你核对**）

## 0. 模块边界

- **包含**：PG 14+ 的索引类型与选型、执行计划与统计信息、MVCC 与隔离级别、VACUUM 与表膨胀、WAL 与复制、分区与连接池、项目里用到的并发控制模式
- **明确不包含**（写下它们，然后放下）：PG 源码、扩展生态（PostGIS / TimescaleDB / Citus）、高可用组件深入（Patroni / repmgr 部署细节）、PG 与 MySQL 的性能对比测评

## 2. 主线拆解（七条线：与 MySQL 同构，内容各自成体系）

| # | 主线（它在回答什么问题） | PG 版的重点（与 MySQL 的差别） | 落几个母题 |
|---|---|---|---|
| 一 | **索引**：怎么让查询不用扫全表 | 索引类型选型（B-tree / GIN / GiST / BRIN）+ 部分索引 + 堆表必回表 | 4 |
| 二 | **SQL 执行与优化**：一条 SQL 怎么走、慢在哪 | EXPLAIN **ANALYZE**、估计行数 vs 实际行数、Bitmap Heap Scan | 2 |
| 三 | **事务与锁**：并发改同一份数据，为什么不会乱 | 默认 **RC**（不是 RR）、Serializable 会失败要重试、**无间隙锁**、FOR UPDATE 四变体 | 3 |
| 四 | **日志与持久化**：提交过的数据，服务挂了为什么不该丢 | **WAL**（单一日志，不像 MySQL 三套）、checkpoint、流复制 vs 逻辑复制 | 2 |
| 五 | **长事务**：它为什么危险，为什么拖系统下水 | **PG 版更狠**：长事务阻塞 VACUUM → 表膨胀 → 事务 ID 回卷 | 3 |
| 六 | **数据增长与高可用**：数据多了怎么不被拖垮 | 声明式分区、**连接池是刚需**（进程模型，连接贵） | 2 |
| 七 | **业务并发场景**：抢库存、冲排行榜怎么不出错 | 乐观并发控制（条件更新 + version）、UPSERT、唯一约束兜底 | 2 |

**PG 与 MySQL 最容易说错的五处**（面试安全底线）：

| 点 | MySQL | PostgreSQL |
|---|---|---|
| 默认隔离级别 | REPEATABLE READ | **READ COMMITTED** |
| MVCC 实现 | undo log 版本链 + ReadView | **元组多版本留在堆里 + xmin/xmax** |
| 旧版本回收 | purge 线程自动 | **VACUUM / autovacuum（可能跟不上）** |
| 幻读防护 | next-key lock（间隙锁） | **无间隙锁，靠 SSI 做可串行化** |
| 索引组织 | 聚簇索引（主键即数据） | **堆表，所有索引都要回表** |
| 日志 | redo + undo + binlog | **WAL（单一）** |
| 连接 | 线程池 | **进程模型，连接很贵** |
