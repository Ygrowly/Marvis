# 母题 P12 · 流复制与逻辑复制

> **模块**：PostgreSQL / 日志与持久化
> **所属主线**：四 · 日志与持久化（提交过的数据，服务挂了为什么不该丢）
> **关联母题**：[[母题-P11-WAL与checkpoint]] · [[母题-P15-VACUUM与事务ID回卷]]
> **素材来源**：`projects/数驭穹图/02-数据接入与轻量湖仓.md`（MySQL 用 Binlog、PG 用逻辑复制/WAL）+ 通用知识（**复制槽细节待你核对**）

**题目**：你要 (1) 搭一个只读副本给报表用，(2) 还要把其中几张表的变更同步到另一个系统。这两件事用同一种复制吗？

**母题**：流复制和逻辑复制有什么区别？同步 / 异步怎么取舍？

**为什么重要**：这是**直接落在你项目上的一道题**——数驭穹图的接入层明确写着「MySQL 优先用 Binlog，PostgreSQL 优先用逻辑复制 / WAL」，而且第一版**有意没上完整 CDC**。**为什么这么选、代价是什么，这道题必须能自己讲出来**，否则那个设计决策就只是一个抄来的结论。

**一句话结论**：**流复制（物理）复制的是「整个实例的 WAL 字节流」**——备库是主库的**逐字节副本**，只能整实例、备库只读、版本必须一致；**逻辑复制复制的是「逻辑变更」**——可以按表、可以按行过滤、备端可写、可跨大版本、能做异构与多源汇聚。所以 **① 只读副本用流复制；② 部分表同步到别的系统用逻辑复制**。同步 / 异步的取舍本质是 **RPO vs 提交延迟**。

**恢复关键词**：物理复制（WAL 字节流）vs 逻辑复制（变更流）/ 表级与行级过滤 / 跨版本 / 备库只读 vs 可写 / 同步提交的 RPO 与延迟 / **复制槽不消费导致 WAL 堆积** / 主从延迟读数不一致

**核心不变量 / 主线**：
**物理复制复制的是「存储的变化」，逻辑复制复制的是「数据的变化」。** 所以前者绑定**实例与版本**，后者绑定**表与行**——**所有能力差异（能不能选择性复制、备端能不能写、能不能跨版本）都是这一句话的推论。**

**完整回答骨架**：两种复制的机制差异 → 各自绑定的东西 → 回到题目做选择 → 同步/异步怎么取舍 → 两个必须知道的坑（复制槽、主从延迟）→ 你项目为什么选逻辑路径

## 原理分解

### 一、两种复制：复制的是什么

| | **流复制（物理）** | **逻辑复制** |
|---|---|---|
| 复制内容 | **WAL 字节流**（存储层变化） | **逻辑变更**（表的行变更） |
| 粒度 | **整个实例** | **表级**（可再按行过滤） |
| 备端 | **只读**（热备） | **可读可写** |
| 版本 | **必须一致**（含小版本，实践上同大版本内也要谨慎） | **可跨大版本** |
| 用途 | 高可用、只读副本、读写分离 | CDC、异构同步、多源汇聚、升级迁移 |
| 机制 | WAL 直接传输 + 重放 | 主库从 WAL **逻辑解码**成变更流，备端按表应用 |

**一句话对照**：**流复制让「另一个我」存在；逻辑复制让「我的一部分数据」出现在别处。**

### 二、回到题目

- **(1) 只读副本做报表** → **流复制**。它是完整副本、可以在备库上跑长查询（**但要注意长查询会阻塞备库上的回放**——见下文「主从延迟」）；
- **(2) 几张表的变更同步到别的系统** → **逻辑复制**。因为你只需要那几张表、目标端可能版本不同或不是 PG。

**数驭穹图的真实选择正好落在这条线上**：它需要的是「授权的分析数据集」——**不是整个实例**，所以走**逻辑路径**；而且要能跨源、能只同步部分表，物理复制**根本做不到**。

### 三、同步 / 异步：本质是 RPO 换延迟

| 模式 | 语义 | 代价 |
|---|---|---|
| **异步**（默认） | 主库提交不等备库 | **主库宕机可能丢最近一段已提交事务**（备库没收到）；备库延迟不稳定 |
| **同步** | 主库提交**等待**备库确认收到（或应用） | **提交延迟 = 等备库的网络 + 刷盘时间**；备库抖动会拖慢主库 |

**判据**：**能接受丢多少（RPO）就选什么。** 但要注意一个陷阱——**同步复制会让「备库的可用性」变成「主库可用性」的一部分**：备库挂了，主库提交就可能被卡住。所以生产通常配 **`FIRST 1 (a, b)` 这类「至少一个备库确认即可」**的写法，而不是「等全部」。

**这一条比结论重要**：**不要简单说「我们用了同步复制保证不丢」——要说清楚「几种确认策略、以及备库故障时主库会怎样」。**

### 四、必须知道的两个坑

**坑一：复制槽不消费 → WAL 永久堆积 → 磁盘写满**

逻辑复制用**复制槽**记录消费位点，**PG 必须保留位点之后的所有 WAL**（否则无法重放给消费者）。所以：

- 消费者挂了、或者某个备库长期离线 → **WAL 只增不减**；
- 结果是**磁盘被 WAL 写满，整个实例写不进去**——这是 PG 最常见的一类生产事故。

**排查**：查复制槽的 `restart_lsn` / `confirmed_flush_lsn` 与当前 WAL 位置的差距；**必须监控「不活跃的复制槽」**，并明确「离线多久就该删槽并重建」的运维约定。

**坑二：主从延迟不只是网络**

延迟有三段：**① 主库产出 WAL 的速度 → ② 网络传输 → ③ 备库回放**。第 ③ 段最容易被忽略，而它的一个主要来源正是 **备库上的长查询/长事务**——**PG 12+ 之前，备库的查询会与 WAL 回放互相阻塞**（现代版本用 `hot_standby_feedback` / 快照导出缓解，但引入了**备库把主库膨胀顶住**的副作用）。

**业务后果与处理**：读写分离下「写主库、读备库」会**读到旧数据**。处理方式按业务重要性排序：**关键读回主库**（最可靠）→ **写后一段时间内钉住主库**（读己之写）→ 监控延迟并在超阈值时降级。**不要用「sleep 一下再读」这种办法。**

## 二、扩展：类似题与追问

**类似题**

1. 「逻辑复制的目标端能写吗？」——能（它是独立的可写表），**代价是冲突要自己处理**（目标端本地已有数据会与回放冲突）。
2. 「能不能用逻辑复制做双向同步？」——技术上可以，但**冲突解决完全靠自己**，收益通常不如改成单向 + 明确归属。**面试里承认「双向的复杂度收益比不高」比硬吹更好。**
3. 「为什么 PG 不用 binlog 也能做 CDC？」——因为 **WAL 本身就是完整的变更记录**，逻辑解码把它翻译成逻辑变更（`pgoutput`）即可。**这也解释了为什么 PG 的 CDC 工具（Debezium 等）在 PG 侧都是基于逻辑解码槽。**

**追问链**

- 追问一层：**「为什么你项目第一版不做完整 CDC？」**——要说出**取舍**：CDC 要求源端**启用逻辑复制/binlog 并常驻一个消费者**，一旦消费者停摆就会有 **WAL/binlog 堆积**风险；而分析场景对新鲜度的要求是**分钟级可接受**。**所以用「可恢复快照 + `updated_at` / 递增主键轮询 + 位点与校验」换来了「不侵入客户生产库 + 可复现」**——升级条件是出现真实的秒级新鲜度需求。**这段是项目叙事的核心，必须能自己讲。**
- 追问二层：**「轮询增量有什么问题？」**——两个：**① 删除的行永远轮询不到**（必须靠 tombstone、变更日志或周期性全量核对）；**② `updated_at` 不可靠**（有些写入不更新它、或者时钟不一致）。**这正是数驭穹图文档里写「发布前校验行数 / 主键重复 / Schema 漂移 / 新鲜度，失败就停在 `INVALID`/`STALE`」的原因**——**用校验兜住轮询的漏，是这个设计的关键一环。**
