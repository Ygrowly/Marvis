# 母题 P12 · 流复制与逻辑复制

> **模块**：PostgreSQL / 日志与持久化
> **所属主线**：四 · 日志与持久化（提交过的数据，服务挂了为什么不该丢）
> **层级**：A · 教材级（两种复制绑定什么是推出来的；同步级别的保证有官方矩阵；堆积与延迟都能算）
> **关联母题**：[[母题-P11-WAL与checkpoint]]（WAL 是两种复制的共同底座）· [[母题-P15-VACUUM与事务ID回卷]]（`hot_standby_feedback` 会把膨胀顶住）· [[母题-P7-统计信息与慢查询定位]]（只读副本的统计信息也要更新）· [[母题-P8-隔离级别与读一致性]]（副本上的读一致性）· [[母题-M14-主从复制与延迟]]（MySQL 侧对照）
> **素材来源**：`projects/数驭穹图/02-数据接入与轻量湖仓.md`（MySQL 用 Binlog、PG 用逻辑复制/WAL）+ **PostgreSQL 官方文档 Warm Standby / Logical Replication / Replication 配置**（2026-09-13 联网核实）+ 通用知识。**三组算式与同步级别矩阵为本次新增（待你核对）**

**导读**：必懂 3 件事（① 物理复制复制的是**存储的变化**，逻辑复制复制的是**数据的变化**——所有能力差异都是这一句的推论 ② **`synchronous_commit` 的五个档位对应备库的四个落点**，有官方矩阵 ③ **复制槽默认可以无限保留 WAL**——这是 PG 最常见的一类"磁盘被写满"事故）· 读完约 12 分钟 · 需要先懂：[[母题-P11-WAL与checkpoint]]

**题目**：你要 (1) 搭一个只读副本给报表用，(2) 还要把其中几张表的变更同步到另一个系统。这两件事用同一种复制吗？

**母题**：流复制和逻辑复制有什么区别？同步 / 异步怎么取舍？

**为什么重要**：这是**直接落在你项目上的一道题**——数驭穹图的接入层明确写着「MySQL 优先用 Binlog，PostgreSQL 优先用逻辑复制 / WAL」，而且第一版**有意没上完整 CDC**。**为什么这么选、代价是什么，这道题必须能自己讲出来**，否则那个设计决策就只是一个抄来的结论。

**一句话结论**：**流复制（物理）复制的是「整个实例的 WAL 字节流」**——备库是主库的**逐字节副本**，只能整实例、备库只读（但可查询）、版本必须一致；**逻辑复制复制的是「逻辑变更」**——可以按表、可以按行过滤、备端可写、可跨大版本、能做异构与多源汇聚。所以 **① 只读副本用流复制；② 部分表同步到别的系统用逻辑复制**。同步 / 异步的取舍本质是 **RPO vs 提交延迟**。

**恢复关键词**：物理复制（WAL 字节流）vs 逻辑复制（变更流）/ 表级与行级过滤 / 跨版本 / 备库只读 vs 可写 / **`synchronous_commit` 五档对应备库四个落点** / **复制槽默认无限保留 WAL（`max_slot_wal_keep_size = -1`）** / 备库冲突查询默认 30 秒后被取消 / 回放能力必须 ≥ 生成能力

**核心不变量 / 主线**：
**物理复制复制的是「存储的变化」，逻辑复制复制的是「数据的变化」。** 所以前者绑定**实例与版本**，后者绑定**表与行**——**所有能力差异（能不能选择性复制、备端能不能写、能不能跨版本）都是这一句话的推论。**
**而同步/异步要看的不是「哪个更安全」，是「备库故障时主库会怎样」。**

**完整回答骨架**：两种复制的机制差异 → 各自绑定的东西 → 回到题目做选择 → **同步级别与它对应的四个落点** → **两个能算的坑（复制槽堆积、回放追不上）** → 你项目为什么选逻辑路径

## 一、教材

### 1. 两种复制：复制的是什么

::figure pg-replication.svg | 两种复制绑定的东西与同步级别的四个落点 | 物理复制与逻辑复制的对照、同步提交档位对应的备库落点、复制槽堆积与回放追不上的两条算式

| | **流复制（物理）** | **逻辑复制** |
|---|---|---|
| 复制内容 | **WAL 字节流**（存储层变化） | **逻辑变更**（表的行变更） |
| 粒度 | **整个实例** | **表级**（可再按行过滤） |
| 备端 | **只读**（热备，可跑查询） | **可读可写** |
| 版本 | **必须一致** | **可跨大版本** |
| 用途 | 高可用、只读副本、读写分离 | CDC、异构同步、多源汇聚、升级迁移 |
| 机制 | WAL 直接传输 + 重放 | 主库从 WAL **逻辑解码**成变更流，备端按表应用 |

**一句话对照**：**流复制让「另一个我」存在；逻辑复制让「我的一部分数据」出现在别处。**

【推论】**所有差异都是「复制的是存储变化还是数据变化」的推论**：

```text
复制存储变化 → 它必须是一模一样的实例（版本一致、不能挑表、备端不能写）
  → 因为 WAL 记录的是「第 N 号页的第 M 个偏移改成了什么」，
    这是【物理位置】，脱离这个实例就失去意义

复制数据变化 → 它可以被翻译成 INSERT/UPDATE/DELETE
  → 于是可以挑表、可以改结构、可以落到另一个版本甚至另一个数据库
  → 代价是：翻译过程会丢信息，而且【大对象、序列、DDL 都不会自动同步】
```

【话术】**「逻辑复制能跨版本」的代价要说全**：**逻辑复制默认只同步 DML，不同步 DDL**——**这是它最容易被低估的限制**：**上游改表结构时，下游不会跟着改**，**所以生产上用逻辑复制必须配一套"结构变更的发布流程"。**

**到这里你应该能回答**：为什么「用逻辑复制做完整迁移」听起来可行、实践上却要额外处理一大摊事？

### 2. 回到题目

- **(1) 只读副本做报表** → **流复制**。它是完整副本、可以在备库上跑长查询（**但要注意长查询与回放会冲突**——见第 4 节）；
- **(2) 几张表的变更同步到别的系统** → **逻辑复制**。因为你只需要那几张表、目标端可能版本不同或不是 PG。

【推论】**数驭穹图的真实选择正好落在这条线上**：它需要的是「授权的分析数据集」——**不是整个实例**，所以走**逻辑路径**；而且要能跨源、能只同步部分表，物理复制**根本做不到**。

### 3. 同步 / 异步：本质是 RPO 换延迟，但有官方矩阵

【事实】**官方给出的 `synchronous_commit` 五档与他们各自的保证**（表 19.1）——**这张表可以直接背**：

| `synchronous_commit` | 本地持久提交 | 备库在 **PG 崩溃**后仍持久 | 备库在 **OS 崩溃**后仍持久 | **备库查询一致性** |
|---|---|---|---|---|
| `remote_apply` | ✓ | ✓ | ✓ | **✓** |
| `on`（默认） | ✓ | ✓ | ✓ | |
| `remote_write` | ✓ | ✓ | | |
| `local` | ✓ | | | |
| `off` | | | | |

【推论】**这张表把「同步复制」拆成了两个正交的问题**：

```text
问题一：数据会不会丢？ → 看「备库持久」那两列
  remote_write  只保证「备库进程崩了不丢」
  on            还保证「备库操作系统崩了也不丢」
  remote_apply  再保证「备库上能查到」

问题二：备库上的读能不能立刻看到？ → 看最后一列
  【只有 remote_apply 能】
```

【结论】**「我们用了同步复制」这句话远远不够**——**要问的是「哪一档」**：

- **`on`（默认）= 走人**：主库不丢、备库不丢，**但备库上刚提交的事务可能还查不到**；
- **`remote_apply` = 走到位**：**连备库上的查询都能看到**——**代价大得多，因为它要等 WAL 重放完**（官方原话：「会带来大得多的提交延迟」）。

【推导】**把提交延迟的代价算出来**（口径写在算式里）：

```text
跨可用区 RTT ≈ 2 ms，备库 fsync ≈ 3 ms

local         ：只等本地 fsync            → ≈ 0 ms（不含本地）
on            ：+ 网络 + 备库刷盘          → ≈ 5 ms
remote_apply  ：+ 备库重放完成             → ≈ 5 + 2 = 【7 ms】

单连接 TPS：从 1/0.001 ≈ 1000 降到 1/0.007 ≈ 【143】
```

【结论】**提交延迟从毫秒级涨到 7ms，单连接吞吐掉到 1/7**——**并发连接能补回吞吐，但补不回延迟**（**P99 从 2ms 变 10ms 是质变**）。

【取舍】**还有一个必须说清的陷阱**：**同步复制会让「备库的可用性」变成「主库可用性」的一部分**——**备库挂了，主库提交就可能被卡住。** 所以生产通常配 **`FIRST 1 (a, b)` 这类「至少一个备库确认即可」**的写法，而不是「等全部」。

【推论】**这一条比结论重要**：**不要简单说「我们用了同步复制保证不丢」——要说清楚「几种确认策略、以及备库故障时主库会怎样」。**

【事实】**最后一个好用的细节**（官方原文）：**提交模式是【每个事务】可以单独选的**——**「在一个默认是同步的系统里，让某一个多语句事务异步提交」只需要在事务里 `SET LOCAL synchronous_commit TO OFF`**。

**到这里你应该能回答**：为什么「我们开了同步复制所以不会丢数据」这句话，在面试官追问「备库挂了怎么办」时会立刻站不住？

### 4. 两个能算的坑

**坑一：复制槽不消费 → WAL 永久堆积 → 磁盘写满**

【事实】**默认值是「无限保留」**——**官方原文**：

> `max_slot_wal_keep_size`：指定复制槽在 checkpoint 时**允许在 `pg_wal` 目录里保留的 WAL 文件的最大体积**。
> **如果它是 `-1`（默认值），复制槽可以保留【无限量】的 WAL 文件。**

【推导】**把事故时间算出来**：

```text
主库 WAL 生成速率 = 10 MB/s
一个逻辑复制槽的消费者挂了（没有任何告警）
pg_wal 可用空间 = 500 GB

500 GB ÷ 10 MB/s = 50,000 秒 ≈ 【13.9 小时】

→ 不到一天磁盘写满
→ 后果：【整个实例写不进去】——不是"这个复制槽坏了"，是【主库挂了】
```

【结论】**「一个消费者掉了」升级成「主库不可写」，只需要不到一天。** **这是 PG 最常见的一类生产事故，而且它是【默认配置】下的行为。**

【动作】**两件事都要做**：

```text
① 显式设 max_slot_wal_keep_size
     比如设成 100 GB → 10,000 秒 ≈ 2.8 小时后该槽失效
     → 后果从「主库写不进去」降级成「这个备库/消费者需要重建」

② 监控「不活跃的复制槽」
     查 pg_replication_slots，看 active 与保留的 WAL 量
     并写下运维约定：离线多久就删槽并重建
```

【判据】**取舍很清楚**：

> **不设上限 = 用「整个实例的可用性」去赌「消费者一定会回来」。**
> **设了上限 = 用「这个消费者需要重建」换「主库不会因为别人掉线而挂」。**
> **显然后者是对的。**

**坑二：主从延迟——回放追不上就永远追不上**

【事实】**延迟有三段**：**① 主库产出 WAL 的速度 → ② 网络传输 → ③ 备库回放。**

【推导】**第 ③ 段是最容易被忽略、也最致命的一段**：

```text
主库生成 1000 事务/秒
备库回放能力 800 事务/秒（CPU 不够 / 有冲突查询 / 单线程回放）

每秒积压 = 1000 − 800 = 200 个事务
1 小时后积压 = 200 × 3600 = 【72 万个事务】

→ 延迟【单调增长】，永远不会自己收敛
```

【结论】**这是一个硬结论**：

> **备库的回放能力必须 ≥ 主库的生成能力，否则延迟不是"有点大"，而是【单调增长到不可用】。**
> **所以「主从延迟大」的第一诊断不是"网络慢"，而是"回放能力够不够"。**

【事实】**而备库上的长查询会直接打击回放能力**——官方对冲突的处理机制是：

> `max_standby_streaming_delay`（默认 **30 秒**）：**备库在取消那些与即将应用的 WAL 记录冲突的查询之前，应该等多久。**
> **`-1` 表示允许备库【永远】等冲突查询完成。**

【推论】**这里有一个必须说清的选择**：

```text
备库上有冲突的长查询（比如报表）
  → 默认行为：等 30 秒 → 【取消那个查询】（报错）
  → 你要么让报表能被取消，要么调大这个值
  → 调成 -1（永远等）= 【让回放无限期停摆】
     → 备库延迟无限增长（上面那个算式）

另一条路：hot_standby_feedback = on
  → 备库把"我还在读这些行"反馈给主库，主库就不清理它们
  → 查询不会被取消
  → 但官方明确警告：【会造成主库的表膨胀】
     （因为主库不能回收备库还在读的旧版本，P14/P15）
```

【结论】**「备库上跑报表」这件事的代价是二选一的**：**要么报表可能被取消（30 秒后）**，**要么主库开始膨胀**。**这是「读写分离」在 PG 里最真实的一笔账。**

【取舍】**业务后果与处理**（读写分离下「写主库、读备库」会**读到旧数据**）：

> **关键读回主库**（最可靠）→ **写后一段时间内钉住主库**（读己之写）→ **监控延迟并在超阈值时降级**。
> **不要用「sleep 一下再读」这种办法。**

### 5. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「开了同步复制就不会丢」 | **要看哪一档**：`remote_write` 只保证备库进程崩不丢；`on` 才保证备库 OS 崩也不丢 |
| 「同步复制就是更安全」 | **它让备库的可用性变成主库可用性的一部分**——**备库挂了主库提交会卡** |
| 「备库上跑报表没有影响」 | **冲突查询默认 30 秒后被取消**；用 `hot_standby_feedback` 救它，**代价是主库膨胀** |
| 「主从延迟大 = 网络慢」 | **先看回放能力够不够**——**回放能力 < 生成能力时延迟单调增长，永远不收敛** |
| 「复制槽只是记个位点」 | **默认可以无限保留 WAL**——**一个掉线的消费者能在 14 小时内写满磁盘、让主库不可写** |
| 「逻辑复制能跨版本，所以能直接做迁移」 | **它默认只同步 DML，不同步 DDL**（还有大对象、序列）——**结构变更要另走流程** |
| 「逻辑复制备端是只读的」 | **反过来——逻辑复制的备端是可读可写的**，**代价是冲突要自己处理** |

## 二、自测

**Q1（计算）**：跨可用区复制，RTT ≈ 2 ms，备库 fsync ≈ 3 ms，备库重放 ≈ 2 ms。

问：**`local` / `on` / `remote_apply` 三档的提交延迟各是多少？单连接 TPS 掉到多少？为什么说「并发能补吞吐但补不回延迟」？**

**A1**：

```text
local        ：只等本地 fsync               → ≈ 0 ms（相对基线）
on           ：+ 网络 2ms + 备库刷盘 3ms     → ≈ 【5 ms】
remote_apply ：+ 备库重放 2ms               → ≈ 【7 ms】

单连接 TPS（串行提交）：
  local        ：1 ÷ 0.001 ≈ 【1000】
  on           ：1 ÷ 0.005 = 【200】
  remote_apply ：1 ÷ 0.007 ≈ 【143】
```

【结论】**从 `local` 到 `remote_apply`，单连接吞吐掉到 1/7。**

【推论】**「并发能补吞吐但补不回延迟」是什么意思**：

```text
加并发（比如 100 条连接）：
  → 总吞吐可以回到几千 TPS（因为提交是并行的）
  → 但【每一个请求的耗时】仍然是 7ms 而不是 1ms
  → P99 从 2ms 变 10ms —— 这是【质变】，不是量变

后果：
  对上游意味着【超时预算变了】
  对用户意味着【首字节延迟变高】
  → 这是吞吐指标看不见的成本
```

【取舍】**所以选哪一档要有理由**：

> **`on` 是默认，也是多数系统的答案**（主库不丢、备库不丢）。
> **`remote_apply` 只在「备库上的读必须立刻看到」时才值得**——**比如"写完立刻从备库查"的读写分离。** **但更常见的做法是：那一两条"写完立刻读"的路径直接【切回主库】，而不是让全系统都付 7ms。**

**Q2（计算）**：某实例 WAL 生成速率 **10 MB/s**，`pg_wal` 可用空间 **500 GB**。一个逻辑复制槽的消费者已经掉线。默认配置。

问：**多久之后主库会不可写？**如果把 `max_slot_wal_keep_size` 设成 100 GB 呢？

**A2**：

```text
默认 max_slot_wal_keep_size = -1（无限保留）：
  WAL 只增不减
  500 GB ÷ 10 MB/s = 50,000 秒 ≈ 【13.9 小时】

设成 100 GB：
  该槽最多保留 100 GB
  100 GB ÷ 10 MB/s = 10,000 秒 ≈ 【2.8 小时后该槽失效】
  → 后果从「主库写不进去」降级成「这个消费者需要重建」
```

【结论】**默认配置下，一个掉线的消费者能在 14 小时内把主库搞挂。**

【推论】**这道题的关键不是算数，是那个判断**：

> **不设上限 = 用「整个实例的可用性」去赌「消费者一定会回来」。**
> **设了上限 = 用「这个消费者需要重建」换「主库不会因为别人掉线而挂」。**

【补充】**光设参数还不够，必须配监控**：**查 `pg_replication_slots`，看 `active` 是不是 false、保留的 WAL 有多少。** **而且要写下运维约定：离线多久就删槽并重建。** **没有这条约定的监控，只是一个没人看的仪表盘。**

**Q3（计算）**：主库生成 **1000 事务/秒**，备库回放能力 **800 事务/秒**。

问：**延迟会稳定吗？一小时后积压多少？为什么说「主从延迟大」的第一诊断不是网络？**

**A3**：

```text
每秒积压 = 1000 − 800 = 200 个事务
一小时积压 = 200 × 3600 = 【720,000 个事务】

→ 延迟【单调增长】，不会自己收敛
```

【结论】**只要回放能力小于生成能力，延迟就是发散的**——**这不是"延迟有点大"，是"备库永远不会追上"。**

【推论】**所以诊断顺序是**：

```text
第一步：备库的回放能力够不够？（CPU / 单线程回放 / 有没有冲突查询）
第二步：有没有冲突查询在拖累回放？（默认等 30 秒后取消，或 hot_standby_feedback）
第三步：才是网络带宽与延迟
```

【取舍】**而「备库上跑报表」这件事的代价必须二选一**：

```text
不反馈（hot_standby_feedback = off，默认）：
  报表查询与回放冲突 → 等 30 秒 → 【取消报表查询】
  → 报表要能承受被取消

反馈（hot_standby_feedback = on）：
  主库不清理备库还在读的旧版本
  → 报表不被取消
  → 但官方警告：【会造成主库的表膨胀】（P14/P15）
```

【结论】**「读写分离 + 备库跑报表」在 PG 里最真实的一笔账就是这个**——**要么报表会被杀，要么主库会胖。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们上了同步复制，所以数据一定不会丢，这比异步复制安全。"

**A4**：四处问题。

1. **「同步复制」不是一个档位，是五个**：**`remote_write` 只保证备库【进程】崩了不丢；`on` 才保证备库【操作系统】崩了也不丢；`remote_apply` 再加上「备库上查得到」**（官方表 19.1）。**笼统说"同步"等于没说。**
2. **它让备库的可用性变成主库可用性的一部分**：**备库挂了，主库提交可能被卡住**——**这时候系统不是"更安全"，是"更不可用"。**
3. **它带来的是提交延迟的量级变化**：Q1 算过，**`remote_apply` 让单连接吞吐掉到 1/7**，**P99 从 2ms 变 10ms**——**这是吞吐指标看不见的成本。**
4. **异步不等于"不安全"**：**它丢的是【连续的一段】、只丢数据不损坏数据**（[[母题-P11-WAL与checkpoint]]）——**很多场景下完全可接受。**

【准确说法】"**要说清三件事：用哪一档（`on` 还是 `remote_apply`）、用几条备库确认（`FIRST 1` 还是等全部）、以及备库全挂时主库会怎样。** **「同步复制保证不丢」这句话，在追问"备库挂了怎么办"时会立刻站不住。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "主从延迟有点大，我们把网络带宽升上去就好了。"

**A5**：三处问题。

1. **延迟有三段，网络只是中间一段**：**① 主库产出 → ② 网络 → ③ 备库回放**。**而在写入密集的系统里，最常见的瓶颈是第 ③ 段。**
2. **回放能力不足时，延迟是【单调增长】的**（Q3）：**不是"有点大"，是"永远追不上"**——**这种情况上升带宽一点用都没有。**
3. **备库上的长查询会主动拖累回放**：**默认 `max_standby_streaming_delay = 30 秒`，冲突查询会被【取消】**；**用 `hot_standby_feedback` 救它，代价是主库膨胀。**

【准确说法】"**先确认备库的回放能力是否 ≥ 主库的生成能力；再看有没有冲突查询在拖慢它；最后才查网络。** **顺序错了，会花冤枉钱升带宽，而延迟仍然是发散的。**"

## 三、面试输出（学完再看）

**一句话结论**：**物理复制复制「存储的变化」，逻辑复制复制「数据的变化」**——**所有能力差异都是这一句的推论**：**物理复制是 WAL 字节流，所以它绑定【实例与版本】（整实例、备库只读可查询、版本必须一致）；逻辑复制把 WAL 解码成 INSERT/UPDATE/DELETE，所以它绑定【表与行】（可按表、可按行过滤、备端可写、可跨大版本）。** 于是 **① 只读副本用流复制，② 部分表同步到别的系统用逻辑复制**——**数驭穹图需要"授权的分析数据集"，所以走逻辑路径，物理复制根本做不到。** **同步/异步要看的是官方那张表**：`synchronous_commit` 五档对应**备库的四个落点**（本地持久 / 备库 PG 崩后持久 / 备库 OS 崩后持久 / **备库查询一致**）——**`remote_write` 只保前两个里的第一个，`on` 保三个，`remote_apply` 四个全保**，**而只有 `remote_apply` 能让备库上的读立刻看到。** **代价是延迟**：跨 AZ 下 `remote_apply` 把提交延迟从约 0 拉到 7ms，**单连接吞吐掉到 1/7**；**而且它让备库的可用性变成主库可用性的一部分**。**两个必须会算的坑**：**复制槽默认可以【无限保留 WAL】（`max_slot_wal_keep_size = -1`）——10 MB/s 的主库，一个掉线的消费者能在【13.9 小时】内把 500 GB 写满，让主库完全不可写**；**备库回放能力必须 ≥ 主库生成能力，否则延迟单调增长到不可用**（1000 vs 800 就是每小时积压 72 万），**而备库上的长查询默认 30 秒后会被取消，用 `hot_standby_feedback` 救它的代价是主库膨胀。**

**恢复关键词**：物理复制 = WAL 字节流 / 逻辑复制 = 解码出的行变更 / 绑定实例版本 vs 绑定表行 / **逻辑复制不同步 DDL** / **同步级别四列**（本地 · 备库 PG 崩 · 备库 OS 崩 · 备库查询一致）/ 只有 `remote_apply` 有第四列 / `FIRST 1 (a, b)` / **`max_slot_wal_keep_size` 默认 -1** / 13.9 小时写满 / **回放能力 ≥ 生成能力** / `max_standby_streaming_delay` 30 秒取消查询 / `hot_standby_feedback` → 主库膨胀 / `SET LOCAL synchronous_commit TO OFF`

**核心不变量 / 主线**：
**物理复制复制的是「存储的变化」，逻辑复制复制的是「数据的变化」——所有能力差异都是这一句话的推论。**
**而同步/异步要看的不是「哪个更安全」，是「备库故障时主库会怎样」。**

**完整回答骨架**：两种复制复制什么 → 各自绑定什么（实例版本 vs 表行）→ 回到题目做选择 → **同步级别矩阵（四个落点）与延迟算式** → **复制槽堆积算式 → 13.9 小时** → **回放能力的硬约束与冲突查询的处理** → 收束到「同步/异步的代价要看故障时的行为」

**追问**（先说后看）

1. **逻辑复制的目标端能写吗？** —— **能**（它是独立的可写表），**代价是冲突要自己处理**（目标端本地已有数据会与回放冲突）。**这也是它能做多源汇聚的原因——同时也是它最难运维的地方。**
2. **能不能用逻辑复制做双向同步？** —— **技术上可以，但冲突解决完全靠自己**，收益通常不如改成单向 + 明确归属。**面试里承认「双向的复杂度收益比不高」比硬吹更好。**
3. **为什么 PG 不用 binlog 也能做 CDC？** —— 因为 **WAL 本身就是完整的变更记录**，**逻辑解码把它翻译成逻辑变更（`pgoutput`）即可**。**这也解释了为什么 PG 侧的 CDC 工具（Debezium 等）都基于逻辑解码槽。**
4. **备库上的统计信息要管吗？** —— **要**。**统计信息不是"复制的数据"，它是每台实例各自 `ANALYZE` 出来的**——**只读副本如果从不分析，它的执行计划可能和主库完全不一样**（[[母题-P7-统计信息与慢查询定位]]）。
5. **为什么你项目第一版不做完整 CDC？** —— 要说出**取舍**：**CDC 要求源端启用逻辑复制/binlog 并常驻一个消费者，一旦消费者停摆就有 WAL/binlog 堆积风险**（这正是 Q2 那个 13.9 小时）；**而分析场景对新鲜度的要求是分钟级可接受**。**所以用「可恢复快照 + `updated_at` / 递增主键轮询 + 位点与校验」换来了「不侵入客户生产库 + 可复现」**——**升级条件是出现真实的秒级新鲜度需求。** **这段是项目叙事的核心，必须能自己讲。**

**同类变体**

- 「MySQL 的复制和 PG 差在哪？」—— **MySQL 靠 binlog（Server 层逻辑日志）**，**格式有 Statement / Row / Mixed 三种**；**PG 的物理复制走 WAL、逻辑复制走 WAL 逻辑解码**。**关键差异**：**MySQL 的复制天生是"逻辑"的（binlog 就是行/语句），所以它天然支持跨版本与按表过滤；PG 的物理复制是字节流，所以它天生不能**——**PG 是后来用逻辑解码补上了逻辑复制的能力**（[[母题-M14-主从复制与延迟]]）。
- 「主从延迟会影响读一致性吗？」—— **会**。**RC 下"写主库读备库"读到旧数据是常态。** **处理按可靠性排序：关键读回主库 → 读己之写时钉住主库 → 监控延迟并降级。** **不要用「sleep 一下再读」。**
