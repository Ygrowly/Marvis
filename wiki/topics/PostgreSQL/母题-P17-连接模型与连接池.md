# 母题 P17 · 连接模型与连接池

> **模块**：PostgreSQL / 数据增长与高可用
> **所属主线**：六 · 数据增长与高可用（数据多了怎么不被拖垮）
> **关联母题**：[[母题-P16-分区表]] · [[母题-P13-MVCC与可见性]] · [[母题-P18-乐观并发控制]]
> **素材来源**：`study/09-数据缓存队列与一致性` 第 7 节（Worker 与任务模型）+ 通用知识（**连接池模式细节待你核对**）

**题目**：同样是 8 核机器，MySQL 能开几千个连接，PG 开几百就开始卡。为什么？

**母题**：为什么 PG 的连接很贵？连接池模式怎么选？

**为什么重要**：这是 **「PG 与 MySQL 的七处差异」里的最后一条**，也是**最容易被"不疼不痒地知道"、却在真实容量规划上踩坑的一条**——因为它决定了你的**服务能起多少并发**。它和主线七（并发控制）是一条链：**连接贵 → 并发受限 → 更需要「短事务 + 无锁并发」**（P18）而不是「长事务 + 加锁等待」。

**一句话结论**：**PG 是「一个连接一个后端进程」**（fork 出独立进程），每个连接有独立内存、进程调度与上下文切换开销大，所以并发连接数上去后性能断崖；**MySQL 是线程模型，连接便宜得多**。因此 **PG 的连接池是刚需**，并且有两种模式：**session 模式**（一个客户端长期占一个连接，简单，但连接数仍随客户端数增长）与 **transaction 模式**（**事务结束就归还**，连接数 ≈ 同时活跃事务数，效率高，**但会话级状态不可用**）。

**恢复关键词**：进程模型 vs 线程模型 / 连接成本（内存 + 调度）/ pgbouncer / session vs transaction 模式 / **会话级状态不可用**（prepared statement / session 变量 / 临时表 / advisory lock）/ 连接数上限由「同时活跃事务数」决定

**核心不变量 / 主线**：
**连接数的上限不是「数据库能不能开」，而是「开了之后每个请求还快不快」。** 所以要管的是**「同时活跃的事务数」**，不是「连接数」——**这也是为什么 PG 的池化推荐 transaction 模式：它让连接数与客户端数解耦。**

**完整回答骨架**：进程模型 vs 线程模型 → 为什么连接贵（三笔开销）→ 所以必须池化 → 两种池化模式与选择 → transaction 模式的约束（会话状态）→ 容量规划的正确口径

## 原理分解

### 一、为什么 PG 的连接贵

| 开销量 | 具体表现 |
|---|---|
| **内存** | 每个后端进程有独立的私有内存 + 共享缓冲区映射；**连接数 × 单连接开销 = 常驻内存** |
| **进程调度** | 每个连接是一个 OS 进程，**上下文切换、调度、信号开销都远高于线程**；连接一多，**CPU 时间大量花在"管理连接"而不是"执行查询"上** |
| **缓冲区争用** | 更多并发会话 → 更多并发访问共享缓冲区 → 锁与争用上升（**吞吐反而下降**，不是平滑增长） |

**对比 MySQL**：线程模型，单连接开销小得多，所以「几千连接」是常规配置。**PG 的实践数字通常是"几十到几百个活跃连接"**——超过这个量级，**继续加连接会让单位吞吐下降**（这也是为什么有连接池这件事在 PG 侧几乎不可省）。

### 二、所以连接池是刚需（不是优化项）

**没有池化时的经典事故**：

```
应用每个请求开一个连接 → 并发请求数 = 连接数
  ↓
峰值流量 → 连接数暴涨 → 数据库 CPU 都在 fork/调度
  ↓
每个请求更慢 → 请求堆积 → 开更多连接 → 雪崩
```

**池化的本质作用**：**把「客户端数量」和「数据库连接数」解耦**，并在数据库前面提供一个**可控的排队点**。

**关键认知**：**连接池不只是"复用连接省开销"，它更重要的功能是"限制并发、保护数据库"**——**池子满了就让请求排队（或快速失败），而不是让数据库被压垮。** 这一点在面试里值得强调，因为它把连接池从"性能优化"提升到"稳定性设计"。

### 三、两种模式：session vs transaction

| | **session 模式** | **transaction 模式** |
|---|---|---|
| 连接何时归还 | **客户端断开时** | **事务结束时** |
| 连接数 | 随客户端数增长 | **≈ 同时活跃的事务数**（大幅降低） |
| 会话级状态 | **可用** | **不可用 / 不可靠** |
| 适用 | 简单、连接数可控、或有会话状态依赖 | **高并发 Web / API 的标准选择** |

**transaction 模式效率高得多**——因为它利用了「**大多数请求的时间花在应用逻辑与网络，而不是在数据库事务里**」这一点：**同一个数据库连接可以在不同请求间轮流服务，因为它只在事务期间被占用。**

### 四、transaction 模式的约束（必须讲清，否则会踩坑）

在 transaction 模式下，**「会话」被切碎了**，所以这些**依赖会话状态**的东西都不能依赖：

| 依赖项 | 问题 |
|---|---|
| **预编译语句（prepared statement）** | 语句缓存在**会话**里，而会话可能换了物理连接 → 报「语句不存在」或隐式重新规划。**实践上常把驱动/代理的语句缓存关掉或设为 0。** |
| **会话变量**（`SET ...`） | 下一次请求可能落到另一个连接，**设置丢失**。**必须改成事务级设置或每次显式设置。** |
| **会话级临时表** | 同上，会不可见。 |
| **advisory lock（会话级）** | 会话一换就失去语义 → **锁可能被错误地"留在"另一个请求身上或提前释放**。 |
| 游标（跨提交保持的） | 多数场景要求事务内使用。 |

**判断方法一句话**：**「这个状态是不是"跟着连接走"的？」跟着走 → transaction 模式不能用；跟着事务走 → 可以用。**

**所以决定池化模式的时间点应该很早**：**在写第一行代码之前就定**——因为「能不能用 transaction 模式」会影响**数据访问层的写法**（比如还敢不敢用会话级临时表、敢不敢依赖驱动的语句缓存）。

### 五、容量规划的正确口径

**要算的是「同时活跃事务数」，不是「连接数」**：

```
需要的连接数 ≈ 峰值 QPS × 单个事务平均持有连接的时间
```

**推论有三条，都很实用**：

1. **缩短事务 = 提高容量**——**同样的连接数能支撑更高 QPS**。这条把 P14（长事务）和容量规划连起来了：**长事务既按住了回收边界，又占着连接不放。**
2. **应用侧也要限并发**：池子 + 应用超时 + 队列上限，**否则池子只是把雪崩推迟几秒**。
3. **读写分离能摊开读压力**，但**写压力只落在主库**——**所以"加只读副本"解决不了写路径的连接瓶颈**。

## 二、扩展：类似题与追问

**类似题**

1. 「连接池调多大合适？」——**先算同时活跃事务数，再用压测验证**；**过大反而降低吞吐**（更多争用、更多上下文切换）。「经验值」不如「自己压出来的曲线」。
2. 「没有连接池会怎样？」——见上面的雪崩路径。**核心不是"慢"，是"没有排队点"**。
3. 「PG 有没有内置的连接池？」——**没有服务端内置池**（连接就是进程），社区方案是外部代理（`pgbouncer` 之类）或语言侧池。**MySQL 的 `thread_cache` 那套类比不成立。**

**追问链**

- 追问一层：**「为什么不能简单把 `max_connections` 调很大？」**——因为**连接本身要占内存**（每连接私有内存 + 共享缓冲区映射）、**调度开销随进程数上升**、**并发访存争用加剧**；**结果往往是"连接数增加了，总吞吐反而下降，尾延迟显著变差"**。**所以正确方向是"减少连接占用时间"（短事务 + 池化），不是"扩大连接池上限"。**
- 追问二层：**「这跟你项目里的 Worker 有什么关系？」**——关系很直接：**Worker/队列消费者天然是"长驻连接"**（它们持续取任务），所以**必须给它们单独的池与上限**，否则**后台任务会把前台请求的连接挤掉**。**RuleArena 的「条件更新认领任务」在这里又赢一次**（P18）：**认领是一个短事务（一条 UPDATE），不是"开事务再慢慢处理"**——**它占用连接的时间极短，既省连接也更少锁等待。** **这条把连接模型、池化模式、并发控制三件事收成了一个设计结论：短事务 + 池化 + 无锁并发控制是同一套选择。**
