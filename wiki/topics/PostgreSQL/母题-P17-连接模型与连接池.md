# 母题 P17 · 连接模型与连接池

> **模块**：PostgreSQL / 数据增长与高可用

**导读**：必懂 3 件事（① **PG 是「一个连接一个进程」**——官方原话是 `fork` 一个新进程，所以连接是**重资源**，不是句柄 ② **`work_mem` 是「每个操作」的上限，不是「每个连接」**——这让内存放大比直觉更狠 ③ **事务级池化会把「预处理语句 / 会话状态」的作用域搞乱**——这是连接池最经典的坑）· 读完约 11 分钟 · 需要先懂：[[母题-P10-无间隙锁与锁变体]]

**题目**：为什么 MySQL 里「连接池开个几百」很正常，PG 上却要配个连接池中间件？

**母题**：PG 的连接为什么贵？连接池怎么配、有什么坑？

**为什么重要**：这是**「数据增长」这条线里最容易被忽略、也最容易在上线当天炸掉的一环**——**应用侧的连接数是一个会随「副本数 × 每副本连接数」相乘的东西**，**而 PG 的 `max_connections` 是一个【服务端启动时固定】的上限**，**两者一旦撞上，表现是"间歇性连不上"而不是"明确的报错"。**

**一句话结论**：**PG 是「一个连接一个进程」**——官方原话是为每个连接 `fork` 一个新进程，所以**每个连接都有一份真实的进程内存**，连接数是**重资源**。再加上 **`work_mem` 是【每个操作】的上限而不是每个连接**，**一个连接可能同时占用好几份 `work_mem`**，**内存放大比直觉大得多**。所以生产上的标准做法是**在应用和数据库之间放一个连接池**（pgbouncer 之类），**把「几百个客户端连接」映射成「几十个服务端连接」**。**但连接池有两个必须知道的坑**：**事务级池化会让预处理语句与会话状态的作用域错乱**；**而池化本身不解决 `idle in transaction`**——它只让这类连接更少。

**恢复关键词**：一个连接一个进程（fork）/ 连接是重资源 / `max_connections` 默认 100（启动时固定）/ **`work_mem` 是每个操作不是每个连接** / 会话级 vs 事务级 vs 语句级池化 / **事务池化 × 预处理语句** / `idle in transaction` 不因池化而消失

**核心不变量 / 主线**：
**连接在 PG 里是「进程」级的资源，不是「句柄」。**
**所以架构上只有一条路：让「客户端连接数」和「服务端连接数」解耦——这就是连接池存在的全部理由。**

**完整回答骨架**：连接为什么贵（进程模型）→ **`work_mem` 的放大陷阱** → 连接池的三种模式 → **事务池化与预处理语句的冲突** → 池的大小怎么定 → 与长事务/空闲事务的关系 → 生产配置

**完整回答（口述稿）**：
**PG 是"一个连接一个进程"**——官方原话是为每个连接 `fork` 一个新进程，所以**每个连接都有一份真实的进程内存**，连接数是**重资源**（这和 MySQL 的线程模型完全不同）。

再加一条常被忽略的：**`work_mem` 是【每个操作】的上限，不是每个连接**——**一个连接可能同时占用好几份 `work_mem`**，**内存放大比直觉大得多**。

所以生产上的标准做法是**在应用和数据库之间放连接池**（pgbouncer 之类），**把"几百个客户端连接"映射成"几十个服务端连接"**。

**但连接池有两个必须知道的坑**：**事务级池化会让预处理语句与会话状态的作用域错乱**；**池化本身不解决 `idle in transaction`**——它只让这类连接更少，长事务还得靠应用侧的纪律去治。

**分层要点**：
- **结论**：进程模型让连接很贵；work_mem 按操作算、放大比直觉大；必须上连接池，但池化不治长事务。
- **推导链**：每连接一进程 → 内存真实占用 → work_mem 按操作 → 内存放大 → 连接池映射 → 两个坑。
- **量化**：几百客户端连接 → 几十服务端连接；work_mem 是按操作不是按连接。
- **边界与常见误解**："调了连接池就不会有 idle in transaction"×；事务级池化会让会话状态错乱。

## 一、教材

### 1. 连接为什么贵：进程模型

::figure pg-connection-pool.svg | 一个连接一个进程：连接成本、work_mem 放大与池化模式 | 每连接 fork 进程、work_mem 是每个操作的上限、三种池化模式的作用域、事务池化与预处理语句的冲突

【事实】**官方对架构的描述就是答案**：

> **为了处理多个并发连接，PG 会为【每个连接启动（`fork`）一个新进程】。**
> **从那一刻起，客户端和这个新的服务端进程直接通信，不再经过原来那个 `postgres` 进程。**
> **因此：监督进程一直在运行、等待连接；而客户端与它对应的服务端进程则来了又走。**

【推论】**「进程」这个词带来三个直接后果**：

```text
① 每个连接有一份【真实的进程内存】（不是共享的栈）
   → 连接数直接等于内存开销的一乘数

② 建立连接 = fork
   → 有 CPU 成本，短连接场景下不可忽略

③ 连接数上限（max_connections）在服务端【启动时】就固定
   → 而且官方说：PG 会根据 max_connections【直接推算若干资源】，
     提高它会导致这些资源（【包括共享内存】）的分配增加
```

【事实】**`max_connections` 的官方口径**：

> **默认通常是 100 个连接**，但如果你的内核设置不支持（`initdb` 时会判断），可能更少。**这个参数只能在服务器启动时设置。**

【推论】**这就是题目里那个对比的根源**：

```text
MySQL：连接是「线程 + 会话状态」，成本低得多
  → 应用池开几百是常规操作

PG：连接是「进程」
  → 服务端 max_connections 默认 100
  → 而应用侧是【副本数 × 每副本池大小】
     8 个副本 × 每副本 50 连接 = 400 连接
     → 【直接超过上限】
```

【结论】**PG 上「连接数」是一个需要架构层解决的问题，不是一个配置项。**

---

### 2. 那个放大陷阱：`work_mem` 是「每个操作」的上限

【推导】**这是 PG 内存规划里最容易算错的一处**：

```text
常见的错误心算：
  「100 个连接 × work_mem 4MB = 400MB，没问题」

实际：
  work_mem 是【每个排序 / 哈希 / 物化操作】的上限
  一个复杂查询可能同时有多个这样的节点
    （排序 + 哈希连接 + 哈希聚合 + …）

  假设平均每个查询有 3 个这样的节点：
    100 连接 × 3 节点 × 4MB = 【1.2 GB】
  峰值时更多
```

【结论】**实际内存占用 = 连接数 × 每个查询的此类节点数 × `work_mem`——三个因子相乘。**

【推论】**所以「把 `work_mem` 调大」这个动作的风险面和直觉不同**：**它不是"每个连接多花 4MB"，而是"每个连接可能多花好几份 4MB"。** **这就是为什么 `work_mem` 应该【按需要调】而不是全局调大**（[[母题-P6-执行计划怎么看]] 里那个 `external merge`，先确认是哪个查询在落盘，再决定是给它调还是改 SQL）。

【补充】**这也是连接池的一个隐藏价值**：**它把「可能的并发查询数」压下来**——**服务端只有 50 个连接，就最多只有 50 个查询在同时消耗 `work_mem`**，**而不是 400 个。**

### 3. 三种池化模式与它们的「作用域」

| 模式 | 连接归还给池的时机 | **不能跨越的东西** |
|---|---|---|
| **会话级**（session pooling） | **客户端断开时** | 无——语义和直连完全一样 |
| **事务级**（transaction pooling） | **每个事务结束时** | **预处理语句、临时表、`SET`、游标、advisory lock（会话级）、`LISTEN`** |
| **语句级**（statement pooling） | **每条语句结束时** | **多语句事务本身** |

【判据】**这张表的读法是**：

> **池化把连接"借出去又收回来"，所以任何【跨越归还点还活着的会话状态】都会出问题。**
> **归还点越靠前（事务结束 < 会话结束），能跨越的东西越少。**

【结论】**会话级池化语义最安全、节省最少；事务级池化节省最多、但破坏了会话状态。** **这就是那道选择题的全部。**

---

### 4. 最经典的坑：事务池化 × 预处理语句

【推导】**把冲突讲清楚**：

```text
预处理语句（PREPARE）的生命周期是【连接级】的：
  在连接 A 上 PREPARE 的语句，只有连接 A 认得

事务级池化下，"连接"在事务之间会被换给别人：
  客户端 ① 在连接 A 上 PREPARE stmt
  → 事务结束，连接 A 归还给池
  → 客户端 ② 拿到了连接 A
  → 客户端 ① 下次执行 stmt 时拿到了连接 B
  → 【连接 B 上没有 stmt】→ 报错
```

【事实】**PG 的驱动程序（JDBC / asyncpg 等）普遍默认使用预处理语句**——**所以"上了 pgbouncer 之后应用开始报 `prepared statement does not exist`"是一个非常典型的现场。**

【推论】**四条出路**：

```text
① 池化模式改成【会话级】（最安全，但节省最少）
② 关掉驱动的预处理语句（改用简单查询协议）
     → 代价：失去服务端预处理带来的规划复用
③ 用支持"预处理语句跟踪"的池（pgbouncer 的对应选项 / 或应用层池）
④ 在应用层用【连接池】（比如 HikariCP 连每一个 PG 后端）
     → 连接数是"应用实例数 × 每实例池大小"，仍然要对服务端负责
```

【取舍】**判据**：

> **「要不要事务级池化」不是看它能省多少连接，是看【你的应用能不能放弃会话状态】。**
> **用不到预处理语句、临时表、会话级 `SET` 的应用，事务池化是免费的午餐；用得到的，改造成本可能远超省下的连接数。**

【补充】**这也是一个很好的「你知道自己在用什么」的检验**：**能说出「事务池化会破坏预处理语句」，说明你配置过 pgbouncer 并踩过这个坑，而不是抄了一份配置。**

### 5. 池的大小怎么定

【推导】**一个常见的误区与它的修正**：

```text
误区：「连接数越多吞吐越高」
实际：连接数超过某个点后，吞吐【下降】
  原因：更多连接 = 更多并发查询 = 更多争抢（CPU、IO、锁）
  而 PG 的锁等待是【无限期】的（P10）
  → 连接越多，队列越长

所以正确的方向是【小池 + 排队】：
  池小一点，让请求在【应用侧】排队（可控、可观测）
  而不是在【数据库侧】排队（无限等、占满连接）
```

【取舍】**定池大小的三个输入**：

```text
① 数据库的 CPU 核数（并发查询数超核数越多，上下文切换越多）
② 每个查询的平均耗时与 IO 比例（IO 密集的可以多一点）
③ 有多少个应用实例共用这个库（这是最容易漏的一个乘数）
```

【补充】**池的上限必须留出运维余量**：**`max_connections` 是给【所有】客户端用的——包括你自己的运维终端、监控采集、备份工具、以及 `superuser_reserved_connections` 预留的那几个槽位。** **把应用池之和顶到 `max_connections`，等于把自己的运维通道也堵死了。**

---

### 6. 连接池不解决的两件事

【事实】**池化让连接更少，但不会消除下面两类事务**：

| 问题 | 为什么池化管不了 |
|---|---|
| **`idle in transaction`** | **它是「事务开着不提交」**，不是「连接太多了」——**池化只让这种连接的数量少一点，不改变性质**。**而且它按住回收边界**（[[母题-P14-长事务与表膨胀]]） |
| **长事务** | **同上**——**事务的时长与池的大小无关**（[[母题-P13-MVCC与可见性]]） |

【推论】**所以正确的做法是「池化 + 超时」两条一起上**：

```text
池化     ：控制【连接数】这个维度
超时     ：控制【事务时长】这个维度
  idle_in_transaction_session_timeout  ← 治 idle in transaction
  statement_timeout                    ← 治跑飞的查询
  lock_timeout                         ← 治 PG 的无限等锁（P10）
```

【结论】**池化解决的是「连接多」，超时解决的是「事务长」——**它们是两个正交的问题**，**只做其中一个，故障的形态会换一个样子出现。**

### 7. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「PG 和 MySQL 一样，连接池是优化项」 | **PG 里连接池是【架构必需项】**——连接是进程级资源，`max_connections` 默认 100 且启动时固定 |
| 「`work_mem` × 连接数就是内存占用」 | **漏了乘数**——它是**每个操作**的上限，**一个查询可能有多个这样的节点** |
| 「上了连接池就万事大吉」 | **事务池化会破坏预处理语句与会话状态**；**而且池化不治 `idle in transaction` 与长事务** |
| 「连接数越多吞吐越高」 | **超过某个点后吞吐会下降**——更多并发争抢，而 PG 的锁等待是无限的 |
| 「池只要不超过 `max_connections` 就行」 | **还要给运维、监控、备份、以及 `superuser_reserved_connections` 留槽位** |
| 「池化到事务级能省最多，所以直接选它」 | **要先确认应用不用预处理语句 / 临时表 / 会话级 `SET`**——否则改造成本可能远超收益 |

## 二、自测

**Q1（计算）**：服务端 `work_mem = 4MB`，应用有 **100 个连接**，平均每个查询有 **3 个**会用到 `work_mem` 的节点（排序 / 哈希）。

问：**这 100 个连接最坏情况下可能占用多少内存？「100 × 4MB = 400MB」错在哪？**

**A1**：

```text
错误心算：
  100 连接 × 4MB = 【400MB】

正确算法：
  work_mem 是【每个排序 / 哈希 / 物化节点】的上限
  平均每个查询有 3 个这样的节点
  → 100 × 3 × 4MB = 【1.2 GB】
  → 峰值时更多
```

【结论】**实际可能是直觉的 3 倍**——**而且这个倍数随查询复杂度变化，不是固定的。**

【推论】**为什么这条重要**：

```text
「把 work_mem 调大」看起来是每个连接多花 4MB
  实际是每个连接可能多花【好几份】

  4MB → 32MB 时：
    直觉：100 × 32MB = 3.2 GB
    实际：100 × 3 × 32MB = 【9.6 GB】
```

【判据】**所以 `work_mem` 应该按需调，不全局调**：

> **先在 `EXPLAIN (ANALYZE, BUFFERS)` 里定位到那个 `Sort Method: external merge`（[[母题-P6-执行计划怎么看]]），**
> **再决定是给那一条查询单独调（`SET LOCAL work_mem`）、还是改写 SQL 让它少排点行。**
> **全局调大是把 9.6 GB 的风险摊给所有人。**

【补充】**这也是连接池的一个隐藏价值**：**服务端只有 50 个连接，就最多只有 50 个查询在同时吃 `work_mem`**——**而不是 400 个。**

**Q2（计算）**：短连接场景：每秒建立 **500** 个新连接，每次 `fork` + 初始化约 **5 ms**。

问：**这部分开销占多少 CPU？连接池能省掉多少？**

**A2**：

```text
每秒 fork 消耗的 CPU 时间 = 500 × 5ms = 2500 ms = 【2.5 秒 / 秒】

也就是说：光建连接这一件事，就吃掉了【2.5 个核】的满载时间
  → 而这段时间里数据库【什么业务都没做】
```

【结论】**在短连接场景下，「建连接」本身可以成为主要负载之一。**

【推论】**连接池省掉的是什么**：

```text
无池：每次请求 = fork + 初始化 + 业务查询
有池：每次请求 = 复用一个已有连接 + 业务查询
  → fork 那 2.5 核/秒的 CPU 全省下来
  → 而且省掉了每次连接的系统调用、内存分配、认证
```

【取舍】**但要算清楚它是【换】不是【消】**：**连接池中间件本身是一个额外组件**——**它要多一跳网络、要多一份运维对象（它的高可用怎么办？）、还会引入事务池化那些坑（第 4 节）。** **所以它是"值得"的前提是：连接建立频率真的高。**

【补充】**反过来说**：**如果应用本来就是长连接（比如服务端只起一次连接池连数据库），那么再加一层 pgbouncer 的收益主要是「连接数收敛」，而不是「省 fork」。** **两者的理由不同，配置也不同。**

**Q3（判读 + 计算）**：某应用 **8 个副本**，每个副本的连接池大小配成 **50**。数据库 `max_connections = 100`。

问：**会发生什么？为什么表现是「间歇性连不上」而不是「启动就报错」？**

**A3**：

```text
应用侧尝试建立的总连接数 = 8 × 50 = 【400】
服务端上限 = 【100】

→ 缺口 300 个连接

表现为什么是"间歇性"：
  ① 每个副本只在【需要时】才去建连接（不是启动时就建满 50 个）
  ② 哪个副本、在哪一刻拿到连接，取决于当时的负载分布
  ③ 拿不到的副本 → 报错 → 熔断 → 重试 → 又碰到别人占着的连接

  → 所以现象是【随机的、和流量相关的失败】，而不是
     "第 101 个连接必然失败"这种确定性错误
```

【结论】**这是一个【乘数没算】的经典事故**——**应用侧写的是一个副本的配置，服务端面对的是所有副本的和。**

【判据与动作】：

> **`max_connections` 是给【所有】客户端用的**——**包括你的运维终端、监控采集、备份工具，以及 `superuser_reserved_connections` 预留的槽位。**
> **正确的算式**：**应用池之和 + 运维/监控/备份 + 预留 ≤ `max_connections`。**
> **而且这个数字要写进文档**——**下次有人加副本时会用到。**

【补充】**这条也说明为什么连接池中间件是 PG 的标准架构**：**它让「8 个副本 × 50」在服务端看起来只是「50 个连接」**——**乘数被消掉了。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们上了 pgbouncer，用的是事务级池化，连接数问题解决了，也不会有空闲事务了。"

**A4**：三处问题。

1. **事务级池化会破坏会话状态**：**预处理语句的生命周期是【连接级】的**，**而事务池化下连接在事务之间会被换给别人**——**应用会报「预处理语句不存在」这类错**。**`PREPARE`、临时表、会话级 `SET`、游标、会话级 advisory lock、`LISTEN` 都有同样的问题。**
2. **它不消除 `idle in transaction`**：**那是一个【开着事务不提交】的状态，和连接数多少无关**——**池化只让它更少，不改变性质**；**而且它仍然按住回收边界。**
3. **它也不消除长事务**：**事务时长与池大小是正交的两个维度。**

【准确说法】"**池化解决的是「连接数」，超时解决的是「事务时长」——两件事要一起做。** **而事务池化要先确认应用不用预处理语句 / 临时表 / 会话级 `SET`；用得到的，就选会话级池化，或者用支持预处理语句跟踪的配置。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "数据库有点慢，我们把 `work_mem` 从 4MB 调到 64MB，应该能缓解排序落盘的问题。"

**A5**：三处问题。

1. **`work_mem` 是每个操作的上限，不是每个连接**：**一个查询可能有多个用到它的节点**（Q1）——**调大 16 倍，内存风险也是 16 倍，而且是乘过节点数的 16 倍。**
2. **它是全局参数**：**调大它等于给【所有】查询都加预算**——**包括那些本来不需要的、以及那些你还没发现的慢查询。**
3. **没定位到根因**：**排序落盘（`external merge`）只是现象**——**可能是排序的数据量本来就该在上游砍掉**（[[母题-P6-执行计划怎么看]]），**调 `work_mem` 只是给一个错误的计划买单。**

【准确说法】"**先用 `EXPLAIN (ANALYZE, BUFFERS)` 定位到具体哪条查询在落盘、落了多少，再决定**：**给那一条单独 `SET LOCAL work_mem`，或者改 SQL 让它少排点行。** **全局调大 `work_mem` 是 PG 里最容易造成 OOM 的动作之一。**"

## 三、面试输出（学完再看）

**一句话结论**：**PG 是「一个连接一个进程」**——**官方原话是为每个连接 `fork` 一个新进程，客户端和这个服务端进程直接通信。** 所以**连接在 PG 里是进程级资源，不是句柄**——**每个连接有一份真实内存、建立连接有 CPU 成本、而 `max_connections` 默认只有 100 且【只能在启动时设置】。** **内存的放大比直觉更狠**：**`work_mem` 是【每个排序/哈希节点】的上限，不是每个连接**——**100 个连接 × 每个查询 3 个这样的节点 × 4MB = 1.2 GB**，**而把它调到 64MB 就是 19.2 GB 的风险**（所以应该按需 `SET LOCAL` 而不是全局调）。**这就是为什么 PG 的标准架构里必须有一个连接池中间件**：**它把「几百个客户端连接」映射成「几十个服务端连接」，把应用侧的乘数（副本数 × 每副本池大小）消掉**——**不然 8 个副本 × 50 连接 = 400 会直接撞上 `max_connections = 100`，而且表现是【间歇性连不上】而不是确定性报错。** **连接池有**三种模式**，**区别在「连接什么时候归还」**：**会话级安全但省得少，事务级省得多但会破坏会话状态，语句级连多语句事务都保不住。** **最经典的坑是「事务池化 × 预处理语句」**：**`PREPARE` 的生命周期是连接级的，而事务池化会把连接在事务之间换给别人**——**表现就是 `prepared statement does not exist`。** **还有一条要分清楚**：**池化解决「连接多」，超时解决「事务长」，两者正交**——**`idle_in_transaction_session_timeout` / `statement_timeout` / `lock_timeout` 是另一条线，池化替代不了它们。**

**恢复关键词**：**一个连接一个进程（fork）** / `max_connections` 默认 100（启动时固定，且影响共享内存分配）/ **`work_mem` 是每个操作不是每个连接** / 100×3×4MB = 1.2 GB / 会话级 vs 事务级 vs 语句级 / **事务池化破坏预处理语句 · 临时表 · 会话级 SET · 游标 · advisory lock · LISTEN** / **8 副本 × 50 = 400 > 100 → 间歇性连不上** / **池化与超时是两条正交的线** / 短连接 fork 500 × 5ms = 2.5 核/秒

**核心不变量 / 主线**：
**连接在 PG 里是「进程」级的资源，不是「句柄」。**
**所以架构上只有一条路：让「客户端连接数」和「服务端连接数」解耦——这就是连接池存在的全部理由。**

**完整回答骨架**：进程模型（fork）→ **`work_mem` 的乘数陷阱（算 1.2 GB）** → 三种池化模式与「作用域」→ **事务池化 × 预处理语句的冲突与四条出路** → 池大小的三个输入 → **池化与超时是两条正交的线** → 收束到「解耦」

**追问**（先说后看）

1. **连接池该用哪种模式？** —— **先问应用需不需要会话状态**：**用不到 `PREPARE` / 临时表 / 会话级 `SET` / 游标 / `LISTEN` 的应用，事务级池化是免费的午餐**；**用得到的，要么改成会话级，要么用支持预处理语句跟踪的配置。** **这个判断不能拍脑袋，要看驱动的默认行为。**
2. **池开多大？** —— **三个输入**：**数据库的核数、每个查询的耗时与 IO 比例、以及【有多少个应用实例共用这个库】。** **而方向是「小池 + 应用侧排队」**——**让请求在应用侧排队（可控、可观测），而不是在数据库侧排队**（**而 PG 的锁等待是无限的**，[[母题-P10-无间隙锁与锁变体]]）。
3. **为什么说 PG 的 `max_connections` 不能随便调大？** —— **官方说得很清楚：PG 会根据 `max_connections` 直接推算若干资源，提高它会导致这些资源（包括共享内存）的分配增加。** **而且它对连接建立的开销没有任何改善**——**只是把"墙"挪远了一点。** **正解是加池，不是加 `max_connections`。**
4. **连接池能不能解决表膨胀？** —— **不能**。**它减少连接数，但不改变「事务开多长」。** **`idle in transaction` 仍然是 `idle in transaction`——它照样按住回收边界**（[[母题-P14-长事务与表膨胀]]）。**要治它，只能靠 `idle_in_transaction_session_timeout` 和代码改造。**
5. **备库上的 `max_connections` 要注意什么？** —— **官方明确说：运行备库时，这个参数必须设成【等于或大于】主库的值**，否则**备库上不允许查询**（[[母题-P12-流复制与逻辑复制]]）。**这是一条很容易漏、而且一漏就整个只读副本不可用的配置。**

**同类变体**

- 「PG 和 MySQL 在连接模型上差多少？」—— **MySQL 是「一个连接一个线程」（线程 + 会话状态），PG 是「一个连接一个进程」。** **后果有三**：**① PG 的单连接内存开销更大；② PG 的 `max_connections` 更保守（默认 100）；③ PG 更需要连接池中间件。** **所以「我们 MySQL 池开 500」搬到 PG 上会直接撞墙。**
- 「应用层连接池（HikariCP 等）够不够，一定要 pgbouncer 吗？」—— **取决于副本数**：**应用层池解决的是「单个实例内的连接复用」，但不解决「多副本相乘」**。**8 个副本各开 50，服务端看到的就是 400。** **要消掉这个乘数，就需要一个【共享的】池化点——这就是 pgbouncer 的位置。**
