# 母题 P1 · 索引类型选型

> **模块**：PostgreSQL / 索引与表设计
> **所属主线**：一 · 索引与表设计（怎么让查询不用扫全表，表怎么建才不埋雷）
> **关联母题**：[[母题-P2-堆表与回表]] · [[母题-P3-部分索引与表达式索引]]
> **素材来源**：`study/09-数据缓存队列与一致性` 第 3 节 + 通用知识（**类型细节部分待你核对**）

**题目**：一张表要同时支撑两种查询——按 `status` 等值过滤，和在 `tags` 数组里做「包含」判断。你只有一次建索引的机会，先建哪个？另一类查询怎么办？

**母题**：为什么 PG 默认是 B-tree？GIN / GiST / BRIN / Hash 各在什么查询形状下才该用？

**为什么重要**：这是 **PG 与 MySQL 最显眼的一处差异**。MySQL 基本上是「B+ 树 + 少量特例」，PG 是**索引类型动物园**——面试官问 PG 索引，考的从来不是记住几个缩写，而是**你会不会按查询形状选型**。答成「都建 B-tree」会立刻暴露没在 PG 上做过真实优化。

**一句话结论**：默认 B-tree 是因为它**覆盖最广的查询形状**（等值、范围、排序、前缀）；其余类型各自绑定一种形状——**GIN 管「多值包含」**（数组 / JSONB / 全文），**GiST 管「几何与近邻 / 范围重叠」**，**BRIN 管「物理有序的大表按范围扫」**，**Hash 只管等值**。选型判据是**「这个查询用的什么操作符」**，不是「哪个更快」。

**恢复关键词**：操作符类别（operator class）/ B-tree 等值+范围+排序 / GIN 多值包含 / GiST 几何近邻 / BRIN 块级摘要 / Hash 只等值 / 与部分索引组合

**核心不变量 / 主线**：
**索引是「按某种方式重新组织或摘要数据」的结构，它能回答哪类查询，由它的组织方式决定。** 所以选型的第一句话永远是——**这个查询用的是哪个操作符**；第二句话才是——**代价是什么**。

**完整回答骨架**：默认为什么是 B-tree（覆盖面）→ 四种类型的组织方式与对应操作符 → 回到题目做选择 → 各自的代价与边界 → 一句判据收尾

## 原理分解

### 一、B-tree 为什么是默认

因为它同时支持这些，而绝大多数业务查询落在这里面：

| 能力 | 例子 |
|---|---|
| 等值 | `WHERE status = 'RUNNING'` |
| 范围 | `WHERE created_at >= ? AND created_at < ?` |
| 排序 | `ORDER BY updated_at DESC`（可直接用索引序，省一次 sort） |
| 前缀匹配 | `WHERE name LIKE 'abc%'`（**前缀**才行，`%abc` 不行） |
| 唯一性 | `UNIQUE`、主键约束的底层 |

**覆盖面最广 → 所以是默认。** 这句话比任何类型清单都重要：默认不是「最好」，是「最不容易选错」。

### 二、四种类型：组织方式决定它能回答什么

| 类型 | 怎么组织 | 擅长回答 | 典型场景 |
|---|---|---|---|
| **B-tree** | 有序树，键 → 位置 | 等值 / 范围 / 排序 / 前缀 | 90% 的普通索引 |
| **GIN** | 倒排：**值 → 出现位置集合** | **多值包含**（`@>`、`&&`、`@@`） | JSONB、数组、全文检索 |
| **GiST** | 可扩展的平衡树，节点存**包围盒 / 范围摘要** | 几何相交、近邻（`<->`）、范围重叠 | 地理位置、区间、模糊匹配 |
| **BRIN** | 只存**每个数据块的最小/最大值摘要** | 大表按**物理有序**列做范围扫 | 时序表按时间追加写 |
| **Hash** | 哈希表，只存哈希 → 位置 | **只有** `=` | 几乎用不上（B-tree 也能等值，还多给排序） |

**关键在 GIN 那一行**：B-tree 的键是「整行的某个值」，所以 `tags = '{a,b}'` 这种整值比较能用，但 `tags @> '{a}'`（包含 a）用不了——因为 B-tree 不知道 `{a,b}` 里有没有 `a`。**GIN 把每个元素单独建成一个键，所以「包含」变成了「按元素查」**。这就是它适合 JSONB / 数组的根本原因，而不是「GIN 比较高级」。

### 三、回到题目

- `status` 等值 → **B-tree**；如果 `status` 只有少量「活跃值」高频被查，直接用**部分索引**（见 P3）更省。
- `tags` 包含判断 → **GIN**（`GIN (tags)`）。

**给「只有一次机会」的答案**：先建 B-tree 的 `status`（它服务的是最高频、最便宜的那类查询），再评估 tags 查询的频率——如果 tags 查询不是热点，就不该为它付 GIN 的写入代价。**「先建哪个」这个问题本身在考你知不知道 GIN 更贵。**

### 四、代价与边界（不说这段就等于没选型）

| 类型 | 主要代价 |
|---|---|
| B-tree | 写放大、空间；更新频繁时页分裂 |
| **GIN** | **写入代价明显更高**（一次写入要更新多个倒排项），常有 pending list / fastupdate 机制缓冲；体积也更大 |
| GiST | 可能是**有损**的（需要回表复核），构建较慢 |
| BRIN | **只对物理有序有效**——数据一旦乱序（更新、VACUUM FULL 后顺序变化），摘要会退化到「每块范围都覆盖全表」，索引形同虚设 |
| Hash | 不支持范围与排序，不能做唯一约束，崩溃安全性历史上也有问题 |

**所以判据是两句话**：① 查询用的操作符，只有这个类型的 operator class 支持；② 加上它以后，写入路径能不能承受。**只说①不说②，是教科书答案；两句都说，才是做过线上的人。**

## 二、扩展：类似题与追问

**类似题**

1. 「GIN 为什么适合 JSONB 和数组？」——因为 JSONB / 数组是**多值**字段，B-tree 只能比较整体，GIN 的倒排结构把「包含某个元素」变成一次键查找。**答这题必须把「倒排」两个字说出来。**
2. 「时序数据用什么索引？」——**BRIN**（按时间追加写、物理有序），体积比 B-tree 小几个数量级；但一旦乱序就失效，所以要先确认「只追加、不更新」。
3. 「全文检索怎么建索引？」——GIN + `tsvector`（配 `to_tsvector` 表达式索引），这正是「表达式索引 + GIN」的组合。

**追问链**

- 追问一层：**「一个字段能同时建两种索引吗？」**——能，但要想清楚收益：比如 JSONB 既要整体等值又要包含查询，可以 B-tree + GIN 各一个，代价是**写入要维护两棵树**。多数情况下只留 GIN 就够（GIN 也能做等值）。
- 追问二层：**「GIN 写入慢，高写入表怎么办？」**——两条路：① 用 GIN 的 fastupdate / pending list，把多次写合并成一次批量合并（代价是查询要先扫 pending list）；② 换思路——**把需要检索的字段在写入时预处理成一个可 B-tree 的列**（比如把常用标签列出来做普通索引），用写入侧的冗余换掉 GIN 的写入开销。**这条能接住「你怎么做技术选型」的叙事。**
