**题目**：一张表要同时支撑两种查询——按 `status` 等值过滤，和在 `tags` 数组里做「包含」判断。你只有一次建索引的机会，先建哪个？另一类查询怎么办？

**母题**：**为什么 PG 默认是 B-tree？GIN / GiST / BRIN / Hash 各在什么查询形状下才该用——选型的判据到底是什么？**

**为什么重要**：这是 **PG 与 MySQL 最显眼的一处差异**。MySQL 基本上是「B+ 树 + 少量特例」，PG 是**索引类型动物园**——面试官问 PG 索引，考的从来不是记住几个缩写，而是**你会不会按查询形状选型**。答成「都建 B-tree」会立刻暴露没在 PG 上做过真实优化。

## 一、教材

### 1. 前提：索引能回答哪类查询，由它的组织方式决定

::figure pg-index-types.svg | 五种索引：组织方式决定它能回答哪类查询 | 左列五种索引的组织方式，右列对应的操作符与场景；底部是同一张时序表的体积对照

【推导】**这条是整张卡的骨架**：

```text
索引 = 按某种方式重新组织或摘要数据
它能回答哪类查询 ← 完全由【组织方式】决定

所以选型的第一句话是：这个查询用【哪个操作符】？
第二句话才是：加上它，【写入路径能不能承受】？
```

【推论】**"只说①不说②"是教科书答案；"两句都说"才是做过线上的人。**

**到这里你应该能回答**：为什么"PG 用 B-tree 就够了"这句话，在 PG 语境下比在 MySQL 语境下更站不住？

---

### 2. B-tree 为什么是默认【推导】

【事实】**它同时支持这些**（而绝大多数业务查询落在这里面）：

| 能力 | 例子 |
|---|---|
| 等值 | `WHERE status = 'RUNNING'` |
| 范围 | `WHERE created_at >= ? AND created_at < ?` |
| 排序 | `ORDER BY updated_at DESC`（**可直接用索引序，省一次 sort**） |
| 前缀匹配 | `WHERE name LIKE 'abc%'`（**前缀**才行，`%abc` 不行） |
| 唯一性 | `UNIQUE`、主键约束的底层 |

【推论】**"覆盖面最广 → 所以是默认"这句话比任何类型清单都重要**：

> **默认不是「最好」，是「最不容易选错」。**

【推论】**这也解释了 MySQL 的对比**：**MySQL 只有聚簇索引 + 二级索引（都是 B+ 树）**，所以"默认"在那边是唯一选择；**而 PG 给了你五种，选型就成了你的责任**（[[母题-M1-为什么用B+树]]）。

**到这里你应该能回答**：为什么"给了更多选择"同时也意味着"更容易选错"？

### 3. 四种类型：组织方式决定它能回答什么

| 类型 | 怎么组织 | 擅长回答 | 典型场景 |
|---|---|---|---|
| **B-tree** | 有序树，键 → 位置 | 等值 / 范围 / 排序 / 前缀 | 90% 的普通索引 |
| **GIN** | **倒排：值 → 出现位置集合** | **多值包含**（`@>`、`&&`、`@@`） | JSONB、数组、全文检索 |
| **GiST** | 可扩展平衡树，节点存**包围盒 / 范围摘要** | 几何相交、近邻（`<->`）、范围重叠 | 地理位置、区间、模糊匹配 |
| **BRIN** | 只为每个数据块存 **min / max 摘要** | 大表按**物理有序**列做范围扫 | 时序表（只追加） |
| **Hash** | 哈希表，哈希 → 位置 | **只有** `=` | 几乎用不上 |

#### 3.1 GIN 那一行的道理【推导】

【推导】**为什么 B-tree 做不了"包含"**：

```text
B-tree 的键 = 「整行的某个值」
  数组列里，那个值是【整个数组】

  tags = '{a,b}'  → 整体比较，能用 B-tree
  tags @> '{a}'   → 「数组里有没有 a」
                  → B-tree 【不知道】{a,b} 里有没有 a
                  → 只能全扫索引逐个比较数组 → 索引形同虚设

GIN 把【每个元素】单独建成一个键
  → 「包含 a」变成「按元素 a 查一次」
```

【结论】**这就是它适合 JSONB / 数组的根本原因**——**不是"GIN 比较高级"，是"倒排结构天然匹配'包含'这个操作符"。**

【推论】**把它推广成判据**：**问"这个操作符在数据上的语义是什么"，再看"哪种组织方式能直接回答它"。**

#### 3.2 BRIN 省在哪【推导】

```text
1 亿行的时序表，行宽约 100B，页 8KB（每页约 80 行）

B-tree（time 列）：
  每条索引项 = 时间戳 8B + 堆表位置 6B ≈ 16B
  1 亿 × 16B = 1.6 GB

BRIN（默认 pages_per_range = 128）：
  总页数 = 1亿 ÷ 80 = 125 万页
  摘要个数 = 125万 ÷ 128 ≈ 9,766 个
  每个摘要存 min / max 各 8B = 16B
  总体积 ≈ 9,766 × 16B ≈ 156 KB
```

【结论】**1.6 GB vs 156 KB——差约 1 万倍。**

【取舍】**代价是"只对物理有序有效"**：

```text
数据一旦乱序（更新、VACUUM FULL 之后顺序变化）
→ 每个块的 min/max 范围都会变大
→ 最后变成"每块都覆盖全表" → 【索引形同虚设】
```

【推论】**所以 BRIN 的前置条件是"只追加、不更新"**——**这条不确认就不能用**。

**到这里你应该能回答**：为什么"BRIN 比 B-tree 小一万倍"这句话，本身不构成选它的理由？

### 4. 回到题目

```text
status 等值       → B-tree
                    （若只有少量「活跃值」高频被查 → 部分索引更省，见 P3）

tags @> '{a}'     → GIN
```

【推导】**"只有一次机会，先建哪个"这个问题在考什么**：

```text
B-tree 服务的是【最高频、最便宜】的那类查询
GIN 的写入代价【明显更高】

→ 所以答案不是"两个都建"，而是：
  先建 B-tree 的 status（服务高频查询）
  再评估 tags 查询的频率 —— 如果它不是热点，
  【就不该为它付 GIN 的写入代价】
```

【结论】**"先建哪个"这个问题本身在考你知不知道 GIN 更贵。**

#### 4.1 GIN 的写入代价能算出来【推导】

```text
一个 JSONB 字段有 20 个键
  插入一行 → GIN 要更新【20 个倒排项】
  而 B-tree 只需要更新【1 个键】

写入放大 ≈ 20 倍
```

【取舍】**高写入表的两条出路**：

```text
① 用 GIN 的 fastupdate / pending list
   把多次写合并成一次批量合并
   代价：查询时要先扫 pending list

② 换思路：把要检索的字段【在写入时预处理成一个可 B-tree 的列】
   比如把常用标签列出来做普通索引
   → 用写入侧的冗余换掉 GIN 的写入开销
```

【推论】**第 ② 条能接住"你怎么做技术选型"的叙事**——**因为它不是"选一个更好的索引"，是"改数据结构让问题消失"。**

**到这里你应该能回答**：为什么"GIN 写入慢"的解法不一定是"换索引"？

### 5. 代价与边界（不说这段就等于没选型）

| 类型 | 主要代价 |
|---|---|
| B-tree | 写放大、空间；更新频繁时页分裂 |
| **GIN** | **写入代价明显更高**（一次写要更新多个倒排项），常有 pending list / fastupdate 缓冲；**体积也更大** |
| GiST | **可能是有损的**（需要回表复核），构建较慢 |
| BRIN | **只对物理有序有效**——乱序后退化成"每块覆盖全表" |
| Hash | 不支持范围与排序，不能做唯一约束 |

【取舍】**判据是两句话**：

```text
① 查询用的操作符，只有这个类型的 operator class 支持
② 加上它以后，写入路径能不能承受
```

**只说 ① 是教科书答案；两句都说，才是做过线上的人。**

**到这里你应该能回答**：为什么"选型"这个问题，答案里必须包含"代价"？

---

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "都建 B-tree 就行" | **B-tree 做不了"包含"**：它的键是**整个数组**，所以 `tags @> '{a}'` 它不知道 `{a,b}` 里有没有 `a`——**只能全扫索引逐个比较**。**"哪种索引能回答哪种查询"由组织方式决定** |
| "BRIN 体积小所以更好" | **体积小 1 万倍（1.6 GB vs 156 KB）只是它的特点，不是它的优势**。**它有硬前提：只对物理有序有效**——**一旦数据乱序，每个块的 min/max 范围都会变大，最后形同虚设**。**"只追加不更新"这条不确认就不能用** |
| "GIN 比较高级，JSONB 就该用它" | **不是"高级"，是"倒排结构天然匹配包含操作符"**。而且**它有明确的代价：写入放大**（20 个键就是 20 个倒排项，≈20 倍）。**高写入表要么用 fastupdate 缓冲，要么改数据结构** |
| "一个字段建两种索引最保险" | **能建，但要想清收益**：JSONB 同时要整体等值和包含查询时可以 B-tree + GIN，**代价是写入要维护两棵树**。**多数情况下只留 GIN 就够（GIN 也能做等值）** |
| "Hash 索引最快，因为哈希是 O(1)" | **它只能做等值**，不支持范围与排序，**不能做唯一约束**。**而 B-tree 也能等值，还多给排序**——**所以它几乎没有使用场景** |
| "选型看哪个更快" | **错**。**判据是"查询用哪个操作符"**——**只有支持那个操作符的类型才在这个问题里有资格**，然后才在候选里比代价。**先比速度等于跳过了资格判定** |
| "MySQL 也可以这么选" | **MySQL 没有 GIN / GiST / BRIN 这套**，它对应的是"全文索引 / 空间索引"这类特例，**多值包含通常要靠生成列或拆表解决**。**不要把"JSONB 用 GIN"套到 MySQL 上** |

【取舍】读成一句话：**先问"这个查询用的什么操作符"，再问"哪种组织方式能直接回答它"，最后问"写路径能不能承受"——三步都有答案，才叫选型。**

## 二、自测

**Q1（计算）**：一张 **1 亿行**的时序表，行宽约 **100B**，页 8KB。`time` 列上分别建 B-tree 和 BRIN（`pages_per_range` 默认 128）。

问：**两者的体积各是多少？**差多少倍？BRIN 的代价是什么？

**A1**：

```text
每页行数 = 8KB ÷ 100B ≈ 80 行

B-tree：
  每条索引项 = time 8B + 堆表位置 6B ≈ 16B
  1 亿 × 16B = 1.6 GB

BRIN：
  总页数 = 1亿 ÷ 80 = 125 万页
  摘要个数 = 125万 ÷ 128 ≈ 9,766
  每个摘要（min / max 各 8B）= 16B
  总体积 ≈ 9,766 × 16B ≈ 156 KB

倍数 ≈ 1.6GB ÷ 156KB ≈ 1 万倍
```

【结论】**1.6 GB vs 156 KB，差约 1 万倍。**

【代价】**它的硬前提是"物理有序"**：

```text
一旦数据乱序（更新、VACUUM FULL 后顺序变化）
→ 每个块的 min/max 范围变大
→ 最后变成"每块都覆盖全表" → 【索引形同虚设】
```

**所以"只追加、不更新"这条不确认就不能用 BRIN。**

**Q2（计算）**：某表有一个 JSONB 字段，平均包含 **20 个键**。

问：**用 GIN 索引时，插入一行要更新多少个倒排项？**对应的 B-tree 插入呢？这个比值说明什么？

**A2**：

```text
GIN：20 个键 → 更新 20 个倒排项
B-tree：1 个键 → 更新 1 个键

写入放大 ≈ 20 倍
```

【结论】**这就是"高写入表慎用 GIN"的量化依据。**

【两条出路】：

```text
① fastupdate / pending list：把多次写合并成一次批量合并
   —— 代价是查询要先扫 pending list
② 改数据结构：把要检索的字段在写入时预处理成一个可 B-tree 的列
   —— 用写入侧的冗余换掉 GIN 的写入开销
```

【推论】**第 ② 条是更值钱的答案**——**因为它不是"换一个更好的索引"，是"改数据结构让问题消失"。**

**Q3（判读）**：下面两个查询，**分别该用什么索引？为什么？**

```sql
-- 查询 A
SELECT * FROM t WHERE status = 'RUNNING';

-- 查询 B
SELECT * FROM t WHERE tags @> ARRAY['urgent'];
```

**A3**：

```text
A（等值）→ B-tree
  它支持等值；而且如果「RUNNING」这类活跃值只占很小比例，
  用【部分索引】更省（[[母题-P3-部分索引与表达式索引]]）

B（数组包含）→ GIN
  B-tree 的键是【整个数组】，它不知道 {a,b} 里有没有 'urgent'
  → 只能全扫索引逐个比较
  GIN 把每个元素建成一个键 → 「包含」变成「按元素查」
```

【结论】**判据不是"哪个更快"，是"哪个类型的组织方式能直接回答这个操作符"。**

【补充】**如果只能建一个**：**先建 `status` 的 B-tree**——**它服务的是最高频、最便宜的那类查询**；**再评估 `tags` 查询的频率**——**如果它不是热点，就不该为它付 GIN 的写入代价**（Q2 的 20 倍）。**"先建哪个"这个问题本身在考你知不知道 GIN 更贵。**

**Q4（纠错）**：下面这段话哪里不准确？

> "PG 的索引类型里 BRIN 体积最小，所以大表上应该优先用 BRIN。"

**A4**：三处问题。

1. **体积小是它的"特点"，不是"优势"**（Q1：1.6 GB vs 156 KB）。**它的组织方式是"每个数据块只存 min/max 摘要"**——**摘要有效的**前提**是"这一块里的值彼此接近"**。
2. **它只对物理有序有效**：**数据一旦乱序（更新、`VACUUM FULL` 后顺序变化），每个块的 min/max 范围都会变大，最后变成"每块都覆盖全表"——索引形同虚设。**
3. **所以它的前置条件是"只追加、不更新"**——**这条不确认就不能用**。**"体积小所以优先用"跳过了这个前提检查。**

【准确说法】"**BRIN 适合"按物理有序的列做范围扫、且只追加不更新"的表**（时序数据的典型形态）。**要先确认数据的物理顺序稳定，再谈它省了多少空间。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们给 JSONB 字段建了 GIN，索引这块就没问题了。"

**A5**：三处问题。

1. **GIN 的写入代价明显更高**：**一个 20 个键的 JSONB，插入一行要更新 20 个倒排项**（Q2，≈20 倍写放大）。**高写入表上这会成为瓶颈。**
2. **它体积也更大**：**倒排项本身占空间**，而且还有 pending list。
3. **"建了索引"不等于"用上了索引"**：**GIN 支持的是 `@>`、`&&`、`@@` 这类操作符**——**如果你的查询写的是 `->>` 取字段再比较，那用的可能不是 GIN**（是表达式索引的场景）。**最终要看 `EXPLAIN`**（[[母题-P6-执行计划怎么看]]）。

【准确说法】"**GIN 的判据是"查询用了多值包含类操作符"**；**加上它之后要评估写入路径**（fastupdate 缓冲，或把检索字段预处理成普通列）。**而且要用 EXPLAIN 确认它真的被用上了。**"

## 三、面试输出（学完再看）

**一句话结论**：**索引能回答哪类查询，由它的组织方式决定**——**B-tree 是有序树，覆盖面最广（等值 / 范围 / 排序 / 前缀 / 唯一），所以是默认**；**但"默认"不是"最好"，是"最不容易选错"**。其余四种各自绑定一种形状：**GIN 是倒排（值 → 出现位置集合），所以"包含"变成"按元素查"，适合 JSONB / 数组 / 全文**；**GiST 节点存包围盒，适合几何近邻与范围重叠（可能是有损的）**；**BRIN 每块只存 min/max，1 亿行时体积 156 KB vs B-tree 的 1.6 GB（差 1 万倍），但只对物理有序有效**；**Hash 只支持等值，几乎没有场景**。**选型判据是两句话**：**① 这个查询用哪个操作符（只有支持它的类型才有资格）② 加上之后写入路径能不能承受**——**只说①是教科书答案，两句都说才是做过线上的人**。题目里的答案：**`status` 用 B-tree，`tags @>` 用 GIN**；**如果只能建一个，先建 B-tree**——因为 **GIN 的写入代价明显更高（20 个键就是 20 倍写放大），不该为一个非热点查询付这个代价**。

**恢复关键词**：**组织方式决定能回答什么** / B-tree = 默认（覆盖面最广，不是最好）/ 等值 · 范围 · 排序 · 前缀（**只有 `abc%`，`%abc` 不行**）/ **GIN = 倒排**（把包含变成按元素查）/ **BRIN = 每块 min/max**（1.6GB vs 156KB，差 1 万倍，**只对物理有序有效**）/ GiST = 包围盒（**可能有损**）/ Hash 只等值 / **判据两句：操作符 + 写入代价** / GIN 写入放大 20 倍 → fastupdate 或改数据结构 / 选型最终由 EXPLAIN 说话

**核心不变量 / 主线**：
**索引是"按某种方式重新组织或摘要数据"的结构，它能回答哪类查询由组织方式决定。**
所以选型的第一步不是比较性能，是**判断资格**——**"这个操作符，只有哪些组织方式能直接回答"。**

**完整回答骨架**：先立判据（组织方式决定能力）→ B-tree 为什么是默认（覆盖面，且"默认≠最好"）→ 四种类型的组织方式与操作符 → **GIN 为什么能做包含（倒排）** → 回到题目做选择 → **代价与边界**（尤其 BRIN 的物理有序前提、GIN 的写放大）→ 收束到"两句话判据"

**完整回答（口述稿）**：
**索引能回答哪类查询，由它的组织方式决定**。**B-tree 是有序树**，能覆盖等值、范围、排序、前缀、唯一，覆盖面最广，**所以是默认**——但"默认"不是"最好"，是"最不容易选错"。

其余四种各自绑定一种形状：**GIN 是倒排**（值 → 出现位置集合），所以"包含"变成"按元素查"，适合 JSONB / 数组 / 全文；**GiST 节点存包围盒**，适合几何近邻与范围重叠（**可能是有损的**）；**BRIN 每块只存 min/max**——1 亿行时体积 **156 KB vs B-tree 的 1.6 GB（差 1 万倍）**，但**只对物理有序有效**；**Hash 只支持等值**，几乎没有场景。

选型判据两句话：**① 这个查询是哪种形状**（等值/范围/包含/近邻）；**② 这份索引的代价值不值**（写放大、空间、VACUUM 负担）。PG 里第三项尤其重要——索引多了会同步抬高 VACUUM 负担，这是 PG 在索引数量上比 MySQL 更保守的原因。

**分层要点**：
- **结论**：B-tree 是默认不是最优；另四种各绑一种查询形状。
- **推导链**：组织方式 → 能回答的查询形状 → GIN 倒排 / GiST 包围盒 / BRIN min-max / Hash 等值 → 判据是查询形状 + 代价。
- **量化**：BRIN 1 亿行 156 KB vs B-tree 1.6 GB（差 1 万倍）。
- **边界与常见误解**：GiST 可能是有损的（需再检查）；BRIN 只对物理有序有效；Hash 索引几乎没有场景。

**追问**（先说后看）

1. **GIN 为什么适合 JSONB 和数组？** —— **因为它们是"多值"字段**：**B-tree 只能比较整体，而 GIN 的倒排结构把"包含某个元素"变成一次键查找。** **答这题必须把"倒排"两个字说出来。**
2. **时序数据用什么索引？** —— **BRIN**（按时间追加写、物理有序），**体积比 B-tree 小几个数量级**；**但一旦乱序就失效，所以要先确认"只追加、不更新"。**
3. **全文检索怎么建索引？** —— **GIN + `tsvector`**（配 `to_tsvector` 表达式索引）——**这正是"表达式索引 + GIN"的组合**（[[母题-P3-部分索引与表达式索引]]）。
4. **一个字段能同时建两种索引吗？** —— **能，但要想清收益**：JSONB 既要整体等值又要包含查询时可以 B-tree + GIN，**代价是写入要维护两棵树**。**多数情况下只留 GIN 就够（GIN 也能做等值）。**
5. **GIN 写入慢，高写入表怎么办？** —— **① fastupdate / pending list**（把多次写合并成一次批量合并，**代价是查询要先扫 pending list**）② **换思路：把需要检索的字段在写入时预处理成一个可 B-tree 的列**——**用写入侧的冗余换掉 GIN 的写入开销。**

**同类变体**

- 「PG 和 MySQL 在索引上的最大差异是什么？」——**MySQL 基本上是「B+ 树 + 少量特例」；PG 是「五种索引类型 + operator class 体系」**。**对应地：PG 里"选型"是必答题，MySQL 里"选型"通常只是"建哪个列的组合索引"**（[[母题-M2-联合索引与最左前缀]]）。
- 「operator class 是什么？」——**它定义了"某种数据类型 + 某个索引类型"支持哪些操作符以及怎么比较**。**这就是为什么"能不能用某个索引"是"操作符 + 类型 + operator class"三者共同决定的**——**换一个 operator class，同一个 GIN 索引支持的操作符就变了。**
