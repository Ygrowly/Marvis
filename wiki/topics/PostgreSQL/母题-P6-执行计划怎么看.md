# 母题 P6 · 执行计划怎么看

> **模块**：PostgreSQL / SQL 执行与优化
> **所属主线**：二 · SQL 执行与优化（一条 SQL 怎么走、慢在哪）
> **关联母题**：[[母题-P7-统计信息与慢查询定位]] · [[母题-P2-堆表与回表]]
> **素材来源**：`study/09-数据缓存队列与一致性` 第 3.4 节（看 EXPLAIN 的主线清单）+ EnergyOps 真实优化过程

**题目**：同一条 SQL，开发环境 50ms，线上 8s。你怎么用执行计划找出差别在哪，而不是靠猜？

**母题**：EXPLAIN 和 EXPLAIN ANALYZE 的区别是什么？看计划应该按什么顺序看？

**为什么重要**：这是**索引设计能不能闭环的那一步**。P1–P5 都在讲「怎么建索引」，而**索引有没有被用上、用得对不对，只有执行计划能回答**。更要紧的是：我上一版把「只看有没有 Index Scan 就宣布优化成功」当成反面案例写进了 P4——**这道题就是那个反面的正面解法。**

**一句话结论**：`EXPLAIN` 只给**估算**（估计行数、估算代价），`EXPLAIN ANALYZE` 会**真的执行**并给出**实际行数、实际耗时、循环次数、排序/哈希有没有落盘**；看计划有固定顺序——**先看「估计 vs 实际行数」的偏差，再看扫描方式是否合理，再看 JOIN 算法与两侧规模，再看 Sort/Hash 有没有落盘，最后看 loops 有没有暴露 N+1**。

**恢复关键词**：估算 vs 实测 / rows vs actual rows / loops / Buffers / Sort Method external merge / Bitmap Heap Scan / Nested Loop 与 Hash Join / BUFFERS 选项

**核心不变量 / 主线**：
**计划里的错误几乎总是先出现在「估计行数」上。** 所以看计划的第一动作永远是比对估计与实际——**偏差大的那个节点，就是问题所在节点**，不需要通读整棵树。

**完整回答骨架**：两种 EXPLAIN 的差别（估算 vs 实测）→ 看计划的五步顺序 → 每个节点该问什么 → 一个真实例子（20 多秒那条）→ 注意事项（ANALYZE 会真跑）

## 原理分解

### 一、EXPLAIN vs EXPLAIN ANALYZE

| | `EXPLAIN` | `EXPLAIN ANALYZE` |
|---|---|---|
| 是否执行 | **不执行**，只规划 | **真的执行** |
| 给什么 | 估算行数、估算代价、算法选择 | **实际行数、实际耗时、循环次数、内存/磁盘使用** |
| 风险 | 无 | **会真的写数据**（写语句要放事务里回滚） |
| 常用组合 | `EXPLAIN` | `EXPLAIN (ANALYZE, BUFFERS)` |

**`BUFFERS` 是必须加的**：它告诉你这次访问命中了多少缓存页、读了多少磁盘页——**没有它，你分不清「慢」是算法差还是缓存冷**。

**写语句的注意**：`EXPLAIN ANALYZE UPDATE ...` 会真的更新。惯例是

```sql
BEGIN;
EXPLAIN (ANALYZE, BUFFERS) UPDATE ...;
ROLLBACK;
```

### 二、看计划的五步顺序

**第一看：估计行数 vs 实际行数（最重要）**

```
rows=1000  ...  (actual time=... rows=12 loops=1)
```

**差一个数量级以上就说明统计信息或相关性有问题**（→ P7）。这一步定了，后面的判断才有意义——因为**选择哪种扫描/连接算法，本身就是优化器根据估算行数算出来的**。

**第二看：扫描方式是否合理**

| 节点 | 什么时候该出现 |
|---|---|
| `Seq Scan` | 命中比例高（比如要取 20% 以上的行）或表很小——**这是正常的，不要一看到 Seq Scan 就想优化** |
| `Index Scan` | 命中行数少、走索引比全表便宜 |
| `Bitmap Heap Scan` | 命中**中等**行数：先用索引把符合条件的页收集成位图、按物理顺序批量读堆——**它出现说明优化器判断「随机回表太贵、全表扫又太浪费」，这是很有价值的信号** |
| `Index Only Scan` | 见 P2——**必须同时看 `Heap Fetches` 是不是 0** |
| `Subquery Scan` / 子查询被优化掉 | 说明优化器改了形状，要确认改对了 |

**第三看：JOIN 算法与两侧规模**

- `Nested Loop`：外层小、内层走索引——**如果外层实际行数远大于估算，它就从「几万次循环」变成「几百万次循环」**，这是最常见的爆炸点；
- `Hash Join`：两侧都不小、需要等值连接；**看哈希表有没有落盘**；
- `Merge Join`：两侧都有序。

**第四看：Sort / Hash 有没有落盘**

```
Sort Method: external merge  Disk: 24576kB
```

**看到 `external merge` 就意味着排序溢到磁盘了**——通常说明 `work_mem` 太小，或者排序的数据量本来就该在上游减掉。

**第五看：loops 有没有暴露 N+1**

`loops=10000` 配一个内层节点，就是 N+1 的执行计划形态（对应 EnergyOps 里的 N+1 问题）。

### 三、回到那个真实例子

EnergyOps「优化前 20 多秒」那条查询链路，按这五步看会得到什么：

1. **估计 vs 实际**：JOIN 之后中间结果远大于估计 → 优化器选错了后续算法；
2. **扫描方式**：先展开全部归属再过滤园区 → 大表 `Seq Scan` + 位图回表；
3. **JOIN 规模**：归属关系一对多未限有效期 → 中间行被放大；
4. **排序/哈希**：聚合排序落盘；
5. **loops**：应用侧还有 N+1（1+100 次往返）。

**这五条恰好对应「先修范围与 JOIN、再建索引、再消 N+1」的优化顺序**——**计划不是用来「看一眼」的，是用来给优化动作排优先级的。**

## 二、扩展：类似题与追问

**类似题**

1. 「Seq Scan 一定比 Index Scan 慢吗？」——**不一定**。命中比例高时顺序读整表比「索引 + 大量随机回表」更快。**能说出「Seq Scan 也是一种正确选择」，就脱离了「索引崇拜」。**
2. 「怎么对比两个计划的优劣？」——看**实际耗时**与 **Buffers**，而不是「估算代价」；估算代价只能用于同结构比较。**要 `ANALYZE` 真跑、固定参数、跑多次取稳定值。**
3. 「`Bitmap Heap Scan` 后面接 `Sort` 说明什么？」——说明索引没有提供所需顺序（它按物理顺序读堆），所以还得排一次。**要排序就应该考虑让索引顺序直接匹配 `ORDER BY`。**

**追问链**

- 追问一层：**「为什么估计会差那么多？」**——三类原因：统计信息过期、**列之间有关联但统计是独立的**（比如「城市=北京」和「区=海淀」相乘会把行数估得极小）、条件是表达式/函数导致无法估算。对应三种修法见 P7。**答这题要说「优化器不是猜的，它是按你给的统计算的」。**
- 追问二层：**「`EXPLAIN ANALYZE` 会不会本身改变行为？」**——会。① 它真的执行，所以有副作用风险；② **`ANALYZE` 会强制用真实参数生成计划，而真实运行可能用的是预编译的通用计划**（见 P7 的 generic plan 陷阱）——**所以「EXPLAIN ANALYZE 里很快、线上很慢」是可能发生的**。这条能把两个母题串起来。
