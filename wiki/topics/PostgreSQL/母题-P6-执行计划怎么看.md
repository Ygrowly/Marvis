# 母题 P6 · 执行计划怎么看

> **模块**：PostgreSQL / SQL 执行与优化
> **所属主线**：二 · SQL 执行与优化（一条 SQL 怎么走、慢在哪）
> **层级**：A · 教材级（五步顺序由「估算行数决定算法选择」这一条推出来，loops 与 Buffers 都能算；不需要先背结论）
> **关联母题**：[[母题-P7-统计信息与慢查询定位]]（估计为什么错）· [[母题-P2-堆表与回表]]（Heap Fetches）· [[母题-P4-索引代价与在线建索引]]（建完索引必须用计划验证）
> **素材来源**：`archive/study-courses/09-数据缓存队列与一致性` 第 3.4 节（看 EXPLAIN 的主线清单）+ EnergyOps 真实优化过程 + **PostgreSQL 官方文档 EXPLAIN / Using EXPLAIN**（2026-09-13 联网核实）。**三组算式与 loops 那一段为本次新增（待你核对）**

**导读**：必懂 3 件事（① **`actual rows` 是「每个循环」的值，不是总数**——不知道这条就会把最贵的节点看成最便宜的 ② 看计划的第一动作永远是**比对估算与实际行数**，因为**算法选择本身就是优化器按估算算出来的** ③ `Buffers` 不加，你分不清「慢」是算法差还是缓存冷）· 读完约 12 分钟 · 需要先懂：[[母题-P2-堆表与回表]]

**题目**：同一条 SQL，开发环境 50ms，线上 8s。你怎么用执行计划找出差别在哪，而不是靠猜？

**母题**：EXPLAIN 和 EXPLAIN ANALYZE 的区别是什么？看计划应该按什么顺序看？

**为什么重要**：这是**索引设计能不能闭环的那一步**。P1–P5 都在讲「怎么建索引」，而**索引有没有被用上、用得对不对，只有执行计划能回答**。更要紧的是：**「只看有没有 Index Scan 就宣布优化成功」是最常见的错误动作——这道题就是那个错误的正面解法。**

**一句话结论**：`EXPLAIN` 只给**估算**（估计行数、估算代价），`EXPLAIN ANALYZE` 会**真的执行**并给出**实际行数、实际耗时、循环次数、排序/哈希有没有落盘**；看计划有固定顺序——**先看「估计 vs 实际行数」的偏差，再看扫描方式是否合理，再看 JOIN 算法与两侧规模，再看 Sort/Hash 有没有落盘，最后看 loops 有没有暴露 N+1**。

**恢复关键词**：估算 vs 实测 / **rows vs actual rows（每循环，要乘 loops）** / Buffers / Sort Method external merge / Bitmap Heap Scan / Nested Loop 与 Hash Join / BUFFERS 选项 / 代价是任意单位

**核心不变量 / 主线**：
**计划里的错误几乎总是先出现在「估计行数」上。** 所以看计划的第一动作永远是比对估计与实际——**偏差大的那个节点，就是问题所在节点**，不需要通读整棵树。
**而 `actual rows` 是【每个循环】的值**——**乘以 `loops` 才是它真正处理了多少行。** 漏掉这一条，你会把最贵的节点当成最便宜的。

**完整回答骨架**：两种 EXPLAIN 的差别（估算 vs 实测）→ **loops 的语义（最容易看错的一条）** → 看计划的五步顺序 → 每个节点该问什么 → 一个真实例子（20 多秒那条）→ 注意事项（ANALYZE 会真跑、代价是任意单位）

**完整回答（口述稿）**：
`EXPLAIN` 只给**估算**（估计行数、估算代价），`EXPLAIN (ANALYZE, BUFFERS)` 会**真的执行**并给出**实际行数、实际耗时、循环次数、排序/哈希有没有落盘**。

看计划有固定顺序：**① 先看"估计 vs 实际行数"的偏差**（偏差本身就是信号）；**② 再看扫描方式是否合理**（该走索引吗、走的是哪个）；**③ 再看 JOIN 算法与两侧规模**（Nested/Hash/Merge 各自的前提）；**④ 再看 Sort/Hash 有没有落盘**（落盘说明 work_mem 不够或集合太大）；**⑤ 最后看 loops 有没有暴露 N+1**（loops 很大但单次很快，往往是重复执行）。

和 MySQL 对照：MySQL 的 `rows` 是估算、要看实际值用 `EXPLAIN ANALYZE`（8.0.18+）；PG 这边 `EXPLAIN ANALYZE` 是常规工具，而且**会真的执行**——所以 `EXPLAIN ANALYZE` 一条 UPDATE/DELETE 会真的改动数据，生产上要小心（可用事务包起来再 ROLLBACK）。

**分层要点**：
- **结论**：EXPLAIN 是估算、ANALYZE 是实测；按五步顺序看，不跳步。
- **推导链**：估算 vs 实际 → 偏差暴露统计问题 → 扫描方式 → JOIN 算法 → 落盘 → loops 暴露 N+1。
- **量化**：无硬数字，看的是偏差倍数与 loops 次数。
- **边界与常见误解**：`EXPLAIN ANALYZE` 会真的执行（写操作要包事务再回滚）；BUFFERS 看的是缓存命中与 IO 量。

## 一、教材

### 1. EXPLAIN vs EXPLAIN ANALYZE

| | `EXPLAIN` | `EXPLAIN ANALYZE` |
|---|---|---|
| 是否执行 | **不执行**，只规划 | **真的执行** |
| 给什么 | 估算行数、估算代价、算法选择 | **实际行数、实际耗时、循环次数、内存/磁盘使用** |
| 风险 | 无 | **会真的写数据**（写语句要放事务里回滚） |
| 常用组合 | `EXPLAIN` | `EXPLAIN (ANALYZE, BUFFERS)` |

【事实】**官方对代价的定性值得背**：

> **cost 的数字是「任意单位」**（习惯上代表磁盘页抓取次数），所以它**和实际的毫秒数不会对得上**。
> **通常最该看的是：估算的行数是否接近现实。**

【推论】**这一句就否掉了「看 cost 谁小谁快」的用法**——**cost 只能用来比较「同一条 SQL 的两个计划」，不能用来估计真实耗时，更不能跨 SQL 比。**

【事实】**`BUFFERS` 是必须加的**：它给出**命中的共享块、读的共享块、脏块、写的块**，以及**临时块（排序/哈希/Materialize 用的）**的读写——**没有它，你分不清「慢」是算法差还是缓存冷。**

【事实】**写语句的注意**：官方明确警告，`ANALYZE` 会**真的执行**，**其他副作用照常发生**。惯例是：

```sql
BEGIN;
EXPLAIN (ANALYZE, BUFFERS) UPDATE ...;
ROLLBACK;
```

**到这里你应该能回答**：为什么「看一眼 cost 挑个小数字就完事」是不成立的？

---

### 2. loops：最容易看错的一条【事实】

【事实】**官方原文**：

> **`loops` 的值报告的是这个节点被执行的总次数，而显示出来的 actual time 和 rows 值都是【每次执行的平均值】。** 这样做是为了让它们和代价估算的呈现方式可比。
> **把 `loops` 乘上去，才能得到这个节点实际花掉的总时间。**

【推导】**这一条会直接改变你对「谁最贵」的判断**：

```text
一条节点写着：
  (actual time=0.05..0.12 rows=12 loops=10000)

看错的读法：
  "rows=12，很小；time=0.12ms，很快" → 以为是廉价节点

正确的读法：
  总行数 = 12 × 10000 = 【12 万行】
  总耗时 = 0.12 × 10000 = 【1200 ms = 1.2 秒】
  → 这是整条查询最贵的节点
```

【结论】**同一个节点，两种读法给出的结论完全相反。** **而上层节点的 `actual time` 里已经包含了子节点的累计时间**——所以**要从最贵的叶子往上看，不是从根往下看。**

【事实】**两种「看着像 bug 其实不是」的情况**，官方专门写了：

- **`BitmapAnd` / `BitmapOr` 节点的实际行数永远显示为 0**（实现限制）——**看到 0 不要以为它没干活**；
- **当外层有很多重复值时，内层子节点的实际行数可能显著大于内层关系本身的行数**——那是**同一个内层行被反复取**的结果，**不是统计错误**。

**到这里你应该能回答**：为什么「我说这个节点只返回 12 行，怎么会慢」这句话是站不住的？

### 3. 看计划的五步顺序

::figure pg-explain-reading.svg | 看执行计划的五步顺序与 loops 陷阱 | 估算与实际行数的比对、loops 乘算、五种扫描节点的判据、Sort/Hash 落盘信号

**第一看：估计行数 vs 实际行数（最重要）**

```
rows=1000  ...  (actual time=... rows=12 loops=1)
```

**差一个数量级以上就说明统计信息或相关性有问题**（→ [[母题-P7-统计信息与慢查询定位]]）。这一步定了，后面的判断才有意义——因为**选择哪种扫描/连接算法，本身就是优化器根据估算行数算出来的**。

【推导】**估错方向决定选错算法——这是「为什么第一步必须是这一步」的证明**：

```text
优化器估算外层只有 10 行：
  → 它认为 Nested Loop 只要 10 次内层索引查找
  → 每次 3 页 → 30 页 → 判定 Nested Loop 最便宜 → 选择它

实际外层有 50,000 行：
  → Nested Loop 实际做 50,000 次内层索引查找
  → 50,000 × 3 页 = 【150,000 页】
  → 比估算多了 【5000 倍】

如果估算是对的（50,000 行），优化器会改选 Hash Join：
  → 全表扫一遍 + 建一次哈希表，行数再涨也不会翻 5000 倍
```

【推论】**所以「估错」不是精度问题，是【算法选错】问题。** **报错的现象是慢，根因在统计信息。**

【事实】**一个容易忘的边界**（官方原话）：

> **代价估算不是线性的，所以对更大或更小的表，优化器可能选出不同的计划。** 一个极端的例子是：**一张只占一个磁盘页的表，几乎总是会走顺序扫描，不管有没有索引。**

**第二看：扫描方式是否合理**

| 节点 | 什么时候该出现 |
|---|---|
| `Seq Scan` | 命中比例高（比如要取 20% 以上的行）或表很小——**这是正常的，不要一看到 Seq Scan 就想优化** |
| `Index Scan` | 命中行数少、走索引比全表便宜 |
| `Bitmap Heap Scan` | 命中**中等**行数：先用索引把符合条件的页收集成位图、按物理顺序批量读堆——**它出现说明优化器判断「随机回表太贵、全表扫又太浪费」，这是很有价值的信号** |
| `Index Only Scan` | 见 [[母题-P2-堆表与回表]]——**必须同时看 `Heap Fetches` 是不是 0** |
| `Subquery Scan` / 子查询被优化掉 | 说明优化器改了形状，要确认改对了 |

**第三看：JOIN 算法与两侧规模**

- `Nested Loop`：外层小、内层走索引——**如果外层实际行数远大于估算，它就从「几万次循环」变成「几百万次循环」**，这是最常见的爆炸点；
- `Hash Join`：两侧都不小、需要等值连接；**看哈希表有没有落盘**（`Batches > 1` 就是落盘了）；
- `Merge Join`：两侧都有序。

**第四看：Sort / Hash 有没有落盘**

```
Sort Method: external merge  Disk: 24576kB
```

**看到 `external merge` 就意味着排序溢到磁盘了**——通常说明 `work_mem` 太小，或者排序的数据量本来就该在上游减掉。

**第五看：loops 有没有暴露 N+1**

`loops=10000` 配一个内层节点，就是 **N+1 的执行计划形态**（对应 EnergyOps 里的 N+1 问题）。**注意这时要按第 2 节的方法乘算，才能看出它真正的代价。**

---

### 4. 回到那个真实例子

EnergyOps「优化前 20 多秒」那条查询链路，按这五步看会得到什么：

1. **估计 vs 实际**：JOIN 之后中间结果远大于估计 → 优化器选错了后续算法；
2. **扫描方式**：先展开全部归属再过滤园区 → 大表 `Seq Scan` + 位图回表；
3. **JOIN 规模**：归属关系一对多未限有效期 → 中间行被放大；
4. **排序/哈希**：聚合排序落盘；
5. **loops**：应用侧还有 N+1（1+100 次往返）。

**这五条恰好对应「先修范围与 JOIN、再建索引、再消 N+1」的优化顺序**——**计划不是用来「看一眼」的，是用来给优化动作排优先级的。**

---

### 5. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「cost 小的计划更快」 | **cost 是任意单位，和毫秒对不上**；它只能用来比较同一条 SQL 的两个计划 |
| 「rows=12 说明这个节点很轻」 | **那是每个循环的行数**——**`loops=10000` 时它处理了 12 万行** |
| 「BitmapAnd 行数是 0，说明没干活」 | **实现限制，它永远报 0** |
| 「`EXPLAIN ANALYZE` 的结果就是线上会发生的」 | **不一定**：它真的执行，**而且强制用真实参数生成计划**，线上可能走预编译的通用计划（见追问 2） |
| 「内层节点行数比表还大，是统计错了」 | **是外层重复值多、同一个内层行被反复取**，不是错误 |
| 「Estimates 差一点点没关系」 | **差一个数量级就要停下来查统计信息**——因为算法选择是按估算做的 |

## 二、自测

**Q1（计算）**：一个计划节点写着：

```text
->  Index Scan using idx_x on t  (cost=0.43..12.60 rows=12 width=40)
                                 (actual time=0.048..0.121 rows=12 loops=10000)
```

问：**这个节点一共处理了多少行、花了多少时间？**如果只看 `rows=12`、`time=0.121ms` 会得出什么错误结论？

**A1**：

```text
官方口径：actual time 和 rows 都是【每次执行的平均值】
  → 总行数 = 12 × 10000 = 【120,000 行】
  → 总耗时 = 0.121 ms × 10000 = 【1210 ms ≈ 1.21 秒】

错误读法：
  "返回 12 行、耗时 0.12 毫秒" → 判定为廉价节点、跳过
```

【结论】**同一个节点，两种读法的结论完全相反。** ——**这是执行计划里最容易看错的一条，没有之一。**

【推论】**判据**：

> **看到任何一个 `loops > 1` 的节点，第一动作是乘算，而不是读它显示的数字。**

【补充】**上层节点的 `actual time` 已经包含了子节点的累计时间**——**所以定位瓶颈要「从最贵的叶子往上看」，不是从根节点往下读。** **根节点的 total time 是你已经知道的「8 秒」，它不提供任何新信息。**

**Q2（计算）**：优化器把某条查询的中间结果估算成 **10 行**，于是选了 `Nested Loop`。实际这个中间结果是 **50,000 行**，内层每次索引查找要读 3 页。

问：**实际比估算多做了多少倍的页读取？为什么「换统计信息」而不是「换索引」才是这个问题的解法？**

**A2**：

```text
优化器以为要做的事：
  10 次内层索引查找 × 3 页 = 【30 页】

实际做的事：
  50,000 次内层索引查找 × 3 页 = 【150,000 页】

倍率：150,000 ÷ 30 = 【5000 倍】
```

【结论】**估算错 5000 倍，代价就错 5000 倍**——**这不是精度问题，是量级问题。**

【推论】**为什么解法是统计信息而不是索引**：

```text
如果估算【是准的】（50,000 行）：
  优化器会自己改选 Hash Join
  → 全表扫一遍 + 建一次哈希表
  → 行数再涨，代价也只是线性涨

所以：
  索引没问题、SQL 写得也没问题——
  问题在【优化器拿到的那份数据分布描述是错的】
```

【推论】**判据**：

> **计划里的错误几乎总是先出现在「估计行数」上。** **先修估算，再谈别的**——**否则你会在一个「本该被优化器自己避开」的计划上做无效优化。**

**Q3（计算）**：一个 `Sort` 节点写着：

```text
Sort Method: external merge  Disk: 24576kB
```

`work_mem` 是 4MB。这条查询每分钟执行 60 次。

问：**这一处每分钟多产生多少磁盘 IO？为什么说「调大 work_mem」和「在上游少排点行」是两个不同的解法？**

**A3**：

```text
落盘 24 MB = 排序数据量已经超过 work_mem(4MB) 的 6 倍

IO 量（排序溢写的账要算两遍：先写临时文件，再读回来）：
  单次 ≈ 24 MB 写 + 24 MB 读 = 48 MB
  每分钟 60 次 → 48 × 60 = 【2.88 GB / 分钟】
```

【结论】**一个 `Sort` 落盘，能变成每分钟 2.88 GB 的临时文件 IO**——**而且这些 IO 不体现在表的 Buffers 上，很容易被忽略。** **`Buffers` 里的 `temp read` / `temp written` 就是专门为它准备的字段。**

【推论】**为什么两个解法不同**：

```text
解法一（调大 work_mem）：
  让这一次排序在内存里完成
  → 代价：work_mem 是【每个排序节点】的上限，并发一高就乘上去
  → 10 个并发 × 32MB = 320MB —— 这是【内存换取】

解法二（在上游少排点行）：
  过滤/聚合/取列更早地砍掉行数
  → 代价：要改 SQL 或数据模型
  → 收益：排序量、网络量、后续所有节点【一起变小】——这是【少做无用功】
```

【取舍】**先问「这些行本来就该被排吗」**——**如果答案是不该，那调 work_mem 只是在给一个错误的计划买单。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我用 `EXPLAIN ANALYZE` 看了，走的是 `Index Scan`，没有 `Seq Scan`，所以这条 SQL 已经优化到位了。"

**A4**：三处问题。

1. **「走了索引」不等于「走得对」**：**索引扫描可以是 10 次，也可以是 10 万次**（Q1）。**要问的是「它被调用了多少次、每次拿多少行」，不是「它叫不叫 Index Scan」。**
2. **`Seq Scan` 本身不是罪**：**命中比例高时（20% 以上）或表很小时，顺序扫描比「索引 + 大量随机回表」更快**。**官方明确说：只占一个磁盘页的表几乎总是走顺序扫描，不管有没有索引。**
3. **漏掉了真正的信号**：**估算 vs 实际的偏差**（Q2）、**Buffers**（Q3）、**Sort/Hash 有没有落盘**——**这三样才是"优化到位没有"的证据。** **只看节点名字，等于只看病人的体温而不看化验单。**

【准确说法】"**判断优化到没到位，要看三件事：估算和实际行数是否接近、`Buffers` 里读了多少页、排序和哈希有没有落盘。** **节点名字只是线索，不是结论。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "我在事务里跑了 `BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;`，看到 `actual time` 是 3ms，很快。所以我们线上这条 UPDATE 没问题。"

**A5**：三处问题。

1. **`ROLLBACK` 之后，这次执行和线上不是同一个环境**：**没有真实的并发、没有锁等待、没有 WAL 落盘压力**。**3ms 是"空跑"的 3ms。**
2. **`EXPLAIN ANALYZE` 会强制用真实参数生成计划**：**而线上走的是预编译语句的通用计划**（[[母题-P7-统计信息与慢查询定位]]）——**「分析时很快、线上很慢」是可能并且常见的**。
3. **`UPDATE` 的用户时间不等于总时间**：**它只是"干活"的时间，不含等锁、等 IO、等 WAL 同步**。**官方也提醒：数据修改节点的耗时大头往往不在计划自身的统计里。**

【准确说法】"**`EXPLAIN ANALYZE` 能回答的是「这个计划形状合不合理」，回答不了「线上会不会等锁」。** **要回答后者，要看线上真实的等待事件与慢查询日志，而不是在空跑的窗口里测。**"

## 三、面试输出（学完再看）

**一句话结论**：`EXPLAIN` 只给**估算**，`EXPLAIN ANALYZE` 会**真的执行**并给出**实际行数、实际耗时、循环次数、内存与磁盘使用**。**看计划的第一动作永远是比对「估算 vs 实际行数」**——因为**扫描方式和连接算法本身就是优化器按估算算出来的**，**估算错 5000 倍，代价就错 5000 倍**（10 次内层查找 → 50,000 次，30 页 → 150,000 页），**所以报错的现象是慢，根因在统计信息。** **最容易被看错的一条是 `loops`**：**`actual rows` 和 `actual time` 都是【每个循环】的平均值**——`rows=12 loops=10000` 意味着**12 万行、1.2 秒**，**漏掉乘算会把最贵的节点当成最便宜的**。**第二步看扫描方式**（`Seq Scan` 不是罪，命中比例高时它才是对的；**`Bitmap Heap Scan` 说明优化器在"随机回表太贵"和"全表扫太浪费"之间选了中间路**），**第三步看 JOIN 算法与两侧规模**（`Nested Loop` 在外层估错时是最常见的爆炸点），**第四步看 Sort/Hash 有没有落盘**（`external merge` 说明溢到磁盘了——**一处 24MB 落盘，每分钟 60 次就是 2.88 GB 的临时 IO**），**第五步看 loops 有没有暴露 N+1**。**而且 `cost` 是任意单位、和毫秒对不上**，只能用来比较同一条 SQL 的两个计划——**「看 cost 谁小谁快」是不成立的。**

**恢复关键词**：估算 vs 实测 / **actual rows 是每循环的（要乘 loops）** / 12 × 10000 = 12 万行 / **从最贵的叶子往上看** / **估算错 → 算法选错**（30 页 → 150,000 页）/ `BUFFERS`（shared hit/read · temp）/ `Seq Scan` 不是罪 / `Bitmap Heap Scan` = 中等命中 / `Heap Fetches` 必须为 0 / `Sort Method: external merge` / `loops=10000` = N+1 形态 / **BitmapAnd 行数永远报 0** / cost 是任意单位

**核心不变量 / 主线**：
**计划里的错误几乎总是先出现在「估计行数」上。**
**而 `actual rows` 是【每个循环】的值**——**乘以 `loops` 才是它真正处理了多少行。**

**完整回答骨架**：两种 EXPLAIN 的差别 → **loops 语义（算 12 万行 / 1.2 秒）** → **五步顺序，第一步是估算 vs 实际（算 5000 倍）** → 扫描方式判据 → JOIN 算法与规模 → Sort/Hash 落盘（算 2.88 GB/分钟）→ loops 与 N+1 → 收束到「计划是用来给优化动作排优先级的」

**追问**（先说后看）

1. **为什么估计会差那么多？** —— 三类原因：**统计信息过期**、**列之间有关联但统计是独立的**（「城市=北京」和「区=海淀」相乘会把行数估得极小）、**条件是表达式或函数导致无法估算**。对应三种修法见 [[母题-P7-统计信息与慢查询定位]]。**答这题要说「优化器不是猜的，它是按你给的统计算的」。**
2. **`EXPLAIN ANALYZE` 会不会本身改变行为？** —— **会。** ① 它真的执行，**所以有副作用风险**；② **`ANALYZE` 会强制用真实参数生成计划，而真实运行可能用的是预编译的通用计划**——**所以「EXPLAIN ANALYZE 里很快、线上很慢」是可能发生的**。这条能把两个母题串起来。**③ 官方还提醒：`ANALYZE` 用随机采样估统计，重跑一次 `ANALYZE` 后 cost 估算可能变化，即使数据分布没变。**
3. **Seq Scan 一定比 Index Scan 慢吗？** —— **不一定。** 命中比例高时顺序读整表比「索引 + 大量随机回表」更快。**能说出「Seq Scan 也是一种正确选择」，就脱离了「索引崇拜」。**
4. **怎么对比两个计划的优劣？** —— 看**实际耗时**与 **Buffers**，**而不是「估算代价」**；估算代价只能用于同结构比较。**要 `ANALYZE` 真跑、固定参数、跑多次取稳定值。**
5. **`Bitmap Heap Scan` 后面接 `Sort` 说明什么？** —— 说明**索引没有提供所需顺序**（它按物理顺序读堆），**所以还得排一次**。**要排序就应该考虑让索引顺序直接匹配 `ORDER BY`。**

**同类变体**

- 「`EXPLAIN` 还能看什么有用但少见的字段？」—— **`SETTINGS`**（哪些非默认参数影响了规划）、**`WAL`**（这条语句生成了多少 WAL）、**`MEMORY`**（规划阶段的内存）、**`GENERIC_PLAN`**（看参数化查询的通用计划）。**能说出 `GENERIC_PLAN`，就证明你真的查过预编译语句的坑。**
- 「怎么把计划变成可对比的东西？」—— **`FORMAT JSON` / `YAML`**，程序化解析；**再配合 `auto_explain` 把线上慢查询的计划自动记下来**。**「线上没有计划可看」和「线上有计划可看」是两个成熟度。**
- 「MySQL 那边怎么对应？」—— **MySQL 的 `EXPLAIN` 只看计划不执行**（要看实际执行用 `EXPLAIN ANALYZE`，8.0.18+），**输出字段是 `type` / `key` / `rows` / `Extra` 这套**（[[母题-M7-慢查询与SQL优化手段]]）。**两边的字段名完全不同，别混着说。**
