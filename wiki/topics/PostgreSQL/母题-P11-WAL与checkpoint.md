**导读**：必懂 3 件事（① WAL 管**正确性**，checkpoint 管**恢复时间**——两件事，但由同一组参数牵动 ② `synchronous_commit = off` **丢的是最近约 600 毫秒的已提交事务，而且是「整段丢」不是「随机丢」** ③ `full_page_writes` 让 checkpoint 越勤、WAL 越大——这是 PG 调优里最经典的两难）· 读完约 12 分钟 · 需要先懂：[[母题-P13-MVCC与可见性]]

**题目**：MySQL 有 redo / undo / binlog 三套日志，PG 只有一套 WAL。它是怎么保证「提交过的不丢」的？

**母题**：WAL 是怎么保证「提交过的不丢」的？checkpoint 在做什么？

**为什么重要**：这是**「PG 与 MySQL 的七处差异」里最容易被追问到底的一处**。表面问题只是「PG 用什么日志」，但**深一层会问到「那它为什么不需要 undo」**——答案在 MVCC（[[母题-P13-MVCC与可见性]]），**所以这两道题是一对，答不上 P13 就讲不透 P11。**

**一句话结论**：**WAL 是「先写日志、再改数据页」**：修改先顺序写进 WAL（顺序 IO），数据页留在共享缓冲区稍后再刷；**提交时靠 `fsync` 保证这个事务的 WAL 已经落盘**（`synchronous_commit = on`），所以崩溃后能用 WAL 把已提交的改动重放出来。**checkpoint 做的事是「把某个 LSN 之前的脏页刷盘，从而把恢复起点向前推」**——它不影响正确性，只影响**崩溃后要重放多久**。PG 不需要 undo，是因为**旧版本本来就留在堆里**（P13），不靠日志回滚。

**恢复关键词**：预写日志 / LSN / fsync 与 synchronous_commit / **off 丢的是三倍 wal_writer_delay ≈ 600ms 的【整段】** / checkpoint 推进恢复起点 / `checkpoint_timeout` 5min · `max_wal_size` 1GB / **full_page_writes（检查点后首写整页）** / `wal_compression` / `pg_stat_checkpointer` / 为什么不需要 undo

**核心不变量 / 主线**：
**WAL 管「已提交的能不能重放出来」（正确性），checkpoint 管「重放要从多久之前开始」（恢复时间）。** 两件事，**但它们由同一组参数牵动**——checkpoint 越勤，恢复越快，常态 IO 压力越大。
**而 `synchronous_commit` 管的是第三件事：「提交」这个动作等不等 WAL 落盘。** **三层要分清楚，才不会把它们混成一个「持久化」谈。**

**完整回答骨架**：为什么需要 WAL（顺序写换随机写 + 崩溃安全）→ WAL 怎么保证已提交不丢 → **off 到底丢多少（算出来）** → checkpoint 在做什么 → **整页写的代价（算出来）** → 为什么 PG 只有一套日志（不需要 undo）→ 生产怎么配

**完整回答（口述稿）**：
**WAL 是"先写日志、再改数据页"**：修改先顺序写进 WAL（顺序 IO），数据页留在共享缓冲区稍后再刷；**提交时靠 `fsync` 保证这个事务的 WAL 已落盘**（`synchronous_commit = on`），所以崩溃后能用 WAL 把已提交的改动重放出来。

**checkpoint 做的事是"把某个 LSN 之前的脏页刷盘，从而把恢复起点向前推"**——它**不影响正确性，只影响崩溃后要重放多久**。

**PG 不需要 undo，是因为旧版本本来就留在堆里**（见 P13），不靠日志回滚——这是它和 MySQL 最大的结构差异：MySQL 是 redo + undo + binlog 三套，PG 只有 WAL 一套。

同步/异步的取舍和 MySQL 一样是 **持久性 vs 提交延迟**：`synchronous_commit=off` 更快，但掉电会丢最近一段已提交的改动。

**分层要点**：
- **结论**：WAL = 顺序写日志 + 提交时 fsync；checkpoint 只影响恢复时长；PG 没有 undo。
- **推导链**：随机写慢 → 先写日志 → fsync 保证持久 → checkpoint 推进恢复起点 → 旧版本在堆里所以不需要 undo。
- **量化**：`synchronous_commit` 三档语义（on/off/remote_write 等，按版本）。
- **边界与常见误解**：checkpoint 不影响正确性；"PG 也有 redo/undo/binlog 三套"×（只有 WAL）。

## 一、教材

### 1. 为什么需要 WAL

修改数据时不直接改磁盘数据页（随机 IO 太慢），而是：

```
改内存（shared_buffers 里的数据页）
  + 把「改了什么」顺序追加到 WAL
  ↓
提交时：fsync WAL（保证这次提交已落盘）
  ↓
数据页留在内存，稍后由后台批量刷盘
```

**两个收益**：① **把随机写换成顺序写**（写入性能）；② **只要 WAL 落盘，即使数据页没刷、机器立刻断电，重启后也能重放出来**（崩溃安全）。

**关键在「提交时 fsync 的是 WAL，不是数据页」**——这就是「提交很快但数据页还没落盘」却依然安全的原因。

---

### 2. `synchronous_commit`：唯一承诺的落盘点，以及**它到底丢多少**

::figure pg-wal-and-checkpoint.svg | WAL 的三层职责、checkpoint 与整页写放大的代价 | 先写日志再改数据页、三个参数各自管什么、off 模式丢多少、整页写为什么让检查点越勤 WAL 越大

【事实】**官方给出的合法取值与默认值**：

> 合法值是 `remote_apply`、**`on`（默认）**、`remote_write`、`local`、`off`。

【事实】**一句很容易被漏掉的限定**：

> **如果 `synchronous_standby_names` 是空的，那么只有 `on` 和 `off` 是有意义的**——**`remote_apply`、`remote_write` 和 `local` 提供的本地同步级别和 `on` 完全一样。**

【推论】**所以「配置了 `remote_apply` 就等于更安全」是错的**——**没有备库时，它和 `on` 没有区别。** **这条能一句话问倒背参数的人。**

【推导】**`off` 到底丢多少？官方给了确切的上界**：

> **在 `off` 模式下没有等待，所以「向客户端报告成功」和「事务真正安全」之间会有一段延迟。**
> **最大延迟是 `wal_writer_delay` 的三倍。**
> `wal_writer_delay` **默认 200 毫秒**。

```text
最大丢失窗口 = 3 × wal_writer_delay
             = 3 × 200 ms
             = 【600 毫秒】

按 500 TPS 算：
  600 ms 内已提交的事务 ≈ 【300 个】
```

【结论】**「丢最近若干毫秒」这句话，可以给出确切数字：最多约 600 毫秒，500 TPS 下约 300 个已提交事务。**

【事实】**更关键的是它的【性质】——官方明确说了两件事**：

> **和 `fsync = off` 不同，把 `synchronous_commit` 设成 `off` 【不会带来任何数据库不一致的风险】。**
> 操作系统或数据库崩溃可能导致一些「号称已提交」的事务丢失，**但数据库的状态会和那些事务【被干净地中止】时完全一样。**

> **风险是数据丢失，不是数据损坏。** …**因为事务是按提交顺序重放的，所以不可能引入不一致**——例如，**如果事务 B 的改动依赖了先前事务 A 的效果，那么【不可能出现 A 的效果丢了而 B 的效果保留】的情况。**

【结论】**所以 `off` 的保证是一个【前缀保证】**：

> **丢的是「最后那一段」，不是「随机的一部分」。** **数据库永远停在一个自洽的状态上。**

【推荐】【事实】**官方给的判断标准非常直接**：

> **如果客户端会采取依赖「这个事务一定被记住了」的外部动作，就不该用异步提交。例如，银行肯定不会用异步提交来记录「ATM 吐了现金」这个事务。** 但在很多场景（**比如事件日志**）并不需要这种强保证。

【取舍】**所以判据是**：

- **钱、订单、状态机、任何会触发外部副作用的路径**：必须 `on`；
- **批量导入、可重建的埋点、可重放的日志**：可以 `off` 换吞吐——**但要在业务层知道「最多丢 600 毫秒的整段」，而不是"顺手关了"。**

【事实】**还有一个好用的细节**：**提交模式是【每个事务】可以单独选的**——**所以同一个系统里可以同时跑同步提交和异步提交的事务**，不必全局二选一。

### 3. checkpoint 在做什么

```
checkpoint 触发
  ↓
把「某个 LSN 之前」的所有脏页刷到磁盘
  ↓
在 WAL 里记一个 checkpoint 记录
  ↓
崩溃恢复时：从最近这个 checkpoint 开始重放 → 而不是从头
```

**所以 checkpoint 的收益是「恢复时间」**，不是数据安全。

【事实】**触发它的两条路，以及各自的默认值**：

| 参数 | 默认 | 含义 |
|---|---|---|
| `checkpoint_timeout` | **5 分钟** | **两次自动 checkpoint 之间的最长间隔**（范围 30 秒 ~ 1 天） |
| `max_wal_size` | **1 GB** | **两次自动 checkpoint 之间允许 WAL 增长到的上限**（**软上限**：重负载、归档失败、`wal_keep_size` 高时都可能被突破） |
| `min_wal_size` | **80 MB** | WAL 磁盘占用低于它时，旧 WAL 文件**总是被回收复用**而不是删除 |
| `checkpoint_completion_target` | **0.9** | **把 checkpoint 摊开到几乎整个间隔里**，提供较平稳的 IO 负载 |

【推导】**「崩溃后要重放多久」是一个可以算出来的数**：

```text
WAL 生成速率 = 10 MB/s，checkpoint_timeout = 5 分钟
  5 分钟产出 = 10 × 300 = 3000 MB = 3 GB > max_wal_size(1 GB)
  → 所以实际是被【max_wal_size】触发的

checkpoint 间隔 = 1 GB ÷ 10 MB/s = 【100 秒】

最坏恢复量 ≈ max_wal_size = 【1 GB】
若重放速率约 100 MB/s（可实测）：
  最坏恢复时间 ≈ 【约 10 秒】
```

【结论】**「恢复要多久」不是一个玄学参数，它就是「最坏重放的 WAL 量 ÷ 重放速度」，而最坏重放量的上界就是 `max_wal_size`。**

【推论】**所以官方说「调大 `max_wal_size` 会增加崩溃恢复所需的时间」——这句话现在有了量级。**

【事实】**官方对 `checkpoint_completion_target` 的建议是「不要调小」**：

> **减小这个参数是不被推荐的，因为它会让 checkpoint 完成得更快。** 结果是 **checkpoint 期间 IO 速率更高，然后在 checkpoint 完成到下一次调度之间有一段时间 IO 更少**——**也就是把平稳的 IO 变成了抖动的 IO。**

【推论】**这就是「为什么默认是 0.9」的答案**：**它把一次 checkpoint 的 IO 摊到几乎整个间隔上——用「更长的完成时间」换「更平稳的负载」。**

### 4. 那个经典两难：`full_page_writes` 让 checkpoint 越勤、WAL 越大

【事实】**官方定义**：

> **当这个参数为 on 时，服务器会在【checkpoint 之后对某个页的第一次修改】时，把【整个页的内容】写进 WAL。**
> 这样做是必要的：**因为操作系统崩溃时正在进行的页写入可能只完成了一部分**，导致磁盘上的页是「新旧数据混合」的状态。**WAL 里通常存的「行级变更数据」不足以完整恢复这样一个页。**

【推导】**算一下这个放大的量级**：

```text
一行普通变更的 WAL 记录：约 【100 字节】
一张页的整页镜像：8 KB = 【8192 字节】
  → 单次放大 ≈ 82 倍

一轮 checkpoint 间隔内，
假设有 20 万个页被改到（每页至少"首写"一次）：
  整页镜像：200,000 × 8 KB = 【1.6 GB】
  纯行级变更：200,000 × 100 B = 【20 MB】

  → 整页写占了这一轮 WAL 的 1.6 / 1.62 ≈ 【98.8%】
```

【结论】**WAL 的主要体积不是「你改了什么」，而是「页的第一个改动点的整页快照」。**

【推论】**这直接解释了两件事**：

```text
① 为什么 checkpoint 越勤 → WAL 反而越大
     每轮 checkpoint 都会把「首写整页」的账重新欠一遍
     → 于是「把 checkpoint 调很勤以缩短恢复时间」
       会【用 WAL 写放大和 IO 抖动换恢复速度】

② 为什么 wal_compression 值得开
     它压缩的正是【写入 WAL 的整页镜像】
     官方支持 pglz / lz4 / zstd（取决于编译选项）
     → 8 KB 的页通常能压不少，而代价只是重放时的解压
```

【取舍】**所以「（checkpoint 间隔、max_wal_size）→（恢复时间、常态 WAL 与 IO）」是同一个旋钮的两头**：

> **想恢复快 → 调小 max_wal_size / checkpoint_timeout → WAL 写放大变大、IO 更抖。**
> **想常态平稳 → 调大 → 崩溃后要重放更多。**
> **这不是一个"哪个更好"的问题，是一个"你的 SLA 要哪个"的问题。**

【事实】**要拿数据调、不要凭感觉调**——**注意统计视图在 PG 17 里被拆开了**：

```text
pg_stat_checkpointer（PG 17+ 从 pg_stat_bgwriter 拆出）
  num_timed       按【超时】调度的 checkpoint 次数
  num_requested   被【请求】的 checkpoint 次数   ← 这个数高说明 max_wal_size 太小
  num_done        实际完成的次数
  write_time / sync_time   写盘与同步各花了多少毫秒
  buffers_written  checkpoint 期间写出的共享缓冲区数
```

【推论】**判据**：

> **`num_requested` 远大于 `num_timed`，说明 checkpoint 是被 WAL 量逼出来的（`max_wal_size` 相对写入量太小）**——**这时你会看到频繁的 checkpoint 与 IO 抖动。**
> **反过来，如果 `num_timed` 占绝对多数，说明时间到了才做，`max_wal_size` 还有余量。**

【补充】**PG 17 之前的版本里，这些字段在 `pg_stat_bgwriter` 上**——**引用视图名时要说明版本。**

### 5. 为什么 PG 只有一套日志（不需要 undo）

MySQL 需要 undo 有两个原因：① 事务回滚；② 给 MVCC 提供旧版本。

**PG 两个都不需要日志层面的 undo**：

- **旧版本**：PG 的 `UPDATE` 是「写新版本 + 标记旧版本」（[[母题-P13-MVCC与可见性]]），**旧版本本来就在堆里**，读的时候按快照挑版本，不需要去 undo log 里拼；
- **回滚**：未提交事务的改动在崩溃恢复/回滚时，靠「这个版本的 `xmin` 属于一个未提交事务」判定为不可见即可，**并且由 VACUUM 清掉**。

【推论】**代价：旧版本占用空间、必须靠 VACUUM 回收**——**于是「PG 没有 undo」这件事，直接解释了三件现象**：

1. 为什么 PG 会**表膨胀**（[[母题-P14-长事务与表膨胀]]）；
2. 为什么有 **VACUUM 与事务 ID 回卷**这种 MySQL 不存在的运维风险（[[母题-P15-VACUUM与事务ID回卷]]）；
3. 为什么**长事务在 PG 里格外危险**（它按住了快照，让回收停摆）。

**这条是整条主线五的入口。**

### 6. 生产怎么配（说这段才像做过线上）

```
① 关键写路径：synchronous_commit = on（默认，别动）
② 可重建的批量写入：按事务粒度开 off（最多丢 600ms 的整段，顺序性有保证）
③ checkpoint 参数：先看 pg_stat_checkpointer 的 num_requested vs num_timed，
   再决定是放宽（减 IO 抖动）还是收紧（减恢复时间）
④ 恢复时间是算出来的：最坏重放量 ≈ max_wal_size ÷ 重放速度
⑤ wal_compression 打开：它压的正是整页写（WAL 体积的大头）
⑥ 复制场景额外考虑：synchronous_standby_names（P12）
```

**第 ③ 步的方法论比结论重要**：**调 checkpoint 之前先拿 `pg_stat_checkpointer` 的数据说话**，而不是「网上说 checkpoint 要调大」。

### 7. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「PG 的 WAL 就等于 MySQL 的 redo log」 | **不准确**。**WAL 同时承担 redo、复制与时间点恢复（经逻辑解码还有部分 binlog 职能）**；**undo 那部分职能被 MVCC 结构替代了** |
| 「`synchronous_commit = remote_apply` 比 `on` 更安全」 | **没有备库时两者本地行为完全一样**（官方原文） |
| 「`off` 会丢随机几个事务」 | **丢的是【最后一段】**——**事务按提交顺序重放，不可能出现"A 丢了 B 还在"** |
| 「`off` 可能把数据库搞坏」 | **风险是数据丢失，不是数据损坏**——**状态等同于那些事务被干净地中止** |
| 「checkpoint 越勤越安全」 | **checkpoint 不影响正确性**，只影响恢复时间；**而且越勤 → 整页写越多 → WAL 反而更大** |
| 「`full_page_writes` 是浪费，应该关掉」 | **关掉它会让崩溃后的页损坏无法恢复**；**要省就用 `wal_compression` 而不是关它** |
| 「恢复时间是个玄学参数」 | **它 = 最坏重放量 ÷ 重放速度**，而最坏重放量的上界就是 `max_wal_size` |

## 二、自测

**Q1（计算）**：某实例 WAL 生成速率 **10 MB/s**。`checkpoint_timeout = 5min`、`max_wal_size = 1GB`。重放速率约 100 MB/s。

问：**实际是哪个参数在触发 checkpoint？间隔多久？崩溃后最坏要重放多少、恢复多久？**

**A1**：

```text
按时间算：5 分钟产出 = 10 MB/s × 300 s = 【3000 MB = 3 GB】
按容量算：max_wal_size = 【1 GB】

3 GB > 1 GB → 【max_wal_size 先到】
  → 实际是被 WAL 量触发的

间隔 = 1 GB ÷ 10 MB/s = 【100 秒】（约 1 分 40 秒，比 5 分钟的设定短得多）

最坏重放量 ≈ max_wal_size = 【1 GB】
最坏恢复时间 ≈ 1 GB ÷ 100 MB/s = 【约 10 秒】
```

【结论】**`checkpoint_timeout` 设成 5 分钟，但实际 100 秒就触发一次**——**因为写入速率把 `max_wal_size` 先撑满了。**

【推论】**这条在面试里很值钱**：**「我设了 5 分钟」不等于「它是 5 分钟一次」**——**两个触发条件是「谁先到算谁」**，而**在写入密集的系统里，先到的几乎总是 `max_wal_size`。**

【补充】**这也给了调参的方向**：**如果你看到 checkpoint 太频繁、IO 抖动，把 `max_wal_size` 调大才是对症的**（`checkpoint_timeout` 调大没用——它根本不是触发者）。**而代价是恢复时间按同一比例变长。**

**Q2（计算）**：某实例 `wal_writer_delay` 保持默认，写入 **500 TPS**，`synchronous_commit = off`。

问：**崩溃最多丢多少事务？这些事务的分布是随机的还是连续的？业务上能接受吗？**

**A2**：

```text
官方给出的最大延迟 = 3 × wal_writer_delay = 3 × 200 ms = 【600 毫秒】

按 500 TPS：
  600 ms 内提交的事务 ≈ 500 × 0.6 = 【300 个】
```

【结论】**最多约 300 个已提交事务。**

【关键的分布问题】**官方明确：是【连续的一段】，不是随机丢失**——**因为事务按提交顺序重放**，而且**「不可能出现 A 的效果丢了而 B 的效果保留」**（B 依赖 A 时尤其重要）。

【推论】**所以业务上的判断可以变得很具体**：

```text
可以接受 off 的场景：
  埋点、日志、可重建的统计
  → 丢 600ms = 丢最后 300 条记录
  → 而且【顺序完整】——不会出现"半条记录"或"依赖错乱"

必须 on 的场景：
  任何会触发外部副作用的路径
  → 官方自己举的例子：【银行不会用异步提交记录 ATM 吐了现金】
  → 因为「吐现金」这个动作一旦发生就不可撤销，
     而事务如果丢了，账上就没有这笔支出
```

【结论】**判据是「客户端会不会根据这个事务采取不可撤销的外部动作」**——**这句话比"重要不重要"具体得多。**

【补充】**它不破坏一致性**：**官方原话是「数据库状态会和那些事务被干净地中止时完全一样」**，**风险是数据丢失，不是数据损坏。** **所以 `off` 的可用范围比很多人想的大——但边界要卡在「外部副作用」上。**

**Q3（计算）**：一行普通变更的 WAL 记录约 100 字节。一轮 checkpoint 间隔内，有 **20 万个页**被改到（每页至少发生一次「首写」）。`full_page_writes = on`。

问：**这一轮 WAL 里，整页镜像占多少比例？这个比例说明了什么？**

**A3**：

```text
整页镜像：200,000 × 8192 B = 【1.6 GB】
纯行级变更：200,000 × 100 B = 【20 MB】

占比 = 1.6 GB ÷ (1.6 GB + 20 MB) ≈ 【98.8%】
单次放大 = 8192 ÷ 100 ≈ 【82 倍】
```

【结论】**WAL 的体积主要不是「你改了什么」，而是「页的第一个改动点的整页快照」。**

【推论】**这解释了一个反直觉的调参结论**：

```text
「把 checkpoint 调勤一点，缩短恢复时间」
  → 每一轮 checkpoint 都会重新欠一遍「首写整页」的账
  → checkpoint 越勤 → 整页写越多 → WAL 越大
  → 用【WAL 写放大 + IO 抖动】换【恢复时间】

所以这不是"哪个更优"，是【你的 SLA 要哪个】
```

【取舍】**所以正确的动作是「压体积」而不是「关功能」**：

> **`wal_compression` 压的正是这些整页镜像**——**支持 `pglz` / `lz4` / `zstd`（取决于编译选项），代价只是重放时的解压。** **相比关掉 `full_page_writes`（那会让崩溃后的半写页无法恢复），压缩是安全的那一侧。**

**Q4（纠错）**：下面这段话哪里不准确？

> "PostgreSQL 的 WAL 就相当于 MySQL 的 redo log，都是用来崩溃恢复的。"

**A4**：三处问题。

1. **WAL 承担的功能更多**：**它同时是崩溃恢复（redo）、复制的基础（流复制直接传 WAL）、时间点恢复（PITR）的载体，而且通过【逻辑解码】还能产出逻辑变更流**——**对应 MySQL 那边是 redo + binlog 的合并。**
2. **MySQL 的 undo 在 PG 里没有对应物**：**undo 的两项职能（回滚、给 MVCC 提供旧版本）在 PG 里由 MVCC 结构本身承担**（旧版本留在堆里，[[母题-P13-MVCC与可见性]]）——**这不是"PG 用别的方式做了同一件事"，而是"PG 换了一套结构，于是不需要 undo"。**
3. **代价不同**：**MySQL 有 undo 表空间要管；PG 有【表膨胀】和【VACUUM + 事务 ID 回卷】要管**（[[母题-P14-长事务与表膨胀]] / [[母题-P15-VACUUM与事务ID回卷]]）。**「PG 没有 undo」不是免费的。**

【准确说法】"**PG 只有一套 WAL，它把 redo 和 binlog 的职能合在了一起；而 undo 的职能被 MVCC 结构替代了。** **所以真正要讲清的不是"PG 有什么日志"，而是"它为什么不需要 undo、代价是什么"。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们把 `checkpoint_timeout` 调小了，这样 checkpoint 更频繁，数据库更安全。"

**A5**：三处问题。

1. **checkpoint 和「安全」无关**：**保证已提交不丢的是 WAL + `fsync`（`synchronous_commit`），不是 checkpoint。** **checkpoint 只影响「崩溃后要重放多久」**——**它调不调，数据该丢还是丢、不该丢还是不会丢。**
2. **调小它会【放大 WAL】**：**每轮 checkpoint 都会让「检查点后首写整页」的账重新欠一遍**（Q3：整页写占了 WAL 的 98.8%）——**所以 checkpoint 越勤，WAL 体积越大、IO 抖动越明显。**
3. **而且它可能根本不是触发者**：**在实际写入密集的系统里，先到的几乎总是 `max_wal_size`**（Q1）——**所以调 `checkpoint_timeout` 可能毫无效果。**

【准确说法】"**checkpoint 频率是一笔【恢复时间 ↔ 常态 IO】的交易，跟数据安全无关。** **要调它，先看 `pg_stat_checkpointer` 的 `num_requested` 与 `num_timed` 谁占多数，确认到底是哪个条件在触发，再动手。**"

## 三、面试输出（学完再看）

**一句话结论**：**WAL 是「先写日志、再改数据页」**——修改先顺序追加到 WAL，数据页留在共享缓冲区稍后批量刷盘；**提交时 `fsync` 的是 WAL 而不是数据页**，所以「提交很快但数据页还没落盘」依然安全。**这三层要分清**：**WAL 管正确性、checkpoint 管恢复时间、`synchronous_commit` 管"提交等不等落盘"。** **`synchronous_commit = off` 丢多少可以算**：**官方给出最大延迟是 `wal_writer_delay` 的三倍，默认 200ms → 最多约 600 毫秒**，500 TPS 下约 300 个已提交事务；**而且丢的是【连续的最后一段】不是随机的**——官方原话是「事务按提交顺序重放，不可能出现 A 的效果丢了而 B 的保留」，**所以它只带来数据丢失、不带来数据损坏**，数据库状态等同于那些事务被干净地中止。**checkpoint 的触发是「`checkpoint_timeout`（默认 5 分钟）与 `max_wal_size`（默认 1GB）谁先到算谁」**——**写入密集时先到的几乎总是 `max_wal_size`**，所以恢复时间可以算：**最坏重放量 ≈ `max_wal_size` ÷ 重放速度**。**而它有一个经典两难：`full_page_writes` 让检查点后对每个页的第一次修改都要写整页镜像**——**8 KB 的整页 vs 100 字节的行级记录，放大 82 倍，整页写能占一轮 WAL 的 98.8%**——**所以 checkpoint 越勤、WAL 反而越大**；**要省体积应该开 `wal_compression`，而不是关 `full_page_writes`。** **最后：PG 不需要 undo**，因为**旧版本本来就留在堆里**（MVCC 结构承担了 undo 的两项职能）——**代价是表膨胀、VACUUM 与事务 ID 回卷，以及长事务格外危险**。**「PG 没有 undo」不是免费的。**

**恢复关键词**：先写日志再改数据页 / 提交 fsync 的是 WAL / **三层：正确性 · 恢复时间 · 提交等待** / **off 最多丢 3 × 200ms = 600ms（连续的一段）** / 数据丢失而非损坏 / **checkpoint：timeout 5min 与 max_wal_size 1GB 谁先到算谁** / 最坏重放 ≈ max_wal_size / **full_page_writes：首写整页、放大 82 倍、占 98.8%** / `wal_compression`（压的正是整页）/ `checkpoint_completion_target` 0.9 / `pg_stat_checkpointer`（PG 17 拆出）/ 不需要 undo → 表膨胀

**核心不变量 / 主线**：
**WAL 管「已提交的能不能重放出来」，checkpoint 管「重放要从多久之前开始」，`synchronous_commit` 管「提交等不等落盘」。**
**三件事由同一组参数牵动——checkpoint 越勤，恢复越快，常态 IO 压力越大。**

**完整回答骨架**：WAL 为什么存在 → **`off` 丢多少（算 600ms / 300 个事务，且是整段）** → checkpoint 管什么 → **两个触发条件谁先到（算 100 秒）** → **整页写放大（算 98.8%）与那个两难** → 为什么不需要 undo → 生产配置 → 收束到「三层要分清」

**追问**（先说后看）

1. **`synchronous_commit = off` 丢的是已提交事务，为什么还能接受？** —— 因为**它丢的是【连续的最后一段】，而且只丢数据不损坏数据**——**数据库状态等同于那些事务被干净地中止**。**判据是官方的原话：「客户端会不会采取依赖这个事务已被记住的外部动作」**——**银行不会用它记录 ATM 吐现金，但事件日志完全可以用。** **这就是「数量级口径」：不是"会不会丢"，而是"丢多少、丢的是哪一段、能不能补"。**
2. **恢复要多久，怎么估算？** —— **最坏重放量 ≈ `max_wal_size`（软上限）**，再除以重放速度（可以拿一次真实恢复或压测测出来）。**所以「恢复时间」是可以给出量级的数字，不是玄学参数。**
3. **PG 也有 binlog 吗？** —— **没有。** 逻辑复制、CDC 靠**逻辑解码**（从 WAL 解出逻辑变更，[[母题-P12-流复制与逻辑复制]]）；MySQL 的 binlog 是 Server 层单独一套逻辑日志。**这是「PG 只有一套日志」的直接后果。**
4. **WAL 会无限增长吗？** —— 不会，回收靠 checkpoint 推进；**但如果开着复制槽而备库/消费者不消费，WAL 就不会被回收**（P12 的经典事故：短时间内能把磁盘写满）。
5. **能不能关掉 WAL？** —— **表可以设 `UNLOGGED`**（不写 WAL，快，**但崩溃后数据会被清空**），**只适合可重建的中间表**。这是一个真实的工程选项，**值得知道——但也要说清它的代价是"崩溃后整张表归零"。**

**同类变体**

- 「调 checkpoint 参数应该看什么？」—— **`pg_stat_checkpointer`（PG 17+；之前是 `pg_stat_bgwriter`）**：**`num_requested` 远大于 `num_timed` 说明被 WAL 量逼出来的**（该调大 `max_wal_size`）；**`write_time` / `sync_time` 告诉你 checkpoint 期间花在写盘和同步上的时间**。**能说出「PG 17 把这个视图拆出来了」，说明你最近真的碰过生产。**
- 「MySQL 的 redo 和 PG 的 WAL 差在哪？」—— **① PG 的 WAL 还兼作复制源与时间点恢复的载体**（redo 不做这两件事）；**② PG 没有 undo**（其职能被 MVCC 结构替代，代价是膨胀）；**③ MySQL 的 redo 是环形写的物理日志，PG 的 WAL 是按段（默认 16MB）切分的**（[[母题-M11-三日志与两阶段提交]]）。
