# 母题 P11 · WAL 与 checkpoint

> **模块**：PostgreSQL / 日志与持久化
> **所属主线**：四 · 日志与持久化（提交过的数据，服务挂了为什么不该丢）
> **关联母题**：[[母题-P12-流复制与逻辑复制]] · [[母题-P13-MVCC与可见性]]
> **素材来源**：`study/09-数据缓存队列与一致性`（数据持久化视角）+ 通用知识（**checkpoint 细节待你核对**）

**题目**：MySQL 有 redo / undo / binlog 三套日志，PG 只有一套 WAL。它是怎么保证「提交过的不丢」的？

**母题**：WAL 是怎么保证「提交过的不丢」的？checkpoint 在做什么？

**为什么重要**：这是**「PG 与 MySQL 的七处差异」里最容易被追问到底的一处**。表面问题只是「PG 用什么日志」，但**深一层会问到「那它为什么不需要 undo」**——答案在 MVCC（P13），**所以这两道题是一对，答不上 P13 就讲不透 P11。**

**一句话结论**：**WAL 是「先写日志、再改数据页」**：修改先顺序写进 WAL（顺序 IO），数据页留在共享缓冲区稍后再刷；**提交时靠 `fsync` 保证这个事务的 WAL 已经落盘**（`synchronous_commit = on`），所以崩溃后能用 WAL 把已提交的改动重放出来。**checkpoint 做的事是「把某个 LSN 之前的脏页刷盘，从而把恢复起点向前推」**——它不影响正确性，只影响**崩溃后要重放多久**。PG 不需要 undo，是因为**旧版本本来就留在堆里**（P13），不靠日志回滚。

**恢复关键词**：预写日志（先日志后数据页）/ LSN / fsync 与 synchronous_commit / checkpoint 推进恢复起点 / checkpoint 频率的两面 / full_page_writes（检查点后首写整页）/ 恢复从最近 checkpoint 开始

**核心不变量 / 主线**：
**WAL 管「已提交的能不能重放出来」（正确性），checkpoint 管「重放要从多久之前开始」（恢复时间）。** 两件事，**但它们由同一组参数牵动**——checkpoint 越勤，恢复越快，常态 IO 压力越大。

**完整回答骨架**：为什么需要 WAL（顺序写换随机写 + 崩溃安全）→ WAL 怎么保证已提交不丢 → checkpoint 在做什么 → 为什么 PG 只有一套日志（不需要 undo）→ `synchronous_commit` 的取舍 → 生产怎么配

## 原理分解

### 一、为什么需要 WAL

修改数据时不直接改磁盘数据页（随机 IO 太慢），而是：

```
改内存（shared_buffers 里的数据页）
  + 把「改了什么」顺序追加到 WAL
  ↓
提交时：fsync WAL（保证这次提交已落盘）
  ↓
数据页留在内存，稍后由后台批量刷盘
```

**两个收益**：① **把随机写换成顺序写**（写入性能）；② **只要 WAL 落盘，即使数据页没刷、机器立刻断电，重启后也能重放出来**（崩溃安全）。

**关键在「提交时 fsync 的是 WAL，不是数据页」**——这就是「提交很快但数据页还没落盘」却依然安全的原因。

### 二、`synchronous_commit`：唯一承诺的落盘点

| 值 | 语义 | 丢什么 |
|---|---|---|
| `on`（默认） | 提交时等本事务 WAL **fsync 完成**才返回成功 | 不丢已提交事务 |
| `off` | 提交不等 fsync，让后台尽快刷 | **可能丢最近若干毫秒「已提交」的事务** |
| `local` / `remote_apply` 等 | 与复制相关（见 P12） | 取决于复制配置 |

**必须讲清的一点**：`off` 丢的是「**已经向客户端返回成功、但 WAL 还没落盘**」的那部分——**这是唯一一个「数据库告诉成功了却可能丢」的配置**。所以：

- **钱、订单、状态机等路径**：必须 `on`；
- **批量导入、可重建的埋点数据**：可以临时 `off` 换吞吐，但**要在业务层知道这件事**，不是"顺手关了"。

### 三、checkpoint 在做什么

```
checkpoint 触发
  ↓
把「某个 LSN 之前」的所有脏页刷到磁盘
  ↓
在 WAL 里记一个 checkpoint 记录
  ↓
崩溃恢复时：从最近这个 checkpoint 开始重放 → 而不是从头
```

**所以 checkpoint 的收益是「恢复时间」**，不是数据安全。

**它带来一个必须知道的副作用——`full_page_writes`**：因为刷盘是「按页」但不是原子的（可能半页写失败），所以 **checkpoint 之后对这些页的第一次修改，WAL 里要记整页内容**（而不是「某偏移改了某个值」）。后果是：

- **checkpoint 越勤 → 「首写整页」发生得越频繁 → WAL 体积反而更大**；
- 所以「把 checkpoint 调很勤以缩短恢复时间」会**用 WAL 写放大和 IO 抖动换恢复速度**——这是 PG 调优里一个经典的两难。

### 四、为什么 PG 只有一套日志（不需要 undo）

MySQL 需要 undo 有两个原因：① 事务回滚；② 给 MVCC 提供旧版本。

**PG 两个都不需要日志层面的 undo**：

- **旧版本**：PG 的 `UPDATE` 是「写新版本 + 标记旧版本」（P13），**旧版本本来就在堆里**，读的时候按快照挑版本，不需要去 undo log 里拼；
- **回滚**：未提交事务的改动在崩溃恢复/回滚时，靠「这个版本的 `xmin` 属于一个未提交事务」判定为不可见即可，**并且由 VACUUM 清掉**。

**代价**：旧版本占用空间、必须靠 **VACUUM** 回收——**于是「PG 没有 undo」这件事，直接解释了三件现象**：

1. 为什么 PG 会**表膨胀**（P14）；
2. 为什么有 **VACUUM 与事务 ID 回卷**这种 MySQL 不存在的运维风险（P15）；
3. 为什么 **长事务在 PG 里格外危险**（它按住了快照，让回收停摆）。

**这条是整条主线五的入口。**

### 五、生产怎么配（说这段才像做过线上）

```
① 关键写路径：synchronous_commit = on（默认，别动）
② checkpoint 频率：先看 pg_stat_bgwriter 的 checkpoint 频率与刷盘量，
   再决定是放宽 checkpoint 间隔（减 IO 抖动）还是收紧（减恢复时间）
③ 恢复时间是可测量的：用 checkpoint 位置与 WAL 生成速率估算「最坏要重放多少」
④ 复制场景额外考虑：synchronous_standby_names（P12）
```

**第 ② 步的方法论比结论重要**：**调 checkpoint 之前先拿 `pg_stat_bgwriter` 的数据说话**，而不是「网上说 checkpoint 要调大」。

## 二、扩展：类似题与追问

**类似题**

1. 「PG 也有 binlog 吗？」——**没有。** 逻辑复制、CDC 靠**逻辑解码**（从 WAL 解出逻辑变更，见 P12）；MySQL 的 binlog 是 Server 层单独一套逻辑日志。**这是「PG 只有一套日志」的直接后果。**
2. 「WAL 会无限增长吗？」——不会，回收靠 checkpoint 推进；**但如果开着复制槽而备库/消费者不消费，WAL 就不会被回收**（P12 的经典事故）。
3. 「能不能关掉 WAL？」——表可以设 `UNLOGGED`（不写 WAL，快，但**崩溃后数据清空**），只适合可重建的中间表。**这是一个真实的工程选项，值得知道。**

**追问链**

- 追问一层：**「`synchronous_commit = off` 丢的是已提交事务，为什么还能接受？」**——因为「丢最近若干毫秒」在很多场景下等价于「丢最近几条埋点」；而且**它不破坏数据库自身一致性**（不会丢一半、也不会出现违反约束的状态）。**判据是「这几毫秒的数据丢了，业务能不能自己补回来」**——能补就可用，不能就必须 `on`。**这就是我们反复强调的「数量级口径」：不是"会不会丢"，而是"丢多少、能不能补"。**
- 追问二层：**「恢复要多久，怎么估算？」**——恢复时间 ≈ 「checkpoint 到现在」的 WAL 量 ÷ 重放速度（可以拿一次真实恢复或压测测出来）。**所以「恢复时间」是一个可以给出量级的数字，而不是一个玄学参数**——这句话在面试里很值钱，因为它把「持久化」从定性讲成了定量。
