# 母题 P9 · 序列化失败与重试

> **模块**：PostgreSQL / 事务与锁
> **所属主线**：三 · 事务与锁（并发改同一份数据，为什么不会乱）
> **层级**：A · 教材级（失败率、重试放大、谓词锁升级都能算出来；而且能从「谓词锁表有多大」推出「为什么误报」）
> **关联母题**：[[母题-P8-隔离级别与读一致性]]（RR 下的 40001 是同一件事）· [[母题-P10-无间隙锁与锁变体]]（不加锁怎么防幻读）· [[母题-P18-乐观并发控制]]（可重试的前提是幂等）· [[母题-P19-唯一约束与UPSERT]]（幂等的最终防线）· [[母题-P14-长事务与表膨胀]]（长事务的另一个面貌）
> **素材来源**：`study/09-数据缓存队列与一致性` 第 2.2 节 + **PostgreSQL 官方文档 Transaction Isolation（Serializable 一节）与 Lock 配置**（2026-09-13 联网核实）+ 通用知识。**三组算式与「谓词锁升级」那一段为本次新增（待你核对）**

**导读**：必懂 3 件事（① 失败**是契约不是故障**——SSI 靠检测依赖环而不是加锁，检测到了就必须有人失败 ② **重试必须是「整个事务」**，因为快照已经不可信 ③ **谓词锁在内存不够或读得太多时会升级成整表锁 → 40001 率飙升**——这是「误报」的机械原因，也是可以调的）· 读完约 12 分钟 · 需要先懂：[[母题-P8-隔离级别与读一致性]]

**题目**：把隔离级别提到 Serializable 之后，接口开始零星报 `could not serialize access due to read/write dependencies`。这是「不能用」还是「设计如此」？

**母题**：为什么 Serializable 会失败？应用层怎么处理才正确？

**为什么重要**：这是**「PG 的并发哲学」最集中的一课**。MySQL 的思路是「加锁等一等，尽量别让你失败」；**PG 的思路是「用快照保证正确，冲突了就直接告诉你，你自己重试」**。**把「失败」理解成缺陷而不是契约，就会做出错误的技术判断**——比如「把隔离级别降回去」或「加锁硬扛」，这两条都比正确重试更糟。

**一句话结论**：PG 的 Serializable 用的是 **SSI（Serializable Snapshot Isolation）**：它在快照隔离之上**检测可能导致非可串行化结果的读写依赖环**，一旦发现就**主动让其中一个事务失败**（SQLSTATE `40001`）。**所以失败是设计的一部分，不是异常**——正确做法是**在应用层捕获 40001、重试整个事务**（带退避和上限），而不是重试单条语句。

**恢复关键词**：SSI / 读写依赖与依赖环 / 40001 / **重试整个事务** / 幂等 / **谓词锁会升级（每页 2 行 · 每表 32 页 → 整表锁）** / `SIReadLock` / 全表扫必然拿整表锁 / `SERIALIZABLE READ ONLY DEFERRABLE`

**核心不变量 / 主线**：
**Serializable 的成本不在执行速度，在「失败与重试」。** 所以选择它的前提不是「我的 SQL 快不快」，而是**「这个业务操作本身可不可以重试」**——可重试，SSI 就是最省心的可串行化；不可重试，就该用显式锁。

**完整回答骨架**：PG 怎么做到可串行化（SSI 检测依赖而不是加锁）→ **谓词锁为什么会升级（误报的机械原因）**→ 所以会失败 → 失败的错误码与语义 → 正确的处理方式（重试整个事务）→ 与悲观锁的取舍 → 一个前提检查清单

## 一、教材

### 1. SSI 是怎么做到可串行化的

传统可串行化靠**两阶段锁**（锁到事务结束），代价是并发度低、容易死锁。PG 走另一条路：

```
① 先按快照隔离执行，读不加锁 —— 大部分事务根本不会冲突
② 在后台记录事务之间的「读写依赖」（谁读了谁写的数据）
③ 如果发现依赖形成一个环 —— 就不可能存在任何串行顺序 → 报错并干掉其中一个
```

**关键在「② 只记录依赖，不是拦住操作」**：所以**没有冲突的事务完全没有额外等待**。只有真的出现环时才失败。

【事实】**官方的三条定性，把 SSI 和「加锁」彻底分开**：

> - 这些锁**不造成任何阻塞**，因此**也不可能参与造成死锁**。它们只用来**标记并发 Serializable 事务之间的依赖**。
> - 对比之下，**一个想保证数据一致性的 RC / RR 事务可能需要拿整张表的锁**，那会阻塞其他用户；**或者用 `SELECT FOR UPDATE` / `FOR SHARE`——它们不仅能阻塞别人，还会带来磁盘访问（必须回表读最新的版本）**。
> - 这些谓词锁在 `pg_locks` 里以 **`SIReadLock`** 模式出现。

【推论】**这就是「SSI 的代价是失败，不是等待」的机制来源**——**它把并发代价从「锁等待」搬到了「事后中止」**。**而且 `SIReadLock` 给了你一个可观测的手柄**：**排查 40001 时，先看 `pg_locks` 里那个事务到底"读"了多大范围。**

**到这里你应该能回答**：为什么「Serializable 会让数据库到处加锁变慢」这个说法在 PG 里是错的？

### 2. 谓词锁会「升级」——误报的机械原因【事实】

这是 P9 最值钱的一段，也是最没人讲的一段。**官方明确给出了升级规则与参数默认值**：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `max_pred_locks_per_page` | **2** | **单页上被谓词锁住超过 2 行 → 升级为整页锁** |
| `max_pred_locks_per_relation` | **-2** | 负数表示 `max_pred_locks_per_transaction ÷ 2` |
| `max_pred_locks_per_transaction` | **64** | 每个事务的谓词锁对象上限 |

【推导】**把这些默认值串起来，得到一个很吓人的数字**：

```text
每页超过 2 行 → 整页锁
每表超过 (64 ÷ 2) = 32 页 → 【整表锁】

也就是说：
  一个 Serializable 事务只要在同一张表上读了【33 页】
  → 它的谓词锁就变成【整张表】级别
  → 此后【任何写这张表的事务】都可能与它冲突

33 页 × 8 KB = 【264 KB】
```

【结论】**读 264 KB 就把整张表标成"我读过"**——**对一张 16 GB 的表，这只是 1/60000。** **但它让 40001 的冲突面从「若干行」放大到「整张表」。**

【推论】**官方原话把后果说得更直白**：

> **当系统因为谓词锁表内存不足，被迫把多个页级谓词锁合并成一个【关系级】谓词锁时，序列化失败率会上升。**
> **一次顺序扫描【总是】需要一个关系级谓词锁——这会导致序列化失败率上升。** 可以通过**降低 `random_page_cost` 和/或提高 `cpu_tuple_cost`** 来鼓励走索引扫描。

【结论】**所以有一个反直觉的结论**：

> **在 Serializable 下建索引，不只是为了查询快——是为了降低 40001 率。**
> **一条没走索引的查询，会把整张表标记成"读过"，让大量本不相干的事务互相冲突。**

【事实】**调大谓词锁的参数是官方认可的动作**：`max_pred_locks_per_transaction`（默认 64）/ `max_pred_locks_per_relation`（默认 -2）/ `max_pred_locks_per_page`（默认 2）——**加大它们就是把"升级"推迟，用内存换更低的误报率。**

【纠正常见误解】**「SSI 的误报」不是玄学，是内存策略**——**细粒度锁（行级/页级）会为了不撑爆锁表而合并成粗粒度锁（页级/表级），合并就丢精度，丢精度就误报。** **能说出这一条，说明你真的理解 SSI 的实现，而不是背了它的名字。**

### 3. 错误长什么样，怎么识别

::figure pg-ssi-and-retry.svg | SSI 的依赖检测、谓词锁升级与重试放大 | 依赖环如何导致失败、谓词锁从行级升级到表级的三级规则、三类错误的分类处置、重试率随并发上升的正反馈

```
ERROR: could not serialize access due to read/write dependencies among transactions
DETAIL: Reason code: Canceled on identification as a pivot...
SQLSTATE: 40001
```

【事实】**判断这件事要用错误码（`40001`），不要用错误文本匹配**——**文本会随版本/语言变化，错误码是契约。** 官方原话也确认了这一点：**「环境必须有一套统一的序列化失败处理方式，因为序列化失败【总是】以 SQLSTATE `40001` 返回」**。

**同一个 `40001` 也会由 RR 下的写冲突产生**（[[母题-P8-隔离级别与读一致性]]），语义都是「**重试就能成功**」。

**要区分的三类错误**：

| 错误 | 语义 | 处理 |
|---|---|---|
| `40001`（序列化失败 / 快照过期） | **可重试**：重放事务大概率成功 | **重试整个事务** |
| `40P01`（死锁） | 也可重试，但说明**加锁顺序有问题** | 重试 + **修加锁顺序** |
| 约束冲突（`23505` 等） | **确定性失败**，重试也没用 | 不要重试，走业务分支 |

【推论】**这个三分法比「统一重试三次」重要得多**——**对确定性错误无脑重试，是在制造重复副作用。**

【事实】**一个非常反直觉的官方提醒**：**Serializable 并不能保证「真实串行执行下不会报的错就不报」**——**它可能报出真实的串行执行里根本不会发生的唯一约束冲突**，**即使你已经先查过那个键不存在**。

> **规避方式是：所有会插入潜在冲突键的 Serializable 事务，都必须【先显式检查】。** 例如：**有的应用直接插入、有的应用先 `SELECT` 再插入，那么前者会让后者报出不该报的唯一冲突。**

【推论】**所以「先查再插」这个动作，只有在【所有】参与者都这么做时才有效。** **协议不统一，比完全不做协议更糟——因为它给了你虚假的安全感。**

### 4. 正确的重试长什么样

**必须是「整个事务」，不是「那一条语句」**：

```
① 记录本次事务的输入（幂等键）
② BEGIN
③ 执行全部读与写
④ COMMIT
   └─ 若报 40001 → 回滚 → 重新执行 ③（用同样的输入）
```

**因为 SSI 失败意味着「你读到的那个快照已经不可信」**——**重试那一条语句没有意义，必须重新读。**

【事实】**失败发生在哪一步，官方给了明确答案**：SSI 的检测**可以一直持续到提交时**——**官方那个例子就是「两个事务都做完了，然后都试着提交」时，其中一个被回滚。** **所以 `COMMIT` 是一个会失败的操作**——**这打破了「提交不会失败」的朴素假设。**

【推导】**这把重试框架的要求提高了**：

```text
朴素写法：
  try { ...; commit(); } catch (...) { /* 只有语句会抛错 */ }
  → COMMIT 抛 40001 时，事务其实【没有提交成功】
  → 但很多框架会把 commit 的异常当成"未知状态"

正确写法：
  把 COMMIT 也包进可重试的范围
  并且确认【回滚是干净的】——失败的事务不能留下任何副作用
```

**四条要求**：

- **带退避 + 抖动**：并发高时同步重试会互相打架，越试越糟；
- **有重试上限**：超过就暴露成失败/未知，不要无限循环；
- **整个事务幂等**：重试不能产生第二次副作用——所以**必须有幂等键或唯一约束兜底**（[[母题-P18-乐观并发控制]] / [[母题-P19-唯一约束与UPSERT]]）；
- **保留 trace**：记录重试次数，它是「并发竞争激烈程度」的直接指标（可以直接做监控）。

**反过来讲最重要的一句**：**SSI 要求业务可重试；而「可重试」的前提是副作用可幂等。** 所以「能不能上 Serializable」其实是一个**幂等设计问题**，不是一个数据库配置问题。**这句话是这道题的分水岭。**

【事实】**官方给的性能建议里，有三条和「重试」直接相关**：

> - **尽可能把事务声明成 `READ ONLY`**（只读事务在很多情况下根本不必拿谓词锁）。
> - **控制活跃连接数，必要时用连接池**——**这条在跑 Serializable 的繁忙系统里尤其重要**。
> - **不要让连接长时间 "idle in transaction"**——可以用 `idle_in_transaction_session_timeout` 自动断开。
> - **消除那些因为 Serializable 已自动提供保护而不再需要的显式锁 / `FOR UPDATE` / `FOR SHARE`。**

**最后一条最容易被忽略**：**很多人一边上 Serializable、一边保留着 `FOR UPDATE`——那是把两套代价都付了。**

### 5. 跟其他方案比

| 方案 | 机制 | 适合 | 代价 |
|---|---|---|---|
| **Serializable（SSI）** | 检测依赖环 → 报错重试 | **冲突低但需要跨行不变量**、业务可重试 | 可能误报；**谓词锁升级会让误报率非线性上升**；要求重试框架 |
| **RR / RC + `FOR UPDATE`** | 悲观锁，冲突就排队 | **冲突高、临界区短**、业务不好重试 | 锁等待、死锁风险、吞吐下降、**要回表读最新版本** |
| **条件更新（乐观）** | 判断与写入合并为一条语句 | 冲突低、单行不变量 | **不能直接保护跨行不变量**（要靠约束） |
| **唯一约束** | 数据库原子性 | **幂等与重复的最终防线** | 只覆盖「重复」，不覆盖「顺序」 |

【取舍】**判据**：**能不能重试 → 能就用 SSI/乐观；冲突频率高到重试成本超过加锁成本 → 才用悲观锁。** 这条判据和 MySQL 那边（[[母题-M16-乐观锁与悲观锁]]）是同一句话，**只是 PG 多了一层「SSI 帮你自动检测」。**

### 6. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「Serializable 会到处加锁变慢」 | **官方明确：谓词锁不阻塞、也不可能造成死锁**；代价是**监控开销 + 中止率** |
| 「SSI 的误报说不清为什么」 | **说得清**：**锁表内存不足 → 细粒度锁合并成粗粒度锁 → 丢精度**；**调 `max_pred_locks_*` 可以推迟升级** |
| 「全表扫和走索引对 Serializable 没差别」 | **差别极大**：**顺序扫描【总是】需要一个关系级谓词锁**，失败率因此上升 |
| 「失败发生在执行语句时」 | **也可能发生在 `COMMIT`**——**所以 `COMMIT` 必须在重试范围内** |
| 「先查再插就能避免唯一冲突」 | **只有在【所有】参与者都遵守同一协议时才成立**；协议不统一反而会报出串行执行里不会发生的错 |
| 「重试次数越多越保险」 | **重试本身增加并发**——**高冲突时是无上限的正反馈**（见 Q1） |

## 二、自测

**Q1（计算）**：某表 16 GB、8000 万行。一个 Serializable 事务执行 `WHERE bigint_col > 0` 的查询（命中约一半行）。

问：**它拿到的谓词锁是什么粒度？冲突面有多大？如果换成能走索引的查询、只碰 100 页呢？**

**A1**：

```text
官方规则（默认参数）：
  每页超过 max_pred_locks_per_page=2 行 → 升级为【整页】锁
  每表超过 64÷2=32 页 → 升级为【整表】锁

全表扫描：
  读 200 万页 → 远超 32 页 → 升级成【关系级（整表）谓词锁】
  → 冲突面 = 【整张表的任何写入】

走索引（只碰 100 页）：
  100 页 > 32 页 → 仍然会升级成整表锁！
  → 要真正避免，得把页数压到【32 页以内】（约 264 KB）
```

【结论】**这里有个反直觉的地方**：**「走索引」本身还不够——只有把访问的页数压到 32 页以下，才拿不到整表锁。** **但官方仍然建议"鼓励走索引"，因为**：

```text
全表扫： 一定拿整表锁（无论表多大）
索引扫： 拿多少页的锁取决于实际命中
  → 命中少的查询（OLTP 的典型形状）可以完全避开升级
  → 命中多的查询至少和全表扫一样
```

【推论】**判据**：

> **在 Serializable 下，「这个查询读了多少页」不只是性能问题，也是【并发度问题】。**
> **同一条 SQL，在 RC 下是"慢一点"，在 Serializable 下可能是"让整张表的事务互相失败"。**

【补充】**这也是官方那条建议的来历**：**「可以通过降低 `random_page_cost` 和/或提高 `cpu_tuple_cost` 来鼓励走索引扫描」**——**在 Serializable 场景下调代价参数，目标是【减少谓词锁的升级】，而不只是让查询更快。**

**Q2（计算）**：一个 Serializable 系统，40001 的发生率 `p` 与并发事务数 `C` 近似成正比：`p = 0.001 × C`。

问：**并发从 100 涨到 500 时，系统的「有效吞吐」怎么变？到多少并发时彻底崩溃？**

**A2**：

```text
有效吞吐 ∝ C × (1 − p)        ← 成功的事务才算数

C = 100：p = 0.10 → 100 × 0.90 = 【90】
C = 200：p = 0.20 → 200 × 0.80 = 【160】
C = 400：p = 0.40 → 400 × 0.60 = 【240】
C = 500：p = 0.50 → 500 × 0.50 = 【250】  ← 拐点
C = 800：p = 0.80 → 800 × 0.20 = 【160】  ← 反而下降
C = 1000：p = 1.00 → 1000 × 0 = 【0】     ← 彻底崩
```

【结论】**吞吐先升后降，在 C = 500 附近到顶（250），然后在 C = 1000 归零。** **而且这只算了一阶效应**——**重试本身也占并发，所以真实拐点会比这个更早。**

【推论】**这是正反馈**：

```text
并发上升 → 冲突率上升 → 失败变多 → 重试变多 → 并发进一步上升 → ...
```

【判据】**所以重试策略必须带**：

> **退避 + 抖动（避免同步重试）+ 上限（避免无限循环）+ 全局并发限制（避免正反馈失控）。**

【补充】**这也是官方那条「控制活跃连接数，必要时用连接池」的来历**——**在 Serializable 场景下，连接池不只是资源管理，它是【防止正反馈】的闸门。** **把 `p` 摁在低位，比把重试写得再花哨都管用。**

**Q3（计算 + 判读）**：谓词锁表内存不足，系统把某事务的 **50 个页级锁**合并成 **1 个整表锁**。

问：**这个事务的冲突面变化了多少倍？**（表 200 万页）

**A3**：

```text
升级前：50 个页级锁
  → 冲突面 = 50 / 2,000,000 = 【0.0025%】的表

升级后：1 个整表锁
  → 冲突面 = 【100%】的表

倍数：1 ÷ 0.0025% = 【40,000 倍】
```

【结论】**内存不够的一次合并，让冲突面扩大了 4 万倍。** **这就是官方那句「序列化失败率会上升」背后的量级。**

【推论】**判据与动作**：

> **误报率突然上升，最先该查的是「谓词锁是不是被合并了」**——**看 `pg_locks` 里 `SIReadLock` 的粒度（页级还是关系级），再把 `max_pred_locks_per_transaction` / `max_pred_locks_per_relation` 调大。**

【取舍】**这是一笔明确的交易**：**调大参数 = 用内存换更低的误报率。** **而如果不调，系统会在压力最大的时候（锁表最紧张时）误报最多——**这是最糟的时机**。**所以这类参数应该在压测时就定下来，而不是等线上出问题。**

**Q4（纠错）**：下面这段话哪里不准确？

> "上了 Serializable 之后开始零星报错，说明这个级别不适合我们。降回 RC 就好了。"

**A4**：三处问题。

1. **报 40001 是 Serializable 的契约，不是故障**：**官方明确说「环境必须有一套统一的序列化失败处理方式，因为序列化失败总是以 `40001` 返回」**——**它从一开始就假设你会重试。**
2. **降回 RC 是有代价的，只是代价变得不可见**：**RC 下没有 40001，但那不是"没问题"，是"问题不报错"**——**跨行不变量会被悄悄破坏**（[[母题-P8-隔离级别与读一致性]] 的 Q3 算过这笔账）。
3. **「零星」恰恰说明它在正常工作**：**失败率低说明冲突少，这正是 SSI 最划算的场景**。**真要降级，判断依据应该是「业务操作不可重试」或「冲突率高到重试成本超过加锁」，而不是「它报错了」。**

【准确说法】"**40001 是「让你重来一次」的信号。** **先给重试加上退避、上限与幂等保证；再看失败率是不是高得不正常——如果高，先查谓词锁有没有升级到整表级，而不是把级别降回去。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "为了保证正确性，我们上了 Serializable，同时把所有关键更新都改成了 `SELECT ... FOR UPDATE`，双保险。"

**A5**：三处问题。

1. **这是把两套代价都付了**：**官方明确建议「消除那些因为 Serializable 已自动提供保护而不再需要的显式锁 / `FOR UPDATE` / `FOR SHARE`」**。
2. **`FOR UPDATE` 会带来 SSI 本来没有的问题**：**它会阻塞其他事务、可能造成死锁，而且官方指出它「还会带来磁盘访问」**（必须去读最新版本）。**等于把 PG 用 SSI 换掉的东西又请回来了。**
3. **它不提高正确性，只降低并发**：**Serializable 已经覆盖了跨行不变量的检测**，**再加 `FOR UPDATE` 是重复保护**——**额外的锁只会增加死锁概率与等待时间。**

【准确说法】"**要么用 SSI，要么用显式锁，不要叠。** **上了 Serializable 之后，正确的动作是【删掉】那些不再需要的 `FOR UPDATE`——这一步能直接换回吞吐。**"

## 三、面试输出（学完再看）

**一句话结论**：PG 的 Serializable 用的是 **SSI**——**在快照隔离之上检测「读写依赖环」，一旦发现就主动让其中一个事务失败（`40001`）**。**它的谓词锁【不阻塞、也不可能造成死锁】**（官方原话），在 `pg_locks` 里以 **`SIReadLock`** 出现——**所以它的代价从来不是"到处加锁变慢"，而是"监控开销 + 中止率"。** **一整套失败是设计出来的契约，不是异常**：官方明确说「环境必须有统一的 40001 处理方式」，**而正确做法是【重试整个事务】**——因为 SSI 失败意味着**你读到的快照已经不可信，重试那一条语句没有意义**。**而且失败可能发生在 `COMMIT`**，所以 `COMMIT` 必须在重试范围内。**误报有明确的机械原因**：谓词锁为了不撑爆内存会**升级**（默认 **每页超 2 行 → 整页锁；每表超 32 页 → 整表锁**，即**读 264 KB 就把整张表标成"读过"**），**一次顺序扫描一定拿整表锁**——**所以在 Serializable 下建索引不只是为了快，是为了降低 40001 率。** 重试必须**带退避 + 抖动 + 上限 + 并发限制**，因为**失败率随并发上升、重试又增加并发，这是一个有明确崩溃点的正反馈**（`p = 0.001C` 时 C=1000 吞吐归零）。**最后一句是关键**：**SSI 要求业务可重试，而可重试的前提是副作用可幂等——所以"能不能上 Serializable"是一个幂等设计问题，不是数据库配置问题。**

**恢复关键词**：SSI / 依赖环 / **谓词锁不阻塞、不造成死锁** / `SIReadLock` / **升级规则：每页 2 行 · 每表 32 页（=64÷2）** / **读 264 KB → 整表锁** / **顺序扫描必然拿整表锁** / `max_pred_locks_*` / 40001 是契约 / **重试整个事务** / **COMMIT 也会失败** / `40P01` vs `40001` vs `23505` / `SERIALIZABLE READ ONLY DEFERRABLE` / 唯一冲突的协议一致性 / **幂等是前提**

**核心不变量 / 主线**：
**Serializable 的成本不在执行速度，在「失败与重试」。**
**所以选择它的前提不是「我的 SQL 快不快」，而是「这个业务操作本身可不可以重试」——可重试，SSI 就是最省心的可串行化；不可重试，就该用显式锁。**

**完整回答骨架**：SSI 检测依赖而不是加锁（所以不阻塞、不死锁）→ **谓词锁的升级规则（算 264 KB / 4 万倍）** → 所以会失败 → **40001 与另外两类错误的分类处置** → **重试整个事务、且 COMMIT 也要包进来** → **重试的四个要素与正反馈的崩溃点** → 与悲观锁的取舍 → 收束到「这是一个幂等设计问题」

**追问**（先说后看）

1. **写偏斜是什么，为什么 RC/RR 拦不住？** —— 两个事务**各读一部分数据、各写另一部分**，**各自的读集与写集不重叠**，所以快照隔离看不出问题，**但合起来破坏了一个跨行的不变量**。**只有 SSI 能自动拦住它**，否则要靠显式锁或约束。
2. **能不能不用 SSI，只用 `SELECT ... FOR UPDATE` 保证正确？** —— **能，但必须保证「读的时候也加锁」**——**只给写加锁的「先查再写」在 RC 下有竞态**。**RuleArena 走的是条件更新而不是「读也加锁」这条路**（项目文档 04 §15：**MVP 优先业务唯一键 + 条件更新**）——**理由是「锁不能成为资金正确性的唯一保证」**，**不是「用不了锁」**。**而一旦读也加锁，你就回到了"锁 + 等待 + 死锁"的老世界。**
3. **重试会不会把压力放大成雪崩？** —— **会，而且是正反馈**（Q2 的算式：C=1000 时吞吐归零）。**所以正确写法必须带退避 + 抖动 + 上限 + 全局并发限制。** **能说出「重试也要限流」，就超出教科书答案了。**
4. **`SERIALIZABLE READ ONLY DEFERRABLE` 是什么意思？** —— **只读事务声明可延迟启动，它会【阻塞】到一个"保证不会因序列化失败"的快照可用为止。** **官方明确指出：这是唯一一种 Serializable 会阻塞、而 RR 不会的情况。** **报表类长只读事务想彻底免重试，这是标准做法——**而且它通常能在启动时就确定这个事实，**从而根本不拿谓词锁**。
5. **怎么判断该不该上 Serializable？** —— 先问三件事：**① 有没有跨行不变量（没有就不用上）；② 业务操作可不可重试（不可重试就别用 SSI，用锁）；③ 冲突频率有多高（很高时重试成本可能超过加锁）**。**三个问题问完，答案自己出来。**
6. **线上 40001 突然变多，怎么排查？** —— **三个方向**：**① 看 `pg_locks` 里 `SIReadLock` 的粒度**（是不是升级成关系级了 → 调 `max_pred_locks_*`）；**② 看有没有新出现的顺序扫描**（→ 它一定拿整表锁，鼓励走索引）；**③ 看有没有事务变长或连接数上涨**（→ 正反馈的前兆）。**这三个方向都是从机制推出来的，不是猜。**

**同类变体**

- 「MySQL 的 Serializable 和 PG 的差多少？」—— **MySQL 靠加锁 + 间隙锁实现，通常表现为【等待与超时】；PG 靠 SSI【主动报错】**。**「MySQL 上到 Serializable 会变慢」和「PG 上到 Serializable 会开始报错」是两种不同的现象**，**这是能直接体现你真用过 PG 的一处差异**。
- 「SSI 的误报能不能彻底消除？」—— **不能，只能压到可接受范围**。**因为升级规则本身就是「用内存换精度」，而内存永远有限。** **能做的是：把热点查询压到 32 页以内、调大谓词锁参数、把只读事务声明成 `READ ONLY`。**
