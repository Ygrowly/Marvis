# 母题 P9 · 序列化失败与重试

> **模块**：PostgreSQL / 事务与锁
> **所属主线**：三 · 事务与锁（并发改同一份数据，为什么不会乱）
> **关联母题**：[[母题-P8-隔离级别与读一致性]] · [[母题-P10-无间隙锁与锁变体]]
> **素材来源**：`study/09-数据缓存队列与一致性` 第 2.2 节 + 通用知识（**SSI 细节待你核对**）

**题目**：把隔离级别提到 Serializable 之后，接口开始零星报 `could not serialize access due to read/write dependencies`。这是「不能用」还是「设计如此」？

**母题**：为什么 Serializable 会失败？应用层怎么处理才正确？

**为什么重要**：这是**「PG 的并发哲学」最集中的一课**。MySQL 的思路是「加锁等一等，尽量别让你失败」；**PG 的思路是「用快照保证正确，冲突了就直接告诉你，你自己重试」**。**把「失败」理解成缺陷而不是契约，就会做出错误的技术判断**——比如「把隔离级别降回去」或「加锁硬扛」，这两条都比正确重试更糟。

**一句话结论**：PG 的 Serializable 用的是 **SSI（Serializable Snapshot Isolation）**：它在快照隔离之上**检测可能导致非可串行化结果的读写依赖环**，一旦发现就**主动让其中一个事务失败**（SQLSTATE `40001`）。**所以失败是设计的一部分，不是异常**——正确做法是**在应用层捕获 40001、重试整个事务**（带退避和上限），而不是重试单条语句。

**恢复关键词**：SSI / 读写依赖与依赖环 / 40001 / **重试整个事务** / 幂等 / 与悲观锁取舍 / 误报

**核心不变量 / 主线**：
**Serializable 的成本不在执行速度，在「失败与重试」。** 所以选择它的前提不是「我的 SQL 快不快」，而是**「这个业务操作本身可不可以重试」**——可重试，SSI 就是最省心的可串行化；不可重试，就该用显式锁。

**完整回答骨架**：PG 怎么做到可串行化（SSI 检测依赖而不是加锁）→ 所以会失败 → 失败的错误码与语义 → 正确的处理方式（重试整个事务）→ 与悲观锁的取舍 → 一个前提检查清单

## 原理分解

### 一、SSI 是怎么做到可串行化的

传统可串行化靠**两阶段锁**（锁到事务结束），代价是并发度低、容易死锁。PG 走另一条路：

```
① 先按快照隔离执行，读不加锁 —— 大部分事务根本不会冲突
② 在后台记录事务之间的「读写依赖」（谁读了谁写的数据）
③ 如果发现依赖形成一个环 —— 就不可能存在任何串行顺序 → 报错并干掉其中一个
```

**关键在「② 只记录依赖，不是拦住操作」**：所以**没有冲突的事务完全没有额外等待**。只有真的出现环时才失败。

**代价有两个**：

1. **可能误报**：SSI 的检测是保守的，某些理论安全的场景也会被判失败——**所以它是「宁可我报错，不给你错结果」。**
2. **失败是概率性的**：同一批事务，跑两次可能一次成功一次失败——**这让「重试」变成必须，而不是可选。**

### 二、错误长什么样，怎么识别

```
ERROR: could not serialize access due to read/write dependencies among transactions
DETAIL: Reason code: Canceled on identification as a pivot...
SQLSTATE: 40001
```

**判断这件事要用错误码（`40001`），不要用错误文本匹配**——文本会随版本/语言变化，**错误码是契约**。同一个 `40001` 也会由 RR 下的写冲突产生（P8），语义都是「**重试就能成功**」。

**要区分的三类错误**：

| 错误 | 语义 | 处理 |
|---|---|---|
| `40001`（序列化失败 / 快照过期） | **可重试**：重放事务大概率成功 | **重试整个事务** |
| `40P01`（死锁） | 也可重试，但说明**加锁顺序有问题** | 重试 + **修加锁顺序** |
| 约束冲突（`23505` 等） | **确定性失败**，重试也没用 | 不要重试，走业务分支 |

**这个三分法比「统一重试三次」重要得多**——**对确定性错误无脑重试，是在制造重复副作用。**

### 三、正确的重试长什么样

**必须是「整个事务」，不是「那一条语句」**：

```
① 记录本次事务的输入（幂等键）
② BEGIN
③ 执行全部读与写
④ COMMIT
   └─ 若报 40001 → 回滚 → 重新执行 ③（用同样的输入）
```

因为 SSI 失败意味着**「你读到的那个快照已经不可信」**——**重试那一条语句没有意义，必须重新读。**

**四条要求**：

- **带退避 + 抖动**：并发高时同步重试会互相打架，越试越糟；
- **有重试上限**：超过就暴露成失败/未知，不要无限循环；
- **整个事务幂等**：重试不能产生第二次副作用——所以**必须有幂等键或唯一约束兜底（P18/P19）**；
- **保留 trace**：记录重试次数，它是「并发竞争激烈程度」的直接指标（可以直接做监控）。

**反过来讲最重要的一句**：**SSI 要求业务可重试；而「可重试」的前提是副作用可幂等。** 所以「能不能上 Serializable」其实是一个**幂等设计问题**，不是一个数据库配置问题。**这句话是这道题的分水岭。**

### 四、跟其他方案比

| 方案 | 机制 | 适合 | 代价 |
|---|---|---|---|
| **Serializable（SSI）** | 检测依赖环 → 报错重试 | **冲突低但需要跨行不变量**、业务可重试 | 可能误报；要求重试框架 |
| **RR / RC + `FOR UPDATE`** | 悲观锁，冲突就排队 | **冲突高、临界区短**、业务不好重试 | 锁等待、死锁风险、吞吐下降 |
| **条件更新（乐观，P18）** | 判断与写入合并为一条语句 | 冲突低、单行不变量 | **不能直接保护跨行不变量**（要靠约束） |
| **唯一约束（P19）** | 数据库原子性 | **幂等与重复的最终防线** | 只覆盖「重复」，不覆盖「顺序」 |

**取舍判据**：**能不能重试 → 能就用 SSI/乐观；冲突频率高到重试成本超过加锁成本 → 才用悲观锁。** 这条判据和 MySQL 那边（M14 乐观锁 vs 悲观锁）是同一句话，只是 PG 多了一层「SSI 帮你自动检测」。

## 二、扩展：类似题与追问

**类似题**

1. 「写偏斜是什么，为什么 RC/RR 拦不住？」——两个事务各读一部分数据、各写另一部分，**各自的读集与写集不重叠**，所以快照隔离看不出问题，但**合起来破坏了一个跨行的不变量**。**只有 SSI 能自动拦住它**，否则要靠显式锁或约束。
2. 「能不能不用 SSI，只用 `SELECT ... FOR UPDATE` 保证正确？」——能，但**必须保证「读的时候也加锁」**——只给写加锁的「先查再写」在 RC 下有竞态（这正是 RuleArena 不用 FOR UPDATE 的原因）。
3. 「`SERIALIZABLE READ ONLY DEFERRABLE` 是什么意思？」——只读事务声明可延迟启动，**它会等到一个「安全快照」再开始**，从而保证一定不会因序列化而失败。**报表类长只读事务想彻底免重试，这是标准做法**——知道这一条会显得非常扎实。

**追问链**

- 追问一层：**「重试会不会把压力放大成雪崩？」**——会，这是 SSI 在高并发下的真实风险：失败率随并发上升，重试又增加并发。**所以正确写法必须带退避 + 抖动 + 上限 + 全局并发限制**，而不是简单 `while(true) retry()`。**能说出「重试也要限流」，就超出教科书答案了。**
- 追问二层：**「怎么判断该不该上 Serializable？」**——先问三件事：**① 有没有跨行不变量（没有就不用上）；② 业务操作可不可重试（不可重试就别用 SSI，用锁）；③ 冲突频率有多高（很高时重试成本可能超过加锁）**。**三个问题问完，答案自己出来。**
