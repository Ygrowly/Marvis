# 母题 P13 · MVCC 与可见性

> **模块**：PostgreSQL / 长事务
> **所属主线**：五 · 长事务（它为什么危险，为什么拖系统下水）
> **层级**：A · 教材级（版本占用、事务 ID 消耗速率都能算；可见性判定可以从「版本 + 快照」推出来）
> **关联母题**：[[母题-P11-WAL与checkpoint]]（为什么不需要 undo）· [[母题-P14-长事务与表膨胀]]（旧版本什么时候能删）· [[母题-P15-VACUUM与事务ID回卷]]（32 位 ID 的后果）· [[母题-P8-隔离级别与读一致性]]（快照粒度决定看到哪个版本）· [[母题-M9-MVCC]]（MySQL 侧对照）
> **素材来源**：`study/09-数据缓存队列与一致性` 第 2 节（事务与并发）+ **PostgreSQL 官方文档 Concurrency Control / System Columns / Routine Vacuuming**（2026-09-13 联网核实）+ 通用知识。**三组算式与 `xmax` 那个陷阱为本次新增（待你核对）**

**导读**：必懂 3 件事（① **PG 的 `UPDATE` 不做原地修改**——它写一个新行版本，官方原话是「每次更新都会为同一个逻辑行创建一个新的行版本」 ② 可见性靠「行上的两个事务 ID + 一份快照」判定，**读不加锁**——这是「读永不阻塞写」的实现 ③ **死元组必须靠 VACUUM 回收，而且索引里也留着指向死元组的条目**——这是主线五全部问题的源头）· 读完约 12 分钟 · 需要先懂：[[母题-P11-WAL与checkpoint]]

**题目**：PG 的 `UPDATE` 为什么不「改一行」，而是「插一行」？

**母题**：MVCC 在 PG 里怎么实现？`xmin` / `xmax` 与「更新即新版本」意味着什么？

**为什么重要**：这是**整条主线五的地基**——膨胀、VACUUM、事务 ID 回卷这三件 PG 独有的事，**全都是「版本留在堆里」的直接后果**。而且它同时是 P11 那道题的答案（**为什么 PG 不需要 undo**）。**面试官问 PG 的 MVCC，其实是在问「你知不知道代价藏在哪」。**

**一句话结论**：**PG 把每个行版本都留在堆里**，用行的 `xmin`（创建它的事务 ID）和 `xmax`（删除它的事务 ID）+ 当前快照的事务范围判断可见性——**读的时候不改数据、不加锁**。所以 `UPDATE` 实际是「**写一个新版本 + 把旧版本的 `xmax` 标成本事务**」。**代价是死元组必须靠 VACUUM 回收，而且索引里还留着指向旧元组的条目**——这正是表膨胀的根源，也是它和 MySQL「版本链放 undo log、purge 线程自动清理」最大的差别。

**恢复关键词**：`xmin`（插入事务）/ `xmax`（删除事务，**非零不等于不可见**）/ `ctid` **会变，不能当行标识** / 版本留在堆里 / 更新即新版本 + 标记旧版本 / 可见性由快照决定 / 死元组 / **索引也指向死元组** / **普通 VACUUM 不还空间给操作系统** / HOT 更新

**核心不变量 / 主线**：
**PG 的 MVCC 是「绝不动旧数据」的 MVCC。** 收益是**读永不阻塞写、写永不阻塞读**（官方原话）；代价是**空间必须由 VACUUM 回收**——**这就是「PG 为什么必须懂 VACUUM」的全部理由。**
**而「回收」这件事在这里要拆成两个动作：把空间标记为可复用（普通 VACUUM）≠ 把空间还给操作系统（要 VACUUM FULL）。**

**完整回答骨架**：为什么需要多版本 → PG 把版本放在哪（对比 MySQL）→ xmin/xmax 怎么判定可见性 → 更新即新版本意味着什么 → 代价：死元组 + 索引指向旧版本 → HOT 更新是什么 → 收束到「绝不动旧数据」

## 一、教材

### 1. 两种 MVCC：版本放在哪，决定了运维形态

::figure pg-mvcc-versions.svg | 版本留在堆里：更新即新版本与它的三项代价 | 一次更新产生的行版本与索引条目、xmin/xmax 可见性判定的两个条件、xmax 非零的一个陷阱、以及 HOT 更新的条件

| | MySQL（InnoDB） | PostgreSQL |
|---|---|---|
| 版本存在哪 | **undo log**（版本链在回滚段） | **堆里**（每行一个新版本） |
| 更新怎么做 | 就地改当前行，旧值写进 undo | **写一个新版本，把旧版本标记为死** |
| 回收 | **purge 线程自动**、基本无需人工关注 | **VACUUM / autovacuum（可能跟不上）** |
| 读的可见性 | 用 ReadView + undo 链回溯 | 用行的 `xmin`/`xmax` + 快照判定 |
| 需要 undo 日志吗 | 需要 | **不需要**（版本本来就在表里） |

【事实】**官方对 MVCC 收益的表述可以直接背**：

> **MVCC 相比加锁模型的主要优势是：为查询（读取）获取的锁与为写入数据获取的锁不冲突，因此【读永不阻塞写、写永不阻塞读】。**

【结论】**这张表是全库最重要的一张对照表**：**「回收是否自动」这一个差异，直接决定了 PG 有一整套 MySQL 没有的运维课题**（膨胀、VACUUM 调参、事务 ID 回卷、`idle in transaction` 监控）。

### 2. `xmin` / `xmax` 怎么工作

【事实】**官方的定义（可直接引用）**：

| 系统列 | 官方定义 |
|---|---|
| **`xmin`** | **这一行版本的【插入】事务的标识。**（**一个行版本是一行的一个状态；每次更新都会为同一个逻辑行创建一个新的行版本**） |
| **`xmax`** | **【删除】事务的标识，未删除的行版本是零。** |
| `cmin` / `cmax` | 插入 / 删除事务内部的命令序号 |
| `ctid` | **这一行版本在表里的物理位置** |

【纠正常见误解】**`xmax` 非零 ≠ 这行不可见**——官方专门写了这一句：

> **`xmax` 这一列在一个【可见的】行版本上也可能非零。** 这通常说明**删除它的事务还没提交**，**或者那次删除尝试被回滚了**。

【推导】**可见性判定的两个条件**：

```text
读取时手里有一个「快照」——它记录了「哪些事务算已提交、哪些还没」
某个版本对当前快照可见，需要同时满足：

① xmin 的事务已提交，且「在快照之前」
     → 这个版本已经被创建出来了

② xmax 为空，或 xmax 的事务「在快照之后 / 未提交 / 已回滚」
     → 还没被真正删掉
```

【推论】**所以「读」完全不需要动数据、也不需要加锁**——**它只是拿两个事务 ID 和一份快照做比较。** **这就是「读永不阻塞写」的实现方式。**

【事实】**一个容易踩的坑，官方专门提醒**：

> **`ctid` 可以用来很快地定位行版本，但【一行的 `ctid` 在它被更新、或被 `VACUUM FULL` 移动之后就会改变】。**
> **因此 `ctid` 不应该被当作行标识来用；应该用主键来标识逻辑行。**

【推论】**这条直接否掉了两种常见做法**：**① 用 `ctid` 做分页游标**（翻页过程中被更新的行会漏掉或重复）；**② 用 `ctid` 做去重或对账的键**。**它不是稳定标识，只是"当下在第几页第几个位置"。**

### 3. 更新即新版本：一句 `UPDATE` 背后发生了什么

```sql
UPDATE tasks SET status = 'DONE' WHERE id = 42;
```

实际动作：

1. 在堆里**写一个新版本**（`xmin` = 当前事务，新值）；
2. 把**旧版本的 `xmax` 设为当前事务**（标记「被它删掉了」）——**旧版本仍然物理存在**；
3. 更新**所有索引**：索引需要指向**新版本的位置**（`ctid` 变了）；
4. 事务提交后：旧版本对**新**快照不可见，但对**还在用旧快照的事务**（长事务！）仍然可见。

**第 4 步是关键**：**旧版本什么时候能被删，取决于「还有没有人在用能看到它的快照」**——**这就是 P14 的全部机理。**

【推导】**把代价算成数字**：

```text
一行 200 字节，被更新 10 次：
  堆里 = 11 个版本 × 200 B = 【2200 字节】
  而"有效数据"只有 200 字节 → 【11 倍】

每个引用被改列的索引：
  也要有 11 个条目 → 索引同样膨胀 11 倍
  （除非走 HOT —— 见第 5 节）
```

【结论】**「表大小」和「数据量」在 PG 里是两个概念**——**一张更新频繁的表，实际占用可以是有效数据的数倍。**

### 4. 代价：死元组 + 索引也指向它

两个必须记住的后果：

**① 堆会变"胖"**：更新 N 次就有 N 个版本（只有一个活着）。

【事实】**而且「回收」要分成两件事，官方原话**：

> **标准形式的 `VACUUM` 会移除表和索引里的死行版本，并把空间标记为【可供将来复用】。**
> **然而，它【不会把空间还给操作系统】——除非出现特殊情况：表末尾的一个或多个页完全空闲，而且能轻易拿到排他表锁。**

【推论】**「VACUUM 过了，表文件没变小」不是故障，是设计**：

```text
普通 VACUUM  ：把死元组的空间标记为【可复用】
               → 后续的 INSERT/UPDATE 会填进来
               → 表文件大小【不变】

VACUUM FULL  ：重写整张表到新文件，把空间还给操作系统
               → 代价：持【排他锁】、需要等量磁盘空间
               → 官方也说了：Plain VACUUM 在大量死元组时可能不够满意，
                 这种情况才需要 VACUUM FULL 或 CLUSTER
```

【取舍】**所以判据是**：

> **你要的是「别再涨」还是「变小」？**
> **「别再涨」→ 普通 VACUUM + 让 autovacuum 跟得上就够。**
> **「变小」→ 只有 VACUUM FULL / CLUSTER 能做到，而且它们要拿排他锁——这条路的代价通常比"表大"本身更贵**（[[母题-P15-VACUUM与事务ID回卷]]）。

**② 索引也要清理**：B-tree 索引项指向 `ctid`，**旧版本的条目会变成指向死元组的"死索引项"**——VACUUM 必须同时清理堆和索引。

【推论】**所以「索引多 → VACUUM 更累」这件事在 PG 里是机制性的，不是经验之谈**——**这也是 P4 里「PG 的索引第三项代价是 VACUUM 压力」的由来。**

---

### 5. HOT 更新：一个重要的写入优化

**HOT（Heap-Only Tuple）更新**：如果

1. 更新的**列不属于任何索引**（官方补充：**排除 BRIN 这类"摘要索引"**），且
2. 新版本能放进**同一个数据页**里

那么 PG **不需要更新任何索引**——新版本通过页内的指针链和旧版本连起来。

【事实】**它还有第二样收益（常被漏掉）**：**当一行被更新多次时，除最旧和最新之外的中间版本，可以在【正常运行期间（包括 `SELECT`）】被直接移除**，不必等 VACUUM。**所以 HOT 同时减轻了写路径和清理路径**——这是它连到 P14/P15 的那根线。

【实践推论】**不要把频繁更新的列放进索引**（比如状态、计数器、`updated_at`——**如果它不需要用来查询就别索引它**）——**这条是从机制推出来的设计规则，比背「索引不要建太多」有力得多。**

【事实】**这一条可以量化验证**：`pg_stat_all_tables` 里有 `n_tup_upd` 与 `n_tup_hot_upd`，**两者的比值就是 HOT 占比**（[[母题-P4-索引代价与在线建索引]]）。

### 6. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「PG 也有 undo log」 | **明确错误**。**版本留在堆里，这正是它不需要 undo 的原因** |
| 「MySQL 也要 VACUUM」 | **明确错误**。**MySQL 靠 purge 线程自动回收版本链**，没有 VACUUM 这个动作 |
| 「`xmax` 非零说明这行被删了」 | **不一定可见性**——**删除可能还没提交、或已经回滚**（官方原话） |
| 「VACUUM 之后表文件会变小」 | **普通 VACUUM 只把空间标记为可复用**；**要还空间给操作系统得 VACUUM FULL / CLUSTER，且要排他锁** |
| 「可以用 `ctid` 做分页游标或行标识」 | **`ctid` 在更新或被 `VACUUM FULL` 移动后会变**——**官方明确说不该当行标识** |
| 「更新一行只影响一行」 | **堆里多一个版本、每个引用被改列的索引多一个条目** |

## 二、自测

**Q1（计算）**：一行 **200 字节**，被更新 **10 次**。表上有 **4 个索引**，其中 **2 个引用了被更新的那一列**。

问：**这一行在磁盘上占多少？其中有效数据占多少？如果那一列不在任何索引里（且走 HOT），结论怎么变？**

**A1**：

```text
堆：
  11 个版本 × 200 B = 【2200 字节】
  有效数据 = 200 字节
  → 占用是有效数据的 【11 倍】

索引：
  2 个引用被改列的索引，各多 10 个条目
  → 假设每个索引项 24 B：2 × 10 × 24 = 【480 字节】
  （另外 2 个索引不受影响，因为它们的列没变）
```

【结论】**一次逻辑上的「改一行」，在磁盘上留下的是 11 个行版本 + 20 个索引条目。**

【如果走 HOT】：

```text
改的列不在任何索引里 → 只写堆（2 个索引也不动）
  堆占用不变（2200 字节）
  索引：【完全不增长】
  而且中间版本可以在正常运行时被就地清掉（不必等 VACUUM）
```

【推论】**判据**：

> **在 PG 里，「更新一行」的成本，取决于【被更新的列出现在几个索引里】。**
> **所以「高频更新的列不进索引」这条设计规则，省的不只是写入，还有【索引膨胀】和【VACUUM 负担】。**

【补充】**这一条是可观测的**：**查 `pg_stat_all_tables` 的 `n_tup_hot_upd / n_tup_upd`**——**HOT 占比低，说明有更新的列被索引引用了，值得回头看一眼那几个索引是不是真的非要不可。**

**Q2（计算）**：某实例稳定 **500 TPS**（每个事务消耗一个事务 ID）。假设 **VACUUM 完全停摆**。

问：**事务 ID 大约多久会逼近回卷保护？**为什么 `autovacuum_freeze_max_age` 默认只有 **2 亿**（官方说这是"相对低"的值）？

**A2**：

```text
事务 ID 是 32 位，可用范围约 2^31 ≈ 【21 亿】

21 亿 ÷ 500 TPS = 4.2 × 10⁶ 秒 ≈ 【48.6 天】

也就是说：如果冻结完全停摆，
不到两个月就会撞上回卷红线
```

【结论】**「事务 ID 用完」在 500 TPS 下是一个【以月计】的量级**——**它不是理论问题，是一个有具体倒计时的运维约束。**

【推论】**这正好解释了官方为什么把 `autovacuum_freeze_max_age` 定在 2 亿**：

```text
2 亿 ÷ 21 亿 ≈ 总空间用了【不到 10%】
→ 每张表最多用掉事务 ID 空间的一小段
→ 留出巨大的余量给别的表、给突发负载

官方原文也给了另一个理由：
  「VACUUM 还允许从 pg_xact 子目录里移除旧文件，
    这就是为什么默认值是一个【相对低的】2 亿事务。」
```

【补充】**官方还给了两条相关默认值**：**`vacuum_freeze_table_age` 默认 1.5 亿**（**它的有效上限被限制为 `0.95 × autovacuum_freeze_max_age`**），**`vacuum_freeze_min_age` 默认 5000 万**（**超过它才冻结**）。**这三个数字构成了一条"什么时候开始冻、什么时候强制冻"的阶梯。**

【事实】**一个必须记住的官方原话**：

> **一张表可以不被 VACUUM 的最长时间，是【20 亿个事务】减去上次激进 VACUUM 时的 `vacuum_freeze_min_age`。如果超过这个时间还没有被 VACUUM，【就可能造成数据丢失】。**

**「可能造成数据丢失」——这是 PG 里唯一一处会因运维不到位而丢数据的机制。**

**Q3（计算）**：一张表 **1000 TPS** 在更新。一个 `REPEATABLE READ` 事务在 **1 小时前**开始，现在还没提交。

问：**这个事务让多少行版本无法被回收？后果是什么？**

**A3**：

```text
这个事务的快照固定在它开始那一刻
  → 它之后产生的所有旧版本，都对它【仍然可见】
  → 因此【都不能被 VACUUM 回收】

压住的版本 ≈ 1000 × 3600 = 【360 万个】
```

【结论】**一个 1 小时的长事务，压住 360 万个行版本**——**而且它们不只是堆里的 360 万个槽位，还会复制到每个索引里。**

【推论】**判据**：

> **在 PG 里，一个事务的【时长】直接等于它给整张表造成的膨胀量。**
> **所以「事务要短」在 PG 里不是风格建议，是有明确数量关系的运行要求。**

【补充】**这条还解释了为什么 `idle in transaction` 特别危险**：**一个"开着事务什么都不干"的连接，和一个"忙了一小时的只读事务"对回收的阻塞效果完全一样**——**所以它是必须监控的状态**（[[母题-P14-长事务与表膨胀]]）。

**Q4（纠错）**：下面这段话哪里不准确？

> "PostgreSQL 的 MVCC 和 MySQL 差不多，都是靠 undo log 保存旧版本，只是清理策略不同。"

**A4**：三处问题。

1. **PG 没有 undo log**：**版本就留在堆里**——**官方原话是「每次更新都会为同一个逻辑行创建一个新的行版本」**。**「PG 也有 undo log」是明确错误。**
2. **「差不多」掩盖了运维形态的质变**：**MySQL 靠 purge 线程自动回收，基本不用人工关注**；**PG 靠 VACUUM / autovacuum，而它会跟不上**——**由此才有一整套 MySQL 不存在的课题**（表膨胀、VACUUM 调参、事务 ID 回卷、`idle in transaction` 监控）。
3. **连「空间怎么还」都不一样**：**PG 的普通 VACUUM 只把空间标记为可复用，不还给操作系统**——**要还空间得 VACUUM FULL，而那要拿排他锁。**

【准确说法】"**两边都是 MVCC，但版本放在哪决定了运维形态**：**MySQL 把旧版本放在 undo 里、由 purge 自动清；PG 把版本留在堆里、必须靠 VACUUM 清。** **所以 PG 的 DBA 有一半时间在跟膨胀打交道，而 MySQL 那边基本不用。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "这张表删了很多数据，我跑一次 `VACUUM` 它就变小了。"

**A5**：三处问题。

1. **普通 `VACUUM` 不会让文件变小**：**官方原话是「它会把空间标记为可供将来复用，但不会把空间还给操作系统」**——**所以跑完 `VACUUM` 之后 `pg_relation_size` 基本不变。**
2. **要变小得用 `VACUUM FULL` 或 `CLUSTER`**，**而这两者都要拿【排他表锁】**——**期间这张表不可读写，而且要额外的等量磁盘空间**。
3. **而且 `VACUUM FULL` 本身会产生大量 WAL**：**它把整张表重写到新文件**——**在一个已经很忙的实例上，这可能比"表大"本身更麻烦。**

【准确说法】"**先问你要的是哪个**：**如果目标是「别再涨」，普通 VACUUM 让 autovacuum 跟得上就够了；如果目标是「变小」，只能 VACUUM FULL / CLUSTER，而那是一次带排他锁的重写。** **大多数情况下，把 autovacuum 调好比事后 VACUUM FULL 划算得多。**"

## 三、面试输出（学完再看）

**一句话结论**：**PG 的 MVCC 是「绝不动旧数据」的 MVCC**——**版本留在堆里**，用行上的 `xmin`（**插入事务**）和 `xmax`（**删除事务**）配合一份快照判定可见性，**读不加锁**。**所以 `UPDATE` 实际是「写一个新行版本 + 把旧版本的 `xmax` 标成本事务」**——**官方原话是「每次更新都会为同一个逻辑行创建一个新的行版本」。** 收益是**读永不阻塞写、写永不阻塞读**（官方原话）；代价有两条：**① 死元组必须靠 VACUUM 回收，而普通 VACUUM 只把空间标记为【可复用】、不还给操作系统**（要还空间得 `VACUUM FULL` / `CLUSTER`，且要排他锁）；**② 索引里也留着指向死元组的条目**——**所以「索引多 → VACUUM 更累」在 PG 里是机制性的**。**一个 200 字节的行更新 10 次，堆里就是 11 个版本共 2200 字节（11 倍），被改列所在的每个索引也各多 10 个条目。** **HOT 更新是 PG 的免费通道**：**只要改的列不在任何索引里、且新版本能放进同一页，索引一个都不用碰**——**而且中间版本还能在正常运行时被就地清掉**——**所以「高频更新的列不进索引」是一条从机制推出来的设计规则**，可以用 `pg_stat_all_tables` 的 HOT 占比验证。**最后两个要记住的坑**：**`xmax` 非零不表示这行不可见**（删除可能没提交或已回滚）；**`ctid` 会变、不能当行标识**（官方明确说应该用主键）。**而这一切的底层约束是：事务 ID 只有 32 位——500 TPS 下，冻结停摆约 48.6 天就会逼近回卷。**

**恢复关键词**：**版本留在堆里** / `xmin` = 插入事务 · `xmax` = 删除事务 / **`xmax` 非零 ≠ 不可见** / **`ctid` 会变，不能当行标识** / 更新即新版本 + 标旧版本 / **读永不阻塞写** / 死元组 / **索引也指向死元组** / **普通 VACUUM 只标可复用、不还空间** / `VACUUM FULL` / **HOT：列不在索引里 + 同页放得下** / 200 字节 × 10 次 = 11 倍 / **21 亿 ÷ 500 TPS ≈ 48.6 天**

**核心不变量 / 主线**：
**PG 的 MVCC 是「绝不动旧数据」的 MVCC。**
**收益是读永不阻塞写；代价是空间必须由 VACUUM 回收——这就是「PG 为什么必须懂 VACUUM」的全部理由。**

**完整回答骨架**：两种 MVCC 版本放哪 → **xmin/xmax 与可见性两个条件（含 `xmax` 非零的陷阱）** → 更新即新版本（**算 11 倍**）→ **两项代价（堆变胖 + 索引指向死元组）** → **「标记可复用」≠「还空间」** → HOT 的两样收益 → 收束到「绝不动旧数据」

**追问**（先说后看）

1. **既然旧版本还在表里，那读的时候怎么知道该读哪个？** —— 按快照判定 `xmin`/`xmax`：**同一个事务读同一个快照，看到的就是同一批版本**。**这也解释了 P8 那个反直觉现象**——**RC 下每条语句换一次快照，所以能看到不同版本；RR 下共用一个快照，所以结果一致。** **P8、P13 是同一件事的两个面。**
2. **`xmin`/`xmax` 是 32 位事务 ID，会不会用完？** —— **会，这就是事务 ID 回卷**（[[母题-P15-VACUUM与事务ID回卷]]）。**32 位 ID 循环使用，所以必须靠【冻结】标记"这行很老、一定可见"**；**清理长期跟不上，就可能出现"老数据被误判成未来才可见"的灾难。** **PG 的应对是：先告警，最后拒绝新事务，强制进入维护模式**——**「宁可停机也不出错数据」这个取舍本身就是很好的面试谈资。** **而且官方的说法很硬：一张表最多可以 20 亿事务不被 VACUUM，超过就【可能造成数据丢失】。**
3. **PG 的读会不会被写阻塞？** —— **不会**（读不加锁）；**但 `ALTER TABLE` 这类 DDL 会拿表锁**（[[母题-P4-索引代价与在线建索引]]），**那会阻塞。**
4. **为什么 PG 的表「更新一次就变大一次」？** —— **没有原地更新，旧版本还在**；**空间要等 VACUUM**。**而且「VACUUM 过」不等于「变小了」**——**它只是把空间标记为可复用。**
5. **PG 有 `SELECT ... FOR UPDATE` 就说明读要加锁吗？** —— **不，那是显式加锁**（[[母题-P10-无间隙锁与锁变体]]），**默认的读不加任何锁**。

**同类变体**

- 「HOT 为什么在 PG 里这么重要？」—— **因为它把「一次更新要改所有索引」降级成「只写堆」**，**并且让中间版本能在正常运行中被清理**。**它是 PG 在高频更新表上最有效的内置优化**，**而且它的生效条件直接变成了一条表设计规则**（高频更新的列不进索引）。
- 「`ctid` 能拿来做什么、不能做什么？」—— **能**：**定位行版本、诊断页分布（`ctid` 的块号分布能看出表有没有物理碎片）**。**不能**：**当行标识、当分页游标、当对账键**——**官方明确说应该用主键标识逻辑行。**
