# 母题 P7 · 统计信息与慢查询定位

> **模块**：PostgreSQL / SQL 执行与优化
> **所属主线**：二 · SQL 执行与优化（一条 SQL 怎么走、慢在哪）
> **层级**：A · 教材级（三类偏差原因都能从「优化器拿什么算」推出来，阈值与桶数都能算；不需要先背结论）
> **关联母题**：[[母题-P6-执行计划怎么看]]（先看到偏差才能修）· [[母题-P3-部分索引与表达式索引]]（表达式条件的解法）· [[母题-P15-VACUUM与事务ID回卷]]（清理与统计是两条独立的阈值）· [[母题-P12-流复制与逻辑复制]]（只读副本的统计信息也要更新）
> **素材来源**：`archive/study-courses/09-数据缓存队列与一致性` 第 3.4 节 + **PostgreSQL 官方文档 Statistics Used by the Planner / CREATE STATISTICS / ANALYZE / Autovacuum 配置 / plan_cache_mode**（2026-09-13 联网核实）+ 通用知识。**三组算式为本次新增（待你核对）**

**导读**：必懂 3 件事（① 优化器不是猜，是**拿统计信息算代价** ② 它有一个写死的假设：**多个条件是相互独立的**——相关性数据上这个假设直接让估算错几百倍 ③ 大表的 autovacuum `ANALYZE` 阈值按**行数比例**算，**几千万行的表可能几小时才更新一次统计**）· 读完约 12 分钟 · 需要先懂：[[母题-P6-执行计划怎么看]]

**题目**：优化器把「只返回 10 行」的条件估成了 100 万行，于是选了 `Seq Scan`。你要不要直接加个索引？

**母题**：估计行数与实际行数差很多说明什么？怎么修？线上的慢查询怎么第一时间定位？

**为什么重要**：这是**「加索引」和「修信息」的分界线**。上一题的例子已经说明——**优化器不是一个会犯傻的黑盒，它是在用你给它的统计信息算代价**。估错说明「给它的信息不对」，这时候加索引是**治症状**：统计信息还是错的，下一个查询照样选错。**能区分这两件事，是「会看计划」和「会调数据库」的差别。**

**一句话结论**：偏差来自三类原因——**统计信息过期、列之间有关联但统计假设独立、条件是表达式或函数**；对应三种修法——**`ANALYZE`（或调 autovacuum 的 analyze 阈值）、`CREATE STATISTICS` 建扩展统计、建表达式索引或改写 SQL**。定位慢查询的第一站是 **`pg_stat_statements`**（按总耗时排序，先治「最贵的」），再对单条用 `EXPLAIN (ANALYZE, BUFFERS)`。

**恢复关键词**：pg_stat_statements / ANALYZE / autovacuum analyze 阈值（50 + 10%）/ n_distinct 与 MCV / 直方图桶数 / **独立假设** / CREATE STATISTICS（ndistinct · dependencies · mcv）/ 表达式与函数 / generic plan 陷阱

**核心不变量 / 主线**：
**优化器不是在猜，它是在拿统计信息算代价。** 所以「计划不对」的排查顺序永远是：**先问信息对不对，再问 SQL 形状对不对，最后才问索引够不够。**

**完整回答骨架**：统计信息从哪来、估什么 → **三类偏差原因与三种修法（各算一笔）** → 定位慢查询的工具链（pg_stat_statements → EXPLAIN ANALYZE）→ 一个隐蔽陷阱（generic plan）→ 优化顺序

**完整回答（口述稿）**：
**偏差来自三类原因**：**统计信息过期**、**列之间有关联但统计假设独立**、**条件是表达式或函数**。对应**三种修法**：`ANALYZE`（或调 autovacuum 的 analyze 阈值）、**`CREATE STATISTICS` 建扩展统计**（把列间关联告诉规划器）、**建表达式索引或改写 SQL**。

**定位慢查询的第一站是 `pg_stat_statements`**（按总耗时排序，**先治"最贵的"**，而不是先治"单次最慢的"）；再对单条用 `EXPLAIN (ANALYZE, BUFFERS)` 定位到底哪一步慢。

和 MySQL 对照：MySQL 侧靠慢查询日志 + `ANALYZE TABLE` 更新统计，8.0 也有直方图；PG 的统计体系更完整（扩展统计、直方图、`pg_stat_statements`）——**这是 PG 在"为什么选错计划"这件事上比 MySQL 更好排查的原因**。

**分层要点**：
- **结论**：三类偏差对应三种修法；先按总耗时排优先级，再对单条用 ANALYZE+BUFFERS。
- **推导链**：估算偏差 → 过期/关联/表达式 → 三种修法 → pg_stat_statements 排序 → 单条深挖。
- **量化**：排序口径是"总耗时 = 单次耗时 × 调用次数"。
- **边界与常见误解**：只看"单次最慢"会治错对象；扩展统计是 PG 比 MySQL 多出来的一类修法。

## 一、教材

### 1. 统计信息从哪来、估什么

::figure pg-stats-and-slowlog.svg | 统计信息的三类偏差与定位慢查询的两站路 | 优化器拿什么算代价、三类偏差的成因与修法、autovacuum 阈值算式、pg_stat_statements 的排序原则

PG 的 autovacuum 进程顺带做 `ANALYZE`，**对表取一个随机样本**（不是全表），记录每个列的：

- **`n_distinct`**：不同值大约有多少个；
- **MCV（most common values）**：出现频率最高的若干个值和它们的频率（**用来处理数据倾斜**）；
- **直方图**：其余值的分布。

【事实】**两句官方定性，决定了整道题的基调**：

> **`pg_statistic` 里的条目是由 `ANALYZE` / `VACUUM ANALYZE` 更新的，而且【即使刚刚更新过，它也总是近似的】。**

> **优化器【通常假设多个条件之间相互独立】——这个假设在列值相关时不成立。常规统计是「每列各自」的，捕捉不到任何跨列相关性。**

【推导】**乘法就埋下了第一个大坑**：

```text
优化器拿到 city 的分布 和 district 的分布
  → 它【相乘】得到「city = 北京 AND district = 海淀」的选择率

这个乘法只有在两列独立时才成立
  而实际上：海淀一定在北京——两者强相关
  → 相乘的结果严重偏离真实值（见 Q2 的算式）
```

**到这里你应该能回答**：为什么「统计信息里每一列都是准的」，仍然可能得出一个错得离谱的估算？

### 2. 偏差的三类原因与三种修法

| # | 原因 | 表现 | 修法 |
|---|---|---|---|
| 1 | **统计信息过期** | 刚导入大批数据、刚大批删除后，估算明显偏离 | **`ANALYZE` 该表**；**把 autovacuum 的 analyze 阈值调低**（大表默认阈值触发太晚，见下） |
| 2 | **列间相关** | 一个条件估得挺准，**两个条件一乘就错得离谱** | **`CREATE STATISTICS` 建扩展统计**，让优化器知道它们不独立 |
| 3 | **表达式 / 函数** | `WHERE lower(name) = ?`、`WHERE date(created_at) = ?` 这类条件**无法用列统计估算** | 建**表达式索引**（[[母题-P3-部分索引与表达式索引]]），**或改写 SQL 去掉函数** |

【推导】**为什么大表的 auto-analyze 总是慢半拍——把阈值算出来**

```text
官方口径：触发 ANALYZE 的条件
  变化的元组数 > autovacuum_analyze_threshold
               + autovacuum_analyze_scale_factor × 表行数

默认值：threshold = 50，scale_factor = 0.1（10%）

对一张 8000 万行的表：
  50 + 0.1 × 80,000,000 = 【800 万行】

也就是说：要改动 800 万行，才会自动重新统计一次。
若写入 500 TPS：
  8,000,000 ÷ 500 = 16,000 秒 ≈ 【4.4 小时】
```

【结论】**统计信息的「保鲜期」是小时级的，而业务的一次批量导入会让它当场失效。**

【推论】**所以「大表导入完数据必须手动 `ANALYZE`」不是洁癖，是刚需**——**你在等一个 4.4 小时才回来的后台进程来修一个此刻正在拖慢线上查询的问题。**

【事实】**扩展统计精确支持三种**，`CREATE STATISTICS` 可指定（不指定则全带）：

| 类型 | 名字 | 解决什么 |
|---|---|---|
| **函数依赖** | `dependencies` | 一列能决定另一列（海淀 → 北京） |
| **多列 n_distinct** | `ndistinct` | 组合起来有多少个不同值（做 GROUP BY 估算） |
| **多列 MCV** | `mcv` | 高频的**值组合**（最贵也最准，**因为它要存实际的值**） |

【取舍】**官方对 `mcv` 的劝告值得直接引**：**「只在实际会一起出现在条件里的列组合上建 MCV 统计对象」**——**否则只是在浪费 ANALYZE 与规划的时间。**

【事实】**一个容易漏掉的新能力**：`CREATE STATISTICS` 还有**单表达式**的形式——**对某个表达式收集单列统计，「提供类似表达式索引的收益，但没有索引维护的开销」**。**它和表达式索引是两种不同的解法**：索引让条件**能被索引**，统计让条件**能被估算**——**只差一样时，不必上更贵的那一个。**

**到这里你应该能回答**：一个查询「单列条件估得准、组合条件估得错」，你该动的是哪一层？

### 3. 为什么「桶数」也会限制估算精度

【事实】**官方口径**：

> **统计目标值（statistics target）决定了 MCV 列表的最大条目数，以及直方图的最大分箱数。默认值是 100。**

【推导】**100 这个数字的后果，算一下才知道**：

```text
某列有 100,000 个不同值、表有 10 亿行：
  平均每个不同值 ≈ 1 万行

直方图只有 100 个桶（等深：每桶约 1% 的行 = 1000 万行）
  → 每个桶要覆盖约 100,000 ÷ 100 = 【1000 个不同值】

桶内的处理方式：被当作【均匀分布】
  → 这 1000 个不同值哪怕实际频次相差 100 倍，
     在估算里也全部一样
```

【结论】**默认 100 个桶对「值很多、分布长尾」的列是不够的**——**MCV 列表只兜住最热的 100 个值，剩下的全靠 100 个桶。**

【取舍】**所以调 `default_statistics_target` 是一笔明确的交易**（官方原话：**「更大的目标值通常让扩展统计更准，同时花更多时间计算」**）：

```text
往上调：估算更准 ←→ ANALYZE 更慢、pg_statistic 占更多空间
往回调：分析更快 ←→ 长尾列的估算更糊

按列调（ALTER TABLE ... ALTER COLUMN ... SET STATISTICS）：
  只给【真正出问题的那一列】加预算，其余列保持默认
  → 这是生产上正确的动作
```

【事实】**一个「关掉统计」的开关**：**把某列的统计目标设为 0，就停止为该列收集统计**。**适合那种「永远只做等值查、且从不在条件里出现」的列。**

【事实】**查看统计时用 `pg_stats` 视图，不要直接看 `pg_statistic`**——**前者可读性更好，而且对所有用户可读；后者只有超级用户能读**（防止无权限用户从统计里反推出别人表的内容）。**这是面试里一个很好的「合规意识」细节。**

### 4. 定位慢查询：先排序，再看单条

**第一站 `pg_stat_statements`**（需要启用扩展）。它把 SQL 按「归一化后的语句」聚合，关键列：

| 列 | 用途 |
|---|---|
| `total_exec_time` | **按总耗时排序——先治最贵的** |
| `calls` | 调用次数 |
| `mean_exec_time` / `p99` | 平均与尾延迟 |
| `rows` | 返回行数总量 |
| `shared_blks_read` / `hit` | **区分「算得慢」和「读得多」** |

【推导】**「按总耗时排，而不是按单次耗时排」——这是可以算的**：

```text
SQL A：单次 2000 ms，每小时 1 次
  → 总耗时 = 2000 × 1 = 【2 秒/小时】

SQL B：单次 20 ms，每秒 300 次
  → 总耗时 = 20 × 300 × 3600 = 【21,600 秒/小时 = 6 小时/小时】
```

【结论】**B 的单次耗时只有 A 的 1/100，但它是真正压垮系统的那个。** **「先治最贵的」的「贵」指的是【总成本】，不是【单次成本】。**

【推论】**这条在面试里是加分项**：**它说明你按「系统视角」而不是「单条 SQL 视角」做优化排序**——**而后者是最常见的用力方向错误。**

**第二站**：对选中的语句跑 `EXPLAIN (ANALYZE, BUFFERS)`，按 [[母题-P6-执行计划怎么看]] 的五步看。

### 5. 一个隐蔽陷阱：generic plan

【事实】**官方对两种计划的定义**：

> **定制计划（custom plan）**每次执行都按**这一组具体参数**重新规划；**通用计划（generic plan）**不依赖参数值、**可以跨多次执行复用**。
> **因此：用通用计划省下的是【规划时间】，但如果理想计划强烈依赖参数值，通用计划就会很低效。**
> 选择通常是**自动**做的，可以用 **`plan_cache_mode`** 覆盖——取值 `auto`（默认）/ `force_custom_plan` / `force_generic_plan`。

【推导】**什么参数分布会让通用计划翻车**：

```text
一条 SQL：WHERE status = $1
  实际分布：'RUNNING' 占 0.1%（热路径任务）
            'COMPLETED' 占 99%（历史归档）

定制计划：
  传 'RUNNING' → 走索引（只取 0.1%）✔
  传 'COMPLETED' → 走顺序扫描（要取 99%）✔

通用计划（只能挑一个折中方案）：
  两个都走同一个计划
  → 至少有一边变得很慢
```

**判据与处理**：

- **现象**：**`EXPLAIN ANALYZE` 里很快，线上同一条 SQL 很慢**；
- **检查**：看计划里是不是用了通用计划（**不同参数下计划完全一样、没有参数被代入**）；
- **处理**：**改写成参数不敏感的形状**，或在连接级别**用 `plan_cache_mode` 强制定制计划**。

【推论】**这条和 P6 的追问正好接上**——**「`EXPLAIN` 里快、线上慢」有一个标准答案，就是这里。** **而且它解释了为什么「在事务里空跑一次 `EXPLAIN ANALYZE`」不能证明线上没问题**。

### 6. 优化顺序（这一段是给面试收尾用的）

```
① 信息层：统计信息对不对（ANALYZE / 扩展统计 / 统计目标）
② SQL 层：有没有多余的行被过早展开（先缩小范围，再 JOIN）
③ 索引层：索引是否存在、是否匹配（P1–P4）
④ 结构层：缓存、物化、预聚合、分区（P16）
⑤ 架构层：读写分离 / OLAP
```

**顺序不能颠倒**：先加索引、再发现统计信息是错的，就白加了。**EnergyOps 的优化顺序（先修范围与 JOIN → 再建索引 → 再消 N+1 → 最后才缓存）和这条链是一致的。**

【推论】**为什么信息层必须排第一**：**它决定了「优化器会在哪些计划里挑」，而其余四层都是在「已挑中的计划」上做工作。** **地基错了，上面每层都是白做。**

---

### 7. 边界与常见误解

| 说法 | 实际情况 |
|---|---|
| 「统计信息刚跑过就是准的」 | **官方原话：即使刚刚更新过，它也总是近似的**（随机采样的结果） |
| 「每列统计都准，组合条件就应该准」 | **不**。优化器**默认按独立相乘**——**相关性数据上会低估几百倍** |
| 「大表数据变了 autovacuum 会自己处理」 | **阈值是 50 + 10%**——**8000 万行的表要改 800 万行才触发，约 4.4 小时** |
| 「调大统计目标总是更好」 | **它换的是 ANALYZE 时间与 `pg_statistic` 空间**；**要按列调，不要全局调** |
| 「`plan_cache_mode` 改成强制定制计划就万事大吉」 | **定制计划每次都重新规划**——**在极高频的简单查询上，规划开销本身就是浪费**。**它是取舍，不是开关** |

## 二、自测

**Q1（计算）**：一张 8000 万行的表，写入 500 TPS。`autovacuum_analyze_threshold = 50`、`autovacuum_analyze_scale_factor = 0.1`。

问：**要改多少行才会自动触发一次 `ANALYZE`？按当前写入速度，大约多久一次？**

**A1**：

```text
触发条件：变化的元组数 > threshold + scale_factor × 表行数
  = 50 + 0.1 × 80,000,000
  = 50 + 8,000,000
  ≈ 【800 万行】

按 500 TPS：
  8,000,000 ÷ 500 = 16,000 秒
  = 【约 4.4 小时】
```

【结论】**统计信息的保鲜期是小时级的。** **一次批量导入（比如补了 2000 万行历史数据）会让统计信息【当场】失效，而自动修复要等几小时。**

【推论】**判据**：

> **大表上的批量写入，操作结束时必须【手动 `ANALYZE`】**——**你在等一个 4.4 小时才回来的后台进程，来修一个此刻正在拖慢线上查询的问题。**

【补充】**注意两个阈值是独立的**：**autovacuum 的「清理（vacuum）」和「统计（analyze）」各有一套阈值**，**所以「表一直在被 VACUUM」不代表「统计信息是新的」**。**`pg_stat_user_tables` 里的 `last_analyze` / `last_autoanalyze` 才是统计信息的真实时间戳。**

**Q2（计算）**：`city` 列有 300 个不同值，`district` 列有 6000 个不同值。查询是 `WHERE city = '北京' AND district = '海淀'`。

问：**优化器按独立假设会把选择率估成多少？真实值是多少？低估了多少倍？**

**A2**：

```text
优化器的算法（独立相乘）：
  city = '北京'     的选择率 ≈ 1 / 300
  district = '海淀'  的选择率 ≈ 1 / 6000
  组合 = (1/300) × (1/6000) = 1 / 1,800,000

真实情况（海淀必然在北京 → 函数依赖）：
  district = '海淀' 已经蕴含 city = '北京'
  → 选择率就是 district 自己的选择率 = 1 / 6000

低估倍数：1,800,000 ÷ 6000 = 【300 倍】
```

【结论】**优化器把结果估小了 300 倍。** **官方对这类情况的描述是「低估结果行数」**——**于是它会认为「这么点行，用 Nested Loop 就行」，而这正是 [[母题-P6-执行计划怎么看]] 里那个爆炸点的成因。**

【推论】**判据**：

> **「每一列各看都准、一乘就错」= 列相关性。** **修法是 `CREATE STATISTICS ... (dependencies)`——把「海淀蕴含北京」这件事告诉优化器。**

【补充】**为什么单列统计救不了它**：**常规统计是「每列各自」的，官方原话是「捕捉不到任何跨列相关性」。** **这不是精度问题，是【维度】问题——单列统计里根本没有「city 和 district 一起出现」这个维度。**

**Q3（计算）**：某列 10 亿行、10 万个不同值。`default_statistics_target` 保持默认。

问：**直方图有多少个桶？每个桶要覆盖多少个不同值？这会带来什么后果？**

**A3**：

```text
官方口径：统计目标值默认 100 = MCV 列表上限 + 直方图分箱上限

桶数 = 【100 个】（等深：每桶约 1% 的行 = 1000 万行）
每桶覆盖的不同值数 = 100,000 ÷ 100 = 【1000 个】

桶内的处理：假设【均匀分布】
  → 这 1000 个不同值即使实际频次相差 100 倍
  → 在估算里也全部一样
```

【结论】**估算精度被桶数封了顶：桶内的一切倾斜都被抹平。**

【推论】**修法不是"全局调大"**：

```text
全局调大（default_statistics_target = 1000）：
  所有列、所有表一起涨——ANALYZE 更慢、pg_statistic 更大

按列调（ALTER TABLE ... ALTER COLUMN ... SET STATISTICS 1000）：
  只给出问题的那一列加预算
  → 这是生产上正确的动作
```

【取舍】**先问「这列的估算不准到底影响了什么」**——**如果它只出现在等值条件里且值很均匀，调大桶数没有收益。** **统计目标是一个**预算**，要花在真正产生错误计划的地方。**

**Q4（纠错）**：下面这段话哪里不准确？

> "线上这条 SQL 慢了，我直接用 `EXPLAIN ANALYZE` 看计划就行了，它给的是实际耗时，最可信。"

**A4**：三处问题。

1. **`EXPLAIN ANALYZE` 会强制用真实参数生成定制计划**：**线上跑的可能是通用计划**（第 5 节）。**所以「分析时快、线上慢」是完全可能的。**
2. **它是一次孤立执行，没有并发、没有锁等待、没有 WAL 压力**：**这些恰恰是线上慢的主要原因之一，而计划里看不到它们。**
3. **它会真的执行**：**在写语句上有副作用**；**而"放在事务里回滚"又会改变 IO 与锁的行为**，**测出来的数不是线上的数。**

【准确说法】"**先用 `pg_stat_statements` 按【总耗时】排序找出最贵的 SQL，再对那一条做 `EXPLAIN (ANALYZE, BUFFERS)`。** **`EXPLAIN ANALYZE` 回答的是「这个计划形状合不合理」，回答不了「线上会不会等锁」。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "优化器把行数估错了，所以它选错了索引——我们加个更强的索引就好了。"

**A5**：三处问题。

1. **估算错时，优化器可能已经在两个计划里做了选择，而它选的那个未必是"索引不够好"**：**Q2 那 300 倍的低估，会让它主动避开哈希连接、改用嵌套循环**——**你再加索引，它可能仍然用同一个错误的形状。**
2. **优化顺序是有层的**（第 6 节）：**信息层在最上面**——**统计信息错的时候，下面的索引层、结构层做得再对，都是在为一个错误的决策做优化。**
3. **"加索引"还会新增负担**：**每个索引都是写放大与 VACUUM 压力**（[[母题-P4-索引代价与在线建索引]]）。**在一个根因是"信息错"的问题上堆索引，是双倍成本。**

【准确说法】"**先问信息对不对（`ANALYZE` / 扩展统计），再问 SQL 形状对不对，最后才问索引够不够。** **顺序不能颠倒——先加索引、再发现统计信息是错的，那个索引就白加了。**"

## 三、面试输出（学完再看）

**一句话结论**：**优化器不是在猜，它是在拿统计信息算代价**——**而统计信息是随机采样的近似值（官方原话：即使刚刚更新过也总是近似的），并且它有一个写死的假设：多个条件相互独立。** 偏差来自三类原因：**统计信息过期**（触发阈值是 `50 + 10% × 表行数`，**8000 万行的表要改 800 万行才自动重统计，按 500 TPS 是 4.4 小时**，**所以大表批量导入后必须手动 `ANALYZE`**）；**列间相关**（`city` × `district` 独立相乘 → **低估 300 倍**，**修法是 `CREATE STATISTICS` 的 `dependencies`**——**单列统计在维度上就捕捉不到相关性**）；**表达式或函数**（列统计用不上，修法是**表达式索引**或**改写 SQL**）。**还有一个天花板是桶数**：`default_statistics_target` 默认 100，**意味着 MCV 只兜住最热的 100 个值、直方图只有 100 个桶**，**桶内一律按均匀分布处理**——**所以要按列调（`ALTER COLUMN ... SET STATISTICS`），不要全局调。** 定位慢查询是两站：**第一站 `pg_stat_statements` 按【总耗时】排序**（单次 20ms、每秒 300 次的 SQL，一小时要花 6 小时；比单次 2000ms、每小时一次的 SQL 贵 10800 倍），**第二站才对选中的那条做 `EXPLAIN (ANALYZE, BUFFERS)`**。**最后有一个隐蔽陷阱：通用计划**——**参数选择性差异极大时，通用计划只能取折中，于是「`EXPLAIN` 里快、线上慢」**，用 `plan_cache_mode` 可以覆盖。

**恢复关键词**：**优化器按你给的统计算** / 采样近似（更新过也是近似的）/ **独立假设** / **50 + 10% × N**（8000 万 → 800 万 → 4.4 小时）/ **手动 ANALYZE** / `CREATE STATISTICS`（dependencies · ndistinct · mcv）/ 单表达式统计 = 轻量版表达式索引 / **target 默认 100 = MCV 上限 + 桶数上限** / 桶内按均匀 / 按列 `SET STATISTICS` / `pg_stats`（pg_statistic 要超管）/ **按 total_exec_time 排序** / custom vs generic plan / `plan_cache_mode`

**核心不变量 / 主线**：
**优化器不是在猜，它是在拿统计信息算代价。**
**所以「计划不对」的排查顺序永远是：先问信息对不对，再问 SQL 形状对不对，最后才问索引够不够。**

**完整回答骨架**：优化器拿什么算 → **三类偏差 + 三种修法（各算一笔：800 万行 / 300 倍 / 1000 个值每桶）** → 桶数天花板 → **两站定位法（算 6 小时 vs 2 秒）** → generic plan 陷阱 → 五层优化顺序 → 收束到「地基错了，上面每层都白做」

**追问**（先说后看）

1. **`CREATE STATISTICS` 具体解决什么？** —— **解决「多列相关」**。典型场景：`city` 和 `district`（海淀一定在北京，两列强相关）、`status` 和 `deleted_at`（删掉的行不再是活跃态）。**优化器原本假设独立相乘，扩展统计给它真实的联合分布。** **官方提醒：`mcv` 统计只建在【实际会一起出现在条件里】的列组合上，否则只是浪费 ANALYZE 与规划时间。**
2. **统计信息准了，计划还是差怎么办？** —— 那就不是信息层的问题：**要么是 SQL 形状让优化器没有好选项**（比如为了复用而写了一个过度参数化的语句 → generic plan），**要么是代价模型对当前硬件不准**（IO 与 CPU 的相对代价随 SSD/内存变化）。此时可以考虑：**改写 SQL**、**用 CTE 的物化提示控制形状**、或（**谨慎地**）调代价参数。**但默认先怀疑前两层——改代价参数是最容易掩盖问题的一步。**
3. **`ANALYZE` 和 `VACUUM ANALYZE` 有什么区别？** —— **`VACUUM` 回收空间**（[[母题-P15-VACUUM与事务ID回卷]]），**`ANALYZE` 只更新统计信息**；`VACUUM ANALYZE` 是顺带一起做。**autovacuum 默认两个都做，但两者的触发阈值是独立的**——**所以「表一直在被 VACUUM」不代表「统计信息是新的」。**
4. **`pg_stat_statements` 能不能看出 N+1？** —— 能：**同一形状的语句 `calls` 极高、每次 `rows` 很小**，就说明应用在循环里查数据库。**这是从数据库侧发现应用问题的有效手段。**
5. **只读副本上的统计信息要不要管？** —— **要**。**统计信息不是复制的对象里的"数据"，它是每台实例各自 `ANALYZE` 出来的**——**只读副本如果从不分析，它的计划可能和主库完全不一样**（[[母题-P12-流复制与逻辑复制]]）。**这一条说出来，说明你运维过真实的主从。**

**同类变体**

- 「为什么我 `ANALYZE` 过了，估算还是不准？」—— **因为它是随机采样，官方原话是「即使刚刚更新过也总是近似的」**；**再加上独立假设与 100 个桶的天花板**。**`ANALYZE` 解决的是"过期"，解决不了"相关"和"维度不够"。**
- 「MySQL 那边怎么对应？」—— **MySQL 的对应工具是慢查询日志 + `EXPLAIN` 的 `filtered` / `rows`**，**没有 `pg_stat_statements` 这种内置的「按总耗时聚合」视图**（要靠 performance_schema 自己搭）；**MySQL 也没有 `CREATE STATISTICS` 扩展统计**（8.0 有直方图，但多列相关性仍主要靠组合索引和 SQL 改写绕开）。**这一条 PG 明显更强，可以主动说。**
