# 母题 C3 · Prompt 版本管理与回归

> **模块**：LLM 与上下文工程 / 变更管理
> **所属主线**：三 · 输出怎么被约束与验收（从"请求它做对"变成"结构上做不错"）
> **层级**：B · 标准级（**为什么必须消融**能从"prompt 是控制层、模型是概率系统"推出来；但**该删哪一条**没有唯一答案——那是取舍，只能测出来，所以不是 A）

> **素材来源**：Anthropic《The new rules of context engineering for Claude 5 generation models》（2026-07-24，作者 Thariq Shihipar）、Anthropic《Reducing cost and improving performance with Claude Platform》（2026-09-08，作者 Lance Martin）、Anthropic Engineering《Effective context engineering for AI agents》（2025-09-29）；`archive/study-courses/02-LLM与Context-Engineering.md` 第 5 节。**其中样本量算式、"相对提升 vs 错误率"换算、年化节省 vs 消融成本、自测题，为本次新增（待你核对）**

**题目**：面试官问——"我看你们 prompt 改得挺频繁的，你怎么知道一次改动是变好了还是变坏了？换模型之后你们做了什么？"

**母题**：**Prompt 是针对"当时的模型"写下的控制层。模型变了、任务变了，这套控制层的收益和代价都会变——那么你怎么用最小的代价，知道自己该删哪一条？**

## 一、教材

### 1. 前提：Prompt 不是配置文件，是控制层

#### 1.1 同一份 prompt 在不同模型上是不同的系统【推导】

Prompt 不是"描述任务的文本"，它是**用来补偿模型某个具体缺陷的补丁**。所以：

```text
prompt 的效果 = f(模型能力, 任务分布)
模型换了  →  函数变了  →  同一份 prompt 的收益和代价都变了
```

【推论】这直接否定了一个常见做法："模型升级了，先不动 prompt，跑跑看。"——**"先不动"本身就是一次未经评估的变更**，因为你已经改变了一个自变量。

#### 1.2 一条指令的完整生命周期【推导】

```text
① 写下指令  ← 为了补当时模型的一个失败模式
② 沉淀下来  ← 进入系统提示 / CLAUDE.md / Skills
③ 模型升级  ← 它补的那个弱点消失了
④ 变成负担  ← 指令只在少数场景成立，还和别的指令打架
⑤ 消融判定  ← 删掉一段，跑同一套 Eval，比指标
```

【事实】第 ④ 步不是假想。Anthropic 读自己内部的 Claude Code 使用记录时，发现**同一个请求里会同时出现互相冲突的指令**——系统提示说"不要加注释"，用户的 CLAUDE.md 或请求又说"文档要写清楚"，两边打架。模型能处理，但**它得先花推理去解决这个冲突**，这本身就是成本。

### 2. 候选方案：三种验证方式（先各自介绍，不比较）

#### 2.1 凭感觉 + 看几个例子【事实】

改完随手试几个 case，觉得好就发布。**这是默认做法，也是最贵的做法**——贵在它把成本转移到线上。

#### 2.2 全量回归【事实】

每次改动都跑完整评测集，比较所有指标。**证据最强，代价最高**（时间和 token 都按评测集规模线性增长）。

#### 2.3 消融实验（ablation）【事实】

**删掉一段**，其余不动，跑同一套 Eval，比较指标：

```text
指标没掉    → 删掉（这段是冗余）
指标变好    → 删掉（这段是拐杖，它在拖后腿）
指标变差    → 保留，并记下"它现在还在补偿什么"
```

**注意方向**：消融问的是"**多了什么**"，不是"少了什么"。这一条与直觉相反——大部分人改 prompt 的默认动作是**加**。

---

### 3. 逐个淘汰（统一指标：改动带来的净收益 ÷ 验证成本）

#### 3.1 为什么"凭感觉"在概率系统里没有信息量【推导】

模型是**采样**的：同一个输入，跑两次可能不一样。这导致：

- **单次观察无法区分"改动生效"和"随机波动"**——你看到的那一次更好，可能就是运气
- **小评测集也救不了**：见第 4 节的样本量算式，200 条的评测集分辨不出 2 个百分点的差异

【取舍】所以"我先试试看"不是错，错在**把试出来的结论当成结论**。试可以，但要清楚地知道：**样本量不够的观察，只能证伪、不能证实。**

#### 3.2 为什么不能"每次都全量回归"【推导】

全量回归的问题不在正确性，在**频率**：

```text
评测集 200 条 × $0.03/条 = $6/次
一天改 10 次           = $60/天
```

【取舍】成本本身不算高，但它**慢**——每次都等全量结果，迭代速度会被拖死。**证据强度和迭代速度是有张力的**，所以正确的结构是分层的（见 3.4）。

#### 3.3 为什么"加规则"是本能的错误方向【推导】

模型出错时，人的第一反应是"再加一条规则告诉它别这样"。但这会撞上 [[母题-C1-上下文组装与窗口预算]] 的两条约束：

1. **每条指令都占注意力预算**——加了这条，别的指令被稀释
2. **规则会互相冲突**——尤其是"吸收教训式"的补丁，它们往往是针对某个具体 case 写的，天然和通用规则打架

【事实】**反直觉的实证**：Anthropic 为 Claude 5 代模型**删掉了超过 80% 的 Claude Code 系统提示**，编码评测**没有可测量的损失**。同一篇文章里，他们列的六类"拐杖"——验证仪式、强调型助推、强制流程与草稿纸、过时示例、互相矛盾的规则、过期配置——**全都是"加"出来的**。

#### 3.4 胜出方案：分层验证 + 训练/测试分离【事实】

```text
改动 → 抽样快筛（便宜、快，只能筛掉明显的坏改动）
     → 全量回归（发布前跑一次，作为门禁）
     → 训练/测试分离（调参看训练集，验收只看未见过的测试集）
```

【事实】最后一条最关键，有真实的翻车案例可以对照。Anthropic 的 hillclimb 工具在客服 benchmark 上做模型/effort/prompt 的联合搜索：

```text
起点：Opus 4.8 默认（high effort）
第一步：换 Opus 5 + low effort + 清掉拐杖
        → 训练集 98.9%，成本 2.6 美分/工单
第二步：降到 Sonnet 5 low effort
        → 更便宜（1 美分/工单），但准确率掉到 88.9%
第三步：读失败的训练样本，补路由规则与退款上限交叉引用
        → Sonnet 5 回到 98.9%，成本不变
```

【事实】真正的结论在**它没看过的 14 条 held-out 工单**上：

```text
最终配置 90.5%  vs  原始配置 78.6%     成本约为原来的 1/5
```

**注意这个差距**：训练集上是 98.9% vs 98.9%（打平），held-out 上才拉开 11.9 个百分点。**如果只看训练集，你会以为"降级到 Sonnet 5 + 补几句规则"没有损失。**

**到这里你应该能回答**：为什么调 prompt 要有"没被搜索看过的"那部分数据？

### 4. 量化验证：三笔账

**第一笔：评测集要多大，才能看出差别？**

```text
比例的标准误：SE = √(p(1−p)/n)

p ≈ 0.9，n = 200：
SE = √(0.9 × 0.1 / 200) = √0.00045 ≈ 0.0212 = 2.1%

要让 SE 降到 1%（能分辨 2 个百分点的差距）：
n = p(1−p) / SE² = 0.09 / 0.0001 = 900 条
```

【结论】**200 条评测集的分辨率大约是 ±2%**。改动前后差 4 条（2 个百分点）时，这个差异**小于一个标准误**——分不出来。所以：

- 小评测集只能抓**大幅回退**（比如掉 10 个点）
- 想论证"我改进了 2 个点"，评测集得按**千条**量级准备

**第二笔：删掉 80% 系统提示，值多少钱？**

```text
假设原系统提示 8,000 token，删掉 80% → 每次请求省 6,400 token
一次 40 轮会话，系统提示被送 40 次 → 省 6,400 × 40 = 256,000 token

无缓存：256K × $5/MTok   = $1.28 / 会话
有缓存：256K × $0.5/MTok = $0.128 / 会话   （读价 0.1×）
```

【推导】**注意这里省的是线性的**——每轮固定省 6,400，不像"历史重发"那样平方增长。所以它的省钱效果远不如压缩历史，但**它的注意力收益是另一回事**：同时减少了 6,400 个 token 对 attention budget 的持续占用（[[母题-C1-上下文组装与窗口预算]]）。

**第三笔：准确率涨 5.3% 到底是多少？**

Anthropic 报告 `/claude-api prompt-audit` 清掉六类拐杖后，**平均成本降 14.6%、准确率升 5.3%**。5.3% 听起来不多，换算成**错误率**：

| 读法 | 准确率 | 错误率 | 变化 |
|---|---|---|---|
| 基线 | 90% | 10% | — |
| 5.3% 是**相对**提升 | 90% → 94.8% | 10% → **5.2%** | 错误率**减半** |
| 5.3% 是**绝对**提升 | 90% → 95.3% | 10% → **4.7%** | 错误率**减少 53%** |

【结论】**两种读法下结论一致：去掉拐杖让错误率腰斩。** 这是面试里很值钱的一次换算——**"准确率提升 5 个点"和"错误率减少一半"是同一件事的两种说法**，而后者对业务方的说服力完全不同。

**再看这笔账的另一面**：验证一次消融要多少钱？

```text
评测集 200 条 × 2 次（删前 / 删后）× $0.03 = $12
```

用 **$12** 的实验，去确认一项年化 **$32,000–$320,000**（按每天 1,000 场会话、250 工作日、有/无缓存两种情况估）的节省。

【取舍】**所以"要不要做消融"根本不是成本问题，是习惯问题。**

**到这里你应该能回答**：为什么说"做消融太贵"这个理由是站不住的？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "模型升级了，prompt 先别动" | **反了**。模型升级恰恰是重估 prompt 的最佳时机——旧指令可能已经从"补偿"变成"约束"。Anthropic 为 Claude 5 代删掉了 **80%+** 的系统提示，编码评测无损失 |
| "评测集上从 88% 提到 92%，这次改动成功了" | 要看**这个评测集有没有被反复看**。被搜索反复优化过的集合是训练集，不是验收集。上面那个案例：训练集上 98.9% vs 98.9% 打平，**held-out 上 90.5% vs 78.6%** |
| "改进了 2 个点" | 200 条评测集的标准误约 2.1%，**2 个点在噪声里**。要么把集合做大，要么只宣称大幅变化 |
| "出了问题就再加一条规则" | 加规则会稀释注意力、并制造冲突。**先问"能不能删"，再问"要不要加"** |
| "准确率涨 5.3%，提升有限" | 换算成错误率是**腰斩**（10% → 5.2%）。汇报时用错误率，比用准确率更贴近业务 |
| "prompt 只是配置，不用版本管理" | Prompt 是**控制层的一部分**，和代码一样会影响行为。它必须：进版本控制、变更走评测、结果与版本绑定（尤其当它和 schema 版本、知识版本一起决定输出时） |
| "示例给得越多越稳" | 【事实】对新一代模型，**示例反而会限制探索空间**。优先改接口设计（枚举、参数命名、默认值），而不是堆示例 |

【取舍】读成一句话：**改 prompt 的正确姿势不是"加一条更好的规则"，是"删掉一条没用的规则，并用没被看过的那部分数据证明它没用"。**

## 二、自测

**Q1（计算）**：你们的评测集有 **200 条**，基线准确率约 90%。这次改 prompt 后对了 184 条（92%），上次 180 条（90%）。

问：**这 2 个百分点的差距，是真差别还是噪声？**如果要稳定分辨 2 个百分点的差距，评测集至少要多大？

**A1**：

```text
标准误 SE = √(p(1−p)/n) = √(0.9 × 0.1 / 200) = √0.00045 ≈ 0.0212 = 2.1%

2 个百分点的差距 < 1 个标准误（2.1%）
→ 落在噪声里，分辨不出来

要让 SE = 1%（此时 2 个点才约等于 2 个标准误）：
n = p(1−p) / SE² = 0.09 / 0.0001 = 900 条
```

【结论】**200 条评测集的分辨率约 ±2%**，只够抓大幅回退。想论证"改进了 2 个点"，评测集要按**千条**量级准备。

【补充】这也解释了为什么"多轮调优后评测分数涨了"经常是幻觉——**你在同一套小集合上反复看，它已经变成训练集了**（见 Q5）。

**Q2（计算）**：为 Claude 5 代模型删掉 **80% 的系统提示**。设原系统提示 8,000 token，一次会话 40 轮。

问：**每次请求省多少 token？一次会话省多少？如果每天 1,000 场会话、一年 250 个工作日，年化省多少**（分有/无 prompt caching 两种情况）？

**A2**：

```text
每次请求省 = 8,000 × 80% = 6,400 token
一次会话省 = 6,400 × 40 = 256,000 token      ← 注意是线性的，每轮都省同样的量

无缓存：256K × $5/MTok   = $1.28/会话
        $1.28 × 1,000 × 250 = $320,000/年
有缓存：256K × $0.5/MTok = $0.128/会话
        $0.128 × 1,000 × 250 = $32,000/年
```

【补充两点】

1. **这里的节省是线性的**，不像"历史重发"那样平方增长——因为系统提示每轮都是固定那 6,400 token。所以单看钱，它的效果不如压缩历史。
2. **但它的注意力收益不是线性的**：同时减少了 6,400 个 token 对 attention budget 的持续占用。**而这部分收益恰好是"省钱账"算不出来的**——所以要靠评测指标来验证（这也正是消融实验存在的理由）。

**Q3（计算）**：`prompt-audit` 清掉六类拐杖后，官方报告"**成本降 14.6%、准确率升 5.3%**"。

问：**如果基线准确率是 90%，准确率升 5.3% 换算成错误率是多少？**这个数字为什么比"升 5.3%"更适合汇报？

**A3**：

| 读法 | 准确率 | 错误率 | 变化 |
|---|---|---|---|
| 基线 | 90% | 10% | — |
| 相对提升 5.3% | 90% × 1.053 = **94.8%** | **5.2%** | 错误率**减半** |
| 绝对提升 5.3% | 90% + 5.3 = **95.3%** | **4.7%** | 错误率**减少 53%** |

【结论】**两种读法下都是"错误率腰斩"。** 汇报时用错误率而不是准确率，是因为：

- 业务的成本模型几乎总是**线性的错误率函数**（每 100 次出几次错 → 几次人工兜底 / 几次客诉 / 几次回滚）
- 而"准确率 +5.3%"在 90% 的基线上，直觉上会被听成"没什么变化"

**这是一次纯粹的表述换算，不改变任何事实，但改变别人对这件事价值的判断。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们换了新模型，prompt 先保持不动，跑一段时间看看效果再决定要不要调整。"

**A4**：**"先不动"本身就是一次未经评估的变更。**

- Prompt 不是"任务描述"，是**针对旧模型的具体缺陷写的补丁**。它和模型是一个**耦合系统**——换了模型，同一份 prompt 的收益和代价都变了。
- 旧指令可能从"补偿"变成"约束"甚至"冲突"。Anthropic 的实测：为 Claude 5 代模型**删掉 80%+ 的 Claude Code 系统提示**，编码评测无损失；他们读自己的使用记录时，还发现**同一个请求里同时带着互相矛盾的指令**。
- 而且"跑一段时间看看"等于**用线上当评测集**——成本被转移给了用户。

【准确说法】"换模型是一次最大的 prompt 变更。正确做法是：换模型的同时跑一次消融（逐段删除、比较同一套 Eval），把已经不产生收益的指令清掉，再用 held-out 集合验收。"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们在评测集上把准确率从 88% 调到了 92%，所以这次 prompt 改动是成功的。"

**A5**：**缺少一个关键信息——这个评测集是不是被反复看过的。**

- 如果这 4 个百分点是**反复在这同一套集合上试出来的**，那它已经变成**训练集**了。你在训练集上的提升，不保证在没见过的数据上成立。
- 有真实的对照案例：Anthropic 的 hillclimb 搜索在客服 benchmark 上，**训练集上最终配置和起点打平（都是 98.9%）**，但在**它没搜索过的 14 条 held-out 工单**上是 **90.5% vs 78.6%**——11.9 个百分点的差距只在未见数据上才现形。
- 另外，即使集合没被反复看，**4 个百分点是否显著仍取决于样本量**（见 Q1：200 条的集合分辨率约 ±2%）。

【准确说法】"要论证改动成功，需要三个条件：**验收用的是未参与调优的 held-out 集合**；**样本量足以分辨这个幅度的差异**；**指标口径和基线固定**（同样的模型版本、同样的评测脚本、同样的采样参数）。"

## 三、面试输出（学完再看）

**一句话结论**：Prompt 不是配置文件，是**针对当时模型写的控制层**——它和模型是一个耦合系统，模型一变，同一份 prompt 的收益和代价全变。所以改动必须走**消融**：逐段删除、跑同一套 Eval、看指标是掉了还是变好；验收必须用**没参与调优的 held-out 集合**（真实案例：训练集上 98.9% 打平，held-out 上 90.5% vs 78.6%）。反直觉的实证是：Anthropic 为 Claude 5 代**删掉了 80%+ 的系统提示**，编码评测无损失；清掉六类"拐杖"后**成本降 14.6%、准确率升 5.3%（错误率腰斩）**。而验证一次消融只要几美元——**所以"要不要做消融"是习惯问题，不是成本问题。**

**恢复关键词**：prompt 是控制层不是配置 / 一条指令的生命周期（补偿 → 沉淀 → 模型升级 → 变成冲突 → 消融） / 六类拐杖（验证仪式·强调助推·强制流程·过时示例·矛盾规则·过期配置）/ 消融方向是"删"不是"加" / 删 80% 系统提示无损失 / 标准误 √(p(1−p)/n)，200 条 ≈ ±2% / held-out 90.5% vs 78.6% / 准确率 +5.3% = 错误率腰斩 / 消融成本 $12 vs 年化 $32K–$320K / 分层验证：抽样快筛 + 全量门禁

**核心不变量 / 主线**：
**Prompt 的效果是「模型能力」的函数，不是常量。**
所以它必须像代码一样被管理：**进版本控制、变更走评测、结果与版本绑定**。而因为它是一份**有限的注意力预算**，正确的动作方向永远是"**先问能不能删**"，而不是"再加一条规则"。

**完整回答骨架**：先立前提（prompt 是针对当时模型的补丁，和模型耦合）→ 一条指令的生命周期 → 单次观察在概率系统里没有信息量 → 样本量算式 → 消融的三个判定分支 → held-out 与训练集分离的真实案例 → 六类拐杖与删 80% 的实证 → 成本换算（错误率腰斩 / 消融成本忽略不计）→ 收束到"prompt 要像代码一样管"

**完整回答（口述稿）**：
先立前提：**Prompt 不是配置文件，是针对当时那个模型写的控制层**——它和模型是耦合系统，模型一变，同一份 prompt 的收益和代价全变。

所以改动必须走**消融**：逐段删除 → 跑同一套 Eval → 看指标是掉了还是变好。指标没掉就是冗余，指标变好就是拐杖。验收必须用**没参与调优的 held-out 集合**——真实案例是训练集上 98.9% 打平，held-out 上 90.5% vs 78.6%。

两个反直觉的实证：Anthropic 为 Claude 5 代**删掉了 80%+ 的系统提示**，编码评测无损失；清掉六类"拐杖"后**成本降 14.6%、准确率升 5.3%（错误率腰斩）**。而验证一次消融只要几美元——所以"要不要做消融"是习惯问题，不是成本问题。

配套一条：模型版本、Prompt 版本、Schema 版本、知识/索引版本**四者必须绑定到结果上**，否则线上输出复现不出来，也就无法归因。

**分层要点**：
- **结论**：Prompt 是针对当时模型的控制层，改动必须走消融 + held-out 验收。
- **推导链**：prompt 与模型耦合 → 单次观察在概率系统里没有信息量 → 样本量算式 → 消融三个判定分支 → held-out 与训练集分离 → 六类拐杖。
- **量化**：`SE = √(p(1−p)/n)`，200 条约 ±2%、分辨 2 个点需约 900 条；删 80% 系统提示无损失；清拐杖后成本 −14.6%、错误率腰斩。
- **边界与常见误解**：直接加规则有三重代价（稀释注意力 / 制造冲突 / 升级后变负担）；改 schema 会打掉 prompt cache，所以 schema 要版本化。

**追问**（先说后看）

1. **一次 prompt 改动，验证流程是什么？** —— 抽样快筛（便宜、抓大幅回退）→ 消融（逐段删，看哪段还在产生收益）→ 全量回归（发布门禁）→ **held-out 验收**。每一层的目的不同，不能互相替代。
2. **为什么不直接加规则？** —— 加规则有三重代价：**稀释注意力预算**、**制造规则冲突**（模型得额外推理去化解）、**在模型升级后变成负担**。先做消融，往往能删掉比你想加的还多。
3. **怎么发现一条指令该删了？** —— 做消融：删掉它，跑同一套 Eval。**指标没掉就是冗余，指标变好就是拐杖。** 另一条便宜的信号是查**文档里互相矛盾的指令**——Anthropic 就是读自己的使用记录时发现同一请求里带着冲突指令的。
4. **评测集要多大？** —— 取决于要分辨多小的差异。`SE = √(p(1−p)/n)`：200 条约 ±2%，想分辨 2 个点需要约 900 条。**先想清楚"我要证明多大的差异"，再决定集合规模。**
5. **Prompt 版本怎么和别的版本绑定？** —— 当输出同时取决于**模型版本、Prompt 版本、Schema 版本、知识/索引版本**时，四者必须一起绑定到结果上。否则你复现不出任何一次线上输出，也就无法归因（[[母题-C1-上下文组装与窗口预算]] 的"上下文是视图"在这里落地成工程要求）。
6. **`CLAUDE.md` 写多长合适？** —— 【事实】轻。写明仓库是干什么的，把大部分 token 花在**代码库里的坑**上；不要写"看文件系统就知道"的显然内容；多条验证指令就做成一个 verification skill，靠渐进披露按需加载。

**同类变体**

- 「模型降级怎么做才安全？」——降级是**最大的一次 prompt 变更**。正确顺序：先按 held-out 选模型 → 再针对新模型做消融清拐杖 → 最后补必要的规则 → 重跑门禁。**真实案例里，降级后补对了几句规则，成本降到 1/5 而 held-out 准确率反而高了 12 个点。**
- 「Prompt 和代码有什么不一样？」——本质相同：都要版本化、都要评测、都要能回滚。**不同的是确定性**：代码的行为可复现，prompt 的行为是分布。所以 prompt 的回归需要**统计口径**（样本量、置信度），代码的回归只需要"通过/不通过"。
- 「能不能让模型自己改 prompt？」——可以（比如 hillclimb 这类自动搜索），但**必须配 held-out 集合**，否则搜索会直接过拟合到你看得见的那部分数据上。

**关联母题**：[[母题-C1-上下文组装与窗口预算]]（每条指令都在抢注意力预算，"删"的收益从这里来）· [[母题-C2-结构化输出与JSON可靠性]]（schema 变更同样要走回归，且会让 prompt cache 失效）· [[母题-C5-模型选型与降级三角]]（换模型是最大的 prompt 变更）

**可迁移场景**：

- **数驭穹图**：Schema 版本、Query Prompt 版本与结果绑定——**这就是把"prompt 要版本化"落到工程上的具体形态**。没有这个绑定，出了 Bad Case 无法归因是"模型变了"还是"prompt 改了"还是"表结构变了"。
- **RuleArena**：发布门禁的评测集必须与调优用的集合分离。**如果调优时反复看同一套集合，那 98.9% 就只是训练集数字**（真实案例：训练集打平、held-out 差 12 个点）。
- **EnergyOps**：六层评测与数据飞轮——每一层评测集的作用不同，**"用来发现问题"和"用来验收改动"的集合应当是两套**。

**方言差异（与软件回归测试对照）**：代码的回归是**确定性**的——同一个 commit，测试要么过要么不过，重跑结果一致。Prompt 的回归是**统计性**的——同一份 prompt 重跑可能不同，所以需要样本量、置信度、训练/测试分离。**这是"把软件工程实践搬到 LLM 上"最容易踩空的一点：照抄了流程，但没有照抄支撑流程的统计前提。**（这也是本卡按 [[母题卡模板]] 的层级判定给 **B 而非 A** 的原因：**"为什么必须消融"能推出来**，但**"该删哪一条"没有唯一答案**，只能靠实验测出来。）
