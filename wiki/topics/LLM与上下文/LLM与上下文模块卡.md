# LLM 与上下文工程模块卡

> 本卡是 [[模块深挖卡模板]] 的实战卡。**主线优先**：先看三条线，再落母题，题单只用来查漏。
> 定位：**AI 主战场的第一块地基**。RAG、Agent Runtime、Eval 三簇都以本模块的"上下文是有限预算"为前提。

## 0. 模块边界（先写这个，防无限扩张）

**包含**：模型为什么不可靠（概率生成的工程后果）、上下文窗口的真实约束（注意力预算 / context rot）、上下文的四种控制手段（选择 / 压缩 / 隔离 / 缓存）、结构化输出的可靠链路、Prompt 与版本的回归管理、模型选型与 effort 标定、token 成本结构与缓存定价。

**明确不包含**：

- **训练侧的一切**（预训练、后训练、RLHF、微调）——只到"知道知识截止与训练分布会影响行为"
- **Transformer 源码级推导**（多头注意力的矩阵形状、位置编码的具体公式）——只到"n² 关系 → 预算有限"这一步
- **各家模型的价格横评与跑分对比**——只到"选型是一个多目标取舍，给判据不给结论"
- **具体向量库 / 框架的选型**——属于 RAG 簇（G 系列）
- **提示词的写作技巧大全**——只讲"可维护的 Prompt 由哪几部分组成、怎么验证改动"

**边界判据**：**本模块只回答"模型为什么这样、上下文该放什么、输出怎么被约束住、钱花在哪"**。凡是"某个具体框架怎么用"的，进别的簇。

## 5. 项目映射（三个简历项目逐个过）

### 5.1 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**Thread / Run / Step 的状态模型就是"权威"，上下文是从它装配出的"视图"**；规则原文、审查摘要、权威状态、Agent 临时判断四者分开放
- 解决什么问题：**长审查任务跨过了单次窗口** —— 靠压缩 + checkpoint + 从权威状态重建最小上下文
- 踩过的坑：**压缩摘要里没记副作用，恢复后就会重做**——摘要是「有损且不可逆」的，它留下的是当时的判断，不是事实。把「已执行过哪几次动作、各自的幂等键是什么」压掉了，恢复时系统就真的不知道做过没有，只能重试 → **重复副作用**。
- 决策与取舍：**恢复时必须先查权威业务状态，不能用旧摘要续跑**——因为**摘要是「意图」，Receipt/Snapshot 才是「事实」**，两者之间夹着那个不确定窗口。摘要省的是 token，不是真相；**省 token 的代价不能是「用猜代替查」**（本库 [[母题-A4-长任务状态与Checkpoint]] 的恢复协议六步、[[母题-P19-唯一约束与UPSERT]] 的 Receipt 是同一件事）。

- 对应母题：【C1】【C4】

### 5.2 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**上下文只装当前领域 Schema + 权限过滤后的候选表 + 关键样例**；SQL 结果过大时写 Artifact 只回传统计与样本
- 解决什么问题：**Schema 太大塞不下，且权限决定谁能看哪些表** —— 上下文装配必须带权限过滤
- 踩过的坑：**砍掉的是「全库 Schema」和「大结果明细」，不是信息本身**——Schema 从全量改成「按领域路由后的候选表 + 关键样例」，SQL 的多万行结果**外置成 Artifact（Hot/Warm/Cold），上下文只留口径摘要 + 聚合统计 + artifact_id**。**东西没丢，只是从「常驻上下文」挪到了「按需取」**。
- 决策与取舍：**版本要跟着结果走，因为「同一个问题不同版本可以给出不同答案」**——口径改过、Prompt 改过、Schema 改过之后，旧结果就不能再拿来对照，否则你分不清「是数据变了还是规则变了」。**不绑定版本的结果，在审计场景里等于没有出处**（[[母题-C3-Prompt版本管理与回归]] 的 Prompt 版本管理在这里落地）。

- 对应母题：【C1】【C3】

### 5.3 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**30 个 MCP 工具的工具定义本身就是上下文开销**；每个工具只收必要业务参数；日志和大表先聚合再进上下文
- 解决什么问题：**工具越多，上下文里光工具定义就吃掉一大块** —— 这是"最小工具集"和延迟加载的直接动因
- 踩过的坑：**30 个工具全量声明，光工具定义每轮就吃掉一大块**——而且这笔钱**每一轮都要付**（历史重发，见 [[母题-C1-上下文组装与窗口预算]] 的平方累计）。高频的查询类留常驻，**低频且重的（结算发布、批量导出、规则变更）标记延迟加载**，用到时才引入。
- 决策与取舍：**描述不是越详细越好，是「够选对就行」**——写太简会选错工具，写太细每轮都多付 token 且**长描述反而稀释关键差异**。判据是**选择准确率 vs token 占用**的实测权衡，不是凭感觉写长。

- 对应母题：【C1】【C2】

## 8. 题级答案（「本主线的题」翻转卡背面 · 先说后翻）

> 题号与第 4 节题单一一对应。**必背**题写成能直接说出口的一段话；**理解 / 了解**题写 1–3 句。
> 翻转卡背面先给这道题的答案，再挂上「所属母题的完整回答（口述稿）」与单卡入口——两段合起来才是深挖。

### 1 （必背）
层级不同。Prompt Engineering 是**在一次调用里把指令写清楚**——措辞、示例、格式，优化对象是提示词本身；Context Engineering 是**管理每一步往窗口里放什么 token**——选哪些工具结果、哪些历史、什么时候压缩、什么时候隔离。一个是"怎么说"，一个是"给什么看"。

为什么后者成了主线：窗口是容量不是质量，注意力是 n² 关系，token 越多这份预算越被摊薄（context rot）。所以上下文工程的目标不是把窗口塞满，而是找到最小的那组高信号 token——四种手段组合：选择、压缩（摘要 + 外部持久化指针）、隔离（子任务独立窗口只回传 1–2K）、缓存（稳定前缀复用）。

### 2 （必背）
不是。两条理由：① 窗口是容量不是质量，token 越多注意力预算越被摊薄，长上下文不等于"看得进去"（context rot）；② 成本是**平方增长**的——每轮都要把全部历史原样重发一遍，40 轮 × 15K 的会话累计输入 12.3M，是最后一轮 prompt 的 20.5 倍。

什么时候反而不用 RAG：数据小、稳定、无权限差异、不需要引用溯源时，直接放长上下文更简单也可能更好。判据是四个维度——质量、成本、延迟、权限，由评测驱动，不由架构偏好驱动。

### 3 （必背）
注意力是 n² 关系：token 越多，每个 token 分到的注意力预算越被摊薄，表现为**越长的上下文里模型越容易忽略中间的信息、越容易捡起不相关的旧内容**。所以它不是"容量不够"，是"预算被稀释"。

而且窗口变大也治不了它——污染和信息相关性问题对所有尺寸的窗口都存在，平方成本来自"重发"这个机制，不来自窗口大小。对策是四种手段的组合：选择（只放当前步骤所需）、压缩（摘要 + 外部持久化指针）、隔离（子任务独立窗口只回传结论）、缓存（稳定前缀复用）。

### 4 （必背）
三者权威性和生命周期完全不同：Context 是**一次调用的可见 token（视图）**；Agent State 是**运行过程的结构化状态（运行权威）**；Memory 是**跨会话复用且获准保存的信息（派生，需要治理）**。

混在一起最常犯的错是"拿模型自己的摘要当业务事实"。正确的工程取向：恢复时**先查权威状态再重建最小上下文**，而不是拿旧摘要直接续跑——RuleArena 的 Thread / Run / Step 就是按这个分层的：结构化状态是权威，上下文是从它装配出来的视图。Memory 只存跨任务稳定、对未来有用、经过授权、能被治理的信息，临时推理和模型猜测不自动写。

### 5 （必背）
压缩是有损操作，所以必须留指针。摘要里必须保留六项：**目标与约束**、**已确认事实及其来源 ID**、已完成/未完成步骤、关键决策与原因、**副作用执行记录**、未决问题与剩余预算。

最贵的一类丢失是副作用记录——前几项丢了大不了重做，**副作用记录丢了会重复执行写操作**。触发时机按平台默认 150,000 输入 token（可配，最小 50,000）；压缩的正确调法是先保 recall 再谈短，不是越短越省。

### 6 （理解）
三招：① 只回传必要的字段或聚合结果（日志和大表先检索聚合，不塞原始结果）；② 大结果写 Artifact / 外部存储，上下文里只留指针 + 统计与样本；③ 工具用延迟加载（defer_loading），少用的留在缓存前缀之外、用到才加载。判据是：工具结果进上下文虽然只发生一次，但它会跟着后面每一轮被重发一遍。

### 7 （理解）
子 Agent 在自己的干净窗口里探索，可能烧掉几万 token，但**只把 1,000–2,000 token 的浓缩结论**回传——搜索过程的噪声全被隔离在子 Agent 内部。多 Agent 按权限域或专长隔离，每个子 Agent 一个干净窗口、只回传结构化结论，最终由主 Agent 合成。

代价要提前知道：同步工具调用或子 Agent 跑超 5 分钟，默认的 5 分钟 TTL 就过期了，下一轮按 1.25× 重写——这类场景要换 1 小时 TTL（写价 2×，但要算一下切换频率）。

### 8 （必背）
同一个 token 有四种价钱：普通输入 1×、缓存写入 1.25×（1 小时 TTL 是 2×）、**缓存读出 0.1×**、输出 5×。缓存解决的是价格不是占用——无损，且只对**稳定前缀**有效。

最反直觉的点：**"开了"不等于"命中"**。回看找的是历史写入记录、要求前缀逐字节相同，还要同一模型同一 effort、在 TTL 内、达到最短长度、落在 20-block 回看窗口内。没命中按概率排查：前缀里有易变值（时间戳 / 每轮变化的 ID）、工具定义被重排、中途改了模型或 effort、TTL 过期、一轮新增超过 20 个 block 把断点推出窗口。命中率看 cache diagnostics——它能指出前缀从哪个位置开始分叉。

### 9 （必背）
**平方增长**，因为每轮都要把全部历史原样重发一遍。40 轮 × 15K 的会话，累计输入 12.3M，是最后一轮 prompt 的 20.5 倍——所以同样一句"每轮 15K"，40 轮的账单不是 40 × 15K，而是它的二十倍量级。

这也解释了为什么降本的第一优先级是提高缓存命中率：命中部分按 0.1× 计价，而模型看到的 token 一个没变，实测能把 100 轮会话的账单降到约 1/9。缓存不改占用，真正降占用只能靠压缩。

### 10 （必背）
按是否有损排：**① 提高缓存命中率**（无损，只改价格不减 token）；**② 去掉 prompt 拐杖**（唯一既降本又提质的杠杆——Anthropic 清掉六类拐杖后成本降 14.6%、准确率升 5.3%、错误率腰斩）；**③ compaction 与工具结果清理**（有损，必须留指针）；**④ 调 effort / 换模型**（换质量，必须 held-out 验证）。

顺序不能反——"降本就是压缩上下文"是错的，压缩是最后手段。另外两个反直觉点：写了没读到要付 1.25×，比不缓存更贵；命中率掉了账单立刻涨，而它的影响因素（TTL 过期、工具定义重排、中途改 effort）都不体现在上下文长度上。

### 11 （理解）
不一定，四个判据：质量（长上下文有 context rot，RAG 有检索漏召）、成本（长上下文平方增长，RAG 每轮只付检索到的）、延迟（看首 token 延迟，RAG 通常更快）、权限（RAG 能在检索层过滤，长上下文要把数据整体塞进去）。

数据小、稳定、无权限差异、不需要溯源时，长上下文更简单也可能更好；反之用 RAG，但接完还要做引用绑定和答案级评测。决策由评测驱动，不由架构偏好驱动。

### 12 （必背）
三层各管一段：**提示约束**只降低概率（免费但不保证）；**解码约束**（strict / json_schema）把不合语法的 token 概率压成 0——这才是保证，但 grammar 编译成本随 schema 复杂度指数增长，且有 20 工具 / 24 可选参数 / 16 union 的硬上限；**事后校验**拦语义错误（必须，因为前两层都管不了）。

两个坑：`refusal` 和 `max_tokens`（截断）会绕过 schema，所以要看 `stop_reason`；枚举的大小写要自己定死，别指望模型猜。

### 13 （必背）
不等于——形状能约束，**含义只能校验**。业务校验要查：枚举值是否真的存在、ID 是否有效、数值范围、用户是否有权限、引用是否可解析、前置条件是否成立、资源预算是否够。不确定的部分要显式标记为"未验证"，而不是假装确定。

schema 太复杂编译不过的处理顺序：只把关键工具标 strict → 把可选参数改成必填（每个大致减半状态空间）→ 简化嵌套 → 拆到多个请求或子 Agent。

### 14 （理解）
通常 **1–2 次**，且只对**解析 / 结构错误**重试；**业务错误由程序直接拒绝**，不让模型绕过约束。连续失败就换模型 / 简化任务 / 转人工，并且每次都进 Trace。

隐藏成本：grammar 编译结果缓存 24 小时（改 `name` / `description` 不会失效，改结构会），而改 `output_config.format` 会让该会话线程的 prompt cache 失效。所以 schema 要版本化管理、不要中途反复改。

### 15 （理解）
不是。它只把"随机挑一个"换成"挑概率最高的那个"，而那个分布本身还受 batch 调度、浮点非确定性等影响，长输出尤其明显。而且"确定"不等于"可靠"——该错的还是会错。

要保证形状靠解码约束（strict / json_schema），要保证语义靠业务校验；temperature 只是调随机性的一个旋钮，不是可靠性开关。

### 16 （必背）
四层，不能互相替代：**抽样快筛**（便宜、抓大幅回退）→ **消融**（逐段删、跑同一套 Eval，看指标是掉了还是变好）→ **全量回归**（发布门禁）→ **held-out 验收**（必须用没参与调优的集合）。

两个数字要会说：**单次观察在概率系统里没有信息量**；评测集规模按 `SE = √(p(1−p)/n)` 定——200 条约 ±2%，要分辨 2 个点需要约 900 条。真实案例：训练集上 98.9% 打平，held-out 上 90.5% vs 78.6%。所以先想清楚"我要证明多大的差异"，再决定集合规模。

### 17 （必背）
因为 Prompt 不是配置文件，是**针对当时那个模型写的控制层**——它和模型是耦合系统，模型一变，同一份 prompt 的收益和代价全变。原来的指令可能变成拐杖：稀释注意力预算、制造规则冲突、在升级后变成负担。

实证：Anthropic 为 Claude 5 代删掉了 80%+ 的系统提示，编码评测无损失；清掉六类拐杖后成本降 14.6%、准确率升 5.3%（错误率腰斩）。所以换代要当成一次完整的选型重做：换模型 + 重新消融清拐杖 + 重跑门禁 + held-out 验收 + 重算缓存定价的影响。

### 18 （理解）
拐杖是**曾经有效、现在只在增加成本**的指令。发现方法就是消融：删掉它跑同一套 Eval——指标没掉就是冗余，指标变好就是拐杖。另一条便宜的信号是查文档里互相矛盾的指令（Anthropic 就是读自己的使用记录时发现同一请求里带着冲突指令的）。

为什么不直接加规则？三重代价：稀释注意力预算、制造规则冲突（模型得额外推理去化解）、模型升级后变成负担。一次消融只要几美元——所以"要不要做"是习惯问题，不是成本问题。

### 19 （必背）
幻觉不是一个 bug，是四件不同的事叠加：① 预训练只有流畅语言的正例、没有真假标签，所以**任意低频事实从统计上就学不出来**；② 评测只按准确率排名时，"猜"的期望收益为正、"弃答"稳定为零，模型被训成应试高手；③ 上下文里根本没有那条信息；④ 信息给了却被稀释、冲突或忽略。

对策必须按来源分开：给证据 + 先摘录再作答 + 引用绑定（治③④）、允许弃答 + 改评分（治②）、上下文管理（治④）。最关键的一个换算：**错误和弃答不能同价**——准确率更低（22% vs 24%）的模型，错误率只要 26% vs 75%，按业务成本算总成本只有对方的 **38%**。

### 20 （理解）
两层：**prompt 层**显式给许可（"不确定就说不确定"）；**评分层**把"自信的错误"罚得比"承认不确定"更重，给恰当的弃答部分分。**第二层更根本**——第一层只是改措辞，第二层才改激励。

长文档（超过 20k token）的做法：先要求逐字摘出相关原文（找不到就明说"没找到"），再基于摘录作答；生成完再自查一遍，每条结论找支撑引用，找不到的直接撤掉。

### 21 （必背）
必要不充分。RAG 降低的是"**无据可依**"这一类（成因③），代价是上下文变长反而可能加剧"**有据不依**"（成因④）。所以接完 RAG 还要做两件事：引用绑定（答案必须能指到具体片段）、答案级评测（和检索级评测分开，别拿召回率冒充正确率）。

口径也要改：汇报用**错误率**不用准确率——准确率对"弃答"和"错误"一视同仁，看不出差别；"准确率 +5.3%"听起来平淡，"错误率减半"是同一件事的另一种说法。

### 22 （必背）
不是挑跑分最高的，而是在**（模型 × effort）二维空间**里、用**每个正确结果的全成本**这一个指标来搜。跑分是那些评测上的表现，不是你的任务分布上的——从 SimpleQA 看，准确率高和错误率低可以是相反方向（24% vs 22% 的准确率，对应 75% vs 26% 的错误率）。

effort 怎么定：跑一次 sweep，对几个档位各跑一遍你的评测集看曲线——平坦说明任务不受思考算力约束，加 effort 没收益；陡峭且需要跨过门槛就加。而且选型不是一次性决策：模型迭代、缓存定价变化、effort 参数引入都会让最优解移动。

### 23 （理解）
不是，两个方向都会坏。太高：effort 曲线是凸的，边际每分成本（$0.704）高于低档平均（$0.465），最后一档多 0.5 分要多花 46%，落在噪声里。太低：**证据不足就收手，而且答案看起来是完整的**——这个更危险。

定档方式是跑一次 sweep 看曲线；延迟敏感场景另看首 token 延迟，而不是总时长。

### 24 （理解）
三个要求：① **已验证**——备用配置必须在 held-out 上过过门禁，不能是"顺手切一个"；② **有明确的质量底线**——降级的目标是保住可用性不是保住质量，所以要知道降级后能接受什么；③ **可观测**——降级本身要打点报警，**不知道自己在降级，比降级更危险**。

另外两条：降级要连 prompt 一起调（便宜模型配好 prompt 后反而更准）；切换时机选在缓存本来就要失效的时刻（比如 compaction 之后，反正要付 miss 的钱）。多模型路由的代价：要维护多套 prompt 与评测、路由判错两头不讨好、排障复杂度上升。
