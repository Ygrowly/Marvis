## 一、教材

### 1. 前提：注意力是一份有限的预算

**先把两个词分清**【事实】：

- **Prompt Engineering** 关心的是"**一条指令怎么写**"——措辞、结构、示例、格式，作用范围是**系统提示那一块文本**。
- **Context Engineering** 关心的是"**这次调用模型到底能看到什么**"——系统规则、当前目标、权威状态、检索证据、工具定义、近期轨迹、长期记忆，以及如何**选择、压缩、隔离、更新**它们。

【推导】**为什么前者不够**？因为 prompt 只是上下文的一个组成部分。一次请求里模型看到的东西，绝大部分不是"你写的那段话"——是工具定义、是历史消息、是检索回来的证据（1.1 会给完整清单）。**前者是局部文本设计，后者是系统级信息架构。** 这个区别在短任务上不明显（prompt 占大头），在 Agent 循环里会立刻放大：循环每转一圈都在**生成新的上下文**（工具结果、状态变化），而没有任何人"写"过它。

**到这里你应该能回答**：为什么"把 prompt 写好"不等于"把上下文管好"？

#### 1.1 先把"上下文窗口"定义清楚【事实】

**上下文窗口（context window）**：一次请求里模型能看到的 **token 总量上限**。它装的不是"你写的那段 prompt"——

| 算进窗口的东西 | 说明 |
|---|---|
| 系统提示 | 每次请求都在 |
| 工具定义（Tool Schema） | 每个工具的 JSON Schema 全文 |
| 全部消息历史 | 含所有工具返回结果、图片、文档 |
| 你这一次的输出 | **模型生成的 token 也占窗口，包括 thinking** |
| 缓存命中的前缀 | **照样占窗口**——缓存改的是你付多少钱，不是占多少地方 |

当前 Claude 模型的窗口是 1M token（Fable 5.1 / Opus 5 / Sonnet 5），单次最多输出 128K。

【事实】几个容易答错的细节：多轮对话里，**上一轮的 thinking block 在 Opus 4.5+ / Sonnet 4.6+ 上默认保留**并像普通输入一样计数（早期 Opus 和所有 Haiku 模型会自动剥掉）；单次请求最多 600 张图片或 PDF 页（200K 窗口的模型是 100）；输入 + `max_tokens` 超出窗口时，4.5 以后的模型不会报错，而是生成到上限后以 `stop_reason: "model_context_window_exceeded"` 结束。

**"1M 很大"是真的，但它是容量，不是质量。**

#### 1.2 为什么"容量大"不等于"用得上"【推导】

Transformer 的注意力让**每个 token 都要和其余每个 token 计算关系**：

```
n 个 token  →  n² 对关系
1M token    →  10¹² 对
```

【推导】两个后果：

1. **预算被摊薄**。n 翻倍，关系数翻 4 倍——多放不是"不亏"，是**边际收益递减**。Anthropic 把它叫 **attention budget**：每引入一个新 token，都从这份预算里扣掉一点。
2. **模型是在短序列上训出来的**。训练数据里短序列远比长序列常见，所以模型对"跨整个窗口的远距离依赖"经验更少、专门参数也更少。

实测表现为 **context rot（上下文腐化）**：窗口里 token 变多，模型**准确回忆其中信息的能力反而下降**。这不是某个模型的 bug，是所有模型共有的特性，只是退化速度不同。

【取舍】所以目标不是"把窗口填满"，而是：

> **找到能让期望结果发生概率最大的、最小的那组高信号 token。**
> （原文：the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome）

#### 1.3 一个反直觉的量化：成本按平方增长【推导】

这条最容易被忽略。**每调用一轮，之前所有历史都要原样重发**——模型是无状态的，它不记得上一轮。

```
一个 40 轮的 Agent 会话，每轮平均新增 15K token

第 40 轮时 prompt 长度 = 40 × 15K = 600K        ← 看起来"窗口还够"
但累计输入 token = 15K × (1 + 2 + … + 40)
                = 15K × 820
                = 12,300K = 12.3M
```

**真实计费是"最后一轮 prompt 大小"的 20.5 倍**——这个 20.5 正好是 (n+1)/2，也就是"平均每一轮历史被重复计费了 20.5 次"。

【推导】一般化：n 轮、每轮新增 k token

```
最后一轮 prompt 长度 = k·n             （线性）
累计输入 token      = k·n(n+1)/2      （平方）
两者之比            = (n+1)/2         （只与轮数有关，与 k 无关）
```

**这就是"长会话贵"的数学原因**：不是单轮贵，是历史被反复重发。它也直接说明了第 4 节为什么要把 prompt caching 单独拎出来算。

### 2. 候选方案：四种控制手段（先各自介绍，不比较）

#### 2.1 选择 Selection【事实】

只把当前步骤真正需要的放进上下文：

- 检索当前步骤相关的文档片段，而不是整个知识库
- 只暴露当前角色允许的工具
- **分阶段加载**，而不是一次性全量注入

#### 2.2 压缩 Compression【事实】

把历史压成摘要。关键不在"压"，在**压什么、留什么**。摘要至少要保留：

- 用户目标与约束
- 已确认的事实**及其来源 ID**
- 已完成 / 未完成步骤
- 关键决策与原因
- **副作用执行记录**
- 未决问题、剩余预算

#### 2.3 隔离 Isolation【事实】

不相干的上下文不要进主窗口：

- 子任务用独立上下文，**只把结构化结果返回**
- 多 Agent 按权限域或专长隔离
- 大产物写对象存储，窗口里只留摘要和引用

#### 2.4 缓存 Caching【事实】

系统提示、稳定的工具定义、大段静态背景放在**前面**且保持不变，交给提供方的 prompt caching；**动态内容一律追加在后面**。

【事实】定价结构（Claude API，2026-09 核实）：缓存**写**按基础输入价的 **1.25×**（5 分钟 TTL）或 **2×**（1 小时 TTL）；缓存**读**按 **0.1×**，**Fable 5.1 是 0.025×**（$0.25/MTok——**官方文档对 Mythos 5.1 标注为「是否同价发布时未定」，虽然它与 Fable 5.1 是同一个模型，但这句话不要说满**）。最短可缓存长度按模型不同：Opus 5 与 Fable 5.1 是 **512** token，Sonnet 5 是 **1,024**，Haiku 4.5 是 **4,096**（**注意这个最短长度不是单调的**：最新一批是 512，反而 Opus 4.6/4.5 与 Haiku 4.5 是 4096）。缓存按前缀字节完全一致匹配，默认 5 分钟过期（每次命中会免费续期）。

### 3. 逐个淘汰（统一指标：每花一个 token 换来的任务成功率）

先立口径：**不比"谁压得更小"，比"每花一个 token，任务成功率提升多少"。**

#### 3.1 "全塞进去"为什么不行【推导】

- **注意力层面**：context rot，关键信息被稀释，准确回忆率下降
- **成本层面**：1.3 的平方曲线
- 【事实】Anthropic 明确说过：等待更大的窗口不是解法——"**对所有尺寸的窗口，上下文污染和信息相关性问题都会持续存在**"（至少在想拿到最强 Agent 表现的场合）

#### 3.2 "只靠摘要"为什么不行【推导】

摘要是**有损且不可逆**的。压缩时判断"这条以后有没有用"是最难的部分——**压得太狠会丢掉当时看不出重要、后来才关键的细节**。

【事实】Anthropic 给的调法是有顺序的：**先把 recall 拉满（保证摘要不漏任何相关信息），再迭代提高 precision（删掉多余内容）**。顺序反过来，丢的信息找不回来。

【事实】另一条边界：**摘要不是审计记录**。原始消息、工具结果、产物必须**外部持久化**，摘要里只放**指针**（artifact ID / 业务键）。理由下一节会看到——副作用记录丢了会重复执行。

#### 3.3 "只靠预检索"为什么不行【推导】

传统 RAG 是**提前**把所有可能相关的数据检索好塞进去。两个问题：

- 预检索要**猜**后面会用到什么，猜错了就是纯浪费 + 噪声
- 索引会**过期**（这正是 Claude Code 不用语法树索引、改用 glob/grep 的原因）

#### 3.4 胜出方案：混合策略（稳定前缀缓存 + 预注入 + 即时检索）【事实】

Claude Code 的实际做法：

- **一部分前期注入**：`CLAUDE.md` 直接进上下文
- **其余按需取**：glob / grep / 读文件，**用到时才加载**
- 模型维护的是**轻量引用**（文件路径、查询语句、链接），不是内容本身

【事实】"即时"（just-in-time）还带来一个附带收益：**引用本身的元数据就是信号**——文件名、所在目录、时间戳都在告诉模型"这是什么、什么时候的、多重要"（`tests/test_utils.py` 和 `src/core_logic/test_utils.py` 暗示的用途完全不同）。

【事实】子 Agent 是隔离的典型实现：它可能烧掉几万 token 去探索，**只回传 1,000–2,000 token 的浓缩结论**，搜索过程的噪声全部留在自己的窗口里。

【取舍】代价是**更慢**（运行时探索比读预计算结果慢），而且**需要工程投入**：工具和启发式设计不好，模型会浪费上下文去试错、走死胡同。

**小结**：四种手段不是四选一，**是一套同时在用的组合**——稳定前缀缓存、按步骤选择、历史压缩、子任务隔离。

### 4. 量化验证：三种策略各算一遍

统一场景：40 轮 Agent 会话，每轮新增 15K token，模型 Opus 5（输入 $5/MTok，缓存写 $6.25/MTok，缓存读 $0.5/MTok）。

**策略 A：什么都不做**

```text
累计输入 = 15K × 820 = 12.3M token
成本     = 12.3M × $5 / 1M = $61.5
```

**策略 B：开 prompt caching（前缀稳定，每轮只有新增的 15K 是新内容）**

```text
缓存读：(12.3M − 0.6M) × $0.5/MTok = $5.85      ← 读价 0.1×
缓存写：0.6M × $6.25/MTok           = $3.75      ← 写价 1.25×
合计 ≈ $9.6                                      （约降到 1/6.4）
```

**但窗口占用一点没少**——第 40 轮的 prompt 还是 600K，注意力稀释也没变。

**策略 C：B + compaction（到 150K 触发，压到约 20K）**

```text
prompt 长度在 20K ↔ 150K 之间锯齿波动，平均约 85K
累计输入 ≈ 40 × 85K = 3.4M          （没压之前是 12.3M）
```

窗口占用和成本**同时**下降。**这就是两者的分工**：

```text
缓存 = 让重复的内容变便宜   （无损，但只对稳定前缀有效，不改占用）
压缩 = 让重复的内容消失     （改占用，但有损，必须留指针）
```

【事实】生产上这两个能力已经是平台内建项：Anthropic 的 **context editing**（自动清理过期的工具调用与结果）在内部 agentic search 评测上单独带来 **+29%**，叠加 **memory tool**（文件式外部记忆）后是 **+39%**；在一次 100 轮的 web search 评测里，context editing 让原本会因上下文耗尽而失败的任务跑完，同时**少用了 84% 的 token**。**Compaction** 的默认触发阈值是 **150,000 输入 token**（可配，最小 50,000）。

**到这里你应该能回答**：为什么 prompt caching 不能替代上下文管理？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "窗口 1M 了，不用管上下文" | 容量 ≠ 注意力质量（context rot）；且历史重发使成本按平方增长 |
| "开了缓存，上下文就变小了" | **缓存只改价格，不改占用**。缓存命中的前缀照样占窗口、照样消耗注意力 |
| "摘要做得好就不用原始记录了" | 摘要**不是审计记录**。原始消息 / 工具结果 / 产物必须外部持久化，摘要只留指针 |
| "上下文多给总没错" | 噪声也是 token。信息变多会**降低**关键信息的利用率 |
| "RAG 和长上下文是替代关系" | 不是。数据小、稳定、无权限差异 → 直接放长上下文更简单；数据大 / 常更新 / 要权限过滤 / 要引用溯源 → RAG 负责候选选择与治理 |
| "压缩可以随便压，越短越好" | 顺序是**先保 recall 再提 precision**。压太狠会丢掉"当时看不出、后来才关键"的信息，且不可逆 |
| "模型升级了/窗口变大了，老办法就废了" | 反例：Claude Code 为 Claude 5 代模型**删掉了超过 80% 的系统提示**且编码评测无损失——**要做的是消融验证，不是凭感觉重写**（[[母题-C3-Prompt版本管理与回归]]） |

【取舍】把这张表读成一句话：**每一条上下文手段都在"信息完整度 / 注意力质量 / 成本"之间换，没有免费午餐，也没有哪一条能单独解决问题。**

## 二、自测

**Q1（计算）**：某 Agent 会话共 30 轮，每轮平均新增 10K token。

问：**最后一轮的 prompt 有多大？累计输入 token 是多少？是最后一轮的多少倍？**

**A1**：

```text
最后一轮 prompt = 30 × 10K = 300K
累计输入        = 10K × (1 + 2 + … + 30)
                = 10K × 30 × 31 ÷ 2
                = 10K × 465 = 4,650K = 4.65M
倍数            = 4.65M ÷ 300K = 15.5 = (30 + 1) ÷ 2
```

【结论】**倍数只和轮数有关，和每轮增量无关**。30 轮是 15.5 倍，40 轮是 20.5 倍。所以"轮数多"比"单轮大"更伤成本——这一点决定了长任务必须做压缩，而不只是减少单次注入。

**Q2（计算）**：沿用 Q1 的会话，模型 Opus 5（输入 $5/MTok、缓存写 $6.25/MTok、缓存读 $0.5/MTok）。假设前缀稳定，每轮只有新增的 10K 是新内容。

问：**不开缓存和开缓存分别花多少？**

**A2**：

| | 算式 | 结果 |
|---|---|---|
| 不开缓存 | 4.65M × $5/MTok | **$23.25** |
| 开缓存 · 读 | (4.65M − 0.3M) × $0.5/MTok = 4.35M × $0.5/MTok | $2.175 |
| 开缓存 · 写 | 0.3M × $6.25/MTok | $1.875 |
| 开缓存 · 合计 | | **$4.05** |

→ 约降到 **1/5.7**。

【补充】**但第 30 轮的 prompt 还是 300K**——缓存省的是钱，（几乎）不省窗口占用，也完全不解决注意力稀释。要动占用只能靠压缩或隔离。

**Q3（计算）**：compaction 的默认触发阈值是多少？一个 1M 窗口的会话，如果每轮新增 15K token 且不做任何处理，**第几轮会触到窗口上限？第几轮会触发 compaction？**这两个数的差距说明了什么？

**A3**：

```text
窗口上限：1,000K ÷ 15K ≈ 66.7  → 第 67 轮左右触顶
           （会以 stop_reason: "model_context_window_exceeded" 结束）
compaction：150K ÷ 15K = 10   → 第 10 轮触发
```

【说明】**compaction 不是"快满了才压"，而是在窗口还剩 85% 的时候就动手了。** 因为触发依据不是"装不装得下"，而是**"注意力从什么时候开始明显稀释"**——这也是"窗口是容量，不是质量"这句话在工程上的直接体现。

**Q4（纠错）**：下面这段话哪里不准确？

> "我们开了 prompt caching，所以历史消息不再占用上下文窗口了，等于把窗口容量变大了。"

**A4**：两处错。

1. **缓存不改变占用**。缓存命中的前缀照样占窗口、照样消耗注意力预算；缓存改变的是**你为这些 token 付多少钱**（读价 0.1×）。
2. **"窗口容量变大"这个说法本身错**。容量是模型属性，不会因为计费方式变化。

【准确说法】"prompt caching 让重复的稳定前缀按 0.1× 计价，降低的是**成本和首 token 延迟**，**不改变窗口占用，也不缓解 context rot**。"

**Q5（纠错）**：下面这段话哪里不准确？

> "上下文压缩就是把历史总结一下，总结得越短越好，这样能塞更多新内容进去。"

**A5**：**"越短越好"方向反了。**

- 正确的调法是**先保 recall 再提 precision**：先把每一条相关信息都抓进摘要（保证不漏），再迭代删冗余。为了短而牺牲 recall，丢掉的是"当时看不出重要、后来才关键"的细节。
- 这种丢失**不可逆**——如果原始内容没有外部持久化，就真没了。
- 而且摘要**必须保留可回溯的指针**（artifact ID、业务键、**已完成副作用记录**）。副作用记录尤其不能丢：丢了会导致恢复时**重复执行**已经做过的写操作。

**核心不变量 / 主线**：
**上下文是"一次调用的视图"，不是状态本身**——它每一轮都要重新装配、重新付钱、重新争夺注意力。
所以任何"把上下文当仓库用"的做法（塞满、只靠摘要、只靠预检索）都会在三个维度上同时付代价：**注意力、成本、可恢复性**。

**完整回答骨架**：先纠正前提（窗口 = 容量 ≠ 质量）→ n² 与 attention budget → context rot → "最小高信号 token 集"这个目标 → 四种手段及各自边界 → 成本平方增长的算式 → 缓存与压缩的分工 → Claude Code 的混合策略实例 → 收束到"上下文是视图，不是仓库"

**完整回答（口述稿）**：
先纠正前提：上下文窗口是**容量**不是**质量**——注意力是 n² 关系，token 越多这份预算越被摊薄，实测表现就是 context rot：越长越容易忽略中间的信息、越容易捡起不相关的旧内容。所以目标不是把窗口塞满，而是找到**最小的那组高信号 token**。

工程上是四种手段的组合：**选择**（只放当前步骤所需）、**压缩**（摘要 + 外部持久化指针）、**隔离**（子任务独立窗口，只回传 1–2K 的浓缩结论）、**缓存**（稳定前缀复用）。压缩和缓存不能互相替代：压缩解决**占用**（有损，必须留指针），缓存解决**价格**（无损，只对稳定前缀有效）。

成本这一面必须说清是**平方增长**：每轮都要把全部历史原样重发一遍，40 轮 × 15K 的会话累计输入 12.3M，是最后一轮 prompt 的 20.5 倍；缓存能把重复内容降到 0.1× 计价，但**不改占用**。

收口一句话：**上下文是视图，不是仓库**——权威状态在数据库和结构化状态里，上下文是从它装配出来的。

**分层要点**：
- **结论**：窗口 = 容量 ≠ 质量；目标是最小高信号 token 集，不是塞满窗口。
- **推导链**：n² 注意力 → 预算被摊薄 → context rot → 四种手段（选择 / 压缩 / 隔离 / 缓存）→ 压缩管占用、缓存管价格。
- **量化**：40 轮 × 15K → 累计 12.3M，是末轮 prompt 的 20.5 倍；缓存读 0.1×、写 1.25×。
- **边界与常见误解**：窗口变大也治不了 rot（污染与相关性问题对所有尺寸都在）；压缩必须留指针——**副作用记录丢了会重复执行写操作**；结尾要分清 Context / State / Memory 三种权威性。

**追问**（先说后看）

1. **压缩和缓存到底谁解决什么？** —— 压缩解决**占用**（有损，必须留指针），缓存解决**价格**（无损，只对稳定前缀有效）。两者互补，不可互相替代。
2. **子 Agent 为什么能省上下文？** —— 它在自己的干净窗口里探索，可能烧几万 token，但**只把 1,000–2,000 token 的浓缩结论**回传。搜索过程的噪声全部隔离在子 Agent 内部。
3. **摘要里必须保留什么？** —— 目标与约束、已确认事实**及其来源 ID**、已完成/未完成步骤、关键决策与原因、**副作用执行记录**、未决问题与剩余预算。前几项丢了大不了重做，**副作用记录丢了会重复执行写操作**。
4. **窗口会一直涨，这套还有用吗？** —— 有用。Anthropic 的判断是"**对所有尺寸的窗口，上下文污染和信息相关性问题都会持续存在**"；而且平方成本来自"重发"这个机制，不来自窗口大小。
5. **什么情况下反而不该做 RAG？** —— 数据小、稳定、无权限差异、不需要引用溯源时，直接放长上下文更简单也可能更好。**决策由质量、成本、延迟、权限的评测驱动，不由架构偏好驱动。**
6. **`CLAUDE.md` 该写多长？** —— **轻**。写清楚仓库是干什么的，然后把大部分 token 花在**代码库里的坑（gotchas）**上，不要写"看文件系统就知道"的显然内容；需要多条验证指令时，做个 verification skill 让它在需要时被调用（渐进披露）。

**同类变体**

- 「Context / State / Memory 三者的区别？」——Context 是**一次调用的可见 token（视图）**；Agent State 是**运行过程的结构化状态（运行权威）**；Memory 是**跨会话复用且获准保存的信息（派生，需要治理）**。三者的权威性和生命周期完全不同，混在一起就会出现"拿模型自己的摘要当业务事实"。
- 「Memory 应该存什么？」——只存**跨任务稳定、对未来有用、经过授权、能被治理**的信息。临时推理、模型猜测、敏感数据不自动写入。每条记忆要有来源、主体、作用域、置信度、更新时间、TTL 和删除机制。
- 「多 Agent 的上下文怎么管？」——按**权限域或专长**隔离，每个子 Agent 一个干净窗口，只回传结构化结论，最终由主 Agent 合成。
