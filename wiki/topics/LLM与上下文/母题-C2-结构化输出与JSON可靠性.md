**题目**：面试官问——"你们让模型返回 JSON，怎么保证解析一定成功？解析失败了怎么办？重试几次？"

**母题**：**模型的输出是逐 token 采样出来的，下游程序需要的是确定的结构。这条鸿沟要在哪一层堵住——决定的是"经常重试"还是"结构上不会错"，也决定你要为此付什么代价。**

## 一、教材

### 1. 前提：为什么"求它输出 JSON"天然不可靠

#### 1.1 生成是逐 token 采样【事实】

模型在每个位置做的是：**从整个词表（几万到十几万 token）里，按概率分布挑一个**。它不是在"写一个 JSON 对象"，是在**一个位置一个位置地预测下一个 token**。

【推导】这一条直接推出三件事：

1. **合法结构不是天然保证，是概率上更可能**。模型见过海量 JSON，所以"下一个 token 是 `"`" 的概率很高——但"很高"不是 1。
2. **越到后面越容易崩**。输出越长，前面每一步都不出错的条件越多；长 JSON 的尾部（闭合括号、最后一个字段）是失败高发区。
3. **提示只能降低概率，不能消除概率**。你在 prompt 里写十遍"必须返回合法 JSON"，改的是分布，不是采样规则。

**那三个采样旋钮呢？它们也只改分布，不改规则**【事实】：

| 参数 | 它做什么 | 常见误区 |
|---|---|---|
| **Temperature** | 把概率分布拉平（更随机）或拉尖（更集中） | **设成 0 也不承诺全链路确定** |
| **Top-p** | 只在累积概率达到 p 的候选集合里采样 | 不该与高 Temperature 盲目叠加调参 |
| **max_tokens / stop** | 控制终止与输出预算 | 设太短会**把 JSON 截断**，以 `stop_reason: "max_tokens"` 结束——**这种输出会绕过 schema 校验** |

【推导】**为什么 Temperature = 0 不等于"输出确定"**：它只是把"随机挑一个"换成"挑概率最高的那个"。但**"概率最高的那个"本身就不是常量**——

1. **模型版本**：快照一变，权重就变，同一个位置的最大概率 token 可能就换了
2. **数值层面**：同一份输入在不同硬件、不同批处理并行下，浮点求和顺序不同，两个候选的分数可能极其接近甚至翻转
3. **上下文**：哪怕差一个空格，分布就不同

【推论】所以**确定性要从系统设计里要，不能从采样参数里要**：结构化输出把语法封死（本卡第 3 节）、固定模型版本、确定性的业务校验、缓存、以及评测兜底（[[母题-C3-Prompt版本管理与回归]]）。
**"我把 temperature 调成 0 了所以结果稳定"是一句会被追问倒的话**——正确的说法是"我把不确定性挡在了系统边界外"。

#### 1.2 失败不是一种，是四种【事实】

面试里说"加个 try-catch 就行"的人，通常只想到第一种：

| 失败形态 | 例子 | 谁能在生成时防住 |
|---|---|---|
| **语法错** | 少一个逗号、字符串没闭合 | 解码约束 ✅ |
| **缺字段** | 没有 `reason` 字段 | 解码约束 ✅ |
| **类型不对** | `"amount": "18.5"`（字符串而非数字） | 解码约束 ✅ |
| **枚举越界 / 语义错** | `"status": "pendng"`；或者 `user_id: 99999` 这个人根本不存在 | 解码约束只防前者，**后者谁都防不住** |

**这一栏的分界线就是本节的主线**：左边三种是**语法问题**，可以靠约束解码从根上消灭；右边两种是**语义问题**，只能在业务层拦。

---

### 2. 候选方案：三层约束（先各自介绍，不比较）

#### 2.1 提示约束【事实】

在 prompt 里给出 schema 描述、字段含义、少量示例，要求模型按格式返回。**这是最古老、零成本、也最不可靠的一层。**

#### 2.2 解码约束（constrained decoding）【事实】

Claude 平台提供两个互补的能力：

- **JSON outputs**（`output_config.format`）：约束**回复正文**的格式，保证是符合你 schema 的 JSON
- **Strict tool use**（`strict: true`）：约束**工具名与工具参数**，用 grammar-constrained sampling 保证符合 schema

原理是**在采样那一刻**把不合法 token 的概率压成 0——模型不是"尽量写对"，是**语法上不可能写错**。

#### 2.3 事后校验 + 有限修复【事实】

拿到输出后：`parse` → `schema 校验` → 失败则**把精简后的错误反馈给模型重试**（通常 1–2 次）→ 连续失败则换模型 / 简化任务 / 转人工。每次失败都要进 Trace，不能静默吞掉。

---

### 3. 逐个淘汰（统一指标：一次请求的"结构可用率"，以及失败时的代价）

#### 3.1 为什么只靠提示不够【推导】

提示改的是概率分布，**不改采样规则**。所以：

- 首次成功率永远小于 1，且**随输出长度下降**（见 1.1 第 2 条）
- 失败率不能靠"把 prompt 写得更好"压到 0，只能压低

【事实】而且"多给示例"这条路正在变窄：Anthropic 明确说，对新一代模型，**给工具使用示例反而会把模型限制在一个探索空间里**，"number one rule for tool usage was to give examples" 已经是过时做法——**更好的做法是设计接口本身**（比如把 status 做成 `pending / in_progress / completed` 的枚举，光是列出来就在提示怎么用）。

#### 3.2 为什么只靠事后重试不够【推导】

重试能救成功率，但要在两个维度上付账：**token 成本**和**尾延迟**。

```text
重试要把输入原样重发一遍 → 失败的那一次，输入和输出都白付
而且延迟是累加的：第 2 次尝试的延迟 = 2 × 单次延迟
```

【取舍】所以重试的正确用法是**兜底**，不是**主路径**。把它当主路径，等于承认"我每次都在赌"。

#### 3.3 解码约束的代价：不是免费的【事实】

把语法错误消灭在采样时是有账单的，而且**账单随 schema 复杂度指数增长**：

| 限制 | 值 | 含义 |
|---|---|---|
| 每请求 strict 工具数 | **20** | 只有标了 `strict: true` 的才算，非 strict 不计 |
| 可选参数总数 | **24** | 所有 strict schema 里"不在 `required` 里"的参数合计 |
| union 类型参数 | **16** | 用 `anyOf` 或类型数组的参数；**它们尤其贵，因为编译成本是指数级的** |

【事实】超出后 API 返回 400 "Schema is too complex for compilation"；即使没超表里的限制，还可能在 **180 秒编译超时**上挂掉。**原因是 schema 复杂度不是一个维度**：可选参数、union 类型、嵌套深度、工具数量会互相作用，编译出来的 grammar 可能大得不成比例。

【事实】几个容易忽略的细节：

- **编译结果缓存 24 小时**；改 **`name` 或 `description` 不会失效**，改 schema 结构会
- **改 `output_config.format` 会让该会话线程的 prompt cache 失效**——所以别在中途反复改 schema
- 有 `stop_reason` 会**绕过 schema**：**`refusal`**（安全拒答，拒答消息优先于 schema 约束，输出可能不匹配）和 **`max_tokens`**（被截断）

#### 3.4 胜出方案：三层叠加，各管一段【取舍】

```text
提示约束   → 降低出错概率（免费，但不保证）
解码约束   → 消灭语法错误（保证，但有编译成本与上限）
事后校验   → 拦住语义错误（必须，因为上面两层都管不了）
```

【推论】**这三层不是三选一，因为它们管的根本不是同一件事。** 面试里能说清"哪一层管哪一类错"，比背任何一层的 API 都有价值。

::figure structured-output-layers.svg | 三种约束手段各自在哪一层生效 | 越早介入代价越低；解码约束把非法 token 概率压成 0，但编译成本指数增长且有硬上限；业务语义永远只能靠最后一层

**到这里你应该能回答**：为什么"用了 JSON Schema 就万无一失"是错的？（语法保证 ≠ 语义保证，而且 refusal / max_tokens 会绕过）

### 4. 量化验证：重试到底值不值

统一场景：一次结构化抽取，输入 3K token、输出 500 token，模型 Opus 5（输入 $5/MTok、输出 $25/MTok）。

```text
单次成本 = 3K × $5/1M + 500 × $25/1M
         = $0.015 + $0.0125 = $0.0275
```

**重试策略：最多尝试 3 次（首次 + 重试 2 次），三次都失败转人工。**

```text
期望尝试次数 = 1 + p + p²        （p = 单次失败率）
转人工比例   = p³
```

| 单次失败率 p | 期望尝试次数 | 成本放大 | 转人工比例 |
|---|---|---|---|
| 10%（解码约束 + 简单 schema） | 1 + 0.1 + 0.01 = **1.11** | +11% | 0.1% |
| 40%（纯提示约束 + 长输出） | 1 + 0.4 + 0.16 = **1.56** | +56% | 6.4% |

【推导】注意最后两列的关系：**失败率从 40% 降到 10%，重试次数只降了 29%，但转人工率降了 64 倍**（6.4% → 0.1%）。原因是转人工率是 **p 的三次方**——**尾部风险对 p 极其敏感**。

【取舍】这解释了为什么解码约束值得付 grammar 编译的固定成本：**它买的不是"少重试几次"，是把 p 压到接近 0，从而把 p³ 压到可以忽略。** 而如果你的失败率本来就在 40%，重试策略救不了你——你只是把 6.4% 的请求推给人工。

**到这里你应该能回答**：为什么"失败就重试"在高失败率下会失效？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "用了 JSON Schema，下游可以直接信任结果" | **只保证了结构与类型**。枚举值是否存在、ID 是否有效、用户是否有权限、状态前置条件是否满足——schema 全都管不了 |
| "解析失败就重试，重试能兜住" | 重试**拿延迟买成功率**：P99 延迟翻倍，且失败率高时转人工率按 p³ 放大。它是兜底不是主路径 |
| "加了解码约束，`stop_reason` 就不用管了" | **`refusal` 和 `max_tokens` 都会绕过 schema**。前者是拒答消息优先于约束，后者是被截断 |
| "枚举值写了就一定按写的来" | 【事实】模型可能在**大小写**上偏离（期望 `conversation topic 3`，得到 `Conversation Topic 3`），**不报错、无特殊 stop_reason、正常结束**。要大小写不敏感比较，且**避免只靠大小写区分的枚举值** |
| "schema 越详细越好" | 每个**可选参数**大致让一部分 grammar 状态空间翻倍；union 类型是**指数级**成本。**"把可选改成必填"比"少写字段"更有效** |
| "工具都给 strict 最稳" | 每请求最多 **20 个** strict 工具。**只把"违反了会真出事"的工具标 strict**，其余靠模型自然遵守 + 事后校验 |
| "给模型几个示例，输出就稳了" | 【事实】对新一代模型，**示例反而会限制探索空间**。优先改接口设计（枚举、参数命名、默认值），而不是堆示例 |

【取舍】读成一句话：**结构正确是"约束"出来的，语义正确只能"校验"出来——两者不能互相替代。**

## 二、自测

**Q1（计算）**：一次结构抽取任务，单次调用平均 2 秒，**首次成功率 90%**，失败重试，最多尝试 3 次（首次 + 2 次重试）。

问：**P50 延迟、平均延迟、P99 延迟各是多少？**这个结果说明了什么？

**A1**：

```text
P(一次成功)     = 0.9          → 延迟 2s
P(需要两次)     = 0.1 × 0.9 = 0.09   → 延迟 4s
P(需要三次)     = 0.1² × 0.9 = 0.009 → 延迟 6s
P(三次都失败)   = 0.1³ = 0.001       → 转人工

P50 = 2s        （90% 的请求一次就过）
平均 = 2 × (1 + 0.1 + 0.01) = 2 × 1.11 = 2.22s
P99：累计到 2s 是 90%，累计到 4s 是 99% → P99 ≈ 4s
```

【结论】**重试把成功率从 90% 拉到 99.9%，代价是平均延迟 +11%、P99 延迟翻倍。** 这就是"拿延迟买成功率"的具体数量——所以不能把重试当主路径，它是兜底。

**Q2（计算）**：平台文档说"**每个可选参数大致让一部分 grammar 的状态空间翻倍**"，并给出三个硬上限。

问：**如果 schema 里有 16 个可选参数，状态空间相对"全必填"放大了多少倍？三个上限分别是多少？**

**A2**：

```text
2^16 = 65,536 倍
```

三个上限：**每请求 20 个 strict 工具 / 24 个可选参数 / 16 个 union 类型参数**。

【补充】为什么 union 类型被单独点名"尤其贵"？因为它不是加法而是**乘法**——每个 union 参数都会分裂出一条新的语法分支。这也是文档给的降复杂度顺序的原因：

```text
1. 只把关键工具标 strict          （减少工具数）
2. 减少可选参数 → 尽量改成 required（每个大致减半状态空间）
3. 简化嵌套结构                    （嵌套 × 可选 是复合放大）
4. 拆到多个请求 / 子 Agent         （最后手段）
```

**注意顺序**：**"把可选改成必填"比"少写几个字段"更有效**——一个字段如果是必填的，它对状态空间的贡献是 1；可选的话大约翻倍。

**Q3（计算）**：同一任务，单次成本 $0.0275（输入 3K @ $5/MTok、输出 500 @ $25/MTok）。

问：**首次成功率 60% 时（复杂 schema + 长输出），期望成本是多少？转人工率是多少？**对比第 4 节表里 90% 那一行，说明什么？

**A3**：

```text
期望尝试次数 = 1 + 0.4 + 0.4² = 1 + 0.4 + 0.16 = 1.56
期望成本     = $0.0275 × 1.56 = $0.0429      （+56%）
转人工率     = 0.4³ = 0.064 = 6.4%
```

对比：

| 首次成功率 | 期望尝试 | 成本放大 | 转人工率 |
|---|---|---|---|
| 90% | 1.11 | +11% | **0.1%** |
| 60% | 1.56 | +56% | **6.4%** |

【结论】**成本只放大 5 倍差距（11% → 56%），转人工率却放大 64 倍（0.1% → 6.4%）**——因为转人工率是 p³。所以在高失败率下，"多试几次"这个策略基本失效：**你付出的成本在涨，兜底却在塌。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们用了 JSON Schema 约束模型的输出，所以下游可以直接信任这个结果。"

**A4**：三处。

1. **schema 只管结构，不管语义**。它保证"类型对、必填字段在、枚举在范围内"，但保证不了：枚举值在数据库里真的存在、引用的 ID 有效、**这个用户有权限**、状态前置条件满足、资源预算够。这些必须由程序独立校验。
2. **两种 `stop_reason` 会绕过 schema**：`refusal`（安全拒答，拒答消息优先于 schema 约束）和 `max_tokens`（截断）。
3. **还有枚举大小写的已知坑**：模型可能返回 `"Conversation Topic 3"` 而不是期望的 `"conversation topic 3"`，**不报错、正常结束**。要大小写不敏感比较，且避免设计只靠大小写区分的枚举值。

【准确说法】"JSON Schema 保证了**结构合法**；**语义合法**必须由业务校验独立完成，并且要显式处理 `refusal` / `max_tokens` 两类会绕过 schema 的终止原因。"

**Q5（纠错）**：下面这段话哪里不准确？

> "结构化输出会让模型变笨，所以我们只在最后一步才用它。"

**A5**：**结论对了一半，归因错了。**

- 约束解码确实会**收窄生成空间**，但要说清收窄的是哪一层：它把**不合语法的 token 概率压成 0**，影响的是"能写出什么形状"，不是"能想到什么内容"。
- "只在最后一步用"是个合理的工程建议，但真正的理由是**编译有固定成本、缓存有失效代价**：schema 要编译成 grammar（结果缓存 24 小时；改 `name` / `description` **不会**失效，改结构会）；而且**改 `output_config.format` 会让该会话线程的 prompt cache 失效**——所以不要中途反复改 schema。
- 更准确的做法是：**只把"违反了会真出事"的工具标 `strict`**（每请求上限 20 个），其余靠模型自然遵守 + 事后校验。

【准确说法】"约束解码在**语法层**收窄生成空间，代价是 grammar 编译成本（随 schema 复杂度指数增长）与缓存失效；所以应该按"违反后果"来挑哪些工具用 strict，而不是全量开或全量关。"

## 三、面试输出（学完再看）

**一句话结论**：模型的输出是**逐 token 采样**出来的，所以"结构正确"不是天然保证，而是要在**正确的层**堵住。三层各管一段：**提示约束**只降低概率（免费但不保证）、**解码约束**（`strict` / `json_schema`）把不合语法的 token 概率压成 0（保证，但 grammar 编译成本随 schema 复杂度指数增长，且有 20 工具 / 24 可选参数 / 16 union 的硬上限）、**事后校验**拦住语义错误（必须，因为上面两层都管不了）。**关键认知：JSON 合法 ≠ 业务合法**——枚举是否存在、ID 是否有效、用户是否有权限，只能自己校验；而且 `refusal` 和 `max_tokens` 会绕过 schema。重试的正确位置是**兜底不是主路径**，因为它是拿延迟买成功率，且转人工率按 p³ 放大。

**恢复关键词**：逐 token 采样 → 长输出尾部易崩 / 四种失败：语法·缺字段·类型·枚举越界 / 三层约束各管一段 / 解码约束 = 采样时概率压成 0 / grammar 编译指数成本 / 20 strict 工具 · 24 可选参数 · 16 union / 改 name·description 不失效，改结构失效 / 改 format 会让 prompt cache 失效 / refusal 与 max_tokens 绕过 schema / 枚举大小写坑 / JSON 合法 ≠ 业务合法 / 重试 = 拿延迟买成功率，p³ 放大尾部

**核心不变量 / 主线**：
**语法正确可以在生成时"约束"出来，语义正确只能在校验时"拦"出来。**
两者的分界线是**"这件事是不是只关于形状"**：形状（类型、必填、枚举范围）可以在采样时封死；**含义（存在性、权限、前置条件）永远需要一次真实的业务查询**——模型看不见你的数据库。

**完整回答骨架**：先纠正前提（生成是采样，不是写结构）→ 四种失败形态，指出分界线 → 三层约束及各自的代价 → grammar 编译成本与三个硬上限 → `stop_reason` 绕过与枚举大小写坑 → "JSON 合法 ≠ 业务合法" → 重试的期望次数与转人工率算式 → 收束到"形状能约束、含义只能校验"

**追问**（先说后看）

1. **重试几次合适？** —— 通常 **1–2 次**，且只对**解析/结构错误**重试；**业务错误由程序直接拒绝**，不让模型绕过约束。连续失败就换模型 / 简化任务 / 转人工，并且每次都进 Trace。
2. **schema 太复杂编译不过怎么办？** —— 按顺序试：只把关键工具标 strict → **把可选参数改成必填**（每个大致减半状态空间）→ 简化嵌套 → 拆到多个请求或子 Agent。
3. **怎么给下游一个可信的结果？** —— 三层：结构由解码约束保证；**语义由业务校验保证**（枚举存在性、范围、权限、引用、前置条件、资源预算）；不确定的部分**显式标记为"未验证"**，而不是假装确定。
4. **为什么不能靠"多给几个示例"来稳输出？** —— 【事实】对新一代模型，**示例反而会把模型限制在某个探索空间里**。更好的做法是**设计接口**：把 status 做成枚举、参数名写清楚、给合理的默认值——**光是列出枚举值本身就在提示怎么用**。
5. **改 schema 有什么隐藏成本？** —— grammar 编译结果缓存 24 小时，**改 `name` / `description` 不会失效，改结构会**；而**改 `output_config.format` 会让该会话线程的 prompt cache 失效**。所以 schema 应该版本化管理、不要中途反复改。
6. **Temperature 调成 0，输出就确定了吗？** —— **不是。** 它只把"随机挑一个"换成"挑概率最高的那个"，但那个"最高"会随**模型快照、数值计算顺序、上下文任何一处变化**而变。确定性要从**系统设计**要：解码约束封死语法、固定版本、确定性的业务校验、评测兜底。**"temperature=0 所以稳定"是一句会被追问倒的话。**

**同类变体**

- 「工具调用参数错误怎么防？」——工具参数走 **strict tool use**（同样的 grammar 约束），但注意每请求 20 个的上限；超过就把工具拆到多个请求或子 Agent。
- 「NL2SQL 算不算结构化输出？」——算，但它的"语义校验"层特别厚：**SQL 语法合法 ≠ 表存在 ≠ 有权限 ≠ 代价可接受**。所以必须"生成 → 解析 → 干跑 → 权限校验 → 拒绝或执行"（[[母题-C4-幻觉的成因与可控性]]）。
- 「为什么模型偶尔会在枚举上大小写出错？」——**官方文档记录了这个现象**（期望 `conversation topic 3`，返回 `Conversation Topic 3`，**不报错、无特殊 `stop_reason`、正常结束**），但**没有给出机制解释**。所以防御只按现象做，别去猜实现：**比较写成大小写不敏感**，并且**不要设计只靠大小写区分的枚举值**。

**关联母题**：[[母题-C1-上下文组装与窗口预算]]（每个工具 schema 都占上下文，这决定了"能不能全量声明"）· [[母题-C3-Prompt版本管理与回归]]（schema 变更要走回归）· [[母题-C4-幻觉的成因与可控性]]（结构合法 ≠ 内容为真）· [[母题-M17-排行榜与防超卖]]（同一逻辑：应用层校验是优化，权威约束才是正确性）

**可迁移场景**：

- **RuleArena**：审查结论的结构化输出（问题清单 + 严重度 + 证据引用）。**结构由 schema 保证，但"引用的规则条款真的存在"必须独立校验**——这正是"JSON 合法 ≠ 业务合法"的项目实例。
- **数驭穹图**：NL2SQL 是结构化输出的重型版本。**SQL 语法合法只是第一层**，后面还有表存在性、权限、代价评估；这解释了为什么必须"干跑 + 权限校验"才能执行。
- **EnergyOps**：30 个 MCP 工具——**注意 strict 有每请求 20 个的上限**，这直接决定了哪些工具标 strict、哪些走自然遵守 + 事后校验；也部分解释了为什么要做能力分组与延迟加载。
- **Ovanta**：前端表单渲染依赖结构稳定，所以 AI 输出的结构可靠性直接决定前端能不能渲染，属于"用户体验级"的约束需求。

**方言差异（与 SQL / 类型系统对照）**：SQL 也是一种"结构化输出"，但它的约束发生在**执行时**——由数据库解析器拒绝非法语句，**不允许你指定文法**；LLM 这边可以把文法前置到**采样时**。反过来，SQL 有权威的元数据（表结构、权限）可以校验语义，**LLM 的输出没有**——这就是为什么 LLM 的结构化输出必须自带一层业务校验，而 SQL 不需要。
