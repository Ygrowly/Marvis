## 一、教材

### 1. 前提：账单是四种 token 的加权和

#### 1.1 四类计价【事实】（2026-09 核实）

| 类别 | 单价（Opus 5） | 相对输入 |
|---|---|---|
| 普通输入 | $5 / MTok | 1× |
| **缓存写入** | $6.25 / MTok（5 分钟 TTL）<br>$10 / MTok（1 小时 TTL） | 1.25× / 2× |
| **缓存读出** | **$0.50 / MTok** | **0.1×** |
| **输出** | **$25 / MTok** | **5×** |

::figure cache-economics.svg | 同一个 token，四种价钱；以及让缓存归零的几条路径 | 上半部分用柱子画出四类计价——缓存读只有输入的 1/10、输出的 1/50；下半部分列出命中要同时满足的五个条件和最常把命中率打回零的六条路径

【推导】看清楚这张表，降本的方向就定了：

```text
输出      是输入的 5 倍     → "话多"比"上下文长"更贵
缓存读出  是输入的 1/10    → 命中部分是 10 倍杠杆
缓存写入  是输入的 1.25 倍 → 写了不读，比不缓存还贵 25%
```

【推论】**最后一行是整张卡的关键**：**缓存不是"开了就省"，是"命中了才省"。** 写了没读，你付的是 1.25 倍。

#### 1.2 为什么用量还会平方增长【事实】

回顾 [[母题-C1-上下文组装与窗口预算]] 的结论——**每一轮请求都要把全部历史原样重发**：

```text
n 轮、每轮新增 k token：
  最后一轮 prompt 长度 = k·n           （线性）
  累计输入 token        = k·n(n+1)/2   （平方）
```

【推论】所以账单里有两块成本，来源完全不同：

```text
第一块：每一轮**新增**的内容      → 线性，跟任务本身多大有关
第二块：每一轮**重发**的历史      → 平方，跟会话多长有关
```

**缓存打的是第二块**（把重发的历史变便宜），**压缩打的是第二块**（把重发的历史直接删掉），**降 effort 打的是输出那一块**。**三个杠杆打的是不同的成本项——所以它们不是互相替代的。**

#### 1.3 缓存的机制：三个必须知道的东西【事实】

**① 断点（breakpoint）**
缓存**只在断点处写入**：标记一个 block 为断点，就只写一条"到这个 block 为止的前缀哈希"的条目。**哈希是累积的**——断点之前任何一处变了，哈希就变了，命中就没了。

**② 回看窗口（lookback）**
读的时候，系统先在断点位置找匹配；**找不到就往前一个 block 一个 block 地找，最多找 20 个位置**。它找的是"**之前的请求写过的条目**"，**不是"稳定内容"**。

**③ TTL 与最短长度**

```text
默认 TTL：5 分钟（每次命中会免费续期）
可配 1 小时 TTL：写价翻倍到 2×
最短可缓存长度：Opus 5 / Fable 5.1 是 512 token
                Sonnet 5 是 1,024        Haiku 4.5 是 4,096
不够长 → 静默不缓存，不报错（usage 里两个 cache 字段都是 0）
```

**到这里你应该能回答**：为什么"写进缓存但没被读到"比"不缓存"更贵？

### 2. 候选方案：四个降本杠杆（先各自介绍，不比较）

#### 2.1 提高缓存命中率【事实】

- 把**稳定部分放前面**（工具定义、系统提示），**增长的内容追加在后面**
- **易变值移出前缀**（时间戳、请求 ID、每轮变化的上下文）
- **工具定义不要重排**（任何顺序变化都会打断点）
- **少用的工具标记延迟加载**（`defer_loading`）——它们留在缓存前缀之外，用到时再通过工具搜索加载进来
- **系统提示的更新用"消息"形式追加**，而不是改写系统提示本身
- **预热缓存**：会话开始时发一个 `max_tokens: 0` 的请求，把前缀先写进缓存
- **移动断点**：用自动缓存让断点自动跟到最后一个可缓存 block
- **长工具调用用 1 小时 TTL**（默认 5 分钟的 TTL 从请求开始算，同步工具调用或子 Agent 跑超 5 分钟，回来时缓存已过期）
- **在缓存本来就要失效的时刻做别的变更**（比如 compaction 之后本来就是大改，那是切换模型或 effort 的好时机）

#### 2.2 减少用量【事实】

- **Compaction**：到阈值时自动把历史摘要掉。默认触发 **150,000 输入 token**，可配，最小 50,000
- **清理过期的工具调用与结果**（context editing）——这是最轻的一档压缩
- **截断**：控制 `max_tokens`；注意输入 + `max_tokens` 超出窗口时，4.5 以后是生成到上限后以 `stop_reason: "model_context_window_exceeded"` 结束

#### 2.3 去掉 prompt 拐杖【事实】

见 [[母题-C3-Prompt版本管理与回归]]。**这是唯一一个同时降本和提质的杠杆。**

#### 2.4 调 effort / 换模型【事实】

见 [[母题-C5-模型选型与降级三角]]。**这一条改的是单价和输出量，不动用量。**

### 3. 逐个淘汰（统一指标：**每个正确结果的成本**，且降本不能伤质量）

先立口径——**降本不是目标，"每个正确结果的成本下降"才是**：

```text
每个正确结果的成本 = (单次成本 + 失败率 × 失败代价) ÷ 成功率
```

【取舍】**如果为了降本把成功率拉下来，你只是在把成本转移到人工兜底上。**

#### 3.1 为什么"提命中率"排第一【推导】

三个理由，一个比一个硬：

```text
① 无损     ——不改变模型看到的任何内容，纯粹改计费
② 改动小   ——不动 prompt、不动架构，通常是配置层的事
③ 可观测   ——有 cache diagnostics，能定位"两个请求在哪里分叉了"
```

【推论】**命中率是唯一一个"改错了也不会变坏、只会变回原价"的杠杆。** 其他三个都有下行的风险：压缩会丢信息、去拐杖需要评测、降 effort 会伤质量。

【事实】量级参考：Anthropic 在 Contextual Retrieval 里给过一个测算——**用 prompt caching 做上下文增强，一次性成本约 $1.02 每百万文档 token**；另一处提到缓存让"延迟降 >2×、成本降最多 90%"。

#### 3.2 "压缩"为什么是最后手段【推导】

因为**它是有损的，而且不可逆**：

- 记忆里丢掉的细节找不回来（除非原始内容外部持久化）
- 摘要必须保留**副作用执行记录**，否则恢复时会重复执行写操作
- 调法有顺序：**先把 recall 拉满，再迭代提高 precision**（[[母题-C1-上下文组装与窗口预算]]）

#### 3.3 压缩与缓存不是二选一【推导】

```text
缓存 → 让重复的内容变便宜    （无损，不改窗口占用）
压缩 → 让重复的内容消失      （有损，改窗口占用）
```

【推论】**它们的收益可以叠加，但优先级不同**：先做无损的（命中率），再做双赢的（去拐杖），最后做有损的（压缩）。

#### 3.4 胜出方案：按"是否有损"排序的四层【取舍】

```text
第一层  提高缓存命中率     ——无损，先做，也是最大的一笔
第二层  去掉 prompt 拐杖   ——双赢（降本 + 提质）
第三层  减少用量           ——有损，必须留指针，且要进 Trace
第四层  调 effort / 换模型 ——换质量，必须用 held-out 验证（C5）
```

**到这里你应该能回答**：为什么"降本 50%"这个问题，不该从"砍上下文"开始答？

### 4. 量化验证：三笔账

**第一笔：全命中能把账单压到多少？**

```text
场景：100 轮会话，稳定前缀 100K（系统提示 + 工具定义），每轮新增 2K
模型：Opus 5，输入 $5/MTok
```

**不开缓存：**

```text
第 i 轮 prompt = 100K + 2K × i
累计输入 = 100 × 100K + 2K × (1 + 2 + … + 100)
        = 10,000K + 2K × 5,050
        = 10,000K + 10,100K = 20,100K = 20.1M

成本 = 20.1M × $5/MTok = $100.5
```

**开缓存（自动断点跟到最后一轮，每轮都命中）：**

```text
每轮：读 (100K + 2K×(i−1)) @ 0.1×   ＋   写 2K @ 1.25×

累计读 = 0.1 × [100 × 100K + 2K × (0 + … + 99)]
       = 0.1 × [10,000K + 2K × 4,950]
       = 0.1 × 19,900K = 1,990K

累计写 = 1.25 × 2K × 100 = 250K

等价总量 = 1,990K + 250K = 2,240K = 2.24M
成本     = 2.24M × $5/MTok = $11.2
```

```text
降幅 = 1 − 11.2 / 100.5 = 88.9% ≈ 89%
```

【结论】**把命中率做到接近 100%，账单降到约 1/9。** 而这个改动**没有动模型看到的任何一个 token**——这就是"先做无损的"这个顺序的价值。

【注意】这个 89% 依赖两个前提：**前缀确实稳定**，以及**TTL 内每轮间隔不超过 5 分钟**。任一条不成立，账就不是这个账（见第二、三笔）。

**第二笔：一行时间戳值多少钱？**

```text
系统提示 50K，其中第 3 个 block 放了一个动态时间戳
→ 每轮前缀哈希都不同 → 缓存永不命中

每轮代价：
  未命中：写 50K @ 1.25× = 62.5K 等价
  本该是：读 50K @ 0.1×  =  5.0K 等价
  差额 = 57.5K 等价 / 轮

100 轮：57.5K × 100 = 5,750K = 5.75M 等价
成本 = 5.75M × $5/MTok = $28.75
```

【结论】**一行时间戳，在 100 轮会话里值 $28.75。** 而它**不会报错**——你只会看到账单偏高，看不到原因。所以要用缓存诊断去定位"两个请求在哪里分叉了"（这是 3.1 里"可观测"那一条的实际价值）。

【推论】**这正是"改动最小、收益最大"的典型**：把时间戳从前缀移到消息里，几行代码，$28.75。

**第三笔：20-block 回看窗口什么时候会失效？**

```text
Turn 1：10 个 block，断点在 block 10，无历史条目 → 在 10 处写入
Turn 2：15 个 block，断点在 15 → 15 处没有条目，往前找 → 在 10 处命中
        只重新处理 block 11–15，并在 15 处写新条目
Turn 3：35 个 block，断点在 35 → 检查 35 到 16（共 20 个位置）
        → 一条都没找到。turn 2 写的 block 15 条目，**恰好落在窗口外一格**
        → 完全未命中
```

【结论】**"自动断点跟着走"只在"每轮新增少于 20 个 block"时成立。** 超过 20 就会有掉出去的风险，这时要**额外加一个显式断点**（最多 4 个），在更早的位置开一个新回看窗口。

【反直觉补充】一轮里**连续的工具调用块算作 1 个位置**（连续的 `tool_use` 算一个，连续的 `tool_result` 也算一个）。所以"一轮里发了 20 个并行工具调用"**不会**把上一轮的条目挤出窗口。

**到这里你应该能回答**：为什么"上下文没变长，账单却突然涨了"是一个真实可能发生的情况？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "开了缓存就降 90%" | **"开了"不等于"命中"**。90% 是**命中部分**的降幅，不是总账单的降幅。而且**写了没读到要付 1.25×，比不缓存更贵** |
| "缓存命中靠内容稳定" | **靠前缀逐字节相同，且必须是之前请求"写过"的条目**。系统不会"帮你找稳定内容缓存起来"——回看找的是历史写入记录 |
| "上下文没变长，成本应该稳定" | 不一定。**命中率掉了，账单立刻涨**；而命中率的影响因素（TTL 过期、工具定义重排、中途改 effort、回看窗口掉出去）**都不会体现在上下文长度上** |
| "降本就是压缩上下文" | **顺序反了**。优先级是：提命中率（无损）→ 去拐杖（双赢）→ 减少用量（有损）→ 调 effort（换质量）。**压缩是最后手段** |
| "压缩得越短越省" | 压缩的正确调法是**先保 recall 再提 precision**；压太狠会丢掉"当时看不出、后来才关键"的信息，而且**不可逆** |
| "输出和输入一个价" | **输出是输入的 5 倍**。所以"让模型别啰嗦"往往比"砍上下文"更有效——但要小心，**别把推理过程一起砍掉**（effort 过低会让模型"证据不足就收手"，[[母题-C5-模型选型与降级三角]]） |
| "缓存前缀不占窗口" | **照样占**。缓存改的是价格，不是占用，也不缓解 context rot（[[母题-C1-上下文组装与窗口预算]]） |
| "工具越多，上下文越贵，只能砍工具" | 可以**延迟加载**：声明但标记 `defer_loading` 的工具**留在缓存前缀之外**，用到时再通过工具搜索加载进来——**代价从"每轮都付"变成"用到才付"** |
| "系统提示要改就直接改" | 改成**以消息形式追加**（mid-conversation system message），可以保住缓存。**直接改写系统提示会打断整个前缀** |
| "想省事就全程用 5 分钟 TTL" | 有长同步工具调用或子 Agent 时，缓存会在结果回来前过期，下一轮变成 1.25× 重写。**这类场景该用 1 小时 TTL** |

【取舍】读成一句话：**降本的第一性是"同一个 token 有四种价钱"——先把钱花在便宜的档位上，再考虑少花。**

## 二、自测

**Q1（计算）**：某 Agent 会话 100 轮，稳定前缀 100K token（系统提示 + 工具定义），每轮新增 2K。模型 Opus 5（输入 $5/MTok、缓存写 $6.25/MTok、缓存读 $0.5/MTok）。

问：**不开缓存和全命中各花多少？降幅多少？**这个降幅有没有动到模型看到的任何内容？

**A1**：

```text
不开缓存：
  第 i 轮 prompt = 100K + 2K × i
  累计输入 = 100 × 100K + 2K × (1+…+100)
          = 10,000K + 2K × 5,050 = 20,100K = 20.1M
  成本 = 20.1M × $5/MTok = $100.5

全命中：
  累计读 = 0.1 × [10,000K + 2K × 4,950] = 0.1 × 19,900K = 1,990K
  累计写 = 1.25 × 2K × 100 = 250K
  等价总量 = 2,240K = 2.24M
  成本 = 2.24M × $5/MTok = $11.2

降幅 = 1 − 11.2 / 100.5 ≈ 88.9%
```

【结论】**降到约 1/9，而模型看到的 token 一个都没变。** 这就是"无损杠杆优先"的具体价值——**它的收益量级和压缩是同一个数量级，但代价为零。**

【前提提醒】这个 89% 依赖：**前缀真的稳定** + **每轮间隔不超过 TTL**。任一条不成立，账就不成立。

**Q2（计算）**：系统提示 50K token，其中第 3 个 block 放了一个**每轮都变的动态时间戳**，导致缓存永不命中。

问：**100 轮会话下，这一行时间戳的代价是多少？**它会在哪里被发现？

**A2**：

```text
每轮差额：
  未命中（写）：50K × 1.25 = 62.5K 等价
  本应（读）  ：50K × 0.1  =  5.0K 等价
  差额 = 57.5K 等价 / 轮

100 轮 = 57.5K × 100 = 5,750K = 5.75M 等价
成本   = 5.75M × $5/MTok = $28.75
```

【结论】**一行时间戳 = $28.75（100 轮会话）。**

它会在哪里被发现？**不会在日志里**——没有报错、没有异常、上下文长度也正常。**只会体现在账单上，而且表现为"单位成本莫名其妙偏高"。** 所以要有 **cache diagnostics**：它能比较相邻两次请求，**精确指出前缀从哪个位置开始分叉**。

【推论】**这一类问题的通用特征：不出错、不变慢、只是变贵。** 所以成本治理必须配可观测性，不能只看"有没有报错"。

**Q3（计算）**：某会话使用自动缓存（断点自动跟到最后一个可缓存 block）。

```text
Turn 1：10 个 block，断点在 10
Turn 2：15 个 block，断点在 15
Turn 3：35 个 block，断点在 35
```

问：**Turn 3 会命中吗？如果想让它命中该怎么办？**另外，"一轮里 20 个并行工具调用"会不会把上一个条目的挤出窗口？

**A3**：

```text
Turn 3 的断点在 block 35
回看窗口检查 35 往下数 20 个位置：block 35, 34, …, 16
turn 2 写入的条目在 block 15 —— 恰好是第 21 个位置，**在窗口外**
→ 未命中，整个前缀按新内容重新写入
```

**解决办法**：在 block 15 加**第二个显式断点**——每个断点开启一个独立的回看窗口，第二个窗口从 15 开始往前找，就能命中 turn 2 的写入。（最多可以定义 **4 个**断点，专门用于这种"增长把断点推出窗口"的情况。）

【反直觉补充】**不会。** 一轮里**连续的 `tool_use` 块算作 1 个位置**，连续的 `tool_result` 块也算 1 个位置。所以"一轮里发了 20 个并行工具调用"**不会**把上一轮的缓存条目挤出窗口。

【结论】**缓存失效的常见原因不是"内容变了"，而是"结构变了"。** 上面三条账（时间戳 / 工具重排 / 回看窗口）没有一条改变了内容量——它们改变的是**"这段内容还能不能被认出来"**。

**Q4（纠错）**：下面这段话哪里不准确？

> "我们开了 prompt caching，所以模型成本会降 90%。"

**A4**：三处。

1. **"开了"不等于"命中"**。缓存按**前缀逐字节相同**匹配，且读的时候找的是"**之前请求写过的条目**"（回看最多 20 个 block）。一行动态时间戳、工具定义顺序变化、中途改 effort、TTL 过期，都会让命中归零。
2. **90% 是"命中部分"的降幅**，不是总账单的降幅。**读价 0.1× 只作用于被读中的那部分**；新增内容、输出、未命中的部分都照原价。总降幅取决于命中率。
3. **写而没读到会更贵**：缓存写价 1.25×（或 1h 的 2×），比不缓存还高。还有个静默前提：**要达到模型的最短可缓存长度**（Opus 5 是 512，Sonnet 5 是 1,024，Haiku 4.5 是 4,096），**不够长就直接不缓存、且不报错**——要检查 `usage` 里的两个 cache 字段才能发现。

【准确说法】"prompt caching 让**被命中的**前缀按 0.1× 计价；实际降幅 = 命中率 × 90% 左右，而且**未命中的写入会更贵**。所以真正要管的是两个指标：**缓存命中率**和**最短可缓存长度是否满足**。"

**Q5（纠错）**：下面这段话哪里不准确？

> "要降本，最直接的就是把上下文压缩一下，历史砍短就省了。"

**A5**：**顺序反了，而且这不是最直接的一条。**

正确的优先级（按"是否有损"排）：

```text
第一层  提高缓存命中率   —— 无损，量级和压缩相当（上面算过：89%）
第二层  去掉 prompt 拐杖 —— 双赢（降本 + 提质）
第三层  减少用量         —— 有损，必须留指针
第四层  调 effort / 换模型 —— 换质量，必须 held-out 验证
```

三条具体问题：

1. **压缩是有损且不可逆的**：丢掉的细节找不回来（除非原始内容外部持久化）；摘要里必须保留**副作用执行记录**，否则恢复时会重复执行写操作。
2. **压缩压的是"占用"，缓存压的是"价格"**——两者打的是不同的成本项，**不能互相替代**。而且压缩会改变前缀，**可能顺带把缓存也打断**（反过来说，compaction 之后是"缓存本来就要失效"的时机，适合顺便做模型/effort 切换）。
3. **还有一个更便宜的杠杆被漏掉了：输出**。输出单价是输入的 5 倍，"减少啰嗦"往往比"砍上下文"更有效——但**别把推理过程一起砍掉**（effort 过低会让模型"证据不足就收手"，而且答案看起来是完整的）。

【准确说法】"降本按'是否有损'排序：先把命中率做到接近 100%（无损），再去掉 prompt 里的拐杖（双赢），然后用 compaction 和工具结果清理压用量（有损、要留指针），最后才考虑调 effort 或换模型（要 held-out 验证）。"

## 三、面试输出（学完再看）

**一句话结论**：降本的第一性是——**同一个 token 有四种价钱**：普通输入 1×、缓存写入 1.25×（1 小时 TTL 是 2×）、**缓存读出 0.1×**、**输出 5×**。所以优先级按"是否有损"排：**① 提高缓存命中率**（无损，实测能把 100 轮会话的账单降到约 1/9，而模型看到的 token 一个没变）；**② 去掉 prompt 拐杖**（唯一降本又提质的杠杆）；**③ compaction 和工具结果清理**（有损，必须留指针，默认在 150K token 触发）；**④ 调 effort / 换模型**（换质量，要 held-out 验证）。而缓存这一层最反直觉的地方是：**"开了"不等于"命中"**——前缀逐字节相同、同一模型同一 effort、TTL 内、达到最短长度、在 20-block 回看窗口内，**五个条件同时满足才命中**；写了没读到还要付 1.25×，比不缓存更贵。

**恢复关键词**：四类价钱：1× / 1.25×(2×) / 0.1× / 5× / 写而不读更贵 / 命中五条件：逐字节·同模型同 effort·TTL 内·够长·回看 20 block / 最短长度 512·1024·4096，不够长静默不缓存 / 一行动态值 = $28.75（100 轮）/ 失败-回看窗口 20 个 block，超出要加断点（最多 4 个）/ 连续工具块算 1 个位置 / 降本顺序：无损 → 双赢 → 有损 → 换质量 / 缓存改价格、压缩改用量 / defer_loading / 1 小时 TTL 给长工具调用 / 预热 max_tokens: 0

**核心不变量 / 主线**：
**降本不是"少放内容"，是"让放进去的内容被认出来"。**
命中率是唯一一个**改错了也不会变坏**的杠杆（最差就是回到原价）；其余三个都有下行风险。所以正确的顺序是**先做无损的、再做双赢的、最后做有损的**——这个顺序就是"先量后砍"。

**完整回答骨架**：先给四类价钱（这才是第一性）→ 写而不读更贵这个反直觉点 → 平方计费与三块成本（新增/重发/输出）→ 缓存五条件 → 提命中率的具体动作 → 降本四层与排序理由 → 三笔账（89% / 一行时间戳 / 回看窗口）→ 收束到"先让内容被认出，再考虑少放"

**追问**（先说后看）

1. **命中率怎么监控？** —— 平台提供 **cache diagnostics**，能比较相邻两次请求、**指出前缀从哪个位置开始分叉**。要盯的是命中率和 `usage` 里的 cache 字段（两个都是 0 说明根本没缓存上，通常是不够长）。
2. **缓存为什么没命中？** —— 按概率排查：**前缀里有易变值**（时间戳 / ID / 每轮变化的上下文）→ 落到了断点之后还好，落在断点之前就全崩；**工具定义被重排**；**中途改了模型或 effort**（设置渲染在前缀里）；**TTL 过期**（同步工具调用 / 子 Agent 跑超 5 分钟）；**一轮新增超过 20 个 block，断点被推出回看窗口**。
3. **工具太多，上下文塞不下怎么办？** —— 用**延迟加载**：全部声明但把少用的标 `defer_loading`，它们**留在缓存前缀之外**，用到时再通过工具搜索加载。**代价从"每轮都付"变成"用到才付"**，而且不打断缓存。
4. **什么时候该用 1 小时 TTL？** —— 有**长同步工具调用或子 Agent**时。默认 5 分钟的 TTL 从请求开始算，工具跑超 5 分钟，回来时缓存已过期，下一轮变成 1.25× 重写。1 小时 TTL 的写价是 2×，所以要算一下切换频率。
5. **什么时候做模型 / effort 切换最划算？** —— **在缓存本来就要失效的时刻**。比如 compaction 之后：对话被重写，缓存本来就要重建，那正是顺便切模型或调 effort 的好时机——**你反正在付 miss 的钱**。
6. **压缩的阈值该设多少？** —— 平台默认 **150,000 输入 token**（可配，最小 50,000）。但更该问的是"**我的注意力从什么时候开始明显稀释**"——那个量级往往远小于窗口上限（[[母题-C1-上下文组装与窗口预算]]）。

**同类变体**

- 「怎么预估一次请求多少钱？」——先算 token：用 **token counting API** 在发送前估计输入量；再按四类价钱加权。**注意它不支持 server tools 和 MCP 连接器**，那类请求只能从响应的 `usage` 里拿真实数字。
- 「批处理能不能省钱？」——可以，**批量处理有 50% 折扣**（结构化输出也兼容批处理）。适合非实时的离线评测和大批量抽取。
- 「缓存会不会影响数据保留？」——会。结构化输出的 **JSON schema 本身会被临时缓存最多 24 小时**用于优化；而且 schema 的缓存**不与消息内容享受同样的保护**——所以**不要把敏感信息写进 schema 的属性名、枚举值或正则**。

**可迁移场景**：

- **EnergyOps**：30 个 MCP 工具的工具定义每轮都要付——**这是"延迟加载"最直接的收益点**。同时日志和大表结果先聚合再进上下文，压的是"新增"那一块的成本。
- **数驭穹图**：SQL 结果过大写 Artifact、只回传统计与样本——**这是"减少新增"的典型**，同时避免把大结果反复重发（否则就是平方计费）。
- **RuleArena**：长审查会话是**缓存收益最大的场景**（稳定前缀大、轮次多）；但审查证据的注入如果每轮都变，反而会打断前缀——**这需要在"证据完整"和"前缀稳定"之间设计分层**（稳定规则进前缀，逐轮证据追加在后）。

**方言差异（与传统后端成本对照）**：传统后端的成本是"**资源 × 时间**"（CPU 小时、存储 GB·月），优化手段是扩容、降配、加缓存；LLM 的成本是"**token × 单价**"，而**同一份 token 在不同位置（前缀 / 新增 / 输出 / 缓存）单价差 50 倍**。所以 LLM 成本优化的核心动作是"**把 token 搬到便宜的档位上去**"——这是传统成本优化里没有的动作。**把 LLM 账单当服务器账单看，就会只想到"少用点"，而想不到"换个档位计价"。**
