# 母题 C5 · 模型选型与降级三角

> **模块**：LLM 与上下文工程 / 选型与容量
> **所属主线**：一 · 模型为什么不可靠（既然不可靠是前提，就得决定用谁的不可靠）
> **层级**：B · 标准级（"为什么贵模型不一定划算"能从成功率与失败代价算出来；但**你的业务里失败值多少钱**是取舍，没有唯一答案——所以不是 A）
> **关联母题**：[[母题-C4-幻觉的成因与可控性]]（"准确率更高的模型"可能错误率更高）· [[母题-C3-Prompt版本管理与回归]]（换模型是最大的一次 prompt 变更）· [[母题-C6-成本与长上下文截断]]（同一个"成本"，一个管单价一个管用量）
> **素材来源**：Claude 平台文档 Models overview / Pricing / Prompt caching / Effort（**2026-09-12 联网核实**）、Anthropic《Reducing cost and improving performance with Claude Platform》（2026-09-08，作者 Lance Martin，含 effort 曲线与 hillclimb 案例）、OpenAI《Why language models hallucinate》（**2025-09-04**，含 SimpleQA 的准确率/错误率对照）。**其中"每个正确结果的全成本"指标、三笔换算、降级链路的设计要求、自测题，为本次新增（待你核对）**

**导读**：必懂 3 件事（① 选型有四维不是一个排行榜 ② effort 曲线是凸的，两个方向都会坏 ③ 降级不是换个模型名）· 读完约 12 分钟 · 需要先懂：[[母题-C4-幻觉的成因与可控性]]（不然会误以为"准确率高"就是"错得少"）

**题目**：面试官问——"你们线上用的哪个模型？为什么用它不用便宜的那个？如果主模型挂了或者限流了怎么办？"

**母题**：**模型的能力、延迟、单价是三个显性的取舍维度，但真正决定费用的是第四个——effort。那么，"更贵"到底买到了什么，你算得出来吗？**

## 一、教材

### 1. 前提：选型是一个多目标问题，指标要自己定义

#### 1.1 四个维度【事实】

| 维度 | 是什么 | 常被忽略的点 |
|---|---|---|
| **能力** | 复杂推理、长程任务、工具调用准确性 | "能力强"要用**你自己的任务**衡量，不是通用跑分（[[母题-C4-幻觉的成因与可控性]]） |
| **延迟** | 从请求到可用结果的时间 | 不是"快慢"一个数——**首 token 延迟和总时长是两件事**（流式场景看前者，批处理看后者） |
| **单价** | 输入 / 输出的每百万 token 价格 | **输入和输出的差价很大**（通常 5 倍），所以"上下文长"和"话多"是两种不同的贵 |
| **effort** | 模型"花多大力气"的档位 | **这个维度最容易被当成不存在的**。同一模型不同 effort 的成本和表现可以差好几倍 |

#### 1.2 现价表【事实】（2026-09 核实）

| 模型 | 输入 | 输出 | 上下文窗口 | 最大输出 | 定位 |
|---|---|---|---|---|---|
| Claude Fable 5.1 | $10 / MTok | $50 / MTok | 1M | 128K | 高难度推理、长程 Agent |
| Claude Opus 5 | $5 / MTok | $25 / MTok | 1M | 128K | 复杂 Agent 与企业任务 |
| Claude Sonnet 5 | $2 / MTok | $10 / MTok | 1M | 128K | 速度与智能的平衡点 |
| Claude Haiku 4.5 | $1 / MTok | $5 / MTok | **200K** | 64K | 最快、接近前沿 |

【事实】缓存价格：**写 1.25×**（5 分钟 TTL）或 **2×**（1 小时 TTL），**读 0.1×**，**Fable 5.1 是 0.025×**（官方对 Mythos 5.1 标注为「发布时未定」，不要说成已确认）。

**注意最后这一行**——缓存读价的差异**会让同一家的两个模型在长会话场景下的成本排序发生变化**：Fable 5.1 的单价比 Fable 5 贵不了多少，但它的缓存读价是 **$0.25 vs $1.00 每 MTok**（1/4）。所以"哪个模型更便宜"这个问题，**在长短会话下答案不同**。

#### 1.3 输出比输入贵 5 倍，这决定了优化方向【推导】

```text
Opus 5：输入 $5/MTok，输出 $25/MTok   → 输出贵 5 倍
```

【推论】所以：

- **"话多"比"上下文长"更贵**（同等 token 数下）——一个啰嗦的 prompt 要求（"请详细解释每一步"）可能比多塞 10K 上下文还费钱
- **减少输出是最直接的省钱手段**，但和"详细推理能提高准确率"直接冲突
- **effort 的本质就是"用多少输出 token 换准确率"**——它把上面这个冲突做成了一个可调旋钮

::figure effort-curve.svg | effort 曲线的形状：两个方向都会坏 | 横轴 effort、纵轴得分，曲线是凸的；低端的问题是证据不足就收手，高端的问题是想过头；右侧是两条实测曲线的数字，以及"强模型配低 effort 可能压过弱模型配高 effort"

**到这里你应该能回答**：为什么"哪个模型更便宜"这个问题，在短会话和长会话下答案可能不同？

### 2. 候选方案（先各自介绍，不比较）

#### 2.1 固定用最强模型【事实】

全部流量走 Fable 5.1 或 Opus 5。**实现最简单，没有路由逻辑，质量上限最高。**

#### 2.2 固定用最便宜模型 + 高 effort【事实】

全部走 Haiku 4.5 或 Sonnet 5，把 effort 拉高来"补能力"。

#### 2.3 按任务难度路由【事实】

轻任务（分类、抽取、格式化）走小模型，重任务（多步推理、长程 Agent）走大模型。**路由依据可以是规则（任务类型）、也可以是模型自己判断（先小模型试，不确定再升级）。**

#### 2.4 评测驱动的联合搜索【事实】

把**模型 × effort × prompt** 当成一个联合空间来搜：用训练集搜索配置，用 held-out 验收。Anthropic 的 hillclimb 工具做的就是这件事——它会**读失败的训练样本**去定位该怎么改（补规则、换模型、调 effort）。

#### 2.5 降级链路（"三角"里的第三条边）【事实】

主模型不可用（限流、超时、故障）或成本超预算时，切到备用模型。要点是：

```text
降级 ≠ 换模型名
降级 = 换一个"已经用你自己的评测验证过"的配置
```

### 3. 逐个淘汰（统一指标：**每个正确结果的全成本**）

这是本卡最重要的一次口径选择。**不能比"单次调用多少钱"，也不能比"准确率多高"**——要合起来算：

```text
每个正确结果的全成本 = (单次成本 + 失败率 × 单次失败代价) ÷ 成功率
```

【推导】这个公式把三个东西绑在了一起：**单价、能力、以及失败在你业务里的代价**。缺任何一项都没法选型。

#### 3.1 为什么"固定最强"不一定对【推导】

能力强不等于划算，因为**存在"够用"这个门槛**：

```text
门槛以下：能力不足 → 失败 → 付失败代价（可能远高于模型费）
门槛以上：能力过剩 → 成功的边际收益很低，但你一直在付高价
```

【推论】所以问题不是"哪个最强"，而是"**我的任务在哪个档位跨过门槛**"。**跨过门槛之后多付的能力钱，是纯浪费。**

#### 3.2 为什么"便宜模型 + 拉高 effort"是个陷阱【推导】

看起来"用 effort 补能力"很合理，但它撞上 effort 曲线的**凸性**：

【事实】在 FrontierCode Diamond 上：

```text
low  effort：11.5% 得分，$5.35 / 任务
max  effort：30.9% 得分，$19.00 / 任务

低档平均每分成本 = $5.35 / 11.5  = $0.465
边际每分成本     = ($19.00 − $5.35) / (30.9 − 11.5)
                 = $13.65 / 19.4 = $0.704
```

**边际比低档的平均还贵 50%**——曲线是凸的，后面的分越来越贵。

【事实】另一条曲线更极端。Humanity's Last Exam（Fable 5.1，无工具）：low 约 53% @ $0.30/题，max 约 61% @ $2.23/题；而**从次高档升到 max 这一步，只多约 0.5 个百分点，成本却多 46%**——**这 0.5 个点落在 run-to-run 的噪声里**（原文：the gain inside the benchmark's run-to-run noise）。

【取舍】**高端的问题不只是贵，是"贵了却看不出差别"。** 而低端也有自己的坑（见下）。

#### 3.3 低 effort 的失败模式同样真实【事实】

effort 设太低时，模型**证据不足就收手**：

- 少调工具（从 3 次搜索退化成只看第一条结果）
- 在困难步骤上少想
- 跳过它本来会自己做的检查

【事实】**结果最危险的地方在于：答案看起来是完整的。** 原文说得很直接——"The answer looks finished, but it's built on partial information."

【推论】所以 effort 的两个方向都会坏：**低端坏在"看不出来它没查全"，高端坏在"看不出来它白花了钱"。**

#### 3.4 一条反直觉的推论：强模型 + 低 effort 可能压过 弱模型 + 高 effort【事实】

【事实】在 CursorBench 3.2 上，**Claude Fable 5.1 在低 effort 下达到 Fable 5 在高 effort 下的水平，成本约为三分之一**。

两个原因：

```text
① 新模型在低 effort 下"每个任务做的工作更少"（不是更笨，是不啰嗦）
② Fable 5.1 的缓存读价是 $0.25/MTok，Fable 5 是 $1.00/MTok
   → 即使按 Fable 5 的价格算，低 effort 的 Fable 5.1 也便宜约 40%
```

【推论】这说明**"模型代际"和"effort 档位"不是同一个旋钮**。降 effort 不等于降能力；**升级模型 + 降 effort 可以同时改善成本和表现**。所以选型应该在"模型 × effort"的二维空间里搜，而不是先选模型再定 effort。

#### 3.5 胜出方案：分层路由 + 联合搜索 + 已验证的降级【取舍】

```text
主路径   ：按任务难度路由到（模型 × effort）组合
调优路径 ：在训练集上搜"模型 × effort × prompt"，读失败样本决定改哪一项
验收     ：held-out 集合（训练集饱和后就失去分辨力，见第 4 节）
降级路径 ：预定义并验证过的备用配置；触发条件可观测；降级本身要打点
```

**到这里你应该能回答**：为什么"用 effort 补能力"这个想法，在曲线上是站不住的？

### 4. 量化验证：用"每个正确结果的全成本"算两笔

**第一笔：那个客服 benchmark 的完整账**（数据来自 3.2 / 3.4 的同一组实验）

```text
起点：Opus 4.8 默认（high effort）   →  held-out 78.6%，成本约 5¢ / 工单
终点：Sonnet 5 低 effort + 补规则    →  held-out 90.5%，成本     1¢ / 工单
```

设**一次失败的代价 = $1**（人工兜底 + 客诉，相对模型费是 20–100 倍）：

```text
原始配置：
  每次尝试期望成本 = $0.05 + 0.214 × $1 = $0.264
  每个正确结果     = $0.264 ÷ 0.786 = $0.336

最终配置：
  每次尝试期望成本 = $0.01 + 0.095 × $1 = $0.105
  每个正确结果     = $0.105 ÷ 0.905 = $0.116
```

【结论】**每个正确结果的成本降到 34.5%**（$0.336 → $0.116），而**模型单价只降到 1/5**。

【关键】**为什么不能只看单价？** 因为单价降 80% 的同时成功率降了，失败代价吃掉了大部分收益。**换成"更好的模型"也一样**——如果失败代价是 $10 而不是 $1：

```text
原始：(0.05 + 0.214 × 10) / 0.786 = $2.786
最终：(0.01 + 0.095 × 10) / 0.905 = $1.061
→ 比值仍是 38%，但绝对差距从 $0.22 拉到 $1.72
```

【取舍】**失败代价越高，"选便宜的"这条路越危险，而"选对的"越值钱。** 所以在算这笔账之前，你必须先回答：**一次失败在我的业务里值多少钱？**

**第二笔：训练集饱和后就失去分辨力**

同一个实验里：

```text
训练集上：最终配置 98.9%  vs  起点 98.9%   →  打平！
held-out ：最终配置 90.5%  vs  起点 78.6%   →  高 11.9 个点
```

【推论】**两个结论的方向一致（降级是对的），但幅度完全不同。** 训练集上你会说"没有损失"，held-out 上才是"明显更好"。

原因是**天花板效应**：98.9% 已经接近这个评测集能达到的上限，**它没有空间再区分好坏**。

【工程含义】**当训练集接近饱和时，它是无效信号。** 这时候唯一能回答"到底有没有变好"的，是没参与搜索的那部分数据（[[母题-C3-Prompt版本管理与回归]]）。

**到这里你应该能回答**：为什么"训练集上打平"不能证明"降级无损"？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "选跑分最高的" | 跑分是**那些评测上的**表现，不是你的任务分布上的。而且从 SimpleQA 数据看，**准确率高和错误率低可以是相反方向**（24% vs 22% 的准确率，对应 75% vs 26% 的错误率） |
| "便宜模型 + 拉满 effort = 性价比最优" | effort 曲线是**凸的**：边际每分成本（$0.704）高于低档平均（$0.465）；HLE 上最后一档多 0.5 分要多花 46%，**落在噪声里** |
| "effort 拉满最保险" | 反方向也有坑：effort 太低会**证据不足就收手**，而且**答案看起来是完整的**。两个方向都会坏，只能标定 |
| "选型是一次性决策" | 它不是。模型迭代、缓存定价变化（Fable 5.1 读价 $1→$0.25）、effort 参数引入，都会让最优解移动。**上面那个案例里，"换个更便宜的模型"最后反而更准** |
| "降级就是把模型名换掉" | 换模型是**最大的一次 prompt 变更**（[[母题-C3-Prompt版本管理与回归]]）。降级路径必须是**用你自己的评测验证过的配置**，而不是"顺手切一个" |
| "降级了质量差一点可以接受" | 降级的**目标**是保住可用性（不超时、不报错、不熔断），不是保住质量。所以要**明确降级后的质量底线**，并让它可观测——**不知道自己在降级，比降级本身更危险** |
| "只看单价就能比出谁便宜" | 必须用 **每个正确结果的全成本** =（单次成本 + 失败率 × 失败代价）÷ 成功率。单价只是分子的一项 |

【取舍】读成一句话：**选型不是选一个模型，是选一组"模型 × effort × prompt"配置，并且用你自己的失败代价把它们换算成同一个单位。**

## 二、自测

**Q1（计算）**：某客服 Agent 的两套配置（同一组实验的实测数据）：

```text
配置 A（起点）：Opus 4.8 默认 high effort   → held-out 78.6%，成本 5¢/工单
配置 B（终点）：Sonnet 5 低 effort + 补规则 → held-out 90.5%，成本 1¢/工单
```

设**一次失败的代价 = $1**。

问：**两个配置"每个正确结果的全成本"各是多少？**如果把失败代价改成 $10，结论会变吗？

**A1**：

```text
公式：每个正确结果的全成本 = (单次成本 + 失败率 × 失败代价) ÷ 成功率

配置 A：
  失败率 = 1 − 0.786 = 0.214
  每次尝试期望成本 = $0.05 + 0.214 × $1 = $0.264
  每个正确结果     = $0.264 ÷ 0.786 = $0.336

配置 B：
  失败率 = 1 − 0.905 = 0.095
  每次尝试期望成本 = $0.01 + 0.095 × $1 = $0.105
  每个正确结果     = $0.105 ÷ 0.905 = $0.116
```

**比值 = $0.116 / $0.336 ≈ 34.5%** → 降到约三分之一。

把失败代价换成 $10：

```text
配置 A = (0.05 + 0.214 × 10) / 0.786 = $2.786
配置 B = (0.01 + 0.095 × 10) / 0.905 = $1.061
比值 ≈ 38%（结论方向不变，绝对差距从 $0.22 拉到 $1.72）
```

【结论】**结论不变，但"失败代价越高，选型越值钱"。** 注意即便失败代价高达 $10，配置 B 仍然更优——**因为它不只是更便宜，它在 held-out 上也更准**。

【补充】真正会翻转结论的情形是：**一个配置更便宜但更不准**。这时失败代价就是那个决定性的数：

```text
若单次成本 1¢ 的配置成功率只有 60%，失败代价 $1：
  (0.01 + 0.4 × 1) / 0.6 = $0.683   → 比配置 A 还贵
```

**所以在算这笔账之前，必须先回答：一次失败在我的业务里值多少钱。**

**Q2（计算）**：FrontierCode Diamond 上：low effort 11.5% 得分 / $5.35 每任务；max effort 30.9% / $19.00。

问：**低档的"平均每分成本"是多少？从 low 走到 max 的"边际每分成本"是多少？**这个差距说明什么？

**A2**：

```text
低档平均每分成本 = $5.35 ÷ 11.5 = $0.465 / 分
边际每分成本     = ($19.00 − $5.35) ÷ (30.9 − 11.5)
                 = $13.65 ÷ 19.4 = $0.704 / 分
```

**边际比低档平均贵约 50%**（$0.704 vs $0.465）。

【结论】**曲线是凸的——越往后每一分越贵。** 这就是"effort 拉满"在数学上站不住的原因：它不是线性加价，是**递减回报**。

【重要限定】这个结论**依赖任务形状**。文档给了一条操作性的判据：

> **在未饱和的评测上，如果性能—成本曲线在各档位之间是平坦的，说明这个任务不受思考算力约束，提高 effort 没有收益。**

所以正确的做法不是记住"不要拉满"，而是**对自己的任务跑一次 effort sweep**，看曲线是陡还是平。

**Q3（计算）**：Humanity's Last Exam（Fable 5.1，无工具）：low 约 53% @ $0.30/题；max 约 61% @ $2.23/题。文档还给出：**从次高档升到 max 这一步，只多约 0.5 个百分点，成本多 46%**。

问：**从 low 直接升到 max，"平均每分成本"是多少？最后那一档的"边际每分成本"是多少？**这两个数的差距说明了什么？

**A3**：

```text
low → max 整体：
  分数提升 = 61 − 53 = 8 个点
  成本提升 = $2.23 − $0.30 = $1.93
  平均每分成本 = $1.93 ÷ 8 = $0.241 / 分

最后一步（次高档 → max）：
  次高档成本 = $2.23 ÷ 1.46 = $1.53
  增量成本   = $2.23 − $1.53 = $0.70
  增量分数   = 0.5 个点
  边际每分成本 = $0.70 ÷ 0.5 = $1.40 / 分
```

**最后一步的每分成本是整体平均的约 5.8 倍**（$1.40 vs $0.241）——**而且那 0.5 个点落在 run-to-run 的噪声里**，也就是说**你付了钱，却无法证明买到了东西**。

【结论】**判断"该不该升一档"，看的是边际而不是平均。** 如果最后一步的增益在噪声内，那它不是"贵一点"，是"白花"。

【补充】这也给了一个可操作的验收标准：**上一档位的差异如果小于评测的 run-to-run 波动，就不该为它付费**——除非你的评测集足够大，能把 0.5 个点做成显著（见 [[母题-C3-Prompt版本管理与回归]] 的样本量算式）。

**Q4（纠错）**：下面这段话哪里不准确？

> "选型就是挑跑分最高的那个模型，选完上线就不用管了。"

**A4**：三处不准确。

1. **跑分是"那些评测上的"表现**，不是你的任务分布上的。更麻烦的是：**"准确率高"和"错误率低"可以是相反方向**——SimpleQA 上 o4-mini 准确率 24% > 22%，但错误率 75% ≫ 26%。**只看跑分你会选错方向。**
2. **不是一次性决策**。模型迭代、effort 参数、缓存定价都会让最优解移动。上面那个案例里，最终方案**换成了更便宜的模型**（Sonnet 5 低 effort），held-out 反而高了 11.9 个点——前提是同时补了 prompt。
3. **它不是一维的**。正确口径是**每个正确结果的全成本** =（单次成本 + 失败率 × 失败代价）÷ 成功率，还要在**模型 × effort** 的二维空间里搜，并且用**没参与搜索的 held-out 集合**验收。

【准确说法】"选型是在（模型 × effort）二维空间里，用你自己的评测和失败代价，搜一组能跨过'够用'门槛的最省配置；它是一个需要定期重跑的决策，不是一次性动作。"

**Q5（纠错）**：下面这段话哪里不准确？

> "effort 越高越保险，所以生产上直接拉满。"

**A5**：两个方向都有坑，而且**低端的坑更隐蔽**。

```text
高端的问题（看得见）：
  · 曲线凸：FrontierCode 边际每分 $0.704 > 低档平均 $0.465
  · HLE 最后一档：多 0.5 分，成本多 46%，增益落在噪声里
  · 会"想过头"：斟酌超过任务所需，成本/延迟上升，质量未必

低端的问题（看不见）：
  · 证据不足就收手：少调工具、只看第一条搜索结果、跳过本该做的检查
  · 危险在于——"The answer looks finished, but it's built on partial information."
```

【准确说法】"effort 应该**标定**而不是拍脑袋。判据是：**在你的任务上跑一次 effort sweep，如果性能—成本曲线在各档位之间是平坦的，说明任务不受思考算力约束，提高 effort 没有收益。** 另外记住：**降 effort 不等于降能力**——实测里更强的模型在低 effort 下达到了上一代模型高 effort 的水平，成本只要三分之一。"

## 三、面试输出（学完再看）

**一句话结论**：选型不是挑最强的，是在**（模型 × effort）二维空间**里、用**每个正确结果的全成本**这一个指标来搜：

```text
每个正确结果的全成本 = (单次成本 + 失败率 × 失败代价) ÷ 成功率
```

四个维度要一起看——**能力、延迟、单价、effort**，其中 effort 最容易被忽略。两条反直觉的实测结论：① **effort 曲线是凸的**，FrontierCode 上边际每分 $0.704 > 低档平均 $0.465，HLE 最后一档多 0.5 分要多花 46% 且落在噪声里；② **强模型 + 低 effort 可能压过 弱模型 + 高 effort**（Fable 5.1 低 effort 匹配 Fable 5 高 effort，成本 1/3）。最后，**降级不是换模型名**，是切到一组已经用你自己的评测验证过的配置。

**恢复关键词**：四维：能力·延迟·单价·effort / 输出比输入贵 5 倍 / 缓存读价差异会改变成本排序 / 每个正确结果的全成本 =（单次 + 失败率×失败代价）÷ 成功率 / effort 曲线凸，边际 > 平均 / HLE 最后一档 +0.5 分 +46% 成本，在噪声里 / 低 effort 的坑是"看起来完整" / 强模型+低 effort ≥ 弱模型+高 effort / 训练集饱和后失去分辨力（98.9% vs 98.9%，held-out 90.5% vs 78.6%）/ 降级要验证过、要可观测

**核心不变量 / 主线**：
**"更贵"买到的不是"更好"，是"失败率更低的那一段"。**
所以选型的分界线永远是：**我的任务在哪个档位跨过"够用"这个门槛**——门槛以下加钱是必要的，门槛以上加钱是纯浪费。而**门槛的位置只能靠你自己的评测找，不能靠别人的排行榜**。

**完整回答骨架**：先立四维（能力/延迟/单价/effort）→ 输出比输入贵 5 倍这个结构事实 → 用"每个正确结果的全成本"统一口径 → effort 曲线的凸性与两个方向的失败模式 → 强模型+低 effort 的实测 → 训练集饱和与 held-out 的分辨力 → 降级链路的设计要求 → 收束到"选一组配置，不是一个模型"

**追问**（先说后看）

1. **便宜模型能不能扛？** —— 取决于任务形状和失败代价。**先算"每个正确结果的全成本"**；如果便宜模型的失败率把失败代价放大到超过节省，就不划算。上面的案例里，便宜模型**配好 prompt 之后反而更准**——所以"降级"要连 prompt 一起调，不是单独换模型。
2. **effort 怎么定？** —— **跑一次 sweep**（对几个档位各跑一遍你的评测集），看曲线。判据：**平坦就说明任务不受思考算力约束，加 effort 没收益**；陡峭且你需要跨过门槛，就加。
3. **降级链路怎么设计？** —— 三个要求：**① 已验证**（备用配置必须在 held-out 上过过门禁，不能是"顺手切一个"）；**② 有明确的质量底线**（降级的目标是保住可用性，不是保住质量，所以要知道降级后能接受什么）；**③ 可观测**（降级本身要打点报警——**不知道自己在降级，比降级更危险**）。
4. **多模型路由的代价是什么？** —— 路由本身有成本和风险：**要维护多套 prompt 与评测**（每个模型都要单独消融调优）、**路由判错会两头不讨好**、**排障复杂度上升**（同一个 bug 在不同模型上表现不同）。所以路由要基于实测收益，不是"看起来更省"。
5. **模型换代了怎么处理？** —— 当成一次完整的选型重做：换模型 + 重新消融清拐杖（[[母题-C3-Prompt版本管理与回归]]）+ 重跑门禁 + held-out 验收。**同时别忘了重算缓存定价的影响**——读价变化会让长会话场景的成本排序改变。

**同类变体**

- 「延迟敏感场景怎么选？」——看的是**首 token 延迟**而不是总时长（流式交互下用户感知的是第一个字什么时候出来）。**缓存命中能显著改善首 token 延迟**，所以"稳定前缀 + 缓存"往往比"换更快的模型"更有效。
- 「怎么向业务方解释"我们换了个更便宜的模型但效果更好"？」——用**每个正确结果的全成本**和**错误率**，不用单价和准确率。单价降了不代表总成本降了（失败代价会吃掉），准确率升了 5% 在业务侧是**错误率腰斩**（[[母题-C4-幻觉的成因与可控性]]）。
- 「成本和质量的取舍谁来定？」——**这个决定必须由能回答"一次失败值多少钱"的人来定**。工程师能给的是这条曲线；把曲线交给业务方去选点，比工程师替业务方拍板更安全。

## 四、拼接

**关联母题**：[[母题-C4-幻觉的成因与可控性]]（准确率高 ≠ 错误率低，选型指标要分开定价）· [[母题-C3-Prompt版本管理与回归]]（换模型是最大的一次 prompt 变更，必须重跑消融）· [[母题-C6-成本与长上下文截断]]（同一个"成本"：C5 管单价与档位，C6 管用量与缓存）

**可迁移场景**：

- **数驭穹图**：NL2SQL 的失败代价极高（错的 SQL 可能扫全表、可能返回错数据），所以**要按"每个正确结果的全成本"选型**——这条链上更应该往质量端倾斜，同时用缓存和上下文裁剪压成本。
- **EnergyOps**：告警诊断是**低频但高价值**的场景，适合高 effort + 自校验（Best-of-N）；而元数据查询是高频低价值，适合小模型 + 低 effort。**同一个系统里不同链路应该有不同的（模型 × effort）配置**——这就是"路由"的实际形态。
- **RuleArena**：长程审查任务的 token 消耗大，**缓存命中率直接影响成本排序**；同时审查错误代价高，所以是"硬件上省、模型上不省"的典型——用 compaction 和缓存压用量，不用降级换模型。

**方言差异（与"服务器选型"对照）**：传统后端选型是**容量规划**问题（QPS × 单请求耗时 → 需要几台机器），模型选型是**质量—成本曲线**问题（同一个"机器"有多个能力档位，且档位可以逐请求切换）。**前者的瓶颈是资源，后者的瓶颈是你对"失败值多少钱"的判断。** 把模型选型当容量规划做，就会漏掉 effort 这一维。
