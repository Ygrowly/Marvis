## 0. 模块边界（先写这个，防无限扩张）

**包含**：一次 HTTP 请求的完整路径（DNS → TCP → HTTP → 连接池 → 状态码）、服务端推送的三种模型（轮询 / SSE / WebSocket）、服务端要同时扛住很多连接时的并发模型（进程 / 线程 / 协程与事件循环）。

**明确不包含**：

- **TCP 协议细节**（拥塞控制、滑动窗口调参、Nagle / 延迟确认）——只到"知道握手挥手为什么、知道什么现象该怀疑它"
- **TLS / 证书链细节**——只知道"加密在 TCP 之上、证书校验什么"
- **网关与负载均衡的产品配置**（Nginx / Envoy 具体指令）——只到"知道哪一层会关缓冲、会加重试、会定超时"
- **业务层并发控制**（乐观锁 / 悲观锁 / 分布式锁）——归 [[母题-M16-乐观锁与悲观锁]] 与"并发与锁"模块，本卡不重复
- **操作系统内核调度细节**（CFS、epoll 内核实现）——只到"知道 epoll 为什么比 select 强"

**边界判据**：**本卡只回答"现象 → 该怀疑哪一层 → 为什么"**。凡是"某框架某参数怎么调"的，不进本卡。

## 5. 项目映射（三个项目逐个过）

### 5.1 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**长任务的 SSE 进度推送**（对话式操作里，一次采集/聚合要跑很久）；30 个 MCP Tool 的**超时与重试**；服务端与上游数据库之间的**连接复用**
- 解决什么问题：用户点了操作之后**必须知道进度**，否则会重复点（这就是"要不要复用连接"从技术问题变成产品问题）
- 踩过的坑：**三个坑都踩过**——① **网关把 SSE 缓冲住了**（Nginx 默认攒着不发），前端看着像卡死，要显式关缓冲；② **不发心跳会被空闲超时掐断**，长任务跑到一半连接就没了，要定期发注释行保活；③ **超时只设了一层**，网关先放弃还是应用先放弃分不清，排查时不知道该看哪边
- 决策与取舍：**选 SSE 不选 WebSocket 是两个理由，不是一个**——① 只需要**单向**推送（服务端 → 客户端），WebSocket 的全双工用不上；② **复用现有 HTTP 网关**——SSE 跑在 HTTP 上，过网关、负载均衡、鉴权链路都不需要额外改造，WebSocket 要动这些（[[母题-N2-SSE与推送模型]]）。

- 对应母题：【N1、N2】

### 5.2 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**一次问数请求的完整链路**（前端 → 网关 → 应用 → 权限/检索/SQL 执行 → 返回）；**权限前置**意味着一次请求里可能有多次串行上游调用
- 解决什么问题：链路上任何一环慢，用户看到的就是"卡住"——**先分清卡在哪一层，再谈优化**（这正好是 N1 主线一的判据）
- 踩过的坑：**网关超时和应用超时设成了一样的值**——结果是两边几乎同时放弃，日志里看不出谁先走的，**排查时无法归因到哪一层慢**。正确做法是**外层比内层略长**，让内层先超时、留下自己的错误，外层只是兜底。
- 决策与取舍：**权限校验收在检索和执行之前，代价是多一次上游调用**，换来的是**未授权内容根本不进后面任何一步**——不进检索、不进 SQL、不进上下文。**用一次串行调用换掉一整类泄露风险**，这笔账划得来（[[母题-N1-一次请求的完整路径]] 的「先分清卡在哪一层」在权限侧的对应）。

- 对应母题：【N1、N3】

### 5.3 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**长任务的进度与状态查询**（Worker 跑一条规则审查是长任务）；**至少一次投递 + 幂等副作用**
- 解决什么问题：**客户端要的到底是"实时推送"还是"能查到最新状态"**——如果是后者，就**不该上 SSE**，轮询更简单
- 踩过的坑：**断线重连后不知道漏了哪些事件**——靠 **`Last-Event-ID` 重连续订**：事件带**递增 sequence**，客户端重连时带上最后收到的 id，服务端从那里补齐。**没有这个机制，重连就会静默丢事件**。
- 决策与取舍：**这里选轮询/状态查询而不是推送**——因为客户端真正要的是「**能查到最新状态**」，不是「实时被通知」。**轮询更简单**：没有长连接要维护、没有重连逻辑、没有网关改造。**「实时」只有在「延迟本身有业务意义」时才值得付这份复杂度**（[[母题-N2-SSE与推送模型]]）。

- 对应母题：【N2、N3】

## 8. 题级答案（「本主线的题」翻转卡背面 · 先说后翻）

> 题号与第 4 节题单一一对应。**必背**题写成能直接说出口的一段话；**理解 / 了解**题写 1–3 句。
> 翻转卡背面先给这道题的答案，再挂上「所属母题的完整回答（口述稿）」与单卡入口——两段合起来才是深挖。

### 1 （必背）
按链路答：**DNS 解析**（域名 → IP，有缓存层级）→ **TCP 三次握手** → **TLS 握手**（HTTPS）→ **发 HTTP 请求**（可能复用已有连接）→ **网关 / 负载均衡** → **应用处理**（可能查 DB、调上游）→ **响应沿原路返回** → 浏览器解析渲染。

面试要点不是背顺序，而是**每一段失败的样子不同**：DNS 失败、连接被拒、TLS 失败、4xx（调用方问题）、5xx（服务端问题）各有对应位置。查慢也是按链路**分段计时**，先定位哪一段再看那一段的指标。

### 2 （理解）
**握手三次**，是因为**双方都要确认"对方能收也能发"**：① 客户端发 SYN（我能发）；② 服务端回 SYN+ACK（我能收、我也能发）；③ 客户端回 ACK（我能收）。两次不够——服务端无法确认客户端的接收能力，会留下半开连接。

**挥手四次**，是因为 **TCP 是全双工的、两个方向要分别关闭**：一方发 FIN 只表示"我不再发"，另一方可能还有数据要发完，所以 ACK 和自己的 FIN 分开发（也可能合并成三次）。主动关闭方还会进入 TIME_WAIT。

### 3 （必背）
四条具体影响：① **握手延迟**——跨机房一次 TCP+TLS 握手约 175 ms，是一次简单查询的 8 倍以上，所以 Agent 反复调工具必须复用连接（Keep-Alive / 连接池）；② **池子需求 = 到达速率 × 单次耗时**（`L = λW`），上游一慢池子立刻被占满；③ **长任务进度推送**不能用"一问一答"的普通请求，要用 SSE 这类推送模型；④ HTTP/2 的多路复用能缓解队头阻塞。判据：Agent 的瓶颈常常不在模型，而在这些连接与超时配置上。

### 4 （必背）
**为什么要有**：省握手（跨机房约 175 ms/次）、减少 TIME_WAIT 与端口消耗。**怎么复用**：Keep-Alive 让同一条 TCP 上跑多个请求；连接池把建好的连接按借还方式复用（要注意归还、超时剔除、最大空闲数）。

**什么时候被占满**：需求 = 到达速率 × 单次耗时（`L = λW`），所以**上游变慢**是最常见原因——此时调大池子只是把压力往后传，正确做法是先查上游时延。还要防**连接泄漏**（借了不还）。

### 5 （必背）
**502**：网关**收到了上游的无效响应**——上游答了但答得不对（进程在但状态/协议不对）；**504**：网关**等上游等到超时**——上游压根没答（耗时问题）；**503**：**应用自己承认不行**（主动拒绝 / 过载保护 / 无可用实例）。

一句话分辨：**502 指向上游进程状态，504 指向上游耗时，503 指向容量与自我保护**。另外 4xx 是调用方的问题。

### 6 （理解）
**分层递减**：客户端 > 网关 > 应用 > 上游。只设一层就分不清谁先放弃——上游还没超时、网关先超时返回 504，你无法判断是"上游慢"还是"网关太急"。

分层递减让**最内层先触发**，日志里能直接读出是哪一层先放弃的。配套一条：**重试要配退避与上限**，否则网关重试会把故障放大（上游已经慢了，再来一倍请求）。

### 7 （理解）
① **多路复用**：HTTP/2 在一条 TCP 上并发多个 stream，解决了 HTTP/1.1 的**队头阻塞**（同一连接上请求要排队，所以浏览器对同一域名开多条连接）；② **头部压缩**（HPACK）；③ **二进制分帧**替代文本协议；④ 支持服务端推送（实际用得少）。

注意：HTTP/1.1 的 Keep-Alive 只是"连接复用"，pipelining 基本没落地；HTTP/2 解决了应用层队头阻塞，但**TCP 层的队头阻塞仍在**——这是 HTTP/3 换 QUIC 的动机。

### 8 （理解）
**短轮询**：客户端定时发请求，服务端立刻返回——大量空跑，实时性与请求量成正比。**长轮询**：服务端**按住请求**直到有数据或超时才返回——减少空跑，但每次都要重建请求，且占用一个连接。

现代系统里长轮询更多被 SSE 替代；还用它的场景是**中间件完全不支持长连接**或兼容性要求极高的旧环境。

### 9 （必背）
**是长连接。** SSE 是**基于 HTTP 的长连接**：客户端发一次请求，服务端保持响应不结束，以 `text/event-stream` 持续**单向**推送，自带事件 ID 与断线重连（`Last-Event-ID`）。

它跑在普通 HTTP 上，所以**过网关不用额外改造**——这是它相对 WebSocket 最大的工程优势。LLM 的逐字流式输出本质上就是它（或分块传输）。

### 10 （必背）
两个维度：**方向**——SSE 单向（服务端 → 客户端），WebSocket 双向；**协议**——SSE 复用普通 HTTP（不需要升级、过网关无改造），WebSocket 需要一次协议升级（Upgrade），部分中间件要额外配置。

选型判据是两个问题：**客户端要不要主动发？要的是事件流还是只要最新状态？** 只需要服务端推（进度、通知、LLM 流式输出）就用 SSE，工程成本低得多；要双向（协作、游戏、实时输入）才上 WebSocket。

### 11 （必背）
三个：① **代理缓冲**——Nginx 等中间层会缓冲响应，把流式变成"一次性返回"，要关掉缓冲（如 `X-Accel-Buffering: no` / `proxy_buffering off`）并按块 flush；② **心跳**——长时间无事件会被中间层或浏览器判为空闲而断开，要定期发注释行（`:ping`）保活；③ **断线重连**——浏览器会自动重连并带 `Last-Event-ID`，但要真正不漏事件，**服务端必须按这个 ID 续推**，或者让客户端重连后拉一次全量状态校准。

另外还要注意网关 / 负载均衡的空闲超时设置。

### 12 （必背）
三点：① **只需要单向**——服务端推进度，客户端不用在同一条连接上发数据；② **复用 HTTP**——鉴权、网关、代理、Observability 全都不用改造，而 WebSocket 要额外支持 Upgrade 和长连接超时；③ **自带断线重连与事件 ID**（`Last-Event-ID`），掉线能续推。

反过来说：如果客户端要持续向服务端发（实时协作、实时语音输入），那就该上 WebSocket。

### 13 （必背）
从"**谁调度**"推出来：**进程**由 OS 调度、**地址空间独立**（隔离好、通信贵）；**线程**由 OS 调度、**共享地址空间**（方便，但切换要进内核，且每个线程在内核侧要占栈和调度实体）；**协程**由**用户态事件循环**调度、约 2KB 一个（切换几乎免费，但**一处阻塞、全体停摆**）。

本质区别是调度方式：**线程是抢占式**（OS 会强行换），**协程是协作式**（你不主动让出就一直占）——"阻塞代码能卡死事件循环"这个代价就是从这一条来的。另外并发的收益由**等待占比**决定：并发不是"同时干很多事"，而是"在等的时候去干别的事"。

### 14 （必背）
两条：① **单线程一次 `epoll` 就能问出成千上万连接里哪些就绪**，不需要一个连接一个线程；② **单位开销小两个数量级**——线程每个要在内核侧占约 25KB（16KB 内核栈 + `task_struct`，且不计入 RSS）和一个调度实体，协程约 2KB、这两笔全省。

前提：**必须是 IO 密集**。CPU 密集的任务会在事件循环里阻塞所有人，而且 asyncio 是单线程，**不能利用多核**（多核靠多进程）。

### 15 （理解）
**卡死整个事件循环**——协程是协作式调度，阻塞代码不会主动让出，事件循环就没机会跑别的协程。表现为"所有接口一起变慢、CPU 不高、日志无异常"，非常难排查。

修法两条：换异步库（aiohttp / asyncpg 之类），或把阻塞调用丢进线程池 / 进程池（`run_in_executor`）。另外单线程异步**仍要考虑竞态**：`await` 会让出控制权，两个协程可能交错修改同一状态——"await 前后状态可能变"是异步里的经典陷阱。

### 16 （理解）
GIL 是 CPython 里**同一时刻只允许一个线程执行 Python 字节码**的锁。含义：① 对 **CPU 密集任务，多线程无效**（不能利用多核），要多进程；② 对 **asyncio 影响小**——它本来就是单线程，IO 等待期间会释放 GIL，并发来自 IO 并行而不是 CPU 并行；③ 对**线程池**——IO 密集场景仍有效（等待时释放 GIL），CPU 密集同样无效。

所以选型是：IO 密集 → asyncio 或线程池；CPU 密集 → 多进程或丢给原生扩展。

### 17 （理解）
背压是**下游处理不过来时向上游反向施压**的机制：有界队列、限流、信号量，或让生产方等待。

不处理会怎样：生产速度 > 消费速度时，队列无界增长 → 内存涨 → GC / swap → 延迟整体升高 → 超时重试又放大流量，最后雪崩。它和"连接池打满"是同一类形态（需求 = 到达速率 × 单次耗时）。

所以队列必须**有界**，满了要么快速失败、要么降速，绝不能无限堆积。

### 18 （理解）
**连接池耗尽**：先按 `L = λW` 查**上游时延**——需求 = 到达速率 × 单次耗时，所以上游变慢是最常见原因，调大池子只是把压力往后传；再看是不是连接泄漏（借了没还）。

**协程泄漏**：通常是**创建了任务但没被正确取消**（超时 / 取消链路要传下去），表现为任务数单调增长、内存渐涨；排查靠任务计数与对当前任务的采样、以及给每个任务加超时。

两类问题的一个共同信号：**延迟升高但 CPU 不高**。
