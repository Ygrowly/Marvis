## 一、教材

### 1. 前提：先把三个容易混在一起的概念分开

**9.9 那道题答错，根子就在这里——把不同层面的概念混成了一个问题。** 先把三个维度立起来：

#### 1.1 三个正交的维度【事实】

| 维度 | 属于哪一层 | 取值 | 问的是 |
|---|---|---|---|
| **连接时长** | **传输层**（TCP） | 短连接 / 长连接 | 这条连接**开多久** |
| **是否保存状态** | **应用层**（HTTP 语义） | 无状态 / 有状态 | 服务端**记不记得你** |
| **通信方向** | 应用层 | 单向 / 双向 | 谁能主动发 |

**关键在"正交"两个字**：**这三个问题互不决定**。任意组合都成立：

- **长连接 + 无状态**：SSE 就是这样——连接一直开着，但服务端不因此记得你是谁
- **长连接 + 有状态**：WebSocket 常配合会话状态
- **短连接 + 有状态**：每次新建连接，但服务端靠 Cookie/Token 认出你

> 【推导】**所以"HTTP 是无状态的"这句话，推不出"HTTP 是短连接"。** 这是最容易混的一处（N1 的 Q5 已经纠过一次），而它正是 SSE 那道题的病根。

#### 1.2 为什么这个区分重要

【推导】面试官问"SSE 是长连接吗"，**他真正想区分的是"你有没有把传输层的事实和应用层的语义混在一起"**。

答"是长连接"只是对了一半——**完整答案要同时说清"它是长连接，且它是单向的、且它跑在普通 HTTP 上"**。

**到这里你应该能回答**：为什么"HTTP 无状态，所以 SSE 也不可能是长连接"这句话是错的？

### 2. 四种做法（先各自介绍，再比较）

#### 2.1 短轮询（Short Polling）【事实】

**做法**：客户端**定时**发请求问"有没有新数据"，不管有没有都立刻返回。

- **优点**：实现最简单，就是个普通接口
- **缺点**：**绝大多数请求是"空跑"**——数据没更新时也在问（下一节算这笔账）

#### 2.2 长轮询（Long Polling）【事实】

**做法**：客户端发请求，**服务端"按住"不立刻回**，一直等到有数据（或超时）才返回；客户端收到后**立刻再发一个**。

- **优点**：比短轮询少了很多空请求，实时性也好
- **缺点**：**每次返回后都要重新建一次请求**；服务端要为每个等待的客户端**挂起一个请求上下文**（占用资源）

#### 2.3 SSE（Server-Sent Events）【事实】

**做法**：客户端**发一次** HTTP 请求，服务端**保持这个响应不结束**，以 `text/event-stream` 格式**持续往回推数据**。

- **优点**：一次请求换来一条长期通道；**自带断线重连**（配合事件 ID）；**跑在普通 HTTP 上**
- **缺点**：**只能服务端 → 客户端单向**；HTTP/1.1 下会**占用一条连接**（见 4.3）

#### 2.4 WebSocket【事实】

**做法**：客户端发起 HTTP 请求，通过 **`Upgrade` 头升级协议**，之后这条连接变成**双向全双工**通道，双方随时可以发。

- **优点**：真正的双向、低开销（帧很小）
- **缺点**：**需要协议升级**——中间件、网关、代理都要支持；连接管理与心跳要自己做

#### 2.5 怎么选：两个问题就分流完了

::figure push-models.svg | 服务端推送怎么选 | 先问是否需要双向，再问要事件流还是只要最新状态

```
问题一：需要「双向」实时通信吗？
   ├─ 需要        → WebSocket
   └─ 不需要
       问题二：只要「最新状态」，还是要「持续的事件流」？
         ├─ 只要最新状态 → 轮询 / 状态查询（最简单，够用就别升级）
         └─ 要事件流     → SSE
```

【取舍】**判据不是"哪个更先进"，而是"客户端要什么"。** 这是本卡最该带走的一句话——**很多系统上 WebSocket 是因为"听起来更强"，而不是因为真的需要双向。**

**回到 Agent 长任务这个具体场景**（面试最可能问的）：

| 需求 | 判断 |
|---|---|
| 客户端要"持续看到进度"吗？ | 要 → 排除"只要最新状态" |
| 客户端需要"随时打断/发指令"吗？ | **通常不需要**（甚至长任务里主动打断是少数） |
| 需要复用现有 HTTP 网关吗？ | **需要** → WebSocket 要额外改造 |

**三条都指向 SSE。** 【取舍】**所以选 SSE 的理由不是"它更弱所以够用"，而是三条具体判据都命中它。**

### 3. SSE 的精确定义（一句话说全）

> 【事实】**SSE（Server-Sent Events）是基于 HTTP 的长连接**：客户端发**一次**请求，服务端**保持这个连接不断开**，以 **`text/event-stream`** 格式持续往回推数据。所以**它是长连接**。它和另外两种的区别：长轮询是客户端反复发短请求；**WebSocket 是双向全双工、需要协议升级**；SSE 是**单向**（只服务端往客户端推），但**自带断线重连**（靠 `Last-Event-ID`）和**事件 ID**，而且**跑在 HTTP 上，过网关和负载均衡不需要额外改造**。

**这段话里有四个技术点，一个都不能少**：

| 点 | 为什么重要 |
|---|---|
| `text/event-stream` | 这是它的**协议标识**，服务端靠它告诉客户端"这不是普通响应，别等结束" |
| **单向** | 决定了它和 WebSocket 的分工 |
| **`Last-Event-ID`** | **断线重连的能力来源**：重连时带上最后收到的事件 ID，服务端可以**从断点续推** |
| **跑在 HTTP 上** | **工程上最实际的优点**：不用改网关、不用新协议、鉴权和限流都能复用 |

### 4. 生产里的坑（这里才是"真做过"的证据）

#### 4.1 反向代理会缓冲【事实】

Nginx 之类的代理**默认会缓冲响应**——它会攒够一定量才转发。**对普通接口无所谓，对 SSE 是致命的：数据会被攒着不发，客户端看到的进度是"卡住然后一次跳一大段"。**

**处理**：关掉该响应的缓冲（Nginx 侧 `X-Accel-Buffering: no`），并确认 `proxy_buffering off`。

#### 4.2 要发心跳【事实】

连接空闲太久会被中间设备（网关、NAT、负载均衡）**当成死连接回收**。

**处理**：定期发**注释行心跳**（SSE 里以 `:` 开头的行会被客户端忽略，但足以让链路上的设备看到流量）。

#### 4.3 HTTP/1.1 下的连接数限制【事实】

**浏览器对同一域名在 HTTP/1.1 下只允许约 6 个并发连接**。SSE 会**独占**一条。所以：

- 一个页面开 1–2 个 SSE 没问题
- **开 7 个以上就会有请求排队**（首页的其他接口被 SSE 挤住）

【推导】**这个坑的解法是 HTTP/2**：多路复用让一条连接上跑多个流（N1 第 4 节）。

#### 4.4 断线重连的语义要设计【推导】

**SSE 自带重连，但它只负责"重连"这个动作，不负责"不丢事件"**。要真做到不丢，需要：

```
服务端：每条事件带自增 id
客户端：记录最后收到的 id，重连时通过 Last-Event-ID 带上
服务端：据此从 id 之后续推（或直接让客户端拉一次全量状态校准）
```

> 【取舍】**"能重连"和"不漏事件"是两件事。** 这是从"我用了 SSE"到"我处理了它的失败模式"的分界。

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "SSE 是短连接" | 【事实】**错。SSE 是长连接**——服务端保持响应不结束。**这正是 9.9 当场答错的那一处，必须一条不错地纠正过来** |
| "SSE 和 WebSocket 差不多，都是长连接" | 【事实】**方向不同**：SSE **单向**（服务端→客户端），WebSocket **双向**；SSE 跑在 HTTP 上，WebSocket 要协议升级。**"都是长连接"只描述了传输层，没描述应用层** |
| "SSE 就是普通 HTTP 响应，过网关不用任何配置" | 【取舍】**代理默认会缓冲**，必须关掉（`X-Accel-Buffering: no`），否则数据会被攒着不发 |
| "SSE 自带重连，所以不会丢消息" | 【推导】**重连 ≠ 不漏**。要配合事件 ID + `Last-Event-ID` 才能续推 |
| "长轮询就是短轮询加了个超时" | 【事实】**本质区别在"服务端是否按住请求"**：短轮询立刻返回（大量空跑），长轮询 hold 住直到有数据。**占用资源的方式也不同**（长轮询会挂起请求上下文） |
| "能用 WebSocket 就用 WebSocket" | 【取舍】WebSocket 要协议升级、要自己做心跳与重连、网关可能不支持。**只需要单向推送时，SSE 的工程成本低得多** |

## 二、自测

**Q1（计算）**：一个进度页有 **1000 个在线用户**。若用**短轮询**、每 **1 秒**问一次，而后端平均每 **100 秒**才产生一条新进度。

问：服务端每秒要处理多少请求？其中"无效请求"占多少？改成 SSE 后大约是多少？

**A1**：

- 短轮询：1000 用户 × 1 次/秒 = **1000 QPS**
- 真正有新数据的比例 = 1 / 100 = **1%** → **约 990 QPS 是空轮询**（问了个寂寞）
- SSE：**1000 条长连接**（建立时各一次请求），之后**只在有事件时发数据** → 服务端要"处理"的请求从 **1000/s 降到约 10/s**

**量级差 100 倍，而且在连接数不变的前提下。**

【推论】**这就是推送模型的价值来源：把"客户端不停问"换成"服务端有事才说"。** 但代价是**服务端要为每条长连接保持状态**（这就是 N3 要讲的"怎么扛住很多连接"）。

**Q2（判读）**：下面三个场景分别该选什么？（从 短轮询 / 长轮询 / SSE / WebSocket 里选，并说明理由）

① 一个 AI 对话页面，用户看到的是模型**逐字返回**的答案
② 规则审查任务跑 5 分钟，前端要显示**当前进度和已发现的问题数**
③ 一个协作白板，多人同时拖拽图形，要**实时同步**

**A2**：

| 场景 | 选择 | 理由 |
|---|---|---|
| ① LLM 逐字输出 | **SSE**（或流式 HTTP 响应） | **单向**（服务端→客户端）、**持续事件流**、要复用现有 HTTP 网关 —— 三条全中 |
| ② 长任务进度 | **SSE**（**或直接用轮询查状态**） | 如果"只要最新状态、过程不重要"，**轮询更简单**；如果要"逐条事件"（进度+问题列表），用 SSE |
| ③ 多人协作 | **WebSocket** | **需要双向**：客户端不断上送自己的操作，服务端广播给别人 |

**关键**：②这一格**两可**，取决于"客户端要的是状态还是事件流"——**能把这个判断说出来，比直接答 SSE 更能体现理解**。

**Q3（计算）**：HTTP/1.1 下，浏览器对同一域名允许约 **6 个**并发连接。一个页面已经用了 1 个 SSE。此时页面同时发起 **8 个**普通接口请求，会发生什么？

**A3**：

- 可用连接 = 6 − 1（SSE 独占）= **5 个**
- 8 个请求里，**5 个先发，剩下 3 个排队**等前面完成
- 现象：**普通接口"变慢"了**，因为它们在等前面的请求释放连接

【推论】**所以 SSE 不是"零成本的长连接"——它在 HTTP/1.1 下要占掉一份宝贵的连接配额。** 解法是 HTTP/2（多路复用，一条连接跑多个流）。

**这条能答出来，说明不是背了 SSE 的定义，而是想过它上线之后会碰到什么。**

**Q4（纠错）**：下面这段话哪里错了？

> "SSE 是通过 HTTP 实现的，而 HTTP 是无状态的短连接，所以 SSE 本质上还是短连接，只是服务端推得比较频繁。"

**A4**：**全错，而且错在两个概念上。错误链条是：**

1. **"HTTP 是短连接的"** —— 不对。**HTTP/1.1 默认就是长连接**（Keep-Alive），加上连接池，同一条 TCP 连接会被复用（N1 第 2.4、Q5）。**"无状态"是应用层语义，"短连接"是传输层事实，两者互不决定。**

2. **"所以 SSE 是短连接"** —— 反了。**SSE 恰恰是长连接**：客户端发**一次**请求，服务端**保持这个响应不结束**，持续往回推。**连接一直开着，这是它的定义。**

**准确说法**：**SSE 是基于 HTTP 的长连接**——它长在"服务端不结束这个响应"上，而不是长在"客户端反复发请求"上（那是长轮询）。

**这是 9.9 全场唯一一处明确的概念性错误。** 记住一句话：

> **SSE 是长连接；它是单向的；它跑在普通 HTTP 上。** 三句都要说全。

**Q5（纠错）**：下面这段话哪里不准确？

> "SSE 就是服务端不结束 HTTP 响应，所以它和普通接口一样过网关，不需要任何额外配置。"

**A5**：**"不需要任何额外配置"是错的——反向代理默认会缓冲响应。**

Nginx 之类的代理**会攒够一定量再转发**。对普通接口无所谓，**对 SSE 是致命的**：

- **数据被攒着不发** → 客户端看到的进度是"长时间没动静，然后一次跳一大段"
- 而不是"平滑地一条条出来"

**必须做的两件事**：

| 配置 | 作用 |
|---|---|
| 关掉该响应的缓冲（`X-Accel-Buffering: no` / `proxy_buffering off`） | 让数据**立即**穿过去 |
| 定期发**心跳注释行** | 防空闲连接被中间设备（网关/NAT/LB）当死连接回收 |

【取舍】**这两条都是"上线才发现"的坑**——它们不在 SSE 的定义里，但在生产里一定会遇到。**能把它们说出来，是从"知道 SSE"到"用过 SSE"的分界。**

## 三、面试输出（学完再看）

**一句话结论**：**SSE 是基于 HTTP 的长连接**——客户端发一次请求，服务端保持响应不结束，以 `text/event-stream` 持续单向推送，自带断线重连（`Last-Event-ID`）与事件 ID，**跑在普通 HTTP 上所以过网关不用额外改造**。它和长轮询的区别是"服务端按住请求 vs 客户端反复发"；和 WebSocket 的区别是"**单向且复用 HTTP** vs **双向但要协议升级**"。**选型判据是两个问题：要不要双向？要事件流还是只要最新状态？**

**恢复关键词**：长连接 / 无状态 / 双向 是三个**正交**维度 / SSE 是长连接不是短连接 / `text/event-stream` / 单向 / `Last-Event-ID` 提供续推 / 跑在 HTTP 上是最大工程优势 / 代理要关缓冲 / 要发心跳 / HTTP1.1 下独占一条连接（同域 6 条）/ 重连 ≠ 不漏事件 / 选型看"客户端要什么"不是"哪个先进"

**核心不变量 / 主线**：
**"连接开多久""记不记得你""谁能主动发"是三个互不决定的维度。** 把这三个分开，SSE 那道题就不会答错；把这三个分开，选型也就变成了两个二选一的问题。

**完整回答骨架**：三个正交维度（破掉"HTTP 无状态所以 SSE 不是长连接"）→ 四种做法各是什么（短轮询/长轮询/SSE/WebSocket）→ 决策树两个问题 → SSE 精确定义四个技术点 → 生产三个坑（代理缓冲 / 心跳 / 连接配额）→ 断线重连要配事件 ID → 回到 Agent 长任务：三条判据都指向 SSE

**追问**（先说后看）

1. **SSE 和 WebSocket 到底怎么选？** —— 先问"客户端要不要主动发"。**只需要服务端推（进度、通知、LLM 逐字输出）就用 SSE**，工程成本低得多；**要双向（协作、游戏、实时输入）才上 WebSocket**。
2. **SSE 断线了会怎样？** —— 浏览器**自动重连**，并带上 `Last-Event-ID`。但要真正"不漏事件"，**服务端必须按这个 ID 续推**，或者让客户端重连后拉一次全量状态校准。
3. **为什么 SSE 适合 LLM 逐字输出？** —— 它就是"**持续的单向事件流**"，且能复用现有 HTTP 网关与鉴权。**这正是 EnergyOps 里推长任务进度、以及大部分大模型产品流式输出的做法。**
4. **长轮询还有什么场景在用它？** —— 【取舍】需要"服务端推"但**中间件完全不支持长连接**时的兜底；或者**兼容性要求极高**的旧环境。**现代系统里它更多是被 SSE 替代。**

**同类变体**

- 「什么是长轮询？和短轮询的区别？」——**服务端是否按住请求**：短轮询立刻返回（大量空跑），长轮询 hold 到有数据
- 「流式输出（streaming）用的是什么？」——**本质就是 SSE**（`text/event-stream`）或分块传输
- 「怎么防止 SSE 连接被中间设备断掉？」——**心跳注释行**，让链路看到持续流量

## 四、拼接

**关联母题**：[[母题-N1-一次请求的完整路径]]（无状态 ≠ 短连接、连接复用、超时分层）· [[母题-N3-进程线程与协程]]（服务端怎么同时扛住上千条 SSE 长连接）

**方言差异（这里的"方言"是"中间件方言"）**：**SSE 的行为强依赖链路上的代理与网关配置**——同一个服务在直连时正常，加了网关就可能"卡住不发"（缓冲）或"几分钟断一次"（空闲超时）。**所以面试时要说"它跑在 HTTP 上，但代理需要配合关缓冲和加心跳"，而不是简单地说"无需配置"。**
