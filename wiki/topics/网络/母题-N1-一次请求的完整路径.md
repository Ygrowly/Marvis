# 母题 N1 · 一次请求走完了什么，以及 502 / 503 / 504 各是哪一层的问题

> **模块**：网络基础
> **所属主线**：一 · 一次请求怎么走完（从输入 URL 到拿到响应，中间经过谁）
> **层级**：A · 教材级（状态码可以从"链路分几段"推出来，不需要背）
> **关联母题**：[[母题-N2-SSE与推送模型]] · [[母题-N3-进程线程与协程]] · [[母题-M6-一条SQL的执行链路]]

**导读**：必懂 3 件事（① 请求穿过的是一条分层的链路 ② 连接复用省的是延迟 ③ 502/503/504 对应不同层）· 读完约 10 分钟 · 需要先懂：无

**题目**：输入一个 URL 到拿到响应，中间经过了什么？如果失败，**502、503、504 分别说明哪一层出了问题**？

**母题**：一次请求从 URL 到响应走完了什么？5xx 状态码该怎么定位？

## 一、教材

### 1. 前提：请求穿过的是一条链路，不是一个函数

#### 1.1 链路分几段【事实】

```
客户端
  ├─ DNS 解析        域名 → IP
  ├─ TCP 握手        建立连接
  ├─ HTTP 请求/响应  讲请求讲什么、回什么
  ↓
网关 / 负载均衡       转发、超时、重试、限流
  ↓
应用                 业务逻辑（可能就是你自己写的服务）
  ↓
上游 / 数据库          缓存、DB、第三方 API
```

【推导】**每一段都可能失败，而且失败的样子不一样**——这就是本卡的全部价值：

> **"报错了"不是结论，"报错的样子"才是线索。** 先定位"哪一段"，再谈"为什么"。

#### 1.2 先建立判据

【推导】把所有失败归纳成两类：

| 失败类型 | 表现 | 对应状态码区间 |
|---|---|---|
| **我的请求有问题** | 参数错、权限不足、路径不存在 | **4xx** |
| **服务端处理不了** | 内部错误、上游异常、过载 | **5xx** |

**4xx 和 5xx 的分界线是"谁的问题"**——这个分法决定排查方向完全不同：4xx 去看调用方，5xx 去看服务端。

**到这里你应该能回答**：为什么 401/403、404 都属于 4xx，而不是 5xx？

### 2. 每一段做什么、失败长什么样

#### 2.1 DNS【事实】

**做什么**：把域名翻译成 IP。

**失败特征**：请求**根本没出去**，客户端立刻报错（"找不到主机"）。**这类失败没有 HTTP 状态码**——因为它还没到 HTTP 层。

#### 2.2 TCP 握手：为什么是三次【推导】

```
客户端 → SYN
服务端 → SYN + ACK
客户端 → ACK
```

**为什么是三次，不是两次**【推导】：因为**双方都要确认"对方能收，也能发"**：

- 第一次：服务端知道"客户端能发"
- 第二次：客户端知道"服务端能收也能发"
- 第三次：服务端知道"客户端能收"

**两次的话，服务端无法确认客户端能收**——它发了 SYN+ACK 之后不知道对方到底收没收到。

【取舍】三次是"可靠的最少次数"。**四次挥手**是因为 TCP 连接是全双工的，**两个方向要各自关闭**（一方说"我没数据了"，另一方可能还有数据要发），所以不能把两次合并。

**失败特征**：`连接超时`（SYN 没回应）或 `连接被拒绝`（对方端口没开，回了 RST）。**同样没有 HTTP 状态码。**

#### 2.3 HTTP：请求与响应【事实】

**HTTP 是无状态协议**——服务端不会自动记住"你是谁"。**所以鉴权要靠每次请求带凭证**（Cookie / Token），而不是靠"上次连过"。

【推导】**这一条直接推出后面的两件事**：

- 为什么需要 **Session / Token**：无状态意味着状态得存在别处
- 为什么**长连接与"有状态"是两件事**：TCP 连接一直开着，**不代表**应用记得你（这正是 N2 要讲清的区别）

#### 2.4 连接复用：Keep-Alive 与连接池

**为什么必须复用**【推导】——算一次延迟就清楚了：

```
跨机房 RTT ≈ 50ms
TCP 三次握手 ≈ 1.5 RTT ≈ 75ms
TLS 握手   ≈ 2 RTT  ≈ 100ms
新建一次连接总计 ≈ 175ms
而一次简单的上游查询可能只要 20ms
```

【推导】**握手成本是查询本身的 8 倍以上。** 所以连接复用**首先省的是延迟**，其次才省服务端资源（每次握手都要占内存和端口）。

**连接池是什么**【事实】：预先建好一批连接，用的时候借、用完还。**池子的作用是把"建连接"的成本从每次请求摊到很少次。**

**池子该设多大**——这里有一个可以直接用的算式（**Little's Law**）：

```
并发需求 L = 到达速率 λ × 单次处理时长 W
```

**这里是本卡最有用的一个推论**【推导】：

> **池子满了，第一反应不该是"把池子调大"，而该问"上游是不是变慢了"。**
>
> 因为 `L = λ × W`——**并发需求对 W 是线性的**。上游慢 3 倍，同样的 QPS 就要 3 倍的连接。**这时候调大池子只是把压力往后传（上游更扛不住），没解决根因。**

【取舍】但池子也不能设太小：设小了会出现"**应用明明不忙，却一直借不到连接**"。**池子大小要按"正常时延 × 峰值 QPS"算，而不是凭感觉给个 100。**

### 3. 状态码：把"哪一层出问题"翻译成数字

::figure http-request-path.svg | 502 503 504 各自发生在链路的哪一段 | 三者都指向不同的排查起点，不能混着说

#### 3.1 五个类别【事实】

| 区间 | 含义 |
|---|---|
| **2xx** | 成功 |
| **3xx** | 重定向（资源搬走了，去新地址） |
| **4xx** | **调用方**的问题：参数、权限、路径 |
| **5xx** | **服务端**的问题 |

#### 3.2 502 / 503 / 504 —— 这是本卡的落点【事实】

| 状态码 | 谁产生的 | 准确含义 |
|---|---|---|
| **502 Bad Gateway** | **网关** | **网关没能从上游拿到一个有效响应**：连接被拒绝（上游没起来 / 端口变了）、连接被重置、响应解析不了、协议对不上。**注意 RFC 的原话是「收到了一个无效响应」——上游【不一定活着】**（连接被拒也算） |
| **503 Service Unavailable** | **应用自己** | **应用主动承认"我现在不行"**：**过载、正在维护**、依赖全挂。**可以带 `Retry-After` 告诉客户端多久后再来** |
| **504 Gateway Timeout** | **网关** | **网关等上游等到超时**：上游**一个字都没回**（太慢或卡住） |

**一句话收口**：

> **502 是答非所问（或根本没连上），504 是根本没答，503 是自己承认不行。**

【推导】**这三者指向完全不同的排查起点**：

| 看到 | 先查什么 |
|---|---|
| 502 | 上游进程**状态**：是不是刚重启、是不是被 OOM 杀了、是不是端口变了、是不是协议/超时配置对不上 |
| 503 | 应用**自身的容量**：CPU/内存/线程池/连接池打满了吗？是不是在发版？依赖是否整体不可用？ |
| 504 | **耗时链路**：上游哪一步慢（DB 慢查询？第三方超时？）以及**网关的超时阈值**设得对不对 |

#### 3.3 超时应该设几层【推导】

**这是"为什么"层面的问题**：如果只有一层超时，你会分不清是谁先放弃的。

正确的做法是**分层递减**：

```
客户端超时（最长）
  > 网关超时
    > 应用自身超时
      > 上游/DB 超时（最短）
```

【推导】**每往里一层都设得更短**，这样超时总是**由最内层先触发**——你就能从错误信息里直接读出**是哪一层放弃的**。

**反过来（内层比外层长）会怎样**：外层先超时，内层还在跑。**结果是"客户端已经报 504 了，服务端还在白白消耗资源算一个没人要的结果"**——而且日志里看不出根因。

### 4. HTTP/1.1 与 HTTP/2

| | HTTP/1.1 | HTTP/2 |
|---|---|---|
| 连接上的并发 | 一个连接一次处理一个请求（**要靠开多个连接来并发**） | **多路复用**：一个连接上并发多个流 |
| 头部 | 每次重复发送 | **头部压缩**（HPACK） |
| 队头阻塞 | 有（前一个响应慢会挡住后面） | 在**应用层**缓解（但 TCP 层面仍有队头阻塞 → HTTP/3 换 UDP） |

【取舍】**HTTP/2 的价值主要在"减少连接数"**：浏览器对同一域名的并发连接数有限制，1.1 时代要靠多域名分流；2 用一条连接多路复用解决。**服务端内部的 RPC 调用如果已经是长连接池，收益就没那么明显。**

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "502 就是上游挂了" | 【事实】**502 是上游"活着但答得不对"**。上游进程如果完全没起来，网关连不上，得到的通常是 **504（等超时）或连接拒绝**。**"502 = 上游不可用"是 9.9 说反的那句** |
| "504 是服务端挂了" | 【事实】**504 是"网关等上游超时"**——服务端可能只是慢。**"挂了"和"慢"是两件事，排查方向完全不同** |
| "HTTP 是无连接的，所以每次请求都新建 TCP 连接" | 【事实】**"无状态"和"短连接"是两个概念**。HTTP 协议本身不保存会话状态（无状态），但**传输层的连接可以复用**（Keep-Alive / 连接池）。两者不冲突 |
| "长连接 = WebSocket" | 【取舍】长连接是**传输层的事实**（连接不关），WebSocket 是**一种协议**。**SSE 也是长连接**，但它跑在普通 HTTP 上（N2） |
| "连接池越大越好" | 【推导】`L = λW`——池子需求由"上游时延 × 到达速率"决定。**池子满通常说明上游变慢，调大只是把压力往后传** |
| "超时设一个就行" | 【推导】超时要**分层递减**，让最内层先触发；否则外层先放弃、内层还在白跑，且日志看不出根因 |

## 二、自测

**Q1（计算）**：上游单次处理耗时 **100ms**，服务需要支撑 **1000 QPS**。

问：连接池至少要多少条连接？如果上游变慢到 **300ms**，池子需要变成多少？

**A1**（用 `L = λ × W`）：

- 100ms 时：L = 1000 × 0.1s = **100 条**
- 300ms 时：L = 1000 × 0.3s = **300 条**

**关键推论**：**上游慢 3 倍，连接需求也变 3 倍。**

> **所以"连接池被打满"的第一反应不该是调大池子，而该问"上游是不是变慢了"。**
>
> 因为调大池子只是把并发放到上游身上——**如果上游是因为资源不够才变慢的，加连接会让它更慢。** 这时正确的动作是查上游（慢查询、锁等待、第三方超时），而不是加连接。

【实务】池子按"正常时延 × 峰值 QPS × 1.2 余量"设；同时设"获取连接超时"，**让借不到连接的请求快速失败，而不是无限等待**。

**Q2（判读）**：下面三个现象，分别最可能对应哪个状态码？该先查什么？

① 上游服务刚重启完，网关日志里出现大量某个 5xx
② 应用 CPU 打满，客户端收到带 `Retry-After` 的 5xx
③ 某条 SQL 因为缺索引跑了 60 秒，客户端收到的 5xx

**A2**：

| 现象 | 状态码 | 先查什么 |
|---|---|---|
| ① 上游刚重启，网关出现大量 5xx | **502** | 上游进程状态：启动完成了吗？端口/健康检查配好了吗？（**典型的"活着但答得不对"**） |
| ② CPU 打满 + `Retry-After` | **503** | 应用自身容量：线程池/连接池是否打满、是否需要限流降级 |
| ③ SQL 跑 60 秒 | **504** | 耗时链路：缺索引导致的慢查询（[[母题-M7-慢查询与SQL优化手段]]）+ 网关超时阈值 |

**三个现象的排查起点完全不同**——这就是"先分清哪一层"的价值。

**Q3（计算）**：跨机房 RTT 约 **50ms**，TLS 握手约 **2 RTT**。

问：新建一次连接比复用一个已有连接**多花多少时间**？如果一个简单查询只要 20ms，这个开销是它的几倍？

**A3**：

- TCP 三次握手 ≈ 1.5 RTT = **75ms**
- TLS 握手 ≈ 2 RTT = **100ms**
- 合计新增 ≈ **175ms**
- 175 ÷ 20 ≈ **8.75 倍**

**结论**：**握手成本是一次简单查询的 8 倍以上。** 所以连接复用的**首要收益是延迟**，其次才是省服务端资源。

【推论】这也是为什么"内网服务之间调得慢"经常不是逻辑慢，而是**没复用连接**——每次调用都重新握手。

**Q4（纠错）**：下面这段话哪里错了？

> "接口返回 502 Bad Gateway，说明上游服务器挂了、不可用了。"

**A4**：**"上游挂了"是错的——502 恰恰说明上游还活着。**

**502 的准确含义是：网关收到了上游的"无效响应"**：

- 上游进程**在**，但连接被重置（可能刚重启、被 OOM 杀了一部分 worker）
- 或者回的东西**解析不了**（协议对不上、响应被截断、返回了非 HTTP 内容）

**如果上游真的完全不可用**（端口没开、进程没了），你看到的通常是：

- **连接被拒绝**（对方回了 RST，很快）
- 或者**504**（网关一直在等，等到超时）

**这是 9.9 当场说反的那一处**：

| | 正确的是 |
|---|---|
| 502 | 上游**答非所问**（响应无效） |
| 504 | 上游**根本没答**（等到超时） |
| 503 | **自己**承认不行 |

**记忆点：502 是"答了但不对"，504 是"压根没答"。**

**Q5（纠错）**：下面这段话哪里错了？

> "HTTP 是无连接、无状态的协议，所以每次请求都必须重新建立 TCP 连接、重新鉴权。"

**A5**：**把两件事混成一件了。**

1. **"无状态"和"无连接"是两个不同层面的事实。**
   - **无状态**（应用层）：HTTP 协议本身不保存"你是谁"——**所以每次请求都要带凭证**（Cookie / Token）。这一半是对的。
   - **无连接**（传输层）：这是 **HTTP/1.0 时代的事实**。**HTTP/1.1 默认就是长连接**（`Connection: keep-alive`），加上连接池，**同一条 TCP 连接会被反复复用**。

2. **所以"每次都重新建立 TCP 连接"是错的** —— 那是 1.0 的行为，而且**即使是无状态也不妨碍复用连接**。

**准确说法**：**HTTP 无状态 → 每次请求都要带凭证；但传输层的连接可以复用 → 不必每次握手。** 两句话各管一层，不能互相推导。

## 三、面试输出（学完再看）

**一句话结论**：一次请求穿过 **DNS → TCP → HTTP → 网关 → 应用 → 上游** 这条链路，**每一段失败的样子都不同**。4xx 是调用方的问题，5xx 是服务端的问题；**502 是网关收到上游的无效响应（答非所问），504 是网关等上游超时（根本没答），503 是应用自己承认不行**。连接复用（Keep-Alive / 连接池）首先省的是**握手延迟**（跨机房约 175ms，是一次简单查询的 8 倍以上）；**池子需求 = 到达速率 × 单次耗时**，所以池子满了要先怀疑上游变慢。

**恢复关键词**：链路六段 / 4xx 是调用方、5xx 是服务端 / TCP 三次是因为双向都要确认 / 无状态 ≠ 短连接 / 握手成本 ≈ 1.5 RTT + 2 RTT / **L = λW** / 池子满先查上游时延 / **502 答非所问、504 根本没答、503 自己承认** / 超时嵌套要由内向外递减 / HTTP2 多路复用

**核心不变量 / 主线**：
**"报错了"不是结论，"哪一层报错"才是线索。** 请求穿过的是一条分层链路，每一层有不同的失败表征（有的压根没有状态码，有的变成 4xx，有的变成特定 5xx）；**定位问题就是把这层分清楚，而不是先猜原因。**

**完整回答骨架**：链路分几段 → 每段做什么、失败长什么样（DNS 无状态码 / TCP 连接超时或被拒 / HTTP 4xx5xx）→ 无状态与长连接是两件事 → 连接复用省的是延迟（算一次 175ms）→ 池子大小用 `L = λW` → 5xx 三个码的准确语义与排查起点 → 超时嵌套由内向外递减 → HTTP/2 的价值在减少连接数

**完整回答（口述稿）**：
一次请求穿过 **DNS → TCP → TLS → HTTP → 网关 → 应用 → 上游** 这条链路，**每一段失败的样子都不同**——这才是这条链路要记的东西，而不是背顺序。

分工：DNS 把域名换成 IP；TCP 建连接（三次握手）；TLS 协商密钥；HTTP 发请求（可能复用已有连接）；网关/负载均衡转发；应用处理（可能查 DB、调上游）；响应沿原路返回。

失败的样子：**4xx 是调用方的问题，5xx 是服务端的问题**；**502 是网关收到上游的无效响应**（上游答了但答得不对，指向上游进程状态），**504 是网关等上游超时**（上游压根没答，指向上游耗时），**503 是应用自己承认不行**（主动拒绝/过载保护/无可用实例，指向容量与自我保护）。

连接复用（Keep-Alive / 连接池）首先省的是**握手延迟**（跨机房约 175 ms，是一次简单查询的 8 倍以上）；**池子需求 = 到达速率 × 单次耗时**（`L = λW`），所以**池子满了要先怀疑上游变慢**，调大池子只是把压力往后传。超时要**分层递减**（客户端 > 网关 > 应用 > 上游），只设一层就分不清谁先放弃；重试要配退避与上限，否则网关重试会放大故障。

**分层要点**：
- **结论**：链路每一段失败的样子不同；502/504/503 分别指向状态、耗时、容量。
- **推导链**：分段 → 各段失败语义 → 连接复用省握手 → 池子需求 = λW → 分层超时让最内层先触发。
- **量化**：跨机房 TCP+TLS 握手约 175 ms，是一次简单查询的 8 倍以上；`L = λW`。
- **边界与常见误解**：HTTP 无状态不等于没有会话（状态放 Cookie/Token）；HTTP/2 解决了应用层队头阻塞，TCP 层的还在（这是 HTTP/3 换 QUIC 的动机）。

**追问**（先说后看）

1. **502 和 504 的区别，一句话说清？** —— **502 是上游答了但答得不对；504 是上游压根没答（等到超时）。** 一个指向"上游进程状态"，一个指向"上游耗时"。
2. **连接池被打满，先做什么？** —— 先看**上游时延**（`L = λW`：W 变大直接推高需求）。调大池子只是把压力往后传。
3. **超时为什么不能只设一层？** —— 只有一层就分不清谁先放弃。**分层递减**让最内层先触发，日志里能直接读出是哪一层。
4. **HTTP 无状态，那 Session 是怎么实现的？** —— 无状态意味着状态要放到别处：Cookie 带 Session ID、或 Token 自带信息（JWT）。**这跟"连接能不能复用"是两件事。**
5. **为什么长任务进度推送不该用普通请求？** —— 普通请求是"一问一答"，长任务要"持续告诉进度"，需要推送模型（[[母题-N2-SSE与推送模型]]）。

**同类变体**

- 「一次请求为什么慢，怎么排查？」——按链路分段计时（DNS/TCP/网关/应用/上游），**先定位哪一段，再看那一段的指标**
- 「RPC 调用超时了，怎么判断是网络问题还是服务端慢？」——分层超时 + 分段耗时埋点；单纯看总耗时分不出来
- 「网关的重试会不会放大故障？」——会。**重试要配退避与上限**，否则上游慢的时候重试会把压力乘几倍
