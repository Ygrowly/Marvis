## 一、教材

### 1. 前提：先问"时间花在哪"

#### 1.1 一个请求的时间构成【事实】

```
一次典型的上游调用，总耗时 100ms：
  CPU 计算（拼参数、解析、序列化）  约 2ms
  等 IO（网络往返、DB 查询、磁盘）  约 98ms
```

【推导】**98% 的时间在等**。而"等"的时候，CPU 是空闲的。

**所以并发的本质不是"同时干很多事"，而是"在等的时候去干别的事"。**

#### 1.2 量化：并发的收益上限

【推导】如果一次请求只占用 2% 的 CPU 时间，那**单核理论上就能"同时"处理 100/2 = 50 个这样的请求**：

```
理论并发上限 ≈ 总耗时 / CPU 占用时间 = 100 / 2 = 50
```

**这个算式给出了本卡最重要的判据**：

| 负载类型 | CPU 占比 | 并发杠杆 | 结论 |
|---|---|---|---|
| **IO 密集**（调上游、查 DB、等网络） | 低（如 2%） | **大（约 50 倍）** | **异步收益巨大** |
| **CPU 密集**（加密、图像处理、大计算） | 高（如 80%+） | 小（约 1.2 倍） | **异步几乎没用**，要靠多核 |

> 【取舍】**所以"要不要用异步"不是风格问题，是"你的程序在等还是在算"的问题。** 而 Agent 服务、API 网关这类程序**几乎全是 IO 密集**——所以异步收益极大。

**到这里你应该能回答**：为什么 asyncio 对"查数据库的接口"帮助很大，对"算加密哈希的接口"几乎没帮助？

### 2. 三种执行单元：用同一指标比

::figure concurrency-models.svg | 进程 线程 协程用同一个指标比较 | 单位开销 / 谁调度 / 共享什么；线程的用户栈是虚拟预留，常驻的是内核侧约 25KB

#### 2.1 进程【事实】

- **是什么**：操作系统分配资源的**基本单位**，**有自己独立的地址空间**
- **调度者**：操作系统
- **单位成本**：栈上限约 8MB（虚拟内存，实际按触碰的页算）
- **优点**：**隔离最好**——一个进程崩了不影响别的
- **代价**：**通信与切换最贵**（数据要跨地址空间拷贝）

#### 2.2 线程【事实】

- **是什么**：进程内的执行单元，**共享同一地址空间**
- **调度者**：**操作系统**（抢占式：时间片到了就被换下来）
- **单位成本**：**用户栈默认 8MB（虚拟预留、按需提交）＋ 内核侧约 25KB（16KB 内核栈 + `task_struct`，不计入 RSS）**

> ⚠️ **2026-09-16 修正**：本卡原写"线程栈约 1MB"，**不对**。按 `pthread_create(3)` man-page：**Linux 上（NPTL）新线程的默认栈大小由 `RLIMIT_STACK` 决定**，而默认 `ulimit -s` 是 8192KB = **8MB**；**x86-32 才是 2MB**（"1MB"是 Windows 的默认值）。更要紧的是**它是虚拟地址空间预留、只有触碰到的页才提交物理内存**，**真正的常驻成本是内核侧的 16KB 内核栈 + 约 9KB `task_struct` ≈ 25KB，且不计入 RSS**。详细推导见 [[母题-O1-上下文切换与死锁]] 第 3 节。
- **优点**：**共享数据方便**（同一个堆，直接读）
- **代价**：**切换要走内核**（用户态↔内核态）；**共享数据要加锁**（[[母题-M10-锁与死锁]] 的业务层同源问题）

#### 2.3 协程【事实】

- **是什么**：**用户态的轻量执行单元**，由程序自己调度，不由 OS 调度
- **调度者**：**事件循环**（asyncio 的核心）
- **单位成本**：约 **2KB**
- **优点**：**切换几乎免费**（本质是函数调用，不经过内核）
- **代价**：**一处阻塞，全体停摆**（见第 4 节）——这是它最致命的约束

#### 2.4 三者的关键差别只有一个

【推导】**从"谁调度"这一个点出发，上面所有差异都能推出来**：

| | 谁调度 | 由此推出 |
|---|---|---|
| 进程 | OS | 隔离最好、切换最贵 |
| 线程 | OS | 抢占式（不用你让）、切换走内核 |
| 协程 | **你的程序** | 切换便宜、**但必须你自己在等待时让出去** |

> **"必须主动让出去"就是"协作式（cooperative）"的含义。** 线程是抢占式的（OS 会强行换），协程是**协作式**的（你不让，它就一直占着）。

### 3. asyncio 为什么能扛住大量连接

#### 3.1 事件循环做什么【事实】

**事件循环（event loop）**：一个单线程里的循环，反复做三件事：

```
① 看有没有 IO 就绪（靠 epoll / kqueue 这类系统调用，一次问一批）
② 就绪了就执行对应的回调（推进那个协程）
③ 没有就绪的，就睡一小会儿再问
```

【推导】**关键在 ①**：**一次系统调用就能拿到"成千上万个连接里哪些有数据了"**。

对比"一个连接一个线程"的做法：1000 个线程都在 `read` 上等 → **内核要维护 1000 个等待上下文、要做 1000 次调度**。而事件循环是**一个线程问一次**。

#### 3.2 量化：能扛多少

【推导】用**单位内存开销**来算 10 万并发单元需要多少内存（**注意区分"虚拟预留"和"真实常驻"**）：

```
虚拟地址空间（预留，不是占用）：
  线程：约 8MB / 个 × 100,000 = 约 800 GB   ← 64 位有 128TB 虚拟空间，这不是瓶颈
  协程：约 2KB / 个 × 100,000 = 约 200 MB

真实常驻（内核侧，不省不可省）：
  线程：约 25KB / 个 × 100,000 = 约 2.5 GB  ← 16KB 内核栈 + task_struct，且【不计入 RSS】
  协程：0                                  ← 用户态调度，没有内核对象
```

【推导】**所以要说得准确，"协程省"省的是两笔**：

| 省的 | 线程 | 协程 |
|---|---|---|
| **内核侧常驻内存**（每单元一个内核栈 + `task_struct`） | **约 25KB/个** | **0** |
| **调度实体个数**（内核要维护的等待上下文、要唤醒的对象） | 每个线程一个 | 内核只看到少数几个线程 |

【取舍】**这就是"为什么长连接服务用异步"的直接答案**：不是"协程更快"，而是**同样的资源能支撑的并发单元多了两个数量级**，而且**真正拦住"1 万/10 万线程"的往往不是内存，是任务数上限**——`pid_max`（默认 32768）、`threads-max`（默认按内存算，内核栈最多占 1/8 内存）、以及容器里的 `pids.max` / systemd 的 `TasksMax`。**撞到时报的是 `Resource temporarily unavailable`（EAGAIN），不是 OOM。**（完整推导见 [[母题-O1-上下文切换与死锁]] 第 3 节）

**回到 N2 的场景**：1000 个用户在等 SSE 推送 —— 用线程模型就是 1000 个线程常驻（**内核侧约 25MB** + 1000 个被内核调度的实体），用协程就是 1000 个挂起的协程（**内核侧 0**，全部在用户态）。**这是量级差别，不是优化技巧。**

#### 3.3 但协程不是"更快"

【推导】必须说清这一条，否则会答成"协程比线程快"：

- **单个操作的速度**：协程切换快，但**你的业务逻辑本身不会变快**
- **总吞吐**：在 **IO 密集**场景下吞吐大幅提升（因为等待时间被利用起来了）；在 **CPU 密集**场景下**几乎没提升**（1.2 的判据）

### 4. 阻塞代码：协程最致命的坑

#### 4.1 会发生什么【推导】

事件循环是**一个线程**。如果某个协程里执行了一段**阻塞调用**（同步 IO、`time.sleep`、CPU 重活），**整个事件循环就停在那里**——**其他几百上千个连接全部等它**。

```
async def handler():
    r = requests.get(url)      # ← 阻塞调用：整个事件循环停在这里
    return r.json()
```

**它坏在哪**：协程的"让出"发生在 **`await` 一个真正的异步操作**时。**同步阻塞调用里没有 await 点，事件循环没有机会切走**——所以它被一个人占住了。

#### 4.2 量化的后果

```
事件循环被阻塞 200ms
此时 QPS = 1000
→ 这 200ms 内到达的 1000 × 0.2 = 200 个请求全部排队
→ P99 延迟直接被抬升 200ms
```

【推导】**而且这种故障很隐蔽**：CPU 看起来不高、日志里没有异常、每个请求单独测都很快——**只是高峰期整体变慢**。**这就是"异步写错了比同步还慢"的原因。**

#### 4.3 三种解法【取舍】

| 解法 | 做法 | 代价 |
|---|---|---|
| **换异步库** | 用 `httpx.AsyncClient` / `asyncpg` 等原生异步客户端 | 需要确认生态支持；改动最大但最彻底 |
| **丢进线程池** | `await asyncio.to_thread(fn)` / `run_in_executor` | 简单，但线程池有上限，**打满了同样会等** |
| **拆成独立进程** | 把 CPU 重活交给进程池 / 独立服务 | 隔离好，但多了通信成本 |

【判据】**如果那段代码是 IO 阻塞 → 换异步库或丢线程池；如果是 CPU 密集 → 必须丢进程池**（因为 GIL，见第 5 节，丢线程池没用）。

### 5. GIL：为什么协程不能靠多线程绕过去

#### 5.1 GIL 是什么【事实】

**GIL（Global Interpreter Lock）**：CPython 的**全局解释器锁**——**同一时刻只允许一个线程执行 Python 字节码**。

【推导】**直接推论**：

| 场景 | 多线程有用吗 |
|---|---|
| **IO 阻塞** | **有用**——线程在等 IO 时会释放 GIL，别的线程可以跑 |
| **CPU 密集** | **没用**——大家都在抢 GIL，等于串行 |

#### 5.2 和 asyncio 的关系【推导】

**asyncio 是单线程的**——它从设计上就不依赖 GIL 的多线程能力，**而是靠"切换发生在等待点"**。

所以：

- **想用多核**：靠**多进程**（`multiprocessing` / 起多个 worker），不是多线程，也不是协程
- **想扛高并发 IO**：靠**单线程 + 事件循环**，不需要多核

**一句话**：**GIL 不阻止你写高并发 IO 服务（因为瓶颈不在 CPU），但阻止你用多线程加速 CPU 计算。**

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "线程栈约 1MB，开一万个就要 10GB" | 【事实】**两处都错**：① Linux 上线程默认栈由 **`ulimit -s` 决定（默认 8192KB = 8MB）**，"1MB"是 Windows 的默认值（x86-32 才是 2MB）；② 它是**虚拟地址空间预留、按需提交**，真实常驻只有**内核侧约 25KB/线程且不计入 RSS**。而**先撞上的通常不是内存，是 `pid_max` / `threads-max` / 容器 `pids.max`**，报错是 `EAGAIN` 不是 OOM。详见 [[母题-O1-上下文切换与死锁]] 第 3 节 |
| "协程比线程快" | 【推导】**单操作的业务逻辑不会变快**。协程的收益在"IO 密集场景下能把等待时间利用起来"+"单位开销小两个数量级" |
| "asyncio 能利用多核" | 【事实】**不能**。它是**单线程**事件循环。要多核靠**多进程** |
| "协程是并行执行的" | 【事实】**是并发，不是并行**。同一时刻只有一个协程在跑（单线程），只是它们互相交错 |
| "在 async 函数里调用普通同步函数没问题" | 【推导】**有问题**。同步阻塞调用没有 `await` 点，**会卡死整个事件循环**（第 4 节） |
| "用 asyncio 就不用管锁了" | 【事实】单线程下不会有多线程那样的数据竞争，**但仍有竞态**——因为 `await` 会让出控制权，两个协程可能交错修改同一状态。**"await 前后状态可能变"是异步里的经典陷阱** |
| "线程模型不行了，应该全换异步" | 【取舍】**按 1.2 的判据选**：IO 密集且并发量大 → 异步；CPU 密集 → 多进程；并发量小 → 线程模型更简单，**没必要为了异步而异步** |

## 二、自测

**Q1（计算）**：一次请求总耗时 **100ms**，其中 CPU 计算占 **2ms**，等待 IO 占 **98ms**。

问：单核理论上能"同时"处理多少个这样的请求？如果换成 CPU 占 80ms 的请求呢？

**A1**：

- IO 密集：100 / 2 = **50 个**
- CPU 密集：100 / 80 = **1.25 个**（基本等于串行）

【推论】**这就是"要不要用异步"的判据**：

| 负载 | CPU 占比 | 理论并发杠杆 |
|---|---|---|
| 查 DB 的接口 | 2% | **50 倍** |
| 加解密 / 图像处理 | 80% | **约 1.25 倍** |

**所以异步不是普适优化，它只对"在等"的程序有效。** Agent 服务、API 网关几乎全是 IO 密集 → 收益极大；纯计算任务 → 应该走多进程。

**Q2（判读）**：下面这段代码有什么问题？高峰期会看到什么现象？

```python
async def get_user(uid):
    r = requests.get(f"{API}/users/{uid}")   # requests 是同步库
    return r.json()
```

**A2**：**问题在 `requests.get` 是同步阻塞调用**——它**没有 `await` 点**，所以事件循环**没有机会切走**，整个循环被卡在这里。

**高峰期现象**：

- **所有连接一起变慢**（不只是这个接口）
- **CPU 不高、日志无异常**、单独压测这个接口又很快
- **P99 明显抬升**：循环被阻塞 200ms，QPS 1000 时就会有约 200 个请求排队

**修法**：

| 方案 | 说明 |
|---|---|
| 换 `httpx.AsyncClient` | 最彻底（原生异步，真让出） |
| `await asyncio.to_thread(requests.get, url)` | 快速止血，但线程池有上限 |

**判断依据**：这是 **IO 阻塞** → 换异步库或线程池都行；**如果是 CPU 密集，丢线程池没用**（GIL，见 Q3）。

**Q3（计算）**：要做一个**图像压缩**接口，单次压缩耗时 400ms（其中 CPU 占 380ms）。

问：用 asyncio 能提高吞吐吗？用多线程呢？该怎么做？

**A3**：

| 方案 | 有没有用 | 原因 |
|---|---|---|
| asyncio（单线程事件循环） | **没用** | 380ms 是 CPU 时间，没有等待可被利用；而它**还会阻塞事件循环**，把其他请求一起拖慢 |
| 多线程 | **也没用** | **GIL**：同一时刻只有一个线程执行字节码，CPU 密集场景下多线程等于串行 |
| **多进程 / 独立计算服务** | **有用** | 每个进程有独立的 GIL，可以真正并行用多核 |

【推论】判据是 `CPU 占比`：**380/400 = 95%** → 接近纯计算 → **杠杆约 1.05 倍，异步没有价值**。

**正确做法**：把压缩放进**进程池**或**独立服务**，主服务保持异步只负责调度。

【这就是 1.2 判据的第二次应用】——**同一个算式，答了三个不同的问题。**

**Q4（纠错）**：下面这段话哪里错了？

> "asyncio 是并行执行的，所以它比多线程更快，还能利用多核。"

**A4**：**"并行"和"利用多核"两处都错。**

1. **asyncio 是并发，不是并行。** 它是**单线程**事件循环——同一时刻**只有一个协程在跑**，只是它们互相交错（一个在等 IO 时换另一个上）。**并行**需要多个 CPU 核心同时执行，那是多进程的事。

2. **不能利用多核。** 单线程只能吃一个核。而且因为 **GIL**，多线程也吃不满多核。

**"更快"也要说清楚快在哪**：

| | 快在哪 |
|---|---|
| asyncio | **IO 密集场景下的吞吐**（把等待时间利用起来）+ 单位开销小两个数量级 |
| | **不快在**：单个操作的业务逻辑速度 |

**准确说法**：**asyncio 用单线程把 IO 等待时间利用起来，从而在小内存下支撑大量并发连接；要多核得靠多进程。**

**Q5（纠错）**：下面这段话哪里错了？

> "协程和线程差不多，只是切换不用走内核所以更快一点。"

**A5**：**"差不多"是错的——差别在调度方式上，而不只是切换速度。**

| | 线程 | 协程 |
|---|---|---|
| **调度者** | **操作系统** | **你的程序（事件循环）** |
| **调度方式** | **抢占式**（时间片到了 OS 强行换） | **协作式**（你不 `await`，它就一直占着） |
| 单位开销 | 内核侧约 **25KB**（不进 RSS）＋ 用户栈 8MB **虚拟预留** | 约 **2KB**，**内核侧 0**（用户态调度） |

**"协作式"这一条的后果比"切换快"重要得多**：

> **线程不会被你写错的代码卡死（OS 会强行切换）；协程会——一段同步阻塞代码就能让整个事件循环停摆。**

**所以协程的代价不是"切换稍贵"，而是"你必须保证不阻塞"。** 这个约束是它和线程最本质的区别。

**一句话结论**：并发不是"同时干很多事"，而是"**在等的时候去干别的事**"——所以**收益由等待占比决定**（CPU 占 2% 的请求，单核理论上能并发约 50 个）。三种执行单元的差别从"谁调度"推出来：**进程由 OS 调度、地址空间独立（隔离好、通信贵）；线程由 OS 调度、共享地址空间（方便、切换走内核）；协程由用户态事件循环调度、约 2KB 一个（切换几乎免费，但一处阻塞全体停摆）**。**asyncio 能扛住大量连接，是因为单线程一次 `epoll` 就能问出成千上万连接里哪些就绪，加上单位开销小两个数量级——线程每个要占内核侧约 25KB（16KB 内核栈 + `task_struct`，且不计入 RSS）和内核里一个调度实体，协程这两笔全省。**

**恢复关键词**：并发 = 利用等待时间 / 并发杠杆 ≈ 总耗时 ÷ CPU 时间 / IO 密集收益大、CPU 密集收益≈1 / 进程独立地址空间 / 线程共享但切换走内核 / **线程内核侧 25KB + 栈 8MB 虚拟；协程内核侧 0** / 协程由事件循环调度、协作式 / epoll 一次问一批 / **任务数上限是 pid_max / threads-max / pids.max，不是内存** / **阻塞调用卡死整个循环** / GIL 让多线程对 CPU 密集无效 / 多核靠多进程 / 是并发不是并行

**核心不变量 / 主线**：
**并发的收益 = 等待时间占总时间的比例。** 这句话同时决定了三件事：该不该用异步（IO 密集才值得）、asyncio 为什么能扛很多连接（同内存下单元数多两个数量级）、以及它最怕什么（一旦有代码不让出，等待时间就被浪费掉了）。

**完整回答骨架**：先算"时间花在哪"（IO 密集 vs CPU 密集的杠杆）→ 三种执行单元用同一指标比（单位开销 / 谁调度 / 共享什么）→ 从"谁调度"推出所有差异 → 事件循环 + epoll 一次问一批 → 量化 10 万并发的内存 → 协作式的代价（阻塞会卡死整个循环 + 三种解法）→ GIL（为什么多线程救不了 CPU 密集）→ 选型判据

**完整回答（口述稿）**：
并发不是"同时干很多事"，而是"**在等的时候去干别的事**"——所以**收益由等待占比决定**（CPU 占 2% 的请求，单核理论上能并发约 50 个）。

三种执行单元的差别从"**谁调度**"推出来：**进程**由 OS 调度、地址空间独立（隔离好、通信贵）；**线程**由 OS 调度、共享地址空间（方便，但切换要进内核，且每个线程在内核侧要占栈和调度实体）；**协程**由**用户态事件循环**调度、约 2KB 一个（切换几乎免费，但**一处阻塞、全体停摆**）。

**asyncio 能扛住大量连接**，是因为单线程一次 `epoll` 就能问出成千上万连接里哪些就绪，加上**单位开销小两个数量级**——线程每个要占内核侧约 25KB（16KB 内核栈 + `task_struct`，且不计入 RSS）和一个调度实体，协程这两笔全省。代价：它是单线程，**不能利用多核**（多核靠多进程），**CPU 密集任务会卡死事件循环**；协程里调同步库的表现是"所有接口一起变慢、CPU 不高、日志无异常"。

GIL 的含义：CPU 密集任务多线程无效（不能利用多核），IO 密集场景线程池仍有效（等待时释放 GIL），asyncio 本来单线程、影响小。单线程异步**仍要考虑竞态**——`await` 会让出控制权，"await 前后状态可能变"是经典陷阱。

**分层要点**：
- **结论**：进程/线程/协程的差别从"谁调度"推出；asyncio 快在 epoll + 单位开销小两个数量级。
- **推导链**：并发 = 等的时候干别的 → 收益由等待占比决定 → 谁调度 → 单位开销 → 单线程的代价（阻塞/无多核/GIL）。
- **量化**：协程约 2KB vs 线程内核侧约 25KB（16KB 栈 + task_struct，不计入 RSS）；CPU 占 2% 的请求单核可并发约 50 个。
- **边界与常见误解**："协程比线程快"要看是不是 IO 密集；无界队列/无界排队会把过载悄悄变成全局超时（要有背压）；`load` 高而 CPU 不高说明在等 IO，不是该加 CPU。

**追问**（先说后看）

1. **协程和线程最本质的区别是什么？** —— **谁调度**：线程由 **OS 抢占式**调度（会强行换），协程由**程序协作式**调度（你不让就一直占）。**"阻塞代码能卡死事件循环"这个代价就是从这一条来的。**
2. **asyncio 能利用多核吗？** —— **不能**，它是单线程。要多核靠**多进程**；多线程因 **GIL** 对 CPU 密集无效。
3. **在协程里调用同步库会怎样？** —— **卡死整个事件循环**，表现为"所有接口一起变慢、但 CPU 不高、日志无异常"。修法是换异步库或丢线程池。
4. **单线程异步还需要考虑竞态吗？** —— **需要**。`await` 会让出控制权，两个协程可能交错修改同一状态。**"await 前后状态可能变"是异步里的经典陷阱**（这一点和线程加锁是不同形态的同一类问题）。
5. **连接池耗尽 / 协程泄漏怎么排查？** —— 池子耗尽先看上游时延（[[母题-N1-一次请求的完整路径]] 的 `L = λW`）；协程泄漏通常是**创建了任务但没有正确取消**（超时/取消链路要传下去）。

**同类变体**

- 「为什么 Nginx / Redis 用单线程还能这么快？」——**IO 密集 + 事件循环**（Nginx 是多 worker 单线程、Redis 主线程单线程），同一个道理
- 「asyncio 的超时和取消怎么做？」——`asyncio.wait_for` / `CancelledError`，**关键是把取消沿调用链传下去**（CORE-07）
- 「什么是背压（backpressure）？」——上游生产快于下游消费时**必须让上游慢下来**（限队列长度、拒绝），否则内存被队列吃光
