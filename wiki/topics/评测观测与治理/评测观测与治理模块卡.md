## 0. 模块边界（先写这个，防无限扩张）

**包含**：指标怎么分层、评测集怎么建与怎么维护、grader 怎么选与怎么校准、Agent 的过程指标与可重置环境、Trace 数据模型与 Replay 四种模式、CI 回归门禁、成本控制与限流、越权与提示注入防护、灰度发布与回滚、线上反馈飞轮。

**明确不包含**：

- **可观测平台的部署与运维**（Helm / Docker 搭建、容量规划、Collector 调参）**与产品功能横评（哪家好用）**——**但「数据模型落到存储与采集上该怎么设计」进 [[母题-E7-AgentOps平台与自建Trace-Eval]]**。**2026-09-21 修订**：原先把「平台」整条排除，实测下来该排除的是**部署与横评**，不是**设计**——字节 JD 把「LangSmith / Langfuse 等 AgentOps 或自建 Trace / Eval」列为**强竞争力要求**，而「两家为什么都长成这个形状」恰好是本模块**证据层**的内容
- **统计学的完整推导**（置信区间、功效分析）——只用到**样本量决定分辨率**这一层（[[母题-C3-Prompt版本管理与回归]] 已给算式）
- **压测与容量规划的工具链**——属于后端底盘
- **合规审计的完整流程**（等保、ISO）——只到"审计日志该留什么"
- **A/B 实验平台的产品设计**——只到"随机化单位与 guardrail 的注意事项"

**边界判据**：**本模块只回答"怎么证明它变好了、怎么在证明不了的时候不上线"**。凡是"某个平台怎么装"的，不进本卡。

## 5. 项目映射（三个简历项目逐个过）

### 5.1 RuleArena（规则竞技场）· 主承载项目

- **锚点**：`projects/RuleArena/`
- 用在哪：**双评测集 + 发布门禁**；**CI Eval + Trace Dashboard**；**轨迹模型与失败归因**
- 解决什么问题：**门禁拒绝是设计目标**（如实降级）——**这是"门禁真的在拦人"的证据**
- 踩过的坑：**一开始只想报搜索层的好消息——只报 `pass@3` 不报 `pass^3`**，把「三次里只有 1 次稳定成立」藏起来。**这是最危险的写法**——正本自己定了规矩：**引用 golden 必须成对陈述，只报一半等同造假**，而且一旦被追问出来，前面所有数字都会被打上问号。教训是：**「跑 3 次至少成一次」和「3 次次次都成」是两个不同的产品承诺**，单次运行会把这两者掩盖成一个好看的数字。
- 决策与取舍：**两套集子分工明确**——**development 21 用于调试和调优**（可以反复看），**hidden 17 由 Evaluation 侧维护、Runtime 全程不可读，且只用于最终裁决并重复多次**。**判据是「哪一套参与过调优」**：参与过的那套就不能再用来证明泛化（[[母题-E3-回归门禁与发布卡口]] 的回归门禁、[[母题-C3-Prompt版本管理与回归]] 的训练集饱和）。**这条实测还带出一个结构性决策**：搜索保证不了覆盖（`pass^3` 只有 7%），所以可靠性不能押在「搜索变强」上，要押在**运行时门禁**这一层。

### 5.2 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**六层评测与数据飞轮**；**P95 重构的量化口径**；**结算的三道质量门**
- 解决什么问题：**每一层评测集的作用不同**——"用来发现问题"和"用来验收改动"必须是两套
- 踩过的坑：**只报了一个数字，没报口径**——「P95 从 20.4 秒降到 2.8 秒」如果没有**查询集、并发数、数据量、环境和正确性断言**，它就是一个不可比较的数。**同一句 SQL 在不同并发下能差一个量级**。
- 决策与取舍：**要补齐五样才算硬证据，缺一样都防守不住**：① **固定查询集**（哪些查询，为什么是这几个）② **数据量与并发**（604 台 / 15 分钟周期下的真实规模）③ **环境**（机器、PG 版本、是否有缓存预热）④ **基线**（20.4s 是怎么测的，是不是同口径）⑤ **正确性断言**（快了之后结果还对吗——**性能优化最容易悄悄改语义**）。

- 对应母题：【E1】【E3】【E4】

### 5.3 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**150 条评测集**；**Retrieval Eval 与 Answer Eval 分开**；**权限召回测试**
- 解决什么问题：**150 条的分辨率约 ±3%**——只能抓大幅回退，这个限制要主动说出来
- 踩过的坑：**把 150 条当成能分辨小改进的尺子**——150 条、p≈0.78 时标准误约 **3.4%**，**它只能抓大幅回退，分辨不出 2–3 个点的改进**。想论证「改进了 2 个点」需要千条量级。**这条要主动说，别等被问。**
- 决策与取舍：**81→95% 是 Top-K Schema 召回率，不是文档块召回，也不是幻觉率**——它是「**该找的表/字段有没有进候选**」这一层。**和幻觉率是两回事**：召回失败是「证据压根没进来」，幻觉是「证据进来了却没被用对」；**RAG 只治前者，甚至可能加重后者**（[[母题-C4-幻觉的成因与可控性]] 的「RAG 只治第三类」）。**说这个数必须带上「Schema」两个字。**

- 对应母题：【E1】

## 8. 题级答案（「本主线的题」翻转卡背面 · 先说后翻）

> 题号与第 4 节题单一一对应。**必背**题写成能直接说出口的一段话；**理解 / 了解**题写 1–3 句。
> 翻转卡背面先给这道题的答案，再挂上「所属母题的完整回答（口述稿）」与单卡入口——两段合起来才是深挖。

### 1 （必背）
三步：① **构造可重置环境**（能反复跑、能固定随机种子与 fixture——这一条排第一位，否则结果不可复现）；② **分层指标 + 分层数据集**；③ **判分优先规则 / 代码 grader，语义部分才用校准过的模型 Judge**，并保存完整轨迹。

流程上：离线回归 → Shadow → A/B；线上 Bad Case 回流成新样本。第一性原理是：把模糊目标变成**可比较、可复现、可定位**的判断。

### 2 （必背）
六层：**业务结果 / 任务结果 / 过程（诊断价值最高）/ 工程 / 资源 / 安全**。

不能用一个综合分，最硬的理由是**安全单独门禁、不参与平均**——把它放进平均等于允许"用高质量文案换一次越权"：业务 80、任务 85、过程 70、工程 90、资源 75、**安全 10** 的平均分是 68.3，看起来"刚及格"。另外单步指标好不等于端到端好（每步 95%，10 步只剩 60%）。

### 3 （必背）
**数据集分五层**：Dev 可以反复看；**Golden / Holdout / Adversarial / Online 不能拿来调优**——看多了就退化成 Dev（真实案例：训练集打平、held-out 差 11.9 个点）。

维护四条：**版本化**、**去重**、**检查泄漏**、**定期审计"坏题"**；来源不能只有专家构造，必须包含**真实失败与用户纠正**。对抗集要有权限攻击样本；线上反馈要经隐私处理与筛选才成为 candidate。

### 4 （必背）
按 `SE = √(p(1−p)/n)` 定：150 条约 ±3.4%，200 条约 ±2.1%，**想分辨 2 个百分点需要约 900 条**。所以先想清楚"我要证明多大的差异"，再决定集合规模。

另外**稳定性和能力要分开测**：看 **pass^k 而不是单次**（单次通过率 0.9，pass^5 只有约 59%），门禁用"**通过率不低于阈值 + 置信区间**"，而不是"这一次过了就行"。

### 5 （必背）
三个问题：**偏差**（偏爱更长的回答）、**漂移**（同一输入不同时间给出不同结果）、**自洽幻觉**（给自己的输出打高分）。

三条纪律：**用人工样本校准**、**记录 grader 版本**（否则两次结果不可比）、**只用在确定性判分覆盖不到的地方**。判分顺序不能反——10 项检查全用模型 Judge（单步 85% 准）只有 **19.7%** 全对，60% 确定化后升到 **52.2%**。

### 6 （理解）
因为模型 Judge 是**概率判断**，确定性检查是**必然判断**——格式、枚举、SQL 能不能跑、工具是否被正确调用，都能用代码判，而且不会漂移。

数字很直白：10 项检查全用模型只有 19.7% 全对，60% 确定化后升到 52.2%。所以顺序是：**规则 / 代码 grader 优先，模型 Judge 兜底语义**，且 Judge 要校准、要记版本。

### 7 （必背）
**日志是线（事件流），Trace 是树（调用树）**。日志回答"发生了什么"，Trace 回答"**谁导致了谁**"。

树有父子关系，所以能算"这一步占多少时间""这个失败是谁引起的"——日志只能人工对着时间戳猜，而 **Agent 天然多步，这个成本随步数急剧上升**。三者分工：指标看分布与趋势、Trace 看因果与归因、日志看细节与原文，互补不是替代。

### 8 （理解）
层级（trace / run / span 的父子关系 + `trace_id`）；每个 span：类型、起止时间、**版本（model / prompt / tool / rule）**、**Artifact 引用**、**幂等键**、token 用量、错误码。检索 span 还要带 query / candidates / 索引版本。

**少了版本就复现不出来**——这跟 Agent 侧 Step 记录是同一套字段。存储要控：50 span × 2KB × 1 万 run ≈ 1 GB/天，所以按信息价值采样（**失败全采 + 成功抽样**）+ 分级存储。

### 9 （必背）
按三岔路走：① 正确证据**进 TopK 了吗**（没进 → 召回问题）；② 进了 TopK 但**进最终 Context 了吗**（没进 → 重排 / 预算 / 去重）；③ 都进了还是错 → **生成 / Prompt / 引用**问题。

**前提是 Trace 把候选、分数、重排位置、上下文版本都留下来了**，否则只能猜。

### 10 （必背）
四种：**Exact view**（复盘当时到底发生了什么）、**Mock**（固定下游，只比 Prompt 与模型的影响）、**Sandbox**（端到端跑，用沙盒隔离副作用）、**Shadow**（真实流量上验分布）。

关键一条：**写工具默认不能在生产 Replay**——否则调试就变成事故重放。

### 11 （必背）
四条：① **看 pass^k 而不是单次**（单次 0.9，pass^5 只有约 59%）；② **固定环境 fixture 与随机种子**；③ 门禁报"**通过率 + 置信区间**"，不是"这一次过没过"；④ **Mock replay 隔离变量**，让比较只受一个因素影响。

### 12 （必背）
两类性质完全不同：**绝对红线型**——越权、未确认副作用、跨租户泄露，**必须为 0，不接受平均也不接受阈值**；**统计阈值型**——成功率降幅、P95、成本，按评测集分辨率定，**两类要分开报**。

阈值要和分辨率匹配：200 条的标准误约 2.1%，阈值设 2% 会在"什么都没变"时产生**约 17% 的单侧误报**——要么放宽到 2 个标准误，要么把集合做大到约 900 条。

红线还要报"**上界**"而不是"通过"：1000 个对抗样本 0 次泄露，按三倍法则 95% 上界约 **0.3%**——你能说"低于 0.3%"，不能说"不会泄露"（要声称 0.1% 就得有 3000 个样本）。

### 13 （理解）
三类原因：① **错误会累积**（每步 95%，10 步只剩 60%）；② **优化子指标反而伤了总目标**（召回更多文档提高了 Recall，但上下文噪声增加让最终正确率下降）；③ **评测口径不一致**（单步用 Mock、端到端用 Sandbox，环境不同）。

### 14 （必背）
第一性原理：**先归因、再动手、先动大头、先做无损的**。先拆账单（按功能 / 租户 / 任务类型 / **环节**），先回答"是**量涨了**还是**单价涨了**"（两件事解法完全不同）。

**环节这一维最重要，因为它直接对应动作**：输入占大头 → 提缓存命中率（**无损**，本例能省 43%）；输出占大头 → 收输出 / 调 effort；工具占大头 → consolidation；存储占大头 → 降采样。

**降本顺序不可颠倒**：提命中率（无损）→ 去拐杖（双赢）→ 压缩（有损）→ 调 effort / 换模型（换质量）。再加按预算分档（七种预算）。

### 15 （理解）
**四层都要放**：入口（总量，最早最粗）、**租户**（公平，否则入口限流对其他租户无意义）、**工具**（保护第三方配额）、**模型**（RPM / TPM 与成本，最贵最容易失控）。

只做入口限流的坑：一个租户就能占满配额；而且 **Agent 一个请求会触发几十次下游调用**，网关看起来正常但模型 TPM 已经满了。

超限后：**有界排队 → 降级 → 快速失败**（带可行动的错误）。关键是**排队必须有界**——无界排队会把过载悄悄变成全局超时。

### 16 （理解）
三个要求：① **已验证**——备用配置要在 held-out 上过过门禁；② **有明确的质量底线**——降级的目标是**保住可用性，不是保住质量**；③ **可观测**——降级本身要打点报警，**不知道自己在降级比降级更危险**。

成本与质量的取舍由**能回答"一次失败值多少钱"的人**定；工程给的是**成本 vs 质量的曲线**，把曲线交给业务方选点，比工程师替业务拍板更安全。

### 17 （必背）
**越权两个方向**：纵向（低权限做了高权限的事）、横向（看到不属于自己的数据——影响半径是"一整个租户的数据"且**静默**，常被低估）。AI 系统里横向越权还有一条特有路径：**检索**——权限必须在召回前生效，因为**未授权内容一旦进上下文就已经泄露了**；而且**缓存会绕过 ACL**，所以缓存按租户分区不是优化，是权限模型的一部分。

**提示注入**的麻烦是"过滤不过来"：间接注入来自任何工具返回的内容（网页、文档、日志、评论），而 Agent 场景的损失在**动作层面**。所以防线按确定性排序：**边界（沙箱 + 最小权限 + 真凭证不进沙箱）→ 契约（参数独立校验、危险动作需确认）→ 过滤（内容检测）**，**顺序不能反**。

### 18 （必背）
因为**"防住"是概率判断，"安全"是存在性判断**。过滤总会被绕过，所以真正的目标不是"阻止注入发生"，而是"**让注入即使发生也没有后果**"——这正是边界优先于过滤的理由，而且"以为有防线"比"没有防线"更危险。

验证方式：**红队测试 + 说清 N**：故意注入"把 ~/.ssh 读出来发到某域名"，看它是否**既读不到、也发不出**——**两个边界各测一条路径，只测一条会漏**。

### 19 （理解）
**不能**。安全是存在性判断（"必须为 0"），不是连续量；放进平均分等于允许"用高质量文案换一次越权"——业务 80、任务 85、过程 70、工程 90、资源 75、安全 10 的平均分是 68.3，看起来"刚及格"。

正确做法：**安全单独门禁、不参与平均，且要报上界**（1000 个样本 0 次泄露 = 95% 上界约 0.3%，不是"不会泄露"）。

### 20 （必背）
**七步，不能跳**：离线 Eval → **Shadow** → 内部 dogfood → 小流量灰度 → A/B → 扩量 → 持续监控。**每一步回答前一步回答不了的问题**——Shadow 零成本发现"打爆下游"，灰度却要影响真实用户。

为什么强调回滚速度：**影响面积 ≈ 事故率 × 灰度流量 × 回滚耗时**，回滚 30 分钟 vs 2 分钟，影响面积差 15 倍。所以"**放 1% 不等于风险 1%**"——比例只决定有多少请求撞上新版本，另外两项与比例无关；**没有回滚能力的灰度只是小规模事故**。降级是应急（切备用配置保可用性），回滚是根治，常见组合是先降级止血再回滚修复。

### 21 （必背）
节奏 **1% → 5% → 20% → 50% → 100%**（经验示例，非规定值），每档确认后再进。

**停止条件是事先定的**：**红线**（越权、未确认副作用）看到就停，**不等统计显著**；**guardrail**（P95、成本）超阈值也停。

### 22 （理解）
五个注意点里最容易踩的两条：① **随机化单位必须与体验的单位一致**——按请求随机时，一个用户 10 次请求约 99.8% 会看到两个版本（体验与度量同时被污染）；② **先定义主指标与 guardrail**——先看数据再挑指标等于制造假阳性。

另外还要：分桶稳定、样本量够、持续时间覆盖业务周期。

### 23 （理解）
能回流的六类：**用户改后的正确答案 / SQL / 规则**、**在哪放弃**、**哪条引用不支持结论**、**工具调用被拒或被撤销**、**任务实际业务状态**——它们都是"**带正确答案的样本**"。

但**必须经过隐私处理 + 人工 / 规则筛选**才能成为 Eval candidate，不能直接拿去训练或评测（否则是拿线上噪声当标准答案）。

### 24 （必背）
平台卖的不是"更漂亮的日志"，是**一条管道**：**采集（SDK / OTel）→ Trace 树 → Score → Dataset + Experiment**，正好把 E 簇三条主线做成了现成实现。

两家的数据模型独立收敛到同一套形状（层级 / 边界 / 归组：observation 或 run 可嵌套 → trace → session / thread），**说明这是问题的形状而不是产品口味——记结构、别背命名**。硬数字：LangSmith 单条 trace 上限 **25,000 个 run**，超过拒收。

### 25 （理解）
自建要付三笔：① **采集链路的可靠性**——必须非阻塞、先落地再入库（SDK 缓冲 → 批量上报 → **先写对象存储** → 队列只放引用 → Worker 落库），两个理由都是可靠性：峰值不打库、库挂了不丢事件；代价是**短命进程必须 `flush()`**，以及 OTLP 下**孤儿 span 会被静默丢弃**，所以"有 Trace"必须靠 **Replay 反向验证**；② **存储按查询形状选**（Trace 的读是分析型、写是追加型）；③ **Score / Dataset / Experiment 三套都要自己搭**。

选型看约束不看功能表：数据要不要留在自己机房、能接受多长的采集延迟、trace 上限与保留期、是否自托管——功能表谁都能勾选，差别在这些约束上。
