# 母题 E6 · 灰度发布与回滚

**题目**：面试官问——"新版本怎么上线？灰度放多少？什么情况下回滚、回滚要多久？"

**母题**：**离线评测过了、门禁也过了——那"上线"这一步还需要什么？为什么"灰度 1%"不等于"风险只有 1%"？**

**为什么重要**：这道题**决定了前五张卡的成果能不能安全地送到用户手里**。**门禁再严，也只是"离线测过"**——**真实分布的复杂性永远超出评测集**。而"灰度"这件事**最容易被误解成"放小一点就行"**——**真正的关键是"能不能立刻收回来"**。**没有回滚能力的灰度，只是小规模事故。**

## 一、教材

### 1. 前提：灰度的本质是"放小 + 能收回"

::figure rollout-and-rollback.svg | 上线七步，以及回滚速度为什么决定灰度的价值 | 七步上线顺序；左侧是回滚速度与影响面积的关系；右侧是随机化单位的概率陷阱

【推导】**为什么"离线评测过了"还不等于"可以全量上"**：

```text
离线评测集是【采样】的：
  · 它覆盖不了真实分布的全部形态（[[母题-E1-评测集设计与pass^k]] 的 Online sample 就是干这个的）
  · 它跑在一次性的环境里，而真实环境是持续变化的
  · 它测不到"新版本在真实流量下的资源行为"（P95、下游压力）

→ 所以上线必须有一个"真实流量、可撤回"的中间阶段
```

【事实】**七步顺序**（study/07）：

```text
离线 Eval → Shadow → 内部 dogfood → 小流量灰度 → A/B → 扩量 → 持续监控
```

【推论】**每一步都在回答前一步回答不了的问题**：

```text
离线 Eval   → 它在已知问题上对不对
Shadow      → 它在【真实流量】上会不会报错、耗多少资源（不影响用户）
dogfood     → 它在【真实使用】下体验如何（自己人承担风险）
灰度        → 它在【真实用户】上会不会出问题（小比例）
A/B         → 它是不是【真的更好】（而不是只是没变差）
扩量 + 监控 → 它在规模下是否稳定
```

【取舍】**顺序不能跳**——**跳步等于用"没测过的维度"去赌**。**比如跳过 Shadow 直接灰度，你会在真实用户身上发现"它会打爆下游 DB"**——而这个问题在 Shadow 阶段零成本就能发现。

**到这里你应该能回答**：为什么"离线评测全过"仍然需要灰度，而不是直接全量？

### 2. 回滚速度决定灰度的价值【推导】

【推导】**灰度期间发生事故，影响面积取决于什么**：

```text
影响面积 ≈ 事故率 × 灰度流量 × 回滚耗时

注意最后一项是【回滚耗时】——
  因为事故从"发生"到"停止"的时间，完全由回滚速度决定
```

【推导】**算一下**：

```text
灰度 5%，总流量 10,000 请求/分钟
回滚需要 30 分钟：
  期间经过的请求 = 10,000 × 30 = 300,000
  受影响（5% 灰度 + 假设 1% 事故率）= 300,000 × 5% × 1% = 150 个

把回滚练到 2 分钟：
  期间经过的请求 = 20,000
  受影响 = 20,000 × 5% × 1% = 10 个

影响面积降到 1/15
```

【结论】**回滚速度直接决定灰度的价值**——**它不是"运维指标"，是"风险控制的乘数"。**

【取舍】**所以灰度上线前必须准备好的**：

```text
① 回滚判据（什么现象出现就回滚 —— 事先定好，不是临时讨论）
② 一键回滚（不需要重新构建、重新发布）
③ 演练过（在非故障时跑过一次，知道要多久）
④ 数据兼容（新旧版本能不能同时存在 —— 这是最常见的回滚障碍）
```

【推论】**第 ④ 条最容易被忽略**：**如果新版本写了旧版本读不懂的数据，代码回滚了数据也回不去**——**这就是"回滚不是免费的"**。**而且它和 [[母题-A3-失败恢复与幂等]] 的"不确定窗口"是同一类问题**：**动作已经产生了不可逆的影响。**

【事实】**一条不等统计显著的规则**：

> **"高风险错误不能等待统计显著才停止。"**

【推论】**A/B 的常规逻辑是"等显著再下结论"，但安全类问题不能这么办**——**看到一次跨租户泄露就停，不需要等它显著**（[[母题-E5-越权与提示注入防护]] 的"红线不参与平均"在发布阶段的版本）。

**到这里你应该能回答**：为什么"我们灰度放 1%，很安全"这句话，必须先回答"回滚要多久"？

### 3. 随机化单位：必须与"体验的单位"一致【推导】

【事实】**study/07 的第一条 A/B 注意点**：

> **"随机化单位要与用户 / 会话一致，避免污染。"**

【推导】**按"请求"随机会发生什么**：

```text
一个用户在一次会话里发了 10 个请求
每个请求独立地以 50% 概率进入新版本

这个用户【看到的全是同一个版本】的概率：
  = 0.5¹⁰ × 2 = 2 / 1024 ≈ 0.2%

→ 也就是说【约 99.8% 的概率，他会看到两个版本混在一起】
```

【结论】**按请求随机，等于让几乎每个用户都经历"版本混用"。**

【推论】**两个后果**：

```text
① 体验层面：同一个用户在几分钟内看到两种行为（答案风格变了、功能时有时无）
   → 用户困惑，而且反馈不可信
② 度量层面：两组之间的差异被"混用"稀释
   → 你测出来的差比真实差小，甚至测不出
```

【推论】**判据是一句话**：**随机化的单位，必须和"用户感知到的那个整体"一致**：

```text
聊天助手      → 按【会话】随机（一次对话内保持一致）
单次工具调用  → 按【请求】随机可以
同一个用户的一致性有意义的场景 → 按【用户】随机
```

**到这里你应该能回答**：为什么"我们把 5% 的请求切给新版本"在对话式产品里是个错误的方案？

### 4. A/B 的其余四个注意点【事实】

【事实】**study/07 给的清单**：

```text
① 随机化单位要与用户 / 会话一致，避免污染
② 先定义主指标与 guardrail
③ 关注新奇效应、网络效应和长期行为
④ 高风险错误不能等待统计显著才停止
⑤ 记录模型、Prompt、知识、工具的完整 treatment
```

【推导】**第 ② 条为什么是"先"**：

```text
先定主指标 → 你想优化什么（比如任务成功率）
先定 guardrail → 什么不许变坏（比如 P95、成本、安全红线）

如果先看数据再定指标 → 【从数据里挑一个"看起来变好了"的指标】
→ 这是 p-hacking 的变体，几乎必然得到假阳性
```

【事实】**第 ③ 条的三个效应各有名字**：

```text
新奇效应：用户因为"它是新的"而多用了 → 一周后回落
网络效应：A 组的改动影响了 B 组的体验
          （典型：改了推荐/内容，两组看到的内容互相影响）
长期行为：短期指标涨、长期留存跌（"薅羊毛"型改动）
```

【事实】**第 ⑤ 条是 AI 系统特有的**：

```text
传统的 A/B 记录"代码版本"就够了
AI 系统的 treatment 是【五元组】：
  模型 + Prompt + 知识/索引 + 工具定义 + 参数（temperature / effort）

少记任何一项 → 你复现不出这次实验，也无法归因
```

【推论】**这和 [[母题-C3-Prompt版本管理与回归]] 的"四者必须绑定到结果上"是同一条**——**A/B 只是把它用在了发布阶段。**

**到这里你应该能回答**：为什么 AI 系统的 A/B 比传统系统更难归因？

### 5. 反馈飞轮：用户反馈不是一个点赞按钮【推导】

【事实】study/07 的原话与清单：

> **"高价值反馈"**：

```text
· 用户修改后的正确答案 / SQL / 规则
· 放弃、重试、转人工
· 哪一条引用不支持结论
· 工具调用被拒绝或撤销
· 任务实际业务状态
· 用户对结果的具体分类原因
```

【推导】**为什么"点赞/点踩"价值低**：

```text
点赞/点踩告诉你"他不满意"，但不告诉你【哪里不满意】
  → 无法定位到具体哪一段
  → 也就无法变成一条可复现的评测样本

而"用户把答案改成了什么"是一条【带正确答案的样本】
  → 直接可以进评测集
  → 而且是【真实高频】的（用户真的问了这个问题）
```

【推论】**反馈飞轮的价值在于"把线上失败变成离线评测集"**——**而这个过程需要的是"带具体信息的反馈"，不是"一个分数"。**

【事实】**一条硬要求**：

> **"每个失败经过隐私处理和人工 / 规则筛选，成为 Eval candidate；不是未经清洗直接训练。"**

【推论】**两个原因**：

```text
① 隐私：用户改的内容里可能有敏感信息（[[母题-E5-越权与提示注入防护]]）
② 质量：用户的修改不一定是"正确答案"——他可能只是改成了自己喜欢的风格
   → 直接拿去训练/评测会引入错误的标准
```

【取舍】**所以飞轮的形状是**：

```text
线上失败 → 隐私处理 + 人工/规则筛选 → Eval candidate → 进入评测集（Dev 或 Golden）
                                                        ↓
                                              再驱动下一轮优化
```

**到这里你应该能回答**：为什么"我们收集了用户点赞"对改进系统帮助有限？

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "灰度放 1% 很安全" | **风险不只看比例，还要看回滚速度**：**影响面积 ≈ 事故率 × 灰度流量 × 回滚耗时**。**回滚 30 分钟 vs 2 分钟，影响面积差 15 倍**。**没有回滚能力的灰度只是小规模事故** |
| "回滚就是 git revert" | **代码能回滚，数据不一定**——**如果新版本写了旧版本读不懂的数据，回滚后系统会坏在数据上**。**这是最常见的回滚障碍**，所以上线前要问"新旧版本能不能同时存在"（[[母题-A3-失败恢复与幂等]] 的同一类问题） |
| "我们把 5% 的请求切给新版本" | **对话式产品里这会污染体验**：**按请求随机时，一个用户 10 次请求里约 99.8% 会看到两个版本**。**随机化单位必须与"体验的单位"一致**——聊天按会话、单次调用按请求 |
| "先上灰度，看数据再说优化什么" | **主指标和 guardrail 必须先定**。**先看数据再挑指标，是 p-hacking 的变体**——**几乎必然得到假阳性**（[[母题-E1-评测集设计与pass^k]] 的"追噪声"） |
| "看到错误率涨了就等等看是否显著" | **高风险错误不能等统计显著**。**一次跨租户泄露就该停**——**安全和质量不一样，它没有"再观察观察"这个选项**（[[母题-E5-越权与提示注入防护]] 的红线逻辑） |
| "A/B 记录代码版本就够了" | **AI 系统的 treatment 是五元组**：**模型 + Prompt + 知识/索引 + 工具定义 + 参数**。**少记任何一项，你都复现不出这次实验**（[[母题-C3-Prompt版本管理与回归]]） |
| "收集用户点赞就是反馈飞轮" | **点赞只说"不满意"，不说"哪里不满意"**——**无法定位、无法变成评测样本**。**高价值的是"用户把答案改成了什么""在哪放弃""哪条引用不支持结论"**。而且**必须经过隐私处理与筛选，不能直接拿去训练** |

【取舍】读成一句话：**上线的目标不是"发布出去"，是"发布出去且随时能收回来"——所以灰度这一步考验的其实是回滚能力。**

## 二、自测

**Q1（计算）**：某服务总流量 **10,000 请求/分钟**，灰度 **5%**，灰度期间的事故率约 **1%**。

问：**如果回滚需要 30 分钟，受影响请求是多少？如果做到 2 分钟呢？**

**A1**：

```text
回滚 30 分钟：
  经过请求 = 10,000 × 30 = 300,000
  受影响 = 300,000 × 5% × 1% = 150 个

回滚 2 分钟：
  经过请求 = 10,000 × 2 = 20,000
  受影响 = 20,000 × 5% × 1% = 10 个

影响面积降到约 1/15
```

【结论】**回滚速度直接决定灰度的价值**——**它不是"运维指标"，是"风险控制的乘数"。**

【推论】**公式可以背**：

```text
影响面积 ≈ 事故率 × 灰度流量 × 回滚耗时
```

**注意最后一项**：**事故从"发生"到"停止"的时间完全由回滚速度决定**——**所以"降低灰度比例"和"加快回滚"是同一件事的两种做法，而后者不需要牺牲验证效果。**

【补充】**还有一个前提容易被漏**：**回滚不一定回得去**——**如果新版本写了旧版本读不懂的数据，代码回滚了系统还是会坏在数据上。** 所以上线前要问"**新旧版本能不能同时存在**"。

**Q2（计算）**：某对话产品按**请求**做 A/B：每个请求独立地以 **50%** 概率进入新版本。

问：**一个用户在一次会话里发 10 个请求，他"全程只看到一个版本"的概率是多少？**

**A2**：

```text
全程都是旧版本：0.5¹⁰ = 1/1024
全程都是新版本：0.5¹⁰ = 1/1024

全程只看到一个版本 = 2 / 1024 ≈ 0.2%

→ 也就是说【约 99.8% 的概率，他会看到两个版本混在一起】
```

【结论】**按请求随机，等于让几乎每个用户都经历"版本混用"。**

【两个后果】：

```text
① 体验层面：同一用户在几分钟内看到两种行为（风格变了、功能时有时无）
   → 用户困惑，反馈也不可信
② 度量层面：两组差异被"混用"稀释 → 测出来的差比真实差小，甚至测不出
```

【判据】**随机化单位必须与"体验的单位"一致**：

```text
聊天助手       → 按【会话】随机
单次工具调用   → 按【请求】随机可以
用户级一致性有意义的场景 → 按【用户】随机
```

**Q3（判读）**：某团队要上线一个新 Prompt。他们的计划是：

```text
直接灰度 5%，观察 1 小时，没问题就扩到 100%。
```

问：**这个计划缺了什么？**

**A3**：**缺了至少三样。**

```text
① 【回滚判据】—— 什么现象出现就回滚？事先定好，不是临时讨论
   现在的问题是："观察 1 小时"要看什么？错误率？P95？成本？业务指标？

② 【回滚能力】—— 能一键回滚吗？要多久？
   如果回滚要 30 分钟，那么"观察 1 小时"里的任何决策都晚了（Q1 的影响面积公式）

③ 【跳过了前面的步骤】
   离线 Eval → Shadow → dogfood → 灰度
   直接灰度跳过了 Shadow —— 而"它在真实流量下会不会打爆下游"这类问题
   在 Shadow 阶段零成本就能发现，在灰度阶段却要影响真实用户
```

【补充】**还有一个 AI 系统特有的**：**treatment 记全了吗？**（模型 + Prompt + 知识/索引 + 工具定义 + 参数）——**少记一项，出问题时就无法归因。**

【准确说法】"**灰度前的准备清单**：**① 离线与 Shadow 已过 ② 回滚判据已定 ③ 回滚演练过、知道耗时 ④ 数据新旧兼容 ⑤ 主指标与 guardrail 已定 ⑥ 完整 treatment 已记录。** **这六项齐了，灰度才是"受控实验"而不是"小规模事故"。**"

**Q4（纠错）**：下面这段话哪里不准确？

> "我们灰度只放 1%，风险很小，可以多观察几天。"

**A4**：三处问题。

1. **风险不只看比例，还要看回滚速度**：**影响面积 ≈ 事故率 × 灰度流量 × 回滚耗时**——**回滚 30 分钟 vs 2 分钟差 15 倍**（Q1）。**"放得小"和"收得快"是两件事，后者更可控。**
2. **"多观察几天"有代价**：**灰度期间是双版本并存的**——**两套代码、两套数据兼容、两套监控**，运维复杂度翻倍；**而且如果新版本写了旧版本读不懂的数据，观察越久回滚越难**（[[母题-A3-失败恢复与幂等]]）。
3. **"观察"要有判据**：**主指标和 guardrail 必须先定**（study/07 明确写了"先定义主指标与 guardrail"）——**否则"观察"就变成了"看到什么算什么"，而人天然倾向于把模糊信号解释成"还行"。**

【准确说法】"**灰度是"受控实验"，不是"小心翼翼地多放一会"**：**判据事先定、回滚练过、扩量有节奏（1% → 5% → 20% → 50% → 100%，每一档确认后再进）。** 而且**高风险错误不能等统计显著**——**看到就停。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们上线后收集用户点赞和点踩，用来改进系统。"

**A5**：三处问题。

1. **点赞/点踩只说"不满意"，不说"哪里不满意"**——**无法定位到具体哪一段，也就无法变成可复现的评测样本**。
2. **高价值反馈是"带信息的那种"**：**用户修改后的正确答案 / SQL / 规则、在哪放弃、哪一条引用不支持结论、工具调用被拒绝或撤销、任务的实际业务状态**——**这些才是"带正确答案的样本"**，而且**是真实高频的**。
3. **而且不能直接拿来用**：study/07 明确要求"**每个失败经过隐私处理和人工 / 规则筛选，成为 Eval candidate；不是未经清洗直接训练**"——**两个原因**：**隐私**（用户改的内容可能有敏感信息）和**质量**（用户的修改不一定等于正确答案）。

【准确说法】"**反馈飞轮的价值在于"把线上失败变成离线评测集"**——**而它需要的是"带具体信息的反馈"，不是"一个分数"。** 而且**中间必须隔着"隐私处理 + 人工/规则筛选"这一步。**"

---

## 三、面试输出（学完再看）

**一句话结论**：**灰度的本质是"放小 + 能收回"**，而**回滚速度决定灰度的价值**——**影响面积 ≈ 事故率 × 灰度流量 × 回滚耗时**：回滚 **30 分钟 vs 2 分钟，影响面积差 15 倍**。**所以"放 1%"不等于"风险 1%"**，**没有回滚能力的灰度只是小规模事故**。**上线七步且不能跳**：离线 Eval → Shadow → dogfood → 小流量灰度 → A/B → 扩量 → 持续监控——**每一步回答前一步回答不了的问题**（Shadow 零成本发现"打爆下游"，灰度却要影响真实用户）。**A/B 有五个注意点**：**① 随机化单位必须与体验的单位一致**（按请求随机时，一个用户 10 次请求**约 99.8% 会看到两个版本**）② **先定义主指标与 guardrail**（先看数据再挑指标是 p-hacking）③ 关注新奇效应、网络效应、长期行为 ④ **高风险错误不能等统计显著** ⑤ **记录完整的 treatment（五元组：模型 + Prompt + 知识/索引 + 工具定义 + 参数）**。最后，**回滚不一定回得去**——**如果新版本写了旧版本读不懂的数据，代码回滚了系统还是会坏在数据上**。而**反馈飞轮要的是"带具体信息的反馈"**（用户改成了什么、在哪放弃），**不是点赞按钮**，**而且中间必须隔着隐私处理与筛选**。

**恢复关键词**：**灰度 = 放小 + 能收回** / **影响面积 ≈ 事故率 × 流量 × 回滚耗时**（30 分 vs 2 分 = 15 倍）/ 七步不可跳（离线 → Shadow → dogfood → 灰度 → A/B → 扩量 → 监控）/ 每一步回答前一步答不了的问题 / **随机化单位 = 体验的单位**（按请求 → 99.8% 看到两版）/ 主指标与 guardrail 先定 / 新奇效应 · 网络效应 · 长期行为 / **高风险不等显著** / **treatment 五元组** / **回滚不一定回得去**（数据兼容）/ 高价值反馈 = 带信息的那种 / 反馈要过隐私 + 筛选

**核心不变量 / 主线**：
**上线的目标不是"发布出去"，是"发布出去且随时能收回来"。**
所以灰度这一步考验的**其实是回滚能力**——**而回滚的能力，取决于你上线前有没有想过"如果它坏了，我能不能退回去"。**

**完整回答骨架**：先破"离线过了就能上"（离线是采样的）→ **七步顺序与每一步回答什么** → **回滚速度的价值（给影响面积算式）** → 回滚的四个准备（判据 / 一键 / 演练 / 数据兼容）→ **随机化单位的概率陷阱** → A/B 的五个注意点 → **反馈飞轮要什么反馈** → 收束到"能收回来"

**追问**（先说后看）

1. **新版本的上线顺序是什么？** —— **离线 Eval → Shadow → 内部 dogfood → 小流量灰度 → A/B → 扩量 → 持续监控。** **每一步回答前一步回答不了的问题**，**顺序不能跳**。
2. **灰度放量怎么定，什么情况下立即停止？** —— **节奏是 1% → 5% → 20% → 50% → 100%，每档确认后再进**；**停止条件是事先定的**：**红线（越权、未确认副作用）看到就停，不等显著**；**guardrail（P95、成本）超阈值也停**。
3. **A/B 有哪些坑？** —— 五个（见上）。**最容易踩的是"随机化单位"和"先定指标 vs 先看数据"**——**前者污染体验与度量，后者制造假阳性。**
4. **线上用户修改怎样回流？** —— **用户改后的正确答案 / SQL / 规则、在哪放弃、哪条引用不支持结论、工具调用被拒或被撤销、任务实际业务状态**——**这些是"带正确答案的样本"**。**但必须经过隐私处理 + 人工/规则筛选才成为 Eval candidate，不能直接拿去训练或评测。**
5. **降级和回滚是什么关系？** —— **降级是"临时切到备用配置，先保住可用性"**（[[母题-E4-成本控制与限流]]）；**回滚是"把版本退回去，问题消失"**。**降级是应急手段、回滚是根治**——**先降级止血，再回滚修复，是常见的组合。**

**同类变体**

- 「Shadow 和灰度有什么区别？」——**Shadow 是"跑真实流量但不生效"**（结果旁路，不影响用户）——**它能发现"会不会报错、耗多少资源"，但测不出"用户体验如何"**（因为用户根本没看到结果）。**灰度是"真实用户真的看到新版本"**——**风险更大，但也只有它能测出体验。**
- 「小团队没有 A/B 平台怎么办？」——**做不了严格的 A/B，但灰度仍然要做**。**替代方案**：**① 用"分阶段放量 + 前后对比"**（不如 A/B 干净，但能抓住大问题）② **重点盯 guardrail 而非增量收益**（"没变坏"比"变好了多少"更容易判断）③ **把资源投在"离线评测 + 回滚能力"上**——**这两样的性价比对小团队最高。**
