# 母题 E7 · AgentOps 平台与自建 Trace / Eval

> **模块**：评测观测与治理 / 动作（第三主线的工程落地）
> **所属主线**：三 · 怎么安全地变（这条线在回答"改了之后怎么知道没退化、以及谁来保证"）
> **层级**：B · 标准级（机制型：存储与采集的设计能由「读是分析型、写是追加型」这条因果链推出来；只有「选哪家」是清单，且清单本身也由约束推出）
> **关联母题**：[[母题-E2-Trace与可观测性]]（本卡是它的数据模型在产品上的落地，E2 只保留指针）· [[母题-E1-评测集设计与pass^k]]（平台沉淀的 Dataset 就是它的五层数据集）· [[母题-E3-回归门禁与发布卡口]]（Dataset run 就是离线门禁的执行单位）· [[母题-E6-灰度发布与回滚]]（反馈飞轮的落地依赖本卡的保留期约束）
> **素材来源**：**两家官方文档，联网核实日期 2026-09-21**——Langfuse：Core Concepts / Self-hosting / Pricing-self-host；LangChain Docs：Observability concepts / Self-hosted LangSmith / Trace with OpenTelemetry。**字节跳动 JD「融合 JD 与能力核对表」第 3.5 节强竞争力要求**（原文：*LangSmith/Langfuse 等 AgentOps 或自建 Trace/Eval*）。**厂商自述的规模数字（月处理量、客户数、镜像拉取量）一律不采用**；**一条二手站点关于「自研列存 / 15 倍提速」的说法未核到一手文档，已剔除**。

**导读**：必懂 4 件事（① 平台卖的是一条管道，不是"更漂亮的日志" ② 两家的数据模型同构 ③ 采集必须非阻塞且先落地 ④ **Trace 会过期、Dataset 不会**）· 读完约 15 分钟 · 需要先懂：[[母题-E2-Trace与可观测性]]（Trace 与日志的分工）

**题目**：面试官问——"你们线上 Agent 的质量怎么保证？用了 LangSmith / Langfuse 这类平台吗？还是自己搭的？"

**母题**：**观测与评测这套东西，业界是怎么做成产品的——它替你做了什么、不替你做什么；如果不用，自己要付什么？**

**为什么重要**：**字节 JD 把它写进了「强竞争力要求」**（不是加分项，是明牌）。**但这类题最容易答砸在两个方向**：① **只说"我们用了 Langfuse"**——那是汇报工具，不是回答能力；② **背功能对比表**——功能表半年就变，而且面试官问的是"为什么这么设计"。**真正值钱的是三层：数据的形状（为什么都长这样）、管道的形状（为什么必须这么存）、以及责任边界（哪些事平台替不了）。**

## 一、教材

### 1. 前提：平台卖的不是"看日志"，是一条管道

::figure agentops-platform-pipeline.svg | AgentOps 平台的四段管道 | 采集 → Trace 树 → Score → Dataset，四段依次相连；E 簇的三条主线正好被拆进这四段里

【推导】**先想清楚"没有平台的时候你在做什么"**：

```text
没有平台时，你要自己回答四个问题：
  ① 一次运行发生了什么     → 需要 Trace（E2）
  ② 这次做得好不好         → 需要 Score（E1 的判分）
  ③ 怎么变成可复现的测试   → 需要 Dataset（E1 的数据集）
  ④ 改了之后有没有退化     → 需要可比的 Experiment（E3 的门禁）
```

【事实】**平台把这四段串成了一条现成管道**——**这就是它卖的东西**：

```text
采集（SDK / OTel）→ Trace 树 → Score 挂载 → Dataset + Experiment
   ↑ 平台自带          ↑ E2 证据层   ↑ E1 判定层   ↑ E1/E3 沉淀层
```

【推论】**所以"我们用了 X"这句话要翻译成"我们用它做了第几段"**——**只接了采集，就只是把日志换了个界面看**（本卡第 7 节的误解表）。

**到这里你应该能回答**：为什么说"平台 = 可观测性 + 评测"仍然是一句空话？

### 2. 数据模型：两家独立收敛到同一套形状【事实】

【事实】**先各介绍一遍，再比较**（Langfuse 与 LangSmith 是两家公司、两套命名）：

| | Langfuse | LangSmith |
|---|---|---|
| 基本单元 | **observation**（**可嵌套**）= LLM 调用 / 工具调用 / 检索步骤；**`span` 只是其中一种类型**，另有 `generation` / `event` 等 | **run**（官方原话：*you can think of a run as a span*） |
| 一次操作 | **trace** = 共享 `trace_id` 的 observation 集合 | **trace** = 共享 trace ID 的 run 集合；**单条 trace 硬上限 25,000 个 run，超过直接拒收** |
| 多轮归组 | **session** | **thread**（靠 `thread_id` 这个 metadata 键归组） |
| 另一种视图 | — | **trajectory**：把 thread **拍平**成有序消息列表（去嵌套、去重）——**看"交换了什么"，不看"怎么执行的"** |
| 组织单位 | project | project |
| 质量挂载 | **Score** | **Feedback**（一个 tag + 一个分，绑定到 run） |
| 底座 | **built on OpenTelemetry** | OTLP **双向**：能摄入，也能导出到已有观测栈 |

【推导】**用同一个指标衡量两者——"三层是否齐全"**：

```text
层级（谁调用谁）：observation / run 可嵌套   → 两家都有
边界（一次请求）：trace                       → 两家都有
归组（多轮怎么串）：session / thread          → 两家都有
```

【结论】**两家独立收敛到同一个模型，说明这不是产品口味，是问题的形状**——**这三件缺一不可**（少了层级就归因不了、少了边界就聚合不了、少了归组就看不出"用户是不是在被反复折腾"）。

【推论】**对面试的含义**：**记结构，别背命名**。被问"Langfuse 的 observation 和 span 什么关系"，答「**span 是 observation 的一种，observation 是统称、可嵌套**」就够了——**背不全类型清单不会扣分，说错"它就是 span"才会**。

**到这里你应该能回答**：为什么两家这么巧长成同一个形状？它反过来说明了什么？

### 3. 语义标准：字段名会变，所以只记语义【事实】

【事实】**两家共用的语义层是 OTel GenAI Semantic Conventions**。以 LangSmith 的 OTel 接入为例：

```text
gen_ai.system              → provider
gen_ai.prompt / completion → inputs / outputs
gen_ai.usage.input_tokens  → usage
平台自己的类型靠一个额外属性标注：
langsmith.span.kind ∈ llm / chain / tool / retriever / embedding / prompt / parser
```

【事实】**官方已把 `gen_ai.usage.prompt_tokens` / `completion_tokens` 标记为 deprecated**（改用 `input_tokens` / `output_tokens`）。

【推论】**这就是"只记语义、不背平台字段"的理由**——**你背的属性名可能在下一版就被改名了**，而「模型名 / 输入 / 输出 / token 用量 / 类型」这些**语义对象不会被改**。

**到这里你应该能回答**：为什么接入细节（端点、header、属性名）只能算【了解】层级？

### 4. 采集：非阻塞 + 先落地再入库【事实】

::figure agentops-ingest-path.svg | 写入路径：先落地，再入库 | SDK 本地缓冲 → Web 批量接收 → 立刻写 S3 → Redis 只留引用 → Worker 从 S3 取 → 写 ClickHouse

【事实】**写入路径不是「SDK → 数据库」**，而是：

```text
SDK 本地批量缓冲（后台导出器，非阻塞）
  → Web 容器批量接收 → 【立刻写进 S3 / Blob】（原始事件）
  → Redis 里只留一条【引用】（当队列用，不搬大对象）
  → Worker 从 S3 取 → 写进 ClickHouse
```

【推导】**两个理由都是可靠性，不是性能**：

```text
① 峰值不打库：队列里只有引用，突发流量不会把数据库压成超时
② 库挂了不丢事件：原始事件已经在对象存储里，可以补处理
   → 官方把这条命名为「可恢复性」（recoverability）
```

【事实】**但非阻塞有代价，官方写明了两处**：

```text
① 短命进程（脚本 / 一次性任务）必须在退出前显式 flush()
   —— 否则进程先退、缓冲没发出去
② LangSmith 的 OTLP 端点是【异步】的：收下批量就返回 200，后台再落库
   —— 如果某个子 span 的父 span 从未被导出，
      这个子 span 会在缓冲期过后被【静默丢弃、且不报错】
      （自托管缓冲窗口由 REDIS_RUNS_EXPIRY_SECONDS 控制，默认 12 小时）
```

【推论】**这条正好回答 [[母题-E2-Trace与可观测性]] 追问 5「怎么验证 Trace 本身没坏」**：**「我们有 Trace」不是靠接了 SDK 证明的，是靠「随便挑一条失败记录能 Replay 出来」证明的**——**静默丢失的定义就是"你以为记了，其实没有"**。

**到这里你应该能回答**：为什么"采集非阻塞"这个正确的设计，反过来制造了一类最难发现的故障？

### 5. 存储：按查询形状选库，不是都塞进 Postgres【推导】

【推导】**先问 Trace 的读写形状是什么**：

```text
写：高吞吐追加、基本不更新、偶尔峰值
读：按维度筛一大片 + 聚合（P95 延迟、token 总量、按 tag 分组）
    → 典型的【分析型】查询，不是按主键取单行
```

【事实】**两家给出的答案几乎一样**：

| 库 | 存什么 | 官方给的理由 |
|---|---|---|
| **ClickHouse**（OLAP） | traces / observations / scores | 宽表、**基本不可变**、**避免读时 join 与去重**——正好吃「按维度筛 + 聚合」 |
| **Postgres**（OLTP） | 项目、配置、账号、权限 | 事务型 |
| **Redis / Valkey** | 队列 + 缓存 | API Key 与 Prompt 都走读缓存，否则每次取 Prompt 都要打库 |
| **S3 / Blob** | 原始事件、多模态附件、大导出 | 大对象不进数据库；多模态文件由 SDK 直传 |

【事实】**LangSmith 自托管的组件划分几乎一样**——ClickHouse 存 traces + feedback、PostgreSQL 存事务型、Redis / Valkey 做队列与缓存、Blob 可选但生产强烈建议；服务侧另有前端（Nginx）、后端、platform 后端、queue、Playground、ACE（任意代码执行）。

【结论】**两家在"用什么库"上又一次收敛 → 这是这类系统的形状，不是某家的偏好。**

【推论】**面试里最耐用的说法**（比背某家用了什么库耐用得多）：

> **Trace 的读是分析型（大范围筛 + 聚合 + 不更新），写是高吞吐追加；所以它该落在列存上，事务库只留配置与权限——而原始事件先落对象存储，是为了让"入库"这个动作可以失败重来。**

**到这里你应该能回答**：为什么不把 trace 直接写进 Postgres？

### 6. Trace 是易失资产，Dataset 是持久资产【事实 + 推导】

::figure agentops-trace-vs-dataset.svg | Trace 会过期，Dataset 不会 | Trace 保留 180 天、到期永久删除；Dataset 无限期保留，即使源 trace 已删

【事实】**LangSmith 官方写明：SaaS 的 trace 数据自摄入起保留 180 天**，到期**永久删除**（只保留少量用量统计元数据）；**而 Dataset 无限期保留，即使源 trace 已被删除**。

【推导】**这条约束能算出人力的硬指标**——假设每天 10,000 个 run、失败率 5%（沿用 [[母题-E2-Trace与可观测性]] 第 4 节的假设，**两个都是经验量级，不是实测值**）：

```text
每天新增失败 trace = 10,000 × 5% = 500 条

如果人工复核队列每天只能处理 50 条：
  净积压 = 500 − 50 = 450 条/天
  180 天保留期内累计积压 = 450 × 180 = 81,000 条
  → 处理能力只覆盖了 10%
  → 剩下的 90% 会在【还没被任何人类看过一眼】的时候就过期删除
```

【结论】**「线上发现坏例 → 人工确认 → 沉淀为 dataset item」不是流程上的好习惯，是数据会过期带来的硬约束**。

【推论】**三条连带结论**：

```text
① 人工标注队列的处理能力必须按【失败量】定，不是按"想标多少"定
② 这也是"失败全采、成功抽样"（E2 第 4 节）在人力侧的同一条约束：
   信息密度高的才值得占人力，而它恰好也正是会被删掉的那部分
③ 平台买的就是这条管道（从线上流量到可复现数据集）的现成实现
   —— 自己拼当然也行，但 180 天从第一天上线就开始倒计时
```

**到这里你应该能回答**：为什么说"坏例要尽快沉淀"不是流程建议而是硬约束？

### 7. 责任边界：平台替不了什么【事实】

【事实】**平台是控制面，它不替代两样东西**：

```text
① 业务真值 —— 根因对不对、答案对不对，平台判不了
② 代码里的确定性安全规则 —— 越权与提示注入的红线必须由代码保证
   （[[母题-E5-越权与提示注入防护]]）
```

【事实】**还有一条与 [[母题-E3-回归门禁与发布卡口]] 一致的口径**：**LLM Judge 与专家的一致性没达到可接受水平之前，不应让它单独触发线上质量告警或发布阻断**。

【事实】**官方另有两条明确的结构要求**（违反它们，平台就退化成日志）：

```text
① LLM 调用要落成 generation（才带 token 与成本）、工具调用要落成 tool
   并挂在【正确的父节点】下
② 不要把整个 Agent 循环包成一个父 generation
   —— 那样每一步的 token 与成本全看不见，
      LLM Judge 也无法按 observation 类型定位
```

**到这里你应该能回答**："我们用了平台"之后，还有哪些事一定得团队自己做？

### 8. 选型与自建：按约束选，不按功能表选【取舍】

【事实】**两家的自建门槛不一样**（这决定"我们为什么没用它 / 用了它"怎么答）：

| | Langfuse | LangSmith |
|---|---|---|
| 许可 | **核心 MIT**；企业功能（管理 API、项目级 RBAC、保留策略、审计日志、SSO）需 license key | **自托管是 Enterprise 计划的 add-on**，需 license key |
| 自托管形态 | Docker Compose（单机试用）· K8s Helm · 各云模板 | K8s（官方给 AWS / GCP / Azure 架构指南） |
| 评测依赖 | 评测功能需外接 LLM API / Gateway | Playground 与 ACE（任意代码执行）需对应服务 |
| 网络 | **可在 VPC 内甚至完全离线部署**（官方原文：*internet access is optional*） | 见官方部署指南 |

【取舍】**选型只有三条约束，且它们不会过期**（功能表半年就变）：

```text
① 数据能不能出网 —— 最硬的一条，直接决定要不要自托管
② 已经在谁的生态里 —— LangChain / LangGraph 的自动埋点最省事
   （但"不用 LangChain 就不能用 LangSmith"是错的：两家都支持 OTLP）
③ 要不要和现有观测栈并存 —— OTLP 可同时投递到
   Langfuse / LangSmith 与 Datadog / Grafana / Jaeger
```

【推导】**自建要付什么，可以照第 5 节直接列出来**：

```text
四件存储：队列（Redis）+ 列存（ClickHouse）+ 事务库（Postgres）+ 对象存储（S3）
外加：它们之间的一致性、采集侧的非阻塞与先落地、以及短命进程的 flush
```

【结论】**但要把两件事分开**：**Trace 管道是脏活但机械（可以外包给平台或开源）**，**评测集与 grader 是判断力（必须自己长）**——**团队真正该自建的是后者**。**这也是"自建 Trace/Eval"这句话在 JD 里的真实含义**：它要的不是你会搭 ClickHouse，是**你知道在没有平台的时候该建什么**。

**到这里你应该能回答**：如果面试官问"那你们为什么不自建"，你怎么分层次回答？

### 9. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| 「上了 Langfuse / LangSmith 就有可观测性和评测了」 | **那只完成了采集**。**没有结构就没有归因**：LLM 调用要落成 `generation`、工具调用要落成 `tool` 并挂在正确的父节点下；**官方明确警告不要把整个 Agent 循环包成一个父 `generation`**——**那样每一步的 token 与成本全看不见**，LLM Judge 也无法按类型定位 |
| 「Trace 都存下来了，随时能查」 | **两个反例**：**保留期到了会删**（SaaS 180 天）；**OTLP 接入下孤儿 span 会被静默丢弃**（父 span 从未导出，子 span 到期丢弃且不报错）。**所以"有 Trace"是待验证的断言，不是接入的副产品** |
| 「用 OTel 就能无缝接」 | **路径与 ID 都有具体的坑**：`OTEL_EXPORTER_OTLP_ENDPOINT` 要填 **base URL**（如 `https://api.smith.langchain.com/otel`），**不能再拼 `/v1/traces`**（否则变成 `.../otel/v1/traces/v1/traces` 报 404）；**原生 OTLP 的 `parentSpanId` 是 8 字节而平台 run ID 是完整 UUID，跨系统续接父节点必须显式把父 UUID 写进属性**。细节属【了解】层级，**但知道"有坑"能防住"我们直接接上了"这种过度承诺** |
| 「不用 LangChain 就不能用 LangSmith」 | **错**。两家都支持 OTLP 摄入，**LangSmith 官方明确写了它不要求 LangChain**（LangChain / LangGraph 只是自动埋点最省事的那一档） |
| 「自建就是把 trace 存进数据库」 | **差得远**。自建要付的是**队列 + 列存 + 事务库 + 对象存储**四件套与它们的一致性，外加非阻塞采集与 flush。**而真正该自建的其实是评测集与 grader，不是存储** |
| 「平台能判定我们的 Agent 做得对不对」 | **不能**。平台存的是你给它的分，**业务真值不在平台职责内**（[[母题-E1-评测集设计与pass^k]] 的 grader 顺序：能确定性的不用模型 Judge） |

【取舍】**读成一句话**：**平台把 E 簇前六节做成了现成管道**——**但管道不等于结论：结构要你自己设计，真值要你自己确认，而保留期在你毫不知情的时候就已经开始倒计时。**

## 二、自测

**Q1（判读）**：下面两种"用了平台"的状态，**哪一种真的具备了归因能力？为什么？**

```text
甲：接了 SDK，Agent 的每次调用都上报，UI 里能看到完整调用链
乙：接了 SDK，且 LLM 调用落成 generation、工具调用落成 tool 并挂在下令它的那一步下
```

**A1**：**乙。**

```text
甲只完成了【采集】：数据进来了，但没有类型、没有正确的父子关系
  → 无法按 observation 类型筛选（Judge 也就无从定位）
  → 无法回答"这一步花了多少 token"
乙完成了【建模】：类型 + 结构都在
  → 可以按 generation 聚合成本、按 tool 筛异常
```

【结论】**"接上了"和"能归因"之间隔着一层建模工作**——**而这层工作平台不会替你做**。

【补充】**官方还警告了一种常见的反向错误**：**把整个 Agent 循环包成一个父 `generation`**，只记最终输出——**那样每一步的 token 与成本全被聚合掉了**，等于自己把归因能力删掉。

**Q2（设计）**：团队决定**不用平台、自建**。请列出**最少要付的五样东西**，并指出其中哪一样最容易被漏掉。

**A2**：

```text
① 列存（ClickHouse 一类）—— 承接"按维度筛 + 聚合"的分析型读
② 事务库（Postgres 一类）—— 项目、配置、权限
③ 队列 + 缓存（Redis 一类）—— 削峰，且队列里只放引用
④ 对象存储（S3 一类）—— 原始事件先落地，让"入库"可以失败重来
⑤ 非阻塞的采集 SDK —— 并且短命进程要能 flush

最容易被漏掉的是【④ + flush 的组合】：
  只做"队列 → 数据库"，数据库一抖就丢事件；
  只做非阻塞而不处理短命进程，脚本类任务会静默少数据
```

【推论】**所以"自建"的最小可用形态不是一张表，是「先落地 + 再入库」这条链**。

**Q3（计算）**：每天 10,000 个 run、失败率 5%，平台 trace 保留 **180 天**。人工复核队列**每天能处理 50 条**。

问：**保留期内会积压多少条从未被人工看过的失败 trace？**这说明什么？

**A3**：

```text
每天新增失败 trace = 10,000 × 5% = 500 条
净积压 = 500 − 50 = 450 条/天
180 天累计 = 450 × 180 = 81,000 条
处理能力覆盖率 = 50 / 500 = 10%
```

【结论】**90% 的失败 trace 会在没被任何人类看过一眼时就过期删除。**

【推论】**这说明两件事**：① **人工标注队列的容量必须按失败量倒推**，不是按"想标多少"定；② **"坏例要尽快沉淀成 dataset"是硬约束**——**因为 Trace 会过期而 Dataset 不会**。

**Q4（纠错）**：下面这段话哪里不准确？

> "我们全链路都上了 OpenTelemetry，任何平台都能无缝接上，父 span 关系自动就对了。"

**A4**：**两处不准确。**

1. **OTLP 的 span ID 与平台 run ID 不是一回事**。**原生 OTLP 的 `parentSpanId` 是 8 字节，而平台 run ID 是完整 UUID**，所以**跨系统续接父节点必须显式把父 UUID 写进属性**（如 `langsmith.span.parent_id`），**不会"自动就对"**。
2. **"无缝"忽略了异步带来的静默丢失**：**OTLP 端点收下批量就返回 200，后台再落库**；**如果父 span 从未被导出，子 span 会在缓冲期后被丢弃且不报错**（自托管缓冲窗口 `REDIS_RUNS_EXPIRY_SECONDS` 默认 12 小时）。**"接上了"之后必须验证，而不是相信。**

【准确说法】"**我们走 OTLP 接入，父节点的 UUID 是显式写进属性的**；**并且上线后会挑失败的 trace 做 Replay 反验，确认没有静默丢失。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "Langfuse 和 LangSmith 都是闭源的 SaaS，所以数据合规的场景只能自建。"

**A5**：**两处不准确。**

1. **Langfuse 核心是 MIT 许可的开源项目**，可自托管，**且官方写明可在 VPC 内甚至完全离线部署（internet access is optional）**；需要 license key 的是**企业功能**（管理 API、项目级 RBAC、保留策略、审计日志、SSO）。
2. **"只能自建"这个结论跳过了另一条路**——**LangSmith 自托管是 Enterprise 计划的 add-on**（需要 license key 与 K8s 部署）。**所以合规场景的正确判据是"数据能不能出网"，选型结论要落到"哪一家能自托管、以及自建要付什么"，而不是笼统地说"只能自建"。**

【准确说法】"**合规约束先落到『数据能不能出网』这一条**：能出网就用 SaaS；不能出网，Langfuse 有 MIT 核心可以离线自托管，LangSmith 需要 Enterprise add-on。**选型看的是约束，不是功能表——功能表半年就变。**"

## 三、面试输出（学完再看）

**一句话结论**：**平台卖的不是"更漂亮的日志"，是一条管道**——**采集（SDK / OTel）→ Trace 树 → Score → Dataset + Experiment**，正好把 E 簇三条主线做成了现成实现。**两家的数据模型独立收敛到同一套形状**（层级 / 边界 / 归组：observation 或 run 可嵌套 → trace → session 或 thread），**说明这是问题的形状而不是产品口味**——所以记结构、别背命名。**采集必须非阻塞且先落地再入库**（SDK 缓冲 → Web 批量 → **立刻写 S3** → Redis 只留引用 → Worker 落 ClickHouse），**两个理由都是可靠性：峰值不打库、库挂了不丢事件**——代价是**短命进程要 `flush()`、以及 OTLP 下孤儿 span 会被静默丢弃**，所以**"有 Trace"必须靠 Replay 反向验证**。**存储按查询形状选**：Trace 的读是分析型、写是追加型 → **列存 + 队列 + 事务库 + 对象存储**。**最关键的一条是 Trace 会过期而 Dataset 不会**（SaaS 只留 **180 天**，到期永久删除；Dataset 无限期保留）——**所以"坏例要尽快沉淀"是硬约束，人工标注队列的容量必须按失败量倒推**（每天 500 条失败、每天只能看 50 条时，**90% 会在没人看过之前就过期**）。**最后，平台是控制面**：**业务真值与代码里的安全红线它都替不了**，**Judge 与专家一致性没达标前不能单独触发发布阻断**；**选型只看三条不会过期的约束——数据能不能出网、在谁的生态里、要不要和现有观测栈并存。**

**恢复关键词**：**管道四段**（采集 → Trace → Score → Dataset）/ **三层同构**（层级 · 边界 · 归组；记结构不背命名）/ **LangSmith 单 trace 上限 25,000 run** / **OTel GenAI SemConv 是公共语义层**（字段名会变）/ **先落地再入库**（S3 → Redis 引用 → ClickHouse；可恢复性）/ **短命进程 flush · 孤儿 span 静默丢弃** / **列存吃分析型读** / **Trace 易失 180 天 · Dataset 持久** / **标注队列容量按失败量倒推**（500 vs 50 → 90% 过期）/ **平台替不了真值与安全红线** / **选型三约束**（出网 · 生态 · 并存）

**核心不变量 / 主线**：
**平台把"怎么证明它变好了"这件事做成了管道，但管道不等于结论。**
三件事永远在你这边：**结构**（类型与父子关系要建模）、**真值**（对不对由你确认）、**时间**（保留期从第一天就在倒计时）。

**完整回答骨架**：先答"我们做了第几段"（不是"用了哪家"）→ **数据模型三层（同构，说明是问题形状）** → **采集先落地再入库 + 静默丢失的坑** → **存储按查询形状选库** → **Trace 会过期、Dataset 不会（给算式）** → **责任边界（真值 / 红线 / Judge 不单独阻断）** → 收束到"选型看约束不看功能表"

**完整回答（口述稿）**：
**平台卖的不是"更漂亮的日志"，是一条管道**：**采集（SDK / OTel）→ Trace 树 → Score → Dataset + Experiment**，正好把 E 簇三条主线做成了现成实现。

两家的数据模型**独立收敛到同一套形状**（层级 / 边界 / 归组：Langfuse 的 observation 可嵌套 → trace → session；LangSmith 的 run → trace → thread，且多一个 trajectory 视图）——**说明这是问题的形状而不是产品口味：记结构、别背命名**。硬数字：LangSmith 单条 trace 上限 **25,000 个 run**，超过拒收。

**采集必须非阻塞且先落地再入库**（SDK 缓冲 → Web 批量 → **立刻写对象存储** → 队列只放引用 → Worker 落分析库），两个理由都是可靠性：**峰值不打库、库挂了不丢事件**；代价是**短命进程要 `flush()`**，以及 **OTLP 下孤儿 span 会被静默丢弃**，所以"有 Trace"必须靠 **Replay 反向验证**。

自建要付三笔：采集链路的可靠性、存储按查询形状选（Trace 读是分析型、写是追加型）、Score/Dataset/Experiment 三套自己搭。**选型看约束不看功能表**：数据要不要留在自己机房、能接受多长采集延迟、trace 上限与保留期、是否自托管。

**分层要点**：
- **结论**：平台 = 采集 → Trace → Score → Dataset+Experiment 的管道；两家的模型同构。
- **推导链**：为什么采集要异步落盘 → 两类丢失（缓冲未刷 / 孤儿 span）→ 用 Replay 反验 → 自建三笔成本 → 选型看约束。
- **量化**：LangSmith 单条 trace 上限 25,000 个 run；孤儿 span 自托管窗口默认 12 小时。
- **边界与常见误解**：同步写库会把观测延迟加进业务请求延迟，且峰值打爆数据库；功能表谁都能勾选，差别在机房/延迟/上限/自托管这些约束上。

**追问**（先说后看）

1. **Langfuse 和 LangSmith 的数据模型有什么差别？** —— **命名不同、结构同构**。**Langfuse：observation（可嵌套，`span` 只是其中一种）/ trace / session**；**LangSmith：run（= span）/ trace / thread**，**且多一个 trajectory 视图**（把 thread 拍平成有序消息列表）。**差别值得提的硬数字：LangSmith 单条 trace 上限 25,000 个 run，超过拒收。**
2. **Trace 的采集为什么不能同步写库？** —— **同步写会把观测的延迟加进业务请求的延迟里**，而且**峰值会打爆数据库**。正确做法是**本地批量缓冲 + 后台导出**，**服务端收到后先写对象存储、队列里只放引用**，让"入库"这个动作可以失败重来。**代价是短命进程必须 `flush()`。**
3. **怎么确认没有丢 trace？** —— **两类丢失**：① **缓冲未刷**（短命进程 / 进程被杀）② **孤儿 span**（父 span 从未导出 → 子 span 到期静默丢弃，自托管窗口 `REDIS_RUNS_EXPIRY_SECONDS` 默认 12 小时）。**验证手段是 Replay**：**挑一条失败的 trace，看能不能复现出当时的行为**（[[母题-E3-回归门禁与发布卡口]]）。
4. **为什么不适合把 trace 放进 Postgres？** —— **读的形状不匹配**：trace 的读是**大范围筛 + 聚合 + 基本不更新**，属于分析型；**列存宽表 + 避免读时 join** 才吃得下。**事务库留给项目、配置与权限。**（这是两家都这么选的理由，不是某家的偏好。）
5. **为什么选 Langfuse / LangSmith？** —— **按约束选**：① **数据能不能出网**（Langfuse 核心 MIT、可离线自托管；LangSmith 自托管是 Enterprise add-on）② **在谁的生态里**（LangChain / LangGraph 自动埋点最省事，**但不用 LangChain 也能用 LangSmith**）③ **要不要和现有观测栈并存**（OTLP 可同时投递）。**功能表半年就变，约束不会变。**
6. **不用平台、自建要付什么？** —— **队列 + 列存 + 事务库 + 对象存储**四件套与它们的一致性，外加**非阻塞采集与 flush**。**但真正该自建的是评测集与 grader**（判断力），**不是存储**（脏活但机械）。

**同类变体**

- 「你们项目里是怎么做可观测的？」——**别报工具名，报"做到第几段"**：**有没有 Trace 结构、有没有 Score、坏例有没有沉淀成 Dataset、改动有没有可比的 Experiment**。**四段里缺哪段，就老实说缺哪段——这比"我们用了平台"有信息量得多。**
- 「Agent 的可观测性和微服务的可观测性有什么不同？」——**多三层语义**（模型调用的 token 与版本、检索的候选与分数、人工审批）**外加一件事：非确定性**——**同一输入两次运行的 Trace 不同**，所以**对比两条 Trace 时要知道"差异可能是采样噪声，也可能是真的退化"**（[[母题-E1-评测集设计与pass^k]] 的 pass^k 就是这个问题的度量）。
- 「自建 Trace/Eval 该从哪一步开始？」——**反过来做**：**先建评测集与 grader（判断力，没有替代品），再考虑要不要自建存储（脏活，能外包就外包）**。**顺序反了会出现"有漂亮的 trace 界面、但没有任何一条可复现的测试"。**
