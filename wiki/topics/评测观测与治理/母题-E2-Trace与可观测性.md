**题目**：面试官问——"线上出了个 Bad Case，你怎么定位？Trace 和日志有什么区别？"

**母题**：**一次运行到底发生了什么——为什么"打日志"不够，必须要有 Trace？而 Trace 里最少要有什么？**

**为什么重要**：这是**"能迭代"和"只能重来"的分界线**。**没有 Trace 的团队，每次 Bad Case 都只能靠猜**——而 [[母题-G5-RAG评测与幻觉率]] 里那条三岔路归因（没捞到 / 没进上下文 / 生成错）**需要 Trace 把候选、分数、重排位置、上下文版本都留下来**。**这道题也是"你是不是真的上过线"的直接证据。**

## 一、教材

### 1. 前提：Trace 是树，日志是线

::figure trace-vs-log.svg | Trace 是一棵树，日志是一条线 | 日志是独立时间戳，因果要靠人猜；Trace 有父子关系，能直接看出谁调用谁、哪步慢、哪步失败

【推导】**两者的本质差别在"有没有结构"**：

```text
日志：一条条独立的记录，彼此之间【没有结构关系】
  → 要还原因果，只能靠人对着时间戳猜
  → 跨服务时更糟：三个服务的日志混在一起

Trace：一棵树，每个节点（span）有【父子关系】
  → 直接能看出"谁调用了谁"
  → 能定位"哪一步慢"、"哪一步失败"
```

【推论】**这不是"Trace 更高级"，是"它们回答的问题不同"**：

| 信号 | 回答什么 | 典型用途 |
|---|---|---|
| **指标（Metrics）** | **分布与趋势** | "P95 涨了吗""错误率多少" |
| **日志（Logs）** | **细节与原文** | "它当时具体打印了什么" |
| **Trace** | **因果与归因** | "**是哪一步导致的**" |

【推论】**面试里最容易答错的地方**：**把三者混着说**（"我们打了很详细的日志所以能定位"）。**正确的说法是：指标告诉你"有问题"，Trace 告诉你"问题在哪一步"，日志告诉你"那一步具体发生了什么"。**

**到这里你应该能回答**：为什么"我们日志打得很全"仍然可能定位不了 Agent 的失败？

### 2. Trace 的数据模型【事实】

【事实】study/07 给的**最低结构**：

```text
Request Trace
 └─ Agent Run Span
     ├─ Model Span      → Tokens / Version / Latency
     ├─ Retrieval Span  → Query / Candidates / Index Version
     ├─ Tool Span
     └─ Approval Span
```

【事实】**Langfuse 的模型更细一层**（2026-09 核实）：

```text
Observations = 单个步骤（LLM 调用 / 工具调用 / 检索步骤），【可以嵌套】
Trace        = 容器；trace 级属性（user_id / session_id / tags / metadata）
               存在于【每一条 observation】上（SDK 自动传播）
Session      = 把属于同一次用户交互的多个 trace 归组
```

【推论】**"trace 级属性冗余到每一行"这个设计值得注意**：

```text
存储上是【反范式】的（每条 observation 都带一份 trace 属性）
但查询与聚合因此很快 —— 不需要 join

这是一个典型的「写入换读取」的取舍，在可观测性场景里几乎总是值得
（因为【读】的频率远高于【写】，而且读常常是在排障时）
```

【事实】**一个 Step 应该记录什么**（[[母题-A4-长任务状态与Checkpoint]] 给过 schema）：**版本（model / prompt / tool / rule）、Artifact 引用、幂等键、latency、token 用量、错误码**。

【推论】**那三组字段在 Trace 里同样是必需的**——**因为 Trace 的主要用途就是"复现"和"归因"，而少了版本就复现不出来**（[[母题-C3-Prompt版本管理与回归]] 的"四者必须一起绑定到结果上"）。

**到这里你应该能回答**：为什么"Trace 里只记了输入输出"是远远不够的？

### 3. 存储成本：span 粒度决定量级【推导】

```text
假设一次 run 有 50 个 span、每个 span 记约 2 KB（**两个都是经验量级假设，不是实测值**）
  单次 run：50 × 2 KB = 100 KB
  每天 10,000 run：100 KB × 10,000 ≈ 1 GB / 天
  一年 ≈ 365 GB

如果只记【关键 span】（模型调用 + 工具调用 + 检索，不记内部函数调用）：
  假设 15 个 span → 30 KB / run → 300 MB / 天 → 一年 ≈ 110 GB
```

【结论】**span 粒度直接决定存储量级**——50 个和 15 个，一年差 **3.3 倍**。

【取舍】**所以"记什么粒度"要有判据**，不能"能记的都记"：

```text
值得记：模型调用、工具调用、检索、审批、外部 HTTP、状态转移
不必记：内部函数、循环体、纯计算的中间步骤（重做代价低）
```

【推论】**这个判据和 [[母题-A4-长任务状态与Checkpoint]] 的"checkpoint 时机"是同一个**：**记"有业务意义或副作用"的那一步**，其余靠重做。

**到这里你应该能回答**：为什么"能把所有调用都 trace 下来"这件事，反而需要克制？

### 4. 采样：失败全采，成功抽样【启发式】

【性质】**先标性质**：这是**通行的工程启发式，不是任何平台的规定值**——没有一份官方文档规定采样必须这么做。它的依据是「**失败样本的信息密度远高于成功样本**」（稀缺不等于重要）。

【推导】**全采存储扛不住时，直觉是"按比例采样"**——**但那会把最需要的证据丢掉**：

```text
随机采样 10%：
  失败样本也只有 10% 被留下
  → 100 个失败里只有 10 个能归因
  → 而且失败往往发生在【长尾】上，随机采样正好把它采没
```

【推导】**正确策略是"按结果分层采样"**：

```text
失败率 5%，存储量按全采的 1 GB/天 算：

失败全采 + 成功抽样 5%：
  = 5% × 100% + 95% × 5%
  = 0.05 + 0.0475
  = 0.0975 → 约 97.5 MB / 天

降到约 1/10，而【全部失败样本都留下来了】
```

【结论】**"失败全采、成功抽样"能在保留全部归因能力的前提下，把存储降到约十分之一。**

【推论】**反过来做（成功全采、失败抽样）是最贵也最容易被忽略的错**——**它恰好把最需要的那部分证据丢掉**。

【事实】**还有一类必须全采的**：**安全相关的事件**（越权尝试、未确认的副作用）——**它们不能靠采样，因为一次就够出事**（[[母题-E5-越权与提示注入防护]]）。

**到这里你应该能回答**：为什么"随机采样 10%"这个看起来很中立的做法，在排障场景下是错的？

### 5. 判分对象：轨迹还是结果【事实】

【事实】**Anthropic 那篇 evals 文章的一个关键区分**：

```text
grade the transcript（轨迹） vs grade the outcome（结果）
```

【推导】**两者的适用场景不同**：

```text
结果判分（outcome）：
  ✓ 确定性强（测试过没过、SQL 跑没跑通）
  ✓ 与用户价值直接对应
  ✗ 只告诉你"成没成"，不告诉你"为什么"

轨迹判分（transcript）：
  ✓ 能诊断"它是不是用了危险的工具""它是不是绕了远路"
  ✓ 能发现"结果对了但过程有问题"的情况
  ✗ 判分本身更难、更容易有偏
```

【事实】**原文对编码 Agent 的建议很具体**：

> **"Once you have a set of pass-or-fail tests for validating the key outcomes of a coding task, it's often useful to also grade the transcript. For instance, heuristics-based code quality rules can evaluate the generated code based on more than passing tests, and model-based graders with clear rubrics can assess behaviors like how the agent calls tools or interacts with the user."**

【推论】**先有结果判分，再补轨迹判分**——**顺序不能反**。**因为结果判分是"底线"，轨迹判分是"体检"。**

【推论】**而轨迹判分依赖 Trace**：**如果没有 Trace，"它绕了远路"这种问题根本无从发现**——**你只能看到"最后成功了"，看不到它花了 40 步做了本该 5 步做完的事。**

**到这里你应该能回答**：为什么"任务成功了"不代表"这次运行是好的"？

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "我们日志打得很详细，能定位问题" | **日志回答"发生了什么"，Trace 回答"谁导致了谁"**。**跨步、跨服务的因果链，靠日志只能人工对着时间戳猜**（差一个数量级的排查效率）。**指标告诉你"有问题"、Trace 告诉你"在哪一步"、日志告诉你"那步具体是什么"——三者分工不同** |
| "Trace 里记下输入输出就够了" | **不够**。必须带**版本**（model / prompt / tool / rule）、**Artifact 引用**、**幂等键**——**少了版本就复现不出来**（[[母题-A4-长任务状态与Checkpoint]] 的三组必需字段）。 |
| "能记的都记下来最保险" | **存储会失控**（50 span × 2KB × 1 万 run = 1 GB/天 = 365 GB/年）。**要按"有业务意义或有副作用"筛粒度**——和 checkpoint 的判据一致 |
| "扛不住就随机采样 10%" | **会把最需要的证据丢掉**：失败样本只剩 10%，**而失败往往发生在长尾上**。**正确做法是"失败全采 + 成功抽样"**——**存储降到约 1/10，而全部失败样本都留下**（5% + 95%×5% = 9.75%） |
| "任务成功了就说明这次运行没问题" | **不一定**。要**同时判轨迹**——它可能**用了危险的工具、绕了远路、或者对用户说了不该说的**。**前提是你有 Trace**；**没有 Trace 时，"绕远路"这类问题根本不可见** |
| "Trace 就是更详细的日志" | **不是同一个东西**。**日志是"事件流"，Trace 是"调用树"**——**树有父子关系，所以能算"这一步占了多少时间""这一步的失败是谁引起的"**；日志算不出来 |
| "安全事件也可以采样" | **不能**。**一次就够出事**——**越权尝试、未确认的副作用必须全采**（[[母题-E5-越权与提示注入防护]]） |

【取舍】读成一句话：**可观测性的目标不是"记录得多"，是"出事时能定位到具体哪一步"——所以既有"记什么粒度"的取舍，也有"留哪些样本"的取舍。**

## 二、自测

**Q1（判读）**：下面两种记录方式，**哪一种能在跨服务的故障里定位到根因？为什么？**

```text
方式 A：三个服务各自打印带时间戳的日志
方式 B：一次请求生成一棵 Trace，三个服务作为同一棵树上的 span
```

**A1**：**方式 B。**

```text
方式 A（日志）：
  三个服务各有自己的一份日志
  时间戳可能有偏移（机器时钟不完全同步）
  一次请求在日志里【没有共同的标识】
  → 要还原因果，只能人工按时间戳拼接
  → 而且"谁调用了谁"是推出来的，不是记录下来的

方式 B（Trace）：
  同一次请求有一个 trace_id，各服务的 span 挂在同一棵树上
  父子关系是【记录下来的事实】，不需要推断
  → 直接能看出"哪一步慢""哪一步失败""谁调用的谁"
```

【结论】**差别不在"信息量"，在"因果是不是被记录下来的"。**

【补充】**这解释了为什么 Trace 在 Agent 场景特别重要**：**Agent 天然是多步的**（模型 → 工具 → 模型 → 工具），**步数多、每步都可能失败**——**用日志拼接因果关系，成本随步数急剧上升。**

**Q2（计算）**：某系统每天 **10,000** 个 run，每个 run 约 **50 个 span**、每 span **2 KB**。

问：**全量 Trace 的日存储和年存储各是多少？**如果只记关键 span（约 15 个），降到多少？

**A2**：

```text
全量（50 span）：
  单 run = 50 × 2 KB = 100 KB
  每天   = 100 KB × 10,000 = 1 GB
  一年   ≈ 365 GB

只记关键 span（15 个）：
  单 run = 15 × 2 KB = 30 KB
  每天   = 300 MB
  一年   ≈ 110 GB

降到约 30%
```

【结论】**span 粒度直接决定存储量级**。

【取舍】**判据和 checkpoint 一致**：

```text
值得记：模型调用 · 工具调用 · 检索 · 审批 · 外部 HTTP · 状态转移
不必记：内部函数 · 循环体 · 纯计算的中间步骤（重做代价低）
```

**Q3（计算）**：某系统的失败率是 **5%**。全量 Trace 的存储是 **1 GB/天**。

问：**"失败全采 + 成功抽样 5%"这个策略下，日存储是多少？**为什么这个策略比"随机采样 10%"更好？

**A3**：

```text
失败全采 + 成功抽样 5%：
  = 5% × 100% + 95% × 5%
  = 0.05 + 0.0475
  = 0.0975

日存储 = 1 GB × 0.0975 ≈ 97.5 MB / 天
```

【结论】**存储降到约 1/10，而全部失败样本都留下来了。**

【为什么比"随机采样 10%"好】：

```text
随机采样 10%：
  失败样本也只剩 10% —— 100 个失败里只有 10 个能归因
  而且失败往往发生在【长尾】上，随机采样正好把它采没

失败全采 + 成功抽样 5%：
  归因能力【完全保留】（所有失败都能查）
  代价只是"成功的样本少了一些"——而成功的样本本来就不需要逐个分析
```

【推论】**这个策略的本质是"按信息价值采样"**：**一次成功的 run 里，绝大多数信息是冗余的；而一次失败的 run，每一步都可能是根因。**

【补充】**还有一类必须全采：安全事件**（越权尝试、未确认的副作用）——**不能靠采样，因为一次就够出事。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们的日志打得很全，每一步都打印了，Bad Case 都能查。"

**A4**：三处问题。

1. **日志回答"发生了什么"，不回答"谁导致了谁"**。**Agent 是多步系统**，**用日志拼接因果关系要靠人对着时间戳推**——**步数一多，成本急剧上升**。
2. **缺版本信息就复现不了**。**日志里如果没有 model / prompt / tool 的版本，就无法 Replay**（[[母题-C3-Prompt版本管理与回归]]）。**这也是为什么 Step 记录必须带版本字段。**
3. **"每一步都打印"和"有结构"是两件事**。**日志多不等于可归因**——**关键是"因果链有没有被记录下来"，而不是"记录了多少行"。**

【准确说法】"**三类信号分工不同**：**指标看分布与趋势、Trace 看因果与归因、日志看细节与原文**。**Trace 里最少要有：run / span 的父子关系 + 版本 + 延迟 + 错误码 + Artifact 引用 + 幂等键。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "任务跑成功了就说明这次 Agent 运行没问题，不用再细看过程。"

**A5**：三处问题。

1. **"结果对"不等于"过程对"**。它可能**用了危险的工具、绕了远路、或者对用户说了不该说的**——**这些只有轨迹判分才能发现**（Anthropic 那篇 evals 文章明确建议"**先有结果判分，再补轨迹判分**"）。
2. **"绕远路"这类问题在成本上很真实**：**一次本该 5 步做完的任务花了 40 步**，结果可能照样正确，**步数是 8 倍**（40 ÷ 5）；而按 [[母题-A1-计划执行循环与停止条件]] 的**平方累计**口径（每步都要把历史重发一遍），**累计输入 token 会涨到约 55 倍**（n(n+1)/2 之比：40×41 ÷ 5×6 = 1640 ÷ 30 ≈ 55）。
3. **前提是你有 Trace**。**没有 Trace 时，"它绕了远路"这件事根本不可见**——**你只能看到"最后成功了"。**

【准确说法】"**结果判分是底线，轨迹判分是体检**。**先保证结果，再看过程**——**而看过程的前提是 Trace 把每一步都留下来了。**"

## 三、面试输出（学完再看）

**一句话结论**：**Trace 是树，日志是线**——**日志回答"发生了什么"，Trace 回答"谁导致了谁"**。三类信号分工不同：**指标看分布与趋势、Trace 看因果与归因、日志看细节与原文**；**跨步、跨服务的因果链，靠日志只能人工对着时间戳猜**，而 **Agent 天然多步，这个成本随步数急剧上升**。**Trace 的数据模型**是 `Request → Run → Model / Retrieval / Tool / Approval Span`，**每个 span 必须带**：**版本（model / prompt / tool / rule）、Artifact 引用、幂等键、latency、token 用量、错误码**——**少了版本就复现不出来**（和 [[母题-A4-长任务状态与Checkpoint]] 的 Step 记录是同一套字段）。**存储要控**：50 span × 2 KB × 1 万 run = **1 GB/天 = 365 GB/年**，所以**只记"有业务意义或有副作用"的 span**（15 个 → 一年约 110 GB）。**采样要按信息价值**：**失败的**全采**、成功的抽样**（失败率 5% 时 = 5% + 95%×5% = **9.75%**，**存储降到约 1/10 而归因能力完全保留**）——**"随机采样 10%"会把最需要的长尾失败采没**。最后，**判分要分结果和轨迹**：**先有结果判分（底线），再补轨迹判分（体检）**——**因为"结果对了但过程有问题"（绕远路、用了危险工具）只有轨迹能发现**。 **而「业界是怎么把它做成产品的」单独成卡**——见 [[母题-E7-AgentOps平台与自建Trace-Eval]]：**管道四段 · 三层同构 · 先落地再入库 · Trace 易失而 Dataset 持久**（字节 JD 把它列为强竞争力要求）。

**核心不变量 / 主线**：
**可观测性的目标不是"记录得多"，是"出事时能定位到具体哪一步"。**
所以它有两个取舍，而不是一个：**记什么粒度**（按"有业务意义"筛）、**留哪些样本**（按"信息价值"筛）——**两个都做错，记录再全也定位不了。**

**完整回答骨架**：先破"日志够用"（树 vs 线）→ 三信号分工 → **Trace 数据模型与必需字段** → 存储算式与粒度判据 → **采样策略（失败全采）** → **grade outcome vs grade transcript** → 收束到"能定位到哪一步"

**完整回答（口述稿）**：
**Trace 是树，日志是线**：**日志回答"发生了什么"，Trace 回答"谁导致了谁"**。三类信号分工——**指标看分布与趋势、Trace 看因果与归因、日志看细节与原文**；跨步、跨服务的因果链靠日志只能人工对着时间戳猜，而 **Agent 天然多步，这个成本随步数急剧上升**。

数据模型是 `Request → Run → Model / Retrieval / Tool / Approval Span`。每个 span 必须带：**版本（model / prompt / tool / rule）、Artifact 引用、幂等键、latency、token 用量、错误码**——**少了版本就复现不出来**（和 Agent 侧 Step 记录是同一套字段）。检索 span 还要带 query / candidates / 索引版本。

存储要控：50 span × 2 KB × 1 万 run = **约 1 GB/天**。手段三条：**控制粒度**（只记有业务意义或有副作用的 span）、**按信息价值采样**（失败全采 + 成功抽样）、**分级存储**（近期全量、历史聚合或采样）。

怎么用：**按三岔路定位 RAG 答错**——① 正确证据进 TopK 了吗（召回）；② 进最终 Context 了吗（重排/预算/去重）；③ 都进了还是错（生成/Prompt/引用）。**前提是 Trace 把这些都留下来了，否则只能猜。**

**分层要点**：
- **结论**：Trace 是调用树（因果），日志是事件流（细节）；span 必须带版本、Artifact 引用、幂等键。
- **推导链**：树有父子 → 能算"这一步占多少时间/失败是谁引起" → 采集字段 → 存不下就控粒度+采样+分级 → 三岔路归因。
- **量化**：50 span × 2 KB × 1 万 run ≈ 1 GB/天；采样策略是失败全采 + 成功抽样。
- **边界与常见误解**：Trace 与日志互补不是替代；采集必须非阻塞、先落地再入库（短命进程要 `flush()`，OTLP 下孤儿 span 会被静默丢弃），"有 Trace"要靠 Replay 反向验证。

**追问**（先说后看）

1. **Trace 和日志有什么区别？** —— **日志是事件流，Trace 是调用树**。**树有父子关系，所以能算"这一步占多少时间""这一步的失败是谁引起的"**——日志算不出来。**两者互补，不是替代关系**（细节还是要看日志）。
2. **Trace 里最少要有哪些字段？** —— **层级**（trace / run / span 的父子关系 + `trace_id`）；**每个 span**：类型、开始结束时间、**版本**（model / prompt / tool）、**Artifact 引用**、**幂等键**、token 用量、错误码。**检索 span 还要带 query / candidates / 索引版本**（[[母题-G5-RAG评测与幻觉率]] 的三岔路归因需要它）。
3. **怎么定位一个 RAG Agent 答错？** —— **按三岔路走**：① 正确证据进 TopK 了吗（没进 → 召回问题）② 进最终 Context 了吗（没进 → 重排 / 预算 / 去重）③ 都进了还是错（→ 生成 / Prompt / 引用）。**前提是 Trace 把这些都留下来了**——**否则只能猜**。
4. **Trace 存不下怎么办？** —— **① 控制粒度**（只记有业务意义或有副作用的 span）② **按信息价值采样**（失败全采 + 成功抽样）③ **分级存储**（近期的全量、历史的聚合或降采样）。**但安全事件永远全采。**
5. **怎么验证 Trace 本身没坏？** —— **用 Replay 反向验**：**随便挑一条失败的 Trace，看能不能从它复现出当时的行为**（[[母题-E3-回归门禁与发布卡口]] 的 Mock replay）。**复现不出来，说明 Trace 缺字段。**

**同类变体**

- 「Agent 的可观测性和微服务的可观测性有什么不同？」——**多了三层语义**：**模型调用（token / 版本 / 工具选择）、检索（候选与分数）、审批（人工介入）**。**而且多了一个传统后端没有的东西：`非确定性`**——**同一输入两次运行的 Trace 不同**，所以**对比两条 Trace 时要知道"差异可能是采样噪声，也可能是真的退化"**（[[母题-E1-评测集设计与pass^k]] 的 pass^k 就是这个问题的度量）。
- 「Session 和 Trace 是什么关系？」——**一次用户交互可能产生多个 trace**（用户追问、重试、换方案），**Session 把它们归组**。**这对"多轮对话的评测"很关键**——**单看一个 trace 看不出"用户是不是在被反复折腾"。**
