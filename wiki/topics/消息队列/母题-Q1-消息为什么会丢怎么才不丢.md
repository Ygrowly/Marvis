## 一、教材

### 1. 前提：MQ 先在回答"为什么值得引入"，再回答"怎么不丢"

#### 1.1 引入 MQ 换到什么【权衡】

引入消息队列是为了三件事：

| 作用 | 在解决什么 | 例子 |
|---|---|---|
| **解耦** | 上游不必知道下游有几个、是谁 | 下单成功后要通知库存 / 积分 / 短信，新增一个下游不用改订单代码 |
| **异步** | 把"用户必须等"的部分缩到最小 | 主流程 50ms 返回，发短信加积分在后台做 |
| **削峰** | 把瞬时洪峰摊平到下游的处理能力上 | 秒杀 10 万请求先进队列，后端按每秒 2000 匀速消费 |

**但它立刻带来三笔代价**（这三笔必须主动说，否则面试官会认为你只看了好处）：

1. **可用性下降**：原来 A 直接调 B，现在中间多一个组件，**MQ 挂了整条链路就断了**——所以不得不做高可用集群
2. **复杂度上升**：一个方法调用变成消息之后，发重了、丢了、消费失败了、顺序乱了，全都变成你要处理的问题
3. **一致性变难**：本地事务成功了但消息没发出去（或反之），两个系统就脱节了

> 【取舍】**所以"要不要上 MQ"不是技术偏好，是算账**。`projects/EnergyOps` 就是一本活教材：当前规模（约 604 台设备）**明确不上 MQ**，用 PostgreSQL 任务表 + APScheduler 就够，只在表计到万级、单机跑不完窗口时才考虑引入。

#### 1.2 本卡真正的核心前提：跨进程通信没有"恰好一次"

【事实】所有主流 MQ 都只承诺 **至少一次（at-least-once）** 投递。原因很硬：

```
进程可能在任何一条指令后崩溃，而"处理消息"和"记录处理进度"是两次独立操作
→ 崩溃点落在两次操作之间时，两件事必有一件没做成
  崩在"记录进度"之前 → 消息会被重投（重复）
  崩在"处理消息"之前但进度已记 → 消息不会再来（丢失）
```

**要同时杜绝两者，就得让"处理"和"记录进度"变成一个原子操作——那需要 MQ 和你的业务数据库做分布式事务，代价高到没人愿意付。**

【取舍】于是业界的一致选择是：**框架保证"至少一次、宁重勿丢"，把去重的责任交给业务层**（这正是 [[母题-Q2-重复与乱序]] 的全部内容）。**所以本卡"不丢"的目标是"已确认的消息绝不丢"，而不是"绝不重复"。**

**到这里你应该能回答**：为什么"加个 MQ 就保证不丢不重"这个说法从根上就不成立？

### 2. 三段接力：一条消息的一生

::figure mq-delivery-chain.svg | 消息的三段接力与每段的确认机制 | 发送 / 存储 / 消费各有一道确认与一个"不确认会怎样"；右侧是对应可调项

【推导】**"消息会丢"只能发生在三个位置，没有第四个**：

| 段 | 消息在哪 | 会怎么丢 | 靠什么兜住 |
|---|---|---|---|
| **① 发送** | 还在生产者内存/网络里 | 发出去了但 Broker 没收到，生产者以为成功 | **生产端确认**（Broker 回 ack 才算成功） |
| **② 存储** | 在 Broker 的页缓存里 | Broker 进程/机器挂了，内存里的消息没了 | **持久化 + 多副本** |
| **③ 消费** | 已投给消费者但没处理完 | 消费者提前确认，然后自己崩了 | **消费端确认**（处理完再 ack） |

**记法：三段各有一道确认（生产确认 / 副本确认 / 消费确认），少一道就有一个漏口。**

#### 2.1 第一段：发送——"Broker 说收到了才算收到"【事实】

**确认（ack）** 指的是 Broker 在什么条件下告诉生产者"这条我收下了"。以 Kafka 的 `acks` 为例，三个档位是递进的：

| 档位 | Broker 何时回 ack | 什么时候会丢 |
|---|---|---|
| `acks=0` | **不回**，发出去就当成功 | Broker 没收到/挂了，你完全不知道 |
| `acks=1` | **Leader 写进自己的本地日志**就回 | Leader 刚回完 ack 就宕机，而 Follower 还没同步 |
| `acks=all`（=−1） | **所有在 ISR 里的副本都收到了**才回 | 只要 ISR 里还剩一个活着，就不丢 |

【纠错】**这里有一个流传极广的错说法**：`acks=all` 常被讲成"所有副本都收到"。**官方 Design 文档明确写的是"当前所有 in-sync replica 都收到"**——如果一个 Topic 配了 2 副本、其中 1 个已经挂了（ISR 只剩 1 个），**`acks=all` 的写依然会成功**，这时如果剩下的那个再挂，这条消息就丢了。

**所以 `acks=all` 单独用是不够的**，它必须配一个"最少几个副本才算数"的门槛——这就是 `min.insync.replicas` 的用途（下一节量化）。

【事实】还有一个反直觉的点：**Kafka 3.0 起 `acks` 的默认值已经是 `all`**（因为幂等生产者默认开启，而幂等要求 `acks=all`）；老版本默认是 `1`。所以"默认 acks=1、要改成 all"这个说法**在现在的 Kafka 上已经过期了**，但很多资料还在讲。

#### 2.2 第二段：存储——有两种"落盘"，别混为一谈【事实】

Broker 侧要扛住的是"进程/机器挂了，内存里的消息没了"。两个手段：

**（a）持久化**：把消息写到磁盘，重启后能从磁盘恢复。代价是写磁盘比写内存慢，所以是否开启、什么时候刷盘，是可配的取舍。

**（b）多副本**：同一条消息存在多台 Broker 上，一台挂了还有别的。上面的 `acks` / `min.insync.replicas` / `replication.factor` 全是在调这一项。

**RabbitMQ 的持久化要特别注意：它是两个开关，不是一个。** 这是高频追问点：

| 开关 | 存的是什么 | 不设会怎样 |
|---|---|---|
| **队列持久化**（`durable=true`） | 队列的**元数据**（名字、绑定、参数） | 重启后**队列整个消失**，消息想恢复也没有容器装 |
| **消息持久化**（`deliveryMode=persistent`） | 队列里**每条消息的内容** | 重启后**队列还在但里面是空的** |

【推导】**两者必须同时设置**：一个是"容器"，一个是"内容"。但即使都设了也不是 100% 安全——消息先写进操作系统的页缓存，再由内核异步刷盘，**这个窗口里断电仍然会丢**。要做到极致可靠，得配合发布者确认（publisher confirm），即 **Broker 确认已经真正落盘/复制成功后才回 ack 给生产者**。

#### 2.3 第三段：消费——ack 的时机是唯一要紧的事【推导】

**核心原则一句话：处理完业务逻辑之后才 ack，绝不能收到就 ack。**

理由用反证最清楚：收到就 ack，等于告诉 Broker"这条我负责了"，而你的业务代码还没跑。**这时候你崩了，Broker 认为消息已经处理完毕，不会重投——消息就永久丢了**，而且**没有任何地方会报警**，因为从系统视角看一切正常。

【事实】各家的 ack 形态不同，但语义相同：

- **Kafka**：提交 offset（"我已经消费到第 N 条了"）。消费者自己拉、自己记进度。
- **RabbitMQ / RocketMQ**：单据签收。消费者对**每条消息**明确回"成功"或"稍后重试"（`CONSUME_SUCCESS` / `RECONSUME_LATER`），返回失败的消息自动进重试队列。

**消费反复失败怎么办**——这是"不丢"的最后一道兜底，三档递进：

```
第一次失败 → 等一会儿重试（可能是临时网络抖动）
重试若干次仍失败 → 进重试队列（RocketMQ 并发消费默认最多 16 次，随后进死信队列）
再失败 → 进死信队列，人工/告警兜底（绝不静默丢弃）
```

**到这里你应该能回答**：如果只让你改一处代码来防丢消息，你改哪里？为什么？

### 3. 量化：把确认加严到哪一档算出来

#### 3.1 先定义两个量【事实】

- **`replication.factor`（副本数）**：一个分区一共存几份
- **`min.insync.replicas`（最小同步副本数）**：**只有当 ISR 里的副本数 ≥ 这个值时，`acks=all` 的写才被接受**；低于这个值时，Broker 直接拒绝写入并报 `NotEnoughReplicas`

**注意 `min.insync.replicas` 只在 `acks=all` 时生效**（官方原话：*this setting only takes effect if the producer uses acks=all*）。配了 `acks=1` 就是白配——这是第二个高频错点。

#### 3.2 主线判据：能同时坏几台【推导】

设 `replication.factor = 3`、`min.insync.replicas = 2`（生产上的常见组合），问：**同时坏几台机器还能写，坏到什么程度开始拒绝写？**

```
① 坏 1 台：ISR 从 3 降到 2
   2 ≥ min.insync.replicas(2) → 写入正常接受
   而且 ISR 里的副本数据是全的 → 不丢

② 坏 2 台：ISR 从 2 降到 1
   1 < min.insync.replicas(2) → 写入被拒绝（NotEnoughReplicas）
   ★ 拒绝写入 = 用"不可用"换"不丢数据"
```

【推导】**这两条就是 `min.insync.replicas` 的全部意义**：

- 它设成 **1**（默认值）→ 单副本也能写，可用性最高，但**副本挂到只剩一个时仍在接受写，那一个再挂就丢数据**
- 它设成 **2** → 少一台就拒绝写，**牺牲可用性换"已确认的消息绝不丢"**

#### 3.3 为什么必须 `replication.factor > min.insync.replicas`【推导】

假设两者**相等**（都是 3）：

```
坏 1 台 → ISR = 2 < 3 → 立刻拒绝写入
```

**也就是说只要有一台机器故障，整个分区就写不进去了**——这不是高可用，是"零容忍"。所以配置上的关系必须是：

```
replication.factor > min.insync.replicas   （推荐 replication.factor = min.insync.replicas + 1）
```

#### 3.4 那"坏了就拒绝写"算不算丢数据？【推导】

**不算，但要分清两件事：**

| 现象 | 性质 | 后果 |
|---|---|---|
| 写入被拒绝（`NotEnoughReplicas`） | **可用性损失** | 消息根本没发出去，生产者收到异常，**可以重发**——数据没丢 |
| 消息 ack 之后随 Leader 一起消失 | **数据丢失** | 不可挽回 |

【推导】**"不丢"的定义是：生产者收到成功 ack 的消息，永远不会消失。** 所以线上看到"MQ 写入报错"，**第一反应应该是"它在保护数据"，而不是"MQ 坏了"**——这个判断方向反了，排查就会走歪。

#### 3.5 加上选举策略：不干净的选主才是最后一道漏口【事实】

Leader 挂了要从副本里选新 Leader。Kafka 的策略由 `unclean.leader.election.enable` 控制：

- **`false`（0.11.0 之后是默认值）**：**只从 ISR 里选**。ISR 里的副本数据是全的 → 选了也不丢；代价是如果 ISR 全挂光，这个分区**一直不可用，直到原来的 Leader 回来**
- **`true`**：允许把**不在 ISR 里**的副本选成 Leader。好处是立刻恢复服务，**代价是没同步上的那部分消息永久消失**

【取舍】**这就是经典的"可用性 vs 一致性"二选一**，官方 Design 文档把它讲得很直白：*If, on the other hand, a non-in-sync replica comes back to life and we allow it to become leader, then its log becomes the source of truth even though it is not guaranteed to have every committed message.*

**到这里你应该能回答**：`acks=all` + `min.insync.replicas=2` + `unclean.leader.election.enable=false` 这三件事分别在挡什么？

### 4. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "`acks=all` 是所有副本都收到" | 【事实】**是所有在 ISR 里的副本**。ISR 只剩一个时 `acks=all` 照样成功（官方 Design 原文），所以必须配 `min.insync.replicas` |
| "acks 默认是 1" | 【事实】那是旧版本。**Kafka 3.0 起默认已是 `all`**（因为幂等生产者默认开启，而幂等要求 `acks=all`） |
| "配了 `min.insync.replicas` 就安全了" | 【事实】**它只在 `acks=all` 时生效**。配了 `acks=1` 的话它一点作用都没有 |
| "持久化配了就一定不丢" | 【推导】持久化有"写进页缓存 → 异步刷盘"的窗口，**这窗口里断电仍会丢**；PB 级可靠性要靠复制确认（publisher confirm / acks=all），而不是靠"开了持久化" |
| "消费者收到消息就该立刻 ack，免得重复" | 【推导】**这是主动制造丢消息**。提前 ack 后进程崩溃 → 消息永久消失且无人报警。**正确顺序永远是"处理成功 → 再 ack"** |
| "消息丢了加个重试就行" | 【取舍】重试只解决**第三段**（消费失败）。发送段和存储段的丢消息，重试根本触及不到——**先定位在哪一段丢，再谈手段** |
| "MQ 报写入失败就是 MQ 出问题了" | 【推导】大概率是**它在用不可用换不丢数据**（ISR 不足）。判断方向反了，会把"保护机制生效"误诊为"故障" |
| "上 MQ 一定比数据库任务表可靠" | 【取舍】错，方向反了。**引入 MQ 立刻要付三笔代价（可用性 / 复杂度 / 一致性）**，收益在吞吐与解耦。EnergyOps 明确不上 MQ 就是这个账 |

## 二、自测

**Q1（计算）**：某 Topic 配 `replication.factor = 3`、`min.insync.replicas = 2`、生产者 `acks = all`、`unclean.leader.election.enable = false`。

问：① 同时坏几台 Broker 还能继续写入？② 坏几台会出现"已 ack 的消息丢失"？③ 如果把 `min.insync.replicas` 改成 1，上面两个答案怎么变？

**A1**：

| 场景 | ISR 大小 | 能否写入 | 会不会丢已确认消息 |
|---|---|---|---|
| 坏 0 台 | 3 | ✅ | 不会 |
| 坏 1 台 | 2 | ✅（2 ≥ 2） | 不会（ISR 内数据是全的） |
| 坏 2 台 | 1 | ❌ 拒绝写（1 < 2） | 不会（要么拒写，要么从 ISR 选主） |
| 坏 3 台 | 0 | ❌ | 不会，但分区**一直不可用**，直到原 Leader 回来 |

- ① 最多**坏 1 台**还能写
- ② **坏到 2 台及以后都不会丢**——因为 `min.insync.replicas` 挡住了"副本不足时的写入"，而 `unclean=false` 挡住了"从落后副本选主"。**这两个参数一起构成了"不丢"的完整闭环**
- ③ 改成 1 之后：坏 2 台仍能写（ISR=1 ≥ 1），**这时最后一个副本再挂，已经 ack 的消息就丢了**。也就是**可用性变好、不丢的保证没了**——这正是 `min.insync.replicas` 默认值是 1 但生产上不推荐用默认值的原因

【这一步在验证什么】验证"不丢"是**两个参数合起来**实现的，不是 `acks=all` 一个参数的事。

**Q2（计算）**：消费者用 `enable.auto.commit=true`（默认），`auto.commit.interval.ms=5000`。某次 `poll()` 拉到 100 条（offset 100–199），处理每条要 50ms。

问：① 如果消费者在第 60 条处理到一半时进程崩溃，最多丢多少条？为什么？② 换成"处理完整批再手动提交"，崩溃时的表现是什么？

**A2**：

① 首先算这批要处理多久：`100 × 50ms = 5000ms`，**刚好等于自动提交间隔**。

自动提交是**定时器**，跟你的处理进度完全无关。它每 5 秒把"最后一次 `poll()` 返回的位置"提交上去（即 offset 200）。所以在第 5 秒那一瞬间：

```
已提交：offset 200（= 100~199 全部"已处理"）
实际处理到：第 60 条
崩溃 → 重启从 offset 200 开始拉
→ 第 61~100 条（40 条）永远不会被处理，且没有任何人知道
```

**丢 40 条**，而且是最危险的那种丢：**静默丢失，监控上 lag 还是 0**。

② 换成手动提交后，崩溃时 offset 还停在 100，重启会**把 100–199 重新拉一遍** → **不丢，但会重复**。

【这一步在验证什么】验证 1.2 的结论：**auto-commit 的语义是"模糊的"**——它既可能丢（提交跑在处理前面），也可能重（提交落后于处理），取决于崩溃点。**要确定语义，就得把提交时机和业务处理绑死**；而一旦绑死到"处理后再提交"，语义就变成至少一次——**重复是"不丢"的代价，这是绕不过去的交换**（[[母题-Q2-重复与乱序]]）。

**Q3（计算）**：Broker 里同时坏掉 2 台（`replication.factor = 3`、`min.insync.replicas = 2`）。生产者的写请求会发生什么？**会不会有消息被静默丢弃**？运维此时应该做什么？

**A3**：

```
坏 2 台 → ISR 从 3 降到 1
1 < min.insync.replicas(2)
→ Broker 对 acks=all 的写请求返回 NotEnoughReplicas 异常
→ 生产者收到异常，消息【没有被接受】
```

**不会有消息被静默丢弃。** 这是关键：`NotEnoughReplicas` 是一个**明确的错误返回**，不是静默失败——生产者能感知，可以进重试、进本地缓冲区、或明确失败上报。

**运维此时的动作顺序**：

1. **先判断这是保护还是故障**：拒绝写说明配置在正确地保护数据（3.4 节），**不要急着把 `min.insync.replicas` 改成 1 来"恢复写入"**——那等于把"不可用"换成"可能丢数据"，是把数据安全问题降级成可用性问题
2. **恢复副本**：把挂掉的 Broker 拉回来，等 ISR 恢复
3. **如果短时间恢复不了且业务不能停**：这才需要**显式决策**——是接受 `acks=1`（丢数据的风险）还是继续不可用。**这是一个必须由人签字的决定，不能由运维顺手改掉**

【这一步在验证什么】验证 3.4 的判据：**"不可用"和"丢数据"是两种性质不同的故障，修复动作完全不同。** 把前者当后者处理（改小 `min.insync.replicas`）会把小事故变成大事故。

**Q4（纠错）**：下面这段话哪里错了？

> "消息不丢很简单：把 `acks` 设成 `all` 就行了，这样所有副本都收到才确认，绝对丢不了。默认 `acks` 是 1，记得改成 all。"

**A4**：**三处都错。**

1. **"所有副本都收到"错了**。`acks=all` 的含义是**所有在 ISR（同步副本集合）里的副本都收到**。官方 Design 文档说得很清楚：*By default, when acks=all, acknowledgement happens as soon as all the current in-sync replicas have received the message*，而且明确举了反例——**一个 2 副本的 Topic 挂掉 1 个（ISR 只剩 1 个）时，`acks=all` 的写依然成功，而这些写在那个副本也挂掉时会丢**。

2. **"设成 all 就绝对丢不了"错了**。`acks=all` 单独用**挡不住"ISR 缩到 1 时仍然接受写"**。要补上门槛必须再配 **`min.insync.replicas ≥ 2`**（它只在 `acks=all` 下生效）——这样 ISR < 2 时直接拒绝写，把"可能丢"变成"明确不可用"。

3. **"默认 acks 是 1"过期了**。**Kafka 3.0 起 `acks` 默认值就是 `all`**——因为幂等生产者默认开启，而幂等要求 `acks=all`。老资料讲默认 1 是没错的，但现在照抄会显得没跟进版本。

**准确说法**：*不丢要三个参数一起给——`acks=all`（等 ISR 全部确认）+ `min.insync.replicas≥2`（ISR 不足就拒写）+ `unclean.leader.election.enable=false`（不从落后副本选主）。它们分别挡的是"Leader 单点"、"ISR 缩水后继续写"、"选到数据不全的新 Leader"这三个不同的漏口。*

**Q5（纠错）**：下面这段话哪里错了？

> "下游收到的消息有重复，这是 MQ 的 bug，换成 Kafka（或换个队列）就好了。"

**A5**：**"这是 bug"和"换个 MQ 就好了"两处都错。**

**"重复"不是缺陷，是所有 MQ 的必然结果。** 原因是结构性的（第 1.2 节）：

```
"处理消息"和"记录处理进度"是两次独立操作，中间崩溃必有一件事没做成：
  进度先记了 → 不重投 → 丢了（Q2 算的 40 条）
  业务先做完 → 进度没记 → 重投 → 重复
```

**要同时杜绝两者，需要 MQ 和业务数据库做分布式事务**——代价高到没人付。所以**所有主流 MQ 的一致选择都是：框架保证至少一次（宁重勿丢），去重交给业务层**。换任何一个 MQ 都不改变这个前提。

**正确的处理方向是两条，不是一条**：

| 方向 | 做什么 |
|---|---|
| **把重复变成无害**（首选） | 业务层做**幂等**：用稳定的业务幂等键（订单号 / 业务主键，**不是消息 ID、不是 ToolCallID**）在数据库唯一约束或 Redis 里查重 |
| **减少重复的量**（辅助） | 调提交时机、缩小批次，让重复窗口变小——但这只是**降低概率，不是消除** |

**RuleArena 就是这么做的**：系统**接受** Redis/ARQ 队列的至少一次投递和 Worker 随时崩溃，靠"稳定幂等键 + 唯一约束 + 权威状态查询"保证业务副作用只生效一次（`projects/RuleArena/04-idempotency-and-recovery.md` §9）。**它连 key 都不能拿 ToolCallID——那东西每次调用都变，重试时对不上。**

**准确说法**：*重复消费是"至少一次投递"的必然代价，不是 bug。正确的问法不是"怎么让它不重"，而是"重了会怎样、我的幂等键是什么"。*

## 三、面试输出（学完再看）

**一句话结论**：消息只可能在**三段**丢——发送、存储、消费，**每段各有一道确认**：生产端等 Broker 确认（`acks`）、Broker 端持久化 + 多副本、消费端**处理完再 ack**。不丢不是一个参数能搞定的，要三个一起给：**`acks=all`（等 ISR 全部确认）+ `min.insync.replicas≥2`（ISR 不足就拒绝写，把"可能丢"换成"明确不可用"）+ `unclean.leader.election.enable=false`（不从落后副本选主）**。而且必须接受一个前提：**跨进程通信没有"恰好一次"，框架只保证至少一次**——所以"不丢"的准确定义是"**生产者收到成功 ack 的消息永不消失**"，重复是它的代价，由业务幂等吃掉。

**恢复关键词**：三段接力 / 每段一道确认 / `acks=0/1/all` / **all = 所有 ISR 副本**（不是所有副本）/ `min.insync.replicas` 只在 acks=all 时生效 / `replication.factor > min.insync.replicas` / `unclean=false` 只从 ISR 选主 / 持久化 vs 多副本是两个手段 / RabbitMQ 队列持久化 ≠ 消息持久化 / **处理完再 ack** / 重试→重试队列→死信队列 / **至少一次 + 幂等 = 恰好一次的效果** / 拒写是保护不是故障

**核心不变量 / 主线**：
**"不丢"是"三道确认 + 一个门槛"的组合，而不是某一项配置的功劳。** 三道确认各自挡住一个位置（网络、磁盘/机器、消费者进程），门槛（`min.insync.replicas` + `unclean=false`）挡住的是"副本已经不全了还在假装正常"。**这三者的共同方向是：宁可明确拒绝服务，也不假装成功。**

**完整回答骨架**：先讲 MQ 换到什么和三笔代价（顺带说明"什么时候不该上"）→ 给出核心前提"没有恰好一次，只有至少一次" → 三段接力表（每段丢法 + 兜法）→ 逐段展开（acks 三档 / 持久化与多副本 / ack 时机）→ 量化"能坏几台"（ISR 算术 + 两个参数的分工）→ 选举策略的可用性 vs 一致性 → 边界与误解

**完整回答（口述稿）**：
消息只可能在**三段**丢——发送、存储、消费，**每段各有一道确认**：生产端等 Broker 确认（`acks`）、Broker 端持久化 + 多副本、消费端**处理完再 ack**。

不丢不是一个参数能搞定的，要**三个一起给**：**`acks=all`（等 ISR 全部确认）+ `min.insync.replicas ≥ 2`（ISR 不足就拒绝写，把"可能丢"换成"明确不可用"）+ 禁止从落后副本选主**。因为 **`acks=all` 单独不保证不丢**——它指的是 ISR 里的副本，ISR 缩到 1 时照样接受写。

两个必须说清的语义：① **"不丢"的准确定义是"生产者收到成功 ack 的消息永不消失"**，不是"消息一定被处理一次"——**跨进程通信没有"恰好一次"，框架只保证至少一次**，重复是它的代价，由业务幂等吃掉；② **不能"收到消息就 ack"**，那是主动制造丢消息：提前 ack 后崩溃，Broker 认为已处理完不会再投，消息永久消失且无任何报警。

消费失败三档兜底：**重试（限次 + 退避）→ 重试队列（RocketMQ 并发消费默认 16 次）→ 死信队列**；死信队列的意义是"**绝不静默丢弃**"。本地事务和发消息的一致性本质是"两个系统没法放进一个本地事务"，三条路线：**事务消息 / 本地消息表 / Outbox**（EnergyOps 用的是 Outbox）。

**分层要点**：
- **结论**：三段各一道确认；不丢要三个参数一起给；框架只保证至少一次。
- **推导链**：三段 → 各段确认 → acks=all 的漏洞（ISR 缩到 1）→ 用 min.insync.replicas 闭环 → 重复的代价交给幂等 → 失败三档兜底 → Outbox 解决跨系统事务。
- **量化**：`acks` 三档（0/1/all）；`min.insync.replicas ≥ 2`；RocketMQ 默认重试 16 次。
- **边界与常见误解**："acks=all 就保证不丢"×；"收到就 ack"会永久丢消息且无报警；持久化开着不等于不会丢（还有异步复制与误操作）。

**追问**（先说后看）

1. **`acks=all` 就保证不丢了吗？** —— **不保证**。它是"所有 **ISR 里**的副本"，ISR 缩到 1 时照样接受写。**必须配 `min.insync.replicas≥2` 才闭环**（这也是 `min.insync.replicas` 默认 1 却不推荐用默认值的原因）。
2. **本地事务和发消息怎么保持一致？** —— 本质是"两个系统没法放进一个本地事务"。三条路线：**事务消息**（RocketMQ 半消息 + Broker 回查）、**本地消息表**、**Outbox**（业务表与待发消息同事务落库，再由 Worker 投递）。**EnergyOps 用的就是 Outbox**（Alarm 与 Notification Outbox 同事务）；RuleArena 明确"当前不提前引入 Kafka/Outbox"，升级条件是出现真实的跨服务事件投递需求。
3. **消费失败反复重试还是失败怎么办？** —— 三档兜底：重试 → 重试队列（RocketMQ 并发消费默认 16 次）→ **死信队列**。**死信队列的意义是"绝不静默丢弃"**，最后一定有人/有告警能看到。
4. **为什么不能"收到消息就 ack"？** —— 那就是**主动制造丢消息**：提前 ack 后崩溃，Broker 认为已处理完不会再投，**消息永久消失且无任何报警**。正确顺序永远是"处理成功 → ack"。
5. **消息发送超时了能不能直接重试？** —— **不能直接重试**。超时表示**结果未知**，不代表失败——下游可能已经收到了。正确动作是**用同一幂等键重试**或**先查外部权威状态**（这条在 EnergyOps 里是原话：超时标记 `result_unknown`，先查或用同键重试）。

**同类变体**

- 「Push 还是 Pull？」——Kafka 选 **Pull**（消费者自己控制节奏、能批量、能重放），RabbitMQ 默认 **Push**（低延迟）；**判断依据是"消费速率该由谁控制"**
- 「Kafka 为什么快？」——顺序写 + 批量 + 压缩 + **零拷贝（sendfile）**；零拷贝的内核原理见 [[母题-O3-IO模型与零拷贝]]（**同一个知识点在不同模块出现，是本卡与 OS 模块的交叉点**）
- 「生产者要按顺序、又要不丢，怎么配？」——`acks=all` + `enable.idempotence=true`（3.0 起默认开）+ `max.in.flight.requests.per.connection ≤ 5`；**细节与"顺序"一并归 [[母题-Q2-重复与乱序]]**
