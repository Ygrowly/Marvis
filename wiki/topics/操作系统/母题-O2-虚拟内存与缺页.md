## 一、教材

### 1. 前提：一开始就要把"两个内存"分开

#### 1.1 虚拟内存要解决三个问题【事实】

**先建立概念**：**虚拟地址空间**（程序看到的地址）和**物理内存**（真实存在的内存条）是**两套东西**，中间由操作系统的**页表**做映射。

【推导】**为什么要多这一层**——三个理由，按重要性排序：

| 理由 | 不这么做会怎样 |
|---|---|
| **① 隔离** | 两个进程可以直接读写对方的内存 → **一个野指针就能改掉别人的数据**（安全与稳定都崩） |
| **② 让"申请"和"占用"解耦** | 程序申请 8GB 时，如果必须立刻找到 8GB 连续物理内存，**大量程序根本启动不了**（而且物理内存会大量闲置） |
| **③ 提供统一的地址视图** | 没有它，程序必须自己关心"我的变量在第几根内存条上" |

【推导】**第 ② 条是这一整张卡的主线**：**虚拟内存让"申请内存"和"占用内存"变成两件事。** 这句话直接解释了三件事——为什么 `malloc` 返回成功不等于有内存、为什么 8GB 的程序能在 4GB 机器上跑、为什么"内存泄漏"有时会拖很久才爆。

#### 1.2 地址翻译：页表、多级页表、TLB【事实】

**页（page）**：内存管理的最小单位，**典型 4KB**（这就是"大页"这个概念的参照点）。

**页表（page table）**：记录"虚拟页 → 物理页"映射关系的表。每次内存访问都要用它把虚拟地址翻译成物理地址。

【事实】**翻译过程要走过几级**：以 x86-64 的 4 级页表为例，48 位虚拟地址被切成 5 段：

```
47..39 (9位) → PGD        指向下一级页表
38..30 (9位) → PUD
29..21 (9位) → PMD
20..12 (9位) → PTE        这一项才是"物理页号"
11..0  (12位) → 页内偏移   4KB = 2^12
```

【推导】**为什么一定要分级**——这里有一个非常干净的算式（自测 Q1）：

```
要映射 48 位地址空间（2^48 = 256 TB），每页 4KB → 2^36 个页
如果只用一级页表：2^36 × 8 字节/项 = 512 GB  ← 只为存页表就要 512GB，荒谬

4 级之后：每级最多 512 项（9 位），每张页表 4KB
  最坏情况映射 4KB 的一小块内存，只需要 1 张 PTE 表 = 4KB
  → 稀疏的地址空间变得便宜了
```

【事实】**TLB（Translation Lookaside Buffer）**：CPU 里的**地址翻译缓存**，避免每次访问都走四级页表。

| 级别 | 容量 | 能覆盖多大 |
|---|---|---|
| L1 dTLB | 64–128 条目 | 极小 |
| **L2 STLB** | **约 1536 条目**（**随 CPU 型号变化**，这里取一个常见值） | **1536 × 4KB = 约 6 MB** |

【推导】**注意最后那一列**——**用 4KB 普通页时，TLB 只能覆盖约 6MB 的工作集**；超过就每次访问都要走页表（[[母题-O1-上下文切换与死锁]] 里"切换后 12.8 μs"的账就是从这来的）。**而如果用 2MB 大页**：

```
1536 × 2MB = 约 3 GB        ← 覆盖范围放大 512 倍
```

**【这就是大页（Huge Page）存在的唯一理由】——不是"更快"，是"让 TLB 装得下"。** 数据库、JVM 这类大内存工作集的场景配大页，就是为这一条。

**到这里你应该能回答**：为什么"多级页表"能省内存，而"大页"能省 TLB？

### 2. 缺页：一句"按需分配"背后的五种代价

#### 2.1 缺页是什么【事实】

**缺页中断（page fault）**：访问的虚拟页**还没有对应的物理页**（或权限不对）时，CPU 陷入内核，由内核处理。

【事实】**分两类，代价差两个数量级**（下表是**量级参考**，随硬件、内核版本、负载变化）：

| 类型 | 情况 | 量级 |
|---|---|---|
| **次要缺页（minor）** | 页在内存里，只是**还没建立映射**（如刚 `malloc` 的第一次写） | **约 1 μs 量级**（公开测量 0.5–2 μs） |
| **主要缺页（major）** | 页**不在内存里**，要从磁盘 / 交换空间读回来 | **约 100 μs 量级**（公开测量 50–200 μs，取决于存储设备） |

【推导】**把不同操作的量级放在一起看，差距有五个数量级**：

```
TLB 命中            ≈ 1 ns        ← 正常路径（≈ L1 缓存访问延迟）
系统调用跨越        ≈ 100 ns
次要缺页            ≈ 1 μs        ← 第一次碰一页新内存
L3 访问             ≈ 30–50 ns    ← 作对照
主要缺页            ≈ 100 μs      ← 要从磁盘换回来（比 TLB 命中慢约 10 万倍）
```

【推导】**这张表能推出三条实用结论**：

1. **`malloc` 之后第一次写会有 minor fault**——所以"刚启动时慢"是正常的，**预热（warm-up）不是玄学**
2. **major fault 是灾难性的**（100 μs 相当于上千次系统调用）——**所以"别让服务去 swap"是一条硬规矩**（见 3.3）
3. **"优化内存访问"的第一手段是提高 TLB 命中率**（局部性、大页），**不是减少 `malloc` 次数**

#### 2.2 从缺页推出 "malloc 成功 ≠ 有内存"【推导】

```
malloc(8GB) 的完整过程：
① 库向内核要 8GB     → 内核只"记一笔账"：这块虚拟地址区间归你了
                        【不分配任何物理页】→ 返回成功
② 你写第一页          → 缺页（minor）→ 这时才分配第一个物理页
③ 你继续写            → 每碰一个新页就缺页一次
④ 如果物理内存 + swap 不够了 → 触发 OOM（第 3 节）
```

【事实】**这个行为由 `vm.overcommit_memory` 控制**（`/proc/sys/vm/overcommit_memory`）：

| 值 | 行为 | 适用 |
|---|---|---|
| **0（默认）** | **启发式**：只拒绝"明显不合理"的请求（比如一次要得比内存+swap 总量还多很多） | 绝大多数场景 |
| 1 | **永远允许**：`malloc` 几乎不会返回 NULL | 申请巨大稀疏数组但从不碰满的场景（HPC） |
| 2 | **严格计账**：承诺总量不超过 `swap + RAM × overcommit_ratio/100`（ratio 默认 50） | 想要"分配就失败"而不是"以后被杀"——**但很多程序（尤其 JVM）会因此 `fork` 失败** |

【取舍】**为什么默认是"启发式"而不是"严格"**：因为 `fork()` 会让子进程的**虚拟**大小暂时翻倍（在 `exec` 之前），严格执行的话**大量正常程序连启动都启动不了**。**这个取舍的代价就是：分配成功不代表有内存——所以 OOM 会在"用的时候"而不是"要的时候"发生。**

**到这里你应该能回答**：为什么"申请成功"和"用得上"是两件事，这是设计缺陷还是刻意设计？

### 3. 量化：8GB 程序怎么跑在 4GB 机器上

#### 3.1 三个量：VSZ、RSS、以及"承诺量"【事实】

**先把三个容易混的概念分开**：

| 指标 | 含义 | 看它有什么用 |
|---|---|---|
| **VSZ / `total-vm`** | **虚拟**地址空间大小，**包含 mmap 的文件、地址预留** | **基本没用**（能大到很夸张却完全无害） |
| **RSS** | **常驻**内存，真正占着物理页的部分 | **这个才是"用了多少内存"** |
| **`anon-rss`** | RSS 里的匿名页（堆、栈）——**OOM 被回收的才是这部分** | **排查 OOM 时看它，不看 `total-vm`** |

【推导】**"8GB 程序跑在 4GB 机器上"的答案就在这张表里**：

```
VSZ  = 8 GB   （程序声明 / 预留的虚拟空间）
RSS  = 3 GB   （真正在用的）
机器 4 GB     → 跑得动

反过来的情形：
VSZ = 8 GB，RSS 涨到 4.5 GB → 触发回收 → 回收不动 → OOM
```

【推导】**所以准确的回答是**：*能不能跑不取决于程序"要多少"，取决于它**实际碰了多少**。虚拟内存把"要"和"用"解耦了，代价就是**爆的时候是在运行中爆，不是在启动时爆**。*

#### 3.2 页缓存：不是"泄漏"，是可回收的【事实】

【事实】Linux 会**主动把读过的文件缓存在内存里**（页缓存 / page cache）。**这部分被算进"已用内存"，但它随时可以被回收**——`free` 里的 `available` 才是"真正还能用的"。

【推导】**这是排查内存问题时最常见的误判源**：

```
free -h 显示 memory used 90%  → 第一反应"内存泄漏了"
实际：其中很大一部分是页缓存，压力来了内核会自己丢掉
判断：看 free 的 available 列，不看 used
进一步：看 /proc/meminfo 的 MemAvailable
```

【事实】**内存压力本身有专门的指标**：`/proc/pressure/memory`（PSI，内核 4.20+）。**`some avg10` 低于 5% 算健康、持续高于 20% 说明 OOM 很可能已经在路上（这是社区常用的经验阈值，不是官方定值）**——**比"等 OOM 日志"更早的预警**。

#### 3.3 swap：目的是"压力阀"，不是"扩内存"【取舍】

【取舍】**swap 的定位要说准**：

```
✅ 对：给冷页一个压力阀——把很久不用的页挪到磁盘，腾出物理内存给热数据
❌ 错：用 swap 来"扩充可用内存"
   → 一旦热数据被换出去，访问它就变成 major fault（百微秒量级）
   → 表现为"服务突然变得奇慢、CPU 不高、磁盘狂转"（thrashing）
```

【取舍】**所以服务端两条经验**：

- **数据库、缓存类**（Redis / MySQL）通常**建议关掉 swap 或设很小**——因为一次 major fault 是 10 万倍的代价，**宁可 OOM 快速失败并告警，也不要拖着半死**
- **通用服务**可以留少量 swap 当缓冲，但**同时要监控 major fault 速率**

#### 3.4 大页：把 TLB 覆盖范围放大 512 倍【推导】

在 1.2 已经算过，这里是它的工程落点：

```
普通 4KB 页：STLB 1536 条目 → 覆盖约 6 MB
2MB 大页：    STLB 1536 条目 → 覆盖约 3 GB
```

【推导】**结论**：**大页解决的是"工作集远超 TLB 容量"的场景**（数据库缓冲池、JVM 堆）。**代价**是**内存被按 2MB 粒度占用**（小进程用了会浪费）与**需要预留（不可交换）**。

**到这里你应该能回答**：为什么数据库和 JVM 要配大页，而一个 50MB 的服务配大页没意义？

### 4. OOM：谁被杀，怎么算的

#### 4.1 触发条件【事实】

【事实】OOM 在**内核把所有回收手段都用完**之后才发生：物理内存 + swap 都耗尽，页缓存、可回收匿名页、内存规整都试过了，**仍然无法满足一次分配请求** → 触发 OOM killer。

#### 4.2 杀谁：`oom_score` 是算出来的【事实】

::figure os-virtual-memory.svg | 虚拟内存的三个账本与 OOM 的选择逻辑 | 上：VSZ / RSS / anon-rss 的区别；下：`oom_badness()` 的组成与两类 OOM

【事实】**内核用 `oom_badness()` 给每个任务打分，杀分数最高的那个**：

```
points = (rss_anon + rss_file + rss_shmem + swapents + pgtables_pages)
       + (oom_score_adj × totalpages / 1000)
```

【推导】**逐项读这个公式，能读出四条规则**：

| 项 | 含义 | 推出 |
|---|---|---|
| `rss_anon` + `rss_file` + `rss_shmem` | 占的内存越多分越高 | **默认杀"最大内存占用者"** |
| `pgtables_pages` | **页表本身也占内存** | 一个疯狂映射大量小区域的进程，**光页表就能成为被杀理由** |
| `swapents` | 换出去的页也算 | 换出去不等于不记账 |
| **`oom_score_adj`** | **可调的偏移，范围 −1000 ~ 1000，默认 0** | **这是唯一的干预手段**：`−1000` = **永不被杀**；正值 = 优先被杀 |

【事实】**还有几条硬规则**：

- **`init` 进程和内核线程永不被杀**（无法杀）
- **与 victim 共享同一地址空间的进程会一起被杀**（同一线程组的线程，所以**"杀了个线程"实际是杀整个进程**）
- **5 秒内不会连续杀**（内核会避免在短时间内连续多杀，造成雪崩式连杀）
- **`oom_score` 只在 4.13+ 才有 `/proc/<pid>/oom_score` 可读**（早期只有 `oom_adj`）

#### 4.3 两类 OOM：这是本卡最实用的一节【推导】

【推导】**"整机还剩 40% 内存却 OOM 了"的答案在这里**——**OOM 有两类，作用范围完全不同**：

| | **整机 OOM（global）** | **cgroup OOM** |
|---|---|---|
| 触发条件 | 整机物理内存 + swap 耗尽 | **某个 cgroup 撞到自己的 `memory.max`** |
| 日志前缀 | `Out of memory:` | **`Memory cgroup out of memory:`** |
| 杀谁 | 全系统范围内按 `oom_score` 挑 | **只在这个 cgroup 内部挑** |
| 整机内存 | 必然紧张 | **可能非常宽松**（40%、60% 都可能） |

【事实】**cgroup v2 的关键旋钮**：

```
memory.max          硬上限，超过 → 触发 cgroup OOM
memory.high         软上限，超过 → 只做限流和积极回收（不杀）
memory.oom.group    如果开启 → 整个 cgroup 一起杀（避免杀一半留一半）
```

【事实】**Kubernetes 从 1.25 起默认 cgroup v2**，1.31 移除了 v1 支持——**所以现在容器里的"内存限制"就是 `memory.max`，超了就是 cgroup OOM。** 而 **systemd 服务的 `MemoryMax=` 也是同一个机制**。

【推导】**这就直接回答了本卡开头的第二个问题**：

```
"整机还剩 40%，容器却被 OOM 杀了"
→ 这不是矛盾，是【cgroup OOM】
→ 容器的 memory.max 是 512MB，而它涨到了 600MB
→ 整机有多少内存跟它没关系
排查动作：去看 cgroup 的内存水位，而不是看 free -h
```

【事实】**RuleArena 就是这种配置**：`08-capacity-cost-and-facts.md` 里 Redis 容器只给 **256~512MB**。**这个数字就是 `memory.max`，超了就是 cgroup OOM，跟宿主机内存无关。**

#### 4.4 怎么控制【取舍】

【取舍】**按"最有效 → 最粗暴"排序**：

| 手段 | 做什么 | 评价 |
|---|---|---|
| **`MemoryMax=` / `memory.max`（配 `MemoryHigh`）** | 给每个服务一个硬上限 | **最推荐**。建议 `MemoryHigh` 设在 `MemoryMax` 下方 10–20%（经验建议），**让内核算先回收而不是直接杀** |
| **`OOMScoreAdjust=` / `oom_score_adj`** | 调整被杀优先级 | 有效但要克制：**别随便设 −1000**，一个不可杀的进程会把"杀一个服务"升级成"杀不掉 → 内核 panic" |
| **代码侧限流 / 队列上限 / 缓存上限** | 从源头限制内存增长 | **最根本**。内存问题的根因几乎总是"某处队列 / 缓存无上界" |
| **加内存** | —— | 只是**推迟**问题。**如果增长无上界，加多少都一样** |

**到这里你应该能回答**：为什么"加内存"通常不是 OOM 的正解？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "`malloc` 成功了就有内存了" | 【事实】**只拿到虚拟地址空间**，物理页在第一次访问（缺页）时才分配。所以 OOM 发生在**运行中**，不在申请时 |
| "`top` 里 VSZ 很大，肯定内存泄漏了" | 【事实】**VSZ 包含 mmap 文件与地址预留，基本没有参考价值**。看 **RSS**；排查 OOM 更看 **`anon-rss`** |
| "`free` 显示内存用满 90%，要爆了" | 【事实】其中很多是**可回收的页缓存**。**看 `available` 而不是 `used`**，或用 `MemAvailable` |
| "被 OOM 杀了就是内存不够，加内存" | 【推导】**先分清两类 OOM**：整机 OOM（真不够）vs **cgroup OOM（撞了容器自己的上限，宿主机可能很空）**。日志前缀不同，排查方向完全不同 |
| "OOM 会杀掉最占内存的进程" | 【事实】公式上**内存占得多分高，但 `oom_score_adj` 可以翻转结果**——所以"杀的不是最大的那个"是正常现象，**先查 `adj` 有没有被人调过** |
| "进程被杀了，只杀了一个线程" | 【事实】**与 victim 共享同一地址空间的任务会一起被杀**——**"杀线程"实际是杀整个进程** |
| "swap 开大点就不怕内存不够了" | 【取舍】**swap 是压力阀不是扩容**。热数据被换出去后访问它是 major fault（比 TLB 命中慢好几个数量级），表现为"CPU 不高、磁盘狂转、服务奇慢"，**比干脆 OOM 更难排查** |
| "大页就是更快" | 【推导】**大页的真实作用是让 TLB 装得下**（4KB 页只能覆盖约 6MB，2MB 大页能覆盖约 3GB）。**小进程配大页没意义还浪费内存** |
| "内存泄漏一定能很快发现" | 【推导】因为有"申请 ≠ 占用"，**无上界的队列 / 缓存常常运行几天才爆**。**所以要在代码里给队列和缓存设上界**（RuleArena 给 Redis 只留 256~512MB 就是这种约束） |
| "容器限制了内存，宿主机就不会 OOM" | 【事实】只约束了这个容器的**上限**，**不保证它不超**；超了是 **cgroup OOM**。而且**宿主机上多个容器加起来仍可能把整机打满**（那时才是整机 OOM） |

## 二、自测

**Q1（计算）**：把这一节的两个算式都算一遍。

① 如果用**一级页表**映射 48 位虚拟地址空间（每页 4KB，页表项 8 字节），页表本身要多大？
② CPU 的 L2 STLB 有 **1536 个条目**。用 4KB 页时它能覆盖多大工作集？换成 2MB 大页呢？

**A1**：

① 一级页表：

```
地址空间 = 2^48 = 256 TB
页大小   = 4KB = 2^12 → 页数 = 2^48 / 2^12 = 2^36 个页
一级页表项数 = 页数 = 2^36
页表大小 = 2^36 × 8 字节 = 2^39 字节 = 【512 GB】

→ 也就是说：为了映射 256TB 的地址空间，光页表就要 512GB，
  而且每个进程都要一份 —— 完全不可行
```

**这就是必须分级的理由**：4 级页表下，**要映射 4KB 的一小块内存，只需要 1 张 PTE 页表（4KB）**，加上路径上的三张上级页表，共约 16KB——**稀疏的地址空间因此变得便宜**。

② TLB 覆盖范围：

```
4KB 页：  1536 × 4KB = 6 MB        ← 稍大点的工作集就装不下
2MB 大页：1536 × 2MB = 3 GB        ← 放大 512 倍
```

【这一步在验证什么】验证 1.2 的两条结论：**多级页表是为了"稀疏映射便宜"，大页是为了"TLB 装得下"。**

**这里可以直接回答一个常见追问**：*"为什么数据库和 JVM 要配大页？"* —— 因为**它们的缓冲池 / 堆动辄几 GB，4KB 页下 TLB 只能覆盖 6MB，几乎每次访问都要走四级页表**；换 2MB 页后 TLB 覆盖能到 3GB，**绝大多数访问命中 TLB（1 纳秒 vs 走页表）**。**这不是优化，是量级差异。**

**Q2（计算）**：某程序启动时 `malloc(8GB)` 成功，测试机只有 **4GB 物理内存 + 0 swap**。

问：① 它能跑起来吗？② 它跑起来之后能写多少数据？③ 什么时候会出问题、以什么形式出问题？④ 如果运维把 `vm.overcommit_memory` 设成 2，会发生什么？

**A2**：

① **能**。`malloc(8GB)` 只是**在虚拟地址空间里记一笔账**（默认 `overcommit_memory=0` 的启发式策略会放行），**不分配任何物理页**。

② **能写的大致是 4GB 减去系统和其他进程占用**——**写到物理内存用光为止**。****每写一个新的 4KB 页就触发一次次要缺页（微秒量级），然后从物理内存里分一页给它。****

```
能写的量 ≈ 可用物理内存 = 4GB − 系统占用 − 其他进程占用
```

③ **当物理页耗尽且没有任何东西可回收时**：

```
内核先尝试回收（页缓存、可回收匿名页）→ 回收不动
→ 触发 OOM killer
→ 按 oom_badness() 打分，杀掉分数最高的进程
```

**最危险的地方在于**：这个进程在**启动时完全正常**（`malloc` 成功、启动很快），**几个小时或几天后才被杀**。所以现象是"服务跑得好好的突然没了"，而不是"启动报错"。**这就是"申请 ≠ 占用"这个设计的直接代价。**

④ 设成 `overcommit_memory = 2` 之后：**`malloc(8GB)` 会直接失败**（严格的承诺量上限是 `swap + RAM × 50%` = 2GB，8GB 远超）。**程序立刻失败，而不是以后被杀。**

【取舍】**这是一个明确的工程选择，没有对错**：

| 策略 | 好处 | 代价 |
|---|---|---|
| `0` 启发式（默认） | 程序都能启动，内存利用率高 | **问题延后到运行期，表现为偶发被杀** |
| `2` 严格 | **问题在启动时暴露**，可预期 | **`fork()` 会失败**（子进程虚拟大小暂时翻倍），**JVM 类程序常常起不来** |

【这一步在验证什么】验证 1.1 的主线：**虚拟内存把"申请"和"占用"解耦**——所以 OOM 是"用的时候"爆，不是"要的时候"爆。

**Q3（计算）**：某 16GB 机器（`totalpages` 按 4KB 页算 = 4194304 页）上有两个进程：

- 进程 A：`anon-rss` = **7.5 GB**，`oom_score_adj` = **0**
- 进程 B：`anon-rss` = **2 GB**，`oom_score_adj` = **0**

问：① 谁会被 OOM killer 选中？② 如果给进程 B 设 `oom_score_adj = -500`，选中的会变吗？③ 如果给 A 设 `oom_score_adj = -1000` 呢？

**A3**：

① 按公式（只看主导项，页表 / swap 项忽略）：

```
points(A) = rss_pages(A) + 0 × totalpages/1000
          = 7.5GB / 4KB = 1,966,080 页   ← 最大
points(B) = 2GB / 4KB = 524,288 页
→ 杀 A（内存占用最大的）
```

② 给 B 设 `-500`：

```
adj 项 = −500 × 4194304 / 1000 = −2,097,152
points(B) = 524,288 + (−2,097,152) = −1,572,864   ← 变成负数
→ B 几乎不会被选（分数被大幅拉低）
→ 仍然是杀 A（而且更确定了）
```

**注意**：这个计算说明 `oom_score_adj` 的**量级很大**——`−500` 就能把 2GB 的进程压到负分。**所以"减一点 adj"这种微调是不存在的，一动就是数量级。**

③ 给 A 设 `−1000`：

```
adj 项 = −1000 × 4194304/1000 = −4,194,304
points(A) = 1,966,080 − 4,194,304 = −2,228,224
→ A 【永不被杀】
→ 于是杀手转向 B（哪怕 B 只有 2GB）
```

【取舍】**这才是这个参数的正常用法**——给"绝不能死"的服务加保护（比如 `sshd`），而不是给自己随便加。**而这里有一个必须记住的副作用**：

```
把 A 设成不可杀之后，内存仍然不够
→ 内核会继续找下一个受害者（B、C……）
→ 如果所有候选都被设成不可杀
   → 【内核 panic】
   → 从"杀一个服务"升级成"整机挂掉"
```

**这就是为什么官方文档反复警告"不要随手设 −1000"**（systemd 侧对应 `OOMScoreAdjust=-1000`）。

【这一步在验证什么】验证 4.2：**OOM 的选择是"算"出来的，`oom_score_adj` 是唯一的干预点，而且它的量级很大、用错会放大事故。**

**Q4（纠错）**：下面这段话哪里错了？

> "运维说容器半夜被 OOM 杀了，我先看了 `free -h`：used 才 62%，available 还有 5.8GB。所以肯定不是内存问题，应该是别的原因。"

**A4**：**"肯定不是内存问题"错得很典型——把两类 OOM 混成了一类。**

**OOM 有两类，作用范围完全不同：**

| | 整机 OOM | **cgroup OOM** |
|---|---|---|
| 触发条件 | 整机内存 + swap 耗尽 | **容器撞到自己的 `memory.max`** |
| 日志前缀 | `Out of memory:` | **`Memory cgroup out of memory:`** |
| 与宿主机内存的关系 | 直接相关 | **完全无关**（宿主机很空也会发生） |

**所以 `free -h` 显示 5.8GB 可用，和"容器被 OOM 杀"完全不矛盾**——正确的问题是：**这个容器的 `memory.max` 是多少？它涨到了多少？**

**排查动作应该是**：

```
① 先看日志前缀是哪一类
   有 "Memory cgroup out of memory" → cgroup OOM，去查容器限额
② 查 cgroup 的内存水位
   /sys/fs/cgroup/<path>/memory.max      （上限）
   /sys/fs/cgroup/<path>/memory.current  （当前）
   或 cgroup v1 的 memory.limit_in_bytes / memory.usage_in_bytes
③ 再看是不是"涨着涨着撞上去的"（泄漏 / 无上界队列）
   还是"突然一次性冲上去的"（大对象 / 一次性加载）
④ 对照 free -h 判断是不是【同时】还有整机压力（可能两层都撞）
```

**另外还有两个附带错误**：

- **`free` 的 `used` 高不代表危险**：里面很大一部分是**可回收的页缓存**。**判断可用量要看 `available`**（这一步它做对了）
- **`available` 5.8GB 也不代表容器能用 5.8GB**——**容器的上限是 `memory.max`，不是宿主机剩余内存**。这是容器与裸机排查思路的分水岭

**准确说法**：*OOM 分整机 OOM 和 cgroup OOM 两类，后者与宿主机剩余内存无关。容器被 OOM 先看日志前缀、再查 `memory.max` 与 `memory.current`，而不是看 `free -h`。*

**Q5（纠错）**：下面这段话哪里错了？

> "服务内存一直在涨，肯定是内存泄漏。解决办法要么修代码，要么给机器加内存。"

**A5**：**"肯定是泄漏"和"加内存"两处都错，而且第一处会让排查方向彻底跑偏。**

**① "一直在涨"有三种完全不同的原因**：

| 原因 | 特征 | 处理 |
|---|---|---|
| **真的泄漏** | 只涨不跌，**回收压力下也不下降** | 修代码（查无上界的容器、未释放的引用） |
| **正常的页缓存增长** | 涨到某处**趋于平稳**，且**压力下会回落** | **不用管**，看 `available` |
| **无上界的数据结构**（队列 / 缓存 / 连接池 / Trace 缓冲） | 涨势和**流量正相关**，流量停了就平 | **给容器设上界**（这才是根因） |

**② "加内存"是最后手段，而且常常只是推迟问题**：

```
如果增长是无上界的（比如一个只进不出的队列）
→ 加多少内存都会在同一天某个时刻爆
→ 唯一有效的动作是【给它一个上界 + 一个溢出策略】
```

**RuleArena 的做法就是这一条的正面例子**：给 Redis 只配 **256~512MB**，**让"无上界"变成"有上界"**——超了就按明确策略处理（队列丢弃 / 拒绝），而不是让进程无限涨到被 OOM 杀。**同样，队列要设长度上限、缓存要设淘汰策略、Trace 缓冲要设采样率**——**"给它一个上界"是内存治理里唯一真正通用的手段。**

**③ 还有一个更早发现的工具**：`/proc/pressure/memory`（PSI）。

```
some avg10 < 5%   → 健康
some avg10 > 20%  → OOM 很可能已经在路上
→ 比等 OOM 日志更早预警，而且能区分"是内存压力还是 CPU 压力"
```

**准确说法**：*先分清"泄漏 / 页缓存 / 无上界结构"三种涨法：只有第一种要修代码，第三种要给上界（加内存没用）。提前用 PSI 判断内存压力，比等 OOM 更早。*

## 三、面试输出（学完再看）

**一句话结论**：**虚拟内存让"申请"和"占用"解耦**——`malloc(8GB)` 只是在虚拟地址空间里记一笔账（默认 `overcommit_memory=0` 的启发式会放行），**物理页在第一次访问时（缺页）才分配**，所以 **8GB 的程序能跑在 4GB 机器上**，但**打满物理内存时会在运行中触发 OOM**（而不是启动时报错）——这就是"申请 ≠ 占用"的代价。**缺页的代价跨几个数量级**：TLB 命中 **纳秒级**（≈ L1）、次要缺页 **微秒级**、主要缺页（要从磁盘换回来）**百微秒级**——所以"别让服务去 swap"是硬规矩。**大页存在的唯一理由是让 TLB 装得下**（4KB 页下 TLB 只能覆盖几 MB，2MB 大页能覆盖几 GB）。**OOM 是算出来的**：`oom_badness()` = 内存占用（`rss` 各项 + **页表** + swap）**+ `oom_score_adj × totalpages/1000`**，杀分最高的；**而且有两类 OOM 必须分清——整机 OOM 与 cgroup OOM，后者的日志前缀是 `Memory cgroup out of memory`，和宿主机剩余内存无关**。

**恢复关键词**：虚拟内存两大作用（隔离 + 申请/占用解耦）/ **`malloc` 只拿虚拟地址，物理页在缺页时才给** / 4 级页表（48 位地址 = 9+9+9+9+12）/ 一级页表要 512GB（所以必须分级）/ **TLB 条目有限 → 4KB 页只能覆盖几 MB，2MB 大页能覆盖几 GB** / 缺页三档（纳秒 / 微秒 / 百微秒）/ **VSZ 无参考价值，看 RSS，排查 OOM 看 anon-rss** / 页缓存可回收，看 available 不看 used / **swap 是压力阀不是扩容** / **`oom_badness()` 的组成，页表也计入** / `oom_score_adj` −1000 = 免死（**滥用会 panic**）/ 共享同一 mm 的任务一起被杀 / **两类 OOM + 日志前缀** / cgroup `memory.max` / `memory.high` 提前回收 / **PSI `some avg10`** / 治理根因 = **给无上界队列设上界** / **测量值只当量级**

**核心不变量 / 主线**：
**"申请"和"占用"被解耦，是一切内存现象的总开关。** 它同时解释了：为什么 `malloc` 成功还会 OOM（解耦的代价）、为什么 8GB 能跑 4GB 机器（解耦的收益）、为什么无上界的队列能拖几天才爆（解耦把故障从启动期推迟到运行期）。**而控制它的唯一通用手段不是"加内存"，是"给每个会增长的东西设上界"。**

**完整回答骨架**：先立"两个内存"的概念与虚拟内存的三个作用 → 地址翻译（多级页表的算式 + TLB 覆盖范围）→ 缺页三档代价 → 从缺页推出"`malloc` 成功 ≠ 有内存"与 overcommit 三档策略 → 量化"8GB 跑 4GB" → VSZ / RSS / anon-rss 三个量 → 页缓存与 PSI → swap 的定位 → 大页的算式 → OOM 的公式与四条硬规则 → **两类 OOM 的分辨（最实用）** → 控制手段排序 → 边界与误解

**完整回答（口述稿）**：
**虚拟内存让"申请"和"占用"解耦**——`malloc(8GB)` 只是在虚拟地址空间里记一笔账（默认 `overcommit_memory=0` 的启发式会放行），**物理页在第一次访问时（缺页）才分配**。所以 **8GB 的程序能跑在 4GB 机器上**，但**打满物理内存时会在运行中触发 OOM**（而不是启动时报错）——这就是"申请 ≠ 占用"的代价。

**缺页的代价跨几个数量级**：TLB 命中**纳秒级**（≈ L1）、次要缺页**微秒级**、主要缺页（要从磁盘换回来）**百微秒级**。所以"**别让服务去 swap**"是一条硬规矩——换页把微秒级操作变成百微秒级，直接反映成延迟抖动。

**大页存在的唯一理由是让 TLB 装得下**（同样条目数覆盖更大内存，减少 TLB miss）。

记一条与容器侧的呼应：**容器里 `free` 看到的是宿主机内存**，自己的额度只在 cgroup 的 `memory.max` / `memory.current` / `memory.events` 里；超了是 **cgroup OOM**，日志前缀和整机 OOM 不同。

**分层要点**：
- **结论**：申请 ≠ 占用；缺页代价跨数量级，所以不能让服务 swap；大页为的是 TLB 覆盖率。
- **推导链**：虚拟地址记账 → 首次访问才分配 → 三种缺页代价 → swap 是延迟抖动源 → 大页减少 TLB miss。
- **量化**：TLB 命中纳秒级、次要缺页微秒级、主要缺页百微秒级。
- **边界与常见误解**："malloc 成功就有内存"×；容器里要看 cgroup 文件而不是 `free`。

**追问**（先说后看）

1. **为什么 `malloc` 成功还会 OOM？** —— **`malloc` 只拿到虚拟地址空间**，物理页在首次访问（缺页）时才分配。所以问题是**推迟到运行期**才暴露的——而且 `overcommit_memory=0`（默认）是刻意这么设计的，因为 `fork()` 会让虚拟大小暂时翻倍，严格执行会连正常程序都起不来。
2. **VSZ 很大是不是内存泄漏？** —— **不是**。VSZ **包含 mmap 的文件和地址预留，基本没有参考价值**。看 **RSS**，排查 OOM 看 **`anon-rss`**（`total-vm` 在 OOM 日志里也印着，但它是"几乎无意义"的那个）。
3. **OOM 会杀哪个进程？** —— 按 `oom_badness()` 打分，**内存占用（`rss_anon` + `rss_file` + `rss_shmem` + swap + **页表页数**）占主导，再用 `oom_score_adj × totalpages/1000` 调整**，杀分最高的。**`init` 和内核线程不杀；与 victim 共享地址空间的一起杀；5 秒内不连杀。**
4. **容器被 OOM 杀了怎么排查？** —— **先看日志前缀分清是哪一类**：`Memory cgroup out of memory` 是 **cgroup OOM**（撞了 `memory.max`，**与宿主机剩余内存无关**）；`Out of memory` 是整机 OOM。然后查 `memory.max` / `memory.current`，再判断是"渐涨撞上去"还是"一次性冲上去"。
5. **swap 要不要开？** —— **看负载**。数据库 / 缓存类**建议关或设很小**（热数据被换出去后一次访问是微秒到百微秒量级，表现为"CPU 不高、磁盘狂转、服务奇慢"，比 OOM 更难查）；通用服务可留少量作压力阀，但要监控 major fault 速率。**swap 的定位是压力阀，不是扩内存。**
6. **怎么提前发现内存问题？** —— **`/proc/pressure/memory`（PSI）**：`some avg10` 低于 5% 健康、持续高于 20% 说明 OOM 可能已在前方。**比等 OOM 日志更早**，还能区分是内存压力还是 IO 压力。

**同类变体**

- 「`free` 显示内存用满怎么办？」——**先看 `available` 不看 `used`**，页缓存是可回收的；再看 PSI 判断压力。**"用满"本身不是问题，回收不动才是**
- 「Redis 为什么要设 `maxmemory`？」——**给无上界的东西设上界**，是本卡 5.5 结论的直接应用（[[母题-R2-持久化与内存淘汰]]）
- 「为什么 Kafka 快也和页缓存有关？」——Kafka 的顺序写 + 读都尽量落在**页缓存**上，**避免真的走磁盘**；这也解释了它为什么对内存量敏感（[[母题-O3-IO模型与零拷贝]]）
- 「`OOM` 和 `cgroup OOM` 的内核路径有什么不同？」——**整机 OOM 在全系统范围挑 victim，cgroup OOM 只在该 cgroup 内挑**（`mem_cgroup_scan_tasks`）；后者的出现说明**限额被撞了，而不是机器不够**
