## 一、教材

### 1. 前提：Linux 其实不区分"线程"和"进程"

#### 1.1 二者在操作系统里是什么【事实】

**先各自介绍，再比较**：

**进程（process）**：操作系统**分配资源的基本单位**。它拥有一个**独立的虚拟地址空间**（页表、代码段、数据段、堆、栈、文件描述符表、信号处理器）。

**线程（thread）**：进程内的**执行单元**。它**共享**所属进程的地址空间和大部分资源，**只独占两样东西**：**寄存器状态**和**自己的栈**。

【事实】**关键的一层事实**：**Linux 内核里没有"线程"这个独立概念**——线程和进程**都是 `task_struct`**（内核里叫"任务"），区别只在创建时传了哪些共享标志：

```
fork()            → 不共享地址空间               → 新 task_struct 有自己的 mm_struct
pthread_create()  → 走 clone()，带一组共享标志：
                    CLONE_VM       共享地址空间
                    CLONE_FS       共享文件系统信息
                    CLONE_FILES    共享文件描述符表
                    CLONE_SIGHAND  共享信号处理器
                    CLONE_THREAD   属于同一个线程组（同一个"进程号"）
```

【推导】**所以"线程是轻量级进程"这个说法在 Linux 上是字面成立的**——它就是"共享得更多的进程"。**从这一句话，下面所有差异都能推出来**：

| 共享了什么 | 由此推出 |
|---|---|
| **地址空间共享** | 线程间**通信极便宜**（直接读同一个变量）；进程间**必须拷贝或走内核** |
| **地址空间共享** | **同一进程内不换页表** → 切换便宜；**跨进程要换页表** → 切换贵（第 2 节） |
| **地址空间独立** | 进程**隔离最好**（一个崩了不影响别的）；**线程共享一切**（一个线程野指针能带崩整个进程） |

#### 1.2 判断"开销"要用同一把尺子【推导】

【推导】这一节的标题是"线程开多了会更慢"，那就必须先说清**"开销"指什么**。执行单元的开销分三块，**面试时能分开说就已经赢一半**：

| 开销类型 | 是什么 | 什么时候发生 |
|---|---|---|
| **① 创建开销** | 建地址空间 / 栈 / 内核对象 | 一次性 |
| **② 切换开销** | 换 CPU 上跑的东西 | **每次被换下都发生**——这是大头 |
| **③ 内存占用** | 栈 + 内核对象 | 常驻，**决定你能开多少个** |

**这三块的方向不一样**：① 和 ③ 决定性"能不能开"，**② 决定"开了之后还快不快"**。第 2、3 节分别量化 ② 和 ③。

**到这里你应该能回答**：为什么"进程和线程的区别"这一题的真正考点是"共享了什么"而不是"谁更轻"？

### 2. 一次上下文切换到底做了什么（量化）

#### 2.1 六步【事实】

::figure os-switch-cost.svg | 一次上下文切换的六步与成本构成 | 直接成本约 0.7~0.9μs；真正的账在间接成本：TLB 与缓存，可达几十微秒

**上下文切换（context switch）**：把 CPU 上正在跑的任务换下去、换另一个上来。

【事实】以 Linux 为例，完整过程六步：

```
① 触发：时间片用完（定时器中断）／主动阻塞（等 IO、sleep、抢不到锁）／被更高优先级抢占
② CPU 从用户态陷入内核态
③ 调度器挑下一个要跑的任务
④ 保存当前任务的 CPU 状态（寄存器、指令指针、栈指针）到它的 task_struct
⑤ 加载下一个任务的 CPU 状态
⑥ ★ 如果下一个任务属于【另一个进程】：写 CR3（页表基址寄存器）+ 处理 TLB 失效
⑦ 返回用户态，新任务从它上次停下的地方继续
```

【推导】**第 ⑥ 步是进程切换和线程切换唯一的直接差别**——同进程的线程共享页表，**这一步被整个跳过**。**记住"差别只有一步"，比背一堆"线程更轻"要有用得多。**

#### 2.2 直接成本：微秒量级【事实】

> ⚠️ **2026-09-17 校验修正**：本卡初版把直接成本写成"线程 0.73 μs / 进程 0.93 μs"，**这是从一份二手测量文章里抄来的单一数据点，不能当【事实】用**。多个独立来源（`lmbench` 的 `lat_ctx`、以及公开的 token 传递基准）给的是**1.3–4 μs**。已按下表改写，并明确标注数据的性质。

【事实】**先把数据的性质说清楚：上下文切换没有唯一的"标准值"**——它随 CPU 型号、内核版本、是否跨核迁移、负载高低变化很大。**公开测量里常见的区间是 1–5 μs**：

| 测量方式 | 典型结果 | 说明 |
|---|---|---|
| `lmbench` 的 `lat_ctx`（现代 x86 服务器） | **约 1.3–1.5 μs** | 隔离得较好，接近"纯"切换成本 |
| 简单 token 传递（两进程/两线程用管道来回） | **约 3–4 μs** | 把调度与唤醒的开销也算进去了 |
| 高负载 + 跨核迁移 | **10 μs 以上** | 含间接成本（下一节） |

【事实】**所以面试时给"量级 + 方向"比给一位小数更安全**：

- **量级**：**微秒级**（不是纳秒级，也不是"几百纳秒"）
- **方向**：**线程切换比进程切换快约 20–30%**（仅直接部分）

【推导】**两者的直接差别只有一处**（第 ⑥ 步：写 CR3 + 处理 TLB 失效），**所以如果只算直接成本，"进程 per request"看起来只贵两三成，根本不值得讨论——真正的故事在下一节。**

#### 2.3 间接成本：这才是大头【推导】

【推导】**切换真正的代价是"换过去之后的冷启动"**，而它不出现在切换那一刻，而是分摊在切换之后的一段时间里：

| 间接成本 | 机制 | 量级 |
|---|---|---|
| **TLB 失效** | 跨进程换页表 → 地址翻译缓存作废 → 后续访问要去**走页表** | **约 25 ns / 页**（每页重走一次） |
| **CPU 缓存污染** | L1/L2 里装的是上一个任务的**数据**，新任务要重新预热 | 取决于工作集大小；L1 约 1 ns、L3 约 30–50 ns、内存约 100 ns，**这个差距就是"冷启动"的成本** |
| **分支预测器失效** | 预测器的历史属于上一个任务的代码 | 难以直接量化 |

【推导】**把 TLB 那一项算出来——但要注意它是一个"上限估计"，不是实测值**：

```
跨进程切换后，假设新任务的工作集是 2MB：
  2MB / 4KB（一页）= 512 页
  每页一次页表遍历 ≈ 25 ns
  → 512 × 25ns ≈ 12.8 μs   ★ 这是"每一页都要重走一遍"的【上限】

实际达不到这个上限，原因有两个：
  ① TLB 有约 1536 个条目 → 2MB（512 页）的工作集本来就能装下
  ② PCID / ASID 能让多数翻译【跨切换保留】
→ 所以真实代价在"接近零"和"十几微秒"之间浮动
```

【事实】**公开测量给出的总量级**：轻载 **1–5 μs**；**高负载、缓存被反复冲刷时可以到 10–50 μs**——**也就是说"间接成本常常比直接成本大一个数量级"这个判断是成立的**，只是一次切换值多少微秒必须看场景。

【推导】**所以"进程 per request 不可行"的正确说法是**：

```
✔ 每请求一个进程 → 每次调度多付一次【页表切换 + TLB 失效】，
                   在并发高、缓存争抢激烈时把切换成本推高一个数量级
✘ 不是"贵 19 倍"这种精确倍数（那是用一个上限估计除以一个单一数据点算出来的）
```

【事实】**这个成本有缓解手段**：

- **TLB 容量**：二级 TLB 约 **1536 个条目**（**随 CPU 型号变化**），4KB 页下能覆盖约 6MB 工作集
- **PCID / ASID**：给 TLB 条目打进程号，**同一 CPU 上最多保留约 6 个地址空间的翻译**（这是内核的编译期常量 `TLB_NR_DYN_ASIDS`）——所以"少数几个进程轮着跑"时**不会每次都全量失效**；超过之后才开始互相驱逐

【取舍】**所以"进程模型还是线程模型"的判断是**：

```
每请求一个进程   → 每次调度多付一次地址空间切换，且在进程数多、缓存争抢激烈时成本跳一个数量级
每请求一个线程   → 省掉那一步，且同进程的线程【缓存常常还是热的】
                   → 这正是"高吞吐服务端普遍是多线程而不是多进程"的量化依据
```

**这就是"高吞吐服务端普遍是多线程而不是多进程"的真正原因**（不是因为创建快，是因为**每次调度的账差近 20 倍**）。

#### 2.4 调度器在做什么【事实】

【事实】调度器要解决的问题是"**有限的核 vs 无限的就绪任务**"，几个要点：

- **时间片**通常 **1–10 ms** 量级，用完就被**强制换下**（这叫**非自愿切换**）
- **自愿切换**：任务自己去等 IO / 睡 / 抢锁失败——**它主动让出 CPU**
- **两种切换要分开看**：`/proc/<pid>/status` 里的 `voluntary_ctxt_switches` 和 `nonvoluntary_ctxt_switches` 分别计数，**优化方向完全不同**（前者多说明在等 IO，后者多说明在抢 CPU）
- **观测手段**：`perf stat -e context-switches,cs,migrations`、`vmstat 1` 的 `cs` 列

【事实】**量级参考**：典型桌面每秒 **1–5 万次**切换；一个 50K req/s 的 Web 服务可能到 **每秒 10–50 万次**。

### 3. 内存开销：线程到底吃掉多少（这是被讲错最多的一节）

#### 3.1 用户栈：8MB 是"虚拟预留"，不是"物理占用"【事实】

【事实】**先纠正一个几乎每份资料都写错的地方**：

| 说法 | 真实情况 |
|---|---|
| "线程栈约 1MB" | ❌ **不准确**。`pthread_create(3)` man-page 明确写：**在 NPTL 实现下，线程创建时的默认栈大小由 `RLIMIT_STACK` 决定**（只要它启动时不是 `unlimited`）。而 Linux 默认 `ulimit -s` 是 **8192 KB = 8MB**。**x86-32 的默认才是 2MB** |
| "线程栈一定占那么多内存" | ❌ 它是**虚拟地址空间预留**，**只有被触碰到的页才真正分配物理内存** |
| "线程栈和主线程栈一样" | ❌ **不一样**：主线程的栈在最顶部、**可以按需向下增长**到 `RLIMIT_STACK`；**非主线程的栈是 `mmap()` 出来的、大小固定、不能增长**——用完就 `SIGSEGV` |

【推导】**那"8MB × 线程数"这个算法错在哪**：

```
开 1000 个线程：
  虚拟地址空间：8MB × 1000 = 8 GB   ← 这个数是"预留"，不是"占用"
  实际物理（假设每个线程只用 2 页栈）：8KB × 1000 = 8 MB
```

【推导】**在 64 位系统上虚拟地址空间有 128TB，8GB 预留根本不算问题**——所以"8MB 栈"在 64 位下**不是**线程数的限制因素。**限制它的是下面这个。**

#### 3.2 内核侧：二三十 KB，这才是真实占用【事实】

【事实】每个任务在内核里都有一份**独立**的结构，这部分**既不共享也不能省略**：

| 项 | x86-64 | 说明 |
|---|---|---|
| **内核栈**（`THREAD_SIZE`） | **16 KB** | **这个数是确定的**：内核源码里 `PAGE_SIZE << 2`（KASAN 关闭时）→ 4KB × 4 = 16KB；x86-32 是 8KB |
| **`task_struct` 等内核对象** | **数 KB 量级** | ⚠️ **具体值随内核版本与编译配置变化很大**（公开资料里有 2KB 到十几 KB 的不同数字），所以这里只给量级 |
| **合计（保守取用）** | **每个线程约 25 KB** | **用作估算的保守值**，不是精确值 |

【推导】**关键的两句话**：

1. 这部分是每线程独立的、不能省的——**它是"线程数"真正的物理成本**（量级二三十 KB，不是 8MB）
2. 它**不计入进程的 RSS**（`top` / `ps` 里看不到）——**所以"看内存占用不高就以为线程不多"是个经典误判**

#### 3.3 上限到底是谁定的【推导】

【推导】**问"能开多少线程"，答案不是"内存够就行"，而是取下面几个上限里的最小值**：

| 上限 | 默认值 | 算法 / 来源 |
|---|---|---|
| **`threads-max`** | 视内存而定 | `mempages / (8 × THREAD_SIZE / PAGE_SIZE)`（内核 `fork_init()`）→ **内核栈最多占 1/8 内存**。16GB 机器 → **131072** |
| **`pid_max`** | **32768**（按 CPU 数上浮，上限 2²² ≈ 419 万） | 每个任务占一个 pid，`proc(5)` 文档 |
| **`ulimit -u`（`RLIMIT_NPROC`）** | 每用户不同 | 限制单个用户 |
| **cgroup `pids.max` / systemd `TasksMax`** | 服务默认是全局上限的 15% | **容器里最常撞到的就是这一条** |

【推导】**算一次就明白"内存不够"往往不是真因**：

```
16GB 机器：
  内核栈上限（threads-max）= 131072 个线程 → 内核侧共 131072 × 25KB ≈ 3.2 GB
  也就是说 16GB 里最多拿出约 1/8 给内核栈——这离"内存用光"还很远

所以真实情况通常是：
  pid_max = 32768  → 先撞它
  或者容器的 pids.max / TasksMax → 更早撞它
  → 报错是 "Resource temporarily unavailable"，而不是 OOM
```

【取舍】**"线程开不出来"和"线程开出来太慢"是两件事**：

- 开不出来（`EAGAIN`）→ 查 `pid_max` / `threads-max` / `pids.max`
- 开出来太慢（吞吐降）→ 是 2.3 的切换成本账

**到这里你应该能回答**：为什么"内存不够所以不能多开线程"这个解释通常是错的？

### 4. 共享的代价：从竞态到死锁

#### 4.1 竞态是"共享地址空间"的直接后果【推导】

【推导】**线程最方便的地方就是最危险的地方**：地址空间共享意味着**同一个变量是同一块内存**。

```
static int n = 0;
// 4 个线程各自执行 n++ 一次
// 期望 n = 4
// 实际可能输出 1 —— 因为 n++ 是"读-改-写"三步，不是原子操作
```

【推导】**加锁解决了正确性，但引入两个新成本**：

| 成本 | 表现 |
|---|---|
| **锁本身的开销** | 无竞争时约几十纳秒；**有竞争时要陷入内核挂起/唤醒，等于多做几次上下文切换** |
| **死锁** | 一旦发生，**相关线程永远等下去**，只能重启 |

#### 4.2 死锁的四个必要条件与破法【事实】

【事实】**死锁发生必须同时满足四个条件**（缺一个就不会死锁——**这就是所有解法的出发点**）：

| # | 条件 | 含义 |
|---|---|---|
| ① | **互斥** | 资源一次只能被一个执行单元占用 |
| ② | **持有并等待** | 占着一个还在等另一个 |
| ③ | **不可剥夺** | 不能强行从别人手里抢走 |
| ④ | **循环等待** | 存在一个环：A 等 B 的资源，B 等 A 的资源 |

【推导】**解法就是"破掉任意一个"**，而工程上的性价比排序很明确：

| 破哪个 | 做法 | 代价 / 适用性 |
|---|---|---|
| **④ 循环等待** | **全局固定加锁顺序**（比如永远先锁账户 ID 小的、再锁大的） | **最实用**。改动小、几乎无性能代价——**这是首选答案** |
| **② 持有并等待** | 一次性申请所有需要的锁，拿不齐就不拿 | 改动大、资源利用率低 |
| **③ 不可剥夺** | 拿不到就释放已持有的锁重试，或设**超时** | 简单但会"活锁"（反复重试一直失败） |
| **① 互斥** | 用无锁结构 / CAS，把"共享"变成"不共享"（比如 `thread_local`、每线程一个计数器最后汇总） | 最强但最难写对 |

【事实】**怎么"检测"已经有死锁**：把"任务"和"资源"画成有向图，**出现了环就是死锁**——建行家的数据库死锁检测用的就是这个思路（[[母题-M10-锁与死锁]] 里 MySQL / PostgreSQL 的死锁检测是同源不同层）。

#### 4.3 自旋锁还是互斥锁【取舍】

【取舍】**判断依据只有一个：临界区短不短、以及能不能睡。**

| | 自旋锁 | 互斥锁 |
|---|---|---|
| 抢不到时 | **忙等**（一直占着 CPU） | **睡**（让出 CPU，等唤醒） |
| 适合 | **临界区极短**（几条指令）、**多核**、**不能睡的场景**（中断上下文） | 临界区可能较长（含 IO / 可能阻塞） |
| 不适合 | 临界区长 → **白烧 CPU，还挡着别人** | 极短临界区 → **睡眠 + 唤醒比干活本身还贵** |

【取舍】**一句话判据：如果"等待的时间"比"切换两次的代价"还短，就该自旋；否则就该睡。**（两次切换按 2.3 算约 1.5 μs 量级——所以"临界区不到 1 微秒"是自旋的合理区间。）

#### 4.4 用户态与内核态：边界在哪，为什么贵【事实】

【事实】

- x86-64 有 **4 个特权级（ring 0–3），实际只用 2 个**：**ring 3 跑应用、ring 0 跑内核**；ARM64 叫 **EL0 / EL1**
- **边界的执行者是硬件，不是内核**：页表里的权限位决定"当前这个环能不能读这个地址"——**所以"内核空间不可访问"是硬件拦的，不是软件检查的**
- **一次边界跨越（系统调用进出）的成本**约 **100 ns 量级**（有实验把"一次系统调用跨越"标在 **100 ns 以内**；这个数在公开资料里比较一致，但也仍是量级）

【推导】**为什么"贵"的定义要小心**：单次 100 ns 其实不贵。**贵的是"次数 × 每次都要跨越"**：

```
100 万次系统调用 / 秒 × 105ns ≈ 0.105 个核
→ 优化方向不是"让系统调用更快"，而是【让系统调用更少】（批量、合并、io_uring）
```

**到这里你应该能回答**：为什么"减少系统调用次数"比"优化单次系统调用"更值得做？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "线程栈约 1MB" | 【事实】**Linux 上是 8MB**（由 `ulimit -s` 默认 8192KB 决定）；x86-32 才是 2MB。而且它是**虚拟预留**，不是物理占用 |
| "10 万线程要 100GB 内存，所以开不了" | 【推导】**8GB × 10万 = 800GB 是虚拟地址空间**，64 位下有 128TB，**不是瓶颈**。真实占用是内核侧 **25KB/线程 ≈ 2.5GB**，而**先撞的通常是 `pid_max` / `threads-max` / 容器的 `pids.max`** |
| "线程很轻，所以越多越好" | 【事实】`task_struct` + 内核栈**每线程约 25KB 且不计入 RSS**；切换成本随线程数上升，**过了拐点总吞吐下降** |
| "进程切换贵是因为寄存器多" | 【推导】寄存器部分只有约 200 字节、几十个周期。**真正的差在跨进程换页表导致的 TLB 失效与缓存污染**——**直接成本线程只比进程快两三成，差距体现在间接部分**。⚠️ **也不要给"贵 19 倍"这种精确倍数**，测量值只能给区间 |
| "一次上下文切换是几百纳秒" | 【事实】**是微秒量级**。公开测量常见区间是 **1–5 μs**（`lmbench` 的 `lat_ctx` 约 1.3–1.5 μs；含调度唤醒的测试 3–4 μs），**重载含间接成本可到 10–50 μs**。**"几百纳秒"通常只是寄存器保存恢复那一段** |
| "看 `top` 内存不高，说明没问题" | 【事实】**内核侧 25KB/线程不在 RSS 里**，容器 cgroup 的内存与 pids 限制也不在 `top` 里。**要看 `/proc/<pid>/status`、`/sys/fs/cgroup/...`、`ulimit -u`** |
| "死锁只能靠重启" | 【推导】**四个条件破一个就够**，工程上首选**固定加锁顺序**（破循环等待）——便宜、有效、几乎无性能代价 |
| "自旋锁一定比互斥锁快" | 【取舍】只有在**临界区极短 + 多核**时才是。临界区长了自旋就是**白烧 CPU 还挡着别人** |
| "多线程能利用多核，所以一定更快" | 【推导】要分负载：**IO 密集**时线程有用（等的时候别人能跑）；**CPU 密集**时线程数超过核数后**只剩切换开销**（Python 还要叠加 GIL，见 [[母题-N3-进程线程与协程]]） |
| "瓶颈就是线程不够，加线程池" | 【推导】**先算"每个单元的工作量 ÷ 切换成本"**。如果大部分时间花在等（IO / 锁 / 下游），加线程只是**让更多执行单元一起去排队**——中间件连接池、下游限流会先成为新瓶颈 |

## 二、自测

**Q1（计算）**：某服务收到用户投诉变慢。`vmstat` 显示该系统每秒 **50 万次**上下文切换，其中绝大多数是**非自愿切换**（时间片被抢）。

问：① 按"一次切换 1 μs"这个量级保守估算，光切换消耗了多少 CPU？② 如果其中 20% 是跨进程切换（含间接成本，按 10 μs 算），成本怎么变？③ 这个数字说明问题出在哪？

**A1**：

```
① 直接成本（按 1 μs 保守估）：500,000 × 1 μs = 0.5 s/s ≈ 【0.5 个核】
   → 一个核的一半被用来"换任务"而不是"干活"

② 跨进程部分：500,000 × 20% = 100,000 次
   按 10 μs（含 TLB 与缓存的间接成本）：
     100,000 × 10 μs = 1.0 s/s  ← 一个整核
   剩余 400,000 次同进程：0.4 s/s
   合计 ≈ 【1.4 个核】

   ⚠️ 注意这个估算对"单次多贵"非常敏感：如果间接成本实际是 3 μs 而不是 10 μs，
      ②的结果就从 1.4 核降到 0.7 核。【所以这类计算只能用来判断"量级"，不能当精确账】
```

③ **问题不是"CPU 不够核"，是"执行单元太多/太小，核都在换任务"**：

- **非自愿切换占绝大多数** = 大量任务在**抢 CPU**（不是等 IO），说明**可运行任务数 >> 核数**
- 优化方向**不是加机器**，而是**减少执行单元数 / 让每个单元干更多的活**：
  - 把细粒度的任务**批量化**（一次处理一批，而不是一条一个任务）
  - IO 等待改成**异步**（让线程不要占着核等）→ [[母题-N3-进程线程与协程]]
  - 检查是不是**线程池 + 定时任务 + 框架内部线程**叠加出了几百个线程
- **关键判断：`nonvoluntary` 多 = 抢 CPU（要减并发）；`voluntary` 多 = 在等（要改异步或加并发）**

【这一步在验证什么】验证 2.4 的判据：**"切换多"必须分成自愿和非自愿看——两者优化方向相反。**

**Q2（计算）**：某服务开了 **1000 个线程**，每个线程的栈**实际只用了 2 页**（8KB）。

问：① 用户栈占多少**虚拟**内存、多少**物理**内存？② 内核侧占多少？③ 在 16GB 的机器上，这个配置能不能再翻 10 倍？④ 如果再翻 10 倍开不出来，最可能撞到哪个限制？

**A2**：

```
① 用户栈（每个线程默认按 RLIMIT_STACK = 8MB 预留）
   虚拟：8MB × 1000 = 8 GB    ← 预留，不是占用
   物理：8KB × 1000 = 8 MB    ← 只有被触碰的页才分配

② 内核侧（每线程约 25KB，不能省）
   25KB × 1000 = 25 MB

③ 翻 10 倍 = 10000 个线程：
   虚拟：8MB × 10000 = 80 GB   ← 64 位有 128TB 虚拟空间，【完全没问题】
   物理：8MB + 250MB ≈ 260 MB  ← 【离 16GB 差得很远】
   → 结论：从"内存"角度看，翻 10 倍没问题

④ 但很可能开不出来，先撞的是这三个：
   · pid_max：默认 32768，10000 个还没到，但如果每用户/每容器叠加就快了
   · ulimit -u（RLIMIT_NPROC）：单用户限制，常被设成几千
   · 容器的 pids.max / systemd TasksMax：服务默认只给全局上限的 15%
   → 报错是 "Resource temporarily unavailable"（EAGAIN），不是 OOM
```

【这一步在验证什么】验证第 3 节的两个结论：**① 用户栈的开销主要是虚拟的，几乎不构成 64 位系统的限制；② 真正的限制是内核侧 25KB 与各种"任务数上限"。**

**这里的推论比答案重要**：**所以面试里答"线程栈 1MB，开一万个就是 10GB，内存扛不住"是错的**——错在把虚拟预留当物理占用、也错在找错了限制源。

**Q3（计算）**：两个线程，共享两个锁 A 和 B。代码是：

```
线程 1：lock(A) → lock(B) → ... → unlock(B) → unlock(A)
线程 2：lock(B) → lock(A) → ... → unlock(A) → unlock(B)
```

问：① 死锁一定发生吗？② 如果发生，是卡在哪个时刻？③ 用"破循环等待"的方法怎么改？④ 改成"加锁超时，超时就释放重试"行不行？

**A3**：

① **不一定，但随时可能**。死锁需要**时序巧合**——只有"线程 1 拿到 A 的同时、线程 2 拿到了 B"才会死锁。**所以这种 bug 的特点就是"压测不复现、线上偶发、一复现就卡死"**。

② 卡在两个线程**各自持有一把、又都在等对方那把**的时刻：

```
时刻 T1：线程 1 持有 A，线程 2 持有 B
时刻 T2：线程 1 执行 lock(B) —— 等线程 2 释放
         线程 2 执行 lock(A) —— 等线程 1 释放
         → 形成环，四个条件全部满足 → 永久等待
```

③ **破"循环等待"：规定全局唯一的加锁顺序**。比如"永远先锁 ID 小的，再锁 ID 大的"：

```
线程 1：lock(min(A,B)) → lock(max(A,B))
线程 2：lock(min(A,B)) → lock(max(A,B))   ← 两边顺序一样，环就不存在了
```

**这是首选方案**：改动小（可能只是几行代码）、**没有性能代价**、彻底解决。

④ **可以，但要接受副作用**：超时重试属于**破"不可剥夺"**，能保证"不会永久卡死"，但会引入两个新问题：

- **活锁风险**：两个线程同时超时、同时释放、同时重试——可能一直撞（要用随机退避打破对称）
- **正确性风险**：**如果临界区里有不可回滚的操作（已经发了外部请求、已经写了不可逆状态），超时释放后重试会造成重复副作用**（这就是 [[母题-Q2-重复与乱序]] 里"结果未知"那一类问题）

【这一步在验证什么】验证 4.2 的判据：**破四条件里的哪一个，性价比差别很大——先破"循环等待"（免费），不到万不得已才用超时（有副作用）。**

**Q4（纠错）**：下面这段话哪里错了？

> "线程很轻量，一个线程才 1MB 栈。所以一台 16GB 的机器开一万个线程没问题——才占 10GB 嘛。"

**A4**：**三处都错。**

1. **"1MB 栈"不是 Linux 的值**。`pthread_create(3)` man-page 写明：**在 NPTL 实现下，新线程的默认栈大小由 `RLIMIT_STACK` 决定**（只要启动时不是 `unlimited`），而 Linux 默认 `ulimit -s` 是 **8192 KB**——**即 8MB**。**1MB 是 Windows 的默认线程栈**；x86-32 上 Linux 是 2MB。**这个数被抄错了很多年。**

2. **栈是"虚拟预留"，不是"物理占用"**。8MB 是**地址空间预留**，只有被触碰的页才分配物理内存。**所以"8MB × 10000 = 80GB"算的是虚拟空间**——而 64 位进程有 **128TB** 虚拟空间，**80GB 完全不是问题**。

3. **真正的成本被漏掉了：内核侧**。每个任务有**独立的内核栈 16KB**（x86-64 的 `THREAD_SIZE`，这是确定值）+ **`task_struct` 等结构（数 KB 量级，随内核配置变化）** ≈ **每个线程二三十 KB（保守按 25KB 估）**，**且不计入 RSS**：

```
物理占用（10000 线程）：
  用户栈物理：8KB × 10000 = 80 MB（按每线程用 2 页）
  内核侧：    25KB × 10000 = 250 MB
  合计约 330 MB  ← 远远不是"内存扛不住"
```

**所以"内存扛不住"这个结论本身也是错的。** 真正会先拦住的不是内存，而是**任务数上限**：`pid_max`（默认 32768）、`ulimit -u`、**容器的 `pids.max` / systemd `TasksMax`**。撞到时报的是 **`Resource temporarily unavailable`（EAGAIN）**，**不是 OOM**——**把错误类型搞错，排查方向就全歪了。**

**准确说法**：*Linux 上线程默认栈由 `ulimit -s` 决定（默认 8MB），但那是虚拟预留、按需提交；真正的常驻成本是内核侧二三十 KB/线程（内核栈 16KB + `task_struct`，保守按 25KB 估），且不进 RSS。64 位系统上虚拟空间不是瓶颈，先撞的是 pid_max / ulimit -u / 容器 pids.max。*

**Q5（纠错）**：下面这段话哪里错了？

> "接口 QPS 上不去，肯定是线程池太小了，把线程数从 50 调到 500 就行——线程越多并发越高嘛。"

**A5**：**"肯定是线程池太小"和"线程越多并发越高"两处都错。**

**① 方向错：并发高不等于吞吐高。** 线程数只有在下述条件下才有用——

```
线程超过核数之后，同一时刻真正在跑的只有【核数】个
多出来的线程：
  要么在等（IO / 锁 / 下游）→ 那加线程对【CPU 密集】部分毫无帮助
  要么在抢（时间片）→ 那加线程让【非自愿切换】上升（Q1 的账）
```

**② 判断必须先分清"在等"还是"在算"**：

| 现象 | 说明 | 该做什么 |
|---|---|---|
| 线程 CPU 利用率低、大部分时间在 `WAITING` | **在等 IO / 下游** | 改异步（[[母题-N3-进程线程与协程]]）或**优化下游**，**加线程只到能填满等待窗口为止** |
| 线程 CPU 接近 100%、`nonvoluntary` 切换高 | **在算** | 加线程**没用**（核就那么多），要去优化算法 / 加机器 / 多进程 |
| 连接池、下游限流已满 | **下游是瓶颈** | **加线程只会把下游打得更死**（[[母题-Q3-积压与高可用]] 的同一类错误） |

**③ 而且调大线程池有三个额外副作用**：每个线程约 25KB 内核侧开销、切换成本上升、**下游被打得更狠**（并发上来但每个请求更慢，P99 先崩）。

**准确说法**：*先看线程在等还是在算。在等就改异步或优化下游，在算就加核/改算法；连接池与下游限流是前置约束——过了它们，加线程只会让整体更差。*

## 三、面试输出（学完再看）

**一句话结论**：进程和线程的区别，在 Linux 上可以一句话说清——**它们都是 `task_struct`，线程只是"共享得更多的任务"**（`clone()` 带上 `CLONE_VM` 等标志，共享地址空间、文件表、信号处理器，只独占寄存器和栈）。**这个"共享了什么"直接推出全部差异**：共享地址空间 → 线程间通信便宜但**没有隔离**；独立地址空间 → **跨进程切换要写 CR3、TLB 失效**。切换成本是**微秒量级**（公开测量 1–5 μs，重载含间接成本可到 10–50 μs），**其中大头是间接的**——TLB 失效与缓存污染，**单看直接成本线程只比进程快约 20–30%**，但因为跨进程要换地址空间，**并发高时这部分会把成本推高一个数量级**，这就是"高吞吐服务端普遍多线程而非多进程"的依据。内存侧要纠正一个流行错说法：**Linux 线程默认栈是 8MB（由 `ulimit -s` 决定）而不是 1MB，而且是虚拟预留、按需提交**；真正的常驻成本是**内核侧二三十 KB/线程（16KB 内核栈 + `task_struct`，不计入 RSS）**；**先撞上的通常不是内存，而是 `pid_max` / `ulimit -u` / 容器 `pids.max`**。共享的代价是竞态，**死锁要同时满足四个条件（互斥、持有并等待、不可剥夺、循环等待），破任一个就够，工程上首选"固定加锁顺序"（破循环等待）**。

**恢复关键词**：Linux 不区分线程与进程（都是 `task_struct`，差别在 `clone` 的共享标志）/ 线程独占寄存器 + 栈 / **切换六步，第 ⑥ 步写 CR3 是唯一直接差别** / **切换是微秒量级（1–5 μs，重载 10–50 μs）** / 线程比进程快约 20–30%（直接部分）/ **间接成本才是大头（TLB 重走页表、缓存污染）** / 测出来的数字只能当量级 / PCID 让若干地址空间的翻译跨切换保留 / 时间片 1–10 ms / **voluntary vs nonvoluntary 优化方向相反** / **线程栈 8MB 虚拟（不是 1MB 物理）** / 非主线程栈 mmap 出来、不能增长 / **内核侧二三十 KB/线程、不进 RSS** / `threads-max` = 1/8 内存 / `pid_max` 32768 / cgroup `pids.max` / 死锁四条件 / 破循环等待（固定加锁顺序）最实用 / 自旋 vs 互斥看临界区长不长 / 系统调用约 100 ns 量级，优化方向是**减少次数**

**核心不变量 / 主线**：
**"共享了什么"决定了"付什么代价"**——线程共享地址空间换来通信便宜，代价是切换要换页表（贵）和没有隔离（危险）；不共享换来隔离，代价是通信与切换都贵。**而"该开几个执行单元"永远由"切换成本 ÷ 每个单元的工作量"决定，不由"越多越并发"决定。**

**完整回答骨架**：先给"Linux 不区分线程和进程、差别在共享了什么" → 从"共享了什么"推出三组差异（通信 / 切换 / 隔离）→ 一次切换的六步 + "第 ⑥ 步是唯一直接差别" → **给切换成本的量级区间与数据性质（1–5 μs；重载 10–50 μs），说明线程与进程只差两三成、真正的差在间接成本** → 说明 PCID 与 TLB 容量的边界 → 调度与自愿/非自愿切换的判据 → **内存账（虚拟 8MB vs 内核二三十 KB vs 上限是谁）** → 共享的代价：竞态 → 死锁四条件与破法 → 自旋 vs 互斥 → 用户态/内核态与系统调用 → 边界与误解

**完整回答（口述稿）**：
进程和线程的区别在 Linux 上可以一句话说清——**它们都是 `task_struct`，线程只是"共享得更多的任务"**（`clone()` 带上 `CLONE_VM` 等标志，共享地址空间、文件表、信号处理器，只独占寄存器和栈）。

**这个"共享了什么"直接推出全部差异**：共享地址空间 → 线程间通信便宜但**没有隔离**；独立地址空间 → **跨进程切换要写 CR3、TLB 失效**。切换成本是**微秒量级**（公开测量 1–5 μs，重载含间接成本可到 10–50 μs），**其中大头是间接的**——TLB 失效与缓存污染；**单看直接成本，线程只比进程快约 20–30%**，真正的差距来自间接成本。

死锁四个必要条件：互斥、占有且等待、不可抢占、循环等待——**破坏任意一个即可**；工程上最常用的是**固定加锁顺序**（破坏循环等待）和**一次性申请**（破坏占有且等待）。

和并发侧的对应关系：协程是用户态调度（协作式，一处阻塞全体停摆），线程/进程是 OS 抢占式调度——**谁调度**这一条推出全部行为差异。

**分层要点**：
- **结论**：进程与线程都是 task_struct，差别在共享了什么；切换成本大头是间接的（TLB/缓存）。
- **推导链**：clone 标志 → 共享内容 → 通信 vs 隔离 → 切换的直接/间接成本 → 死锁四条件与破法 → 与协程的调度对照。
- **量化**：切换 1–5 μs（重载含间接成本 10–50 μs）；线程直接成本只比进程快约 20–30%。
- **边界与常见误解**："线程一定比进程快很多"×（直接成本只差 20–30%，差距在 TLB/缓存）；协程不是"更轻的线程"，是调度者不同。

**追问**（先说后看）

1. **线程切换和进程切换差在哪一步？** —— **只差"写 CR3 + TLB 失效"这一步**（跨进程），同进程的线程**整个跳过**。**直接成本只差两三成，但跨进程会让缓存与 TLB 冷掉**，并发高时这一部分能把成本推高一个数量级——**所以答案是"差在地址空间，不是差在寄存器"**。⚠️ **不要说"贵 19 倍"这种精确倍数**，测量值只能给区间。
2. **为什么线程不是越多越好？** —— 两个原因：**① 每线程内核侧约 25KB 且要占一个 pid（上限是 `pid_max` / `pids.max`）**；**② 超过核数后多出来的执行单元只在"等"或"抢"——抢就会推高非自愿切换，等就没有收益**。要按"每个单元的工作量 ÷ 切换成本"算。
3. **死锁的四个条件是什么、怎么破？** —— 互斥 / 持有并等待 / 不可剥夺 / 循环等待，**破任一个即可**；**首选固定加锁顺序破循环等待**（免费）；超时重试（破不可剥夺）有活锁与"重复副作用"的风险。
4. **`malloc` 之后不写会不会占内存？** —— **不会**。`malloc` 只拿到虚拟地址空间，**物理页在首次访问（缺页）时才分配**——这就是 overcommit 的机制（详见 [[母题-O2-虚拟内存与缺页]]）。
5. **容器里被 OOM 杀了，怎么看？** —— 要分清**两类 OOM**：**整机 OOM**（内核挑 `oom_score` 最高的）和 **cgroup OOM**（撞 `memory.max`）。**日志前缀不同**，排查方向也不同（详见 [[母题-O2-虚拟内存与缺页]] 第 5 节）。

**同类变体**

- 「Java 的虚拟线程 / Go 的 goroutine 和操作系统线程什么关系？」——**都是"用户态调度"这一族**：把"一个并发任务一个内核线程"改成"M 个内核线程上跑 N 个轻量任务"，**省掉的就是本卡第 3 节的内核侧 25KB 和 2.3 的切换成本**
- 「线程池该设多大？」——按负载定：**CPU 密集 ≈ 核数 + 1**；**IO 密集 ≈ 核数 ×（1 + 等待时间/计算时间）**——**后者就是 2.1 那张"时间花在哪"的账**（同 [[母题-N3-进程线程与协程]]）
- 「为什么 Redis / Nginx 单线程/少线程还能这么快？」——**IO 密集 + 事件循环**（[[母题-O3-IO模型与零拷贝]]），**它们要的并发不需要靠线程数换**
- 「`top` 里 `LOAD` 高但 CPU 不高是什么情况？」——**大量任务处于不可中断等待**（D 状态，通常在等磁盘 / NFS），**这是 IO 瓶颈而不是 CPU 瓶颈**
