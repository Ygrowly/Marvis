# 操作系统模块深挖卡

> 本卡是 [[模块深挖卡模板]] 的实战卡。**主线优先**：先看三条线，再落母题，题单只用来查漏。
> **定位**：这是**后端基本盘里唯一一个"底层"模块**——它不解决某个中间件的问题，它解释**上面所有模块为什么长成那样**。
> **与 [[网络基础模块卡]] 的分工**：N3（进程 / 线程 / 协程）讲的是**执行单元怎么选**；本卡讲**它们在操作系统内部到底花了什么**（一次切换做什么、地址空间怎么映射、IO 为什么慢）。**两边不重复：N3 是"选哪个"，本卡是"为什么有这个成本"。**
> **本轮只落 3 张母题**（CPU / 内存 / IO 各一张），其余在下面题单里排期。

## 0. 模块边界（先写这个，防无限扩张）

**包含**：**CPU 侧**（进程与线程在操作系统里的真实差别、一次上下文切换花了什么、调度器在做什么、共享地址空间带来的竞态与死锁）、**内存侧**（虚拟地址空间、页表、缺页、overcommit、OOM 归谁杀）、**IO 侧**（五种 IO 模型、`select/poll/epoll` 的就绪通知、零拷贝省掉的到底是什么）。

**明确不包含**：

- **内核源码**（调度器 `task_struct` 全字段、`fork()` 调用链、内存管理子系统实现）——只到"知道这个结构承担什么职责"
- **调度器算法调参**（CFS 的 `vruntime` 权重、实时调度策略的优先级）——校招几乎不问，只到"知道有哪几类策略、解决什么问题"
- **发行版运维**（`systemd` 单元、`sysctl` 调参、内核参数持久化）——归后续的「Linux 与部署」模块
- **协程 / 事件循环的选型与写法**——归 [[母题-N3-进程线程与协程]]，本卡只解释它底下的 `epoll` 与切换成本
- **TCP 协议细节**——归 [[母题-N1-一次请求的完整路径]]
- **数据库层的锁与死锁**——归 [[母题-M10-锁与死锁]]；本卡讲**内核层的锁与死锁**，并明确标出两者的同源与不同

**边界判据**：**本卡只回答"程序跑起来，CPU / 内存 / IO 这三样资源被谁怎么分配，出问题该怀疑哪一层、代价是多少"。** 凡是"某个框架 / 某个参数怎么调"的，不进本卡。

**一条必须先说清的认知**：**"操作系统"这个模块的面试价值不在名词，在"能算"。** 面试官问"进程和线程有什么区别"，想听的**不是背定义，而是"你知不知道这个差别在什么场景下会变成瓶颈"**——所以本卡的三张母题**全部落到一个算式上**（切换成本账 / 虚拟内存 vs 物理内存 / 拷贝次数与系统调用次数）。

## 2. 主线拆解（骨架：这个域在回答哪几个问题）

| # | 主线（它在回答什么问题） | 这条线的关键取舍 | 落几个母题 |
|---|---|---|---|
| 一 | **CPU 怎么决定先跑谁**：进程和线程到底差在哪、一次切换花了什么、为什么线程开多了反而更慢、共享地址空间带来的竞态与死锁 | 多开执行单元换并发度 vs 切换与缓存失效的成本；加锁保正确 vs 锁的粒度与死锁风险 | 1 |
| 二 | **内存为什么看起来够用**：8GB 的程序为什么能跑在 4GB 内存上、`malloc` 成功为什么还会 OOM、OOM 杀的是谁 | 虚拟地址空间（宽敞但会缺页）vs 物理内存（真实但有限）；overcommit（跑得动 vs 会崩） | 1 |
| 三 | **IO 为什么慢、内核能省掉什么**：一次 IO 的等待发生在哪、`epoll` 比 `select` 强在哪、零拷贝省掉的是哪几次拷贝 | 阻塞（简单但占线程）vs 多路复用（一个线程管很多连接）；拷贝次数 vs 代码可控性 | 1 |

**三条线的关系**：一是"谁在跑"，二是"它看到的内存是什么"，三是"它在等 IO 时干什么"。**这三条合起来正好解释了一个高并发服务端的三笔主要成本：切换、内存、IO。**

**为什么这个模块必须最先补**：9.9 实测最低分是「计算机基础」（12.4）。而**上面所有模块的追问最终都会落到这里**——为什么 Redis 单线程还快（IO 密集 + 事件循环）、为什么 Kafka 用零拷贝（省掉 2 次拷贝）、为什么 MySQL 的连接不能无限开（每连接一个线程 → 内核栈 + 切换成本）、为什么容器里的 Java 会被 OOM 杀（cgroup 限制 + `oom_score`）。**这是唯一一个能"反向解释整个后端基本盘"的模块。**

## 5. 项目映射（三个项目逐个过）

> 素材来源：`projects/` 下的项目说明与编号手册。**这里每一句都要能指回原文**，不许编。

### 5.1 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**服务端是"受控并发"的活教材**——当前规模明确用 PostgreSQL 任务表 + APScheduler + 批处理 + **受控并发**，而不是无限开线程/协程。这里 O1 的切换成本账就是"受控"两个字的依据：**并发单元不是越多越好，过了拐点总吞吐反而下降**。
- 解决什么问题：**任务中断后的恢复**——服务重启后扫描最近七天缺口、**限定窗口、分批、低优先级**回补（`02-aggregation-and-recovery.md`）。**"低优先级"这个设计就是因为它要和实时任务争同一批 CPU 和数据库连接**——这是调度与资源竞争在业务层的投影。
- 踩过的坑：**把 Checkpoint 当成"业务完成证明"**——Checkpoint 是恢复线索，不是事实。**这在操作系统层面的对应是"进程崩溃后内存状态全丢，只有落盘的东西算数"**（`07-task-lifecycle-and-delivery.md`）。
- 决策与取舍：**并发度是配出来的、不是开出来的**——受控并发 + 并发配额限流，而不是"有多少任务就起多少执行单元"（O1 的量化判据）。

- 对应母题：【O1、O3】

### 5.2 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**一次问数请求的绝大部分时间是 IO 等待**——SQL 要发给 DuckDB / PostgreSQL 执行、结果集要从对象存储读回来。所以服务端该用异步（[[母题-N3-进程线程与协程]] 的判据），而**这张卡要补的是"等待时线程在操作系统里处于什么状态"**：它被换下 CPU、进等待队列，**换下去和换回来都要付 O1 的切换成本**——这就是"IO 密集时别用线程池硬扛"的底层原因。
- 解决什么问题：**硬超时与取消**——项目里明确要求"超时、行数、扫描量、并发、取消能力"（`07-权限安全与生产隔离.md`）。**"取消"在操作系统层面不是免费的**：把取消传下去 = 让还在内核里等待的线程退出等待，这需要能中断阻塞的系统调用（O3 的 IO 模型）。
- 踩过的坑：**超时设了一层就以为够了**——外层和内层同时放弃时无法归因（此坑在 [[母题-N1-一次请求的完整路径]] 已记）；这里补一句：**超时的实现依赖"能中断阻塞调用"，否则超时只是标记，线程还挂在原地。**
- 决策与取舍：**并发靠配额而不是靠机器**——按租户限制并发和队列、超预算拒绝或缩小范围。**这是"资源有限"这个前提在应用层的直接落地**（O1 的并发拐点、O2 的内存上限）。

- 对应母题：【O1、O3】

### 5.3 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**这是本模块的主证据。** 架构是 **PostgreSQL 权威状态 + Redis/ARQ 队列 + Worker 进程**，任务长、**进程随时可能崩**（`06-architecture-and-scenarios.md`、`04-idempotency-and-recovery.md` §9）。**"进程随时崩"这件事在操作系统层面就是 O1 的进程模型**——地址空间独立、崩溃不传染（优点），但**内存里的所有状态全丢**（代价，所以状态必须落在数据库里）。
- 解决什么问题：**Worker 重启后的状态重建**——Worker 起来先读 AttackRun 和最后一个 Receipt，再校准 Checkpoint。**这正对应"进程 = 独立地址空间 + 内存态不持久"这条底层事实**：重启等于内存清零，所以能恢复的只有落盘的部分。
- 踩过的坑：**容器内存限制**——`08-capacity-cost-and-facts.md` 给 Redis 只配 256~512MB，意味着**这个容器是被 cgroup 限制的**。一旦超限，**cgroup 级 OOM 会杀容器内的进程**（不是整机 OOM）。**不区分这两种 OOM，排查方向会完全错**（O2 第 5 节的判据）。
- 决策与取舍：**队列可以丢或重投，业务正确性落在可恢复的权威数据库里**——**这句话的底层理由就是"进程内存不可信、只有持久化状态可信"**。它把"进程会崩"当作设计前提，而不是异常。

- 对应母题：【O1、O2】

- **2026-09-16**：[[母题-N3-进程线程与协程]] 与 `site/figures/concurrency-models.svg` 里"线程栈约 1MB"、"10 万并发线程约 100GB"**不准确**。按 `pthread_create(3)` man-page：Linux 上**新线程的默认栈大小由 `RLIMIT_STACK`（`ulimit -s`，默认 8192KB = 8MB）决定**，x86-32 才是 2MB；而且它**是虚拟地址空间预留、按需提交**，真正持续占用的是内核侧约 **25KB（16KB 内核栈 + ~9KB `task_struct`）**，且**不计入 RSS**。已按此修正母题卡与配图（详见 [[母题-O1-上下文切换与死锁]] 第 2 节）。
