## 一、教材

### 1. 前提：一次 IO 其实分两段

#### 1.1 两段成本【事实】

【推导】**一次网络读取，钱花在两个地方**：

```
第一步：等数据到达
  网卡收包 → DMA 写入内核的 socket 缓冲区
  ★ 这一段时间，应用线程在【等】——它插不上手

第二步：把数据搬给应用
  应用调用 read() → 内核把数据从【内核缓冲区】拷贝到【用户缓冲区】
  ★ 这一次拷贝是 CPU 干的，而且应用必须等它做完
```

【推导】**这个"两段"的分法非常重要，因为几乎所有 IO 概念都在说"我改造了哪一段"**：

| 概念 | 它改造的是哪一段 |
|---|---|
| **阻塞 IO** | 两段都等（最简单，一个连接一个线程） |
| **非阻塞 IO** | 第一段不等（但要**反复问**——把"等"变成了"轮询"） |
| **IO 多路复用** | **第一段不再"一个连接一个线程地等"，而是"一个线程等很多个"** |
| **异步 IO** | **第二段也不等**（内核拷完再通知你） |

【推导】**记住这张表，五道 IO 模型题就都变成了"你说的是哪一段"。**

#### 1.2 为什么"一个连接一个线程"不可行【推导】

【推导】**先算一遍这个账**（这也直接回答了本卡的第一个问题）：

```
10000 个连接，一个连接一个线程：
  内核侧：25KB × 10000 = 250 MB     （[[母题-O1-上下文切换与死锁]] 3.2）
  用户栈：8MB 虚拟 × 10000 = 80 GB 虚拟（按需提交，物理约 80 MB）
  更贵的：这 10000 个线程大部分时间在【等】，但它们是【内核调度的实体】
          → 内核要维护 10000 个等待上下文
          → 数据来了要唤醒对应的线程（每次唤醒两次切换）
          → 线程数和连接数绑死，扩不动
```

【推导】**而"一个线程等 10000 个连接"怎么做得到**：靠**内核提供一个"一次问一批"的能力**——**这就是 IO 多路复用的全部内容**。

**到这里你应该能回答**：为什么"IO 多路复用"要解决的问题是"连接数 vs 线程数"的解耦？

### 2. 五种 IO 模型：用同一把尺子排队

#### 2.1 先用"两段"把五个模型排好【事实】

**先各自介绍，再用同一指标比较**（指标 = 两段里哪些要应用等）：

| 模型 | 第一段（等就绪） | 第二段（拷贝） | 一句话 |
|---|---|---|---|
| **① 阻塞 IO** | **等**（线程睡着） | **等** | 一个连接一个线程，简单但扩不动 |
| **② 非阻塞 IO** | **不等**，立即返回 `EAGAIN` | **等** | 要**自己反复轮询**——"不等"变成了"一直问"，**更浪费 CPU** |
| **③ IO 多路复用** | **等**，但**一次等一批** | **等** | `select` / `poll` / `epoll`——**这是本节的主角** |
| **④ 信号驱动 IO** | **不等**（内核发 `SIGIO` 通知） | **等** | 实际很少用（信号处理麻烦） |
| **⑤ 异步 IO** | **不等** | **不等**（内核拷完再通知） | `io_uring` / POSIX AIO |

【事实】**必须讲清一个概念**：**"同步 / 异步"的准确判据是第二段**——

> **内核把数据从内核缓冲区拷贝到用户缓冲区这一步，是不是由内核在应用线程之外完成（完成后再通知应用）？**
> **是 → 异步 IO；不是 → 同步 IO。**

【推导】**按这个判据，前四个（包括 IO 多路复用）都是"同步 IO"**——因为 `epoll_wait` 通知你"连接可读了"之后，**你调 `read()` 时仍然要阻塞在"拷贝"那一段上**。

【纠错】**所以"`epoll` 是异步 IO"这个说法是错的**（很常见的混淆）。**`epoll` 是"多路复用"——它让一个线程能同时等很多连接，但拷贝那段还是你自己等。**

#### 2.2 IO 多路复用要解决的三个问题【推导】

【推导】一个"一次问一批"的机制必须回答三件事，**而三个版本的差别正好就是"它们怎么回答这三件事"**：

| 问题 | 含义 |
|---|---|
| **怎么表示"我在等哪些 fd"** | 数据结构 |
| **谁来发现"哪些就绪了"** | 内核轮询 vs 内核回调 |
| **怎么把结果告诉应用** | 返回什么、要拷多少、应用要不要再筛一遍 |

**到这里你应该能回答**：为什么"非阻塞 IO"比"阻塞 IO"更费 CPU，它到底解决了什么？

### 3. `select` → `poll` → `epoll`：优势是算出来的

#### 3.1 三个版本各自是什么【事实】

::figure os-io-models.svg | 五种 IO 模型的两段观与 epoll 的内部结构 | 上半：两段成本与五个模型各自改造哪一段；下半：interest list / ready list 与 O(n) vs O(k)

**`select`（最老）**

- **怎么表示**：`fd_set` —— 一个**位图**，每一位代表一个 fd
- **限制**：位图大小固定为 `FD_SETSIZE`，**通常 1024** → **超过 1024 的 fd 根本表示不了**
- **谁发现就绪**：内核**遍历**整个集合
- **怎么返回**：只返回"有几个就绪"，**应用必须自己把整个集合再遍历一遍**才知道是哪些
- **成本**：`O(n)`，n = 监控的 fd 总数

**`poll`（改进版）**

- **怎么表示**：`pollfd` **数组**（每个元素带 fd + 关注的事件）
- **限制**：**没有 1024 这种硬上限**（受内存与 `RLIMIT_NOFILE` 限制）
- **其余**：仍然**每次调用把整个数组拷进内核**、内核仍遍历、返回后应用仍要遍历
- **成本**：**仍然 `O(n)`**

【推导】**`poll` 只解决了"数量上限"这一个问题，没解决"每次都白遍历一遍"这个更贵的问题。**

**`epoll`（Linux 专用，2.6+）**

【事实】**按 man-page 原文，`epoll` 在内核里的核心是"两个列表"**：

```
interest list（关注列表）—— 我注册了要监控哪些 fd
ready list（就绪列表）—— 其中【已经就绪】的那些
```

- **`epoll_create`**：创建一个 epoll 实例
- **`epoll_ctl`**：注册 / 修改 / 删除关注 —— **列表只在此时拷进内核，之后不再重复拷**
- **`epoll_wait`**：**从就绪列表里取事件** —— man-page 原话是 *fetching items from the ready list*

【事实】**这里有一个必须纠正的流行错说法**：

> ❌ "`epoll` 用 `mmap` 共享内存，所以是零拷贝。"

**错。** man-page 说得清楚：interest list 和 ready list 都是**内核态的数据结构**，`epoll_wait` 是把就绪事件**拷到用户提供的数组**里（`maxevents` 就限定了这次最多拷几个）。**`epoll` 省的从来不是"拷贝"，而是两笔更贵的账**：

| `epoll` 省掉的 | 怎么省的 |
|---|---|
| **每次调用都拷整个 fd 集合** | 只在 `epoll_ctl` 时拷一次 |
| **每次调用都遍历全部 fd** | 内核用**回调**把就绪的 fd 打进 ready list，`epoll_wait` **只取就绪的那些** |

【推导】**所以准确说法是**：*`epoll` 的工作量只和"就绪数"有关，和"监控总数"无关。*

#### 3.2 量化：O(n) 和 O(k) 差多少【推导】

【推导】**用同一个场景算一遍**（自测 Q1 会完整算）：

```
场景：10000 个连接被监控，每秒有 1000 次"有事件发生"的时刻，每次平均 10 个连接就绪

用 poll：每次调用要处理全部 10000 个 fd
  1000 次/秒 × 10000 = 10,000,000 次检查/秒
  ★ 而这个数字会随连接数【线性增长】——连接翻倍，开销翻倍

用 epoll：每次调用只处理就绪的那些
  1000 次/秒 × 10 = 10,000 次/秒
  ★ 这个数字与【监控的连接总数无关】——连接从 10000 涨到 10 万，它不变
```

**差 1000 倍**，而且**差距随连接数拉大**——**这就是"`epoll` 是 O(1)"这句话的正确含义**：**不是"开销为零"，是"开销与监控总数无关"。**

【事实】**`select` 在这里连参赛资格都没有**：10000 个连接**超过了 `FD_SETSIZE`（1024）**，用它根本表示不了。

#### 3.3 水平触发与边缘触发【事实】

【事实】这是 `epoll` 的两种通知模式，**理解的关键是"通知的时机"**：

| 模式 | 什么时候通知 | 编程要求 |
|---|---|---|
| **水平触发（LT，默认）** | **只要还有数据可读，就反复通知** | 简单——**没读完下次还会告诉你** |
| **边缘触发（ET）** | **只在状态变化时通知一次** | **必须配非阻塞 fd，并且一直读到 `EAGAIN`**——否则剩下的数据**永远不会再通知你** |

【推导】**LT 更安全、ET 更省**：

```
LT：可能被"反复通知同一个 fd"浪费一些系统调用，但【不会漏】
ET：通知次数最少，但【依赖你把数据读干净】——漏了就卡死
```

【事实】**man-page 的推荐用法很明确**：用 ET 就**必须**（1）设非阻塞 fd，（2）**只在 `read()` 返回 `EAGAIN` 之后才回去等事件**。另外 `EPOLLONESHOT` 可以让一个 fd 通知一次后自动失效，避免多线程下的重复唤醒（惊群）。

**到这里你应该能回答**：为什么说"`epoll` 是 O(1)"而不说"`epoll` 更快"？

### 4. 零拷贝：省掉的是哪几次拷贝

#### 4.1 传统 `read` + `write` 的账【事实】

【事实】**把一个大文件从磁盘发到网络，传统写法要拷 4 次**：

```
① 磁盘 → 内核页缓存          （DMA 拷贝，硬件做）
② 内核页缓存 → 用户缓冲区    （★ CPU 拷贝）  ← read()
③ 用户缓冲区 → socket 缓冲区 （★ CPU 拷贝）  ← write()
④ socket 缓冲区 → 网卡        （DMA 拷贝，硬件做）

合计：4 次拷贝（2 次 DMA + 【2 次 CPU】）、2 次系统调用、4 次用户/内核态切换
```

【推导】**看清楚浪费在哪里**：数据从内核 → 用户 → 又回内核，**而应用程序很可能一个字都没看**（比如 Nginx 发静态文件、Kafka 把消息发给消费者）。**这就像快递员把包裹从仓库搬到你的办公桌，你看都没看就说"发货"，他又搬回仓库——两次搬运完全是白干。**

#### 4.2 `sendfile`：从 4 次降到 2 次（甚至 0 次 CPU 拷贝）【事实】

【事实】`sendfile(out_fd, in_fd, offset, count)` **一个系统调用直接把文件发到 socket**：

```
① 磁盘 → 内核页缓存            （DMA）
② 页缓存 → socket 缓冲区       （拷贝，但【全程在核内，不进用户态】）
③ socket 缓冲区 → 网卡          （DMA）

合计：2 次拷贝（0 次 CPU 参与、2 次 DMA）、1 次系统调用、2 次态切换
★ 数据从头到尾【没有进过用户态】
```

【事实】**还有更强的版本**：如果**网卡支持 SG-DMA**（Scatter-Gather DMA，即网卡能直接按描述符从内存里散读），那么第 ② 步可以退化成"**只传递一个描述符（数据在哪、多长）**"——

```
① 磁盘 → 内核页缓存                    （DMA）
② 把【描述符】交给网卡，网卡直接从页缓存读走（DMA 直接从页缓存取）
→ 【一次 DMA 拷贝 + 一次描述符传递】，真正意义上的"零 CPU 拷贝"
```

【事实】**两个必须知道的限制**（Linux 上）：

- `in_fd` 必须是**可 mmap 的普通文件 / 块设备**（**不能是 socket**）
- `out_fd` 必须是 **socket**（**不能拿它来拷两个普通文件**——那是 `copy_file_range` 的事）

#### 4.3 `mmap` + `write`：另一种零拷贝（3 次拷贝）【事实】

【事实】**`mmap` 走的是另一条路**：

```
① 磁盘 → 内核页缓存                （DMA）
   mmap：把页缓存【映射】进用户地址空间 —— 应用直接"看到"页缓存，
         【省掉了"内核→用户"的那次拷贝】
② 用户写入 socket 缓冲区时，还是要拷一次 （★ CPU 拷贝）
   → 所以总共 3 次拷贝
```

【推导】**比 `sendfile` 多一次 CPU 拷贝，那它为什么存在**：

| | `sendfile` | `mmap` + `write` |
|---|---|---|
| 拷贝次数 | **2**（理想情况 1） | 3 |
| 应用能不能处理数据 | ❌ **不能**（数据不进用户态） | ✅ **能**（应用看得到页缓存） |
| 典型用户 | **Kafka** | **RocketMQ** |

【推导】**所以"谁更零拷贝"的答案是**：*`sendfile` 省得更多，但代价是应用碰不到数据；`mmap` 多一次拷贝，换来的是应用能在发送前处理数据。* **Kafka 不需要改消息内容 → 用 `sendfile`；RocketMQ 需要处理（比如按 ConsumeQueue 组织）→ 用 `mmap`。** 这是**同一个目标下的两种权衡**，不是"谁更先进"。

#### 4.4 量化的收益【推导】

【推导】**零拷贝的收益随"并发连接数"放大**（自测 Q2 会算）：

```
发 1GB 文件：
  传统方式：2 次 CPU 拷贝 = 2GB 内存流量
  sendfile：0 次 CPU 拷贝
→ 单连接就省 2GB 的内存带宽

如果是 1000 个并发连接同时发：
  省下的 CPU 拷贝流量 = 2GB × 1000 = 2 TB
→ 按 20 GB/s 内存带宽算，相当于省掉约 100 秒的纯内存搬运
```

【推导】**这就是为什么"零拷贝"是高吞吐服务的标配**：**省的不是"拷贝"这个动作，是"每个连接的拷贝 × 连接数"这个乘积。**

#### 4.5 更上一层：减少系统调用的次数【推导】

【推导】**顺着"省拷贝"再往前一步**：**系统调用本身也不便宜**（约 105 ns 一次，[[母题-O1-上下文切换与死锁]] 4.4）。所以真正现代的优化方向是**"批量化"**：

```
100 万次 IO 操作/秒，每次都一次系统调用：
  1,000,000 × 105 ns ≈ 0.105 秒/秒 ≈ 【0.105 个核】光花在"跨越边界"上

用 io_uring（提交队列 + 完成队列）批量化，深度 128：
  1,000,000 / 128 ≈ 7,812 次提交/秒
  → ≈ 0.0008 个核  ← 省掉约 99%
```

【推导】**注意这里"省"的性质**：**工作本身一点没变便宜，只是"跨越"的次数少了 128 倍。** 这和 [[母题-O1-上下文切换与死锁]] 的结论是同一条：**优化方向是"让系统调用更少"，而不是"让系统调用更快"。**

**到这里你应该能回答**：为什么"零拷贝"的同时还要关心"系统调用次数"？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "`epoll` 是异步 IO" | 【推导】**不是**。`epoll_wait` 通知你"可读了"之后，**你调 `read()` 时仍要阻塞在"内核→用户"的拷贝上**。按 POSIX 的判据，**它属于同步 IO**；"异步"要看**拷贝那一段是否由内核在应用线程之外完成** |
| "`epoll` 用 `mmap` 共享内存实现零拷贝" | 【事实】**错**（man-page 可查）。interest list 和 ready list **都在内核态**，`epoll_wait` 要把就绪事件**拷回**用户数组。**它省的是"每次拷整个 fd 集合"和"每次遍历全部 fd"，不是拷贝本身** |
| "`epoll` 比 `select` 快" | 【推导】**要说得更准**：`epoll` 的**每次调用工作量只与就绪数有关（O(k)），与监控总数无关**；`select`/`poll` 是 **O(n)**。**连接少的时候两者差不多**，优势在连接多的时候才显现 |
| "`select` 能监控 1024 个 fd，`poll` 无限" | 【事实】`select` 的上限是 **`FD_SETSIZE`，通常 1024**；`poll` 没有这个硬上限，但**受内存与 `RLIMIT_NOFILE` 限制**，**而且仍然是 O(n)** |
| "ET 比 LT 高级，应该都用 ET" | 【取舍】ET **要求非阻塞 + 一直读到 `EAGAIN`**，**漏读就会永久卡住**。LT 更安全、ET 更省——**没有"哪个更好"，只有"你能不能保证把数据读干净"** |
| "零拷贝就是一次拷贝都没有" | 【事实】**"零"指的是"零 CPU 拷贝"**。DMA 拷贝还在（那是硬件做的，不占 CPU）——所以准确说法是"**数据不再经过用户态、CPU 不参与搬运**" |
| "`sendfile` 什么场景都能用" | 【事实】**Linux 上限制很明确**：`in_fd` 必须是可 mmap 的普通文件，**`out_fd` 必须是 socket**。**不能用它拷两个普通文件** |
| "`mmap` 一定比 `sendfile` 好/差" | 【取舍】**用途不同**：`sendfile` 省得更多但应用碰不到数据；`mmap` 多一次拷贝但**应用能处理数据**。Kafka 选前者、RocketMQ 选后者，各自贴合需求 |
| "多路复用可以让单线程跑满多核" | 【事实】**不能**。多路复用只是让**一个线程能等很多连接**，**它仍然跑在一个核上**。要多核得靠多进程 / 多线程（[[母题-N3-进程线程与协程]]：Nginx 是多 worker 单线程，Redis 主线程单线程） |
| "一个连接一个线程就够用了" | 【推导】**连接数一大就崩**：10000 连接 → 内核侧 250MB、10000 个被调度的实体、唤醒时的切换开销。**这是"连接数和线程数必须解耦"的量化理由** |

## 二、自测

**Q1（计算）**：某服务要同时监控 **10000 个连接**，每秒有 **1000 次**"有事件可处理"的时刻，每次平均只有 **10 个连接**就绪。

问：① `select` 能用吗？② 用 `poll` 每秒要做多少次 fd 检查？③ 用 `epoll` 呢？④ 如果连接数涨到 10 万，两者的开销各怎么变？

**A1**：

① **不能用**（至少不能直接表示）：`select` 用 `fd_set` 位图，上限是 **`FD_SETSIZE`，通常 1024**。10000 个连接**超过了这个硬上限**——**这一条就足以淘汰 `select`**。

② `poll`：

```
每次调用要遍历全部 10000 个 fd
1000 次/秒 × 10000 = 【每秒 1000 万次】fd 检查
```

③ `epoll`：

```
每次 epoll_wait 只处理就绪的那些（10 个）
1000 次/秒 × 10 = 【每秒 1 万次】
→ 比 poll 少 1000 倍
```

④ 连接数涨到 10 万：

| | 10000 连接 | 100000 连接 | 变化 |
|---|---|---|---|
| `poll` | 1000 万次/秒 | **1 亿次/秒** | **线性增长 10 倍** |
| `epoll` | 1 万次/秒 | **1 万次/秒** | **不变** |

【这一步在验证什么】验证 3.2 的结论：**`epoll` 的"O(1)"指的是"每次调用的工作量与监控总数无关"，而不是"开销为零"。**

**这里有一个可以加分的话**：*`epoll` 的优势不是"常数时间"，而是"**把复杂度从"连接数"解耦到了"活跃连接数"**——**在"连接多但活跃少"的场景（长连接、推送、IM）里收益最大**；如果所有连接都一直活跃，`epoll` 和 `poll` 的差距就没那么大了。*

**Q2（计算）**：一台服务器要做文件下载服务。单文件 **1GB**，平均并发 **1000 个连接**同时在下载。

问：① 用传统 `read` + `write`，CPU 每次要搬多少数据（只看单连接）？② 用 `sendfile` 呢？③ 1000 并发下，两者差的"CPU 拷贝流量"是多少？按内存带宽 **20 GB/s** 算，相当于省了多少时间？

**A2**：

```
① 传统 read + write：2 次 CPU 拷贝
   1GB × 2 = 【2 GB】的 CPU 搬运（每连接）

② sendfile：
   CPU 拷贝 = 【0】次（数据从磁盘 DMA 到页缓存，再由 DMA 到网卡，
   全程不进用户态）→ CPU 只负责发描述符

③ 1000 并发：
   传统方式 CPU 拷贝总量 = 2GB × 1000 = 【2 TB】
   sendfile            = 0
   省下 2 TB 的内存搬运
   按 20 GB/s 内存带宽：2 TB / 20 GB/s = 【约 100 秒】
   → 相当于省掉了 100 秒【纯内存搬运】的 CPU 时间
```

【这一步在验证什么】验证 4.4 的结论：**零拷贝的收益是"每次拷贝 × 连接数"的乘积**——**并发越高，收益越大**。

**这里还有一个必须说对的细节**：**"零拷贝"不等于"没有拷贝"**。DMA 拷贝仍然发生两次（磁盘→页缓存、页缓存/缓冲区→网卡），**只是不占 CPU**。所以准确说法是"**数据不再经过用户态、CPU 不参与搬运**"。

**Q3（计算）**：某服务每秒要做 **100 万次**小的 IO 操作，每次都调用一次系统调用。已知一次系统调用跨越约 **105 ns**。

问：① 光"跨越边界"消耗多少 CPU？② 用批量提交（比如 `io_uring`，提交深度 128）能降到多少？③ 这说明什么？

**A3**：

```
① 1,000,000 × 105 ns = 0.105 秒/秒 ≈ 【0.105 个核】
   → 一个核的 10.5% 全花在"进出内核"上，一点活没干

② 批量化后，每 128 个操作只提交一次：
   1,000,000 / 128 ≈ 7,812 次提交/秒
   7,812 × 105 ns ≈ 0.00082 秒/秒 ≈ 【0.0008 个核】
   省掉约 99.2%
   ★ 注意：操作本身的工作量【一点没变】，变的只是"跨越次数"
```

③ **说明"优化系统调用"的正确方向是减少次数，而不是让单次更快**：

```
单次系统调用 105 ns 已经很难再压（涉及硬件特权级切换）
→ 能动的只有【怎么把 100 万次变成 7812 次】
→ 手段：批量（io_uring 的提交队列）、合并（一次读大块）、缓存（少调）
```

【这一步在验证什么】验证 4.5 与 [[母题-O1-上下文切换与死锁]] 4.4 的同一条判据：**"边界跨越"的成本靠"次数"而不是"单价"优化。**

**Q4（纠错）**：下面这段话哪里错了？

> "`epoll` 之所以快，是因为它用了 mmap 把内核的 fd 集合共享给用户态，避免了每次系统调用的数据拷贝，实现了零拷贝。"

**A4**：**核心机制说错了——`epoll` 从来不是靠 mmap 共享内存。**

**按 `epoll(7)` man-page 的原文**，`epoll` 在内核里的核心是**两个内核态结构**：

```
interest list（关注列表）—— 已注册要监控的 fd
ready list（就绪列表）   —— 其中已经就绪的那些
```

- **注册只在 `epoll_ctl` 时发生**——**此时拷一次**，之后不再重复拷
- **`epoll_wait` 是从 ready list 取事件**，man-page 原话是 *fetching items from the ready list*；取出来的事件**要拷到你提供的用户态数组**里（`maxevents` 就限定了这次最多取几个）

**所以"零拷贝"这个说法不成立**——`epoll_wait` 确实在拷（只是**只拷就绪的那几个**）。

**`epoll` 真正省掉的是两笔更贵的账**：

| 省掉的 | `select` / `poll` | `epoll` |
|---|---|---|
| **每次调用拷整个 fd 集合** | 每次调用都拷 | **只在注册时拷一次** |
| **每次调用遍历全部 fd** | 每次 `O(n)` 遍历 | 内核用**回调**把就绪 fd 打进 ready list，**`O(就绪数)`** |

**准确说法**：*`epoll` 快的根本原因是「把"每次主动遍历全部 fd"换成了"内核回调填就绪列表"」——工作量从 O(监控总数) 变成 O(就绪数)。跟 mmap 无关；`epoll_wait` 仍然要把就绪事件拷回用户态。*

**Q5（纠错）**：下面这段话哪里错了？

> "`epoll` 就是异步 IO，用它就能让单线程跑满多核，所以 Nginx 和 Redis 才那么快。"

**A5**：**三处都错。**

**① "`epoll` 是异步 IO"错了。** 判据是**第二段**（内核把数据从内核缓冲区拷到用户缓冲区）**是不是由内核在应用线程之外完成**：

```
epoll_wait 通知"可读了" → 你调 read() → 【仍然要阻塞在"拷贝"上】
→ 拷贝这一段还是你自己等
→ 按 POSIX 的定义，epoll 属于【同步 IO】（多路复用）
```

**真正的异步 IO**（`io_uring` / POSIX AIO）是**提交一个读请求，内核把"等 + 拷"都做完后通知你**——那时你拿到的已经是"数据在缓冲区里了"。

**② "让单线程跑满多核"错了。** **多路复用解决的是"一个线程能等很多连接"，不是"一个线程能用多个核"**：

```
多路复用 → 连接数与线程数解耦（10000 连接不用 10000 个线程）
但它仍然跑在【一个核】上
→ 要多核仍然要【多进程 / 多线程】
```

**事实也正是这样**：**Nginx 是多 worker 进程、每个 worker 单线程**；**Redis 是主线程单线程**（还另起了后台线程做落盘等杂事）。**"单线程"是"每个 worker/主线程单线程"，不是"整个服务一个线程"。** 这句话说错，就暴露了没看清架构。

**③ "所以那么快"的归因也太单薄。** `epoll` 只是**其中一环**，完整的账是：

| 原因 | 对应母题 |
|---|---|
| **IO 密集 + 多路复用**（等待时间被利用起来） | 本卡 2.1 / 3.2 |
| **内存态 + 少切换**（Redis 全在内存里，几乎没有磁盘等待） | [[母题-R1-Redis数据结构与选型]] |
| **单个操作快**（数据结构与实现极简，如 epoll 回调） | 本卡 3.1 |
| **没有额外的序列化 / 并发控制开销**（单线程天然无锁） | [[母题-O1-上下文切换与死锁]] 4.1 |

**准确说法**：*`epoll` 是多路复用（属同步 IO），作用是把连接数和线程数解耦、让一个线程能等上万连接；它不提供多核能力。Nginx 靠多 worker 进程、Redis 靠主线程单线程 + 全内存，快是多条原因的组合。*

## 三、面试输出（学完再看）

**一句话结论**：**一次 IO 分两段——"等就绪"和"拷到用户态"**，**IO 多路复用只改造第一段**（让一个线程能一次等一批连接，把**连接数与线程数解耦**：10000 连接不需要 10000 个线程，后者光内核侧就要 250MB 且都是被调度的实体）。`select` 的上限是 **`FD_SETSIZE`（通常 1024）**、和 `poll` 一样**每次调用都要拷整个集合并遍历全部 fd（O(n)）**；**`epoll` 在内核里维护 interest list 和 ready list，注册只在 `epoll_ctl` 时拷一次，`epoll_wait` 只取就绪的那些（O(就绪数)）**——**所以"O(1)"的准确含义是"每次调用的工作量与监控总数无关"**（10000 连接 1000 次/秒唤醒下，`poll` 每秒 1000 万次检查，`epoll` 只要 1 万次）。**零拷贝省掉的是 CPU 拷贝次数**：传统 `read`+`write` 要 **4 次拷贝（2 次 CPU + 2 次 DMA）**、`sendfile` 降到 **2 次（0 次 CPU，数据不进用户态）**、`mmap`+`write` 是 **3 次**（多一次拷贝换"应用能处理数据"，RocketMQ 选它、Kafka 选 `sendfile`）。**而且按 POSIX 判据，`epoll` 属于同步 IO——拷贝那一段仍要应用自己等。**

**恢复关键词**：IO 两段（等就绪 / 拷到用户态）/ **多路复用只改第一段** / 一万连接一线程 → 250MB 内核侧 + 唤醒切换 / 五种模型 = 两段里谁在等 / **同步 vs 异步看第二段谁做**（所以 epoll 是同步 IO）/ `select` FD_SETSIZE 1024 且 O(n) / `poll` 无上限但仍 O(n) / **`epoll` = interest list + ready list，`epoll_ctl` 拷一次，`epoll_wait` 取就绪** / **O(1) = 与监控总数无关** / LT 安全、ET 省但要读到 `EAGAIN` / **零拷贝 = 零 CPU 拷贝，DMA 还在** / 4 次 → 2 次（sendfile）→ 3 次（mmap）/ `sendfile` 数据不进用户态 / **Kafka=sendfile、RocketMQ=mmap** / 系统调用 105 ns，优化靠**减少次数**（io_uring 深度 128 省 99%）

**核心不变量 / 主线**：
**IO 的每一层优化都在回答同一个问题："哪一段等待或搬运是可以省掉的？"** 多路复用省掉"一个连接一个线程的等待"（连接数与线程数解耦）；`epoll` 省掉"每次遍历全部 fd"（O(n) → O(就绪数)）；零拷贝省掉"数据进用户态又出来"（2 次 CPU 拷贝 → 0）；批量化省掉"每个操作一次边界跨越"。**四件事的方向完全一致：把"与规模成正比的固定开销"变成"与活跃度成正比"。**

**完整回答骨架**：先给"两段成本"这把尺子 → 五种模型各自改造哪一段（含同步/异步的准确判据）→ 为什么"一个连接一个线程"不可行（算一遍）→ `select` / `poll` / `epoll` 的表示 / 发现 / 返回三问 → **量化 O(n) vs O(k)** → LT / ET 的取舍 → 零拷贝：4 次 → 2 次 → 3 次的账 → `sendfile` vs `mmap` 的取舍（Kafka / RocketMQ）→ 收益随并发放大 → 再往上一层：减少系统调用次数 → 边界与误解

**完整回答（口述稿）**：
**一次 IO 分两段——"等就绪"和"拷到用户态"**；**IO 多路复用只改造第一段**——让一个线程能一次等一批连接，把**连接数与线程数解耦**：10000 连接不需要 10000 个线程（后者光内核侧就要约 250MB，且都是被调度的实体）。

三代机制的差别：`select` 上限是 **`FD_SETSIZE`（通常 1024）**，和 `poll` 一样**每次调用都要拷整个集合并遍历全部 fd（O(n)）**；**`epoll` 在内核里维护 interest list 和 ready list**，注册只在 `epoll_ctl` 时拷一次，**`epoll_wait` 只取就绪的那些（O(就绪数)）**。

**零拷贝改造的是第二段**：`sendfile` / `mmap` 让数据不绕用户态，减少一次拷贝与一次上下文切换——Kafka 快的原因之一就是它。

和上层呼应：**asyncio 能扛大量连接**正是靠 epoll（一次问出哪些就绪）+ 协程单位开销小两个数量级（约 2KB vs 线程内核侧约 25KB）。

**分层要点**：
- **结论**：多路复用改造"等就绪"，零拷贝改造"拷数据"；epoll 是 O(就绪数)。
- **推导链**：IO 两段 → 连接数与线程数解耦 → select/poll 的 O(n) 与 epoll 的就绪列表 → 零拷贝 → 上层 asyncio 的解释。
- **量化**：10000 线程光内核侧约 250MB；`FD_SETSIZE` 通常 1024；协程约 2KB vs 线程内核侧约 25KB。
- **边界与常见误解**：多路复用不减少数据拷贝（那是零拷贝的活）；epoll 的代价是注册与回调模型更复杂。

**追问**（先说后看）

1. **`epoll` 为什么比 `select` 快？** —— **不是"常数时间"，是"复杂度与监控总数无关"**：`select`/`poll` 每次调用都要**把整个集拷进内核 + 遍历全部 fd（O(n)）**；`epoll` **注册只拷一次**，内核用**回调**把就绪 fd 放进 ready list，**`epoll_wait` 只取就绪的（O(就绪数)）**。**连接多、活跃少时优势最大。**
2. **`epoll` 是异步 IO 吗？** —— **不是**。通知"可读"之后，**`read()` 的拷贝那一段仍要应用等**，按 POSIX 判据属于**同步 IO**。真正异步的是 `io_uring` / POSIX AIO（等和拷都由内核做完再通知）。
3. **水平触发和边缘触发怎么选？** —— **LT 更安全**（没读完下次还会通知）；**ET 通知更少但要求非阻塞 + 一直读到 `EAGAIN`**，**漏读会永久卡住**。用 ET 时 man-page 明确要求"**只在 `read()` 返回 `EAGAIN` 之后才回去等事件**"。
4. **零拷贝到底省了什么？** —— **省的是 CPU 拷贝次数**：传统 4 次拷贝里有 2 次是 CPU 干的（内核→用户、用户→socket），`sendfile` 把这两次全省掉（**数据不进用户态**）；`mmap` 只省一次（留在页缓存里，应用可直接访问，但写 socket 时还要拷）。**DMA 那两次仍然存在，只是不占 CPU。**
5. **Kafka 为什么比 RocketMQ 更"零拷贝"？** —— **Kafka 用 `sendfile`**（2 次拷贝，数据不进用户态）；**RocketMQ 用 `mmap` + `write`**（3 次，**多一次拷贝换来应用能处理数据**）。**这不是谁更先进，是各自的取舍**：Kafka 只转发不需要改内容，RocketMQ 需要按自己的存储结构组织。
6. **多路复用能让单线程跑满多核吗？** —— **不能**。它只把"连接数与线程数"解耦，**执行仍然在一个核上**。要多核靠**多进程 / 多线程**——**Nginx 是多 worker 单线程、Redis 是主线程单线程**，都不是"整个服务一个线程"。

**同类变体**

- 「事件循环里为什么不能有阻塞调用？」——阻塞调用**没有 `await` 点**，会让**整个事件循环停摆**（所有连接一起等）。**这条在 [[母题-N3-进程线程与协程]] 已经从"选型"角度讲过，本节补的是"它在操作系统层面对应什么"**：那个线程被挂在内核等待队列里，**其它几千个连接的事件没人取**（`epoll_wait` 也没人调）
- 「`io_uring` 相比 `epoll` 多了什么？」——`epoll` 告诉你"**可以读了**"，读完还要你自己发起 `read`；`io_uring` 是**提交队列 + 完成队列**：你提交"读这个 fd 到这个缓冲"，内核做完（含拷贝）再报告完成——**是真正的异步 IO，而且把"系统调用次数"从"每操作一次"降到"每批一次"**（本卡 4.5 算过：深度 128 → 省 99%）
- 「Nginx 作为反向代理为什么要零拷贝？」——它**只转发不修改**（静态文件尤其典型），**完美匹配 `sendfile` 的适用条件**；一旦要压缩 / 改写内容，就得回到"数据进用户态"的路径
- 「阻塞 IO 还能用吗？」——**能**，只要**并发量可控**。**简单性本身就是收益**：阻塞模型代码直白、不用管事件循环和"不能阻塞"的约束。**"用不用多路复用"是并发量与复杂度的取舍，不是先进与落后的区别**

**可迁移场景**：
**EnergyOps**——**长任务的 SSE 进度推送**意味着**大量长连接同时挂着**（[[母题-N2-SSE与推送模型]]）：这些连接**绝大部分时间没有数据**，正是"连接多、活跃少"的典型场景，也是多路复用的最大收益区。**"网关关缓冲 + 发心跳"这两个坑，本质是在让"活跃"这件事能被内核正确感知**。
**RuleArena**——长任务 Worker + Redis 队列：**Redis 单线程 + 多路复用**能扛住大量客户端，是因为"每个操作都极短、几乎不阻塞"；**而一旦客户端里出现慢操作，整个服务受影响**——这正是多路复用把"并发"和"快"绑在一起的代价。
**数驭穹图**——**Parquet 放对象存储、DuckDB 执行分析**：一次查询是典型的 **IO 密集 + 大块数据搬运**，**"少拷贝 + 批量读"在这个场景里直接变成查询延迟**；而"超时、取消"依赖能中断阻塞调用（本卡 2.1 的"第一段"）。

**方言差异（不同平台的同一件事）**：

| 同一件事 | Linux | macOS / BSD | Windows |
|---|---|---|---|
| 多路复用原语 | `epoll` | `kqueue` | IOCP（完成端口，**本身是异步模型**） |
| 零拷贝接口 | `sendfile` / `splice` | `sendfile` | `TransmitFile` / `CopyFile2` |
| 批量异步 IO | `io_uring`（5.1+） | `kqueue` 的 AIO | IOCP |
| 完全异步 AIO | POSIX AIO（实现较弱）、`io_uring` | —— | IOCP |

【推导】**所以"为什么 Node / Nginx 这些要封装一层"就说得通了**：**同一份"事件循环"逻辑，在 Linux 上用 `epoll`、BSD/macOS 上用 `kqueue`、Windows 上用 IOCP**——这就是 libuv 这类抽象层存在的原因。**面试里能说出这一层，说明你知道"多路复用"是概念而不是某个函数。**
