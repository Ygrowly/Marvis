### 5.1 EnergyOps（金山园区能耗 · PostgreSQL）

**锚点**：`projects/EnergyOps/03-query-and-performance.md`（四层事实表：原始 → 可信聚合区间 → hourly → daily；联合索引；`EXPLAIN ANALYZE`；消除重复 join）、`02-aggregation-and-recovery.md`（15 分钟窗口、幂等与补数）

- **用在哪**：604 台电表 15 分钟一次的累计读数采集与治理落库；查询链路按粒度命中 daily / hourly 事实表，不回到 Raw 现算差分。
- **解决什么问题**：原查询慢的根因不是单条 SQL，而是**先展开设备归属和大量事实、再过滤园区**——既产生大量中间行，又可能重复 JOIN，还叠加应用层 `N+1` 和现算差分；接口 P95 二十多秒。
- **踩过的坑**：① 归属关系未限制有效期 → 历史设备套用当前归属，同一设备被重复统计；② N+1（先查 100 台设备，再循环查每台 30 天用量 = 1+100 次往返）；③ 晚到数据重算后数据库已是新值，Redis 仍返回旧结果（缓存陈旧）。
- **决策与取舍**：没有换 OLAP、也没有全量上缓存，而是按顺序来——**先修范围与 JOIN 逻辑 → 再建联合索引 → 再选正确聚合层 → 消除 N+1 → 最后才上缓存/预聚合**。索引按「等值条件在前、时间范围在后」，如 `(device_id, energy_type, stat_date)`；事实表合法冗余园区快照时也可考虑 `(campus_id, energy_type, stat_date)`，最终以选择性和执行计划为准。缓存一致性用「事务内写 CacheInvalidation Outbox → 提交 → 异步 worker 幂等删缓存」，或把聚合版本放进缓存键——因为「PG 提交」和「Redis 删除」不可能构成同一个 ACID 事务。
- **对应母题**：M2、M3、M6、M7、M15
- **口径提醒**：`P95 20.4s → 2.8s` 属**待验证数字**（手册未关联原始报告）。面试必须自带口径：查询范围、样本数、并发、硬件、缓存冷热、统计窗口、P95 算法。**报数字前先说口径，比被追问出来安全。**

### 5.2 数驭穹图（企业问数 · PG 存元数据，接入 MySQL 数据源）

**锚点**：`projects/数驭穹图/02-数据接入与轻量湖仓.md`、`07-权限安全与生产隔离.md`、`08-查询性能与成本控制.md`

- **用在哪**：PostgreSQL 保存租户、数据目录、Schema、同步任务与文件索引；对象存储按租户/数据集/分区存 Parquet；DuckDB 读 Parquet 做分析。接入客户源库时——**MySQL 优先用 Binlog，PostgreSQL 优先用逻辑复制 / WAL**。
- **解决什么问题**：既要拿到真实数据，又不能把未知 SQL 的风险转嫁给客户生产库。所以分两种访问模式：`SNAPSHOT`（同步到租户隔离的轻量湖仓，可跨源 JOIN、可复现）与 `LIVE_READ`（只读副本 / 分析库，新鲜度高但依赖源端性能）。**这是 MySQL 模块里「CDC / 增量同步」的真实落地场景。**
- **踩过的坑**：① 多租户数据源方言差异（同一个查询在不同源上行为不同）；② 只读账号的权限边界——必须有只读事务、允许表清单、超时、扫描量、并发、行数和取消能力；客户只有生产主库时默认不开放复杂即席查询；③ **删除行没有 tombstone 就会静默漏数**，所以发布前必须校验行数、主键重复、字段类型、分区完整性、Schema 漂移、同步位点和新鲜度，关键校验失败就停在 `INVALID` / `STALE`，不得进入正式问数。
- **决策与取舍**：第一版只做**可恢复快照 + `updated_at` / 递增主键轮询**，不上完整 CDC。理由：CDC 要求源端开启 binlog/逻辑复制并承担权限与稳定性风险，而分析场景容忍分钟级新鲜度；用「快照 + 位点 + 校验」换来的生产隔离与可复现性更值。升级条件：出现真实的秒级新鲜度需求。
- **对应母题**：M7、M14、M15

### 5.3 RuleArena（规则竞技场 · PostgreSQL）

**锚点**：`projects/RuleArena/04-idempotency-and-recovery.md`（条件更新、Checkpoint、Worker 重启恢复）、`03-executable-world-and-oracle.md`（PG 事务、Sandbox 副本环境）

- **用在哪**：PostgreSQL 是所有权威状态的落点——AttackRun / StrategyStep / ActionReceipt / Ledger / BusinessEvent 在同一事务内提交；沙箱用**数据库副本**重放高风险操作组合。
- **解决什么问题**：Worker 随时可能崩、队列按「至少一次投递」设计，而退款 / 发券这类**有副作用**的动作绝不能执行两次。要回答的是：**请求结果未知时，怎么避免重复副作用、并让任务恢复到可判断状态。**
- **踩过的坑**：① 沙箱若直接在生产库上重放，长事务 + 锁等待 + 高风险组合会把生产拖下水 → 必须用副本；② 曾把 **ToolCallID 当成幂等键**——模型重新规划、Worker 重启、超时重发都会产生不同的 ToolCallID，业务幂等键必须基于业务身份构造（`run_id + action_type + target_id + 参数 + 规则版本 + 逻辑步骤`）。
- **决策与取舍**：用**条件更新（乐观并发）+ 唯一约束**，不用 `SELECT ... FOR UPDATE`：

  ```sql
  UPDATE orders
  SET refunded_amount = refunded_amount + :amount,
      version = version + 1
  WHERE id = :id
    AND version = :expected_version
    AND refunded_amount + :amount <= paid_amount;
  ```

  影响行数为 0 → 说明版本冲突或超额，读出权威 Snapshot 后返回冲突，**不盲目重试业务动作**。为什么不用悲观锁：扣退款是低频写、读多写少，加锁会把锁等待和死锁风险带进来；正确性最终靠数据库唯一约束 `UNIQUE(run_id, action_type, idempotency_key)` 兜底，而不是靠内存锁或 Redis 锁。Checkpoint 只存 frontier / 预算 / 版本元组，**不存业务结论**——因为「动作」与「Checkpoint」之间永远存在崩溃窗口，不存在完美保存顺序。
- **对应母题**：M7、M10、M16、M17
