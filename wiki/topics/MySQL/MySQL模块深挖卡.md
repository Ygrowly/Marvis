### 5.1 EnergyOps（金山园区能耗 · PostgreSQL）

**锚点**：`projects/EnergyOps/03-query-and-performance.md`（四层事实表：原始 → 可信聚合区间 → hourly → daily；联合索引；`EXPLAIN ANALYZE`；消除重复 join）、`02-aggregation-and-recovery.md`（15 分钟窗口、幂等与补数）

- **用在哪**：604 台电表 15 分钟一次的累计读数采集与治理落库；查询链路按粒度命中 daily / hourly 事实表，不回到 Raw 现算差分。
- **解决什么问题**：原查询慢的根因不是单条 SQL，而是**先展开设备归属和大量事实、再过滤园区**——既产生大量中间行，又可能重复 JOIN，还叠加应用层 `N+1` 和现算差分；接口 P95 二十多秒。
- **踩过的坑**：① 归属关系未限制有效期 → 历史设备套用当前归属，同一设备被重复统计；② N+1（先查 100 台设备，再循环查每台 30 天用量 = 1+100 次往返）；③ 晚到数据重算后数据库已是新值，Redis 仍返回旧结果（缓存陈旧）。
- **决策与取舍**：没有换 OLAP、也没有全量上缓存，而是按顺序来——**先修范围与 JOIN 逻辑 → 再建联合索引 → 再选正确聚合层 → 消除 N+1 → 最后才上缓存/预聚合**。索引按「等值条件在前、时间范围在后」，如 `(device_id, energy_type, stat_date)`；事实表合法冗余园区快照时也可考虑 `(campus_id, energy_type, stat_date)`，最终以选择性和执行计划为准。缓存一致性用「事务内写 CacheInvalidation Outbox → 提交 → 异步 worker 幂等删缓存」，或把聚合版本放进缓存键——因为「PG 提交」和「Redis 删除」不可能构成同一个 ACID 事务。
- **对应母题**：M2、M3、M6、M7、M15
- **口径提醒**：`P95 20.4s → 2.8s` 属**待验证数字**（手册未关联原始报告）。面试必须自带口径：查询范围、样本数、并发、硬件、缓存冷热、统计窗口、P95 算法。**报数字前先说口径，比被追问出来安全。**

### 5.2 数驭穹图（企业问数 · PG 存元数据，接入 MySQL 数据源）

**锚点**：`projects/数驭穹图/02-数据接入与轻量湖仓.md`、`07-权限安全与生产隔离.md`、`08-查询性能与成本控制.md`

- **用在哪**：PostgreSQL 保存租户、数据目录、Schema、同步任务与文件索引；对象存储按租户/数据集/分区存 Parquet；DuckDB 读 Parquet 做分析。接入客户源库时——**MySQL 优先用 Binlog，PostgreSQL 优先用逻辑复制 / WAL**。
- **解决什么问题**：既要拿到真实数据，又不能把未知 SQL 的风险转嫁给客户生产库。所以分两种访问模式：`SNAPSHOT`（同步到租户隔离的轻量湖仓，可跨源 JOIN、可复现）与 `LIVE_READ`（只读副本 / 分析库，新鲜度高但依赖源端性能）。**这是 MySQL 模块里「CDC / 增量同步」的真实落地场景。**
- **踩过的坑**：① 多租户数据源方言差异（同一个查询在不同源上行为不同）；② 只读账号的权限边界——必须有只读事务、允许表清单、超时、扫描量、并发、行数和取消能力；客户只有生产主库时默认不开放复杂即席查询；③ **删除行没有 tombstone 就会静默漏数**，所以发布前必须校验行数、主键重复、字段类型、分区完整性、Schema 漂移、同步位点和新鲜度，关键校验失败就停在 `INVALID` / `STALE`，不得进入正式问数。
- **决策与取舍**：第一版只做**可恢复快照 + `updated_at` / 递增主键轮询**，不上完整 CDC。理由：CDC 要求源端开启 binlog/逻辑复制并承担权限与稳定性风险，而分析场景容忍分钟级新鲜度；用「快照 + 位点 + 校验」换来的生产隔离与可复现性更值。升级条件：出现真实的秒级新鲜度需求。
- **对应母题**：M7、M14、M15

### 5.3 RuleArena（规则竞技场 · PostgreSQL）

**锚点**：`projects/RuleArena/04-idempotency-and-recovery.md`（条件更新、Checkpoint、Worker 重启恢复）、`03-executable-world-and-oracle.md`（PG 事务、Sandbox 副本环境）

- **用在哪**：PostgreSQL 是所有权威状态的落点——AttackRun / StrategyStep / ActionReceipt / Ledger / BusinessEvent 在同一事务内提交；沙箱用**数据库副本**重放高风险操作组合。
- **解决什么问题**：Worker 随时可能崩、队列按「至少一次投递」设计，而退款 / 发券这类**有副作用**的动作绝不能执行两次。要回答的是：**请求结果未知时，怎么避免重复副作用、并让任务恢复到可判断状态。**
- **踩过的坑**：① 沙箱若直接在生产库上重放，长事务 + 锁等待 + 高风险组合会把生产拖下水 → 必须用副本；② 曾把 **ToolCallID 当成幂等键**——模型重新规划、Worker 重启、超时重发都会产生不同的 ToolCallID，业务幂等键必须基于业务身份构造（`run_id + action_type + target_id + 参数 + 规则版本 + 逻辑步骤`）。
- **决策与取舍**：用**条件更新（乐观并发）+ 唯一约束**，不用 `SELECT ... FOR UPDATE`：

  ```sql
  UPDATE orders
  SET refunded_amount = refunded_amount + :amount,
      version = version + 1
  WHERE id = :id
    AND version = :expected_version
    AND refunded_amount + :amount <= paid_amount;
  ```

  影响行数为 0 → 说明版本冲突或超额，读出权威 Snapshot 后返回冲突，**不盲目重试业务动作**。为什么优先条件更新而不是悲观锁：项目文档 `04 §15` 给的是**「MVP 优先业务唯一键 + 条件更新」**，`Q7` 给的是**「锁可以降低竞争，但不能成为资金正确性的唯一保证」**——**理由是权威性，不是「低频写」**；而且文档 `04 §12` 同时给了**「锁定订单行 **或** 乐观版本条件更新」**，所以别说成「完全不用锁」。正确性最终靠数据库唯一约束 `UNIQUE(run_id, action_type, idempotency_key)` 兜底，而不是靠内存锁或 Redis 锁。Checkpoint 只存 frontier / 预算 / 版本元组，**不存业务结论**——因为「动作」与「Checkpoint」之间永远存在崩溃窗口，不存在完美保存顺序。
- **对应母题**：M7、M10、M16、M17

## 8. 题级答案（「本主线的题」翻转卡背面 · 先说后翻）

> 题号与第 4 节题单一一对应。**必背**题写成能直接说出口的一段话；**理解 / 了解**题写 1–3 句。
> 翻转卡背面先给这道题的答案，再挂上「所属母题的完整回答（口述稿）」与单卡入口——两段合起来才是深挖。

### 1 （必背）
判据是磁盘 IO 次数：磁盘随机读比内存随机访问慢约 5 个数量级，而一次 IO 读的是一整页（InnoDB 默认 16KB）、成本几乎不随读多少变化。所以比较四个候选只看「定位一行要几次 IO」。哈希表只能等值、做不了范围；红黑树扇出只有 2，2000 万行树高约 24 层、约 24 次 IO；B 树非叶也存数据，扇出被挤小、范围查询还要回溯父节点；B+ 树非叶只存键，扇出约 1170，三层覆盖约 2000 万行、只要 3 次 IO，叶子双向链表让范围查询一次下降后顺序扫，页与磁盘块对齐让每次 IO 都不浪费。

### 2 （必背）
三点硬差异：InnoDB 支持事务、行级锁、崩溃恢复；MyISAM 是表级锁、不支持事务、崩溃后可能丢数据。业务表同时要并发写和「不能丢」，所以 InnoDB 成了默认；MyISAM 只在「读多写少 + 无事务需求 + 数据可重建」三者同时成立时才勉强可用。

### 3 （了解）
业务表用 InnoDB 就够；另外两个常见的：**MEMORY** 把数据放内存、**默认哈希索引**、**服务重启数据即丢**（表结构还在，但重启后是空的），适合临时表 / 缓存这类可重建的数据；**ARCHIVE** 只支持插入（含 REPLACE）和查询，**不支持删除和更新**，数据用 zlib 压缩、压缩比很高，适合日志归档。两者都不支持事务，都不适合做业务表。（依据：MySQL 官方手册 ARCHIVE / MEMORY 两节）

### 4 （理解）
长度真的固定（定长编码、MD5 之类）用 char，省掉长度字节；长度不定用 varchar——char(10) 存 'a' 占 10 字节，varchar(10) 只占 2 字节（1 字节长度 + 1 字节内容），差 5 倍。注意 char 会补齐空格，取值比较时尾部空格容易被忽略掉。

### 5 （理解）
DATETIME 存 8 字节、范围到 9999 年、存的就是字面时间、不受时区影响；TIMESTAMP 只有 4 字节、内部存 UTC 秒数、显示随时区变，但上限是 2^31−1 秒 ≈ 68 年，到 2038-01-19 就溢出。所以远期时间（合同到期、生日）必须用 DATETIME；只记最近发生的时间可以用 TIMESTAMP 省 4 字节。

### 6 （必背）
两笔代价。① 写入层面：UUID 是随机值，插入位置随机 → 目标页常常已满 → 页分裂 → 填充率从约 100% 掉到约一半、页数翻倍，缓存能装的页数也跟着减半；② 存储层面：主键会被复制进每一个二级索引，36B 的 UUID 让单个索引从 18B/条涨到 46B/条。要全局唯一又要顺序写，用趋势递增的雪花 ID——但要主动说它的代价：趋势递增不是严格递增（时钟回拨仍可能乱序），位数也更长。

### 7 （理解）
1NF 列不可再分；2NF 非主键列完全依赖主键（不能只依赖联合主键的一部分）；3NF 非主键列不传递依赖别的非主键列。范式解决的是「一处修改要不要改多处」。反范式是拿冗余换查询次数，判据是能不能算出收益：只有当这个冗余是热点查询的关键路径、省掉的 JOIN 或回表可量化时才做，且要保证冗余列的更新路径唯一——不能凭感觉加。

### 8 （理解）
判据不是「删了什么」，而是「怎么删」。drop 删表结构和数据，是 DDL、隐式提交、不能回滚；truncate 走「丢段 + 重建」，也归 DDL、同样不可回滚，但比逐行删快得多、自增值也重置；delete 是 DML，逐行删、写 undo、可回滚、可带 WHERE，还会留碎片。

### 9 （了解）
常用约束：主键、唯一、非空、默认值、外键、CHECK。主键约束与唯一约束的差别有两处：主键隐含非空、一张表只能有一个，而且它决定聚簇索引的物理顺序；唯一索引允许 NULL（多个 NULL 不算重复），一张表可以有多个。

### 10 （必背）
InnoDB 是索引组织表：主键索引的叶子就是整行数据，二级索引的叶子只是「索引列 + 主键值」。所以走二级索引取非索引列要两次 B+ 树查找——先在二级索引定位到主键，再拿主键回聚簇索引取整行，第二次就是回表。它随命中行数线性增长，而且是随机 IO：扫 1000 行就是 1000 次随机 IO。对照：PG 是堆表，所有索引叶子都存 ctid、一律要回表。

### 11 （必背）
联合索引 (a, b, c) 是按字典序排的。索引的有序性能做三件事：定位、截断（LIMIT 到了就停）、免排序，前提都是「满足条件的记录在索引里是连续的一段」。所以只有从最左列开始的连续前缀才能切出一个可定位区间。单独查 b = 2 用不上，是因为 b 只在每个 a 段内有序、段之间无序，找不到包含全部结果的连续区间——「用不上」的准确含义是退化成扫描量约等于全表，不是报错。WHERE 里条件的书写顺序不影响，优化器会按列集合重排。

### 12 （必背）
覆盖索引 = 查询需要的列全都在索引里，第二次查找消失、不用回表。判据是 EXPLAIN 的 Extra 出现 Using index。代价必须一起说：索引变宽 → 每次 INSERT/UPDATE 的维护成本更高、页里能装的项更少、树可能多长一层，还会干扰优化器的选择。所以覆盖是给热点查询的，不是全表都建宽索引。

### 13 （必背）
四类典型：① 不满足最左前缀（跳过了前导列，或前缀里有断点）；② 在索引列上做函数、运算或隐式类型转换——列被包住就失去定位能力；③ 范围列之后的列失去定位（仍能靠 ICP 在索引层过滤，省回表不省扫描）；④ 优化器主动放弃——选择度太低时（比如状态位只有几个取值），走索引 + 回表比直接全表扫更贵，它算完成本就不用索引。前三条要改写法，第四条要动统计信息或者接受它。

### 14 （理解）
不是越多越好，三笔代价：写放大（一次写要维护 N+1 棵 B+ 树）、空间（主键被复制进每个二级索引）、优化器负担（可选项多了，选错的成本变高）。没被用上的索引是纯负债。判断标准是「这条索引服务了哪条查询」，而不是「这一列好像会被查」。

### 15 （必背）
先看清 DDL 的两步：改元数据 + 改数据，危险在第二步要拿 MDL 写锁。方案三条：① Online DDL（ALGORITHM=INPLACE / LOCK=NONE）——只保证执行期间不阻塞别人，不保证自己不被长事务阻塞，而且改列类型、重建聚簇索引这类做不到 INPLACE；② 影子表：pt-osc 用触发器同步增量，gh-ost 吃 binlog、对主库压力更小更可控；③ 前置动作：先查并干掉长事务、设短 lock_wait_timeout 让等待快速失败、低峰执行、备好回滚。选哪条按表的规模和是否可回滚决定。

### 16 （必背）
五层：连接器（鉴权、连接管理）→ 分析器（词法语法解析）→ 优化器（选索引、选 JOIN 顺序、决定是否用临时表和排序）→ 执行器（按计划逐行调引擎接口）→ InnoDB 引擎层（Buffer Pool、索引、事务）。分工一句话：server 层管功能与计划，引擎层管数据怎么存怎么取。题眼是：五层里只有优化器在做决定，所以「SQL 慢」的第一嫌疑人是它估算错了——估算依赖统计信息，统计过期、数据倾斜、条件带函数时就会错。

### 17 （必背）
主要看四个字段：type（访问方式）、key（实际用了哪个索引）、rows（估算扫描行数）、Extra（附加动作——Using index 说明覆盖，Using filesort 说明还要排序，Using temporary 说明用了临时表）。type 从好到坏记这七个够用：system > const > eq_ref > ref > range > index > ALL。两个提醒：rows 是估算值，要实际值用 EXPLAIN ANALYZE（8.0.18+）；判断标准是 rows 与最终返回行数的比值，而不是 rows 的绝对值。

### 18 （必背）
定位三步：慢查询日志按「频率 × 单次耗时」排优先级 → EXPLAIN 看计划 → 动手改完再 EXPLAIN 验证。手段归三类：少扫（最左前缀设计、避开大偏移量）、少回（覆盖索引、ICP 下推）、少排（让索引顺序匹配 ORDER BY），再加一条小表驱动大表。最反直觉的一条：索引没走不一定是写法问题，可能是优化器算过成本主动放弃——条件命中比例太高时全表扫反而是对的。

### 19 （理解）
LIMIT 1000000, 10 不是「取 10 行」，而是「取前 1,000,010 行、丢掉前 100 万行」，所以扫描量与回表量约等于偏移量，而且是线性增长。首选游标定位：记住上一页最后一条的排序键，下一页用 WHERE id > ? 跳过去，扫描和回表都降到 10 行。必须跳页时才用延迟关联（先用覆盖索引取主键集合，再 JOIN 回原表取整列）——它只降回表，不降扫描量。

### 20 （理解）
索引条件下推（ICP）是把 WHERE 里能用索引判断的条件交给引擎，在索引层先把行过滤掉，过滤掉的就不用回表。它治的是「回表次数多」这一类慢：比如 (age, name) 索引上查 age = 18 AND name LIKE '%张%'，原本所有 age = 18 的行都要回表再判 name，有 ICP 后 name 在索引层就判掉，回表次数大幅下降。关键词是回表次数——它不减少扫描。

### 21 （理解）
判据是小表驱动大表：子查询结果集小用 in，外层表小用 exists。not in 要特别小心两点：子查询结果里出现 NULL 时整个条件恒不成立（永远返回空）；而且它往往用不上索引。所以实际写法上通常换成 NOT EXISTS 或左连接判空。

### 22 （理解）
count(*) 和 count(1) 在 InnoDB 里基本一样，都是统计行数、不取值；count(列) 要判断该列是不是 NULL，所以更慢。count(*) 慢的根因不是写法而是机制：InnoDB 没有行数缓存、必须真数；只有 MyISAM 有行数缓存，而业务表不该用 MyISAM。要快只能自己维护计数（计数表 / 缓存 / 增量更新）。

### 23 （理解）
驱动表是「先扫的那张」，扫描量约等于驱动表行数 × 被驱动表的定位成本，所以要小表驱动大表——反过来可能差几个数量级。优化顺序：先保证被驱动表的连接列有索引（这是前提），再看优化器选的驱动表对不对（EXPLAIN 里谁在前面、type 是不是 ALL），必要时用 STRAIGHT_JOIN 指定顺序，或者把过滤条件写得更有选择性。

### 24 （必背）
原子性 A 靠 undo（前镜像，撤销回滚）；持久性 D 靠 redo（后镜像，崩溃后重放）；隔离性 I 分两块：写写冲突靠锁、读写冲突靠 MVCC。一致性 C 不是独立机制——它是 A + D + I 再加约束共同得到的结果。这一点必须点出来，否则很容易答成「一致性由隔离级别实现」，那是错的。

### 25 （必背）
三个并发问题：脏读 = 读到别人还没提交的数据；不可重复读 = 同一行两次读结果不同（别人改了）；幻读 = 同一个范围两次读行数不同（别人插了）。四个级别逐级挡：RU 什么都不挡；RC 挡脏读；RR 再挡不可重复读；Serializable 全挡。越严格并发越低——串行化把读也拉进排队。InnoDB 默认 RR，快照读的幻读靠 MVCC 挡、当前读的幻读靠间隙锁挡。

### 26 （必背）
MVCC = 多版本 + 可见性判定。数据页只留最新版本，旧版本写进 undo log、靠每行的 roll_pointer 串成版本链；读的时候拿一个 ReadView（记录「拍快照那一刻还活跃的事务名单」），沿版本链往回找第一个可见的版本。RC 和 RR 的唯一差别是 ReadView 的生成时机：RC 每条语句重新生成，RR 整个事务只生成一次——这就是「可重复读」的全部实现。

### 27 （必背）
先分清两种读：快照读（普通 SELECT）不加锁、走版本链；当前读（UPDATE、SELECT ... FOR UPDATE）看的是最新数据、要加锁。RR 下幻读靠两套机制：快照读靠 MVCC（同一个 ReadView，别的事务插入的行看不见），当前读靠间隙锁（锁住记录之间的空隙、不让插入）。所以说「RR 完全解决了幻读」不严谨——两种读各自都不幻读，但混用时会看到「看起来像幻读」的现象。

### 28 （必背）
三种锁都加在索引记录上：Record Lock 锁记录本身；Gap Lock 锁记录之间的空隙、防插入，是防幻读的必要手段，只在 RR 下有；Next-Key Lock = 记录 + 前面的间隙，是 RR 下的默认加锁单位。因为锁跟着扫描范围走，锁全表只需要一个条件：没有可用索引（或条件把整棵索引都扫过）——非唯一索引 + 范围条件、缺索引、索引列上做函数，都会把锁从 1 条放大到万级、甚至整表。

### 29 （理解）
粒度：InnoDB 以行级锁为主，另有表级意向锁（IS / IX，作用是声明「我要在表里加行锁」，让表锁请求不必逐行检查）；MyISAM 只有表级锁。类型：共享锁 S（读锁，多个可共存）与排他锁 X（写锁，互斥）。要强调 S/X 是类型、Record/Gap/Next-Key 是粒度，两个维度别混；FOR SHARE 加 S 锁，FOR UPDATE 加 X 锁，两者都在某个粒度上。

### 30 （理解）
死锁的本质是多个事务的加锁顺序不一致、形成环；InnoDB 会检测并回滚代价小的事务，所以表现是某次请求报错而不是系统挂掉。排查：SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 段，看两个事务各持有什么锁、在等什么、执行到哪条 SQL；再用 performance_schema.data_locks / data_lock_waits 看当前等待关系。顺序是先看「谁在等谁」，再回溯加锁顺序——结论几乎总是「顺序不一致」或「事务扫得太宽」。避免：精确索引缩小锁范围、事务尽量短、多表多行固定访问顺序、队列场景用 SKIP LOCKED 或改成条件更新。

### 31 （必背）
各管一件事：undo 管回滚和 MVCC 的旧版本（前镜像，引擎层）；redo 管崩溃恢复（后镜像、物理日志、固定大小循环写、用完即弃）；binlog 管复制和时间点恢复（逻辑日志、追加写、Server 层）。它们靠 WAL 串起来——把「随机写数据页」换成「顺序写日志」，一次拿到性能和崩溃安全。三条不能互相替代：binlog 单独保证不了 crash-safe，redo 也不服务复制。

### 32 （理解）
WAL（Write-Ahead Logging）= 先写日志、再写数据页，把随机写换成顺序写，从而兼顾性能与崩溃安全。redo 循环写是因为它只服务「崩溃恢复到最新状态」这一个目的：一旦它记录的改动已经落到数据页上，这条 redo 就没用了，空间可以复用。它用两个指针管理：write pos 是当前写到哪（不断前进），check point 是「已经安全刷盘」的位置。危险场景是 check point 长期不推进，write pos 绕上来追上 check point——没有空闲区域可写，写入被迫停下等刷脏页，表现是写入突然卡顿。

### 33 （必背）
唯一理由是让 redo 和 binlog 逻辑一致。它们不在一个组件里、没法用一个本地事务包住，中间崩溃就会不一致。不做的话有两个窗口：redo 提交了但 binlog 没写 → 主库多、从库少；binlog 写完了但 redo 没提交 → 从库多、主库少。2PC 用三步堵住它们：prepare（redo 写好但标 prepare）→ 写 binlog → commit；崩溃后由 binlog 的完整性裁决——完整就提交，不完整就回滚。

### 34 （了解）
innodb_flush_log_at_trx_commit 和 sync_binlog 都设 1 叫「双一」：每次提交都刷盘，最安全、也最慢；设成 0 或 2 会快，但掉电可能丢最近约 1 秒已提交的事务。取舍标准是业务能不能容忍丢这 1 秒——埋点、日志能忍，涉及钱和订单的不能；不是「哪个快选哪个」。

### 35 （必背）
三种格式：Statement 记原始 SQL，日志小，但含 UUID()、NOW() 这类非确定函数时从库会算出不同结果，造成主从漂移；Row 记每行修改前后的具体内容，复制绝对精确，代价是日志量大、批量 UPDATE 会暴涨；Mixed 自动判断，安全的用 Statement、危险的切 Row。现在主流是 Row——数据安全优先于日志体积。

### 36 （必背）
崩溃瞬间每个事务只有三种状态：已提交、未提交、提交到一半（prepare）。恢复 = redo 重放 + undo 回滚，顺序不能反。redo 从 check point 起顺序重放：每页自带 LSN、已落盘的页直接跳过，所以重放是幂等的——幂等的本质是「能判断出已经做过了」，不是「只做一次」。然后 undo 撤销未提交的事务；prepare 的事务由 binlog 完整性裁决。反过来先 undo，会在「已提交但数据页还没落盘」时把已提交的数据弄丢。

### 37 （理解）
崩溃窗口指的是 2PC 的中间态被切断。① binlog 已落盘、redo 还停在 prepare 时崩溃：如果只看 redo 状态就回滚，而这个事务从库已经重放过了 → 从库多、主库少；② redo 已提交但 binlog 没写完：主库多、从库少。所以裁决依据必须是外部的完整性判据——binlog 完整就提交、不完整就回滚，不能让两边各按自己的日志判断。

### 38 （必背）
它按住两样东西，所以危害是两条独立的链。① MVCC 链：ReadView 不释放 → purge 不敢清理它还可能读到的旧版本 → undo 膨胀、版本链变长 → 别人的快照读要沿这条链回溯（一行每秒改 100 次、挂 2 小时就是约 72 万节、单次回溯约 72 毫秒），回滚成本也更高；② 锁链：写锁持到事务结束 → 其他写事务排队、死锁概率上升。反直觉的点：只读事务触发不了锁那条，但 MVCC 那条照样走——回收看的是 ReadView，不是你做了什么。最常见的真实形态是 SET autocommit = 0 之后跑了查询忘提交，这种连接 CPU 低、监控上很不起眼，却在按住全库的回收边界。

### 39 （必背）
三步：主库提交时写 binlog → 从库 IO 线程拉取并写入 relay log → 从库 SQL 线程重放。同步方式：异步（主库写完 binlog 就返回，主库宕机可能丢最后一段）；半同步（至少一个从库确认收到 binlog 才返回，解决的是 RPO，不保证从库已经重放完）；再强就是组复制/全同步，代价是延迟与复杂度。要主动点出半同步治的是「主库挂了丢不丢」，不是读一致性。

### 40 （理解）
延迟三个来源：① 回放并行度永远 ≤ 主库（按库并行时天花板就是库数）；② 大事务必须整体重放，期间这批变更对从库完全不可见；③ 从库自身慢——Row 格式下无主键表的更新退化成全表扫，量级差约 20 万倍，所以「每张表都要有主键」是复制性能问题。缓解：调并行度、拆大事务、保证主键、别让从库扛太多读。读到旧数据按优先级三层解：读己之写（刚写完的读走主库或等位点）、会话粘主库、超阈值降级——不要 sleep，延迟会波动，时长没有依据。

### 41 （理解）
冷热分离：按时间轴把热数据和冷数据分层，让热查询不背着冷数据跑——8000 万行归档到 800 万行，索引从 4 层降到 3 层，同样的点查少一次 IO，还避免冷数据把热数据挤出 Buffer Pool。归档：把历史数据搬到独立存储，注意它不等于删除——要保留独立索引与访问路径、要有生命周期口径，而且必须分批搬分批删（一次性删 7000 万行是长事务 + 膨胀源，undo 峰值约 14 GB）。读写分离：把读流量分到从库，只降读压力、不降写压力，还要处理读到旧数据。

### 42 （理解）
判据不是行数，而是前三步（索引与 SQL、事务与锁、冷热分离与归档）做完仍然扛不住——也就是单机容量或写入上限真的到了。它有四项代价：路由变复杂（查询必须带分片键，否则广播到所有分片）、跨分片聚合与分页难、跨分片事务难、扩容要迁移约 50% 的数据。分片键是「查询形状的属性」：选高频查询都带的那个维度（如 user_id），让绝大多数查询落在单个分片；选错会导致大量广播，而它又是最难改的决定。

### 43 （理解）
先分清这两件事分别是谁的症状。数据库 CPU 飙高：先看是不是慢 SQL / 全表扫（慢查询日志 + EXPLAIN + performance_schema），再看是不是大量并发小查询打上来，同时排长事务和大事务。连接池打满：它通常不是根因，而是上游变慢的结果——慢 SQL 让连接迟迟不释放，或者事务里塞了 RPC / 计算把持有时间拉长；也可能只是池子配小了。顺序是：先看 SQL 有没有变慢、事务边界有没有问题，再谈加连接数。

### 44 （必背）
两者是对冲突概率的两种假设：悲观锁假定冲突一定发生、先加锁（SELECT ... FOR UPDATE）；乐观锁假定冲突很少、不加锁但提交时校验——UPDATE ... SET ... WHERE id = ? AND version = ?，影响行数 0 就是冲突。判据只有一个：冲突频率。乐观锁成本约等于单次成本 ÷ (1−p)，p 趋近 1 时发散；高冲突下 N 个请求抢同一行，乐观锁总工作量约 N²、悲观锁约 N。所以冲突高到「重试成本 > 加锁成本」就换悲观。两个细节：乐观锁的核心是「期望值进 WHERE」（CAS 思想），version 顺带防 ABA；影响行数 0 是正常业务分支不是异常，重试必须有上限和退避。

### 45 （必背）
先澄清榜单范围、更新频率、同分怎么排、要不要防作弊、榜单规模，再选型。排行榜用 Redis ZSet：跳表把「按 score 有序」内建进结构，ZADD / ZREVRANK 都是 O(logN)；MySQL 算名次要 COUNT(*) WHERE score > ?，是 O(N)——200 万榜单要数约 100 万行，ZSet 大约 21 次比较，差约 5 万倍，且榜单越大差距越大。同分先到者优先用复合分数：分数 × 倍率 + (MAX_TS − 通关时间戳)；注意 score 是双精度浮点、只有 2^53 以内能精确表示，倍率取 10^10 时分数上限必须小于约 90 万，否则低位被抹掉、同分排序错乱而且不报错。

### 46 （必背）
三条路。① 把判断下推进 WHERE：UPDATE ... SET stock = stock − 1 WHERE id = ? AND stock > 0，看影响行数，0 就是没抢到——单条语句原子，是首选；② Redis 预扣 + 异步落库（Lua 保证原子），适合超高并发、允许少量失败回滚；③ 悲观锁 SELECT ... FOR UPDATE 排队，实现最简单但吞吐最低。判据是并发量和能不能容忍少量回滚。共同的前提：先查库存再扣在并发下必然有窗口，不能只靠「加个事务」了事。
