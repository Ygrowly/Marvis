# 母题 M15 · 数据增长治理

> **模块**：MySQL / 数据增长与高可用
> **所属主线**：六 · 数据增长与高可用（数据多了怎么不被拖垮）
> **关联母题**：[[母题-M14-主从复制与延迟]] · [[母题-M7-慢查询与SQL优化手段]] · [[母题-M13-长事务为什么危险]] · [[母题-P16-分区表]]
> **素材来源**：`raw/后端视角复盘_MySQL` 第六条主线（冷热分离 / 归档 / 读写分离 / 为什么不是一上来就分库分表）

**题目**：任务表 8000 万行，执行日志还在以每天百万条增长。你会按什么顺序处理？

**母题**：冷热分离、归档、读写分离、分库分表——它们分别解决什么？为什么不是一上来就分库分表？

**为什么重要**：**这是主线六的收口题**，而且它有一个**几乎所有人都会答错的顺序问题**——"数据量大 = 分库分表"。**raw 里给出的五步顺序是这道题的灵魂**，它同时考验**克制（知道什么时候不动）**和**视野（知道每一步解决什么）**。**而且它和 P16（PG 分区）合流：有持续清理需求的大表，分区的"丢弃分区"就是归档的最优解。**

**一句话结论**：**合理的顺序是五步——① 索引和 SQL 做好 → ② 事务边界和锁冲突管好 → ③ 冷热分离和归档 → ④ 读写分离 → ⑤ 单机真的扛不住才分库分表**。**冷热分离**把热查询与冷数据分层（时间轴是最自然的切分轴）；**归档** = 把不再高频访问的历史**从在线主链路移走（不等于删除）**；**读写分离**解决"读太多与写争资源"；**分库分表**是最后一步，因为它的复杂度（路由、聚合分页、跨分片事务、扩容迁移）是一次性的长期负担。

**恢复关键词**：冷热分离按时间轴 / **归档 ≠ 删除** / 读写分离解决读争写 / 分库分表的四项代价 / **五步顺序** / 分片键按高频查询路径选

**核心不变量 / 主线**：
**"数据量大"本身不是问题，"热查询背着冷数据跑"才是问题。** 所以治理的第一动作永远是**把热和冷分开**，而不是"把大表拆开"——**两者听起来像，做的完全是不同的事。**

**完整回答骨架**：先定问题（是读慢还是写慢还是单纯大）→ 五步顺序逐条 → 冷热分离怎么做 → 归档怎么做 → 分库分表的四项代价与分片键 → 回到题目

## 原理分解

### 一、先定问题（这一步决定一切）

**"8000 万行"是三种完全不同的问题**：

| 症状 | 真问题 | 对应手段 |
|---|---|---|
| **查询慢** | 热查询在扫大量冷数据 / 索引不行 | **先 M7（索引与 SQL），再冷热分离** |
| **写入慢 / 锁冲突** | 事务边界大、锁范围大 | **M13 / M10（分批 + 短事务）** |
| **单机容量到顶** | 磁盘 / 内存 / 连接真的不够 | **先归档，最后才分库分表** |

**所以第一动作是定位症状，而不是拆表**——**"8000 万行"本身不构成任何动作的理由**。

### 二、五步顺序（raw 原文，必须背）

```
① 先把索引和 SQL 做好
② 再把事务边界和锁冲突管好
③ 然后做冷热分离和归档
④ 再做读写分离
⑤ 单机真的扛不住了，再考虑分库分表
```

**为什么这个顺序**：**每一步的复杂度递增，且后面的步骤会改变前面步骤的优化对象**（比如先分表再优化索引，索引设计会复杂一倍）。**所以"便宜且可逆的先做，贵且难回头的后做"。**

### 三、冷热分离：让热查询只打热数据

**raw 里的例子**：最近 7 天的任务日志经常查，半年前的几乎只在审计时查。

**问题不是"数据太多"，而是"热查询背着冷数据一起跑"**：

- **索引更深、缓存命中率更低**（冷数据把热数据挤出 shared buffer）；
- **扫描范围里绝大部分是不会命中的行**——表里留两年（730 天）、查询只覆盖最近 7 天时，**热数据只占 7/730 ≈ 1%**，剩下 **99% 被扫到但用不上**。

**做法**：**按时间轴（最自然的切分轴）把近期热数据和历史冷数据分层**——**MySQL 里通常是"两张表 + 定期迁移"**（在线表只留热数据），**PG 里更优解是分区表（P16）**——**分区是数据库原生支持的分层，且"丢弃分区即归档"**。**这是两边能力差异的一个直接体现。**

### 四、归档：从在线主链路移走（不等于删除）

> **不再高频访问的旧数据，别一直留在在线主表里拖性能。**

**特别适合归档的**（raw 原文）：**执行日志、状态流转记录、任务事件流水**——**保留要求长，但在线查询需求低**。

**归档的三个关键点**：

1. **不是 `DELETE` 完就结束**——**大批 DELETE 本身就是长事务 + 膨胀源**（M13），**要分批 + 低峰执行**；
2. **归档表要有独立的索引与访问路径**（审计查询还是存在的，不能"存进去就找不到"）；
3. **归档要有明确的生命周期与合规口径**（保留多久、谁来查、怎么查）——**这一条是工程之外的纪律，但面试里说出来很加分**。

### 五、分库分表：最后一步，四项代价要背

> **它通常更像最后一步，而不是起手式。**

| 代价 | 说明 |
|---|---|
| **路由变复杂** | 分片键决定数据在哪，**所有查询都要带上分片键，否则广播到所有分片** |
| **聚合和分页更麻烦** | 跨分片的 `count` / `ORDER BY LIMIT` 要**在各分片执行再合并**，深分页几乎不可用 |
| **跨分片事务更难** | 本地事务不再够用，**要么业务上避免跨分片写，要么引入分布式事务（复杂度陡增）** |
| **扩容迁移更重** | 分片数固定后，**扩容要迁移数据（rehash）**，是高风险操作 |

**分片键怎么选**：**按最高频查询路径选**——**让绝大多数查询能带上分片键，避免广播**。**所以分片键不是"数据本身的属性"，而是"你的查询形状的属性"**——**这句话是分片设计的核心**。

**顺带一条**：**MySQL 生态里有成熟中间件（ShardingSphere 之类），但模块边界里明确写了"不深入它的源码"——面试里说"知道选型与代价，未深入源码"是诚实且合格的回答。**

## 二、扩展：类似题与追问

**类似题**

1. 「冷热分离和分库分表的区别？」——**冷热分离是"按时间把数据分层"（同库或不同库），分库分表是"按分片键水平拆分"（多库多表）**。**前者解决"热查询背着冷数据"，后者解决"单机容量/写入上限"**——**两个不同的问题。**
2. 「8000 万行必须分表吗？」——**不一定**。**单表几千万行在索引合理时完全可服务**；**真正的信号是：索引与 SQL 已优化到位、事务已拆批、冷数据已归档，仍然扛不住**。**"行数"从来不是分表的直接理由。**
3. 「归档和分区怎么选？」——**MySQL：两张表 + 定期迁移（应用管理）；PG：分区表 + DROP 分区（数据库管理）**。**PG 的方案更顺——"丢弃分区"几乎瞬时且不产生死元组（P16），MySQL 的"DELETE + 迁移"是长事务与膨胀源（M13）**。**这条对照能同时展示两边的能力差异。**

**追问链**

- 追问一层：**「分片键选错了怎么办？」**——**分片键是"最难改的决定"**：改了要**全量迁移数据**。**所以选型时必须基于真实的查询分布（哪些字段出现在 WHERE 里、频率多少），而不是"字段看起来像 ID"**。**这一条和 P16 的"分区键必须进大部分查询条件"是同一个原则。**
- 追问二层：**「跨分片的事务怎么办？」**——**最好的答案是"业务上避免跨分片写"**（把强一致的数据放同一分片，即"按业务单元分片"）；**实在避免不了，才考虑分布式事务，而那是复杂度的新台阶**。**RuleArena 的设计里有现成对照**：**"至少一次投递 + 幂等消费者 + 权威查询"替代"exactly-once"——跨边界的正确性优先用幂等解决，而不是用强一致事务硬扛**（P19 的结论在这里再次成立）。**这条把三个母题串成了一个方法论。**
