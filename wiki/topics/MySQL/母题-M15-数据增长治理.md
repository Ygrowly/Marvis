# 母题 M15 · 数据增长治理

> **模块**：MySQL / 数据增长与高可用
> **所属主线**：六 · 数据增长与高可用（数据多了怎么不被拖垮）
> **层级**：B · 标准级（"为什么分库分表在最后"能从"复杂度递增 + 可逆性递减"推出来，索引层数与归档成本能算；但五步里每一步的具体手段是取舍）
> **关联母题**：[[母题-M7-慢查询与SQL优化手段]]（第①步）· [[母题-M13-长事务为什么危险]]（第②步 + 归档时的分批）· [[母题-M14-主从复制与延迟]]（第④步的代价）· [[母题-P16-分区表]]（PG 侧的更优解）
> **素材来源**：`raw/后端视角复盘_MySQL` 第六条主线（冷热分离 / 归档 / 读写分离 / 为什么不是一上来就分库分表）。**本轮升级补入：索引层数、归档成本、扩展迁移三组算式、阶梯图、自测题**

**导读**：必懂 3 件事（① "8000 万行"本身不是理由 ② 五步顺序是有依据的，不是偏好 ③ 归档 ≠ 删除）· 读完约 12 分钟 · 需要先懂：[[母题-M13-长事务为什么危险]]（归档时为什么要分批）

**题目**：任务表 8000 万行，执行日志还在以每天百万条增长。你会按什么顺序处理？

**母题**：**冷热分离、归档、读写分离、分库分表——它们分别解决什么？为什么不是一上来就分库分表？**

**为什么重要**：**这是主线六的收口题**，而且它有一个**几乎所有人都会答错的顺序问题**——"数据量大 = 分库分表"。**原始素材给出的五步顺序是这道题的灵魂**，它同时考验**克制（知道什么时候不动）**和**视野（知道每一步解决什么）**。**而且它和 [[母题-P16-分区表]] 合流：有持续清理需求的大表，分区的"丢弃分区"就是归档的最优解。**

## 一、教材

### 1. 前提：先定问题，"大"本身不构成动作的理由

【推导】**"8000 万行"是三种完全不同的问题**，对应完全不同的手段：

| 症状 | 真问题 | 对应手段 |
|---|---|---|
| **查询慢** | 热查询在扫大量冷数据 / 索引不行 | **先 M7（索引与 SQL），再冷热分离** |
| **写入慢 / 锁冲突** | 事务边界大、锁范围大 | **M13 / M10（分批 + 短事务）** |
| **单机容量到顶** | 磁盘 / 内存 / 连接真的不够 | **先归档，最后才分库分表** |

【推论】**所以第一动作是定位症状，而不是拆表**——**"8000 万行"本身不构成任何动作的理由。**

**到这里你应该能回答**：为什么"我们表到 8000 万行了"这句话，面试官听到会先反问"然后呢"？

---

### 2. 五步顺序（必须背，而且要能解释为什么）

::figure data-growth-ladder.svg | 数据增长的治理阶梯：为什么分库分表在最后一步 | 五步按复杂度递增排列，每步标注它解决什么、代价与可逆性

```text
① 先把索引和 SQL 做好
② 再把事务边界和锁冲突管好
③ 然后做冷热分离和归档
④ 再做读写分离
⑤ 单机真的扛不住了，再考虑分库分表
```

【推导】**为什么是这个顺序**：**每一步的复杂度递增，且后面的步骤会改变前面步骤的优化对象**——比如先分了表，再优化索引，索引设计会复杂一倍（每个分片都要建、且要考虑分片键）。

【推论】**判据是一句话：便宜且可逆的先做，贵且难回头的后做。** 而分库分表恰好是**最贵、最难回头**的那一步（见第 5 节）。

---

### 3. 冷热分离：让热查询只打热数据

【事实】原始素材的例子：**最近 7 天的任务日志经常查，半年前的几乎只在审计时查。**

**问题不是"数据太多"，而是"热查询背着冷数据一起跑"。** 具体有两个后果：

#### 3.1 索引更深 → 每次查找多一次 IO【推导】

```text
行宽 1KB、页 16KB → 每页 16 行；扇出按 1170 算

8000 万行：叶子页 = 8000万 ÷ 16 = 500 万页
           500万 ÷ 1170 ≈ 4273 个中间节点
           根（1170 个指针）覆盖不了 4273 → 需要再分一层
           → 树高 = 根 + 二级内部 + 一级内部 + 叶 = 【4 层】

归档后 800 万行：叶子页 = 800万 ÷ 16 = 50 万页
           50万 ÷ 1170 ≈ 427 个中间节点
           根可直接覆盖 427 → 树高 = 根 + 内部 + 叶 = 【3 层】
```

【结论】**数据量降到 1/10，索引层数从 4 层降到 3 层**——同样的点查，**IO 次数少一次**。而且这还没算**冷数据把热数据挤出 buffer pool** 的那部分损失（那部分是无条件的）。

#### 3.2 做法【取舍】

**按时间轴（最自然的切分轴）把近期热数据和历史冷数据分层**——**MySQL 里通常是"两张表 + 定期迁移"**（在线表只留热数据），**PG 里更优解是分区表**——**分区是数据库原生支持的分层，且"丢弃分区即归档"**（[[母题-P16-分区表]]）。**这是两边能力差异的一个直接体现。**

---

### 4. 归档：从在线主链路移走（不等于删除）

> **不再高频访问的旧数据，别一直留在在线主表里拖性能。**

【事实】**特别适合归档的**：**执行日志、状态流转记录、任务事件流水**——**保留要求长，但在线查询需求低**。

**归档的三个关键点**：

1. **不是 `DELETE` 完就结束**——**大批 `DELETE` 本身就是长事务 + 膨胀源**（[[母题-M13-长事务为什么危险]]），**要分批 + 低峰执行**（下面给算式）
2. **归档表要有独立的索引与访问路径**（审计查询还是存在的，**不能"存进去就找不到"**）
3. **归档要有明确的生命周期与合规口径**（保留多久、谁来查、怎么查）——**这一条是工程之外的纪律，但面试里说出来很加分**

#### 4.1 为什么不能一次性 DELETE【推导】

```text
删除 7000 万行冷数据，每次删除产生约 200 字节 undo

一次性 DELETE：
  undo 峰值 ≈ 7000万 × 200B = 14 GB
  锁持有 = 整个删除时长（可能几十分钟）
  而且这是一条【长事务】——purge 全程停摆（M13）

分批（每批 1 万行，共 7000 批）：
  undo 峰值 ≈ 1万 × 200B = 2 MB        （降到 1/7000）
  锁持有 = 单批时长
```

【结论】**"归档"这个动作本身也是数据治理的一部分**——**用错方法的归档，会把长事务问题原样引入一遍。**

**到这里你应该能回答**：为什么"把老数据 DELETE 掉"听起来是清理，实际是制造问题？

### 5. 分库分表：最后一步，四项代价要背

> **它通常更像最后一步，而不是起手式。**

| 代价 | 说明 |
|---|---|
| **路由变复杂** | 分片键决定数据在哪，**所有查询都要带上分片键，否则广播到所有分片** |
| **聚合和分页更麻烦** | 跨分片的 `count` / `ORDER BY LIMIT` 要**在各分片执行再合并**，深分页几乎不可用（[[母题-M7-慢查询与SQL优化手段]] 的深分页问题在这里更难解） |
| **跨分片事务更难** | 本地事务不再够用，**要么业务上避免跨分片写，要么引入分布式事务（复杂度陡增）** |
| **扩容迁移更重** | 分片数固定后，**扩容要迁移数据**（下面给算式），是高风险操作 |

#### 5.1 分片键为什么"最难改"【推导】

```text
从 4 个分片扩到 8 个分片，按 hash 取模分片：

  一个键的归属 = hash(key) % 分片数
  4 分片时：hash % 4
  8 分片时：hash % 8

  若 hash % 8 < 4 → 归属不变（占一半）
  若 hash % 8 ≥ 4 → 归属改变（占一半）

  → 约 50% 的数据需要跨分片迁移
```

【结论】**换分片键或扩分片数 = 一次全量级别的数据迁移。** 所以**分片键是整套设计里最难改的决定**——这也是"能不能用范围分片 / 一致性哈希做局部迁移"值得提前想的原因。

#### 5.2 分片键怎么选【事实】

**按最高频查询路径选**——**让绝大多数查询能带上分片键，避免广播**。

【推论】**所以分片键不是"数据本身的属性"，而是"你的查询形状的属性"**——**这句话是分片设计的核心**。选型时必须基于**真实的查询分布**（哪些字段出现在 `WHERE` 里、频率多少），**而不是"字段看起来像 ID"**。这一条和 [[母题-P16-分区表]] 的"分区键必须进大部分查询条件"是同一个原则。

【事实】顺带一条：**MySQL 生态里有成熟中间件（ShardingSphere 之类）**，但本模块边界里明确写了"不深入它的源码"——**面试里说"知道选型与代价，未深入源码"是诚实且合格的回答**。

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "8000 万行了，赶紧分库分表" | **行数从来不是分表的直接理由**。真正的信号是：**索引与 SQL 已优化到位、事务已拆批、冷数据已归档，仍然扛不住**。而这三件事做完，很多表根本不需要分 |
| "归档就是把历史数据 DELETE 掉" | **归档 ≠ 删除**。① 一次性 `DELETE` 7000 万行是**长事务 + 膨胀源**（undo 峰值 14 GB），必须分批；② 归档表要**保留独立索引与访问路径**（审计还要查）；③ 要有**生命周期与合规口径** |
| "冷热分离和分库分表是一回事" | 完全不是。**冷热分离是"按时间把数据分层"（同库或不同库）；分库分表是"按分片键水平拆分"（多库多表）**。前者解决"热查询背着冷数据"，后者解决"单机容量 / 写入上限" |
| "分片键用 ID 就行" | **分片键是"查询形状的属性"**，不是"数据本身的属性"。选错了会导致**大量查询广播到所有分片**（等于没分）；而且它是**最难改的决定**（换密钥迁移约 50% 数据） |
| "先分表，再慢慢优化索引" | **顺序反了**。分表之后每个分片都要建索引、还要考虑分片键，**复杂度翻倍**；而且分表会改变前面步骤的优化对象（第 2 节的判据） |
| "跨分片事务用分布式事务解决就好" | **最好的答案是"业务上避免跨分片写"**（把强一致的数据放同一分片，即**按业务单元分片**）；实在避免不了才上分布式事务——**那是复杂度的新台阶**（见追问 2） |
| "MySQL 要分库分表，所以 PG 也要" | **PG 侧对应的问题通常是分区设计**，而不是分库分表。**说的时候要说清楚讲的是哪一套** |

【取舍】读成一句话：**"'数据量大'本身不是问题，'热查询背着冷数据跑'才是问题"——所以治理的第一动作永远是"把热和冷分开"，而不是"把大表拆开"。两者听起来像，做的完全是不同的事。**

## 二、自测

**Q1（计算）**：一张表 8000 万行，行宽 1KB、页 16KB（每页 16 行），索引扇出按 1170 算。

问：**这张表的索引是几层？**如果把 90% 的冷数据归档掉（剩 800 万行），索引变成几层？**这对一次点查意味着什么？**

**A1**：

```text
8000 万行：
  叶子页 = 8000万 ÷ 16 = 500 万页
  需要中间节点 = 500万 ÷ 1170 ≈ 4,273 个
  根只有 1170 个指针，覆盖不了 4273 → 需要再加一层
  层数 = 根 + 二级内部 + 一级内部 + 叶 = 【4 层】

800 万行（归档后）：
  叶子页 = 800万 ÷ 16 = 50 万页
  需要中间节点 = 50万 ÷ 1170 ≈ 427 个
  根可直接覆盖 427 → 层数 = 根 + 内部 + 叶 = 【3 层】
```

【结论】**数据量降到 1/10，索引层数从 4 层降到 3 层**——一次点查**少一次 IO（约少 25%）**。

【补充】这还只是"树高"这一笔。**更值钱的是 buffer pool**：冷数据会**把热数据挤出内存**，这部分损失是无条件的（跟查询有没有走索引无关）。所以归档的收益通常比这个算式更大。

**Q2（计算）**：要归档 **7000 万行**冷数据，每次删除产生约 **200 字节** undo。

问：**一次性 `DELETE` 和每批 1 万行分批删除，undo 峰值各是多少？**为什么这个差别不只是"省空间"？

**A2**：

```text
一次性 DELETE 7000 万行：
  undo 峰值 ≈ 7000万 × 200B = 14 GB
  锁持有 = 整个删除时长（几十分钟级）
  性质 = 一个【长事务】

分批（每批 1 万行，共 7000 批）：
  undo 峰值 ≈ 1万 × 200B = 2 MB      （降到 1/7000）
  锁持有 = 单批时长
```

【结论】**差别不只是省空间——是"是不是长事务"这个性质的区别。**

14 GB 的 undo 意味着**purge 在整个删除期间停摆**（[[母题-M13-长事务为什么危险]]）：全库的快照读版本链都在变长、回收边界被按住几十分钟。**分批把它拆成 7000 个短事务，回收可以持续进行。**

【推论】**"归档"这个动作本身也需要用对方法**——**用错方法的归档，会把长事务问题原样引入一遍。**

**Q3（计算）**：一个表按 `hash(key) % 分片数` 分片，当前 **4 个分片**，要扩容到 **8 个**。

问：**大约多少比例的数据需要跨分片迁移？**这对"分片键选型"意味着什么？

**A3**：

```text
4 分片时归属 = hash % 4
8 分片时归属 = hash % 8

若 hash % 8 < 4 → 与 hash % 4 相同 → 归属不变
若 hash % 8 ≥ 4 → 归属改变 → 必须迁移

→ 约 50% 的数据需要跨分片迁移
```

【结论】**扩分片数就要迁移约一半的数据**。而如果**换分片键**（不是扩容），那几乎是 **100% 全量重分布**。

【推论】**分片键是整套设计里最难改的决定**——这也是为什么选型必须基于**真实的查询分布**（哪些字段出现在 `WHERE` 里、频率多少），而不是"字段看起来像 ID"。

【补充】这也是**范围分片 / 一致性哈希**值得考虑的原因：它们能让扩容只迁移**相邻的一部分**，而不是对半分。代价是可能产生热点。

**Q4（纠错）**：下面这段话哪里不准确？

> "我们任务表已经 8000 万行了，再涨下去肯定扛不住，得赶紧安排分库分表。"

**A4**：三处问题。

1. **"8000 万行 = 扛不住"不成立**。**单表几千万行在索引合理时完全可服务**。要先分清是**查询慢**、**写入慢**还是**单机容量到顶**——三者对应完全不同的手段。
2. **跳过了前三步**。正确顺序是：**① 索引与 SQL → ② 事务边界与锁 → ③ 冷热分离与归档 → ④ 读写分离 → ⑤ 分库分表**。**做完前四步，很多表根本不需要分。**
3. **低估了分库分表是"最难回头"的一步**：路由、聚合分页、跨分片事务、扩容迁移（扩一次迁移约 50% 数据）——**这些是长期负担，不是一次性的上线成本**。

【准确说法】"先定位症状：**是查询慢就先优化 SQL 与索引，是热查询背着冷数据就先冷热分离，是容量到顶就先归档**。**只有这些都做完还扛不住，才轮到分库分表**——而那时你已经有数据支撑这个决定了。"

**Q5（纠错）**：下面这段话哪里不准确？

> "归档就是把半年前的日志 DELETE 掉，腾出空间。"

**A5**：三处错。

1. **归档 ≠ 删除**。归档是**把数据从在线主链路移走**，数据本身要保留（审计、合规都还要查）。**直接 DELETE 是销毁，不是归档。**
2. **一次性 DELETE 大表是长事务 + 膨胀源**：7000 万行一次性删会产生约 **14 GB undo**（Q2），**purge 全程停摆**。必须**分批 + 低峰执行**。
3. **归档表要有独立索引与访问路径**，还得有**明确的生命周期与合规口径**（保留多久、谁来查、怎么查）——**否则"归档"就变成了"存进去就找不到"**。

【准确说法】"归档 = **移走 + 可查 + 有生命周期**。执行上要**分批搬、分批删**；在 PG 上还有更优解——**分区表 + `DROP PARTITION`，几乎瞬时且不产生死元组**（[[母题-P16-分区表]]）。"

## 三、面试输出（学完再看）

**一句话结论**：**"数据量大"本身不是问题，"热查询背着冷数据跑"才是问题。** 所以治理顺序是五步：**① 索引与 SQL做好 → ② 事务边界与锁冲突管好 → ③ 冷热分离与归档 → ④ 读写分离 → ⑤ 单机真的扛不住才分库分表**。这个顺序的依据是**"便宜且可逆的先做，贵且难回头的后做"**——而分库分表有**四项代价**：路由变复杂（查询必须带分片键，否则广播）、跨分片聚合分页难、跨分片事务难、**扩容要迁移约 50% 的数据**。**冷热分离**按时间轴把热数据与冷数据分层（8000 万行归档到 800 万行，**索引从 4 层降到 3 层**）；**归档 ≠ 删除**，要分批搬分批删（否则 7000 万行一次性 DELETE 会产生约 14 GB undo、拖成长事务）；**分片键不是"数据本身的属性"，是"查询形状的属性"**，而且它最难改。

**核心不变量 / 主线**：

所以治理的第一动作永远是**把热和冷分开**，而不是"把大表拆开"——**两者听起来像，做的完全是不同的事。**

**完整回答骨架**：先定问题（三选一）→ 五步顺序 + 为什么是这个顺序 → 冷热分离（索引层数算式）→ 归档（≠ 删除 + 分批的算式）→ 分库分表四项代价 + 分片键选法（迁移 50% 的算式）→ 回到题目

**完整回答（口述稿）**：
先定问题：「数据量大」本身不是问题，「热查询背着冷数据跑」才是。所以治理顺序五步：① 索引与 SQL 做好 → ② 事务边界与锁冲突管好 → ③ 冷热分离与归档 → ④ 读写分离 → ⑤ 单机真的扛不住才分库分表。依据只有一条：便宜且可逆的先做，贵且难回头的后做。

冷热分离是按时间轴把热数据与冷数据分层，8000 万行归档到 800 万行，索引从 4 层降到 3 层。归档不等于删除：一次性 DELETE 7000 万行是长事务加膨胀源（undo 峰值到约 14 GB），必须分批搬、分批删；而且归档表要保留独立索引和访问路径，审计还要查。

分库分表有四项代价：路由变复杂（查询必须带分片键，否则广播）、跨分片聚合分页难、跨分片事务难、扩容要迁移约 50% 的数据。分片键是「查询形状的属性」，不是数据本身的属性，选错会导致大量查询广播到所有分片，而它又是最难改的决定。

边界：行数从来不是分表的直接理由，真正的信号是前三步做完仍然扛不住。

**分层要点**：
- **结论**：治理五步，判据是「便宜且可逆的先做」；行数本身不是分表理由。
- **推导链**：问题定义（热查询背冷数据）→ 先便宜后贵 → 冷热分离降索引层数 → 归档必须分批 → 最后才是分库分表（四项代价）。
- **量化**：8000 万 → 800 万行，索引 4 层 → 3 层；一次性删 7000 万行 undo 峰值约 14 GB；扩容要迁移约 50% 的数据。
- **边界与常见误解**：归档 ≠ 删除；冷热分离 ≠ 分库分表（前者按时间分层，后者按分片键水平拆）；分片键用 ID 就行 ×；加从库只降读压力。

**追问**（先说后看）

1. **分片键选错了怎么办？** —— **分片键是"最难改的决定"**：改它要全量重分布数据，扩容也要迁移约 50%。**所以选型必须基于真实的查询分布**，而不是"字段看起来像 ID"。**这和 [[母题-P16-分区表]] 的"分区键必须进大部分查询条件"是同一个原则。**
2. **跨分片的事务怎么办？** —— **最好的答案是"业务上避免跨分片写"**（把强一致的数据放同一分片，即**按业务单元分片**）；实在避免不了才考虑分布式事务——**那是复杂度的新台阶**。**RuleArena 的"至少一次投递 + 幂等消费者 + 权威查询"替代 exactly-once 就是同一思路**：跨边界的正确性优先用幂等解决，而不是用强一致事务硬扛（[[母题-P19-唯一约束与UPSERT]]）。
3. **归档和分区怎么选？** —— **MySQL：两张表 + 定期迁移（应用管理）；PG：分区表 + `DROP` 分区（数据库管理）**。**PG 的方案更顺——"丢弃分区"几乎瞬时且不产生死元组**；MySQL 的 "`DELETE` + 迁移"是长事务与膨胀源。**这条对照能同时展示两边的能力差异。**
4. **8000 万行必须分表吗？** —— **不一定**。单表几千万行在索引合理时完全可服务；**真正的信号是：索引与 SQL 已优化到位、事务已拆批、冷数据已归档，仍然扛不住**。**"行数"从来不是分表的直接理由。**

**同类变体**

- 「冷热分离和分库分表的区别？」——**冷热分离按时间分层（解决"热查询背着冷数据"），分库分表按分片键水平拆分（解决"单机容量 / 写入上限"）**。两个不同的问题。
- 「读写分离排第几步？为什么？」——**第四步**。因为它**要显式处理延迟语义**（[[母题-M14-主从复制与延迟]]），复杂度不是免费的——所以排在"改代码"和"搬数据"之后，排在"改架构"之前。
- 「EnergyOps 的四层事实表算什么？」——**本质上就是应用层的冷热/粒度分离**：Raw 层不直接给报表查，hourly / daily 才给。**这是"冷热分离"思想在数据建模上的体现。**
