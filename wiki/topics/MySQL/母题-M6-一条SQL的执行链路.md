**题目**：一条 `SELECT * FROM task WHERE status='PENDING' LIMIT 10` 从客户端发出到结果返回，中间经历了哪些步骤？每一步都可能因为什么变慢？

**母题**：**MySQL 的 server 层和引擎层各管什么？那条 SQL 慢的时候，你凭什么判断是"哪一层"出了问题？**

**为什么重要**：这是**"会用 SQL"和"能定位慢 SQL"的分界线**。它同时是 M7 的前提——**你必须先知道"慢可以慢在哪几层"，explain 里那些字段才有意义**（`type` 是优化器选的访问方式、`rows` 是它的估算、`Extra` 是执行器阶段的附加动作）。**背得出分层没用，能把"某一层慢"对应到"某个现象"才有用。**

## 一、教材

### 1. 前提：五层链路，每层一句话

::figure sql-pipeline.svg | 一条 SQL 的五层链路，以及「慢」可以慢在哪一层 | 左列五层、中列各层做什么、右列各层可能的慢因；底部把三种慢源收口到 EXPLAIN 的字段

| 层 | 做什么 | 可能因为什么出问题 |
|---|---|---|
| **连接器** | TCP 握手、鉴权、管理连接；长/短连接 | 连接数暴涨、鉴权慢（少见）；**长连接要 `reset_connection` 释放内存** |
| ~~查询缓存~~ | **8.0 已移除** | —— |
| **分析器** | 词法/语法分析，生成解析树 | 语法错误（很快报错，**不会是慢的原因**） |
| **优化器** | **决定用哪个索引、按什么顺序 JOIN、是否用临时表/排序** | **估算错 → 选错索引 → 最常见的慢因** |
| **执行器** | 按计划循环调用引擎接口，判断条件、返回结果 | **逐行回表**（覆盖索引能省掉，[[母题-M3-聚簇索引与回表]]） |
| **InnoDB** | Buffer Pool 命中与否、加锁、写 undo/redo | 缓存冷（随机 IO）、锁等待、日志刷盘 |

【推导】**这五层里只有一层在"做决定"**——优化器。连接器和分析器是固定动作，执行器只是照计划执行，引擎层负责"怎么取"。**所以"SQL 慢"的第一嫌疑人永远是"优化器做错了决定"。** 而它做错的原因通常只有一个：**估算不准**（这条直接连到 [[母题-M7-慢查询与SQL优化手段]]）。

**到这里你应该能回答**：为什么说"SQL 慢"要先怀疑优化器，而不是先怀疑引擎？

### 2. 查询缓存为什么被移除【推导】

缓存键是**整条 SQL 文本**，失效条件是**这张表只要有一个更新就全部失效**。把这两个条件放在一起，就能算出它在写多的表上注定失效：

```text
某表每天被更新 10 万次
  平均更新间隔 = 86400 秒 ÷ 100,000 = 0.864 秒

一条热门 SQL 每 5 秒被请求一次
  两次请求之间平均发生 5 ÷ 0.864 ≈ 5.8 次更新
  → 缓存必然已经被清掉 → 命中率趋近 0
```

【推论】**"查一次缓存白拿"的收益 < "每次更新都要清一堆缓存"的成本。** 这就是它被移除的量化理由。

【事实】这条能推出一个**通用结论**：**任何"以表为粒度整体失效"的缓存，都会在写多的表上失效。** 这正是 EnergyOps 里缓存一致性那部分的设计依据——**事务内写 Outbox / 用版本号做缓存键，而不是"提交完顺手清缓存"**（[[母题-R3-缓存一致性与三类事故]]）。

**到这里你应该能回答**：为什么"给查询加个缓存"这件事，在写多的表上不但没用，还多一份开销？

### 3. 优化器在做哪三个决定【事实】

| 决定 | 依据 | 决定错了会怎样 |
|---|---|---|
| **用哪个索引**（或者干脆不用） | 统计信息里的区分度、扫描代价估算 | **明明有索引却走全表**（[[母题-M2-联合索引与最左前缀]] 里"索引失效的最后一类"） |
| **JOIN 顺序**（谁做驱动表） | 小表驱动大表原则 + 各自的过滤后行数 | **大表驱动小表 → 循环次数爆炸**（下面算） |
| **是否用临时表 / 文件排序** | 排序数据量与内存限制 | **filesort 落盘 → 慢一个数量级** |

#### 3.1 为什么"小表驱动大表"能差三个数量级【推导】

```text
表 A 过滤后 100 行，表 B 过滤后 10 万行

A 驱动 B：外层循环 100 次，每次去 B 的索引里查一次 → 约 100 次索引查找
B 驱动 A：外层循环 10 万次，每次去 A 的索引里查一次 → 约 100,000 次索引查找

差 1000 倍
```

【推论】**外层循环次数 = 驱动表的行数。** 所以"小表驱动大表"不是一个口诀，是**把循环次数按数量级压下来**。

#### 3.2 优化器估算错的代价【推导】

```text
1000 万行的表，WHERE status='DONE'（占 99%）

估算准确（990 万行）→ 应该选全表扫描：
  1000万 ÷ 16 行/页 = 62.5 万页，顺序读

统计信息过期，估成 1000 行 → 选 status 索引：
  990 万行命中，每条都要回表，每次约 3 次随机 IO
  = 990万 × 3 = 2970 万次随机 IO

量级比：2970万 ÷ 62.5万 ≈ 47 倍
```

【结论】**优化器一次估算错误，可以把代价放大近 50 倍。** 所以"加索引"之前应该先问：**统计信息是不是准的？**

**到这里你应该能回答**：为什么"有索引却走全表"有时候是**正确的决定**（[[母题-M2-联合索引与最左前缀]] 会展开）？

### 4. 怎么判断是"哪一层"慢

【事实】`EXPLAIN` 的字段与三种慢源的对应关系（M7 展开）：

```text
① 扫描行数多  → type（访问方式）与 rows（估算行数）
② 回表次数多  → Extra 里的 Using index（覆盖，好事）/ 没有它就要回表
③ JOIN 顺序错 → 看驱动表选择 + Extra 里的 Using temporary / Using filesort
```

【事实】**怎么判断"优化器选错了"**：看 `key`（实际用的索引）与 `rows`（估算扫描行数）——**估算行数和实际差很远时，就是统计信息/选择性出了问题**。

- **MySQL 侧**：主要靠 `ANALYZE TABLE` 更新统计信息；8.0 也有直方图（histogram），但比"加索引"更少被人注意
- **PG 侧**：统计信息体系更完整——扩展统计、直方图、`pg_stat_statements`（[[母题-P7-统计信息与慢查询定位]]）

**到这里你应该能回答**：`EXPLAIN` 里哪个字段对应"回表多"，哪个对应"扫描多"，哪个对应"排序落盘"？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "SQL 慢就是没建索引" | 慢源有三类：**扫描行数多、回表次数多、JOIN 顺序错**。加索引只治第一类，而且**当条件命中比例很高时，全表扫描反而是对的**（优化器选它没错） |
| "查询缓存是 MySQL 的重要优化" | **8.0 已移除**。原因是它**以整表为失效粒度**——写多的表上，更新间隔比请求间隔还短，命中率趋近 0（见第 2 节算式） |
| "优化器会选最优计划" | 它选的是**它估算出来的**最优计划。**估算依赖统计信息**，统计过期/数据倾斜/条件是函数时就会错，代价可达 50 倍 |
| "分层只是为了讲清楚流程" | 分层是**架构约束**：server 层要兼容多种存储引擎，所以"解析、优化、执行"放上层，"存储与事务"由引擎各自实现。**代价是有些优化跨不了层**（比如早期 `count(*)` 必须逐行数，其实引擎知道行数但 server 层不知道） |
| "`rows` 是实际扫描行数" | `EXPLAIN` 的 `rows` 是**估算**；`EXPLAIN ANALYZE`（8.0.18+）才给**实际**行数与耗时。**两者的差就是判断统计信息准不准的直接证据** |

【取舍】读成一句话：**先用 `rows` 估算 vs 实际 的差距判断"是不是优化器的问题"，再用三种慢源判断"是哪一类问题"——顺序不能反。**

## 二、自测

**Q1（计算）**：表 A 过滤后 **100 行**，表 B 过滤后 **10 万行**，两表按等值条件 JOIN，且 B 上有对应索引。

问：**A 驱动 B 和 B 驱动 A 分别要多少次索引查找？差多少倍？**这个结论为什么能推广？

**A1**：

```text
A 驱动 B：外层循环 = A 的行数 = 100
          每次用 A 的一行去 B 的索引里查 → 约 100 次索引查找

B 驱动 A：外层循环 = B 的行数 = 100,000
          每次用 B 的一行去 A 的索引里查 → 约 100,000 次索引查找

倍率 = 100,000 ÷ 100 = 1000 倍
```

【结论】**"小表驱动大表"的本质是：外层循环的次数完全由驱动表的行数决定。** 所以它不是口诀，是**把循环次数按数量级压下来**——两张表差 1000 倍，循环次数就差 1000 倍。

【补充】这也是**优化器把 JOIN 顺序选错**的真实代价。而"哪张表更小"取决于**过滤后**的行数，不是表的原始行数——**加了 WHERE 条件之后，小表可能变成更小的那个**。

**Q2（计算）**：某表每天被更新 **10 万次**。一条热门 SQL 平均每 **5 秒**被请求一次。MySQL 的查询缓存以"整条 SQL 文本"为键、**该表任一更新就全部失效**。

问：**这条 SQL 的缓存命中率大约是多少？为什么？**

**A2**：

```text
平均更新间隔 = 86400 秒 ÷ 100,000 = 0.864 秒
两次请求之间的平均更新次数 = 5 ÷ 0.864 ≈ 5.8 次

→ 每次请求到来时，缓存几乎必然已被某个更新清掉
→ 命中率趋近 0
```

【结论】**缓存的有效窗口（0.864 秒）比请求间隔（5 秒）还短，它注定没有机会被命中。** 而且你还一直在付**维护缓存的成本**（每次更新都要去失效一批条目）。

【补充】**这就是 MySQL 8.0 移除查询缓存的量化理由**，也推出一条通用结论：**任何"以表为粒度整体失效"的缓存，在写多的表上都会退化成纯开销**。要让它有效，必须把失效粒度做细——**按 key 失效、按版本号失效**，而不是按表。

**Q3（计算）**：一张 1000 万行的表，`WHERE status='DONE'` 命中 **99%（990 万行）**。每页 16 行。

问：**如果统计信息是准的，优化器应该选全表扫描还是走 `status` 索引？**如果统计信息过期把结果估成 1000 行，会发生什么？代价差多少？

**A3**：

```text
表总页数 = 1000万 ÷ 16 = 62.5 万页

① 估算准确（990 万行）：优化器应选【全表扫描】
   顺序读 62.5 万页

② 统计过期估成 1000 行：优化器选【status 索引】
   990 万行命中 → 每条都要回表，每次约 3 次随机 IO
   = 990万 × 3 = 2970 万次随机 IO

量级比 = 2970万 ÷ 62.5万 ≈ 47 倍
```

【结论】**优化器一次估算错误，能把代价放大近 50 倍**——而且它还**走对了索引**（`key` 里有值），所以只看"有没有走索引"根本发现不了。

【补充】判断方法：**对比 `EXPLAIN` 的 `rows`（估算）和 `EXPLAIN ANALYZE` 的实际行数**，差一个数量级以上就该 `ANALYZE TABLE`（MySQL）或查 `pg_statistic`（PG，[[母题-P7-统计信息与慢查询定位]]）。

**Q4（纠错）**：下面这段话哪里不准确？

> "SQL 慢基本都是没建索引，加个索引就好了。"

**A4**：三处问题。

1. **慢源有三类，加索引只治第一类**：① 扫描行数多（索引能治）；② **回表次数多**（要靠**覆盖索引**，不是随便加一个索引）；③ **JOIN 顺序错**（要靠改写法或统计信息，加索引无用）。
2. **"有索引却走全表"有时是对的**：当条件命中的行占比很高（如 99%），**回表的随机 IO 会远超全表顺序扫描**——优化器选全表是**正确决定**。见 Q3 的 47 倍。
3. **漏了"估算不准"这一类**：优化器选错计划的根因常常是**统计信息过期**，而不是"缺索引"。**这时候加索引可能让情况更糟**（多一个候选，优化器多一个选错的机会）。

【准确说法】"SQL 慢要先分类：**看 `rows` 估算 vs 实际差多少**（判断是不是优化器的问题）→ 再看是**扫描多、回表多、还是 JOIN 顺序错**（三种慢源）→ 最后才落到具体手段。**加索引只覆盖其中一类，而且不总是对的。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "MySQL 有查询缓存，把结果缓存起来能大幅提升查询性能，我们应该把它打开。"

**A5**：**MySQL 8.0 已经移除查询缓存了**，这句话的前提就不成立。

即使回退到 5.7，它的问题也是结构性的：

- **缓存键是整条 SQL 文本**：多一个空格、大小写不同就是不同的缓存项
- **失效粒度是整张表**：这张表**任一**更新，该表所有查询的缓存全部失效

【量化】一个每天更新 10 万次的表，**缓存平均存活 0.864 秒**；而热门 SQL 每 5 秒请求一次 → **命中率趋近 0**（Q2）。

【准确说法】"要缓存也是**在应用层按业务键缓存**（粒度可控、失效可控），而不是依赖数据库的整表级查询缓存。**粒度决定成败**——这正是 Redis 那套缓存设计要解决的核心问题（[[母题-R3-缓存一致性与三类事故]]）。"

## 三、面试输出（学完再看）

**一句话结论**：一条 SQL 走五层——**连接器**（鉴权与连接管理）→ **分析器**（词法/语法解析）→ **优化器**（选索引、选 JOIN 顺序、决定是否临时表/排序）→ **执行器**（按计划逐行调用引擎接口）→ **InnoDB 引擎层**（Buffer Pool、索引、事务）。**server 层管"功能与计划"，引擎层管"数据怎么存怎么取"。** 五层里**只有优化器在做决定**，所以"SQL 慢"的第一嫌疑人是**它估算错了**——一次估算错误能把代价放大近 50 倍（990 万行回表 vs 62.5 万页全表扫）。慢的根源收口成三类：**扫描行数多、回表次数多、JOIN 顺序错**——每一个都能在 `EXPLAIN` 的字段上找到对应位置。

**恢复关键词**：连接器 / 查询缓存（8.0 已移除，整表失效故命中率趋零）/ 分析器 / **优化器是唯一做决定的一层** / 执行器逐行回表 / Buffer Pool / server 层 vs 引擎层（分层为可插拔，代价是有些优化跨不了层）/ 三种慢源 / **rows 是估算、EXPLAIN ANALYZE 才是实际** / 小表驱动大表 = 外层循环次数 = 驱动表行数

**核心不变量 / 主线**：
**优化器是整条链路里唯一"做决定"的环节**——它决定走哪个索引、按什么顺序 JOIN。
**所以"SQL 慢"的第一嫌疑人永远是"优化器做错了决定"，而它做错的原因通常是"统计信息估算不准"。**

**完整回答骨架**：五层链路各一句 → 只有优化器在做决定（这是题眼）→ 查询缓存为什么被移除（给失效窗口算式）→ 优化器的三个决定 + 各自错了会怎样 → 三种慢源与 explain 字段的对应 → 收束到"先看 rows 估算 vs 实际，再分类"

**完整回答（口述稿）**：
一条 SQL 走五层：连接器（鉴权与连接管理）→ 分析器（词法语法解析）→ 优化器（选索引、选 JOIN 顺序、决定是否用临时表和排序）→ 执行器（按计划逐行调引擎接口）→ InnoDB 引擎层（Buffer Pool、索引、事务）。分工一句话：server 层管功能与计划，引擎层管数据怎么存怎么取。这个分层是架构约束——server 层要兼容多种引擎，代价是有些优化跨不了层。

题眼是：五层里只有优化器在做决定。所以「SQL 慢」的第一嫌疑人是它估算错了——它选的是「它估算出来的」最优计划，而估算依赖统计信息，统计过期、数据倾斜、条件带函数时就会错，代价能放大近 50 倍（990 万行回表对 62.5 万页全表扫）。慢的根源收口成三类：扫描行数多、回表次数多、JOIN 顺序错，每一类对应 EXPLAIN 里不同的字段。

另外 8.0 已经移除查询缓存：它以整表为失效粒度，写多的表上更新间隔比请求间隔还短，命中率趋近 0。最后提醒：EXPLAIN 的 rows 是估算值，要看实际值得用 EXPLAIN ANALYZE（8.0.18+）。

**分层要点**：
- **结论**：五层链路里只有优化器在做决定，所以慢的第一嫌疑人是它估算错；慢源三类——扫描多、回表多、JOIN 顺序错。
- **推导链**：分层是架构约束（server 要兼容多引擎）→ 决定集中在优化器 → 估算依赖统计信息 → 统计过期 / 数据倾斜 / 条件带函数会算错 → 代价被放大。
- **量化**：估算错时 990 万行回表 vs 62.5 万页全表扫（近 50 倍）；查询缓存以整表为失效粒度，写多场景命中率趋近 0。
- **边界与常见误解**：SQL 慢 ≠ 没建索引（条件命中比例高时全表扫是对的）；优化器选的是估算最优，不是真实最优；rows 是估算，实际值看 EXPLAIN ANALYZE。

**追问**（先说后看）

1. **优化器怎么估行数？** —— 按**索引的区分度（基数）统计**：`SHOW INDEX` 的 `cardinality`。**估不准的常见原因**：统计信息过期、数据倾斜（某个值占 90% 行）、条件是表达式/函数。**PG 侧有扩展统计和更完整的直方图**，MySQL 8.0 也有直方图，但两者都比"加索引"更少被人注意。
2. **server 层和引擎层为什么要分开？** —— 因为 **server 层要兼容多种存储引擎**（MyISAM/Memory/InnoDB），所以"解析、优化、执行"放上层，"存储与事务"由引擎各自实现。**代价**：有些优化跨不了层（早期 `count(*)` 必须逐行数，其实引擎知道行数但 server 层不知道）。**能说出"分层是为可插拔、代价是有些优化跨不了层"，说明理解了架构取舍。**
3. **一条 UPDATE 的链路和 SELECT 差在哪？** —— 多了**两阶段提交**（[[母题-M11-三日志与两阶段提交]]）与**锁获取**（[[母题-M10-锁与死锁]]）；而且 UPDATE 是**当前读**（[[母题-M9-MVCC]]），不走 MVCC 快照。**这条能把 M9/M10/M11 三张卡串起来。**
4. **长连接和短连接怎么选？** —— 长连接省握手与鉴权，但**连接对象的内存会随执行增长**，所以要定期 `reset_connection`；短连接每次都付握手 + 鉴权成本。**连接池是两者的折中**（PG 那边连接池是刚需，见 [[母题-P17-连接模型与连接池]]）。

**同类变体**

- 「一条 SQL 到了 InnoDB 之后怎么取数据？」——按执行计划给的方式（全表扫 / 走某个索引）访问，**二级索引命中后回聚簇索引取整行**；行数据在 Buffer Pool 命中就直接返回，未命中才读盘（[[母题-M3-聚簇索引与回表]]）。
- 「为什么要 `ANALYZE TABLE`？」——因为它更新优化器依赖的**统计信息**。**估算不准是"走错计划"的头号原因**，而它比加索引便宜得多、也更容易被忽略。
