# 母题 M6 · 一条 SQL 的执行链路

> **模块**：MySQL / SQL 执行与优化
> **所属主线**：二 · SQL 执行与优化（一条 SQL 到底怎么走、慢在哪）
> **关联母题**：[[母题-M7-慢查询与SQL优化手段]] · [[母题-M5-引擎与表设计基本盘]]
> **素材来源**：`raw/Mysql面试题-2026-09-07T004734+0800.md` 第 1.12 节（查询执行过程）+ 通用知识（**各层细节待你核对**）

**题目**：一条 `SELECT * FROM task WHERE status='PENDING' LIMIT 10` 从客户端发出到结果返回，中间经历了哪些步骤？每一步都可能因为什么变慢？

**母题**：MySQL 的 server 层和引擎层各管什么？优化器在做什么决定？

**为什么重要**：这是**"会用 SQL"和"能定位慢 SQL"的分界线**。它同时是 M7 的前提——**你必须先知道"慢可以慢在哪几层"，explain 里那些字段才有意义**（`type` 是优化器选的访问方式、`rows` 是它的估算、`Extra` 是执行器阶段的附加动作）。**背得出分层没用，能把"某一层慢"对应到"某个现象"才有用。**

**一句话结论**：**连接器**（鉴权与连接管理）→ **分析器**（词法/语法解析）→ **优化器**（选索引、选 JOIN 顺序、生成执行计划）→ **执行器**（按计划逐行调用引擎接口）→ **InnoDB 引擎层**（Buffer Pool、索引、事务）→ 返回。**server 层管"功能与计划"，引擎层管"数据怎么存怎么取"**；慢的根源通常只有三种——**扫描行数多、回表次数多、JOIN 顺序错**。

**恢复关键词**：连接器 / 查询缓存（8.0 已移除）/ 分析器 / 优化器 / 执行器 / Buffer Pool / server 层 vs 引擎层 / 三种慢源

**核心不变量 / 主线**：
**优化器是整条链路里唯一"做决定"的环节**——它决定走哪个索引、按什么顺序 JOIN。**所以"SQL 慢"的第一嫌疑人永远是"优化器做错了决定"，而它做错的原因通常是"估算不准"**（这条直接连到 M7）。

**完整回答骨架**：五层链路各一句 → 查询缓存为什么被移除 → 优化器在决定什么 → 三种慢源 → 与 explain 字段的对应关系

## 原理分解

### 一、五层链路（每层一句话说清）

| 层 | 做什么 | 可能因为什么出问题 |
|---|---|---|
| **连接器** | TCP 握手、鉴权、管理连接；长/短连接 | 连接数暴涨、鉴权慢（少见）；**长连接要 `reset_connection` 释放内存** |
| ~~查询缓存~~ | **8.0 已移除** | —— |
| **分析器** | 词法/语法分析，生成解析树 | 语法错误（很快报错，不会是慢的原因） |
| **优化器** | **决定用哪个索引、按什么顺序 JOIN、是否用临时表/排序** | **估算错 → 选错索引 → 这是最常见的慢因** |
| **执行器** | 按计划循环调用引擎接口，判断条件、返回结果 | **逐行回表**（覆盖索引能省掉，M3） |
| **InnoDB** | Buffer Pool 命中与否、加锁、写 undo/redo | 缓存冷（随机 IO）、锁等待、日志刷盘 |

### 二、为什么"查询缓存"被移除了（常见追问）

缓存键是**整条 SQL 文本**，失效条件是**这张表只要有一个更新就全部失效**：

- 对**更新频繁**的表，命中率极低，还带来维护开销；
- **"查一次缓存白拿"的收益 < "每次更新都要清一堆缓存"的成本**。

**这条能推出一个通用结论**：**任何"以表为粒度整体失效"的缓存都会在写多的表上失效**——这正是 EnergyOps 里"缓存一致性"那部分的设计依据（事务内写 Outbox / 版本缓存键，而不是"提交完顺手清缓存"）。

### 三、优化器在决定什么（这是本题的核心）

| 决定 | 依据 | 决定错了会怎样 |
|---|---|---|
| **用哪个索引**（或者干脆不用） | 统计信息里的区分度、扫描代价估算 | **明明有索引却走全表**（M2 里"索引失效的最后一类"） |
| **JOIN 顺序**（谁做驱动表） | 小表驱动大表原则 + 各自的过滤后行数 | **大表驱动小表 → 循环次数爆炸** |
| **是否用临时表 / 文件排序** | 排序数据量与内存限制 | **filesort 落盘 → 慢一个数量级** |

**判断"优化器选错了"的方法**：`EXPLAIN` 里看 `key`（实际用的索引）与 `rows`（估算扫描行数）——**估算行数和实际差很远时，就是统计信息/选择性出了问题**（PG 的对应解法见 P7；MySQL 侧主要靠 `ANALYZE TABLE` 更新统计信息）。

### 四、三种慢源（收口）

```
① 扫描行数多      → 索引没命中 / 选择性差 / 估算错
② 回表次数多      → 二级索引没覆盖，命中的每一行都要回聚簇索引（M3）
③ JOIN 顺序错     → 驱动表选错，循环次数爆炸
```

**对应到 explain 的读法**（M7 展开）：`type` 与 `rows` 对应 ①，`Extra` 里的 `Using index`（覆盖）/`Using filesort`（排序）/`Using temporary`（临时表）对应 ②③。

## 二、扩展：类似题与追问

**类似题**

1. 「一条 UPDATE 的链路和 SELECT 差在哪？」——多了**两阶段提交**（M11）与**锁获取**（M10）；而且 update 是**当前读**（M9），不走 MVCC 快照。**这条能把 M9/M10/M11 三张卡串起来。**
2. 「长连接和短连接怎么选？」——长连接省握手与鉴权，但**连接对象内存会随执行增长**，所以要定期 `reset_connection`；短连接每次都付握手 + 鉴权成本。**连接池（PG 那边是刚需，MySQL 侧主要靠应用侧池）是两者的折中。**
3. 「一条 SQL 到了 InnoDB 之后怎么取数据？」——按执行计划给的方式（全表扫 / 走某个索引）访问，**二级索引命中后回聚簇索引取整行**，行数据在 Buffer Pool 命中就直接返回，未命中才读盘。

**追问链**

- 追问一层：**「优化器怎么估行数？」**——按**索引的区分度（基数）统计**：`SHOW INDEX` 的 cardinality。**估算不准的常见原因**：统计信息过期、数据倾斜（某个值占了 90% 行）、条件是表达式/函数。**PG 侧有扩展统计和更完整的直方图，MySQL 8.0 也有直方图（histogram），但两者都比"加索引"更少被人注意**——这条是 M7 的核心。
- 追问二层：**「server 层和引擎层为什么要分开？」**——因为 **server 层要兼容多种存储引擎**（MyISAM/Memory/InnoDB，M5），所以"解析、优化、执行"这些通用能力放在 server 层，"存储与事务"由引擎各自实现。**代价**：有些优化做不了跨层（例如早期的 count(*) 全表扫描必须逐行数，引擎其实知道行数但 server 层不知道）。**能说出"分层是为了可插拔、代价是有些优化跨不了层"，说明理解了架构取舍。**
