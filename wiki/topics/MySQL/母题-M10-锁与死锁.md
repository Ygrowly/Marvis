# 母题 M10 · 锁与死锁

> **模块**：MySQL / 事务与锁
> **所属主线**：三 · 事务与锁（并发改同一份数据，为什么不会乱）
> **关联母题**：[[母题-M9-MVCC]] · [[母题-M8-隔离级别与ACID]] · [[母题-M16-乐观锁与悲观锁]]
> **素材来源**：`raw/后端视角复盘_MySQL` 第四条主线（锁为什么会变大、死锁怎么来）+ `raw/Mysql面试题` 第 4 节（4.3 临键锁 / 4.6 死锁日志）

**题目**：`WHERE status='PENDING' FOR UPDATE` 明明只想锁几行，为什么**插入**被卡住了？多个 Worker 还互相锁住了。为什么？

**母题**：行锁、间隙锁、next-key lock 各锁什么？锁为什么会变大？死锁怎么来、怎么排查、怎么避免？

**为什么重要**：**raw 里明确说这是"面试高频题 + 线上高频坑"**。它有一个几乎必考的反直觉点——**"行锁 = 只锁一行"是错的**：**InnoDB 锁的范围和索引扫描路径强相关**，不是 `WHERE id=1` 就只锁一行。**而且它和 PG 那边形成一组非常有说服力的对照：MySQL 用间隙锁"挡住"插入，PG 干脆没有间隙锁（P10）。**

**一句话结论**：三种锁——**Record Lock 锁记录本身；Gap Lock 锁"记录之间的区间"，阻止插入；Next-Key Lock = 记录 + 前面的间隙（RR 下的默认单位）**。**锁变大的原因只有一个：它锁的是"扫描到的索引范围"，不是"WHERE 里写的行"**——所以非唯一索引命中、索引路径不精确、范围条件（`<= now()`、`BETWEEN`、非唯一状态过滤）都会把锁扩大。**死锁 = 多个事务拿锁顺序不一致形成循环等待**；排查用 `SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK`；避免靠**精确索引 + 短事务 + 一致顺序 +（队列场景）`SKIP LOCKED`**。

**恢复关键词**：Record / Gap / Next-Key Lock / **锁的是扫描到的索引范围** / 范围条件高危 / 死锁=顺序不一致 / `SKIP LOCKED` / `SHOW ENGINE INNODB STATUS` / 统一加锁顺序

**核心不变量 / 主线**：
**锁冲突、死锁，追到根上不是"数据库不行"，而是「查询路径、事务边界、资源访问顺序」没设计好。**（raw 原话）——**所以解法永远先在这三件事上，而不是换数据库或调参数。**

**完整回答骨架**：三种锁各锁什么 → 为什么会锁大（三个原因 + 一句话原理）→ 死锁怎么来 → 怎么避免（五条）→ 怎么排查 → 队列场景的专门解法

## 原理分解

### 一、三种锁：各锁什么

| 锁 | 锁什么 | 谁在用 |
|---|---|---|
| **Record Lock** | 索引记录本身 | 等值命中唯一索引 |
| **Gap Lock** | **两条记录之间的"区间"**（不含记录本身），**阻止往这个区间插入** | RR 下的范围查询 |
| **Next-Key Lock** | **记录 + 它前面的间隙**（左开右闭），RR 下的默认加锁单位 | RR 下的当前读 |

**关键理解**：**Gap Lock 的存在理由就是"防幻读"**——锁住区间，别人插不进来，下次查询行数就不会变。**而它也是"锁大"的元凶**：为了防幻读，它锁住的比你要的行多。

**另一个必须知道的边界**：**间隙锁只在 RR（及串行化）下存在**；RC 下没有间隙锁，**所以 RC 下不会"因为 gap 锁把插入卡住"，但会有幻读**。**隔离级别决定了锁的行为**——这把 M8 和 M10 连起来了。

**还有一个精度细节**：**锁是加在索引上的**。如果 WHERE 条件**没有可用索引**，InnoDB 只能**全表扫描并把所有记录都锁住**（相当于锁全表）——**"什么时候锁全表"的答案就是这里**。

### 二、锁为什么会变大（raw 的三条 + 原理）

| 原因 | 例子 |
|---|---|
| **① 不是唯一索引精确命中** | `WHERE id=? FOR UPDATE`（唯一索引等值）锁得小；换成**状态扫描**就大了 |
| **② 索引路径不精确** | 没走到合适的索引，**扫描了更多记录**，锁跟着变大 |
| **③ 范围条件天然高危** | `<= now()`、`BETWEEN`、**非唯一状态过滤**——带出 gap / next-key lock |

**原理一句话（本题题眼）**：

> **它锁的不是最终返回给你的那几行，而是扫描到的索引范围。**

**所以线上的典型现象**：**明明只查了几条，插入却被卡住**——因为被锁住的是"扫过的那些索引记录 + 它们之间的间隙"，**新插入的行恰好落在某个间隙里**。

### 三、死锁怎么来

**死锁不是"数据库坏了"，而是多个事务拿锁顺序不一致，形成循环等待**：

```
事务 A：先锁任务 1，再锁任务 2
事务 B：先锁任务 2，再锁任务 1
   ↓
A 等 B 释放 2，B 等 A 释放 1 → 循环等待
```

**InnoDB 会自动检测死锁并回滚其中代价较小的事务**（不是永远等下去）——**所以死锁的表现通常是"某次请求报 Deadlock found"，而不是系统卡死**。

### 四、怎么避免（raw 的五条 + 一条补充）

```
① 让查询命中更精确的索引          → 缩小锁范围（本题第一条原理的直接应用）
② 缩小事务范围                    → 持锁时间短，窗口小
③ 避免长时间持锁                  → 事务里不放 RPC / 网络 / 复杂计算（M13）
④ 多个事务按一致顺序访问资源       → 比如总是按主键升序更新，消除循环等待
⑤ 队列式场景用 SKIP LOCKED        → 直接跳过被别人锁住的行，不排队
```

**`SKIP LOCKED`（8.0+）值得专门讲**：任务抢占场景里，多个 Worker 都在捞同一批任务，传统做法是排队等锁；**`FOR UPDATE SKIP LOCKED` 让后来者直接跳过被锁住的行**——**"别人在处理的任务我不碰"，天然适合队列**。**这条是"用查询语义替代等待"的一个漂亮例子**，也是 raw 里点名的思路。

### 五、怎么排查

| 工具 | 看什么 |
|---|---|
| `SHOW ENGINE INNODB STATUS` | **`LATEST DETECTED DEADLOCK`** 段：两个事务各自持有什么锁、在等什么锁、执行到了哪条 SQL——**死锁分析的起点** |
| `performance_schema.data_locks` / `data_lock_waits` | **当前**正在持有的锁与等待关系（实时排查阻塞） |
| `information_schema.innodb_trx` | 正在运行的事务（找长事务，M13） |

**排查的正确顺序**：**先看是谁在等谁（锁等待），再回溯事务的加锁顺序**——**最终答案几乎总是"顺序不一致"或"事务太大"**（回到核心不变量）。

## 二、扩展：类似题与追问

**类似题**

1. 「共享锁（S）和排他锁（X）的区别？」——**S 锁之间兼容**（都可以读），**S 与 X、X 与 X 互斥**；`FOR SHARE` 加 S 锁，`FOR UPDATE` 加 X 锁。**行锁的类型（S/X）与粒度（Record/Gap/Next-Key）是两个维度，别混。**
2. 「表锁、页锁、行锁？」——**InnoDB 只有行锁（和表级的意向锁）**；MyISAM 是表锁。**意向锁（IS/IX）的作用是"表明行锁意图"，让表锁请求不必逐行检查**——知道这一条就够了。
3. 「RR 下一个普通 `SELECT` 会加锁吗？」——**不会**（快照读，M9）；**只有当前读才加锁**。**所以"读很多"的报表查询在 MySQL 下不会互相锁**（但会持有 ReadView，M13）。

**追问链**

- 追问一层：**「为什么唯一索引等值命中不产生间隙锁？」**——因为**精确命中后没有"下一个要挡的间隙"需要保护**（记录已定位，不存在"再插入一条相等键"的可能性——唯一约束保证了）。**所以"精确命中唯一索引"是锁范围最小的情形，这正好和 M5 的"主键要精确"呼应。**
- 追问二层：**「为什么这个场景你项目里没用 FOR UPDATE？」**——（RuleArena 的取舍）**任务认领是低频写、读多写少**：`FOR UPDATE` 在 MySQL 里还会带出 next-key lock（状态扫描是范围条件，正好命中上面 ③），**锁大 + 死锁风险 + 排队等待**三样都来了；**条件更新（乐观锁，M16）一次原子写解决，重复执行第二次影响 0 行**。**这正是"锁大"这条机制决定工程选择的实例。**
