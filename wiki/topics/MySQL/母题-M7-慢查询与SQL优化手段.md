## 一、教材

### 1. 前提：所有优化都在做同一件事

**让"扫过的行"尽量等于"要返回的行"。**

```text
两者差距越大越慢，差距只有两个来源：
  ① 没命中的扫描——该过滤的没提前过滤
  ② 白拿的回表——取回了不用的列 / 索引没覆盖
```

【推论】**每一种优化手段都能归到这两类里**——归不进去的，说明你还没搞清它在治什么。这也是后面那份清单的组织方式（少扫 / 少回 / 少排）。

---

### 2. 定位三步【事实】

```text
① 慢查询日志（long_query_time）→ 把问题 SQL 抓出来
   先按【出现频率 × 单次耗时】排优先级——高频的中等慢比低频的极慢更值钱
② EXPLAIN 看计划 → 判断问题类型
③ 按类型动手 → 再 explain 验证，最后压测确认
```

**`EXPLAIN` 四个字段的读法**：

| 字段 | 看什么 |
|---|---|
| `type` | 访问方式，**从好到坏**：`system > const > eq_ref > ref > range > index > ALL`。**`ALL` = 全表扫；`index` = 扫全索引（比 ALL 好一点，也危险）** |
| `key` | 实际用的索引。**`possible_keys` 有值但 `key` 为 NULL → 优化器主动放弃了**（见第 5 节） |
| `rows` | **估算**扫描行数——与实际差很远时说明统计信息/选择性有问题 |
| `Extra` | `Using index`（覆盖，好）/ `Using filesort`（额外排序）/ `Using temporary`（临时表）/ `Using index condition`（下推生效） |

**到这里你应该能回答**：为什么定位的第一步是"排序"，而不是"看到一条慢 SQL 就改"？

### 3. 优化手段清单（按"少扫 / 少回 / 少排"归类）

#### 3.1 少扫：让过滤更早发生【事实】

- **最左前缀设计**：等值列在前、范围列在后（[[母题-M2-联合索引与最左前缀]]）
- **能用定位键就不要用偏移量**：`WHERE id > ?` 而不是 `LIMIT 1000000, 10`
- **不要 `SELECT *`**：列少了，优化器才可能选覆盖索引

#### 3.2 少回：让索引自己回答完【事实 + 推导】

- **覆盖索引**：把 `SELECT` 的列都放进索引（[[母题-M3-聚簇索引与回表]]）
- **索引下推 ICP（5.6+）**：`(age, name)` 索引下，`age=18 AND name LIKE '%三'` 可以**在索引层先过滤 name**——**把"符合条件才回表"变成"索引层就过滤掉不合格的"**。`EXPLAIN` 里显示 `Using index condition`。

**ICP 的收益能算出来**：

```text
索引 (age, name)，age=18 命中 10,000 行，其中 name LIKE '%三' 只命中 100 行

无 ICP：10,000 行全部回表，再在 server 层过滤 name → 10,000 次回表
有 ICP：索引层先过滤 name → 只回表 100 行

降 100 倍
```

【推论】**ICP 治的是"回表次数"，不是"扫描量"**——扫过的索引项没变，变的是"哪些需要回表"。**关键词永远是"回表次数"。**

#### 3.3 少排：避免额外排序与临时表【事实】

- **让索引顺序匹配 `ORDER BY`**（索引本身有序，天然省 filesort）
- **小表驱动大表**：`in` / `exists` 的选择、JOIN 的驱动表顺序（[[母题-M6-一条SQL的执行链路]] 算过 1000 倍的差别）
- **`GROUP BY` 尽量走索引列**，避免临时表

**几个"知道就行"的点**：`count(*)` ≈ `count(1)` > `count(列)`（要判空）；**`count(*)` 没有捷径，InnoDB 是真数**（只有 MyISAM 有行数缓存——但业务表不该用 MyISAM）。

**到这里你应该能回答**：为什么"加了索引但还是慢"经常是因为缺的不是索引，是**覆盖**？

### 4. 深分页为什么慢【推导】

```text
LIMIT 1000000, 10 不是"取 10 行"
而是"取前 1,000,010 行，丢掉前 100 万行"
```

【推论】**扫描与回表量 = 偏移量**，所以**越翻越慢**——而且这是**线性增长**，第 100 万页的代价是第 1 页的 10 万倍。

#### 4.1 两种解法【事实】

**① 游标定位（首选）**：记住上一页最后一条的排序键，下一页用条件跳过去

```sql
SELECT ... WHERE id > :last_id ORDER BY id LIMIT 10;   -- 恒定扫描 10 行
```

**② 延迟关联**：必须跳页时，先用覆盖索引把 `id` 捞出来，再回表取详情

```sql
SELECT t.* FROM task t
JOIN (SELECT id FROM task ORDER BY id LIMIT 1000000, 10) s ON t.id = s.id;
```

**子查询走覆盖索引（只扫索引，不回表）**，**回表只发生在最后 10 行上**——**把"100 万次回表"降成"10 次回表"**。

#### 4.2 两者的差别在哪【取舍】

```text
① 游标定位：扫描量 100 万 → 10     、回表 100 万 → 10      （两个都降）
② 延迟关联：扫描量 100 万 → 100 万  、回表 100 万 → 10      （只降回表）
```

**所以能拿到上一页排序键时，① 优于 ②**。② 的适用场景是**必须跳到任意页**（用户直接点第 1000 页、或者外部传入 offset）时——**它是"无法用游标"时的退路，不是首选**。

::figure deep-pagination.svg | 深分页：三种写法的扫描量与回表量 | 直接 LIMIT 要扫 100 万零 10 行并逐行回表；游标定位只扫 10 行；延迟关联扫描量没降但回表从 100 万降到 10

**到这里你应该能回答**：为什么说"深分页的代价 = 偏移量"？

### 5. 优化器主动放弃索引（最容易被漏掉的一类）【推导】

**现象**：索引存在、条件也该走索引，`EXPLAIN` 却显示 `key = NULL`、全表扫。

**原因**：优化器**估算过成本**——当它判断"走索引 + 大量回表"比"顺序扫全表"更贵时，**主动放弃索引是正确行为**。典型触发：

- 二级索引**命中比例过高**（比如要取 30% 的行）
- **统计信息过期**（行数/区分度估错）
- 条件是**表达式 / 函数 / 隐式类型转换**（M2 的失效清单）

【取舍】**排查顺序不能反**：**先看是不是"写法问题"（照 M2 的失效清单过一遍），再看是不是"成本判断"**。后者的改法不是改 SQL，而是：

1. `ANALYZE TABLE` 更新统计信息
2. 用 `FORCE INDEX` 验证"走了索引确实更快"——**确认判断确实错了再强推**
3. 或者**接受全表扫**——命中比例高时它本来就是对的

【推论】**这一条把"索引失效"从"背清单"升级成"理解优化器的成本模型"。** 面试里能主动说出"有时候全表扫是优化器的正确决定"，比背出十条失效场景更能证明你懂原理。

**到这里你应该能回答**：为什么"有索引却没用上"不能直接判定为 bug？

### 6. 优化优先级（收口）

```text
① 先缩小业务范围（别把不相关的行扫进来）
② 再修 JOIN 逻辑与 N+1
③ 再建/改索引（含覆盖索引、下推）
④ 再改写 SQL（深分页、排序、count）
⑤ 最后才考虑缓存、预聚合、架构（M15）
```

【事实】**EnergyOps 的实际顺序就是这条**：修范围与 JOIN → 建联合索引 → 消 N+1 → 才谈缓存。**反过来做（先上缓存）是典型的"在错误的链路上加速"**——缓存只是把慢查询挡住，慢查询本身还在那里，而且会随着数据增长变得更慢。

### 7. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "索引失效一定是写法问题" | **不一定**。有一类恰恰是**优化器算过成本后主动放弃**（命中比例过高时走索引+回表反而更贵）——这时全表扫是**正确决定**，要动的是统计信息或接受它 |
| "深分页改成延迟关联就不慢了" | **只降回表，不降扫描量**。能拿到上一页排序键时，**游标定位（`WHERE id > ?`）两个都降**，才是首选；延迟关联是"必须跳页"时的退路 |
| "加索引能解决慢查询" | 只治三类慢源里的一类。**回表多要靠覆盖索引，JOIN 顺序错要靠改写法/统计信息**——加索引无效 |
| "`count(1)` 比 `count(*)` 快" | **在 InnoDB 里基本一样**。真正慢的是 `count(列)`（要判 NULL）。而 `count(*)` 慢的根因是 **InnoDB 没有行数缓存、必须真数**——不是写法问题，是机制问题 |
| "`ORDER BY` 走了索引就不慢了" | 排序只占成本的一部分。**排序走了索引只解决"少排"，不解决"少扫少回"**——`SELECT *` 带来的大量回表照样拖慢 |
| "优化就是把 explain 里的 type 调到 ref 以上" | `type` 是**结果**不是目标。目标是"扫过的行 ≈ 要返回的行"，有时**全表扫（ALL）反而是达成这个目标的方式**（当条件命中 99% 时） |

【取舍】读成一句话：**先分类再动手——用 `rows` 估算 vs 实际判断"是不是优化器的问题"，用三种慢源判断"是哪一类问题"，最后才落到具体手段。**

## 二、自测

**Q1（计算）**：某表用 `LIMIT 1000000, 10` 翻页。

问：**这条 SQL 实际扫描多少行？**如果走的是二级索引（需要回表），**回表多少次？**换成游标定位 `WHERE id > :last_id LIMIT 10` 之后呢？

**A1**：

```text
LIMIT 1000000, 10
  实际扫描 = 1,000,000 + 10 = 1,000,010 行（前 100 万行全部丢弃）
  走二级索引时：前 100 万行每行都要回表 → 1,000,000 次回表
  随机 IO 估算：1,000,000 × 3 ≈ 300 万次

游标定位 WHERE id > :last_id ORDER BY id LIMIT 10
  扫描 = 10 行（直接用有序索引跳到位置）
  回表 = 10 次
```

【结论】**扫描量的差距是 100,001 倍**（1,000,010 ÷ 10），回表差距是 100,000 倍。

【关键】这个差距**随偏移量线性增长**——第 1000 万页时就是 1000 倍的差距。所以"越翻越慢"不是偶发问题，是**结构性的**。

**Q2（计算）**：索引是 `(age, name)`，查询 `WHERE age = 18 AND name LIKE '%三'`。`age = 18` 命中 **10,000 行**，其中 `name LIKE '%三'` 只命中 **100 行**。

问：**没有 ICP 和有 ICP 分别要回表多少次？**ICP 降的是扫描量还是回表量？

**A2**：

```text
无 ICP：
  索引只能定位 age = 18 的段 → 这 10,000 行【全部回表】
  回到 server 层才过滤 name LIKE '%三' → 白回了 9,900 次
  回表次数 = 10,000

有 ICP：
  在【索引层】就过滤 name LIKE '%三'
  只有合格的 100 行需要回表
  回表次数 = 100

降幅 = 100 倍
```

【结论】**ICP 降的是"回表量"，不是"扫描量"**——扫过的索引项还是那 10,000 个（`name LIKE '%三'` 这类前置通配也没法用索引定位），**但需要回表的从 10,000 降到 100**。

【推论】**所以 ICP 的价值完全取决于"回表有多贵"**：如果回表都命中 Buffer Pool，收益就有限；如果回表是随机 IO，收益就是 100 倍级别的。**回答时把"关键词是回表次数"说出来，比只说"ICP 能优化"强得多。**

**Q3（计算）**：一张表 1000 万行，`WHERE status='DONE'` 命中 99%。`EXPLAIN` 显示 `key = NULL`、`type = ALL`（全表扫），`rows = 10000000`。

问：**这是 bug 吗？**请用数字说明为什么优化器可能是对的。如果统计信息过期、`rows` 被估成 1000，会发生什么？

**A3**（按每页 16 行估）：

```text
① 全表扫描（优化器的选择）：
   1000万 ÷ 16 = 62.5 万页，【顺序读】

② 如果走 status 索引：
   990 万行命中 → 每行都要回表，每次约 3 次随机 IO
   = 990万 × 3 = 2970 万次【随机 IO】

量级比 = 2970万 ÷ 62.5万 ≈ 47 倍
```

【结论】**不是 bug**——当命中比例高达 99% 时，"走索引 + 990 万次回表"比"顺序扫 62.5 万页"贵约 47 倍。**优化器选全表扫是正确决定。**

【反过来】如果**统计信息过期**把结果估成 1000 行，优化器就会选 status 索引 → **实际要跑 2970 万次随机 IO**。这才是真的出错，而**修正手段是 `ANALYZE TABLE`，不是加索引、更不是 `FORCE INDEX`**（强推只会把它锁死在错误的选择上）。

**Q4（纠错）**：下面这段话哪里不准确？

> "我们的 SQL explain 显示没走索引，肯定是写法有问题，加个 force index 强制走索引就好了。"

**A4**：三处问题。

1. **"没走索引 = 写法问题"不成立**。有一类恰恰是**优化器算过成本后主动放弃**——命中比例过高时，"走索引 + 大量回表"比"顺序扫全表"更贵（Q3 里是 47 倍）。这时**全表扫是正确决定**。
2. **`FORCE INDEX` 是验证工具，不是修复手段**。它的正确用法是：**先确认"走了索引确实更快"**，再决定是否强推。**直接强推可能把性能锁死在更差的计划上**，而且优化器以后即使统计信息更新了也没法改回来。
3. **排查顺序反了**。正确顺序是：**先照失效清单过一遍写法（表达式/函数/隐式转换/最左前缀），再对比 `rows` 估算与实际判断是不是统计信息问题**，最后才考虑 `FORCE INDEX`。

【准确说法】"先分清是**写法问题**（照失效清单查）还是**成本判断问题**（对比估算与实际行数）。后者该做的是 `ANALYZE TABLE` 更新统计信息，或者**接受全表扫**——命中 99% 时它本来就是对的。"

**Q5（纠错）**：下面这段话哪里不准确？

> "`count(*)` 在 InnoDB 上很慢，改成 `count(1)` 能快很多。"

**A5**：**`count(*)` 和 `count(1)` 在 InnoDB 里性能基本一样**（MySQL 5.7.18 之后对 `count(*)` 也走最小的二级索引）。

真正慢的是 **`count(列)`**——它要**判断该列是否为 NULL**，所以不能走"最小索引"那条捷径。

【根因】**`count(*)` 慢不是因为写法，是因为 InnoDB 必须真的去数**：

- **MyISAM** 在表头存了一个行数计数器 → `count(*)` 是 **O(1)**（但业务表不该用 MyISAM，[[母题-M5-引擎与表设计基本盘]]）
- **InnoDB** 有 MVCC，**不同事务在同一时刻看到的行数可能不同** → 没有全局行数可缓存 → **只能扫描索引来数**

【准确说法】"`count(*)` 的代价是**必须扫一遍最小索引**，这是 MVCC 的必然代价，不是写法问题。如果它成了瓶颈，解法是**业务侧维护计数表**（用增量更新换 O(1) 读），或者接受**近似值**——而不是换 `count(1)`。"

## 三、面试输出（学完再看）

**一句话结论**：定位按三步走——**慢查询日志（按"频率 × 单次耗时"排优先级）→ `EXPLAIN` 看计划（`type` / `key` / `rows` / `Extra`）→ 按类型动手再 explain 验证**。所有优化手段围绕**"少扫、少回、少排"**：少扫靠最左前缀设计与不用偏移量；少回靠**覆盖索引与索引下推 ICP**（ICP 把回表从 10,000 次降到 100 次）；少排靠让索引顺序匹配 `ORDER BY`。**深分页的代价 = 偏移量**（`LIMIT 1000000, 10` 要扫 1,000,010 行），首选**游标定位**（扫描与回表都降到 10），必须跳页时才用延迟关联（只降回表）。**最容易漏的一类**：索引失效不一定是写法错——**优化器算过成本后主动放弃**，命中 99% 时全表扫比走索引快约 47 倍。所以最后有一条不可颠倒的**优化优先级**：先缩小业务范围 → 修 JOIN 与 N+1 → 再改索引 → 再改写 SQL → **最后才上缓存**。

**恢复关键词**：三步定位 / 四字段（type·key·rows·Extra）/ 三种慢源（扫描多·回表多·JOIN 顺序错）/ 少扫少回少排 / 覆盖索引 / **ICP 降的是回表量不是扫描量** / 深分页代价 = 偏移量 / 游标定位 vs 延迟关联（都降回表，只有前者降扫描）/ **优化器主动放弃索引** / rows 是估算、EXPLAIN ANALYZE 才是实际 / count(*) 慢是 MVCC 的必然 / 优先级：范围 → JOIN → 索引 → SQL → 缓存

**核心不变量 / 主线**：
**所有 SQL 优化都在做同一件事：让"扫过的行"尽量等于"要返回的行"。**
差距只有两个来源：**没命中的扫描**（该过滤的没提前过滤）和**白拿的回表**（取回了不用的列）。**每一种手段都能归到这两类里**——归不进去的，说明还没搞清它在治什么。

**完整回答骨架**：先把目标说清（扫过的行 ≈ 要返回的行）→ 定位三步 → explain 四字段 → 三组手段各治什么（少扫/少回/少排，各带一个数）→ 深分页专讲（扫描量 = 偏移量）→ **优化器主动放弃索引**（最反直觉的一类）→ 优化优先级五步 → 收束到"先分类再动手"

**追问**（先说后看）

1. **怎么确认统计信息错了？** —— 对比 `EXPLAIN` 的 `rows`（估算）与 `EXPLAIN ANALYZE`（8.0.18+）的实际行数；**差一个数量级以上就该 `ANALYZE TABLE`**。这条和 PG 的 [[母题-P7-统计信息与慢查询定位]] 是同一件事的两个实现。
2. **那条 20 多秒的 SQL 你具体怎么定位的？** —— 按顺序讲：**估计 vs 实际行数 → 扫描方式 → JOIN 规模 → 排序/临时表 → loops（N+1）**。**重点不是"发现了什么"，而是"为什么按这个顺序"**——每一步都对应一个明确的修复动作，做完立刻验证，不会白做。**这一段要练成 60 秒口述。**
3. **索引下推解决了什么？** —— **回表前先过滤**。没有 ICP 时 `(age, name)` 只能用 `age = 18` 定位，**所有 age=18 的行都要回表**；有 ICP 后**在索引层就过滤 name**，回表次数大幅下降。**关键词是"回表次数"。**
4. **`in` 和 `exists` 怎么选？** —— **小表驱动大表**：子查询结果集小用 `in`，外表小用 `exists`。`not in` 遇到 `NULL` 或无法利用索引时要换 `not exists`。
5. **`ORDER BY` 没走 filesort 但还是很慢？** —— **排序不是唯一成本**：可能回表次数多（`SELECT *`），或者扫描范围太大。**"少排"解决了不代表"少扫少回"解决了**——三类要分开看。

**同类变体**

- 「一条 SQL 你会按什么顺序优化？」——就是第 6 节的五步。**关键是把"先范围、再 JOIN、再索引、后缓存"这个顺序说成有理由的**（范围与 JOIN 决定扫描量，索引只能加速已有的扫描）。
- 「`EXPLAIN` 里 `rows` 很大就一定是坏计划吗？」——**不一定**。看的是"`rows` 与最终返回行数的比值"：如果 `rows` 是 100 万但返回 10 条（且没有更好的过滤手段），那才是问题；如果返回 90 万条，那 `rows` 大是必然的。
- 「分区能替代这些优化吗？」——**不能替代，只能补充**（[[母题-M15-数据增长治理]]、[[母题-P16-分区表]]）。分区解决的是"整块数据根本不用碰"，前提是分区键出现在条件里。
