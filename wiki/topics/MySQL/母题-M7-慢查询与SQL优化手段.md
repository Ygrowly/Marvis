# 母题 M7 · 慢查询与 SQL 优化手段

> **模块**：MySQL / SQL 执行与优化
> **所属主线**：二 · SQL 执行与优化（一条 SQL 到底怎么走、慢在哪）
> **关联母题**：[[母题-M6-一条SQL的执行链路]] · [[母题-M3-聚簇索引与回表]] · [[母题-M2-联合索引与最左前缀]]
> **素材来源**：`raw/Mysql面试题-2026-09-07T004734+0800.md` 第 3 节（索引下推 3.11、失效 3.12、自增主键 3.13）+ EnergyOps 真实优化过程

**题目**：线上有条 SQL 偶尔 20 多秒。你按什么顺序定位？深分页 `LIMIT 1000000, 10` 为什么慢，怎么改？

**母题**：慢查询怎么定位？常见的 SQL 优化手段有哪些？

**为什么重要**：**这是面试里"给一个真实案例"最容易出彩的题**——因为它能同时展示：定位方法（有章法）、优化手段（有清单）、以及**"索引失效不一定是写法错"这种反直觉判断**。EnergyOps 的 20.4s → 2.8s 就是这条线的真实案例，**必须能讲成"按顺序定位、按优先级动手"，而不是"我们加了个索引"**。

**一句话结论**：定位按三步走——**慢查询日志（找出来）→ `EXPLAIN` 看计划（`type` / `key` / `rows` / `Extra`）→ 确认扫描行数与回表**。优化手段围绕**"少扫、少回、少排"**三件事：**覆盖索引、最左前缀设计、索引下推（ICP）、深分页用游标定位或延迟关联、小表驱动大表、`count(*)` 走最小索引**。**特别的一条：索引失效不一定是写法错——可能是优化器估算后主动放弃**（这是最容易漏的一类）。

**恢复关键词**：慢查询日志 long_query_time / explain 的 type 与 rows / 覆盖索引 / 索引下推 ICP / 延迟关联（先查 id 再回表）/ 深分页 / 小表驱动大表 / 优化器主动放弃索引

**核心不变量 / 主线**：
**所有 SQL 优化都在做同一件事：让"扫过的行"尽量等于"要返回的行"。** 两者差距越大越慢——**差距来自"没命中的扫描"（该过滤的没提前过滤）和"白拿的回表"（取回了不用的列）**。**所以每一种手段都能归到这两类里。**

**完整回答骨架**：定位三步 → explain 四个字段怎么读 → 优化手段清单（按"少扫少回少排"归类）→ 深分页专讲 → 优化器主动放弃 → 优化优先级

## 原理分解

### 一、定位三步（有章法，不是"打开 explain 看看"）

```
① 慢查询日志（long_query_time）→ 把问题 SQL 抓出来，先按出现频率 × 单次耗时排优先级
② EXPLAIN 看计划 → 判断问题类型
③ 按类型动手 → 再 explain 验证，最后压测确认
```

**explain 四个字段的读法**：

| 字段 | 看什么 |
|---|---|
| `type` | 访问方式，从好到坏：`system > const > eq_ref > ref > range > index > ALL`。**`ALL` = 全表扫，`index` = 扫全索引（比 ALL 好一点点，也危险）** |
| `key` | 实际用的索引。**`possible_keys` 有但 `key` 为 NULL → 优化器主动放弃了**（见第五节） |
| `rows` | **估算扫描行数**——与实际差很远时说明统计信息/选择性有问题 |
| `Extra` | `Using index`（覆盖，好）/ `Using filesort`（额外排序）/ `Using temporary`（临时表）/ `Using index condition`（下推生效，M2 提过） |

### 二、优化手段清单（按"少扫少回少排"归类）

**少扫（让过滤更早发生）**

- **最左前缀设计**：等值列在前、范围列在后（M2）；
- **范围查询能缩就缩**：`LIMIT` 之外，能用 `id > ?` 定位就不要按偏移量扫；
- **不要 `SELECT *`**：列少了，优化器才可能选覆盖索引。

**少回（让索引自己回答完）**

- **覆盖索引**：把 `SELECT` 的列都放进索引（M3）；
- **索引下推 ICP**（5.6+）：`(age, name)` 索引下，`age=18 AND name LIKE '%三'` 可以**在索引层先过滤 name**，**把"符合条件才回表"变成"索引层就过滤掉不合格的"**——**大幅减少回表次数**。explain 里显示 `Using index condition`。

**少排（避免额外排序与临时表）**

- **让索引顺序匹配 `ORDER BY`**（索引本身有序，天然省 filesort）；
- **小表驱动大表**：`in` / `exists` 的选择、JOIN 的驱动表顺序；
- **`GROUP BY` 尽量走索引列**，避免临时表。

**几个"知道就行"的点**：`count(*)` ≈ `count(1)` > `count(列)`（要判空）；**`count(*)` 没有专门的优化捷径，InnoDB 是真数**（MyISAM 才有行数缓存——但业务表不该用 MyISAM）。

### 三、深分页：`LIMIT 1000000, 10` 为什么慢

**它不是"取 10 行"，而是"取前 1000010 行，丢掉前 100 万行"**——**扫描与回表量等于偏移量**，所以越翻越慢。

**两种解法**：

**① 游标定位（首选）**：记住上一页最后一条的排序键，下一页用条件跳过去：

```sql
SELECT ... WHERE id > :last_id ORDER BY id LIMIT 10;   -- 恒定扫描 10 行
```

**② 延迟关联**：必须跳页时，先用覆盖索引把 `id` 捞出来，再回表取详情：

```sql
SELECT t.* FROM task t
JOIN (SELECT id FROM task ORDER BY id LIMIT 1000000, 10) s ON t.id = s.id;
```

**子查询走覆盖索引（只扫索引，不回表）**，**回表只发生在最后 10 行上**——**把"100 万次回表"降成"10 次回表"**。

### 四、优化器主动放弃索引（最容易被漏掉的一类）

**现象**：索引存在、条件也该走索引，explain 却显示 `key = NULL`、全表扫。

**原因**：优化器**估算过成本**——当它判断"走索引 + 大量回表"比"顺序扫全表"更贵时，**主动放弃索引是正确行为**。典型触发：

- 二级索引命中比例过高（比如要取 30% 的行）；
- 统计信息过期（行数/区分度估错）；
- 条件是表达式/函数/隐式类型转换（M2 的失效清单）。

**所以排查顺序是**：**先看是不是"写法问题"（失效清单），再看是不是"成本判断"**——**后者改法不是改 SQL，而是** ① `ANALYZE TABLE` 更新统计信息，② 用 `FORCE INDEX` 验证"走了索引确实更快"（确认判断确实错了再强推），③ 或者接受全表扫（命中比例高时它就是对的）。

**这一条的价值**：**它把"索引失效"从"背清单"升级成"理解优化器的成本模型"**。

### 五、优化优先级（收口，面试必背）

```
① 先缩小业务范围（别把不相关的行扫进来）
② 再修 JOIN 逻辑与 N+1
③ 再建/改索引（含覆盖索引、下推）
④ 再改写 SQL（深分页、排序、count）
⑤ 最后才考虑缓存、预聚合、架构（M15）
```

**EnergyOps 的实际顺序就是这条**：修范围与 JOIN → 建联合索引 → 消 N+1 → 才谈缓存。**反过来做（先上缓存）是典型的"在错误的链路上加速"。**

## 二、扩展：类似题与追问

**类似题**

1. 「索引下推解决了什么？」——**回表前先过滤**。没有 ICP 时，`(age,name)` 索引只能用 `age=18` 定位，**所有 age=18 的行都要回表**，`name LIKE` 在 server 层过滤；有 ICP 后**在索引层就过滤**，回表次数大幅下降。**关键词是"回表次数"。**
2. 「`in` 和 `exists` 怎么选？」——**小表驱动大表**：子查询结果集小用 `in`（先算出子查询再匹配），外表小用 `exists`（外表每行去内表探一次）。`not in` 遇到 `NULL` 或无法利用索引时要换 `not exists`。
3. 「`ORDER BY` 没有 filesort 但还是很慢？」——**排序不是唯一成本**：可能回表次数多（`SELECT *`），或者扫描范围太大。**排序走了索引只解决"少排"，不解决"少扫少回"。**

**追问链**

- 追问一层：**「怎么确认统计信息错了？」**——对比 `EXPLAIN` 的 `rows` 与真实行数（`EXPLAIN ANALYZE` 8.0.18+，或业务侧计数）；**差一个数量级以上就该 `ANALYZE TABLE`**。**这条和 PG 的 P7 是同一件事的两个实现。**
- 追问二层：**「20 多秒那条你具体怎么定位的？」**——按五步顺序讲（P6 的五步）：**估计 vs 实际行数 → 扫描方式 → JOIN 规模 → 排序/临时表 → loops（N+1）**。**重点不是"发现了什么"，而是"为什么按这个顺序"**——**因为每一步都对应一个明确的修复动作，做完立刻验证，不会白做。** **这一段要练成 60 秒口述。**
