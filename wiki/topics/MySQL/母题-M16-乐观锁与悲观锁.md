## 一、教材

### 1. 前提：它们是对冲突概率的两种假设

【事实】

- **悲观锁假定冲突一定发生** → 所以在访问前**先加锁**，拿到锁才能改，其他事务阻塞等待
- **乐观锁假定冲突很少** → 所以**不加锁直接改**，**提交时校验有没有被别人改过**

【推论】**"哪个更好"这个问题本身就是错的**——**没有冲突概率，选型就是空谈**。

【推论】**所以回答的第一句话永远是"冲突频率"，第二句才是机制。** **这正是 9.9 那次缺的东西。**

---

### 2. 悲观锁：先拿锁，再操作【事实】

```sql
SELECT status FROM task WHERE id = 1 FOR UPDATE;   -- 加 X 锁
UPDATE task SET status = 'RUNNING' WHERE id = 1;
COMMIT;
```

**实现**：数据库 `SELECT ... FOR UPDATE`（排他锁）；Java 里 `synchronized` / `ReentrantLock`；分布式场景是 Redis / ZK 锁（**但分布式锁不能替代数据库约束，见 [[母题-P19-唯一约束与UPSERT]]**）。

**适用**：**写多、冲突频繁、临界区长**（拿到锁之后要做一堆事）。

**代价**：① **等待与吞吐下降**；② **死锁风险**（加锁顺序不一致时，[[母题-M10-锁与死锁]]）；③ **连接占用时间长**。

【事实】**实现上的一个坑**：`SELECT ... FOR UPDATE` 在 RR 下**会带出 next-key lock**，锁范围可能比预期大（[[母题-M10-锁与死锁]]）——**这正是"悲观锁代价"的具体体现**。

---

### 3. 乐观锁：不加锁，提交时校验【事实】

**两种实现**：

**① version 字段（数据库场景的标准做法）**

```sql
UPDATE task
SET status = 'RUNNING', version = version + 1
WHERE id = 1 AND version = :expected_version;   -- 期望值进 WHERE
-- 影响行数 = 0 → 别人改过 → 读出最新值再决定
```

**② CAS（Compare-And-Swap，CPU / Java 层面）**

```text
期望值 E、新值 V：内存位置当前值 == E 才写入 V
Java 里即 Atomic* 类（底层是一条 CAS 指令）
```

**适用**：**读多写少、冲突少、单行**。

**代价**：**冲突多时反复重试，成本反而更高**；**只能保护单行 / 单个变量**——**跨行不变量靠它撑不住**（要靠约束或事务，[[母题-P18-乐观并发控制]]）。

【事实】**核心是"期望值进 WHERE"**：用 version、用状态、用时间戳都行，**本质是 CAS 思想**。version 字段的好处是**自带 ABA 防护**（下一节）。

---

### 4. ABA 问题：CAS 的固有缺陷【推导】

【事实】CAS 只比较"值是否相等"，**不比较"中间有没有变过"**：

```text
线程 1 读到值 100（准备改成 200）
线程 2 把 100 改成 80，又改回 100
线程 1 CAS(100 → 200) 成功          ← 但它不知道中间发生过 80
```

【推导】**什么时候有害、什么时候无害**：

| 场景 | 有害吗 | 为什么 |
|---|---|---|
| **数值累加/设置** | **通常无害** | "1 加 5 次" 和 "1 加 1 次" 结果一样——CAS 只关心最终值 |
| **引用 / 状态 / 指针** | **有害** | 栈顶指针被弹出又压回**同一个地址**，但链表结构已经被破坏，CAS 却认为"没变过" |

【事实】**解法**：**版本号 / 时间戳一起比**——Java 里 `AtomicStampedReference`（带 stamp）；**数据库里 `version` 字段本质就是"自带 ABA 防护的 CAS"**。

【推论】**这一条能把"version 为什么比直接比较值更稳"讲成因果，而不是一句"要加 version"的口诀。** 面试里能这样讲，就超过只背结论的人。

**到这里你应该能回答**：为什么"用状态字段当期望值"在某些场景下不如 version？

### 5. 判据：两条成本曲线的交点（本题的落点）

> **冲突频率高到「重试成本 > 加锁成本」时，用悲观锁；否则用乐观。**

::figure lock-cost-curves.svg | 乐观锁与悲观锁的成本曲线：判据在交点 | 悲观锁成本线性上升（等待是排队，不全部重来）；乐观锁按 1/(1−p) 上升、在 p→1 处发散（每次冲突都要整段重做）；交点就是判据

【推导】**为什么要画曲线而不是背结论**——因为**两种方案的成本函数形状完全不同**：

```text
悲观锁成本 ≈ 加锁开销 + 冲突时的【排队等待】
            → 随冲突率【线性】上升（等待是排队，工作不会白做）

乐观锁成本 ≈ 单次成本 ÷ (1 − p)
            → 随冲突率【发散】（每次冲突都要把整段工作重做）
```

#### 5.1 把"发散"算出来【推导】

乐观锁的**期望尝试次数**：

```text
期望尝试次数 = 1 + p + p² + … = 1 / (1 − p)      （p = 单次尝试遇到冲突的概率）

p = 0.05 →  1.05 次
p = 0.30 →  1.43 次
p = 0.70 →  3.33 次
p = 0.90 → 10    次
p → 1    → 发散
```

【推论】**这就是"高冲突时乐观锁崩掉"的数学表达**——**它不是"慢一点"，是在 p→1 时成本发散。**

#### 5.2 高冲突下的量级差【推导】

```text
N 个请求同时抢同一行（此时单次冲突概率 p ≈ (N−1)/N）
  乐观锁期望尝试次数 = 1/(1−p) ≈ N
  总工作量 = N 个请求 × N 次尝试 = N² 次

悲观锁：串行执行，每个请求做一次
  总工作量 = N 次

量级比 = N
```

【结论】**高冲突时乐观锁的总工作量是 N²，悲观锁是 N——差一个 N 倍。** 10 个并发就差 10 倍，100 个并发差 100 倍。

【推论】**这就是"重试成本 > 加锁成本"这句话的量化版本**——面试里能给出 N² vs N 这个对比，比说"高冲突别用乐观锁"有说服力得多。

**到这里你应该能回答**：为什么"乐观锁不加锁所以更快"是一句危险的话？

### 6. 选了乐观锁，就必须把重试当成方案的一部分【推导】

```text
某热点行 1000 QPS，乐观锁冲突率 90%
  期望尝试次数 = 1/(1−0.9) = 10 次
  总更新尝试 = 1000 × 10 = 10,000 次/秒

加退避 + 抖动，把有效冲突率降到 30%：
  期望尝试次数 = 1/(1−0.3) ≈ 1.43 次
  总更新尝试 = 1000 × 1.43 = 1,430 次/秒

降到约 1/7
```

【事实】**"影响行数 0"是正常业务分支，不是异常**：正确的处理是**读权威状态 → 判定 → 决定**，而不是无脑重试。**不要写 `while(true) retry`**——要有**退避、抖动和上限**（[[母题-P9-序列化失败与重试]] 的四条要求）。

**主动说出自己方案不适用的情况，比硬吹乐观锁可信得多。**

### 8. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "乐观锁不加锁，性能一定更好" | **低冲突时对，高冲突时反了**。乐观锁成本 ≈ 单次成本 ÷ (1−p)，**在 p→1 时发散**；高冲突下总工作量是 **N²**，悲观锁是 **N**——差一个 N 倍 |
| "乐观锁就是加个 version 字段" | **核心是"期望值进 WHERE"**——version、状态、时间戳都行，**本质是 CAS 思想**。version 的好处是**自带 ABA 防护** |
| "CAS 比较值相等就安全" | **漏了 ABA**：值相等 ≠ 中间没变过。数值场景通常无害，**引用 / 状态 / 指针场景有害**（栈顶指针弹出又压回同一地址） |
| "影响行数 0 说明出异常了" | **是正常业务分支**。它可能是"别人抢先了"，也可能是"条件本来就不满足"——**分不出来，也不需要分**；正确做法是**读权威状态再判定** |
| "重试失败就一直重试到成功" | **三处错**：没有上限（可能无限循环）、没有退避（会形成重试风暴）、没意识到有些失败**重试一万次也不会成功**（条件本身不满足）。**要有退避 + 抖动 + 上限** |
| "分布式锁就是悲观锁，能保证正确性" | **它是应用层的锁，不能替代数据库约束做正确性兜底**（[[母题-P19-唯一约束与UPSERT]]）。**锁会失效（过期、网络分区），约束不会** |

【取舍】读成一句话：**两者不是"谁更好"，而是对冲突概率的两种假设——所以没有冲突频率，就没有选型。**

## 二、自测

**Q1（计算）**：乐观锁的期望尝试次数 = `1 / (1 − p)`，其中 `p` 是单次尝试遇到冲突的概率。

问：**`p` 分别为 0.05 / 0.3 / 0.7 / 0.9 时，期望尝试次数各是多少？**这个函数在 `p` 接近 1 时会怎样？

**A1**：

| p | 期望尝试次数 = 1/(1−p) |
|---|---|
| 0.05 | 1.05 |
| 0.30 | 1.43 |
| 0.70 | 3.33 |
| 0.90 | **10** |
| → 1 | **发散（趋于无穷）** |

【结论】**乐观锁的成本不是"随冲突线性上升"，是"在 p→1 时发散"。**

【推论】**这就是"高冲突时乐观锁会崩"的数学表达**——不是"慢一点"，是**每次冲突都要把整段工作重做，而成功率越低重做的次数越多**。

**Q2（计算）**：**N 个请求同时抢同一行**（此时单次冲突概率约为 `(N−1)/N`）。

问：**乐观锁和悲观锁的总工作量各是多少？差多少倍？**N = 10 和 N = 100 时分别是多少？

**A2**：

```text
乐观锁：
  期望尝试次数 = 1/(1 − (N−1)/N) = N
  总工作量 = N 个请求 × N 次尝试 = N² 次

悲观锁：
  串行执行，每个请求做一次
  总工作量 = N 次

量级比 = N² / N = N
```

| N | 乐观锁 | 悲观锁 | 倍数 |
|---|---|---|---|
| 10 | 100 次 | 10 次 | **10 倍** |
| 100 | 10,000 次 | 100 次 | **100 倍** |

【结论】**并发越高，乐观锁的劣势越大**——**它是 N² 对 N，差距随并发线性放大。**

【推论】**这就是"重试成本 > 加锁成本"的量化版本**：当 N 足够大（冲突足够密集），乐观锁白做的工作量会远超悲观锁的排队成本。

**Q3（计算）**：某热点行 **1000 QPS**，乐观锁的冲突率 **90%**。

问：**总更新尝试次数是多少？**如果加退避 + 抖动把有效冲突率降到 **30%**，总尝试次数变成多少？

**A3**：

```text
无退避（冲突率 90%）：
  期望尝试次数 = 1/(1−0.9) = 10 次
  总尝试 = 1000 × 10 = 10,000 次/秒

有退避 + 抖动（有效冲突率降到 30%）：
  期望尝试次数 = 1/(1−0.3) ≈ 1.43 次
  总尝试 = 1000 × 1.43 = 1,430 次/秒

降到约 1/7
```

【结论】**退避 + 抖动不是"优化"，是乐观锁方案的必要组成部分。**

【为什么抖动也必要】没有抖动时，**失败的请求会同时回来重试**，形成"重试风暴"——瞬时并发不降，冲突率也不会降。**抖动把重试摊开到时间窗里，两者才一起下降。**

**Q4（纠错）**：下面这段话哪里不准确？

> "我们用的是乐观锁，不加锁，所以并发性能肯定比悲观锁好。"

**A4**：**在低冲突时对，在高冲突时完全反了。**

1. **乐观锁的成本是 `单次成本 ÷ (1−p)`**（Q1）——**在 p→1 时发散**，不是"常数级更快"。
2. **高冲突下的量级差是 N 倍**（Q2）：N 个请求抢同一行时，乐观锁总工作量 **N²**、悲观锁 **N**。100 并发就是 100 倍。
3. **"不加锁"省下的只是加锁开销**——而它换来的是**每次冲突都要整段重做**。**当整段工作比加锁贵得多时，这笔交换是亏的。**

【准确说法】"**乐观锁在低冲突下更便宜，悲观锁在高冲突下更便宜**——判据是两条成本曲线的交点（冲突频率）。**没有冲突频率，'性能更好'这句话不成立。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们的乐观锁失败后会 `while(true)` 一直重试，直到更新成功为止。"

**A5**：三处错。

1. **没有上限**：可能无限循环。要在**有限次**（常见 2–3 次）后**转人工或走降级**。
2. **没有退避和抖动**：失败请求会**同时回来重试**，形成重试风暴——**瞬时并发不降，冲突率也不降**（Q3 里退避能把总尝试降到 1/7）。
3. **把"影响行数 0"当成了异常**：它**可能是条件本身不满足**（比如 `WHERE status='READY'` 但状态已经是 `SEARCHING`），**这种情况重试一万次也不会成功**——必须**先读权威状态再判定**。

【准确说法】"`影响行数 0` 是**正常业务分支**：**读权威状态 → 判定 → 决定**（重试 / 放弃 / 转人工）。重试要带**退避 + 抖动 + 上限**（[[母题-P9-序列化失败与重试]] 的四条要求）。"

**完整回答（口述稿）**：
两者不是谁更好，是对冲突概率的两种假设。悲观锁假定冲突一定发生，所以先加锁（SELECT ... FOR UPDATE、synchronized）；乐观锁假定冲突很少，不加锁、提交时校验——version 字段或 CAS，写法是 UPDATE ... SET ... WHERE id = ? AND version = ?，影响行数 0 就是冲突。

判据只有一个：冲突频率。乐观锁的成本约等于单次成本 ÷ (1 − p)，p 趋近 1 时发散；高冲突下 N 个请求抢同一行，乐观锁总工作量约 N²，悲观锁约 N，差一个 N 倍。所以冲突高到「重试成本 > 加锁成本」就该换悲观。

乐观锁的核心是「期望值进 WHERE」，version、状态、时间戳都行，本质是 CAS 思想；version 的好处是自带 ABA 防护——CAS 比较值相等并不安全，值相等不等于中间没变过，数值场景通常无害，引用 / 状态 / 指针场景有害（栈顶指针弹出又压回同一地址）。

工程上：影响行数 0 是正常业务分支，可能是别人抢先了、也可能条件本来就不满足，分不出来也不需要分，正确做法是读权威状态再判定；重试必须有次数上限和退避，不能一直重试到成功。

**分层要点**：
- **结论**：两种假设，不是优劣；判据是冲突频率 p。
- **推导链**：悲观先加锁 vs 乐观提交时校验（期望值进 WHERE）→ 成本曲线 1/(1−p) → p→1 发散 → 高冲突下 N² vs N → 换悲观。
- **量化**：乐观锁成本 ≈ 单次成本 ÷ (1−p)；高冲突下乐观约 N²、悲观约 N，差一个 N 倍。
- **边界与常见误解**：乐观锁性能一定更好 ×；乐观锁 ≠ 加个 version（本质是 CAS，version 顺带防 ABA）；影响行数 0 是正常分支不是异常；重试要有上限和退避。
