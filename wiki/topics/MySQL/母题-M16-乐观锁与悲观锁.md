# 母题 M16 · 乐观锁与悲观锁

> **模块**：MySQL / 业务并发场景
> **所属主线**：七 · 业务并发场景（抢库存、冲排行榜怎么不出错）
> **关联母题**：[[母题-M10-锁与死锁]] · [[母题-M17-排行榜与防超卖]] · [[母题-P18-乐观并发控制]]
> **素材来源**：**9.9 乐元素一面原题（答得不合格）**，标答见 `wiki/interview/乐元素-服务端一二面复盘报告.md`（A21）+ RuleArena 真实取舍（P18）

**题目**：说一下乐观锁与悲观锁的区别。（**9.9 一面原题，当次 11 分——口误"悲观所"、没提版本号/CAS、没讲适用边界**）

**母题**：乐观锁和悲观锁怎么选？各自的实现与边界是什么？

**为什么重要**：**这是你 9.9 一面真实被问、且答得不合格的题**——**所以这张卡不只是知识点，是"补掉一个真实丢分点"的修复卡**。当次的扣分点有三条：① 口误；② 乐观锁部分只说"先执行，变更时才上锁"，**没有提到版本号 / CAS 这两个关键词**；③ 没讲适用边界——**按评分表，概念不完整、论据只能给 2 分**。**这张卡的目标是：再遇到时能拿满分。**

**一句话结论**：**区别在对冲突的假设不同**。**悲观锁假定冲突一定发生**，所以访问前先加锁：数据库里是 `SELECT ... FOR UPDATE`，Java 里是 `synchronized` / `ReentrantLock`，**拿到锁才能改，其他事务阻塞等待**——适合**写多、冲突频繁、临界区长**，代价是锁开销与死锁风险。**乐观锁假定冲突很少**，不加锁直接改，**提交时校验有没有被别人改过**：常见做法是 **version 字段**（`UPDATE ... WHERE version=?`，影响行数 0 即冲突）或 **CAS**——适合**读多写少**，要注意 **ABA 问题**。**判据一句话：冲突频率高到重试成本大于加锁成本时，才用悲观锁。**

**恢复关键词**：假设不同 / 悲观=FOR UPDATE / 乐观=version 或 CAS / 影响行数 0 判冲突 / **ABA 问题**（AtomicStampedReference）/ **冲突频率是唯一判据** / RuleArena 的条件更新

**核心不变量 / 主线**：
**两者不是"谁更好"，而是对冲突概率的两种假设。** **没有冲突概率，选型就是空谈**——**所以回答的第一句话永远是"冲突频率"，第二句才是机制**（这正是 9.9 那次缺的东西）。

**完整回答骨架**：两种假设 → 悲观锁的实现与适用 → 乐观锁的实现（version / CAS）与 ABA → 一条判据 → 结合自己项目（RuleArena 条件更新）→ 反向讲"什么情况我会换悲观锁"

## 原理分解

### 一、悲观锁：先拿锁，再操作

```sql
SELECT status FROM task WHERE id = 1 FOR UPDATE;   -- 加 X 锁
UPDATE task SET status = 'RUNNING' WHERE id = 1;
COMMIT;
```

**实现**：数据库 `SELECT ... FOR UPDATE`（排他锁）；Java 里 `synchronized` / `ReentrantLock`；分布式场景是 Redis/ZK 锁（**但分布式锁不能替代数据库约束，P19 的结论**）。

**适用**：**写多、冲突频繁、临界区长**（拿到锁之后要做一堆事）。
**代价**：① 等待与吞吐下降；② **死锁风险**（顺序不一致时，M10）；③ **连接占用时间长**（P17 的口径）。

### 二、乐观锁：不加锁，提交时校验

**两种实现**：

**① version 字段（数据库场景的标准做法）**

```sql
UPDATE task
SET status = 'RUNNING', version = version + 1
WHERE id = 1 AND version = :expected_version;   -- 期望值进 WHERE
-- 影响行数 = 0 → 别人改过 → 读出最新值再决定
```

**② CAS（Compare-And-Swap，CPU/Java 层面）**

```
期望值 E、新值 V：内存位置当前值 == E 才写入 V
Java 里即 Atomic* 类（AtomicInteger 等，底层 CAS 指令）
```

**适用**：**读多写少、冲突少、单行**。
**代价**：**冲突多时反复重试，成本反而更高**；**只能保护单行/单个变量**——**跨行不变量靠它撑不住**（要靠约束或事务，P18）。

### 三、ABA 问题（必考的细节）

**CAS 只比较"值是否相等"，不比较"中间有没有变过"**：

```
线程 1 读到值 100（准备改成 200）
线程 2 把 100 改成 80，又改回 100
线程 1 CAS(100 → 200) 成功          ← 但它不知道中间发生过 80
```

**数值场景通常无害（1 加 5 次 = 5 加 1 次），但"引用/状态"场景有害**——**比如栈顶指针被弹出又压回同一个地址，链表结构已被破坏，CAS 却认为"没变过"。**

**解法**：**版本号 / 时间戳一起比**——Java 里 `AtomicStampedReference`（带 stamp），**数据库里 `version` 字段本质就是"自带 ABA 防护的 CAS"**。

**这一条能把"version 为什么比直接比较值更稳"讲成因果，而不是一句"要加 version"的口诀。**

### 四、判据（本题的落点）

> **冲突频率高到「重试成本 > 加锁成本」时，用悲观锁；否则乐观。**

**为什么这条是唯一判据**：**两种方案的成本函数不同**——

```
悲观锁成本 ≈ 加锁开销 + 冲突时的等待（随冲突率线性上升）
乐观锁成本 ≈ 重试次数 × 单次成本（随冲突率更快上升）
```

**低冲突时乐观的曲线更平（几乎零成本），高冲突时悲观的曲线更平（等待是排队，不是全部重来）**。**所以不是"乐观更先进"，是"冲突少时乐观便宜"**。**面试里画这两条成本曲线，比背定义高一个档次。**

### 五、结合自己的项目（必练：这条是你的差异化）

**RuleArena 的退款与任务认领用的是乐观锁（条件更新）**，理由（P18 已展开）：

- **扣退款是低频写、读多写少** → 冲突少；
- **条件更新一次原子写**，天然幂等（重复执行第二次影响 0 行）；
- **跨行不变量写进 WHERE**（`refunded + amount <= paid`）；
- **唯一约束兜底**（`UNIQUE(run_id, action_type, idempotency_key)`）。

**然后反向讲一句（这是"懂边界"的证据）**：**"如果同一个任务被大量 Worker 高频争抢，重试成本就会超过加锁成本，那时我会换成悲观锁或者把任务分区错开"**——**主动说出自己方案不适用的情况，比硬吹乐观锁可信得多**（这也是 A11 复盘里"主动暴露局限"那条经验在技术题上的应用）。

## 二、扩展：类似题与追问

**类似题**

1. 「乐观锁在数据库里就是加 version 字段吗？」——**核心是"期望值进 WHERE"**：用 version、用状态、用时间戳都行；**本质是 CAS 思想**。**version 字段的好处是自带 ABA 防护。**
2. 「悲观锁在 MySQL 里怎么实现？」——`SELECT ... FOR UPDATE`（X 锁）；**注意它会带出 next-key lock（M10），锁范围可能比预期大**——**这正是"悲观锁代价"的具体体现**。
3. 「分布式锁算悲观锁吗？」——**算**（假设冲突、先拿锁），**但它是应用层的锁，不能替代数据库约束做正确性兜底**（P19）。

**追问链**

- 追问一层：**「version 冲突之后怎么处理？」**——**读出权威状态，再决定重试还是放弃**——**"影响行数 0"是正常业务分支，不是异常**（P18 展开过）。**不要写 `while(true) retry`**：要有退避、抖动和上限（P9 的重试四要求）。
- 追问二层：**「9.9 那次你的答案缺了什么？」**——**三条：① 没提 version / CAS（实现层面）；② 没讲适用边界（判据层面）；③ 口误（表达层面）**。**这张卡的通过标准：40 秒内给出「假设不同 → 两种实现 → ABA → 判据 → 自己项目实例」五段结构，并主动补一句"什么情况我会换悲观锁"。**
