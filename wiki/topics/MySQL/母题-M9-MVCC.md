# 母题 M9 · MVCC

> **模块**：MySQL / 事务与锁
> **所属主线**：三 · 事务与锁（并发改同一份数据，为什么不会乱）
> **关联母题**：[[母题-M8-隔离级别与ACID]] · [[母题-M10-锁与死锁]] · [[母题-M11-三日志与两阶段提交]]
> **素材来源**：`raw/后端视角复盘_MySQL` 第二条主线（MVCC 的意义）+ `raw/Mysql面试题` 第 2.5–2.8 节

**题目**：RR 下为什么"两次一样的 `SELECT` 结果一样"？这个快照是什么时候定的？和 PG 的实现差在哪？

**母题**：MVCC 怎么实现？RR 与 RC 生成 ReadView 的时机差在哪？幻读到底怎么解决？

**为什么重要**：**这是主线三里机制密度最高的一道**，也是**"背结论"和"能推导"的分水岭**——因为 **RC 和 RR 的全部差别就一个时机**，答得出这一条，四个隔离级别的行为就都能自己推出来。**而且它是 P13（PG 版 MVCC）的对照面**：两边"版本放哪"不同，导致所有后续行为不同。

**一句话结论**：**MVCC = 多版本 + ReadView**。InnoDB 的旧版本存在 **undo log 版本链**里（每行带 `trx_id` 事务 ID 和 `roll_pointer` 指向旧版本），读的时候用一个 **ReadView**（记录生成时刻的活跃事务列表 + 低水位/高水位）**沿着版本链找第一个对自己可见的版本**。**RC 与 RR 的唯一差别是 ReadView 的生成时机：RC 每条语句生成一次，RR 整个事务第一次快照读时生成一次**——这一个时机差异，就是"可重复读"的全部实现。

**恢复关键词**：undo 版本链 / trx_id / roll_pointer / ReadView / m_ids·低水位·高水位 / **RC 每语句 vs RR 每事务** / 快照读 vs 当前读 / 幻读一半靠 MVCC 一半靠锁

**核心不变量 / 主线**：
**"可见性"是按快照判定的，而快照的粒度由隔离级别决定。** 这一句同时解释了 MySQL 的 RC/RR 差别（P8）和 PG 的语句/事务快照差别——**两边机制不同，但"快照决定可见性"这条原理完全一致。**

**完整回答骨架**：为什么需要多版本（读写互不堵）→ 版本链的结构 → ReadView 的三个字段与可见性判断 → RC/RR 只差生成时机 → 快照读 vs 当前读 → 幻读的真相

## 原理分解

### 一、为什么需要多版本（raw 里那句最实在的解释）

如果**所有读都去抢锁**，系统并发会很差。MVCC 的核心价值：

> **普通查询走快照读，读一个一致版本，而不是非得去抢当前正在被别人改的那份数据。**

raw 里把它压成两句话：**当前读偏"我要最新，还可能要加锁"；快照读偏"我要一个一致版本，别跟写全撞上"。**

### 二、版本链的结构

每一行数据带着两个隐藏字段：

| 字段 | 含义 |
|---|---|
| **`trx_id`** | 最近一次修改（插入/更新）它的事务 ID |
| **`roll_pointer`** | 指向 **undo log 里上一个版本** |

于是**一行数据的所有历史版本通过 `roll_pointer` 串成一条链**（存在 undo log 里）：

```
当前版本 (trx_id=105) → 旧版本 (trx_id=98) → 更旧 (trx_id=90) → ...
```

**注意与 PG 的对照（这里是两边最容易说反的地方）**：**MySQL 的旧版本在 undo log 里，数据页上只有当前版本；PG 的旧版本直接留在堆里**。**这决定了两边回收方式的差别**（MySQL purge 线程自动清 undo；PG 靠 VACUUM，P13）。

### 三、ReadView：可见性怎么判

ReadView 里关键是这几样：

| 字段 | 含义 |
|---|---|
| `m_ids` | 生成 ReadView 时**还活跃（未提交）**的事务 ID 列表 |
| `min_trx_id` | `m_ids` 里最小的（低水位） |
| `max_trx_id` | **下一个**将分配的事务 ID（高水位） |
| `creator_trx_id` | 当前事务自己的 ID |

**对某个版本的 `trx_id`，判定规则（简化）**：

```
trx_id == 自己              → 可见（自己改的当然看得见）
trx_id <  min_trx_id        → 可见（生成快照前已提交）
trx_id >= max_trx_id        → 不可见（快照之后才开始的事务）
min_trx_id <= trx_id < max_trx_id
    在 m_ids 里（当时还没提交）→ 不可见 → 沿 roll_pointer 找更旧版本
    不在（当时已提交）         → 可见
```

**不可见就顺着 `roll_pointer` 往前找，直到找到一个可见的版本**——**这就是"快照读"的全部实现。**

### 四、RC 与 RR：只差一个时机

| | ReadView 生成时机 | 后果 |
|---|---|---|
| **RC** | **每条 SELECT 语句**都生成一个新的 | 能看到别人刚提交的 → **不可重复读** |
| **RR** | **整个事务第一次快照读时**生成一次，之后复用 | 整个事务看到同一份 → **可重复读** |

**这就是"可重复读"的全部实现**——**不是靠锁，是靠"快照不再刷新"。** **理解了这一点，四个隔离级别的行为都能自己推出来，不用背。**

### 五、快照读 vs 当前读（幻读的真相）

| | 什么操作 | 用什么 |
|---|---|---|
| **快照读** | 普通 `SELECT` | **MVCC + ReadView**（不加锁） |
| **当前读** | `SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` / `INSERT` | **读最新版本 + 加锁**（`X` 锁 / 间隙锁，M10） |

**所以幻读的准确说法是**：

- **快照读下**：RR 的快照不变，**看不到后来插入的行** → 不幻读；
- **当前读下**：**必须读最新版本**，MVCC 帮不上 → 靠 **next-key lock 锁住范围**，阻止别人插入 → 也不幻读；
- **两种读混用时**：先用快照读看到 10 行，再 `UPDATE`（当前读）时行数变了——**这是"看起来像幻读"的正常现象**，**不是 bug**。

**答"RR 完全解决了幻读"是错的；答"InnoDB RR 下两种读都不幻读，机制不同"才是对的。**

## 二、扩展：类似题与追问

**类似题**

1. 「MVCC 在 RC 下也生效吗？」——**生效**，只是 ReadView 每条语句刷新一次。**MVCC 是 InnoDB 的基础能力，不是 RR 专属。**
2. 「undo log 什么时候删？」——**当它不再被任何 ReadView 需要时**，由 **purge 线程**清理。**所以长事务（M13）会让 purge 推不动，undo 膨胀**——这条直接连到 P13 的 PG 对照。
3. 「`UPDATE` 影响行数和我预期不符，是不是 MVCC 出错了？」——不是。**`UPDATE` 是当前读**，它看到的是最新数据，可能和你刚才快照读看到的不一样。**这是"两种读混用"的正常结果。**

**追问链**

- 追问一层：**「ReadView 判定里的 m_ids 为什么需要？」**——因为**"开始得早"不等于"已提交"**：一个事务可能在快照生成前就开始了，但直到快照生成后才提交——**它对这份快照不可见**。**所以必须记下"当时还活跃的名单"**。**这一条能答出来，说明不是背口诀。**
- 追问二层：**「MVCC 和两阶段提交有关系吗？」**——没有直接关系，但**有一个共同点：都依赖 undo/redo 的分工**（M11）。**两阶段提交解决的是 redo 与 binlog 的一致性；MVCC 解决的是读的一致性**——**两件事，别混在一起答。**
