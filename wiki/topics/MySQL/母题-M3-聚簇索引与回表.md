# 母题 M3 · 聚簇索引与回表

> **模块**：MySQL / 索引
> **所属主线**：一 · 索引（怎么让查询不用扫全表）
> **关联母题**：[[母题-M1-为什么用B+树]] · [[母题-M2-联合索引与最左前缀]]
> **素材来源**：`raw/后端视角复盘_MySQL` 第一条主线「EXPLAIN 的意义不是背字段」；聚簇/二级索引结构为通用知识补充（**待你核对**）

**题目**：同一条 SQL，有时加个索引就快 10 倍，有时加了却没用。`EXPLAIN` 出来怎么看它到底走了没走索引、慢在哪？

**母题**：聚簇索引和二级索引的区别是什么？「回表」为什么慢，「覆盖索引」为什么能省掉它？

**为什么重要**：这是**索引设计的最小闭环**。M1 讲树有多矮，M2 讲有序性怎么用，M3 讲**真正的成本在哪里**——树高只有 3 层，但回表可能是 100 次额外的随机 IO。答不出这层，就会以为「加了索引就快」。

**一句话结论**：聚簇索引的叶子存**整行数据**，二级索引的叶子只存**索引列 + 主键值**；用二级索引查非索引列时必须「回表」再查一次聚簇索引——**覆盖索引就是让需要的列全在二级索引里，从而免掉这次回表**。

**恢复关键词**：索引组织表 / 主键即数据 / 回表 = 二次查找 / 覆盖索引 / Using index

**核心不变量 / 主线**：
InnoDB 是**索引组织表**——主键索引的叶子就是数据本身，二级索引只是「指向主键的目录」。所以任何「先用二级索引、再取非索引列」的查询都要付出**两次 B+ 树查找**的代价。

**完整回答骨架**：聚簇 vs 二级索引的结构 → 回表是怎么发生的 → 覆盖索引怎么免掉它 → explain 四个字段怎么看

## 原理分解

### 一、两种索引的结构差异

**聚簇索引（clustered index）= 主键索引**

```
叶子节点 = 完整的一行数据（id, status, next_retry_time, priority, ...）
```

所以 InnoDB 里「按主键查」是最快的——**一次 B+ 树定位就拿到整行**。

**二级索引（secondary index）= 普通索引**

```
叶子节点 = 索引列的值 + 主键值
例：(status, next_retry_time) 的叶子 → (status, next_retry_time, id)
```

注意：二级索引**必须**带上主键值，否则找不到对应的行。这也解释了两个常见现象：
- 主键越短，所有二级索引都越小
- 用非主键做聚簇代价很高（所以 InnoDB 固定用主键）

### 二、回表：那一次被忽略的额外查找

```sql
-- 有索引 (status, next_retry_time)
SELECT id, status, next_retry_time, priority
FROM task
WHERE status = 'PENDING' AND next_retry_time <= NOW();
```

执行过程：

1. 走二级索引 `(status, next_retry_time)` 定位到满足条件的索引项 → 拿到 `id`
2. `priority` **不在**二级索引里 → 拿 `id` 回聚簇索引再查一次，取出整行
3. 第 2 步就是**回表**，每条命中行都要做一次

**这就是为什么「命中 1000 行」比「命中 10 行」危险得多**：树高始终 3 层，但回表次数随命中行数线性增长。

### 三、覆盖索引：让索引自己回答完

把查询要用的列都放进索引，就不需要回表了：

```sql
-- 索引改成 (status, next_retry_time, priority)
SELECT id, status, next_retry_time, priority   -- id 本来就在二级索引里
FROM task
WHERE status = 'PENDING' AND next_retry_time <= NOW();
```

`EXPLAIN` 的 `Extra` 里出现 **`Using index`**，就是走了覆盖索引。

代价：索引变宽、写入变慢、占用空间。**不是所有查询都值得覆盖**，热点查询值得。

### 四、EXPLAIN 只看四个字段

| 字段 | 看什么 | 好 / 坏的信号 |
|---|---|---|
| `type` | 访问类型 | 好 → 坏：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL`；出现 `ALL` 就是全表扫 |
| `key` | 实际用了哪个索引 | 是 `NULL` 说明没走索引；和预期不一致要看 `possible_keys` |
| `rows` | 预估扫描行数 | 越小越好；这个值是估算，不是精确值 |
| `Extra` | 额外动作 | `Using index` 好（覆盖）；**`Using filesort` / `Using temporary` 是明确的优化信号** |

素材里那句话可以当口诀用：**出现 `Using filesort` 或 `Using temporary`，基本就说明这条 SQL 还有优化空间。**

## 二、扩展：类似题与两层追问

**同类变体**

- 为什么建议用自增主键，而不是 UUID？（页分裂 + 二级索引膨胀）
- 索引下推（ICP）和覆盖索引的区别？（ICP 减少**回表次数**，覆盖索引**免掉回表**）
- 为什么 `SELECT *` 在 InnoDB 里代价更高？（几乎必然回表，且无法覆盖）

**追问**（数量不限，能答完才算通过）

1. **既然覆盖索引能免回表，为什么不全表都建宽索引？** —— 索引要跟着写入一起维护：越宽的索引写入越慢、占空间越多；且索引数量多会干扰优化器选择。**覆盖是给热点查询的，不是给全表的。**
2. **`rows` 很小就一定快吗？** —— 不一定。`rows` 是**估算值**，且它不含回表成本。命中 10 行但每行回表一次，可能比扫 100 行的覆盖索引还慢。
