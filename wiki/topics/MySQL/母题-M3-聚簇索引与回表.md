## 一、教材

### 1. 前提：一张表可以有两种存法

#### 1.1 两种存法【事实】

这是理解回表之前必须先有的一张底图：

| 存法 | 表本身长什么样 | 代表 |
|---|---|---|
| **堆表**（heap-organized） | 一张**无序的大堆**，行按写入顺序堆放；所有索引都是"指向堆里某一行"的目录 | PostgreSQL、Oracle |
| **索引组织表**（index-organized） | **表本身就是一个 B+ 树**，按主键排好；行就住在主键索引的叶子节点里 | InnoDB |

**定义要说准**：在索引组织表里，"主键索引"和"表"**是同一个东西**——不是两张数据结构，是一张。这就是"聚簇"（clustered）的含义：**数据与主键索引聚集在一起。**

#### 1.2 InnoDB 为什么选索引组织表【取舍】

**换来的好处**：

- **按主键查一次就拿到整行**——少一次查找。主键查询（`WHERE id = ?`）是后台系统里最高频的访问路径。
- 主键相邻的行**物理相邻**——按主键范围扫是顺序 IO，不是随机 IO。

**付出的代价**：

- **主键不能随便选。** 主键一变，整棵树的物理组织就变（见 [[母题-M5-引擎与表设计基本盘]] 的自增主键与页分裂）。
- **所有二级索引都被"传染"。** 二级索引必须带上主键（下一节讲），所以**主键越宽，所有二级索引一起变胖**。

**结论一句话**：InnoDB 用"**每次主键查询省一次查找**"换"**主键长度影响全表所有索引**"。这是个真实取舍，不是免费午餐。

### 2. 两种索引的叶子装什么

::figure clustered-vs-secondary.svg | 聚簇索引与二级索引的叶子节点对比 | 聚簇索引叶子存完整一行；二级索引叶子只存索引列加主键，取别的列就要回表

#### 2.1 聚簇索引（主键索引）

```
叶子节点 = 完整的一行  (id, status, next_retry_time, priority, …)
```

所以 `WHERE id = 123` 是**一次 B+ 树下降**（M1 算过：约 3 层）就直接拿到整行。**这也是"主键查询最快"的机制来源。**

#### 2.2 二级索引（普通索引）

```
索引 (status, next_retry_time) 的叶子 = (status, next_retry_time, id)
                                                          ↑ 主键必须带上
```

【推导】**为什么必须带主键**：索引项要能回答"这一项对应哪一行"。堆表里这个答案是"物理地址"；InnoDB 里没有独立物理地址，**主键就是那行的地址**。所以二级索引的叶子 = 索引列 + 主键。

**两个直接推论**：

1. **主键越短，所有二级索引越小**（见 3.3 的量化）。
2. **二级索引天然包含主键列**——所以 `SELECT id` 走二级索引时**本来就不回表**，这是白拿的。

#### 2.3 一个常被忽略的后果

一张表有 5 个二级索引时，**主键被复制了 5 份**（每个索引的叶子里都有一份）。

**所以"主键长度"这个选择的成本不是乘以 1，而是乘以"二级索引个数 + 1"。** 这是 [[母题-M5-引擎与表设计基本盘]] "别用 UUID 当主键"这句话在存储层面的真实证据。

### 3. 回表：把它算出来，而不是当名词记住

#### 3.1 定义

**回表（back to table / row lookup）**：用一个**不包含所需列**的二级索引定位到记录后，拿索引叶子里带的主键值，**回到聚簇索引再查一次取出整行**。

关键：**它是第二次独立的 B+ 树查找**，不是"顺便读一下"。

#### 3.2 一次查询的完整成本拆解

```sql
-- 索引 (status, next_retry_time)，表里有 1000 万行
SELECT id, status, next_retry_time, priority
FROM task
WHERE status = 'PENDING' AND next_retry_time <= NOW();   -- 命中约 1000 行
```

| 步骤 | 成本 |
|---|---|
| ① 定位 | 二级索引下降 ~3 层 ≈ 3 次 IO（前两层大概率在缓存） |
| ② 扫索引项 | 1000 个索引项在叶子层连续排列 → 顺序读，几十次 IO |
| ③ **取 `priority`** | **不在二级索引里 → 1000 次回表** |

【推导】**步骤 ③ 是唯一随命中行数线性增长的项。**

| 命中行数 | ② 扫索引 | ③ 回表次数 |
|---|---|---|
| 10 | 十几次 | 10 |
| 1000 | 几十次 | 1000 |
| 100 万 | 几百次（顺序） | **100 万** |

**这就是"命中 1000 行比命中 10 行危险得多"的量化版本**：树高始终是 3 层，但回表次数跟着行数走。

#### 3.3 为什么回表贵——不只是"多几次 IO"

两个放大因素：

1. **它是随机 IO。** ② 扫索引是顺序的（叶子连成链表，M1 讲过），但 ③ 要按主键值去树的**任意位置**取行——**每一次都是一个独立位置**。顺序 IO 有预读和块对齐的优惠，随机 IO 没有。
2. **它破坏了 M2 好不容易挣来的收益。** M2 的功夫都花在"把扫描量从 100 万压到 3.3 万"；如果每一条都要回表，**省下来的扫描量就以另一张账单付回去了。**

【推论】**判断一条查询快不快，不能只看 `EXPLAIN` 里扫了多少行，还要看这些行有多少需要回表。**

### 4. 覆盖索引：让索引自己把答案答完

#### 4.1 定义与判据

**覆盖索引（covering index）**：查询需要的**所有列**都出现在这条索引里（索引列 + 主键），因此**不需要回表**。

```sql
-- 索引改成 (status, next_retry_time, priority)
SELECT id, status, next_retry_time, priority   -- id 本来就在二级索引里
FROM task
WHERE status = 'PENDING' AND next_retry_time <= NOW();   -- 不再回表
```

**判据只有一个**：`EXPLAIN` 的 `Extra` 里出现 **`Using index`**。

【事实】**这里有个容易混淆的点**：`Using index` 表示"覆盖"，`key` 有值表示"走了索引"，两件事不同。**走了索引 ≠ 不回表。**

#### 4.2 代价（必须说全，否则会答成"能覆盖就覆盖"）

| 代价 | 具体表现 |
|---|---|
| **索引变宽** | 每多一列，叶子每条索引项都变长 → 每页装的项变少 → **树可能多一层**、缓存命中率下降 |
| **写放大** | 索引要跟着每次 `INSERT` / `UPDATE` 维护；列越多，写入越慢。**更新被覆盖的列时，索引要改** |
| **优化器负担** | 索引数量多，优化器的选择空间变大，选错计划的概率上升 |

#### 4.3 什么时候值得

【取舍】**判据是"读的频率 × 命中行数"是否显著大于"写的频率"。**

- **值得**：高频、窄、命中行数多的查询（列表页、报表、任务调度取批）——**这里省下的是几千次回表**
- **不值得**：写多读少的表、命中行数极少（命中 3 行，回表 9 次 IO，无所谓）、或者只在夜间跑一次的分析查询

**不要为了"看起来优化过"而给每张表加宽索引。** 索引是欠写入的债。

### 5. `EXPLAIN` 只先看四个字段

| 字段 | 看什么 | 信号 |
|---|---|---|
| `type` | 访问类型 | 好 → 坏：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL`。**出现 `ALL` 就是全表扫** |
| `key` | 实际用了哪个索引 | `NULL` = 没走索引；和预期不符就看 `possible_keys` |
| `rows` | **预估**扫描行数 | 越小越好，但它是**估算**且**不含回表成本**（见 Q3） |
| `Extra` | 额外动作 | `Using index` = 覆盖；**`Using filesort` / `Using temporary` 是明确的优化信号** |

素材里那句话可以直接当口诀：**出现 `Using filesort` 或 `Using temporary`，基本说明这条 SQL 还有优化空间。**

【推导】**这四个字段的阅读顺序是有逻辑的**：`type` → 有没有走索引 → `key` → 走了哪条 → `rows` → 要扫多少 → `Extra` → 还要不要排序/临时表/回表。**按这个顺序读，就不会看到 `ALL` 还在纠结 `Extra`。**

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "加了索引就快" | 【推导】索引只保证**定位**便宜。真实成本 = 扫描行数 + **回表次数**，后者可能才是大头 |
| "树高 3 层所以很快" | 【推导】树高对任何查询都一样，解释不了差异。差异在扫了多少行、回了多少次表 |
| "`Extra` 里没有 `filesort` 就说明优化到位了" | 【取舍】只能说明排序免掉了。回表次数和扫描行数可能仍然很差 |
| "只要覆盖索引就免回表，所以越宽越好" | 【取舍】索引变宽会让**写入**和**所有其他查询**一起变慢（见 4.2） |
| "PG 和 MySQL 一样，主键就是数据" | 【事实】**PG 是堆表**，所有索引叶子存 `ctid`，**都要回表**；`CLUSTER` 只做一次性重排、不持久。见 [[母题-P2-堆表与回表]] |

## 二、自测

**Q1（计算）**：一条查询命中 1000 行，需要的 `priority` 列不在二级索引里。请拆开算：「二级索引 + 回表」和「覆盖索引」的成本差在哪一步、差多少？

**A1**：

| 步骤 | 二级索引 + 回表 | 覆盖索引 |
|---|---|---|
| ① 定位 | ~3 次 IO | ~3 次 IO |
| ② 扫 1000 个索引项 | 顺序读，约几十次 IO | 同样几十次 |
| ③ 取 `priority` | **1000 次回表**（每条一次 B+ 树查找，缓存不命中时每次约 3 次**随机** IO） | **0** |

**差异全部在 ③，量级是 0 → 1000。** 而且 ③ 是随机 IO、② 是顺序 IO——**所以真实差距比"1000 对 0"还要大**。

**Q2（计算）**：一张表有 5 个二级索引，主键从 `BIGINT`（8B）换成 `UUID`（36B）。二级索引的空间会怎么变？

**A2**：每个二级索引的叶子都存主键 → **每条索引项多 28B**。

- 若某二级索引平均每条原本约 50B → 变成 78B，**膨胀约 1.56 倍**
- 每页能装的索引项减少约 36% → **树可能多一层**，且缓存能装下的索引页变少
- **5 个二级索引全部受影响**，不是只影响主键索引

**这就是"别用 UUID 当主键"的存储层证据**——代价不在主键本身，在**被复制的 5 份**。

【补充】这也解释了为什么 InnoDB 里更常见的折中是**自增 `BIGINT` + 业务唯一键**：把 UUID 放到普通唯一索引上，主键仍然保持窄。

**Q3（判读）**：`EXPLAIN` 显示 `rows = 10`，`type = ref`，但这条 SQL 实测很慢。可能是什么原因？

**A3**：`rows` 只是**预估的扫描行数**，它有两个盲区：

1. **它是估算值**，来自统计信息；统计信息过期（比如刚批量导入）会严重低估。
2. **它不含回表成本。** 假设这 10 行每行都要回表，且回表的目标页**都不在 Buffer Pool 里** → 10 × 3 = **约 30 次随机 IO**。而同一次比较里，另一条扫 100 行的**覆盖索引**全程顺序读，可能只要十几次 IO——**反而更快**。

**所以"rows 小就一定快"不成立。** 正确的读法是：`rows` × （是否回表）一起看。

**Q4（纠错）**：下面这段话哪里错了？

> "二级索引查到的是主键，再顺便去主键索引里读一下整行，成本不高。"

**A4**：**"顺便"这个词错了。** 回表是**第二次独立的 B+ 树查找**，不是"顺路读一下"：

- **位置独立**：按主键值去树的任意位置，**每次都是随机 IO**；而扫二级索引是顺序的。
- **次数随行数增长**：命中 N 行就是 N 次查找。**这是整条查询里唯一随数据量放大的项。**

准确说法：**回表是"每条命中行各付一次随机 B+ 树查找"，成本随命中行数线性增长。**

**Q5（纠错）**：下面这段话哪里错了？

> "PostgreSQL 的主键索引也是聚簇的，主键就是数据本身，所以和 InnoDB 一样按主键查最快。"

**A5**：**前半句错了。PG 是堆表，没有聚簇索引。** 在 PG 里：

- 表是一堆**无序的行**，所有索引（包括主键索引）叶子都存 **`ctid`**（物理位置），**都要回表**
- `CLUSTER` 命令能按某个索引**重排一次**数据，但这是**一次性操作、不会持久**——后续写入又变回无序

**所以准确的对比是**：InnoDB 用"索引组织表"让主键查询少一次回表；PG 用"堆表"换取**更新时不必移动整棵树**（行在原地改，索引只更新 `ctid` 指向）。

**说成"PG 也有聚簇索引"是典型的把 MySQL 语义套到 PG 上——面试里这句会被直接抓住。**

## 三、面试输出（学完再看）

**一句话结论**：InnoDB 是**索引组织表**——主键索引的叶子就是整行数据，二级索引的叶子只是「索引列 + 主键」。所以"先用二级索引、再取非索引列"要付出**两次 B+ 树查找**的代价，这就是**回表**；它随命中行数线性增长，且是随机 IO。**覆盖索引把需要的列全放进索引里，让第二次查找消失**（`Extra` 出现 `Using index`）。

**恢复关键词**：索引组织表 vs 堆表 / 主键即数据 / 二级索引叶子 = 索引列 + 主键 / 主键被复制 N+1 份 / 回表 = 第二次查找、随行数增长、随机 IO / 覆盖索引 = 免掉第二次 / 代价是写放大

**核心不变量 / 主线**：
**InnoDB 把"表"和"主键索引"合成了一份数据结构。** 好处是按主键查只需一次下降；代价是**主键出现在每一个二级索引里**，于是"主键怎么选"变成了全表级的成本问题，而"取不在索引里的列"变成了一次额外查找。

**完整回答骨架**：索引组织表 vs 堆表（为什么 InnoDB 这么选）→ 两种索引的叶子装什么 → 二级索引为什么要带主键 → 回表的成本拆解（定位 / 扫描 / 回表三段，只有第三段随行数增长、且是随机 IO）→ 覆盖索引免掉它（`Using index`）与它的代价（写放大、索引变宽）→ `EXPLAIN` 四字段的阅读顺序 → 方言（PG 是堆表）

**完整回答（口述稿）**：
先说两种存法：堆表里索引叶子存行地址；InnoDB 是索引组织表，主键索引的叶子就是整行数据，二级索引的叶子只是「索引列 + 主键值」。

所以取非索引列要两次 B+ 树查找——先在二级索引树上定位到主键，再回聚簇索引取整行，第二次就是回表。成本拆成定位、扫描、回表三段，只有第三段随命中行数线性增长，而且是随机 IO：扫 1000 行就是 1000 次随机 IO，这才是「加了索引还是慢」的主因。

覆盖索引把需要的列全放进索引，让第二次查找消失，判据是 EXPLAIN 的 Extra 出现 Using index。代价要一起说：索引变宽、写入维护变贵、还可能干扰优化器，所以它是给热点查询的，不是给全表的。

EXPLAIN 只看四个字段：type、key、rows（估算值，且不含回表成本）、Extra（Using index 说明覆盖、Using filesort 说明还要排序）。边界：PG 是堆表，索引叶子存 ctid，一律回表。
**分层要点**：
- **结论**：InnoDB 是索引组织表；回表 = 第二次 B+ 树查找，随命中行数线性增长且是随机 IO；覆盖索引让它消失（Extra 出现 Using index）。
- **推导链**：两种存法 → InnoDB 的取舍（按主键查只需一次下降）→ 二级索引叶子必须带主键 → 取整行要再查一次 → 覆盖把需要的列放进索引 → 代价是写放大与索引变宽。
- **量化**：成本 = 定位 + 扫描 + 回表 × 命中行数；扫 1000 行 = 1000 次随机 IO；覆盖之后第三段归零。
- **边界与常见误解**：树高 3 层解释不了快慢差异（对所有查询都一样）；rows 小也可能慢（不含回表）；覆盖索引越宽越好 ×；PG 是堆表，一律回表。
**追问**（先说后看）

1. **既然覆盖索引能免回表，为什么不全表都建宽索引？** —— 索引是**欠写入的债**：越宽，每次 `INSERT`/`UPDATE` 维护成本越高、页里能装的项越少、树还可能多一层。而且索引多了会干扰优化器的选择。**覆盖是给热点查询的，不是给全表的。**
2. **`rows` 很小就一定快吗？** —— 不一定。它是**估算值**，且**不含回表成本**。扫 10 行的回表可能比扫 100 行的覆盖索引还慢。
3. **`SELECT *` 为什么在 InnoDB 里代价更高？** —— 它几乎必然需要回表（`*` 里的列不可能全在一条二级索引里），而且**不可能被覆盖**。
4. **为什么建议自增主键而不是 UUID？** —— 两个层面：① **写入**层面，随机主键导致页分裂（见 [[母题-M5-引擎与表设计基本盘]]）；② **存储**层面，36B 主键被复制进**每一个**二级索引。**第二点比第一点更常被忽略。**

**同类变体**

- 索引下推（ICP）和覆盖索引的区别？（ICP 减少**回表次数**，覆盖索引**免掉回表**）
- 为什么 `ORDER BY id` 在 InnoDB 里几乎免费，PG 里不一定？（InnoDB 数据按主键物理有序，PG 堆表无序）
- 二级索引能不能反向遍历？（能。B+ 树叶子是双向链表，M1 讲过为什么是双向）
