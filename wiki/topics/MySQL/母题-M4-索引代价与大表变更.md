# 母题 M4 · 索引代价与大表变更

> **模块**：MySQL / 索引
> **所属主线**：一 · 索引（怎么让查询不用扫全表）
> **层级**：B · 标准级（MDL 连锁能从"锁队列是先进先出"推出来，写放大与空间能算；但"选 Online DDL 还是影子表"是取舍）
> **关联母题**：[[母题-M1-为什么用B+树]]（每棵索引都是一棵 B+ 树）· [[母题-M2-联合索引与最左前缀]]（一个索引服务更多查询 = 少建几个）· [[母题-M3-聚簇索引与回表]]（主键被复制进每个二级索引）
> **素材来源**：通用知识 + 生产实践（raw 材料第一条主线未覆盖这块，属补充，**待你核对**）。**本轮升级补入：写放大/空间的两组算式、MDL 队列的三个量化、自测题、图**

**导读**：必懂 3 件事（① 索引的三笔代价 ② "把库搞挂"的真实机制是**排队**不是慢 ③ Online DDL 保证了什么、又没保证什么）· 读完约 11 分钟 · 需要先懂：[[母题-M1-为什么用B+树]]

**题目**：任务表 5000 万行，线上正在跑。现在要给 `status` 加一个索引，你直接执行 `ALTER TABLE task ADD INDEX idx_status(status)`。会发生什么？

**母题**：**索引不是免费的——它的代价具体是什么？在大表上做结构变更，危险到底来自哪里，怎么才能不阻塞线上流量？**

**为什么重要**：这是"知识"和"工程"的分界线。知道索引能加速是课本，知道**加索引可能把库搞挂**才是生产经验。而且它是面试官区分"背过八股"和"动过线上库"的典型问题。

## 一、教材

### 1. 前提：索引是读的快照，写的负债

#### 1.1 三笔代价【事实】

| 代价 | 具体是什么 | 谁在付 |
|---|---|---|
| **写放大** | 每次 `INSERT`/`UPDATE`/`DELETE` 都要同步维护所有相关索引 | **每一笔写** |
| **空间** | 二级索引的叶子存「索引列 + 主键」，主键越长、索引越多，占的空间越大 | **磁盘与缓存** |
| **优化器负担** | 候选索引变多 → 优化器要评估的计划变多 → **选错的概率上升**（统计信息不准时更明显） | **每一次查询** |

#### 1.2 写放大能算出来【推导】

一张表有 **1 个聚簇索引**（数据本身）+ **N 个二级索引**，那么一次写入要改 **N + 1 棵 B+ 树**，每棵都要保证有序（可能触发页分裂）。

```text
一张表 1 个聚簇索引 + 6 个二级索引
  一次写入 → 维护 7 棵 B+ 树
  写入 QPS 5000 时 → 每秒 5000 × 7 = 35,000 次 B+ 树插入

删掉 2 个"从没被查询用过"的索引：
  7 棵 → 5 棵，每秒 35,000 → 25,000 次
  写入侧直接省 29%
```

【取舍】所以判据是**一句可执行的话**：**这个索引有没有高频查询真的在用它？** 没有任何查询用得上的索引，是**纯负债**——它只在写入时收费。

#### 1.3 空间也能算出来【推导】

二级索引的叶子存「索引列 + 主键」。以给 `status`（INT，4B）建索引为例，算上 InnoDB 的记录头开销约 6B：

```text
主键 BIGINT（8B）：每条 ≈ 4 + 8 + 6 = 18B
  5000 万行 → 18B × 5000万 ≈ 900 MB

主键换 UUID（36B）：每条 ≈ 4 + 36 + 6 = 46B
  5000 万行 → 46B × 5000万 ≈ 2.3 GB
```

**同一个索引，只因为主键变长，就膨胀 2.6 倍**（46 ÷ 18）。而且这还只是**一个**索引——有 6 个二级索引，就是 6 份一起膨胀（[[母题-M5-引擎与表设计基本盘]] 会再讲主键选型）。

**到这里你应该能回答**：为什么"反正磁盘便宜，索引多建几个"在写多的表上是错的？

### 2. 大表 DDL 的危险到底来自哪里

#### 2.1 它要做两件事【事实】

`ALTER TABLE ... ADD INDEX` 分两步：

1. **扫描全表 + 排序，建出一棵新索引**（5000 万行，几分钟到几十分钟）
2. 在**开始和结束**各拿一次 **MDL（元数据锁）**

直觉会怪第 1 步"太慢"。**但危险在第 2 步。**

#### 2.2 MDL 连锁：真正的机制【推导】

MDL 的规则很短：**读锁与读锁兼容，读锁与写锁互斥**；而 **MDL 请求队列是先进先出、不能插队的**。

```text
① 一个长事务在跑（持 MDL 读锁）——它可能只是一条跑了 5 分钟的慢 SELECT
        ↓
② DDL 要申请 MDL 写锁 → 与读锁互斥 → 排队等待
        ↓
③ 后面来的普通查询也要 MDL 读锁。它们本该和①兼容（都是读），
   但因为队列 FIFO，它们必须排在「正在等待的 DDL」后面
        ↓
④ 每个排队的请求都占着一条数据库连接 → 连接池被占满
        ↓
⑤ 新请求连不上库 → 服务雪崩（而且不只是这张表的问题）
```

【推导】**危险被放大的方式**：

```text
积压的请求数 ≈ QPS × DDL 等待的秒数

QPS 2000、DDL 等 30 秒 → 积压 2000 × 30 = 60,000 个请求
连接池通常只有几百条 → 瞬间排满
```

【推论】**DDL 的等待时间被"并发度"放大了**——所以真正要控制的不是 DDL 有多快，是**它等待的时间**。

::figure mdl-queue.svg | MDL 连锁：为什么「加个索引」能把库搞挂 | 长事务持有读锁 → DDL 等写锁 → 后面的查询因队列 FIFO 全部排在 DDL 后面 → 队列线性增长 → 连接池耗尽

**到这里你应该能回答**：为什么说"危险的不是 DDL 慢，是它堵出了一条越来越长的队"？

### 3. 候选方案（先各自介绍，不比较）

#### 3.1 Online DDL（MySQL 5.6+）【事实】

```sql
ALTER TABLE task ADD INDEX idx_status(status), ALGORITHM=INPLACE, LOCK=NONE;
```

| 参数 | 作用 |
|---|---|
| `ALGORITHM=INPLACE` | 不重建整表（加二级索引只需扫描 + 排序） |
| `LOCK=NONE` | DDL **执行期间**允许并发读写 |

#### 3.2 影子表方案（pt-osc / gh-ost）【事实】

四步：

1. 建一张结构相同的新表（带新索引）
2. **同步增量**：pt-osc 用触发器、gh-ost 读 binlog，把旧表的新写入同步到新表
3. **分批拷贝存量**：可限速、可暂停
4. `RENAME TABLE` 瞬间切换

| | pt-osc | gh-ost |
|---|---|---|
| 增量来源 | 触发器 | **binlog** |
| 对主库影响 | 触发器有额外开销 | 更小 |
| 可暂停 / 限速 | 支持 | 支持，且更细 |

#### 3.3 先处理掉长事务（这不是方案，是前置动作）【事实】

```sql
SELECT trx_id, trx_started, trx_mysql_thread_id
FROM information_schema.innodb_trx
WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;
```

### 4. 逐个淘汰（统一指标：**对线上流量的最坏影响**）

#### 4.1 为什么"直接执行 DDL"不可接受【推导】

它把**不可控的等待时间**暴露给了整条链路：DDL 等多久，取决于**碰巧有没有长事务**。而由上面积压公式，等待 30 秒就能把连接池打满。

#### 4.2 为什么"开了 LOCK=NONE 就安全"是错的【推导】

`LOCK=NONE` 只保证**DDL 执行期间**不阻塞别人。它**不能保证 DDL 自己不被别人阻塞**——长事务持读锁时，DDL 照样要等。**而它一旦开始等，第 2.2 节的连锁照样发生。**

【事实】另外 `ALGORITHM=INPLACE` 也不是万能的：改列类型、重建聚簇索引这类操作做不到 INPLACE。

#### 4.3 胜出方案：按"表的规模 + 是否可回滚"选【取舍】

| 场景 | 选择 |
|---|---|
| 加二级索引、表不算很大 | **Online DDL**（`ALGORITHM=INPLACE, LOCK=NONE`） |
| 表很大、要求可控可回滚 | **pt-osc / gh-ost** |
| 改列类型等无法 INPLACE 的操作 | **影子表方案** |
| **任何情况** | **先查长事务；设短 `lock_wait_timeout`；别在高峰动手；备好回滚** |

【取舍】三个方案的差别在**代价放在哪**：Online DDL 简单但等待不可控；影子表可控但要多一倍空间、还要运维工具。**没有"最安全"的方案，只有"这次变更最适合"的方案。**

【事实】顺带一个 MySQL / PG 的方言差异：PG 的对应手段是 `CREATE INDEX CONCURRENTLY`，**它同样有个容易踩的点**——建索引过程中失败会**留下一个 invalid 索引**，需要手动 `DROP` 再重建（[[母题-P4-索引代价与在线建索引]]）。

**到这里你应该能回答**：为什么"选哪个方案"这个问题，答案里必须包含"先查长事务"？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "加了索引查询就快，反正空间便宜" | 三笔代价：**写放大**（+1 棵聚簇 + N 棵二级）、**空间**（主键越长所有索引越大）、**优化器负担**。没被用上的索引是**纯负债** |
| "`LOCK=NONE` 开了就不会影响线上" | 它只保证 **DDL 执行期间**不阻塞；**不保证 DDL 不被长事务阻塞**。等待一旦发生，MDL 连锁照样雪崩 |
| "`ALGORITHM=INPLACE` 所有 DDL 都适用" | 改列类型、重建聚簇索引这类做不到 INPLACE，只能重建表或用影子表 |
| "DDL 慢是因为要扫 5000 万行" | 扫描几分钟确实慢，但**把库搞挂的是 MDL 排队**——两者是不同的机制，要分开说 |
| "删索引很快，没风险" | `DROP INDEX` 通常快，但**同样要拿 MDL**，同样会被长事务卡住 |
| "在业务低峰执行就安全了" | 低峰降低了 QPS，从而降低积压速度，但**没有消除长事务这个触发源**。低峰 + 查长事务 + 短 `lock_wait_timeout` 才是完整动作 |

【取舍】读成一句话：**索引的代价是"每一次写"，DDL 的危险是"不可控的等待"——这两件事都不是靠"表大不大"决定的，是靠"有没有人用、有没有人挡"决定的。**

## 二、自测

**Q1（计算）**：一张表有 1 个聚簇索引 + 6 个二级索引，写入 QPS 为 5000。

问：**一次写入要维护几棵 B+ 树？每秒总共多少次 B+ 树插入？如果删掉 2 个从没被查询用过的索引，写入侧省多少？**

**A1**：

```text
一次写入维护 = 1（聚簇）+ 6（二级）= 7 棵
每秒插入次数 = 5000 × 7 = 35,000 次

删掉 2 个没用上的索引：
  7 棵 → 5 棵
  5000 × 5 = 25,000 次/秒
  降幅 = 1 − 25000/35000 = 28.6% ≈ 29%
```

【结论】**"没被用上的索引是纯负债"这句话可以量化**：每多一个索引，写入侧的 B+ 树维护次数就多 1/7（以 7 棵为例）。删两个就是 **29% 的写入开销**。

【补充】注意这里只算了"次数"，没算每次的代价不同——如果被删的索引恰好是那个**最宽**的（比如包含长字符串列），省下的还不止 29%。

**Q2（计算）**：某接口 QPS 2000。一条 DDL 因为撞上长事务，**等了 30 秒**才开始执行。

问：**这 30 秒里积压了多少个请求？**如果连接池上限是 500 条，会发生什么？如果 DDL 等的是 5 秒而不是 30 秒，情况会好转多少？

**A2**：

```text
积压 = QPS × 等待秒数 = 2000 × 30 = 60,000 个请求
连接池上限 500 → 前 500 个占满连接池，剩下 59,500 个连不上库
   → 表现为：整个服务超时（不只是这张表的接口）
```

等 5 秒时：`2000 × 5 = 10,000` 个请求——**仍然是连接池的 20 倍**，照样打满。

【结论】**积压量对等待时间是一次的线性关系，而连接池是个固定的小数字。** 所以要压的不是"积压从 6 万降到 1 万"，而是**把等待压到接近 0**（先处理长事务 + 设短 `lock_wait_timeout` 让 DDL 快速失败）。

**Q3（计算）**：给 `status`（INT，4B）建二级索引。InnoDB 记录头开销按 6B 估。

问：**主键是 BIGINT（8B）和 UUID（36B）两种情况下，这个索引各占多大空间（5000 万行）？差多少倍？**

**A3**：

```text
每条索引项 = 索引列 + 主键 + 记录头

BIGINT：4 + 8 + 6 = 18B
  5000万 × 18B ≈ 900 MB

UUID：  4 + 36 + 6 = 46B
  5000万 × 46B ≈ 2.3 GB

倍率 = 46 / 18 ≈ 2.6 倍
```

【结论】**同一个索引，只因为主键从 8B 变成 36B，就膨胀 2.6 倍。** 而且**主键会被复制进每一个二级索引**——6 个索引就是 6 份一起膨胀（[[母题-M3-聚簇索引与回表]]、[[母题-M5-引擎与表设计基本盘]]）。

【补充】这也是"主键要短"这条经验法则的**唯一量化依据**：不是因为"短的主键比较快"，是因为**它会被复制很多份**。

**Q4（纠错）**：下面这段话哪里错了？

> "我用 `ALGORITHM=INPLACE, LOCK=NONE` 建的索引，所以这个 DDL 不会影响线上。"

**A4**：错在**把"执行期间不阻塞"当成了"整个过程不会被阻塞"**。

- `LOCK=NONE` 保证的是：**DDL 真正执行的那段时间**允许并发读写。
- 它**不保证**：DDL **拿 MDL 写锁**这一步不被长事务挡住。长事务持读锁时，DDL 照样排队。
- 而**一旦开始排队，MDL 连锁就启动了**：后续所有查询（哪怕只是读）都会因为队列 FIFO 排在 DDL 后面 → 连接池打满。

【准确说法】"`LOCK=NONE` 解决的是'DDL 不阻塞别人'，**没解决'别人阻塞 DDL'**。所以要配套：执行前先查并处理长事务，再设一个短的 `lock_wait_timeout` 让 DDL 快速失败而不是长期堵着。"

**Q5（纠错）**：下面这段话哪里错了？

> "索引当然是越多越好，反正磁盘便宜，查询总能挑到合适的。"

**A5**：三处错。

1. **写放大**：一次写入要维护「1 棵聚簇 + N 棵二级」共 N+1 棵 B+ 树，每棵都可能触发页分裂。**索引的代价是按"每一次写"收的**，不是一次性的。
2. **空间不是"便宜"就能忽略**：索引占的不只是磁盘，还有 **buffer pool**。索引越胖，能缓存在内存里的页越少，**读也会变慢**。
3. **优化器负担**：候选计划变多，选错的概率上升（尤其是统计信息不准时）。

【准确说法】"索引数量的判据是**'有没有高频查询真的用它'**——用得上的索引是资产，**用不上的索引是纯负债**（只在写入时收费）。所以工程上不仅要会加索引，还要定期**找出并删掉没人用的索引**。"

## 三、面试输出（学完再看）

**一句话结论**：索引的代价是**三笔**——写放大（一次写维护 N+1 棵 B+ 树）、空间（主键被复制进每个二级索引，BIGINT→UUID 能让单个索引膨胀 2.6 倍）、优化器负担。大表 DDL 的危险**不在"扫 5000 万行慢"，而在 MDL**：长事务持读锁 → DDL 等写锁 → **后续查询因队列 FIFO 全排在 DDL 后面** → 积压数 = QPS × 等待秒数（2000 QPS 等 30 秒 = 6 万个请求）→ 连接池打满 → 整个服务雪崩。**`LOCK=NONE` 只解决"DDL 不阻塞别人"，没解决"别人阻塞 DDL"。** 所以真正的处方式是：**先查并处理长事务 + 设短 `lock_wait_timeout` + 按表规模选在线 DDL 或影子表 + 低峰执行 + 备回滚**。

**恢复关键词**：三笔代价（写放大/空间/优化器负担）/ 一次写维护 N+1 棵 B+ 树 / 主键被复制进每个二级索引，BIGINT→UUID 膨胀 2.6 倍 / **MDL 连锁**（读锁持住 → DDL 等写锁 → FIFO 不能插队 → 后续查询全排队）/ 积压 = QPS × 等待秒数 / 连接池打满 → 雪崩 / `LOCK=NONE` 只解决一半 / INPLACE 不是万能 / pt-osc 触发器 vs gh-ost binlog / 任何情况都先查长事务

**核心不变量 / 主线**：
**索引是读的快照，写的负债。**
它的全部代价都记在**写入路径**上；而大表变更的全部危险都来自**锁的排队语义**——不是"慢"，是"堵"。**两件事都不由表的大小决定，而由"有没有人用、有没有人挡"决定。**

**完整回答骨架**：三笔代价（写放大给算式、空间给算式）→ 大表 DDL 的两步，指出危险在第二步 → **MDL 队列 FIFO 的连锁推导 + 积压公式** → Online DDL 保证什么、没保证什么 → 影子表四步与 pt-osc/gh-ost 差异 → 按规模与可回滚性选 → 收束到"先查长事务 + 短 lock_wait_timeout"

**完整回答（口述稿）**：
索引的代价三笔：写放大（一次 INSERT 要维护 N+1 棵 B+ 树）、空间（主键被复制进每一个二级索引，BIGINT 换成 UUID 让单索引从 18B/条涨到 46B/条、约 2.6 倍）、优化器负担。没被用上的索引是纯负债。

大表 DDL 的危险不在「扫 5000 万行慢」，而在 MDL：DDL 要拿 MDL 写锁，前面有个长事务持着读锁没放，DDL 就只能在队列里等；MDL 队列是 FIFO，后面进来的查询全堵在它后面。积压数约等于 QPS × 等待秒数——2000 QPS 等 30 秒就是约 6 万个请求堆着，连接池打满、服务雪崩。

所以 LOCK=NONE 只解决「DDL 不阻塞别人」，没解决「别人阻塞 DDL」；ALGORITHM=INPLACE 也不是万能。

处方四步：先查并干掉长事务（前置动作，不是方案）；设短 lock_wait_timeout，让等待快速失败而不是无限堆积；按表规模与可回滚性选 Online DDL 还是影子表（pt-osc 用触发器、gh-ost 吃 binlog）；低峰执行 + 备好回滚。低峰只降低积压速度，不消除长事务这个触发源。
**分层要点**：
- **结论**：索引的代价是「每一次写」；大表 DDL 的危险是「不可控的等待」（MDL 连锁），不是扫描慢。两者都不是由表大不大决定的，是由有没有人用、有没有人挡决定的。
- **推导链**：三笔代价 → DDL 要做的两件事（改元数据 + 改数据）→ 危险在拿 MDL 写锁那一步 → 长事务持读锁 → DDL 排队 → 队列 FIFO 让后续查询一起堵 → 积压 = QPS × 等待秒数 → 连接池打满。
- **量化**：BIGINT→UUID 单索引 18B→46B（约 2.6 倍）；2000 QPS 等 30 秒 ≈ 6 万个请求积压。
- **边界与常见误解**：LOCK=NONE 只管一半；INPLACE 不是所有 DDL 都行（改列类型、重建聚簇只能重建表）；DROP INDEX 同样要拿 MDL；低峰是降速不是除因；完整动作 = 查长事务 + 短 lock_wait_timeout + 按规模选方案 + 低峰 + 备回滚。
**追问**（先说后看）

1. **`LOCK=NONE` 都开了，为什么还是可能卡住线上？** —— 关键在于**MDL 等待的连锁**：长事务持读锁 → DDL 等写锁 → 后续查询再排在 DDL 后面。`LOCK=NONE` 只保证 DDL 执行期间不阻塞，**不保证它不被别人阻塞**。
2. **索引是不是越多越好？** —— 不是。写放大 + 空间（还挤占 buffer pool）+ 优化器负担；判据是"有没有高频查询真的用它"。**没被用上的索引应该主动删掉。**
3. **MySQL 和 PG 在这件事上有什么不同？** —— PG 用 `CREATE INDEX CONCURRENTLY`，**它不会长时间持锁等**，但代价是**失败会留下 invalid 索引**需要手动清理，而且**不能在一个事务块里执行**。
4. **为什么 `NOT NULL + DEFAULT` 加字段有时很快、有时很慢？** —— 取决于能不能走 instant 路径。MySQL 8.0 支持 instant add column（元数据操作）；更早版本或某些类型会触发重建表。**判断方式是看 `ALGORITHM` 到底是 INSTANT / INPLACE / COPY，不要凭版本印象。**

**同类变体**

- 「**删索引**呢？」——`DROP INDEX` 通常快，但**同样要拿 MDL**，同样会被长事务卡住。流程与加索引一致。
- 「**加字段**为什么有时比加索引更危险？」——加索引是 INPLACE（不重建整表）；而加列在不能走 instant 时会**触发整表重建**，代价高一个量级。
- 「为什么说「**主键要短**」？」——因为它会被复制进**每一个二级索引**的叶子（[[母题-M3-聚簇索引与回表]]）。见 Q3 的 2.6 倍。
- 「**分区表**能替代这个方案吗？」——能缓解（`DROP PARTITION` 比 `DELETE` 干净），但**分区本身也是一次 DDL**，同样要走这套流程（[[母题-M15-数据增长治理]]、[[母题-P16-分区表]]）。
