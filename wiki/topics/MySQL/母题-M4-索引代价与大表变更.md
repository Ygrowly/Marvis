# 母题 M4 · 索引代价与大表变更

> **模块**：MySQL / 索引
> **所属主线**：一 · 索引（怎么让查询不用扫全表）
> **关联母题**：[[母题-M1-为什么用B+树]] · [[母题-M2-联合索引与最左前缀]]
> **素材来源**：通用知识 + 生产实践（**raw 材料第一条主线未覆盖这块，属补充，待你核对**）

**题目**：任务表 5000 万行，线上正在跑。现在要给 `status` 加一个索引，你直接执行 `ALTER TABLE task ADD INDEX idx_status(status)`。会发生什么？

**母题**：索引不是免费的——它的代价是什么？大表上做结构变更，怎么才能不阻塞线上流量？

**为什么重要**：这是「知识」和「工程」的分界线。知道索引能加速是课本，知道**加索引可能把库搞挂**才是生产经验。而且它是面试官区分"背过八股"和"动过线上库"的典型问题。

**一句话结论**：索引的代价是**写放大 + 空间 + 优化器负担**；大表变更的代价来自**重建结构 + 拿元数据锁（MDL）**——危险的不是 DDL 慢，而是**它把后续所有查询都堵在队列里**。

**恢复关键词**：写放大 / MDL 连锁 / Online DDL · LOCK=NONE / 影子表 / 长事务卡 DDL

**核心不变量 / 主线**：
**索引是读的快照，写的负债。** 每加一个索引，所有写入都要多维护一棵 B+ 树。所以索引数量是「读收益」与「写代价」的平衡，不是越多越好。

**完整回答骨架**：索引的三种代价 → 大表 DDL 为什么危险（重建 + MDL 连锁）→ Online DDL 怎么做到不阻塞 → 影子表方案 → 工程上怎么选

## 原理分解

### 一、索引的三种代价

1. **写放大**：每次 `INSERT` / `UPDATE` / `DELETE` 都要同步维护所有相关索引。**10 个索引 = 一次写入要改 10 棵 B+ 树**，而且每棵都要保证有序（可能触发页分裂）。
2. **空间**：二级索引的叶子存「索引列 + 主键」。主键越长，**所有**二级索引越大——这也是"别用 UUID 当主键"的原因之一。
3. **优化器负担**：索引越多，优化器要评估的执行计划越多，选错的概率上升；统计信息不准时还可能选错索引。

**所以判据是**：这个索引有没有高频查询真的用它？**没有任何查询用上的索引，是纯负债。**

### 二、大表加索引为什么危险

`ALTER TABLE ... ADD INDEX` 要做两件事：

1. 扫描全表 + 排序，建出一棵新索引（5000 万行，几分钟到几十分钟）
2. 在**开始和结束**拿 MDL（元数据锁）

危险不在第 1 步，在第 2 步的**连锁反应**：

```text
一个长事务还在跑（持有 MDL 读锁）
   ↓
DDL 请求 MDL 写锁 → 排队等待
   ↓
DDL 之后的所有查询也要 MDL 读锁 → 全部排在 DDL 后面
   ↓
连接池被排满 → 服务雪崩
```

**这才是"加个索引把库搞挂"的真实机制**：不是 DDL 本身慢，是它**在后面堵了一条越来越长的队**。

### 三、Online DDL（MySQL 5.6+）

```sql
ALTER TABLE task ADD INDEX idx_status(status), ALGORITHM=INPLACE, LOCK=NONE;
```

| 参数 | 作用 |
|---|---|
| `ALGORITHM=INPLACE` | 不重建整表（加二级索引只需扫描 + 排序） |
| `LOCK=NONE` | DDL 期间允许并发读写，只在开始/结束瞬间要短暂排他锁 |

**但边界仍在**：
- DDL 如果被长事务卡住等 MDL，`LOCK=NONE` 救不了你——它只是"允许并发"，不是"不需要锁"
- 有些操作无法 INPLACE（改列类型、重建聚簇索引等）

**所以执行前先查长事务**：

```sql
SELECT trx_id, trx_started, trx_mysql_thread_id
FROM information_schema.innodb_trx
WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;
```

### 四、影子表方案（pt-osc / gh-ost）

原理四步：

1. 建一张结构相同的新表（带新索引）
2. **同步增量**：pt-osc 用触发器、gh-ost 读 binlog，把旧表的新写入同步到新表
3. **分批拷贝存量**：可限速、可暂停
4. `RENAME TABLE` 瞬间切换

| | pt-osc | gh-ost |
|---|---|---|
| 增量来源 | 触发器 | binlog |
| 对主库影响 | 触发器有额外开销 | 更小 |
| 可暂停/限速 | 支持 | 支持，且更细 |

代价：需要约一倍额外空间；切换瞬间仍需短暂 MDL。

### 五、怎么选

| 场景 | 选择 |
|---|---|
| 加二级索引、表不算很大 | Online DDL（`ALGORITHM=INPLACE, LOCK=NONE`） |
| 表很大、要求可控可回滚 | pt-osc / gh-ost |
| 改列类型等无法 INPLACE | 影子表方案 |
| **任何情况** | **先查长事务；别在业务高峰动手；准备好回滚方案** |

## 二、扩展：类似题与两层追问

**同类变体**

- **删索引**呢？（`DROP INDEX` 通常快，但同样有 MDL 问题）
- **加字段**为什么比加索引更危险？（可能触发重建表；`NOT NULL + DEFAULT` 在 5.7 与 8.0 行为不同，8.0 支持 instant add column）
- 为什么说「主键要短」？（它会被复制进每一个二级索引）

**两层追问**（能答完才算通过）

1. **`LOCK=NONE` 都开了，为什么还是可能卡住线上？** —— 关键在于 **MDL 等待的连锁反应**：长事务持读锁 → DDL 等写锁 → 后续查询再排在 DDL 后面。`LOCK=NONE` 只保证 DDL 执行期间不阻塞，**不保证它不被别人阻塞**。
2. **索引是不是越多越好？** —— 不是。写放大 + 空间 + 优化器负担三笔账；判据是"有没有高频查询真的用它"。**没被用上的索引是纯负债，应该删掉。**
