# 母题 M1 · 为什么 InnoDB 用 B+ 树

> **模块**：MySQL / 索引与表设计
> **所属主线**：一 · 索引与表设计（怎么让查询不用扫全表）
> **层级**：A · 教材级（结论可以从前提推出来，所以必须推一遍而不是背）
> **关联母题**：[[母题-M2-联合索引与最左前缀]] · [[母题-M3-聚簇索引与回表]] · [[母题-M5-引擎与表设计基本盘]]
> **素材来源**：B+ 树结构原理与 InnoDB 页大小等参数为通用工程事实（**待你核对**）；推导线、量化算式与自测题为本次新增

**导读**：必懂 3 件事（① 页是一次 IO 的单位 ② 树高决定 IO 次数 ③ 三个设计点各解决什么）· 读完约 10 分钟 · 需要先懂：无

**题目**：InnoDB 的索引底层是 B+ 树。为什么是 B+ 树，而不是 B 树、红黑树或哈希表？

**母题**：数据库索引为什么必须选择 B+ 树？这个选择的约束条件是什么？

## 一、教材

### 1. 前提：真正的约束是磁盘 IO，不是比较速度

#### 1.1 先看量级

【事实】几种访问的延迟量级：

| 访问 | 典型延迟 | 相对内存 |
|---|---|---|
| 内存随机访问 | 约 100 纳秒 | ×1 |
| SSD 随机读 | 约 100 微秒 | **约 ×1000** |
| 机械盘随机读（含寻道） | 约 10 毫秒 | **约 ×100000** |

【推导】两个结论：

1. **磁盘随机 IO 比内存访问慢约 5 个数量级**（10 毫秒对 100 纳秒）。所以"每次比较多花一条指令"这种优化，在磁盘面前没有意义。
2. **因此评价任何磁盘索引结构，只有一个指标：定位一行需要几次 IO。** 少一次 IO，比少一百次比较值钱得多。

**这个指标必须固定**——后面比较哈希、红黑树、B 树，全部用它，否则不是比较。

#### 1.2 页（page）是什么【事实】

**定义**：页是数据库与磁盘之间**读写数据的最小单位**。InnoDB 默认 **16KB**。

**为什么会有这个粒度**【推导】：

- 磁盘不是按字节读写的。机械盘要等盘片转到目标位置（**寻道 + 旋转**），SSD 也要按块擦写——**硬件层面本来就有最小读写单位**（通常是 4KB 的块）。
- 操作系统在这个基础上做抽象，按"页"管理内存与磁盘之间的搬运。
- 数据库再往上，把**一次 IO 传输的数据量**定成自己的一页：InnoDB 选 16KB。

**关键推论**：**一次 IO 的成本几乎不随读多少数据变化**。读一行（如果做得到）和读一整页，都是"转过去、读一块"（机械盘约 10 毫秒）。

所以：

> **既然一次 IO 的价格是固定的，就应该让每一次 IO 尽量多带数据回来。** 16KB 一页，能装几十到几百条记录。

::figure page-io.svg | 页是读写的最小单位 | 磁盘按块读写，数据库一次读入整整一页；页内含几十到几百条记录

**这就是理解后面一切的钥匙**：**数据库里不存在"只读一行"的操作，只存在"读一页，然后在页里找那一行"。**

【类比】去图书馆取书，不是一次取一页纸，而是一次**搬回一箱**。所以"书架上怎么摆箱子（索引结构）、每箱装多少（扇出）"，决定了你要跑几趟。

**到这里你应该能回答**：为什么说"读一行"这个说法在数据库里其实不准确？

#### 1.3 由此得到唯一判据

【推导】**索引结构的设计目标 = 让定位一条记录所需的 IO 次数最少。**

因为一次 IO 的成本固定，**IO 次数就是总成本的唯一变量**——一切设计都在减少它。

### 2. 四个候选结构（先各自介绍，再比较）

比较之前必须先把每个结构自己讲清楚，否则"某某输在哪"是没有依据的。

#### 2.1 哈希表【事实】

- **是什么**：用哈希函数把键映射到桶，桶里放数据位置。
- **特点**：**等值查询 O(1)**——一次计算就定位，比任何树都快。
- **局限**：哈希把顺序打散了，**数据之间不再有大小关系**。所以不支持范围查询（`next_retry_time <= NOW()`）、不支持排序、不支持前缀匹配（`LIKE 'abc%'`）。

#### 2.2 红黑树（一种二叉搜索树）【事实】

- **是什么**：自平衡的**二叉**搜索树，保证树高是 O(log₂N)。
- **特点**：**每个节点最多 2 个孩子**——这是它的定义，不是实现选择。**所以树高由"2"决定，改不了。**
- **在内存里表现很好**：二叉比较快、实现成熟。"内存中的有序字典"几乎都用它（或跳表）。

#### 2.3 B 树【事实】

- **是什么**：**多路**平衡查找树。"多路"指一个节点可以有 M 个孩子（M 通常几十到几百），所以树高是 log_M(N)，比二叉矮得多。
- **特点**：**每个节点都同时存「键」和「数据」**（数据可以是指向行的指针，也可以是行本身）。
- **后果**：一个节点能放多少个键，被"数据也要占地方"限制住了。

#### 2.4 B+ 树【事实】

**B+ 树是 B 树的变体**，只改了两件事：

1. **非叶节点只存键，不存数据**（数据只出现在叶子层）；
2. **所有叶子用链表串起来**（InnoDB 里是双向链表）。

**这两个改动带来什么**，下一节用 IO 指标逐个算。

### 3. 逐个淘汰（统一指标：定位一行需要几次 IO）

::figure tree-height-compare.svg | 三种结构的树高与 IO 次数 | 统一指标下比较：红黑树 24 次、B 树 6 次、B+ 树 3 次

#### 3.1 哈希表：不是"更慢"，是"不能"【推导】

哈希只解决**等值**。而真实业务查询里范围条件几乎无处不在：`WHERE stat_date BETWEEN ? AND ?`、`ORDER BY updated_at DESC`、`status = ? AND next_retry_time <= NOW()`。

**关键不是性能差多少，而是这类查询在哈希索引上根本做不了**——只能退化成全表扫描。**这是能力缺失，不是速度问题。**

【取舍】所以哈希在 InnoDB 里只作为**内部优化**存在（自适应哈希索引，加速热点等值查询），不是用户可选的主索引类型。

#### 3.2 红黑树：树高由"2"决定【推导】

红黑树树高 ≈ log₂(N)。算一遍：

```
N ≈ 2000 万行
树高 ≈ log₂(2×10⁷) ≈ 24          （因为 2²⁴ ≈ 1678 万）
```

**为什么树高就等于 IO 次数**：每从一层下降到下一层，子节点**大概率在另一个页上**（节点分散存储），所以每次下降都要读一个新页 → **一次随机 IO**。

**所以最坏 24 次 IO**，对比 B+ 树的 3 次——**差 8 倍**。而且这 24 次几乎全是随机 IO；B+ 树那 3 次里前两层还可能命中内存缓存。

【取舍】但这不等于"红黑树差"——它有个隐含前提：**假设节点分散在不同页**。把整棵树放进内存，红黑树就够了（Redis 的 ZSet 用跳表正是这个道理）。

**准确的说法是：红黑树适合放内存，不适合做磁盘索引。**

#### 3.3 B 树：扇出被数据挤小了，而且范围查询要回溯【推导】

B 树的"多路"本来能大幅降低树高，但它输在两点：

**① 非叶节点存数据 → 扇出被挤小 → 树高降不下来**

算一遍（假设行数据 1KB）：

```
非叶节点每条记录 = 键 8B + 数据 1KB ≈ 1KB
16KB 一页能放 ≈ 16 条
扇出 = 16
树高 = log₁₆(2000 万) ≈ 6
```

而 B+ 树非叶只存「键 8B + 页号 6B = 14B」，一页放约 1170 条，扇出 1170，树高只有 3。**同样的数据量，B 树要多读 3 次 IO。**

**② 范围查询要在层间上下跳**

这一点更致命，也是"为什么需要叶子链表"的答案。

B 树的数据**分布在所有层**。要取一段连续区间的记录（`next_retry_time <= NOW()`），得按顺序**中序遍历**整棵树，而访问顺序是：

```
根 → 中层 → 根 → 中层 → 叶 → 中层 → 根 → …
```

**层级忽上忽下。** 每换一个节点就是换一页 → 新的 IO；而且**"上一个节点"和"下一个节点"在物理上并不相邻**，没法靠顺序读省下来。

::figure leaf-scan.svg | 范围查询的路径对比 | B 树层级忽上忽下要反复回溯；B+ 树下降到起点后沿叶子链表一直向右

**小结**：B 树淘汰在**①扇出小、树高多 3 层；②范围查询要跨层回溯**。两点都是硬伤。

#### 3.4 B+ 树：三个设计点，各解决一个问题【推导】

**① 非叶节点只存键 → 扇出变大 → 树变矮**

```
非叶节点每条记录 = 键 8B + 页号 6B = 14B
16KB 一页能放 ≈ 16384 / 14 ≈ 1170 条
扇出 = 1170
```

**扇出（fan-out）的定义**：一个节点平均指向的子节点数。它是树高的底盘：

```
树高 ≈ log_扇出(行数)
```

**扇出越大，树越矮；树越矮，IO 越少。** 1170 的扇出把 2000 万行的树高压到 3 层。

**② 数据只在叶子层 + 叶子双向链表 → 范围查询一次下降就够**

数据全在叶子层意味着：**物理顺序 = 逻辑顺序**。相邻叶子用指针直接相连，所以定位到区间起点后，**顺着链表向右扫即可，不需要回到根重新下降**（对比 3.3 的 B 树）。

**为什么是双向**【取舍】：范围查询本身只需要向右；但 `ORDER BY ... DESC` 这类反向扫描、以及部分优化器路径需要向左。双向的代价只是每个叶子多 6 字节，换来的是与扫描方向无关。

**③ 页大小固定并与磁盘块对齐 → 每一次 IO 都不浪费**

页是 16KB，正好是"一次 IO 能搬的量"。页内含几十上百条记录，**一次 IO 的固定成本被摊薄到这些记录上**。如果一次只能读一条记录，扇出再大也没意义——因为每次下降都要付全额 IO 成本。

**小结**：三个设计点不是三件孤立的事——**①解决"树高"，②解决"范围查询"，③解决"单次 IO 的利用率"**。它们合起来才让"3 次 IO 查 2000 万行"成立。

### 4. 量化验证（把结论算出来，而不是背下来）

```
根节点      1 页 × 1170 个键
第二层   1170 页 × 1170 个键  = 约 137 万个叶子页
叶子层  137 万页 × 约 16 行    ≈ 2000 万行
```

【推导】**查 2000 万行 = 3 次 IO**（根 → 第二层 → 叶子，定位到那一行所在的页，再在页内二分）。

记忆点：**三层 ≈ 2000 万行。**

**一个有用的推论**：几百万行和几千万行**都是 3 层**——所以在"表大了要不要加索引"这类问题里，树高通常不是关键变量，**扫描行数与回表次数才是**（连到 [[母题-M3-聚簇索引与回表]]）。

**到这里你应该能回答**：把主键从 8B 的 BIGINT 换成 36B 的 UUID，扇出和树高各会怎么变？

### 5. 边界与常见误解（不写这段最容易背成口诀）

| 常见说法 | 修正 |
|---|---|
| "页必须是 16KB" | 【取舍】它是在"一次 IO 效率"与"扇出不足会树高"之间选的。太大则一次读进大量当前用不到的数据，太小则扇出不够 |
| "B+ 树因为矮所以快" | 【推导】树矮只保证**定位到索引项**便宜。要取整行还要**回表**（二级索引场景），那才是大头 |
| "红黑树不适合数据库" | 【取舍】准确说法是**不适合做磁盘索引**。内存场景（Redis ZSet 用跳表、Java TreeMap 用红黑树）完全合理 |
| "B+ 树是唯一答案" | 【取舍】写多读少的场景走另一条路：**LSM 树**（LevelDB / RocksDB）把随机写变成顺序追加，代价是读可能多查几层、且需要 compaction |

## 二、自测

**Q1（计算）**：InnoDB 一页 16KB，非叶节点每条「键 + 页号」按 14B 算，扇出约 1170。如果换成 **36 字节的 UUID 作主键**，非叶节点每条记录变成多少字节？扇出约变成多少？

**A1**：非叶每条 = 键 36B + 页号 6B = **42B**；扇出 ≈ 16384 / 42 ≈ **390**，约为原来的三分之一。

**Q2（判读）**：接着 Q1——扇出从 1170 降到 390，**树高会不会变高？**

**A2**：**会，从 3 层变成 4 层。** 按本卡的口径（树高 = 层数，含根与叶子；扇出 f 的树在 h 层时叶子页数 = f^(h−1)）：

```text
需要覆盖 2000 万行，每叶子页 16 行 → 需要 2000万 / 16 = 125 万个叶子页

扇出 1170：
  3 层 → 1170² = 136.9 万页 → ×16 ≈ 2190 万行   ✓ 够（刚好）
扇出 390：
  3 层 →  390² =  15.2 万页 → ×16 ≈  243 万行   ✗ 不够
  4 层 →  390³ = 5932 万页 → ×16 ≈  9.5 亿行   ✓ 够
```

【结论】**扇出降到三分之一，树高就要多一层**——每次查询多一次随机 IO。

**所以用 UUID 当主键有两笔代价，两笔都要说**：

1. **树高 +1**：只影响主键索引本身（一次查询多 1 次 IO）
2. **更关键的是"体积"**：**主键会出现在每一个二级索引的叶子里**（36B 对 8B），于是**所有二级索引都变胖、每页能装的索引项变少、缓存命中率下降**——5 个二级索引就是 5 份复制品一起变胖。

**这才是"别用 UUID 当主键"的真实理由**：第一笔是一次性的 1 次 IO，第二笔是**全表所有索引的长期成本**。

**Q3（计算）**：一张只有 100 行的表，B+ 树树高是几层？

**A3**：**2 层**（根 + 1 个叶子页）。根页有 1170 个键，一个叶子页就装得下 100 行。**不可能是 1 层**——根节点也是页，而数据必须落在叶子层。

**这个推论的意义**：小表和大表的树高只差 1 到 2 层，**所以"表小所以快"不是因为树矮，而是因为扫描行数少、且整张表都在缓存里**。

**Q4（纠错）**：下面这段话哪里错了？

> "B+ 树因为每个节点只存键，所以树矮；红黑树因为节点里存了数据，所以树高。"

**A4**：**后半句错了，属于张冠李戴。**
"节点存数据导致树高"是 **B 树**的问题（见 3.3 ①）。**红黑树树高是因为它是二叉树、扇出只有 2**——它节点存不存数据与树高无关（即使不存数据，扇出还是 2，树高还是约 24）。

正确说法：**B 树输在"非叶存数据挤小了扇出"，红黑树输在"扇出天生只有 2"。**

**Q5（纠错）**：下面这段话哪里错了？

> "B 树的叶子节点也存数据，所以它的范围查询比 B+ 树慢。"

**A5**：**错在归因。** B 树范围查询慢，**不是因为"叶子存数据"，而是因为数据分布在所有层，中序遍历要在层间上下跳**（见 3.3 ②）。而且 B 树是**所有**节点都存数据，不只是叶子。

正确说法：**B+ 树的叶子之间用链表相连、数据只在叶子层，所以定位到起点后可以顺序向右扫；B 树没有这条链，相邻记录可能在不同层，只能靠跨层遍历。**

## 三、面试输出（学完再看）

**一句话结论**：B+ 树是**为磁盘 IO 次数最少**而设计的——非叶节点只存键让扇出达到约 1170、树高压到 3 层；叶子双向链表让范围查询一次下降后顺序扫；页与磁盘块对齐让每次 IO 都不浪费。于是查 2000 万行只要 3 次 IO，而红黑树要约 24 次。

**恢复关键词**：IO 次数是唯一指标 / 页与扇出 / 非叶只存键 / 叶子双向链表 / 树高 = log 扇出 / 三次 IO 两千万行 / 回表另算

**核心不变量 / 主线**：
磁盘随机 IO 是瓶颈（比内存慢约 5 个数量级），所以索引结构的唯一目标是**把定位一条记录所需的 IO 次数，从「行数」降到「树高」**。

**完整回答骨架**：约束（IO 次数是唯一指标）→ 四个候选各是什么 → 逐个淘汰（哈希不能范围 / 红黑树扇出 2 / B 树扇出小且要回溯）→ B+ 树三个设计点 → 量化（三层 2000 万行）→ 边界（回表另算、LSM 是另一条路）

**完整回答（口述稿）**：
判据只有一个：磁盘随机读比内存随机访问慢约 5 个数量级（机械盘约 10 毫秒对内存约 100 纳秒），而一次 IO 读的是一整页（InnoDB 默认 16KB）、成本几乎不随读多少变化，所以评价索引结构只看「定位一行要几次 IO」，也就是树高。

四个候选逐个淘汰：哈希表只能等值、做不了范围；红黑树是二叉、扇出 2，2000 万行树高约 24 层、约 24 次 IO；B 树非叶也存数据，扇出被挤小、范围查询还要回溯父节点；B+ 树非叶只存键，扇出约 1170，三层就能覆盖约 2000 万行，只要 3 次 IO。它三个设计点各解决一件事：非叶只存键让扇出最大、树最矮；叶子双向链表让范围查询一次下降后顺序扫；页与磁盘块对齐让每次 IO 都不浪费。

边界：树矮只保证定位索引项便宜，二级索引查到的是主键，取整行还要回表，扫 1000 行时回表才是大头；写多读少的场景走另一条路——LSM 树（RocksDB / LevelDB）。
**分层要点**：
- **结论**：B+ 树是为「磁盘 IO 次数最少」设计的；唯一判据是「定位一行要几次 IO」，不是比较次数。
- **推导链**：IO 比内存慢约 5 个数量级 → 一次 IO 读一页、成本与数据量无关 → 判据落在树高 → 哈希不能范围 / 红黑树扇出 2 / B 树扇出被数据挤小且范围要回溯 → B+ 树非叶只存键。
- **量化**：页 16KB、扇出约 1170 → 三层约 2000 万行 = 3 次 IO；红黑树同样数据约 24 层 ≈ 24 次 IO。
- **边界与常见误解**：树矮 ≠ 快（回表才是大头）；红黑树只是「不适合做磁盘索引」，内存场景（Redis 跳表、Java 红黑树）完全合理；写多读少走 LSM，代价是读要多查几层 + 需要 compaction。
**追问**（先说后看）

1. **既然 B+ 树这么矮，为什么还要尽量走覆盖索引？** —— 树高决定的是**定位索引项**的成本；二级索引查到的是主键值，要取整行还得**回表**再查一次聚簇索引。**树高只有 3 层，可命中的每一行都要多付一次回表 IO**——扫 1000 行时，回表才是大头（连到 [[母题-M3-聚簇索引与回表]]）。
2. **叶子的链表为什么做成双向的？** —— 范围查询本身只需向右；但 `ORDER BY ... DESC` 的反向扫描与部分优化器路径需要向左。双向的代价只是每个叶子多 6 字节，换来的是与扫描方向无关。
3. **为什么 InnoDB 的页是 16KB？** —— 它是"一次 IO 的效率"与"扇出/浪费"之间的折中。SSD 时代也可以配更大（如 32KB），但页越大，一次读进当前用不上的数据也越多。

**同类变体**

- MongoDB 用什么索引结构，为什么？（读多写少 → 与 B 树同族的取向）
- LSM 树（RocksDB / LevelDB）为什么反着来？（写优化：把随机写变成顺序追加，代价是读可能多查几层）
- 为什么不用跳表（SkipList）做磁盘索引？（跳表的跳转粒度不固定，一次跳转可能跨多个页，无法保证"一次 IO 一跳"）
