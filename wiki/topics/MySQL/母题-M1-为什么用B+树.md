# 母题 M1 · 为什么 InnoDB 用 B+ 树

> **模块**：MySQL / 索引
> **所属主线**：一 · 索引（怎么让查询不用扫全表）
> **关联母题**：[[母题-M3-聚簇索引与回表]]
> **素材来源**：`raw/后端视角复盘_MySQL` 第一条主线；B+ 树结构原理为通用知识补充（**待你核对**）

**题目**：InnoDB 的索引底层是 B+ 树。为什么是 B+ 树，而不是 B 树、红黑树或哈希表？

**母题**：数据库索引为什么必须选择 B+ 树？这个选择的约束条件是什么？

**为什么重要**：这是索引所有问题的地基。答不出这一层，后面「为什么最左前缀」「为什么回表慢」「为什么索引失效」全是背结论；答得出，那些结论都能自己推出来。

**一句话结论**：B+ 树是**为磁盘 IO 次数最少**而设计的——非叶节点只存键让树变矮，叶子有序链表让范围查询不用回溯，于是查两千万行也只要 3 次 IO。

**恢复关键词**：IO 次数 / 矮胖 / 非叶只存键 / 叶子链表 / 扇出

**核心不变量 / 主线**：
磁盘随机 IO 是瓶颈（一次约 10ms，内存访问是纳秒级），所以索引结构的唯一目标是**把定位一条记录所需的 IO 次数，从「行数」降到「树高」**。

**完整回答骨架**：约束（IO 是瓶颈）→ 三个设计点（非叶只存键 / 数据全在叶子 / 页与磁盘块对齐）→ 量化（三层 ≈ 2000 万行 ≈ 3 次 IO）→ 对比为什么其他结构不行

---

## 原理分解

### 一、约束：瓶颈不是 CPU，是磁盘 IO

数据库的数据量远超内存，绝大多数查询要读磁盘。一次随机 IO 的代价比一次内存访问高 5–6 个数量级。

所以问题不是「怎么让比较更快」，而是「**怎么让 IO 次数更少**」。任何索引结构的评价标准都是这一条。

### 二、B+ 树的三个设计点

**① 非叶节点只存键，不存数据**
非叶节点每条记录只有「键（8B）+ 页号（6B）」≈ 14B，16KB 的页能放下约 1170 个键。
→ 一个节点指向 1170 个子节点，这叫**扇出大**；扇出越大，树越矮。

**② 所有真实数据都在叶子层，叶子之间用双向链表串起来**
范围查询（`next_retry_time <= NOW()`）定位到起点后，顺着链表向右扫就行，**不需要回到根节点重新下降**。

**③ 页大小固定（16KB），与磁盘块对齐**
一次 IO 正好读一整页，页内含几十上百条记录，摊薄了单次 IO 的成本。

### 三、量化：三层 B+ 树能存多少

```
根节点       1 页 × 1170 个键
第二层    1170 页 × 1170 个键  = 约 137 万个叶子页
叶子层  137 万页 × 约 16 行    ≈ 2000 万行
```

**查 2000 万行只需要 3 次 IO**（除非走索引扫了很多行，或频繁回表）。
记忆点：**三层 ≈ 2000 万行**。这也解释了为什么几百万行的表只有三层、加不加索引高度感受不到差别。

### 四、为什么不是别的结构

| 结构 | 致命问题 |
|---|---|
| **B 树** | 非叶节点也存数据 → 同样一页能放的键少得多 → 扇出小、树更高；范围查询要中序遍历回溯，不能顺链表走 |
| **红黑树 / AVL** | 二叉树，扇出只有 2。几百万行高度 20+ → 20+ 次随机 IO，完全不可接受 |
| **哈希表** | 等值查询 O(1) 很快，但**不支持范围、排序、最左前缀**——而真实业务查询几乎都是范围的 |

一句话：B 树败在扇出，红黑树败在高度，哈希败在不支持范围。

## 二、扩展：类似题与两层追问

**同类变体**

- MySQL 的索引是 B+ 树，那 MongoDB 呢？（考察点：读多写少和写多读少的选择差异）
- LSM 树（RocksDB / LevelDB）为什么反着来？（写优化路线：把随机写变成顺序写）
- 为什么 InnoDB 页大小是 16KB？（与磁盘块、与一次 IO 的平衡）

**两层追问**（能答完才算通过）

1. **既然 B+ 树这么矮，为什么还要尽量走覆盖索引？** —— 树高决定定位成本，但**回表是额外的 IO**。B+ 树只解决「找到索引项」，回表要再查一次聚簇索引，那才是大头。
2. **为什么 B+ 树的叶子要用双向链表，单向不行？** —— 范围查询通常只需要向右扫（单向够用），但**反向扫描**（`ORDER BY ... DESC`）和某些优化器路径需要向左，双向是通用选择。
