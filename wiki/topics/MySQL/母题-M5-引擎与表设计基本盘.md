# 母题 M5 · 引擎与表设计基本盘

> **模块**：MySQL / 引擎与表设计
> **所属主线**：一 · 索引与表设计（怎么让查询不用扫全表，表怎么建才不埋雷）
> **关联母题**：[[母题-M1-为什么用B+树]] · [[母题-M3-聚簇索引与回表]]
> **素材来源**：`raw/Mysql面试题-2026-09-07T004734+0800.md` 第 1 节「基础面试题」（1.2–1.5、1.7、1.11）

**题目**：让你从零设计一张「任务表」——几十亿行、读写混合、以后还要按状态和时间捞任务。你会怎么选引擎、主键和字段类型？为什么不用 MyISAM？

**母题**：MyISAM 和 InnoDB 差在哪？建表时主键、varchar/char、DATETIME/TIMESTAMP 该怎么选？

**为什么重要**：这是**最高频、也最容易被轻视**的一类题。它不难，但答"知道"和答"选过"是两回事——面试官问它是为了确认：你建的表现在会不会埋雷（主键用 UUID 导致页分裂、时间字段选了 TIMESTAMP 结果 2038 年溢出）。**而且它是后面所有索引题的前置**：不懂 InnoDB 是索引组织表，就讲不清回表。

**一句话结论**：选 InnoDB 是因为它**支持事务、行级锁和崩溃恢复**，这是默认引擎的根本原因；表设计的三条硬规则是——**主键用自增（保证顺序写、避免页分裂）**、**长度不定用 varchar、长度固定用 char**、**要自动更新和时区语义用 TIMESTAMP，要大范围日期用 DATETIME**。

**恢复关键词**：事务 / 表锁 vs 行锁 / 非聚集索引 vs 索引组织表 / 自增主键防页分裂 / 变长 + 长度字节 / 4 字节受时区

**核心不变量 / 主线**：
**表设计不是审美问题，是"写入路径顺不顺、存储紧不紧凑、以后改不改得动"的问题。** 所有具体选择（引擎、主键、字段类型）都服务这三件事。

**完整回答骨架**：引擎对比（三条硬差异）→ 为什么 InnoDB 成默认 → 主键为什么必须自增（页分裂）→ varchar vs char → DATETIME vs TIMESTAMP → 约束与范式（反范式的条件）

## 原理分解

### 一、MyISAM vs InnoDB：差异只有三条硬的

| 维度 | MyISAM | InnoDB |
|---|---|---|
| 事务 | **不支持** | 支持（ACID） |
| 锁粒度 | **表级锁**（写锁全表） | 行级锁 + MVCC |
| 崩溃恢复 | 不支持（靠 repair） | **redo/undo 保证 crash-safe** |
| 索引结构 | 非聚集索引：索引文件与数据文件分离，叶子存**物理地址** | 索引组织表：主键即数据，二级索引叶子存**主键值**（要回表） |
| 外键 | 不支持 | 支持 |

**一条判断**：写并发一上来，MyISAM 的表级锁会让写请求排队；加上没有事务和崩溃恢复，它只适合**读多写少、且可以重建的数据**（日志、统计中间表）。**业务表一律 InnoDB。**

**顺带一个高频追问**：「MyISAM 和 InnoDB 的 B+ 树实现差在哪？」答上表第四行——MyISAM 叶子存**地址**（还要再去数据文件捞一次），InnoDB 主键叶子存**整行**、二级索引叶子存**主键**。这一条正是 [[母题-M3-聚簇索引与回表]] 的起点。

### 二、主键为什么强烈建议自增（这条最常被追问）

B+ 树的叶子按主键有序。所以：

- **自增主键**：新记录永远追加到最右边 → **顺序写**；写满就开新页，对已有数据几乎无影响。
- **随机主键（UUID / 随机字符串）**：新记录要插到中间 → 为保持有序得**搬数据、触发页分裂**；分裂还会让页填充率下降（碎片化），索引变得不紧凑，后续查询也变慢。

**再加一条**：二级索引的叶子存主键值，**主键越长，所有二级索引越大**。UUID 是 36 字节字符串，自增 BIGINT 是 8 字节——**每建一个二级索引都在为主键长度重复付费**。

> 什么时候可以不用自增？当业务**没有天然自增键**、且需要**分布式唯一**时（比如分库分表要全局唯一 ID），用雪花算法这类**趋势递增**的 ID——它保住了「大致有序」，比纯随机的 UUID 好得多。这是权衡，不是破例。

### 三、varchar vs char

| | char | varchar |
|---|---|---|
| 长度 | **定长**，不足用空格补齐 | **变长**，按实际长度分配 |
| 额外开销 | 无 | **1–2 字节记录实际长度** |
| 适用 | 长度固定：手机号、MD5(32)、性别、状态码 | 长度不确定：用户名、地址、备注 |

**判断标准只有一句**：长度是否真的固定。定长用 char 省了长度字节、比较也略快；但只要长度不确定，char 就会浪费空间（`char(10)` 存 `'a'` 也占 10 个字符）。

**一个坑**：char 尾部会补空格，比较时可能表现出 `'a'` 与 `'a '` 的差异——**别用 char 存会被拼接或比较的值**。

### 四、DATETIME vs TIMESTAMP

| | DATETIME | TIMESTAMP |
|---|---|---|
| 存什么 | 字面的日期时间 | Unix 时间戳（秒） |
| 时区 | **与时区无关**（存什么就是什么） | **受时区影响**（按会话时区换算） |
| 字节 | 8 | 4 |
| 范围 | 1000–9999 年 | 1970–**2038** |
| 默认值 | NULL | 可 `CURRENT_TIMESTAMP`，支持自动更新 |

**怎么选**：需要**跨时区**或**自动记录创建/更新时间** → TIMESTAMP；需要**大范围日期**（生日、合同到期、业务上的远期时间）→ DATETIME。

**面试安全点**：TIMESTAMP 有 **2038 问题**（4 字节存秒，2038-01-19 溢出）。被问到"为什么不用 TIMESTAMP 存所有时间"，这就是答案。

### 五、约束、范式与三条删除语句

- **常用约束**：主键（唯一且非空）、唯一（唯一但可有 NULL）、非空、默认值、外键、CHECK。**主键和唯一的区别就是「是否允许 NULL」**。
- **三范式**：1NF 列不可再分；2NF 非主键列完全依赖整个主键（针对联合主键）；3NF 非主键列之间不能有传递依赖。**反范式的唯一理由是可测量的读性能**——比如事实表冗余园区快照以避免一次 JOIN。**先有执行计划，再谈反范式。**

  | 语句 | 类型 | 能回滚 | 删什么 | 速度 |
  |---|---|---|---|---|
  | `DELETE` | DML | **可以** | 表结构留着，可带 WHERE 删部分行 | 慢（逐行） |
  | `TRUNCATE` | DDL | 不可以 | 清空全部行，结构保留 | 快（重建） |
  | `DROP` | DDL | 不可以 | **表结构、数据、索引、权限全删** | 最快 |

## 二、扩展：类似题与追问

**类似题**

1. 「MySQL 支持哪些存储引擎？」——InnoDB（默认）、MyISAM、Memory（内存表，重启即失，适合临时表）、Archive（高压缩，只插不查）。**考官想听的是「为什么默认是 InnoDB」**，不是背名单。
2. 「建表时字段类型怎么选？」——够用就好：能用 INT 不用 BIGINT，能用定长不用变长；**别用字符串存时间，也别用浮点存金额**（用 DECIMAL）。
3. 「InnoDB 和 MyISAM 谁快？」——**读多写少且无事务需求时 MyISAM 的表扫描可能更快**；但只要涉及并发写、事务、恢复，InnoDB 全面胜出。承认这一点比硬吹 InnoDB 更显水平。

**追问链**

- 追问一层：**「页分裂到底损失什么？」**——① 分裂是同步的写操作，直接抬高写入延迟；② 分裂后两页各约半满，索引不紧凑，同样的数据占更多页，范围扫描要读更多页；③ 顺序写变成随机写，失去 B+ 树最大的性能来源。
- 追问二层：**「那用趋势递增的自增 ID（雪花）不就好了？」**——可以，但注意两点：① 趋势递增不是严格递增，跨节点时钟回拨仍可能插到中间，只是概率远小于 UUID；② 全局唯一 ID 通常位数更长（64 位 LONG），二级索引体积会变大，要接受这个代价。
