**题目**：① 产品要给开心消消乐每个关卡加一个排行榜（DAU 2000 万），让玩家看到自己排名——结合 AI 做个设计。② 高并发扣体力 / 扣库存怎么防超卖？

**为什么重要**：**这是"场景设计题"的样板卡**——它考的不是知识点，而是**"拿到模糊需求后的章法"**（澄清 → 拆解 → 方案 → 风险 → 指标）。**9.9 那次的失败链是：假设错（以为消消乐是单机）→ 被否（提分享）→ 澄清不系统 → 长时间空白 → 没有成型方案**。**这张卡就是修复：把"排行榜"变成一道可以闭卷重放的母题**——**它同时覆盖场景设计方法论 + 技术选型 + 高并发扣减三个考点，性价比极高。**

## 一、教材

### 1. 前提：场景题的第一动作是澄清，不是给方案

【推导】**9.9 那次丢分的一半在"没问够"**——另一半才是技术。**技术选型（MySQL vs Redis）反而是这张卡里最容易的部分。**

**六步章法（先背这个，再背技术）**：

```text
① 澄清（开口前先问 10 秒）：排名依据？榜单范围（全服/好友/Top N）？更新频率？
                          展示字段？历史榜/周榜？防作弊？规模？
② 拆解：规模估算（2000 万 DAU × 千级关卡 → 不可能全量存排名）
③ 方案：存储 + 读写路径 + 数据结构
④ 风险：热点 key、写入尖峰、内存、作弊
⑤ 指标：写入 QPS、查榜 P99、内存占用、裁剪耗时
⑥ 降级：Redis 挂了怎么办
```

【事实】**9.9 的澄清对照**（复盘里的 ✅/❌ 清单）：**问了排名依据、展示字段、规模；没问榜单范围、更新频率、历史榜、防作弊**——**把这张清单背下来，下次第一分钟就不会空白。**

**到这里你应该能回答**：为什么"澄清"这一步在场景题里比"给出漂亮方案"更能得分？

### 2. 排行榜选型：为什么必须是 Redis ZSet

| | Redis ZSet | MySQL |
|---|---|---|
| 排名查询 | `ZREVRANK` **O(logN)** | **`COUNT(*) WHERE score > ?`，O(N)**（或加冗余排名字段，但更新代价高） |
| 榜单读取 | `ZREVRANGE` 直接取 Top N | `ORDER BY score DESC LIMIT N`（索引可以，但更新热点行代价高） |
| 更新 | `ZADD` **O(logN)** | 高频 `UPDATE` 同一行 → **行锁热点**（[[母题-M10-锁与死锁]]） |
| 底层 | **跳表 + 哈希表**（既能按 member 查 score，又能按 score 范围查） | B+ 树 |

#### 2.1 把复杂度差算出来【推导】

```text
某热门关卡 200 万玩家上榜，查询一个中位玩家的名次

MySQL：SELECT COUNT(*) FROM scores WHERE level_id=? AND score > ?
       要数出所有比它高的行 → 约 100 万行索引扫描

Redis：ZREVRANK
       跳表 O(log N)，N = 200 万 → log₂(200万) ≈ 21 次比较

量级比 ≈ 100万 ÷ 21 ≈ 5 万倍
```

【推论】**这不是"Redis 快一点"，是数量级的差别**——而且它**随榜单长度增长**：MySQL 是 O(N)，Redis 是 O(logN)。**所以榜单越大，差距越大。**

#### 2.2 复合分数：把两个排序维度压进一个数字【事实 + 推导】

**需求**：同分时，**先通关的排前面**。

```text
score = 分数 × 倍率 + (MAX_TS − 通关时间戳)
        分数越高 → 值越大
        同分时，时间越早（MAX_TS − ts 越大）→ 值越大
```

【推论】**这样做避免了两级排序**（先按分数排、同分再按时间排）——**一次比较就定出唯一顺序**。

::figure composite-score.svg | 复合分数的位数预算：为什么 10¹⁰ 这个位宽会踩到精度上限 | 分数部分在高位、时间戳差在低位；但 Redis 的 score 是双精度浮点，只有 2⁵³ 以内可精确表示——倍率取 10¹⁰ 时分数上限必须小于约 90 万

#### 2.3 复合分数有一个"位数预算"【推导】

【事实】**Redis 的 score 是 IEEE 754 双精度浮点，只有 2⁵³ 以内的整数能被精确表示。**

```text
2⁵³ = 9,007,199,254,740,992 ≈ 9.007 × 10¹⁵

用 10¹⁰ 作倍率时：
  分数上限 × 10¹⁰ 必须 < 2⁵³
  → 分数上限 < 约 90 万

若分数上限取 100 万：
  100万 × 10¹⁰ = 10¹⁶ > 9.007 × 10¹⁵    ✗ 越界
```

【推论】**越界的后果是：低位（时间戳差）被抹掉 → 同分玩家的先后变得不确定，而且不报错。**

【取舍】**更稳的做法：倍率按"时间窗"定，而不是按时间戳原值**：

```text
时间差不超过一年（约 3.15 × 10⁷）→ 倍率取 10⁸ 就够
分数上限 100 万时：100万 × 10⁸ = 10¹⁴  ✓ 安全（离 9×10¹⁵ 还有 90 倍余量）
```

【推论】**这类"看着能算、其实越界且不报错"的坑，正是面试官区分"用过"和"看过"的地方。**

**到这里你应该能回答**：为什么复合分数的倍率不能随便取大？

### 3. 2000 万 DAU 下的工程问题（答到这层才像服务端）

```text
① 热点 key：热门关卡集中在少数 key → 按"关卡 + 区服/分片"拆，或本地缓存 + 异步刷新
② 写入削峰：通关上报是尖峰 → 消息队列异步落榜，前端先返回"计算中"
③ 名次不必实时精确：非头部玩家用"分数段桶计数"近似名次，精确 ZREVRANK 留给头部
④ 只存 Top N：每关只保留 Top N（ZREMRANGEBYRANK 定期裁剪）——内存控制的关键
   玩家个人最佳与名次另存（DB），榜外玩家看"自己的最佳 + 击败百分比"
⑤ 持久化：Redis 只是热层，冷数据定时落 DB；Redis 挂了可从 DB 重建
⑥ 活动榜：带过期时间的 key（EXPIRE），活动结束自动清理
```

#### 3.1 "只存 Top N"能省多少内存【推导】

```text
假设 2000 万 DAU、人均上榜 5 个关卡 → 1 亿条记录
每条 ZSet 成员 ≈ member(玩家ID 16B) + score(8B)，加跳表指针开销按 2 倍估 ≈ 50B

全量存：1 亿 × 50B = 5 GB
只存每关 Top 1000（假设 1000 个关卡）：
  1000 × 1000 = 100 万条 × 50B = 50 MB

降到 1/100
```

【结论】**"只存 Top N"是内存控制的关键手段，量级上直接差 100 倍。**

#### 3.2 "名次近似"是这一题的亮点【取舍】

**2000 万 DAU 下，大多数玩家的名次并不需要精确到个位**（"你超过了 97% 的玩家"）。

【推论】**这是把 O(logN) 的精确查询留给头部、用 O(1) 的近似服务长尾的取舍。** **"花更少的代价满足绝大多数人的真实需求"是这类题的通用解法**，值得单独背。

### 4. 游戏特性（乐元素面试官最想听的）

【事实】

- **防作弊**：**消消乐是弱联网玩法，客户端上报的分数必须校验**——步数下限、最短通关时长、关键操作日志回放；**异常分数进人工审核队列，不直接入榜**
- **弱联网容错**：离线通关本地缓存，联网后补报，**用"玩家 ID + 关卡 + 时间戳"做幂等，避免重复提交刷榜**（**这就是 [[母题-P19-唯一约束与UPSERT]] 的幂等键思想在游戏场景的落点**）
- **活动榜时效**：`EXPIRE` 自动清理

【事实】**"防作弊没提"是 9.9 那次被明确点名的缺口**——**游戏公司的场景题里这是必答项**。

---

### 5. 防超卖三条路

#### 5.1 ① 数据库原子扣减（最简单、强一致）【事实】

```sql
UPDATE stock SET num = num - 1
WHERE id = :id AND num > 0;
-- 影响行数 = 1 → 扣成功；0 → 已售罄
```

【推导】**为什么能防超卖**：**判断和写入在一条语句里原子完成**——**不存在"查到还剩 1，两个人都扣"的窗口**。

【推论】**这和 [[母题-M16-乐观锁与悲观锁]] 的条件更新、[[母题-P18-乐观并发控制]] 是同一个原理**：**把判断下推到数据库的原子操作里**，而不是在应用层先查后写。

**代价**：**热点行锁竞争**（同一行高频更新会排队，[[母题-M10-锁与死锁]]）。

#### 5.2 ② 乐观锁（version）【事实】

语义同上，多一个 version 字段（[[母题-M16-乐观锁与悲观锁]]）；**适合"扣减前还要做别的判断"的场景**。

#### 5.3 ③ Redis 预扣 + 异步落库（高并发削峰）【事实】

```text
请求 → Redis DECR（原子）→ 扣成功才进队列 → 异步落 DB
                ↓ 扣成负数 → 回滚/拒绝
```

**代价**：**最终一致**（Redis 与 DB 有窗口）、**要处理重复消费与对账**（[[母题-P19-唯一约束与UPSERT]] 的幂等键 + 唯一约束兜底）。

【取舍】**判据**：**强一致（钱）→ 数据库原子更新；高并发（秒杀、体力）→ Redis 前置 + DB 兜底。**

---

### 6. 指标与降级【事实】

- **指标**：写入 QPS、查榜 P99、Redis 内存占用、裁剪任务耗时、**超卖告警（库存对账）**
- **降级**：**Redis 不可用时返回 DB 快照或"榜单维护中"，绝不让排行榜拖垮主玩法**

【推论】**"排行榜挂了不能影响游戏本体"是这一题的底线判断**——**依赖服务的可用性必须低于主链路**，这条原则可以迁移到任何"附加功能"上。

### 7. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "排行榜用 MySQL 加个索引就行" | **数量级不对**。MySQL 算名次要 `COUNT(*) WHERE score > ?`，**O(N)**（200 万榜单要数 100 万行）；ZSet 的 `ZREVRANK` 是 **O(logN)**（约 21 次比较）——**差约 5 万倍，且榜单越大差距越大** |
| "复合分数的倍率取大一点更保险" | **取大了会越界**。Redis 的 score 是双精度浮点，**只有 2⁵³ 以内可精确表示**；倍率取 10¹⁰ 时**分数上限必须小于约 90 万**，否则低位被抹掉、**同分排序错乱且不报错** |
| "客户端上报的分数直接入榜就行" | **漏了防作弊**，而这是游戏公司场景题的必答项。弱联网玩法客户端可被篡改，**必须校验（步数下限 / 最短通关时长 / 操作日志回放），异常分数进人工审核** |
| "先查库存再扣，加个事务就行" | **先查后写在并发下必然有窗口**——除非把判断下推进 `WHERE`（`UPDATE ... WHERE num > 0`）或加锁把窗口关掉。**"查到还剩 1，两个人都扣"就是这么发生的** |
| "排行榜要精确到个位" | **不必要**。2000 万 DAU 下大多数玩家只需要"你超过了 97% 的玩家"。**用近似服务长尾、把精确留给头部**，是这道题最值钱的取舍 |
| "Redis 挂了就等它起来" | **要有降级路径**：从 DB 重建（前提是冷数据定时落库）+ 降级为"榜单维护中"。**附加功能不能拖垮主玩法** |
| "同分排序不重要" | **它是这类题的必答细节**，而且复合分数有个**位数预算**的坑（见上）。**答得出这一层，和只答"用 ZSet"是两个档次** |

【取舍】读成一句话：**排行榜的答案是"把计算内建进数据结构"（ZSet 的排名是结构自带的，不是查出来的）；防超卖的答案是"把判断下推进原子操作"——两者是同一条原理的两个应用。**

## 二、自测

**Q1（计算）**：某热门关卡有 **200 万**玩家上榜，要查询一个**中位**玩家的名次。

问：**MySQL 和 Redis 分别要多少次操作？差多少倍？**榜单变成 2000 万时，差距会怎么变？

**A1**：

```text
MySQL：SELECT COUNT(*) FROM scores WHERE level_id=? AND score > ?
  中位玩家 → 要数出约 100 万行比它高的记录
  = 约 100 万次索引扫描            （O(N)）

Redis：ZREVRANK
  跳表 O(log N)，N = 200 万
  log₂(200 万) ≈ 21 次比较

倍率 ≈ 100万 ÷ 21 ≈ 5 万倍
```

【结论】**MySQL 是 O(N)，Redis 是 O(logN)**——所以榜单越长，差距越大：

| 榜单长度 | MySQL | Redis | 倍数 |
|---|---|---|---|
| 200 万 | 100 万次 | 21 次 | 约 5 万倍 |
| 2000 万 | 1000 万次 | 约 24 次 | 约 42 万倍 |

【补充】MySQL 也可以"加冗余排名字段"把读变成 O(logN)，但**每写一次分数就要更新所有受影响的名次**（写放大）——**只是把代价从读搬到写，没有消除。**

**Q2（计算）**：假设 2000 万 DAU、人均上榜 5 个关卡，每条 ZSet 成员开销约 **50 字节**（玩家 ID + score + 跳表指针）。

问：**全量存要多少内存？只存每关 Top 1000（假设 1000 个关卡）呢？**

**A2**：

```text
全量存：
  记录数 = 2000万 × 5 = 1 亿条
  内存 = 1亿 × 50B = 5,000,000,000 B ≈ 5 GB

只存 Top 1000：
  记录数 = 1000 关卡 × 1000 = 100 万条
  内存 = 100万 × 50B = 50,000,000 B ≈ 50 MB

降到 1/100
```

【结论】**"只存 Top N"不是优化技巧，是内存量级的分水岭**——5 GB 对 50 MB，差 100 倍。

【补充】代价是**榜外玩家看不到自己的名次**。解法：**玩家个人最佳与名次另存 DB**，榜外玩家看"自己的最佳 + 击败百分比"——**这就是第 3 节"名次近似"的落地方式。**

**Q3（计算）**：排行榜用复合分数 `score = 分数 × 10¹⁰ + (MAX_TS − 通关时间戳)`。

问：**分数上限是多少时才安全？**如果分数上限是 100 万，会发生什么？给出一个更安全的倍率。

**A3**：

```text
Redis 的 score 是 IEEE 754 双精度浮点
能精确表示的整数上限 = 2⁵³ = 9,007,199,254,740,992 ≈ 9.007 × 10¹⁵

约束：分数上限 × 10¹⁰ < 2⁵³
  → 分数上限 < 2⁵³ ÷ 10¹⁰ ≈ 900,719
  → 【约 90 万】
```

**分数上限取 100 万时**：

```text
100万 × 10¹⁰ = 10¹⁶ > 9.007 × 10¹⁵    ✗ 越界
```

【后果】**低位（时间戳差）被抹掉 → 同分玩家的先后变得不确定，而且不报错**——你会得到一个"看起来正常、偶尔顺序不对"的榜单。

【更安全的做法】**倍率按"时间窗"定，而不是按时间戳原值**：

```text
时间差不超过一年 ≈ 3.15 × 10⁷ → 倍率取 10⁸ 就够
分数上限 100 万 × 10⁸ = 10¹⁴   ✓ 距 2⁵³ 还有约 90 倍余量
```

【推论】**"看着能算、其实越界且不报错"是这类题目最好的加分点**——面试里主动说出这个约束，比背出公式更能证明你真的用过。

**Q4（纠错）**：下面这段话哪里不准确？

> "排行榜直接建在 MySQL 里就行，给 score 加个索引，查询很快的。"

**A4**：三处问题。

1. **算名次不是"加索引"能解决的**：`COUNT(*) WHERE score > ?` **需要数出所有比它高的行**，加索引也只能让这个计数变成索引扫描——**复杂度还是 O(N)**（Q1 里 200 万榜单要数 100 万行）。
2. **高频更新的热点行锁竞争**：热门关卡的分数集中在同一批行上，`UPDATE` 会**排队等锁**（[[母题-M10-锁与死锁]]）。
3. **"榜单读取"和"名次查询"是两个不同的操作**：`ORDER BY score DESC LIMIT N` 加索引确实能拿到 Top N（这是索引擅长的范围扫描），**但"我排第几"这个高频操作才是 MySQL 的短板**。

【准确说法】"**排行榜要的是"按 score 有序"这个结构本身**——ZSet 用跳表把这个顺序内建进去，`ZREVRANK` 是 O(logN)、`ZADD` 也是 O(logN)。**MySQL 只能把这个顺序"查出来"，每次查都是 O(N)。**"

**Q5（纠错）**：下面这段话哪里不准确？

> "玩家通关后客户端上报分数，服务端直接写进排行榜，简单可靠。"

**A5**：**错在把客户端上报当成可信数据**——这在游戏公司是**明确的必答缺口**（9.9 那次被点名）。

1. **消消乐是弱联网玩法，客户端可被篡改**（改分数、加速、改包、重放请求）。**直接入榜等于把排行榜的公信力交给客户端。**
2. **必须做服务端校验**：**步数下限、最短通关时长、关键操作日志回放**；**异常分数进人工审核队列，不直接入榜**。
3. **还要防重复提交刷榜**：弱联网下会补报，**用"玩家 ID + 关卡 + 时间戳"做幂等键**（[[母题-P19-唯一约束与UPSERT]] 的思想），否则同一次通关能被重放多次刷分。

【准确说法】"**客户端上报的数据一律当"不可信输入"处理**：先校验合理性，再幂等去重，异常进审核队列。**"排行榜的公信力"是这类产品的核心资产**——技术上多做一步，产品上少一次事故。"

## 三、面试输出（学完再看）

**一句话结论**：**场景题的第一动作是澄清**（六步：澄清 → 拆解 → 方案 → 风险 → 指标 → 降级）——9.9 那次丢分的一半在"没问够"（榜单范围、更新频率、防作弊全没问）。技术上**排行榜用 Redis ZSet**：跳表把"按 score 有序"内建进结构，`ZREVRANK` / `ZADD` 都是 **O(logN)**；MySQL 算名次要 `COUNT(*) WHERE score > ?`，**O(N)**（200 万榜单要数 100 万行，**差约 5 万倍**）。**同分先到者优先靠复合分数** `分数 × 倍率 + (MAX_TS − 通关时间戳)`——注意**位数预算**：Redis 的 score 是双精度浮点，**2⁵³ 以内的整数才精确**，倍率取 10¹⁰ 时分数上限必须小于约 90 万，否则同分排序会静默错乱。规模上做三件事：**只存 Top N**（5 GB → 50 MB）、**名次近似**（把 O(logN) 留给头部）、**Redis 前置 + DB 兜底**。**防超卖的本质是"把判断下推进原子操作"**（`UPDATE ... WHERE num > 0`），三条路按一致性要求选。

**恢复关键词**：六步章法（澄清优先）/ ZSet = 跳表 + 哈希表 / `ZREVRANK` O(logN) vs `COUNT(*)` O(N) / 复合分数 / **2⁵³ 位数预算，倍率 10¹⁰ → 分数上限 < 90 万** / 只存 Top N（5GB→50MB）/ 名次近似 / 热点 key 分片 / 削峰走 MQ / **防作弊三条**（步数下限·最短时长·日志回放）+ 异常进审核 / 幂等键防重复上报 / **原子扣减 `WHERE num > 0`** / Redis 预扣 + 异步落库 = 最终一致 / 排行榜挂了不能影响主玩法

**核心不变量 / 主线**：
**排行榜的答案是"把计算内建进数据结构"**（ZSet 的排名是结构自带的，不是查出来的）；
**防超卖的答案是"把判断下推进原子操作"**（`WHERE num > 0`，而不是先查后写）。
**两者是同一条原理的两个应用：把"需要原子的那一步"交给真正能保证原子的那一层。**

**完整回答骨架**：先澄清（六步 + 9.9 的 ✅/❌ 清单）→ 拆解规模 → 选型（ZSet vs MySQL，给复杂度算式）→ 复合分数（+ 位数预算）→ 工程问题（热点 / 削峰 / Top N / 近似名次 / 持久化）→ **防作弊（必答）** → 防超卖三条路 + 判据 → 指标与降级 → 收束到"判断下推"

**完整回答（口述稿）**：
场景题第一动作是澄清。先问清六件事：榜单范围（全区还是好友）、更新频率、同分怎么排、要不要防作弊、读写比例、榜单规模。9.9 那次丢分有一半在「没问够」。

技术上排行榜用 Redis ZSet：跳表把「按 score 有序」内建进结构，ZADD 和 ZREVRANK 都是 O(logN)；MySQL 算名次要 COUNT(*) WHERE score > ?，是 O(N)——200 万榜单要数约 100 万行，而 ZSet 大约 21 次比较，差约 5 万倍，且榜单越大差距越大。

同分先到者优先靠复合分数：分数 × 倍率 + (MAX_TS − 通关时间戳)。这里有个位数陷阱：Redis 的 score 是双精度浮点，只有 2^53 以内能精确表示，倍率取 10^10 时分数上限必须小于约 90 万，否则低位被抹掉、同分排序错乱而且不报错。

防作弊是必答项：弱联网玩法客户端可被篡改，必须校验（步数下限、最短通关时长、操作日志回放），异常分数进人工审核。

防超卖三条路：把判断下推进 WHERE（UPDATE ... SET stock = stock − 1 WHERE stock > 0）、Redis 预扣 + 异步落库、悲观锁排队；判据是并发量与能否容忍少量回滚。

**分层要点**：
- **结论**：先澄清六件事再选型；排行榜用 ZSet（O(logN)），MySQL 算名次是 O(N)。
- **推导链**：澄清 → 拆解规模 → 选型算复杂度 → 复合分数（位数预算）→ 工程问题（热点 / Top N / 持久化）→ 防作弊 → 防超卖。
- **量化**：200 万榜单 MySQL 约数 100 万行 vs ZSet 约 21 次比较，差约 5 万倍；score 是双精度，倍率 10^10 时分数上限约 90 万。
- **边界与常见误解**：MySQL 加个索引就行 ×（数量级不对）；倍率取大更保险 ×（会越界且不报错）；客户端上报直接入榜 ×（漏了防作弊）；先查库存再扣 ×（并发有窗口，判断要下推进 WHERE）。

**追问**（先说后看）

1. **Redis 挂了排行榜怎么办？** —— **① 从 DB 重建**（冷数据定时落 DB 是前提）；**② 降级为"榜单维护中"，主玩法不受影响**；**③ 写路径要能容忍 Redis 不可用**（丢分但不断游戏）。**"依赖服务的可用性必须低于主链路"是通用原则。**
2. **ZSet 为什么快？** —— **跳表**：按 score 有序的多级链表，`ZREVRANK` 走 O(logN)；**哈希表保证 member → score 的 O(1) 查询**。**两个结构配合，所以它"既能查排名又能按成员取分数"。**
3. **为什么不用 MySQL 的冗余排名字段？** —— **每写一次分数要更新所有受影响的名次**（写放大），**或者用 `COUNT` 现算（读放大）**；**ZSet 把排名维护内建进了数据结构**。**"把计算内建进数据结构"是选型的通用思路。**
4. **消消乐是单机游戏吧？** —— **不是**（9.9 那次的第一条失误就是假设单机）。**它有联网排行榜、好友榜、活动榜**——**澄清阶段没问，这里就假设错。**
5. **这道题和你项目有什么关系？** —— **方法论一致**：**① 澄清优先**（RuleArena 的"先查规格再重放"）；**② 幂等键防重复上报**（[[母题-P19-唯一约束与UPSERT]]）；**③ 削峰走异步 + 最终一致 + 对账**（[[母题-P12-流复制与逻辑复制]] 的延迟语义）。**答场景题时主动把这些连线，就把"知识题"答成了"工程题"。**

**同类变体**

- 「秒杀系统怎么设计？」——同一条原理的更大规模版本：**Redis 预扣（`DECR`）→ MQ 削峰 → DB 异步落库 + 唯一约束兜底**。**核心问题一样：把"扣减"放到能保证原子性的那一层。**
- 「为什么排行榜不能用 `ORDER BY score DESC` 加索引？」——**能拿到 Top N，但拿不到"我排第几"**。前者是范围扫描（索引擅长），后者是计数（O(N)）。**题目问的是后者**。
