# 母题 M17 · 排行榜与防超卖

> **模块**：MySQL / 业务并发场景
> **所属主线**：七 · 业务并发场景（抢库存、冲排行榜怎么不出错）
> **关联母题**：[[母题-M16-乐观锁与悲观锁]] · [[母题-M10-锁与死锁]] · [[母题-P19-唯一约束与UPSERT]]
> **素材来源**：**9.9 一面 A24 场景题（"给消消乐加排行榜"，10 分全场最低）**，标答在 `wiki/interview/乐元素-服务端一二面复盘报告.md` + `raw/后端视角复盘_MySQL` 第六条主线

**题目**：① 产品要给开心消消乐每个关卡加一个排行榜（DAU 2000 万），让玩家看到自己排名——结合 AI 做个设计。② 高并发扣体力/扣库存怎么防超卖？（**A24 是 9.9 全场最低分模块（10 分）：没给出成型方案、防作弊完全没提**）

**母题**：排行榜用 MySQL 还是 Redis，为什么？高并发扣减怎么防超卖？

**为什么重要**：**这是"场景设计题"的样板卡**——它考的不是知识点，而是**"拿到模糊需求后的章法"**（澄清 → 拆解 → 方案 → 风险 → 指标）。**9.9 那次的失败链是：假设错（以为消消乐是单机）→ 被否（提分享）→ 澄清不系统 → 长时间空白 → 没有成型方案**。**这张卡就是修复：把"排行榜"变成一道可以闭卷重放的母题**——**它同时覆盖场景设计方法论 + 技术选型 + 高并发扣减三个考点，性价比极高。**

**一句话结论**：**排行榜用 Redis ZSet**（成员按 score 有序，`ZREVRANK` / `ZREVRANGE` 都是 O(logN)，天然就是排行榜）；**MySQL 不适合**（排名需要 `COUNT(*)` 统计比自己分高的行数，代价 O(N)，且高频更新排序索引压力大）。**同分先到者优先 → 复合分数**：`score = 分数 × 10^10 + (MAX_TS - 通关时间戳)`。**防超卖三条路**：**① 数据库原子扣减**（`UPDATE ... SET n=n-1 WHERE id=? AND n>0`，影响行数判断）、**② 乐观锁（version 条件更新，M16）**、**③ Redis 预扣 + 异步落库（最终一致）**。**判据：强一致用数据库原子更新；高并发削峰用 Redis 前置、DB 兜底。**

**恢复关键词**：ZSet 跳表 / 复合分数 / ZREVRANK / 只存 Top N / 原子扣减 `WHERE n>0` / 乐观锁 / **Redis 预扣 + 异步落库** / 最终一致 / 场景题六步

**核心不变量 / 主线**：
**场景题的第一动作是澄清，不是给方案。** ——**9.9 那次丢分的一半在"没问够"（榜单范围、更新频率、防作弊全没问），另一半才是技术**。**技术选型（MySQL vs Redis）反而是这张卡里最容易的部分。**

**完整回答骨架**：六步章法 → 排行榜选型与复合分数 → 2000 万 DAU 的工程问题（热点 key / 削峰 / 名次近似 / 持久化）→ 游戏特性（防作弊 / 弱联网）→ 防超卖三条路 → 指标与降级

## 原理分解

### 一、场景题六步（先背这个，再背技术）

```
① 澄清（开口前先问 10 秒）：排名依据？榜单范围（全服/好友/Top N）？更新频率？
                          展示字段？历史榜/周榜？防作弊？规模？
② 拆解：规模估算（2000 万 DAU × 千级关卡 → 不可能全量存排名）
③ 方案：存储 + 读写路径 + 数据结构
④ 风险：热点 key、写入尖峰、内存、作弊
⑤ 指标：写入 QPS、查榜 P99、内存占用、裁剪耗时
⑥ 降级：Redis 挂了怎么办
```

**9.9 那次的澄清对照**（复盘里的 ✅/❌ 清单）：**问了排名依据、展示字段、规模；没问榜单范围、更新频率、历史榜、防作弊**——**把这张清单背下来，下次第一分钟就不会空白**。

### 二、排行榜选型：为什么是 Redis ZSet

| | Redis ZSet | MySQL |
|---|---|---|
| 排名查询 | `ZREVRANK` **O(logN)** | **`COUNT(*) WHERE score > ?`，O(N)**（或加冗余排名字段，但更新代价高） |
| 榜单读取 | `ZREVRANGE` 直接取 Top N | `ORDER BY score DESC LIMIT N`（索引可以，但更新热点行代价高） |
| 更新 | `ZADD` O(logN) | 高频 `UPDATE` 同一行 → 行锁热点（M10） |
| 底层 | **跳表 + 哈希表**（既能按 member 查 score，又能按 score 范围查） | B+ 树 |

**同分按时间早的优先 → 复合分数**（这是 9.9 标答里最巧的一步）：

```
score = 分数 × 10^10 + (MAX_TS − 通关时间戳)
        分数越高越大；同分时时间越早（MAX_TS - ts 越大）排名越高
```

**一句话解释**：**把两个排序维度压进一个可比较的数字**——**避免"先按分数排、再按时间排"的两级查询**。

### 三、2000 万 DAU 下的工程问题（答到这层才像服务端）

```
① 热点 key：热门关卡集中在少数 key → 按"关卡+区服/分片"拆，或本地缓存 + 异步刷新
② 写入削峰：通关上报是尖峰 → 消息队列异步落榜，前端先返回"计算中"
③ 名次不必实时精确：非头部玩家用"分数段桶计数"近似名次，精确 ZREVRANK 留给头部
④ 只存 Top N：每关只保留 Top N（ZREMRANGEBYRANK 定期裁剪）——内存控制的关键
   玩家个人最佳与名次另存（DB），榜外玩家看"自己的最佳 + 击败百分比"
⑤ 持久化：Redis 只是热层，冷数据定时落 DB；Redis 挂了可从 DB 重建
⑥ 活动榜：带过期时间的 key（EXPIRE），活动结束自动清理
```

**第 ③ 条是"名次近似"**——**2000 万 DAU 下大多数玩家的名次并不需要精确到个位**（"你超过了 97% 的玩家"），**这是把 O(logN) 精确查询留给头部、用 O(1) 近似服务长尾的取舍**。**这一条是 9.9 标答里的亮点，值得单独背。**

### 四、游戏特性（乐元素面试官最想听的）

- **防作弊**：**消消乐是弱联网玩法，客户端上报的分数必须校验**——步数下限、最短通关时长、关键操作日志回放；**异常分数进人工审核队列，不直接入榜**；
- **弱联网容错**：离线通关本地缓存，联网后补报，**用"玩家 ID + 关卡 + 时间戳"做幂等，避免重复提交刷榜**（**这就是 P19 的幂等键思想在游戏场景的落点**）；
- **活动榜时效**：EXPIRE 自动清理。

**"防作弊没提"是 9.9 那次被明确点名的缺口**——**游戏公司的场景题里这是必答项**。

### 五、防超卖三条路

**① 数据库原子扣减（最简单、强一致）**

```sql
UPDATE stock SET num = num - 1
WHERE id = :id AND num > 0;
-- 影响行数 = 1 → 扣成功；0 → 已售罄
```

**为什么能防超卖**：**判断和写入在一条语句里原子完成**（和 P18/M16 的条件更新是同一个原理）——**不存在"查到还剩 1，两个人都扣"的窗口**。**热点行锁竞争是它的代价**（同一行高频更新会排队，M10）。

**② 乐观锁（version）**：语义同上，多一个 version 字段（M16）；**适合"扣减前还要做别的判断"的场景**。

**③ Redis 预扣 + 异步落库（高并发削峰）**

```
请求 → Redis DECR（原子）→ 扣成功才进队列 → 异步落 DB
                ↓ 扣成负数 → 回滚/拒绝
```

**代价**：**最终一致**（Redis 与 DB 有窗口）、**要处理重复消费与对账**（P19 的幂等键 + 唯一约束兜底）。**判据**：**强一致（钱）→ 数据库原子更新；高并发（秒杀、体力）→ Redis 前置 + DB 兜底**。

### 六、指标与降级

- **指标**：写入 QPS、查榜 P99、Redis 内存占用、裁剪任务耗时、**超卖告警（库存对账）**；
- **降级**：**Redis 不可用时返回 DB 快照或"榜单维护中"，绝不让排行榜拖垮主玩法**——**"排行榜挂了不能影响游戏本体"是这一题的底线判断**。

## 二、扩展：类似题与追问

**类似题**

1. 「ZSet 为什么快？」——**跳表**：按 score 有序的多级链表，`ZREVRANK` 走 O(logN)；**哈希表保证 member → score 的 O(1) 查询**。**两个结构配合，所以它"既能查排名又能按成员取分数"。**
2. 「为什么不用 MySQL 的排名字段？」——**每写一次分数要更新所有受影响排名**（写放大），**或者用 `COUNT` 现算（读放大）**；**ZSet 把排名维护内建进了数据结构**。**"把计算内建进数据结构"是选型的通用思路。**
3. 「消消乐是单机游戏吧？」——**不是**（9.9 那次的第一条失误就是假设单机）。**它有联网排行榜、好友榜、活动榜**——**澄清阶段没问，这里就假设错**。

**追问链**

- 追问一层：**「Redis 挂了排行榜怎么办？」**——**① 从 DB 重建（冷数据定时落 DB 是前提）；② 降级为"榜单维护中"，主玩法不受影响**；**③ 写路径要能容忍 Redis 不可用（丢分但不断游戏）**。**"依赖服务的可用性必须低于主链路"是这条的通用原则。**
- 追问二层：**「这道题和你项目有什么关系？」**——**方法论一致**：**① 澄清优先（RuleArena 的"先查规格再重放"）；② 幂等键防重复上报（P19）；③ 削峰走异步 + 最终一致 + 对账（M14/P12 的延迟语义）**。**答场景题时主动把这些连线，就把"知识题"答成了"工程题"。**
