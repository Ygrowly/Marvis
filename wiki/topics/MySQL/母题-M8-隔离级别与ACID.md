## 一、教材

### 1. 前提：事务只有一句话

#### 1.1 定义【事实】

**事务 = 一组动作，一起成功或一起失败。**

就这一句。**没有"必须满足 ACID"这种前提**——ACID 是从这一句**推出来的**。

#### 1.2 从这一句推出 ACID

推四步：

**① 要能"一起失败" → 必须能撤销 → 需要 undo（前镜像）**

【推导】部分成功必须能退回去，所以写入之前要记下"**改之前是什么样**"。这就是 undo log 的职责。

**② 要能"一起成功"在这之后不丢 → 必须能重放 → 需要 redo（后镜像）**

【推导】事务说"提交成功"，但数据页可能还在内存里。此时断电，需要一个"**改成什么样**"的记录，重启后重放补上。这是 redo log 的职责。

**③ 并发下多个事务同时在跑 → 需要两种分工**

【推导】并发只分两种关系：

- **写与写**：会互相覆盖 → **必须排队** → 用**锁**
- **读与写**：读不需要改变数据 → **不必排队** → 用 **MVCC** 让读去看一个"旧版本"

**④ 前三步都做完，整体就表现出"从合法状态到合法状态" → 这就是一致性**

【推导】**一致性不是第四件事，是前三件事的结果。** 它还需要数据库约束（唯一、外键、CHECK）和业务校验兜底——但那些是"额外加固"，不是"单独的机制"。

**到这里你应该能回答**：为什么"一致性靠什么实现"这句话本身就问得不准确？

> 【结论】**A = undo｜D = redo｜I = 锁 + MVCC｜C = 前三者 + 约束共同得到的结果。**
> **撤销看前镜像，恢复看后镜像。**
>
> 【事实】数据库界把这个四要素结构称为 ACID。

### 2. 并发会出什么问题

#### 2.1 三个现象【事实】

| 现象 | 定义 | 例子 |
|---|---|---|
| **脏读** | 读到了别人**还没提交**的数据（它可能回滚） | 读到 `status='DONE'`，但那个事务后来回滚了 |
| **不可重复读** | 同一事务内**两次读同一行**，结果不同 | 先读余额 100，再读变 80 |
| **幻读** | 同一事务内**两次范围查询**，行数不同 | 先查到 10 条，再查变 11 条 |

**三者的区别在"变的是什么"**：

- 脏读 → 变的是**数据的提交状态**
- 不可重复读 → 变的是**同一行的值**
- 幻读 → 变的是**结果集的成员（行数）**

【推导】**这个区分不是文字游戏**：不可重复读可以用"锁住那一行"解决；幻读锁不住——**因为要防的是"还不存在的行"**，所以它必须靠另一套机制（间隙锁，见 M10）。

#### 2.2 为什么会有这些问题

根子上只有一个原因：**并发事务的执行顺序不确定，而你看见的东西取决于"你在哪一刻看"。**

【推导】所以解决思路只有两条：

1. **让读看到固定的某一刻** → 快照（MVCC 路线）
2. **让冲突的操作排队** → 锁（串行化路线）

**四个隔离级别，就是这两条路线的不同配比。**

### 3. 四个级别：一条单调的取舍谱系

::figure isolation-spectrum.svg | 四个隔离级别是一条取舍谱系 | 越往右挡住的异常越多、并发越低；InnoDB 默认取中间的可重复读

#### 3.1 逐级挡住什么【事实】

| 级别 | 挡住 | 没挡住 |
|---|---|---|
| **读未提交 RU** | —— | 全都会发生 |
| **读已提交 RC** | 脏读 | 不可重复读、幻读 |
| **可重复读 RR**（InnoDB 默认） | 脏读、不可重复读 | 幻读（在 MySQL 里被间隙锁额外挡住，见 4） |
| **串行化** | 全部 | —— |

**这个表的规律**：**每一级都是一次"用并发换正确性"的交换**，不是"越严格越好"。

#### 3.2 唯一指标：读写冲突面

要比较级别，必须**用同一个指标**。取"**任意两个并发请求会互相阻塞的概率**"（按请求对估算）：

假设真实负载里 **读占 90%、写占 10%**：

| 情况 | 谁参与互斥 | 冲突面 |
|---|---|---|
| **无 MVCC**（读加 S 锁、写加 X 锁，S 与 X 互斥） | 读-写、写-写 | 2 × 0.9 × 0.1 = **约 18%** |
| **有 MVCC**（读不加锁） | 只剩写-写 | 0.1 × 0.1 = **约 1%** |

【推导】**MVCC 的价值不是"更快"，是"把读从冲突里摘出去"。** 读占比越高，收益越大——报表型、列表型负载收益最明显。

**同一把尺子量四个级别**：

| 级别 | 读要不要参与排队 |
|---|---|
| RU / RC / RR（快照读） | **不参与**（MVCC 兜住） |
| 串行化 | **参与**（普通 `SELECT` 也要加 S 锁）→ 冲突面回到约 18% |

【推导】**串行化的代价，本质是把 MVCC 挣来的那 17 个百分点又还回去了。**

#### 3.3 为什么 InnoDB 默认 RR【取舍】

两个理由，**两个都要说，只答一个会显得是背的**：

1. **历史原因**：早期 RC 在 binlog 为 statement 格式时，主从可能执行出不同结果（RR 的间隙锁恰好压住了这类不确定性）。
2. **工程权衡**：RR + MVCC + 间隙锁的组合，在"一致性够用"与"并发不塌"之间取了一个划算的点。

**准确说法是**：**默认 RR 是历史 + 权衡的结果，不是"RR 唯一正确"。** PostgreSQL 默认就是 RC，而且不靠间隙锁——两边都活得很好（[[母题-P8-隔离级别与读一致性]]）。

### 4. RR 下的幻读：一半靠 MVCC，一半靠锁

先把两个读定义清楚【事实】：

| | 什么操作 | 用什么 |
|---|---|---|
| **快照读** | 普通 `SELECT` | **MVCC + 快照**（不加锁） |
| **当前读** | `SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` / `INSERT` | **读最新版本 + 加锁** |

【推导】**幻读的准确说法**，靠这一对概念分开讲：

- **快照读下不幻读**：RR 的快照在事务第一次读时定住，**别人后面插的行根本不在快照里**；
- **当前读下也不幻读**：必须读最新版本，MVCC 帮不上，**靠 next-key lock 锁住范围阻止插入**（M10）；
- **两者混用时会"看起来像幻读"**：先用快照读看到 10 行，接着 `UPDATE`（当前读）时发现是 11 行——**这是两套机制各干各的正常结果，不是 bug。**

**到这里你应该能回答**：为什么"RR 完全解决了幻读"这句话是错的？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "一致性由隔离级别实现" | 【推导】C 是**结果**：A（undo）+ D（redo）+ I（锁+MVCC）+ 约束共同得到，**没有独立的一致性机制** |
| "RR 完全解决了幻读" | 【推导】快照读靠 MVCC、当前读靠间隙锁，**两种读都不幻读，但混用时会出现"看起来像幻读"**；说"完全解决"是漏了机制 |
| "隔离级别越高越好" | 【取舍】串行化把读也拉进排队，冲突面从约 1% 回到约 18%（3.2 的估算） |
| "MVCC 是 RR 专属" | 【事实】MVCC 是 InnoDB 的基础能力，**RC 下同样生效**，只是快照刷新得更勤（M9） |
| "MySQL 和 PG 默认隔离级别一样" | 【事实】**MySQL 默认 RR，PG 默认 RC**。这是最容易被抓住的方言错误——两边连"怎么处理幻读"都不是一套（[[母题-P8-隔离级别与读一致性]]） |
| "写写冲突时 MySQL 会报错让我重试" | 【取舍】MySQL 的哲学是**排队等锁**；PG 在 RR 以上会**报序列化失败（40001）让你重试**。"冲突就等"和"冲突就报错"是两种代价模型 |

## 二、自测

**Q1（计算）**：一个服务的负载里读占 90%、写占 10%。分别估算"读加锁"和"读靠 MVCC 不加锁"两种情况下，并发请求互相阻塞的比例。

**A1**（按请求对估算，只计数互斥的组合）：

- **读加锁**（S 与 X 互斥）：互斥组合是 **读-写 + 写-写** → 2 × 0.9 × 0.1 + 0.1 × 0.1 = **约 19%**
- **读靠 MVCC**（读不参与）：互斥组合只剩 **写-写** → 0.1 × 0.1 = **约 1%**

**降低约一个数量级。** 口径提醒：这是**只按请求类型占比估的粗略模型**，真实系统还要看访问同一份数据的倾斜度（热点行会把概率显著推高）。

**这个算式的意义**：**MVCC 的收益不是"更快"，是"把读从冲突里摘出去"——读占比越高收益越大。**

**Q2（判读）**：事务 A 依次执行：① `BEGIN` ② `SELECT balance FROM account WHERE id=1`（读到 100）③ 事务 B 执行 `UPDATE account SET balance=80 WHERE id=1` 并 `COMMIT` ④ A 再执行一次同样的 `SELECT`。

分别在 **RC** 和 **RR** 下，第 ④ 步读到什么？

**A2**：

- **RC**：读到 **80**。RC 每条语句生成一个新的 ReadView，所以能看到 B 刚提交的结果 → **出现不可重复读**。
- **RR**：读到 **100**。RR 在第一次快照读时定住 ReadView 并复用，**B 的提交不在这个快照里** → 可重复读。

**关键差别只有一个**：**ReadView 是不是每条语句重新生成**。这就是"可重复读"的全部实现（M9 展开）。

**Q3（计算）**：要同时满足"回滚能撤销"和"提交后断电不丢"，最少需要哪几个日志组件？各自记的是"改之前"还是"改成什么"？

**A3**：

| 需求 | 组件 | 记什么 |
|---|---|---|
| 回滚能撤销（原子性） | **undo log** | **改之前的镜像（前镜像）** |
| 提交后不丢（持久性） | **redo log** | **改成什么样（后镜像）** |

**两个都需要，不能省。** 记忆点：**撤销看前镜像，恢复看后镜像。**

【补充】InnoDB 还有一个 **binlog**，那是 Server 层的归档日志（用于复制和恢复）。**它不负责 A 也不负责 D**，但它的存在带来一个新问题——两份日志要一致，于是有了两阶段提交（[[母题-M11-三日志与两阶段提交]]）。

**Q4（纠错）**：下面这段话哪里错了？

> "数据库的一致性是通过隔离级别实现的，所以隔离级别越高，一致性越强。"

**A4**：**两处都错。**

1. **"一致性由隔离级别实现"** —— C 不是独立机制，它是 **A（undo）+ D（redo）+ I（锁与 MVCC）+ 数据库约束**共同作用的**结果**。隔离级别只负责 I 这一项。
2. **"隔离级别越高一致性越强"** —— 隔离级别提高的是**并发正确性**，不是"一致性"这个整体属性。而且它有代价：串行化会把读也拉进排队（Q1 的模型里冲突面从约 1% 回到约 19%）。

**准确说法**：**一致性是"事务把数据库从一个合法状态带到另一个合法状态"，它靠 A、D、I 加上约束共同保证；隔离级别只是其中 I 的档位。**

**Q5（纠错）**：下面这段话哪里错了？

> "MySQL 和 PostgreSQL 都默认使用可重复读，两边处理幻读的方式也一样。"

**A5**：**两句都错。**

1. **默认值不同**：**MySQL 默认 RR，PostgreSQL 默认 RC**。
2. **幻读处理机制不同**：**MySQL 用 next-key lock（间隙锁）"挡住"插入**；**PostgreSQL 根本没有间隙锁**，它靠快照 + 在必要时报序列化失败让应用重试。

**这两条是面试安全底线**——把 MySQL 的语义套到 PG 上（或反过来）是**明确错误**，一说出来就暴露只在一边工作过。PG 侧的对照见 [[母题-P8-隔离级别与读一致性]] 和 [[母题-P10-无间隙锁与锁变体]]。

## 三、面试输出（学完再看）

**一句话结论**：事务就是"一组动作一起成败"。**A 靠 undo（前镜像）、D 靠 redo（后镜像）、I 靠锁管写写 + MVCC 管读写、C 是前三者加约束共同得到的结果——它不是独立机制。** 并发三问题是脏读、不可重复读、幻读，四个隔离级别逐级挡住它们，越严格并发越低。**InnoDB 默认 RR，靠 MVCC 挡快照读的幻读、靠间隙锁挡当前读的幻读。**

**恢复关键词**：一起成败 / 撤销看前镜像、恢复看后镜像 / undo=A、redo=D、锁+MVCC=I / **一致性是结果不是机制** / 脏读=未提交·不可重复读=同一行·幻读=行数 / RC 挡脏读、RR 再加不可重复读 / 快照读 vs 当前读 / 默认 RR 是历史+权衡 / MySQL RR vs PG RC

**核心不变量 / 主线**：
**事务 = "一组动作一起成功或一起失败"。** ACID 不是四条并列的规矩，而是从这一句推出来的四步：要能撤销（undo）、要能不丢（redo）、并发下要分工（锁管写写、MVCC 管读写）、最后整体表现为一致。

**完整回答骨架**：事务的唯一前提 → 四步推出 ACID（特别点明 C 是结果）→ 三个并发问题及其区别（未提交 / 同一行 / 行数）→ 四个级别逐级挡 + 用"读写冲突面"这个统一指标说代价 → 为什么默认 RR（历史 + 权衡，不是唯一正确）→ RR 的幻读靠两套机制 → 方言（PG 默认 RC、没有间隙锁）

**追问**（先说后看）

1. **为什么 A 是 undo、D 是 redo，不能反过来？** —— **undo 记前镜像，所以能撤销**；**redo 记后镜像，所以能重放**。撤销要把数据往回变，重放要把数据往前推。**一句话：撤销看前面，恢复看后面。**
2. **RR 下两个事务同时 `UPDATE` 同一行会怎样？** —— **排队等锁**（MySQL 的哲学是"冲突就等"），不是报错。如果等待成环就死锁，InnoDB 会检测并**回滚代价较小的那个事务**（M10）。
3. **串行化下还死锁吗？** —— **更容易**。读也加 S 锁，锁的持有面更大、成环机会更多。缓解靠**统一加锁顺序 + 缩短事务**（M10）。
4. **为什么报表查询在 MySQL 下不会互相锁？** —— 普通 `SELECT` 是快照读，**不加锁**。但它**会持有 ReadView**，长查询因此变成"长事务"的一种，拖住 undo 回收（[[母题-M13-长事务为什么危险]]）。

**同类变体**

- 「RC 和 RR 的差别到底在哪一层？」——**ReadView 生成时机**，别的全一样（M9）
- 「MySQL 为什么默认 RR，PG 为什么默认 RC？」——两种**代价模型**：MySQL 用锁"挡住"冲突，PG 用快照 + 报错"检测"冲突。**不要用"哪个更好"回答**
- 「MySQL 的 RR 里幻读到底解决了吗？」——分快照读/当前读回答（见 Q5 与第 4 节）
