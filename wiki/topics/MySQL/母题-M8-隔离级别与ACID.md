# 母题 M8 · 隔离级别与 ACID

> **模块**：MySQL / 事务与锁
> **所属主线**：三 · 事务与锁（并发改同一份数据，为什么不会乱）
> **关联母题**：[[母题-M9-MVCC]] · [[母题-M10-锁与死锁]] · [[母题-M11-三日志与两阶段提交]]
> **素材来源**：`raw/后端视角复盘_MySQL：为什么它能查得快、并发稳、还扛得住.md` 第二条主线（事务/锁/MVCC）+ `raw/Mysql面试题` 第 2 节

**题目**：四个隔离级别各挡住哪个并发问题？ACID 四个字母分别靠什么机制实现？

**母题**：四个隔离级别分别解决什么问题？ACID 分别是怎么实现的？

**为什么重要**：**这是主线三的地基**。它有一个几乎人人会答错一半的追问——**"一致性由谁实现？"** 答成"由隔离级别实现"或"由某个机制实现"都错了：**C 是前三者 + 约束共同保证的结果，它自己不是独立机制**。**答对这一条，比背四个级别有用得多。**

**一句话结论**：并发三问题是**脏读（读到未提交）、不可重复读（同一事务两次读不同值）、幻读（两次范围查询行数不同）**；四个级别逐级递进——**读未提交（全暴露）→ 读已提交（挡脏读）→ 可重复读（InnoDB 默认，再挡不可重复读，用间隙锁挡幻读）→ 串行化（读也加锁，全挡但并发最差）**。**ACID 的实现：A 原子性 = undo log；D 持久性 = redo log；I 隔离性 = 锁 + MVCC；C 一致性 = 前三者加上业务约束共同得到的结果。**

**恢复关键词**：脏读 / 不可重复读 / 幻读 / RC vs RR / 快照读与当前读 / undo=原子性 / redo=持久性 / 锁+MVCC=隔离性 / **一致性是结果不是机制**

**核心不变量 / 主线**：
**事务 = "一组动作一起成功或一起失败"。** 这句话（raw 里的原话）比背 ACID 四个字有用——**因为四个字母能从这一句推出来**：一起成败需要 undo（能撤销）和 redo（不丢），并发下多个事务同时做，需要锁和 MVCC 分工，最后整体表现出"一致"。

**完整回答骨架**：三个并发问题 → 四个级别逐级挡 → InnoDB 默认 RR（快照读 + 间隙锁挡幻读）→ ACID 逐条对应机制 → 一致性为什么不是独立机制

## 原理分解

### 一、三个并发问题（先分清，级别才有的放矢）

| 问题 | 定义 | 例子 |
|---|---|---|
| **脏读** | 读到了**别的事务还没提交**的数据（它可能回滚） | 读到 `status='DONE'`，但那个事务回滚了 |
| **不可重复读** | 同一事务内**两次读同一行**结果不同（中间有人改了并提交） | 先读余额 100，再读变 80 |
| **幻读** | 同一事务内**两次范围查询**返回的行数不同（中间有人插入） | 先查到 10 条，再查变 11 条 |

**三者区别一句话**：**脏读关于"未提交"，不可重复读关于"同一行被改"，幻读关于"行数变化"。**

### 二、四个级别逐级递进

| 级别 | 挡住 | 没挡住 |
|---|---|---|
| **读未提交 RU** | —— | **全都可能发生**（读未提交数据） |
| **读已提交 RC** | 脏读 | 不可重复读、幻读 |
| **可重复读 RR（InnoDB 默认）** | 脏读、不可重复读 | **幻读（InnoDB 靠间隙锁挡住了大部分，见下）** |
| **串行化** | 全部 | ——（读也加锁，并发最差） |

**InnoDB 为什么默认 RR**：历史原因（早期 RC 在复制场景下可能出现主从不一致），**但更本质的是 RR + MVCC + 间隙锁的组合在"一致性"与"并发"之间取了一个工程上很划算的平衡**。**面试时能说"默认 RR 是历史 + 权衡，不是唯一正确"就比死记强。**

### 三、RR 下幻读怎么挡住（一半靠 MVCC，一半靠锁）

这是本题最容易说错的地方。**RR 并不是"完全解决幻读"**：

- **快照读**（普通 `SELECT`）：靠 **MVCC**——事务开始时定住快照，**后面就算别人插入并提交，快照读也看不到** → **不会幻读**；
- **当前读**（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）：**必须读最新版本**，MVCC 帮不上 → 靠 **next-key lock（记录锁 + 间隙锁）** 锁住范围，**阻止别人在范围内插入** → **也不幻读**。

**所以准确说法是**：**InnoDB 的 RR 在"快照读"下靠 MVCC、在"当前读"下靠 next-key lock，两种读都不幻读**——**但两种读混用的场景仍可能出现"看起来像幻读"的现象**（先用快照读看到 10 行，再 `UPDATE` 时行数变了，因为当前读看到了新数据）。**这个细节能讲清，说明真的理解了两套机制。**

### 四、ACID 逐条对应机制（本题核心）

| 字母 | 靠什么实现 | 一句话 |
|---|---|---|
| **A 原子性** | **undo log** | 改错了/回滚了，**用 undo 恢复原状**——"改之前的备份" |
| **D 持久性** | **redo log** | 提交过但数据页没落盘，崩溃后**用 redo 重放补上** |
| **I 隔离性** | **锁 + MVCC** | 写写用锁排队，读写靠 MVCC 不互相堵 |
| **C 一致性** | **前三者 + 约束 + 业务校验** | **它不是独立机制，是结果** |

**C 那一行必须展开说**：一致性 = **事务把数据库从一个合法状态带到另一个合法状态**。它需要：**A 保证这组动作要么全做要么全不做**、**D 保证不丢**、**I 保证并发下互相看不见对方的中间状态**、**再加上数据库约束（唯一/外键/CHECK）和业务校验**。**所以"一致性靠什么实现"的标准答案是"前三者共同作用 + 约束"，而不是某一个组件。**

**这个结构可以直接迁移**：RuleArena 的幂等设计里"业务校验 + 数据库约束都要有"（P19）是同一句话在另一处的重述——**业务校验给清晰错误，约束防并发穿透，一致性是两者加事务共同的结果。**

### 五、raw 里那句核心（值得记住）

> **事务保证一起成败，锁保证修改别打架，MVCC 保证读写别互相堵死。**

**三句对应三块**：undo（一起成败的一部分）+ redo（不丢）、锁（写写）、MVCC（读写）。**背下这句，整个主线三的骨架就有了。**

## 二、扩展：类似题与追问

**类似题**

1. 「RC 和 RR 的差别到底在哪一层？」——**ReadView 生成时机**：RC 每条语句生成一次，RR 整个事务第一次快照读时生成一次（M9 展开讲）。**别的都一样，就差这一条。**
2. 「MySQL 默认为什么是 RR，PG 默认是 RC？」——**两边的默认值不同是设计哲学差异**：MySQL 用 RR + 间隙锁尽量"挡住"冲突；PG 用 RC + 快照 + 报错重试"检测"冲突（P8）。**不要试图用"哪个更好"来回答，要答"两种代价模型不同"。**
3. 「串行化下还死锁吗？」——**更容易**（读也加锁，锁的持有范围更大），**靠统一顺序 + 缩短事务缓解**（M10）。

**追问链**

- 追问一层：**「为什么说 A 和 D 分别是 undo 和 redo，而不是反过来？」**——**undo 记"改之前"，所以能撤销（原子性）；redo 记"改成什么"，所以能重放（持久性）**。**一句话记忆：撤销看前镜像，恢复看后镜像。**
- 追问二层：**「RR 下两个事务同时 `UPDATE` 同一行会怎样？」**——**排队等锁**（MySQL 的哲学：冲突就等），**不是报错让你重试**（PG 的哲学，P8）。**如果互相等就死锁**（M10），InnoDB 会自动检测并回滚代价较小的事务。**这条是 M8→M10 的桥。**
