## 一、教材

### 1. 前提：为什么不能"改完直接写磁盘"

#### 1.1 两个约束同时成立【推导】

要回答"断电后订单还在吗"，先看数据库面临的两个约束：

1. **数据要最终落到磁盘**（内存断电就没了）
2. **提交返回的那一刻，修改就不能丢**（这是"持久性"的定义）

**最朴素的做法**是：`UPDATE` 一执行，就把数据页写回磁盘。**但这行不通**，原因只有一个字：**慢**。

#### 1.2 量化：慢在哪

【事实】磁盘的两种访问方式成本差得很远：

| 访问方式 | 机械盘 | SSD |
|---|---|---|
| **顺序写** | 约 100–200 MB/s | 几百 MB/s 到 GB/s |
| **随机写** | 受寻道限制，约 100–200 次 IOPS × 4KB ≈ **0.4–0.8 MB/s** | 比顺序写慢，但没有寻道代价 |

【推导】机械盘上**两者差 2–3 个数量级**。而"把刚改的那一页写回去"**是随机写**（那一页在磁盘上的位置是散的）。

> **所以要换一个做法：把"随机写数据页"换成"顺序写日志"。**

#### 1.3 WAL 由此而来【事实】

**WAL（Write-Ahead Logging，日志先行）**：**先写日志，再写数据页。**

```
① 改内存（Buffer Pool）——快
② 把"改了什么"顺序追加到 redo log —— 顺序写，快
③ 提交时保证 redo 已落盘 —— 这一步成功，"提交"才成立
④ 数据页什么时候写回磁盘，无所谓（后台慢慢刷）
```

**WAL 一次拿到两样东西**：

- **性能**：把随机写换成了顺序写（1.2 的量化）
- **崩溃安全性**：只要 ②③ 成功，**内存里的修改就是可恢复的**

**到这里你应该能回答**：为什么数据库可以说"提交成功"而数据页还在内存里？

> **因为"安全"的标志不是"数据在磁盘上"，而是"修改这件事已经落盘了"。**

### 2. 三条日志：先各自介绍，再比较

#### 2.1 undo log —— 前镜像【事实】

- **属于**：InnoDB 引擎层
- **记什么**：**数据修改之前的旧值**（"改之前是什么样"）
- **职责**：**回滚**（原子性）+ **给 MVCC 提供旧版本**（[[母题-M9-MVCC]]）

**两个职责共用同一份数据**——因为"上一个版本"就是回滚要恢复的那个值。

#### 2.2 redo log —— 后镜像【事实】

- **属于**：InnoDB 引擎层
- **记什么**：**数据页的物理修改**（"某数据页某偏移被改成了什么"）
- **物理形态**：**固定大小、循环写**，会覆盖旧内容
- **职责**：**崩溃恢复**（持久性）

#### 2.3 binlog —— 逻辑日志【事实】

- **属于**：**Server 层**（注意：不在 InnoDB 里，这是关键）
- **记什么**：**逻辑操作**（SQL 语句，或每行的前后镜像）
- **物理形态**：**追加写**，写满切新文件，**不覆盖**
- **职责**：**主从复制** + **时间点恢复**

#### 2.4 对照表

| | undo | redo | binlog |
|---|---|---|---|
| 所属层 | InnoDB | InnoDB | **Server** |
| 内容 | 前镜像 | 后镜像（物理） | 逻辑操作 |
| 文件形态 | 段/回滚段 | **固定大小循环写** | **追加写，不覆盖** |
| 职责 | 回滚 + MVCC 旧版本 | 崩溃恢复 | 复制 + 时间点恢复 |

**换个说法更好记**（放在工单/订单系统里）：

- 状态更新失败要能撤销 → **undo**
- 更新成功但机器崩了不能丢 → **redo**
- 主从同步和备份恢复 → **binlog**

#### 2.5 一个高价值追问

**「binlog 能不能单独保证 crash-safe？」**

【推导】**不能。** 两个理由：

1. 它**不在 InnoDB 内部**——它的写入时机与 redo 不同步；
2. 它**不记录数据页的物理变化**，没法用来把内存页恢复成正确状态。

**所以 binlog 必须和 redo 配合——而"配合"这件事本身有风险，于是有了两阶段提交。**

### 3. redo 的环形结构

#### 3.1 两个指针【事实】

redo 文件是**固定大小、循环写**的，上面有两个位置：

| 指针 | 含义 |
|---|---|
| **write pos** | 当前写到哪（不断前进） |
| **check point** | **已经被安全刷盘（脏页已落盘）的位置** |

```
...[ check point ...... write pos ]......... 回到开头
    ↑ 之前的日志可以复用        ↑ 之后的区域空闲
    待刷盘的记录在这段区间里
```

#### 3.2 为什么是"循环写"而不是"无限追加"

【推导】**因为 redo 只服务于"崩溃恢复到最新状态"这一个目的**——一旦它记录的改动**已经落到数据页上**，这条 redo 就再也没用了，占的位置可以复用。

**注意这里和 binlog 的分工**：binlog 要**长期保留**（做复制和时间点恢复），所以它追加写、不覆盖；**redo 用完即弃，所以循环写。**

> **同一个系统里两种相反的文件形态，是因为两个目的不同。** 这个对比能讲清楚，说明不是背的。

#### 3.3 危险场景：write pos 追上 check point

【推导】如果 check point 长期不推进（脏页没刷出去），write pos 会绕上来**追上 check point**——此时**没有空闲区域可写了**。

**结果**：写入被迫停下来等刷脏页，**表现是"写入突然卡顿"**。

**顺序必须是**【推导】：

```
先刷脏页  →  再推 check point  →  才释放这段空间
```

**不能反过来**——否则这段 redo 已经没了，而对应的脏页还没落盘，**崩溃就丢数据**。

#### 3.4 刷盘参数

**redo 侧** `innodb_flush_log_at_trx_commit`：

| 值 | 行为 | 代价 |
|---|---|---|
| **1（默认）** | 每次提交都 `fsync` | 最安全，最慢 |
| 0 | 提交只写内存 buffer，后台每秒刷 | 最快，**掉电丢最近 1 秒** |
| 2 | 写 OS 缓存，不立刻 `fsync` | **进程崩不丢，整机掉电会丢** |

**binlog 侧** `sync_binlog`：0 = 交给系统；N = 每 N 个事务刷一次；**1 = 每次提交刷**。

【事实】**生产上要金融级一致，就是「双一」**：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`。**这意味着接口返回"提交成功"时，两份日志都已经真的在磁盘上了**——这才是"断电不丢"的前提。

### 4. binlog 的三种格式

| 格式 | 记什么 | 优点 | 风险 |
|---|---|---|---|
| **Statement** | 原始 SQL 语句 | 日志小 | 含 `UUID()` / `NOW()` 等**非确定函数**会让从库算出不同结果 → **主从漂移** |
| **Row** | 每行修改前后的具体内容 | **复制绝对精确** | 日志量大（批量 `UPDATE` 会暴涨） |
| **Mixed** | 自动判断，安全用 Statement、危险切 Row | 平衡 | 判断逻辑需要理解 |

【取舍】**现在主流是 Row**——数据安全优先于日志体积。Statement 只在"日志体积敏感 + SQL 确定"时才考虑。

### 5. 两阶段提交：为什么非它不可

#### 5.1 推导：问题出在"两份日志"

【推导】现在有**两份都要写**的日志：redo（InnoDB）和 binlog（Server）。**它们不在一个组件里，没法用一个本地事务包住。**

那么"两个写入"必然会有一个中间状态——**如果正好在中间崩溃，两份日志就可能不一致**。而不一致的后果是**主从数据不同**。

::figure two-phase-commit.svg | 两阶段提交的三步与两个崩溃点 | 无论崩在哪一步，裁决依据都是 binlog 是否完整

#### 5.2 三步（实际是两个阶段 + 一次裁决）

```
① 【prepare】InnoDB 写完 redo，但把状态标成 prepare，不算提交
② 【提交阶段】执行器写 binlog 并落盘
③            binlog 落盘成功后，通知 InnoDB 把 redo 改成 commit
```

#### 5.3 反证：不用 2PC，两种顺序各有一个后果

【推导】假设不做两阶段提交，只是简单地把两次写按某个顺序做：

| 顺序 | 崩溃点 | 后果 |
|---|---|---|
| **先 redo 后 binlog** | redo 写完、binlog 没写就崩 | 重启后 redo 重放 → **主库有这次更新**；binlog 没有 → **从库没有** → **主库多、从库少** |
| **先 binlog 后 redo** | binlog 写完、redo 没写就崩 | InnoDB 认为未提交 → **主库回滚**；binlog 已记录 → **从库执行了** → **从库多、主库少** |

**两种顺序都会造出主从不一致**——这就是不做 2PC 的必然后果。

#### 5.4 一句话收口

> 【推导】**两阶段提交把两份日志"捆绑"成一个原子操作：要么都成功，要么都失败。** 这是它唯一的存在理由——不是"规范要求这么做"，而是**不做就一定会在崩溃窗口里造出主从不一致**。

**到这里你应该能回答**：为什么不用两阶段提交，也"大多数时候没问题"？

> 因为**崩溃窗口很窄**，概率低。但**它一定会发生**——而数据库的可靠性要求不能建立在"概率低"上。

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "binlog 能单独保证 crash-safe" | 【推导】不能。它不在 InnoDB 内、不记物理页变化，必须靠 2PC 与 redo 配合 |
| "redo 是无限的，会一直追加" | 【事实】**固定大小循环写**，会覆盖；边界靠 check point 推进 |
| "有 redo 就不需要 binlog" | 【事实】职责不同：redo 只服务**崩溃恢复**（且用完即弃）；binlog 服务**复制与时间点恢复**（要长期保留） |
| "两阶段提交是为了保证 ACID" | 【取舍】它保证的是**两份日志的逻辑一致**（进而保证主从一致）。ACID 里的 A 和 D 分别由 undo 和 redo 负责，不是 2PC 的职责 |
| "刷盘参数设 0 最快，性能最好" | 【取舍】是快，但**掉电丢最近 1 秒**。取舍标准是**业务能不能容忍丢这 1 秒**（埋点/日志能忍，涉及钱的不能），不是"哪个快选哪个" |
| "PG 也有 redo / undo / binlog 三套日志" | 【事实】**PG 只有 WAL 一套**。旧版本留在堆里靠 VACUUM 回收，复制也靠 WAL——**所以 PG 根本不存在"两份日志要协调"的问题，也就没有 prepare/commit 这套两阶段日志状态**（[[母题-P11-WAL与checkpoint]]） |

## 二、自测

**Q1（计算）**：SSD 上单次 `fsync` 约 **0.2 ms**。生产配置 `innodb_flush_log_at_trx_commit=1`（每次提交 fsync）。

问：**单条连接串行提交**的 TPS 上限是多少？MySQL 靠什么机制突破它？

**A1**：

- 上限 = 1 / 0.0002s = **约 5000 TPS**
- **瓶颈是 fsync 的等待，不是 CPU**

**突破靠「组提交（group commit）」**：把**并发到达的多个事务的 fsync 合并成一次**——10 个事务一起提交，只付一次 0.2ms，等效 TPS 提到约 5 万。

【推论】**这就是为什么"双一"配置在生产上可行**：安全的代价被组提交摊薄了。**反过来说，如果业务是"单线程串行提交"（没有并发可以合并），双一的代价就是实打实的**——

```text
"双一"每提交要等 2 次 fsync：redo 一次 + binlog 一次
= 2 × 0.2 ms = 0.4 ms
单线程串行提交上限 = 1 / 0.0004 = 约 2500 TPS
```

正好比"只等一次 fsync"的 5000 TPS **再腰斩一半**。取舍要看并发行不行。

**Q2（判读）**：数据库在下面两个时刻断电，重启后分别是什么结果？对主从一致性各有什么影响？

① 写完 redo（prepare）、**binlog 还没写**
② binlog 已写完整、**redo 还是 prepare**

**A2**：

| 崩溃点 | redo 状态 | binlog 状态 | 恢复动作 | 一致性 |
|---|---|---|---|---|
| ① | prepare | **不完整** | **回滚**（undo） | 主库、从库**都没有**这次更新 → **一致** |
| ② | prepare | **完整** | **提交**（把 redo 改成 commit） | 主库、从库**都有**这次更新 → **一致** |

**两个窗口都收敛到一致**——这正是两阶段提交的作用。

**关键**：**裁决依据只有一个——binlog 是否完整。** 因为 binlog 完整就意味着"这个事务已经对外宣布过成功了"（binlog 是复制的源头），**必须让它生效**。

**Q3（计算）**：redo 日志组总大小 **4GB**，业务写入速率约 **100 MB/s**（按 redo 生成量估）。

问：**多久会绕满一圈？** 这个数字对"崩溃后要重放多少"意味着什么？

**A3**：

- 绕一圈时间 = 4 GB ÷ 100 MB/s = **约 41 秒**
- 含义：**check point 最多落后 41 秒的日志**。崩溃重启时，**最坏要从 41 秒前的位置开始重放**（数据页落盘位点再靠后，实际重放量可能更小）

【推论】**redo 组的大小直接决定"崩溃恢复时间上限"**：调大 redo 组 → 恢复时间上限变长但写入更不容易被 check point 追上；调小则相反。**这是同一组参数的两面**（[[母题-M12-崩溃恢复]]）。

**Q4（纠错）**：下面这段话哪里错了？

> "既然 binlog 也记录了所有的修改，那只要保证 binlog 落盘就够了，redo log 可以省掉。"

**A4**：**三处都错。**

1. **binlog 不记物理页变化。** 它是**逻辑日志**（SQL 或行前后镜像），**没法用来把内存里的数据页恢复成正确状态**——恢复需要知道"哪个页的哪个偏移要变成什么"。
2. **binlog 在 Server 层，不在 InnoDB 里。** 它的写入时机与 InnoDB 的提交不是一件事，**单独依赖它无法保证 InnoDB 内部状态一致**。
3. **职责不同**：redo 服务**崩溃恢复**（用完即弃、循环写）；binlog 服务**复制与时间点恢复**（长期保留、追加写）。**去掉任何一个都会塌掉一块能力。**

**正确说法**：**redo 保证 InnoDB 能恢复到最新状态，binlog 保证复制和时间点恢复能工作，两阶段提交保证这两份日志逻辑一致。**

**Q5（纠错）**：下面这段话哪里错了？

> "MySQL 和 PostgreSQL 都是关系数据库，所以都有 redo log、undo log 和 binlog，崩溃恢复的原理也一样。"

**A5**：**"都有三套日志"是错的。**

**PostgreSQL 只有一套 WAL。** 它：

- 旧版本**留在堆里**，靠 **VACUUM** 回收（没有独立 undo 表空间）
- 复制**也靠 WAL**（流复制 / WAL 归档），**不需要第二份逻辑日志**

【推导】**由此推出一连串差异**：

| | MySQL | PostgreSQL |
|---|---|---|
| 日志套数 | redo + undo + binlog | **WAL 一套** |
| 有没有"两份日志要协调" | **有** → 需要两阶段提交 | **没有** → 不存在这个问题 |
| 复制依赖 | **binlog**（逻辑） | **WAL**（物理） |

**所以"PG 也有 prepare/commit 两阶段日志状态"是明确错误**——那是 MySQL 为了协调两份日志才发明的东西。

## 三、面试输出（学完再看）

**一句话结论**：三条日志各管一件事——**undo 管回滚和 MVCC 旧版本（前镜像），redo 管崩溃恢复（后镜像、物理、循环写），binlog 管复制与时间点恢复（逻辑、追加写、Server 层）**。用 **WAL** 把"随机写数据页"换成"顺序写日志"，同时拿到性能和崩溃安全性。而**两阶段提交存在的唯一理由，是让 redo 和 binlog 逻辑一致**——不做的话，两个崩溃窗口分别造出"主库多从库少"和"从库多主库少"。

**恢复关键词**：WAL 换掉随机写 / 顺序 vs 随机差 2–3 个数量级 / undo 前镜像 / redo 后台镜像·循环写 / binlog 逻辑·追加写·Server 层 / redo 用完即弃所以循环，binlog 长期保留所以追加 / write pos 追上 check point = 写入卡顿 / 先刷页再推 check point / 双一 / prepare → binlog → commit / 崩溃窗口 = 主从不一致 / binlog 是否完整 = 唯一裁决依据

**核心不变量 / 主线**：
**"安全"的标志不是"数据在磁盘上"，而是"修改这件事已经落盘了"。** 数据库用"顺序写日志"换掉"随机写数据页"——这一步同时给出了性能（顺序 vs 随机的量级差）和崩溃恢复能力（WAL）。而只要有两份日志，就必然需要一次裁决（2PC）。

**完整回答骨架**：为什么不能直接写磁盘（顺序 vs 随机的量级差）→ WAL 是什么、换来了什么 → 三条日志各属于哪一层、记什么、什么文件形态、什么职责 → redo 为什么循环写（用完即弃）→ 双一配置与组提交 → 两份日志必须一致 → 2PC 三步 → 两个崩溃窗口反证 → 方言（PG 只有 WAL）

**完整回答（口述稿）**：
三条日志各管一件事：undo 管回滚和 MVCC 的旧版本，是前镜像，在引擎层；redo 管崩溃恢复，是后镜像、物理日志、固定大小循环写、用完即弃；binlog 管复制和时间点恢复，是逻辑日志、追加写、在 Server 层。它们靠 WAL 串起来：把「随机写数据页」换成「顺序写日志」，一次拿到性能和崩溃安全。

两阶段提交存在的唯一理由是让 redo 和 binlog 逻辑一致。不做的话有两个崩溃窗口：redo 提交了但 binlog 没写 → 主库多从库少；binlog 写完了但 redo 没提交 → 从库多主库少。2PC 用 prepare → 写 binlog → commit 三步堵住这两个窗口，崩溃后由 binlog 的完整性裁决。

刷盘参数要会取舍：innodb_flush_log_at_trx_commit 和 sync_binlog 都设 1 是双一，最安全也最慢；设 0 快，但掉电会丢最近 1 秒——取舍标准是业务能不能容忍丢这 1 秒（埋点能忍，涉及钱的不能），不是「哪个快选哪个」。

边界：binlog 单独保证不了 crash-safe（它不在 InnoDB 内、不记物理页变化）；redo 是循环写会覆盖，边界靠 check point 推进；PG 只有 WAL 一套日志。

**分层要点**：
- **结论**：undo 管前镜像（回滚 + MVCC），redo 管后镜像（崩溃恢复、循环写），binlog 管复制与时间点恢复（追加写）；2PC 只为两份日志逻辑一致。
- **推导链**：随机写慢 → WAL 换成顺序写 → 三条日志分层归属 → redo 用完即弃 vs binlog 长期保留 → 两份日志必须一致 → 2PC 三步堵住两个崩溃窗口。
- **量化**：双一（两个参数都设 1）最安全最慢；设 0 时掉电丢最近 1 秒。
- **边界与常见误解**：binlog 不能单独 crash-safe；redo 会覆盖（靠 check point 推进）；2PC 保证的不是 ACID，A 和 D 分别由 undo、redo 负责；PG 只有 WAL。

**追问**（先说后看）

1. **redo 循环写，为什么不怕覆盖掉还没刷盘的日志？** —— **check point 只在脏页真正刷盘后才前移**；write pos 追上 check point 时**必须停下来先刷脏页**。顺序是"先刷页 → 再推 check point → 才释放空间"，**不能反过来**。
2. **`innodb_flush_log_at_trx_commit` 设 0/2 能换多少性能？** —— **必须拿压测数据说话，不能凭感觉。** SDD 时代 `fsync` 成本下降，1 与 2 的差距远小于机械盘时代，**所以现在更多是直接上"双一"**。这是"按业务定口径"而不是"按性能定口径"。
3. **binlog 有哪几种格式？生产用哪个？** —— Statement / Row / Mixed；**现在主流是 Row**（数据安全优先），Statement 只在日志体积敏感且 SQL 确定时才考虑。
4. **redo log 是无限增长的吗？** —— 不是。固定大小循环写，边界靠 check point 推进。

**同类变体**

- 「redo log 和 binlog 有什么不同？」——四条按顺序说完就是完整答案：**所属层 / 内容（物理 vs 逻辑）/ 文件形态（循环写 vs 追加写）/ 职责（崩溃恢复 vs 复制）**
- 「什么是 WAL，好处是什么？」——日志先行；**两个好处缺一不可**：把随机写换成顺序写（性能）+ 提供崩溃恢复（可靠性）
- 「两阶段提交崩在中间会怎样？」——见 Q2 的两个窗口
