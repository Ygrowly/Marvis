# 母题 M11 · 三日志与两阶段提交

> **模块**：MySQL / 日志与崩溃恢复
> **所属主线**：四 · 日志与持久化（提交过的数据，服务挂了为什么不该丢）
> **关联母题**：[[母题-M12-崩溃恢复]] · [[母题-M10-锁与死锁]]
> **素材来源**：`raw/后端视角复盘_MySQL：为什么它能查得快、并发稳、还扛得住.md` 第三条主线（undo / redo / binlog 分工）+ `raw/Mysql面试题-2026-09-07T004734+0800.md` 第 5 节（5.1–5.9）

**题目**：用户下单，接口返回「提交成功」。一秒后机器断电。重启后，这条订单还在吗？为什么？

**母题**：redo / undo / binlog 各管什么？两阶段提交为什么必要？

**为什么重要**：这是**「会用数据库」和「懂数据库为什么不丢数据」的分界线**。它也是唯一一条能把原子性、持久性、主从复制三件事串起来的线——**答不出这条，前面讲的 ACID 就只是四个字母**。

**一句话结论**：三条日志各管一件事——**undo 管回滚 + MVCC 旧版本，redo 管崩溃恢复（保证已提交不丢），binlog 管复制与时间点恢复**；而**两阶段提交存在的唯一理由，是让 redo 和 binlog 在逻辑上绝对一致**——否则崩溃时会造出「主库有、从库没有」或「从库有、主库没有」的数据。

**恢复关键词**：WAL 日志先行 / undo 回滚 / redo 循环写 + checkpoint / binlog 追加写 / prepare → commit / 逻辑一致

**核心不变量 / 主线**：
**先写日志，再写数据页（WAL）。** 只要「修改这件事」已经顺序落盘，内存里的修改就是安全的——数据库用「顺序写日志」换掉了「随机写数据页」，这是所有崩溃恢复能力的地基。

**完整回答骨架**：为什么需要 WAL → 三日志分工（一句话 × 3）→ redo 的环形结构与刷盘参数 → binlog 的三种格式 → 两阶段提交的两个阶段 → 不做会怎样（两种顺序各一个后果）

## 原理分解

### 一、为什么需要 WAL（Write-Ahead Logging）

修改数据时不直接改磁盘数据页（随机 IO 太慢），而是：

```
改内存（Buffer Pool）→ 把"改了什么"顺序写入 redo log → 提交时保证 redo 落盘
```

**只要 redo 落盘成功，这次修改就是安全的**——即使数据页还没刷回磁盘时崩溃，重启后也能用 redo 把它重放回来。**用顺序写换随机写，同时拿到崩溃安全性**，这是 WAL 的全部价值。

### 二、三日志分工（必须能一句话说清）

| 日志 | 所属层 | 记录什么 | 物理特性 | 核心职责 |
|---|---|---|---|---|
| **undo log** | InnoDB | 数据修改**前**的旧值 | — | **回滚** + 给 MVCC 提供旧版本 |
| **redo log** | InnoDB | 数据页的**物理**修改（"某页某偏移写成什么"） | **固定大小、循环写**，会覆盖 | **崩溃恢复**（持久性） |
| **binlog** | **Server 层** | **逻辑**操作（SQL / 行变更前后镜像） | **追加写**，写满切新文件，不覆盖 | **主从复制** + 时间点恢复 |

放到工单/订单系统里最好记：

- 状态更新失败要能撤销 → **undo**
- 更新成功但机器崩了不能丢 → **redo**
- 主从同步和备份恢复 → **binlog**

**一条高价值追问**：「binlog 能不能单独保证 crash-safe？」——**不能**。它不在 InnoDB 内部，写入时机与 redo 不同步；单独依赖它，崩溃时会不一致。**它必须靠两阶段提交与 redo 配合。**

### 三、redo 的环形结构与刷盘参数

redo 文件是**固定大小、循环写**的环形，两个指针：

- **write pos**：当前写到哪。
- **check point**：已经刷盘（脏页已落盘）的位置之后一格。

`write pos → check point` 之间是空闲区（可写新日志）；`check point → write pos` 之间是**待刷盘**的记录，**如果不刷就会被新记录覆盖**。危险场景就是「write pos 追上 check point」——此时必须停下来刷脏页，**表现为写入卡顿**。

**刷盘时机由 `innodb_flush_log_at_trx_commit` 控制**：

| 值 | 行为 | 代价 |
|---|---|---|
| **1（默认）** | 每次提交都 fsync 落盘 | 最安全，最慢 |
| 0 | 提交只写内存 buffer，后台每秒刷 | 最快，掉电丢最近 1 秒事务 |
| 2 | 提交写入 OS 缓存，不立刻 fsync | 进程崩不丢，**整机掉电会丢** |

**binlog 侧对应 `sync_binlog`**：0 = 交给系统决定；N = 每 N 个事务刷一次；**1 = 每次提交刷**。生产要金融级一致就是 **`flush_log_at_trx_commit=1` + `sync_binlog=1`**，代价是吞吐下降。

### 四、binlog 的三种格式

| 格式 | 记什么 | 优点 | 风险 |
|---|---|---|---|
| **Statement** | 原始 SQL 语句 | 日志小 | 含 `UUID()` / `NOW()` 等非确定函数会导致**主从漂移** |
| **Row** | 每行修改前后的具体内容 | 复制绝对精确 | 日志量大（批量 UPDATE 会暴涨） |
| **Mixed** | 自动判断，安全用 Statement、危险切 Row | 平衡 | 判断逻辑需要理解 |

### 五、两阶段提交：为什么非它不可

提交分两步：

```
① 准备（Prepare）：InnoDB 写完 redo log，但状态标记为 prepare，不提交
② 提交（Commit）：执行器写 binlog → binlog 落盘成功 → 通知 InnoDB 把 redo 改成 commit
```

**如果不这么做，两种顺序各有一个后果：**

| 顺序 | 崩溃点 | 结果 |
|---|---|---|
| 先写 redo，再写 binlog | redo 写完、binlog 没写就崩 | 重启后 redo 重放 → **主库有这次更新**；binlog 没有 → **从库没有**，主从多了/少了一次更新 |
| 先写 binlog，再写 redo | binlog 写完、redo 没写就崩 | InnoDB 认为事务未提交 → **主库回滚**；binlog 已记录 → **从库执行了**，从库多出一次主库不存在的更新 |

**一句话收口**：两阶段提交把两份日志「捆绑」成原子操作，**要么都成功，要么都失败**——这就是它唯一的存在理由。

## 二、扩展：类似题与追问

**类似题**

1. 「redo log 和 binlog 有什么不同？」——**所属层**（InnoDB vs Server）、**内容**（物理 vs 逻辑）、**文件形式**（循环写覆盖 vs 追加写不覆盖）、**职责**（崩溃恢复 vs 复制与恢复）。四条按顺序说完就是完整答案。
2. 「什么是 WAL，好处是什么？」——日志先行；把随机写换成顺序写（**提升写入性能**）+ 提供崩溃恢复能力。两个好处缺一不可。
3. 「binlog 有哪几种格式？」——见上表；**补一句生产现实**：现在主流是 Row（数据安全优先），Statement 只在日志体积敏感且 SQL 确定时才考虑。

**追问链**

- 追问一层：**「redo 循环写，为什么不怕把还没刷盘的日志覆盖掉？」**——因为循环写的边界由 check point 决定，而 check point 只在**脏页真正刷盘后**才前移；write pos 追上 check point 时必须先停下刷脏页。**顺序是"先刷页、再推 check point、再释放空间"，不是反过来。**
- 追问二层：**「刷盘参数设 0/2 能换来多少性能？」**——这是可测量的：SSD 上 1 与 2 的差距通常远小于机械盘时代（fsync 成本下降），所以**现代生产更多是「1 + 1」直接拉满安全**；真要做取舍，也必须拿压测的 TPS 数据说话，不能凭感觉选。**这条还能顺手接住"你怎么做技术选型"的面试叙事。**
