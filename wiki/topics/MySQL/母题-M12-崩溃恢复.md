**题目**：数据库在「事务提交到一半」时断电。重启后它怎么知道哪些事务该重做、哪些该回滚？会不会把已经提交的又回滚掉？

**母题**：崩溃重启后 MySQL 怎么恢复数据？为什么不会丢已提交的、也不会错回滚？

## 一、教材

### 1. 前提：先把"恢复"这个问题拆小

#### 1.1 崩溃瞬间，一个事务只可能是三种状态【事实】

这是全卡的地基。**不要一上来就想"恢复算法"，先问"崩溃那一刻，每种状态留下了什么痕迹"。**

| 崩溃时的状态 | 数据页 | 日志留下了什么 | 恢复动作 |
|---|---|---|---|
| **还没提交** | 可能已改内存 | redo 里没有 commit、binlog 没写 | **undo 回滚** |
| **已经提交** | **可能还没落盘** | redo 已 commit、binlog 已完整 | **redo 重放补上** |
| **提交到一半** | 不确定 | redo 是 **prepare**，binlog 可能完整也可能不完整 | **看 binlog 裁决** ← 本题题眼 |

**注意第二行**："已提交"的事务，它的**数据页也可能还没落盘**（因为 WAL —— 提交只保证日志落盘，不保证数据页落盘，[[母题-M11-三日志与两阶段提交]]）。**这正是需要 redo 重放的原因。**

#### 1.2 由此得到恢复只能回答三个问题【推导】

```
① 哪些该重做？        → 已提交的（redo 重放）
② 哪些该回滚？        → 未提交的（undo 回滚）
③ 怎么保证重做不做两遍？→ 幂等（下一个问题）
```

**上面那张三状态表已经把 ① ② 回答完了**：**"状态"来自日志，"动作"由状态决定。** 恢复的每一步都不是"猜"出来的。

**到这里你应该能回答**：为什么说"恢复不会把已提交的事务回滚掉"？

> 因为**已提交的事务在 redo 里留下了 commit 标记**——这不是猜，是**读日志读出来的确定结论**。

### 2. redo 重放：幂等从哪里来

#### 2.1 恢复为什么可能"做两遍"

【推导】崩溃可能发生在恢复过程中（比如重放到一半又断电）。**如果重放不是幂等的，第二次恢复就会把某些改动应用两遍**——某些操作（比如"在某个位置追加"）做两遍就错了。

#### 2.2 LSN：让"是否已做过"变得可判断【事实】

**LSN（Log Sequence Number，日志序列号）**：日志的单调递增编号。**关键点**：**每个数据页的头部也存着自己最后一次被修改对应的 LSN。**

于是重放一条 redo 之前，只要比一次：

```
页.LSN >= redo.LSN   →  这条改动已经落盘了 → 跳过
页.LSN <  redo.LSN   →  还没应用 → 写进内存页（并更新页的 LSN）
```

::figure crash-recovery.svg | 崩溃恢复的四步 | 定位起点 → redo 重放（按 LSN 跳过）→ 用 binlog 裁决 prepare → undo 回滚未提交

#### 2.3 幂等的本质（这句话比结论值钱）

> 【推导】**幂等不是"不去做"，而是"做之前能判断是否已做过"。**

**redo 重放的幂等，不是靠锁、不是靠"只允许做一次"的机制，而是靠"每个页自带 LSN 这个状态标记"。**

【类推】这个模式可以迁移到任何重放系统：

- 业务层的**幂等键**：写之前先查"这个请求处理过没有"
- **ActionReceipt**（RuleArena 的做法）：把"已经执行过"变成一条可查的记录
- 消息队列的**去重表**：同一模式

**所以"怎么保证幂等"的标准答案不是"加锁"，而是"留下一个能判断已做过的状态"。**

### 3. undo 回滚，以及顺序为什么不能反

redo 重放结束后，内存里已经包含了「已提交」和「prepare 待裁决」的修改。接下来：

- **已提交** → 保留
- **未提交** → 用 **undo log 反向撤销**（undo 存的是前镜像，正好用来恢复原状）

**顺序必须是「先 redo 重放，再 undo 回滚」**【推导】**——** 反过来会出问题：

> 如果先 undo：一个**已提交但数据页未落盘**的事务，在内存里被当成"未提交"处理（因为数据页还没体现它），于是被回滚掉。**这就是丢已提交数据。**
>
> **redo 重放的作用正是"先把所有已提交的事务在内存里补出来"**，让后续的撤销判断有正确的输入。

**到这里你应该能回答**：为什么"先 undo 再 redo"会丢数据？

### 4. 题眼：prepare 状态怎么裁决

#### 4.1 为什么 InnoDB 自己判不了【推导】

redo 里状态是 `prepare` 的事务，处于一个**"日志说它写过了，但没人说它算不算成功"**的中间态。InnoDB 光看自己的 redo，**无法判断该提交还是回滚**。

**决定权在 binlog** —— 因为两阶段提交的第三步（"把 redo 改成 commit"）**必须在 binlog 落盘成功之后才能做**。所以：

```
redo = prepare
   ├─ binlog 完整（该事务的 binlog 记录已写完，可校验）
   │     → 视为成功：把 redo 改成 commit，数据保留
   └─ binlog 不完整 / 不存在
         → 视为失败：用 undo 回滚
```

#### 4.2 为什么这个判据是对的【推导】

按 2PC 的顺序反推：

| binlog 状态 | 说明 2PC 走到哪一步 | 逻辑结论 |
|---|---|---|
| **完整** | 第二步成功了 | **这个事务已经对外宣布过成功**（binlog 是复制的源头）→ **必须让它生效**，否则从库执行了而主库没有 |
| **不完整** | 第二步没成功 | **这个事务从未对外宣布**→ **必须回滚**，否则主库有效而从库没有 |

【取舍】**这是"崩溃恢复"和"主从一致性"在同一处收口的地方——不是两套逻辑，是一套。**

### 5. 恢复要多久（把成本算出来）

【推导】恢复时间 ≈ **需要重放的 redo 量 ÷ 重放速度**。而"需要重放的量"由 **check point 的位置**决定：

```
check point 越靠后（越新）→ 需要重放的 redo 越少 → 恢复越快
```

**这看起来是"让 check point 越新越好"，但代价在另一边**【取舍】：

| 让 check point 更频繁前移 | 结果 |
|---|---|
| 需要**更频繁地刷脏页** | 正常运行时多了大量**随机 IO**（写数据页是随机的，M11 的 1.2）→ **写入性能下降** |
| 崩溃恢复时间 | **变短** |

> **同一组参数，同时决定"恢复时间"和"正常运行时的刷脏压力"。不能只调一边。**
>
> **这又是一个"取舍而不是最优解"的地方**——面试时能说出这两面，比答"把 check point 调密一点"有价值得多。

### 6. 生产配置：为什么主库都配「双一」

| 参数 | 值 | 作用 |
|---|---|---|
| `innodb_flush_log_at_trx_commit` | **1** | 每次提交 `fsync` redo |
| `sync_binlog` | **1** | 每次提交 `fsync` binlog |

【推导】**两个都为 1，事务的"提交成功"才算真的落到磁盘**——这才是"接口返回成功之后断电也不丢"的前提。

**只配一个会怎样**：redo 保证了主库能恢复，但 binlog 丢了 → **从库缺数据**；或者反过来。**两边的安全级别必须匹配，否则一致性从最弱的那一环漏出去。**

### 7. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "恢复是靠猜或者靠事务开始时间" | 【推导】靠**日志状态**。崩溃瞬间每个事务只有三种状态，**每种状态都有明确的日志痕迹**，动作由痕迹决定 |
| "已提交的事务肯定已经在磁盘上了" | 【事实】不一定。**WAL 只保证日志落盘**，数据页可能还在内存里 —— **这正是要 redo 重放的原因** |
| "重放和回滚的顺序无所谓" | 【推导】**必须先 redo 重放再 undo 回滚**。反过来会在"已提交但页未落盘"时丢掉已提交的数据 |
| "恢复中断（又崩了）会出问题" | 【推导】没关系。redo 重放**按页 LSN 判断是否已应用**，是幂等的；重启后从最新 check point 继续即可。**系统不怕反复崩，怕的是重放不幂等** |
| "恢复时间长是磁盘慢" | 【取舍】更主要的原因是 **check point 落后太多**（要重放的日志多）。**而 check point 的推进频率同时影响正常写入性能**，不能单边调 |
| "PG 也有 prepare/commit 的两阶段日志状态" | 【事实】**没有**。PG 只有 WAL 一套日志，**不存在"两份日志要协调"的问题**，所以没有 2PC 的日志状态；它的恢复是"重放 WAL + 回滚未提交元组"（[[母题-P11-WAL与checkpoint]]） |

## 二、自测

**Q1（计算）**：redo 生成速率约 **100 MB/s**，崩溃时 **check point 落后 30 秒**。重放（顺序读 + 应用）速度按 **300 MB/s** 估。

问：恢复大约要多久？想缩短它，代价在哪？

**A1**：

- 待重放量 = 100 MB/s × 30s = **3 GB**
- 恢复时间 ≈ 3 GB ÷ 300 MB/s ≈ **10 秒**

**缩短它的唯一手段是让 check point 更靠前**——即**更频繁地把脏页刷到磁盘**。

【代价】刷脏页是**随机写**（M11 的 1.2：随机写比顺序写慢 2–3 个数量级）。check point 推得越勤，**正常运行时的写入性能越差**。

**所以这是同一组参数的两面**：

| check point 推进 | 恢复时间 | 正常运行写入性能 |
|---|---|---|
| 更频繁 | **变短** | **变差** |
| 更少 | 变长 | 变好 |

**没有"都变好"的选项**——面试时能把这句说出来，比背"把 check point 调密"有价值得多。

**Q2（判读）**：重启后，日志里发现三个事务：

① redo 有 commit 标记 ② redo 是 prepare，且它的 binlog 记录完整 ③ redo 是 prepare，binlog 里找不到它

分别怎么处理？为什么？

**A2**：

| 事务 | 状态 | 处理 | 依据 |
|---|---|---|---|
| ① | 已提交 | **保留**（必要时 redo 重放把数据页补上） | redo 里的 commit 标记 |
| ② | 提交到一半 | **提交**（把 redo 改成 commit） | 2PC 第二步成功了 = **已对外宣布过成功**，必须生效，否则从库有主库没有 |
| ③ | 提交到一半 | **回滚**（用 undo 撤销） | 2PC 第二步没成功 = **从未对外宣布**，必须回滚，否则主库有从库没有 |

**三者的动作都不是猜的**——**状态来自日志，动作由状态决定**。这就是"恢复靠自证，不靠猜"。

**Q3（判读）**：恢复进行到一半，**又断电了**。再次重启时会不会出问题？为什么？

**A3**：**不会出问题。**

因为 **redo 重放是幂等的**：每条 redo 应用前都**比较数据页头部的 LSN 与这条 redo 的 LSN**——已经应用过的（`页.LSN >= redo.LSN`）**直接跳过**。所以再重启时从最新的 check point 继续重放即可，**不会重复应用**。

**幂等的来源是"每个页自带 LSN 这个状态标记"，不是"只允许做一次"的锁。**

【推论】**系统不怕反复崩，怕的是重放不幂等。** 这个判据可以迁移：设计任何重试/重放机制时，先问"能不能判断已做过"，而不是先问"怎么保证只做一次"。

**Q4（纠错）**：下面这段话哪里错了？

> "崩溃恢复的原理是：比较各个事务的开始时间，开始得早且日志写完了的就提交，没写完的就回滚。"

**A4**：**"比较开始时间"是错的，恢复不看时间，看状态。**

准确的做法是**读日志留下的状态标记**：

| 日志里的状态 | 结论 |
|---|---|
| redo 有 **commit** | 已提交 → 保留 |
| redo 是 **prepare** + binlog **完整** | 视为提交 |
| redo 是 **prepare** + binlog **不完整** | 回滚 |
| redo **没有该事务的提交痕迹** | 未提交 → 回滚 |

**为什么不能靠时间**：事务的"开始时间"和"是否提交"**没有任何必然关系**——一个很早就开始的事务可能一直没提交；一个刚开的事务可能已经提交。

**"依赖时间推断状态"在分布式系统里是典型的错误设计**——**状态必须被显式记录，而不是被推断。** 这一点同样适用于业务层的幂等设计。

**Q5（纠错）**：下面这段话哪里错了？

> "PostgreSQL 崩溃恢复也是靠 redo 重放 + 用 binlog 裁决 prepare 事务，和 MySQL 一样。"

**A5**：**"靠 binlog 裁决 prepare"是错的——PG 没有 binlog，也没有 prepare/commit 这套日志状态。**

**PostgreSQL 只有 WAL 一套日志**：

- 恢复 = **重放 WAL + 回滚未提交的元组**
- 复制也走 WAL（流复制 / WAL 归档），**不依赖第二份逻辑日志**
- 旧的元组版本**留在堆里**，靠 VACUUM 回收

【推导】**所以 PG 从一开始就不存在"两份日志要协调"的问题** —— 而**两阶段提交恰恰是 MySQL 为了解决这个问题才发明的**。

| | MySQL | PostgreSQL |
|---|---|---|
| 日志 | redo + undo + binlog | **WAL 一套** |
| 恢复关键步骤 | redo 重放 → **用 binlog 裁决 prepare** → undo 回滚 | **重放 WAL + 回滚未提交元组** |
| 一致性协调 | **需要**（2PC） | **不需要**（单一日志天然一致） |

**把 MySQL 的"binlog 裁决"套到 PG 上，是把两边最容易混的地方说反了。**

## 三、面试输出（学完再看）

**一句话结论**：恢复 = **redo 重放 + undo 回滚**。重启后从 check point 起顺序重放 redo（**每页自带 LSN，已落盘的直接跳过，所以重放幂等**），把**已提交**的事务补上；再用 undo 把**未提交**的撤销。**提交到一半（prepare）的事务由 binlog 的完整性裁决**——binlog 完整就提交，不完整就回滚。**顺序不能反：必须先 redo 再 undo。**

**恢复关键词**：崩溃时只有三种状态 / 已提交的页也可能还在内存 / 动作由日志状态决定、不靠猜 / **幂等 = 做之前能判断是否已做过** / 页 LSN 比较 / prepare 靠 binlog 裁决 / 先 redo 后 undo / check point 位置决定恢复时长（且与写入性能是同一组参数的两面）/ 双一

**核心不变量 / 主线**：
**恢复的正确性不靠"猜"，靠"日志状态"。** 每个事务在崩溃瞬间只有三种可能——没开始、已提交、提交到一半。**前两种由日志标记无歧义地确定，第三种由两阶段提交给出的裁决规则唯一确定。**

**完整回答骨架**：崩溃瞬间的三状态表 → 恢复只回答三个问题（重做谁/回滚谁/怎么不重复）→ redo 重放为什么幂等（页 LSN）→ **幂等的本质是"能判断已做过"而不是"只做一次"** → 为什么必须先 redo 后 undo → prepare 靠 binlog 完整性裁决（并解释为什么这个判据对）→ 恢复时间与 check point 的两面性 → 双一 → 方言（PG 没有 binlog 裁决这套）

**完整回答（口述稿）**：
崩溃瞬间每个事务只有三种状态：已提交、未提交、提交到一半（prepare）。恢复只回答三个问题：重做谁、回滚谁、怎么保证不重复做。

答案是 redo 重放 + undo 回滚，顺序不能反。先从 check point 起顺序重放 redo：每页自带 LSN，已经落盘的页直接跳过，所以重放是幂等的——幂等的本质是「能判断出已经做过了」，而不是「只做一次」。这也是为什么系统不怕反复崩，只怕重放不幂等。

然后用 undo 把未提交的事务撤销。必须先 redo 再 undo：反过来会在「已提交但数据页还没落盘」的情况下把已提交的数据弄丢——WAL 只保证日志落盘，数据页可能还在内存里，这正是要重放的原因。

提交到一半的事务由 binlog 的完整性裁决：binlog 完整就提交，不完整就回滚。

恢复时间长的根因通常不是磁盘慢，而是 check point 落后太多、要重放的日志多；但 check point 的推进频率同时影响正常写入性能，不能单边调。PG 没有 binlog 裁决这一套。

**分层要点**：
- **结论**：redo 重放（幂等）+ undo 回滚，顺序必须先 redo 后 undo；prepare 事务由 binlog 完整性裁决。
- **推导链**：三状态表 → 日志痕迹决定动作 → redo 按页 LSN 判重放 → 再用 undo 撤销未提交 → prepare 看 binlog 完整性。
- **量化**：恢复时间 ≈ 从 check point 起要重放的日志量，由 check point 落后程度决定。
- **边界与常见误解**：恢复靠日志状态，不靠猜或开始时间；已提交的不一定已在磁盘上（WAL 只保证日志落盘）；顺序无所谓 ×（反过来会丢已提交数据）；恢复中再崩没关系（重放幂等）；恢复慢常因 check point 落后而非磁盘慢；PG 没有 binlog 裁决。

**追问**（先说后看）

1. **恢复要重放多久？** —— 取决于 **check point 的位置**。它越新，要重放的越少、恢复越快；但推进它需要更频繁刷脏页，**代价是正常运行时更多的随机 IO**。**同一组参数的两面。**
2. **恢复途中又崩了怎么办？** —— **没关系**。重放按页 LSN 跳过已应用的，是幂等的，重启后从最新 check point 继续。**不怕反复崩，怕重放不幂等。**
3. **为什么不会重复执行已提交的事务？** —— **数据页自带 LSN，重放前先比较**，已落盘的直接跳过。
4. **主从不一致是怎么被崩溃窗口造出来的？** —— 不做 2PC 时的两个反向窗口：redo 写完 binlog 没写就崩 → 主库有从库没有；binlog 写完 redo 没写就崩 → 从库有主库没有（M11）。

**同类变体**

- 「MySQL 宕机重启后为什么不会重复执行已提交事务？」——页 LSN 比较（幂等重放的标准答案）
- 「redo log 是无限增长的吗？」——不是，固定大小循环写，边界靠 check point
- 「恢复过程中最怕什么？」——**怕重放不幂等**，不是怕崩
