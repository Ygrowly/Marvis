# 母题 M12 · 崩溃恢复

> **模块**：MySQL / 日志与崩溃恢复
> **所属主线**：四 · 日志与持久化（提交过的数据，服务挂了为什么不该丢）
> **关联母题**：[[母题-M11-三日志与两阶段提交]] · [[母题-M8-隔离级别与ACID]]
> **素材来源**：`raw/后端视角复盘_MySQL：为什么它能查得快、并发稳、还扛得住.md` 第三条主线 + `raw/Mysql面试题-2026-09-07T004734+0800.md` 5.2 / 5.5 / 5.9 / 5.10

**题目**：数据库在「事务提交到一半」时断电。重启后它怎么知道哪些事务该重做、哪些该回滚？会不会把已经提交的又回滚掉？

**母题**：崩溃重启后 MySQL 怎么恢复数据？为什么不会丢已提交的、也不会错回滚？

**为什么重要**：M11 讲的是「日志怎么写」，这一题讲的是「日志怎么被读回来用」——**一个系统可不可靠，不取决于它平时跑得多顺，而取决于它在任意一点断电后能不能自证状态**。这也是最容易被面试官用来分辨「背过两阶段提交」和「真的想通了」的一道题。

**一句话结论**：恢复 = **redo 重放 + undo 回滚**：重启后从 check point 起把 redo 顺序重放（已落盘的页按 LSN 跳过，所以重放幂等），把**已提交**的事务补上；再用 undo 把**未提交**的事务回滚掉。**判据来自两阶段提交留下的状态**——redo 是 `prepare` 且 binlog 完整 → 提交；binlog 不完整 → 回滚。

**恢复关键词**：redo 重放幂等 / LSN 比较 / undo 回滚未提交 / prepare 状态判据 / binlog 完整性 / 双一配置

**核心不变量 / 主线**：
**恢复的正确性不靠"猜",靠"日志状态"**。每一个事务在崩溃瞬间都只有三种可能——还没开始、已经提交、提交到一半（prepare）。**规范状态机让前两种无歧义，第三种由两阶段提交给出唯一裁决。**

**完整回答骨架**：崩溃后的三个问题 → redo 的重放规则（为什么幂等）→ undo 回滚谁 → prepare 状态怎么当判据 → binlog 完整性的边界 → 为什么生产要「双一」

## 原理分解

### 一、崩溃瞬间，一个事务只有三种状态

| 崩溃时的状态 | 数据页 | 日志 | 恢复动作 |
|---|---|---|---|
| 还没提交 | 可能已改内存 | redo 里没有 commit / binlog 没写 | **undo 回滚** |
| 已经提交 | 可能还没落盘 | redo 已 commit、binlog 已完整 | **redo 重放补上** |
| 提交到一半 | 不确定 | redo 是 `prepare`，binlog **可能完整也可能不完整** | **看 binlog 裁决** ← 这题的题眼 |

**所以恢复算法只回答三件事**：哪些该重做？哪些该回滚？怎么保证重做不会做两遍？

### 二、redo 重放：为什么重放两次也不会出错

redo 记录的是「某数据页某偏移被改成了什么值」，而且**每个数据页头部都存着自己的 LSN（日志序列号）**。

```
重放一条 redo 前：比较 页的 LSN 与 该条 redo 的 LSN
  页.LSN >= redo.LSN  →  这条改动已经落盘了，跳过
  页.LSN <  redo.LSN  →  需要应用，把它写进内存页
```

**这就是重放幂等的来源**——不是靠"只做一次"的锁，而是靠**"已经做过就认得出"的状态标记**。恢复中断后再次重启，可以继续从断点重放，不会重复应用。

> 这个思路值得迁移到任何重放系统里：**幂等不是"不去做"，是"做之前能判断是否已做过"。** RuleArena 里的 ActionReceipt 就是这个模式在业务层的翻版。

### 三、undo 回滚未提交的事务

redo 重放结束后，内存里已经包含了「已提交」和「提交到一半但还没裁决」的修改。此时：

- **已提交** → 保留（就是它该在的状态）。
- **未提交** → 用 undo log 把改动**反向撤销**，恢复成修改前的样子。

**注意顺序**：一定是**先 redo 重放、再 undo 回滚**。反过来会在「提交了但数据页未落盘」的场景里丢数据。

### 四、题眼：prepare 状态怎么裁决（两阶段提交的收尾）

redo 里状态是 `prepare` 的事务，InnoDB 自己**无法判断该提交还是回滚**——因为决定权在 binlog：

```
redo = prepare
   ├─ binlog 完整（该事务的 binlog 记录已写完，可校验）
   │     → 事务视为成功，把 redo 改成 commit，数据保留
   └─ binlog 不完整 / 不存在
         → 事务视为失败，用 undo 回滚
```

**为什么这么判？** 因为两阶段提交的顺序是「写 redo（prepare）→ 写 binlog → 改 redo 为 commit」。所以：

- **binlog 完整 = 第二步成功了 = 这个事务对外已经宣布过成功**，必须让它生效（否则从库执行了、主库却没有）。
- **binlog 不完整 = 第二步没成功 = 这个事务从未对外宣布**，必须回滚（否则主库有效、从库却没有）。

**这就是「崩溃恢复」和「主从一致性」在同一个机制上收口的地方**——不是两套逻辑，是一套。

### 五、生产配置：为什么主库都配「双一」

| 参数 | 值 | 作用 |
|---|---|---|
| `innodb_flush_log_at_trx_commit` | **1** | 每次提交 fsync redo |
| `sync_binlog` | **1** | 每次提交 fsync binlog |

**两个都为 1 时，事务的"提交成功"才算真的落到磁盘**——这才是接口返回「提交成功」后断电也不丢的前提。**只配一个**会出现：redo 保证了主库恢复，但 binlog 丢了 → 从库缺数据；或者反过来。

> 面试追问「这样不是更慢吗？」→ 是，但可以先给出**代价量化**（吞吐下降幅度要靠压测），再说**取舍标准**：涉及钱的写路径不省这个 fsync；能容忍丢最近 1 秒的场景（埋点、日志类）才降到 2 或 0。**这是"按业务定口径"，不是"按性能定口径"。**

## 二、扩展：类似题与追问

**类似题**

1. 「MySQL 宕机后重启，为什么不会重复执行已经提交的事务？」——**数据页自带 LSN，重放前先比较**，已落盘的直接跳过。这是"幂等重放"的标准答案。
2. 「主从不一致是怎么被崩溃窗口造出来的？」——**两阶段提交的第一个崩溃窗口**：redo 写完（prepare）、binlog 没写就崩 → 主库重放后有数据、从库没有。**反向窗口**：binlog 写完、redo 没写就崩 → 主库回滚、从库执行了。
3. 「redo log 是无限增长的吗？」——不是，**固定大小循环写**；边界的推进靠 check point（脏页落盘后才前移）。

**追问链**

- 追问一层：**「恢复要重放多久？」**——取决于 **check point 的位置**：check point 越新，需要重放的 redo 越少，恢复越快。所以 check point 的推进频率同时影响**恢复时间**和**正常写入时的刷脏压力**——这是同一组参数的两面，不能只调一边。
- 追问二层：**「如果恢复过程中又崩了呢？」**——没关系。redo 重放本身幂等（按 LSN 跳过已应用的页），重启后从最新的 check point 继续重放即可。**系统不怕反复崩，怕的是重放不幂等。**
