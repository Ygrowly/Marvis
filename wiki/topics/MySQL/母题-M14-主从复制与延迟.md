# 母题 M14 · 主从复制与延迟

> **模块**：MySQL / 数据增长与高可用
> **所属主线**：六 · 数据增长与高可用（数据多了怎么不被拖垮）
> **关联母题**：[[母题-M11-三日志与两阶段提交]] · [[母题-M13-长事务为什么危险]] · [[母题-P12-流复制与逻辑复制]]
> **素材来源**：`raw/Mysql面试题` 第 6 节（主从同步）+ `raw/后端视角复盘_MySQL` 第六条主线（读写分离的现实坑）

**题目**：读写分离上线后，用户反馈"刚提交的数据看不到"。为什么？怎么解决？

**母题**：主从复制的原理是什么？主从延迟从哪来？读到旧数据怎么办？

**为什么重要**：**读写分离是"数据增长"最常用的第一步**，而它的**第一个现实坑就是"从库不是绝对实时的"**（raw 原话）。**这道题的难点不在背原理，而在延迟的三类来源能不能讲清、以及"读到旧数据"的解法为什么不能是"sleep 一下再读"。** **它和 P12（PG 的复制）是同构对照，也是数驭穹图接入层设计的直接背景。**

**一句话结论**：**主库写 binlog → 从库 IO 线程拉取并写入 relay log → 从库 SQL 线程重放**。**延迟来自三处：① 主库可并行写、从库回放（历史上单线程，现代有按库/按事务并行）；② 大事务——一条 binlog 必须整体重放；③ 从库机器更差 / Row 格式下无主键的更新极慢**。**缓解**：并行复制、拆大事务、监控 `Seconds_Behind_Master`。**读到旧数据的解法按优先级**：**关键读回主库（读己之写）→ 会话内粘主库 → 延迟超阈值降级**，**不要用 sleep**。

**恢复关键词**：binlog 三种格式 / IO 线程与 SQL 线程 / relay log / 并行复制 / 大事务 = 整体重放 / `Seconds_Behind_Master` / 读己之写 / 不要 sleep

**核心不变量 / 主线**：
**复制是"至少存在延迟的"，读写分离的正确性必须显式设计，不能靠"从库应该很快"。** ——**所以"哪些读可以走从库"是业务决策，不是技术默认值。**

**完整回答骨架**：复制三步（binlog → relay → 重放）→ binlog 三种格式（M11 已讲，这里串一遍）→ 延迟的三类来源 → 缓解手段 → 读到旧数据的三层解法 → 什么时候才该上读写分离

## 原理分解

### 一、复制三步

```
主库：事务提交时写 binlog（M11 的两阶段提交保证 redo/binlog 一致）
  ↓
从库 IO 线程：连主库拉 binlog，写入本地 relay log
  ↓
从库 SQL 线程：重放 relay log 里的变更
```

**要点**：**复制的是 binlog（逻辑日志），不是数据页**——所以从库回放的是"变更"，这也是它**可能有延迟**的根本原因（重放速度追不上主库写入速度）。

**binlog 三种格式**（M11 已展开，这里只串一遍）：**Statement（记 SQL，省空间但非确定函数会主从漂移）/ Row（记每行前后镜像，精确但大）/ Mixed（自动切换）**。**现代生产主流是 Row**（数据安全优先）。

### 二、延迟的三类来源（本题核心）

| # | 来源 | 说明 |
|---|---|---|
| **① 回放并行度不足** | **主库可以多线程并发写，从库回放（老版本单线程）** | 现代版本有按库/按事务/按 WRITESET 的并行复制，**但并行度永远 ≤ 主库**，所以高峰期追不上是常态 |
| **② 大事务** | **一个事务在 binlog 里是一条记录，必须整体重放** | **一百万行的 UPDATE 在主库跑 10 分钟，从库也要重放 10 分钟，而且期间这个事务的变更对从库不可见**——**这正好是 M13"批量要分批"的另一个理由** |
| **③ 从库自身慢** | 机器差 / **Row 格式下表没有主键，更新要全表扫** | **Row 格式的变更靠"找到那一行"来应用，无主键时退化成全表扫描**——**所以"每张表都要有主键"不只是规范，是复制性能问题** |

**第 ③ 条是加分项**：**能说出"无主键表在 Row 格式下会拖慢从库回放"，说明你真的理解复制在做什么**。

### 三、缓解手段

```
① 并行复制（按库 / 按事务 / 按 WRITESET）
② 拆大事务（分批提交——M13 的公共答案）
③ 表必须有主键
④ 从库用差不多的机器（别用"淘汰的旧机器做从库"）
⑤ 监控 Seconds_Behind_Master，超阈值告警
⑥ 半同步复制（semi-sync）：主库至少等一个从库收到 binlog——换 RPO，不解决延迟
```

**注意 ⑥**：**半同步解决的是"主库挂了丢不丢"，不解决"从库读到旧数据"**——**这两件事经常被混为一谈**。**PG 侧对应的是 synchronous_commit / synchronous_standby_names（P12），同样是"RPO 换提交延迟"。**

### 四、读到旧数据：三层解法（按优先级）

```
① 关键读回主库（读己之写）
   用户提交后立刻展示的那次读（订单详情、提交结果页）必须读主库。
   实现：写路径打标记，同会话/同用户的后续一次读路由到主库。

② 会话内粘主库
   "这个用户在这个会话里，写后 N 秒内的读都走主库"——比 ① 粒度粗，但实现简单。

③ 延迟超阈值降级
   Seconds_Behind_Master 超过阈值时，读操作直接回主库（或降级响应）。
   ——这是兜底，不是常规路径。
```

**为什么不是 sleep**：**① sleep 的时长没有依据（延迟是波动的）；② 它把"正确性"建立在"猜测延迟足够小"上；③ 高峰期 sleep 完还是旧的。** **这一句"为什么不用 sleep"是面试里最容易露水平的地方。**

**还有一个更根本的视角**：**"读旧数据"很多时候不是复制的问题，是业务语义问题**——**"提交后立刻展示"这种读，本来就不该从副本读**。**先把"哪些读必须强一致"定义清楚，再谈路由**——**这一条数驭穹图的文档里有现成表达（新鲜度要求决定访问模式），可以直接迁移。**

### 五、什么时候才该上读写分离（防止过早优化）

**先问一句：读压力真的把主库打满了吗？** 如果没有，**先做索引与慢查询（M7）、缓存与预聚合（M15 的前面几步）**——**读写分离的代价是"必须处理延迟语义"，这个复杂度不是免费的**（M15 的五步顺序里它排第四）。

## 二、扩展：类似题与追问

**类似题**

1. 「`Seconds_Behind_Master` 准吗？」——**不精确**：它衡量的是"从库 SQL 线程处理到的位置与当前主库时间的差"，**主库空闲时它会归零（哪怕 binlog 还没传完），从库卡住时也可能显示不准**。**生产要配合 `GTID` 位点与binlog 延迟时间来综合判断。**
2. 「GTID 是什么？」——**全局事务 ID，让从库定位"我回放到哪了"不再依赖文件名+偏移量**，**主从切换、搭建新从库都因此简单很多**。**知道它的作用即可。**
3. 「为什么主库挂了从库可能丢数据？」——**异步复制下主库提交不等从库确认**；**半同步能缓解（等至少一个从库收到）**。**这条是 P12"同步/异步取舍"的 MySQL 版。**

**追问链**

- 追问一层：**「为什么 Row 格式更安全但更大？」**——**Statement 记 SQL**，遇到 `NOW()`/`UUID()` 这类非确定函数，主从执行结果可能不同（主从漂移）；**Row 记每行的前后镜像**，重放绝对精确，**但一条批量 UPDATE 会把每一行的变化都记下来，日志量暴涨**。**Mixed 是折中（自动判断）**——**M11 里讲过三种格式的表，这里是"为什么生产主流用 Row"的理由**。
- 追问二层：**「读写分离之后，主库的压力真的降了吗？」**——**读压力降了，写压力一点没降**；**而且主从同步本身消耗主库资源**。**所以"加从库"解决的是读瓶颈，不是写瓶颈**——**写瓶颈要么靠拆（分库分表，M15），要么靠异步化（消息队列）**。**这条防止"加从库"被当成万能药。**
