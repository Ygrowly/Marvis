# 母题 M14 · 主从复制与延迟

> **模块**：MySQL / 数据增长与高可用
> **所属主线**：六 · 数据增长与高可用（数据多了怎么不被拖垮）
> **层级**：B · 标准级（"并行度永远 ≤ 主库"与"大事务必须整体重放"都能推；但三层解法本身是取舍）
> **关联母题**：[[母题-M11-三日志与两阶段提交]]（binlog 的来源与一致性保证）· [[母题-M13-长事务为什么危险]]（大事务的另一层危害）· [[母题-M15-数据增长治理]]（读写分离在五步里的位置）· [[母题-P12-流复制与逻辑复制]]（PG 侧同构）
> **素材来源**：`raw/Mysql面试题` 第 6 节（主从同步）+ `raw/后端视角复盘_MySQL` 第六条主线（读写分离的现实坑）。**本轮升级补入：并行度/大事务/无主键三组算式、复制链路图、自测题**

**导读**：必懂 3 件事（① 复制的是变更不是数据页 ② 延迟有三类来源，其中两类是结构性的 ③ "读到旧数据"该怎么答，以及为什么不能 sleep）· 读完约 12 分钟 · 需要先懂：[[母题-M11-三日志与两阶段提交]]（binlog）

**题目**：读写分离上线后，用户反馈"刚提交的数据看不到"。为什么？怎么解决？

**母题**：**主从复制的原理是什么？延迟到底从哪来——换成"更好的机器"能解决吗？读到旧数据该怎么处理？**

**为什么重要**：**读写分离是"数据增长"最常用的第一步**，而它的**第一个现实坑就是"从库不是绝对实时的"**（原始素材原话）。**这道题的难点不在背原理，而在延迟的三类来源能不能讲清、以及"读到旧数据"的解法为什么不能是"sleep 一下再读"。** 它和 [[母题-P12-流复制与逻辑复制]] 是同构对照，**也是数驭穹图接入层设计的直接背景**。

## 一、教材

### 1. 前提：复制的是"变更"，不是数据页

::figure replication-lag.svg | 主从复制：延迟从哪来，读到旧数据怎么办 | 上半部分是复制三步与延迟的三个来源；下半部分是按优先级排的三层解法，以及为什么不能用 sleep

```text
主库：事务提交时写 binlog（两阶段提交保证 redo / binlog 一致，M11）
        ↓
从库 IO 线程：连主库拉 binlog，写入本地 relay log
        ↓
从库 SQL 线程：重放 relay log 里的变更
```

【推导】**复制的对象是 binlog（变更流），不是数据页**——这个前提直接推出一件事：

> **从库是"追赶者"，不是"镜像"。它必须把主库做过的事重做一遍。**

【推论】**所以"追不上"是**结构性的**，不是故障。** 只要主库的写入速度超过从库的重放速度，延迟就会累积。**任何"让从库更实时"的手段，本质上都是在提高重放速度——而不是消除这个结构。**

**binlog 三种格式**（M11 已展开，这里只串一遍）：**Statement**（记 SQL，省空间但非确定函数会主从漂移）/ **Row**（记每行前后镜像，精确但大）/ **Mixed**（自动切换）。**现代生产主流是 Row**（数据安全优先）。

**到这里你应该能回答**：为什么"从库应该很快"不是一个可以依赖的假设？

### 2. 延迟的三类来源

| # | 来源 | 说明 | 是结构性的吗 |
|---|---|---|---|
| **① 回放并行度不足** | 主库可以多线程并发写，从库回放受"事务之间有没有冲突"限制 | **并行度永远 ≤ 主库** | **是** |
| **② 大事务** | 一个事务在 binlog 里是**一条记录，必须整体重放** | 主库跑 10 分钟，从库也要 10 分钟，**期间这个事务的变更对从库不可见** | **是**（只要还有大事务） |
| **③ 从库自身慢** | 机器差 / **Row 格式下表没有主键，更新退化成全表扫** | 靠"找到那一行"来应用 | 否（可修） |

#### 2.1 并行度为什么是瓶颈【推导】

```text
主库写入 100,000 TPS
按库并行：只有 4 个库 → 并行度 4
  从库能力 = 4 × 25,000 = 100,000 TPS
  → 刚好打平，任何波动都会落后

按 WRITESET 并行（8.0）：并行度可到 32
  从库能力 = 32 × 25,000 = 800,000 TPS
  → 8 倍余量
```

【推论】**"按库并行"的天花板就是库的数量。** 所以从"按库"升级到"按 WRITESET"（行级判断冲突）不是为了更快，是**为了把并行度从"库数"这个硬上限里解放出来**。

#### 2.2 大事务的延迟能算出来【推导】

```text
一个 100 万行的 UPDATE，主库跑 10 分钟（600 秒）
  从库要整体重放 → 延迟 ≈ 600 秒

拆成 1000 批（每批 1000 行，约 0.6 秒）
  从库每批独立重放 → 延迟降到约 0.6 秒

降到 1/1000
```

【推论】**这正好是 [[母题-M13-长事务为什么危险]] "批量要分批"的另一个理由**——同一个动作，同时治了锁持有、undo 峰值、主从延迟三个问题。

#### 2.3 无主键表的代价【推导】

```text
一个 UPDATE 影响 1000 行，表 1000 万行（每页 16 行 → 62.5 万页）

表有主键：按主键定位 1000 次，每次约 3 次 IO
        = 3,000 次 IO

表无主键（Row 格式）：每行都要全表扫才能找到
        = 1000 × 62.5 万页 = 6.25 亿页读

量级比 ≈ 20 万倍
```

【推论】**"每张表都要有主键"不只是规范，是复制性能问题。** 面试里能说出"无主键表在 Row 格式下会拖慢从库回放"，**说明你真的理解复制在做什么**（而不是背了三步流程）。

**到这里你应该能回答**：为什么把从库换成更好的机器，只能治三类延迟里的一类？

### 3. 缓解手段

```text
① 并行复制（按库 → 按事务 → 按 WRITESET）
② 拆大事务（分批提交——M13 的公共答案）
③ 表必须有主键
④ 从库别用"淘汰的旧机器"
⑤ 监控延迟指标，超阈值告警
⑥ 半同步复制（semi-sync）：主库至少等一个从库收到 binlog
```

【取舍】**注意 ⑥ 解决的不是延迟**：**半同步解决的是"主库挂了丢不丢"（RPO），不解决"从库读到旧数据"。** **这两件事经常被混为一谈**——能主动分开说，是这道题的加分点。PG 侧对应的是 `synchronous_commit` / `synchronous_standby_names`（[[母题-P12-流复制与逻辑复制]]），同样是"用提交延迟换 RPO"。

**到这里你应该能回答**：为什么"上了半同步"仍然可能读到旧数据？

### 4. 读到旧数据：三层解法（按优先级）【事实】

```text
① 关键读回主库（读己之写）
   用户提交后立刻展示的那次读（订单详情、提交结果页）必须读主库。
   实现：写路径打标记，同会话/同用户的后续一次读路由到主库。

② 会话内粘主库
   "这个用户在这个会话里，写后 N 秒内的读都走主库"——比 ① 粒度粗，但实现简单。

③ 延迟超阈值降级
   延迟指标超过阈值时，读操作直接回主库（或降级响应）。
   ——这是兜底，不是常规路径。
```

#### 4.1 为什么不能 sleep【推导】

```text
① sleep 的时长没有依据——延迟是波动的，你不知道该睡多久
② 它把【正确性】建立在【猜测延迟足够小】上
③ 高峰期 sleep 完还是旧的——因为追赶速度本来就落后
```

【推论】**这三条合起来说明：sleep 不是"简单方案"，是"把正确性交给运气"。** 面试里主动说清这一点，比背出三层解法更能体现你想过。

#### 4.2 一个更根本的视角【取舍】

**"读旧数据"很多时候不是复制的问题，是业务语义问题**——**"提交后立刻展示"这种读，本来就不该从副本读。**

【推论】**先把"哪些读必须强一致"定义清楚，再谈路由**——**这个顺序不能反**。反过来做（先上读写分离，再到处打补丁）会得到一个到处都是例外的路由规则。数驭穹图里"新鲜度要求决定访问模式"就是这个思路的现成表达。

### 5. 什么时候才该上读写分离【取舍】

**先问一句：读压力真的把主库打满了吗？**

如果没有，**先做索引与慢查询（[[母题-M7-慢查询与SQL优化手段]]）、缓存与预聚合**——**读写分离的代价是"必须处理延迟语义"，这个复杂度不是免费的**（[[母题-M15-数据增长治理]] 的五步顺序里它排在第四）。

### 6. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "从库应该很快，延迟是异常" | **延迟是结构性的**：复制的是变更流，从库必须重做一遍；**并行度永远 ≤ 主库**。所以"追不上"是常态，不是故障 |
| "上了半同步就不会读到旧数据" | **半同步解决的是 RPO（主库挂了丢不丢），不是读一致性**。它只保证"至少一个从库收到了 binlog"，**不保证从库已经重放完** |
| "读到旧数据就 sleep 一下再读" | **三处错**：延迟波动所以时长没依据；把正确性建立在猜测上；高峰期睡完还是旧的。**正确做法是读己之写 / 会话粘主库 / 超阈值降级** |
| "表没主键只是规范问题" | **是复制性能问题**：Row 格式下无主键的更新**退化成全表扫**，量级差到 20 万倍。这直接拖慢从库回放 |
| "加从库能解决压力" | **只降读压力，写压力一点没降**；而且**主从同步本身消耗主库资源**。写瓶颈要靠拆（分库分表）或异步化（消息队列） |
| "并行复制开了就能追上" | 并行度受**事务冲突**限制（按库并行时受库数限制）。而且它只治"回放并行度不足"这一类，**治不了大事务**——大事务必须整体重放 |
| "PT 的延迟数字很准" | `Seconds_Behind_Master` **不精确**：主库空闲时它会归零（哪怕 binlog 还没传完），从库卡住时也可能不准。**生产要配合 GTID 位点综合判断** |

【取舍】读成一句话：**复制是"至少存在延迟的"——所以"哪些读可以走从库"是业务决策，不是技术默认值。**

## 二、自测

**Q1（计算）**：主库写入 **100,000 TPS**，单线程回放能力约 **25,000 TPS**。

问：**按库并行（4 个库）和按 WRITESET 并行（32 路）分别能提供多少回放能力？**哪一种能追得上主库？

**A1**：

```text
按库并行（并行度 = 库数 = 4）：
  回放能力 = 4 × 25,000 = 100,000 TPS
  → 与主库【刚好打平】——没有任何余量，一旦有波动就落后

按 WRITESET 并行（并行度 32）：
  回放能力 = 32 × 25,000 = 800,000 TPS
  → 8 倍余量，能追
```

【结论】**"按库并行"的天花板就是库的数量。** 所以升级到"按 WRITESET"（行级判断事务冲突）不是为了更快，是**为了把并行度从"库数"这个硬上限里解放出来**。

【补充】但**并行度永远有上限**：同一行的并发修改**无法并行**（必须按顺序重放）。所以**"主库在同一个热行上高频写"这种负载，从库一定追不上**——这不是并行度的问题，是重放语义的问题。

**Q2（计算）**：一个批量任务要 `UPDATE` **100 万行**，在主库上耗时 **10 分钟**。主从异步复制。

问：**这段时间里从库的延迟是多少？**如果拆成 1000 批（每批 1000 行、约 0.6 秒），延迟变成多少？

**A2**：

```text
单事务（一条 binlog 记录）：
  从库必须【整体重放】→ 重放耗时 ≈ 主库的 10 分钟
  延迟 ≈ 600 秒
  而且这 600 秒内，这个事务的全部变更对从库【都不可见】

拆成 1000 批：
  每批在从库独立重放，约 0.6 秒
  延迟 ≈ 0.6 秒

降到 1/1000
```

【结论】**大事务的延迟不是"按行累加"，是"整块不可见"。** 所以它比同等数据量的小事务严重得多——**从库要么看到全部，要么什么都看不到。**

【补充】这正是 [[母题-M13-长事务为什么危险]] "批量要分批"的另一个理由：**同一个动作（分批）同时治了锁持有、undo 峰值、主从延迟三件事。**

**Q3（计算）**：Row 格式下，一个 `UPDATE` 影响了 **1000 行**，表有 **1000 万行**（每页 16 行）。从库要"找到这些行"才能应用变更。

问：**表有主键和表没有主键，从库分别要做多少 IO？差多少倍？**

**A3**：

```text
表页数 = 1000万 ÷ 16 = 62.5 万页

有主键：
  按主键定位 1000 次，每次约 3 次随机 IO
  = 3,000 次 IO

没有主键（Row 格式退化成全表扫描）：
  每行都要扫全表才能找到
  = 1000 × 62.5 万页 = 6.25 亿次页读

倍率 ≈ 6.25亿 ÷ 3,000 ≈ 20 万倍
```

【结论】**"每张表都要有主键"不是规范洁癖，是复制性能问题。** 一张无主键的大表上跑批量更新，**会把从库回放直接拖死**。

【补充】这也是为什么 DBA 见到无主键表会如临大敌——**它在主库上只是"不够优雅"，在从库上是灾难**（[[母题-M5-引擎与表设计基本盘]]）。

**Q4（纠错）**：下面这段话哪里不准确？

> "我们上了半同步复制，主库要等从库确认才提交，所以不会读到旧数据了。"

**A4**：**把两个不同的问题混成了一个。**

- **半同步解决的是 RPO**：主库至少等**一个**从库**收到** binlog 才返回。它保证的是"主库此时挂了，这条数据不会丢"。
- **它不解决读一致性**：从库**收到 binlog ≠ 已经重放完**。SQL 线程可能还在追赶——**所以从库上仍然可能读到旧数据**。

【准确说法】"半同步是**用提交延迟换 RPO**，不是用来保证读一致性的。要解决'读到旧数据'，要靠**读己之写 / 会话粘主库 / 延迟超阈值降级**这套路由策略——**两件事要分开说**。"

**Q5（纠错）**：下面这段话哪里不准确？

> "读写分离后，从库读到旧数据，我们让前端 sleep 200 毫秒再重试一次就好了。"

**A5**：三处错。

1. **sleep 的时长没有依据**：延迟是**波动**的，200ms 是从哪来的？高峰期它可能是 5 秒。
2. **它把"正确性"建立在"猜测延迟足够小"上**：这不是工程方案，是概率赌注。
3. **高峰期 sleep 完还是旧的**：因为**追赶速度本来就落后**（Q1 里按库并行刚好打平，任何波动都落后），睡再久也追不上累积的延迟。

【准确说法】"**先定义清楚哪些读必须强一致**，再按优先级做路由：**① 读己之写（把刚写完就要展示的那次读路由回主库）② 会话内粘主库 ③ 延迟超阈值时整体降级回主库**。**sleep 是'把正确性交给运气'，不是解法。**"

## 三、面试输出（学完再看）

**一句话结论**：**主库提交时写 binlog → 从库 IO 线程拉取并写入 relay log → 从库 SQL 线程重放**。关键是**复制的是"变更流"不是数据页**，所以从库是追赶者，**"追不上"是结构性的**。延迟有三个来源：**① 回放并行度永远 ≤ 主库**（按库并行时天花板就是库数——4 个库 × 25,000 = 100,000 TPS，与主库刚好打平）；**② 大事务必须整体重放**（主库跑 10 分钟，从库也 10 分钟，**期间变更对从库完全不可见**）；**③ 从库自身慢**（Row 格式下**无主键表退化成全表扫，量级差 20 万倍**——所以"每张表都要有主键"是复制性能问题）。**"读到旧数据"的三层解法按优先级**：**读己之写 → 会话粘主库 → 延迟超阈值降级**；**不能用 sleep**（延迟波动、时长无依据、把正确性建立在猜测上）。注意**半同步解决的是 RPO，不是读一致性**——这两件事最常被混为一谈。

**恢复关键词**：binlog → relay log → 重放 / 复制的是变更不是数据页 / 从库是追赶者 / 并行度 ≤ 主库（按库并行的天花板 = 库数）/ 大事务整体重放、期间不可见 / Row 格式无主键退化成全表扫（20 万倍）/ 并行复制按库→按事务→按 WRITESET / 拆大事务 / 表必须有主键 / **半同步 = RPO ≠ 读一致性** / 读己之写 → 会话粘主库 → 超阈值降级 / 不要 sleep

**核心不变量 / 主线**：
**复制是"至少存在延迟的"，读写分离的正确性必须显式设计，不能靠"从库应该很快"。**
——**所以"哪些读可以走从库"是业务决策，不是技术默认值。**

**完整回答骨架**：复制三步 + "复制的是变更"这个前提 → 延迟三源（①②是结构性的）→ 缓解手段（并点明半同步治的不是这个）→ **读到旧数据的三层解法 + 为什么不用 sleep** → 什么时候才该上读写分离 → 收束到"延迟是结构性的"

**追问**（先说后看）

1. **为什么 Row 格式更安全但更大？** —— **Statement 记 SQL**，遇到 `NOW()` / `UUID()` 这类非确定函数**主从执行结果可能不同（主从漂移）**；**Row 记每行的前后镜像**，重放绝对精确，**但一条批量 UPDATE 会把每一行的变化都记下来，日志量暴涨**。**Mixed 是折中。**
2. **读写分离之后，主库的压力真的降了吗？** —— **读压力降了，写压力一点没降**；而且**主从同步本身消耗主库资源**。**所以"加从库"解决的是读瓶颈，不是写瓶颈**——写瓶颈要么靠拆（分库分表），要么靠异步化（消息队列）。
3. **延迟指标准吗？** —— **不精确**：它衡量的是"从库 SQL 线程处理到的位置与主库当前时间的差"，**主库空闲时它会归零**（哪怕 binlog 还没传完），从库卡住时也可能不准。**生产要配合 GTID 位点综合判断。**
4. **GTID 是什么？** —— **全局事务 ID**，让从库定位"我回放到哪了"不再依赖文件名 + 偏移量，**主从切换、搭建新从库都因此简单很多**。知道作用即可。
5. **异步复制下主库挂了会丢数据吗？** —— **会**。异步复制下主库提交不等从库确认；**半同步能缓解（等至少一个从库收到）**，代价是提交延迟变长。**这是 [[母题-P12-流复制与逻辑复制]] "同步/异步取舍"的 MySQL 版。**

**同类变体**

- 「CDC 是怎么做的？」——本质上就是**消费 binlog**（数驭穹图的接入层就是这么干的）。**理解"复制三步"是理解 CDC 的前提**。
- 「读写分离的分库分表什么关系？」——**读写分离解决读瓶颈，分库分表解决容量与写瓶颈**。两者层次不同，**不能互相替代**（[[母题-M15-数据增长治理]]）。
- 「从库能不能当备份？」——**不能替代备份**。从库上的误操作（`DROP TABLE`）会照样同步过去；而且从库本身也可能故障。**备份是另一条独立的链。**
