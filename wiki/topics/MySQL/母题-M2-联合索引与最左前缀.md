# 母题 M2 · 联合索引与最左前缀

> **模块**：MySQL / 索引
> **所属主线**：一 · 索引（怎么让查询不用扫全表）
> **关联母题**：[[母题-M1-为什么用B+树]] · [[母题-M3-聚簇索引与回表]]
> **素材来源**：`raw/后端视角复盘_MySQL` 第一条主线「联合索引不是随便拼字段」；最左前缀的成因与失效场景为通用知识补充（**待你核对**）

**题目**：任务表要支持这样一条调度 SQL：

```sql
SELECT id, status, next_retry_time, priority
FROM task
WHERE status = 'PENDING'
  AND next_retry_time <= NOW()
ORDER BY priority DESC, id ASC
LIMIT 100;
```

联合索引该怎么建？为什么 `(a, b, c)` 能用上 `a=1` 和 `a=1 AND b=2`，却用不上单独 `b=2`？

**母题**：联合索引的字段顺序由什么决定？「最左前缀」这个限制是怎么来的？

**为什么重要**：索引设计是后端最高频的追问点，而且它**从 M1 就能推出来**——索引是有序结构，「最左前缀」是这个有序性的直接后果。答得出成因，就不用背。

**一句话结论**：联合索引 `(a, b, c)` 的排序方式是**先按 a 排、a 相同再按 b 排、b 相同再按 c 排**；所以只有从最左列开始的连续前缀才能用上这份有序性。

**恢复关键词**：有序性 / 连续前缀 / 等值在前范围在后 / 排序列收尾 / 少扫少回表少排序

**核心不变量 / 主线**：
索引的价值只有一条——**让 MySQL 少扫数据、少回表、少排序**。联合索引的字段顺序，是围绕这条 SQL 的执行路径决定的，不是围绕「哪些字段经常出现」决定的。

**完整回答骨架**：索引是有序结构 → 联合索引的排序规则 → 最左前缀是这个规则的后果 → 字段顺序的四条经验 → 失效的典型场景

## 原理分解

### 一、最左前缀的成因（一次推完）

索引本身就是一份**排好序的数据**。`(status, next_retry_time, priority)` 的排序规则是：

```
先按 status 排  →  status 相同再按 next_retry_time 排  →  再相同才按 priority 排
```

所以：

| 查询条件 | 能否用索引 | 原因 |
|---|---|---|
| `status = 'PENDING'` | ✅ | 命中最左列 |
| `status = ? AND next_retry_time <= ?` | ✅ | 连续前缀 |
| `next_retry_time <= ?`（单独） | ❌ | `next_retry_time` 只在「同 status 内」有序，全局无序 |
| `priority = 3`（单独） | ❌ | 只在最小范围内有序 |

**一句话**：`b` 是「局部有序、全局无序」的，所以只用 `b` 查等于在无序数据里找。

### 二、字段顺序的四条经验（来自素材）

围绕**执行路径**设计，不是围绕字段热度：

1. **等值过滤列放前面** —— 等值条件能一次定位到一个连续区间
2. **范围列要谨慎** —— 范围条件会**截断**后面的列，`a = ? AND b > ? AND c = ?` 里 `c` 用不上索引
3. **排序列尽量接在后面** —— 让 `ORDER BY` 直接吃索引的有序性，避免 `Using filesort`
4. **目标始终是**：少扫、少回表、少排序

### 三、回到那条调度 SQL

```sql
WHERE status = 'PENDING' AND next_retry_time <= NOW()
ORDER BY priority DESC, id ASC
LIMIT 100
```

按上面的规则推：

- `status` 是等值 → 放最前
- `next_retry_time` 是范围 → 放第二位（它会截断后面）
- `priority` 是排序列 → 接在范围列后面，**能用上一部分有序性**（同一 `next_retry_time` 区间内仍是排好的）
- 若 `priority` 无法完全靠索引排序，`Extra` 里会出现 `Using filesort`

**注意**：范围列之后的有序性只在「范围内部」有效，这是这条 SQL 是否出现 filesort 的关键——**不要背「范围列后面全失效」，那是过度简化**。

### 四、索引失效的典型场景

| 场景 | 为什么失效 |
|---|---|
| 列上做函数 / 运算：`WHERE YEAR(created_at) = 2026` | 破坏了「按列原值有序」这个前提 |
| 隐式类型转换：字符串列 `WHERE phone = 13800138000` | 相当于对列做了类型转换 |
| 前导模糊：`LIKE '%abc'` | 前缀不定，无法定位有序区间的起点 |
| `OR` 连接的条件里有非索引列 | 只能全表扫再合并 |
| `!=` / `NOT IN` | 命中区间过于分散，优化器判断扫索引不如全表 |
| 选择度太低（如 `status` 只有 3 个值） | 优化器主动放弃索引走全表 |

**最后一条最容易被忽略**：索引失效不一定是「写法错了」，可能是**优化器算过成本后主动不选**。

## 二、扩展：类似题与两层追问

**同类变体**

- `(a, b, c)` 和 `(c, b, a)` 在什么查询下效果不同？（围绕高频路径，不是数量）
- 索引下推（Index Condition Pushdown）是什么？（5.6+ 优化：在索引层就过滤掉不满足的行，减少回表）
- 覆盖索引能不能绕过最左前缀？（不能，它解决的是回表，不是有序性）

**两层追问**（能答完才算通过）

1. **`WHERE b = 2 AND a = 1` 和 `WHERE a = 1 AND b = 2` 有区别吗？** —— 没有。优化器会重排条件，**索引匹配看的是列集合，不是书写顺序**。
2. **`a = 1 AND c = 3` 能用上 `(a, b, c)` 吗？** —— `a` 能用（定位区间），`c` 用不上（被中间断开的 `b` 阻断）。但如果是 `a = 1 AND b = 2 AND c = 3`，三列都能用。
