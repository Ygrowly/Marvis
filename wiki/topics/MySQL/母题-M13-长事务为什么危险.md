# 母题 M13 · 长事务为什么危险

> **模块**：MySQL / 长事务
> **所属主线**：五 · 长事务（它为什么危险，为什么拖系统下水）
> **关联母题**：[[母题-M9-MVCC]] · [[母题-M10-锁与死锁]] · [[母题-M15-数据增长治理]]
> **素材来源**：`raw/后端视角复盘_MySQL` 第五条主线（长事务不是慢，而是拖系统下水）

**题目**：一个只做 `SELECT`、什么都没改的事务，挂了两个小时不结束。它会带来什么问题？

**母题**：长事务为什么危险？不只是持锁久——它到底坏了什么？

**为什么重要**：**raw 里这句"很多人知道不太好，但说不清楚到底坏在哪"就是这道题的价值**——**它考的是你能不能从 MVCC 机制推导出长事务的完整危害链**，而不是背一句"长事务不好"。**而且它有一个反直觉点：只读事务同样危险。** **这条和 PG 的 P14 几乎是同构的**——两边的机制都指向"长事务按住旧版本不让回收"。

**一句话结论**：长事务最可怕的隐患是**拖住旧版本数据的清理**——MVCC 的普通读依赖 undo 里的旧版本，**事务不结束，purge 线程就不敢清那些它还可能要读的版本** → **undo 膨胀、历史链越来越长 → 回滚成本更高、快照读沿链回溯更慢、锁持有更久** → **系统整体越来越沉**。**加上持锁久这一层，两条危害叠加**。**只读事务同样有害**（手动关了 autocommit 忘了提交，是最常见的真实事故形态）。

**恢复关键词**：拖住 undo 清理 / 历史链变长 / 回滚成本更高 / **只读事务也危险** / autocommit 意外关闭 / 事务里不放 RPC / `innodb_trx` 监控

**核心不变量 / 主线**：
**长事务最可怕的不是"执行久"，而是它会持续占着数据库资源，让整个系统越来越难受。**（raw 原话）——**它不是"慢"，是"按住资源的柄"。**

**完整回答骨架**：危害一：拖住旧版本清理（从 MVCC 推导）→ 危害二：持锁久 → 只读事务为什么也危险 → 工程规避清单 → 怎么监控

## 原理分解

### 一、危害一：拖住旧版本清理（从 M9 直接推导）

M9 讲过：**快照读要沿 undo 版本链回溯找可见版本**。

**关键问题**：**旧版本什么时候能删？**

```
purge 线程清理 undo 的前提：
   没有任何 ReadView 还需要它
     ↓
而 ReadView 是事务级的（RR 下整个事务一个）
     ↓
所以：一个长事务开着 → 它的 ReadView 一直在 → 链上它之前的旧版本都不能清
```

**于是**：

```
undo 清理跟不上
  → 历史链越来越长
  → 快照读沿链回溯的步数变多（读变慢）
  → 回滚成本更高（要撤销的更多）
  → 系统整体越来越沉
```

**这条链值得完整背下来**——**它把 M9 的机制变成了 M13 的后果**，是"会 MVCC"和"会运维"的分界线。

### 二、危害二：持锁久

事务里如果有 `UPDATE` / `FOR UPDATE`，**锁会一直持有到事务结束**：

```
事务越长 → 锁持有越久 → 其他事务排队越久 → 死锁概率越高（M10）
```

**注意这两条危害的来源不同**：**一条来自 MVCC（对读的影响），一条来自锁（对写的影响）**——**长事务是两条路同时变坏。**

### 三、只读事务为什么也危险（最容易被忽略）

**因为回收看的是 ReadView，不是"这个事务做了什么"**：

```
很多人以为只有写事务才会造成问题。
其实只读事务如果一直不结束，在一致性读场景下，同样可能拖住旧版本清理。
```

**最常见的真实形态**（raw 原话）：**手动关了 autocommit，跑了一个查询，结果忘了提交或结束**。

```
SET autocommit = 0;
SELECT ...;        -- 开了一个事务（隐式 BEGIN）
-- 然后连接挂着，什么都没做
                   ← 这个事务可能挂好几个小时
```

**这种连接在监控上很不起眼（CPU 低、几乎无查询），但它在按住回收边界。** **PG 那边对应的形态是 `idle in transaction`（P14）**——**两边是同一类事故，只是监控指标不同。**

### 四、工程规避清单（raw 的五条，全部照背）

```
① 事务里只放必须的数据库动作
② 不要把外部 RPC / 网络调用放进事务
③ 不要把复杂业务计算放进事务
④ 批量更新尽量分批做
⑤ 大查询和导出要格外注意事务边界
```

**第 ② ③ 条是同一类错误**：**把"外部系统的响应时间"绑进了"事务的持有时间"**——外部一抖，事务就长。**RuleArena 里"事务只包数据库操作、Checkpoint 不当业务事实"是同一个纪律**（P19 的对照）。

### 五、怎么监控

| 看什么 | 用途 |
|---|---|
| `information_schema.innodb_trx` 的 `trx_started` | **运行时间最长的事务**——回收边界的直接代理 |
| `SHOW PROCESSLIST` | 长时间处于 `Sleep` 状态的连接（可能是 `idle in transaction` 的 MySQL 版） |
| undo 表空间大小 / 历史链长度相关指标 | 膨胀程度 |

**面试加分点**：**能说出"我盯的是最老事务的 trx_started，因为回收边界由最老的 ReadView 决定"**——**这和 PG 侧"盯最老事务的 xmin"（P14）是同一句话**，**两套数据库，同一条原理。**

## 二、扩展：类似题与追问

**类似题**

1. 「批量更新一百万行为什么要分批？」——**① 事务过长（本母题）；② 单事务产生的 undo 与 redo 都大；③ 大事务在主从复制里是一条 binlog，从库要整体重放（M14）；④ 锁持有范围大（M10）**。**分批（比如每 1000 行提交一次）把这四个问题一起解决**——**所以"分批"是四张卡的公共答案，这个判断要能自己说出来。**
2. 「怎么找到是谁把 purge 卡住的？」——**查最老的事务**；**MySQL 8.0 的 `performance_schema` / `information_schema.innodb_trx` 能直接看到 `trx_started` 与正在执行的语句**。
3. 「长查询（没开事务）会拖吗？」——**autocommit 开着时，单条查询自己是原子提交的，结束后就释放**；**危险的是"显式 BEGIN 之后挂着"**。**所以"只读长事务危险"的准确条件是"它持有 ReadView"——而持有 ReadView 的前提是事务没结束。**

**追问链**

- 追问一层：**「undo 膨胀了怎么办？」**——**先杀掉肇事的长事务**（purge 立刻恢复推进），**再等 purge 追上来**（undo 表空间可以配置为可收缩，取决于版本与 undo 表空间配置）。**预防才是重点：超时参数 + 代码纪律（事务里不做 IO）。** **这条和 PG 的"先治因再回收"（P15）完全同构。**
- 追问二层：**「为什么两边（MySQL/PG）都会因为长事务出事，但表现形式不一样？」**——**因为版本存放位置不同（M9 的对照表）**：MySQL 的版本在 **undo log**，所以膨胀表现为 **undo 表空间与回溯变慢**；PG 的版本在**堆里**，所以膨胀表现为**表与索引变大（表膨胀）**。**机制同源（长事务按住回收），症状不同（undo 膨胀 vs 表膨胀）**——**能说出这句对照，就超过了 90% 的候选人。**
