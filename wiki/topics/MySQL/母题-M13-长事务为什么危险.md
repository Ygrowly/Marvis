# 母题 M13 · 长事务为什么危险

> **模块**：MySQL / 长事务
> **所属主线**：五 · 长事务（它为什么危险，为什么拖系统下水）
> **层级**：A · 教材级（两条危害链**都能从 M9 的 MVCC 机制完整推导**，回溯成本与 undo 增长能算；"只读事务也危险"是推导的必然结论）
> **关联母题**：[[母题-M9-MVCC]]（ReadView 与版本链的来源）· [[母题-M10-锁与死锁]]（持锁久的另一面）· [[母题-M15-数据增长治理]]（分批是公共答案）· [[母题-P14-长事务与表膨胀]]（PG 侧的同构问题）
> **素材来源**：`raw/后端视角复盘_MySQL` 第五条主线（"长事务不是慢，而是拖系统下水"）。**本轮升级补入：回溯成本/undo 增长/分批收益三组算式、两条危害路径图、自测题**

**导读**：必懂 3 件事（① 危害有两条链，来源不同 ② 只读事务只会走其中一条却不因此安全 ③ 监控盯的是最老事务）· 读完约 11 分钟 · 需要先懂：[[母题-M9-MVCC]]（ReadView 与版本链）

**题目**：一个只做 `SELECT`、什么都没改的事务，挂了两个小时不结束。它会带来什么问题？

**母题**：**长事务为什么危险——它到底"按住"了什么？为什么"只读"这件事并不构成豁免？**

**为什么重要**：**raw 里这句"很多人知道不太好，但说不清楚到底坏在哪"就是这道题的价值**——**它考的是你能不能从 MVCC 机制推导出长事务的完整危害链**，而不是背一句"长事务不好"。**而且它有一个反直觉点：只读事务同样危险。** **这条和 PG 的 [[母题-P14-长事务与表膨胀]] 几乎是同构的。**

---

## 一、教材

### 1. 前提：长事务按住的是两样东西

【推导】一个事务只要没结束，它就同时按住两样东西：

```text
① 它的 ReadView      —— 影响【读】这一侧（MVCC 的版本回收）
② 它持有的锁          —— 影响【写】这一侧（其他写事务的排队）
```

【推论】**所以"长事务危险"不是一个原因，是两条独立的链。** 而它们**只在有写操作时才同时出现**——这一点决定了只读事务的地位（第 3 节）。

::figure long-transaction.svg | 长事务的两条危害路径：一条走 MVCC，一条走锁 | 按住 ReadView 的一条让 purge 不敢清理、undo 膨胀、回溯变慢；按住锁的一条让写事务排队、死锁概率上升。只读事务触发不了右边那条，但左边那条照样走

---

### 2. 危害一：拖住旧版本清理（从 M9 直接推导）

【事实】[[母题-M9-MVCC]] 讲过：**快照读要沿 undo 版本链回溯找可见版本**。

**关键问题是：旧版本什么时候能删？**

```text
purge 线程清理 undo 的前提：
   没有任何 ReadView 还需要它
        ↓
而 ReadView 是事务级的（RR 下整个事务一个 ReadView）
        ↓
所以：一个长事务开着 → 它的 ReadView 一直在
     → 链上【它之前】的旧版本都不能清
```

**于是这条链启动**：

```text
undo 清理跟不上
  → 历史链越来越长
  → 快照读沿链回溯的步数变多（读变慢）
  → 回滚成本更高（要撤销的更多）
  → 系统整体越来越沉
```

【事实】原始素材的一句话点破了本质：**它不是"慢"，是"按住资源的柄"。**

#### 2.1 这条链能算出来【推导】

```text
一行数据每秒被修改 100 次，一个事务挂 2 小时（7200 秒）
  版本链长度 = 100 × 7200 = 720,000 节（72 万）

设每次可见性判断约 100 纳秒：
  单次快照读在这一行上的回溯开销 = 72万 × 100ns = 72 毫秒
  而正常情况（链长约 10 节）只有约 1 微秒

放大 7 万倍以上
```

【推论】**一个"什么都没干"的只读事务，能让别人读这一行慢 72 毫秒——而这条链是别人造成的。** 这就是"长事务拖慢别人"的机制版本：不是抽象地说"它占资源"，而是**它让全库的 undo 回收停摆**。

---

### 3. 危害二：持锁久【推导】

事务里如果有 `UPDATE` / `FOR UPDATE`，**锁会一直持有到事务结束**：

```text
事务越长 → 锁持有越久 → 其他事务排队越久 → 死锁概率越高（[[母题-M10-锁与死锁]]）
```

【取舍】**注意这两条危害的来源不同**：**一条来自 MVCC（对读的影响），一条来自锁（对写的影响）**——**长事务是两条路同时变坏。** 面试里能分开说，比笼统说"长事务不好"高一个层次。

---

### 4. 只读事务为什么也危险（最容易被忽略）

【推导】**因为回收看的是 ReadView，不是"这个事务做了什么"。**

```text
很多人以为只有写事务才会造成问题。
其实只读事务只要一直不结束，就同样持有 ReadView，
同样拖住旧版本清理。
```

**最常见的真实形态**（原始素材原话）：**手动关了 autocommit，跑了一个查询，结果忘了提交或结束。**

```sql
SET autocommit = 0;
SELECT ...;        -- 隐式开了一个事务
-- 然后连接挂着，什么都没做
                   -- 这个事务可能挂好几个小时
```

【事实】**这种连接在监控上很不起眼（CPU 低、几乎无查询），但它在按住回收边界。** PG 那边对应的形态是 `idle in transaction`（[[母题-P14-长事务与表膨胀]]）——**两边是同一类事故，只是监控指标不同。**

**到这里你应该能回答**：为什么"我这个事务只读、不会锁别人"不是一句可以放心的话？

---

### 5. 工程规避清单

【事实】五条纪律（原始素材的五条，全部照背）：

```text
① 事务里只放必须的数据库动作
② 不要把外部 RPC / 网络调用放进事务
③ 不要把复杂业务计算放进事务
④ 批量更新尽量分批做
⑤ 大查询和导出要格外注意事务边界
```

【推导】**第 ② ③ 条是同一类错误**：**把"外部系统的响应时间"绑进了"事务的持有时间"**——外部一抖，事务就长。**RuleArena 里"事务只包数据库操作、Checkpoint 不当业务事实"是同一个纪律。**

#### 5.1 "分批"的收益能算出来【推导】

```text
一个批量更新 100 万行的任务，总耗时 100 秒

单事务：
  锁持有 = 整个任务时长 = 100 秒
  undo 峰值 ≈ 100万 × 200B = 200 MB
  binlog 是【一条大事务】→ 从库要整体重放（M14）

分批（每 1000 行提交一次，共 1000 批，每批约 0.1 秒）：
  锁持有 = 单批时长 = 0.1 秒        （降到 1/1000）
  undo 峰值 ≈ 1000 × 200B = 200 KB  （降到 1/1000）
  binlog 是 1000 条小事务 → 从库可以并行重放
```

【推论】**"分批"是 M10（锁）、M13（undo）、M14（主从）、M15（数据增长）四张卡的公共答案**——它同时解决四个问题。**这个判断要能自己说出来**，而不是记住"批量更新要分批"这句话。

### 6. 怎么监控

| 看什么 | 用途 |
|---|---|
| `information_schema.innodb_trx` 的 `trx_started` | **运行时间最长的事务**——回收边界的直接代理 |
| `SHOW PROCESSLIST` | 长时间处于 `Sleep` 状态的连接（可能是"隐式事务挂着"） |
| undo 表空间大小 | 膨胀程度 |

【事实】**面试加分点**：**能说出"我盯的是最老事务的 `trx_started`，因为回收边界由最老的 ReadView 决定"**——这和 PG 侧"盯最老事务的 `xmin`"（[[母题-P14-长事务与表膨胀]]）是同一句话。**两套数据库，同一条原理。**

---

### 7. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "长事务的问题就是锁持有太久" | **这只是两条链里的一条**。另一条走 MVCC：**ReadView 不释放 → purge 不敢清 → undo 膨胀 → 回溯变慢**。只看锁，会漏掉只读事务这一整类 |
| "只读事务不会有什么影响" | **错**。回收看的是 ReadView，不是"做了什么"。只读事务只要不结束，就照样拖住回收——**而且它在监控上不起眼（CPU 低、无查询）** |
| "autocommit 开着就没事" | 前提是你**没有显式开事务**。`SET autocommit = 0` 之后跑一条查询就隐式开了事务，**忘了提交 = 挂一个长事务** |
| "长事务只是让它自己慢" | **它拖慢的是别人**：别人读这一行要沿它撑长的版本链回溯（2 小时能撑到 72 万节）；purge 停摆是全库范围的 |
| "把长事务杀掉就好了" | 杀掉只治标——**purge 要追上来还需要时间**，而且杀之前大事务回滚本身也要花时间（要撤销的更多）。**重点在预防：超时参数 + 代码纪律** |
| "MySQL 和 PG 的长事务是一回事" | **机制同源、症状不同**：MySQL 的版本在 **undo log** → 症状是 **undo 表空间膨胀 + 回溯变慢**；PG 的版本在**堆里** → 症状是**表与索引膨胀 + 阻塞 VACUUM**（[[母题-P14-长事务与表膨胀]]、[[母题-P15-VACUUM与事务ID回卷]]） |

【取舍】读成一句话：**长事务按住的是"回收边界"和"锁"两样东西——只读事务只按其中一样，但那一样是全库范围的。**

## 二、自测

**Q1（计算）**：一行数据每秒被修改 **100 次**。一个**只读**事务持有了 ReadView 整整 **2 小时**。设每次可见性判断约 **100 纳秒**。

问：**这条行的版本链上大约有多少节？一次快照读在这一行上的回溯开销是多少？**对比链长为 10 节的正常情况。

**A1**：

```text
版本链长度 = 100 次/秒 × 7200 秒 = 720,000 节（72 万）

回溯开销 = 72万 × 100ns = 72,000,000 ns = 72 毫秒

正常情况（链长 10 节）：10 × 100ns = 1 微秒
放大倍数 = 72ms ÷ 1μs = 72,000 倍
```

【结论】**一个"什么都没干"的只读事务，能让别人读这一行慢 72 毫秒**——而**这条链完全是它造成的**。

【补充】注意这是**单行**的代价。如果这个长事务影响到的是热表上的多行，代价会成倍叠加；而且**它拖住的是全库的 purge**，不只这一行。

**Q2（计算）**：一个批量更新任务要改 **100 万行**，总耗时 **100 秒**。每次更新产生约 **200 字节** undo。

问：**单事务提交和每 1000 行分批提交，分别在"锁持有时间"和"undo 峰值"上差多少？**

**A2**：

```text
单事务（一次提交）：
  锁持有 = 整个任务时长 = 100 秒
  undo 峰值 ≈ 100万 × 200B = 200 MB

分批（每 1000 行一批，共 1000 批，每批约 0.1 秒）：
  锁持有 = 单批时长 = 0.1 秒
  undo 峰值 ≈ 1000 × 200B = 200 KB

锁持有：100 秒 → 0.1 秒      （1/1000）
undo 峰值：200 MB → 200 KB   （1/1000）
```

【结论】**同样的工作量、同样的总时长，"分批"把锁持有和 undo 峰值各降到 1/1000。**

【补充】分批还顺带解决了另外两个问题：**主从复制**——单事务是一条巨大的 binlog，从库要整体重放（[[母题-M14-主从复制与延迟]]）；而 1000 条小事务可以并行。**所以"分批"是四张卡的公共答案**，这个判断要能自己说出来。

**Q3（判读）**：下面三种连接，**哪些会拖住 undo 回收？**请说明理由。

```text
A. autocommit = 1（默认），执行了一条 SELECT，已经返回
B. SET autocommit = 0; 执行了一条 SELECT; 然后连接一直挂着没提交
C. BEGIN; UPDATE ...; 然后连接一直挂着没提交
```

**A3**：

| | 拖住回收？ | 理由 |
|---|---|---|
| **A** | **不会** | autocommit 下**单条查询自己是原子提交的**，语句结束 → 事务结束 → ReadView 释放 |
| **B** | **会** | `autocommit = 0` 之后**一条查询就隐式开了事务**，没提交 = **ReadView 一直活着** |
| **C** | **会，而且更重** | 既有 ReadView（走 MVCC 那条链），**又持有写锁**（走锁那条链）——**两条链全中** |

【结论】**判据是"事务有没有结束"，不是"这条语句是读还是写"。** B 是最容易被忽略的形态：**它在监控上 CPU 低、几乎无查询，看起来完全无害**，但它在按住回收边界。

【补充】**准确条件是"它持有 ReadView"**——所以 `autocommit = 1` 下的一条长查询（比如跑 10 分钟的 SELECT）**不构成长事务**（语句结束即释放）；**危险的是"显式开启事务之后挂着"**。这个区分要能主动说出来。

**Q4（纠错）**：下面这段话哪里不准确？

> "长事务的危害就是锁持有太久，把其他写请求都堵住了。"

**A4**：**只说了两条链里的一条。**

- 说对的那条：**锁持有久** → 其他写事务排队 → 死锁概率上升（[[母题-M10-锁与死锁]]）。
- **漏掉的那条（更重要）**：**ReadView 不释放 → purge 不敢清理旧版本 → undo 膨胀 → 快照读沿链回溯变慢**。这条链**对读的影响**才是长事务最普遍、也最难察觉的危害。
- **漏掉这条的后果是**：会得出"只读事务没关系"的错误结论——而只读事务恰恰**只触发这条链**。

【准确说法】"长事务按住两样东西：**ReadView（影响读，走 MVCC）和锁（影响写）**。前者让 undo 回收停摆、版本链变长、所有人的快照读都变慢；后者让写事务排队。**两条链来源不同，要分开说**——而且**只读事务会走第一条**。"

**Q5（纠错）**：下面这段话哪里不准确？

> "我们把 autocommit 关掉做批处理，性能好很多，而且都是只读操作，不会有锁的问题。"

**A5**：**"不会有锁的问题"是对的，但"只读就安全"是错的。**

1. **只读事务照样持有 ReadView** → 照样拖住 undo 回收。批量只读如果跑了很久不提交，**它会让整库的旧版本清不掉**。
2. **`autocommit = 0` 本身是风险源**——它把"一条查询"变成了"一个需要显式结束的事务"。**只要有一条路径忘了 `COMMIT`/`ROLLBACK`，就留下一个长事务**（Q3 的 B 类）。
3. **"性能好很多"这个收益要问清来源**：如果收益来自"少提交 N 次"，那**分批提交（每 1000 行一次）能拿到大部分收益，同时把事务时长压到单批**——不需要全程不开 autocommit。

【准确说法】"只读不等于无副作用——**它按住的 ReadView 会拖住 undo 回收**。`autocommit = 0` 要配**明确的超时兜底与代码纪律**；更好的做法是**分批提交**，而不是全程挂着一个事务。"

## 三、面试输出（学完再看）

**一句话结论**：长事务按住**两样东西**，所以危害是**两条独立的链**。走 MVCC 的那条：**ReadView 不释放 → purge 不敢清理它还可能读的旧版本 → undo 膨胀、版本链变长 → 快照读回溯变慢（一行每秒改 100 次、挂 2 小时就是 72 万节，单次回溯 72 毫秒）、回滚成本更高**。走锁的那条：**写锁持到事务结束 → 其他写事务排队 → 死锁概率上升**。**反直觉点：只读事务触发不了锁那条，但 MVCC 那条照样走**——最常见的真实形态是 `SET autocommit = 0` 之后跑了查询忘了提交，**这种连接 CPU 低、几乎无查询，监控上很不起眼，却在按住全库的回收边界**。监控口径：**盯最老事务的 `trx_started`**（PG 侧对应最老事务的 `xmin`）。

**恢复关键词**：按住两样东西（ReadView / 锁）/ purge 的清理判据是"没有 ReadView 还需要它" / 版本链 100×7200 = 72 万节 / 回溯 72ms，正常 1μs / 只读事务也危险（它只走 MVCC 那条）/ `autocommit = 0` 忘了提交 = 最常见的真实事故 / 五条纪律（事务里不做 RPC、不做计算、批量分批、注意导出）/ **分批把锁持有与 undo 峰值各降到 1/1000** / 盯最老 trx_started / MySQL 是 undo 膨胀、PG 是表膨胀

**核心不变量 / 主线**：
**长事务最可怕的不是"执行久"，而是它会持续占着数据库资源，让整个系统越来越难受。**
**它不是"慢"，是"按住资源的柄"**——而那个柄（ReadView）**是它自己的，代价却是全库的**。

**完整回答骨架**：先说是两条链 → 走 MVCC 的那条（ReadView → purge → undo 膨胀 → 回溯变慢，给算式）→ 走锁的那条 → **只读事务为什么也在其中** → 五条纪律 + 分批的量化收益 → 监控盯最老 trx_started → 收束到"MySQL 是 undo 膨胀、PG 是表膨胀，机制同源症状不同"

**追问**（先说后看）

1. **undo 膨胀了怎么办？** —— **先杀掉肇事的长事务**（purge 立刻恢复推进），**再等 purge 追上来**。**但预防才是重点**：超时参数 + 代码纪律（事务里不做 IO）。**这条和 PG 的"先治因再回收"完全同构。**
2. **为什么两边（MySQL/PG）都会因为长事务出事，但表现形式不一样？** —— **因为版本存放位置不同**：MySQL 的版本在 **undo log** → 症状是 **undo 表空间膨胀与回溯变慢**；PG 的版本在**堆里** → 症状是**表与索引变大（表膨胀）**。**机制同源（长事务按住回收），症状不同**——**能说出这句对照，就超过了 90% 的候选人。**
3. **怎么找到是谁把 purge 卡住的？** —— **查最老的事务**：`information_schema.innodb_trx` 的 `trx_started` 与正在执行的语句（MySQL 8.0 的 `performance_schema` 更完整）。**判据是"最老的 ReadView"，不是"最慢的语句"。**
4. **长查询（没开事务）会拖吗？** —— **`autocommit = 1` 时单条查询原子提交、结束即释放**，不构成长事务；**危险的是"显式 BEGIN 之后挂着"**。**准确条件是"它持有 ReadView"**。
5. **批量更新一百万行为什么要分批？** —— **一次解决四个问题**：① 事务过长（本卡）；② 单事务的 undo 与 redo 都大；③ **大事务在主从复制里是一条 binlog，从库要整体重放**（[[母题-M14-主从复制与延迟]]）；④ **锁持有范围大**（[[母题-M10-锁与死锁]]）。**"分批"是四张卡的公共答案。**

**同类变体**

- 「怎么在代码层面避免长事务？」——三条：**事务里不做 IO**（RPC / 文件 / 缓存都不行）、**只包必须的数据库动作**、**批量走分批提交**。再加一道兜底：**设置事务超时**（`innodb_lock_wait_timeout` / 应用层超时）。
- 「长事务和死锁是什么关系？」——长事务**提高死锁概率**（锁持有久 → 交叉等待的窗口变大），但**它不是死锁的原因**（死锁的原因是加锁顺序不一致，[[母题-M10-锁与死锁]]）。**两者要分清。**
