## 一、教材

### 1. 前提：锁怎么跨过进程边界

#### 1.1 为什么单机锁不够【事实】

【事实】**单机锁（`mutex` / `synchronized` / 行锁）的可见范围止于一个进程**——因为它本质上是**同一块内存里的一个标记**，而两个进程各有自己的地址空间（[[母题-O1-上下文切换与死锁]] 1.1）。

【推导】**要跨机器，就必须把"锁的状态"放到一个两个进程都能访问的地方**——于是有三种选择：

```
① 放在一个高性能的共享存储里     → Redis（最常见）
② 放在本来就是权威状态的数据库里 → 唯一约束 / 带条件更新
③ 放在一个专门的强一致协调服务   → ZooKeeper / etcd
```

**记住这个分类方式**：**先问"我能不能把锁放到已经有的组件里"**，答案常常是"能"——**引入新组件是最后一步，不是第一步**。

#### 1.2 先问一个更重要的问题：真的需要锁吗？【取舍】

【推导】**分布式锁是并发控制里最重的方案**，因为它引入了一个**新的可用性依赖**：锁服务挂了，业务就卡住了。所以顺序应该是：

| 顺序 | 方案 | 什么条件下够用 |
|---|---|---|
| **① 幂等** | 唯一约束 + 幂等键 | **只要"重复执行无害"就够了**——绝大多数场景都属于这一类 |
| **② 条件更新** | `UPDATE ... WHERE 条件` | 要"只生效一次"且状态在数据库里 |
| **③ 队列串行** | 把竞争收进队列，单消费者处理 | 该资源的处理本来就可以排队 |
| **④ 分布式锁** | 见下 | **上面都不行**：必须"同一时刻只有一个在跑"，且跑的过程本身不能被重复（比如调度外部定时的批处理） |

【取舍】**关键判据**：**你要的是"不会被重复执行"，还是"不会同时在跑"？**

- 前者 → **幂等就够了**（不需要锁）
- 后者 → 才可能需要锁（典型的例子：**只应该有一个实例去执行的定时任务**）

【事实】**RuleArena 的选择正是①**：**Redis 只负责队列、限流与短期进度，权威状态在 PostgreSQL**——用"稳定幂等键 + 唯一约束"消化重复，**不引入分布式锁**。**它连"锁"都没用，却得到了同样的正确性保证。**

**到这里你应该能回答**：为什么"要不要用分布式锁"应该排在"能不能幂等"之后问？

### 2. 三种实现：各自解决什么、代价是什么

#### 2.1 Redis【事实】

::figure distributed-lock-fencing.svg | 分布式锁的三种实现、三大失效场景与 fencing token | 锁过期而持有者还活着时会同时出现两个持有者；只有资源侧校验 token 才真正安全

【事实】**Redis 做锁的核心是一条原子命令**：

```
SET lock:key <唯一值> NX PX <毫秒>
    NX = 只有 key 不存在时才设置（= 抢锁成功）
    PX = 同时设置过期时间（防止持有者挂掉后锁永不释放）
```

【推导】**三个必须做对的地方**：

| 要做的 | 为什么 |
|---|---|
| **加锁必须用一条命令**（`SET ... NX PX`） | 如果拆成"先 `SETNX` 再 `EXPIRE`"，中间挂了就是**死锁**（锁永不过期） |
| **值要是唯一标识**（UUID / 实例 ID） | 释放时才能确认"这是不是我加的锁" |
| **释放必须校验值**（`GET` 比对 + `DEL`，或直接用 Lua 脚本） | 否则会出现**误删别人的锁**：自己超时过期了，别人拿到锁，自己这时 `DEL` 一下把别人的删了 |

【事实】**Redis 锁的天然弱点**：**主从复制是异步的**——写进主节点、还没同步到从节点时主挂了，从节点被提升为新主，**那把锁就"没存在过"**，另一个人可以立刻拿到。**Redlock（向多个独立 Redis 实例加锁）就是为了缓解这个问题而提出的**（它也有公开争议，见 3.4）。

#### 2.2 数据库【事实】

【推导】**数据库本来就有"让一件事只发生一次"的能力**，用它是三种里**最不需要引入新组件**的：

| 做法 | 怎么用 | 代价 |
|---|---|---|
| **唯一约束**（推荐） | 往锁表插一条 `(资源名)` 唯一索引记录，插不进去就是没抢到 | **最简单、语义最硬**；释放就是删记录 |
| **带条件更新** | `UPDATE 锁表 SET 持有者 = ? WHERE 资源 = ? AND 过期时间 < now()` | 不需要单独的"抢锁"语句，还能顺便带过期 |
| **`SELECT ... FOR UPDATE`** | 在事务里锁住那一行 | 持锁时间 = 整个事务，**把并发压在数据库上** |

【取舍】**数据库做锁的最大代价是"锁争用直接压在数据库上"**——**锁本身也是流量**。如果这把锁每秒要被抢几百上千次，你其实是在用数据库做一件 Redis 更擅长的事。

【事实】**EnergyOps 用的正是"带条件更新"这一档**：任务抢占不用锁服务，而是一条 `UPDATE ... WHERE 状态 = 待处理 AND 租约版本 = 我看到的`——**改到 0 行就是没抢到**（`02-aggregation-and-recovery.md`）。

#### 2.3 ZooKeeper / etcd【事实】

【事实】这两者都是**强一致的协调服务**，做锁的方式与 Redis 不同：

| | 机制 | 特点 |
|---|---|---|
| **ZooKeeper** | **临时顺序节点** + watch：排队、最小的那个拿到锁；**会话断开则节点自动删除** | **锁与会话绑定**——客户端崩了锁自动释放，不用等 TTL |
| **etcd** | **租约（lease）+ revision**：revision 单调递增，**天然可以当 fencing token** | 语义最干净，**但要维护一套独立的强一致集群** |

【推导】**它的优势正好补上 Redis 的两个短板**：① **不怕"客户端挂了但锁没释放"**（会话结束即释放）；② **revision 单调递增，能直接做 token**。**代价是要多维护一套系统**，对校招项目通常是过重的。

**到这里你应该能回答**：为什么"锁要跟会话绑定"比"锁要设过期时间"更强？

### 3. 失效的根因：锁服务的判断 ≠ 客户端的事实

#### 3.1 三大失效场景【推导】

【推导】**所有失效都来自同一个根因**：**"锁是否还被持有"这件事，由锁服务根据时间判断；而"我是不是还在跑"这件事，只有客户端自己知道——两者会脱节。**

| 场景 | 发生了什么 | 结果 |
|---|---|---|
| **① GC 停顿 / 线程长时间阻塞** | 业务还没跑完，但**进程被暂停了**，没来得及续期 → **锁过期** | 另一个人拿到锁，**两个人同时在跑** |
| **② 时钟漂移** | 过期判断依赖时间，**机器之间时钟不一致** | 过期时刻算错，窗口提前或延后 |
| **③ 网络分区** | 客户端与锁服务之间断了；锁服务按租约到期释放 | 客户端**仍然认为自己持有**，继续写 |

【推导】**所以 TTL 的设置是一个无解的两难**（自测 Q1 会完整算）：

```
TTL 设短 → 业务没跑完就过期 → 【两个持有者】
TTL 设长 → 持有者真挂了要等很久才释放 → 【可用性变差】
```

**【没有"安全值"，只有"选哪种失效"。】** 这句话是这道题的分水岭。

#### 3.2 续期只能降低概率，不能消除【推导】

【推导】**"看门狗"式续期（后台线程定期把 TTL 顶回去）能缓解，但缓解不了根因**：

```
续期线程也是这个进程里的线程
→ 进程被 GC 暂停 / 被 SIGSTOP / 网络分区时，【续期和业务一起停】
→ 停的时间超过 TTL，锁照样过期
→ 而业务可能在恢复后继续执行 —— 于是两个持有者
```

【取舍】**判据**：**续期把"锁过期"的概率从"业务超时"降到"进程被暂停超过 TTL"**——后者概率更低，但**在 GC 停顿长的语言（大堆 JVM）里一点也不低**。

#### 3.3 真正的解法：fencing token【推导】

【推导】**换一个方向想**：**如果"锁"不能保证互斥，那就别让"锁"负这个责任。**

```
fencing token 的做法：
  ① 每次发出锁的时候，附带一个【单调递增】的号（1, 2, 3, …）
  ② 写操作带上这个号
  ③ 【被保护的资源自己校验】：只接受号比上次更大的写入
     → 旧持有者的写入一定被拒绝
```

【推导】**为什么这样才真正安全**：

```
即使发生了"两个人同时持有"（GC / 分区 / 时钟任何一种）
  旧持有者（token = 33）写 → 资源发现当前已见过 34 → 【拒绝】
  新持有者（token = 34）写 → 接受
→ 互斥性由【资源侧】保证，不再依赖锁服务的判断
```

【取舍】**代价**：**被保护的资源必须支持"带条件写"**（能比较 token）。如果资源不支持（比如你在写一个第三方 API，人家只认"覆盖"），**那就只能退到幂等**——**这就是为什么"锁"经常不如"幂等"划算**。

【事实】**etcd 的 revision 天然满足"单调递增"**，所以它能直接当 token；**Redis 需要一个额外的单调计数器**（`INCR`）来实现。

#### 3.4 Redlock 的争议：共识部分怎么讲【了解】

【取舍】**面试里如果被问到，讲共识、别站队**：

| 共识 | 内容 |
|---|---|
| **单实例 Redis 锁在主从切换时会丢** | 因为复制是异步的——**这是双方都同意的问题** |
| **Redlock 想做的是"多数派加锁"** | 向 N 个独立实例加锁，多数成功才算拿到 |
| **争议点是"它在极端场景下是否还能保证互斥"** | 反对一方指出：**它依赖假设的时钟漂移上限与有限停顿**，而这些假设在真实系统里可能不成立；**支持一方认为这些场景极罕见** |
| **双方都会同意的一句话** | **需要严格正确性时，应该用 fencing token；讨论"用哪种锁"之前先讨论"资源侧能不能校验"** |

【了解】**面试里给这一句就够了**：*"Redlock 争的是概率边界；但无论哪种锁，要严格保证互斥，最终都要靠被保护资源侧的 token 校验——锁只能降低概率。"*

**到这里你应该能回答**：为什么"用了分布式锁还是可能重复执行"这件事无法靠"换一个更好的锁"解决？

### 4. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "加个过期时间就安全了" | 【推导】**过期时间只能解决"持有者挂了锁不释放"，解决不了"持有者还活着但锁过期了"**。后者会直接产生**两个持有者**（GC / 分区 / 时钟三种成因） |
| "分布式锁保证了互斥" | 【推导】**严格说：不能**。它给的是"**大概互斥**"——除非**被保护的资源自己校验单调递增的 token**。**锁降低概率，资源侧的校验才给保证** |
| "用 Redis 锁就够了" | 【事实】**单实例 Redis 锁在主从切换时会丢**（异步复制）。而且它**引入了一个新的可用性依赖**：Redis 挂了，业务也卡住 |
| "先加锁再说，锁总归是保险的" | 【取舍】**锁是并发控制里最重的方案**。先问"能不能幂等 / 条件更新 / 队列串行"——**大多数场景用幂等就够了，而且不依赖锁服务的可用性** |
| "续期（看门狗）能彻底解决过期问题" | 【推导】**不能**：续期线程也在同一个进程里，**进程被暂停时续期和业务一起停**。它只是把概率降低 |
| "锁要设过期时间，所以要选个合适的值" | 【推导】**这个值没有安全解**（Q1 的两难）：短了会双持有者，长了可用性差。**正确动作是加 fencing token，而不是继续调 TTL** |
| "释放锁直接 `DEL` 就行" | 【事实】**会误删别人的锁**——你超时过期后别人拿到了锁，你这时 `DEL` 删的是别人的。**必须校验值**（比对 + 删除，或 Lua 保证原子） |
| "加锁和 `SETNX` 加 `EXPIRE` 一样" | 【事实】**不一样**：两条命令中间挂了就是**死锁**（锁永不过期）。**必须用一条 `SET ... NX PX`** |
| "分布式锁能保证任务只执行一次" | 【取舍】**不能**。要"只执行一次"应该用**幂等**（[[母题-Q2-重复与乱序]]）。**锁能保证"不同时跑"，保证不了"不重复跑"** |
| "ZooKeeper 锁比 Redis 锁性能差，所以不用" | 【取舍】**两条都对一半**：ZK 的强一致语义确实更干净（会话绑定、revision 可做 token），代价是要多维护一套集群。**选型看"你已经有哪个"与"正确性要求有多硬"** |

## 二、自测

**Q1（计算）**：某定时批处理需要分布式锁保护。已知：业务处理 **P99 = 200 ms**，但该进程用的是大堆 JVM，**实测最长 GC 停顿 3 s**。

问：① 锁的 TTL 设成 1 s 会怎样？② 设成 5 s 呢？③ 有没有安全值？④ 正确的解法是什么？

**A1**：

```
① TTL = 1 s：
   GC 停顿 3 s > TTL 1 s
   → 在这 3 s 里锁已经过期，别人拿到锁开始跑
   → GC 结束后，原持有者【继续执行】（它并不知道锁已失效）
   → 【两个持有者同时在跑】

② TTL = 5 s：
   最长停顿 3 s + 业务 0.2 s = 3.2 s < 5 s
   → 正常情况下【不会双持有者】
   但代价：如果持有者真的崩了，这把锁会【卡死最多 5 s】才释放
   → 对高频场景是可用性问题（别人白等 5 s）
```

③ **没有安全值**：

```
TTL 必须 > 最长停顿 + 业务耗时，否则会双持有者
TTL 又必须足够小，否则崩溃后恢复慢
→ 而"最长停顿"本身是【不可预知且无上界】的（GC 停顿取决于堆与回收器，
  还可能被 SIGSTOP / 换页 / CPU 争抢进一步拉长）
→ 所以这个不等式【没有可靠解】
```

④ **正确解法（按优先级）**：

| 顺序 | 做法 | 说明 |
|---|---|---|
| **1** | **问一句：能不能不用锁？** | 批处理通常可以做成**幂等**（按窗口 / 批次键），重复执行无害——**这是最省事的解** |
| **2** | **加 fencing token** | 每次发锁带一个单调递增号，**写入时由存储校验"只用更大的号"** → 即使双持有者，旧的写会被拒 |
| **3** | **把锁与会话绑定**（ZK / etcd） | 进程死了锁自动释放，不用等 TTL——**但进程"暂停"（GC）时租约也会过期，所以仍要 token** |
| **4** | 缩短停顿本身 | 换回收器、把大堆拆小、把批处理做成**分批 + checkpoint**（每批重新抢锁） |

【取舍】**第 4 条里的"分批 + checkpoint"值得单独说**：**把"一次持锁跑 10 分钟"改成"每 30 秒一批、每批重新抢锁"**——这样即使某一批的锁过期，**损失也只有一批的工作量**，而且和"锁可能失效"这个前提自洽（**这正好对上 [[母题-A4-长任务状态与Checkpoint]] 的思路**）。

【这一步在验证什么】验证 3.1 的核心结论：**TTL 的两难没有安全解，所以正确方向是"加 token"或"让重复无害"，而不是继续调 TTL。**

**Q2（计算）**：某服务用 Redis 锁保护一个"**每秒 100 次、单次 1 ms**"的操作，锁用"加锁 + 业务 + 释放 + 看门狗续期"。

问：① 这把锁每次操作要多花几次网络往返？② 如果换成"幂等键查重"，要多花几次？③ 两者的可用性风险差在哪？

**A2**：

```
① Redis 锁：SET NX PX（1 次往返）+ 释放用 Lua（1 次往返）+ 续期（每 TTL/3 一次）
   → 至少【2 次往返】，如果 TTL 短还要加续期
   按 0.1–1 ms/次往返估：锁本身就要 0.2–2 ms
   ★ 而业务本身只有 1 ms —— 【锁的开销和业务同一量级】

② 幂等查重：一次 GET（1 次往返）+ 写入时唯一约束（本来就要写）
   → 【1 次往返】，而且这条查询还能合并进业务写入
```

③ **可用性风险完全不同**：

| | 依赖 | 挂了会怎样 |
|---|---|---|
| **Redis 锁** | **Redis 必须可用** | Redis 挂 → **业务直接卡住**（连"降级跑一遍"都不敢，因为怕重复） |
| **幂等** | **只依赖自己的数据库** | 查重用的 Redis 挂了 → 退到**数据库唯一约束**照样正确（只是慢一点） |

【取舍】**结论**：**在这个场景里幂等全面胜出**——更少的往返、不引入新的可用性依赖、而且"重复执行"这件事本来就是模型允许的。**锁只有在"重复执行绝对不可接受"时才有必要。**

【这一步在验证什么】验证 1.2 的判据：**先问"能不能幂等"，能就千万别上锁。**

**Q3（判读）**：下面这段"释放锁"的代码有什么问题？会出现什么现象？

```python
# 加锁
ok = redis.set("lock:order", instance_id, nx=True, px=30000)
if not ok:
    return "busy"

try:
    do_business()          # 可能超过 30 秒
finally:
    redis.delete("lock:order")   # ← 直接删
```

**A3**：**两个问题，一个比一个隐蔽。**

```
问题 ①：释放时不校验持有者 → 【可能删掉别人的锁】
   T0  实例 A 加锁成功（TTL 30s）
   T30 业务还没跑完，锁【自动过期】
   T31 实例 B 加锁成功，开始跑
   T32 实例 A 的业务终于跑完，执行 redis.delete("lock:order")
        → 删掉的是【实例 B 的锁】！
   T33 实例 C 加锁成功 → 于是 B 和 C 同时认为自己持有
   → 一个删锁动作，制造了一次双重执行

问题 ②：业务可能超过 30 秒 → 【锁过期而业务还在跑】
   这就是 3.1 的 GC 场景的同族问题（这里是"业务本身就慢"）
```

**修法（两层，缺一不可）**：

| 层 | 做法 |
|---|---|
| **释放要校验值** | `if redis.get(key) == instance_id: redis.delete(key)`，**用 Lua 保证"比对 + 删除"原子** |
| **业务不能假定锁一定还在** | **写入侧带 fencing token，由存储校验**；或把长业务改成**分批 + 每批重新抢锁**（Q1 的第 4 条） |

【这一步在验证什么】验证 2.1 的三个"必须做对的地方"，以及 3.3 的核心：**锁侧的所有修补都只能降低概率，"业务不能假定锁还在"才是根本。**

**Q4（纠错）**：下面这段话哪里错了？

> "分布式锁加个过期时间就安全了——反正持有者挂了锁会自己释放，不会出现两个人同时跑。"

**A4**：**把"过期"当成了"安全"，方向反了。**

**过期时间解决的是 A，制造的是 B**：

```
✅ 它解决的：持有者【崩溃】后锁不释放 → 死锁  （A）
❌ 它制造不出保证的：持有者【还活着但卡住了】→ 锁过期 → （B）
```

**(B) 的三种成因**：

| 成因 | 机制 |
|---|---|
| **GC 停顿 / 线程被挂起** | 业务没跑完，进程被暂停，来不及续期，**锁过期了但它还在跑** |
| **时钟漂移** | 过期判断依赖时间，机器间时钟不一致 |
| **网络分区** | 锁服务按租约释放，客户端仍认为自己持有 |

**这三种情况都会产生"两个持有者"**——而**过期时间再长也解决不了**，因为：
**TTL 必须 > 最长停顿，而"最长停顿"是不可预知且无上界的**（自测 Q1 已算：TTL 短了双持有者、长了可用性差，**没有安全值**）。

**正确说法**：

> **要严格保证互斥，必须让"被保护的资源"自己校验单调递增的 token（fencing token）**——锁只降低概率，**资源侧的校验才给保证**。如果资源不支持带条件写，那就退到幂等（[[母题-Q2-重复与乱序]]），**而不是继续调 TTL**。

**Q5（纠错）**：下面这段话哪里错了？

> "这个任务只能执行一次，所以要加分布式锁；加锁之后就不会重复执行了。"

**A5**：**需求说对了，方案选错了——"只执行一次"是幂等问题，不是锁问题。**

**分清两件事**（这是本卡最重要的一次区分）：

| 你要的 | 该用什么 | 为什么 |
|---|---|---|
| **不同时跑** | 锁 | 锁的语义是"**互斥**"——它只保证同一时刻只有一个持有者 |
| **不重复执行** | **幂等** | 锁**保证不了**这一点：锁过期后别人拿到锁，同一个业务就被执行了第二次 |

**所以"加锁之后就不会重复执行"是错的**——Q3 的代码已经演示了：**一个误删锁的动作就能制造出双重执行**；再加上 GC、分区、时钟任何一种，**锁都会失效**。

**正确做法是"幂等 + （必要时）锁"**：

```
① 先让"重复执行"变得无害：稳定幂等键 + 唯一约束 / 条件更新
   → 这一步做完，"重复执行"就已经不构成问题了
② 只有在"重复执行代价极高"（同时跑会互相干扰、会打爆下游）时，
   才额外加锁把并发度收到 1
   → 而这时锁的作用是【减少干扰】，不是【保证正确性】
③ 如果确实需要严格的互斥保证 → 再加 fencing token
```

【事实】**RuleArena 就是①的极端形态**：**它连锁都没用**——靠"稳定幂等键 + 同事务唯一约束"，**系统坦然接受"队列至少一次投递 + Worker 随时崩溃"**，业务副作用仍然只生效一次。

**准确说法**：*"只执行一次"要靠幂等（幂等键 + 唯一约束），不是靠锁；锁只能降低"同时在跑"的概率，而且受 GC / 时钟 / 分区影响。顺序是：先幂等，再（必要时）加锁减少干扰，最后才考虑 fencing token。*

## 三、面试输出（学完再看）

**一句话结论**：跨机器互斥要把锁状态放到一个共享的地方，三种实现各有代价：**Redis**（`SET ... NX PX` 一条原子命令 + 释放要校验值；**弱点是主从异步复制，切换会丢锁**）、**数据库**（唯一约束 / 带条件更新，**不引入新组件但把锁争用压在数据库上**）、**ZooKeeper / etcd**（临时顺序节点 / 租约 + 单调 revision，**语义最干净但要维护一套强一致系统**）。**它们的共同弱点来自同一个根因：锁服务的判断（按时间）与客户端的事实（是不是还在跑）会脱节**——**GC 停顿、时钟漂移、网络分区**都会产生"两个持有者"，而 **TTL 没有安全值**（短了双持有者、长了可用性差，且"最长停顿"无上界）。**所以真正的解法是把安全性搬到被保护的资源上：fencing token（单调递增号）+ 资源侧拒绝更小的号**。但更该先问的是：**"我到底要'不同时跑'还是'不重复执行'？"**——**后者靠幂等就够了**（RuleArena 连锁都没用），锁只在地一步之后才考虑，而且它的作用是"减少干扰"，不是"保证正确性"。

**恢复关键词**：单机锁止于进程 / 三种实现（Redis / 数据库 / ZK-etcd）/ `SET ... NX PX` 必须一条命令 / 释放要校验值（否则误删别人的锁）/ Redis 弱点是异步复制丢锁 / 数据库做锁把争用压在库上 / ZK 会话绑定 + revision / **失效根因：锁服务按时间判断 vs 客户端的事实** / **GC 停顿 · 时钟漂移 · 网络分区** / **TTL 没有安全值** / 续期只能降概率（续期和业务一起停）/ **fencing token = 单调递增号 + 资源侧拒绝更小的号** / Redlock 争的是概率边界 / **"只执行一次"是幂等问题不是锁问题** / 先幂等 → 再锁减少干扰 → 最后 token

**核心不变量 / 主线**：
**锁能买到的只有"大概互斥"，买到"一定互斥"的从来不是锁，而是被保护资源自己的校验。** 所以判断顺序永远是：**先让重复无害（幂等）→ 再考虑用锁减少干扰 → 最后才用 token 补上保证**。**把这三步的顺序倒过来（先加锁、以为就安全了）是这一块最典型的错。**

**完整回答骨架**：先问"真的需要锁吗"（幂等 / 条件更新 / 队列排在前）→ 三种实现的机制与代价 → **失效的根因（锁服务按时间判断 vs 客户端事实）** → 三大场景（GC / 时钟 / 分区）→ 用 TTL 两难说明"没有安全值" → 续期只能降概率 → **fencing token 才给保证** → Redlock 争议的共识部分 → 边界与误解

**完整回答（口述稿）**：
单机 mutex 的共享状态只在进程内可见；**跨机器互斥要把锁状态放到一个共享的地方**。三种实现各有代价：**Redis**（`SET ... NX PX` 一条原子命令 + 释放要校验值；**弱点是主从异步复制，切换会丢锁**）、**数据库**（唯一约束 / 带条件更新，**不引入新组件但把锁争用压在数据库上**）、**ZooKeeper / etcd**（临时顺序节点 / 租约 + 单调 revision，**语义最干净但要维护一套强一致系统**）。

它们的**共同弱点来自同一个根因：锁服务的判断（按时间）与客户端的事实（是不是还在跑）会脱节**——GC 停顿、时钟漂移、网络分区都会产生"两个持有者"，而 **TTL 没有安全值**（短了双持有者、长了可用性差，且"最长停顿"无上界）。看门狗续期只是缓解，不是根治（续期本身也会停）。

**所以真正的解法是把安全性搬到被保护的资源上：fencing token（单调递增号）+ 资源侧拒绝更小的号**。但**更该先问的是："我到底要'不同时跑'还是'不重复执行'？"**——后者用**幂等**就够了（更便宜、不引入新依赖），RuleArena 连锁都没用。

释放锁**不能直接 `DEL`**：你过期后别人拿到了锁，你这时 `DEL` 删的是别人的，等于一次删锁动作制造了双重执行；必须**校验值**（GET 比对 + DEL，用 Lua 保证原子）。Redlock 想用多数实例缓解丢锁，但依赖时钟漂移与停顿上限的假设；**两方都同意的是：要严格正确性就得用 fencing token**。

**分层要点**：
- **结论**：三种实现各有代价；共同弱点是时间判断与客户端事实脱节，根治靠 fencing token；先问"互斥还是不重复"。
- **推导链**：共享状态 → 三种实现 → 时间 vs 事实脱节（GC/时钟/分区）→ TTL 无安全值 → 安全性搬到资源侧 → 幂等可能比锁更划算。
- **量化**：没有安全的 TTL 值（"最长停顿"无上界）。
- **边界与常见误解**："加锁时间设长就安全"×；"Redis 锁万无一失"×（主从切换丢锁）；幂等常常比锁更便宜，RuleArena 就是例子。

**追问**（先说后看）

1. **锁过期了业务还在跑怎么办？** —— **加 fencing token**：发锁时给单调递增号，**写入由存储校验"只接受更大的号"** → 旧持有者的写被拒。**同时把长业务改成分批 + 每批重新抢锁**，把损失限制在一批内。
2. **为什么分布式锁不能保证互斥？** —— 因为它依赖"**锁服务对时间的判断**"，而这可能与"**客户端是不是真的在跑**"脱节（GC 停顿 / 时钟漂移 / 网络分区）。**TTL 的取值是个两难，没有安全解。**
3. **Redlock 有什么问题？** —— 它想用"向多数实例加锁"缓解单实例丢锁，但**反对意见指出它依赖假设的时钟漂移上限与有限停顿**；**两方都同意的是：要严格正确性就得用 fencing token。**（面试讲到这一层即可，不必站队）
4. **什么时候该用分布式锁、什么时候不该？** —— **先问"要的是不同时跑，还是不重复执行"**：后者用**幂等**（更便宜、不引入新依赖）；只有"重复执行的代价极高、必须串行"时才上锁。**RuleArena 连锁都没用，靠幂等键 + 唯一约束就够了。**
5. **释放锁为什么不能直接 `DEL`？** —— **会误删别人的锁**：你过期后别人拿到了锁，你这时 `DEL` 删的是别人的 → 于是"一个删锁动作制造了一次双重执行"。**必须校验值**（`GET` 比对 + `DEL`，用 Lua 保证原子）。

**同类变体**

- 「单机的 `mutex` 和分布式锁差别在哪？」——**共享状态的可见范围**：`mutex` 在同一块内存里（[[母题-O1-上下文切换与死锁]]），分布式锁在共享存储里。**前者的失败模式是死锁，后者的失败模式是"两个持有者"**
- 「选主（leader election）和分布式锁有什么区别？」——**本质同一件事**（都要"最多一个"），**但选主的持有期更长**，所以更依赖**租约 + 心跳 + token**；etcd 的 `election` 与 `lease` 就是为这个场景设计的
- 「数据库的唯一约束能当锁吗？」——**能，而且常常是更好的锁**：**不引入新组件、语义硬、和业务状态同事务**。代价是**锁争用变成数据库流量**（[[母题-P19-唯一约束与UPSERT]]）
- 「条件更新和分布式锁怎么选？」——**能用条件更新就别用锁**：它把"抢"变成"一条原子语句"，**不需要过期、不需要续期、不需要校验 token**（[[母题-L1-乐观锁与悲观锁]] 2.3）
