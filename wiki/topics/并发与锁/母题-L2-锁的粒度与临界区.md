## 一、教材

### 1. 前提：锁的成本有三笔，别只算"获取"那一笔

#### 1.1 三笔成本【事实】

【推导】**任何一把锁都有三笔账**：

| 成本 | 是什么 | 什么时候最大 |
|---|---|---|
| **① 记账开销** | 加锁 / 解锁本身的指令与原子操作 | 临界区**极短**时（开销占比高） |
| **② 等待成本** | 抢不到时要等（而且等的方式还有代价，见第 3 节） | 冲突率**高**时 |
| **③ 阻塞别人的时间** | 你持锁期间，别人干不了活 | 临界区**长**时 |

【推导】**①和③都随"临界区长度"变化，但方向相反**：

```
临界区越短 → ①的相对占比越高（可能"锁本身比干活还贵"）
临界区越长 → ③越严重（别人排队越久）

→ 所以"锁画多大/临界区多长"没有单向答案，要让 ① 和 ③ 在一个点上平衡
```

#### 1.2 临界区的定义【事实】

【**临界区（critical section）**】：**持锁期间执行的那段代码**。判断它画得对不对，只有一个标准：

> **"在这段代码里，我有没有做与'保护共享状态'无关的事？"**

【推导】**最常见的错误是把这些放进临界区**：

- **外部调用**（HTTP / RPC / 发消息）——**网络延迟完全不可控**
- **日志 / 序列化 / 大对象构造**
- **循环里的多条独立更新**（本该批量化或分段）

【取舍】**"把外部调用挪出临界区"通常是收益最大的一次改动**，因为它把"不可控的等待"从持锁时间里摘了出去——**这是 [[母题-L1-乐观锁与悲观锁]] 里说的"两边都改善"的动作**。

**到这里你应该能回答**：为什么"临界区短"本身不是目标，而"临界区里没有不属于它的东西"才是目标？

### 2. 粒度：在"冲突率"和"记账开销"之间选

#### 2.1 粒度决定冲突率【推导】

::figure lock-granularity.svg | 锁的粒度、冲突率与记账开销的三角，以及分段锁的算术 | 分段把单段冲突率降到约 1/N；但段数越多，记账与内存开销越高

【推导】**锁的粒度越大，覆盖的范围越大，冲突概率越高**：

```
1 把锁保护 100 万行  →  任何两个请求碰到一起都冲突（冲突率高，但记账便宜）
100 万把锁保护 100 万行 → 几乎不冲突（但每行一个锁对象，内存与记账开销大）
```

【推导】**这就是"分段锁 / 锁条带化（lock striping）"的全部内容**——**把一把锁变成 N 把，按 key 分派**：

```
单段（1 把锁）→ 期望尝试次数 = 1 / (1 − p)
分 N 段（均匀分布）→ 每段的并发压力降到约 1/N
                  → 单段冲突率降到约 p / N
                  → 期望尝试次数 ≈ 1 / (1 − p/N)
```

**代进去算一遍**（自测 Q1 完整算）：`p = 40%`、分 16 段：

```
单段：1 / (1 − 0.40) = 1.67 次   → 多干 67% 的活
分段：冲突率 ≈ 0.40 / 16 = 2.5%
      → 1 / (1 − 0.025) ≈ 1.026 次 → 多干 2.6% 的活
```

【推导】**收益看起来巨大，但它有前提，而且前提很容易被违反**：

| 前提 | 违反了会怎样 |
|---|---|
| **访问要均匀分散在各段** | 有一个"热键"时，它落的那一段照样被打爆——**分段救不了热点** |
| **一次操作只碰一段** | 如果一次事务要同时改多段（比如转账改两个账户），**就有了跨段加锁 → 死锁风险**（[[母题-O1-上下文切换与死锁]] 的循环等待） |
| **N 不要大到记账反超收益** | 段数过多 → 内存、cache 命中率、遍历开销都变差 |

【取舍】**所以"锁粒度越小越好"是错的**。正确的说法是：

> **在"访问能被均匀分散"的前提下，粒度小一点更好；一旦出现热点或跨段事务，粒度反而该往回加。**

**热点键为什么分段也救不了**：分段是按 key 分派的，**热键始终落在同一段**——这时候要用的不是"更多段"，而是**换方案**：本地聚合（先攒再写）、队列串行、或者把计数拆成"每节点一个累加器 + 定期汇总"（这是"无共享"的思路）。

#### 2.2 数据库里的同一件事【事实】

【事实】数据库的锁粒度是同一条逻辑（[[母题-M10-锁与死锁]]、[[母题-P10-无间隙锁与锁变体]]）：

| 粒度 | 冲突率 | 记账开销 |
|---|---|---|
| 表锁 | 高（任何两行都冲突） | 低 |
| **行锁** | 低（只有同一行冲突） | 高（要维护大量锁对象） |
| 间隙锁 / 范围锁 | **更高**（连"插入位置"都锁） | 更高 |

【推导】**所以"为什么 MySQL 用行锁"和"为什么要分段锁"是同一个答案**：**让冲突只发生在真正竞争的那一小块上**。**而补间隙锁的原因也一样**：防幻读需要锁"不存在的行"，**这是用更大的锁粒度换一致性**（[[母题-M8-隔离级别与ACID]]）。

**到这里你应该能回答**：为什么"分段"能提速，但"热键"不行？

### 3. 抢不到的时候：自旋还是睡眠

#### 3.1 两种等待方式【事实】

- **自旋（spin）**：**一直问"好了没"**，占着 CPU 不放手
- **睡眠（block / park）**：**放手，让别人跑**，等被唤醒

【推导】**判据只有一个比值**：

```
等待时间  vs  "挂起 + 唤醒"的两次上下文切换成本
```

【推导】**代进量级算一遍**（切换成本取 [[母题-O1-上下文切换与死锁]] 的量级 ~1 μs，两次约 2 μs）：

| 临界区 / 预计等待 | 该选什么 | 为什么 |
|---|---|---|
| **不到 1 μs** | **自旋** | 睡下去再醒过来（~2 μs）比等还贵，**而且自旋不占别人的锁** |
| **几微秒到几十微秒** | 先自旋一小会儿，再睡 | 这是"自适应自旋"的思路 |
| **毫秒级以上** | **睡眠** | 自旋会把整个时间片烧光，**而且占着 CPU 不让别人干活** |

【取舍】**"先自旋一会儿再睡"是工程上最常见的折中**——因为现实中"临界区到底多长"很难预知，**用一小段自旋去赌"马上就好了"，赌输再睡**。

#### 3.2 读写锁：读多写少不一定更快【推导】

【推导】**直觉是"读可以并行，所以读写锁更适合读多写少"，但有两个反直觉的地方**：

```
① 读写锁自己要额外记账（读计数、写者状态、锁升级判断）
   → 临界区【极短】时，这笔记账可能比省下的等待还贵

② 写者可能被饿死：读很多且持续不断时，写请求一直排在后面
   → 需要额外的策略（写者优先 / 公平模式），而公平模式又要更多记账
```

【取舍】**判据**：

| 场景 | 选什么 |
|---|---|
| 临界区极短（几条指令） | **普通互斥锁**往往更快——**读写锁的记账比省下的等待还多** |
| 读多写少 + 临界区**较长**（含计算 / 序列化） | 读写锁值得 |
| 读多写少 + 想彻底不互斥 | **考虑 MVCC / 快照**：让读走旧版本，根本不和写抢（[[母题-M9-MVCC]]） |

**到这里你应该能回答**：为什么"读多写少就该用读写锁"这句话是不完整的？

### 4. 不加锁：CAS 与它的三个边界

#### 4.1 CAS 是什么【事实】

**CAS（Compare-And-Swap）**：**一条原子指令**——"如果这个位置的值还是 A，就把它改成 B，否则什么都不做并告诉我失败了"。

【推导】**它把 [[母题-L1-乐观锁与悲观锁]] 的"乐观"下沉到了指令层**：

```
应用层乐观锁：读 version → 计算 → UPDATE ... WHERE version = N   （两次往返）
CAS：        比较 + 交换，一条指令完成                            （无锁、无排队）
```

【推导】**CAS 的典型用法是"循环重试"**：

```
do {
    old = load(p);
    new = f(old);          // 基于读到的旧值算新值
} while (!CAS(p, old, new));   // 只要中间被别人改了，就重新读、重算
```

#### 4.2 CAS 的三个边界【取舍】

| 边界 | 是什么 | 后果 |
|---|---|---|
| **① ABA 问题** | 值从 A 改成 B 又改回 A，**CAS 发现"还是 A"就通过了**，但它不知道中间变过 | 在"值本身不重要、但变化次数重要"的场景出错（如无锁栈的指针复用） |
| **② 激烈竞争下退化成"自旋烧 CPU"** | 大家都失败、都重试，**成功率低但耗着 CPU** | **比加锁更差**：加锁至少会让失败者睡下去 |
| **③ 只能保护一个变量** | 一次 CAS 只对一个内存位置原子 | 跨多个字段/多个对象的不变量，CAS 表达不了（要靠事务） |

【推导】**ABA 的解法不是"记住更多信息"这么简单**，常见三档：

```
① 加版本号一起 CAS（把 [值, 版本] 一起比较）—— 最常用
② 用带标记的指针（tagged pointer，把版本编进指针高位）
③ 干脆别用无锁结构，改用锁 + 简单逻辑（如果竞争激烈，这往往是更好的选择）
```

【取舍】**所以"无锁一定更快"是错的**：

```
低竞争（冲突率 ≈ 0）  → CAS 好：没有排队、没有阻塞
高竞争               → CAS 会大量失败重试，CPU 白烧
                       → 这时【加锁反而更好】：它把失败者变成"睡着等"，
                          而不是"醒着抢"
```

【事实】**EnergyOps 的"受控并发"正是这个道理的应用**：与其让大量任务自由抢（无论用锁还是 CAS），不如**显式限制并发数**——**"减少竞争"永远优先于"更好地处理竞争"**（`02-aggregation-and-recovery.md`）。

**到这里你应该能回答**：为什么"无锁"在低竞争下赢、在高竞争下输？

### 5. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "锁粒度越小越好" | 【推导】**有前提**：访问要能**均匀分散**。**出现热键或跨段事务时，粒度小反而更糟**（热点照样打爆那一段、跨段加锁带来死锁风险）。正确说法是"在能均匀分散的前提下，粒度小一点更好" |
| "分段锁能解决热点问题" | 【推导】**不能**。分段按 key 分派，**热键始终在同一段**。热点要靠换方案：本地聚合、队列串行、每节点累加器（无共享） |
| "读多写少就上读写锁" | 【取舍】**临界区极短时读写锁可能更慢**——它的额外记账比省下的等待还贵；还有**写者饥饿**问题。长临界区的读多写少才明显划算 |
| "无锁一定比加锁快" | 【推导】**看竞争强度**。低竞争下 CAS 赢（无排队、无阻塞）；**高竞争下 CAS 退化成"自旋烧 CPU"，加锁反而更好**（失败者会睡下去） |
| "CAS 能保证不出错" | 【事实】**有 ABA 问题**——值改走又改回来，CAS 看不出来。解法是**连版本号一起 CAS**（或用带标记指针） |
| "CAS 能保护整个对象" | 【事实】**一次 CAS 只对一个内存位置原子**。跨字段 / 跨对象的不变量它表达不了，要靠事务或把不变量收进一个字段 |
| "加锁就会阻塞" | 【取舍】**加锁也可以不自旋不阻塞**——"抢不到就睡"才是关键；而"抢不到就转圈"（自旋）在临界区极短时反而更快。**阻塞与否由等待策略决定，不由"有没有锁"决定** |
| "自旋锁一定比互斥锁快" | 【取舍】只有**临界区极短 + 多核**时才是。临界区长时自旋是**白烧 CPU 还占着调度资源**（[[母题-O1-上下文切换与死锁]] 4.3） |

## 二、自测

**Q1（计算）**：某计数器被并发更新，单锁下**冲突率 40%**，单次尝试耗时 **2 ms**。

问：① 期望尝试几次、多干多少活？② 拆成 16 段后（访问均匀）每段冲突率约多少、期望尝试几次？③ 如果其中一个 key 承担了 50% 的访问量，分段还有用吗？

**A1**：

```
① 单锁：期望尝试 = 1 / (1 − 0.40) = 【1.67 次】
       多干 = 67% 的活

② 分 16 段（均匀分布）：每段并发压力降到约 1/16
       单段冲突率 ≈ 0.40 / 16 = 【2.5%】
       期望尝试 ≈ 1 / (1 − 0.025) ≈ 【1.026 次】→ 多干 2.6%
```

③ **用处大打折扣**：

```
那个 key 落到其中一段，该段承担 50% 的访问量
→ 该段的冲突率仍会很高（而不是 2.5%）
→ 【热键所在的那一段就是瓶颈】，其余 15 段闲着
```

**热键的正确解法（按性价比）**：

| 做法 | 说明 |
|---|---|
| **本地聚合** | 先在进程内攒一批再写（比如每 100 次汇总一次）——**把 N 次竞争压成 1 次** |
| **队列串行** | 把该 key 的更新收进一个队列，单消费者处理（RuleArena 的思路） |
| **每节点累加器** | 每个实例各自加，定期汇总——**从"无共享"入手，而不是"更好的锁"** |
| **换存储模型** | 计数类场景用支持原子增的数据结构（Redis 的 `INCR` 是单线程 + 原子，天然没有这个问题） |

【这一步在验证什么】验证 2.1 的两条：**分段有效的前提是均匀分散；热键救不了，要换方案。**

**Q2（计算）**：某临界区里有一段**外部 HTTP 调用，平均 50 ms**；其余计算与写库共 **0.5 ms**。

问：① 乐观锁下"单次尝试"耗时多少？② 悲观锁下"持锁时间"多少？③ 该怎么改？改完两边的账各变成多少？

**A2**：

```
① 乐观锁：读 + 计算 + 外部调用 + 写 ≈ 50.5 ms
   （★ 注意：如果外部调用在"读"和"写"之间，那么【从读到写】的窗口是 50.5 ms，
     这个窗口越大，别人插进来改的概率越高 → 冲突率随之上升）

② 悲观锁：50.5 ms —— 但这 50.5 ms 里【别人全在排队】，
   吞吐上限 = 1 / 50.5ms ≈ 20 次/秒
```

③ **改法：把外部调用挪出临界区**，顺序调整成"先算好、再调用、最后用一条语句落库"：

```
改前：读 → 算 → 【HTTP 50ms】→ 写        窗口 50.5 ms
改后：读 → 算 → 写（短事务）→ 调用外部      持锁/窗口 ≈ 0.5 ms

收益：
  悲观锁吞吐上限：20 次/秒 → 约 2000 次/秒（差 100 倍）
  乐观锁冲突率：窗口从 50.5 ms 缩到 0.5 ms → 冲突率下降约两个数量级
```

【取舍】**代价要交代清楚**：改后可能出现"本地已提交、外部调用失败"——**这时必须靠幂等键 + 状态查询来补**（[[母题-Q2-重复与乱序]]、EnergyOps 的 `result_unknown`）。**"把外部调用挪出去"不是免费的，它把并发问题换成了最终一致性问题**——但那笔账通常好算得多。

【这一步在验证什么】验证 1.2：**临界区里最该挪走的是"不可控的等待"**，而且这一改动同时改善乐观与悲观两条路。

**Q3（判读）**：某服务读操作占 **99%**，读与写的临界区都是 **1 ms**，**QPS 1000**。有人提议把互斥锁换成读写锁，说"读能并行，吞吐能翻几倍"。

问：① 用互斥锁时吞吐上限是多少？② 换读写锁后理论吞吐能到多少、实际会怎样？③ 你会怎么决策？

**A3**：

```
① 互斥锁：所有请求（读 + 写）串行，每次 1 ms
   吞吐上限 = 1 / 1ms = 【1000 次/秒】
   → 刚好卡在 QPS 1000 上【没有余量】，P99 会很难看

② 读写锁理论上：读可以并行，只有写要独占
   但读仍受【读锁的记账 + 读之间的竞争】限制，不是无限并行；
   而且写会被持续的读"饿着"
   实际还要扣掉读写锁自己的记账开销 → 收益远小于"翻几倍"
```

③ **决策顺序**：

| 优先 | 动作 | 理由 |
|---|---|---|
| **1** | **先看这 1 ms 里有什么** | 如果含 IO / 序列化 → **挪出临界区**，比换锁有效得多（Q2） |
| **2** | **看能不能让读完全不和写抢**（MVCC / 快照 / 读副本） | **这才是"读多写少"的正解**：让读走旧版本，根本不参与竞争（[[母题-M9-MVCC]]） |
| **3** | 前两条都做不了，且读临界区确实较长 → **再上读写锁** | 并给它配"写者优先 / 公平"策略，防饥饿 |

【这一步在验证什么】验证 3.2 的判据：**"读多写少"的第一选择通常不是读写锁，而是"让读不参与竞争"**（MVCC / 快照 / 读副本）。

**Q4（纠错）**：下面这段话哪里错了？

> "锁的粒度越小并发越高，所以应该尽量把锁拆细；实在不行就用无锁 CAS，反正无锁肯定比加锁快。"

**A4**：**三处都错。**

1. **"锁粒度越小并发越高"有前提**：**访问要能均匀分散**。有一个**热键**时，它落的那一段照样被打爆（Q1 第 ③ 问）——**分段救不了热点，只会让你以为问题解决了**。

2. **粒度小还有两个代价**：

```
① 记账开销上升：锁对象更多、内存与 cache 占用更大、遍历更慢
② 跨段加锁 → 死锁风险：一次事务要改多段时，
   不同顺序加锁就构成"循环等待"（[[母题-O1-上下文切换与死锁]] 4.2）
```

**所以正确说法是**："**在能均匀分散、且一次只碰一段的前提下，粒度小一点更好**"。

3. **"无锁肯定比加锁快"错了**——**看竞争强度**：

```
低竞争（冲突率≈0）→ CAS 赢：无排队、无阻塞、一条指令
高竞争           → CAS 输：大量失败重试，CPU 白烧；
                   而加锁会把失败者【送去睡觉】，反而更好
```

【取舍】**而且这里有一个更根本的判断**：**"减少竞争"永远优先于"更好地处理竞争"**。**EnergyOps 的"受控并发"就是这个思路**——与其让 5000 个任务自由抢锁（无论用哪种锁），不如显式限制并发数。

**准确说法**：*粒度小有前提（均匀分散、无跨段事务），热键要靠"本地聚合 / 队列 / 无共享"解决；无锁与加锁的胜负取决于竞争强度——低竞争 CAS 赢，高竞争加锁赢；而最优先的动作永远是**减少竞争本身**。*

**Q5（纠错）**：下面这段话哪里错了？

> "用 CAS 实现了一个无锁计数器，压测时发现 QPS 比加锁还低，肯定是 CAS 有问题或者 CPU 不行。"

**A5**：**"CAS 有问题"或"CPU 不行"都是错误归因——这是 CAS 在高竞争下的典型表现，不是 bug。**

**机制**：

```
N 个线程同时对同一个位置 CAS：
  同一时刻只有一个能成功，其余全部失败
  失败的按写法【立刻重试】→ 又失败 → ……
→ 成功率和吞吐都很低，但 CPU 一直满载
→ 这就是"自旋烧 CPU"：失败者【醒着抢】，而不是睡下去等
```

**对比加锁**：加锁下失败者会被**挂起**（让出 CPU），虽然也有切换成本，但**不会持续占着核**——所以高竞争下加锁的吞吐反而更高。

**正确的三档处理（按优先级）**：

| 优先 | 动作 | 说明 |
|---|---|---|
| **1** | **减少竞争** | **最有效**。把单个计数器拆成"每线程/每节点一个"，最后汇总——**这就把 N 个写同一位置变成各写各的** |
| **2** | **换成加锁（或带退让的 CAS）** | 高竞争下让失败者睡下去，比让它继续抢好 |
| **3** | 给重试加**退避 / 让出 CPU** | `pause` 指令、`yield`、指数退避——**降低"抢"的频率** |

【取舍】**这里有一个可以直接用的话**：*"无锁的收益来自'几乎不冲突'，而不是来自'没有锁'。"* ——**低竞争时它免掉了排队与阻塞，高竞争时它把阻塞换成了空转**。**所以选它之前先估冲突率，而不是先看它是不是"无锁"。**

**准确说法**：*CAS 在低竞争下赢、高竞争下输，因为失败者会空转而不是让出 CPU。压测发现无锁更慢时，正确动作是减少竞争（分片/每线程累加）或改回加锁，而不是怀疑 CPU。*

## 三、面试输出（学完再看）

**一句话结论**：锁的粒度不是在"性能"和"开销"之间选，而是在**冲突率**和**记账开销**之间选——**分段锁（striping）把冲突率降到约 1/N**（p = 40% 分 16 段后从 1.67 次降到 1.03 次），**但前提是访问均匀分散；热键始终落在同一段，分段救不了它**，得换方案（本地聚合 / 队列串行 / 每节点累加）。**自旋还是睡眠由一个比值决定**：等待时间 vs "挂起 + 唤醒"约 2 μs 的成本——**临界区不到 1 μs 就自旋，毫秒级必须睡**；**读写锁在临界区极短时可能比互斥锁更慢**（记账比省下的等待还贵），"读多写少"的第一选择通常是**让读不参与竞争**（MVCC / 快照 / 读副本）。**CAS 把乐观并发下沉到了指令层**，但它有**三个边界**：ABA（要连版本号一起 CAS）、**高竞争时退化成"自旋烧 CPU"（这时加锁反而更好）**、一次只能保护一个变量。**而最优先的动作永远是：减少竞争本身。**

**恢复关键词**：三笔成本（记账 / 等待 / 阻塞别人）/ **临界区判据：有没有做不属于它的事** / 把外部调用挪出临界区（两边都改善）/ 分段把冲突率降到约 1/N / **前提：均匀分散、一次只碰一段** / **热键救不了（换方案）** / 行锁 vs 表锁是同一逻辑 / 自旋 vs 睡眠 = 等待时间 vs 两次切换（≈2 μs）/ 临界区 < 1 μs 自旋 / 读写锁有记账开销与写者饥饿 / **读多写少的正解是 MVCC / 快照** / CAS = 一条指令 + 循环重试 / **ABA → 连版本号一起 CAS** / **高竞争下无锁输给加锁** / 无锁收益来自"几乎不冲突" / 减少竞争 > 更好地处理竞争

**核心不变量 / 主线**：
**锁的一切参数（粒度、等待方式、有没有锁）都在服务同一件事——把"冲突"限制在真正竞争的那一小块上。** 分段是"缩小冲突范围"，自旋/睡眠是"选择怎么等待"，CAS 是"把等待变成重试"，而**最有效的永远是"让冲突根本不发生"**（无共享、聚合、队列）。

**完整回答骨架**：锁的三笔成本 → 临界区判据（挪走不可控等待）→ 粒度与冲突率的换算 + 分段锁的算式与三个前提 → 热键为什么救不了 → 数据库里的同一逻辑（行锁/表锁/间隙锁）→ 自旋 vs 睡眠的比值判据 → 读写锁的两个反直觉 → CAS 的原理、ABA 与三个边界 → **无锁与加锁的胜负取决于竞争强度** → 减少竞争优先 → 边界与误解

**完整回答（口述稿）**：
锁的粒度不是在"性能"和"开销"之间选，而是在**冲突率**和**记账开销**之间选——粒度太细会让锁对象变多、记账（获取/释放、内存、死锁检测）变贵，甚至超过省下的等待。

**分段锁（striping）把冲突率降到约 1/N**：p = 40% 分 16 段后，期望尝试次数从 1.67 降到 1.03。但前提是**访问均匀分散**——**热键始终落在同一段，分段救不了它**，得换方案（本地聚合 / 队列串行 / 每节点累加）；而且段数不能大到记账反超收益。

**自旋还是睡眠由一个比值决定**：等待时间 vs "挂起 + 唤醒"约 2 μs 的成本——临界区不到 1 μs 就自旋，毫秒级必须睡；工程上常用"先自旋一小会儿再睡"。

**读写锁在读多写少时不一定更快**：临界区极短时它的记账（读计数、写者状态、升级判断）可能比省下的等待还贵，还有写者饥饿；"读多写少"的第一选择通常是**让读不参与竞争**（MVCC / 快照 / 读副本）。

**CAS 把乐观并发下沉到指令层**，三个边界：**ABA**（值 A→B→A，CAS 看不出；解法是把版本号一起 CAS）、**高竞争时退化成自旋烧 CPU**（这时加锁更好）、**一次只能保护一个变量**。**最优先的动作永远是减少竞争本身**。

**分层要点**：
- **结论**：粒度在冲突率与记账之间权衡；分段锁约降 1/N，但救不了热键。
- **推导链**：记账 vs 等待 → 分段效果与前提 → 自旋/睡眠的 2 μs 判据 → 读写锁的记账成本 → CAS 的三个边界。
- **量化**：p=40% 分 16 段 → 期望次数 1.67 → 1.03；挂起+唤醒约 2 μs。
- **边界与常见误解**："无锁一定更快"×（高竞争时空转烧 CPU）；"读写锁读多写少必胜"×（临界区极短时反而更慢）。

**追问**（先说后看）

1. **怎么决定分几段？** —— **按"单段冲突率 ÷ 段数后仍可接受"反推**（Q1 的算式），同时**段数不能大到记账反超收益**。更关键的是**先确认没有热键**——有热键的话分段没用，先解决热点。
2. **自旋还是睡眠？** —— 看**等待时间与"挂起 + 唤醒"成本（约 2 μs）的比值**：短于它自旋（比如临界区不到 1 μs），长于它睡眠；**工程上常用"先自旋一小会儿再睡"**。
3. **读写锁什么时候会变慢？** —— **临界区极短时**：它的读计数、写者状态、升级判断这些**记账**可能比省下的等待还贵；另外还有**写者饥饿**。**"读多写少"的正解通常是 MVCC / 快照 / 读副本。**
4. **ABA 是什么、怎么解？** —— 值从 A 改到 B 又改回 A，CAS 看不出中间变过。**解法：把版本号一起 CAS**（`[值, 版本]` 同时比较），或用带标记的指针。
5. **无锁什么时候不该用？** —— **竞争激烈时**。失败者会**空转而不是让出 CPU**，CPU 白烧、吞吐反降。**这时加锁更好**（失败者睡下去）；**而更优先的动作是减少竞争**（分片、每线程累加、显式限制并发）。

**同类变体**

- 「为什么 MySQL 用行锁而不是表锁？」——**同一逻辑**：让冲突只发生在真正竞争的那一行；代价是锁对象更多、记账更贵（[[母题-M10-锁与死锁]]）
- 「为什么 InnoDB 还要间隙锁？」——**用更大的锁粒度换一致性**（防幻读），**这是"粒度"和"语义"之间的取舍**（[[母题-M8-隔离级别与ACID]]、[[母题-P10-无间隙锁与锁变体]]）
- 「连接池为什么不用一把大锁？」——连接池本质也是一个"共享资源池"，**分段/分桶**是它常见的优化方向；而**池子耗尽**是另一类问题（[[母题-N1-一次请求的完整路径]]）
- 「为什么 Redis 的 `INCR` 没有并发问题？」——**因为它把并发收成了单线程**：**不是"更好的锁"，而是"根本没有并发"**——这是"减少竞争"的极致形态
