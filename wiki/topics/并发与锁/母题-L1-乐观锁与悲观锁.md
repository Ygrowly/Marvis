## 一、教材

### 1. 前提：并发控制的目标不是"不出错"，是"给出错定价"

#### 1.1 两种方案，两种定价方式【事实】

**先各自介绍，再用同一指标衡量**（指标 = **同一个数据被并发修改时，谁的浪费更少**）：

**悲观锁（pessimistic）**：**先排队，再动手**。动手之前先拿到独占权（数据库的 `SELECT ... FOR UPDATE`、代码里的 `mutex`）。

**乐观锁（optimistic）**：**先动手，提交时校验**。读的时候记住一个"版本"，写的时候要求版本没变过；变了就说明中间被别人改过，**这次白干，重来**。

【推导】**两者不是"快慢"的关系，是"把代价花在哪"的关系**：

| | 悲观锁 | 乐观锁 |
|---|---|---|
| 什么时候付出代价 | **动手之前**（排队等） | **动手之后**（可能白干） |
| 最坏情况是什么 | **排队很长、可能死锁** | **反复冲突、一直重试** |
| 并发度 | **被压成串行**（同一份数据同一时刻只有一个持有者） | **不受锁限制**（只有写那一条语句会串行） |
| 适合什么 | 冲突率高、临界区短、重试代价大 | 冲突率低、计算便宜、能安全重试 |

【取舍】**所以合适的问法不是"哪个快"，而是**："**这段并发里，冲突发生得有多频繁？**"——**下一节把这个问题变成了一个算式。**

#### 1.2 一个必须先纠正的认知：乐观锁也加锁【纠错】

【事实】**"乐观锁就是不加锁"是错的**。以数据库为例：

```
悲观锁的写法（把锁跨越多条语句）：
  BEGIN
    SELECT stock FROM t WHERE id = 1 FOR UPDATE;   ← 在这里就拿到行锁
    ... 应用层计算 ...
    UPDATE t SET stock = 新值 WHERE id = 1;         ← 一直持锁到这里
  COMMIT                                            ← 才释放

乐观锁的写法（锁只覆盖一条语句）：
  UPDATE t SET stock = 新值, version = version + 1
   WHERE id = 1 AND version = 我之前读到的版本;      ← 这条语句本身也要拿行锁
```

【推导】**两条写法都要拿行锁，差别在"持有多久"**：

| | 持锁时间 | 由此推出 |
|---|---|---|
| 悲观锁 | **跨越"读 → 应用层计算 → 写"整段** | 计算越慢、外部调用越多，别人排队越久 |
| 乐观锁 | **只有那一条 `UPDATE`** | 计算再慢也不影响别人；**代价转移成"可能白干"** |

**【这就是"乐观锁更快"的真实含义】**：不是"不用锁"，而是**把持锁时间从"整个业务处理"压缩到"一条语句"**，代价是可能重来。**这句话说清楚，比背定义有用得多。**

**到这里你应该能回答**：为什么"乐观锁就是不加锁"这个说法在数据库场景里是错的？

### 2. 判据：冲突率多高才该换（本卡的核心算式）

#### 2.1 期望尝试次数【推导】

::figure opt-vs-pessimistic.svg | 乐观锁与悲观锁把成本花在哪，以及冲突率的判据 | 期望尝试次数 = 1/(1−p)；p = 10% 只要 1.11 次，p = 90% 要 10 次

设**冲突率 p** = 一次尝试被别人抢先的概率（假设各次尝试独立），那么**"成功一次"需要的尝试次数服从几何分布**：

```
期望尝试次数 = 1 / (1 − p)
```

【推导】**把几个 p 代进去，判据就出来了**：

| 冲突率 p | 期望尝试次数 | 多做的功（浪费比例） |
|---|---|---|
| 1% | **1.01** | 约 1% |
| 10% | **1.11** | 约 11% |
| 30% | **1.43** | 约 43% |
| 50% | **2.00** | 约 100%（等于全部白干一遍） |
| 70% | **3.33** | 约 233% |
| 90% | **10.0** | 约 900% |

【推导】**这个表就是本卡最重要的判据**：

```
p 小（几十个百分点以内）  → 乐观锁划算：多做的功可以忽略，而并发度没被限制
p 大（过半）              → 乐观锁开始"白干比干活还多"
p 很大（接近 1）          → 乐观锁基本就是"反复重试"，必须换方案
```

#### 2.2 两边的账要放在同一个坐标系里【推导】

```
乐观锁：处理 N 个请求，实际尝试 N / (1 − p) 次
        → 【多做的工作量】= N × p / (1 − p)
        → 好处：这 N 次尝试【可以并发进行】，不被锁串起来
           （只有最后那条 UPDATE 会短暂串行）

悲观锁：不浪费任何工作，但同一份数据的处理被【强制串行】
        → 吞吐上限 = 1 / 持锁时间
        → 好处：不会白干，冲突率再高也不受影响
```

【推导】**两者的分界不是"哪个快"，而是**：

> **"重试浪费掉的时间" 与 "排队等掉的时间" 哪个更长。**

而**这两个量都可以被同一件事压缩**——**缩短临界区**（[[母题-L2-锁的粒度与临界区]]）：

- 悲观锁下缩短持锁时间 → 排队变短
- 乐观锁下缩短单次尝试时间 → 每次白干也更便宜、窗口也更小

**【所以"缩临界区"是比"换锁"更优先的动作】**——它两边都改善。

#### 2.3 第三种做法：条件更新（既不加锁也不重试）【推导】

【推导】**"防超卖"这道题最能说明问题**——它有三种做法，**最实用的那种既不是乐观锁也不是悲观锁**：

| 做法 | 写法 | 超卖 | 吞吐 | 死锁风险 |
|---|---|---|---|---|
| **① 先查再改**（错） | `SELECT n` → 应用判断 → `UPDATE n = 算出来的值` | **会超卖** ❌ | 高 | 无 |
| **② 悲观锁** | `SELECT ... FOR UPDATE` → 判断 → `UPDATE` | 不会 | **低**（串行） | 有（多行时） |
| **③ 条件更新**（推荐） | `UPDATE t SET n = n - 1 WHERE id = 1 AND n >= 1` | 不会 | **高** | 无 |
| **④ 乐观锁（版本号）** | 读 version → `UPDATE ... WHERE version = N` | 不会 | 中（冲突时要重试） | 无 |

【推导】**为什么 ① 会超卖**：**"读"和"写"是两条语句，中间别人也能读**——两个请求都读到 `n = 1`，都判断"够"，都执行 `n = 1 - 1 = 0`，结果**卖了两件但库存只减了一**。**这不是"锁选错了"，是"根本没有原子性"。**

【推导】**为什么 ③ 更好**：**把"判断"和"写入"合进一条语句，数据库保证这条语句原子执行**：

```
UPDATE t SET n = n - 1 WHERE id = 1 AND n >= 1;
  → 影响行数 = 1：扣减成功
  → 影响行数 = 0：库存不够（或 id 不存在）→ 直接返回"卖完了"
```

**它不需要"先读"、不需要重试、不需要显式拿锁**——**因为竞争被数据库在这一条语句里解决掉了**。（**注意 `n = n - 1` 是"基于当前值"的写法，不是"基于我读到的值"**——这就是它和 ① 的本质差别。）

【事实】**EnergyOps 里用的是同一类做法**：任务抢占不靠锁，而是一条带条件的 `UPDATE`——`WHERE 状态 = 待处理 AND 租约版本 = 我看到的那个`，**改到 0 行就说明被别人抢先，主动退让**（`02-aggregation-and-recovery.md`）。

【取舍】**所以完整的决策顺序是三问**：

```
① 能不能用「条件更新」把判断和写入合成一条原子语句？  → 能，就别用锁
② 不能（需要跨多条语句 / 跨多行的不变量），冲突率高不高？  → 低用乐观、高用悲观
③ 真的要悲观锁，能不能把临界区再缩小？  → 能就缩（L2）
```

**到这里你应该能回答**：为什么"防超卖"的标准答案不是"用乐观锁"也不是"用悲观锁"？

### 3. 乐观锁的重试：不处理就会变成风暴

#### 3.1 重试要退避【推导】

【推导】**上游在重试时，冲突率会自己变大**——因为重试的请求又回到了同一个竞争池里，形成正反馈：

```
假设 50 个并发请求抢同一行，冲突率 50%
  第一次：50 个请求，25 个成功、25 个失败
  这 25 个立刻重试 → 25 个请求抢 1 行 → 冲突率更高
  → 失败者再重试 → ……
  结果：成功次数没变多，但【打到数据库的请求数翻了几倍】
```

【推导】**三条对策**：

| 对策 | 做什么 | 代价 |
|---|---|---|
| **指数退避 + 抖动** | 失败后等 `随机(0, base × 2^次数)` 再试 | 单次延迟变大 |
| **限制重试次数** | 试 2–3 次就放弃，返回"稍后重试"给用户 | 用户体验（要能接受） |
| **退化成排队** | 冲突率持续高就切悲观锁 / 用队列串行 | 复杂度 |

【取舍】**"重试几次"是个必须显式定的参数，不能默认无限重试**——**无限重试 = 把冲突率放大成请求量**。

#### 3.2 冲突失败必须能和"业务失败"区分【推导】

【推导】**`UPDATE` 影响 0 行有两种含义**，混在一起会误导：

```
影响 0 行 = ① 版本不匹配（并发冲突 → 应该重试）
          ② 条件不满足（业务规则不通过 → 重试一万次也没用）
```

**处理方式**：要么把两种条件分开（先做业务校验，再用版本号做并发控制），要么在"0 行"之后再查一次当前状态来区分。**否则会出现"对一个永远不会成功的操作反复重试"**。

**到这里你应该能回答**：为什么"乐观锁失败就重试"这句话是不完整的？

### 4. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "乐观锁就是不加锁" | 【事实】**错**。数据库里乐观锁**同样要拿行锁**，只不过只有那一条 `UPDATE` 持锁；真正的区别是**持锁时间从"整个业务处理"压缩到"一条语句"**，代价变成"可能白干" |
| "乐观锁一定比悲观锁快" | 【推导】**看冲突率**。p 超过一半时，乐观锁"白干的工作量"就超过了它省下的排队时间（期望尝试 2 次以上）。**判据是 `1/(1−p)`，不是感觉** |
| "悲观锁慢，高并发要避免" | 【取舍】**悲观锁把不确定性换成了排队**——如果临界区很短、冲突率很高，它反而更稳。**"慢"是因为临界区太长，不是因为锁本身** |
| "库存扣减先查再改就行" | 【推导】**会超卖**。读和写是两条语句，中间没有原子性。**正确写法是条件更新：`UPDATE ... SET n = n-1 WHERE n >= 1`** |
| "乐观锁失败就重试" | 【推导】不完整。**必须**：① **区分**"版本冲突"与"业务条件不满足"；② **限制次数**；③ **指数退避 + 抖动**，否则重试自己会把冲突率推高 |
| "有版本号就万无一失" | 【事实】版本号只保护**你读的那一行**。跨行 / 跨表的不变量（比如"订单总额 = 明细之和"）它管不了——那需要事务 + 约束 |
| "冲突高就把重试次数调大" | 【推导】**反了**。冲突高说明"白干比例高"，正确动作是**换方案**（条件更新 / 悲观锁 / 队列串行），不是加大重试 |
| "乐观锁没有死锁问题" | 【事实】单条 `UPDATE` 确实不易死锁，**但如果一次事务里更新多行、加锁顺序不一致，照样会死锁**（[[母题-M10-锁与死锁]]） |

## 二、自测

**Q1（计算）**：某接口对同一行做"读出 → 计算 → 写回"，单次尝试耗时 **5 ms**，实测**冲突率 60%**。

问：① 期望尝试几次？② 多做了多少百分比的工作？③ 如果换成悲观锁（持锁 4 ms、串行），哪个更快？④ 你会怎么改？

**A1**：

```
① 期望尝试次数 = 1 / (1 − 0.6) = 1 / 0.4 = 【2.5 次】

② 多做的功 = (2.5 − 1) / 1 = 【150%】——三分之二的算力在重复劳动

③ 同一行的吞吐对比：
   乐观：每秒成功次数 ≈ 1 / (5ms × 2.5) = 80 次/秒（并行下能更高，但浪费 150% 的算力）
   悲观：串行，每秒 ≈ 1 / 4ms = 250 次/秒
   → 【悲观在这组参数下明显更好】：它不浪费工作，而且持锁时间比乐观的"单次尝试"还短
```

④ **改法优先级**：

| 顺序 | 动作 | 为什么 |
|---|---|---|
| **1** | **先找能不能转成条件更新** | 如果这段业务本质是"读一个值 → 判断 → 改一个值"，那就该写成一条 `UPDATE ... WHERE 条件`，**既不排队也不重试** |
| **2** | **缩临界区**（[[母题-L2-锁的粒度与临界区]]） | 把"5ms 里不属于临界区的部分"（外部调用、日志、序列化）挪出事务，两边的账都会变好 |
| **3** | **换悲观锁** | 冲突率 60% 已经很高，排队比白干划算 |
| **4** | **退化成串行队列** | 同一份数据的竞争本质上就是串行的——把并发收成一个队列，比让 N 个线程互相踩更干净 |

【这一步在验证什么】验证 2.1 的判据：**冲突率过半时乐观锁"白干比干活多"**（150% vs 100%）。

**Q2（判读）**：下面这段扣库存的代码有什么问题？高并发下会看到什么现象？

```sql
-- 事务里
SELECT stock FROM product WHERE id = 1;     -- 假设读到 1
-- 应用层判断：if stock >= 1 { ... }
UPDATE product SET stock = 0 WHERE id = 1;  -- 用的还是"我读到的那个值"算出来的结果
```

**A2**：**问题不在锁，在没有原子性——"读"与"写"是两条语句，中间任何事务都能插进来。**

```
T1 读到 stock = 1
T2 读到 stock = 1          ← 两条 SELECT 之间没有任何互斥
T1 判断"够"，写 stock = 0   ← 卖出 1 件
T2 判断"够"，写 stock = 0   ← 又卖 1 件（但库存已经是 0 了）
→ 【超卖 1 件】
```

**高并发下的现象**：`stock` 最终停在 0 或某个非负值，**但订单数比库存多**——而且**这种 bug 在低并发压测时复现不了**（没有重叠窗口）。

**正确写法（条件更新）**：

```sql
UPDATE product SET stock = n - 1
 WHERE id = 1 AND stock >= 1;
-- 影响 1 行 → 扣减成功；影响 0 行 → 卖完了，直接返回
```

【这一步在验证什么】验证 2.3：**"先查再改"的错误不是锁选错了，而是把"判断 + 写入"拆成了两步。**

**这里还有一个关键点值得说**：`SET stock = n - 1` 和 `SET stock = 0`（我算出来的值）**语义不同**——前者是"基于当前值减一"（数据库读取时锁定当前值），后者是"写入一个可能已经过期的快照"。**很多"看起来加了判断却还是超卖"的代码，问题就出在这一字之差上。**

**Q3（计算）**：某服务峰值 **2000 QPS** 都在抢同一行，冲突率 **50%**，代码里**失败就无限重试**（每次重试不打散）。

问：① 实际打到数据库的请求量会变成多少？② 这会引发什么连锁反应？③ 最小改动该怎么改？

**A3**：

```
① 每次"成功"需要 1/(1−0.5) = 2 次尝试
   期望总请求量 = 2000 × 2 = 【4000 次/秒】
   ⚠️ 注意这是【下限】：因为重试的请求又加入了竞争池，
      冲突率会被推高（50% → 更高），实际会超过 2 倍
```

② **连锁反应**：

| 反应 | 机制 |
|---|---|
| **连接池被打满** | 请求数翻倍 → 连接占用翻倍 → 排队 → 超时 |
| **数据库 CPU 上升但有效吞吐不升** | 大部分 `UPDATE` 是白干的 |
| **P99 抬升** | 重试的请求要走"多次往返"，尾延迟被拉长 |
| **雪崩** | 上游超时重试 + 本层重试叠加 → 请求量再翻倍 |

③ **最小改动（按性价比排序）**：

```
1. 改成条件更新（如果业务允许）→ 直接消除重试
2. 给重试加「指数退避 + 抖动」+ 上限 2–3 次
   失败就返回"排队中/请稍后"，让上游控制节奏
3. 同一份数据的竞争本质是串行的 → 引入队列把它显式串起来
   （这就是 RuleArena 用队列 + 幂等替代"抢锁"的思路）
```

【这一步在验证什么】验证 3.1：**无限重试会把"冲突率"放大成"请求量"**——这是乐观锁在生产里最常见的翻车方式。

**Q4（纠错）**：下面这段话哪里错了？

> "乐观锁就是不加锁，所以它一定比悲观锁快，高并发场景应该都用乐观锁。"

**A4**：**三处都错。**

1. **"乐观锁就是不加锁"错了**。在数据库里，乐观锁那条 `UPDATE ... WHERE version = N` **本身也要拿行锁**——它和悲观锁的真正区别是**持锁时间**：悲观锁把锁从"读"一直持有到"写"，乐观锁只持有写那一条语句。**所以准确说法是"把持锁时间从整个业务处理压缩到一条语句"**，而不是"不锁"。

2. **"一定比悲观锁快"错了**。两者是把代价花在不同地方：悲观的代价是**强制串行 + 排队**，乐观的代价是**冲突时白干**。**用同一个算式比就行**：

```
期望尝试次数 = 1 / (1 − p)
p = 10% → 1.11 次（乐观划算）
p = 50% → 2.00 次（白干 100%）
p = 90% → 10.0 次（完全不可接受）
```

**冲突率过半之后，"白干的工作量"就超过了它省下的排队时间**——这时悲观锁反而更稳。

3. **"高并发场景都用乐观锁"错了**。决定因素是**冲突率**而不是**并发量**：

```
10000 QPS 打 10000 个【不同的】行 → 冲突率≈0 → 乐观锁极好
100 QPS 打【同一个】热门行        → 冲突率极高 → 乐观锁会很惨
```

**真正的高并发场景（比如秒杀）通常既不用乐观也不用悲观，而是：条件更新 + 异步下单 + 把竞争收进队列**（[[母题-M17-排行榜与防超卖]]）。

**准确说法**：*乐观锁不是不加锁，而是只拿一条语句的锁，代价变成"冲突时白干"。选哪个看冲突率：`1/(1−p)` 接近 1 就用乐观，逼近 2 以上就该换条件更新、缩临界区或改用排队。*

**Q5（纠错）**：下面这段话哪里错了？

> "用版本号做乐观锁就万无一失了，反正版本不对就会更新失败，不会出现数据不一致。"

**A5**：**"万无一失"错了，漏了三件事，而且它保护的范围比你想的小。**

1. **它只保护"你读的那一行"**。版本号是**行级**的：

```
✅ 能保护：同一行的并发修改（"这条记录的 name 被两个人同时改"）
❌ 保护不了：【跨行 / 跨表的不变量】——
   比如"账户余额 = 所有流水之和"、"订单总额 = 明细之和"
   两个人的修改可能落在不同行上，各自版本都对，但合起来违反了不变量
→ 这类不变量要靠【事务 + 约束】或【把聚合写进一条语句】来保证
```

2. **"更新失败"之后如果不处理，等于什么都没保护**。`影响 0 行`有两种含义——**版本冲突**（该重试）和**业务条件不满足**（重试无用）。不区分就会出现"对一个永远不可能成功的操作反复重试"（3.2）。

3. **无限重试会把冲突放大成请求风暴**（Q3）。**版本号保护的是数据，不是系统**——风暴照样能把数据库打垮。

4. **还有一个隐藏前提**：**"重试必须是安全的"**。如果那次失败的操作里有**不可回滚的副作用**（已经发了短信、已经调了外部接口），**重试会造成重复副作用**——这时要先靠幂等键把它变成安全的（[[母题-Q2-重复与乱序]]），再谈重试。

**准确说法**：*版本号是行级的并发保护，只保证"这一行不会被两个人按同一个旧值覆盖"；跨行不变量要靠事务与约束，重试要限次 + 退避，有副作用的操作要先幂等再重试。*

## 三、面试输出（学完再看）

**一句话结论**：乐观锁和悲观锁不是"快慢"之别，而是**把代价花在不同地方**——**悲观锁在动手前排队**（并发被压成串行，但不浪费工作），**乐观锁在提交时校验**（并发不受限，但冲突时白干）。**判据可以算**：期望尝试次数 = **1/(1−冲突率 p)**，p = 10% 只要 1.11 次、p = 50% 就要 2 次（等于白干一遍）、p = 90% 要 10 次——**所以冲突率低用乐观、高则换方案**。还要纠正一个关键认知：**乐观锁在数据库里同样要拿行锁**，只是只拿一条语句（`UPDATE ... WHERE version = N`），**真正的差别是持锁时间**。而**最好的答案往往既不是乐观也不是悲观，而是"条件更新"**：`UPDATE ... SET n = n−1 WHERE n ≥ 1`——**把判断和写入合成一条原子语句，不排队也不重试**（EnergyOps 的任务抢占用的就是这类带条件的 UPDATE）。

**恢复关键词**：悲观=先排队不白干 / 乐观=先干再校验会白干 / **乐观锁也拿锁，只是只拿一条语句** / **持锁时间 vs 白干** / **期望尝试 = 1/(1−p)** / 10%→1.11、30%→1.43、50%→2、90%→10 / **先查再改会超卖（读改写不原子）** / **条件更新 `SET n = n−1 WHERE n ≥ 1`** / 影响 0 行要区分"冲突"与"条件不满足" / 重试要限次 + 退避 + 抖动 / 无限重试会把冲突率放大成请求量 / 版本号只保护一行、管不了跨行不变量 / 缩临界区优先于换锁

**核心不变量 / 主线**：
**并发控制的一切手段都是在给"出错"定价，而不是消灭它。** 悲观锁把"出错"定价成"排队时间"，乐观锁定价成"白干的工作量"，条件更新则把定价降到最低（因为它让数据库在一条语句里解决竞争）。**而定价的依据永远是一个可算的量——冲突率。**

**完整回答骨架**：先讲"两者把代价花在不同地方" → **纠正"乐观锁不加锁"**（持锁时间之差）→ 给判据算式 `1/(1−p)` 与数值表 → 说明两边其实可以被同一动作改善（缩临界区）→ **给第三条路：条件更新**（防超卖标准答案）→ 重试的三条对策与"0 行的两种含义" → 边界与误解

**完整回答（口述稿）**：
乐观锁和悲观锁不是"快慢"之别，而是**把代价花在不同地方**：**悲观锁在动手前排队**（并发被压成串行，但不浪费工作），**乐观锁在提交时校验**（并发不受限，但冲突时白干）。

判据可以算：**期望尝试次数 = 1/(1−冲突率 p)**——p = 10% 只要 1.11 次；p = 50% 就要 2 次（等于白干一遍）；p = 90% 要 10 次。所以**冲突率低用乐观**，冲突率过半或重试代价很高或临界区本身很短时换悲观。**顺序上：先想能不能改成条件更新，再想缩临界区，最后才换锁**。

数据库里两种实现：**版本号**（`UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = N`，看影响行数）和**条件更新**（`UPDATE ... SET n = n − 1 WHERE id = ? AND n ≥ 1`）。**最好的答案往往既不是乐观也不是悲观，而是条件更新**——把判断和写入合成一条原子语句，**不排队也不重试**。

一个关键纠正：**乐观锁在数据库里同样要拿行锁**，只是只拿一条语句的时间——**真正的差别是持锁时间**。失败处理：**限次（2–3 次）+ 指数退避 + 抖动**，先区分"版本冲突"与"业务条件不满足"（后者重试一万次也没用）。

**分层要点**：
- **结论**：代价位置不同；判据 `1/(1−p)`；最好答案是条件更新而不是乐观/悲观二选一。
- **推导链**：排队 vs 校验 → 期望尝试次数 → 换锁的三个条件 → 实现（版本号/条件更新）→ 失败重试的纪律。
- **量化**：p=10% → 1.11 次、p=50% → 2 次、p=90% → 10 次；高冲突下乐观 N² vs 悲观 N。
- **边界与常见误解**："乐观锁不加锁"×（差别在持锁时间）；"先查再改 + 事务"防不住并发窗口；单条 UPDATE 不易死锁，但事务里多行且加锁顺序不同照样会。

**追问**（先说后看）

1. **什么情况该换悲观锁？** —— **冲突率过半之后**（`1/(1−p)` ≥ 2，白干的工作量已经超过一次），或者**重试代价很高**（重试要做昂贵计算 / 有外部调用），或者**临界区本身很短**（排队不痛）。**注意顺序：先想能不能改成条件更新，再想缩临界区，最后才换锁。**
2. **乐观锁失败怎么重试？** —— **限次（2–3 次）+ 指数退避 + 抖动**，并在失败后返回"稍后重试"而不是无限重试。**还要先区分"版本冲突"与"业务条件不满足"**——后者重试一万次也没用。
3. **防超卖该怎么做？** —— **条件更新**：`UPDATE ... SET stock = stock − 1 WHERE id = ? AND stock ≥ 1`，看影响行数。**别用"先查再改"，也别一上来就 `FOR UPDATE`**。真要极致吞吐再上"Redis 预扣 + 异步落库 + 幂等"（[[母题-M17-排行榜与防超卖]]）。
4. **乐观锁真的不会有死锁吗？** —— **单条 `UPDATE` 不容易死锁，但一次事务里更新多行、加锁顺序不同样会死锁**（[[母题-M10-锁与死锁]]）。**"乐观"指的是并发控制策略，不是"没有锁"。**
5. **冲突率怎么测？** —— 三个来源：① **更新影响 0 行的比例**（最直接，版本冲突会体现在这里）；② 版本号 / 业务键的**热点分布**（同一个 key 被多少请求打）；③ 压测时对比"实际尝试次数 / 成功次数"。**有了这个数才能谈选型，否则都是感觉。**

**同类变体**

- 「CAS 和乐观锁是一回事吗？」——**思想同源、层次不同**：CAS 是 CPU/语言层的**一条原子指令**（比较并交换），乐观锁是**应用层的策略**（读版本 → 带版本写）。ABA 问题见 [[母题-L2-锁的粒度与临界区]]
- 「MVCC 算乐观还是悲观？」——**都不算**。MVCC 是**读写不互斥**的机制：读走快照、写走新版本，**冲突只有在"写写"时才需要处理**（[[母题-M9-MVCC]]、[[母题-P13-MVCC与可见性]]）
- 「PG 的序列化失败为什么建议重试？」——那是 **SSI（可串行化快照隔离）** 把冲突检测推迟到提交时，失败即 `40001`，**它的补偿手段就是"重试"，和乐观锁是同一套逻辑**（[[母题-P9-序列化失败与重试]]、[[母题-P18-乐观并发控制]]）
- 「任务抢占怎么保证只有一个 Worker 干？」——**不用锁**：一条带条件的 `UPDATE`（`WHERE 状态 = 待处理 AND 租约版本 = 我看到的`），**改到 0 行就退让**——这就是 EnergyOps 的做法
