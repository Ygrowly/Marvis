# 并发与锁模块深挖卡

> 本卡是 [[模块深挖卡模板]] 的实战卡。**主线优先**：先看三条线，再落母题，题单只用来查漏。
> **定位**：这是后端基本盘里**唯一一个"横切"模块**——它不占某一个中间件，而是**穿过所有中间件**：数据库有锁、缓存有锁、MQ 有幂等、服务本身有并发。
> **与相邻模块的分工（三处，别串台）**：
> - [[母题-O1-上下文切换与死锁]] 讲**内核层**：自旋锁 / 互斥量、切换成本、死锁四条件
> - [[母题-M10-锁与死锁]] / [[母题-P10-无间隙锁与锁变体]] 讲**数据库层**：行锁、间隙锁、死锁检测与回滚
> - **本卡讲应用层与跨机层**：该不该加锁、锁画多大、多台机器怎么抢同一份资源
>
> **三处互链、不重复**：内核层给"锁的物理代价"，数据库层给"锁在存储引擎里的形态"，本卡给"你的代码该怎么决定"。
> **本轮落 3 张母题**（对应三条主线），题单里其余题目排期。

## 0. 模块边界（先写这个，防无限扩张）

**包含**：**该不该加锁**（乐观与悲观的选择判据、冲突率与重试代价）、**锁画多大**（粒度、临界区、自旋与互斥的取舍、读写锁、分段锁、CAS 与 ABA）、**跨机器怎么互斥**（分布式锁的三种实现、各自的失效场景、fencing token、租约与续期）。

**明确不包含**：

- **内核层的锁实现**（futex、自旋锁的 CPU 指令、调度器行为）——归 [[母题-O1-上下文切换与死锁]]
- **数据库的锁机制**（行锁 / 间隙锁 / MVCC / 死锁检测）——归 [[母题-M10-锁与死锁]]、[[母题-P10-无间隙锁与锁变体]]、[[母题-M9-MVCC]]
- **编程语言的内存模型**（Java 的 `volatile` / happens-before / `synchronized` 的完整语义、Go 的内存模型）——**除非明确投 Java 岗**，本卡只到"可见性与原子性是两件事"
- **某个框架的锁源码**（Redisson 的看门狗实现、ZooKeeper 的 Curator 配方）——只到"它解决什么问题、代价是什么"
- **具体的流量治理**（限流、熔断、降级）——归 [[母题-E4-成本控制与限流]] 与消息队列的降级节

**边界判据**：**本卡只回答"这段代码要不要加锁、锁要画多大、多台机器上怎么抢"。** 凡是"某个锁的内核实现怎么写的"（归 O1）、"MySQL 的间隙锁长什么样"（归 M10）的，不进本卡。

**一条必须先立住的认知**：**"加锁"是并发控制里最贵、也最容易做错的一种手段。** 判断顺序应该是——

```
① 能不能不用锁？（幂等 / 队列化 / 无共享 / CAS）
② 非加不可，能不能让"冲突"变少？（缩小临界区、分段）
③ 真的是跨机器的竞争吗？（是 → 分布式锁；不是 → 别用分布式锁）
```

**倒过来做（先加锁、再想为什么）是这一块最常见的错。**

## 2. 主线拆解（骨架：这个域在回答哪几个问题）

| # | 主线（它在回答什么问题） | 这条线的关键取舍 | 落几个母题 |
|---|---|---|---|
| 一 | **要不要加锁**：冲突率多高才值得用悲观锁；乐观锁重试失败怎么办；这两种在数据库和代码里分别长什么样 | 悲观锁（排队，不会白干）vs 乐观锁（不排队，可能白干重试）；重试次数与"重试风暴" | 1 |
| 二 | **锁画多大**：粒度、临界区、自旋还是睡眠、读写锁什么时候退化、无锁 CAS 与 ABA | 锁越细并发越高 vs 锁越细越容易写错、开销占比越高；CAS 无锁 vs 可读性与 ABA | 1 |
| 三 | **多台机器怎么抢同一份资源**：分布式锁三种实现，各自的失效场景，为什么"锁"本身还要配 fencing token | 正确性（会不会两个持有者）vs 可用性（锁服务挂了能不能继续）；性能 vs 安全 | 1 |

**三条线的关系**：一是"要不要付这个代价"，二是"付了之后怎么付得少"，三是"把范围从一台机器扩到多台"。**顺序就是决策顺序**——先判断要不要，再决定多大，最后才考虑跨机。

**这三条线共享同一个前提**：**并发控制的目标不是"不出错"，而是"出错的方式可以接受"。** 乐观锁接受"重试"，CAS 接受"失败重来"，分布式锁接受"锁可能失效所以要再校验一次"——**每种方案都是在给"出错"定价，而不是消灭它**。

## 5. 项目映射（三个项目逐个过）

> 素材来源：`projects/` 下的项目说明与编号手册。**这里每一句都要能指回原文**，不许编。

### 5.1 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**"用条件更新代替加锁"的活教材**——任务表用**窗口业务键 + 唯一约束 + 条件抢占 + 租约版本**来避免多个 Worker 抢同一个窗口（`02-aggregation-and-recovery.md`）。**这不是悲观锁，是"带期望版本的条件更新"**——正是 L1 说的乐观并发控制，只不过不用版本号字段，而用"租约版本"。
- 解决什么问题：**多个 Worker 同时扫到同一个缺口窗口时，只能有一个真的干活**。做法是把"抢"变成一条带条件的 UPDATE：`WHERE 状态 = 待处理 AND 租约版本 = 我看到的那个`——**改到 0 行就说明别人先拿到了，我退让**。**一个原子 UPDATE 就完成了加锁、判断和推进三件事**。
- 踩过的坑：**租约版本只挡住了本地数据库的旧写，撤不回旧 Worker 已经发出的外部调用**（`07-task-lifecycle-and-delivery.md`）——这正是 L3 的核心结论：**任何"锁"都保护不了已经离开进程的副作用**，那要靠幂等键与权威状态查询。
- 决策与取舍：**并发度是"受控"出来的**——受控并发 + 并发配额，而不是让所有任务自由抢。**"先限制并发，再考虑锁"这个顺序**就是本卡第 0 节的判据。

- 对应母题：【L1、L3】

### 5.2 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**并发配额代替锁**——按租户限制并发和队列、给查询设超时、扫描量、行数与取消能力（`07-权限安全与生产隔离.md`、`08-查询性能与成本控制.md`）。**这里根本没有"锁"，而是"限流 + 排队"**。
- 解决什么问题：**保护源库**。多个租户的查询同时打到只读副本上，靠**配额**把它们隔开，而不是靠锁——因为**这些请求之间没有共享状态要保护，只是争资源**。
- 踩过的坑：**"无依赖子查询可以并发，但写回顺序必须确定"**——同一个问题在 L2 里的形态是"**并发度可以放开，但要保序的地方必须显式串起来**"。
- 决策与取舍：**"争资源"和"争状态"要分开处理**——争资源用配额（限流），争状态才用锁或条件更新。**把这两件事混在一起是设计里常见的错**。

- 对应母题：【L2、L3】

### 5.3 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**"不用锁，用幂等"的主证据**——`04-idempotency-and-recovery.md` §9 明确：接受队列至少一次投递与 Worker 随时崩溃，靠**稳定幂等键 + 同一事务里的唯一约束**保证业务副作用只生效一次；`08-capacity-cost-and-facts.md` 给 Redis 只配 256~512MB，**队列与限流用 Redis，但权威状态在 PostgreSQL**。
- 解决什么问题：**多 Worker 并行跑规则审查时，同一个动作不会被两个 Worker 各执行一次**。做法不是"抢锁"，而是**"谁先写进唯一约束谁生效，另一个读到冲突就当自己已经做过"**。**这比分布式锁简单、也更强壮**——因为不依赖锁服务可用。
- 踩过的坑：**超时后不许换 key 重试**（不然幂等键失效）；**不能拿 ToolCallID 当幂等键**（它每次调用都变）。
- 决策与取舍：**"能幂等就不用锁"**。锁要引入一个额外的可用性依赖（锁服务），幂等只依赖自己的数据库——**这是 L3 最后一条追问的答案：能用幂等解决的，不要用锁。**

- 对应母题：【L1、L3】

## 8. 题级答案（「本主线的题」翻转卡背面 · 先说后翻）

> 题号与第 4 节题单一一对应。**必背**题写成能直接说出口的一段话；**理解 / 了解**题写 1–3 句。
> 翻转卡背面先给这道题的答案，再挂上「所属母题的完整回答（口述稿）」与单卡入口——两段合起来才是深挖。

### 1 （必背）
不是"快慢"之别，是**把代价花在不同地方**：**悲观锁在动手前排队**（并发被压成串行，但不浪费工作），**乐观锁在提交时校验**（并发不受限，但冲突时白干）。

一个关键纠正：**乐观锁在数据库里同样要拿行锁**——`UPDATE ... WHERE version = N` 这条语句本身有锁，真正的差别是**持锁时间**。

### 2 （必背）
判据可以算：**期望尝试次数 = 1/(1−冲突率 p)**——p = 10% 只要 1.11 次；p = 50% 就要 2 次（等于白干一遍）；p = 90% 要 10 次。

所以：**冲突率低 → 乐观**；**冲突率过半**（`1/(1−p) ≥ 2`）、**重试代价很高**（重试要做昂贵计算或外部调用）、或**临界区本身很短**（排队不痛）→ 换悲观。

顺序上：**先想能不能改成条件更新，再想缩临界区，最后才换锁。**

### 3 （必背）
两种：**版本号**（`UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = N`，看影响行数）和**条件更新**（`UPDATE ... SET n = n − 1 WHERE id = ? AND n ≥ 1`）。

**最好的答案往往既不是乐观也不是悲观，而是条件更新**——把判断和写入合成一条原子语句，**不排队也不重试**（EnergyOps 的任务抢占就是这类）。

注意：单条 UPDATE 不容易死锁，但**一个事务里更新多行、加锁顺序不同样会死锁**——"乐观"指的是并发控制策略，不是"没有锁"。

### 4 （必背）
**限次（2–3 次）+ 指数退避 + 抖动**，失败后返回"稍后重试"而不是无限重试（否则会变成重试风暴，把冲突再放大）。

前提动作：先区分"**版本冲突**"（可以重试）与"**业务条件不满足**"（重试一万次也没用）。影响行数 0 时不要直接当成失败，要**读权威状态再判定**。

### 5 （必背）
**① 条件更新（首选）**：`UPDATE ... SET stock = stock − 1 WHERE id = ? AND stock ≥ 1`，看影响行数——一条语句原子，不排队也不重试；**② 悲观锁**：`SELECT ... FOR UPDATE` 后更新，实现简单但**吞吐最低**（并发压成串行）；**③ Redis 预扣 + 异步落库 + 幂等**：极致吞吐，但引入"缓存与 DB 的不一致窗口"和补账逻辑。

**别用"先查再改"**——并发下必然有窗口，加事务也补不上（除非可串行化隔离级别）。

### 6 （理解）
期望尝试次数 `1/(1−p)` 会发散：p = 50% 白干一遍，p = 90% 要 10 次。高冲突下 N 个请求抢同一行，**乐观锁总工作量约 N²**（每次失败都重做），**悲观锁约 N**（排队一次做完），差一个 N 倍。

所以冲突率高时要换方案——**优先改成条件更新或缩临界区，最后才换悲观锁**。

### 7 （必背）
CAS（Compare-And-Swap）把乐观并发下沉到**指令层**：比较值等于期望值就写入，否则失败。

**ABA**：值从 A 改到 B 又改回 A，CAS 看不出中间变过——**数值场景通常无害，引用 / 状态 / 指针场景有害**（栈顶指针弹出又压回同一地址）。**解法：把版本号一起 CAS**（`[值, 版本]` 同时比较），或用带标记的指针。

另外两个边界：**高竞争时退化成自旋烧 CPU**（这时加锁更好）、**一次只能保护一个变量**。最优先的动作永远是**减少竞争本身**。

### 8 （必背）
粒度不是在"性能 vs 开销"之间选，而是在**冲突率 vs 记账开销**之间选。粒度太细：锁对象变多、记账（获取 / 释放、内存、死锁检测）变贵，**可能比省下的等待还贵**。

正确的判据是**分段锁的效果**：冲突率降到约 1/N（p = 40% 分 16 段后，期望尝试次数从 1.67 降到 1.03），但**前提是访问均匀分散**——**热键始终落在同一段，分段救不了它**，得换方案（本地聚合 / 队列串行 / 每节点累加）。而且**段数不能大到记账反超收益**。

### 9 （理解）
由一个比值决定：**等待时间 vs "挂起 + 唤醒"的成本（约 2 μs）**。临界区不到 1 μs 就自旋（省掉挂起唤醒）；毫秒级必须睡（否则空转烧 CPU）。工程上常用"**先自旋一小会儿再睡**"的混合策略。

### 10 （理解）
不一定。**临界区极短时**，读写锁的**记账**（读计数、写者状态、升级判断）可能比省下的等待还贵，反而更慢；另外还有**写者饥饿**。

"读多写少"的第一选择通常是**让读不参与竞争**——MVCC / 快照 / 读副本（MySQL 的 MVCC、PG 的快照都是这个思路）。

### 11 （理解）
把一个大锁拆成 N 个小锁，按 key 哈希落到其中一段：**冲突率降到约 1/N**，段间可并行。典型应用是 ConcurrentHashMap 的分段。

代价与前提：**段数不能大到记账反超收益**；而且**有热键时分段没用**（热键恒定落在同一段），要先解决热点——本地聚合 / 队列串行 / 每节点累加。

### 12 （理解）
**不是**。**竞争激烈时**，CAS 的失败者会**空转而不是让出 CPU**——CPU 白烧、吞吐反降，这时加锁反而更好（失败者睡下去）。

而且无锁有边界：一次只能保护一个变量、有 ABA、高竞争退化。**更优先的动作永远是减少竞争**（分片、每线程累加、显式限制并发）。

### 13 （必背）
单机锁（mutex）的共享状态只在进程内可见；跨机器互斥要把**锁状态放到一个共享的地方**（Redis / 数据库 / ZooKeeper / etcd）。

但先问一句：**我要的是"不同时跑"还是"不重复执行"？** 后者用**幂等**就够了——更便宜、不引入新依赖，RuleArena 连锁都没用。只有"重复执行的代价极高、必须串行"时才上锁。

### 14 （必背）
**① 加锁要一条原子命令**：`SET key value NX PX ttl`（不能用 SETNX + EXPIRE 两条，中间崩溃会留下永不过期的锁）；**② 释放要校验值**（GET 比对 + DEL，用 Lua 保证原子）——否则你过期后别人拿到了锁，你这时 DEL 删的是别人的；**③ TTL 必须设**，但不能指望设成"足够长"就安全。

另外一条硬伤：**主从异步复制会丢锁**——主库加了锁还没同步就宕机，切主后另一个客户端又能加上。

### 15 （必背）
**看门狗续期**：拿到锁后起后台线程，在 TTL 到期前不断续期（Redisson 的 watchLock），业务跑完再主动释放。

但**续期只是缓解，不是根治**——续期本身也可能因 GC 停顿 / 网络分区而中断。真正保证安全要靠 **fencing token**；另外把长业务改成**分批 + 每批重新抢锁**，把损失限制在一批内。

### 16 （必背）
因为**锁服务判断的是"时间"，而客户端的事实是"是不是还在跑"**，这两者会脱节：**GC 停顿**（线程停了但锁没停）、**时钟漂移**（本地时间不准）、**网络分区**（还活着但联系不上锁服务）。

所以 **TTL 没有安全值**：短了出现双持有者，长了可用性差，而"最长停顿"没有上界。结论：**安全性不能只靠锁服务对时间的判断，要搬到资源侧（fencing token）**。

### 17 （必背）
发锁时给一个**单调递增的号**（ZooKeeper / etcd 的 revision，或自增计数），客户端带着这个号去写资源，**资源侧只接受比已见过的最大号更大的写**。

解决的是"**旧持有者（其实已经过期）的写仍然被接受**"——即使锁服务判错了，资源侧也能拒掉。代价：**资源侧必须配合改造**（很多存储做不到），所以它是正确性的最后一道，不是默认配置。

### 18 （理解）
**Redis**：`SET NX PX` 一条原子命令 + 释放校验值；快、可复用已有组件；**弱点是主从异步复制会丢锁**。**数据库**：唯一约束 / 带条件更新；不引入新组件，但**把锁争用压在数据库上**（连接与行锁）。**ZooKeeper / etcd**：临时顺序节点 / 租约 + 单调 revision；**语义最干净**（天然带 fencing 号），**但要维护一套强一致系统**。

共性弱点：三者都依赖"锁服务对时间的判断"，所以严格正确性都要 fencing token。

### 19 （了解）
Redlock 想用"向多个独立实例加锁、多数成功即拿到"来缓解单实例丢锁。反对意见指出它**依赖对时钟漂移上限和最大停顿的假设**，而这些假设在 GC 停顿 / 网络分区下不成立。

**两方都同意的是：要严格正确性就得用 fencing token。** 面试讲到这里即可，不必站队。

### 20 （必背）
**幂等常常比锁更划算**：锁解决"不同时跑"（互斥），幂等解决"不重复执行"（效果只发生一次）。真实需求如果是后者，幂等就够了——不引入新组件、不牺牲可用性、不依赖时间假设。

判据：**先问"要的是互斥还是不重复"**；只有"重复执行的代价极高且必须串行"时才上锁，而且要明白**锁并不能提供绝对互斥**（严格正确需要 fencing token）。
