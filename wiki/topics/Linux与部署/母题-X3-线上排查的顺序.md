## 一、教材

### 1. 前提：排查的能力体现在"顺序"，不在"记得多少命令"

#### 1.1 为什么顺序比工具重要【推导】

::figure triage-order.svg | 线上变慢的排查顺序：先分类，再看数 | 两个二分问题把原因分成四块；三个最容易误判的信号

【推导】**"把所有命令敲一遍，看哪个数字大"这个做法有两个硬伤**：

```
① 成本：一次完整巡检要几分钟，而线上故障的分秒都在计费
② 误导：总会有【某个数字看起来偏高】——它可能只是噪声，
        而不是根因；一旦你顺着它查下去，就会离真因越来越远
```

【推导】**正确的做法是"用两个是的/否问题，把可能性先砍掉一大半"**：

```
问题一：是【全部接口】慢，还是【某个接口】慢？
        全部 → 看共用的东西（DB、缓存、网络、宿主机）
        个别 → 看这个接口自己的代码与它独用的依赖
        ★ 这一个问题就能把范围缩掉八成

问题二：是【所有实例】慢，还是【个别实例】慢？
        所有 → 共性资源 / 上游 / 流量
        个别 → 这台机器 / 这个容器 / 这一次部署
```

【取舍】**这两个问题加起来只有四个组合，但每一个组合都指明了下一步**——**这就是"顺序"的价值：它让你在信息最少的时候，做出最有信息量的动作。**

#### 1.2 两个二分：压力 / 能力，在等 / 在算【推导】

【推导】**第二个二分问题决定"加资源有没有用"**：

| | **压力** | **能力** |
|---|---|---|
| 含义 | **活来得太多** | **每件活干得太慢** |
| 判断 | QPS 涨了 / 并发涨了 | QPS 没变，但耗时变长 |
| 对策 | 限流、扩容、排队 | **优化**（算法 / 查询 / 下游） |
| 加机器有用吗 | **有用**（有上限） | **常常没用**（瓶颈在单次耗时上） |

【推导】**第三个二分问题决定"该优化什么"**（同一个算式在三个模块里出现过）：

```
在等（IO / 锁 / 下游）→ 改异步、优化下游、缩小临界区
在算（CPU 密集）      → 加核、改算法、拆到进程池
判据：CPU 占用 / 总耗时
  占比低（如 2%）→ 基本都在等 → 加核没用
  占比高（如 80%）→ 基本都在算 → 改异步没用
（这一算式在 [[母题-O3-IO模型与零拷贝]] 1.1、[[母题-O1-上下文切换与死锁]] 5 反复出现）
```

**到这里你应该能回答**：为什么"先问两个是非题"比"先跑一遍巡检命令"更省时间？

### 2. 四类症状：每一类先看什么

#### 2.1 CPU【事实】

【事实】**先区分三种完全不同的情况**：

| 现象 | 含义 | 下一步 |
|---|---|---|
| **使用率高 + 有用的工作在推进** | **能力问题**（真的在算） | 找热点：火焰图 / `perf`，或看哪个线程在烧 |
| **使用率高 + 吞吐没有提高** | **可能是空转**（自旋、忙等、重试风暴） | 看是否在重试、锁竞争（[[母题-L2-锁的粒度与临界区]]） |
| **使用率不高 + 延迟抖动** | **可能被限流**（容器）或在等 IO | **看 `cpu.stat` 的 `nr_throttled` / `throttled_usec`**（[[母题-X1-容器是什么]] 3.2） |

【推导】**`load average` 是这里最大的坑**：

```
load ≈ 可运行的任务数 + 【不可中断等待】的任务数
→ load 高有两种完全不同的解释：
   ① 很多任务在抢 CPU（可运行）   → 真的 CPU 不够
   ② 很多任务卡在磁盘 IO（不可中断等待）→ 【CPU 可能很闲】
→ 判据：load 高 + CPU 低 = 在等 IO（这是最经典的误判）
```

#### 2.2 内存【事实】

【事实】**三步，顺序不能反**：

```
① 看 available，不看 used        —— used 里很多是可回收的页缓存（[[母题-O2-虚拟内存与缺页]] 3.2）
② 看容器自己的额度               —— free 是宿主机的视图（[[母题-X1-容器是什么]] 2.1）
③ 区分三种"涨"                   —— 泄漏 / 页缓存 / 无上界结构（[[母题-O2-虚拟内存与缺页]] 5.5）
```

【推导】**加一个更早的信号**：**`/proc/pressure/memory`（PSI）** ——**它在 OOM 之前就会升高**，**比"等 OOM 日志"早**（[[母题-O2-虚拟内存与缺页]] 3.2）。

#### 2.3 磁盘【事实】

【事实】**先分清"空间"和"性能"两件事**：

| 问题 | 先看 |
|---|---|
| **空间满** | 从根目录逐层 `du` 排序，或按文件大小找；**注意"已删除但被进程占用的文件"**（`df` 满而 `du` 对不上，就是它） |
| **性能差** | **`%util`（设备忙的程度）与 `await`（平均等待）**；「`%util` 高 + `await` 高」= 设备真的到顶了；「`%util` 不高但 `await` 高」= 排队在别处（如队列深度、文件系统层） |

【推导】**一个高频误判**：**空间满 ≠ 性能差**，**性能差 ≠ 空间满**——**两个问题的定位工具、处理动作完全不同**，**第一句就要分清。**

#### 2.4 网络【事实】

【事实】**四个方向**：

| 方向 | 看什么 | 典型现象 |
|---|---|---|
| **连接** | 连接数、`TIME_WAIT` / `CLOSE_WAIT` 的数量 | 连接池打满 / 端口耗尽（[[母题-N1-一次请求的完整路径]]） |
| **丢包与重传** | 重传率 | 延迟抖动、吞吐上不去 |
| **带宽** | 网卡吞吐 | 大 key / 大结果集把网卡打满（[[母题-R4-大key与热key]]） |
| **对端延迟** | 下游的响应时间 | **这才是"网络慢"最常见的原因**——不是网络，是**下游慢** |

【推导】**最后一条最值得记住**：**大多数"网络问题"其实是"下游问题"**——**因为在调用方看来，两者的表现都是"等待"**。所以**排查时必须把"链路耗时"和"对端处理耗时"分开**，否则会一直修自己不慢的那一段。

**到这里你应该能回答**：为什么"网络慢"这个结论通常需要再往下拆一步？

### 3. 量化与判据

#### 3.1 压力还是能力：用一个比值判断【推导】

【推导】**同一个指标看趋势，两个指标看关系**：

```
判定"压力"：QPS / 并发数【上升】了，而单次耗时基本不变
            → 活多了 → 限流 / 扩容（有效）

判定"能力"：QPS 没变，但单次耗时【上升】了
            → 每件活变慢 → 优化（扩容常常无效）
```

【推导】**再加一条"资源与吞吐的关系"**：

```
加资源能提高吞吐 → 说明瓶颈在这个资源上（压力型）
加资源吞吐不动   → 瓶颈在别处（能力型 / 或别的资源）
→ 这条也叫"看有没有饱和信号"：接近饱和的资源才可能是瓶颈
```

#### 3.2 等 IO 还是等 CPU：交叉判定【推导】

【推导】**单看一个指标不够，要看两个的关系**：

```
CPU 高 + load 高 + 磁盘忙 → 在算，且可能是 CPU 或磁盘
CPU 低 + load 高          → 【在等 IO】（签名）
CPU 低 + load 也低        → 在等【外部】（锁 / 下游 / 连接池）
```

【推导】**第三种最容易被忽略**：**自己什么都不忙，但很慢**——**那一定是在等一个不在本机上的东西**。**这就是分层归因的价值**（[[母题-N1-一次请求的完整路径]] 的"先分清卡在哪一层"）。

**到这里你应该能回答**：为什么"本机指标一切正常"这件事本身就是一条重要线索？

### 4. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "load 高就是 CPU 不够" | 【推导】**两个原因**：可运行任务在抢 CPU，**或**大量任务卡在**不可中断等待**（多为磁盘 IO）。**`load` 高 + CPU 低就是在等 IO 的签名** |
| "CPU 利用率不高就说明没压力" | 【推导】**在容器里尤其错**：配额是"每周期的时间预算"，**用完之后即使核空闲也用不了**——看 `cpu.stat` 的 `nr_throttled` / `throttled_usec`（[[母题-X1-容器是什么]] 3.2） |
| "`free` 显示内存用满就是要爆了" | 【事实】**先看 `available`**：`used` 里很大一部分是**可回收的页缓存**。"用满"本身不是问题，**"回收不动"才是**（[[母题-O2-虚拟内存与缺页]]） |
| "磁盘告警就是空间要满了" | 【事实】**空间与性能是两件事**：空间用 `du`/`df`（注意"已删除但被占用的文件"），**性能看 `%util` 与 `await`**。**第一句就要分清问的是哪一个** |
| "接口慢就是网络问题" | 【推导】**大多数"网络慢"其实是下游慢**——调用方看来都是等待。**必须把链路耗时与对端处理耗时分开**，否则会一直修自己不慢的那一段 |
| "所有指标都正常，那一定是代码有 bug" | 【取舍】**也可能是"在等一个不在本机上的东西"**（锁、连接池、下游、队列）。**"本机一切正常"是一条指向"外部依赖"的线索，不是"没问题"的结论** |
| "先跑一遍完整巡检，把所有指标都看一眼" | 【推导】**先缩范围再看数**：一次巡检几分钟，而且**总会有某个数字偏高**，顺着噪声查会离真因更远。**顺序：全部/个别 → 压力/能力 → 在等/在算，然后才落指标** |
| "排查一个人的活，靠经验" | 【取舍】**经验体现在"知道先排除什么"**：比如"全部接口都慢 → 先看共用依赖"，"个别实例慢 → 先看这台机器和这次部署"。**这些是可以写下来的规则** |

## 二、自测

**Q1（判读）**：监控画面：**CPU 利用率 45%**、`load average = 48`（机器 8 核）、内存 `available` 充足、磁盘空间充足。

问：① 最可能的原因是什么？② 下一步看什么？③ 为什么"CPU 只有 45%"这一条不能让你放心？

**A1**：

```
① load = 48 而机器只有 8 核 → 负载是核数的 6 倍
   但 CPU 利用率只有 45% → 说明【大量任务不是在用 CPU，而是在等】
   最可能：大量任务处于【不可中断等待】（通常是在等磁盘 IO）

② 下一步（按顺序）：
   · 看 IO 压力：iostat 的 %util 与 await；或看 PSI 的 IO 压力
     （/proc/pressure/io）
   · 看这些等待是谁在等：是数据库（可能在本机也可能在别处）
     还是日志 / 临时文件 / 对象存储
   · 如果这台机器上跑着数据库 → 看它的慢查询与刷盘行为
     （[[母题-M7-慢查询与SQL优化手段]]）
```

③ **因为在容器与高并发场景下，"CPU 利用率"本身就可能误导**：

```
· 在容器里：配额用完后即使核空闲也不能用（[[母题-X1-容器是什么]]）
· 在等 IO 时：任务不在 CPU 上，利用率自然不高，但【它就是慢】
· load 高 + CPU 低 这个组合本身就是"在等"的签名
→ 结论：CPU 利用率回答的是"用了多少"，而"慢"的原因是"在等"。
  用"用了多少"去解释"为什么慢"，方向就错了。
```

【这一步在验证什么】验证 2.1 与 3.2：**`load` 与 CPU 的交叉判定，是排查里信息量最大的一个组合。**

**Q2（计算）**：某接口调用链：

```
本服务处理（不含调用）：30 ms
  ├─ 调用服务 B：120 ms     ← B 自己处理 100 ms，网络 20 ms
  └─ 查询数据库：350 ms
总耗时：约 500 ms
```

P99 告警要求压到 **200 ms** 以下。问：① 该优化哪一段？② 如果只优化"网络"能到多少？③ 该项目里"网关超时与应用超时设成一样"为什么会妨碍这次排查？

**A2**：

```
① 按耗时排序，瓶颈很清楚：
   数据库 350 ms（70%）＞ 服务 B 120 ms（24%）＞ 本服务 30 ms（6%）
   → 【先优化数据库那 350 ms】
   → 这一步就是"分层归因"：不分层的话，可能有人会去优化那 30 ms 的代码

② 只优化网络（20 ms）：
   500 → 480 ms，【离 200 ms 的目标差得远】
   → 典型错误：在最小的一块上使劲
```

③ **超时设成一样会妨碍排查**（这一点在 [[母题-N1-一次请求的完整路径]] 已记，这里是它在本卡的形态）：

```
网关超时 = 应用超时 → 两边几乎同时放弃
→ 日志里看不出【是谁先超时的】
→ 无法判断"是应用处理慢"还是"网关等不及"
→ 正确做法：外层比内层略长，让内层先超时并留下自己的错误
   （这样错误里带着"内层的原因"，归因才有依据）
```

【这一步在验证什么】验证 2.4 与 3.2：**"慢"要按耗时排序去优化；而"能归因"是排查的前提——超时层级设计错了，日志里就没有归因信息。**

**Q3（计算/判读）**：某服务 `df` 显示磁盘 **100% 满**，但 `du` 从根目录加起来只有 **60%**。

问：① 差额那部分去哪了？② 怎么确认？③ 该怎么处理？

**A3**：

```
① 差额最可能是【已删除但被进程占用的文件】：

   进程打开了文件 → 文件被删除 → 【目录项没了，但进程还持有文件描述符】
   → du 看不到它（不在目录树里了）
   → df 仍然算着它（磁盘块没释放）
   → 于是 df 满、du 不满
```

② **确认方法**：找"持有已删除文件的进程"——

```
按 /proc/<pid>/fd 里的链接状态找"deleted"的文件
（常用做法：lsof +L1 一类，或遍历 /proc/*/fd 找指向已删除文件的链接）
→ 排名靠前的通常就是"没关日志文件 / 没关临时文件"的那个进程
```

③ **处理（按风险从低到高）**：

| 顺序 | 动作 | 说明 |
|---|---|---|
| **1** | **先确认这个文件是谁、有多大** | 别急着动手——**它可能是正在写的日志，也可能是关键数据** |
| **2** | **能重启就重启那个进程**（或让它正常关闭文件） | **释放描述符即释放空间**，最干净 |
| **3** | **如果它是日志，改配置（轮转 + 上限）** | **根因是"日志没有上限"** ← 见下 |
| **4** | 应急：清空文件内容（而不是删文件） | 只对**能安全清空的日志类文件**用；**对业务文件绝不能用** |

【推导】**根因几乎总是同一句话**：**"某个会增长的东西没有上界"** ——

```
日志没轮转 → 一直写 → 占满
临时文件不清理 → 占满
队列 / 缓存落盘不设上限 → 占满
→ 与 [[母题-O2-虚拟内存与缺页]] 5.5 的结论完全一致：
  【给每个会增长的东西设上界】是资源治理里唯一通用的手段
```

【这一步在验证什么】验证 2.3：**"空间"和"性能"是两件事**；而空间问题的根因，通常又是"没有上界"。

**Q4（纠错）**：下面这段话哪里错了？

> "接口变慢了，我先看了监控：CPU 45%、内存正常、磁盘正常、网络正常。所以本机资源都没问题，肯定是代码有 bug，我先把代码 review 一遍。"

**A4**：**"本机资源都正常 ⇒ 一定是代码 bug"这个推理跳过了最重要的一步。**

**【推导】慢的原因有三类，只排除了其中一类**：

| 类别 | 例子 | 本机指标会怎样 |
|---|---|---|
| **① 本机资源不够** | CPU 打满、内存紧、磁盘满 | **指标异常** ← 他排除了这一类 |
| **② 在等外部** | 下游慢、数据库慢、锁 / 连接池排队、**队列积压** | **指标"一切正常"** ← 这一类**完全没排除** |
| **③ 真的在算** | 算法退化、N+1 查询、序列化大对象 | 可能指标正常 |

**"本机一切正常"本身就是一条线索：说明它在等一个不在本机上的东西**（3.2）。**而代码 review 是成本最高、命中率最低的动作**（几百行代码里找一个性能问题）。

**正确顺序**：

```
① 先问两个是非题：全部接口还是个别接口？所有实例还是个别实例？
② 再看"在等还是在算"（CPU 占用 ÷ 总耗时）
③ 若判定"在等" → 【看调用链各段的耗时】
   （下游 / 数据库 / 锁 / 队列，这一步就能定位到段）
④ 只有确认"在算"且"没找到外部原因"时，才去看代码
```

【取舍】**并且要给"在等"这一类别更明确的检查项**（极易被"本机正常"掩盖）：

```
· 数据库慢查询 / 锁等待时长
· 下游接口的 P99
· 连接池的 active / idle / 等待队列长度
· 队列的 lag（[[母题-Q3-积压与高可用]]）
```

**准确说法**：*"本机资源正常"只排除了一类原因，它反而在提示"在等外部"。正确顺序是先用两个是非题缩范围，再按调用链分段比耗时，最后才看代码。*

**Q5（纠错）**：下面这段话哪里错了？

> "这次慢是网络问题，我看了，跨机房调用延迟很高。所以让运维把网络优化一下就好了。"

**A5**：**"网络问题"这个结论很可能把"下游慢"误诊成了"链路慢"——而两者的处置完全不同。**

**【事实】调用方看到的"等待"包含两段，必须分开**：

```
调用总耗时 = 【链路耗时】（网络往返 + 排队）+ 【对端处理耗时】
→ 两者在调用方看来都是"等"，但责任方完全不同
```

**怎么分辨**：

| 现象 | 更像 |
|---|---|
| **对端有"处理耗时"的日志/埋点，且它很大** | **对端慢**（网络只是背锅） |
| **对端处理很快，但调用方测出来很慢** | 链路问题（丢包、重传、带宽、排队） |
| 两者都正常但偶发变慢 | 看**重传率**与**尾部延迟**（偶发通常指向丢包） |

【推导】**为什么"网络慢"这个结论常常是错的**：

```
· 跨机房调用延迟高是【设计上就存在】的固定成本（几十毫秒量级），
  它不解释"从 200ms 涨到 3s"这种量级的变化
· 真正会突然变慢的，通常是【对端】：
  数据库慢了、下游依赖慢了、对端实例数少了
· 而"网络"这个解释最省事、最不需要证据，所以最容易被当成结论
```

【取舍】**正确的动作**：**先去对端看它的处理耗时**（有没有埋点、有没有 Trace，见 [[母题-E2-Trace与可观测性]]）——**如果对端说"我处理只用了 10ms"，那才轮到怀疑链路**。**先归因，再优化**；顺序反了就是让运维白干。

**准确说法**：*调用方的"等待"包含链路与对端两段，要先分开再归因。跨机房的固定延迟不解释量级变化；突然变慢更常来自对端。定位要落到分段耗时上，而不是先给结论。*

## 三、面试输出（学完再看）

**一句话结论**：排查的能力**体现在顺序上，不在记得多少命令**——先用两个是非题把范围缩掉八成：**① 是全部接口慢还是个别人慢？② 是所有实例慢还是个别实例慢？**；再用两个二分问题定方向：**是"压力"（活来得太多 → 限流扩容有效）还是"能力"（每件活变慢 → 要优化）**、**是"在等"还是"在算"（CPU 占用 ÷ 总耗时，低就是等）**。四类症状各有第一眼：**CPU** 要分清"在算 / 空转 / **被容器限流**"（后者看 `cpu.stat` 的 `nr_throttled`）；**内存**先看 `available` 不看 `used`、再看容器自己的 cgroup 额度、最后分清泄漏 / 页缓存 / 无上界；**磁盘**要**先分清"空间"还是"性能"**（空间用 `du`/`df`，注意"已删除但被占用的文件"；性能看 `%util` 与 `await`）；**网络**要记住**大多数"网络慢"其实是下游慢**——必须把链路耗时与对端处理耗时分开。**三个最容易误判的信号**：`load` 高 + CPU 低（在等 IO）、CPU 不高但延迟抖（被限流）、`free` 显示满（页缓存可回收）。**而"本机一切正常"是一条指向"我在等外部"的线索，不是"代码有 bug"的结论。**

**恢复关键词**：**顺序比命令重要** / 两个是非题（全部/个别接口 · 所有/个别实例）/ 二分：压力 vs 能力 / 二分：在等 vs 在算（CPU 占比）/ **load 高 + CPU 低 = 在等 IO** / **CPU 不高但延迟抖 = 可能被限流（cpu.stat）** / 内存先看 `available`、容器看 cgroup / PSI 比 OOM 日志早 / **磁盘：空间 vs 性能先分清** / `df` 满 `du` 不满 = 已删除但被占用 / **"网络慢"大多是下游慢**：分开链路耗时与对端耗时 / 本机正常 → 在等外部 / 根因常是"某处没有上界" / 先归因再优化

**核心不变量 / 主线**：
**排查的本质是"用最少的动作，把可能性砍成两半"，而不是"把所有指标看一遍"。** 每一次二分（全部/个别、压力/能力、在等/在算）都把范围砍掉一半；**而"本机指标一切正常"从来不是结论，它是一条指向"外部依赖"的线索。**

**完整回答骨架**：先立"顺序比命令重要" → 两个是非题缩范围 → 两个二分定方向（压力/能力、在等/在算）→ 四类症状的第一眼（CPU / 内存 / 磁盘 / 网络）→ 三个最易误判的信号 → 用耗时排序定位到段（分层归因）→ 边界与误解

**完整回答（口述稿）**：
排查的能力**体现在顺序上，不在记得多少命令**。先用**两个是非题**把范围缩掉八成：**① 全部接口慢还是个别慢？② 所有实例慢还是个别实例慢？**；再用**两个二分**定方向：**是"压力"（活太多 → 限流扩容有效）还是"能力"（每件活变慢 → 要优化）**、**是"在等"还是"在算"**（看 CPU 占用 ÷ 总耗时，低就是等）。

四类症状各有第一眼：**CPU** 要分清在算 / 空转 / **被容器限流**（看 `cpu.stat` 的 `nr_throttled`）；**内存**先看 `available` 不看 `used`、再看容器自己的 cgroup 额度、最后分清泄漏 / 页缓存 / 无上界；**磁盘**要先分清"**空间**"还是"**性能**"（空间用 `df`/`du`，注意"已删除但仍被占用"的文件 —— `df` 满但 `du` 对不上时用 `lsof +L1` 找；性能看 `%util` 与 `await`）；**网络**要记住**大多数"网络慢"其实是下游慢**，必须把链路耗时与对端处理耗时分开。

三个最容易误判的信号：**`load` 高但 CPU 不高 = 在等 IO**（下一步看 IO 压力，不是加 CPU）；**CPU 利用率不高但延迟抖动 = 可能已被限流**；**接口慢但本机指标全正常 = 指向外部依赖**（按调用链分段比耗时）。

**PSI 比 load 好**：它直接报"有多少比例的时间在等"，且 CPU/内存/IO 分开报；而 load 是队列长度的移动平均，分不清是 CPU 还是 IO，容器限流更是看不出来。

**分层要点**：
- **结论**：顺序优先——两个是非题 → 两个二分 → 四类症状分头看；先聚合后单机。
- **推导链**：缩范围 → 定压力/能力与在等/在算 → 分类看资源 → 三个易误判信号的正确读法 → PSI 补 load 的盲区。
- **量化**：CPU 占用 ÷ 总耗时定"在等还是算"；`cpu.stat` 的 `nr_throttled` / `throttled_usec` 看限流。
- **边界与常见误解**：TIME_WAIT 多出现在主动关闭方、本身不是故障（治法是长连接/连接池，不是调参数）；connection 打满要先看是否上游变慢（`L = λW`），不是先调大上限。

**追问**（先说后看）

1. **`load` 高但 CPU 不高说明什么？** —— **大量任务处于不可中断等待**（通常是磁盘 IO）。**这就是"在等"的签名**——下一步看 IO 压力（`%util` / `await` / IO PSI），而不是加 CPU。
2. **CPU 利用率不高，为什么还可能是 CPU 的问题？** —— **容器配额是"每周期的时间预算"**，用完就不给——**看 `cpu.stat` 的 `nr_throttled` / `throttled_usec`**（[[母题-X1-容器是什么]] 3.2）。
3. **怎么区分 IO 瓶颈和 CPU 瓶颈？** —— 看 **CPU 占用 ÷ 总耗时**：占比低就是"在等"（IO / 锁 / 下游）；再交叉 `load` 与磁盘指标定位到具体是哪一种"等"。
4. **接口慢但本机指标全正常，怎么查？** —— **它指向"外部依赖"**：按调用链分段比耗时（下游、数据库、连接池、队列），**先归因再优化**。**别忘了检查超时层级是否设成了"内外一样"**——那会让日志失去归因信息。
5. **"网络慢"该怎么验证？** —— **把链路耗时和对端处理耗时分开**：对端有埋点就看它的处理时间；**跨机房的固定延迟不解释量级变化**，突然变慢通常是**对端**的问题。

**同类变体**

- 「怎么知道扩容有没有用？」——**看瓶颈有没有饱和**：加资源后吞吐上去了 → 瓶颈在这；**不动 → 瓶颈在别处**。这也是"压力还是能力"的实践版
- 「日志刷得太多会不会导致变慢？」——**会**：同步写日志会阻塞（[[母题-O1-上下文切换与死锁]] 4.3 的"阻塞会拖垮整条链路"），而且日志文件本身就是"没设上界的东西"（Q3）
- 「为什么要有 Trace？」——**因为"本机正常但慢"这一类问题，只能靠跨段耗时来定位**（[[母题-E2-Trace与可观测性]]）；排查顺序的最后一步就是"追一条完整链路看时间花在哪一段"
- 「项目和排查有关的一个教训是什么？」——**EnergyOps 的 `00-project-map.md` 里有"故障 → 后端归属"的对照表**：**把"这类现象该去哪个模块查"提前写下来**——这就是把"顺序"沉淀成资产
