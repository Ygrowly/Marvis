**题目**：某服务发版时，每次滚动更新都会有**少量请求失败**（大概千分之几）。日志里看不到异常，监控上就是"发版那两分钟错误率抬升"。为什么？另外：服务启动时数据库还没就绪，容器直接崩了，反复重启——这该怎么处理？

**母题**：一个服务从"镜像是好的"到"能稳定服务"，中间要过哪几关。

## 一、教材

### 1. 前提：上线的成败取决于"怎么退出"

#### 1.1 两个方向，两个难点【推导】

【推导】**上线包含"起"和"停"两件事，而它们的难点完全不同**：

| | 启动 | 停止 |
|---|---|---|
| 难点 | **依赖没就绪**（DB / Redis / 配置中心还没好） | **在途请求还没处理完** |
| 代价 | 起不来（能发现） | **丢请求（难发现）** |
| 常见错法 | 依赖没就绪就退出，然后被反复重启 | 收到停止信号就立刻退出 |

【推导】**为什么"停止"更难**：

```
启动失败 → 进程起不来 → 【有人立刻知道】
停止不当 → 进程优雅地退出了、日志一切正常 →
          但【那几百个正在处理的请求被丢了】→ 只有监控上的错误率抬升
→ 而"发版时错误率抬升"常被当成偶然，不被追责
```

**【本卡开头的那个问题就是这一类型】** ——**发版时千分之几的错误，就是"收到停止信号就退出"造成的。**

#### 1.2 信号：`SIGTERM` 与 `SIGKILL`【事实】

【事实】**这两个信号的语义完全不同**：

| 信号 | 含义 | 能不能被处理 |
|---|---|---|
| **`SIGTERM`（15）** | **"请你收工"** ——进程可以捕获它、做清理、然后自己退出 | ✅ 可以捕获与处理 |
| **`SIGKILL`（9）** | **"现在就走"** ——内核直接终止，**不能捕获、不能阻塞** | ❌ 不可捕获、不可忽略 |

【推导】**平台的停止流程几乎都是"先 15、后 9"**：

```
停止指令 → 发 SIGTERM → 等【一段宽限期】（grace period）→ 还没退出 → 发 SIGKILL
```

【事实】**宽限期的默认值随平台不同**（**属默认值，不是规范**，具体要看你自己的配置）：

- 容器运行时：通常是**秒级到十几秒**（例如 10 秒一类）
- 编排平台：常见默认**30 秒**一类，且可配

**所以优雅退出的时间窗不是"想设多少就多少"** ——**它被平台设定的宽限期卡住**。**你的退出逻辑必须能在宽限期内完成，否则会在最后被 `SIGKILL` 打断。**

**到这里你应该能回答**：为什么应用里的优雅退出逻辑通常要"顺便主动告诉平台：我要退了"？

### 2. 优雅退出的四个动作（顺序不能乱）

#### 2.1 四步【推导】

::figure graceful-shutdown.svg | 优雅退出的四步与时间窗 | 先摘流量、再等排空、然后关依赖、最后退出；时间窗要大于最长在途请求

【推导】**正确顺序是"先摘流量，再等排空，然后关依赖，最后才退出"**：

| # | 动作 | 为什么必须在这一步 |
|---|---|---|
| **① 停止接收新请求** | 从负载均衡 / 服务注册里摘掉自己（或把就绪探针置为失败） | **这是最关键的一步**：不做的话，你一边处理在途请求、一边还在接新请求，**永远排不空** |
| **② 等在途请求处理完** | 设一个"最长等待时间"，等到都返回或超时 | 这才是"优雅"的本体 |
| **③ 关掉对外依赖** | 关连接池、提交 / 回滚事务、flush 缓冲 | 在 ② 之后，因为 ② 里还要用它们 |
| **④ 退出进程** | 主动 `exit(0)`，不必等 `SIGKILL` | **主动退出比被 `SIGKILL` 好**：能控制退出码、能打完日志 |

【推导】**① 为什么最容易漏**：

```
如果不在负载均衡侧摘掉自己：
  发版时，LB 还在把新请求发给你
  你在等"在途请求变 0"，但新请求一直在进来
  → 永远等不到 → 宽限期到 → 【SIGKILL 杀掉一批在途请求】
→ 这就是"发版时错误率抬升"的机制
```

#### 2.2 一个更隐蔽的点：异步任务与队列【推导】

【推导】**HTTP 请求不是唯一的"在途工作"**：

```
消费队列的 Worker：
  ① 停止拉取新消息
  ② 等当前这条处理完（或者主动把没处理完的【放回队列】）
  ③ 关闭连接
  ④ 退出
```

【取舍】**这里要和"至少一次投递"配合**（[[母题-Q2-重复与乱序]]）：**退出时"没处理完的消息"应该让它重投，而不是标记为已处理**——**因为重复是安全的（有幂等），丢是不可接受的**。

【事实】**RuleArena 与 EnergyOps 都是这个思路**：**Worker 重启后先读权威状态再校准 Checkpoint**（`04-idempotency-and-recovery.md` §9、`07-task-lifecycle-and-delivery.md`）——**这说明它们的设计前提就是"进程会被随时拿走"**，而不是"优雅退出一定做得到"。

**到这里你应该能回答**：为什么"进程会被随时杀掉"是设计前提，而不是异常情况？

### 3. 量化：时间窗该怎么算

#### 3.1 优雅退出的时间窗【推导】

【推导】**时间窗的算式**：

```
优雅退出时间窗 > 停止接线生效时间 + 最长在途请求时间 + 清理时间
```

【推导】**代进数字算一遍**（自测 Q1 完整算）：

```
最长在途请求时间（P99.9）：800 ms
停止接线生效时间（LB / 注册中心把状态同步下去）：约 1 s
清理（关连接池、flush）：200 ms
→ 时间窗至少 ≈ 1 + 0.8 + 0.2 = 【2 s】

如果平台宽限期只有 10 s，那 2 s 足够，还能留余量；
如果某个接口【设计上就可能跑 30 s】（比如导出），
→ 它一定会被 SIGKILL 打断 → 【这种接口不该阻塞退出】
```

【取舍】**结论**：**"长任务"不应该在退出路径上等** ——它应该被设计成"**可中断 + 可恢复**"：

```
长任务：停止接新任务 → 把当前进度写下来（checkpoint）→ 主动退出
        → 恢复时从 checkpoint 继续（[[母题-A4-长任务状态与Checkpoint]]）
```

#### 3.2 启动：依赖没就绪怎么办【推导】

【推导】**三种做法，各有代价**：

| 做法 | 怎么做 | 代价 |
|---|---|---|
| **① 启动重试** | 连不上依赖就重试，**有上限与退避** | 起得慢；重试耗尽还是会失败 |
| **② 就绪探针（推荐）** | **进程照常启动，但"就绪"状态先为"未就绪"** ——收到流量前先自检依赖 | **要有就绪探针这个概念**（不能只靠"进程活着"） |
| **③ 硬失败退出** | 连不上直接退出，让平台重启 | **会造成"重启风暴"**：依赖越忙越重启，越重启越忙 |

【推导】**② 为什么最好**：它把"**进程活着**"和"**能服务**"分开了：

```
存活（liveness）   → 进程还在、没死锁   → 失败 → 【重启】
就绪（readiness）  → 依赖都通、能服务   → 失败 → 【暂时不接流量，不重启】
→ 关键区分：依赖没就绪时，【不该重启】，只该"暂时不接流量"
```

【取舍】**探针设计错的两个典型后果**：

```
就绪探针太严（把慢依赖也算进去）→ 依赖一抖，所有实例一起"不就绪"→ 全站不可用
存活探针太敏感（把"暂时不健康"当"死了"）→ 频繁重启 → 雪上加霜
→ 判据：就绪探针可以严（不接流量而已），存活探针必须【极其保守】（它会导致重启）
```

**到这里你应该能回答**：为什么"依赖不可用"应该表现为"暂时不接流量"而不是"重启"？

### 4. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "发版时错误率抬升是正常的" | 【推导】**不是正常的**。千分之几的错误率抬升通常就是**没有优雅退出**（或没在 LB 侧摘流量）造成的——**它是 bug，不是发版成本** |
| "收到停止信号就 `exit(0)` 就行" | 【推导】**会丢在途请求**。正确顺序是**先摘流量 → 等在途完成 → 关依赖 → 退出**，且**①摘流量最容易漏** |
| "优雅退出做得好就一定不丢请求" | 【取舍】**不能保证**：宽限期到就 `SIGKILL`。所以**长任务必须设计成"可中断 + 可恢复"**，而不是指望"一定能优雅退完" |
| "进程活着就是服务可用" | 【事实】**要分存活与就绪**：**存活失败 → 重启；就绪失败 → 暂时不接流量**。混在一起会在依赖抖动时造成重启风暴或全站不就绪 |
| "启动时依赖没就绪，多重启几次就好了" | 【取舍】**可能变成重启风暴**（依赖越忙越重启）。更好的做法是**就绪探针 + 有上限的退避重试** |
| "配置写死在镜像里就行" | 【取舍】要分清：**镜像里放不变的东西**（代码、依赖），**环境相关的走环境变量 / 配置中心**。**配置中心引入了一个新的启动依赖**——它不可用时要有兜底（本地默认值 / 上次成功的缓存） |
| "优雅退出只跟 HTTP 服务有关" | 【推导】**队列消费者同样要**：停止拉取 → 处理完当前 / 把未完成的放回队列 → 关连接 → 退出。**关键是"没处理完的要让它重投，而不是标记成功"** |
| "多实例滚动更新就不需要优雅退出了" | 【推导】**反了**：**滚动更新恰恰让"摘流量"成了必须做的事**——多实例的每一次替换都会触发一轮"摘流量 → 排空 → 退出"，做得不对就每次发版都掉一点请求 |

## 二、自测

**Q1（计算）**：某服务最长在途请求 **P99.9 = 800 ms**；LB 摘流量生效约 **1 s**；清理约 **200 ms**；平台的宽限期是 **10 s**。

问：① 优雅退出最少需要多久？② 留多少余量合适？③ 如果有个导出接口最长跑 60 s，怎么办？

**A1**：

```
① 最少 = 摘流量生效（1 s）+ 最长在途（0.8 s）+ 清理（0.2 s）= 【2 s】

② 建议留到 2–3 倍余量（4–6 s），理由：
   · "最长在途"是个统计值，会有更长的尾巴
   · 摘流量生效时间受注册中心推送延迟影响，会抖
   · 必须严格小于平台宽限期（10 s），留出安全边界
   → 设 5 s 左右：既覆盖住正常情况，也不会逼近 10 s 上限
```

③ **导出接口（60 s）绝不能阻塞退出**：

```
❌ 等它跑完 → 60 s > 宽限期 10 s → 必然被 SIGKILL，而且还拖慢了整个发版
✅ 设计成"可中断 + 可恢复"：
     收到停止信号 → 把当前进度写入 checkpoint → 主动结束该任务
     → 下一次启动（或另一个实例）从 checkpoint 继续
   → 这正是 [[母题-A4-长任务状态与Checkpoint]] 的形态
   → 如果这个导出已经产生副作用（比如发了一个文件），
     恢复时要靠幂等键避免重复（[[母题-Q2-重复与乱序]]）
```

【这一步在验证什么】验证 2.1 与 3.1：**优雅退出有一个可算的时间窗，而"长任务"必须在设计上就不进入这个窗口。**

**Q2（判读）**：某服务的"存活探针"配置是"调用 `/health` 接口，如果 3 秒不返回就重启容器"，而 `/health` 里会去查一次数据库。

问：① 这个配置会引发什么？② 怎么改？

**A2**：

```
① 会引发「重启风暴」：
   数据库变慢 → /health 3 秒不返回 → 探针判定"不健康" → 【重启容器】
   → 所有实例同时重启 → 重启后依然要查数据库 → 又超时 → 又重启
   → 而且重启期间【连接池重建、缓存失效】，数据库压力更大
   → 【依赖的一点点抖动，被放大成全站不可用】
```

② **改法（把两类探针的职责分开）**：

| 探针 | 该检查什么 | 失败后果 |
|---|---|---|
| **存活（liveness）** | **只检查"进程自己还行不行"**：事件循环没死锁、主线程在转 —— **绝不查外部依赖** | 重启 |
| **就绪（readiness）** | **检查"能不能服务"**：关键依赖是否可用 | **暂时不接流量（不重启）** |
| **启动（startup）** | 给慢启动的服务争取时间（避免存活探针在启动期就开火） | 重启 |

【取舍】**判据一句话**：**"这件事重不重启能改善？"** ——

```
不能改善的（数据库慢、下游挂）→ 绝不放在【存活】里 → 重启只会更糟
能改善的（进程死锁、内存泄漏到没法跑）→ 才放存活
```

【这一步在验证什么】验证 3.2：**"进程活着"和"能服务"是两件事，混在一起会把外部故障放大成自身故障。**

**Q3（判读）**：某队列消费者的代码是：

```python
while True:
    msg = queue.pop(timeout=1)
    handle(msg)
    queue.ack(msg)          # 处理完就确认
```

收到 `SIGTERM` 时进程直接退出。问：① 会丢消息吗？② 会不会重复？③ 该怎么改？

**A3**：

```
① 会丢：
   如果在 handle(msg) 之后、ack(msg) 之前收到 SIGTERM → 进程退出
   → 消息【没被 ack】→ 按"至少一次"语义它会被重投
   → 这反而是【安全的】——因为它没被确认

   真正会丢的是另一种写法：先 ack 再 handle
   → ack 之后进程退出 → 消息永久丢失（[[母题-Q1-消息为什么会丢怎么才不丢]] 2.3）

② 会重复（这是设计上的必然）：
   凡是"处理完但没 ack 就崩"的消息都会重投
   → 所以【消费逻辑必须幂等】（[[母题-Q2-重复与乱序]]）
```

③ **改法（四步，与 HTTP 服务同构）**：

```
① 收到 SIGTERM → 置标志位，【停止拉取新消息】
② 等当前这条处理完 → 然后 ack（或按策略 ack）
③ 如果在宽限期内跑不完 → 【主动不 ack】（让它重投），而不是硬撑
④ 关闭连接 → 退出
```

【取舍】**这里有一条很值得说的取舍**：**"宽限期内跑不完"时，不 ack 让它重投，比"硬撑着跑完"更安全**——因为**重复是幂等能吃掉的问题，而"被 SIGKILL 打断在处理中间"可能留下半个副作用**。**这就是"宁可重投，不要半途而废"的原则。**

【这一步在验证什么】验证 2.2：**队列消费者的退出规则和 HTTP 服务同构，但多一条"没处理完就不 ack"** ——**这条规则让"退出"变成了安全动作**。

**Q4（纠错）**：下面这段话哪里错了？

> "我们服务做了优雅退出，收到 SIGTERM 会等 30 秒让请求跑完。所以发版是绝对安全的，不会丢请求。"

**A4**：**"做了优雅退出"和"绝对安全"之间差了四个坑。**

1. **宽限期可能比 30 秒短**：**平台先发 `SIGTERM`、等够了宽限期再发 `SIGKILL`**——**如果平台设的是 10 秒，你的 30 秒等待根本走不完**，最后 20 秒的工作会被 `SIGKILL` 打断。**所以等待时间必须小于平台宽限期**。

2. **没有"先摘流量"的话，永远等不到"没有在途请求"**：

```
只在应用内等：LB 还在往你这儿发新请求
→ 在途请求数不降反升 → 30 秒等完还有一堆 → SIGKILL 打断
→ 必须先在 LB / 注册中心侧摘掉自己（或让就绪探针失败）
```

3. **`SIGKILL` 是不可捕获的**：所以"等够了就不会被强杀"是错觉——**宽限期一到就一定被强杀**，你的清理逻辑可能那一瞬间还没跑。

4. **长任务和异步任务不一定走这条路径**：**队列消费者**有自己的规则（停止拉取、不 ack 让它重投），**定时任务与长导出**根本不该进入退出等待——**它们要设计成可中断 + 可恢复**。

**准确说法**：*优雅退出需要"先摘流量 → 等在途 → 关依赖 → 退出"，且等待时间要小于平台宽限期；`SIGKILL` 不可捕获，所以长任务必须可中断可恢复；队列消费者要额外遵守"没处理完不 ack"。*

**Q5（纠错）**：下面这段话哪里错了？

> "服务起来时连不上数据库就直接退出，让平台自动重启——反正重试几次总有一次能连上。"

**A5**：**"总有一次能连上"是一个会把小故障放大成大故障的假设。**

**【推导】问题在于正反馈**：

```
数据库变慢（比如因为流量高峰）
  → 所有实例连不上 / 连上超时 → 【集体退出】
  → 平台重启它们 → 重启期间：
      连接池要重建、本地缓存要预热、可能全量加载数据
  → 数据库承受【更大的瞬时压力】
  → 更连不上 → 又集体退出
→ 【重启风暴】：依赖越忙越重启，越重启越忙
```

**正确做法（三步）**：

| 步 | 做法 |
|---|---|
| **① 启动用有上限的退避重试** | 连不上就退避重试（指数退避 + 抖动），**而不是立刻退出** |
| **② 把"能服务"与"进程活着"分开** | **就绪探针失败 → 暂时不接流量（不重启）**；存活探针只管进程自身（**绝不查外部依赖**） |
| **③ 给依赖故障留降级路径** | 关键依赖不可用时的行为要预先定义（**fail closed 还是降级**）——数驭穹图的选择是"权限不确定就 fail closed"（`07-权限安全与生产隔离.md`） |

【推导】**本卡开头第二个问题的答案就是这个**：**服务启动时数据库没就绪 → 容器反复重启 → 必须改成"就绪探针 + 退避重试"**，**让"依赖不可用"表现为"暂时不接流量"，而不是"进程死掉"。**

**准确说法**：*"连不上就退出让平台重启"会造成重启风暴——依赖越忙越重启、越重启越忙。正确做法是启动退避重试 + 就绪探针（不接流量而不是重启）+ 预先定义依赖不可用时的降级行为。*

## 三、面试输出（学完再看）

**一句话结论**：上线的成败**取决于"怎么退出"，不取决于"怎么启动"**。正确的优雅退出顺序是 **① 先摘流量（从 LB / 注册中心摘掉，或让就绪探针失败）→ ② 等在途请求处理完 → ③ 关依赖（连接池、事务、缓冲）→ ④ 主动退出**，其中 **①最容易漏**（漏了就会"永远等不到没有在途请求"，最后被 `SIGKILL` 打断）。**时间窗可以算**：`摘流量生效 + 最长在途请求 + 清理` ≤ **平台宽限期**（`SIGTERM` 之后平台会等一段，超时就 `SIGKILL`——**不可捕获、不可协商**），所以**长任务必须设计成"可中断 + 可恢复"**（写 checkpoint 后主动退出，而不是撑着跑完）。启动侧的关键是**分清两类探针**：**存活失败 → 重启（只检查进程自己，绝不查外部依赖）；就绪失败 → 暂时不接流量（不重启）**——**把依赖故障放进存活探针会造成"重启风暴"**。队列消费者额外遵守一条：**没处理完就不 ack，让它重投**（重复由幂等吃掉，丢是不可接受的）。

**恢复关键词**：难点在"停止"不在"启动" / **`SIGTERM` 可捕获（请你收工）、`SIGKILL` 不可捕获（现在就走）** / 平台流程：15 → 宽限期 → 9 / **四步：摘流量 → 排空 → 关依赖 → 退出** / **摘流量最容易漏（否则永远排不空）** / 时间窗 = 摘流量生效 + 最长在途 + 清理 < 宽限期 / **长任务要可中断可恢复，不该进退出窗口** / **存活（进程自己，失败→重启）vs 就绪（能服务，失败→不接流量）** / 存活探针绝不查外部依赖（否则重启风暴） / 启动用退避重试而不是硬退出 / 队列消费者：停止拉取 → 处理完 / **不 ack 让它重投** / 配置中心也是一个启动依赖，要有兜底

**核心不变量 / 主线**：
**"进程会被随时拿走"是设计前提，不是异常情况。** 所以正确的思路不是"把优雅退出做到完美"，而是**让"被拿走"成为安全事件**：在途请求要么完成、要么可重投；长任务要么可中断、要么可恢复；依赖不可用只影响"接不接流量"，不影响"进程是否活着"。

**完整回答骨架**：先立"难点在停止"→ `SIGTERM` / `SIGKILL` 的语义与平台的宽限期 → 优雅退出四步（强调摘流量）→ 异步与队列的版本 → **算时间窗** → 长任务的处理方式 → 启动侧：两类探针的分工 + 退避重试 → 边界与误解

**完整回答（口述稿）**：
上线的成败**取决于"怎么退出"，不取决于"怎么启动"**。优雅退出四步：**① 先摘流量**（从 LB / 注册中心摘掉，或让就绪探针失败）→ ② 等在途请求处理完 → ③ 关依赖（连接池、事务、缓冲）→ ④ 主动退出；其中 **①最容易漏**（漏了就会"永远等不到没有在途请求"，最后被 `SIGKILL` 打断，这是发版时错误率抬升最常见的根因）。

`SIGTERM` **可被捕获**，平台是"**先发 15、等宽限期、再发 9**"，`SIGKILL` **不可捕获、不可协商**。时间窗要满足 `摘流量生效 + 最长在途请求 + 清理 ≤ 平台宽限期`；设错的后果：短了请求被硬打断，长了等于没做清理。所以**长任务必须设计成"可中断 + 可恢复"**（写 checkpoint 后主动退出，而不是撑着跑完）。

探针两种：**存活失败 → 重启（只检查进程自己，绝不查外部依赖）**；**就绪失败 → 只是不接流量（不重启）**。判据是"**重启这件事能不能改善现状**"——把依赖故障放进存活探针会造成**重启风暴**。

启动依赖没就绪：**有上限的退避重试 + 就绪探针**，不要"连不上就退出"。队列消费者额外一条：**没处理完就不 ack，让它重投**（重复由幂等吃掉，丢是不可接受的）。配置三种来源里，**密钥永远不要进环境变量**（会进进程环境、容易被打进日志）。

**分层要点**：
- **结论**：退出比启动重要；先摘流量是第一步；存活与就绪探针的分工看"重启能不能改善现状"。
- **推导链**：不摘流量 → 永远等在途 → 被 SIGKILL → 错误率抬升 → 时间窗算式 → 可中断可恢复 → 探针分工 → 重启风暴。
- **量化**：`摘流量生效 + 最长在途请求 + 清理 ≤ 平台宽限期`；SIGTERM=15、SIGKILL=9。
- **边界与常见误解**：宽限期超时是不可协商的；依赖故障只能放就绪探针；滚动更新让"摘流量"成为必须。

**追问**（先说后看）

1. **优雅退出为什么要"先摘流量"？** —— **否则会永远等不到"没有在途请求"**：LB 还在发新请求，在途数不降反升，直到宽限期用完被 `SIGKILL`。**这是"发版时错误率抬升"最常见的根因。**
2. **`SIGTERM` 和 `SIGKILL` 有什么区别？** —— `SIGTERM` **可被捕获**（做清理后自己退出）；`SIGKILL` **不可捕获、不可忽略**，内核直接终止。**平台是"先 15、等宽限期、再 9"**。
3. **存活探针和就绪探针怎么分工？** —— **存活只管进程自身**（死锁、卡死），失败**重启**；**就绪表示"能服务"**，失败**只是不接流量**。**判断依据是"重启这件事能不能改善现状"**——不能（依赖挂、下游慢）就绝不放存活。
4. **队列消费者怎么优雅退出？** —— **停止拉取 → 处理完当前这条 → ack → 关连接 → 退出**；**宽限期内跑不完就【不 ack】，让它重投**——**重复由幂等吃掉，丢是不可接受的**（[[母题-Q2-重复与乱序]]）。
5. **服务启动依赖服务没就绪怎么办？** —— **有上限的退避重试 + 就绪探针**（表现为"暂时不接流量"），**不要"连不上就退出"**——那会造成重启风暴。

**同类变体**

- 「滚动更新和优雅退出什么关系？」——**滚动更新让"摘流量"成为必须**：每次替换实例都会触发一轮"摘流量 → 排空 → 退出"，**做错就每次发版掉一点请求**（策略层面见 [[母题-E6-灰度发布与回滚]]）
- 「为什么长连接（SSE）服务退出更麻烦？」——**长连接意味着"在途"是长期存在的**：**必须主动向客户端发结束事件并让客户端重连**，而不是等它自己断（[[母题-N2-SSE与推送模型]]）
- 「配置中心挂了服务就起不来怎么办？」——**配置中心也是一个启动依赖**：要有本地兜底（默认值 / 上次成功的快照），**否则它就成了新的单点**
- 「为什么"发版前预热"有用？」——启动期的第一批请求要付**缺页、连接建立、缓存预热、JIT** 的成本（[[母题-O2-虚拟内存与缺页]] 的 minor fault），**预热就是把这段时间提前付掉**
