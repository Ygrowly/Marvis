## 0. 模块边界（先写这个，防无限扩张）

**包含**：**盒子**（容器到底隔离了什么、限制了哪些资源、namespace 与 cgroup 在这件事里的分工）、**上线**（从镜像到一个能服务的进程：配置与依赖、健康检查、优雅退出、进程与信号）、**排查**（CPU / 内存 / 磁盘 / 网络四类症状的**定位顺序**与常见误判）。

**明确不包含**：

- **Kubernetes 的对象与语法**（Deployment / Service / Ingress / Operator 的 yaml 写法）——只到"它替你做了什么"，**不教怎么配**
- **CI/CD 流水线搭建**（Jenkins / GitLab CI / ArgoCD 的具体编排）——归 [[母题-E3-回归门禁与发布卡口]]、[[母题-E6-灰度发布与回滚]] 的领域
- **云厂商产品选型**（ECS / RDS / SLB 的规格与计费）——属于现场决策
- **内核参数调优大全**（`sysctl` 逐项、文件系统参数）——按需查，不背
- **操作系统原理**（切换成本、虚拟内存、IO 模型）——归 [[操作系统模块卡|操作系统]] 的 O1–O3

**边界判据**：**本卡只回答"东西跑起来了，我怎么知道它好不好；出问题了从哪开始查"。** 凡是"某个平台的 yaml 怎么写"的，不进本卡；凡是"这个机制为什么是这样"的，归操作系统模块。

**一条必须先立的认知**：**运维与排查的能力不体现在"记得多少命令"，而体现在"先看什么、再看什么"的顺序上。**

```
❌ 把所有命令都敲一遍，看哪个数字大
✅ 先用症状把范围缩到一类资源（CPU / 内存 / 磁盘 / 网络），
   再用"压力"还是"能力"两个词把原因分到两半，最后才去查具体指标
```

**命令可以查，顺序查不出来。**

| # | 主线（它在回答什么问题） | 这条线的关键取舍 | 落几个母题 |
|---|---|---|---|
| 一 | **盒子**：容器到底隔离了什么、限制了哪些资源；为什么"容器里的上限"和"宿主机还剩多少"经常是两回事 | 隔离（互不干扰）vs 共享内核（逃逸与资源争抢）；限得紧（安全）vs 限得松（性能） | 1 |
| 二 | **上线**：从镜像到一个能服务的进程，中间要过哪几关（配置、依赖、健康检查、优雅退出、信号） | 启动快（少依赖）vs 起得稳（等依赖就绪）；退出快（少等）vs 退得干净（处理完在途请求） | 1 |
| 三 | **排查**：CPU / 内存 / 磁盘 / 网络四类症状分别先看什么；哪些数字最容易误判 | 先缩范围（省时间）vs 先抓全量（可能漏）；看利用率 vs 看压力/等待 | 1 |

**三条线的关系**：一是"**它被关在什么盒子里**"，二是"**它怎么被放进去、怎么被拿出来**"，三是"**它进去之后坏了怎么查**"。**顺序也是运维的日常顺序：先理解边界，再理解生命周期，最后才是排障。**

**这三条线共享同一个前提**：**现代服务都是"被管起来的"** ——它不是你在终端里 `python app.py` 的那个进程，而是**被容器、被编排系统、被信号和探针管理着的进程**。**不知道这层管理，很多现象就无法解释**（为什么进程"莫名"被杀了、为什么 `SIGTERM` 没处理完就没了、为什么 CPU 不高但延迟抖动）。

### 5.1 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**"受控并发 + 低优先级回补"是这个模块最直接的证据**——服务重启后**扫描最近七天缺口并低优先级回补**（`02-aggregation-and-recovery.md`），这既是**启动期的依赖就绪问题**（X2：服务起来时任务表里可能有积压），也是**排查问题**（X3：怎么知道重启后有没有漏算）。
- 解决什么问题：**重启不等于状态清零**——**能恢复的只有落到数据库里的部分**（这正是 [[母题-O1-上下文切换与死锁]] 的进程模型在运维层的对应）。
- 踩过的坑：**Checkpoint 被当成"业务完成证明"**——它是恢复线索，所以**重启后的自检（扫描缺口）必须存在**，不能假设"没报错就是都跑过了"。
- 决策与取舍：**当前规模不上 MQ、不上复杂编排**——`EnergyOps-快速学习掌握与面试实战.md` 里明确"达到升级条件才引入"。**这与本模块第 0 节的"边界判断"同源：能不能不上，先算账。**

- 对应母题：【X2、X3】

### 5.2 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**"资源上限"在应用层的落地**——超时、扫描量、行数、并发、内存配额、取消能力（`07-权限安全与生产隔离.md`、`08-查询性能与成本控制.md`）。**这些正是容器/进程级限制在业务层的对应物**：**限制不是"不信任用户"，而是"防止一个请求把整个服务拖下水"。**
- 解决什么问题：**只读副本 / 分析库 / 对象存储这一串依赖同时可用**才能完成一次问数——**这是 X2 的"启动依赖与降级路径"问题**：某一环不可用时，应该 fail closed（权限不确定就不放行）还是降级。
- 踩过的坑：**权限不确定时必须 fail closed**（`07` 明确）；**超时、取消要能真正中断**（依赖底层 IO 机制，见 [[母题-O3-IO模型与零拷贝]]）。
- 决策与取舍：**限额与配额优先于"加机器"**——因为**"加机器"不解决"单个请求无上界"**（[[母题-O2-虚拟内存与缺页]] 的同一结论）。

### 5.3 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**"进程随时可能崩"被当成设计前提**——PostgreSQL 存权威状态，Redis/ARQ 负责队列、限流与短期进度（`06-architecture-and-scenarios.md`、`04-idempotency-and-recovery.md` §9）。**这就是 X1 与 X2 合起来要说的事：容器里的进程是"会被随时拿走"的**，所以**生命周期必须由外部状态来重建**。

## 8. 题级答案（「本主线的题」翻转卡背面 · 先说后翻）

> 题号与第 4 节题单一一对应。**必背**题写成能直接说出口的一段话；**理解 / 了解**题写 1–3 句。
> 翻转卡背面先给这道题的答案，再挂上「所属母题的完整回答（口述稿）」与单卡入口——两段合起来才是深挖。

### 1 （必背）
**内核是不是共享的**。VM 有独立来宾内核（硬件虚拟化隔离，强但重、启动慢）；**容器共享宿主机内核**，用 **namespace 管"能看到什么"**（PID / NET / MNT / UTS / IPC / USER 等，把视野收窄）+ **cgroup 管"能用多少"**（memory / cpu / pids / io，给资源设上界），两者合起来让一个普通进程"看起来像小机器"。

启动快是因为**不用起内核**；隔离弱于虚拟机也是因为**共享内核**。

### 2 （理解）
**PID**：进程号（容器里 PID 1 是自己的）；**NET**：网络栈（网卡、端口、路由表）；**MNT**：挂载点；**UTS**：主机名；**IPC**：进程间通信；**USER**：用户与组映射。较新的还有 cgroup、time 等。

关键推论：**内存没有 namespace**——所以容器里 `free` 看到的是宿主机的内存。

### 3 （理解）
**限制**：memory、cpu、pids、io、cpuset 等，给资源设上界并按层级分配。

**v1 vs v2**：v1 按资源分成多个独立层级（memory、cpu 各一套树），同一进程可属于不同层级，**协同困难**；**v2 是单一统一层级**，所有控制器挂在同一棵树上，并改进了内存语义（`memory.events`、`memory.low` 这些更细的信号）与 PSI 支持。

### 4 （必背）
**日志前缀就能分辨**：`Memory cgroup out of memory:` 是 **cgroup OOM**（撞到 `memory.max`，此时**宿主机可能还很空**）；`Out of memory:` 才是整机 OOM。

原因：**内存没有 namespace**，容器的额度只写在 cgroup 文件里。所以容器被 OOM kill 时，宿主机 `free` 可能很富余——这也是"容器里 `free` 看到的是宿主机内存"的直接后果。

### 5 （必背）
被 **cgroup 的 `memory.max`** 限制（不是宿主机剩余内存）。超了会发生 **cgroup OOM**：容器内进程被 OOM killer 选中杀掉，日志前缀 `Memory cgroup out of memory`，`memory.events` 里的 `max` / `oom` 计数增加。

怎么看"还有多少额度"：**不要看 `free`**（那是宿主机），看 **`memory.current` / `memory.max`** 的比值、`memory.events`，以及 **`/proc/pressure/memory`**（PSI）。

### 6 （理解）
因为 **namespace 没有内存这一维**——`free` 读的是 `/proc/meminfo`，而 `/proc` 只挂载了 pid / mnt 等 namespace，内存信息是全局的。所以容器里看到的是整机内存总量，与自己的 cgroup 额度无关。

正确做法是读 cgroup 自己的文件（`memory.max` / `memory.current` / `memory.events`），这是第 4、5 题能分辨两类 OOM 的前提。

### 7 （必背）
**构建 → 镜像 → 部署（滚动 / 蓝绿）→ 探针就绪 → 接流量 → 观察 → 扩量或回滚**。

但真正的成败在**退出**：发版时错误率抬升最常见的根因是"**没先摘流量**"。顺序要点：先摘流量 → 等在途请求处理完 → 关依赖（连接池、事务、缓冲）→ 主动退出；并且要有回滚路径（**影响面积 ≈ 事故率 × 灰度流量 × 回滚耗时**）。

### 8 （必背）
两种：**存活探针**（liveness，失败**重启**）与**就绪探针**（readiness，失败**只是不接流量**）。

设计错的后果：**把依赖故障放进存活探针会造成"重启风暴"**——下游挂了，所有实例一起重启，重启后依然挂。判据是"**重启这件事能不能改善现状**"：能（死锁、卡死）就放存活；不能（依赖挂、下游慢）只能放就绪。

### 9 （必背）
`SIGTERM` **可被捕获**（收到后做清理再自己退出）；`SIGKILL` **不可捕获、不可忽略**，内核直接终止。平台是"**先发 15、等宽限期、再发 9**"。

优雅退出四步：**① 先摘流量**（从 LB / 注册中心摘掉，或让就绪探针失败）→ ② 等在途请求处理完 → ③ 关依赖（连接池、事务、缓冲）→ ④ 主动退出。**① 最容易漏**——漏了就永远等不到"没有在途请求"，最后被 SIGKILL 打断。

### 10 （必背）
`摘流量生效 + 最长在途请求 + 清理 ≤ 平台的宽限期`（SIGTERM 之后平台会等一段，超时就 SIGKILL，**不可协商**）。

设错的后果：短了 → 请求被硬打断（用户看到 5xx / 连接重置）；长了 → 一直等到被 SIGKILL，等于没做清理。所以**长任务必须设计成"可中断 + 可恢复"**：写 checkpoint 后主动退出，而不是撑着跑完。

### 11 （理解）
**有上限的退避重试 + 就绪探针**（表现为"暂时不接流量"），**不要"连不上就退出"**——那会造成重启风暴（依赖还没起来，所有实例一起重启）。

顺序上，依赖应该由编排层保证（initContainer / depends_on / 健康检查），应用侧只做"连不上就重试 + 报未就绪"。

### 12 （理解）
三种：**环境变量**（最简单，但改了要重启、无版本、不适合大段配置）；**配置文件 / 挂载**（适合大段配置，改了要重载）；**配置中心**（支持动态下发、版本与灰度，但要引入一个依赖组件，并考虑它挂了怎么办）。

硬规则：**密钥永远不要进环境变量**（会进进程环境、容易被打进日志），用 secret 挂载或密钥管理服务。

### 13 （必背）
先用**两个是非题**把范围缩掉八成：**① 全部接口慢还是个别慢？② 所有实例慢还是个别实例慢？**；再用**两个二分**定方向：**是"压力"（活太多 → 限流扩容有效）还是"能力"（每件活变慢 → 要优化）**、**是"在等"还是"在算"**（看 CPU 占用 ÷ 总耗时，低就是等）。

然后按四类症状分头看（CPU / 内存 / 磁盘 / 网络）；**接口慢但本机指标全正常 → 指向外部依赖**，按调用链分段比耗时。能力体现在**顺序**上，不在记得多少命令。

### 14 （必背）
三类：**① 被容器 CPU 限流**（看 `cpu.stat` 的 `nr_throttled` / `throttled_usec`——配额是"每周期的时间预算"，用完就不给，利用率当然不高）；**② 在等 IO**（看 `wa` 与 IO PSI）；**③ 在等锁 / 连接池 / 下游**。

**先分类，再看数。**

### 15 （理解）
**大量任务处于不可中断等待**（通常是磁盘 IO）。这是"**在等**"的签名——下一步看 IO 压力（`%util` / `await` / IO PSI），而不是加 CPU。

### 16 （必背）
看 **CPU 占用 ÷ 总耗时**：占比低就是"**在等**"（IO / 锁 / 下游）；占比高就是"**在算**"。再交叉 `load` 与磁盘指标（`%util`、`await`）定位是哪种"等"。

对磁盘还要先分清"**空间**"还是"**性能**"：空间用 `df` / `du`，性能看 `%util` 与 `await`。

### 17 （必背）
**不要看 `used`**——Linux 会用空闲内存做页缓存，`used` 高不代表紧张。看三样：**`available`**（真正可分配的）、容器自己的 **cgroup 额度**（`memory.current` / `memory.max`，而不是宿主机的 `free`）、以及 **`memory.events`** 有没有触发 `max` / `high`。

泄漏的判断看趋势：**available 单调下降 + 回收不掉 + OOM 计数增长**，再结合 PSI 的 memory 压力。

### 18 （理解）
两条命令思路：`df -h` 先确认是哪个挂载点，再用 `du -x -d1 <挂载点>` 逐层找最大的目录。

经典坑：**`df` 显示满但 `du` 加起来不够**——那是"**已删除但仍被进程占用**"的文件（句柄没关，空间没释放），用 `lsof +L1` 找，关闭句柄或重启对应进程才释放。

### 19 （理解）
**TIME_WAIT 多**：它出现在**主动关闭方**，是正常的（2MSL），本身不是故障。量太大时可以开端口复用（`tcp_tw_reuse`），更根本的是**用长连接 / 连接池**减少主动关闭次数。

**连接数打满**：先看是"真的量涨了"还是"连接没释放"（泄漏），再看是不是**上游变慢导致占用时间变长**（`L = λW`）。处理顺序：先查根因，再谈调大上限。

### 20 （理解）
**先聚合后单机**：聚合指标（错误率、P95、QPS）回答"**是不是真出问题、影响面多大**"；单机指标回答"**坏在哪台、坏在哪个资源**"。

反过来先钻单机，容易把个别实例的抖动当成全局故障（或反过来漏掉单实例问题）。顺序是：聚合确认现象 → 按实例维度对比找出异常的那批 → 再进单机看资源。

### 21 （理解）
PSI（Pressure Stall Information）直接报告"**任务因为资源不足被卡住的时间占比**"（`/proc/pressure/{cpu,memory,io}` 的 `some` / `full`）。

比 load 好在哪：load 是"等待队列长度的移动平均"，**看不出被卡的是谁、卡了多久，也分不清是 CPU 还是 IO**；PSI 直接给"**有多少比例的时间在等**"，且 CPU / 内存 / IO 分开报。容器里尤其有用——**被 CPU 限流导致的卡顿，load 上看不出来，PSI 和 `cpu.stat` 能看出来**。

### 22 （必背）
**延迟抖动 / P99 抬高，但 CPU 利用率看起来不高**——因为配额是"**每周期的时间预算**"（`cpu.max`），用完就被暂停到下一个周期，利用率统计上不去，但请求真的被卡住了。

怎么看：`cpu.stat` 里的 **`nr_throttled`**（被限流次数）与 **`throttled_usec`**（被限流总时长），以及 PSI 的 cpu `full`。处理：调大 `cpu.max`，或先查为什么消耗这么多 CPU。
