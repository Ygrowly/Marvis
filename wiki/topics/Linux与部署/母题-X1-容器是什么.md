## 一、教材

### 1. 前提：容器是一个被"重新布置过视角"的普通进程

#### 1.1 不是虚拟机【事实】

::figure container-boundary.svg | namespace 管视图，cgroup 管额度 | 内存没有 namespace，所以 free 看到宿主机；超 cgroup 上限的后果与宿主机剩余资源无关

【事实】**两者的根本差别只有一个：内核是不是共享的。**

| | 虚拟机 | 容器 |
|---|---|---|
| 内核 | **每个 VM 一个完整的来宾内核** | **共享宿主机的同一个内核** |
| 隔离靠什么 | **硬件虚拟化**（CPU 的特权级 + 虚拟设备） | **内核特性**（namespace + cgroup） |
| 启动成本 | 秒级到分钟级（要启动一个内核） | **毫秒级（本质就是启动一个进程）** |
| 隔离强度 | **强**（内核都不同） | **较弱**（内核漏洞可能被用来逃逸） |

【推导】**"容器就是一个进程"这句话要讲准确**：

```
它确实只是一个普通进程（有 PID、有地址空间、被调度）
但它被"重新布置过视角"：
  ① namespace 让它的【视野】变小——看不到宿主机的其他进程、自己的网络栈
  ② cgroup   给它的【额度】设上界——最多用多少 CPU、内存、任务数
→ 这两件事合起来，才让一个普通进程"看起来像一台小机器"
```

#### 1.2 一句话分工【推导】

【推导】**把这两者的分工记成一句话，本卡后面全部由它推出**：

> **namespace 管"能看到什么"（视图），cgroup 管"能用多少"（额度）。**

| | namespace | cgroup |
|---|---|---|
| 它回答 | 我能看到哪些进程 / 哪个网络栈 / 哪份文件系统 | 我能用多少 CPU / 多少内存 / 多少任务 |
| 本质 | **隔离视图** | **限制资源** |
| 名字 | PID / NET / MNT / UTS / IPC / USER / CGROUP / TIME | memory / cpu / pids / io / blkio |
| 越界会怎样 | 看不到（隔离住了） | **被拒 / 被限流 / 被杀** |

**到这里你应该能回答**：为什么"容器"这个词其实概括了两件不相干的事（隔离 + 限额）？

### 2. 关键推论：内存没有 namespace

#### 2.1 为什么 `free` 看到的是宿主机【推导】

【推导】**namespace 有 PID / NET / MNT / UTS / IPC / USER / CGROUP 等好几类，但没有"内存 namespace"**——因为**内存本身是被所有进程共享的资源池**，隔离它的方式是"设上限"（cgroup），而不是"换个视图"。

【推导】**由此推出三个很实用的判断**：

```
① 容器里 free / top 显示的内存是【宿主机】的
   → 不要用它判断"我这个容器还剩多少额度"
② 同理，容器里看不到别的容器在抢 CPU
   → "宿主机很空"和"我这个容器够用"是两件事（那张 container-boundary 图就是算这个）
③ 要知道真实额度，只能看 cgroup 的文件：
     /sys/fs/cgroup/<path>/memory.max      上限
     /sys/fs/cgroup/<path>/memory.current  当前
     /sys/fs/cgroup/<path>/memory.events   有没有触发过 OOM
```

#### 2.2 两类 OOM 的分辨（复习 + 落点）【事实】

【事实】这一点在 [[母题-O2-虚拟内存与缺页]] 4.3 已完整推导，这里只给**排查用的落点**：

| | 整机 OOM | **cgroup OOM** |
|---|---|---|
| 日志前缀 | `Out of memory:` | **`Memory cgroup out of memory:`** |
| 触发条件 | 整机内存 + swap 耗尽 | **撞到自己的 `memory.max`** |
| 与宿主机剩余内存 | 直接相关 | **完全无关** |

【推导】**这就是本卡开头第一个问题的答案**：**`free` 显示 8 GB 可用，和"这个 512 MB 的容器被 OOM 杀"完全不矛盾**——**前者是宿主机的视图，后者是 cgroup 的额度**。**"内存没有 namespace"这一条，同时解释了这两个现象。**

【事实】**RuleArena 就是这种配置**：`08-capacity-cost-and-facts.md` 里 Redis 容器只给 **256~512MB**——**这个数字就是 `memory.max`**。它超了就是 cgroup OOM，**跟宿主机有多少内存无关**。

#### 2.3 `memory.high` 与 `memory.max` 的分工【事实】

【事实】

```
memory.max   = 硬上限：超过 → 触发 cgroup OOM
memory.high  = 软上限：超过 → 【只做限流与积极回收】，不杀
```

【取舍】**把 `memory.high` 设在 `memory.max` 下方（比如留 10–20% 的余量）**，可以让内核算**先回收**而不是直接杀——**这是"给进程一个喘息空间"的常规做法**（同 [[母题-O2-虚拟内存与缺页]] 4.4）。

**到这里你应该能回答**：为什么容器里"看内存"要去看 cgroup 的文件，而不是 `free`？

### 3. CPU 的限制方式与"限流"这个隐形杀手

#### 3.1 配额-周期模型【事实】

【事实】cgroup v2 的 CPU 限制是**"每个周期内允许多少 CPU 时间"**：

```
cpu.max = "<配额> <周期>"        单位微秒
  例："50000 100000" = 每 100 ms 最多用 50 ms CPU = 【0.5 核】
  例："200000 100000" = 每 100 ms 最多用 200 ms CPU = 【2 核】
```

【推导】**注意"0.5 核"这个说法**：**它不是一个"半个核心"的物理约束，而是"每个 100 ms 周期内只能用 50 ms 的 CPU 时间"**。这个区别很重要，因为它带来一个反直觉的现象：

```
只要【一个周期内】用完配额，剩下的时间即使核是空的，这个容器也用不了
→ 表现为：【CPU 看着不高，但延迟抖动】
```

#### 3.2 量化：为什么"利用率 40%"可能是骗人的【推导】

【推导】**把本卡开头的第二个问题算出来**：

```
容器配额：cpu.max = "50000 100000" → 0.5 核
单个请求的 CPU 时间：60 ms
请求到达速率：20 个/秒

需要：20 × 60 ms = 1200 ms CPU / 1000 ms 时间 = 【1.2 核】
实际有：0.5 核
→ 超出 140% → 大量请求【在周期内用完配额后被限流】
```

【推导】**被限流的表现极具迷惑性**：

| 现象 | 为什么会这样 |
|---|---|
| **CPU 利用率看起来不高** | 因为**被限流的时间是不计入"使用"的**——不是用不了，是**不许用** |
| **延迟抖动、P99 明显抬升** | 一批请求在周期末尾被迫等到下个周期 |
| **换个空闲的宿主机就好了** | 宿主机空闲不改变配额——但如果配额是"按宿主机核数比例"给的，就会变 |
| **压测时问题不明显** | 压测往往只看吞吐，而限流会先把**尾部延迟**搞坏 |

【事实】**决定性证据在 `cpu.stat`**：

```
nr_throttled   —— 被限流的次数
throttled_usec —— 累计被限流的时间
→ 这两个数【在涨】= 就是被限流了，不用再猜
```

【取舍】**这正是"资源限制不是越小越好"的落点**：**限得太紧会让服务在"看起来没负载"的时候出问题**——而这类问题**只能靠"看 throttled 这个数"发现**，因为它不出现在 CPU 利用率曲线里。

**到这里你应该能回答**：为什么"CPU 利用率"这个指标在容器里会误导人？

### 4. 边界与常见误解

| 常见说法 | 修正 |
|---|---|
| "容器是轻量级虚拟机" | 【事实】**错**。**容器共享宿主机的内核**，它只是"被重新布置过视角的进程"：namespace 改视野、cgroup 设额度。**没有内核隔离，所以隔离强度弱于虚拟机** |
| "容器里 `free` 显示还有内存，所以不会 OOM" | 【推导】**内存没有 namespace**——`free` 看到的是**宿主机**的视图。**容器的上限在 `memory.max` 里**，超了就是 cgroup OOM，**和宿主机剩多少无关** |
| "CPU 利用率不高，说明还有余量" | 【推导】**在容器里这个判断可能完全错**：配额是"每周期允许用多少 CPU 时间"，**用完之后即使核空闲也用不了**——表现为"CPU 不高但延迟抖动"。**要看 `cpu.stat` 的 `nr_throttled` / `throttled_usec`** |
| "容器里 `top` 的 CPU 就是我的使用量" | 【事实】`top` 在容器里的视角是**被 namespace 与挂载视图影响过的**；**判断自己的真实用量与额度，应该以 cgroup 的文件为准**（`cpu.stat`、`memory.current`、`memory.max`） |
| "容器的资源限制是运维的事，业务不用管" | 【取舍】**业务必须知道自己的上限**：一次查询的扫描量上限、一个任务的内存上限、并发上限——**"单个请求没有上界"是这类事故的共同根因**（数驭穹图的超时/行数/扫描量限制就是这条原则） |
| "限制越严越安全" | 【取舍】**限得太紧会换来"延迟抖动"这种难查的问题**（3.2）。**正确的做法是"设立上界 + 可观测"**：既有 `memory.max` / `cpu.max`，也监控 `throttled` 与 `memory.events` |
| "`memory.high` 和 `memory.max` 是一回事" | 【事实】**不是**：`max` 是硬上限（超了 OOM），**`high` 是软上限（超了只限流与回收）**。**把 `high` 设在 `max` 下方留出余量，才是温和的做法** |
| "容器被 OOM 杀了就是宿主机内存不够" | 【事实】**先看日志前缀**：`Memory cgroup out of memory:` 是 **cgroup OOM**（撞 `memory.max`，宿主机可能很空）；`Out of memory:` 才是整机 OOM |

## 二、自测

**Q1（计算）**：容器配额 `cpu.max = "50000 100000"`（0.5 核）。单请求 CPU 时间 **50 ms**，请求速率 **8 个/秒**；到达**均匀分布**。

问：① 需要多少核？② 会不会被限流？③ 如果把请求速率提到 12 个/秒呢？④ 怎么看"有没有被限流"？

**A1**：

```
① 需要 = 8 × 50 ms = 400 ms CPU / 1000 ms = 【0.4 核】
   < 配额 0.5 核 → 有余量

② 平均不会限流（0.4 < 0.5）
   ⚠️ 但要注意：这是【平均值】。如果 8 个请求【挤在同一个 100 ms 周期里】到达：
      8 × 50 ms = 400 ms > 周期配额 50 ms
      → 那个周期内必然被限流
   → 结论：【平均值够用 ≠ 不会抖】——这正是"限流引发抖动"的机制

③ 12 个/秒：
   需要 = 12 × 50 ms = 600 ms = 【0.6 核】> 0.5 核
   → 超出 20%，【持续限流】
   → 表现：吞吐被压到约 10 个/秒（0.5 核 ÷ 50 ms），多余的请求排队
   → P99 抬升，但 CPU 利用率仍然"看着不高"
```

④ **看 `cpu.stat`**：

```
nr_throttled    被限流的次数（在涨就是被限流了）
throttled_usec  累计被限流的时间
```

【这一步在验证什么】验证 3.1 与 3.2：**配额是"周期内的时间预算"，所以"平均够用"和"不抖动"是两件事。**

**这里有一个可加分的推论**：**这也解释了"为什么容器化之后延迟抖动变多"**——裸机上多个进程争抢时是**加权分时**（谁忙谁多拿），而**容器配额是硬边界**：**到点就不给了**。所以**同样的平均利用率，容器里的尾部延迟会更差**。

**Q2（计算）**：某 Java 服务放进容器，`memory.max = 512 MB`。宿主机 **16 GB**。JVM 是老版本（**不感知容器**），默认按"宿主机物理内存的 1/4"设置最大堆。

问：① 它会设多大的堆？② 会发生什么？③ 正确做法是什么？

**A2**：

```
① 老版本 JVM 按宿主机 16 GB 算：最大堆 ≈ 16 GB / 4 = 【4 GB】

② 容器上限是 512 MB，堆要 4 GB：
   → 堆还没长到 1/4 就撞上 memory.max
   → 【cgroup OOM，容器被杀】
   → 现象极难查：日志里看不到 OutOfMemoryError（因为 JVM 还没到自己的堆上限，
     是【内核】动的手），只有 cgroup 的 memory.events 与 `Memory cgroup out of memory`
   → 而且表现为【周期性重启】：起来就跑满、被杀了又起来
```

③ **正确做法（三层）**：

| 层 | 做法 |
|---|---|
| **① 让运行时感知容器** | 新版本 JVM（8u191+ / 11+）默认开启容器感知；用 `-XX:MaxRAMPercentage=70` 之类的**百分比**而不是固定 `-Xmx`；**Go 语言 1.19+ 也默认读 cgroup 限制** |
| **② 给总量留出余量** | 堆只是 JVM 内存的一部分——**还有元空间、线程栈、直接内存、JIT 代码缓存**。所以堆不能吃掉全部 512 MB |
| **③ 把 `memory.high` 设上** | 让它先被"限流 + 回收"而不是直接被杀，留出观察窗口 |

**【这条题的通用形态】**：**"进程以为自己有多少内存"和"它实际能有多少"不一致**——而**坑往往就出在"运行时按宿主机规格自适应"上**。

【这一步在验证什么】验证 2.1 与 2.2：**容器的额度只写在 cgroup 里，任何"按宿主机总量自适应"的机制都会踩坑。**

**Q3（判读）**：某服务在容器里运行。运维给出三条信息：

- `free -h` 显示宿主机 `available` 6 GB
- 容器的 `memory.max` 是 1 GB，`memory.current` 是 950 MB
- 容器**没有被 OOM 杀过**，但日志里偶发"连接超时"

问：① 内存还有余量吗？② 更该警惕的是什么？③ 该做什么动作？

**A3**：

```
① "还有余量"这个判断必须【只按 cgroup 看】：
   memory.current 950 MB / memory.max 1024 MB = 【93%】
   → 余量只有 7%（约 74 MB）——【已经很紧】
   ★ free 的 6 GB 和这个容器【毫无关系】（内存没有 namespace）

② 更该警惕的是「逼近上限的副作用」：

   · 如果配了 memory.high → 现在就会【开始积极回收】，表现为延迟变差
   · 如果没配 high → 下一次内存增长（一个新连接、一批数据、一次 GC 峰值）
     就会直接触发 cgroup OOM → 【容器被杀】
   · "偶发连接超时"本身可能是信号：回收 / 换页 / 分配变慢
```

③ **动作（按顺序）**：

| 顺序 | 动作 |
|---|---|
| **1** | **确认是不是真的内存问题**：看 PSI（`/proc/pressure/memory`）与 `memory.events`（有没有触发过 `max` / `high`） |
| **2** | **找增长的来源**：是泄漏、是无上界的队列/缓存、还是"本来就需要这么多"（把上界调大，但要算账） |
| **3** | **给上界 + 给观测**：`memory.high` 留余量、把 `memory.current` 与 `memory.events` 纳入监控 |
| **4** | **别用"宿主机还空"作为理由** | 这句是这类误判的根源 |

【这一步在验证什么】验证 2.1 与贯穿全库的一条原则：**"资源够不够"要按"该资源那层的上界"判断，不是按最外层**——这和应用里的"给每个会增长的东西设上界"（[[母题-O2-虚拟内存与缺页]] 5.5）是同一条。

**Q4（纠错）**：下面这段话哪里错了？

> "容器就是轻量级虚拟机——它把自己那部分内存和 CPU 分出来给应用，所以容器里 `free` 看到的内存就是分给它的那部分，比虚拟机启动快。"

**A4**：**三处都错，而且第三处错在把两件不相干的事当成了一件事。**

1. **"轻量级虚拟机"错了**：**容器与虚拟机最根本的差别是"内核是不是共享的"**。虚拟机有自己的来宾内核（靠硬件虚拟化隔离），**容器共享宿主机的内核**——它的隔离靠 **namespace**（改视野）与 **cgroup**（设额度）。**所以容器的隔离强度弱于虚拟机**（内核漏洞可能被用来逃逸）。

2. **"把自己那部分内存和 CPU 分出来"错了**：**容器并没有"划分"资源，它只是"给这个进程组设了上界"**——内存还是宿主机的内存池，CPU 还是同一批核。**区别在于**：**上界到了就不给用**（`memory.max` → OOM；`cpu.max` → 限流），而不是"它拥有这一份"。

3. **"`free` 看到的就是分给它的那部分"错了**：**内存没有 namespace**，所以 **`free` 看到的是宿主机的内存视图**——它能显示 16 GB 总量、6 GB 可用，而容器的上界可能只有 512 MB。**"容器里看到的内存"和"容器能用多少"在 Linux 上就是两个不同的地方**：

```
free / top           → 宿主机的视图
/sys/fs/cgroup/.../memory.max / current → 这个容器的真实额度
```

4. **"比虚拟机启动快"是对的**，但**原因要改**：不是"轻量"，而是**因为不用启动内核**——它就是启动一个进程（毫秒级）。

**准确说法**：*容器是"被 namespace 收窄了视野、被 cgroup 设了额度的普通进程"，共享宿主机的内核。所以它启动快（不起内核）、隔离弱于虚拟机；而 `free` 看到的是宿主机的内存，容器真正的上限要去 cgroup 里看。*

**Q5（纠错）**：下面这段话哪里错了？

> "服务变慢先看 CPU：我查了监控，CPU 利用率只有 40%，所以肯定不是计算资源的问题，应该是代码有性能问题。"

**A5**：**"CPU 利用率不高 ⇒ 计算资源没问题" 这个推理在容器环境里不成立。**

**【事实】容器里的 CPU 是"每周期的时间预算"，不是"平均利用率"**：

```
cpu.max = "50000 100000"（0.5 核）= 每 100 ms 最多用 50 ms CPU
→ 用完之后，【即使宿主机的核全空着，这个容器也用不了】
→ 所以"利用率 40%"可能只是"它被允许用的那部分的 40%"
   （极端情况下，被限流的进程连"用不了的那部分"都不会计入使用量）
```

**决定性证据不是利用率曲线，而是 `cpu.stat`**：

```
nr_throttled    被限流的次数（在涨 = 被限流了）
throttled_usec  累计被限流的时间
→ 这两个数在涨，就说明"不是代码慢，是被按住了"
```

**除了限流，还有另外三类"CPU 看着不高但确实慢"的原因**（正好是排查的下一个方向）：

| 原因 | 判断依据 |
|---|---|
| **在等 IO** | `vmstat` 的 `wa`（IO 等待）高；PSI 的 IO 压力高；见 X3 |
| **在等锁 / 等连接池** | 线程状态大量处于等待；连接池 `active` 打满 |
| **在等下游** | 调用的下游延迟高（[[母题-N1-一次请求的完整路径]] 的分层归因） |

**准确说法**：*CPU 利用率是"用了多少"，而容器能不能用还受"允许用多少"限制——要看 `cpu.stat` 的 `nr_throttled` / `throttled_usec`。另外"CPU 不高但慢"还有三类常见原因：等 IO、等锁/池、等下游——所以排查顺序是"先分类，再看数"。*

## 三、面试输出（学完再看）

**一句话结论**：**容器不是轻量级虚拟机，它共享宿主机的同一个内核**——**namespace 管"能看到什么"（PID / NET / MNT / UTS / IPC / USER 等，把视野收窄），cgroup 管"能用多少"（memory / cpu / pids / io，给资源设上界）**，两者合起来才让一个普通进程"看起来像小机器"（启动快是因为**不用起内核**，隔离弱于虚拟机也是因为**共享内核**）。**关键推论：内存没有 namespace**——所以**容器里 `free` 看到的是宿主机的内存**，而**真实额度只在 cgroup 的文件里**（`memory.max` / `memory.current` / `memory.events`）；**超 `memory.max` 是 cgroup OOM（日志前缀 `Memory cgroup out of memory`），与宿主机剩多少无关**。CPU 是**"每周期的时间预算"**（`cpu.max = "50000 100000"` = 0.5 核），**用完之后即使核空闲也用不了**——所以**"利用率不高"不代表没被限流**，要看 `cpu.stat` 的 **`nr_throttled` / `throttled_usec`**。而**"进程以为有多少内存"和"实际能有多少"不一致，是容器里最经典的一类坑**（老版本 JVM 按宿主机 1/4 设堆，在 512MB 的容器里会被反复杀）。

**恢复关键词**：共享内核（不是小虚拟机）· 启动快因为不起内核 / **namespace 管视图，cgroup 管额度** / **内存没有 namespace** → `free` 看到的是宿主机 / 真实额度在 `/sys/fs/cgroup/.../memory.max` / **两类 OOM + 日志前缀** / `memory.high`（软）vs `memory.max`（硬）/ **cpu.max = 配额 / 周期**（"50000 100000" = 0.5 核）/ **用完了即使核空也不能用** / **利用率不高 ≠ 没被限流 → 看 nr_throttled / throttled_usec** / pids.max（任务数上限）/ 运行时按宿主机自适应会踩坑（JVM 堆）/ 给上界 + 给观测

**核心不变量 / 主线**：
**容器的一切现象都可以从"共享内核 + 视图收窄 + 额度设上界"这三条推出。** 最常出错的地方是**拿错参照系**——**用宿主机的数字判断容器的余量**（`free`、CPU 利用率），而真实答案永远在**这个容器自己的 cgroup 文件**里。**换参照系，是容器排查的第一动作。**

**完整回答骨架**：先给"共享内核"这个根本差别 → namespace（管视图，列几类）vs cgroup（管额度，列几类）→ **推出"内存没有 namespace"** → 由此解释 `free` 的迷惑与两类 OOM → CPU 的配额-周期模型 → **算出"利用率 40% 却被限流"** → 证据在 `cpu.stat` → JVM 堆那个经典坑 → 边界与误解

**完整回答（口述稿）**：
**容器不是轻量级虚拟机，它共享宿主机的同一个内核**——**namespace 管"能看到什么"**（PID / NET / MNT / UTS / IPC / USER 等，把视野收窄），**cgroup 管"能用多少"**（memory / cpu / pids / io，给资源设上界），两者合起来才让一个普通进程"看起来像小机器"。**启动快是因为不用起内核，隔离弱于虚拟机也是因为共享内核**。

关键推论：**内存没有 namespace**——所以**容器里 `free` 看到的是宿主机的内存**，真实额度只在 cgroup 的文件里（`memory.max` / `memory.current` / `memory.events`）。**超 `memory.max` 是 cgroup OOM**（日志前缀 `Memory cgroup out of memory`），与宿主机剩多少无关；`Out of memory:` 才是整机 OOM。

CPU 是"**每周期的时间预算**"（`cpu.max`），用完就被暂停到下一周期——表现是**延迟抖动/P99 抬高，但 CPU 利用率看起来不高**，要看 `cpu.stat` 的 `nr_throttled` / `throttled_usec`。

cgroup **v1 按资源分多套层级**（同一进程可属不同层级，协同困难）；**v2 是单一统一层级**，且内存语义更细（`memory.events` / `memory.low`）并支持 PSI。

**分层要点**：
- **结论**：内核共享；namespace 管可见、cgroup 管额度；内存没有 namespace 是两类 OOM 的根因。
- **推导链**：共享内核 → 两种隔离机制 → 内存例外 → 容器额度只在 cgroup 文件 → CPU 是时间预算 → v1/v2 差异。
- **量化**：cgroup OOM 与整机 OOM 的日志前缀不同（`Memory cgroup out of memory` vs `Out of memory`）。
- **边界与常见误解**：容器里 `free` 不是自己的额度；CPU 利用率不高也可能是被限流；PSI 比 load 更能说清"卡在哪"。

**追问**（先说后看）

1. **容器和虚拟机的本质区别是什么？** —— **内核是不是共享的**。VM 有独立来宾内核（硬件虚拟化隔离，强但重）；**容器共享宿主机内核**（namespace + cgroup，轻但隔离弱）。
2. **为什么容器里的 OOM 和宿主机的 OOM 是两回事？** —— **日志前缀就能分辨**：`Memory cgroup out of memory:` 是 cgroup OOM（撞 `memory.max`，**宿主机可能很空**）；`Out of memory:` 才是整机 OOM。**因为内存没有 namespace，容器的上限只写在 cgroup 里。**
3. **CPU 利用率不高但延迟抖动，可能是什么？** —— 三类：**① 被 CPU 限流**（看 `nr_throttled` / `throttled_usec`）；**② 在等 IO**（看 `wa` 与 IO PSI）；**③ 在等锁 / 连接池 / 下游**。**先分类，再看数**——这正是 X3 的排查顺序。
4. **容器里怎么知道"我还有多少内存额度"？** —— **不要看 `free`**（那是宿主机）。看 **`memory.current` / `memory.max`**（比值），以及 **`memory.events`**（有没有触发 `max` / `high`），再加 **`/proc/pressure/memory`** 看压力。
5. **`pids.max` 有什么用？** —— **限制这个 cgroup 里的任务数**。它比"内存不够"更早撞上（[[母题-O1-上下文切换与死锁]] 3.3 的 `pid_max` 是同一族限制），**报错是"创建任务失败"而不是 OOM**——**搞错这一对，排查方向就全歪了**。

**同类变体**

- 「Kubernetes 的 `resources.limits` 和 `requests` 分别是什么？」——`limits` 落到 **cgroup 的 `max`**（硬上界）；`requests` 影响**调度**（"给我预留这么多"）。**限制是内核执行的，调度是平台决策的**——两者不要混
- 「为什么容器化之后延迟抖动变多了？」——因为**配额是硬边界**：裸机上多个进程争抢是**加权分时**（谁忙谁多拿），容器是**到点就不给**。**同样的平均利用率，容器里的尾部延迟更差**
- 「`memory.high` 有什么用？」——**软上限**：超了做限流与回收，**不杀**。**给观察窗口**——让问题以"变慢"出现，而不是以"被杀"出现
- 「sidecar / 服务网格算什么？」——**仍是同一套机制**（同 Pod 共享 NET namespace 所以能劫持流量）。**知道了 namespace 的粒度，这类架构就自己解释出来了**
