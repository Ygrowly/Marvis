01主干：别丢 → 别重复别乱序 → 扛不住怎么办正本 wiki/topics/消息队列/

三个大框就是排查顺序——线上出问题先问丢了没、再问重复没、最后问扛不住了吗；底部横幅是全模块的前提与「什么时候不该上 MQ」。
主干叙事（一段读完）：消息队列的一条线就是排查顺序：「别丢 → 别重复别乱序 → 扛不住怎么办」，共享前提是跨进程通信没有恰好一次 —— MQ 的全部设计都是「至少一次 + 幂等」去逼近它。 别丢：消息的一生是三段接力（发送 acks → 存储持久化多副本 → 消费先处理后 ack），acks = all 是「所有 ISR 内副本」不是全部副本，必须配 min.insync.replicas；MQ 写入报错是在保护数据，不是坏了；本地事务和发消息不可能原子，用 Outbox 兜。 别重复别乱序：重复 / 乱序 / 丢失同一根源（确认本身可能丢），框架只保证至少一次、宁重勿丢 —— 去重是业务层的事：稳定业务幂等键 + Redis 查重 + 唯一约束兜底；顺序 = 局部串行，保序的粒度就是并行的粒度（100 分区拿 100 倍吞吐，单订单上限仍是单分区）。 扛不住：积压先查根因再扩容；消费者天花板 = 分区数（多开白加），加分区要迁移且可能改 Key 哈希；高可用三层递进（多副本 → 自动选主 → 路由感知），ISR 缩水后选主是可用性 vs 一致性的正面对决。 EnergyOps 反着讲一遍：604 台设备不上 MQ —— 三笔代价（可用性 / 复杂度 / 一致性）立刻要付，收益门槛还远，升级条件写明。
读法：三个大框就是排查顺序；橙字是判据与算式（要能现场算），紫字是毒教材高发区（acks=ISR / 重复无法框架层杜绝 / 消费者超分区白加）；绿字是三个项目的落点。底部一行是全模块的前提。

      05要能现场算出来的数正本 母题卡「一、教材」推导

      每个数都要带推导，只报结果是会被追问倒的。
      acks=all 的真义
      ISR ≠ 全部副本
      ISR 剩 1 个照样 ack 成功——必须配 min.insync.replicas 才有「已确认不丢」的保证。
      min ISR 拒写
      2 台坏 → 报错
      ISR=1 < min.insync.replicas=2 → 生产者被拒绝：在保护数据，不是 MQ 坏了。
      重复窗口
      5s ≈ 100 条
      auto.commit 间隔 5s × 100 条 × 50ms：提交前崩溃 = 这 100 条重新投递（至少一次）。
      幂等键必错式
      消息 ID
      重投时 ID 变了、查重永不命中——稳定业务键 = 业务 + 动作 + 目标 + 参数 + 版本。
      保序天花板
      200 TPS / 单订单
      100 分区拿 100 倍总吞吐，单个订单仍是单分区 200 TPS——保序粒度 = 并行粒度。
      积压消净
      ≈ 56 分钟
      10 分区 × 500 − 2000 = 净 3000 条/s；1000 万条 ÷ 3000 ≈ 56 分钟——积压是能算出来的问题。
      消费者白加
      20 消费者 / 10 分区
      多出的 10 个全闲置：同一分区同一时刻只被一个消费者消费——天花板是分区数。
      三笔代价
      可用性·复杂度·一致性
      604 台设备不上 MQ（EnergyOps）：收益门槛还远、代价立刻要付——升级条件写明。
      Kafka 快四件套
      顺序写·批量·压缩·零拷贝
      每件都在省「磁盘随机写」与「用户态搬运」——与操作系统模块的零拷贝同一笔账。

      06八句最容易说错的话正本 母题卡「二、自测」纠错题原话

      说对前半句没用，后半句才是判据。
      ✗「acks=all 是所有副本确认」✓ 是所有在 ISR 里的副本；ISR 剩 1 个照样成功——必须配 min.insync.replicas。
      ✗「Kafka 默认 acks=1，要手动改成 all」✓ 3.0 起默认已是 all（幂等生产者默认开启）——过期答案，很多资料还在讲。
      ✗「配了 min.insync.replicas 就安全了」✓ 它只在 acks=all 时生效；配 acks=1 的话它一点作用都没有。
      ✗「消息重复消费是 bug，换个 MQ 就好」✓ 框架只保证至少一次：「处理」与「记录进度」无法原子化——去重必须落在业务键上。
      ✗「用消息 ID 做幂等键」✓ 重投时 ID 变了、查重永不命中；要稳定业务键（业务 + 动作 + 目标 + 参数 + 版本）。
      ✗「消费者多开几个就能更快消费」✓ 同一分区同一时刻只被一个消费者消费——天花板 = 分区数；顺序是先查根因、再加分区、再加消费者。
      ✗「加分区没代价」✓ 要数据迁移，且可能改变 Key 哈希分布、影响顺序语义——分区数应在设计期估算。
      ✗「MQ 挂了业务就得停服」✓ 写路径先问「为什么强依赖 MQ」：本地消息表 / Outbox 让业务先落库、投递后补——队列可以丢或重投。
