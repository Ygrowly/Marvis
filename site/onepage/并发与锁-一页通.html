01主干：要不要加锁 → 锁画多大 → 跨机怎么办正本 wiki/topics/并发与锁/

三条主线就是三步决策，顺序即依赖：先判断要不要付这个代价，再决定怎么付得少，最后才考虑把范围扩到多台机器。
主干叙事（一段读完）：这一模块的一条线是三步决策「要不要加锁 → 锁画多大 → 跨机怎么办」，共享同一个前提：并发控制的目标不是不出错，而是给出错定价。 要不要：悲观 = 排队不白干、乐观 = 条件更新可能白干重试 —— 先报冲突频率再谈机制，判据是 1/(1−p)（p 过半就该换悲观）；重试必须显式定参（退避 / 抖动 / 上限），否则重试回竞争池、正反馈成风暴。 画多大：锁有三笔账且随临界区反向变化 —— 外部调用绝不进临界区（50ms HTTP 把 0.5ms 临界区放大 100 倍，单锁吞吐只剩 ≈20 QPS）；分段锁前提是访问能均匀分散；自旋还是睡眠看 2μs 的比值；CAS 无锁快但有 ABA，用版本号兜住。 跨机：Redis / ZK / DB 三种实现各有一个软肋，失效根因只有一个 —— 「锁是否被持有」由锁服务按时间判，「我还在跑」只有客户端知道；TTL 设多少都错（GC 3s vs P99 200ms），看门狗只缓解，fencing token 让资源侧校验单调 token 才是保证；而能幂等就不用锁 —— 幂等只依赖自己的数据库。
读法：三个大框就是决策顺序，从上往下走；橙字是判据与算式（要能现场算），紫字是失效与边界（要能举反例），绿字是三个项目各自的落点。底部一句是全模块的母题：每种方案都在给定错定价。

      05要能现场算出来的数正本 母题卡「一、教材」推导

      每个数都要带推导，只报结果是会被追问倒的。
      冲突 60% 的账
      2.5 次 ≈ 12.5ms
      单次尝试 5ms、冲突率 60% → 期望尝试 E=1/(1−p)=2.5 次、期望耗时 12.5ms——p 过半，悲观锁开始占优。
      高冲突发散
      N² vs N
      乐观锁 N 个并发写同一行总工作量 ≈N²/2，悲观锁 ≈N：10 并发差 10 倍、100 并发差 100 倍——p→1 时发散。
      临界区放大
      100 倍
      0.5ms 的临界区塞进一次 50ms 外部 HTTP → 持锁 50.5ms：外部调用 / IO 一律放锁外。
      单锁吞吐
      ≈ 20 QPS
      1s ÷ 50.5ms ≈ 19.8——锁住的资源每秒只能过 20 个请求，应用层并发再高也白搭。
      自旋判据
      2 μs
      抢不到锁睡下去再唤醒 ≈ 两次上下文切换 ≈2μs；临界区远大于 2μs 就直接睡——先自旋再睡是折中。
      TTL 两难
      15 倍
      GC 最长 3s ÷ 业务 P99 200ms ≈ 15：TTL 盖住 P99 会被 GC 打穿（两个持有者），盖住 GC 就得接受挂了白等。
      看门狗的边界
      缓解 ≠ 解决
      续期把 TTL 顶回去能缓解「活着的持有者」，但客户端整体挂掉 / 长暂停时根因仍在——所以还需要 fencing token。
      Redis 的定位
      256–512MB
      RuleArena 给 Redis 只配 256~512MB：队列与限流走 Redis，权威状态在 PostgreSQL——不把正确性押在锁服务上。
      幂等的收益
      少一个依赖
      锁要引入锁服务的可用性依赖；幂等只依赖自己的数据库——「能幂等就不用锁」是 L3 最后一条追问的答案。

      06八句最容易说错的话正本 母题卡「二、自测」纠错题原话

      说对前半句没用，后半句才是判据。
      ✗「乐观锁就是不加锁」✓ 数据库里同样拿行锁，只是持锁时间从「整个业务」压缩到「一条 UPDATE」；代价变成「可能白干」。
      ✗「乐观锁一定比悲观锁快」✓ 看冲突率：p 过半时白干的工作量超过省下的排队（期望尝试 2 次以上）；判据是 1/(1−p)，不是感觉。
      ✗「悲观锁慢，高并发要避免」✓ 悲观是把不确定性换成排队；临界区短、冲突高时反而更稳——慢是因为临界区长，不是锁本身。
      ✗「库存扣减先查再改就行」✓ 查和改之间有窗口：判断必须下推进原子操作（条件更新 / 原子扣减），否则高并发下超卖。
      ✗「分段锁能解决热点问题」✓ 分段按 key 分派，热键始终在同一段；热点要换方案：本地聚合、队列串行、每节点累加器。
      ✗「读多写少就上读写锁」✓ 临界区极短时记账比省下的等待还贵，还有写者饥饿；长临界区的读多写少才明显划算。
      ✗「分布式锁保证了互斥」✓ 它给的是「大概互斥」：GC / 时钟 / 分区能造出两个持有者；资源侧校验 fencing token 才是保证。
      ✗「用 Redis 锁就够了」✓ 主从异步切换时锁会丢（还没同步主就挂）；且引入新的可用性依赖——Redis 挂了业务卡住。
