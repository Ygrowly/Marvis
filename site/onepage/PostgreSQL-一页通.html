01主干：两个根 → 七条主线（读快 → 写稳 → 持久 → 回收 → 增长 → 落地）正本 wiki/topics/PostgreSQL/

一切差异的根只有两个：堆表（索引只是路标）与版本留在堆里（回收不自动）。七条主线从这两个根推出；底部横幅是七处 MySQL/PG 差异的安全底线。
主干叙事（一段读完）：PG 的一切差异都从两个结构性事实推出来 —— 堆表（索引只是「指向数据的路标」，所有索引都要回表）和版本留在堆里（更新即新版本，旧版本靠 VACUUM 回收，回收不自动）。 存与索引：B-tree 是默认（覆盖面最广），GIN 的倒排天然匹配「包含」；部分索引把调度器索引做到 1/100 但会静默失效；CONCURRENTLY 失败留下 invalid 索引——它仍被优化器计算，纯负债，删掉重建。 执行：EXPLAIN ANALYZE 看 actual rows 与 loops（total = actual × loops，从最贵叶子往上看）；估行数失真先查统计信息（默认 100 桶，大表导入后手动 ANALYZE）。 事务与锁：默认 READ COMMITTED；Serializable 是 SSI——代价是失败（40001）不是等待，应用必须能重试；没有间隙锁，跨行不变量靠显式约束 + 条件更新，不靠「先查一遍」。 持久化：只有一套 WAL（没有 undo）——这正是旧版本必须靠 VACUUM 回收的原因；恢复时长 = checkpoint 落后的 WAL 量 ÷ 重放速度。 回收是主戏：长事务按住回收边界（idle in transaction 也要防），2 小时 × 1000 行/s = 720 万死元组；autovacuum 默认要堆 20% 死元组才动手；事务 ID 32 位靠冻结重置。 增长与落地：分区的价值是「丢弃即归档」；进程模型连接贵，连接池是刚需（事务池化破坏预处理语句）；业务侧用条件更新（FOR UPDATE 吞吐 = 1÷持锁时长）+ 唯一约束兜底幂等。
读法：蓝线主线；紫框是并发与失效（PG 与 MySQL 差异最大的一段）；绿框是回收与增长（PG 独有的运维主戏）；底部横幅是七处 MySQL/PG 差异——每一条都能从「堆表 + 版本留堆」两个根推出。

P2 堆表回表为什么都要回表PG 是堆表：索引只存「值 → 位置」，回表随命中行数线性涨（InnoDB 至少主键不回）；Index Only Scan 的判据是「页全可见」不是「列齐」——前提是 visibility map 正常，即 VACUUM 一直在跑3、5EnergyOps：事实表按（等值在前、范围在后）建索引；优化重心是减少扫描与回表，不凑覆盖索引
P3 部分索引什么场景省一大截部分索引只覆盖「WHERE 里那部分行」（调度器只查活跃态 → 体积 1/100、写入与 VACUUM 同步减负）；表达式索引把 lower(email) 的结果当索引键；部分唯一索引 = 软删除经典解；最大风险：需求变了它静默失效4未使用 —— 部分索引必须写清「它服务谁」，这是它和普通索引最大的不同
P4 索引代价在线建索引的坑三项代价：写放大（每个索引多一份维护）、空间、VACUUM 压力；HOT 更新（不改索引列 + 页内有空间）免索引维护；CONCURRENTLY 两阶段不阻塞写入但慢——失败留下 INVALID 索引：仍被计算、拖慢规划，删掉重建6、7、34未使用 —— PG 方言：CONCURRENTLY 失败留 invalid（MySQL 影子表方案对应物不同）
P5 类型选型text / jsonb / 主键 / 时间text 与 varchar 无性能差（存法一样）、char(n) 真实有代价；jsonb 可建 GIN（选了它才有索引可言）但丢重复键改键序——签名校验会悄悄坏；identity 替代 serial（SQL 标准）；timestamptz 默认答案，timestamp 只留给「墙上时间」8–12EnergyOps：能耗事实表用 timestamptz + 数值类型按口径选
P6 执行计划看计划看什么EXPLAIN ANALYZE 才是真相（cost 是估算、只能比同一条 SQL 的两个计划）；loops 是乘数（total = actual × loops），从最贵叶子往上看；BUFFERS 必加——分不清算法差还是缓存冷；Bitmap Heap Scan = 两步走（索引定位 + 堆顺序取）13、15EnergyOps：EXPLAIN ANALYZE 是索引设计唯一依据；坑：把「看到 Index Scan」当成功，接口还是慢
P7 统计信息估行为什么不准估行数 = 各条件独立假设相乘，JOIN 后膨胀；默认 100 桶 + MCV 兜最热 100 值，长尾列失真；大表 auto-analyze 阈值是行数比例——批量导入后必须手动 ANALYZE；generic plan 在参数分布倾斜时翻车（EXPLAIN 快、线上慢的标准答案）14、16EnergyOps：JOIN 后行数膨胀导致优化器选错——先修统计信息与写法，不是先换索引
P8 隔离级别默认 RC 与读一致性默认 READ COMMITTED（每条语句取新快照）；PG 的 RR 比 SQL 标准强（快照取自事务第一条语句）但写冲突直接报错；「调高级别更安全」的反向代价：快照更旧更久 → 死元组更多 → 膨胀更快；序列不是事务性的（自增必有洞）17、18数驭穹图：LIVE_READ 强制只读事务 + 超时 + 取消能力——事务边界是生产纪律
P9 SSI 失败重试Serializable 为什么失败SSI 不额外阻塞、检测到「组合不可串行」就中止（40001）；谓词锁会升级（读 264KB 就把整表标读过）→ 冲突面放大；错误用错误码判（40001 是契约），重试框架必须覆盖 COMMIT 失败；对确定性错误无脑重试 = 制造重复副作用19未使用 —— 判据：能重试就用 SSI/乐观；冲突率高到重试成本超过加锁才用悲观
P10 无间隙锁幻读与不变量靠什么PG 无间隙锁：「先查一遍再插入」天然竞态，必须唯一约束兜底；幻读防护靠 SSI（可选），业务不变量靠显式约束 + 条件更新；FOR UPDATE 四变体按冲突矩阵选（外键用最弱的 FOR KEY SHARE）；advisory lock 会话级回滚不释放；锁默认无限等20–22RuleArena：PG 无间隙锁 → 跨行不变量（refunded+amount≤paid）不能靠「我先查」，只能条件更新 + 约束
P11 WAL提交过为什么不丢WAL 单一日志（无 undo）：synchronous_commit 是唯一承诺的落盘点（无备库时 remote_apply 与 on 无区别）；checkpoint 把脏页落盘、允许重用 WAL；恢复时长 = checkpoint 落后量 ÷ 重放速度；full_page_writes 让 checkpoint 越勤 WAL 越大（整页镜像）23、24数驭穹图：PG 源的增量同步路径建立在 WAL / 逻辑复制上
P12 复制流复制 vs 逻辑复制流复制复制存储变化（整实例、字节级、备只读）；逻辑复制复制数据变化（按表、可跨版本、可筛选）；synchronous_commit 五档 = RPO 与延迟的正交矩阵；复制槽默认无限保留 WAL——一个消费者掉线，不到一天主库不可写25、26数驭穹图：只要「授权的分析数据集」→ 走逻辑路径；第一版快照 + 轮询，不上完整 CDC
P13 MVCCxmin/xmax 与死元组版本留在堆里：UPDATE = 插新版本 + 旧版本标 xmax；可见性 = 拿快照比 xmin/xmax，读不加锁；代价：一张更新频繁的表占用可达有效数据数倍；索引也指向死元组 → 索引多则 VACUUM 更累；HOT 更新免索引维护（可量化：n_tup_hot_upd 占比）27、28RuleArena：条件更新读权威 Snapshot 判定——多版本让「读权威」随时可行
P14 长事务表膨胀的机制回收边界由最老快照决定：2 小时长事务 + 每秒 1000 次更新 = 720 万死元组（且复制到每个索引）；只读长事务同样按边界（idle in transaction 有专门超时参数）；膨胀正反馈：扫描更多页 → 缓存有效行变少 → 更慢 → 事务更长29数驭穹图：长事务阻塞 VACUUM、拉长快照持有——发布前校验新鲜度与位点
P15 VACUUM回收与事务 ID 回卷VACUUM 三件事：清死元组（空间标可复用不缩文件）、更新可见性映射、冻结旧元组；autovacuum 阈值 = 50 + 0.2×行数（大表最经不起堆积却最晚动手，max_workers 默认 3）；事务 ID 32 位 ≈ 43 亿：靠冻结重置，回卷红线前 PG 宁肯拒服；膨胀已发生：先切源头再 pg_repack30–32未使用 —— 判据：「跑完 VACUUM 表还是 10GB」是设计不是故障
P16 分区什么时候才值得分三种分区（范围/列表/哈希）；收益一：分区裁剪（扫描量降到命中分区）；收益二（更值钱）：DROP PARTITION = 元数据操作，DELETE = 大清理；代价：唯一约束必须含分区键（分区结构的数学后果）、分区上在线建索引是一套流程；EnergyOps 当前规模未分区33EnergyOps：分区列为「暂缓」——等容量与 SLO 证明不足才升级，不预先优化
P17 连接池连接为什么贵进程模型：每连接一个进程（内存 + fork 成本），连接很贵 → 池是刚需；work_mem 是「每个操作」的上限：实际内存 = 连接数 × 节点数 × work_mem（100×4MB=400MB 是错的）；三种池化：会话安全省最少、事务省最多但破坏预处理语句（pgbouncer 经典坑）35未使用 —— 判据：池化解决「连接多」，超时解决「事务长」——正交问题都要做
P18 乐观并发项目里怎么选条件更新 = 期望值进 WHERE（version 防状态回流；状态会 READY→SEARCHING→READY 时只有版本号能区分两轮）；影响 0 行是业务分支；FOR UPDATE 吞吐 = 1÷持锁时长（与并发无关）vs 条件更新成本 = 1/(1−p)——冲突率定选型；「用不用乐观」最终是幂等设计问题36、39EnergyOps + RuleArena：条件更新 + version；理由是「权威性」不是「低频写」，别说满「不用锁」
P19 唯一约束幂等的最终防线应用层幂等不够：唯一约束的失败是确定的（23505 = 「做过」，可查 Receipt 返回原结果）；幂等键按业务身份构造（ToolCallID 每次都变是反例）；复合唯一别漏 NOT NULL（NULL 不参与唯一判重）；UPSERT 四坑：excluded 可能被触发器改过、序列必有洞、DO UPDATE 需要 NOT DEFERRABLE 排除约束、死元组加速消耗37、38RuleArena：UNIQUE(run_id, action_type, idempotency_key) 兜底资金正确性；副作用与 Receipt 同一事务提交

      05要能现场算出来的数正本 母题卡「一、教材」推导

      两小时长事务
      720 万死元组
      1000 行/s × 7200s，且复制到每个索引——长事务拖全库的不是 CPU，是回收停摆。
      autovacuum 阈值
      50 + 0.2 × 行数
      1000 万行的表要堆 200 万死元组才触发——大表最经不起堆积、却最晚动手。
      SSI 谓词锁升级
      264 KB = 整表
      读 264KB 就把整张表标「我读过」（16GB 表的 1/60000）——40001 的冲突面被放大到表级。
      FOR UPDATE 天花板
      200 TPS
      吞吐 = 1 ÷ 持锁时长（5ms），加并发无效；条件更新的成本是期望尝试次数，与冲突率相关。
      条件更新
      p=0.6 → 2.5 次
      E = 1/(1−p)：冲突率 60% 时期望 2.5 次尝试——与「悲观排队」的成本曲线交点就是选型。
      事务 ID 回卷
      43 亿 ≈ 100 天
      32 位事务 ID，500 TPS 约 100 天走完一圈——靠冻结重置；回卷红线前 PG 宁肯拒绝服务。
      work_mem 乘法
      100×3×4MB
      work_mem 是「每个操作」的上限：实际内存 = 连接数 × 排序/哈希节点数 × work_mem ≈ 1.2GB，不是 400MB。
      统计桶
      默认 100 个
      MCV 只兜最热 100 值、直方图 100 桶——长尾列估算失真；大表导入后手动 ANALYZE 是刚需。
      部分索引
      体积 1/100
      调度器只查活跃态：只索引活跃行，写入与 VACUUM 同步减负——代价是会静默失效。

      06八句最容易说错的话正本 母题卡「二、自测」纠错题原话

      说对前半句没用，后半句才是判据。
      ✗「PG 默认 RR，跟 MySQL 一样」✓ 默认 READ COMMITTED；PG 的 RR 也比 SQL 标准强（快照取自第一条语句），且写冲突直接报错。
      ✗「PG 的 MVCC 靠 undo log」✓ 版本留在堆里（xmin/xmax），旧版本靠 VACUUM 回收——「回收不自动」是 PG 一切运维课题的来源。
      ✗「看到 Index Scan 就是优化成功」✓ 真正看 actual rows / loops / 过滤行数 + 分段计时——EnergyOps 的坑：接口还是慢。
      ✗「Index Only Scan 就是索引列齐了」✓ 判据是可见性：页全可见才免回表——前提是 VACUUM 一直正常跑。
      ✗「PG 没间隙锁，幻读没防护」✓ 防护靠 SSI（可串行化，可选）；业务不变量靠显式约束 + 条件更新，不是默认级别。
      ✗「VACUUM 完表应该变小」✓ 常规 VACUUM 只把空间标为可复用，表文件不变小是设计；要缩表用 pg_repack / VACUUM FULL（排他锁）。
      ✗「更新列不在索引里就没代价」✓ 只有 HOT 路径成立（不动索引列 + 页内有空间）；否则每个索引多一个死元组等 VACUUM。
      ✗「连接池配好就万事大吉」✓ 池化解决「连接多」，超时解决「事务长」——正交问题；事务池化还会破坏预处理语句。
