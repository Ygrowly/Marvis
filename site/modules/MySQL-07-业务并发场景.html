M16**乐观锁 vs 悲观锁怎么选**（9.9 一面原题，答得不合格）草稿 · 待验收单卡 →

乐观锁和悲观锁怎么选？各自的实现与边界是什么？

说一下乐观锁与悲观锁的区别。（9.9 一面原题，当次 11 分——口误"悲观所"、没提版本号/CAS、没讲适用边界）

一句话结论：区别在对冲突的假设不同。悲观锁假定冲突一定发生，所以访问前先加锁：数据库里是 SELECT ... FOR UPDATE，Java 里是 synchronized / ReentrantLock，拿到锁才能改，其他事务阻塞等待——适合写多、冲突频繁、临界区长，代价是锁开销与死锁风险。乐观锁假定冲突很少，不加锁直接改，提交时校验有没有被别人改过：常见做法是 version 字段（UPDATE ... WHERE version=?，影响行数 0 即冲突）或 CAS——适合读多写少，要注意 ABA 问题。判据一句话：冲突频率高到重试成本大于加锁成本时，才用悲观锁。

  • 假设不同
  • 悲观=FOR UPDATE
  • 乐观=version 或 CAS
  • 影响行数 0 判冲突
  • **ABA 问题**（AtomicStampedReference）
  • **冲突频率是唯一判据**
  • RuleArena 的条件更新

主线：两者不是"谁更好"，而是对冲突概率的两种假设。 没有冲突概率，选型就是空谈——所以回答的第一句话永远是"冲突频率"，第二句才是机制（这正是 9.9 那次缺的东西）。

原理分解

一、悲观锁：先拿锁，再操作

SELECT status FROM task WHERE id = 1 FOR UPDATE;   -- 加 X 锁
UPDATE task SET status = 'RUNNING' WHERE id = 1;
COMMIT;

实现：数据库 SELECT ... FOR UPDATE（排他锁）；Java 里 synchronized / ReentrantLock；分布式场景是 Redis/ZK 锁（但分布式锁不能替代数据库约束，P19 的结论）。

适用：写多、冲突频繁、临界区长（拿到锁之后要做一堆事）。 代价：① 等待与吞吐下降；② 死锁风险（顺序不一致时，M10）；③ 连接占用时间长（P17 的口径）。

二、乐观锁：不加锁，提交时校验

两种实现：

① version 字段（数据库场景的标准做法）

UPDATE task
SET status = 'RUNNING', version = version + 1
WHERE id = 1 AND version = :expected_version;   -- 期望值进 WHERE
-- 影响行数 = 0 → 别人改过 → 读出最新值再决定

② CAS（Compare-And-Swap，CPU/Java 层面）

期望值 E、新值 V：内存位置当前值 == E 才写入 V
Java 里即 Atomic* 类（AtomicInteger 等，底层 CAS 指令）

适用：读多写少、冲突少、单行。 代价：冲突多时反复重试，成本反而更高；只能保护单行/单个变量——跨行不变量靠它撑不住（要靠约束或事务，P18）。

三、ABA 问题（必考的细节）

CAS 只比较"值是否相等"，不比较"中间有没有变过"：

线程 1 读到值 100（准备改成 200）
线程 2 把 100 改成 80，又改回 100
线程 1 CAS(100 → 200) 成功          ← 但它不知道中间发生过 80

数值场景通常无害（1 加 5 次 = 5 加 1 次），但"引用/状态"场景有害——比如栈顶指针被弹出又压回同一个地址，链表结构已被破坏，CAS 却认为"没变过"。

解法：版本号 / 时间戳一起比——Java 里 AtomicStampedReference（带 stamp），数据库里 version 字段本质就是"自带 ABA 防护的 CAS"。

这一条能把"version 为什么比直接比较值更稳"讲成因果，而不是一句"要加 version"的口诀。

四、判据（本题的落点）

冲突频率高到「重试成本 > 加锁成本」时，用悲观锁；否则乐观。

为什么这条是唯一判据：两种方案的成本函数不同——

悲观锁成本 ≈ 加锁开销 + 冲突时的等待（随冲突率线性上升）
乐观锁成本 ≈ 重试次数 × 单次成本（随冲突率更快上升）

低冲突时乐观的曲线更平（几乎零成本），高冲突时悲观的曲线更平（等待是排队，不是全部重来）。所以不是"乐观更先进"，是"冲突少时乐观便宜"。面试里画这两条成本曲线，比背定义高一个档次。

五、结合自己的项目（必练：这条是你的差异化）

RuleArena 的退款与任务认领用的是乐观锁（条件更新），理由（P18 已展开）：

  • 扣退款是低频写、读多写少 → 冲突少；
  • 条件更新一次原子写，天然幂等（重复执行第二次影响 0 行）；
  • 跨行不变量写进 WHERE（refunded + amount <= paid）；
  • 唯一约束兜底（UNIQUE(run_id, action_type, idempotency_key)）。

然后反向讲一句（这是"懂边界"的证据）："如果同一个任务被大量 Worker 高频争抢，重试成本就会超过加锁成本，那时我会换成悲观锁或者把任务分区错开"——主动说出自己方案不适用的情况，比硬吹乐观锁可信得多（这也是 A11 复盘里"主动暴露局限"那条经验在技术题上的应用）。

M17排行榜 / 防超卖：用 MySQL 还是 Redis，为什么草稿 · 待验收单卡 →

排行榜用 MySQL 还是 Redis，为什么？高并发扣减怎么防超卖？

① 产品要给开心消消乐每个关卡加一个排行榜（DAU 2000 万），让玩家看到自己排名——结合 AI 做个设计。② 高并发扣体力/扣库存怎么防超卖？（A24 是 9.9 全场最低分模块（10 分）：没给出成型方案、防作弊完全没提）

一句话结论：排行榜用 Redis ZSet（成员按 score 有序，ZREVRANK / ZREVRANGE 都是 O(logN)，天然就是排行榜）；MySQL 不适合（排名需要 COUNT(*) 统计比自己分高的行数，代价 O(N)，且高频更新排序索引压力大）。同分先到者优先 → 复合分数：score = 分数 × 10^10 + (MAX_TS - 通关时间戳)。防超卖三条路：① 数据库原子扣减（UPDATE ... SET n=n-1 WHERE id=? AND n>0，影响行数判断）、② 乐观锁（version 条件更新，M16）、③ Redis 预扣 + 异步落库（最终一致）。判据：强一致用数据库原子更新；高并发削峰用 Redis 前置、DB 兜底。

  • ZSet 跳表
  • 复合分数
  • ZREVRANK
  • 只存 Top N
  • 原子扣减 `WHERE n>0`
  • 乐观锁
  • **Redis 预扣 + 异步落库**
  • 最终一致
  • 场景题六步

主线：场景题的第一动作是澄清，不是给方案。 ——9.9 那次丢分的一半在"没问够"（榜单范围、更新频率、防作弊全没问），另一半才是技术。技术选型（MySQL vs Redis）反而是这张卡里最容易的部分。

原理分解

一、场景题六步（先背这个，再背技术）

① 澄清（开口前先问 10 秒）：排名依据？榜单范围（全服/好友/Top N）？更新频率？
                          展示字段？历史榜/周榜？防作弊？规模？
② 拆解：规模估算（2000 万 DAU × 千级关卡 → 不可能全量存排名）
③ 方案：存储 + 读写路径 + 数据结构
④ 风险：热点 key、写入尖峰、内存、作弊
⑤ 指标：写入 QPS、查榜 P99、内存占用、裁剪耗时
⑥ 降级：Redis 挂了怎么办

9.9 那次的澄清对照（复盘里的 ✅/❌ 清单）：问了排名依据、展示字段、规模；没问榜单范围、更新频率、历史榜、防作弊——把这张清单背下来，下次第一分钟就不会空白。

二、排行榜选型：为什么是 Redis ZSet

Redis ZSetMySQL
排名查询ZREVRANK O(logN)COUNT(*) WHERE score > ?，O(N)（或加冗余排名字段，但更新代价高）
榜单读取ZREVRANGE 直接取 Top NORDER BY score DESC LIMIT N（索引可以，但更新热点行代价高）
更新ZADD O(logN)高频 UPDATE 同一行 → 行锁热点（M10）
底层跳表 + 哈希表（既能按 member 查 score，又能按 score 范围查）B+ 树

同分按时间早的优先 → 复合分数（这是 9.9 标答里最巧的一步）：

score = 分数 × 10^10 + (MAX_TS − 通关时间戳)
        分数越高越大；同分时时间越早（MAX_TS - ts 越大）排名越高

一句话解释：把两个排序维度压进一个可比较的数字——避免"先按分数排、再按时间排"的两级查询。

三、2000 万 DAU 下的工程问题（答到这层才像服务端）

① 热点 key：热门关卡集中在少数 key → 按"关卡+区服/分片"拆，或本地缓存 + 异步刷新
② 写入削峰：通关上报是尖峰 → 消息队列异步落榜，前端先返回"计算中"
③ 名次不必实时精确：非头部玩家用"分数段桶计数"近似名次，精确 ZREVRANK 留给头部
④ 只存 Top N：每关只保留 Top N（ZREMRANGEBYRANK 定期裁剪）——内存控制的关键
   玩家个人最佳与名次另存（DB），榜外玩家看"自己的最佳 + 击败百分比"
⑤ 持久化：Redis 只是热层，冷数据定时落 DB；Redis 挂了可从 DB 重建
⑥ 活动榜：带过期时间的 key（EXPIRE），活动结束自动清理

第 ③ 条是"名次近似"——2000 万 DAU 下大多数玩家的名次并不需要精确到个位（"你超过了 97% 的玩家"），这是把 O(logN) 精确查询留给头部、用 O(1) 近似服务长尾的取舍。这一条是 9.9 标答里的亮点，值得单独背。

四、游戏特性（乐元素面试官最想听的）

  • 防作弊：消消乐是弱联网玩法，客户端上报的分数必须校验——步数下限、最短通关时长、关键操作日志回放；异常分数进人工审核队列，不直接入榜；
  • 弱联网容错：离线通关本地缓存，联网后补报，用"玩家 ID + 关卡 + 时间戳"做幂等，避免重复提交刷榜（这就是 P19 的幂等键思想在游戏场景的落点）；
  • 活动榜时效：EXPIRE 自动清理。

"防作弊没提"是 9.9 那次被明确点名的缺口——游戏公司的场景题里这是必答项。

五、防超卖三条路

① 数据库原子扣减（最简单、强一致）

UPDATE stock SET num = num - 1
WHERE id = :id AND num > 0;
-- 影响行数 = 1 → 扣成功；0 → 已售罄

为什么能防超卖：判断和写入在一条语句里原子完成（和 P18/M16 的条件更新是同一个原理）——不存在"查到还剩 1，两个人都扣"的窗口。热点行锁竞争是它的代价（同一行高频更新会排队，M10）。

② 乐观锁（version）：语义同上，多一个 version 字段（M16）；适合"扣减前还要做别的判断"的场景。

③ Redis 预扣 + 异步落库（高并发削峰）

请求 → Redis DECR（原子）→ 扣成功才进队列 → 异步落 DB
                ↓ 扣成负数 → 回滚/拒绝

代价：最终一致（Redis 与 DB 有窗口）、要处理重复消费与对账（P19 的幂等键 + 唯一约束兜底）。判据：强一致（钱）→ 数据库原子更新；高并发（秒杀、体力）→ Redis 前置 + DB 兜底。

六、指标与降级

  • 指标：写入 QPS、查榜 P99、Redis 内存占用、裁剪任务耗时、超卖告警（库存对账）；
  • 降级：Redis 不可用时返回 DB 快照或"榜单维护中"，绝不让排行榜拖垮主玩法——"排行榜挂了不能影响游戏本体"是这一题的底线判断。
