M16乐观锁 vs 悲观锁怎么选（9.9 一面原题，答得不合格）

骨架：两种假设 → 悲观锁的实现与代价 → 乐观锁的实现（version / CAS）→ ABA 为什么是 CAS 的固有缺陷 → 一条判据 + 两条成本曲线（1/(1−p) 会发散） → 结合自己项目（RuleArena 条件更新）→ 反向说"什么情况我会换悲观锁"

一句话结论：两者不是"谁更好"，而是对冲突概率的两种假设——悲观锁假定冲突一定发生，所以先加锁（SELECT ... FOR UPDATE / synchronized）；乐观锁假定冲突很少，不加锁、提交时校验（version 字段或 CAS，UPDATE ... WHERE version=?，影响行数 0 即冲突）。判据只有一个：冲突频率——冲突高到"重试成本 > 加锁成本"时用悲观。这不是口号：乐观锁成本是 单次成本 ÷ (1−p)，在 p→1 时发散；高冲突下 N 个请求抢同一行，乐观锁总工作量 N²、悲观锁 N，差一个 N 倍。乐观锁要注意 ABA 问题（值相等 ≠ 中间没变过），version 字段本质就是"自带 ABA 防护的 CAS"。RuleArena 的退款与任务认领用的是乐观锁（条件更新），项目给的判据是「权威性」不是「频率」（04 §15「MVP 优先业务唯一键 + 条件更新」；Q7「锁可以降低竞争，但不能成为资金正确性的唯一保证」），而且条件更新天然幂等；但如果同一个任务被大量 Worker 高频争抢，我会换成悲观锁或把任务分区错开。

  • 悲观 = FOR UPDATE（注意 next-key）、有死锁风险
  • 乐观 = version 或 CAS、期望值进 WHERE
  • 影响行数 0 = 正常业务分支
  • ABA（值相等 ≠ 没变过；引用场景有害）
  • AtomicStampedReference、version 自带 ABA 防护
  • 判据 = 冲突频率
  • 乐观成本 = 1
  • (1−p) 会发散
  • 高冲突 N² vs N
  • 重试要有退避 + 抖动 + 上限
  • 分布式锁不能替代约束

两者不是谁更好，是对冲突概率的两种假设。悲观锁假定冲突一定发生，所以先加锁（SELECT ... FOR UPDATE、synchronized）；乐观锁假定冲突很少，不加锁、提交时校验——version 字段或 CAS，写法是 UPDATE ... SET ... WHERE id = ? AND version = ?，影响行数 0 就是冲突。

判据只有一个：冲突频率。乐观锁的成本约等于单次成本 ÷ (1 − p)，p 趋近 1 时发散；高冲突下 N 个请求抢同一行，乐观锁总工作量约 N²，悲观锁约 N，差一个 N 倍。所以冲突高到「重试成本 > 加锁成本」就该换悲观。

乐观锁的核心是「期望值进 WHERE」，version、状态、时间戳都行，本质是 CAS 思想；version 的好处是自带 ABA 防护——CAS 比较值相等并不安全，值相等不等于中间没变过，数值场景通常无害，引用 / 状态 / 指针场景有害（栈顶指针弹出又压回同一地址）。

工程上：影响行数 0 是正常业务分支，可能是别人抢先了、也可能条件本来就不满足，分不出来也不需要分，正确做法是读权威状态再判定；重试必须有次数上限和退避，不能一直重试到成功。

分层要点追问深挖时用

  • 结论：两种假设，不是优劣；判据是冲突频率 p。
  • 推导链：悲观先加锁 vs 乐观提交时校验（期望值进 WHERE）→ 成本曲线 1/(1−p) → p→1 发散 → 高冲突下 N² vs N → 换悲观。
  • 量化：乐观锁成本 ≈ 单次成本 ÷ (1−p)；高冲突下乐观约 N²、悲观约 N，差一个 N 倍。
  • 边界与常见误解：乐观锁性能一定更好 ×；乐观锁 ≠ 加个 version（本质是 CAS，version 顺带防 ABA）；影响行数 0 是正常分支不是异常；重试要有上限和退避。

WHERE num > 0），三条路按一致性要求选。

  • 六步章法（澄清优先）
  • ZSet = 跳表 + 哈希表
  • ZREVRANK O(logN) vs COUNT(*) O(N)
  • 复合分数
  • 2⁵³ 位数预算，倍率 10¹⁰ → 分数上限 < 90 万
  • 只存 Top N（5GB→50MB）
  • 名次近似
  • 热点 key 分片
  • 削峰走 MQ
  • 防作弊三条（步数下限·最短时长·日志回放）+ 异常进审核
  • 幂等键防重复上报
  • 原子扣减 WHERE num > 0
  • Redis 预扣 + 异步落库 = 最终一致
  • 排行榜挂了不能影响主玩法

场景题第一动作是澄清。先问清六件事：榜单范围（全区还是好友）、更新频率、同分怎么排、要不要防作弊、读写比例、榜单规模。9.9 那次丢分有一半在「没问够」。

技术上排行榜用 Redis ZSet：跳表把「按 score 有序」内建进结构，ZADD 和 ZREVRANK 都是 O(logN)；MySQL 算名次要 COUNT(*) WHERE score > ?，是 O(N)——200 万榜单要数约 100 万行，而 ZSet 大约 21 次比较，差约 5 万倍，且榜单越大差距越大。

同分先到者优先靠复合分数：分数 × 倍率 + (MAX_TS − 通关时间戳)。这里有个位数陷阱：Redis 的 score 是双精度浮点，只有 2^53 以内能精确表示，倍率取 10^10 时分数上限必须小于约 90 万，否则低位被抹掉、同分排序错乱而且不报错。

防作弊是必答项：弱联网玩法客户端可被篡改，必须校验（步数下限、最短通关时长、操作日志回放），异常分数进人工审核。

防超卖三条路：把判断下推进 WHERE（UPDATE ... SET stock = stock − 1 WHERE stock > 0）、Redis 预扣 + 异步落库、悲观锁排队；判据是并发量与能否容忍少量回滚。

  • 推导链：澄清 → 拆解规模 → 选型算复杂度 → 复合分数（位数预算）→ 工程问题（热点 / Top N / 持久化）→ 防作弊 → 防超卖。
  • 量化：200 万榜单 MySQL 约数 100 万行 vs ZSet 约 21 次比较，差约 5 万倍；score 是双精度，倍率 10^10 时分数上限约 90 万。
  • 边界与常见误解：MySQL 加个索引就行 ×（数量级不对）；倍率取大更保险 ×（会越界且不报错）；客户端上报直接入榜 ×（漏了防作弊）；先查库存再扣 ×（并发有窗口，判断要下推进 WHERE）。

主线：两者不是"谁更好"，而是对冲突概率的两种假设。

1. version 冲突之后怎么处理？

读出权威状态，再决定重试还是放弃——"影响行数 0"是正常业务分支，不是异常。不要写 while(true) retry：要有退避、抖动和上限。

2. 9.9 那次你的答案缺了什么？

三条：① 没提 version / CAS（实现层面）；② 没讲适用边界（判据层面）；③ 口误（表达层面）。通过标准：40 秒内给出「假设不同 → 两种实现 → ABA → 判据 → 自己项目实例」五段结构，并主动补一句"什么情况我会换悲观锁"。

3. 乐观锁在数据库里就是加 version 字段吗？

核心是"期望值进 WHERE"：用 version、用状态、用时间戳都行；本质是 CAS 思想。version 字段的好处是自带 ABA 防护。

4. 分布式锁算悲观锁吗？

算（假设冲突、先拿锁），但它是应用层的锁，不能替代数据库约束做正确性兜底（[[母题-P19-唯一约束与UPSERT]]）。锁会失效（过期、网络分区），约束不会。

  • 防作弊三条（步数下限·最短时长·日志回放）+ 异常进审核
  • 幂等键防重复上报
  • 原子扣减 WHERE num > 0
  • Redis 预扣 + 异步落库 = 最终一致
  • 排行榜挂了不能影响主玩法

主线：排行榜的答案是"把计算内建进数据结构"（ZSet 的排名是结构自带的，不是查出来的）；

1. Redis 挂了排行榜怎么办？

① 从 DB 重建（冷数据定时落 DB 是前提）；② 降级为"榜单维护中"，主玩法不受影响；③ 写路径要能容忍 Redis 不可用（丢分但不断游戏）。"依赖服务的可用性必须低于主链路"是通用原则。

2. ZSet 为什么快？

跳表：按 score 有序的多级链表，ZREVRANK 走 O(logN)；哈希表保证 member → score 的 O(1) 查询。两个结构配合，所以它"既能查排名又能按成员取分数"。

3. 为什么不用 MySQL 的冗余排名字段？

每写一次分数要更新所有受影响的名次（写放大），或者用 COUNT 现算（读放大）；ZSet 把排名维护内建进了数据结构。"把计算内建进数据结构"是选型的通用思路。

4. 消消乐是单机游戏吧？

不是（9.9 那次的第一条失误就是假设单机）。它有联网排行榜、好友榜、活动榜——澄清阶段没问，这里就假设错。

5. 这道题和你项目有什么关系？

方法论一致：① 澄清优先（RuleArena 的"先查规格再重放"）；② 幂等键防重复上报（[[母题-P19-唯一约束与UPSERT]]）；③ 削峰走异步 + 最终一致 + 对账（[[母题-P12-流复制与逻辑复制]] 的延迟语义）。答场景题时主动把这些连线，就把"知识题"答成了"工程题"。

44必背M16

这道题属于母题 M16 · 乐观锁 vs 悲观锁怎么选（9.9 一面原题，答得不合格） · 下面挂它的完整回答（学的时候看）

实测 467 字 · 按 4 字/秒折算约 117 秒（秒数是估算，字数才是实测）

两者不是谁更好，是对冲突概率的两种假设。悲观锁假定冲突一定发生，所以先加锁（SELECT ... FOR UPDATE、synchronized）；乐观锁假定冲突很少，不加锁、提交时校验——version 字段或 CAS，写法是 UPDATE ... SET ... WHERE id = ? AND version = ?，影响行数 0 就是冲突。

判据只有一个：冲突频率。乐观锁的成本约等于单次成本 ÷ (1 − p)，p 趋近 1 时发散；高冲突下 N 个请求抢同一行，乐观锁总工作量约 N²，悲观锁约 N，差一个 N 倍。所以冲突高到「重试成本 > 加锁成本」就该换悲观。

乐观锁的核心是「期望值进 WHERE」，version、状态、时间戳都行，本质是 CAS 思想；version 的好处是自带 ABA 防护——CAS 比较值相等并不安全，值相等不等于中间没变过，数值场景通常无害，引用 / 状态 / 指针场景有害（栈顶指针弹出又压回同一地址）。

工程上：影响行数 0 是正常业务分支，可能是别人抢先了、也可能条件本来就不满足，分不出来也不需要分，正确做法是读权威状态再判定；重试必须有次数上限和退避，不能一直重试到成功。

分层要点追问深挖时用

  • 结论：两种假设，不是优劣；判据是冲突频率 p。
  • 推导链：悲观先加锁 vs 乐观提交时校验（期望值进 WHERE）→ 成本曲线 1/(1−p) → p→1 发散 → 高冲突下 N² vs N → 换悲观。
  • 量化：乐观锁成本 ≈ 单次成本 ÷ (1−p)；高冲突下乐观约 N²、悲观约 N，差一个 N 倍。
  • 边界与常见误解：乐观锁性能一定更好 ×；乐观锁 ≠ 加个 version（本质是 CAS，version 顺带防 ABA）；影响行数 0 是正常分支不是异常；重试要有上限和退避。

45必背M17

这道题属于母题 M17 · 排行榜 / 防超卖：用 MySQL 还是 Redis，为什么 · 下面挂它的完整回答（学的时候看）

实测 482 字 · 按 4 字/秒折算约 120 秒（秒数是估算，字数才是实测）

场景题第一动作是澄清。先问清六件事：榜单范围（全区还是好友）、更新频率、同分怎么排、要不要防作弊、读写比例、榜单规模。9.9 那次丢分有一半在「没问够」。

技术上排行榜用 Redis ZSet：跳表把「按 score 有序」内建进结构，ZADD 和 ZREVRANK 都是 O(logN)；MySQL 算名次要 COUNT(*) WHERE score > ?，是 O(N)——200 万榜单要数约 100 万行，而 ZSet 大约 21 次比较，差约 5 万倍，且榜单越大差距越大。

同分先到者优先靠复合分数：分数 × 倍率 + (MAX_TS − 通关时间戳)。这里有个位数陷阱：Redis 的 score 是双精度浮点，只有 2^53 以内能精确表示，倍率取 10^10 时分数上限必须小于约 90 万，否则低位被抹掉、同分排序错乱而且不报错。

防作弊是必答项：弱联网玩法客户端可被篡改，必须校验（步数下限、最短通关时长、操作日志回放），异常分数进人工审核。

防超卖三条路：把判断下推进 WHERE（UPDATE ... SET stock = stock − 1 WHERE stock > 0）、Redis 预扣 + 异步落库、悲观锁排队；判据是并发量与能否容忍少量回滚。

分层要点追问深挖时用

  • 结论：先澄清六件事再选型；排行榜用 ZSet（O(logN)），MySQL 算名次是 O(N)。
  • 推导链：澄清 → 拆解规模 → 选型算复杂度 → 复合分数（位数预算）→ 工程问题（热点 / Top N / 持久化）→ 防作弊 → 防超卖。
  • 量化：200 万榜单 MySQL 约数 100 万行 vs ZSet 约 21 次比较，差约 5 万倍；score 是双精度，倍率 10^10 时分数上限约 90 万。
  • 边界与常见误解：MySQL 加个索引就行 ×（数量级不对）；倍率取大更保险 ×（会越界且不报错）；客户端上报直接入榜 ×（漏了防作弊）；先查库存再扣 ×（并发有窗口，判断要下推进 WHERE）。
