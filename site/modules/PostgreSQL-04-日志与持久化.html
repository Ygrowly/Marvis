P11WAL 是怎么保证「提交过的不丢」的？checkpoint 在做什么

骨架：为什么需要 WAL（顺序写换随机写 + 崩溃安全）→ WAL 怎么保证已提交不丢 → off 到底丢多少（算出来） → checkpoint 在做什么 → 整页写的代价（算出来） → 为什么 PG 只有一套日志（不需要 undo）→ 生产怎么配

一句话结论：WAL 是「先写日志、再改数据页」：修改先顺序写进 WAL（顺序 IO），数据页留在共享缓冲区稍后再刷；提交时靠 fsync 保证这个事务的 WAL 已经落盘（synchronous_commit = on），所以崩溃后能用 WAL 把已提交的改动重放出来。checkpoint 做的事是「把某个 LSN 之前的脏页刷盘，从而把恢复起点向前推」——它不影响正确性，只影响崩溃后要重放多久。PG 不需要 undo，是因为旧版本本来就留在堆里（P13），不靠日志回滚。

  • fsync 与 synchronous_commit
  • off 丢的是三倍 wal_writer_delay ≈ 600ms 的【整段】
  • checkpoint 推进恢复起点
  • checkpoint_timeout 5min · max_wal_size 1GB
  • full_page_writes（检查点后首写整页）
  • wal_compression
  • pg_stat_checkpointer
  • 为什么不需要 undo

P12流复制和逻辑复制有什么区别？同步/异步怎么取舍

骨架：两种复制的机制差异 → 各自绑定的东西 → 回到题目做选择 → 同步级别与它对应的四个落点 → 两个能算的坑（复制槽堆积、回放追不上） → 你项目为什么选逻辑路径

一句话结论：流复制（物理）复制的是「整个实例的 WAL 字节流」——备库是主库的逐字节副本，只能整实例、备库只读（但可查询）、版本必须一致；逻辑复制复制的是「逻辑变更」——可以按表、可以按行过滤、备端可写、可跨大版本、能做异构与多源汇聚。所以 ① 只读副本用流复制；② 部分表同步到别的系统用逻辑复制。同步 / 异步的取舍本质是 RPO vs 提交延迟。

  • 物理复制（WAL 字节流）vs 逻辑复制（变更流）
  • 表级与行级过滤
  • 跨版本
  • 备库只读 vs 可写
  • synchronous_commit 五档对应备库四个落点
  • 复制槽默认无限保留 WAL（max_slot_wal_keep_size = -1）
  • 备库冲突查询默认 30 秒后被取消
  • 回放能力必须 ≥ 生成能力

主线：WAL 管「已提交的能不能重放出来」（正确性），checkpoint 管「重放要从多久之前开始」（恢复时间）。 两件事，但它们由同一组参数牵动——checkpoint 越勤，恢复越快，常态 IO 压力越大。

1. synchronous_commit = off 丢的是已提交事务，为什么还能接受？

因为它丢的是【连续的最后一段】，而且只丢数据不损坏数据——数据库状态等同于那些事务被干净地中止。判据是官方的原话：「客户端会不会采取依赖这个事务已被记住的外部动作」——银行不会用它记录 ATM 吐现金，但事件日志完全可以用。 这就是「数量级口径」：不是"会不会丢"，而是"丢多少、丢的是哪一段、能不能补"。

2. 恢复要多久，怎么估算？

最坏重放量 ≈ max_wal_size（软上限），再除以重放速度（可以拿一次真实恢复或压测测出来）。所以「恢复时间」是可以给出量级的数字，不是玄学参数。

3. PG 也有 binlog 吗？

没有。 逻辑复制、CDC 靠逻辑解码（从 WAL 解出逻辑变更，[[母题-P12-流复制与逻辑复制]]）；MySQL 的 binlog 是 Server 层单独一套逻辑日志。这是「PG 只有一套日志」的直接后果。

4. WAL 会无限增长吗？

不会，回收靠 checkpoint 推进；但如果开着复制槽而备库/消费者不消费，WAL 就不会被回收（P12 的经典事故：短时间内能把磁盘写满）。

5. 能不能关掉 WAL？

表可以设 UNLOGGED（不写 WAL，快，但崩溃后数据会被清空），只适合可重建的中间表。这是一个真实的工程选项，值得知道——但也要说清它的代价是"崩溃后整张表归零"。

主线：物理复制复制的是「存储的变化」，逻辑复制复制的是「数据的变化」。 所以前者绑定实例与版本，后者绑定表与行——所有能力差异（能不能选择性复制、备端能不能写、能不能跨版本）都是这一句话的推论。

1. 逻辑复制的目标端能写吗？

能（它是独立的可写表），代价是冲突要自己处理（目标端本地已有数据会与回放冲突）。这也是它能做多源汇聚的原因——同时也是它最难运维的地方。

2. 能不能用逻辑复制做双向同步？

技术上可以，但冲突解决完全靠自己，收益通常不如改成单向 + 明确归属。面试里承认「双向的复杂度收益比不高」比硬吹更好。

3. 为什么 PG 不用 binlog 也能做 CDC？

因为 WAL 本身就是完整的变更记录，逻辑解码把它翻译成逻辑变更（pgoutput）即可。这也解释了为什么 PG 侧的 CDC 工具（Debezium 等）都基于逻辑解码槽。

4. 备库上的统计信息要管吗？

要。统计信息不是"复制的数据"，它是每台实例各自 ANALYZE 出来的——只读副本如果从不分析，它的执行计划可能和主库完全不一样（[[母题-P7-统计信息与慢查询定位]]）。

5. 为什么你项目第一版不做完整 CDC？

要说出取舍：CDC 要求源端启用逻辑复制/binlog 并常驻一个消费者，一旦消费者停摆就有 WAL/binlog 堆积风险（这正是 Q2 那个 13.9 小时）；而分析场景对新鲜度的要求是分钟级可接受。所以用「可恢复快照 + updated_at / 递增主键轮询 + 位点与校验」换来了「不侵入客户生产库 + 可复现」——升级条件是出现真实的秒级新鲜度需求。 这段是项目叙事的核心，必须能自己讲。
