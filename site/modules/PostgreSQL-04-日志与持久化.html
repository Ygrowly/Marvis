WAL 是怎么保证「提交过的不丢」的？checkpoint 在做什么？

MySQL 有 redo / undo / binlog 三套日志，PG 只有一套 WAL。它是怎么保证「提交过的不丢」的？

一句话结论：WAL 是「先写日志、再改数据页」：修改先顺序写进 WAL（顺序 IO），数据页留在共享缓冲区稍后再刷；提交时靠 fsync 保证这个事务的 WAL 已经落盘（synchronous_commit = on），所以崩溃后能用 WAL 把已提交的改动重放出来。checkpoint 做的事是「把某个 LSN 之前的脏页刷盘，从而把恢复起点向前推」——它不影响正确性，只影响崩溃后要重放多久。PG 不需要 undo，是因为旧版本本来就留在堆里（P13），不靠日志回滚。

  • 预写日志（先日志后数据页）
  • LSN
  • fsync 与 synchronous_commit
  • checkpoint 推进恢复起点
  • checkpoint 频率的两面
  • full_page_writes（检查点后首写整页）
  • 恢复从最近 checkpoint 开始

主线：WAL 管「已提交的能不能重放出来」（正确性），checkpoint 管「重放要从多久之前开始」（恢复时间）。 两件事，但它们由同一组参数牵动——checkpoint 越勤，恢复越快，常态 IO 压力越大。

原理分解

一、为什么需要 WAL

修改数据时不直接改磁盘数据页（随机 IO 太慢），而是：

改内存（shared_buffers 里的数据页）
  + 把「改了什么」顺序追加到 WAL
  ↓
提交时：fsync WAL（保证这次提交已落盘）
  ↓
数据页留在内存，稍后由后台批量刷盘

两个收益：① 把随机写换成顺序写（写入性能）；② 只要 WAL 落盘，即使数据页没刷、机器立刻断电，重启后也能重放出来（崩溃安全）。

关键在「提交时 fsync 的是 WAL，不是数据页」——这就是「提交很快但数据页还没落盘」却依然安全的原因。

二、synchronous_commit：唯一承诺的落盘点

值语义丢什么
on（默认）提交时等本事务 WAL fsync 完成才返回成功不丢已提交事务
off提交不等 fsync，让后台尽快刷可能丢最近若干毫秒「已提交」的事务
local / remote_apply 等与复制相关（见 P12）取决于复制配置

必须讲清的一点：off 丢的是「已经向客户端返回成功、但 WAL 还没落盘」的那部分——这是唯一一个「数据库告诉成功了却可能丢」的配置。所以：

  • 钱、订单、状态机等路径：必须 on；
  • 批量导入、可重建的埋点数据：可以临时 off 换吞吐，但要在业务层知道这件事，不是"顺手关了"。

三、checkpoint 在做什么

checkpoint 触发
  ↓
把「某个 LSN 之前」的所有脏页刷到磁盘
  ↓
在 WAL 里记一个 checkpoint 记录
  ↓
崩溃恢复时：从最近这个 checkpoint 开始重放 → 而不是从头

所以 checkpoint 的收益是「恢复时间」，不是数据安全。

它带来一个必须知道的副作用——full_page_writes：因为刷盘是「按页」但不是原子的（可能半页写失败），所以 checkpoint 之后对这些页的第一次修改，WAL 里要记整页内容（而不是「某偏移改了某个值」）。后果是：

  • checkpoint 越勤 → 「首写整页」发生得越频繁 → WAL 体积反而更大；
  • 所以「把 checkpoint 调很勤以缩短恢复时间」会用 WAL 写放大和 IO 抖动换恢复速度——这是 PG 调优里一个经典的两难。

四、为什么 PG 只有一套日志（不需要 undo）

MySQL 需要 undo 有两个原因：① 事务回滚；② 给 MVCC 提供旧版本。

PG 两个都不需要日志层面的 undo：

  • 旧版本：PG 的 UPDATE 是「写新版本 + 标记旧版本」（P13），旧版本本来就在堆里，读的时候按快照挑版本，不需要去 undo log 里拼；
  • 回滚：未提交事务的改动在崩溃恢复/回滚时，靠「这个版本的 xmin 属于一个未提交事务」判定为不可见即可，并且由 VACUUM 清掉。

代价：旧版本占用空间、必须靠 VACUUM 回收——于是「PG 没有 undo」这件事，直接解释了三件现象：

1. 为什么 PG 会表膨胀（P14）； 2. 为什么有 VACUUM 与事务 ID 回卷这种 MySQL 不存在的运维风险（P15）； 3. 为什么 长事务在 PG 里格外危险（它按住了快照，让回收停摆）。

这条是整条主线五的入口。

五、生产怎么配（说这段才像做过线上）

① 关键写路径：synchronous_commit = on（默认，别动）
② checkpoint 频率：先看 pg_stat_bgwriter 的 checkpoint 频率与刷盘量，
   再决定是放宽 checkpoint 间隔（减 IO 抖动）还是收紧（减恢复时间）
③ 恢复时间是可测量的：用 checkpoint 位置与 WAL 生成速率估算「最坏要重放多少」
④ 复制场景额外考虑：synchronous_standby_names（P12）

第 ② 步的方法论比结论重要：调 checkpoint 之前先拿 pg_stat_bgwriter 的数据说话，而不是「网上说 checkpoint 要调大」。

流复制和逻辑复制有什么区别？同步 / 异步怎么取舍？

你要 (1) 搭一个只读副本给报表用，(2) 还要把其中几张表的变更同步到另一个系统。这两件事用同一种复制吗？

一句话结论：流复制（物理）复制的是「整个实例的 WAL 字节流」——备库是主库的逐字节副本，只能整实例、备库只读、版本必须一致；逻辑复制复制的是「逻辑变更」——可以按表、可以按行过滤、备端可写、可跨大版本、能做异构与多源汇聚。所以 ① 只读副本用流复制；② 部分表同步到别的系统用逻辑复制。同步 / 异步的取舍本质是 RPO vs 提交延迟。

  • 物理复制（WAL 字节流）vs 逻辑复制（变更流）
  • 表级与行级过滤
  • 跨版本
  • 备库只读 vs 可写
  • 同步提交的 RPO 与延迟
  • **复制槽不消费导致 WAL 堆积**
  • 主从延迟读数不一致

主线：物理复制复制的是「存储的变化」，逻辑复制复制的是「数据的变化」。 所以前者绑定实例与版本，后者绑定表与行——所有能力差异（能不能选择性复制、备端能不能写、能不能跨版本）都是这一句话的推论。

原理分解

一、两种复制：复制的是什么

流复制（物理）逻辑复制
复制内容WAL 字节流（存储层变化）逻辑变更（表的行变更）
粒度整个实例表级（可再按行过滤）
备端只读（热备）可读可写
版本必须一致（含小版本，实践上同大版本内也要谨慎）可跨大版本
用途高可用、只读副本、读写分离CDC、异构同步、多源汇聚、升级迁移
机制WAL 直接传输 + 重放主库从 WAL 逻辑解码成变更流，备端按表应用

一句话对照：流复制让「另一个我」存在；逻辑复制让「我的一部分数据」出现在别处。

二、回到题目

  • (1) 只读副本做报表 → 流复制。它是完整副本、可以在备库上跑长查询（但要注意长查询会阻塞备库上的回放——见下文「主从延迟」）；
  • (2) 几张表的变更同步到别的系统 → 逻辑复制。因为你只需要那几张表、目标端可能版本不同或不是 PG。

数驭穹图的真实选择正好落在这条线上：它需要的是「授权的分析数据集」——不是整个实例，所以走逻辑路径；而且要能跨源、能只同步部分表，物理复制根本做不到。

三、同步 / 异步：本质是 RPO 换延迟

模式语义代价
异步（默认）主库提交不等备库主库宕机可能丢最近一段已提交事务（备库没收到）；备库延迟不稳定
同步主库提交等待备库确认收到（或应用）提交延迟 = 等备库的网络 + 刷盘时间；备库抖动会拖慢主库

判据：能接受丢多少（RPO）就选什么。 但要注意一个陷阱——同步复制会让「备库的可用性」变成「主库可用性」的一部分：备库挂了，主库提交就可能被卡住。所以生产通常配 FIRST 1 (a, b) 这类「至少一个备库确认即可」的写法，而不是「等全部」。

这一条比结论重要：不要简单说「我们用了同步复制保证不丢」——要说清楚「几种确认策略、以及备库故障时主库会怎样」。

四、必须知道的两个坑

坑一：复制槽不消费 → WAL 永久堆积 → 磁盘写满

逻辑复制用复制槽记录消费位点，PG 必须保留位点之后的所有 WAL（否则无法重放给消费者）。所以：

  • 消费者挂了、或者某个备库长期离线 → WAL 只增不减；
  • 结果是磁盘被 WAL 写满，整个实例写不进去——这是 PG 最常见的一类生产事故。

排查：查复制槽的 restart_lsn / confirmed_flush_lsn 与当前 WAL 位置的差距；必须监控「不活跃的复制槽」，并明确「离线多久就该删槽并重建」的运维约定。

坑二：主从延迟不只是网络

延迟有三段：① 主库产出 WAL 的速度 → ② 网络传输 → ③ 备库回放。第 ③ 段最容易被忽略，而它的一个主要来源正是 备库上的长查询/长事务——PG 12+ 之前，备库的查询会与 WAL 回放互相阻塞（现代版本用 hot_standby_feedback / 快照导出缓解，但引入了备库把主库膨胀顶住的副作用）。

业务后果与处理：读写分离下「写主库、读备库」会读到旧数据。处理方式按业务重要性排序：关键读回主库（最可靠）→ 写后一段时间内钉住主库（读己之写）→ 监控延迟并在超阈值时降级。不要用「sleep 一下再读」这种办法。
