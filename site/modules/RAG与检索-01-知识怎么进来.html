G1文档该怎么切？切多大、按什么切、上下文不够怎么办

骨架：先说两个矛盾需求 → 两端各坏在哪（各给一个机制）→ 解耦方案（Child-Parent） → 另一种思路（Contextual Retrieval，给收益与成本的数）→ 按数据结构选策略 → 参数必须靠评测定 → 收束到"拆开两种表示"

一句话结论：切块粒度是一个两头都会坏的问题——太小语义不自足（条款的例外被切走，单块意思可能是反的）；太大相关内容占比下降、相似度被稀释，关键内容排不进 Top-K（2000 字里只有 200 字相关时占比只剩 10%）。所以答案不是某个数字，而是把两个矛盾的需拆开：小块召回（保召回率）+ 父块返回（保上下文完整）——这就是 Child-Parent。另一种思路是不改粒度、改信息：Contextual Retrieval 先给每块补 50–100 token 的定位说明再做索引，索引只涨约 12.5%，实测把检索失败率从 5.7% 降到 2.9%（−49%），再叠加重排是 1.88%（−67%）。切分策略必须按数据结构选（标题 / FAQ / 代码 / 表格 / 条款各有首选），并用目标问题集评测来定参数，不能照搬经验值。

  • 两个矛盾需求（匹配准 vs 语义自足）
  • 太大的机制是稀释（占比 10%）
  • 太小的机制是语义不自足（例外被切走）
  • Child-Parent = 小块召回 + 父块返回
  • 解耦可以推广（重排用小块、索引用补上下文的块）
  • Contextual Retrieval：+50–100 token 定位说明，索引 +12.5%
  • 失败率 5.7% → 3.7% → 2.9% → 1.88%
  • 块越小，上下文增强的相对成本越高（200 token 时涨 50%）
  • 切分按数据结构选，参数靠评测定

G6文档改了、删了、撤权了，索引怎么跟上；怎么保证不返回已失效的内容

骨架：索引是派生数据（三种变化）→ 为什么值得增量（给 99% 的算式）+ 增量的代价 → 删除为什么最难（反查表 + 漏删的性质）→ 派生物两层：索引内 / 索引外，删除和撤权都要清（缓存绕开主链路）→ 删除按内容反查、撤权按主体反查（分区只挡跨主体 + 失效动作 + provenance 回查 + TTL 只是上界）→ 新鲜度可观测（滞后指标 + 展示生效时间 + 冲突显式说明）→ 双写切换模式 → 收束到"删除与撤权是正确性问题"

一句话结论：索引是派生数据，源变了它就必须变——三种变化各自要处理：新增 / 修改走增量链路（只重跑变化的 1%，100 万块每天改 1% 时能省 99% 的嵌入调用）；删除最难，因为要按 doc_id 反查它切出来的全部块（一份文档 100 个块就要清 100 个），漏一个就是"已删内容还能被搜到"的合规事故——而且派生物有索引内、索引外两层，索引外的缓存与派生引用同样要清（缓存绕开主链路，命中一次就把已删内容交出去了；只是反查方向是反的：缓存键是 query，不是 doc_id）；撤权是按主体清——主索引、向量、倒排，以及缓存，因为缓存会绕过 ACL 过滤（有权用户查过的结果会命中给无权用户），所以缓存必须按租户 / 权限分区——但分区只挡跨主体泄漏，同一用户被撤权后键没变、照样命中自己查过的内容，所以分区之外还要有显式的失效动作。新鲜度必须可观测：文档带 effective_at / expires_at / source_version，索引滞后（变更时刻 → 可检索时刻）要是一个被监控的指标，回答要展示规则生效时间，冲突时显式说明版本而不是偷偷选一个。改索引结构（比如换 Embedding 模型）要走双写 / 影子索引再切换——凡是要改正在服务的派生结构，都用"新建 + 双写 + 验证 + 切换"这套动作。

  • 三种变化（新增修改 / 删除 / 撤权）
  • 增量省 99% 嵌入
  • 删除要按 doc_id 反查全部块（漏一个 = 合规事故）
  • 派生物两层：索引内（向量·倒排·元数据）+ 索引外（缓存·派生引用）
  • 删除和撤权都要清索引外
  • 删除按内容反查、撤权按主体反查
  • 缓存绕过 ACL，撤权要连缓存一起清
  • 缓存按租户权限分区，但分区只挡跨主体（同主体撤权后键没变仍命中）
  • 分区是结构、失效是动作
  • 命中缓存后按 provenance 二次校验
  • TTL 是陈旧上界，不是生效保证
  • effective_at · expires_at · source_version
  • 索引滞后 = 变更时刻 → 可检索时刻，要监控
  • 最大滞后 = 任务周期
  • 回答要展示生效时间
  • 冲突时显式说明版本
  • 双写 + 影子索引 + 切换（同影子表方案）
  • 换 Embedding = 全量重嵌入 + 双写

主线："检索用的表示"和"喂给模型的表示"，不必是同一个东西。 一旦这条被认出来，切分粒度的矛盾就消失了——后面所有 RAG 优化用的都是同一个套路（重排用小块、生成用大块；索引用补过上下文的块、展示用原文）。

1. Child-Parent 和 Contextual Retrieval 有什么区别？

一个改"返回什么"，一个改"索引什么"。Child-Parent 索引小块、返回父块；Contextual Retrieval 索引的是"补了定位说明的块"。两者可以叠加，而且叠加后正好覆盖了"匹配准"和"信息全"两个需求。

2. 表格怎么切？

表头与行 / 分组绑定，不能拆掉口径。拆开表头的行是"无意义的数字"——这在企业知识库里是最常见的坏切法之一（指标表、口径表尤其明显）。

3. 多长的块最合适？

没有通用答案。要先用代表性问题集测 Recall 与答案正确性。能给的经验只有方向：制度文档按标题层级（几百字量级）、FAQ 按问答、代码按函数边界、条款按"条件+例外+生效时间"。

4. RAG、微调、长上下文怎么选？

最新 / 私有 / 可引用的知识 → RAG；稳定的行为、格式、领域表达 → 可能微调；小而稳定的知识 → 长上下文可能更简单。通常先用 Prompt / RAG 建 Eval，再判断是否微调。

  • 最大滞后 = 任务周期
  • 回答要展示生效时间
  • 冲突时显式说明版本
  • 双写 + 影子索引 + 切换（同影子表方案）
  • 换 Embedding = 全量重嵌入 + 双写

主线：增量省的是成本，删除与撤权保的是正确性。 前者做不好是"慢"，后者做不好是事故——所以删除传播必须当成一条独立的、可验证的链路，而不是"我调了删除接口"。

1. 知识更新怎么做到增量且不返回失效内容？

Source 事件触发增量解析与索引；新旧索引双轨验证；文档和 chunk 版本化；删除 / 撤权必须传播；回答记录知识版本；支持回滚，并监控索引滞后。 这是 study/03 给的完整清单。

2. 删除与撤权怎么传播？缓存会不会污染？

两层都要清：索引内（删除按 doc_id 反查全部 chunk_id 逐个清向量 + 倒排 + 元数据；撤权改 ACL 字段 / 向量分区）+ 索引外（缓存、派生引用、Agent 记忆）。删除按内容反查（doc_id → 哪些缓存条目引用了它），撤权按主体反查（user / tenant → 他能命中哪些）。缓存会绕过 ACL 过滤——所以缓存按租户 / 权限分区不是优化，是权限模型的一部分；但分区只挡跨主体，同主体撤权后键没变仍会命中，所以还要显式失效，兜底是命中后按 provenance 回查有效性。

3. 索引滞后多少算正常？

取决于业务承诺：如果承诺"规则修改 10 分钟内生效"，那任务周期取 5 分钟（2 倍余量）就是合理的；滞后指标超过承诺时限就是故障。关键是它必须是个指标，不是"大概几分钟"。

4. 换 Embedding 模型要注意什么？

新旧向量不可比，必须全量重嵌入；不能原地替换（没有回滚路径），要走双写 + 影子索引 + 验证 + 切换；切换期间要双写，成本要提前规划。

5. 冲突的文档怎么处理？

优先权威级别和最新生效版本，并显式说明——不要偷偷选一个，否则用户会以为那是唯一的答案（[[母题-G4-引用绑定与证据可追溯]]）。
