redo / undo / binlog 各管什么？两阶段提交为什么必要？

用户下单，接口返回「提交成功」。一秒后机器断电。重启后，这条订单还在吗？为什么？

一句话结论：三条日志各管一件事——undo 管回滚和 MVCC 旧版本（前镜像），redo 管崩溃恢复（后镜像、物理、循环写），binlog 管复制与时间点恢复（逻辑、追加写、Server 层）。用 WAL 把"随机写数据页"换成"顺序写日志"，同时拿到性能和崩溃安全性。而两阶段提交存在的唯一理由，是让 redo 和 binlog 逻辑一致——不做的话，两个崩溃窗口分别造出"主库多从库少"和"从库多主库少"。

  • WAL 换掉随机写
  • 顺序 vs 随机差 2–3 个数量级
  • undo 前镜像
  • redo 后台镜像·循环写
  • binlog 逻辑·追加写·Server 层
  • redo 用完即弃所以循环，binlog 长期保留所以追加
  • write pos 追上 check point = 写入卡顿
  • 先刷页再推 check point
  • 双一
  • prepare → binlog → commit
  • 崩溃窗口 = 主从不一致
  • binlog 是否完整 = 唯一裁决依据

主线："安全"的标志不是"数据在磁盘上"，而是"修改这件事已经落盘了"。 数据库用"顺序写日志"换掉"随机写数据页"——这一步同时给出了性能（顺序 vs 随机的量级差）和崩溃恢复能力（WAL）。而只要有两份日志，就必然需要一次裁决（2PC）。

1. redo 循环写，为什么不怕覆盖掉还没刷盘的日志？

check point 只在脏页真正刷盘后才前移；write pos 追上 check point 时必须停下来先刷脏页。顺序是"先刷页 → 再推 check point → 才释放空间"，不能反过来。

2. innodb_flush_log_at_trx_commit 设 0/2 能换多少性能？

必须拿压测数据说话，不能凭感觉。 SDD 时代 fsync 成本下降，1 与 2 的差距远小于机械盘时代，所以现在更多是直接上"双一"。这是"按业务定口径"而不是"按性能定口径"。

3. binlog 有哪几种格式？生产用哪个？

Statement / Row / Mixed；现在主流是 Row（数据安全优先），Statement 只在日志体积敏感且 SQL 确定时才考虑。

4. redo log 是无限增长的吗？

不是。固定大小循环写，边界靠 check point 推进。

M12崩溃重启后 MySQL 怎么恢复数据；为什么不会丢已提交、也不会重复回滚草稿 · 待验收单卡 →

崩溃重启后 MySQL 怎么恢复数据？为什么不会丢已提交的、也不会错回滚？

数据库在「事务提交到一半」时断电。重启后它怎么知道哪些事务该重做、哪些该回滚？会不会把已经提交的又回滚掉？

一句话结论：恢复 = redo 重放 + undo 回滚。重启后从 check point 起顺序重放 redo（每页自带 LSN，已落盘的直接跳过，所以重放幂等），把已提交的事务补上；再用 undo 把未提交的撤销。提交到一半（prepare）的事务由 binlog 的完整性裁决——binlog 完整就提交，不完整就回滚。顺序不能反：必须先 redo 再 undo。

  • 崩溃时只有三种状态
  • 已提交的页也可能还在内存
  • 动作由日志状态决定、不靠猜
  • 幂等 = 做之前能判断是否已做过
  • 页 LSN 比较
  • prepare 靠 binlog 裁决
  • 先 redo 后 undo
  • check point 位置决定恢复时长（且与写入性能是同一组参数的两面）
  • 双一

主线：恢复的正确性不靠"猜"，靠"日志状态"。 每个事务在崩溃瞬间只有三种可能——没开始、已提交、提交到一半。前两种由日志标记无歧义地确定，第三种由两阶段提交给出的裁决规则唯一确定。

1. 恢复要重放多久？

取决于 check point 的位置。它越新，要重放的越少、恢复越快；但推进它需要更频繁刷脏页，代价是正常运行时更多的随机 IO。同一组参数的两面。

2. 恢复途中又崩了怎么办？

没关系。重放按页 LSN 跳过已应用的，是幂等的，重启后从最新 check point 继续。不怕反复崩，怕重放不幂等。

3. 为什么不会重复执行已提交的事务？

数据页自带 LSN，重放前先比较，已落盘的直接跳过。

4. 主从不一致是怎么被崩溃窗口造出来的？

不做 2PC 时的两个反向窗口：redo 写完 binlog 没写就崩 → 主库有从库没有；binlog 写完 redo 没写就崩 → 从库有主库没有（M11）。
