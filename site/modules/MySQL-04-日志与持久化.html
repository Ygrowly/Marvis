M11redo / undo / binlog 各管什么；两阶段提交为什么必要草稿 · 待验收

redo / undo / binlog 各管什么？两阶段提交为什么必要？

用户下单，接口返回「提交成功」。一秒后机器断电。重启后，这条订单还在吗？为什么？

一句话结论：三条日志各管一件事——undo 管回滚 + MVCC 旧版本，redo 管崩溃恢复（保证已提交不丢），binlog 管复制与时间点恢复；而两阶段提交存在的唯一理由，是让 redo 和 binlog 在逻辑上绝对一致——否则崩溃时会造出「主库有、从库没有」或「从库有、主库没有」的数据。

  • WAL 日志先行
  • undo 回滚
  • redo 循环写 + checkpoint
  • binlog 追加写
  • prepare → commit
  • 逻辑一致

主线：先写日志，再写数据页（WAL）。 只要「修改这件事」已经顺序落盘，内存里的修改就是安全的——数据库用「顺序写日志」换掉了「随机写数据页」，这是所有崩溃恢复能力的地基。

原理分解

一、为什么需要 WAL（Write-Ahead Logging）

修改数据时不直接改磁盘数据页（随机 IO 太慢），而是：

改内存（Buffer Pool）→ 把"改了什么"顺序写入 redo log → 提交时保证 redo 落盘

只要 redo 落盘成功，这次修改就是安全的——即使数据页还没刷回磁盘时崩溃，重启后也能用 redo 把它重放回来。用顺序写换随机写，同时拿到崩溃安全性，这是 WAL 的全部价值。

二、三日志分工（必须能一句话说清）

日志所属层记录什么物理特性核心职责
undo logInnoDB数据修改前的旧值—回滚 + 给 MVCC 提供旧版本
redo logInnoDB数据页的物理修改（"某页某偏移写成什么"）固定大小、循环写，会覆盖崩溃恢复（持久性）
binlogServer 层逻辑操作（SQL / 行变更前后镜像）追加写，写满切新文件，不覆盖主从复制 + 时间点恢复

放到工单/订单系统里最好记：

  • 状态更新失败要能撤销 → undo
  • 更新成功但机器崩了不能丢 → redo
  • 主从同步和备份恢复 → binlog

一条高价值追问：「binlog 能不能单独保证 crash-safe？」——不能。它不在 InnoDB 内部，写入时机与 redo 不同步；单独依赖它，崩溃时会不一致。它必须靠两阶段提交与 redo 配合。

三、redo 的环形结构与刷盘参数

redo 文件是固定大小、循环写的环形，两个指针：

  • write pos：当前写到哪。
  • check point：已经刷盘（脏页已落盘）的位置之后一格。

write pos → check point 之间是空闲区（可写新日志）；check point → write pos 之间是待刷盘的记录，如果不刷就会被新记录覆盖。危险场景就是「write pos 追上 check point」——此时必须停下来刷脏页，表现为写入卡顿。

刷盘时机由 innodb_flush_log_at_trx_commit 控制：

值行为代价
1（默认）每次提交都 fsync 落盘最安全，最慢
0提交只写内存 buffer，后台每秒刷最快，掉电丢最近 1 秒事务
2提交写入 OS 缓存，不立刻 fsync进程崩不丢，整机掉电会丢

binlog 侧对应 sync_binlog：0 = 交给系统决定；N = 每 N 个事务刷一次；1 = 每次提交刷。生产要金融级一致就是 flush_log_at_trx_commit=1 + sync_binlog=1，代价是吞吐下降。

四、binlog 的三种格式

格式记什么优点风险
Statement原始 SQL 语句日志小含 UUID() / NOW() 等非确定函数会导致主从漂移
Row每行修改前后的具体内容复制绝对精确日志量大（批量 UPDATE 会暴涨）
Mixed自动判断，安全用 Statement、危险切 Row平衡判断逻辑需要理解

五、两阶段提交：为什么非它不可

提交分两步：

① 准备（Prepare）：InnoDB 写完 redo log，但状态标记为 prepare，不提交
② 提交（Commit）：执行器写 binlog → binlog 落盘成功 → 通知 InnoDB 把 redo 改成 commit

如果不这么做，两种顺序各有一个后果：

顺序崩溃点结果
先写 redo，再写 binlogredo 写完、binlog 没写就崩重启后 redo 重放 → 主库有这次更新；binlog 没有 → 从库没有，主从多了/少了一次更新
先写 binlog，再写 redobinlog 写完、redo 没写就崩InnoDB 认为事务未提交 → 主库回滚；binlog 已记录 → 从库执行了，从库多出一次主库不存在的更新

一句话收口：两阶段提交把两份日志「捆绑」成原子操作，要么都成功，要么都失败——这就是它唯一的存在理由。

M12崩溃重启后 MySQL 怎么恢复数据；为什么不会丢已提交、也不会重复回滚草稿 · 待验收

崩溃重启后 MySQL 怎么恢复数据？为什么不会丢已提交的、也不会错回滚？

数据库在「事务提交到一半」时断电。重启后它怎么知道哪些事务该重做、哪些该回滚？会不会把已经提交的又回滚掉？

一句话结论：恢复 = redo 重放 + undo 回滚：重启后从 check point 起把 redo 顺序重放（已落盘的页按 LSN 跳过，所以重放幂等），把已提交的事务补上；再用 undo 把未提交的事务回滚掉。判据来自两阶段提交留下的状态——redo 是 prepare 且 binlog 完整 → 提交；binlog 不完整 → 回滚。

  • redo 重放幂等
  • LSN 比较
  • undo 回滚未提交
  • prepare 状态判据
  • binlog 完整性
  • 双一配置

主线：恢复的正确性不靠"猜",靠"日志状态"。每一个事务在崩溃瞬间都只有三种可能——还没开始、已经提交、提交到一半（prepare）。规范状态机让前两种无歧义，第三种由两阶段提交给出唯一裁决。

原理分解

一、崩溃瞬间，一个事务只有三种状态

崩溃时的状态数据页日志恢复动作
还没提交可能已改内存redo 里没有 commit / binlog 没写undo 回滚
已经提交可能还没落盘redo 已 commit、binlog 已完整redo 重放补上
提交到一半不确定redo 是 prepare，binlog 可能完整也可能不完整看 binlog 裁决 ← 这题的题眼

所以恢复算法只回答三件事：哪些该重做？哪些该回滚？怎么保证重做不会做两遍？

二、redo 重放：为什么重放两次也不会出错

redo 记录的是「某数据页某偏移被改成了什么值」，而且每个数据页头部都存着自己的 LSN（日志序列号）。

重放一条 redo 前：比较 页的 LSN 与 该条 redo 的 LSN
  页.LSN >= redo.LSN  →  这条改动已经落盘了，跳过
  页.LSN <  redo.LSN  →  需要应用，把它写进内存页

这就是重放幂等的来源——不是靠"只做一次"的锁，而是靠"已经做过就认得出"的状态标记。恢复中断后再次重启，可以继续从断点重放，不会重复应用。

这个思路值得迁移到任何重放系统里：幂等不是"不去做"，是"做之前能判断是否已做过"。 RuleArena 里的 ActionReceipt 就是这个模式在业务层的翻版。

三、undo 回滚未提交的事务

redo 重放结束后，内存里已经包含了「已提交」和「提交到一半但还没裁决」的修改。此时：

  • 已提交 → 保留（就是它该在的状态）。
  • 未提交 → 用 undo log 把改动反向撤销，恢复成修改前的样子。

注意顺序：一定是先 redo 重放、再 undo 回滚。反过来会在「提交了但数据页未落盘」的场景里丢数据。

四、题眼：prepare 状态怎么裁决（两阶段提交的收尾）

redo 里状态是 prepare 的事务，InnoDB 自己无法判断该提交还是回滚——因为决定权在 binlog：

redo = prepare
   ├─ binlog 完整（该事务的 binlog 记录已写完，可校验）
   │     → 事务视为成功，把 redo 改成 commit，数据保留
   └─ binlog 不完整 / 不存在
         → 事务视为失败，用 undo 回滚

为什么这么判？ 因为两阶段提交的顺序是「写 redo（prepare）→ 写 binlog → 改 redo 为 commit」。所以：

  • binlog 完整 = 第二步成功了 = 这个事务对外已经宣布过成功，必须让它生效（否则从库执行了、主库却没有）。
  • binlog 不完整 = 第二步没成功 = 这个事务从未对外宣布，必须回滚（否则主库有效、从库却没有）。

这就是「崩溃恢复」和「主从一致性」在同一个机制上收口的地方——不是两套逻辑，是一套。

五、生产配置：为什么主库都配「双一」

参数值作用
innodb_flush_log_at_trx_commit1每次提交 fsync redo
sync_binlog1每次提交 fsync binlog

两个都为 1 时，事务的"提交成功"才算真的落到磁盘——这才是接口返回「提交成功」后断电也不丢的前提。只配一个会出现：redo 保证了主库恢复，但 binlog 丢了 → 从库缺数据；或者反过来。

面试追问「这样不是更慢吗？」→ 是，但可以先给出代价量化（吞吐下降幅度要靠压测），再说取舍标准：涉及钱的写路径不省这个 fsync；能容忍丢最近 1 秒的场景（埋点、日志类）才降到 2 或 0。这是"按业务定口径"，不是"按性能定口径"。
