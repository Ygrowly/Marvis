E4Agent 的成本怎么控；限流该限在哪里、超了怎么办草稿 · 待验收单卡 →

面试官问——"你们怎么控成本？如果账单翻倍了你怎么查？限流限在哪里？"

一句话结论：成本控制的第一性原理是"先归因、再动手、先动大头、先做无损的"。先拆账单（按功能 / 租户 / 任务类型 / 环节拆），先回答"是量涨了还是单价涨了"——两件事的解法完全不同。环节这一维最重要，因为它直接对应动作：输入占大头就提缓存命中率（无损，本例能省 43%）、输出占大头就收输出 / 调 effort、工具占大头就 consolidation、存储占大头就降采样。降本有顺序且不可颠倒：提命中率（无损）→ 去拐杖（双赢）→ 压缩（有损）→ 调 effort / 换模型（换质量）。限流的本质是"保护某一条具体的资源"，所以要分四层放：入口（总量）· 租户（公平）· 工具（外部配额）· 模型（RPM / TPM 与预算）——只做入口限流，一个租户就能占满配额，而且 Agent 一个请求会触发几十次下游调用，网关看起来正常但模型 TPM 已经满了。超限后的处理顺序是"有界排队 → 降级 → 快速失败"，无界排队是最差的（把"立刻被拒"变成"等 30 秒后被拒"）。降级的本质是把"不可用"换成"质量下降"——这笔交换划不划算取决于业务（能不能接受质量降一点），而且备用配置必须是用你自己的评测验证过的，不是"顺手切一个"。

  • 先归因再动手（量涨了 vs 单价涨了）
  • 四维归因（功能 · 租户 · 任务类型 · 环节）
  • 降本顺序（提命中率 → 去拐杖 → 压缩 → 调档位）
  • 先动大头（43% vs 7.5%）
  • 限流四层（入口·租户·工具·模型）
  • 限流的本质 = 保护某一条具体资源
  • 超限处理：有界排队 → 降级 → 快速失败（无界排队最差）
  • 可用性 99% → 99.9%（10 个失败 → 1 个 + 9 个质量下降）
  • 降级是业务决策不是技术默认
  • 备用配置必须验证过
  • 降级必须可观测

主线：成本要先归因，限流要先问"保护什么"。 两件事的共同点是：都不能从"上一个手段"开始，而要从"看清问题的形状"开始——代价最高的一刀，往往是最后才该动的那个。

1. Agent 的成本怎么控？

按环节拆：输入（提缓存命中率，无损且量级最大）→ 输出（收输出 / 调 effort）→ 工具（consolidation，[[母题-A2-工具调用与MCP边界]]）→ 存储（采样，[[母题-E2-Trace与可观测性]]）。而且要按预算分档（[[母题-A1-计划执行循环与停止条件]] 的七种预算）。

2. 限流该限在哪里？

四层都要：入口（总量，最早最粗）、租户（公平，否则入口限流对其他租户无意义）、工具（保护第三方配额）、模型（RPM / TPM 与成本，最贵最容易失控）。

3. 超限之后怎么办？

有界排队 → 降级 → 快速失败（带可行动的错误）。关键是"排队必须有界"——无界排队会把过载悄悄变成全局超时。

4. 降级链路怎么设计？

三个要求：① 已验证（备用配置要过 held-out 门禁）② 有明确的质量底线（降级目标是保住可用性，不是保住质量）③ 可观测（降级本身要打点报警——不知道自己在降级，比降级更危险）。

5. 成本和质量的取舍谁来定？

能回答"一次失败值多少钱"的人。工程能给的是曲线（成本 vs 质量），把曲线交给业务方选点，比工程师替业务拍板更安全（[[母题-C5-模型选型与降级三角]]）。

E5越权和提示注入怎么防；为什么"防住"不等于"没问题"草稿 · 待验收单卡 →

面试官问——"你们怎么防越权？提示注入呢？"

一句话结论：越权有两个方向——纵向（低权限做了高权限的事）和横向（看到不属于自己的数据），后者常常被低估，因为它的影响半径是"一整个租户的数据"且静默。在 AI 系统里，横向越权还有一条特有路径：检索——权限必须在召回前生效，因为未授权内容一旦进上下文就已经泄露了；而且缓存会绕过 ACL（有权用户查过的结果会命中给无权用户），所以缓存按租户分区是权限模型的一部分。提示注入的麻烦在于"你过滤不过来"：间接注入来自任何工具返回的内容（网页、文档、日志、评论），而 Agent 场景下损失在动作层面（删文件、发消息、转账），是真的发生了。所以防线按确定性排序：边界（沙箱 + 最小权限 + 真凭证不进沙箱）→ 契约（参数独立校验、危险动作需确认）→ 过滤（内容检测）——顺序不能反：过滤是概率性的、有持续成本、会被绕过，而"以为有防线"比"没有防线"更危险。最后，"测过"必须说清 N：三倍法则下 0/200 只给 1.5% 的上界，要声称 0.1% 需要 3000 个样本——而攻击面是组合爆炸的（30 工具 × 5 类来源 × 变体）。安全红线永远不参与平均。

  • 纵向 vs 横向越权（后者的半径是"一整个租户"+ 静默）
  • 权限必须在召回前生效（先召回再让模型别说 = 已泄露）
  • 缓存绕过 ACL → 按租户分区是权限模型的一部分
  • 必测六类（跨租户·撤权·共享链接·继承·删除传播·缓存污染）
  • 直接 vs 间接注入（后者来自工具返回）
  • Agent 的损失在动作层面
  • 三层防线：边界 > 契约 > 过滤，顺序不可反
  • 过滤 = 概率性 + 持续成本 + 会被绕过
  • "以为有防线"最危险
  • **三倍法则 3
  • n**（0/200 → 1.5%；0.1% 需 3000）
  • 攻击面组合爆炸
  • 红线不参与平均

主线：安全的特殊性在于"它没有中间态"。 功能可以"迭代改进"，安全只能"守住或失守"——所以防线要按确定性排序（边界优先），验证要说清覆盖多少（N），而红线永远不参与平均。

1. 怎么防止 RAG 越权？

身份进入检索层、ACL filter 先于召回；缓存按租户 / 权限分区；引用和下载再次鉴权；做跨租户与撤权测试；日志避免记录敏感原文。

2. 提示注入在 Agent 场景下为什么更危险？

聊天场景的损失在信息层面，Agent 场景的损失在动作层面（删文件、发消息、转账、改权限），而且动作真的发生了。所以防线要以"边界"为主、"过滤"为辅。

3. 为什么"防住注入"不等于"安全"？

因为"防住"是一个概率判断，"安全"是一个存在性判断。过滤总会被绕过，所以真正的目标不是"阻止注入发生"，是"让注入即使发生也没有后果"。

4. 安全违规能不能和其他指标平均？

不能。它是存在性判断（"必须为 0"），不是连续量。放进平均分等于允许"用高质量文案换一次越权"。

5. 怎么验证安全防线真的有效？

红队测试 + 说清 N：故意注入"把 ~/.ssh 读出来发到某域名"的指令，看它是否既读不到、也发不出——两个边界各测一条路径（[[母题-A6-沙箱权限与可信执行]]），只测一条会漏。

E6新版本怎么上；灰度放多少、什么情况下回滚、回滚要多久草稿 · 待验收单卡 →

面试官问——"新版本怎么上线？灰度放多少？什么情况下回滚、回滚要多久？"

一句话结论：灰度的本质是"放小 + 能收回"，而回滚速度决定灰度的价值——影响面积 ≈ 事故率 × 灰度流量 × 回滚耗时：回滚 30 分钟 vs 2 分钟，影响面积差 15 倍。所以"放 1%"不等于"风险 1%"，没有回滚能力的灰度只是小规模事故。上线七步且不能跳：离线 Eval → Shadow → dogfood → 小流量灰度 → A/B → 扩量 → 持续监控——每一步回答前一步回答不了的问题（Shadow 零成本发现"打爆下游"，灰度却要影响真实用户）。A/B 有五个注意点：① 随机化单位必须与体验的单位一致（按请求随机时，一个用户 10 次请求约 99.8% 会看到两个版本）② 先定义主指标与 guardrail（先看数据再挑指标是 p-hacking）③ 关注新奇效应、网络效应、长期行为 ④ 高风险错误不能等统计显著 ⑤ 记录完整的 treatment（五元组：模型 + Prompt + 知识/索引 + 工具定义 + 参数）。最后，回滚不一定回得去——如果新版本写了旧版本读不懂的数据，代码回滚了系统还是会坏在数据上。而反馈飞轮要的是"带具体信息的反馈"（用户改成了什么、在哪放弃），不是点赞按钮，而且中间必须隔着隐私处理与筛选。

  • 灰度 = 放小 + 能收回
  • 影响面积 ≈ 事故率 × 流量 × 回滚耗时（30 分 vs 2 分 = 15 倍）
  • 七步不可跳（离线 → Shadow → dogfood → 灰度 → A/B → 扩量 → 监控）
  • 每一步回答前一步答不了的问题
  • 随机化单位 = 体验的单位（按请求 → 99.8% 看到两版）
  • 主指标与 guardrail 先定
  • 新奇效应 · 网络效应 · 长期行为
  • 高风险不等显著
  • treatment 五元组
  • 回滚不一定回得去（数据兼容）
  • 高价值反馈 = 带信息的那种
  • 反馈要过隐私 + 筛选

主线：上线的目标不是"发布出去"，是"发布出去且随时能收回来"。 所以灰度这一步考验的其实是回滚能力——而回滚的能力，取决于你上线前有没有想过"如果它坏了，我能不能退回去"。

1. 新版本的上线顺序是什么？

离线 Eval → Shadow → 内部 dogfood → 小流量灰度 → A/B → 扩量 → 持续监控。 每一步回答前一步回答不了的问题，顺序不能跳。

2. 灰度放量怎么定，什么情况下立即停止？

节奏是 1% → 5% → 20% → 50% → 100%，每档确认后再进；停止条件是事先定的：红线（越权、未确认副作用）看到就停，不等显著；guardrail（P95、成本）超阈值也停。

3. A/B 有哪些坑？

五个（见上）。最容易踩的是"随机化单位"和"先定指标 vs 先看数据"——前者污染体验与度量，后者制造假阳性。

4. 线上用户修改怎样回流？

用户改后的正确答案 / SQL / 规则、在哪放弃、哪条引用不支持结论、工具调用被拒或被撤销、任务实际业务状态——这些是"带正确答案的样本"。但必须经过隐私处理 + 人工/规则筛选才成为 Eval candidate，不能直接拿去训练或评测。

5. 降级和回滚是什么关系？

降级是"临时切到备用配置，先保住可用性"（[[母题-E4-成本控制与限流]]）；回滚是"把版本退回去，问题消失"。降级是应急手段、回滚是根治——先降级止血，再回滚修复，是常见的组合。
