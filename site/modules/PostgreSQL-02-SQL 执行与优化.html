主线：计划里的错误几乎总是先出现在「估计行数」上。 所以看计划的第一动作永远是比对估计与实际——偏差大的那个节点，就是问题所在节点，不需要通读整棵树。

1. 为什么估计会差那么多？

三类原因：统计信息过期、列之间有关联但统计是独立的（「城市=北京」和「区=海淀」相乘会把行数估得极小）、条件是表达式或函数导致无法估算。对应三种修法见 [[母题-P7-统计信息与慢查询定位]]。答这题要说「优化器不是猜的，它是按你给的统计算的」。

2. EXPLAIN ANALYZE 会不会本身改变行为？

会。 ① 它真的执行，所以有副作用风险；② ANALYZE 会强制用真实参数生成计划，而真实运行可能用的是预编译的通用计划——所以「EXPLAIN ANALYZE 里很快、线上很慢」是可能发生的。这条能把两个母题串起来。③ 官方还提醒：ANALYZE 用随机采样估统计，重跑一次 ANALYZE 后 cost 估算可能变化，即使数据分布没变。

3. Seq Scan 一定比 Index Scan 慢吗？

不一定。 命中比例高时顺序读整表比「索引 + 大量随机回表」更快。能说出「Seq Scan 也是一种正确选择」，就脱离了「索引崇拜」。

4. 怎么对比两个计划的优劣？

看实际耗时与 Buffers，而不是「估算代价」；估算代价只能用于同结构比较。要 ANALYZE 真跑、固定参数、跑多次取稳定值。

5. Bitmap Heap Scan 后面接 Sort 说明什么？

说明索引没有提供所需顺序（它按物理顺序读堆），所以还得排一次。要排序就应该考虑让索引顺序直接匹配 ORDER BY。

主线：优化器不是在猜，它是在拿统计信息算代价。 所以「计划不对」的排查顺序永远是：先问信息对不对，再问 SQL 形状对不对，最后才问索引够不够。

1. CREATE STATISTICS 具体解决什么？

解决「多列相关」。典型场景：city 和 district（海淀一定在北京，两列强相关）、status 和 deleted_at（删掉的行不再是活跃态）。优化器原本假设独立相乘，扩展统计给它真实的联合分布。 官方提醒：mcv 统计只建在【实际会一起出现在条件里】的列组合上，否则只是浪费 ANALYZE 与规划时间。

2. 统计信息准了，计划还是差怎么办？

那就不是信息层的问题：要么是 SQL 形状让优化器没有好选项（比如为了复用而写了一个过度参数化的语句 → generic plan），要么是代价模型对当前硬件不准（IO 与 CPU 的相对代价随 SSD/内存变化）。此时可以考虑：改写 SQL、用 CTE 的物化提示控制形状、或（谨慎地）调代价参数。但默认先怀疑前两层——改代价参数是最容易掩盖问题的一步。

3. ANALYZE 和 VACUUM ANALYZE 有什么区别？

VACUUM 回收空间（[[母题-P15-VACUUM与事务ID回卷]]），ANALYZE 只更新统计信息；VACUUM ANALYZE 是顺带一起做。autovacuum 默认两个都做，但两者的触发阈值是独立的——所以「表一直在被 VACUUM」不代表「统计信息是新的」。

4. pg_stat_statements 能不能看出 N+1？

能：同一形状的语句 calls 极高、每次 rows 很小，就说明应用在循环里查数据库。这是从数据库侧发现应用问题的有效手段。

5. 只读副本上的统计信息要不要管？

要。统计信息不是复制的对象里的"数据"，它是每台实例各自 ANALYZE 出来的——只读副本如果从不分析，它的计划可能和主库完全不一样（[[母题-P12-流复制与逻辑复制]]）。这一条说出来，说明你运维过真实的主从。

偏差来自三类原因：统计信息过期、列之间有关联但统计假设独立、条件是表达式或函数。对应三种修法：ANALYZE（或调 autovacuum 的 analyze 阈值）、CREATE STATISTICS 建扩展统计（把列间关联告诉规划器）、建表达式索引或改写 SQL。

分层要点追问深挖时用

  • 结论：三类偏差对应三种修法；先按总耗时排优先级，再对单条用 ANALYZE+BUFFERS。
  • 推导链：估算偏差 → 过期/关联/表达式 → 三种修法 → pg_stat_statements 排序 → 单条深挖。
  • 量化：排序口径是"总耗时 = 单次耗时 × 调用次数"。
  • 边界与常见误解：只看"单次最慢"会治错对象；扩展统计是 PG 比 MySQL 多出来的一类修法。
