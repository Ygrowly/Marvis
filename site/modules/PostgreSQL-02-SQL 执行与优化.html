EXPLAIN 和 EXPLAIN ANALYZE 的区别是什么？看计划应该按什么顺序看？

同一条 SQL，开发环境 50ms，线上 8s。你怎么用执行计划找出差别在哪，而不是靠猜？

一句话结论：EXPLAIN 只给估算（估计行数、估算代价），EXPLAIN ANALYZE 会真的执行并给出实际行数、实际耗时、循环次数、排序/哈希有没有落盘；看计划有固定顺序——先看「估计 vs 实际行数」的偏差，再看扫描方式是否合理，再看 JOIN 算法与两侧规模，再看 Sort/Hash 有没有落盘，最后看 loops 有没有暴露 N+1。

  • 估算 vs 实测
  • rows vs actual rows
  • loops
  • Buffers
  • Sort Method external merge
  • Bitmap Heap Scan
  • Nested Loop 与 Hash Join
  • BUFFERS 选项

主线：计划里的错误几乎总是先出现在「估计行数」上。 所以看计划的第一动作永远是比对估计与实际——偏差大的那个节点，就是问题所在节点，不需要通读整棵树。

原理分解

一、EXPLAIN vs EXPLAIN ANALYZE

EXPLAINEXPLAIN ANALYZE
是否执行不执行，只规划真的执行
给什么估算行数、估算代价、算法选择实际行数、实际耗时、循环次数、内存/磁盘使用
风险无会真的写数据（写语句要放事务里回滚）
常用组合EXPLAINEXPLAIN (ANALYZE, BUFFERS)

BUFFERS 是必须加的：它告诉你这次访问命中了多少缓存页、读了多少磁盘页——没有它，你分不清「慢」是算法差还是缓存冷。

写语句的注意：EXPLAIN ANALYZE UPDATE ... 会真的更新。惯例是

BEGIN;
EXPLAIN (ANALYZE, BUFFERS) UPDATE ...;
ROLLBACK;

二、看计划的五步顺序

第一看：估计行数 vs 实际行数（最重要）

rows=1000  ...  (actual time=... rows=12 loops=1)

差一个数量级以上就说明统计信息或相关性有问题（→ P7）。这一步定了，后面的判断才有意义——因为选择哪种扫描/连接算法，本身就是优化器根据估算行数算出来的。

第二看：扫描方式是否合理

节点什么时候该出现
Seq Scan命中比例高（比如要取 20% 以上的行）或表很小——这是正常的，不要一看到 Seq Scan 就想优化
Index Scan命中行数少、走索引比全表便宜
Bitmap Heap Scan命中中等行数：先用索引把符合条件的页收集成位图、按物理顺序批量读堆——它出现说明优化器判断「随机回表太贵、全表扫又太浪费」，这是很有价值的信号
Index Only Scan见 P2——必须同时看 Heap Fetches 是不是 0
Subquery Scan / 子查询被优化掉说明优化器改了形状，要确认改对了

第三看：JOIN 算法与两侧规模

  • Nested Loop：外层小、内层走索引——如果外层实际行数远大于估算，它就从「几万次循环」变成「几百万次循环」，这是最常见的爆炸点；
  • Hash Join：两侧都不小、需要等值连接；看哈希表有没有落盘；
  • Merge Join：两侧都有序。

第四看：Sort / Hash 有没有落盘

Sort Method: external merge  Disk: 24576kB

看到 external merge 就意味着排序溢到磁盘了——通常说明 work_mem 太小，或者排序的数据量本来就该在上游减掉。

第五看：loops 有没有暴露 N+1

loops=10000 配一个内层节点，就是 N+1 的执行计划形态（对应 EnergyOps 里的 N+1 问题）。

三、回到那个真实例子

EnergyOps「优化前 20 多秒」那条查询链路，按这五步看会得到什么：

1. 估计 vs 实际：JOIN 之后中间结果远大于估计 → 优化器选错了后续算法； 2. 扫描方式：先展开全部归属再过滤园区 → 大表 Seq Scan + 位图回表； 3. JOIN 规模：归属关系一对多未限有效期 → 中间行被放大； 4. 排序/哈希：聚合排序落盘； 5. loops：应用侧还有 N+1（1+100 次往返）。

这五条恰好对应「先修范围与 JOIN、再建索引、再消 N+1」的优化顺序——计划不是用来「看一眼」的，是用来给优化动作排优先级的。

P7估计行数与实际行数差很多说明什么；怎么修草稿 · 待验收单卡 →

估计行数与实际行数差很多说明什么？怎么修？线上的慢查询怎么第一时间定位？

优化器把「只返回 10 行」的条件估成了 100 万行，于是选了 Seq Scan。你要不要直接加个索引？

一句话结论：偏差来自三类原因——统计信息过期、列之间有关联但统计假设独立、条件是表达式或函数；对应三种修法——ANALYZE（或调 autovacuum 的 analyze 阈值）、CREATE STATISTICS 建扩展统计、把表达式抽成索引或改写 SQL。定位慢查询的第一站是 pg_stat_statements（按总耗时排序，先治「最贵的」），再对单条用 EXPLAIN (ANALYZE, BUFFERS)。

  • ANALYZE
  • autovacuum analyze
  • n_distinct 与 MCV
  • 列相关性
  • CREATE STATISTICS
  • 表达式与函数
  • generic plan 陷阱

主线：优化器不是在猜，它是在拿统计信息算代价。 所以「计划不对」的排查顺序永远是：先问信息对不对，再问 SQL 形状对不对，最后才问索引够不够。

原理分解

一、统计信息从哪来、估什么

PG 的 autovacuum 进程顺带做 ANALYZE，采样表的一部分行，记录每个列的：

  • n_distinct：不同值大约有多少个；
  • MCV（most common values）：出现频率最高的若干个值和它们的频率（用来处理数据倾斜）；
  • 直方图：其余值的分布。

优化器拿这些数字相乘得到组合条件的行数估计。乘法就埋下了第一个大坑：它假设列之间相互独立。

二、偏差的三类原因与三种修法

#原因表现修法
1统计信息过期刚导入大批数据、刚大批删除后，估算明显偏离ANALYZE 该表；把 autovacuum 的 analyze 阈值调低（大表默认阈值往往触发太晚）
2列间相关一个条件估得挺准，两个条件一乘就错得离谱CREATE STATISTICS 建扩展统计（多列相关性 / 多列 n_distinct），让优化器知道它们不独立
3表达式 / 函数WHERE lower(name) = ?、WHERE date(created_at) = ? 这类条件几乎无法估算建表达式索引（P3）让条件变成可按索引估算，或改写 SQL 去掉函数

第 2 类最容易被忽略：单列统计都是准的，所以「统计信息没错啊」——但优化器把两个独立假设乘起来，结果差三个数量级。被判据就是：单列条件各自估得准、组合条件估得错，就是相关性问题。

三、定位慢查询：先排序，再看单条

第一站 pg_stat_statements（需要启用扩展）。它把 SQL 按「归一化后的语句」聚合，关键列：

列用途
total_exec_time按总耗时排序——先治最贵的（一条慢但很少跑的 SQL，往往不如一条中等但每秒跑一万次的重要）
calls调用次数
mean_exec_time / p99平均与尾延迟
rows返回行数总量
shared_blks_read / hit区分「算得慢」和「读得多」

这一步的核心判断是「按总耗时排，而不是按单次耗时排」。 优化资源应该给「总成本最高」的语句。

第二站：对选中的语句跑 EXPLAIN (ANALYZE, BUFFERS)，按 P6 的五步看。

四、一个隐蔽陷阱：generic plan

PG 的预处理语句有个行为：前 5 次执行会根据具体参数生成「定制计划」（custom plan），之后可能切换成「通用计划」（generic plan）——一个不含参数值的固定计划。

后果：如果某条 SQL 的参数选择性差异极大（比如 status = 'RUNNING' 只命中 0.1%，status = 'COMPLETED' 命中 99%），通用计划只能取一个折中方案，于是对某些参数就变得很慢。

判据与处理：

  • 现象：EXPLAIN ANALYZE 里很快，线上同一条 SQL 很慢；
  • 检查：看计划里是不是用了通用计划（不同参数下计划完全一样、没有参数被代入）；
  • 处理：改写成参数不敏感的形状、或强制重新规划（在连接级别控制）。

这条和 P6 的追问正好接上——「explain 里快、线上慢」有一个标准答案，就是这里。

五、优化顺序（这一段是给面试收尾用的）

① 信息层：统计信息对不对（ANALYZE / 扩展统计）
② SQL 层：有没有多余的行被过早展开（先缩小范围，再 JOIN）
③ 索引层：索引是否存在、是否匹配（P1–P4）
④ 结构层：缓存、物化、预聚合、分区（P16）
⑤ 架构层：读写分离 / OLAP

顺序不能颠倒：先加索引、再发现统计信息是错的，就白加了。EnergyOps 的优化顺序（先修范围与 JOIN → 再建索引 → 再消 N+1 → 最后才缓存）和这条链是一致的。
