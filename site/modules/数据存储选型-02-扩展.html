S2单机不够了怎么扩：读写分离 / 分库分表 / 分布式数据库（OceanBase、TiDB）三条路各买到什么

骨架：先拆"不够用是哪一种"（四类上限表）→ 破除"多少行就要分表"的误解（判据是维护成本）→ 三条路各自买到什么、付出什么 → 分片的七条代价（重点讲分片键与跨片查询）→ OceanBase vs TiDB 的架构对照与共同点 → 分布式事务为什么难（没有全局时钟）+ 五种方案 → 全局 ID → CAP 的准确讲法 + PACELC → 边界

一句话结论：扩展的第一步是分清"哪一种不够用"——读并发高就加从库（最便宜，但绝不解决写）；分析干扰线上就隔离到从库或列存；容量与维护成本高就先归档 + 分区；只有写并发高才需要分片。分片买到的是总写入能力与容量，付出的是七条代价（跨片 join / 分页 / 事务 / 全局 ID / 全局二级索引 / 扩容迁移 / 分片键选错），所以它的判据不是"多少行"，而是"你还付不付得起维护这张表的代价"。而"应用层分片"与"换分布式数据库（OceanBase / TiDB）"的区别是把复杂度放在应用层还是下沉到基础设施——后者把跨片事务、自动扩容、全局索引都做进数据库，代价是产品锁定更深、资源开销更高。OceanBase 与 TiDB 的共同点是"多副本一致性协议（Paxos / Raft）+ 自动分片 + 分布式事务"，差别主要在组件摆法（TiDB 是计算存储分离 + PD 调度；OceanBase 是一体化、单机也能跑）。最后 CAP 不是三选二：P 是前提，真实选择是"分区时选 C 还是 A"，而日常的取舍是 PACELC 的后半句——一致性与延迟。

  • 判据不是行数而是维护成本
  • 归档+分区 → 读写分离 → 分片

  • 分片键按高频查询维度选（选错=灾难）

  • 2PC 阻塞 · TCC 侵入 · Saga 补偿 · 本地消息表最终一致

主线：扩展的一切手段都在"用复杂度换能力"，而复杂度的落点是"新增了多少个失败点 + 新增了多长的不一致窗口"。所以每一个扩展方案都要能回答：我新增了几个要监控、要处理故障、要对账的东西？ 分库分表把这件事放在应用层（每个开发者都要懂），分布式数据库把它放到基础设施层（数据库团队管一次）——这个"放哪层"才是真正的选型分界，而不是"哪个更快"。

1. 加了从库为什么还是慢？

因为从库只分担读（1.1）。写入压力无法用复制解决——副本不进写路径。要先确认瓶颈是读还是写，再选手段。

2. 分片键怎么选？

按"最高频的查询维度"选（2.2 第 ⑦ 条），不是按数据分布选。选错的后果是：高频查询全部变成广播，或者数据倾斜导致热点分片。 而低频的非分片键查询，应该另建一份聚合数据（物化视图 / 列存）来解决。

3. OceanBase 和 TiDB 最大的差别是什么？

组件摆法：TiDB 是计算存储分离（TiDB Server 无状态 + TiKV 行存 + TiFlash 列存 + PD 调度，依赖 Raft）；OceanBase 是一体化（每个节点同时是 SQL 与存储层，用 Paxos 多副本，单机也能跑出分布式架构，对运维更友好）。共同点是"多副本一致性 + 自动分片 + 分布式事务"——它们解决的是同一个问题。

4. 分布式事务为什么难？

因为没有全局时钟、没有共享日志、没有全局锁，原子提交的"一个提交点"不存在（4.1）。要么用协议造一个（2PC / Raft，慢且有阻塞），要么放弃原子性用补偿 + 幂等 + 对账逼近最终一致——后者的关键不是事务，是幂等与对账。

5. 什么情况下不该分库分表？

数据量没到（归档 + 分区能解决）、瓶颈在别处（慢查询 / 主从延迟 / 缺索引）、以及"分片键还没想清楚"的时候——分片键选错的迁移成本极高，所以宁可晚分也别乱分。

6. HTAP 的分布式数据库是不是就不用分库分表了？

是的，它把分片内化了——但分区键仍然存在且要选对（只是由数据库管理）。它取消的是"应用层要知道分片规则"这件事，不是取消"设计决策"。

扩展的第一步是分清"哪一种不够用"：读并发高 → 加从库（最便宜，但绝不解决写）；分析干扰线上 → 隔离到从库或列存；容量与维护成本高 → 先归档 + 分区；只有写并发高才需要分片。

分层要点追问深挖时用

  • 结论：先分清楚哪一种不够用；分片只解决写与容量，代价七条；判据不是行数。
  • 推导链：四类瓶颈 → 各自的解法 → 分片的收益与七条代价 → 判据 → 分片键性质 → 自建分片 vs 分布式库。
  • 量化：扩容迁移约 50% 数据；分片把"单机写上限"横向扩展。
  • 边界与常见误解：加从库不解决写瓶颈；分片键选错 = 大量广播（等于没分）。
