X2一个服务怎么上线：从镜像到能服务，要过哪几关（依赖就绪、健康检查、优雅退出、信号）

骨架：先立"难点在停止"→ SIGTERM / SIGKILL 的语义与平台的宽限期 → 优雅退出四步（强调摘流量）→ 异步与队列的版本 → 算时间窗 → 长任务的处理方式 → 启动侧：两类探针的分工 + 退避重试 → 边界与误解

一句话结论：上线的成败取决于"怎么退出"，不取决于"怎么启动"。正确的优雅退出顺序是 ① 先摘流量（从 LB / 注册中心摘掉，或让就绪探针失败）→ ② 等在途请求处理完 → ③ 关依赖（连接池、事务、缓冲）→ ④ 主动退出，其中 ①最容易漏（漏了就会"永远等不到没有在途请求"，最后被 SIGKILL 打断）。时间窗可以算：摘流量生效 + 最长在途请求 + 清理 ≤ 平台宽限期（SIGTERM 之后平台会等一段，超时就 SIGKILL——不可捕获、不可协商），所以长任务必须设计成"可中断 + 可恢复"（写 checkpoint 后主动退出，而不是撑着跑完）。启动侧的关键是分清两类探针：存活失败 → 重启（只检查进程自己，绝不查外部依赖）；就绪失败 → 暂时不接流量（不重启）——把依赖故障放进存活探针会造成"重启风暴"。队列消费者额外遵守一条：没处理完就不 ack，让它重投（重复由幂等吃掉，丢是不可接受的）。

  • 难点在"停止"不在"启动"
  • SIGTERM 可捕获（请你收工）、SIGKILL 不可捕获（现在就走）
  • 平台流程：15 → 宽限期 → 9
  • 四步：摘流量 → 排空 → 关依赖 → 退出
  • 摘流量最容易漏（否则永远排不空）
  • 时间窗 = 摘流量生效 + 最长在途 + 清理 < 宽限期
  • 长任务要可中断可恢复，不该进退出窗口
  • 存活（进程自己，失败→重启）vs 就绪（能服务，失败→不接流量）
  • 存活探针绝不查外部依赖（否则重启风暴）
  • 启动用退避重试而不是硬退出
  • 队列消费者：停止拉取 → 处理完
  • 不 ack 让它重投
  • 配置中心也是一个启动依赖，要有兜底

主线："进程会被随时拿走"是设计前提，不是异常情况。 所以正确的思路不是"把优雅退出做到完美"，而是让"被拿走"成为安全事件：在途请求要么完成、要么可重投；长任务要么可中断、要么可恢复；依赖不可用只影响"接不接流量"，不影响"进程是否活着"。

1. 优雅退出为什么要"先摘流量"？

否则会永远等不到"没有在途请求"：LB 还在发新请求，在途数不降反升，直到宽限期用完被 SIGKILL。这是"发版时错误率抬升"最常见的根因。

2. SIGTERM 和 SIGKILL 有什么区别？

SIGTERM 可被捕获（做清理后自己退出）；SIGKILL 不可捕获、不可忽略，内核直接终止。平台是"先 15、等宽限期、再 9"。

3. 存活探针和就绪探针怎么分工？

存活只管进程自身（死锁、卡死），失败重启；就绪表示"能服务"，失败只是不接流量。判断依据是"重启这件事能不能改善现状"——不能（依赖挂、下游慢）就绝不放存活。

4. 队列消费者怎么优雅退出？

停止拉取 → 处理完当前这条 → ack → 关连接 → 退出；宽限期内跑不完就【不 ack】，让它重投——重复由幂等吃掉，丢是不可接受的（[[母题-Q2-重复与乱序]]）。

5. 服务启动依赖服务没就绪怎么办？

有上限的退避重试 + 就绪探针（表现为"暂时不接流量"），不要"连不上就退出"——那会造成重启风暴。

启动依赖没就绪：有上限的退避重试 + 就绪探针，不要"连不上就退出"。队列消费者额外一条：没处理完就不 ack，让它重投（重复由幂等吃掉，丢是不可接受的）。配置三种来源里，密钥永远不要进环境变量（会进进程环境、容易被打进日志）。
