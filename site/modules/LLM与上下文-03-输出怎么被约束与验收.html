C2怎么保证模型输出的是程序能用的结构？JSON 合法就等于业务合法吗？草稿 · 待验收单卡 →

面试官问——"你们让模型返回 JSON，怎么保证解析一定成功？解析失败了怎么办？重试几次？"

一句话结论：模型的输出是逐 token 采样出来的，所以"结构正确"不是天然保证，而是要在正确的层堵住。三层各管一段：提示约束只降低概率（免费但不保证）、解码约束（strict / json_schema）把不合语法的 token 概率压成 0（保证，但 grammar 编译成本随 schema 复杂度指数增长，且有 20 工具 / 24 可选参数 / 16 union 的硬上限）、事后校验拦住语义错误（必须，因为上面两层都管不了）。关键认知：JSON 合法 ≠ 业务合法——枚举是否存在、ID 是否有效、用户是否有权限，只能自己校验；而且 refusal 和 max_tokens 会绕过 schema。重试的正确位置是兜底不是主路径，因为它是拿延迟买成功率，且转人工率按 p³ 放大。

  • 逐 token 采样 → 长输出尾部易崩
  • 四种失败：语法·缺字段·类型·枚举越界
  • 三层约束各管一段
  • 解码约束 = 采样时概率压成 0
  • grammar 编译指数成本
  • 20 strict 工具 · 24 可选参数 · 16 union
  • 改 name·description 不失效，改结构失效
  • 改 format 会让 prompt cache 失效
  • refusal 与 max_tokens 绕过 schema
  • 枚举大小写坑
  • JSON 合法 ≠ 业务合法
  • 重试 = 拿延迟买成功率，p³ 放大尾部

主线：语法正确可以在生成时"约束"出来，语义正确只能在校验时"拦"出来。 两者的分界线是"这件事是不是只关于形状"：形状（类型、必填、枚举范围）可以在采样时封死；含义（存在性、权限、前置条件）永远需要一次真实的业务查询——模型看不见你的数据库。

1. 重试几次合适？

通常 1–2 次，且只对解析/结构错误重试；业务错误由程序直接拒绝，不让模型绕过约束。连续失败就换模型 / 简化任务 / 转人工，并且每次都进 Trace。

2. schema 太复杂编译不过怎么办？

按顺序试：只把关键工具标 strict → 把可选参数改成必填（每个大致减半状态空间）→ 简化嵌套 → 拆到多个请求或子 Agent。

3. 怎么给下游一个可信的结果？

三层：结构由解码约束保证；语义由业务校验保证（枚举存在性、范围、权限、引用、前置条件、资源预算）；不确定的部分显式标记为"未验证"，而不是假装确定。

4. 为什么不能靠"多给几个示例"来稳输出？

【事实】对新一代模型，示例反而会把模型限制在某个探索空间里。更好的做法是设计接口：把 status 做成枚举、参数名写清楚、给合理的默认值——光是列出枚举值本身就在提示怎么用。

5. 改 schema 有什么隐藏成本？

grammar 编译结果缓存 24 小时，改 name / description 不会失效，改结构会；而改 output_config.format 会让该会话线程的 prompt cache 失效。所以 schema 应该版本化管理、不要中途反复改。

6. Temperature 调成 0，输出就确定了吗？

不是。 它只把"随机挑一个"换成"挑概率最高的那个"，但那个"最高"会随模型快照、数值计算顺序、上下文任何一处变化而变。确定性要从系统设计要：解码约束封死语法、固定版本、确定性的业务校验、评测兜底。"temperature=0 所以稳定"是一句会被追问倒的话。

C3Prompt 改了怎么知道变好还是变坏？换个模型为什么要重新验证？草稿 · 待验收单卡 →

面试官问——"我看你们 prompt 改得挺频繁的，你怎么知道一次改动是变好了还是变坏了？换模型之后你们做了什么？"

一句话结论：Prompt 不是配置文件，是针对当时模型写的控制层——它和模型是一个耦合系统，模型一变，同一份 prompt 的收益和代价全变。所以改动必须走消融：逐段删除、跑同一套 Eval、看指标是掉了还是变好；验收必须用没参与调优的 held-out 集合（真实案例：训练集上 98.9% 打平，held-out 上 90.5% vs 78.6%）。反直觉的实证是：Anthropic 为 Claude 5 代删掉了 80%+ 的系统提示，编码评测无损失；清掉六类"拐杖"后成本降 14.6%、准确率升 5.3%（错误率腰斩）。而验证一次消融只要几美元——所以"要不要做消融"是习惯问题，不是成本问题。

  • prompt 是控制层不是配置
  • 一条指令的生命周期（补偿 → 沉淀 → 模型升级 → 变成冲突 → 消融）
  • 六类拐杖（验证仪式·强调助推·强制流程·过时示例·矛盾规则·过期配置）
  • 消融方向是"删"不是"加"
  • 删 80% 系统提示无损失
  • 标准误 √(p(1−p)/n)，200 条 ≈ ±2%
  • held-out 90.5% vs 78.6%
  • 准确率 +5.3% = 错误率腰斩
  • 消融成本 $12 vs 年化 $32K–$320K
  • 分层验证：抽样快筛 + 全量门禁

主线：Prompt 的效果是「模型能力」的函数，不是常量。 所以它必须像代码一样被管理：进版本控制、变更走评测、结果与版本绑定。而因为它是一份有限的注意力预算，正确的动作方向永远是"先问能不能删"，而不是"再加一条规则"。

1. 一次 prompt 改动，验证流程是什么？

抽样快筛（便宜、抓大幅回退）→ 消融（逐段删，看哪段还在产生收益）→ 全量回归（发布门禁）→ held-out 验收。每一层的目的不同，不能互相替代。

2. 为什么不直接加规则？

加规则有三重代价：稀释注意力预算、制造规则冲突（模型得额外推理去化解）、在模型升级后变成负担。先做消融，往往能删掉比你想加的还多。

3. 怎么发现一条指令该删了？

做消融：删掉它，跑同一套 Eval。指标没掉就是冗余，指标变好就是拐杖。 另一条便宜的信号是查文档里互相矛盾的指令——Anthropic 就是读自己的使用记录时发现同一请求里带着冲突指令的。

4. 评测集要多大？

取决于要分辨多小的差异。SE = √(p(1−p)/n)：200 条约 ±2%，想分辨 2 个点需要约 900 条。先想清楚"我要证明多大的差异"，再决定集合规模。

5. Prompt 版本怎么和别的版本绑定？

当输出同时取决于模型版本、Prompt 版本、Schema 版本、知识/索引版本时，四者必须一起绑定到结果上。否则你复现不出任何一次线上输出，也就无法归因（[[母题-C1-上下文组装与窗口预算]] 的"上下文是视图"在这里落地成工程要求）。

6. CLAUDE.md 写多长合适？

【事实】轻。写明仓库是干什么的，把大部分 token 花在代码库里的坑上；不要写"看文件系统就知道"的显然内容；多条验证指令就做成一个 verification skill，靠渐进披露按需加载。
