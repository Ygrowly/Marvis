L3分布式锁怎么实现（Redis / 数据库 / ZK）；三种失效场景；为什么还需要 fencing token

骨架：先问"真的需要锁吗"（幂等 / 条件更新 / 队列排在前）→ 三种实现的机制与代价 → 失效的根因（锁服务按时间判断 vs 客户端事实） → 三大场景（GC / 时钟 / 分区）→ 用 TTL 两难说明"没有安全值" → 续期只能降概率 → fencing token 才给保证 → Redlock 争议的共识部分 → 边界与误解

一句话结论：跨机器互斥要把锁状态放到一个共享的地方，三种实现各有代价：Redis（SET ... NX PX 一条原子命令 + 释放要校验值；弱点是主从异步复制，切换会丢锁）、数据库（唯一约束 / 带条件更新，不引入新组件但把锁争用压在数据库上）、ZooKeeper / etcd（临时顺序节点 / 租约 + 单调 revision，语义最干净但要维护一套强一致系统）。它们的共同弱点来自同一个根因：锁服务的判断（按时间）与客户端的事实（是不是还在跑）会脱节——GC 停顿、时钟漂移、网络分区都会产生"两个持有者"，而 TTL 没有安全值（短了双持有者、长了可用性差，且"最长停顿"无上界）。所以真正的解法是把安全性搬到被保护的资源上：fencing token（单调递增号）+ 资源侧拒绝更小的号。但更该先问的是："我到底要'不同时跑'还是'不重复执行'？"——后者靠幂等就够了（RuleArena 连锁都没用），锁只在地一步之后才考虑，而且它的作用是"减少干扰"，不是"保证正确性"。

  • 三种实现（Redis / 数据库 / ZK-etcd）
  • SET ... NX PX 必须一条命令
  • 释放要校验值（否则误删别人的锁）
  • Redis 弱点是异步复制丢锁
  • 数据库做锁把争用压在库上
  • ZK 会话绑定 + revision
  • 失效根因：锁服务按时间判断 vs 客户端的事实
  • GC 停顿 · 时钟漂移 · 网络分区
  • TTL 没有安全值
  • 续期只能降概率（续期和业务一起停）
  • fencing token = 单调递增号 + 资源侧拒绝更小的号
  • Redlock 争的是概率边界
  • "只执行一次"是幂等问题不是锁问题
  • 先幂等 → 再锁减少干扰 → 最后 token

主线：锁能买到的只有"大概互斥"，买到"一定互斥"的从来不是锁，而是被保护资源自己的校验。 所以判断顺序永远是：先让重复无害（幂等）→ 再考虑用锁减少干扰 → 最后才用 token 补上保证。把这三步的顺序倒过来（先加锁、以为就安全了）是这一块最典型的错。

1. 锁过期了业务还在跑怎么办？

加 fencing token：发锁时给单调递增号，写入由存储校验"只接受更大的号" → 旧持有者的写被拒。同时把长业务改成分批 + 每批重新抢锁，把损失限制在一批内。

2. 为什么分布式锁不能保证互斥？

因为它依赖"锁服务对时间的判断"，而这可能与"客户端是不是真的在跑"脱节（GC 停顿 / 时钟漂移 / 网络分区）。TTL 的取值是个两难，没有安全解。

3. Redlock 有什么问题？

它想用"向多数实例加锁"缓解单实例丢锁，但反对意见指出它依赖假设的时钟漂移上限与有限停顿；两方都同意的是：要严格正确性就得用 fencing token。（面试讲到这一层即可，不必站队）

4. 什么时候该用分布式锁、什么时候不该？

先问"要的是不同时跑，还是不重复执行"：后者用幂等（更便宜、不引入新依赖）；只有"重复执行的代价极高、必须串行"时才上锁。RuleArena 连锁都没用，靠幂等键 + 唯一约束就够了。

5. 释放锁为什么不能直接 DEL？

会误删别人的锁：你过期后别人拿到了锁，你这时 DEL 删的是别人的 → 于是"一个删锁动作制造了一次双重执行"。必须校验值（GET 比对 + DEL，用 Lua 保证原子）。
