R2Redis 的数据怎么不丢：RDB / AOF、过期删除、内存淘汰草稿 · 待验收单卡 →

Redis 的数据会在什么情况下丢？每种"不丢"的手段各自付了什么代价？

Redis 有哪几种持久化方式？RDB 和 AOF 的区别是什么、该怎么选？ AOF 为什么要重写？过期删除策略和内存淘汰策略有什么区别？内存满了 Redis 会怎么样？

一句话结论：Redis 的"不丢"分三件事——持久化（RDB 记结果、文件小恢复快但有窗口；AOF 记过程、最多丢 1 秒但文件大恢复慢，生产常混用）、过期删除（惰性 + 定期抽样，不是立即删）、内存淘汰（8 种策略，按"在哪个池子挑 + 用什么算法"组合）。核心是认清一个约束：Redis 单线程，所有设计都在避免 O(n) 或长时间阻塞主线程——所以定期删除用抽样、bgsave 用子进程、LRU 用近似、always 要付一个数量级的吞吐。

  • 记结果 vs 记过程
  • RDB 丢两次快照之间、AOF 最多丢 1 秒
  • `appendfsync` 三选一（always 0.2ms×5000=1 秒）
  • AOF 重写＝把过程压成结果
  • `bgsave` 用子进程，但 fork 要停一下 + COW 让内存涨
  • **先执行后记日志，因为命令不幂等**
  • 惰性删除（省 CPU 但占内存）+ 定期删除（抽样，25% 水位 + 25ms 上限）
  • 过期删除（时间）vs 内存淘汰（空间）
  • `volatile-*` 的陷阱
  • 近似 LRU 用采样换开销
  • **异步复制的窗口**（故障转移会丢未同步的写入）
  • 集群=分片不是副本
  • **从库不主动删过期 key**

主线：Redis 的每一条"删除"和"持久化"设计，都在同一个约束下做取舍——「不能让单线程被长时间占住」。 所以：定期删除用抽样而不是全扫；bgsave 用子进程而不是主线程；LRU 用近似而不是精确链表；AOF 用 everysec 而不是 always。这四条是同一个约束的四种解法。

1. RDB 和 AOF 选哪个？

通常都开：RDB 做冷备与快速恢复，AOF 保最多丢 1 秒；4.0 后可用混合持久化。

2. AOF 重写是干什么的？

把"记过的所有过程"重新压成"当前结果"，用一次全量替换掉整个历史，加快恢复。

3. bgsave 会影响线上吗？

会，两个途径：fork 复制页表时的短暂停顿；COW 导致快照期间内存上涨（写入越多涨得越多）。

4. 为什么不做精确 LRU？

精确 LRU 要维护全量链表、每次访问都移动节点，内存和操作开销都大。采样近似能拿到接近的效果，代价小得多。

5. 持久化开着，数据就一定不会丢吗？

不是。 everysec 仍有 1 秒窗口；always 也不等于零。而且持久化不是备份——误删、误 FLUSHALL 同样会被记进 AOF，所以要另有备份策略。

6. Redis 内存满了会怎么样？

看策略：noeviction 写报错；其余按池子和算法淘汰。注意 volatile-* 在没有 TTL 的 key 时等同 noeviction。
