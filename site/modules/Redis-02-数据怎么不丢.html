Redis 的"不丢"是三件事，不是一件事：持久化、过期删除、内存淘汰。

持久化两种：RDB 记结果（定时快照，文件小恢复快，但两次快照之间宕机会丢）；AOF 记过程（追加每条写命令，everysec 最多丢约 1 秒，但文件大恢复慢，所以有 AOF 重写把历史压成当前结果）。生产通常两者都开：RDB 做冷备与快速恢复，AOF 保最多丢 1 秒（4.0 后还有混合持久化）。

过期删除是惰性 + 定期抽样，不是立即删——因为 Redis 单线程，不能为了清理去扫全表或给每个 key 起定时器。

内存淘汰是 8 种策略，按"在哪个池子挑（allkeys / volatile）× 用什么算法（LRU / LFU / random / 不淘汰）"组合；noeviction 是写报错，注意 volatile-* 在没有 TTL 的 key 时等同 noeviction。不做精确 LRU 是因为精确 LRU 要维护全量链表、每次访问都要移动节点，采样近似效果接近而代价小得多。

一条必须说清：持久化不是备份——误删、误 FLUSHALL 同样会被记进 AOF，所以要另有备份策略。而且 bgsave 并非无代价：fork 复制页表时的短暂停顿 + COW 让快照期间内存上涨。

主线：Redis 的每一条"删除"和"持久化"设计，都在同一个约束下做取舍——「不能让单线程被长时间占住」。 所以：定期删除用抽样而不是全扫；bgsave 用子进程而不是主线程；LRU 用近似而不是精确链表；AOF 用 everysec 而不是 always。这四条是同一个约束的四种解法。

1. RDB 和 AOF 选哪个？

通常都开：RDB 做冷备与快速恢复，AOF 保最多丢 1 秒；4.0 后可用混合持久化。

2. AOF 重写是干什么的？

把"记过的所有过程"重新压成"当前结果"，用一次全量替换掉整个历史，加快恢复。

3. bgsave 会影响线上吗？

会，两个途径：fork 复制页表时的短暂停顿；COW 导致快照期间内存上涨（写入越多涨得越多）。

4. 为什么不做精确 LRU？

精确 LRU 要维护全量链表、每次访问都移动节点，内存和操作开销都大。采样近似能拿到接近的效果，代价小得多。

5. 持久化开着，数据就一定不会丢吗？

不是。 everysec 仍有 1 秒窗口；always 也不等于零。而且持久化不是备份——误删、误 FLUSHALL 同样会被记进 AOF，所以要另有备份策略。

6. Redis 内存满了会怎么样？

看策略：noeviction 写报错；其余按池子和算法淘汰。注意 volatile-* 在没有 TTL 的 key 时等同 noeviction。

  • 量化：AOF everysec 最多丢约 1 秒；8 种淘汰策略；volatile-* 无 TTL 时等同 noeviction。
  • 边界与常见误解：持久化 ≠ 备份；bgsave 有 fork 停顿与 COW 内存上涨；"Redis 内存满了会怎样"取决于策略，不是统一行为。
