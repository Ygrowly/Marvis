E1怎么设计一套评测——测什么、拿什么测、谁来判分、多少样本才够草稿 · 待验收单卡 →

"这个系统好不好"该怎么变成一个可比较、可复现、可定位的判断——为什么"一个综合分"是错的？

面试官问——"你们怎么评测这个系统？用一个什么分数衡量？"

一句话结论：评测的第一性原理是"把模糊目标变成可比较、可复现、可定位的判断"，所以它必须分层。指标分六层：业务结果 / 任务结果 / 过程（诊断价值最高）/ 工程 / 资源 / 安全——安全单独门禁，不参与平均，因为把它放进平均等于允许"用高质量文案换一次越权"（业务 80、任务 85、过程 70、工程 90、资源 75、安全 10 的平均分是 68.3，看起来"刚及格"）。数据集分五层：Dev 可以反复看，Golden / Holdout / Adversarial / Online 不能拿来调优——看多了就变成 Dev 了（真实案例：训练集打平、held-out 差 11.9 个点）。判分四级且顺序不能反：能确定性判断的不用模型 Judge（10 项检查全用模型只有 19.7% 全对，60% 确定化后 52.2%）。稳定性和能力要分开测：pass@k 测能力上限（有一个能用的就行），pass^k 测稳定性（每次都要对）——p=0.9 时 pass^5 只有 59%、pass^10 只有 34.9%；反过来，要求 pass^5 = 90% 意味着单次要做到 97.9%。最后，样本量决定分辨率：200 条约 ±2.1%，想论证"改进了 2 个点"需要约 900 条。

  • 指标六层（业务 / 任务 / 过程 / 工程 / 资源 / 安全单独门禁）
  • 综合分会掩盖严重错误（68.3 分的例子）
  • 数据集五层（Dev 可反复看，其余四层不行）
  • holdout 的必要性（训练集打平、held-out 差 11.9 点）
  • **grader 顺序：Code
  • Rule > Reference > Model Judge > Human**
  • rubric 六条（别把长度语气误当正确）
  • pass@k 测上限、pass^k 测稳定（0.9⁵ = 59%）
  • 200 条约 ±2.1%，900 条分辨 2 点
  • 评测集要审计（别把错题 benchmark 当目标）

主线：评测不是"算出一个数"，是"把模糊目标变成可比较、可复现、可定位的判断"。 所以它必须分层——因为不同的层回答不同的问题，把它们压在一起，就一个都答不了。

1. 如何评测一个 Agent？

从真实任务构造可重置环境；分结果、过程、工程、安全和业务指标；规则 / 代码 grader 优先，语义用校准过的模型 Judge；保存完整轨迹；离线回归后再 shadow / A-B；线上 Bad Case 回流。（这是 study/07 的 Q1 标准答案，注意它把"可重置环境"放在第一位——[[母题-E2-Trace与可观测性]] 会展开。）

2. LLM-as-a-Judge 有什么问题？

偏差（偏爱长回答）、漂移（同输入不同时间不同结果）、自洽幻觉（给自己打高分）。所以要用人工样本校准、记录 grader 版本、并且只用在确定性判分覆盖不到的地方。

3. Golden Set 怎么维护？

版本化；去重；检查泄漏；定期审计"坏题"；来源要包含真实失败与用户纠正（不只是专家构造）。关键是"它不能参与调优"——否则它就退化成 Dev 集。

4. 模型输出非确定，CI 怎么做？

看 pass^k 而不是单次；固定随机种子与环境 fixture；门禁用"通过率不低于阈值 + 置信区间"，而不是"这一次过了就行"（[[母题-E3-回归门禁与发布卡口]] 展开）。

5. 怎么评估新模型是否值得切换？

同一套 holdout 上对比，看 pass^k、P95 延迟、单任务成本三件事；而且要重跑消融——因为 prompt 是针对旧模型写的（[[母题-C3-Prompt版本管理与回归]]、[[母题-C5-模型选型与降级三角]]）。
