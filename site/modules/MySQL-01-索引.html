M1为什么 InnoDB 用 B+ 树，不用 B 树 / 红黑树 / 哈希草稿 · 待验收

InnoDB 的索引底层是 B+ 树。为什么是 B+ 树，而不是 B 树、红黑树或哈希表？

数据库索引为什么必须选择 B+ 树？这个选择的约束条件是什么？

一句话结论：B+ 树是为磁盘 IO 次数最少而设计的——非叶节点只存键让树变矮，叶子有序链表让范围查询不用回溯，于是查两千万行也只要 3 次 IO。

  • IO 次数
  • 矮胖
  • 非叶只存键
  • 叶子链表
  • 扇出

主线：磁盘随机 IO 是瓶颈（一次约 10ms，内存访问是纳秒级），所以索引结构的唯一目标是把定位一条记录所需的 IO 次数，从「行数」降到「树高」。

原理分解

一、约束：瓶颈不是 CPU，是磁盘 IO

数据库的数据量远超内存，绝大多数查询要读磁盘。一次随机 IO 的代价比一次内存访问高 5–6 个数量级。

所以问题不是「怎么让比较更快」，而是「怎么让 IO 次数更少」。任何索引结构的评价标准都是这一条。

二、B+ 树的三个设计点

① 非叶节点只存键，不存数据 非叶节点每条记录只有「键（8B）+ 页号（6B）」≈ 14B，16KB 的页能放下约 1170 个键。 → 一个节点指向 1170 个子节点，这叫扇出大；扇出越大，树越矮。

② 所有真实数据都在叶子层，叶子之间用双向链表串起来 范围查询（next_retry_time <= NOW()）定位到起点后，顺着链表向右扫就行，不需要回到根节点重新下降。

③ 页大小固定（16KB），与磁盘块对齐 一次 IO 正好读一整页，页内含几十上百条记录，摊薄了单次 IO 的成本。

三、量化：三层 B+ 树能存多少

根节点       1 页 × 1170 个键
第二层    1170 页 × 1170 个键  = 约 137 万个叶子页
叶子层  137 万页 × 约 16 行    ≈ 2000 万行

查 2000 万行只需要 3 次 IO（除非走索引扫了很多行，或频繁回表）。 记忆点：三层 ≈ 2000 万行。这也解释了为什么几百万行的表只有三层、加不加索引高度感受不到差别。

四、为什么不是别的结构

结构致命问题
B 树非叶节点也存数据 → 同样一页能放的键少得多 → 扇出小、树更高；范围查询要中序遍历回溯，不能顺链表走
红黑树 / AVL二叉树，扇出只有 2。几百万行高度 20+ → 20+ 次随机 IO，完全不可接受
哈希表等值查询 O(1) 很快，但不支持范围、排序、最左前缀——而真实业务查询几乎都是范围的

一句话：B 树败在扇出，红黑树败在高度，哈希败在不支持范围。

1. 既然 B+ 树这么矮，为什么还要尽量走覆盖索引？

树高决定定位成本，但回表是额外的 IO。B+ 树只解决「找到索引项」，回表要再查一次聚簇索引，那才是大头。

2. 为什么 B+ 树的叶子要用双向链表，单向不行？

范围查询通常只需要向右扫（单向够用），但反向扫描（ORDER BY ... DESC）和某些优化器路径需要向左，双向是通用选择。

M2联合索引与最左前缀为什么存在；索引失效有哪些场景草稿 · 待验收

任务表要支持这样一条调度 SQL：

SELECT id, status, next_retry_time, priority
FROM task
WHERE status = 'PENDING'
  AND next_retry_time <= NOW()
ORDER BY priority DESC, id ASC
LIMIT 100;

联合索引该怎么建？为什么 (a, b, c) 能用上 a=1 和 a=1 AND b=2，却用不上单独 b=2？

联合索引的字段顺序由什么决定？「最左前缀」这个限制是怎么来的？

一句话结论：联合索引 (a, b, c) 的排序方式是先按 a 排、a 相同再按 b 排、b 相同再按 c 排；所以只有从最左列开始的连续前缀才能用上这份有序性。

  • 有序性
  • 连续前缀
  • 等值在前范围在后
  • 排序列收尾
  • 少扫少回表少排序

主线：索引的价值只有一条——让 MySQL 少扫数据、少回表、少排序。联合索引的字段顺序，是围绕这条 SQL 的执行路径决定的，不是围绕「哪些字段经常出现」决定的。

原理分解

一、最左前缀的成因（一次推完）

索引本身就是一份排好序的数据。(status, next_retry_time, priority) 的排序规则是：

先按 status 排  →  status 相同再按 next_retry_time 排  →  再相同才按 priority 排

所以：

查询条件能否用索引原因
status = 'PENDING'✅命中最左列
status = ? AND next_retry_time <= ?✅连续前缀
next_retry_time <= ?（单独）❌next_retry_time 只在「同 status 内」有序，全局无序
priority = 3（单独）❌只在最小范围内有序

一句话：b 是「局部有序、全局无序」的，所以只用 b 查等于在无序数据里找。

二、字段顺序的四条经验（来自素材）

围绕执行路径设计，不是围绕字段热度：

1. 等值过滤列放前面 —— 等值条件能一次定位到一个连续区间 2. 范围列要谨慎 —— 范围条件会截断后面的列，a = ? AND b > ? AND c = ? 里 c 用不上索引 3. 排序列尽量接在后面 —— 让 ORDER BY 直接吃索引的有序性，避免 Using filesort 4. 目标始终是：少扫、少回表、少排序

三、回到那条调度 SQL

WHERE status = 'PENDING' AND next_retry_time <= NOW()
ORDER BY priority DESC, id ASC
LIMIT 100

按上面的规则推：

  • status 是等值 → 放最前
  • next_retry_time 是范围 → 放第二位（它会截断后面）
  • priority 是排序列 → 接在范围列后面，能用上一部分有序性（同一 next_retry_time 区间内仍是排好的）
  • 若 priority 无法完全靠索引排序，Extra 里会出现 Using filesort

注意：范围列之后的有序性只在「范围内部」有效，这是这条 SQL 是否出现 filesort 的关键——不要背「范围列后面全失效」，那是过度简化。

四、索引失效的典型场景

场景为什么失效
列上做函数 / 运算：WHERE YEAR(created_at) = 2026破坏了「按列原值有序」这个前提
隐式类型转换：字符串列 WHERE phone = 13800138000相当于对列做了类型转换
前导模糊：LIKE '%abc'前缀不定，无法定位有序区间的起点
OR 连接的条件里有非索引列只能全表扫再合并
!= / NOT IN命中区间过于分散，优化器判断扫索引不如全表
选择度太低（如 status 只有 3 个值）优化器主动放弃索引走全表

最后一条最容易被忽略：索引失效不一定是「写法错了」，可能是优化器算过成本后主动不选。

1. WHERE b = 2 AND a = 1 和 WHERE a = 1 AND b = 2 有区别吗？

没有。优化器会重排条件，索引匹配看的是列集合，不是书写顺序。

2. a = 1 AND c = 3 能用上 (a, b, c) 吗？

a 能用（定位区间），c 用不上（被中间断开的 b 阻断）。但如果是 a = 1 AND b = 2 AND c = 3，三列都能用。

M3聚簇索引、回表、覆盖索引：explain 里怎么看出来草稿 · 待验收

同一条 SQL，有时加个索引就快 10 倍，有时加了却没用。EXPLAIN 出来怎么看它到底走了没走索引、慢在哪？

聚簇索引和二级索引的区别是什么？「回表」为什么慢，「覆盖索引」为什么能省掉它？

一句话结论：聚簇索引的叶子存整行数据，二级索引的叶子只存索引列 + 主键值；用二级索引查非索引列时必须「回表」再查一次聚簇索引——覆盖索引就是让需要的列全在二级索引里，从而免掉这次回表。

  • 索引组织表
  • 主键即数据
  • 回表 = 二次查找
  • 覆盖索引
  • Using index

主线：InnoDB 是索引组织表——主键索引的叶子就是数据本身，二级索引只是「指向主键的目录」。所以任何「先用二级索引、再取非索引列」的查询都要付出两次 B+ 树查找的代价。

原理分解

一、两种索引的结构差异

聚簇索引（clustered index）= 主键索引

叶子节点 = 完整的一行数据（id, status, next_retry_time, priority, ...）

所以 InnoDB 里「按主键查」是最快的——一次 B+ 树定位就拿到整行。

二级索引（secondary index）= 普通索引

叶子节点 = 索引列的值 + 主键值
例：(status, next_retry_time) 的叶子 → (status, next_retry_time, id)

注意：二级索引必须带上主键值，否则找不到对应的行。这也解释了两个常见现象：

  • 主键越短，所有二级索引都越小
  • 用非主键做聚簇代价很高（所以 InnoDB 固定用主键）

二、回表：那一次被忽略的额外查找

-- 有索引 (status, next_retry_time)
SELECT id, status, next_retry_time, priority
FROM task
WHERE status = 'PENDING' AND next_retry_time <= NOW();

执行过程：

1. 走二级索引 (status, next_retry_time) 定位到满足条件的索引项 → 拿到 id 2. priority 不在二级索引里 → 拿 id 回聚簇索引再查一次，取出整行 3. 第 2 步就是回表，每条命中行都要做一次

这就是为什么「命中 1000 行」比「命中 10 行」危险得多：树高始终 3 层，但回表次数随命中行数线性增长。

三、覆盖索引：让索引自己回答完

把查询要用的列都放进索引，就不需要回表了：

-- 索引改成 (status, next_retry_time, priority)
SELECT id, status, next_retry_time, priority   -- id 本来就在二级索引里
FROM task
WHERE status = 'PENDING' AND next_retry_time <= NOW();

EXPLAIN 的 Extra 里出现 Using index，就是走了覆盖索引。

代价：索引变宽、写入变慢、占用空间。不是所有查询都值得覆盖，热点查询值得。

四、EXPLAIN 只看四个字段

字段看什么好 / 坏的信号
type访问类型好 → 坏：const > eq_ref > ref > range > index > ALL；出现 ALL 就是全表扫
key实际用了哪个索引是 NULL 说明没走索引；和预期不一致要看 possible_keys
rows预估扫描行数越小越好；这个值是估算，不是精确值
Extra额外动作Using index 好（覆盖）；Using filesort / Using temporary 是明确的优化信号

素材里那句话可以当口诀用：出现 Using filesort 或 Using temporary，基本就说明这条 SQL 还有优化空间。

1. 既然覆盖索引能免回表，为什么不全表都建宽索引？

索引要跟着写入一起维护：越宽的索引写入越慢、占空间越多；且索引数量多会干扰优化器选择。覆盖是给热点查询的，不是给全表的。

2. rows 很小就一定快吗？

不一定。rows 是估算值，且它不含回表成本。命中 10 行但每行回表一次，可能比扫 100 行的覆盖索引还慢。

M4索引的代价与大表变更：为什么「加个索引」可能把库搞挂草稿 · 待验收

任务表 5000 万行，线上正在跑。现在要给 status 加一个索引，你直接执行 ALTER TABLE task ADD INDEX idx_status(status)。会发生什么？

索引不是免费的——它的代价是什么？大表上做结构变更，怎么才能不阻塞线上流量？

一句话结论：索引的代价是写放大 + 空间 + 优化器负担；大表变更的代价来自重建结构 + 拿元数据锁（MDL）——危险的不是 DDL 慢，而是它把后续所有查询都堵在队列里。

  • 写放大
  • MDL 连锁
  • Online DDL
  • LOCK=NONE
  • 影子表
  • 长事务卡 DDL

主线：索引是读的快照，写的负债。 每加一个索引，所有写入都要多维护一棵 B+ 树。所以索引数量是「读收益」与「写代价」的平衡，不是越多越好。

原理分解

一、索引的三种代价

1. 写放大：每次 INSERT / UPDATE / DELETE 都要同步维护所有相关索引。10 个索引 = 一次写入要改 10 棵 B+ 树，而且每棵都要保证有序（可能触发页分裂）。 2. 空间：二级索引的叶子存「索引列 + 主键」。主键越长，所有二级索引越大——这也是"别用 UUID 当主键"的原因之一。 3. 优化器负担：索引越多，优化器要评估的执行计划越多，选错的概率上升；统计信息不准时还可能选错索引。

所以判据是：这个索引有没有高频查询真的用它？没有任何查询用上的索引，是纯负债。

二、大表加索引为什么危险

ALTER TABLE ... ADD INDEX 要做两件事：

1. 扫描全表 + 排序，建出一棵新索引（5000 万行，几分钟到几十分钟） 2. 在开始和结束拿 MDL（元数据锁）

危险不在第 1 步，在第 2 步的连锁反应：

一个长事务还在跑（持有 MDL 读锁）
   ↓
DDL 请求 MDL 写锁 → 排队等待
   ↓
DDL 之后的所有查询也要 MDL 读锁 → 全部排在 DDL 后面
   ↓
连接池被排满 → 服务雪崩

这才是"加个索引把库搞挂"的真实机制：不是 DDL 本身慢，是它在后面堵了一条越来越长的队。

三、Online DDL（MySQL 5.6+）

ALTER TABLE task ADD INDEX idx_status(status), ALGORITHM=INPLACE, LOCK=NONE;
参数作用
ALGORITHM=INPLACE不重建整表（加二级索引只需扫描 + 排序）
LOCK=NONEDDL 期间允许并发读写，只在开始/结束瞬间要短暂排他锁

但边界仍在：

  • DDL 如果被长事务卡住等 MDL，LOCK=NONE 救不了你——它只是"允许并发"，不是"不需要锁"
  • 有些操作无法 INPLACE（改列类型、重建聚簇索引等）

所以执行前先查长事务：

SELECT trx_id, trx_started, trx_mysql_thread_id
FROM information_schema.innodb_trx
WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;

四、影子表方案（pt-osc / gh-ost）

原理四步：

1. 建一张结构相同的新表（带新索引） 2. 同步增量：pt-osc 用触发器、gh-ost 读 binlog，把旧表的新写入同步到新表 3. 分批拷贝存量：可限速、可暂停 4. RENAME TABLE 瞬间切换

pt-oscgh-ost
增量来源触发器binlog
对主库影响触发器有额外开销更小
可暂停/限速支持支持，且更细

代价：需要约一倍额外空间；切换瞬间仍需短暂 MDL。

五、怎么选

场景选择
加二级索引、表不算很大Online DDL（ALGORITHM=INPLACE, LOCK=NONE）
表很大、要求可控可回滚pt-osc / gh-ost
改列类型等无法 INPLACE影子表方案
任何情况先查长事务；别在业务高峰动手；准备好回滚方案

1. LOCK=NONE 都开了，为什么还是可能卡住线上？

关键在于 MDL 等待的连锁反应：长事务持读锁 → DDL 等写锁 → 后续查询再排在 DDL 后面。LOCK=NONE 只保证 DDL 执行期间不阻塞，不保证它不被别人阻塞。

2. 索引是不是越多越好？

不是。写放大 + 空间 + 优化器负担三笔账；判据是"有没有高频查询真的用它"。没被用上的索引是纯负债，应该删掉。
