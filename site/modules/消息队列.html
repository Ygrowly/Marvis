本模块的题 · 总纲 2 道 · 不属于某一条主线，先说后翻

1必背Q1

这道题属于母题 Q1 · 消息为什么会丢；要它不丢，生产者 / Broker / 消费者三段各要做对什么，每段加严的代价是什么 · 下面挂它的完整回答（学的时候看）

实测 515 字 · 按 4 字/秒折算约 129 秒（秒数是估算，字数才是实测）

消息只可能在三段丢——发送、存储、消费，每段各有一道确认：生产端等 Broker 确认（acks）、Broker 端持久化 + 多副本、消费端处理完再 ack。

不丢不是一个参数能搞定的，要三个一起给：acks=all（等 ISR 全部确认）+ min.insync.replicas ≥ 2（ISR 不足就拒绝写，把"可能丢"换成"明确不可用"）+ 禁止从落后副本选主。因为 acks=all 单独不保证不丢——它指的是 ISR 里的副本，ISR 缩到 1 时照样接受写。

两个必须说清的语义：① "不丢"的准确定义是"生产者收到成功 ack 的消息永不消失"，不是"消息一定被处理一次"——跨进程通信没有"恰好一次"，框架只保证至少一次，重复是它的代价，由业务幂等吃掉；② 不能"收到消息就 ack"，那是主动制造丢消息：提前 ack 后崩溃，Broker 认为已处理完不会再投，消息永久消失且无任何报警。

消费失败三档兜底：重试（限次 + 退避）→ 重试队列（RocketMQ 并发消费默认 16 次）→ 死信队列；死信队列的意义是"绝不静默丢弃"。本地事务和发消息的一致性本质是"两个系统没法放进一个本地事务"，三条路线：事务消息 / 本地消息表 / Outbox（EnergyOps 用的是 Outbox）。

分层要点追问深挖时用

  • 结论：三段各一道确认；不丢要三个参数一起给；框架只保证至少一次。
  • 推导链：三段 → 各段确认 → acks=all 的漏洞（ISR 缩到 1）→ 用 min.insync.replicas 闭环 → 重复的代价交给幂等 → 失败三档兜底 → Outbox 解决跨系统事务。
  • 量化：acks 三档（0/1/all）；min.insync.replicas ≥ 2；RocketMQ 默认重试 16 次。
  • 边界与常见误解："acks=all 就保证不丢"×；"收到就 ack"会永久丢消息且无报警；持久化开着不等于不会丢（还有异步复制与误操作）。

项目映射 把这个模块挂到真实经历上

锚点

projects/EnergyOps/

  • 用在哪：这是"什么时候不该上 MQ"的活教材。 当前规模（约 604 台设备）用的是 PostgreSQL 任务表 + APScheduler + 批处理 + 受控并发，项目里明确决定不引入消息队列与流处理，并写下了升级条件（表计到万级 / 分钟写入持续高峰 / 补数大量堆积 / 单机无法在窗口内完成）。长耗时导出、规则回放与结算才走队列 + 并发配额限流（[[母题-Q1-消息为什么会丢怎么才不丢]] 的前提节）。
  • 解决什么问题：通知这类外部副作用不能进数据库事务——短信发出去了没法回滚。所以 Alarm 与 Notification Outbox 在同一个本地事务里落库，通知 Worker 再拿业务幂等键去调外部平台；调用超时标记 result_unknown，不直接重试，先查外部权威状态或用同一幂等键重试。这就是"本地消息表 / Outbox"这条路线在没有 MQ 时的真实形态。
  • 踩过的坑：① 超时被当成失败——超时表示结果未知，直接重试会重复发短信；② 租约版本只防住了本地数据库的旧写，撤不回旧 Worker 已经发出的外部调用——所以外部调用必须用稳定幂等键 + 恢复前先查权威状态；③ Checkpoint 被当成"业务完成证明"——它只是恢复线索（[[母题-A4-长任务状态与Checkpoint]]）。
  • 决策与取舍：先用数据库任务表换掉 MQ，等升级条件出现再说。这笔账划得来是因为：当前吞吐离 MQ 的收益门槛还远，而引入 MQ 的三笔代价（可用性、复杂度、一致性）立刻要付。"不上 MQ"不是保守，是算了账（[[母题-Q1-消息为什么会丢怎么才不丢]]）。
  • 对应母题：【Q1、Q2】
锚点

projects/数驭穹图/

  • 用在哪：队列在这里只承担"限流与排队"一个职责——按租户限制并发和队列、给查询设超时/扫描量/行数配额，超预算时拒绝、缩小范围或转异步（08-查询性能与成本控制.md）。不承担解耦，也不承担削峰。
  • 解决什么问题：保护源库不被慢 SQL 打穿。SQL 执行是不确定的（数据倾斜、统计信息过期都会让它变慢），所以必须有硬超时、取消和租户配额——这是"队列最小的用法"：不为削峰，只为排队。
  • 踩过的坑：无依赖子查询可以并发，但写回顺序必须确定——这是 Q2 说的"局部串行"在非 MQ 场景里的同一个问题。
  • 决策与取舍：异步是预算超支后的降级动作，不是默认路径——默认同步返回，超预算才转异步。"什么时候把同步改成异步"是产品问题，不是技术偏好。
  • 对应母题：【Q1、Q2】
锚点

projects/RuleArena/

  • 用在哪：这是本卡的主证据。 架构是 PostgreSQL 存权威状态 + Redis/ARQ 负责队列、限流与短期进度（06-architecture-and-scenarios.md）；04-idempotency-and-recovery.md §9 直接叫「Worker、队列与至少一次投递」，并有一节专答「Q5：消息队列能保证 exactly-once 吗」。Worker 跑一条规则审查是长任务，进程随时可能崩。
  • 解决什么问题："队列可以丢或重投，业务正确性必须落在可恢复的权威数据库里"——这一句就是 Q2 的全部答案。系统接受至少一次投递和进程随时崩溃，靠不重复的业务副作用把这个前提吃掉：同一数据库事务里完成聚合更新、账本、BusinessEvent 和 ActionReceipt，用唯一约束保证同一动作只生效一次。
  • 踩过的坑：① 不能拿 ToolCallID 当幂等键——它每次调用都变，重试时对不上；正确的是按「run + 动作 + 目标 + 参数 + 规则版本 + 逻辑步骤」构造稳定幂等键（这是 Q2 里"幂等键怎么选"的原题）；② Worker 超时后不许换 key 直接重试——先查 Receipt，已完成就继续，明确失败才按错误类型决定重试，仍无法确认就记 ACTION_UNKNOWN 并停下（这就是"超时 ≠ 失败"）。
  • 决策与取舍：不提前引入 Kafka / Outbox，升级条件是"出现真实的跨服务事件投递需求"（04 §9 末尾）。当前用 %RETRY% 式的重投 + 权威状态查询就够了。队列选 Redis/ARQ 而不是 RabbitMQ/Kafka，理由是 MVP 阶段要的是"能异步跑、能查状态"，不是"高吞吐 + 丰富特性"（这条取舍正是 Q3 选型节的判据）。
  • 对应母题：【Q1、Q2、Q3】
