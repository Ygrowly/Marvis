S4语义层与 Ontology：NL2SQL 的准确率上限为什么是"口径"而不是模型，含义该存在哪里

骨架：先用一道口径题暴露问题（同一句话 6 个"正确"答案）→ 给根因（模型没有业务先验 / 错误主要来自业务定义）→ 语义的三种存放位置对比 → 语义层是什么（三层知识 + 六节卡片 + 状态机 + 健康度 + fail closed）→ 区分检索层与语义层 → 拆"塞提示词"为什么不够 → Ontology 的两种用法与为什么现在热（因为 Agent 要做事）→ 边界（不要为了建本体而建本体）

一句话结论：NL2SQL 的准确率上限不在模型，在"业务定义"——模型没有业务先验，它看到 pay_amount 不知道这是下单金额、实付还是净额；而企业分析中的大多数错误不是 SQL 语法错误，而是业务定义错误（语法全对但口径错，而且错了看不出来）。所以正确形态不是"让模型猜口径"，而是把口径做成可检索、可版本化、可审计的语义资产：三层知识（技术元数据自动抽取 / 业务语义人工确权 / 公共规则平台统一）、状态机（DRAFT → REVIEWED → PUBLISHED → DEPRECATED）、查询只用已发布版本并把语义版本写进溯源。把口径塞进提示词是最常见的偷懒解法，它的硬伤是上下文有上界、改了没记录、无法对账、无法评测、会漂移——正确做法是按问题检索后只注入相关的那几条。Ontology 这个词有两种用法：学术义指概念层的形式化定义（与"实例化的知识图谱"是"类定义 vs 对象集合"的关系），厂商语境指把数据、逻辑、动作打包成可操作层——两者的共同内核都是"显式表达含义，而不是让它隐含在代码里"，而这个内核在 Agent 时代变重要，是因为 Agent 还要"做事"，必须知道什么动作在什么状态下允许。

  • 模型没有业务先验
  • 错误主要来自业务定义而不是语法
  • 同一个词 3 口径 × 2 时间维度 = 6 个"语法正确的答案"
  • 语义的三种位置（人脑 / 提示词 / 系统）
  • 提示词的五个硬伤（预算、无版本、无法对账、无法评测、会漂移）
  • 三层知识（技术元数据 / 业务语义 / 公共规则）
  • 六节知识卡片（口径与关联约束是核心）
  • 状态机 + 语义版本进溯源
  • 检索找候选，语义层做确权（相似度解决不了"哪个现行有效"）
  • Ontology 两种用法：形式化本体 vs 数据+逻辑+动作的可操作层
  • Ontology 的 Action 层 ≈ 工具契约（[[母题-A2-工具调用与MCP边界]]）
  • 核心指标没定义时暂停自动问数（fail closed）

主线："含义"必须是一个可以被系统管理的东西，而不是散在人脑、代码和提示词里的隐式约定。 这条主线能解释语义层的全部设计：为什么要有状态机（含义会过期）、为什么要确权（含义必须唯一且被授权）、为什么要检索（含义太多，上下文装不下）、为什么要写进溯源（含义有多版本，事后要对账）。把"含义"从隐式变成显式，就是这一整层的意义。

1. 为什么说 NL2SQL 的瓶颈是"口径"而不是模型能力？

因为模型没有业务先验（1.1）。同一个词在不同部门有不同定义，同样的 SQL 语法正确但结果不同，而且错了看不出来。模型能做的是"映射与使用"，不能是"创造定义"——后者必须由业务负责人确权。

2. 语义层和知识图谱什么关系？

要分清三层（4.1）：Ontology（学术义）= 概念层的定义（有哪些类型、允许什么关系与约束）；知识图谱 = 实例化的数据（具体有哪些实体与关系）；厂商语境的 Ontology = 数据 + 逻辑 + 动作的可操作层。"类定义 vs 对象集合"是理解前两者的关键。

3. 为什么不把所有指标定义写进系统提示词？

四件事同时不成立（3.2）：上下文有上界（Q2：只算 120 个核心指标就吃掉 16.7%）、无法版本化、无法对账、长提示词会漂移。正确做法是按问题检索后只注入相关的那几条，并把语义版本写进溯源。

4. 语义资产为什么需要状态机？

因为含义会过期（2.3）：表结构变了、业务规则变了、负责部门调整了——没有 DEPRECATED，旧口径会一直假装有效，而模型分不出来。配合"语义版本写进溯源"，才能事后回答"这个数按哪版算的"。

5. Agent 场景下，语义层要多做什么？

多一层"动作"（4.2）：BI 只要读，Agent 要写（下单、退款、改状态）——系统必须显式声明"什么动作在什么状态下允许、谁有权做"，这就是工具契约（[[母题-A2-工具调用与MCP边界]]）与厂商语境 Ontology 的 Action 层。

6. 什么情况下不该建完整语义层？

看数据复杂度与团队规模（4.3）：数驭穹图的"钢人比较"写得很清楚——只用 DDL + 模型推理接入快、维护少，适合结构简单的场景；完整语义层建设成本高。 它的选择是"自动生成技术部分 + 人工确认高价值业务部分，不追求所有字段一次性治理"——按核心指标逐步确权才是务实形态。
