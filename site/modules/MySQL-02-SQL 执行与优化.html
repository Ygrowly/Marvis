M6一条 SQL 从连接到返回经历了什么（server 层 + 引擎层）草稿 · 待验收单卡 →

MySQL 的 server 层和引擎层各管什么？优化器在做什么决定？

一条 SELECT * FROM task WHERE status='PENDING' LIMIT 10 从客户端发出到结果返回，中间经历了哪些步骤？每一步都可能因为什么变慢？

一句话结论：连接器（鉴权与连接管理）→ 分析器（词法/语法解析）→ 优化器（选索引、选 JOIN 顺序、生成执行计划）→ 执行器（按计划逐行调用引擎接口）→ InnoDB 引擎层（Buffer Pool、索引、事务）→ 返回。server 层管"功能与计划"，引擎层管"数据怎么存怎么取"；慢的根源通常只有三种——扫描行数多、回表次数多、JOIN 顺序错。

  • 连接器
  • 查询缓存（8.0 已移除）
  • 分析器
  • 优化器
  • 执行器
  • Buffer Pool
  • server 层 vs 引擎层
  • 三种慢源

主线：优化器是整条链路里唯一"做决定"的环节——它决定走哪个索引、按什么顺序 JOIN。所以"SQL 慢"的第一嫌疑人永远是"优化器做错了决定"，而它做错的原因通常是"估算不准"（这条直接连到 M7）。

原理分解

一、五层链路（每层一句话说清）

层做什么可能因为什么出问题
连接器TCP 握手、鉴权、管理连接；长/短连接连接数暴涨、鉴权慢（少见）；长连接要 reset_connection 释放内存
~~查询缓存~~8.0 已移除——
分析器词法/语法分析，生成解析树语法错误（很快报错，不会是慢的原因）
优化器决定用哪个索引、按什么顺序 JOIN、是否用临时表/排序估算错 → 选错索引 → 这是最常见的慢因
执行器按计划循环调用引擎接口，判断条件、返回结果逐行回表（覆盖索引能省掉，M3）
InnoDBBuffer Pool 命中与否、加锁、写 undo/redo缓存冷（随机 IO）、锁等待、日志刷盘

二、为什么"查询缓存"被移除了（常见追问）

缓存键是整条 SQL 文本，失效条件是这张表只要有一个更新就全部失效：

  • 对更新频繁的表，命中率极低，还带来维护开销；
  • "查一次缓存白拿"的收益 < "每次更新都要清一堆缓存"的成本。

这条能推出一个通用结论：任何"以表为粒度整体失效"的缓存都会在写多的表上失效——这正是 EnergyOps 里"缓存一致性"那部分的设计依据（事务内写 Outbox / 版本缓存键，而不是"提交完顺手清缓存"）。

三、优化器在决定什么（这是本题的核心）

决定依据决定错了会怎样
用哪个索引（或者干脆不用）统计信息里的区分度、扫描代价估算明明有索引却走全表（M2 里"索引失效的最后一类"）
JOIN 顺序（谁做驱动表）小表驱动大表原则 + 各自的过滤后行数大表驱动小表 → 循环次数爆炸
是否用临时表 / 文件排序排序数据量与内存限制filesort 落盘 → 慢一个数量级

判断"优化器选错了"的方法：EXPLAIN 里看 key（实际用的索引）与 rows（估算扫描行数）——估算行数和实际差很远时，就是统计信息/选择性出了问题（PG 的对应解法见 P7；MySQL 侧主要靠 ANALYZE TABLE 更新统计信息）。

四、三种慢源（收口）

① 扫描行数多      → 索引没命中 / 选择性差 / 估算错
② 回表次数多      → 二级索引没覆盖，命中的每一行都要回聚簇索引（M3）
③ JOIN 顺序错     → 驱动表选错，循环次数爆炸

对应到 explain 的读法（M7 展开）：type 与 rows 对应 ①，Extra 里的 Using index（覆盖）/Using filesort（排序）/Using temporary（临时表）对应 ②③。

M7慢查询怎么定位；常见 SQL 优化手段（深分页、索引下推、in/exists、join 驱动表、count）草稿 · 待验收单卡 →

慢查询怎么定位？常见的 SQL 优化手段有哪些？

线上有条 SQL 偶尔 20 多秒。你按什么顺序定位？深分页 LIMIT 1000000, 10 为什么慢，怎么改？

一句话结论：定位按三步走——慢查询日志（找出来）→ EXPLAIN 看计划（type / key / rows / Extra）→ 确认扫描行数与回表。优化手段围绕"少扫、少回、少排"三件事：覆盖索引、最左前缀设计、索引下推（ICP）、深分页用游标定位或延迟关联、小表驱动大表、count(*) 走最小索引。特别的一条：索引失效不一定是写法错——可能是优化器估算后主动放弃（这是最容易漏的一类）。

  • 慢查询日志 long_query_time
  • explain 的 type 与 rows
  • 覆盖索引
  • 索引下推 ICP
  • 延迟关联（先查 id 再回表）
  • 深分页
  • 小表驱动大表
  • 优化器主动放弃索引

主线：所有 SQL 优化都在做同一件事：让"扫过的行"尽量等于"要返回的行"。 两者差距越大越慢——差距来自"没命中的扫描"（该过滤的没提前过滤）和"白拿的回表"（取回了不用的列）。所以每一种手段都能归到这两类里。

原理分解

一、定位三步（有章法，不是"打开 explain 看看"）

① 慢查询日志（long_query_time）→ 把问题 SQL 抓出来，先按出现频率 × 单次耗时排优先级
② EXPLAIN 看计划 → 判断问题类型
③ 按类型动手 → 再 explain 验证，最后压测确认

explain 四个字段的读法：

字段看什么
type访问方式，从好到坏：system > const > eq_ref > ref > range > index > ALL。ALL = 全表扫，index = 扫全索引（比 ALL 好一点点，也危险）
key实际用的索引。possible_keys 有但 key 为 NULL → 优化器主动放弃了（见第五节）
rows估算扫描行数——与实际差很远时说明统计信息/选择性有问题
ExtraUsing index（覆盖，好）/ Using filesort（额外排序）/ Using temporary（临时表）/ Using index condition（下推生效，M2 提过）

二、优化手段清单（按"少扫少回少排"归类）

少扫（让过滤更早发生）

  • 最左前缀设计：等值列在前、范围列在后（M2）；
  • 范围查询能缩就缩：LIMIT 之外，能用 id > ? 定位就不要按偏移量扫；
  • 不要 SELECT *：列少了，优化器才可能选覆盖索引。

少回（让索引自己回答完）

  • 覆盖索引：把 SELECT 的列都放进索引（M3）；
  • 索引下推 ICP（5.6+）：(age, name) 索引下，age=18 AND name LIKE '%三' 可以在索引层先过滤 name，把"符合条件才回表"变成"索引层就过滤掉不合格的"——大幅减少回表次数。explain 里显示 Using index condition。

少排（避免额外排序与临时表）

  • 让索引顺序匹配 ORDER BY（索引本身有序，天然省 filesort）；
  • 小表驱动大表：in / exists 的选择、JOIN 的驱动表顺序；
  • GROUP BY 尽量走索引列，避免临时表。

几个"知道就行"的点：count(*) ≈ count(1) > count(列)（要判空）；count(*) 没有专门的优化捷径，InnoDB 是真数（MyISAM 才有行数缓存——但业务表不该用 MyISAM）。

三、深分页：LIMIT 1000000, 10 为什么慢

它不是"取 10 行"，而是"取前 1000010 行，丢掉前 100 万行"——扫描与回表量等于偏移量，所以越翻越慢。

两种解法：

① 游标定位（首选）：记住上一页最后一条的排序键，下一页用条件跳过去：

SELECT ... WHERE id > :last_id ORDER BY id LIMIT 10;   -- 恒定扫描 10 行

② 延迟关联：必须跳页时，先用覆盖索引把 id 捞出来，再回表取详情：

SELECT t.* FROM task t
JOIN (SELECT id FROM task ORDER BY id LIMIT 1000000, 10) s ON t.id = s.id;

子查询走覆盖索引（只扫索引，不回表），回表只发生在最后 10 行上——把"100 万次回表"降成"10 次回表"。

四、优化器主动放弃索引（最容易被漏掉的一类）

现象：索引存在、条件也该走索引，explain 却显示 key = NULL、全表扫。

原因：优化器估算过成本——当它判断"走索引 + 大量回表"比"顺序扫全表"更贵时，主动放弃索引是正确行为。典型触发：

  • 二级索引命中比例过高（比如要取 30% 的行）；
  • 统计信息过期（行数/区分度估错）；
  • 条件是表达式/函数/隐式类型转换（M2 的失效清单）。

所以排查顺序是：先看是不是"写法问题"（失效清单），再看是不是"成本判断"——后者改法不是改 SQL，而是 ① ANALYZE TABLE 更新统计信息，② 用 FORCE INDEX 验证"走了索引确实更快"（确认判断确实错了再强推），③ 或者接受全表扫（命中比例高时它就是对的）。

这一条的价值：它把"索引失效"从"背清单"升级成"理解优化器的成本模型"。

五、优化优先级（收口，面试必背）

① 先缩小业务范围（别把不相关的行扫进来）
② 再修 JOIN 逻辑与 N+1
③ 再建/改索引（含覆盖索引、下推）
④ 再改写 SQL（深分页、排序、count）
⑤ 最后才考虑缓存、预聚合、架构（M15）

EnergyOps 的实际顺序就是这条：修范围与 JOIN → 建联合索引 → 消 N+1 → 才谈缓存。反过来做（先上缓存）是典型的"在错误的链路上加速"。
