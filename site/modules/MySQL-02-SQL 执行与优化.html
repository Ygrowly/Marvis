一条 SQL 走五层：连接器（鉴权与连接管理）→ 分析器（词法语法解析）→ 优化器（选索引、选 JOIN 顺序、决定是否用临时表和排序）→ 执行器（按计划逐行调引擎接口）→ InnoDB 引擎层（Buffer Pool、索引、事务）。分工一句话：server 层管功能与计划，引擎层管数据怎么存怎么取。这个分层是架构约束——server 层要兼容多种引擎，代价是有些优化跨不了层。

题眼是：五层里只有优化器在做决定。所以「SQL 慢」的第一嫌疑人是它估算错了——它选的是「它估算出来的」最优计划，而估算依赖统计信息，统计过期、数据倾斜、条件带函数时就会错，代价能放大近 50 倍（990 万行回表对 62.5 万页全表扫）。慢的根源收口成三类：扫描行数多、回表次数多、JOIN 顺序错，每一类对应 EXPLAIN 里不同的字段。

另外 8.0 已经移除查询缓存：它以整表为失效粒度，写多的表上更新间隔比请求间隔还短，命中率趋近 0。最后提醒：EXPLAIN 的 rows 是估算值，要看实际值得用 EXPLAIN ANALYZE（8.0.18+）。

M7慢查询怎么定位；常见 SQL 优化手段（深分页、索引下推、in/exists、join 驱动表、count）

骨架：先把目标说清（扫过的行 ≈ 要返回的行）→ 定位三步 → explain 四字段 → 三组手段各治什么（少扫/少回/少排，各带一个数）→ 深分页专讲（扫描量 = 偏移量）→ 优化器主动放弃索引（最反直觉的一类）→ 优化优先级五步 → 收束到"先分类再动手"

一句话结论：定位按三步走——慢查询日志（按"频率 × 单次耗时"排优先级）→ EXPLAIN 看计划（type / key / rows / Extra）→ 按类型动手再 explain 验证。所有优化手段围绕"少扫、少回、少排"：少扫靠最左前缀设计与不用偏移量；少回靠覆盖索引与索引下推 ICP（ICP 把回表从 10,000 次降到 100 次）；少排靠让索引顺序匹配 ORDER BY。深分页的代价 = 偏移量（LIMIT 1000000, 10 要扫 1,000,010 行），首选游标定位（扫描与回表都降到 10），必须跳页时才用延迟关联（只降回表）。最容易漏的一类：索引失效不一定是写法错——优化器算过成本后主动放弃，命中 99% 时全表扫比走索引快约 47 倍。所以最后有一条不可颠倒的优化优先级：先缩小业务范围 → 修 JOIN 与 N+1 → 再改索引 → 再改写 SQL → 最后才上缓存。

定位三步：慢查询日志按「频率 × 单次耗时」排优先级 → EXPLAIN 看计划（type / key / rows / Extra）→ 动手改完再 EXPLAIN 验证。

深分页是典型：LIMIT 1000000, 10 要扫 1,000,010 行，代价就等于偏移量。首选游标定位（WHERE id > ?，扫描和回表都降到 10 行）；只有必须跳页时才用延迟关联，而它只降回表、不降扫描量。

边界：count(1) 和 count(*) 在 InnoDB 里基本一样，真正慢的是 count(列)（要判 NULL）；count(*) 慢的根因是 InnoDB 没有行数缓存、必须真数，是机制问题不是写法问题。

主线：优化器是整条链路里唯一"做决定"的环节——它决定走哪个索引、按什么顺序 JOIN。

1. 优化器怎么估行数？

按索引的区分度（基数）统计：SHOW INDEX 的 cardinality。估不准的常见原因：统计信息过期、数据倾斜（某个值占 90% 行）、条件是表达式/函数。PG 侧有扩展统计和更完整的直方图，MySQL 8.0 也有直方图，但两者都比"加索引"更少被人注意。

2. server 层和引擎层为什么要分开？

因为 server 层要兼容多种存储引擎（MyISAM/Memory/InnoDB），所以"解析、优化、执行"放上层，"存储与事务"由引擎各自实现。代价：有些优化跨不了层（早期 count(*) 必须逐行数，其实引擎知道行数但 server 层不知道）。能说出"分层是为可插拔、代价是有些优化跨不了层"，说明理解了架构取舍。

3. 一条 UPDATE 的链路和 SELECT 差在哪？

多了两阶段提交（[[母题-M11-三日志与两阶段提交]]）与锁获取（[[母题-M10-锁与死锁]]）；而且 UPDATE 是当前读（[[母题-M9-MVCC]]），不走 MVCC 快照。这条能把 M9/M10/M11 三张卡串起来。

4. 长连接和短连接怎么选？

长连接省握手与鉴权，但连接对象的内存会随执行增长，所以要定期 reset_connection；短连接每次都付握手 + 鉴权成本。连接池是两者的折中（PG 那边连接池是刚需，见 [[母题-P17-连接模型与连接池]]）。

主线：所有 SQL 优化都在做同一件事：让"扫过的行"尽量等于"要返回的行"。 差距只有两个来源：没命中的扫描（该过滤的没提前过滤）和白拿的回表（取回了不用的列）。每一种手段都能归到这两类里——归不进去的，说明还没搞清它在治什么。

1. 怎么确认统计信息错了？

对比 EXPLAIN 的 rows（估算）与 EXPLAIN ANALYZE（8.0.18+）的实际行数；差一个数量级以上就该 ANALYZE TABLE。这条和 PG 的 [[母题-P7-统计信息与慢查询定位]] 是同一件事的两个实现。

2. 那条 20 多秒的 SQL 你具体怎么定位的？

按顺序讲：估计 vs 实际行数 → 扫描方式 → JOIN 规模 → 排序/临时表 → loops（N+1）。重点不是"发现了什么"，而是"为什么按这个顺序"——每一步都对应一个明确的修复动作，做完立刻验证，不会白做。这一段要练成 60 秒口述。

3. 索引下推解决了什么？

回表前先过滤。没有 ICP 时 (age, name) 只能用 age = 18 定位，所有 age=18 的行都要回表；有 ICP 后在索引层就过滤 name，回表次数大幅下降。关键词是"回表次数"。

4. in 和 exists 怎么选？

小表驱动大表：子查询结果集小用 in，外表小用 exists。not in 遇到 NULL 或无法利用索引时要换 not exists。

5. ORDER BY 没走 filesort 但还是很慢？

排序不是唯一成本：可能回表次数多（SELECT *），或者扫描范围太大。"少排"解决了不代表"少扫少回"解决了——三类要分开看。
