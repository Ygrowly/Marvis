乐观并发控制在 PG 里怎么写？条件更新和 FOR UPDATE 怎么选？

两个 Worker 同时认领同一个任务。用 SELECT ... FOR UPDATE 锁住再改，有什么问题？不用锁怎么写？

一句话结论：「先查再写」必然有竞态（两个请求都读到合法状态），唯一解法是让判断和写入不可分割。条件更新就是把判断条件搬进 WHERE——影响 1 行 = 成功，影响 0 行 = 别人先改了，0 行是一个正常业务分支，不是异常。它相对 FOR UPDATE 的好处是三条：冲突时不排队（立即返回 0 行）、基本无死锁、天然幂等（重复执行第二次影响 0 行）。判据是冲突频率：冲突低 → 条件更新；冲突高到重试成本超过加锁成本 → 才用悲观锁。

  • 先查再写有竞态
  • 判断与写入压进一条语句
  • 影响行数 0 是正常分支
  • RETURNING 省一次往返
  • 版本号还是状态
  • 乐观天然幂等
  • FOR UPDATE 的吞吐上限 = 1 ÷ 持锁时长
  • 冲突高才用悲观

主线：并发正确性的单位是「一次原子操作」，不是「一段代码」。

1. 冲突高的时候该不该换成悲观锁？

先别急：条件更新的期望尝试是 1/(1−p)、有上界（p = 80% 也才 5 次）；而悲观锁的队列是无上界的。只有一种情况必须换：临界区里有不可重试的东西（跨行不变量、外部副作用）——那时要先把那些东西挪出去，再决定。

2. 版本号怎么设计？

单调递增的整数（version = version + 1），由数据库在同一条 UPDATE 里自增——不要在应用里算。而且要让版本号对所有会改这一行的路径都生效——漏一条路径，乐观锁就有个洞。

3. 影响 0 行之后到底该怎么处理？

读一次权威状态，按状态分三类：不存在 → 业务错误；状态不匹配 → 正常跳过（比如任务已被别人做完，直接返回）；版本不匹配 → 并发冲突（可以重试，重试次数按冲突率定）。「用一次权威读取替代对原因的猜测」是一条可以迁移到所有并发场景的原则（[[母题-P10-无间隙锁与锁变体]]）。

4. 乐观并发下能不能批量更新？

能，但要小心：一次 UPDATE ... WHERE ... 影响多行时，"影响行数"就不再是"我抢到了一行"那么简单——它变成了"我抢到了 N 行"。 判断逻辑要按 N 处理（比如抢批任务时 N > 0 就算抢到）。而 RETURNING 在多行时会把每行都返回——这是批量认领的正确姿势。

5. 这套和 MySQL 那边一样吗？

核心思想一样（判断与写入合并），但有两处不同：① MySQL 的 UPDATE 撞上时会【等锁】而不是"对更新后的版本重新求值"——等待超时是 innodb_lock_wait_timeout；② PG 的 UPDATE 拿的是 FOR NO KEY UPDATE，改键列会升级成 FOR UPDATE（[[母题-P10-无间隙锁与锁变体]]）——这会影响"会不会阻塞子表插入"（[[母题-M16-乐观锁与悲观锁]]）。

唯一约束为什么是幂等的最终防线？UPSERT（ON CONFLICT）怎么用、有哪些坑？

消息队列按「至少一次」投递，同一个业务动作可能被投递两次。你怎么保证业务效果只有一次？

一句话结论：因为它是数据库级别、原子、且对所有并发路径都生效的——应用层的「先查再插」有竞态（P18 讲过），而唯一约束让第二次插入直接失败，从结构上堵住了。前提是幂等键要基于业务身份构造（run_id + 动作类型 + 目标 + 参数 + 规则版本 + 逻辑步骤），并且参与约束的列必须 NOT NULL（PG 里 NULL 彼此不相等，否则约束会漏）。UPSERT 用 INSERT ... ON CONFLICT ... DO NOTHING / DO UPDATE。

  • 唯一约束是原子防线
  • 应用层幂等是优化
  • 先查再插有竞态
  • 幂等键基于业务身份（不能用 ToolCallID）
  • 约束列必须 NOT NULL
  • ON CONFLICT DO NOTHING vs DO UPDATE
  • 唯一索引推断（inference）
  • 冲突也消耗序列值

主线：幂等的最终责任必须落在数据库约束上。 应用层做幂等只能减少无效尝试（省资源），不能提供正确性保证——因为任何「查—判断—写」在多进程/多副本下都有窗口。唯一约束是唯一一个"无论如何都拦得住"的位置。

1. ON CONFLICT DO NOTHING 和 DO UPDATE 怎么选？

DO NOTHING 用于幂等写入（"做过了就不管"）；DO UPDATE 用于"存在就更新"（计数器累加、状态推进）。注意 DO UPDATE 拿的是行锁，而且会是"最后写入获胜"——要防止覆盖别人的更新，就得在 SET 里带条件（SET v = t.v + 1 WHERE t.v = :expected）。而 DO UPDATE 也会消耗序列值。

2. 为什么不能只靠应用层的分布式锁？

因为它引入了新的失效模式：锁的获取可能失败/超时；持锁进程挂掉后锁的释放要靠 TTL（于是又有"锁过期了活还没干完"的窗口）。 而数据库约束没有这些——它就在唯一的权威副本上。

3. Receipt 的 status 字段有什么用？

它解决"副作用做到一半崩溃"：Receipt 的处理状态是四态——ACCEPTED / COMPLETED / REJECTED / UNKNOWN（项目文档 04 §4），不是简单的两态。重投时看到 ACCEPTED 说明"上一次可能没做完"，这时要走【权威查询】去确认实际状态；只有 COMPLETED 才能直接复用原结果；REJECTED 是确定性失败；UNKNOWN 要停分支并保留证据（[[母题-P18-乐观并发控制]] 的「用一次权威读取替代猜测」）。

4. 序列会被填满吗？

会，而且比预期快（冲突也消耗）。官方原话是序列"不能用来获得无空洞的序列"——所以主键连续这个期待本身就该放下。 要抗高写入量就用 bigint，别在 int4 上赌。

5. 这套在分区表上有什么额外的坑？

两个：① 唯一约束必须包含所有分区键列（[[母题-P16-分区表]]），所以幂等键的组成会被分区键绑住；② ON CONFLICT DO UPDATE 不能更新分区键（官方明确不支持"需要移动到新分区"的更新）。这两条在"分区 + 幂等"叠加时必须在设计阶段就验证。
