乐观并发控制在 PG 里怎么做？为什么你项目里选它而不选 FOR UPDATE？

两个 Worker 同时认领同一个任务，怎么保证只有一个成功、而且不靠加锁？

一句话结论：条件更新——把「我期望的状态」写进 WHERE：

  • 条件更新
  • 期望状态进 WHERE
  • version 或状态机做期望
  • **影响行数 0 = 冲突**
  • 与 `FOR UPDATE` 取舍
  • 无锁可重试
  • 跨行不变量要靠约束
  • `RETURNING`

主线：乐观并发控制的正确性不来自「不加锁」，而来自「把判断和写入合并成一条语句」。 只要判断和写入是两个步骤，中间就一定有窗口——这不是概率问题，是结构问题。

原理分解

一、先讲清楚「先查再写」为什么必然有竞态

Worker A: SELECT ... WHERE id=1 AND status='QUEUED'   → 查到
Worker B: SELECT ... WHERE id=1 AND status='QUEUED'   → 也查到
Worker A: UPDATE ... SET status='RUNNING' WHERE id=1  → 成功
Worker B: UPDATE ... SET status='RUNNING' WHERE id=1  → 也成功 ← 重复认领

两个请求都"读到了合法状态"，所以都认为自己有资格改。 在 RC（PG 默认，P8）下这完全可能，因为两条语句各自取快照，中间没有任何东西阻止另一个事务提交。

唯一能救的办法是让「判断」和「写入」不可分割。 三条路：

1. 加锁（SELECT ... FOR UPDATE）——把中间窗口锁住； 2. 数据库约束（唯一约束）——让重复的那次直接失败（P19）； 3. 条件更新——把判断条件搬进 WHERE，让数据库在一次原子操作里同时判断和写入。

第 3 条就是本题答案，也是 PG 项目里最常用的那条。

二、条件更新的完整形态

-- 认领任务：只有当前状态还是 QUEUED、且版本没变，才改成 RUNNING
UPDATE tasks
SET status = 'RUNNING',
    worker_id = :worker_id,
    started_at = now(),
    version = version + 1
WHERE id = :id
  AND status = 'QUEUED'
  AND version = :expected_version
RETURNING id, status, version;

三个要点：

① 判断依据可以是「状态」也可以是「版本号」，通常两个一起用：状态管业务语义（必须是 QUEUED 才能认领），版本管并发冲突（即便状态刚好又变回 QUEUED，版本也不会重复）。

② RETURNING 让这件事变成一次往返：认领成功时直接拿到更新后的行，不用再去 SELECT 一次。减少一次往返对连接占用和延迟都有意义（P17）。

③ 用「影响行数」判断结果，不要用异常：

影响行数含义处理
1认领成功继续执行
0别人先改了 / 状态不匹配 / 版本不匹配读出权威状态再决定（继续跳过、或重试、或报冲突）

「影响行数 0 不是错误」这个认知很关键——它是一个正常的业务分支，不需要抛异常、不需要重试循环。

三、为什么不用 FOR UPDATE

FOR UPDATE 是可行的（而且更"直观"），但在这个场景下有三处不划算：

维度FOR UPDATE条件更新
冲突时行为排队等待（可能超时/死锁）立即返回 0 行（无等待）
死锁风险有（多行多路径加锁顺序不一致）基本没有（无长持锁）
幂等性需要自己保证天然幂等（重复执行第二次影响 0 行）
连接占用事务持续到业务处理完一条语句就结束

再加上 PG 的一个特殊性（P10）：PG 没有间隙锁，所以「锁住一个范围以防别人插入」这件事本身做不到——也就是说，即使你用了 FOR UPDATE，它也只保护「已存在的行」，不会保护「还没出现的行」。在任务认领这种场景里，要保护的是"这一行的状态"，条件更新正好够用；而在需要跨行不变量的场景里，FOR UPDATE 也未必够——那要用约束或 SSI（P9）。

所以取舍判据是：冲突频率 × 锁等待成本 vs 重试成本。 冲突低 → 条件更新（乐观）；冲突高到重试成本超过加锁成本 → 才用悲观锁。

四、它覆盖不了什么（必须主动说出边界）

条件更新保护的是「同一行的状态转换」。它不能直接保护跨行不变量，比如：

已退款金额 + 本次退款 <= 已付金额        ← 跨列，但可以在同一个 UPDATE 里带上条件
用户多得的优惠 == 平台多付的成本          ← 跨表/跨行，条件更新做不到

处理方式分三层：

1. 能在同一条 SQL 里表达的条件，就写进 WHERE（RuleArena 的实际做法）：

UPDATE orders
SET refunded_amount = refunded_amount + :amount,
    version = version + 1
WHERE id = :id
  AND version = :expected_version
  AND refunded_amount + :amount <= paid_amount;

这条 SQL 一次性守住了三件事：版本没变（没被别人改过）、金额上限没被突破（超额时影响 0 行）、以及幂等（重复执行第二次失败）。这是"把不变量压进原子操作"的典范。

2. 跨行的重复性 → 唯一约束兜底（P19）； 3. 真正需要的跨行可串行化 → SSI（P9） 或显式加锁 + 统一顺序（P10）。

说清第 4 节这段，就把「乐观并发控制」从一个技巧升级成了一套有边界的方案。

五、冲突频繁时怎么办

条件更新在高冲突下会表现为「大量 0 行」——这不是错，但要处理：

  • 有界重试 + 退避 + 抖动（和 P9 的重试要求一样，但这里重试的是一条语句，不是整个事务，成本低得多）；
  • 限流 / 排队：把并发收敛到可接受范围（比如按任务分区，不同分区不互相冲突）；
  • 换模式：如果某个热点行必然被高频争抢（计数器、库存），考虑把它改成"队列串行化"（单一写入者）或挪到内存侧（Redis 的原子操作）——这是"改结构"而不是"调参数"。

唯一约束为什么是幂等的最终防线？UPSERT（ON CONFLICT）怎么用、有哪些坑？

消息队列按「至少一次」投递，同一个业务动作可能被投递两次。你怎么保证业务效果只有一次？

一句话结论：因为它是数据库级别、原子、且对所有并发路径都生效的——应用层的「先查再插」有竞态（P18 讲过），而唯一约束让第二次插入直接失败，从结构上堵住了。前提是幂等键要基于业务身份构造（run_id + 动作类型 + 目标 + 参数 + 规则版本 + 逻辑步骤），并且参与约束的列必须 NOT NULL（PG 里 NULL 彼此不相等，否则约束会漏）。UPSERT 用 INSERT ... ON CONFLICT ... DO NOTHING / DO UPDATE。

  • 唯一约束是原子防线
  • 应用层幂等是优化
  • 先查再插有竞态
  • 幂等键基于业务身份（**不能用 ToolCallID 这类技术 ID**）
  • 约束列必须 NOT NULL
  • `ON CONFLICT DO NOTHING` vs `DO UPDATE`
  • `excluded` 与条件覆盖
  • 冲突也消耗序列值

主线：幂等的最终责任必须落在数据库约束上。 应用层做幂等只能减少无效尝试（省资源），不能提供正确性保证——因为任何「查—判断—写」在多进程/多副本下都有窗口。唯一约束是唯一一个"无论如何都拦得住"的位置。

原理分解

一、为什么应用层幂等「不够」

幂等的常见应用层实现：

查：这个 idempotency_key 有没有处理过？
  没有 → 处理 → 记录
  有   → 直接返回上次结果

问题就在「查」和「记录」之间（和 P18 是同一个结构缺陷）：

实例 A: 查 → 不存在
实例 B: 查 → 不存在          ← 两个实例拿到同一个答案
实例 A: 处理 → 记录
实例 B: 处理 → 记录           ← 副作用发生了两次

读者会问：「那加锁不就行了？」——加锁可以，但有两个代价：① 锁是应用层的，一旦有第二台机器/第二个进程就失效（除非用分布式锁，那又引入新依赖和新的失效模式）；② 锁的获取本身可能失败/超时，于是又回到"要么重试要么放弃"的老问题。

所以判断是：应用层幂等能挡掉绝大多数重复（这是有价值的优化——省掉了重复的昂贵操作），但不能作为正确性保证。

二、唯一约束为什么是「最终防线」

它同时满足四个条件，缺一不可：

条件说明
原子插入与唯一性检查在数据库内部是一次操作，不存在「查—写」窗口
对所有路径生效不管来自哪个实例、哪个进程、哪条代码路径、甚至是运维手工插入，都拦得住
由持久状态保证约束建立在索引/数据上，不是内存状态（重启不丢）
失败是确定的第二次插入报 23505，语义明确，不会"有时成功有时失败"

所以正确的分工是：

应用层幂等：优化（减少无效的昂贵操作）
数据库约束：正确性（唯一一个"无论如何都拦得住"的位置）
权威查询：判定（Receipt/Snapshot 告诉你"它到底成没成"，P18 追问）

这三层合起来才是完整的幂等方案——只说其中一层都是不完整的。

三、幂等键怎么构造（含反例）

规则：基于业务身份构造，不依赖任何一次技术调用。

RuleArena 的组成（projects/RuleArena/04-idempotency-and-recovery.md）：

run_id + action_type + target_id + normalized_arguments + rule_version + logical_step

要能说出每一项挡的是什么：

组成挡什么
run_id不同运行的相同动作不能混为一谈
action_type同一目标的不同动作（退款 vs 发券）要分开
target_id同一动作作用在不同对象上要分开
normalized_arguments参数要归一化（顺序、大小写、数值表示），否则「同一个业务意图」会因为参数写法不同而被当成两次
rule_version规则变了之后，同一个动作是新的业务意图，不该复用旧结果
logical_step同一意图可能被合法地重复执行多次（比如重试策略的第 3 步），逻辑步骤要区分开

明确的反例（这是这道题最值钱的部分）：

不能用 ToolCallID 当幂等键。 因为它是由模型/运行时为"这一次调用"生成的，而同一个业务意图在这些情况下会产生不同的 ToolCallID：

  • 模型重新规划（换了调用方式）；
  • Worker 重启后恢复；
  • 会话恢复；
  • HTTP 超时后重新发起；
  • 两个策略恰好提出相同动作（各自生成自己的 ID）。

所以用 ToolCallID 做幂等键，等于"每次重试都换一把新钥匙"——约束永远不生效，重复副作用照样发生。 这条是"幂等设计里最典型的错误"，能讲出来直接体现项目深度。

四、NOT NULL：一个容易漏的坑

PG 里 NULL 彼此不相等（P5 提过），所以唯一约束允许多行 NULL。

后果：如果幂等键的某一列可为 NULL，那么「同一业务意图」可能因为该列为 NULL 而不被判定为重复，约束形同虚设。

所以规则是：参与唯一约束的列一律 NOT NULL；确实有可选维度时，用空字符串 / 哨兵值而不是 NULL（或者把可选维度塞进归一化后的参数哈希里）。

「设计唯一约束时必须检查 NOT NULL」——这是一个可以在 5 秒内检查完、但漏掉会致命的检查项。

五、UPSERT：两种形态与三个坑

-- 形态一：重复就跳过（幂等写入的默认选择）
INSERT INTO action_receipts (idempotency_key, run_id, action_type, status)
VALUES (:key, :run_id, :type, 'ACCEPTED')
ON CONFLICT (idempotency_key) DO NOTHING;

-- 形态二：重复就更新（"取最新"，要小心）
INSERT INTO counters (id, value)
VALUES (:id, 1)
ON CONFLICT (id) DO UPDATE
  SET value = counters.value + 1;

三个坑：

坑说明
DO UPDATE 可能把更新的旧值写回去如果目标是「保留最新」，必须加条件：... DO UPDATE SET ... WHERE excluded.updated_at > t.updated_at（excluded 指"本次想插入的那行"）。不加条件，一个延迟到达的旧请求就能覆盖掉新数据。
冲突也会消耗序列值INSERT ... ON CONFLICT 先尝试插入，所以自增序列会前进——于是主键会出现"空洞"。这是正常现象，不要试图修它。
并发下仍可能报错DO UPDATE 涉及行锁，同键高并发可能出现序列化失败或死锁（P9 / P10），所以重试逻辑依然需要。

还有一个语义选择：DO NOTHING 有一个副作用——它不告诉你是"真的插入了"还是"跳过了"（RETURNING 在这种情况下不返回行）。如果你需要区分，就得靠"有没有返回行"来判断：

有返回行 → 本次是新插入（首次执行）
无返回行 → 已有记录（重复执行）  ← 正是幂等判断需要的信号

这个技巧很实用：一条 INSERT ... ON CONFLICT DO NOTHING RETURNING 同时完成了「写入 + 幂等判定」——不需要先 SELECT，也不存在竞态。

六、落到项目（RuleArena 的真实设计）

projects/RuleArena/04-idempotency-and-recovery.md 里的做法值得逐条对照：

1. 唯一约束：UNIQUE(run_id, action_type, idempotency_key) —— 约束带上了业务身份前缀（不只是幂等键本身）； 2. 同一事务提交：业务效果 + 账本 + BusinessEvent + Receipt 在同一个事务里——否则会出现"业务成功但没有 Receipt"（无法判定）或"Receipt 成功但业务回滚"（假成功）； 3. Receipt 状态机：ACCEPTED / COMPLETED / REJECTED / UNKNOWN——把"不知道"变成一个显式状态（ACTION_UNKNOWN），而不是硬塞进成功或失败； 4. 超时后不换 key：重试仍用同一个幂等键，因为换了 key 就等于放弃幂等保护； 5. 业务校验 + 数据库约束都要有：业务校验给出清晰的错误信息，唯一约束防并发穿透——两者职责不同，不能互相替代。

第 5 条是这道题最好的收尾："清晰错误"是给人和业务看的，"原子约束"是给正确性看的——一个负责体验，一个负责不出错。
