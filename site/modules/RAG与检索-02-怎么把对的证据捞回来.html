一句话结论：召回和精排的优化目标不同——召回面对全量，目标是"不漏"，所以只能用便宜的方法（双塔，文档向量可预计算）；精排面对已经缩小过的候选集，目标是"排得准"，所以可以用贵的方法（交叉编码器）。两者的本质差别是"有没有词级交互"：双塔把 query 和 doc 分别编码，编码时看不到对方，所以"除外""不适用"这类否定词被平均掉（这是结构性损失，换更大的双塔也补不回来）；交叉编码器把两者拼在一起，能看到逐词交互。代价是延迟随候选数线性增长（5ms × N，重排 200 条就是 1 秒，比 ANN 召回慢两个数量级），所以常见折中是"召回几百 → 重排 50–100 → 进上下文 5–20"。收益要说清口径：Contextual Retrieval 里重排把失败率从 2.9% 降到 1.88%，相对重排前降 35%、相对基线累计降 67%——这两个数不能混。最后，Recall@K 高不等于答案好，还要看 nDCG@K。

主线：两路检索的盲区不重叠，所以"选哪一路"是个伪问题；真正的问题是"融合要怎么处理量纲不可比"，以及"权限要在哪一层拦"。 前者用 RRF 只排名不拼分解决，后者用 ACL Filter 前置解决——两个都是"不试图用错的方式解决错的问题"。

1. 向量检索和 BM25 怎么选？

按查询类型分桶评测：专有名词、编号、错误码偏 BM25；自然语言同义改写偏向量；企业知识通常混合检索后重排。选择由数据决定，不由偏好决定。

2. RRF 的 k 是干什么的？

它平滑高排名的差距：k 越大，第 1 名和第 2 名的贡献差距越小（1/(k+1) vs 1/(k+2)）。k=60 是社区默认值，k 太小会让"某一路单独第一"过于强势。

3. HNSW 为什么在精度和速度之间平衡得最好？

分层给了"对数级"的搜索路径（100 万节点约 5–6 层），贪心导航在每层只需要局部比较；而且它实现成熟、生态完善（ES、Faiss、Milvus 都默认支持）。

4. 多跳（multi-hop）问题怎么处理？

第二轮检索由第一轮发现的实体驱动。比如"某公司 CEO 的母校在哪"——先检索"公司 CEO"，再用找到的人名检索"母校"。这不是检索算法的问题，是查询规划的问题（见 [[母题-G3-重排与召回质量]]）。

5. 怎么防止 RAG 越权？

身份进入检索层、ACL filter 先于召回；缓存按租户 / 权限分区；引用和下载再次鉴权；做跨租户与撤权测试；日志避免记录敏感原文。

  • 边界与常见误解：RRF 融合不判断内容相关性深浅（那是交叉编码器的活），两级是串联不是二选一；K 取多大要用评测定（Anthropic 试 5/10/20，20 最好，但成本线性上升）。

一句话结论：召回和精排的优化目标不同——召回面对全量，目标是"不漏"，所以只能用便宜的方法（双塔，文档向量可预计算）；精排面对已经缩小过的候选集，目标是"排得准"，所以可以用贵的方法（交叉编码器）。两者的本质差别是"有没有词级交互"：双塔把 query 和 doc 分别编码，编码时看不到对方，所以"除外""不适用"这类否定词被平均掉（这是结构性损失，换更大的双塔也补不回来）；交叉编码器把两者拼在一起，能看到逐词交互。代价是延迟随候选数线性增长（5ms × N，重排 200 条就是 1 秒，比 ANN 召回慢两个数量级），所以常见折中是"召回几百 → 重排 50–100 → 进上下文 5–20"。收益要说清口径：Contextual Retrieval 里重排把失败率从 2.9% 降到 1.88%，相对重排前降 35%、相对基线累计降 67%——这两个数不能混。最后，Recall@K 高不等于答案好，还要看 nDCG@K。

  • 召回要"不漏"、精排要"排得准"
  • 双塔 = 分别编码 + 可预计算 + 无词级交互
  • 交叉编码器 = 拼在一起 + 不能预计算 + 有词级交互
  • 双塔的损失是结构性的，换大模型补不回来
  • 重排延迟 = 5ms × N（200 条 = 1 秒）
  • 常见折中：召回几百 → 重排 50–100 → 进上下文 5–20
  • 重排收益口径：绝对 1.02 个点 · 相对前一环 35% · 相对基线累计 67%
  • Recall@K 看"有没有捞到"，nDCG@K 看"排得对不对"

主线："能不能预计算"决定了"用在哪一阶段"。 双塔能预计算 → 用在召回（面对全量）；交叉编码器不能 → 用在精排（面对小候选集）。这不是模型优劣，是约束匹配。

1. 重排一定值得吗？

不一定。它是用延迟换质量，应该通过 Eval 判断是否只在难题启用。精确编号、单跳事实这类查询，召回本身已经排得很准，重排收益很小。archive/study-courses/03 的结论就是"应通过 Eval 判断是否只在难题启用"。

2. K 该取多少？

Anthropic 试了 5 / 10 / 20，20 最好；但 K 大会带来重排成本线性上升 + 上下文预算被占。所以 K 要按"召回率 vs 成本"用评测定，并且要和重排的候选数、最终进上下文的条数一起考虑。

3. 多跳（multi-hop）问题重排能解决吗？

不能。重排只是把已有候选重排；多跳需要的候选压根不在池子里。要解决它得靠 Query Decomposition（多条件问题拆成子查询）或 Multi-hop 检索（第二轮由第一轮发现的实体驱动）。

4. 多路召回和重排是什么关系？

前者解决"捞得全"，后者解决"排得准"。RRF 融合只是把两路的排名合成一个顺序（[[母题-G2-向量与关键词的混合检索]]），它不判断内容相关性的深浅——那正是交叉编码器要做的事。两级是串联的，不是二选一。
