S3什么时候不该用关系数据库：缓存、文档、搜索、向量、图各自的边界在哪

骨架：先给唯一判据（查询的入口）→ 关系库的强项与它的反面（五类做不好的查询形状）→ 澄清"能做 ≠ 划得来" → 五类专有存储各一段（擅长 / 结构来源 / 牺牲了什么）→ 用四个需求演练一遍 → 引入六项固定成本（本卡落点）→ RuleArena 的正面样本 → 边界（Redis 不能当数据库、ES 不能当唯一数据源、图被高估、向量库不是必需品）

一句话结论：判断该不该用关系库，只看一件事——这次查询的"入口"是什么。 入口是主键/范围 → 关系库（B+ 树就是为等值、范围、前缀、排序设计的）；入口是关键词 → 检索库（倒排索引，LIKE '%x%' 用不上 B+ 树而且没有"相关性"这个概念）；入口是向量距离 → 向量索引（相似度不是可排序的一维标量）；入口是关系路径 → 图（多跳时 JOIN 会组合爆炸）；入口是纯 key → 键值库。但"能做 ≠ 划得来"：关系库靠 JSONB、递归 CTE、pg_trgm 这些也能做，所以真正的判断是算账——引入任何新引擎都要付六项固定成本（同步链路、谁是准的、失败点、运维监控、学习协作、存储资源），而这六项不随数据量缩小，所以数据量越小、团队越小，越不该引入。落到项目上：RuleArena 的选型卡就是正面样本——PostgreSQL 存权威状态，Redis 只做队列与限流，并明确写下"Redis 不能做权威状态"和升级条件。

  • 入口决定结构（主键 / 关键词 / 向量 / 关系路径 / key）
  • 倒排索引 vs B+ 树是相反的组织方式
  • LIKE '%x%' 用不上索引且无相关性
  • 相似度不是可排序标量
  • 图只在深度多跳时有优势
  • 能做 ≠ 划得来
  • Redis 与 ES 都不是权威存储（一个易失、一个近实时无事务）
  • pgvector = 少一个引擎
  • 引入六项固定成本，不随数据量缩小
  • RuleArena：PG 权威 + Redis 队列 + 写清升级条件
  • 引擎数量是成本项，不是能力项

主线：存储选型的顺序是：先问"查询的入口"，再问"能不能用现有的顶住"，最后才问"引入哪个"。 大多数选型失误不是因为选错了引擎，而是因为跳过了第二步——没有回答"用现有引擎顶住会付出什么代价"，就直接跳到了"引入新的"。所以每条引入决策都应该配一句升级条件（什么信号出现时才换），这一句是把"感觉"变成"判据"的关键。

1. Redis 能做持久化，为什么不能当数据库？

它缺的不只是持久化：还有事务强度、容量上界（内存 + 淘汰机制）、查询能力。判断依据是"这类数据丢了会怎样"——能重新算出来的（会话、计数、队列进度）可以放；算不出来的（订单、账）不行。RuleArena 把这条直接写进了选型卡：Redis 同时做权威状态 → "持久和事务不足"，淘汰。

2. 为什么 LIKE '%关键词%' 加索引也没用？

前置通配符让 B+ 树无法做任何裁剪（B+ 树是按值得顺序排的，从中间开始匹配就跳不过任何数据）。而且检索要的是"相关性排序"，关系库没有这个概念。

3. 做 RAG 一定要上独立向量库吗？

不一定。判据是规模与能力要求：小规模 + 已有 PostgreSQL → pgvector 更划算（少一个引擎就是少六项成本）；数据量大或需要专门的混合检索、多路召回能力 → 独立向量库。"标配"这个说法跳过了算账。

4. ES 能当主库用吗？

不建议。它的写入是近实时的（有刷新周期），而且通常不提供跨文档 ACID 事务——它不是为权威存储设计的。正确形态是：权威数据在关系库/对象存储，ES 是为检索优化的一份副本。

5. 怎么判断"该不该引入一个新引擎"？

三步：① 这个负载的查询入口是什么（现有引擎真的做不好吗）② 用现有引擎顶住会付出什么代价（能不能接受）③ 引入要付六项固定成本，收益是否大于它。并且无论结论如何，都写下升级条件。

6. 多引擎架构最大的隐性成本是什么？

不是钱，是"谁是准的"。两份数据必然出现对不上的时候（summaries/oceanBase.md 把这条列为"数据一致性风险"），而这个问题会以"报表和明细对不上"的形式反复出现，且对账机制必须提前设计，不能事后补。

判断该不该用关系库，只看一件事——这次查询的"入口"是什么。

入口是主键 / 范围 → 关系库（B+ 树就是为等值、范围、前缀、排序设计的）；入口是关键词 → 检索库（倒排索引；LIKE '%x%' 用不上 B+ 树，而且没有"相关性"这个概念）；入口是向量距离 → 向量索引（相似度不是可排序的一维标量）；入口是关系路径 → 图（多跳时 JOIN 会组合爆炸）；入口是纯 key → 键值库。

分层要点追问深挖时用

  • 结论：按查询入口选型；能做不等于划得来，要算引入新组件的四笔成本。
  • 推导链：入口类型 → 各自适配的存储（B+ 树/倒排/向量/图/KV）→ 关系库能勉强替代 → 判据变成算账。
  • 量化：无（判据为主）。
  • 边界与常见误解：LIKE '%x%' 用不上 B+ 树；多跳关系用 JOIN 会组合爆炸。
