M1为什么 InnoDB 用 B+ 树，不用 B 树 / 红黑树 / 哈希草稿 · 待验收单卡 →

InnoDB 的索引底层是 B+ 树。为什么是 B+ 树，而不是 B 树、红黑树或哈希表？

一句话结论：B+ 树是为磁盘 IO 次数最少而设计的——非叶节点只存键让扇出达到约 1170、树高压到 3 层；叶子双向链表让范围查询一次下降后顺序扫；页与磁盘块对齐让每次 IO 都不浪费。于是查 2000 万行只要 3 次 IO，而红黑树要约 24 次。

  • IO 次数是唯一指标
  • 页与扇出
  • 非叶只存键
  • 叶子双向链表
  • 树高 = log 扇出
  • 三次 IO 两千万行
  • 回表另算

主线：磁盘随机 IO 是瓶颈（比内存慢约 5 个数量级），所以索引结构的唯一目标是把定位一条记录所需的 IO 次数，从「行数」降到「树高」。

1. 既然 B+ 树这么矮，为什么还要尽量走覆盖索引？

树高决定的是定位索引项的成本；二级索引查到的是主键值，要取整行还得回表再查一次聚簇索引。树高只有 3 层，可命中的每一行都要多付一次回表 IO——扫 1000 行时，回表才是大头（连到 [[母题-M3-聚簇索引与回表]]）。

2. 叶子的链表为什么做成双向的？

范围查询本身只需向右；但 ORDER BY ... DESC 的反向扫描与部分优化器路径需要向左。双向的代价只是每个叶子多 6 字节，换来的是与扫描方向无关。

3. 为什么 InnoDB 的页是 16KB？

它是"一次 IO 的效率"与"扇出/浪费"之间的折中。SSD 时代也可以配更大（如 32KB），但页越大，一次读进当前用不上的数据也越多。

M2联合索引与最左前缀为什么存在；索引失效有哪些场景草稿 · 待验收单卡 →

任务表要支持这条调度 SQL：

SELECT id, status, next_retry_time, priority
FROM task
WHERE status = 'PENDING'
  AND next_retry_time <= NOW()
ORDER BY priority DESC, id ASC
LIMIT 100;

联合索引该怎么建？为什么 (a, b, c) 能用上 a = 1 和 a = 1 AND b = 2，却用不上单独 b = 2？

一句话结论：联合索引 (a, b, c) 是按字典序排的——先按 a、a 相同按 b、b 相同按 c。所以只有从最左列开始的连续前缀才能确定一个"可定位区间"，从而缩小扫描范围；中间的列断开，后面的列就只能过滤、不能定位。

  • 字典序逐层细分
  • 可定位区间必须连续
  • 扫描量 = 区间长度
  • 局部有序 = 全局无序
  • 等值在前范围靠后
  • 范围列之后失去定位保留过滤（ICP）
  • 选择度低优化器主动放弃

主线：索引的有序性只有三种用法——定位、截断、免排序，三者共享同一个前提：满足条件的记录在索引里连续。 字段顺序就是在"让哪段连续"上做取舍。

1. 为什么 WHERE b = 2 用不上 (a, b, c)？

因为 b 在每个 a 段内有序、段之间无序，找不到一个包含全部结果的连续区间。"用不上"准确含义是退化成扫描量≈全部，不是报错。

2. 范围列后面的列到底还能不能用？

能过滤（ICP），不能定位。省回表，不省扫描。

3. (a, b) 和 (b, a) 该选哪个？

看去重后的基数（选择度）和查询比例。等值列在前能让切出的段最短；但如果业务里 b 才是高频等值且区分度高，两个顺序的收益就会反转。这是数据分布问题，不是规则问题。

4. 为什么 status 这种列建了索引也不走？

选择度太低，优化器算成本后主动放弃。先看区分度，再看写法。

M3聚簇索引、回表、覆盖索引：explain 里怎么看出来草稿 · 待验收单卡 →

同一条 SQL，有时加个索引就快 10 倍，有时加了没用。EXPLAIN 出来怎么看它到底走没走索引、慢在哪一步？

一句话结论：InnoDB 是索引组织表——主键索引的叶子就是整行数据，二级索引的叶子只是「索引列 + 主键」。所以"先用二级索引、再取非索引列"要付出两次 B+ 树查找的代价，这就是回表；它随命中行数线性增长，且是随机 IO。覆盖索引把需要的列全放进索引里，让第二次查找消失（Extra 出现 Using index）。

  • 索引组织表 vs 堆表
  • 主键即数据
  • 二级索引叶子 = 索引列 + 主键
  • 主键被复制 N+1 份
  • 回表 = 第二次查找、随行数增长、随机 IO
  • 覆盖索引 = 免掉第二次
  • 代价是写放大

主线：InnoDB 把"表"和"主键索引"合成了一份数据结构。 好处是按主键查只需一次下降；代价是主键出现在每一个二级索引里，于是"主键怎么选"变成了全表级的成本问题，而"取不在索引里的列"变成了一次额外查找。

1. 既然覆盖索引能免回表，为什么不全表都建宽索引？

索引是欠写入的债：越宽，每次 INSERT/UPDATE 维护成本越高、页里能装的项越少、树还可能多一层。而且索引多了会干扰优化器的选择。覆盖是给热点查询的，不是给全表的。

2. rows 很小就一定快吗？

不一定。它是估算值，且不含回表成本。扫 10 行的回表可能比扫 100 行的覆盖索引还慢。

3. SELECT * 为什么在 InnoDB 里代价更高？

它几乎必然需要回表（* 里的列不可能全在一条二级索引里），而且不可能被覆盖。

4. 为什么建议自增主键而不是 UUID？

两个层面：① 写入层面，随机主键导致页分裂（见 [[母题-M5-引擎与表设计基本盘]]）；② 存储层面，36B 主键被复制进每一个二级索引。第二点比第一点更常被忽略。

正本：wiki/topics/MySQL/母题-M3-聚簇索引与回表.md

M4索引的代价与大表变更：为什么「加个索引」可能把库搞挂草稿 · 待验收单卡 →

任务表 5000 万行，线上正在跑。现在要给 status 加一个索引，你直接执行 ALTER TABLE task ADD INDEX idx_status(status)。会发生什么？

一句话结论：索引的代价是三笔——写放大（一次写维护 N+1 棵 B+ 树）、空间（主键被复制进每个二级索引，BIGINT→UUID 能让单个索引膨胀 2.6 倍）、优化器负担。大表 DDL 的危险不在"扫 5000 万行慢"，而在 MDL：长事务持读锁 → DDL 等写锁 → 后续查询因队列 FIFO 全排在 DDL 后面 → 积压数 = QPS × 等待秒数（2000 QPS 等 30 秒 = 6 万个请求）→ 连接池打满 → 整个服务雪崩。LOCK=NONE 只解决"DDL 不阻塞别人"，没解决"别人阻塞 DDL"。 所以真正的处方式是：先查并处理长事务 + 设短 lock_wait_timeout + 按表规模选在线 DDL 或影子表 + 低峰执行 + 备回滚。

  • 三笔代价（写放大/空间/优化器负担）
  • 一次写维护 N+1 棵 B+ 树
  • 主键被复制进每个二级索引，BIGINT→UUID 膨胀 2.6 倍
  • MDL 连锁（读锁持住 → DDL 等写锁 → FIFO 不能插队 → 后续查询全排队）
  • 积压 = QPS × 等待秒数
  • 连接池打满 → 雪崩
  • LOCK=NONE 只解决一半
  • INPLACE 不是万能
  • pt-osc 触发器 vs gh-ost binlog
  • 任何情况都先查长事务

主线：索引是读的快照，写的负债。 它的全部代价都记在写入路径上；而大表变更的全部危险都来自锁的排队语义——不是"慢"，是"堵"。两件事都不由表的大小决定，而由"有没有人用、有没有人挡"决定。

1. LOCK=NONE 都开了，为什么还是可能卡住线上？

关键在于MDL 等待的连锁：长事务持读锁 → DDL 等写锁 → 后续查询再排在 DDL 后面。LOCK=NONE 只保证 DDL 执行期间不阻塞，不保证它不被别人阻塞。

2. 索引是不是越多越好？

不是。写放大 + 空间（还挤占 buffer pool）+ 优化器负担；判据是"有没有高频查询真的用它"。没被用上的索引应该主动删掉。

3. MySQL 和 PG 在这件事上有什么不同？

PG 用 CREATE INDEX CONCURRENTLY，它不会长时间持锁等，但代价是失败会留下 invalid 索引需要手动清理，而且不能在一个事务块里执行。

4. 为什么 NOT NULL + DEFAULT 加字段有时很快、有时很慢？

取决于能不能走 instant 路径。MySQL 8.0 支持 instant add column（元数据操作）；更早版本或某些类型会触发重建表。判断方式是看 ALGORITHM 到底是 INSTANT / INPLACE / COPY，不要凭版本印象。

M5引擎与表设计基本盘：MyISAM 与 InnoDB 差在哪；varchar/char、DATETIME/TIMESTAMP、主键怎么选草稿 · 待验收单卡 →

让你从零设计一张「任务表」——几十亿行、读写混合、以后还要按状态和时间捞任务。你会怎么选引擎、主键和字段类型？为什么不用 MyISAM？

一句话结论：选 InnoDB 是因为它的三条硬差异——支持事务、行级锁、崩溃恢复——正好对应业务表的三个硬要求；MyISAM 只适合"读多写少 + 无事务 + 数据可重建"。表设计的三条硬规则都有可算的依据：主键用自增（随机主键导致页分裂，填充率降到约一半、页数翻倍，还让缓存能装的页减半）、长度不定用 varchar（char(10) 存 'a' 占 10 字节 vs varchar(10) 占 2 字节，差 5 倍）、远期时间用 DATETIME（TIMESTAMP 只有 4 字节，2^31−1 秒 ÷ 31,557,600 ≈ 68 年，2038-01-19 溢出）。另外主键会被复制进每一个二级索引——BIGINT→UUID 让单个索引从 18B/条涨到 46B/条。

  • 三条硬差异（事务/行锁/崩溃恢复）
  • 索引组织表 vs 非聚集索引（叶子存主键 vs 存地址）
  • 自增=顺序写，随机=页分裂
  • 填充率 100%→50% → 页数翻倍 → 缓存减半
  • 主键被复制进每个二级索引，18B→46B
  • char 补空格、varchar 存长度（2 字节差 8 字节）
  • 2038-01-19 = 2^31−1 秒 ÷ 31,557,600 ≈ 68 年
  • 雪花是趋势递增，是折中不是替代

主线：表设计不是审美问题，是"写入路径顺不顺、存储紧不紧凑、以后改不改得动"的问题。 而这三件事里，主键选型的影响面最大——它是唯一一个"改一次就影响全表所有索引"的决策。

1. 页分裂到底损失什么？

① 分裂是同步写，抬高写入延迟；② 分裂后两页各约半满，同样的数据占更多页，范围扫描读更多页、缓存命中率下降；③ 顺序写变随机写，失去 B+ 树最大的性能来源。

2. 那用趋势递增的雪花 ID 不就好了？

可以，但注意两点：① 趋势递增不是严格递增，跨节点时钟回拨仍可能插到中间（概率远小于 UUID）；② 全局唯一 ID 通常位数更长（64 位），二级索引体积会变大。要接受这两个代价才叫权衡过。

3. char 和 varchar 谁快？

单看存取，定长略快（省长度字节、不用变长解析）；但只要长度不固定，char 浪费的空间远超这点收益。判断标准只有一句：长度是否真的固定。

4. 为什么 MySQL 有 DATETIME 还要 TIMESTAMP？

因为 TIMESTAMP 省一半空间、且带时区语义与自动更新，适合"创建/更新时间"这类只关心过去与现在的字段。代价是 2038 边界——所以它和时间范围是绑定的取舍，不能当通用时间类型。

5. InnoDB 相比 MyISAM 在索引实现上差在哪？

MyISAM 是非聚集索引：索引文件与数据文件分离，叶子存物理地址，查到后还要再去数据文件捞一次；InnoDB 是索引组织表：主键叶子存整行、二级索引叶子存主键值，所以要回表（[[母题-M3-聚簇索引与回表]]）。
