M1为什么 InnoDB 用 B+ 树，不用 B 树 / 红黑树 / 哈希

骨架：约束（IO 次数是唯一指标）→ 四个候选各是什么 → 逐个淘汰（哈希不能范围 / 红黑树扇出 2 / B 树扇出小且要回溯）→ B+ 树三个设计点 → 量化（三层 2000 万行）→ 边界（回表另算、LSM 是另一条路）

一句话结论：B+ 树是为磁盘 IO 次数最少而设计的——非叶节点只存键让扇出达到约 1170、树高压到 3 层；叶子双向链表让范围查询一次下降后顺序扫；页与磁盘块对齐让每次 IO 都不浪费。于是查 2000 万行只要 3 次 IO，而红黑树要约 24 次。

  • IO 次数是唯一指标
  • 页与扇出
  • 非叶只存键
  • 叶子双向链表
  • 树高 = log 扇出
  • 三次 IO 两千万行
  • 回表另算

实测 381 字 · 按 4 字/秒折算约 95 秒（秒数是估算，字数才是实测）

判据只有一个：磁盘随机读比内存随机访问慢约 5 个数量级（机械盘约 10 毫秒对内存约 100 纳秒），而一次 IO 读的是一整页（InnoDB 默认 16KB）、成本几乎不随读多少变化，所以评价索引结构只看「定位一行要几次 IO」，也就是树高。

四个候选逐个淘汰：哈希表只能等值、做不了范围；红黑树是二叉、扇出 2，2000 万行树高约 24 层、约 24 次 IO；B 树非叶也存数据，扇出被挤小、范围查询还要回溯父节点；B+ 树非叶只存键，扇出约 1170，三层就能覆盖约 2000 万行，只要 3 次 IO。它三个设计点各解决一件事：非叶只存键让扇出最大、树最矮；叶子双向链表让范围查询一次下降后顺序扫；页与磁盘块对齐让每次 IO 都不浪费。

边界：树矮只保证定位索引项便宜，二级索引查到的是主键，取整行还要回表，扫 1000 行时回表才是大头；写多读少的场景走另一条路——LSM 树（RocksDB / LevelDB）。

分层要点追问深挖时用

  • 结论：B+ 树是为「磁盘 IO 次数最少」设计的；唯一判据是「定位一行要几次 IO」，不是比较次数。
  • 推导链：IO 比内存慢约 5 个数量级 → 一次 IO 读一页、成本与数据量无关 → 判据落在树高 → 哈希不能范围 / 红黑树扇出 2 / B 树扇出被数据挤小且范围要回溯 → B+ 树非叶只存键。
  • 量化：页 16KB、扇出约 1170 → 三层约 2000 万行 = 3 次 IO；红黑树同样数据约 24 层 ≈ 24 次 IO。
  • 边界与常见误解：树矮 ≠ 快（回表才是大头）；红黑树只是「不适合做磁盘索引」，内存场景（Redis 跳表、Java 红黑树）完全合理；写多读少走 LSM，代价是读要多查几层 + 需要 compaction。
M2联合索引与最左前缀为什么存在；索引失效有哪些场景

骨架：成本指标是扫过的行数（不是树高）→ 字典序是什么 → 可定位区间 → 最左前缀是这个要求的后果 → 四种条件逐个判 → 范围列截断的准确说法（失去定位、保留 ICP 过滤）→ 字段顺序三条规则 + 排序的边界 → 失效场景（含优化器主动放弃）

一句话结论：联合索引 (a, b, c) 是按字典序排的——先按 a、a 相同按 b、b 相同按 c。所以只有从最左列开始的连续前缀才能确定一个"可定位区间"，从而缩小扫描范围；中间的列断开，后面的列就只能过滤、不能定位。

  • 字典序逐层细分
  • 可定位区间必须连续
  • 扫描量 = 区间长度
  • 局部有序 = 全局无序
  • 等值在前范围靠后
  • 范围列之后失去定位保留过滤（ICP）
  • 选择度低优化器主动放弃

实测 423 字 · 按 4 字/秒折算约 106 秒（秒数是估算，字数才是实测）

索引的价值只有一个——少扫。有序性能做三件事：定位、截断、免排序，前提都一样：满足条件的记录在索引里是连续的一段。

联合索引 (a, b, c) 按字典序排，所以只有从最左列开始的连续前缀能切出「可定位区间」。单独查 b = 2 用不上，是因为 b 只在每个 a 段内有序、段之间无序；「用不上」的准确含义是退化成扫描量约等于全表，不是报错。WHERE 里条件的书写顺序不影响，优化器按列集合重排。范围列之后的列失去定位、保留 ICP 过滤——省的是回表，不省的是扫描。

字段顺序三条：等值在前、范围靠后、选择度高的在前，再看能否免排序。所以那条调度 SQL 没有完美解：(status, next_retry_time, priority) 扫描约 3.3 万行但要 filesort；(status, priority, next_retry_time) 免排序却缩不了范围——选哪个看两边的选择度。

边界：索引列不是越多越好；选择度太低的列（status 这种）优化器会主动放弃，先问区分度再问写法。

分层要点追问深挖时用

  • 结论：联合索引按字典序排，只有最左连续前缀能切出「可定位区间」；有序性只有定位 / 截断 / 免排序三种用法，前提都是「结果在索引里连续」。
  • 推导链：固定指标（扫过的行数，不是树高）→ 字典序逐层细分 → 局部有序 = 全局无序 → 单独 b 找不到连续区间 → 范围列之后失去定位、保留 ICP 过滤。
  • 量化：调度 SQL 用 (status, next_retry_time, priority) 扫描约 3.3 万行但要 filesort；换 (status, priority, next_retry_time) 免排序却缩不了范围——取舍看选择度。
  • 边界与常见误解：条件书写顺序不影响匹配（优化器重排）；索引列越多越好 ×；建了索引优化器不一定用（选择度低会主动放弃）；前缀索引不能替代联合索引（丢完整有序性）。
M3聚簇索引、回表、覆盖索引：explain 里怎么看出来

骨架：索引组织表 vs 堆表（为什么 InnoDB 这么选）→ 两种索引的叶子装什么 → 二级索引为什么要带主键 → 回表的成本拆解（定位 / 扫描 / 回表三段，只有第三段随行数增长、且是随机 IO）→ 覆盖索引免掉它（Using index）与它的代价（写放大、索引变宽）→ EXPLAIN 四字段的阅读顺序 → 方言（PG 是堆表）

一句话结论：InnoDB 是索引组织表——主键索引的叶子就是整行数据，二级索引的叶子只是「索引列 + 主键」。所以"先用二级索引、再取非索引列"要付出两次 B+ 树查找的代价，这就是回表；它随命中行数线性增长，且是随机 IO。覆盖索引把需要的列全放进索引里，让第二次查找消失（Extra 出现 Using index）。

  • 索引组织表 vs 堆表
  • 主键即数据
  • 二级索引叶子 = 索引列 + 主键
  • 主键被复制 N+1 份
  • 回表 = 第二次查找、随行数增长、随机 IO
  • 覆盖索引 = 免掉第二次
  • 代价是写放大

实测 392 字 · 按 4 字/秒折算约 98 秒（秒数是估算，字数才是实测）

先说两种存法：堆表里索引叶子存行地址；InnoDB 是索引组织表，主键索引的叶子就是整行数据，二级索引的叶子只是「索引列 + 主键值」。

所以取非索引列要两次 B+ 树查找——先在二级索引树上定位到主键，再回聚簇索引取整行，第二次就是回表。成本拆成定位、扫描、回表三段，只有第三段随命中行数线性增长，而且是随机 IO：扫 1000 行就是 1000 次随机 IO，这才是「加了索引还是慢」的主因。

覆盖索引把需要的列全放进索引，让第二次查找消失，判据是 EXPLAIN 的 Extra 出现 Using index。代价要一起说：索引变宽、写入维护变贵、还可能干扰优化器，所以它是给热点查询的，不是给全表的。

EXPLAIN 只看四个字段：type、key、rows（估算值，且不含回表成本）、Extra（Using index 说明覆盖、Using filesort 说明还要排序）。边界：PG 是堆表，索引叶子存 ctid，一律回表。

分层要点追问深挖时用

  • 结论：InnoDB 是索引组织表；回表 = 第二次 B+ 树查找，随命中行数线性增长且是随机 IO；覆盖索引让它消失（Extra 出现 Using index）。
  • 推导链：两种存法 → InnoDB 的取舍（按主键查只需一次下降）→ 二级索引叶子必须带主键 → 取整行要再查一次 → 覆盖把需要的列放进索引 → 代价是写放大与索引变宽。
  • 量化：成本 = 定位 + 扫描 + 回表 × 命中行数；扫 1000 行 = 1000 次随机 IO；覆盖之后第三段归零。
  • 边界与常见误解：树高 3 层解释不了快慢差异（对所有查询都一样）；rows 小也可能慢（不含回表）；覆盖索引越宽越好 ×；PG 是堆表，一律回表。
M4索引的代价与大表变更：为什么「加个索引」可能把库搞挂

骨架：三笔代价（写放大给算式、空间给算式）→ 大表 DDL 的两步，指出危险在第二步 → MDL 队列 FIFO 的连锁推导 + 积压公式 → Online DDL 保证什么、没保证什么 → 影子表四步与 pt-osc/gh-ost 差异 → 按规模与可回滚性选 → 收束到"先查长事务 + 短 lock_wait_timeout"

一句话结论：索引的代价是三笔——写放大（一次写维护 N+1 棵 B+ 树）、空间（主键被复制进每个二级索引，BIGINT→UUID 能让单个索引膨胀 2.6 倍）、优化器负担。大表 DDL 的危险不在"扫 5000 万行慢"，而在 MDL：长事务持读锁 → DDL 等写锁 → 后续查询因队列 FIFO 全排在 DDL 后面 → 积压数 = QPS × 等待秒数（2000 QPS 等 30 秒 = 6 万个请求）→ 连接池打满 → 整个服务雪崩。LOCK=NONE 只解决"DDL 不阻塞别人"，没解决"别人阻塞 DDL"。 所以真正的处方式是：先查并处理长事务 + 设短 lock_wait_timeout + 按表规模选在线 DDL 或影子表 + 低峰执行 + 备回滚。

  • 三笔代价（写放大/空间/优化器负担）
  • 一次写维护 N+1 棵 B+ 树
  • 主键被复制进每个二级索引，BIGINT→UUID 膨胀 2.6 倍
  • MDL 连锁（读锁持住 → DDL 等写锁 → FIFO 不能插队 → 后续查询全排队）
  • 积压 = QPS × 等待秒数
  • 连接池打满 → 雪崩
  • LOCK=NONE 只解决一半
  • INPLACE 不是万能
  • pt-osc 触发器 vs gh-ost binlog
  • 任何情况都先查长事务

实测 446 字 · 按 4 字/秒折算约 112 秒（秒数是估算，字数才是实测）

索引的代价三笔：写放大（一次 INSERT 要维护 N+1 棵 B+ 树）、空间（主键被复制进每一个二级索引，BIGINT 换成 UUID 让单索引从 18B/条涨到 46B/条、约 2.6 倍）、优化器负担。没被用上的索引是纯负债。

大表 DDL 的危险不在「扫 5000 万行慢」，而在 MDL：DDL 要拿 MDL 写锁，前面有个长事务持着读锁没放，DDL 就只能在队列里等；MDL 队列是 FIFO，后面进来的查询全堵在它后面。积压数约等于 QPS × 等待秒数——2000 QPS 等 30 秒就是约 6 万个请求堆着，连接池打满、服务雪崩。

所以 LOCK=NONE 只解决「DDL 不阻塞别人」，没解决「别人阻塞 DDL」；ALGORITHM=INPLACE 也不是万能。

处方四步：先查并干掉长事务（前置动作，不是方案）；设短 lock_wait_timeout，让等待快速失败而不是无限堆积；按表规模与可回滚性选 Online DDL 还是影子表（pt-osc 用触发器、gh-ost 吃 binlog）；低峰执行 + 备好回滚。低峰只降低积压速度，不消除长事务这个触发源。

分层要点追问深挖时用

  • 结论：索引的代价是「每一次写」；大表 DDL 的危险是「不可控的等待」（MDL 连锁），不是扫描慢。两者都不是由表大不大决定的，是由有没有人用、有没有人挡决定的。
  • 推导链：三笔代价 → DDL 要做的两件事（改元数据 + 改数据）→ 危险在拿 MDL 写锁那一步 → 长事务持读锁 → DDL 排队 → 队列 FIFO 让后续查询一起堵 → 积压 = QPS × 等待秒数 → 连接池打满。
  • 量化：BIGINT→UUID 单索引 18B→46B（约 2.6 倍）；2000 QPS 等 30 秒 ≈ 6 万个请求积压。
  • 边界与常见误解：LOCK=NONE 只管一半；INPLACE 不是所有 DDL 都行（改列类型、重建聚簇只能重建表）；DROP INDEX 同样要拿 MDL；低峰是降速不是除因；完整动作 = 查长事务 + 短 lock_wait_timeout + 按规模选方案 + 低峰 + 备回滚。
M5引擎与表设计基本盘：MyISAM 与 InnoDB 差在哪；varchar/char、DATETIME/TIMESTAMP、主键怎么选

骨架：引擎三条硬差异 → 为什么 InnoDB 成默认（并发写 + 不能丢） → 主键必须自增（页分裂的三层损失 + 页数翻倍算式）→ 主键被复制进每个二级索引（18B vs 46B）→ varchar/char（5 倍差 + 补齐陷阱）→ DATETIME/TIMESTAMP（当场算 2038）→ 约束与范式（反范式要有执行计划支撑）

一句话结论：选 InnoDB 是因为它的三条硬差异——支持事务、行级锁、崩溃恢复——正好对应业务表的三个硬要求；MyISAM 只适合"读多写少 + 无事务 + 数据可重建"。表设计的三条硬规则都有可算的依据：主键用自增（随机主键导致页分裂，填充率降到约一半、页数翻倍，还让缓存能装的页减半）、长度不定用 varchar（char(10) 存 'a' 占 10 字节 vs varchar(10) 占 2 字节，差 5 倍）、远期时间用 DATETIME（TIMESTAMP 只有 4 字节，2^31−1 秒 ÷ 31,557,600 ≈ 68 年，2038-01-19 溢出）。另外主键会被复制进每一个二级索引——BIGINT→UUID 让单个索引从 18B/条涨到 46B/条。

  • 三条硬差异（事务/行锁/崩溃恢复）
  • 索引组织表 vs 非聚集索引（叶子存主键 vs 存地址）
  • 自增=顺序写，随机=页分裂
  • 填充率 100%→50% → 页数翻倍 → 缓存减半
  • 主键被复制进每个二级索引，18B→46B
  • char 补空格、varchar 存长度（2 字节差 8 字节）
  • 2038-01-19 = 2^31−1 秒 ÷ 31,557,600 ≈ 68 年
  • 雪花是趋势递增，是折中不是替代

实测 465 字 · 按 4 字/秒折算约 116 秒（秒数是估算，字数才是实测）

引擎三条硬差异：InnoDB 支持事务、行级锁、崩溃恢复，正好对应业务表的三个硬要求；MyISAM 是表级锁、不支持事务、崩溃可能丢数据，只在「读多写少 + 无事务 + 数据可重建」三者同时成立时才勉强可用。

主键用自增，代价可以算：随机主键是随机插入 → 页分裂 → 填充率从约 100% 掉到约一半、页数翻倍、缓存能装的页减半；更要紧的是主键会被复制进每一个二级索引，UUID 让单个索引从 18B/条涨到 46B/条。要全局唯一又趋势递增用雪花 ID，但得主动说它的代价：趋势递增不等于严格递增（时钟回拨仍可能乱序）、位数更长——它是折中，不是替代。

字段两条：长度不定用 varchar（char(10) 存 'a' 占 10 字节 vs varchar(10) 占 2 字节，差 5 倍）；远期时间用 DATETIME（TIMESTAMP 只有 4 字节，2^31−1 秒 ≈ 68 年，2038-01-19 溢出）。

边界：MySQL 的 DDL 会隐式提交、不能回滚，判据是「它有没有写 undo、会不会隐式提交」，不是「因为它是 DDL」——PG 的 DDL 是事务性的，DROP TABLE 可以 ROLLBACK。

分层要点追问深挖时用

  • 结论：引擎看事务 / 行锁 / 崩溃恢复三条；主键用自增、长度不定用 varchar、远期时间用 DATETIME。
  • 推导链：并发写 + 不能丢 → InnoDB 成默认 → 主键顺序决定写入是不是顺序 → 随机主键页分裂 → 主键还要被复制 N 份 → 字段宽度与时间边界决定存储紧不紧凑、以后改不改得动。
  • 量化：随机主键填充率约 100%→50%、页数翻倍、缓存减半；主键复制进每个二级索引，18B→46B；char(10) 10 字节 vs varchar(10) 2 字节，5 倍差；TIMESTAMP 2^31−1 秒 ≈ 68 年 → 2038-01-19 溢出。
  • 边界与常见误解：MyISAM 三个条件要同时成立；雪花 ID 是折中不是替代；「DDL 不能回滚」只在 MySQL 成立（PG 可 ROLLBACK），判据是写不写 undo；TRUNCATE 归 DDL 的判据是「怎么删」不是「删了什么」。

M1为什么 InnoDB 用 B+ 树，不用 B 树 / 红黑树 / 哈希单卡 →

InnoDB 的索引底层是 B+ 树。为什么是 B+ 树，而不是 B 树、红黑树或哈希表？

实测 381 字 · 按 4 字/秒折算约 95 秒（秒数是估算，字数才是实测）

判据只有一个：磁盘随机读比内存随机访问慢约 5 个数量级（机械盘约 10 毫秒对内存约 100 纳秒），而一次 IO 读的是一整页（InnoDB 默认 16KB）、成本几乎不随读多少变化，所以评价索引结构只看「定位一行要几次 IO」，也就是树高。

四个候选逐个淘汰：哈希表只能等值、做不了范围；红黑树是二叉、扇出 2，2000 万行树高约 24 层、约 24 次 IO；B 树非叶也存数据，扇出被挤小、范围查询还要回溯父节点；B+ 树非叶只存键，扇出约 1170，三层就能覆盖约 2000 万行，只要 3 次 IO。它三个设计点各解决一件事：非叶只存键让扇出最大、树最矮；叶子双向链表让范围查询一次下降后顺序扫；页与磁盘块对齐让每次 IO 都不浪费。

边界：树矮只保证定位索引项便宜，二级索引查到的是主键，取整行还要回表，扫 1000 行时回表才是大头；写多读少的场景走另一条路——LSM 树（RocksDB / LevelDB）。

分层要点追问深挖时用

  • 结论：B+ 树是为「磁盘 IO 次数最少」设计的；唯一判据是「定位一行要几次 IO」，不是比较次数。
  • 推导链：IO 比内存慢约 5 个数量级 → 一次 IO 读一页、成本与数据量无关 → 判据落在树高 → 哈希不能范围 / 红黑树扇出 2 / B 树扇出被数据挤小且范围要回溯 → B+ 树非叶只存键。
  • 量化：页 16KB、扇出约 1170 → 三层约 2000 万行 = 3 次 IO；红黑树同样数据约 24 层 ≈ 24 次 IO。
  • 边界与常见误解：树矮 ≠ 快（回表才是大头）；红黑树只是「不适合做磁盘索引」，内存场景（Redis 跳表、Java 红黑树）完全合理；写多读少走 LSM，代价是读要多查几层 + 需要 compaction。

一句话结论：B+ 树是为磁盘 IO 次数最少而设计的——非叶节点只存键让扇出达到约 1170、树高压到 3 层；叶子双向链表让范围查询一次下降后顺序扫；页与磁盘块对齐让每次 IO 都不浪费。于是查 2000 万行只要 3 次 IO，而红黑树要约 24 次。

  • IO 次数是唯一指标
  • 页与扇出
  • 非叶只存键
  • 叶子双向链表
  • 树高 = log 扇出
  • 三次 IO 两千万行
  • 回表另算

主线：磁盘随机 IO 是瓶颈（比内存慢约 5 个数量级），所以索引结构的唯一目标是把定位一条记录所需的 IO 次数，从「行数」降到「树高」。

1. 既然 B+ 树这么矮，为什么还要尽量走覆盖索引？

树高决定的是定位索引项的成本；二级索引查到的是主键值，要取整行还得回表再查一次聚簇索引。树高只有 3 层，可命中的每一行都要多付一次回表 IO——扫 1000 行时，回表才是大头（连到 [[母题-M3-聚簇索引与回表]]）。

2. 叶子的链表为什么做成双向的？

范围查询本身只需向右；但 ORDER BY ... DESC 的反向扫描与部分优化器路径需要向左。双向的代价只是每个叶子多 6 字节，换来的是与扫描方向无关。

3. 为什么 InnoDB 的页是 16KB？

它是"一次 IO 的效率"与"扇出/浪费"之间的折中。SSD 时代也可以配更大（如 32KB），但页越大，一次读进当前用不上的数据也越多。

联合索引该怎么建？为什么 (a, b, c) 能用上 a = 1 和 a = 1 AND b = 2，却用不上单独 b = 2？

实测 423 字 · 按 4 字/秒折算约 106 秒（秒数是估算，字数才是实测）

索引的价值只有一个——少扫。有序性能做三件事：定位、截断、免排序，前提都一样：满足条件的记录在索引里是连续的一段。

联合索引 (a, b, c) 按字典序排，所以只有从最左列开始的连续前缀能切出「可定位区间」。单独查 b = 2 用不上，是因为 b 只在每个 a 段内有序、段之间无序；「用不上」的准确含义是退化成扫描量约等于全表，不是报错。WHERE 里条件的书写顺序不影响，优化器按列集合重排。范围列之后的列失去定位、保留 ICP 过滤——省的是回表，不省的是扫描。

字段顺序三条：等值在前、范围靠后、选择度高的在前，再看能否免排序。所以那条调度 SQL 没有完美解：(status, next_retry_time, priority) 扫描约 3.3 万行但要 filesort；(status, priority, next_retry_time) 免排序却缩不了范围——选哪个看两边的选择度。

边界：索引列不是越多越好；选择度太低的列（status 这种）优化器会主动放弃，先问区分度再问写法。

分层要点追问深挖时用

  • 结论：联合索引按字典序排，只有最左连续前缀能切出「可定位区间」；有序性只有定位 / 截断 / 免排序三种用法，前提都是「结果在索引里连续」。
  • 推导链：固定指标（扫过的行数，不是树高）→ 字典序逐层细分 → 局部有序 = 全局无序 → 单独 b 找不到连续区间 → 范围列之后失去定位、保留 ICP 过滤。
  • 量化：调度 SQL 用 (status, next_retry_time, priority) 扫描约 3.3 万行但要 filesort；换 (status, priority, next_retry_time) 免排序却缩不了范围——取舍看选择度。
  • 边界与常见误解：条件书写顺序不影响匹配（优化器重排）；索引列越多越好 ×；建了索引优化器不一定用（选择度低会主动放弃）；前缀索引不能替代联合索引（丢完整有序性）。

一句话结论：联合索引 (a, b, c) 是按字典序排的——先按 a、a 相同按 b、b 相同按 c。所以只有从最左列开始的连续前缀才能确定一个"可定位区间"，从而缩小扫描范围；中间的列断开，后面的列就只能过滤、不能定位。

  • 字典序逐层细分
  • 可定位区间必须连续
  • 扫描量 = 区间长度
  • 局部有序 = 全局无序
  • 等值在前范围靠后
  • 范围列之后失去定位保留过滤（ICP）
  • 选择度低优化器主动放弃

主线：索引的有序性只有三种用法——定位、截断、免排序，三者共享同一个前提：满足条件的记录在索引里连续。 字段顺序就是在"让哪段连续"上做取舍。

1. 为什么 WHERE b = 2 用不上 (a, b, c)？

因为 b 在每个 a 段内有序、段之间无序，找不到一个包含全部结果的连续区间。"用不上"准确含义是退化成扫描量≈全部，不是报错。

2. 范围列后面的列到底还能不能用？

能过滤（ICP），不能定位。省回表，不省扫描。

3. (a, b) 和 (b, a) 该选哪个？

看去重后的基数（选择度）和查询比例。等值列在前能让切出的段最短；但如果业务里 b 才是高频等值且区分度高，两个顺序的收益就会反转。这是数据分布问题，不是规则问题。

4. 为什么 status 这种列建了索引也不走？

选择度太低，优化器算成本后主动放弃。先看区分度，再看写法。

M3聚簇索引、回表、覆盖索引：explain 里怎么看出来单卡 →

同一条 SQL，有时加个索引就快 10 倍，有时加了没用。EXPLAIN 出来怎么看它到底走没走索引、慢在哪一步？

实测 392 字 · 按 4 字/秒折算约 98 秒（秒数是估算，字数才是实测）

先说两种存法：堆表里索引叶子存行地址；InnoDB 是索引组织表，主键索引的叶子就是整行数据，二级索引的叶子只是「索引列 + 主键值」。

所以取非索引列要两次 B+ 树查找——先在二级索引树上定位到主键，再回聚簇索引取整行，第二次就是回表。成本拆成定位、扫描、回表三段，只有第三段随命中行数线性增长，而且是随机 IO：扫 1000 行就是 1000 次随机 IO，这才是「加了索引还是慢」的主因。

覆盖索引把需要的列全放进索引，让第二次查找消失，判据是 EXPLAIN 的 Extra 出现 Using index。代价要一起说：索引变宽、写入维护变贵、还可能干扰优化器，所以它是给热点查询的，不是给全表的。

EXPLAIN 只看四个字段：type、key、rows（估算值，且不含回表成本）、Extra（Using index 说明覆盖、Using filesort 说明还要排序）。边界：PG 是堆表，索引叶子存 ctid，一律回表。

分层要点追问深挖时用

  • 结论：InnoDB 是索引组织表；回表 = 第二次 B+ 树查找，随命中行数线性增长且是随机 IO；覆盖索引让它消失（Extra 出现 Using index）。
  • 推导链：两种存法 → InnoDB 的取舍（按主键查只需一次下降）→ 二级索引叶子必须带主键 → 取整行要再查一次 → 覆盖把需要的列放进索引 → 代价是写放大与索引变宽。
  • 量化：成本 = 定位 + 扫描 + 回表 × 命中行数；扫 1000 行 = 1000 次随机 IO；覆盖之后第三段归零。
  • 边界与常见误解：树高 3 层解释不了快慢差异（对所有查询都一样）；rows 小也可能慢（不含回表）；覆盖索引越宽越好 ×；PG 是堆表，一律回表。

一句话结论：InnoDB 是索引组织表——主键索引的叶子就是整行数据，二级索引的叶子只是「索引列 + 主键」。所以"先用二级索引、再取非索引列"要付出两次 B+ 树查找的代价，这就是回表；它随命中行数线性增长，且是随机 IO。覆盖索引把需要的列全放进索引里，让第二次查找消失（Extra 出现 Using index）。

  • 索引组织表 vs 堆表
  • 主键即数据
  • 二级索引叶子 = 索引列 + 主键
  • 主键被复制 N+1 份
  • 回表 = 第二次查找、随行数增长、随机 IO
  • 覆盖索引 = 免掉第二次
  • 代价是写放大

主线：InnoDB 把"表"和"主键索引"合成了一份数据结构。 好处是按主键查只需一次下降；代价是主键出现在每一个二级索引里，于是"主键怎么选"变成了全表级的成本问题，而"取不在索引里的列"变成了一次额外查找。

1. 既然覆盖索引能免回表，为什么不全表都建宽索引？

索引是欠写入的债：越宽，每次 INSERT/UPDATE 维护成本越高、页里能装的项越少、树还可能多一层。而且索引多了会干扰优化器的选择。覆盖是给热点查询的，不是给全表的。

2. rows 很小就一定快吗？

不一定。它是估算值，且不含回表成本。扫 10 行的回表可能比扫 100 行的覆盖索引还慢。

3. SELECT * 为什么在 InnoDB 里代价更高？

它几乎必然需要回表（* 里的列不可能全在一条二级索引里），而且不可能被覆盖。

4. 为什么建议自增主键而不是 UUID？

两个层面：① 写入层面，随机主键导致页分裂（见 [[母题-M5-引擎与表设计基本盘]]）；② 存储层面，36B 主键被复制进每一个二级索引。第二点比第一点更常被忽略。

M4索引的代价与大表变更：为什么「加个索引」可能把库搞挂单卡 →

任务表 5000 万行，线上正在跑。现在要给 status 加一个索引，你直接执行 ALTER TABLE task ADD INDEX idx_status(status)。会发生什么？

实测 446 字 · 按 4 字/秒折算约 112 秒（秒数是估算，字数才是实测）

索引的代价三笔：写放大（一次 INSERT 要维护 N+1 棵 B+ 树）、空间（主键被复制进每一个二级索引，BIGINT 换成 UUID 让单索引从 18B/条涨到 46B/条、约 2.6 倍）、优化器负担。没被用上的索引是纯负债。

大表 DDL 的危险不在「扫 5000 万行慢」，而在 MDL：DDL 要拿 MDL 写锁，前面有个长事务持着读锁没放，DDL 就只能在队列里等；MDL 队列是 FIFO，后面进来的查询全堵在它后面。积压数约等于 QPS × 等待秒数——2000 QPS 等 30 秒就是约 6 万个请求堆着，连接池打满、服务雪崩。

所以 LOCK=NONE 只解决「DDL 不阻塞别人」，没解决「别人阻塞 DDL」；ALGORITHM=INPLACE 也不是万能。

处方四步：先查并干掉长事务（前置动作，不是方案）；设短 lock_wait_timeout，让等待快速失败而不是无限堆积；按表规模与可回滚性选 Online DDL 还是影子表（pt-osc 用触发器、gh-ost 吃 binlog）；低峰执行 + 备好回滚。低峰只降低积压速度，不消除长事务这个触发源。

分层要点追问深挖时用

  • 结论：索引的代价是「每一次写」；大表 DDL 的危险是「不可控的等待」（MDL 连锁），不是扫描慢。两者都不是由表大不大决定的，是由有没有人用、有没有人挡决定的。
  • 推导链：三笔代价 → DDL 要做的两件事（改元数据 + 改数据）→ 危险在拿 MDL 写锁那一步 → 长事务持读锁 → DDL 排队 → 队列 FIFO 让后续查询一起堵 → 积压 = QPS × 等待秒数 → 连接池打满。
  • 量化：BIGINT→UUID 单索引 18B→46B（约 2.6 倍）；2000 QPS 等 30 秒 ≈ 6 万个请求积压。
  • 边界与常见误解：LOCK=NONE 只管一半；INPLACE 不是所有 DDL 都行（改列类型、重建聚簇只能重建表）；DROP INDEX 同样要拿 MDL；低峰是降速不是除因；完整动作 = 查长事务 + 短 lock_wait_timeout + 按规模选方案 + 低峰 + 备回滚。

一句话结论：索引的代价是三笔——写放大（一次写维护 N+1 棵 B+ 树）、空间（主键被复制进每个二级索引，BIGINT→UUID 能让单个索引膨胀 2.6 倍）、优化器负担。大表 DDL 的危险不在"扫 5000 万行慢"，而在 MDL：长事务持读锁 → DDL 等写锁 → 后续查询因队列 FIFO 全排在 DDL 后面 → 积压数 = QPS × 等待秒数（2000 QPS 等 30 秒 = 6 万个请求）→ 连接池打满 → 整个服务雪崩。LOCK=NONE 只解决"DDL 不阻塞别人"，没解决"别人阻塞 DDL"。 所以真正的处方式是：先查并处理长事务 + 设短 lock_wait_timeout + 按表规模选在线 DDL 或影子表 + 低峰执行 + 备回滚。

  • 三笔代价（写放大/空间/优化器负担）
  • 一次写维护 N+1 棵 B+ 树
  • 主键被复制进每个二级索引，BIGINT→UUID 膨胀 2.6 倍
  • MDL 连锁（读锁持住 → DDL 等写锁 → FIFO 不能插队 → 后续查询全排队）
  • 积压 = QPS × 等待秒数
  • 连接池打满 → 雪崩
  • LOCK=NONE 只解决一半
  • INPLACE 不是万能
  • pt-osc 触发器 vs gh-ost binlog
  • 任何情况都先查长事务

主线：索引是读的快照，写的负债。 它的全部代价都记在写入路径上；而大表变更的全部危险都来自锁的排队语义——不是"慢"，是"堵"。两件事都不由表的大小决定，而由"有没有人用、有没有人挡"决定。

1. LOCK=NONE 都开了，为什么还是可能卡住线上？

关键在于MDL 等待的连锁：长事务持读锁 → DDL 等写锁 → 后续查询再排在 DDL 后面。LOCK=NONE 只保证 DDL 执行期间不阻塞，不保证它不被别人阻塞。

2. 索引是不是越多越好？

不是。写放大 + 空间（还挤占 buffer pool）+ 优化器负担；判据是"有没有高频查询真的用它"。没被用上的索引应该主动删掉。

3. MySQL 和 PG 在这件事上有什么不同？

PG 用 CREATE INDEX CONCURRENTLY，它不会长时间持锁等，但代价是失败会留下 invalid 索引需要手动清理，而且不能在一个事务块里执行。

4. 为什么 NOT NULL + DEFAULT 加字段有时很快、有时很慢？

取决于能不能走 instant 路径。MySQL 8.0 支持 instant add column（元数据操作）；更早版本或某些类型会触发重建表。判断方式是看 ALGORITHM 到底是 INSTANT / INPLACE / COPY，不要凭版本印象。

引擎三条硬差异：InnoDB 支持事务、行级锁、崩溃恢复，正好对应业务表的三个硬要求；MyISAM 是表级锁、不支持事务、崩溃可能丢数据，只在「读多写少 + 无事务 + 数据可重建」三者同时成立时才勉强可用。

主键用自增，代价可以算：随机主键是随机插入 → 页分裂 → 填充率从约 100% 掉到约一半、页数翻倍、缓存能装的页减半；更要紧的是主键会被复制进每一个二级索引，UUID 让单个索引从 18B/条涨到 46B/条。要全局唯一又趋势递增用雪花 ID，但得主动说它的代价：趋势递增不等于严格递增（时钟回拨仍可能乱序）、位数更长——它是折中，不是替代。

字段两条：长度不定用 varchar（char(10) 存 'a' 占 10 字节 vs varchar(10) 占 2 字节，差 5 倍）；远期时间用 DATETIME（TIMESTAMP 只有 4 字节，2^31−1 秒 ≈ 68 年，2038-01-19 溢出）。

边界：MySQL 的 DDL 会隐式提交、不能回滚，判据是「它有没有写 undo、会不会隐式提交」，不是「因为它是 DDL」——PG 的 DDL 是事务性的，DROP TABLE 可以 ROLLBACK。

一句话结论：选 InnoDB 是因为它的三条硬差异——支持事务、行级锁、崩溃恢复——正好对应业务表的三个硬要求；MyISAM 只适合"读多写少 + 无事务 + 数据可重建"。表设计的三条硬规则都有可算的依据：主键用自增（随机主键导致页分裂，填充率降到约一半、页数翻倍，还让缓存能装的页减半）、长度不定用 varchar（char(10) 存 'a' 占 10 字节 vs varchar(10) 占 2 字节，差 5 倍）、远期时间用 DATETIME（TIMESTAMP 只有 4 字节，2^31−1 秒 ÷ 31,557,600 ≈ 68 年，2038-01-19 溢出）。另外主键会被复制进每一个二级索引——BIGINT→UUID 让单个索引从 18B/条涨到 46B/条。

  • 索引组织表 vs 非聚集索引（叶子存主键 vs 存地址）
  • 自增=顺序写，随机=页分裂
  • 填充率 100%→50% → 页数翻倍 → 缓存减半
  • 主键被复制进每个二级索引，18B→46B

主线：表设计不是审美问题，是"写入路径顺不顺、存储紧不紧凑、以后改不改得动"的问题。 而这三件事里，主键选型的影响面最大——它是唯一一个"改一次就影响全表所有索引"的决策。

1. 页分裂到底损失什么？

① 分裂是同步写，抬高写入延迟；② 分裂后两页各约半满，同样的数据占更多页，范围扫描读更多页、缓存命中率下降；③ 顺序写变随机写，失去 B+ 树最大的性能来源。

2. 那用趋势递增的雪花 ID 不就好了？

可以，但注意两点：① 趋势递增不是严格递增，跨节点时钟回拨仍可能插到中间（概率远小于 UUID）；② 全局唯一 ID 通常位数更长（64 位），二级索引体积会变大。要接受这两个代价才叫权衡过。

3. char 和 varchar 谁快？

单看存取，定长略快（省长度字节、不用变长解析）；但只要长度不固定，char 浪费的空间远超这点收益。判断标准只有一句：长度是否真的固定。

4. 为什么 MySQL 有 DATETIME 还要 TIMESTAMP？

因为 TIMESTAMP 省一半空间、且带时区语义与自动更新，适合"创建/更新时间"这类只关心过去与现在的字段。代价是 2038 边界——所以它和时间范围是绑定的取舍，不能当通用时间类型。

5. InnoDB 相比 MyISAM 在索引实现上差在哪？

MyISAM 是非聚集索引：索引文件与数据文件分离，叶子存物理地址，查到后还要再去数据文件捞一次；InnoDB 是索引组织表：主键叶子存整行、二级索引叶子存主键值，所以要回表（[[母题-M3-聚簇索引与回表]]）。

这道题属于母题 M1 · 为什么 InnoDB 用 B+ 树，不用 B 树 / 红黑树 / 哈希 · 下面挂它的完整回答（学的时候看）

实测 381 字 · 按 4 字/秒折算约 95 秒（秒数是估算，字数才是实测）

判据只有一个：磁盘随机读比内存随机访问慢约 5 个数量级（机械盘约 10 毫秒对内存约 100 纳秒），而一次 IO 读的是一整页（InnoDB 默认 16KB）、成本几乎不随读多少变化，所以评价索引结构只看「定位一行要几次 IO」，也就是树高。

四个候选逐个淘汰：哈希表只能等值、做不了范围；红黑树是二叉、扇出 2，2000 万行树高约 24 层、约 24 次 IO；B 树非叶也存数据，扇出被挤小、范围查询还要回溯父节点；B+ 树非叶只存键，扇出约 1170，三层就能覆盖约 2000 万行，只要 3 次 IO。它三个设计点各解决一件事：非叶只存键让扇出最大、树最矮；叶子双向链表让范围查询一次下降后顺序扫；页与磁盘块对齐让每次 IO 都不浪费。

边界：树矮只保证定位索引项便宜，二级索引查到的是主键，取整行还要回表，扫 1000 行时回表才是大头；写多读少的场景走另一条路——LSM 树（RocksDB / LevelDB）。

分层要点追问深挖时用

  • 结论：B+ 树是为「磁盘 IO 次数最少」设计的；唯一判据是「定位一行要几次 IO」，不是比较次数。
  • 推导链：IO 比内存慢约 5 个数量级 → 一次 IO 读一页、成本与数据量无关 → 判据落在树高 → 哈希不能范围 / 红黑树扇出 2 / B 树扇出被数据挤小且范围要回溯 → B+ 树非叶只存键。
  • 量化：页 16KB、扇出约 1170 → 三层约 2000 万行 = 3 次 IO；红黑树同样数据约 24 层 ≈ 24 次 IO。
  • 边界与常见误解：树矮 ≠ 快（回表才是大头）；红黑树只是「不适合做磁盘索引」，内存场景（Redis 跳表、Java 红黑树）完全合理；写多读少走 LSM，代价是读要多查几层 + 需要 compaction。

10必背M3

这道题属于母题 M3 · 聚簇索引、回表、覆盖索引：explain 里怎么看出来 · 下面挂它的完整回答（学的时候看）

实测 392 字 · 按 4 字/秒折算约 98 秒（秒数是估算，字数才是实测）

先说两种存法：堆表里索引叶子存行地址；InnoDB 是索引组织表，主键索引的叶子就是整行数据，二级索引的叶子只是「索引列 + 主键值」。

所以取非索引列要两次 B+ 树查找——先在二级索引树上定位到主键，再回聚簇索引取整行，第二次就是回表。成本拆成定位、扫描、回表三段，只有第三段随命中行数线性增长，而且是随机 IO：扫 1000 行就是 1000 次随机 IO，这才是「加了索引还是慢」的主因。

覆盖索引把需要的列全放进索引，让第二次查找消失，判据是 EXPLAIN 的 Extra 出现 Using index。代价要一起说：索引变宽、写入维护变贵、还可能干扰优化器，所以它是给热点查询的，不是给全表的。

EXPLAIN 只看四个字段：type、key、rows（估算值，且不含回表成本）、Extra（Using index 说明覆盖、Using filesort 说明还要排序）。边界：PG 是堆表，索引叶子存 ctid，一律回表。

分层要点追问深挖时用

  • 结论：InnoDB 是索引组织表；回表 = 第二次 B+ 树查找，随命中行数线性增长且是随机 IO；覆盖索引让它消失（Extra 出现 Using index）。
  • 推导链：两种存法 → InnoDB 的取舍（按主键查只需一次下降）→ 二级索引叶子必须带主键 → 取整行要再查一次 → 覆盖把需要的列放进索引 → 代价是写放大与索引变宽。
  • 量化：成本 = 定位 + 扫描 + 回表 × 命中行数；扫 1000 行 = 1000 次随机 IO；覆盖之后第三段归零。
  • 边界与常见误解：树高 3 层解释不了快慢差异（对所有查询都一样）；rows 小也可能慢（不含回表）；覆盖索引越宽越好 ×；PG 是堆表，一律回表。

11必背M2

这道题属于母题 M2 · 联合索引与最左前缀为什么存在；索引失效有哪些场景 · 下面挂它的完整回答（学的时候看）

实测 423 字 · 按 4 字/秒折算约 106 秒（秒数是估算，字数才是实测）

索引的价值只有一个——少扫。有序性能做三件事：定位、截断、免排序，前提都一样：满足条件的记录在索引里是连续的一段。

联合索引 (a, b, c) 按字典序排，所以只有从最左列开始的连续前缀能切出「可定位区间」。单独查 b = 2 用不上，是因为 b 只在每个 a 段内有序、段之间无序；「用不上」的准确含义是退化成扫描量约等于全表，不是报错。WHERE 里条件的书写顺序不影响，优化器按列集合重排。范围列之后的列失去定位、保留 ICP 过滤——省的是回表，不省的是扫描。

字段顺序三条：等值在前、范围靠后、选择度高的在前，再看能否免排序。所以那条调度 SQL 没有完美解：(status, next_retry_time, priority) 扫描约 3.3 万行但要 filesort；(status, priority, next_retry_time) 免排序却缩不了范围——选哪个看两边的选择度。

边界：索引列不是越多越好；选择度太低的列（status 这种）优化器会主动放弃，先问区分度再问写法。

分层要点追问深挖时用

  • 结论：联合索引按字典序排，只有最左连续前缀能切出「可定位区间」；有序性只有定位 / 截断 / 免排序三种用法，前提都是「结果在索引里连续」。
  • 推导链：固定指标（扫过的行数，不是树高）→ 字典序逐层细分 → 局部有序 = 全局无序 → 单独 b 找不到连续区间 → 范围列之后失去定位、保留 ICP 过滤。
  • 量化：调度 SQL 用 (status, next_retry_time, priority) 扫描约 3.3 万行但要 filesort；换 (status, priority, next_retry_time) 免排序却缩不了范围——取舍看选择度。
  • 边界与常见误解：条件书写顺序不影响匹配（优化器重排）；索引列越多越好 ×；建了索引优化器不一定用（选择度低会主动放弃）；前缀索引不能替代联合索引（丢完整有序性）。

索引的代价三笔：写放大（一次 INSERT 要维护 N+1 棵 B+ 树）、空间（主键被复制进每一个二级索引，BIGINT 换成 UUID 让单索引从 18B/条涨到 46B/条、约 2.6 倍）、优化器负担。没被用上的索引是纯负债。

大表 DDL 的危险不在「扫 5000 万行慢」，而在 MDL：DDL 要拿 MDL 写锁，前面有个长事务持着读锁没放，DDL 就只能在队列里等；MDL 队列是 FIFO，后面进来的查询全堵在它后面。积压数约等于 QPS × 等待秒数——2000 QPS 等 30 秒就是约 6 万个请求堆着，连接池打满、服务雪崩。

所以 LOCK=NONE 只解决「DDL 不阻塞别人」，没解决「别人阻塞 DDL」；ALGORITHM=INPLACE 也不是万能。

处方四步：先查并干掉长事务（前置动作，不是方案）；设短 lock_wait_timeout，让等待快速失败而不是无限堆积；按表规模与可回滚性选 Online DDL 还是影子表（pt-osc 用触发器、gh-ost 吃 binlog）；低峰执行 + 备好回滚。低峰只降低积压速度，不消除长事务这个触发源。
