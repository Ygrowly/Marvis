锚点

projects/EnergyOps/03-query-and-performance.md、02-aggregation-and-recovery.md

  • 用在哪："受控并发 + 低优先级回补"是本模块在应用层的一次选型——不引入 MQ、不引入分析引擎，用调度 + 批量 + 幂等把负载压在单库能承受的范围里。
  • 解决什么问题：能耗数据是"写多、按时间窗聚合读"的形态——这本来偏向时序/分析类存储，但当前规模下"加一套引擎"的代价大于收益，所以选择"用现有库 + 受控并发"顶住。
  • 踩过的坑：Checkpoint 被当成"业务完成证明"——恢复线索不等于完成证明（对应 S1 的"数据同步有窗口"同一类问题：两边不一致时，以哪边为准）。
  • 决策与取舍："达到升级条件才引入"——这是本模块第 0 节那条判据（先算账，再换引擎）的现场版。

S1 分野

PostgreSQL 管控制面（租户、权限、目录、任务——典型 OLTP），Parquet + 对象存储存分析数据，DuckDB Worker 做隔离分析（列存 + 进程内）。02 写得很直白：*"PostgreSQL 只保存目录、Schema、同步状态和版本，DuckDB 负责分析执行"*。这就是"两种负载交给两种引擎"的标准做法。

S2 扩展

快照（SNAPSHOT）与实时（LIVE_READ）双模式——实时模式优先只读副本或分析库，且*"若客户只有生产主库，默认不开放复杂即席查询"*。这就是"不许分析负载打到生产主库"这条硬规矩。

S4 语义

03 的三层知识（技术元数据 / 业务语义 / 公共规则）与"模型只能映射和使用，不能自行创造"——这是 S4 的项目正本。

  • 解决什么问题：同一份数据，控制面要强一致（权限不能错），数据面要扫描快（分析不能慢）——一个引擎同时满足两者的代价，比分成两层更高。
  • 踩过的坑：扫描量、超时、行数、并发都必须有上界（07、08）——"单个请求没有上界"是这类事故的共同根因（同 [[母题-X1-容器是什么]] 的结论）。
  • 决策与取舍：不做全量复制（成本与合规），只同步"选定数据集"；02 的钢人比较写明：*"完全直连无需同步、数据最新，适合已经有成熟分析库的企业；全量复制查询自由，但成本和合规压力大。"*
  • 对应母题：【S1、S2、S4】
锚点

projects/RuleArena/06-architecture-and-scenarios.md、08-capacity-cost-and-facts.md、04-idempotency-and-recovery.md

  • 用在哪："权威状态放关系库，易失状态与队列放 Redis"的经典二分——PostgreSQL 存 AttackRun 与 Receipt，Redis/ARQ 负责队列、限流与短期进度。
  • 解决什么问题：崩溃后能重建——*"起来先读 AttackRun 和最后一个 Receipt，再校准 Checkpoint"*。这直接回答 S3 的第一问：Redis 能替代数据库吗？不能，因为它的权威性不在这里。
  • 踩过的坑：Redis 只配 256~512MB（08）——一个"进程随时可能被拿走"的存储，不能承载不可再生的状态（同 [[母题-X1-容器是什么]] 2.2）。
  • 决策与取舍：K8s、RabbitMQ、通用 DAG 都进了"主动删除"清单（06 §秒级删除清单）——明确不做的比做的更能说明取舍；这正是 S3 要练的"多引入一个引擎要付什么账"。
  • 对应母题：【S3】
