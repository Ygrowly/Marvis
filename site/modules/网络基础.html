锚点

projects/EnergyOps/

  • 用在哪：长任务的 SSE 进度推送（对话式操作里，一次采集/聚合要跑很久）；30 个 MCP Tool 的超时与重试；服务端与上游数据库之间的连接复用
  • 解决什么问题：用户点了操作之后必须知道进度，否则会重复点（这就是"要不要复用连接"从技术问题变成产品问题）
  • 踩过的坑：三个坑都踩过——① 网关把 SSE 缓冲住了（Nginx 默认攒着不发），前端看着像卡死，要显式关缓冲；② 不发心跳会被空闲超时掐断，长任务跑到一半连接就没了，要定期发注释行保活；③ 超时只设了一层，网关先放弃还是应用先放弃分不清，排查时不知道该看哪边
  • 决策与取舍：选 SSE 不选 WebSocket 是两个理由，不是一个——① 只需要单向推送（服务端 → 客户端），WebSocket 的全双工用不上；② 复用现有 HTTP 网关——SSE 跑在 HTTP 上，过网关、负载均衡、鉴权链路都不需要额外改造，WebSocket 要动这些（[[母题-N2-SSE与推送模型]]）。
  • 对应母题：【N1、N2】
锚点

projects/数驭穹图/

  • 用在哪：一次问数请求的完整链路（前端 → 网关 → 应用 → 权限/检索/SQL 执行 → 返回）；权限前置意味着一次请求里可能有多次串行上游调用
  • 解决什么问题：链路上任何一环慢，用户看到的就是"卡住"——先分清卡在哪一层，再谈优化（这正好是 N1 主线一的判据）
  • 踩过的坑：网关超时和应用超时设成了一样的值——结果是两边几乎同时放弃，日志里看不出谁先走的，排查时无法归因到哪一层慢。正确做法是外层比内层略长，让内层先超时、留下自己的错误，外层只是兜底。
  • 决策与取舍：权限校验收在检索和执行之前，代价是多一次上游调用，换来的是未授权内容根本不进后面任何一步——不进检索、不进 SQL、不进上下文。用一次串行调用换掉一整类泄露风险，这笔账划得来（[[母题-N1-一次请求的完整路径]] 的「先分清卡在哪一层」在权限侧的对应）。
  • 对应母题：【N1、N3】
锚点

projects/RuleArena/

  • 用在哪：长任务的进度与状态查询（Worker 跑一条规则审查是长任务）；至少一次投递 + 幂等副作用
  • 解决什么问题：客户端要的到底是"实时推送"还是"能查到最新状态"——如果是后者，就不该上 SSE，轮询更简单
  • 踩过的坑：断线重连后不知道漏了哪些事件——靠 Last-Event-ID 重连续订：事件带递增 sequence，客户端重连时带上最后收到的 id，服务端从那里补齐。没有这个机制，重连就会静默丢事件。
  • 决策与取舍：这里选轮询/状态查询而不是推送——因为客户端真正要的是「能查到最新状态」，不是「实时被通知」。轮询更简单：没有长连接要维护、没有重连逻辑、没有网关改造。「实时」只有在「延迟本身有业务意义」时才值得付这份复杂度（[[母题-N2-SSE与推送模型]]）。
  • 对应母题：【N2、N3】
