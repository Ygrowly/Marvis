锚点

projects/RuleArena/

  • 用在哪：Thread / Run / Step 的状态模型就是"权威"，上下文是从它装配出的"视图"；规则原文、审查摘要、权威状态、Agent 临时判断四者分开放
  • 解决什么问题：长审查任务跨过了单次窗口 —— 靠压缩 + checkpoint + 从权威状态重建最小上下文
  • 踩过的坑：压缩摘要里没记副作用，恢复后就会重做——摘要是「有损且不可逆」的，它留下的是当时的判断，不是事实。把「已执行过哪几次动作、各自的幂等键是什么」压掉了，恢复时系统就真的不知道做过没有，只能重试 → 重复副作用。
  • 决策与取舍：恢复时必须先查权威业务状态，不能用旧摘要续跑——因为摘要是「意图」，Receipt/Snapshot 才是「事实」，两者之间夹着那个不确定窗口。摘要省的是 token，不是真相；省 token 的代价不能是「用猜代替查」（本库 [[母题-A4-长任务状态与Checkpoint]] 的恢复协议六步、[[母题-P19-唯一约束与UPSERT]] 的 Receipt 是同一件事）。
  • 对应母题：【C1】【C4】
锚点

projects/数驭穹图/

  • 用在哪：上下文只装当前领域 Schema + 权限过滤后的候选表 + 关键样例；SQL 结果过大时写 Artifact 只回传统计与样本
  • 解决什么问题：Schema 太大塞不下，且权限决定谁能看哪些表 —— 上下文装配必须带权限过滤
  • 踩过的坑：砍掉的是「全库 Schema」和「大结果明细」，不是信息本身——Schema 从全量改成「按领域路由后的候选表 + 关键样例」，SQL 的多万行结果外置成 Artifact（Hot/Warm/Cold），上下文只留口径摘要 + 聚合统计 + artifact_id。东西没丢，只是从「常驻上下文」挪到了「按需取」。
  • 决策与取舍：版本要跟着结果走，因为「同一个问题不同版本可以给出不同答案」——口径改过、Prompt 改过、Schema 改过之后，旧结果就不能再拿来对照，否则你分不清「是数据变了还是规则变了」。不绑定版本的结果，在审计场景里等于没有出处（[[母题-C3-Prompt版本管理与回归]] 的 Prompt 版本管理在这里落地）。
  • 对应母题：【C1】【C3】
锚点

projects/EnergyOps/

  • 用在哪：30 个 MCP 工具的工具定义本身就是上下文开销；每个工具只收必要业务参数；日志和大表先聚合再进上下文
  • 解决什么问题：工具越多，上下文里光工具定义就吃掉一大块 —— 这是"最小工具集"和延迟加载的直接动因
  • 踩过的坑：30 个工具全量声明，光工具定义每轮就吃掉一大块——而且这笔钱每一轮都要付（历史重发，见 [[母题-C1-上下文组装与窗口预算]] 的平方累计）。高频的查询类留常驻，低频且重的（结算发布、批量导出、规则变更）标记延迟加载，用到时才引入。
  • 决策与取舍：描述不是越详细越好，是「够选对就行」——写太简会选错工具，写太细每轮都多付 token 且长描述反而稀释关键差异。判据是选择准确率 vs token 占用的实测权衡，不是凭感觉写长。
  • 对应母题：【C1】【C2】
