锚点

projects/EnergyOps/

  • 用在哪："受控并发 + 低优先级回补"是这个模块最直接的证据——服务重启后扫描最近七天缺口并低优先级回补（02-aggregation-and-recovery.md），这既是启动期的依赖就绪问题（X2：服务起来时任务表里可能有积压），也是排查问题（X3：怎么知道重启后有没有漏算）。
  • 解决什么问题：重启不等于状态清零——能恢复的只有落到数据库里的部分（这正是 [[母题-O1-上下文切换与死锁]] 的进程模型在运维层的对应）。
  • 踩过的坑：Checkpoint 被当成"业务完成证明"——它是恢复线索，所以重启后的自检（扫描缺口）必须存在，不能假设"没报错就是都跑过了"。
  • 决策与取舍：当前规模不上 MQ、不上复杂编排——EnergyOps-快速学习掌握与面试实战.md 里明确"达到升级条件才引入"。这与本模块第 0 节的"边界判断"同源：能不能不上，先算账。
  • 对应母题：【X2、X3】
锚点

projects/数驭穹图/

  • 用在哪："资源上限"在应用层的落地——超时、扫描量、行数、并发、内存配额、取消能力（07-权限安全与生产隔离.md、08-查询性能与成本控制.md）。这些正是容器/进程级限制在业务层的对应物：限制不是"不信任用户"，而是"防止一个请求把整个服务拖下水"。
  • 解决什么问题：只读副本 / 分析库 / 对象存储这一串依赖同时可用才能完成一次问数——这是 X2 的"启动依赖与降级路径"问题：某一环不可用时，应该 fail closed（权限不确定就不放行）还是降级。
  • 踩过的坑：权限不确定时必须 fail closed（07 明确）；超时、取消要能真正中断（依赖底层 IO 机制，见 [[母题-O3-IO模型与零拷贝]]）。
  • 决策与取舍：限额与配额优先于"加机器"——因为"加机器"不解决"单个请求无上界"（[[母题-O2-虚拟内存与缺页]] 的同一结论）。
  • 对应母题：【X3】
锚点

projects/RuleArena/

  • 用在哪："进程随时可能崩"被当成设计前提——PostgreSQL 存权威状态，Redis/ARQ 负责队列、限流与短期进度（06-architecture-and-scenarios.md、04-idempotency-and-recovery.md §9）。这就是 X1 与 X2 合起来要说的事：容器里的进程是"会被随时拿走"的，所以生命周期必须由外部状态来重建。
  • 解决什么问题：Worker 重启后的状态重建——起来先读 AttackRun 和最后一个 Receipt，再校准 Checkpoint。
  • 踩过的坑：容器内存与任务上限——08-capacity-cost-and-facts.md 给 Redis 只配 256~512MB，意味着这个容器被 cgroup 限制：超了是 cgroup OOM，和宿主机还剩多少内存无关（[[母题-O2-虚拟内存与缺页]] 4.3 的判据）。
  • 决策与取舍：K8s、RabbitMQ、通用 DAG 都进了"主动删除"清单（06 §秒级删除清单）——明确不做的比做的更能说明取舍。
  • 对应母题：【X1、X2】
