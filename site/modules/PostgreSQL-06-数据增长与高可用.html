PG 的分区表有哪几种？什么规模才值得分？

一张 5 亿行的表，查询永远带时间范围，而且每月要清掉两年前的数据。该不该分区？

一句话结论：PG 是声明式分区——PARTITION BY RANGE / LIST / HASH。它的主要收益有两个：① 分区裁剪（查询带分区键时只扫相关分区）；② 批量删除变成 DROP/DETACH 分区（比 DELETE 便宜得多，且不产生大批死元组）。代价：分区键必须进大部分查询条件、分区太多会有规划开销、跨分区唯一约束做不了（除非约束里带上分区键）、运维更复杂。所以判据不是「数据大」，而是「数据大 + 天然有分区键 + 有批量清理需求」。

  • 声明式分区
  • RANGE LIST HASH
  • 分区裁剪（partition pruning）
  • 分区即批量删除
  • 分区多=规划开销
  • 唯一约束要带分区键
  • 与归档、索引、统计信息配合

主线：分区不是「把大表变小表」，而是「把一张表的管理粒度变细」。 它的收益全部来自「能只碰一部分」——只扫一部分（裁剪）、只丢一部分（DROP 分区）。没有这两类操作的场景，分区只会增加复杂度。

原理分解

一、三种分区方式

方式按什么分典型场景
RANGE值区间时间（按月 / 按季）、ID 段
LIST枚举值集合租户 / 区域 / 类别
HASH哈希取模，均匀打散没有天然分区键、只想把单表压力摊开

PG 的分区是「声明式的」：建表时就声明分区键和分区子表，插入时由数据库路由（早年的继承 + 触发器手工方案已经是历史）。并且支持默认分区（捕获不匹配任何分区的行）——没有默认分区时，插入一个落在所有分区之外的值会直接报错，这是第一个常见坑。

二、收益一：分区裁剪（查询变快）

当查询条件明确落在某个/某些分区上时，规划器根本不去碰其他分区：

查询：WHERE stat_date >= '2026-01-01' AND stat_date < '2026-02-01'
  ↓ 分区裁剪
只扫描 2026-01 那一个分区 → 扫描量从 5 亿行降到约 2100 万行（5 亿 ÷ 24 个月）

关键前提：分区键必须出现在查询条件里。 如果查询经常不带分区键（比如只按 device_id 查），裁剪失效，等于在 24 张分区表上做 24 次扫描——比不分区分区还慢。这是评估分区是否值得的第一道门槛。

第二个要求：条件要与分区边界"可推断"。用 date_trunc / 表达式包住分区键，规划器可能无法裁剪（和索引谓词匹配是同一类问题，P3）。

三、收益二：丢弃即归档（这是更值钱的那个）

不分区的表，清理两年前数据只能 DELETE：

DELETE FROM facts WHERE stat_date < '2024-09-01';
  ↓
逐行标死 → 产生海量死元组 → 表与索引一起膨胀 → 要等 VACUUM 回收（P14/P15）
  ↓
而且回收后文件也不变小（P15）

分区表：

ALTER TABLE facts DETACH PARTITION facts_2024_08;   -- 摘掉（几乎瞬时）
DROP TABLE facts_2024_08;                            -- 或直接丢弃

代价对比是数量级的：不产生死元组、不触发膨胀、不占用 VACUUM 资源、可以随时取消（DETACH 后可再挂回来）。

所以「有持续清理需求的大表」应该在设计阶段就分区——这不是优化，是避免了后面必然出现的膨胀问题。这条把主线五和主线六合成了一条线。

四、代价与限制（不说这段就等于没评估）

限制说明
唯一约束 / 主键要带分区键跨分区的唯一性无法用普通唯一索引保证（每个分区是独立索引）。所以唯一键必须包含分区键，或者用别的机制兜底。这是最常被忽略、也最容易在业务上炸的一条。
分区数量影响规划时间分区越多，规划器要枚举的候选越多 → 规划耗时上升（不是执行慢，是"想"得久）。几百上千个分区会明显拖慢短查询。
跨分区查询没有并行优势不裁剪时，多个分区是各自扫描，聚合要合并（有并行改善，但不能指望它抵消设计问题）。
外键、约束、触发器的行为更复杂子表独立管理，迁移/变更脚本更啰嗦。
统计信息按分区维护分区多了 autovacuum/ANALYZE 的对象也变多（又回到 VACUUM 负担）。

五、回到题目做判断

条件是：① 数据大（5 亿行）② 查询永远带时间（有天然分区键，可裁剪）③ 每月要清两年前数据（有批量清理需求）。

三条全中 → 该分区，按 stat_date 做 RANGE 分区（按月或按季）。

反过来，什么情况不该分：

  • 查询不带分区键（裁剪失效）；
  • 数据量其实不大（几千万行、索引够用）——先加索引、先优化查询（P6/P7）；
  • 没有清理需求（那就只是增加复杂度）；
  • 需要跨分区的强唯一约束（成本和复杂度会显著上升）。

一句判据：「我能不能只碰一部分」——能，就分；不能，先别分。

1. 「分区表的主键怎么设计？」

因为唯一约束必须带分区键，如果业务主键是「业务 ID」而分区键是「时间」，就不能只对业务 ID 建主键。常见处理：主键改成「业务 ID + 时间」的复合，或者放弃数据库级唯一约束、改用「全局 ID 生成 + 幂等写入」来保证唯一（把唯一性交到上游或应用层）。这是一个"分区代价"落到具体 DDL 上的例子——能讲出来说明真设计过。

2. 「分区真的能让 5 亿行的查询变快吗？」

只在裁剪生效时。裁剪后扫描量下降到单分区，本质收益和「加索引」是一样的（少扫数据），区别在于：索引解决"行级过滤"，分区解决"整块数据根本不用碰"。当条件本身能排除大量整块数据（时间范围）时，分区比索引更彻底——因为它连索引都不用读。但如果查询本来就命中很少的行，单表加索引可能更划算（改动更小、不用承担分区代价）。

P17为什么 PG 的连接很贵？连接池模式怎么选草稿 · 待验收单卡 →

为什么 PG 的连接很贵？连接池模式怎么选？

同样是 8 核机器，MySQL 能开几千个连接，PG 开几百就开始卡。为什么？

一句话结论：PG 是「一个连接一个后端进程」（fork 出独立进程），每个连接有独立内存、进程调度与上下文切换开销大，所以并发连接数上去后性能断崖；MySQL 是线程模型，连接便宜得多。因此 PG 的连接池是刚需，并且有两种模式：session 模式（一个客户端长期占一个连接，简单，但连接数仍随客户端数增长）与 transaction 模式（事务结束就归还，连接数 ≈ 同时活跃事务数，效率高，但会话级状态不可用）。

  • 进程模型 vs 线程模型
  • 连接成本（内存 + 调度）
  • pgbouncer
  • session vs transaction 模式
  • **会话级状态不可用**（prepared statement
  • session 变量
  • 临时表
  • advisory lock）
  • 连接数上限由「同时活跃事务数」决定

主线：连接数的上限不是「数据库能不能开」，而是「开了之后每个请求还快不快」。 所以要管的是「同时活跃的事务数」，不是「连接数」——这也是为什么 PG 的池化推荐 transaction 模式：它让连接数与客户端数解耦。

原理分解

一、为什么 PG 的连接贵

开销量具体表现
内存每个后端进程有独立的私有内存 + 共享缓冲区映射；连接数 × 单连接开销 = 常驻内存
进程调度每个连接是一个 OS 进程，上下文切换、调度、信号开销都远高于线程；连接一多，CPU 时间大量花在"管理连接"而不是"执行查询"上
缓冲区争用更多并发会话 → 更多并发访问共享缓冲区 → 锁与争用上升（吞吐反而下降，不是平滑增长）

对比 MySQL：线程模型，单连接开销小得多，所以「几千连接」是常规配置。PG 的实践数字通常是"几十到几百个活跃连接"——超过这个量级，继续加连接会让单位吞吐下降（这也是为什么有连接池这件事在 PG 侧几乎不可省）。

二、所以连接池是刚需（不是优化项）

没有池化时的经典事故：

应用每个请求开一个连接 → 并发请求数 = 连接数
  ↓
峰值流量 → 连接数暴涨 → 数据库 CPU 都在 fork/调度
  ↓
每个请求更慢 → 请求堆积 → 开更多连接 → 雪崩

池化的本质作用：把「客户端数量」和「数据库连接数」解耦，并在数据库前面提供一个可控的排队点。

关键认知：连接池不只是"复用连接省开销"，它更重要的功能是"限制并发、保护数据库"——池子满了就让请求排队（或快速失败），而不是让数据库被压垮。 这一点在面试里值得强调，因为它把连接池从"性能优化"提升到"稳定性设计"。

三、两种模式：session vs transaction

session 模式transaction 模式
连接何时归还客户端断开时事务结束时
连接数随客户端数增长≈ 同时活跃的事务数（大幅降低）
会话级状态可用不可用 / 不可靠
适用简单、连接数可控、或有会话状态依赖高并发 Web / API 的标准选择

transaction 模式效率高得多——因为它利用了「大多数请求的时间花在应用逻辑与网络，而不是在数据库事务里」这一点：同一个数据库连接可以在不同请求间轮流服务，因为它只在事务期间被占用。

四、transaction 模式的约束（必须讲清，否则会踩坑）

在 transaction 模式下，「会话」被切碎了，所以这些依赖会话状态的东西都不能依赖：

依赖项问题
预编译语句（prepared statement）语句缓存在会话里，而会话可能换了物理连接 → 报「语句不存在」或隐式重新规划。实践上常把驱动/代理的语句缓存关掉或设为 0。
会话变量（SET ...）下一次请求可能落到另一个连接，设置丢失。必须改成事务级设置或每次显式设置。
会话级临时表同上，会不可见。
advisory lock（会话级）会话一换就失去语义 → 锁可能被错误地"留在"另一个请求身上或提前释放。
游标（跨提交保持的）多数场景要求事务内使用。

判断方法一句话：「这个状态是不是"跟着连接走"的？」跟着走 → transaction 模式不能用；跟着事务走 → 可以用。

所以决定池化模式的时间点应该很早：在写第一行代码之前就定——因为「能不能用 transaction 模式」会影响数据访问层的写法（比如还敢不敢用会话级临时表、敢不敢依赖驱动的语句缓存）。

五、容量规划的正确口径

要算的是「同时活跃事务数」，不是「连接数」：

需要的连接数 ≈ 峰值 QPS × 单个事务平均持有连接的时间

推论有三条，都很实用：

1. 缩短事务 = 提高容量——同样的连接数能支撑更高 QPS。这条把 P14（长事务）和容量规划连起来了：长事务既按住了回收边界，又占着连接不放。 2. 应用侧也要限并发：池子 + 应用超时 + 队列上限，否则池子只是把雪崩推迟几秒。 3. 读写分离能摊开读压力，但写压力只落在主库——所以"加只读副本"解决不了写路径的连接瓶颈。

1. 「为什么不能简单把 max_connections 调很大？」

因为连接本身要占内存（每连接私有内存 + 共享缓冲区映射）、调度开销随进程数上升、并发访存争用加剧；结果往往是"连接数增加了，总吞吐反而下降，尾延迟显著变差"。所以正确方向是"减少连接占用时间"（短事务 + 池化），不是"扩大连接池上限"。

2. 「这跟你项目里的 Worker 有什么关系？」

关系很直接：Worker/队列消费者天然是"长驻连接"（它们持续取任务），所以必须给它们单独的池与上限，否则后台任务会把前台请求的连接挤掉。RuleArena 的「条件更新认领任务」在这里又赢一次（P18）：认领是一个短事务（一条 UPDATE），不是"开事务再慢慢处理"——它占用连接的时间极短，既省连接也更少锁等待。 这条把连接模型、池化模式、并发控制三件事收成了一个设计结论：短事务 + 池化 + 无锁并发控制是同一套选择。
