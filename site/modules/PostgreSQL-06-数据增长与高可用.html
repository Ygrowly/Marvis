PG 的分区表有哪几种？什么规模才值得分？

一张 5 亿行的表，查询永远带时间范围，而且每月要清掉两年前的数据。该不该分区？

一句话结论：PG 是声明式分区——PARTITION BY RANGE / LIST / HASH。它的主要收益有两个：① 分区裁剪（查询带分区键时只扫相关分区）；② 批量删除变成 DROP/DETACH 分区（比 DELETE 便宜得多，而且官方明确说它完全避免了 DELETE 带来的 VACUUM 开销）。代价：分区键必须进大部分查询条件、分区太多会有规划开销、跨分区唯一约束做不了（除非约束里带上分区键）、运维更复杂。所以判据不是「数据大」，而是「数据大 + 天然有分区键 + 有批量清理需求」。

  • 声明式分区
  • RANGE LIST HASH
  • 分区裁剪（规划时 + 执行时）
  • **裁剪只由分区键驱动，与索引无关**
  • 分区即批量删除（**绕开 VACUUM**）
  • **唯一约束必须包含分区键**
  • **分区上建索引不能直接 CONCURRENTLY**
  • 分区多 = 规划时间 + 内存

主线：分区不是「把大表变小表」，而是「把一张表的管理粒度变细」。 它的收益全部来自「能只碰一部分」——只扫一部分（裁剪）、只丢一部分（DROP 分区）。没有这两类操作的场景，分区只会增加复杂度。

1. 分区数量和性能是什么关系？

不是线性变好，是先好后坏：裁剪的收益随分区数上升，但规划时间与内存也上升。官方明确警告内存可能随时间显著增长，尤其是很多会话都碰到大量分区时。 所以按「月/季」分、总数几十到几百，是把两条曲线折中的经验值。

2. DETACH 会不会阻塞写入？

默认的 DETACH 会拿较强的锁；热表上要用 ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY——它需要额外一次表扫描，但锁更轻。 这条如果不知道，会在生产上直接把写入卡住。

3. 分区表上怎么做在线建索引？

不能用一条 CONCURRENTLY。要先用 CREATE INDEX ON ONLY 在父表建一个【无效】索引（阻止它自动应用到已有分区），再在每个分区上分别 CONCURRENTLY 建，最后逐个 ALTER INDEX ... ATTACH PARTITION；全部挂上后父索引会自动变为有效。 注意这里的"无效"是【故意】的、是流程的一部分——和 P4 里那个"失败留下的无效索引"是同一个状态、完全不同的含义。

4. 默认分区为什么必须建？

没有默认分区时，插入一个落在所有分区之外的值会直接报错。这在生产上意味着"某天凌晨的写入突然全部失败"——所以设计时要么建默认分区兜底，要么保证有自动建分区的任务。 两者选一个，不能不选。

5. enable_partition_pruning 是干什么的？

它是裁剪的开关。排查"到底裁了没有"的时候，可以关掉它做对比；而执行时才被裁掉的分区不会出现在 EXPLAIN 里，要看 EXPLAIN ANALYZE 的 loops（官方原话）。

P17为什么 PG 的连接很贵？连接池模式怎么选草稿 · 待验收单卡 →

PG 的连接为什么贵？连接池怎么配、有什么坑？

为什么 MySQL 里「连接池开个几百」很正常，PG 上却要配个连接池中间件？

一句话结论：PG 是「一个连接一个进程」——官方原话是为每个连接 fork 一个新进程，所以每个连接都有一份真实的进程内存，连接数是重资源。再加上 work_mem 是【每个操作】的上限而不是每个连接，一个连接可能同时占用好几份 work_mem，内存放大比直觉大得多。所以生产上的标准做法是在应用和数据库之间放一个连接池（pgbouncer 之类），把「几百个客户端连接」映射成「几十个服务端连接」。但连接池有两个必须知道的坑：事务级池化会让预处理语句与会话状态的作用域错乱；而池化本身不解决 idle in transaction——它只让这类连接更少。

  • 一个连接一个进程（fork）
  • 连接是重资源
  • `max_connections` 默认 100（启动时固定）
  • **`work_mem` 是每个操作不是每个连接**
  • 会话级 vs 事务级 vs 语句级池化
  • **事务池化 × 预处理语句**
  • `idle in transaction` 不因池化而消失

主线：连接在 PG 里是「进程」级的资源，不是「句柄」。

1. 连接池该用哪种模式？

先问应用需不需要会话状态：用不到 PREPARE / 临时表 / 会话级 SET / 游标 / LISTEN 的应用，事务级池化是免费的午餐；用得到的，要么改成会话级，要么用支持预处理语句跟踪的配置。 这个判断不能拍脑袋，要看驱动的默认行为。

2. 池开多大？

三个输入：数据库的核数、每个查询的耗时与 IO 比例、以及【有多少个应用实例共用这个库】。 而方向是「小池 + 应用侧排队」——让请求在应用侧排队（可控、可观测），而不是在数据库侧排队（而 PG 的锁等待是无限的，[[母题-P10-无间隙锁与锁变体]]）。

3. 为什么说 PG 的 max_connections 不能随便调大？

官方说得很清楚：PG 会根据 max_connections 直接推算若干资源，提高它会导致这些资源（包括共享内存）的分配增加。 而且它对连接建立的开销没有任何改善——只是把"墙"挪远了一点。 正解是加池，不是加 max_connections。

4. 连接池能不能解决表膨胀？

不能。它减少连接数，但不改变「事务开多长」。 idle in transaction 仍然是 idle in transaction——它照样按住回收边界（[[母题-P14-长事务与表膨胀]]）。要治它，只能靠 idle_in_transaction_session_timeout 和代码改造。

5. 备库上的 max_connections 要注意什么？

官方明确说：运行备库时，这个参数必须设成【等于或大于】主库的值，否则备库上不允许查询（[[母题-P12-流复制与逻辑复制]]）。这是一条很容易漏、而且一漏就整个只读副本不可用的配置。
