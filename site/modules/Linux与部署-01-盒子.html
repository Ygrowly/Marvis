主线：容器的一切现象都可以从"共享内核 + 视图收窄 + 额度设上界"这三条推出。 最常出错的地方是拿错参照系——用宿主机的数字判断容器的余量（free、CPU 利用率），而真实答案永远在这个容器自己的 cgroup 文件里。换参照系，是容器排查的第一动作。

1. 容器和虚拟机的本质区别是什么？

内核是不是共享的。VM 有独立来宾内核（硬件虚拟化隔离，强但重）；容器共享宿主机内核（namespace + cgroup，轻但隔离弱）。

2. 为什么容器里的 OOM 和宿主机的 OOM 是两回事？

日志前缀就能分辨：Memory cgroup out of memory: 是 cgroup OOM（撞 memory.max，宿主机可能很空）；Out of memory: 才是整机 OOM。因为内存没有 namespace，容器的上限只写在 cgroup 里。

3. CPU 利用率不高但延迟抖动，可能是什么？

三类：① 被 CPU 限流（看 nr_throttled / throttled_usec）；② 在等 IO（看 wa 与 IO PSI）；③ 在等锁 / 连接池 / 下游。先分类，再看数——这正是 X3 的排查顺序。

4. 容器里怎么知道"我还有多少内存额度"？

不要看 free（那是宿主机）。看 memory.current / memory.max（比值），以及 memory.events（有没有触发 max / high），再加 /proc/pressure/memory 看压力。

5. pids.max 有什么用？

限制这个 cgroup 里的任务数。它比"内存不够"更早撞上（[[母题-O1-上下文切换与死锁]] 3.3 的 pid_max 是同一族限制），报错是"创建任务失败"而不是 OOM——搞错这一对，排查方向就全歪了。

这道题属于母题 X1 · 容器是什么：namespace 和 cgroup 各管什么；为什么"容器里看到的内存"不是宿主机的内存 · 下面挂它的完整回答（学的时候看）

实测 534 字 · 按 4 字/秒折算约 134 秒（秒数是估算，字数才是实测）

容器不是轻量级虚拟机，它共享宿主机的同一个内核——namespace 管"能看到什么"（PID / NET / MNT / UTS / IPC / USER 等，把视野收窄），cgroup 管"能用多少"（memory / cpu / pids / io，给资源设上界），两者合起来才让一个普通进程"看起来像小机器"。启动快是因为不用起内核，隔离弱于虚拟机也是因为共享内核。

关键推论：内存没有 namespace——所以容器里 free 看到的是宿主机的内存，真实额度只在 cgroup 的文件里（memory.max / memory.current / memory.events）。超 memory.max 是 cgroup OOM（日志前缀 Memory cgroup out of memory），与宿主机剩多少无关；Out of memory: 才是整机 OOM。

CPU 是"每周期的时间预算"（cpu.max），用完就被暂停到下一周期——表现是延迟抖动/P99 抬高，但 CPU 利用率看起来不高，要看 cpu.stat 的 nr_throttled / throttled_usec。

cgroup v1 按资源分多套层级（同一进程可属不同层级，协同困难）；v2 是单一统一层级，且内存语义更细（memory.events / memory.low）并支持 PSI。

分层要点追问深挖时用

  • 结论：内核共享；namespace 管可见、cgroup 管额度；内存没有 namespace 是两类 OOM 的根因。
  • 推导链：共享内核 → 两种隔离机制 → 内存例外 → 容器额度只在 cgroup 文件 → CPU 是时间预算 → v1/v2 差异。
  • 量化：cgroup OOM 与整机 OOM 的日志前缀不同（Memory cgroup out of memory vs Out of memory）。
  • 边界与常见误解：容器里 free 不是自己的额度；CPU 利用率不高也可能是被限流；PSI 比 load 更能说清"卡在哪"。
