三个模型的区别：短轮询是"客户端定时发、服务端立刻回"（大量空跑）；长轮询是"服务端按住请求直到有数据或超时"（减少空跑，但每次要重建请求）；WebSocket 是"双向 + 协议升级"。

选型判据是两个问题：客户端要不要主动发？要的是事件流还是只要最新状态？ 只需要服务端推（进度、通知、LLM 逐字输出）就用 SSE，工程成本低得多；要双向（协作、游戏、实时输入）才上 WebSocket。LLM 的逐字流式输出本质上就是 SSE（或分块传输）。

生产三个坑：① 代理缓冲——Nginx 等中间层会缓冲响应，把流式变成一次性返回，要关掉缓冲并按块 flush；② 心跳——长时间无事件会被判为空闲而断开，要定期发注释行保活；③ 断线重连——浏览器会自动重连并带 Last-Event-ID，但要真正不漏事件，服务端必须按这个 ID 续推，或让客户端重连后拉一次全量状态校准。还要注意网关的空闲超时。

  • 推导链：服务端推的三种模型 → SSE 复用 HTTP 省掉 Upgrade → 代价是代理缓冲/心跳/重连三个坑。

主线："连接开多久""记不记得你""谁能主动发"是三个互不决定的维度。 把这三个分开，SSE 那道题就不会答错；把这三个分开，选型也就变成了两个二选一的问题。

1. SSE 和 WebSocket 到底怎么选？

先问"客户端要不要主动发"。只需要服务端推（进度、通知、LLM 逐字输出）就用 SSE，工程成本低得多；要双向（协作、游戏、实时输入）才上 WebSocket。

2. SSE 断线了会怎样？

浏览器自动重连，并带上 Last-Event-ID。但要真正"不漏事件"，服务端必须按这个 ID 续推，或者让客户端重连后拉一次全量状态校准。

3. 为什么 SSE 适合 LLM 逐字输出？

它就是"持续的单向事件流"，且能复用现有 HTTP 网关与鉴权。这正是 EnergyOps 里推长任务进度、以及大部分大模型产品流式输出的做法。

4. 长轮询还有什么场景在用它？

【取舍】需要"服务端推"但中间件完全不支持长连接时的兜底；或者兼容性要求极高的旧环境。现代系统里它更多是被 SSE 替代。

SSE 是基于 HTTP 的长连接：客户端发一次请求，服务端保持响应不结束，以 text/event-stream 持续单向推送，自带断线重连（Last-Event-ID）与事件 ID，跑在普通 HTTP 上所以过网关不用额外改造——这是它相对 WebSocket 最大的工程优势。

三个模型的区别：短轮询是"客户端定时发、服务端立刻回"（大量空跑）；长轮询是"服务端按住请求直到有数据或超时"（减少空跑，但每次要重建请求）；WebSocket 是"双向 + 协议升级"。

选型判据是两个问题：客户端要不要主动发？要的是事件流还是只要最新状态？ 只需要服务端推（进度、通知、LLM 逐字输出）就用 SSE，工程成本低得多；要双向（协作、游戏、实时输入）才上 WebSocket。LLM 的逐字流式输出本质上就是 SSE（或分块传输）。

生产三个坑：① 代理缓冲——Nginx 等中间层会缓冲响应，把流式变成一次性返回，要关掉缓冲并按块 flush；② 心跳——长时间无事件会被判为空闲而断开，要定期发注释行保活；③ 断线重连——浏览器会自动重连并带 Last-Event-ID，但要真正不漏事件，服务端必须按这个 ID 续推，或让客户端重连后拉一次全量状态校准。还要注意网关的空闲超时。

分层要点追问深挖时用

  • 结论：SSE 是单向、复用 HTTP 的长连接；选型问"要不要双向"和"要事件流还是最新状态"。
  • 推导链：服务端推的三种模型 → SSE 复用 HTTP 省掉 Upgrade → 代价是代理缓冲/心跳/重连三个坑。
  • 量化：子事件用 Last-Event-ID 续推；长轮询/短轮询的差别在"服务端是否按住请求"。
  • 边界与常见误解："SSE 不是长连接"×；只靠浏览器自动重连不够，服务端必须能按 ID 续推；中间件完全不支持长连接时才退回长轮询。
