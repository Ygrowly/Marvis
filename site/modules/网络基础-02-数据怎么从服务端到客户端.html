SSE 是长连接吗？三种推送方式该怎么选？

通过 SSE 推送长任务的进度，SSE 是什么？是长连接吗？ 和 WebSocket、长轮询的本质区别是什么？

一句话结论：SSE 是基于 HTTP 的长连接——客户端发一次请求，服务端保持响应不结束，以 text/event-stream 持续单向推送，自带断线重连（Last-Event-ID）与事件 ID，跑在普通 HTTP 上所以过网关不用额外改造。它和长轮询的区别是"服务端按住请求 vs 客户端反复发"；和 WebSocket 的区别是"单向且复用 HTTP vs 双向但要协议升级"。选型判据是两个问题：要不要双向？要事件流还是只要最新状态？

  • 长连接
  • 无状态
  • 双向 是三个正交维度
  • SSE 是长连接不是短连接
  • `text
  • event-stream`
  • 单向
  • Last-Event-ID 提供续推
  • 跑在 HTTP 上是最大工程优势
  • 代理要关缓冲
  • 要发心跳
  • HTTP1.1 下独占一条连接（同域 6 条）
  • 重连 ≠ 不漏事件
  • 选型看"客户端要什么"不是"哪个先进"

主线："连接开多久""记不记得你""谁能主动发"是三个互不决定的维度。 把这三个分开，SSE 那道题就不会答错；把这三个分开，选型也就变成了两个二选一的问题。

1. SSE 和 WebSocket 到底怎么选？

先问"客户端要不要主动发"。只需要服务端推（进度、通知、LLM 逐字输出）就用 SSE，工程成本低得多；要双向（协作、游戏、实时输入）才上 WebSocket。

2. SSE 断线了会怎样？

浏览器自动重连，并带上 Last-Event-ID。但要真正"不漏事件"，服务端必须按这个 ID 续推，或者让客户端重连后拉一次全量状态校准。

3. 为什么 SSE 适合 LLM 逐字输出？

它就是"持续的单向事件流"，且能复用现有 HTTP 网关与鉴权。这正是 EnergyOps 里推长任务进度、以及大部分大模型产品流式输出的做法。

4. 长轮询还有什么场景在用它？

【取舍】需要"服务端推"但中间件完全不支持长连接时的兜底；或者兼容性要求极高的旧环境。现代系统里它更多是被 SSE 替代。
