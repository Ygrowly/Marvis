这道题属于母题 G1 · 文档该怎么切？切多大、按什么切、上下文不够怎么办 · 下面挂它的完整回答（学的时候看）

实测 417 字 · 按 4 字/秒折算约 104 秒（秒数是估算，字数才是实测）

切块粒度是一个两头都会坏的问题：太小语义不自足（条款的例外被切走，单块意思可能是反的）；太大相关内容占比下降、相似度被稀释，关键内容排不进 Top-K（2000 字里只有 200 字相关时占比只剩 10%）。所以答案不是某个数字，而是把两个矛盾的需求拆开。

两条思路：Child-Parent（小块召回保召回率 + 父块返回保上下文完整）改的是"返回什么"；Contextual Retrieval（先给每块补 50–100 token 的定位说明再做索引）改的是"索引什么"，索引只涨约 12.5%，实测把检索失败率从 5.7% 降到 2.9%（−49%），再叠加重排是 1.88%（−67%）。两者可以叠加。

切分策略必须按数据结构选：制度文档按标题层级（几百字量级）、FAQ 按问答、代码按函数边界、条款按"条件 + 例外 + 生效时间"；表格必须表头与行绑定，不能拆掉口径（拆开表头的行是无意义的数字，指标表/口径表尤其明显）。参数要用目标问题集评测来定，不能照搬经验值。

分层要点追问深挖时用

  • 结论：粒度两头都会坏；小块召回 + 父块返回（Child-Parent）或补定位说明再索引（Contextual Retrieval）。
  • 推导链：太小→语义不自足；太大→相似度稀释、排不进 Top-K → 拆成"召回准"与"信息全" → 改返回 vs 改索引。
  • 量化：2000 字里 200 字相关 → 占比只剩 10%；Contextual Retrieval 索引涨约 12.5%，失败率 5.7% → 2.9%（−49%），叠重排 → 1.88%（−67%）。
  • 边界与常见误解：固定字数切块切的是字符数不是语义边界；表格拆掉表头是常见的坏切法；"多长的块最合适"没有通用答案，只能评测定。

这道题属于母题 G6 · 文档改了、删了、撤权了，索引怎么跟上；怎么保证不返回已失效的内容 · 下面挂它的完整回答（学的时候看）

实测 221 字 · 按 4 字/秒折算约 55 秒（秒数是估算，字数才是实测）

索引是派生数据，源变了它就必须变。三种变化各自要处理：新增 / 修改走增量链路（只重跑变化的 1%，100 万块每天改 1% 时能省 99% 的嵌入调用）；删除最难，因为要按 doc_id 反查它切出来的全部块（一份文档 100 个块就要清 100 个），漏一个就是"已删内容还能被搜到"的合规事故；撤权要清的地方更多——主索引、向量、倒排，以及缓存，因为缓存会绕过 ACL 过滤（有权用户查过的结果会命中给无权用户），所以缓存按租户/权限分区不是优化，是权限模型的一部分。

分层要点追问深挖时用

  • 结论：增量 + 删除/撤权传播 + 索引滞后可观测；缓存分区是权限的一部分。
  • 推导链：索引是派生 → 源变必须变 → 三类变化各自的难点 → 删除最难（反查全部块）→ 撤权还要清缓存 → 换模型必须双写切换。
  • 量化：100 万块每天改 1% → 增量省 99% 嵌入调用；一份文档 100 个块 → 删一次要清 100 个。
  • 边界与常见误解：索引滞后"大概几分钟"不行，必须是指标，超承诺时限就是故障；冲突文档不要偷偷选一个，要显式说明版本。

项目映射 把这个模块挂到真实经历上

锚点

projects/数驭穹图/

  • 用在哪：把 Schema / 指标口径 / 样例查询视作不同知识类型，关键词 + 向量混合召回表、字段和业务术语；权限过滤先于 Schema Linking
  • 解决什么问题：Top-K Schema 召回率 81% → 95% 的提升是靠什么拿到的？——这条是本模块最值得在面试里讲的证据
  • 踩过的坑：砍掉的检索结果是「外置」不是「丢弃」——大结果写 Artifact（Hot/Warm/Cold 三级生命周期），上下文里只留口径摘要、聚合统计和 artifact_id。需要下钻时按 id 取回。说成「为了省 token 把数据扔了」就错了：扔的是常驻，不是数据。
  • 决策与取舍：权限必须在检索前生效，因为「进上下文」就等于「已经泄露」——模型说不说只是概率问题，不是控制手段；而且未授权内容还会挤占预算、可能进日志和缓存。「让模型别说」是概率保证，「检索前过滤」才是权限控制（[[母题-G2-向量与关键词的混合检索]] 5.1 的三条理由）。
补充（G3 / G5 的真实落点，一手证据在项目 md 里）

候选 Schema 走「精确匹配 + 知识卡 + 关键词 + 向量」混合召回，再按权限、粒度、场景适用性、更新时间、JOIN 关系重排，只把少量相关 Schema 交给生成（05-领域路由与Schema-Linking.md）；失败的归因按「召回缺失 ≠ 重排错误」分两段看，各自对应不同的修复动作（数驭穹图-可视化复习图谱.md）。Top-K Schema 召回 81% → 95% 是用 150 条问题集量出来的（数驭穹图项目说明.md，必须带「Schema」两个字）。

锚点

projects/RuleArena/

  • 用在哪：条款按"条件 / 例外 / 生效时间"结构化切分；召回规则后用确定性状态模型验证
  • 解决什么问题：冲突规则显式返回证据，不强行合成唯一答案——这是"拒答"的正例
  • 踩过的坑：按字数切条款会把「条件」和「例外」切散——一条规则的含义被拆到两个 chunk 里，召回任一半都不完整，模型只能猜。语义被切碎比没召回更危险：它给了你一个看起来有出处的错答案。
  • 决策与取舍：条款的语义边界是逻辑结构，不是长度——按「条件 / 例外 / 生效时间」结构化切分，每个 chunk 才语义自足。字数切分只适合叙述型文本，对「条件-例外」型规则是破坏性的（[[母题-G1-切分策略与索引粒度]] 的「切分要按语义边界」）。

锚点

projects/EnergyOps/

  • 用在哪：运维文档、设备数据和实时状态不混成一个索引；实时事实走 Tool / 数据库，静态说明走 RAG
  • 解决什么问题：故障建议要引用日志 / 指标 Artifact 和操作手册——"证据"有两种形态
  • 踩过的坑：把运维文档和设备实时状态混进同一个索引——检索出来的「当前负荷」其实是上次同步时的，而模型会把它当作当下事实引用。过期的实时数据比没有更危险，因为它带着「这是事实」的外观。
  • 决策与取舍：证据有两种形态，不能混——日志/指标是运行时产生的、会变，走 Artifact 引用（绑定运行 id）；操作手册是静态的，走 RAG。混在一个索引里会让「引用」失去意义：你分不清引的是哪一次运行的日志（[[母题-G4-引用绑定与证据可追溯]] 的可追溯性）。
