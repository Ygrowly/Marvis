锚点

projects/数驭穹图/

  • 用在哪：把 Schema / 指标口径 / 样例查询视作不同知识类型，关键词 + 向量混合召回表、字段和业务术语；权限过滤先于 Schema Linking
  • 解决什么问题：Top-K Schema 召回率 81% → 95% 的提升是靠什么拿到的？——这条是本模块最值得在面试里讲的证据
  • 踩过的坑：砍掉的检索结果是「外置」不是「丢弃」——大结果写 Artifact（Hot/Warm/Cold 三级生命周期），上下文里只留口径摘要、聚合统计和 artifact_id。需要下钻时按 id 取回。说成「为了省 token 把数据扔了」就错了：扔的是常驻，不是数据。
  • 决策与取舍：权限必须在检索前生效，因为「进上下文」就等于「已经泄露」——模型说不说只是概率问题，不是控制手段；而且未授权内容还会挤占预算、可能进日志和缓存。「让模型别说」是概率保证，「检索前过滤」才是权限控制（[[母题-G2]] 5.1 的三条理由）。
  • 对应母题：【G1】【G2】【G4】
锚点

projects/RuleArena/

  • 用在哪：条款按"条件 / 例外 / 生效时间"结构化切分；召回规则后用确定性状态模型验证
  • 解决什么问题：冲突规则显式返回证据，不强行合成唯一答案——这是"拒答"的正例
  • 踩过的坑：按字数切条款会把「条件」和「例外」切散——一条规则的含义被拆到两个 chunk 里，召回任一半都不完整，模型只能猜。语义被切碎比没召回更危险：它给了你一个看起来有出处的错答案。
  • 决策与取舍：条款的语义边界是逻辑结构，不是长度——按「条件 / 例外 / 生效时间」结构化切分，每个 chunk 才语义自足。字数切分只适合叙述型文本，对「条件-例外」型规则是破坏性的（[[母题-G1]] 的「切分要按语义边界」）。
  • 对应母题：【G1】【G4】
锚点

projects/EnergyOps/

  • 用在哪：运维文档、设备数据和实时状态不混成一个索引；实时事实走 Tool / 数据库，静态说明走 RAG
  • 解决什么问题：故障建议要引用日志 / 指标 Artifact 和操作手册——"证据"有两种形态
  • 踩过的坑：把运维文档和设备实时状态混进同一个索引——检索出来的「当前负荷」其实是上次同步时的，而模型会把它当作当下事实引用。过期的实时数据比没有更危险，因为它带着「这是事实」的外观。
  • 决策与取舍：证据有两种形态，不能混——日志/指标是运行时产生的、会变，走 Artifact 引用（绑定运行 id）；操作手册是静态的，走 RAG。混在一个索引里会让「引用」失去意义：你分不清引的是哪一次运行的日志（[[母题-G4]] 的可追溯性）。
  • 对应母题：【G4】【G6】
