缓存怎么和 DB 保持一致？三类经典事故各自的根因与对策是什么？

缓存和数据库不一致怎么办？缓存穿透、击穿、雪崩分别是什么，怎么防？

一句话结论：数据库是权威状态，缓存是它的派生副本——两个独立系统没有共同事务，所以只能追求"最终一致 + 可接受的不一致窗口"。写路径用 Cache Aside（先写 DB 再删缓存），删除失败要靠 TTL 兜底或 Outbox 保证（EnergyOps 用 Outbox，因为 PG 提交与 Redis 删除不可能构成同一个事务）。三类事故的共同根因是"缓存没挡住请求"：穿透 = 键不存在（空值缓存 / 布隆过滤器）、击穿 = 一个热点过期（互斥重建 / 逻辑过期）、雪崩 = 一大批同时过期（TTL 加抖动 / 多级缓存 / 限流降级）。

  • 缓存是派生数据
  • DB 权威
  • 没有跨系统事务所以做不到强一致
  • 判据是"允许多大的不一致窗口"
  • 先写 DB 再删缓存
  • 删缓存失败要有兜底（TTL 或 Outbox）
  • 删比更新好（懒加载）
  • 穿透=不存在、击穿=一个热点、雪崩=一大批
  • 空值缓存 + 布隆
  • 互斥重建
  • TTL 加抖动
  • DB 是最后一道防线要能限流
  • 缓存故障会把流量倒给 DB

主线：缓存的价值是"用可接受的不一致，换吞吐与延迟"。 一旦把缓存当权威状态、或追求强一致，就同时失去了它的价值和它的安全边界。所以判断任何一个缓存方案，先问两件事：这是派生数据吗？能容忍多大的不一致窗口？

1. 先删缓存还是先写 DB？

先写 DB 再删缓存。反过来会让"并发读把旧值写回缓存并长期保留"。

2. 删缓存失败了怎么办？

TTL 兜底（让脏数据自己过期）+ 重试/对账；要可靠性就上 Outbox（把"删缓存"和业务改动写进同一个本地事务）。

3. 为什么删除缓存而不是更新缓存？

懒加载：只在真有人读时才付重建成本；聚合值（如榜单）尤其不该每次写都重算。

4. 击穿和雪崩怎么区分？

击穿是"一个热点键"，雪崩是"一大批同时失效"。对策也因此不同：击穿靠互斥重建，雪崩靠TTL 抖动。

5. 缓存和 DB 能强一致吗？

不能（没有共同事务）。能做的是"最终一致 + 明确的不一致窗口 + 对账"。

6. 为什么项目里用 Outbox 而不是顺手删缓存？

因为 PG 的提交和 Redis 的删除不可能构成同一个 ACID 事务。把"删缓存"变成一条 DB 记录，才能用本地事务保证"这件事一定会做"。
