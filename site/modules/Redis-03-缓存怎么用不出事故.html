骨架：缓存是派生数据、DB 是权威 → 为什么做不到强一致（没有跨系统事务）→ 四种写路径的对比（先删的坑 / Cache Aside / 删 vs 更新 / Outbox 与 CDC）→ 三类事故的定义与对策（按根因配药）→ 热 key / big value / 跨租户 key → 缓存故障时 DB 要能限流降级

主线：缓存的价值是"用可接受的不一致，换吞吐与延迟"。 一旦把缓存当权威状态、或追求强一致，就同时失去了它的价值和它的安全边界。所以判断任何一个缓存方案，先问两件事：这是派生数据吗？能容忍多大的不一致窗口？

1. 先删缓存还是先写 DB？

先写 DB 再删缓存。反过来会让"并发读把旧值写回缓存并长期保留"。

2. 删缓存失败了怎么办？

TTL 兜底（让脏数据自己过期）+ 重试/对账；要可靠性就上 Outbox（把"删缓存"和业务改动写进同一个本地事务）。

3. 为什么删除缓存而不是更新缓存？

懒加载：只在真有人读时才付重建成本；聚合值（如榜单）尤其不该每次写都重算。

4. 击穿和雪崩怎么区分？

击穿是"一个热点键"，雪崩是"一大批同时失效"。对策也因此不同：击穿靠互斥重建，雪崩靠TTL 抖动。

5. 缓存和 DB 能强一致吗？

不能（没有共同事务）。能做的是"最终一致 + 明确的不一致窗口 + 对账"。

6. 为什么项目里用 Outbox 而不是顺手删缓存？

因为 PG 的提交和 Redis 的删除不可能构成同一个 ACID 事务。把"删缓存"变成一条 DB 记录，才能用本地事务保证"这件事一定会做"。

写路径用 Cache Aside：先写 DB，再删缓存——反过来会让并发读把旧值写回缓存并长期保留。为什么是删除而不是更新：懒加载，只在真有人读时才付重建成本，聚合值（如榜单）尤其不该每次写都重算。删除失败靠 TTL 兜底 + 重试/对账；要可靠性就上 Outbox（把"删缓存"变成一条 DB 记录，用本地事务保证一定会做——因为 PG 的提交和 Redis 的删除不可能构成同一个 ACID 事务，EnergyOps 用的就是 Outbox）。

三类事故的共同根因是"缓存没挡住请求"：穿透 = 键不存在（空值缓存 / 布隆过滤器）、击穿 = 一个热点过期（互斥重建 / 逻辑过期）、雪崩 = 一大批同时过期（TTL 加抖动 / 多级缓存 / 限流降级）。击穿和雪崩的区别：前者是"一个热 key"，后者是"一大批"，对策也因此不同。

分层要点追问深挖时用

  • 结论：DB 是权威、缓存是派生；先写 DB 再删缓存；三类事故根因都是"缓存没挡住请求"。
  • 推导链：两系统无共同事务 → 只能最终一致 → Cache Aside 顺序 → 删而非更（懒加载）→ 失败靠 TTL/Outbox → 三类事故分类。
  • 量化：没有共同事务，所以强一致做不到；Outbox 把"一定会做"交给本地事务。
  • 边界与常见误解：先删缓存再写 DB 是错的（并发读会把旧值写回并长期保留）；预热也要加 TTL 抖动（否则预热即埋雷）；Redis Stream 有持久化但不能简单替代 Kafka。
