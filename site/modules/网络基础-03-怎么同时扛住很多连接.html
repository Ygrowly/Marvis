N3进程 / 线程 / 协程有什么区别；asyncio 为什么能扛住大量并发连接

骨架：先算"时间花在哪"（IO 密集 vs CPU 密集的杠杆）→ 三种执行单元用同一指标比（单位开销 / 谁调度 / 共享什么）→ 从"谁调度"推出所有差异 → 事件循环 + epoll 一次问一批 → 量化 10 万并发的内存 → 协作式的代价（阻塞会卡死整个循环 + 三种解法）→ GIL（为什么多线程救不了 CPU 密集）→ 选型判据

一句话结论：并发不是"同时干很多事"，而是"在等的时候去干别的事"——所以收益由等待占比决定（CPU 占 2% 的请求，单核理论上能并发约 50 个）。三种执行单元的差别从"谁调度"推出来：进程由 OS 调度、地址空间独立（隔离好、通信贵）；线程由 OS 调度、共享地址空间（方便、切换走内核）；协程由用户态事件循环调度、约 2KB 一个（切换几乎免费，但一处阻塞全体停摆）。asyncio 能扛住大量连接，是因为单线程一次 epoll 就能问出成千上万连接里哪些就绪，加上单位开销小两个数量级——线程每个要占内核侧约 25KB（16KB 内核栈 + task_struct，且不计入 RSS）和内核里一个调度实体，协程这两笔全省。

  • 并发 = 利用等待时间
  • 并发杠杆 ≈ 总耗时 ÷ CPU 时间
  • IO 密集收益大、CPU 密集收益≈1
  • 进程独立地址空间
  • 线程共享但切换走内核
  • 线程内核侧 25KB + 栈 8MB 虚拟；协程内核侧 0
  • 协程由事件循环调度、协作式
  • epoll 一次问一批
  • **任务数上限是 pid_max
  • threads-max
  • pids.max，不是内存**
  • 阻塞调用卡死整个循环
  • GIL 让多线程对 CPU 密集无效
  • 多核靠多进程
  • 是并发不是并行

主线：并发的收益 = 等待时间占总时间的比例。 这句话同时决定了三件事：该不该用异步（IO 密集才值得）、asyncio 为什么能扛很多连接（同内存下单元数多两个数量级）、以及它最怕什么（一旦有代码不让出，等待时间就被浪费掉了）。

1. 协程和线程最本质的区别是什么？

谁调度：线程由 OS 抢占式调度（会强行换），协程由程序协作式调度（你不让就一直占）。"阻塞代码能卡死事件循环"这个代价就是从这一条来的。

2. asyncio 能利用多核吗？

不能，它是单线程。要多核靠多进程；多线程因 GIL 对 CPU 密集无效。

3. 在协程里调用同步库会怎样？

卡死整个事件循环，表现为"所有接口一起变慢、但 CPU 不高、日志无异常"。修法是换异步库或丢线程池。

4. 单线程异步还需要考虑竞态吗？

需要。await 会让出控制权，两个协程可能交错修改同一状态。"await 前后状态可能变"是异步里的经典陷阱（这一点和线程加锁是不同形态的同一类问题）。

5. 连接池耗尽 / 协程泄漏怎么排查？

池子耗尽先看上游时延（[[母题-N1-一次请求的完整路径]] 的 L = λW）；协程泄漏通常是创建了任务但没有正确取消（超时/取消链路要传下去）。

  • 量化：协程约 2KB vs 线程内核侧约 25KB（16KB 栈 + task_struct，不计入 RSS）；CPU 占 2% 的请求单核可并发约 50 个。
  • 边界与常见误解："协程比线程快"要看是不是 IO 密集；无界队列/无界排队会把过载悄悄变成全局超时（要有背压）；load 高而 CPU 不高说明在等 IO，不是该加 CPU。
