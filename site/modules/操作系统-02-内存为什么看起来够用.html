骨架：先立"两个内存"的概念与虚拟内存的三个作用 → 地址翻译（多级页表的算式 + TLB 覆盖范围）→ 缺页三档代价 → 从缺页推出"malloc 成功 ≠ 有内存"与 overcommit 三档策略 → 量化"8GB 跑 4GB" → VSZ / RSS / anon-rss 三个量 → 页缓存与 PSI → swap 的定位 → 大页的算式 → OOM 的公式与四条硬规则 → 两类 OOM 的分辨（最实用） → 控制手段排序 → 边界与误解

一句话结论：虚拟内存让"申请"和"占用"解耦——malloc(8GB) 只是在虚拟地址空间里记一笔账（默认 overcommit_memory=0 的启发式会放行），物理页在第一次访问时（缺页）才分配，所以 8GB 的程序能跑在 4GB 机器上，但打满物理内存时会在运行中触发 OOM（而不是启动时报错）——这就是"申请 ≠ 占用"的代价。缺页的代价跨几个数量级：TLB 命中 纳秒级（≈ L1）、次要缺页 微秒级、主要缺页（要从磁盘换回来）百微秒级——所以"别让服务去 swap"是硬规矩。大页存在的唯一理由是让 TLB 装得下（4KB 页下 TLB 只能覆盖几 MB，2MB 大页能覆盖几 GB）。OOM 是算出来的：oom_badness() = 内存占用（rss 各项 + 页表 + swap）+ oom_score_adj × totalpages/1000，杀分最高的；而且有两类 OOM 必须分清——整机 OOM 与 cgroup OOM，后者的日志前缀是 Memory cgroup out of memory，和宿主机剩余内存无关。

  • 虚拟内存两大作用（隔离 + 申请/占用解耦）
  • malloc 只拿虚拟地址，物理页在缺页时才给
  • 4 级页表（48 位地址 = 9+9+9+9+12）
  • 一级页表要 512GB（所以必须分级）
  • TLB 条目有限 → 4KB 页只能覆盖几 MB，2MB 大页能覆盖几 GB
  • 缺页三档（纳秒 / 微秒 / 百微秒）
  • VSZ 无参考价值，看 RSS，排查 OOM 看 anon-rss
  • 页缓存可回收，看 available 不看 used
  • swap 是压力阀不是扩容
  • oom_badness() 的组成，页表也计入
  • oom_score_adj −1000 = 免死（滥用会 panic）
  • 共享同一 mm 的任务一起被杀
  • 两类 OOM + 日志前缀

  • memory.high 提前回收
  • PSI some avg10
  • 治理根因 = 给无上界队列设上界
  • 测量值只当量级

主线："申请"和"占用"被解耦，是一切内存现象的总开关。 它同时解释了：为什么 malloc 成功还会 OOM（解耦的代价）、为什么 8GB 能跑 4GB 机器（解耦的收益）、为什么无上界的队列能拖几天才爆（解耦把故障从启动期推迟到运行期）。而控制它的唯一通用手段不是"加内存"，是"给每个会增长的东西设上界"。

1. 为什么 malloc 成功还会 OOM？

malloc 只拿到虚拟地址空间，物理页在首次访问（缺页）时才分配。所以问题是推迟到运行期才暴露的——而且 overcommit_memory=0（默认）是刻意这么设计的，因为 fork() 会让虚拟大小暂时翻倍，严格执行会连正常程序都起不来。

2. VSZ 很大是不是内存泄漏？

不是。VSZ 包含 mmap 的文件和地址预留，基本没有参考价值。看 RSS，排查 OOM 看 anon-rss（total-vm 在 OOM 日志里也印着，但它是"几乎无意义"的那个）。

3. OOM 会杀哪个进程？

按 oom_badness() 打分，内存占用（rss_anon + rss_file + rss_shmem + swap + 页表页数）占主导，再用 oom_score_adj × totalpages/1000 调整，杀分最高的。init 和内核线程不杀；与 victim 共享地址空间的一起杀；5 秒内不连杀。

4. 容器被 OOM 杀了怎么排查？

先看日志前缀分清是哪一类：Memory cgroup out of memory 是 cgroup OOM（撞了 memory.max，与宿主机剩余内存无关）；Out of memory 是整机 OOM。然后查 memory.max / memory.current，再判断是"渐涨撞上去"还是"一次性冲上去"。

5. swap 要不要开？

看负载。数据库 / 缓存类建议关或设很小（热数据被换出去后一次访问是微秒到百微秒量级，表现为"CPU 不高、磁盘狂转、服务奇慢"，比 OOM 更难查）；通用服务可留少量作压力阀，但要监控 major fault 速率。swap 的定位是压力阀，不是扩内存。

6. 怎么提前发现内存问题？

/proc/pressure/memory（PSI）：some avg10 低于 5% 健康、持续高于 20% 说明 OOM 可能已在前方。比等 OOM 日志更早，还能区分是内存压力还是 IO 压力。

虚拟内存让"申请"和"占用"解耦——malloc(8GB) 只是在虚拟地址空间里记一笔账（默认 overcommit_memory=0 的启发式会放行），物理页在第一次访问时（缺页）才分配。所以 8GB 的程序能跑在 4GB 机器上，但打满物理内存时会在运行中触发 OOM（而不是启动时报错）——这就是"申请 ≠ 占用"的代价。

分层要点追问深挖时用

  • 结论：申请 ≠ 占用；缺页代价跨数量级，所以不能让服务 swap；大页为的是 TLB 覆盖率。
  • 推导链：虚拟地址记账 → 首次访问才分配 → 三种缺页代价 → swap 是延迟抖动源 → 大页减少 TLB miss。
  • 量化：TLB 命中纳秒级、次要缺页微秒级、主要缺页百微秒级。
  • 边界与常见误解："malloc 成功就有内存"×；容器里要看 cgroup 文件而不是 free。
