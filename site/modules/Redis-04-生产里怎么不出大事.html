R4大 key 和热 key 怎么发现、怎么拆；它们为什么会同时打穿内存、网络和单个分片

骨架：先把两个维度分开（体积 vs 频率）→ 给两个共同前提（单线程、单分片）→ 大 key 的四个危害面 → 发现（三种手段与注意事项）→ 拆（UNLINK / 分批 / 按业务维度拆）→ 热 key 为什么加节点无效（算一遍）→ 发现（客户端统计 + 分片倾斜）→ 解（读热 vs 写热分开）→ 本地缓存的代价要量化 → 边界与误解

一句话结论：大 key 与热 key 是两个维度的问题——大 key 是体积（危害来自"Redis 命令执行单线程"，一条大命令会把所有人一起挡住；删一个 200 万 field 的 Hash 能阻塞约 200 ms，所以要用 UNLINK 或 HSCAN 分批）；热 key 是频率（危害来自"集群里一个 key 只属于一个分片"，加节点完全无效，只对读有效——读热用本地缓存（命中 95% 就把 3 万 QPS 降到 1500）或打散成多个副本 key；写热只能靠本地聚合、队列串行或换结构）。发现手段分别是 --bigkeys/MEMORY USAGE（采样估算 + 逐个确认）和客户端/代理层统计 + "单分片倾斜"这个信号；MONITOR 能看但代价大，别在生产常开。而"按业务维度拆成大堆小 key"是一箭双雕的动作：既解决了大 key，也顺带分散了访问。

主线：大 key 的危险来自"单线程"（一条大命令挡住全体），热 key 的危险来自"单分片"（一个 key 打不散）。 想清楚这两个前提，就能自己推出所有解法：大 key 要把一次大操作拆成多次小操作，热 key 要把一个点变成多个点（读）或把多次写变成一次写（写）。

1. 大 key 为什么危险？

因为 Redis 命令执行是单线程的：一条 DEL 大 key 会在主线程里同步释放所有元素（200 万 field 约 200 ms），这期间所有请求的延迟都 +200 ms。另外还有网络带宽、主从复制延迟、集群迁移卡住三个面。

2. 删大 key 该怎么做？

UNLINK（异步回收）或 HSCAN/SSCAN + 分批删。注意 UNLINK 之后内存是逐步释放的，监控上不会立刻掉。

3. 热 key 为什么扩容没用？

集群里一个 key 只落在一个分片，压力不会因为加节点而摊开。"单分片打满、其他分片闲置"就是热 key 的签名。

4. 热 key 怎么解决？

先分清读热还是写热：读热用本地缓存（首选，命中率高时直接把 Redis 的流量砍掉一个数量级）或打散成多个副本 key；写热打散无效（一次写变 N 份），要靠本地聚合 / 队列串行 / 换数据结构。

5. 本地缓存能用吗？有没有一致性问题？

能，而且一致性可以量化：TTL 50 ms 就意味着"最多旧 50 ms"。判据是三问：丢了能不能重建、旧 50 ms 能不能忍、会不会因为旧值做错事。只要它参与判断（余额、库存），就不能用。

主线：缓存能解决的问题只有"快"，不能解决"可靠"和"正确"。 所以边界只有一条：能被重建的、不参与判断的、能容忍旧值的东西，才属于缓存（能用 1/(1−命中率) 量化它的风险、能用 TTL 量化它的不一致）。而"权威状态在哪"是一句架构级的话——它决定了"哪个组件挂了是事故、哪个挂了只是变慢"。

1. 余额能不能缓存？

看路径：展示可以（旧一点无所谓）；判断不能（旧值会让用户做错决定）。标准做法是"显示走缓存、扣减用 UPDATE ... WHERE balance >= ? 下沉到数据库"（[[母题-L1-乐观锁与悲观锁]] 2.3）。

2. 缓存挂了怎么办？

先算回源放大 1/(1−命中率)（95% → 20 倍）；然后按"限流 → 降级 → 本地缓存兜底"设计闸门。绝不能让"未命中"直接等于"打数据库"。

3. TTL 设多少？

按最苛刻的用途定（展示路径可以长、判断路径基本是 0）；加随机抖动防集体到期；而且它的角色是给写时失效兜底，不是主要机制。

4. Redis 能当数据库用吗？

不能。AOF everysec 最坏丢约 1 秒、RDB 丢更多，加上异步复制、主动淘汰、误操作——持久化保证的是"重启后数据大多还在"，不是"唯一一份"。

5. 缓存一致性怎么做到"不骗人"？

说清三件事：① 上限是多少（TTL 几秒 / 写时失效几百毫秒）；② 失败怎么办（删缓存失败靠 TTL 兜底，用 Outbox 保证最终执行）；③ 哪些路径不能容忍（参与判断的那条走权威来源）。

17必背**R4**

这道题属于母题 R4 · 大 key 和热 key 怎么发现、怎么拆；它们为什么会同时打穿内存、网络和单个分片 · 下面挂它的完整回答（学的时候看）

实测 38 字 · 按 4 字/秒折算约 10 秒（秒数是估算，字数才是实测）

大 key 与热 key 是两个维度：大 key 是体积，热 key 是频率，对策完全不同。

分层要点追问深挖时用

  • 结论：大 key 管体积（单线程阻塞），热 key 管频率（分片归属），对策不同。
  • 推导链：单线程 → 一条大命令挡住所有人 → UNLINK/分批；一个 key 只属一个分片 → 扩容无效 → 读热/写热分治。
  • 量化：删 200 万 field 的 Hash ≈ 阻塞 200 ms；本地缓存命中 95% 把 3 万 QPS 降到 1500；TTL 50 ms = 最多旧 50 ms。
  • 边界与常见误解：扩容治不了热 key（MONITOR 别生产常开）；写热打散会变成 N 份写，反而更糟；UNLINK 后内存是逐步释放的，监控不会立刻掉。
