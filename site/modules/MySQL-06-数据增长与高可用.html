M14主从复制原理；主从延迟怎么来的、读到旧数据怎么办

骨架：复制三步 + "复制的是变更"这个前提 → 延迟三源（①②是结构性的）→ 缓解手段（并点明半同步治的不是这个）→ 读到旧数据的三层解法 + 为什么不用 sleep → 什么时候才该上读写分离 → 收束到"延迟是结构性的"

一句话结论：主库提交时写 binlog → 从库 IO 线程拉取并写入 relay log → 从库 SQL 线程重放。关键是复制的是"变更流"不是数据页，所以从库是追赶者，"追不上"是结构性的。延迟有三个来源：① 回放并行度永远 ≤ 主库（按库并行时天花板就是库数——4 个库 × 25,000 = 100,000 TPS，与主库刚好打平）；② 大事务必须整体重放（主库跑 10 分钟，从库也 10 分钟，期间变更对从库完全不可见）；③ 从库自身慢（Row 格式下无主键表退化成全表扫，量级差 20 万倍——所以"每张表都要有主键"是复制性能问题）。"读到旧数据"的三层解法按优先级：读己之写 → 会话粘主库 → 延迟超阈值降级；不能用 sleep（延迟波动、时长无依据、把正确性建立在猜测上）。注意半同步解决的是 RPO，不是读一致性——这两件事最常被混为一谈。

  • binlog → relay log → 重放
  • 复制的是变更不是数据页
  • 从库是追赶者
  • 并行度 ≤ 主库（按库并行的天花板 = 库数）
  • 大事务整体重放、期间不可见
  • Row 格式无主键退化成全表扫（20 万倍）
  • 并行复制按库→按事务→按 WRITESET
  • 拆大事务
  • 表必须有主键
  • 半同步 = RPO ≠ 读一致性
  • 读己之写 → 会话粘主库 → 超阈值降级
  • 不要 sleep

M15冷热分离 / 归档 / 读写分离；为什么不是一上来就分库分表

骨架：先定问题（三选一）→ 五步顺序 + 为什么是这个顺序 → 冷热分离（索引层数算式）→ 归档（≠ 删除 + 分批的算式）→ 分库分表四项代价 + 分片键选法（迁移 50% 的算式）→ 回到题目

一句话结论："数据量大"本身不是问题，"热查询背着冷数据跑"才是问题。 所以治理顺序是五步：① 索引与 SQL做好 → ② 事务边界与锁冲突管好 → ③ 冷热分离与归档 → ④ 读写分离 → ⑤ 单机真的扛不住才分库分表。这个顺序的依据是"便宜且可逆的先做，贵且难回头的后做"——而分库分表有四项代价：路由变复杂（查询必须带分片键，否则广播）、跨分片聚合分页难、跨分片事务难、扩容要迁移约 50% 的数据。冷热分离按时间轴把热数据与冷数据分层（8000 万行归档到 800 万行，索引从 4 层降到 3 层）；归档 ≠ 删除，要分批搬分批删（否则 7000 万行一次性 DELETE 会产生约 14 GB undo、拖成长事务）；分片键不是"数据本身的属性"，是"查询形状的属性"，而且它最难改。

主线：复制是"至少存在延迟的"，读写分离的正确性必须显式设计，不能靠"从库应该很快"。 ——所以"哪些读可以走从库"是业务决策，不是技术默认值。

1. 为什么 Row 格式更安全但更大？

Statement 记 SQL，遇到 NOW() / UUID() 这类非确定函数主从执行结果可能不同（主从漂移）；Row 记每行的前后镜像，重放绝对精确，但一条批量 UPDATE 会把每一行的变化都记下来，日志量暴涨。Mixed 是折中。

2. 读写分离之后，主库的压力真的降了吗？

读压力降了，写压力一点没降；而且主从同步本身消耗主库资源。所以"加从库"解决的是读瓶颈，不是写瓶颈——写瓶颈要么靠拆（分库分表），要么靠异步化（消息队列）。

3. 延迟指标准吗？

不精确：它衡量的是"从库 SQL 线程处理到的位置与主库当前时间的差"，主库空闲时它会归零（哪怕 binlog 还没传完），从库卡住时也可能不准。生产要配合 GTID 位点综合判断。

4. GTID 是什么？

全局事务 ID，让从库定位"我回放到哪了"不再依赖文件名 + 偏移量，主从切换、搭建新从库都因此简单很多。知道作用即可。

5. 异步复制下主库挂了会丢数据吗？

会。异步复制下主库提交不等从库确认；半同步能缓解（等至少一个从库收到），代价是提交延迟变长。这是 [[母题-P12-流复制与逻辑复制]] "同步/异步取舍"的 MySQL 版。

主线："数据量大"本身不是问题，"热查询背着冷数据跑"才是问题。 所以治理的第一动作永远是把热和冷分开，而不是"把大表拆开"——两者听起来像，做的完全是不同的事。

1. 分片键选错了怎么办？

分片键是"最难改的决定"：改它要全量重分布数据，扩容也要迁移约 50%。所以选型必须基于真实的查询分布，而不是"字段看起来像 ID"。这和 [[母题-P16-分区表]] 的"分区键必须进大部分查询条件"是同一个原则。

2. 跨分片的事务怎么办？

最好的答案是"业务上避免跨分片写"（把强一致的数据放同一分片，即按业务单元分片）；实在避免不了才考虑分布式事务——那是复杂度的新台阶。RuleArena 的"至少一次投递 + 幂等消费者 + 权威查询"替代 exactly-once 就是同一思路：跨边界的正确性优先用幂等解决，而不是用强一致事务硬扛（[[母题-P19-唯一约束与UPSERT]]）。

3. 归档和分区怎么选？

MySQL：两张表 + 定期迁移（应用管理）；PG：分区表 + DROP 分区（数据库管理）。PG 的方案更顺——"丢弃分区"几乎瞬时且不产生死元组；MySQL 的 "DELETE + 迁移"是长事务与膨胀源。这条对照能同时展示两边的能力差异。

4. 8000 万行必须分表吗？

不一定。单表几千万行在索引合理时完全可服务；真正的信号是：索引与 SQL 已优化到位、事务已拆批、冷数据已归档，仍然扛不住。"行数"从来不是分表的直接理由。

原理三步：主库提交时写 binlog → 从库 IO 线程拉取并写入 relay log → 从库 SQL 线程重放。关键是复制的是「变更流」不是数据页，所以从库永远是追赶者，「追不上」是结构性的，不是故障。

延迟有三个来源。① 回放并行度永远 ≤ 主库：按库并行时天花板就是库数，4 个库 × 25,000 TPS 才与主库刚好打平。② 大事务必须整体重放：主库跑 10 分钟，从库也要 10 分钟，期间这批变更对从库完全不可见。③ 从库自身慢：Row 格式下无主键表的更新退化成全表扫，量级差到约 20 万倍——所以「每张表都要有主键」本质是复制性能问题。

读到旧数据按优先级三层解法：读己之写（刚写完的读走主库或等位点追上）、会话粘主库、超阈值降级。不要用 sleep——延迟会波动，时长没有依据，而且那是把正确性建立在猜测上。

边界：半同步解决的是 RPO（主库挂了丢不丢），不是读一致性，它只保证至少一个从库收到了 binlog，不保证已经重放完；加从库只降读压力，写压力一点没降，而且同步本身还消耗主库资源。

分层要点追问深挖时用

边界：行数从来不是分表的直接理由，真正的信号是前三步做完仍然扛不住。

  • 结论：治理五步，判据是「便宜且可逆的先做」；行数本身不是分表理由。
