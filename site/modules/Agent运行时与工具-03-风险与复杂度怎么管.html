A6怎么让 Agent 能干活又不闯祸（沙箱、权限分级、人工确认）

骨架：先破"每次都确认"（审批疲劳 + 84% 的实测）→ 两个边界必须同时（两条泄露路径）→ 实现细节（cwd 读写 + unix socket 代理 + 新域名确认）→ 风险分级（减少 80% 打断 + 划线的两个维度）→ 批准绑定具体动作（禁止"允许所有"）→ 真凭证不进沙箱 → 提示注入的三层防线 → 收束到"确定性 vs 概率性"

一句话结论："不闯祸"不能靠"让模型别做坏事"，也不能靠"人一直盯着"——要靠"即使它决定做坏事，也做不到"。 所以核心机制是用边界替代确认：文件系统隔离（管"能碰什么"）+ 网络隔离（管"能送到哪"），两个必须是"与"不是"或"——只有文件系统隔离，它能读到的东西可以被传出去；只有网络隔离，它能改坏沙箱外的东西甚至绕出去再联网。Anthropic 的实测是沙箱把审批提示减少 84%、同时更安全——因为"每次都确认"会失效：50 个动作里用户从第 20 次左右就不看了，后 30 次形同虚设。所以还要风险分级（R0 自动 / R1 提示 / R2 强制拦截），把打断减少 80% 且集中在真正重要的动作上。批准必须绑定具体动作摘要和版本——"允许所有"等于把批准从"一次动作"降级成"一个类别"。最后，真正的凭证永远不进沙箱：沙箱内只给范围受限的凭证，真 token 由沙箱外的代理校验内容之后才附加。

  • 审批疲劳（50 个动作里后 30 次被无视）
  • 实测沙箱减少 84% 提示
  • 两个边界必须同时（文件系统 + 网络）
  • 只有文件系统 → 能外传；只有网络 → 能改坏
  • 只读默认 + 改前要问
  • 新域名才确认（频率从 O(动作) 降到 O(新增目标)）

  • R1
  • R2（减少 80% 打断）
  • 判据 = 可逆性 + 影响范围
  • 批准绑定动作摘要与版本，禁止"允许所有"
  • 真凭证不进沙箱（代理附加）

A7什么时候真的需要多 Agent，什么时候是自找麻烦

骨架：先破"更聪明"（给 80% 方差的归因）→ 效果 90.2% 与代价 15× → 两条判据（价值 + 可并行性） → 适用/不适用的场景 → effort 分档（给 24 倍浪费的算式）→ 两级并行降 90% + 上下文隔离 → 同步执行的瓶颈 → 涌现行为与评测 → 收束到"用钱买性能"

一句话结论：多 Agent 有效的原因不是"多个模型更聪明"，是"多花了 token + 并行"——Anthropic 的归因分析显示，token 用量单独就解释了 80% 的性能方差（三个因素合计 95%）。效果实测是比单 Agent 高 90.2%（Opus 4 做 lead + Sonnet 4 做子 agent，对比单 Opus 4）。代价是 15× token（普通对话 1×、单 agent ≈ 4×、多 agent ≈ 15×），所以它的判据是"任务价值高到足以支付这个性能提升"。适用的任务有三类特征：重并行、信息量超出单窗口、要对接很多复杂工具；不适合的是"所有 agent 必须共享同一份上下文"或"子任务依赖很密"——原文明确说大多数编码任务的真正可并行部分比研究少。effort 必须分档（简单查找 1 个 agent/3–10 次调用、直接对比 2–4 个子 agent、复杂研究 >10 个），因为模型判断不了该用多大力，不分档会浪费约 24 倍。并行的收益来自两级（lead 派 3–5 个子 agent + 子 agent 内部并行 3+ 工具），实测降 90% 时间；而另一半收益是上下文隔离——子 agent 烧几万 token 探索，只回传 1,000–2,000 token 的结论。最后，多 Agent 的评测更难：它有涌现行为，改 lead 的 prompt 会不可预测地改变子 agent 的行为，所以要评交互模式，不只是单个 agent。

  • 有效原因是"多花 token + 并行"（token 解释 80% 方差）
  • 实测高 90.2%
  • 代价 15×（对话 1×、单 agent 4×）
  • 判据 = 任务价值 + 能否并行拆开
  • 适用：重并行 · 超单窗口 · 多复杂工具
  • 不适：共享上下文 · 依赖密集（大多数编码任务）
  • effort 分档（1 个 / 2–4 个 / >10 个），不分档浪费 24 倍
  • 两级并行降 90% 时间
  • 子 agent 只回传 1–2K（噪声留在它自己窗口）
  • 同步执行是瓶颈（被最慢的卡住）
  • 涌现行为 → 评交互模式
  • prompt 从"指令"变成"协作框架"

A8计划是模型动态生成且会变的情况下，怎么保证执行不失控

骨架：先破"让它别改"（动态计划的价值就在能改）→ 跑偏的隐蔽性（看起来很正常）→ 计划外化（给成本对比）→ 可读性（agent 访问不到 = 不存在，给 10 倍收益）→ 验证优先级与确定化的收益（给 19.7% vs 52.2%）→ linter 的错误信息注入修复指令 → Reflection 的局限 → 收束到"把脑子里的东西搬到系统里"

一句话结论：动态计划的问题不是"会变"，是"变了没人知道、也回不去"。 而且跑偏最难的地方在于"它看起来很正常"——还在调工具、还在推进，没有任何信号告诉你它在做的不是原来那件事。所以解法是三件事一起做：① 计划外化——把计划做成版本化的产物（OpenAI 的做法是 checked into the repository，修订产生新版本，偏离变成可见的 diff）；② 把目标变成可验证的信号——"agent 访问不到的东西等于不存在"，把 logs/metrics/traces 暴露给 agent 后，目标从"确保启动快一点"变成"启动在 800ms 内"，验证成本差 10 倍；③ 能确定化的检查就确定化——10 项检查全用模型 Judge（85% 准）只有 19.7% 全对，60% 确定化后是 52.2%（20 项时差 7 倍）。Reflection 不能替代外部 oracle（同一模型重复同一盲点），它的正确位置是生成候选修复，不是验收。最后一条设计很值：约束不写在提示里，而是写成 linter，把修复指令塞进错误信息——只在违反时出现，而且出现得正是时候。

  • 动态计划的问题是不可见不是"会变"
  • 跑偏的 agent 看起来很正常
  • 计划外化成版本化产物（checked into repository，偏离 = 可见 diff）
  • 成本 16 KB vs 整个任务作废
  • "agent 访问不到就等于不存在"
  • 可观测性暴露给 agent → 目标可验证（10 倍人工差）
  • 能确定化的就确定化：10 项 19.7% → 52.2%，20 项差 7 倍
  • custom linter + 错误信息注入修复指令
  • Reflection 只生成候选不验收
  • 验证优先级：确定性 > 权威状态 > 交叉证据 > 模型 Judge > 人工

1. 危险动作的人工确认该展示什么？

为什么不能每次都确认：Anthropic 的实测是沙箱把审批提示减少 84%、同时更安全，因为"每次都确认"会失效——50 个动作里用户从第 20 次左右就不看了，后 30 次形同虚设。所以还要风险分级（R0 自动 / R1 提示 / R2 强制拦截）。

人工确认要展示六项：将执行什么、作用对象、关键参数、影响、证据、是否可撤销；而且批准必须绑定具体动作摘要和版本——"允许所有"等于把批准从"一次动作"降级成"一个类别"。

提示注入在 Agent 场景更危险：聊天场景的损失在信息层面，Agent 场景在动作层面（删文件、发消息、转账、改权限），而且是真发生了。所以防线按确定性排序：边界 → 契约（参数独立校验、危险动作需确认）→ 过滤（内容检测），顺序不能反——过滤是概率性的、有持续成本、会被绕过，而"以为有防线"比"没有防线"更危险。最后一条：真正的凭证永远不进沙箱。

分层要点追问深挖时用

  • 结论：用边界替代确认；文件系统 + 网络两个隔离必须同时有；防线按确定性排序。
  • 推导链：确认会失效 → 用边界 → 两个方向都要堵 → 风险分级集中打断 → 注入损失在动作层 → 边界 > 契约 > 过滤。

  • 边界与常见误解：云端沙箱还要防跨租户逃逸（独立容器 / microVM）；Skill/插件扩大能力面也就扩大权限面，按"能做什么"而非"谁提供的"授权；验证靠红队测试（既读不到、也发不出，两个边界各测一条）。

多 Agent 有效的原因不是"多个模型更聪明"，是多花了 token + 并行——Anthropic 的归因分析显示，token 用量单独就解释了 80% 的性能方差（三个因素合计 95%）。效果实测比单 Agent 高 90.2%（Opus 4 做 lead + Sonnet 4 做子 agent，对比单 Opus 4）。

代价是 15× token（普通对话 1×、单 agent ≈ 4×、多 agent ≈ 15×），所以判据是"任务价值高到足以支付这个性能提升"。适用的任务有三类特征：重并行、信息量超出单窗口、要对接很多复杂工具；不适合的是"所有 agent 必须共享同一份上下文"（如大多数编码任务）或"子任务依赖很密"。

上下文怎么传：子 agent 用独立上下文窗口，只回传结构化的浓缩结论（1–2K token）；大产物写外部系统、只传轻量引用——避免"传话游戏（game of telephone）"。

  • 结论：多 Agent 的收益来自 token 与并行，不是更聪明；判据是任务价值能否支付 15× token。
  • 推导链：归因分析（token 解释 80% 方差）→ 收益 +90.2% → 代价 15× → 三类适用特征 → 隔离与传递 → effort 分档。

动态计划的问题不是"会变"，是"变了没人知道、也回不去"。而且跑偏最难的地方在于"它看起来很正常"——还在调工具、还在推进，没有任何信号告诉你它在做的不是原来那件事。

所以三件事一起做：① 计划外化——把计划做成版本化的产物（OpenAI 的做法是 checked into the repository，修订产生新版本，偏离变成可见的 diff），人不必读全过程，只需要看计划变了没有；② 把目标变成可验证的信号——"agent 访问不到的东西等于不存在"，把 logs / metrics / traces 暴露给 agent 后，目标从"确保启动快一点"变成"启动在 800ms 内"，验证成本差 10 倍；③ 能确定化的检查就确定化——10 项检查全用模型 Judge（85% 准）只有 19.7% 全对，60% 确定化后是 52.2%。

  • 推导链：跑偏无声 → 外化让偏离可见 → 目标可验证（访问不到的等于不存在）→ 确定化检查 → 约束写成 linter 而不是提示。
  • 量化：10 项检查全用模型 Judge（85% 准）只有 19.7% 全对，60% 确定化后 52.2%；"启动 800ms 内"让验证成本差 10 倍。
  • 边界与常见误解：Agent 评测的归因层次比 RAG 多（目标理解 → 计划 → 工具选择与参数 → 副作用 → 终止判定），且要评交互模式；RuleArena 用显式 FSM 是因为高风险动作要"当前该做哪一步"可检查，而不是"模型觉得该做哪一步"。
