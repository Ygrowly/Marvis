A6怎么让 Agent 能干活又不闯祸（沙箱、权限分级、人工确认）草稿 · 待验收单卡 →

Agent 要动真实世界，但它的决策是概率的——那"不闯祸"这件事靠什么保证？为什么"每一步都让人确认"是错的？

面试官问——"你们怎么让 Agent 能干活又不闯祸？危险操作怎么控制？"

一句话结论："不闯祸"不能靠"让模型别做坏事"，也不能靠"人一直盯着"——要靠"即使它决定做坏事，也做不到"。 所以核心机制是用边界替代确认：文件系统隔离（管"能碰什么"）+ 网络隔离（管"能送到哪"），两个必须是"与"不是"或"——只有文件系统隔离，它能读到的东西可以被传出去；只有网络隔离，它能改坏沙箱外的东西甚至绕出去再联网。Anthropic 的实测是沙箱把审批提示减少 84%、同时更安全——因为"每次都确认"会失效：50 个动作里用户从第 20 次左右就不看了，后 30 次形同虚设。所以还要风险分级（R0 自动 / R1 提示 / R2 强制拦截），把打断减少 80% 且集中在真正重要的动作上。批准必须绑定具体动作摘要和版本——"允许所有"等于把批准从"一次动作"降级成"一个类别"。最后，真正的凭证永远不进沙箱：沙箱内只给范围受限的凭证，真 token 由沙箱外的代理校验内容之后才附加。

  • **审批疲劳**（50 个动作里后 30 次被无视）
  • 实测沙箱**减少 84% 提示**
  • **两个边界必须同时**（文件系统 + 网络）
  • 只有文件系统 → 能外传；只有网络 → 能改坏
  • 只读默认 + 改前要问
  • **新域名才确认**（频率从 O(动作) 降到 O(新增目标)）
  • 风险分级 R0
  • R1
  • R2（减少 80% 打断）
  • 判据 = 可逆性 + 影响范围
  • **批准绑定动作摘要与版本**，禁止"允许所有"
  • 真凭证不进沙箱（代理附加）
  • 防注入三层：边界 > 契约 > 过滤

主线：安全不能建立在"概率性的判断"上——无论是模型的自律、人的注意力，还是内容过滤器。

1. 危险动作的人工确认该展示什么？

将执行什么、作用对象、关键参数、影响、证据、是否可撤销（study/04 的清单）。而且批准要绑定具体动作摘要和版本——不能用一次"允许所有"永久放权。

2. 提示注入在 Agent 场景下为什么更危险？

聊天场景的损失在信息层面，Agent 场景的损失在动作层面（删文件、发消息、转账、改权限），而且这些动作是真的发生了。所以防线要以"边界"为主、"过滤"为辅。

3. Agent 需要哪些权限？怎么给？

最小权限：每个工具只拿到完成它所需的最小权限；跨权限域的操作拆成多个工具；高权限动作必须有人工确认。原文的 git 例子是范围受限凭证 + 代理校验内容后附加真 token。

4. Skill / 插件这类扩展怎么管？

它们扩大了 Agent 的能力面，也就扩大了权限面。要按"能做什么"而不是"是谁提供的"来授权，而且扩展本身也要能被审计和禁用（[[母题-A2-工具调用与MCP边界]] 的"工具的每个面都是给模型看的界面"在这里变成"每个扩展都是一个新的权限面"）。

A7什么时候真的需要多 Agent，什么时候是自找麻烦草稿 · 待验收单卡 →

一个 Agent 不够用的时候，加一个 Agent 就能解决吗——"多 Agent"到底买到了什么，又付出了什么？

面试官问——"什么时候该用多 Agent？你们为什么用它 / 为什么不用它？"

一句话结论：多 Agent 有效的原因不是"多个模型更聪明"，是"多花了 token + 并行"——Anthropic 的归因分析显示，token 用量单独就解释了 80% 的性能方差（三个因素合计 95%）。效果实测是比单 Agent 高 90.2%（Opus 4 做 lead + Sonnet 4 做子 agent，对比单 Opus 4）。代价是 15× token（普通对话 1×、单 agent ≈ 4×、多 agent ≈ 15×），所以它的判据是"任务价值高到足以支付这个性能提升"。适用的任务有三类特征：重并行、信息量超出单窗口、要对接很多复杂工具；不适合的是"所有 agent 必须共享同一份上下文"或"子任务依赖很密"——原文明确说大多数编码任务的真正可并行部分比研究少。effort 必须分档（简单查找 1 个 agent/3–10 次调用、直接对比 2–4 个子 agent、复杂研究 >10 个），因为模型判断不了该用多大力，不分档会浪费约 24 倍。并行的收益来自两级（lead 派 3–5 个子 agent + 子 agent 内部并行 3+ 工具），实测降 90% 时间；而另一半收益是上下文隔离——子 agent 烧几万 token 探索，只回传 1,000–2,000 token 的结论。最后，多 Agent 的评测更难：它有涌现行为，改 lead 的 prompt 会不可预测地改变子 agent 的行为，所以要评交互模式，不只是单个 agent。

  • **有效原因是"多花 token + 并行"**（token 解释 **80%** 方差）
  • 实测高 **90.2%**
  • 代价 **15×**（对话 1×、单 agent 4×）
  • 判据 = **任务价值 + 能否并行拆开**
  • 适用：重并行
  • 超单窗口
  • 多复杂工具
  • 不适：共享上下文
  • 依赖密集（**大多数编码任务**）
  • **effort 分档**（1 个
  • 2–4 个
  • >10 个），不分档浪费 **24 倍**
  • **两级并行降 90% 时间**
  • 子 agent 只回传 **1–2K**（噪声留在它自己窗口）
  • **同步执行是瓶颈**（被最慢的卡住）
  • 涌现行为 → 评交互模式
  • prompt 从"指令"变成"协作框架"

主线：多 Agent 买的是"token 预算 + 并行度 + 上下文隔离"，不是"集体智慧"。 所以判据从来不是"这个任务难不难"，而是"这个任务值不值得多花 15 倍的钱"和"它能不能被并行拆开"。

1. 什么时候该拆多 Agent，什么时候不该？

该：重并行 + 信息超出单窗口 + 工具复杂（研究、多源调研）。不该：需要共享同一份上下文（如大多数编码任务）、子任务依赖很密、需要实时协调。

2. 多 Agent 的上下文怎么隔离与传递？

子 agent 用独立上下文窗口，只回传结构化的浓缩结论（1–2K token）；大产物写外部系统，只传轻量引用——原文叫"避免传话游戏（game of telephone）"。这本质上是 [[母题-A5-上下文压缩与记忆]] 的压缩，而且是"天然干净"的那种。

3. 多 Agent 的成本怎么算？

按 token 算：普通对话 1×、单 agent 4×、多 agent 15×。再乘上任务量。而且要注意"effort 分档"——不分档会让简单查询也按复杂配置跑（浪费 24 倍）。

4. 为什么不让模型自己决定派几个子 agent？

原文原话是"Agents struggle to judge appropriate effort for different tasks"。所以把分档规则写进 prompt——这是 Harness 的通用思路：模型判断不了的地方，用显式规则兜住。

5. 多 Agent 的评测和单 Agent 有什么不同？

它要评"交互模式"而不只是单个 agent。因为有涌现行为：改 lead 的 prompt 可能不可预测地改变子 agent 的行为（[[母题-G5-RAG评测与幻觉率]] 的分层归因在这里同样成立，只是层次更多）。

A8计划是模型动态生成且会变的情况下，怎么保证执行不失控草稿 · 待验收单卡 →

计划由模型动态生成、而且会变——那"可靠执行"靠什么保证？为什么"让模型自己反思一下"不够？

面试官问——"Agent 的计划是模型自己定的，它还会中途改，你怎么保证它不跑偏？"

一句话结论：动态计划的问题不是"会变"，是"变了没人知道、也回不去"。 而且跑偏最难的地方在于"它看起来很正常"——还在调工具、还在推进，没有任何信号告诉你它在做的不是原来那件事。所以解法是三件事一起做：① 计划外化——把计划做成版本化的产物（OpenAI 的做法是 checked into the repository，修订产生新版本，偏离变成可见的 diff）；② 把目标变成可验证的信号——"agent 访问不到的东西等于不存在"，把 logs/metrics/traces 暴露给 agent 后，目标从"确保启动快一点"变成"启动在 800ms 内"，验证成本差 10 倍；③ 能确定化的检查就确定化——10 项检查全用模型 Judge（85% 准）只有 19.7% 全对，60% 确定化后是 52.2%（20 项时差 7 倍）。Reflection 不能替代外部 oracle（同一模型重复同一盲点），它的正确位置是生成候选修复，不是验收。最后一条设计很值：约束不写在提示里，而是写成 linter，把修复指令塞进错误信息——只在违反时出现，而且出现得正是时候。

  • 动态计划的问题是**不可见**不是"会变"
  • **跑偏的 agent 看起来很正常**
  • 计划外化成**版本化产物**（checked into repository，偏离 = 可见 diff）
  • 成本 16 KB vs 整个任务作废
  • **"agent 访问不到就等于不存在"**
  • 可观测性暴露给 agent → 目标可验证（10 倍人工差）
  • **能确定化的就确定化**：10 项 19.7% → 52.2%，20 项差 7 倍
  • **custom linter + 错误信息注入修复指令**
  • Reflection 只生成候选不验收
  • 验证优先级：确定性 > 权威状态 > 交叉证据 > 模型 Judge > 人工

主线：动态计划本身不是风险，"不可见的变化"才是。 所以三件事都指向同一个方向：把只存在于模型脑子里的东西，搬到系统能看、能查、能验证的地方——计划变成产物、目标变成指标、约束变成检查。

1. 计划变更是怎么处理的？

计划是版本化产物：修订产生新版本（可 diff）、进度与决策日志一起进版本控制、偏离变成可见的。人不必读全过程，只需要看计划变了没有。

2. Reflection 有什么局限？

同一模型可能重复同一盲点，而且多一次调用增加成本。优先给外部测试 / 工具反馈；Reflection 适合生成候选修复或检查清单，并通过 Eval 验证增益。

3. 怎么保证 Agent 遵守了一堆约束？

别写在提示里，写成 linter / structural test：违规必然被拦住，而且把修复指令写进错误信息（只在违反时出现，出现得正是时候）。而且检查可复用、不依赖模型状态。

4. Agent 的评测和 RAG 的评测有什么不同？

RAG 的归因是三段（没捞到 / 没进上下文 / 生成错）；Agent 的归因层次更多：目标理解 → 计划 → 每一步的工具选择与参数 → 副作用 → 终止判定，而且要评交互模式（[[母题-A7-多Agent拆分与协作]] 的涌现行为）。共同点：都必须能定位到具体哪一段坏了（[[母题-G5-RAG评测与幻觉率]]）。

5. 为什么 RuleArena 用显式 FSM 而不是自由编排？

因为高风险动作需要可控性与可回溯：显式 FSM 让"当前该做哪一步"是可检查的，而不是"模型觉得该做哪一步"。自由编排更灵活，但它的状态在模型脑子里——而本卡的结论正是"脑子里的东西不可检查"。
