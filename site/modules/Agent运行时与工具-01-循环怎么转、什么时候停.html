A1一个 Agent 循环长什么样；凭什么判定它"做完了"，又怎么防它转不停

骨架：五条件与 Workflow 之分 → 循环四步（点明"复杂度放边界组件"）→ 七种预算与"先到先停" → 失控成本算式 → 无进展检测（比调 max_steps 更准） → 八种终止原因与可观测性 → 验证优先级与"反思不能替代 oracle" → 收束到"三个出口"

一句话结论：Agent 的五条件是有目标、能观察、模型能选动作、动作改变环境、根据结果继续或停止——所以"问一次模型返回文本"不是 Agent，固定 DAG 是 Workflow。循环体只有四步（组装上下文 → 模型决策 → 校验并执行工具 → 记录 Step），工程的分量全在出口：正常出口是结果通过验证（而不是模型说 done），异常出口是多种预算 + 无进展检测。预算是七种不是一个——max_steps（防循环）、max_tokens/cost、deadline（防慢）、max_tool_calls、per-tool quota、max_retries（防重试放大）、artifact size；而且它们先到先停，设的时候要算清楚哪个会先生效。为什么必须设：50 步每步 2.5K token 的失控 run，累计输入 3.19M、成本约 $16（平方累计，不是线性）。无进展检测比调小 max_steps 更准——判的是"状态有没有变"，能把浪费降到 1/14。最后，终止原因必须分八类（completed_verified / needs_clarification / waiting_approval / budget_exhausted / tool_unavailable / policy_blocked / cancelled_by_user / unrecoverable_error）——"模型停了"不是工程可用的终止原因。

  • 五条件（动作改变环境 + 根据结果停止）
  • Workflow vs Agent
  • 循环四步
  • 复杂度放可测试的边界组件，不放巨大 Prompt
  • 七种预算 + 先到先停
  • 平方累计的失控成本（50 步 = 3.19M ≈ $16）
  • 无进展检测（状态没变 / 重复同参数调用）
  • 八种终止原因
  • 验证优先级（确定性测试 > 权威状态 > 交叉证据 > 模型 Judge > 人工）
  • 模型自我反思不能替代外部 oracle

先说清什么是 Agent：有目标、能观察、模型能选动作、动作改变环境、根据结果继续或停止——五条同时成立。所以"问一次模型返回文本"不是 Agent；步骤固定的固定 DAG 是 Workflow。

循环体只有四步：组装上下文 → 模型决策 → 校验并执行工具 → 记录 Step。工程的分量全在出口：正常出口是结果通过验证（而不是模型说 done），异常出口是多种预算 + 无进展检测。

预算是七种不是一个：max_steps（防循环）、max_tokens/cost、deadline（防慢）、max_tool_calls、per-tool quota、max_retries（防重试放大）、artifact size；它们先到先停，设的时候要算清楚哪个会先生效。

防止无限循环是六条叠加：多种预算、检测重复状态与重复调用、工具返回明确错误语义、每轮验证进展、连续无进展就触发澄清/降级/转人工、终止原因结构化进 Eval 用来调阈值。

  • 推导链：谁决定下一步 → 动作是否改变环境 → 与 Workflow 分界 → 七种预算先到先停 → 六条防循环手段。
  • 量化：七种预算（步数/token/成本/时间/工具次数/单工具配额/重试次数/产物大小）；max_retries 防的是重试放大。
  • 边界与常见误解："模型说 done 就结束"×（要结果通过验证）；"一个 max_steps 就够了"×（七种先到先停，得算清哪个先到）；终止原因要结构化才进得了 Eval。
A2工具该怎么设计和裁剪；工具多了为什么会选错；MCP 的边界在哪

骨架：先破"包装 API"（给 affordance 的差别）→ consolidation 三组例子 + 收益的两层 → 命名空间 → 响应设计（206 vs 72 + 判据）→ 错误响应要可行动 → 平方放大的成本算式 → 评测指标与"调次数暴露合并机会" → 收束到"工具是界面"

一句话结论：工具不是"能力的暴露面"，是"给模型看的界面"——所以要按 agent 的 affordance 设计，而不是把 API 包一层。第一条原则：别把 API 直接封装——传统软件内存充足可以遍历全量，agent 只能 token by token 读，list_contacts 会逼它用有限上下文做暴力搜索，search_contacts 才是对的。第二条：按工作流做 consolidation（list_users+list_events+create_event → schedule_event；read_logs → search_logs），收益不只是少调几次，更是让中间产物不进上下文。第三条：命名空间（asana_projects_search），而且前缀还是后缀对评测有实质影响、因模型而异。第四条：返回什么取决于"接下来还需不需要它发起调用"——同一份数据详细版 206 token、精简版 72 token，差约 2/3。第五条：错误响应要"可行动"，不是不透明错误码。最后，工具的真实代价会被平方放大：5,000 token 的响应在 40 轮里能被重发 30 次 = 1.5M token ≈ $7.5；Claude Code 因此把工具响应默认限制在 25,000 token。

主线：循环体很短，工程全在出口。 而出口的设计决定了两件事：花多少钱停下来（预算 + 无进展检测），以及停下来之后你知不知道为什么（结构化的终止原因）。

1. Agent State、Context、Memory 有何区别？

State 是运行时结构化事实；Context 是某一次模型调用看到的投影；Memory 是跨步骤 / 会话复用的信息。业务状态仍由数据库权威维护。恢复时从 State 和业务状态重新装配 Context（[[母题-A5-上下文压缩与记忆]]）。

2. 怎么防止 Agent 无限循环？

最大步数 / 时间 / 成本 / 工具次数；检测重复状态和重复调用；工具返回明确错误语义；每轮验证进展；连续无进展触发澄清、降级或人工；终止原因进 Eval。

3. Checkpoint 存什么？

目标、运行状态、当前节点、结构化中间结果、Artifact 引用、剩余预算、版本、已完成副作用与幂等键、待审批动作（[[母题-A4-长任务状态与Checkpoint]]）。

4. Reflection 有什么局限？

同一模型可能重复同一盲点，而且多一次调用增加成本。优先给外部测试 / 工具反馈；Reflection 适合生成候选修复或检查清单，并通过 Eval 验证增益。

5. 什么时候该用 Agent 而不是 Workflow？

当"下一步做什么"无法预先穷举、需要模型看情况决定时。步骤固定就别用 Agent——它带来成本不可预测和行为不可穷举两个代价（[[母题-A7-多Agent拆分与协作]] 会从"多 Agent"的角度再讲一遍这个判据）。

主线：工具的每一个面（描述、参数、返回、错误）都是"给模型看的界面"。 所以设计判据不是"API 长什么样"，是"模型要分几步、中间产物占多少上下文"——能一步做完、中间结果不外露的工具，比功能更全的工具更好。

1. 工具数量多了会怎样？

三种代价：① 每个工具的描述都占上下文（30 个 ≈ 6,000 token/请求，每轮都付，且注意力层面没有折扣）；② 重叠或含糊的工具让 agent 分不清该用哪个；③ 选错的概率上升。手段：consolidation + namespacing + 延迟加载（defer_loading，把少用工具移出缓存前缀）。

2. MCP 解决什么问题，边界在哪？

MCP 是工具接入的标准化协议（把"每个客户端各写一套集成"变成"一次实现、多处复用"）。边界：MCP 只统一了"怎么暴露和调用"，没有统一"该不该暴露"——工具的职责划分、权限边界、返回设计仍然是你的事（[[母题-A6-沙箱权限与可信执行]]）。

3. 工具描述该怎么写？

清晰、具体、有边界。但对新一代模型，给示例反而可能限制探索空间（[[母题-C3-Prompt版本管理与回归]]）——更好的做法是设计接口本身：把 status 做成 pending / in_progress / completed 的枚举，光是列出来就在提示怎么用。

4. 怎么知道该合并哪些工具？

看"工具调用总次数"这个指标：经常被连着调用的工具组合，就是 consolidation 的候选；冗余调用多说明分页/token 参数要调；参数无效的错误多说明描述不清或缺示例。
