五种结构各解决什么问题？ZSet 为什么是跳表 + 哈希表？

Redis 了解吗？它都有哪些主要的数据结构？ ZSet 底层是怎么实现的？为什么用跳表而不用 B+ 树？

一句话结论：Redis 快在三点——数据在内存、命令执行单线程（无锁、无切换）、IO 多路复用；注意 6.0 之后网络 IO 是多线程，只有命令执行仍是单线程。五种基础结构按"要不要唯一 + 要不要顺序"选：String / List / Hash / Set / ZSet；另有 Bitmap、HyperLogLog（估算 UV，有误差）、Geo、Stream 四种扩展。ZSet 底层是"跳表 + 哈希表"——哈希表支撑按成员查分数，跳表支撑按分数取范围与排名；用跳表而不用 B+ 树，是因为 B+ 树的优势（减少磁盘 IO）在内存里用不上，而跳表不需要重平衡、范围查询更自然。

  • 内存（差 5 个数量级）
  • 命令执行单线程 + 网络 IO 多线程
  • 单线程的代价是慢命令卡所有人
  • 选型两问（唯一？有序？）
  • ZSet = 跳表 + 哈希表
  • 跳表的层数随机所以不需重平衡
  • B+ 树为磁盘设计、内存里优势失效
  • HyperLogLog 用误差换空间
  • **每个结构都要挂一个自己的场景**

主线："该用什么结构"由"数据是一份什么形状的内存数据"决定，而不是由"哪个结构更高级"决定。同理，"该用什么索引结构"由"瓶颈是 IO 还是比较"决定——约束变了，答案就变了。

1. Redis 是单线程还是多线程？

命令执行单线程，网络 IO 在 6.0 之后是多线程。 后台任务另有线程/子进程。

2. 单线程为什么还快？

无锁竞争、无上下文切换、单条命令天然原子；加上内存访问快、epoll 一次管很多连接。

3. 单线程有什么代价？

一条慢命令卡住所有人（KEYS *、大 key 的 DEL）。所以有"慢命令禁用清单"和"大 key 治理"。

4. ZSet 为什么用跳表不用 B+ 树？

见 Q5：不是快慢，是约束。

5. HyperLogLog 精确吗？

不精确，标准误差约 0.81%，用它换的是固定的小内存。

6. Redis 能当消息队列吗？

能用 List / Stream 做中小规模；但持久化、分区、重放、生态与 Kafka 差距明显，不能因为"已经用了 Redis"就默认替代（[[母题-R3-缓存一致性与三类事故]]）。
