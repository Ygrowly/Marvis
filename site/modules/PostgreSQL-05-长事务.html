P13MVCC 在 PG 里怎么实现？xmin/xmax 与「更新即新版本」意味着什么草稿 · 待验收单卡 →

MVCC 在 PG 里怎么实现？xmin / xmax 与「更新即新版本」意味着什么？

PG 的 UPDATE 为什么不「改一行」，而是「插一行」？

一句话结论：PG 把每个行版本都留在堆里，用行的 xmin（创建它的事务 ID）和 xmax（删除它的事务 ID）+ 当前快照的事务范围判断可见性——读的时候不改数据、不加锁。所以 UPDATE 实际是「写一个新版本 + 把旧版本的 xmax 标成本事务」。代价是死元组必须靠 VACUUM 回收，而且索引里还留着指向旧元组的条目——这正是表膨胀的根源，也是它和 MySQL「版本链放 undo log、purge 线程自动清理」最大的差别。

  • xmin
  • xmax
  • 版本留在堆里
  • 更新即新版本 + 标记旧版本
  • 可见性由快照决定
  • 死元组
  • 索引也指向死元组
  • HOT 更新

主线：PG 的 MVCC 是「绝不动旧数据」的 MVCC。 收益是读永不阻塞写、写永不阻塞读；代价是空间必须由 VACUUM 回收——这就是「PG 为什么必须懂 VACUUM」的全部理由。

原理分解

一、两种 MVCC：版本放在哪，决定了运维形态

MySQL（InnoDB）PostgreSQL
版本存在哪undo log（版本链在回滚段）堆里（每行一个新版本）
更新怎么做就地改当前行，旧值写进 undo写一个新版本，把旧版本标记为死
回收purge 线程自动、基本无需人工关注VACUUM / autovacuum（可能跟不上）
读的可见性用 ReadView + undo 链回溯用行的 xmin/xmax + 快照判定
需要 undo 日志吗需要不需要（版本本来就在表里）

这张表是全库最重要的一张对照表：「回收是否自动」这一个差异，直接决定了 PG 有一整套 MySQL 没有的运维课题（膨胀、VACUUM 调参、事务 ID 回卷、idle in transaction 监控）。

二、xmin / xmax 怎么工作

每一行版本头部有两个关键字段：

字段含义
xmin创建这个版本的事务 ID
xmax删除/更新掉这个版本的事务 ID（为空表示还活着）

可见性判定的简化版：

读取时，用一个「快照」——它记录了「哪些事务算是已提交、哪些还没」
某个版本对当前快照可见，需要：
   xmin 的事务已提交且「在快照之前」         → 这个版本已经被创建出来了
   且 xmax 为空，或 xmax 的事务「在快照之后 / 未提交」  → 还没被真正删掉

所以「读」完全不需要动数据、也不需要加锁——它只是拿两个事务 ID 和一份快照做比较。这就是「读永不阻塞写」的实现方式。

三、更新即新版本：一句 UPDATE 背后发生了什么

UPDATE tasks SET status = 'DONE' WHERE id = 42;

实际动作：

1. 在堆里写一个新版本（xmin = 当前事务，新值）； 2. 把旧版本的 xmax 设为当前事务（标记「被它删掉了」）——旧版本仍然物理存在； 3. 更新所有索引：索引需要指向新版本的位置（ctid 变了）； 4. 事务提交后：旧版本对新快照不可见，但对还在用旧快照的事务（长事务！）仍然可见。

第 4 步是关键：旧版本什么时候能被删，取决于「还有没有人在用能看到它的快照」——这就是 P14 的全部机理。

四、代价：死元组 + 索引也指向它

两个必须记住的后果：

① 堆会变"胖"：更新 N 次就有 N 个版本（只有一个活着）。表文件不会自动变小，空间只能靠 VACUUM 标记为「可复用」——注意：可复用 ≠ 文件变小（见 P15）。

② 索引也要清理：B-tree 索引项指向 ctid，旧版本的条目会变成指向死元组的"死索引项"——VACUUM 必须同时清理堆和索引。所以「索引多 → VACUUM 更累」这件事在 PG 里是机制性的，不是经验之谈（这也是 P4 里「PG 的索引第三项代价是 VACUUM 压力」的由来）。

一个可以直接说出来的量化直觉：一张更新频繁的表，实际占用的空间可以是"有效数据"的好几倍——「表大小」和「数据量」在 PG 里是两个概念。

五、HOT 更新：一个重要的写入优化

HOT（Heap-Only Tuple）更新：如果

1. 更新的列不属于任何索引，且 2. 新版本能放进同一个数据页里

那么 PG 不需要更新任何索引——新版本通过页内的指针链和旧版本连起来。

为什么重要：它把「一次更新要改所有索引」降级成「只写堆」，是 PG 在高频更新表上最有效的内置优化。实践推论：不要把频繁更新的列放进索引（比如状态、计数器、updated_at 如果不需要用来查询就别索引它）——这条是从机制推出来的设计规则，比背「索引不要建太多」有力得多。

P14长事务为什么会造成表膨胀？机制是什么草稿 · 待验收单卡 →

长事务为什么会造成表膨胀？机制是什么？

一个开了两小时、只做 SELECT、一行都没改过的事务，会让表变大吗？

一句话结论：会。 膨胀的机制是「旧的死元组不能被回收」：VACUUM 只能回收「对所有活跃快照都不可见」的死元组——长事务持有的快照还需要看到旧版本，于是 VACUUM 不敢删，死元组一直堆积 → 表页越来越多 → 扫描同样的行要读更多页、回表更贵、缓存命中率下降。所以长事务的危害不是「持锁久」，而是它按住了一个旧快照，让空间回收停摆。

  • 活跃快照按住回收
  • 回收的判据是「对所有人不可见」
  • 死元组积压 → 表与索引一起膨胀
  • `idle in transaction`
  • **只读长事务同样有害**
  • 监控最老事务

主线：回收的判据是「对所有人都不可见」，不是「对当前事务不可见」。 换句话说——表能不能瘦，由「最老的那个活跃快照」决定，不由「现在有多少死数据」决定。

原理分解

一、机制：回收边界由最老快照决定

结合 P13 的版本模型：

一个行版本被删/被更新后 → 变成「死元组」，但它还物理存在
VACUUM 判断「这个死元组能不能清掉」的唯一问题：
   还有没有活跃事务能看到它？
     有 → 不能删（删了那个事务就读不到了）
     没有 → 可以标记为可复用

所以 VACUUM 的清理边界 = 所有活跃快照里最老的那一个。

一个两小时前开始的事务 → 它的快照就是两小时前 → 这两小时内产生的所有死元组都不能回收。两小时的写入量全部变成"不能动的垃圾"。

这就是「长事务拖系统下水」的真实路径——不是它占了多少 CPU，而是它让整张表的回收停摆了两小时。

二、为什么「只读」也有害（最反直觉的一点）

因为回收看的是「快照」，不是「这个事务做了什么」。

  • 一个只读事务不做任何修改，看上去"人畜无害"；
  • 但它持有快照，而快照决定了回收边界；
  • 所以只要它开着，膨胀就在积累。

三种常见的「无害长事务」：

形态为什么出现危害
idle in transaction（开了事务但没提交、连接挂着）应用逻辑里 BEGIN 之后做了网络请求 / 等用户输入 / 调了慢接口最坏的形态：不干活但一直按住快照
长只读事务（报表、导出、全量扫描）一次性拉大量数据分析按快照 + 占备库回放
批处理事务（几千行一提交）「为了原子性把一批包在一个事务里」事务内的写入量本身就是膨胀源

三、膨胀的连锁代价

膨胀不只是"占空间"，它会污染整条查询链路：

表页变多
  → 同样的行数分布在更多页上
  → Seq Scan 要读更多页（同样的数据，更多 IO）
  → 索引查询的回表随机 IO 次数上升（P2：ctid 指向更多稀疏页）
  → 缓存命中率下降（shared_buffers 装不下有用的数据）
  → 于是查询整体变慢 → 更慢的查询又延长事务 → 环路加剧

这个环路值得记住：膨胀 → 查询变慢 → 事务变长 → 回收继续停摆 → 膨胀更严重。这就是为什么「PG 表膨胀」经常是性能事故的起点，而不是结果。

四、怎么发现（要能说出监控哪一个）

看什么用途
pg_stat_activity 里最老的活动事务 / 其 xmin（或 backend_xmin）回收边界——这是最直接的指标
「运行时间最长的事务」+「处于 idle in transaction 的连接」找出真正的肇事者
表的死元组数量 / 上次 VACUUM 时间（表级统计）判断哪张表在积累死元组
表与索引的实际大小 vs 有效数据量判断膨胀程度

面试里能说出「我盯的是最老事务的 xmin，也就是回收边界」这一句，就说明你真的理解了机制——因为大部分人只会说「看有没有长事务」。

五、怎么防（按有效性排序）

1. 设超时：idle_in_transaction_session_timeout（这条最有效，直接干掉"挂着不干活"的连接）、statement_timeout； 2. 拆批：大批处理拆成小事务分批提交（不要为了"原子性"把几万行包进一个事务）； 3. 别在事务里做外部 IO：网络调用、调外部服务、等人工确认——事务边界应该只包住数据库操作； 4. 调 autovacuum：对大表/高更新表单独设更激进的触发阈值（pg_stat_bgwriter 与表级统计是依据）； 5. 设计层：把「高频更新的列」排除出索引（利用 HOT，见 P13）、用状态表 / 追加式日志代替就地更新。

第 3 条是最容易被忽略的工程纪律：「事务里不调外部服务」和「事务里等用户输入」是同一类错误——它们都把「数据库锁与快照的持有时间」绑到了「外部系统的响应时间」上。

P15VACUUM vs VACUUM FULL；autovacuum 怎么调；事务 ID 回卷是什么草稿 · 待验收单卡 →

VACUUM 和 VACUUM FULL 有什么区别？autovacuum 怎么调？事务 ID 回卷是什么？

为什么 PG 会「因为太久没清理而拒绝服务」？这是设计缺陷吗？

一句话结论：VACUUM 是「标记可复用」——在线、拿轻锁、不缩小文件，只是把死元组占的空间留给表自己复用；VACUUM FULL 是「重写整表」——能真正缩小文件，但要排他锁、等量额外空间，期间业务不可用。事务 ID 是 32 位、循环使用，所以必须靠「冻结（freeze）」告诉未来的自己「这些行很老、一定可见」；清理长期跟不上就没法安全冻结，PG 会先告警、最后拒绝新事务以避免把老数据误判成未来才可见——这是「宁可停止服务，也不出错数据」的取舍。

  • 标记复用 vs 重写整表
  • autovacuum 与触发阈值
  • freeze（冻结）
  • 32 位事务 ID 回卷
  • 告警 → 只读维护模式
  • `pg_repack` 在线重建
  • 膨胀已发生的三步处理

主线：VACUUM 解决「空间能不能复用」，VACUUM FULL / pg_repack 解决「文件要不要变小」。 两件事，回答时混为一谈是最常见的失分点——因为绝大多数人以为「跑一次 VACUUM 表就变小了」。

原理分解

一、VACUUM 做的三件事

1. 回收死元组占用的空间 → 标记为「可复用」（注意：不是还给操作系统）； 2. 清理索引里指向死元组的条目（P13 里那条：索引也要清）； 3. 更新统计信息（VACUUM ANALYZE）并推进冻结（下面讲）。

「可复用」的含义要讲准：空间留在表文件里，后续插入/更新可以填进去。所以表文件大小不会下降，只是「不再继续长」。「跑完 VACUUM 表还是 10GB」是正常的。 很多人的困惑就来自这一步。

二、VACUUM vs VACUUM FULL

VACUUMVACUUM FULL
做什么标记空间可复用重写整张表（新文件 + 拷贝有效行）
锁轻锁，业务基本不受影响排他锁，期间该表不可读写
空间不缩小文件真正缩小
额外空间不需要需要等量额外空间（新表 + 旧表同时存在）
适用日常、autovacuum 自动做万不得已（大表上等于一次业务中断）

所以「表膨胀了要一次 VACUUM FULL」在生产上通常不是一个可接受的方案——尤其大表。生产更常用 pg_repack：它用类似 CREATE INDEX CONCURRENTLY 的思路做在线重建，不长时间持锁，代价是需要额外空间、过程更复杂。

判据：小表或可停机窗口 → VACUUM FULL；大表在线 → pg_repack；根本解法 → 治因（P14）。

三、autovacuum 为什么经常跟不上

autovacuum 是按比例触发的（默认「变更行数超过表的约 20% + 固定阈值」）。两类问题：

问题说明
大表触发太晚比例阈值对大表意味着「要变更多少行」才触发——偏偏大表最经不起堆积。所以大表需要单独调低阈值。
被长事务/复制槽顶住有长事务时，回收边界推不动，autovacuum 跑上去也清不掉东西（P14）；有离线复制槽时 WAL 不回收（P12）。这两个是"看起来在跑但没效果"的典型。

所以「调 autovacuum」不是万能的：它先要能被放开回收边界。判断顺序应该是「有没有东西按住边界」→ 再「阈值够不够激进」。

四、事务 ID 回卷：为什么 PG 宁肯拒绝服务

机制：

  • 事务 ID 是 32 位、循环使用（所以有回卷的概念）；
  • 一个行版本靠 xmin/xmax 判定可见性，如果 ID 用完一圈回来，同一个 ID 既可能表示「很久以前的已提交」又可能表示「很新的事务」，比较就会彻底错乱——老数据可能被判定成"未来才可见"，于是凭空消失。
  • 解决办法是冻结（freeze）：把足够老的行标记为「无论 ID 怎么变，它都是可见的」。冻结必须在 ID 循环到它之前完成。
  • 冻结需要 VACUUM 推进到那个位置 —— 所以清理长期跟不上（长事务 / 停止的消费者）→ 冻结推不动 → 回卷风险上升。

PG 的应对是渐进升级的：

① 远未到期：正常
② 接近阈值：日志/监控告警
③ 非常接近：强制 autovacuum、可能拒绝新事务
④ 超过安全线：进入只允许维护操作的状态（业务写不进来）

为什么这样设计：它宁可付出「短时间不可用」的代价，也不接受「静默丢数据/读错数据」。 这个取舍本身是 PG 的一条设计哲学（和 P9 的「宁可报错让你重试」是同一种态度）——能把这个共性说出来，说明你理解了 PG 的价值观，而不只是记住了一个现象。

五、膨胀已经发生了：三步处理（顺序不能反）

① 先治因：干掉长事务 / 调 autovacuum / 清掉不活跃复制槽
      （否则重建完还会再膨胀）
② 再回收空间：优先 pg_repack；小表或可停机窗口才用 VACUUM FULL
      （VACUUM FULL 要排他锁 + 等量额外空间）
③ 再做结构改造：分区 + 丢弃旧分区，把「持续 DELETE」变成「周期 DROP」
      （P16 —— 这才是不再反复膨胀的解法）

第 ③ 步是真正意义上的解决：「DELETE 历史数据」这个动作本身就是膨胀源（删了要等回收），分区的 DROP 分区几乎瞬时且不产生死元组。所以「有持续清理需求的大表」应该直接设计成分区表——这是从膨胀问题反推出的表设计结论。
