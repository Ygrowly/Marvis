P13MVCC 在 PG 里怎么实现？xmin/xmax 与「更新即新版本」意味着什么草稿 · 待验收单卡 →

PG 的 UPDATE 为什么不「改一行」，而是「插一行」？

一句话结论：PG 把每个行版本都留在堆里，用行的 xmin（创建它的事务 ID）和 xmax（删除它的事务 ID）+ 当前快照的事务范围判断可见性——读的时候不改数据、不加锁。所以 UPDATE 实际是「写一个新版本 + 把旧版本的 xmax 标成本事务」。代价是死元组必须靠 VACUUM 回收，而且索引里还留着指向旧元组的条目——这正是表膨胀的根源，也是它和 MySQL「版本链放 undo log、purge 线程自动清理」最大的差别。

  • xmin（插入事务）
  • xmax（删除事务，非零不等于不可见）
  • ctid 会变，不能当行标识
  • 版本留在堆里
  • 更新即新版本 + 标记旧版本
  • 可见性由快照决定
  • 死元组
  • 索引也指向死元组
  • 普通 VACUUM 不还空间给操作系统
  • HOT 更新

主线：PG 的 MVCC 是「绝不动旧数据」的 MVCC。 收益是读永不阻塞写、写永不阻塞读（官方原话）；代价是空间必须由 VACUUM 回收——这就是「PG 为什么必须懂 VACUUM」的全部理由。

1. 既然旧版本还在表里，那读的时候怎么知道该读哪个？

按快照判定 xmin/xmax：同一个事务读同一个快照，看到的就是同一批版本。这也解释了 P8 那个反直觉现象——RC 下每条语句换一次快照，所以能看到不同版本；RR 下共用一个快照，所以结果一致。 P8、P13 是同一件事的两个面。

2. xmin/xmax 是 32 位事务 ID，会不会用完？

会，这就是事务 ID 回卷（[[母题-P15-VACUUM与事务ID回卷]]）。32 位 ID 循环使用，所以必须靠【冻结】标记"这行很老、一定可见"；清理长期跟不上，就可能出现"老数据被误判成未来才可见"的灾难。 PG 的应对是：先告警，最后拒绝新事务，强制进入维护模式——「宁可停机也不出错数据」这个取舍本身就是很好的面试谈资。 而且官方的说法很硬：一张表最多可以 20 亿事务不被 VACUUM，超过就【可能造成数据丢失】。

3. PG 的读会不会被写阻塞？

不会（读不加锁）；但 ALTER TABLE 这类 DDL 会拿表锁（[[母题-P4-索引代价与在线建索引]]），那会阻塞。

4. 为什么 PG 的表「更新一次就变大一次」？

没有原地更新，旧版本还在；空间要等 VACUUM。而且「VACUUM 过」不等于「变小了」——它只是把空间标记为可复用。

5. PG 有 SELECT ... FOR UPDATE 就说明读要加锁吗？

不，那是显式加锁（[[母题-P10-无间隙锁与锁变体]]），默认的读不加任何锁。

P14长事务为什么会造成表膨胀？机制是什么草稿 · 待验收单卡 →

一个两小时前开的只读事务，什么都没改，为什么会把线上写卡死？

一句话结论：VACUUM 只能回收「所有活跃快照都看不见」的死元组，所以回收边界 = 最老的那个活跃快照。一个长事务（包括只读的）会把回收边界钉在过去，这两小时内产生的所有死元组都不能清——表就这么胖起来的。膨胀又会让扫描读更多页、缓存命中率下降，于是查询变慢、事务更长、回收更停摆——这是一个正反馈环，而且 PG 表膨胀经常是性能事故的【起点】而不是结果。

  • 回收边界 = 最老快照
  • 只读事务也有害
  • idle in transaction
  • 死元组与索引条目一起堆
  • 膨胀 → 扫描变多 → 缓存命中率降
  • autovacuum_vacuum_scale_factor 0.2
  • autovacuum_max_workers 只有 3
  • pg_stat_activity 看 backend_xmin

主线：VACUUM 的清理边界由「最老快照」决定，而不是由「谁改了什么」决定。

1. 为什么「只读」也有害？

因为回收看的是快照，不是"这个事务做了什么"。 只读事务不做修改，但它持有快照，而快照决定了回收边界。 所以只要它开着，膨胀就在积累。 这条最反直觉，也最能区分"背过"和"懂了"。

2. idle in transaction 为什么是头号来源？

因为它不消耗 CPU、不占锁、不报错、监控上看起来正常，但持续按住回收边界。 它的病因几乎总是同一个：应用在 BEGIN 之后做了网络请求、调了外部接口、或者等用户输入。 idle_in_transaction_session_timeout 就是为它准备的。

3. 膨胀了怎么办？

三步，顺序不能反：① 先切断长事务（否则做什么都白做）；② 需要在线重建时用 pg_repack，而不是 VACUUM FULL（后者要排他锁 + 等量磁盘空间，[[母题-P15-VACUUM与事务ID回卷]]）；③ 最后才调 autovacuum 的阈值。

4. 备库上的长查询会造成主库膨胀吗？

会。hot_standby_feedback = on 时，备库会把"我还在读这些行"反馈给主库，主库就不清理它们——官方明确警告这「会造成主库的表膨胀」（[[母题-P12-流复制与逻辑复制]]）。所以"在备库上跑报表"这件事是有成本的，而且成本记在主库头上。

5. autovacuum_max_workers 调大有用吗？

只影响并发条数。边界被按住时，多几个 worker 也清不掉；而且它们会争抢 IO、互相拖慢。它是一个"清理能力"参数，不是一个"清理意愿"参数。

正本：wiki/topics/PostgreSQL/母题-P14-长事务与表膨胀.md

P15VACUUM vs VACUUM FULL；autovacuum 怎么调；事务 ID 回卷是什么草稿 · 待验收单卡 →

VACUUM 跑完，表还是 10 GB。正常吗？为什么 PG 会宁可拒绝服务也不让事务 ID 用完？

一句话结论：VACUUM 做三件事——把死元组的空间标记为「可复用」（不是还给操作系统）、清理索引里指向死元组的条目、推进冻结。所以「跑完 VACUUM 表还是 10 GB」完全正常，它只是不再继续长。要真正缩小只能 VACUUM FULL / CLUSTER（排他锁 + 等量磁盘空间）或 pg_repack（在线重建）。而事务 ID 是 32 位、循环使用，所以必须在 ID 绕回来之前把老行「冻结」成"永远可见"——清理长期跟不上（长事务、离线复制槽）→ 冻不住 → 逼近回卷红线。PG 的应对是渐进升级，最后宁可拒绝新事务——「宁可停机也不出错数据」。

  • 标记可复用 ≠ 还空间
  • 清理索引条目
  • 推进冻结
  • VACUUM FULL 要排他锁
  • pg_repack
  • 32 位事务 ID 循环
  • 冻结阶梯：5000 万 → 1.5 亿 → 2 亿
  • 激进 VACUUM
  • 「20 亿事务不被 VACUUM 就可能丢数据」
  • 渐进升级与拒绝服务

主线：「回收」要拆成两个动作：把空间标记为可复用（普通 VACUUM）≠ 把空间还给操作系统（VACUUM FULL）。

1. 为什么 VACUUM FULL 不能天天跑？

它要排他锁（业务中断）、要等量额外磁盘、还要产生大量 WAL。小表可以，大表上等于一次业务中断。 大表在线重建的正确工具是 pg_repack。

2. 「冻结」这个词容易误解成什么？

它不是"锁住"，是【改写行头上的事务 ID 为"永远可见"的标记】。而且它要付出一次页写入 + WAL——所以太早冻是浪费（官方原话：冻结一个很快又会被修改的行是浪费时间）。

3. 为什么 autovacuum_freeze_max_age 默认只有 2 亿，不设大一点？

官方给了理由：VACUUM 还允许从 pg_xact 子目录里移除旧文件，这就是为什么默认是一个相对低的值。 官方还给了另一半建议：如果 pg_xact / pg_commit_ts 相对总库容很小，可以调到允许的最大值；否则按你愿意为它们付出多少空间来定。

4. 关了 autovacuum 会怎样？

常规清理没了，但【防回卷那一路照样会启动】（官方原话）。所以"关掉 autovacuum"只是把问题从"定期小清理"变成"突然一次激进扫描 + 业务被拒绝"——更糟。

5. 怎么监控回卷风险？

看 age(relfrozenxid)（每张表）和 age(datfrozenxid)（整个库），设多级告警（比如 60% / 80% 各一档）。同时盯 pg_stat_activity 里最老的 backend_xmin——那是"倒计时有没有被按住"的直接指针（[[母题-P14-长事务与表膨胀]]）。

正本：wiki/topics/PostgreSQL/母题-P15-VACUUM与事务ID回卷.md
