A3工具调用失败、超时、重复投递时怎么保证不出错（幂等与副作用）草稿 · 待验收单卡 →

失败之后重试是本能——但"重试一次"和"多扣一次款"之间的距离，靠什么堵住？

面试官问——"工具调用超时了怎么办？如果重试，怎么保证不会重复扣款、重复建单？"

一句话结论：幂等不是"让操作不重复执行"（做不到，网络就是会重发），是"让重复执行不产生第二次效果"。 核心是幂等键必须用业务身份——RuleArena 的真实设计是 UNIQUE(run_id, action_type, idempotency_key)；用 ToolCallID 当键会永远失效，因为重试会产生新的调用 ID，唯一约束认为那是新记录。第二件事是重试分类：可重试（网络抖动、限流、死锁回滚）、不可重试（约束冲突、参数校验、权限拒绝——确定性失败）、不确定（超时、连接中断）。第三件事：不确定状态必须先查权威状态，不要赌——P(已执行) 50%、事故代价 100 单位时，直接重试的期望损失 50 单位 vs 查询成本 1 单位，差 50 倍。第四：重试要分层——三层各重试 3 次 = 最坏 27 倍放大，raw 里的真实事故就是"队列积压时扩副本反而更糟"。最后，Resume / Replay / Retry / Fork 四个操作对副作用的处理完全不同——Replay 默认不重做真实副作用，否则就是在重放事故。

  • 副作用三分类（只读 / 幂等写 / 非幂等写）
  • 幂等键 = 业务身份（run_id + action_type + 业务键），不能用 ToolCallID
  • 重试放大 3×3×3 = 27
  • 重试三件套（可重试分类 + 退避抖动 + 上限）
  • 超时 ≠ 失败，先查权威状态
  • 期望损失 50 vs 1
  • checkpoint 前记 intent、后记结果
  • 应用层幂等是优化，数据库约束才是正确性
  • Resume · Replay · Retry · Fork 四分工
  • Replay 不重做副作用

主线：幂等的实现位置决定了它的可靠性：应用层是优化，数据库约束才是正确性。 应用层的"先查再写"在并发下有窗口、在崩溃后会失效；唯一约束是唯一一个"无论如何都拦得住"的位置（[[母题-P19-唯一约束与UPSERT]]）。

1. 中断恢复时如何避免重复扣款 / 建单？

副作用前记录 intent 和业务幂等键；调用端和服务端共同支持幂等；超时不确定时先按业务键查询状态；结果落库后 checkpoint；Resume 跳过已完成动作。必要时补偿或人工。

2. 哪些错误可以重试，哪些不能？

可重试：网络抖动、限流、下游 5xx、死锁回滚（40001）。不可重试：参数校验失败、权限拒绝、约束冲突（确定性失败，重试也没用）。不确定：超时、连接中断——先查权威状态。

3. 幂等键怎么设计？

用业务身份：run_id + action_type + 业务键。判据是"同一个业务意图重试时这个键会不会变"。不能用 ToolCallID、时间戳、随机 UUID（重试都会变）。

4. 为什么"应用层判断是否已执行"不够？

两个漏洞：① 并发下有窗口（两个请求同时查到"没执行"）；② 崩溃后失效（应用层的记录可能比业务写入更晚落盘）。数据库唯一约束是唯一"无论如何都拦得住"的位置。

5. Replay 和 Resume 有什么区别？

Resume 要把事做完（该做的副作用要真做，且要先查状态）；Replay 要复现轨迹（默认用记录结果或沙盒，不重做真实副作用）。混用会把调试变成事故重放。

A4长任务中断之后怎么接着跑；checkpoint 存什么、什么时候存草稿 · 待验收单卡 →

一个跑了几十步、做过若干写操作的长任务挂了——凭什么能安全地接着跑，而不是从头再来？

面试官问——"你们的长任务跑到一半挂了怎么办？checkpoint 里存什么？"

一句话结论：长任务的状态必须分层——Thread / Run / Step / Branch / Checkpoint / Artifact / Event 七类实体；只存聊天历史恢复不了，因为里面没有"哪些写操作真的发生了"（原始素材点名的头号反例）。Step 级记录必须带三组字段：版本（model / prompt / tool，否则 Replay 不出来）、Artifact 引用（否则大产物塞满状态表）、幂等键（否则不知道做过没有）。checkpoint 的核心是"记两次"：副作用前记 intent、后记 result——这两次之间夹着的"不确定窗口"，正是恢复时必须先查权威状态的原因。持久化分两层：Checkpointer 管单 thread 短期状态、Store 管跨 thread 长期记忆（LangGraph 的划分），混在一起会让快照变重、失效判断变复杂。成本上：50 步每步都记是 2.5 MB/run、每天 25 GB 量级，所以时机按"业务意义"选；而收益远大于成本——50 步任务在第 45 步崩溃时，有 checkpoint 重做 5 步 vs 无 checkpoint 重做 45 步，差约 69 倍（因为历史重发是平方累计的）。

  • 七类实体（Thread / Run / Step / Branch / Checkpoint / Artifact / Event）
  • 只存聊天记录 = 头号反例
  • Step 记录三组必需字段（版本 · Artifact 引用 · 幂等键）
  • checkpoint 记两次：前 intent 后 result
  • 不确定窗口
  • 恢复协议六步（读 → 校验版本 → 查权威状态 → 判断副作用 → 重建最小 Context → 从安全节点恢复）
  • failed vs unknown
  • Checkpointer（单 thread）vs Store（跨 thread）
  • 存储 2.5 MB
  • run、25 GB
  • 天
  • 重做成本差 69 倍（平方累计）
  • Context 压缩后必须 checkpoint

主线：能恢复的关键不是"存得频繁"，是"存得位置对"。 checkpoint 要卡在不确定窗口的两侧——而恢复的第一步永远是去问"事实"（业务权威状态），而不是相信"意图"（checkpoint）。

1. Checkpoint 存什么？

目标、运行状态、当前节点、结构化中间结果、Artifact 引用、剩余预算、版本、已完成副作用与幂等键、待审批动作。大结果存外部，敏感信息按权限治理。

2. 什么时间做 checkpoint？

进出业务节点、副作用前后、人工中断前、大型子任务完成后、Context 压缩或分支合并后。纯只读的中间步骤不必记（重做代价低，而存储成本高）。

3. Resume / Replay / Retry / Fork 有什么区别？

见 [[母题-A3-失败恢复与幂等]]：Resume 要把事做完、Replay 只复现轨迹（不重做副作用）、Retry 仅对可重试错误且有幂等保障、Fork 继承只读事实但不继承未批准写权限。

4. 为什么恢复时要"重建最小 Context"而不是"恢复原 Context"？

上下文是视图不是状态。恢复时按当前状态重新装配，才能避免把过期信息和已经解决的中间产物带回来（[[母题-C1-上下文组装与窗口预算]]）。

5. 框架（LangGraph 之类）能替我解决这些吗？

部分能：它提供 checkpointer / store / interrupt 这些机制。但框架不会替你决定：业务权威状态在哪、幂等键怎么设计、什么算"有业务意义的节点"、以及 Eval 的定义（study/04 的原话："框架不会替你决定业务权威状态、权限、幂等键和 Eval 定义"）。

A5Agent 的上下文满了怎么办；记忆该存什么、什么时候该清草稿 · 待验收单卡 →

Agent 的上下文满了要压缩、跨会话要记东西——但"压缩什么、记什么"的判据是什么？为什么记忆不是越多越好？

面试官问——"Agent 跑久了上下文满了怎么办？记忆该存什么？"

一句话结论：记忆要分三层，判据是权威性不是容量——运行状态（Checkpointer，单 thread、短期、自动写入）→ 长期记忆（Store，跨 thread、需治理、有写入门槛）→ 业务权威状态（最高权威，任何恢复动作都要先查它）。混在一起的后果很具体：拿模型自己总结的"已执行"当成工具真的执行成功了。 压缩在 Agent 里比对话里多一条判据：除了看窗口，还要看当前处在哪个业务节点——工具调用序列中间压缩可能丢掉"这一步还没做完"，副作用之后压缩才安全；而且压缩点要和 checkpoint 点对齐，压缩后必须 checkpoint。收益能算：50 步每 20 步压一次，累计输入从 3.19M 降到 1.49M（约一半），而且任务越长省得越多。摘要必须留三类指针：已完成副作用 + 幂等键、证据 ID / Artifact 引用、未决问题与剩余预算——多留 200 token 只要 $0.001，丢掉副作用记录的代价是事故。长期记忆要有写入门槛（跨任务稳定 + 已验证 + 可治理），否则会以 2,000 倍量级累积噪声，让"回忆"退化成低质量检索。

  • 三层记忆（运行状态 / 长期记忆 / 业务权威）
  • 权威性不同，不是容量不同
  • Checkpointer 单 thread vs Store 跨 thread
  • "agent 访问不到就等于不存在"
  • 压缩点与业务节点对齐 + 与 checkpoint 点对齐
  • 50 步压缩降到 47%
  • 摘要三类指针（副作用+幂等键 · 证据ID · 未决与预算）
  • 200 token = $0.001 vs 一次重复扣款
  • 写入门槛（2,000 倍差）
  • 记忆三失效（过期 · 污染 · 过载）
  • 记忆必备元数据（来源·作用域·置信度·TTL·删除）
  • 压缩后必须 checkpoint

主线：记忆的核心问题是"权威性"，不是"容量"。 分不清"我记住的"和"事情本来的样子"，压缩会丢掉恢复所需的指针，记忆会把模型自己的猜测固化成事实——两者都会变成事故来源。

1. Agent State、Context、Memory 有何区别？

State 是运行时结构化事实；Context 是某一次模型调用看到的投影；Memory 是跨步骤 / 会话复用的信息。业务状态仍由数据库权威维护。恢复时从 State 和业务状态重新装配 Context。

2. Memory 应该存什么？

只存跨任务稳定、对未来有用、经过授权、能治理的信息。临时推理、模型猜测、敏感数据不自动写入。每条有来源、主体、作用域、置信度、更新时间、TTL 和删除机制。

3. 怎么防止记忆污染？

两道：写入门槛（只写验证过的）+ 条目自带来源与置信度（这样模型读到它时知道这是"推断"还是"事实"）。最危险的是"模型推断写进去后，下一轮就看不到推断标记了"。

4. 压缩和 checkpoint 什么关系？

同一个动作的两面：一个改上下文、一个存状态。压缩后必须 checkpoint，否则压缩后崩溃又回到压缩前，等于白压一次。

5. 长文档场景怎么保证 grounding？

对超过 20k token 的文档，先要求逐字摘出相关原文（找不到就明说"没找到"），再基于摘录作答——这样引用在生成时就产生了，而且摘要里天然带着可回溯的指针（[[母题-G4-引用绑定与证据可追溯]]）。
