N1一次请求从 URL 到响应走完了什么；502 / 503 / 504 各是哪一层出的问题

骨架：链路分几段 → 每段做什么、失败长什么样（DNS 无状态码 / TCP 连接超时或被拒 / HTTP 4xx5xx）→ 无状态与长连接是两件事 → 连接复用省的是延迟（算一次 175ms）→ 池子大小用 L = λW → 5xx 三个码的准确语义与排查起点 → 超时嵌套由内向外递减 → HTTP/2 的价值在减少连接数

一句话结论：一次请求穿过 DNS → TCP → HTTP → 网关 → 应用 → 上游 这条链路，每一段失败的样子都不同。4xx 是调用方的问题，5xx 是服务端的问题；502 是网关收到上游的无效响应（答非所问），504 是网关等上游超时（根本没答），503 是应用自己承认不行。连接复用（Keep-Alive / 连接池）首先省的是握手延迟（跨机房约 175ms，是一次简单查询的 8 倍以上）；池子需求 = 到达速率 × 单次耗时，所以池子满了要先怀疑上游变慢。

  • 链路六段
  • 4xx 是调用方、5xx 是服务端
  • TCP 三次是因为双向都要确认
  • 无状态 ≠ 短连接
  • 握手成本 ≈ 1.5 RTT + 2 RTT
  • L = λW
  • 池子满先查上游时延
  • 502 答非所问、504 根本没答、503 自己承认
  • 超时嵌套要由内向外递减
  • HTTP2 多路复用

一次请求穿过 DNS → TCP → TLS → HTTP → 网关 → 应用 → 上游 这条链路，每一段失败的样子都不同——这才是这条链路要记的东西，而不是背顺序。

分工：DNS 把域名换成 IP；TCP 建连接（三次握手）；TLS 协商密钥；HTTP 发请求（可能复用已有连接）；网关/负载均衡转发；应用处理（可能查 DB、调上游）；响应沿原路返回。

失败的样子：4xx 是调用方的问题，5xx 是服务端的问题；502 是网关收到上游的无效响应（上游答了但答得不对，指向上游进程状态），504 是网关等上游超时（上游压根没答，指向上游耗时），503 是应用自己承认不行（主动拒绝/过载保护/无可用实例，指向容量与自我保护）。

连接复用（Keep-Alive / 连接池）首先省的是握手延迟（跨机房约 175 ms，是一次简单查询的 8 倍以上）；池子需求 = 到达速率 × 单次耗时（L = λW），所以池子满了要先怀疑上游变慢，调大池子只是把压力往后传。超时要分层递减（客户端 > 网关 > 应用 > 上游），只设一层就分不清谁先放弃；重试要配退避与上限，否则网关重试会放大故障。

分层要点追问深挖时用

  • 结论：链路每一段失败的样子不同；502/504/503 分别指向状态、耗时、容量。
  • 推导链：分段 → 各段失败语义 → 连接复用省握手 → 池子需求 = λW → 分层超时让最内层先触发。
  • 量化：跨机房 TCP+TLS 握手约 175 ms，是一次简单查询的 8 倍以上；L = λW。
  • 边界与常见误解：HTTP 无状态不等于没有会话（状态放 Cookie/Token）；HTTP/2 解决了应用层队头阻塞，TCP 层的还在（这是 HTTP/3 换 QUIC 的动机）。

主线："报错了"不是结论，"哪一层报错"才是线索。 请求穿过的是一条分层链路，每一层有不同的失败表征（有的压根没有状态码，有的变成 4xx，有的变成特定 5xx）；定位问题就是把这层分清楚，而不是先猜原因。

1. 502 和 504 的区别，一句话说清？

502 是上游答了但答得不对；504 是上游压根没答（等到超时）。 一个指向"上游进程状态"，一个指向"上游耗时"。

2. 连接池被打满，先做什么？

先看上游时延（L = λW：W 变大直接推高需求）。调大池子只是把压力往后传。

3. 超时为什么不能只设一层？

只有一层就分不清谁先放弃。分层递减让最内层先触发，日志里能直接读出是哪一层。

4. HTTP 无状态，那 Session 是怎么实现的？

无状态意味着状态要放到别处：Cookie 带 Session ID、或 Token 自带信息（JWT）。这跟"连接能不能复用"是两件事。

5. 为什么长任务进度推送不该用普通请求？

普通请求是"一问一答"，长任务要"持续告诉进度"，需要推送模型（[[母题-N2-SSE与推送模型]]）。

分工：DNS 把域名换成 IP；TCP 建连接（三次握手）；TLS 协商密钥；HTTP 发请求（可能复用已有连接）；网关/负载均衡转发；应用处理（可能查 DB、调上游）；响应沿原路返回。

失败的样子：4xx 是调用方的问题，5xx 是服务端的问题；502 是网关收到上游的无效响应（上游答了但答得不对，指向上游进程状态），504 是网关等上游超时（上游压根没答，指向上游耗时），503 是应用自己承认不行（主动拒绝/过载保护/无可用实例，指向容量与自我保护）。

连接复用（Keep-Alive / 连接池）首先省的是握手延迟（跨机房约 175 ms，是一次简单查询的 8 倍以上）；池子需求 = 到达速率 × 单次耗时（L = λW），所以池子满了要先怀疑上游变慢，调大池子只是把压力往后传。超时要分层递减（客户端 > 网关 > 应用 > 上游），只设一层就分不清谁先放弃；重试要配退避与上限，否则网关重试会放大故障。

分层要点追问深挖时用

  • 结论：链路每一段失败的样子不同；502/504/503 分别指向状态、耗时、容量。
  • 推导链：分段 → 各段失败语义 → 连接复用省握手 → 池子需求 = λW → 分层超时让最内层先触发。
  • 量化：跨机房 TCP+TLS 握手约 175 ms，是一次简单查询的 8 倍以上；L = λW。
  • 边界与常见误解：HTTP 无状态不等于没有会话（状态放 Cookie/Token）；HTTP/2 解决了应用层队头阻塞，TCP 层的还在（这是 HTTP/3 换 QUIC 的动机）。
