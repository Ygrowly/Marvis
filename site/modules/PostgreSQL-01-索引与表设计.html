P1为什么默认用 B-tree？GIN / GiST / BRIN / Hash 各在什么查询形状下才该用草稿 · 待验收单卡 →

为什么 PG 默认是 B-tree？GIN / GiST / BRIN / Hash 各在什么查询形状下才该用——选型的判据到底是什么？

一张表要同时支撑两种查询——按 status 等值过滤，和在 tags 数组里做「包含」判断。你只有一次建索引的机会，先建哪个？另一类查询怎么办？

一句话结论：索引能回答哪类查询，由它的组织方式决定——B-tree 是有序树，覆盖面最广（等值 / 范围 / 排序 / 前缀 / 唯一），所以是默认；但"默认"不是"最好"，是"最不容易选错"。其余四种各自绑定一种形状：GIN 是倒排（值 → 出现位置集合），所以"包含"变成"按元素查"，适合 JSONB / 数组 / 全文；GiST 节点存包围盒，适合几何近邻与范围重叠（可能是有损的）；BRIN 每块只存 min/max，1 亿行时体积 156 KB vs B-tree 的 1.6 GB（差 1 万倍），但只对物理有序有效；Hash 只支持等值，几乎没有场景。选型判据是两句话：① 这个查询用哪个操作符（只有支持它的类型才有资格）② 加上之后写入路径能不能承受——只说①是教科书答案，两句都说才是做过线上的人。题目里的答案：status 用 B-tree，tags @> 用 GIN；如果只能建一个，先建 B-tree——因为 GIN 的写入代价明显更高（20 个键就是 20 倍写放大），不该为一个非热点查询付这个代价。

  • 组织方式决定能回答什么
  • B-tree = 默认（覆盖面最广，不是最好）
  • 等值 · 范围 · 排序 · 前缀（只有 abc%，%abc 不行）
  • GIN = 倒排（把包含变成按元素查）
  • **BRIN = 每块 min
  • max（1.6GB vs 156KB，差 1 万倍，只对物理有序有效**）
  • GiST = 包围盒（可能有损）
  • Hash 只等值
  • 判据两句：操作符 + 写入代价
  • GIN 写入放大 20 倍 → fastupdate 或改数据结构
  • 选型最终由 EXPLAIN 说话

主线：索引是"按某种方式重新组织或摘要数据"的结构，它能回答哪类查询由组织方式决定。 所以选型的第一步不是比较性能，是判断资格——"这个操作符，只有哪些组织方式能直接回答"。

1. GIN 为什么适合 JSONB 和数组？

因为它们是"多值"字段：B-tree 只能比较整体，而 GIN 的倒排结构把"包含某个元素"变成一次键查找。 答这题必须把"倒排"两个字说出来。

2. 时序数据用什么索引？

BRIN（按时间追加写、物理有序），体积比 B-tree 小几个数量级；但一旦乱序就失效，所以要先确认"只追加、不更新"。

3. 全文检索怎么建索引？

GIN + tsvector（配 to_tsvector 表达式索引）——这正是"表达式索引 + GIN"的组合（[[母题-P3-部分索引与表达式索引]]）。

4. 一个字段能同时建两种索引吗？

能，但要想清收益：JSONB 既要整体等值又要包含查询时可以 B-tree + GIN，代价是写入要维护两棵树。多数情况下只留 GIN 就够（GIN 也能做等值）。

5. GIN 写入慢，高写入表怎么办？

① fastupdate / pending list（把多次写合并成一次批量合并，代价是查询要先扫 pending list）② 换思路：把需要检索的字段在写入时预处理成一个可 B-tree 的列——用写入侧的冗余换掉 GIN 的写入开销。

P2PG 是堆表，为什么每次索引查询都要回表？Index Only Scan 怎么避免草稿 · 待验收单卡 →

PG 是堆表，为什么索引查询要回表？Index Only Scan 靠什么成立？联合索引在 PG 也有最左前缀吗？

一条 WHERE device_id = ? AND stat_date >= ? 只返回 device_id, stat_date 的查询，同样的表结构在 MySQL 里可以做到「不回表」，在 PG 里为什么不一定？

一句话结论：MySQL 的主键就是数据本身（索引组织表），PG 的索引只是"指向数据的路标"——PG 的表是堆，所有索引都是二级索引，叶子存 ctid（物理位置），所以走索引只能拿到"行在哪"，取行必须再读堆，这就是回表。而且回表成本随命中行数线性增长（命中 1000 行 ≈ 100ms，命中 10 行 ≈ 1ms），树查找却是 O(log N)——所以"命中行数"比"树查找深度"重要得多。Index Only Scan 的判据不是"列齐了"，而是"可见性映射说这一页所有版本都可见"——因为可见性信息存在堆页头部。所以它依赖 VACUUM 的维护，而验证的唯一依据是 EXPLAIN ANALYZE 里的 Heap Fetches（不是 0 就还在回堆）。最左前缀在 PG 依然成立（原因相同：B 树有序），差别在叶子存什么——PG 存 ctid + 各列值，所以更容易做到覆盖，但仍受可见性限制；而 INCLUDE 列是"不改索引的可用形状，只加覆盖能力"。

  • **堆
  • 所有索引都是二级索引
  • ctid = (页号, 页内偏移)**
  • 回表必然
  • 回表成本线性增长（1000 行 ≈ 100ms）
  • 树查找 O(log N) 不是瓶颈
  • Index Only Scan 的判据是可见性映射（不是列齐）
  • 可见性信息在堆页头部
  • 依赖 VACUUM
  • Heap Fetches 判断真假（≈ 返回行数 = 省了个寂寞）
  • 最左前缀成立（B 树有序）
  • PG 叶子存 ctid + 各列值
  • INCLUDE 列不参与最左前缀
  • CLUSTER 是一次性重排、不持久

主线：MySQL 的主键就是数据本身（索引组织表），PG 的索引只是「指向数据的路标」。 这一条决定了两边索引的一切行为差异：回表、主键选型、页分裂、覆盖索引的可行性。

1. PG 的主键一定是聚簇索引吗？

不是。PG 的主键只是"唯一且非空的 B-tree 索引"，数据仍然是堆。这是最容易被 MySQL 语义污染的一题。

2. PG 有聚簇吗？

有 CLUSTER 命令，但它是一次性重排（按某个索引把堆重写一遍），之后新写入的行不会再维持顺序——所以不是持续的"聚簇索引"。知道它存在、也知道它不持久，就够了。

3. 为什么 PG 的索引个数对写入影响大？

每次写要在堆里插行，同时更新每一个索引；而且 PG 的 MVCC 让更新等于"插入新版本 + 标记旧版本"，写放大被进一步放大。

4. 怎么判断有没有真的省掉回表？

EXPLAIN ANALYZE 看三点：节点是不是 Index Only Scan；Heap Fetches 是多少（不是 0 就说明还是回了堆）；实际行数与 buffered read 的关系。只看节点名不看 Heap Fetches，是典型的假优化。

5. 表膨胀会让回表更慢吗？

会，而且是双重影响：① 堆页更稀疏，同样的行数分布在更多页上，回表的随机 IO 次数上升；② 索引的 ctid 指向的旧位置让局部性更差。所以"回表慢"在 PG 里经常要先治膨胀（VACUUM），而不是先加索引。

P3部分索引（Partial Index）与表达式索引：什么场景能省一大截草稿 · 待验收单卡 →

部分索引与表达式索引各解决什么问题——它们省的那一大截，代价是什么？

attack_run 表里 99% 的行都是终态（COMPLETED / CANCELLED），只有少量是活跃态（READY / SEARCHING / REPLAYING）——但调度器每秒都在查这些活跃行。给 status 建一个全表索引，浪费在哪？

一句话结论：索引的价值 = 它服务的那部分查询的频率 × 被索引集合的大小——只用得上 1% 的行，就不该为 100% 的行付维护成本。部分索引只给满足谓词的行建索引，体积与服务范围成正比（本例约 1/100），而且终态化那一步完全不碰它；它还有 PG 特有的第三项收益：VACUUM 负担同步下降。唯一的关键规则是"谓词必须匹配（可证明蕴含）"——WHERE updated_at > ?（不带 status）用不上，因为谓词缺失，PG 不敢用（用了会漏终态行），这时只能改写查询，不能靠加索引解决。表达式索引把计算结果作为索引键，让 lower(email) 这类条件也能走索引——两个硬约束是：函数必须 IMMUTABLE（now() 不行），且查询要写一模一样的表达式。两者组合就是部分唯一索引（UNIQUE (lower(email)) WHERE deleted_at IS NULL），这是软删除场景的经典解，也最能体现"索引是为业务规则服务"。最大的风险是静默失效——以后新增一条不匹配谓词的查询就自动走全表扫，而你不会收到通知，所以必须把服务范围写进注释。

  • 价值 = 频率 × 集合大小
  • 全表索引的四项浪费（体积·写入·VACUUM·统计）
  • 部分索引体积 ≈ 1
  • 100
  • 谓词必须可证明蕴含
  • 缺谓词 = 用不上（只能改写查询）
  • 静默失效是最大风险 → 服务范围要写注释
  • 表达式索引：把结果作为键
  • 两个约束：IMMUTABLE + 表达式一模一样
  • now() 不行
  • 部分唯一索引 = 软删除的经典解
  • MySQL 没有部分索引（用 (status, updated_at) 但索引仍含全量行）

主线：索引的价值 = 它服务的那部分查询的频率 × 被索引集合的大小。

1. PG 怎么做软删除的唯一约束？

部分唯一索引：CREATE UNIQUE INDEX ... ON users (lower(email)) WHERE deleted_at IS NULL。删掉的行不参与唯一性，所以可以重新注册同一个邮箱。

2. LIKE '%xx' 能走索引吗？

普通 B-tree 不行（前缀无序）；PG 的常规解法是 pg_trgm + GIN / GiST。答这题能顺手展示你知道"扩展"而不是只会内置类型。

3. 函数写在条件里索引失效，怎么办？

两条路：改写成 col >= ? AND col < ?（去掉函数），或建表达式索引。前者不付额外代价，后者只在改不动 SQL 时用。

4. 部分索引会不会失效？

会，而且是静默的：查询条件与谓词不再匹配时，新查询自动用不上、走全表扫，而你收不到通知。所以必须把服务范围写进注释或文档——这是它最大的运维风险。

5. 索引多了对 VACUUM 有什么影响？

每多一个索引，autovacuum 清理死元组要多处理一棵索引树，代价从"写放大"延伸到"清理负担"。所以"索引不是越多越好"在 PG 里的后半句是："索引越多，表膨胀越难被自动控制住"（[[母题-P15-VACUUM与事务ID回卷]]）。

P4索引的代价与在线建索引：CREATE INDEX CONCURRENTLY 有什么坑草稿 · 待验收单卡 →

索引的代价是什么（PG 版）？CREATE INDEX CONCURRENTLY 有什么坑，失败了怎么办？

线上 8000 万行的表要加一个索引。你直接执行 CREATE INDEX idx_x ON big_table (col)。会发生什么？换成 CREATE INDEX CONCURRENTLY 就安全了吗？

一句话结论：PG 里索引的代价有三项——写放大 / 空间 / VACUUM 与缓存压力（第三项是 PG 特有的，也是它在索引数量上比 MySQL 更保守的原因）；CREATE INDEX CONCURRENTLY 做到了不长时间阻塞写入，代价是不能在事务里跑、要扫两遍表所以更慢、失败会留下 INVALID 索引——那个索引不报错、但照样占空间并拖慢写入，必须手动 DROP 再重建。

  • 写放大
  • 空间
  • vacuum 压力
  • HOT 与 fillfactor
  • CONCURRENTLY 不能在事务内
  • 两遍扫描
  • INVALID 索引
  • 幂等重建脚本

主线：在线变更安全的判据不是「它快不快」，而是「失败之后系统停在一个什么状态、以及这个状态是否可见」。 MySQL 的答案是「看不见的队列堵住一切」，PG 的答案是「看得见但不报错的无效索引」——两次都是「静默」最危险。

1. 为什么不能放在事务里，机制上是什么？

因为它需要跨多个事务、让并发事务持续提交才能收集到完整数据；被放进一个事务里，就变成「持锁等待」，反而退化成普通 CREATE INDEX 的语义，所以 PG 直接禁止。它不是更聪明的锁，而是换了一套做法。

2. 如果建到一半应用在写，会不会丢行？

不会。第二次全表扫描就是为这件事存在的：它补齐构建期间新增/更新的行；两遍覆盖完整之后才把索引标记为 valid，中途出问题就停在 invalid。所以正确性靠「补扫 + 校验」，不靠「停写」——这和 MySQL 影子表方案（pt-osc / gh-ost）的「先建后换」是两种哲学，可以对比着讲。

3. HOT 和加索引是怎么互相影响的？

HOT 的前提之一就是「更新的列不在任何索引里」，所以每多一个索引，就多一批更新被判出 HOT 通道。这是 PG 里「索引数量」这件事比 MySQL 更贵的一条具体机制（不只是抽象的「写放大」）。顺带还能说出第二样收益：HOT 链上的中间版本能在正常运行时被就地清掉，所以它同时减轻 VACUUM 负担。

4. 唯一索引用 CONCURRENTLY 建失败了，约束到底生效没有？

生效了。 第二次扫描一开始，唯一性就已经在强制；构建失败之后，那个 invalid 索引【仍然继续强制唯一性】。所以它的状态是「约束在，索引不在」——写入侧像个约束，读取侧不像个索引。 这条最能说明"失败不是回到原点"（[[母题-P19-唯一约束与UPSERT]]）。

5. PG 加字段会不会锁表？

ADD COLUMN 只有默认值在 PG 11+ 后是元数据操作、不重写表（很轻）；但改类型 / 加约束要重写表，那才是真正危险的。要区分「加列」和「改列」。

6. 怎么发现线上有无效索引？

pg_index.indisvalid = false；顺手还能查重复/冗余索引（同一前缀的多个索引）与从未被用过的索引（pg_stat_user_indexes.idx_scan = 0）。「该删的索引」和「该补的索引」一样值钱。

P5表设计与数据类型：text 与 varchar、jsonb 与 json、serial 与 identity、timestamptz 怎么选草稿 · 待验收单卡 →

PG 里 text 与 varchar、jsonb 与 json、serial 与 identity、timestamptz 怎么选？

给一张新的业务表定字段：一个存放用户输入的文本字段、一个结构不固定的配置项、一个主键、两个时间戳。每项怎么选，为什么？

一句话结论：PG 里 text 与 varchar(n) 性能没有差别（同一套变长存储），所以选哪个是语义选择——要长度约束才用 varchar(n)；jsonb 存解析后的二进制、可建 GIN 索引，json 存原始文本、保留格式与键序，要查就用 jsonb；主键用 GENERATED ... AS IDENTITY（SQL 标准，序列是隐式的，随表走），serial 是历史写法；时间一律 timestamptz（存 UTC 瞬时点、会话时区显示），timestamp 只用于「就是本地墙上时间」的语义。

  • text = varchar（无性能差）
  • varchar(n) 只做校验
  • 1 字节头 ≤126 字符
  • char(n) 最慢
  • jsonb 可索引 vs json 保原文
  • identity（自动 NOT NULL，但不保证唯一）vs serial
  • UUID 的索引代价在索引不在堆
  • timestamptz 存 UTC、不保留原时区

主线：类型选择不是「哪个性能好」，而是「哪个语义对」。 长度约束、时区语义、结构固定性、唯一性来源——先把语义说清，性能差异在 PG 里往往小到不值得作为第一理由。

1. jsonb 存的配置项想做范围查询怎么办？

两条路：① 表达式索引把某个内部字段抽出来（(data->>'priority')）建 B-tree；② 如果被查询字段是核心业务字段，就把它提升成独立列——「能被高频查询的字段不该藏在 JSON 里」，这是比建索引更根本的建议。

2. 改了字段类型会不会锁表？

ALTER COLUMN TYPE 通常会重写整表（危险）；但扩大长度、加/去掉 varchar 的长度限制在 PG 里是不重写的。所以「想加长字段」不需要紧张，而「改存的是什么」必须排窗口——这条又回到 P4 的「区分加列与改列」。

3. PG 用 numeric 还是 float 存金额？

numeric。官方定义里 numeric 是「用户指定精度、精确」，而 real / double precision 是「变精度、不精确」（分别约 6 / 15 位十进制有效数字）。浮点是二进制近似，金额会出现比较与累加误差。 这条在 MySQL 里也是同一答案，属于跨栈通用。

4. NULL 在唯一约束里怎么算？

PG 里 NULL 彼此不相等，所以 UNIQUE 列允许多行 NULL。这正是 P19「唯一约束做幂等防线」要注意的地方：作为幂等键的列必须 NOT NULL（[[母题-P19-唯一约束与UPSERT]]）。

5. 枚举用 enum 还是 varchar + CHECK？

enum 紧凑、约束强、而且有序（枚举值的顺序就是定义顺序，可以直接比较大小）；varchar + CHECK 更灵活。关键事实：PG 12+ 之后 ALTER TYPE ... ADD VALUE 已经是轻量操作（还能指定 BEFORE / AFTER 插到中间），「加值要重建表」是过时说法。
