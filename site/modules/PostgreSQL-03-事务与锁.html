P8默认 RC 还是 RR？同一事务内两次查询为什么会看到不同结果

骨架：PG 默认 RC（对比 MySQL 的 RR）→ 快照粒度差异（语句 vs 事务）→ 所以「两次查询不同」是规范行为 → RR 的代价是写冲突要报 40001 → RC 下 UPDATE 的特殊行为 → Serializable 做了什么 → 快照的隐藏成本 → 怎么选

一句话结论：PG 默认 READ COMMITTED。RC 下每条语句开始时取一次快照，所以同一事务里的两条 SELECT 之间如果有别的事务提交，你就会看到不同的结果——这是规范允许的不可重复读。要事务内一致就提到 REPEATABLE READ（PG 的 RR 是快照隔离，整个事务一个快照，而且连幻读也一并挡住了）；但 PG 的 RR 遇到写冲突会直接报 40001 让你重试，它不靠间隙锁把冲突挡住（那是 MySQL 的做法，见 [[母题-P10-无间隙锁与锁变体]]）。

  • RR = 快照隔离且挡幻读
  • RR 写冲突报 40001
  • Serializable = 不额外阻塞、只检测中止

主线：隔离级别在 PG 里承诺的是「你能看到什么」，不是「你不会失败」。 级别越高，看到的越一致，但越可能被要求重试——这是 PG 与 MySQL 的哲学差异：PG 用「快照 + 报错重试」换掉了「加锁等待」。

1. PG 为什么不加间隙锁？

因为它用快照隔离，幻读已经被快照挡住了，不需要用锁挡。 加间隙锁会让并发插入互相阻塞（MySQL 的死锁大头就来自这里）。这是 PG 用「快照 + 报错」换「锁 + 等待」的一个具体体现（[[母题-P10-无间隙锁与锁变体]]）。

2. Serializable 是不是就万无一失了？

一致性上万无一失，可用性上更容易失败：它连写偏斜都检测，所以中止率更高。而且它要求「读到的数据在事务成功提交前都不算数」——包括只读事务（除非用 READ ONLY DEFERRABLE）。所以它适合"正确性压倒一切"的场景，不适合高并发写入的常规业务。

3. 40001 和死锁（40P01）有什么区别？

40001 是「你的快照过期了，重来一次就好」，没有等待、没有资源占用；死锁是「两个事务互相等对方的锁」，需要一个被牺牲掉。前者是快照隔离的正常输出，后者是加锁模型的固有代价——PG 两种都有，但 40001 是它主动选择的。

4. FOR UPDATE 能不能替代提高隔离级别？

能替代一部分。SELECT ... FOR UPDATE 在 RC 下也会锁住读到的行，所以"读-改-写"这种最常见的竞态可以直接用它防住，不必升到 RR。PG 还有四种变体（FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE），选最弱的那一个能显著减少锁冲突（[[母题-P10-无间隙锁与锁变体]]）。

5. 只读副本上的读一致性怎么办？

副本上的默认也是 RC，但副本有额外一层：复制延迟。要在副本上做「事务内一致读」，RR 只保证副本自身快照一致，不保证读到主库最新——要读最新得走主库，或者用复制槽 / pg_last_wal_replay_lsn() 做等待（[[母题-P12-流复制与逻辑复制]]）。

主线：Serializable 的成本不在执行速度，在「失败与重试」。 所以选择它的前提不是「我的 SQL 快不快」，而是「这个业务操作本身可不可以重试」——可重试，SSI 就是最省心的可串行化；不可重试，就该用显式锁。

1. 写偏斜是什么，为什么 RC/RR 拦不住？

两个事务各读一部分数据、各写另一部分，各自的读集与写集不重叠，所以快照隔离看不出问题，但合起来破坏了一个跨行的不变量。只有 SSI 能自动拦住它，否则要靠显式锁或约束。

2. 能不能不用 SSI，只用 SELECT ... FOR UPDATE 保证正确？

能，但必须保证「读的时候也加锁」——只给写加锁的「先查再写」在 RC 下有竞态。RuleArena 走的是条件更新而不是「读也加锁」这条路（项目文档 04 §15：MVP 优先业务唯一键 + 条件更新）——理由是「锁不能成为资金正确性的唯一保证」，不是「用不了锁」。而一旦读也加锁，你就回到了"锁 + 等待 + 死锁"的老世界。

3. 重试会不会把压力放大成雪崩？

会，而且是正反馈（Q2 的算式：C=1000 时吞吐归零）。所以正确写法必须带退避 + 抖动 + 上限 + 全局并发限制。 能说出「重试也要限流」，就超出教科书答案了。

4. SERIALIZABLE READ ONLY DEFERRABLE 是什么意思？

只读事务声明可延迟启动，它会【阻塞】到一个"保证不会因序列化失败"的快照可用为止。 官方明确指出：这是唯一一种 Serializable 会阻塞、而 RR 不会的情况。 报表类长只读事务想彻底免重试，这是标准做法——而且它通常能在启动时就确定这个事实，从而根本不拿谓词锁。

5. 怎么判断该不该上 Serializable？

先问三件事：① 有没有跨行不变量（没有就不用上）；② 业务操作可不可重试（不可重试就别用 SSI，用锁）；③ 冲突频率有多高（很高时重试成本可能超过加锁）。三个问题问完，答案自己出来。

6. 线上 40001 突然变多，怎么排查？

三个方向：① 看 pg_locks 里 SIReadLock 的粒度（是不是升级成关系级了 → 调 max_pred_locks_*）；② 看有没有新出现的顺序扫描（→ 它一定拿整表锁，鼓励走索引）；③ 看有没有事务变长或连接数上涨（→ 正反馈的前兆）。这三个方向都是从机制推出来的，不是猜。

一句话结论：PG 没有间隙锁——它不会因为「锁了一个范围」而阻止别人往这个范围里插入（MySQL 的 next-key lock 会）。所以防幻读只有两条路：提高隔离级别靠快照（RR / Serializable，冲突时报错重试），或者用显式锁 / 谓词式约束（唯一约束、条件更新）自己把不变量守住。四种行锁从强到弱：FOR UPDATE → FOR NO KEY UPDATE → FOR SHARE → FOR KEY SHARE。

  • 无间隙锁
  • 不阻塞插入
  • FOR UPDATE
  • FOR NO KEY UPDATE
  • FOR SHARE
  • FOR KEY SHARE
  • 外键用最弱的 KEY SHARE
  • 普通 UPDATE 对应 NO KEY UPDATE，但改被外键引用的键列会升到 UPDATE
  • PG 默认无限等锁
  • advisory lock

主线：MySQL 用「范围锁」把幻读挡在门外；PG 用「多版本快照」让幻读不产生错误结果，代价是冲突时要报错重试。 一个靠「不许发生」，一个靠「发生但可检测」——理解这个分歧，后面的锁与隔离全都能推出来。

1. FOR UPDATE 是不是就万无一失了？

不是。① 它只锁匹配到的行，如果范围里还没有行（还没插入），照样锁不住——这正是「无间隙锁」的直接后果；② 它需要读的时候也用它，一旦某条路径忘了加锁就出现竞态；③ 它会把并发冲突从「报错重试」变成「排队等待」，而 PG 默认无限等，高并发下可能拖垮吞吐。

2. 那 RuleArena 为什么优先条件更新？

项目文档给的理由是「权威性」不是「频率」：04 §15 原话「MVP 优先业务唯一键 + 条件更新」，Q7 原话「锁可以降低竞争，但不能成为资金正确性的唯一保证……只有真实高竞争时再评估锁」——注意文档 04 §12 同时给了「锁定订单行【或】乐观版本条件更新」，所以不要说成「完全不用锁」；准确说法是「优先条件更新，锁留到真实高竞争时再评估」。而且条件更新天然幂等（重复执行第二次影响 0 行），唯一约束负责最终防线（[[母题-P18-乐观并发控制]]）。

3. SELECT ... FOR UPDATE 和 UPDATE 自己差在哪？

UPDATE 会自动加行锁（普通更新对应 FOR NO KEY UPDATE，改键列则升到 FOR UPDATE）；FOR UPDATE 是先把行锁住再去判断/计算，用于「读—判断—写」跨越多次交互的场景。另外官方提醒：SELECT FOR UPDATE 会因为"标记行已锁"而产生磁盘写。

4. PG 的表锁呢？

PG 有一套 8 种表级锁（ACCESS SHARE 到 ACCESS EXCLUSIVE），日常业务基本不用；要被提醒的是 ALTER TABLE 会拿较重的表锁——那才是真正会堵住整张表的（[[母题-P4-索引代价与在线建索引]]）。

5. advisory lock 适合做什么？

适合那些"不适合用表里的标志位"的锁：官方说它比标志位更快、避免表膨胀、而且会话结束时服务器自动清理。 典型场景是调度器选主、单例任务互斥。 但要注意两个坑：会话级的不遵守事务语义（回滚后仍持有），以及它和普通锁共用同一个内存池——耗尽它会让服务器无法授予任何锁。

这道题属于母题 P8 · 默认 RC 还是 RR？同一事务内两次查询为什么会看到不同结果 · 下面挂它的完整回答（学的时候看）

实测 217 字 · 按 4 字/秒折算约 54 秒（秒数是估算，字数才是实测）

PG 默认 READ COMMITTED（注意：MySQL 默认是 RR，这是最容易被抓住的方言错误）。RC 下每条语句开始时取一次快照，所以同一事务里两条 SELECT 之间如果有别的事务提交，你会看到不同结果——这是规范允许的不可重复读。

要事务内一致就提到 REPEATABLE READ：PG 的 RR 是快照隔离（整个事务一个快照），而且连幻读也一并挡住了——这一点和 MySQL 的 RR 不同（MySQL 靠 MVCC 挡快照读的幻读、靠间隙锁挡当前读的幻读）。

分层要点追问深挖时用

  • 结论：PG 默认 RC（MySQL 默认 RR）；PG 的 RR 是快照隔离，连幻读一并挡住，冲突时报 40001。
  • 推导链：默认 RC → 每语句取快照 → 允许不可重复读 → 提到 RR 得快照隔离 → 冲突处理是报错重试而非排队。
  • 量化：错误码 SQLSTATE 40001（序列化失败）。
  • 边界与常见误解："MySQL 和 PG 默认级别一样"×；"PG 的 RR 靠间隙锁"×（PG 没有间隙锁）。

19必背P9

这道题属于母题 P9 · 为什么 Serializable 会失败？应用层怎么处理才正确 · 下面挂它的完整回答（学的时候看）

实测 113 字 · 按 4 字/秒折算约 28 秒（秒数是估算，字数才是实测）

PG 的 Serializable 用的是 SSI（Serializable Snapshot Isolation）：它在快照隔离之上检测可能导致非可串行化结果的读写依赖环，一旦发现就主动让其中一个事务失败（SQLSTATE 40001）。

分层要点追问深挖时用

  • 结论：SSI 主动检测依赖环并让一方失败；40001 必须整事务重试，且带退避与上限。
  • 推导链：快照隔离之上 → 检测读写依赖环 → 主动失败 → 应用重试整个事务 → 与 MySQL 的排队方案对照。
  • 量化：SQLSTATE 40001；重试要带退避与次数上限。
  • 边界与常见误解：不能只重试单条语句；死锁与序列化失败在 PG 里都是"报错让你重试"，不是"帮你排队"。
