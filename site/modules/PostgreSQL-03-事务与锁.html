P8默认 RC 还是 RR？同一事务内两次查询为什么会看到不同结果草稿 · 待验收单卡 →

PG 默认是 RC 还是 RR？同一事务内两次查询为什么会看到不同结果？

同一个事务里，两条完全一样的 SELECT 返回了不同的行。这算 bug 吗？

一句话结论：PG 默认 READ COMMITTED。RC 下每条语句开始时取一次快照，所以同一事务里的两条 SELECT 之间如果有别的事务提交，你就会看到不同的结果——这是规范允许的不可重复读。要事务内一致就提到 REPEATABLE READ（PG 的 RR 是快照隔离，整个事务一个快照）；但 PG 的 RR 遇到写冲突会直接报错让你重试，它不靠间隙锁把冲突挡住（那是 MySQL 的做法，见 P10）。

  • 默认 RC
  • 每条语句一个快照 vs 每事务一个快照
  • 快照隔离 SI
  • 写冲突要重试
  • RC 下 UPDATE 会重新检查最新版本
  • 快照基于事务开始时间

主线：隔离级别在 PG 里承诺的是「你能看到什么」，不是「你不会失败」。 级别越高，看到的越一致，但越可能被要求重试——这是 PG 与 MySQL 的哲学差异：PG 用「快照 + 报错重试」换掉了「加锁等待」。

原理分解

一、默认值：第一处必须说对的差异

MySQL（InnoDB）PostgreSQL
默认隔离级别REPEATABLE READREAD COMMITTED
幻读防护next-key lock（间隙锁）无间隙锁，靠快照 / SSI
写冲突表现等待锁（可能超时/死锁）报 40001，让应用重试

为什么这个默认值差异重要：MySQL 的 RR 让很多「本来会出现的读不一致」被默认挡住，所以从 MySQL 过来的人习惯性地假设「事务内读是一致的」；而 PG 默认不保证这一点。面试里只要开口说「PG 默认也是 RR」，后面所有关于并发行为的判断都会被怀疑。

二、快照粒度：理解一切的关键

级别快照什么时候取
READ COMMITTED（默认）每条语句开始时各取一次
REPEATABLE READ（PG 的快照隔离）事务开始时取一次，整个事务都用它

所以 RC 下：

事务 A                                    事务 B
BEGIN
SELECT balance  → 100
                                          UPDATE ... COMMIT（改成 80）
SELECT balance  → 80     ← 同一事务，结果变了

这不是 bug——两条语句各自取了自己的快照，各自看到了当时已提交的最新数据。

RR 下这两条都会返回 100（整个事务用同一快照）——这才叫「可重复读」。

三、RC 下一个必须知道的细节：UPDATE 会看到「最新的那一行」

RC 下，当你 UPDATE 一行时，如果这一行在语句执行期间被别人改过，PG 的规则是：

重新读取该行的最新已提交版本，重新判定 WHERE 条件是否仍成立，成立才更新；不成立就跳过（受影响的可能比你以为的少）。

为什么这条重要：它解释了两件常见现象——

  • UPDATE ... WHERE status = 'QUEUED' 在 RC 下是「相对安全」的：因为重新判定时会发现 status 已经不是 QUEUED 了，于是跳过。这正好是 P18 条件更新能成立的基础。
  • 反面：它也可能让你「以为改了一行、实际没改」，所以必须用影响行数判断结果，不能假定一定成功。

四、RR 的代价：写冲突会报错

PG 的 REPEATABLE READ 是快照隔离。当两个事务基于同一个旧快照去改同一行时，第二个会拿到：

ERROR: could not serialize access due to concurrent update (SQLSTATE 40001)

这不是故障，是设计：要么让你看到一致快照、要么明确告诉你没改成功，二者不能都要。 所以 PG 的做法是「报错 + 应用重试」，而不是 MySQL 那样「加锁等待」。

所以把级别提到 RR 的那一刻，你的应用就必须能重试事务（见 P9）。

五、怎么选（面试收尾）

场景选择
绝大多数业务读写RC（默认）——每条语句看最新已提交数据，最接近直觉，并发冲突最少
一条事务里需要多次读同一批数据保持一致（对账、汇总计算）RR，并且整套写路径要能处理 40001 重试
有跨行不变量、写偏斜风险Serializable（SSI），同样要能重试（P9）
只读报表RC 或 RR 都行，但注意长事务对膨胀的影响（P14）

一句判据：能接受「读到别人刚提交的数据」就用 RC；需要「整段计算基于同一时刻」就往上提，同时接受重试。

P9为什么 Serializable 会失败？应用层怎么处理才正确草稿 · 待验收单卡 →

为什么 Serializable 会失败？应用层怎么处理才正确？

把隔离级别提到 Serializable 之后，接口开始零星报 could not serialize access due to read/write dependencies。这是「不能用」还是「设计如此」？

一句话结论：PG 的 Serializable 用的是 SSI（Serializable Snapshot Isolation）：它在快照隔离之上检测可能导致非可串行化结果的读写依赖环，一旦发现就主动让其中一个事务失败（SQLSTATE 40001）。所以失败是设计的一部分，不是异常——正确做法是在应用层捕获 40001、重试整个事务（带退避和上限），而不是重试单条语句。

  • SSI
  • 读写依赖与依赖环
  • 40001
  • **重试整个事务**
  • 幂等
  • 与悲观锁取舍
  • 误报

主线：Serializable 的成本不在执行速度，在「失败与重试」。 所以选择它的前提不是「我的 SQL 快不快」，而是「这个业务操作本身可不可以重试」——可重试，SSI 就是最省心的可串行化；不可重试，就该用显式锁。

原理分解

一、SSI 是怎么做到可串行化的

传统可串行化靠两阶段锁（锁到事务结束），代价是并发度低、容易死锁。PG 走另一条路：

① 先按快照隔离执行，读不加锁 —— 大部分事务根本不会冲突
② 在后台记录事务之间的「读写依赖」（谁读了谁写的数据）
③ 如果发现依赖形成一个环 —— 就不可能存在任何串行顺序 → 报错并干掉其中一个

关键在「② 只记录依赖，不是拦住操作」：所以没有冲突的事务完全没有额外等待。只有真的出现环时才失败。

代价有两个：

1. 可能误报：SSI 的检测是保守的，某些理论安全的场景也会被判失败——所以它是「宁可我报错，不给你错结果」。 2. 失败是概率性的：同一批事务，跑两次可能一次成功一次失败——这让「重试」变成必须，而不是可选。

二、错误长什么样，怎么识别

ERROR: could not serialize access due to read/write dependencies among transactions
DETAIL: Reason code: Canceled on identification as a pivot...
SQLSTATE: 40001

判断这件事要用错误码（40001），不要用错误文本匹配——文本会随版本/语言变化，错误码是契约。同一个 40001 也会由 RR 下的写冲突产生（P8），语义都是「重试就能成功」。

要区分的三类错误：

错误语义处理
40001（序列化失败 / 快照过期）可重试：重放事务大概率成功重试整个事务
40P01（死锁）也可重试，但说明加锁顺序有问题重试 + 修加锁顺序
约束冲突（23505 等）确定性失败，重试也没用不要重试，走业务分支

这个三分法比「统一重试三次」重要得多——对确定性错误无脑重试，是在制造重复副作用。

三、正确的重试长什么样

必须是「整个事务」，不是「那一条语句」：

① 记录本次事务的输入（幂等键）
② BEGIN
③ 执行全部读与写
④ COMMIT
   └─ 若报 40001 → 回滚 → 重新执行 ③（用同样的输入）

因为 SSI 失败意味着「你读到的那个快照已经不可信」——重试那一条语句没有意义，必须重新读。

四条要求：

  • 带退避 + 抖动：并发高时同步重试会互相打架，越试越糟；
  • 有重试上限：超过就暴露成失败/未知，不要无限循环；
  • 整个事务幂等：重试不能产生第二次副作用——所以必须有幂等键或唯一约束兜底（P18/P19）；
  • 保留 trace：记录重试次数，它是「并发竞争激烈程度」的直接指标（可以直接做监控）。

反过来讲最重要的一句：SSI 要求业务可重试；而「可重试」的前提是副作用可幂等。 所以「能不能上 Serializable」其实是一个幂等设计问题，不是一个数据库配置问题。这句话是这道题的分水岭。

四、跟其他方案比

方案机制适合代价
Serializable（SSI）检测依赖环 → 报错重试冲突低但需要跨行不变量、业务可重试可能误报；要求重试框架
RR / RC + FOR UPDATE悲观锁，冲突就排队冲突高、临界区短、业务不好重试锁等待、死锁风险、吞吐下降
条件更新（乐观，P18）判断与写入合并为一条语句冲突低、单行不变量不能直接保护跨行不变量（要靠约束）
唯一约束（P19）数据库原子性幂等与重复的最终防线只覆盖「重复」，不覆盖「顺序」

取舍判据：能不能重试 → 能就用 SSI/乐观；冲突频率高到重试成本超过加锁成本 → 才用悲观锁。 这条判据和 MySQL 那边（M14 乐观锁 vs 悲观锁）是同一句话，只是 PG 多了一层「SSI 帮你自动检测」。

正本：wiki/topics/PostgreSQL/母题-P9-序列化失败与重试.md

P10PG 没有间隙锁，幻读和写偏斜靠什么防？FOR UPDATE 四个变体怎么选草稿 · 待验收单卡 →

PG 没有间隙锁，幻读和写偏斜靠什么防？FOR UPDATE 的四个变体怎么选？

一个只用过 MySQL 的候选人说「RR 靠间隙锁防幻读」。这句话在 PG 里哪里不成立？

一句话结论：PG 没有间隙锁——它不会因为「锁了一个范围」而阻止别人往这个范围里插入（MySQL 的 next-key lock 会）。所以防幻读只有两条路：提高隔离级别靠快照（RR / Serializable，冲突时报错重试），或者用显式锁 / 谓词式约束（唯一约束、条件更新）自己把不变量守住。四种行锁从强到弱：FOR UPDATE → FOR NO KEY UPDATE → FOR SHARE → FOR KEY SHARE。

  • **无间隙锁**
  • 不阻塞插入
  • FOR UPDATE
  • FOR NO KEY UPDATE
  • FOR SHARE
  • FOR KEY SHARE
  • 外键用最弱的 KEY SHARE
  • 写偏斜

主线：MySQL 用「范围锁」把幻读挡在门外；PG 用「多版本快照」让幻读不产生错误结果，代价是冲突时要报错重试。 一个靠「不许发生」，一个靠「发生但可检测」——理解这个分歧，后面的锁与隔离全都能推出来。

原理分解

一、PG 为什么没有间隙锁

MySQL 的 next-key lock = 记录锁 + 间隙锁：锁定「某个范围」，从而阻止别人在这个范围内插入新行，这样「第二次查询不会多出几行」（防幻读）。

PG 的做法完全不同：读操作完全不加锁，靠快照保证「你看到的数据是某个一致时刻的」。所以：

  • 「幻读」在 PG 里表现为：你换了快照就会看到新行（RC 下每条语句一次快照，P8），或看到旧快照（RR/Serializable 下）；
  • PG 不会为此阻塞插入——所以插入和范围查询几乎不互相干扰，并发度更高。

这就是为什么「PG 没有间隙锁」不是缺陷，而是另一条设计路线。

二、幻读和不变量：两条路

需求路径
「我这段计算要基于同一时刻的数据」提隔离级别（RR / Serializable），接受 40001 重试（P8 / P9）
「某个跨行不变量绝不能破」用锁或约束显式守住：FOR UPDATE 锁住涉及行、唯一约束堵住重复、条件更新把判断与写入合并（P18/P19）

关键判断：PG 不会自动帮你把不变量守住（不像 MySQL 会用间隙锁顺手挡住一部分幻读），所以PG 的业务正确性更依赖「显式约束 + 显式锁」，而不是「依赖默认隔离级别」。这句话说出来，对 PG 的理解层次就到位了。

三、四种行锁：从强到弱

变体它阻止什么什么时候用
FOR UPDATE最强：阻止其他事务对这行做 UPDATE / DELETE / SELECT FOR UPDATE / FOR NO KEY UPDATE你马上要改这一行，且不希望任何人插队（注意：它虽然强，但默认不阻止对「非键列」的某些并发路径——见追问）
FOR NO KEY UPDATE弱一点：允许其他事务对同一行做不涉及唯一键的更新更新非键字段的常规写路径（PG 的普通 UPDATE 实际对应这一档）
FOR SHARE共享锁：阻止别人改这行，但允许多人同时读锁「我要基于这行做判断，先别动它」
FOR KEY SHARE最弱：只阻止「删行」和「改键值」外键检查用的就是它

为什么外键用最弱的 FOR KEY SHARE：外键只需要保证「被引用的键还在」——只要没人删它、没人改它的键值就够了，不需要阻止别人改它的其他字段。所以「向子表插入一行」通常不会和被引用行的普通更新互相阻塞。 这是 PG 在外键上的一个精细优化，能主动说出来很加分。

四、写偏斜：比幻读更麻烦的东西

定义：两个事务读的集合和写的集合都不重叠，但合起来破坏了一个跨行不变量。

经典例子：约束是「至少有一名医生值班」。两个事务各自看到「有 2 人值班」，各自把其中一人设为「不值班」——各自的读集不包含对方要写的行，所以 RC 和 RR 都拦不住，最后 0 人值班。

为什么 RC/RR 拦不住：快照隔离只保证「你看到的是一致的」，它不保证「你的读和你的写之间没有别人插进来」。

三条解法：

1. Serializable（SSI）：它能检测出这种依赖环 → 报错重试（P9）——这是最省心的解法； 2. 显式锁：把「读」也加锁（FOR UPDATE 锁住所有涉及行），退化成悲观并发的写法； 3. 改成约束 / 单行聚合：把跨行不变量收敛成一个能被数据库原子保护的东西（比如在一行里维护计数并用条件更新守护）。

第 3 条最值钱：工程上最好的做法不是「加锁保护不变量」，而是「把不变量设计成不需要跨行保护」——这是设计层面的解法，比机制层面的更根本。

五、死锁：PG 里怎么来、怎么减少

1. 统一加锁/更新顺序（例如总是按主键升序更新）； 2. 缩短事务、别在事务里做网络 IO 或等人工确认； 3. 能不用锁就不用锁——条件更新把「等待」变成「0 行受影响」，根本不产生锁等待，也就没有死锁； 4. 批量按固定顺序、分批提交。

  • 来：两个事务以不同顺序锁同一批行（UPDATE 顺序不一致、FOR UPDATE 顺序不一致），或者RC 下 UPDATE 重新检查最新版本（P8）造成的互相等待；
  • 减少：

第 3 条接到 P18：PG 里减少死锁最有效的手段不是调参，而是换并发控制方式。
