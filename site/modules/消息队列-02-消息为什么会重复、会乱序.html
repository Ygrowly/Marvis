Q2消息为什么会重复、会乱序；怎么把"至少一次"变成"只生效一次"，要顺序要牺牲什么

骨架：先给前提"重复与乱序同源，都是至少一次 + 并行的产物" → 重复三来源 → 幂等的定义与"四类查重问的是同一个问题" → 幂等键怎么选（稳定业务键，两个反例） → 超时≠失败 → 乱序的来源 → 全局串行 vs 局部串行（同一指标：并行度）→ 量化"保序粒度 = 并行粒度" → 双端实现要点与生产者重试这个坑 → 边界与误解

一句话结论：重复和乱序同源——重复来自"至少一次投递"（处理与记录进度无法原子化，三处来源框架层都杜绝不了），乱序来自"为了吞吐而并行"。解法是两个动作：① 幂等——用稳定的业务幂等键（业务键 + 动作 + 目标 + 参数 + 版本/步骤，不能用消息 ID 或 ToolCallID，重试时它们会变）做查重，Redis 查重挡大多数、数据库唯一约束兜底，并注意超时是"结果未知"、必须用同一个键；② 局部串行——按业务键哈希到同一分区 / 队列，通道内单线程消费、通道间并行，保序的粒度就是并行的粒度（单条 5ms → 单分区 200 TPS → 要 2000 TPS 就 10 个分区，但单键上限永远仍是 200 TPS）。

  • 至少一次 + 幂等 = 只生效一次
  • 重复三来源（生产重发、消费端提交前崩溃、Broker 重投）
  • 幂等 = "这个操作做过没"
  • 四类查重（唯一键 / 唯一约束 / 乐观锁 / 状态机）
  • 稳定业务键，不用消息 ID 和 ToolCallID
  • 幂等粒度对到"一次动作"不是"一个业务实体"
  • 超时≠失败，不许换键
  • 乱序源于并行
  • 局部串行：保序粒度 = 并行粒度
  • 单分区 TPS = 1
  • 单条耗时
  • 分区数是并行度天花板
  • 生产者重试也会乱序（幂等 + in.flight ≤ 5）
  • linger.ms 管不了乱序

解法是两个动作：① 幂等——用稳定的业务幂等键（业务键 + 动作 + 目标 + 参数 + 版本/步骤）做查重。不能用消息 ID 或 ToolCallID，重投时它们会变，查重永远不命中；粒度还要对到"一次动作"（只用订单号会把"创建"和"取消"混成一个键）。Redis 查重挡大多数、数据库唯一约束兜底；Redis 不可用时让唯一约束顶上，不要简单 fail open（会重复）或 fail closed（会全量积压）。而且超时是"结果未知"：要用同一幂等键重试，或先查下游权威状态，不要猜。

  • 结论：至少一次 → 重复靠业务幂等；并行 → 乱序靠局部串行（保序粒度 = 并行粒度）。
  • 推导链：处理与记录进度无法原子 → 重复三来源 → 业务幂等键 + 唯一约束兜底 → 并行导致乱序 → 按业务键哈希 + 通道内单线程。

主线："至少一次 + 幂等 = 只生效一次"是唯一可行的路线，而"保序的粒度就是并行的粒度"是唯一能算的判据。 前一句决定了"重复要去业务层解决"，后一句决定了"顺序不能靠全局串行换"。两句合起来，就是这一整个模块的设计边界。

1. 幂等键为什么不能用消息 ID？

重投时 ID 会变，查重永远不命中。要用业务动作指纹（业务键 + 动作 + 目标 + 参数 + 版本/步骤），保证"同一动作重试时算出同一个键"。粒度还要对到"一次动作"，只用订单号会把"创建"和"取消"混成一个键，反而把动作吃掉。

2. 超时之后能不能重试？

不能直接重试。超时是结果未知，下游可能已经执行成功。正确动作是用同一幂等键重试，或者先查下游的权威状态；两者都做不到就停下并记录 UNKNOWN，不要猜。

3. 生产者重试会不会把顺序搞乱？

会（enable.idempotence=false 且 in.flight>1 时）。正确配置是 幂等开启（3.0 起默认）+ acks=all + in.flight ≤ 5，既保序又不丢吞吐。in.flight=1 是保序但牺牲吞吐的退路。

4. Redis 查重挂了怎么办？

关键是不能只依赖一条查重路径：Redis 查重负责快，数据库唯一约束负责准。Redis 不可用时让唯一约束兜底，不要简单地 fail open（会重复）或 fail closed（会全量积压）。

5. 顺序消费的代价是什么？

并行度。同一条通道（分区 / 队列）同一时刻只能被一个消费者消费，分区数就是并行度的天花板；而单个业务键的吞吐上限 = 单分区上限，加分区也提不高它（热点键问题）。
