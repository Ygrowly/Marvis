一次运行到底发生了什么——为什么"打日志"不够，必须要有 Trace？而 Trace 里最少要有什么？

面试官问——"线上出了个 Bad Case，你怎么定位？Trace 和日志有什么区别？"

一句话结论：Trace 是树，日志是线——日志回答"发生了什么"，Trace 回答"谁导致了谁"。三类信号分工不同：指标看分布与趋势、Trace 看因果与归因、日志看细节与原文；跨步、跨服务的因果链，靠日志只能人工对着时间戳猜，而 Agent 天然多步，这个成本随步数急剧上升。Trace 的数据模型是 Request → Run → Model / Retrieval / Tool / Approval Span，每个 span 必须带：版本（model / prompt / tool / rule）、Artifact 引用、幂等键、latency、token 用量、错误码——少了版本就复现不出来（和 [[母题-A4-长任务状态与Checkpoint]] 的 Step 记录是同一套字段）。存储要控：50 span × 2 KB × 1 万 run = 1 GB/天 = 365 GB/年，所以只记"有业务意义或有副作用"的 span（15 个 → 一年约 110 GB）。采样要按信息价值：失败的全采、成功的抽样（失败率 5% 时 = 5% + 95%×5% = 9.75%，存储降到约 1/10 而归因能力完全保留）——"随机采样 10%"会把最需要的长尾失败采没。最后，判分要分结果和轨迹：先有结果判分（底线），再补轨迹判分（体检）——因为"结果对了但过程有问题"（绕远路、用了危险工具）只有轨迹能发现。

  • **Trace 是树、日志是线**
  • 三信号分工（指标=分布
  • Trace=因果
  • 日志=细节）
  • 模型 `Request → Run → Model
  • Retrieval
  • Tool
  • Approval Span`
  • **Langfuse：Observations 可嵌套、trace 属性冗余到每行**（写换读）
  • span 必需字段（**版本
  • Artifact 引用
  • 幂等键
  • 延迟
  • 错误码**）
  • 存储 1 GB
  • 天
  • 365 GB
  • 年
  • 粒度判据 = 有业务意义或有副作用
  • **失败全采 + 成功抽样**（5% + 95%×5% = 9.75%）
  • 安全事件必须全采
  • **grade outcome vs grade transcript**（先结果后轨迹）

主线：可观测性的目标不是"记录得多"，是"出事时能定位到具体哪一步"。 所以它有两个取舍，而不是一个：记什么粒度（按"有业务意义"筛）、留哪些样本（按"信息价值"筛）——两个都做错，记录再全也定位不了。

1. Trace 和日志有什么区别？

日志是事件流，Trace 是调用树。树有父子关系，所以能算"这一步占多少时间""这一步的失败是谁引起的"——日志算不出来。两者互补，不是替代关系（细节还是要看日志）。

2. Trace 里最少要有哪些字段？

层级（trace / run / span 的父子关系 + trace_id）；每个 span：类型、开始结束时间、版本（model / prompt / tool）、Artifact 引用、幂等键、token 用量、错误码。检索 span 还要带 query / candidates / 索引版本（[[母题-G5-RAG评测与幻觉率]] 的三岔路归因需要它）。

3. 怎么定位一个 RAG Agent 答错？

按三岔路走：① 正确证据进 TopK 了吗（没进 → 召回问题）② 进最终 Context 了吗（没进 → 重排 / 预算 / 去重）③ 都进了还是错（→ 生成 / Prompt / 引用）。前提是 Trace 把这些都留下来了——否则只能猜。

4. Trace 存不下怎么办？

① 控制粒度（只记有业务意义或有副作用的 span）② 按信息价值采样（失败全采 + 成功抽样）③ 分级存储（近期的全量、历史的聚合或降采样）。但安全事件永远全采。

5. 怎么验证 Trace 本身没坏？

用 Replay 反向验：随便挑一条失败的 Trace，看能不能从它复现出当时的行为（[[母题-E3-回归门禁与发布卡口]] 的 Mock replay）。复现不出来，说明 Trace 缺字段。

改了东西怎么保证不退化——门禁该卡在哪一道、卡多严，而"没测出问题"又意味着什么？

面试官问——"你们的发布门禁卡什么？阈值怎么定的？模型输出是非确定的，CI 怎么做？"

一句话结论：门禁有两类，性质完全不同——统计阈值型（成功率降幅、P95、成本）与绝对红线型（跨租户泄露 = 0、未确认执行 = 0）；红线不接受平均、也不接受阈值。阈值必须与评测集分辨率匹配：200 条的标准误约 2.1%，阈值设 2% 会在"什么都没变"时约 32% 的概率误报——要么放宽到 2 个标准误，要么把集合做大到约 900 条。红线还要报"上界"而不是"通过"：1000 个对抗样本 0 次泄露，按三倍法则 95% 上界约 0.3%——你能说"低于 0.3%"，不能说"不会泄露"；要声称 0.1% 就得有 3000 个样本。Replay 有四种模式（Exact view 复盘 / Mock 比 Prompt 与模型 / Sandbox 验端到端 / Shadow 验真实分布），写工具默认不能在生产 Replay——否则调试变成事故重放。最后，门禁要分层过滤：冒烟 30 条先筛（70% 的坏改动在这里被否），全量 500 条只跑剩下的 3 次/天，成本从 $150 降到 $54（36%）——这解决的是"太慢 → 被跳过 → 名存实亡"这个真实矛盾。而 Anthropic 把评测分成 capability（新能力）与 regression（不退化），它们的基线不同，必须分开卡。

  • 两类卡口（**统计阈值 vs 绝对红线**）
  • 红线不接受平均与阈值
  • **阈值必须匹配分辨率**（200 条 SE 2.1%，阈值 2% → 32% 误报）
  • 放宽到 2 SE 或把集合做到 900 条
  • **三倍法则**（0
  • 1000 → 上界 0.3%）
  • 要 0.1% 就需 3000 样本
  • Replay 四模式（Exact
  • Mock
  • Sandbox
  • Shadow）
  • **写工具默认不能生产 Replay**
  • 分层过滤（$150 → $54）
  • **capability vs regression（基线不同）**
  • 报样本量与置信区间，小波动别过度解释

主线：门禁的目标不是"卡得严"，是"每次变更都有一次可信的判断"。 太严 → 频繁误报 → 团队学会绕过 → 门禁失效；太松 → 退化上线。所以阈值是一个统计决策，"红线"则根本不是在讨论阈值——它在讨论"这件事能不能发生"。

1. 模型输出非确定，CI 怎么做？

① 看 pass^k 而不是单次（[[母题-E1-评测集设计与pass^k]]：0.9 的单次、pass^5 只有 59%）② 固定环境 fixture 与随机种子（[[母题-A8-动态计划下的可靠执行]] 的"可重置环境"）③ 门禁报"通过率 + 置信区间"，不是"这一次过没过"④ Mock replay 隔离变量，让比较只受一个因素影响。

2. 门禁该卡哪些指标，阈值怎么定？

红线（越权、未确认副作用、跨租户泄露）必须为 0；统计阈值（成功率、P95、成本、新能力最低线）按评测集分辨率定。而且这两类要分开报。

3. 单步指标好但端到端差，为什么？

可能的原因有三类：① 错误会累积（每步 95%，10 步就是 60%）② 优化某个子指标伤害了总目标（典型：召回更多文档提高 Recall，但上下文噪声增加让最终正确率下降——[[母题-G5-RAG评测与幻觉率]]）③ 评测口径不一致（单步用 Mock、端到端用 Sandbox，两者的环境不同）。"错误会累积"这条原文明确点过。

4. 新模型要不要切？

同一套 holdout 上比三件事：pass^k、P95 延迟、单任务成本；而且要重跑消融（prompt 是针对旧模型写的，[[母题-C3-Prompt版本管理与回归]]、[[母题-C5-模型选型与降级三角]]）。

5. 怎么保证 Replay 是确定的？

Mock replay 固定了工具结果，所以剩下的变量只有模型和 Prompt；Sandbox replay 要保证环境 fixture 可重置（否则两次运行的初始状态不同，结果没法比）。
