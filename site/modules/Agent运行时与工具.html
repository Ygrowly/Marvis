锚点

projects/RuleArena/

  • 用在哪：显式 FSM 编排（准备 → 取证 → 各角色审查 → 合并 → 确定性验证 → 人工确认 → 完成）；Thread/Run/Step/Checkpoint/Artifact/Event 数据模型；每个步骤记录 Prompt/Model/Tool/Rule 版本
  • 解决什么问题：高风险修复发布前 interrupt；从任一步 fork 比较不同策略；Replay 默认使用记录的工具结果
  • 踩过的坑：一开始想过用 LangGraph 的自由编排，最后没用——它的控制流由框架决定，而这个项目的卖点恰恰是「流程确定性」：发布门禁的每一步都必须可复现、可审计，裁决不能落在一个模型驱动的调度器手里。用自由编排等于把「可证明」换成了「大概率」。
  • 决策与取舍：三种终止原因必须各占一个码——completed_verified（结果通过验证）/ budget_exhausted（预算耗尽）/ unrecoverable_error（证据冲突等不可恢复）。合成一个「失败了」会毁掉归因：预算耗尽说明任务太难或预算太紧，该调参；证据冲突说明规则或 Oracle 有问题，该查设计。终止原因是 Eval 的输入，不是一个日志字段。
  • 对应母题：【A4】【A8】
锚点

projects/EnergyOps/

  • 用在哪：Hook 链 + R0/R1/R2 风险分级（这是简历最硬的一条 bullet）；30 个 MCP 工具封装、6 类 Capability Bundle
  • 解决什么问题：Agent 在跑，但危险动作被 Hook 拦住
  • 踩过的坑：一开始想用 Prompt 约束代替 Hook——「你已经拿到了审批，可以执行了」。Prompt 是说服，Hook 是强制：模型可能幻觉出一个不存在的审批、或把上一次的审批用到这一次。改成 Before Tool Hook 里校验一次性确认令牌（绑定动作摘要 + 版本 + 期望状态）后，越权才真正归零。
  • 决策与取舍：30 个工具按 6 类业务域分组，不是平铺——平铺的代价是每次请求都要付全部工具定义的 token，且相似命名的工具会互相干扰选择（选择的准确率随工具数下降）。少用且重的（结算、批量）标记延迟加载，用到时才通过工具搜索引入；高频查询类常驻。
  • 对应母题：【A2】【A3】【A6】
锚点

projects/数驭穹图/

  • 用在哪：意图路由（该走 RAG 还是 NL2SQL 还是直接回答）；五层安全
  • 解决什么问题：Agent 的计划依赖领域判断——路由错了后面全错
  • 踩过的坑：意图路由错一步，后面全错——把「本月销售额」路由到 NL2SQL 是对的，但把「为什么下降」也当成一次取数就会漏掉归因。早期没有独立的路由阶段，模型会直接选工具，错误要到结果出来才暴露，且无法归因到哪一环。
  • 决策与取舍：「先判断意图」是把一次不可归因的失败拆成可归因的两段：路由错 → 看路由的输入输出；生成错 → 看 SQL。全给模型则是把两个问题混成一个，出错时只能说「答错了」，说不出错在哪。这也是六阶段链路存在的理由——可归因 > 看起来更聪明。
  • 对应母题：【A2】【A7】
