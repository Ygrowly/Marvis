M8四个隔离级别各解决什么问题；ACID 分别怎么实现草稿 · 待验收单卡 →

四个隔离级别分别解决什么问题？ACID 分别是怎么实现的？

四个隔离级别各挡住哪个并发问题？ACID 四个字母分别靠什么机制实现？

一句话结论：并发三问题是脏读（读到未提交）、不可重复读（同一事务两次读不同值）、幻读（两次范围查询行数不同）；四个级别逐级递进——读未提交（全暴露）→ 读已提交（挡脏读）→ 可重复读（InnoDB 默认，再挡不可重复读，用间隙锁挡幻读）→ 串行化（读也加锁，全挡但并发最差）。ACID 的实现：A 原子性 = undo log；D 持久性 = redo log；I 隔离性 = 锁 + MVCC；C 一致性 = 前三者加上业务约束共同得到的结果。

  • 脏读
  • 不可重复读
  • 幻读
  • RC vs RR
  • 快照读与当前读
  • undo=原子性
  • redo=持久性
  • 锁+MVCC=隔离性
  • **一致性是结果不是机制**

主线：事务 = "一组动作一起成功或一起失败"。 这句话（raw 里的原话）比背 ACID 四个字有用——因为四个字母能从这一句推出来：一起成败需要 undo（能撤销）和 redo（不丢），并发下多个事务同时做，需要锁和 MVCC 分工，最后整体表现出"一致"。

原理分解

一、三个并发问题（先分清，级别才有的放矢）

问题定义例子
脏读读到了别的事务还没提交的数据（它可能回滚）读到 status='DONE'，但那个事务回滚了
不可重复读同一事务内两次读同一行结果不同（中间有人改了并提交）先读余额 100，再读变 80
幻读同一事务内两次范围查询返回的行数不同（中间有人插入）先查到 10 条，再查变 11 条

三者区别一句话：脏读关于"未提交"，不可重复读关于"同一行被改"，幻读关于"行数变化"。

二、四个级别逐级递进

级别挡住没挡住
读未提交 RU——全都可能发生（读未提交数据）
读已提交 RC脏读不可重复读、幻读
可重复读 RR（InnoDB 默认）脏读、不可重复读幻读（InnoDB 靠间隙锁挡住了大部分，见下）
串行化全部——（读也加锁，并发最差）

InnoDB 为什么默认 RR：历史原因（早期 RC 在复制场景下可能出现主从不一致），但更本质的是 RR + MVCC + 间隙锁的组合在"一致性"与"并发"之间取了一个工程上很划算的平衡。面试时能说"默认 RR 是历史 + 权衡，不是唯一正确"就比死记强。

三、RR 下幻读怎么挡住（一半靠 MVCC，一半靠锁）

这是本题最容易说错的地方。RR 并不是"完全解决幻读"：

  • 快照读（普通 SELECT）：靠 MVCC——事务开始时定住快照，后面就算别人插入并提交，快照读也看不到 → 不会幻读；
  • 当前读（SELECT ... FOR UPDATE、UPDATE、DELETE）：必须读最新版本，MVCC 帮不上 → 靠 next-key lock（记录锁 + 间隙锁） 锁住范围，阻止别人在范围内插入 → 也不幻读。

所以准确说法是：InnoDB 的 RR 在"快照读"下靠 MVCC、在"当前读"下靠 next-key lock，两种读都不幻读——但两种读混用的场景仍可能出现"看起来像幻读"的现象（先用快照读看到 10 行，再 UPDATE 时行数变了，因为当前读看到了新数据）。这个细节能讲清，说明真的理解了两套机制。

四、ACID 逐条对应机制（本题核心）

字母靠什么实现一句话
A 原子性undo log改错了/回滚了，用 undo 恢复原状——"改之前的备份"
D 持久性redo log提交过但数据页没落盘，崩溃后用 redo 重放补上
I 隔离性锁 + MVCC写写用锁排队，读写靠 MVCC 不互相堵
C 一致性前三者 + 约束 + 业务校验它不是独立机制，是结果

C 那一行必须展开说：一致性 = 事务把数据库从一个合法状态带到另一个合法状态。它需要：A 保证这组动作要么全做要么全不做、D 保证不丢、I 保证并发下互相看不见对方的中间状态、再加上数据库约束（唯一/外键/CHECK）和业务校验。所以"一致性靠什么实现"的标准答案是"前三者共同作用 + 约束"，而不是某一个组件。

这个结构可以直接迁移：RuleArena 的幂等设计里"业务校验 + 数据库约束都要有"（P19）是同一句话在另一处的重述——业务校验给清晰错误，约束防并发穿透，一致性是两者加事务共同的结果。

五、raw 里那句核心（值得记住）

事务保证一起成败，锁保证修改别打架，MVCC 保证读写别互相堵死。

三句对应三块：undo（一起成败的一部分）+ redo（不丢）、锁（写写）、MVCC（读写）。背下这句，整个主线三的骨架就有了。

M9MVCC 怎么实现；RR 与 RC 生成 ReadView 的时机差在哪；幻读怎么解决草稿 · 待验收单卡 →

MVCC 怎么实现？RR 与 RC 生成 ReadView 的时机差在哪？幻读到底怎么解决？

RR 下为什么"两次一样的 SELECT 结果一样"？这个快照是什么时候定的？和 PG 的实现差在哪？

一句话结论：MVCC = 多版本 + ReadView。InnoDB 的旧版本存在 undo log 版本链里（每行带 trx_id 事务 ID 和 roll_pointer 指向旧版本），读的时候用一个 ReadView（记录生成时刻的活跃事务列表 + 低水位/高水位）沿着版本链找第一个对自己可见的版本。RC 与 RR 的唯一差别是 ReadView 的生成时机：RC 每条语句生成一次，RR 整个事务第一次快照读时生成一次——这一个时机差异，就是"可重复读"的全部实现。

  • undo 版本链
  • trx_id
  • roll_pointer
  • ReadView
  • m_ids
  • 低水位
  • 高水位
  • **RC 每语句 vs RR 每事务**
  • 快照读 vs 当前读
  • 幻读一半靠 MVCC 一半靠锁

主线："可见性"是按快照判定的，而快照的粒度由隔离级别决定。 这一句同时解释了 MySQL 的 RC/RR 差别（P8）和 PG 的语句/事务快照差别——两边机制不同，但"快照决定可见性"这条原理完全一致。

原理分解

一、为什么需要多版本（raw 里那句最实在的解释）

如果所有读都去抢锁，系统并发会很差。MVCC 的核心价值：

普通查询走快照读，读一个一致版本，而不是非得去抢当前正在被别人改的那份数据。

raw 里把它压成两句话：当前读偏"我要最新，还可能要加锁"；快照读偏"我要一个一致版本，别跟写全撞上"。

二、版本链的结构

每一行数据带着两个隐藏字段：

字段含义
trx_id最近一次修改（插入/更新）它的事务 ID
roll_pointer指向 undo log 里上一个版本

于是一行数据的所有历史版本通过 roll_pointer 串成一条链（存在 undo log 里）：

当前版本 (trx_id=105) → 旧版本 (trx_id=98) → 更旧 (trx_id=90) → ...

注意与 PG 的对照（这里是两边最容易说反的地方）：MySQL 的旧版本在 undo log 里，数据页上只有当前版本；PG 的旧版本直接留在堆里。这决定了两边回收方式的差别（MySQL purge 线程自动清 undo；PG 靠 VACUUM，P13）。

三、ReadView：可见性怎么判

ReadView 里关键是这几样：

字段含义
m_ids生成 ReadView 时还活跃（未提交）的事务 ID 列表
min_trx_idm_ids 里最小的（低水位）
max_trx_id下一个将分配的事务 ID（高水位）
creator_trx_id当前事务自己的 ID

对某个版本的 trx_id，判定规则（简化）：

trx_id == 自己              → 可见（自己改的当然看得见）
trx_id <  min_trx_id        → 可见（生成快照前已提交）
trx_id >= max_trx_id        → 不可见（快照之后才开始的事务）
min_trx_id <= trx_id < max_trx_id
    在 m_ids 里（当时还没提交）→ 不可见 → 沿 roll_pointer 找更旧版本
    不在（当时已提交）         → 可见

不可见就顺着 roll_pointer 往前找，直到找到一个可见的版本——这就是"快照读"的全部实现。

四、RC 与 RR：只差一个时机

ReadView 生成时机后果
RC每条 SELECT 语句都生成一个新的能看到别人刚提交的 → 不可重复读
RR整个事务第一次快照读时生成一次，之后复用整个事务看到同一份 → 可重复读

这就是"可重复读"的全部实现——不是靠锁，是靠"快照不再刷新"。 理解了这一点，四个隔离级别的行为都能自己推出来，不用背。

五、快照读 vs 当前读（幻读的真相）

什么操作用什么
快照读普通 SELECTMVCC + ReadView（不加锁）
当前读SELECT ... FOR UPDATE / UPDATE / DELETE / INSERT读最新版本 + 加锁（X 锁 / 间隙锁，M10）

所以幻读的准确说法是：

  • 快照读下：RR 的快照不变，看不到后来插入的行 → 不幻读；
  • 当前读下：必须读最新版本，MVCC 帮不上 → 靠 next-key lock 锁住范围，阻止别人插入 → 也不幻读；
  • 两种读混用时：先用快照读看到 10 行，再 UPDATE（当前读）时行数变了——这是"看起来像幻读"的正常现象，不是 bug。

答"RR 完全解决了幻读"是错的；答"InnoDB RR 下两种读都不幻读，机制不同"才是对的。

M10行锁、间隙锁、next-key lock 各锁什么；死锁怎么来、怎么排查草稿 · 待验收单卡 →

行锁、间隙锁、next-key lock 各锁什么？锁为什么会变大？死锁怎么来、怎么排查、怎么避免？

WHERE status='PENDING' FOR UPDATE 明明只想锁几行，为什么插入被卡住了？多个 Worker 还互相锁住了。为什么？

一句话结论：三种锁——Record Lock 锁记录本身；Gap Lock 锁"记录之间的区间"，阻止插入；Next-Key Lock = 记录 + 前面的间隙（RR 下的默认单位）。锁变大的原因只有一个：它锁的是"扫描到的索引范围"，不是"WHERE 里写的行"——所以非唯一索引命中、索引路径不精确、范围条件（<= now()、BETWEEN、非唯一状态过滤）都会把锁扩大。死锁 = 多个事务拿锁顺序不一致形成循环等待；排查用 SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK；避免靠精确索引 + 短事务 + 一致顺序 +（队列场景）SKIP LOCKED。

  • Record
  • Gap
  • Next-Key Lock
  • **锁的是扫描到的索引范围**
  • 范围条件高危
  • 死锁=顺序不一致
  • `SKIP LOCKED`
  • `SHOW ENGINE INNODB STATUS`
  • 统一加锁顺序

主线：锁冲突、死锁，追到根上不是"数据库不行"，而是「查询路径、事务边界、资源访问顺序」没设计好。（raw 原话）——所以解法永远先在这三件事上，而不是换数据库或调参数。

原理分解

一、三种锁：各锁什么

锁锁什么谁在用
Record Lock索引记录本身等值命中唯一索引
Gap Lock两条记录之间的"区间"（不含记录本身），阻止往这个区间插入RR 下的范围查询
Next-Key Lock记录 + 它前面的间隙（左开右闭），RR 下的默认加锁单位RR 下的当前读

关键理解：Gap Lock 的存在理由就是"防幻读"——锁住区间，别人插不进来，下次查询行数就不会变。而它也是"锁大"的元凶：为了防幻读，它锁住的比你要的行多。

另一个必须知道的边界：间隙锁只在 RR（及串行化）下存在；RC 下没有间隙锁，所以 RC 下不会"因为 gap 锁把插入卡住"，但会有幻读。隔离级别决定了锁的行为——这把 M8 和 M10 连起来了。

还有一个精度细节：锁是加在索引上的。如果 WHERE 条件没有可用索引，InnoDB 只能全表扫描并把所有记录都锁住（相当于锁全表）——"什么时候锁全表"的答案就是这里。

二、锁为什么会变大（raw 的三条 + 原理）

原因例子
① 不是唯一索引精确命中WHERE id=? FOR UPDATE（唯一索引等值）锁得小；换成状态扫描就大了
② 索引路径不精确没走到合适的索引，扫描了更多记录，锁跟着变大
③ 范围条件天然高危<= now()、BETWEEN、非唯一状态过滤——带出 gap / next-key lock

原理一句话（本题题眼）：

它锁的不是最终返回给你的那几行，而是扫描到的索引范围。

所以线上的典型现象：明明只查了几条，插入却被卡住——因为被锁住的是"扫过的那些索引记录 + 它们之间的间隙"，新插入的行恰好落在某个间隙里。

三、死锁怎么来

死锁不是"数据库坏了"，而是多个事务拿锁顺序不一致，形成循环等待：

事务 A：先锁任务 1，再锁任务 2
事务 B：先锁任务 2，再锁任务 1
   ↓
A 等 B 释放 2，B 等 A 释放 1 → 循环等待

InnoDB 会自动检测死锁并回滚其中代价较小的事务（不是永远等下去）——所以死锁的表现通常是"某次请求报 Deadlock found"，而不是系统卡死。

四、怎么避免（raw 的五条 + 一条补充）

① 让查询命中更精确的索引          → 缩小锁范围（本题第一条原理的直接应用）
② 缩小事务范围                    → 持锁时间短，窗口小
③ 避免长时间持锁                  → 事务里不放 RPC / 网络 / 复杂计算（M13）
④ 多个事务按一致顺序访问资源       → 比如总是按主键升序更新，消除循环等待
⑤ 队列式场景用 SKIP LOCKED        → 直接跳过被别人锁住的行，不排队

SKIP LOCKED（8.0+）值得专门讲：任务抢占场景里，多个 Worker 都在捞同一批任务，传统做法是排队等锁；FOR UPDATE SKIP LOCKED 让后来者直接跳过被锁住的行——"别人在处理的任务我不碰"，天然适合队列。这条是"用查询语义替代等待"的一个漂亮例子，也是 raw 里点名的思路。

五、怎么排查

工具看什么
SHOW ENGINE INNODB STATUSLATEST DETECTED DEADLOCK 段：两个事务各自持有什么锁、在等什么锁、执行到了哪条 SQL——死锁分析的起点
performance_schema.data_locks / data_lock_waits当前正在持有的锁与等待关系（实时排查阻塞）
information_schema.innodb_trx正在运行的事务（找长事务，M13）

排查的正确顺序：先看是谁在等谁（锁等待），再回溯事务的加锁顺序——最终答案几乎总是"顺序不一致"或"事务太大"（回到核心不变量）。
