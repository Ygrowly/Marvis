M8四个隔离级别各解决什么问题；ACID 分别怎么实现草稿 · 待验收单卡 →

四个隔离级别分别解决什么问题？ACID 分别是怎么实现的？

四个隔离级别各挡住哪个并发问题？ACID 四个字母分别靠什么机制实现？

一句话结论：事务就是"一组动作一起成败"。A 靠 undo（前镜像）、D 靠 redo（后镜像）、I 靠锁管写写 + MVCC 管读写、C 是前三者加约束共同得到的结果——它不是独立机制。 并发三问题是脏读、不可重复读、幻读，四个隔离级别逐级挡住它们，越严格并发越低。InnoDB 默认 RR，靠 MVCC 挡快照读的幻读、靠间隙锁挡当前读的幻读。

  • 一起成败
  • 撤销看前镜像、恢复看后镜像
  • undo=A、redo=D、锁+MVCC=I
  • 一致性是结果不是机制
  • 脏读=未提交·不可重复读=同一行·幻读=行数
  • RC 挡脏读、RR 再加不可重复读
  • 快照读 vs 当前读
  • 默认 RR 是历史+权衡
  • MySQL RR vs PG RC

主线：事务 = "一组动作一起成功或一起失败"。 ACID 不是四条并列的规矩，而是从这一句推出来的四步：要能撤销（undo）、要能不丢（redo）、并发下要分工（锁管写写、MVCC 管读写）、最后整体表现为一致。

1. 为什么 A 是 undo、D 是 redo，不能反过来？

undo 记前镜像，所以能撤销；redo 记后镜像，所以能重放。撤销要把数据往回变，重放要把数据往前推。一句话：撤销看前面，恢复看后面。

2. RR 下两个事务同时 UPDATE 同一行会怎样？

排队等锁（MySQL 的哲学是"冲突就等"），不是报错。如果等待成环就死锁，InnoDB 会检测并回滚代价较小的那个事务（M10）。

3. 串行化下还死锁吗？

更容易。读也加 S 锁，锁的持有面更大、成环机会更多。缓解靠统一加锁顺序 + 缩短事务（M10）。

4. 为什么报表查询在 MySQL 下不会互相锁？

普通 SELECT 是快照读，不加锁。但它会持有 ReadView，长查询因此变成"长事务"的一种，拖住 undo 回收（[[母题-M13-长事务为什么危险]]）。

正本：wiki/topics/MySQL/母题-M8-隔离级别与ACID.md

M9MVCC 怎么实现；RR 与 RC 生成 ReadView 的时机差在哪；幻读怎么解决草稿 · 待验收单卡 →

MVCC 怎么实现？RR 与 RC 生成 ReadView 的时机差在哪？幻读到底怎么解决？

RR 下为什么"两次一样的 SELECT 结果一样"？这个快照是什么时候定的？和 PostgreSQL 的实现差在哪？

一句话结论：MVCC = 多版本 + 可见性判定。InnoDB 让数据页只留最新版本，旧版本写进 undo log、靠每行的 roll_pointer 串成版本链；读的时候拿一个 ReadView（记录"拍快照那一刻还活跃的事务名单"）沿链往回找第一个可见的版本。RC 与 RR 的唯一差别是 ReadView 生成时机——RC 每条语句重新生成，RR 整个事务生成一次，这就是"可重复读"的全部实现。

  • 不复制数据
  • undo 存前镜像 → 天然就是上一个版本
  • trx_id + roll_pointer
  • 版本链长度受长事务牵制
  • ReadView = 活跃名单
  • m_ids 是为了区分"开始得早"和"已提交"
  • RC 每语句 vs RR 每事务
  • 快照读不加锁、当前读才加锁
  • 幻读一半靠快照一半靠间隙锁

主线："可见性"是按快照判定的，而快照的粒度（每条语句 / 整个事务）由隔离级别决定。 这一条同时解释了 MySQL 的 RC/RR 差别和 PG 的语句/事务快照差别——两边实现完全不同，但"快照决定可见性"这条原理一致。

1. m_ids 为什么必需？

因为"开始得早"不等于"已提交"：事务可能在你拍快照前就开始了、拍完之后才提交。它的 trx_id 比高水位小，光看水位判断不出来。

2. undo log 什么时候能删？

当没有任何快照还需要它时，由 purge 线程清理。所以长事务会让 purge 推不动（M13）。

3. MVCC 和两阶段提交有关系吗？

没有直接关系。 两阶段提交解决的是 redo 与 binlog 的一致性（M11）；MVCC 解决的是读的一致性。两件事，别混在一起答。

4. UPDATE 影响行数和预期不符，是 MVCC 出错了吗？

不是。UPDATE 是当前读，看到的是最新数据；和之前的快照读不一致是正常的。

5. 为什么说"RR 完全解决了幻读"不准确？

快照读靠快照、当前读靠间隙锁，两种读都不幻读，但混用时会出现"看起来像幻读"。

正本：wiki/topics/MySQL/母题-M9-MVCC.md

M10行锁、间隙锁、next-key lock 各锁什么；死锁怎么来、怎么排查草稿 · 待验收单卡 →

行锁、间隙锁、next-key lock 各锁什么？锁为什么会变大？死锁怎么来、怎么排查、怎么避免？

WHERE status='PENDING' FOR UPDATE 明明只想锁几行，为什么插入被卡住了？多个 Worker 还互相锁住了。为什么？

一句话结论：三种锁——Record Lock 锁记录本身；Gap Lock 锁记录之间的空隙（防插入，是防幻读的必要手段）；Next-Key Lock 把两者合起来，是 RR 下的默认单位。锁加在索引记录上，所以锁的范围等于"扫描到的索引范围"，不是"WHERE 里写的行"——非唯一索引、范围条件、缺少索引都会把锁放大到万级甚至全表。死锁 = 多个事务的加锁顺序不一致形成环，InnoDB 会检测并回滚代价小的事务。避免靠精确索引 + 短事务 + 一致顺序 +（队列场景）SKIP LOCKED。

  • 只有在当前读才谈锁
  • 锁加在索引记录上
  • Gap Lock 是为防插入
  • Next-Key = 间隙 + 记录
  • 间隙锁只在 RR 有
  • 锁范围 = 扫描范围
  • 无索引 → 锁全表
  • 死锁 = 顺序不一致不是锁太多
  • 回滚代价小的那个
  • SKIP LOCKED 把排队变分流
  • SHOW ENGINE INNODB STATUS

主线：锁冲突和死锁追到根上，不是"数据库不行"，而是「查询路径、事务边界、资源访问顺序」没设计好。（raw 原话）——所以解法永远先在这三件事上，不在换数据库或调参数。

1. 为什么唯一索引等值命中不产生间隙锁？

精确命中后，没有"下一个需要保护的间隙"：唯一约束已经保证了不会再有相同的键插进来。所以这是锁范围最小的情形——这正好呼应了 M5"主键要精确"。

2. 为什么这个场景你项目里没用 FOR UPDATE？

（RuleArena 的取舍）项目文档给的理由是「权威性」不是「频率」：04 §15 原话「MVP 优先业务唯一键 + 条件更新」，Q7 原话「锁可以降低竞争，但不能成为资金正确性的唯一保证……只有真实高竞争时再评估锁」。而且认领的判据是「状态是否匹配」（PG 侧还有状态回流的问题），用 FOR UPDATE 会把锁等待、死锁风险与排队三样成本一起带进来；条件更新（乐观锁，M16）一次原子写解决，重复执行第二次影响 0 行。 这正是"锁机制"决定工程选择的实例。注意别说成「完全不用锁」——文档 04 §12 给的是「在事务中锁定订单行 或 使用乐观版本条件更新」。

3. RR 下 SELECT 不加锁，那为什么还会有死锁？

死锁来自当前读（UPDATE / FOR UPDATE）和写操作的加锁顺序，与快照读无关。

4. 间隙锁能不能关掉？

【取舍】可以（把隔离级别降到 RC），代价是接受幻读。这是"用正确性换并发"的又一次交换（M8 的谱系）。

正本：wiki/topics/MySQL/母题-M10-锁与死锁.md
