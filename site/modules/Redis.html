锚点

projects/EnergyOps/

  • 用在哪：缓存加速读取（园区/表/指标的元数据）；写路径用 Outbox 而不是"提交完顺手删 Redis"
  • 解决什么问题：缓存是派生数据，DB 才是权威 —— 这条定位决定了"不一致时以谁为准"
  • 踩过的坑：【待填 —— 提示：缓存里存的是"元数据"还是"业务事实"？两者对一致性的要求完全不同。】
  • 决策与取舍：【待填 —— 提示：为什么用 Outbox 而不是"提交完顺手删 Redis"？（关键：PG 提交与 Redis 删除不可能构成同一个 ACID 事务）】
  • 对应母题：【R3】
锚点

projects/数驭穹图/

  • 用在哪：权限与语义层的缓存（口径、指标、粒度这类读多写少的数据）；限流与短期去重
  • 解决什么问题：权限相关的数据能不能缓存？ —— 能，但必须有明确的失效路径（权限变了要能立刻失效，否则是安全问题不是性能问题）
  • 踩过的坑：【待填 —— 提示：权限相关的缓存，改权限时怎么保证立刻生效？TTL 够吗？】
  • 决策与取舍：【待填 —— 提示：哪些数据可以容忍几分钟的不一致，哪些一秒都不能容忍？这个分界线是怎么划的？】
  • 对应母题：【R3】
锚点

projects/RuleArena/

  • 用在哪：短期去重 / 限流 / lease 归属（study/09 明确写了"Redis 用 Cache Aside、限流或短期去重，但不把缓存当最终事实"）
  • 解决什么问题：动作有副作用，所以 Redis 只能做"辅助判断"，不能做"最终裁决" —— 最终裁决必须是 DB 的约束或条件更新
  • 踩过的坑：【待填 —— 提示：如果用 Redis 做"任务是否已处理"的判断，Redis 挂了会怎样？（会不会重复处理）】
  • 决策与取舍：【待填 —— 提示：为什么"短期状态"可以放 Redis，"任务状态"不行？】
