19必背**[[母题-L3-分布式锁与fencing-token]]**

这道题属于母题 L3（并发与锁 模块） · 分布式锁：三种实现、三大失效场景与 fencing token · 下面挂它的完整回答（学的时候看）

实测 316 字 · 按 4 字/秒折算约 79 秒（秒数是估算，字数才是实测）

单机 mutex 的共享状态只在进程内可见；跨机器互斥要把锁状态放到一个共享的地方。三种实现各有代价：Redis（SET ... NX PX 一条原子命令 + 释放要校验值；弱点是主从异步复制，切换会丢锁）、数据库（唯一约束 / 带条件更新，不引入新组件但把锁争用压在数据库上）、ZooKeeper / etcd（临时顺序节点 / 租约 + 单调 revision，语义最干净但要维护一套强一致系统）。

它们的共同弱点来自同一个根因：锁服务的判断（按时间）与客户端的事实（是不是还在跑）会脱节——GC 停顿、时钟漂移、网络分区都会产生"两个持有者"，而 TTL 没有安全值（短了双持有者、长了可用性差，且"最长停顿"无上界）。看门狗续期只是缓解，不是根治（续期本身也会停）。

分层要点追问深挖时用

  • 结论：三种实现各有代价；共同弱点是时间判断与客户端事实脱节，根治靠 fencing token；先问"互斥还是不重复"。
  • 推导链：共享状态 → 三种实现 → 时间 vs 事实脱节（GC/时钟/分区）→ TTL 无安全值 → 安全性搬到资源侧 → 幂等可能比锁更划算。
  • 量化：没有安全的 TTL 值（"最长停顿"无上界）。
  • 边界与常见误解："加锁时间设长就安全"×；"Redis 锁万无一失"×（主从切换丢锁）；幂等常常比锁更便宜，RuleArena 就是例子。

项目映射 把这个模块挂到真实经历上

锚点

projects/EnergyOps/

  • 用在哪：缓存加速读取（园区/表/指标的元数据）；写路径用 Outbox 而不是"提交完顺手删 Redis"
  • 解决什么问题：缓存是派生数据，DB 才是权威 —— 这条定位决定了"不一致时以谁为准"
  • 踩过的坑：把聚合结果当缓存读——缓存里该放的是元数据（园区/表/指标定义），不是业务事实（用量、账单）。元数据陈旧最多是查询慢一点；业务事实陈旧会让页面和月账单出现两套数字，而结算必须只有一个权威口径
  • 决策与取舍：为什么用 Outbox 而不是「提交完顺手删 Redis」——因为 PG 提交与 Redis 删除不可能构成同一个 ACID 事务。先删缓存再提交，提交失败就留下脏缓存；先提交再删，删除失败就留下更久的脏缓存。Outbox 把「删除」变成事务内可提交的一条事实，再由异步消费者执行，失败可重试、可审计
  • 对应母题：【R3】
锚点

projects/数驭穹图/

  • 用在哪：权限与语义层的缓存（口径、指标、粒度这类读多写少的数据）；限流与短期去重
  • 解决什么问题：权限相关的数据能不能缓存？ —— 能，但必须有明确的失效路径（权限变了要能立刻失效，否则是安全问题不是性能问题）
  • 踩过的坑：权限数据一进缓存，撤权就不再是即时的——TTL 没到期前，已经失去权限的人照样能命中。这是安全问题，不是性能问题，不能用「缓存总会过期」搪塞
  • 决策与取舍：分界线是「陈旧的后果是慢还是错」。口径、粒度、常用指标这类，陈旧几分钟只是体验问题 → 可缓存；行级权限、租户归属、字段可见性一秒都不能陈旧 → 所以它们不作为缓存值，而是作为召回前的过滤条件每次重新求值（[[母题-G2-向量与关键词的混合检索]] 的「权限必须在召回前生效」在缓存侧的同一件事）
  • 对应母题：【R3】
锚点

projects/RuleArena/

  • 用在哪：短期去重 / 限流 / lease 归属（study/09 明确写了"Redis 用 Cache Aside、限流或短期去重，但不把缓存当最终事实"）
  • 解决什么问题：动作有副作用，所以 Redis 只能做"辅助判断"，不能做"最终裁决" —— 最终裁决必须是 DB 的约束或条件更新
  • 踩过的坑：用 Redis 判断「这笔动作做过没有」——Redis 重启、主从切换、或单纯的过期，都会让同一个幂等键被判成「没做过」→ 重复执行副作用。而超时重投在 Agent 场景里是常态，不是异常
  • 决策与取舍：区别在「丢了会怎样」。短期状态（限流计数、去重窗口、Worker lease）丢了最多是多做一次检查，可恢复、可重来 → 放 Redis 划算；任务状态与幂等判断丢了就不知道「做过没有」，这是正确性问题 → 必须落 PG 的唯一约束（[[母题-P19-唯一约束与UPSERT]]）。Redis 只能做辅助判断，不能做最终裁决
  • 对应母题：【R3】
