题目

一个只做 SELECT、什么都没改的事务，挂了两个小时不结束。它会带来什么问题？

三 · 面试输出 闭卷口述 60 秒，再看结论

长事务为什么危险？不只是持锁久——它到底坏了什么？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：raw 里这句"很多人知道不太好，但说不清楚到底坏在哪"就是这道题的价值——它考的是你能不能从 MVCC 机制推导出长事务的完整危害链，而不是背一句"长事务不好"。而且它有一个反直觉点：只读事务同样危险。 这条和 PG 的 P14 几乎是同构的——两边的机制都指向"长事务按住旧版本不让回收"。

一句话结论 全卡唯一要背的锚点

长事务最可怕的隐患是拖住旧版本数据的清理——MVCC 的普通读依赖 undo 里的旧版本，事务不结束，purge 线程就不敢清那些它还可能要读的版本 → undo 膨胀、历史链越来越长 → 回滚成本更高、快照读沿链回溯更慢、锁持有更久 → 系统整体越来越沉。加上持锁久这一层，两条危害叠加。只读事务同样有害（手动关了 autocommit 忘了提交，是最常见的真实事故形态）。
  • 拖住 undo 清理
  • 历史链变长
  • 回滚成本更高
  • 只读事务也危险
  • autocommit 意外关闭
  • 事务里不放 RPC
  • innodb_trx 监控

卡住时靠这几个词重建整条链。

EnergyOps 的月度结算（跨多表多步，事务边界最容易画大——"事务里不做外部调用"在这里最值钱）；RuleArena 的Worker 长任务（事务只包数据库动作，Checkpoint 之外不做 IO）。方言差异（面试安全底线）：MySQL 长事务 → undo 膨胀 + 持锁久；PG 长事务 → 表膨胀 + 阻塞 VACUUM + 事务 ID 回卷风险（P15）。两边都要"短事务"，但症状与监控指标不同——这是"机制同源、症状不同"的最佳案例。

危害一：拖住旧版本清理（从 MVCC 推导）→ 危害二：持锁久 → 只读事务为什么也危险 → 工程规避清单 → 怎么监控

长事务最可怕的不是"执行久"，而是它会持续占着数据库资源，让整个系统越来越难受。（raw 原话）——它不是"慢"，是"按住资源的柄"。

通过证据：能从 MVCC 推导出"长事务拖住清理"的完整链条，能说出五条规避纪律，并指出只读事务为什么也危险。

讲解

原理分解

一、危害一：拖住旧版本清理（从 M9 直接推导）

M9 讲过：快照读要沿 undo 版本链回溯找可见版本。

关键问题：旧版本什么时候能删？

purge 线程清理 undo 的前提：
   没有任何 ReadView 还需要它
     ↓
而 ReadView 是事务级的（RR 下整个事务一个）
     ↓
所以：一个长事务开着 → 它的 ReadView 一直在 → 链上它之前的旧版本都不能清

于是：

undo 清理跟不上
  → 历史链越来越长
  → 快照读沿链回溯的步数变多（读变慢）
  → 回滚成本更高（要撤销的更多）
  → 系统整体越来越沉

这条链值得完整背下来——它把 M9 的机制变成了 M13 的后果，是"会 MVCC"和"会运维"的分界线。

二、危害二：持锁久

事务里如果有 UPDATE / FOR UPDATE，锁会一直持有到事务结束：

事务越长 → 锁持有越久 → 其他事务排队越久 → 死锁概率越高（M10）

注意这两条危害的来源不同：一条来自 MVCC（对读的影响），一条来自锁（对写的影响）——长事务是两条路同时变坏。

三、只读事务为什么也危险（最容易被忽略）

因为回收看的是 ReadView，不是"这个事务做了什么"：

很多人以为只有写事务才会造成问题。
其实只读事务如果一直不结束，在一致性读场景下，同样可能拖住旧版本清理。

最常见的真实形态（raw 原话）：手动关了 autocommit，跑了一个查询，结果忘了提交或结束。

SET autocommit = 0;
SELECT ...;        -- 开了一个事务（隐式 BEGIN）
-- 然后连接挂着，什么都没做
                   ← 这个事务可能挂好几个小时

这种连接在监控上很不起眼（CPU 低、几乎无查询），但它在按住回收边界。 PG 那边对应的形态是 idle in transaction（P14）——两边是同一类事故，只是监控指标不同。

四、工程规避清单（raw 的五条，全部照背）

① 事务里只放必须的数据库动作
② 不要把外部 RPC / 网络调用放进事务
③ 不要把复杂业务计算放进事务
④ 批量更新尽量分批做
⑤ 大查询和导出要格外注意事务边界

第 ② ③ 条是同一类错误：把"外部系统的响应时间"绑进了"事务的持有时间"——外部一抖，事务就长。RuleArena 里"事务只包数据库操作、Checkpoint 不当业务事实"是同一个纪律（P19 的对照）。

五、怎么监控

看什么用途
information_schema.innodb_trx 的 trx_started运行时间最长的事务——回收边界的直接代理
SHOW PROCESSLIST长时间处于 Sleep 状态的连接（可能是 idle in transaction 的 MySQL 版）
undo 表空间大小 / 历史链长度相关指标膨胀程度

面试加分点：能说出"我盯的是最老事务的 trx_started，因为回收边界由最老的 ReadView 决定"——这和 PG 侧"盯最老事务的 xmin"（P14）是同一句话，两套数据库，同一条原理。
