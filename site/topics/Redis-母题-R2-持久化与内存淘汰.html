题目

Redis 有哪几种持久化方式？RDB 和 AOF 的区别是什么、该怎么选？ AOF 为什么要重写？过期删除策略和内存淘汰策略有什么区别？内存满了 Redis 会怎么样？

一 · 教材 从前提推到结论，不需要先会

1. 前提：先把三件「数据消失」的事拆开

面试里这三个问题经常被混着问，但它们触发条件完全不同：

场景什么时候发生谁会消失由什么机制管
持久化进程挂了 / 机器断电整个内存RDB / AOF
过期删除某个 key 的 TTL 到了那个 key惰性删除 + 定期删除
内存淘汰内存到达 maxmemory被挑中的若干 key8 种淘汰策略

先把它们分开，后面就不会答串。 一句话区分后两个：

过期删除问的是「这个 key 该死了吗」（时间维度）；内存淘汰问的是「必须谁死」（空间维度）。

【推导】为什么必须分开？因为触发源不同：前者由数据自己的属性（有没有设 TTL、到没到期）决定；后者由实例的状态（内存够不够）决定。一个 key 完全没用过期时间，也可能被淘汰；一个设了 TTL 的 key，也可能在被淘汰前就自然过期。

2. 持久化：RDB 与 AOF

2.1 两条路线的本质区别【推导】

RDBAOF
记什么结果（某一时刻的全部数据）过程（每条写命令）
文件里是什么二进制数据命令文本流
恢复怎么做直接把数据加载进内存逐条重放命令

看清这一行，后面所有差异都能推出来：

指标RDBAOF为什么
文件大小小大命令流比数据冗余（改 100 次只留 1 个结果 vs 记 100 次）
恢复速度快慢直接加载 vs 要重放
丢失窗口丢两次快照之间最多 1 秒（everysec）快照只在那一刻全 vs 每条都在

【取舍】这两条路线没有优劣，只有你更怕哪个：怕丢数据选 AOF，怕恢复慢 / 文件大选 RDB。生产上通常两个都开——RDB 做冷备份和快速恢复，AOF 保证最多丢 1 秒（4.0 之后还有混合持久化：RDB 全量 + 后续 AOF 增量，写在同一个文件里）。

2.2 AOF 的写回策略：三选一【取舍】

命令执行完只是"写进了 AOF 的内核缓冲区"，什么时候真正落到磁盘由 appendfsync 决定：

策略做法最多丢代价
always每条命令都 fsync几乎不丢性能最差
everysec（默认）每秒 fsync 一次最多 1 秒折中
no交给操作系统决定不确定性能最好

量化一下 always 的代价：SSD 上一次 fsync 约 0.2 毫秒（与 [[母题-M11-三日志与两阶段提交]] 是同一个数）。所以单连接串行提交的理论上限：

1 秒 ÷ 0.2 毫秒 = 5000 条/秒

也就是说 QPS 到 5000 时，光等 fsync 就把 1 秒用满了——还没算执行命令本身的时间。这和 MySQL 里"双一配置下单连接串行提交上限约 5000 TPS"是同一个数量级，因为卡在同一个物理成本上。

【推论】所以生产上选 everysec 不是因为"不重要的数据可以丢"，而是用"最多丢 1 秒"换回整整 1 个数量级的吞吐。

2.3 AOF 为什么要重写【推导】

AOF 记的是过程，所以同一个 key 被改 100 次就留下 100 条命令——但恢复时只有最后一条有意义。

重写的本质：把"记过的所有过程"重新压成"当前的结果"。 它不是压缩算法，是用一次全量快照替换掉整个历史。

重写同样由子进程做（不占主线程），所以它也会 fork——见下一节的代价。

2.4 RDB：save 与 bgsave，以及 fork 的真实代价

命令谁来做后果
save主线程阻塞整个 Redis
bgsavefork 出的子进程主线程继续服务

生产环境一定用 bgsave，但"不阻塞主线程"这个说法只对了一半，有两个代价要讲：

代价一：fork 本身会停一下主线程【事实】。

fork 要复制父进程的页表（不是复制数据），实例越大、页表越长，这一步越久。所以大实例上 fork 是毫秒到数十毫秒级的停顿——不是零。

代价二：写时复制（COW）会让内存涨上去【推导】。

fork 之后父子进程共享同一份物理内存，只有当某一页被写的时候，才复制一份出来。所以：

实例 20GB，快照期间有 30% 的页被修改
→ 每个被写的页都要额外复制一份
→ 峰值内存 ≈ 20GB + 20GB × 30% = 26GB

【取舍】这是 RDB 最容易被忽略的代价：快照期间写越多，内存涨得越多。如果实例已经接近 maxmemory，一次 bgsave 就可能触发淘汰甚至 OOM。这也是为什么大实例上要留出余量（常见做法是让 maxmemory 不超过物理内存的一半到 2/3）。

2.5 一个和 MySQL 相反的细节：为什么可以先执行、后记日志【推导】

raw 里特意加了一句"注意是先执行命令再记日志，不是先写日志再执行"。这和 MySQL 的 WAL（日志先于数据页）方向相反，值得讲清楚。

原因不是"Redis 不严谨"，是它的命令不幂等：

MySQLRedis
日志里记什么数据页的物理/逻辑修改原样的命令（INCR、LPUSH…）
如果日志记了一条其实没执行的命令重放就是"把这页改成目标值"，幂等重放会把 INCR 多算一次——结果就错了
所以顺序必须是日志可以先写命令必须先执行过

【推论】一句话：因为恢复靠"重放命令"，所以日志必须只出现在"确实发生过的命令"。 代价就是 2.2 里那个"最多丢 1 秒"——顺序反过来能换来"不丢"，但会换来"可能算错"，那更不可接受。

顺带澄清一个常见误会：Redis 的 AOF 和 MySQL 的 WAL 目的不同——WAL 是"数据页的后盾"（页可以晚点写），AOF 是"内存的重建脚本"。所以两者在顺序上的选择不同，是目的不同带来的，不是谁更先进。

3. 过期删除：惰性 + 定期

3.1 为什么不能"立即删除"【推导】

最直觉的方案是：给每个 key 定一个闹钟，到点就删。

为什么不行——因为 Redis 是单线程。假设有 100 万个设了 TTL 的 key：

  • 要么维护 100 万个定时器（内存开销巨大，且到期那一刻要处理大批事件）
  • 要么每秒遍历一遍全部 key 检查谁到期（O(n) 遍历 = 卡住所有人）

这是 Redis 的通用约束：任何 O(全量) 的操作都不能放在主线程上。 后面会看到，本节和下一节的设计全都是在躲这一件事。

3.2 惰性删除：不主动删，访问时才检查

做法：不主动检查。有请求来访问某个 key 时，顺手看一眼它过期没，过期了就当它不存在（返回 nil 并删掉）。

  • 好处：零额外 CPU 开销（判断是访问路径上顺手做的）
  • 坏处：一个过期 key 如果一直没人访问，就会一直占着内存

3.3 定期删除：补上一条的漏，但只能抽样

做法：Redis 每秒做 10 次过期检查，每次随机抽 20 个设了 TTL 的 key，删掉其中已过期的。

一轮抽查：20 个
如果其中过期数 > 25%（即 > 5 个）
   → 说明"过期 key 还很多"，继续抽下一轮
直到：过期比例降到 25% 以下
  或：这一轮已经花掉 25 毫秒

两个参数各自在防什么：

参数防的是
25% 水位过期 key 大量堆积（占比高就说明还有一堆没清，不该停）
25ms 上限如果过期 key 特别多，清理会一直循环 → 主线程被它独占

【取舍】定期删除用的是"抽样"而不是"全扫"——它接受"有些过期 key 暂时没被清掉"，换"主线程永远不会被清理工作长时间占住"。

4. 内存淘汰：8 种策略

当内存达到 maxmemory，Redis 必须做选择。策略是两个维度组合出来的：

维度一：在哪个池子里挑？

池子含义风险
noeviction（默认）不淘汰，直接拒绝写入并报错写请求开始失败
volatile-*只在设了 TTL 的 key 里挑见下面的陷阱
allkeys-*在所有 key 里挑可能淘汰掉本来该常驻的数据

维度二：挑谁？（算法）

算法淘汰谁
random随机
ttl最快过期的先走
lru最久没被访问的
lfu访问频率最低的（4.0 新增）

1 + 4 + 3 = 8 种。

4.1 最容易踩的配置陷阱【事实】

配了 volatile-lru，但业务里所有 key 都没设 TTL → 一个都挑不出来，行为等同于 noeviction。

内存满时直接写报错——而报错时你多半不会想到"是淘汰策略选错了"。所以：用 volatile-* 就要求业务真的给缓存设 TTL；否则应该用 allkeys-*。

4.2 LRU 与 LFU 的差别：一个具体场景就够

LRU 的问题：它只看"最近一次访问"，不看"访问了多少次"。

缓存容量 1 万 key，里面是 1 万个真正常用的热数据
某次后台任务批量扫了 10 万条只读一次的数据（全部经过缓存）
→ 这 10 万次访问把「最近访问」的位置全占了
→ 淘汰时按 LRU 挑，会把真正热的 1 万条挤出去

这就是"缓存污染"：一次性的冷数据把热数据挤走了。LFU 用"访问次数"计数来抵抗它——只访问过一次的数据，频率就是 1，不会比长期被访问的数据更"值得留"。

LFU 自己的代价：计数需要内存（每个 key 一个计数器），而且旧的热数据会一直占着位置（除非加衰减）。所以它不是 LRU 的升级版，是另一个取舍。

另外，Redis 的 LRU 是"近似 LRU"【事实】：它随机采样 N 个 key（默认 5），淘汰其中"最久没用"的那个。为什么不做精确 LRU？——精确 LRU 要维护一条全量链表，每次访问都要移动节点，内存和操作开销都上来了。又是同一个思路：用近似的抽样，换掉一个 O(n) 或重开销的结构。

5. 复制与集群：它们为什么也不能保证「不丢」

持久化管的是"进程重启后能不能恢复"。但机器直接挂了（磁盘也在的那台机器没了），就需要另一台机器上有数据。这就是复制要解决的问题——它同样有窗口。

5.1 主从复制是异步的，所以有窗口【推导】

客户端 → 主库：写入
主库：写入成功，立刻返回 OK        ← 此刻还没同步到从库
     ↓ 复制是异步的，从库晚一点才收到
主库突然宕机
   ↓ 哨兵把从库提成新主库
新主库上没有刚才那条写入 → 客户端以为写成功了，数据却没了

【推论】很多"Redis 丢数据"的真实原因不是持久化没配，而是这里——持久化保证的是"同一台机器重启能恢复"，故障转移走的是另一条路，那条路上没同步的部分就丢了。

要缩小这个窗口：可以用 WAIT 主动等 N 个从库确认（但会变慢，等于把异步改成半同步）；或者接受它——因为 Redis 通常是派生数据，丢了能从权威库重建（[[母题-R3-缓存一致性与三类事故]] 的地基）。

5.2 集群解决的是容量，不是"不丢"【事实】

机制解决什么不解决什么
主从 + 哨兵单点故障（主库挂了自动切换）异步复制的窗口（5.1）
集群（Cluster）容量与吞吐（把 key 分片到多节点）不丢——分片是"分成几份"，不是"每份都有副本"

一个常见误答："用了集群所以数据更安全。" —— 集群做的是分片（每片只存一部分），提高的是容量和并发，安全性来自每片自己的主从副本。

5.3 一个容易答反的细节：从库不主动删过期 key【事实】

从库不会自己删过期 key，而是等主库发来 DEL 再删。

为什么：如果从库自己删，主从就会不一致——主库可能还没删（因为它是等惰性/定期删除，时机由访问和抽样决定）。所以主从之间"删不删"的决定权必须只在主库，从库照做。（代价：从库上可能读到"其实已经过期"的数据——这也是从库读要注意的一点。）

6. 边界与常见误解

常见说法实际情况
"AOF 比 RDB 安全，所以只用 AOF"AOF 文件更大、恢复更慢。生产常两个都开（4.0 后可用混合持久化）
"bgsave 完全不阻塞主线程"fork 本身要停一下（复制页表，大实例可到数十毫秒）；且 COW 会让内存上涨
"过期了就会立刻被删掉"不会。惰性删除要等访问，定期删除是抽样。内存里可能存在已过期的 key
"配了 volatile-lru 内存满了就会自动淘汰"只有设了 TTL 的 key 可被挑；一个都没有时等同 noeviction（写报错）
"Redis 持久化 = 数据不会丢"持久化只保证"重启后能恢复"，不保证"不丢"——AOF everysec 仍有 1 秒窗口。而且持久化不是备份（误删 FLUSHALL 也会被记进 AOF）
"allkeys-lru 最省心，直接用"如果实例里混着"必须常驻"的数据（配置、字典），它们可能被淘汰掉

【取舍】把这张表读成一句话：Redis 的所有"不丢"手段都是用一致性、内存或性能换来的，没有一个能同时做到"快、省、不丢"。

Redis 的数据会在什么情况下丢？每种"不丢"的手段各自付了什么代价？

一句话结论 全卡唯一要背的锚点

Redis 的"不丢"分三件事——持久化（RDB 记结果、文件小恢复快但有窗口；AOF 记过程、最多丢 1 秒但文件大恢复慢，生产常混用）、过期删除（惰性 + 定期抽样，不是立即删）、内存淘汰（8 种策略，按"在哪个池子挑 + 用什么算法"组合）。核心是认清一个约束：Redis 单线程，所有设计都在避免 O(n) 或长时间阻塞主线程——所以定期删除用抽样、bgsave 用子进程、LRU 用近似、always 要付一个数量级的吞吐。
  • 记结果 vs 记过程
  • RDB 丢两次快照之间、AOF 最多丢 1 秒
  • appendfsync 三选一（always 0.2ms×5000=1 秒）
  • AOF 重写＝把过程压成结果
  • bgsave 用子进程，但 fork 要停一下 + COW 让内存涨
  • 先执行后记日志，因为命令不幂等
  • 惰性删除（省 CPU 但占内存）+ 定期删除（抽样，25% 水位 + 25ms 上限）
  • 过期删除（时间）vs 内存淘汰（空间）
  • volatile-* 的陷阱
  • 近似 LRU 用采样换开销
  • 异步复制的窗口（故障转移会丢未同步的写入）
  • 集群=分片不是副本
  • 从库不主动删过期 key

卡住时靠这几个词重建整条链。

展开（先自答，再看 · 默认收起，不进复训调度）

1. RDB 和 AOF 选哪个？

通常都开：RDB 做冷备与快速恢复，AOF 保最多丢 1 秒；4.0 后可用混合持久化。

2. AOF 重写是干什么的？

把"记过的所有过程"重新压成"当前结果"，用一次全量替换掉整个历史，加快恢复。

3. bgsave 会影响线上吗？

会，两个途径：fork 复制页表时的短暂停顿；COW 导致快照期间内存上涨（写入越多涨得越多）。

4. 为什么不做精确 LRU？

精确 LRU 要维护全量链表、每次访问都移动节点，内存和操作开销都大。采样近似能拿到接近的效果，代价小得多。

5. 持久化开着，数据就一定不会丢吗？

不是。 everysec 仍有 1 秒窗口；always 也不等于零。而且持久化不是备份——误删、误 FLUSHALL 同样会被记进 AOF，所以要另有备份策略。

6. Redis 内存满了会怎么样？

看策略：noeviction 写报错；其余按池子和算法淘汰。注意 volatile-* 在没有 TTL 的 key 时等同 noeviction。
  • 「Redis 能做消息队列的持久化保证吗？」——Stream 有持久化（AOF/RDB），能支撑中小规模；但保留、分区、重放、运维生态与专业 MQ 差距明显。按可靠性需求选，不因为"已经用了 Redis"就默认替代（[[母题-R3-缓存一致性与三类事故]]）。
  • 「主从 + 持久化能保证不丢吗？」——异步复制下有窗口：主库写入后未同步即挂，从库不会有这条数据。要更稳就得用 WAIT 或换强一致的存储。
  • 「save 和 bgsave 区别？」——save 在主线程做，整个 Redis 阻塞；bgsave fork 子进程。生产只用 bgsave（且常配自动触发规则）。

EnergyOps / 数驭穹图 里的 Redis 都是缓存与短期状态，不承载业务真相——所以持久化策略的选择是"够用即可"，而不是"必须零丢失"。这一点值得在面试里主动说出来：因为它是派生数据，丢了可以从权威库重建；所以我用默认 everysec，用那 1 秒的窗口换吞吐。（判断依据来自 [[母题-R3-缓存一致性与三类事故]] 的地基：缓存是派生数据。）

先拆三件事（进程崩溃 / key 过期 / 内存满）→ RDB 与 AOF 的区别与各自的丢失窗口 → appendfsync 三选一的代价（给 fsync 算式）→ RDB 的 fork 与 COW 代价 → 先执行后记日志的原因（命令不幂等） → 过期删除为什么不能立即删（单线程 + O(n)）→ 惰性 + 定期抽样 → 内存淘汰的两个维度 + volatile-* 陷阱 → 收束到"四条设计躲同一件事"

Redis 的每一条"删除"和"持久化"设计，都在同一个约束下做取舍——「不能让单线程被长时间占住」。 所以：定期删除用抽样而不是全扫；bgsave 用子进程而不是主线程；LRU 用近似而不是精确链表；AOF 用 everysec 而不是 always。这四条是同一个约束的四种解法。
