题目

消息队列按「至少一次」投递，同一个业务动作可能被投递两次。你怎么保证业务效果只有一次？

一 · 教材 从前提推到结论，不需要先会

1. 为什么应用层幂等「不够」

幂等的常见应用层实现：

查：这个 idempotency_key 有没有处理过？
  没有 → 处理 → 记录
  有   → 直接返回上次结果

问题就在「查」和「记录」之间（和 P18 是同一个结构缺陷）：

实例 A: 查 → 不存在
实例 B: 查 → 不存在          ← 两个实例拿到同一个答案
实例 A: 处理 → 记录
实例 B: 处理 → 记录           ← 副作用发生了两次

【推论】「那加锁不就行了？」——加锁可以，但有两个代价：

  • 锁是应用层的，一旦有第二台机器/第二个进程就失效（除非用分布式锁，那又引入新依赖和新的失效模式）；
  • 锁的获取本身可能失败/超时，于是又回到"要么重试要么放弃"的老问题。

所以判断是：应用层幂等能挡掉绝大多数重复（这是有价值的优化——省掉了重复的昂贵操作），但不能作为正确性保证。

2. 唯一约束为什么是「最终防线」

它同时满足四个条件，缺一不可：

条件说明
原子插入与唯一性检查在数据库内部是一次操作，不存在「查—写」窗口
对所有路径生效不管来自哪个实例、哪个进程、哪条代码路径、甚至是运维手工插入，都拦得住
由持久状态保证约束建立在索引/数据上，不是内存状态（重启不丢）
失败是确定的第二次插入报 23505，语义明确，不会"有时成功有时失败"

【推论】「失败是确定的」这一条值得单独说：它让错误处理变得可推理——23505 就是"这件业务已经做过了"，可以直接查 Receipt 返回原结果；而不是像分布式锁那样"可能没抢到、也可能对方挂了"。

所以正确的分工是：

应用层幂等：优化（减少无效的昂贵操作）
数据库约束：正确性（唯一一个"无论如何都拦得住"的位置）
权威查询：判定（Receipt/Snapshot 告诉你"它到底成没成"）

【取舍】这三层不是"三个可选方案"，是三个【职责不同】的位置——只说其中一层都是不完整的：

应用层省资源（挡掉绝大多数重复，省下昂贵操作），但不提供保证；

约束提供保证，但它只回答"做没做过"，不回答"做到什么程度了"；

权威查询回答"程度"，但它是读操作，本身不能防止第二次执行。

三者缺一：只做应用层 → 会重复；只做约束 → 不知道半成品怎么办；只做权威查询 → 竞态照旧。

3. 幂等键怎么构造（含反例）

规则：基于业务身份构造，不依赖任何一次技术调用。

RuleArena 的组成（projects/RuleArena/04-idempotency-and-recovery.md）：

run_id + action_type + target_id + normalized_arguments + rule_version + logical_step

要能说出每一项挡的是什么：

组成挡什么
run_id不同运行的相同动作不能混为一谈
action_type同一目标的不同动作（退款 vs 发券）要分开
target_id同一动作作用在不同对象上要分开
normalized_arguments参数要归一化（顺序、大小写、数值表示），否则「同一个业务意图」会因为参数写法不同而被当成两次
rule_version规则变了之后，同一个动作是新的业务意图，不该复用旧结果
logical_step同一意图可能被合法地重复执行多次（比如重试策略的第 3 步），逻辑步骤要区分开

【推论】这张表的读法是「每一项都在回答一个『什么不算同一个意图』」：

漏掉任何一项，都会让【两个不同的业务意图】塌缩成同一个键——那是"该做的没做"。

而把技术 ID 放进去，会让【同一个业务意图】散成多个键——那是"做了两次"。

明确的反例（这是这道题最值钱的部分）：

不能用 ToolCallID 当幂等键。 因为它是由模型/运行时为"这一次调用"生成的，而同一个业务意图在这些情况下会产生不同的 ToolCallID：

  • 模型重新规划（换了调用方式）；
  • Worker 重启后恢复；
  • 会话恢复；
  • HTTP 超时后重新发起；
  • 两个策略恰好提出相同动作（各自生成自己的 ID）。

所以用 ToolCallID 做幂等键，等于"每次重试都换一把新钥匙"——约束永远不生效，重复副作用照样发生。 这条是"幂等设计里最典型的错误"，能讲出来直接体现项目深度。

【判据】一句话判据：

幂等键必须由【业务事实】决定，不能由【这一次怎么调用的】决定。

检验方法：把所有会产生同一个业务意图的代码路径列出来，问「它们会不会算出同一个键」——会，才是对的。

4. NOT NULL：一个容易漏的坑

PG 里 NULL 彼此不相等（[[母题-P5-表设计与数据类型]]），所以唯一约束允许多行 NULL。

【推导】后果可以算：

幂等键由 N 列组成，其中某一列可以为 NULL
假设这一列有 1% 的概率为 NULL

那么这 1% 的请求：
  → 它们的约束判定永远是"不重复"（因为 NULL ≠ NULL）
  → 【完全不受约束保护】

而且这个洞是【静默的】：约束建着、索引在、不报错，
只是对那 1% 不生效

【结论】约束看起来在，实际漏了一条缝——而且这条缝只在"恰好重复且恰好带 NULL"时才暴露。

所以规则是：参与唯一约束的列一律 NOT NULL；确实有可选维度时，用空字符串 / 哨兵值而不是 NULL（或者把可选维度塞进归一化后的参数哈希里）。

「设计唯一约束时必须检查 NOT NULL」——这是一个可以在 5 秒内检查完、但漏掉会致命的检查项。

5. UPSERT：两种形态与四个坑

-- 形态一：重复就跳过（幂等写入的默认选择）
INSERT INTO action_receipts (idempotency_key, run_id, action_type, status)
VALUES (:key, :run_id, :type, 'ACCEPTED')
ON CONFLICT (idempotency_key) DO NOTHING;

-- 形态二：重复就更新（"最后写入获胜"或状态机推进）
INSERT INTO counters (key, value) VALUES (:key, 1)
ON CONFLICT (key) DO UPDATE SET value = counters.value + excluded.value;

【事实】excluded 是什么——官方定义：

ON CONFLICT DO UPDATE 的 SET 和 WHERE 子句里，可以用表名（或别名）访问【已存在的行】，用那个特殊的 excluded 表访问【准备插入的那一行】。

【纠正常见误解】一个反直觉的官方提醒：

注意：所有逐行 BEFORE INSERT 触发器的效果都会反映在 excluded 的值里，因为那些效果可能正是这一行被排除插入的原因。

【推论】所以「excluded 就是我要插入的值」这句话不完全对——它可能已经被触发器改过了。 依赖 excluded 做计算时要意识到这一点。

四个坑

坑一：冲突也消耗序列值

【事实】官方对序列的定性：

这意味着事务中止或数据库崩溃会导致已分配值出现【空洞】。而且即使没有事务中止，也会发生。

因此，PostgreSQL 的序列对象【不能用来获得"无空洞"的序列】。

【推导】为什么 UPSERT 场景下这个洞更值得注意：

INSERT ... ON CONFLICT DO NOTHING 的默认值是在【检测冲突之前】求值的
  → 每次冲突的插入都白白消耗一个序列值
  → 序列消耗速度 > 有效行的增长速度

如果冲突率 30%：
  有效行增长 100 万 → 序列消耗约 143 万（100万 ÷ 0.7）
  → 【1.43 倍】

【结论】幂等键让冲突变成常态，而冲突会加速序列消耗——所以主键用 int4（serial）时，这个"加速"值得算进去。

坑二：批量插入里两行互相冲突会报错

【事实】官方原话：

准备插入的多行之间，不应该在裁决索引/约束所约束的属性上互相重复。

【推导】具体表现：

INSERT INTO t (k, v) VALUES (1, 'a'), (1, 'b')
ON CONFLICT (k) DO UPDATE SET v = excluded.v;
-- ERROR: ON CONFLICT DO UPDATE command cannot affect row a second time

【结论】同一个 INSERT 语句里的两行不能撞同一个键——但【两次不同的 INSERT】可以。 所以批量写入要先去重（或者在应用侧按键聚合）。

坑三：裁决索引是「推断」出来的，推断失败会报错

【事实】官方说明：

事务表上所有【不区分顺序地】包含 conflict_target 指定列的【唯一索引】都会被推断（选中）作为裁决索引。 如果指定了 index_predicate，它必须作为进一步的推断条件。如果推断不成功，会抛错。

【推论】这条的实际影响是：

ON CONFLICT (a, b) 需要有一个唯一索引【恰好】覆盖 (a, b)（顺序无关）
  → 如果你只有一个 【部分唯一索引】 WHERE deleted_at IS NULL
     → 普通写法推不出来 → 要带上 index_predicate 才推得出

另外两条限制（官方）：
  · 【排除约束不能作为 DO UPDATE 的裁决者】
  · 【只有 NOT DEFERRABLE 的约束和唯一索引能作为裁决者】

【结论】「我明明有唯一索引，为什么报错"没有匹配的裁决索引"」——去看那三条限制。 尤其注意分区表上：唯一约束必须包含所有分区键列（[[母题-P16-分区表]]），所以那也约束了 conflict_target 能写什么。

坑四：分区表上不能靠 UPSERT 移动分区

【事实】官方原话：

目前不支持：对分区表使用的 INSERT 的 ON CONFLICT DO UPDATE 子句去更新冲突行的分区键，从而使这一行需要被移动到新的分区。

【结论】在分区表上，DO UPDATE 不能改分区键——而分区键通常就是业务上的时间字段，很容易被顺手更新。 这是分区与 UPSERT 交叉处的一个硬限制，上线前必须验证。

6. 落到项目：RuleArena 的 Receipt

【事实】项目文档 04 §4 给的字段与 §5 给的约束（这里按正本还原，别用简化版）：

-- 表：ActionReceipt（项目文档字段清单见 04 §4）
CREATE TABLE action_receipts (
  receipt_id        bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  run_id            bigint      NOT NULL,
  action_type       text        NOT NULL,
  idempotency_key   text        NOT NULL,   -- 参与约束 → 必须 NOT NULL
  request_hash      text        NOT NULL,   -- 同一个 key 但 hash 不同 → 必须报冲突，不能静默复用旧结果
  processing_status text        NOT NULL,   -- ACCEPTED / COMPLETED / REJECTED / UNKNOWN（四态）
  business_status   text,
  result_json       jsonb,
  error_type        text,
  aggregate_version bigint,
  created_at        timestamptz NOT NULL DEFAULT now(),
  completed_at      timestamptz,

  -- 项目文档 04 §5 的原文约束形状：
  UNIQUE (run_id, action_type, idempotency_key)
);

【事实】Receipt 的处理状态是四态，不是两态（04 §4 原话）：

ACCEPTED ：已接收，尚未确认完成
COMPLETED：事务已成功
REJECTED ：确定性拒绝，没有副作用
UNKNOWN  ：当前无法确认，需要人工 / 后续恢复

【纠正常见误解】别把它简化成「ACCEPTED → 完成」两态——REJECTED 与 UNKNOWN 各有各的处置，而且方向相反：

查到 COMPLETED → 读权威 Snapshot，继续（复用结果，不重做）
查到 REJECTED  → 确定性失败，按错误类型决定是否换业务动作
查到 ACCEPTED  → 短暂等待 / 轮询，受预算限制
查不到 Receipt → 确认请求未被接受后，才可用同一个 key 重试
无法查询       → ACTION_UNKNOWN，停止当前分支

【推论】关键在「副作用与 Receipt 在同一个事务里提交」：

幂等写入的正确形态：
  BEGIN
    ① INSERT INTO action_receipts ... ON CONFLICT DO NOTHING
       → 影响 0 行 = 【已经做过了】→ 读 Receipt 返回原结果，回滚
       → 影响 1 行 = 【我是第一个】→ 继续
    ② 执行真正的业务副作用
    ③ （可选）更新 Receipt 状态
  COMMIT

→ 副作用和 Receipt 【要么一起成功，要么一起回滚】
→ 所以"Receipt 存在"就等价于"副作用已经发生"

【推论】如果撤销这一步，整个方案就塌了：Receipt 先提交、副作用后执行 → 中间崩溃会留下"有 Receipt 但没副作用"的记录 → 重投时被判定为"做过了"直接返回 → 业务动作【永久丢失】。 这是一个比"做两次"更糟的失败模式——因为它静默。

【事实】这条正是案例里那两句话的组合：「Receipt / Snapshot 权威查询」+「同一事务提交」——前者解决"做没做"，后者解决"记录与事实一致"。

7. 边界与常见误解

说法实际情况
「应用层做了幂等就够了」它只能减少无效尝试，不能提供正确性——任何「查—判断—写」都有窗口
「用 ToolCallID 当幂等键」等于每次重试换一把新钥匙——同一业务意图在这些路径下 ID 都不同：重新规划 / 重启 / 会话恢复 / 超时重发
「幂等键就是请求 ID」请求 ID 是技术身份，幂等键是业务身份——判据是「所有产生同一业务意图的路径会不会算出同一个键」
「唯一约束建了就能拦住重复」可空列会让它漏——PG 里 NULL 彼此不相等（[[母题-P5-表设计与数据类型]]）
「Receipt 先写、副作用后做，一样」反了——中间崩溃会留下"有记录没副作用"，重投时被判为已做过 → 业务动作永久丢失
「excluded 就是我要插入的值」不一定——逐行 BEFORE INSERT 触发器的效果会反映在 excluded 里
「ON CONFLICT 会自动找到唯一索引」它是【推断】的，推不出来会报错；而且排除约束不能当 DO UPDATE 的裁决者，只有 NOT DEFERRABLE 的才行
「主键不连续是 bug」序列本来就会有空洞——官方原话：「序列对象不能用来获得无空洞的序列」；UPSERT 的冲突还会加速消耗

三 · 面试输出 闭卷口述 60 秒，再看结论

唯一约束为什么是幂等的最终防线？UPSERT（ON CONFLICT）怎么用、有哪些坑？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是幂等设计的地基，而且它有一个非常有说服力的论证结构——「应用层幂等是优化，数据库约束才是正确性」。它还接住了你的项目里最核心的一段：RuleArena 的 ActionReceipt 与唯一约束（projects/RuleArena/04-idempotency-and-recovery.md）。能把"为什么必须在数据库层兜底"讲成一条必然性论证，而不是一句结论，这道题就到位了。

一句话结论 全卡唯一要背的锚点

因为它是数据库级别、原子、且对所有并发路径都生效的——应用层的「先查再插」有竞态（P18 讲过），而唯一约束让第二次插入直接失败，从结构上堵住了。前提是幂等键要基于业务身份构造（run_id + 动作类型 + 目标 + 参数 + 规则版本 + 逻辑步骤），并且参与约束的列必须 NOT NULL（PG 里 NULL 彼此不相等，否则约束会漏）。UPSERT 用 INSERT ... ON CONFLICT ... DO NOTHING / DO UPDATE。
  • 唯一约束是原子防线
  • 应用层幂等是优化
  • 先查再插有竞态
  • 幂等键基于业务身份（不能用 ToolCallID）
  • 约束列必须 NOT NULL
  • ON CONFLICT DO NOTHING vs DO UPDATE
  • 唯一索引推断（inference）
  • 冲突也消耗序列值

卡住时靠这几个词重建整条链。

展开（先自答，再看 · 默认收起，不进复训调度）

MySQL 的 INSERT ... ON DUPLICATE KEY UPDATE 与 PG 的 ON CONFLICT 语义接近但不相同：MySQL 的那个是"先在唯一键上冲突，再更新"，而 PG 的 ON CONFLICT 可以指定裁决索引（conflict_target）、可以用 excluded 引用待插入行、还支持 WHERE 条件——表达能力更强。而"NULL 让唯一约束失效"这一条两边一样（SQL 标准行为）。「我们在 MySQL 上用 ON DUPLICATE KEY」搬到 PG 上时，最容易漏的是【裁决索引要能推出来】这一步。

1. ON CONFLICT DO NOTHING 和 DO UPDATE 怎么选？

DO NOTHING 用于幂等写入（"做过了就不管"）；DO UPDATE 用于"存在就更新"（计数器累加、状态推进）。注意 DO UPDATE 拿的是行锁，而且会是"最后写入获胜"——要防止覆盖别人的更新，就得在 SET 里带条件（SET v = t.v + 1 WHERE t.v = :expected）。而 DO UPDATE 也会消耗序列值。

2. 为什么不能只靠应用层的分布式锁？

因为它引入了新的失效模式：锁的获取可能失败/超时；持锁进程挂掉后锁的释放要靠 TTL（于是又有"锁过期了活还没干完"的窗口）。 而数据库约束没有这些——它就在唯一的权威副本上。

3. Receipt 的 status 字段有什么用？

它解决"副作用做到一半崩溃"：Receipt 的处理状态是四态——ACCEPTED / COMPLETED / REJECTED / UNKNOWN（项目文档 04 §4），不是简单的两态。重投时看到 ACCEPTED 说明"上一次可能没做完"，这时要走【权威查询】去确认实际状态；只有 COMPLETED 才能直接复用原结果；REJECTED 是确定性失败；UNKNOWN 要停分支并保留证据（[[母题-P18-乐观并发控制]] 的「用一次权威读取替代猜测」）。

4. 序列会被填满吗？

会，而且比预期快（冲突也消耗）。官方原话是序列"不能用来获得无空洞的序列"——所以主键连续这个期待本身就该放下。 要抗高写入量就用 bigint，别在 int4 上赌。

5. 这套在分区表上有什么额外的坑？

两个：① 唯一约束必须包含所有分区键列（[[母题-P16-分区表]]），所以幂等键的组成会被分区键绑住；② ON CONFLICT DO UPDATE 不能更新分区键（官方明确不支持"需要移动到新分区"的更新）。这两条在"分区 + 幂等"叠加时必须在设计阶段就验证。
  • 「幂等键和业务主键是一回事吗？」—— 不是。业务主键标识"这个对象是谁"；幂等键标识"这个动作做没做过"。 同一个对象上可以有多个幂等键（不同动作各一个），所以幂等键通常是【复合的、带动作维度的】。 把它们混成一个，是"该做的没做"的常见来源。
  • 「消息队列的『至少一次』投递，是不是靠 MQ 自身去重更简单？」—— MQ 的去重只能覆盖"同一批次/同一时间窗"，跨天重投、死信重放、运维手工补投它都管不了。而业务幂等键是对【业务事实】的判定——它不关心消息从哪来。 所以正确姿势是 MQ 只保证"至少一次"，"恰好一次的效果"由消费端的幂等键负责。

- RuleArena 的 ActionReceipt（本场主战场：UNIQUE(run_id, action_type, idempotency_key) + 同一事务提交）。 - EnergyOps 的扣退款（外部支付接口 + 重试是必然的，所以幂等键必须在数据库层兜底）。 - 数驭穹图的写入去重（轮询式增量同步 → 同一批数据可能被重复读入，幂等键挡住重复写入）。

为什么应用层幂等不够（竞态）→ 唯一约束为什么是最终防线（四个条件） → 幂等键怎么构造（含 ToolCallID 反例） → NOT NULL 这个坑 → UPSERT 的两种形态与四个坑 → 落到项目的 Receipt 设计

幂等的最终责任必须落在数据库约束上。 应用层做幂等只能减少无效尝试（省资源），不能提供正确性保证——因为任何「查—判断—写」在多进程/多副本下都有窗口。唯一约束是唯一一个"无论如何都拦得住"的位置。
