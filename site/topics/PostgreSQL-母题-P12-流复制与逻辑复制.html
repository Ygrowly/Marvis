必懂 3 件事（① 物理复制复制的是存储的变化，逻辑复制复制的是数据的变化——所有能力差异都是这一句的推论 ② synchronous_commit 的五个档位对应备库的四个落点，有官方矩阵 ③ 复制槽默认可以无限保留 WAL——这是 PG 最常见的一类"磁盘被写满"事故）· 读完约 12 分钟 · 需要先懂：[[母题-P11-WAL与checkpoint]]

题目

你要 (1) 搭一个只读副本给报表用，(2) 还要把其中几张表的变更同步到另一个系统。这两件事用同一种复制吗？

一 · 教材 从前提推到结论，不需要先会

1. 两种复制：复制的是什么

流复制（物理）逻辑复制
复制内容WAL 字节流（存储层变化）逻辑变更（表的行变更）
粒度整个实例表级（可再按行过滤）
备端只读（热备，可跑查询）可读可写
版本必须一致可跨大版本
用途高可用、只读副本、读写分离CDC、异构同步、多源汇聚、升级迁移
机制WAL 直接传输 + 重放主库从 WAL 逻辑解码成变更流，备端按表应用

一句话对照：流复制让「另一个我」存在；逻辑复制让「我的一部分数据」出现在别处。

【推论】所有差异都是「复制的是存储变化还是数据变化」的推论：

复制存储变化 → 它必须是一模一样的实例（版本一致、不能挑表、备端不能写）
  → 因为 WAL 记录的是「第 N 号页的第 M 个偏移改成了什么」，
    这是【物理位置】，脱离这个实例就失去意义

复制数据变化 → 它可以被翻译成 INSERT/UPDATE/DELETE
  → 于是可以挑表、可以改结构、可以落到另一个版本甚至另一个数据库
  → 代价是：翻译过程会丢信息，而且【大对象、序列、DDL 都不会自动同步】

【话术】「逻辑复制能跨版本」的代价要说全：逻辑复制默认只同步 DML，不同步 DDL——这是它最容易被低估的限制：上游改表结构时，下游不会跟着改，所以生产上用逻辑复制必须配一套"结构变更的发布流程"。

到这里你应该能回答：为什么「用逻辑复制做完整迁移」听起来可行、实践上却要额外处理一大摊事？

2. 回到题目

  • (1) 只读副本做报表 → 流复制。它是完整副本、可以在备库上跑长查询（但要注意长查询与回放会冲突——见第 4 节）；
  • (2) 几张表的变更同步到别的系统 → 逻辑复制。因为你只需要那几张表、目标端可能版本不同或不是 PG。

【推论】数驭穹图的真实选择正好落在这条线上：它需要的是「授权的分析数据集」——不是整个实例，所以走逻辑路径；而且要能跨源、能只同步部分表，物理复制根本做不到。

3. 同步 / 异步：本质是 RPO 换延迟，但有官方矩阵

【事实】官方给出的 synchronous_commit 五档与他们各自的保证（表 19.1）——这张表可以直接背：

synchronous_commit本地持久提交备库在 PG 崩溃后仍持久备库在 OS 崩溃后仍持久备库查询一致性
remote_apply✓✓✓✓
on（默认）✓✓✓
remote_write✓✓
local✓
off

【推论】这张表把「同步复制」拆成了两个正交的问题：

问题一：数据会不会丢？ → 看「备库持久」那两列
  remote_write  只保证「备库进程崩了不丢」
  on            还保证「备库操作系统崩了也不丢」
  remote_apply  再保证「备库上能查到」

问题二：备库上的读能不能立刻看到？ → 看最后一列
  【只有 remote_apply 能】

【结论】「我们用了同步复制」这句话远远不够——要问的是「哪一档」：

  • on（默认）= 走人：主库不丢、备库不丢，但备库上刚提交的事务可能还查不到；
  • remote_apply = 走到位：连备库上的查询都能看到——代价大得多，因为它要等 WAL 重放完（官方原话：「会带来大得多的提交延迟」）。

【推导】把提交延迟的代价算出来（口径写在算式里）：

跨可用区 RTT ≈ 2 ms，备库 fsync ≈ 3 ms

local         ：只等本地 fsync            → ≈ 0 ms（不含本地）
on            ：+ 网络 + 备库刷盘          → ≈ 5 ms
remote_apply  ：+ 备库重放完成             → ≈ 5 + 2 = 【7 ms】

单连接 TPS：从 1/0.001 ≈ 1000 降到 1/0.007 ≈ 【143】

【结论】提交延迟从毫秒级涨到 7ms，单连接吞吐掉到 1/7——并发连接能补回吞吐，但补不回延迟（P99 从 2ms 变 10ms 是质变）。

【取舍】还有一个必须说清的陷阱：同步复制会让「备库的可用性」变成「主库可用性」的一部分——备库挂了，主库提交就可能被卡住。 所以生产通常配 FIRST 1 (a, b) 这类「至少一个备库确认即可」的写法，而不是「等全部」。

【推论】这一条比结论重要：不要简单说「我们用了同步复制保证不丢」——要说清楚「几种确认策略、以及备库故障时主库会怎样」。

【事实】最后一个好用的细节（官方原文）：提交模式是【每个事务】可以单独选的——「在一个默认是同步的系统里，让某一个多语句事务异步提交」只需要在事务里 SET LOCAL synchronous_commit TO OFF。

到这里你应该能回答：为什么「我们开了同步复制所以不会丢数据」这句话，在面试官追问「备库挂了怎么办」时会立刻站不住？

4. 两个能算的坑

坑一：复制槽不消费 → WAL 永久堆积 → 磁盘写满

【事实】默认值是「无限保留」——官方原文：

max_slot_wal_keep_size：指定复制槽在 checkpoint 时允许在 pg_wal 目录里保留的 WAL 文件的最大体积。

如果它是 -1（默认值），复制槽可以保留【无限量】的 WAL 文件。

【推导】把事故时间算出来：

主库 WAL 生成速率 = 10 MB/s
一个逻辑复制槽的消费者挂了（没有任何告警）
pg_wal 可用空间 = 500 GB

500 GB ÷ 10 MB/s = 50,000 秒 ≈ 【13.9 小时】

→ 不到一天磁盘写满
→ 后果：【整个实例写不进去】——不是"这个复制槽坏了"，是【主库挂了】

【结论】「一个消费者掉了」升级成「主库不可写」，只需要不到一天。 这是 PG 最常见的一类生产事故，而且它是【默认配置】下的行为。

【动作】两件事都要做：

① 显式设 max_slot_wal_keep_size
     比如设成 100 GB → 10,000 秒 ≈ 2.8 小时后该槽失效
     → 后果从「主库写不进去」降级成「这个备库/消费者需要重建」

② 监控「不活跃的复制槽」
     查 pg_replication_slots，看 active 与保留的 WAL 量
     并写下运维约定：离线多久就删槽并重建

【判据】取舍很清楚：

不设上限 = 用「整个实例的可用性」去赌「消费者一定会回来」。

设了上限 = 用「这个消费者需要重建」换「主库不会因为别人掉线而挂」。

显然后者是对的。

坑二：主从延迟——回放追不上就永远追不上

【事实】延迟有三段：① 主库产出 WAL 的速度 → ② 网络传输 → ③ 备库回放。

【推导】第 ③ 段是最容易被忽略、也最致命的一段：

主库生成 1000 事务/秒
备库回放能力 800 事务/秒（CPU 不够 / 有冲突查询 / 单线程回放）

每秒积压 = 1000 − 800 = 200 个事务
1 小时后积压 = 200 × 3600 = 【72 万个事务】

→ 延迟【单调增长】，永远不会自己收敛

【结论】这是一个硬结论：

备库的回放能力必须 ≥ 主库的生成能力，否则延迟不是"有点大"，而是【单调增长到不可用】。

所以「主从延迟大」的第一诊断不是"网络慢"，而是"回放能力够不够"。

【事实】而备库上的长查询会直接打击回放能力——官方对冲突的处理机制是：

max_standby_streaming_delay（默认 30 秒）：备库在取消那些与即将应用的 WAL 记录冲突的查询之前，应该等多久。

-1 表示允许备库【永远】等冲突查询完成。

【推论】这里有一个必须说清的选择：

备库上有冲突的长查询（比如报表）
  → 默认行为：等 30 秒 → 【取消那个查询】（报错）
  → 你要么让报表能被取消，要么调大这个值
  → 调成 -1（永远等）= 【让回放无限期停摆】
     → 备库延迟无限增长（上面那个算式）

另一条路：hot_standby_feedback = on
  → 备库把"我还在读这些行"反馈给主库，主库就不清理它们
  → 查询不会被取消
  → 但官方明确警告：【会造成主库的表膨胀】
     （因为主库不能回收备库还在读的旧版本，P14/P15）

【结论】「备库上跑报表」这件事的代价是二选一的：要么报表可能被取消（30 秒后），要么主库开始膨胀。这是「读写分离」在 PG 里最真实的一笔账。

【取舍】业务后果与处理（读写分离下「写主库、读备库」会读到旧数据）：

关键读回主库（最可靠）→ 写后一段时间内钉住主库（读己之写）→ 监控延迟并在超阈值时降级。

不要用「sleep 一下再读」这种办法。

5. 边界与常见误解

说法实际情况
「开了同步复制就不会丢」要看哪一档：remote_write 只保证备库进程崩不丢；on 才保证备库 OS 崩也不丢
「同步复制就是更安全」它让备库的可用性变成主库可用性的一部分——备库挂了主库提交会卡
「备库上跑报表没有影响」冲突查询默认 30 秒后被取消；用 hot_standby_feedback 救它，代价是主库膨胀
「主从延迟大 = 网络慢」先看回放能力够不够——回放能力 < 生成能力时延迟单调增长，永远不收敛
「复制槽只是记个位点」默认可以无限保留 WAL——一个掉线的消费者能在 14 小时内写满磁盘、让主库不可写
「逻辑复制能跨版本，所以能直接做迁移」它默认只同步 DML，不同步 DDL（还有大对象、序列）——结构变更要另走流程
「逻辑复制备端是只读的」反过来——逻辑复制的备端是可读可写的，代价是冲突要自己处理

三 · 面试输出 闭卷口述 60 秒，再看结论

流复制和逻辑复制有什么区别？同步 / 异步怎么取舍？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是直接落在你项目上的一道题——数驭穹图的接入层明确写着「MySQL 优先用 Binlog，PostgreSQL 优先用逻辑复制 / WAL」，而且第一版有意没上完整 CDC。为什么这么选、代价是什么，这道题必须能自己讲出来，否则那个设计决策就只是一个抄来的结论。

一句话结论 全卡唯一要背的锚点

流复制（物理）复制的是「整个实例的 WAL 字节流」——备库是主库的逐字节副本，只能整实例、备库只读（但可查询）、版本必须一致；逻辑复制复制的是「逻辑变更」——可以按表、可以按行过滤、备端可写、可跨大版本、能做异构与多源汇聚。所以 ① 只读副本用流复制；② 部分表同步到别的系统用逻辑复制。同步 / 异步的取舍本质是 RPO vs 提交延迟。
  • 物理复制（WAL 字节流）vs 逻辑复制（变更流）
  • 表级与行级过滤
  • 跨版本
  • 备库只读 vs 可写
  • synchronous_commit 五档对应备库四个落点
  • 复制槽默认无限保留 WAL（max_slot_wal_keep_size = -1）
  • 备库冲突查询默认 30 秒后被取消
  • 回放能力必须 ≥ 生成能力

卡住时靠这几个词重建整条链。

展开（先自答，再看 · 默认收起，不进复训调度）

MySQL 的复制靠 binlog（Server 层逻辑日志）+ 各种格式（Statement / Row / Mixed）；PG 的物理复制走 WAL、逻辑复制走 WAL 逻辑解码。关键结论：MySQL 的 binlog 天生是逻辑的，所以按表过滤、跨版本是"本来就有的能力"；PG 的物理复制天生是物理的，逻辑复制是后补的能力层。 「MySQL 用 binlog、PG 用逻辑复制/WAL」这句话本身就是两套机制的对照，说的时候要清楚自己在对照什么。

1. 逻辑复制的目标端能写吗？

能（它是独立的可写表），代价是冲突要自己处理（目标端本地已有数据会与回放冲突）。这也是它能做多源汇聚的原因——同时也是它最难运维的地方。

2. 能不能用逻辑复制做双向同步？

技术上可以，但冲突解决完全靠自己，收益通常不如改成单向 + 明确归属。面试里承认「双向的复杂度收益比不高」比硬吹更好。

3. 为什么 PG 不用 binlog 也能做 CDC？

因为 WAL 本身就是完整的变更记录，逻辑解码把它翻译成逻辑变更（pgoutput）即可。这也解释了为什么 PG 侧的 CDC 工具（Debezium 等）都基于逻辑解码槽。

4. 备库上的统计信息要管吗？

要。统计信息不是"复制的数据"，它是每台实例各自 ANALYZE 出来的——只读副本如果从不分析，它的执行计划可能和主库完全不一样（[[母题-P7-统计信息与慢查询定位]]）。

5. 为什么你项目第一版不做完整 CDC？

要说出取舍：CDC 要求源端启用逻辑复制/binlog 并常驻一个消费者，一旦消费者停摆就有 WAL/binlog 堆积风险（这正是 Q2 那个 13.9 小时）；而分析场景对新鲜度的要求是分钟级可接受。所以用「可恢复快照 + updated_at / 递增主键轮询 + 位点与校验」换来了「不侵入客户生产库 + 可复现」——升级条件是出现真实的秒级新鲜度需求。 这段是项目叙事的核心，必须能自己讲。
  • 「MySQL 的复制和 PG 差在哪？」—— MySQL 靠 binlog（Server 层逻辑日志），格式有 Statement / Row / Mixed 三种；PG 的物理复制走 WAL、逻辑复制走 WAL 逻辑解码。关键差异：MySQL 的复制天生是"逻辑"的（binlog 就是行/语句），所以它天然支持跨版本与按表过滤；PG 的物理复制是字节流，所以它天生不能——PG 是后来用逻辑解码补上了逻辑复制的能力（[[母题-M14-主从复制与延迟]]）。
  • 「主从延迟会影响读一致性吗？」—— 会。RC 下"写主库读备库"读到旧数据是常态。 处理按可靠性排序：关键读回主库 → 读己之写时钉住主库 → 监控延迟并降级。 不要用「sleep 一下再读」。

- 数驭穹图的接入层（本场主战场）——MySQL 源走 Binlog、PG 源走逻辑复制/WAL、都不支持时退回轮询。 - EnergyOps 的读写分离与报表查询（能接受延迟就上备库——但要想清楚报表被取消还是主库膨胀）。

两种复制的机制差异 → 各自绑定的东西 → 回到题目做选择 → 同步级别与它对应的四个落点 → 两个能算的坑（复制槽堆积、回放追不上） → 你项目为什么选逻辑路径

物理复制复制的是「存储的变化」，逻辑复制复制的是「数据的变化」。 所以前者绑定实例与版本，后者绑定表与行——所有能力差异（能不能选择性复制、备端能不能写、能不能跨版本）都是这一句话的推论。
