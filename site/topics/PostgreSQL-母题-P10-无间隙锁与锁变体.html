题目

一个只用过 MySQL 的候选人说「RR 靠间隙锁防幻读」。这句话在 PG 里哪里不成立？

一 · 教材 从前提推到结论，不需要先会

1. PG 为什么没有间隙锁

MySQL 的 next-key lock = 记录锁 + 间隙锁：锁定「某个范围」，从而阻止别人在这个范围内插入新行，这样「第二次查询不会多出几行」（防幻读）。

PG 的做法完全不同：读操作完全不加锁，靠快照保证「你看到的数据是某个一致时刻的」。所以：

  • 「幻读」在 PG 里表现为：你换了快照就会看到新行（RC 下每条语句一次快照，[[母题-P8-隔离级别与读一致性]]），或看到旧快照（RR/Serializable 下）；
  • PG 不会为此阻塞插入——所以插入和范围查询几乎不互相干扰，并发度更高。

【推论】「无间隙锁」有一个必须记住的后果：

你锁不住「还不存在的行」。 一个范围查询锁到的只是当下匹配的那些行——别人仍然可以在你锁住的范围内插入新行。

【结论】这就是为什么「先查一遍有没有，再插入」这个动作在 PG 里天然有竞态——必须靠唯一约束兜底，不能靠锁（[[母题-P19-唯一约束与UPSERT]]）。

这就是为什么「PG 没有间隙锁」不是缺陷，而是另一条设计路线。

2. 幻读和不变量：两条路

需求路径
「我这段计算要基于同一时刻的数据」提隔离级别（RR / Serializable），接受 40001 重试（[[母题-P9-序列化失败与重试]]）
「某个跨行不变量绝不能破」用锁或约束显式守住：FOR UPDATE 锁住涉及行、唯一约束堵住重复、条件更新把判断与写入合并（P18/P19）

【推论】关键判断：PG 不会自动帮你把不变量守住（不像 MySQL 会用间隙锁顺手挡住一部分幻读），所以PG 的业务正确性更依赖「显式约束 + 显式锁」，而不是「依赖默认隔离级别」。 这句话说出来，对 PG 的理解层次就到位了。

3. 四种行锁：一个冲突矩阵定强弱

【事实】官方原文：「行级锁不影响数据查询，它们只阻塞对同一行的【写者与加锁者】。」

模式官方定义（要点）
FOR UPDATE最强：阻止其他事务对这行做 UPDATE / DELETE / FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE
FOR NO KEY UPDATE比它弱：不阻塞 FOR KEY SHARE
FOR SHARE共享锁：阻塞 UPDATE / DELETE / FOR UPDATE / FOR NO KEY UPDATE，不阻塞 FOR SHARE / FOR KEY SHARE
FOR KEY SHARE最弱：阻塞 FOR UPDATE，但不阻塞 FOR NO KEY UPDATE

【事实】官方给出的冲突矩阵（表 13.3）——这是判断一切锁问题的唯一依据：

请求的锁 ↓ ／ 已持有的锁 →FOR KEY SHAREFOR SHAREFOR NO KEY UPDATEFOR UPDATE
FOR KEY SHARE✗
FOR SHARE✗✗
FOR NO KEY UPDATE✗✗✗
FOR UPDATE✗✗✗✗

【推论】从矩阵里能读出两件反直觉的事：

1. FOR KEY SHARE 和 FOR SHARE 之间完全不冲突，和 FOR NO KEY UPDATE 也不冲突——这就是「弱档位能大幅减少阻塞」的来源； 2. 只有 FOR UPDATE 是「和谁都冲突」的——所以它是最后手段，不是默认选择。

【纠正常见误解】普通 UPDATE 拿的是哪一档？ 官方原话：

FOR NO KEY UPDATE …这个锁模式也被任何【没有拿到 FOR UPDATE 锁】的 UPDATE 获取。

而 FOR UPDATE 锁模式也被任何 DELETE 获取，以及任何【修改了某些列的】UPDATE 获取。目前被考虑的那组列，是那些【上面有可用于外键的唯一索引】的列（所以部分索引和表达式索引不算）。

【推论】这条把「改哪一列」和「阻塞谁」连起来了：

UPDATE t SET note = ? WHERE id = ?        → FOR NO KEY UPDATE（弱）
  → 不阻塞子表的 FOR KEY SHARE 插入  ✔

UPDATE t SET id = ? WHERE ...             → FOR UPDATE（强）
  → 阻塞所有 FOR KEY SHARE（包括外键检查）
  → 也阻塞其他一切

【结论】「改一个被外键引用的键值」是一个远比「改一个普通字段」重的动作——这是很多 ORM 无脑 SET 全字段时踩的坑：它可能顺手把一个本该是弱锁的更新升级成了 FOR UPDATE。 「更新时只 SET 你真正改的字段」这条建议，在 PG 里有一个具体的并发收益。

到这里你应该能回答：为什么「FOR UPDATE 是最强的所以最安全」这个直觉在 PG 里是错的？

4. 外键用最弱的 FOR KEY SHARE【事实】

【推导】为什么外键只需要最弱的那一档：

外键约束需要保证的事情，只有一件：
  「被引用的那个键【还在】」

它不需要：
  ✗ 阻止别人改被引用行的【其他字段】
  ✗ 阻止别人读它

它需要：
  ✔ 没人删这一行
  ✔ 没人改【键值】本身

→ 这正好就是 FOR KEY SHARE 的定义

【结论】所以「向子表插入一行」通常不会和被引用行的普通更新互相阻塞——因为普通更新拿的是 FOR NO KEY UPDATE，而它和 FOR KEY SHARE 不冲突（看矩阵）。

【取舍】官方对它的定位是一句实用的建议：

应该确保一个事务中在某个对象上获取的【第一个锁】，是该对象后续需要的【最严格的】模式。

最好的防死锁办法是避免死锁：确保所有应用都以【一致的顺序】在多个对象上获取锁。

【推论】这两句话合起来是一条设计规则：要么一开始就拿最强的锁（避免中途升级），要么始终按同一个顺序拿（避免交叉等待）。 最糟的是"先拿弱的、中途想升级"——因为锁升级在 PG 里会互相等待。

到这里你应该能回答：为什么「给表加个外键会让写入变慢」这个担心，在 PG 里通常不成立？

5. 一个必须知道的默认值：PG 会【无限】等锁【事实】

官方原文：

只要没有检测到死锁，一个寻求表级或行级锁的事务会【无限期地等待】冲突锁被释放。

这意味着让应用长时间持有事务是个坏主意（比如在等用户输入的时候）。

【事实】死锁检测的机制与默认值：

PostgreSQL 会自动检测死锁并解决它们——牺牲掉其中一个事务，让其余的完成。（具体牺牲哪一个难以预测，不应该依赖它。）

deadlock_timeout（默认 1 秒）：在锁上等待多久之后去检查是否存在死锁。 死锁检查相对昂贵，所以服务器不是每次等锁都查——它乐观地假设生产应用里死锁不常见，先等一会儿再说。

【推导】把「无限等锁」的后果算出来：

某个事务因为写了外部 API / 等人工确认，持锁 30 秒
  → 后续所有要碰这一行的请求【全部排队】
  → 连接池 100 条连接在 30 秒内被这个队列占满
  → 正常能扛 100 ÷ 0.05s = 2000 QPS，此刻读请求也拿不到连接
  → 故障形态：不是"某个接口慢"，是【整站超时】

【推论】判据：

PG 的「无限等锁」意味着：一个失控的事务不只是自己慢，它会把整个连接池变成它的等待队列。

所以 lock_timeout / statement_timeout / idle_in_transaction_session_timeout 这三个参数在生产上是必须设的——它们是给"失控事务"准备的保险丝。

【方言差异】这是与 MySQL 最容易混淆的一处：MySQL 有 innodb_lock_wait_timeout（默认 50 秒），等不到就报错；PG 默认【无限等】，只靠死锁检测兜底。所以「MySQL 里这行代码会报超时」和「PG 里这行代码会一直挂着」是两个不同的现象。

到这里你应该能回答：为什么「我们的事务里调了一下第三方接口」这件事，在 PG 里比在 MySQL 里更危险？

6. advisory lock：不写表也能加锁【事实】

官方定义：

PostgreSQL 提供了创建【应用自定义含义】的锁的手段，叫 advisory lock（咨询锁）——因为【系统不强制它的使用】，用对用错取决于应用自己。

它适合那些不太契合 MVCC 模型的加锁策略。 一个常见用法是模拟那种「扁平文件」数据管理系统的悲观锁策略。

【推导】为什么它比「在表里插一个标志位」更好——官方给了三条：

在表里插标志位（自己实现锁）        用 advisory lock
  → 多一次写                    → 只在内存里
  → 产生死元组 → 表膨胀（P14）    → 【避免表膨胀】
  → 崩溃后标志位残留             → 【会话结束自动清理】
  → 要自己写清理逻辑             → 不用

【事实】两个级别，区别在「回滚时会不会释放」：

级别何时释放是否遵守事务语义
会话级（pg_advisory_lock）显式解锁或会话结束不遵守——事务回滚后锁仍然被持有；同一个进程可以重复获取，每次都要配对解锁
事务级（pg_advisory_xact_lock）事务结束时自动释放遵守；没有显式解锁操作

【取舍】官方明确说：短期使用 advisory lock，事务级往往比会话级更方便。 而会话级那个「回滚后仍然持有」的行为，是最容易踩的坑——它和普通锁的直觉相反。

【事实】它的存储与上限：advisory lock 和普通锁共用同一个共享内存池，大小由 max_locks_per_transaction 和 max_connections 决定。 必须小心不要耗尽它——否则服务器将【完全无法授予任何锁】。 典型上限是几万到几十万个。

【结论】所以 advisory lock 不是免费的：它是一个有全局上限的共享资源，用得失控会波及整个实例。

【事实】排查工具：所有 advisory lock 都能在 pg_locks 里查到。

7. 写偏斜：比幻读更麻烦的东西

【事实】定义：两个事务读的集合和写的集合都不重叠，但合起来破坏了一个跨行不变量。

【推导】经典例子：约束是「至少有一名医生值班」。

事务 A：SELECT count(*) WHERE on_call = true  → 2（够）
        把其中一人设为不值班
事务 B：SELECT count(*) WHERE on_call = true  → 2（够）
        把【另一人】设为不值班

结果：0 人值班 —— 不变量破了

【结论】A 的读集不包含 B 要写的行，写集也不重叠——所以 RC 和 RR 都拦不住。

【推论】为什么 RC/RR 拦不住：快照隔离只保证「你看到的是一致的」，它不保证「你的读和你的写之间没有别人插进来」。

三条解法：

1. Serializable（SSI）：它能检测出这种依赖环 → 报错重试（[[母题-P9-序列化失败与重试]]）——这是最省心的解法； 2. 显式锁：把「读」也加锁（FOR UPDATE 锁住所有涉及行），退化成悲观并发的写法； 3. 改成约束 / 单行聚合：把跨行不变量收敛成一个能被数据库原子保护的东西（比如在一行里维护计数并用条件更新守护）。

【推论】第 3 条最值钱：工程上最好的做法不是「加锁保护不变量」，而是「把不变量设计成不需要跨行保护」——这是设计层面的解法，比机制层面的更根本。

8. 死锁：PG 里怎么来、怎么减少

1. 统一加锁/更新顺序（例如总是按主键升序更新）； 2. 对象上拿的第一个锁就是后续需要的最强那一档（避免中途升级）； 3. 缩短事务、别在事务里做网络 IO 或等人工确认（官方明确点名这个场景）； 4. 能不用锁就不用锁——条件更新把「等待」变成「0 行受影响」，根本不产生锁等待，也就没有死锁。

  • 来：两个事务以不同顺序锁同一批行（UPDATE 顺序不一致、FOR UPDATE 顺序不一致），或者 RC 下 UPDATE 重新检查最新版本（P8）造成的互相等待；
  • 减少（前两条是官方原话）：

【推论】第 4 条接到 P18：PG 里减少死锁最有效的手段不是调参，而是换并发控制方式。

9. 边界与常见误解

说法实际情况
「PG 也靠间隙锁防幻读」PG 没有间隙锁——它靠快照挡幻读，代价是串行化冲突时重试
「FOR UPDATE 最强所以最安全」它是唯一和一切都冲突的那一档——不该阻塞的也阻塞了
「外键会阻塞被引用行的所有更新」只要没改键值，外键的 FOR KEY SHARE 和普通更新的 FOR NO KEY UPDATE 不冲突
「普通更新都是 FOR NO KEY UPDATE」改被外键引用的键列时，UPDATE 会升到 FOR UPDATE
「PG 的锁等不到会像 MySQL 一样超时」PG 默认【无限等】——只有死锁检测会救你
「advisory lock 是内存里的，所以随便用」和普通锁共用同一个内存池——耗尽它会让服务器完全无法授予任何锁
「advisory lock 也会被回滚掉」会话级 advisory lock 不遵守事务语义——回滚后仍然持有

三 · 面试输出 闭卷口述 60 秒，再看结论

PG 没有间隙锁，幻读和写偏斜靠什么防？FOR UPDATE 的四个变体怎么选？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是「最容易说反的一处」——因为它不是「PG 也有类似的东西只是名字不同」，而是PG 从根本上换了一套机制。而且它接得很实：为什么你的项目选条件更新而不选 FOR UPDATE（P18），答案就在这里——PG 的显式锁有四种强度，选错要么挡不住、要么挡太多。

一句话结论 全卡唯一要背的锚点

PG 没有间隙锁——它不会因为「锁了一个范围」而阻止别人往这个范围里插入（MySQL 的 next-key lock 会）。所以防幻读只有两条路：提高隔离级别靠快照（RR / Serializable，冲突时报错重试），或者用显式锁 / 谓词式约束（唯一约束、条件更新）自己把不变量守住。四种行锁从强到弱：FOR UPDATE → FOR NO KEY UPDATE → FOR SHARE → FOR KEY SHARE。
  • 无间隙锁
  • 不阻塞插入
  • FOR UPDATE
  • FOR NO KEY UPDATE
  • FOR SHARE
  • FOR KEY SHARE
  • 外键用最弱的 KEY SHARE
  • 普通 UPDATE 对应 NO KEY UPDATE，但改被外键引用的键列会升到 UPDATE
  • PG 默认无限等锁
  • advisory lock

卡住时靠这几个词重建整条链。

展开（先自答，再看 · 默认收起，不进复训调度）

MySQL 的 RR + next-key lock 会阻止插入（表现为插入被阻塞）；PG 不会。MySQL 的锁等待有 50 秒超时，PG 默认无限等。 MySQL 没有四档行锁，也没有 advisory lock（要用 GET_LOCK()）。 「PG 也靠间隙锁」是明确的概念性错误，和「SSE 是短连接」同一级别。

1. FOR UPDATE 是不是就万无一失了？

不是。① 它只锁匹配到的行，如果范围里还没有行（还没插入），照样锁不住——这正是「无间隙锁」的直接后果；② 它需要读的时候也用它，一旦某条路径忘了加锁就出现竞态；③ 它会把并发冲突从「报错重试」变成「排队等待」，而 PG 默认无限等，高并发下可能拖垮吞吐。

2. 那 RuleArena 为什么优先条件更新？

项目文档给的理由是「权威性」不是「频率」：04 §15 原话「MVP 优先业务唯一键 + 条件更新」，Q7 原话「锁可以降低竞争，但不能成为资金正确性的唯一保证……只有真实高竞争时再评估锁」——注意文档 04 §12 同时给了「锁定订单行【或】乐观版本条件更新」，所以不要说成「完全不用锁」；准确说法是「优先条件更新，锁留到真实高竞争时再评估」。而且条件更新天然幂等（重复执行第二次影响 0 行），唯一约束负责最终防线（[[母题-P18-乐观并发控制]]）。

3. SELECT ... FOR UPDATE 和 UPDATE 自己差在哪？

UPDATE 会自动加行锁（普通更新对应 FOR NO KEY UPDATE，改键列则升到 FOR UPDATE）；FOR UPDATE 是先把行锁住再去判断/计算，用于「读—判断—写」跨越多次交互的场景。另外官方提醒：SELECT FOR UPDATE 会因为"标记行已锁"而产生磁盘写。

4. PG 的表锁呢？

PG 有一套 8 种表级锁（ACCESS SHARE 到 ACCESS EXCLUSIVE），日常业务基本不用；要被提醒的是 ALTER TABLE 会拿较重的表锁——那才是真正会堵住整张表的（[[母题-P4-索引代价与在线建索引]]）。

5. advisory lock 适合做什么？

适合那些"不适合用表里的标志位"的锁：官方说它比标志位更快、避免表膨胀、而且会话结束时服务器自动清理。 典型场景是调度器选主、单例任务互斥。 但要注意两个坑：会话级的不遵守事务语义（回滚后仍持有），以及它和普通锁共用同一个内存池——耗尽它会让服务器无法授予任何锁。
  • 「PG 和 MySQL 的锁模型差多少？」—— ① PG 无间隙锁，MySQL 有（next-key lock）；② PG 行锁有四档，MySQL 只有两档（FOR UPDATE / LOCK IN SHARE MODE）；③ PG 默认无限等锁，MySQL 有 50 秒超时；④ PG 有 advisory lock、MySQL 靠 GET_LOCK()。四条说清，这道题就满分。
  • 「怎么知道是谁在等锁？」—— pg_locks（含 SIReadLock 与 advisory lock）+ pg_stat_activity.wait_event_type = 'Lock'。能说出 wait_event_type 就说明你真的排过线上锁问题。

- RuleArena 的任务认领（多个 Worker 抢同一任务——用条件更新而不是 FOR UPDATE；而且「抢一个还没被创建的任务」这个需求，FOR UPDATE 天然做不到）。 - EnergyOps 的月度结算（跨行不变量多，正是该考虑 SSI 或"把不变量收敛到一行"的地方）。 - 数驭穹图的同步任务互斥（advisory lock 的教科书场景：既要互斥、又不想在表里插标志位）。

MySQL 用「范围锁」把幻读挡在门外；PG 用「多版本快照」让幻读不产生错误结果，代价是冲突时要报错重试。 一个靠「不许发生」，一个靠「发生但可检测」——理解这个分歧，后面的锁与隔离全都能推出来。
