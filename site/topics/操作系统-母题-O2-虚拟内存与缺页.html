题目

线上一个服务被人问："我这个程序要 8GB 内存，但我测试机只有 4GB，为什么它跑起来了？"另一个问题：某容器半夜被杀了，日志写着 Memory cgroup out of memory，但运维说"整机内存还剩 40%，不可能 OOM"。这两个问题能不能用同一套原理解释？

一 · 教材 从前提推到结论，不需要先会

1. 前提：一开始就要把"两个内存"分开

1.1 虚拟内存要解决三个问题【事实】

先建立概念：虚拟地址空间（程序看到的地址）和物理内存（真实存在的内存条）是两套东西，中间由操作系统的页表做映射。

【推导】为什么要多这一层——三个理由，按重要性排序：

理由不这么做会怎样
① 隔离两个进程可以直接读写对方的内存 → 一个野指针就能改掉别人的数据（安全与稳定都崩）
② 让"申请"和"占用"解耦程序申请 8GB 时，如果必须立刻找到 8GB 连续物理内存，大量程序根本启动不了（而且物理内存会大量闲置）
③ 提供统一的地址视图没有它，程序必须自己关心"我的变量在第几根内存条上"

【推导】第 ② 条是这一整张卡的主线：虚拟内存让"申请内存"和"占用内存"变成两件事。 这句话直接解释了三件事——为什么 malloc 返回成功不等于有内存、为什么 8GB 的程序能在 4GB 机器上跑、为什么"内存泄漏"有时会拖很久才爆。

1.2 地址翻译：页表、多级页表、TLB【事实】

页（page）：内存管理的最小单位，典型 4KB（这就是"大页"这个概念的参照点）。

页表（page table）：记录"虚拟页 → 物理页"映射关系的表。每次内存访问都要用它把虚拟地址翻译成物理地址。

【事实】翻译过程要走过几级：以 x86-64 的 4 级页表为例，48 位虚拟地址被切成 5 段：

47..39 (9位) → PGD        指向下一级页表
38..30 (9位) → PUD
29..21 (9位) → PMD
20..12 (9位) → PTE        这一项才是"物理页号"
11..0  (12位) → 页内偏移   4KB = 2^12

【推导】为什么一定要分级——这里有一个非常干净的算式（自测 Q1）：

要映射 48 位地址空间（2^48 = 256 TB），每页 4KB → 2^36 个页
如果只用一级页表：2^36 × 8 字节/项 = 512 GB  ← 只为存页表就要 512GB，荒谬

4 级之后：每级最多 512 项（9 位），每张页表 4KB
  最坏情况映射 4KB 的一小块内存，只需要 1 张 PTE 表 = 4KB
  → 稀疏的地址空间变得便宜了

【事实】TLB（Translation Lookaside Buffer）：CPU 里的地址翻译缓存，避免每次访问都走四级页表。

级别容量能覆盖多大
L1 dTLB64–128 条目极小
L2 STLB约 1536 条目（随 CPU 型号变化，这里取一个常见值）1536 × 4KB = 约 6 MB

【推导】注意最后那一列——用 4KB 普通页时，TLB 只能覆盖约 6MB 的工作集；超过就每次访问都要走页表（[[母题-O1-上下文切换与死锁]] 里"切换后 12.8 μs"的账就是从这来的）。而如果用 2MB 大页：

1536 × 2MB = 约 3 GB        ← 覆盖范围放大 512 倍

【这就是大页（Huge Page）存在的唯一理由】——不是"更快"，是"让 TLB 装得下"。 数据库、JVM 这类大内存工作集的场景配大页，就是为这一条。

到这里你应该能回答：为什么"多级页表"能省内存，而"大页"能省 TLB？

2. 缺页：一句"按需分配"背后的五种代价

2.1 缺页是什么【事实】

缺页中断（page fault）：访问的虚拟页还没有对应的物理页（或权限不对）时，CPU 陷入内核，由内核处理。

【事实】分两类，代价差两个数量级（下表是量级参考，随硬件、内核版本、负载变化）：

类型情况量级
次要缺页（minor）页在内存里，只是还没建立映射（如刚 malloc 的第一次写）约 1 μs 量级（公开测量 0.5–2 μs）
主要缺页（major）页不在内存里，要从磁盘 / 交换空间读回来约 100 μs 量级（公开测量 50–200 μs，取决于存储设备）

【推导】把不同操作的量级放在一起看，差距有五个数量级：

TLB 命中            ≈ 1 ns        ← 正常路径（≈ L1 缓存访问延迟）
系统调用跨越        ≈ 100 ns
次要缺页            ≈ 1 μs        ← 第一次碰一页新内存
L3 访问             ≈ 30–50 ns    ← 作对照
主要缺页            ≈ 100 μs      ← 要从磁盘换回来（比 TLB 命中慢约 10 万倍）

【推导】这张表能推出三条实用结论：

1. malloc 之后第一次写会有 minor fault——所以"刚启动时慢"是正常的，预热（warm-up）不是玄学 2. major fault 是灾难性的（100 μs 相当于上千次系统调用）——所以"别让服务去 swap"是一条硬规矩（见 3.3） 3. "优化内存访问"的第一手段是提高 TLB 命中率（局部性、大页），不是减少 malloc 次数

2.2 从缺页推出 "malloc 成功 ≠ 有内存"【推导】

malloc(8GB) 的完整过程：
① 库向内核要 8GB     → 内核只"记一笔账"：这块虚拟地址区间归你了
                        【不分配任何物理页】→ 返回成功
② 你写第一页          → 缺页（minor）→ 这时才分配第一个物理页
③ 你继续写            → 每碰一个新页就缺页一次
④ 如果物理内存 + swap 不够了 → 触发 OOM（第 3 节）

【事实】这个行为由 vm.overcommit_memory 控制（/proc/sys/vm/overcommit_memory）：

值行为适用
0（默认）启发式：只拒绝"明显不合理"的请求（比如一次要得比内存+swap 总量还多很多）绝大多数场景
1永远允许：malloc 几乎不会返回 NULL申请巨大稀疏数组但从不碰满的场景（HPC）
2严格计账：承诺总量不超过 swap + RAM × overcommit_ratio/100（ratio 默认 50）想要"分配就失败"而不是"以后被杀"——但很多程序（尤其 JVM）会因此 fork 失败

【取舍】为什么默认是"启发式"而不是"严格"：因为 fork() 会让子进程的虚拟大小暂时翻倍（在 exec 之前），严格执行的话大量正常程序连启动都启动不了。这个取舍的代价就是：分配成功不代表有内存——所以 OOM 会在"用的时候"而不是"要的时候"发生。

到这里你应该能回答：为什么"申请成功"和"用得上"是两件事，这是设计缺陷还是刻意设计？

3. 量化：8GB 程序怎么跑在 4GB 机器上

3.1 三个量：VSZ、RSS、以及"承诺量"【事实】

先把三个容易混的概念分开：

指标含义看它有什么用
VSZ / total-vm虚拟地址空间大小，包含 mmap 的文件、地址预留基本没用（能大到很夸张却完全无害）
RSS常驻内存，真正占着物理页的部分这个才是"用了多少内存"
anon-rssRSS 里的匿名页（堆、栈）——OOM 被回收的才是这部分排查 OOM 时看它，不看 total-vm

【推导】"8GB 程序跑在 4GB 机器上"的答案就在这张表里：

VSZ  = 8 GB   （程序声明 / 预留的虚拟空间）
RSS  = 3 GB   （真正在用的）
机器 4 GB     → 跑得动

反过来的情形：
VSZ = 8 GB，RSS 涨到 4.5 GB → 触发回收 → 回收不动 → OOM

【推导】所以准确的回答是：*能不能跑不取决于程序"要多少"，取决于它实际碰了多少。虚拟内存把"要"和"用"解耦了，代价就是爆的时候是在运行中爆，不是在启动时爆。*

3.2 页缓存：不是"泄漏"，是可回收的【事实】

【事实】Linux 会主动把读过的文件缓存在内存里（页缓存 / page cache）。这部分被算进"已用内存"，但它随时可以被回收——free 里的 available 才是"真正还能用的"。

【推导】这是排查内存问题时最常见的误判源：

free -h 显示 memory used 90%  → 第一反应"内存泄漏了"
实际：其中很大一部分是页缓存，压力来了内核会自己丢掉
判断：看 free 的 available 列，不看 used
进一步：看 /proc/meminfo 的 MemAvailable

【事实】内存压力本身有专门的指标：/proc/pressure/memory（PSI，内核 4.20+）。some avg10 低于 5% 算健康、持续高于 20% 说明 OOM 很可能已经在路上（这是社区常用的经验阈值，不是官方定值）——比"等 OOM 日志"更早的预警。

3.3 swap：目的是"压力阀"，不是"扩内存"【取舍】

【取舍】swap 的定位要说准：

✅ 对：给冷页一个压力阀——把很久不用的页挪到磁盘，腾出物理内存给热数据
❌ 错：用 swap 来"扩充可用内存"
   → 一旦热数据被换出去，访问它就变成 major fault（百微秒量级）
   → 表现为"服务突然变得奇慢、CPU 不高、磁盘狂转"（thrashing）

【取舍】所以服务端两条经验：

  • 数据库、缓存类（Redis / MySQL）通常建议关掉 swap 或设很小——因为一次 major fault 是 10 万倍的代价，宁可 OOM 快速失败并告警，也不要拖着半死
  • 通用服务可以留少量 swap 当缓冲，但同时要监控 major fault 速率

3.4 大页：把 TLB 覆盖范围放大 512 倍【推导】

在 1.2 已经算过，这里是它的工程落点：

普通 4KB 页：STLB 1536 条目 → 覆盖约 6 MB
2MB 大页：    STLB 1536 条目 → 覆盖约 3 GB

【推导】结论：大页解决的是"工作集远超 TLB 容量"的场景（数据库缓冲池、JVM 堆）。代价是内存被按 2MB 粒度占用（小进程用了会浪费）与需要预留（不可交换）。

到这里你应该能回答：为什么数据库和 JVM 要配大页，而一个 50MB 的服务配大页没意义？

4. OOM：谁被杀，怎么算的

4.1 触发条件【事实】

【事实】OOM 在内核把所有回收手段都用完之后才发生：物理内存 + swap 都耗尽，页缓存、可回收匿名页、内存规整都试过了，仍然无法满足一次分配请求 → 触发 OOM killer。

4.2 杀谁：oom_score 是算出来的【事实】

【事实】内核用 oom_badness() 给每个任务打分，杀分数最高的那个：

points = (rss_anon + rss_file + rss_shmem + swapents + pgtables_pages)
       + (oom_score_adj × totalpages / 1000)

【推导】逐项读这个公式，能读出四条规则：

项含义推出
rss_anon + rss_file + rss_shmem占的内存越多分越高默认杀"最大内存占用者"
pgtables_pages页表本身也占内存一个疯狂映射大量小区域的进程，光页表就能成为被杀理由
swapents换出去的页也算换出去不等于不记账
oom_score_adj可调的偏移，范围 −1000 ~ 1000，默认 0这是唯一的干预手段：−1000 = 永不被杀；正值 = 优先被杀

【事实】还有几条硬规则：

  • init 进程和内核线程永不被杀（无法杀）
  • 与 victim 共享同一地址空间的进程会一起被杀（同一线程组的线程，所以"杀了个线程"实际是杀整个进程）
  • 5 秒内不会连续杀（内核会避免在短时间内连续多杀，造成雪崩式连杀）
  • oom_score 只在 4.13+ 才有 /proc/<pid>/oom_score 可读（早期只有 oom_adj）

4.3 两类 OOM：这是本卡最实用的一节【推导】

【推导】"整机还剩 40% 内存却 OOM 了"的答案在这里——OOM 有两类，作用范围完全不同：

整机 OOM（global）cgroup OOM
触发条件整机物理内存 + swap 耗尽某个 cgroup 撞到自己的 memory.max
日志前缀Out of memory:Memory cgroup out of memory:
杀谁全系统范围内按 oom_score 挑只在这个 cgroup 内部挑
整机内存必然紧张可能非常宽松（40%、60% 都可能）

【事实】cgroup v2 的关键旋钮：

memory.max          硬上限，超过 → 触发 cgroup OOM
memory.high         软上限，超过 → 只做限流和积极回收（不杀）
memory.oom.group    如果开启 → 整个 cgroup 一起杀（避免杀一半留一半）

【事实】Kubernetes 从 1.25 起默认 cgroup v2，1.31 移除了 v1 支持——所以现在容器里的"内存限制"就是 memory.max，超了就是 cgroup OOM。 而 systemd 服务的 MemoryMax= 也是同一个机制。

【推导】这就直接回答了本卡开头的第二个问题：

"整机还剩 40%，容器却被 OOM 杀了"
→ 这不是矛盾，是【cgroup OOM】
→ 容器的 memory.max 是 512MB，而它涨到了 600MB
→ 整机有多少内存跟它没关系
排查动作：去看 cgroup 的内存水位，而不是看 free -h

【事实】RuleArena 就是这种配置：08-capacity-cost-and-facts.md 里 Redis 容器只给 256~512MB。这个数字就是 memory.max，超了就是 cgroup OOM，跟宿主机内存无关。

4.4 怎么控制【取舍】

【取舍】按"最有效 → 最粗暴"排序：

手段做什么评价
MemoryMax= / memory.max（配 MemoryHigh）给每个服务一个硬上限最推荐。建议 MemoryHigh 设在 MemoryMax 下方 10–20%（经验建议），让内核算先回收而不是直接杀
OOMScoreAdjust= / oom_score_adj调整被杀优先级有效但要克制：别随便设 −1000，一个不可杀的进程会把"杀一个服务"升级成"杀不掉 → 内核 panic"
代码侧限流 / 队列上限 / 缓存上限从源头限制内存增长最根本。内存问题的根因几乎总是"某处队列 / 缓存无上界"
加内存——只是推迟问题。如果增长无上界，加多少都一样

5. 边界与常见误解

常见说法修正
"malloc 成功了就有内存了"【事实】只拿到虚拟地址空间，物理页在第一次访问（缺页）时才分配。所以 OOM 发生在运行中，不在申请时
"top 里 VSZ 很大，肯定内存泄漏了"【事实】VSZ 包含 mmap 文件与地址预留，基本没有参考价值。看 RSS；排查 OOM 更看 anon-rss
"free 显示内存用满 90%，要爆了"【事实】其中很多是可回收的页缓存。看 available 而不是 used，或用 MemAvailable
"被 OOM 杀了就是内存不够，加内存"【推导】先分清两类 OOM：整机 OOM（真不够）vs cgroup OOM（撞了容器自己的上限，宿主机可能很空）。日志前缀不同，排查方向完全不同
"OOM 会杀掉最占内存的进程"【事实】公式上内存占得多分高，但 oom_score_adj 可以翻转结果——所以"杀的不是最大的那个"是正常现象，先查 adj 有没有被人调过
"进程被杀了，只杀了一个线程"【事实】与 victim 共享同一地址空间的任务会一起被杀——"杀线程"实际是杀整个进程
"swap 开大点就不怕内存不够了"【取舍】swap 是压力阀不是扩容。热数据被换出去后访问它是 major fault（比 TLB 命中慢好几个数量级），表现为"CPU 不高、磁盘狂转、服务奇慢"，比干脆 OOM 更难排查
"大页就是更快"【推导】大页的真实作用是让 TLB 装得下（4KB 页只能覆盖约 6MB，2MB 大页能覆盖约 3GB）。小进程配大页没意义还浪费内存
"内存泄漏一定能很快发现"【推导】因为有"申请 ≠ 占用"，无上界的队列 / 缓存常常运行几天才爆。所以要在代码里给队列和缓存设上界（RuleArena 给 Redis 只留 256~512MB 就是这种约束）
"容器限制了内存，宿主机就不会 OOM"【事实】只约束了这个容器的上限，不保证它不超；超了是 cgroup OOM。而且宿主机上多个容器加起来仍可能把整机打满（那时才是整机 OOM）

1. 为什么 malloc 成功还会 OOM？

malloc 只拿到虚拟地址空间，物理页在首次访问（缺页）时才分配。所以问题是推迟到运行期才暴露的——而且 overcommit_memory=0（默认）是刻意这么设计的，因为 fork() 会让虚拟大小暂时翻倍，严格执行会连正常程序都起不来。

2. VSZ 很大是不是内存泄漏？

不是。VSZ 包含 mmap 的文件和地址预留，基本没有参考价值。看 RSS，排查 OOM 看 anon-rss（total-vm 在 OOM 日志里也印着，但它是"几乎无意义"的那个）。

3. OOM 会杀哪个进程？

按 oom_badness() 打分，内存占用（rss_anon + rss_file + rss_shmem + swap + 页表页数）占主导，再用 oom_score_adj × totalpages/1000 调整，杀分最高的。init 和内核线程不杀；与 victim 共享地址空间的一起杀；5 秒内不连杀。

4. 容器被 OOM 杀了怎么排查？

先看日志前缀分清是哪一类：Memory cgroup out of memory 是 cgroup OOM（撞了 memory.max，与宿主机剩余内存无关）；Out of memory 是整机 OOM。然后查 memory.max / memory.current，再判断是"渐涨撞上去"还是"一次性冲上去"。

5. swap 要不要开？

看负载。数据库 / 缓存类建议关或设很小（热数据被换出去后一次访问是微秒到百微秒量级，表现为"CPU 不高、磁盘狂转、服务奇慢"，比 OOM 更难查）；通用服务可留少量作压力阀，但要监控 major fault 速率。swap 的定位是压力阀，不是扩内存。

6. 怎么提前发现内存问题？

/proc/pressure/memory（PSI）：some avg10 低于 5% 健康、持续高于 20% 说明 OOM 可能已在前方。比等 OOM 日志更早，还能区分是内存压力还是 IO 压力。
  • 「free 显示内存用满怎么办？」——先看 available 不看 used，页缓存是可回收的；再看 PSI 判断压力。"用满"本身不是问题，回收不动才是
  • 「Redis 为什么要设 maxmemory？」——给无上界的东西设上界，是本卡 5.5 结论的直接应用（[[母题-R2-持久化与内存淘汰]]）
  • 「为什么 Kafka 快也和页缓存有关？」——Kafka 的顺序写 + 读都尽量落在页缓存上，避免真的走磁盘；这也解释了它为什么对内存量敏感（[[母题-O3-IO模型与零拷贝]]）
  • 「OOM 和 cgroup OOM 的内核路径有什么不同？」——整机 OOM 在全系统范围挑 victim，cgroup OOM 只在该 cgroup 内挑（mem_cgroup_scan_tasks）；后者的出现说明限额被撞了，而不是机器不够
