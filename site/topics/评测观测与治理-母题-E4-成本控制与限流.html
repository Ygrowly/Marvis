题目

面试官问——"你们怎么控成本？如果账单翻倍了你怎么查？限流限在哪里？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：成本要先归因，再动手

【推导】假设一个 Agent 系统的日成本构成是：

模型输入     60%
模型输出     20%
工具调用     15%
存储         5%

【推导】算一下"先动哪一刀"：

先砍工具（占 15%）：
  最多省 15%

先提缓存命中率（作用于输入的 60%）：
  假设输入里 80% 是可缓存的稳定前缀
  命中后按 0.1× 计价（[[母题-C6-成本与长上下文截断]]）
  省下 = 60% × 80% × 90% ≈ 43%

【结论】两个动作的收益差约 3 倍——而"砍工具"还会损失能力，"提命中率"是无损的。

【推论】所以顺序是"先动大头，先做无损的"（[[母题-C6-成本与长上下文截断]] 的降本四层）：

① 提缓存命中率   —— 无损，量级最大
② 去 prompt 拐杖 —— 双赢（同时提质）
③ 压缩 / 少放    —— 有损，要留指针
④ 调 effort / 换模型 —— 换质量，要 held-out 验证

【取舍】"账单翻倍了怎么查"的正确回答是"先归因"：

按【功能 / 租户 / 任务类型 / 模型 / 环节】拆开成本
→ 定位到"是哪一类请求涨了"还是"单次成本涨了"
→ 前者是流量问题，后者是效率问题 —— 【两件事的解法完全不同】

到这里你应该能回答：为什么"我们做了缓存和压缩"这句话，不能回答"账单为什么翻倍"？

2. 限流要分四层放【推导】

【推导】只在入口限流的漏洞：

入口限流 1000 QPS —— 看似保护了系统
但一个租户可以占满这 1000 QPS
  → 其他租户全部被拒
  → 【入口限流保护了系统，但没有保护公平】

而且 Agent 的一个请求可能触发几十次模型调用与工具调用
  → 1000 QPS 的入口流量，下游可能是 30,000 QPS
  → 【入口限流根本保护不了最贵的那个资源】

【事实】四个位置，各保护一样东西：

位置保护什么放太后面的后果
入口 · 总量整体不过载—— （最早、最粗）
租户 / 用户 · 公平防单租户打满没有它 → 入口限流对其他租户无意义
工具 · 外部依赖第三方配额（会被对方限）没有它 → 被对方限流时错误暴露得晚
模型 · RPM / TPM 与预算最贵、最容易失控的资源没有它 → 成本失控（[[母题-A1-计划执行循环与停止条件]] 的七种预算）

【推论】"限流"这个动作的本质是"保护某一条具体的资源"——所以要先问"我在保护什么"，再决定限流放哪。放错了位置，保护的就是错的东西。

【事实】超限之后不只是"拒绝"（这一点最容易被漏掉）：

① 排队（有界的等待 —— 无界排队等于把过载变成超时）
② 降级（切到备用配置 / 更小的模型）
③ 拒绝（快速失败，并给出可行动的错误）

【推论】"无界排队"是最差的处理——它把"立刻被拒"变成了"等 30 秒后被拒"，而等待期间连接、内存都被占着（[[母题-M4-索引代价与大表变更]] 的 MDL 连锁是同一个形状）。

到这里你应该能回答：为什么"我们在网关做了限流"这句话，对 Agent 系统来说远远不够？

3. 降级：把"不可用"换成"质量下降"【推导】

【事实】三级降级链路：

主配置（贵、准）
   ↓ 限流 / 超时 / 故障
备用配置（已验证）
   ↓ 仍不可用
排队 / 降级答复 / 拒绝

【推导】算一下降级的收益：

某服务主配置的可用性是 99%
每天 1,000 个请求 → 约 10 个失败

加降级链路后，可用性提到 99.9%
→ 约 1 个失败，另外 9 个变成"质量下降的结果"

【取舍】这笔交换是否划算，取决于业务：

能接受"质量降一点但一定有结果"  → 降级是对的
宁可失败也不能给错的结果        → 【不该降级，该拒绝】

【推论】所以"降级"不是一个技术默认值，是一次业务决策——面试里能说出"要看业务能不能接受质量下降"，比说"我们有降级链路"更像设计过。

【事实】一条硬要求（[[母题-C5-模型选型与降级三角]]）：备用配置必须是"已经用你自己的评测验证过的"，不是"顺手切一个"。

【推论】理由：换模型是最大的一次 prompt 变更——旧 prompt 是针对旧模型写的（[[母题-C3-Prompt版本管理与回归]]）。"顺手切一个"的结果是"可用性上去了、质量掉得比预期多"，而且你测不出来。

【事实】还有一条容易被漏掉：降级本身必须可观测——不知道自己在降级，比降级本身更危险。

到这里你应该能回答：为什么"我们有降级"这句话，必须先回答"降级后质量底线是什么"？

4. 成本归因的四个维度【事实】

【推导】"账单翻倍"要先答一个问题：是"量"涨了还是"单价"涨了：

量涨了：流量上升 / 重试变多 / 步数变多 / 上下文变长
单价涨了：换了更贵的模型 / 缓存命中率下降 / effort 调高了 / 输出变长

【事实】四个归因维度：

维度拆开看什么典型发现
功能 / 链路哪个功能花的钱某个实验性功能占了 40% 预算
租户 / 用户谁花得多一个租户的重试风暴
任务类型哪类任务贵长任务 vs 短问答差一个数量级
环节输入 / 输出 / 工具 / 缓存输入往往是大头，而它最容易被缓存优化

【推论】"环节"这一维最重要——因为它直接对应"该动哪一刀"：

输入占大头    → 提缓存命中率（无损、量级大）
输出占大头    → 收输出 / 调 effort（换质量）
工具占大头    → 合并工具调用（[[母题-A2-工具调用与MCP边界]] 的 consolidation）
存储占大头    → 降采样 / 缩短保留期（[[母题-E2-Trace与可观测性]] 的采样策略）

【推论】这就是"先归因再动手"的具体形态——没有归因，你只能凭"哪个词听起来更有道理"来选择动作。

到这里你应该能回答：为什么"成本优化"这件事，第一步不是"上手段"而是"拆账单"？

5. 边界与常见误解

常见说法修正
"我们加了缓存、压缩、换了小模型"这是清单，不是方法。要先归因：账单涨了是"量涨了"还是"单价涨了"？拆到"输入 / 输出 / 工具 / 存储"才对应得上动作——先动大头、先做无损的（提命中率 ≈ 43% vs 砍工具 15%）
"限流在网关做就够了"入口限流只保护整体不过载。一个租户就能占满入口配额（所以要有租户级）；而 Agent 一个请求会触发几十次下游调用（所以要有工具级与模型级）。四个位置各保护一样东西
"超限就排队，排到就好了"无界排队是最差的处理——它把"立刻被拒"变成"等 30 秒后被拒"，而等待期间连接和内存都被占着。排队必须有界，超了要走降级或拒绝
"降级就是把模型换小的"不是"换模型名"，是"换一组已经用你的评测验证过的配置"——因为换模型是最大的一次 prompt 变更（旧 prompt 是针对旧模型写的）。"顺手切一个"会让可用性上去了、质量掉得比预期多，而且你测不出来
"降级了但没人知道"降级本身必须可观测——"不知道自己在降级，比降级本身更危险"（[[母题-C5-模型选型与降级三角]]）。要有触发条件打点 + 质量底线告警
"成本优化就是把贵的地方调便宜"贵 ≠ 该动。要看"边际收益"：输入占 60% 且可缓存 → 动它省 43%；工具占 15% → 动它最多省 15% 还损失能力。先动大头、先做无损的
"降级总是比失败好"不一定。能接受"质量降一点但一定有结果" → 降级对；宁可失败也不能给错结果 → 该拒绝。（[[母题-C4-幻觉的成因与可控性]] 的"错误 vs 弃答分开定价"在这里再次成立）

【取舍】读成一句话：成本控制的第一性原理是"先归因、再动手、先动大头、先做无损的"；而限流的本质是"保护某一条具体资源"——所以它必须分四层放。

三 · 面试输出 闭卷口述 60 秒，再看结论

成本失控时该先动哪一刀——以及"限流"这个动作，到底在保护什么？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这道题最容易答成清单（"我们加了缓存、做了压缩、换了小模型"）。能说出"先归因再动手、先动大头"以及"限流保护的是具体某条资源"才算过关。 而且它和 [[母题-C6-成本与长上下文截断]] 是一对——C6 讲"钱花在哪"，E4 讲"怎么管住它"。

一句话结论 全卡唯一要背的锚点

成本控制的第一性原理是"先归因、再动手、先动大头、先做无损的"。先拆账单（按功能 / 租户 / 任务类型 / 环节拆），先回答"是量涨了还是单价涨了"——两件事的解法完全不同。环节这一维最重要，因为它直接对应动作：输入占大头就提缓存命中率（无损，本例能省 43%）、输出占大头就收输出 / 调 effort、工具占大头就 consolidation、存储占大头就降采样。降本有顺序且不可颠倒：提命中率（无损）→ 去拐杖（双赢）→ 压缩（有损）→ 调 effort / 换模型（换质量）。限流的本质是"保护某一条具体的资源"，所以要分四层放：入口（总量）· 租户（公平）· 工具（外部配额）· 模型（RPM / TPM 与预算）——只做入口限流，一个租户就能占满配额，而且 Agent 一个请求会触发几十次下游调用，网关看起来正常但模型 TPM 已经满了。超限后的处理顺序是"有界排队 → 降级 → 快速失败"，无界排队是最差的（把"立刻被拒"变成"等 30 秒后被拒"）。降级的本质是把"不可用"换成"质量下降"——这笔交换划不划算取决于业务（能不能接受质量降一点），而且备用配置必须是用你自己的评测验证过的，不是"顺手切一个"。

  • 环节）
  • 降本顺序（提命中率 → 去拐杖 → 压缩 → 调档位）
  • 先动大头（43% vs 7.5%）
  • 限流四层（入口

  • 可用性 99% → 99.9%（10 个失败 → 1 个 + 9 个质量下降）

展开（先自答，再看 · 默认收起，不进复训调度）

1. Agent 的成本怎么控？

按环节拆：输入（提缓存命中率，无损且量级最大）→ 输出（收输出 / 调 effort）→ 工具（consolidation，[[母题-A2-工具调用与MCP边界]]）→ 存储（采样，[[母题-E2-Trace与可观测性]]）。而且要按预算分档（[[母题-A1-计划执行循环与停止条件]] 的七种预算）。

2. 限流该限在哪里？

四层都要：入口（总量，最早最粗）、租户（公平，否则入口限流对其他租户无意义）、工具（保护第三方配额）、模型（RPM / TPM 与成本，最贵最容易失控）。

3. 超限之后怎么办？

有界排队 → 降级 → 快速失败（带可行动的错误）。关键是"排队必须有界"——无界排队会把过载悄悄变成全局超时。

4. 降级链路怎么设计？

三个要求：① 已验证（备用配置要过 held-out 门禁）② 有明确的质量底线（降级目标是保住可用性，不是保住质量）③ 可观测（降级本身要打点报警——不知道自己在降级，比降级更危险）。

5. 成本和质量的取舍谁来定？

能回答"一次失败值多少钱"的人。工程能给的是曲线（成本 vs 质量），把曲线交给业务方选点，比工程师替业务拍板更安全（[[母题-C5-模型选型与降级三角]]）。
  • 「P95 延迟和成本是不是一回事？」——不是，但它们经常同向。P95 高往往因为步数多 / 上下文长，而这两样也直接推高成本。但它们是两个独立的门禁指标（[[母题-E3-回归门禁与发布卡口]]）——成本降了但 P95 涨了，不一定能发。
  • 「怎么防重试风暴打爆成本？」——这是成本失控最常见的原因之一（raw 里的真实事故：队列积压 → 扩副本 → LLM 429 → 超时重入队 → 风暴）。手段：分层重试（只让一层重试，[[母题-A3-失败恢复与幂等]]）、max_retries 预算、退避 + 抖动（[[母题-M16-乐观锁与悲观锁]]）、按租户限流。

- EnergyOps：P95 重构的量化口径——要补齐样本数 / 并发 / 硬件 / 统计窗口才算硬证据；结算的三道质量门里的成本门。 - 数驭穹图：SQL 结果过大写 Artifact——这是"减少新增"而不是"压缩历史"，两者要配合。

先归因（四个维度 + "量 vs 单价"）→ 降本顺序与"先动大头"的算式 → 限流四层与各自的保护对象 → 超限的三种处理（强调有界）→ 降级是把什么换成什么（给可用性算式 + 业务判据 + 必须验证 + 必须可观测）→ 收束到"先看清再动手"

成本要先归因，限流要先问"保护什么"。 两件事的共同点是：都不能从"上一个手段"开始，而要从"看清问题的形状"开始——代价最高的一刀，往往是最后才该动的那个。
