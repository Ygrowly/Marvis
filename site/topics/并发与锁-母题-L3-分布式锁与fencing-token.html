题目

两个实例要抢同一份资源，单机的 mutex 管不到对方，于是上 Redis 分布式锁。上线后偶发"任务被跑了两次"，日志里两次执行都持有锁成功。为什么会这样？加个过期时间能解决吗？

一 · 教材 从前提推到结论，不需要先会

1. 前提：锁怎么跨过进程边界

1.1 为什么单机锁不够【事实】

【事实】单机锁（mutex / synchronized / 行锁）的可见范围止于一个进程——因为它本质上是同一块内存里的一个标记，而两个进程各有自己的地址空间（[[母题-O1-上下文切换与死锁]] 1.1）。

【推导】要跨机器，就必须把"锁的状态"放到一个两个进程都能访问的地方——于是有三种选择：

① 放在一个高性能的共享存储里     → Redis（最常见）
② 放在本来就是权威状态的数据库里 → 唯一约束 / 带条件更新
③ 放在一个专门的强一致协调服务   → ZooKeeper / etcd

记住这个分类方式：先问"我能不能把锁放到已经有的组件里"，答案常常是"能"——引入新组件是最后一步，不是第一步。

1.2 先问一个更重要的问题：真的需要锁吗？【取舍】

【推导】分布式锁是并发控制里最重的方案，因为它引入了一个新的可用性依赖：锁服务挂了，业务就卡住了。所以顺序应该是：

顺序方案什么条件下够用
① 幂等唯一约束 + 幂等键只要"重复执行无害"就够了——绝大多数场景都属于这一类
② 条件更新UPDATE ... WHERE 条件要"只生效一次"且状态在数据库里
③ 队列串行把竞争收进队列，单消费者处理该资源的处理本来就可以排队
④ 分布式锁见下上面都不行：必须"同一时刻只有一个在跑"，且跑的过程本身不能被重复（比如调度外部定时的批处理）

【取舍】关键判据：你要的是"不会被重复执行"，还是"不会同时在跑"？

  • 前者 → 幂等就够了（不需要锁）
  • 后者 → 才可能需要锁（典型的例子：只应该有一个实例去执行的定时任务）

【事实】RuleArena 的选择正是①：Redis 只负责队列、限流与短期进度，权威状态在 PostgreSQL——用"稳定幂等键 + 唯一约束"消化重复，不引入分布式锁。它连"锁"都没用，却得到了同样的正确性保证。

到这里你应该能回答：为什么"要不要用分布式锁"应该排在"能不能幂等"之后问？

2. 三种实现：各自解决什么、代价是什么

2.1 Redis【事实】

【事实】Redis 做锁的核心是一条原子命令：

SET lock:key <唯一值> NX PX <毫秒>
    NX = 只有 key 不存在时才设置（= 抢锁成功）
    PX = 同时设置过期时间（防止持有者挂掉后锁永不释放）

【推导】三个必须做对的地方：

要做的为什么
加锁必须用一条命令（SET ... NX PX）如果拆成"先 SETNX 再 EXPIRE"，中间挂了就是死锁（锁永不过期）
值要是唯一标识（UUID / 实例 ID）释放时才能确认"这是不是我加的锁"
释放必须校验值（GET 比对 + DEL，或直接用 Lua 脚本）否则会出现误删别人的锁：自己超时过期了，别人拿到锁，自己这时 DEL 一下把别人的删了

【事实】Redis 锁的天然弱点：主从复制是异步的——写进主节点、还没同步到从节点时主挂了，从节点被提升为新主，那把锁就"没存在过"，另一个人可以立刻拿到。Redlock（向多个独立 Redis 实例加锁）就是为了缓解这个问题而提出的（它也有公开争议，见 3.4）。

2.2 数据库【事实】

【推导】数据库本来就有"让一件事只发生一次"的能力，用它是三种里最不需要引入新组件的：

做法怎么用代价
唯一约束（推荐）往锁表插一条 (资源名) 唯一索引记录，插不进去就是没抢到最简单、语义最硬；释放就是删记录
带条件更新UPDATE 锁表 SET 持有者 = ? WHERE 资源 = ? AND 过期时间 < now()不需要单独的"抢锁"语句，还能顺便带过期
SELECT ... FOR UPDATE在事务里锁住那一行持锁时间 = 整个事务，把并发压在数据库上

【取舍】数据库做锁的最大代价是"锁争用直接压在数据库上"——锁本身也是流量。如果这把锁每秒要被抢几百上千次，你其实是在用数据库做一件 Redis 更擅长的事。

【事实】EnergyOps 用的正是"带条件更新"这一档：任务抢占不用锁服务，而是一条 UPDATE ... WHERE 状态 = 待处理 AND 租约版本 = 我看到的——改到 0 行就是没抢到（02-aggregation-and-recovery.md）。

2.3 ZooKeeper / etcd【事实】

【事实】这两者都是强一致的协调服务，做锁的方式与 Redis 不同：

机制特点
ZooKeeper临时顺序节点 + watch：排队、最小的那个拿到锁；会话断开则节点自动删除锁与会话绑定——客户端崩了锁自动释放，不用等 TTL
etcd租约（lease）+ revision：revision 单调递增，天然可以当 fencing token语义最干净，但要维护一套独立的强一致集群

【推导】它的优势正好补上 Redis 的两个短板：① 不怕"客户端挂了但锁没释放"（会话结束即释放）；② revision 单调递增，能直接做 token。代价是要多维护一套系统，对校招项目通常是过重的。

到这里你应该能回答：为什么"锁要跟会话绑定"比"锁要设过期时间"更强？

3. 失效的根因：锁服务的判断 ≠ 客户端的事实

3.1 三大失效场景【推导】

【推导】所有失效都来自同一个根因："锁是否还被持有"这件事，由锁服务根据时间判断；而"我是不是还在跑"这件事，只有客户端自己知道——两者会脱节。

场景发生了什么结果
① GC 停顿 / 线程长时间阻塞业务还没跑完，但进程被暂停了，没来得及续期 → 锁过期另一个人拿到锁，两个人同时在跑
② 时钟漂移过期判断依赖时间，机器之间时钟不一致过期时刻算错，窗口提前或延后
③ 网络分区客户端与锁服务之间断了；锁服务按租约到期释放客户端仍然认为自己持有，继续写

【推导】所以 TTL 的设置是一个无解的两难（自测 Q1 会完整算）：

TTL 设短 → 业务没跑完就过期 → 【两个持有者】
TTL 设长 → 持有者真挂了要等很久才释放 → 【可用性变差】

【没有"安全值"，只有"选哪种失效"。】 这句话是这道题的分水岭。

3.2 续期只能降低概率，不能消除【推导】

【推导】"看门狗"式续期（后台线程定期把 TTL 顶回去）能缓解，但缓解不了根因：

续期线程也是这个进程里的线程
→ 进程被 GC 暂停 / 被 SIGSTOP / 网络分区时，【续期和业务一起停】
→ 停的时间超过 TTL，锁照样过期
→ 而业务可能在恢复后继续执行 —— 于是两个持有者

【取舍】判据：续期把"锁过期"的概率从"业务超时"降到"进程被暂停超过 TTL"——后者概率更低，但在 GC 停顿长的语言（大堆 JVM）里一点也不低。

3.3 真正的解法：fencing token【推导】

【推导】换一个方向想：如果"锁"不能保证互斥，那就别让"锁"负这个责任。

fencing token 的做法：
  ① 每次发出锁的时候，附带一个【单调递增】的号（1, 2, 3, …）
  ② 写操作带上这个号
  ③ 【被保护的资源自己校验】：只接受号比上次更大的写入
     → 旧持有者的写入一定被拒绝

【推导】为什么这样才真正安全：

即使发生了"两个人同时持有"（GC / 分区 / 时钟任何一种）
  旧持有者（token = 33）写 → 资源发现当前已见过 34 → 【拒绝】
  新持有者（token = 34）写 → 接受
→ 互斥性由【资源侧】保证，不再依赖锁服务的判断

【取舍】代价：被保护的资源必须支持"带条件写"（能比较 token）。如果资源不支持（比如你在写一个第三方 API，人家只认"覆盖"），那就只能退到幂等——这就是为什么"锁"经常不如"幂等"划算。

【事实】etcd 的 revision 天然满足"单调递增"，所以它能直接当 token；Redis 需要一个额外的单调计数器（INCR）来实现。

3.4 Redlock 的争议：共识部分怎么讲【了解】

【取舍】面试里如果被问到，讲共识、别站队：

共识内容
单实例 Redis 锁在主从切换时会丢因为复制是异步的——这是双方都同意的问题
Redlock 想做的是"多数派加锁"向 N 个独立实例加锁，多数成功才算拿到
争议点是"它在极端场景下是否还能保证互斥"反对一方指出：它依赖假设的时钟漂移上限与有限停顿，而这些假设在真实系统里可能不成立；支持一方认为这些场景极罕见
双方都会同意的一句话需要严格正确性时，应该用 fencing token；讨论"用哪种锁"之前先讨论"资源侧能不能校验"

【了解】面试里给这一句就够了：*"Redlock 争的是概率边界；但无论哪种锁，要严格保证互斥，最终都要靠被保护资源侧的 token 校验——锁只能降低概率。"*

到这里你应该能回答：为什么"用了分布式锁还是可能重复执行"这件事无法靠"换一个更好的锁"解决？

4. 边界与常见误解

常见说法修正
"加个过期时间就安全了"【推导】过期时间只能解决"持有者挂了锁不释放"，解决不了"持有者还活着但锁过期了"。后者会直接产生两个持有者（GC / 分区 / 时钟三种成因）
"分布式锁保证了互斥"【推导】严格说：不能。它给的是"大概互斥"——除非被保护的资源自己校验单调递增的 token。锁降低概率，资源侧的校验才给保证
"用 Redis 锁就够了"【事实】单实例 Redis 锁在主从切换时会丢（异步复制）。而且它引入了一个新的可用性依赖：Redis 挂了，业务也卡住
"先加锁再说，锁总归是保险的"【取舍】锁是并发控制里最重的方案。先问"能不能幂等 / 条件更新 / 队列串行"——大多数场景用幂等就够了，而且不依赖锁服务的可用性
"续期（看门狗）能彻底解决过期问题"【推导】不能：续期线程也在同一个进程里，进程被暂停时续期和业务一起停。它只是把概率降低
"锁要设过期时间，所以要选个合适的值"【推导】这个值没有安全解（Q1 的两难）：短了会双持有者，长了可用性差。正确动作是加 fencing token，而不是继续调 TTL
"释放锁直接 DEL 就行"【事实】会误删别人的锁——你超时过期后别人拿到了锁，你这时 DEL 删的是别人的。必须校验值（比对 + 删除，或 Lua 保证原子）
"加锁和 SETNX 加 EXPIRE 一样"【事实】不一样：两条命令中间挂了就是死锁（锁永不过期）。必须用一条 SET ... NX PX
"分布式锁能保证任务只执行一次"【取舍】不能。要"只执行一次"应该用幂等（[[母题-Q2-重复与乱序]]）。锁能保证"不同时跑"，保证不了"不重复跑"
"ZooKeeper 锁比 Redis 锁性能差，所以不用"【取舍】两条都对一半：ZK 的强一致语义确实更干净（会话绑定、revision 可做 token），代价是要多维护一套集群。选型看"你已经有哪个"与"正确性要求有多硬"

一句话结论 全卡唯一要背的锚点

跨机器互斥要把锁状态放到一个共享的地方，三种实现各有代价：Redis（SET ... NX PX 一条原子命令 + 释放要校验值；弱点是主从异步复制，切换会丢锁）、数据库（唯一约束 / 带条件更新，不引入新组件但把锁争用压在数据库上）、ZooKeeper / etcd（临时顺序节点 / 租约 + 单调 revision，语义最干净但要维护一套强一致系统）。它们的共同弱点来自同一个根因：锁服务的判断（按时间）与客户端的事实（是不是还在跑）会脱节——GC 停顿、时钟漂移、网络分区都会产生"两个持有者"，而 TTL 没有安全值（短了双持有者、长了可用性差，且"最长停顿"无上界）。所以真正的解法是把安全性搬到被保护的资源上：fencing token（单调递增号）+ 资源侧拒绝更小的号。但更该先问的是："我到底要'不同时跑'还是'不重复执行'？"——后者靠幂等就够了（RuleArena 连锁都没用），锁只在地一步之后才考虑，而且它的作用是"减少干扰"，不是"保证正确性"。
  • 单机锁止于进程
  • 三种实现（Redis / 数据库 / ZK-etcd）
  • SET ... NX PX 必须一条命令
  • 释放要校验值（否则误删别人的锁）
  • Redis 弱点是异步复制丢锁
  • 数据库做锁把争用压在库上
  • ZK 会话绑定 + revision
  • 失效根因：锁服务按时间判断 vs 客户端的事实
  • GC 停顿 · 时钟漂移 · 网络分区
  • TTL 没有安全值
  • 续期只能降概率（续期和业务一起停）
  • fencing token = 单调递增号 + 资源侧拒绝更小的号
  • Redlock 争的是概率边界
  • "只执行一次"是幂等问题不是锁问题
  • 先幂等 → 再锁减少干扰 → 最后 token

  • 结论：三种实现各有代价；共同弱点是时间判断与客户端事实脱节，根治靠 fencing token；先问"互斥还是不重复"。
  • 推导链：共享状态 → 三种实现 → 时间 vs 事实脱节（GC/时钟/分区）→ TTL 无安全值 → 安全性搬到资源侧 → 幂等可能比锁更划算。

1. 锁过期了业务还在跑怎么办？

加 fencing token：发锁时给单调递增号，写入由存储校验"只接受更大的号" → 旧持有者的写被拒。同时把长业务改成分批 + 每批重新抢锁，把损失限制在一批内。

2. 为什么分布式锁不能保证互斥？

因为它依赖"锁服务对时间的判断"，而这可能与"客户端是不是真的在跑"脱节（GC 停顿 / 时钟漂移 / 网络分区）。TTL 的取值是个两难，没有安全解。

3. Redlock 有什么问题？

它想用"向多数实例加锁"缓解单实例丢锁，但反对意见指出它依赖假设的时钟漂移上限与有限停顿；两方都同意的是：要严格正确性就得用 fencing token。（面试讲到这一层即可，不必站队）

4. 什么时候该用分布式锁、什么时候不该？

先问"要的是不同时跑，还是不重复执行"：后者用幂等（更便宜、不引入新依赖）；只有"重复执行的代价极高、必须串行"时才上锁。RuleArena 连锁都没用，靠幂等键 + 唯一约束就够了。

5. 释放锁为什么不能直接 DEL？

会误删别人的锁：你过期后别人拿到了锁，你这时 DEL 删的是别人的 → 于是"一个删锁动作制造了一次双重执行"。必须校验值（GET 比对 + DEL，用 Lua 保证原子）。
  • 「单机的 mutex 和分布式锁差别在哪？」——共享状态的可见范围：mutex 在同一块内存里（[[母题-O1-上下文切换与死锁]]），分布式锁在共享存储里。前者的失败模式是死锁，后者的失败模式是"两个持有者"
  • 「选主（leader election）和分布式锁有什么区别？」——本质同一件事（都要"最多一个"），但选主的持有期更长，所以更依赖租约 + 心跳 + token；etcd 的 election 与 lease 就是为这个场景设计的
  • 「数据库的唯一约束能当锁吗？」——能，而且常常是更好的锁：不引入新组件、语义硬、和业务状态同事务。代价是锁争用变成数据库流量（[[母题-P19-唯一约束与UPSERT]]）
  • 「条件更新和分布式锁怎么选？」——能用条件更新就别用锁：它把"抢"变成"一条原子语句"，不需要过期、不需要续期、不需要校验 token（[[母题-L1-乐观锁与悲观锁]] 2.3）

RuleArena——"不用锁"的完整示范：Redis 只做队列、限流与短期进度，权威状态在 PostgreSQL；靠"稳定幂等键 + 同事务唯一约束"消化至少一次投递。它接受"重复执行"，所以从根上不需要互斥保证。

先问"真的需要锁吗"（幂等 / 条件更新 / 队列排在前）→ 三种实现的机制与代价 → 失效的根因（锁服务按时间判断 vs 客户端事实） → 三大场景（GC / 时钟 / 分区）→ 用 TTL 两难说明"没有安全值" → 续期只能降概率 → fencing token 才给保证 → Redlock 争议的共识部分 → 边界与误解

锁能买到的只有"大概互斥"，买到"一定互斥"的从来不是锁，而是被保护资源自己的校验。 所以判断顺序永远是：先让重复无害（幂等）→ 再考虑用锁减少干扰 → 最后才用 token 补上保证。把这三步的顺序倒过来（先加锁、以为就安全了）是这一块最典型的错。
