题目

同一个事务里执行两次 SELECT，结果不一样。这是 bug 吗？该把级别调高吗？

一 · 教材 从前提推到结论，不需要先会

1. 默认值：第一处必须说对的差异

MySQL（InnoDB）PostgreSQL
默认隔离级别REPEATABLE READREAD COMMITTED
幻读防护next-key lock（间隙锁）无间隙锁，靠快照 / SSI
写冲突表现等待锁（可能超时/死锁）报 40001，让应用重试
RR 下的写冲突等待 / 死锁直接报错中止

为什么这个默认值差异重要：MySQL 的 RR 让很多「本来会出现的读不一致」被默认挡住，所以从 MySQL 过来的人习惯性地假设「事务内读是一致的」；而 PG 默认不保证这一点。面试里只要开口说「PG 默认也是 RR」，后面所有关于并发行为的判断都会被怀疑。

【事实】PG 其实只实现了三种级别——官方原话：

在 PostgreSQL 里你可以请求四种标准级别，但内部只实现了三种不同的隔离级别——PG 的 Read Uncommitted 模式的行为等同于 Read Committed。

（因为这是把标准级别映射到 PG 的 MVCC 架构上唯一合理的做法。）

所以「PG 支持四种级别」这句话是错的：你写 READ UNCOMMITTED 也不会读到脏数据，它被静默升成了 RC。

2. 快照粒度：理解一切的关键

级别快照什么时候取
READ COMMITTED（默认）每条语句开始时各取一次
REPEATABLE READ（PG 的快照隔离）事务里第一条非事务控制语句开始时取一次，整个事务都用它
SERIALIZABLE同上，外加一层序列化异常检测

【事实】官方对 RC 的措辞把三件事一次说清：

一个 SELECT（不带 FOR UPDATE/SHARE）只看到【查询开始之前】已提交的数据，它既看不到未提交的数据，也看不到在本查询执行期间被其他事务提交的改动。

而且要注意：即使在一个事务里，两条相继的 SELECT 也可能看到不同的数据——只要在第一条开始之后、第二条开始之前有别的事务提交了改动。

所以 RC 下：

事务 A                                    事务 B
BEGIN
SELECT balance  → 100
                                          UPDATE ... COMMIT（改成 80）
SELECT balance  → 80     ← 同一事务，结果变了

这不是 bug——两条语句各自取了自己的快照，各自看到了当时已提交的最新数据。

RR 下这两条都会返回 100（整个事务用同一快照）——这才叫「可重复读」。

【事实】PG 的 RR 比 SQL 标准更强——官方原话：

这是一个比 SQL 标准对该级别的要求【更强】的保证，它阻止了表 13.1 里描述的所有现象，除了序列化异常。标准只描述每个级别必须提供的【最低】保护，所以更强的保证是被允许的。

【推导】强在哪，用官方那张表看最清楚：

级别脏读不可重复读幻读序列化异常
Read uncommitted标准允许，但 PG 里不会可能可能可能
Read committed不会可能可能可能
Repeatable read不会不会标准允许，但 PG 里不会可能
Serializable不会不会不会不会

【结论】PG 的 RR 是「快照隔离」——它挡住幻读靠的是「整事务一个快照」，不是靠锁。 这就是为什么 PG 不需要间隙锁（[[母题-P10-无间隙锁与锁变体]]）。

到这里你应该能回答：为什么「PG 的 RR 和 MySQL 的 RR 都叫 Repeatable Read，但机制完全不同」？

3. RR 的代价：写冲突直接报错【事实】

这是 PG 最反直觉、也最能体现「快照 + 报错重试」哲学的一段。官方原文：

UPDATE / DELETE / MERGE / SELECT FOR UPDATE / SELECT FOR SHARE 和 SELECT 一样只找【事务开始时刻】已提交的目标行。但这样一行可能已经被另一个并发事务改过或锁住了。这时 RR 事务会等第一个更新者提交或回滚。

如果第一个更新者提交了（并且真的改过或删除了该行，而不只是加锁），那么 RR 事务会被回滚，报：

```

ERROR: could not serialize access due to concurrent update

```

因为 RR 事务不能修改或锁住那些【在它开始之后】被其他事务改过的行。

应用收到这条错误时，应该中止当前事务并从头重试整个事务。

【推导】两种级别的同一个场景，结果完全不一样：

场景：事务 A 在 RR 下 UPDATE 一行，这一行已被事务 B 改过并提交

【RR】
  → A 报 40001，整个事务作废
  → 应用必须从头重试
  → 但 A 看到的数据从头到尾是一致的

【RC】
  → 官方原话：A 会【忽略被删的行】，否则【对更新后的版本施加自己的操作】
  → 而且命令的 WHERE 条件会被【重新求值】，看新版本是否仍匹配
  → A 不报错，但 A 的视角【变了】

【推论】这就是那道题的答案：

PG 把「数据可能已经变了」这个事实，在 RC 下处理成「重新读最新的」，在 RR 下处理成「报错让你重来」。

前者静默、不中断；后者显式、要重试。

没有哪个更"好"——RC 的代价是可能产生业务层面的不一致，RR 的代价是可能失败。 选级别，本质上是在选「你想要哪种代价」。

【事实】那为什么 PostgreSQL 官方建议应用"必须准备重试"？ 因为官方对 RC 之外的级别有一句明确的提醒：

使用这个级别的应用【必须准备好因为序列化失败而重试事务】。

【纠正常见误解】这条同样适用于 RC——RC 下 UPDATE 冲突不报错，但它"重新读最新版本再改"这件事本身，就可能让业务逻辑的前提失效（你基于旧值做的判断，被应用到了新值上）。所以"RC 不会失败"是错觉：它只是把失败从【数据库报错】挪到了【业务结果不对】。

到这里你应该能回答：为什么「把隔离级别调高」不是免费的——它把什么换成了什么？

4. Serializable：不额外阻塞，只检测并中止【事实】

官方原文：

这个级别的工作方式和 Repeatable Read 完全一样，【除了】它还会监控那些可能让并发执行的结果与任何串行顺序都不一致的条件。

这种监控除了 RR 本来就有的阻塞之外，【不引入任何额外的阻塞】——但监控本身有开销，而且一旦检测到可能造成序列化异常的条件，就会触发一次序列化失败。

【推导】用官方那个例子把 SSI 在防什么讲清：

初始：class=1 有 (10, 20)，class=2 有 (100, 200)

事务 A（Serializable）：SELECT SUM(value) WHERE class=1  → 30
                      INSERT (class=2, 30)
事务 B（Serializable）：SELECT SUM(value) WHERE class=2  → 300
                      INSERT (class=1, 300)

两边都提交时：
  如果是 RR → 【两个都被允许提交】
  但没有任何串行顺序能产生这个结果：
    若 A 先执行，B 会算出 330
    若 B 先执行，A 会算出 330
  → Serializable 会让其中一个提交、另一个回滚并报：
     ERROR:  could not serialize access due to read/write dependencies among transactions

【结论】SSI 防的是「单独看每个事务都没问题、但合起来没有任何串行顺序能解释」这件事——这叫写偏斜（write skew），RR 挡不住它。

【推论】判据：

RR 保证「你看到的一致」，Serializable 保证「结果能解释成某种串行顺序」。 后者更强，但失败率也更高——因为它检测的范围更大。

【事实】一个很实用的特例：可延迟的只读事务（SERIALIZABLE READ ONLY DEFERRABLE）读到的数据在读到的那一刻就是有效的——因为它会等到能拿到一个保证没有这类问题的快照之后才开始读。做长报表、一致性快照导出时，这是最干净的做法。

5. 一个连带的坑：序列不是事务性的【事实】

官方专门用一段 "Important" 提醒：

有些 PostgreSQL 数据类型和函数在事务行为上有特殊规则。特别是：对序列的改动（因此也包括 serial 声明列的那个计数器）【对其他所有事务立即可见】，而且【即使改动它的事务中止了也不会回滚】。

【推论】这是「自增主键为什么一定有洞」的第二个原因（第一个是「分配出去就算用过」）——它是事务可见性模型的一个明确例外。在 RR 事务里，你可能看不到别人刚提交的行，但你一定能看到自增值已经跳过去了。 面试里能主动说出这条，说明你读的是文档而不是二手总结。

到这里你应该能回答：为什么「事务里回滚了，自增值也该回退」这个期待是错的？

6. 快照的隐藏成本：它挡住了 VACUUM

【推导】隔离级别选得越高，持有的快照越旧、越久——而旧快照是 VACUUM 的天敌：

一张表写 500 TPS
一个 RR / Serializable 事务跑了 10 分钟

这个事务的快照固定在开始那一刻
  → 它【之后产生的所有死元组都不能被回收】
  → 10 × 60 × 500 = 【30 万个死元组被压住】

后果：表膨胀、索引膨胀、查询越来越慢
（这正是主线五的主题，见 P14 / P15）

【结论】「把级别调高更安全」这句话，在 PG 里还有一个反向代价：它让表膨胀得更快。

【取舍】所以正确的动作是：

  • 默认保持 RC——绝大多数业务读不需要事务级一致性；
  • 只在真正需要「事务内一致读」的地方（对账、生成报表、跨表一致性校验）提升到 RR，而且把事务做得尽量短；
  • 不要"为了安全"把全局默认调成 RR——那是把全局的事务时长都变成了膨胀源。

到这里你应该能回答：为什么「全局调高隔离级别」在 PG 里是一个会反噬的决定？

7. 边界与常见误解

说法实际情况
「PG 默认也是 RR」PG 默认是 READ COMMITTED；MySQL 才是 RR
「PG 支持四种隔离级别」内部只实现三种——READ UNCOMMITTED 被静默当成 RC
「同一事务两次读不同是 bug」RC 下是规范行为——每条语句各取一次快照
「调高到 RR 就没有并发问题了」RR 挡不住写偏斜（那是 Serializable 的活），而且写冲突会变成 40001
「40001 是数据库出故障了」是隔离级别的正常输出——应用的正确答案是重试整个事务，不是加锁
「Serializable 会让并发变慢（到处加锁）」官方明确：除了 RR 本来就有的阻塞，它不引入额外阻塞；代价是监控开销 + 更高的中止率
「事务回滚了，自增值也要回退」序列不是事务性的——立即可见、不回滚

三 · 面试输出 闭卷口述 60 秒，再看结论

PG 默认是 RC 还是 RR？同一事务内两次查询为什么会看到不同结果？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是「PG 与 MySQL 最容易说错的七处」里的第一条——MySQL 默认 RR，PG 默认 RC。而且它的反直觉程度最高：「同一事务内读到不一样的结果」在 PG 的默认级别下不算 bug，是规范行为。 如果这条说错，后面 MVCC、锁、膨胀全都跟着错。

一句话结论 全卡唯一要背的锚点

PG 默认 READ COMMITTED。RC 下每条语句开始时取一次快照，所以同一事务里的两条 SELECT 之间如果有别的事务提交，你就会看到不同的结果——这是规范允许的不可重复读。要事务内一致就提到 REPEATABLE READ（PG 的 RR 是快照隔离，整个事务一个快照，而且连幻读也一并挡住了）；但 PG 的 RR 遇到写冲突会直接报 40001 让你重试，它不靠间隙锁把冲突挡住（那是 MySQL 的做法，见 [[母题-P10-无间隙锁与锁变体]]）。
  • 默认 RC
  • 每条语句一个快照 vs 每事务一个快照
  • RR = 快照隔离且挡幻读
  • RR 写冲突报 40001
  • Serializable = 不额外阻塞、只检测中止
  • 快照留久 = 挡住 VACUUM
  • 必须准备重试

卡住时靠这几个词重建整条链。

1. PG 为什么不加间隙锁？

因为它用快照隔离，幻读已经被快照挡住了，不需要用锁挡。 加间隙锁会让并发插入互相阻塞（MySQL 的死锁大头就来自这里）。这是 PG 用「快照 + 报错」换「锁 + 等待」的一个具体体现（[[母题-P10-无间隙锁与锁变体]]）。

2. Serializable 是不是就万无一失了？

一致性上万无一失，可用性上更容易失败：它连写偏斜都检测，所以中止率更高。而且它要求「读到的数据在事务成功提交前都不算数」——包括只读事务（除非用 READ ONLY DEFERRABLE）。所以它适合"正确性压倒一切"的场景，不适合高并发写入的常规业务。

3. 40001 和死锁（40P01）有什么区别？

40001 是「你的快照过期了，重来一次就好」，没有等待、没有资源占用；死锁是「两个事务互相等对方的锁」，需要一个被牺牲掉。前者是快照隔离的正常输出，后者是加锁模型的固有代价——PG 两种都有，但 40001 是它主动选择的。

4. FOR UPDATE 能不能替代提高隔离级别？

能替代一部分。SELECT ... FOR UPDATE 在 RC 下也会锁住读到的行，所以"读-改-写"这种最常见的竞态可以直接用它防住，不必升到 RR。PG 还有四种变体（FOR UPDATE / FOR NO KEY UPDATE / FOR SHARE / FOR KEY SHARE），选最弱的那一个能显著减少锁冲突（[[母题-P10-无间隙锁与锁变体]]）。

5. 只读副本上的读一致性怎么办？

副本上的默认也是 RC，但副本有额外一层：复制延迟。要在副本上做「事务内一致读」，RR 只保证副本自身快照一致，不保证读到主库最新——要读最新得走主库，或者用复制槽 / pg_last_wal_replay_lsn() 做等待（[[母题-P12-流复制与逻辑复制]]）。
  • 「MySQL 的 RR 和 PG 的 RR 差多少？」—— 三处：① MySQL RR 用 next-key lock 挡幻读，PG 用快照挡；② MySQL RR 写冲突是等待（可超时/死锁），PG RR 写冲突是报 40001；③ MySQL RR 事务内的一致性读更"重"（因为要维护锁），PG 更轻但要处理重试。两边同名的级别不是同一件东西（[[母题-M8-隔离级别与ACID]]）。
  • 「为什么 PG 文档反复强调"应用必须准备重试"？」—— 因为 PG 的一致性模型把失败【暴露】给应用了：RC 下它把失败藏进业务结果里，RR/Serializable 下它明确报错。 这条提醒本身，就是「PG 把选择权交给应用」的体现。

- RuleArena 的状态机更新（status 条件更新——这正是 RC 下「WHERE 重新求值」发挥作用的场景：两个 worker 抢同一个任务，第二个会发现条件不再匹配）。 - EnergyOps 的对账与聚合（需要事务内一致读 → 显式 RR，并且事务要短）。 - 数驭穹图的目录/权限校验（读一致性敏感 → 值得用 RR；但如果并发写少，RC 就够）。

PG 默认 RC（对比 MySQL 的 RR）→ 快照粒度差异（语句 vs 事务）→ 所以「两次查询不同」是规范行为 → RR 的代价是写冲突要报 40001 → RC 下 UPDATE 的特殊行为 → Serializable 做了什么 → 快照的隐藏成本 → 怎么选

隔离级别在 PG 里承诺的是「你能看到什么」，不是「你不会失败」。 级别越高，看到的越一致，但越可能被要求重试——这是 PG 与 MySQL 的哲学差异：PG 用「快照 + 报错重试」换掉了「加锁等待」。
