题目

同一个事务里，两条完全一样的 SELECT 返回了不同的行。这算 bug 吗？

主卡

在这里练也可以，评分会进训练台的复训调度。

为什么重要：这是「PG 与 MySQL 最容易说错的七处」里的第一条——MySQL 默认 RR，PG 默认 RC。而且它的反直觉程度最高：「同一事务内读到不一样的结果」在 PG 的默认级别下不算 bug，是规范行为。 如果这条说错，后面 MVCC、锁、膨胀全都跟着错。

恢复关键词

  • 默认 RC
  • 每条语句一个快照 vs 每事务一个快照
  • 快照隔离 SI
  • 写冲突要重试
  • RC 下 UPDATE 会重新检查最新版本
  • 快照基于事务开始时间

卡住时靠这几个词重建整条链。

展开（默认收起，不进复训调度）

RuleArena 的任务状态机与退款路径（条件更新能在 RC 下安全工作，正是因为这里说的「重新判定 WHERE」）；EnergyOps 的结算批处理（如果要求「整批基于同一时刻」，那就是该用 RR 的场景，同时必须能重试）。方言差异（面试安全底线）：MySQL 默认 RR + 间隙锁；PG 默认 RC + 快照 + 报错重试。绝对不要说「PG 的 RR 也靠间隙锁」——PG 根本没有间隙锁。

PG 默认 RC（对比 MySQL 的 RR）→ 快照粒度差异（语句 vs 事务）→ 所以「两次查询不同」是规范行为 → RR 的代价是写冲突要报错 → RC 下 UPDATE 的特殊行为 → 怎么选

隔离级别在 PG 里承诺的是「你能看到什么」，不是「你不会失败」。 级别越高，看到的越一致，但越可能被要求重试——这是 PG 与 MySQL 的哲学差异：PG 用「快照 + 报错重试」换掉了「加锁等待」。

通过证据：能用「快照粒度」解释「同一事务两次查询结果不同」，并说清 RC / RR 在写冲突上的不同表现（等锁 vs 报错重试）。

正文底稿

原理分解

一、默认值：第一处必须说对的差异

MySQL（InnoDB）PostgreSQL
默认隔离级别REPEATABLE READREAD COMMITTED
幻读防护next-key lock（间隙锁）无间隙锁，靠快照 / SSI
写冲突表现等待锁（可能超时/死锁）报 40001，让应用重试

为什么这个默认值差异重要：MySQL 的 RR 让很多「本来会出现的读不一致」被默认挡住，所以从 MySQL 过来的人习惯性地假设「事务内读是一致的」；而 PG 默认不保证这一点。面试里只要开口说「PG 默认也是 RR」，后面所有关于并发行为的判断都会被怀疑。

二、快照粒度：理解一切的关键

级别快照什么时候取
READ COMMITTED（默认）每条语句开始时各取一次
REPEATABLE READ（PG 的快照隔离）事务开始时取一次，整个事务都用它

所以 RC 下：

事务 A                                    事务 B
BEGIN
SELECT balance  → 100
                                          UPDATE ... COMMIT（改成 80）
SELECT balance  → 80     ← 同一事务，结果变了

这不是 bug——两条语句各自取了自己的快照，各自看到了当时已提交的最新数据。

RR 下这两条都会返回 100（整个事务用同一快照）——这才叫「可重复读」。

三、RC 下一个必须知道的细节：UPDATE 会看到「最新的那一行」

RC 下，当你 UPDATE 一行时，如果这一行在语句执行期间被别人改过，PG 的规则是：

重新读取该行的最新已提交版本，重新判定 WHERE 条件是否仍成立，成立才更新；不成立就跳过（受影响的可能比你以为的少）。

为什么这条重要：它解释了两件常见现象——

  • UPDATE ... WHERE status = 'QUEUED' 在 RC 下是「相对安全」的：因为重新判定时会发现 status 已经不是 QUEUED 了，于是跳过。这正好是 P18 条件更新能成立的基础。
  • 反面：它也可能让你「以为改了一行、实际没改」，所以必须用影响行数判断结果，不能假定一定成功。

四、RR 的代价：写冲突会报错

PG 的 REPEATABLE READ 是快照隔离。当两个事务基于同一个旧快照去改同一行时，第二个会拿到：

ERROR: could not serialize access due to concurrent update (SQLSTATE 40001)

这不是故障，是设计：要么让你看到一致快照、要么明确告诉你没改成功，二者不能都要。 所以 PG 的做法是「报错 + 应用重试」，而不是 MySQL 那样「加锁等待」。

所以把级别提到 RR 的那一刻，你的应用就必须能重试事务（见 P9）。

五、怎么选（面试收尾）

场景选择
绝大多数业务读写RC（默认）——每条语句看最新已提交数据，最接近直觉，并发冲突最少
一条事务里需要多次读同一批数据保持一致（对账、汇总计算）RR，并且整套写路径要能处理 40001 重试
有跨行不变量、写偏斜风险Serializable（SSI），同样要能重试（P9）
只读报表RC 或 RR 都行，但注意长事务对膨胀的影响（P14）

一句判据：能接受「读到别人刚提交的数据」就用 RC；需要「整段计算基于同一时刻」就往上提，同时接受重试。
