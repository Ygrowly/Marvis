题目

面试官问——"Agent 的计划是模型自己定的，它还会中途改，你怎么保证它不跑偏？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：动态计划的问题不是"会变"

【推导】先纠正一个常见的误解：

错的问法：怎么让模型不改计划？
   → 动态计划的价值就在于【能根据观察到的情况调整】
   → 要求它不变，等于放弃 Agent 相对 Workflow 的全部优势

对的问法：计划变了之后，怎么保证【变化是可见的、可回溯的、可验证的】

【推导】"跑偏"最难的地方：

模型偏离原计划时，它通常【看起来很正常】：
  它还在调工具、还在产生输出、还在"推进"
  → 没有任何一个信号告诉你"它在做的不是原来那件事"
  → 直到最后交付了一个偏掉的结果，你才知道

【推论】这才是动态计划的真正风险：不是"它会变"，是"变了没人知道，而且回不去"。

到这里你应该能回答：为什么"Agent 跑偏"这件事，往往到最后一步才被发现？

2. 计划必须离开模型的上下文【推导】

【推导】计划只活在上下文里会发生什么：

第 1 步：模型想出一个计划（写在它的上下文里）
第 40 步：上下文被压缩 / 重置（[[母题-A5-上下文压缩与记忆]]）
        → 【计划丢了】，只剩摘要里的残余
        → 模型开始凭印象干活
        → 越走越偏，而且没人看得出

【事实】OpenAI 的做法是把计划变成一等产物：

"Plans are treated as first-class artifacts. Ephemeral lightweight plans are used for small changes, while complex work is captured in execution plans with progress and decision logs that are checked into the repository. Active plans, completed plans, and known technical debt are all versioned and co-located…"

【推论】"checked into the repository" 这几个词是关键——它把计划从"模型的短期记忆"变成了"版本的、可 diff 的、可被检查的产物"。于是：

① 上下文压缩不影响它        → 从磁盘读回来就行
② 偏离变成【可见的 diff】     → 人不必读全过程，只需要看计划变了没有
③ 计划本身可回溯            → 能回答"当时为什么这么打算"

2.1 外化的成本【推导】

一个 100 步的任务，平均修订计划 8 次
每次修订产生一个新版本，约 2 KB
总存储 = 8 × 2 KB = 16 KB

而上下文里丢一次计划的代价 = 整个任务重跑或结果作废

【结论】16 KB 的版本化成本，换来"计划不会丢 + 偏离可见"——这笔账不需要算。

【推论】这也解释了为什么"记忆/计划要写文件"是 Agent 的一个核心模式：写文件的成本是 O(KB)，而上下文里的信息会在压缩时被有损地丢掉的（[[母题-A5-上下文压缩与记忆]] 的"摘要只留指针"）。

到这里你应该能回答：为什么"让模型把计划记在心里"这种设计，在长任务上一定会出问题？

3. 可读性：agent 访问不到的东西，等于不存在【推导】

【事实】OpenAI 那篇的原话：

"From the agent's point of view, anything it can't access in-context while running effectively doesn't exist. Knowledge that lives in Google Docs, chat threads, or people's heads are not accessible to the system. Repository-local, versioned artifacts (e.g., code, markdown, schemas, executable plans) are all it can see."

【事实】他们为此做了两件事（都是"把信息推到 agent 能看到的地方"）：

① 可观测性：把 logs / metrics / traces 通过一个【每个 worktree 一份的临时可观测栈】
   暴露给 agent，它可以查 LogQL、PromQL
   → 于是 prompt 从"确保启动快一点"变成可验证的
     "ensure service startup completes in under 800ms"、
     "no span in these four critical user journeys exceeds two seconds"

② 错误信息注入修复指令：custom linter 的报错里【写清楚怎么修】
   → 因为 linter 是自研的，所以能把修复指令直接塞进 agent 的上下文

【推导】第 ① 条的收益能算：

目标："确保服务启动在 800ms 内"

agent 能看到启动耗时：
  → 它可以自己迭代到达标，全程不需要人
  → 每次验证约 30 秒

agent 看不到启动耗时：
  → 它只能改代码然后声称"应该快了"
  → 需要人来验证
  → 每次人工验证约 5 分钟

差 10 倍

【结论】把"可验证的信号"暴露给 agent，收益是 10 倍量级的人工节省。

【推论】而且它改变了不确定性：没有可验证信号时，agent 的输出是"我改完了"，而这是一个无法检验的声明（[[母题-C4-幻觉的成因与可控性]] 的"自信但不是事实"）。有了信号，"改完了"就变成了"启动耗时 780ms"——一个可检验的事实。

到这里你应该能回答：为什么"给 agent 配上可观测性工具"这件事，价值不只是"方便排查"？

4. 验证：能确定化的，就不要交给模型判断【推导】

【事实】验证的优先级（[[母题-A1-计划执行循环与停止条件]] 引过）：

① 确定性测试、Schema、规则、编译器、SQL AST
② 工具返回和权威状态查询
③ 多源交叉证据
④ 模型 Judge
⑤ 人工复核

【事实】原始素材一句很硬的话：

"模型'自我反思'不能替代外部 oracle。"

【推导】为什么"优先确定性"这件事的收益是指数级的——假设一个任务需要过 10 项检查：

模型 Judge 的准确率假设 85%（乐观估计）
确定性检查对它覆盖的部分准确率 = 100%

【全部用模型 Judge】10 项全对的概率：
  0.85¹⁰ ≈ 19.7%

【60% 确定化（6 项）+ 40% 模型（4 项）】：
  1⁶ × 0.85⁴ ≈ 52.2%

【结论】把能确定化的检查确定化，端到端可靠性能从约 20% 提到约 52%——差 2.6 倍。

【推论】而且这个差距随检查项数放大：20 项检查时，全模型 Judge 是 0.85²⁰ ≈ 3.9%，而 60% 确定化是 0.85⁸ ≈ 27%——差 7 倍。

【取舍】所以工程动作很明确：每遇到一类"模型老是判错"的检查，就把它写成一条确定性规则。这正是 OpenAI 那篇里"custom linters and structural tests"在做的事——把组织的品味和约束固化成可执行的检查。

【事实】他们还顺带解决了"规则怎么传达给 agent"这个问题：

"Because the lints are custom, we write the error messages to inject remediation instructions into agent context."

【推论】这条设计很精妙：规则不写在提示里（那会占用上下文且容易被忽略），而是写在"违反时的错误信息"里——只在真正违反时才出现，而且出现得正是时候。这是"渐进披露"在约束传达上的应用。

到这里你应该能回答：为什么"多写几条规则进系统提示"不如"写一条 linter"？

5. Reflection 的局限【事实】

【事实】study/04 的结论：

"同一模型可能重复同一盲点，而且多一次调用增加成本。优先给外部测试/工具反馈；Reflection 适合生成候选修复或检查清单，并通过 Eval 验证增益。"

【推导】为什么"同一模型重复同一盲点"：

模型反思时用的是【同一个权重】
  → 它看不出自己上次为什么错，因为它"觉得那样是对的"才那么做的
  → 换个问法问它，它可能给出同样的错误答案，只是措辞不同

而外部 oracle（测试、编译器、数据库查询）不依赖模型的判断
  → 它给的是【事实】

【推论】所以 Reflection 的正确位置是"生成候选"，不是"验收"：

✓ 让它反思 → 生成几个可能的修复方案 → 用测试验证
✗ 让它反思 → 它说"我检查过了，没问题" → 相信它

【事实】OpenAI 那篇里有一个对应的做法：他们让 Codex 审查自己的改动、请求额外的 agent 审查（本地和云端）、回应反馈并迭代，直到所有 agent reviewer 满意。但注意——那个循环的判据是"reviewer 满意"，而 reviewer 的输出最终仍然要过仓库里的确定性检查（linter、测试）。

到这里你应该能回答：为什么"让模型自己复核一遍"不能作为最后的验收手段？

6. 边界与常见误解

常见说法修正
"让模型别改计划就行了"反了。动态计划的价值就在于能根据观察到的情况调整——要求它不变，等于放弃 Agent 相对 Workflow 的优势。要解决的是"变了没人知道"，不是"会变"
"让模型把计划记在心里"长任务上一定会出问题：上下文一压缩，只存在于上下文里的计划就丢了，模型开始凭残余记忆干活。计划要做成版本化的产物（OpenAI 的做法是 checked into the repository），偏离才会变成可见的 diff
"跑偏了让它自己反思一下就行"Reflection 不能替代外部 oracle：同一模型会重复同一盲点，而且多一次调用增加成本。它的正确位置是"生成候选修复"，不是"验收"
"规则写在系统提示里就够了"占用上下文，而且容易被忽略。参考做法是把约束写成 linter / structural test，违规时把修复指令写进错误信息——只在真正违反时出现，而且出现得正是时候
"agent 看不到指标没关系，人来盯就行""agent 访问不到的东西，等于不存在"（OpenAI 原话）。把可观测性暴露给 agent 之后，目标从"确保启动快一点"变成可验证的"启动在 800ms 内"——收益是 10 倍量级的人工节省
"验证都交给模型 Judge 最省事"可靠性会指数衰减：10 项检查全用模型（假设 85% 准）是 19.7%；60% 确定化后是 52.2%——差 2.6 倍，20 项检查时差 7 倍
"确定性检查写起来太麻烦，不如让模型判断"麻烦一次，之后每次都省。而且确定性检查是可复用的——它把"组织的品味和约束"固化成了可执行的东西，不依赖某次模型状态

【取舍】读成一句话：动态计划本身不是问题，"不可见的变化"才是问题——把计划外化、把目标变成可验证的信号、把能确定化的检查确定化，三件事一起做。

计划由模型动态生成、而且会变——那"可靠执行"靠什么保证？为什么"让模型自己反思一下"不够？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是 Agent 面试里最难、也最能区分层次的一题。因为"跑偏"这件事最难的地方不是"它偏了"，是"你看不出来它偏了"——它一直在正常地干活。而解法不是"让计划不变"（动态计划本来就要变），是让变化可见、让验证可执行。这题也是 RuleArena 显式 FSM 设计的直接对应。

动态计划的问题不是"会变"，是"变了没人知道、也回不去"。 而且跑偏最难的地方在于"它看起来很正常"——还在调工具、还在推进，没有任何信号告诉你它在做的不是原来那件事。所以解法是三件事一起做：① 计划外化——把计划做成版本化的产物（OpenAI 的做法是 checked into the repository，修订产生新版本，偏离变成可见的 diff）；② 把目标变成可验证的信号——"agent 访问不到的东西等于不存在"，把 logs/metrics/traces 暴露给 agent 后，目标从"确保启动快一点"变成"启动在 800ms 内"，验证成本差 10 倍；③ 能确定化的检查就确定化——10 项检查全用模型 Judge（85% 准）只有 19.7% 全对，60% 确定化后是 52.2%（20 项时差 7 倍）。Reflection 不能替代外部 oracle（同一模型重复同一盲点），它的正确位置是生成候选修复，不是验收。最后一条设计很值：约束不写在提示里，而是写成 linter，把修复指令塞进错误信息——只在违反时出现，而且出现得正是时候。

  • 跑偏的 agent 看起来很正常
  • 计划外化成版本化产物（checked into repository，偏离 = 可见 diff）

1. 计划变更是怎么处理的？

计划是版本化产物：修订产生新版本（可 diff）、进度与决策日志一起进版本控制、偏离变成可见的。人不必读全过程，只需要看计划变了没有。

2. Reflection 有什么局限？

同一模型可能重复同一盲点，而且多一次调用增加成本。优先给外部测试 / 工具反馈；Reflection 适合生成候选修复或检查清单，并通过 Eval 验证增益。

3. 怎么保证 Agent 遵守了一堆约束？

别写在提示里，写成 linter / structural test：违规必然被拦住，而且把修复指令写进错误信息（只在违反时出现，出现得正是时候）。而且检查可复用、不依赖模型状态。

4. Agent 的评测和 RAG 的评测有什么不同？

RAG 的归因是三段（没捞到 / 没进上下文 / 生成错）；Agent 的归因层次更多：目标理解 → 计划 → 每一步的工具选择与参数 → 副作用 → 终止判定，而且要评交互模式（[[母题-A7-多Agent拆分与协作]] 的涌现行为）。共同点：都必须能定位到具体哪一段坏了（[[母题-G5-RAG评测与幻觉率]]）。

5. 为什么 RuleArena 用显式 FSM 而不是自由编排？

因为高风险动作需要可控性与可回溯：显式 FSM 让"当前该做哪一步"是可检查的，而不是"模型觉得该做哪一步"。自由编排更灵活，但它的状态在模型脑子里——而本卡的结论正是"脑子里的东西不可检查"。
  • 「Agent 的幻觉和 RAG 的幻觉有什么不同？」——RAG 的幻觉是"内容不实"；Agent 的幻觉是"动作不实"（声称做了但没做、或做了但说没做）。代价也不同：前者是信息层面的，后者是动作层面的（[[母题-A6-沙箱权限与可信执行]]）。而且 Agent 的"声称"必须用权威状态核对——这正是 [[母题-A4-长任务状态与Checkpoint]] 的"查权威状态"那一步。
  • 「怎么知道 Agent 真的在进步，而不是在做无用功？」——看"状态有没有变"（[[母题-A1-计划执行循环与停止条件]] 的无进展检测）+ 看"计划的完成度"（外化之后，这就是一个可计算的比例）。

- RuleArena：显式审查状态（准备 → 取证 → 各角色审查 → 合并 → 确定性验证 → 人工确认 → 完成）——这是"把计划变成可检查的状态机"的落地；连续无进展、预算耗尽、证据冲突各有独立终止原因（[[母题-A1-计划执行循环与停止条件]]）。 - EnergyOps：Hook 链——它本质上就是"把约束写成可执行的检查"（而不是写在提示里）；R2 的强制拦截则保证了"违规必然被拦住"。

先破"让它别改"（动态计划的价值就在能改）→ 跑偏的隐蔽性（看起来很正常）→ 计划外化（给成本对比）→ 可读性（agent 访问不到 = 不存在，给 10 倍收益）→ 验证优先级与确定化的收益（给 19.7% vs 52.2%）→ linter 的错误信息注入修复指令 → Reflection 的局限 → 收束到"把脑子里的东西搬到系统里"

动态计划本身不是风险，"不可见的变化"才是。 所以三件事都指向同一个方向：把只存在于模型脑子里的东西，搬到系统能看、能查、能验证的地方——计划变成产物、目标变成指标、约束变成检查。
