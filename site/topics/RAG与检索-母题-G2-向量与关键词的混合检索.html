题目

面试官问——"你们的检索是怎么做的？为什么既要用向量又要用关键词？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：两路检索的盲区正好互补

强项弱项
BM25 / 关键词专有名词、编号、精确短语、可解释同义表达与语义泛化弱
Dense Vector语义相似、自然语言改写编号 / 罕见词弱，且受 Embedding 版本影响
Hybrid同时覆盖精确与语义需要融合、去重和调参

【事实】得物文章给的那个反例最直观：

搜 "SLB-20250101-abc" 这种 trace ID
→ Embedding 模型无能为力（语义向量对专有编码不敏感）
→ BM25 倒排索引才是正解

反过来：

搜 "数据库连接池"
→ 应该命中 "DB connection pool 配置"
→ 文字完全不同、意思一样 → 这是 Dense 的强项，BM25 匹配不上

【推论】所以"用哪个"这个问题的正确答案是"两个都用"——不是因为混合更先进，是因为它们的盲区不重叠。而两者都覆盖不到的（比如需要多跳推理的关系），才是 GraphRAG 要解决的问题（见第 5 节）。

到这里你应该能回答：为什么"我们的检索用的是向量库"这个回答不完整？

2. 向量这一路的基础：相似度怎么量

2.1 余弦相似度是默认选择【事实】

余弦相似度 = cos(θ) = (A·B) / (|A| × |B|)
值域 [-1, 1]；实践中 Embedding 产出的向量通常落在 [0, 1]，负值极少
1 = 方向完全一致，0 = 正交（无关）

【推导】为什么是余弦而不是别的——因为 Embedding 模型在训练时就是用余弦相似度优化的。

得物文章的原话："你用别的度量去比，相当于考试的评分标准都换了，成绩自然不准。"

度量什么时候用
余弦相似度默认选它
欧氏距离衡量空间直线距离，受向量长度影响大（两个意思相同但长度不同的向量，欧氏距离可能很大而余弦很高）——通常不优先
点积当向量已做 L2 归一化（长度为 1）时，点积 = 余弦，而且更快

2.2 维度是模型定的，不是你能调优的【事实】

主流 Embedding 模型的维度：768 / 1024 / 1536
比如「用户喜欢川菜」 → [0.21, -0.43, 0.07, 0.85, ..., -0.12]  ← 1536 个数字

【推论】维度不是"越大越好"的调优项——它由模型决定，换模型就换维度，整个索引必须重建。

【取舍】这也是"Embedding 版本"必须进版本管理的原因：新旧向量混在同一个索引里是不可比的，所以换模型 = 全量重嵌入 + 双写切换（[[母题-G6-知识更新与增量索引]]）。

3. 为什么必须用 ANN：算力账

3.1 精确 KNN 算不动【推导】

精确 KNN = 逐条遍历所有向量，逐一算相似度，排序取 Top-K
复杂度 O(N × D)

100 万条向量 × 1536 维：
  100万 × 1536 = 15.36 亿次浮点运算

即使每次运算只要 1 纳秒：
  15.36 亿 × 1ns ≈ 1.5 秒 / 次查询

【结论】单次查询 1.5 秒，这在任何在线系统里都不可接受。 而这是单条的代价——并发一来直接崩。

【推论】ANN（近似最近邻）不是"精度优化"，是"算力逼出来的"：牺牲一点召回精度，换数量级的性能提升。这是所有 ANN 算法共同的设计取舍。

3.2 HNSW 怎么做到【推导】

【事实】回顾跳表（[[母题-R1-Redis数据结构与选型]]）：有序链表加多级索引，上层稀疏、下层稠密，查找时从上层快速跳。

HNSW 把分层思想搬到了图上——但这里有个关键问题：

跳表能工作，是因为链表是有序的，
比一下大小就知道往左还是往右。

但向量没有「大小」概念——向量 (1,3) 和 (-2,5) 谁大？没法比。
→ 光有分层不够，还得解决「图上怎么导航」

【事实】HNSW 的解法：

① 分层：每个节点按概率随机分配到若干层，同时存在于所属层及以下所有层
   （层间只有同一节点的纵向连接，没有跨节点连线）
② 贪心导航：上层节点少、边长跨度大 → 先粗定位
             顺着纵向连接降到下一层 → 逐层下沉
             到第 0 层做精细搜索

层数能算出来：

100 万节点，晋升概率按 1/M（M = 16）：
  第 1 层 ≈ 100万 / 16 = 6.25 万
  第 2 层 ≈ 3,906
  第 3 层 ≈ 244
  第 4 层 ≈ 15
  第 5 层 ≈ 1
  → 最高约 5 层

【事实】得物文章给的实测口径一致："100 万节点，图的最高层大概 5–6 层"；论文默认用 mL = 1/ln(M)（M=16 时约 0.36）作为晋升概率，真实分布比 1/M 更"胖"，但"层级越高节点越少"的指数衰减规律不变。

【推论】上层的长距离边还有一个作用：帮搜索在早期跳过"看起来近但其实不对"的区域，避免卡在局部最优里。

【事实】选型分档（得物的口径）：百万级以内用 HNSW，千万级用 IVF，亿级考虑 DiskANN 或分片。ES、Faiss、Milvus 都默认支持 HNSW。

到这里你应该能回答：为什么"向量库慢"通常不是硬件问题，而是索引选型问题？

4. 两路怎么合：RRF

4.1 为什么不能直接加分数【推导】

向量路：doc_A 得分 0.92   ← 余弦相似度，值域 [0, 1]
关键词路：doc_B 得分 8.7  ← BM25 相关度，无上界

0.92 和 8.7 谁更相关？没法比。

【推论】量纲不可比 → 加权求和需要调参，而且换个数据集就失效。

4.2 RRF 的做法：扔掉分数，只看排名【事实】

score(d) = Σ 1 / (k + rank_i(d))       k 通常取 60

规则：某一路排得越前贡献越大；在越多路里靠前，总分越高（各路独立贡献、自然叠加）。得物原文的说法是"不偏向任何一路，只看综合排名"，实现只要约 30 行代码。

4.3 把融合结果算出来【推导】

doc_A：ANN 第 1，BM25 第 10
  RRF = 1/(60+1) + 1/(60+10) = 0.0164 + 0.0143 = 0.0307

doc_B：两路都第 5
  RRF = 1/(60+5) + 1/(60+5) = 0.0154 + 0.0154 = 0.0308

【结论】doc_B 略胜——它一路第一、另一路第十，却输给了"两路都在前列"的 doc_B。

【推论】这就是 RRF 的设计意图：奖励"多路共识"，而不是"单路极端强"。 只在一路出现、另一路没出现的文档，自然排后面。

i(d)）　　k 通常取 60 某一路排得越前，贡献越大；在越多路里靠前，总分越高（各路独立贡献、自然叠加） doc_A：ANN 第 1，BM25 第 10 1/(60+1) + 1/(60+10) = 0.0164 + 0.0143 = 0.0307 一路很强，另一路很弱 doc_B：两路都第 5 1/(60+5) + 1/(60+5) = 0.0154 + 0.0154 = 0.0308 两路都在前列 → 略胜一筹

到这里你应该能回答：为什么"一路第一、另一路第十"的文档，可能排不过"两路都第五"的？

5. 融合之外的几件事

5.1 权限必须在检索前生效【事实】

错误做法：先检索全部文档，再让模型"不要泄露"。

正确做法：

身份 / 租户 / 角色  →  策略决策  →  生成 ACL Filter  →  受权召回  →  生成与引用

【推论】为什么必须在召回前：

① 未授权内容一旦进入上下文，就已经"泄露"了——
   模型是否说出来是概率问题，不是权限控制
② 未授权内容还会挤占上下文预算，降低有用证据的质量
③ 日志、Trace、缓存都可能把未授权内容带出去

【事实】还要测的场景（这些都是真实事故形态）：跨租户、已撤权、共享链接、继承权限、删除传播、缓存污染。

5.2 其他几种召回增强【事实】

  • Query Rewrite / Decomposition：多条件问题拆成子查询，再合并证据
  • Multi-hop：第二轮检索由第一轮发现的实体驱动
  • Metadata Filter：租户、ACL、时间、地区、文档类型

【取舍】Filter 有一个反直觉的坑：过滤会缩小候选集，可能把正确答案滤掉（比如 ACL 配置错了、或者时间字段本身标错）。所以过滤条件本身也要进评测——不能只测"过滤生效了没有"，还要测"过滤有没有误伤"。

5.3 GraphRAG 什么时候值得【取舍】

当问题依赖实体关系、多跳路径和全局结构，普通相似检索难覆盖时才考虑。

【取舍】代价是图谱构建、更新和评测成本都不低。 如果只是品牌词查询或单文档问答，混合检索更简单——不要为了技术先进性上图谱。

6. 边界与常见误解

常见说法修正
"向量检索比 BM25 先进，全用向量就行"反例很硬：搜 SLB-20250101-abc 这种 trace ID，Embedding 模型无能为力（语义向量对专有编码不敏感），BM25 才是正解。两者盲区不重叠，所以企业库通常两路都要
"直接给两路分数加权求和就行"量纲不可比（余弦 ∈ [0,1]，BM25 无上界），加权要调参且换数据集就失效。RRF 扔掉分数只看排名，不需要调参
"RRF 就是取平均"不是。它是 Σ 1/(k+排名)——奖励"多路共识"：一路第 1、另一路第 10 的文档（0.0307）排不过两路都第 5 的（0.0308）
"向量维度越高检索越准"维度由模型决定，不是调优项。而且换模型就换维度，整个索引必须重建——所以 Embedding 版本必须进版本管理，新旧向量不可比
"向量库慢就加机器"多半是索引选型问题。精确 KNN 是 O(N×D)（100 万 × 1536 维 ≈ 1.5 秒/次），必须用 ANN；百万级以内 HNSW、千万级 IVF、亿级 DiskANN 或分片
"先把全部召回来，再让模型别说没权限的"这是明确的数据泄露——未授权内容一旦进入上下文就已经出去了；而且它会挤占预算、还可能进日志和缓存。权限必须在召回前生效
"HNSW 保证找到最近的"它是近似算法，不保证命中全局最近邻——这是所有 ANN 的共同取舍：用可控的召回损失换数量级性能。要 100% 精确就得回到 O(N×D)

【取舍】读成一句话："用哪一路"不是先进性问题，是"你的查询里有多少是专有编码、有多少是自然语言"——所以要按查询类型分桶评测来定，而不是拍脑袋。

展开（先自答，再看 · 默认收起，不进复训调度）

1. 向量检索和 BM25 怎么选？

按查询类型分桶评测：专有名词、编号、错误码偏 BM25；自然语言同义改写偏向量；企业知识通常混合检索后重排。选择由数据决定，不由偏好决定。

2. RRF 的 k 是干什么的？

它平滑高排名的差距：k 越大，第 1 名和第 2 名的贡献差距越小（1/(k+1) vs 1/(k+2)）。k=60 是社区默认值，k 太小会让"某一路单独第一"过于强势。

3. HNSW 为什么在精度和速度之间平衡得最好？

分层给了"对数级"的搜索路径（100 万节点约 5–6 层），贪心导航在每层只需要局部比较；而且它实现成熟、生态完善（ES、Faiss、Milvus 都默认支持）。

4. 多跳（multi-hop）问题怎么处理？

第二轮检索由第一轮发现的实体驱动。比如"某公司 CEO 的母校在哪"——先检索"公司 CEO"，再用找到的人名检索"母校"。这不是检索算法的问题，是查询规划的问题（见 [[母题-G3-重排与召回质量]]）。

5. 怎么防止 RAG 越权？

身份进入检索层、ACL filter 先于召回；缓存按租户 / 权限分区；引用和下载再次鉴权；做跨租户与撤权测试；日志避免记录敏感原文。
  • 「余弦相似度和欧氏距离怎么选？」——默认余弦（模型就是这么训的）；欧氏距离受向量长度影响大（意思相同但长度不同的向量，欧氏可能很大而余弦很高）；点积在向量已 L2 归一化时等于余弦，且更快。
  • 「稀疏向量（SPLADE 之类）和 BM25 什么关系？」——都是稀疏表示，但稀疏向量是学出来的、能部分覆盖同义改写；BM25 是统计出来的、完全不做语义泛化但绝对可解释。两者常作为"关键词这一路"的不同实现。

- 数驭穹图：关键词 + 向量混合召回表、字段和业务术语——Schema 名和字段名恰恰是"专有编码"那一类（BM25 的主场），而用户的自然语言问法是 Dense 的主场。这是"两路互补"最典型的项目实例。 - EnergyOps：运维文档、设备数据和实时状态不要混成一个索引——不同来源的检索特性不同，混在一起会让权重没法调。

两路各自强/弱（各给一个反例）→ 相似度度量怎么选（余弦 + 为什么）→ 精确 KNN 算不动 → ANN 与 HNSW（给算力账和层数）→ 融合用 RRF（给融合算式）→ 权限必须在召回前（并说清"先召回再让模型别说"为什么是泄露）→ GraphRAG 的边界 → 收束到"按查询类型分桶评测来定权重"

两路检索的盲区不重叠，所以"选哪一路"是个伪问题；真正的问题是"融合要怎么处理量纲不可比"，以及"权限要在哪一层拦"。 前者用 RRF 只排名不拼分解决，后者用 ACL Filter 前置解决——两个都是"不试图用错的方式解决错的问题"。
