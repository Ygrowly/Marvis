题目

面试官问——"Agent 跑久了上下文满了怎么办？记忆该存什么？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：记忆分三层，权威性完全不同

层作用域寿命写入方式权威性
① 运行状态单个 thread一次 run自动（每一步）运行权威
② 长期记忆跨 thread用户 / 组织级有门槛派生（需治理）
③ 业务权威状态业务系统长期业务系统自己最高

【推导】这个分层的判据是"权威性"，不是"存哪"：

① 运行状态：是"我做到哪了" —— 权威，但只对本次 run 有效
② 长期记忆：是"我记住了什么" —— 【派生】，可能过期、可能被推断污染
③ 业务状态：是"事情到底是什么样" —— 【唯一权威】

【推论】混在一起的后果很具体：拿模型自己总结的"已执行"当成工具真的执行成功了。这正是 [[母题-C1-上下文组装与窗口预算]] 里那句"不把模型自己总结的已执行当作工具执行成功"的机制版本。

【事实】LangGraph 的划分和这个同构（[[母题-A4-长任务状态与Checkpoint]] 引过）：

Checkpointer = 单 thread、短期、thread 级  → 对应 ①
Store        = 跨 thread、长期、需治理    → 对应 ②

【事实】OpenAI 那篇 Harness 工程给了一个更狠的说法：

"From the agent's point of view, anything it can't access in-context while running effectively doesn't exist."

【推论】这句话反过来推出一件重要的事："我告诉过模型"不等于"模型知道"——知识必须落在 agent 能访问的地方（仓库里、可检索的存储里），而不是留在人的脑子里或聊天记录里。

到这里你应该能回答：为什么"用户上周说过他偏好 A 方案"这句话，如果只留在聊天记录里，第二周就不算数了？

2. 压缩：Agent 里和纯对话里的区别【推导】

【事实】共同的原理（[[母题-C1-上下文组装与窗口预算]]）：

压缩 = 把历史摘要掉，用摘要 + 最近若干条重新开始
调法 = 先保 recall（不漏），再提 precision（删冗余）
摘要必须有可回溯的指针，原始内容外部持久化
触发阈值：Claude 平台默认 150,000 输入 token

【推导】Agent 里多出来的是"压缩时机的判据"：

纯对话：什么时候压，主要看【窗口快满了】
Agent ：什么时候压，还要看【当前处在哪个业务节点】

因为压缩在 Agent 里是【有状态语义的】：
  在一个工具调用序列中间压缩 → 可能丢掉"这一步还没做完"的标记
  在副作用之后压缩           → 正好，因为结果已经落盘了（[[母题-A4-长任务状态与Checkpoint]]）

【推论】所以 Agent 的压缩点应该和 checkpoint 点对齐——study/04 把"Context 压缩或分支合并后"列为 checkpoint 时机之一，正是这个道理：压缩和 checkpoint 是同一个动作的两面，一个改上下文，一个存状态。

2.1 压缩能省多少【推导】

50 步任务，每步新增 2.5K token，每 20 步压缩一次（压到 10K）

不压缩：
  累计输入 = 2.5K × (1 + … + 50) = 2.5K × 1,275 = 3.19M

压缩（分三段）：
  段 1（1–20）：prompt 从 2.5K 涨到 50K
               累计 = 2.5K × 210 = 525K
               段末压到 10K
  段 2（21–40）：prompt 从 10K 涨到 60K
               累计 = 20 × 10K + 2.5K × 210 = 200K + 525K = 725K
               段末压到 10K
  段 3（41–50）：prompt 从 10K 涨到 35K
               累计 = 10 × 10K + 2.5K × 55 = 100K + 137.5K = 237.5K

  合计 ≈ 1,487.5K ≈ 1.49M

【结论】压缩把累计输入从 3.19M 降到 1.49M，约一半（47%）。

【推论】而且压缩的收益随任务变长而变大：不压缩是"整段平方"，压缩是"分段平方"——段数越多，省得越多。（[[母题-C6-成本与长上下文截断]] 里那句"缓存改价格、压缩改占用"在这里同样成立，但 Agent 场景下压缩的触发点还要和状态对齐。）

到这里你应该能回答：为什么 Agent 的压缩不能只看"窗口还剩多少"？

3. 摘要里必须留下什么【推导】

【推导】压缩是有损的，所以"留什么"是设计出来的，不是概括出来的。三类必须留：

① 与副作用相关的：已完成的操作 + 幂等键
   → 丢了会导致恢复时【重复执行】（[[母题-A3-失败恢复与幂等]]）

② 与证据相关的：来源 ID / Artifact 引用
   → 丢了会导致结论无法追溯（[[母题-G4-引用绑定与证据可追溯]]）

③ 与进度相关的：未决问题、剩余预算、当前节点
   → 丢了会导致恢复时不知道该从哪继续（[[母题-A4-长任务状态与Checkpoint]]）

【推导】算一下"多留这几个字段"的成本：

在摘要里多保留约 200 token 的指针信息
成本 = 200 × $5 / 1M = $0.001           （Opus 5 输入价）

而丢掉"已完成副作用记录"的代价：
  一次重复扣款 / 重复建单 → 对账、退款、客诉 → 【远大于 $0.001】

【结论】在摘要里保留指针的成本可以忽略，而丢掉的代价是事故。

【推论】这就是"摘要不是审计记录"这句话的正确理解：它不是"摘要可以随便写"，而是"摘要不该承担记录真相的责任"——真相要外部持久化，摘要只留指针。

到这里你应该能回答：为什么"摘要写得好不好"这件事，不能用"读起来通不通顺"来判断？

4. 长期记忆的写入门槛【推导】

【事实】门槛是三条同时成立（[[母题-C1-上下文组装与窗口预算]] 给过）：

跨任务稳定 + 对未来有用 + 经过授权（能治理）

【事实】不该自动写入的：临时推理、模型猜测、敏感数据。

【推导】算一下"不设门槛"的代价：

什么都写（每次 run 写 10 条）：
  每天 10,000 run → 100,000 条/天
  一年 ≈ 3,650 万条

只写"跨任务稳定 + 已验证"的（每天约 50 条）：
  一年 ≈ 18,250 条

差约 2,000 倍

【结论】写入门槛决定长期记忆是"资产"还是"噪声"。

【推论】这个差别不是存储成本的问题，是检索质量的问题——当记忆里有 3,650 万条时，"回忆相关偏好"这件事本身就变成了一次低质量检索：大部分条目是噪声，真正有用的被淹没（和 [[母题-G1-切分策略与索引粒度]] 里"块太大导致信号被稀释"是同一个机制）。

【事实】每条记忆应有的元数据：来源、主体、作用域、置信度、更新时间、TTL、删除机制。

【推论】"删除机制"这一条是硬要求，不是可选项——因为记忆里可能有敏感信息，也可能有已经被推翻的结论（[[母题-G6-知识更新与增量索引]] 的删除传播在记忆上的版本）。

到这里你应该能回答：为什么"模型觉得重要就自动记下来"这个设计是危险的？

5. 记忆的三种失效【事实】

【推导】长期记忆会以三种方式变坏，各要一种对策：

失效方式表现对策
过期用户偏好变了，记忆还是旧的TTL + 更新时间；关键事实回权威源重查
污染模型推断被当成事实写进去写入门槛（只写验证过的）+ 标注置信度与来源
过载条目太多，检索不出有用的写入门槛（Q2）+ 定期清理

【推论】第二类最隐蔽：模型推断被写进记忆后，下一轮它就不再有"这是推断"的标记了——它变成了一条"事实"。所以记忆条目必须自带来源与置信度，否则系统会逐渐把"自己猜的"当成"知道的"。

【推论】这和 [[母题-C4-幻觉的成因与可控性]] 的"多轮对话里幻觉会累积"是同一个机制：上一轮的错误结论进了下一轮上下文，就变成了"已确认事实"。

到这里你应该能回答：为什么记忆条目必须自带来源和置信度？

6. 边界与常见误解

常见说法修正
"记忆越多越聪明，都存下来"写入门槛决定它是资产还是噪声：什么都写是每年 3,650 万条，只写稳定已验证的约 1.8 万条——差 2,000 倍。条目多了之后，"回忆相关偏好"本身就退化成一次低质量检索
"模型自己总结的'已执行'可以当状态用"这是最危险的混淆。运行状态（①）是权威的，长期记忆（②）是派生的——拿模型自己的摘要当业务事实，就是 [[母题-C1-上下文组装与窗口预算]] 里点名的反例
"摘要就是把历史概括一下"摘要的判据不是"通顺"，是"能不能恢复"。必须留下三类指针：已完成副作用 + 幂等键、证据 ID / Artifact 引用、未决问题与剩余预算。多留 200 token 的成本是 $0.001，丢掉副作用记录的代价是事故
"压缩什么时候做，看窗口快满了就行"Agent 里还要看当前处在哪个业务节点。在工具调用序列中间压缩可能丢掉"这一步还没做完"的标记；在副作用之后压缩才是安全的。所以压缩点应该和 checkpoint 点对齐
"长期记忆写进去就不用管了"记忆会以三种方式变坏：过期、污染、过载。所以要 TTL + 更新时间 + 来源 + 置信度 + 删除机制——"删除机制"是硬要求（可能有敏感信息，也可能有被推翻的结论）
"提示里告诉过模型就行"OpenAI 的原话是"agent 访问不到的东西，等于不存在"。知识必须落在可访问、版本化、可检索的地方——留在聊天记录和人的脑子里都不算
"压缩和 checkpoint 是两件事"它们是同一个动作的两面：一个改上下文、一个存状态，而且压缩后必须 checkpoint——否则压缩后崩溃又回到压缩前，等于白压一次

【取舍】读成一句话：记忆的核心问题是"权威性"，不是"容量"——分不清"我记住的"和"事情本来的样子"，压缩和记忆都会变成事故来源。

1. Agent State、Context、Memory 有何区别？

State 是运行时结构化事实；Context 是某一次模型调用看到的投影；Memory 是跨步骤 / 会话复用的信息。业务状态仍由数据库权威维护。恢复时从 State 和业务状态重新装配 Context。

2. Memory 应该存什么？

只存跨任务稳定、对未来有用、经过授权、能治理的信息。临时推理、模型猜测、敏感数据不自动写入。每条有来源、主体、作用域、置信度、更新时间、TTL 和删除机制。

3. 怎么防止记忆污染？

两道：写入门槛（只写验证过的）+ 条目自带来源与置信度（这样模型读到它时知道这是"推断"还是"事实"）。最危险的是"模型推断写进去后，下一轮就看不到推断标记了"。

4. 压缩和 checkpoint 什么关系？

同一个动作的两面：一个改上下文、一个存状态。压缩后必须 checkpoint，否则压缩后崩溃又回到压缩前，等于白压一次。

5. 长文档场景怎么保证 grounding？

对超过 20k token 的文档，先要求逐字摘出相关原文（找不到就明说"没找到"），再基于摘录作答——这样引用在生成时就产生了，而且摘要里天然带着可回溯的指针（[[母题-G4-引用绑定与证据可追溯]]）。
  • 「多轮对话里幻觉会累积吗？」——会。上一轮的错误结论进了下一轮上下文，就变成"已确认事实"。所以摘要必须标注哪些是已验证事实、哪些是模型推断，关键状态要回权威源重查。
  • 「子 Agent 的上下文怎么和主 Agent 交互？」——子 Agent 在自己的干净窗口里探索，只回传 1,000–2,000 token 的浓缩结论——这本质上是"压缩"的一种实现，而且它天然地只回传了结论、不带过程的噪声（[[母题-A7-多Agent拆分与协作]]）。

- RuleArena：长审查任务压缩时保留证据 ID 和副作用记录——恢复时先查权威状态再重建最小上下文，而不是拿旧摘要直接续跑。 - EnergyOps：每个 MCP 工具只收到必要业务参数；日志和大表先检索聚合再进上下文——这是"减少新增"而不是"压缩历史"，两者要配合用。

三层记忆与权威性 → Agent 的压缩为什么要看业务节点 → 压缩收益算式 → 摘要必须留的三类指针（给成本对比）→ 长期记忆的写入门槛（给 2,000 倍）→ 记忆的三种失效 → 收束到"权威性不是容量"

记忆的核心问题是"权威性"，不是"容量"。 分不清"我记住的"和"事情本来的样子"，压缩会丢掉恢复所需的指针，记忆会把模型自己的猜测固化成事实——两者都会变成事故来源。
