题目

面试官问——"你们的文档更新了怎么办？删除和撤权呢？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：索引是派生数据，源变了它就必须变

【推导】索引（向量 + 倒排 + 元数据）不是事实来源，它只是源文档的派生视图。 这直接推出一件事：

源文档的三种变化，索引都必须跟着变：
  ① 新增 / 修改  → 内容变了，派生视图要重算
  ② 删除         → 源没了，派生副本不能留着
  ③ 撤权         → 内容还在，但"谁能看"变了

【推论】新增最容易（多加一份），删除最难——因为删除要找全所有派生物，而派生物是散开的（一个文档切成 N 个块，每块有向量、倒排项、元数据）。

到这里你应该能回答：为什么"我们每天全量重建一次索引"这个答案会让面试官追问删除和撤权？

2. 为什么值得做增量【推导】

100 万块文档，每天只改 1%：

全量重建：
  每天重算 100 万次嵌入

增量更新：
  只重算变化的 1% = 1 万次嵌入

降到 1/100

【结论】增量的收益是数量级的——尤其在嵌入调用要花钱的时候（[[母题-C6-成本与长上下文截断]] 的成本口径）。

【取舍】但增量不是免费的，它换来两个新问题：

① 要维护【版本】：哪一版索引对应哪一版源文档？
② 要保证【一致性】：增量跑失败一半怎么办？新旧混在一起怎么办？

【推论】所以"全量重建"不是笨办法，是"数据量小、更新频率低"时的正确选择——它的简单性是真实的收益。判断该不该上增量，看的是"重建一次要多久、多久需要重建一次"，不是技术先进性。

3. 删除：为什么它比新增难得多【推导】

【推导】删除必须按文档 ID 反查它切出来的全部块：

一份文档 → 切成 100 个块 → 每块有：向量 + 倒排项 + 元数据

删除时必须清掉这 100 个块的全部派生物

漏掉 1 个块 → 用户还能搜到已删除内容
            → 在合规场景里，这就是事故

【推论】新增漏了只是"少了一条"，删除漏了是"多了一条不该在的"——后者的性质完全不同。

【事实】所以删除需要一张反查表：doc_id → [chunk_id...]。这张表本身也是索引的一部分，也要维护、也要能容错。这也是为什么"删除传播"在 archive/study-courses/03 里被单独列为一步。

3.5 删除同样要清"索引之外"的派生物【推导】

【推导】第 3 节只清了索引内的三处（向量 / 倒排 / 元数据），但派生物不止在索引里——源文档的派生物是两层：

① 索引内：向量 · 倒排 · 元数据
② 索引外：检索结果缓存 · 生成回答缓存 / 语义缓存 · 派生引用与摘要 · Agent 记忆

【推论】删除传播的定义是"源没了，它的所有派生物都不能留"——缓存也是派生物，所以删除同样必须清缓存。否则：

文档已删 → 索引里的块清干净了
        → 但用户用同样的 query 查 → 直接命中缓存 → 拿到已删内容

成因和撤权是同一个：缓存不接在主链路的过滤之后，它是绕开主链路的另一条路。

【取舍】但删除比撤权更难清，难在反查方向：

撤权：缓存键里带 user / tenant → 从"主体"反查缓存条目，方向是顺的
删除：缓存键是 query 文本      → 要从"内容"反查缓存条目，方向是反的

一份文档切成 N 个块，而一个缓存条目里又拼了多个文档的块
→ doc_id 与 cache_key 是多对多，缓存本身不维护这个映射

【事实】三条可行做法（从细到粗）：

① 缓存条目记录 provenance（它引用了哪些 doc_id / chunk_id）→ 建 doc_id → cache_key 反查，删除时批量失效
② 命中缓存后"二次校验"：把命中的条目当成召回结果，用它记的 source_id 回查"块还在吗、还有权吗"
   → 不成立就丢弃重算（和 [[母题-G4-引用绑定与证据可追溯]] 的"引用再次鉴权"是同一条思路）
③ 索引版本 / 知识库版本号进缓存键，删除后 bump → 整片逻辑失效（粒度粗，但不会漏）

【推论】第 ② 条是最该说的一句：过滤链要在缓存之后也走一遍——命中缓存 ≠ 已经过了有效性检查和鉴权。

【取舍】TTL 的定位：TTL 只是"最多陈旧 T 秒"的上界，不是"删除后立即生效"的保证。合规场景（删除请求、违规内容撤回）不能拿 TTL 兜底。

【推论】派生引用是最长尾的一层：它已经离开检索系统（Agent 记忆、会话摘要、历史回答里引用的正文）。穷尽清除做不到，只能靠"再次使用前回查有效性"——和撤权的差别是：删除是全局失效（谁都不该看），撤权是按主体失效（只有他被撤了）。

到这里你应该能回答：删除只清索引里的块够不够？为什么"缓存按权限分区"挡不住已删内容？

4. 撤权：要清的地方比删除还多【推导】

【推导】撤权时，内容没变，变的是"谁能看"——所以要清的不只是索引：

① 主索引里的元数据（ACL 字段）
② 向量索引里的对应项（如果按权限分区的话）
③ 倒排索引
④ 【缓存】——这一条最容易被漏掉
⑤ 任何派生的引用、摘要、Agent 的记忆

【推论】第 ④ 条是关键：缓存会绕过 ACL 过滤（[[母题-G2-向量与关键词的混合检索]] 里"权限必须在召回前生效"讲的是主链路，缓存是绕开主链路的另一条路）。

如果缓存是按 query 文本做键的，那么：
  有权用户查过 → 结果进了缓存
  无权用户用同样的 query 查 → 直接命中缓存 → 拿到不该看的内容

【推论】所以缓存必须按租户 / 权限分区——它不是优化，是权限模型的一部分。

【补充】但分区也不是万能的：分区挡的是"跨主体泄漏"（A 查过 → B 命中）；同一个用户被撤权后，他的 (user_id, query) 键没变，照样会命中他自己以前查到的内容。所以撤权除了分区，还要显式失效该主体的缓存条目——分区是结构，失效是动作，两个都要有。

到这里你应该能回答：为什么"下次查询时 ACL 会过滤掉"这句话，挡不住缓存泄漏？

5. 新鲜度：必须可观测【事实】

【事实】archive/study-courses/03 的要求（这一节可以直接背）：

① 文档带 effective_at、expires_at、source_version
② 索引延迟【可观测】
③ 已删除 / 过期内容可追踪传播
④ 回答【展示规则生效时间】
⑤ 冲突时优先权威级别和最新生效版本，并【显式说明】

【推导】第 ② 条是最该盯的指标：

索引滞后 = 文档变更时刻 → 该内容可被检索到的时刻

如果增量任务每 5 分钟跑一次：
  平均滞后 ≈ 2.5 分钟
  最大滞后 ≈ 5 分钟（在两次跑之间提交的变更）

这个数必须是个可观测的指标，而不是"我们大概几分钟同步一次"

【推论】为什么它必须是"指标"而不是"约数"：因为它决定"回答能不能引用刚改过的规则"——如果业务承诺"规则改了 10 分钟内生效"，那滞后指标超过 10 分钟就是故障。

【取舍】第 ④ 条第 ⑤ 条是同一个思路：冲突或过期时，不要偷偷选一个——把"这是哪一版、什么时候生效的"显式告诉用户。这跟 [[母题-G4-引用绑定与证据可追溯]] 的"引用要能定位到版本"是同一条。

6. 双写 / 影子索引再切换【事实】

【推导】直接原地覆盖索引有两个问题：

① 没有回滚路径（覆盖了就回不去）
② 重建期间旧索引已被破坏 → 出问题只能全量重来

【事实】正确做法是双写 / 影子索引：

新建一份索引 → 双写（或先切流量的一小部分）→ 验证指标没问题 → 切换
                                                                  ↓
                                                            切错了能回滚

【推论】这和 [[母题-M4-索引代价与大表变更]] 的"影子表方案（pt-osc / gh-ost）"是同一个模式：

凡是要改"正在服务的派生结构"，都用"新建一份 + 双写 + 验证 + 切换"这套动作。

到这里你应该能回答：为什么换 Embedding 模型必须走双写切换，而不能原地重跑？

7. 边界与常见误解

常见说法修正
"删除就是把文档记录删掉"文档记录只是主记录，派生物散在 100 个块里（向量 + 倒排 + 元数据）。必须按 doc_id 反查全部 chunk_id 逐个清——漏一个就是"已删内容还能被搜到"的合规事故
"删除只要把索引里的块清干净就行"不够。派生物还有索引外一层：检索结果缓存、生成回答缓存 / 语义缓存、派生引用与 Agent 记忆。缓存绕开主链路过滤，不清就会命中已删内容。而且删除的反查方向是反的（缓存键是 query，不是 doc_id）→ 给缓存条目记 provenance 后按 doc_id 反查失效 / 命中后回查有效性 / 版本号进缓存键，三选一。TTL 只是陈旧上界，不是生效保证
"缓存按权限分区了，就不用担心缓存泄漏"只挡住了一半。分区挡的是跨主体泄漏；挡不住已删内容，也挡不住同一用户被撤权后命中自己以前查过的缓存（键没变）。分区是结构，失效是动作，两个都要有
"撤权了下一次查询会被 ACL 过滤掉"挡不住缓存。如果缓存按 query 文本做键，有权用户查过的结果会直接命中给无权用户。缓存必须按租户 / 权限分区——它是权限模型的一部分，不是优化项
"每天全量重建最省心"在数据量小、更新少时确实对（简单性是真实收益）。但重建一次要多久、多久要重建一次才是判据——100 万块每天改 1% 时，增量能省 99% 的嵌入调用
"原地覆盖索引就行，反正内容一样"没有回滚路径，而且重建期间旧索引已被破坏。要新建一份 + 双写 + 验证 + 切换——和影子表方案是同一个模式
"索引滞后我们大概几分钟""大概"不够。它是个必须可观测的指标（变更时刻 → 可被检索时刻）。如果业务承诺"规则 10 分钟内生效"，那它超 10 分钟就是故障
"旧版本新版本都一样，选一个返回就行"冲突时要显式说明：优先权威级别和最新生效版本，并把"这是哪一版、什么时候生效"告诉用户。偷偷选一个会让用户以为那是唯一的答案
"换 Embedding 模型只要重跑一遍"新旧向量不可比（[[母题-G2-向量与关键词的混合检索]]），混在一起检索结果会错乱。必须全量重嵌入 + 双写切换——这意味着换模型是一次成本很高的操作，要提前规划

【取舍】读成一句话：增量省的是成本，删除与撤权保的是正确性——前者做不好是慢，后者做不好是事故。

三 · 面试输出 闭卷口述 60 秒，再看结论

知识改了、删了、撤权了，索引怎么跟上——为什么"更新"这件事里最难的不是新增，而是删除？

翻面对照自测；复训调度以训练台派单为准。

为什么重要：这是 RAG 面试里最容易被忽略、但工程上最容易出事的一题。多数人答得出"我们每天重建一次索引"，但答不出"删除怎么传播"。而删除和撤权出事不是性能问题，是合规事故——用户能搜到已经删除或本无权看的内容。

一句话结论 全卡唯一要背的锚点

索引是派生数据，源变了它就必须变——三种变化各自要处理：新增 / 修改走增量链路（只重跑变化的 1%，100 万块每天改 1% 时能省 99% 的嵌入调用）；删除最难，因为要按 doc_id 反查它切出来的全部块（一份文档 100 个块就要清 100 个），漏一个就是"已删内容还能被搜到"的合规事故——而且派生物有索引内、索引外两层，索引外的缓存与派生引用同样要清（缓存绕开主链路，命中一次就把已删内容交出去了；只是反查方向是反的：缓存键是 query，不是 doc_id）；撤权是按主体清——主索引、向量、倒排，以及缓存，因为缓存会绕过 ACL 过滤（有权用户查过的结果会命中给无权用户），所以缓存必须按租户 / 权限分区——但分区只挡跨主体泄漏，同一用户被撤权后键没变、照样命中自己查过的内容，所以分区之外还要有显式的失效动作。新鲜度必须可观测：文档带 effective_at / expires_at / source_version，索引滞后（变更时刻 → 可检索时刻）要是一个被监控的指标，回答要展示规则生效时间，冲突时显式说明版本而不是偷偷选一个。改索引结构（比如换 Embedding 模型）要走双写 / 影子索引再切换——凡是要改正在服务的派生结构，都用"新建 + 双写 + 验证 + 切换"这套动作。

1. 知识更新怎么做到增量且不返回失效内容？

Source 事件触发增量解析与索引；新旧索引双轨验证；文档和 chunk 版本化；删除 / 撤权必须传播；回答记录知识版本；支持回滚，并监控索引滞后。 这是 archive/study-courses/03 给的完整清单。

2. 删除与撤权怎么传播？缓存会不会污染？

两层都要清：索引内（删除按 doc_id 反查全部 chunk_id 逐个清向量 + 倒排 + 元数据；撤权改 ACL 字段 / 向量分区）+ 索引外（缓存、派生引用、Agent 记忆）。删除按内容反查（doc_id → 哪些缓存条目引用了它），撤权按主体反查（user / tenant → 他能命中哪些）。缓存会绕过 ACL 过滤——所以缓存按租户 / 权限分区不是优化，是权限模型的一部分；但分区只挡跨主体，同主体撤权后键没变仍会命中，所以还要显式失效，兜底是命中后按 provenance 回查有效性。

3. 索引滞后多少算正常？

取决于业务承诺：如果承诺"规则修改 10 分钟内生效"，那任务周期取 5 分钟（2 倍余量）就是合理的；滞后指标超过承诺时限就是故障。关键是它必须是个指标，不是"大概几分钟"。

4. 换 Embedding 模型要注意什么？

新旧向量不可比，必须全量重嵌入；不能原地替换（没有回滚路径），要走双写 + 影子索引 + 验证 + 切换；切换期间要双写，成本要提前规划。

5. 冲突的文档怎么处理？

优先权威级别和最新生效版本，并显式说明——不要偷偷选一个，否则用户会以为那是唯一的答案（[[母题-G4-引用绑定与证据可追溯]]）。
  • 「多租户的知识库怎么更新？」——按租户分区：索引分区、缓存分区、删除与撤权也要按租户生效。跨租户的测试是必测项（不属于"边界情况"，是"核心正确性"）。
  • 「实时数据（比如设备状态）要不要进 RAG？」——不要。实时事实走 Tool / 数据库，静态说明走 RAG（EnergyOps 的做法）。把实时数据塞进索引会同时毁掉两边：索引追不上实时变化，而查询又会拿到过期的"事实"。

- 数驭穹图：Schema / 指标口径 / 样例查询都会变——口径变了要让哪些历史回答失效？这是"删除传播"在语义层的版本（不只是删除文档，还要处理"用旧口径得出的结论"）。 - RuleArena：条款有生效时间——"某条款什么时候开始适用"必须能回答，而且过期条款不能被召回（否则会拿着作废的规则做审查）。 - EnergyOps：运维文档、设备数据和实时状态不混成一个索引——实时状态根本不进 RAG，所以它的"更新"问题不存在；只有静态说明才需要走本卡这套链路。

索引是派生数据（三种变化）→ 为什么值得增量（给 99% 的算式）+ 增量的代价 → 删除为什么最难（反查表 + 漏删的性质）→ 派生物两层：索引内 / 索引外，删除和撤权都要清（缓存绕开主链路）→ 删除按内容反查、撤权按主体反查（分区只挡跨主体 + 失效动作 + provenance 回查 + TTL 只是上界）→ 新鲜度可观测（滞后指标 + 展示生效时间 + 冲突显式说明）→ 双写切换模式 → 收束到"删除与撤权是正确性问题"

增量省的是成本，删除与撤权保的是正确性。 前者做不好是"慢"，后者做不好是事故——所以删除传播必须当成一条独立的、可验证的链路，而不是"我调了删除接口"。
