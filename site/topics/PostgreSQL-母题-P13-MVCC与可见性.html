题目

PG 的 UPDATE 为什么不「改一行」，而是「插一行」？

三 · 面试输出 闭卷口述 60 秒，再看结论

MVCC 在 PG 里怎么实现？xmin / xmax 与「更新即新版本」意味着什么？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是整条主线五的地基——膨胀、VACUUM、事务 ID 回卷这三件 PG 独有的事，全都是「版本留在堆里」的直接后果。而且它同时是 P11 那道题的答案（为什么 PG 不需要 undo）。面试官问 PG 的 MVCC，其实是在问「你知不知道代价藏在哪」。

一句话结论 全卡唯一要背的锚点

PG 把每个行版本都留在堆里，用行的 xmin（创建它的事务 ID）和 xmax（删除它的事务 ID）+ 当前快照的事务范围判断可见性——读的时候不改数据、不加锁。所以 UPDATE 实际是「写一个新版本 + 把旧版本的 xmax 标成本事务」。代价是死元组必须靠 VACUUM 回收，而且索引里还留着指向旧元组的条目——这正是表膨胀的根源，也是它和 MySQL「版本链放 undo log、purge 线程自动清理」最大的差别。
  • xmin
  • xmax
  • 版本留在堆里
  • 更新即新版本 + 标记旧版本
  • 可见性由快照决定
  • 死元组
  • 索引也指向死元组
  • HOT 更新

PG 的 MVCC 是「绝不动旧数据」的 MVCC。 收益是读永不阻塞写、写永不阻塞读；代价是空间必须由 VACUUM 回收——这就是「PG 为什么必须懂 VACUUM」的全部理由。

讲解

原理分解

一、两种 MVCC：版本放在哪，决定了运维形态

MySQL（InnoDB）PostgreSQL
版本存在哪undo log（版本链在回滚段）堆里（每行一个新版本）
更新怎么做就地改当前行，旧值写进 undo写一个新版本，把旧版本标记为死
回收purge 线程自动、基本无需人工关注VACUUM / autovacuum（可能跟不上）
读的可见性用 ReadView + undo 链回溯用行的 xmin/xmax + 快照判定
需要 undo 日志吗需要不需要（版本本来就在表里）

这张表是全库最重要的一张对照表：「回收是否自动」这一个差异，直接决定了 PG 有一整套 MySQL 没有的运维课题（膨胀、VACUUM 调参、事务 ID 回卷、idle in transaction 监控）。

二、xmin / xmax 怎么工作

每一行版本头部有两个关键字段：

字段含义
xmin创建这个版本的事务 ID
xmax删除/更新掉这个版本的事务 ID（为空表示还活着）

可见性判定的简化版：

读取时，用一个「快照」——它记录了「哪些事务算是已提交、哪些还没」
某个版本对当前快照可见，需要：
   xmin 的事务已提交且「在快照之前」         → 这个版本已经被创建出来了
   且 xmax 为空，或 xmax 的事务「在快照之后 / 未提交」  → 还没被真正删掉

所以「读」完全不需要动数据、也不需要加锁——它只是拿两个事务 ID 和一份快照做比较。这就是「读永不阻塞写」的实现方式。

三、更新即新版本：一句 UPDATE 背后发生了什么

UPDATE tasks SET status = 'DONE' WHERE id = 42;

实际动作：

1. 在堆里写一个新版本（xmin = 当前事务，新值）； 2. 把旧版本的 xmax 设为当前事务（标记「被它删掉了」）——旧版本仍然物理存在； 3. 更新所有索引：索引需要指向新版本的位置（ctid 变了）； 4. 事务提交后：旧版本对新快照不可见，但对还在用旧快照的事务（长事务！）仍然可见。

第 4 步是关键：旧版本什么时候能被删，取决于「还有没有人在用能看到它的快照」——这就是 P14 的全部机理。

四、代价：死元组 + 索引也指向它

两个必须记住的后果：

① 堆会变"胖"：更新 N 次就有 N 个版本（只有一个活着）。表文件不会自动变小，空间只能靠 VACUUM 标记为「可复用」——注意：可复用 ≠ 文件变小（见 P15）。

② 索引也要清理：B-tree 索引项指向 ctid，旧版本的条目会变成指向死元组的"死索引项"——VACUUM 必须同时清理堆和索引。所以「索引多 → VACUUM 更累」这件事在 PG 里是机制性的，不是经验之谈（这也是 P4 里「PG 的索引第三项代价是 VACUUM 压力」的由来）。

一个可以直接说出来的量化直觉：一张更新频繁的表，实际占用的空间可以是"有效数据"的好几倍——「表大小」和「数据量」在 PG 里是两个概念。

五、HOT 更新：一个重要的写入优化

HOT（Heap-Only Tuple）更新：如果

1. 更新的列不属于任何索引，且 2. 新版本能放进同一个数据页里

那么 PG 不需要更新任何索引——新版本通过页内的指针链和旧版本连起来。

为什么重要：它把「一次更新要改所有索引」降级成「只写堆」，是 PG 在高频更新表上最有效的内置优化。实践推论：不要把频繁更新的列放进索引（比如状态、计数器、updated_at 如果不需要用来查询就别索引它）——这条是从机制推出来的设计规则，比背「索引不要建太多」有力得多。
