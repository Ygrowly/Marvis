母题 P13 · MVCC 与可见性

关联 母题-P11-WAL与checkpoint（为什么不需要 undo）· 母题-P14-长事务与表膨胀（旧版本什么时候能删）· 母题-P15-VACUUM与事务ID回卷（32 位 ID 的后果）· 母题-P8-隔离级别与读一致性（快照粒度决定看到哪个版本）· 母题-M9-MVCC（MySQL 侧对照） ｜ 正本 wiki/topics/PostgreSQL/母题-P13-MVCC与可见性.md

必懂 3 件事（① PG 的 UPDATE 不做原地修改——它写一个新行版本，官方原话是「每次更新都会为同一个逻辑行创建一个新的行版本」 ② 可见性靠「行上的两个事务 ID + 一份快照」判定，读不加锁——这是「读永不阻塞写」的实现 ③ 死元组必须靠 VACUUM 回收，而且索引里也留着指向死元组的条目——这是主线五全部问题的源头）· 读完约 12 分钟 · 需要先懂：[[母题-P11-WAL与checkpoint]]

题目

PG 的 UPDATE 为什么不「改一行」，而是「插一行」？

一 · 教材 从前提推到结论，不需要先会

1. 两种 MVCC：版本放在哪，决定了运维形态

MySQL（InnoDB）PostgreSQL
版本存在哪undo log（版本链在回滚段）堆里（每行一个新版本）
更新怎么做就地改当前行，旧值写进 undo写一个新版本，把旧版本标记为死
回收purge 线程自动、基本无需人工关注VACUUM / autovacuum（可能跟不上）
读的可见性用 ReadView + undo 链回溯用行的 xmin/xmax + 快照判定
需要 undo 日志吗需要不需要（版本本来就在表里）

【事实】官方对 MVCC 收益的表述可以直接背：

MVCC 相比加锁模型的主要优势是：为查询（读取）获取的锁与为写入数据获取的锁不冲突，因此【读永不阻塞写、写永不阻塞读】。

【结论】这张表是全库最重要的一张对照表：「回收是否自动」这一个差异，直接决定了 PG 有一整套 MySQL 没有的运维课题（膨胀、VACUUM 调参、事务 ID 回卷、idle in transaction 监控）。

2. xmin / xmax 怎么工作

【事实】官方的定义（可直接引用）：

系统列官方定义
xmin这一行版本的【插入】事务的标识。（一个行版本是一行的一个状态；每次更新都会为同一个逻辑行创建一个新的行版本）
xmax【删除】事务的标识，未删除的行版本是零。
cmin / cmax插入 / 删除事务内部的命令序号
ctid这一行版本在表里的物理位置

【纠正常见误解】xmax 非零 ≠ 这行不可见——官方专门写了这一句：

xmax 这一列在一个【可见的】行版本上也可能非零。 这通常说明删除它的事务还没提交，或者那次删除尝试被回滚了。

【推导】可见性判定的两个条件：

读取时手里有一个「快照」——它记录了「哪些事务算已提交、哪些还没」
某个版本对当前快照可见，需要同时满足：

① xmin 的事务已提交，且「在快照之前」
     → 这个版本已经被创建出来了

② xmax 为空，或 xmax 的事务「在快照之后 / 未提交 / 已回滚」
     → 还没被真正删掉

【推论】所以「读」完全不需要动数据、也不需要加锁——它只是拿两个事务 ID 和一份快照做比较。 这就是「读永不阻塞写」的实现方式。

【事实】一个容易踩的坑，官方专门提醒：

ctid 可以用来很快地定位行版本，但【一行的 ctid 在它被更新、或被 VACUUM FULL 移动之后就会改变】。

因此 ctid 不应该被当作行标识来用；应该用主键来标识逻辑行。

【推论】这条直接否掉了两种常见做法：① 用 ctid 做分页游标（翻页过程中被更新的行会漏掉或重复）；② 用 ctid 做去重或对账的键。它不是稳定标识，只是"当下在第几页第几个位置"。

3. 更新即新版本：一句 UPDATE 背后发生了什么

UPDATE tasks SET status = 'DONE' WHERE id = 42;

实际动作：

1. 在堆里写一个新版本（xmin = 当前事务，新值）； 2. 把旧版本的 xmax 设为当前事务（标记「被它删掉了」）——旧版本仍然物理存在； 3. 更新所有索引：索引需要指向新版本的位置（ctid 变了）； 4. 事务提交后：旧版本对新快照不可见，但对还在用旧快照的事务（长事务！）仍然可见。

第 4 步是关键：旧版本什么时候能被删，取决于「还有没有人在用能看到它的快照」——这就是 P14 的全部机理。

【推导】把代价算成数字：

一行 200 字节，被更新 10 次：
  堆里 = 11 个版本 × 200 B = 【2200 字节】
  而"有效数据"只有 200 字节 → 【11 倍】

每个引用被改列的索引：
  也要有 11 个条目 → 索引同样膨胀 11 倍
  （除非走 HOT —— 见第 5 节）

【结论】「表大小」和「数据量」在 PG 里是两个概念——一张更新频繁的表，实际占用可以是有效数据的数倍。

4. 代价：死元组 + 索引也指向它

两个必须记住的后果：

① 堆会变"胖"：更新 N 次就有 N 个版本（只有一个活着）。

【事实】而且「回收」要分成两件事，官方原话：

标准形式的 VACUUM 会移除表和索引里的死行版本，并把空间标记为【可供将来复用】。

然而，它【不会把空间还给操作系统】——除非出现特殊情况：表末尾的一个或多个页完全空闲，而且能轻易拿到排他表锁。

【推论】「VACUUM 过了，表文件没变小」不是故障，是设计：

普通 VACUUM  ：把死元组的空间标记为【可复用】
               → 后续的 INSERT/UPDATE 会填进来
               → 表文件大小【不变】

VACUUM FULL  ：重写整张表到新文件，把空间还给操作系统
               → 代价：持【排他锁】、需要等量磁盘空间
               → 官方也说了：Plain VACUUM 在大量死元组时可能不够满意，
                 这种情况才需要 VACUUM FULL 或 CLUSTER

【取舍】所以判据是：

你要的是「别再涨」还是「变小」？

「别再涨」→ 普通 VACUUM + 让 autovacuum 跟得上就够。

「变小」→ 只有 VACUUM FULL / CLUSTER 能做到，而且它们要拿排他锁——这条路的代价通常比"表大"本身更贵（[[母题-P15-VACUUM与事务ID回卷]]）。

② 索引也要清理：B-tree 索引项指向 ctid，旧版本的条目会变成指向死元组的"死索引项"——VACUUM 必须同时清理堆和索引。

【推论】所以「索引多 → VACUUM 更累」这件事在 PG 里是机制性的，不是经验之谈——这也是 P4 里「PG 的索引第三项代价是 VACUUM 压力」的由来。

5. HOT 更新：一个重要的写入优化

HOT（Heap-Only Tuple）更新：如果

1. 更新的列不属于任何索引（官方补充：排除 BRIN 这类"摘要索引"），且 2. 新版本能放进同一个数据页里

那么 PG 不需要更新任何索引——新版本通过页内的指针链和旧版本连起来。

【事实】它还有第二样收益（常被漏掉）：当一行被更新多次时，除最旧和最新之外的中间版本，可以在【正常运行期间（包括 SELECT）】被直接移除，不必等 VACUUM。所以 HOT 同时减轻了写路径和清理路径——这是它连到 P14/P15 的那根线。

【实践推论】不要把频繁更新的列放进索引（比如状态、计数器、updated_at——如果它不需要用来查询就别索引它）——这条是从机制推出来的设计规则，比背「索引不要建太多」有力得多。

【事实】这一条可以量化验证：pg_stat_all_tables 里有 n_tup_upd 与 n_tup_hot_upd，两者的比值就是 HOT 占比（[[母题-P4-索引代价与在线建索引]]）。

6. 边界与常见误解

说法实际情况
「PG 也有 undo log」明确错误。版本留在堆里，这正是它不需要 undo 的原因
「MySQL 也要 VACUUM」明确错误。MySQL 靠 purge 线程自动回收版本链，没有 VACUUM 这个动作
「xmax 非零说明这行被删了」不一定可见性——删除可能还没提交、或已经回滚（官方原话）
「VACUUM 之后表文件会变小」普通 VACUUM 只把空间标记为可复用；要还空间给操作系统得 VACUUM FULL / CLUSTER，且要排他锁
「可以用 ctid 做分页游标或行标识」ctid 在更新或被 VACUUM FULL 移动后会变——官方明确说不该当行标识
「更新一行只影响一行」堆里多一个版本、每个引用被改列的索引多一个条目

三 · 面试输出 闭卷口述 60 秒，再看结论

MVCC 在 PG 里怎么实现？xmin / xmax 与「更新即新版本」意味着什么？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是整条主线五的地基——膨胀、VACUUM、事务 ID 回卷这三件 PG 独有的事，全都是「版本留在堆里」的直接后果。而且它同时是 P11 那道题的答案（为什么 PG 不需要 undo）。面试官问 PG 的 MVCC，其实是在问「你知不知道代价藏在哪」。

一句话结论 全卡唯一要背的锚点

PG 把每个行版本都留在堆里，用行的 xmin（创建它的事务 ID）和 xmax（删除它的事务 ID）+ 当前快照的事务范围判断可见性——读的时候不改数据、不加锁。所以 UPDATE 实际是「写一个新版本 + 把旧版本的 xmax 标成本事务」。代价是死元组必须靠 VACUUM 回收，而且索引里还留着指向旧元组的条目——这正是表膨胀的根源，也是它和 MySQL「版本链放 undo log、purge 线程自动清理」最大的差别。
  • xmin（插入事务）
  • xmax（删除事务，非零不等于不可见）
  • ctid 会变，不能当行标识
  • 版本留在堆里
  • 更新即新版本 + 标记旧版本
  • 可见性由快照决定
  • 死元组
  • 索引也指向死元组
  • 普通 VACUUM 不还空间给操作系统
  • HOT 更新

卡住时靠这几个词重建整条链。

展开（先自答，再看 · 默认收起，不进复训调度）

MySQL 的 MVCC 是undo log 版本链 + ReadView，purge 线程自动回收；PG 是版本留在堆里 + xmin/xmax，靠 VACUUM 回收。「MySQL 也要 VACUUM」是明确错误；「PG 有 undo log」也是明确错误。还有一处容易漏：PG 的 xmin/xmax 是行上的可见系统列，可以直接 SELECT xmin, xmax FROM t——这是排查"这行为什么看得到/看不到"的最直接手段，MySQL 那边没有对等的东西。

1. 既然旧版本还在表里，那读的时候怎么知道该读哪个？

按快照判定 xmin/xmax：同一个事务读同一个快照，看到的就是同一批版本。这也解释了 P8 那个反直觉现象——RC 下每条语句换一次快照，所以能看到不同版本；RR 下共用一个快照，所以结果一致。 P8、P13 是同一件事的两个面。

2. xmin/xmax 是 32 位事务 ID，会不会用完？

会，这就是事务 ID 回卷（[[母题-P15-VACUUM与事务ID回卷]]）。32 位 ID 循环使用，所以必须靠【冻结】标记"这行很老、一定可见"；清理长期跟不上，就可能出现"老数据被误判成未来才可见"的灾难。 PG 的应对是：先告警，最后拒绝新事务，强制进入维护模式——「宁可停机也不出错数据」这个取舍本身就是很好的面试谈资。 而且官方的说法很硬：一张表最多可以 20 亿事务不被 VACUUM，超过就【可能造成数据丢失】。

3. PG 的读会不会被写阻塞？

不会（读不加锁）；但 ALTER TABLE 这类 DDL 会拿表锁（[[母题-P4-索引代价与在线建索引]]），那会阻塞。

4. 为什么 PG 的表「更新一次就变大一次」？

没有原地更新，旧版本还在；空间要等 VACUUM。而且「VACUUM 过」不等于「变小了」——它只是把空间标记为可复用。

5. PG 有 SELECT ... FOR UPDATE 就说明读要加锁吗？

不，那是显式加锁（[[母题-P10-无间隙锁与锁变体]]），默认的读不加任何锁。
  • 「HOT 为什么在 PG 里这么重要？」—— 因为它把「一次更新要改所有索引」降级成「只写堆」，并且让中间版本能在正常运行中被清理。它是 PG 在高频更新表上最有效的内置优化，而且它的生效条件直接变成了一条表设计规则（高频更新的列不进索引）。
  • 「ctid 能拿来做什么、不能做什么？」—— 能：定位行版本、诊断页分布（ctid 的块号分布能看出表有没有物理碎片）。不能：当行标识、当分页游标、当对账键——官方明确说应该用主键标识逻辑行。

- EnergyOps 的四层事实表（聚合表高频重算 → 版本堆积最快，是最需要盯 VACUUM 的表）。 - RuleArena 的状态机表（status 反复更新——正因为 status 不在索引里，HOT 更新能生效，这是它写入性能还不错的原因之一）。 - 数驭穹图的元数据表（更新少但行数大，主要盯冻结而不是盯膨胀）。

为什么需要多版本 → PG 把版本放在哪（对比 MySQL）→ xmin/xmax 怎么判定可见性 → 更新即新版本意味着什么 → 代价：死元组 + 索引指向旧版本 → HOT 更新是什么 → 收束到「绝不动旧数据」

PG 的 MVCC 是「绝不动旧数据」的 MVCC。 收益是读永不阻塞写、写永不阻塞读（官方原话）；代价是空间必须由 VACUUM 回收——这就是「PG 为什么必须懂 VACUUM」的全部理由。
