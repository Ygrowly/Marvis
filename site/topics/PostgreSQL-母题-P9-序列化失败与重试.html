题目

把隔离级别提到 Serializable 之后，接口开始零星报 could not serialize access due to read/write dependencies。这是「不能用」还是「设计如此」？

一 · 教材 从前提推到结论，不需要先会

1. SSI 是怎么做到可串行化的

传统可串行化靠两阶段锁（锁到事务结束），代价是并发度低、容易死锁。PG 走另一条路：

① 先按快照隔离执行，读不加锁 —— 大部分事务根本不会冲突
② 在后台记录事务之间的「读写依赖」（谁读了谁写的数据）
③ 如果发现依赖形成一个环 —— 就不可能存在任何串行顺序 → 报错并干掉其中一个

关键在「② 只记录依赖，不是拦住操作」：所以没有冲突的事务完全没有额外等待。只有真的出现环时才失败。

【事实】官方的三条定性，把 SSI 和「加锁」彻底分开：

- 这些锁不造成任何阻塞，因此也不可能参与造成死锁。它们只用来标记并发 Serializable 事务之间的依赖。

- 对比之下，一个想保证数据一致性的 RC / RR 事务可能需要拿整张表的锁，那会阻塞其他用户；或者用 SELECT FOR UPDATE / FOR SHARE——它们不仅能阻塞别人，还会带来磁盘访问（必须回表读最新的版本）。

- 这些谓词锁在 pg_locks 里以 SIReadLock 模式出现。

【推论】这就是「SSI 的代价是失败，不是等待」的机制来源——它把并发代价从「锁等待」搬到了「事后中止」。而且 SIReadLock 给了你一个可观测的手柄：排查 40001 时，先看 pg_locks 里那个事务到底"读"了多大范围。

到这里你应该能回答：为什么「Serializable 会让数据库到处加锁变慢」这个说法在 PG 里是错的？

2. 谓词锁会「升级」——误报的机械原因【事实】

这是 P9 最值钱的一段，也是最没人讲的一段。官方明确给出了升级规则与参数默认值：

参数默认值含义
max_pred_locks_per_page2单页上被谓词锁住超过 2 行 → 升级为整页锁
max_pred_locks_per_relation-2负数表示 max_pred_locks_per_transaction ÷ 2
max_pred_locks_per_transaction64每个事务的谓词锁对象上限

【推导】把这些默认值串起来，得到一个很吓人的数字：

每页超过 2 行 → 整页锁
每表超过 (64 ÷ 2) = 32 页 → 【整表锁】

也就是说：
  一个 Serializable 事务只要在同一张表上读了【33 页】
  → 它的谓词锁就变成【整张表】级别
  → 此后【任何写这张表的事务】都可能与它冲突

33 页 × 8 KB = 【264 KB】

【结论】读 264 KB 就把整张表标成"我读过"——对一张 16 GB 的表，这只是 1/60000。 但它让 40001 的冲突面从「若干行」放大到「整张表」。

【推论】官方原话把后果说得更直白：

当系统因为谓词锁表内存不足，被迫把多个页级谓词锁合并成一个【关系级】谓词锁时，序列化失败率会上升。

一次顺序扫描【总是】需要一个关系级谓词锁——这会导致序列化失败率上升。 可以通过降低 random_page_cost 和/或提高 cpu_tuple_cost 来鼓励走索引扫描。

【结论】所以有一个反直觉的结论：

在 Serializable 下建索引，不只是为了查询快——是为了降低 40001 率。

一条没走索引的查询，会把整张表标记成"读过"，让大量本不相干的事务互相冲突。

【事实】调大谓词锁的参数是官方认可的动作：max_pred_locks_per_transaction（默认 64）/ max_pred_locks_per_relation（默认 -2）/ max_pred_locks_per_page（默认 2）——加大它们就是把"升级"推迟，用内存换更低的误报率。

【纠正常见误解】「SSI 的误报」不是玄学，是内存策略——细粒度锁（行级/页级）会为了不撑爆锁表而合并成粗粒度锁（页级/表级），合并就丢精度，丢精度就误报。 能说出这一条，说明你真的理解 SSI 的实现，而不是背了它的名字。

3. 错误长什么样，怎么识别

ERROR: could not serialize access due to read/write dependencies among transactions
DETAIL: Reason code: Canceled on identification as a pivot...
SQLSTATE: 40001

【事实】判断这件事要用错误码（40001），不要用错误文本匹配——文本会随版本/语言变化，错误码是契约。 官方原话也确认了这一点：「环境必须有一套统一的序列化失败处理方式，因为序列化失败【总是】以 SQLSTATE 40001 返回」。

同一个 40001 也会由 RR 下的写冲突产生（[[母题-P8-隔离级别与读一致性]]），语义都是「重试就能成功」。

要区分的三类错误：

错误语义处理
40001（序列化失败 / 快照过期）可重试：重放事务大概率成功重试整个事务
40P01（死锁）也可重试，但说明加锁顺序有问题重试 + 修加锁顺序
约束冲突（23505 等）确定性失败，重试也没用不要重试，走业务分支

【推论】这个三分法比「统一重试三次」重要得多——对确定性错误无脑重试，是在制造重复副作用。

【事实】一个非常反直觉的官方提醒：Serializable 并不能保证「真实串行执行下不会报的错就不报」——它可能报出真实的串行执行里根本不会发生的唯一约束冲突，即使你已经先查过那个键不存在。

规避方式是：所有会插入潜在冲突键的 Serializable 事务，都必须【先显式检查】。 例如：有的应用直接插入、有的应用先 SELECT 再插入，那么前者会让后者报出不该报的唯一冲突。

【推论】所以「先查再插」这个动作，只有在【所有】参与者都这么做时才有效。 协议不统一，比完全不做协议更糟——因为它给了你虚假的安全感。

4. 正确的重试长什么样

必须是「整个事务」，不是「那一条语句」：

① 记录本次事务的输入（幂等键）
② BEGIN
③ 执行全部读与写
④ COMMIT
   └─ 若报 40001 → 回滚 → 重新执行 ③（用同样的输入）

因为 SSI 失败意味着「你读到的那个快照已经不可信」——重试那一条语句没有意义，必须重新读。

【事实】失败发生在哪一步，官方给了明确答案：SSI 的检测可以一直持续到提交时——官方那个例子就是「两个事务都做完了，然后都试着提交」时，其中一个被回滚。 所以 COMMIT 是一个会失败的操作——这打破了「提交不会失败」的朴素假设。

【推导】这把重试框架的要求提高了：

朴素写法：
  try { ...; commit(); } catch (...) { /* 只有语句会抛错 */ }
  → COMMIT 抛 40001 时，事务其实【没有提交成功】
  → 但很多框架会把 commit 的异常当成"未知状态"

正确写法：
  把 COMMIT 也包进可重试的范围
  并且确认【回滚是干净的】——失败的事务不能留下任何副作用

四条要求：

  • 带退避 + 抖动：并发高时同步重试会互相打架，越试越糟；
  • 有重试上限：超过就暴露成失败/未知，不要无限循环；
  • 整个事务幂等：重试不能产生第二次副作用——所以必须有幂等键或唯一约束兜底（[[母题-P18-乐观并发控制]] / [[母题-P19-唯一约束与UPSERT]]）；
  • 保留 trace：记录重试次数，它是「并发竞争激烈程度」的直接指标（可以直接做监控）。

反过来讲最重要的一句：SSI 要求业务可重试；而「可重试」的前提是副作用可幂等。 所以「能不能上 Serializable」其实是一个幂等设计问题，不是一个数据库配置问题。这句话是这道题的分水岭。

【事实】官方给的性能建议里，有三条和「重试」直接相关：

- 尽可能把事务声明成 READ ONLY（只读事务在很多情况下根本不必拿谓词锁）。

- 控制活跃连接数，必要时用连接池——这条在跑 Serializable 的繁忙系统里尤其重要。

- 不要让连接长时间 "idle in transaction"——可以用 idle_in_transaction_session_timeout 自动断开。

- 消除那些因为 Serializable 已自动提供保护而不再需要的显式锁 / FOR UPDATE / FOR SHARE。

最后一条最容易被忽略：很多人一边上 Serializable、一边保留着 FOR UPDATE——那是把两套代价都付了。

5. 跟其他方案比

方案机制适合代价
Serializable（SSI）检测依赖环 → 报错重试冲突低但需要跨行不变量、业务可重试可能误报；谓词锁升级会让误报率非线性上升；要求重试框架
RR / RC + FOR UPDATE悲观锁，冲突就排队冲突高、临界区短、业务不好重试锁等待、死锁风险、吞吐下降、要回表读最新版本
条件更新（乐观）判断与写入合并为一条语句冲突低、单行不变量不能直接保护跨行不变量（要靠约束）
唯一约束数据库原子性幂等与重复的最终防线只覆盖「重复」，不覆盖「顺序」

【取舍】判据：能不能重试 → 能就用 SSI/乐观；冲突频率高到重试成本超过加锁成本 → 才用悲观锁。 这条判据和 MySQL 那边（[[母题-M16-乐观锁与悲观锁]]）是同一句话，只是 PG 多了一层「SSI 帮你自动检测」。

6. 边界与常见误解

说法实际情况
「Serializable 会到处加锁变慢」官方明确：谓词锁不阻塞、也不可能造成死锁；代价是监控开销 + 中止率
「SSI 的误报说不清为什么」说得清：锁表内存不足 → 细粒度锁合并成粗粒度锁 → 丢精度；调 max_pred_locks_* 可以推迟升级
「全表扫和走索引对 Serializable 没差别」差别极大：顺序扫描【总是】需要一个关系级谓词锁，失败率因此上升
「失败发生在执行语句时」也可能发生在 COMMIT——所以 COMMIT 必须在重试范围内
「先查再插就能避免唯一冲突」只有在【所有】参与者都遵守同一协议时才成立；协议不统一反而会报出串行执行里不会发生的错
「重试次数越多越保险」重试本身增加并发——高冲突时是无上限的正反馈（见 Q1）

三 · 面试输出 闭卷口述 60 秒，再看结论

为什么 Serializable 会失败？应用层怎么处理才正确？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是「PG 的并发哲学」最集中的一课。MySQL 的思路是「加锁等一等，尽量别让你失败」；PG 的思路是「用快照保证正确，冲突了就直接告诉你，你自己重试」。把「失败」理解成缺陷而不是契约，就会做出错误的技术判断——比如「把隔离级别降回去」或「加锁硬扛」，这两条都比正确重试更糟。

一句话结论 全卡唯一要背的锚点

PG 的 Serializable 用的是 SSI（Serializable Snapshot Isolation）：它在快照隔离之上检测可能导致非可串行化结果的读写依赖环，一旦发现就主动让其中一个事务失败（SQLSTATE 40001）。所以失败是设计的一部分，不是异常——正确做法是在应用层捕获 40001、重试整个事务（带退避和上限），而不是重试单条语句。
  • SSI
  • 读写依赖与依赖环
  • 40001
  • 重试整个事务
  • 幂等
  • **谓词锁会升级（每页 2 行
  • 每表 32 页 → 整表锁）**
  • SIReadLock
  • 全表扫必然拿整表锁
  • SERIALIZABLE READ ONLY DEFERRABLE

卡住时靠这几个词重建整条链。

展开（先自答，再看 · 默认收起，不进复训调度）

MySQL 的 Serializable 靠加锁 + 间隙锁，表现为等待与超时；PG 靠 SSI 主动报错。而且 PG 的 40001 有两个来源：SSI 的依赖环、RR 下的写冲突（[[母题-P8-隔离级别与读一致性]]）——MySQL 没有对等的第二种。「同名级别、不同失败方式」说清楚，这道题就满分。

1. 写偏斜是什么，为什么 RC/RR 拦不住？

两个事务各读一部分数据、各写另一部分，各自的读集与写集不重叠，所以快照隔离看不出问题，但合起来破坏了一个跨行的不变量。只有 SSI 能自动拦住它，否则要靠显式锁或约束。

2. 能不能不用 SSI，只用 SELECT ... FOR UPDATE 保证正确？

能，但必须保证「读的时候也加锁」——只给写加锁的「先查再写」在 RC 下有竞态。RuleArena 走的是条件更新而不是「读也加锁」这条路（项目文档 04 §15：MVP 优先业务唯一键 + 条件更新）——理由是「锁不能成为资金正确性的唯一保证」，不是「用不了锁」。而一旦读也加锁，你就回到了"锁 + 等待 + 死锁"的老世界。

3. 重试会不会把压力放大成雪崩？

会，而且是正反馈（Q2 的算式：C=1000 时吞吐归零）。所以正确写法必须带退避 + 抖动 + 上限 + 全局并发限制。 能说出「重试也要限流」，就超出教科书答案了。

4. SERIALIZABLE READ ONLY DEFERRABLE 是什么意思？

只读事务声明可延迟启动，它会【阻塞】到一个"保证不会因序列化失败"的快照可用为止。 官方明确指出：这是唯一一种 Serializable 会阻塞、而 RR 不会的情况。 报表类长只读事务想彻底免重试，这是标准做法——而且它通常能在启动时就确定这个事实，从而根本不拿谓词锁。

5. 怎么判断该不该上 Serializable？

先问三件事：① 有没有跨行不变量（没有就不用上）；② 业务操作可不可重试（不可重试就别用 SSI，用锁）；③ 冲突频率有多高（很高时重试成本可能超过加锁）。三个问题问完，答案自己出来。

6. 线上 40001 突然变多，怎么排查？

三个方向：① 看 pg_locks 里 SIReadLock 的粒度（是不是升级成关系级了 → 调 max_pred_locks_*）；② 看有没有新出现的顺序扫描（→ 它一定拿整表锁，鼓励走索引）；③ 看有没有事务变长或连接数上涨（→ 正反馈的前兆）。这三个方向都是从机制推出来的，不是猜。
  • 「MySQL 的 Serializable 和 PG 的差多少？」—— MySQL 靠加锁 + 间隙锁实现，通常表现为【等待与超时】；PG 靠 SSI【主动报错】。「MySQL 上到 Serializable 会变慢」和「PG 上到 Serializable 会开始报错」是两种不同的现象，这是能直接体现你真用过 PG 的一处差异。
  • 「SSI 的误报能不能彻底消除？」—— 不能，只能压到可接受范围。因为升级规则本身就是「用内存换精度」，而内存永远有限。 能做的是：把热点查询压到 32 页以内、调大谓词锁参数、把只读事务声明成 READ ONLY。

- RuleArena 的沙箱重放（同一批动作重放要能拿到一样的结果——这正是「事务可重试」的业务前提）。 - EnergyOps 的月度结算（跨行不变量多、但通常可以按周期重算，天然后可重试）。 - 数驭穹图的权限/配置变更（跨行不变量（比如"每个租户只有一个默认配置"）正是 SSI 的主场——而且这类操作的冲突率天然很低）。

PG 怎么做到可串行化（SSI 检测依赖而不是加锁）→ 谓词锁为什么会升级（误报的机械原因）→ 所以会失败 → 失败的错误码与语义 → 正确的处理方式（重试整个事务）→ 与悲观锁的取舍 → 一个前提检查清单

Serializable 的成本不在执行速度，在「失败与重试」。 所以选择它的前提不是「我的 SQL 快不快」，而是「这个业务操作本身可不可以重试」——可重试，SSI 就是最省心的可串行化；不可重试，就该用显式锁。
