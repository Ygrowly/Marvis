题目

10 个线程处理 10000 个连接会怎样？为什么 Nginx / Redis / Node 用"少数线程"就能扛住上万连接？另一个问题：Kafka 号称靠"零拷贝"很快——它到底省掉了哪几次拷贝？数据一次都没被拷吗？

一 · 教材 从前提推到结论，不需要先会

1. 前提：一次 IO 其实分两段

1.1 两段成本【事实】

【推导】一次网络读取，钱花在两个地方：

第一步：等数据到达
  网卡收包 → DMA 写入内核的 socket 缓冲区
  ★ 这一段时间，应用线程在【等】——它插不上手

第二步：把数据搬给应用
  应用调用 read() → 内核把数据从【内核缓冲区】拷贝到【用户缓冲区】
  ★ 这一次拷贝是 CPU 干的，而且应用必须等它做完

【推导】这个"两段"的分法非常重要，因为几乎所有 IO 概念都在说"我改造了哪一段"：

概念它改造的是哪一段
阻塞 IO两段都等（最简单，一个连接一个线程）
非阻塞 IO第一段不等（但要反复问——把"等"变成了"轮询"）
IO 多路复用第一段不再"一个连接一个线程地等"，而是"一个线程等很多个"
异步 IO第二段也不等（内核拷完再通知你）

【推导】记住这张表，五道 IO 模型题就都变成了"你说的是哪一段"。

1.2 为什么"一个连接一个线程"不可行【推导】

【推导】先算一遍这个账（这也直接回答了本卡的第一个问题）：

10000 个连接，一个连接一个线程：
  内核侧：25KB × 10000 = 250 MB     （[[母题-O1-上下文切换与死锁]] 3.2）
  用户栈：8MB 虚拟 × 10000 = 80 GB 虚拟（按需提交，物理约 80 MB）
  更贵的：这 10000 个线程大部分时间在【等】，但它们是【内核调度的实体】
          → 内核要维护 10000 个等待上下文
          → 数据来了要唤醒对应的线程（每次唤醒两次切换）
          → 线程数和连接数绑死，扩不动

【推导】而"一个线程等 10000 个连接"怎么做得到：靠内核提供一个"一次问一批"的能力——这就是 IO 多路复用的全部内容。

到这里你应该能回答：为什么"IO 多路复用"要解决的问题是"连接数 vs 线程数"的解耦？

2. 五种 IO 模型：用同一把尺子排队

2.1 先用"两段"把五个模型排好【事实】

先各自介绍，再用同一指标比较（指标 = 两段里哪些要应用等）：

模型第一段（等就绪）第二段（拷贝）一句话
① 阻塞 IO等（线程睡着）等一个连接一个线程，简单但扩不动
② 非阻塞 IO不等，立即返回 EAGAIN等要自己反复轮询——"不等"变成了"一直问"，更浪费 CPU
③ IO 多路复用等，但一次等一批等select / poll / epoll——这是本节的主角
④ 信号驱动 IO不等（内核发 SIGIO 通知）等实际很少用（信号处理麻烦）
⑤ 异步 IO不等不等（内核拷完再通知）io_uring / POSIX AIO

【事实】必须讲清一个概念："同步 / 异步"的准确判据是第二段——

内核把数据从内核缓冲区拷贝到用户缓冲区这一步，是不是由内核在应用线程之外完成（完成后再通知应用）？

是 → 异步 IO；不是 → 同步 IO。

【推导】按这个判据，前四个（包括 IO 多路复用）都是"同步 IO"——因为 epoll_wait 通知你"连接可读了"之后，你调 read() 时仍然要阻塞在"拷贝"那一段上。

【纠错】所以"epoll 是异步 IO"这个说法是错的（很常见的混淆）。epoll 是"多路复用"——它让一个线程能同时等很多连接，但拷贝那段还是你自己等。

2.2 IO 多路复用要解决的三个问题【推导】

【推导】一个"一次问一批"的机制必须回答三件事，而三个版本的差别正好就是"它们怎么回答这三件事"：

问题含义
怎么表示"我在等哪些 fd"数据结构
谁来发现"哪些就绪了"内核轮询 vs 内核回调
怎么把结果告诉应用返回什么、要拷多少、应用要不要再筛一遍

到这里你应该能回答：为什么"非阻塞 IO"比"阻塞 IO"更费 CPU，它到底解决了什么？

3. select → poll → epoll：优势是算出来的

3.1 三个版本各自是什么【事实】

select（最老）

  • 怎么表示：fd_set —— 一个位图，每一位代表一个 fd
  • 限制：位图大小固定为 FD_SETSIZE，通常 1024 → 超过 1024 的 fd 根本表示不了
  • 谁发现就绪：内核遍历整个集合
  • 怎么返回：只返回"有几个就绪"，应用必须自己把整个集合再遍历一遍才知道是哪些
  • 成本：O(n)，n = 监控的 fd 总数

poll（改进版）

  • 怎么表示：pollfd 数组（每个元素带 fd + 关注的事件）
  • 限制：没有 1024 这种硬上限（受内存与 RLIMIT_NOFILE 限制）
  • 其余：仍然每次调用把整个数组拷进内核、内核仍遍历、返回后应用仍要遍历
  • 成本：仍然 O(n)

【推导】poll 只解决了"数量上限"这一个问题，没解决"每次都白遍历一遍"这个更贵的问题。

epoll（Linux 专用，2.6+）

【事实】按 man-page 原文，epoll 在内核里的核心是"两个列表"：

interest list（关注列表）—— 我注册了要监控哪些 fd
ready list（就绪列表）—— 其中【已经就绪】的那些
  • epoll_create：创建一个 epoll 实例
  • epoll_ctl：注册 / 修改 / 删除关注 —— 列表只在此时拷进内核，之后不再重复拷
  • epoll_wait：从就绪列表里取事件 —— man-page 原话是 *fetching items from the ready list*

【事实】这里有一个必须纠正的流行错说法：

❌ "epoll 用 mmap 共享内存，所以是零拷贝。"

错。 man-page 说得清楚：interest list 和 ready list 都是内核态的数据结构，epoll_wait 是把就绪事件拷到用户提供的数组里（maxevents 就限定了这次最多拷几个）。epoll 省的从来不是"拷贝"，而是两笔更贵的账：

epoll 省掉的怎么省的
每次调用都拷整个 fd 集合只在 epoll_ctl 时拷一次
每次调用都遍历全部 fd内核用回调把就绪的 fd 打进 ready list，epoll_wait 只取就绪的那些

【推导】所以准确说法是：*epoll 的工作量只和"就绪数"有关，和"监控总数"无关。*

3.2 量化：O(n) 和 O(k) 差多少【推导】

【推导】用同一个场景算一遍（自测 Q1 会完整算）：

场景：10000 个连接被监控，每秒有 1000 次"有事件发生"的时刻，每次平均 10 个连接就绪

用 poll：每次调用要处理全部 10000 个 fd
  1000 次/秒 × 10000 = 10,000,000 次检查/秒
  ★ 而这个数字会随连接数【线性增长】——连接翻倍，开销翻倍

用 epoll：每次调用只处理就绪的那些
  1000 次/秒 × 10 = 10,000 次/秒
  ★ 这个数字与【监控的连接总数无关】——连接从 10000 涨到 10 万，它不变

差 1000 倍，而且差距随连接数拉大——这就是"epoll 是 O(1)"这句话的正确含义：不是"开销为零"，是"开销与监控总数无关"。

【事实】select 在这里连参赛资格都没有：10000 个连接超过了 FD_SETSIZE（1024），用它根本表示不了。

3.3 水平触发与边缘触发【事实】

【事实】这是 epoll 的两种通知模式，理解的关键是"通知的时机"：

模式什么时候通知编程要求
水平触发（LT，默认）只要还有数据可读，就反复通知简单——没读完下次还会告诉你
边缘触发（ET）只在状态变化时通知一次必须配非阻塞 fd，并且一直读到 EAGAIN——否则剩下的数据永远不会再通知你

【推导】LT 更安全、ET 更省：

LT：可能被"反复通知同一个 fd"浪费一些系统调用，但【不会漏】
ET：通知次数最少，但【依赖你把数据读干净】——漏了就卡死

【事实】man-page 的推荐用法很明确：用 ET 就必须（1）设非阻塞 fd，（2）只在 read() 返回 EAGAIN 之后才回去等事件。另外 EPOLLONESHOT 可以让一个 fd 通知一次后自动失效，避免多线程下的重复唤醒（惊群）。

到这里你应该能回答：为什么说"epoll 是 O(1)"而不说"epoll 更快"？

4. 零拷贝：省掉的是哪几次拷贝

4.1 传统 read + write 的账【事实】

【事实】把一个大文件从磁盘发到网络，传统写法要拷 4 次：

① 磁盘 → 内核页缓存          （DMA 拷贝，硬件做）
② 内核页缓存 → 用户缓冲区    （★ CPU 拷贝）  ← read()
③ 用户缓冲区 → socket 缓冲区 （★ CPU 拷贝）  ← write()
④ socket 缓冲区 → 网卡        （DMA 拷贝，硬件做）

合计：4 次拷贝（2 次 DMA + 【2 次 CPU】）、2 次系统调用、4 次用户/内核态切换

【推导】看清楚浪费在哪里：数据从内核 → 用户 → 又回内核，而应用程序很可能一个字都没看（比如 Nginx 发静态文件、Kafka 把消息发给消费者）。这就像快递员把包裹从仓库搬到你的办公桌，你看都没看就说"发货"，他又搬回仓库——两次搬运完全是白干。

4.2 sendfile：从 4 次降到 2 次（甚至 0 次 CPU 拷贝）【事实】

【事实】sendfile(out_fd, in_fd, offset, count) 一个系统调用直接把文件发到 socket：

① 磁盘 → 内核页缓存            （DMA）
② 页缓存 → socket 缓冲区       （拷贝，但【全程在核内，不进用户态】）
③ socket 缓冲区 → 网卡          （DMA）

合计：2 次拷贝（0 次 CPU 参与、2 次 DMA）、1 次系统调用、2 次态切换
★ 数据从头到尾【没有进过用户态】

【事实】还有更强的版本：如果网卡支持 SG-DMA（Scatter-Gather DMA，即网卡能直接按描述符从内存里散读），那么第 ② 步可以退化成"只传递一个描述符（数据在哪、多长）"——

① 磁盘 → 内核页缓存                    （DMA）
② 把【描述符】交给网卡，网卡直接从页缓存读走（DMA 直接从页缓存取）
→ 【一次 DMA 拷贝 + 一次描述符传递】，真正意义上的"零 CPU 拷贝"

【事实】两个必须知道的限制（Linux 上）：

  • in_fd 必须是可 mmap 的普通文件 / 块设备（不能是 socket）
  • out_fd 必须是 socket（不能拿它来拷两个普通文件——那是 copy_file_range 的事）

4.3 mmap + write：另一种零拷贝（3 次拷贝）【事实】

【事实】mmap 走的是另一条路：

① 磁盘 → 内核页缓存                （DMA）
   mmap：把页缓存【映射】进用户地址空间 —— 应用直接"看到"页缓存，
         【省掉了"内核→用户"的那次拷贝】
② 用户写入 socket 缓冲区时，还是要拷一次 （★ CPU 拷贝）
   → 所以总共 3 次拷贝

【推导】比 sendfile 多一次 CPU 拷贝，那它为什么存在：

sendfilemmap + write
拷贝次数2（理想情况 1）3
应用能不能处理数据❌ 不能（数据不进用户态）✅ 能（应用看得到页缓存）
典型用户KafkaRocketMQ

【推导】所以"谁更零拷贝"的答案是：*sendfile 省得更多，但代价是应用碰不到数据；mmap 多一次拷贝，换来的是应用能在发送前处理数据。* Kafka 不需要改消息内容 → 用 sendfile；RocketMQ 需要处理（比如按 ConsumeQueue 组织）→ 用 mmap。 这是同一个目标下的两种权衡，不是"谁更先进"。

4.4 量化的收益【推导】

【推导】零拷贝的收益随"并发连接数"放大（自测 Q2 会算）：

发 1GB 文件：
  传统方式：2 次 CPU 拷贝 = 2GB 内存流量
  sendfile：0 次 CPU 拷贝
→ 单连接就省 2GB 的内存带宽

如果是 1000 个并发连接同时发：
  省下的 CPU 拷贝流量 = 2GB × 1000 = 2 TB
→ 按 20 GB/s 内存带宽算，相当于省掉约 100 秒的纯内存搬运

【推导】这就是为什么"零拷贝"是高吞吐服务的标配：省的不是"拷贝"这个动作，是"每个连接的拷贝 × 连接数"这个乘积。

4.5 更上一层：减少系统调用的次数【推导】

【推导】顺着"省拷贝"再往前一步：系统调用本身也不便宜（约 105 ns 一次，[[母题-O1-上下文切换与死锁]] 4.4）。所以真正现代的优化方向是"批量化"：

100 万次 IO 操作/秒，每次都一次系统调用：
  1,000,000 × 105 ns ≈ 0.105 秒/秒 ≈ 【0.105 个核】光花在"跨越边界"上

用 io_uring（提交队列 + 完成队列）批量化，深度 128：
  1,000,000 / 128 ≈ 7,812 次提交/秒
  → ≈ 0.0008 个核  ← 省掉约 99%

【推导】注意这里"省"的性质：工作本身一点没变便宜，只是"跨越"的次数少了 128 倍。 这和 [[母题-O1-上下文切换与死锁]] 的结论是同一条：优化方向是"让系统调用更少"，而不是"让系统调用更快"。

到这里你应该能回答：为什么"零拷贝"的同时还要关心"系统调用次数"？

5. 边界与常见误解

常见说法修正
"epoll 是异步 IO"【推导】不是。epoll_wait 通知你"可读了"之后，你调 read() 时仍要阻塞在"内核→用户"的拷贝上。按 POSIX 的判据，它属于同步 IO；"异步"要看拷贝那一段是否由内核在应用线程之外完成
"epoll 用 mmap 共享内存实现零拷贝"【事实】错（man-page 可查）。interest list 和 ready list 都在内核态，epoll_wait 要把就绪事件拷回用户数组。它省的是"每次拷整个 fd 集合"和"每次遍历全部 fd"，不是拷贝本身
"epoll 比 select 快"【推导】要说得更准：epoll 的每次调用工作量只与就绪数有关（O(k)），与监控总数无关；select/poll 是 O(n)。连接少的时候两者差不多，优势在连接多的时候才显现
"select 能监控 1024 个 fd，poll 无限"【事实】select 的上限是 FD_SETSIZE，通常 1024；poll 没有这个硬上限，但受内存与 RLIMIT_NOFILE 限制，而且仍然是 O(n)
"ET 比 LT 高级，应该都用 ET"【取舍】ET 要求非阻塞 + 一直读到 EAGAIN，漏读就会永久卡住。LT 更安全、ET 更省——没有"哪个更好"，只有"你能不能保证把数据读干净"
"零拷贝就是一次拷贝都没有"【事实】"零"指的是"零 CPU 拷贝"。DMA 拷贝还在（那是硬件做的，不占 CPU）——所以准确说法是"数据不再经过用户态、CPU 不参与搬运"
"sendfile 什么场景都能用"【事实】Linux 上限制很明确：in_fd 必须是可 mmap 的普通文件，out_fd 必须是 socket。不能用它拷两个普通文件
"mmap 一定比 sendfile 好/差"【取舍】用途不同：sendfile 省得更多但应用碰不到数据；mmap 多一次拷贝但应用能处理数据。Kafka 选前者、RocketMQ 选后者，各自贴合需求
"多路复用可以让单线程跑满多核"【事实】不能。多路复用只是让一个线程能等很多连接，它仍然跑在一个核上。要多核得靠多进程 / 多线程（[[母题-N3-进程线程与协程]]：Nginx 是多 worker 单线程，Redis 主线程单线程）
"一个连接一个线程就够用了"【推导】连接数一大就崩：10000 连接 → 内核侧 250MB、10000 个被调度的实体、唤醒时的切换开销。这是"连接数和线程数必须解耦"的量化理由

  • 推导链：IO 两段 → 连接数与线程数解耦 → select/poll 的 O(n) 与 epoll 的就绪列表 → 零拷贝 → 上层 asyncio 的解释。

  • 边界与常见误解：多路复用不减少数据拷贝（那是零拷贝的活）；epoll 的代价是注册与回调模型更复杂。

1. epoll 为什么比 select 快？

不是"常数时间"，是"复杂度与监控总数无关"：select/poll 每次调用都要把整个集拷进内核 + 遍历全部 fd（O(n)）；epoll 注册只拷一次，内核用回调把就绪 fd 放进 ready list，epoll_wait 只取就绪的（O(就绪数)）。连接多、活跃少时优势最大。

2. epoll 是异步 IO 吗？

不是。通知"可读"之后，read() 的拷贝那一段仍要应用等，按 POSIX 判据属于同步 IO。真正异步的是 io_uring / POSIX AIO（等和拷都由内核做完再通知）。

3. 水平触发和边缘触发怎么选？

LT 更安全（没读完下次还会通知）；ET 通知更少但要求非阻塞 + 一直读到 EAGAIN，漏读会永久卡住。用 ET 时 man-page 明确要求"只在 read() 返回 EAGAIN 之后才回去等事件"。

4. 零拷贝到底省了什么？

省的是 CPU 拷贝次数：传统 4 次拷贝里有 2 次是 CPU 干的（内核→用户、用户→socket），sendfile 把这两次全省掉（数据不进用户态）；mmap 只省一次（留在页缓存里，应用可直接访问，但写 socket 时还要拷）。DMA 那两次仍然存在，只是不占 CPU。

5. Kafka 为什么比 RocketMQ 更"零拷贝"？

Kafka 用 sendfile（2 次拷贝，数据不进用户态）；RocketMQ 用 mmap + write（3 次，多一次拷贝换来应用能处理数据）。这不是谁更先进，是各自的取舍：Kafka 只转发不需要改内容，RocketMQ 需要按自己的存储结构组织。

6. 多路复用能让单线程跑满多核吗？

不能。它只把"连接数与线程数"解耦，执行仍然在一个核上。要多核靠多进程 / 多线程——Nginx 是多 worker 单线程、Redis 是主线程单线程，都不是"整个服务一个线程"。
  • 「事件循环里为什么不能有阻塞调用？」——阻塞调用没有 await 点，会让整个事件循环停摆（所有连接一起等）。这条在 [[母题-N3-进程线程与协程]] 已经从"选型"角度讲过，本节补的是"它在操作系统层面对应什么"：那个线程被挂在内核等待队列里，其它几千个连接的事件没人取（epoll_wait 也没人调）
  • 「io_uring 相比 epoll 多了什么？」——epoll 告诉你"可以读了"，读完还要你自己发起 read；io_uring 是提交队列 + 完成队列：你提交"读这个 fd 到这个缓冲"，内核做完（含拷贝）再报告完成——是真正的异步 IO，而且把"系统调用次数"从"每操作一次"降到"每批一次"（本卡 4.5 算过：深度 128 → 省 99%）
  • 「Nginx 作为反向代理为什么要零拷贝？」——它只转发不修改（静态文件尤其典型），完美匹配 sendfile 的适用条件；一旦要压缩 / 改写内容，就得回到"数据进用户态"的路径
  • 「阻塞 IO 还能用吗？」——能，只要并发量可控。简单性本身就是收益：阻塞模型代码直白、不用管事件循环和"不能阻塞"的约束。"用不用多路复用"是并发量与复杂度的取舍，不是先进与落后的区别

EnergyOps——长任务的 SSE 进度推送意味着大量长连接同时挂着（[[母题-N2-SSE与推送模型]]）：这些连接绝大部分时间没有数据，正是"连接多、活跃少"的典型场景，也是多路复用的最大收益区。"网关关缓冲 + 发心跳"这两个坑，本质是在让"活跃"这件事能被内核正确感知。

IO 的每一层优化都在回答同一个问题："哪一段等待或搬运是可以省掉的？" 多路复用省掉"一个连接一个线程的等待"（连接数与线程数解耦）；epoll 省掉"每次遍历全部 fd"（O(n) → O(就绪数)）；零拷贝省掉"数据进用户态又出来"（2 次 CPU 拷贝 → 0）；批量化省掉"每个操作一次边界跨越"。四件事的方向完全一致：把"与规模成正比的固定开销"变成"与活跃度成正比"。
