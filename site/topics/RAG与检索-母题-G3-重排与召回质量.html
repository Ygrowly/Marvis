题目

面试官问——"你们召回之后还做了什么？为什么要加重排？加了多少分、代价是什么？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：召回和精排的优化目标本来就不一样

① 召回阶段：面对的是【全量】
   目标是「不漏」——宁可多捞，不能把正确答案漏在外面
   所以它只能用【便宜】的方法（否则全量算不动）

② 精排阶段：面对的是【已经缩小过的候选集】
   目标是「排得准」——把最该进上下文的那几条顶上来
   所以它可以用【贵】的方法（候选少，算得起）

【推论】两个阶段的约束不同，所以"用同一个模型做一件事"必然有一头不划算：用贵的方法做召回 → 全量算不动；用便宜的方法做精排 → 排不准。两级漏斗不是工程习惯，是被约束逼出来的。

到这里你应该能回答：为什么"直接用最准的模型排全量"这条路走不通？

2. 双塔 vs 交叉编码器：本质差别是"能不能预计算"【推导】

双塔（Bi-Encoder）交叉编码器（Cross-Encoder）
怎么算query 和 doc 分别编码成向量，再算 cos(Q, D)[query + doc] 拼在一起送进模型，出一个分数
交互没有词级交互（两者编码时没见过对方）有——能看到每个词和每个词的关系
能不能预计算能——文档向量离线算好，查询时只算 query不能——每个 (query, doc) 对都要现算
用途召回精排

【推导】为什么双塔"不够准"：

query:  "7 天无理由退款适用哪些情况"
doc_A:  "购买后 7 天内可无理由退款，拆封数码产品除外"
doc_B:  "7 天无理由退货政策说明"

双塔：两句都单独编码成向量
      doc_A 的向量是整句的「平均语义」
      → "除外" 这个关键的否定词，在向量里几乎被稀释掉
      → doc_A 和 doc_B 的相似度可能很接近

交叉编码器：把 query 和 doc_A 拼起来送进模型
      → 模型能直接看到「除外」这两个字
      → 给出显著更低的分数

【推论】双塔的信息损失来自"编码时看不到对方"——这是一个结构性的损失，不是模型不够大。所以它必须靠交叉编码器补回来，而不是靠换一个更好的双塔。

【取舍】交叉编码器不能用于召回，不是因为慢，是因为"不能预计算"：文档向量无法离线算好，每次查询都要对全量重算一遍——这才是它只能用在"已经缩小过的候选集"上的根本原因。

到这里你应该能回答：为什么"换一个更强的 Embedding 模型"不能替代重排？

3. 重排的代价：延迟随候选数线性增长【推导】

交叉编码器对每个候选都要现算一次

假设单个候选推理约 5ms：
  重排  20 条 → 100ms
  重排 100 条 → 500ms
  重排 200 条 → 1000ms

对比：ANN 召回本身约 10ms

【结论】重排会主导整条链路的延迟——它是"数量级更大"的那一项。

【取舍】所以"重排多少条"是一个必须算的成本决策：

候选数越大 → 召回率越高（更多正确答案被保留）
          → 但重排延迟线性上升
          → 而且最终进上下文的条数受 token 预算限制（[[母题-C1-上下文组装与窗口预算]]）

→ 常见的折中是「召回几百条、重排前 50–100、最终进上下文 5–20 条」

【事实】分档启用也是常见做法：重排提高质量但增加延迟与成本，应通过 Eval 判断是否只在难题启用（study/03 的结论）——简单查询（精确编号、单跳事实）不需要重排，难题才需要。

4. 重排的收益：两个口径别混【推导】

【事实】Anthropic 在 Contextual Retrieval 里给的实测（检索失败率，top-20 口径）：

基线                    5.7%
+ Contextual Embeddings 3.7%   （相对基线 −35%）
+ Contextual BM25       2.9%   （相对基线 −49%）
+ Rerank                1.88%  （相对基线 −67%）

【推导】"重排降了 67%"这句话是错的——67% 是相对基线的累计降幅。单看重排这一步：

重排前 2.9% → 重排后 1.88%
相对重排前：1 − 1.88/2.9 = 35%
绝对降幅：2.9% − 1.88% = 1.02 个百分点

【结论】三个口径要分清：绝对降幅（1.02 个百分点）、相对前一环（35%）、相对基线（累计 67%）。

【推论】汇报时要说清用的是哪个口径——把"累计降幅"说成"这一步的降幅"会显著高估单点手段的价值，追问一句就露馅。

【事实】另一个可用的对照：study/03 记的数驭穹图口径是召回 81% → 95%。

【纠正常见误解】但不要把它和上面的 5.7%→1.9% 当成"同一枚硬币的两面"——它们的对象和分母都不一样：

Anthropic 的 5.7% → 1.9%  ：top-20 【chunk】检索失败率（文档块这一层）
数驭穹图的 81% → 95%      ：Top-K 【Schema】召回率（表/语义资产这一层）

"95% 召回 ≈ 5% 失败"这个换算是错的：前者说的是"该找的表有没有被捞进候选"，后者说的是"该找的文档块有没有被捞到"。层不同、分母不同，量级相近纯属巧合，不能互相换算，更不能说"互补"。 一句话记：说数驭穹图那个数时，必须带上「Schema」两个字——只说"召回率"，会被理解成文档块召回，追问一句就露馅。

到这里你应该能回答：为什么"我们加了重排，失败率降了 67%"这句话经不起追问？

5. 召回质量看哪些指标【事实】

指标回答什么问题什么时候看
Recall@K正确证据是否出现在前 K 个候选里召回阶段——它决定"上限"
Precision@K前 K 个里有多少是相关证据上下文预算紧张时
MRR第一个正确证据出现得有多早只需要一条正确证据的场景
nDCG@K多级相关性 + 排序质量精排阶段——它决定"答案能不能用上"

【推导】为什么 Recall@K 高不等于答案好：

Recall@5 = 100%（正确证据都在前 5 里）
但它排在第 5，而前 4 条是相关度较低的内容

→ 上下文预算有限时，真正需要的那条可能被挤掉或被淹没
→ 这正是 [[母题-C1-上下文组装与窗口预算]] 说的「context rot」

【推论】召回率回答"有没有捞到"，nDCG 回答"排得对不对"，两者都要看。 只看召回率会漏掉"捞到了但排太后"这一类失败——而归因时必须能分开（[[母题-G5-RAG评测与幻觉率]]）。

【事实】K 怎么定：Anthropic 试过交付 5 / 10 / 20 个 chunk，结论是 20 表现最好。但 K 增大会带来两个代价：重排成本线性上升、上下文预算被占。所以 K 是"召回率 vs 成本"的取舍，必须用评测定，不能照搬。

6. 边界与常见误解

常见说法修正
"重排就是把分数重新算一遍"不是。差别在模型结构：召回用的是双塔（query 和 doc 分别编码，无词级交互），重排用的是交叉编码器（拼在一起，有词级交互）。双塔的损失是结构性的，换更大的双塔也补不回来
"换个更强的 Embedding 模型就不用重排了"换不掉。交叉编码器比双塔准，不是因为模型更大，是因为它能看到 query 和 doc 之间每个词的交互——这是结构优势，不是规模优势
"我们加了重排，失败率降了 67%"口径错了。67% 是相对基线的累计降幅（5.7% → 1.88%）；单看重排这一步是 35%（2.9% → 1.88%）。把累计说成单点会显著高估它的价值
"召回率 95% 说明检索没问题了"召回率只管"有没有捞到"，不管"排得对不对"。正确证据排在第 20 位、被上下文预算挤掉，召回率照样是 100%。要看 nDCG@K
"重排越多条越好"延迟随候选数线性增长（5ms × N）。重排 200 条就是 1 秒——比 ANN 召回慢两个数量级。常见折中是"召回几百、重排 50–100、进上下文 5–20"
"所有查询都要走重排"不必。重排是用延迟换质量，应该通过 Eval 判断是否只在难题启用——精确编号、单跳事实这类查询收益很小
"重排能解决多跳问题"不能。重排只是把已有候选重排；多跳需要的候选压根不在池子里。多跳要靠 Query Decomposition / Multi-hop 检索（第二轮由第一轮发现的实体驱动）

【取舍】读成一句话：重排的价值来自"双塔看不到词级交互"这个结构性缺陷，所以它不能被更强的双塔替代、也不能被"多召回几条"替代——它排的是"同样的候选里谁更该进上下文"。

三 · 面试输出 闭卷口述 60 秒，再看结论

召回来的候选已经按相似度排过序了，为什么还要再排一遍——这一遍排的到底是什么？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是区分"搭过 RAG"和"调过 RAG"的题。搭过的人会说"我们加了 rerank，效果好"；调过的人会说清它为什么好（双塔没有词级交互）、好多少（相对基线的 67%）、代价是什么（延迟随候选数线性增长）。而且它的答案模板可以直接迁移到 Agent 的工具选择（[[母题-A2-工具调用与MCP边界]]）。

一句话结论 全卡唯一要背的锚点

召回和精排的优化目标不同——召回面对全量，目标是"不漏"，所以只能用便宜的方法（双塔，文档向量可预计算）；精排面对已经缩小过的候选集，目标是"排得准"，所以可以用贵的方法（交叉编码器）。两者的本质差别是"有没有词级交互"：双塔把 query 和 doc 分别编码，编码时看不到对方，所以"除外""不适用"这类否定词被平均掉（这是结构性损失，换更大的双塔也补不回来）；交叉编码器把两者拼在一起，能看到逐词交互。代价是延迟随候选数线性增长（5ms × N，重排 200 条就是 1 秒，比 ANN 召回慢两个数量级），所以常见折中是"召回几百 → 重排 50–100 → 进上下文 5–20"。收益要说清口径：Contextual Retrieval 里重排把失败率从 2.9% 降到 1.88%，相对重排前降 35%、相对基线累计降 67%——这两个数不能混。最后，Recall@K 高不等于答案好，还要看 nDCG@K。
  • 召回要"不漏"、精排要"排得准"
  • 双塔 = 分别编码 + 可预计算 + 无词级交互
  • 交叉编码器 = 拼在一起 + 不能预计算 + 有词级交互
  • 双塔的损失是结构性的，换大模型补不回来
  • 重排延迟 = 5ms × N（200 条 = 1 秒）
  • 常见折中：召回几百 → 重排 50–100 → 进上下文 5–20
  • 重排收益口径：绝对 1.02 个点 · 相对前一环 35% · 相对基线累计 67%
  • Recall@K 看"有没有捞到"，nDCG@K 看"排得对不对"

展开（先自答，再看 · 默认收起，不进复训调度）

1. 重排一定值得吗？

不一定。它是用延迟换质量，应该通过 Eval 判断是否只在难题启用。精确编号、单跳事实这类查询，召回本身已经排得很准，重排收益很小。study/03 的结论就是"应通过 Eval 判断是否只在难题启用"。

2. K 该取多少？

Anthropic 试了 5 / 10 / 20，20 最好；但 K 大会带来重排成本线性上升 + 上下文预算被占。所以 K 要按"召回率 vs 成本"用评测定，并且要和重排的候选数、最终进上下文的条数一起考虑。

3. 多跳（multi-hop）问题重排能解决吗？

不能。重排只是把已有候选重排；多跳需要的候选压根不在池子里。要解决它得靠 Query Decomposition（多条件问题拆成子查询）或 Multi-hop 检索（第二轮由第一轮发现的实体驱动）。

4. 多路召回和重排是什么关系？

前者解决"捞得全"，后者解决"排得准"。RRF 融合只是把两路的排名合成一个顺序（[[母题-G2-向量与关键词的混合检索]]），它不判断内容相关性的深浅——那正是交叉编码器要做的事。两级是串联的，不是二选一。
  • 「为什么 rerank 模型的参数量通常比 Embedding 模型小，效果却更好？」——因为任务不同：双塔要做的是"把任意文本编码成一个通用向量"（难的通用任务），交叉编码器做的是"判断这一对 query-doc 相关到什么程度"（窄得多，且有交互信息可用）。参数量小但信息更充分。
  • 「重排和"用 LLM 打分"有什么区别？」——本质相同（都是交叉编码器式的判断），区别在成本与稳定性：通用 LLM 打分更贵、更慢，但不需要额外训练；专用重排模型（如 bge-reranker 这类）更快、更便宜。选型取决于你的 QPS 与延迟预算。

- 数驭穹图：召回 81% → 95% 这条数据要说清是 Top-K Schema 召回率口径（表这一层，不是文档块），且要能回答"重排在里面贡献了多少"——这正是本卡"三个口径"那一节的直接应用。 - EnergyOps：故障建议的检索里，设备编号与错误码属于"召回已经排得很准"的类型，重排收益小；而自然语言描述的故障现象需要重排。按查询类型分档启用是这个项目的直接落点。

两个阶段目标不同 → 双塔 vs 交叉编码器（本质差别是词级交互）→ 为什么双塔的损失补不回来 → 重排的延迟账 → 收益的三个口径 → K 怎么定 → Recall@K 与 nDCG@K 的分工 → 收束到"两级漏斗是约束逼出来的"

"能不能预计算"决定了"用在哪一阶段"。 双塔能预计算 → 用在召回（面对全量）；交叉编码器不能 → 用在精排（面对小候选集）。这不是模型优劣，是约束匹配。
