题目

说一下乐观锁与悲观锁的区别。

9.9 一面原题，当次 11 分——口误"悲观所"、没提版本号 / CAS、没讲适用边界。

一 · 教材 从前提推到结论，不需要先会

1. 前提：它们是对冲突概率的两种假设

【事实】

  • 悲观锁假定冲突一定发生 → 所以在访问前先加锁，拿到锁才能改，其他事务阻塞等待
  • 乐观锁假定冲突很少 → 所以不加锁直接改，提交时校验有没有被别人改过

【推论】"哪个更好"这个问题本身就是错的——没有冲突概率，选型就是空谈。

【推论】所以回答的第一句话永远是"冲突频率"，第二句才是机制。 这正是 9.9 那次缺的东西。

2. 悲观锁：先拿锁，再操作【事实】

SELECT status FROM task WHERE id = 1 FOR UPDATE;   -- 加 X 锁
UPDATE task SET status = 'RUNNING' WHERE id = 1;
COMMIT;

实现：数据库 SELECT ... FOR UPDATE（排他锁）；Java 里 synchronized / ReentrantLock；分布式场景是 Redis / ZK 锁（但分布式锁不能替代数据库约束，见 [[母题-P19-唯一约束与UPSERT]]）。

适用：写多、冲突频繁、临界区长（拿到锁之后要做一堆事）。

代价：① 等待与吞吐下降；② 死锁风险（加锁顺序不一致时，[[母题-M10-锁与死锁]]）；③ 连接占用时间长。

【事实】实现上的一个坑：SELECT ... FOR UPDATE 在 RR 下会带出 next-key lock，锁范围可能比预期大（[[母题-M10-锁与死锁]]）——这正是"悲观锁代价"的具体体现。

3. 乐观锁：不加锁，提交时校验【事实】

两种实现：

① version 字段（数据库场景的标准做法）

UPDATE task
SET status = 'RUNNING', version = version + 1
WHERE id = 1 AND version = :expected_version;   -- 期望值进 WHERE
-- 影响行数 = 0 → 别人改过 → 读出最新值再决定

② CAS（Compare-And-Swap，CPU / Java 层面）

期望值 E、新值 V：内存位置当前值 == E 才写入 V
Java 里即 Atomic* 类（底层是一条 CAS 指令）

适用：读多写少、冲突少、单行。

代价：冲突多时反复重试，成本反而更高；只能保护单行 / 单个变量——跨行不变量靠它撑不住（要靠约束或事务，[[母题-P18-乐观并发控制]]）。

【事实】核心是"期望值进 WHERE"：用 version、用状态、用时间戳都行，本质是 CAS 思想。version 字段的好处是自带 ABA 防护（下一节）。

4. ABA 问题：CAS 的固有缺陷【推导】

【事实】CAS 只比较"值是否相等"，不比较"中间有没有变过"：

线程 1 读到值 100（准备改成 200）
线程 2 把 100 改成 80，又改回 100
线程 1 CAS(100 → 200) 成功          ← 但它不知道中间发生过 80

【推导】什么时候有害、什么时候无害：

场景有害吗为什么
数值累加/设置通常无害"1 加 5 次" 和 "1 加 1 次" 结果一样——CAS 只关心最终值
引用 / 状态 / 指针有害栈顶指针被弹出又压回同一个地址，但链表结构已经被破坏，CAS 却认为"没变过"

【事实】解法：版本号 / 时间戳一起比——Java 里 AtomicStampedReference（带 stamp）；数据库里 version 字段本质就是"自带 ABA 防护的 CAS"。

【推论】这一条能把"version 为什么比直接比较值更稳"讲成因果，而不是一句"要加 version"的口诀。 面试里能这样讲，就超过只背结论的人。

到这里你应该能回答：为什么"用状态字段当期望值"在某些场景下不如 version？

5. 判据：两条成本曲线的交点（本题的落点）

冲突频率高到「重试成本 > 加锁成本」时，用悲观锁；否则用乐观。

【推导】为什么要画曲线而不是背结论——因为两种方案的成本函数形状完全不同：

悲观锁成本 ≈ 加锁开销 + 冲突时的【排队等待】
            → 随冲突率【线性】上升（等待是排队，工作不会白做）

乐观锁成本 ≈ 单次成本 ÷ (1 − p)
            → 随冲突率【发散】（每次冲突都要把整段工作重做）

5.1 把"发散"算出来【推导】

乐观锁的期望尝试次数：

期望尝试次数 = 1 + p + p² + … = 1 / (1 − p)      （p = 单次尝试遇到冲突的概率）

p = 0.05 →  1.05 次
p = 0.30 →  1.43 次
p = 0.70 →  3.33 次
p = 0.90 → 10    次
p → 1    → 发散

【推论】这就是"高冲突时乐观锁崩掉"的数学表达——它不是"慢一点"，是在 p→1 时成本发散。

5.2 高冲突下的量级差【推导】

N 个请求同时抢同一行（此时单次冲突概率 p ≈ (N−1)/N）
  乐观锁期望尝试次数 = 1/(1−p) ≈ N
  总工作量 = N 个请求 × N 次尝试 = N² 次

悲观锁：串行执行，每个请求做一次
  总工作量 = N 次

量级比 = N

【结论】高冲突时乐观锁的总工作量是 N²，悲观锁是 N——差一个 N 倍。 10 个并发就差 10 倍，100 个并发差 100 倍。

【推论】这就是"重试成本 > 加锁成本"这句话的量化版本——面试里能给出 N² vs N 这个对比，比说"高冲突别用乐观锁"有说服力得多。

到这里你应该能回答：为什么"乐观锁不加锁所以更快"是一句危险的话？

6. 选了乐观锁，就必须把重试当成方案的一部分【推导】

某热点行 1000 QPS，乐观锁冲突率 90%
  期望尝试次数 = 1/(1−0.9) = 10 次
  总更新尝试 = 1000 × 10 = 10,000 次/秒

加退避 + 抖动，把有效冲突率降到 30%：
  期望尝试次数 = 1/(1−0.3) ≈ 1.43 次
  总更新尝试 = 1000 × 1.43 = 1,430 次/秒

降到约 1/7

【事实】"影响行数 0"是正常业务分支，不是异常：正确的处理是读权威状态 → 判定 → 决定，而不是无脑重试。不要写 while(true) retry——要有退避、抖动和上限（[[母题-P9-序列化失败与重试]] 的四条要求）。

7. 结合自己的项目（这条是你的差异化）

【事实】RuleArena 的退款与任务认领用的是乐观锁（条件更新），理由（[[母题-P18-乐观并发控制]] 已展开）：

  • 扣退款是低频写、读多写少 → 冲突少（落在曲线交点的左边）
  • 条件更新一次原子写，天然幂等（重复执行第二次影响 0 行）
  • 跨行不变量写进 WHERE（refunded + amount <= paid）
  • 唯一约束兜底（UNIQUE(run_id, action_type, idempotency_key)）

【取舍】然后反向讲一句（这是"懂边界"的证据）：

"如果同一个任务被大量 Worker 高频争抢，重试成本就会超过加锁成本，那时我会换成悲观锁，或者把任务分区错开。"

主动说出自己方案不适用的情况，比硬吹乐观锁可信得多。

8. 边界与常见误解

常见说法修正
"乐观锁不加锁，性能一定更好"低冲突时对，高冲突时反了。乐观锁成本 ≈ 单次成本 ÷ (1−p)，在 p→1 时发散；高冲突下总工作量是 N²，悲观锁是 N——差一个 N 倍
"乐观锁就是加个 version 字段"核心是"期望值进 WHERE"——version、状态、时间戳都行，本质是 CAS 思想。version 的好处是自带 ABA 防护
"CAS 比较值相等就安全"漏了 ABA：值相等 ≠ 中间没变过。数值场景通常无害，引用 / 状态 / 指针场景有害（栈顶指针弹出又压回同一地址）
"影响行数 0 说明出异常了"是正常业务分支。它可能是"别人抢先了"，也可能是"条件本来就不满足"——分不出来，也不需要分；正确做法是读权威状态再判定
"重试失败就一直重试到成功"三处错：没有上限（可能无限循环）、没有退避（会形成重试风暴）、没意识到有些失败重试一万次也不会成功（条件本身不满足）。要有退避 + 抖动 + 上限
"分布式锁就是悲观锁，能保证正确性"它是应用层的锁，不能替代数据库约束做正确性兜底（[[母题-P19-唯一约束与UPSERT]]）。锁会失效（过期、网络分区），约束不会

【取舍】读成一句话：两者不是"谁更好"，而是对冲突概率的两种假设——所以没有冲突频率，就没有选型。

一句话结论 全卡唯一要背的锚点

两者不是"谁更好"，而是对冲突概率的两种假设——悲观锁假定冲突一定发生，所以先加锁（SELECT ... FOR UPDATE / synchronized）；乐观锁假定冲突很少，不加锁、提交时校验（version 字段或 CAS，UPDATE ... WHERE version=?，影响行数 0 即冲突）。判据只有一个：冲突频率——冲突高到"重试成本 > 加锁成本"时用悲观。这不是口号：乐观锁成本是 单次成本 ÷ (1−p)，在 p→1 时发散；高冲突下 N 个请求抢同一行，乐观锁总工作量 N²、悲观锁 N，差一个 N 倍。乐观锁要注意 ABA 问题（值相等 ≠ 中间没变过），version 字段本质就是"自带 ABA 防护的 CAS"。RuleArena 的退款与任务认领用的是乐观锁（条件更新），因为它是低频写、且条件更新天然幂等；但如果同一个任务被大量 Worker 高频争抢，我会换成悲观锁或把任务分区错开。
  • 假设不同（冲突一定发生 vs 冲突很少）
  • 悲观 = FOR UPDATE（注意 next-key）、有死锁风险
  • 乐观 = version 或 CAS、期望值进 WHERE
  • 影响行数 0 = 正常业务分支
  • ABA（值相等 ≠ 没变过；引用场景有害）
  • AtomicStampedReference、version 自带 ABA 防护
  • 判据 = 冲突频率
  • 乐观成本 = 1
  • (1−p) 会发散
  • 高冲突 N² vs N
  • 重试要有退避 + 抖动 + 上限
  • 分布式锁不能替代约束

1. version 冲突之后怎么处理？

读出权威状态，再决定重试还是放弃——"影响行数 0"是正常业务分支，不是异常。不要写 while(true) retry：要有退避、抖动和上限。

2. 9.9 那次你的答案缺了什么？

三条：① 没提 version / CAS（实现层面）；② 没讲适用边界（判据层面）；③ 口误（表达层面）。通过标准：40 秒内给出「假设不同 → 两种实现 → ABA → 判据 → 自己项目实例」五段结构，并主动补一句"什么情况我会换悲观锁"。

3. 乐观锁在数据库里就是加 version 字段吗？

核心是"期望值进 WHERE"：用 version、用状态、用时间戳都行；本质是 CAS 思想。version 字段的好处是自带 ABA 防护。

4. 分布式锁算悲观锁吗？

算（假设冲突、先拿锁），但它是应用层的锁，不能替代数据库约束做正确性兜底（[[母题-P19-唯一约束与UPSERT]]）。锁会失效（过期、网络分区），约束不会。
  • 「MySQL 和 PG 在乐观锁上有什么不同？」——乐观锁在两边的写法几乎一样（条件更新），判据也一致——这是少数两边完全互通的机制。但"冲突时数据库怎么响应"不同：MySQL 乐观返回 0 行；PG 乐观返回 0 行，而 Serializable 隔离级别下是直接报 40001 让你重试（[[母题-P8-隔离级别与读一致性]]、[[母题-P9-序列化失败与重试]]）。判据通用，实现细节按库区分。
  • 「什么场景下乐观锁一定不能用在数据库里？」——跨行不变量。乐观锁只能保护单行 / 单个变量；像"账户余额总和不能为负"这种跨行约束，要么写进 WHERE（条件更新），要么靠唯一约束 / 外键兜底（[[母题-P18-乐观并发控制]]）。

- RuleArena 的任务认领与退款（乐观锁，真实 SQL）——这是主战场案例，要练成 60 秒。 - EnergyOps 的告警处置与设备状态（状态机 + 条件更新）。

两者不是"谁更好"，而是对冲突概率的两种假设。
