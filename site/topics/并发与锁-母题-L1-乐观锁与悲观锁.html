题目

面试官问"乐观锁和悲观锁有什么区别、你项目里用哪个"。你答完区别之后他追问："那什么情况下该换？给我一个判据。"——请用数字回答，并说清"防超卖"该怎么做。

一 · 教材 从前提推到结论，不需要先会

1. 前提：并发控制的目标不是"不出错"，是"给出错定价"

1.1 两种方案，两种定价方式【事实】

先各自介绍，再用同一指标衡量（指标 = 同一个数据被并发修改时，谁的浪费更少）：

悲观锁（pessimistic）：先排队，再动手。动手之前先拿到独占权（数据库的 SELECT ... FOR UPDATE、代码里的 mutex）。

乐观锁（optimistic）：先动手，提交时校验。读的时候记住一个"版本"，写的时候要求版本没变过；变了就说明中间被别人改过，这次白干，重来。

【推导】两者不是"快慢"的关系，是"把代价花在哪"的关系：

悲观锁乐观锁
什么时候付出代价动手之前（排队等）动手之后（可能白干）
最坏情况是什么排队很长、可能死锁反复冲突、一直重试
并发度被压成串行（同一份数据同一时刻只有一个持有者）不受锁限制（只有写那一条语句会串行）
适合什么冲突率高、临界区短、重试代价大冲突率低、计算便宜、能安全重试

【取舍】所以合适的问法不是"哪个快"，而是："这段并发里，冲突发生得有多频繁？"——下一节把这个问题变成了一个算式。

1.2 一个必须先纠正的认知：乐观锁也加锁【纠错】

【事实】"乐观锁就是不加锁"是错的。以数据库为例：

悲观锁的写法（把锁跨越多条语句）：
  BEGIN
    SELECT stock FROM t WHERE id = 1 FOR UPDATE;   ← 在这里就拿到行锁
    ... 应用层计算 ...
    UPDATE t SET stock = 新值 WHERE id = 1;         ← 一直持锁到这里
  COMMIT                                            ← 才释放

乐观锁的写法（锁只覆盖一条语句）：
  UPDATE t SET stock = 新值, version = version + 1
   WHERE id = 1 AND version = 我之前读到的版本;      ← 这条语句本身也要拿行锁

【推导】两条写法都要拿行锁，差别在"持有多久"：

持锁时间由此推出
悲观锁跨越"读 → 应用层计算 → 写"整段计算越慢、外部调用越多，别人排队越久
乐观锁只有那一条 UPDATE计算再慢也不影响别人；代价转移成"可能白干"

【这就是"乐观锁更快"的真实含义】：不是"不用锁"，而是把持锁时间从"整个业务处理"压缩到"一条语句"，代价是可能重来。这句话说清楚，比背定义有用得多。

到这里你应该能回答：为什么"乐观锁就是不加锁"这个说法在数据库场景里是错的？

2. 判据：冲突率多高才该换（本卡的核心算式）

2.1 期望尝试次数【推导】

设冲突率 p = 一次尝试被别人抢先的概率（假设各次尝试独立），那么"成功一次"需要的尝试次数服从几何分布：

期望尝试次数 = 1 / (1 − p)

【推导】把几个 p 代进去，判据就出来了：

冲突率 p期望尝试次数多做的功（浪费比例）
1%1.01约 1%
10%1.11约 11%
30%1.43约 43%
50%2.00约 100%（等于全部白干一遍）
70%3.33约 233%
90%10.0约 900%

【推导】这个表就是本卡最重要的判据：

p 小（几十个百分点以内）  → 乐观锁划算：多做的功可以忽略，而并发度没被限制
p 大（过半）              → 乐观锁开始"白干比干活还多"
p 很大（接近 1）          → 乐观锁基本就是"反复重试"，必须换方案

2.2 两边的账要放在同一个坐标系里【推导】

乐观锁：处理 N 个请求，实际尝试 N / (1 − p) 次
        → 【多做的工作量】= N × p / (1 − p)
        → 好处：这 N 次尝试【可以并发进行】，不被锁串起来
           （只有最后那条 UPDATE 会短暂串行）

悲观锁：不浪费任何工作，但同一份数据的处理被【强制串行】
        → 吞吐上限 = 1 / 持锁时间
        → 好处：不会白干，冲突率再高也不受影响

【推导】两者的分界不是"哪个快"，而是：

"重试浪费掉的时间" 与 "排队等掉的时间" 哪个更长。

而这两个量都可以被同一件事压缩——缩短临界区（[[母题-L2-锁的粒度与临界区]]）：

  • 悲观锁下缩短持锁时间 → 排队变短
  • 乐观锁下缩短单次尝试时间 → 每次白干也更便宜、窗口也更小

【所以"缩临界区"是比"换锁"更优先的动作】——它两边都改善。

2.3 第三种做法：条件更新（既不加锁也不重试）【推导】

【推导】"防超卖"这道题最能说明问题——它有三种做法，最实用的那种既不是乐观锁也不是悲观锁：

做法写法超卖吞吐死锁风险
① 先查再改（错）SELECT n → 应用判断 → UPDATE n = 算出来的值会超卖 ❌高无
② 悲观锁SELECT ... FOR UPDATE → 判断 → UPDATE不会低（串行）有（多行时）
③ 条件更新（推荐）UPDATE t SET n = n - 1 WHERE id = 1 AND n >= 1不会高无
④ 乐观锁（版本号）读 version → UPDATE ... WHERE version = N不会中（冲突时要重试）无

【推导】为什么 ① 会超卖："读"和"写"是两条语句，中间别人也能读——两个请求都读到 n = 1，都判断"够"，都执行 n = 1 - 1 = 0，结果卖了两件但库存只减了一。这不是"锁选错了"，是"根本没有原子性"。

【推导】为什么 ③ 更好：把"判断"和"写入"合进一条语句，数据库保证这条语句原子执行：

UPDATE t SET n = n - 1 WHERE id = 1 AND n >= 1;
  → 影响行数 = 1：扣减成功
  → 影响行数 = 0：库存不够（或 id 不存在）→ 直接返回"卖完了"

它不需要"先读"、不需要重试、不需要显式拿锁——因为竞争被数据库在这一条语句里解决掉了。（注意 n = n - 1 是"基于当前值"的写法，不是"基于我读到的值"——这就是它和 ① 的本质差别。）

【事实】EnergyOps 里用的是同一类做法：任务抢占不靠锁，而是一条带条件的 UPDATE——WHERE 状态 = 待处理 AND 租约版本 = 我看到的那个，改到 0 行就说明被别人抢先，主动退让（02-aggregation-and-recovery.md）。

【取舍】所以完整的决策顺序是三问：

① 能不能用「条件更新」把判断和写入合成一条原子语句？  → 能，就别用锁
② 不能（需要跨多条语句 / 跨多行的不变量），冲突率高不高？  → 低用乐观、高用悲观
③ 真的要悲观锁，能不能把临界区再缩小？  → 能就缩（L2）

到这里你应该能回答：为什么"防超卖"的标准答案不是"用乐观锁"也不是"用悲观锁"？

3. 乐观锁的重试：不处理就会变成风暴

3.1 重试要退避【推导】

【推导】上游在重试时，冲突率会自己变大——因为重试的请求又回到了同一个竞争池里，形成正反馈：

假设 50 个并发请求抢同一行，冲突率 50%
  第一次：50 个请求，25 个成功、25 个失败
  这 25 个立刻重试 → 25 个请求抢 1 行 → 冲突率更高
  → 失败者再重试 → ……
  结果：成功次数没变多，但【打到数据库的请求数翻了几倍】

【推导】三条对策：

对策做什么代价
指数退避 + 抖动失败后等 随机(0, base × 2^次数) 再试单次延迟变大
限制重试次数试 2–3 次就放弃，返回"稍后重试"给用户用户体验（要能接受）
退化成排队冲突率持续高就切悲观锁 / 用队列串行复杂度

【取舍】"重试几次"是个必须显式定的参数，不能默认无限重试——无限重试 = 把冲突率放大成请求量。

3.2 冲突失败必须能和"业务失败"区分【推导】

【推导】UPDATE 影响 0 行有两种含义，混在一起会误导：

影响 0 行 = ① 版本不匹配（并发冲突 → 应该重试）
          ② 条件不满足（业务规则不通过 → 重试一万次也没用）

处理方式：要么把两种条件分开（先做业务校验，再用版本号做并发控制），要么在"0 行"之后再查一次当前状态来区分。否则会出现"对一个永远不会成功的操作反复重试"。

到这里你应该能回答：为什么"乐观锁失败就重试"这句话是不完整的？

4. 边界与常见误解

常见说法修正
"乐观锁就是不加锁"【事实】错。数据库里乐观锁同样要拿行锁，只不过只有那一条 UPDATE 持锁；真正的区别是持锁时间从"整个业务处理"压缩到"一条语句"，代价变成"可能白干"
"乐观锁一定比悲观锁快"【推导】看冲突率。p 超过一半时，乐观锁"白干的工作量"就超过了它省下的排队时间（期望尝试 2 次以上）。判据是 1/(1−p)，不是感觉
"悲观锁慢，高并发要避免"【取舍】悲观锁把不确定性换成了排队——如果临界区很短、冲突率很高，它反而更稳。"慢"是因为临界区太长，不是因为锁本身
"库存扣减先查再改就行"【推导】会超卖。读和写是两条语句，中间没有原子性。正确写法是条件更新：UPDATE ... SET n = n-1 WHERE n >= 1
"乐观锁失败就重试"【推导】不完整。必须：① 区分"版本冲突"与"业务条件不满足"；② 限制次数；③ 指数退避 + 抖动，否则重试自己会把冲突率推高
"有版本号就万无一失"【事实】版本号只保护你读的那一行。跨行 / 跨表的不变量（比如"订单总额 = 明细之和"）它管不了——那需要事务 + 约束
"冲突高就把重试次数调大"【推导】反了。冲突高说明"白干比例高"，正确动作是换方案（条件更新 / 悲观锁 / 队列串行），不是加大重试
"乐观锁没有死锁问题"【事实】单条 UPDATE 确实不易死锁，但如果一次事务里更新多行、加锁顺序不一致，照样会死锁（[[母题-M10-锁与死锁]]）

一句话结论 全卡唯一要背的锚点

乐观锁和悲观锁不是"快慢"之别，而是把代价花在不同地方——悲观锁在动手前排队（并发被压成串行，但不浪费工作），乐观锁在提交时校验（并发不受限，但冲突时白干）。判据可以算：期望尝试次数 = 1/(1−冲突率 p)，p = 10% 只要 1.11 次、p = 50% 就要 2 次（等于白干一遍）、p = 90% 要 10 次——所以冲突率低用乐观、高则换方案。还要纠正一个关键认知：乐观锁在数据库里同样要拿行锁，只是只拿一条语句（UPDATE ... 1. 什么情况该换悲观锁？

冲突率过半之后（1/(1−p) ≥ 2，白干的工作量已经超过一次），或者重试代价很高（重试要做昂贵计算 / 有外部调用），或者临界区本身很短（排队不痛）。注意顺序：先想能不能改成条件更新，再想缩临界区，最后才换锁。

2. 乐观锁失败怎么重试？

限次（2–3 次）+ 指数退避 + 抖动，并在失败后返回"稍后重试"而不是无限重试。还要先区分"版本冲突"与"业务条件不满足"——后者重试一万次也没用。

3. 防超卖该怎么做？

条件更新：UPDATE ... SET stock = stock − 1 WHERE id = ? AND stock ≥ 1，看影响行数。别用"先查再改"，也别一上来就 FOR UPDATE。真要极致吞吐再上"Redis 预扣 + 异步落库 + 幂等"（[[母题-M17-排行榜与防超卖]]）。

4. 乐观锁真的不会有死锁吗？

单条 UPDATE 不容易死锁，但一次事务里更新多行、加锁顺序不同样会死锁（[[母题-M10-锁与死锁]]）。"乐观"指的是并发控制策略，不是"没有锁"。

5. 冲突率怎么测？

三个来源：① 更新影响 0 行的比例（最直接，版本冲突会体现在这里）；② 版本号 / 业务键的热点分布（同一个 key 被多少请求打）；③ 压测时对比"实际尝试次数 / 成功次数"。有了这个数才能谈选型，否则都是感觉。
  • 「CAS 和乐观锁是一回事吗？」——思想同源、层次不同：CAS 是 CPU/语言层的一条原子指令（比较并交换），乐观锁是应用层的策略（读版本 → 带版本写）。ABA 问题见 [[母题-L2-锁的粒度与临界区]]
  • 「MVCC 算乐观还是悲观？」——都不算。MVCC 是读写不互斥的机制：读走快照、写走新版本，冲突只有在"写写"时才需要处理（[[母题-M9-MVCC]]、[[母题-P13-MVCC与可见性]]）
  • 「PG 的序列化失败为什么建议重试？」——那是 SSI（可串行化快照隔离） 把冲突检测推迟到提交时，失败即 40001，它的补偿手段就是"重试"，和乐观锁是同一套逻辑（[[母题-P9-序列化失败与重试]]、[[母题-P18-乐观并发控制]]）
  • 「任务抢占怎么保证只有一个 Worker 干？」——不用锁：一条带条件的 UPDATE（WHERE 状态 = 待处理 AND 租约版本 = 我看到的），改到 0 行就退让——这就是 EnergyOps 的做法

EnergyOps——任务抢占用"带租约版本的条件更新"，一句话实现加锁 + 判断 + 推进；通知超时进 result_unknown 而不是直接重试，正是"重试前先确认状态"。

先讲"两者把代价花在不同地方" → 纠正"乐观锁不加锁"（持锁时间之差）→ 给判据算式 1/(1−p) 与数值表 → 说明两边其实可以被同一动作改善（缩临界区）→ 给第三条路：条件更新（防超卖标准答案）→ 重试的三条对策与"0 行的两种含义" → 边界与误解

并发控制的一切手段都是在给"出错"定价，而不是消灭它。 悲观锁把"出错"定价成"排队时间"，乐观锁定价成"白干的工作量"，条件更新则把定价降到最低（因为它让数据库在一条语句里解决竞争）。而定价的依据永远是一个可算的量——冲突率。

本次断点：【待填 —— 闭卷时具体卡在哪，写成事实不写评价】

通过证据：能闭卷说清"两种锁把代价花在哪"并纠正"乐观锁不加锁"；能用 1/(1−p) 算出该选哪个；能当场写出防超卖的条件更新并说清它为什么优于"先查再改"；能说清重试的三条对策与"0 行的两种含义"；且自测 5 题全对（尤其 Q4、Q5 的纠错）。
