题目

一个计数器被所有请求争抢，有人建议"把一把大锁拆成 16 把锁"。这个建议什么时候对、什么时候没用？另外——"无锁一定比加锁快吧？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：锁的成本有三笔，别只算"获取"那一笔

1.1 三笔成本【事实】

【推导】任何一把锁都有三笔账：

成本是什么什么时候最大
① 记账开销加锁 / 解锁本身的指令与原子操作临界区极短时（开销占比高）
② 等待成本抢不到时要等（而且等的方式还有代价，见第 3 节）冲突率高时
③ 阻塞别人的时间你持锁期间，别人干不了活临界区长时

【推导】①和③都随"临界区长度"变化，但方向相反：

临界区越短 → ①的相对占比越高（可能"锁本身比干活还贵"）
临界区越长 → ③越严重（别人排队越久）

→ 所以"锁画多大/临界区多长"没有单向答案，要让 ① 和 ③ 在一个点上平衡

1.2 临界区的定义【事实】

【临界区（critical section）】：持锁期间执行的那段代码。判断它画得对不对，只有一个标准：

"在这段代码里，我有没有做与'保护共享状态'无关的事？"

【推导】最常见的错误是把这些放进临界区：

  • 外部调用（HTTP / RPC / 发消息）——网络延迟完全不可控
  • 日志 / 序列化 / 大对象构造
  • 循环里的多条独立更新（本该批量化或分段）

【取舍】"把外部调用挪出临界区"通常是收益最大的一次改动，因为它把"不可控的等待"从持锁时间里摘了出去——这是 [[母题-L1-乐观锁与悲观锁]] 里说的"两边都改善"的动作。

到这里你应该能回答：为什么"临界区短"本身不是目标，而"临界区里没有不属于它的东西"才是目标？

2. 粒度：在"冲突率"和"记账开销"之间选

2.1 粒度决定冲突率【推导】

【推导】锁的粒度越大，覆盖的范围越大，冲突概率越高：

1 把锁保护 100 万行  →  任何两个请求碰到一起都冲突（冲突率高，但记账便宜）
100 万把锁保护 100 万行 → 几乎不冲突（但每行一个锁对象，内存与记账开销大）

【推导】这就是"分段锁 / 锁条带化（lock striping）"的全部内容——把一把锁变成 N 把，按 key 分派：

单段（1 把锁）→ 期望尝试次数 = 1 / (1 − p)
分 N 段（均匀分布）→ 每段的并发压力降到约 1/N
                  → 单段冲突率降到约 p / N
                  → 期望尝试次数 ≈ 1 / (1 − p/N)

代进去算一遍（自测 Q1 完整算）：p = 40%、分 16 段：

单段：1 / (1 − 0.40) = 1.67 次   → 多干 67% 的活
分段：冲突率 ≈ 0.40 / 16 = 2.5%
      → 1 / (1 − 0.025) ≈ 1.026 次 → 多干 2.6% 的活

【推导】收益看起来巨大，但它有前提，而且前提很容易被违反：

前提违反了会怎样
访问要均匀分散在各段有一个"热键"时，它落的那一段照样被打爆——分段救不了热点
一次操作只碰一段如果一次事务要同时改多段（比如转账改两个账户），就有了跨段加锁 → 死锁风险（[[母题-O1-上下文切换与死锁]] 的循环等待）
N 不要大到记账反超收益段数过多 → 内存、cache 命中率、遍历开销都变差

【取舍】所以"锁粒度越小越好"是错的。正确的说法是：

在"访问能被均匀分散"的前提下，粒度小一点更好；一旦出现热点或跨段事务，粒度反而该往回加。

热点键为什么分段也救不了：分段是按 key 分派的，热键始终落在同一段——这时候要用的不是"更多段"，而是换方案：本地聚合（先攒再写）、队列串行、或者把计数拆成"每节点一个累加器 + 定期汇总"（这是"无共享"的思路）。

2.2 数据库里的同一件事【事实】

【事实】数据库的锁粒度是同一条逻辑（[[母题-M10-锁与死锁]]、[[母题-P10-无间隙锁与锁变体]]）：

粒度冲突率记账开销
表锁高（任何两行都冲突）低
行锁低（只有同一行冲突）高（要维护大量锁对象）
间隙锁 / 范围锁更高（连"插入位置"都锁）更高

【推导】所以"为什么 MySQL 用行锁"和"为什么要分段锁"是同一个答案：让冲突只发生在真正竞争的那一小块上。而补间隙锁的原因也一样：防幻读需要锁"不存在的行"，这是用更大的锁粒度换一致性（[[母题-M8-隔离级别与ACID]]）。

到这里你应该能回答：为什么"分段"能提速，但"热键"不行？

3. 抢不到的时候：自旋还是睡眠

3.1 两种等待方式【事实】

  • 自旋（spin）：一直问"好了没"，占着 CPU 不放手
  • 睡眠（block / park）：放手，让别人跑，等被唤醒

【推导】判据只有一个比值：

等待时间  vs  "挂起 + 唤醒"的两次上下文切换成本

【推导】代进量级算一遍（切换成本取 [[母题-O1-上下文切换与死锁]] 的量级 ~1 μs，两次约 2 μs）：

临界区 / 预计等待该选什么为什么
不到 1 μs自旋睡下去再醒过来（~2 μs）比等还贵，而且自旋不占别人的锁
几微秒到几十微秒先自旋一小会儿，再睡这是"自适应自旋"的思路
毫秒级以上睡眠自旋会把整个时间片烧光，而且占着 CPU 不让别人干活

【取舍】"先自旋一会儿再睡"是工程上最常见的折中——因为现实中"临界区到底多长"很难预知，用一小段自旋去赌"马上就好了"，赌输再睡。

3.2 读写锁：读多写少不一定更快【推导】

【推导】直觉是"读可以并行，所以读写锁更适合读多写少"，但有两个反直觉的地方：

① 读写锁自己要额外记账（读计数、写者状态、锁升级判断）
   → 临界区【极短】时，这笔记账可能比省下的等待还贵

② 写者可能被饿死：读很多且持续不断时，写请求一直排在后面
   → 需要额外的策略（写者优先 / 公平模式），而公平模式又要更多记账

【取舍】判据：

场景选什么
临界区极短（几条指令）普通互斥锁往往更快——读写锁的记账比省下的等待还多
读多写少 + 临界区较长（含计算 / 序列化）读写锁值得
读多写少 + 想彻底不互斥考虑 MVCC / 快照：让读走旧版本，根本不和写抢（[[母题-M9-MVCC]]）

到这里你应该能回答：为什么"读多写少就该用读写锁"这句话是不完整的？

4. 不加锁：CAS 与它的三个边界

4.1 CAS 是什么【事实】

CAS（Compare-And-Swap）：一条原子指令——"如果这个位置的值还是 A，就把它改成 B，否则什么都不做并告诉我失败了"。

【推导】它把 [[母题-L1-乐观锁与悲观锁]] 的"乐观"下沉到了指令层：

应用层乐观锁：读 version → 计算 → UPDATE ... WHERE version = N   （两次往返）
CAS：        比较 + 交换，一条指令完成                            （无锁、无排队）

【推导】CAS 的典型用法是"循环重试"：

do {
    old = load(p);
    new = f(old);          // 基于读到的旧值算新值
} while (!CAS(p, old, new));   // 只要中间被别人改了，就重新读、重算

4.2 CAS 的三个边界【取舍】

边界是什么后果
① ABA 问题值从 A 改成 B 又改回 A，CAS 发现"还是 A"就通过了，但它不知道中间变过在"值本身不重要、但变化次数重要"的场景出错（如无锁栈的指针复用）
② 激烈竞争下退化成"自旋烧 CPU"大家都失败、都重试，成功率低但耗着 CPU比加锁更差：加锁至少会让失败者睡下去
③ 只能保护一个变量一次 CAS 只对一个内存位置原子跨多个字段/多个对象的不变量，CAS 表达不了（要靠事务）

【推导】ABA 的解法不是"记住更多信息"这么简单，常见三档：

① 加版本号一起 CAS（把 [值, 版本] 一起比较）—— 最常用
② 用带标记的指针（tagged pointer，把版本编进指针高位）
③ 干脆别用无锁结构，改用锁 + 简单逻辑（如果竞争激烈，这往往是更好的选择）

【取舍】所以"无锁一定更快"是错的：

低竞争（冲突率 ≈ 0）  → CAS 好：没有排队、没有阻塞
高竞争               → CAS 会大量失败重试，CPU 白烧
                       → 这时【加锁反而更好】：它把失败者变成"睡着等"，
                          而不是"醒着抢"

【事实】EnergyOps 的"受控并发"正是这个道理的应用：与其让大量任务自由抢（无论用锁还是 CAS），不如显式限制并发数——"减少竞争"永远优先于"更好地处理竞争"（02-aggregation-and-recovery.md）。

到这里你应该能回答：为什么"无锁"在低竞争下赢、在高竞争下输？

5. 边界与常见误解

常见说法修正
"锁粒度越小越好"【推导】有前提：访问要能均匀分散。出现热键或跨段事务时，粒度小反而更糟（热点照样打爆那一段、跨段加锁带来死锁风险）。正确说法是"在能均匀分散的前提下，粒度小一点更好"
"分段锁能解决热点问题"【推导】不能。分段按 key 分派，热键始终在同一段。热点要靠换方案：本地聚合、队列串行、每节点累加器（无共享）
"读多写少就上读写锁"【取舍】临界区极短时读写锁可能更慢——它的额外记账比省下的等待还贵；还有写者饥饿问题。长临界区的读多写少才明显划算
"无锁一定比加锁快"【推导】看竞争强度。低竞争下 CAS 赢（无排队、无阻塞）；高竞争下 CAS 退化成"自旋烧 CPU"，加锁反而更好（失败者会睡下去）
"CAS 能保证不出错"【事实】有 ABA 问题——值改走又改回来，CAS 看不出来。解法是连版本号一起 CAS（或用带标记指针）
"CAS 能保护整个对象"【事实】一次 CAS 只对一个内存位置原子。跨字段 / 跨对象的不变量它表达不了，要靠事务或把不变量收进一个字段
"加锁就会阻塞"【取舍】加锁也可以不自旋不阻塞——"抢不到就睡"才是关键；而"抢不到就转圈"（自旋）在临界区极短时反而更快。阻塞与否由等待策略决定，不由"有没有锁"决定
"自旋锁一定比互斥锁快"【取舍】只有临界区极短 + 多核时才是。临界区长时自旋是白烧 CPU 还占着调度资源（[[母题-O1-上下文切换与死锁]] 4.3）

一句话结论 全卡唯一要背的锚点

锁的粒度不是在"性能"和"开销"之间选，而是在冲突率和记账开销之间选——分段锁（striping）把冲突率降到约 1/N（p = 40% 分 16 段后从 1.67 次降到 1.03 次），但前提是访问均匀分散；热键始终落在同一段，分段救不了它，得换方案（本地聚合 / 队列串行 / 每节点累加）。自旋还是睡眠由一个比值决定：等待时间 vs "挂起 + 唤醒"约 2 μs 的成本——临界区不到 1 μs 就自旋，毫秒级必须睡；读写锁在临界区极短时可能比互斥锁更慢（记账比省下的等待还贵），"读多写少"的第一选择通常是让读不参与竞争（MVCC / 快照 / 读副本）。CAS 把乐观并发下沉到了指令层，但它有三个边界：ABA（要连版本号一起 CAS）、高竞争时退化成"自旋烧 CPU"（这时加锁反而更好）、一次只能保护一个变量。而最优先的动作永远是：减少竞争本身。
  • 三笔成本（记账 / 等待 / 阻塞别人）
  • 临界区判据：有没有做不属于它的事
  • 把外部调用挪出临界区（两边都改善）
  • 分段把冲突率降到约 1
  • N
  • 前提：均匀分散、一次只碰一段
  • 热键救不了（换方案）
  • 行锁 vs 表锁是同一逻辑
  • 自旋 vs 睡眠 = 等待时间 vs 两次切换（≈2 μs）
  • 临界区 < 1 μs 自旋
  • 读写锁有记账开销与写者饥饿
  • **读多写少的正解是 MVCC
  • 快照**
  • CAS = 一条指令 + 循环重试
  • ABA → 连版本号一起 CAS
  • 高竞争下无锁输给加锁

1. 怎么决定分几段？

按"单段冲突率 ÷ 段数后仍可接受"反推（Q1 的算式），同时段数不能大到记账反超收益。更关键的是先确认没有热键——有热键的话分段没用，先解决热点。

2. 自旋还是睡眠？

看等待时间与"挂起 + 唤醒"成本（约 2 μs）的比值：短于它自旋（比如临界区不到 1 μs），长于它睡眠；工程上常用"先自旋一小会儿再睡"。

3. 读写锁什么时候会变慢？

临界区极短时：它的读计数、写者状态、升级判断这些记账可能比省下的等待还贵；另外还有写者饥饿。"读多写少"的正解通常是 MVCC / 快照 / 读副本。

4. ABA 是什么、怎么解？

值从 A 改到 B 又改回 A，CAS 看不出中间变过。解法：把版本号一起 CAS（[值, 版本] 同时比较），或用带标记的指针。

5. 无锁什么时候不该用？

竞争激烈时。失败者会空转而不是让出 CPU，CPU 白烧、吞吐反降。这时加锁更好（失败者睡下去）；而更优先的动作是减少竞争（分片、每线程累加、显式限制并发）。
  • 「为什么 MySQL 用行锁而不是表锁？」——同一逻辑：让冲突只发生在真正竞争的那一行；代价是锁对象更多、记账更贵（[[母题-M10-锁与死锁]]）
  • 「为什么 InnoDB 还要间隙锁？」——用更大的锁粒度换一致性（防幻读），这是"粒度"和"语义"之间的取舍（[[母题-M8-隔离级别与ACID]]、[[母题-P10-无间隙锁与锁变体]]）
  • 「连接池为什么不用一把大锁？」——连接池本质也是一个"共享资源池"，分段/分桶是它常见的优化方向；而池子耗尽是另一类问题（[[母题-N1-一次请求的完整路径]]）
  • 「为什么 Redis 的 INCR 没有并发问题？」——因为它把并发收成了单线程：不是"更好的锁"，而是"根本没有并发"——这是"减少竞争"的极致形态

EnergyOps——受控并发 + 分区批处理就是"减少竞争"的直接应用：把一个大任务按窗口/设备分区，每个分区只被一个 Worker 处理（本质是"按 key 分段"）；02-aggregation-and-recovery.md 里的"限定窗口、分批、低优先级回补"同理。

锁的三笔成本 → 临界区判据（挪走不可控等待）→ 粒度与冲突率的换算 + 分段锁的算式与三个前提 → 热键为什么救不了 → 数据库里的同一逻辑（行锁/表锁/间隙锁）→ 自旋 vs 睡眠的比值判据 → 读写锁的两个反直觉 → CAS 的原理、ABA 与三个边界 → 无锁与加锁的胜负取决于竞争强度 → 减少竞争优先 → 边界与误解

锁的一切参数（粒度、等待方式、有没有锁）都在服务同一件事——把"冲突"限制在真正竞争的那一小块上。 分段是"缩小冲突范围"，自旋/睡眠是"选择怎么等待"，CAS 是"把等待变成重试"，而最有效的永远是"让冲突根本不发生"（无共享、聚合、队列）。
