母题 N1 · 一次请求走完了什么，以及 502 / 503 / 504 各是哪一层的问题

关联 母题-N2-SSE与推送模型 · 母题-N3-进程线程与协程 · 母题-M6-一条SQL的执行链路 ｜ 正本 wiki/topics/网络/母题-N1-一次请求的完整路径.md

必懂 3 件事（① 请求穿过的是一条分层的链路 ② 连接复用省的是延迟 ③ 502/503/504 对应不同层）· 读完约 10 分钟 · 需要先懂：无

题目

输入一个 URL 到拿到响应，中间经过了什么？如果失败，502、503、504 分别说明哪一层出了问题？

一 · 教材 从前提推到结论，不需要先会

1. 前提：请求穿过的是一条链路，不是一个函数

1.1 链路分几段【事实】

客户端
  ├─ DNS 解析        域名 → IP
  ├─ TCP 握手        建立连接
  ├─ HTTP 请求/响应  讲请求讲什么、回什么
  ↓
网关 / 负载均衡       转发、超时、重试、限流
  ↓
应用                 业务逻辑（可能就是你自己写的服务）
  ↓
上游 / 数据库          缓存、DB、第三方 API

【推导】每一段都可能失败，而且失败的样子不一样——这就是本卡的全部价值：

"报错了"不是结论，"报错的样子"才是线索。 先定位"哪一段"，再谈"为什么"。

1.2 先建立判据

【推导】把所有失败归纳成两类：

失败类型表现对应状态码区间
我的请求有问题参数错、权限不足、路径不存在4xx
服务端处理不了内部错误、上游异常、过载5xx

4xx 和 5xx 的分界线是"谁的问题"——这个分法决定排查方向完全不同：4xx 去看调用方，5xx 去看服务端。

到这里你应该能回答：为什么 401/403、404 都属于 4xx，而不是 5xx？

2. 每一段做什么、失败长什么样

2.1 DNS【事实】

做什么：把域名翻译成 IP。

失败特征：请求根本没出去，客户端立刻报错（"找不到主机"）。这类失败没有 HTTP 状态码——因为它还没到 HTTP 层。

2.2 TCP 握手：为什么是三次【推导】

客户端 → SYN
服务端 → SYN + ACK
客户端 → ACK

为什么是三次，不是两次【推导】：因为双方都要确认"对方能收，也能发"：

  • 第一次：服务端知道"客户端能发"
  • 第二次：客户端知道"服务端能收也能发"
  • 第三次：服务端知道"客户端能收"

两次的话，服务端无法确认客户端能收——它发了 SYN+ACK 之后不知道对方到底收没收到。

【取舍】三次是"可靠的最少次数"。四次挥手是因为 TCP 连接是全双工的，两个方向要各自关闭（一方说"我没数据了"，另一方可能还有数据要发），所以不能把两次合并。

失败特征：连接超时（SYN 没回应）或 连接被拒绝（对方端口没开，回了 RST）。同样没有 HTTP 状态码。

2.3 HTTP：请求与响应【事实】

HTTP 是无状态协议——服务端不会自动记住"你是谁"。所以鉴权要靠每次请求带凭证（Cookie / Token），而不是靠"上次连过"。

【推导】这一条直接推出后面的两件事：

  • 为什么需要 Session / Token：无状态意味着状态得存在别处
  • 为什么长连接与"有状态"是两件事：TCP 连接一直开着，不代表应用记得你（这正是 N2 要讲清的区别）

2.4 连接复用：Keep-Alive 与连接池

为什么必须复用【推导】——算一次延迟就清楚了：

跨机房 RTT ≈ 50ms
TCP 三次握手 ≈ 1.5 RTT ≈ 75ms
TLS 握手   ≈ 2 RTT  ≈ 100ms
新建一次连接总计 ≈ 175ms
而一次简单的上游查询可能只要 20ms

【推导】握手成本是查询本身的 8 倍以上。 所以连接复用首先省的是延迟，其次才省服务端资源（每次握手都要占内存和端口）。

连接池是什么【事实】：预先建好一批连接，用的时候借、用完还。池子的作用是把"建连接"的成本从每次请求摊到很少次。

池子该设多大——这里有一个可以直接用的算式（Little's Law）：

并发需求 L = 到达速率 λ × 单次处理时长 W

这里是本卡最有用的一个推论【推导】：

池子满了，第一反应不该是"把池子调大"，而该问"上游是不是变慢了"。

因为 L = λ × W——并发需求对 W 是线性的。上游慢 3 倍，同样的 QPS 就要 3 倍的连接。这时候调大池子只是把压力往后传（上游更扛不住），没解决根因。

【取舍】但池子也不能设太小：设小了会出现"应用明明不忙，却一直借不到连接"。池子大小要按"正常时延 × 峰值 QPS"算，而不是凭感觉给个 100。

3. 状态码：把"哪一层出问题"翻译成数字

3.1 五个类别【事实】

区间含义
2xx成功
3xx重定向（资源搬走了，去新地址）
4xx调用方的问题：参数、权限、路径
5xx服务端的问题

3.2 502 / 503 / 504 —— 这是本卡的落点【事实】

状态码谁产生的准确含义
502 Bad Gateway网关网关没能从上游拿到一个有效响应：连接被拒绝（上游没起来 / 端口变了）、连接被重置、响应解析不了、协议对不上。注意 RFC 的原话是「收到了一个无效响应」——上游【不一定活着】（连接被拒也算）
503 Service Unavailable应用自己应用主动承认"我现在不行"：过载、正在维护、依赖全挂。可以带 Retry-After 告诉客户端多久后再来
504 Gateway Timeout网关网关等上游等到超时：上游一个字都没回（太慢或卡住）

一句话收口：

502 是答非所问（或根本没连上），504 是根本没答，503 是自己承认不行。

【推导】这三者指向完全不同的排查起点：

看到先查什么
502上游进程状态：是不是刚重启、是不是被 OOM 杀了、是不是端口变了、是不是协议/超时配置对不上
503应用自身的容量：CPU/内存/线程池/连接池打满了吗？是不是在发版？依赖是否整体不可用？
504耗时链路：上游哪一步慢（DB 慢查询？第三方超时？）以及网关的超时阈值设得对不对

3.3 超时应该设几层【推导】

这是"为什么"层面的问题：如果只有一层超时，你会分不清是谁先放弃的。

正确的做法是分层递减：

客户端超时（最长）
  > 网关超时
    > 应用自身超时
      > 上游/DB 超时（最短）

【推导】每往里一层都设得更短，这样超时总是由最内层先触发——你就能从错误信息里直接读出是哪一层放弃的。

反过来（内层比外层长）会怎样：外层先超时，内层还在跑。结果是"客户端已经报 504 了，服务端还在白白消耗资源算一个没人要的结果"——而且日志里看不出根因。

4. HTTP/1.1 与 HTTP/2

HTTP/1.1HTTP/2
连接上的并发一个连接一次处理一个请求（要靠开多个连接来并发）多路复用：一个连接上并发多个流
头部每次重复发送头部压缩（HPACK）
队头阻塞有（前一个响应慢会挡住后面）在应用层缓解（但 TCP 层面仍有队头阻塞 → HTTP/3 换 UDP）

【取舍】HTTP/2 的价值主要在"减少连接数"：浏览器对同一域名的并发连接数有限制，1.1 时代要靠多域名分流；2 用一条连接多路复用解决。服务端内部的 RPC 调用如果已经是长连接池，收益就没那么明显。

5. 边界与常见误解

常见说法修正
"502 就是上游挂了"【事实】502 是上游"活着但答得不对"。上游进程如果完全没起来，网关连不上，得到的通常是 504（等超时）或连接拒绝。"502 = 上游不可用"是 9.9 说反的那句
"504 是服务端挂了"【事实】504 是"网关等上游超时"——服务端可能只是慢。"挂了"和"慢"是两件事，排查方向完全不同
"HTTP 是无连接的，所以每次请求都新建 TCP 连接"【事实】"无状态"和"短连接"是两个概念。HTTP 协议本身不保存会话状态（无状态），但传输层的连接可以复用（Keep-Alive / 连接池）。两者不冲突
"长连接 = WebSocket"【取舍】长连接是传输层的事实（连接不关），WebSocket 是一种协议。SSE 也是长连接，但它跑在普通 HTTP 上（N2）
"连接池越大越好"【推导】L = λW——池子需求由"上游时延 × 到达速率"决定。池子满通常说明上游变慢，调大只是把压力往后传
"超时设一个就行"【推导】超时要分层递减，让最内层先触发；否则外层先放弃、内层还在白跑，且日志看不出根因

一句话结论 全卡唯一要背的锚点

一次请求穿过 DNS → TCP → HTTP → 网关 → 应用 → 上游 这条链路，每一段失败的样子都不同。4xx 是调用方的问题，5xx 是服务端的问题；502 是网关收到上游的无效响应（答非所问），504 是网关等上游超时（根本没答），503 是应用自己承认不行。连接复用（Keep-Alive / 连接池）首先省的是握手延迟（跨机房约 175ms，是一次简单查询的 8 倍以上）；池子需求 = 到达速率 × 单次耗时，所以池子满了要先怀疑上游变慢。
  • 链路六段
  • 4xx 是调用方、5xx 是服务端
  • TCP 三次是因为双向都要确认
  • 无状态 ≠ 短连接
  • 握手成本 ≈ 1.5 RTT + 2 RTT
  • L = λW
  • 池子满先查上游时延
  • 502 答非所问、504 根本没答、503 自己承认
  • 超时嵌套要由内向外递减
  • HTTP2 多路复用

展开（先自答，再看 · 默认收起，不进复训调度）

1. 502 和 504 的区别，一句话说清？

502 是上游答了但答得不对；504 是上游压根没答（等到超时）。 一个指向"上游进程状态"，一个指向"上游耗时"。

2. 连接池被打满，先做什么？

先看上游时延（L = λW：W 变大直接推高需求）。调大池子只是把压力往后传。

3. 超时为什么不能只设一层？

只有一层就分不清谁先放弃。分层递减让最内层先触发，日志里能直接读出是哪一层。

4. HTTP 无状态，那 Session 是怎么实现的？

无状态意味着状态要放到别处：Cookie 带 Session ID、或 Token 自带信息（JWT）。这跟"连接能不能复用"是两件事。

5. 为什么长任务进度推送不该用普通请求？

普通请求是"一问一答"，长任务要"持续告诉进度"，需要推送模型（[[母题-N2-SSE与推送模型]]）。
  • 「一次请求为什么慢，怎么排查？」——按链路分段计时（DNS/TCP/网关/应用/上游），先定位哪一段，再看那一段的指标
  • 「RPC 调用超时了，怎么判断是网络问题还是服务端慢？」——分层超时 + 分段耗时埋点；单纯看总耗时分不出来
  • 「网关的重试会不会放大故障？」——会。重试要配退避与上限，否则上游慢的时候重试会把压力乘几倍

数驭穹图的一次问数请求——前端 → 网关 → 应用 → 权限/检索/SQL 执行，任何一环慢，用户看到的都是"卡住"，所以要先按 N1 的分段法定位；EnergyOps 的上游数据库调用——连接复用与超时分层在这里是实打实的配置项。

链路分几段 → 每段做什么、失败长什么样（DNS 无状态码 / TCP 连接超时或被拒 / HTTP 4xx5xx）→ 无状态与长连接是两件事 → 连接复用省的是延迟（算一次 175ms）→ 池子大小用 L = λW → 5xx 三个码的准确语义与排查起点 → 超时嵌套由内向外递减 → HTTP/2 的价值在减少连接数

"报错了"不是结论，"哪一层报错"才是线索。 请求穿过的是一条分层链路，每一层有不同的失败表征（有的压根没有状态码，有的变成 4xx，有的变成特定 5xx）；定位问题就是把这层分清楚，而不是先猜原因。
