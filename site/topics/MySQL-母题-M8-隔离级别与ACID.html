题目

四个隔离级别各挡住哪个并发问题？ACID 四个字母分别靠什么机制实现？

一 · 教材 从前提推到结论，不需要先会

1. 前提：事务只有一句话

1.1 定义【事实】

事务 = 一组动作，一起成功或一起失败。

就这一句。没有"必须满足 ACID"这种前提——ACID 是从这一句推出来的。

1.2 从这一句推出 ACID

推四步：

① 要能"一起失败" → 必须能撤销 → 需要 undo（前镜像）

【推导】部分成功必须能退回去，所以写入之前要记下"改之前是什么样"。这就是 undo log 的职责。

② 要能"一起成功"在这之后不丢 → 必须能重放 → 需要 redo（后镜像）

【推导】事务说"提交成功"，但数据页可能还在内存里。此时断电，需要一个"改成什么样"的记录，重启后重放补上。这是 redo log 的职责。

③ 并发下多个事务同时在跑 → 需要两种分工

【推导】并发只分两种关系：

  • 写与写：会互相覆盖 → 必须排队 → 用锁
  • 读与写：读不需要改变数据 → 不必排队 → 用 MVCC 让读去看一个"旧版本"

④ 前三步都做完，整体就表现出"从合法状态到合法状态" → 这就是一致性

【推导】一致性不是第四件事，是前三件事的结果。 它还需要数据库约束（唯一、外键、CHECK）和业务校验兜底——但那些是"额外加固"，不是"单独的机制"。

到这里你应该能回答：为什么"一致性靠什么实现"这句话本身就问得不准确？

【结论】A = undo｜D = redo｜I = 锁 + MVCC｜C = 前三者 + 约束共同得到的结果。

撤销看前镜像，恢复看后镜像。

【事实】数据库界把这个四要素结构称为 ACID。

2. 并发会出什么问题

2.1 三个现象【事实】

现象定义例子
脏读读到了别人还没提交的数据（它可能回滚）读到 status='DONE'，但那个事务后来回滚了
不可重复读同一事务内两次读同一行，结果不同先读余额 100，再读变 80
幻读同一事务内两次范围查询，行数不同先查到 10 条，再查变 11 条

三者的区别在"变的是什么"：

  • 脏读 → 变的是数据的提交状态
  • 不可重复读 → 变的是同一行的值
  • 幻读 → 变的是结果集的成员（行数）

【推导】这个区分不是文字游戏：不可重复读可以用"锁住那一行"解决；幻读锁不住——因为要防的是"还不存在的行"，所以它必须靠另一套机制（间隙锁，见 M10）。

2.2 为什么会有这些问题

根子上只有一个原因：并发事务的执行顺序不确定，而你看见的东西取决于"你在哪一刻看"。

【推导】所以解决思路只有两条：

1. 让读看到固定的某一刻 → 快照（MVCC 路线） 2. 让冲突的操作排队 → 锁（串行化路线）

四个隔离级别，就是这两条路线的不同配比。

3. 四个级别：一条单调的取舍谱系

3.1 逐级挡住什么【事实】

级别挡住没挡住
读未提交 RU——全都会发生
读已提交 RC脏读不可重复读、幻读
可重复读 RR（InnoDB 默认）脏读、不可重复读幻读（在 MySQL 里被间隙锁额外挡住，见 4）
串行化全部——

这个表的规律：每一级都是一次"用并发换正确性"的交换，不是"越严格越好"。

3.2 唯一指标：读写冲突面

要比较级别，必须用同一个指标。取"任意两个并发请求会互相阻塞的概率"（按请求对估算）：

假设真实负载里 读占 90%、写占 10%：

情况谁参与互斥冲突面
无 MVCC（读加 S 锁、写加 X 锁，S 与 X 互斥）读-写、写-写2 × 0.9 × 0.1 + 0.1 × 0.1 = 约 19%
有 MVCC（读不加锁）只剩写-写0.1 × 0.1 = 约 1%

【推导】MVCC 的价值不是"更快"，是"把读从冲突里摘出去"。 读占比越高，收益越大——报表型、列表型负载收益最明显。

同一把尺子量四个级别：

级别读要不要参与排队
RU / RC / RR（快照读）不参与（MVCC 兜住）
串行化参与（普通 SELECT 也要加 S 锁）→ 冲突面回到约 19%

【推导】串行化的代价，本质是把 MVCC 挣来的那 18 个百分点又还回去了。

3.3 为什么 InnoDB 默认 RR【取舍】

两个理由，两个都要说，只答一个会显得是背的：

1. 历史原因：早期 RC 在 binlog 为 statement 格式时，主从可能执行出不同结果（RR 的间隙锁恰好压住了这类不确定性）。 2. 工程权衡：RR + MVCC + 间隙锁的组合，在"一致性够用"与"并发不塌"之间取了一个划算的点。

准确说法是：默认 RR 是历史 + 权衡的结果，不是"RR 唯一正确"。 PostgreSQL 默认就是 RC，而且不靠间隙锁——两边都活得很好（[[母题-P8-隔离级别与读一致性]]）。

4. RR 下的幻读：一半靠 MVCC，一半靠锁

先把两个读定义清楚【事实】：

什么操作用什么
快照读普通 SELECTMVCC + 快照（不加锁）
当前读SELECT ... FOR UPDATE / UPDATE / DELETE / INSERT读最新版本 + 加锁

【推导】幻读的准确说法，靠这一对概念分开讲：

  • 快照读下不幻读：RR 的快照在事务第一次读时定住，别人后面插的行根本不在快照里；
  • 当前读下也不幻读：必须读最新版本，MVCC 帮不上，靠 next-key lock 锁住范围阻止插入（M10）；
  • 两者混用时会"看起来像幻读"：先用快照读看到 10 行，接着 UPDATE（当前读）时发现是 11 行——这是两套机制各干各的正常结果，不是 bug。

到这里你应该能回答：为什么"RR 完全解决了幻读"这句话是错的？

5. 边界与常见误解

常见说法修正
"一致性由隔离级别实现"【推导】C 是结果：A（undo）+ D（redo）+ I（锁+MVCC）+ 约束共同得到，没有独立的一致性机制
"RR 完全解决了幻读"【推导】快照读靠 MVCC、当前读靠间隙锁，两种读都不幻读，但混用时会出现"看起来像幻读"；说"完全解决"是漏了机制
"隔离级别越高越好"【取舍】串行化把读也拉进排队，冲突面从约 1% 回到约 19%（3.2 的估算）
"MVCC 是 RR 专属"【事实】MVCC 是 InnoDB 的基础能力，RC 下同样生效，只是快照刷新得更勤（M9）
"MySQL 和 PG 默认隔离级别一样"【事实】MySQL 默认 RR，PG 默认 RC。这是最容易被抓住的方言错误——两边连"怎么处理幻读"都不是一套（[[母题-P8-隔离级别与读一致性]]）
"写写冲突时 MySQL 会报错让我重试"【取舍】MySQL 的哲学是排队等锁；PG 在 RR 以上会报序列化失败（40001）让你重试。"冲突就等"和"冲突就报错"是两种代价模型

事务就是"一组动作一起成败"。A 靠 undo（前镜像）、D 靠 redo（后镜像）、I 靠锁管写写 + MVCC 管读写、C 是前三者加约束共同得到的结果——它不是独立机制。 并发三问题是脏读、不可重复读、幻读，四个隔离级别逐级挡住它们，越严格并发越低。InnoDB 默认 RR，靠 MVCC 挡快照读的幻读、靠间隙锁挡当前读的幻读。

  • 撤销看前镜像、恢复看后镜像
  • undo=A、redo=D、锁+MVCC=I
  • 一致性是结果不是机制
  • 脏读=未提交·不可重复读=同一行·幻读=行数
  • RC 挡脏读、RR 再加不可重复读

实测 386 字 · 按 4 字/秒折算约 96 秒（秒数是估算，字数才是实测）

先说事务的前提：一组动作一起成败。ACID 逐个落地：A 原子性靠 undo（前镜像），D 持久性靠 redo（后镜像），I 隔离性靠锁管写写、MVCC 管读写；C 一致性不是独立机制——它是 A + D + I 再加约束共同得到的结果。

并发三问题：脏读（读到了别人没提交的）、不可重复读（同一行两次读不一样）、幻读（同一个范围两次读行数不一样）。四个级别逐级挡：RU 什么都不挡，RC 挡脏读，RR 再挡不可重复读，Serializable 全挡；越严格并发越低——串行化把读也拉进排队，冲突面从约 1% 回到约 19%。

InnoDB 默认 RR：快照读的幻读靠 MVCC 挡，当前读的幻读靠间隙锁挡，两套机制分工。

边界：不能说 RR「完全解决」幻读——两种读各自都不幻读，但混用时会出现看起来像幻读；MVCC 不是 RR 专属，RC 下同样生效，只是快照刷新更勤；另外 MySQL 默认 RR、PG 默认 RC，两边连处理幻读都不是一套。

分层要点追问深挖时用

  • 结论：A = undo、D = redo、I = 锁 + MVCC，C 是结果不是机制；默认 RR 靠 MVCC（快照读）+ 间隙锁（当前读）两套挡幻读。
  • 推导链：事务前提 → 四个字母逐个找落地点 → 三个并发问题（未提交 / 同一行 / 行数）→ 四个级别逐级挡 → 用「读写冲突面」衡量代价。
  • 量化：串行化把冲突面从约 1% 拉回约 19%（估算）。
  • 边界与常见误解：隔离级别越高越好 ×；MVCC 只在 RR 生效 ×；MySQL 默认 RR、PG 默认 RC；写写冲突时 MySQL 是排队等锁，PG 在 RR 以上会报序列化失败（40001）让你重试。

MySQL 默认 RR + 间隙锁；PG 默认 RC + 快照——注意 40001 不是 RC 的行为：PG 在 RR 及以上才会因写冲突报序列化失败让你重试，默认的 RC 下它同样表现为等待 + 对更新后的版本重新求值（[[母题-P8-隔离级别与读一致性]]）。MySQL 靠锁"挡住"幻读；PG 没有间隙锁，靠检测冲突报错。默认值、幻读处理方式、冲突表现三项全不同——这是全库最容易说反的一组对照。

1. 为什么 A 是 undo、D 是 redo，不能反过来？

undo 记前镜像，所以能撤销；redo 记后镜像，所以能重放。撤销要把数据往回变，重放要把数据往前推。一句话：撤销看前面，恢复看后面。

2. RR 下两个事务同时 UPDATE 同一行会怎样？

排队等锁（MySQL 的哲学是"冲突就等"），不是报错。如果等待成环就死锁，InnoDB 会检测并回滚代价较小的那个事务（M10）。

3. 串行化下还死锁吗？

更容易。读也加 S 锁，锁的持有面更大、成环机会更多。缓解靠统一加锁顺序 + 缩短事务（M10）。

4. 为什么报表查询在 MySQL 下不会互相锁？

普通 SELECT 是快照读，不加锁。但它会持有 ReadView，长查询因此变成"长事务"的一种，拖住 undo 回收（[[母题-M13-长事务为什么危险]]）。
  • 「RC 和 RR 的差别到底在哪一层？」——ReadView 生成时机，别的全一样（M9）
  • 「MySQL 为什么默认 RR，PG 为什么默认 RC？」——两种代价模型：MySQL 用锁"挡住"冲突，PG 用快照 + 报错"检测"冲突。不要用"哪个更好"回答
  • 「MySQL 的 RR 里幻读到底解决了吗？」——分快照读/当前读回答（见 Q5 与第 4 节）

EnergyOps 的采集与聚合事务——"一组动作一起成败"就是窗口幂等与补数的理论基础；RuleArena 的退款事务（10 步在同一事务里提交 + 唯一约束兜底）是 A 与 C 的真实体现——业务校验给清晰错误，数据库约束防并发穿透，两者一起才是"一致"。

事务的唯一前提 → 四步推出 ACID（特别点明 C 是结果）→ 三个并发问题及其区别（未提交 / 同一行 / 行数）→ 四个级别逐级挡 + 用"读写冲突面"这个统一指标说代价 → 为什么默认 RR（历史 + 权衡，不是唯一正确）→ RR 的幻读靠两套机制 → 方言（PG 默认 RC、没有间隙锁）

事务 = "一组动作一起成功或一起失败"。 ACID 不是四条并列的规矩，而是从这一句推出来的四步：要能撤销（undo）、要能不丢（redo）、并发下要分工（锁管写写、MVCC 管读写）、最后整体表现为一致。
