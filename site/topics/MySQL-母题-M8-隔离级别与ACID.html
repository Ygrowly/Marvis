题目

四个隔离级别各挡住哪个并发问题？ACID 四个字母分别靠什么机制实现？

三 · 面试输出 闭卷口述 60 秒，再看结论

四个隔离级别分别解决什么问题？ACID 分别是怎么实现的？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是主线三的地基。它有一个几乎人人会答错一半的追问——"一致性由谁实现？" 答成"由隔离级别实现"或"由某个机制实现"都错了：C 是前三者 + 约束共同保证的结果，它自己不是独立机制。答对这一条，比背四个级别有用得多。

一句话结论 全卡唯一要背的锚点

并发三问题是脏读（读到未提交）、不可重复读（同一事务两次读不同值）、幻读（两次范围查询行数不同）；四个级别逐级递进——读未提交（全暴露）→ 读已提交（挡脏读）→ 可重复读（InnoDB 默认，再挡不可重复读，用间隙锁挡幻读）→ 串行化（读也加锁，全挡但并发最差）。ACID 的实现：A 原子性 = undo log；D 持久性 = redo log；I 隔离性 = 锁 + MVCC；C 一致性 = 前三者加上业务约束共同得到的结果。
  • 脏读
  • 不可重复读
  • 幻读
  • RC vs RR
  • 快照读与当前读
  • undo=原子性
  • redo=持久性
  • 锁+MVCC=隔离性
  • 一致性是结果不是机制

展开（先自答，再看 · 默认收起，不进复训调度）

EnergyOps 的采集与聚合事务（"一组动作一起成败"——窗口幂等与补数）；RuleArena 的退款事务（10 步在同一事务里提交 + 唯一约束兜底——ACID 的 A/C 在这里的真实体现）。方言差异（面试安全底线）：MySQL 默认 RR + 间隙锁；PG 默认 RC + 快照 + 40001 重试。MySQL 的 RR 靠锁挡幻读；PG 没有间隙锁。两边的默认值、幻读处理方式、冲突表现全部不同——这是全库最容易说反的对照（PG 侧的对照表在 PostgreSQL 模块卡第 2 节）。

三个并发问题 → 四个级别逐级挡 → InnoDB 默认 RR（快照读 + 间隙锁挡幻读）→ ACID 逐条对应机制 → 一致性为什么不是独立机制

事务 = "一组动作一起成功或一起失败"。 这句话（raw 里的原话）比背 ACID 四个字有用——因为四个字母能从这一句推出来：一起成败需要 undo（能撤销）和 redo（不丢），并发下多个事务同时做，需要锁和 MVCC 分工，最后整体表现出"一致"。

讲解

原理分解

一、三个并发问题（先分清，级别才有的放矢）

问题定义例子
脏读读到了别的事务还没提交的数据（它可能回滚）读到 status='DONE'，但那个事务回滚了
不可重复读同一事务内两次读同一行结果不同（中间有人改了并提交）先读余额 100，再读变 80
幻读同一事务内两次范围查询返回的行数不同（中间有人插入）先查到 10 条，再查变 11 条

三者区别一句话：脏读关于"未提交"，不可重复读关于"同一行被改"，幻读关于"行数变化"。

二、四个级别逐级递进

级别挡住没挡住
读未提交 RU——全都可能发生（读未提交数据）
读已提交 RC脏读不可重复读、幻读
可重复读 RR（InnoDB 默认）脏读、不可重复读幻读（InnoDB 靠间隙锁挡住了大部分，见下）
串行化全部——（读也加锁，并发最差）

InnoDB 为什么默认 RR：历史原因（早期 RC 在复制场景下可能出现主从不一致），但更本质的是 RR + MVCC + 间隙锁的组合在"一致性"与"并发"之间取了一个工程上很划算的平衡。面试时能说"默认 RR 是历史 + 权衡，不是唯一正确"就比死记强。

三、RR 下幻读怎么挡住（一半靠 MVCC，一半靠锁）

这是本题最容易说错的地方。RR 并不是"完全解决幻读"：

  • 快照读（普通 SELECT）：靠 MVCC——事务开始时定住快照，后面就算别人插入并提交，快照读也看不到 → 不会幻读；
  • 当前读（SELECT ... FOR UPDATE、UPDATE、DELETE）：必须读最新版本，MVCC 帮不上 → 靠 next-key lock（记录锁 + 间隙锁） 锁住范围，阻止别人在范围内插入 → 也不幻读。

所以准确说法是：InnoDB 的 RR 在"快照读"下靠 MVCC、在"当前读"下靠 next-key lock，两种读都不幻读——但两种读混用的场景仍可能出现"看起来像幻读"的现象（先用快照读看到 10 行，再 UPDATE 时行数变了，因为当前读看到了新数据）。这个细节能讲清，说明真的理解了两套机制。

四、ACID 逐条对应机制（本题核心）

字母靠什么实现一句话
A 原子性undo log改错了/回滚了，用 undo 恢复原状——"改之前的备份"
D 持久性redo log提交过但数据页没落盘，崩溃后用 redo 重放补上
I 隔离性锁 + MVCC写写用锁排队，读写靠 MVCC 不互相堵
C 一致性前三者 + 约束 + 业务校验它不是独立机制，是结果

C 那一行必须展开说：一致性 = 事务把数据库从一个合法状态带到另一个合法状态。它需要：A 保证这组动作要么全做要么全不做、D 保证不丢、I 保证并发下互相看不见对方的中间状态、再加上数据库约束（唯一/外键/CHECK）和业务校验。所以"一致性靠什么实现"的标准答案是"前三者共同作用 + 约束"，而不是某一个组件。

这个结构可以直接迁移：RuleArena 的幂等设计里"业务校验 + 数据库约束都要有"（P19）是同一句话在另一处的重述——业务校验给清晰错误，约束防并发穿透，一致性是两者加事务共同的结果。

五、raw 里那句核心（值得记住）

事务保证一起成败，锁保证修改别打架，MVCC 保证读写别互相堵死。

三句对应三块：undo（一起成败的一部分）+ redo（不丢）、锁（写写）、MVCC（读写）。背下这句，整个主线三的骨架就有了。
