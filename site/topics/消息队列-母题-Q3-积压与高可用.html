题目

凌晨告警：某 Topic 积压 1000 万条，还在涨。你打开监控，CPU 不高、磁盘还有空间。该怎么处理？另外——如果 Broker 自己挂了一台，为什么服务还能继续？这套高可用到底靠什么撑住？

一 · 教材 从前提推到结论，不需要先会

1. 前提：这一节在回答两个不同的问题

1.1 积压是"容量"问题，宕机是"可用性"问题【推导】

这两个问题经常被混在一起，但它们的根因、判据和处理动作完全不同：

积压宕机
是什么消息进来得比出去快某个组件不工作了
一句话判据生产速率 > 消费速率副本数 - 已坏数 < 最小可用数
处理方向提高消费能力 / 减少进入 / 明确丢弃切到副本、恢复故障件
共同的危险都需要在"业务能不能接受"这个层面做决策，不是纯技术动作

【推导】先分清这一点很重要，因为在面试和线上都常见一个错误动作：把积压当成"MQ 坏了"，或者把宕机当成"消费慢了"。前者会让你去加机器，后者会让你去重启——两个动作都不对症。

1.2 本卡要用的三个量

  • 生产速率 λ：每秒进来多少条
  • 消费速率 μ：每秒处理多少条（每个消费者一份）
  • 积压量 L：队列里现在堆了多少条

【推导】消积压的净速度就是 λ 和 μ 的差，而消费能力有天花板——这个天花板不是"你能买多少台机器"，而是分区数（第 3 节量化）。记住这个天花板，它决定了积压是一个"能算出来"的问题。

到这里你应该能回答：为什么"积压"和"MQ 挂了"不该用同一套动作去处理？

2. 积压：先查根因，再谈扩容（顺序不能反）

2.1 积压的四种原因【事实】

原因表现该做什么
消费者变慢消费速率突然掉下来先查消费端：慢查询、下游超时、代码死循环、日志爆量
上游流量突增生产速率突然涨削峰（限流 / 排队 / 降级）
消费者挂了 / 被限流消费者数量不足恢复消费者实例，检查是不是被 OOM 杀或配额限流
消费能力本身不够长期缓慢增长真正的扩容：加分区 + 加消费者

【取舍】处理顺序必须是"根因 → 容量"：如果消费变慢是因为"代码里多了一次慢查询"，那加消费者只是让更多线程一起去撞那个慢查询（还会把下游数据库打得更死）。先修根因，再看要不要扩容——这个顺序反了会放大故障。

2.2 扩容的天花板：分区数【推导】

这是本卡最容易被忽略的一条结论：

同一个分区（队列）同一时刻只能被一个消费者消费
→ 消费者数超过分区数后，多出来的消费者分不到分区，处于空闲
→ 消费能力上限 = 分区数 × 单个消费者速率

【推导】所以"加消费者"这个动作有一个硬天花板。越过它的唯一办法是先把分区数加上去（Kafka 里可以给 Topic 增加分区；RocketMQ 可以加队列）。但加分区有代价：

  • 需要数据迁移（分区增加后原有的 Key 哈希分布会变）
  • 顺序语义可能被打破（同一个 Key 原来在一个分区，加分区后如果哈希函数变了会换分区）
  • 所以分区数要在设计期就估算好，临时加是应急手段而不是常规操作

【事实】RocketMQ 的应急手段更"野"一点：海量积压时会用临时 Topic 嫁接——写一个只做转发、不做业务处理的搬运程序，把积压消息转到一个队列数多几十倍的新 Topic，再部署对应数量的消费者快速清掉。关键是"不处理业务"，否则搬运速度和消费速度一样慢，等于没搬。

2.3 最后手段：明确丢弃【取舍】

积压还有一条路：确认这些消息不重要，直接重置 offset 跳过。

【取舍】这是一个必须在业务层面签字的决定，不是技术决定：

  • 合适：监控指标、埋点、日志类数据，丢了不影响正确性
  • 不合适：涉及钱、涉及状态变更、涉及不可逆动作的消息

【事实】跳之前应该先把积压导出备份到对象存储或日志，别跳完才发现里面有重要数据（这就是"不可逆"的定义）。RocketMQ 的原话：非核心数据可以直接重置 offset 跳过；但最后一定要排查消费慢的根因并优化。

到这里你应该能回答：为什么"积压了先加消费者"是一个会踩到天花板的动作？

3. 高可用：三板斧与"MQ 挂了怎么办"

3.1 三板斧是递进的，缺一不可【推导】

【推导】所有 MQ 的高可用都在做同一件事，只是分三层：

层做什么缺了会怎样
① 数据有备份多副本（Kafka 的 Partition 副本 / RabbitMQ 的 quorum queue / RocketMQ 的 Broker 主从）单机故障 → 数据直接没了
② 挂了能自动切选举 + 故障转移（Kafka 的 controller / RocketMQ 的 DLedger / quorum queue 的 Raft）有备份但要停服等人切 → 服务中断
③ 客户端知道切到哪了路由感知（Kafka 靠客户端自己拿元数据 / RocketMQ 靠 NameServer）换了主但客户端还连老地址 → 连不上

【推导】三层是递进关系：有备份不能自动切，等于没有；能自动切但客户端不知道新地址，等于没有。回答"MQ 怎么高可用"时按这三层说，就不会漏。

3.2 选举策略：这是 Q1 那张账的另一面【事实】

选举时"从哪些副本里选"决定了故障的性质（参数细节见 [[母题-Q1-消息为什么会丢怎么才不丢]] 3.5）：

策略选谁换来什么付出什么
只从 ISR 里选（Kafka 0.11 起默认）数据是全的副本不丢数据ISR 全挂光时分区一直不可用
允许从 ISR 之外选谁先回来选谁立刻恢复服务没同步上的消息永久丢失

【推导】这就是"可用性 vs 一致性"在 MQ 里的落点。注意它和积压、和"消费者慢"完全不是一回事——它是"副本层面"的取舍。

3.3 一个必须先说清的边界：MQ 挂了，系统就停了吗【取舍】

【推导】严格说：如果所有写路径都必须经过 MQ，那么 MQ 全挂 = 写路径全停。 这不是配置能解决的问题，而是架构问题。所以正确的做法不是"追求 MQ 永不挂"，而是让"MQ 不可用"成为一个被设计过的状态：

手段做什么
降级非核心链路（通知、埋点）直接丢弃或排队到本地，核心链路（下单、支付）同步执行
熔断 + 本地缓冲发不出去时写入本地文件 / 本地表，恢复后补发（本质上就是把"本地消息表"用在故障期）
幂等 + 可重放保证补发的重复不会造成事故（[[母题-Q2-重复与乱序]]）
可观测积压、ISR 缩小、under-replicated partition、消费 lag 都要有告警——故障要在业务指标恶化之前被发现

【事实】RuleArena 的选择很典型：PostgreSQL 保存权威状态，Redis/ARQ 只负责队列、限流与短期进度。队列被刻意设计成"可以丢或重投"——因为"业务正确性必须落在可恢复的权威数据库里"。这就是"MQ 不可用"被设计过的样子：队列挂了，任务重投；队列丢了，从权威状态扫描重建。它把"MQ 必须永不挂"这个不可能的要求，换成了"MQ 挂了也能恢复"这个可工程化的要求。

3.4 选型到底在选什么【取舍】

【取舍】选型不是选"最好的"，是选"最适合你约束的"。看五个维度就够了：

维度为什么重要量级参考
吞吐决定能不能扛住峰值Kafka / RocketMQ 十万级，RabbitMQ 万级
Topic / 队列数量Topic 多了 Kafka 会退化（要开很多文件、页缓存被摊薄）量级参考（工程经验值，随版本与硬件变化）：Kafka 百级开始明显下滑；RocketMQ 千级；RabbitMQ 队列数可以很多（十万级以上）
顺序与回溯能不能重放历史、能不能按时间/offset 回读Kafka 按 offset 回溯；RocketMQ 按时间回溯；RabbitMQ 原生不支持
高级特性延迟消息 / 事务消息 / 消息过滤要不要RocketMQ 最全（18 级延迟、半事务消息）；Kafka 相对单一
团队与运维出问题时能不能自己查下去与团队技术栈同源，源码可读、可二次开发

【推导】五个维度里，只有前两个是"硬约束"，后三个是"看场景"：

日志 / 大数据管道 / 追求极致吞吐        → Kafka（顺序写 + 批量 + 零拷贝，见 [[母题-O3-IO模型与零拷贝]]）
电商 / 金融 / 要延迟消息和事务消息      → RocketMQ
Topic 数量极多 / 需要灵活路由           → RabbitMQ
只需要"能异步跑 + 能查状态"的 MVP 任务  → 可能根本不需要 MQ，Redis + ARQ 就够（RuleArena 的选择）

到这里你应该能回答：为什么说"MQ 高可用"不是一个参数，而是三层加一个降级设计？

4. 量化：把积压和可用性都算出来

4.1 积压消解时间【推导】

净消解速率 = 有效消费速率 − 生产速率
有效消费速率 = min(消费者数, 分区数) × 单消费者速率
清空时间 = 积压量 / 净消解速率

注意 min(消费者数, 分区数)——这就是天花板进算式的方式（自测 Q1 会算一遍）。

4.2 消费模型：为什么 Kafka 选 Pull【事实】

先介绍双方，再比较：

  • Push（Broker 推）：消息一到就推给消费者。优点是延迟低；问题是 Broker 不知道每个消费者的处理能力，推快了会把慢消费者压垮（可以从限流方向缓解，但控制权仍在 Broker）
  • Pull（消费者拉）：消费者按自己的节奏去拉。优点是永远不会被压垮，还能自由控制进度（想重放就把 offset 往回拨）；问题是没数据时可能空轮询——Kafka 用"拉取时带 timeout（长轮询）"解决

【推导】判断依据是"消费速率该由谁控制"：

  • Kafka 选 Pull：它面向高吞吐、消费者差异大（实时计算引擎 vs 批量 ETL）的场景，让消费者自己控制节奏最合理，还能批量拉取
  • RabbitMQ 默认 Push：面向低延迟业务场景（订单处理、通知发送），消息来了尽快处理更重要

到这里你应该能回答：为什么"Kafka 为什么用 Pull"和"积压为什么加消费者没用"其实是同一个问题的两个问法？

5. 边界与常见误解

常见说法修正
"积压了先加消费者"【推导】会撞天花板：消费者数超过分区数后多出来的全闲置。顺序是"先查根因 → 再加分区 → 再加消费者"
"消费者多开几个就能更快消费同一个队列"【事实】同一分区/队列同一时刻只能被一个消费者消费。消费能力上限 = 分区数 × 单消费者速率
"加分区没代价"【取舍】有：要数据迁移，且可能改变 Key 的哈希分布、影响顺序语义。分区数应在设计期估算
"积压了先重置 offset 跳过"【取舍】跳过是不可逆的，且是业务决定不是技术决定。跳之前先导出备份
"MQ 高可用就是多副本"【推导】只是三板斧的第一层。有备份不能自动切、切了客户端找不到新地址，都等于没有
"MQ 挂了整个系统就停了，所以要保证 MQ 永不挂"【取舍】这是把架构问题当成了运维问题。正确做法是让"MQ 不可用"成为被设计过的状态：降级、本地缓冲、幂等补发、可观测。RuleArena 就是"队列可以丢或重投，权威状态在数据库"
"Kafka 的 Topic 可以随便多开"【事实】Topic / 分区数量多了性能会明显下滑（更多文件、更多页缓存与内存开销）——这是工程经验值（"百级开始下滑"），不是官方硬上限；RabbitMQ 在这个维度上反而更松（队列数可以很多）。选型时这是个要提前估的约束
"所有 MQ 都要靠 ZooKeeper"【事实】Kafka 4.0 起已经只用 KRaft（不再依赖 ZooKeeper）；RocketMQ 用的是自研的 NameServer（无状态、节点间不通信）。还在讲"Kafka 强依赖 ZK"的资料已经过期
"RabbitMQ 用镜像队列做高可用"【事实】镜像队列（classic mirrored queue）2021 年弃用、RabbitMQ 4.0 已彻底移除，官方推荐 quorum queue（基于 Raft，复制到多数派即算成功）。这一条必须更新
"选型选吞吐最高的那个"【取舍】选最匹配约束的。Topic 数量、延迟消息/事务消息、回溯能力、团队栈都可能是真正的瓶颈；MVP 阶段甚至可能不需要 MQ（RuleArena 的选择）

一句话结论 全卡唯一要背的锚点

积压是一个减法：净消解速率 = min(消费者数, 分区数) × 单消费者速率 − 生产速率，而消费能力的天花板是分区数——消费者数超过分区数后多出来的全闲置，要扩容得先加分区再加消费者，并且扩容前必须先查根因（否则只是让更多线程一起去撞慢点）。高可用是三层递进：多副本 → 能自动选主 → 客户端知道新地址，缺一层都等于没有；选举策略上"只从 ISR 选"是用可用性换不丢数据（ISR 全光则分区不可用）。但"MQ 永不挂"是个伪目标——正确的兜底是让"MQ 不可用"成为被设计过的状态：降级、本地缓冲 / Outbox、幂等补发、可观测。选型看五个维度（吞吐 / Topic 数 / 顺序与回溯 / 高级特性 / 团队栈），选最匹配约束的，MVP 阶段甚至可能不需要 MQ。
  • 积压 = 生产 − 消费
  • 消费能力上限 = 分区数 × 单消费者速率
  • 先查根因再扩容
  • 先加分区再加消费者
  • 加分区有迁移与顺序代价
  • 临时 Topic 嫁接只转发不处理
  • 重置 offset 要业务签字 + 先备份
  • 高可用三板斧（多副本 → 自动选主 → 路由感知）
  • ISR 缩水则拒写
  • unclean 是可用性换数据
  • MQ 不可用要设计过：降级 + Outbox + 幂等 + 可观测
  • 选型五维度
  • Pull 因为"消费速率该由消费者控制"
  • RabbitMQ 4.0 移除镜像队列 → quorum queue
  • Kafka 4.0 用 KRaft

积压是一个减法：净消解速率 = min(消费者数, 分区数) × 单消费者速率 − 生产速率；消费能力的天花板是分区数——同一分区同一时刻只能被一个消费者消费，消费者数超过分区数后多出来的全闲置，要扩容得先加分区再加消费者（代价：数据迁移、顺序语义可能变化）。而且扩容前必须先查根因（通常是"每件活变慢"），否则只是让更多线程一起去撞慢点。

分层要点追问深挖时用

  • 结论：积压是减法，天花板是分区数；高可用三层递进，只从 ISR 选主 = 用可用性换不丢。
  • 推导链：净消解速率 → 天花板 → 先查根因再扩容 → 副本/选主/路由三层 → ISR 与非 ISR 选主的后果 → 不可用要被设计过。
  • 量化：min(消费者数, 分区数) × 单消费者速率 − 生产速率；__consumer_offsets 默认 50 分区；自动提交默认每 5 秒。
  • 边界与常见误解："消费者加得比分区多没用"；自动提交与业务处理进度脱钩（可能丢也可能重）；Push 与 Pull 的判据是"消费速率由谁控制"。

1. 消费能力上限是什么？

分区数 × 单消费者速率。同一分区同一时刻只能被一个消费者消费，所以消费者数超过分区数是白加；要扩容得先加分区（代价是数据迁移和顺序语义可能变化）。

2. 消费进度存在哪？两种提交方式的风险是什么？

Kafka 存在内部的 __consumer_offsets 主题（默认 50 分区、压缩、多副本）。自动提交（enable.auto.commit=true，默认每 5 秒）风险是和业务处理进度脱钩——可能丢（提交跑在处理前）也可能重；手动提交分同步（可靠但阻塞）和异步（快但不重试，可能丢 offset）。生产上的常见组合是热路径用异步、关闭 / 重平衡时用同步兜一次。

3. Push 和 Pull 该怎么选？

判断依据是"消费速率该由谁控制"。消费者能力差异大、要批量、要能重放 → Pull（Kafka）；延迟敏感、消息来了要尽快处理 → Push（RabbitMQ 默认）。

4. 积压到几百万条的时候，能不能直接丢掉？

是业务决定，不是技术决定。监控 / 埋点类可以；涉及钱和状态变更的不行。跳之前先导出备份——因为"跳过"是不可逆的。

5. Kafka 和 RocketMQ 的核心区别？

三个维度：存储模型（Kafka 每分区独立日志，Topic 多了退化为随机写；RocketMQ 所有 Topic 写同一个 CommitLog，永远是顺序写）、协调机制（Kafka 用 KRaft，4.0 起不再依赖 ZK；RocketMQ 用无状态 NameServer）、可用性粒度（Kafka 是 Partition 级选举，RocketMQ 是 Broker 级主从）。
  • 「Kafka 的 Consumer Group 是什么？」——组内分工（一个分区只分给组内一个消费者）、组间独立（每个组各自消费全量）。分区数是并行度的天花板
  • 「消息积压到 MQ 磁盘快满了怎么救急？」——优先级：先止住上游（限流 / 降级）→ 再提消费（修根因 / 加分区加消费者）→ 实在不行明确丢弃 + 先备份。MQ 磁盘满会导致写入失败，进而扩散到上游，所以"先止上游"是止损而不是补救
  • 「RabbitMQ 怎么做高可用？」——quorum queue（Raft，复制到多数派即确认；永远都是持久化队列）。镜像队列已在 4.0 移除，别再答它
  • 「怎么监控 MQ 的健康？」——四个指标：消费 lag（积压）、ISR 缩放 / under-replicated 分区、生产/消费速率、磁盘与页缓存。lag 是"业务已经出问题了"，ISR 缩小是"即将出问题"——后者更有价值

积压和宕机都是"容量/可用性"问题，而它们共同的可工程化解法只有一条：别让任何单点承担业务正确性。 积压的解法是"算清楚天花板再扩容"，宕机的解法是"降级 + 本地缓冲 + 幂等补发"——两者都指向同一句话：队列是可以丢、可以重投、可以变慢的，业务正确性必须落在可恢复的权威状态里。
