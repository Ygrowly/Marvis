题目

优化器把「只返回 10 行」的条件估成了 100 万行，于是选了 Seq Scan。你要不要直接加个索引？

三 · 面试输出 闭卷口述 60 秒，再看结论

估计行数与实际行数差很多说明什么？怎么修？线上的慢查询怎么第一时间定位？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是「加索引」和「修信息」的分界线。上一题的例子已经说明——优化器不是一个会犯傻的黑盒，它是在用你给它的统计信息算代价。估错说明「给它的信息不对」，这时候加索引是治症状：统计信息还是错的，下一个查询照样选错。能区分这两件事，是「会看计划」和「会调数据库」的差别。

一句话结论 全卡唯一要背的锚点

偏差来自三类原因——统计信息过期、列之间有关联但统计假设独立、条件是表达式或函数；对应三种修法——ANALYZE（或调 autovacuum 的 analyze 阈值）、CREATE STATISTICS 建扩展统计、把表达式抽成索引或改写 SQL。定位慢查询的第一站是 pg_stat_statements（按总耗时排序，先治「最贵的」），再对单条用 EXPLAIN (ANALYZE, BUFFERS)。

展开（先自答，再看 · 默认收起，不进复训调度）

1. 「CREATE STATISTICS 具体解决什么？」

解决「多列相关」。典型场景：city 和 district（海淀一定在北京，两列强相关）、status 和 deleted_at（删掉的行不再是活跃态）。优化器原本假设独立相乘，扩展统计给它真实的联合分布。

2. 「统计信息准了，计划还是差怎么办？」

那就不是信息层的问题，要么是 SQL 形状让优化器没有好选项（比如为了复用而写了一个过度参数化的语句），要么是代价模型对当前硬件不准（IO 与 CPU 的相对代价随 SSD/内存变化）。此时可以考虑：改写 SQL、用 CTE 的物化提示控制形状、或（谨慎地）调代价参数。但默认先怀疑前两层，因为改代价参数是最容易掩盖问题的一步。
  • 「ANALYZE 和 VACUUM ANALYZE 有什么区别？」——VACUUM 回收空间（见 P15），ANALYZE 只更新统计信息；VACUUM ANALYZE 是顺带一起做。autovacuum 默认两个都做，但两者触发阈值是独立的。
  • 「大表 autovacuum 为什么总是不及时？」——autovacuum 的 analyze 阈值按行数百分比算，超大表要变更多行才触发；而统计信息过期恰恰在大表上最致命。所以大表常常需要单独调 autovacuum 的 analyze 参数。
  • 「pg_stat_statements 能不能看出 N+1？」——能：同一形状的语句 calls 极高、每次 rows 很小，就说明应用在循环里查数据库。这是从数据库侧发现应用问题的有效手段。

EnergyOps 的四层事实表（聚合表数据量跳变，最容易统计过期）；数驭穹图的查询成本控制（按总耗时而不是单次耗时做优化排序）。方言差异（面试安全底线）：MySQL 的对应工具是慢查询日志 + EXPLAIN 的 filtered / rows，没有 pg_stat_statements 这种「按总耗时聚合」的内置视图（要靠 performance_schema）；MySQL 也没有 CREATE STATISTICS 扩展统计，多列相关性主要靠组合索引和 SQL 改写绕开。这一条 PG 明显更强，可以主动说。

偏差的三类原因 → 三种修法 → 定位慢查询的工具链（pg_stat_statements → EXPLAIN ANALYZE）→ 一个隐蔽陷阱（generic plan）→ 优化顺序

优化器不是在猜，它是在拿统计信息算代价。 所以「计划不对」的排查顺序永远是：先问信息对不对，再问 SQL 形状对不对，最后才问索引够不够。

讲解

原理分解

一、统计信息从哪来、估什么

PG 的 autovacuum 进程顺带做 ANALYZE，采样表的一部分行，记录每个列的：

  • n_distinct：不同值大约有多少个；
  • MCV（most common values）：出现频率最高的若干个值和它们的频率（用来处理数据倾斜）；
  • 直方图：其余值的分布。

优化器拿这些数字相乘得到组合条件的行数估计。乘法就埋下了第一个大坑：它假设列之间相互独立。

二、偏差的三类原因与三种修法

#原因表现修法
1统计信息过期刚导入大批数据、刚大批删除后，估算明显偏离ANALYZE 该表；把 autovacuum 的 analyze 阈值调低（大表默认阈值往往触发太晚）
2列间相关一个条件估得挺准，两个条件一乘就错得离谱CREATE STATISTICS 建扩展统计（多列相关性 / 多列 n_distinct），让优化器知道它们不独立
3表达式 / 函数WHERE lower(name) = ?、WHERE date(created_at) = ? 这类条件几乎无法估算建表达式索引（P3）让条件变成可按索引估算，或改写 SQL 去掉函数

第 2 类最容易被忽略：单列统计都是准的，所以「统计信息没错啊」——但优化器把两个独立假设乘起来，结果差三个数量级。被判据就是：单列条件各自估得准、组合条件估得错，就是相关性问题。

三、定位慢查询：先排序，再看单条

第一站 pg_stat_statements（需要启用扩展）。它把 SQL 按「归一化后的语句」聚合，关键列：

列用途
total_exec_time按总耗时排序——先治最贵的（一条慢但很少跑的 SQL，往往不如一条中等但每秒跑一万次的重要）
calls调用次数
mean_exec_time / p99平均与尾延迟
rows返回行数总量
shared_blks_read / hit区分「算得慢」和「读得多」

这一步的核心判断是「按总耗时排，而不是按单次耗时排」。 优化资源应该给「总成本最高」的语句。

第二站：对选中的语句跑 EXPLAIN (ANALYZE, BUFFERS)，按 P6 的五步看。

四、一个隐蔽陷阱：generic plan

PG 的预处理语句有个行为：前 5 次执行会根据具体参数生成「定制计划」（custom plan），之后可能切换成「通用计划」（generic plan）——一个不含参数值的固定计划。

后果：如果某条 SQL 的参数选择性差异极大（比如 status = 'RUNNING' 只命中 0.1%，status = 'COMPLETED' 命中 99%），通用计划只能取一个折中方案，于是对某些参数就变得很慢。

判据与处理：

  • 现象：EXPLAIN ANALYZE 里很快，线上同一条 SQL 很慢；
  • 检查：看计划里是不是用了通用计划（不同参数下计划完全一样、没有参数被代入）；
  • 处理：改写成参数不敏感的形状、或强制重新规划（在连接级别控制）。

这条和 P6 的追问正好接上——「explain 里快、线上慢」有一个标准答案，就是这里。

五、优化顺序（这一段是给面试收尾用的）

① 信息层：统计信息对不对（ANALYZE / 扩展统计）
② SQL 层：有没有多余的行被过早展开（先缩小范围，再 JOIN）
③ 索引层：索引是否存在、是否匹配（P1–P4）
④ 结构层：缓存、物化、预聚合、分区（P16）
⑤ 架构层：读写分离 / OLAP

顺序不能颠倒：先加索引、再发现统计信息是错的，就白加了。EnergyOps 的优化顺序（先修范围与 JOIN → 再建索引 → 再消 N+1 → 最后才缓存）和这条链是一致的。
