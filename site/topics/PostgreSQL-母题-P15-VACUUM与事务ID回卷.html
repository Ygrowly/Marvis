题目

为什么 PG 会「因为太久没清理而拒绝服务」？这是设计缺陷吗？

三 · 面试输出 闭卷口述 60 秒，再看结论

VACUUM 和 VACUUM FULL 有什么区别？autovacuum 怎么调？事务 ID 回卷是什么？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是PG 独有、MySQL 完全没有的一类运维风险，也是「PG 必须有 DBA 意识」的证明。风险在于它有前兆但不致命、直到某个时点突然致命（突然拒绝写入）——所以它考的不是知识，是「你会不会监控和预防」。而且它解释了 P14 那个结论的另一半：为什么「回收跟不上」在 PG 里是会死人的事。

一句话结论 全卡唯一要背的锚点

VACUUM 是「标记可复用」——在线、拿轻锁、不缩小文件，只是把死元组占的空间留给表自己复用；VACUUM FULL 是「重写整表」——能真正缩小文件，但要排他锁、等量额外空间，期间业务不可用。事务 ID 是 32 位、循环使用，所以必须靠「冻结（freeze）」告诉未来的自己「这些行很老、一定可见」；清理长期跟不上就没法安全冻结，PG 会先告警、最后拒绝新事务以避免把老数据误判成未来才可见——这是「宁可停止服务，也不出错数据」的取舍。

  • autovacuum 与触发阈值
  • freeze（冻结）
  • 32 位事务 ID 回卷
  • 告警 → 只读维护模式
  • pg_repack 在线重建

展开（先自答，再看 · 默认收起，不进复训调度）

1. 「为什么 VACUUM FULL 需要等量额外空间？」

因为它新建一张表、把有效行拷过去、再替换（和 MySQL 影子表方案同一个思路，P4 里对比过）。所以磁盘本来就紧张时，VACUUM FULL 反而先把磁盘写爆——这是它最实际的失败方式。能说出这一点，说明不是在背命令。

2. 「怎么判断一个实例的回卷风险高不高？」

看最老未冻结事务 ID 与当前事务 ID 的距离（PG 有相关视图/函数可以查）。这个指标比"有没有长事务"更接近本质——因为真正致命的是「冻结推进不动」，而不是「有长事务」这件事本身。监控口径要盯"离出事还有多远"，不是"有没有出现某个现象" ——这句话可以迁移到所有运维监控设计上。
  • 「VACUUM 和 ANALYZE 什么关系？」——ANALYZE 只更新统计信息（P7）；autovacuum 默认顺带做 ANALYZE，但两者的触发阈值是独立的。
  • 「VACUUM FREEZE 是什么？」——强制做冻结。PG 9.4+ 后有 aggressive vacuum 与 freeze map，手工执行通常没必要，但要知道它在处理什么风险。
  • 「pg_repack 和 VACUUM FULL 到底差在哪？」——pg_repack 的收益是「不长时间持锁」，代价是需要额外空间、需要触发器/复制机制跟踪变更、极端情况下仍可能吃到锁。它是"在线优先"的选择，不是"零成本"的选择。

EnergyOps 的历史事实表（天然该分区按月/季，归档就是丢弃分区——这条把「数据增长治理」和「膨胀治理」合成一个动作）；RuleArena 的事件流水表（追加写、量增长快，是 VACUUM 与分区设计的典型场景）。方言差异（面试安全底线）：MySQL 没有 VACUUM、没有事务 ID 回卷、没有冻结——它靠 purge 线程自动回收 undo，所以「MySQL 也要定期 VACUUM」是明确错误。反过来，MySQL 有它自己的膨胀类问题（表碎片 / undo 表空间膨胀），但机制和处置方式完全不同。两边不能互相套用。

VACUUM 到底做了什么（标记复用）→ 它和 VACUUM FULL 的分工 → autovacuum 为什么跟不上 → 事务 ID 回卷的机制与 PG 的应对 → 膨胀已经发生怎么处理 → 预防清单

VACUUM 解决「空间能不能复用」，VACUUM FULL / pg_repack 解决「文件要不要变小」。 两件事，回答时混为一谈是最常见的失分点——因为绝大多数人以为「跑一次 VACUUM 表就变小了」。

讲解

原理分解

一、VACUUM 做的三件事

1. 回收死元组占用的空间 → 标记为「可复用」（注意：不是还给操作系统）； 2. 清理索引里指向死元组的条目（P13 里那条：索引也要清）； 3. 更新统计信息（VACUUM ANALYZE）并推进冻结（下面讲）。

「可复用」的含义要讲准：空间留在表文件里，后续插入/更新可以填进去。所以表文件大小不会下降，只是「不再继续长」。「跑完 VACUUM 表还是 10GB」是正常的。 很多人的困惑就来自这一步。

二、VACUUM vs VACUUM FULL

VACUUMVACUUM FULL
做什么标记空间可复用重写整张表（新文件 + 拷贝有效行）
锁轻锁，业务基本不受影响排他锁，期间该表不可读写
空间不缩小文件真正缩小
额外空间不需要需要等量额外空间（新表 + 旧表同时存在）
适用日常、autovacuum 自动做万不得已（大表上等于一次业务中断）

所以「表膨胀了要一次 VACUUM FULL」在生产上通常不是一个可接受的方案——尤其大表。生产更常用 pg_repack：它用类似 CREATE INDEX CONCURRENTLY 的思路做在线重建，不长时间持锁，代价是需要额外空间、过程更复杂。

判据：小表或可停机窗口 → VACUUM FULL；大表在线 → pg_repack；根本解法 → 治因（P14）。

三、autovacuum 为什么经常跟不上

autovacuum 是按比例触发的（默认「变更行数超过表的约 20% + 固定阈值」）。两类问题：

问题说明
大表触发太晚比例阈值对大表意味着「要变更多少行」才触发——偏偏大表最经不起堆积。所以大表需要单独调低阈值。
被长事务/复制槽顶住有长事务时，回收边界推不动，autovacuum 跑上去也清不掉东西（P14）；有离线复制槽时 WAL 不回收（P12）。这两个是"看起来在跑但没效果"的典型。

所以「调 autovacuum」不是万能的：它先要能被放开回收边界。判断顺序应该是「有没有东西按住边界」→ 再「阈值够不够激进」。

四、事务 ID 回卷：为什么 PG 宁肯拒绝服务

机制：

  • 事务 ID 是 32 位、循环使用（所以有回卷的概念）；
  • 一个行版本靠 xmin/xmax 判定可见性，如果 ID 用完一圈回来，同一个 ID 既可能表示「很久以前的已提交」又可能表示「很新的事务」，比较就会彻底错乱——老数据可能被判定成"未来才可见"，于是凭空消失。
  • 解决办法是冻结（freeze）：把足够老的行标记为「无论 ID 怎么变，它都是可见的」。冻结必须在 ID 循环到它之前完成。
  • 冻结需要 VACUUM 推进到那个位置 —— 所以清理长期跟不上（长事务 / 停止的消费者）→ 冻结推不动 → 回卷风险上升。

PG 的应对是渐进升级的：

① 远未到期：正常
② 接近阈值：日志/监控告警
③ 非常接近：强制 autovacuum、可能拒绝新事务
④ 超过安全线：进入只允许维护操作的状态（业务写不进来）

为什么这样设计：它宁可付出「短时间不可用」的代价，也不接受「静默丢数据/读错数据」。 这个取舍本身是 PG 的一条设计哲学（和 P9 的「宁可报错让你重试」是同一种态度）——能把这个共性说出来，说明你理解了 PG 的价值观，而不只是记住了一个现象。

五、膨胀已经发生了：三步处理（顺序不能反）

① 先治因：干掉长事务 / 调 autovacuum / 清掉不活跃复制槽
      （否则重建完还会再膨胀）
② 再回收空间：优先 pg_repack；小表或可停机窗口才用 VACUUM FULL
      （VACUUM FULL 要排他锁 + 等量额外空间）
③ 再做结构改造：分区 + 丢弃旧分区，把「持续 DELETE」变成「周期 DROP」
      （P16 —— 这才是不再反复膨胀的解法）

第 ③ 步是真正意义上的解决：「DELETE 历史数据」这个动作本身就是膨胀源（删了要等回收），分区的 DROP 分区几乎瞬时且不产生死元组。所以「有持续清理需求的大表」应该直接设计成分区表——这是从膨胀问题反推出的表设计结论。
