题目

两个 Worker 同时认领同一个任务。用 SELECT ... FOR UPDATE 锁住再改，有什么问题？不用锁怎么写？

一 · 教材 从前提推到结论，不需要先会

1. 先讲清楚「先查再写」为什么必然有竞态

Worker A: SELECT ... WHERE id=1 AND status='READY'   → 查到
Worker B: SELECT ... WHERE id=1 AND status='READY'   → 也查到
Worker A: UPDATE ... SET status='SEARCHING' WHERE id=1  → 成功
Worker B: UPDATE ... SET status='SEARCHING' WHERE id=1  → 也成功 ← 重复认领

两个请求都"读到了合法状态"，所以都认为自己有资格改。

【事实】为什么这在 PG 默认级别下完全可能（[[母题-P8-隔离级别与读一致性]]）：RC 下两条语句各自取快照，中间没有任何东西阻止另一个事务提交。

【事实】而且更微妙的是：即使两条 UPDATE 真的撞上了，RC 下的行为也不是报错——官方说：第二个更新者会等第一个提交，然后【对更新后的版本施加自己的操作】，并且【把 WHERE 条件重新求值】。 所以 WHERE id=1 会匹配，操作照样生效——这就是"重复认领"发生的完整路径。

唯一能救的办法是让「判断」和「写入」不可分割。 三条路：

1. 加锁（SELECT ... FOR UPDATE）——把中间窗口锁住； 2. 数据库约束（唯一约束）——让重复的那次直接失败（[[母题-P19-唯一约束与UPSERT]]）； 3. 条件更新——把判断条件搬进 WHERE，让数据库在一次原子操作里同时判断和写入。

第 3 条就是本题答案，也是 PG 项目里最常用的那条。

2. 条件更新的完整形态

-- ① RuleArena 认领 Run：项目文档 02 §5 给的就是这个形状（表叫 attack_run）
UPDATE attack_run
SET status = 'SEARCHING',
    worker_id  = :worker_id,
    started_at = now()
WHERE id = :run_id
  AND status = 'READY'          -- 只有还是 READY 才抢得到
RETURNING id, status;

-- ② 改「聚合」时再加版本号——防的是「基于旧值做的判断」
--    （项目文档 04 §12 的退款例子：版本 + 业务不变量一起进 WHERE）
UPDATE orders
SET refunded_amount = refunded_amount + :amount,
    version         = version + 1
WHERE id = :id
  AND version = :expected_version
  AND refunded_amount + :amount <= paid_amount;

【推论】两段的差别在于「要不要防旧值」：

认领 Run：判断依据是【状态本身】，状态变了条件自然不成立
          → 状态这一个条件就够
改聚合  ：判断依据是【读到的那个旧值】（剩余可退 = 已付 − 已退）
          → 必须把版本号也进 WHERE，否则"读到 100、要退 80"这个前提会失效

三个要点：

① 判断依据可以是「状态」也可以是「版本号」，看你在防什么：

状态：管业务语义（必须是 READY 才能认领）
版本：管并发冲突（即便状态刚好又变回 READY，版本也不会重复）

【推论】为什么「状态」单独不够——当状态会回流时：如果一行能从 READY → SEARCHING → READY（比如失败后重置），那么"状态是 READY"这个判断对两次不同的认领都成立——版本号能区分"这一轮的 READY"和"上一轮的 READY"。

② RETURNING 让这件事变成一次往返：认领成功时直接拿到更新后的行，不用再去 SELECT 一次。减少一次往返对连接占用和延迟都有意义（[[母题-P17-连接模型与连接池]]）。

③ 用「影响行数」判断结果，不要用异常：

影响行数含义处理
1认领成功继续执行
0别人先改了 / 状态不匹配 / 版本不匹配先读出权威状态再决定（继续跳过、或重试、或报冲突）

【推论】「影响行数 0 不是错误」这个认知很关键——它是一个正常的业务分支，不需要抛异常、不需要重试循环。

【事实】为什么 0 行有多个可能的原因，直接影响处理方式：

0 行可能是：
  ① id 不存在            → 业务上应该报"任务不存在"
  ② status 不是 READY   → 【正常分支】，跳过就行
  ③ version 不匹配       → 【并发冲突】，可以重试

→ 这三者的区别只能靠【再读一次权威状态】来分辨
→ 所以正确做法是：影响 0 行 → SELECT 读权威状态 → 按状态决定

【推论】这也是 [[母题-P10-无间隙锁与锁变体]] 里那条原则的又一次出现：「用一次权威读取替代对原因的猜测」。 不要去猜"0 行是为啥"，去读。

到这里你应该能回答：为什么「更新影响 0 行」这件事，不能简单地当成"失败"？

3. 为什么不用 FOR UPDATE

FOR UPDATE 是可行的（而且更"直观"），但在这个场景下有三处不划算：

维度FOR UPDATE条件更新
冲突时行为排队等待（可能超时/死锁）立即返回 0 行（无等待）
死锁风险有（多行多路径加锁顺序不一致）基本没有（无长持锁）
幂等性需要自己保证天然幂等（重复执行第二次影响 0 行）
连接占用事务持续到业务处理完一条语句就结束

【推导】把「排队等待」的代价算出来——这是 FOR UPDATE 的硬天花板：

FOR UPDATE 把临界区【串行化】了：
  同一行上的并发操作，同一时刻只有一个能进行

吞吐上限 = 1 ÷ 持锁时长

如果持锁 20 ms（比如要在锁里做业务处理）：
  → 这一行的吞吐上限 = 1 ÷ 0.02 s = 【50 TPS】
  → 加再多并发也没用，多出来的都在排队

而条件更新：
  每次尝试 2 ms，冲突率 p = 5%
  → 期望耗时 = 2 ms ÷ 0.95 ≈ 2.1 ms
  → 【不排队】，只是偶尔多跑一次

【结论】FOR UPDATE 的吞吐上限是「1 ÷ 持锁时长」，与并发数无关；条件更新的成本是「期望尝试次数」，与冲突率相关。

【推论】这就是判据的量化版本：

冲突低 → 条件更新（期望尝试 ≈ 1 次，几乎无额外成本）

冲突高 → 条件更新的期望尝试次数会上去（1/(1−p)，见 Q1），但即使 p = 50% 也才 2 次尝试——而 FOR UPDATE 在同样的冲突下会变成一条队列。

【结论】所以真正让 FOR UPDATE 变得必要的不是"冲突高"，而是「临界区里有不可重试的东西」——比如跨行不变量（[[母题-P9-序列化失败与重试]]）、或者临界区里有外部副作用。

【补充】再加上 PG 的一个特殊性（[[母题-P10-无间隙锁与锁变体]]）：PG 没有间隙锁，所以「锁住一个范围以防别人插入」这件事本身做不到——即使你用了 FOR UPDATE，它也只保护「已存在的行」。 在任务认领这种场景里，要保护的是"这一行的状态"，条件更新正好够用；而在需要跨行不变量的场景里，FOR UPDATE 也未必够——那要用约束或 SSI。

4. 它覆盖不了什么（必须主动说出边界）

场景为什么条件更新不行该用什么
跨行不变量（比如「租户至少一个管理员」）一条 UPDATE 只能守一行——多行之间的约束它表达不了SSI（[[母题-P9-序列化失败与重试]]）或把不变量收敛到一行上
必须跨多步操作（读外部数据 → 判断 → 写）判断依据来自数据库之外，没法搬进 WHERE悲观锁 / SSI / 把判断依据也落到数据库
插入语义（"不存在才插入"）条件是"不存在"，UPDATE 天然表达不了唯一约束 + ON CONFLICT（[[母题-P19-唯一约束与UPSERT]]）
临界区里有不可重试的副作用条件更新天然鼓励重试，但副作用重试会重复必须先把副作用做成幂等的（P19）

【推论】第四行是这条主线反复出现的那个前提：「能不能重试」取决于「副作用可不可幂等」——所以「用不用乐观并发」最终是一个幂等设计问题（和 [[母题-P9-序列化失败与重试]] 的结论是同一句）。

5. 落到项目：RuleArena 的认领与扣退款

【事实】项目里的真实形态（表格与状态名以项目正本为准）：

认领 Run（表 attack_run；状态机 DRAFT→NEEDS_CONFIRMATION→READY→SEARCHING→REPLAYING→COMPLETED）
  UPDATE attack_run SET status='SEARCHING', worker_id=:w, started_at=now()
  WHERE id = :run_id AND status = 'READY'          ← 项目文档 02 §5 的原示例
  → 影响 1 行 = 我抢到了；影响 0 行 = 别人抢到了

扣退款 / 记账（改的是聚合，要防"基于旧值做的判断"）
  幂等键走唯一约束（UNIQUE(run_id, action_type, idempotency_key)）
  业务不变量进 WHERE（refunded_amount + :amount <= paid_amount），还要带 version
  → 应用层的条件判断只是【优化】，正确性由约束 + 事务保证

【推论】两段的配合关系要说清：

条件更新管「同一行的状态转移」——它保证「READY → SEARCHING 只发生一次」。

唯一约束管「同一笔业务动作只落一次账」——它保证「重复投递不产生第二次副作用」。

前者是「并发控制」，后者是「幂等防线」——两个问题，两个机制。

【取舍】项目为什么优先条件更新而不是加锁——项目文档给的理由是「权威性」不是「频率」：

项目文档 15 节原话：MVP 优先业务唯一键 + 条件更新
项目文档 Q7 原话：锁可以降低竞争，但不能成为资金正确性的唯一保证。
                 数据库事务、条件更新和唯一约束更接近权威状态；
                 只有真实高竞争时再评估锁。

【事实】而且项目文档明确划了边界，不能把设计说满——04 §12 结尾原话：

「MVP 当前主要覆盖重复和顺序动作；真正并发需要后续加入 barrier 和并发测试，不能把设计说明成已完整实现。」

【取舍】同时要知道文档给的是一个「或」：04 §12 的退款保守方案写的是「在事务中锁定订单行，或使用乐观版本条件更新」——所以"我项目里完全不用锁"是说满了；准确的说法是「优先条件更新，锁留到真实高竞争时再评估」。

6. 边界与常见误解

说法实际情况
「先查再写，查到了就改，没问题」必然有竞态——两个请求都读到合法状态，都会认为自己有资格改
「影响 0 行说明出错了」它是正常业务分支——而且有多个可能原因，要靠权威读取分辨，不能猜
「条件更新失败要重试」多数情况下不该无条件重试——要先读出权威状态，判断是"正常跳过"还是"并发冲突"
「FOR UPDATE 更直观，用它更保险」它把临界区串行化——吞吐上限 = 1 ÷ 持锁时长，与并发数无关
「有了乐观锁就不需要唯一约束了」它守的是「行的状态转移」，守不住「不存在才插入」——那是唯一约束的活
「版本号可有可无，看状态就行」状态能从 A→B→A 时，两次不同的操作都能通过状态判断——版本号才能区分轮次

乐观并发控制在 PG 里怎么写？条件更新和 FOR UPDATE 怎么选？

翻面对照自测；复训调度以训练台派单为准。

为什么重要：这是「业务并发」这条线上最直接能落到代码的一题——它不是"选个模式"，而是"你的判据和写入必须在同一个原子操作里"。 而且它承接 [[母题-P10-无间隙锁与锁变体]]：PG 没有间隙锁，所以"锁住一个范围"根本做不到——这直接决定了有些场景只能用条件更新或约束。

一句话结论 全卡唯一要背的锚点

「先查再写」必然有竞态（两个请求都读到合法状态），唯一解法是让判断和写入不可分割。条件更新就是把判断条件搬进 WHERE——影响 1 行 = 成功，影响 0 行 = 别人先改了，0 行是一个正常业务分支，不是异常。它相对 FOR UPDATE 的好处是三条：冲突时不排队（立即返回 0 行）、基本无死锁、天然幂等（重复执行第二次影响 0 行）。判据是冲突频率：冲突低 → 条件更新；冲突高到重试成本超过加锁成本 → 才用悲观锁。
  • 先查再写有竞态
  • 判断与写入压进一条语句
  • 影响行数 0 是正常分支
  • RETURNING 省一次往返
  • 版本号还是状态
  • 乐观天然幂等
  • FOR UPDATE 的吞吐上限 = 1 ÷ 持锁时长
  • 冲突高才用悲观

  • 推导链：先查再写有竞态 → 判断与写入合并 → 影响行数即结果 → 三条好处 → 判据是冲突频率。

核心思想两边一样（判断与写入合并为一条语句），但撞上时的行为不同：MySQL 是【等锁】（超时由 innodb_lock_wait_timeout 控制）；PG 是【对更新后的版本重新求值 WHERE 并继续】（官方口径）。所以 MySQL 上"两条 UPDATE 撞上会报超时"，在 PG 上表现为"两条都成功"。 这一点不说清，会把两边的事故形态搞混。

1. 冲突高的时候该不该换成悲观锁？

先别急：条件更新的期望尝试是 1/(1−p)、有上界（p = 80% 也才 5 次）；而悲观锁的队列是无上界的。只有一种情况必须换：临界区里有不可重试的东西（跨行不变量、外部副作用）——那时要先把那些东西挪出去，再决定。

2. 版本号怎么设计？

单调递增的整数（version = version + 1），由数据库在同一条 UPDATE 里自增——不要在应用里算。而且要让版本号对所有会改这一行的路径都生效——漏一条路径，乐观锁就有个洞。

3. 影响 0 行之后到底该怎么处理？

读一次权威状态，按状态分三类：不存在 → 业务错误；状态不匹配 → 正常跳过（比如任务已被别人做完，直接返回）；版本不匹配 → 并发冲突（可以重试，重试次数按冲突率定）。「用一次权威读取替代对原因的猜测」是一条可以迁移到所有并发场景的原则（[[母题-P10-无间隙锁与锁变体]]）。

4. 乐观并发下能不能批量更新？

能，但要小心：一次 UPDATE ... WHERE ... 影响多行时，"影响行数"就不再是"我抢到了一行"那么简单——它变成了"我抢到了 N 行"。 判断逻辑要按 N 处理（比如抢批任务时 N > 0 就算抢到）。而 RETURNING 在多行时会把每行都返回——这是批量认领的正确姿势。

5. 这套和 MySQL 那边一样吗？

核心思想一样（判断与写入合并），但有两处不同：① MySQL 的 UPDATE 撞上时会【等锁】而不是"对更新后的版本重新求值"——等待超时是 innodb_lock_wait_timeout；② PG 的 UPDATE 拿的是 FOR NO KEY UPDATE，改键列会升级成 FOR UPDATE（[[母题-P10-无间隙锁与锁变体]]）——这会影响"会不会阻塞子表插入"（[[母题-M16-乐观锁与悲观锁]]）。
  • 「条件更新和 ON CONFLICT DO UPDATE 是一回事吗？」—— 不是。条件更新是 UPDATE 加条件（守「已存在行的状态转移」）；ON CONFLICT DO UPDATE 是 INSERT 加冲突处理（守「不存在才插入 / 存在就更新」）。两者都做到了"判断与写入原子化"，但保护的语义不同。 需要"插入语义"时只能用后者（[[母题-P19-唯一约束与UPSERT]]）。
  • 「为什么不用一个 SELECT ... FOR UPDATE + UPDATE 的两步写法？」—— 因为它把两步变成了"在锁里做两步"，持锁时长翻倍——而吞吐上限是 1 ÷ 持锁时长（Q2）。如果能用一条语句表达，就不要用两条。

- RuleArena 的 Run 认领（本场主战场：表 attack_run，UPDATE ... WHERE id=:run_id AND status='READY'，抢到后进 SEARCHING）。 - EnergyOps 的结算状态流转（状态能从"待结算 → 结算中 → 失败 → 待结算"回流，所以必须带版本号）。 - 数驭穹图的同步任务抢占（多个 Worker 抢同一批任务 → 用 RETURNING 批量认领）。
