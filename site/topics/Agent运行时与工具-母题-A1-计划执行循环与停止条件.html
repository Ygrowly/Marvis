题目

面试官问——"请解释一下 Agent Loop。你们的 Agent 怎么保证不会一直转下去？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：Agent 的必要条件

【事实】Agent 的五个必要条件：

① 有目标
② 能观察环境
③ 模型能选择下一动作
④ 动作改变信息或环境
⑤ 根据结果继续或停止

【推论】"问模型一次、返回一段文本"不是 Agent——它缺 ④ 和 ⑤（动作不改变环境、也没有"根据结果继续"）。固定 DAG 即便用了 LLM，也更准确地称为 Workflow（[[母题-C1-上下文组装与窗口预算]] 里那句"workflow vs agent 的分界判据"）。

【取舍】这个区分不是术语洁癖：Agent 的自主性带来两个必须付的代价——成本不可预测（步数不定）、行为不可穷举（路径不定）。所以选 Agent 之前要先确认：任务真的需要模型现场决定下一步吗？ 如果步骤是固定的，Workflow 更便宜也更可控。

到这里你应该能回答：为什么"我们的系统会调用 LLM 来选工具"还不足以称为 Agent？

2. 循环体：四步，很短

while not state.is_terminal:
    ① 组装上下文（State → Context 投影）
    ② 模型决策：给最终答案，还是调工具
    ③ 校验工具调用 → 执行 → 拿结果
    ④ 记录 Step（版本、幂等键、耗时、错误码）

【事实】原始素材给的关键原则很准：

"Loop 很短，复杂度应集中在可测试的边界组件，而不是一个巨大的 Prompt。"

【推论】这句话有一个直接的工程含义：如果你发现自己在往系统提示里堆"遇到 X 要 Y"的规则，那多半是缺一个边界组件（校验器、预算检查、重试分类），而不是提示写得不细。提示里堆的规则无法被测试，边界组件可以。

【事实】最小 Loop 之外还需要什么（study/04 列全了）：超时、取消、重试分类、HITL、流式事件、并发控制、checkpoint、版本和 trace。

到这里你应该能回答：为什么"把规则写进 Prompt"解决不了 Agent 的失控问题？

3. 预算不是一个数，是七种

【事实】因为"失控"有不同的形状，每种形状要一个对应的预算：

预算防的是什么
max_steps防无限循环
max_tokens / cost控模型成本
deadline控端到端时间
max_tool_calls控外部系统负载
per-tool quota限制昂贵 / 危险工具
max_retries防重试放大（[[母题-A3-失败恢复与幂等]]）
artifact size防日志和结果爆炸

【推导】为什么一个 max_steps 不够：

只设 max_steps = 50，但每步特别慢（模型 2 秒 + 工具 1 秒 = 3 秒）
  最坏耗时 = 50 × 3 = 150 秒
  → 用户等不了，而且这 150 秒里连接、内存、锁都被占着

如果同时设 deadline = 60 秒：
  60 / 3 = 20 步
  → deadline 会在第 20 步先生效

【推论】多个预算之间是"先到先停"——所以设预算时要算清楚哪个会先生效，否则你以为在防 A，实际被 B 拦住了，而 B 的终止原因又会误导排查方向。

【取舍】第 ⑥ 条最容易漏：max_retries 防的是重试放大——一次故障触发重试，重试又失败触发更多重试，把一次故障放大成任务风暴（raw 里的真实事故形态）。

3.1 失控要花多少钱【推导】

max_steps = 50，每步新增约 2.5K token（模型决策 + 工具结果）
累计输入 = 2.5K × (1 + 2 + … + 50)      ← 历史每轮都要重发（[[母题-C1-上下文组装与窗口预算]]）
        = 2.5K × 50 × 51 / 2
        = 2.5K × 1,275
        = 3,187.5K ≈ 3.19M token

成本（Opus 5，输入 $5/MTok）= 3.19M × $5 / 1M ≈ $15.9

【结论】一个失控的 50 步 Agent，单次就要约 16 美元——而这还只是一个 run。并发一来，账单是乘出来的。

【推论】这是"必须有多层预算"最直接的理由：不是"防死循环"这种概念问题，是每一分钟都在烧钱。

到这里你应该能回答：为什么"我们设了 max_steps"这句话还不够？

4. 第三个出口：无进展检测【推导】

【事实】连续无进展是比"步数耗尽"更早、更准的停止信号。两个可判定的信号：

① 状态没变（这一步没有产生新的信息或新的副作用）
② 重复调用同一个工具 + 同样的参数

【推导】它能把浪费压下来：

场景：第 10 步进入循环，max_steps = 50

不做无进展检测：
  跑满 50 步 → 累计输入 = 2.5K × 1,275 = 3.19M → 约 $15.9

做检测（连续 3 步无进展就停）：
  第 13 步停下 → 累计输入 = 2.5K × (13 × 14 / 2) = 2.5K × 91 = 227.5K
  → 约 $1.14

降到约 1/14

【结论】无进展检测把"跑到预算耗尽"变成"确认卡住就停"——它比调小 max_steps 更准，因为正常的复杂任务确实需要很多步，卡住和"在认真干活"长得很像，只有"状态有没有变"能区分。

【取舍】检测到无进展之后做什么，比检测本身更重要：

① 触发澄清（缺输入 → needs_clarification）
② 降级（换更简单的手段）
③ 转人工（unrecoverable_error）

【推论】直接报错退出是最差的选择——它丢掉了"卡在哪"这个最有价值的信息。

到这里你应该能回答：为什么"步数少"不等于"没失控"，而"步数多"也不等于"失控"？

5. 终止原因必须结构化【推导】

【事实】八种终止原因（study/04 的清单）：

completed_verified     结果通过验证
needs_clarification    缺少必要输入
waiting_approval       高风险步骤待确认
budget_exhausted       步骤 / Token / 时间耗尽
tool_unavailable       关键依赖失败
policy_blocked         权限或安全策略拒绝
cancelled_by_user      用户取消
unrecoverable_error    不可恢复错误

【推导】为什么粒度重要——它直接决定可观测性的粒度：

只有 success / fail 两种：
  「失败率从 3% 涨到 12%」—— 看不出发生了什么，也不知道该动哪

有八种：
  「budget_exhausted 占比从 2% 涨到 15%」→ 该看预算与循环检测
  「tool_unavailable 涨了」              → 该看外部依赖
  「policy_blocked 涨了」                → 该看权限策略是否过严

【推论】"模型停了"不是工程可用的终止原因——它把四类完全不同的失败压成了一句话，等于放弃了排查的入口。

【推论】终止原因还要进 Eval（[[母题-G5-RAG评测与幻觉率]] 的归因思路在这里同样成立）：不同终止原因的占比变化，是 Agent 系统最重要的健康指标之一。

到这里你应该能回答：为什么"终止原因"这种看起来是日志细节的东西，值得在面试里专门讲？

6. 验证：Agent 必须能检查自己的工作【事实】

【事实】验证的优先级（study/04 的排序，从强到弱）：

① 确定性测试、Schema、规则、编译器、SQL AST
② 工具返回和权威状态查询
③ 多源交叉证据
④ 模型 Judge
⑤ 人工复核

【事实】原始素材给了一句很硬的话：

"模型'自我反思'不能替代外部 oracle。最强的 Harness 通常给 Agent 可执行测试、浏览器、终端、数据库只读查询等真实反馈。"

【推论】这解释了为什么"Reflection"类技巧效果有限：同一模型重复同一盲点——它反思时用的是同一个"坏掉的尺子"（[[母题-A8-动态计划下的可靠执行]] 会展开）。真正有效的是给它一个外部的、可执行的判据。

到这里你应该能回答：为什么"让模型自己检查一遍"不能替代"让它跑一遍测试"？

7. 边界与常见误解

常见说法修正
"Agent 就是一个 while 循环调模型"循环体确实很短（四步），但工程全在出口：正常终止要靠验证、异常终止要靠多种预算 + 无进展检测，而终止原因必须结构化。只写循环体不写出口，就是 raw 里那个反例："无限 while 等模型说 done"
"模型说 done 就说明做完了"不算。只有"结果通过验证"才算完成（completed_verified）。模型说 done 是它的判断，不是事实——而且它可能只是"觉得自己做完了"
"设一个 max_steps 就够了"不够。失控有不同形状：步数多、每步慢（要 deadline）、工具调得多（要 max_tool_calls）、重试放大（要 max_retries）。而且多个预算先到先停——要算清楚哪个会先生效
"只保存消息历史就能恢复"这是 raw 里点名的反例。消息历史里没有"哪些写操作已经完成"——重启后不知道要不要重做，要么重复扣款，要么漏做。必须记录 Step 级别的副作用与幂等键
"Agent 步数多就是失控"不一定。复杂任务确实需要很多步。判据是"状态有没有变"——认真干活和无意义循环的区别在进展，不在步数
"把规则写进系统提示就能防失控"防不住，而且不可测试。原始的判断是"复杂度应集中在可测试的边界组件，而不是一个巨大的 Prompt"——预算检查、校验器、重试分类都是可测试的组件，提示里的规则不是
"让模型自己反思一遍就能纠错"不能替代外部 oracle。同一模型会重复同一盲点。优先给可执行的反馈（测试、编译器、只读查询），Reflection 只适合生成候选修复，且要通过 Eval 验证增益

【取舍】读成一句话：循环体谁都会写，工程的分量全在"什么情况下必须停下来"——以及停下来之后，你知不知道是为什么停的。

三 · 面试输出 闭卷口述 60 秒，再看结论

一个 Agent 循环长什么样——以及凭什么判定它"做完了"、又怎么防它转不停？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是 Agent 方向的第一道门。它看起来简单（画个循环谁都会），但"怎么停"才是真问题——raw 里那句 "只保存消息历史，进程重启后不知道哪些写操作已完成" 和 "无限 while 等模型说 done" 就是两个反例。能说清终止原因的粒度，比能画出循环体更能证明你跑过线上。

一句话结论 全卡唯一要背的锚点

Agent 的五条件是有目标、能观察、模型能选动作、动作改变环境、根据结果继续或停止——所以"问一次模型返回文本"不是 Agent，固定 DAG 是 Workflow。循环体只有四步（组装上下文 → 模型决策 → 校验并执行工具 → 记录 Step），工程的分量全在出口：正常出口是结果通过验证（而不是模型说 done），异常出口是多种预算 + 无进展检测。预算是七种不是一个——max_steps（防循环）、max_tokens/cost、deadline（防慢）、max_tool_calls、per-tool quota、max_retries（防重试放大）、artifact size；而且它们先到先停，设的时候要算清楚哪个会先生效。为什么必须设：50 步每步 2.5K token 的失控 run，累计输入 3.19M、成本约 $16（平方累计，不是线性）。无进展检测比调小 max_steps 更准——判的是"状态有没有变"，能把浪费降到 1/14。最后，终止原因必须分八类（completed_verified / needs_clarification / waiting_approval / budget_exhausted / tool_unavailable / policy_blocked / cancelled_by_user / unrecoverable_error）——"模型停了"不是工程可用的终止原因。
  • 五条件（动作改变环境 + 根据结果停止）
  • Workflow vs Agent
  • 循环四步
  • 复杂度放可测试的边界组件，不放巨大 Prompt
  • 七种预算 + 先到先停
  • 平方累计的失控成本（50 步 = 3.19M ≈ $16）
  • 无进展检测（状态没变 / 重复同参数调用）
  • 八种终止原因
  • 验证优先级（确定性测试 > 权威状态 > 交叉证据 > 模型 Judge > 人工）
  • 模型自我反思不能替代外部 oracle

1. Agent State、Context、Memory 有何区别？

State 是运行时结构化事实；Context 是某一次模型调用看到的投影；Memory 是跨步骤 / 会话复用的信息。业务状态仍由数据库权威维护。恢复时从 State 和业务状态重新装配 Context（[[母题-A5-上下文压缩与记忆]]）。

2. 怎么防止 Agent 无限循环？

最大步数 / 时间 / 成本 / 工具次数；检测重复状态和重复调用；工具返回明确错误语义；每轮验证进展；连续无进展触发澄清、降级或人工；终止原因进 Eval。

3. Checkpoint 存什么？

目标、运行状态、当前节点、结构化中间结果、Artifact 引用、剩余预算、版本、已完成副作用与幂等键、待审批动作（[[母题-A4-长任务状态与Checkpoint]]）。

4. Reflection 有什么局限？

同一模型可能重复同一盲点，而且多一次调用增加成本。优先给外部测试 / 工具反馈；Reflection 适合生成候选修复或检查清单，并通过 Eval 验证增益。

5. 什么时候该用 Agent 而不是 Workflow？

当"下一步做什么"无法预先穷举、需要模型看情况决定时。步骤固定就别用 Agent——它带来成本不可预测和行为不可穷举两个代价（[[母题-A7-多Agent拆分与协作]] 会从"多 Agent"的角度再讲一遍这个判据）。
  • 「Agent 的"步"（Step）具体指什么？」——一次模型调用或一次工具调用都算一步。Step 要记录 kind（model / tool）、版本、耗时、错误码、幂等键——只存最终聊天文本就没法 Replay 和归因。
  • 「怎么判断一个任务该给多少预算？」——先跑一批真实任务，统计步数与耗时的 P95，再按 P95 的 1.5–2 倍设预算。拍脑袋设的数字要么误杀正常任务，要么拦不住失控。

- RuleArena：连续无进展、预算耗尽、证据冲突各有独立终止原因——这是"终止原因结构化"在项目里的直接落地。 - EnergyOps：任务自愈——从"重试失败的任务"升级为"带进展检测与结构化终止的 Agent run"；Hook 链决定了"哪些动作在循环里被拦住"（[[母题-A6-沙箱权限与可信执行]]）。

五条件与 Workflow 之分 → 循环四步（点明"复杂度放边界组件"）→ 七种预算与"先到先停" → 失控成本算式 → 无进展检测（比调 max_steps 更准） → 八种终止原因与可观测性 → 验证优先级与"反思不能替代 oracle" → 收束到"三个出口"

循环体很短，工程全在出口。 而出口的设计决定了两件事：花多少钱停下来（预算 + 无进展检测），以及停下来之后你知不知道为什么（结构化的终止原因）。
