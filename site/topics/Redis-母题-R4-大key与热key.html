题目

某天 Redis 出现周期性卡顿，SLOWLOG 里出现一条"命令耗时 300 ms"，但那条命令只是 DEL。另一次，集群扩容到 10 个分片之后，整体 QPS 上不去——监控显示只有一个分片的 CPU 打满。这两件事的根因分别是什么？

一 · 教材 从前提推到结论，不需要先会

1. 前提：两个维度，两种打法

1.1 先把两个概念分开【事实】

大 key热 key
维度体积 / 元素个数访问频率
典型形态一个 Hash 里有几百万元素；一个 String 有几 MB一个 key 每秒被读几十万次
危险在哪一次性操作要耗很多时间/带宽单点压力集中
打穿什么内存、网络带宽、主从复制、集群迁移单个分片 / 单个实例的 CPU
救法拆开 + 分批操作打散 + 本地挡

【推导】这两个问题经常被混着讲，但它们的解法完全不同：

大 key  → 问题是"一次操作太大"，解法是【把大操作变小操作】
热 key  → 问题是"所有请求都找同一个点"，解法是【让请求分散到多个点】

1.2 两个共同前提：单线程 + 单分片【推导】

【推导】为什么这两个问题在 Redis 里特别严重，取决于两个结构性事实：

① Redis 的【命令执行是单线程】的
   → 一条慢命令会挡住后面所有命令（不是"这一条慢"，是"全体排队"）
   → 所以"一条 300ms 的 DEL"= 这 300ms 内所有请求的延迟都 +300ms

② 集群里【一个 key 只属于一个分片】
   → 热 key 的压力无法被自动摊到其他分片
   → 所以"加节点"对热 key 是无效的（自测 Q2 会算）

【推导】这两条合起来就是本卡的全部逻辑：

大 key 的危险来自 ①（单线程被一条大命令挡住）；热 key 的危险来自 ②（单分片被打满）。

到这里你应该能回答：为什么"Redis 单线程"这个前提，是理解大 key 危害的关键？

2. 大 key：把大操作拆成小操作

2.1 危害的四个面【事实】

【事实】大 key 不止"占内存"这一个问题：

面机制
① 操作阻塞DEL 一个几百万元素的 Hash 要同步释放所有元素——期间单线程被占住
② 网络带宽一次 GET 一个 5MB 的 String → 5MB 走一遍网络（还会打满网卡）
③ 主从复制大 key 的每次修改都要复制给从库 → 复制延迟被拉长（[[母题-M14-主从复制与延迟]] 是同一问题）
④ 集群迁移槽位迁移时按 key 搬，大 key 会让单个迁移卡住

【推导】第 ① 条最能说明"单线程"的代价：

假设一个 Hash 有 200 万个 field
  删除一个 field 约 100 ns 级（释放对象 + 更新结构）
  逐个释放：200 万 × 100 ns ≈ 【200 ms】
→ 这 200 ms 里，Redis 处理不了任何其他命令
→ 而这期间到达的所有请求，延迟都至少 +200 ms

【注意：这 200 ms 不是"那一个请求慢"，而是"所有人都慢"】 ——这正是 1.2 ① 的后果。

2.2 怎么发现【事实】

【事实】三种手段，按成本从低到高：

手段做什么注意
redis-cli --bigkeys用 SCAN 采样扫描，报告各类型最大的 key⚠️ 它是采样估算，不是精确值；对生产有压力，低峰期跑
MEMORY USAGE <key>精确看单个 key 占多少内存需要对可疑 key 逐个查
监控侧采样 + 慢日志定期按比例扫一批 key 统计大小分布；看 SLOWLOG长期、低开销，适合常态化

【事实】判断"多大算大"没有统一阈值，要按你的集群规格来定，常见的经验线：

String  > 10 KB 就要关注（单条命令的网络与延迟成本）
集合类  > 5000 个元素就要关注（一次全量操作的耗时）
集合类  > 1 MB 基本必须拆

2.3 怎么拆【推导】

【推导】两类处理，别混：

场景做法关键
要删一个大 key用 UNLINK 而不是 DEL【事实】DEL 是同步释放（阻塞主线程）；UNLINK 只把 key 从键空间摘掉，真正的内存回收交给后台线程
要慢慢清一个大的集合HSCAN / SSCAN + 分批 HDEL每次删一小批，让单线程有机会处理别的命令
要长期保留这份数据按业务维度拆成多个 key例如把"某设备全年数据"拆成"每天一个 key"——把大 key 变成一堆小 key，顺带让访问也分散了

【推导】"拆"这个动作有双重收益（这一点最能体现设计感）：

拆之前：一个大 Hash，200 万 field
  删除 → 200 ms 阻塞；而且这个 key 落在【一个分片】上

拆成按天 365 个 key：
  删除 → 每个 key 只有 5000 field（几毫秒）；且 365 个 key 分到不同分片
  → 【既解决了大 key，也顺便缓解了单分片压力】

到这里你应该能回答：为什么"把大 key 按业务维度拆成小 key"比"优化删除方式"更根本？

3. 热 key：让请求分散到多个点

3.1 危害：单分片打满，而且加节点无效【推导】

【推导】热 key 的危害只有一个，但很硬：

集群有 10 个分片，总容量 10 万 QPS，平均每分片 1 万
某个 key 独占 3 万 QPS
→ 它落到的那 1 个分片要承担 3 万 + 其它 key 的流量
→ 【那一个分片打满】，其余 9 个还有余量
→ 而扩容到 20 个分片？那个 key 还是只在一个分片上
→ 【加节点对这个 key 完全无效】

【事实】这就是热 key 与"普通高负载"的本质区别：普通高负载靠水平扩展能解决，热 key 不能——因为它违背了"水平扩展假设请求能均匀分布"这个前提。

3.2 怎么发现【事实】

手段说明
客户端埋点统计在客户端记录 key 的访问频次（最直接，但要改代码）
代理层 / SDK 中间件统计如果有统一的数据访问层，在这里统计最自然
MONITOR（高成本，别在生产常开）能看到实时命令流，但会显著影响性能
采样分析按比例采样命令流，估算 top key
监控指标的"倾斜"集群里某个分片的 QPS/CPU 显著高于其他 —— 这本身就是热 key 的信号

3.3 怎么解（三种，按成本递增）【取舍】

【取舍】

解法做法代价
① 本地缓存（多级缓存）在应用进程内缓存这份数据（几十毫秒 TTL），请求根本不落到 Redis一致性变差：各实例的值可能不同，且更新要广播或等 TTL 过期
② 打散成多个副本 key把 hot:key 变成 hot:key:0 … hot:key:9，读时随机取一个，把读压力摊到 10 个分片写要写 10 份（或缩短 TTL）；读到的可能不一致；key 数量变多
③ 只读副本 / 多副本读读请求走多个副本实例要额外的路由逻辑；主从延迟带来不一致

【推导】选哪个看是"读热"还是"写热"：

读热（绝大多数情况）→ ① 本地缓存最划算：连 Redis 都不用打
                   → ② 打散是退而求其次（不想引入本地缓存时）
写热（同一个 key 被高频写）→ 打散【没用】（写要写 N 份，压力不减）
                        → 只能：本地聚合（攒批） / 队列串行 / 换数据结构

【推导】"写热"这一点值得单独记住：热 key 的"打散"只对读有效，因为一次写会变成 N 次写。写热要靠"聚合"或"串行"，和 [[母题-L2-锁的粒度与临界区]] 里"热键分段救不了、要换方案"是同一个结论。

【事实】RuleArena 的容量文档里给 Redis 只留 256~512MB——这种小规格下，"放到 Redis 里的东西必须是有选择的"，这正是 [[母题-R5-缓存的边界]] 要回答的问题。

到这里你应该能回答：为什么"热 key 打散"只对读有效，对写无效？

4. 边界与常见误解

常见说法修正
"删一个大 key 和删小 key 一样"【事实】不一样。DEL 是同步释放——删一个 200 万元素的 Hash 会让整个实例阻塞约 200 ms。要用 UNLINK（异步回收）或 HSCAN 分批删
"集群加节点就能解决热 key"【推导】不能。集群里一个 key 只属于一个分片，热 key 的压力不会因为加节点而摊开——这正是热 key 与普通高负载的本质区别
"热 key 打散一下就行了"【推导】只对读有效。一次写会变成 N 份写，写热打散反而更糟；写热要靠"本地聚合 / 队列串行 / 换结构"
"大 key 的问题就是占内存"【事实】占内存只是其中之一。更要紧的是单线程被阻塞、网络带宽、主从复制延迟、集群迁移卡住这四样
"用 --bigkeys 扫一遍就知道所有大 key"【事实】它是采样估算，可能漏；而且对生产有压力，应该在低峰跑。要精确得用 MEMORY USAGE 逐个看
"MONITOR 能直接找出热 key"【事实】能看，但代价大——它会把每条命令都推给客户端，生产常开等于自伤。热 key 更适合在客户端/代理层统计，或用"分片倾斜"这个信号去发现
"本地缓存会有一致性问题，所以不能用"【取舍】一致性可以量化：本地缓存放 50 ms TTL，就意味着"最多旧 50 ms"。对于那些本来就能容忍几秒延迟的数据，这 50 ms 根本不算问题——不要用"有一致性问题"一票否决
"大 key 拆分之后就没问题了"【推导】拆完要检查两件事：① 会不会把一个 key 的请求集中到多个 key 上造成新的热点 ② 跨 key 的原子操作是否还需要（拆开之后原来"一个命令搞定"的可能要多个命令 + 事务）

  • 大 key = 体积
  • 热 key = 频率
  • 单线程 → 一条慢命令挡住全体
  • 一个 key 只在一个分片 → 加节点对热 key 无效
  • DEL 同步阻塞 vs UNLINK 后台回收
  • HSCAN 分批删
  • --bigkeys 是采样估算
  • MEMORY USAGE 精确
  • 热 key 发现靠客户端统计 + 分片倾斜
  • MONITOR 代价大
  • 读热：本地缓存 > 打散副本
  • **写热：聚合
  • 串行（打散无效）**
  • 按业务维度拆 key 一箭双雕

1. 大 key 为什么危险？

因为 Redis 命令执行是单线程的：一条 DEL 大 key 会在主线程里同步释放所有元素（200 万 field 约 200 ms），这期间所有请求的延迟都 +200 ms。另外还有网络带宽、主从复制延迟、集群迁移卡住三个面。

2. 删大 key 该怎么做？

UNLINK（异步回收）或 HSCAN/SSCAN + 分批删。注意 UNLINK 之后内存是逐步释放的，监控上不会立刻掉。

3. 热 key 为什么扩容没用？

集群里一个 key 只落在一个分片，压力不会因为加节点而摊开。"单分片打满、其他分片闲置"就是热 key 的签名。

4. 热 key 怎么解决？

先分清读热还是写热：读热用本地缓存（首选，命中率高时直接把 Redis 的流量砍掉一个数量级）或打散成多个副本 key；写热打散无效（一次写变 N 份），要靠本地聚合 / 队列串行 / 换数据结构。

5. 本地缓存能用吗？有没有一致性问题？

能，而且一致性可以量化：TTL 50 ms 就意味着"最多旧 50 ms"。判据是三问：丢了能不能重建、旧 50 ms 能不能忍、会不会因为旧值做错事。只要它参与判断（余额、库存），就不能用。
  • 「缓存击穿和热 key 是什么关系？」——同一个压力来源的不同表现：击穿是"单个热 key 失效瞬间全部回源"，热 key 是"单个 key 长期打满分片"。解法都指向"别让请求集中到一个点"（[[母题-R3-缓存一致性与三类事故]]）
  • 「大 key 和数据倾斜是什么关系？」——大 key 常常就是数据倾斜的成因：按用户 ID 分片时，某个超大用户的 key 会固定落在某一片上
  • 「热 key 和锁的热键问题是同一件事吗？」——是同一件：分段救不了热键，都要换方案（聚合/串行/本地化），见 [[母题-L2-锁的粒度与临界区]] 2.1
  • 「Redis Cluster 的槽位迁移为什么怕大 key？」——迁移是按 key 搬的，大 key 会让单次迁移卡住，这是大 key 危害的第四个面

RuleArena——08-capacity-cost-and-facts.md 给 Redis 只配 256~512MB：这个规格下"大 key"几乎没有容身之地，也意味着放进去的东西必须是有选择的（→ R5）。

先把两个维度分开（体积 vs 频率）→ 给两个共同前提（单线程、单分片）→ 大 key 的四个危害面 → 发现（三种手段与注意事项）→ 拆（UNLINK / 分批 / 按业务维度拆）→ 热 key 为什么加节点无效（算一遍）→ 发现（客户端统计 + 分片倾斜）→ 解（读热 vs 写热分开）→ 本地缓存的代价要量化 → 边界与误解

大 key 的危险来自"单线程"（一条大命令挡住全体），热 key 的危险来自"单分片"（一个 key 打不散）。 想清楚这两个前提，就能自己推出所有解法：大 key 要把一次大操作拆成多次小操作，热 key 要把一个点变成多个点（读）或把多次写变成一次写（写）。
