题目

凌晨告警"接口 P99 从 200ms 涨到 3s"。你打开监控，看到一个"CPU 利用率 45%、内存正常、磁盘正常"的画面。请说出你的排查顺序——以及你会先排除什么、为什么。

一 · 教材 从前提推到结论，不需要先会

1. 前提：排查的能力体现在"顺序"，不在"记得多少命令"

1.1 为什么顺序比工具重要【推导】

【推导】"把所有命令敲一遍，看哪个数字大"这个做法有两个硬伤：

① 成本：一次完整巡检要几分钟，而线上故障的分秒都在计费
② 误导：总会有【某个数字看起来偏高】——它可能只是噪声，
        而不是根因；一旦你顺着它查下去，就会离真因越来越远

【推导】正确的做法是"用两个是的/否问题，把可能性先砍掉一大半"：

问题一：是【全部接口】慢，还是【某个接口】慢？
        全部 → 看共用的东西（DB、缓存、网络、宿主机）
        个别 → 看这个接口自己的代码与它独用的依赖
        ★ 这一个问题就能把范围缩掉八成

问题二：是【所有实例】慢，还是【个别实例】慢？
        所有 → 共性资源 / 上游 / 流量
        个别 → 这台机器 / 这个容器 / 这一次部署

【取舍】这两个问题加起来只有四个组合，但每一个组合都指明了下一步——这就是"顺序"的价值：它让你在信息最少的时候，做出最有信息量的动作。

1.2 两个二分：压力 / 能力，在等 / 在算【推导】

【推导】第二个二分问题决定"加资源有没有用"：

压力能力
含义活来得太多每件活干得太慢
判断QPS 涨了 / 并发涨了QPS 没变，但耗时变长
对策限流、扩容、排队优化（算法 / 查询 / 下游）
加机器有用吗有用（有上限）常常没用（瓶颈在单次耗时上）

【推导】第三个二分问题决定"该优化什么"（同一个算式在三个模块里出现过）：

在等（IO / 锁 / 下游）→ 改异步、优化下游、缩小临界区
在算（CPU 密集）      → 加核、改算法、拆到进程池
判据：CPU 占用 / 总耗时
  占比低（如 2%）→ 基本都在等 → 加核没用
  占比高（如 80%）→ 基本都在算 → 改异步没用
（这一算式在 [[母题-O3-IO模型与零拷贝]] 1.1、[[母题-O1-上下文切换与死锁]] 5 反复出现）

到这里你应该能回答：为什么"先问两个是非题"比"先跑一遍巡检命令"更省时间？

2. 四类症状：每一类先看什么

2.1 CPU【事实】

【事实】先区分三种完全不同的情况：

现象含义下一步
使用率高 + 有用的工作在推进能力问题（真的在算）找热点：火焰图 / perf，或看哪个线程在烧
使用率高 + 吞吐没有提高可能是空转（自旋、忙等、重试风暴）看是否在重试、锁竞争（[[母题-L2-锁的粒度与临界区]]）
使用率不高 + 延迟抖动可能被限流（容器）或在等 IO看 cpu.stat 的 nr_throttled / throttled_usec（[[母题-X1-容器是什么]] 3.2）

【推导】load average 是这里最大的坑：

load ≈ 可运行的任务数 + 【不可中断等待】的任务数
→ load 高有两种完全不同的解释：
   ① 很多任务在抢 CPU（可运行）   → 真的 CPU 不够
   ② 很多任务卡在磁盘 IO（不可中断等待）→ 【CPU 可能很闲】
→ 判据：load 高 + CPU 低 = 在等 IO（这是最经典的误判）

2.2 内存【事实】

【事实】三步，顺序不能反：

① 看 available，不看 used        —— used 里很多是可回收的页缓存（[[母题-O2-虚拟内存与缺页]] 3.2）
② 看容器自己的额度               —— free 是宿主机的视图（[[母题-X1-容器是什么]] 2.1）
③ 区分三种"涨"                   —— 泄漏 / 页缓存 / 无上界结构（[[母题-O2-虚拟内存与缺页]] 5.5）

【推导】加一个更早的信号：/proc/pressure/memory（PSI） ——它在 OOM 之前就会升高，比"等 OOM 日志"早（[[母题-O2-虚拟内存与缺页]] 3.2）。

2.3 磁盘【事实】

【事实】先分清"空间"和"性能"两件事：

问题先看
空间满从根目录逐层 du 排序，或按文件大小找；注意"已删除但被进程占用的文件"（df 满而 du 对不上，就是它）
性能差%util（设备忙的程度）与 await（平均等待）；「%util 高 + await 高」= 设备真的到顶了；「%util 不高但 await 高」= 排队在别处（如队列深度、文件系统层）

【推导】一个高频误判：空间满 ≠ 性能差，性能差 ≠ 空间满——两个问题的定位工具、处理动作完全不同，第一句就要分清。

2.4 网络【事实】

【事实】四个方向：

方向看什么典型现象
连接连接数、TIME_WAIT / CLOSE_WAIT 的数量连接池打满 / 端口耗尽（[[母题-N1-一次请求的完整路径]]）
丢包与重传重传率延迟抖动、吞吐上不去
带宽网卡吞吐大 key / 大结果集把网卡打满（[[母题-R4-大key与热key]]）
对端延迟下游的响应时间这才是"网络慢"最常见的原因——不是网络，是下游慢

【推导】最后一条最值得记住：大多数"网络问题"其实是"下游问题"——因为在调用方看来，两者的表现都是"等待"。所以排查时必须把"链路耗时"和"对端处理耗时"分开，否则会一直修自己不慢的那一段。

到这里你应该能回答：为什么"网络慢"这个结论通常需要再往下拆一步？

3. 量化与判据

3.1 压力还是能力：用一个比值判断【推导】

【推导】同一个指标看趋势，两个指标看关系：

判定"压力"：QPS / 并发数【上升】了，而单次耗时基本不变
            → 活多了 → 限流 / 扩容（有效）

判定"能力"：QPS 没变，但单次耗时【上升】了
            → 每件活变慢 → 优化（扩容常常无效）

【推导】再加一条"资源与吞吐的关系"：

加资源能提高吞吐 → 说明瓶颈在这个资源上（压力型）
加资源吞吐不动   → 瓶颈在别处（能力型 / 或别的资源）
→ 这条也叫"看有没有饱和信号"：接近饱和的资源才可能是瓶颈

3.2 等 IO 还是等 CPU：交叉判定【推导】

【推导】单看一个指标不够，要看两个的关系：

CPU 高 + load 高 + 磁盘忙 → 在算，且可能是 CPU 或磁盘
CPU 低 + load 高          → 【在等 IO】（签名）
CPU 低 + load 也低        → 在等【外部】（锁 / 下游 / 连接池）

【推导】第三种最容易被忽略：自己什么都不忙，但很慢——那一定是在等一个不在本机上的东西。这就是分层归因的价值（[[母题-N1-一次请求的完整路径]] 的"先分清卡在哪一层"）。

到这里你应该能回答：为什么"本机指标一切正常"这件事本身就是一条重要线索？

4. 边界与常见误解

常见说法修正
"load 高就是 CPU 不够"【推导】两个原因：可运行任务在抢 CPU，或大量任务卡在不可中断等待（多为磁盘 IO）。load 高 + CPU 低就是在等 IO 的签名
"CPU 利用率不高就说明没压力"【推导】在容器里尤其错：配额是"每周期的时间预算"，用完之后即使核空闲也用不了——看 cpu.stat 的 nr_throttled / throttled_usec（[[母题-X1-容器是什么]] 3.2）
"free 显示内存用满就是要爆了"【事实】先看 available：used 里很大一部分是可回收的页缓存。"用满"本身不是问题，"回收不动"才是（[[母题-O2-虚拟内存与缺页]]）
"磁盘告警就是空间要满了"【事实】空间与性能是两件事：空间用 du/df（注意"已删除但被占用的文件"），性能看 %util 与 await。第一句就要分清问的是哪一个
"接口慢就是网络问题"【推导】大多数"网络慢"其实是下游慢——调用方看来都是等待。必须把链路耗时与对端处理耗时分开，否则会一直修自己不慢的那一段
"所有指标都正常，那一定是代码有 bug"【取舍】也可能是"在等一个不在本机上的东西"（锁、连接池、下游、队列）。"本机一切正常"是一条指向"外部依赖"的线索，不是"没问题"的结论
"先跑一遍完整巡检，把所有指标都看一眼"【推导】先缩范围再看数：一次巡检几分钟，而且总会有某个数字偏高，顺着噪声查会离真因更远。顺序：全部/个别 → 压力/能力 → 在等/在算，然后才落指标
"排查一个人的活，靠经验"【取舍】经验体现在"知道先排除什么"：比如"全部接口都慢 → 先看共用依赖"，"个别实例慢 → 先看这台机器和这次部署"。这些是可以写下来的规则

1. load 高但 CPU 不高说明什么？

大量任务处于不可中断等待（通常是磁盘 IO）。这就是"在等"的签名——下一步看 IO 压力（%util / await / IO PSI），而不是加 CPU。

2. CPU 利用率不高，为什么还可能是 CPU 的问题？

容器配额是"每周期的时间预算"，用完就不给——看 cpu.stat 的 nr_throttled / throttled_usec（[[母题-X1-容器是什么]] 3.2）。

3. 怎么区分 IO 瓶颈和 CPU 瓶颈？

看 CPU 占用 ÷ 总耗时：占比低就是"在等"（IO / 锁 / 下游）；再交叉 load 与磁盘指标定位到具体是哪一种"等"。

4. 接口慢但本机指标全正常，怎么查？

它指向"外部依赖"：按调用链分段比耗时（下游、数据库、连接池、队列），先归因再优化。别忘了检查超时层级是否设成了"内外一样"——那会让日志失去归因信息。

5. "网络慢"该怎么验证？

把链路耗时和对端处理耗时分开：对端有埋点就看它的处理时间；跨机房的固定延迟不解释量级变化，突然变慢通常是对端的问题。
  • 「怎么知道扩容有没有用？」——看瓶颈有没有饱和：加资源后吞吐上去了 → 瓶颈在这；不动 → 瓶颈在别处。这也是"压力还是能力"的实践版
  • 「日志刷得太多会不会导致变慢？」——会：同步写日志会阻塞（[[母题-O1-上下文切换与死锁]] 4.3 的"阻塞会拖垮整条链路"），而且日志文件本身就是"没设上界的东西"（Q3）
  • 「为什么要有 Trace？」——因为"本机正常但慢"这一类问题，只能靠跨段耗时来定位（[[母题-E2-Trace与可观测性]]）；排查顺序的最后一步就是"追一条完整链路看时间花在哪一段"
  • 「项目和排查有关的一个教训是什么？」——EnergyOps 的 00-project-map.md 里有"故障 → 后端归属"的对照表：把"这类现象该去哪个模块查"提前写下来——这就是把"顺序"沉淀成资产

数驭穹图——08-查询性能与成本控制.md 的"结果层优先 → 强制分区 → JOIN 基数校验 → EXPLAIN 成本门禁 → 超时与扫描量限制"排列顺序本身就是一套排查顺序：先做最便宜的判断，再逐层加深。
