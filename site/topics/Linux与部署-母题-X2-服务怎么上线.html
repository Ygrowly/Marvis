题目

某服务发版时，每次滚动更新都会有少量请求失败（大概千分之几）。日志里看不到异常，监控上就是"发版那两分钟错误率抬升"。为什么？另外：服务启动时数据库还没就绪，容器直接崩了，反复重启——这该怎么处理？

一 · 教材 从前提推到结论，不需要先会

1. 前提：上线的成败取决于"怎么退出"

1.1 两个方向，两个难点【推导】

【推导】上线包含"起"和"停"两件事，而它们的难点完全不同：

启动停止
难点依赖没就绪（DB / Redis / 配置中心还没好）在途请求还没处理完
代价起不来（能发现）丢请求（难发现）
常见错法依赖没就绪就退出，然后被反复重启收到停止信号就立刻退出

【推导】为什么"停止"更难：

启动失败 → 进程起不来 → 【有人立刻知道】
停止不当 → 进程优雅地退出了、日志一切正常 →
          但【那几百个正在处理的请求被丢了】→ 只有监控上的错误率抬升
→ 而"发版时错误率抬升"常被当成偶然，不被追责

【本卡开头的那个问题就是这一类型】 ——发版时千分之几的错误，就是"收到停止信号就退出"造成的。

1.2 信号：SIGTERM 与 SIGKILL【事实】

【事实】这两个信号的语义完全不同：

信号含义能不能被处理
SIGTERM（15）"请你收工" ——进程可以捕获它、做清理、然后自己退出✅ 可以捕获与处理
SIGKILL（9）"现在就走" ——内核直接终止，不能捕获、不能阻塞❌ 不可捕获、不可忽略

【推导】平台的停止流程几乎都是"先 15、后 9"：

停止指令 → 发 SIGTERM → 等【一段宽限期】（grace period）→ 还没退出 → 发 SIGKILL

【事实】宽限期的默认值随平台不同（属默认值，不是规范，具体要看你自己的配置）：

  • 容器运行时：通常是秒级到十几秒（例如 10 秒一类）
  • 编排平台：常见默认30 秒一类，且可配

所以优雅退出的时间窗不是"想设多少就多少" ——它被平台设定的宽限期卡住。你的退出逻辑必须能在宽限期内完成，否则会在最后被 SIGKILL 打断。

到这里你应该能回答：为什么应用里的优雅退出逻辑通常要"顺便主动告诉平台：我要退了"？

2. 优雅退出的四个动作（顺序不能乱）

2.1 四步【推导】

【推导】正确顺序是"先摘流量，再等排空，然后关依赖，最后才退出"：

#动作为什么必须在这一步
① 停止接收新请求从负载均衡 / 服务注册里摘掉自己（或把就绪探针置为失败）这是最关键的一步：不做的话，你一边处理在途请求、一边还在接新请求，永远排不空
② 等在途请求处理完设一个"最长等待时间"，等到都返回或超时这才是"优雅"的本体
③ 关掉对外依赖关连接池、提交 / 回滚事务、flush 缓冲在 ② 之后，因为 ② 里还要用它们
④ 退出进程主动 exit(0)，不必等 SIGKILL主动退出比被 SIGKILL 好：能控制退出码、能打完日志

【推导】① 为什么最容易漏：

如果不在负载均衡侧摘掉自己：
  发版时，LB 还在把新请求发给你
  你在等"在途请求变 0"，但新请求一直在进来
  → 永远等不到 → 宽限期到 → 【SIGKILL 杀掉一批在途请求】
→ 这就是"发版时错误率抬升"的机制

2.2 一个更隐蔽的点：异步任务与队列【推导】

【推导】HTTP 请求不是唯一的"在途工作"：

消费队列的 Worker：
  ① 停止拉取新消息
  ② 等当前这条处理完（或者主动把没处理完的【放回队列】）
  ③ 关闭连接
  ④ 退出

【取舍】这里要和"至少一次投递"配合（[[母题-Q2-重复与乱序]]）：退出时"没处理完的消息"应该让它重投，而不是标记为已处理——因为重复是安全的（有幂等），丢是不可接受的。

【事实】RuleArena 与 EnergyOps 都是这个思路：Worker 重启后先读权威状态再校准 Checkpoint（04-idempotency-and-recovery.md §9、07-task-lifecycle-and-delivery.md）——这说明它们的设计前提就是"进程会被随时拿走"，而不是"优雅退出一定做得到"。

到这里你应该能回答：为什么"进程会被随时杀掉"是设计前提，而不是异常情况？

3. 量化：时间窗该怎么算

3.1 优雅退出的时间窗【推导】

【推导】时间窗的算式：

优雅退出时间窗 > 停止接线生效时间 + 最长在途请求时间 + 清理时间

【推导】代进数字算一遍（自测 Q1 完整算）：

最长在途请求时间（P99.9）：800 ms
停止接线生效时间（LB / 注册中心把状态同步下去）：约 1 s
清理（关连接池、flush）：200 ms
→ 时间窗至少 ≈ 1 + 0.8 + 0.2 = 【2 s】

如果平台宽限期只有 10 s，那 2 s 足够，还能留余量；
如果某个接口【设计上就可能跑 30 s】（比如导出），
→ 它一定会被 SIGKILL 打断 → 【这种接口不该阻塞退出】

【取舍】结论："长任务"不应该在退出路径上等 ——它应该被设计成"可中断 + 可恢复"：

长任务：停止接新任务 → 把当前进度写下来（checkpoint）→ 主动退出
        → 恢复时从 checkpoint 继续（[[母题-A4-长任务状态与Checkpoint]]）

3.2 启动：依赖没就绪怎么办【推导】

【推导】三种做法，各有代价：

做法怎么做代价
① 启动重试连不上依赖就重试，有上限与退避起得慢；重试耗尽还是会失败
② 就绪探针（推荐）进程照常启动，但"就绪"状态先为"未就绪" ——收到流量前先自检依赖要有就绪探针这个概念（不能只靠"进程活着"）
③ 硬失败退出连不上直接退出，让平台重启会造成"重启风暴"：依赖越忙越重启，越重启越忙

【推导】② 为什么最好：它把"进程活着"和"能服务"分开了：

存活（liveness）   → 进程还在、没死锁   → 失败 → 【重启】
就绪（readiness）  → 依赖都通、能服务   → 失败 → 【暂时不接流量，不重启】
→ 关键区分：依赖没就绪时，【不该重启】，只该"暂时不接流量"

【取舍】探针设计错的两个典型后果：

就绪探针太严（把慢依赖也算进去）→ 依赖一抖，所有实例一起"不就绪"→ 全站不可用
存活探针太敏感（把"暂时不健康"当"死了"）→ 频繁重启 → 雪上加霜
→ 判据：就绪探针可以严（不接流量而已），存活探针必须【极其保守】（它会导致重启）

到这里你应该能回答：为什么"依赖不可用"应该表现为"暂时不接流量"而不是"重启"？

4. 边界与常见误解

常见说法修正
"发版时错误率抬升是正常的"【推导】不是正常的。千分之几的错误率抬升通常就是没有优雅退出（或没在 LB 侧摘流量）造成的——它是 bug，不是发版成本
"收到停止信号就 exit(0) 就行"【推导】会丢在途请求。正确顺序是先摘流量 → 等在途完成 → 关依赖 → 退出，且①摘流量最容易漏
"优雅退出做得好就一定不丢请求"【取舍】不能保证：宽限期到就 SIGKILL。所以长任务必须设计成"可中断 + 可恢复"，而不是指望"一定能优雅退完"
"进程活着就是服务可用"【事实】要分存活与就绪：存活失败 → 重启；就绪失败 → 暂时不接流量。混在一起会在依赖抖动时造成重启风暴或全站不就绪
"启动时依赖没就绪，多重启几次就好了"【取舍】可能变成重启风暴（依赖越忙越重启）。更好的做法是就绪探针 + 有上限的退避重试
"配置写死在镜像里就行"【取舍】要分清：镜像里放不变的东西（代码、依赖），环境相关的走环境变量 / 配置中心。配置中心引入了一个新的启动依赖——它不可用时要有兜底（本地默认值 / 上次成功的缓存）
"优雅退出只跟 HTTP 服务有关"【推导】队列消费者同样要：停止拉取 → 处理完当前 / 把未完成的放回队列 → 关连接 → 退出。关键是"没处理完的要让它重投，而不是标记成功"
"多实例滚动更新就不需要优雅退出了"【推导】反了：滚动更新恰恰让"摘流量"成了必须做的事——多实例的每一次替换都会触发一轮"摘流量 → 排空 → 退出"，做得不对就每次发版都掉一点请求

一句话结论 全卡唯一要背的锚点

上线的成败取决于"怎么退出"，不取决于"怎么启动"。正确的优雅退出顺序是 ① 先摘流量（从 LB / 注册中心摘掉，或让就绪探针失败）→ ② 等在途请求处理完 → ③ 关依赖（连接池、事务、缓冲）→ ④ 主动退出，其中 ①最容易漏（漏了就会"永远等不到没有在途请求"，最后被 SIGKILL 打断）。时间窗可以算：摘流量生效 + 最长在途请求 + 清理 ≤ 平台宽限期（SIGTERM 之后平台会等一段，超时就 SIGKILL——不可捕获、不可协商），所以长任务必须设计成"可中断 + 可恢复"（写 checkpoint 后主动退出，而不是撑着跑完）。启动侧的关键是分清两类探针：存活失败 → 重启（只检查进程自己，绝不查外部依赖）；就绪失败 → 暂时不接流量（不重启）——把依赖故障放进存活探针会造成"重启风暴"。队列消费者额外遵守一条：没处理完就不 ack，让它重投（重复由幂等吃掉，丢是不可接受的）。
  • 难点在"停止"不在"启动"
  • SIGTERM 可捕获（请你收工）、SIGKILL 不可捕获（现在就走）
  • 平台流程：15 → 宽限期 → 9
  • 四步：摘流量 → 排空 → 关依赖 → 退出
  • 摘流量最容易漏（否则永远排不空）
  • 时间窗 = 摘流量生效 + 最长在途 + 清理 < 宽限期
  • 长任务要可中断可恢复，不该进退出窗口
  • 存活（进程自己，失败→重启）vs 就绪（能服务，失败→不接流量）
  • 存活探针绝不查外部依赖（否则重启风暴）
  • 启动用退避重试而不是硬退出
  • 队列消费者：停止拉取 → 处理完
  • 不 ack 让它重投
  • 配置中心也是一个启动依赖，要有兜底

1. 优雅退出为什么要"先摘流量"？

否则会永远等不到"没有在途请求"：LB 还在发新请求，在途数不降反升，直到宽限期用完被 SIGKILL。这是"发版时错误率抬升"最常见的根因。

2. SIGTERM 和 SIGKILL 有什么区别？

SIGTERM 可被捕获（做清理后自己退出）；SIGKILL 不可捕获、不可忽略，内核直接终止。平台是"先 15、等宽限期、再 9"。

3. 存活探针和就绪探针怎么分工？

存活只管进程自身（死锁、卡死），失败重启；就绪表示"能服务"，失败只是不接流量。判断依据是"重启这件事能不能改善现状"——不能（依赖挂、下游慢）就绝不放存活。

4. 队列消费者怎么优雅退出？

停止拉取 → 处理完当前这条 → ack → 关连接 → 退出；宽限期内跑不完就【不 ack】，让它重投——重复由幂等吃掉，丢是不可接受的（[[母题-Q2-重复与乱序]]）。

5. 服务启动依赖服务没就绪怎么办？

有上限的退避重试 + 就绪探针（表现为"暂时不接流量"），不要"连不上就退出"——那会造成重启风暴。
  • 「滚动更新和优雅退出什么关系？」——滚动更新让"摘流量"成为必须：每次替换实例都会触发一轮"摘流量 → 排空 → 退出"，做错就每次发版掉一点请求（策略层面见 [[母题-E6-灰度发布与回滚]]）
  • 「为什么长连接（SSE）服务退出更麻烦？」——长连接意味着"在途"是长期存在的：必须主动向客户端发结束事件并让客户端重连，而不是等它自己断（[[母题-N2-SSE与推送模型]]）
  • 「配置中心挂了服务就起不来怎么办？」——配置中心也是一个启动依赖：要有本地兜底（默认值 / 上次成功的快照），否则它就成了新的单点
  • 「为什么"发版前预热"有用？」——启动期的第一批请求要付缺页、连接建立、缓存预热、JIT 的成本（[[母题-O2-虚拟内存与缺页]] 的 minor fault），预热就是把这段时间提前付掉

"进程会被随时拿走"是设计前提，不是异常情况。 所以正确的思路不是"把优雅退出做到完美"，而是让"被拿走"成为安全事件：在途请求要么完成、要么可重投；长任务要么可中断、要么可恢复；依赖不可用只影响"接不接流量"，不影响"进程是否活着"。
