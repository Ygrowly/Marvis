题目

线上有条 SQL 偶尔 20 多秒。你按什么顺序定位？深分页 LIMIT 1000000, 10 为什么慢，怎么改？

一 · 教材 从前提推到结论，不需要先会

1. 前提：所有优化都在做同一件事

让"扫过的行"尽量等于"要返回的行"。

两者差距越大越慢，差距只有两个来源：
  ① 没命中的扫描——该过滤的没提前过滤
  ② 白拿的回表——取回了不用的列 / 索引没覆盖

【推论】每一种优化手段都能归到这两类里——归不进去的，说明你还没搞清它在治什么。这也是后面那份清单的组织方式（少扫 / 少回 / 少排）。

2. 定位三步【事实】

① 慢查询日志（long_query_time）→ 把问题 SQL 抓出来
   先按【出现频率 × 单次耗时】排优先级——高频的中等慢比低频的极慢更值钱
② EXPLAIN 看计划 → 判断问题类型
③ 按类型动手 → 再 explain 验证，最后压测确认

EXPLAIN 四个字段的读法：

字段看什么
type访问方式，从好到坏：system > const > eq_ref > ref > range > index > ALL。ALL = 全表扫；index = 扫全索引（比 ALL 好一点，也危险）
key实际用的索引。possible_keys 有值但 key 为 NULL → 优化器主动放弃了（见第 5 节）
rows估算扫描行数——与实际差很远时说明统计信息/选择性有问题
ExtraUsing index（覆盖，好）/ Using filesort（额外排序）/ Using temporary（临时表）/ Using index condition（下推生效）

到这里你应该能回答：为什么定位的第一步是"排序"，而不是"看到一条慢 SQL 就改"？

3. 优化手段清单（按"少扫 / 少回 / 少排"归类）

3.1 少扫：让过滤更早发生【事实】

  • 最左前缀设计：等值列在前、范围列在后（[[母题-M2-联合索引与最左前缀]]）
  • 能用定位键就不要用偏移量：WHERE id > ? 而不是 LIMIT 1000000, 10
  • 不要 SELECT *：列少了，优化器才可能选覆盖索引

3.2 少回：让索引自己回答完【事实 + 推导】

  • 覆盖索引：把 SELECT 的列都放进索引（[[母题-M3-聚簇索引与回表]]）
  • 索引下推 ICP（5.6+）：(age, name) 索引下，age=18 AND name LIKE '%三' 可以在索引层先过滤 name——把"符合条件才回表"变成"索引层就过滤掉不合格的"。EXPLAIN 里显示 Using index condition。

ICP 的收益能算出来：

索引 (age, name)，age=18 命中 10,000 行，其中 name LIKE '%三' 只命中 100 行

无 ICP：10,000 行全部回表，再在 server 层过滤 name → 10,000 次回表
有 ICP：索引层先过滤 name → 只回表 100 行

降 100 倍

【推论】ICP 治的是"回表次数"，不是"扫描量"——扫过的索引项没变，变的是"哪些需要回表"。关键词永远是"回表次数"。

3.3 少排：避免额外排序与临时表【事实】

  • 让索引顺序匹配 ORDER BY（索引本身有序，天然省 filesort）
  • 小表驱动大表：in / exists 的选择、JOIN 的驱动表顺序（[[母题-M6-一条SQL的执行链路]] 算过 1000 倍的差别）
  • GROUP BY 尽量走索引列，避免临时表

几个"知道就行"的点：count(*) ≈ count(1) > count(列)（要判空）；count(*) 没有捷径，InnoDB 是真数（只有 MyISAM 有行数缓存——但业务表不该用 MyISAM）。

到这里你应该能回答：为什么"加了索引但还是慢"经常是因为缺的不是索引，是覆盖？

4. 深分页为什么慢【推导】

LIMIT 1000000, 10 不是"取 10 行"
而是"取前 1,000,010 行，丢掉前 100 万行"

【推论】扫描与回表量 = 偏移量，所以越翻越慢——而且这是线性增长，第 100 万页的代价是第 1 页的 10 万倍。

4.1 两种解法【事实】

① 游标定位（首选）：记住上一页最后一条的排序键，下一页用条件跳过去

SELECT ... WHERE id > :last_id ORDER BY id LIMIT 10;   -- 恒定扫描 10 行

② 延迟关联：必须跳页时，先用覆盖索引把 id 捞出来，再回表取详情

SELECT t.* FROM task t
JOIN (SELECT id FROM task ORDER BY id LIMIT 1000000, 10) s ON t.id = s.id;

子查询走覆盖索引（只扫索引，不回表），回表只发生在最后 10 行上——把"100 万次回表"降成"10 次回表"。

4.2 两者的差别在哪【取舍】

① 游标定位：扫描量 100 万 → 10     、回表 100 万 → 10      （两个都降）
② 延迟关联：扫描量 100 万 → 100 万  、回表 100 万 → 10      （只降回表）

所以能拿到上一页排序键时，① 优于 ②。② 的适用场景是必须跳到任意页（用户直接点第 1000 页、或者外部传入 offset）时——它是"无法用游标"时的退路，不是首选。

到这里你应该能回答：为什么说"深分页的代价 = 偏移量"？

5. 优化器主动放弃索引（最容易被漏掉的一类）【推导】

现象：索引存在、条件也该走索引，EXPLAIN 却显示 key = NULL、全表扫。

原因：优化器估算过成本——当它判断"走索引 + 大量回表"比"顺序扫全表"更贵时，主动放弃索引是正确行为。典型触发：

  • 二级索引命中比例过高（比如要取 30% 的行）
  • 统计信息过期（行数/区分度估错）
  • 条件是表达式 / 函数 / 隐式类型转换（M2 的失效清单）

【取舍】排查顺序不能反：先看是不是"写法问题"（照 M2 的失效清单过一遍），再看是不是"成本判断"。后者的改法不是改 SQL，而是：

1. ANALYZE TABLE 更新统计信息 2. 用 FORCE INDEX 验证"走了索引确实更快"——确认判断确实错了再强推 3. 或者接受全表扫——命中比例高时它本来就是对的

【推论】这一条把"索引失效"从"背清单"升级成"理解优化器的成本模型"。 面试里能主动说出"有时候全表扫是优化器的正确决定"，比背出十条失效场景更能证明你懂原理。

到这里你应该能回答：为什么"有索引却没用上"不能直接判定为 bug？

6. 优化优先级（收口）

① 先缩小业务范围（别把不相关的行扫进来）
② 再修 JOIN 逻辑与 N+1
③ 再建/改索引（含覆盖索引、下推）
④ 再改写 SQL（深分页、排序、count）
⑤ 最后才考虑缓存、预聚合、架构（M15）

【事实】EnergyOps 的实际顺序就是这条：修范围与 JOIN → 建联合索引 → 消 N+1 → 才谈缓存。反过来做（先上缓存）是典型的"在错误的链路上加速"——缓存只是把慢查询挡住，慢查询本身还在那里，而且会随着数据增长变得更慢。

7. 边界与常见误解

常见说法修正
"索引失效一定是写法问题"不一定。有一类恰恰是优化器算过成本后主动放弃（命中比例过高时走索引+回表反而更贵）——这时全表扫是正确决定，要动的是统计信息或接受它
"深分页改成延迟关联就不慢了"只降回表，不降扫描量。能拿到上一页排序键时，游标定位（WHERE id > ?）两个都降，才是首选；延迟关联是"必须跳页"时的退路
"加索引能解决慢查询"只治三类慢源里的一类。回表多要靠覆盖索引，JOIN 顺序错要靠改写法/统计信息——加索引无效
"count(1) 比 count(*) 快"在 InnoDB 里基本一样。真正慢的是 count(列)（要判 NULL）。而 count(*) 慢的根因是 InnoDB 没有行数缓存、必须真数——不是写法问题，是机制问题
"ORDER BY 走了索引就不慢了"排序只占成本的一部分。排序走了索引只解决"少排"，不解决"少扫少回"——SELECT * 带来的大量回表照样拖慢
"优化就是把 explain 里的 type 调到 ref 以上"type 是结果不是目标。目标是"扫过的行 ≈ 要返回的行"，有时全表扫（ALL）反而是达成这个目标的方式（当条件命中 99% 时）

【取舍】读成一句话：先分类再动手——用 rows 估算 vs 实际判断"是不是优化器的问题"，用三种慢源判断"是哪一类问题"，最后才落到具体手段。

三 · 面试输出 闭卷口述 60 秒，再看结论

慢查询怎么定位？常见的优化手段各自在治什么——为什么"加个索引"只是其中一类？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是面试里"给一个真实案例"最容易出彩的题——因为它能同时展示：定位方法（有章法）、优化手段（有清单）、以及"索引失效不一定是写法错"这种反直觉判断。EnergyOps 的 20.4s → 2.8s 就是这条线的真实案例，必须能讲成"按顺序定位、按优先级动手"，而不是"我们加了个索引"。

一句话结论 全卡唯一要背的锚点

定位按三步走——慢查询日志（按"频率 × 单次耗时"排优先级）→ EXPLAIN 看计划（type / key / rows / Extra）→ 按类型动手再 explain 验证。所有优化手段围绕"少扫、少回、少排"：少扫靠最左前缀设计与不用偏移量；少回靠覆盖索引与索引下推 ICP（ICP 把回表从 10,000 次降到 100 次）；少排靠让索引顺序匹配 ORDER BY。深分页的代价 = 偏移量（LIMIT 1000000, 10 要扫 1,000,010 行），首选游标定位（扫描与回表都降到 10），必须跳页时才用延迟关联（只降回表）。最容易漏的一类：索引失效不一定是写法错——优化器算过成本后主动放弃，命中 99% 时全表扫比走索引快约 47 倍。所以最后有一条不可颠倒的优化优先级：先缩小业务范围 → 修 JOIN 与 N+1 → 再改索引 → 再改写 SQL → 最后才上缓存。
  • 三步定位
  • 四字段（type
  • key
  • rows
  • Extra）
  • 三种慢源（扫描多
  • 回表多
  • JOIN 顺序错）
  • 少扫少回少排
  • 覆盖索引
  • ICP 降的是回表量不是扫描量
  • 深分页代价 = 偏移量
  • 游标定位 vs 延迟关联（都降回表，只有前者降扫描）
  • 优化器主动放弃索引
  • rows 是估算、EXPLAIN ANALYZE 才是实际
  • count(*) 慢是 MVCC 的必然
  • 优先级：范围 → JOIN → 索引 → SQL → 缓存

展开（先自答，再看 · 默认收起，不进复训调度）

PG 的对应工具是 pg_stat_statements（按总耗时排序）+ EXPLAIN (ANALYZE, BUFFERS)（真执行），还能看 Heap Fetches；MySQL 靠慢查询日志 + EXPLAIN（8.0.18+ 才有 EXPLAIN ANALYZE）。Using index 在 MySQL 里表示覆盖索引，在 PG 里对应的是 Index Only Scan——名字完全不同，别串。

1. 怎么确认统计信息错了？

对比 EXPLAIN 的 rows（估算）与 EXPLAIN ANALYZE（8.0.18+）的实际行数；差一个数量级以上就该 ANALYZE TABLE。这条和 PG 的 [[母题-P7-统计信息与慢查询定位]] 是同一件事的两个实现。

2. 那条 20 多秒的 SQL 你具体怎么定位的？

按顺序讲：估计 vs 实际行数 → 扫描方式 → JOIN 规模 → 排序/临时表 → loops（N+1）。重点不是"发现了什么"，而是"为什么按这个顺序"——每一步都对应一个明确的修复动作，做完立刻验证，不会白做。这一段要练成 60 秒口述。

3. 索引下推解决了什么？

回表前先过滤。没有 ICP 时 (age, name) 只能用 age = 18 定位，所有 age=18 的行都要回表；有 ICP 后在索引层就过滤 name，回表次数大幅下降。关键词是"回表次数"。

4. in 和 exists 怎么选？

小表驱动大表：子查询结果集小用 in，外表小用 exists。not in 遇到 NULL 或无法利用索引时要换 not exists。

5. ORDER BY 没走 filesort 但还是很慢？

排序不是唯一成本：可能回表次数多（SELECT *），或者扫描范围太大。"少排"解决了不代表"少扫少回"解决了——三类要分开看。
  • 「一条 SQL 你会按什么顺序优化？」——就是第 6 节的五步。关键是把"先范围、再 JOIN、再索引、后缓存"这个顺序说成有理由的（范围与 JOIN 决定扫描量，索引只能加速已有的扫描）。
  • 「EXPLAIN 里 rows 很大就一定是坏计划吗？」——不一定。看的是"rows 与最终返回行数的比值"：如果 rows 是 100 万但返回 10 条（且没有更好的过滤手段），那才是问题；如果返回 90 万条，那 rows 大是必然的。
  • 「分区能替代这些优化吗？」——不能替代，只能补充（[[母题-M15-数据增长治理]]、[[母题-P16-分区表]]）。分区解决的是"整块数据根本不用碰"，前提是分区键出现在条件里。

- EnergyOps 的 20.4s → 2.8s（本场主战场）——口径见模块卡第 5 节：必须补齐样本数 / 并发 / 硬件 / 统计窗口。讲成"按五步顺序定位、按优先级动手"，而不是"我们加了个索引"。 - 数驭穹图的查询成本控制——每改一处都要 explain 验证 + 固定数据集对比，不能"感觉快了"。

先把目标说清（扫过的行 ≈ 要返回的行）→ 定位三步 → explain 四字段 → 三组手段各治什么（少扫/少回/少排，各带一个数）→ 深分页专讲（扫描量 = 偏移量）→ 优化器主动放弃索引（最反直觉的一类）→ 优化优先级五步 → 收束到"先分类再动手"

所有 SQL 优化都在做同一件事：让"扫过的行"尽量等于"要返回的行"。 差距只有两个来源：没命中的扫描（该过滤的没提前过滤）和白拿的回表（取回了不用的列）。每一种手段都能归到这两类里——归不进去的，说明还没搞清它在治什么。
