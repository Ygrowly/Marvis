题目

MySQL 有 redo / undo / binlog 三套日志，PG 只有一套 WAL。它是怎么保证「提交过的不丢」的？

主卡

在这里练也可以，评分会进训练台的复训调度。

为什么重要：这是「PG 与 MySQL 的七处差异」里最容易被追问到底的一处。表面问题只是「PG 用什么日志」，但深一层会问到「那它为什么不需要 undo」——答案在 MVCC（P13），所以这两道题是一对，答不上 P13 就讲不透 P11。

展开（默认收起，不进复训调度）

EnergyOps 的幂等补数（「重放不产生副作用」和 WAL 重放是同一个思路：先判断是否已做过）；RuleArena 的Checkpoint 与崩溃恢复（同样是「任务进度」和「业务事实」分开存——PG 这里也把「恢复起点」和「数据安全」分开了，是同一个设计原则）。方言差异（面试安全底线）：MySQL 是 redo（崩溃恢复）+ undo（回滚与 MVCC）+ binlog（复制与时间点恢复）三套；PG 只有 WAL一套。注意不要说「PG 的 WAL 相当于 MySQL 的 redo log」——WAL 同时承担了 redo、部分 binlog（通过逻辑解码）的功能，而 undo 那部分职能被 MVCC 结构替代了。

为什么需要 WAL（顺序写换随机写 + 崩溃安全）→ WAL 怎么保证已提交不丢 → checkpoint 在做什么 → 为什么 PG 只有一套日志（不需要 undo）→ synchronous_commit 的取舍 → 生产怎么配

WAL 管「已提交的能不能重放出来」（正确性），checkpoint 管「重放要从多久之前开始」（恢复时间）。 两件事，但它们由同一组参数牵动——checkpoint 越勤，恢复越快，常态 IO 压力越大。

正文底稿

原理分解

一、为什么需要 WAL

修改数据时不直接改磁盘数据页（随机 IO 太慢），而是：

改内存（shared_buffers 里的数据页）
  + 把「改了什么」顺序追加到 WAL
  ↓
提交时：fsync WAL（保证这次提交已落盘）
  ↓
数据页留在内存，稍后由后台批量刷盘

两个收益：① 把随机写换成顺序写（写入性能）；② 只要 WAL 落盘，即使数据页没刷、机器立刻断电，重启后也能重放出来（崩溃安全）。

关键在「提交时 fsync 的是 WAL，不是数据页」——这就是「提交很快但数据页还没落盘」却依然安全的原因。

二、synchronous_commit：唯一承诺的落盘点

值语义丢什么
on（默认）提交时等本事务 WAL fsync 完成才返回成功不丢已提交事务
off提交不等 fsync，让后台尽快刷可能丢最近若干毫秒「已提交」的事务
local / remote_apply 等与复制相关（见 P12）取决于复制配置

必须讲清的一点：off 丢的是「已经向客户端返回成功、但 WAL 还没落盘」的那部分——这是唯一一个「数据库告诉成功了却可能丢」的配置。所以：

  • 钱、订单、状态机等路径：必须 on；
  • 批量导入、可重建的埋点数据：可以临时 off 换吞吐，但要在业务层知道这件事，不是"顺手关了"。

三、checkpoint 在做什么

checkpoint 触发
  ↓
把「某个 LSN 之前」的所有脏页刷到磁盘
  ↓
在 WAL 里记一个 checkpoint 记录
  ↓
崩溃恢复时：从最近这个 checkpoint 开始重放 → 而不是从头

所以 checkpoint 的收益是「恢复时间」，不是数据安全。

它带来一个必须知道的副作用——full_page_writes：因为刷盘是「按页」但不是原子的（可能半页写失败），所以 checkpoint 之后对这些页的第一次修改，WAL 里要记整页内容（而不是「某偏移改了某个值」）。后果是：

  • checkpoint 越勤 → 「首写整页」发生得越频繁 → WAL 体积反而更大；
  • 所以「把 checkpoint 调很勤以缩短恢复时间」会用 WAL 写放大和 IO 抖动换恢复速度——这是 PG 调优里一个经典的两难。

四、为什么 PG 只有一套日志（不需要 undo）

MySQL 需要 undo 有两个原因：① 事务回滚；② 给 MVCC 提供旧版本。

PG 两个都不需要日志层面的 undo：

  • 旧版本：PG 的 UPDATE 是「写新版本 + 标记旧版本」（P13），旧版本本来就在堆里，读的时候按快照挑版本，不需要去 undo log 里拼；
  • 回滚：未提交事务的改动在崩溃恢复/回滚时，靠「这个版本的 xmin 属于一个未提交事务」判定为不可见即可，并且由 VACUUM 清掉。

代价：旧版本占用空间、必须靠 VACUUM 回收——于是「PG 没有 undo」这件事，直接解释了三件现象：

1. 为什么 PG 会表膨胀（P14）； 2. 为什么有 VACUUM 与事务 ID 回卷这种 MySQL 不存在的运维风险（P15）； 3. 为什么 长事务在 PG 里格外危险（它按住了快照，让回收停摆）。

这条是整条主线五的入口。

五、生产怎么配（说这段才像做过线上）

① 关键写路径：synchronous_commit = on（默认，别动）
② checkpoint 频率：先看 pg_stat_bgwriter 的 checkpoint 频率与刷盘量，
   再决定是放宽 checkpoint 间隔（减 IO 抖动）还是收紧（减恢复时间）
③ 恢复时间是可测量的：用 checkpoint 位置与 WAL 生成速率估算「最坏要重放多少」
④ 复制场景额外考虑：synchronous_standby_names（P12）

第 ② 步的方法论比结论重要：调 checkpoint 之前先拿 pg_stat_bgwriter 的数据说话，而不是「网上说 checkpoint 要调大」。
