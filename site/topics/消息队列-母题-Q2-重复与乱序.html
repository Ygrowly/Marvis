题目

下游说"这条消息我收到了两遍"，另有人说"我的订单状态更新反了——'完成'先到、'创建'后到"。这两件事是同一个问题吗？分别该怎么解？把消费端做成完全串行能不能一次性解决？

一 · 教材 从前提推到结论，不需要先会

1. 前提：重复和乱序其实是同一个根源

1.1 重复的三个来源【事实】

上一张卡（[[母题-Q1-消息为什么会丢怎么才不丢]]）证明了一件事："处理消息"和"记录处理进度"是两次独立操作，中间崩溃必有一件没做成。 想两件都不出错，需要 MQ 和业务数据库做分布式事务——代价高到没人付。

于是"重复"就从三个位置冒出来：

来源机制能不能在框架层杜绝
生产端重发消息已到 Broker，但返回 ack 时网络断了，生产者以为没成功又发一次❌ 生产者不知道对面到底收到没
消费端重投消费者处理完了，但提交进度之前崩了，重启后从上次进度重新拉❌ 这正是"宁重勿丢"的代价
Broker 侧重投已投递但未确认的消息，在超时、重平衡后被重新投给另一个消费者❌ 同上

【推导】三处都不可能在框架层杜绝，因为它们的根因是同一个：跨进程通信里"确认"这件事本身可能丢失。 所以所有主流 MQ 的一致选择是——

框架只保证 at-least-once（至少一次，宁重勿丢）
去重的责任交给业务层（幂等）
"至少一次" + "幂等" = "只生效一次" 的效果

最后一个等号是这一整张卡的核心：不是"实现恰好一次"，而是"让恰好一次的语义由业务来兜"。

1.2 乱序的来源：并行【推导】

乱序只有一个根源：为了吞吐把消息分散到多个通道并行处理了。

一个订单的三条消息：创建 → 支付 → 完成
如果分散到 3 个通道、3 个消费者并行处理：
  消费者 C3 先处理"完成"，C1 才开始处理"创建" → 顺序全乱

即使都在同一个通道里：
  消费者开了多线程处理 → 线程 1 拿到"创建"但处理慢，
  线程 2 拿到"支付"先处理完 → 还是乱

【推导】所以"顺序"和"并行"是同一枚硬币的两面：要顺序就必须在某些地方退回串行。关键判断不是"要不要串行"，而是"串到多细"——这就是第 3 节的量化，也是本卡最重要的一个算式。

到这里你应该能回答：为什么"重复"和"乱序"在面试里常常被问在一起？

2. 幂等：把"至少一次"消化成"只生效一次"

2.1 幂等的定义【事实】

幂等（idempotent） 是数学概念：f(f(x)) = f(x)——执行一次和执行多次，结果完全一样。

生活例子最好懂：

  • 电梯按钮是幂等的：按一次开门和按十次开门，门就开一次
  • "转账 100 元"不是幂等的：执行两次就变成转了 200 元

【推导】为什么工程上要它：分布式系统里，网络超时、消息重复、请求重试无处不在，你没办法保证一个操作只被执行一次。既然做不到"只执行一次"，就换个目标——不保证只执行一次，但保证执行多次效果一样。

2.2 所有幂等方案都在回答同一个问题【推导】

【推导】幂等方案看起来有五种，其实它们只是"查重方式"不同，问的都是同一句话：

"这个操作之前是不是已经执行过了？"

方案查重方式代价适合
唯一标识查重用业务键去 Redis / 数据库查有没有处理过每条消息一次查询最通用，首选
数据库唯一约束让数据库拦住重复插入（冲突就是重复）依赖事务边界插入型操作，最硬的兜底
乐观锁（版本号）UPDATE ... WHERE version = 1，第二次时 version 已变 → 更新 0 行要带版本号更新型操作（[[母题-M16-乐观锁与悲观锁]]）
状态机条件更新UPDATE ... WHERE status = 'PENDING'，第二次条件不成立要设计好状态流转状态推进型（订单 / 任务）
分布式锁同一时刻只让一个执行最重、有锁失效问题临界区互斥，不是幂等的首选

【取舍】生产上的常见组合是"Redis 查重 + 数据库唯一约束兜底"：Redis 挡掉绝大多数重复（快），唯一约束挡掉"Redis 查重和写入之间又被重放一次"的极端情况（硬）。只用 Redis 会漏，只用唯一约束会在数据库上多一轮冲突处理。

2.3 幂等键怎么选——这里是真正的考点【推导】

【推导】幂等键必须满足一个条件：同一个业务动作，重试时它能算出同一个值。

把这个条件当成筛子，就能筛掉最常见的两个错答案：

候选能不能当幂等键为什么
消息 ID / offset❌重投时换了新 ID，对不上——查重必然失效
ToolCallID / 请求 ID❌每次调用都重新生成，重试时变了一个新值（RuleArena 明确否掉过这个）
时间戳 / 自增号❌重试时不一样
业务主键（订单号 / 任务号）⚠️ 偏粗能查重，但"同一个订单"上可能有多个不同动作，会误判
业务动作指纹（业务主键 + 动作 + 目标 + 关键参数 + 版本/步骤）✅重试时全部参数不变 → 算出同一个键（RuleArena 的解法）

【事实】RuleArena 的原话：不把 ToolCallID 当业务幂等键，而是根据 run、动作、目标、参数、规则版本和逻辑步骤 构造稳定幂等键——因为在同一数据库事务里用唯一约束保证同一动作效果只发生一次。

【推导】为什么"偏粗"也要标出来：如果幂等键只用订单号，那么"订单 123 的创建"和"订单 123 的取消"会共用一个键——第二次会被当成重复而跳过，这就把"防重复"做成了"丢动作"。粒度必须对到"一次业务动作"，不是"一个业务实体"。

2.4 超时 ≠ 失败——幂等的前提条件被违反时最危险【推导】

【推导】一个必须单独强调的边界：幂等方案解决的是"重复到达"，解决不了"结果未知"。

调用下游超时了 → 三种可能，你分不清是哪一种：
  ① 请求根本没到
  ② 到了，执行失败
  ③ 到了，执行成功，但响应丢了  ← 最危险

如果你的代码把超时当失败换一个键重试，那么情况 ③ 就会真的执行两次——幂等键此时完全失效，因为它变了。

【事实】EnergyOps 的处理是原话：Worker 携带稳定业务幂等键调用通知平台；调用超时标记 result_unknown，不直接重试——平台支持幂等就用同一个键重试，否则先查询外部权威状态。RuleArena 同理：Worker 超时后不换 key 直接重试，先查 Receipt，已完成就继续，明确失败才按错误类型决定重试，仍无法确认就记 ACTION_UNKNOWN 并停止该分支。

到这里你应该能回答：为什么"用消息 ID 做幂等键"是一个看起来对、实际必错的答案？

3. 顺序：保序的粒度就是并行的粒度（量化）

3.1 两种串行的代价【推导】

先介绍两种方案，再用同一个指标衡量它们：

方案怎么串行后果
全局串行整个 Topic 只用一个分区 / 队列并行度 = 1，吞吐被单条处理时间锁死，且加机器也没用
局部串行把需要保序的那组消息（比如同一个订单）用业务键哈希到同一个通道，通道内串行、通道之间并行吞吐可以靠加通道水平扩展；代价是"每个业务键的吞吐上限"被锁死

【推导】判断依据只有一条：你要的顺序，是"同一个订单内的顺序"，还是"全局的顺序"？

  • 99% 的业务要的是前者（订单状态、账户流水、任务步骤）
  • 要后者时，先反问"全局有序是业务要求还是我图省事"——绝大多数情况下是后者

3.2 主线判据：算一次就够【推导】

把 "单条处理时间" 和 "需要的吞吐" 放到一起，两个问题同时有了答案：

单分区的吞吐上限 = 1 / 单条处理时间
需要的分区数     = 目标吞吐 / 单分区上限
每个业务键的吞吐上限 = 单分区上限（因为它只能落在一个分区里）

这就把"要不要分区、分几个"从感觉变成了算术（自测 Q1 会算一遍）。

【取舍】这里有本卡最容易被忽略的一句：即使你把分区加到 100 个拿了 100 倍吞吐，单个订单的处理速度上限仍是单分区那 200 TPS。保序的粒度就是并行的粒度——你要哪个粒度的顺序，就只能拿到那个粒度的并行。

3.3 双端的实现要点【事实】

生产者端必须能"按业务键路由"：

  • Kafka：给消息指定相同的 Key，同 Key 哈希到同一 Partition（分区内天然有序）
  • RocketMQ：实现 MessageQueueSelector，例如 orderId % queueCount

消费者端必须对同一通道单线程顺序处理——开了多线程就白做。

【事实】消费端的实现两家不同（这是可以加分的细节）：

KafkaRocketMQ
怎么保证一个通道只有一个消费者分区分配（一个分区同一时刻只分给组内一个消费者）对 MessageQueue 加锁（消费前先向 Broker 申请队列锁）
发生重平衡（消费者增减）时分区会重新分配，存在交接窗口锁机制保证不会出现两个消费者同时消费同一队列

【事实】RocketMQ 还区分两种顺序：普通顺序（Broker 正常时有序，某个 Broker 挂了消息会被转到别的队列而短暂乱序）和严格顺序（任何情况都有序，但 Broker 挂了对应队列就不可用）。"严格"的代价是可用性——和 Q1 里的选举取舍是同一类账。

3.4 生产者自己也会把顺序搞乱【事实】

【事实】这一点最容易被忽略，也最容易被追问：即使你把消息都发到同一个分区，生产者开启重试后，第一条发送失败重试时，第二条可能已经先写进去了。

Kafka 官方配置文档的规则：

max.in.flight.requests.per.connection > 1 且 enable.idempotence = false
  → 重试会导致消息重排
enable.idempotence = true（Kafka 3.0 起默认开启），且该值 ≤ 5
  → 顺序保持（broker 最多保留 5 个批次）

【事实】所以要"有序 + 不丢"这一对目标，配置是三件一起给：enable.idempotence=true + acks=all + max.in.flight.requests.per.connection ≤ 5（幂等要求 acks=all、retries>0、in.flight ≤ 5 三项同时成立，否则会直接抛配置异常）。

【纠错】顺带纠一个流行说法："把 linger.ms 调小就能避免乱序"是错的。linger.ms 只控制"攒多久才发"，和重试导致的重排无关——治不了根因。

4. 边界与常见误解

常见说法修正
"重复消费是 MQ 的 bug"【推导】是必然，不是 bug。框架只保证至少一次，因为"处理"与"记录进度"无法原子化。换个 MQ 不改变这个前提
"做幂等就是在框架里开个开关"【推导】幂等是业务层的事。框架能给的只有"至少一次"，去重必须落在你的业务键上
"用消息 ID 做幂等键"【推导】必错：重投时 ID 变了，查重永远不命中。要的是稳定业务键（业务键 + 动作 + 目标 + 参数 + 版本），粒度对到"一次动作"而不是"一个业务实体"
"超时就重试，反正有幂等"【推导】危险。超时是"结果未知"，换键重试会真的执行两次。幂等的前提是"用同一个键"——超时要么同键重试，要么先查权威状态
"加个唯一索引就幂等了"【取舍】方向对但不够：要把"唯一冲突"这个返回当成成功来处理（冲突即代表已生效），并且操作和记录要在同一个事务边界内，否则会出现"约束拦住了但业务状态没推进"
"顺序就是把分区设成 1"【推导】代价是并行度归零且不可水平扩展。正确做法是局部串行：按业务键哈希，通道内串行、通道间并行
"消费者多开几个就能更快消费同一队列"【事实】同一个队列同一时刻只能被一个消费者消费。多开的那些闲置——分区数是并行度的天花板（[[母题-Q3-积压与高可用]] Q1 会算这条）
"开了重试也不会影响顺序"【事实】会。enable.idempotence=false 且 in.flight>1 时重试会重排；3.0 起幂等默认开启，但要确认这个默认没被改掉
"调小 linger.ms 能避免乱序"【纠错】不能。linger.ms 只管"攒多久发"，和重试导致的乱序无关

一句话结论 全卡唯一要背的锚点

重复和乱序同源——重复来自"至少一次投递"（处理与记录进度无法原子化，三处来源框架层都杜绝不了），乱序来自"为了吞吐而并行"。解法是两个动作：① 幂等——用稳定的业务幂等键（业务键 + 动作 + 目标 + 参数 + 版本/步骤，不能用消息 ID 或 ToolCallID，重试时它们会变）做查重，Redis 查重挡大多数、数据库唯一约束兜底，并注意超时是"结果未知"、必须用同一个键；② 局部串行——按业务键哈希到同一分区 / 队列，通道内单线程消费、通道间并行，保序的粒度就是并行的粒度（单条 5ms → 单分区 200 TPS → 要 2000 TPS 就 10 个分区，但单键上限永远仍是 200 TPS）。
  • 至少一次 + 幂等 = 只生效一次
  • 重复三来源（生产重发、消费端提交前崩溃、Broker 重投）
  • 幂等 = "这个操作做过没"
  • 四类查重（唯一键 / 唯一约束 / 乐观锁 / 状态机）
  • 稳定业务键，不用消息 ID 和 ToolCallID
  • 幂等粒度对到"一次动作"不是"一个业务实体"
  • 超时≠失败，不许换键
  • 乱序源于并行
  • 局部串行：保序粒度 = 并行粒度
  • 单分区 TPS = 1
  • 单条耗时
  • 分区数是并行度天花板
  • 生产者重试也会乱序（幂等 + in.flight ≤ 5）
  • linger.ms 管不了乱序

  • 结论：至少一次 → 重复靠业务幂等；并行 → 乱序靠局部串行（保序粒度 = 并行粒度）。
  • 推导链：处理与记录进度无法原子 → 重复三来源 → 业务幂等键 + 唯一约束兜底 → 并行导致乱序 → 按业务键哈希 + 通道内单线程。
  • 量化：单条 5 ms → 单分区 200 TPS；10 分区 = 2000 TPS，但单键上限仍是 200 TPS；in.flight ≤ 5。
  • 边界与常见误解：消息 ID 不能当幂等键；超时不能直接重试（结果未知）；生产者重试会自己搞乱顺序。

| 同一件事 | Kafka | RocketMQ | RabbitMQ | |---|---|---|---| | 按业务键路由 | 消息 Key 哈希到 Partition | MessageQueueSelector（如 orderId % queueCount） | 按 RoutingKey / 交换机路由 | | 保证同通道只有一个消费者 | 分区分配（重平衡时有交接窗口） | MessageQueue 加锁（不出现交接窗口） | 单消费者（Single Active Consumer） | | 顺序的强弱档位 | 只保证分区内有序 | 普通顺序 / 严格顺序两档（严格档 Broker 挂则该队列不可用） | 队列内 FIFO |

1. 幂等键为什么不能用消息 ID？

重投时 ID 会变，查重永远不命中。要用业务动作指纹（业务键 + 动作 + 目标 + 参数 + 版本/步骤），保证"同一动作重试时算出同一个键"。粒度还要对到"一次动作"，只用订单号会把"创建"和"取消"混成一个键，反而把动作吃掉。

2. 超时之后能不能重试？

不能直接重试。超时是结果未知，下游可能已经执行成功。正确动作是用同一幂等键重试，或者先查下游的权威状态；两者都做不到就停下并记录 UNKNOWN，不要猜。

3. 生产者重试会不会把顺序搞乱？

会（enable.idempotence=false 且 in.flight>1 时）。正确配置是 幂等开启（3.0 起默认）+ acks=all + in.flight ≤ 5，既保序又不丢吞吐。in.flight=1 是保序但牺牲吞吐的退路。

4. Redis 查重挂了怎么办？

关键是不能只依赖一条查重路径：Redis 查重负责快，数据库唯一约束负责准。Redis 不可用时让唯一约束兜底，不要简单地 fail open（会重复）或 fail closed（会全量积压）。

5. 顺序消费的代价是什么？

并行度。同一条通道（分区 / 队列）同一时刻只能被一个消费者消费，分区数就是并行度的天花板；而单个业务键的吞吐上限 = 单分区上限，加分区也提不高它（热点键问题）。
  • 「Kafka 的 Consumer Group 是什么？」——组内分工（一个分区只给一个消费者）、组间独立（每个组各消费全量）；消费者数超过分区数，多出来的闲置（→[[母题-Q3-积压与高可用]]）
  • 「Kafka 怎么保证顺序消费？」——只保证分区内有序：生产者同 Key 路由到同分区，消费者对分区单线程消费，跨分区无法保证
  • 「exactly-once 到底能不能做到？」——Kafka 有事务 API，能在"Kafka → Kafka"的链路里做到（消费者 offset 提交放进生产者的同一个事务，下游用 read_committed 读）；但"-Kafka → 外部系统"仍然要靠幂等消费者。框架层的恰好一次只在"闭环在 Kafka 内部"时成立——这句话能答出来就明显高一个层次

RuleArena——稳定幂等键（run + 动作 + 目标 + 参数 + 规则版本 + 步骤）+ 同事务唯一约束 + 超时先查 Receipt，把"至少一次投递"消化成"业务副作用只生效一次"，是这张卡最完整的落地；EnergyOps——通知超时不换键、只用稳定业务幂等键重试或查外部权威状态，是"超时 ≠ 失败"的落地；数驭穹图——"无依赖子查询可以并发，但写回顺序必须确定"，是非 MQ 场景里的同一个"局部串行"问题。

先给前提"重复与乱序同源，都是至少一次 + 并行的产物" → 重复三来源 → 幂等的定义与"四类查重问的是同一个问题" → 幂等键怎么选（稳定业务键，两个反例） → 超时≠失败 → 乱序的来源 → 全局串行 vs 局部串行（同一指标：并行度）→ 量化"保序粒度 = 并行粒度" → 双端实现要点与生产者重试这个坑 → 边界与误解

"至少一次 + 幂等 = 只生效一次"是唯一可行的路线，而"保序的粒度就是并行的粒度"是唯一能算的判据。 前一句决定了"重复要去业务层解决"，后一句决定了"顺序不能靠全局串行换"。两句合起来，就是这一整个模块的设计边界。
