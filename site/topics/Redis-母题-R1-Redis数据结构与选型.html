题目

Redis 了解吗？它都有哪些主要的数据结构？ ZSet 底层是怎么实现的？为什么用跳表而不用 B+ 树？

一 · 教材 从前提推到结论，不需要先会

1. 前提：Redis 为什么快

1.1 第一个原因：数据在内存里

【事实】把量级摆出来（[[母题-M1-为什么用B+树]] 用过同一张表）：

访问典型延迟
内存随机访问约 100 纳秒
机械盘随机读约 10 毫秒

【推导】差 5 个数量级。这一条推出一件很关键的事：

磁盘系统里最重要的优化目标是"减少 IO 次数"（M1 的全部内容）；而 Redis 里没有磁盘 IO 可省——所以它优化的是别的东西。

记住这一条：第 4 节讲"为什么用跳表不用 B+ 树"时，它就是唯一答案。

1.2 第二个原因：单线程（但要先澄清"单"的是什么）

【事实】Redis 的"单线程"指的是：命令的执行是单线程的。

【推导】为什么单线程反而快——三个理由：

1. 没有锁竞争：不用为每个键加锁解锁（对比多线程模型要处理并发修改） 2. 没有上下文切换：避免线程切换的开销 3. 没有原子性问题：一条命令天然原子（这也是它适合做计数器、分布式锁的基础）

【事实】必须说清的边界（版本演进）：

版本变化
早期网络 IO 与命令执行都在同一个线程
Redis 6+网络 IO 用多线程（读写 socket、解析协议），命令执行仍然是单线程

所以"Redis 是单线程还是多线程"的准确答案是：命令执行单线程，网络 IO 在 6.0 之后是多线程。 只说"单线程"是旧答案，会被追问。

【推导】单线程的代价，直接推出下一件事：

一条慢命令会卡住所有人。 因为是单线程，一条 KEYS * 或大 key 的 DEL 执行期间，其他所有请求都在等。

【联系】这正是 [[母题-N3-进程线程与协程]] 里"协作式的代价"——一处阻塞，全体停摆。同一个道理，在进程、协程、Redis 三处重复出现。

1.3 第三个原因：IO 多路复用

【事实】Redis 用 epoll 这类机制，一个线程一次系统调用就能问出"成千上万个连接里哪些有数据了"（N3 第 3.1 节讲过同一个机制）。

三个原因合起来：内存（快）+ 单线程（无锁、无切换）+ 事件循环（一个线程管很多连接）。

2. 五种基础结构：各自是什么形状、解决什么

理解的方式不是背名字，而是问"它是一份什么形状的数据"。

结构形状典型场景
String一个值（字符串/数字/二进制）计数（INCR）、缓存单值、分布式锁（SET NX EX）、限流计数器
List有序、两端进出的线队列 / 栈（LPUSH+RPOP）、简单消息流、最近 N 条
Hash一个对象的一堆字段对象属性（购物车 key=cart:1, field=sku）、部分字段更新
Set不重复的集合，无序去重、交集并集（共同好友、抽奖去重）、标签
ZSet不重复的集合，但每个成员带一个分数，按分数排序排行榜、延迟队列（score 存时间戳 + ZRANGEBYSCORE 捞到期任务）、带权重的去重

【推导】五种结构的差别可以归纳成两个问题：

1. 要不要"有序"？ → 要排序用 List（按插入位置）或 ZSet（按分数） 2. 要不要"唯一"？ → 要去重用 Set 或 ZSet

所以选型就是这两问的组合：

要唯一 + 要按分数排序 → ZSet
要唯一 + 不要顺序     → Set
不要唯一 + 要顺序     → List
要按字段取子集        → Hash
就是个值              → String

2.1 Set 和 ZSet 的区别（9.9 漏掉的那一条）

【事实】Set 只存成员，ZSet 存成员 + 分数。

  • Set 的操围绕"有没有 / 交并差"
  • ZSet 的操围绕"排名 / 按分数范围取"

【推导】ZSet 多出来的那个"分数"，是它一切能力的来源：能排序、能取 Top N、能按分数区间捞。所以排行榜必须用 ZSet，用 Set 做不到。

3. 四种扩展结构（知道场景就够了）

结构是什么场景关键代价
Bitmap用位来表示"是/否"签到、日活打点、布尔标记稀疏数据浪费空间
HyperLogLog基数估算（不存原始数据）大流量 UV 去重计数有误差（约 0.81%），不能取回原始元素
Geo存经纬度并做距离查询附近的人 / 附近的门店精度依赖底层 ZSet 编码
Stream带消费组的消息流中小规模事件流、任务分发与 Kafka 的持久化/分区/生态差距明显

【取舍】HyperLogLog 最值得记的一点：它用"接受误差"换"固定的小内存"——统计 1 亿 UV，内存也就十几 KB。这是"用精度换空间"的典型取舍。

4. ZSet 的底层：跳表 + 哈希表，以及为什么不用 B+ 树

4.1 为什么是"两个结构"

【事实】ZSet 内部同时用了两样东西：

组件支撑什么操作
哈希表（member → score）按成员 O(1) 查分数（ZSCORE）
跳表（按 score 排序）按分数范围 / 排名 O(log N)（ZRANGE、ZRANGEBYSCORE）

【推导】两个结构是为了支撑两类完全不同的查询。这也解释了为什么"ZSet 既能查某个人的分数，又能取 Top 100"——两件事走两条路径。

4.2 跳表是什么

定义：跳表（Skip List）= 有序链表 + 多层稀疏索引。查询从最上层开始：

能往右就往右（目标更大），不能往右就往下一层
→ 比较次数从 O(n) 降到期望 O(log n)

关键设计：每一层是否出现是随机的（约 1/2 概率向上）。

【推导】这说明它不需要重平衡——而平衡树（AVL / 红黑树）在插入删除后必须旋转来维持平衡。这是跳表"实现简单"的根本原因。

4.3 为什么不用 B+ 树（本题的落点）

【推导】用 M1 的判据反推：

B+ 树的全部优势来自一句话——"一次磁盘 IO 的成本几乎固定，所以让每次 IO 尽量多带数据回来"（扇出大 → 树矮 → IO 少）。

但这个前提在 Redis 里不成立：

B+ 树的主场（MySQL）Redis
数据在哪磁盘内存
瓶颈是什么磁盘 IO 次数比较与内存访问
扇出的价值极高（一次 IO 带回一页）几乎为零（没有 IO 可省）
代价节点分裂/合并（重平衡）跳表用随机层数替代，不需要重平衡

【推导】内存里没有"IO 分摊"这回事，所以 B+ 树最大的优势失效了，只剩下"实现复杂"这个缺点。

那为什么不用红黑树 / AVL？【取舍】它们能用，但：

  • 平衡操作复杂（旋转、维护颜色）
  • 范围查询不如跳表自然（跳表底层的链表天然支持顺序遍历）

准确的说法：不是"跳表比 B+ 树快"，而是"B+ 树为磁盘设计，它的优势在内存里用不上；而跳表实现更简单、范围查询更自然"。 这个分寸比"跳表更快"准确得多。

5. 怎么答才拿分：每个结构配一个你的场景

【取舍】9.9 这道题丢分的关键不是"漏了哪个结构"，而是"没有给出任何一个自己用过的场景"——听起来像背书。

所以每个结构都要能挂上真实场景（面试时挑 2–3 个讲，不要全报）：

结构可以挂的场景
String限流计数器（INCR + EXPIRE）、接口幂等键（SET NX）、短期去重标记
Hash缓存一个对象的多个字段，只更新其中一两个字段（不用整对象重写）
Set短期去重（"这个请求处理过没有"）、标签集合
ZSet延迟队列（score = 到期时间戳，ZRANGEBYSCORE 捞到期任务）、按权重的优先级队列
Stream中小规模的任务分发与消费组

（面试话术的结构）：先给"五种基础 + 四种扩展"的总览（一句话一个），再挑 1–2 个展开讲你项目里怎么用的。总览证明覆盖面，展开证明真用过。

6. 边界与常见误解

常见说法修正
"Redis 是单线程的"【事实】准确说法：命令执行单线程，网络 IO 在 6.0 后是多线程。 只说"单线程"是旧答案
"跳表比 B+ 树快"【推导】不是快慢问题：B+ 树为磁盘 IO 设计，它的优势在内存里用不上；而跳表实现更简单、范围查询更自然
"单线程所以不会有并发问题"【推导】单条命令原子，但多条命令的组合不原子（GET 完再 SET 之间可能插进别的请求）→ 需要 INCR/Lua/SET NX 这类原子操作
"Redis 什么都能缓存"【取舍】它适合缓存"派生数据"，不适合当权威状态（[[母题-R3-缓存一致性与三类事故]]）
"Hash 就是 ZSet 少了个排序"【事实】两者形状完全不同：Hash 是"字段→值"的映射（按字段取），ZSet 是"成员→分数"的有序集合（按分数取）
"HyperLogLog 能精确统计 UV"【事实】它是估算，标准误差约 0.81%，且不能取回原始元素。换来的是固定的小内存

一句话结论 全卡唯一要背的锚点

Redis 快在三点——数据在内存、命令执行单线程（无锁、无切换）、IO 多路复用；注意 6.0 之后网络 IO 是多线程，只有命令执行仍是单线程。五种基础结构按"要不要唯一 + 要不要顺序"选：String / List / Hash / Set / ZSet；另有 Bitmap、HyperLogLog（估算 UV，有误差）、Geo、Stream 四种扩展。ZSet 底层是"跳表 + 哈希表"——哈希表支撑按成员查分数，跳表支撑按分数取范围与排名；用跳表而不用 B+ 树，是因为 B+ 树的优势（减少磁盘 IO）在内存里用不上，而跳表不需要重平衡、范围查询更自然。
  • 内存（差 5 个数量级）
  • 命令执行单线程 + 网络 IO 多线程
  • 单线程的代价是慢命令卡所有人
  • 选型两问（唯一？有序？）
  • ZSet = 跳表 + 哈希表
  • 跳表的层数随机所以不需重平衡
  • B+ 树为磁盘设计、内存里优势失效
  • HyperLogLog 用误差换空间
  • 每个结构都要挂一个自己的场景

展开（先自答，再看 · 默认收起，不进复训调度）

1. Redis 是单线程还是多线程？

命令执行单线程，网络 IO 在 6.0 之后是多线程。 后台任务另有线程/子进程。

2. 单线程为什么还快？

无锁竞争、无上下文切换、单条命令天然原子；加上内存访问快、epoll 一次管很多连接。

3. 单线程有什么代价？

一条慢命令卡住所有人（KEYS *、大 key 的 DEL）。所以有"慢命令禁用清单"和"大 key 治理"。

4. ZSet 为什么用跳表不用 B+ 树？

见 Q5：不是快慢，是约束。

5. HyperLogLog 精确吗？

不精确，标准误差约 0.81%，用它换的是固定的小内存。

6. Redis 能当消息队列吗？

能用 List / Stream 做中小规模；但持久化、分区、重放、生态与 Kafka 差距明显，不能因为"已经用了 Redis"就默认替代（[[母题-R3-缓存一致性与三类事故]]）。
  • 「ZSet 还能做什么？」——延迟队列（score = 到期时间戳）、带权重的优先级队列、滑动窗口限流（score 存时间戳 + ZREMRANGEBYSCORE 清窗口外）
  • 「Hash 和 String 存对象哪个好？」——只改部分字段用 Hash（避免整对象序列化重写）；整个对象一起读写用 String（更省内存、少一次 field 开销）
  • 「怎么发现大 key / 热 key？」——redis-cli --bigkeys、SCAN 采样、监控命令耗时；线上更可靠的是慢日志 + 代理层统计

RuleArena 的短期去重与限流（SET NX + EXPIRE、INCR）；EnergyOps 的元数据缓存；数驭穹图 的限流与口径缓存。共性：Redis 负责"加速"和"短期标记"，不负责"裁决"。

快的三个原因（内存 / 单线程 / 事件循环）+ 版本澄清 → 五种基础结构按"唯一 + 有序"两问选型 → 四种扩展结构及各自代价 → ZSet 为什么是两个结构 → 跳表是什么、为什么不需要重平衡 → 为什么不用 B+ 树（约束变了） → 每个结构配一个自己的场景

"该用什么结构"由"数据是一份什么形状的内存数据"决定，而不是由"哪个结构更高级"决定。同理，"该用什么索引结构"由"瓶颈是 IO 还是比较"决定——约束变了，答案就变了。
