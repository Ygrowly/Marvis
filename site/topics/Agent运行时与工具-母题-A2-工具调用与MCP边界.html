题目

面试官问——"你们的 Agent 有多少个工具？怎么定的？工具描述怎么写？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：Agent 的 affordance 和传统软件不一样

【事实】Anthropic 原文点出的最常见错误：

"A common error we've observed is tools that merely wrap existing software functionality or API endpoints—whether or not the tools are appropriate for agents."

【推导】差别在哪：

传统软件程序：内存便宜且充足
  → 可以一次取出全部数据，再在程序里逐条处理

LLM Agent：上下文有限且昂贵
  → 如果工具返回全部联系人，它只能【token by token 读过去】
  → 等于拿有限的上下文做【暴力搜索】

【事实】原文给了一个很直观的类比：

"imagine searching for a contact in your address book by reading each page from top-to-bottom—that is, via brute-force search"

【推论】人找通讯录不会从头读到尾——会先翻到那一页。所以工具设计的目标不是"暴露能力"，是"让 agent 用接近人的方式完成任务"。

到这里你应该能回答：为什么"我们能调的通路都封装成工具了"不是一句好话？

2. 原则一：按工作流做，不按 API 做【事实】

【事实】原文给的三组对照（这三组可以直接背）：

✗ list_users + list_events + create_event
✓ schedule_event        （自己找可用时间并排期）

✗ read_logs
✓ search_logs           （只返回相关行 + 一点上下文）

✗ get_customer_by_id + list_transactions + list_notes
✓ get_customer_context  （把该客户的近期相关信息一次性汇总）

【推导】consolidation 的收益有两层：

① 减少调用次数   → 少几步、少几轮上下文累积
② 把中间产物搬回工具内部 → 【这些中间产物本来会进 agent 的上下文，现在不进了】

【推论】第 ② 条才是关键：一次 list_transactions 返回的 100 条流水，如果只是为了让 agent 数个数，那这 100 条就白占了上下文。 把它合进 get_customer_context，计数在工具内部完成。

【事实】原文对判据的表述：

"Make sure each tool you build has a clear, distinct purpose. Tools should enable agents to subdivide and solve tasks in much the same way that a human would, given access to the same underlying resources, and simultaneously reduce the context that would have otherwise been consumed by intermediate outputs."

2.1 工具响应会被平方放大【推导】

一个工具返回 5,000 token 的原始日志，40 轮会话里有 10 次这样的调用

这 10 × 5,000 = 50,000 token 会【留在历史里】
之后的每一轮都要把它重发一遍（[[母题-C1-上下文组装与窗口预算]]）

在剩余 30 轮里被重发：50,000 × 30 = 1,500,000 token 的额外输入
成本（Opus 5，$5/MTok）= 1.5M × $5 / 1M = $7.5

【结论】工具响应的代价不是"这一次调用花了多少 token"，而是"它进了历史之后，被重发了多少次"。

【推论】改成 search_logs 只返回 500 token（1/10），就能省下约 $6.75。

【事实】所以原文建议对任何可能吃上下文的响应实现：分页、范围选择、过滤、截断，并给合理的默认值。Claude Code 把工具响应默认限制在 25,000 token。

到这里你应该能回答：为什么"工具返回得多一点，信息更全"在 Agent 里反而更差？

3. 原则二：命名空间【事实】

【事实】原文的观察：

"Your AI agents will potentially gain access to dozens of MCP servers and hundreds of different tools… When tools overlap in function or have a vague purpose, agents can get confused about which ones to use."

【事实】两种命名空间方式：

按服务：asana_search、jira_search
按资源：asana_projects_search、asana_users_search

【事实】一个反直觉的实测结论：

"We have found selecting between prefix- and suffix-based namespacing to have non-trivial effects on our tool-use evaluations. Effects vary by LLM."

【推论】前缀还是后缀，对评测有实质影响，而且因模型而异——所以这个选择要靠自己的评测定，不能照搬。

【事实】原文还列了四种工具调用失败（这四种可以直接当追问的答案）：

① 调错工具
② 调对了工具但参数错
③ 工具调用太少（没查够就下结论）
④ 工具响应处理错误

【推论】命名反映任务的天然切分，能同时降低四类失败——因为它减少了加载进上下文的工具数与描述长度，把计算从"agent 的上下文"搬回"工具调用本身"。

4. 原则三：返回什么，取决于"接下来还需不需要它"【推导】

【事实】原文给的同一份数据的两种响应（Slack 线程）：

详细版（206 token）：含 thread_ts / channel_id / user_id
  → 这些 ID 是【发起后续调用所必需的】

精简版（72 token）：只有线程内容，不含 ID
  → 省了约 2/3 的 token

【推导】所以"该返回什么"的判据不是"信息全不全"，是：

模型接下来还需不需要用这些字段发起新调用？
  需要 → 返回 ID 类字段（详细版）
  不需要 → 只返回内容（精简版）

【事实】还有一条容易被忽略的：响应的结构（XML / JSON / Markdown）本身会影响评测表现——原文说没有万能解，因为模型是按 next-token prediction 训练的，对匹配训练数据的格式表现更好，要按自己的评测选。

【事实】错误响应也要"可行动"：

"…prompt-engineer your error responses to clearly communicate specific and actionable improvements, rather than opaque error codes or tracebacks."

【事实】一个真实的例子：Claude 的 web search 工具上线时，它会在 query 参数里无意义地加上 "2025"，影响搜索结果——修法是改工具描述，不是改模型。

【推论】这两条合起来说明一件事：工具的描述、参数、返回、错误，全都是"给模型看的界面"——它们不是文档，是可调优的输入。

到这里你应该能回答：为什么"工具报错返回一个错误码"是不合格的？

5. 原则四：怎么知道工具做得好不好——用 Agent 评估 Agent【事实】

【事实】原文的流程：

① 先做一个 prototype（别一上来设计完美工具集）
② 跑评测
③ 和 agent 一起打磨工具（"with agents"）

【事实】要收集的指标：

顶层准确率
单个工具调用的耗时
任务总耗时
工具调用总次数
总 token 消耗
工具错误

【推导】每个指标对应一类可行动的诊断：

冗余调用多      → 分页或 token 上限的参数需要调整
参数无效的错误多 → 描述不清或缺少示例
工具调用次数异常 → 可能有一批工具总是连着用 → 【合并的机会】

【推论】最后一条特别值："工具调用总次数"这个指标能暴露出"经常被连起来调用的工具组合"，那就是 consolidation 的候选。

到这里你应该能回答：为什么"重新设计工具"这件事不能靠拍脑袋，而要先跑评测？

6. 边界与常见误解

常见说法修正
"工具越多能力越强"反了。原文原话："More tools don't always lead to better outcomes"。重叠或用途含糊的工具会分散 agent 的注意力，而且每个工具的描述都占上下文
"把现有 API 全部封装成工具就行"这是最常见的错误（原文点名）。传统软件内存充足、可以遍历全部数据；agent 只能 token by token 读。list_contacts 会逼 agent 暴力搜索，search_contacts 才是对的
"工具返回的信息越多越好"响应会被平方放大：5,000 token 的日志在 40 轮里被重发 30 次 = 1.5M token ≈ $7.5。要分页 / 过滤 / 截断 + 合理默认值（Claude Code 默认上限 25,000 token）
"报错就返回错误码"要"可行动"：原文明确要求清楚地传达具体的、可改进的信息，而不是不透明的错误码或堆栈。错误响应也是给模型看的界面
"命名前缀还是后缀无所谓"有非平凡的影响，而且因模型而异（原文实测）。要按自己的评测选，不能照搬别人的命名方案
"工具描述写清楚就行，不用给示例"对新一代模型，示例反而会限制探索空间（[[母题-C3-Prompt版本管理与回归]]）——更好的做法是设计接口本身（枚举值、参数命名、默认值）。"光是列出枚举值就在提示怎么用"
"工具集设计是一次性的"原文的流程是"prototype → 评测 → 和 agent 一起打磨"。"工具调用总次数"这个指标能暴露"总被连着调用的组合"——那就是下一次 consolidation 的候选

【取舍】读成一句话：工具不是"能力的暴露面"，是"给模型看的界面"——它的描述、参数、返回、错误都要按 agent 的 affordance 设计，而不是按 API 的形状包装。

工具太多的三种代价：每个描述都占上下文（30 个约 6,000 token/请求，每轮都付且注意力层面没有折扣）、重叠或含糊让 agent 分不清该用哪个、选错概率上升。手段是 consolidation + namespacing + 延迟加载（defer_loading，把少用工具移出缓存前缀）。

1. 工具数量多了会怎样？

三种代价：① 每个工具的描述都占上下文（30 个 ≈ 6,000 token/请求，每轮都付，且注意力层面没有折扣）；② 重叠或含糊的工具让 agent 分不清该用哪个；③ 选错的概率上升。手段：consolidation + namespacing + 延迟加载（defer_loading，把少用工具移出缓存前缀）。

2. MCP 解决什么问题，边界在哪？

MCP 是工具接入的标准化协议（把"每个客户端各写一套集成"变成"一次实现、多处复用"）。边界：MCP 只统一了"怎么暴露和调用"，没有统一"该不该暴露"——工具的职责划分、权限边界、返回设计仍然是你的事（[[母题-A6-沙箱权限与可信执行]]）。

3. 工具描述该怎么写？

清晰、具体、有边界。但对新一代模型，给示例反而可能限制探索空间（[[母题-C3-Prompt版本管理与回归]]）——更好的做法是设计接口本身：把 status 做成 pending / in_progress / completed 的枚举，光是列出来就在提示怎么用。

4. 怎么知道该合并哪些工具？

看"工具调用总次数"这个指标：经常被连着调用的工具组合，就是 consolidation 的候选；冗余调用多说明分页/token 参数要调；参数无效的错误多说明描述不清或缺示例。
  • 「工具返回的结果要不要缓存？」——要区分"确定性工具"和"有副作用的工具"。只读且参数相同 → 可以缓存；有副作用的工具缓存等于跳过执行（[[母题-A3-失败恢复与幂等]]）。而且缓存要按租户 / 权限分区（[[母题-G6-知识更新与增量索引]]）。
  • 「工具太多，全给模型 vs 按意图路由给一部分，怎么选？」——按评测定，但先天的判据是"意图能否可靠地判断"。数驭穹图的意图路由就是这个思路：先判断意图（RAG / NL2SQL / 直接回答），再给对应的工具子集。路由错了后面全错，所以路由本身的准确率要单独评测。

- EnergyOps：30 个 MCP 工具 + 6 类 Capability Bundle——Bundle 的作用是控制"每次请求加载哪些工具定义"（Q2 的 6,000 token 账）；哪些该延迟加载、哪些该合并，判据是本卡的"中间产物是否进上下文"。 - 数驭穹图：意图路由——先判断意图再给工具子集，本质是"用路由换上下文与选择准确率"。

先破"包装 API"（给 affordance 的差别）→ consolidation 三组例子 + 收益的两层 → 命名空间 → 响应设计（206 vs 72 + 判据）→ 错误响应要可行动 → 平方放大的成本算式 → 评测指标与"调次数暴露合并机会" → 收束到"工具是界面"

工具的每一个面（描述、参数、返回、错误）都是"给模型看的界面"。 所以设计判据不是"API 长什么样"，是"模型要分几步、中间产物占多少上下文"——能一步做完、中间结果不外露的工具，比功能更全的工具更好。
