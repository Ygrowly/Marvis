题目

WHERE status='PENDING' FOR UPDATE 明明只想锁几行，为什么插入被卡住了？多个 Worker 还互相锁住了。为什么？

一 · 教材 从前提推到结论，不需要先会

1. 前提：读的问题已经被解决了，剩下的是写

1.1 谁还需要锁

【推导】[[母题-M9-MVCC]] 已经把读从冲突里摘出去了：普通 SELECT 走快照读，不加锁。

所以还会打架的只剩两种：

关系为什么必须管
写 vs 写两个事务改同一行，后写的会盖掉先写的 → 必须排队
当前读 vs 写FOR UPDATE / UPDATE 读的是最新版本，不能再靠快照糊弄 → 必须排队

由此得到一条判据：只有"当前读"才需要讨论锁。 普通 SELECT 谈锁是谈错了对象。

1.2 锁加在什么上（本题题眼）【事实】

这是全卡最重要的一句定义：

InnoDB 的锁加在「索引记录」上，不是加在「数据行」上。

【推导】为什么？因为 InnoDB 是索引组织表（[[母题-M3-聚簇索引与回表]]）——"行"这个概念在存储层就是"某个索引上的一条记录"。锁必须有一个"可寻址的对象"，能寻址的只有索引项。

这一条定义会直接推出后面的一切：

  • 如果一个 WHERE 条件没有可用的索引 → 只能全表扫描 → 扫过的每一条记录都要加锁 → 等价于锁全表
  • 如果走的是范围扫描 → 扫过的那一段都要加锁，不只是结果集里的那几行

到这里你应该能回答：为什么"行锁"这个名字容易让人误会？

2. 三种锁（先各自介绍，再比较）

2.1 Record Lock（记录锁）【事实】

锁什么：索引上的一条记录本身。 什么时候用：等值命中唯一索引（WHERE id = 123）。 范围：一条。这是锁最小的情形。

2.2 Gap Lock（间隙锁）【事实】

锁什么：两条索引记录之间的"空隙"（不含两端的记录本身）。

为什么需要它【推导】：因为幻读要防的不是"已有的行"，而是"还不存在的行"。

锁住已有行只能防止别人改那些行；别人完全可以"插入"一条新行，让范围查询的结果集变大。既然要防的是"插入"，就必须锁住"允许插入的位置"——也就是记录之间的空隙。

代价：它锁住的比你要的多。 为了防幻读，它把"你可能插入的地方"一起锁了——这就是"锁变大"的元凶。

2.3 Next-Key Lock（临键锁）【事实】

锁什么：记录本身 + 它前面的那个间隙（左开右闭）。

为什么要有这个组合【推导】：如果只用 Gap Lock，那么已被命中的那几条记录本身就没被保护（别人还能改）。所以 RR 下的默认加锁单位是"间隙 + 记录"的组合——既防插入，也保护已有记录。

三种锁的关系一句话：

锁覆盖防什么
Record Lock一条记录改这一行
Gap Lock一个空隙往空隙里插入
Next-Key Lock空隙 + 记录上面两件一起

2.4 一个必须先说清的边界【事实】

间隙锁主要存在于 RR（及串行化）下。RC 下【搜索与索引扫描】不再加间隙锁。

【事实】官方的原话有一个常被漏掉的例外：

间隙锁可以被显式关闭——把隔离级别改成 READ COMMITTED 就会关闭它。 这种情况下，间隙锁在搜索和索引扫描中被禁用，只在【外键约束检查】和【重复键检查】时仍然使用。

【推论】所以"RC 下没有间隙锁"这句话要说全：

RC 下：
  搜索 / 索引扫描 → 【不加】间隙锁（这是最常被问的那一半）
  外键检查 · 重复键检查 → 【仍然加】

→ 说"RC 下完全没有间隙锁"不准确；
  说"RC 下查询不再因为间隙锁被卡住插入"才是准确的那一半

【推导】所以隔离级别直接决定了锁的行为：

  • RC 下：不会"因为间隙锁把插入卡住"，但会有幻读
  • RR 下：插入可能被卡，但幻读被挡住

这把 M8（隔离级别）和 M10（锁）连起来了："默认 RR" 这个选择的代价，就是用"插入可能被卡"换"幻读被挡住"。

3. 锁为什么会变大：把它算出来

3.1 指标：被锁住的索引记录数

要比较不同写法的代价，用同一个指标：这次加锁一共锁住了多少条索引记录（含间隙）。

3.2 量化对比

场景：一张 100 万行的表，其中 status = 'PENDING' 占 20%（约 20 万行）。

写法扫描路径被锁住的量
WHERE id = 123 FOR UPDATE（唯一索引等值）精确定位1 条记录，0 间隙
WHERE status = 'PENDING' AND next_retry_time <= NOW() FOR UPDATE（走 (status, next_retry_time)）索引范围扫描约 20 万条记录 + 它们之间的间隙
WHERE priority = 3 FOR UPDATE（priority 没有索引）全表扫描100 万条记录 + 所有间隙 ≈ 锁全表

【推导】同样是"更新 pending 任务"这件事，锁的量可以从 1 条膨胀到 100 万条——差 6 个数量级。

3.3 三个原因（都指向同一句话）

原因例子
① 不是唯一索引精确命中走主键/唯一索引等值 → 锁得小；换成状态扫描 → 直接放大到万级
② 索引路径不精确优化器没选到合适的索引 → 扫描了更多记录 → 锁跟着变大
③ 范围条件天然高危<= NOW()、BETWEEN、非唯一状态过滤 → 带出 gap / next-key lock

三者的共同原理就一句话：

它锁的不是"最终返回给你的那几行"，而是"扫描到的索引范围"。

所以线上的典型现象是：明明只查了几条，插入却被卡住——因为被锁的是"扫过的区间 + 间隙"，新插入的行恰好落在某个被锁的间隙里。

4. 死锁：从"循环等待"推出来

4.1 定义【推导】

死锁 = 多个事务持有资源的同时，又都在等对方释放，形成环。

事务 A：先锁任务 1，再锁任务 2
事务 B：先锁任务 2，再锁任务 1
   ↓
A 等 B 放 2，B 等 A 放 1 → 环 → 谁都不动

【推导】关键不是"锁太多"，而是"顺序不一致"。同样的两个资源，只要所有事务按同一顺序拿，就不会成环。

4.2 InnoDB 怎么处理【事实】

它会主动检测死锁，并回滚其中"代价较小"的那个事务。

【推导】所以死锁的表现通常是"某次请求报 Deadlock found"，而不是系统整体卡死——这一点要说清，很多人以为死锁 = 数据库挂了。

代价较小怎么判断：InnoDB 比较两个事务的修改行数（undo 记录量），选回滚成本低的那个。这是"牺牲小的"策略，不是"牺牲后到的"。

5. 怎么避免，怎么排查

5.1 五条手段（每条都对应上面某个机制）

① 让查询命中更精确的索引      → 直接缩小"扫描范围"（3.3 原理的直接应用）
② 缩小事务范围                → 持锁时间短，成环窗口小
③ 事务里不放 RPC / 网络 / 复杂计算 → 别让锁在外等待时被白占（M13）
④ 多个事务按一致顺序访问资源   → 消除循环等待（4.1 的根因）
⑤ 队列式场景用 SKIP LOCKED    → 用查询语义替代等待

5.2 SKIP LOCKED 值得单独讲【取舍】

任务抢占场景里，很多 Worker 都在捞同一批任务。传统做法是排队等锁——后来者要等前面的处理完。

SELECT ... FOR UPDATE SKIP LOCKED 让后来者直接跳过被锁住的行："别人正在处理的，我不碰"。

【推导】这本质上是用"查询语义"替代了"等待"：

做法N 个 Worker 抢 M 个任务
不加 SKIP LOCKED所有 Worker 排队串行，后面的等前面释放
加 SKIP LOCKED每个 Worker 直接拿到还没被锁的那批，等待 ≈ 0（除非全部被锁）

代价：拿到的不是"最前面的 M 个"，而是"当前可用的 M 个"——如果业务要求严格按优先级处理，SKIP LOCKED 会破坏这个顺序。这是它的适用边界。

5.3 排查工具

工具看什么
SHOW ENGINE INNODB STATUSLATEST DETECTED DEADLOCK 段：两个事务各持有什么锁、在等什么、执行到哪条 SQL
performance_schema.data_locks / data_lock_waits当前持有的锁与等待关系（查正在发生的阻塞）
information_schema.innodb_trx正在运行的事务（找长事务，M13）

排查顺序【推导】：先看"谁在等谁"，再回溯"事务的加锁顺序"——最终答案几乎总是两条之一：顺序不一致，或事务太大（扫得太宽）。回到 5.1 的 ① 和 ④。

6. 边界与常见误解

常见说法修正
"行锁就是只锁一行"【推导】锁的是扫描到的索引记录范围。非唯一索引 + 范围条件能锁到万级；没有索引时锁全表
"RR 下一个普通 SELECT 也会加锁"【事实】不会。它是快照读（M9），不加锁。只有当前读才加锁
"死锁说明数据库有问题"【取舍】死锁是应用侧访问顺序不一致的症状。InnoDB 会检测并回滚代价小的事务，表现是某次请求报错，不是系统挂掉
"共享锁和排他锁是两种粒度"【事实】类型与粒度是两个维度：S/X 是类型（读锁/写锁），Record/Gap/Next-Key 是粒度。FOR SHARE 加 S 锁，FOR UPDATE 加 X 锁，两者都在某个粒度上
"InnoDB 也有表锁"【事实】InnoDB 以行级锁为主，另有表级意向锁（IS/IX）——意向锁的作用是"声明行锁意图"，让表锁请求不必逐行检查
"PG 也有间隙锁"【事实】PG 没有间隙锁。它靠快照 + 必要时报序列化失败（40001）让应用重试。"PG 有间隙锁"和"MySQL 不需要间隙锁"都是明确错误（[[母题-P10-无间隙锁与锁变体]]）

一句话结论 全卡唯一要背的锚点

三种锁——Record Lock 锁记录本身；Gap Lock 锁记录之间的空隙（防插入，是防幻读的必要手段）；Next-Key Lock 把两者合起来，是 RR 下的默认单位。锁加在索引记录上，所以锁的范围等于"扫描到的索引范围"，不是"WHERE 里写的行"——非唯一索引、范围条件、缺少索引都会把锁放大到万级甚至全表。死锁 = 多个事务的加锁顺序不一致形成环，InnoDB 会检测并回滚代价小的事务。避免靠精确索引 + 短事务 + 一致顺序 +（队列场景）SKIP LOCKED。
  • 只有在当前读才谈锁
  • 锁加在索引记录上
  • Gap Lock 是为防插入
  • Next-Key = 间隙 + 记录
  • 间隙锁只在 RR 有
  • 锁范围 = 扫描范围
  • 无索引 → 锁全表
  • 死锁 = 顺序不一致不是锁太多
  • 回滚代价小的那个
  • SKIP LOCKED 把排队变分流
  • SHOW ENGINE INNODB STATUS

展开（先自答，再看 · 默认收起，不进复训调度）

1. 为什么唯一索引等值命中不产生间隙锁？

精确命中后，没有"下一个需要保护的间隙"：唯一约束已经保证了不会再有相同的键插进来。所以这是锁范围最小的情形——这正好呼应了 M5"主键要精确"。

2. 为什么这个场景你项目里没用 FOR UPDATE？

（RuleArena 的取舍）任务认领是低频写，而状态扫描是范围条件（正好命中 3.3 的 ③）：用 FOR UPDATE 会锁大 + 有死锁风险 + 要排队三样一起来。条件更新（乐观锁，M16）一次原子写解决，重复执行第二次影响 0 行。 这正是"锁机制"决定工程选择的实例。

3. RR 下 SELECT 不加锁，那为什么还会有死锁？

死锁来自当前读（UPDATE / FOR UPDATE）和写操作的加锁顺序，与快照读无关。

4. 间隙锁能不能关掉？

【取舍】可以（把隔离级别降到 RC），代价是接受幻读。这是"用正确性换并发"的又一次交换（M8 的谱系）。
  • 「S 锁和 X 锁的区别？」——S 之间兼容；S 与 X、X 与 X 互斥。注意 S/X 是"类型"，Record/Gap/Next-Key 是"粒度"，两个维度别混
  • 「表锁、页锁、行锁？」——InnoDB 以行级锁为主 + 表级意向锁（声明行锁意图，让表锁请求不必逐行检查）
  • 「为什么报表查询在 MySQL 下不会互相锁？」——普通 SELECT 是快照读，不加锁；但它会持有 ReadView（M13）

RuleArena 的任务认领与退款（条件更新替代 FOR UPDATE）；EnergyOps 的采集任务重跑（多 Worker 抢同一窗口——"条件更新 + 唯一约束"比"锁定读"更合适）。
