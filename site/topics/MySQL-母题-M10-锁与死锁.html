正文底稿

原理分解

一、三种锁：各锁什么

锁锁什么谁在用
Record Lock索引记录本身等值命中唯一索引
Gap Lock两条记录之间的"区间"（不含记录本身），阻止往这个区间插入RR 下的范围查询
Next-Key Lock记录 + 它前面的间隙（左开右闭），RR 下的默认加锁单位RR 下的当前读

关键理解：Gap Lock 的存在理由就是"防幻读"——锁住区间，别人插不进来，下次查询行数就不会变。而它也是"锁大"的元凶：为了防幻读，它锁住的比你要的行多。

另一个必须知道的边界：间隙锁只在 RR（及串行化）下存在；RC 下没有间隙锁，所以 RC 下不会"因为 gap 锁把插入卡住"，但会有幻读。隔离级别决定了锁的行为——这把 M8 和 M10 连起来了。

还有一个精度细节：锁是加在索引上的。如果 WHERE 条件没有可用索引，InnoDB 只能全表扫描并把所有记录都锁住（相当于锁全表）——"什么时候锁全表"的答案就是这里。

二、锁为什么会变大（raw 的三条 + 原理）

原因例子
① 不是唯一索引精确命中WHERE id=? FOR UPDATE（唯一索引等值）锁得小；换成状态扫描就大了
② 索引路径不精确没走到合适的索引，扫描了更多记录，锁跟着变大
③ 范围条件天然高危<= now()、BETWEEN、非唯一状态过滤——带出 gap / next-key lock

原理一句话（本题题眼）：

它锁的不是最终返回给你的那几行，而是扫描到的索引范围。

所以线上的典型现象：明明只查了几条，插入却被卡住——因为被锁住的是"扫过的那些索引记录 + 它们之间的间隙"，新插入的行恰好落在某个间隙里。

三、死锁怎么来

死锁不是"数据库坏了"，而是多个事务拿锁顺序不一致，形成循环等待：

事务 A：先锁任务 1，再锁任务 2
事务 B：先锁任务 2，再锁任务 1
   ↓
A 等 B 释放 2，B 等 A 释放 1 → 循环等待

InnoDB 会自动检测死锁并回滚其中代价较小的事务（不是永远等下去）——所以死锁的表现通常是"某次请求报 Deadlock found"，而不是系统卡死。

四、怎么避免（raw 的五条 + 一条补充）

① 让查询命中更精确的索引          → 缩小锁范围（本题第一条原理的直接应用）
② 缩小事务范围                    → 持锁时间短，窗口小
③ 避免长时间持锁                  → 事务里不放 RPC / 网络 / 复杂计算（M13）
④ 多个事务按一致顺序访问资源       → 比如总是按主键升序更新，消除循环等待
⑤ 队列式场景用 SKIP LOCKED        → 直接跳过被别人锁住的行，不排队

SKIP LOCKED（8.0+）值得专门讲：任务抢占场景里，多个 Worker 都在捞同一批任务，传统做法是排队等锁；FOR UPDATE SKIP LOCKED 让后来者直接跳过被锁住的行——"别人在处理的任务我不碰"，天然适合队列。这条是"用查询语义替代等待"的一个漂亮例子，也是 raw 里点名的思路。

五、怎么排查

工具看什么
SHOW ENGINE INNODB STATUSLATEST DETECTED DEADLOCK 段：两个事务各自持有什么锁、在等什么锁、执行到了哪条 SQL——死锁分析的起点
performance_schema.data_locks / data_lock_waits当前正在持有的锁与等待关系（实时排查阻塞）
information_schema.innodb_trx正在运行的事务（找长事务，M13）

排查的正确顺序：先看是谁在等谁（锁等待），再回溯事务的加锁顺序——最终答案几乎总是"顺序不一致"或"事务太大"（回到核心不变量）。
