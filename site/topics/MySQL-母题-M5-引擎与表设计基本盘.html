题目

让你从零设计一张「任务表」——几十亿行、读写混合、以后还要按状态和时间捞任务。你会怎么选引擎、主键和字段类型？为什么不用 MyISAM？

一 · 教材 从前提推到结论，不需要先会

1. 前提：表设计只在回答三个问题

写入路径顺不顺、存储紧不紧凑、以后改不改得动。 所有具体选择（引擎、主键、字段类型）都服务这三件事——说得出它服务哪一条，才算真选过，而不是背过。

2. 候选方案一：MyISAM vs InnoDB

2.1 差异只有三条硬的【事实】

维度MyISAMInnoDB
事务不支持支持（ACID）
锁粒度表级锁（写锁全表）行级锁 + MVCC
崩溃恢复不支持（靠 repair）redo/undo 保证 crash-safe
索引结构非聚集索引：索引文件与数据文件分离，叶子存物理地址索引组织表：主键即数据，二级索引叶子存主键值（要回表）
外键不支持支持

2.2 为什么 InnoDB 成了默认【推导】

不是"因为它更先进"，是因为写并发一上来，表级锁会让所有写请求排队：

MyISAM 的写锁是全表级 → 同一张表上两个写事务必须串行

再加上没有事务、没有崩溃恢复（崩溃后要靠 repair 扫全表，还可能丢数据），它只适合读多写少、且可以重建的数据（日志、统计中间表）。

【推论】"业务表一律 InnoDB"不是偏好，是被"并发写 + 不能丢数据"这两条需求逼出来的。

【事实】顺带一个高频追问：「MyISAM 和 InnoDB 的 B+ 树实现差在哪？」——答上表第四行：MyISAM 叶子存地址（还要再去数据文件捞一次），InnoDB 主键叶子存整行、二级索引叶子存主键。这一条正是 [[母题-M3-聚簇索引与回表]] 的起点。

3. 候选方案二：主键选什么

3.1 为什么强烈建议自增【推导】

B+ 树的叶子按主键有序，所以"新行插在哪"完全由主键决定：

自增主键：新记录永远追加到最右边 → 顺序写
          写满就在右边开新页，对已有数据几乎无影响

随机主键（UUID / 随机串）：新记录插到中间
          → 为保持有序要搬数据、触发【页分裂】

页分裂的损失有三层（每一层都要能说出来）：

1. 分裂是同步的写操作，直接抬高写入延迟 2. 分裂后两页各约半满 → 索引不紧凑 → 同样的数据占更多页（下一页会算） 3. 顺序写变成随机写，失去 B+ 树最大的性能来源

3.2 把"占多少页"算出来【推导】

5000 万行 · 行宽 1KB · 页 16KB（每页约 16 行）

自增（填充率≈100%）：5000万 × 1KB ÷ 16KB = 312.5 万页
随机（填充率≈50%）：5000万 × 1KB ÷  8KB = 625 万页

【结论】同一份数据，主键选错就多占一倍页。而且影响不止磁盘——缓存能装下的页数减半，读也会跟着变慢。

3.3 还有一笔：主键会被复制很多份【推导】

二级索引的叶子存主键值，主键越长，所有二级索引越大：

给 status(INT 4B) 建索引，记录头按 6B 估：
  主键 BIGINT(8B)： 4 + 8 + 6 = 18B/条
  主键 UUID(36B)：  4 + 36 + 6 = 46B/条   → 2.6 倍

每建一个二级索引，都在为主键长度重复付费（详细算式见 [[母题-M4-索引代价与大表变更]]）。

【取舍】什么时候可以不用自增？ 当业务没有天然自增键、且需要分布式唯一时（比如分库分表要全局唯一 ID），用雪花算法这类趋势递增的 ID——它保住了"大致有序"，比纯随机的 UUID 好得多。这是权衡，不是破例，而且要主动说出它的两个代价：① 趋势递增不是严格递增，跨节点时钟回拨仍可能插到中间；② 64 位 ID 比 8 字节的 BIGINT 更长，二级索引体积会变大。

到这里你应该能回答：为什么"用 UUID 当主键"这件事不是"技术上可行所以没问题"？

4. 候选方案三：字段类型

4.1 varchar vs char【事实 + 推导】

charvarchar
长度定长，不足用空格补齐变长，按实际长度分配
额外开销无1–2 字节记录实际长度
适用长度固定：手机号、MD5(32)、性别、状态码长度不确定：用户名、地址、备注

算一下差多少：

char(10) 存 'a'      → 占 10 字节（空格补齐）
varchar(10) 存 'a'   → 1 字节内容 + 1 字节长度 = 2 字节
差 5 倍

5000 万行 × 8 字节的差 = 400 MB

【推论】判断标准只有一句：长度是不是真的固定。 只要长度不确定，char 就是白扔空间。

【事实】一个坑：char 尾部会补空格，比较时可能表现出 'a' 与 'a ' 的差异——别用 char 存会被拼接或比较的值。

4.2 DATETIME vs TIMESTAMP【事实 + 推导】

DATETIMETIMESTAMP
存什么字面的日期时间Unix 时间戳（秒）
时区与时区无关（存什么就是什么）受时区影响（按会话时区换算）
字节84
范围1000–9999 年1970–2038
默认值NULL可 CURRENT_TIMESTAMP，支持自动更新

2038 这个数能当场算出来：

TIMESTAMP 用有符号 32 位存秒
最大秒数 = 2,147,483,647

2147483647 ÷ (365.25 × 24 × 3600) = 2147483647 ÷ 31,557,600 ≈ 68.05 年
1970 + 68.05 → 2038 年 1 月（准确说是 2038-01-19 03:14:07 UTC）

【推论】"为什么不用 TIMESTAMP 存所有时间"这个问题，答案是可以当场算给面试官看的。

【取舍】怎么选：需要跨时区或自动记录创建/更新时间 → TIMESTAMP；需要大范围日期（生日、合同到期、业务上的远期时间）→ DATETIME。注意代价不对称：选 TIMESTAMP 省了 4 字节/行，但换来一个 2038 的硬边界——低价值的省空间不值得换一个定时炸弹。

4.3 约束、范式与三条删除语句【事实】

  • 常用约束：主键（唯一且非空）、唯一（唯一但可有 NULL）、非空、默认值、外键、CHECK。主键和唯一的区别就是"是否允许 NULL"。
  • 三范式：1NF 列不可再分；2NF 非主键列完全依赖整个主键（针对联合主键）；3NF 非主键列之间不能有传递依赖。反范式的唯一理由是可测量的读性能——比如事实表冗余园区快照以避免一次 JOIN。先有执行计划，再谈反范式。
语句类型能回滚删什么速度
DELETEDML可以表结构留着，可带 WHERE 删部分行慢（逐行）
TRUNCATEDDL不可以清空全部行，结构保留快（重建）
DROPDDL不可以表结构、数据、索引、权限全删最快

到这里你应该能回答：为什么"表设计"这个看起来很主观的问题，其实每一问都有可算的答案？

5. 边界与常见误解

常见说法修正
"MyISAM 读更快，读多的表用它"只有"读多写少 + 无事务需求 + 数据可重建"三者同时成立才勉强成立。一旦有并发写，表级锁就让写排队；崩溃还可能丢数据
"UUID 全局唯一又方便，为什么不能用"它有两笔代价：① 随机插入 → 页分裂 → 页数翻倍；② 36B 被复制进每个二级索引（单个索引膨胀 2.6 倍）。分布式唯一可以用趋势递增的雪花 ID，不必用纯随机 UUID
"char 比 varchar 快，所以都用 char"只在长度真的固定时才成立。长度不定时 char 要补齐空格，char(10) 存 'a' 占 10 字节而 varchar(10) 只占 2 字节——差 5 倍
"TIMESTAMP 省空间，全用它"省 4 字节/行，换来 2038-01-19 硬边界。远期时间（合同到期、生日）必须用 DATETIME
"主键选不对只是慢一点"不止慢：页数翻倍（磁盘 + 缓存）、写入随机化、所有二级索引一起变胖。它是唯一一个"改一次影响全表所有索引"的设计决策
"雪花 ID 是自增的替代品，一样好"是折中不是替代：趋势递增≠严格递增（时钟回拨仍可能乱序），而且位数更长。要主动说出这两个代价，才显得是权衡过而不是抄的

【取舍】读成一句话：引擎、主键、字段类型这三类选择，都只在回答"写入顺不顺、存储紧不紧凑、以后改不改得动"——答不出付了什么代价，就等于没选过。

MyISAM 和 InnoDB 差在哪？建表时主键、varchar/char、DATETIME/TIMESTAMP 该怎么选——每一个选择背后付的是什么代价？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是最高频、也最容易被轻视的一类题。它不难，但答"知道"和答"选过"是两回事——面试官问它是为了确认：你建的表现在会不会埋雷（主键用 UUID 导致页分裂、时间字段选了 TIMESTAMP 结果 2038 年溢出）。而且它是后面所有索引题的前置：不懂 InnoDB 是索引组织表，就讲不清回表。

一句话结论 全卡唯一要背的锚点

选 InnoDB 是因为它的三条硬差异——支持事务、行级锁、崩溃恢复——正好对应业务表的三个硬要求；MyISAM 只适合"读多写少 + 无事务 + 数据可重建"。表设计的三条硬规则都有可算的依据：主键用自增（随机主键导致页分裂，填充率降到约一半、页数翻倍，还让缓存能装的页减半）、长度不定用 varchar（char(10) 存 'a' 占 10 字节 vs varchar(10) 占 2 字节，差 5 倍）、远期时间用 DATETIME（TIMESTAMP 只有 4 字节，2^31−1 秒 ÷ 31,557,600 ≈ 68 年，2038-01-19 溢出）。另外主键会被复制进每一个二级索引——BIGINT→UUID 让单个索引从 18B/条涨到 46B/条。
  • 三条硬差异（事务
  • 行锁
  • 崩溃恢复）
  • 索引组织表 vs 非聚集索引（叶子存主键 vs 存地址）
  • 自增=顺序写，随机=页分裂
  • 填充率 100%→50% → 页数翻倍 → 缓存减半
  • 主键被复制进每个二级索引，18B→46B
  • char 补空格、varchar 存长度（2 字节差 8 字节）

展开（先自答，再看 · 默认收起，不进复训调度）

1. 页分裂到底损失什么？

① 分裂是同步写，抬高写入延迟；② 分裂后两页各约半满，同样的数据占更多页，范围扫描读更多页、缓存命中率下降；③ 顺序写变随机写，失去 B+ 树最大的性能来源。

2. 那用趋势递增的雪花 ID 不就好了？

可以，但注意两点：① 趋势递增不是严格递增，跨节点时钟回拨仍可能插到中间（概率远小于 UUID）；② 全局唯一 ID 通常位数更长（64 位），二级索引体积会变大。要接受这两个代价才叫权衡过。

3. char 和 varchar 谁快？

单看存取，定长略快（省长度字节、不用变长解析）；但只要长度不固定，char 浪费的空间远超这点收益。判断标准只有一句：长度是否真的固定。

4. 为什么 MySQL 有 DATETIME 还要 TIMESTAMP？

因为 TIMESTAMP 省一半空间、且带时区语义与自动更新，适合"创建/更新时间"这类只关心过去与现在的字段。代价是 2038 边界——所以它和时间范围是绑定的取舍，不能当通用时间类型。

5. InnoDB 相比 MyISAM 在索引实现上差在哪？

MyISAM 是非聚集索引：索引文件与数据文件分离，叶子存物理地址，查到后还要再去数据文件捞一次；InnoDB 是索引组织表：主键叶子存整行、二级索引叶子存主键值，所以要回表（[[母题-M3-聚簇索引与回表]]）。
  • 「MySQL 支持哪些存储引擎？」——InnoDB（默认）、MyISAM、Memory（内存表，重启即失）、Archive（高压缩，只插不查）。考官想听的是"为什么默认是 InnoDB"，不是背名单。
  • 「字段类型怎么选？」——够用就好：能用 INT 不用 BIGINT，能用定长不用变长；别用字符串存时间，也别用浮点存金额（用 DECIMAL）。
  • 「InnoDB 和 MyISAM 谁快？」——读多写少且无事务需求时，MyISAM 的表扫描可能更快；但只要涉及并发写、事务、恢复，InnoDB 全面胜出。承认这一点比硬吹 InnoDB 更显水平。

- EnergyOps：四层事实表的粒度与冗余设计、时间字段选型——按本卡的判据走。 - 数驭穹图：元数据表（Schema 登记）需要用大范围时间，所以 DATETIME 而不是 TIMESTAMP。

引擎三条硬差异 → 为什么 InnoDB 成默认（并发写 + 不能丢） → 主键必须自增（页分裂的三层损失 + 页数翻倍算式）→ 主键被复制进每个二级索引（18B vs 46B）→ varchar/char（5 倍差 + 补齐陷阱）→ DATETIME/TIMESTAMP（当场算 2038）→ 约束与范式（反范式要有执行计划支撑）

表设计不是审美问题，是"写入路径顺不顺、存储紧不紧凑、以后改不改得动"的问题。 而这三件事里，主键选型的影响面最大——它是唯一一个"改一次就影响全表所有索引"的决策。
