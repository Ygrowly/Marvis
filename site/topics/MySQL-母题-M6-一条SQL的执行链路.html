题目

一条 SELECT * FROM task WHERE status='PENDING' LIMIT 10 从客户端发出到结果返回，中间经历了哪些步骤？每一步都可能因为什么变慢？

三 · 面试输出 闭卷口述 60 秒，再看结论

MySQL 的 server 层和引擎层各管什么？优化器在做什么决定？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是"会用 SQL"和"能定位慢 SQL"的分界线。它同时是 M7 的前提——你必须先知道"慢可以慢在哪几层"，explain 里那些字段才有意义（type 是优化器选的访问方式、rows 是它的估算、Extra 是执行器阶段的附加动作）。背得出分层没用，能把"某一层慢"对应到"某个现象"才有用。

一句话结论 全卡唯一要背的锚点

连接器（鉴权与连接管理）→ 分析器（词法/语法解析）→ 优化器（选索引、选 JOIN 顺序、生成执行计划）→ 执行器（按计划逐行调用引擎接口）→ InnoDB 引擎层（Buffer Pool、索引、事务）→ 返回。server 层管"功能与计划"，引擎层管"数据怎么存怎么取"；慢的根源通常只有三种——扫描行数多、回表次数多、JOIN 顺序错。

展开（先自答，再看 · 默认收起，不进复训调度）

1. 「优化器怎么估行数？」

按索引的区分度（基数）统计：SHOW INDEX 的 cardinality。估算不准的常见原因：统计信息过期、数据倾斜（某个值占了 90% 行）、条件是表达式/函数。PG 侧有扩展统计和更完整的直方图，MySQL 8.0 也有直方图（histogram），但两者都比"加索引"更少被人注意——这条是 M7 的核心。

2. 「server 层和引擎层为什么要分开？」

因为 server 层要兼容多种存储引擎（MyISAM/Memory/InnoDB，M5），所以"解析、优化、执行"这些通用能力放在 server 层，"存储与事务"由引擎各自实现。代价：有些优化做不了跨层（例如早期的 count(*) 全表扫描必须逐行数，引擎其实知道行数但 server 层不知道）。能说出"分层是为了可插拔、代价是有些优化跨不了层"，说明理解了架构取舍。
  • 「一条 UPDATE 的链路和 SELECT 差在哪？」——多了两阶段提交（M11）与锁获取（M10）；而且 update 是当前读（M9），不走 MVCC 快照。这条能把 M9/M10/M11 三张卡串起来。
  • 「长连接和短连接怎么选？」——长连接省握手与鉴权，但连接对象内存会随执行增长，所以要定期 reset_connection；短连接每次都付握手 + 鉴权成本。连接池（PG 那边是刚需，MySQL 侧主要靠应用侧池）是两者的折中。
  • 「一条 SQL 到了 InnoDB 之后怎么取数据？」——按执行计划给的方式（全表扫 / 走某个索引）访问，二级索引命中后回聚簇索引取整行，行数据在 Buffer Pool 命中就直接返回，未命中才读盘。

EnergyOps 的 20 多秒链路——那不是单层问题，是"扫描行数（未限归属范围）+ 应用层 N+1 + 现算差分"三层叠加，所以优化也必须按层做；数驭穹图的查询成本控制（"先缩小业务范围再查"本质上就是帮优化器少做错误决定）。方言差异（面试安全底线）：PG 的执行链路里没有查询缓存（本来就没有），但统计信息体系更完整（扩展统计、直方图、pg_stat_statements）；MySQL 8.0 移除查询缓存、8.0.18 加了 EXPLAIN ANALYZE。"一条 SQL 怎么走"两边都要会，但字段名和工具名不能混。

五层链路各一句 → 查询缓存为什么被移除 → 优化器在决定什么 → 三种慢源 → 与 explain 字段的对应关系

优化器是整条链路里唯一"做决定"的环节——它决定走哪个索引、按什么顺序 JOIN。所以"SQL 慢"的第一嫌疑人永远是"优化器做错了决定"，而它做错的原因通常是"估算不准"（这条直接连到 M7）。

讲解

原理分解

一、五层链路（每层一句话说清）

层做什么可能因为什么出问题
连接器TCP 握手、鉴权、管理连接；长/短连接连接数暴涨、鉴权慢（少见）；长连接要 reset_connection 释放内存
~~查询缓存~~8.0 已移除——
分析器词法/语法分析，生成解析树语法错误（很快报错，不会是慢的原因）
优化器决定用哪个索引、按什么顺序 JOIN、是否用临时表/排序估算错 → 选错索引 → 这是最常见的慢因
执行器按计划循环调用引擎接口，判断条件、返回结果逐行回表（覆盖索引能省掉，M3）
InnoDBBuffer Pool 命中与否、加锁、写 undo/redo缓存冷（随机 IO）、锁等待、日志刷盘

二、为什么"查询缓存"被移除了（常见追问）

缓存键是整条 SQL 文本，失效条件是这张表只要有一个更新就全部失效：

  • 对更新频繁的表，命中率极低，还带来维护开销；
  • "查一次缓存白拿"的收益 < "每次更新都要清一堆缓存"的成本。

这条能推出一个通用结论：任何"以表为粒度整体失效"的缓存都会在写多的表上失效——这正是 EnergyOps 里"缓存一致性"那部分的设计依据（事务内写 Outbox / 版本缓存键，而不是"提交完顺手清缓存"）。

三、优化器在决定什么（这是本题的核心）

决定依据决定错了会怎样
用哪个索引（或者干脆不用）统计信息里的区分度、扫描代价估算明明有索引却走全表（M2 里"索引失效的最后一类"）
JOIN 顺序（谁做驱动表）小表驱动大表原则 + 各自的过滤后行数大表驱动小表 → 循环次数爆炸
是否用临时表 / 文件排序排序数据量与内存限制filesort 落盘 → 慢一个数量级

判断"优化器选错了"的方法：EXPLAIN 里看 key（实际用的索引）与 rows（估算扫描行数）——估算行数和实际差很远时，就是统计信息/选择性出了问题（PG 的对应解法见 P7；MySQL 侧主要靠 ANALYZE TABLE 更新统计信息）。

四、三种慢源（收口）

① 扫描行数多      → 索引没命中 / 选择性差 / 估算错
② 回表次数多      → 二级索引没覆盖，命中的每一行都要回聚簇索引（M3）
③ JOIN 顺序错     → 驱动表选错，循环次数爆炸

对应到 explain 的读法（M7 展开）：type 与 rows 对应 ①，Extra 里的 Using index（覆盖）/Using filesort（排序）/Using temporary（临时表）对应 ②③。
