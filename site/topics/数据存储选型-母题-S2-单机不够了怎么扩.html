题目

某业务库单表 4 亿行，QPS 8000（读写比 9:1）。现在两个症状：① 主库 CPU 常年在 70% 以上，写延迟偶尔飙升；② 每次加索引、改字段都要停机维护窗口，业务方已经拒绝再给窗口了。 团队提了四条路：

  • A：加两个从库，读走从库
  • B：按 user_id 水平拆成 16 张表，放在同一个实例里
  • C：按 user_id 拆到 4 个实例，每个实例 4 张表
  • D：迁移到 OceanBase / TiDB

选哪个？第二个问题：CAP 定理说分布式系统只能三选二，那是不是意味着"强一致"和"高可用"不可能同时要？

一 · 教材 从前提推到结论，不需要先会

1. 前提：单机到底卡在哪——先分清"不够用"是哪一种不够用

1.1 单机的四类上限【事实】

【事实】"单机到顶了"这句话必须先拆开，因为四类上限的解法完全不同：

上限卡在哪症状解法
容量单表/单库数据量增长 → 备份、DDL、索引维护的时间都在涨加索引要几小时、DDL 要停机归档 / 分区（[[母题-M15-数据增长治理]]）→ 再考虑分片
写并发单实例的写入必须串行化到同一份日志与同一批页上写延迟抖动、锁等待上升分片（把一个写入口变成 N 个）
读并发连接数与会话内存（每个连接都有代价，见 [[母题-O1-上下文切换与死锁]]）连接打满、too many connections加从库（读天然可以复制）
分析干扰重查询与事务争抢 CPU / IO / 缓存报表一跑，线上接口就变慢隔离（从库 / 列存引擎，见 [[母题-S1-OLTP与OLAP的分野与选型]]）

【推导】这张表决定了后面所有讨论的顺序：

读并发高       → 读写分离（最便宜，先做）
分析干扰线上   → 隔离到从库或列存（次便宜）
容量增长       → 先归档分区，再谈分片
写并发高       → 只有分片这一条路（写在单机上无法被复制解决）

【事实】关键判断：写入压力无法用"加从库"解决。 从库是复制的副本，写入还是只有主库在承担——加从库只增加"能同时读的人"，不增加"能同时写的人"。这是很多"加了从库还是慢"的根因。

1.2 一个必须先破除的误解【推导】

【推导】"单表多少行就必须分表"这个说法是假的。 数据库里没有"表超过 N 行就不行"的硬限制。真正随时间增长的是"维护成本"：

数据量增长 → B+ 树变高 → 点查多一次 IO        （慢一点，但不致命）
           → 索引变大 → 加字段/加索引要重建更久 （致命：要停机窗口）
           → 备份/恢复时间线性增长              （致命：RTO 不可接受）
           → 缓存命中率下降                     （致命：缓冲池装不下热数据）

【推导】所以"该不该分"的判据不是"多少行"，而是：

你是否已经付不起"维护一次这张表的代价"了？（DDL 要多久、备份要多久、热数据还装不装得进内存）

【取舍】这也是为什么"归档 + 分区"要先于分片：如果 4 亿行里有 3 亿行是两年前的历史数据，那么归档掉历史数据 + 对当前表做分区，可能让维护成本直接回到可接受范围——而这比引入分片中间件的成本低一个数量级。

到这里你应该能回答：为什么"读取慢"和"写入慢"不能用同一招解决？

2. 三条路，先各自介绍

2.1 A · 读写分离【事实】

【事实】做法：一个主库接收写，N 个从库通过复制协议（binlog / WAL）同步，应用层把读请求路由到从库。

它买到什么：读的并发能力（读可以水平复制，因为副本之间互不影响）。

它付出什么：

① 主从延迟 —— 从库是【异步或半同步】复制的，所以从库上的数据可能比主库旧
   → 直接的业务后果：「写后立刻读」可能读不到自己刚写的东西（read-your-write 被破坏）
② 路由复杂度 —— 应用要区分哪些读能走从库（容忍延迟）、哪些必须走主库
③ 一致性窗口 —— 报表与实时数据对不上，必须有对账或"数据截止时间"标注

【事实】数驭穹图的 LIVE_READ 走的就是这条路：02 写明实时模式*"优先连接只读副本或分析库"*，且*"若客户只有生产主库，默认不开放复杂即席查询"*——把"不许打到主库"写成了产品规则。

2.2 B / C · 分库分表【事实】

【事实】两个维度，不要混：

垂直拆水平拆
拆什么按业务/字段拆（订单库、用户库；把大字段挪到附表）按行拆（user_id % 16）
解决耦合与"热点表"问题容量与写并发
典型形态微服务化后的自然结果分片键 + 路由规则

它买到什么：写并发能力（N 个实例各自有独立的日志、锁、缓冲池）+ 单表容量回到可控范围。

它付出什么（这张清单是本节的重点）：

① 跨片 join 消失 —— 要么在应用层拼装，要么建冗余宽表
② 跨片分页与排序变难 —— 原来一个 ORDER BY + LIMIT 能做的事，
   现在要【每个分片各取前 N 条再归并】
③ 跨片事务消失 —— 必须换成分布式事务方案（见第 4 节）
④ 全局唯一 ID —— 自增主键不能再用了（见第 4 节）
⑤ 二级索引变成"全局索引"问题 —— 非分片键的查询要么广播、要么自建索引表
⑥ 扩容迁移 —— 分片数一变，数据要重新分布（一致性哈希能减轻但解决不了全部）
⑦ 【选错分片键是灾难】—— 数据倾斜（热点分片）、或者大多数查询都要广播

【取舍】第 ⑦ 条最容易出事：分片键决定了"哪些查询变成广播"。按 user_id 分片，那么"按城市统计"这类查询就要打到所有分片。所以分片键的选择不是看数据怎么分布，而是看"最高频的查询按什么维度来"。

2.3 D · 分布式数据库（OceanBase / TiDB）【事实】

【事实】它把上面所有"应用层要自己做的事"下沉到数据库内部：自动分片、自动扩容、分布式事务、全局索引。

两条技术路线的架构差别（这是本题最容易被追问的地方）：

TiDBOceanBase
整体形态计算与存储分离（三层）一体化（单机与分布式同一套代码）
计算层TiDB Server（无状态 SQL 层，可任意加）OBServer（每个节点都同时是 SQL 与存储）
存储层TiKV（行存，按 Range 分片成 Region）分区表 + 底层 LSM 存储
分析副本TiFlash（列存，以 Raft learner 从 TiKV 同步）列存副本
调度PD（独立组件，管 Region 分布与负载均衡）内建于集群管理
多副本一致性Raft（TiKV 内部按 Region 做 Raft 组）Paxos（多副本日志同步）
部署重心组件多、依赖 PD，规模弹性好单机即可跑出分布式架构，对运维更友好（这是它在国内金融/政企吃香的一个原因）

【事实】两者的共同点更重要：都是"用多副本一致性协议（Raft / Paxos）把复制做对，用自动分片把容量做开，用快照隔离 + 两阶段提交把分布式事务做出来"。它们解决的是同一个问题，差别主要在"组件怎么摆"和"对单机场景的友好度"。

【取舍】选它而不选分库分表的理由：把复杂度从"每个业务团队都要懂"变成"数据库团队管一次"。 分库分表是应用层方案（每个写代码的人都要知道分片规则、都要处理跨片查询），分布式数据库是基础设施方案（应用写普通 SQL）。

代价：产品锁定更深（换回来极难）、资源开销更高（多副本意味着至少 3 份存储）、学习与调优门槛在数据库侧。

到这里你应该能回答：分库分表与分布式数据库，本质上是"把复杂度放在应用层还是放在基础设施层"的选择？

3. 逐个淘汰：统一指标是"新增了多少个失败点"

统一指标：新增的失败点数量 + 新增的不一致窗口。 扩展的本质是用复杂度换能力，所以要比的是"换来的能力"与"付出的复杂度"。

【推导】把开头的四个方案放进同一把尺子：

方案新增能力新增失败点 / 不一致窗口结论
A 加两个从库读并发+2 个实例（故障面）+ 主从延迟窗口该做，但它解决不了"写延迟飙升"（1.1 的判据）
B 同实例拆 16 表单表维护成本下降几乎为零（还是同一个实例，事务与 join 都还在）性价比最高的一步，但不解决写并发（还是同一个实例的日志与锁）
C 拆到 4 实例写并发 ×4+4 个实例；跨片事务、跨片 join、跨片分页全部变成应用层问题；分片键选错 = 灾难真能解决写并发，但要吃下整张代价清单（2.2）
D 迁分布式数据库写并发 + 容量 + 自动扩容锁定、资源开销；但应用层复杂度大幅下降团队规模小、不想长期维护分片中间件时最优

【推导】用题面给的两个症状来判：

症状① 写延迟偶尔飙升 → 这是【写并发】问题
   → 加从库（A）无效：从库不承担写（1.1）
   → B 无效：同实例内拆表不增加写入并行度（日志、锁、页仍是同一份）
   → 只有 C 或 D 能解决

症状② 加索引要停机窗口 → 这是【容量/维护成本】问题
   → A 完全无效
   → B 有效（单表变小，DDL 更快），但表还会继续长大
   → C / D 有效（单表规模回到可控范围；D 还能在线 DDL）

★ 所以 A 和 B 都该做（成本低、解决部分问题），
  但题面里最痛的两个症状，需要 C 或 D 才能根治。
  选 C 还是 D，看"团队愿不愿意长期维护分片中间件与那套应用层规则"。

【取舍】"先做 A 和 B、同时评估 C 或 D"不是和稀泥，而是成本顺序：A 与 B 便宜且不排他，先用它们买到喘息时间，再决定要不要吃下 C/D 的长期复杂度——这也是得物那个案例的实际路径（summaries/oceanBase.md：*"低风险业务迁移 → TP/AP 一体化重构"*，先小步验证，再动核心）。

4. 分布式事务与全局 ID：为什么"没有全局时钟"是根本困难

4.1 分布式事务的五个方案【事实】

【事实】

方案思路代价
2PC（两阶段提交）协调者先问所有参与者"能不能提交"，都答应再统一提交阻塞（参与者要一直占着资源等结论）+ 协调者单点
TCC（Try-Confirm-Cancel）每个服务自己实现"预留 / 确认 / 取消"三个操作业务侵入极大，要为每个操作写三个反向逻辑
Saga一串本地事务，失败时按反序执行补偿补偿逻辑要写；中间态对外可见
本地消息表 / 事务消息本地事务和"要发的消息"写在同一库，靠投递保证最终一致只是最终一致；要有幂等与对账
分布式数据库内建快照隔离 + 两阶段提交，由数据库自己做依赖产品；跨库（跨产品）仍然做不到

【推导】所有方案的困难来自同一个地方：

单机事务能原子提交，靠的是【共享的日志 + 一个本地的锁 + 一个提交点】。
分布式之后：没有共享日志、没有全局锁、【没有统一的时间（各机器时钟有偏差）】
→ 于是只剩两条路：
   ① 用协议（2PC / Raft 日志）把"一个提交点"造出来 → 慢、有阻塞
   ② 放弃原子性，用"补偿 + 幂等 + 对账"逼近最终一致 → 复杂但有弹性

【取舍】工程上的主流选择是 ②，而它的核心不是事务本身，是幂等与对账——这正是 [[母题-A3-失败恢复与幂等]] 与 [[母题-L3-分布式锁与fencing-token]] 要解决的问题："用最终一致"这句话只有在"重复执行不出错"和"能对账发现差异"都成立时才是安全的。

4.2 全局唯一 ID【事实】

【事实】自增主键在分片后失效（每个分片都会从 1 开始）。可选方案：

① UUID          → 全局唯一，但无序 → 【B+ 树索引插入变成随机写】，且体积大
② 号段模式      → 数据库批量发号（一次领 1000 个），本地自增
                  → 高性能，但重启/多实例要考虑浪费与重复
③ 雪花算法（Snowflake） → 时间戳 + 机器 ID + 序列号
                  → 趋势递增，但【依赖机器时钟】—— 时钟回拨会产生重复 ID
④ 数据库序列 / 分布式协调服务 → 简单但引入额外依赖

【推导】选型的判据是"这个 ID 要不要参与索引和排序"：要按时间排序、要作为主键插入 → 必须趋势递增（这直接关系到 [[母题-M1-为什么用B+树]] 的插入代价）；纯业务标识、不参与排序 → UUID 的随机性无所谓。

5. CAP 到底该怎么讲

5.1 为什么"C 和 A 二选一"是个过度简化【推导】

【推导】CAP 的准确含义：

C（一致性）：线性一致性——所有节点看到同一个最新值
A（可用性）  ：每个请求都能在有限时间内得到【非错误】响应
P（分区容错）：网络分区（节点之间消息丢失/延迟）时系统仍能继续运行

【推导】问题出在"三选二"这个说法上：

① 网络分区在分布式系统里【不是可选项】——只要跨机器通信，
   分区迟早会发生。所以 P 不是"要不要"，是"必须接受"。
   → 于是真正的选择只剩：【分区发生的时候，选 C 还是选 A】

② 而"分区发生的时候"是一个【很短的窗口】。
   绝大多数时间里网络是好的，系统可以【同时】提供一致性与可用性。
   → 所以 CAP 描述的是"极端情况下的行为"，不是"日常的取舍"

【取舍】更实用的框架是 PACELC：

P（分区时）：在 A（可用）和 C（一致）之间选
E（否则 Else，即正常运行时）：在 L（低延迟）和 C（一致）之间选
→ 后半句才是日常真正在做的权衡：
  想要强一致的多副本写入，就必须等多数派确认 → 【延迟必然更高】

【推导】所以面对"强一致和高可用能不能同时要"，准确的回答是：

可以，在正常情况下两者都能得到。CAP 描述的是"网络分区发生的那一刻，你预先选了哪一个"——而这个选择应该由业务来定，不是由技术来定（涉及钱和账的，选 C；可以被降级和缓存的，选 A）。

5.2 一致性不是布尔值【事实】

【事实】"一致"是个谱系，不是开关：

线性一致（最强）：所有操作看起来像在单一副本上按时间顺序发生
    ↓
顺序一致 / 因果一致：至少保证有因果关系的操作间的顺序
    ↓
快照隔离：每个事务看到某个一致的快照（大多数分布式数据库的默认档）
    ↓
读己之写（read-your-writes）：至少能看到自己刚写的东西
    ↓
最终一致（最弱）：不保证多久，只保证最终会一致

【取舍】工程上的常见落法：数据库内部用强一致（Raft / Paxos 多副本）保证"这份数据不会丢也不会分裂"，而业务层接受"跨系统的最终一致"。这是两个不同层次的一致，不要混着说——把它们混成"你们系统是最终一致的吗"这种问法，就没法讨论了。

到这里你应该能回答：为什么"你们系统选 CP 还是 AP"这个问题，问法本身就有问题？

6. 边界与常见误解

常见说法修正
"单表超过 1000 万行就要分表"【事实】没有这个硬限制。真正随时间增长的是维护成本（DDL 与备份耗时、缓冲池装不下热数据）。判据是"你还付不付得起维护这张表的代价"，不是行数（1.2）
"加几个从库就能扛住"【推导】从库只分担读（1.1）。写入压力加从库无效——这是"加了从库还是慢"的最常见根因
"分库分表能提升性能"【取舍】它提升的是"能承受的写并发与容量"，代价是"跨片操作全都变难"（2.2 的七条）。在数据量没到时做这件事，是纯负债

1. 加了从库为什么还是慢？

因为从库只分担读（1.1）。写入压力无法用复制解决——副本不进写路径。要先确认瓶颈是读还是写，再选手段。

2. 分片键怎么选？

按"最高频的查询维度"选（2.2 第 ⑦ 条），不是按数据分布选。选错的后果是：高频查询全部变成广播，或者数据倾斜导致热点分片。 而低频的非分片键查询，应该另建一份聚合数据（物化视图 / 列存）来解决。

3. OceanBase 和 TiDB 最大的差别是什么？

组件摆法：TiDB 是计算存储分离（TiDB Server 无状态 + TiKV 行存 + TiFlash 列存 + PD 调度，依赖 Raft）；OceanBase 是一体化（每个节点同时是 SQL 与存储层，用 Paxos 多副本，单机也能跑出分布式架构，对运维更友好）。共同点是"多副本一致性 + 自动分片 + 分布式事务"——它们解决的是同一个问题。

4. 分布式事务为什么难？

因为没有全局时钟、没有共享日志、没有全局锁，原子提交的"一个提交点"不存在（4.1）。要么用协议造一个（2PC / Raft，慢且有阻塞），要么放弃原子性用补偿 + 幂等 + 对账逼近最终一致——后者的关键不是事务，是幂等与对账。

5. 什么情况下不该分库分表？

数据量没到（归档 + 分区能解决）、瓶颈在别处（慢查询 / 主从延迟 / 缺索引）、以及"分片键还没想清楚"的时候——分片键选错的迁移成本极高，所以宁可晚分也别乱分。

6. HTAP 的分布式数据库是不是就不用分库分表了？

是的，它把分片内化了——但分区键仍然存在且要选对（只是由数据库管理）。它取消的是"应用层要知道分片规则"这件事，不是取消"设计决策"。
  • 「读写分离为什么会有主从延迟？」——复制是异步或半同步的（[[母题-M14-主从复制与延迟]]）。直接的业务后果是 read-your-write 被破坏——所以"写后立刻读"的场景必须走主库
  • 「一致性哈希为什么能减轻扩容迁移？」——它让"增加一个节点时只影响相邻的一段数据"，而不是全量重分布。但它解决不了数据倾斜，也解决不了跨片查询
  • 「为什么分布式数据库至少三副本？」——多数派协议（Raft / Paxos）需要"多数派存活才能提交"。三副本能容忍 1 个节点故障；两副本没有容错能力（任何一台挂了都凑不齐多数派）
  • 「分库分表中间件（ShardingSphere 这类）解决什么？」——在应用层把"分片规则"变成透明的（改写 SQL、路由、归并结果）。这正是"复杂度放在哪层"的中间态——比纯应用层改造轻，比换数据库重

数驭穹图 —— 02-数据接入与轻量湖仓.md 里的 LIVE_READ 模式就是读写分离的工程实践：*"实时模式通过受控连接器查询只读副本或分析库"*，并且明确*"若客户只有生产主库，默认不开放复杂即席查询"*——这就是"分析负载不许打到主库"这条硬规矩的落地。同时它也做了第 1.1 节顺序里的"隔离"这一步：先隔离分析负载，而不是先分片。

扩展的一切手段都在"用复杂度换能力"，而复杂度的落点是"新增了多少个失败点 + 新增了多长的不一致窗口"。所以每一个扩展方案都要能回答：我新增了几个要监控、要处理故障、要对账的东西？ 分库分表把这件事放在应用层（每个开发者都要懂），分布式数据库把它放到基础设施层（数据库团队管一次）——这个"放哪层"才是真正的选型分界，而不是"哪个更快"。
