题目

面试官问——"你们的 RAG 是怎么切块的？切多大？为什么是这么大？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：检索单元必须同时满足两个互相矛盾的需求

【推导】把"一块文档"当成检索单元，它要同时做到：

① 能被准确匹配到  → 要求块里mostly 是相关内容
                     → 块越小越好（相关内容占比高，相似度信号强）

② 能被模型直接使用 → 要求块语义自足
                     → 块越大越好（前因后果、例外条件都在里面）

【推论】这两个需求方向相反，所以"切多大"这个问题的正确答案不是某个数字，而是"承认它们矛盾、然后想办法解耦"。

到这里你应该能回答：为什么"我们切 500 字"这种回答一定会被追问"为什么是 500"？

2. 两端各坏在哪

2.1 太小：语义不完整【推导】

一份退款规则切成「条件」「例外」「生效时间」三块

用户问：「7 天无理由退款适用哪些情况？」
召回命中「条件」那一块：「购买后 7 天内可无理由退款」
→ 模型照此回答

但「例外」块里写着：「拆封的数码产品除外」
→ 这一块没被召回，答案就是错的

【推论】单个块的意思甚至可能是反的。 小块的"高召回率"只说明它容易被匹配到，不说明它能独立支撑一个答案。

【事实】另外两个代价：块数暴涨（索引与检索成本上升）、重叠切分时重复召回（挤占上下文预算）。

2.2 太大：相似度被稀释【推导】

一段 2000 字的文档，其中只有 200 字与问题相关
  相关内容占比 = 200 / 2000 = 10%

如果整篇作为一个块：
  它的向量是整篇内容的「平均表示」
  → 与 query 的相似度被另外 90% 的无关内容拉低
  → 在 Top-K 排序里排不过那些「占比高」的小块

【推论】块越大，单块的相似度信号越弱——关键内容不是"没被切到"，是被淹没在噪声里排不进 Top-K。

【取舍】这是"块大小"这个数字真正的含义：它调节的是"相关内容在块里的占比"。500 字对制度文档可能合适，对表格或代码就是灾难——因为它不取决于文档长度，取决于"相关内容通常有多长"。

到这里你应该能回答：为什么"块大小"不能用文档平均长度来定？

3. 候选方案一：解耦——小块召回、大块返回【事实】

索引时：把文档切成【小块】（child），每块记住自己的【父块】（parent / 整节 / 整篇）
检索时：用【小块】去匹配          → 粒度细，召回率高
返回时：把【父块】塞给模型        → 上下文完整，模型能理解全貌

【事实】得物那篇文章把它叫 Child-Parent，总结成一句很准的话：

"检索时用 Child 去搜——小块粒度细，召回率高；返回时把 Parent 塞给 LLM——大块上下文完整，LLM 能理解全貌。兼顾了召回率和上下文完整性。"

【推论】这个方案的通用价值在于：它把"检索用的表示"和"喂给模型的表示"拆成了两份。 只要这两者可以不同，矛盾就消失了——这也是后面所有 RAG 优化的同一个套路（重排用小块、生成用大块；索引用补过上下文的块、展示用原文）。

4. 候选方案二：不改粒度，改"块自己知不知道自己在说什么"

【事实】Contextual Retrieval 的做法：切块之后，先让模型给每块补一句"它在全文里是什么位置、指代谁"（约 50–100 token），再把补过上下文的块拿去做向量和 BM25 索引。

原文给的例子：

原始块：  "The company's revenue grew by 3% over the previous quarter."
          （哪家公司？哪个季度？单看这块无从判断 → 检不到）

补上下文："This chunk is from an SEC filing on ACME corp's performance in Q2 2023;
          the previous quarter's revenue was $314 million.
          The company's revenue grew by 3% over the previous quarter."

4.1 收益与成本都能算【推导】

收益（实测的平均检索失败率，top-20 口径）：

基线                              5.7%
+ Contextual Embeddings           3.7%   （−35%）
+ Contextual BM25                 2.9%   （−49%）
+ 再叠加 Rerank                   1.88%  （−67%）

换算成"每 1000 次查询失败几次"更直观：57 次 → 37 次 → 29 次 → 19 次。

成本：

每个块多 50–100 token 的上下文
若块本身 800 token，加上 100 token 上下文：
  索引体积增加 100 / 800 = 12.5%

【结论】用约 12.5% 的索引体积，换 49% 的检索失败率下降。 这笔账很划算，而且它不需要改切分策略——是在现有切法上加一层。

【事实】一次性成本：Anthropic 给过一个测算——用 prompt caching 做上下文增强，一次性成本约 $1.02 每百万文档 token（前提是缓存复用参考文档，否则要为每个块都重传全文）。

到这里你应该能回答：Contextual Retrieval 和 Child-Parent 是两种什么思路？（一个改"返回什么"，一个改"索引什么"）

5. 三种切分策略的适用【事实】

数据首选策略为什么
Markdown / 制度文档标题层级 + 段落，保存父子关系标题本身就是语义边界
FAQ一个问答为基本单元天然自足，不需要再切
代码函数 / 类 / 模块边界 + 符号信息半个函数无法被理解
表格表头与行 / 分组绑定，不拆掉口径拆开表头的行是"无意义的数字"
长报告小块召回 + parent 扩展典型的 Child-Parent 场景
规则条款条款 / 条件 / 例外 / 生效时间结构化例外与条件必须同行，否则意思会反

【取舍】得物文章里的一句总结可以当通用判据：

"Chunk 参数必须通过目标问题集评测，而不是照搬经验数值。"

【推论】这句话的落点是：切分策略的唯一验收标准是"在你的目标问题上召回率是多少"，而不是"是否符合某个最佳实践"。所以切分是一个需要 Eval 才能定的事（[[母题-G5-RAG评测与幻觉率]]）。

6. 边界与常见误解

常见说法修正
"固定切 500 字是行业标准"没有这个标准。块大小调节的是"相关内容在块里的占比"，所以它取决于你的文档里相关内容通常多长，而不是一个全局数字。对表格和代码，固定字数切块是灾难
"块越小召回率越高，所以越小越好"召回率高 ≠ 答案对。块太小会让语义不自足（例外的条款被切走，单个块的意思可能是反的），而且块数暴涨、重复召回挤占预算。正解是解耦，不是把块切小
"Child-Parent 就是把块切小一点"不是。它是把"检索用的表示"和"喂给模型的表示"拆成两份——这个概念可以推广到重排（重排用小块、生成用大块）和索引（索引用补过上下文的块）
"Contextual Retrieval 要重做切分"不用。它是在现有切法上加一层预处理：切完再给每块补 50–100 token 的定位说明。收益 49%，索引只涨约 12.5%
"切分是一次性的离线工作"它和更新绑在一起：文档改了要重切、重嵌入。所以切分粒度的选择会直接影响增量更新的成本（[[母题-G6-知识更新与增量索引]]）
"切分没什么可优化的，重点是模型"反了。切分决定的是召回的质量上限——块没被召回，后面多强的模型都看不到它

【取舍】读成一句话："切多大"没有正确答案，只有"辨认出两个矛盾的需求，然后把它们在系统里拆开"——这才是这道题真正在考的东西。

把文档切成检索单元时，粒度该多大——为什么这个问题无论怎么答都会被追问？

翻面对照自测；复训调度以训练台派单为准。

为什么重要：这道题几乎每场 RAG 面试都会问，而且它是最容易暴露"照搬经验数值"的一题——答"我们切 500 字"和答"我们用小块召回 + 父块返回，因为这两个需求互相矛盾"是两个档次。它也是唯一一个"在离线阶段就能决定线上质量上限"的环节：切坏了，后面的重排和生成再强也救不回来。

一句话结论 全卡唯一要背的锚点

切块粒度是一个两头都会坏的问题——太小语义不自足（条款的例外被切走，单块意思可能是反的）；太大相关内容占比下降、相似度被稀释，关键内容排不进 Top-K（2000 字里只有 200 字相关时占比只剩 10%）。所以答案不是某个数字，而是把两个矛盾的需拆开：小块召回（保召回率）+ 父块返回（保上下文完整）——这就是 Child-Parent。另一种思路是不改粒度、改信息：Contextual Retrieval 先给每块补 50–100 token 的定位说明再做索引，索引只涨约 12.5%，实测把检索失败率从 5.7% 降到 2.9%（−49%），再叠加重排是 1.88%（−67%）。切分策略必须按数据结构选（标题 / FAQ / 代码 / 表格 / 条款各有首选），并用目标问题集评测来定参数，不能照搬经验值。
  • 两个矛盾需求（匹配准 vs 语义自足）
  • 太大的机制是稀释（占比 10%）
  • 太小的机制是语义不自足（例外被切走）
  • Child-Parent = 小块召回 + 父块返回
  • 解耦可以推广（重排用小块、索引用补上下文的块）
  • Contextual Retrieval：+50–100 token 定位说明，索引 +12.5%
  • 失败率 5.7% → 3.7% → 2.9% → 1.88%
  • 块越小，上下文增强的相对成本越高（200 token 时涨 50%）
  • 切分按数据结构选，参数靠评测定

  • 结论：粒度两头都会坏；小块召回 + 父块返回（Child-Parent）或补定位说明再索引（Contextual Retrieval）。
  • 推导链：太小→语义不自足；太大→相似度稀释、排不进 Top-K → 拆成"召回准"与"信息全" → 改返回 vs 改索引。
  • 量化：2000 字里 200 字相关 → 占比只剩 10%；Contextual Retrieval 索引涨约 12.5%，失败率 5.7% → 2.9%（−49%），叠重排 → 1.88%（−67%）。
  • 边界与常见误解：固定字数切块切的是字符数不是语义边界；表格拆掉表头是常见的坏切法；"多长的块最合适"没有通用答案，只能评测定。

1. Child-Parent 和 Contextual Retrieval 有什么区别？

一个改"返回什么"，一个改"索引什么"。Child-Parent 索引小块、返回父块；Contextual Retrieval 索引的是"补了定位说明的块"。两者可以叠加，而且叠加后正好覆盖了"匹配准"和"信息全"两个需求。

2. 表格怎么切？

表头与行 / 分组绑定，不能拆掉口径。拆开表头的行是"无意义的数字"——这在企业知识库里是最常见的坏切法之一（指标表、口径表尤其明显）。

3. 多长的块最合适？

没有通用答案。要先用代表性问题集测 Recall 与答案正确性。能给的经验只有方向：制度文档按标题层级（几百字量级）、FAQ 按问答、代码按函数边界、条款按"条件+例外+生效时间"。

4. RAG、微调、长上下文怎么选？

最新 / 私有 / 可引用的知识 → RAG；稳定的行为、格式、领域表达 → 可能微调；小而稳定的知识 → 长上下文可能更简单。通常先用 Prompt / RAG 建 Eval，再判断是否微调。
  • 「小块召回父块返回，和"检索后扩展上下文窗口"有什么区别？」——前者扩的是"同一文档内的父级"（结构关系），后者扩的是"相邻块"（位置关系）。前者更准（父块是语义边界），后者更便宜（不需要维护父子关系）。
  • 「代码库怎么做 RAG？」——按函数 / 类 / 模块边界切 + 带上符号信息（函数签名、所在文件路径、被谁调用）。半个函数无法被理解，而符号信息相当于代码版的"Contextual Retrieval"。

- 数驭穹图：把 Schema / 指标口径 / 样例查询视作不同知识类型——它们的"相关内容长度"完全不同（表名很短、口径说明较长），所以不能用同一个块大小。这正是"按数据结构选策略"的项目实例。 - RuleArena：条款按"条件 / 例外 / 生效时间"结构化切分——例外与条件必须同行，否则单块意思会反。这是 Q1 那个例子的真实版本。 - EnergyOps：运维文档、设备数据和实时状态不混成一个索引——不同来源的文档结构不同，切法也要分开。

先说两个矛盾需求 → 两端各坏在哪（各给一个机制）→ 解耦方案（Child-Parent） → 另一种思路（Contextual Retrieval，给收益与成本的数）→ 按数据结构选策略 → 参数必须靠评测定 → 收束到"拆开两种表示"

"检索用的表示"和"喂给模型的表示"，不必是同一个东西。 一旦这条被认出来，切分粒度的矛盾就消失了——后面所有 RAG 优化用的都是同一个套路（重排用小块、生成用大块；索引用补过上下文的块、展示用原文）。
