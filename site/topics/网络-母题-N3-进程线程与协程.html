母题 N3 · 进程 / 线程 / 协程，以及 asyncio 为什么能扛住很多连接

关联 母题-N1-一次请求的完整路径 · 母题-N2-SSE与推送模型 · 母题-M10-锁与死锁 ｜ 正本 wiki/topics/网络/母题-N3-进程线程与协程.md

必懂 3 件事（① 并发的收益来自"等待占比" ② 三者用同一指标比 ③ 协程的致命前提是不阻塞）· 读完约 10 分钟 · 需要先懂：无

题目

进程、线程、协程有什么区别？asyncio 为什么能同时扛住很多连接？

一 · 教材 从前提推到结论，不需要先会

1. 前提：先问"时间花在哪"

1.1 一个请求的时间构成【事实】

一次典型的上游调用，总耗时 100ms：
  CPU 计算（拼参数、解析、序列化）  约 2ms
  等 IO（网络往返、DB 查询、磁盘）  约 98ms

【推导】98% 的时间在等。而"等"的时候，CPU 是空闲的。

所以并发的本质不是"同时干很多事"，而是"在等的时候去干别的事"。

1.2 量化：并发的收益上限

【推导】如果一次请求只占用 2% 的 CPU 时间，那单核理论上就能"同时"处理 100/2 = 50 个这样的请求：

理论并发上限 ≈ 总耗时 / CPU 占用时间 = 100 / 2 = 50

这个算式给出了本卡最重要的判据：

负载类型CPU 占比并发杠杆结论
IO 密集（调上游、查 DB、等网络）低（如 2%）大（约 50 倍）异步收益巨大
CPU 密集（加密、图像处理、大计算）高（如 80%+）小（约 1.2 倍）异步几乎没用，要靠多核

【取舍】所以"要不要用异步"不是风格问题，是"你的程序在等还是在算"的问题。 而 Agent 服务、API 网关这类程序几乎全是 IO 密集——所以异步收益极大。

到这里你应该能回答：为什么 asyncio 对"查数据库的接口"帮助很大，对"算加密哈希的接口"几乎没帮助？

2. 三种执行单元：用同一指标比

2.1 进程【事实】

  • 是什么：操作系统分配资源的基本单位，有自己独立的地址空间
  • 调度者：操作系统
  • 单位成本：栈上限约 8MB（虚拟内存，实际按触碰的页算）
  • 优点：隔离最好——一个进程崩了不影响别的
  • 代价：通信与切换最贵（数据要跨地址空间拷贝）

2.2 线程【事实】

  • 是什么：进程内的执行单元，共享同一地址空间
  • 调度者：操作系统（抢占式：时间片到了就被换下来）
  • 单位成本：栈约 1MB
  • 优点：共享数据方便（同一个堆，直接读）
  • 代价：切换要走内核（用户态↔内核态）；共享数据要加锁（[[母题-M10-锁与死锁]] 的业务层同源问题）

2.3 协程【事实】

  • 是什么：用户态的轻量执行单元，由程序自己调度，不由 OS 调度
  • 调度者：事件循环（asyncio 的核心）
  • 单位成本：约 2KB
  • 优点：切换几乎免费（本质是函数调用，不经过内核）
  • 代价：一处阻塞，全体停摆（见第 4 节）——这是它最致命的约束

2.4 三者的关键差别只有一个

【推导】从"谁调度"这一个点出发，上面所有差异都能推出来：

谁调度由此推出
进程OS隔离最好、切换最贵
线程OS抢占式（不用你让）、切换走内核
协程你的程序切换便宜、但必须你自己在等待时让出去

"必须主动让出去"就是"协作式（cooperative）"的含义。 线程是抢占式的（OS 会强行换），协程是协作式的（你不让，它就一直占着）。

3. asyncio 为什么能扛住大量连接

3.1 事件循环做什么【事实】

事件循环（event loop）：一个单线程里的循环，反复做三件事：

① 看有没有 IO 就绪（靠 epoll / kqueue 这类系统调用，一次问一批）
② 就绪了就执行对应的回调（推进那个协程）
③ 没有就绪的，就睡一小会儿再问

【推导】关键在 ①：一次系统调用就能拿到"成千上万个连接里哪些有数据了"。

对比"一个连接一个线程"的做法：1000 个线程都在 read 上等 → 内核要维护 1000 个等待上下文、要做 1000 次调度。而事件循环是一个线程问一次。

3.2 量化：能扛多少

【推导】用单位内存开销来算 10 万并发单元需要多少内存：

线程：约 1MB / 个 × 100,000 = 约 100 GB
协程：约 2KB / 个 × 100,000 = 约 200 MB

差约 500 倍。

【取舍】这就是"为什么长连接服务用异步"的直接答案：不是"协程更快"，而是同样的内存能支撑的并发单元多了两个数量级。

回到 N2 的场景：1000 个用户在等 SSE 推送 —— 用线程模型就是 1000 个线程常驻（约 1GB），用协程就是 1000 个挂起的协程（约 2MB）。这是量级差别，不是优化技巧。

3.3 但协程不是"更快"

【推导】必须说清这一条，否则会答成"协程比线程快"：

  • 单个操作的速度：协程切换快，但你的业务逻辑本身不会变快
  • 总吞吐：在 IO 密集场景下吞吐大幅提升（因为等待时间被利用起来了）；在 CPU 密集场景下几乎没提升（1.2 的判据）

4. 阻塞代码：协程最致命的坑

4.1 会发生什么【推导】

事件循环是一个线程。如果某个协程里执行了一段阻塞调用（同步 IO、time.sleep、CPU 重活），整个事件循环就停在那里——其他几百上千个连接全部等它。

async def handler():
    r = requests.get(url)      # ← 阻塞调用：整个事件循环停在这里
    return r.json()

它坏在哪：协程的"让出"发生在 await 一个真正的异步操作时。同步阻塞调用里没有 await 点，事件循环没有机会切走——所以它被一个人占住了。

4.2 量化的后果

事件循环被阻塞 200ms
此时 QPS = 1000
→ 这 200ms 内到达的 1000 × 0.2 = 200 个请求全部排队
→ P99 延迟直接被抬升 200ms

【推导】而且这种故障很隐蔽：CPU 看起来不高、日志里没有异常、每个请求单独测都很快——只是高峰期整体变慢。这就是"异步写错了比同步还慢"的原因。

4.3 三种解法【取舍】

解法做法代价
换异步库用 httpx.AsyncClient / asyncpg 等原生异步客户端需要确认生态支持；改动最大但最彻底
丢进线程池await asyncio.to_thread(fn) / run_in_executor简单，但线程池有上限，打满了同样会等
拆成独立进程把 CPU 重活交给进程池 / 独立服务隔离好，但多了通信成本

【判据】如果那段代码是 IO 阻塞 → 换异步库或丢线程池；如果是 CPU 密集 → 必须丢进程池（因为 GIL，见第 5 节，丢线程池没用）。

5. GIL：为什么协程不能靠多线程绕过去

5.1 GIL 是什么【事实】

GIL（Global Interpreter Lock）：CPython 的全局解释器锁——同一时刻只允许一个线程执行 Python 字节码。

【推导】直接推论：

场景多线程有用吗
IO 阻塞有用——线程在等 IO 时会释放 GIL，别的线程可以跑
CPU 密集没用——大家都在抢 GIL，等于串行

5.2 和 asyncio 的关系【推导】

asyncio 是单线程的——它从设计上就不依赖 GIL 的多线程能力，而是靠"切换发生在等待点"。

所以：

  • 想用多核：靠多进程（multiprocessing / 起多个 worker），不是多线程，也不是协程
  • 想扛高并发 IO：靠单线程 + 事件循环，不需要多核

一句话：GIL 不阻止你写高并发 IO 服务（因为瓶颈不在 CPU），但阻止你用多线程加速 CPU 计算。

6. 边界与常见误解

常见说法修正
"协程比线程快"【推导】单操作的业务逻辑不会变快。协程的收益在"IO 密集场景下能把等待时间利用起来"+"单位开销小两个数量级"
"asyncio 能利用多核"【事实】不能。它是单线程事件循环。要多核靠多进程
"协程是并行执行的"【事实】是并发，不是并行。同一时刻只有一个协程在跑（单线程），只是它们互相交错
"在 async 函数里调用普通同步函数没问题"【推导】有问题。同步阻塞调用没有 await 点，会卡死整个事件循环（第 4 节）
"用 asyncio 就不用管锁了"【事实】单线程下不会有多线程那样的数据竞争，但仍有竞态——因为 await 会让出控制权，两个协程可能交错修改同一状态。"await 前后状态可能变"是异步里的经典陷阱
"线程模型不行了，应该全换异步"【取舍】按 1.2 的判据选：IO 密集且并发量大 → 异步；CPU 密集 → 多进程；并发量小 → 线程模型更简单，没必要为了异步而异步

一句话结论 全卡唯一要背的锚点

并发不是"同时干很多事"，而是"在等的时候去干别的事"——所以收益由等待占比决定（CPU 占 2% 的请求，单核理论上能并发约 50 个）。三种执行单元的差别从"谁调度"推出来：进程由 OS 调度、地址空间独立（隔离好、通信贵）；线程由 OS 调度、共享地址空间（方便、切换走内核）；协程由用户态事件循环调度、约 2KB 一个（切换几乎免费，但一处阻塞全体停摆）。asyncio 能扛住大量连接，是因为单线程一次 epoll 就能问出成千上万连接里哪些就绪，加上单位开销小两个数量级——10 万并发线程要 100GB、协程只要 200MB。
  • 并发 = 利用等待时间
  • 并发杠杆 ≈ 总耗时 ÷ CPU 时间
  • IO 密集收益大、CPU 密集收益≈1
  • 进程独立地址空间
  • 线程共享但切换走内核
  • 协程由事件循环调度、协作式
  • epoll 一次问一批
  • 10 万并发线程 100GB vs 协程 200MB
  • 阻塞调用卡死整个循环
  • GIL 让多线程对 CPU 密集无效
  • 多核靠多进程
  • 是并发不是并行

卡住时靠这几个词重建整条链。

展开（先自答，再看 · 默认收起，不进复训调度）

1. 协程和线程最本质的区别是什么？

谁调度：线程由 OS 抢占式调度（会强行换），协程由程序协作式调度（你不让就一直占）。"阻塞代码能卡死事件循环"这个代价就是从这一条来的。

2. asyncio 能利用多核吗？

不能，它是单线程。要多核靠多进程；多线程因 GIL 对 CPU 密集无效。

3. 在协程里调用同步库会怎样？

卡死整个事件循环，表现为"所有接口一起变慢、但 CPU 不高、日志无异常"。修法是换异步库或丢线程池。

4. 单线程异步还需要考虑竞态吗？

需要。await 会让出控制权，两个协程可能交错修改同一状态。"await 前后状态可能变"是异步里的经典陷阱（这一点和线程加锁是不同形态的同一类问题）。

5. 连接池耗尽 / 协程泄漏怎么排查？

池子耗尽先看上游时延（[[母题-N1-一次请求的完整路径]] 的 L = λW）；协程泄漏通常是创建了任务但没有正确取消（超时/取消链路要传下去）。
  • 「为什么 Nginx / Redis 用单线程还能这么快？」——IO 密集 + 事件循环（Nginx 是多 worker 单线程、Redis 主线程单线程），同一个道理
  • 「asyncio 的超时和取消怎么做？」——asyncio.wait_for / CancelledError，关键是把取消沿调用链传下去（CORE-07）
  • 「什么是背压（backpressure）？」——上游生产快于下游消费时必须让上游慢下来（限队列长度、拒绝），否则内存被队列吃光

EnergyOps 的服务端——采集/聚合是 IO 密集、且要同时管很多任务，异步是自然选择；RuleArena 的 Worker——如果里面有 CPU 密集的规则校验，要丢进程池，不能丢线程池（GIL）；数驭穹图的问数接口——一次请求里可能串行调好几次上游，每次都是 await 点，所以单机能并发很多个请求。

先算"时间花在哪"（IO 密集 vs CPU 密集的杠杆）→ 三种执行单元用同一指标比（单位开销 / 谁调度 / 共享什么）→ 从"谁调度"推出所有差异 → 事件循环 + epoll 一次问一批 → 量化 10 万并发的内存 → 协作式的代价（阻塞会卡死整个循环 + 三种解法）→ GIL（为什么多线程救不了 CPU 密集）→ 选型判据

并发的收益 = 等待时间占总时间的比例。 这句话同时决定了三件事：该不该用异步（IO 密集才值得）、asyncio 为什么能扛很多连接（同内存下单元数多两个数量级）、以及它最怕什么（一旦有代码不让出，等待时间就被浪费掉了）。
