题目

面试官问——"你们的长任务跑到一半挂了怎么办？checkpoint 里存什么？"

一 · 教材 从前提推到结论，不需要先会

1. 前提：状态必须分层，不能只存聊天记录

【事实】七张表 / 七个实体（study/04 的模型）：

实体作用关键字段
Thread会话 / 长期交互容器user、scope、memory refs
Run一次目标执行goal、status、versions、budget
Step一次模型或工具动作type、input/output refs、latency、error
Branch平行探索或用户回退分支parent_step、merge status
Checkpoint可恢复状态快照state version、resume node、side effects
Artifact大结果或中间产物URI、hash、ACL、schema、TTL
Event流式 / 审计事实sequence、kind、timestamp、trace IDs

【推导】"只存聊天记录"为什么不行：

聊天记录里有：模型说了什么
聊天记录里没有：哪些写操作已经真的发生了

→ 进程重启后，系统不知道第 7 步那个"创建工单"到底成没成
→ 重做可能重复建单，不重做可能漏掉

【事实】这正是原始素材点名的头号反例：

"只保存消息历史，进程重启后不知道哪些写操作已完成。"

【推论】根因是"聊天记录是给模型看的，不是给系统用的"——它记录的是对话，不是状态。系统要恢复，需要的是"我做到哪了、做过什么、还剩什么"。

到这里你应该能回答：为什么"我们的会话记录都存了数据库"不等于"我们的任务可以恢复"？

2. 一个 Step 应该记录什么【事实】

【事实】study/04 给的 schema（这一份可以直接背）：

{
  "run_id": "r1",              "step_id": "s7",           "sequence": 7,
  "kind": "tool",              "status": "succeeded",
  "model_version": "...",      "prompt_version": "p12",
  "tool_name": "create_ticket", "tool_version": "v3",
  "input_ref": "artifact://...", "output_ref": "artifact://...",
  "idempotency_key": "ticket:incident-42",
  "latency_ms": 824,           "token_usage": null,       "error_code": null
}

【推导】这份 schema 里有三组字段是"多余的"，但少了任何一组都恢复不了：

① 【版本】model_version / prompt_version / tool_version
   → 少了它，Replay 时不知道当时用的是什么版本，轨迹复现不出来

② 【引用而不是内容】input_ref / output_ref 指向 Artifact
   → 少了它，大产物会塞满状态表

③ 【幂等键】
   → 少了它，恢复时无法判断"这一步做过没有"（[[母题-A3-失败恢复与幂等]]）

【事实】原始素材的结论一句话：

"不要只存最终聊天文本，否则无法 Replay 和失败归因。"

【推论】这一条在面试里的价值：它把"日志"从"排错用的辅助材料"提升为"运行时的必要组成"——没有 Step 级的记录，Agent 的 Replay、失败归因、成本核算、权限审计四件事同时做不了。

3. Checkpoint 的核心：记两次，中间夹着"不确定窗口"【推导】

【事实】study/04 给的 checkpoint 时机：

① 进入 / 离开每个有业务意义的节点
② 【外部副作用之前】记录 intent
③ 【副作用完成后】记录结果与业务幂等键
④ 人工中断前
⑤ 大型子任务完成后
⑥ Context 压缩或分支合并后

【推导】为什么必须"前后各记一次"：

只记 ② （intent，无 result）：
  进程在调用中间崩掉 → 恢复时知道"本来要做 X"，但不知道做成没有
  → 【必须先查权威状态】（[[母题-A3-失败恢复与幂等]] 第 4 节）

只记 ③ （result，无 intent）：
  进程在调用中间崩掉 → 连"本来要做什么"都不知道
  → 【无从恢复】：既不知道该查什么状态，也不知道该不该重试

【结论】这两次 checkpoint 之间，正好夹着那个"不确定窗口"。 而正是这个窗口的存在，决定了恢复协议的第一步必须是查权威状态。

【推论】这是"checkpoint 不是简单序列化内存"的真正含义：内存序列化只会给你一个时间点的快照；而能恢复的 checkpoint 必须能回答"我停在了哪一步的哪一侧"——在 intent 之后、result 之前停的，和不在这两者之间的，处理方式完全不同。

到这里你应该能回答：为什么"每隔 30 秒存一次状态"这种做法，可能仍然无法恢复？

4. 恢复协议【事实】

【事实】study/04 的恢复流程：

读取 Checkpoint → 校验版本与完整性 → 【查询业务权威状态】
  → 副作用已发生？ → 是：补记结果 / 跳过重复
                   → 否：按策略重试或人工
  → 重建最小 Context → 从安全节点恢复

【推导】注意"查询业务权威状态"是独立的一步——它不是"顺手查一下"，是必要环节：

Checkpoint 里记的是【意图】（打算做 X）
业务系统里记的是【事实】（X 到底做了没有）
→ 两者可能不一致（就是那个不确定窗口）
→ 所以必须去问"事实"，而不是相信"意图"

【推断】这也解释了为什么恢复时要"重建最小 Context"而不是"恢复原 Context"：

原 Context 是当时那一刻的投影（可能已经很长、很脏）
恢复时应该【按当前状态重新装配】——[[母题-C1-上下文组装与窗口预算]] 的"上下文是视图"在这里落地

到这里你应该能回答：恢复时为什么不能直接用 checkpoint 里存的上下文？

5. 存储成本：checkpoint 不是越密越好【推导】

每次 checkpoint 约 50 KB
一个 50 步的 run → 50 个 checkpoint × 50 KB = 2.5 MB

若每天 10,000 个 run：
  2.5 MB × 10,000 = 25 GB / 天

【结论】"每一步都 checkpoint"的存储成本是每天 25 GB 量级。

【取舍】所以时机要按"业务意义"选，不是按"步"选：

值得记的：业务节点进出、副作用前后、人工中断前、子任务完成后、Context 压缩后
不必记的：纯只读的中间步骤（重做代价低）

【推导】更值钱的是"不做 checkpoint 的重做成本"：

一个 50 步的任务在第 45 步崩了，每步新增 2.5K token

无 checkpoint：从头重跑 45 步
  累计输入 = 2.5K × (45 × 46 / 2) = 2.5K × 1,035 = 2,587.5K

有 checkpoint（第 40 步）：只需重做 5 步
  累计输入 = 2.5K × (5 × 6 / 2) = 2.5K × 15 = 37.5K

差约 69 倍

【结论】checkpoint 的收益不在"省了多少存储"，在"少重做了多少步"——而且因为历史重发是平方累计的（[[母题-C1-上下文组装与窗口预算]]），重做 45 步比重做 5 步贵 69 倍，不是 9 倍。

到这里你应该能回答：为什么"长任务"比"短任务"更需要 checkpoint，而且需要的密度不同？

6. 持久化分两层：Checkpointer 与 Store【事实】

【事实】LangGraph 文档给的划分（这个划分很干净，值得直接吸收）：

CheckpointerStore
作用域单个 thread跨 thread
记忆类型短期、thread 级长期、跨 thread
访问方式在 graph config 里传 thread_id从节点或应用代码里读写
典型用途对话连续性、HITL、时间旅行、容错用户偏好、事实、共享知识

【推论】为什么必须分开：

如果混在一起（把长期记忆也塞进 checkpoint）：
  ① 每次 checkpoint 都要写它 —— 它其实没变，纯浪费
  ② 快照变重 —— 而快照是要在【每一次有意义的步骤】写的
  ③ 失效判断变复杂 —— "这次失败是因为 thread 状态变了，还是因为长期记忆变了？"

【推论】这个划分和 [[母题-C1-上下文组装与窗口预算]] 的"Context / State / Memory 三分"是同构的：

Checkpointer ≈ State（运行过程的结构化状态，thread 级）
Store       ≈ Long-term Memory（跨会话复用，需要治理）

到这里你应该能回答：为什么"用户偏好"不该存在 checkpoint 里？

7. 边界与常见误解

常见说法修正
"把消息历史存下来就能恢复"这是原始素材点名的头号反例。消息历史里有"模型说了什么"，没有"哪些写操作真的发生了"——重启后不知道第 7 步的建单成没成。必须记 Step 级的状态、版本和幂等键
"checkpoint 就是把内存序列化下来"不是。内存序列化只给一个时间点快照；能恢复的 checkpoint 必须能回答"停在某一步的哪一侧"——所以要副作用前记 intent、后记 result（第 3 节）
"每一步都 checkpoint 最安全"存储成本会失控（50 步 = 2.5 MB/run；每天 1 万 run = 25 GB/天）。时机按"业务意义"选：业务节点进出、副作用前后、中断前、压缩后——纯只读步骤不必记
"恢复时直接用 checkpoint 存的上下文就行"不行。上下文是"当时那一刻的视图"，恢复时应该按当前状态重建最小 Context——否则会把过期信息、已解决的中间产物一起带回来
"checkpoint 里记录的副作用说明它发生了"只能说明"打算做"。checkpoint 记意图，业务系统记事实——两者之间那个不确定窗口正是恢复协议必须先查权威状态的原因（[[母题-A3-失败恢复与幂等]]）
"长期记忆也存 checkpoint 里方便"会让快照变重、失效判断变复杂。LangGraph 的划分很清楚：Checkpointer 管单 thread 短期、Store 管跨 thread 长期——它们的更新频率和生命周期完全不同
"只存最终结果，中间步骤不用记"那就没法归因。原始素材的原话是"不要只存最终聊天文本，否则无法 Replay 和失败归因"。Step 级记录是 Replay、归因、成本核算、权限审计四件事共同的前提

【取舍】读成一句话：能恢复的关键不是"存得频繁"，是"存得位置对"——checkpoint 要卡在那个不确定窗口的两侧。

三 · 面试输出 闭卷口述 60 秒，再看结论

一个跑了几十步、做过若干写操作的长任务挂了——凭什么能安全地接着跑，而不是从头再来？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是 Agent 面试里最能看出"有没有真跑过长任务"的一题。Demo 级的答案会说"我们把状态存数据库"；做过的人会说出"checkpoint 前记 intent、后记结果"——因为只有记了两次，才知道那个"不确定窗口"里到底发生了什么。而且这一题直接对应 RuleArena 的 Thread/Run/Step 数据模型。

一句话结论 全卡唯一要背的锚点

长任务的状态必须分层——Thread / Run / Step / Branch / Checkpoint / Artifact / Event 七类实体；只存聊天历史恢复不了，因为里面没有"哪些写操作真的发生了"（原始素材点名的头号反例）。Step 级记录必须带三组字段：版本（model / prompt / tool，否则 Replay 不出来）、Artifact 引用（否则大产物塞满状态表）、幂等键（否则不知道做过没有）。checkpoint 的核心是"记两次"：副作用前记 intent、后记 result——这两次之间夹着的"不确定窗口"，正是恢复时必须先查权威状态的原因。持久化分两层：Checkpointer 管单 thread 短期状态、Store 管跨 thread 长期记忆（LangGraph 的划分），混在一起会让快照变重、失效判断变复杂。成本上：50 步每步都记是 2.5 MB/run、每天 25 GB 量级，所以时机按"业务意义"选；而收益远大于成本——50 步任务在第 45 步崩溃时，有 checkpoint 重做 5 步 vs 无 checkpoint 重做 45 步，差约 69 倍（因为历史重发是平方累计的）。
  • 七类实体（Thread / Run / Step / Branch / Checkpoint / Artifact / Event）
  • 只存聊天记录 = 头号反例
  • Step 记录三组必需字段（版本 · Artifact 引用 · 幂等键）
  • checkpoint 记两次：前 intent 后 result
  • 不确定窗口
  • 恢复协议六步（读 → 校验版本 → 查权威状态 → 判断副作用 → 重建最小 Context → 从安全节点恢复）
  • failed vs unknown
  • Checkpointer（单 thread）vs Store（跨 thread）
  • 存储 2.5 MB
  • run、25 GB
  • 天
  • 重做成本差 69 倍（平方累计）
  • Context 压缩后必须 checkpoint

展开（先自答，再看 · 默认收起，不进复训调度）

1. Checkpoint 存什么？

目标、运行状态、当前节点、结构化中间结果、Artifact 引用、剩余预算、版本、已完成副作用与幂等键、待审批动作。大结果存外部，敏感信息按权限治理。

2. 什么时间做 checkpoint？

进出业务节点、副作用前后、人工中断前、大型子任务完成后、Context 压缩或分支合并后。纯只读的中间步骤不必记（重做代价低，而存储成本高）。

3. Resume / Replay / Retry / Fork 有什么区别？

见 [[母题-A3-失败恢复与幂等]]：Resume 要把事做完、Replay 只复现轨迹（不重做副作用）、Retry 仅对可重试错误且有幂等保障、Fork 继承只读事实但不继承未批准写权限。

4. 为什么恢复时要"重建最小 Context"而不是"恢复原 Context"？

上下文是视图不是状态。恢复时按当前状态重新装配，才能避免把过期信息和已经解决的中间产物带回来（[[母题-C1-上下文组装与窗口预算]]）。

5. 框架（LangGraph 之类）能替我解决这些吗？

部分能：它提供 checkpointer / store / interrupt 这些机制。但框架不会替你决定：业务权威状态在哪、幂等键怎么设计、什么算"有业务意义的节点"、以及 Eval 的定义（study/04 的原话："框架不会替你决定业务权威状态、权限、幂等键和 Eval 定义"）。
  • 「人机确认（HITL）怎么实现？」——本质是一次"计划内的长暂停"：进入 WaitingApproval 状态 → checkpoint 保存待审批动作 → 释放进程 → 用户批准后从 checkpoint Resume。关键是"用户审批不占住进程"（study/04 的原话）。而且批准必须绑定具体动作摘要和版本，不能用一次"允许所有"永久放权（[[母题-A6-沙箱权限与可信执行]]）。
  • 「事件流（SSE）和 checkpoint 是什么关系？」——SSE 是"传输视图"，数据库状态才是权威。事件带递增 sequence，客户端断线后可以从 last event 恢复——但恢复的依据是数据库，不是事件流。这个区分和"上下文是视图"是同一条原理。

- RuleArena：Thread/Run/Step/Checkpoint/Artifact/Event 数据模型——这就是本卡七类实体在项目里的直接落地；每个步骤记录 Prompt/Model/Tool/Rule 版本正是"版本字段不能省"。 - EnergyOps：任务自愈——把现有的任务查询 / 重试升级为 durable task evidence，关键是补上"intent / result 两侧的 checkpoint"。

状态七类实体 → 只存聊天记录为什么不行 → Step 记录的三组必需字段 → checkpoint 记两次与不确定窗口 → 恢复协议六步 → 存储成本与时机选择 → 重做成本的 69 倍 → Checkpointer vs Store 的分层 → 收束到"位置比频率重要"

能恢复的关键不是"存得频繁"，是"存得位置对"。 checkpoint 要卡在不确定窗口的两侧——而恢复的第一步永远是去问"事实"（业务权威状态），而不是相信"意图"（checkpoint）。
