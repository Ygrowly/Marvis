题目

任务表 8000 万行，执行日志还在以每天百万条增长。你会按什么顺序处理？

一 · 教材 从前提推到结论，不需要先会

1. 前提：先定问题，"大"本身不构成动作的理由

【推导】"8000 万行"是三种完全不同的问题，对应完全不同的手段：

症状真问题对应手段
查询慢热查询在扫大量冷数据 / 索引不行先 M7（索引与 SQL），再冷热分离
写入慢 / 锁冲突事务边界大、锁范围大M13 / M10（分批 + 短事务）
单机容量到顶磁盘 / 内存 / 连接真的不够先归档，最后才分库分表

【推论】所以第一动作是定位症状，而不是拆表——"8000 万行"本身不构成任何动作的理由。

到这里你应该能回答：为什么"我们表到 8000 万行了"这句话，面试官听到会先反问"然后呢"？

2. 五步顺序（必须背，而且要能解释为什么）

① 先把索引和 SQL 做好
② 再把事务边界和锁冲突管好
③ 然后做冷热分离和归档
④ 再做读写分离
⑤ 单机真的扛不住了，再考虑分库分表

【推导】为什么是这个顺序：每一步的复杂度递增，且后面的步骤会改变前面步骤的优化对象——比如先分了表，再优化索引，索引设计会复杂一倍（每个分片都要建、且要考虑分片键）。

【推论】判据是一句话：便宜且可逆的先做，贵且难回头的后做。 而分库分表恰好是最贵、最难回头的那一步（见第 5 节）。

3. 冷热分离：让热查询只打热数据

【事实】原始素材的例子：最近 7 天的任务日志经常查，半年前的几乎只在审计时查。

问题不是"数据太多"，而是"热查询背着冷数据一起跑"。 具体有两个后果：

3.1 索引更深 → 每次查找多一次 IO【推导】

行宽 1KB、页 16KB → 每页 16 行；扇出按 1170 算

8000 万行：叶子页 = 8000万 ÷ 16 = 500 万页
           500万 ÷ 1170 ≈ 4273 个中间节点
           根（1170 个指针）覆盖不了 4273 → 需要再分一层
           → 树高 = 根 + 二级内部 + 一级内部 + 叶 = 【4 层】

归档后 800 万行：叶子页 = 800万 ÷ 16 = 50 万页
           50万 ÷ 1170 ≈ 427 个中间节点
           根可直接覆盖 427 → 树高 = 根 + 内部 + 叶 = 【3 层】

【结论】数据量降到 1/10，索引层数从 4 层降到 3 层——同样的点查，IO 次数少一次。而且这还没算冷数据把热数据挤出 buffer pool 的那部分损失（那部分是无条件的）。

3.2 做法【取舍】

按时间轴（最自然的切分轴）把近期热数据和历史冷数据分层——MySQL 里通常是"两张表 + 定期迁移"（在线表只留热数据），PG 里更优解是分区表——分区是数据库原生支持的分层，且"丢弃分区即归档"（[[母题-P16-分区表]]）。这是两边能力差异的一个直接体现。

4. 归档：从在线主链路移走（不等于删除）

不再高频访问的旧数据，别一直留在在线主表里拖性能。

【事实】特别适合归档的：执行日志、状态流转记录、任务事件流水——保留要求长，但在线查询需求低。

归档的三个关键点：

1. 不是 DELETE 完就结束——大批 DELETE 本身就是长事务 + 膨胀源（[[母题-M13-长事务为什么危险]]），要分批 + 低峰执行（下面给算式） 2. 归档表要有独立的索引与访问路径（审计查询还是存在的，不能"存进去就找不到"） 3. 归档要有明确的生命周期与合规口径（保留多久、谁来查、怎么查）——这一条是工程之外的纪律，但面试里说出来很加分

4.1 为什么不能一次性 DELETE【推导】

删除 7000 万行冷数据，每次删除产生约 200 字节 undo

一次性 DELETE：
  undo 峰值 ≈ 7000万 × 200B = 14 GB
  锁持有 = 整个删除时长（可能几十分钟）
  而且这是一条【长事务】——purge 全程停摆（M13）

分批（每批 1 万行，共 7000 批）：
  undo 峰值 ≈ 1万 × 200B = 2 MB        （降到 1/7000）
  锁持有 = 单批时长

【结论】"归档"这个动作本身也是数据治理的一部分——用错方法的归档，会把长事务问题原样引入一遍。

到这里你应该能回答：为什么"把老数据 DELETE 掉"听起来是清理，实际是制造问题？

5. 分库分表：最后一步，四项代价要背

它通常更像最后一步，而不是起手式。

代价说明
路由变复杂分片键决定数据在哪，所有查询都要带上分片键，否则广播到所有分片
聚合和分页更麻烦跨分片的 count / ORDER BY LIMIT 要在各分片执行再合并，深分页几乎不可用（[[母题-M7-慢查询与SQL优化手段]] 的深分页问题在这里更难解）
跨分片事务更难本地事务不再够用，要么业务上避免跨分片写，要么引入分布式事务（复杂度陡增）
扩容迁移更重分片数固定后，扩容要迁移数据（下面给算式），是高风险操作

5.1 分片键为什么"最难改"【推导】

从 4 个分片扩到 8 个分片，按 hash 取模分片：

  一个键的归属 = hash(key) % 分片数
  4 分片时：hash % 4
  8 分片时：hash % 8

  若 hash % 8 < 4 → 归属不变（占一半）
  若 hash % 8 ≥ 4 → 归属改变（占一半）

  → 约 50% 的数据需要跨分片迁移

【结论】换分片键或扩分片数 = 一次全量级别的数据迁移。 所以分片键是整套设计里最难改的决定——这也是"能不能用范围分片 / 一致性哈希做局部迁移"值得提前想的原因。

5.2 分片键怎么选【事实】

按最高频查询路径选——让绝大多数查询能带上分片键，避免广播。

【推论】所以分片键不是"数据本身的属性"，而是"你的查询形状的属性"——这句话是分片设计的核心。选型时必须基于真实的查询分布（哪些字段出现在 WHERE 里、频率多少），而不是"字段看起来像 ID"。这一条和 [[母题-P16-分区表]] 的"分区键必须进大部分查询条件"是同一个原则。

【事实】顺带一条：MySQL 生态里有成熟中间件（ShardingSphere 之类），但本模块边界里明确写了"不深入它的源码"——面试里说"知道选型与代价，未深入源码"是诚实且合格的回答。

6. 边界与常见误解

常见说法修正
"8000 万行了，赶紧分库分表"行数从来不是分表的直接理由。真正的信号是：索引与 SQL 已优化到位、事务已拆批、冷数据已归档，仍然扛不住。而这三件事做完，很多表根本不需要分
"归档就是把历史数据 DELETE 掉"归档 ≠ 删除。① 一次性 DELETE 7000 万行是长事务 + 膨胀源（undo 峰值 14 GB），必须分批；② 归档表要保留独立索引与访问路径（审计还要查）；③ 要有生命周期与合规口径
"冷热分离和分库分表是一回事"完全不是。冷热分离是"按时间把数据分层"（同库或不同库）；分库分表是"按分片键水平拆分"（多库多表）。前者解决"热查询背着冷数据"，后者解决"单机容量 / 写入上限"
"分片键用 ID 就行"分片键是"查询形状的属性"，不是"数据本身的属性"。选错了会导致大量查询广播到所有分片（等于没分）；而且它是最难改的决定（换密钥迁移约 50% 数据）
"先分表，再慢慢优化索引"顺序反了。分表之后每个分片都要建索引、还要考虑分片键，复杂度翻倍；而且分表会改变前面步骤的优化对象（第 2 节的判据）
"跨分片事务用分布式事务解决就好"最好的答案是"业务上避免跨分片写"（把强一致的数据放同一分片，即按业务单元分片）；实在避免不了才上分布式事务——那是复杂度的新台阶（见追问 2）
"MySQL 要分库分表，所以 PG 也要"PG 侧对应的问题通常是分区设计，而不是分库分表。说的时候要说清楚讲的是哪一套

【取舍】读成一句话："'数据量大'本身不是问题，'热查询背着冷数据跑'才是问题"——所以治理的第一动作永远是"把热和冷分开"，而不是"把大表拆开"。两者听起来像，做的完全是不同的事。

三 · 面试输出 闭卷口述 60 秒，再看结论

冷热分离、归档、读写分离、分库分表——它们分别解决什么？为什么不是一上来就分库分表？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是主线六的收口题，而且它有一个几乎所有人都会答错的顺序问题——"数据量大 = 分库分表"。原始素材给出的五步顺序是这道题的灵魂，它同时考验克制（知道什么时候不动）和视野（知道每一步解决什么）。而且它和 [[母题-P16-分区表]] 合流：有持续清理需求的大表，分区的"丢弃分区"就是归档的最优解。

一句话结论 全卡唯一要背的锚点

"数据量大"本身不是问题，"热查询背着冷数据跑"才是问题。 所以治理顺序是五步：① 索引与 SQL做好 → ② 事务边界与锁冲突管好 → ③ 冷热分离与归档 → ④ 读写分离 → ⑤ 单机真的扛不住才分库分表。这个顺序的依据是"便宜且可逆的先做，贵且难回头的后做"——而分库分表有四项代价：路由变复杂（查询必须带分片键，否则广播）、跨分片聚合分页难、跨分片事务难、扩容要迁移约 50% 的数据。冷热分离按时间轴把热数据与冷数据分层（8000 万行归档到 800 万行，索引从 4 层降到 3 层）；归档 ≠ 删除，要分批搬分批删（否则 7000 万行一次性 DELETE 会产生约 14 GB undo、拖成长事务）；分片键不是"数据本身的属性"，是"查询形状的属性"，而且它最难改。

先定问题：「数据量大」本身不是问题，「热查询背着冷数据跑」才是。所以治理顺序五步：① 索引与 SQL 做好 → ② 事务边界与锁冲突管好 → ③ 冷热分离与归档 → ④ 读写分离 → ⑤ 单机真的扛不住才分库分表。依据只有一条：便宜且可逆的先做，贵且难回头的后做。

冷热分离是按时间轴把热数据与冷数据分层，8000 万行归档到 800 万行，索引从 4 层降到 3 层。归档不等于删除：一次性 DELETE 7000 万行是长事务加膨胀源（undo 峰值到约 14 GB），必须分批搬、分批删；而且归档表要保留独立索引和访问路径，审计还要查。

分库分表有四项代价：路由变复杂（查询必须带分片键，否则广播）、跨分片聚合分页难、跨分片事务难、扩容要迁移约 50% 的数据。分片键是「查询形状的属性」，不是数据本身的属性，选错会导致大量查询广播到所有分片，而它又是最难改的决定。

MySQL 的归档靠"两张表 + 迁移"；PG 可以用分区 + DROP 分区。MySQL 的分库分表是常见架构手段（有 ShardingSphere 生态）；PG 更常用原生分区与 FDW，分库分表相对少。说的时候要说清楚自己讲的是哪一套，别把"MySQL 需要分库分表"当成通用结论——PG 侧对应的问题是分区设计。

1. 分片键选错了怎么办？

分片键是"最难改的决定"：改它要全量重分布数据，扩容也要迁移约 50%。所以选型必须基于真实的查询分布，而不是"字段看起来像 ID"。这和 [[母题-P16-分区表]] 的"分区键必须进大部分查询条件"是同一个原则。

2. 跨分片的事务怎么办？

最好的答案是"业务上避免跨分片写"（把强一致的数据放同一分片，即按业务单元分片）；实在避免不了才考虑分布式事务——那是复杂度的新台阶。RuleArena 的"至少一次投递 + 幂等消费者 + 权威查询"替代 exactly-once 就是同一思路：跨边界的正确性优先用幂等解决，而不是用强一致事务硬扛（[[母题-P19-唯一约束与UPSERT]]）。

3. 归档和分区怎么选？

MySQL：两张表 + 定期迁移（应用管理）；PG：分区表 + DROP 分区（数据库管理）。PG 的方案更顺——"丢弃分区"几乎瞬时且不产生死元组；MySQL 的 "DELETE + 迁移"是长事务与膨胀源。这条对照能同时展示两边的能力差异。

4. 8000 万行必须分表吗？

不一定。单表几千万行在索引合理时完全可服务；真正的信号是：索引与 SQL 已优化到位、事务已拆批、冷数据已归档，仍然扛不住。"行数"从来不是分表的直接理由。
  • 「冷热分离和分库分表的区别？」——冷热分离按时间分层（解决"热查询背着冷数据"），分库分表按分片键水平拆分（解决"单机容量 / 写入上限"）。两个不同的问题。
  • 「读写分离排第几步？为什么？」——第四步。因为它要显式处理延迟语义（[[母题-M14-主从复制与延迟]]），复杂度不是免费的——所以排在"改代码"和"搬数据"之后，排在"改架构"之前。
  • 「EnergyOps 的四层事实表算什么？」——本质上就是应用层的冷热/粒度分离：Raw 层不直接给报表查，hourly / daily 才给。这是"冷热分离"思想在数据建模上的体现。

- EnergyOps 的四层事实表——本质上就是应用层的冷热/粒度分离（Raw 层不直接给报表查，hourly/daily 才给）。 - RuleArena 的事件流水——典型的"追加写 + 归档"场景。
