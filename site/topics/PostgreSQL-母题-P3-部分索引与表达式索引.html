题目

agent_runs 表里 99% 的行都是终态（COMPLETED / FAILED），只有少量是活跃态（QUEUED / RUNNING / WAITING_APPROVAL）——但调度器每秒都在查这些活跃行。给 status 建一个全表索引，浪费在哪？

三 · 面试输出 闭卷口述 60 秒，再看结论

部分索引（Partial Index）与表达式索引：什么场景能省一大截？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是 PG 相对 MySQL 的一个实打实的优势，也是「索引设计」和「索引堆砌」的分界线。它同时回答了另外两个高频追问——「索引是不是越多越好」（不是，所以要把索引做小）和「函数为什么导致索引失效」（PG 有解）。能主动提这一条，说明你真的是在 PG 上做过优化。

一句话结论 全卡唯一要背的锚点

部分索引 = 只给满足谓词的行建索引，让索引体积和「热子集」成正比而不是跟全表成正比（省空间、省写入、省 VACUUM 负担）；表达式索引 = 把计算结果作为索引键，让 lower(email) 这种「函数写在列上」的条件也能走索引。代价只有一条：查询条件必须能匹配谓词 / 表达式——部分索引的 WHERE 要能被「证明蕴含」，表达式索引要求函数确定性（IMMUTABLE）。
  • WHERE 谓词
  • 只索引热子集
  • 谓词必须匹配（可证明蕴含）
  • 函数确定性 IMMUTABLE
  • 部分唯一索引
  • 软删除

卡住时靠这几个词重建整条链。

RuleArena 的任务队列（status 只索引活跃态，正是上面那条 SQL 的真实场景）；数驭穹图的同步任务表（只查未完成的任务）。方言差异（面试安全底线）：MySQL 没有部分索引，同需求要么靠前置过滤 + 组合索引，要么靠业务层改写。被问到时正确说法是「PG 用部分索引；MySQL 里我会用 (status, updated_at) 的联合索引，靠最左列过滤，但索引里仍然包含终态行」。

全表索引浪费在哪 → 部分索引的机制 → 谓词必须匹配的规则 → 表达式索引解决什么问题 → 两者组合（部分唯一索引）→ 判据与边界

索引的价值 = 它服务的那部分查询的频率 × 被索引集合的大小。 部分索引直接砍掉第二个因子——「只用得上 1% 的行，就不该为 100% 的行付维护成本」。

讲解

原理分解

一、全表索引浪费在哪

调度器只查活跃态，但全表索引包含所有行：

浪费维度具体表现
体积99% 的索引项永远不会被这次查询用到，却一直占空间、占缓存
写入每次「终态化」的更新都要维护这个索引项——而它永远不会被那条查询用到
VACUUM 负担索引项越多，autovacuum 要清理的索引页越多（这是 PG 特有的第三项，见 P4）
统计信息选择性估算被大量无用值稀释

二、部分索引：把索引做小

CREATE INDEX idx_runs_active
ON agent_runs (tenant_id, updated_at)
WHERE status IN ('QUEUED', 'RUNNING', 'WAITING_APPROVAL');

效果：索引里只有活跃行 → 体积涨落跟随活跃量（稳定在一个小规模），终态化的写入完全不碰这个索引。

这就是「调度器扫活跃任务」这类场景的标准做法——用「状态 + 时间」的队列式捞取，索引只覆盖队内元素。

唯一的关键规则：谓词必须匹配（可证明蕴含）。

查询能否用上面的索引
WHERE status = 'RUNNING'✅ 能——RUNNING 蕴含在 IN (...) 里
WHERE status IN ('QUEUED','RUNNING')✅ 能
WHERE status = 'COMPLETED'❌ 不能
WHERE updated_at > ?（不带 status）❌ 不能——谓词缺失，PG 无法证明蕴含

最后一行是最容易踩的：「我明明有索引，为什么不走？」——因为查询条件里没有那句 WHERE 谓词，PG 不敢用（用了会漏掉终态行）。这时只能改写查询条件，不能靠加索引解决。

三、表达式索引：让函数也能走索引

CREATE UNIQUE INDEX idx_users_email_lower ON users (lower(email));

问题：WHERE lower(email) = ? 在函数写在列上的情况下，普通索引完全用不上（索引里存的是原始值，不是 lower() 之后的值）。

PG 的解法：把 lower(email) 的结果本身作为索引键。于是「函数导致索引失效」这件事在 PG 里是可以修的——不是「必须避免写函数」，而是「要么避免，要么为它建表达式索引」。

两个硬约束：

1. 函数必须是 IMMUTABLE（确定性）。lower() 是；now() 不是（每次结果不同），所以不能在表达式索引里用。这是选型前必须查的一件事。 2. 查询必须写完全一样的表达式。lower(email) 的索引，upper(email) 或 email ILIKE ? 都用不上。所以表达式索引某种程度上是「给某一条 SQL 定制的」。

四、两者组合：部分唯一索引（软删除场景的经典解）

需求：邮箱唯一，但只在未删除的行里唯一（软删除后允许同邮箱重新注册）。

CREATE UNIQUE INDEX idx_users_email_active
ON users (lower(email))
WHERE deleted_at IS NULL;

一条语句同时用了部分 + 唯一 + 表达式：只对「未删除」的行（部分）保证 lower(email)（表达式）唯一。这是最能体现「索引是为业务规则服务」的一个例子——业务说的是「未删除的邮箱唯一」，索引就应该只约束那部分行。

MySQL 没有部分索引，同场景通常要靠「软删除时改写唯一列（拼一个后缀）」绕过去——这是一个可以主动说出来的方言差异。
