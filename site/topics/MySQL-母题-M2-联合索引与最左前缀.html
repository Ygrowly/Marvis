必懂 3 件事（① 索引的价值是少扫行 ② 字典序是什么 ③ 范围列截断的准确含义）· 读完约 10 分钟 · 需要先懂：[[母题-M1-为什么用B+树]]（索引是有序结构）

题目

任务表要支持这条调度 SQL：

SELECT id, status, next_retry_time, priority
FROM task
WHERE status = 'PENDING'
  AND next_retry_time <= NOW()
ORDER BY priority DESC, id ASC
LIMIT 100;

联合索引该怎么建？为什么 (a, b, c) 能用上 a = 1 和 a = 1 AND b = 2，却用不上单独 b = 2？

一 · 教材 从前提推到结论，不需要先会

1. 前提：索引的价值只有一个——少扫

1.1 先固定唯一指标

[[母题-M1-为什么用B+树]] 已经推出：磁盘索引的成本就是 IO 次数。但那条结论只说到了定位。

真实查询读的不是一行，是一段。所以本卡把指标再推进一步：

【推导】一条查询的成本 = 扫过的索引项数 + 回表次数。 这两个数都是「行数」的函数，不是「树高」的函数。

为什么要先说这个：树高永远是 3 层（M1 算过），它对任何查询都一样，所以它解释不了"为什么换个索引顺序就快 30 倍"。能解释的是扫了多少行、回了多少次表。

到这里你应该能回答：为什么"索引让查询从全表扫变成 3 次 IO"这句话，在真实查询里基本不成立？

1.2 有序性能被用来做三件事【推导】

索引是排好序的，这份有序性只有三种用法：

用法靠什么效果
定位二分找到起点不用从头扫
截断扫到条件不满足就停不用扫到末尾
免排序读出来天然有序省掉 filesort

三件事共享同一个前提： 满足条件的记录必须在索引里连着排。一旦不连续，"扫到不满足就停"就失效——因为后面可能还有满足的。

这就是最左前缀的全部由来。 后面三节都在讲这一句话。

2. 联合索引是一片什么形状的数据

2.1 字典序（lexicographic order）是什么【事实】

定义：多列排序时，先按第一列排；第一列相同的，再按第二列排；以此类推。

它就是我们排电话簿的方式：先按姓排，姓相同的再按名排。不是"三个列各自有序"，而是"逐层细分"。

索引 (status, next_retry_time, priority) 的真实形状：

status='DONE'     ┐
status='PENDING'  ├─ 大段：先按 status 分成几块
status='RUNNING'  ┘
   ↓ 每一块内部
next_retry_time 递增
   ↓ 每一个 next_retry_time 值内部
priority 递增

2.2 由此得到「可定位区间」

定义：一个查询条件，如果能确定索引里的某一段连续区间必然包含全部结果、且区间外必然没有，就说它能确定一个可定位区间。

一旦有区间：起点二分（O(log N)），然后顺序扫到区间末尾就停——扫描量 = 区间长度，而不是全表。

量化的对照（1000 万行，status 三个值均匀分布，next_retry_time <= NOW() 命中约 100 万行）：

索引扫描情况扫过的索引项
(status, next_retry_time)status 切出约 333 万行的连续段 → 段内再按 time 二分到起点约 3.3 万
(next_retry_time, status)time 范围切出约 100 万行的连续段 → 段内再筛 status约 100 万

【推导】同样的字段、同样的条件，只是顺序不同，扫描量差约 30 倍。 字段顺序不是风格问题，是成本问题。

2.3 为什么"局部有序"等于"无序"

关键在 2.1 那张图的段与段之间。

next_retry_time 在每个 status 段内递增，但 DONE 段的第一条可能比 PENDING 段的最后一条还早。所以从全局看，next_retry_time 是乱序的。

【推导】单独用 next_retry_time 查，找不到任何连续区间——满足条件的记录散落在每一个 status 段里，只能逐段扫（或者干脆全索引扫描）。

这就是"用不上索引"的准确含义：不是报错，是退化成"扫描量 ≈ 全部"。

3. 最左前缀：把结论一条条推出来

3.1 四种条件逐个判

拿索引 (a, b, c)：

查询条件能用上为什么
a = 1✅ 定位所有 a=1 的记录在索引里连续
a = 1 AND b = 2✅ 定位连续段内继续细分，仍然是连续的
a = 1 AND b = 2 AND c = 3✅ 精确定位三层细分，直接命中
a = 1 AND c = 3⚠️ 部分能用 a 切段；c 缩小不了扫描范围，但能减少回表（见 3.3）
b = 2（单独）❌b 只在每个 a 段内有序，全局无序
c = 3（单独）❌同上，而且是最小范围

规律一句话：从最左列开始、连续不断的那一段，才能用来缩小扫描范围（定位 + 截断）。

3.2 为什么 WHERE b = 2 AND a = 1 和反过来写没区别【事实】

优化器会重排条件。 联合索引的匹配看的是列集合，不是 SQL 里的书写顺序。

所以"把等值条件写前面"这种说法，对人读有用，对执行计划没用。能决定顺序的是索引定义，不是 SQL 文本。

3.3 范围列截断：一句必须说准的话

拿 (a, b, c) 和 a = 1 AND b > 5 AND c = 3：

a = 1        → 切出一个连续段
b > 5        → 段内二分到起点，然后顺序扫到段尾      ← 扫描范围到这里的确定
c = 3        → 扫描过程中逐个判断                      ← 缩小不了范围

【推导】范围列之后的列，失去的是"缩小扫描范围"的能力，没有失去"过滤"的能力。

MySQL 5.6+ 的索引下推（ICP, Index Condition Pushdown）正是做这件事：把 c = 3 的判断下推到索引层，不满足的索引项直接不回表。

所以对"范围后面的列"，准确的说法是：

说法对不对
"范围列后面的索引列全部失效"❌ 过度简化
"范围列后面的列不能缩小扫描范围，但可以在索引层过滤、减少回表"✅

【取舍】ICP 能省回表，但省不掉扫描——b > 5 范围内的每个索引项还是要读一遍。所以"扫描量"永远是第一位的，ICP 是第二位的优化。

4. 字段顺序怎么定（围绕执行路径，不围绕字段热度）

4.1 三条规则

1. 等值列在前 —— 等值条件切出的段最短，越早切段，后面所有步骤的基数越小。 2. 范围列尽量靠后 —— 它之后的列失去缩小范围的能力，所以别把还想用来定位的列排在它后面。 3. 排序列接在最后 —— 让 ORDER BY 直接吃索引的有序性，避免 filesort。

4.2 第 3 条的边界（容易答错）

ORDER BY 能不能免掉排序，取决于扫描结果是否天然有序：

查询能否免 filesort
WHERE a = 1 AND b = 2 ORDER BY c✅ 能。a、b 都是等值 → 落在连续段内，c 递增
WHERE a = 1 ORDER BY b, c✅ 能。同一 a 段内 b 递增、b 相同则 c 递增
WHERE a = 1 AND b > 5 ORDER BY c❌ 不能。会扫过多个不同的 b 值，c 只在每个 b 内部有序 → 全局无序
WHERE a = 1 AND b > 5 ORDER BY b, c✅ 能。先按 b 排再按 c 排，正好是索引顺序

【推导】判据不是"有没有范围列"，而是"扫描结果在索引顺序上是不是单调的"。 范围列本身不破坏排序，范围列之后的列被 ORDER BY 单独使用才破坏排序。

4.3 回到那条调度 SQL

WHERE status = 'PENDING' AND next_retry_time <= NOW()
ORDER BY priority DESC, id ASC
LIMIT 100

按规则推：

列角色放哪
status等值第一位（切出最短的段）
next_retry_time范围第二位（它之后的列失去定位能力）
priority排序第三位 —— 但 priority DESC 与索引的 ASC 方向相反，且扫描跨多个 time 值，所以仍会出现 filesort

【取舍】这里没有完美解，只能在两种代价里选：

  • 索引 (status, next_retry_time, priority)：扫描量最小（约 3.3 万），但要 filesort 排 100 行后再取 100 条 → 排序对象是 3.3 万行，代价大
  • 拆成两步：先用索引取主键集合，再在应用层/子查询里排 → 复杂度上去了

还有一个更常见的做法：把 priority 提前，改成 (status, priority, next_retry_time)。这样排序免费，但 next_retry_time 的范围条件就缩小不了范围了——这时候要看哪一边的选择度高。选哪个取决于数据分布，面试时能把这两个方案的代价说清楚，比背一个"标准答案"更有价值。

5. 失效场景（含"优化器主动放弃"）

场景为什么失效
列上做函数 / 运算：WHERE YEAR(created_at) = 2026破坏了「按列原值有序」这个前提——索引里没有 YEAR(created_at) 的顺序
隐式类型转换：WHERE phone = 13800138000（phone 是 varchar）等价于对列做了类型转换，同上
前导模糊：LIKE '%abc'前缀不定，无法定位区间起点
OR 里有一个非索引列两边都要全表扫，索引那一半白做
!= / NOT IN命中区间过于分散，"可定位区间"退化成多个小段，加起来接近全表
选择度太低优化器算过成本后主动放弃索引，走全表

最后一条最容易误判：索引失效不一定是写法错了。像 status 只有 3 个值，走索引要"扫 1/3 的索引 + 回表 1/3 的行"，而全表扫是顺序读——优化器的成本模型会选后者，这是正确的决定。

【推论】所以"为什么这条 SQL 没走索引"的第一问不是"写法有什么问题"，而是"这个条件的区分度够不够"。

6. 边界与常见误解

常见说法修正
"范围列后面的索引列全失效"【推导】准确说是失去缩小扫描范围的能力，但仍可通过 ICP 在索引层过滤、减少回表
"WHERE 的条件顺序会影响索引匹配"【事实】不会。优化器重排条件，看的是列集合
"索引列越多越好"【取舍】每加一列都会让索引变宽、写入变慢（见 [[母题-M4-索引代价与大表变更]]）。联合索引的收益来自"一条索引服务多条查询"，不是来自列多
"建了索引优化器就会用"【取舍】选择度低时它会主动放弃。先问区分度，再问写法
"前缀索引可以替代联合索引"【取舍】前缀索引让索引变窄，但丢掉了完整有序性，不能用于精确的定位与排序

一句话结论 全卡唯一要背的锚点

联合索引 (a, b, c) 是按字典序排的——先按 a、a 相同按 b、b 相同按 c。所以只有从最左列开始的连续前缀才能确定一个"可定位区间"，从而缩小扫描范围；中间的列断开，后面的列就只能过滤、不能定位。
  • 字典序逐层细分
  • 可定位区间必须连续
  • 扫描量 = 区间长度
  • 局部有序 = 全局无序
  • 等值在前范围靠后
  • 范围列之后失去定位保留过滤（ICP）
  • 选择度低优化器主动放弃

卡住时靠这几个词重建整条链。

展开（先自答，再看 · 默认收起，不进复训调度）

1. 为什么 WHERE b = 2 用不上 (a, b, c)？

因为 b 在每个 a 段内有序、段之间无序，找不到一个包含全部结果的连续区间。"用不上"准确含义是退化成扫描量≈全部，不是报错。

2. 范围列后面的列到底还能不能用？

能过滤（ICP），不能定位。省回表，不省扫描。

3. (a, b) 和 (b, a) 该选哪个？

看去重后的基数（选择度）和查询比例。等值列在前能让切出的段最短；但如果业务里 b 才是高频等值且区分度高，两个顺序的收益就会反转。这是数据分布问题，不是规则问题。

4. 为什么 status 这种列建了索引也不走？

选择度太低，优化器算成本后主动放弃。先看区分度，再看写法。
  • (a, b, c) 与 (c, b, a) 在什么查询下效果不同？（围绕高频执行路径，不围绕字段个数）
  • 索引下推（ICP）和覆盖索引的区别？（ICP 减少回表次数，覆盖索引免掉回表）
  • 覆盖索引能不能绕过最左前缀？（不能。它解决的是回表，不是有序性）

EnergyOps 的四层事实表联合索引、数驭穹图的元数据检索、RuleArena 的"按状态取一批待重试任务"——任何"任务调度 + 按优先级取批"的场景都长这样，因为后台系统的标配查询就是"等值状态 + 时间范围 + 排序 + LIMIT"。

成本指标是扫过的行数（不是树高）→ 字典序是什么 → 可定位区间 → 最左前缀是这个要求的后果 → 四种条件逐个判 → 范围列截断的准确说法（失去定位、保留 ICP 过滤）→ 字段顺序三条规则 + 排序的边界 → 失效场景（含优化器主动放弃）

索引的有序性只有三种用法——定位、截断、免排序，三者共享同一个前提：满足条件的记录在索引里连续。 字段顺序就是在"让哪段连续"上做取舍。
