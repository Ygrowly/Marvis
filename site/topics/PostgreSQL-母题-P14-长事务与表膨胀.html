题目

一个开了两小时、只做 SELECT、一行都没改过的事务，会让表变大吗？

三 · 面试输出 闭卷口述 60 秒，再看结论

长事务为什么会造成表膨胀？机制是什么？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是 PG 里最反直觉、也最容易在生产上踩的一题——「只读事务无害」是错的。而且它是主线五的核心：膨胀不是一个独立现象，它是「长事务按住了回收边界」的必然结果。 答得出这条链，P13（MVCC）和 P15（VACUUM）就串成了一条线；答不出，那两道题也只是两个孤立的知识点。

一句话结论 全卡唯一要背的锚点

会。 膨胀的机制是「旧的死元组不能被回收」：VACUUM 只能回收「对所有活跃快照都不可见」的死元组——长事务持有的快照还需要看到旧版本，于是 VACUUM 不敢删，死元组一直堆积 → 表页越来越多 → 扫描同样的行要读更多页、回表更贵、缓存命中率下降。所以长事务的危害不是「持锁久」，而是它按住了一个旧快照，让空间回收停摆。
  • 活跃快照按住回收
  • 回收的判据是「对所有人不可见」
  • 死元组积压 → 表与索引一起膨胀
  • idle in transaction
  • 只读长事务同样有害
  • 监控最老事务

卡住时靠这几个词重建整条链。

展开（先自答，再看 · 默认收起，不进复训调度）

EnergyOps 的聚合表重算（15 分钟窗口持续重算 → 版本堆积最快，是最需要盯回收边界的表）；RuleArena 的Worker 长任务（如果任务在事务里等外部 HTTP，就会产生 idle in transaction——「事务边界只包数据库操作」这条纪律在这里最值钱）。方言差异（面试安全底线）：MySQL 的旧版本进 undo log、由 purge 线程自动回收，所以「长事务导致表膨胀」不是 MySQL 的主要话题（MySQL 长事务的主要危害是持锁久、undo 表空间膨胀）；PG 的长事务会直接按住空间回收。「MySQL 也需要 VACUUM」是明确错误。

膨胀的机制（回收边界）→ 为什么只读事务也有害 → 膨胀的连锁代价（扫描 / 回表 / 缓存）→ 怎么发现（监控哪几个视图）→ 怎么防（超时 + 拆批 + 别在事务里等外部）

回收的判据是「对所有人都不可见」，不是「对当前事务不可见」。 换句话说——表能不能瘦，由「最老的那个活跃快照」决定，不由「现在有多少死数据」决定。

通过证据：能用「回收边界 = 最老快照」把机制推一遍，并说清「只读长事务为什么同样有害」和该监控哪个指标。

讲解

原理分解

一、机制：回收边界由最老快照决定

结合 P13 的版本模型：

一个行版本被删/被更新后 → 变成「死元组」，但它还物理存在
VACUUM 判断「这个死元组能不能清掉」的唯一问题：
   还有没有活跃事务能看到它？
     有 → 不能删（删了那个事务就读不到了）
     没有 → 可以标记为可复用

所以 VACUUM 的清理边界 = 所有活跃快照里最老的那一个。

一个两小时前开始的事务 → 它的快照就是两小时前 → 这两小时内产生的所有死元组都不能回收。两小时的写入量全部变成"不能动的垃圾"。

这就是「长事务拖系统下水」的真实路径——不是它占了多少 CPU，而是它让整张表的回收停摆了两小时。

二、为什么「只读」也有害（最反直觉的一点）

因为回收看的是「快照」，不是「这个事务做了什么」。

  • 一个只读事务不做任何修改，看上去"人畜无害"；
  • 但它持有快照，而快照决定了回收边界；
  • 所以只要它开着，膨胀就在积累。

三种常见的「无害长事务」：

形态为什么出现危害
idle in transaction（开了事务但没提交、连接挂着）应用逻辑里 BEGIN 之后做了网络请求 / 等用户输入 / 调了慢接口最坏的形态：不干活但一直按住快照
长只读事务（报表、导出、全量扫描）一次性拉大量数据分析按快照 + 占备库回放
批处理事务（几千行一提交）「为了原子性把一批包在一个事务里」事务内的写入量本身就是膨胀源

三、膨胀的连锁代价

膨胀不只是"占空间"，它会污染整条查询链路：

表页变多
  → 同样的行数分布在更多页上
  → Seq Scan 要读更多页（同样的数据，更多 IO）
  → 索引查询的回表随机 IO 次数上升（P2：ctid 指向更多稀疏页）
  → 缓存命中率下降（shared_buffers 装不下有用的数据）
  → 于是查询整体变慢 → 更慢的查询又延长事务 → 环路加剧

这个环路值得记住：膨胀 → 查询变慢 → 事务变长 → 回收继续停摆 → 膨胀更严重。这就是为什么「PG 表膨胀」经常是性能事故的起点，而不是结果。

四、怎么发现（要能说出监控哪一个）

看什么用途
pg_stat_activity 里最老的活动事务 / 其 xmin（或 backend_xmin）回收边界——这是最直接的指标
「运行时间最长的事务」+「处于 idle in transaction 的连接」找出真正的肇事者
表的死元组数量 / 上次 VACUUM 时间（表级统计）判断哪张表在积累死元组
表与索引的实际大小 vs 有效数据量判断膨胀程度

面试里能说出「我盯的是最老事务的 xmin，也就是回收边界」这一句，就说明你真的理解了机制——因为大部分人只会说「看有没有长事务」。

五、怎么防（按有效性排序）

1. 设超时：idle_in_transaction_session_timeout（这条最有效，直接干掉"挂着不干活"的连接）、statement_timeout； 2. 拆批：大批处理拆成小事务分批提交（不要为了"原子性"把几万行包进一个事务）； 3. 别在事务里做外部 IO：网络调用、调外部服务、等人工确认——事务边界应该只包住数据库操作； 4. 调 autovacuum：对大表/高更新表单独设更激进的触发阈值（pg_stat_bgwriter 与表级统计是依据）； 5. 设计层：把「高频更新的列」排除出索引（利用 HOT，见 P13）、用状态表 / 追加式日志代替就地更新。

第 3 条是最容易被忽略的工程纪律：「事务里不调外部服务」和「事务里等用户输入」是同一类错误——它们都把「数据库锁与快照的持有时间」绑到了「外部系统的响应时间」上。
