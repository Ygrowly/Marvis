题目

一个两小时前开的只读事务，什么都没改，为什么会把线上写卡死？

一 · 教材 从前提推到结论，不需要先会

1. 机制：回收边界由最老快照决定

结合 P13 的版本模型：

一个行版本被删/被更新后 → 变成「死元组」，但它还物理存在
VACUUM 判断「这个死元组能不能清掉」的唯一问题：
   还有没有活跃事务能看到它？
     有 → 不能删（删了那个事务就读不到了）
     没有 → 可以标记为可复用

所以 VACUUM 的清理边界 = 所有活跃快照里最老的那一个。

【推导】把「一个两小时的长事务」的代价算出来：

表上写入 1000 TPS
一个事务在 2 小时前开始、现在还没提交

它的快照固定在 2 小时前
  → 这 2 小时内产生的所有死元组，都还【可能被它看到】
  → 因此【一个都不能回收】

压住的死元组 ≈ 1000 × 7200 = 【720 万个】

【结论】720 万个死元组——而且它们不只是堆里的 720 万个槽位，还会复制到每个索引里。

【推论】所以「长事务拖系统下水」的真实路径不是它占了多少 CPU，而是它让整张表的回收停摆了两小时。 一个只跑了几毫秒 CPU 的只读事务，和一次重计算，对膨胀的伤害可以完全一样。

到这里你应该能回答：为什么「这个事务很快，它只是开着」这句话在 PG 里是危险的？

2. 为什么「只读」也有害（最反直觉的一点）

因为回收看的是「快照」，不是「这个事务做了什么」。

  • 一个只读事务不做任何修改，看上去"人畜无害"；
  • 但它持有快照，而快照决定了回收边界；
  • 所以只要它开着，膨胀就在积累。

三种常见的「无害长事务」：

形态为什么出现危害
idle in transaction（开了事务但没提交、连接挂着）应用逻辑里 BEGIN 之后做了网络请求 / 等用户输入 / 调了慢接口最坏的形态：不干活但一直按住快照
长只读事务（报表、导出、全量扫描）一次性拉大量数据分析按快照 + 占备库回放（[[母题-P12-流复制与逻辑复制]]）
批处理事务（几千行一提交）「为了原子性把一批包在一个事务里」事务内的写入量本身就是膨胀源

【推论】第一种最值得强调，因为它有一个非常具体的技术原因：

idle in transaction 是唯一一种「不消耗 CPU、不占锁、但持续制造膨胀」的状态。

它不报错、不变慢、监控上看起来"连接数正常"——只会让表悄悄变胖。

【事实】这正是官方为什么给出 idle_in_transaction_session_timeout 这个参数——它存在的全部理由就是杀掉这种连接。 生产上不设它，等于允许任何人用一个忘记提交的事务把整张表按住。

到这里你应该能回答：为什么「连接池里有一堆 idle 连接」在 MySQL 里大概没事，在 PG 里可能是事故前兆？

3. 膨胀的连锁代价：一个正反馈环

膨胀不只是"占空间"，它会污染整条查询链路：

【推导】算一下膨胀对扫描的放大：

表 8000 万有效行，每行 200 字节 → 有效数据 16 GB

没有膨胀：Seq Scan 读 16 GB
膨胀到 2 倍（有效行只占一半的页）：
  → 同样的 8000 万行分布在 32 GB 里
  → Seq Scan 要读【32 GB】—— 同样的数据，两倍 IO

而缓存呢：
  shared_buffers 是固定的
  → 同样装得下的"有效行数"【减半】
  → 命中率下降 → 更多随机 IO

【结论】膨胀的代价是双重的：顺序扫描要读更多页，而且缓存能装下的有效数据变少。

【推论】而这两件事会形成环路：

表页变多
  → 同样的行数分布在更多页上
  → Seq Scan 要读更多页
  → 索引查询的回表随机 IO 次数上升（ctid 指向更稀疏的页）
  → 缓存命中率下降
  → 于是查询整体变慢
  → 更慢的查询又延长事务
  → 回收边界被按得更死
  → 膨胀更严重  ← 回到起点

这个环路值得记住：膨胀 → 查询变慢 → 事务变长 → 回收继续停摆 → 膨胀更严重。 这就是为什么「PG 表膨胀」经常是性能事故的【起点】，而不是结果。

【取舍】这个环也给出了唯一的破法：从任意一点切断都行，但切「事务变长」这一点最省力——因为它是一个【配置 + 代码习惯】问题，而不是一次数据迁移。

4. autovacuum 的两道门槛

【事实】官方给出的触发条件与默认值：

参数默认含义
autovacuum_vacuum_threshold50固定基数（行数）
autovacuum_vacuum_scale_factor0.2表大小的 20%
autovacuum_max_workers3同时最多 3 个 autovacuum 进程

【推导】把触发阈值算出来：

触发条件：过期的元组数 > 50 + 0.2 × 表行数

8000 万行的表：
  50 + 0.2 × 80,000,000 = 【1600 万行】

也就是说：要过期 1600 万个元组，autovacuum 才会来一次

【结论】大表的比例阈值意味着「要堆很多才动手」——而偏偏大表最经不起堆积。

【推论】所以大表通常需要【按表】调低比例（ALTER TABLE ... SET (autovacuum_vacuum_scale_factor = 0.02)），而不是全局调——全局调会让所有小表被过度清理。

【事实】但调阈值只是第一道门槛。第二道门槛更硬：

有长事务时，回收边界推不动——autovacuum 跑上去也清不掉东西（第 1 节）。

有离线复制槽时，WAL 不回收（[[母题-P12-流复制与逻辑复制]]）。

【推论】这两种是「看起来在跑但没效果」的典型：

监控上看到：autovacuum 进程在跑、跑完了、退出
  → 以为清理正常
实际：它扫了一遍，发现【所有死元组都还被旧快照需要】
  → 一个都没清掉
  → 表继续胖

【判据】所以「调 autovacuum」不是万能的，判断顺序必须是：

先问「有没有东西按住回收边界」（长事务 / 离线复制槽 / 备库反馈）→ 再问「阈值够不够激进」。

顺序反了，你会发现阈值调得再低也没用。

【事实】autovacuum_max_workers 只有 3 这件事也值得说：它意味着同一时间最多只有 3 张表在被清理——表多、每张都要清理时，会排队。而加大 workers 的代价是它们会争抢 IO。

到这里你应该能回答：为什么「我们开了 autovacuum」不能回答「你们的表为什么还是胖」？

5. 怎么发现（要能说出监控哪一个）

看什么用途
pg_stat_activity 里最老的活动事务及其 xmin（backend_xmin）回收边界——这是最直接的指标（[[母题-P13-MVCC与可见性]] 说过 xmin 是可见的系统列）
idle in transaction 的数量与时长膨胀的头号来源；要配 idle_in_transaction_session_timeout 自动杀
pg_stat_user_tables 的 n_dead_tup死元组堆积量
pg_stat_user_tables 的 last_autovacuum上次自动清理是什么时候——时间久 ≠ 没问题，可能是"跑了但清不掉"
表与索引的实际大小 vs 有效行数膨胀率；可用扩展（pgstattuple）或按 relpages 估算
pg_replication_slots 的 active 与保留 WAL离线复制槽（[[母题-P12-流复制与逻辑复制]]）

【推论】判据：

最有信息量的一件事是「最老快照有多老」。

它直接等于"回收边界离现在多远"，也就是"这段时间的写入全部变成了不能动的垃圾"。

6. 怎么防（按性价比排序）

① 设 idle_in_transaction_session_timeout（治 idle in transaction，成本最低）
② 设 statement_timeout（治跑飞的查询 → 治被迫变长的事务）
③ 代码层：绝不在事务里做网络 IO / 调外部接口 / 等人工（这是 ① 的病因）
④ 批处理拆批：几千行一提交 → 几百行一提交（同时降锁持有与 undo 峰值）
⑤ 大表按表调低 autovacuum 阈值（autovacuum_vacuum_scale_factor）
⑥ 需要在线重建时用 pg_repack，而不是 VACUUM FULL（P15）

【推论】第 ①② 是「保险丝」，第 ③ 是「治因」——只设超时不改代码，只是把事故从"表胖"换成"接口超时"：那个外部调用还是会在事务里，只是现在会被杀掉。 两者都要做。

7. 边界与常见误解

说法实际情况
「只读事务不会造成膨胀」会——回收看快照不看行为，开着就按住了边界
「autovacuum 开了就没问题」它有两道门槛——边界推不动时，它跑上去也清不掉东西
「事务要短是为了少占锁」在 PG 里更重要的理由是【别按住回收边界】
「表变大了说明数据变多了」PG 里「表大小」和「数据量」是两个概念（P13）
「清理跑过了，所以没问题」要看 n_dead_tup 有没有降下来，而不是看 last_autovacuum 有没有更新
「调大 autovacuum_max_workers 就快了」它只影响并发条数；边界被按住时，多几个 worker 也清不掉；而且会争抢 IO

长事务为什么危险？表膨胀是怎么发生的？

翻面对照自测，评分会进训练台的复训调度。

为什么重要：这是PG 最反直觉、也最容易造成真实事故的一条——MySQL 里的「长事务」主要是不放锁，PG 里的「长事务」是【不让回收】。 而且它解释了 PG DBA 为什么有一半时间在跟膨胀打交道，而 MySQL 那边几乎不用。

一句话结论 全卡唯一要背的锚点

VACUUM 只能回收「所有活跃快照都看不见」的死元组，所以回收边界 = 最老的那个活跃快照。一个长事务（包括只读的）会把回收边界钉在过去，这两小时内产生的所有死元组都不能清——表就这么胖起来的。膨胀又会让扫描读更多页、缓存命中率下降，于是查询变慢、事务更长、回收更停摆——这是一个正反馈环，而且 PG 表膨胀经常是性能事故的【起点】而不是结果。
  • 回收边界 = 最老快照
  • 只读事务也有害
  • idle in transaction
  • 死元组与索引条目一起堆
  • 膨胀 → 扫描变多 → 缓存命中率降
  • autovacuum_vacuum_scale_factor 0.2
  • autovacuum_max_workers 只有 3
  • pg_stat_activity 看 backend_xmin

展开（先自答，再看 · 默认收起，不进复训调度）

MySQL 的长事务主要危险是「不放锁 + undo 链长」，PG 的长事务主要危险是「按住回收边界」。所以「长事务要短」这句话在两边都成立，但理由完全不同——在 PG 里说「长事务的危险是它占着锁」，等于把最重要的那半边漏掉了。

1. 为什么「只读」也有害？

因为回收看的是快照，不是"这个事务做了什么"。 只读事务不做修改，但它持有快照，而快照决定了回收边界。 所以只要它开着，膨胀就在积累。 这条最反直觉，也最能区分"背过"和"懂了"。

2. idle in transaction 为什么是头号来源？

因为它不消耗 CPU、不占锁、不报错、监控上看起来正常，但持续按住回收边界。 它的病因几乎总是同一个：应用在 BEGIN 之后做了网络请求、调了外部接口、或者等用户输入。 idle_in_transaction_session_timeout 就是为它准备的。

3. 膨胀了怎么办？

三步，顺序不能反：① 先切断长事务（否则做什么都白做）；② 需要在线重建时用 pg_repack，而不是 VACUUM FULL（后者要排他锁 + 等量磁盘空间，[[母题-P15-VACUUM与事务ID回卷]]）；③ 最后才调 autovacuum 的阈值。

4. 备库上的长查询会造成主库膨胀吗？

会。hot_standby_feedback = on 时，备库会把"我还在读这些行"反馈给主库，主库就不清理它们——官方明确警告这「会造成主库的表膨胀」（[[母题-P12-流复制与逻辑复制]]）。所以"在备库上跑报表"这件事是有成本的，而且成本记在主库头上。

5. autovacuum_max_workers 调大有用吗？

只影响并发条数。边界被按住时，多几个 worker 也清不掉；而且它们会争抢 IO、互相拖慢。它是一个"清理能力"参数，不是一个"清理意愿"参数。
  • 「MySQL 的长事务和 PG 的长事务危险在哪不一样？」—— MySQL 主要是不放锁（阻塞别人）+ undo 链太长（回滚慢）；PG 是按住回收边界（制造膨胀）。所以 MySQL 里"只读长事务"危害小得多，而 PG 里它是头号制造者（[[母题-M13-长事务为什么危险]]）。
  • 「表膨胀会不会自己恢复？」—— 不会。普通 VACUUM 只是把空间标成可复用——如果后续写入量不够填回去，那些空闲空间就一直空在那里。 它会停在某个水平，但不会变小。

- EnergyOps 的四层事实表（高频重算 → 死元组产生最快，是最需要盯的）。 - RuleArena 的任务状态机（UPDATE status 极频繁；但因为 status 走 HOT 更新，堆上的版本链能就地清理——这是它没胖起来的原因）。 - 数驭穹图的同步任务（典型场景：BEGIN 之后调客户数据库的接口 —— 这正是 idle in transaction 的教科书成因）。

机制（回收边界）→ 为什么只读事务也有害 → 膨胀的连锁代价与正反馈环 → autovacuum 的两个门槛（触发阈值 + 回收边界） → 怎么发现（监控哪几个视图）→ 怎么防（超时 + 拆批 + 别在事务里等外部）

VACUUM 的清理边界由「最老快照」决定，而不是由「谁改了什么」决定。
