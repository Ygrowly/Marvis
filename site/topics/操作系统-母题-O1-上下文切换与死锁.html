题目

面试官问"进程和线程有什么区别"。你答完"是否共享地址空间"之后，他追问："那你为什么不多开线程？"——请用数字回答"线程不是越多越好"，并说清一次切换到底花了什么。

一 · 教材 从前提推到结论，不需要先会

1. 前提：Linux 其实不区分"线程"和"进程"

1.1 二者在操作系统里是什么【事实】

先各自介绍，再比较：

进程（process）：操作系统分配资源的基本单位。它拥有一个独立的虚拟地址空间（页表、代码段、数据段、堆、栈、文件描述符表、信号处理器）。

线程（thread）：进程内的执行单元。它共享所属进程的地址空间和大部分资源，只独占两样东西：寄存器状态和自己的栈。

【事实】关键的一层事实：Linux 内核里没有"线程"这个独立概念——线程和进程都是 task_struct（内核里叫"任务"），区别只在创建时传了哪些共享标志：

fork()            → 不共享地址空间               → 新 task_struct 有自己的 mm_struct
pthread_create()  → 走 clone()，带一组共享标志：
                    CLONE_VM       共享地址空间
                    CLONE_FS       共享文件系统信息
                    CLONE_FILES    共享文件描述符表
                    CLONE_SIGHAND  共享信号处理器
                    CLONE_THREAD   属于同一个线程组（同一个"进程号"）

【推导】所以"线程是轻量级进程"这个说法在 Linux 上是字面成立的——它就是"共享得更多的进程"。从这一句话，下面所有差异都能推出来：

共享了什么由此推出
地址空间共享线程间通信极便宜（直接读同一个变量）；进程间必须拷贝或走内核
地址空间共享同一进程内不换页表 → 切换便宜；跨进程要换页表 → 切换贵（第 2 节）
地址空间独立进程隔离最好（一个崩了不影响别的）；线程共享一切（一个线程野指针能带崩整个进程）

1.2 判断"开销"要用同一把尺子【推导】

【推导】这一节的标题是"线程开多了会更慢"，那就必须先说清"开销"指什么。执行单元的开销分三块，面试时能分开说就已经赢一半：

开销类型是什么什么时候发生
① 创建开销建地址空间 / 栈 / 内核对象一次性
② 切换开销换 CPU 上跑的东西每次被换下都发生——这是大头
③ 内存占用栈 + 内核对象常驻，决定你能开多少个

这三块的方向不一样：① 和 ③ 决定性"能不能开"，② 决定"开了之后还快不快"。第 2、3 节分别量化 ② 和 ③。

到这里你应该能回答：为什么"进程和线程的区别"这一题的真正考点是"共享了什么"而不是"谁更轻"？

2. 一次上下文切换到底做了什么（量化）

2.1 六步【事实】

上下文切换（context switch）：把 CPU 上正在跑的任务换下去、换另一个上来。

【事实】以 Linux 为例，完整过程六步：

① 触发：时间片用完（定时器中断）／主动阻塞（等 IO、sleep、抢不到锁）／被更高优先级抢占
② CPU 从用户态陷入内核态
③ 调度器挑下一个要跑的任务
④ 保存当前任务的 CPU 状态（寄存器、指令指针、栈指针）到它的 task_struct
⑤ 加载下一个任务的 CPU 状态
⑥ ★ 如果下一个任务属于【另一个进程】：写 CR3（页表基址寄存器）+ 处理 TLB 失效
⑦ 返回用户态，新任务从它上次停下的地方继续

【推导】第 ⑥ 步是进程切换和线程切换唯一的直接差别——同进程的线程共享页表，这一步被整个跳过。记住"差别只有一步"，比背一堆"线程更轻"要有用得多。

2.2 直接成本：微秒量级【事实】

⚠️ 2026-09-17 校验修正：本卡初版把直接成本写成"线程 0.73 μs / 进程 0.93 μs"，这是从一份二手测量文章里抄来的单一数据点，不能当【事实】用。多个独立来源（lmbench 的 lat_ctx、以及公开的 token 传递基准）给的是1.3–4 μs。已按下表改写，并明确标注数据的性质。

【事实】先把数据的性质说清楚：上下文切换没有唯一的"标准值"——它随 CPU 型号、内核版本、是否跨核迁移、负载高低变化很大。公开测量里常见的区间是 1–5 μs：

测量方式典型结果说明
lmbench 的 lat_ctx（现代 x86 服务器）约 1.3–1.5 μs隔离得较好，接近"纯"切换成本
简单 token 传递（两进程/两线程用管道来回）约 3–4 μs把调度与唤醒的开销也算进去了
高负载 + 跨核迁移10 μs 以上含间接成本（下一节）

【事实】所以面试时给"量级 + 方向"比给一位小数更安全：

  • 量级：微秒级（不是纳秒级，也不是"几百纳秒"）
  • 方向：线程切换比进程切换快约 20–30%（仅直接部分）

【推导】两者的直接差别只有一处（第 ⑥ 步：写 CR3 + 处理 TLB 失效），所以如果只算直接成本，"进程 per request"看起来只贵两三成，根本不值得讨论——真正的故事在下一节。

2.3 间接成本：这才是大头【推导】

【推导】切换真正的代价是"换过去之后的冷启动"，而它不出现在切换那一刻，而是分摊在切换之后的一段时间里：

间接成本机制量级
TLB 失效跨进程换页表 → 地址翻译缓存作废 → 后续访问要去走页表约 25 ns / 页（每页重走一次）
CPU 缓存污染L1/L2 里装的是上一个任务的数据，新任务要重新预热取决于工作集大小；L1 约 1 ns、L3 约 30–50 ns、内存约 100 ns，这个差距就是"冷启动"的成本
分支预测器失效预测器的历史属于上一个任务的代码难以直接量化

【推导】把 TLB 那一项算出来——但要注意它是一个"上限估计"，不是实测值：

跨进程切换后，假设新任务的工作集是 2MB：
  2MB / 4KB（一页）= 512 页
  每页一次页表遍历 ≈ 25 ns
  → 512 × 25ns ≈ 12.8 μs   ★ 这是"每一页都要重走一遍"的【上限】

实际达不到这个上限，原因有两个：
  ① TLB 有约 1536 个条目 → 2MB（512 页）的工作集本来就能装下
  ② PCID / ASID 能让多数翻译【跨切换保留】
→ 所以真实代价在"接近零"和"十几微秒"之间浮动

【事实】公开测量给出的总量级：轻载 1–5 μs；高负载、缓存被反复冲刷时可以到 10–50 μs——也就是说"间接成本常常比直接成本大一个数量级"这个判断是成立的，只是一次切换值多少微秒必须看场景。

【推导】所以"进程 per request 不可行"的正确说法是：

✔ 每请求一个进程 → 每次调度多付一次【页表切换 + TLB 失效】，
                   在并发高、缓存争抢激烈时把切换成本推高一个数量级
✘ 不是"贵 19 倍"这种精确倍数（那是用一个上限估计除以一个单一数据点算出来的）

【事实】这个成本有缓解手段：

  • TLB 容量：二级 TLB 约 1536 个条目（随 CPU 型号变化），4KB 页下能覆盖约 6MB 工作集
  • PCID / ASID：给 TLB 条目打进程号，同一 CPU 上最多保留约 6 个地址空间的翻译（这是内核的编译期常量 TLB_NR_DYN_ASIDS）——所以"少数几个进程轮着跑"时不会每次都全量失效；超过之后才开始互相驱逐

【取舍】所以"进程模型还是线程模型"的判断是：

每请求一个进程   → 每次调度多付一次地址空间切换，且在进程数多、缓存争抢激烈时成本跳一个数量级
每请求一个线程   → 省掉那一步，且同进程的线程【缓存常常还是热的】
                   → 这正是"高吞吐服务端普遍是多线程而不是多进程"的量化依据

这就是"高吞吐服务端普遍是多线程而不是多进程"的真正原因（不是因为创建快，是因为每次调度的账差近 20 倍）。

2.4 调度器在做什么【事实】

【事实】调度器要解决的问题是"有限的核 vs 无限的就绪任务"，几个要点：

  • 时间片通常 1–10 ms 量级，用完就被强制换下（这叫非自愿切换）
  • 自愿切换：任务自己去等 IO / 睡 / 抢锁失败——它主动让出 CPU
  • 两种切换要分开看：/proc/<pid>/status 里的 voluntary_ctxt_switches 和 nonvoluntary_ctxt_switches 分别计数，优化方向完全不同（前者多说明在等 IO，后者多说明在抢 CPU）
  • 观测手段：perf stat -e context-switches,cs,migrations、vmstat 1 的 cs 列

【事实】量级参考：典型桌面每秒 1–5 万次切换；一个 50K req/s 的 Web 服务可能到 每秒 10–50 万次。

到这里你应该能回答：为什么"进程切换更贵"这个结论不能只靠"寄存器多"来解释？

3. 内存开销：线程到底吃掉多少（这是被讲错最多的一节）

3.1 用户栈：8MB 是"虚拟预留"，不是"物理占用"【事实】

【事实】先纠正一个几乎每份资料都写错的地方：

说法真实情况
"线程栈约 1MB"❌ 不准确。pthread_create(3) man-page 明确写：在 NPTL 实现下，线程创建时的默认栈大小由 RLIMIT_STACK 决定（只要它启动时不是 unlimited）。而 Linux 默认 ulimit -s 是 8192 KB = 8MB。x86-32 的默认才是 2MB
"线程栈一定占那么多内存"❌ 它是虚拟地址空间预留，只有被触碰到的页才真正分配物理内存
"线程栈和主线程栈一样"❌ 不一样：主线程的栈在最顶部、可以按需向下增长到 RLIMIT_STACK；非主线程的栈是 mmap() 出来的、大小固定、不能增长——用完就 SIGSEGV

【推导】那"8MB × 线程数"这个算法错在哪：

开 1000 个线程：
  虚拟地址空间：8MB × 1000 = 8 GB   ← 这个数是"预留"，不是"占用"
  实际物理（假设每个线程只用 2 页栈）：8KB × 1000 = 8 MB

【推导】在 64 位系统上虚拟地址空间有 128TB，8GB 预留根本不算问题——所以"8MB 栈"在 64 位下不是线程数的限制因素。限制它的是下面这个。

3.2 内核侧：二三十 KB，这才是真实占用【事实】

【事实】每个任务在内核里都有一份独立的结构，这部分既不共享也不能省略：

项x86-64说明
内核栈（THREAD_SIZE）16 KB这个数是确定的：内核源码里 PAGE_SIZE << 2（KASAN 关闭时）→ 4KB × 4 = 16KB；x86-32 是 8KB
task_struct 等内核对象数 KB 量级⚠️ 具体值随内核版本与编译配置变化很大（公开资料里有 2KB 到十几 KB 的不同数字），所以这里只给量级
合计（保守取用）每个线程约 25 KB用作估算的保守值，不是精确值

【推导】关键的两句话：

1. 这部分是每线程独立的、不能省的——它是"线程数"真正的物理成本（量级二三十 KB，不是 8MB） 2. 它不计入进程的 RSS（top / ps 里看不到）——所以"看内存占用不高就以为线程不多"是个经典误判

3.3 上限到底是谁定的【推导】

【推导】问"能开多少线程"，答案不是"内存够就行"，而是取下面几个上限里的最小值：

上限默认值算法 / 来源
threads-max视内存而定mempages / (8 × THREAD_SIZE / PAGE_SIZE)（内核 fork_init()）→ 内核栈最多占 1/8 内存。16GB 机器 → 131072
pid_max32768（按 CPU 数上浮，上限 2²² ≈ 419 万）每个任务占一个 pid，proc(5) 文档
ulimit -u（RLIMIT_NPROC）每用户不同限制单个用户
cgroup pids.max / systemd TasksMax服务默认是全局上限的 15%容器里最常撞到的就是这一条

【推导】算一次就明白"内存不够"往往不是真因：

16GB 机器：
  内核栈上限（threads-max）= 131072 个线程 → 内核侧共 131072 × 25KB ≈ 3.2 GB
  也就是说 16GB 里最多拿出约 1/8 给内核栈——这离"内存用光"还很远

所以真实情况通常是：
  pid_max = 32768  → 先撞它
  或者容器的 pids.max / TasksMax → 更早撞它
  → 报错是 "Resource temporarily unavailable"，而不是 OOM

【取舍】"线程开不出来"和"线程开出来太慢"是两件事：

  • 开不出来（EAGAIN）→ 查 pid_max / threads-max / pids.max
  • 开出来太慢（吞吐降）→ 是 2.3 的切换成本账

到这里你应该能回答：为什么"内存不够所以不能多开线程"这个解释通常是错的？

4. 共享的代价：从竞态到死锁

4.1 竞态是"共享地址空间"的直接后果【推导】

【推导】线程最方便的地方就是最危险的地方：地址空间共享意味着同一个变量是同一块内存。

static int n = 0;
// 4 个线程各自执行 n++ 一次
// 期望 n = 4
// 实际可能输出 1 —— 因为 n++ 是"读-改-写"三步，不是原子操作

【推导】加锁解决了正确性，但引入两个新成本：

成本表现
锁本身的开销无竞争时约几十纳秒；有竞争时要陷入内核挂起/唤醒，等于多做几次上下文切换
死锁一旦发生，相关线程永远等下去，只能重启

4.2 死锁的四个必要条件与破法【事实】

【事实】死锁发生必须同时满足四个条件（缺一个就不会死锁——这就是所有解法的出发点）：

#条件含义
①互斥资源一次只能被一个执行单元占用
②持有并等待占着一个还在等另一个
③不可剥夺不能强行从别人手里抢走
④循环等待存在一个环：A 等 B 的资源，B 等 A 的资源

【推导】解法就是"破掉任意一个"，而工程上的性价比排序很明确：

破哪个做法代价 / 适用性
④ 循环等待全局固定加锁顺序（比如永远先锁账户 ID 小的、再锁大的）最实用。改动小、几乎无性能代价——这是首选答案
② 持有并等待一次性申请所有需要的锁，拿不齐就不拿改动大、资源利用率低
③ 不可剥夺拿不到就释放已持有的锁重试，或设超时简单但会"活锁"（反复重试一直失败）
① 互斥用无锁结构 / CAS，把"共享"变成"不共享"（比如 thread_local、每线程一个计数器最后汇总）最强但最难写对

【事实】怎么"检测"已经有死锁：把"任务"和"资源"画成有向图，出现了环就是死锁——建行家的数据库死锁检测用的就是这个思路（[[母题-M10-锁与死锁]] 里 MySQL / PostgreSQL 的死锁检测是同源不同层）。

4.3 自旋锁还是互斥锁【取舍】

【取舍】判断依据只有一个：临界区短不短、以及能不能睡。

自旋锁互斥锁
抢不到时忙等（一直占着 CPU）睡（让出 CPU，等唤醒）
适合临界区极短（几条指令）、多核、不能睡的场景（中断上下文）临界区可能较长（含 IO / 可能阻塞）
不适合临界区长 → 白烧 CPU，还挡着别人极短临界区 → 睡眠 + 唤醒比干活本身还贵

【取舍】一句话判据：如果"等待的时间"比"切换两次的代价"还短，就该自旋；否则就该睡。（两次切换按 2.3 算约 1.5 μs 量级——所以"临界区不到 1 微秒"是自旋的合理区间。）

4.4 用户态与内核态：边界在哪，为什么贵【事实】

【事实】

  • x86-64 有 4 个特权级（ring 0–3），实际只用 2 个：ring 3 跑应用、ring 0 跑内核；ARM64 叫 EL0 / EL1
  • 边界的执行者是硬件，不是内核：页表里的权限位决定"当前这个环能不能读这个地址"——所以"内核空间不可访问"是硬件拦的，不是软件检查的
  • 一次边界跨越（系统调用进出）的成本约 100 ns 量级（有实验把"一次系统调用跨越"标在 100 ns 以内；这个数在公开资料里比较一致，但也仍是量级）

【推导】为什么"贵"的定义要小心：单次 100 ns 其实不贵。贵的是"次数 × 每次都要跨越"：

100 万次系统调用 / 秒 × 105ns ≈ 0.105 个核
→ 优化方向不是"让系统调用更快"，而是【让系统调用更少】（批量、合并、io_uring）

到这里你应该能回答：为什么"减少系统调用次数"比"优化单次系统调用"更值得做？

5. 边界与常见误解

常见说法修正
"线程栈约 1MB"【事实】Linux 上是 8MB（由 ulimit -s 默认 8192KB 决定）；x86-32 才是 2MB。而且它是虚拟预留，不是物理占用
"10 万线程要 100GB 内存，所以开不了"【推导】8GB × 10万 = 800GB 是虚拟地址空间，64 位下有 128TB，不是瓶颈。真实占用是内核侧 25KB/线程 ≈ 2.5GB，而先撞的通常是 pid_max / threads-max / 容器的 pids.max
"线程很轻，所以越多越好"【事实】task_struct + 内核栈每线程约 25KB 且不计入 RSS；切换成本随线程数上升，过了拐点总吞吐下降
"进程切换贵是因为寄存器多"【推导】寄存器部分只有约 200 字节、几十个周期。真正的差在跨进程换页表导致的 TLB 失效与缓存污染——直接成本线程只比进程快两三成，差距体现在间接部分。⚠️ 也不要给"贵 19 倍"这种精确倍数，测量值只能给区间
"一次上下文切换是几百纳秒"【事实】是微秒量级。公开测量常见区间是 1–5 μs（lmbench 的 lat_ctx 约 1.3–1.5 μs；含调度唤醒的测试 3–4 μs），重载含间接成本可到 10–50 μs。"几百纳秒"通常只是寄存器保存恢复那一段
"看 top 内存不高，说明没问题"【事实】内核侧 25KB/线程不在 RSS 里，容器 cgroup 的内存与 pids 限制也不在 top 里。要看 /proc/<pid>/status、/sys/fs/cgroup/...、ulimit -u
"死锁只能靠重启"【推导】四个条件破一个就够，工程上首选固定加锁顺序（破循环等待）——便宜、有效、几乎无性能代价
"自旋锁一定比互斥锁快"【取舍】只有在临界区极短 + 多核时才是。临界区长了自旋就是白烧 CPU 还挡着别人
"多线程能利用多核，所以一定更快"【推导】要分负载：IO 密集时线程有用（等的时候别人能跑）；CPU 密集时线程数超过核数后只剩切换开销（Python 还要叠加 GIL，见 [[母题-N3-进程线程与协程]]）
"瓶颈就是线程不够，加线程池"【推导】先算"每个单元的工作量 ÷ 切换成本"。如果大部分时间花在等（IO / 锁 / 下游），加线程只是让更多执行单元一起去排队——中间件连接池、下游限流会先成为新瓶颈

  • 推导链：clone 标志 → 共享内容 → 通信 vs 隔离 → 切换的直接/间接成本 → 死锁四条件与破法 → 与协程的调度对照。

1. 线程切换和进程切换差在哪一步？

只差"写 CR3 + TLB 失效"这一步（跨进程），同进程的线程整个跳过。直接成本只差两三成，但跨进程会让缓存与 TLB 冷掉，并发高时这一部分能把成本推高一个数量级——所以答案是"差在地址空间，不是差在寄存器"。⚠️ 不要说"贵 19 倍"这种精确倍数，测量值只能给区间。

2. 为什么线程不是越多越好？

两个原因：① 每线程内核侧约 25KB 且要占一个 pid（上限是 pid_max / pids.max）；② 超过核数后多出来的执行单元只在"等"或"抢"——抢就会推高非自愿切换，等就没有收益。要按"每个单元的工作量 ÷ 切换成本"算。

3. 死锁的四个条件是什么、怎么破？

互斥 / 持有并等待 / 不可剥夺 / 循环等待，破任一个即可；首选固定加锁顺序破循环等待（免费）；超时重试（破不可剥夺）有活锁与"重复副作用"的风险。

4. malloc 之后不写会不会占内存？

不会。malloc 只拿到虚拟地址空间，物理页在首次访问（缺页）时才分配——这就是 overcommit 的机制（详见 [[母题-O2-虚拟内存与缺页]]）。

5. 容器里被 OOM 杀了，怎么看？

要分清两类 OOM：整机 OOM（内核挑 oom_score 最高的）和 cgroup OOM（撞 memory.max）。日志前缀不同，排查方向也不同（详见 [[母题-O2-虚拟内存与缺页]] 第 5 节）。
  • 「Java 的虚拟线程 / Go 的 goroutine 和操作系统线程什么关系？」——都是"用户态调度"这一族：把"一个并发任务一个内核线程"改成"M 个内核线程上跑 N 个轻量任务"，省掉的就是本卡第 3 节的内核侧 25KB 和 2.3 的切换成本
  • 「线程池该设多大？」——按负载定：CPU 密集 ≈ 核数 + 1；IO 密集 ≈ 核数 ×（1 + 等待时间/计算时间）——后者就是 2.1 那张"时间花在哪"的账（同 [[母题-N3-进程线程与协程]]）
  • 「为什么 Redis / Nginx 单线程/少线程还能这么快？」——IO 密集 + 事件循环（[[母题-O3-IO模型与零拷贝]]），它们要的并发不需要靠线程数换
  • 「top 里 LOAD 高但 CPU 不高是什么情况？」——大量任务处于不可中断等待（D 状态，通常在等磁盘 / NFS），这是 IO 瓶颈而不是 CPU 瓶颈

RuleArena——"进程随时可能崩"的底层理由就是本卡的进程模型：地址空间独立（崩了不传染，这是优点）、但内存态全丢（所以状态必须落数据库）。Worker 重启后靠"读权威状态 + 校准 Checkpoint"恢复，正是"只有持久化的东西算数"这条事实；容器内存限制（Redis 只给 256~512MB）意味着会撞 cgroup OOM，要和整机 OOM 分开排查。

先给"Linux 不区分线程和进程、差别在共享了什么" → 从"共享了什么"推出三组差异（通信 / 切换 / 隔离）→ 一次切换的六步 + "第 ⑥ 步是唯一直接差别" → 给切换成本的量级区间与数据性质（1–5 μs；重载 10–50 μs），说明线程与进程只差两三成、真正的差在间接成本 → 说明 PCID 与 TLB 容量的边界 → 调度与自愿/非自愿切换的判据 → 内存账（虚拟 8MB vs 内核二三十 KB vs 上限是谁） → 共享的代价：竞态 → 死锁四条件与破法 → 自旋 vs 互斥 → 用户态/内核态与系统调用 → 边界与误解

"共享了什么"决定了"付什么代价"——线程共享地址空间换来通信便宜，代价是切换要换页表（贵）和没有隔离（危险）；不共享换来隔离，代价是通信与切换都贵。而"该开几个执行单元"永远由"切换成本 ÷ 每个单元的工作量"决定，不由"越多越并发"决定。
