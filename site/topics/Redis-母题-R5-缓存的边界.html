题目

有人提议"把订单状态也放 Redis，读起来快"。这个提议对不对？另一个问题：某服务把用户余额的读取加了 Redis 缓存——上线后出现过"用户看到余额充足但下单失败"。这两件事的根因是同一个吗？

一 · 教材 从前提推到结论，不需要先会

1. 前提："缓存"这个词掩盖了两类东西

1.1 派生数据 vs 权威状态【事实】

【推导】"要不要加缓存"这个问题问错了。正确的问法是：这份数据的"权威来源"在哪？

派生数据（可以缓存）权威状态（不该只放缓存）
定义能从权威来源重新算/重新查出来的丢了就真的没了，它就是事实本身
例子榜单、统计结果、列表页、配置副本、搜索结果订单、账本、库存、余额、状态机当前状态
丢了怎么办重建（慢一点，但正确）不可恢复（或要人工核对）
缓存挂了的影响变慢可能读错、写错

【推导】关键区别在"它参不参与判断"：

只用来【展示】的数据（榜单、详情页）→ 旧一点无所谓 → 可以缓存
用来【做决定】的数据（余额够不够、库存还有没有、状态能不能流转）
  → 旧值会导致【错误的决定】→ 不能只靠缓存

1.2 判据：三问【推导】

【推导】任何一份数据要不要进缓存，问三个问题就够：

#问题答"是"才适合缓存
①丢了能不能重建？能（有权威来源）
②旧一段时间能忍吗？能忍多久？能，且能给出具体秒数
③会不会因为读到旧值而做错事？不会

【推导】三问里有任何一问不过，就不是"缓存策略该怎么调"的问题，而是"放错地方了"：

①不过（是唯一一份）      → 它是权威状态，应该留在数据库里
②不过（完全不能旧）      → 只能读权威来源（或接受强一致的方案）
③不过（旧值会做错事）    → 同上 —— 这是最容易被忽略、也最危险的一问

到这里你应该能回答：为什么"余额"和"排行榜"虽然都是"用 Redis 存的数据"，但它们的性质完全不同？

2. 放错的代价：从"慢"升级成"错"

2.1 典型的三类放错【事实】

【推导】按"后果严重程度"排：

类型例子后果为什么
① 权威状态只放缓存订单状态 / 账本 / 唯一一份配置数据丢失Redis 的持久化是"尽力而为"（[[母题-R2-持久化与内存淘汰]]），不能当唯一存储
② 参与判断的数据带旧值余额、库存、状态机状态业务错误（超卖、状态乱跳）判断发生在应用层，应用层相信了一个旧值
③ 大量冷数据 / 大对象全量用户信息、整篇文档塞一个 String内存被打爆、淘汰把热数据挤出去命中率极低却占着内存（[[母题-R4-大key与热key]]）
④ 能本地算出来的东西用 Redis 存"列表页的排序结果"，而排序本身很便宜多了一个故障点，收益接近零引入缓存的收益必须 > 它带来的可用性风险

【推导】第 ② 类最难发现，因为它在低并发下完全正常：

缓存里余额 = 100（TTL 60 秒）
用户在 60 秒窗口里扣了 90（数据库余额变成 10）
缓存还没过期 → 用户再读，看到 100 → 以为还能扣 → 下单
→ 数据库扣款失败（余额不足）
→ 【用户看到"我明明有钱"】

这就是"缓存不一致"从"慢"变成"错"的那一刻——同一个不一致，用在展示上是"旧了 60 秒"，用在判断上是"业务做错了"。

2.2 缓存不可用：回源放大【推导】

【推导】这是必须先算清楚的数（自测 Q1）：

回源请求量 = 总请求 × (1 − 命中率)
回源放大倍数 = 1 / (1 − 命中率)
命中率 h正常回源缓存全挂时回源放大倍数
99%1%100%100 倍
95%5%100%20 倍
90%10%100%10 倍
50%50%100%2 倍

【推导】这张表解释了"为什么缓存挂了等于数据库挂了"：

  • 命中率越高，缓存的价值越大，但它挂掉时的冲击也越大
  • 命中率 95% 的缓存挂掉 → 数据库要扛原来 20 倍的流量 → 大概率打穿
  • 而"打穿"的标志是：数据库因为慢查询排队，响应变慢 → 上游重试 → 流量再翻倍

【取舍】所以"缓存挂了怎么办"必须提前设计，三档：

档做法代价
限流直接把入口流量压到数据库能扛的量（拒绝一部分请求）有损：部分用户被拒
降级返回兜底数据（默认值 / 上一次成功的快照 / 静态页）数据可能不准，但服务活着
本地缓存兜底实例内的本地缓存还能顶一会儿最长顶一个 TTL，且不适用于"写"
不降级（fail open）直接放行到数据库通常就是压垮数据库的那个选项

【事实】EnergyOps 与 RuleArena 的做法值得对照：权威状态全部落在 PostgreSQL，Redis 只承担队列、限流与短期进度（RuleArena 06、08）——这样"Redis 挂了"的影响是"任务排队变慢"，而不是"数据读错"。这是"把缓存放在不影响正确性的位置上"最直接的示范。

到这里你应该能回答：为什么"缓存挂了大不了回源"这句话在命中率高的时候特别危险？

3. 一致性这件事，先说清"上限"再谈方案

3.1 TTL 是"最多旧多久"，不是"不会不一致"【推导】

【推导】缓存的一致性问题分两种时机，各自的上限不同：

更新时机不一致的上限代价
只靠 TTL最多旧一个 TTL（比如 60 秒）极简单；但 60 秒内可能读到旧值
写时失效（写完删缓存）旧到下一次读把它重建为止（通常毫秒级）要处理"删缓存失败"（[[母题-R3-缓存一致性与三类事故]]）
写时更新 + 双删同上，且窗口更小复杂度上升
不用缓存0（但读压力全在数据库）性能

【推导】所以一致性的选择是一个"能容忍多久"的问题，而不是"有没有问题"的问题：

能容忍 60 秒旧值       → 只配 TTL，最简单
能容忍几百毫秒旧值     → 写时删缓存 + TTL 兜底
一毫秒都不能旧         → 这份数据【不该进缓存】，或者要上"强一致"的读路径

【事实】EnergyOps 里有一个必须讲清的点："数据库提交"与"Redis 删除"无法组成一个普通的数据库事务——所以它不用"假装同一个事务"，而是用 Outbox（失效消息与业务同事务落库，再由 Worker 执行删除）（02-aggregation-and-recovery.md、03-query-and-performance.md）。这说明：缓存一致性最终是"最终一致"，不是"强一致"。

3.2 权威状态放在哪，决定了整个架构的骨架【取舍】

【推导】RuleArena 的架构选择可以当成模板：

PostgreSQL = 权威状态（唯一事实来源）
Redis      = 队列、限流、短期进度（都可以丢、可以重投）
→ 于是"Redis 挂了"是【可恢复】的：任务重投、状态从 PG 重建
→ 而如果反过来（Redis 存权威状态），"Redis 挂了"就是【数据事故】

【取舍】一句话判据：

能丢的东西放缓存，不能丢的东西放数据库；而"哪个组件挂了可以重来"这件事，应该在设计阶段就写下来。

到这里你应该能回答：为什么"权威状态在哪"是一个架构问题，而不是一个缓存配置问题？

4. 边界与常见误解

常见说法修正
"有 TTL 就不怕不一致"【推导】TTL 只给"最多旧多久"这个上限（60 秒 TTL = 最多旧 60 秒），它不保证正确性。如果这份数据参与判断，那 60 秒里的错误决定照样发生
"缓存挂了大不了回源"【推导】回源压力会放大 1/(1−命中率) 倍：命中率 95% 时全挂 → 数据库要扛 20 倍流量，大概率打穿。"缓存挂了怎么办"必须提前设计限流 / 降级
"Redis 很可靠，可以当数据库用"【事实】不可以。它的持久化是"尽力而为"（AOF 默认每秒刷盘，最坏丢 1 秒；RDB 丢更多），定位就是缓存（[[母题-R2-持久化与内存淘汰]]）。权威状态不能只放它
"余额可以缓存，加个 TTL 就行"【推导】不行。余额是参与判断的数据（够不够扣），旧值会导致业务做错。这类数据要"读权威来源"，或者只缓存一个"肯定够用"的上界做快速失败（不能用来放行）
"什么都能缓存，只要 TTL 够短"【推导】TTL 再短也有窗口，而"窗口内做错事"这个后果不随 TTL 变短而消失，只是概率降低。判据三问里第 ③ 问不过，就不该进缓存
"缓存能提升性能，所以能加就加"【取舍】加缓存同时引入：一个新的不一致来源、一个新的故障点、一份新的内存成本。收益必须大于这三样——"能本地算出来的东西"就不值得（第 2.1 的第 ④ 类）
"用了缓存就是最终一致，没关系"【推导】"最终一致"必须配一个数字：最终是多久（TTL？几百毫秒？）。说不出数字，就等于没设计
"Redis 和数据库之间用事务保证一致"【事实】做不到——跨两个系统没有普通事务。能做到的是：Outbox / 失效消息（与业务同事务落库）→ 由 Worker 异步执行删除。EnergyOps 用的就是这个

判断"什么数据该放缓存"要问三问——丢了能不能重建、旧一段时间能忍吗（几秒）、会不会因为读到旧值做错事；任何一问不过就不是"缓存策略要调"，而是放错地方了。核心区分是派生数据（榜单、统计、配置副本 —— 可以缓存）与权威状态（订单、账本、余额、库存 —— 不能只放缓存）；而同一份数据的"展示路径"和"判断路径"容忍度完全不同：展示可以旧 60 秒，判断一秒都不能旧（所以余额的正确做法是"显示可以走缓存、扣减用条件更新下沉到数据库"）。另外两笔必须提前算的账：缓存全挂时回源压力放大 1/(1−命中率) 倍（命中率 95% 就是 20 倍，足以打穿数据库，所以限流与降级必须提前设计）；TTL 给的是"最多旧多久"的上限，它的角色是给"写时失效"兜底，不是主要机制，而且要加随机抖动防集体到期。至于 Redis 的持久化——它保证"重启后数据大多还在"，不保证"数据是唯一一份"（AOF everysec 最坏丢约 1 秒），所以权威状态必须留在数据库里（RuleArena 的 PG + Redis 分工就是这个模板）。

  • 判据三问（能否重建 · 能忍多久 · 会不会做错事）
  • "展示路径"和"判断路径"容忍度不同
  • 余额不能直接缓存（扣减下沉到数据库用条件更新）
  • 冷数据放缓存会通过淘汰伤害热数据
  • **回源放大 = 1
  • (1−命中率)**（95% → 20 倍）
  • 缓存挂了要限流 + 降级 + 本地兜底，绝不能让未命中直连数据库

  • 权威状态在 PG、Redis 放可重投的东西
  • "哪个组件挂了可以重来"要写下来

分层要点追问深挖时用

  • 结论：三问定能不能缓存；派生数据可缓存，权威状态不行；展示可旧、判断不能旧。
  • 推导链：三问 → 派生 vs 权威 → 两条路径容忍度不同 → 回源放大与 TTL 定位 → Redis 不能当唯一数据源。
  • 量化：回源放大 1/(1−命中率)（95% → 20 倍）；展示可旧 60 秒、判断基本 0；AOF everysec 最坏丢约 1 秒。

1. 余额能不能缓存？

看路径：展示可以（旧一点无所谓）；判断不能（旧值会让用户做错决定）。标准做法是"显示走缓存、扣减用 UPDATE ... WHERE balance >= ? 下沉到数据库"（[[母题-L1-乐观锁与悲观锁]] 2.3）。

2. 缓存挂了怎么办？

先算回源放大 1/(1−命中率)（95% → 20 倍）；然后按"限流 → 降级 → 本地缓存兜底"设计闸门。绝不能让"未命中"直接等于"打数据库"。

3. TTL 设多少？

按最苛刻的用途定（展示路径可以长、判断路径基本是 0）；加随机抖动防集体到期；而且它的角色是给写时失效兜底，不是主要机制。

4. Redis 能当数据库用吗？

不能。AOF everysec 最坏丢约 1 秒、RDB 丢更多，加上异步复制、主动淘汰、误操作——持久化保证的是"重启后数据大多还在"，不是"唯一一份"。

5. 缓存一致性怎么做到"不骗人"？

说清三件事：① 上限是多少（TTL 几秒 / 写时失效几百毫秒）；② 失败怎么办（删缓存失败靠 TTL 兜底，用 Outbox 保证最终执行）；③ 哪些路径不能容忍（参与判断的那条走权威来源）。
  • 「本地缓存（进程内）和 Redis 缓存的边界怎么划？」——本地缓存的 TTL 更短（几十毫秒）、容量更小、不一致更明显，但连 Redis 的网络往返都省了。适合"极热 + 能容忍几十毫秒旧值"的数据（[[母题-R4-大key与热key]] 3.3）
  • 「多级缓存怎么分层？」——常见三层：本地 → Redis → 数据库，每层容忍度递增、延迟递增；关键是要给每层都定"命中率与回源放大"的目标
  • 「配置中心算缓存还是权威状态？」——看它是不是唯一一份。配置本身往往有权威来源（Git / 数据库），缓存是派生数据；但如果配置只存在配置中心里，它自己就必须高可用（不能当"可丢的缓存"）
  • 「为什么 RuleArena 敢把 Redis 只给 256~512MB？」——因为放进去的是可重投的队列与短期进度（08-capacity-cost-and-facts.md）——规格小不是问题，放错东西才是问题

RuleArena——本卡的核心证据：PostgreSQL 存权威状态，Redis 只做队列、限流、短期进度；08-capacity-cost-and-facts.md 里 Redis 只给 256~512MB。"Redis 挂了"在这里是可恢复事件。

把"缓存"拆成派生数据与权威状态 → 给判据三问 → 三类放错的后果（尤其"参与判断的数据带旧值"为什么会从慢变成错）→ 量化回源放大 1/(1−h) 与降级设计 → 一致性的上限（TTL vs 写时失效 vs 不用）→ 权威状态放哪决定架构骨架 → Redis 持久化 ≠ 不丢 → 边界与误解

缓存能解决的问题只有"快"，不能解决"可靠"和"正确"。 所以边界只有一条：能被重建的、不参与判断的、能容忍旧值的东西，才属于缓存（能用 1/(1−命中率) 量化它的风险、能用 TTL 量化它的不一致）。而"权威状态在哪"是一句架构级的话——它决定了"哪个组件挂了是事故、哪个挂了只是变慢"。
