题目

RR 下为什么"两次一样的 SELECT 结果一样"？这个快照是什么时候定的？和 PostgreSQL 的实现差在哪？

一 · 教材 从前提推到结论，不需要先会

1. 前提：读为什么需要"多版本"

1.1 不用多版本会怎样

【推导】最朴素的并发控制只有锁：读加共享锁（S），写加排他锁（X）。S 与 X 互斥，于是读会挡住写，写会挡住读。

[[母题-M8-隔离级别与ACID]] 算过这笔账：读占 90% 的负载下，读写互斥让约 19% 的请求会互相阻塞；把读摘出去之后只剩 约 1%。

所以目标很明确：

让读不需要排队，同时又不能读到"半成品"。

【推导】这两个要求直接推出"多版本"——如果读不去看正在被改的那份数据，就只剩一种选择：让它看这份数据在某个过去时刻的样子。

1.2 由此得到唯一指标

和索引那几张卡一样，比较任何方案都要先固定指标。这里取：

读操作需要等待的概率，以及为了不等，付出了多少存储与回溯成本。

后面讲版本链、讲长事务的危害，用的都是这个尺子。

2. 实现"快照"的两条路线（先各自介绍，再比较）

2.1 路线 A：把数据复制一份【事实】

做法：开事务时，把需要的数据整体拷一份出来，读这份副本。

  • 优点：判定极简单——读到的就是快照，不存在"可见性判断"
  • 缺点：拷贝本身是 O(数据量) 的成本，而且是每个事务一次。写密集、数据大的场景完全不可行

2.2 路线 B：不复制，保留旧版本 + 判定可见性【事实】

做法：数据页上只留最新版本；每次修改时，把旧版本（前镜像）写进一个专门的地方。读的时候从最新版本往回找，用一套规则判断"哪个版本对我可见"。

  • 优点：写入时只多写一份前镜像，不需要拷贝整个数据集；读也不阻塞写
  • 缺点：需要一个可见性判定规则，而且旧版本要有人负责回收

InnoDB 选的是路线 B。 【取舍】理由：A 的成本随"数据量"增长，B 的成本随"修改量"增长。 数据库的真实场景是"数据多、每次只改几行"——B 的成本模型正好匹配。

记住这个选择的形状：它的所有后续特性（版本链、ReadView、purge、长事务的危害）都是"路线 B"的直接后果。

3. 版本链：旧版本存在哪、怎么串起来

3.1 undo log 在这里的职责【事实】

[[母题-M8-隔离级别与ACID]] 已经给 undo log 派了一个差事：原子性（回滚时撤销）。它在这里派上第二个差事：

undo log 里存的是"改之前的镜像"，所以它天然就是"这个行的上一个版本"。

同一个组件，两个用途：回滚要用它（A），快照读也要用它（I）。这也是为什么 undo 不能随便清。

3.2 每一行的两个隐藏字段【事实】

InnoDB 给每一行加两个不可见的字段：

字段含义
trx_id最近一次修改它的事务 ID（谁改的）
roll_pointer指向上一个版本在 undo log 里的位置

【推导】有了 roll_pointer，一行数据的所有历史版本就串成了一条链：

当前版本(trx_id=105) → 上一个(98) → 更旧(90) → …

3.3 链会变得很长——这是本卡最重要的一笔账

【推导】版本链的长度 = 这条行被修改的次数（在被保留的时间窗内）。

量化：

一行每秒被修改 100 次
一个快照被持有 1 小时 = 3600 秒
→ 这条链上有 100 × 3600 = 36 万节

后果是两层：

1. 回溯变贵：找一个可见版本，最坏要用可见性规则逐节判断 36 万次； 2. 空间不回收：旧版本只有在"没有快照还需要它"之后才能清（由 purge 线程负责）——只要还有一个长事务活着，这条链就一直长下去。

到这里你应该能回答：为什么"一次长事务"的危害不止是"占着连接"，而是会拖慢别人的查询？

4. ReadView：可见性怎么判

4.1 ReadView 是什么【事实】

定义：ReadView 是"拍快照那一刻"记录下来的一个名单——记下当时哪些事务还活着（未提交）。

关键理解：InnoDB 并没有真的"定格"数据。它记的是一个判断依据：知道"当时谁还活着"，就能推断出"哪些修改是那时候还没落定的"，从而把那些版本判定为不可见。

4.2 四个字段【事实】

字段含义
m_ids生成时仍然活跃（未提交）的事务 ID 列表
min_trx_idm_ids 里最小的（低水位）
max_trx_id下一个将要分配的事务 ID（高水位）
creator_trx_id当前事务自己的 ID

4.3 判定规则【推导】

对一个版本的 trx_id：

trx_id == 自己                           → 可见（自己改的当然看得见）
trx_id <  min_trx_id                     → 可见（快照之前就已提交）
trx_id >= max_trx_id                     → 不可见（快照之后才开始的）
min_trx_id <= trx_id < max_trx_id
    在 m_ids 里（当时还没提交）           → 不可见，沿 roll_pointer 找更旧版本
    不在 m_ids 里（当时已提交）           → 可见

不可见就顺着 roll_pointer 往前找，直到找到一个可见的版本。这就是"快照读"的全部实现。

4.4 为什么必须有 m_ids

【推导】因为"开始得早"不等于"已提交"。

一个事务可能在你拍快照之前就开始了，但直到你拍快照之后才提交。它的 trx_id 是小的（比高水位小），光看水位判断不出来它当时的状态——所以必须记下当时还活着的名单。

这就是 m_ids 存在的唯一理由。 能把这条说出来，说明不是背口诀。

5. RC 与 RR：只差一个时机

ReadView 生成时机后果
RC每条 SELECT 都重新生成一个能看到别人刚提交的 → 不可重复读
RR整个事务第一次快照读时生成一次，之后一直复用整个事务看到同一份 → 可重复读

【推导】"可重复读"的全部实现就是这一句：快照不再刷新。 不是靠锁，不是靠别的东西。

理解了这一点，四个隔离级别的行为都能自己推出来（M8 那张谱系表可以直接从这一条生成）。

6. 快照读 vs 当前读

什么操作用什么
快照读普通 SELECTMVCC + ReadView（不加锁）
当前读SELECT ... FOR UPDATE / UPDATE / DELETE / INSERT读最新版本 + 加锁

【推导】幻读的准确说法（M8 已给结论，这里给机制来源）：

  • 快照读不幻读：快照不刷新，别人后面插的行不在快照里；
  • 当前读不幻读：必须读最新版本，MVCC 帮不上 → 靠 next-key lock 锁住范围阻止插入（M10）；
  • 混用时会"看起来像幻读"：快照读看到 10 行，接着 UPDATE（当前读）发现 11 行——两套机制各干各的正常结果。

7. 边界与常见误解

常见说法修正
"快照是把数据复制了一份"【事实】InnoDB 走的是保留旧版本 + 判定可见性（路线 B），没有拷贝整份数据
"MVCC 只在 RR 生效"【事实】RC 下同样生效，只是 ReadView 每条语句重新生成。MVCC 是 InnoDB 的基础能力
"旧版本可以立刻删"【推导】只有当没有任何快照还需要它时才能清。所以一个长事务就能让整条链的回收停摆（3.3）
"undo log 只用于回滚"【事实】两个用途：A 的撤销 + I 的快照读。这也是它不能随便清的原因
"UPDATE 影响行数和我预期不符，是 MVCC 出错了"【推导】UPDATE 是当前读，看的是最新数据；它和之前的快照读本来就可能不一样
"PG 也用 undo log + ReadView"【事实】没有。PG 把旧版本留在堆里、用 xmin/xmax + 快照判定，回收靠 VACUUM。两边是两套实现，只有"快照决定可见性"这一条原理共通（[[母题-P13-MVCC与可见性]]）

一句话结论 全卡唯一要背的锚点

MVCC = 多版本 + 可见性判定。InnoDB 让数据页只留最新版本，旧版本写进 undo log、靠每行的 roll_pointer 串成版本链；读的时候拿一个 ReadView（记录"拍快照那一刻还活跃的事务名单"）沿链往回找第一个可见的版本。RC 与 RR 的唯一差别是 ReadView 生成时机——RC 每条语句重新生成，RR 整个事务生成一次，这就是"可重复读"的全部实现。
  • 不复制数据
  • undo 存前镜像 → 天然就是上一个版本
  • trx_id + roll_pointer
  • 版本链长度受长事务牵制
  • ReadView = 活跃名单
  • m_ids 是为了区分"开始得早"和"已提交"
  • RC 每语句 vs RR 每事务
  • 快照读不加锁、当前读才加锁
  • 幻读一半靠快照一半靠间隙锁

卡住时靠这几个词重建整条链。

MVCC 等于两件事：多版本 + 可见性判定。实现上，数据页只留最新版本，旧版本写进 undo log，靠每行的 roll_pointer 串成版本链；读的时候拿一个 ReadView——记录「拍快照那一刻还活跃的事务名单」——沿版本链往回找第一个可见的版本。

RC 和 RR 的唯一差别就是 ReadView 的生成时机：RC 每条语句重新生成，RR 整个事务只生成一次。这就是「可重复读」的全部实现。

要分清两种读：快照读（普通 SELECT）不加锁，走版本链；当前读（UPDATE、SELECT ... FOR UPDATE）看的是最新数据、要加锁。幻读的机制差异就来自这里，也解释了为什么 UPDATE 的影响行数和之前的快照读可能不一致。

成本面要说：版本链越长，回溯越慢、purge 越难回收；而一个长事务就能让整条链的回收停摆，因为旧版本只有在「没有任何快照还需要它」时才能清。

边界：快照不是把数据复制一份，是保留旧版本 + 判定可见性；PG 不用 undo + ReadView，它把旧版本留在堆里、用 xmin / xmax 判定，回收靠 VACUUM——两边只有「快照决定可见性」这一条原理相同。

分层要点追问深挖时用

  • 结论：多版本（undo 版本链）+ ReadView 可见性判定；RC 与 RR 只差 ReadView 的生成时机。
  • 推导链：读写不互堵 → 保留旧版本而不是拷贝整份数据 → trx_id / roll_pointer 串成链 → ReadView 判定 → 快照读 vs 当前读 → 幻读的两套机制。
  • 量化：版本链长度 = 该行被修改的次数；回收条件是「没有任何快照还需要它」。
  • 边界与常见误解：快照不是复制数据；MVCC 不只 RR 生效；undo 有两个用途（回滚 + 快照读）；UPDATE 是当前读，与之前的快照读本来就可能不一致；PG 走堆内多版本 + VACUUM。

MySQL 的旧版本在 undo log、靠 purge 回收；PG 的旧版本留在堆里、靠 VACUUM 回收。 PG 没有 undo log、没有 ReadView（用 xmin/xmax + 快照）；MySQL 没有 VACUUM。两边只有"快照决定可见性"一条原理共通。

1. m_ids 为什么必需？

因为"开始得早"不等于"已提交"：事务可能在你拍快照前就开始了、拍完之后才提交。它的 trx_id 比高水位小，光看水位判断不出来。

2. undo log 什么时候能删？

当没有任何快照还需要它时，由 purge 线程清理。所以长事务会让 purge 推不动（M13）。

3. MVCC 和两阶段提交有关系吗？

没有直接关系。 两阶段提交解决的是 redo 与 binlog 的一致性（M11）；MVCC 解决的是读的一致性。两件事，别混在一起答。

4. UPDATE 影响行数和预期不符，是 MVCC 出错了吗？

不是。UPDATE 是当前读，看到的是最新数据；和之前的快照读不一致是正常的。

5. 为什么说"RR 完全解决了幻读"不准确？

快照读靠快照、当前读靠间隙锁，两种读都不幻读，但混用时会出现"看起来像幻读"。
  • 「MVCC 在 RC 下也生效吗？」——生效，只是 ReadView 刷新更勤
  • 「MySQL 和 PG 的 MVCC 差在哪？」——旧版本放哪：undo log vs 留在堆里；由此推出回收方式（purge vs VACUUM）与长事务危害形状（undo 膨胀 vs 表膨胀）
  • 「为什么 RR 下我读到的还是旧数据？」——这正是"可重复读"的定义，不是 bug

RuleArena 的任务认领——条件更新是当前读，不受快照影响，所以它看到的是最新状态，这正是它防重复认领的机制之一；EnergyOps 的报表查询——长查询 + RR = 长时间持有 ReadView，这正是 M13 风险的真实来源（不是"查询占 CPU"，是"快照挡住了回收"）。

读为什么要多版本（读写不互堵，M8 的估算）→ 两条实现路线及为什么选"保留旧版本"→ 版本链结构（trx_id / roll_pointer / undo 的两个用途）→ ReadView 四个字段与判定规则 → 为什么必须有 m_ids → RC/RR 只差时机 → 快照读 vs 当前读（幻读的机制来源）→ 成本面（链长、purge、长事务）

"可见性"是按快照判定的，而快照的粒度（每条语句 / 整个事务）由隔离级别决定。 这一条同时解释了 MySQL 的 RC/RR 差别和 PG 的语句/事务快照差别——两边实现完全不同，但"快照决定可见性"这条原理一致。
