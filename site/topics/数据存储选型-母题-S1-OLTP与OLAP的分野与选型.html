题目

某业务库 MySQL 里有一张 1 亿行的订单明细表（约 100 个字段）。分析师要跑一句"按城市统计近一年客单价"的报表：SELECT city, sum(amount)/count(distinct user_id) FROM orders WHERE dt >= ... GROUP BY city。这句 SQL 在 MySQL 上要跑 几分钟，而且跑的时候线上接口开始变慢。团队提了三个方案：

  • A：给 MySQL 加上 city、dt、amount 的联合索引
  • B：主库不动，加一个从库专门跑报表
  • C：把这批数据同步到 ClickHouse，报表查 ClickHouse

选哪个？还有第二个问题：另一个团队只有 500 万行 的数据，也想上 ClickHouse，该不该拦？

一 · 教材 从前提推到结论，不需要先会

1. 前提：所有的差别只来自一件事——数据在磁盘上怎么排

1.1 先把两类负载说清楚【事实】

【事实】这不是两个技术名词，这是两类负载。 先用"一次操作碰多少数据"把它们分开：

OLTP（联机事务处理）OLAP（联机分析处理）
全称Online Transaction ProcessingOnline Analytical Processing
一次操作碰多少几行到几十行百万行到亿行
典型动作下单、扣库存、改状态、按主键查详情按维度聚合、算比值、多表关联、下钻
并发高（每笔都很小）低（每条都很重）
延迟预期毫秒亚秒到分钟都可接受
数据新鲜度必须是当前最新允许有窗口（T+1 或分钟级）
失败代价不可接受（钱和账不能错）可重跑

【推导】这张表已经决定了一件事：这两类负载对"读取效率"的定义是相反的——OLTP 希望"给我一行时一次把这一行拿全"，OLAP 希望"给我一列时别把别的列也读进来"。同一个物理排布不可能同时满足这两个愿望，这就是整个分野的起点。

1.2 两种物理排布【事实】

【事实】行式存储（row store）：同一行的字段连续存放，一行接一行。 【事实】列式存储（column store）：同一列的字段连续存放，一列接一列。

别把这张图当成"两种索引"——它不是索引层面的差异，是数据文件本身的组织方式。索引再花哨，底层读的还是这些块。

到这里你应该能回答：为什么"OLTP 和 OLAP 的区别"这个问题，不能从"功能列表"回答，只能从"物理排布"回答？

2. 用同一个指标把两种排布算一遍

统一指标：扫一次全表，要从磁盘读多少字节。 这是唯一能公平比较的尺子——别的指标（QPS、响应时间）都受硬件和实现影响，只有"读多少字节"是由排布直接决定的。

2.1 场景一：按主键查一行【推导】

【推导】假设表宽 100 个字段、行宽约 1 KB：

行存：读一行 = 找到这 1 KB 连续数据 → 1 次 IO 拿回整行（全部 100 个字段都在）
列存：要拼出一行 = 需要从【100 个不同的列段】各取一个值 → 100 次定位
      （而且这 100 个值在磁盘上彼此相距很远，因为列与列之间隔着一整列的数据）

结论：点查场景行存赢，而且赢的不是一点。

2.2 场景二：扫全表算一列的聚合【推导】

【推导】还是那张表，现在只算 3 个数值列（每列 8 字节）：

行存：必须把每一行整行读进来，再扔掉其中 97 个字段
   1 亿行 × 1 KB = 【约 100 GB】要读

列存：只读这 3 列
   1 亿行 × 3 列 × 8 B = 【2.4 GB】要读
   → 而且同列数据同构、取值域窄，可压缩 → 实际读的更少（倍数取决于数据基数，属【经验值】，必须按自己的数据实测）

同一个查询，IO 量差 40 倍以上。 这就是"为什么列存快"的全部秘密——不是它算得快，是它要读的东西少。

【推导】附带还有两个加成，都来自同一件事：

加成为什么来源
压缩率高同一列的数据类型相同、相邻、取值域窄（城市名、状态码、日期），列式排列让"相似的东西挨在一起"，通用压缩算法能吃到更多重复同列同构
能用向量化执行连续内存 + 同构类型 → 可以一次处理一批值，而不是一行一行循环（SIMD 指令的前提）数据连续

2.3 场景三：改一行【推导】

【推导】这一条最容易被忽略，但它决定了 OLAP 引擎的"功能边界"：

行存：改一行 = 在那一行 1 KB 上原地改（或追加新版本，见 MVCC）
列存：改一行 = 要改 100 个列段里的各一个值
      → 逻辑上的"一行"，物理上散落在 100 个地方
      → 所以列存引擎普遍把"更新"实现成【异步重写整块数据】（先标记，后台合并）

【事实】这就是为什么列存引擎的"UPDATE"普遍是异步的、按批的、代价高的（ClickHouse 的 mutation 走这条路径；Doris / StarRocks 用 Unique Key 模型 + 后台合并来缓解，但语义上仍是"最终一致"）。"它能做点更新"和"它划得来做高频点更新"是两句话。

3. 从物理排布推出的全部差异

【推导】下面是同一张表的两种排布推导出来的完整差异表——每一条都能追到 2.1 / 2.2 / 2.3：

维度OLTP（行存）OLAP（列存）
单次数据量几行 ~ 几十行百万 ~ 亿行
并发 / QPS高（每笔小）低（每条重）
延迟预期毫秒级亚秒 ~ 分钟
索引B+ 树主键 + 少量二级索引（更新时维护代价高）稀疏索引 / 排序键 / min-max / 布隆过滤器（不要求唯一，维护便宜）
事务强 ACID、细粒度锁 / MVCC多数没有跨行事务；批量导入有原子性；点更新昂贵
写入模式高频点更新 / 删除大批量追加（append）
数据新鲜度当前最新状态通常有窗口（要最新就得付同步代价）
表设计规范化（3NF）：避免冗余、避免更新异常反规范化 / 宽表 / 星型模型：少 join、少扫描；用冗余换查询速度
瓶颈所在随机 IO、锁竞争、写放大扫描量、shuffle、join 内存、数据倾斜

【取舍】最后两行是真正的哲学分歧，值得单独记：

规范化是为了"一份事实只存在一个地方"（保证更新不出错）；反规范化是为了"一次查询少碰几个地方"（保证读得快）。 两者的代价正好是对方的目标。

【推导】由此还能推出一件工程事实：既然两边的表设计不一样，数据就不能"同一张表两边共用"——必须经过 ETL / CDC 同步，于是必然带来延迟和一致性窗口。"要不要上 OLAP 引擎"这个问题，一半的答案其实是在问"你受得了这个延迟窗口吗"。

到这里你应该能回答：为什么说"OLAP 引擎快"这个说法不准确，准确说法应该是"它要读的字节少"？

4. 选型：三个问题，依次收敛

【取舍】选型不要从"哪个引擎先进"开始。按顺序问三个问题，任何一个能定死答案，后面的就不用问了。

第一问：访问模式是什么？

点查 / 小事务 / 要求强一致  → 行存（OLTP）
大范围扫描 / 聚合 / 多表关联 → 列存（OLAP），继续问第二问

第二问：数据量到底多大？

【取舍】这一问是"拦住过度设计"的那一关。

千万行以内、查询不复杂 → 【先用现有的关系库】加索引 / 物化视图 / 分区
                     → 上第二个引擎的收益小于它的代价（见第三问）
亿级以上、宽表聚合、要压缩率 → 列存引擎

【事实】关系型数据库本身也能做分析（PostgreSQL 的并行扫描、物化视图、分区表；MySQL 8 的窗口函数与 CTE）。"能不能做"和"划不划得来"是两件事——数据量没到那个量级时，多一套引擎带来的同步链路、一致性窗口、运维面、以及"两份数据谁是准的"这一串问题，代价远大于省下的那几秒查询时间。

第三问：更新与并发怎么分布？

高频单行 UPDATE / DELETE   → 【留在行存那边】，或者用支持 Unique Key 的列存引擎
                        → 高频点更新打到 ClickHouse 这类引擎上，是最常见的误用
大批量 append（日志、埋点、流水归档）→ 列存引擎最舒服
交互式 BI、几百人同时点报表 → 需要强并发能力的列存引擎（Doris / StarRocks 这类）
单条重查询跑到底、并发不高 → ClickHouse 这类擅长单表扫描的引擎

4.1 回到开头那道题【推导】

【推导】三个方案，逐个用指标算：

方案会发生什么
A 加联合索引改善有限。这个查询要的是"近一年全部明细的和与去重计数"，它天然要扫掉那一年的大量数据——索引能帮 WHERE dt >= ... 做范围裁剪，但聚合本身躲不掉全量读。而且1 亿行的宽表加索引，写入代价也要算（见 [[母题-M4-索引代价与大表变更]]）
B 加一个从库跑报表解决了"干扰线上"这一半，没解决"慢"这一半。它把负载隔离出去（这是对的，也是数驭穹图 SNAPSHOT / LIVE_READ 分流想干的事），但行存扫宽表这件事本身还是那么贵
C 同步到 ClickHouse两条都解决：扫描只读需要的那几列（2.2 的 40 倍），而且和线上库物理隔离。代价是：新增一条同步链路、新增一个要对齐的存储、新增一个口径可能不一致的地方

【取舍】正确答案是 C，但理由要说完整：C 赢在两个地方——IO 量、负载隔离；C 的成本也在这两个地方——多一份数据、多一个"谁是准的"的问题。 只答"因为 ClickHouse 快"是没答到点的（那是方案说明，不是选型理由）。

4.2 第二个问题：500 万行该不该上 ClickHouse【推导】

【推导】该拦。 按第二问：

500 万行 × 假设行宽 1 KB ≈ 5 GB 原始数据
→ 单机关系库加好索引 / 物化视图，这类量级的聚合是【秒级】能给出的
→ 而引入 ClickHouse 的固定成本是【不变的】：
   一条同步链路 + 一个引擎的运维 + 一份口径对齐 + 一条"数据延迟了怎么办"的处理路径
→ 固定成本不变、收益随数据量增长 → 数据量小的时候，收益 < 固定成本

【取舍】这里有一个反直觉但重要的判断："要不要上 OLAP 引擎"的主要变量是"团队能不能承受多一份数据的复杂度"，不是"数据量到了哪个数"。 数据量只是让它变得划算的快慢问题。一个有专职数据团队的公司，500 万行上实时数仓也可能合理；一个三人的小团队，5 亿行也未必该上——因为上了没人能维护。

到这里你应该能回答：为什么"我们数据量很大"这句话本身，不足以支撑选型决策？

5. HTAP 与那几个容易被说错的边界

5.1 HTAP 是折中，不是全面胜出【事实】

【事实】HTAP（Hybrid Transactional/Analytical Processing） 指一套系统同时承担两类负载。主流实现方式有两条路线：

路线做法代表
一份数据 + 两种副本行存副本负责事务，列存副本负责分析，通过复制协议同步TiDB（TiKV 行存 + TiFlash 列存）· OceanBase（行存 + 列存副本）
单一引擎兼顾内存列存 / 向量化 + 事务能力共存MySQL HeatWave · 部分单机分布式一体化产品

【取舍】它的价值是明确的：省掉"再搭一套同步链路"，并且把分析拉近实时（这是多库架构最主要的痛点，summaries/oceanBase.md 里得物的实践正是从"多库并存"走向"一体化"）。

【取舍】但它不是免费的，也不是终点：

好处：少一条同步链路、少一份口径分歧、实时性更好、运维面收敛
代价：① 分析负载与事务负载仍会争抢同一套底层资源（要靠资源隔离去管）
      ② 极重的分析场景下，专用 OLAP 引擎的性价比仍可能更高
      ③ 单产品锁定更深——迁移成本比"多个独立引擎"更高

【推导】准确的表述：HTAP 把"同步链路"这个成本换成了"资源隔离 + 产品锁定"这两个成本。 它在中大数据量 + 强实时性 + 团队规模有限时最优；数据量极大、查询极重时，专用引擎分工仍更划算。

5.2 边界与常见误解

常见说法修正
"OLAP 引擎也支持 UPDATE，所以一个引擎就够了"【事实】它支持，但那是异步、按批、代价高的路径（列存的"改一行"物理上要碰 N 个列段，见 2.3）。能做的语义 ≈ 最终一致的批量重写，不是 ACID 事务——面试里把这两者混着说，是硬伤
"列存快是因为它算得快"【推导】错在归因。列存快的根本原因是它要读的字节少（只读用到的列 + 压缩率更高），执行层的向量化是"数据连续"这个前提带来的附加收益，不是原因
"MySQL 上跑得慢，加个索引就好了"【推导】要看慢在哪。索引解决的是"定位"（WHERE 挑出少数行）；如果查询本身就要聚合掉大量数据，索引帮不上忙——那是扫描量的问题，属于"选错引擎族"而不是"缺索引"
"我们数据量大，必须上大数据方案"【取舍】"大"要有量级。千万行以内先算账（4.2）：固定成本不变的条件下，收益必须随量级增长才划算
"HTAP 是最终答案，两套系统迟早要合并"【取舍】它是折中（5.1）：省掉同步链路，换来资源争抢与产品锁定。在什么规模上哪种更优，取决于数据量、实时性要求和团队规模三个变量，没有普适答案
"ClickHouse 是 OLAP，所以它=分析"【事实】OLAP 是一类负载，不是一类产品。同样叫 OLAP 引擎，有的擅长单表大扫描（压缩与扫描速度优先），有的擅长多表 join 与高并发短查询（这与它们的存储与执行设计有关）。"OLAP 引擎"这个词不能替代具体选型
"从库跑报表就不影响线上了"【事实】只搬走了负载，没搬走成本。从库仍要承担复制开销，而且报表如果扫的是同一份行存数据，慢的根源一点没变（4.1 方案 B）
"报表慢一点没关系，反正不影响交易"【取舍】要区分"慢"和"把线上拖慢"。这两件事的解法不同：前者是引擎族选型问题（本卡），后者是资源隔离问题（[[母题-X1-容器是什么]] 的同一个原则：给资源设上界）。数驭穹图 07/08 对"扫描量、超时、行数、并发"的限制，正是把这两件事分开处理

翻面对照自测，评分会进训练台的复训调度。

一句话结论 全卡唯一要背的锚点

OLTP 与 OLAP 的差别只有一个根因——数据在磁盘上怎么排。 行存把同一行的字段放在一起，所以点查一次 IO 拿回整行、改写一行只碰一处，但它做聚合时必须整行读进来再扔掉大部分字段；列存把同一列的放在一起，所以聚合只读用到的列（一张 100 列的表只取 2 列时，IO 差 60 倍以上），而且同列同构所以压缩率高、数据连续所以能用向量化，但它点查要拼 N 个列段、改一行要碰 N 个列段——这就是列存引擎的 UPDATE 普遍是异步按批的根本原因。由此推出选型三步：先问访问模式（点查→行存，聚合→列存）；再问数据量（千万行以内先别加引擎，因为同步链路与运维的固定成本不随数据量缩小）；最后问更新模式（高频点更新别给列存，大批量追加才是列存的地盘）。HTAP 是折中不是终点：它把"同步链路"的成本换成"资源隔离 + 产品锁定"的成本。
  • 根因只有一个——数据在磁盘上怎么排
  • 行存=同一行连续
  • 列存=同一列连续
  • 统一指标：扫全表要读多少字节
  • 点查看行存 · 聚合看列存 · 点更新看行存
  • 列存快的真因是读得少（压缩与向量化是附加）
  • 改一行要碰 N 个列段 → UPDATE 异步按批
  • 规范化 vs 反规范化
  • 选型三问：访问模式 → 数据量 → 更新模式
  • 千万行以内先算账
  • HTAP = 折中（省同步链路，换资源隔离与锁定）
  • OLAP 是一类负载不是一类产品

OLTP 与 OLAP 的差别只有一个根因——数据在磁盘上怎么排。 行存把同一行的字段放在一起：点查一次 IO 拿回整行、改写一行只碰一处；但做聚合时必须整行读进来再扔掉大部分字段。列存把同一列的放在一起：聚合只读用到的列（100 列的表只取 2 列时 IO 差 60 倍以上），而且同列同构所以压缩率高、数据连续所以能用向量化；代价是点查要拼 N 个列段、改一行要碰 N 个列段——这就是列存引擎的 UPDATE 普遍是异步按批的根本原因。

选型三步：① 先问访问模式（点查 → 行存，聚合 → 列存）；② 再问数据量（千亿以下的行存大多够用，别一上来就上列存）；③ 最后问维护成本（两套存储 = 两套运维 + 一条同步链路）。

和 MySQL 侧呼应：冷热分离/归档解决的是"热查询背着冷数据跑"，而分析型查询要隔离到列存或从库，不能让它在主库上跑全表聚合。

  • 结论：根因是存储布局；行存利点查与改写，列存利聚合。
  • 推导链：布局 → 点查 vs 聚合的 IO 差异 → 列存 UPDATE 为什么按批 → 选型三步。
  • 量化：100 列取 2 列时 IO 差 60 倍以上。
  • 边界与常见误解："列存全面更好"×（点查和单行改写是它的短板）；数据量不大时用不上列存。

| 同一件事 | 行存（MySQL / PG） | 列存（ClickHouse / Doris / DuckDB） | |---|---|---| | "改一行" | 原地改 / 版本链（MVCC） | 异步重写整块（mutation / 合并） | | "事务" | 强 ACID、跨行、可回滚 | 批量导入原子性；无跨行事务 | | 索引的用途 | 定位（挑出少数行） | 裁剪（跳过整块数据：min-max / 排序键） | | 唯一性约束 | 主键 / 唯一索引，强制保证 | 通常不强制（去重要在写入或查询时另做） | | 一条查询能吞多少行 | 要控制（会拖垮线上） | 上亿行是常态 |

1. 为什么列存的压缩率高？

因为同列的数据类型相同、取值域窄、物理相邻，"相似的东西挨在一起"让通用压缩算法能吃到大量重复。注意：具体倍数取决于数据基数，是经验值——正确说法是"取决于基数，要按自己的数据实测"，而不是给一个倍数。

2. 为什么 ClickHouse 这类引擎不适合高频单行更新？

列存的物理结构决定的：改一行要碰 N 个列段（100 列就是 100 处），只能实现成异步重写整块数据。所以它的更新语义是"最终一致的批量重写"，不是 ACID 事务。要高频点更新就留在行存。

3. 一张 100 列的表，MySQL 上跑聚合很慢，加索引能解决吗？

不能根治。索引解决的是"定位少数行"；如果查询本来就要聚合掉大量数据，索引帮不上忙——那是扫描量问题，属于"选错引擎族"。先确认慢在哪（是缺索引、写法问题，还是要扫的数据本来就多），再决定加索引还是换引擎。

4. HTAP 是不是就不需要数仓了？

不是。它解决的是"同一份数据里分析与事务共存"，跨系统的同步该有还是有；而且它把成本从"同步链路"换成了"资源隔离 + 产品锁定"。它是折中，不是终点。

5. 为什么 OLAP 要有反规范化的宽表？

因为规范化是为了"更新不出错"，反规范化是为了"读得少"——两者的代价正好是对方的目标。OLAP 允许冗余，是因为它的负载是"大量读、极少更新"，规范化的更新保护在它这里换不到好处。

6. 数据同步（ETL / CDC）会带来什么？

一个必然的一致性窗口。所以真正的选型问题不只是"分析要不要更快"，还有"业务受不受得了这个窗口"（报表要标注数据截止时间、实时决策类需求要另想办法）。
  • 「为什么大宽表在 OLAP 里反而好？」——列存 + 宽表是配套的：列存让"多列"不成为负担（只读用到的列），宽表让查询不用 join。两者是同一个"少碰数据"的目标
  • 「DuckDB 为什么能嵌进进程里，还能很快？」——它是列存 + 向量化执行 + 面向单机分析（数驭穹图正是这么用的：02 写"PostgreSQL 只保存目录与状态，DuckDB 负责分析执行"）。它证明"列存"这件事不依赖分布式
  • 「数据湖 / 湖仓是什么？」——把数据以开放格式（如 Parquet）放在对象存储上，再由计算引擎去读。数驭穹图的"轻量湖仓"就是这个思路的小型版：存储与计算分开，算的时候才把列读进来
  • 「向量数据库算 OLAP 吗？」——都不算，它是第三类负载（近邻检索）。但"按查询形状选结构"这条判据是同一条（见 [[母题-G2-向量与关键词的混合检索]]）

数驭穹图（本卡最完整的实例，三条线都命中）——02-数据接入与轻量湖仓.md 把它写得很直白：*"实际分析数据保存为对象存储中的 Parquet，PostgreSQL 只保存目录、Schema、同步状态和版本，DuckDB 负责分析执行。"* 这句话就是本卡第 4 节的落地：控制面（权限、目录、任务状态）是典型 OLTP，交给 PG；数据面（大范围聚合）是典型 OLAP，交给列存引擎；而且通过 SNAPSHOT / LIVE_READ 双模式控制"数据新鲜度 vs 成本"——LIVE_READ *"优先连接只读副本或分析库"*，并且明确"若客户只有生产主库，默认不开放复杂即席查询"（02）——这正是"不许分析负载打到生产主库"这条硬规矩。
