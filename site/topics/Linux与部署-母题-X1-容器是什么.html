题目

容器里跑 free -h 显示宿主机有 16 GB 内存、还剩 8 GB"可用"，但这个容器的内存限制是 512 MB，而且它已经因为 OOM 被重启过两次。这两件事矛盾吗？另一个问题：某个服务 CPU 利用率只有 40%，却被上游投诉"延迟抖动"——问题可能在哪？

一 · 教材 从前提推到结论，不需要先会

1. 前提：容器是一个被"重新布置过视角"的普通进程

1.1 不是虚拟机【事实】

【事实】两者的根本差别只有一个：内核是不是共享的。

虚拟机容器
内核每个 VM 一个完整的来宾内核共享宿主机的同一个内核
隔离靠什么硬件虚拟化（CPU 的特权级 + 虚拟设备）内核特性（namespace + cgroup）
启动成本秒级到分钟级（要启动一个内核）毫秒级（本质就是启动一个进程）
隔离强度强（内核都不同）较弱（内核漏洞可能被用来逃逸）

【推导】"容器就是一个进程"这句话要讲准确：

它确实只是一个普通进程（有 PID、有地址空间、被调度）
但它被"重新布置过视角"：
  ① namespace 让它的【视野】变小——看不到宿主机的其他进程、自己的网络栈
  ② cgroup   给它的【额度】设上界——最多用多少 CPU、内存、任务数
→ 这两件事合起来，才让一个普通进程"看起来像一台小机器"

1.2 一句话分工【推导】

【推导】把这两者的分工记成一句话，本卡后面全部由它推出：

namespace 管"能看到什么"（视图），cgroup 管"能用多少"（额度）。

namespacecgroup
它回答我能看到哪些进程 / 哪个网络栈 / 哪份文件系统我能用多少 CPU / 多少内存 / 多少任务
本质隔离视图限制资源
名字PID / NET / MNT / UTS / IPC / USER / CGROUP / TIMEmemory / cpu / pids / io / blkio
越界会怎样看不到（隔离住了）被拒 / 被限流 / 被杀

到这里你应该能回答：为什么"容器"这个词其实概括了两件不相干的事（隔离 + 限额）？

2. 关键推论：内存没有 namespace

2.1 为什么 free 看到的是宿主机【推导】

【推导】namespace 有 PID / NET / MNT / UTS / IPC / USER / CGROUP 等好几类，但没有"内存 namespace"——因为内存本身是被所有进程共享的资源池，隔离它的方式是"设上限"（cgroup），而不是"换个视图"。

【推导】由此推出三个很实用的判断：

① 容器里 free / top 显示的内存是【宿主机】的
   → 不要用它判断"我这个容器还剩多少额度"
② 同理，容器里看不到别的容器在抢 CPU
   → "宿主机很空"和"我这个容器够用"是两件事（那张 container-boundary 图就是算这个）
③ 要知道真实额度，只能看 cgroup 的文件：
     /sys/fs/cgroup/<path>/memory.max      上限
     /sys/fs/cgroup/<path>/memory.current  当前
     /sys/fs/cgroup/<path>/memory.events   有没有触发过 OOM

2.2 两类 OOM 的分辨（复习 + 落点）【事实】

【事实】这一点在 [[母题-O2-虚拟内存与缺页]] 4.3 已完整推导，这里只给排查用的落点：

整机 OOMcgroup OOM
日志前缀Out of memory:Memory cgroup out of memory:
触发条件整机内存 + swap 耗尽撞到自己的 memory.max
与宿主机剩余内存直接相关完全无关

【推导】这就是本卡开头第一个问题的答案：free 显示 8 GB 可用，和"这个 512 MB 的容器被 OOM 杀"完全不矛盾——前者是宿主机的视图，后者是 cgroup 的额度。"内存没有 namespace"这一条，同时解释了这两个现象。

【事实】RuleArena 就是这种配置：08-capacity-cost-and-facts.md 里 Redis 容器只给 256~512MB——这个数字就是 memory.max。它超了就是 cgroup OOM，跟宿主机有多少内存无关。

2.3 memory.high 与 memory.max 的分工【事实】

【事实】

memory.max   = 硬上限：超过 → 触发 cgroup OOM
memory.high  = 软上限：超过 → 【只做限流与积极回收】，不杀

【取舍】把 memory.high 设在 memory.max 下方（比如留 10–20% 的余量），可以让内核算先回收而不是直接杀——这是"给进程一个喘息空间"的常规做法（同 [[母题-O2-虚拟内存与缺页]] 4.4）。

到这里你应该能回答：为什么容器里"看内存"要去看 cgroup 的文件，而不是 free？

3. CPU 的限制方式与"限流"这个隐形杀手

3.1 配额-周期模型【事实】

【事实】cgroup v2 的 CPU 限制是"每个周期内允许多少 CPU 时间"：

cpu.max = "<配额> <周期>"        单位微秒
  例："50000 100000" = 每 100 ms 最多用 50 ms CPU = 【0.5 核】
  例："200000 100000" = 每 100 ms 最多用 200 ms CPU = 【2 核】

【推导】注意"0.5 核"这个说法：它不是一个"半个核心"的物理约束，而是"每个 100 ms 周期内只能用 50 ms 的 CPU 时间"。这个区别很重要，因为它带来一个反直觉的现象：

只要【一个周期内】用完配额，剩下的时间即使核是空的，这个容器也用不了
→ 表现为：【CPU 看着不高，但延迟抖动】

3.2 量化：为什么"利用率 40%"可能是骗人的【推导】

【推导】把本卡开头的第二个问题算出来：

容器配额：cpu.max = "50000 100000" → 0.5 核
单个请求的 CPU 时间：60 ms
请求到达速率：20 个/秒

需要：20 × 60 ms = 1200 ms CPU / 1000 ms 时间 = 【1.2 核】
实际有：0.5 核
→ 超出 140% → 大量请求【在周期内用完配额后被限流】

【推导】被限流的表现极具迷惑性：

现象为什么会这样
CPU 利用率看起来不高因为被限流的时间是不计入"使用"的——不是用不了，是不许用
延迟抖动、P99 明显抬升一批请求在周期末尾被迫等到下个周期
换个空闲的宿主机就好了宿主机空闲不改变配额——但如果配额是"按宿主机核数比例"给的，就会变
压测时问题不明显压测往往只看吞吐，而限流会先把尾部延迟搞坏

【事实】决定性证据在 cpu.stat：

nr_throttled   —— 被限流的次数
throttled_usec —— 累计被限流的时间
→ 这两个数【在涨】= 就是被限流了，不用再猜

【取舍】这正是"资源限制不是越小越好"的落点：限得太紧会让服务在"看起来没负载"的时候出问题——而这类问题只能靠"看 throttled 这个数"发现，因为它不出现在 CPU 利用率曲线里。

到这里你应该能回答：为什么"CPU 利用率"这个指标在容器里会误导人？

4. 边界与常见误解

常见说法修正
"容器是轻量级虚拟机"【事实】错。容器共享宿主机的内核，它只是"被重新布置过视角的进程"：namespace 改视野、cgroup 设额度。没有内核隔离，所以隔离强度弱于虚拟机
"容器里 free 显示还有内存，所以不会 OOM"【推导】内存没有 namespace——free 看到的是宿主机的视图。容器的上限在 memory.max 里，超了就是 cgroup OOM，和宿主机剩多少无关
"CPU 利用率不高，说明还有余量"【推导】在容器里这个判断可能完全错：配额是"每周期允许用多少 CPU 时间"，用完之后即使核空闲也用不了——表现为"CPU 不高但延迟抖动"。要看 cpu.stat 的 nr_throttled / throttled_usec
"容器里 top 的 CPU 就是我的使用量"【事实】top 在容器里的视角是被 namespace 与挂载视图影响过的；判断自己的真实用量与额度，应该以 cgroup 的文件为准（cpu.stat、memory.current、memory.max）
"容器的资源限制是运维的事，业务不用管"【取舍】业务必须知道自己的上限：一次查询的扫描量上限、一个任务的内存上限、并发上限——"单个请求没有上界"是这类事故的共同根因（数驭穹图的超时/行数/扫描量限制就是这条原则）
"限制越严越安全"【取舍】限得太紧会换来"延迟抖动"这种难查的问题（3.2）。正确的做法是"设立上界 + 可观测"：既有 memory.max / cpu.max，也监控 throttled 与 memory.events
"memory.high 和 memory.max 是一回事"【事实】不是：max 是硬上限（超了 OOM），high 是软上限（超了只限流与回收）。把 high 设在 max 下方留出余量，才是温和的做法
"容器被 OOM 杀了就是宿主机内存不够"【事实】先看日志前缀：Memory cgroup out of memory: 是 cgroup OOM（撞 memory.max，宿主机可能很空）；Out of memory: 才是整机 OOM

1. 容器和虚拟机的本质区别是什么？

内核是不是共享的。VM 有独立来宾内核（硬件虚拟化隔离，强但重）；容器共享宿主机内核（namespace + cgroup，轻但隔离弱）。

2. 为什么容器里的 OOM 和宿主机的 OOM 是两回事？

日志前缀就能分辨：Memory cgroup out of memory: 是 cgroup OOM（撞 memory.max，宿主机可能很空）；Out of memory: 才是整机 OOM。因为内存没有 namespace，容器的上限只写在 cgroup 里。

3. CPU 利用率不高但延迟抖动，可能是什么？

三类：① 被 CPU 限流（看 nr_throttled / throttled_usec）；② 在等 IO（看 wa 与 IO PSI）；③ 在等锁 / 连接池 / 下游。先分类，再看数——这正是 X3 的排查顺序。

4. 容器里怎么知道"我还有多少内存额度"？

不要看 free（那是宿主机）。看 memory.current / memory.max（比值），以及 memory.events（有没有触发 max / high），再加 /proc/pressure/memory 看压力。

5. pids.max 有什么用？

限制这个 cgroup 里的任务数。它比"内存不够"更早撞上（[[母题-O1-上下文切换与死锁]] 3.3 的 pid_max 是同一族限制），报错是"创建任务失败"而不是 OOM——搞错这一对，排查方向就全歪了。
  • 「Kubernetes 的 resources.limits 和 requests 分别是什么？」——limits 落到 cgroup 的 max（硬上界）；requests 影响调度（"给我预留这么多"）。限制是内核执行的，调度是平台决策的——两者不要混
  • 「为什么容器化之后延迟抖动变多了？」——因为配额是硬边界：裸机上多个进程争抢是加权分时（谁忙谁多拿），容器是到点就不给。同样的平均利用率，容器里的尾部延迟更差
  • 「memory.high 有什么用？」——软上限：超了做限流与回收，不杀。给观察窗口——让问题以"变慢"出现，而不是以"被杀"出现
  • 「sidecar / 服务网格算什么？」——仍是同一套机制（同 Pod 共享 NET namespace 所以能劫持流量）。知道了 namespace 的粒度，这类架构就自己解释出来了

RuleArena——08-capacity-cost-and-facts.md 给 Redis 容器只配 256~512MB：这就是 memory.max，超了是 cgroup OOM；同时 06 里把 K8s 放进"主动删除"清单——说明"用不用编排"本身也是算账的结果。

容器的一切现象都可以从"共享内核 + 视图收窄 + 额度设上界"这三条推出。 最常出错的地方是拿错参照系——用宿主机的数字判断容器的余量（free、CPU 利用率），而真实答案永远在这个容器自己的 cgroup 文件里。换参照系，是容器排查的第一动作。
