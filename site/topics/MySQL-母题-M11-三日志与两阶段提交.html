题目

用户下单，接口返回「提交成功」。一秒后机器断电。重启后，这条订单还在吗？为什么？

一 · 教材 从前提推到结论，不需要先会

1. 前提：为什么不能"改完直接写磁盘"

1.1 两个约束同时成立【推导】

要回答"断电后订单还在吗"，先看数据库面临的两个约束：

1. 数据要最终落到磁盘（内存断电就没了） 2. 提交返回的那一刻，修改就不能丢（这是"持久性"的定义）

最朴素的做法是：UPDATE 一执行，就把数据页写回磁盘。但这行不通，原因只有一个字：慢。

1.2 量化：慢在哪

【事实】磁盘的两种访问方式成本差得很远：

访问方式机械盘SSD
顺序写约 100–200 MB/s几百 MB/s 到 GB/s
随机写受寻道限制，约 100–200 次 IOPS × 4KB ≈ 0.4–0.8 MB/s比顺序写慢，但没有寻道代价

【推导】机械盘上两者差 2–3 个数量级。而"把刚改的那一页写回去"是随机写（那一页在磁盘上的位置是散的）。

所以要换一个做法：把"随机写数据页"换成"顺序写日志"。

1.3 WAL 由此而来【事实】

WAL（Write-Ahead Logging，日志先行）：先写日志，再写数据页。

① 改内存（Buffer Pool）——快
② 把"改了什么"顺序追加到 redo log —— 顺序写，快
③ 提交时保证 redo 已落盘 —— 这一步成功，"提交"才成立
④ 数据页什么时候写回磁盘，无所谓（后台慢慢刷）

WAL 一次拿到两样东西：

  • 性能：把随机写换成了顺序写（1.2 的量化）
  • 崩溃安全性：只要 ②③ 成功，内存里的修改就是可恢复的

到这里你应该能回答：为什么数据库可以说"提交成功"而数据页还在内存里？

因为"安全"的标志不是"数据在磁盘上"，而是"修改这件事已经落盘了"。

2. 三条日志：先各自介绍，再比较

2.1 undo log —— 前镜像【事实】

  • 属于：InnoDB 引擎层
  • 记什么：数据修改之前的旧值（"改之前是什么样"）
  • 职责：回滚（原子性）+ 给 MVCC 提供旧版本（[[母题-M9-MVCC]]）

两个职责共用同一份数据——因为"上一个版本"就是回滚要恢复的那个值。

2.2 redo log —— 后镜像【事实】

  • 属于：InnoDB 引擎层
  • 记什么：数据页的物理修改（"某数据页某偏移被改成了什么"）
  • 物理形态：固定大小、循环写，会覆盖旧内容
  • 职责：崩溃恢复（持久性）

2.3 binlog —— 逻辑日志【事实】

  • 属于：Server 层（注意：不在 InnoDB 里，这是关键）
  • 记什么：逻辑操作（SQL 语句，或每行的前后镜像）
  • 物理形态：追加写，写满切新文件，不覆盖
  • 职责：主从复制 + 时间点恢复

2.4 对照表

undoredobinlog
所属层InnoDBInnoDBServer
内容前镜像后镜像（物理）逻辑操作
文件形态段/回滚段固定大小循环写追加写，不覆盖
职责回滚 + MVCC 旧版本崩溃恢复复制 + 时间点恢复

换个说法更好记（放在工单/订单系统里）：

  • 状态更新失败要能撤销 → undo
  • 更新成功但机器崩了不能丢 → redo
  • 主从同步和备份恢复 → binlog

2.5 一个高价值追问

「binlog 能不能单独保证 crash-safe？」

【推导】不能。 两个理由：

1. 它不在 InnoDB 内部——它的写入时机与 redo 不同步； 2. 它不记录数据页的物理变化，没法用来把内存页恢复成正确状态。

所以 binlog 必须和 redo 配合——而"配合"这件事本身有风险，于是有了两阶段提交。

3. redo 的环形结构

3.1 两个指针【事实】

redo 文件是固定大小、循环写的，上面有两个位置：

指针含义
write pos当前写到哪（不断前进）
check point已经被安全刷盘（脏页已落盘）的位置
...[ check point ...... write pos ]......... 回到开头
    ↑ 之前的日志可以复用        ↑ 之后的区域空闲
    待刷盘的记录在这段区间里

3.2 为什么是"循环写"而不是"无限追加"

【推导】因为 redo 只服务于"崩溃恢复到最新状态"这一个目的——一旦它记录的改动已经落到数据页上，这条 redo 就再也没用了，占的位置可以复用。

注意这里和 binlog 的分工：binlog 要长期保留（做复制和时间点恢复），所以它追加写、不覆盖；redo 用完即弃，所以循环写。

同一个系统里两种相反的文件形态，是因为两个目的不同。 这个对比能讲清楚，说明不是背的。

3.3 危险场景：write pos 追上 check point

【推导】如果 check point 长期不推进（脏页没刷出去），write pos 会绕上来追上 check point——此时没有空闲区域可写了。

结果：写入被迫停下来等刷脏页，表现是"写入突然卡顿"。

顺序必须是【推导】：

先刷脏页  →  再推 check point  →  才释放这段空间

不能反过来——否则这段 redo 已经没了，而对应的脏页还没落盘，崩溃就丢数据。

3.4 刷盘参数

redo 侧 innodb_flush_log_at_trx_commit：

值行为代价
1（默认）每次提交都 fsync最安全，最慢
0提交只写内存 buffer，后台每秒刷最快，掉电丢最近 1 秒
2写 OS 缓存，不立刻 fsync进程崩不丢，整机掉电会丢

binlog 侧 sync_binlog：0 = 交给系统；N = 每 N 个事务刷一次；1 = 每次提交刷。

【事实】生产上要金融级一致，就是「双一」：innodb_flush_log_at_trx_commit=1 + sync_binlog=1。这意味着接口返回"提交成功"时，两份日志都已经真的在磁盘上了——这才是"断电不丢"的前提。

4. binlog 的三种格式

格式记什么优点风险
Statement原始 SQL 语句日志小含 UUID() / NOW() 等非确定函数会让从库算出不同结果 → 主从漂移
Row每行修改前后的具体内容复制绝对精确日志量大（批量 UPDATE 会暴涨）
Mixed自动判断，安全用 Statement、危险切 Row平衡判断逻辑需要理解

【取舍】现在主流是 Row——数据安全优先于日志体积。Statement 只在"日志体积敏感 + SQL 确定"时才考虑。

5. 两阶段提交：为什么非它不可

5.1 推导：问题出在"两份日志"

【推导】现在有两份都要写的日志：redo（InnoDB）和 binlog（Server）。它们不在一个组件里，没法用一个本地事务包住。

那么"两个写入"必然会有一个中间状态——如果正好在中间崩溃，两份日志就可能不一致。而不一致的后果是主从数据不同。

5.2 三步（实际是两个阶段 + 一次裁决）

① 【prepare】InnoDB 写完 redo，但把状态标成 prepare，不算提交
② 【提交阶段】执行器写 binlog 并落盘
③            binlog 落盘成功后，通知 InnoDB 把 redo 改成 commit

5.3 反证：不用 2PC，两种顺序各有一个后果

【推导】假设不做两阶段提交，只是简单地把两次写按某个顺序做：

顺序崩溃点后果
先 redo 后 binlogredo 写完、binlog 没写就崩重启后 redo 重放 → 主库有这次更新；binlog 没有 → 从库没有 → 主库多、从库少
先 binlog 后 redobinlog 写完、redo 没写就崩InnoDB 认为未提交 → 主库回滚；binlog 已记录 → 从库执行了 → 从库多、主库少

两种顺序都会造出主从不一致——这就是不做 2PC 的必然后果。

5.4 一句话收口

【推导】两阶段提交把两份日志"捆绑"成一个原子操作：要么都成功，要么都失败。 这是它唯一的存在理由——不是"规范要求这么做"，而是不做就一定会在崩溃窗口里造出主从不一致。

到这里你应该能回答：为什么不用两阶段提交，也"大多数时候没问题"？

因为崩溃窗口很窄，概率低。但它一定会发生——而数据库的可靠性要求不能建立在"概率低"上。

6. 边界与常见误解

常见说法修正
"binlog 能单独保证 crash-safe"【推导】不能。它不在 InnoDB 内、不记物理页变化，必须靠 2PC 与 redo 配合
"redo 是无限的，会一直追加"【事实】固定大小循环写，会覆盖；边界靠 check point 推进
"有 redo 就不需要 binlog"【事实】职责不同：redo 只服务崩溃恢复（且用完即弃）；binlog 服务复制与时间点恢复（要长期保留）
"两阶段提交是为了保证 ACID"【取舍】它保证的是两份日志的逻辑一致（进而保证主从一致）。ACID 里的 A 和 D 分别由 undo 和 redo 负责，不是 2PC 的职责
"刷盘参数设 0 最快，性能最好"【取舍】是快，但掉电丢最近 1 秒。取舍标准是业务能不能容忍丢这 1 秒（埋点/日志能忍，涉及钱的不能），不是"哪个快选哪个"
"PG 也有 redo / undo / binlog 三套日志"【事实】PG 只有 WAL 一套。旧版本留在堆里靠 VACUUM 回收，复制也靠 WAL——所以 PG 根本不存在"两份日志要协调"的问题，也就没有 prepare/commit 这套两阶段日志状态（[[母题-P11-WAL与checkpoint]]）

redo / undo / binlog 各管什么？两阶段提交为什么必要？

翻面对照自测，评分会进训练台的复训调度。

一句话结论 全卡唯一要背的锚点

三条日志各管一件事——undo 管回滚和 MVCC 旧版本（前镜像），redo 管崩溃恢复（后镜像、物理、循环写），binlog 管复制与时间点恢复（逻辑、追加写、Server 层）。用 WAL 把"随机写数据页"换成"顺序写日志"，同时拿到性能和崩溃安全性。而两阶段提交存在的唯一理由，是让 redo 和 binlog 逻辑一致——不做的话，两个崩溃窗口分别造出"主库多从库少"和"从库多主库少"。
  • WAL 换掉随机写
  • 顺序 vs 随机差 2–3 个数量级
  • undo 前镜像
  • redo 后台镜像·循环写
  • binlog 逻辑·追加写·Server 层
  • redo 用完即弃所以循环，binlog 长期保留所以追加
  • write pos 追上 check point = 写入卡顿
  • 先刷页再推 check point
  • 双一
  • prepare → binlog → commit
  • 崩溃窗口 = 主从不一致
  • binlog 是否完整 = 唯一裁决依据

卡住时靠这几个词重建整条链。

展开（先自答，再看 · 默认收起，不进复训调度）

PostgreSQL 只有 WAL 一套日志（没有 redo / undo / binlog 三套），旧版本留在堆里靠 VACUUM 回收，复制也走 WAL。所以 PG 不存在"两份日志要协调"的问题，也就没有 prepare/commit 两阶段日志状态。 不要把 MySQL 的三日志结构套到 PG 上。

1. redo 循环写，为什么不怕覆盖掉还没刷盘的日志？

check point 只在脏页真正刷盘后才前移；write pos 追上 check point 时必须停下来先刷脏页。顺序是"先刷页 → 再推 check point → 才释放空间"，不能反过来。

2. innodb_flush_log_at_trx_commit 设 0/2 能换多少性能？

必须拿压测数据说话，不能凭感觉。 SDD 时代 fsync 成本下降，1 与 2 的差距远小于机械盘时代，所以现在更多是直接上"双一"。这是"按业务定口径"而不是"按性能定口径"。

3. binlog 有哪几种格式？生产用哪个？

Statement / Row / Mixed；现在主流是 Row（数据安全优先），Statement 只在日志体积敏感且 SQL 确定时才考虑。

4. redo log 是无限增长的吗？

不是。固定大小循环写，边界靠 check point 推进。
  • 「redo log 和 binlog 有什么不同？」——四条按顺序说完就是完整答案：所属层 / 内容（物理 vs 逻辑）/ 文件形态（循环写 vs 追加写）/ 职责（崩溃恢复 vs 复制）
  • 「什么是 WAL，好处是什么？」——日志先行；两个好处缺一不可：把随机写换成顺序写（性能）+ 提供崩溃恢复（可靠性）
  • 「两阶段提交崩在中间会怎样？」——见 Q2 的两个窗口

EnergyOps 的「15 分钟窗口 + 幂等补数」——重放与幂等是同一个思路；RuleArena 的「至少一次投递 + 幂等副作用」——消息队列做不出端到端 exactly-once，就像数据库单靠 binlog 做不出 crash-safe，都得靠幂等 + 权威查询兜底。

为什么不能直接写磁盘（顺序 vs 随机的量级差）→ WAL 是什么、换来了什么 → 三条日志各属于哪一层、记什么、什么文件形态、什么职责 → redo 为什么循环写（用完即弃）→ 双一配置与组提交 → 两份日志必须一致 → 2PC 三步 → 两个崩溃窗口反证 → 方言（PG 只有 WAL）

"安全"的标志不是"数据在磁盘上"，而是"修改这件事已经落盘了"。 数据库用"顺序写日志"换掉"随机写数据页"——这一步同时给出了性能（顺序 vs 随机的量级差）和崩溃恢复能力（WAL）。而只要有两份日志，就必然需要一次裁决（2PC）。
