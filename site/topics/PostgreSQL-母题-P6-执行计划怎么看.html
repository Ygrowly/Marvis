题目

同一条 SQL，开发环境 50ms，线上 8s。你怎么用执行计划找出差别在哪，而不是靠猜？

一 · 教材 从前提推到结论，不需要先会

1. EXPLAIN vs EXPLAIN ANALYZE

EXPLAINEXPLAIN ANALYZE
是否执行不执行，只规划真的执行
给什么估算行数、估算代价、算法选择实际行数、实际耗时、循环次数、内存/磁盘使用
风险无会真的写数据（写语句要放事务里回滚）
常用组合EXPLAINEXPLAIN (ANALYZE, BUFFERS)

【事实】官方对代价的定性值得背：

cost 的数字是「任意单位」（习惯上代表磁盘页抓取次数），所以它和实际的毫秒数不会对得上。

通常最该看的是：估算的行数是否接近现实。

【推论】这一句就否掉了「看 cost 谁小谁快」的用法——cost 只能用来比较「同一条 SQL 的两个计划」，不能用来估计真实耗时，更不能跨 SQL 比。

【事实】BUFFERS 是必须加的：它给出命中的共享块、读的共享块、脏块、写的块，以及临时块（排序/哈希/Materialize 用的）的读写——没有它，你分不清「慢」是算法差还是缓存冷。

【事实】写语句的注意：官方明确警告，ANALYZE 会真的执行，其他副作用照常发生。惯例是：

BEGIN;
EXPLAIN (ANALYZE, BUFFERS) UPDATE ...;
ROLLBACK;

到这里你应该能回答：为什么「看一眼 cost 挑个小数字就完事」是不成立的？

2. loops：最容易看错的一条【事实】

【事实】官方原文：

loops 的值报告的是这个节点被执行的总次数，而显示出来的 actual time 和 rows 值都是【每次执行的平均值】。 这样做是为了让它们和代价估算的呈现方式可比。

把 loops 乘上去，才能得到这个节点实际花掉的总时间。

【推导】这一条会直接改变你对「谁最贵」的判断：

一条节点写着：
  (actual time=0.05..0.12 rows=12 loops=10000)

看错的读法：
  "rows=12，很小；time=0.12ms，很快" → 以为是廉价节点

正确的读法：
  总行数 = 12 × 10000 = 【12 万行】
  总耗时 = 0.12 × 10000 = 【1200 ms = 1.2 秒】
  → 这是整条查询最贵的节点

【结论】同一个节点，两种读法给出的结论完全相反。 而上层节点的 actual time 里已经包含了子节点的累计时间——所以要从最贵的叶子往上看，不是从根往下看。

【事实】两种「看着像 bug 其实不是」的情况，官方专门写了：

  • BitmapAnd / BitmapOr 节点的实际行数永远显示为 0（实现限制）——看到 0 不要以为它没干活；
  • 当外层有很多重复值时，内层子节点的实际行数可能显著大于内层关系本身的行数——那是同一个内层行被反复取的结果，不是统计错误。

到这里你应该能回答：为什么「我说这个节点只返回 12 行，怎么会慢」这句话是站不住的？

3. 看计划的五步顺序

第一看：估计行数 vs 实际行数（最重要）

rows=1000  ...  (actual time=... rows=12 loops=1)

差一个数量级以上就说明统计信息或相关性有问题（→ [[母题-P7-统计信息与慢查询定位]]）。这一步定了，后面的判断才有意义——因为选择哪种扫描/连接算法，本身就是优化器根据估算行数算出来的。

【推导】估错方向决定选错算法——这是「为什么第一步必须是这一步」的证明：

优化器估算外层只有 10 行：
  → 它认为 Nested Loop 只要 10 次内层索引查找
  → 每次 3 页 → 30 页 → 判定 Nested Loop 最便宜 → 选择它

实际外层有 50,000 行：
  → Nested Loop 实际做 50,000 次内层索引查找
  → 50,000 × 3 页 = 【150,000 页】
  → 比估算多了 【5000 倍】

如果估算是对的（50,000 行），优化器会改选 Hash Join：
  → 全表扫一遍 + 建一次哈希表，行数再涨也不会翻 5000 倍

【推论】所以「估错」不是精度问题，是【算法选错】问题。 报错的现象是慢，根因在统计信息。

【事实】一个容易忘的边界（官方原话）：

代价估算不是线性的，所以对更大或更小的表，优化器可能选出不同的计划。 一个极端的例子是：一张只占一个磁盘页的表，几乎总是会走顺序扫描，不管有没有索引。

第二看：扫描方式是否合理

节点什么时候该出现
Seq Scan命中比例高（比如要取 20% 以上的行）或表很小——这是正常的，不要一看到 Seq Scan 就想优化
Index Scan命中行数少、走索引比全表便宜
Bitmap Heap Scan命中中等行数：先用索引把符合条件的页收集成位图、按物理顺序批量读堆——它出现说明优化器判断「随机回表太贵、全表扫又太浪费」，这是很有价值的信号
Index Only Scan见 [[母题-P2-堆表与回表]]——必须同时看 Heap Fetches 是不是 0
Subquery Scan / 子查询被优化掉说明优化器改了形状，要确认改对了

第三看：JOIN 算法与两侧规模

  • Nested Loop：外层小、内层走索引——如果外层实际行数远大于估算，它就从「几万次循环」变成「几百万次循环」，这是最常见的爆炸点；
  • Hash Join：两侧都不小、需要等值连接；看哈希表有没有落盘（Batches > 1 就是落盘了）；
  • Merge Join：两侧都有序。

第四看：Sort / Hash 有没有落盘

Sort Method: external merge  Disk: 24576kB

看到 external merge 就意味着排序溢到磁盘了——通常说明 work_mem 太小，或者排序的数据量本来就该在上游减掉。

第五看：loops 有没有暴露 N+1

loops=10000 配一个内层节点，就是 N+1 的执行计划形态（对应 EnergyOps 里的 N+1 问题）。注意这时要按第 2 节的方法乘算，才能看出它真正的代价。

4. 回到那个真实例子

EnergyOps「优化前 20 多秒」那条查询链路，按这五步看会得到什么：

1. 估计 vs 实际：JOIN 之后中间结果远大于估计 → 优化器选错了后续算法； 2. 扫描方式：先展开全部归属再过滤园区 → 大表 Seq Scan + 位图回表； 3. JOIN 规模：归属关系一对多未限有效期 → 中间行被放大； 4. 排序/哈希：聚合排序落盘； 5. loops：应用侧还有 N+1（1+100 次往返）。

这五条恰好对应「先修范围与 JOIN、再建索引、再消 N+1」的优化顺序——计划不是用来「看一眼」的，是用来给优化动作排优先级的。

5. 边界与常见误解

说法实际情况
「cost 小的计划更快」cost 是任意单位，和毫秒对不上；它只能用来比较同一条 SQL 的两个计划
「rows=12 说明这个节点很轻」那是每个循环的行数——loops=10000 时它处理了 12 万行
「BitmapAnd 行数是 0，说明没干活」实现限制，它永远报 0
「EXPLAIN ANALYZE 的结果就是线上会发生的」不一定：它真的执行，而且强制用真实参数生成计划，线上可能走预编译的通用计划（见追问 2）
「内层节点行数比表还大，是统计错了」是外层重复值多、同一个内层行被反复取，不是错误
「Estimates 差一点点没关系」差一个数量级就要停下来查统计信息——因为算法选择是按估算做的

和 MySQL 对照：MySQL 的 rows 是估算、要看实际值用 EXPLAIN ANALYZE（8.0.18+）；PG 这边 EXPLAIN ANALYZE 是常规工具，而且会真的执行——所以 EXPLAIN ANALYZE 一条 UPDATE/DELETE 会真的改动数据，生产上要小心（可用事务包起来再 ROLLBACK）。

分层要点追问深挖时用

  • 结论：EXPLAIN 是估算、ANALYZE 是实测；按五步顺序看，不跳步。
  • 推导链：估算 vs 实际 → 偏差暴露统计问题 → 扫描方式 → JOIN 算法 → 落盘 → loops 暴露 N+1。
  • 量化：无硬数字，看的是偏差倍数与 loops 次数。
  • 边界与常见误解：EXPLAIN ANALYZE 会真的执行（写操作要包事务再回滚）；BUFFERS 看的是缓存命中与 IO 量。

MySQL 的 EXPLAIN 是只看计划不执行，要看实际执行要用 EXPLAIN ANALYZE（8.0.18+）或 EXPLAIN FORMAT=JSON；输出字段是 type / key / rows / Extra 这一套，没有 PG 的 loops / Buffers / actual time 这些维度。MySQL 的分析器输出里「rows」是估算值——两边「rows 是估算还是实测」这件事本身就不一样，别混着说。

1. 为什么估计会差那么多？

三类原因：统计信息过期、列之间有关联但统计是独立的（「城市=北京」和「区=海淀」相乘会把行数估得极小）、条件是表达式或函数导致无法估算。对应三种修法见 [[母题-P7-统计信息与慢查询定位]]。答这题要说「优化器不是猜的，它是按你给的统计算的」。

2. EXPLAIN ANALYZE 会不会本身改变行为？

会。 ① 它真的执行，所以有副作用风险；② ANALYZE 会强制用真实参数生成计划，而真实运行可能用的是预编译的通用计划——所以「EXPLAIN ANALYZE 里很快、线上很慢」是可能发生的。这条能把两个母题串起来。③ 官方还提醒：ANALYZE 用随机采样估统计，重跑一次 ANALYZE 后 cost 估算可能变化，即使数据分布没变。

3. Seq Scan 一定比 Index Scan 慢吗？

不一定。 命中比例高时顺序读整表比「索引 + 大量随机回表」更快。能说出「Seq Scan 也是一种正确选择」，就脱离了「索引崇拜」。

4. 怎么对比两个计划的优劣？

看实际耗时与 Buffers，而不是「估算代价」；估算代价只能用于同结构比较。要 ANALYZE 真跑、固定参数、跑多次取稳定值。

5. Bitmap Heap Scan 后面接 Sort 说明什么？

说明索引没有提供所需顺序（它按物理顺序读堆），所以还得排一次。要排序就应该考虑让索引顺序直接匹配 ORDER BY。
  • 「EXPLAIN 还能看什么有用但少见的字段？」—— SETTINGS（哪些非默认参数影响了规划）、WAL（这条语句生成了多少 WAL）、MEMORY（规划阶段的内存）、GENERIC_PLAN（看参数化查询的通用计划）。能说出 GENERIC_PLAN，就证明你真的查过预编译语句的坑。
  • 「怎么把计划变成可对比的东西？」—— FORMAT JSON / YAML，程序化解析；再配合 auto_explain 把线上慢查询的计划自动记下来。「线上没有计划可看」和「线上有计划可看」是两个成熟度。
  • 「MySQL 那边怎么对应？」—— MySQL 的 EXPLAIN 只看计划不执行（要看实际执行用 EXPLAIN ANALYZE，8.0.18+），输出字段是 type / key / rows / Extra 这套（[[母题-M7-慢查询与SQL优化手段]]）。两边的字段名完全不同，别混着说。

- EnergyOps 的 20 多秒链路（五步逐条对上的真实案例）。 - 数驭穹图的查询成本控制（每次改索引都要用计划证明，而不是「感觉快了」）。 - RuleArena 的调度轮询查询（loops 特别容易在这里骗人——轮询查询常常是「外层几行 × 内层很多次」的形状）。

两种 EXPLAIN 的差别（估算 vs 实测）→ loops 的语义（最容易看错的一条） → 看计划的五步顺序 → 每个节点该问什么 → 一个真实例子（20 多秒那条）→ 注意事项（ANALYZE 会真跑、代价是任意单位）

计划里的错误几乎总是先出现在「估计行数」上。 所以看计划的第一动作永远是比对估计与实际——偏差大的那个节点，就是问题所在节点，不需要通读整棵树。
