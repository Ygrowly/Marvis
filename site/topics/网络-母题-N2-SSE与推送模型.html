题目

通过 SSE 推送长任务的进度，SSE 是什么？是长连接吗？ 和 WebSocket、长轮询的本质区别是什么？

一 · 教材 从前提推到结论，不需要先会

1. 前提：先把三个容易混在一起的概念分开

9.9 那道题答错，根子就在这里——把不同层面的概念混成了一个问题。 先把三个维度立起来：

1.1 三个正交的维度【事实】

维度属于哪一层取值问的是
连接时长传输层（TCP）短连接 / 长连接这条连接开多久
是否保存状态应用层（HTTP 语义）无状态 / 有状态服务端记不记得你
通信方向应用层单向 / 双向谁能主动发

关键在"正交"两个字：这三个问题互不决定。任意组合都成立：

  • 长连接 + 无状态：SSE 就是这样——连接一直开着，但服务端不因此记得你是谁
  • 长连接 + 有状态：WebSocket 常配合会话状态
  • 短连接 + 有状态：每次新建连接，但服务端靠 Cookie/Token 认出你

【推导】所以"HTTP 是无状态的"这句话，推不出"HTTP 是短连接"。 这是最容易混的一处（N1 的 Q5 已经纠过一次），而它正是 SSE 那道题的病根。

1.2 为什么这个区分重要

【推导】面试官问"SSE 是长连接吗"，他真正想区分的是"你有没有把传输层的事实和应用层的语义混在一起"。

答"是长连接"只是对了一半——完整答案要同时说清"它是长连接，且它是单向的、且它跑在普通 HTTP 上"。

到这里你应该能回答：为什么"HTTP 无状态，所以 SSE 也不可能是长连接"这句话是错的？

2. 四种做法（先各自介绍，再比较）

2.1 短轮询（Short Polling）【事实】

做法：客户端定时发请求问"有没有新数据"，不管有没有都立刻返回。

  • 优点：实现最简单，就是个普通接口
  • 缺点：绝大多数请求是"空跑"——数据没更新时也在问（下一节算这笔账）

2.2 长轮询（Long Polling）【事实】

做法：客户端发请求，服务端"按住"不立刻回，一直等到有数据（或超时）才返回；客户端收到后立刻再发一个。

  • 优点：比短轮询少了很多空请求，实时性也好
  • 缺点：每次返回后都要重新建一次请求；服务端要为每个等待的客户端挂起一个请求上下文（占用资源）

2.3 SSE（Server-Sent Events）【事实】

做法：客户端发一次 HTTP 请求，服务端保持这个响应不结束，以 text/event-stream 格式持续往回推数据。

  • 优点：一次请求换来一条长期通道；自带断线重连（配合事件 ID）；跑在普通 HTTP 上
  • 缺点：只能服务端 → 客户端单向；HTTP/1.1 下会占用一条连接（见 4.3）

2.4 WebSocket【事实】

做法：客户端发起 HTTP 请求，通过 Upgrade 头升级协议，之后这条连接变成双向全双工通道，双方随时可以发。

  • 优点：真正的双向、低开销（帧很小）
  • 缺点：需要协议升级——中间件、网关、代理都要支持；连接管理与心跳要自己做

2.5 怎么选：两个问题就分流完了

问题一：需要「双向」实时通信吗？
   ├─ 需要        → WebSocket
   └─ 不需要
       问题二：只要「最新状态」，还是要「持续的事件流」？
         ├─ 只要最新状态 → 轮询 / 状态查询（最简单，够用就别升级）
         └─ 要事件流     → SSE

【取舍】判据不是"哪个更先进"，而是"客户端要什么"。 这是本卡最该带走的一句话——很多系统上 WebSocket 是因为"听起来更强"，而不是因为真的需要双向。

回到 Agent 长任务这个具体场景（面试最可能问的）：

需求判断
客户端要"持续看到进度"吗？要 → 排除"只要最新状态"
客户端需要"随时打断/发指令"吗？通常不需要（甚至长任务里主动打断是少数）
需要复用现有 HTTP 网关吗？需要 → WebSocket 要额外改造

三条都指向 SSE。 【取舍】所以选 SSE 的理由不是"它更弱所以够用"，而是三条具体判据都命中它。

3. SSE 的精确定义（一句话说全）

【事实】SSE（Server-Sent Events）是基于 HTTP 的长连接：客户端发一次请求，服务端保持这个连接不断开，以 text/event-stream 格式持续往回推数据。所以它是长连接。它和另外两种的区别：长轮询是客户端反复发短请求；WebSocket 是双向全双工、需要协议升级；SSE 是单向（只服务端往客户端推），但自带断线重连（靠 Last-Event-ID）和事件 ID，而且跑在 HTTP 上，过网关和负载均衡不需要额外改造。

这段话里有四个技术点，一个都不能少：

点为什么重要
text/event-stream这是它的协议标识，服务端靠它告诉客户端"这不是普通响应，别等结束"
单向决定了它和 WebSocket 的分工
Last-Event-ID断线重连的能力来源：重连时带上最后收到的事件 ID，服务端可以从断点续推
跑在 HTTP 上工程上最实际的优点：不用改网关、不用新协议、鉴权和限流都能复用

4. 生产里的坑（这里才是"真做过"的证据）

4.1 反向代理会缓冲【事实】

Nginx 之类的代理默认会缓冲响应——它会攒够一定量才转发。对普通接口无所谓，对 SSE 是致命的：数据会被攒着不发，客户端看到的进度是"卡住然后一次跳一大段"。

处理：关掉该响应的缓冲（Nginx 侧 X-Accel-Buffering: no），并确认 proxy_buffering off。

4.2 要发心跳【事实】

连接空闲太久会被中间设备（网关、NAT、负载均衡）当成死连接回收。

处理：定期发注释行心跳（SSE 里以 : 开头的行会被客户端忽略，但足以让链路上的设备看到流量）。

4.3 HTTP/1.1 下的连接数限制【事实】

浏览器对同一域名在 HTTP/1.1 下只允许约 6 个并发连接。SSE 会独占一条。所以：

  • 一个页面开 1–2 个 SSE 没问题
  • 开 7 个以上就会有请求排队（首页的其他接口被 SSE 挤住）

【推导】这个坑的解法是 HTTP/2：多路复用让一条连接上跑多个流（N1 第 4 节）。

4.4 断线重连的语义要设计【推导】

SSE 自带重连，但它只负责"重连"这个动作，不负责"不丢事件"。要真做到不丢，需要：

服务端：每条事件带自增 id
客户端：记录最后收到的 id，重连时通过 Last-Event-ID 带上
服务端：据此从 id 之后续推（或直接让客户端拉一次全量状态校准）

【取舍】"能重连"和"不漏事件"是两件事。 这是从"我用了 SSE"到"我处理了它的失败模式"的分界。

5. 边界与常见误解

常见说法修正
"SSE 是短连接"【事实】错。SSE 是长连接——服务端保持响应不结束。这正是 9.9 当场答错的那一处，必须一条不错地纠正过来
"SSE 和 WebSocket 差不多，都是长连接"【事实】方向不同：SSE 单向（服务端→客户端），WebSocket 双向；SSE 跑在 HTTP 上，WebSocket 要协议升级。"都是长连接"只描述了传输层，没描述应用层
"SSE 就是普通 HTTP 响应，过网关不用任何配置"【取舍】代理默认会缓冲，必须关掉（X-Accel-Buffering: no），否则数据会被攒着不发
"SSE 自带重连，所以不会丢消息"【推导】重连 ≠ 不漏。要配合事件 ID + Last-Event-ID 才能续推
"长轮询就是短轮询加了个超时"【事实】本质区别在"服务端是否按住请求"：短轮询立刻返回（大量空跑），长轮询 hold 住直到有数据。占用资源的方式也不同（长轮询会挂起请求上下文）
"能用 WebSocket 就用 WebSocket"【取舍】WebSocket 要协议升级、要自己做心跳与重连、网关可能不支持。只需要单向推送时，SSE 的工程成本低得多

SSE 是基于 HTTP 的长连接：客户端发一次请求，服务端保持响应不结束，以 text/event-stream 持续单向推送，自带断线重连（Last-Event-ID）与事件 ID，跑在普通 HTTP 上所以过网关不用额外改造——这是它相对 WebSocket 最大的工程优势。

三个模型的区别：短轮询是"客户端定时发、服务端立刻回"（大量空跑）；长轮询是"服务端按住请求直到有数据或超时"（减少空跑，但每次要重建请求）；WebSocket 是"双向 + 协议升级"。

选型判据是两个问题：客户端要不要主动发？要的是事件流还是只要最新状态？ 只需要服务端推（进度、通知、LLM 逐字输出）就用 SSE，工程成本低得多；要双向（协作、游戏、实时输入）才上 WebSocket。LLM 的逐字流式输出本质上就是 SSE（或分块传输）。

生产三个坑：① 代理缓冲——Nginx 等中间层会缓冲响应，把流式变成一次性返回，要关掉缓冲并按块 flush；② 心跳——长时间无事件会被判为空闲而断开，要定期发注释行保活；③ 断线重连——浏览器会自动重连并带 Last-Event-ID，但要真正不漏事件，服务端必须按这个 ID 续推，或让客户端重连后拉一次全量状态校准。还要注意网关的空闲超时。

分层要点追问深挖时用

  • 结论：SSE 是单向、复用 HTTP 的长连接；选型问"要不要双向"和"要事件流还是最新状态"。
  • 推导链：服务端推的三种模型 → SSE 复用 HTTP 省掉 Upgrade → 代价是代理缓冲/心跳/重连三个坑。
  • 量化：子事件用 Last-Event-ID 续推；长轮询/短轮询的差别在"服务端是否按住请求"。
  • 边界与常见误解："SSE 不是长连接"×；只靠浏览器自动重连不够，服务端必须能按 ID 续推；中间件完全不支持长连接时才退回长轮询。

SSE 的行为强依赖链路上的代理与网关配置——同一个服务在直连时正常，加了网关就可能"卡住不发"（缓冲）或"几分钟断一次"（空闲超时）。所以面试时要说"它跑在 HTTP 上，但代理需要配合关缓冲和加心跳"，而不是简单地说"无需配置"。

1. SSE 和 WebSocket 到底怎么选？

先问"客户端要不要主动发"。只需要服务端推（进度、通知、LLM 逐字输出）就用 SSE，工程成本低得多；要双向（协作、游戏、实时输入）才上 WebSocket。

2. SSE 断线了会怎样？

浏览器自动重连，并带上 Last-Event-ID。但要真正"不漏事件"，服务端必须按这个 ID 续推，或者让客户端重连后拉一次全量状态校准。

3. 为什么 SSE 适合 LLM 逐字输出？

它就是"持续的单向事件流"，且能复用现有 HTTP 网关与鉴权。这正是 EnergyOps 里推长任务进度、以及大部分大模型产品流式输出的做法。

4. 长轮询还有什么场景在用它？

【取舍】需要"服务端推"但中间件完全不支持长连接时的兜底；或者兼容性要求极高的旧环境。现代系统里它更多是被 SSE 替代。
  • 「什么是长轮询？和短轮询的区别？」——服务端是否按住请求：短轮询立刻返回（大量空跑），长轮询 hold 到有数据
  • 「流式输出（streaming）用的是什么？」——本质就是 SSE（text/event-stream）或分块传输
  • 「怎么防止 SSE 连接被中间设备断掉？」——心跳注释行，让链路看到持续流量

EnergyOps 的长任务 SSE 进度推送（这是本卡最直接的项目证据——选 SSE 不选 WebSocket 的理由就是"只需要单向 + 复用现有 HTTP 网关"）；数驭穹图的流式返回；RuleArena 的进度查询（这里更该用轮询状态而不是推送——正好是个反例，说明"判据而不是习惯"）。

三个正交维度（破掉"HTTP 无状态所以 SSE 不是长连接"）→ 四种做法各是什么（短轮询/长轮询/SSE/WebSocket）→ 决策树两个问题 → SSE 精确定义四个技术点 → 生产三个坑（代理缓冲 / 心跳 / 连接配额）→ 断线重连要配事件 ID → 回到 Agent 长任务：三条判据都指向 SSE

"连接开多久""记不记得你""谁能主动发"是三个互不决定的维度。 把这三个分开，SSE 那道题就不会答错；把这三个分开，选型也就变成了两个二选一的问题。
