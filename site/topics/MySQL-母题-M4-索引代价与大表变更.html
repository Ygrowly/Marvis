题目

任务表 5000 万行，线上正在跑。现在要给 status 加一个索引，你直接执行 ALTER TABLE task ADD INDEX idx_status(status)。会发生什么？

一 · 教材 从前提推到结论，不需要先会

1. 前提：索引是读的快照，写的负债

1.1 三笔代价【事实】

代价具体是什么谁在付
写放大每次 INSERT/UPDATE/DELETE 都要同步维护所有相关索引每一笔写
空间二级索引的叶子存「索引列 + 主键」，主键越长、索引越多，占的空间越大磁盘与缓存
优化器负担候选索引变多 → 优化器要评估的计划变多 → 选错的概率上升（统计信息不准时更明显）每一次查询

1.2 写放大能算出来【推导】

一张表有 1 个聚簇索引（数据本身）+ N 个二级索引，那么一次写入要改 N + 1 棵 B+ 树，每棵都要保证有序（可能触发页分裂）。

一张表 1 个聚簇索引 + 6 个二级索引
  一次写入 → 维护 7 棵 B+ 树
  写入 QPS 5000 时 → 每秒 5000 × 7 = 35,000 次 B+ 树插入

删掉 2 个"从没被查询用过"的索引：
  7 棵 → 5 棵，每秒 35,000 → 25,000 次
  写入侧直接省 29%

【取舍】所以判据是一句可执行的话：这个索引有没有高频查询真的在用它？ 没有任何查询用得上的索引，是纯负债——它只在写入时收费。

1.3 空间也能算出来【推导】

二级索引的叶子存「索引列 + 主键」。以给 status（INT，4B）建索引为例，算上 InnoDB 的记录头开销约 6B：

主键 BIGINT（8B）：每条 ≈ 4 + 8 + 6 = 18B
  5000 万行 → 18B × 5000万 ≈ 900 MB

主键换 UUID（36B）：每条 ≈ 4 + 36 + 6 = 46B
  5000 万行 → 46B × 5000万 ≈ 2.3 GB

同一个索引，只因为主键变长，就膨胀 2.6 倍（46 ÷ 18）。而且这还只是一个索引——有 6 个二级索引，就是 6 份一起膨胀（[[母题-M5-引擎与表设计基本盘]] 会再讲主键选型）。

到这里你应该能回答：为什么"反正磁盘便宜，索引多建几个"在写多的表上是错的？

2. 大表 DDL 的危险到底来自哪里

2.1 它要做两件事【事实】

ALTER TABLE ... ADD INDEX 分两步：

1. 扫描全表 + 排序，建出一棵新索引（5000 万行，几分钟到几十分钟） 2. 在开始和结束各拿一次 MDL（元数据锁）

直觉会怪第 1 步"太慢"。但危险在第 2 步。

2.2 MDL 连锁：真正的机制【推导】

MDL 的规则很短：读锁与读锁兼容，读锁与写锁互斥；而 MDL 请求队列是先进先出、不能插队的。

① 一个长事务在跑（持 MDL 读锁）——它可能只是一条跑了 5 分钟的慢 SELECT
        ↓
② DDL 要申请 MDL 写锁 → 与读锁互斥 → 排队等待
        ↓
③ 后面来的普通查询也要 MDL 读锁。它们本该和①兼容（都是读），
   但因为队列 FIFO，它们必须排在「正在等待的 DDL」后面
        ↓
④ 每个排队的请求都占着一条数据库连接 → 连接池被占满
        ↓
⑤ 新请求连不上库 → 服务雪崩（而且不只是这张表的问题）

【推导】危险被放大的方式：

积压的请求数 ≈ QPS × DDL 等待的秒数

QPS 2000、DDL 等 30 秒 → 积压 2000 × 30 = 60,000 个请求
连接池通常只有几百条 → 瞬间排满

【推论】DDL 的等待时间被"并发度"放大了——所以真正要控制的不是 DDL 有多快，是它等待的时间。

到这里你应该能回答：为什么说"危险的不是 DDL 慢，是它堵出了一条越来越长的队"？

3. 候选方案（先各自介绍，不比较）

3.1 Online DDL（MySQL 5.6+）【事实】

ALTER TABLE task ADD INDEX idx_status(status), ALGORITHM=INPLACE, LOCK=NONE;
参数作用
ALGORITHM=INPLACE不重建整表（加二级索引只需扫描 + 排序）
LOCK=NONEDDL 执行期间允许并发读写

3.2 影子表方案（pt-osc / gh-ost）【事实】

四步：

1. 建一张结构相同的新表（带新索引） 2. 同步增量：pt-osc 用触发器、gh-ost 读 binlog，把旧表的新写入同步到新表 3. 分批拷贝存量：可限速、可暂停 4. RENAME TABLE 瞬间切换

pt-oscgh-ost
增量来源触发器binlog
对主库影响触发器有额外开销更小
可暂停 / 限速支持支持，且更细

3.3 先处理掉长事务（这不是方案，是前置动作）【事实】

SELECT trx_id, trx_started, trx_mysql_thread_id
FROM information_schema.innodb_trx
WHERE TIME_TO_SEC(TIMEDIFF(NOW(), trx_started)) > 60;

4. 逐个淘汰（统一指标：对线上流量的最坏影响）

4.1 为什么"直接执行 DDL"不可接受【推导】

它把不可控的等待时间暴露给了整条链路：DDL 等多久，取决于碰巧有没有长事务。而由上面积压公式，等待 30 秒就能把连接池打满。

4.2 为什么"开了 LOCK=NONE 就安全"是错的【推导】

LOCK=NONE 只保证DDL 执行期间不阻塞别人。它不能保证 DDL 自己不被别人阻塞——长事务持读锁时，DDL 照样要等。而它一旦开始等，第 2.2 节的连锁照样发生。

【事实】另外 ALGORITHM=INPLACE 也不是万能的：改列类型、重建聚簇索引这类操作做不到 INPLACE。

4.3 胜出方案：按"表的规模 + 是否可回滚"选【取舍】

场景选择
加二级索引、表不算很大Online DDL（ALGORITHM=INPLACE, LOCK=NONE）
表很大、要求可控可回滚pt-osc / gh-ost
改列类型等无法 INPLACE 的操作影子表方案
任何情况先查长事务；设短 lock_wait_timeout；别在高峰动手；备好回滚

【取舍】三个方案的差别在代价放在哪：Online DDL 简单但等待不可控；影子表可控但要多一倍空间、还要运维工具。没有"最安全"的方案，只有"这次变更最适合"的方案。

【事实】顺带一个 MySQL / PG 的方言差异：PG 的对应手段是 CREATE INDEX CONCURRENTLY，它同样有个容易踩的点——建索引过程中失败会留下一个 invalid 索引，需要手动 DROP 再重建（[[母题-P4-索引代价与在线建索引]]）。

到这里你应该能回答：为什么"选哪个方案"这个问题，答案里必须包含"先查长事务"？

5. 边界与常见误解

常见说法修正
"加了索引查询就快，反正空间便宜"三笔代价：写放大（+1 棵聚簇 + N 棵二级）、空间（主键越长所有索引越大）、优化器负担。没被用上的索引是纯负债
"LOCK=NONE 开了就不会影响线上"它只保证 DDL 执行期间不阻塞；不保证 DDL 不被长事务阻塞。等待一旦发生，MDL 连锁照样雪崩
"ALGORITHM=INPLACE 所有 DDL 都适用"改列类型、重建聚簇索引这类做不到 INPLACE，只能重建表或用影子表
"DDL 慢是因为要扫 5000 万行"扫描几分钟确实慢，但把库搞挂的是 MDL 排队——两者是不同的机制，要分开说
"删索引很快，没风险"DROP INDEX 通常快，但同样要拿 MDL，同样会被长事务卡住
"在业务低峰执行就安全了"低峰降低了 QPS，从而降低积压速度，但没有消除长事务这个触发源。低峰 + 查长事务 + 短 lock_wait_timeout 才是完整动作

【取舍】读成一句话：索引的代价是"每一次写"，DDL 的危险是"不可控的等待"——这两件事都不是靠"表大不大"决定的，是靠"有没有人用、有没有人挡"决定的。

一句话结论 全卡唯一要背的锚点

索引的代价是三笔——写放大（一次写维护 N+1 棵 B+ 树）、空间（主键被复制进每个二级索引，BIGINT→UUID 能让单个索引膨胀 2.6 倍）、优化器负担。大表 DDL 的危险不在"扫 5000 万行慢"，而在 MDL：长事务持读锁 → DDL 等写锁 → 后续查询因队列 FIFO 全排在 DDL 后面 → 积压数 = QPS × 等待秒数（2000 QPS 等 30 秒 = 6 万个请求）→ 连接池打满 → 整个服务雪崩。LOCK=NONE 只解决"DDL 不阻塞别人"，没解决"别人阻塞 DDL"。 所以真正的处方式是：先查并处理长事务 + 设短 lock_wait_timeout + 按表规模选在线 DDL 或影子表 + 低峰执行 + 备回滚。
  • 三笔代价（写放大/空间/优化器负担）
  • 一次写维护 N+1 棵 B+ 树
  • 主键被复制进每个二级索引，BIGINT→UUID 膨胀 2.6 倍
  • MDL 连锁（读锁持住 → DDL 等写锁 → FIFO 不能插队 → 后续查询全排队）
  • 积压 = QPS × 等待秒数
  • 连接池打满 → 雪崩
  • LOCK=NONE 只解决一半
  • INPLACE 不是万能
  • pt-osc 触发器 vs gh-ost binlog
  • 任何情况都先查长事务

索引的代价三笔：写放大（一次 INSERT 要维护 N+1 棵 B+ 树）、空间（主键被复制进每一个二级索引，BIGINT 换成 UUID 让单索引从 18B/条涨到 46B/条、约 2.6 倍）、优化器负担。没被用上的索引是纯负债。

大表 DDL 的危险不在「扫 5000 万行慢」，而在 MDL：DDL 要拿 MDL 写锁，前面有个长事务持着读锁没放，DDL 就只能在队列里等；MDL 队列是 FIFO，后面进来的查询全堵在它后面。积压数约等于 QPS × 等待秒数——2000 QPS 等 30 秒就是约 6 万个请求堆着，连接池打满、服务雪崩。

所以 LOCK=NONE 只解决「DDL 不阻塞别人」，没解决「别人阻塞 DDL」；ALGORITHM=INPLACE 也不是万能。

处方四步：先查并干掉长事务（前置动作，不是方案）；设短 lock_wait_timeout，让等待快速失败而不是无限堆积；按表规模与可回滚性选 Online DDL 还是影子表（pt-osc 用触发器、gh-ost 吃 binlog）；低峰执行 + 备好回滚。低峰只降低积压速度，不消除长事务这个触发源。

分层要点追问深挖时用

  • 结论：索引的代价是「每一次写」；大表 DDL 的危险是「不可控的等待」（MDL 连锁），不是扫描慢。两者都不是由表大不大决定的，是由有没有人用、有没有人挡决定的。
  • 推导链：三笔代价 → DDL 要做的两件事（改元数据 + 改数据）→ 危险在拿 MDL 写锁那一步 → 长事务持读锁 → DDL 排队 → 队列 FIFO 让后续查询一起堵 → 积压 = QPS × 等待秒数 → 连接池打满。
  • 量化：BIGINT→UUID 单索引 18B→46B（约 2.6 倍）；2000 QPS 等 30 秒 ≈ 6 万个请求积压。
  • 边界与常见误解：LOCK=NONE 只管一半；INPLACE 不是所有 DDL 都行（改列类型、重建聚簇只能重建表）；DROP INDEX 同样要拿 MDL；低峰是降速不是除因；完整动作 = 查长事务 + 短 lock_wait_timeout + 按规模选方案 + 低峰 + 备回滚。

1. LOCK=NONE 都开了，为什么还是可能卡住线上？

关键在于MDL 等待的连锁：长事务持读锁 → DDL 等写锁 → 后续查询再排在 DDL 后面。LOCK=NONE 只保证 DDL 执行期间不阻塞，不保证它不被别人阻塞。

2. 索引是不是越多越好？

不是。写放大 + 空间（还挤占 buffer pool）+ 优化器负担；判据是"有没有高频查询真的用它"。没被用上的索引应该主动删掉。

3. MySQL 和 PG 在这件事上有什么不同？

PG 用 CREATE INDEX CONCURRENTLY，它不会长时间持锁等，但代价是失败会留下 invalid 索引需要手动清理，而且不能在一个事务块里执行。

4. 为什么 NOT NULL + DEFAULT 加字段有时很快、有时很慢？

取决于能不能走 instant 路径。MySQL 8.0 支持 instant add column（元数据操作）；更早版本或某些类型会触发重建表。判断方式是看 ALGORITHM 到底是 INSTANT / INPLACE / COPY，不要凭版本印象。
  • 「删索引呢？」——DROP INDEX 通常快，但同样要拿 MDL，同样会被长事务卡住。流程与加索引一致。
  • 「加字段为什么有时比加索引更危险？」——加索引是 INPLACE（不重建整表）；而加列在不能走 instant 时会触发整表重建，代价高一个量级。
  • 「为什么说「主键要短」？」——因为它会被复制进每一个二级索引的叶子（[[母题-M3-聚簇索引与回表]]）。见 Q3 的 2.6 倍。
  • 「分区表能替代这个方案吗？」——能缓解（DROP PARTITION 比 DELETE 干净），但分区本身也是一次 DDL，同样要走这套流程（[[母题-M15-数据增长治理]]、[[母题-P16-分区表]]）。

- EnergyOps：四层事实表（大表聚合）——任何加索引/改列都要走"查长事务 → 选方案 → 低峰 → 备回滚"这套动作。 - 数驭穹图：元数据表变更——低频但不可中断，所以更偏向影子表方案（可控、可回滚）。 - 面试里的说法：「我项目里用 PostgreSQL，对应的是 CREATE INDEX CONCURRENTLY——它同样有个容易踩的点：建索引过程失败会留下 invalid 索引，需要手动 drop 再重建。」主动说出方言差异，比只背 MySQL 的参数更能证明真用过。

三笔代价（写放大给算式、空间给算式）→ 大表 DDL 的两步，指出危险在第二步 → MDL 队列 FIFO 的连锁推导 + 积压公式 → Online DDL 保证什么、没保证什么 → 影子表四步与 pt-osc/gh-ost 差异 → 按规模与可回滚性选 → 收束到"先查长事务 + 短 lock_wait_timeout"

索引是读的快照，写的负债。 它的全部代价都记在写入路径上；而大表变更的全部危险都来自锁的排队语义——不是"慢"，是"堵"。两件事都不由表的大小决定，而由"有没有人用、有没有人挡"决定。
