早上坐下脑子里的清单有七八件：整理标签体系、补 PostgreSQL、改简历、看面经、内推开口……每件都有用，越想越乱。

标准动作

把清单按「投递流水线的关键路径」过一遍——今天真正推进转化率的最多两件（比如内推开口 + 复训保底）。其余的写一行记下，不展开（R2 有限计划会的写法）。晚上验收只对这两件，做了四件有用但不在关键路径的事 = 今天没完成。

触发器
  • 当清单超过 3 件 → 强制排序，问「哪件在投递→面试→offer 的主线上」

  • 当一天结束时只干了杂活 → 记进复盘：不是忙错了，是目标没砍
易错

把「少」理解成「不做别的」——是关键路径的事先做且必做，杂活排在它后面，而不是二选一。

标准动作

一句话　不是「因为 X 所以做不了 Y」，而是「先决定了不做 Y，再制造出 X 当理由」——看清目的，才能重选。

情境　

「等我状态好了再改简历」「等我先把基础补完再投」，一小时过去文档还是空白。

先想：这个情境你会怎么做，再展开对
标准动作

把句子改写一遍——把「因为 X 所以不做 Y」改成「我用 X 当不做 Y 的理由」。改写完通常就看清了：真正的目的是躲开「被拒/被拷打」的风险。然后直接开 30 分钟丑版本倒计时（R5），让行为戳破理由。

触发器

  • 当情绪很大不想动 → 问「这个情绪在帮我达成什么目的」（通常是回避某个具体动作）

心智模型

七条主线分两组——一、二回答「怎么读得快」，三至六回答「怎么写得稳」，七是真实业务落地。全部机制的根判据是同一条：磁盘随机 IO 比内存慢约 5 个数量级，所以 B+ 树三层（扇出约 1170）覆盖约 2000 万行只要 3 次 IO；所有设计都在做两件事之一：换 IO 次数，或把随机写换成顺序写（WAL）。抓住这条根，每个机制都能从它推出来。

必会清单

  • 联合索引按字典序排列，只有连续前缀能切出定位区间；「用不上」= 扫描量约等于全表 @MySQL-1
  • 二级索引叶子只存「索引列 + 主键值」，回表是随机 IO，代价随命中行数线性增长 @MySQL-1
  • ACID 的机制拆解：A 靠 undo、D 靠 redo、I 分锁与 MVCC 两路，C 是结果不是机制 @MySQL-3
  • RC 与 RR 的唯一差别是 ReadView 的生成时机 @MySQL-3
  • 两阶段提交的唯一理由是 redo 与 binlog 的逻辑一致，崩溃后由 binlog 完整性裁决 @MySQL-4
  • 长事务只读也危险：MVCC 链的回收看 ReadView，不是看你做了什么 @MySQL-5

PostgreSQL 地基包PostgreSQLPostgreSQL 模块概览 →
定位与 MySQL 平行的关系库第二主干——面试里常作「对比数据库」出现，答出实现差异才是加分项。范围：索引、执行、事务 MVCC、WAL、VACUUM、复制；不含扩展生态（PostGIS 等）与 DBA 调优。
心智模型

与 MySQL 共用同一条根判据（磁盘随机 IO 慢约 5 个数量级），但多版本 answers 不同：MySQL 把旧版本存 undo，PostgreSQL 把旧版本存在表里（元组多版本），靠 VACUUM 回收。只抓住「多版本存哪、谁回收」这一条，七条主线的差异全能推出来：长事务拖 VACUUM → 表膨胀与事务 ID 回卷；索引里也存旧版本 → 膨胀；写 = 追加新元组 → 写放大。

必会清单
  • 索引家族比 MySQL 宽：B-tree 同款判据之外，GIN（JSONB / 全文倒排）、部分索引都是选型项 @PostgreSQL-1
  • 执行器：代价估算决定 Seq Scan 还是 Index Scan，统计信息过期是慢查询第一嫌疑 @PostgreSQL-2
  • MVCC：元组带 xmin/xmax，快照判可见性；RC 与 RR 的差别仍是快照生成时机（与 MySQL 同构不同实现） @PostgreSQL-3
  • WAL：先写日志再刷数据页，与 MySQL redo 同理；checkpoint 在平衡恢复时长与刷页压力 @PostgreSQL-4
  • 长事务的 PG 特有代价：阻塞 VACUUM → 死元组堆积 → 表膨胀，极端时事务 ID 回卷（强制停机） @PostgreSQL-5
  • 复制两形态：流复制（物理，整实例）与逻辑复制（按表），主从切换靠它 @PostgreSQL-6

心智模型

快是两条的乘积——内存比磁盘快 4–5 个数量级 + 单线程事件循环免去锁与上下文切换。五个结构全是「为特定访问模式定制的内存索引」。而它的三类风险共用一个根源：内存是易失且昂贵的——易失，所以持久化在赌（快照还是日志）；昂贵，所以只放热数据、缓存在骗（与 DB 两份真相）；单线程，所以一个慢命令或大 key 就能堵住所有人。

心智模型

锁的每一步都是花性能买正确性，所以每个决策都是判据题：冲突率决定要不要锁（乐观 vs 悲观），共享范围决定锁画多大（粒度、临界区、读写），机器边界决定锁放哪里（单机内存 → 分布式）。分布式锁的根问题是：锁服务和真相分离了——持锁者可能已经死了但锁还在，所以无论哪种实现，最终都要配 fencing token（一次单调递增的凭据）兜底。

心智模型

操作系统 = 把有限的物理资源虚拟成无限的逻辑资源：CPU 用时间片虚拟（切换有代价）、内存用页表虚拟（缺页有代价）、IO 用缓冲与中断虚拟（拷贝有代价）。一切性能问题的句式都是同一条——某种虚拟化代价失控了：线程开太多是切换代价失控、程序假装内存够用是缺页代价失控、IO 慢是拷贝与阻塞代价失控。

必会清单
  • 进程 vs 线程：隔离单位 vs 调度单位；切换代价 = 寄存器保存恢复 + CPU 缓存污染 @操作系统-1
  • 线程开多了反而慢：上下文切换与锁竞争吃满；线程池大小按任务类型（CPU 型 ≈ 核数，IO 型按等待比）估 @操作系统-1
  • 虚拟内存：页表映射、缺页中断；malloc 成功 ≠ 内存到手（overcommit，用时才真分配） @操作系统-2
  • OOM 的真实语义：内存耗尽时内核按评分挑进程杀，不是程序自己报错 @操作系统-2
  • IO 等待发生在哪：设备等待 + 数据拷贝；select/poll/epoll 的本质差别是「谁在遍历 fd、唤醒谁」 @操作系统-3
  • 零拷贝：sendfile 把「内核→用户态→内核」的往返砍掉 @操作系统-3

数据存储选型地基包数据存储选型数据存储选型 模块概览 →
定位架构判断层——OLTP/OLAP 分野、扩展三路、何时引入新引擎、语义层。这是系统设计题的评分暗线，也是数驭穹图（NL2SQL）的方法论地基。不含具体引擎内部实现。
心智模型

存储选型 = 为读写模式选数据布局。行存服务「按事务取一行」，列存服务「按列聚合一大片」——这不是谁更先进，是 OLTP 与 OLAP 两类负载的物理必然，所以合不成一个引擎。扩展不是免费的：副本买读与可用性、分片买写但砍掉跨片事务、缓存买读但引入一致性账单。最后一层是语义：数据仓库存的是事实，「事实的含义」（指标口径）得有地方放——NL2SQL 与 Agent 靠它才答得对。

必会清单
  • OLTP vs OLAP：读写模式差异决定行存/列存布局，混合负载才有 HTAP 的折中 @数据存储选型-1
  • 扩展三路各自的买与付：副本（读+可用，无写扩展）、分片（写，砍跨片事务）、缓存（读，加一致性） @数据存储选型-2
  • 不该用关系库的信号：访问模式是文档/宽列/图时再换引擎；每多一个引擎就多一份运维与一致性账 @数据存储选型-3
  • 语义层：指标口径、血缘、元数据为什么是 NL2SQL 与 Agent 的成败点 @数据存储选型-4

定位异步与削峰的底盘——MQ 三问（丢 / 重 / 积压）是后端面试标配，也直接对应 Agent 任务队列场景。不含具体 MQ 的运维与调参。
心智模型

MQ 的全部保证从一条推出：跨进程跨网络的传递是会失败的，所以只敢承诺「至少一次」。不丢靠每一段的确认（生产确认 → Broker 持久化 → 消费 ACK）——少一段就有一个丢失点；「重复」是至少一次的必然代价，用幂等消费接住；「乱序」是分区的代价，按业务 key 路由换局部有序。积压不是事故是常态，消费速度怎么扩要在设计时想好。

必会清单
  • 三段丢失点与兜法：生产者确认机制、Broker 持久化（刷盘策略）、消费者手动 ACK @消息队列-1
  • 至少一次 → 只生效一次：幂等消费（唯一业务键 / 去重表 / 版本号），业务层接住重投 @消息队列-2
  • 乱序的来源与对策：多分区并行必然乱序；按 key 路由保「同一实体局部有序」 @消息队列-2
  • 积压治理：加消费者受分区数上限时，换思路（批处理 / 跳过 / 临时转储队列） @消息队列-3
  • 选型到底在选什么：吞吐 / 延迟 / 顺序 / 语义保证的组合，没有全能冠军 @消息队列-3

定位八股高频层 + Agent 后端真正要用的部分：HTTP/TCP/TLS 的链路观、SSE/WebSocket 选型（Agent 流式输出天天用）、高并发连接模型。不含抓包技巧与协议字段背诵。
心智模型

网络 = 一层层委托，每层只解决一段不可靠：TCP 管「包会丢会乱」，TLS 管「会偷会改」，HTTP 管「语义与缓存」。所以排查铁律是先定位断在哪一层。而服务端到客户端的演进（轮询 → SSE → WebSocket）是一条线：从「反复问」到「挂着听」——Agent 流式输出选 SSE 的全部理由都在这条线上：单向、文本、够用，就不该为它上双向协议。

必会清单
  • URL → 响应全链路：DNS → TCP 握手 → TLS 握手 → HTTP → 渲染；每层背一个典型失败点（解析失败/超时/证书/状态码） @网络基础-1
  • TCP 三次握手的理由：双方都要确认「收与发」两个方向的能力，两次不够 @网络基础-1
  • SSE vs WebSocket vs 轮询：单向文本流够用就不上双向协议；断线重连 SSE 内建 @网络基础-2
  • 心跳与重连是谁的责任：连接断了应用层要能恢复现场（续传/幂等） @网络基础-2
  • C10K：每连接一线程为什么崩（切换与内存），事件循环 + epoll 怎么救 @网络基础-3

定位AI 应用岗的差异化底盘——评测、可观测、上线治理。这是你区别于纯后端候选人的区分带，也是 RuleArena 与数驭穹图共同的方法论地基。不含具体评测框架的教程。
心智模型

AI 系统的输出是概率的，工程重心从「保证正确」移到「度量并守住底线」，三步是因果链：先定义什么算好（指标分层 + 数据集 + 谁判分），再能看见为什么（轨迹与归因），最后才能安全地变（回归评测挡退化，成本与安全护栏兜底）。没有第一步，后面全是空转——口径都没定，数字再多也不能比较。

必会清单
  • 指标分层：系统级 / 任务级 / 组件级，口径先于数字；没有口径的指标不可比较 @评测观测与治理-1
  • 数据集与判分者：金标集怎么建、多大才够；LLM 判分的偏差与校准 @评测观测与治理-1
  • 轨迹与归因：一次坏输出是在哪一步坏的（检索/生成/工具）；变更后靠回归评测防退化 @评测观测与治理-2
  • 安全与成本护栏：阈值、熔断、降级，先把「不能更差」定成线 @评测观测与治理-3
