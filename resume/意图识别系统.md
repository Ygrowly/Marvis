
### **结论：这篇文章的核心不是“如何调一个小模型”，而是如何在真实业务约束下，把开放式用户表达稳定地翻译成可执行的结构化意图，并通过数据、评测和自动化迭代形成闭环。**

其完整方法可以概括为：

> **明确下游目标 → 拆解意图与边界 → 按约束选模型 → 构造黄金数据集 → 建立多维评测 → 自动优化提示词 → 防止过拟合 → 用线上指标验证业务价值。**

## 一、问题本质：意图识别不是分类，而是翻译

### 1. 定义：系统要解决什么问题

用户输入的是自然语言，例如：

- “想买个蓝牙耳机，200以内”
- “有没有手机券”
- “给女朋友买个礼物”
- “随便看看”

下游系统需要的却是结构化信息：

```json
{
  "intent_type": "ITEM",
  "priority": "L1",
  "keywords": ["蓝牙耳机"],
  "summary": "用户想购买预算200元以内的蓝牙耳机"
}
```

因此，意图识别模块的本质是：

> **把用户的人话翻译成搜索、推荐和权益系统能够消费的查询语言。**

它不是导购，也不是推荐器，不负责：

- 查商品；
- 判断商品是否存在；
- 生成最终推荐；
- 持有 SKU 数据；
- 代替下游算法排序。

它只负责三件事：

1. 判断用户想做什么；
2. 提取下游检索所需的关键词；
3. 用摘要保留用户需求中的关键约束。

### 2. 机理：为什么意图识别决定最终体验

整个链路可以抽象为：

```text
用户输入
   ↓
意图识别
   ↓
结构化查询
   ↓
权益/商品召回
   ↓
相关性排序
   ↓
页面展示
```

意图识别是中间的“翻译层”。

如果意图类型错了：

- 用户想找商品，却进入权益召回；
- 用户想找优惠，却进入商品推荐；
- 用户只是闲聊，却被强行推荐商品。

如果关键词错了：

- 下游检索不到结果；
- 结果与用户需求偏离；
- 即使召回系统本身准确，最终体验仍然错误。

所以，意图识别虽然只占链路的一小段，却具有较强的误差放大效应。

---

## 二、为什么一期推荐模式不够，必须增加对话式识别

### 1. 一期：预测用户可能喜欢什么

一期采用类似猜你喜欢的主动推荐：

```text
用户打开页面
   ↓
系统读取用户画像、行为、偏好
   ↓
从多个权益池筛选可能感兴趣的权益
   ↓
自动展示
```

这种方式的优势是：

- 用户无需输入；
- 使用门槛低；
- 适合没有明确目标的用户；
- 推荐链路简单。

但它解决的是：

> **用户可能喜欢什么？**

而不是：

> **用户现在明确想要什么？**

### 2. 二期：理解用户当前需求

二期增加自然语言输入：

```text
用户主动表达需求
   ↓
系统识别意图
   ↓
生成结构化查询
   ↓
精准检索权益或商品
```

它解决的是：

> **用户此刻到底想找什么？**

### 3. 第一性原理：推荐与搜索的适用边界

推荐和搜索的差异，来自信息来源不同：

- 推荐依赖系统已有的用户信息；
- 搜索依赖用户当前主动提供的信息。

当用户意图不明确时，推荐更合适；当用户表达了明确诉求时，搜索更准确。

因此，合理方案不是二选一，而是：

> **用推荐承接不确定需求，用对话和搜索承接明确需求。**

---

## 三、意图体系设计：先定义业务决策，再定义标签

### 1. 四类意图

文章将用户输入划分为四类：

| 类型 | 定义 | 下游动作 |
|---|---|---|
| ITEM | 用户想找商品或品类 | 商品推荐或商品搜索 |
| BENEFIT | 用户想找优惠、红包、券等权益 | 权益匹配 |
| VAGUE | 有购物倾向，但需求不明确 | 追问和澄清 |
| IRRELEVANT | 与购物和优惠无关 | 不推荐商品或权益 |

### 2. 为什么要设置 VAGUE

传统分类通常假设每句话都可以直接落入一个明确类别，但实际用户表达经常不完整：

- “想买点东西”
- “送女生的礼物”
- “最近有什么好物”
- “帮我看看有什么优惠”

这些表达包含购物倾向，却不足以支撑准确检索。

因此，VAGUE 不是“分类失败”，而是一种有价值的中间状态：

> **承认当前信息不足，并通过追问降低不确定性。**

### 3. 优先级设计

系统采用 L1～L4 表示意图明确程度：

- **L1**：需求明确，可以直接检索；
- **L2**：大致方向明确，需要少量补充；
- **L3**：购物意图存在，但品类或约束较模糊；
- **L4**：只有泛化购物倾向，几乎无法直接检索。

优先级的作用不是评价用户，而是决定系统动作：

```text
L1 → 直接推荐
L2/L3 → 追问关键条件
L4 → 引导用户明确需求
IRRELEVANT → 不触发购物推荐
```

### 4. 优先级规则

文章的核心判断是：

- ITEM 和 BENEFIT 已经包含明确对象，统一为 L1；
- VAGUE 才需要进一步判断 L2～L4；
- IRRELEVANT 不进入购物推荐链路。

这体现了一个重要原则：

> **分类标签不是为了描述用户，而是为了驱动下游决策。**

---

## 四、模型选型：不是追求最大模型，而是满足约束的最小充分模型

### 1. 业务约束

模型选型受到五个约束：

#### 速度

用户正在等待回复，首 token 需要在约 1～2 秒内出现。

#### 成本

618 是高流量场景，按 token 计费的大模型成本可能无法承受。

#### 准确性

模型必须理解语义关系，而不是简单匹配关键词。

例如：

- “给女朋友买个生日礼物”
- “有没有适合送人的东西”

二者表面表达不同，但都属于模糊购物意图。

#### 上下文

输入包括：

- 约 5000 token 的系统提示词；
- 约 50 token 的用户输入；
- 约 100 token 的模型输出。

因此，32K 上下文是合理底线。

#### 职责边界

模型只做意图翻译，不做商品推荐。

### 2. 为什么选择小模型

该任务的特点是：

- 输出结构固定；
- 意图类别有限；
- 输入通常较短；
- 不需要复杂知识问答；
- 不需要深度商品知识；
- 对低延迟和低成本敏感。

所以，任务不需要最大模型，而需要：

> **在业务目标上足够准确、在工程约束下能够稳定运行的模型。**

这就是“最小充分模型”原则。

### 3. 候选模型筛选逻辑

最终聚焦 Qwen3 系列的 8B、14B、30B 纯文本模型。

#### 排除多模态模型

原因：

- 当前输入只有文本；
- 视觉和音频模块不会被使用；
- 仍可能占用显存并增加计算开销；
- 在同等参数规模下，纯文本模型更适合低延迟场景。

边界条件是：如果未来支持上传图片识别商品，多模态模型才有必要。

#### 排除嵌入模型

嵌入模型适合：

```text
输入文本 → 向量 → 与意图向量库做相似度匹配
```

但当前任务不仅要分类，还要：

- 生成追问；
- 抽取关键词；
- 生成用户需求摘要；
- 区分商品意图与权益意图；
- 处理多轮状态变化。

因此，嵌入模型无法独立完成完整任务。

其维护成本也更高：

- 需要建设意图向量库；
- 需要调阈值；
- 需要处理边界样本；
- 规则变化时需要更新索引。

#### 最终候选

留下四个纯文本模型：

- Qwen3-8B；
- Qwen3-14B；
- Qwen3-30B；
- 另一种 30B MoE 方案。

### 4. 最终选择 8B 的原因

评测中，14B 效果最好，8B 时延最好。

但14B存在资源交付风险，因此最终选择8B。

这不是因为8B绝对最好，而是因为综合目标函数更优：

```text
最终方案 = 准确性 + 时延 + 成本 + 资源可交付性
```

体现出真实工程中的基本原则：

> **线上选型不是单指标冠军，而是在全部约束下寻找最稳妥的可交付解。**

## 五、评测数据：先保证问题可信，再比较模型优劣

### 1. 为什么不能直接跑 benchmark

模型评测的基本关系是：

```text
错误数据集 → 错误评分 → 错误选型
```

如果测试样本本身：

- 不符合真实业务；
- 标签存在歧义；
- 边界覆盖不足；
- 期望输出不合理；

那么再精确的评测分数也没有实际意义。

因此，评测的第一步不是调用模型，而是构造可信用例。

### 2. 用例设计的三个原则

#### 覆盖边界

不能只测试典型样本。

典型样本：

- “我想买个手机” → ITEM。

边界样本更有区分度：

- “有没有数码产品的券”；
- “电脑配件有红包吗”；
- 商品与权益同时出现；
- 多轮对话中意图从 VAGUE 变成 ITEM。

#### 贴近真实表达

用户表达通常具有：

- 口语化；
- 省略；
- 不完整；
- 错别字；
- 非标准语序。

例如：

- 不应只测试“请为我推荐一款适合送女友的生日礼物”；
- 还应测试“给女朋友买个礼物，不知道买啥”。

#### 可标注

每条样本必须有相对明确的答案。

如果人工本身无法判断：

```text
A 类也合理，B 类也合理
```

那么该样本不适合作为评测样本，应该删除或重新定义规则。

### 3. 黄金用例集

文章使用模型辅助构造数据，再由人工复核。

人工复核的价值在于修正“语言正确但业务不合理”的标签。

例如：

> “电脑配件有红包可以领取吗？”

从语言看更像 BENEFIT，但如果当前权益系统没有电脑配件相关权益，识别为 BENEFIT 可能导致权益召回失败。因此业务上选择识别为 ITEM，以便进入商品推荐。

这说明：

> **标签定义不能只依据语言学含义，还必须考虑下游能力和用户最终体验。**

黄金数据集的关键不在数量，而在：

- 标签经过人工确认；
- 规则边界清晰；
- 输出结构符合下游实际需要；
- 每条样本都有业务解释。

---

## 六、评测体系：效果、速度、成本、上下文四维平衡

### 1. 基础评测流程

为了公平比较模型：

1. 每个模型运行全部用例；
2. 每次调用都使用全新上下文；
3. 所有模型使用同一版 system prompt；
4. 所有模型使用同一批用户输入；
5. 将结果与黄金标签对比；
6. 统计准确率和工程指标。

这样可以保证：

```text
唯一变量 = 模型本身
```

### 2. 四个评测维度

#### 效果

关注：

- 意图类型是否正确；
- 优先级是否正确；
- 关键词是否准确；
- 摘要是否完整；
- 追问是否自然；
- 输出格式是否合规。

#### 时延

重点观察：

- TTFT，即首 token 延迟；
- 总响应时间；
- 高并发下吞吐能力。

#### 成本

考虑：

- 输入 token 成本；
- 输出 token 成本；
- 并发资源成本；
- 高峰流量下的整体预算。

#### 上下文

确认模型是否能稳定处理：

- 长 system prompt；
- 多轮对话；
- 较长历史上下文；
- 结构化输出要求。

### 3. 工程结论

这类任务不应只看准确率。

应使用多目标决策：

```text
模型价值 =
效果 × 业务权重
− 时延惩罚
− 成本惩罚
− 资源风险
```

14B准确率更高，但资源风险更大；8B准确率略低，却更容易按时交付。最终选择8B，体现的是工程最优，而非实验室最优。

## 七、提示词优化：从手工试错变成自动反馈系统

模型确定后，真正决定效果的关键变成 system prompt。

### 1. 初始问题：提示词不是一次写完的

第一版 prompt 得分为80.8，存在明显问题。

手动优化的过程是：

```text
改几个词
   ↓
重新跑全部样本
   ↓
肉眼比较
   ↓
继续修改
```

其根本问题是缺少稳定反馈：

- 不知道整体是否变好；
- 修复一个 case 可能破坏其他 case；
- 难以定位哪条规则导致变化；
- 人容易被偶然结果误导。

因此：

> **提示词优化本质上不是文案修改，而是一个需要反馈回路的优化问题。**

---

## 八、第一轮改进：建立自动化闭环

自动化流程为：

```text
读取当前版本
   ↓
运行评测
   ↓
计算得分
   ↓
定位 badcase
   ↓
分析混淆模式
   ↓
自动改写 prompt
   ↓
进入下一轮
```

系统通过目录和版本信息管理每轮结果，自动完成：

- 评测；
- 评分；
- badcase 分类；
- 收敛判断；
- prompt 改写；
- 版本记录。

### 改进原因

自动化的价值不只是节省时间，更重要的是建立可重复实验条件：

```text
Prompt 版本 A → 分数 A
Prompt 版本 B → 分数 B
```

这样才能判断一次修改到底产生了什么效果。

---

## 九、第二轮改进：引入 train/test，解决背答案问题

### 1. 为什么单一数据集会导致过拟合

如果同一批样本同时用于：

- 发现问题；
- 修改 prompt；
- 判断改进；
- 评估最终效果；

那么 prompt 很容易记住具体样本的表述，而不是学会通用规则。

例如：

```text
看到“电脑配件有红包”就输出 ITEM
```

这可能只对某一条样本有效，却无法泛化到其他类似表达。

### 2. 数据拆分

#### 训练集

用于：

- 发现 badcase；
- 生成规则；
- 驱动 prompt 改写。

#### 测试集

用于：

- 验证泛化能力；
- 不参与 prompt 改写；
- 独立判断是否真正进步。

流程变为：

```text
训练集发现问题并优化
测试集检验是否泛化
```

### 3. 双门槛收敛

文章设置：

```text
train ≥ 90
test ≥ 92
```

两个条件必须同时满足。

这样可以避免：

- 训练集分数上涨；
- 测试集分数下降；
- prompt 逐渐记忆训练样本。

### 4. 为什么测试集门槛高于训练集

这代表系统更重视泛化能力，而不是记忆能力。

如果训练集高、测试集低，说明：

```text
规则可能过于具体
```

如果训练集和测试集都高，才说明：

```text
规则具有稳定的业务抽象能力
```

---

## 十、第三轮改进：建立提示词反过拟合防线

仅有 train/test 还不够，因为 prompt 改写器本身也可能过拟合。

文章设置了四条规则。

### 1. 案例服务于规则

错误方式：

```text
在 prompt 中不断添加：
“输入 X 时输出 Y”
```

正确方式：

```text
从多个 badcase 中抽象共同边界：
“当商品对象与优惠诉求同时出现时，根据下游可承接能力判断主意图”
```

核心原则：

> **规则解释案例，而不是案例堆积成规则。**

### 2. 限制新增案例数量

每条规则最多新增一条示意案例。

目的：

- 防止 prompt 膨胀；
- 防止模型背诵样本；
- 迫使改写器提炼一般规律；
- 控制上下文和维护成本。

### 3. 区分 train/test 的错误信号

文章用意图混淆模式描述问题：

```text
ITEM → BENEFIT
train 3 / test 2
```

表示两端都出现，可能是真实规则缺口。

```text
BENEFIT → ITEM
train 1 / test 0
```

表示只在训练集出现，可能是噪声或长尾，不应单独加规则。

```text
VAGUE → IRRELEVANT
train 0 / test 2
```

表示测试集出现，说明当前规则泛化不足，需要修正判断原理。

### 4. 已达标维度保持不动

如果某个维度已经满足要求，改写器不应随意修改该部分。

目的：

- 降低回归风险；
- 避免“修一个问题，制造另一个问题”；
- 让每轮改动更可解释；
- 缩小优化搜索空间。

---

## 十一、评分设计：规则评分负责正确性，LLM评分负责质量

### 1. 为什么不能全部用规则评分

规则适合判断：

- 意图类型字符串是否相同；
- JSON 是否合法；
- 字段是否缺失；
- 优先级是否符合标签。

但无法很好判断：

- 关键词是否自然；
- 摘要是否准确；
- 追问是否真正有帮助；
- 内容是否与用户表达一致。

### 2. 为什么不能全部用 LLM 评分

全部使用 LLM 评分会带来：

- 成本高；
- 速度慢；
- 结果可能不稳定；
- 简单问题没有必要调用大模型。

### 3. 双轨评分

#### 规则评分

判断“对不对”：

- `intent_accuracy`
- `format_compliance`
- 优先级精确匹配
- JSON schema 校验

特点：

- 快；
- 稳定；
- 可重复；
- 适合全部样本。

#### LLM 评分

判断“好不好”：

- 关键词质量；
- 摘要准确性；
- 追问自然度；
- 语义完整性。

特点：

- 更接近人类判断；
- 能处理开放式输出；
- 成本与延迟更高。

### 4. 权重分配原则

文章将高权重放在：

- 意图类型准确性：30%；
- 关键词准确性：30%。

原因是这两个字段直接决定下游行为：

```text
意图类型 → 选择哪条召回链路
关键词 → 下游具体检索什么
```

这体现了评分设计的第一性原理：

> **指标权重应由业务损失决定，而不是由实现难度决定。**

---

## 十二、方向纠偏：自动优化不能替代人工架构判断

自动 Loop 可能在局部上提高分数，却在整体设计上走偏。

例如，本来应该新增一个“无关意图初筛”步骤，优化器却可能通过修改多处规则来绕过问题。

### 正确做法

```text
发现方向错误
   ↓
立即停止当前 Loop
   ↓
人工重新确定整体方案
   ↓
先写一版方向正确的粗 prompt
   ↓
再重新启动自动优化
```

### 原因

自动优化擅长：

- 局部修正；
- 规则补全；
- badcase 归纳；
- 反复评测。

人工更适合：

- 判断系统结构；
- 调整处理顺序；
- 重新定义职责边界；
- 选择新增流程还是修改规则。

所以合理分工是：

> **人负责方向和架构，模型负责局部搜索和迭代。**

---

## 十三、线上 Bad Case：必须从全链路而不是单模块排查

### 1. 问题表现

用户询问非电商权益，例如签证相关优惠券。

模型将其识别为 BENEFIT，但权益召回失败后，工程链路兜底到商品推荐，最终展示与用户问题无关的商品。

表面上看是模型分类问题，实际上是：

```text
意图判断
   + 权益召回失败
   + 无条件商品兜底
   = 错误推荐
```

### 2. 最优解

理想方案是：

- 权益召回增加相关性评分；
- 相关度不足时不展示；
- 删除无关的商品兜底；
- 让推荐链路具备“空结果”能力。

这比单纯修改模型更彻底。

### 3. 现实约束下的折中方案

由于一期链路仍在线，无法立即重构全部工程逻辑，因此调整意图识别：

> **非电商属性的权益请求直接判为 IRRELEVANT。**

这样可以在现有链路下阻断错误兜底。

### 4. 这类问题的根本启示

模型不能脱离下游系统单独优化。

一个局部上“语义正确”的分类，如果会触发错误的工程路径，整体结果仍然是错的。

因此，真正的目标函数应是：

```text
用户最终体验
```

而不是：

```text
分类标签在语言学上的纯粹正确性
```

---

## 十四、线上验证：互动深度是转化效率的关键变量

文章将用户行为分为三组：

1. 自动首推；
2. 预设按钮交互；
3. 自定义对话。

并观察：

- 商品点击率；
- 人均价值贡献。

### 1. 自动推荐并不必然带来转化

自动首推组相比基线：

- 商品点击率下降约11.8%；
- 人均价值贡献下降约8.3%。

原因可能是：

- 用户需求尚未形成；
- 推荐内容与当前意图不匹配；
- 被动展示无法产生足够参与感；
- 系统无法获得用户的即时需求信号。

### 2. 主动交互提升效果

用户开始主动表达后，指标显著提升。

其机理是：

```text
主动表达
   ↓
需求信息增加
   ↓
意图识别更准确
   ↓
召回结果更相关
   ↓
点击和转化提升
```

### 3. 互动越深，转化越高

自定义对话组：

- 商品点击率约为普通版本的3.7倍；
- 人均价值贡献约为普通版本的2.1倍。

这里的关键不是“对话”本身，而是：

> **互动深度提升了系统获得有效需求信息的能力。**

### 4. 业务决策

应当：

- 不单独依赖自动首推；
- 用预设按钮降低表达门槛；
- 重点建设自定义对话；
- 把用户从被动浏览引导到主动表达。

---

## 十五、工程方法论：把重复工作变成工具，把人从执行者变成调度者

### 1. 重复三次就自动化

文章提出一个实用原则：

> **同一件事重复三遍，就应该考虑造工具。**

例子包括：

- 增量单元测试脚本；
- 评测结果可视化脚本。

其本质是用少量工程投入，消除大量重复操作和认知负担。

收益不只是时间节省，还包括：

- 降低人为错误；
- 提升实验频率；
- 保持流程一致；
- 让结果更容易比较。

### 2. 上下文切换是新的生产力瓶颈

开发过程中同时存在多个工作流：

- Java 代码开发；
- prompt 优化框架；
- 评测运行；
- 多个 worktree；
- 单元测试和可视化。

AI提高了执行速度，却增加了任务调度和上下文管理压力。

因此，开发者角色从：

```text
亲自完成每一步
```

转向：

```text
拆解任务、分配任务、监控结果、及时纠偏
```

### 3. AI时代的核心能力

文章最终强调三种能力：

- 保持对新技术的热情；
- 具备动手实现能力；
- 对 AI 能力保持客观、谦逊和务实。

不能走向两个极端：

- 认为 AI 什么都能做；
- 认为 AI 什么都做不好。

更有效的态度是：

> **相信工具的效率，但用数据验证结果；借助模型执行，但由人掌握方向。**

---

## 十六、未来架构：从同步接口走向流式 Agent

当前方案中：

- 意图识别；
- 商品相关性评分；

通过内部同步接口提供服务，因此无法真正流式输出。

未来可能演进为 React Agent 架构，使系统能够：

```text
识别需求
   ↓
判断是否需要追问
   ↓
调用权益或商品工具
   ↓
进行相关性判断
   ↓
根据结果继续决策
   ↓
流式返回用户
```

这意味着系统从固定链路：

```text
输入 → 分类 → 召回 → 展示
```

演进为动态决策链路：

```text
输入 → 判断 → 工具调用 → 观察结果 → 再判断 → 输出
```

其价值在于：

- 支持多轮对话；
- 支持意图流转；
- 支持根据召回结果动态决策；
- 支持更自然的流式交互；
- 减少单点模块对整体体验的限制。

# 母题驱动的证据闭环

## 母题一：为什么小模型也能承担复杂业务？

### 论点

任务复杂度不等于模型规模要求。

### 证据

- 意图类型有限；
- 输出结构固定；
- 输入较短；
- 不需要商品知识；
- 14B虽效果更好，但8B更易交付；
- 最终选择8B并上线。

### 推论

只要职责边界清晰、提示词设计合理、评测闭环完善，小模型也能完成高价值链路中的关键环节。

---

## 母题二：为什么数据集比模型排行榜更重要？

### 论点

不可信的数据会使模型比较失去意义。

### 证据

- 先按业务规则构造数据；
- 强调真实表达和边界 case；
- 删除人工无法明确判断的样本；
- 用模型生成后再人工校验；
- 形成黄金用例集。

### 推论

评测质量首先取决于标签质量，而不是样本数量或模型名气。

---

## 母题三：为什么提示词优化必须自动化？

### 论点

没有反馈回路，就无法稳定优化。

### 证据

- 手动修改依赖主观感受；
- 修复一个 case 可能破坏其他 case；
- 自动化后可以记录版本、分数和 badcase；
- 进一步引入 train/test 和收敛条件。

### 推论

系统提示词应当被当作可版本化、可测试、可评估的软件资产，而不是一次性文案。

---

## 母题四：为什么防过拟合是提示词工程的核心问题？

### 论点

Prompt 也可能记忆样本，而不是学习规则。

### 证据

- 单一数据集会导致 prompt 背答案；
- 引入 train/test；
- 限制新增案例；
- 要求从案例抽象规则；
- 区分训练集和测试集信号。

### 推论

优秀 prompt 的标准不是覆盖多少案例，而是能否对未见表达保持稳定判断。

---

## 母题五：为什么局部正确不等于系统正确？

### 论点

模型输出必须放在完整工程链路中评价。

### 证据

- BENEFIT 分类本身可能合理；
- 权益召回失败后触发无关商品兜底；
- 用户最终看到错误内容；
- 通过识别 IRRELEVANT 或修改召回逻辑解决。

### 推论

AI系统的最终评价对象应是用户体验和业务结果，而不是单一模块的离线准确率。

---

## 十七、可复用的完整方法模板

以后设计类似系统，可以直接采用以下流程：

```text
1. 明确用户最终目标
2. 画出完整业务链路
3. 定义模型职责边界
4. 将自然语言需求映射为下游动作
5. 设计互斥且可执行的意图体系
6. 明确边界 case 和异常路径
7. 根据速度、成本、准确率、上下文、资源选模型
8. 构造真实且可标注的黄金数据集
9. 使用统一环境进行模型评测
10. 建立规则评分与语义评分双轨体系
11. 用 train/test 防止 prompt 过拟合
12. 让改写器抽象规则而不是堆案例
13. 为每个维度设置业务权重和收敛门槛
14. 自动化评测、版本管理和结果可视化
15. 发现架构方向错误时及时人工纠偏
16. 用线上 CTR、转化和价值指标验证离线结论
17. 从固定链路逐步演进为可规划、可调用工具的 Agent
```

这套方法的核心，可以压缩为一句话：

> **先把问题定义正确，再把模型选得合适，随后用可信数据和自动反馈持续优化，最后必须回到完整链路和真实业务指标验证。**
