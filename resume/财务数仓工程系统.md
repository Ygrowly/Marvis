
### **结论：文章的核心不是“用 Claude 写 SQL”，而是把财务数仓研发重构为一套“规则由人定义、执行由 AI 加速、结果由数据验证”的工程系统。**

其本质是：先把隐性的业务知识、建模规范和质量规则显式化，再将需求理解、代码生成、测试验证和文档沉淀串成闭环，从而在降低重复劳动的同时，提升规范性、交付速度和质量稳定性。

## 一、第一性原理：为什么财务数仓特别适合引入 AI

### 1. 财务数仓的本质任务

财务数仓工程师主要承担三类工作：

| 任务 | 本质问题 | 典型产物 |
|---|---|---|
| 业务翻译 | 将交易、支付、成本等业务语言转换为财务语言 | 指标口径、计算逻辑 |
| 资产架构 | 将原始数据组织为可复用的数据资产 | ODS、DWD、DWS、ADS |
| 质量兜底 | 证明结果符合业务规则和数学关系 | DQC、测试 SQL、核对报告 |

财务数仓并非简单的数据搬运，而是一个“业务规则编译系统”：

\[
业务事实 + 业务规则 + 时间关系 \rightarrow 财务指标
\]

其中任何一处错误都可能影响经营分析、成本核算或财务决策。

![[Pasted image 20260808164305.png]]

### 2. 财务域的特殊复杂性

财务域的难点来自四个方面：

**第一，口径复杂。** 同一个指标可能存在业务口径、资金口径和财务管理口径。

**第二，依赖广泛。** 财务是横向域，需要连接交易、支付、营销、物流、云资源、人力等多个业务域。

**第三，时间关系复杂。** 订单发生时间、收入确认时间、结算时间可能不同，涉及跨周期分摊。

**第四，正确性要求高。** 指标之间通常存在严格关系，例如：

\[
冲销之后 = 正向 - 冲销
\]

\[
汇总项 = \sum 子项
\]

因此，财务数仓同时具备“复杂业务系统”和“高精度计算系统”的特征。

### 3. 为什么人工模式容易失效

人工研发的问题并不主要是能力不足，而是工作方式存在结构性缺陷：

- 需求文档过长，容易理解遗漏；
- 业务术语模糊，容易产生口径偏差；
- 表、字段和代码数量过多，难以全面溯源；
- 命名、分层、注释和分区等规范容易被忽略；
- 测试点数量随字段和依赖关系快速增长；
- 工期压力会降低复核深度；
- 文档、代码和测试之间容易失去同步。

因此，问题可以抽象为：

\[
研发风险 = 复杂度 \times 信息不完整 \times 人工注意力限制
\]

AI 的价值，就是降低重复性复杂度，扩大信息处理容量，并稳定执行已明确的规则。

## 二、AI 应该解决什么问题

文章并不主张 AI 代替工程师，而是重新划分人和 AI 的职责。

### 1. 人与 AI 的能力边界

| 工作类型 | 更适合人 | 更适合 AI |
|---|---|---|
| 业务判断 | 是 | 否 |
| 口径取舍 | 是 | 否 |
| 多方协调 | 是 | 否 |
| 规范执行 | 较弱 | 较强 |
| 大量文档阅读 | 较弱 | 较强 |
| SQL 初稿生成 | 较弱 | 较强 |
| 测试用例扩展 | 较弱 | 较强 |
| 影响面分析 | 较弱 | 较强 |
| 文档结构化 | 较弱 | 较强 |
| 最终上线决策 | 是 | 否 |

由此形成基本分工：

> 人负责定义目标、规则和边界；AI 负责理解材料、生成方案、执行重复动作；人再通过验证结果进行决策。

### 2. AI 能发挥作用的三个机理

#### 超大上下文：把知识集中到同一个工作空间

模型可以同时读取：

- 表结构；
- SQL 源码；
- 指标字典；
- 词根字典；
- 建模规范；
- PRD；
- 历史文档；
- 测试规则。

这解决了传统研发中的“知识孤岛”问题，使模型可以沿着字段、表、指标和业务规则进行全链路推理。

#### 语义抽象：把自然语言转成数据逻辑

AI 可以将：

- “大促期间”
- “退小仓”
- “挂在最后一单”
- “邮费返利抵减技术服务费”

转化为：

- 时间条件；
- 业务分支；
- 归属规则；
- 字段计算逻辑；
- 测试条件。

#### 稳定执行：将规范转成可重复执行的约束

当规范被写入 Prompt、Cursor Rules 或模板后，AI 可以稳定执行：

- 表命名；
- 字段命名；
- 数据分层；
- 分区过滤；
- 生命周期设置；
- 注释要求；
- DDL 模板；
- DQC 规则。

但“几乎不会出错”不能理解为无需校验。AI 只能降低低级错误，不能替代业务验证和上线审核。

## 三、整体方案：从单点提效到全链路闭环

完整方案不是某个 Prompt，而是一条研发流水线：

```text
需求文档
   ↓
业务口径解析
   ↓
技术方案与影响分析
   ↓
OneData 建模
   ↓
SQL / DDL 生成
   ↓
性能优化
   ↓
测试用例与测试 SQL
   ↓
跑数验证
   ↓
问题溯源与修正
   ↓
文档沉淀与规范更新
```

这条链路的关键是“前后相互约束”：

- 需求决定口径；
- 口径决定模型；
- 模型决定代码；
- 代码决定测试；
- 测试反过来验证需求和代码；
- 迭代结果继续完善规范。

因此，AI 应用的正确单位不是“写一段 SQL”，而是“完成一个可验证的工程闭环”。

## 四、核心方法论一：规范即 Prompt

### 1. 定义

所谓“规范即 Prompt”，不是把几条提示词发给模型，而是把团队的隐性经验整理成可执行的知识资产。

规范至少应覆盖：

- 模型分层规范；
- 表命名规范；
- 字段命名规范；
- 词根字典；
- 时间周期规范；
- 生命周期规范；
- 刷新周期规范；
- 业务过程总线；
- 指标口径；
- 数据质量规则；
- SQL 编码规范；
- 文档模板；
- 测试模板。

### 2. 为什么规范是前提

模型输出质量取决于三个因素：

\[
输出质量 = 上下文质量 \times 规则清晰度 \times 验证强度
\]

如果没有规范，模型只能根据一般经验生成“看起来合理”的结果；有了规范，模型才可能输出符合团队约束的结果。

例如，字段命名可以抽象成：

```text
主体 + 业务场景 + 币种标识 + 度量类型 + 时间单位
```

这比单纯告诉模型“字段名要规范”更容易执行和检查。

### 3. 改进原因

传统规范通常存在三个问题：

- 存在于个人经验中，难以复制；
- 分散在文档、代码和口头约定中；
- 只在评审时被动检查，无法前置约束。

将规范转为 Prompt、规则文件和模板后，规范从“事后检查标准”变成“事前生成约束”。

## 五、核心方法论二：迭代收敛，而非一次生成

### 1. 基本原则

不要期待模型第一次生成完整、正确的结果。更合理的流程是：

```text
生成初稿 → 复杂字段抽查 → 发现偏差 → 修正规范或上下文 → 重新生成 → 再次验证
```

### 2. 为什么必须迭代

财务逻辑中最难验证的不是普通字段，而是：

- 条件分支；
- 冲销逻辑；
- 跨周期分摊；
- 多口径指标；
- 多表关联；
- 精度和空值处理；
- 主键与粒度变化。

这些内容往往不能仅靠表结构推断，必须对照源码、业务文档和实际数据验证。

### 3. 迭代的真正产物

一次迭代不只是得到一版更好的 SQL，还应沉淀：

- 新的业务规则；
- 新的命名约束；
- 新的测试用例；
- 新的异常样本；
- 新的 Prompt；
- 新的文档模板。

所以，迭代过程实际上是在把个人经验转化为组织知识。

## 六、核心方法论三：海量文件阅读

### 1. AI 的作用

在大型财务项目中，模型可以同时理解：

- 多层数据表；
- 上下游 SQL；
- 历史建模方案；
- PRD；
- 业务系统文档；
- 指标定义；
- 相关测试脚本。

它可以辅助完成：

- 字段来源溯源；
- 依赖关系分析；
- 业务架构梳理；
- 表之间的影响分析；
- 旧代码结构理解；
- 建模方案生成。

### 2. 改进原因

人工阅读通常是线性的，容易出现：

- 只看当前表，不看上下游；
- 只看代码，不看业务定义；
- 只看局部逻辑，不看跨周期关系；
- 因时间限制跳过历史文档。

AI 可以先做全局扫描和结构化提炼，工程师再把精力集中到高风险字段和关键决策上。

## 七、场景一：AI OneData 标准化建模

### 1. What：要解决什么

财务核算 OneData 项目通常涉及：

- 百张以上数据表；
- 多个业务子域；
- 十余个业务过程；
- 数百个指标；
- 多层数据模型；
- 多种指标口径；
- 大量上下游依赖。

传统方式需要工程师逐表阅读、逐字段溯源、逐项命名和编写文档，投入巨大。

### 2. Why：为什么需要改进

主要问题包括：

- 口径大量隐藏在代码中；
- 文档不完整；
- 人工命名不一致；
- 跨域依赖难以全面识别；
- OnePage、口径文档和 mapping 文档重复编写；
- DQC 规则难以系统覆盖。

### 3. How：方案如何设计

输入内容包括：

- 原始建表语句；
- 源表和上下游 SQL；
- 数仓建模规范；
- 词根字典；
- 字段命名规则；
- 业务过程总线；
- 财务业务链路；
- 数据质量规范；
- 团队 Cursor Rules。

模型输出包括：

- 分层建议；
- 表级建模建议；
- 字段重命名建议；
- 指标口径说明；
- 字段来源溯源；
- 上下游依赖；
- OnePage 文档；
- DQC 规则建议；
- 需要人工确认的歧义点。

### 4. 推荐的建模流程

```text
读取规范
   ↓
读取原始表结构与源码
   ↓
识别业务过程、主体和粒度
   ↓
分析字段来源与指标口径
   ↓
划分 ODS / DWD / DIM / DWS / ADS
   ↓
生成命名、分层和生命周期建议
   ↓
生成文档与质量规则
   ↓
抽查复杂字段
   ↓
迭代规范和模型
```

### 5. 为什么采用分层建模

文章强调的业务链路是：

```text
计费层 → 核算层 → 结算层 → 财务分析层
```

分层的作用不是形式化拆表，而是隔离不同变化：

- ODS 保留源系统事实；
- DWD 统一明细粒度和业务语义；
- DWS 沉淀主题汇总；
- ADS 面向具体分析或报表需求。

这样可以减少指标重复计算，提高复用性，并降低需求变化时的影响范围。

### 6. 结果与收益

文章归纳的收益包括：

- 大幅压缩百张表的口径溯源和文档工作；
- 提升表、字段和周期规范的遵守度；
- Prompt、工具脚本、流程和模板可以跨子域复用；
- 根据指标逻辑自动推荐完整性、准确性、一致性和业务规则类 DQC。

## 八、场景二：AI SQL Coding

### 1. What：要解决什么

以财务 UE 表迭代为例，研发需要处理：

- 新增字段；
- 删除字段；
- 修改既有口径；
- 多层表同步变更；
- 多维聚合；
- 冲销和归因逻辑；
- 性能优化；
- 上下游影响分析。

### 2. Why：传统 SQL 开发的问题

复杂 SQL 常见问题包括：

- 代码过长；
- 子查询层级过深；
- 命名不统一；
- 注释缺失；
- 业务逻辑和技术逻辑混在一起；
- 分区过滤不显式；
- 公共逻辑重复；
- 改一个字段却遗漏上下游。

因此，问题不只是“写得慢”，更是“难以阅读、难以验证、难以维护”。

### 3. How：五步开发流程

#### 第一步：整理需求

将 BI 需求文档转换为技术文档，明确：

- 新增字段；
- 修改字段；
- 删除字段；
- 字段口径；
- 数据来源；
- 目标层级；
- 统计周期；
- 主键和粒度；
- 待确认问题。

#### 第二步：分析字段来源

让模型读取 DWD、DWS 和 ADS 源码，判断：

- 哪些字段已经存在；
- 哪些字段需要新增；
- 哪些表需要关联；
- 哪些字段需要向下游传递；
- 哪些字段的粒度不一致。

#### 第三步：生成 ETL 代码

由模型生成各层的：

- DDL；
- SELECT；
- JOIN；
- 聚合；
- 窗口函数；
- 条件分支；
- 字段注释；
- 分区过滤。

#### 第四步：执行命名规范校准

结合指标字典、词根字典和 Cursor Rules，统一：

- 字段名；
- 别名；
- 表名；
- 注释；
- 关键字段标识；
- 时间周期后缀。

#### 第五步：生成测试 SQL 并跑数验证

模型生成：

- 字段级校验；
- 汇总关系校验；
- 冲销关系校验；
- 上下游一致性校验；
- 边界条件校验；
- 精度校验。

### 4. 代码重构的改进原因

AI 重构旧 SQL 的价值，不是为了追求代码“更漂亮”，而是为了降低后续变更成本：

- 按业务域或指标口径分段；
- 拆分过长子查询；
- 抽取公共逻辑；
- 统一别名；
- 补充字段说明；
- 显式增加分区条件；
- 保留业务逻辑并改善结构。

可维护性可以近似理解为：

\[
维护成本 \propto 逻辑耦合度 \times 阅读成本
\]

结构化 SQL 能降低这两个因素。

### 5. 性能优化机制

模型可以结合 SQL、表结构和执行计划，识别：

- 大表全量扫描；
- 分区裁剪失效；
- JOIN 顺序不合理；
- 数据倾斜；
- 重复计算；
- 中间结果过大；
- 不必要的表链路；
- 资源配置不足。

并提出：

- 谓词下推；
- 分区过滤；
- JOIN 重排；
- 中间结果物化；
- 表合并；
- 逻辑下沉；
- Spark 或 ODPS 参数调优。

但性能建议必须通过实际执行计划和跑数验证，不能只依据模型推测。

## 九、场景三：AI 数据测试


![[Pasted image 20260808164421.png]]

### 1. What：要验证什么

财务数据测试不是只验证“SQL 能否运行”，而是验证：

- 字段计算正确；
- 汇总关系正确；
- 冲销关系正确；
- 时间分摊正确；
- 上下游结果一致；
- 边界场景不出错；
- 精度误差在可接受范围内；
- 业务规则已经正确转译。

### 2. Why：为什么人工测试容易遗漏

指标之间存在连锁关系：

\[
字段变化 \rightarrow 相关字段变化 \rightarrow 汇总指标变化 \rightarrow 下游报表变化
\]

一个字段的改动可能影响数十个字段。人工测试容易只验证主路径，而忽略：

- 退货；
- 冲销；
- 空值；
- 负数；
- 跨周期；
- 多次发生；
- 精度舍入；
- 极端金额；
- 无匹配关联记录。

### 3. How：测试体系设计

#### 字段级验证

验证单个字段是否符合预期计算逻辑。

#### 公式级验证

例如：

\[
正向金额 - 冲销金额 = 冲销后金额
\]

\[
子项金额之和 = 汇总金额
\]

#### 业务规则验证

将自然语言转为可执行断言，例如：

- 退小仓场景下，卖家邮费出资应归入指定收入冲销；
- 邮费返利应抵减技术服务费；
- 商业化订单和交易订单时间不一致时，应按规则跨周期分摊。

#### 边界场景验证

覆盖：

- 空值；
- 零值；
- 负值；
- 重复记录；
- 无关联记录；
- 首单和末单；
- 跨月和跨周期；
- 多次退款；
- 小数精度。

#### 影响面验证

识别字段变动会影响哪些：

- 上游表；
- 下游表；
- 汇总字段；
- 报表；
- 指标；
- DQC 规则。

### 4. AI 的实际价值

AI 在测试阶段主要承担五类工作：

- 自动扩展测试用例；
- 从业务规则中发现遗漏测试点；
- 自动生成测试 SQL；
- 对异常结果进行逐步溯源；
- 区分逻辑错误与可接受的精度误差。

它的核心价值不是“自动判定一切正确”，而是扩大测试覆盖范围和问题发现能力。

## 十、场景四：AI 需求文档转换

### 1. What：要解决什么

BI 需求通常包含大量：

- 字段口径调整；
- 新增字段；
- 废弃字段；
- 冲销逻辑；
- 跨表关系；
- 业务术语；
- 隐含前置条件。

工程师需要把业务语言转换为技术变更方案。

### 2. Why：为什么这是高价值环节

需求理解错误会在后续被放大：

\[
需求误解 \rightarrow 模型错误 \rightarrow SQL 错误 \rightarrow 测试遗漏 \rightarrow 上线返工
\]

越早消除歧义，后续成本越低。

### 3. How：转换结果应包含什么

模型读取 PRD、相关表代码和财务规则后，应输出：

- 按表分类的改动清单；
- 字段含义和口径变化；
- 数据来源；
- 计算位置；
- 新增字段；
- 废弃字段；
- 冲销逻辑；
- 表之间的依赖关系；
- 实现顺序；
- 待业务确认事项；
- 对应代码修改建议；
- 修改原因和影响范围。

例如，先修改 DWS，再修改 ADS，是因为 ADS 通常依赖 DWS 的结构和口径。明确实现顺序可以减少反复返工。

## 十一、端到端质量闭环

完整的 AI 数仓研发应形成如下闭环：

```text
规范资产
  ↓
需求解析
  ↓
模型设计
  ↓
代码生成
  ↓
性能分析
  ↓
测试生成
  ↓
跑数验证
  ↓
异常溯源
  ↓
文档沉淀
  ↓
规范更新
```

其中每个环节都应有输入、输出和验收条件：

| 环节 | 输入 | 输出 | 验收重点 |
|---|---|---|---|
| 需求解析 | PRD、业务规则 | 技术需求 | 口径是否完整 |
| 模型设计 | 表结构、规范 | 分层和字段方案 | 粒度、依赖、命名 |
| 代码生成 | 技术方案 | DDL、SQL | 逻辑和规范 |
| 性能优化 | SQL、执行计划 | 优化方案 | 扫描量、耗时、资源 |
| 数据测试 | 规则、代码 | 测试 SQL | 覆盖度和准确性 |
| 跑数验证 | 测试 SQL、样本数据 | 异常结果 | 公式、边界、精度 |
| 文档沉淀 | 最终方案 | OnePage、口径文档 | 可复用性 |

## 十二、母题驱动的证据闭环

这篇文章可以归纳为五个核心母题。

### 母题一：AI 的价值取决于知识是否被结构化

**证据：**

- 模型需要规范、词根、指标字典和历史代码；
- 没有规范时，输出只能依赖通用经验；
- 规范沉淀后，命名、分层和文档质量提升。

**结论：**

AI 项目首先是知识工程项目，其次才是模型调用项目。

### 母题二：规范执行是 AI 最容易产生稳定收益的领域

**证据：**

- AI 能稳定执行命名、分层、注释、分区和 DQC 规则；
- 人在工期压力下容易漏项；
- 规范越细，AI 的相对优势越明显。

**结论：**

优先让 AI 接管规则明确、重复度高、人工容易遗漏的工作。

### 母题三：AI 不能替代业务判断

**证据：**

- 多种指标口径需要业务权衡；
- 跨周期分摊需要理解真实业务；
- 模糊术语仍需要人工确认；
- 最终上线需要人工审核。

**结论：**

人机协作的边界应是：

\text{人定口径，AI 执行逻辑，人验结果}
\]

### 母题四：测试不是收尾动作，而是 AI 研发的核心环节

**证据：**

- 财务指标具有公式关系；
- 字段变更存在上下游影响；
- AI 能自动生成公式、边界和业务规则测试；
- 测试结果又能反向修正模型和代码。

**结论：**

没有测试闭环的 AI Coding，只是更快地产生未经验证的代码。

### 母题五：真正的收益来自流程重构，而非单次提速

**证据：**

- 文章同时覆盖建模、编码、测试和文档；
- Prompt、脚本、模板和 SOP 可以复用；
- 团队目标是从“人做”为主转向“人定规则、模型执行”。

**结论：**

AI 的长期价值是改变研发流程和组织知识复用方式，而不仅是缩短某一次 SQL 编写时间。

## 十三、方案落地时的边界与风险

### 1. AI 不能可靠决定业务口径

当 PRD 存在歧义时，模型可以列出问题，但不应自行选择答案。

### 2. AI 不能仅凭文本证明结果正确

代码结构合理、SQL 能运行，并不代表业务结果正确。必须结合：

- 样本数据；
- 历史基线；
- 公式校验；
- 上下游核对；
- 业务确认。

### 3. 上下文过多不等于信息有效

超大上下文只有在材料结构清晰、版本正确、关系明确时才有价值。否则可能引入：

- 过期规范；
- 相互矛盾的定义；
- 无关代码；
- 错误历史结论。

### 4. 生成质量不等于生产质量

模型生成的代码仍需经过：

- 语法检查；
- 规范检查；
- 数据测试；
- 性能测试；
- 权限与合规检查；
- 人工评审。

### 5. 不能只追求速度

如果只考核“代码生成速度”，可能导致：

- 测试缩水；
- 口径确认不足；
- 文档质量下降；
- 返工和线上风险增加。

合理的指标应同时衡量：

- 交付周期；
- 一次通过率；
- 缺陷率；
- 测试覆盖度；
- 规范遵守率；
- 返工次数；
- 资源消耗；
- 知识资产复用率。

## 十四、可执行的落地路线

### 第一阶段：选择小而明确的试点

优先选择：

- 规范相对稳定；
- 重复劳动较多；
- 数据可重跑；
- 结果容易验证；
- 业务边界清晰。

例如：

- SQL 重构；
- 测试 SQL 生成；
- 字段命名校准；
- PRD 转技术文档。

### 第二阶段：建立规范资产

整理：

- 表和字段命名；
- 词根；
- 分层；
- 时间周期；
- 生命周期；
- DDL 模板；
- SQL 模板；
- 测试模板；
- DQC 规则；
- 常见业务术语；
- 历史异常案例。

### 第三阶段：建立标准 Prompt 和工作流

Prompt 不应只写“请生成 SQL”，而应明确：

- 角色；
- 输入材料；
- 业务背景；
- 规则约束；
- 输出格式；
- 验收标准；
- 必须追问的歧义；
- 禁止自行假设的内容。

### 第四阶段：建立人机协作门禁

模型输出后至少经过：

```text
规范检查
→ 业务口径检查
→ 代码检查
→ 数据测试
→ 性能检查
→ 人工审批
```

### 第五阶段：沉淀可复用资产

将有效成果沉淀为：

- Prompt 模板；
- Cursor Rules；
- SQL 模板；
- 测试用例库；
- 异常样本库；
- 指标字典；
- 业务知识库；
- 自动化脚本；
- 团队 SOP。

## 十五、最终抽象

这篇文章可以压缩成一个完整公式：

\[
AI 数仓效能
=
规范资产
\times
上下文组织
\times
模型执行
\times
自动化验证
\times
迭代沉淀
\]

其中：

- **规范资产**决定模型是否知道“应该怎么做”；
- **上下文组织**决定模型能否理解完整问题；
- **模型执行**负责生成方案、代码、文档和测试；
- **自动化验证**决定结果是否可信；
- **迭代沉淀**决定一次实践能否转化为团队能力。

因此，文章真正提出的是一种新的财务数仓研发范式：

> 业务专家定义口径，数仓工程师定义模型与质量边界，AI 负责大规模理解、生成和执行，数据测试负责证明结果，规范资产负责让经验持续复用。
