
### **结论：Agent 评测的本质，是把“Agent 是否可靠”转化为可观测、可判断、可迭代、可规模化的工程系统。**

文章的核心公式是：

> **观测 + 评测 = 持续迭代**

评测对象已经从单一模型的“答案质量”，升级为由模型、Prompt、Skill、工具、记忆、状态和业务流程共同构成的“任务系统”。因此，成熟的 Agent 评测必须同时回答四个问题：

1. **What：Agent 做得好不好？**
2. **Why：哪里出了问题，为什么出问题？**
3. **How：如何稳定地测量、定位和改进？**
4. **Scale：如何接入研发、发布和线上运营，持续扩大覆盖？**

---

## 一、从第一性原理定义 Agent 评测

### 1.1 评测的根本目的

评测不是为了生成一个分数，而是为了支持决策：

- 当前版本是否比上一版本更好？
- 哪些能力已经达标？
- 哪些问题限制了业务效果？
- 问题来自模型、Prompt、Skill、工具还是环境？
- 修改后是否引入了新的回归问题？
- Agent 能否从 Demo 走向稳定生产？

因此，评测的最终产物不应只是分数，而应包括：

> **结果判断 + 问题定位 + 优化方向 + 回归依据**

### 1.2 Agent 评测的对象

传统评测主要关注单个模型：

```text
输入 → 模型 → 输出
```

Agent 的真实执行链路更接近：

```text
用户需求
  ↓
模型理解与规划
  ↓
Prompt / Skill / 策略
  ↓
工具调用
  ↓
外部环境交互
  ↓
记忆与状态更新
  ↓
多轮执行与动态调整
  ↓
最终结果
```

所以，Agent 的评测对象不是模型本身，而是：

> **模型 + 系统 + 工具 + 流程 + 环境的整体协作能力**

这也是为什么单纯提高模型榜单分数，不一定能带来业务收益。

---

## 二、Agent 评测与传统模型评测的根本差异

### 2.1 三种评测问题

| 阶段 | 核心问题 | 主要对象 |
|---|---|---|
| 传统机器学习 | 算得准不准 | 模型预测结果 |
| 大模型评测 | 能力强不强 | 模型输出与知识能力 |
| Agent 评测 | 能否稳定完成任务 | 完整任务系统 |

Agent 评测的关键变化是：

> 从“判断答案对不对”，转向“判断事情是否做成，以及是如何做成的”。

### 2.2 为什么最终结果不够

两个 Agent 可能都完成了任务，但工程质量不同：

- Agent A：步骤清晰、工具调用稳定、耗时可控、结果可复现；
- Agent B：反复试错、路径混乱、成本较高、偶然成功。

如果只看最终答案，两者会得到相同评价；但在真实生产中，Agent B 可能带来：

- 更高 Token 成本；
- 更长响应时间；
- 更高工具调用费用；
- 更大的失败概率；
- 更难排查的问题；
- 更严重的误操作风险。

因此，评测必须从单一结果扩展为多维质量模型：

```text
Agent质量
= 结果质量
+ 过程质量
+ 效率
+ 安全与风险
```

---

## 三、评测的四个核心维度

### 3.1 结果层：任务是否完成

回答：

- 任务是否成功？
- 输出是否正确？
- 输出是否满足用户目标？
- 结果是否可执行、可使用？
- 外部环境状态是否真正完成变更？

应避免只相信 Agent 的自述。

例如，Agent 回复“航班已经预订”，并不代表任务完成；真正的成功标准应是：

> 数据库中是否生成了有效订单，或者外部系统是否产生了预期状态变化。

### 3.2 过程层：执行路径是否合理

关注：

- 是否正确理解任务？
- 是否进行了合理拆解？
- 是否制定了有效计划？
- 是否选择了正确的工具和 Skill？
- 是否出现无效循环？
- 是否在中间结果变化后调整了策略？
- 是否存在多余步骤？

过程层用于解释“为什么成功”或“为什么失败”。

### 3.3 效率层：成本是否可接受

主要指标包括：

- 总耗时；
- Token 消耗；
- 工具调用次数；
- 重试次数；
- 并发资源占用；
- 外部 API 调用成本；
- 单任务平均成本。

一个准确但极其昂贵的 Agent，可能不具备生产价值。

### 3.4 风险层：是否安全可靠

关注：

- 是否越权访问；
- 是否执行未经授权的操作；
- 是否修改或删除错误数据；
- 是否泄露敏感信息；
- 是否在高风险场景缺少确认；
- 是否受提示注入或异常环境影响；
- 是否产生不可逆误操作。

对于生产系统，风险指标通常不是“加分项”，而是准入门槛。

---

## 四、为什么观测是评测的基础

### 4.1 根本原因：黑盒无法稳定改进

Agent 具有生成随机性，同一个输入可能产生不同路径。用户却需要稳定的结果。

这形成了一个矛盾：

```text
模型具有概率性
        ↓
用户需要确定性和可靠性
        ↓
必须观察并控制执行过程
```

如果系统只记录：

```text
用户输入 → 最终回复
```

就无法回答：

- Agent 为什么选择这个工具？
- 为什么没有调用另一个工具？
- 哪一步开始偏离？
- 是规划错误还是工具返回错误？
- 是 Skill 描述不清还是环境状态异常？
- 为什么这次成功、下次失败？

因此：

> **看不见的问题，几乎不可能被稳定解决。**

### 4.2 Trace 的作用

Trace 或 Trajectory 应记录一次任务的完整执行过程，包括：

- 用户输入；
- 系统提示词和上下文；
- 模型输出；
- 规划过程；
- 工具调用；
- 工具参数；
- 工具返回结果；
- Skill 执行；
- 中间状态；
- 重试和异常；
- 最终输出；
- 环境最终状态。

它的目标不是简单记录日志，而是：

> **还原现场、定位问题、支持回放和评测。**

### 4.3 观测与评测的关系

二者分工不同：

| 能力 | 解决的问题 |
|---|---|
| 观测 | 发生了什么 |
| 评测 | 做得好不好 |
| 归因 | 为什么好或不好 |
| 回归 | 修改后是否变好 |
| 门禁 | 是否允许发布 |

没有观测，评测只能停留在结果打分；没有评测，观测只能成为日志堆积。

---

## 五、两类核心评测：Response Evaluation 与 Trajectory Evaluation

### 5.1 Response Evaluation

主要评价最终输出：

```text
Query → Answer
```

适合：

- AI 搜索；
- 客服问答；
- 文本生成；
- 摘要和翻译；
- 简单信息查询。

典型指标：

- 正确性；
- 相关性；
- 完整性；
- 清晰度；
- 风格；
- 安全性。

### 5.2 Trajectory Evaluation

评价完整执行轨迹：

```text
Prompt
  → Expected Behavior
  → Trace / Trajectory
  → Outcome
```

适合：

- 多步骤任务；
- 工具调用；
- 文件操作；
- 代码开发；
- 工作流执行；
- 长程 Agent；
- Skill 评测。

它要判断：

- 是否完成目标；
- 是否采取合理步骤；
- 是否正确调用工具；
- 是否有效处理错误；
- 是否浪费资源；
- 是否满足安全约束；
- 是否产生正确的最终环境状态。

## 六、评测体系设计：核心不是堆指标，而是搭桥

### 6.1 为什么业务指标和模型指标无法直接连接

业务通常关心：

- DAU；
- 留存；
- 点击率；
- 转化率；
- 履约率；
- 客诉率；
- 成本。

模型或 Agent 层通常关心：

- 意图识别；
- 工具调用准确率；
- 检索质量；
- 规划质量；
- 输出正确性；
- 任务成功率。

二者之间存在鸿沟：

```text
模型能力提升 ≠ 必然带来业务增长
业务指标下降 ≠ 必然是模型问题
```

必须建立中间层的“桥梁指标”。

### 6.2 分层指标体系

可以建立四层结构：

```text
业务层：业务结果
   ↓
系统层：系统运行效果
   ↓
Agent层：任务与行为质量
   ↓
模型层：基础能力
```

以 AI 搜索为例：

- 业务层：DAU、留存、点击；
- 搜索层：召回率、点击率；
- Agent 层：意图识别、检索策略、结果整合、答案可信度；
- 模型层：理解、推理、生成能力。

这样才能回答：

- 业务指标为什么下降？
- 是召回问题、Agent 问题还是模型问题？
- 模型能力提升为什么没有转化为业务收益？

### 6.3 桥梁指标的设计原则

桥梁指标应满足：

1. 与业务目标存在因果或强相关关系；
2. 能被 Agent 行为直接影响；
3. 能通过 Trace 或结果验证；
4. 能形成具体优化动作；
5. 能支持版本对比和回归。

一个好的指标不是“看起来专业”，而是能指导下一步改进。

---

## 七、客观评测与主观评测必须并行

### 7.1 客观评测

客观评测依赖明确规则或可验证状态，例如：

- 是否完成任务；
- 是否调用指定工具；
- 参数是否正确；
- 是否生成目标文件；
- 数据库状态是否改变；
- 是否触发违规操作；
- Token 是否超过阈值；
- 是否在规定时间内完成。

优点是：

- 结果稳定；
- 成本较低；
- 易于自动化；
- 适合高频回归。

适合覆盖：

> 高频、结构化、可规则化的问题。

### 7.2 主观评测

主观评测用于判断开放性和复杂业务质量，例如：

- 回答是否自然；
- 方案是否合理；
- 解释是否充分；
- 沟通是否符合业务规范；
- 内容是否真正有帮助。

优点是能够覆盖复杂质量，但存在：

- 评测员标准不一致；
- 评测成本高；
- 结果不稳定；
- 机器难以直接复现。

适合覆盖：

> 开放性、高价值、复杂业务场景。

### 7.3 推荐组合方式

```text
客观评测：覆盖确定性问题
主观评测：覆盖复杂质量
人工评测：定义和校准标准
AI评测：规模化运行和回归
```

正确的方向不是完全依赖人工，也不是盲目依赖模型评分，而是：

> 人负责定义判断标准，机器负责扩大判断规模。

---

## 八、主观评测如何实现“人人一致、人机一致”

### 8.1 两种不一致

主观评测的核心问题不是没人会评，而是：

```text
评测员之间不一致
人工与机器之间不一致
```

如果同一个 Case 在不同人、不同时间、不同评测方式下结论不同，指标就不具备可信度。

### 8.2 “独裁者”机制的本质

文章中的“独裁者”不是强调个人权力，而是强调：

> 必须有明确的最终标准整合者，避免多方各自定义“好”。

其职责是：

- 收集产品、运营、研发、QA 的意见；
- 统一评测目标；
- 在分歧时做最终决策；
- 防止评测体系碎片化；
- 随着线上 Good Case 和 Bad Case 持续修正标准。

评测标准最终应由真实业务反馈校准，而不是永久依赖某个人。

### 8.3 指标下钻

“大而模糊”的指标无法稳定判断。

例如：

> “请判断回答是否口语化，并打 0 到 10 分。”

这个问题的问题在于：

- “口语化”定义模糊；
- 评分尺度主观；
- 不同人对 6 分和 8 分的理解不同；
- 机器难以学习隐含标准。

改进方式是拆成可观察事实：

- 是否使用指定称谓；
- 是否使用非正式口语词；
- 是否包含符合场景的语气词；
- 是否避免正式公文表达。

### 8.4 Rubric 二元化

尽可能把 Rubric 变成：

```text
是 / 否 / 未知
0 / 1 / unknown
```

原因是二元规则：

- 边界更清晰；
- 判断成本更低；
- 更容易培训评测员；
- 更容易让机器复现；
- 更容易分析分歧来源。

### 8.5 Unknown 的作用

`unknown` 不是无效结果，而是诊断信号。

如果某条 Rubric 的 unknown 占比很高，说明：

- 定义不清；
- 证据不足；
- 样本不适配；
- 评测维度拆解错误；
- 需要补充上下文或重写规则。

因此，评测规则应持续迭代，直到：

- 人人一致率达到可信阈值；
- 人机一致率达到可信阈值。

文章举例说明，二元化方案可以显著提升人机一致率。

## 九、从第一性原理设计 Rubric

一个可执行的 Rubric 应包含四部分：

```text
判断对象 + 判断条件 + 证据来源 + 输出结果
```

例如评价“是否正确完成退款”：

- 判断对象：退款任务；
- 判断条件：订单状态已变更为退款完成；
- 证据来源：订单系统最终状态；
- 输出结果：是 / 否 / 未知。

评价“是否正确调用工具”：

- 判断对象：工具调用；
- 判断条件：工具名称、参数、调用时机均符合预期；
- 证据来源：Trace；
- 输出结果：是 / 否 / 未知。

评价“是否安全”：

- 判断对象：高风险操作；
- 判断条件：是否经过授权和确认；
- 证据来源：用户授权记录、工具调用记录；
- 输出结果：是 / 否 / 未知。

优秀 Rubric 的标准是：

> 不依赖评测员的整体感觉，而依赖可观察证据。

## 十、Agent 评测是一门实践科学

### 10.1 五个关键环节

完整评测链路可以拆成：

```text
采集 → 清洗 → 评测 → 质检 → 分析归因
```

#### 采集

获取线上或沙箱中的任务数据，包括：

- 用户输入；
- 任务上下文；
- Trace；
- 最终输出；
- 环境状态；
- 错误信息。

#### 清洗

处理：

- 重复样本；
- 无效样本；
- 缺失上下文；
- 脏数据；
- 场景分类；
- 任务难度；
- 数据版本。

#### 评测

使用：

- 规则评测；
- 人工评测；
- AI 评测；
- 结果检查；
- 轨迹检查；
- 风险检查。

#### 质检

检查：

- 评测标准是否一致；
- Rubric 是否可判断；
- 人机是否一致；
- 评测结果是否稳定；
- 是否存在系统性偏差。

#### 分析与归因

将问题定位到：

- 模型；
- Prompt；
- Skill；
- 工具；
- 规划；
- 记忆；
- 环境；
- 数据；
- 评测规则。

最终形成：

- 优化建议；
- 回归样本；
- 版本对比；
- 研发任务。

### 10.2 为什么不应一开始设计复杂体系

初期直接设计大量指标，通常会出现：

- 指标难以执行；
- 评测员无法对齐；
- 机器无法判断；
- 数据不足以验证指标价值；
- 评测成本过高；
- 评测结果无法指导研发。

更合理的路径是：

```text
高频场景
  → 少量关键指标
  → 线上 Bad Case
  → 高质量 Good Case
  → 标准评测样本
  → 反哺优化
  → 新一轮线上采样
```

### 10.3 Good Case 与 Bad Case 的作用

#### Good Case

用于定义：

- 什么叫高质量完成；
- 什么是优秀执行范式；
- 哪些行为值得保留；
- 目标效果的上限是什么。

#### Bad Case

用于发现：

- 能力边界；
- 系统短板；
- 异常路径；
- 风险点；
- 指标遗漏；
- 真实用户痛点。

通常 Bad Case 的信息价值更高，因为它暴露了系统真正的问题。

### 10.4 数据飞轮

评测应形成持续循环：

```text
线上运行
  → 采集 Case
  → 识别 Good / Bad Case
  → 更新评测集和 Rubric
  → 评测新版本
  → 优化模型、Prompt、Skill、策略
  → 灰度或全量
  → 再次采样
```

这比一次性构建“完美评测体系”更具可行性。

## 十一、专家知识为什么不可替代

### 11.1 模型能力的边界

模型能力依赖训练数据。即使基座模型能力持续增强，也可能在垂直场景中缺少：

- 行业知识；
- 隐含规则；
- 业务流程；
- 专业术语；
- 风险判断；
- 高质量示例；
- 真实用户偏好。

因此，很多所谓“模型做不到”的问题，本质上是：

> 模型缺少足够高质量的领域数据和专家标准。

### 11.2 专家知识的作用

行业专家可以补充：

- 什么结果才算真正完成；
- 哪些行为符合行业规范；
- 哪些错误不可接受；
- 哪些策略适合不同用户；
- 哪些边界情况需要人工介入。

评测中的核心问题是：

> 谁来定义“好”？

答案通常不是通用模型，而是最懂业务目标和风险的人。

### 11.3 专家意见不一致怎么办

分歧不一定是噪声，可能说明：

- 业务存在多种优秀策略；
- 用户偏好不同；
- 场景目标不同；
- 需要建立多个风格或策略分支。

可以将其转化为：

- 不同 Benchmark；
- 不同用户画像；
- 不同策略路线；
- 不同业务目标。

例如，同一个销售 Agent 可以分别评测：

- 激进转化型；
- 稳健关系型；
- 长期维护型。

---

## 十二、冷启动阶段如何建立评测集

### 12.1 为什么需要种子评测集

大模型和 Agent 存在随机性，少量线上样本不能稳定代表真实能力。Corner Case 可能导致体验剧烈波动。

种子集可以用于：

- 建立初始基线；
- 进行版本回测；
- 覆盖典型场景；
- 约束能力下限；
- 防止优化一个问题时破坏另一个问题。

### 12.2 是否必须先做完整种子集

不是绝对必须，而是成本与风险的权衡。

适合先构建种子集的情况：

- 业务风险高；
- 错误代价大；
- 线上试错成本高；
- 任务复杂；
- 外部影响大。

可以小流量灰度采集 Case 的情况：

- 场景容错率较高；
- 用户反馈成本较低；
- 种子集构建成本很高；
- 线上试错风险可控。

### 12.3 推荐方案

```text
少量人工生产高质量样本
  → AI 辅助扩写和生成
  → 人工抽检和修正
  → 建立冷启动种子集
```

人工负责质量，AI 负责规模。

---

## 十三、短程 Agent 与长程 Agent 的变化

### 13.1 短程 Agent

典型模式：

```text
Query → Answer
```

特点：

- 任务步骤少；
- 工具调用少；
- 主要关注回答质量；
- 结果相对容易判断；
- 人工评测仍可承担较大比例。

### 13.2 长程 Agent

典型模式：

```text
复杂任务
  → 多步拆解
  → 多次调用工具或 Skill
  → 读取中间结果
  → 动态调整策略
  → 修改环境状态
  → 输出结果
```

重点从“回答问题”变为“完成任务”。

长程 Agent 的复杂性来自时间跨度：

- 中间状态更多；
- 失败点更多；
- 工具依赖更强；
- 环境变化更多；
- 路径不确定性更高；
- 任务成功标准更接近环境状态。

### 13.3 最本质的评测变化

```text
短程 Agent：说得好不好
长程 Agent：事情做成没有，以及怎么做成
```

因此，长程 Agent 必须重点评测：

- Task；
- Expected Behavior；
- Trace；
- Outcome；
- Grader；
- Trial；
- Evaluation Harness。

---

## 十四、面向 Task 的长程 Agent 评测模型

### 14.1 Task 的定义

Task 是：

> 具有明确输入和成功标准的单个测试任务。

一个 Task 至少应包含：

```text
Prompt
Expected Behavior
Success Criteria
Environment
```

### 14.2 三元组模型

可以将任务评测抽象为：

```text
Prompt + Expected Behavior + Trace
```

其中：

- Prompt：用户要求；
- Expected Behavior：预期行为；
- Trace：Agent 实际执行路径。

进一步还应加入：

```text
Outcome：环境最终状态
```

因为最终文本可能与真实状态不一致。

### 14.3 Trial 的必要性

同一 Task 多次运行，可能得到不同轨迹。因此需要多次 Trial：

```text
一个 Task → 多次 Trial → 统计稳定性
```

可观察：

- 成功率；
- 路径一致性；
- 平均成本；
- 失败模式；
- 最差表现；
- 结果方差。

对于具有随机性的 Agent，只测试一次往往不足以判断可靠性。

---

## 十五、Skill 评测的特殊要求

### 15.1 为什么 Skill 评测会成为普遍需求

Skill 的开发门槛越来越低，可能由：

- 专业研发人员创建；
- 业务人员修改；
- AI 自动生成；
- 多个团队复用。

因此，未来的评测对象不再只是少数专业 Agent，而可能是：

> 任何创建、修改或接入 Skill 的人。

### 15.2 Skill 评测系统的要求

系统必须：

- 简单；
- 标准化；
- 自动化；
- 易于接入开发流程；
- 易于接入发布流程；
- 能够提供明确反馈。

### 15.3 Skill 全生命周期

可抽象为：

```text
设计 → 开发 → 测试 → 发布 → 使用 → 监控 → 迭代 → 下线
```

每个阶段都需要评测：

- 设计阶段：目标和边界是否清楚；
- 开发阶段：逻辑和依赖是否正确；
- 测试阶段：核心任务是否通过；
- 发布阶段：是否达到准入标准；
- 使用阶段：线上成功率和风险如何；
- 迭代阶段：新版本是否回归；
- 下线阶段：是否存在替代能力或遗留风险。

---

## 十六、长程 Agent 评测基础设施设计

一个可生产化的评测平台至少应具备以下模块。

### 16.1 全链路回放

能够复现：

```text
输入 → 规划 → 工具 → 中间结果 → 重试 → 最终输出 → 环境状态
```

作用是：

- 复现问题；
- 对比版本；
- 检查路径；
- 支持调试；
- 支持人工复核。

### 16.2 Case 管理

统一维护：

- 任务输入；
- 上下文；
- 环境配置；
- 预期行为；
- 成功标准；
- Rubric；
- 版本；
- 标签；
- 历史结果。

### 16.3 执行沙箱

按风险等级隔离：

- 只读环境；
- 可写环境；
- 高风险环境；
- 模拟工具；
- 脱敏数据；
- 可回滚环境。

评测本身不能破坏真实生产数据。

### 16.4 AI 评测引擎

应支持：

- Rubric 驱动；
- 规则判定；
- 轨迹分析；
- 结果校验；
- 人机一致性校准；
- 批量评测；
- 自动回归。

关键不是让机器自由打分，而是让机器执行清晰、稳定的判断规则。

### 16.5 报告与归因

报告不应只显示：

```text
得分：72
```

而应说明：

- 哪条规则失败；
- 哪一步开始偏离；
- 是否为规划错误；
- 是否为工具错误；
- 是否为 Skill 错误；
- 是否为环境错误；
- 是否为模型能力不足；
- 应采取什么优化动作。

### 16.6 回归机制

每次修改以下内容，都应自动回归：

- 模型；
- Prompt；
- Skill；
- 工具；
- 记忆策略；
- 规划策略；
- 环境依赖。

回归不仅要检查平均分，还要关注：

- 历史问题是否修复；
- 新问题是否产生；
- 风险是否增加；
- 成本是否恶化；
- 长尾场景是否退化。

### 16.7 准入与准出门禁

将评测接入：

- 开发流程；
- 代码提交；
- Skill 发布；
- Agent 上线；
- 灰度扩量；
- 全量发布；
- 版本回滚。

典型门禁条件包括：

```text
核心任务成功率 ≥ 阈值
高风险违规率 = 0
关键 Rubric 通过率 ≥ 阈值
平均成本 ≤ 阈值
关键历史 Case 不得回归
```

这样评测才真正成为生产系统的一部分。

---

## 十七、评测系统的完整闭环设计

可以将完整体系抽象为六层：

```text
第一层：任务层
定义用户要完成什么任务。

第二层：行为层
定义 Agent 应该如何执行。

第三层：观测层
记录 Agent 实际做了什么。

第四层：判断层
通过 Rubric、规则和模型进行评价。

第五层：归因层
定位问题来自哪里。

第六层：工程层
将结果接入迭代、回归和发布门禁。
```

完整链路如下：

```text
业务目标
  ↓
任务定义
  ↓
成功标准
  ↓
Expected Behavior
  ↓
Trace 采集
  ↓
Outcome 检查
  ↓
Rubric 评测
  ↓
问题归因
  ↓
Prompt / Skill / 工具 / 模型优化
  ↓
回归测试
  ↓
灰度发布
  ↓
线上再采样
```

## 十八、评测中最重要的几个改进原则

### 原则一：从答案评测升级为任务评测

因为真实价值不在于“回答得像不像”，而在于“任务是否完成”。

### 原则二：从结果评测升级为结果、过程、效率、风险并重

因为相同结果可能对应完全不同的工程质量。

### 原则三：从黑盒打分升级为全链路观测

因为没有 Trace 就无法归因，也无法稳定优化。

### 原则四：从堆砌指标升级为搭建业务桥梁

因为模型指标和业务指标之间需要可解释的中间层。

### 原则五：从模糊评分升级为可验证 Rubric

因为清晰、二元化、证据化的规则更容易实现人机一致。

### 原则六：从一次性评测升级为持续数据飞轮

因为 Agent 能力、用户分布和业务目标都会变化。

### 原则七：从人工主导升级为“人工定标准、机器做规模”

因为长程轨迹数量增长后，人工无法承担全部执行。

### 原则八：从项目工具升级为基础设施

因为评测只有嵌入开发、发布和运营流程，才能真正影响质量。

---

## 十九、边界与局限

### 19.1 不是所有质量都能二元化

开放式创作、复杂策略和多目标任务，可能无法完全转换为是或否。此时可以：

- 拆成多个局部 Rubric；
- 使用等级式规则；
- 建立多个风格 Benchmark；
- 保留人工复核；
- 允许多种成功路径。

### 19.2 不是所有行为都应固定

长程 Agent 可能存在多条合理路径。评测不应强制唯一轨迹，而应区分：

- 必须满足的行为；
- 推荐行为；
- 可接受替代行为；
- 禁止行为。

也就是说，应评测“约束和目标”，而不是机械复制一条路径。

### 19.3 AI 评测不等于自动化评测

只有当机器与人工标准保持足够一致时，AI 评分才具有评测价值。否则只是机器预标注。

### 19.4 平均分不能代表稳定性

Agent 可能平均成功率很高，但在关键任务上偶发严重失败。因此必须补充：

- 多次 Trial；
- 长尾 Case；
- 风险 Case；
- 最差表现；
- 失败模式；
- 结果方差。

### 19.5 评测目标会变化

随着用户从早期尝鲜者扩展到大众用户：

- 用户画像变化；
- 容错率变化；
- 业务目标变化；
- 风险要求变化；
- 评测标准也需要变化。

评测体系不能被视为永久不变的规范。

## 二十、可直接复用的落地方法

### 阶段一：明确业务目标

先回答：

```text
Agent 为谁解决什么问题？
成功意味着什么？
失败的代价是什么？
```

### 阶段二：定义 Task

为每个核心场景明确：

- 输入；
- 环境；
- 约束；
- 预期行为；
- 成功条件；
- 风险边界。

### 阶段三：建立最小评测集

从高频核心场景开始，优先覆盖：

- 典型成功案例；
- 高频失败案例；
- 高风险案例；
- 关键长尾案例。

### 阶段四：建立 Trace 和 Outcome

确保不仅记录最终回复，还能获得：

- 工具调用；
- 中间结果；
- 错误；
- 环境最终状态。

### 阶段五：设计 Rubric

每条规则尽量：

- 单一；
- 清晰；
- 可观察；
- 可验证；
- 二元化；
- 有明确证据来源。

### 阶段六：进行人工和机器对齐

通过背靠背评测确认：

- 人人一致；
- 人机一致；
- unknown 比例可控；
- 分歧有明确原因。

### 阶段七：接入回归

将评测集接入版本迭代，每次修改后自动检查：

- 核心能力；
- 历史 Bad Case；
- 风险规则；
- 成本和延迟；
- 新增退化。

### 阶段八：接入发布门禁

将关键评测结果变成发布条件，而不是上线后的参考报告。

### 阶段九：持续更新资产

持续将线上数据转化为：

```text
问题 → Case → Rubric → 回归集 → 优化任务
```

## 二十一、用母题驱动的证据闭环理解全文

### 母题一：为什么 Agent 不能只看最终答案？

**论点：** 相同结果可能对应不同工程质量。  
**证据：** 一个 Agent 路径稳定，另一个反复试错但偶然成功。  
**推论：** 必须评测过程、效率和风险。  
**方案：** 引入 Trace、Trajectory Evaluation 和 Outcome 校验。

### 母题二：为什么观测是评测的基础？

**论点：** 无法看到执行过程，就无法定位问题。  
**证据：** 仅有输入和最终输出时，无法知道错误发生在哪一层。  
**推论：** 评测必须建立在全链路记录之上。  
**方案：** 记录模型、Prompt、Skill、工具、状态和环境变化。

### 母题三：为什么不能只堆指标？

**论点：** 指标数量多不等于业务解释力强。  
**证据：** 模型指标和业务指标无法直接映射。  
**推论：** 需要建立 Agent 层的桥梁指标。  
**方案：** 构建业务层、系统层、Agent 层、模型层的分层体系。

### 母题四：为什么主观评测必须下钻和二元化？

**论点：** 模糊概念无法保证评测一致性。  
**证据：** “口语化”“好不好”等概念容易产生不同理解。  
**推论：** 必须把抽象判断转化为可观察事实。  
**方案：** 指标下钻、Rubric 二元化、持续处理 unknown。

### 母题五：为什么评测体系应从 Good Case 和 Bad Case 演进？

**论点：** 真实问题无法完全预先设计。  
**证据：** 线上失败暴露能力边界，优秀案例定义真实标准。  
**推论：** 评测体系必须由真实数据持续校准。  
**方案：** 通过数据飞轮不断更新样本、规则和回归集。

### 母题六：为什么长程 Agent 需要新的评测基础设施？

**论点：** 多步骤、多工具、动态状态使单次答案评测失效。  
**证据：** 长程任务具有丰富轨迹和真实环境状态。  
**推论：** 必须评测 Task、Trace 和 Outcome。  
**方案：** 建设回放、沙箱、Case 管理、AI Grader、归因、回归和门禁能力。

## 二十二、最终抽象

Agent 评测可以被压缩为一条工程逻辑：

```text
业务目标
  ↓
可执行任务
  ↓
成功标准
  ↓
预期行为
  ↓
完整观测
  ↓
证据化判断
  ↓
问题归因
  ↓
版本回归
  ↓
发布门禁
  ↓
线上反馈
```

其中每一步都解决一个根本问题：

| 环节 | 解决的问题 |
|---|---|
| 业务目标 | 为什么评测 |
| 任务定义 | 评测什么 |
| 成功标准 | 什么叫做好 |
| Expected Behavior | 应该怎么做 |
| Trace | 实际做了什么 |
| Outcome | 最终是否真的完成 |
| Rubric | 如何判断 |
| 归因 | 为什么失败 |
| 回归 | 修改后是否变好 |
| 门禁 | 是否允许上线 |
| 线上反馈 | 如何持续进化 |

因此，成熟的 Agent 评测不是“给 Agent 打分”，而是建立一套能够：

> **看见问题、定义标准、验证结果、解释原因、控制风险、支持回归、驱动迭代的基础设施。**
