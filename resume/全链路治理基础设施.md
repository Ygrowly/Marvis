
### **结论：文章的核心不是介绍一套埋点工具，而是把 GenAI 系统从“零散记录调用日志”升级为“统一语义驱动的全链路治理基础设施”。**

阿里巴巴与蚂蚁在 OpenTelemetry（OTel）GenAI 语义规范之上，补充了 Agent、Skill、Step、Token 级推理等真实生产场景中缺失的观测对象，并通过 GenAI Utils 将规范转化为可复用的工程实现，最终形成从数据采集、链路分析到性能、成本、质量和安全治理的闭环。

## 一、问题定义：为什么传统可观测方式不够用

### 1. GenAI 系统的观测对象发生了变化

传统系统主要观测：

- HTTP 请求
- 数据库调用
- RPC 调用
- 服务延迟
- 错误率

GenAI 系统则新增了大量核心对象：

- Model：调用了哪个模型
- Prompt：输入了什么上下文
- Token：输入、输出和生成过程消耗了多少 Token
- Tool Calling：调用了哪些工具
- Agent：任务由哪个 Agent 执行
- Skill：具体业务能力由谁完成
- Memory：使用了哪些历史记忆
- Session：请求处于哪段会话
- Retrieval、Rerank、Embedding：检索增强链路中的各类操作

这些对象跨越模型、框架、平台和基础设施。如果每个团队自行设计字段和 Span 结构，就会产生三个根本问题：

1. **同一概念无法比较**：模型名、Token 数、响应内容等字段命名和统计口径不一致。
2. **链路无法统一分析**：不同框架产生的 Trace 结构不同，平台难以复用分析能力。
3. **治理无法规模化**：性能、成本、质量和安全分析只能停留在单系统内。

因此，核心矛盾不是“有没有日志”，而是：

> GenAI 系统缺少一套跨业务、跨框架、跨基础设施的统一数据语言。

## 二、核心解法：用语义规范统一数据语言

### 1. What：什么是 GenAI SemConv

OTel Semantic Conventions（SemConv）是一套可观测数据语义规范，用于规定：

- 观测对象是什么
- 字段如何命名
- 数据类型是什么
- Span 如何组织
- Context 如何传递
- Metrics 和 Events 如何记录

例如，GenAI 语义规范统一定义：

- `gen_ai.system`：使用的 GenAI 系统
- `gen_ai.request.model`：请求模型
- `gen_ai.usage.input_tokens`：输入 Token 数
- `gen_ai.usage.output_tokens`：输出 Token 数

它的本质是建立一套标准化的数据词汇和语法，使不同系统产生的数据能够被同一套工具理解。

### 2. Why：为什么语义规范比单一采集工具更重要

自动插桩、SDK 和 Collector 解决的是“如何采集和传输数据”，属于工程实现层。

语义规范解决的是“采集什么、如何定义、如何解释”，属于数据标准层。

可以抽象为：

```text
语义规范：定义数据含义
插桩工具：提取业务数据
SDK/Handler：生成标准遥测数据
Collector：传输和治理数据
观测平台：分析和展示数据
```

如果没有统一规范，即使每个系统都能采集数据，也无法实现集团级比较和治理。

### 3. 统一语义带来的能力

统一语义之后，同一套数据可以支持：

- **技术排查**：通过 Trace ID 查看跨 Agent 的完整执行链路。
- **经营分析**：比较不同业务、模型和功能的成本与效果。
- **持续评测**：从真实用户轨迹中构建评测数据集。
- **合规审计**：形成统一的调用和处理链路。
- **基础设施复用**：复用插桩、看板、告警和分析服务。

因此，语义规范的价值不是增加字段，而是让观测数据具备跨系统复用能力。

## 三、为什么需要 LoongSuite GenAI SemConv

### 1. OTel 的定位与现实边界

OTel 的标准强调：

- 广泛适用
- 长期稳定
- 社区共识
- 谨慎演进

这使得 OTel 适合作为行业通用标准，但也带来一个现实问题：

> 生产场景变化快，而社区标准需要较长时间才能完成讨论、验证和稳定化。

阿里巴巴和蚂蚁拥有大量真实 GenAI 应用，因此遇到了 OTel 尚未覆盖的问题：

- Agent 长流程如何分层展示
- Skill 如何作为业务能力聚合层观测
- 如何定位单个 Token 的性能和精度异常
- 如何让多种插桩库低成本复用同一套实现

### 2. LoongSuite 的定位

LoongSuite 不是要替代 OTel，而是：

> 在 OTel GenAI SemConv 基础上的厂商增强标准，先解决真实生产问题，再逐步向 OTel 上游贡献。

其演进路径是：

```text
真实业务问题
    ↓
抽象为通用观测对象
    ↓
设计语义字段和 Span 模型
    ↓
在集团内部落地验证
    ↓
形成 LoongSuite 扩展标准
    ↓
择机贡献至 OTel 上游
```

这种方式兼顾了两个目标：

- 解决当前业务的实际问题
- 避免形成与行业标准割裂的私有体系

## 四、方案一：Entry Span 与 Step Span

### 1. 问题是什么

长程 Agent 通常包含多轮：

```text
思考 → 工具调用 → 模型调用 → 再思考 → 再调用
```

当任务变长时，一个 Trace 可能包含数百甚至上千个 Span，导致：

- 链路过于冗长
- 难以识别每轮 Agent 行为
- 用户原始请求被 System Prompt 和框架 Prompt 淹没
- 排障时无法快速定位具体出错轮次

### 2. Entry Span 是什么

Entry Span 位于 Agent 调用入口，用来记录：

- 用户最原始的输入
- Agent 最终的输出
- 对话级别的完整边界

它解决的是“用户到底请求了什么、最终得到了什么”。

### 3. 为什么需要 Entry Span

Agent 内部会不断拼接：

- System Prompt
- Framework Prompt
- Tool 描述
- 历史上下文
- 中间推理内容

如果直接观察内部模型调用，原始用户请求可能被大量内部信息干扰。

Entry Span 将“外部请求边界”独立出来，使排障人员能够区分：

```text
用户输入
内部编排过程
模型和工具调用
最终输出
```

因此，Entry Span 的核心价值是还原真实的对话上下文。

### 4. Step Span 是什么

Step Span 表示 Agent 一轮 ReAct 过程的层次化节点。

一轮 Step 通常包含：

```text
反思 → 工具调用 → 模型调用
```

多个 Step 组成完整 Agent Trace：

```text
Entry
 ├── Step 1
 │    ├── Model
 │    └── Tool
 ├── Step 2
 │    ├── Model
 │    └── Tool
 └── Step 3
      └── Model
```

### 5. 为什么采用分层设计

排障通常采用 Top-down 方法：

1. 先判断整个 Agent 是否异常。
2. 再定位第几轮 Step 出错。
3. 最后深入到某个 Model 或 Tool Span。

Step Span 将复杂链路转换为“按轮次组织的执行过程”，降低了认知和排障成本。

### 6. 方案边界

Entry 和 Step 不替代原有 Model、Tool Span，而是增加上层结构：

- Entry：业务请求边界
- Step：Agent 执行轮次
- Model：模型调用细节
- Tool：工具执行细节

它们解决的是不同层级的可观测问题。

## 五、方案二：Skill 语义

### 1. Skill 是什么

Skill 是 Agent 可复用的最小业务能力单元。

例如：

- 搜索商品
- 加入购物车
- 申请退款
- 查询物流
- 生成报告

Skill 通常由多个 Model 调用和 Tool 调用编排而成。

它位于 Agent 和 Tool 之间：

```text
Agent：理解用户意图并编排任务
Skill：完成某类具体业务能力
Tool：执行单个外部动作
```

### 2. 现有 OTel 语义的缺口

OTel 已覆盖：

- Agent
- LLM
- Tool

但如果没有 Skill 维度，平台只能看到：

```text
execute_tool
inference
execute_tool
inference
```

却不知道这些调用属于哪个业务功能。

### 3. Skill 缺失造成的问题

#### 无法归因到功能域

性能异常只能定位到某个 Tool 或模型调用，无法快速判断是：

- 搜索商品功能
- 退款功能
- 推荐功能
- 物流查询功能

#### 无法建立 Skill 级指标

无法稳定统计：

- Skill P99 延迟
- Skill 成功率
- Skill 调用频率
- Skill 版本表现
- Skill 的模型耗时占比

#### 并发场景下链路混淆

多个 Skill 同时执行时，不同 Skill 的 Model 和 Tool Span 混在同一棵 Trace 树中，难以区分归属。

### 4. 如何设计 Skill 语义

LoongSuite 增加 `gen_ai.skill.*` 属性，用于描述：

- Skill 身份
- Skill 名称
- Skill 版本
- Skill 执行相关信息

早期方案将这些属性附加到已有的 `execute_tool` Span 上。

这样做的原因是：

- 不引入新的 Span 类型
- 降低改造成本
- 快速兼容已有插桩
- 先实现 Skill 维度的聚合分析

### 5. 为什么又需要独立的 invoke_skill Span

属性附着方案能够快速落地，但无法完整表示 Skill 生命周期。

Skill 可能包含：

```text
加载
初始化
参数校验
模型调用
工具调用
结果处理
执行完成
```

因此，集团内部进一步采用独立的 `invoke_skill` Span，用于覆盖 Skill 从加载到完成的全过程。

两种方案分别适用于不同阶段：

| 方案 | 优点 | 局限 |
|---|---|---|
| Skill 属性附着在 Tool Span | 改造快、兼容性好 | 无法完整表达 Skill 生命周期 |
| 独立 invoke_skill Span | 结构清晰、可端到端分析 | 需要新增 Span 类型和插桩逻辑 |

这体现了一个重要设计原则：

> 先通过低成本兼容方案获得覆盖，再通过独立抽象完善语义模型。

### 6. Skill 语义带来的分析能力

统一 Skill 语义后，可以直接分析：

- 哪个 Skill 错误率最高
- 新版本 Skill 是否导致延迟上升
- Skill 内部模型调用占总耗时的比例
- 不同业务功能的调用量和资源消耗
- 不同框架对同一 Skill 的执行差异

## 六、方案三：Token 级推理观测

### 1. 为什么请求级 Trace 不够

传统模型观测通常以请求为单位，记录：

- 请求总耗时
- 首 Token 延迟
- 平均 Token 输出时间
- 输入和输出 Token 数
- 请求成功或失败

但很多生产问题发生在请求内部：

- 某一个 Token 生成异常慢
- 并发请求之间产生资源干扰
- 某个 Token 开始出现乱码或复读
- 某个异常 Token 造成后续答案整体偏离

因此，请求级观测只能回答：

> 哪个请求慢或错了？

却无法回答：

> 请求内部的哪一个 Token 出现问题？为什么出现问题？

### 2. 推理引擎的基本机理

推理引擎本质上是一个循环调度系统：

```text
选择一批请求组成 Batch
        ↓
执行一次迭代
        ↓
每个请求生成一个 Token
        ↓
进入下一轮迭代
```

每个 Token 的生成时间受到以下因素影响：

- 调度等待时间
- 实际执行时间
- 当前 Batch 负载
- 同一实例中的其他请求
- Prefill 与 Decode 的资源竞争
- 引擎调度策略

因此，Token 是理解推理性能的最小关键单位。

### 3. Token 性能数据如何采集

对每个请求的每个 Token，采集：

- 进入迭代时间
- 退出迭代时间
- 所属 Batch
- Batch 请求数
- Batch Token 数
- 调度相关时间
- 执行相关时间
- 用户感知的总耗时

这些数据可以推导：

- 哪个 Token 最慢
- 慢在调度还是执行
- 慢 Token 产生时 Batch 有多大
- 是否存在跨请求资源竞争
- 并发请求是否相互影响

### 4. Token 精度数据如何采集

对每个 Token 记录：

- Top-K 候选 Token
- 每个候选 Token 的概率
- 最终选中的 Token
- 采样相关信息

这些数据用于区分不同类型的问题：

#### 模型输出本身异常

如果预期 Token 在候选分布中就不合理，问题可能来自：

- 模型能力
- 模型训练数据
- 模型版本
- 推理状态异常

#### 采样参数异常

如果预期 Token 具有较高概率，但最终选中的 Token 不在合理范围内，问题可能来自：

- 温度
- Top-K
- Top-P
- 其他采样参数

因此，Top-K 分布将“模型问题”和“采样配置问题”区分开来。

## 七、Token 观测的两个典型排障逻辑

### 1. 慢 Token：从现象到根因

观测现象：

```text
第 125 个 Token 耗时 6.8 秒
TPOT 达到 54.77 ms
```

排查过程：

```text
异常请求 Trace
    ↓
定位慢 Token
    ↓
查看同一推理实例的并发情况
    ↓
发现其他请求的 Prefill 阶段占用资源
    ↓
中断当前请求的 Decode
    ↓
定位为跨请求资源干扰
```

根因是：

> 其他租户请求的 Prefill 阶段影响了当前请求的 Decode 阶段。

可能的优化方向是：

> 进行 Prefill 和 Decode 分离，即 PD 分离，降低两类任务之间的资源干扰。

这个案例说明，Token 分析回答“哪个 Token 慢”，引擎并发分析回答“为什么慢”。

### 2. 答非所问：从异常 Token 定位模型问题

观测现象：

- 用户询问医疗问题
- 模型却输出了与问题无关的代码答案
- 普通日志中看不到明显异常

Token 级分析发现：

```text
首 Token = begin_of_sentence（BOS）
```

BOS 是用于分隔无关语料的特殊 Token。正常回答中不应出现该 Token。

排查链路：

```text
错误回答
    ↓
定位首个异常 Token
    ↓
发现 BOS
    ↓
判断后续输出与原 Prompt 失去关联
    ↓
进一步确认属于模型 badcase
    ↓
调整模型或等待模型版本优化
```

该案例说明，Token 级数据可以发现普通响应文本和日志中隐藏的特殊 Token 问题。

## 八、方案四：GenAI Utils 工程化封装

### 1. 为什么需要公共工具层

如果每个框架插桩库独立实现遥测逻辑，就需要重复处理：

- 创建 Span
- 设置 SpanKind
- 写入属性
- 记录 Metrics
- 发送 Events
- 传递 Context
- 处理异常
- 控制消息内容采集
- 跟随语义规范升级

这些代码在不同插桩库中高度重复，产生两个问题：

1. **重复开发和维护**
2. **规范升级成本随插桩数量线性甚至倍增**

### 2. GenAI Utils 的职责

GenAI Utils 将规范实现集中起来，提供：

- Invocation 数据类
- Context Manager
- Span 创建与结束
- 属性挂载
- Metrics 记录
- Event 发送
- Context 管理
- 异常处理
- 消息内容采集控制

其目标是把插桩开发从：

```text
提取数据 + 设计遥测结构 + 操作 OTel API
```

简化为：

```text
只提取框架中的业务数据
```

### 3. 核心架构

```text
GenAI 框架
    ↓
框架插桩层
    └── Hook / Monkey-Patch
    └── 提取业务数据
    └── 填充 Invocation 对象
            ↓
GenAI Utils
    └── ExtendedTelemetryHandler
    └── 创建 Span
    └── 设置属性
    └── 记录 Metrics
    └── 发送 Events
    └── 管理 Context
            ↓
OTel SDK / Collector
            ↓
可观测平台
```

### 4. 为什么采用 Invocation 数据对象

Invocation 对象承担“业务数据”和“遥测输出”的解耦作用。

插桩库只负责描述：

```text
这次调用是什么
调用了谁
输入输出是什么
消耗了多少 Token
是否发生错误
```

Handler 负责决定：

```text
如何创建 Span
如何命名字段
如何设置状态
如何记录指标
如何输出事件
```

这种设计将框架差异隔离在插桩层，将规范一致性集中在工具层。

### 5. 为什么采用 Handler 单例

统一 Handler 可以保证：

- 所有插桩使用同一套输出逻辑
- 配置和行为保持一致
- 避免不同库重复初始化
- 规范升级只修改一个位置

### 6. 为什么使用 Context Manager

Context Manager 可以统一管理调用生命周期：

```text
进入上下文
    ↓
创建 Span
    ↓
执行实际调用
    ↓
记录结果或异常
    ↓
结束 Span
```

如果调用失败，Handler 可以自动：

- 捕获异常
- 设置错误状态
- 写入 `error.type`
- 结束 Span
- 记录相关指标

插桩开发者不需要反复编写样板代码。

## 九、从第一性原理看整体设计

可以从“观测系统必须回答什么问题”反推方案。

### 1. 观测的基本目标

一个可观测系统至少需要回答四类问题：

| 问题 | 对应设计 |
|---|---|
| 发生了什么 | Entry、Agent、Skill、Model、Tool Span |
| 在哪里发生 | Trace、Step、层级化 Span |
| 为什么发生 | Token 时间、Batch、并发、Top-K 分布 |
| 如何持续治理 | 统一语义、Metrics、平台聚合、版本分析 |

### 2. 从宏观到微观的观测层次

```text
业务请求
    ↓
Agent 执行
    ↓
Step/ReAct 轮次
    ↓
Skill 业务能力
    ↓
Model/Tool 调用
    ↓
推理请求
    ↓
Token 生成
    ↓
Token 候选概率
```

不同层级承担不同职责：

- **业务层**：用户请求是否完成
- **编排层**：Agent 如何执行
- **能力层**：哪个 Skill 出现问题
- **调用层**：哪个模型或工具异常
- **引擎层**：哪个 Token 慢或错
- **概率层**：模型输出还是采样参数导致问题

### 3. 统一语义是系统复用的前提

只有数据结构统一，才能复用：

```text
采集逻辑
    ↓
传输链路
    ↓
存储模型
    ↓
查询语句
    ↓
指标体系
    ↓
看板
    ↓
告警
    ↓
评测与治理
```

因此，LoongSuite 的根本设计不是增加更多观测维度，而是将这些维度纳入同一套数据模型。

## 十、该方案的边界与代价

### 1. 数据量显著增加

Token 级观测会产生远高于请求级观测的数据量，尤其是：

- 长文本输出
- 高并发推理
- Top-K 概率分布
- 多轮 Agent 执行

因此必须考虑：

- 采样策略
- 动态开关
- 数据保留周期
- 敏感内容脱敏
- 高价值请求优先采集

### 2. 内容采集存在隐私与合规问题

Prompt、响应、Memory 和 Token 内容可能包含：

- 用户隐私
- 业务机密
- 个人信息
- 敏感业务数据

所以观测系统不能默认采集所有原文，而应支持：

- 内容采集配置
- 脱敏
- 权限控制
- 分级存储
- 审计记录

### 3. 标准仍处于演进过程

LoongSuite 是厂商增强标准，部分能力尚未进入 OTel 稳定规范。因此需要注意：

- 字段可能变化
- Span 类型可能调整
- 上下游工具兼容性需要验证
- 长期使用应保留迁移能力

### 4. Token 级数据不等于完整质量评估

Token 概率可以帮助定位：

- 异常 Token
- 采样问题
- 生成路径异常

但它不能单独判断：

- 回答是否符合业务目标
- 是否真正解决用户问题
- 是否存在事实错误
- 是否满足安全和合规要求

这些仍需要结合：

- 评测数据集
- 规则检查
- 人工标注
- 模型评审
- 业务结果指标

## 十一、文章背后的证据闭环

文章的论证结构可以归纳为：

```text
生产问题
    ↓
传统请求级观测无法解释
    ↓
识别缺失的观测对象
    ↓
建立新的语义模型
    ↓
通过统一工具实现采集
    ↓
在真实 Agent 和推理引擎中落地
    ↓
通过案例验证排障效率和根因解释能力
```

具体证据包括：

- Agent Trace 过长：引出 Entry/Step Span
- Tool 和 Model 无法归因到业务功能：引出 Skill 语义
- 请求级数据无法解释慢 Token：引出 Token 性能观测
- 日志无法发现 BOS 异常：引出 Token 精度观测
- 插桩重复实现成本高：引出 GenAI Utils
- 集团多业务接入需求：证明统一语义和公共工具层的必要性

这不是单纯的功能罗列，而是按照：

```text
问题 → 抽象 → 设计 → 工程化 → 落地 → 验证
```

逐层建立方案合理性。

## 十二、可迁移的方法论

### 1. 先定义观测对象，再设计采集方式

不要先问“应该埋哪些字段”，而应先问：

- 系统由哪些核心对象组成？
- 每个对象承担什么职责？
- 运维需要回答哪些问题？
- 哪些对象具有独立生命周期？
- 哪些对象需要独立聚合分析？

### 2. 用层级结构解决复杂系统可读性

当链路变复杂时，不应简单增加更多 Span，而应建立层级：

```text
请求 → 任务 → 轮次 → 能力 → 调用 → 微观执行单元
```

层级化结构可以同时满足：

- 宏观概览
- 中观定位
- 微观分析

### 3. 先兼容落地，再完善独立抽象

Skill 的演进说明：

1. 先把 Skill 属性挂到已有 Span 上，快速获得覆盖。
2. 再建立独立 Span，完整表达生命周期。
3. 最终推动上游标准化。

这是一种兼顾速度和长期正确性的演进策略。

### 4. 把规范实现集中到公共层

插桩层应该只负责：

```text
识别调用
提取数据
填充对象
```

公共工具层负责：

```text
统一输出
统一状态
统一指标
统一异常处理
统一规范升级
```

这样可以避免规范碎片化。

### 5. 从请求级指标下沉到最小可解释单元

当请求级观测只能发现异常、不能解释异常时，应继续向下拆分：

```text
请求 → 阶段 → 迭代 → Token → 候选概率
```

但下沉必须以问题定位价值为前提，否则会造成数据量和成本失控。

## 十三、最终模型

整篇文章可以压缩成一个完整模型：

```text
统一语义规范
    ↓
统一观测对象
    ├── Entry / Step：还原 Agent 执行结构
    ├── Skill：建立业务功能归因
    ├── Token 性能：定位微观延迟
    ├── Token 精度：解释异常输出
    └── Invocation / Handler：统一工程实现
            ↓
统一采集与传输链路
            ↓
统一平台分析
            ↓
性能、成本、质量、安全和合规治理
```

其最终目标是让 GenAI 系统具备四种能力：

- **可看见**：知道系统发生了什么。
- **可分析**：知道问题发生在哪里。
- **可归因**：知道问题为什么发生。
- **可治理**：能够持续优化和规模化管理。
