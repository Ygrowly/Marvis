### **结论：这篇文章的核心不是“让 Claude 更聪明”，而是把数仓 AI 开发从依赖模型记忆的对话模式，改造成由持久化上下文、确定性校验和上下文隔离共同支撑的工程化流水线。**

其基本分工是：

- **LLM**：理解需求、进行业务判断、设计方案、生成代码。
- **持久化文件与 Memory**：保存不会随会话压缩而丢失的业务语义和迭代约束。
- **Hooks**：强制执行规范、安全检查和任务完整性校验。
- **Subagents**：隔离高 token 操作，避免主上下文膨胀。
- **SKILL**：将重复流程、规范和产出格式标准化。

---

## 一、从第一性原理看：问题究竟是什么

### 1. 问题定义：AI 数仓开发为何不稳定

数仓 AI 开发的核心问题并不是 SQL 生成能力不足，而是以下三类不确定性叠加：

1. **语义不确定性**：AI 不理解或遗忘字段口径、业务定义和迭代约束。
2. **执行不确定性**：规范是否执行依赖人工或模型记忆。
3. **上下文不确定性**：复杂任务产生大量血缘、DDL、自测结果，导致上下文压缩和信息丢失。

因此，错误来源可以抽象为：

$$
开发错误 = 语义偏差 + 规范遗漏 + 上下文损失
$$

传统方式把三类问题都交给 LLM 记忆和判断，可靠性自然不稳定。

---

### 2. 核心矛盾：复杂任务越需要 AI，越容易让 AI 失效

复杂数仓任务通常包含：

- 多层上下游血缘；
- 大量表结构和字段信息；
- 多条自测 SQL；
- 多轮需求澄清；
- 多个 SKILL 文件；
- 多次代码修改和验证。

这些内容会持续占用 context。接近上限后，系统触发 compact，将完整对话替换成摘要。

问题在于，摘要通常保留“发生了什么”，但不一定保留：

- 临时业务约束；
- 字段单位；
- 特定版本决策；
- 被暂时忽略的字段；
- 已确认和未确认的问题；
- SKILL 执行到哪一步。

所以，系统出现一种结构性悖论：

> 任务越复杂，越需要上下文；上下文越复杂，越容易被压缩；越被压缩，AI 越容易遗忘关键约束。

---

## 二、Harness 是什么：定义、机理与边界

### 1. 定义

Harness 可以理解为：

> 位于 LLM 推理循环之外，负责管理上下文、执行自动化规则、协调子任务的宿主工程框架。

它不是另一个模型，也不是简单的提示词集合，而是一个由客户端、配置、Hooks、Subagents、持久化文件共同组成的控制层。

### 2. 解决的问题

Harness 主要解决四件事：

| 机制 | 主要问题 | 核心能力 |
|---|---|---|
| CLAUDE.md / Memory | 失忆 | 持久化业务语义和迭代状态 |
| Hooks | 规范靠记忆 | 确定性检查与阻断 |
| Subagents | Context 膨胀 | 独立上下文执行高 token 任务 |
| SKILL | 流程不统一 | 固化步骤、规范和产出格式 |

### 3. 不解决的问题

Harness 不能替代业务判断，也不能自动解决需求本身的歧义。

它不能保证：

- 需求定义一定正确；
- 字段口径一定已经确认；
- AI 一定理解业务目标；
- 数据结果一定符合真实业务；
- 错误输入不会被持久化。

因此，Harness 的边界是：

> 它主要保证“已经明确的规则被稳定执行”，而不是替代人完成“规则应该是什么”的判断。

---

## 三、核心机理：如何解决 compact 导致的信息丢失

### 1. 不可靠信息与可靠信息

对话中的信息可以分为两类：

#### 临时信息

例如：

- “这次使用 OVERWRITE 模式。”
- “先不要处理 field_a。”
- “amount 单位是千元。”

这些信息只存在于对话历史中，容易在 compact 后消失。

#### 持久化信息

例如写入：

- `.claude/CLAUDE.md`；
- `MEMORY.md`；
- `.claude/context/dw_conventions.md`；
- 项目配置和规则文件。

这些信息存储在磁盘中，可以在新会话或 compact 后重新注入。

### 2. 持久化设计原则

应当把信息按生命周期分类：

| 信息类型 | 保存位置 | 生命周期 |
|---|---|---|
| 全局数仓规范 | CLAUDE.md / conventions 文件 | 长期 |
| 当前迭代约束 | CLAUDE.md | 单次迭代 |
| 跨项目经验 | Auto Memory | 跨会话 |
| 当前技术决策 | CLAUDE.md | 当前需求 |
| 过程性查询结果 | Subagent context | 单次任务 |
| 自动检查规则 | Hooks | 长期 |

### 3. 为什么不能把所有内容都写进 CLAUDE.md

因为持久化本身也会增加上下文消耗。

因此应遵循：

> 持久化“决策和约束”，不要持久化“原始过程数据”。

适合写入：

- 字段业务口径；
- 金额单位；
- 当前版本；
- 禁止修改的表；
- 已确认的技术决策；
- 历史踩坑。

不适合写入：

- 完整血缘列表；
- 全量 DDL；
- 23 条 SQL 的执行结果；
- 大段原始查询输出；
- 可重复生成的过程数据。

---

## 四、五层防御体系：从弱约束到强约束

这五层不是互相替代，而是逐层加强。

![[Pasted image 20260808152158.png]]

### 第一层：CLAUDE.md——持久化当前状态

#### What

在项目根目录维护项目级上下文。

#### Why

对话中的临时约束会丢失，而文件内容可以在会话启动和 compact 后重新注入。

#### How

建议划分为三类内容：

```text
# 全局规范
- 金额字段使用 DECIMAL(26,4)
- 分区字段使用 partition_dt STRING
- 禁止 SELECT *

# 当前迭代
- 正在开发：db_a.dws_table_a
- 当前版本：V1.0

# 本次约束
- amount 单位为千元
- 使用 INSERT OVERWRITE
- 暂不处理 field_a
```

迭代完成后清理临时约束，避免旧信息污染新任务。

#### 边界

CLAUDE.md 不应变成完整项目百科，否则会增加每次会话的基础 token 消耗。文章建议全局规范控制在约 100 行以内。

---

### 第二层：Auto Memory——积累跨会话经验

#### What

让 AI 自动或主动记录跨会话有效的信息。

#### Why

某些信息不是单次迭代约束，而是长期经验，例如：

- 某字段在特殊场景下为空；
- 某张表存在历史数据问题；
- 某业务指标容易被误解；
- 某类任务曾经出现过错误。

#### How

通过明确表达触发记忆，例如：

```text
请记住：这张表的 amount 字段单位是千元。
请记住：field_a 在特定场景下可能为空。
```

#### 边界

Memory 适合保存经验，不适合替代正式规范和强制校验。因为 Memory 仍然属于模型可读取的信息，不具备 Hook 的阻断能力。

---

### 第三层：Hooks——把规范从“建议”变成“强制规则”

这是整套方案中最关键的防御层。

#### What

Hooks 是在特定事件发生时自动执行的脚本或检查逻辑。

#### Why

规范如果依赖模型记忆，就会出现：

- 忘记检查；
- 检查不完整；
- compact 后规范丢失；
- 生成代码后没有复核。

Hooks 不依赖模型是否记得，而是在动作发生时自动执行。

#### How

典型事件包括：

- `PostToolUse`：写入或修改 SQL 后自动检查；
- `PreToolUse`：执行危险命令前拦截；
- `SessionStart`：会话开始或 compact 后重新注入规范；
- `Stop`：检查任务是否完成。

核心流程是：

```text
写入 SQL
   ↓
PostToolUse Hook
   ↓
检查规范
   ↓
通过：继续
失败：exit 2 阻断
   ↓
Claude 修正 SQL
```

可检查的规则包括：

- 是否使用 `SELECT *`；
- 是否带 `PARTITION`；
- 是否符合字段类型规范；
- 是否使用正确的 INSERT 模式；
- 是否存在跨库 JOIN；
- 是否违反命名规范；
- 是否包含危险 DDL。

#### 为什么必须使用 exit 2

文章强调，阻断 Hook 必须使用 `exit 2`。使用 `exit 1` 可能无法阻止 Claude 继续执行。

这体现了一个关键原则：

> 只有真正改变执行路径的检查，才是护栏；仅返回提示的检查仍然只是建议。

#### 边界

Hooks 擅长验证形式化规则，不擅长判断开放式业务语义。

例如：

- “是否带分区”适合 Hook；
- “GMV 是否符合业务定义”通常需要人和 AI 共同判断；
- “这个字段是否应该参与计算”不能只靠正则表达式。

---

### 第四层：Subagents——隔离高 token 任务

#### What

Subagent 是拥有独立上下文的子代理，用于执行具体、耗时或数据量大的任务。

#### Why

如果把所有过程数据都返回主对话，会造成 context 膨胀。例如：

- 血缘查询：500～3000 tokens；
- 多层 DDL；
- 23 项自测结果；
- 两张表的大量样本数据；
- 多轮 SQL 验证日志。

主会话通常不需要这些原始内容，只需要结论。

#### How

采用“过程隔离、结论回传”：

```text
主会话：提出任务
   ↓
Subagent：读取数据、执行查询、完成分析
   ↓
Subagent：只返回摘要
   ↓
主会话：继续决策
```

适合拆出的子任务：

- `sql-validator`：SQL 规范和语法验证；
- `dw-explorer`：表结构、DDL、上下游血缘查询；
- `data-quality-checker`：标准自测；
- `data-comparator`：数据比对；
- 性能分析和大规模结果处理。

#### 返回结果应当是什么

不要返回：

- 全量查询结果；
- 全部血缘节点；
- 全部 SQL 日志；
- 大段 DDL。

应返回：

```text
状态：PASS / FAIL
问题数量：3
关键问题：
1. 缺少 PARTITION
2. 使用了 SELECT *
3. amount 类型不符合规范

建议：修正后重新验证
```

#### 边界

Subagent 适合“数据量大但结论相对明确”的任务，不适合把需要连续业务决策的核心流程完全隔离，否则主会话会失去必要上下文。

---

### 第五层：SKILL——把经验封装成标准能力

#### What

SKILL 是对某类任务的规范、步骤、输入、输出和工具调用方式的封装。

#### Why

如果每次都依赖人工提示，会出现：

- 遗漏步骤；
- 产出格式不统一；
- 不同开发者执行方式不同；
- 相同规则重复输入；
- 过程难以复用。

SKILL 的本质是把“反复讲解的流程”变成标准化入口。

#### How

以 `/dw-etl` 为例，可以封装：

- 建表规范；
- 字段类型规范；
- 分区规范；
- INSERT 模式；
- 禁止事项；
- 输出文件路径；
- 自动验证步骤；
- 失败后的修正流程。

调用过程为：

```text
/dw-etl
   ↓
读取 ETL 规范
   ↓
生成 DDL 和 INSERT SQL
   ↓
触发 SQL Hook
   ↓
调用 sql-validator
   ↓
返回文件路径和验证摘要
```

#### SKILL 的改造方向

文章指出，直接加载完整 SKILL 文件会消耗主上下文。因此建议：

- 由 Subagent 读取完整 SKILL；
- 主会话只接收最终产物；
- 规范章节可拆为按路径加载的规则；
- 主会话只保留决策级结果。

---

## 五、整体架构：为什么要职责分层

整体架构可以抽象为四层：

```text
业务与技术决策
        ↓
LLM 主会话
        ↓
┌──────────────┬──────────────┬──────────────┐
│ 持久化层      │ Harness 层    │ Subagent 层   │
│ CLAUDE.md    │ Hooks         │ 独立 Context  │
│ Memory       │ 强制校验       │ 高 token 任务 │
└──────────────┴──────────────┴──────────────┘
        ↓
SQL、配置、测试结果和交付物
```

### 1. 持久化层

解决：

> 关键约束是否会丢失？

### 2. Harness 层

解决：

> 规范是否一定执行？

### 3. Subagent 层

解决：

> 过程数据是否会撑爆主上下文？

### 4. LLM 层

解决：

> 需求是否被理解？方案是否合理？代码是否正确？

这四层不能混用：

- 用 CLAUDE.md 不能替代 Hook；
- 用 Hook 不能替代业务判断；
- 用 Subagent 不能替代主会话决策；
- 用 SKILL 不能替代真实数据验证。

---

## 六、数仓八步工作流：What、Why、How

![[Pasted image 20260808152222.png]]

### Step 1：需求分析

#### 目标

明确业务指标、统计范围、粒度、口径和待确认问题。

#### Why

需求理解偏差是数仓返工的主要来源之一。AI 最大的风险不是不会写 SQL，而是理解错了“要计算什么”。

#### How

- 读取 PRD；
- 查询上游表结构；
- 用 `dw-explorer` 返回摘要；
- 输出口径草稿；
- 列出待确认问题；
- 将已确认约束写入 CLAUDE.md。

输出应包括：

```text
业务目标：
统计粒度：
时间范围：
核心指标：
字段口径：
待确认问题：
```

---

### Step 2：技术设计

#### 目标

将业务需求转成可执行的数据模型和处理方案。

#### How

明确：

- 目标表粒度；
- 上游表和字段；
- 主键；
- 分区；
- 字段类型；
- 数据加工逻辑；
- 增量或全量模式；
- 异常数据处理方式；
- 性能约束。

设计完成后，把关键决策写入当前迭代状态，避免后续被 compact 丢失。

---

### Step 3：ETL 开发

这是 Harness 价值最高的步骤。

#### 目标

生成建表 DDL 和 INSERT SQL。

#### 文章中的关键约束

- 分区字段使用 `partition_dt STRING`；
- 金额字段使用 `DECIMAL(26,4)`；
- 必须使用 `INSERT OVERWRITE`；
- 必须带 `PARTITION`；
- 禁止 `SELECT *`；
- 非血缘关系不允许跨库 JOIN。

#### How

```text
读取 ETL SKILL
   ↓
生成 DDL 和 INSERT SQL
   ↓
保存文件
   ↓
PostToolUse 自动校验
   ↓
失败则 exit 2
   ↓
Claude 修正
   ↓
sql-validator 再验证
```

这里的关键改进是：

> “生成后检查”由人工动作改成系统事件。

---

### Step 4：自测

#### 目标

验证数据完整性、准确性和基本质量。

#### Why

自测通常包含大量 SQL 和结果，直接放入主会话会快速消耗 context。

#### How

将 23 项标准自测交给 `data-quality-checker`，主会话只接收：

- PASS / FAIL；
- 失败规则；
- 失败字段；
- 样例异常；
- 修复建议。

---

### Step 5：数据比对

#### 目标

将新结果与旧表、基准表或业务数据进行差异分析。

#### How

由 `data-comparator` 执行：

- 行数对比；
- 指标对比；
- 字段级差异；
- 空值率变化；
- 分布变化；
- 异常样本提取。

主会话只获取差异摘要，而不是全部样本数据。

---

### Step 6：SR 数据库导入

#### 目标

生成或执行标准化的数据服务、存储或建表任务。

#### How

- 查询相关表 DDL；
- 查询一层上下游血缘；
- 仅返回摘要；
- 根据 `dw-sr` SKILL 生成任务；
- 验证建表参数和字段映射。

---

### Step 7：性能优化

#### 目标

降低执行成本、延迟和资源消耗。

#### How

先由 `dw-explorer` 查询：

- 一层上下游血缘；
- 相关 DDL；
- 分区设计；
- JOIN 关系；
- 数据规模；
- 下游依赖。

再分析：

- 是否存在全表扫描；
- 分区是否有效；
- JOIN 是否可裁剪；
- 是否存在重复计算；
- 是否需要中间层或预聚合；
- 是否需要调整字段类型或存储方式。

---

### Step 8：SLA / DQC

#### 目标

将数据质量要求和交付时效转化为可执行规则。

#### How

按规范生成九类 DQC 规则，例如围绕：

- 行数；
- 空值；
- 唯一性；
- 主键；
- 枚举值；
- 波动；
- 及时性；
- 分区；
- 业务逻辑一致性。

这一步适合保留在主会话中生成规则，但具体执行结果可以交给 Subagent。

---

## 七、母题驱动的证据闭环

这篇文章可以围绕四个母题理解，而不是机械记忆八个章节。

### 母题一：为什么 AI 会“失忆”？

#### 证据

- context 接近上限时触发 compact；
- 历史对话被替换成摘要；
- 临时约束可能不再出现在摘要中。

#### 结论

不能把关键约束只放在对话里。

#### 方案

- CLAUDE.md；
- Auto Memory；
- SessionStart 重新注入；
- 当前迭代状态文件化。

---

### 母题二：为什么规范不能只写在提示词里？

#### 证据

- 人工执行规范不稳定；
- AI 依赖记忆；
- compact 后规范可能丢失；
- “提醒模型检查”不能保证每次执行。

#### 结论

规范必须从指导性知识变成确定性控制。

#### 方案

- PostToolUse 自动校验；
- PreToolUse 危险操作拦截；
- 失败使用 exit 2；
- 通过后才允许继续。

---

### 母题三：为什么复杂任务需要 Subagent？

#### 证据

- 血缘、DDL、自测和样本结果 token 数量大；
- 主会话真正需要的是决策信息，而不是全部过程数据；
- 过程数据越多，compact 越频繁。

#### 结论

应当把“数据处理上下文”和“决策上下文”分离。

#### 方案

- Subagent 独立读取和分析；
- 主会话只接收摘要；
- 采用 PASS/FAIL、问题列表和文件路径等结构化输出。

---

### 母题四：为什么需要 SKILL？

![[Pasted image 20260808152245.png]]

#### 证据

- 相同工作重复出现；
- 不同人执行方式不同；
- 流程步骤和产出格式容易遗漏；
- 规范需要反复输入。

#### 结论

重复知识应被封装为可调用能力。

#### 方案

- 将规范写入 SKILL；
- 将执行步骤标准化；
- 将输出格式固定化；
- 将 Hook 和 Subagent 接入 SKILL 流程。

---

## 八、方案改进的本质：从“记忆型控制”转向“机制型控制”

### 1. 传统方式

```text
人告诉 AI 规则
   ↓
AI 记住规则
   ↓
AI 生成代码
   ↓
人提醒 AI 检查
```

问题是每一步都依赖记忆。

### 2. Harness 方式

```text
规则写入文件
   ↓
流程写入 SKILL
   ↓
代码写入时自动触发 Hook
   ↓
大数据操作交给 Subagent
   ↓
结果摘要回到主会话
   ↓
关键状态持续写入文件
```

### 3. 改进后的控制对象

| 传统依赖 | 工程化替代 |
|---|---|
| 依赖 AI 记住约束 | 文件持久化 |
| 依赖 AI 主动检查 | Hook 自动触发 |
| 依赖主会话承载所有数据 | Subagent 隔离 |
| 依赖个人经验 | SKILL 标准化 |
| 依赖人工发现危险操作 | PreToolUse 拦截 |
| 依赖人工判断任务是否结束 | Stop Hook 检查 |

## 九、准确率公式：语义 × 规范

文章给出的核心抽象是：

$$
准确率 = 语义理解深度 \times 数据规范覆盖度
$$

这个公式可以进一步解释为：

- **语义理解深度**决定“做什么、为什么做、口径是什么”；
- **规范覆盖度**决定“怎么稳定、合规、可重复地做”。

如果任一项接近零，最终准确率都会显著下降。

例如：

- 业务口径完全理解，但 SQL 缺分区：结果不可交付；
- SQL 规范完全正确，但 GMV 口径理解错误：结果仍然错误。

因此 Harness 的作用不是单纯提升代码生成能力，而是稳定公式中的第二个变量，并通过持久化机制辅助第一个变量。

## 十、工程设计原则

### 原则一：决策持久化，过程隔离

持久化：

- 业务口径；
- 技术决策；
- 当前约束；
- 历史经验。

隔离：

- 原始血缘；
- 大量 SQL 结果；
- 样本数据；
- 全量 DDL；
- 执行日志。

---

### 原则二：能确定性验证的，不交给模型记忆

适合自动化的规则：

- 文件格式；
- SQL 关键字；
- 分区要求；
- 字段类型；
- 禁止操作；
- 命名规则；
- 输出文件是否存在。

不适合完全自动化的判断：

- 业务口径；
- 需求是否合理；
- 指标定义；
- 异常是否符合业务；
- 方案是否满足真实目标。

---

### 原则三：主会话只承载决策信息

主会话应保留：

- 当前目标；
- 关键约束；
- 技术决策；
- 风险；
- PASS / FAIL；
- 差异摘要；
- 下一步动作。

主会话不应长期承载：

- 大段执行日志；
- 全量血缘；
- 大量数据样本；
- 重复的规范原文；
- 可重新查询的中间结果。

---

### 原则四：失败必须改变流程

“发现问题并输出提示”不等于“阻止错误继续传播”。

有效护栏必须满足：

```text
检测失败
   ↓
阻断后续动作
   ↓
要求修复
   ↓
重新验证
```

否则检查只是报告，不是控制机制。

---

### 原则五：规则按生命周期管理

- 全局规则长期保留；
- 迭代约束随需求更新；
- 上线后清除临时约束；
- 经验进入 Memory；
- 过程结果不长期保存。

这样可以避免旧需求信息干扰新需求。

---

## 十一、落地实施顺序

### 第一步：先建立持久化上下文

创建：

```text
.claude/CLAUDE.md
.claude/context/dw_conventions.md
```

先固化：

- 项目规范；
- 当前迭代；
- 字段口径；
- 重要技术决策；
- 禁止修改对象。

这是成本最低、收益最直接的一步。

### 第二步：配置自动校验

创建：

```text
.claude/settings.json
.claude/hooks/validate_sql.sh
.claude/hooks/block_dangerous_ddl.sh
```

优先实现：

- SQL 写入后的规范检查；
- 危险 DDL 拦截；
- compact 后重新注入规范。

### 第三步：隔离高 token 操作

优先创建：

```text
.claude/agents/sql-validator.md
.claude/agents/dw-explorer.md
.claude/agents/data-quality-checker.md
```

优先迁移：

- 血缘查询；
- DDL 查询；
- 自测；
- 数据比对；
- 大量 SQL 验证。

### 第四步：将流程封装为 SKILL

最后再将成熟流程标准化为：

```text
/dw-requirement
/dw-design
/dw-etl
/dw-test
/dw-compare
/dw-sr
/dw-optimize
/dw-dqc
```

原因是：如果底层规则和 Hook 尚未稳定，过早封装 SKILL，只会把不成熟的流程固化下来。

---

## 十二、最终抽象

这套方案可以压缩成一个工程闭环：

```text
明确语义
   ↓
持久化约束
   ↓
标准化流程
   ↓
生成代码
   ↓
Hook 强制校验
   ↓
Subagent 执行高 token 任务
   ↓
返回结构化结论
   ↓
更新迭代状态
   ↓
交付与持续积累
```

其本质是把不同类型的问题交给不同机制：

| 问题 | 最适合的机制 |
|---|---|
| 不知道业务含义 | 人与 LLM 共同澄清 |
| 容易忘记字段口径 | CLAUDE.md / Memory |
| 容易违反 SQL 规范 | Hooks |
| 查询结果过大 | Subagents |
| 流程重复且易漏步骤 | SKILL |
| 任务是否完成不确定 | Stop Hook |
| 危险操作风险 | PreToolUse Hook |

最终目标不是让 AI 在所有事情上都自主判断，而是建立一种更可靠的协作边界：

> **让模型负责需要理解和推理的部分，让工程机制负责需要稳定、重复和强制执行的部分。**

这就是从“AI 帮我写 SQL”到“AI 嵌入数仓研发流水线”的根本变化。
