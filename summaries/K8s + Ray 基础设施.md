### **结论：本文的核心不是“Ray 替代 K8s”，而是通过 K8s、KubeRay 与 Ray 的分层协同，把 AI Workload 的调度从“节点级、静态、粗粒度”推进到“进程级、动态、可恢复、可编排”。**

其基本范式是：

```text
K8s：管理物理算力与 Pod
KubeRay：把 K8s 资源组织成 Ray 集群
Ray：管理进程级计算单元与 AI 任务流
上层框架：执行训练、推理、数据处理和 Agent 业务
```

本文可以归纳为一条完整因果链：

```text
AI Workload 复杂化
→ 固定计算范式失配
→ 需要异构、动态、高容错、跨角色编排
→ Ray 提供进程级通用调度
→ K8s 提供企业级基础设施
→ KubeRay 连接两者
→ 超大规模场景进一步要求跨集群联邦与跨层闭环
```

---

## **一、从第一性原理看：调度究竟要解决什么问题**

### **1. 调度问题的本质**

任何分布式计算系统都可以还原为四个基本问题：

1. **计算单元是什么**
2. **计算单元需要什么资源**
3. **计算单元如何协作**
4. **计算单元失败后如何恢复**

传统系统往往先固定计算范式，再设计调度机制。例如：

- Spark 以批处理 Stage 为基本单位；
- Flink 以流式算子和 Slot 为基本单位；
- PyTorch 分布式训练以同构进程组为基本单位。

而大模型时代的任务具有更高的不确定性：

- 任务由 CPU、GPU、网络、存储等不同资源共同组成；
- 不同阶段的资源需求不同；
- 训练、推理、评估、奖励计算等角色并不对称；
- 任务运行中的负载和瓶颈会变化；
- GPU 故障、OOM、Spot 回收等问题难以避免；
- 任务流可能包含复杂的多播、异步调用和动态扩展。

因此，调度系统不能只回答“把任务放到哪台机器”，还要回答：

> 如何让不同类型的计算单元，在变化的资源环境中协作运行，并在局部故障时继续完成全局任务？

---

## **二、AI Workload 为什么超出了传统调度范式**

## **1. 多模态数据处理：异构 Pipeline**

典型流程如下：

```text
读取数据
→ 抽帧 / 格式转换
→ OCR / ASR
→ 多模态模型推理
→ 清洗、过滤与输出
```

其中：

- 抽帧、格式转换通常是 CPU 密集型；
- OCR、语音识别和模型推理通常依赖 GPU；
- 各阶段并发度不同；
- 数据处理链路长、运行时间久。

因此产生三类需求：

### **异构资源**

不同算子必须匹配不同资源。例如，将 GPU 算子安排到 CPU 节点上没有意义；将 CPU 预处理能力配置不足，又会造成 GPU 空转。

### **动态分配**

如果某个 Stage 堵塞，系统需要增加该阶段的并发实例，而不是静态增加整个集群。

### **细粒度容错**

某个进程、Pod 或 GPU 出错时，应只恢复受影响的计算单元，而不是让整条 Pipeline 从头开始。

---

## **2. RLHF：多角色协同**

一次典型 PPO 流程可抽象为：

```text
Prompt
→ Actor 生成 Response
→ Reference / Reward / Critic 并行评估
→ Advantage 计算
→ Actor 与 Critic 更新
```

该流程具有以下特征：

- Actor 可能同时包含训练和推理角色；
- Reference、Reward、Critic 的资源需求不同；
- 推理依赖 vLLM 或 SGLang；
- 训练依赖 FSDP、Megatron 等框架；
- 角色之间存在复杂的数据传递和多播；
- 不同角色的并发量并不相同。

这不是简单的线性 DAG，而是一个由多种异构角色组成的协同系统。

---

## **三、预训练范式为什么不适合后训练与强化学习**

## **1. 预训练的 SPMD 模式**

FSDP、Megatron 等预训练系统通常采用：

```text
多个同构进程
+ 同一份程序
+ 同步 Barrier
+ 集合通信
```

这种模式适合大规模、规则化、同步式的预训练任务，但它隐含了几个前提：

- 计算单元基本同构；
- 资源需求相近；
- 通信组相对固定；
- 任务流程较稳定；
- 整体任务可以同步推进。

## **2. SPMD 的局限**

在 RLHF 中，这些前提往往不成立：

### **无法自然表达异构角色**

Actor、Reward、Critic、Reference 的程序、模型和资源需求不同。

### **故障影响范围过大**

一个进程或一张 GPU 出错，可能导致整个通信组失败。

### **缺少全局编排者**

各角色之间需要由一个中心控制逻辑统一协调，而不是让每个进程只关注自身计算。

---

## **3. Single-Controller + MPMD 的改进**

后训练框架逐渐采用：

```text
一个中心 Driver
+ 多个异构角色
+ 每个角色内部仍可使用 SPMD
```

这是一种分层设计：

- **全局层**：使用 Single-Controller 和 MPMD 管理异构角色；
- **局部层**：角色内部继续使用 SPMD 以获得高性能。

它同时取得了两种能力：

- 通过中心 Driver 表达复杂任务流；
- 通过角色内部的并行训练保留计算效率。

---

## **四、Ray 的第一性原理：把进程作为通用计算单元**

Ray 的关键抽象不是固定的批处理、流处理或训练通信组，而是：

> 一个可声明资源、可远程调用、可独立恢复的进程级计算单元。

这一抽象通过四组机制实现 AI 调度需求。

---

## **1. 用 Actor 表达长期运行的角色**

例如：

```python
@ray.remote(num_cpus=2, num_gpus=1, max_restarts=-1)
class RolloutWorker:
    ...
```

它同时声明了：

- 角色类型；
- CPU 需求；
- GPU 需求；
- 故障后的重启策略；
- 角色内部的状态恢复逻辑。

这比单纯提交一个批处理任务更接近 RLHF 中的实际角色。

---

## **2. 用资源声明完成异构调度**

不同角色可以声明不同资源：

```python
@ray.remote(num_gpus=2)
class Trainer:
    ...
```

于是：

- RolloutWorker 使用 2 个 CPU 和 1 个 GPU；
- Trainer 使用 2 个 GPU；
- Ray 根据资源约束将它们安排到合适的 Ray Node 上。

这里的关键改进是：

```text
资源调度粒度：
节点级 / Stage 级
→ 进程级 / Actor 级
```

---

## **3. 用远程调用编排任务流**

Ray 的远程调用形式为：

```python
response = rollout_worker.generate.remote("Hello")
ret = trainer.fit.remote(response)
```

其中：

- `generate.remote()` 异步触发远程计算；
- 返回 `ObjectRef`；
- `ObjectRef` 可以直接传递给下游角色；
- Driver 可以控制角色之间的依赖关系。

因此，复杂任务流不需要被强制表达为固定 DAG，可以在程序运行过程中动态构造。

---

## **4. 用动态创建实现运行时扩展**

例如：

```python
rollout_worker_group.append(RolloutWorker.remote())
```

这意味着系统可以根据负载：

- 增加 Rollout 实例；
- 减少低负载实例；
- 单独扩大某个瓶颈 Stage；
- 调整不同角色之间的并发比例。

因此，Ray 的弹性不是只扩展整个集群，而是可以扩展具体的进程级计算角色。

---

## **五、Ray 与其他计算引擎的本质差异**

| 系统 | 基本范式 | 异构资源 | 动态分配 | 容错粒度 | Single-Controller |
|---|---|---|---|---|---|
| Spark | BSP 批处理 | Stage 内粗粒度 | Stage 间 | RDD / Stage | 支持 |
| Flink | 流式 Dataflow | Slot 粗粒度 | 相对支持 | Checkpoint | 支持 |
| PyTorch | SPMD | 弱 | 静态通信组 | 整组重启 | 不支持 |
| Ray | 通用分布式 | 进程级 | 进程级 | 进程级 | 支持 |

### **1. Spark：适合规则化批处理**

Spark 的优化对象是批处理任务和 Stage。它可以进行一定程度的动态调整，但通常以 Stage 为边界，资源粒度较粗。

### **2. Flink：适合连续数据流**

Flink 的调度模型与流式 Dataflow 深度绑定，适合长期运行的流处理，但资源通常围绕 Slot 和算子并行度组织。

### **3. PyTorch：适合同构同步训练**

PyTorch 的分布式能力重点在高效集合通信和同步训练，而不是复杂异构角色的全局编排。

### **4. Ray：不预设业务计算范式**

Ray 提供的是：

```text
进程级计算单元
+ 资源约束
+ 远程调用
+ 状态对象
+ 动态创建
+ 自动重启
```

用户可以在其上构建：

- 批处理；
- 流处理；
- Actor-Critic 训练；
- 多角色 RL；
- 在线推理；
- Agent 工作流；
- 数据处理 Pipeline。

所以 Ray 的优势并非在某一种固定计算模式中达到最优，而是能够适配多种复杂 AI 任务。

---

## **六、Ray 的架构机理：请求如何被执行**

Ray 集群主要由以下组件构成：

```text
Driver
  ↓
本地 Raylet
  ↓
目标节点 Raylet
  ↓
Worker 进程
  ↓
远程 Actor / Task
```

### **主要组件职责**

#### **Driver**

中心控制进程，负责：

- 创建远程角色；
- 发起远程调用；
- 传递 ObjectRef；
- 编排全局任务流；
- 动态调整实例数量。

#### **GCS**

Global Control Store，负责：

- 集群元数据；
- 节点状态；
- 全局控制信息；
- 集群级状态同步。

#### **Raylet**

每个 Worker 节点上的本地调度与进程管理组件，负责：

- 维护本地资源状态；
- 选择目标节点；
- 启动和管理 Worker 进程；
- 执行本地调度决策。

### **一次调度流程**

1. Driver 向本地 Raylet 发起资源请求；
2. 本地 Raylet 选择目标 Ray Node；
3. 请求转发到目标 Raylet；
4. 目标 Raylet检查本地资源；
5. 若资源满足，则启动 Worker 进程；
6. Driver 通过 gRPC 或 RDMA 与远程实例通信。

### **可用调度策略**

Ray 支持多种策略，包括：

- Round-Robin；
- 按资源堆叠水位调度；
- Node / Label 亲和性；
- Gang Scheduling；
- Data Locality。

这说明 Ray 不只是“把进程随机放到节点上”，而是可以依据资源、拓扑和数据位置进行调度。

---

## **七、为什么必须引入 K8s**

Ray 解决的是应用层计算调度，但不适合独立承担完整的企业级基础设施管理。

K8s 负责的内容包括：

- 物理节点资源管理；
- 容器和 Pod 生命周期；
- 服务发现；
- 存储编排；
- 权限体系；
- 监控和运维；
- 大规模集群管理；
- 资源池和节点故障处理。

因此，Ray 与 K8s 的关系不是替代关系，而是上下层分工。

---

## **八、K8s 与 Ray 的职责边界**

| 维度 | K8s | Ray |
|---|---|---|
| 定位 | 物理资源调度与管理 | 应用层调度与编排 |
| 管理对象 | 物理节点、Pod | Ray Node、Worker 进程 |
| 生命周期 | 容器 / Pod | Worker 进程、Actor、Task |
| 调度路径 | Pod → 物理节点 | Worker → Ray Node |
| API | YAML 声明式 | Python 编程式 |
| 主要使用者 | 平台和运维团队 | 分布式应用开发者 |

可以将两者概括为：

```text
K8s 决定“Ray 集群使用哪些物理资源”
Ray 决定“AI 任务如何使用 Ray 集群中的资源”
```

---

## **九、KubeRay：连接 K8s 与 Ray 的控制层**

KubeRay Operator 通过自定义资源 `RayCluster` 管理 Ray 集群。

其基本流程是：

```text
用户提交 RayCluster CR
→ KubeRay Operator 持续调谐
→ 创建 Head Pod 和 Worker Pod
→ 形成 Ray Cluster
→ Ray Scheduler 调度业务进程
```

KubeRay 的作用包括：

- 创建和维护 Ray Head；
- 创建异构 Worker；
- 管理 Ray 集群生命周期；
- 支持运行时扩缩容；
- 将 Ray 集群接入 K8s 的声明式管理体系。

三层调度关系如下：

```text
K8s
负责 Pod → 物理节点

KubeRay
负责 RayCluster 生命周期与组网

Ray Scheduler
负责 Worker 进程 → Ray Node
```

其核心思想是：

```text
由粗到细
由基础设施到应用
由静态资源到运行时计算
```

---

## **十、腾讯超大规模落地为什么不能直接使用社区方案**

社区版 KubeRay 通常假设：

```text
一个 RayCluster
→ 部署在一个 K8s 物理集群内
```

但腾讯内部基础设施具有更复杂的现实约束：

- 物理 K8s 集群不直接暴露给上层；
- 由联邦层统一管理；
- 生产环境有上百个 K8s 物理集群；
- CPU 与 GPU 算力分布在不同集群；
- WeData 与太极 AI 平台维护不同的 K8s 基础设施；
- Ray 又要求 CPU 与 GPU 融合组网。

因此产生结构性矛盾：

```text
Ray 需要跨集群融合异构资源
KubeRay 默认只支持单集群部署
```

如果直接使用社区能力，就无法满足：

- CPU + GPU 统一调度；
- 跨物理集群组网；
- 大规模资源弹性；
- 多平台复用；
- 统一运维和容灾。

---

## **十一、跨集群部署的三种方案及取舍**

### **方案一：增加中间调度层**

做法：

```text
K8s
→ 自定义中间调度器
→ 预申请 Pod
→ Ray
```

问题：

- 从两层调度变成三层调度；
- 引入额外资源预留；
- 调度链路复杂；
- 调优和故障定位困难；
- 可能出现资源浪费。

### **方案二：平台侧自行 Standalone 组网**

做法：

- 平台直接调度多个 K8s 集群；
- 创建多个 Deployment 和 Pod 组；
- Pod 内自行启动 Ray；
- 手工指定 Head 节点。

问题：

- 放弃 KubeRay 的标准能力；
- 平台需要重新实现组网、生命周期、扩缩容和故障处理；
- 长期维护成本高；
- 与开源生态脱节。

### **方案三：扩展 KubeRay 支持联邦**

做法：

- 保留 KubeRay 的核心能力；
- 在其上增加跨集群联邦；
- 在多个物理集群中部署 KubeRay Workload；
- 只让一个 Workload 启动 GCS；
- 其他 Workload 作为同一 Ray 集群的 Worker。

最终选择方案三的根本原因是：

```text
最大程度复用社区能力
避免额外调度层
保持 KubeRay 生态兼容性
同时满足跨集群异构资源需求
```

---

## **十二、KubeRay 联邦架构的两阶段演进**

## **1. 阶段一：Virtual Kubelet 架构**

### **设计思路**

- CPU 集群保留完整 KubeRay；
- 通过 Virtual Kubelet 将 GPU 集群抽象为虚拟节点；
- KubeRay 通过 VK 请求创建 GPU Pod；
- VK 再调用上层 ModelService；
- ModelService 最终创建真正的 GPU Pod。

链路为：

```text
KubeRay
→ Virtual Kubelet
→ ModelService
→ GPU Pod
```

### **为什么最初采用**

它可以在不大幅改造现有 KubeRay 的情况下，把外部 GPU 资源“映射”进 CPU 集群。

### **为什么必须改进**

该方案存在三个根本问题：

#### **架构依赖倒置**

底层 VK 反向依赖上层服务，破坏了层次边界。

#### **调用链过长**

每创建一个 GPU Pod，都要触发一次上层服务调用。

#### **规模扩展性不足**

当 RayCluster 节点超过 100 个时，大量 Pod 创建请求会对 ModelService 造成压力。

因此，VK 方案适合快速落地，但不适合作为超大规模通用架构。

---

## **2. 阶段二：原生 KubeRay 联邦架构**

### **核心设计**

在多个 K8s 物理集群中并发部署 KubeRay Workload：

```text
CPU K8s 集群
→ KubeRay Workload

GPU K8s 集群
→ KubeRay Workload

其中一个 Workload 启动 GCS
其他 Workload 加入同一 Ray Cluster
```

同时增加：

- 联邦集群 Autoscaling；
- 跨集群 Worker 组网；
- 全局资源弹性；
- CPU 与 GPU 统一入口。

### **改进结果**

该方案实现：

- CPU 与 GPU 异构资源统一调度；
- 单集群规模达到万卡以上；
- WeData 与太极 AI 平台复用相同调度链路；
- Data 与 AI 平台调度统一；
- 保留 KubeRay 的生命周期与生态能力。

---

## **十三、为什么还需要跨层弹性调度**

即便完成跨集群组网，业务仍然面临一个现实问题：

> 业务方通常知道期望产能，却不知道实现该产能需要多少 CPU、GPU、网络和存储资源。

例如：

- CPU 预处理不足，导致 GPU 利用率低；
- CPU 与 GPU 分属不同地域，跨地域 IO 成为瓶颈；
- 某个 Stage 的并发量不足，导致数据堆积；
- 预先配置过多资源，造成长期空转。

因此，传统的“业务方预先填写资源规格”不再适用。

新的接口应从：

```text
请指定 CPU 数量、GPU 数量和节点类型
```

转向：

```text
请提交算子和预期产能
```

然后由系统根据运行时反馈自动完成资源匹配。

---

## **十四、跨层弹性调度的三级闭环**

### **第一级：动态扩缩容**

根据：

- Ray 集群资源水位；
- 任务队列长度；
- 各 Stage 负载；
- 数据堆积情况；

动态调整异构 Ray 节点数量。

目标是：

- 减少资源空转；
- 避免数据积压；
- 增加瓶颈 Stage 的并发；
- 维持目标产能。

### **第二级：Pod 重调度**

当节点存在潜在风险时，例如：

- GPU ECC Error；
- 磁盘空间不足；
- 节点健康度异常；

系统可以只替换问题 Pod，而不必重启整个任务。

### **第三级：任务重调度**

如果前两级调整仍无法恢复目标产能，则：

- 将任务交回 K8s 资源调度层；
- 重新选择资源池和物理节点；
- 重建任务运行环境；
- 继续执行任务。

形成如下升级链路：

```text
进程级调整
→ Pod 级调整
→ 任务级调整
```

其基本原则是：

> 优先使用最小代价解决问题，只有局部修复无效时才扩大重调度范围。

---

## **十五、为什么需要跨层自动化容灾**

在强化学习中，训练任务通常运行时间长、资源规模大、对单卡故障敏感。

如果 Ray 或 RL 框架与 K8s 各自独立处理故障，就会出现信息断裂：

### **问题一：K8s 知道故障，RL 不知道**

K8s 屏蔽故障 GPU 后，RL 框架可能仍然等待或继续使用旧状态，直到训练失败后才发现问题。

### **问题二：RL 知道故障，K8s 不知道**

RL 任务失败并重启后，K8s 未记录故障卡，新的任务可能再次被调度到同一张卡上，导致重复失败。

本质上，这是一个跨层状态不一致问题：

```text
故障信息没有在 Ray / RL / K8s 之间闭环流动
```

---

## **十六、跨层自动化容灾的设计**

整体闭环为：

```text
故障感知
→ 统一故障标记
→ 故障节点替换
→ 任务续训
→ 故障卡屏蔽
→ 后续调度自动避开
```

### **1. 多源故障感知**

#### **Worker 节点**

Dashboard Agent 周期性检查：

- 磁盘；
- GPU 健康度；
- 其他关键资源指标。

#### **Head 节点**

Train Monitor 分析：

- 训练日志；
- 任务异常；
- 训练进度停滞。

#### **K8s 算力层**

通过定期巡检发现：

- 故障 GPU；
- 异常节点；
- 资源池健康问题。

### **2. 统一故障标记**

任意组件发现故障后，都通过 Ray Dashboard 的开放接口标记故障节点。

这一步的关键不是“谁发现故障”，而是：

> 所有故障最终进入统一的状态系统。

### **3. 故障替换与续训**

训练任务重启时：

- 替换所有已标记故障节点；
- 在 K8s 层屏蔽故障 GPU；
- 新任务自动避开已知故障；
- RL 框架恢复训练状态。

这样就把容灾从：

```text
任务失败
→ 人工分析
→ 人工处理
→ 手工重启
```

改进为：

```text
自动发现
→ 自动隔离
→ 自动替换
→ 自动恢复
```

---

## **十七、本文的核心设计原则**

### **原则一：按层次划分职责**

不要让一个系统同时承担所有问题：

```text
K8s 管物理资源
KubeRay 管 Ray 集群
Ray 管应用计算
业务框架管模型和任务逻辑
```

### **原则二：调度粒度越接近真实计算单元，灵活性越高**

```text
节点级
→ Pod 级
→ Worker 进程级
→ Actor / Task 级
```

AI Workload 的资源需求通常在进程级发生变化，因此进程级调度比节点级调度更匹配实际需求。

### **原则三：优先局部恢复，避免全局重启**

故障处理应遵循：

```text
进程重启
→ Pod 替换
→ 角色恢复
→ 任务重调度
→ 全局重建
```

故障范围越小，恢复成本越低。

### **原则四：控制面与执行面分离**

- Driver 是控制面；
- Actor 和 Task 是执行面；
- K8s 与 KubeRay 是基础设施控制面；
- Raylet 负责节点级执行调度。

这种分离使系统能够集中编排，同时保持执行单元的独立性。

### **原则五：从静态资源配置转向目标驱动调度**

传统方式要求用户提供：

```text
CPU = ?
GPU = ?
节点类型 = ?
```

跨层弹性调度要求用户提供：

```text
算子是什么
目标产能是多少
```

系统根据观测到的运行状态反推资源配置。

### **原则六：故障处理必须形成跨层闭环**

只在某一层处理故障是不够的：

```text
感知层发现故障
→ 调度层传播状态
→ 资源层隔离故障
→ 任务层恢复执行
```

---

## **十八、适用边界：Ray + K8s 并非所有场景的最优解**

### **Ray 更适合的场景**

- 多模态数据处理；
- 后训练与强化学习；
- 多角色异构协同；
- 在线推理编排；
- Agent 工作流；
- 需要动态扩缩容的任务；
- 需要进程级容错的长任务；
- 训练与推理混合场景。

### **固定框架可能更适合的场景**

如果任务具有以下特征，专用系统可能更高效：

- 计算模式高度固定；
- 角色完全同构；
- 通信模式稳定；
- 资源需求可提前确定；
- 主要目标是极致的同步训练性能。

例如，规则化的大规模预训练仍然需要依靠 Megatron、FSDP 等专用训练框架。Ray 更适合承担上层编排、角色调度与任务生命周期管理，而不一定替代角色内部的高性能训练内核。

---

## **十九、本文的证据闭环**

按照“母题—证据—方案—结果”的方式，可以形成以下闭环：

### **母题一：AI 任务是否真的需要异构调度？**

**证据：**

- 多模态 Pipeline 同时包含 CPU 和 GPU 算子；
- RLHF 包含 Actor、Reference、Reward、Critic 等异构角色。

**方案：**

- Ray 以进程为单位声明 CPU、GPU 和节点约束。

**结果：**

- 不同角色可以被分配到匹配的异构节点。

---

### **母题二：AI 任务是否需要运行时动态扩展？**

**证据：**

- 各 Stage 的吞吐和瓶颈随运行状态变化；
- 业务方事先无法准确预估资源规格。

**方案：**

- 动态增加或减少 Actor；
- 根据 Ray 资源水位和负载调整 Pod 数量；
- 根据产能目标自动优化资源配置。

**结果：**

- 资源从静态预留变为按需分配。

---

### **母题三：AI 任务是否需要细粒度容错？**

**证据：**

- OOM、GPU Error、磁盘问题和 Spot 回收不可避免；
- 整组重启会造成高昂恢复成本。

**方案：**

- Actor 自动重启；
- Pod 级替换；
- 任务级重调度；
- 故障节点统一标记和隔离。

**结果：**

- 故障从全局失败转变为局部恢复。

---

### **母题四：为什么不能只使用 K8s？**

**证据：**

- K8s 擅长 Pod 到物理节点的资源调度；
- 复杂 AI 任务需要进程级、角色级和任务流级编排。

**方案：**

- 由 K8s 管理基础资源；
- 由 Ray 管理应用内部计算单元。

**结果：**

- 形成两层协同调度，而不是让 K8s 直接承担全部 AI 任务逻辑。

---

### **母题五：为什么社区方案还不够？**

**证据：**

- 社区 KubeRay 通常面向单一 K8s 物理集群；
- 腾讯需要跨多个 CPU / GPU 集群统一组网。

**方案：**

- 从 VK 架构演进到 KubeRay 联邦；
- 在多个物理集群中部署 Workload；
- 共享同一 Ray 集群的控制面。

**结果：**

- 实现跨集群异构资源统一与大规模弹性。

---

## **二十、未来方向的内在逻辑**

本文提出的三个未来方向，实际上分别对应三个尚未完全解决的问题。

### **1. 更原生的 Ray 联邦**

当前联邦方案仍需要接入层感知和场景迁移，说明跨集群能力还没有完全内化到 K8s + Ray 技术栈中。

目标是：

```text
跨集群能力原生化
→ 降低接入成本
→ 减少迁移差异
→ 提升通用性
```

### **2. 更通用的分布式底座**

当前场景包括：

- 数据处理；
- 预训练；
- 强化学习；
- 在线推理；
- Agent。

未来需要统一的不只是调度，还包括：

- 通信；
- 存储；
- 数据传递；
- 生命周期；
- 容错；
- 观测和运维。

### **3. 更统一的 Agentic RL Infra**

传统 RL 已经需要统一训练和推理。Agentic RL 进一步引入：

- Agent；
- 工具调用；
- Sandbox；
- 多轮环境交互；
- 任务状态与长期记忆。

因此未来的核心问题是：

```text
如何统一编排模型训练、模型推理、Agent 执行和 Sandbox 环境
```

---

## **最终抽象**

本文可以压缩成一个四层模型：

```text
第一层：物理资源层
K8s 管理节点、GPU、CPU、网络、存储和 Pod。

第二层：集群组织层
KubeRay 将多个 K8s 资源组织为统一 Ray Cluster。

第三层：计算调度层
Ray 以进程、Actor、Task 为单位进行异构调度、动态扩展和细粒度容错。

第四层：AI 应用层
PyTorch、vLLM、RL 框架、数据处理框架和 Agent 使用 Ray 完成复杂编排。
```

其最终目标不是单纯提高调度效率，而是建立一个具备以下特征的 AI 基础设施：

```text
资源异构但可统一管理
任务复杂但可程序化编排
负载变化但可动态适配
局部故障但可自动恢复
跨集群部署但保持统一体验
```

因此，K8s + Ray 的真正价值可以概括为：

> K8s 提供稳定的资源底座，Ray 提供灵活的计算抽象，KubeRay 负责两者协同；三者共同把大模型基础设施从“静态部署系统”推进为“可编排、可弹性、可恢复的分布式 AI 操作系统”。
