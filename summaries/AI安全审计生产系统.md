### **核心结论**

这篇文章的本质不是“用大模型扫描代码”，而是构建了一套可规模化运行的 **AI 安全审计生产系统**：以通用 Agent 提供代码理解与执行能力，以业务 Skill 固化漏洞检测方法，以 MCP/CLI 提供数据工具，以人工复核保障最终准确性，并通过 Early-Exit、精准取数和分层模型降低成本。

其核心目标是同时解决三个矛盾：

- **全量覆盖**与有限人工之间的矛盾；
- **检测速度**与审计深度之间的矛盾；
- **模型能力**与调用成本之间的矛盾。

---

## **一、问题定义：为什么需要 AI 驱动的网关安全审计**

### **1. 审计对象是什么**

审计对象是网关中的 API 路由及其完整调用链，包括：

- 路由配置；
- 认证与登录态；
- Controller 或入口参数；
- Service、RPC、DAO 等下游调用；
- 数据读取与写入逻辑；
- 返回结果及其敏感性；
- 用户身份、资源 ID、所有权校验等安全边界。

因此，真正要判断的不是“某段代码是否包含权限注解”，而是：

> 一个请求是否能够在缺乏合法身份或资源所有权的情况下，访问或操作不属于当前用户的资源。

### **2. 传统方案为什么失效**

传统人工抽样审计存在三个结构性问题。

#### **覆盖不足**

人工只能抽查有限接口，无法覆盖持续增长的数万条 API 和数百个微服务。文章称，抽样审计覆盖率约为 20%。

#### **响应滞后**

新接口上线后，如果依赖排期审计，漏洞可能在较长时间内处于未发现状态。

#### **规则难以复用**

经验通常存在于个人判断中，难以转化为统一、可追踪、可持续优化的审计标准。

### **3. 第一性原理还原**

安全审计的最小闭环是：

```text
对象枚举 → 证据获取 → 安全判断 → 风险评估 → 人工确认 → 修复反馈
```

其中最耗费人力的部分是：

- 重复读取大量代码；
- 沿调用链追踪参数与权限；
- 区分真实漏洞与表面风险；
- 对风险进行业务化定级。

这些工作具有较强的模式识别和规则推理特征，适合由 AI 承担初筛；而复杂业务判断、最终定性和修复决策仍需要人工参与。

## **二、总体方案：What、Why、How**

## **1. What：系统由什么组成**

整体系统可以抽象为六层：

```text
任务调度层
    ↓
通用 Agent 层
    ↓
业务 Skill 层
    ↓
MCP / CLI 工具层
    ↓
代码、配置、调用链数据层
    ↓
告警、报告、人工复核层
```

各层职责不同：

| 层次 | 主要职责 | 解决的问题 |
|---|---|---|
| 调度层 | 日检、月检、任务编排、结果存储 | 如何持续运行 |
| 通用 Agent | 代码理解、推理、上下文管理、会话恢复 | 如何分析复杂代码 |
| Skill 层 | 漏洞规则、分析流程、报告模板 | 如何保证业务一致性 |
| 工具层 | 获取代码、路由、配置、调用链信息 | 如何提供可靠证据 |
| 数据层 | GitLab、网关、Dubbo、源码等 | 从哪里获取事实 |
| 结果层 | 告警、风险等级、修复建议、人工复核 | 如何形成闭环 |

## **2. Why：为什么采用这种架构**

### **通用 Agent 与业务 Skill 分离**

这是整个方案最关键的架构原则。

#### **通用 Agent 负责通用能力**

例如：

- 代码阅读；
- 跨文件推理；
- 上下文管理；
- 多轮分析；
- 会话恢复；
- 工具调用。

这些能力由成熟的 Agent 框架提供，避免重复建设。

#### **业务 Skill 负责变化频繁的安全知识**

例如：

- 哪些配置属于公开路由；
- 如何判断认证是否存在；
- 如何追踪用户 ID 来源；
- 如何判断资源是否属于当前用户；
- 如何评估数据敏感性；
- 如何生成标准化报告。

安全规则会随着漏洞案例、业务架构和误报分析持续变化，因此应放在 Skill 中，而不是固化在 Agent 代码中。

### **这种分离带来的收益**

```text
通用能力稳定复用
业务规则独立迭代
分析过程可以恢复
结果能够追溯复现
```

如果把业务规则直接写进 Agent 或底层代码中，规则更新会带来较高开发成本，也难以解释历史审计结果。

---

## **三、运行模式：如何实现规模化审计**

文章采用“增量日检 + 存量月检”的运行模式。

### **1. 增量日检**

主要面向：

- 新增路由；
- 路由配置变更；
- 调用链变化；
- 权限逻辑变更；
- 关键代码提交。

目标是缩短漏洞暴露时间，使安全审计接近开发变更速度。

### **2. 存量月检**

主要面向：

- 历史未审计路由；
- 规则升级后重新审计；
- 模型能力升级后的全量复查；
- 过去误报较多的重点服务。

目标是避免一次审计后长期失效。

### **3. AI 与人工的分工**

合理分工不是“AI 自动决定一切”，而是：

```text
AI：全量筛查、证据整理、初步判断、风险排序
人工：复杂分析、边界确认、最终定性、修复推动
```

其逻辑是：

- AI 擅长规模化、重复性和结构化工作；
- 人工擅长业务语境理解、异常情况处理和最终责任判断。

---

## **四、漏洞判断模型：以越权为例**

越权漏洞的核心不是“有没有登录”，而是：

> 当前身份是否有权访问或操作目标资源。

可以将判断拆解为四个问题：

```text
身份是谁？
资源是什么？
身份与资源之间是否存在合法关系？
系统是否在最终操作点验证了这种关系？
```

---

## **五、越权检测的四步决策流程**

## **1. 第一步：路由配置检查**

检查重点包括：

- `auth_config.public`；
- `required_scopes`；
- 路由是否公开；
- 路由是否声明权限范围。

### **为什么先检查配置**

路由配置是低成本、高信息密度的证据。如果配置已经明确表明路由不公开且具备标准权限要求，就没有必要立即深入分析全部代码。

### **设计方式：短路退出**

```text
配置无异常 → 直接跳过后续深度审计
配置存在风险 → 继续分析
```

这就是 Early-Exit 的第一处应用。

---

## **2. 第二步：登录态识别**

沿调用链查找认证节点，判断：

- 是否已经经过统一认证；
- 是否存在标准登录态；
- 认证信息是否被正确传递；
- 当前路由是否属于可信认证链路。

### **为什么需要单独识别登录态**

如果每条路由都从头分析认证代码，会产生大量重复计算。标准认证路由可以被信任，只有认证链不明确或异常时才进入代码审计。

```text
标准认证路由 → 信任并跳过深度认证分析
认证关系不明确 → 进入下一步
```

文章称，这种 Early-Exit 在标准认证场景下可节省约 50%～70% 成本。

---

## **3. 第三步：代码审计**

代码审计主要从三个维度展开。

### **权限注解**

检查类似：

```java
@PreAuthorize(...)
```

重点不是注解是否存在，而是判断注解是否：

- 绑定了正确的权限；
- 覆盖了当前操作；
- 与业务资源匹配；
- 没有被错误配置或绕过。

### **用户 ID 来源**

判断用户 ID 来自哪里：

```text
登录态 / Token / Session
        vs
请求参数 / URL / Body
```

如果用户身份直接由请求参数决定，就存在被伪造或替换的可能。

需要重点识别：

- `userId`；
- `memberId`；
- `accountId`；
- `ownerId`；
- 其他代表用户身份的字段。

### **所有权校验**

判断系统是否验证了：

```text
当前用户 == 资源所有者
```

常见安全方式是将用户身份直接加入数据库查询条件：

```sql
SELECT *
FROM resource
WHERE resource_id = ?
  AND user_id = current_user_id;
```

风险方式则可能是：

```sql
SELECT *
FROM resource
WHERE resource_id = ?;
```

随后仅依赖上层逻辑或中间层判断，这会造成信任边界不完整。

---

## **4. 第四步：精细化危害评估**

发现“可能存在越权”并不等于完成审计，还需要判断漏洞造成的实际影响。

文章将风险分为两类：

```text
越权读取：未经授权获取数据
越权操作：未经授权改变业务状态或利益归属
```

### **越权读取：看数据敏感性**

分析依据包括：

- 变量名；
- 字段类型；
- 接口定义；
- 返回对象；
- 数据库字段；
- 业务语义。

风险判断可抽象为：

```text
漏洞真实性 × 数据敏感性 × 暴露范围
```

例如：

- 普通展示信息：风险较低；
- 联系方式、交易信息、身份信息：风险较高；
- 凭证、支付、敏感个人信息：风险更高。

### **越权操作：看利益流向**

越权操作的重点不是返回了什么，而是攻击者能改变什么。

需要判断：

- 是否改变订单、账户或资产状态；
- 是否产生资金或权益转移；
- 是否修改关键业务配置；
- 是否影响其他用户；
- 是否造成不可逆后果。

因此，可以用以下模型理解：

```text
操作风险 ≈ 可控性 × 利益价值 × 不可逆程度 × 影响范围
```

这比简单按照“存在越权”统一定为高危更符合真实业务风险。

---

## **六、MCP 工具集：为什么工具设计决定审计质量**

Agent 的判断质量取决于两件事：

```text
推理能力 + 证据质量
```

如果工具返回的信息不完整、过多或缺少上下文，即使模型能力很强，也容易误判。

工具应围绕审计所需证据设计，包括：

- 路由配置查询；
- 调用链查询；
- 文件精准读取；
- 代码搜索；
- GitLab 文件获取；
- Dubbo 配置获取；
- 结果与报告存储。

### **工具设计原则**

#### **按需获取**

工具不应默认返回完整仓库或完整文件，而应支持：

- 指定文件；
- 指定行号；
- 指定方法；
- 指定关键词；
- 指定调用链节点；
- 指定字段。

#### **结果结构化**

采用 YAML 等更适合模型阅读的结构化格式，减少冗余字段，降低解析成本。

#### **上下文完整**

返回结果既不能过度膨胀，也不能缺失做判断所需的关键上下文。

## **七、Token 成本优化：从哪里浪费，如何解决**

文章实现 Token 成本降低 95% 以上，核心不是单纯更换模型，而是减少无效上下文。

可以将成本抽象为：

```text
总成本 ≈ 调用次数 × 每次输入 Token
```

因此需要同时降低：

- 每次输入的 Token；
- 不必要的调用次数；
- 单次返回内容大小；
- 使用高价模型的比例。

## **八、三层成本优化方案**

## **1. MCP 转 CLI：减少工具描述开销**

### **问题**

每次使用 MCP 工具时，模型可能需要加载完整工具定义、参数说明和上下文信息。

### **方案**

将 MCP 工具转换为 CLI 命令，即 `mcp2cli`：

```text
原始方式：Agent → MCP 上下文 → MCP 工具
优化方式：Agent → CLI 命令
```

### **为什么有效**

CLI 的调用形式更简洁，避免在每轮会话中重复加载完整 MCP 上下文。

文章给出的结果是：可节省约 61% Token。

---

## **2. 精准提取：避免返回完整文件**

### **问题**

无参数调用可能返回完整文件，最大达到约 1.47 MB，约 50 万 Token。

这会带来三类问题：

- 成本高；
- 模型注意力被无关内容稀释；
- 重要代码更容易被忽略。

### **方案**

为文件读取工具增加精准参数，例如：

- 文件路径；
- 起止行号；
- 类名；
- 方法名；
- 搜索关键词；
- 上下文行数。

### **核心原则**

```text
先定位，再读取
先摘要，再深入
按证据需求获取内容
```

文章称，v2 相较 v1 可进一步节省约 88%。

---

## **3. Early-Exit：在低风险分支提前结束**

### **问题**

所有路由都执行完整代码审计，会导致大量重复计算。

### **方案**

建立分层决策：

```text
配置正常 → 结束
认证标准 → 结束
存在异常 → 深入代码
存在疑点 → 人工复核
```

### **本质**

Early-Exit 不是降低审计标准，而是利用更高层级、更低成本的证据先排除不需要深挖的对象。

---

## **4. YAML 返回格式：降低结构化数据成本**

相较于字段冗余较多的 JSON，YAML 通常能以更紧凑的形式表达层级数据，并且便于模型阅读。

但其适用前提是：

- 字段结构稳定；
- 缩进格式可靠；
- 不承担严格机器校验时优先使用。

---

## **九、模型选型：为什么不能只看模型排行榜**

安全审计模型不能只比较通用能力，而应建立场景化决策矩阵。

关键指标包括：

- **Precision，准确率**：模型判断为漏洞的结果中，有多少是真漏洞；
- **Recall，召回率**：所有真实漏洞中，有多少被模型发现；
- 单次调用成本；
- 处理速度；
- 长上下文能力；
- 代码理解能力；
- 输出稳定性。

### **准确率与召回率的权衡**

在安全审计中，漏掉真实高危漏洞通常比产生误报更危险，因此召回率通常需要优先满足底线。

但召回率过高、准确率过低，也会造成：

- 人工复核压力过大；
- 告警疲劳；
- 真实风险被大量噪声淹没。

因此应采用约束式决策：

```text
先满足召回率底线
再满足准确率要求
最后比较成本和速度
```

文章最终选择 `qwen3.5-plus`，原因是：在满足召回率要求的候选模型中，它具有更低的单位成本和可接受的准确率，适合批量审计。

### **选型边界**

文章也明确指出：

- 测试集只有 100+ 条人工标注样本；
- 测试集与生产告警数据隔离；
- 结果只能作为基线；
- 模型更新可能改变评测结论。

因此，模型选型不是一次性决定，而应持续评测。

---

## **十、误报分析：为什么模型会误判**

误报并不只是模型能力不足，更多是证据链不完整或规则边界不清。

文章识别出四类主要原因。

## **1. 中间层与最终操作层之间的信任边界断裂**

### **错误模式**

模型发现中间层没有校验，就立即判断存在漏洞，没有继续追踪到最终数据操作层。

### **为什么会误报**

中间层缺少校验，并不代表最终数据库查询或业务方法没有校验。真正的判断点应是最终资源访问或状态修改的位置。

### **改进方案**

在 Skill 中加入规则：

```text
发现校验就停止；
发现缺失就继续追踪。
```

也就是：

- 找到明确有效的最终校验：可以停止；
- 中间层未发现校验：不能立即定性；
- 必须继续追踪到数据访问或最终操作点。

该方案预计解决约 35% 的误报。

---

## **2. 上游与下游参数语义不一致**

### **错误模式**

下游方法接收资源 ID，看起来存在越权可能；但上游 Controller 实际上并没有传入资源 ID。

### **为什么会误报**

模型只看到了下游方法的危险形态，却没有确认该参数是否能够由用户控制。

### **改进方案**

优先检查 Controller 层 Request 对象：

- 是否包含资源 ID；
- 资源 ID 是否来自用户请求；
- 是否由系统内部生成；
- 上游是否始终固定为当前用户资源。

如果入口参数中没有资源 ID，则可能只是“操作当前用户自己的数据”，不应直接判定为越权。

该方案预计解决约 25% 的误报。

---

## **3. Dubbo 配置信息缺失**

### **错误模式**

开放网关调用内部 Dubbo 服务时，模型无法获取完整的传参与认证信息，因此错误判断认证关系。

### **为什么会误报**

代码本身无法表达所有运行时配置。若只分析源码，Agent 看不到：

- Dubbo 方法映射；
- 参数转换；
- 内部认证；
- 服务间信任关系；
- 实际调用配置。

### **改进方案**

引入 `get_dubbo_config` 工具，补充开放网关到 Dubbo 服务之间的运行时配置。

这说明：

> 当代码证据不足时，不能单纯要求模型“推理得更好”，而应补充模型无法直接获得的外部事实。

该方案预计解决约 10% 的误报。

---

## **4. 对低价值响应的敏感性判断过度**

### **错误模式**

模型将没有敏感信息的读取操作也判断为高风险越权。

### **为什么会误报**

模型把“能够读取其他数据”和“读取了高价值敏感数据”混为一谈。

### **改进方案**

在 Skill 中明确区分：

- 不敏感数据；
- 一般业务数据；
- 用户隐私数据；
- 交易与资产数据；
- 凭证及高敏感数据。

风险评估必须同时考虑：

```text
是否越权 × 读取了什么 × 影响了多少对象
```

---

## **十一、这套方案的证据闭环**

可以将整个审计系统表达为一条母题驱动的证据链。

### **母题**

```text
该接口是否允许不具备合法权限的主体访问或改变不属于自己的资源？
```

### **证据链**

```text
路由是否公开？
    ↓
是否存在标准认证？
    ↓
身份从哪里来？
    ↓
资源 ID 从哪里来？
    ↓
是否验证身份与资源的归属关系？
    ↓
最终读取或操作点是否仍受保护？
    ↓
实际影响是什么？
    ↓
风险等级与修复建议是什么？
```

每一步都必须有证据支撑，不能仅凭局部代码做结论。

### **正向证据**

- 明确的认证配置；
- 标准登录态；
- 权限注解；
- 用户 ID 来自可信身份；
- 数据库查询包含当前用户条件；
- 最终操作点存在所有权校验。

### **负向证据**

- 路由公开；
- 权限配置缺失；
- 用户 ID 来自请求参数；
- 资源查询仅按资源 ID；
- 中间层没有继续追踪；
- Dubbo 配置缺失；
- 返回敏感数据或执行高价值操作。

### **定性原则**

```text
局部异常 ≠ 已确认漏洞
完整信任链断裂 + 可控输入 + 可达危险操作 = 高可信漏洞
```

---

## **十二、从第一性原理提炼出的设计原则**

### **原则一：先定义安全属性，再设计检测流程**

不要从“代码里有哪些危险关键词”出发，而要先定义：

```text
谁可以对什么资源执行什么操作？
```

代码规则只是安全属性的证据。

### **原则二：先使用便宜且稳定的证据**

证据应按成本从低到高排列：

```text
路由配置
→ 认证信息
→ 入口参数
→ 调用链
→ 业务代码
→ 数据库与运行时配置
→ 人工验证
```

这既提升效率，也降低 Token 成本。

### **原则三：审计必须追踪到最终信任边界**

中间层是否校验不是最终答案。必须追踪到：

- 最终数据查询；
- 最终写入；
- 最终状态变更；
- 最终利益流向。

### **原则四：工具质量决定模型上限**

模型不能推断工具完全没有提供的信息。缺少 Dubbo 配置、调用参数或运行时关系时，应优先补充工具，而不是盲目升级模型。

### **原则五：风险等级必须结合业务后果**

漏洞严重程度不能只由漏洞类型决定，还要结合：

- 数据敏感性；
- 利益价值；
- 影响范围；
- 可逆性；
- 攻击难度。

### **原则六：优化优先减少无效信息，而不是压缩有效推理**

正确的优化顺序是：

```text
减少无关上下文
→ 减少不必要调用
→ 提前结束简单分支
→ 使用分层模型
→ 最后再考虑模型替换
```

### **原则七：AI 负责扩大覆盖面，人负责承担最终判断**

AI 的最佳定位是“审计放大器”，而不是“完全自动化裁判”。

---

## **十三、方案边界与局限性**

这套系统并不能自动解决所有安全问题。

### **业务语义依赖**

如果资源归属关系只存在于复杂业务规则中，且没有清晰代码或配置证据，模型可能无法准确判断。

### **运行时信息依赖**

动态配置、服务治理、网关规则和 Dubbo 映射如果未纳入工具，静态代码审计会产生误判。

### **模型稳定性**

模型版本变化可能影响准确率、召回率和输出格式，因此必须保留固定测试集和回归评测。

### **人工复核成本**

当召回率提高而准确率不足时，告警数量会增加，人工复核可能成为新的瓶颈。

### **测试集代表性**

100+ 样本只能作为基线，不能充分代表全部业务、语言、框架和漏洞类型。

## **十四、可复用的落地方法**

如果将这套方法迁移到其他安全审计场景，可以按以下顺序设计：

### **第一步：定义漏洞的业务本质**

例如：

- 越权：身份与资源关系不成立；
- SSRF：用户输入影响了服务端请求目标；
- 敏感信息泄露：低权限主体获得高敏感数据；
- 注入：不可信输入改变了解释器语义。

### **第二步：建立最小证据集**

明确判断漏洞至少需要哪些信息：

```text
入口 → 身份 → 参数 → 调用链 → 最终操作 → 影响
```

### **第三步：设计分层检测流程**

把流程拆成：

```text
低成本规则过滤
→ 结构化代码分析
→ 深度 Agent 推理
→ 人工复核
```

### **第四步：让工具围绕证据提供数据**

不要提供“大而全”的工具，而要提供可精准定位的接口。

### **第五步：把规则沉淀进 Skill**

将以下内容配置化：

- 检测步骤；
- 停止条件；
- 继续追踪条件；
- 误报排除规则；
- 风险评级标准；
- 报告模板。

### **第六步：建立误报反馈机制**

每个误报都应归类为：

- 证据缺失；
- 参数语义误读；
- 信任边界追踪不足；
- 业务规则不完整；
- 风险评级过度；
- 工具返回不准确。

然后分别通过 Skill、工具、数据或模型进行修正。

### **第七步：用指标验证系统**

至少持续跟踪：

- 路由覆盖率；
- 漏洞召回率；
- 告警准确率；
- 误报率；
- 单条审计成本；
- 平均审计时延；
- 人工复核耗时；
- 修复闭环率。

## **最终抽象**

这篇文章可以压缩为一个完整公式：

```text
高质量 AI 安全审计
=
明确的安全属性
× 完整的证据链
× 可复用的业务 Skill
× 精准的数据工具
× 分层检测流程
× 人工最终复核
```

其中：

- **What**：审计 API 是否存在身份、资源和权限关系断裂；
- **Why**：人工抽样无法满足大规模 API 的覆盖率、时效性和一致性要求；
- **How**：用通用 Agent 承担推理，用 Skill 固化规则，用 MCP/CLI 提供证据，用 Early-Exit 和精准取数降低成本，用人工完成最终定性；
- **边界**：AI 不能替代缺失的业务事实，也不能替代复杂风险判断；
- **改进方向**：优先补齐证据链和工具能力，再优化 Skill，最后再调整模型。
