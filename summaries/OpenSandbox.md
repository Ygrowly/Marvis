
### **结论：Credential Vault 的本质，是把“凭据持有”从沙箱执行环境中剥离，改为由沙箱外的出站代理按请求规则完成认证。**

它解决的不是“如何更方便地把密钥放进沙箱”，而是重新定义安全边界：**沙箱只负责发起业务请求，平台负责判断请求是否被授权，并在网络出口处注入真实凭据。**

## **一、问题定义：为什么真实密钥不能直接进入沙箱**

### **1. 沙箱的基本前提**

OpenSandbox 面向 AI Agent、代码执行、GUI Agent、Coding Agent 和评测等场景。沙箱运行的代码和工具通常具有以下特点：

- 代码来源不完全可信；
- Agent 行为具有不确定性；
- 可能执行第三方脚本和依赖；
- 可能受到 Prompt Injection 或网页内容影响；
- 工具链较长，难以穷举所有行为。

因此，沙箱的核心安全假设是：

> **沙箱内部的进程、代码、依赖和工具都不应天然被视为可信。**

### **2. 传统凭据注入方式的问题**

常见做法是将 API Key、Git Token 或内部服务 Token 放入：

- 环境变量；
- 命令行参数；
- 配置文件；
- 工作目录；
- 日志或临时文件。

这些方式的共同问题是：**真实凭据一旦进入沙箱，就变成沙箱内部可读取、可复制、可转发的普通字符串。**

可能的泄露路径包括：

| 暴露位置 | 典型风险 |
|---|---|
| 环境变量 | 进程枚举、调试信息、子进程继承 |
| 命令行参数 | 被进程列表、诊断工具或日志读取 |
| 配置文件 | 被代码、依赖或恶意脚本扫描 |
| 日志输出 | 被错误处理、调试输出或日志采集带出 |
| 第三方依赖 | 恶意包读取并外传 |
| 任意网络访问 | 密钥被转发到攻击者控制的地址 |

第一性原理可以归纳为：

> **只要秘密进入不可信计算边界，就无法再保证它不会被读取和复制。**

所以，问题不能只靠“更小心地保存密钥”解决，而应从架构上避免密钥进入该边界。

---

## **二、核心方案：Credential Vault 是什么**

Credential Vault 是 OpenSandbox 的**出站凭据代理机制**。

它将真实凭据保存在沙箱外部，由 egress sidecar 在请求离开沙箱时，根据预先配置的规则向请求中注入认证信息。

其核心分工是：

- **沙箱：** 执行代码、调用工具、发起请求；
- **Credential Vault：** 保存真实凭据；
- **egress sidecar：** 检查请求并注入凭据；
- **egress policy：** 限制沙箱能够访问哪些目标。

因此，凭据不再表现为沙箱里的字符串，而表现为：

> **只有在特定请求满足授权条件时，才会生效的一条出站规则。**

---

## **三、方案机理：真实请求是如何完成认证的**

### **1. 运行流程**

```text
宿主侧 SDK
    │
    ├─ 创建沙箱
    ├─ 配置出站网络策略
    └─ 将真实凭据和绑定规则写入 Vault
            │
            ▼
沙箱内部
    │
    ├─ 只获得假凭据或空值
    ├─ 运行 Claude Code、Git、curl 等工具
    └─ 发起普通 HTTPS 请求
            │
            ▼
egress sidecar
    │
    ├─ 检查请求是否匹配规则
    ├─ 匹配成功：注入真实认证 Header
    └─ 匹配失败：不注入或拒绝请求
            │
            ▼
外部服务
```

### **2. 请求匹配条件**

一条 Credential Vault binding 通常可以绑定以下维度：

- scheme，例如 `https`；
- host，例如 `api.anthropic.com`；
- port，例如 `443`；
- method，例如 `GET`、`POST`；
- path，例如 `/v1/*`；
- 认证位置，例如 `x-api-key` Header；
- 真实凭据值。

只有请求满足绑定条件，sidecar 才会注入真实凭据。

这意味着授权不再是：

> “这个沙箱拥有某个 Token。”

而变成：

> “这个沙箱只能用某个凭据访问某个服务的特定请求范围。”

---

## **四、典型案例：Claude Code 调用模型 API**

### **传统方式**

沙箱中设置真实密钥：

```bash
ANTHROPIC_API_KEY=真实密钥
```

Claude Code 从环境变量中读取密钥，再访问 Anthropic API。

问题是，任何能够读取沙箱环境的代码，都可能获得该密钥。

### **Credential Vault 方式**

沙箱中只设置假值：

```bash
ANTHROPIC_API_KEY=fake-key-inside-sandbox
```

宿主侧将真实密钥写入 Vault，并建立类似如下绑定：

```text
scheme: https
host: api.anthropic.com
port: 443
method: GET, POST
path: /v1/*
auth header: x-api-key
```

Claude Code 发起请求时：

```text
沙箱请求：
https://api.anthropic.com/v1/*

sidecar 判断：
请求是否满足 scheme、host、port、method、path？

匹配成功：
注入真实 x-api-key Header

发送至外部服务：
携带真实认证信息
```

Claude Code 能正常工作，但沙箱内部始终无法读取真实密钥。

---

## **五、适用场景：不仅是模型 API**

### **1. 私有 Git 仓库**

沙箱执行普通的 Git 操作：

```bash
GIT_TERMINAL_PROMPT=0 git clone https://api.github.com/org/private-repo.git
```

真实的 `username:token` 由宿主侧预先编码并保存在 Vault 中，再通过 Basic Auth binding 注入。

这样可以避免：

- 将 Token 写入 Git URL；
- 将 Token 放入环境变量；
- 将 Token 记录到命令历史；
- 将 Token 暴露给 Git 进程或仓库脚本。

### **2. 私有包仓库**

包管理器可以继续使用标准访问地址。凭据在出站请求经过 sidecar 时注入，而不是写入：

- `.npmrc`；
- `pip.conf`；
- Maven 配置；
- Shell 环境；
- 构建脚本。

### **3. 内部 API**

沙箱执行：

```bash
curl -fsS https://api.github.com/v1/projects/
```

真实 Token 由 sidecar 根据 Host、Path、Method 和 Header 规则补齐。

该方式尤其适合 Agent 调用多个内部服务，因为每个服务可以配置不同凭据和不同权限范围。

---

## **六、为什么这种方案比直接注入更安全**

### **1. 从“秘密暴露”转为“请求授权”**

传统模式的授权对象是一个字符串：

```text
拥有 Token → 可以尝试访问任何目标
```

Credential Vault 的授权对象是一个请求条件集合：

```text
请求匹配规则 → sidecar 才注入凭据
```

攻击者即使控制了沙箱内的代码，也难以直接读取 Token。它只能尝试发起请求，而请求是否能获得认证信息取决于绑定规则。

### **2. 缩小凭据使用范围**

凭据可以限定到：

- 特定协议；
- 特定域名；
- 特定端口；
- 特定 HTTP 方法；
- 特定 URL 路径；
- 特定认证 Header。

这符合最小权限原则：

> **凭据只能用于完成明确声明的业务动作。**

### **3. 减少自然残留**

真实密钥不会自然出现在：

- 沙箱环境变量；
- 命令行参数；
- 文件系统；
- 工具配置；
- 构建日志；
- 调试输出。

这并不意味着风险绝对为零，但显著减少了常见泄露面。

### **4. 便于审计和治理**

平台可以围绕 binding 记录：

- 哪个沙箱使用了哪类凭据；
- 请求访问了哪个 Host；
- 使用了什么 Method 和 Path；
- 哪些请求被允许或拒绝；
- 哪些凭据绑定过宽。

这使凭据治理从“检查代码是否泄露密钥”转向“审计出站授权规则”。

---

## **七、为什么还需要配合默认拒绝的出站策略**

Credential Vault 只负责：

> **请求匹配时注入什么凭据。**

它不一定单独负责：

> **沙箱是否能够访问任意外部地址。**

如果沙箱可以访问任意网络地址，即使真实密钥不会直接暴露，攻击者仍可能利用合法的认证请求进行越权操作，或者利用开放网络扩大攻击范围。

因此，推荐组合使用：

```text
默认拒绝出站网络
        +
仅允许访问必要的服务 Host
        +
Credential Vault 精确绑定凭据
```

三者分别承担不同职责：

| 机制 | 解决的问题 |
|---|---|
| 沙箱隔离 | 限制进程、文件和资源 |
| egress policy | 限制可以访问哪些网络目标 |
| Credential Vault | 限制请求何时获得真实认证信息 |

完整安全边界不是单一组件提供的，而是多层控制共同形成的。

---

## **八、设计中的关键改进原因**

### **改进一：从环境变量凭据改为出站注入**

**原方案问题：** 凭据进入沙箱后，任何内部代码都可能读取。

**改进方式：** 真实凭据留在沙箱外，出站时由 sidecar 注入。

**改进结果：** 沙箱仍能调用服务，但无法直接获得凭据本体。

### **改进二：从粗粒度 Token 权限改为细粒度请求绑定**

**原方案问题：** 一个 Token 可能被用于任意 Host、Path 或 Method。

**改进方式：** 将凭据绑定到具体请求属性。

**改进结果：** 即使 Agent 行为偏离预期，凭据可利用范围也更窄。

### **改进三：从开放网络改为默认拒绝**

**原方案问题：** 沙箱可以访问与任务无关的外部服务。

**改进方式：** 只允许访问任务需要的 Host，再叠加凭据绑定。

**改进结果：** 降低数据外传、越权调用和攻击扩散风险。

### **改进四：从“保护密钥存储”转向“避免密钥进入执行环境”**

**原方案问题：** 重点放在如何加密、隐藏或清理沙箱内的密钥。

**改进方式：** 从生命周期源头上不让真实密钥进入沙箱。

**改进结果：** 减少密钥复制、缓存、日志和残留带来的风险。

---

## **九、边界与限制**

### **1. 它不能消除所有风险**

Credential Vault 主要解决的是：

> **沙箱内代码直接读取真实凭据的问题。**

它不能自动阻止所有经过授权的恶意行为。例如，若某个请求本身被允许，沙箱内代码仍可能利用该权限：

- 读取不应读取的数据；
- 修改允许范围内的资源；
- 通过合法 API 进行过度操作；
- 将外部服务返回的数据带回沙箱。

因此仍需要配合：

- 最小权限的服务账号；
- 精确的 API 路径和方法限制；
- 请求审计；
- 速率限制；
- 服务端权限控制；
- 输入和输出治理。

### **2. 需要透明出站拦截**

Credential Vault 依赖 egress sidecar 对出站流量进行透明拦截，并通过 MITM 路径检查和修改请求。

因此，网络链路本身必须允许 sidecar 正常工作。

### **3. 不兼容同一 Pod 中的透明 Service Mesh Sidecar**

如果 Sandbox Pod 同时注入 Istio、Envoy 等透明 Service Mesh sidecar，可能出现两个网络拦截层竞争同一网络命名空间的问题。

当前限制是：

> **Credential Vault 不支持与这类透明 Service Mesh sidecar 同时部署在同一个 Sandbox Pod 内。**

这属于实现架构和网络拦截层面的边界，不是凭据绑定规则能够解决的问题。

### **4. 规则过宽会削弱安全性**

例如以下绑定就可能过于宽泛：

```text
host: api.example.com
path: /*
method: *
```

更安全的方式应尽量限制为：

```text
host: api.example.com
path: /v1/projects/*
method: GET
```

规则越宽，凭据可使用范围越大；规则越窄，安全性和治理能力越强，但配置复杂度也会提高。

---

## **十、第一性原理下的完整模型**

可以将整个设计抽象为四个问题：

### **1. 定义：保护什么**

保护对象不是“某个环境变量”，而是：

> **能够代表身份、权限或资源访问能力的真实凭据。**

### **2. 机理：凭据如何生效**

凭据不进入沙箱，而是在满足请求条件时，由出站代理临时注入。

### **3. 边界：凭据在哪里可以使用**

由以下条件共同决定：

```text
凭据绑定规则
+
网络出口策略
+
外部服务自身权限
```

### **4. 方法：如何落地**

实施时应遵循以下顺序：

1. 确定 Agent 实际需要访问的服务；
2. 为每个服务创建独立凭据；
3. 默认拒绝所有不必要的出站网络；
4. 将凭据绑定到具体 Host、Path、Method 和 Header；
5. 沙箱内只配置假值或空值；
6. 记录允许、拒绝和异常请求；
7. 定期收窄规则并轮换真实凭据；
8. 避免与透明 Service Mesh sidecar 共存于同一个 Sandbox Pod。

---

## **十一、母题驱动的证据闭环**

### **母题一：秘密不应进入不可信边界**

**现象：** Agent 需要凭据才能工作。  
**矛盾：** Agent 执行环境又不能被完全信任。  
**推论：** 凭据必须留在沙箱外。  
**方案：** 由 egress sidecar 在出站时注入。  
**验证：** 沙箱内只保存假值，真实密钥不出现在环境、命令、文件和日志中。

### **母题二：认证应当绑定请求，而不是绑定环境**

**现象：** Token 一旦进入环境，通常可以被任意代码复用。  
**矛盾：** 环境级凭据权限过于粗粒度。  
**推论：** 授权应绑定请求的具体属性。  
**方案：** 使用 scheme、host、port、method、path 等条件匹配。  
**验证：** 只有符合规则的出站请求能够获得认证信息。

### **母题三：凭据安全必须与网络安全联动**

**现象：** 单独保护 Token 不能限制沙箱访问哪些服务。  
**矛盾：** 即使 Token 不可读，开放网络仍可能扩大攻击面。  
**推论：** 必须同时控制目标地址和认证注入。  
**方案：** 默认拒绝出站网络，加上精确 Credential Vault binding。  
**验证：** 无关 Host 无法访问，相关 Host 也只能在限定路径和方法上获得凭据。

### **母题四：生产级 Agent 需要授权治理，而不仅是执行隔离**

**现象：** Agent 的工具链长、行为不确定、依赖复杂。  
**矛盾：** 传统沙箱只控制进程和文件，无法充分控制凭据使用。  
**推论：** Agent Runtime 必须增加凭据隔离和出站授权层。  
**方案：** 将沙箱、网络策略和凭据代理组合起来。  
**验证：** 凭据使用能够被限制、记录、审计和持续收敛。

---

## **十二、最终抽象**

Credential Vault 的完整架构可以概括为：

```text
不可信执行环境
    ↓
只能发起请求，不能持有真实凭据

受控网络出口
    ↓
检查目标、协议、端口、方法和路径

外部凭据代理
    ↓
仅在请求匹配时注入认证信息

最小权限外部服务
    ↓
最终决定该请求能执行什么操作
```

其核心转变是：

```text
传统模式：
凭据进入沙箱 → 工具读取凭据 → 工具访问服务

Credential Vault：
工具发起请求 → 出口验证请求 → 代理注入凭据 → 服务完成认证
```

因此，Credential Vault 的价值可以用一句话概括：

> **把“谁拥有密钥”的问题，转化为“哪一个请求在什么条件下可以获得认证”的问题。**

这正是 OpenSandbox 从单纯的执行隔离，进一步走向生产级 AI Agent Runtime 的关键改进。
