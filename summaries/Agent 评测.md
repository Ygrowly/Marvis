### **结论：Agent 评测的本质，是把不稳定的智能行为转化为可度量、可定位、可修复、可回归的工程质量。**

完整体系不是“设计一套打分规则”，而是建立从**目标定义、数据构造、执行观测、自动评分、根因分析、修复建议到线上反馈**的质量闭环。其核心原则是：

> **先定义成功，再采集证据；先区分现象，再定位根因；先形成动作，再验证修复。**

## 一、第一性原理：为什么 Agent 必须进行体系化评测

### 1. Agent 质量问题的根源

传统软件通常遵循：

\[
输入 + 固定逻辑 \rightarrow 输出
\]

Agent 更接近：

\[
用户输入 + 上下文 + 模型状态 + 工具环境 + 外部系统 \rightarrow 多步行为 + 最终结果
\]

因此，Agent 同时具有四类不确定性：

| 不确定性 | 表现 | 工程后果 |
|---|---|---|
| 输入不确定 | 用户表达多样、意图隐含 | 测试样本不能只覆盖标准问法 |
| 输出不确定 | 模型存在随机性 | 单次成功不等于稳定成功 |
| 状态不确定 | 多轮上下文持续变化 | 必须评估会话级结果 |
| 环境不确定 | 工具、数据库、网络可能异常 | 必须检查过程和异常恢复 |

这导致 Agent 的错误不是单点错误，而可能是**错误级联**：

\[
意图识别错误 \rightarrow 检索错误 \rightarrow 工具参数错误 \rightarrow 业务动作错误 \rightarrow 错误回复
\]

所以，仅观察最终答案会遗漏两类问题：

1. **结果正确但过程危险**：例如跳过必要的订单状态校验，却偶然返回了正确结论。
2. **结果错误但责任不明**：不知道是意图识别、知识检索、工具调用还是回复生成出了问题。

### 2. 评测体系要解决的三个基本问题

任何成熟的评测系统都必须回答：

#### What：Agent 做得怎么样？

需要量化准确性、稳定性、可靠性、风险和用户体验。

#### Why：为什么做错？

需要从 Trace 和模块输入输出中定位具体责任模块与失败原因。

#### How：如何修复并证明修复有效？

需要将根因转化为明确的工程动作，并通过回归测试验证。

因此，评测平台的目标不是“出一个分数”，而是：

\[
质量评测 = 发现问题 + 解释问题 + 推动修复 + 验证修复
\]

# 二、评测对象：先定义 Agent，再决定评什么

## 1. Agent 类型决定评测重点

不同 Agent 的目标不同，不能用同一套指标评价。

| Agent 类型 | 核心目标 | 重点评测内容 |
|---|---|---|
| 知识问答型 | 正确回答问题 | 事实准确性、证据一致性、引用质量 |
| 任务执行型 | 完成业务动作 | 工具选择、参数、调用顺序、状态变化 |
| 决策推理型 | 做出合理决策 | 规则理解、推理链路、边界处理 |
| 内容生成型 | 产出可用内容 | 完整性、格式、风格、可执行性 |
| 对话型 | 通过多轮交互解决问题 | 上下文、目标保持、情绪、转人工、最终结果 |
| Skill 密集型 | 正确调用并组合能力 | Skill 触发、流程、产物、异常降级 |

评测底层流程可以复用：

\[
执行用例 \rightarrow 采集 Trace \rightarrow 评分 \rightarrow 报告 \rightarrow 根因归类
\]

但“评什么”和“如何判定”必须按业务定制。

## 2. Skill 为什么必须单独评测

端到端结果正确，不代表 Skill 使用正确；端到端失败，也不一定是 Skill 本身的问题。

一个 Skill 至少需要检查四个阶段：

\[
是否触发 \rightarrow 是否正确执行 \rightarrow 产物是否可用 \rightarrow 异常是否能恢复
\]

例如退款 Skill：

- 用户提出退款请求时是否应该触发；
- 是否先查询订单状态；
- 是否正确传入订单号和退款原因；
- 订单已发货或工具失败时是否正确解释、重试或转人工；
- 最终生成的售后单是否真实创建成功。

## 3. 对话 Agent 的特殊评测对象

对话 Agent 不能只评价单轮回答，而要同时评价四个层级：

| 层级 | 核心问题 |
|---|---|
| Turn | 当前这一轮答得是否正确 |
| Session | 整段会话是否最终解决问题 |
| Trace | 执行过程是否符合预期 |
| Outcome | 业务结果是否真正达成 |

原因是：每一轮都“看起来不错”，但如果用户最终仍未解决问题，整体仍然失败。

# 三、评测指标：从“感觉好”转化为可比较的质量标准

## 1. 指标设计的基本逻辑

指标必须满足：

\[
业务目标 \rightarrow 可观察行为 \rightarrow 可判定标准 \rightarrow 可执行动作
\]

指标不仅用于排名，更用于：

- 发布门禁；
- 版本比较；
- 回归检测；
- 问题定位；
- 优化优先级排序。

## 2. 五类核心指标

### 第一类：任务结果指标

回答或任务是否达成目标。

例如：

- 任务完成率；
- 会话解决率；
- 工单闭环率；
- 退款或赔付成功率；
- 最终答案正确率。

这是最接近业务价值的指标，但不能单独使用，因为它无法解释过程风险。

### 第二类：过程与执行指标

检查 Agent 是否按照正确流程完成任务。

例如：

- 是否调用必要工具；
- 工具调用顺序是否正确；
- 参数是否完整、合法；
- 是否正确处理工具返回；
- 是否发生数据库状态变化；
- 是否按照业务 SOP 执行。

### 第三类：交互与体验指标

衡量用户是否容易完成任务。

例如：

- 意图识别准确率；
- 上下文保持率；
- 重复追问率；
- 转人工率；
- 回复相关性；
- 回复完整性；
- 情绪回应质量。

### 第四类：风险与安全指标

关注“看起来正确但实际存在风险”的情况。

例如：

- 是否过度承诺；
- 是否绕过必要校验；
- 是否泄露隐私；
- 是否执行禁用动作；
- 是否错误赔付或退款；
- 是否正确触发 Guardrail；
- 是否在高风险场景下转人工。

### 第五类：稳定性与工程指标

衡量系统是否持续可靠。

例如：

- 连续成功率；
- 至少一次成功率；
- 延迟；
- 超时率；
- 工具异常率；
- 重试成功率；
- 多轮状态一致性；
- 版本回归率。

## 3. P0、P1、P2 分层

| 等级 | 用途 | 示例 |
|---|---|---|
| P0 | 发布门禁 | 合规、资损、关键任务失败、关键工具错误 |
| P1 | 版本比较和优化 | 任务完成率、事实准确率、工具参数正确率 |
| P2 | 体验改善和长期观察 | 回复风格、表达流畅度、轻微延迟 |

P0 不达标时不能通过发布；P1 用于判断版本是否变好；P2 用于长期体验优化。

## 4. 至少一次成功率与连续成功率

设某任务运行 \(N\) 次。

### 至少一次成功率

只要成功一次，就认为任务具备完成可能性：

\[
P_{\text{至少一次}}=\frac{\text{至少成功一次的任务数}}{\text{任务总数}}
\]

它衡量能力上限，适合探索性测试。

### 连续成功率

同一任务每次运行都成功，才算成功：

\[
P_{\text{连续}}=\frac{\text{全部运行均成功的任务数}}{\text{任务总数}}
\]

它衡量生产可靠性，适用于：

- 客服；
- 支付；
- 退款；
- 合规；
- 关键业务流程。

生产系统更关注连续成功率，因为用户不会接受“多试几次总有一次成功”。

## 5. 为什么需要统计检验

版本差异可能来自随机波动，而不是能力变化。因此应同时报告：

- 置信区间；
- 与基线版本的显著性判断；
- 最小可感知变化阈值。

发布判断不应只是：

> 新版本提升了 1 分。

而应判断：

> 该提升是否超过统计噪声，并且是否达到值得发布的业务阈值。

# 四、数据集建设：评测集不是随机样本，而是风险资产

## 1. 为什么不能只随机抽线上数据

线上正常样本通常占多数，真正容易出错的边界场景占比很低。随机抽样会造成**幸存者偏差**：

\[
正常样本多 \neq 系统风险低
\]

因此，评测集必须围绕以下内容主动设计：

- 核心业务路径；
- 高风险流程；
- 关键业务规则；
- 历史 Badcase；
- 长尾表达；
- 异常与工具失败；
- 对抗性输入；
- 线上新分布。

## 2. Golden Set 的作用

Golden Set 是长期稳定复用的核心评测集，用于：

- 版本基线比较；
- 发布门禁；
- 关键能力回归；
- Judge 校准；
- 质量趋势观察。

推荐起步规模为 50—200 条高质量样本，优先覆盖核心路径和高风险边界，而不是盲目追求数量。

## 3. 数据集的四类来源

### 专家设计用例

用于定义标准和期望行为。

例如：

> 用户要求退款，但订单已经发货。Agent 必须先查询订单状态，再解释退款规则或转入售后流程。

### 扩展用例

用于增加表达覆盖。

应先固定结构字段：

- 场景类型；
- 订单状态；
- 用户诉求；
- 期望动作；
- 情绪强度；
- 约束条件。

再由模型生成自然语言表达，避免自由生成导致标准漂移。

### 线上真实数据

来源包括：

- 客服会话；
- 工单；
- 投诉；
- 低满意度样本；
- 监控告警。

### Badcase 回流

例如：

> Agent 未查询订单状态，直接承诺退款一定成功。

Badcase 不只是被动记录，还应转化为回归样本和修复验证样本。

## 4. Skill 用例的设计框架

Skill 评测可以采用：

\[
触发 \rightarrow 核心逻辑 \rightarrow 产物质量 \rightarrow 异常容错
\]

其中：

- **触发**：是否应该调用 Skill；
- **核心逻辑**：是否走对步骤和分支；
- **产物质量**：结果是否完整、正确、可使用；
- **异常容错**：工具失败、参数缺失、边界状态下是否稳定。

## 5. 样本治理

评测集不能无限膨胀。应当：

- 同一问题簇保留代表样本；
- P0、P1 风险长期保留；
- 多版本稳定通过且低风险的样本降级为抽样集；
- 对新意图、新工具、新知识点优先主动采样；
- 所有样本完成脱敏；
- 期望行为和根因标签明确后再入库。

样本入库至少应满足：

1. 失败可复现，或有稳定 Trace 和人工确认；
2. 期望行为明确；
3. 根因标签清楚；
4. 样本具有代表性；
5. 已完成隐私和合规处理。

# 五、评分体系：规则负责确定性，模型负责语义，人工负责争议

## 1. 三类评分器

### 规则 Scorer

适用于可确定判断的硬条件：

- 工具是否调用；
- 参数是否正确；
- 字段是否缺失；
- 状态是否变化；
- 是否执行禁用动作；
- 是否违反调用顺序；
- 引用来源是否存在。

### LLM-as-Judge

适用于语义和策略判断：

- 是否答非所问；
- 解释是否清楚；
- 策略是否妥当；
- 回复是否完整；
- 是否存在过度承诺；
- 是否忠实使用证据。

### Human Scorer

适用于：

- 新业务口径；
- 高风险场景；
- 规则和 Judge 冲突；
- Judge 置信度低；
- 边界样本；
- 自动评分标准尚未稳定的场景。

核心分工是：

\[
规则判硬条件，LLM 判语义策略，人工判争议和高风险
\]

## 2. 为什么不能完全依赖 LLM Judge

LLM Judge 存在以下风险：

- 与被评模型偏好相似风格；
- 评分标准理解不一致；
- 边界样本波动；
- 对内部业务规则不了解；
- 容易给出看似合理但缺乏证据的判断。

因此，Judge 需要具备：

- 明确的分档标准；
- 每个分档的可执行定义；
- reason；
- 边界样本和反例；
- 定期人工校准；
- 多模型对抗评分；
- 稳定性和漏判率监控。

作为参考，Judge 与人工一致率达到约 85% 后，再考虑进入日常自动化。

## 3. 人工评分路由

人工介入不应只依据分数阈值，而应由风险和不确定性共同决定：

```text
自动评分
   ├─ 明确通过 → 自动通过
   ├─ 明确失败 → 自动进入 Badcase
   ├─ 低置信度 → 人工复核
   ├─ 规则/Judge 冲突 → 人工复核
   ├─ 高风险场景 → 人工抽检或终判
   └─ 新模型/新 Prompt/新工具 → 抽样校准
```

## 4. 分层筛查

为了控制成本，可以采用三层结构：

### 粗筛层

使用规则和轻量 Judge，快速识别明显通过、明显失败和存疑样本。

### 精判层

使用完整规则和详细 Judge 标准，确认是否为 Badcase，并输出：

- 问题分类；
- 问题现象；
- 置信度；
- 判定依据。

### 人工复核层

处理：

- 高风险；
- 低置信；
- 规则和 Judge 冲突；
- 业务口径未固化的样本。

## 5. 评分输出不能只有 Pass/Fail

至少应包含：

| 字段 | 作用 |
|---|---|
| 分数 | 衡量质量程度 |
| Pass/Fail | 判断是否通过 |
| 问题分类 | 便于看板统计 |
| 问题现象 | 描述表面错误 |
| 置信度 | 判断是否需要人工介入 |
| 判定依据 | 支持后续 RCA |

注意：**问题现象不等于根因**。

例如：

- 问题现象：事实性错误；
- 可能根因：知识召回失败、证据筛选失败或回复生成错误。

## 6. 假阳性检测

假阳性是“最终答案看起来正确，但过程或风险不合格”。

应额外增加：

- 工具调用顺序检查；
- 必要校验是否完成；
- 关键状态是否真实变化；
- 证据是否真实存在；
- 是否绕过 Guardrail；
- 是否存在过度承诺；
- 是否发生异常但被掩盖。

# 六、Badcase 分析：从错误现象定位到可修复根因

## 1. Badcase 的来源

Badcase 不仅来自离线评测，还可以来自：

- 线上会话；
- 人工质检；
- 投诉工单；
- 低满意度样本；
- 版本回归失败；
- 监控告警；
- 业务主动排查。

这些来源最终应进入统一的 Badcase 任务表和 RCA Pipeline。

## 2. 根因分析的基本链路

\[
证据汇总 \rightarrow 范围收敛 \rightarrow 分模块诊断 \rightarrow 责任判定 \rightarrow 结构化落盘
\]

### 第一步：证据汇总

根据 `sessionId`、`chatId`、`traceId` 或评测运行 ID，收集：

- 用户输入；
- Agent 回复；
- Prompt；
- 模块输入输出；
- 检索结果；
- 工具调用；
- 工具返回；
- 异常；
- 时间和耗时；
- 中间产物；
- 最终状态。

Trace 是 RCA 的事实基础。没有完整 Trace，只能猜测，不能稳定定责。

### 第二步：范围收敛

不能对所有模块逐个排查，应建立：

\[
问题现象 \times 功能模块
\]

例如：

| 问题现象 | 优先排查模块 |
|---|---|
| 答非所问 | 意图识别、Query 改写、知识筛选 |
| 事实性错误 | FAQ 检索、知识召回、回复生成 |
| 过度承诺 | 风险拦截、回复生成 |
| 未澄清关键条件 | 槽位抽取、上下文判断 |
| 工具执行失败 | 工具选择、参数构造、异常处理 |

映射表只用于缩小范围，不能直接等同于最终责任。

### 第三步：分模块诊断

对候选模块逐一检查：

- 输入是否正确；
- 输出是否正确；
- Prompt 是否合理；
- 工具返回是否正确；
- 是否存在异常；
- 是否符合预期规则。

每个模块应输出：

- 问题摘要；
- 关键证据；
- PASS、SOFT_PASS 或 FAIL；
- 改进建议；
- 结构化诊断字段。

### 第四步：责任判定

根据问题现象、模块诊断和根因知识库，输出：

- 问题分类；
- 问题枚举；
- 主责模块；
- 次责模块；
- 责任层；
- 置信度；
- 修复建议。

可采用三层定责策略：

1. 由严重模块结论直接定责；
2. 用规则匹配确定性错误；
3. 由 LLM 汇总复杂链路中的责任传递关系。

### 第五步：结构化落盘

根因不能只保存在报告中，应写入任务记录：

- 问题分类；
- 问题现象；
- 问题枚举；
- 责任层；
- 责任模块；
- 置信度；
- 详细诊断；
- 修复建议；
- owner；
- 验收方式。

## 3. 根因标签体系

标签必须满足：

\[
稳定、可统计、能指向 Owner、能对应行动
\]

可从以下能力域开始：

- 语义理解；
- 上下文管理；
- 知识检索；
- 工具选择；
- 参数构造；
- 流程执行；
- 模型推理；
- 回复生成；
- 风险防控；
- 外部系统异常；
- 评测或数据问题。

问题枚举应比问题分类更细，例如：

- 关键工具未调用；
- 工具调用顺序错误；
- 参数缺失；
- 工具返回误读；
- 证据使用错误；
- 上下文被覆盖；
- 业务规则理解错误；
- 风险拦截遗漏。

## 4. 一个完整示例

场景：

> 用户申请退款，但订单已经发货。Agent 直接承诺“可以退款”，没有查询订单状态。

分析过程：

1. **问题现象**：过度承诺；
2. **规则检查**：订单状态查询工具未调用；
3. **Trace 检查**：退款 Skill 直接生成退款结论；
4. **责任模块**：退款 Skill 或退款流程执行模块；
5. **问题分类**：工具覆盖与执行；
6. **问题枚举**：关键工具未调用；
7. **修复动作**：增加订单状态查询前置条件；
8. **回归用例**：已发货、未发货、拒收、特殊类目等多种状态；
9. **发布门禁**：所有退款场景必须先完成状态校验。

# 七、自动优化：把根因翻译成工程行动

## 1. 为什么泛化建议没有价值

以下建议不可执行：

- 优化 Prompt；
- 提升准确率；
- 加强训练；
- 完善异常处理。

它们没有说明：

- 改什么；
- 谁来改；
- 为什么改；
- 如何验收；
- 改后是否有效。

## 2. 标准行动项

每条优化建议至少包含：

| 字段 | 内容 |
|---|---|
| 失败范围 | 哪些场景失败 |
| 关键证据 | Trace、规则或 Judge 依据 |
| 根因 | 具体责任模块和问题枚举 |
| 修复动作 | 具体改 Prompt、规则、工具或数据 |
| Owner | 运营、算法、工程或业务 |
| 验收标准 | 指标和通过条件 |
| 优先级 | P0、P1 或 P2 |
| 回归集 | 需要重新执行的样本 |

## 3. 不同根因对应不同优化手段

| 根因 | 优先修复方式 |
|---|---|
| 业务口径不明确 | 业务先定规则和边界 |
| 知识缺失或过期 | 修订知识库、增加时效校验 |
| 检索召回不足 | 优化 Query、索引、召回和排序 |
| 工具未调用 | 增加触发条件和前置约束 |
| 参数错误 | 强化 Schema、校验和示例 |
| 流程跳步 | 增加状态机或确定性编排 |
| 回复过度承诺 | 增加证据约束和风险拦截 |
| 模型推理错误 | 优化 Prompt、示例或训练数据 |
| 异常未恢复 | 增加重试、降级和转人工机制 |

## 4. 修复优先级

可以采用四级策略：

1. **规则和流程修复**：适合高风险、确定性错误；
2. **工具与系统修复**：适合接口、状态和执行问题；
3. **Prompt、模型或数据优化**：适合语义和泛化能力问题；
4. **人工兜底或产品改造**：适合复杂、低频、高风险且暂时无法自动化的问题。

通常应优先选择确定性更高、收益更直接、风险更低的方案。

# 八、闭环设计：从 Bug 到生产质量资产

## 1. 完整平台的九类能力

一个成熟的 Agent 评测平台通常包含：

1. 用例与数据集管理；
2. Agent 执行；
3. Trace 采集；
4. 规则与模型评分；
5. 人工复核；
6. Badcase 管理；
7. RCA 根因分析；
8. 优化建议和工单流转；
9. 线上监控与反馈回流。

## 2. 离线和线上必须联动

离线通过不代表线上一定变好。发布阶段至少要同时观察：

### 离线质量信号

- 核心场景通过率；
- P0 风险数；
- 关键工具参数正确率；
- 连续成功率。

### 线上体验信号

- 转人工率；
- 重复追问率；
- 投诉率；
- 满意度；
- 会话解决率。

### 业务结果信号

- 任务完成率；
- 工单闭环率；
- 退款成功率；
- 赔付成功率；
- 实际转化或留存结果。

如果离线指标提升，但线上关键指标恶化，应触发：

- 回滚；
- 降级；
- 扩大人工接管；
- 暂停发布；
- 重新分析分布变化。

## 3. Trace 必须是标准能力

Trace 不能在出问题后临时补采。至少应稳定记录：

- 工具名称；
- 入参；
- 返回值；
- 时间戳；
- 耗时；
- 错误；
- 重试；
- 最终状态。

复杂 Agent 还应记录：

- 计划；
- 检索过程；
- 证据；
- Guardrail；
- Skill 调用；
- 中间产物；
- 状态变迁。

评测环境还应隔离，避免不同用例共享状态，导致结果不可复现。

## 4. 一条 Badcase 应产生三类资产

### 回归用例

防止同类问题再次出现。

### 根因标签

帮助统计问题分布、识别高频责任模块。

### 修复行动项

推动具体改动进入研发流程。

进一步还可以形成三条生产线：

- **数据生产线**：Badcase 转为评测样本和训练数据；
- **知识生产线**：错误反馈转为知识库修订；
- **工程生产线**：根因转为规则、Prompt、工具或代码变更。

## 5. 反馈资产的长期积累

最终应沉淀：

- 用例库；
- Trace 库；
- 根因标签库；
- 修复建议库；
- Judge 校准集；
- 回归集；
- 问题簇和版本演化记录。

这些资产越丰富，后续迭代越不依赖个人经验，也越少依赖临时救火。

# 九、从框架学习法看整套体系

## 1. 定义

Agent 评测是对 Agent 的**结果、过程、风险、稳定性和业务价值**进行系统化验证，并将结果转化为修复和回归行动。

## 2. 机理

Agent 的输出由多个不确定模块共同产生，因此必须：

\[
结果评测 + 过程观测 + 根因分析 + 闭环修复
\]

缺少任何一环，体系都会失效：

- 只看结果：无法定责；
- 只看过程：无法判断业务是否成功；
- 只做分析：不能推动修复；
- 只做修复：无法证明是否有效。

## 3. 边界

这套方法不等于：

- 单纯的模型 benchmark；
- 只看最终答案的质量检查；
- 只依赖人工抽样；
- 只依赖 LLM Judge；
- 只做一次性的上线前测试；
- 用一个通用指标评价所有 Agent。

## 4. 方法

完整方法可以压缩成一条主线：

```text
定义业务成功
→ 分类 Agent 类型
→ 设计 Golden Set
→ 执行并采集 Trace
→ 规则/LLM/人工分层评分
→ 识别 Badcase
→ 汇总证据并缩小范围
→ 分模块诊断
→ 判定根因和 Owner
→ 生成结构化行动项
→ 修复后回归
→ 联动线上监控
→ 将新问题沉淀为质量资产
```

# 十、用“母题驱动的证据闭环”理解全文

全文可以归纳为五个母题。

## 母题一：如何证明 Agent 做对了？

证据包括：

- 最终结果；
- 任务状态；
- 工具返回；
- 数据库变化；
- 用户是否真正解决问题。

结论：不能只看生成文本，必须验证 Outcome。

## 母题二：如何证明 Agent 做得稳定？

证据包括：

- 重复运行；
- 至少一次成功率；
- 连续成功率；
- 置信区间；
- 版本显著性；
- 线上长期指标。

结论：单次成功只是能力存在，连续成功才接近生产可靠性。

## 母题三：如何证明 Agent 的过程安全？

证据包括：

- Trace；
- 工具调用顺序；
- 参数；
- 必要校验；
- Guardrail；
- 异常恢复；
- 外部状态变化。

结论：必须同时检测结果和过程，防止假阳性。

## 母题四：如何知道错在哪里？

证据包括：

- 问题现象；
- 模块输入输出；
- Prompt；
- 检索结果；
- 工具返回；
- 异常日志；
- 规则和 Judge 判断。

结论：先从现象缩小范围，再根据证据进行模块级诊断，不能直接让模型猜责任。

## 母题五：如何保证下次不再错？

证据包括：

- 根因标签；
- 修复行动项；
- 回归用例；
- 版本前后对比；
- 线上反馈；
- 同类问题簇变化。

结论：Badcase 只有进入回归集、规则库、知识库或工程工单，才真正产生长期价值。

---

## 最终抽象

Agent 评测体系可以表示为：

\[
\boxed{
质量 = 结果正确 \times 过程可靠 \times 风险可控 \times 多次稳定 \times 持续可修复
}
\]

其中任一项接近零，整体生产质量都会显著下降。

因此，最重要的设计思想不是“如何把 Agent 打分”，而是：

> **把每一个失败转化为可观察证据，把每一组证据转化为明确根因，把每一个根因转化为可执行修复，再把修复结果转化为下一轮可验证的质量资产。**
