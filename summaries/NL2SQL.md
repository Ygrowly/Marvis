### **结论：这篇文章的核心不是“如何让模型生成 SQL”，而是“如何把企业数仓知识、业务口径和执行约束工程化，使模型能够稳定地生成正确 SQL”。**

其完整方法可以概括为：

> **确定性路由负责缩小问题空间，渐进式知识加载负责控制上下文，标准工作流负责保证过程一致，结构化知识负责保证语义正确，自动化评测负责推动持续改进。**

---

## 一、问题本质：NL2SQL 为什么难

### 1. 定义

NL2SQL 是将自然语言问题转换为可执行 SQL 的系统。

简单场景中，流程是：

> 用户提问 → 模型理解 → 选择表和字段 → 生成 SQL → 执行 → 返回结果

但企业数仓场景并不是单纯的语法转换，而是一个多层决策问题：

\[
\text{自然语言} \rightarrow \text{业务意图} \rightarrow \text{指标口径} \rightarrow \text{数据域} \rightarrow \text{数据表} \rightarrow \text{字段与关联} \rightarrow \text{SQL}
\]

真正困难的不是 SQL 语法，而是中间的语义决策。

### 2. 根本矛盾

企业数仓通常具有以下特征：

- 表数量多，涉及多个业务域；
- 同一个词在不同业务域中含义不同；
- 同一个指标存在多种统计口径；
- 表具有不同粒度和数据时效；
- 明细表、汇总表、结果表的适用场景不同；
- 业务规则往往不写在 DDL 中；
- 错误 SQL 可能语法正确，但业务含义错误。

因此，NL2SQL 的核心评价标准不是：

> SQL 能否执行。

而是：

> SQL 是否使用了正确的业务定义、正确的表、正确的时间范围和正确的计算方式。

---

## 二、第一性原理拆解：系统到底要解决什么

可以把一次取数任务拆成六个基本问题：

| 问题 | 实际含义 | 需要的能力 |
|---|---|---|
| What | 用户想查询什么 | 意图识别 |
| Which domain | 属于哪个业务域 | 跨域路由 |
| Which table | 应该使用哪张表 | 域内选表 |
| What definition | 指标到底如何定义 | 口径理解 |
| How to query | SQL 应该如何生成 | SQL 规划与自检 |
| How to explain | 结果如何被信任和使用 | 执行与解释 |

文章的 V2 架构，正是围绕这六个问题设计的。

---

# 三、V1：为什么从多 Skill 起步，又为什么必须升级

## 1. V1 的方案

V1 按业务域拆分 Skill：

- 交易域
- 业财域
- 广告域
- 流量域
- 内容域
- 供给域
- 商品域
- 服务域
- ODPS 执行 Skill

每个 Skill 都拥有：

- 独立的提示词；
- 独立的知识库；
- 独立的业务规则；
- 独立的 SQL 执行能力。

初期只覆盖约 40 张核心 ADS 表。

## 2. V1 为什么有效

V1 的有效性来自三个条件：

### 第一，知识范围小

每个 Skill 只处理一个业务域，模型面对的候选表较少，干扰信息有限。

### 第二，业务边界清晰

早期主要处理域内问题，例如交易 Skill 处理订单量，广告 Skill 处理广告消耗。

### 第三，知识足够集中

表结构、字段含义和业务口径都放在对应 Skill 中，模型可以在较小范围内完成推理。

因此，V1 验证了一个重要假设：

> 当领域知识完整、提示词约束严格时，LLM 可以生成企业级可用的 SQL。

## 3. V1 为什么不能继续扩展

当表从 40 张扩展到 352 张后，V1 暴露出五个结构性问题。

### 问题一：用户承担了路由成本

用户需要自己判断：

- “收入”属于广告还是业财；
- “供给”属于门店还是商品；
- “转化”属于交易还是流量。

这要求用户理解数仓内部的组织方式，但用户通常只关心业务问题。

**改进原因：**

系统应该理解用户意图，而不是要求用户理解系统架构。

---

### 问题二：外部路由不可调试

多 Skill 依赖 Skill 描述文本进行自动匹配。

这种路由方式存在两个问题：

1. 描述文本无法表达复杂的消歧规则；
2. 路由过程在 Skill 外部，开发者无法观察和精确修改。

例如，“收入”这个词本身不足以决定路由结果，必须结合“投放”“广告主”“结算”“净收入”等上下文。

**改进原因：**

路由是可靠性的关键环节，必须收回系统内部，变成可观察、可调试、可维护的逻辑。

---

### 问题三：跨域查询无法处理

真实业务问题经常跨越多个域：

> 交易订单 + 流量归因 → 分析转化漏斗

如果问题被路由到交易 Skill，它可能不知道流量表的关联规则；如果被路由到流量 Skill，它又可能缺少交易指标口径。

**改进原因：**

业务域是知识组织方式，不应成为问题处理的硬边界。

---

### 问题四：公共逻辑重复维护

日期计算、权限处理、SQL 安全约束、节假日判断和执行协议，被重复写入多个 Skill。

由此产生：

- 修改成本高；
- 容易漏改；
- 不同 Skill 行为不一致；
- 问题难以定位。

**改进原因：**

公共能力必须集中维护，领域知识才应该按域隔离。

---

### 问题五：架构扩展僵硬

新增业务域或重新划分边界时，需要：

- 新建 Skill；
- 调整多个 Skill；
- 修改路由描述；
- 要求用户重新安装或适应。

**改进原因：**

业务边界会变化，架构必须允许业务知识和路由规则独立演进。

---

## 4. V1 到 V2 的关键认知转折

五个问题最终指向同一个根因：

> **路由决策发生在系统控制范围之外。**

因此，V2 不再把“一个业务域对应一个 Skill”作为基本单位，而是改成：

> **一个统一 Skill + 内部确定性路由 + 按需加载领域知识。**

---

# 四、V2：统一 Skill 的四层架构

V2 并不是把所有知识简单塞进一个超大的 `SKILL.md`，而是在统一入口内部进行分层。

## 1. L1：域路由层

### What：做什么

从用户问题中识别：

- 指标；
- 查询视角；
- 维度；
- 时间范围；
- 过滤条件；
- 业务语境。

然后判断问题属于哪个业务域。

### Why：为什么需要

同一个业务词可能对应多个定义。例如：

- 收入：广告收入或财务结算收入；
- 供给：门店供给或商品供给；
- DAU：大盘 DAU 或业务线 DAU；
- 补贴：预估补贴或结算补贴。

仅依赖向量相似度或简单关键词，无法稳定完成消歧。

### How：如何实现

维护确定性域路由表，记录：

- 典型指标关注点；
- 判断要点；
- 业务域边界；
- 易混淆术语；
- 消歧规则；
- 无法判断时的澄清选项。

例如：

- 看“实际成交了多少” → 交易域；
- 看“公司赚了多少钱” → 业财域；
- 出现“投放、广告主、消耗” → 广告域；
- 出现“结算、净收入、UE” → 业财域。

如果仍无法判断，就向用户提供有限选项，而不是提出开放式问题。

### 关键设计

澄清问题应当是：

> 你说的“收入”是指：  
> A. 广告投放收入  
> B. 财务结算收入

而不是：

> 请详细说明你所说的收入是什么意思。

前者降低用户认知负担，也降低交互成本。

---

## 2. L2：知识加载层

### What：做什么

路由确定业务域后，只加载对应领域的知识，而不是一次性加载全部文档。

### Why：为什么需要

全部知识约 30,000 行，而单个问题通常只需要：

- 一个领域；
- 一张或几张候选表；
- 少量公共规则。

全量加载会造成：

- 上下文过长；
- 无关知识干扰；
- 域间定义冲突；
- 模型注意力稀释；
- 成本和延迟上升。

### How：如何实现

采用渐进式加载：

1. 先读取域路由规则；
2. 再读取目标域的 `DOMAIN.md`；
3. 确定候选表；
4. 加载候选表知识卡片；
5. 必要时加载公共维度表或节假日规则。

典型查询只加载约 200—400 行知识。

### 关键机制

> **加载路径即推理路径。**

如果系统选错了表，可以追溯：

- 是否路由到了错误领域；
- 是否没有读取正确的领域文档；
- 是否 DOMAIN.md 的选表规则缺失；
- 是否表文档中的口径描述不清。

这使错误从“模型答错了”变成了可定位的工程问题。

---

## 3. L3：标准工作流层

### What：做什么

所有业务域遵循同一套处理流程。

### Why：为什么需要

V1 中不同 Skill 的行为不一致：

- 有的会确认口径；
- 有的直接生成 SQL；
- 有的会解释数据来源；
- 有的只返回结果。

这会导致：

- 质量标准不统一；
- 用户体验不一致；
- 错误难以比较；
- 评测无法统一。

### How：统一为六步流程

#### Step 1：前置检查

判断问题是否涉及：

- 节假日；
- 特殊日期；
- T+1 数据；
- 数据是否已更新；
- 权限或执行限制。

例如用户问“春节期间”，系统不能简单使用连续自然日，而应读取节假日历。

#### Step 2：一级路由

提取：

- 指标；
- 维度；
- 时间；
- 过滤条件；
- 查询视角。

然后判断所属业务域。

#### Step 3：二级路由

读取目标域的 `DOMAIN.md`，定位：

- 推荐表；
- 备选表；
- 表的迁移状态；
- 表的使用边界；
- 跨域关联规则。

#### Step 4：口径确认

检查是否存在歧义：

- 自然月还是近 30 天；
- 支付金额还是下单金额；
- 含退款还是不含退款；
- 一级类目还是二级类目；
- 首次注册还是首次支付；
- 当日数据还是 T+1 数据。

存在歧义时先澄清，避免生成“看似合理但语义错误”的 SQL。

#### Step 5：选表、生成 SQL、自检

优先级：

\[
ADS > DWS > DWD
\]

即：

- 标准结果查询优先用 ADS；
- 非标准汇总分析降级到 DWS；
- 明细排查才使用 DWD。

SQL 生成后执行五项检查：

1. 是否包含分区条件；
2. 字段是否确实来自所选表；
3. CUBE 表的维度是否正确约束；
4. JOIN 键是否符合知识库定义；
5. 是否设置合理的 `LIMIT`。

#### Step 6：执行与解释

通过 ODPS 执行 SQL，并返回：

- 结果；
- Markdown 表格；
- 数据来源；
- 计算公式；
- 时间范围；
- 过滤条件；
- 口径说明；
- 必要的结果解释。

这样系统输出的不是一段 SQL，而是一份可验证的取数结果。

---

## 4. L4：公共服务层

### What：做什么

集中维护所有领域共享的基础规则：

- 日期计算；
- SQL 安全约束；
- ODPS 执行协议；
- 权限处理；
- 节假日判断；
- 公共维度表索引。

### Why：为什么需要

公共逻辑如果分散在多个领域，会造成重复、漂移和不一致。

### How：如何实现

将公共知识放入：

- `references/common/`
- `SKILL.md` 的公共规则部分

领域 Skill 只保留本领域特有的知识。

### 架构收益

四层架构的职责可以概括为：

| 层级 | 解决的问题 |
|---|---|
| L1 域路由 | 去哪个领域 |
| L2 知识加载 | 读取哪些知识 |
| L3 工作流 | 按什么流程完成 |
| L4 公共服务 | 共享基础能力 |

---

# 五、为什么当前选择确定性路由，而不是直接使用 RAG

## 1. RAG 的基本思路

RAG 通常通过向量检索寻找与用户问题最相似的：

- 表；
- 字段；
- 文档；
- 示例 SQL。

它适合知识量大、语义相对稳定、相似度能够代表相关性的场景。

## 2. 在该场景中的三个问题

### 问题一：业务术语语义重叠

“收入”在不同领域含义不同，但向量表示可能非常接近。

因此：

\[
\text{语义相似} \neq \text{业务口径相同}
\]

Embedding 可以判断词语“像不像”，却不一定能判断业务定义“是不是同一个”。

### 问题二：候选规模仍然可枚举

当前只有：

- 9 个业务域；
- 352 张表；
- 每个域 3—96 张表。

域路由是一个有限分类问题，域内选表也可以通过映射规则完成。

既然候选集合有限，就不必用复杂的概率检索替代可维护的规则表。

### 问题三：可解释性和可调试性不足

规则可以解释：

> 因为出现“广告主”和“投放”，所以进入广告域；因为查询 GMV 总览，所以优先使用 ADS 表。

向量检索通常只能说明：

> 这篇文档与问题相似。

当结果错误时，规则能够定位具体错误行，而相似度检索较难进行定向修正。

## 3. 确定性规则的适用边界

确定性路由并不是永远优于 RAG，而是适用于：

- 业务域数量有限；
- 术语边界清晰或可人工定义；
- 规则具有较高稳定性；
- 结果需要可解释；
- 错误成本较高。

## 4. 未来的混合架构

当表规模达到数千张甚至更多时，可以采用：

> **确定性域路由 + RAG 辅助域内排序**

即：

1. 用规则判断业务域；
2. 在目标域内使用向量检索缩小候选表；
3. 再用规则和表知识进行最终约束；
4. 由模型生成 SQL。

这样保留跨域路由的可靠性，同时利用 RAG 应对域内规模增长。

# 六、知识工程：如何让 352 张表变得“AI-Friendly”

文章最重要的判断之一是：

> **NL2SQL 系统的上限主要由知识质量决定，而不是单纯由模型能力决定。**

## 1. 为什么知识工程是核心

DDL 通常只能提供：

- 表名；
- 字段名；
- 字段类型；
- 分区字段；
- 注释。

但模型真正需要的是：

- 这个字段的业务含义；
- 指标的计算公式；
- 这张表适用于什么场景；
- 什么时候不能使用；
- 如何 JOIN；
- 哪些值必须过滤；
- 数据何时更新；
- 是否包含退款或取消订单。

这些信息大部分不在技术元数据中。

---

## 2. 六节知识卡片

每张表使用一个 Markdown 文件，并统一为六个部分。

### S1：表元数据

包括：

- 完整表名；
- 项目或数据库前缀；
- 数仓层级；
- 数据粒度；
- 分区字段；
- 更新频率；
- 出数时间。

**作用：**

判断这张表是否满足用户的时间和粒度要求。

例如，用户询问今天上午的数据，但表是 T+1 更新，则系统应明确提示数据时效限制。

---

### S2：字段列表

每个字段标记类别：

- `KEY`：主键或分区键；
- `DIM`：维度字段；
- `IDX`：指标字段。

同时附上：

- 中文含义；
- 数据类型；
- 使用说明；
- 特殊限制。

**作用：**

帮助模型快速判断：

- 哪些字段用于过滤；
- 哪些字段放入 `GROUP BY`；
- 哪些字段需要聚合；
- 哪些字段是关联键。

---

### S3：场景映射

说明：

- 适用于什么问题；
- 不适用于什么问题；
- 适合标准查询还是明细分析；
- 是否支持非标准维度；
- 是否存在粒度限制。

**作用：**

避免“表结构正确但场景错误”。

例如，ADS 总览表适合标准指标查询，但不适合明细排查；如果错误使用，会导致结果粒度和业务口径不一致。

---

### S4：关联方式

说明：

- 需要关联哪些维度表；
- 使用什么 JOIN 键；
- 哪些字段不能直接 JOIN；
- 是否存在一对多风险；
- 城市 ID 如何转换为城市名称。

公共关联规则可以集中维护在维度索引中，单表文档只保留指引。

**作用：**

避免模型自行猜测 JOIN 关系。

---

### S5：指标口径定义

这是知识卡片的核心。

每个指标应包含：

- 计算公式；
- 业务定义；
- 是否含退款；
- 是否含取消订单；
- 去重方式；
- 统计粒度；
- 注意事项。

例如：

\[
GMV = \sum pay\_amt
\]

但必须继续说明：

- `pay_amt` 是否为实付金额；
- 是否扣除退款；
- 是否包含补贴；
- 是否按照订单还是用户聚合。

**作用：**

防止 SQL 语法正确但指标语义错误。

---

### S6：SQL 模板

为高频问题提供参考 SQL：

- 标准指标查询；
- 按日期趋势查询；
- 按城市拆分；
- 按业务线汇总；
- 常见 JOIN；
- CUBE 表查询。

模板不是固定答案，而是受约束的最佳实践。

**作用：**

让模型在稳定结构上做参数化调整，减少从零生成 SQL 的错误概率。

---

# 七、元数据 Pipeline：哪些可以自动化，哪些不能

## 1. 第一步：自动拉取技术元数据

从数据地图或 MCP 接口获取：

- 表名；
- 字段名；
- 类型；
- 分区；
- 行数；
- Owner；
- 更新信息。

这一步适合完全自动化。

## 2. 第二步：LLM 生成文档初稿

利用模型根据技术元数据生成：

- 字段中文含义；
- 数仓层级判断；
- 数据粒度；
- 初步场景映射；
- 文档结构。

可以完成约 60\% 的初稿工作。

## 3. 第三步：人工注入业务知识

必须由 BI、数仓或领域专家补充：

- 指标精确定义；
- 字段真实业务含义；
- 业务规则；
- 适用与不适用场景；
- JOIN 约束；
- SQL 最佳实践。

这是无法完全自动化的部分。

原因是：

> 技术元数据描述“数据是什么”，业务知识决定“数据代表什么”。

例如，字段 `pay_amt` 到底是：

- 支付金额；
- 含退款金额；
- 净支付金额；
- 订单实付金额；

仅靠字段名和类型无法可靠判断。

## 4. 第四步：自动化标准检查

检查：

- 字段是否完整覆盖；
- 六个章节是否齐全；
- 命名是否统一；
- 表名是否正确；
- 文档格式是否符合规范。

这种校验可以自动化，但业务准确性仍需人工确认。

---

# 八、知识分层：为什么要按变更频率组织

知识不是一个整体，而是变化速度不同的三类信息。

## 1. 静态层

包括：

- 表结构；
- 字段定义；
- 分区信息；
- 数据粒度。

特点：

- 变化频率低；
- 适合自动监控；
- 发生 DDL 变化时更新。

## 2. 规则层

包括：

- 域路由；
- 术语消歧；
- 域内选表；
- 指标口径；
- 场景映射。

特点：

- 变化频率中等；
- 需要业务迭代；
- 适合快速修改和回归测试。

## 3. 公共层

包括：

- 日期规则；
- 执行协议；
- 权限处理；
- 维度表索引；
- 节假日历。

特点：

- 所有域共享；
- 变化频率低；
- 修改一次即可全局生效。

## 4. 重要方法：写粒度与读粒度分离

维护时：

> 可以按业务域批量修改。

查询时：

> 只按问题加载相关表和规则。

这同时满足：

- 维护效率；
- 上下文效率；
- 错误隔离；
- 变更可控。

---

# 九、质量保障：如何形成证据闭环

可以用“母题驱动的证据闭环”理解整套质量机制。

## 母题一：系统是否真的答对

### 证据

维护 900+ 道测试题，覆盖全部业务域。

### 方法

自动执行：

1. 发送测试问题；
2. 获取生成 SQL；
3. 执行 SQL；
4. 对比标准 SQL 或标准结果；
5. 统计通过率。

### 价值

把“感觉更准了”变成可量化的准确率变化。

---

## 母题二：错在哪里

错误不能只记录为“答案错误”，而要分类：

- 选表错误；
- SQL 语法错误；
- 口径理解错误；
- 用户问题本身模糊但系统未澄清；
- 字段错误；
- JOIN 错误；
- 时间范围错误。

### 证据闭环

\[
\text{错误类型} \rightarrow \text{对应知识层} \rightarrow \text{针对性修复} \rightarrow \text{回归测试}
\]

例如：

- 选表错误 → 修改 `DOMAIN.md`；
- 口径错误 → 修改指标知识卡片；
- SQL 语法错误 → 增加 SQL 模板和约束；
- 未澄清 → 增加路由消歧规则。

---

## 母题三：知识是否已经过时

线上表结构会变化：

- 新增字段；
- 删除字段；
- 字段类型变化；
- 字段注释变化；
- 分区变化。

因此需要 DDL 一致性监控，定期对比：

\[
\text{线上表结构} \leftrightarrow \text{知识库表文档}
\]

如果不一致，就触发差异报告和文档更新。

### 价值

避免“沉默失败”：

- 模型继续引用已删除字段；
- SQL 执行失败；
- 业务口径与线上实现不一致；
- 结果错误但不易察觉。

---

## 母题四：真实用户是否满意

关注三类信号：

1. 用户纠正系统：“不对，应该是……”
2. 多人反复询问同一个问题但答案不一致；
3. 用户提问后直接放弃对话。

这些信号进入问题池，由值班机制定期审查。

### 闭环

\[
\text{用户反馈} \rightarrow \text{问题池} \rightarrow \text{知识或规则修复} \rightarrow \text{回归测试}
\]

这比只依靠离线测试更接近真实使用效果。

---

# 十、AI-Friendly 标准分：把知识质量变成工程指标

知识质量不能只凭专家感觉，因此文章设计了标准分。

主要维度包括：

- 字段覆盖率；
- 口径完整度；
- SQL 模板覆盖率；
- 场景标注率；
- 路由规则完备度。

其基本逻辑是：

\[
\text{准确率问题}
\rightarrow
\text{检查知识标准分}
\rightarrow
\text{定位薄弱维度}
\rightarrow
\text{补充知识}
\rightarrow
\text{重新评测}
\]

这样，知识建设从“编文档”变成可度量、可管理的工程过程。

---

# 十一、五条核心设计原则

## 原则一：确定性优于模糊性

应使用规则约束的环节：

- 域路由；
- 术语消歧；
- 选表；
- 指标口径；
- 分区条件；
- JOIN 规则；
- SQL 安全约束。

模型更适合：

- 理解自然语言；
- 组织查询计划；
- 处理用户表达差异；
- 解释结果。

基本分工是：

> 规则负责可靠性，模型负责灵活性。

---

## 原则二：按需加载优于全量灌入

全量加载的问题不是模型完全读不懂，而是：

- 有效信息比例下降；
- 冲突信息增多；
- 注意力被稀释；
- 推理路径不清晰。

因此，应该用少量路由逻辑换取大规模知识的按需加载能力。

---

## 原则三：知识分层对齐变更频率

变化快的规则应便于修改和回归；变化慢的元数据应自动监控；公共能力应统一维护。

这能同时降低：

- 维护成本；
- 回归风险；
- 知识漂移；
- 多域不一致。

---

## 原则四：标准化优于自由发挥

统一的：

- 文档格式；
- 路由表格式；
- 工作流；
- 输出口径；
- 测试方法；

会限制局部自由度，但能提高整体稳定性。

对于多域、多表、多人协作系统，标准化是质量基线，而不是形式主义。

---

## 原则五：评测驱动优于经验判断

经验可以提出假设，但不能证明方案有效。

更可靠的迭代方式是：

\[
\text{提出改动}
\rightarrow
\text{运行回归测试}
\rightarrow
\text{比较准确率和错误类型}
\rightarrow
\text{保留有效改动}
\]

---

# 十二、方案设计的本质：把概率系统改造成受约束的智能系统

LLM 本质上是概率生成器。直接让它完成全部决策，容易出现：

- 猜测表；
- 猜测指标口径；
- 猜测 JOIN 关系；
- 忽略分区条件；
- 混淆同名业务术语。

文章的方案不是消除模型的不确定性，而是把不确定性限制在适合模型发挥的部分。

可以抽象为：

```text
用户问题
   ↓
确定性域路由
   ↓
确定性知识加载
   ↓
确定性口径检查
   ↓
模型生成查询计划和 SQL
   ↓
规则化 SQL 自检
   ↓
执行引擎验证
   ↓
结构化结果解释
```

其中：

- 路由是规则控制；
- 知识加载是结构控制；
- 口径是业务约束；
- SQL 生成由模型完成；
- 执行结果提供事实验证；
- 反馈推动知识更新。

---

# 十三、边界与未解决问题

## 1. 取数与分析仍然分离

取数解决：

> 查到数据。

分析解决：

> 解释为什么变化。

例如：

> GMV 为什么下降？哪些城市、业务线或渠道造成了下降？

这需要：

- 取数知识；
- 指标口径；
- 维度关系；
- 因果分析；
- 归因方法。

目前取数 Skill 和分析 Skill 的知识库独立维护，存在重复建设问题。

---

## 2. 树形知识结构不是自然结构

当前知识按以下方式组织：

```text
业务域
 └── 表
      └── 字段
```

这利于按路径加载，但知识实际更像图：

- 一张表引用另一张表；
- 一个指标依赖多个字段；
- 一个业务规则跨越多个域；
- 一个维度表被很多事实表共享；
- 一个口径变化影响多个文档。

因此，未来需要：

> 以图的形式管理知识，以树的形式加载知识。

---

## 3. 知识冲突和过时检测仍需增强

需要自动发现：

- 一个术语在不同域中的定义冲突；
- 指标定义修改后，引用方是否同步更新；
- 一个表被替换后，旧表文档是否仍被使用；
- 不同文档是否存在相互矛盾的 JOIN 规则。

---

## 4. 端到端评测仍不完整

SQL 准确率并不能完全代表用户体验，还需要评价：

- 是否正确理解问题；
- 是否及时澄清；
- 解释是否清楚；
- 口径说明是否完整；
- 交互是否顺畅；
- 结果是否便于决策。

未来评测对象应从：

\[
\text{SQL 正确率}
\]

扩展到：

\[
\text{端到端 Agent 使用质量}
\]

---

# 十四、最终方法论抽象

这篇文章可以抽象为一个适用于企业智能体的通用公式：

\[
\text{可靠智能体}
=
\text{领域知识}
+
\text{确定性约束}
+
\text{按需检索}
+
\text{标准工作流}
+
\text{执行验证}
+
\text{持续评测}
\]

更具体地说：

1. **先拆问题，不要先选模型。**  
   明确哪些步骤需要理解，哪些步骤必须确定。

2. **把业务知识结构化。**  
   不要只提供表名和字段名，还要提供口径、边界、适用场景和模板。

3. **把路由收回系统内部。**  
   路由决定后续上下文，必须可观察、可解释、可修改。

4. **把上下文设计成加载路径。**  
   知识库不是文档仓库，而是模型的推理路径。

5. **让模型负责灵活部分，让规则负责关键部分。**  
   不要让模型猜测高风险业务决策。

6. **让每次错误都能定位到具体层级。**  
   错误必须可以归因到路由、知识、口径、SQL 或交互。

7. **用评测而不是感觉驱动演进。**  
   每次修改都应有测试、指标和错误分类作为依据。

这也是文章标题中“架构突破与工程实践”的真正含义：突破点不在于使用了更强的模型，而在于重新设计了模型与企业知识、规则和执行系统之间的关系。
