### **结论：BP Claw 的本质，是把“非标准业务需求”转化为“AI 编码可执行的结构化输入”，从源头提升实时数仓 AI Coding 的确定性。**

它并不是单纯的 PRD 生成器，而是连接产品需求与 FlinkSpec AI 工程框架的中间层：通过知识召回、需求结构化、质量评分和评审流程自动化，将经验、约束和业务口径提前固化，减少后续反复沟通、编码阻塞和返工。

## 一、问题的第一性原理

### 1. 根本矛盾：AI Coding 的上限取决于输入质量

AI 编码的基本链路是：

```text
业务意图 → 需求文档 → 技术定义 → SQL/代码 → 验收上线
```

每一层都会放大上一层的不确定性。

如果需求中存在以下问题：

- 指标定义不完整；
- 统计粒度不明确；
- 数据源和字段缺失；
- 口径存在歧义；
- 验收标准不清；
- 用数链路没有说明；

那么后续系统只能自行推断。AI 会选择“看起来合理”的实现，但不一定符合团队真实业务语义。

因此，许多 AI Coding 问题并不首先是模型能力不足，而是输入缺少可执行约束。

### 2. 需求质量的本质：减少自由度

一份好的实时数仓 PRD，不是文字写得多，而是能够减少实现空间中的歧义。

可以抽象为：

```text
需求质量 = 业务信息完整度 + 技术约束明确度 + 验收可验证性
```

需求越模糊，AI 的可选实现越多，错误概率越高；需求越结构化，AI 的推理空间越小，生成结果越稳定。

BP Claw 的核心作用，就是把隐含信息变成显式约束。

## 二、BP Claw 的定义、定位与边界

### 1. 定义

BP Claw 是面向实时数仓场景的 AI 数据 BP，负责：

```text
原始 PRD
→ 需求理解
→ 业务与技术信息提取
→ 知识召回
→ 口径补全与歧义标注
→ 标准化 PRD
→ 质量评分
→ 自动组织评审
```

### 2. 在 FlinkSpec 中的定位

![[Pasted image 20260808152544.png]]

FlinkSpec 将实时数据开发拆成多个阶段，并通过门控机制控制质量。BP Claw 位于最上游的需求澄清阶段。

```text
BP Claw
   ↓
高质量标准化 PRD
   ↓
FlinkSpec Intake
   ↓
Define
   ↓
Flink-SQL Agent 编码
   ↓
Review / 验收
```

它解决的是“进入工程流程前，需求是否已经足够明确”的问题，而不是替代 FlinkSpec 的编码、测试或验收能力。

![[Pasted image 20260808152559.png]]

### 3. 明确边界

BP Claw：

- 可以提取原文已有信息；
- 可以召回历史知识和既有决策；
- 可以识别歧义并提出补充要求；
- 可以将需求转成统一结构；
- 可以对文档质量进行评估。

BP Claw 不应：

- 凭空创造业务口径；
- 替用户决定未确认的指标定义；
- 将建议伪装成事实；
- 用评分结果强制阻塞所有流程；
- 直接替代专业评审和最终验收。

其原则是：

> 能确认的信息结构化，不能确认的信息标记，存在歧义的信息保留并提示。

## 三、典型问题：为什么“SQL 能跑”仍然可能是错的

文章中的广告曝光案例揭示了实时数仓最典型的语义问题。

一次曝光可能对应多个商家，因此存在两种都合理、但语义不同的统计方式：

```text
平台口径：一次曝光 = 1
商家口径：一次曝光对应 N 个商家 = N
```

如果同一个字段同时承载两种语义，便会出现：

```text
商家明细加总 ≠ 平台总量
```

进一步会导致 CTR、CVR、ROI 等衍生指标失真。

### 为什么传统 Code Review 难以发现

因为两种 SQL 实现都可能：

- 语法正确；
- 逻辑完整；
- 能够正常运行；
- 产出看似合理的数据。

真正的问题不是代码错误，而是业务语义没有在需求阶段明确。

例如，下面两种操作都可能合法：

```sql
UNNEST(advertiser_id_list)
```

或：

```sql
保留原始流量粒度后聚合
```

但它们代表完全不同的指标口径。

### BP Claw 的改进方式

BP Claw 在需求阶段识别：

- 指标的统计对象；
- 指标的聚合粒度；
- 是否需要展开主体；
- 平台口径和主体口径是否需要拆分；
- 明细加总与平台总量是否允许一致；
- 不同场景下应使用哪个字段。

它将这些内容写入标准化 PRD，作为 FlinkSpec 的显式输入。

因此，解决路径从：

```text
写完 SQL → 发现数据异常 → 回溯口径
```

变成：

```text
建模前明确口径 → 生成受约束的 SQL → 降低语义错误
```

## 四、产品设计：为什么选择“嵌入工作流”

### 1. 产品目标

BP Claw 面向两类核心角色：

- 产品经理：提交原始需求，不必学习复杂模板；
- 数据开发与评审人：获得结构化、可执行、可评审的需求文档。

它要解决的不是“不会写文档”，而是：

- 产品表达与技术执行之间存在信息损耗；
- 需求评审需要反复拉群和转发；
- 需求质量依赖个人经验；
- AI 工具无法稳定消费非标准输入。

### 2. 三条设计原则

#### 原则一：嵌入现有场景

用户直接在飞书群中：

```text
@机器人 @评审人 + PRD 链接
```

不需要进入新系统，也不需要学习新操作。

**原因：** 新工具带来的学习成本和流程切换成本，可能抵消 AI 带来的效率收益。

#### 原则二：产品经理零感知提效

产品经理只提交原始 PRD，系统自动完成：

- 读取文档；
- 结构化转换；
- 质量评估；
- 创建评审群；
- 邀请相关人员；
- 发送文档和报告。

**原因：** 如果让上游用户先按照复杂格式重写需求，工具就把成本转移给了最需要被帮助的人。

#### 原则三：评分是参照，不是硬门槛

评分用于：

- 暴露缺失信息；
- 建立质量意识；
- 追踪业务域质量；
- 沉淀优秀样例。

评分不直接阻塞流程。

**原因：** 早期强制卡点会引发抵触，降低使用率；先建立度量体系，再逐步提升质量基线，更容易落地。

## 五、目标输出：实时数仓 PRD 应包含什么

实时数仓 PRD 的核心不是普通产品描述，而是要能够直接支持数据建模和编码。

文章将其抽象为七类内容：

1. **业务背景与目标**  
   为什么建设，解决什么问题，产生什么业务价值。

2. **角色—页面—指标矩阵**  
   谁在什么场景下查看什么指标。

3. **指标定义**  
   指标名称、含义、计算逻辑、统计对象和聚合方式。

4. **数据源与字段**  
   使用哪些事件流、维度表、字段和关联关系。

5. **技术口径**  
   时间语义、去重逻辑、Join 类型、窗口、延迟和数据处理方式。

6. **用数链路**  
   指标如何被查询、消费、下钻或用于后续计算。

7. **验收标准**  
   如何判断实现正确，包含样例、边界和数据校验方式。

产品原始 PRD 通常只覆盖其中一部分，尤其容易缺失技术口径和验收标准。BP Claw 的重点，就是围绕这些缺失项完成转换和提示。

## 六、核心能力一：智能需求转化

### 1. What：做什么

智能需求转化将非标准 PRD 转换成实时数仓可消费的标准文档。

其工作过程可以抽象为：

```text
读取原始文档
→ 识别业务对象
→ 提取角色、页面、指标和场景
→ 识别数据源与字段
→ 召回历史知识
→ 判断歧义与缺失
→ 填充标准模板
→ 输出待补充项
```

### 2. Why：为什么需要

原始 PRD 往往存在：

- 同一指标多种叫法；
- 业务目标与技术实现混在一起；
- 只描述页面，不描述数据粒度；
- 只描述结果，不描述验收方式；
- 技术字段和数据源没有对应关系；
- 历史决策没有被复用。

如果直接交给 AI Coding，模型需要同时完成需求理解、业务推断、技术设计和代码生成，任务复杂度过高。

需求转化将这些任务前置并拆开，降低编码阶段的认知负担。

### 3. How：如何实现

#### 第一步：原文忠实提取

只提取原始文档明确表达的内容，不进行无依据补全。

#### 第二步：结构化归类

将内容映射到固定模块，例如：

```text
业务背景
角色与页面
指标定义
数据源
技术口径
用数链路
验收标准
```

#### 第三步：历史知识召回

通过 OpenViking 等知识库召回：

- 历史建模文档；
- 字段定义；
- 同类需求；
- 历史踩坑记录；
- 已确认的业务决策；
- 团队通用约束。

#### 第四步：歧义检测

重点检查：

- 一个指标是否存在多个统计粒度；
- 是否同时存在平台口径和主体口径；
- 指标名称与计算方式是否一致；
- 明细加总是否应等于总量；
- 维度展开是否会造成重复计数；
- 时间范围和时间语义是否明确。

#### 第五步：输出待补充项

对于缺失内容，使用结构化标记：

```text
待补充：统计时间口径
待确认：是否按商家维度展开
待明确：平台侧与商家侧是否使用不同指标字段
```

这比模型自行猜测更安全、更可审查。

## 七、核心能力二：PRD 质量评分

### 1. What：做什么

评分器对标准化 PRD 进行多维检查，输出：

- 总分；
- 分项得分；
- 缺失项；
- 风险项；
- 改进建议；
- 是否具备执行条件。

### 2. 五大评分维度

文章将评分拆分为五个维度，核心关注点包括：

- 业务完整性；
- 指标定义质量；
- 数据与技术口径；
- 用数链路；
- 验收标准。

评分的重点不是产生一个看似精确的数字，而是将“质量问题”变成可定位、可追踪的诊断信息。

### 3. 三条关键规则

#### 技术口径具有否决权

技术口径低于阈值时，即使总分较高，也标记为不可执行。

**原因：** 业务描述写得完整，并不代表数据开发可以开始。如果缺少粒度、去重、Join、时间语义等技术信息，Flink-SQL Agent 仍无法可靠编码。

#### 缺少验收标准直接扣分

验收标准完全缺失或严重不足，会产生较大扣分。

**原因：** 没有验收标准，就无法判断生成结果是否正确，也无法形成自动化闭环。

#### 允许维度溢出，但总分不超过 100

允许某个关键维度表现突出，以鼓励高质量内容；同时限制总分上限，避免评分失真。

### 4. 评分的边界

评分不等于事实，不等于最终审批，也不等于流程准入。

它更适合承担三种作用：

```text
诊断工具
对比工具
运营度量工具
```

## 八、核心能力三：自动拉群

### 1. What：做什么

用户在已有飞书群中触发指令后，BP Claw 自动：

```text
读取 PRD
→ 生成标准化文档
→ 进行质量评分
→ 创建评审群
→ 邀请成员
→ 发送文档与报告
```

### 2. Why：为什么不是只生成文档

如果系统只生成文档，用户还要手动：

- 找评审人；
- 创建群聊；
- 转发文档；
- 解释处理结果；
- 通知相关人员。

这会形成“工具输出”和“实际工作流”之间的断裂。

自动拉群将文档生成直接连接到评审动作，使工具从“内容生成器”变成“流程执行器”。

### 3. 设计价值

自动拉群减少了三个摩擦：

- 操作摩擦：无需重复创建群和发送资料；
- 协作摩擦：相关人员自动进入同一上下文；
- 认知摩擦：评审人直接看到标准文档和问题报告。

## 九、技术方案：如何控制 Token、稳定性和复杂度

## 1. 分段生成：把大任务拆成小事务

### 问题

长 PRD、多个指标和复杂模板一次性生成，会导致：

- Token 超限；
- 请求超时；
- 输出截断；
- 失败后需要全部重来；
- 用户无法判断系统是否仍在运行。

### 方案

采用分段生成：

```text
先写文档骨架
→ 分批生成指标模块
→ 定期发送进度
→ 最后补充验收标准和用数链路
```

例如每次处理 3～5 个指标，并在写入后反馈进度。

### 改进原因

它将：

```text
一次大事务
```

拆成：

```text
多个可恢复的小事务
```

收益包括：

- 降低单次调用失败概率；
- 失败时保留已有结果；
- 减少重复上下文传递；
- 增强用户对处理状态的感知。

---

## 2. 分层 Skill：把复杂能力拆开

BP Claw 没有将所有逻辑放入一个超长 Prompt，而是采用编排者加多个 Skill 的模式。

可以抽象为：

```text
编排者
├── 需求转化 Skill
├── 质量评分 Skill
└── 流程执行 Skill
```

每个 Skill 负责相对独立的任务，并独立管理上下文。

### 改进原因

单一大模型上下文容易出现：

- Token 膨胀；
- 任务边界模糊；
- 输出格式不稳定；
- 错误定位困难；
- 修改一个能力影响其他能力。

分层后，能够实现：

- 职责分离；
- 上下文隔离；
- 独立调试；
- 局部重试；
- 更清晰的失败处理。

---

## 3. 模板化 Prompt：限制输出自由度

模板化设计包括：

- 明确字段；
- 固定模块；
- Markdown 表格；
- Few-Shot 示例；
- 指定输出边界；
- 禁止额外扩写。

### 改进原因

对于企业内部场景，输出“有创意”通常不是目标，稳定、完整、可解析才是目标。

模板通过减少输出自由度，换取：

- 格式稳定；
- 字段完整；
- 内容可比较；
- 结果可被下游系统直接消费；
- 更少的冗余 Token。

---

## 十、稳定性设计：如何避免幻觉

### 1. 核心原则：真实性优先于完整性

在需求转化中，错误补全比信息缺失更危险。

因此系统应遵循：

```text
缺失 ≠ 可以猜测
建议 ≠ 已确认事实
相似案例 ≠ 当前需求结论
```

### 2. 四层防幻觉机制

#### 第一层：源材料约束

要求所有确定性内容都能在原文或可信知识库中找到依据。

#### 第二层：标记代替猜测

无法确定时，必须输出：

- 缺失内容；
- 具体影响；
- 建议补充方向；
- 待业务确认的问题。

#### 第三层：独立质量复核

需求转化与质量评分使用相对独立的 Skill，让评分器对生成结果进行第二次检查。

重点识别：

- 逻辑矛盾；
- 口径冲突；
- 模块缺失；
- 内容不合理；
- 业务和技术定义不一致。

#### 第四层：API 参数校验与重试

调用飞书等外部接口前，校验必填参数，并对可恢复错误执行重试。

这解决的是工程稳定性问题，而不是模型幻觉问题，但两者共同决定用户最终体验。

## 十一、领域知识注入：为什么通用 LLM 不够

实时数仓有大量领域概念，例如：

- 去重视图；
- Lookup Join；
- 时间语义；
- 流维表关联；
- `sink.properties.columns`；
- 指标粒度；
- 事件时间与处理时间；
- 多主体展开；
- 延迟与数据完整性。

通用模型即使理解字面含义，也不一定理解团队的具体约束和历史决策。

因此 BP Claw 使用三种方式增强领域能力：

### 1. 领域知识注入

在 Skill 中解释实时数仓中的关键概念和使用边界。

### 2. 模板驱动

通过固定模块限制模型只关注与实时数仓相关的信息。

### 3. Few-Shot 示例

提供真实的标准化 PRD，展示：

- 什么是合格指标定义；
- 如何表达粒度；
- 如何描述技术口径；
- 如何写验收标准；
- 如何标记待补充项。

### 最关键的知识来源

BP Claw 与通用 AI Coding 的根本差异，不只是 Prompt 更长，而是知识来源不同：

```text
通用 AI Coding：
基于通用语言知识推断

BP Claw：
基于团队历史决策、字段定义和踩坑经验进行约束
```

这使系统能够复用组织经验，而不是每次重新猜测。

---

## 十二、长文档与多 Skill 协调

### 1. 长文档处理

当 PRD 超过模型上下文或接口处理能力时，采用：

- 更长的超时时间；
- 分批处理指标；
- 分段写入文档；
- 进度消息；
- 失败后从已完成位置继续。

### 2. Skill 串行编排

推荐顺序是：

```text
Step 1：读取和解析原始 PRD
Step 2：生成标准化 PRD
Step 3：执行质量评分
Step 4：创建评审群并发送结果
```

规则是：

```text
前一步成功后，才执行下一步
```

### 3. 为什么评分失败不阻塞

评分是辅助能力，而标准化文档和评审群是主流程。

因此：

- 文档生成失败：主流程失败；
- 评审群创建失败：需要重试或人工处理；
- 质量评分失败：可以发送文档，但注明评分未完成。

这体现了功能优先级设计：

```text
核心交付能力 > 辅助诊断能力
```

## 十三、BP Claw 与 FlinkSpec 的价值闭环

完整链路是：

```text
原始 PRD
→ BP Claw 需求转化
→ 口径和约束显式化
→ 标准化 PRD
→ FlinkSpec Intake
→ Define
→ Flink-SQL Agent 编码
→ Review
→ 验收上线
```

BP Claw 的价值不在于单独生成一份更漂亮的文档，而在于改善下游每个阶段的输入条件。

### 关键传递关系

```text
PRD 信息完整
→ Intake 少返工
→ Define 更快通过
→ Agent 更少阻塞
→ SQL 更少返工
→ 验收更容易自动化
```

### 文章给出的经验性结论

文章指出，PRD 质量每提升 10 分，FlinkSpec 编码阶段效率约提升 30%。这一结论应理解为该团队实践中的经验数据，而不是普适定律。它说明需求质量与编码效率之间存在显著的正相关关系。

## 十四、落地运营：为什么产品能力还不够

单次生成工具容易使用，但难以持续改变组织习惯。要让 BP Claw 真正落地，还需要运营机制。

### 1. 域级成熟度评分

按业务域追踪 PRD 质量，识别不同团队的成熟度差异。

作用是把个体问题转化为组织层面的改进对象。

### 2. 质量趋势追踪

持续收集评分结果，观察：

- 质量是否提升；
- 哪些缺失项反复出现；
- 哪些业务域长期偏低；
- 哪些改进措施有效。

这使 PRD 质量从一次性评价变成持续指标。

### 3. 最佳实践沉淀

将高分 PRD、常见问题和改进模板沉淀为知识资产：

```text
优秀案例库
→ 扣分项指南
→ 标准补充模板
→ 新人培训材料
→ 知识库持续增强
```

形成：

```text
使用工具
→ 产生高质量案例
→ 沉淀组织知识
→ 提升后续生成质量
```

这是 BP Claw 的长期复利机制。

## 十五、用“母题—证据—闭环”理解全文

### 母题一：AI Coding 的问题首先是输入问题

**证据：**

- 非标准 PRD 导致需求反复澄清；
- 技术口径缺失导致 Agent 阻塞；
- 验收标准不清导致后期返工；
- SQL 正确但业务口径错误。

**结论：**

应把优化点前移到需求源头，而不是只优化代码生成器。

---

### 母题二：业务语义必须显式化

**证据：**

- 平台口径与商家口径可能同时存在；
- 多主体展开会改变统计粒度；
- 不同实现都可能通过语法和代码检查。

**结论：**

代码审查无法替代需求语义确认，指标粒度、去重方式和聚合边界必须进入 PRD。

---

### 母题三：企业 AI 的核心竞争力是组织知识

**证据：**

- OpenViking 召回历史建模文档；
- 复用字段定义和历史踩坑记录；
- 将既有决策转化为当前需求的约束。

**结论：**

企业 AI 不应只依赖通用模型推理，还要把组织历史经验转化为可检索、可执行的知识资产。

---

### 母题四：自动化必须嵌入现有工作流

**证据：**

- 用户通过飞书群直接触发；
- 系统自动建立评审群；
- 文档、评分和成员同步到位。

**结论：**

降低使用门槛比增加功能数量更重要。真正的自动化不仅生成内容，还要完成内容后的协作动作。

---

### 母题五：质量控制应“可见但不过度阻塞”

**证据：**

- 技术口径采用一票否决；
- 总分本身不作为强制门槛；
- 评分失败不阻塞标准化文档和评审群。

**结论：**

不同质量问题需要分级处理：核心执行条件必须严格控制，辅助性指标则应主要用于反馈和改进。

## 十六、可迁移的方法论

这套方案可以抽象为一个通用的企业 AI 落地框架：

```text
1. 找到下游自动化失败的最早原因
2. 将隐含约束前移到上游输入
3. 把非标准输入转成标准中间制品
4. 用组织知识库补充历史决策
5. 对缺失信息标记而不是猜测
6. 将复杂任务拆成可恢复的小步骤
7. 将能力拆成独立 Skill
8. 用评分和反馈持续改进输入质量
9. 将工具嵌入现有协作流程
10. 把高质量结果沉淀为新的组织知识
```

其通用闭环是：

```text
输入标准化
→ 约束显式化
→ AI 执行
→ 自动评估
→ 人工确认
→ 结果沉淀
→ 反哺下一次执行
```

## 十七、最终抽象

BP Claw 的整体逻辑可以压缩成四句话：

1. **What：** 它是实时数仓场景的 AI 需求转换与评审协作工具。  
2. **Why：** AI Coding 的不稳定，很多时候源于 PRD 不完整、口径不清和验收不可验证。  
3. **How：** 通过模板化转换、知识召回、歧义标注、质量评分、分段生成和自动拉群，构造高质量中间制品。  
4. **Boundary：** 它不替业务猜测，也不替代最终评审，而是把不确定性提前暴露并转化为待确认事项。  

因此，BP Claw 真正改变的不是“写 PRD 的速度”，而是实时数仓开发链路中信息流动的质量：

```text
模糊需求
→ 显式语义
→ 可执行约束
→ 稳定编码
→ 可验证交付
```
