
### **结论：文章的核心不是“如何搭建多 Agent 聊天室”，而是探索一种让 AI 具备持续判断、协作修正、执行验证和业务自迭代能力的组织结构。**

其基本路径是：

> **共享上下文 → 多角色判断 → 公开修正 → 任务结构化 → 真实执行 → 证据沉淀 → 记忆更新 → 持续迭代**

文章认为，单点自动化和预设流程只能提升执行效率；只有当 AI 能围绕目标自主拆解问题、识别风险、协调角色、执行任务并根据结果修正方案，才接近真正的 AI Native 组织。

## 一、问题定义：AI 为什么“会做事”，却不一定“会决策”

### 1. What：文章试图解决什么问题

文章讨论的是：

> **如何让多个 AI Agent 在共享上下文中产生比单个 Agent 更高质量的判断，并将判断转化为可执行、可验证、可持续迭代的业务闭环。**

具体包括：

- 从用户目标出发，而不是从固定需求出发；
- 自动识别需要哪些专业角色；
- 让产品、架构、开发、QA、运维、数据等角色互相补充；
- 将讨论结果转化为任务、依赖、执行动作和验收证据；
- 根据执行结果修正原有决策；
- 将有效经验沉淀为可检索、可失效的记忆。

### 2. Why：为什么传统自动化不够

传统 AI 工程往往解决的是：

> **如何把已经定义好的流程自动执行。**

例如：

```text
需求输入 → 任务拆解 → 代码生成 → 测试 → 部署
```

它的问题在于，流程本身由人预先定义，AI 只负责执行流程节点。

但真实业务通常具有以下特征：

- 需求会在讨论中变化；
- 关键边界在实现过程中才暴露；
- 架构风险可能只有专家角色能发现；
- 测试标准可能在开发前并不完整；
- 发布路径可能因环境、资源或中间件条件发生变化；
- 原始问题可能进一步演化为产品需求或代码缺陷。

因此，真正困难的不是“如何执行下一步”，而是：

> **系统如何判断下一步是什么，以及是否需要改变原来的路径。**

## 二、第一性原理：从单体智能到协作智能

## 1. 第一层涌现：语言中产生智能

单个 token 没有智能，单句话也没有完整智能。

但大量文本、知识、语义关系、推理过程和行动描述经过训练后，模型获得了：

- 语言理解；
- 知识关联；
- 问题分解；
- 推理和规划；
- 工具调用；
- 代码生成；
- 一定程度的业务判断。

这可以理解为：

```text
大量局部语言关系
        ↓
模型内部形成复杂表示
        ↓
出现单个词语或句子本身不具备的能力
```

文章将其称为“从语言中涌现智能”。

## 2. 第二层涌现：上下文中产生协作判断

单个 Agent 通常只拥有局部视角：

- 产品关注目标和边界；
- 架构关注系统结构和风险；
- 开发关注实现路径和成本；
- QA 关注正确性和可验证性；
- 运维关注部署、资源和线上风险；
- 数据研发关注数据口径和链路可靠性。

如果这些 Agent 各自独立工作，结果只是多个局部判断的集合。

如果它们共享同一份上下文，并不断将判断写回公共空间，就可能产生更高层次的协作判断：

```text
局部视角
  ×
共享上下文
  ×
相互修正
  ×
执行反馈
  ↓
整体判断质量提升
```

核心不在于 Agent 数量，而在于：

> **不同视角之间是否产生了新增信息。**

---

## 三、核心定义：什么是 Agent Room

### 1. 定义

Agent Room 是一个共享上下文的多 Agent 协作空间。

它不是简单的群聊，也不是预设好的专家团队，而是让多个角色：

- 进入同一个问题空间；
- 看到完整上下文；
- 根据自身专业判断是否介入；
- 发现问题时主动补充；
- 对其他角色的判断进行修正；
- 将共识沉淀为任务和产物；
- 通过真实运行环境执行；
- 用证据验证完成情况。

### 2. 与普通多 Agent 系统的区别

普通多 Agent 系统通常以“任务分发”为核心：

```text
总控 Agent
  ↓
拆分任务
  ↓
分发给不同 Agent
  ↓
汇总结果
```

Agent Room 以“上下文共享”为核心：

```text
所有相关 Agent
       ↓
共享完整上下文
       ↓
各自判断是否有新增价值
       ↓
相互补充与修正
       ↓
形成共识
       ↓
沉淀为可执行结构
```

两者的核心问题不同：

| 类型 | 核心问题 |
|---|---|
| 传统编排 | 下一步由谁执行 |
| Agent Room | 谁需要看到同一份上下文，以及共享后会产生什么新判断 |

## 四、演进过程：为什么需要从流程自动化转向协作涌现

## 1. 第一阶段：流程自动化

最初的系统将研发拆为固定阶段：

```text
PRD
→ 需求澄清
→ 技术方案
→ 代码生成
→ 代码评审
→ 知识沉淀
```

每个阶段由一个 Agent 生成对应产物。

### 优点

- 流程清晰；
- 阶段边界明确；
- 产物格式统一；
- 状态可追踪；
- 容易工程化。

### 根本局限

- 流程必须事先定义；
- AI 只能在既定节点中执行；
- 无法自主改变流程；
- 不能主动发现跨角色问题；
- 不能根据现场信息重组任务。

因此，它本质上仍然是：

> **人定义流程，AI 执行流程。**

## 2. 第二阶段：全链路 Agent 自动化

随着 Agent 框架和工具能力增强，系统可以自动：

- 读取需求；
- 识别多应用仓库；
- 推断技术栈；
- 生成配置；
- 拆分跨应用任务；
- 修改代码；
- 运行测试；
- 查询日志和数据库；
- 创建分支和环境；
- 执行部署和验证。

这一步实现了：

> **AI 可以接管一条完整流程。**

但它仍不等于业务自迭代，因为它主要解决的是：

```text
给定流程的自动执行
```

而不是：

```text
根据目标自主生成、修改和优化流程
```

## 3. 第三阶段：协作涌现

Agent Room 的出现，是因为系统发现：

- 单个 Agent 很难覆盖全部业务信息；
- 中央调度者会裁剪上下文；
- 任务拆分可能在最初就判断错误；
- 关键风险常常由非当前执行角色发现；
- 讨论如果没有任务和证据，容易停在口头共识。

因此，系统转向：

> **先共享上下文并形成判断，再将共识沉淀为任务结构。**

## 五、两个案例：协作涌现如何实际发生

## 案例一：需求自迭代

### 表面流程

系统可以自动完成：

```text
创建变更
→ 创建分支
→ 创建项目环境
→ 修改前后端代码
→ 构建
→ 部署
→ 测试
```

这些属于流程自动化，是必要基础，但不是重点。

### 真正的协作过程

产品角色首先明确：

- 当前只解决主路径问题；
- 不扩展到历史修复；
- 不处理旁路流程；
- 不扩大本次需求范围。

QA 提前提出：

- 正确性要求；
- 幂等性要求；
- 并发风险；
- 异常状态；
- 重复操作；
- 发布前置条件。

架构角色指出：

- 直接复用旧逻辑可能导致状态错乱；
- 可能造成重复处理；
- 边界行为难以控制；
- 应该新增更明确、可验证的专用实现路径。

全栈开发发现门禁尚未满足，因此要求先补齐：

- 执行 DAG；
- 变更记录；
- 研发分支；
- 接口契约冻结；
- 测试准入证明。

### 产生的协作增益

没有任何一个角色拥有完整答案：

```text
产品：定义做什么、不做什么
QA：定义如何证明正确
架构：修正实现方向
开发：完成真实代码变更
DAG：沉淀依赖关系
Runtime：执行命令和修改
Artifacts：保存证据
Memory：保留有效结论
```

最终系统不只是完成代码修改，还形成了：

- 业务边界；
- 实现路径；
- 风险清单；
- 任务依赖；
- 代码变更；
- 测试结果；
- 部署状态；
- 验收证据。

## 案例二：工单排查到代码修复

### 初始任务

用户只提出：

> 排查一个工单问题。

技术支持 Agent 查询日志后发现：

- 日志报错符合预期；
- 但这并不能证明系统没有问题。

### 协作链路

开发 Agent 进一步：

1. 检查代码逻辑；
2. 对照历史事件；
3. 判断问题可能涉及代码行为；
4. 发现是否修复需要产品确认；
5. 主动将产品角色拉入房间。

产品确认后，系统继续推进：

```text
工单排查
→ 代码逻辑核对
→ 产品确认是否进入需求迭代
→ 单 Case 修复
→ 代码修改
→ 测试验证
```

### 关键启示

初始任务并没有要求：

- 拉产品进来；
- 修改代码；
- 形成需求；
- 创建修复闭环。

这些步骤是 Agent 根据共享上下文自行推导出来的。

因此，Agent Room 的价值不是完成更多动作，而是：

> **在问题发展过程中自主识别新的角色、新的任务和新的闭环。**

## 六、传统编排方式的能力与边界

## 1. Pipeline / DAG

### 机制

按固定依赖逐步执行：

```text
拉代码
→ 编译
→ 单测
→ 部署
→ 回归
→ 发布
```

### 擅长

- 确定性流程；
- 稳定执行；
- 状态追踪；
- 可重复运行。

### 局限

- 前期拆错后不灵活；
- 难以应对动态需求；
- 难以发现流程外的新问题。

### 在 Agent Room 中的作用

DAG 仍然必要，但它应当是协作判断收敛后的执行结构，而不是一开始就完全写死的流程。

## 2. Planner-Executor

### 机制

Planner 先拆解任务，再由 Executor 执行。

### 擅长

- 开放任务拆解；
- 单点任务规划；
- 较清晰的执行分工。

### 局限

- Planner 的错误会传递给所有执行者；
- 执行者通常无法补充总体判断；
- 后续发现的问题难以反向修改全局计划。

## 3. Supervisor / Router

### 机制

由路由器决定任务交给哪个 Agent。

### 擅长

- 入口清晰；
- 减少无关信息；
- 便于权限和资源管理。

### 局限

- 路由器可能判断错误；
- 未被路由的角色看不到问题；
- 跨领域风险容易被遗漏。

## 4. Manager-Worker

### 机制

Manager 将任务拆成多个子任务，由 Worker 并行执行，最后由 Manager 汇总。

### 擅长

- 并行处理；
- 大规模代码修改；
- 批量生产。

### 局限

- Worker 之间上下文弱；
- 集成风险集中回到 Manager；
- Worker 不一定理解全局约束。

## 5. 辩论与投票

### 机制

多个 Agent 独立提出观点，再由裁判总结或投票。

### 擅长

- 方案比较；
- 风险识别；
- 多角度评估。

### 局限

- 容易停留在观点层；
- 缺少真实执行；
- 缺少验收闭环；
- 投票不等于正确。

## 6. Agent Room

### 机制

所有相关角色共享上下文，自主判断是否介入，再将共识转化为任务、依赖和执行证据。

### 擅长

- 处理不确定问题；
- 发现跨角色风险；
- 形成动态协作；
- 连接讨论与执行；
- 持续修正决策。

### 新增风险

- 发言过多导致噪音；
- Agent 互相触发无限循环；
- 上下文过长；
- 旧记忆污染新决策；
- 缺少约束时难以收敛。

因此，Agent Room 并不是取消传统编排，而是将不同编排方式放在不同层次：

```text
Agent Room：负责发现问题、形成判断
DAG：负责表达依赖、执行确定流程
Router：负责提醒和调度
Worker：负责具体落地
Runtime：负责真实执行
Artifacts：负责保存证据
```

## 七、上下文编排：为什么共享上下文比中心化分发更重要

## 1. 中心化编排的上下文损耗

在 Manager-Worker 或 Planner-Executor 系统中，中心节点通常会裁剪上下文：

```text
完整上下文
    ↓
中心节点筛选
    ↓
每个 Agent 只获得局部上下文
```

裁剪在简单任务中有益，因为它可以减少噪音。

例如：

```text
CSV 转 JSON
```

执行者不需要知道公司的战略目标。

但对于以下任务，裁剪可能直接损害判断：

- 需求取舍；
- 业务边界；
- 架构约束；
- 测试标准；
- 线上风险；
- 发布条件；
- 历史决策。

因为 Agent 不知道自己没有看到什么，也就无法判断哪些缺失信息可能影响结论。

## 2. Agent Room 的默认原则

传统系统的默认值是：

> 只给 Agent 它应该看的内容。

Agent Room 的默认值是：

> 允许 Agent 看完整上下文，但要求它克制发言。

这形成了新的协作规则：

```text
看见不等于必须回应
回应必须带来新增价值
没有新增价值就 NO_REPLY
```

---

## 八、沉默机制：为什么“少说话”是系统能力

如果所有 Agent 都看到完整上下文并且持续发言，系统会变成噪音机器。

### 1. Agent 是否发言的判断

可以将一次发言看成一个有成本的动作：

```text
发言收益 > 发言噪音成本 × 惩罚系数
```

发言收益包括：

- 提供新事实；
- 发现风险；
- 纠正错误；
- 冻结决策；
- 推进任务；
- 补充验收条件；
- 触发必要执行。

噪音成本包括：

- 重复已有观点；
- 无效转述；
- 抢夺发言；
- 造成额外任务；
- 触发无意义的 Agent 链式响应。

### 2. 发言准入标准

Agent 只有在以下情况下才应发言：

- 发现新事实；
- 发现已有结论错误；
- 发现关键风险；
- 需要冻结边界；
- 可以推动一个任务；
- 可以提供验证证据；
- 发现需要新增角色或新增任务。

否则应输出：

```text
NO_REPLY
```

这说明：

> **沉默不是缺少能力，而是协作系统中的主动控制行为。**

---

## 九、任务账本：为什么讨论必须转化为状态

群聊可以产生共识，但不能自动保证执行。

常见问题是：

- 大家都以为任务已经有人做；
- 已完成任务被旧消息反复阻塞；
- 依赖未满足时 Agent 越权执行；
- QA 提前验收不具备准入条件的代码；
- 用户无法判断当前进度。

因此，需要任务账本记录：

- 任务内容；
- owner；
- 当前状态；
- 前置依赖；
- 验收标准；
- 关联产物；
- 执行证据；
- 失败和重试信息。

## 1. 基本状态

可采用：

```text
待创建
→ 待认领
→ 进行中
→ 待验证
→ 已完成
```

异常状态包括：

```text
阻塞
取消
豁免
失败
待重试
```

## 2. 状态约束

重要规则包括：

- 未指派不能视为执行中；
- 依赖未完成不能进入实现；
- 开发未提供准入证据，QA 不能正式验收；
- 没有执行证据，不能直接标记完成；
- 用户改变口径后，旧阻塞必须重新评估；
- 已完成任务不能被旧消息重新打开。

任务账本的本质是：

> **将自然语言共识转化为可验证的状态机。**

---

## 十、Memory 系统：记住正确的信息，而不是记住全部信息

## 1. 为什么简单保存聊天记录不够

没有记忆：

- 每轮都要重新解释背景；
- 房间无法持续推进；
- 历史决策无法复用。

只有原始聊天记录：

- 旧结论持续干扰新决策；
- 已完成任务仍被视为未完成；
- 已废弃的需求仍被当作当前约束；
- 失败记录可能覆盖成功重试结果。

因此，Memory 不是聊天记录仓库，而应当是：

> **分层、可检索、可更新、可失效的协作记忆系统。**

## 2. 记忆的检索原则

调度 Agent 时，不应将所有历史消息直接塞入上下文，而应根据当前目标检索。

检索排序不能只看语义相似度，还应考虑：

- 权威性；
- 新鲜度；
- 是否被覆盖；
- 是否已经完成；
- 是否与当前任务直接相关；
- 是否具有执行证据。

### 权威性排序示例

```text
用户最新确认
>
明确的 Decision
>
Contract Freeze
>
任务状态变更
>
执行证据
>
Agent Proposal
>
普通讨论
```

### 失效规则

以下内容应被标记为过期：

- 被新决策覆盖的旧结论；
- 已完成任务的旧阻塞；
- 已成功重试的失败日志；
- 被用户取消的前置条件；
- 不再适用的历史方案。

## 3. 六类记忆

| 类型 | 记录内容 | 解决问题 |
|---|---|---|
| 短期记忆 | 最近几轮对话 | 保持讨论连续 |
| 决策记忆 | Decision、Contract Freeze、用户确认 | 防止旧口径反复阻塞 |
| 任务记忆 | owner、状态、依赖、验收 | 明确当前可执行事项 |
| 运行记忆 | 命令、日志、diff、错误 | 支持追溯和重试 |
| 产物记忆 | DAG、报告、证据、风险清单 | 沉淀交付资产 |
| 领域记忆 | 业务、仓库、数据表、应用、历史知识 | 建立业务世界模型 |

Memory 的目标不是让 Agent 记得更多，而是：

> **在正确的时间，记得正确且仍然有效的信息。**

---

## 十一、DAG 系统：把协作共识转化为执行拓扑

## 1. 定义

DAG 是由节点和依赖边组成的有向无环图。

在 Agent Room 中，节点不只代表代码任务，还可以代表：

- 决策；
- 契约；
- 实现；
- 测试；
- 运维；
- 数据核验；
- 交付产物。

例如：

```text
需求边界冻结
      ↓
接口契约冻结
      ↓
代码实现
      ↓
单元测试
      ↓
预发部署
      ↓
浏览器验证
      ↓
验收报告
```

## 2. DAG 解决的问题

### 问题一：讨论结束后没人知道下一步

DAG 明确：

- 当前 ready 节点；
- 对应 owner；
- 前置依赖；
- 验收标准。

### 问题二：旧消息持续制造阻塞

DAG 通过状态区分：

```text
ready / running / blocked / done / cancelled / waived
```

系统不再依赖旧消息判断任务是否完成。

### 问题三：Agent 互相 @，造成无限讨论

DAG 直接告诉系统：

- 哪些节点可以运行；
- 哪些节点仍然阻塞；
- 哪些节点不需要任何角色继续发言。

## 3. 节点完成必须有证据

“完成”不能只依靠自然语言声明。

可接受的证据包括：

- 测试输出；
- 代码 diff；
- 命令日志；
- 浏览器截图；
- 发布单状态；
- SQL 查询结果；
- 人工确认；
- 运行环境状态。

因此：

```text
没有 evidence 的 done
只能视为口头完成
```

## 4. 用户改变口径后的处理

用户如果确认新的决策，受影响节点不能继续作为阻塞条件。

应当：

- 标记为 `waived`；
- 取消；
- 修改依赖；
- 重新连接拓扑；
- 重新计算可执行节点。

这使 DAG 不只是静态流程图，而是：

> **随决策变化而更新的协作状态图。**

---

## 十二、Artifacts：把过程转化为可复用资产

如果讨论、代码、日志、截图和验证结果散落在不同地方，最终会无法回答：

> 这次需求到底交付了什么？

因此需要产出物系统统一管理结果。

## 1. 产出物至少应包含

- 类型；
- 名称；
- 所属任务；
- 所属节点；
- 创建者；
- 创建时间；
- 当前版本；
- 内容位置；
- 验证状态；
- 是否有效；
- 关联证据。

## 2. 四类产出物

| 类型 | 示例 | 归属 |
|---|---|---|
| 代码产物 | 源码、测试、配置、迁移脚本 | 业务代码仓库 |
| 过程产物 | 执行 DAG、决策 DAG、发布 DAG | 房间工作区 |
| 验证产物 | 测试日志、截图、QA 报告 | 房间工作区 |
| 交付产物 | MR、CR、发布证据、最终总结 | 工作区与群聊摘要 |

## 3. 四套系统的闭环

```text
Memory：过去发生了什么
DAG：现在应该做什么
Runtime：实际执行了什么
Artifact：产生了什么证据
```

然后：

```text
Artifact
   ↓
反哺 Memory
   ↓
影响下一轮 DAG
```

这样，房间状态的增长不再只是“多了几条聊天消息”，而是增加了：

- 新决策；
- 新任务状态；
- 新执行记录；
- 新验证证据；
- 新领域知识。

---

## 十三、整体架构：四个核心系统与一个交互层

Agent Room 可以抽象为：

```text
共享上下文层
      ↓
Memory：提供有效历史
      ↓
多 Agent 判断与修正
      ↓
DAG：形成依赖与任务结构
      ↓
Runtime：执行代码、命令和部署
      ↓
Artifacts：保存代码、日志和证据
      ↓
Memory：沉淀新的有效状态
```

更完整地说：

| 层次 | 作用 |
|---|---|
| 共享上下文 | 让不同角色看到同一问题 |
| Agent 角色 | 提供专业视角和局部判断 |
| Memory | 提供有效历史与领域知识 |
| DAG | 记录任务、依赖和状态 |
| Runtime | 执行真实动作 |
| Artifacts | 留存结果和证据 |
| 可观测界面 | 展示进度、命令、变更、失败和重试 |

其中，群聊只是交互入口，不是完整系统。

---

## 十四、系统运行机制：从目标到交付

一个完整的 Agent Room 运行过程可以拆成八步。

### 第一步：输入目标

用户提供目标，而不必提供完整需求或详细流程。

例如：

```text
解决用户反馈的登录问题，并确保上线后不再复现。
```

### 第二步：建立初始上下文

系统收集：

- 当前问题；
- 相关业务；
- 代码仓库；
- 历史决策；
- 线上日志；
- 相关数据；
- 当前环境；
- 既有任务和产物。

### 第三步：角色自主判断

各 Agent 判断：

- 问题是否与自己相关；
- 是否有新增事实；
- 是否存在风险；
- 是否需要新增角色；
- 是否需要建立任务或决策。

没有价值的角色保持沉默。

### 第四步：形成共识

不同角色将局部信息写回公共上下文：

- 产品冻结边界；
- 架构修正方案；
- QA 补充验收标准；
- 开发确认实现路径；
- 运维确认发布约束；
- 数据研发确认数据口径。

### 第五步：转化为任务和 DAG

将讨论结果转为：

- 决策节点；
- 契约节点；
- 实现节点；
- 验证节点；
- 发布节点；
- 交付节点。

### 第六步：Runtime 执行

系统实际运行：

- 查询日志；
- 查询数据库；
- 修改代码；
- 执行测试；
- 创建分支；
- 构建部署；
- 查询环境状态；
- 进行浏览器或接口验证。

### 第七步：证据回写

Runtime 产出的：

- diff；
- 日志；
- 测试结果；
- 截图；
- SQL 结果；
- 发布状态；

被写入 Artifacts，并更新任务状态。

### 第八步：根据结果迭代

如果验证失败：

```text
失败证据
→ 更新 Memory
→ 修改 DAG
→ 重新分配任务
→ 再次执行
```

如果验证成功：

```text
完成证据
→ 关闭相关节点
→ 生成交付产物
→ 冻结房间快照
```

## 十五、房间生命周期

房间不是临时聊天页面，而是有状态的协作容器。

### 1. 创建

- 设定目标；
- 创建初始上下文；
- 初始化角色；
- 建立工作区；
- 创建初始任务。

### 2. 协作

- Agent 阅读上下文；
- 进行必要发言；
- 形成决策；
- 创建任务和依赖；
- 触发执行。

### 3. 验证

- 运行测试；
- 检查环境；
- 收集证据；
- 处理失败；
- 重新迭代。

### 4. 关闭

房间关闭意味着：

- 冻结最终 Memory 快照；
- 关闭、取消或保留未完成节点；
- 保存产物索引；
- 生成交付总结；
- 回收临时工作区；
- 保留审计和交付证据。

## 十六、边界：Agent Room 不是什么

## 1. 不是简单多 Agent 聊天

如果只是让多个 Agent 发言，结果通常是：

- 重复观点；
- 无休止讨论；
- 缺少执行；
- 无法判断完成；
- 历史消息污染当前任务。

真正的 Agent Room 必须具有：

```text
上下文共享
+ 发言约束
+ 任务状态
+ 依赖关系
+ 真实执行
+ 证据留存
+ 记忆校正
```

## 2. 不是取消流程编排

DAG、Router、Worker 仍然有价值。

区别在于：

- 它们不再独立决定全局判断；
- 它们服务于协作形成的共识；
- 确定性流程仍由 DAG 执行；
- 具体工作仍由 Worker 落地；
- Router 仍可承担提醒和调度。

## 3. 不是无限上下文

共享上下文不意味着所有历史都永久有效。

必须进行：

- 相关性筛选；
- 权威性排序；
- 新鲜度判断；
- 过期标记；
- 决策覆盖；
- 任务状态校正。

## 4. 不是让 Agent 代替用户做决策

系统可以：

- 提供方案；
- 发现冲突；
- 推导风险；
- 生成任务；
- 执行已授权动作。

但用户身份和用户决策不能被 AI 模拟。

用户确认的决策应具备高权威性，但 AI 不能伪造用户确认。

## 5. 不是所有任务都需要协作涌现

对于确定性任务，Agent Room 可能是过度设计。

例如：

- 格式转换；
- 简单数据清洗；
- 固定脚本执行；
- 明确的批量操作；
- 标准化部署流水线。

这些任务更适合使用：

- Pipeline；
- DAG；
- 单 Agent；
- 函数调用；
- 传统自动化。

Agent Room 更适合：

- 目标不完整；
- 需求会变化；
- 风险跨领域；
- 需要多角色权衡；
- 结果必须真实验证；
- 任务可能自发扩展。

## 十七、改进方案：如何把概念做成可靠系统

下面是从文章原理进一步推导出的工程设计方案。

## 1. 以“目标”作为入口，而非“任务”

用户不应被要求提前拆分全部步骤。

系统应先识别：

- 目标；
- 成功标准；
- 当前约束；
- 非目标范围；
- 已知风险；
- 可用资源；
- 用户需要确认的事项。

然后让 Agent Room 自主生成任务和流程。

## 2. 建立结构化消息协议

自然语言消息应尽量具有明确类型，例如：

```text
[Observation] 观察
[Evidence] 证据
[Proposal] 方案
[Risk] 风险
[Decision] 决策
[Contract Freeze] 契约冻结
[Task] 任务
[Blocker] 阻塞
[Verification] 验证
[Artifact] 产物
```

这样可以减少：

- 语义歧义；
- 状态误判；
- 旧消息污染；
- 任务漏建；
- 证据丢失。

## 3. 把“发言”与“执行”分离

Agent 的发言不应自动等于执行授权。

应区分：

```text
提出建议
→ 用户或系统确认
→ 创建任务
→ 检查依赖
→ 执行
→ 收集证据
```

对于低风险、已授权的确定性动作，可以自动执行。

对于高风险动作，应增加：

- 人工确认；
- 权限检查；
- 环境隔离；
- 回滚方案；
- 变更审计。

## 4. 用“证据门禁”替代“语言门禁”

不能因为 Agent 说“已完成”就认为完成。

每个关键节点应配置证据要求：

```text
实现完成：必须有代码 diff
测试完成：必须有测试输出
部署完成：必须有环境状态
数据确认：必须有查询结果
验收完成：必须有报告或确认
```

这可以显著降低“看起来完成，实际上没有完成”的问题。

## 5. 建立可失效的记忆模型

每条记忆至少应包含：

- 内容；
- 来源；
- 创建时间；
- 更新时间；
- 权威级别；
- 适用范围；
- 当前状态；
- 被谁覆盖；
- 关联任务；
- 关联证据。

记忆不是永久真理，而是带状态的判断：

```text
有效
过期
被覆盖
已验证
待验证
仅供参考
```

## 6. 让 DAG 支持动态重构

DAG 不应只支持“节点完成”，还应支持：

- 新增节点；
- 删除节点；
- 修改依赖；
- 重新计算 ready；
- 标记 waived；
- 从失败节点重试；
- 从新决策处重新分叉；
- 保留历史版本。

DAG 应记录：

```text
当前拓扑
+ 历史变更
+ 变更原因
+ 关联决策
```

## 7. 建立角色介入策略

角色是否发言，不应只由 `@` 决定。

系统可以结合：

- 当前领域相关性；
- 任务风险；
- 角色专业能力；
- 新信息量；
- 当前阶段；
- 是否已有角色负责；
- 发言历史；
- 噪音成本。

角色介入可以分为：

```text
必须介入
建议介入
可观察
无需介入
```

## 8. 建立协作收敛指标

可以通过指标判断房间是否正在变好：

### 决策质量

- 方案被验证的比例；
- 返工次数；
- 线上问题复发率；
- 关键风险提前发现率；
- 用户目标达成率。

### 协作效率

- 每个有效决策所需轮次；
- 无效消息比例；
- 重复发言比例；
- 任务遗漏率；
- 阻塞平均持续时间。

### 执行可靠性

- 有证据完成的任务比例；
- 自动执行成功率；
- 失败重试成功率；
- 部署回滚率；
- 产物完整率。

### 记忆质量

- 旧结论误用率；
- 过期记忆命中率；
- 用户决策覆盖成功率；
- 重新解释次数；
- 历史经验复用率。

## 十八、母题驱动的证据闭环

这篇文章可以围绕五个母题理解。

## 母题一：为什么“自动化”不等于“智能化”

### 观点

自动化只要求系统执行既定流程；智能化要求系统能够在不确定环境中形成判断。

### 证据链

```text
固定流程
→ AI 执行节点
→ 只能处理预定义问题
→ 无法修正流程
→ 无法完成真正业务自迭代
```

### 结论

AI Native 的关键不是接入更多工具，而是让 AI 能根据目标自主形成并修正流程。

---

## 母题二：为什么共享上下文是协作涌现的前提

### 观点

不同角色只有看到同一问题的完整背景，才能发现彼此之间的约束和冲突。

### 证据链

```text
局部上下文
→ 局部判断
→ 跨角色信息缺失
→ 风险无法互相修正
```

而：

```text
共享上下文
→ 多专业视角
→ 公开反馈
→ 判断互相修正
→ 形成整体判断
```

### 结论

共享上下文不是为了让 Agent 获得更多信息，而是为了让不同视角发生交互。

---

## 母题三：为什么沉默与约束同样重要

### 观点

协作不是发言越多越好，而是每次发言都应有边际价值。

### 证据链

```text
所有 Agent 积极发言
→ 重复与抢话
→ 上下文膨胀
→ 调度失控
→ 有效信息被噪音淹没
```

### 结论

高质量协作需要：

```text
可见性高
+ 发言门槛高
+ 执行约束强
```

---

## 母题四：为什么讨论必须有任务、状态和证据

### 观点

没有结构化状态的讨论无法可靠推进。

### 证据链

```text
自然语言共识
→ 无明确 owner
→ 无依赖关系
→ 无完成标准
→ 无法判断是否真正完成
```

转化为：

```text
任务
→ owner
→ 状态
→ 依赖
→ 验收标准
→ 执行证据
```

### 结论

群聊负责生成判断，任务账本负责管理状态，Runtime 负责行动，Artifacts 负责证明。

---

## 母题五：为什么记忆必须可失效

### 观点

记住所有历史不等于拥有更好的记忆。

### 证据链

```text
只追加聊天历史
→ 旧结论长期存在
→ 新决策与旧阻塞冲突
→ Agent 反复犯旧错误
```

### 结论

有效记忆必须具备：

```text
权威性
+ 新鲜度
+ 适用范围
+ 状态
+ 失效机制
```

---

## 十九、对“业务自迭代”的严格定义

文章中的业务自迭代，不是简单的自动执行，也不是自动写代码。

它应满足：

```text
人提供目标
→ AI 理解业务环境
→ AI 识别问题和边界
→ AI 自主拆解方案
→ AI 协调专业角色
→ AI 执行真实动作
→ AI 获取效果证据
→ AI 根据结果修正方案
→ 持续推进直到目标达成
```

其中最关键的是最后两步：

- 获取真实结果；
- 根据结果继续调整。

如果系统只能：

```text
目标
→ 生成代码
→ 提交代码
```

但不能验证代码是否解决真实问题，就仍然只是自动化生产。

## 二十、最终抽象：Agent Room 的底层模型

可以将 Agent Room 抽象为：

```text
Agent Room
=
共享上下文
+ 多角色视角
+ 发言选择
+ 任务状态机
+ 动态 DAG
+ 真实 Runtime
+ 证据型产物
+ 可失效 Memory
+ 用户决策边界
```

其核心闭环是：

```text
目标
 ↓
上下文
 ↓
多视角判断
 ↓
冲突与修正
 ↓
决策冻结
 ↓
任务与依赖
 ↓
真实执行
 ↓
证据验证
 ↓
记忆更新
 ↓
目标达成或继续迭代
```

最简洁的判断标准是：

> **如果系统只能按照既定流程完成动作，它是自动化系统；如果系统能在共享上下文中发现问题、改变流程、调用新角色、执行并验证，它才开始具备协作智能。**
