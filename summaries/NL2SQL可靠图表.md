

### **结论：NL2BI Agent 的核心不是“让模型写 SQL”，而是把自然语言接入一条可控、可验证、可追溯的业务数据流水线。**

其基本分工是：

> **模型处理语言的不确定性；确定性系统负责权限、业务语义、数据状态、参数合法性、查询执行、证据来源与质量评测。**

## 一、先从第一性原理定义问题

### 1. NL2BI 是什么

NL2BI，即 Natural Language to Business Intelligence，可以抽象为：

```text
自然语言问题
→ 意图与实体理解
→ 权限与租户验证
→ 业务能力选择
→ 参数校验
→ 受治理查询
→ 证据封装
→ 文本或图表生成
→ 结果校验与评测
```

它不是简单的：

```text
自然语言 → SQL → 查询结果
```

而是：

```text
自然语言
→ 受权限、业务口径、数据状态和证据约束的业务查询
→ 可解释、可验证的结果
```

### 2. 为什么 Text2SQL 不够

SQL 只能表达“查什么、怎么算”，不能天然决定：

- “当前报价”是最新记录，还是已审批生效的当前版本；
- “运费”是哪个方向、哪个吨位档；
- “平均”按哪一层业务对象聚合；
- 用户能否访问某个租户或某些数据行；
- 返回结果是否完整；
- 两个业务事实是否具备合法关联关系；
- 图表中的数字究竟来自哪一次真实查询。

因此，**SQL 解决表达转换，NL2BI 解决业务解释与事实治理**。

### 3. 系统可信度来自哪里

一条业务答案要可信，至少需要满足：

```text
权限正确
∧ 业务口径正确
∧ 数据状态正确
∧ 查询参数正确
∧ 查询结果完整
∧ 结果来源可追踪
∧ 展示内容未被模型篡改
```

任何一项不成立，都可能出现“看起来正确、实际上错误”的答案。

---

## 二、核心设计原则：不确定性与确定性分工

### 1. 模型适合处理什么

模型擅长：

- 理解自然语言；
- 识别用户意图；
- 从口语中抽取业务实体；
- 选择可能的业务工具；
- 组织自然语言回答；
- 选择合适的展示形式。

### 2. 模型不应该负责什么

模型不应成为：

- 数据库；
- 权限中心；
- 租户边界的决定者；
- 当前业务事实的来源；
- 任意 SQL 执行器；
- 业务规则解释器；
- 图表数据的最终事实来源。

### 3. 代码和业务系统应负责什么

确定性系统负责：

- 身份认证；
- 租户隔离；
- 数据权限；
- 当前态规则；
- 业务实体解析；
- Tool 参数校验；
- 聚合白名单；
- 跨域关联条件；
- 数据新鲜度；
- 结果完整性；
- 证据绑定；
- 评测与审计。

这形成一个基本原则：

> **能用代码强制的规则，不要只写在 Prompt 中；能由数据库计算的内容，不要让模型在上下文中自行计算。**

---

## 三、业务事实层必须先于 Agent

### 1. 为什么不能让 AI 自己构造业务事实

传统业务系统通常已经拥有：

```text
录入
→ 校验
→ 审批
→ 生效
→ 当前态查询
```

如果 Agent 又从底表重新拼装数据，就会产生第二套事实链：

```text
后台页面看到一套数据
外部 API 返回一套数据
AI 助手回答另一套数据
```

这会导致口径冲突、权限绕过和审计困难。

### 2. 正确方案：复用已有事实链

AI 查询应当读取与后台系统、API 和评测系统一致的当前态数据：

```text
业务数据
→ 应用服务与审批治理
→ Current View
→ Query Layer
→ Tool
→ Agent
```

Agent 只读取，不重新定义业务事实。

### 3. Current View 的作用

Current View 将复杂的业务状态收口为“当前有效事实”，例如：

- 审批状态；
- 生效时间；
- 供应状态；
- 版本关系；
- 租户可见性；
- 当前快照。

它不是简单的数据库视图，而是业务当前态的确定性入口。

### 4. 为什么数据过期时必须失败

如果当前视图：

- 未刷新；
- 刷新失败；
- 已过期；
- 校验异常；
- 快照状态无法确认；

系统不应继续使用旧数据生成“当前结果”。

正确策略是：

```text
无法证明数据是当前的
→ 拒绝生成当前结论
→ 返回明确失败原因
```

这属于 **fail closed**：无法确认安全和事实状态时，默认拒绝，而不是继续放行。

### 5. 如何避免刷新竞态

仅在查询开始前检查一次“数据是否新鲜”仍然不够，因为检查后数据可能立即刷新。

更可靠的方式是：

```text
新鲜度检查
+ 数据读取
```

在同一套锁或快照条件下完成：

- 查询链持有共享锁；
- 刷新链使用互斥机制；
- 新鲜度验证和数据读取看到同一个当前态。

这样可以避免“验证时是旧快照，读取时又处于切换状态”的问题。

---

## 四、语义层不是一份巨型 Prompt

### 1. 语义层解决什么问题

语义层负责定义：

- 指标是什么；
- 维度是什么；
- 字段如何解释；
- 同义词如何映射；
- 哪些数据属于当前事实；
- 哪些聚合组合合法；
- 哪些跨域关系可以连接；
- 哪些问题必须先完成前置查询。

### 2. 为什么不能只依赖模型理解语义

业务语义通常具有隐含规则。例如：

```text
报价 + 运费 ≠ 自动等于到岸成本
```

只有满足以下条件才可以相加：

- 报价与运费属于同一产品；
- 矿山与发货地映射成立；
- 发货方向一致；
- 收货地一致；
- 吨位档精确匹配；
- 两项数据均为当前有效事实。

模型可以理解“要计算到岸成本”，但不能独立决定这些业务条件已经满足。

### 3. 语义规则应分层承载

| 规则类型 | 更适合的位置 |
|---|---|
| Tool 的用途、参数和返回字段 | Tool Description / Schema |
| 数据集允许的维度、指标、聚合 | Query Layer / Validator |
| 跨 Tool 的业务前置条件 | SemanticPolicy / 状态机 |
| 租户、权限、状态、新鲜度 | 确定性代码 |
| 典型口语和意图表达 | SemanticPolicy / 少量示例 |
| UI 展示方式 | 输出协议 / Renderer |
| 高层行为原则 | 简洁 System Prompt |

核心改进原因是：

> **Prompt 负责解释规则，代码负责执行规则。**

如果同一规则同时出现在 Prompt、Tool 描述和 Validator 中，就容易产生版本不一致、Token 浪费和维护困难。

---

## 五、不要让模型直接接触数据库

### 1. 直接数据库访问的问题

数据库不知道或不应直接承担：

- 当前用户是谁；
- 当前用户属于哪个租户；
- 哪些行对用户可见；
- 哪些版本已审批生效；
- 当前视图是否新鲜；
- 哪些字段允许对外返回；
- 哪些聚合符合业务口径；
- 哪些数据不能进入模型上下文。

让模型持有数据库凭证并生成任意 SQL，相当于把所有业务边界交给非确定性组件。

### 2. 受治理 Tool 的架构

模型看到的不是数据库表，而是有限的业务能力：

```text
主数据 Tool
关系 Tool
当前明细 Tool
受治理分析 Tool
```

典型能力包括：

- 查询矿山；
- 查询规格；
- 查询发货地和收货地；
- 查询吨位档；
- 查询矿山与发货地映射；
- 查询当前报价；
- 查询当前运费；
- 执行白名单聚合。

### 3. 一个生产 Tool 必须回答四个问题

1. 它解决什么明确的业务任务？
2. 哪些参数合法，哪些组合非法？
3. 它返回哪些事实和元数据？
4. 空结果、歧义、权限拒绝和系统失败如何区分？

Tool 本质上是：

> **非确定性 Agent 与确定性业务系统之间的契约。**

## 六、建立多层安全边界

### 第一层：调用模型之前拒绝

在任何模型、MCP 或查询调用前检查：

- JWT 是否有效；
- 用户是否启用 AI 查询能力；
- 用户是否拥有查询权限；
- 租户上下文是否有效；
- 权限依赖是否可用。

检查失败时直接拒绝，避免无权请求继续消耗模型 Token 和后端资源。

### 第二层：只暴露受治理能力

工具注册表只暴露必要能力，不提供：

- 任意 SQL；
- 任意表访问；
- 任意租户选择；
- 任意字段读取；
- 任意跨域连接。

### 第三层：Tool Call 必须视为不可信输入

模型产生的 JSON 只是待验证输入，必须经过 Schema 和 Validator。

应校验：

- 未声明字段；
- 类型；
- 枚举值；
- 页码与数量上限；
- 数据集与字段关系；
- 过滤字段是否合法；
- 互斥参数；
- 成对参数；
- 数组长度；
- 业务组合约束。

`tenant_id` 等认证上下文参数不能由模型传入，而应由服务端注入。

### 第四层：数据查询必须走当前态

Query Layer 不允许绕过 Current View，直接从版本底表拼接“最新数据”。

### 第五层：输出也必须受控

最终输出应过滤：

- SQL；
- 内部 Tool 名；
- 内部状态名；
- JWT；
- 密钥；
- 租户信息；
- Trace ID；
- 内部字段；
- 任意 ECharts 配置；
- JavaScript。

原则是：

> **内部保留完整审计，用户只看到完成任务所需的信息。**

---

## 七、意图识别不是简单分类，而是多层决策

### 1. 真实意图结构

一个问题通常同时包含多个维度：

```text
数据领域
→ 查询类型
→ 聚合方式
→ 业务实体
→ 实体是否唯一
→ 是否跨域
→ 是否需要前置条件
→ 是否需要当前态
→ 是否需要图表
→ 是否支持该口径
```

例如：

> 各矿山目前分别有多少条报价，用柱状图展示。

至少包含：

- 报价数据集；
- 当前状态；
- 按矿山分组；
- 计数指标；
- 聚合查询；
- 图表展示；
- 返回数量上限。

只分类为“报价查询”是不够的，否则模型可能调用明细查询，读取一页数据后自行计数。

### 2. SemanticPolicy 的作用

SemanticPolicy 不仅识别意图，还维护：

- 当前业务状态；
- 允许使用的 Tool；
- 禁止使用的 Tool；
- 必须完成的前置条件；
- 最终必须出现的证据；
- 是否允许结束本轮。

它相当于 Agent 的确定性语义门。

### 3. 适合加护栏的高价值场景

尤其应约束：

- 当前数据查询；
- 历史趋势查询；
- 聚合；
- 比较；
- 排名；
- 图表；
- 到岸成本；
- 跨域关联；
- 权限敏感查询。

模型可以负责理解用户表达，但系统负责决定：

```text
什么时候可以调用什么工具
什么时候不能结束
什么时候必须追问
什么时候必须拒绝
```

---

## 八、实体解析：先确认对象，再查询事实

### 1. 为什么实体解析重要

用户通常说的是：

- 矿山简称；
- 规格口语；
- 城市或港口；
- “大船”“小吨位”等业务习惯词。

系统真正需要的是受治理主数据中的标准 ID。

### 2. 推荐流程

```text
抽取关键词
→ 查询主数据
→ 0 个候选：停止事实查询
→ 1 个候选：继续
→ 多个候选：要求消歧
→ 写入标准实体参数
→ 执行后续查询
```

### 3. 为什么不能让模型自行消歧

模型可能根据语言习惯随意选择一个同名对象，从而造成：

- 查询了错误地点；
- 关联了错误路线；
- 生成了错误成本；
- 形成无法察觉的事实污染。

两个关键原则是：

> **没有唯一实体，不进入事实查询。**

> **不能通过扩大搜索范围来伪造完整性。**

---

## 九、不同问题必须走不同查询路径

### 1. 单域明细查询

例如：

> 查询某矿山某规格的当前报价。

路径：

```text
确认矿山
→ 确认规格
→ 查询当前报价
→ 返回用户要求字段
```

模型只负责理解和表达，事实由 Tool 返回。

注意：有界明细结果不能随意描述为“全量”。如果结果受分页、数量或权限限制，必须说明其完整性状态。

### 2. 受治理聚合查询

例如：

> 各矿山目前分别有多少条报价，用柱状图展示。

正确路径：

```text
识别当前 + 聚合 + 图表
→ 选择报价数据集
→ 选择矿山维度
→ 选择报价数量指标
→ 选择计数聚合
→ Query Layer 执行白名单聚合
→ 返回分组数据与完整性证据
→ 生成绑定证据的 ChartSpec
```

为什么不能让模型自己聚合：

- 模型不知道明细是否完整；
- 可能只看到一页数据；
- 可能漏掉分页结果；
- 可能错误去重；
- 可能将不同查询结果混在一起；
- 计算过程不可审计。

原则是：

> **数据库和代码做聚合，模型解释聚合结果。**

### 3. 跨域查询

例如：

> 某矿山某规格运到南京的当前到岸成本是多少？

正确链路：

```text
矿山与规格
→ 当前报价
→ 矿山—发货地映射
→ 发货地到南京的当前运费
→ 校验方向、吨位档和当前状态
→ 报价 + 运费
→ 保留两部分来源
```

只有在前置条件全部满足时才能计算。

缺少映射、吨位档或方向一致性时，应报告缺口，不能：

- 选择附近发货地；
- 使用相邻吨位档；
- 估算缺失运费；
- 将反向路线当作正向路线；
- 用两个真实但不可关联的数字相加。

### 4. 多轮追问

多轮对话需要区分：

| 内容 | 是否直接继承 |
|---|---|
| 用户讨论的实体 | 通常继承 |
| 用户筛选条件 | 通常继承 |
| 历史回答文字 | 作为理解材料 |
| 历史 Tool Result | 不能默认作为当前事实 |
| 当前报价、当前运费 | 默认重新查询 |
| 历史证据引用 | 可以保留，但需重新验证适用性 |

核心原则：

> **历史上下文负责保持语义连续；当前查询负责确认业务事实。**

## 十、可信图表必须具备证据链

### 1. 合法 JSON 不等于可信图表

结构化输出只能保证：

```text
字段存在
类型正确
JSON 可解析
```

它不能保证：

- 数值来自真实查询；
- 维度和指标选对；
- 图表绑定了本轮结果；
- 数据没有被模型补写；
- 查询结果完整；
- 结论没有超出证据范围。

### 2. ChartSpec 应是“数据 + 证据”

ChartSpec 不应只是：

```json
{
  "chart_type": "bar",
  "dimension": "mine",
  "metric": "count",
  "data": []
}
```

还应包含与真实查询绑定的信息：

```text
图表类型
标题
维度
指标
单位
数据行
Call ID
Query Fingerprint
Result Hash
Snapshot Version
完整性信息
```

### 3. Provenance 链

每次 Tool 调用应记录：

- Call ID；
- 规范化参数；
- Query Fingerprint；
- Result Hash；
- Registry Version；
- Schema Hash；
- Snapshot Version；
- Complete / Truncated；
- Row Count / Group Count；
- 刷新时间；
- 查询范围。

### 4. 绑定验证

图表只有满足以下条件才能渲染为可信图表：

```text
ChartSpec.call_id
= 本轮已完成 Tool Call.call_id

ChartSpec.query_fingerprint
= Tool Call.query_fingerprint

ChartSpec.result_hash
= Tool Result.result_hash
```

若绑定失败：

```text
图表块降级或不渲染
正文和其他合法图表继续展示
```

不应因为一个图表失败而让整条回答失败。

### 5. 前端 Renderer 的职责

模型只生成最小业务协议，Renderer 负责：

- 转换为 ECharts 配置；
- 主题；
- 响应式布局；
- 移动端展示；
- 标签密集处理；
- 导出图片；
- 统一交互。

这样可以避免模型直接生成：

- 任意 JavaScript；
- 任意 ECharts option；
- 不受控的前端逻辑；
- 隐藏敏感字段。

## 十一、上下文工程：保存历史不等于模型看到了历史

### 1. 需要区分五种记忆

| 记忆层 | 作用 |
|---|---|
| Visible Memory | 用户看到的聊天 |
| Trajectory Memory | Agent 实际执行过什么 |
| Working Memory | 当前模型真正看到什么 |
| Evidence Memory | 历史事实来自哪里 |
| Current Business Truth | 本轮重新查询得到的当前事实 |

这五者不能混为一谈。

### 2. 两层本地存储

#### localStorage：可见会话

保存：

- 会话标题；
- 用户消息；
- 最终回答；
- 简化后的中文 Tool 活动。

不保存复杂内部字段，适合 UI 展示。

#### IndexedDB：完整轨迹

保存：

- 请求；
- 用户消息；
- Assistant 消息；
- Tool Call；
- Tool Result；
- Retry；
- Error；
- Checkpoint；
- Compaction；
- Telemetry；
- 大型 Tool Result Artifact。

适合审计、恢复和评测。

### 3. Push Context 机制

当前模型不会主动搜索全部历史，而是：

```text
浏览器选择历史
→ 发送 Context Envelope
→ 服务端重建 Working Context
→ 模型读取精选上下文
```

因此：

```text
浏览器保存了什么
≠
本轮模型看到了什么
```

### 4. Archive Memory 与 Working Memory

可以将历史分为：

```text
IndexedDB 全量历史
= Archive Memory

当前筛选出的最近若干回合
= Working Memory
```

历史保存在本地，不代表一定会进入当前 Prompt。

### 5. Atomic Turn

恢复历史时，应尽量以完整回合为单位：

```text
User
Assistant Tool Call
Tool Result
Assistant Final
```

不能只恢复 Tool Call 而丢失 Tool Result，也不能从 Tool Call 和 Tool Result 中间截断。

缺少关联结果或必要推理内容时，该 Tool Chain 不应安全重放，应移除或降级。

### 6. 大结果外置为 Artifact

明细查询可能返回大量数据，不能全部放入 Prompt。

采用：

```text
Tool Result
→ 超过阈值
→ 外置到 Artifact
→ 主轨迹只保存 artifact_id、tool_call_id、hash
```

大对象可以有三种状态：

- Hot：直接进入当前上下文；
- Warm：只保留事实与证据引用；
- Cold：留在本地，但当前不自动加载。

这能减少上下文污染和 Token 消耗。

### 7. Checkpoint 压缩

上下文达到预算阈值后，将旧历史折叠为结构化 Checkpoint。

建议保留：

```text
facts
decisions
constraints
unresolved
evidenceRefs
snapshotVersions
registryVersions
schemaHashes
summary
```

它更接近：

```text
历史快照 + 最近增量日志
```

而不是普通聊天摘要。

Checkpoint 的核心不是“尽量短”，而是保留未来决策所需要的信息。

### 8. 压缩策略的原则

优先保留：

- 未解决问题；
- 用户约束；
- 业务实体；
- 关键事实；
- 证据引用；
- 当前快照版本；
- 关键决策；
- 失败原因。

可以清除或外置：

- 大型原始 Tool Result；
- 重复解释；
- 已失效的临时推理；
- 无法影响后续决策的细节。

## 十二、Agent Runtime 应采用 Workflow 与 Agent 的混合模式

### 1. 两个极端

#### 完全固定 Pipeline

优点：

- 可预测；
- 易测试；
- 易审计。

缺点：

- 难处理自然语言变化；
- 灵活性不足；
- 复杂问题容易分支爆炸。

#### 完全自主 Agent Loop

优点：

- 灵活；
- 能动态规划；
- 适合开放任务。

缺点：

- 工具路径不稳定；
- 容易重复调用；
- 成本和延迟不可控；
- 失败时难以定位；
- 业务前置条件容易被绕过。

### 2. 推荐的混合方式

让代码控制：

- 权限；
- 数据集边界；
- 历史能力是否支持；
- 分析白名单；
- 跨域前置条件；
- 状态转移；
- 停止条件；
- 重试预算；
- 错误处理。

让模型控制：

- 自然语言理解；
- 实体候选抽取；
- 部分 Tool 选择；
- 结果说明；
- 展示意图。

这是一种：

```text
Workflow 守住业务不变量
+
Agent 提供语言理解和局部决策
```

### 3. 跨域任务适合有限状态机

例如到岸成本可以建模为：

```text
开始
→ 已解析实体
→ 已取得矿山—发货地映射
→ 已取得当前报价
→ 已取得当前运费
→ 连接条件验证通过
→ 计算到岸成本
→ 生成答案
```

每个状态定义：

- 允许调用什么；
- 禁止调用什么；
- 必须拥有的证据；
- 失败如何处理；
- 下一步如何转移；
- 什么条件下可以结束。

Agent 的可靠性，本质上取决于状态机是否能表达：

> **什么时候允许进入下一步，什么时候必须停止。**

## 十三、流式响应应该区分用户视图与内部轨迹

### 1. SSE 事件类型

一次业务回合可以拆为：

| 事件 | 用户侧用途 |
|---|---|
| Tool Status | 显示“正在查询报价” |
| Text Delta | 增量展示正文 |
| Final Message | 用服务端定稿替换草稿 |
| Audit | 记录内部用量和上下文 |
| Trajectory | 记录执行轨迹与证据 |
| Done / Error | 结束回合并恢复输入 |

### 2. 为什么不能把内部过程全部展示给用户

用户需要知道：

```text
系统正在查询什么业务信息
```

但不需要知道：

- 内部 Tool 名；
- 原始 JSON；
- JWT；
- Trace ID；
- 推理文本；
- 数据库字段；
- 内部错误堆栈。

因此：

> **可观测性不等于把实现细节全部暴露给用户。**

前端显示业务投影，系统内部保留完整轨迹。

## 十四、如何评测 NL2BI Agent

### 1. 最终答案正确，不代表 Agent 正确

同一个正确数字可能来自：

- 正确 Tool；
- 错误方向但巧合相同；
- 不完整数据但结果碰巧一致；
- 历史记忆；
- 模型猜测。

所以不能只评测最终文本。

应评测：

```text
任务
→ 运行轨迹
→ Tool 调用
→ 受控事实
→ 证据绑定
→ 最终呈现
→ 资源消耗
```

### 2. 第一层：Tool Contract

检查：

- 必须调用的 Tool；
- 禁止调用的 Tool；
- 允许的能力路径；
- 前置条件；
- 调用顺序中真正重要的业务不变量。

例如：

```text
到岸成本必须先取得矿山—发货地映射
```

但不应机械要求所有普通 Tool 必须完全按唯一顺序执行。评测应约束业务不变量，而不是过度约束实现路径。

### 3. 第二层：Oracle 事实

Oracle 通过确定性业务查询或真实 Tool Result 检查：

- 预期行；
- 数值；
- 聚合结果；
- 完整性元数据；
- 快照版本；
- 查询参数。

若无法唯一绑定某次真实 Tool 调用，应报告：

```text
证据绑定失败
```

而不是猜测哪次结果被模型使用。

### 4. 第三层：Presentation 与 Evidence

检查：

- ChartSpec 是否可解析；
- 图表是否绑定正确 Tool；
- Result Hash 是否一致；
- 维度和指标是否符合题意；
- 数据行是否来自受控结果；
- 完整性信息是否一致；
- 是否出现敏感字段。

### 5. 第四层：LLM Judge

适合评价：

- 是否真正理解用户问题；
- 是否解决了任务；
- 语言是否清楚；
- 缺数据时是否妥善处理；
- 说明是否适合业务人员；
- 交互是否自然。

不适合让 LLM Judge 独立判断：

- 权限；
- 租户；
- 数值；
- Tool 参数；
- 快照；
- 证据绑定；
- Schema 合法性。

这些应优先由确定性检查完成。

### 6. 第五层：运行成本

应记录：

- Tool Call 数量；
- LLM 调用次数；
- Prompt Token；
- Completion Token；
- Reasoning Token；
- Cache Token；
- 首个 Tool 时间；
- 首次回答时间；
- 总延迟；
- MCP 耗时；
- 下游 API 耗时；
- 重试次数；
- Oracle 和 Judge 耗时。

一次 Agent 运行应形成完整时间线：

```text
Agent
→ LLM
→ Tool
→ MCP
→ Go API
→ Oracle
→ Judge
```

## 十五、性能与工程问题，以及对应改进

### 1. LLM 成本和延迟过高

#### 原因

一个业务回合可能经历：

```text
首次生成
→ Tool 调用
→ Tool 续写
→ nudge
→ 最终合成
→ 修复
```

每一步都可能重复发送上下文和 Tool Schema。

#### 改进

- 优先减少 LLM 往返次数；
- 设定单任务最大 LLM 调用数；
- 减少无必要的 nudge；
- 复用已有事实；
- 区分简单查询与复杂分析；
- 设置任务级输出预算。

优化优先级应是：

```text
先减少请求次数
→ 再减少输入 Token
→ 再减少输出 Token
→ 最后优化缓存
```

### 2. Tool 路由不稳定

#### 原因

模型先试探工具，失败后再纠偏，造成额外调用。

#### 改进

在首次模型调用前，由 SemanticPolicy 确定：

- Capability Bundle；
- 可用 Tool；
- 必需 Tool；
- 禁用 Tool；
- 是否允许并行；
- 是否必须走分析能力。

这样可以把开放选择收敛到稳定能力包。

### 3. Agent Loop 进入高成本错误路径

#### 原因

只设置统一最大步数，无法区分不同任务的风险和预算。

#### 改进

按任务类型分别设定：

- 最大 LLM 调用次数；
- 最大 Tool 次数；
- 最大重试次数；
- 阶段预算；
- 失败转移；
- 终止条件。

最终应逐步收敛为有限状态机。

### 4. Prompt Cache 不稳定

#### 原因

以下内容频繁变化：

- Tool 列表；
- Tool 顺序；
- 动态指令；
- nudge；
- Context 拼接顺序；
- 序列化方式。

#### 改进

- 固定 Capability Bundle；
- 固定 Tool 顺序；
- 固定 System Prompt；
- 固定 Schema 顺序；
- 固定消息序列化；
- 区分稳定前缀和动态上下文。

Prompt Cache 只能降低重复前缀的计算成本，不能消除额外 LLM 往返。

### 5. 上下文预算缺乏统一模型

#### 原因

上下文处理分散在：

- 历史裁剪；
- Token 估算；
- Tool Schema；
- Provider Window；
- 输出预留；
- Checkpoint；
- Artifact；
- 最终请求构造。

容易出现预算重复计算或前后不一致。

#### 改进

建立不可变的：

```text
ResolvedWorkingContext
```

每次 LLM 调用前一次确定：

- System；
- Tools；
- 历史消息；
- Checkpoint；
- Artifact；
- Token Budget；
- Provider Profile；
- 输出预留。

实际发送给模型的内容必须来自这一份快照。

### 6. 多轮状态一致性风险

#### 原因

浏览器历史、Artifact、Context Event、服务端 Turn 和模型上下文分别管理，刷新或中断后可能出现残缺状态。

#### 改进

引入：

```text
Session Ledger
+
Atomic Turn
+
版本化状态
```

将以下内容统一纳入提交边界：

- 用户消息；
- Tool Call；
- Tool Result；
- Artifact；
- Checkpoint；
- Turn 状态。

### 7. Tool 调用串行导致耗时高

#### 原因

多个互不依赖的查询被串行执行，相同查询也可能重复触发。

#### 改进

- 无依赖 Tool 并发执行；
- 相同参数在单回合内去重；
- 保持结果写回顺序确定；
- 分别记录排队、MCP、下游 API、重试和缓存耗时。

### 8. 简单任务使用过多 Thinking

#### 原因

默认推理等级和输出长度没有按任务复杂度区分。

#### 改进

动态设置：

- Thinking 等级；
- 最大输出；
- 最终合成预算；
- 图表修复预算。

简单明细查询不应使用与跨域计算相同的推理成本。

### 9. Provider 指标不统一

#### 原因

不同模型服务商对以下字段定义不同：

- 输入 Token；
- 输出 Token；
- 缓存 Token；
- 推理 Token；
- TTFT；
- Finish Reason；
- 错误类型。

#### 改进

在 Provider Adapter 边界做统一归一化：

```text
Provider-specific Usage
→ 内部统一指标
```

便于比较模型、版本和请求策略。

### 10. 缺乏统一质量回归闭环

#### 原因

质量、成本、延迟、安全和上下文由不同系统分别判断，难以确认某项优化是否真正有效。

#### 改进

采用 Eval Driven：

```text
建立基线
→ 修改一个变量
→ 运行真实任务
→ 比较质量、成本、延迟和安全
→ 保留或回滚
```

需要同时观察：

- 最终答案；
- Tool 路径；
- Oracle；
- Evidence；
- Token；
- Cache；
- 调用次数；
- TTFT；
- Tool 耗时；
- 浏览器持久化链路。

## 十六、可以提炼出的通用设计方法

### 方法一：先定义事实，再定义 Agent

不要先问：

> 用哪个模型、哪个框架？

应先问：

- 什么是业务事实？
- 什么是当前事实？
- 谁可以访问？
- 哪些事实可以关联？
- 哪些结果允许对外展示？
- 什么情况下必须拒绝？

### 方法二：把不可妥协的规则写成代码

凡是可以写成以下形式的规则，都应尽量代码化：

```text
枚举
状态机
Schema
Validator
权限检查
数据库约束
白名单
快照校验
证据绑定
```

### 方法三：让非法状态不可表示

例如：

- `tenant_id` 不允许由模型填写；
- dataset、dimension、metric 使用枚举；
- 无效参数组合不允许通过 Schema；
- 不支持的历史查询不提供对应 Tool；
- 未完成映射时，分析 Tool 不可用；
- 未绑定证据的图表不能渲染。

### 方法四：聚合和循环交给代码

大量明细数据、分页、过滤、去重和聚合交给数据库或服务端完成。

模型只消费：

```text
高信号、结构化、完整且带证据的结果
```

### 方法五：证据必须贯穿执行链

不要只在最后生成引用，而应从 Tool 执行时就记录：

```text
Call ID
→ 参数
→ 查询指纹
→ 结果 Hash
→ 快照版本
→ 完整性
→ 输出绑定
```

### 方法六：评测过程与结果，但不要迷信固定路径

应强制检查真正的业务不变量，例如：

- 租户不能越权；
- 到岸成本必须有合法映射；
- 聚合必须使用完整数据；
- 图表数据必须来自真实结果。

但如果多条不同路径都能得到同样可信的结果，不应因为路径不同而机械判错。

### 方法七：上下文只保留未来决策需要的信息

上下文工程的目标不是保留最多历史，而是保留：

```text
最少但足够改变当前决策的信息
```

尤其要区分：

```text
语义记忆可以继承
当前业务事实需要刷新
```

## 十七、最终的完整链路

以问题：

> 帮我看看各矿山目前分别有多少条报价，用柱状图展示，最多展示二十个矿山。

为例，生产级链路应是：

```text
验证身份
→ 验证租户与权限
→ 判断“当前 + 聚合 + 图表”意图
→ 确定报价数据集
→ 选择受治理分析能力
→ 生成严格参数
→ 校验 Schema、枚举和参数边界
→ 注入认证上下文
→ 查询 Current View
→ 执行白名单聚合
→ 返回分组数据、完整性和快照证据
→ 生成最小 ChartSpec
→ 校验图表结构
→ 校验敏感字段
→ 校验 Call ID
→ 校验 Query Fingerprint
→ 校验 Result Hash
→ Renderer 转换为图表
→ SSE 返回用户可见结果
→ 保存完整轨迹
→ Eval 验证 Tool、Oracle、图表和运行成本
```

最终可以将整套方法压缩为五句话：

1. **业务系统先于 Agent，Agent 不得成为第二套事实链。**
2. **模型负责理解和表达，代码负责边界和事实。**
3. **Tool 是业务契约，不是数据库能力的简单代理。**
4. **当前数据必须重新查询，历史上下文不能冒充当前事实。**
5. **可信结果不仅要正确，还要能够证明它为什么正确、来自哪里以及是否完整。**
