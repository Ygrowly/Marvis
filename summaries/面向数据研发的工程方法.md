
### **结论：文章的核心不是“用 Agent 自动写埋点”，而是把数据研发需求改造成一条可验证、可回放、可复用、有人负责放行的工程流程。**

Hermes Agent 的价值在于：让 AI 负责整理事实、调用工具、执行预演、暴露风险和沉淀规则；让人负责业务口径、风险判断、敏感字段、下游影响以及生产发布。文章试图解决的根本问题，是避免 AI 在信息不完整、依据不透明的情况下直接产出“看起来完整”的方案。

---

## **一、What：文章要解决什么问题**

### **1. 业务需求与数据实现之间存在信息断层**

以“查看昨天各体裁发布量”为例，表面上只是写一条 SQL，实际至少需要确认：

- “发布量”对应哪个业务动作；
- “昨天”采用业务发生时间、事件时间还是入库时间；
- “体裁”对应哪个字段或维度；
- 是否存在历史同类埋点；
- 指标是否已被下游使用；
- 新增字段需要修改哪些表、任务或配置；
- 是否涉及敏感字段；
- 发布前由谁确认，失败后如何回退。

因此，数据研发的难点并不只是编码，而是把分散在需求文档、聊天记录、历史方案、数仓结构和生产系统中的信息重新拼起来。

### **2. 传统 AI 自动化存在三类风险**

第一，**事实不完整**。AI 可能遗漏历史口径、上下游依赖或既有字段。

第二，**判断依据不透明**。AI 给出方案，却无法清楚说明读了哪些材料、调用了哪些系统、哪些结论只是推断。

第三，**自动执行不可控**。一旦 AI 直接接近生产系统，错误可能从文本层面扩大为数据污染、指标错误或配置事故。

### **3. 真正需要自动化的是“判断前准备”**

文章没有把 Agent 定位成最终决策者，而是定位为流程编排者。其任务是把判断所需的材料和证据准备完整：

1. 收集需求及相关上下文；
2. 检索历史事实和规则；
3. 生成候选方案；
4. 调用系统进行预演；
5. 暴露风险和待确认事项；
6. 等待责任人确认；
7. 再进入生产动作；
8. 将过程和经验归档。

---

## **二、Why：为什么要这样改造**

## **1. 为什么不能只靠一段 Prompt**

单纯依赖 Prompt 有两个根本缺陷：

- 同一需求换一种表达，模型可能改变输出结构和检查重点；
- 模型可以生成方案，却不一定遵循固定的事实来源、工具边界和人工确认要求。

因此，稳定性不能只靠提示词，而要靠流程契约。每个能力模块都必须明确：

- 输入是什么；
- 可以执行什么；
- 不能执行什么；
- 输出什么产物；
- 失败时如何处理；
- 哪些条件下必须暂停；
- 哪些经验可以回写为规则。

Prompt 负责表达意图，流程契约负责约束行为。

## **2. 为什么选择单 Agent，而不是多个 Agent**

文章采用“单 Agent 编排 + 多能力模块”的方式，而不是让多个独立 Agent 相互协作。

原因是：此类需求高度依赖统一上下文。若拆成多个 Agent，容易出现上下文重复传递、阶段结论丢失、责任边界模糊和最终结果难以追溯的问题。

单 Agent 负责：

- 保持全流程上下文；
- 调度不同阶段；
- 统一理解任务状态；
- 串联人工确认点。

能力模块负责：

- 固化稳定动作；
- 约束工具调用；
- 定义输入输出；
- 处理失败和停顿；
- 沉淀可复用经验。

二者形成“统一上下文、模块化执行”的结构。

## **3. 为什么要使用工作区、看板和规则包**

这三个组件分别解决不同问题：

| 组件 | 解决的问题 | 核心作用 |
|---|---|---|
| 工作区 | 依据散落 | 保存需求、讨论、事实、评审结论和交付物 |
| 看板 | 状态不透明 | 展示阶段、责任人、阻断项和人工确认 |
| 规则包 | 经验难复用 | 将历史判断转化为可执行检查清单 |

它们共同构成了任务的“外部记忆”和“过程控制面”。

如果只有聊天记录，信息难以定位；如果只有规则，没有具体事实；如果只有工作区，没有推进机制。因此三者必须联动。

## **4. 为什么需要长期记忆和技能沉淀**

数据研发中的大量知识不是一次性信息，而是反复出现的团队经验，例如：

- 哪些字段不能直接使用；
- 某类指标默认采用什么时间口径；
- 某张表的字段存在历史兼容问题；
- 某类变更必须经过哪些角色确认；
- 某类下游任务容易受到影响。

文章将信息分层：

- **短期信息**：只服务当前对话；
- **中期交互**：保存近期任务推进和反馈；
- **长期知识**：保存稳定事实和团队规则；
- **技能库**：保存可重复执行的流程能力。

这样做不是让系统“记住更多”，而是让不同性质的信息进入正确的位置，避免临时信息污染长期知识，也避免关键经验随任务结束而消失。

## **三、How：整体方案如何运转**

## **1. 用工作区承接单个需求**

每个需求建立独立工作区，集中保存：

- 原始需求；
- 会议纪要；
- 历史讨论；
- 已确认事实；
- 待澄清问题；
- 候选方案；
- 预演结果；
- 评审结论；
- 最终交付产物；
- 运行日志和审计记录。

工作区相当于任务的证据档案，保证后续任何人都能恢复任务上下文。

## **2. 用看板推动状态机流转**

需求不是一次性完成，而是按照状态逐步推进：

```text
进入 → 设计 → 预演 → 评审 → 交付
```

每个阶段都应包含：

- 当前状态；
- 阶段产物；
- 责任人；
- 待解决问题；
- 阻断条件；
- 是否需要人工确认。

看板的作用不是简单展示进度，而是把“下一步能不能继续”显式化。

## **3. 用会议纪要补充协作语境**

会议纪要不能直接替代事实源，但可以补充：

- 需求背景；
- 已达成的业务共识；
- 责任人；
- 尚未解决的问题；
- 特殊约束；
- 需要进一步确认的事项。

文章明确区分了聊天和事实：

- 聊天记录补充语境；
- 工作区保存证据；
- 系统预演验证结果；
- 生产系统作为最终事实源。

## **4. 用规则包驱动检查**

规则包回答的是“应该怎样判断”，而不是“当前任务具体是什么”。

例如，一个规则包可以规定：

- 先确认指标业务定义；
- 再确认时间口径；
- 检查是否存在历史同类字段；
- 检查字段是否被下游使用；
- 识别敏感字段；
- 评估表结构和任务链路影响；
- 生成预演方案；
- 未完成人工确认不得发布。

规则包使每次任务都按照相对稳定的检查顺序执行。

## **5. 用结构化接口连接生产系统**

文章反对让 Agent 依赖页面识别和临场点击接近生产系统，而是建议将系统动作封装为结构化接口，例如：

- 查询；
- 字段绑定；
- 变更生成；
- 影响分析；
- 预演；
- 发布；
- 发布后验证；
- 回滚或撤销。

结构化接口应具备：

- 参数明确；
- 输入约束清晰；
- 返回结果结构化；
- 失败状态可识别；
- 操作过程可审计；
- 权限边界可控制。

这样，Agent 不是“凭感觉操作系统”，而是通过可验证的命令执行动作。

---

## **四、端到端流程：从需求到交付**

### **第一步：需求进入**

业务提出需求，例如查看“昨天各体裁发布量”。

Agent 不立即写 SQL，而是先建立工作区，并收集：

- 原始需求；
- 相关文档；
- 历史聊天；
- 会议纪要；
- 责任人；
- 已知限制。

### **第二步：事实整理**

Agent 检索历史数据和规则，整理出：

- 指标定义；
- 时间定义；
- 维度定义；
- 现有数据来源；
- 历史同类实现；
- 下游使用情况；
- 可能存在的歧义。

如果事实不足，就生成待澄清项，而不是自行补全。

### **第三步：方案设计**

Agent 基于事实和规则生成候选方案，包括：

- 埋点或字段设计；
- 表结构变更；
- 任务链路变更；
- 指标计算逻辑；
- 下游影响；
- 权限与敏感性分析；
- 需要人工裁决的地方。

该阶段的输出应是“可评审方案”，而不是直接生产代码。

### **第四步：系统预演**

在不影响生产数据的环境中验证：

- 字段是否存在；
- 绑定关系是否正确；
- SQL 或配置是否可执行；
- 表结构是否兼容；
- 下游任务是否受影响；
- 数据结果是否符合预期；
- 是否产生异常或重复采集。

预演的目的，是把文本方案转化为系统证据。

### **第五步：人工评审**

评审重点不是检查 Agent 是否写得完整，而是判断：

- 业务口径是否成立；
- 指标定义是否准确；
- 风险是否可接受；
- 敏感字段是否合规；
- 下游影响是否可控；
- 是否允许进入生产。

Agent 可以准备证据，但不能代替责任人承担这些判断。

### **第六步：生产发布**

只有满足发布条件后，才能执行生产动作。发布过程应包括：

- 责任人确认；
- 权限校验；
- 结构化命令调用；
- 操作记录；
- 发布结果；
- 发布后验证；
- 异常处理或回滚。

### **第七步：归档和经验回写**

任务完成后，把可复用内容沉淀为：

- 新规则；
- 新技能；
- 常见失败模式；
- 工具调用模板；
- 评审检查项；
- 典型案例。

而只对本次任务有效的临时信息则保留在工作区，不进入长期规则。

---

## **五、风险治理：为什么必须设置人工确认线**

文章将生产前治理概括为三道门。

### **1. 事实源门**

确认方案所依据的信息是否可信：

- 需求是否有明确来源；
- 业务定义是否经过确认；
- 字段和表是否真实存在；
- 历史结论是否仍然有效；
- 下游依赖是否有证据。

没有可靠事实，Agent 只能停留在候选方案阶段。

### **2. 预演门**

确认系统层面是否验证通过：

- 方案能否执行；
- 数据结果是否符合预期；
- 结构变更是否兼容；
- 下游链路是否正常；
- 是否出现异常数据。

没有预演结果，不能直接进入生产。

### **3. 责任门**

确认责任人是否完成明确授权：

- 业务方确认指标口径；
- 数据方确认技术方案；
- 风险相关角色确认敏感性和影响；
- 发布责任人确认生产操作。

没有责任人确认，Agent 只能等待，不能继续写入生产。

这三道门的本质是把“自动化效率”限制在“可证明安全”的范围内。

## **六、文章设计背后的第一性原理**

### **1. 数据研发的本质是证据链，而不是代码生成**

代码只是最终表达形式。真正决定结果正确性的，是以下链条是否成立：

```text
业务问题
→ 业务定义
→ 数据事实
→ 技术方案
→ 系统预演
→ 人工确认
→ 生产结果
```

任一环节缺失，最终产物都可能表面正确、实际错误。

### **2. AI 的核心价值是降低信息组织成本**

Agent 最适合处理：

- 材料收集；
- 信息检索；
- 历史比对；
- 依赖分析；
- 方案整理；
- 工具调用；
- 状态推进；
- 过程记录。

而以下工作仍需要人承担：

- 业务语义裁决；
- 风险取舍；
- 责任承担；
- 生产授权。

因此，合理的自动化不是“人被 AI 替代”，而是“人从低价值的信息搬运中释放出来”。

### **3. 越接近生产，自动化越要转向可验证和可审计**

离生产较远时，可以接受探索性生成；接近生产时，必须提高约束强度：

```text
探索阶段：允许生成候选方案
设计阶段：要求事实和规则
预演阶段：要求系统验证
评审阶段：要求责任人确认
生产阶段：要求权限、审计和可回退
```

也就是说，自动化程度不能只看技术能力，还要看风险距离。

### **4. 可复用能力必须沉淀为契约，而不是经验口号**

真正可复用的不是“写一段更好的提示词”，而是把经验固化为：

- 输入约束；
- 工具边界；
- 输出格式；
- 暂停条件；
- 失败处理；
- 确认条件；
- 经验回写机制。

只有这样，经验才能从个人记忆转化为团队资产。

## **七、文章方案的改进原因与改进效果**

| 改进方向 | 原有问题 | 方案改进 | 预期效果 |
|---|---|---|---|
| 从一次性问答转向流程编排 | 输出容易漂移且不可追踪 | 使用状态机和阶段产物 | 过程可回放 |
| 从单一 Prompt 转向流程契约 | 检查重点不稳定 | 固化输入、边界、输出和停顿条件 | 执行更稳定 |
| 从多 Agent 协作转向单 Agent 编排 | 上下文容易断裂 | 单 Agent 统一调度能力模块 | 上下文一致 |
| 从隐式记忆转向规则资产 | 专家经验难复用 | 将经验沉淀为规则包和技能 | 团队能力可继承 |
| 从聊天记录转向工作区证据 | 信息难检索、难审计 | 集中保存事实和产物 | 依据清晰 |
| 从后台自动执行转向看板协作 | 人不知道 AI 做到哪一步 | 暴露状态、阻断项和责任人 | 协作可见 |
| 从页面点击转向结构化接口 | 操作脆弱、结果难验证 | 封装明确参数和结构化返回 | 系统调用可验证 |
| 从直接发布转向预演加确认 | 生产风险集中 | 先预演、再人工确认、后发布 | 降低事故风险 |
| 从任务结束即遗忘转向经验回写 | 相同问题反复处理 | 沉淀规则和失败模式 | 持续改进 |

---

## **八、如何衡量方案是否真正有效**

文章最后强调，不能只看 Agent 是否“能跑通”，而要用连续样本验证工程效果，重点观察：

- 需求准备时间是否减少；
- 端到端交付周期是否缩短；
- 评审一次通过率是否提高；
- 返工次数和返工原因是否减少；
- 预演拦截了多少问题；
- 人工确认点是否集中在真正高风险环节；
- 规则和技能被复用的次数；
- 生产事故和回滚次数是否下降。

这些指标必须能与看板、日志、确认记录和系统执行结果对应，否则只能说明流程“看起来规范”，不能证明它真正有效。

## **九、最终归纳**

文章提出的是一种面向数据研发的 Agent 工程方法：

- **What**：把埋点和指标需求改造成可追踪的端到端工作流；
- **Why**：因为数据研发的主要风险来自事实遗漏、口径不清、上下文丢失和生产执行不可控；
- **How**：通过单 Agent 编排、能力模块、工作区、看板、规则包、长期记忆、结构化接口、系统预演和人工确认，建立完整证据链。

其核心原则可以概括为：

> **AI 负责把问题整理到足够可判断，人负责作出关键判断并承担生产责任。**

这也是 Hermes Agent 从“会回答问题”走向“能够稳定交接和执行流程”的关键。
