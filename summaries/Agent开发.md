### **核心结论**

这篇文章表面上总结 Agent 岗面试题，实质上提供了一套从“能调用模型”走向“能设计可靠 Agent 系统”的学习框架：以真实需求为起点，以模型能力边界为约束，以工程机制保障可靠性，再通过评估和复盘形成闭环。

## **一、第一性原理：Agent 开发究竟在解决什么问题**

### **1. 定义：Agent 是什么**

Agent 不是简单的聊天机器人，也不是固定的 Chain。它的基本结构是：

> **目标理解 → 状态维护 → 任务规划 → 工具调用 → 环境反馈 → 结果修正**

其核心区别在于：传统程序的执行路径主要由开发者预先决定，而 Agent 会根据上下文和环境反馈动态决定下一步行动。

### **2. 根本矛盾**

Agent 系统需要同时满足四个目标：

| 目标 | 具体要求 | 主要矛盾 |
|---|---|---|
| 能力 | 理解需求、检索信息、调用工具 | 模型并不真正理解，只是在概率生成 |
| 自主性 | 能拆解任务并连续执行 | 自主性越强，失控风险越高 |
| 可靠性 | 结果正确、流程不死循环 | LLM 输出具有随机性 |
| 经济性 | Token、延迟、算力可控 | 更长上下文通常意味着更高成本 |

因此，Agent 开发的本质不是“如何把 Prompt 写得更好”，而是：

> **如何在不确定的模型之上，构建可控、可恢复、可评估的执行系统。**

### **3. 面试真正考查的三层能力**

第一层是使用能力：是否使用过 RAG、MCP、LangChain、Agent SDK 等。

第二层是理解能力：是否理解为什么要做记忆分层、结构化 Prompt、工具路由或模型网关。

第三层是工程判断力：能否在 Token、延迟、准确率、安全性和开发成本之间做取舍。

文章认为，越接近第三层，越难通过背诵获得，也越能体现真实水平。

---

## **二、完整系统框架：从需求到可靠 Agent**

可以将 Agent 系统抽象为以下闭环：

```text
用户目标
  ↓
需求澄清与约束提取
  ↓
任务拆解与 Agent 路由
  ↓
上下文构建与记忆检索
  ↓
模型决策
  ↓
工具调用
  ↓
权限、参数与状态校验
  ↓
执行、反馈与恢复
  ↓
结果验证
  ↓
评估、日志与持续优化
```

这条链路中的每个环节，都对应文章中的一类面试问题。

## **三、需求理解：把模糊愿望变成可执行目标**

### **定义**

用户常说“让 AI 更聪明”“更有活人感”“帮我分析一下”，这些不是技术需求，而是模糊目标。

可执行需求至少应包含：

- 目标：最终要完成什么；
- 对象：服务谁、处理什么数据；
- 输出：结果以什么形式呈现；
- 约束：时间、风格、权限、成本等限制；
- 评价标准：什么叫做完成得好。

### **为什么需要需求澄清**

如果直接让模型执行，模型只能根据概率猜测用户意图。需求越模糊，错误方向越多，后续的 Prompt、工具和评估都会建立在错误目标上。

因此，需求澄清不是增加交互，而是在降低整个系统的无效执行成本。

### **方案：Counter-Questioning**

当关键约束缺失时，Agent 不直接执行，而是主动询问：

```text
模糊需求
  ↓
识别缺失变量
  ↓
判断哪些变量影响最大
  ↓
优先询问关键问题
  ↓
形成结构化任务描述
```

例如“做一份市场分析”可以拆解为：

```json
{
  "target": "分析对象",
  "audience": "报告读者",
  "scope": "时间与地域范围",
  "criteria": "重点指标",
  "format": "输出格式",
  "constraints": "限制条件"
}
```

### **边界**

不能无限追问。有效澄清应满足：

- 问题会显著影响最终结果；
- 用户能快速回答；
- 能减少后续返工；
- 不应询问模型可以自行推断的低价值细节。

### **评估方法**

文章提到但尚未充分实践的关键问题是：如何判断澄清问题是否有效。

可使用以下指标：

- 澄清后任务成功率；
- 用户修改需求的次数；
- 首次结果接受率；
- 澄清轮数；
- 用户中途退出率；
- 每个问题带来的信息增益。

## **四、上下文工程：解决有限窗口下的信息取舍**

### **定义**

上下文工程不是简单地“把更多信息塞给模型”，而是：

> **在有限 Token 预算下，选择最相关、最可靠、最有用的信息，并以合适结构提供给模型。**

### **根本原因**

上下文窗口有限，且上下文并非越长越好：

- 成本增加；
- 延迟增加；
- 重点信息被稀释；
- 模型更容易忽略中间内容；
- 旧信息可能与新信息冲突。

所以“上下文爆了”本质上是一个信息压缩和优先级管理问题。

### **为什么 FIFO 不够**

先进先出只依据时间排序，但重要性不等于新旧程度。

例如用户在对话开始时提出的长期约束，如果因为时间较早被删除，Agent 就会产生结构性错误。

### **记忆分层方案**

文章提到四类机制：

| 层级 | 作用 | 特征 |
|---|---|---|
| Working Memory | 当前任务状态 | 实时、短暂、优先级最高 |
| Short-term Memory | 最近对话与中间结果 | 保留近期上下文 |
| Long-term Memory | 用户偏好、稳定事实 | 跨会话持久化 |
| External Retrieval | 外部知识与历史资料 | 按需检索 |

整体流程可以表示为：

```text
原始对话
  ↓
提取任务状态与重要事实
  ↓
短期对话摘要
  ↓
高价值信息写入长期记忆
  ↓
当前任务按需检索
  ↓
拼接最小有效上下文
```

### **上下文压缩方法**

#### **1. 摘要压缩**

将多轮对话压缩成：

- 当前目标；
- 已完成工作；
- 未解决问题；
- 关键约束；
- 重要决策；
- 待执行步骤。

#### **2. 重要性筛选**

为信息建立优先级：

```text
系统约束 > 当前任务状态 > 用户明确偏好 > 关键事实 > 普通历史对话
```

#### **3. 语义检索**

不按时间取历史，而是按当前任务相关性检索。

#### **4. 结构化状态替代原始对话**

与其保留几十轮自然语言，不如保存：

```json
{
  "goal": "...",
  "constraints": ["..."],
  "decisions": ["..."],
  "pending_tasks": ["..."],
  "known_facts": ["..."]
}
```

#### **5. Token Budget 管理**

为不同模块预留预算：

```text
系统指令：固定预算
任务状态：高优先级预算
工具说明：按需加载
历史对话：压缩预算
检索结果：动态预算
输出：预留预算
```

### **边界**

压缩不能破坏：

- 否定条件；
- 数字和时间；
- 用户明确约束；
- 因果关系；
- 未完成任务；
- 权限与安全信息。

因此，摘要系统应同时保留“压缩文本”和“关键结构化字段”，不能完全依赖自由文本摘要。

## **五、Prompt 设计：让模型更容易正确执行**

### **定义**

Prompt 不是一段自然语言，而是模型执行任务时使用的控制界面。

高质量 Prompt 至少要明确：

- 角色；
- 目标；
- 输入；
- 输出；
- 约束；
- 工具使用规则；
- 异常处理；
- 判断标准。

### **为什么结构化 Prompt 更有效**

文章从 Attention 角度给出解释：

- XML、JSON Schema、分隔符提供了清晰锚点；
- 不同信息被显式分区；
- 任务、约束和示例不容易混淆；
- 模型在长上下文中更容易定位重点；
- 输出结构更容易被程序校验。

可以理解为：

> 结构化 Prompt 并没有直接提升模型的智力，而是降低了模型从输入中提取任务结构的难度。

### **推荐结构**

```xml
<role>你是什么角色</role>
<goal>需要完成什么目标</goal>
<context>可使用的背景信息</context>
<constraints>必须遵守的限制</constraints>
<tools>工具及使用条件</tools>
<workflow>执行步骤</workflow>
<output_schema>输出格式</output_schema>
<failure_policy>失败时如何处理</failure_policy>
```

### **One-shot 的边界**

示例可以帮助模型理解格式和任务标准，但存在两个风险：

- 示例差异不足，模型过度模仿；
- 示例包含隐含错误，模型复制错误模式。

因此示例应：

- 覆盖不同类型；
- 保留必要差异；
- 说明哪些内容不可机械复制；
- 与 Schema 和约束保持一致。

---

## **六、Tool Calling：从“能调用”到“不会乱调用”**

### **问题本质**

工具调用包含三类风险：

1. **选择错误**：调用了不合适的工具；
2. **参数错误**：参数缺失、类型错误或语义错误；
3. **执行失控**：重复调用、死循环、超时、重复副作用。

因此，工具可靠性不能只依靠模型判断，需要 Prompt、Schema、Runtime 和权限系统共同保障。

### **事前约束：工具设计**

工具描述应明确：

- 何时使用；
- 何时禁止使用；
- 输入参数含义；
- 参数之间的约束；
- 是否有副作用；
- 是否需要用户确认；
- 失败时返回什么；
- 是否允许重复调用。

工具接口应尽量窄，而不是提供一个“万能工具”。

### **路由设计**

可以先由路由器判断：

```text
用户请求
  ↓
意图识别
  ↓
候选工具筛选
  ↓
权限检查
  ↓
参数生成
  ↓
工具调用
```

这样可以减少所有工具同时暴露给模型造成的选择噪声。

### **运行时状态机**

文章提到的异步状态机包括：

- checkpoint；
- 重试；
- 幂等；
- 超时；
- 回滚；
- 状态恢复；
- watermark；
- 去重。

其核心不是让模型更聪明，而是让系统即使面对错误决策，也能安全地继续运行或停止。

```text
准备调用
  ↓
参数校验
  ↓
权限校验
  ↓
执行中
  ├─ 成功 → 记录结果
  ├─ 可重试失败 → 重试
  ├─ 超时 → 中止或恢复
  └─ 不可恢复失败 → 回滚并报告
```

### **如何防止死循环**

至少需要：

- 最大步骤数；
- 同一工具重复调用上限；
- 参数或状态变化检测；
- 调用结果去重；
- 进度检测；
- 总 Token 和时间上限；
- 连续失败熔断；
- 超限后转人工或返回中间结果。

### **幂等性**

对于有副作用的工具，必须设计幂等键：

```text
idempotency_key = task_id + action_type + logical_step
```

这样网络重试不会重复创建订单、发送消息或执行写入。

### **Human-in-the-loop**

以下操作通常不应完全自动执行：

- 删除数据；
- 发送外部消息；
- 付款或交易；
- 修改权限；
- 公开发布内容；
- 不可逆的生产操作。

Agent 可以负责准备和解释，但最终动作应要求确认。

## **七、RAG 的演进：从被动检索到主动研究**

### **基础 RAG**

```text
问题 → 向量检索 → 拼接文档 → 生成答案
```

优点是简单、成本低；缺点是检索策略固定，无法处理复杂任务。

### **多重 RAG**

针对不同知识类型使用不同检索路径：

- 向量检索：语义相似内容；
- 关键词检索：精确术语；
- 图数据库：实体关系；
- SQL：结构化数据；
- 时间检索：最新信息；
- API：实时状态。

核心不是“检索越多越好”，而是根据问题类型选择正确数据源。

### **Agentic Search**

Agent 自主决定：

- 是否需要检索；
- 搜索什么；
- 搜索几轮；
- 是否改写查询；
- 是否交叉验证；
- 何时停止。

其代价是更高的延迟、Token 和错误传播风险，因此需要设置搜索预算和停止条件。

### **Agentic Memory**

记忆不再只是存储历史对话，而是由 Agent 判断：

- 什么值得记住；
- 记多久；
- 何时调用；
- 是否需要更新；
- 信息是否已经过时。

### **RAG 数据清洗**

数据质量直接决定检索质量。应处理：

- 重复内容；
- 无效页面；
- 标题与正文错配；
- 过长文档；
- 表格和代码结构损失；
- 时间和版本信息；
- 权限隔离；
- 来源可信度。

切分不应只按固定字符数，还应结合标题、段落、语义和实体关系。

---

## **八、安全：Prompt Injection 不是单纯的文本过滤问题**

### **威胁来源**

恶意指令可能出现在：

- 用户输入；
- 网页内容；
- 检索文档；
- 工具返回值；
- 文件内容；
- 其他 Agent 的输出。

关键原则是：

> **外部内容是数据，不是指令。**

### **为什么简单过滤不够**

攻击者可以通过：

- 改写表达；
- 编码；
- 多轮诱导；
- 隐藏在文档或网页中；
- 伪装成系统指令；
- 诱导 Agent 调用高权限工具。

因此，安全不能只依靠关键词过滤。

### **指令层级**

文章引用的核心思想是：

```text
系统指令
  >
开发者指令
  >
用户指令
  >
外部数据
```

当不同来源发生冲突时，低优先级内容不能覆盖高优先级规则。

### **沙盒化**

高风险工具或外部内容应放在隔离环境中：

- 限制网络访问；
- 限制文件权限；
- 限制命令执行；
- 限制工具范围；
- 设置资源上限；
- 记录全部行为。

### **纵深防御**

```text
输入分类
  ↓
可信度标记
  ↓
Prompt 中隔离数据与指令
  ↓
工具权限控制
  ↓
参数校验
  ↓
输出校验
  ↓
审计与告警
```

### **边界**

不能把所有外部文本都当作恶意内容，也不能仅依赖模型“自觉遵守”。安全机制必须尽可能下沉到权限、网络、运行时和数据层。

## **九、LLM 基础与模型工程**

### **1. Attention 与 Prompt**

Attention 通过 Query、Key、Value 建立 Token 间的关联。结构化 Prompt 的作用，是为关键信息提供更清晰的边界和关系线索，降低长文本中的信息检索难度。

但它不是绝对保证。结构化格式仍可能被长上下文、冲突指令和错误示例削弱。

### **2. Pretrain 与 LoRA**

- Pretrain：学习通用语言和世界知识；
- LoRA：在较低成本下调整特定任务或领域行为。

应优先通过 Prompt、检索和工具解决知识更新问题；只有当任务需要稳定改变模型行为时，才考虑微调。

### **3. LLM as a Judge**

适合评估：

- 风格；
- 完整性；
- 相关性；
- 多候选结果比较。

局限包括：

- Judge 自身会产生偏差；
- 对表面流畅度过度奖励；
- 可能偏好与自己相似的答案；
- 难以判断事实真实性。

因此应结合：

- 规则校验；
- 参考答案；
- 人工抽检；
- 真实业务指标；
- 多模型交叉评估。

### **4. 幻觉处理**

不能只依靠 Prompt 要求“不要幻觉”，应采用组合策略：

- RAG 提供依据；
- 限制回答范围；
- 要求引用来源；
- 输出结构化置信度；
- 对关键事实进行二次验证；
- 无证据时允许拒答；
- 高风险领域引入人工审核。

### **5. 速度与质量**

应根据任务分层：

- 路由、分类、摘要：小模型；
- 复杂规划、推理：强模型；
- 高风险决策：强模型加验证；
- 简单工具参数生成：专用模型或规则。

不要让所有任务都使用最强模型。

## **十、Agent 架构与编排**

### **单 Agent 与多 Agent**

单 Agent 适合：

- 任务边界清晰；
- 工具数量有限；
- 流程不复杂；
- 需要较低延迟。

多 Agent 适合：

- 任务具有明显专业分工；
- 不同模块需要独立上下文；
- 可以并行执行；
- 需要隔离复杂性。

但多 Agent 会增加：

- 通信成本；
- 状态同步难度；
- 错误传播；
- 调试复杂度；
- Token 消耗。

因此不能为了“看起来高级”而拆分 Agent。

### **Sub-Agent 设计问题**

应明确：

- 是否并行；
- 是否异步；
- 是否共享上下文；
- 谁负责聚合；
- 是否可以互相调用；
- 失败如何恢复；
- 是否需要优先级调度。

### **路由原则**

路由器应基于：

- 任务类型；
- 所需工具；
- 数据来源；
- 风险等级；
- 成本和延迟预算；
- Agent 当前负载。

路由结果最好可解释、可记录、可回放。

## **十一、AI Infra：从 Demo 走向生产**

文章认为，面试重点正在从 Prompt 和 Chain，扩展到基础设施。

### **模型网关**

模型网关通常负责：

- 统一模型接口；
- 模型路由；
- 限流；
- 重试；
- 降级；
- 成本统计；
- 日志；
- 敏感信息处理；
- 供应商切换。

### **Agent 网关**

相比模型网关，Agent 网关还需要处理：

- Agent 路由；
- 工具权限；
- 会话状态；
- 任务级超时；
- 并发控制；
- 审计；
- 多租户隔离。

### **Eval 平台**

完整评估不应只看“回答像不像”，而应覆盖：

```text
输入样本
  ↓
模型或 Agent 执行
  ↓
轨迹记录
  ↓
自动评估
  ↓
人工抽检
  ↓
指标分析
  ↓
Prompt、模型或工具迭代
```

重点指标包括：

- 任务成功率；
- 工具选择准确率；
- 参数正确率；
- 幻觉率；
- 失败恢复率；
- 平均延迟；
- Token 成本；
- 用户满意度；
- 人工接管率。

---

## **十二、MCP 与 Skill：能力标准化**

### **MCP**

MCP 更接近一种工具和上下文的标准化连接协议，解决 Agent 如何发现和调用外部能力。

### **Skill**

Skill 更接近可复用的任务能力封装，通常包含：

- 目标；
- 工作流程；
- Prompt；
- 工具组合；
- 输出规范；
- 失败处理。

### **二者关系**

可以简单理解为：

```text
MCP：连接能力
Skill：组织能力
Agent：选择并编排能力
```

未来 Agent 开发可能从“每次重新开发”转向“组合标准化能力模块”。但标准化也会带来权限、版本、兼容性和供应链安全问题。

---

## **十三、工程选型：技术名称不是答案，取舍才是答案**

文章以 Vercel AI SDK 与 LangChain 的比较为例，强调面试官真正关心的是：

- 为什么选它；
- 它解决了什么问题；
- 它的限制是什么；
- 什么时候不该使用；
- 替代方案是什么；
- 迁移成本如何。

一个合格的技术选型回答应遵循：

```text
业务约束
  ↓
候选方案
  ↓
关键指标
  ↓
Trade-off
  ↓
最终选择
  ↓
验证结果
```

不要回答“大家都在用，所以我用了”，而应说明技术选择与实际约束之间的因果关系。

---

## **十四、面试复盘：把经历转化为能力**

### **问题本质**

做过项目不等于掌握项目。只有当你能解释设计决策、权衡和结果，经验才真正转化为能力。

### **推荐复盘模板**

对每个项目决策，用以下结构整理：

```text
问题：系统遇到了什么困难？
原因：为什么会发生？
方案：采用了什么设计？
机制：方案为什么有效？
权衡：放弃了什么，付出了什么？
结果：指标或体验如何变化？
边界：什么时候该使用其他方案？
```

例如“上下文爆了”：

```text
问题：长对话超出 Token 限制
原因：原始历史消息线性增长
方案：记忆分层、摘要、检索和预算管理
机制：只保留当前任务所需信息
权衡：摘要可能损失细节，需要结构化字段补偿
结果：降低 Token 与延迟，同时保留关键约束
边界：高风险任务仍需保留原始证据
```

### **面试结束后的闭环**

文章建议：

- 立即记录问题和回答；
- 标记没答好或答得不清楚的部分；
- 向面试官询问改进点；
- 询问岗位入职后的第一个项目；
- 将面试官视为长期职业网络；
- 根据反馈更新自己的知识体系。

复盘的价值在于把一次性经历变成可迁移的方法。

## **十五、Offer 判断：从个人收益而不是公司名气出发**

对于创业公司，文章建议重点判断：

- 产品是否有明确差异化；
- 产品方向是否清晰；
- 团队是否具备真实能力；
- 是否有可靠 mentor；
- 实际工作是否能获得成长；
- 业务方向是否符合个人兴趣；
- 融资是否只是宣传，而不是唯一依据。

核心原则是：

> 实习不是单纯出售时间，而是用时间换取能力、经验、判断力和机会。

主动联系看似招聘全职的岗位，也是一种信息不对称下的机会发现方式。不要因为岗位标签就自动排除自己。

## **十六、行业趋势的因果推导**

### **1. RAG 走向 Agentic Search**

原因是静态检索无法满足复杂、多轮、跨来源任务。系统必须让 Agent 自主判断搜索策略，但同时需要预算和停止机制。

### **2. 三类场景高频出现**

AI 搜索、Chat-to-BI、Vibe Coding 的共同需求是：

- 自然语言理解；
- 多步执行；
- 外部工具调用；
- 结果验证；
- 高交互性。

所以它们成为 Agent 的典型落地场景。

### **3. AI Infra 被重视**

原因是 Demo 阶段主要追求“能运行”，生产阶段必须解决：

- 稳定性；
- 成本；
- 观测；
- 评估；
- 安全；
- 扩展性。

### **4. MCP 与 Skill 标准化**

原因是重复开发工具和能力的成本过高，标准化可以提高复用与组合效率。但标准化之后，权限、版本、可信来源和兼容性会成为新的核心问题。

### **5. 工具选型体现工程品味**

工具本身没有绝对优劣，只有与业务约束是否匹配。真正成熟的开发者能够解释自己的选择，也能明确选择的边界。

## **十七、可直接使用的 Agent 学习框架**

### **阶段一：定义**

先明确：

- Agent 要完成什么目标；
- 用户是谁；
- 工具是什么；
- 输入和输出是什么；
- 成功如何判断；
- 风险在哪里。

### **阶段二：理解机理**

至少理解：

- LLM 为什么会产生幻觉；
- Attention 如何处理上下文；
- RAG 为什么有效；
- Prompt 为什么会影响行为；
- Tool Calling 为什么会失控；
- Token、延迟和成本如何产生。

### **阶段三：设计方法**

围绕五个核心模块搭建：

```text
需求澄清
上下文管理
工具调用
安全防护
评估与观测
```

### **阶段四：验证边界**

主动测试：

- 长上下文；
- 模糊需求；
- 工具失败；
- 工具重复调用；
- 外部恶意内容；
- 数据缺失；
- 模型拒答；
- 并发任务；
- 超时和恢复；
- 成本超限。

### **阶段五：形成证据闭环**

每个母题都建立：

```text
问题
  ↓
根因
  ↓
设计方案
  ↓
运行机制
  ↓
实验或线上证据
  ↓
失败案例
  ↓
边界与改进
```

这比单纯背诵“标准答案”更能证明真实能力。

## **十八、文章的主要不足与可改进之处**

文章最大的价值是经验真实、覆盖面广，但仍有几个可以进一步完善的地方。

### **1. 缺少量化证据**

许多设计被提到，但没有给出：

- Token 降低比例；
- 延迟变化；
- 工具成功率；
- 失败恢复率；
- 用户满意度；
- 线上错误率。

改进方式是为每个系统设计前后对比指标，而不是只描述方案。

### **2. 部分概念停留在方向层面**

例如 Agentic Memory、Skill、Agent 网关等概念只提供了趋势判断，缺少：

- 数据结构；
- API 设计；
- 状态机；
- 评估样本；
- 失败处理；
- 部署边界。

改进方式是将每个概念落实为一个最小可运行系统。

### **3. 安全部分缺少攻击—防御实验**

文章提到指令层级和沙盒化，但没有展示具体攻击样本、误报率和防御效果。

改进方式是建立安全测试集，按来源、攻击方式、风险等级分类，并测量：

- 攻击成功率；
- 正常请求误拦截率；
- 高风险工具拦截率；
- 防御延迟和成本。

### **4. 评估体系仍不完整**

文章正确提出 LLM as a Judge 的局限，但没有完整展开评估平台如何落地。

改进方式是采用多层评估：

```text
规则指标
+ 模型评估
+ 人工评估
+ 真实业务指标
```

### **5. 行业判断存在时间敏感性**

Manus、OpenClaw、OpenCode、MCP、Skill 等方向变化很快，文章中的判断需要持续验证，不能直接当作长期不变的结论。

---

## **最终方法论**

这篇文章可以压缩为一条工程主线：

> **先把模糊目标变成结构化任务，再为模型提供最小有效上下文；让模型只在明确边界内调用工具，用状态机、权限、幂等、超时和恢复机制控制执行；通过安全隔离防止外部内容影响系统；最后用评估、日志和面试复盘形成持续改进闭环。**

也可以用五个问题检验自己是否真正理解一个 Agent 系统：

1. **What：** 它要完成什么任务？
2. **Why：** 为什么采用这种架构和机制？
3. **How：** 具体如何执行、校验和恢复？
4. **Boundary：** 在什么情况下会失效，如何降级？
5. **Evidence：** 有什么实验、指标或真实案例证明它有效？

能完整回答这五个问题，才是从“使用过 Agent”走向“能够设计可靠 Agent 系统”。
