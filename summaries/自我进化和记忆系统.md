### **这篇文章的核心结论是：通过 Hook、行为模式提炼和语义记忆召回，Claude Code 可以从“每次重新解释的无状态工具”，演进为“能够持续学习并主动适应用户的编程助手”。**

## **一、问题本质：为什么需要长期记忆**

### **What：原系统存在什么问题**

Claude Code 每次启动新会话时，默认缺少前序上下文，主要表现为：

- 不记得项目架构和技术栈；
- 不记得用户的代码风格与工作习惯；
- 不记得曾经解决过的 Bug；
- 不记得已经确认过的开发规范；
- 用户需要重复解释背景、约束和经验。

这导致上下文冷启动慢、Token 消耗高，并且相同错误可能反复出现。

### **Why：问题为什么会发生**

从第一性原理看，智能系统要持续改进，至少需要具备三个能力：

1. **观察**：知道发生了什么；
2. **抽象**：从具体行为中提炼可复用规律；
3. **应用**：在未来相似场景中主动使用这些规律。

普通会话模型通常只具备短期上下文，缺少跨会话的“数据—知识—行为”闭环。因此，单纯增加上下文长度不能根治问题，因为历史信息会不断膨胀，而且无法保证相关信息被准确召回。

### **How：解决思路是什么**

文章将系统拆成三个相互衔接的子系统：

```text
工具调用
   ↓
行为观测层 Observation Engine
   ↓
模式提炼层 Instinct Engine
   ↓
记忆注入层 Memory Engine
   ↓
下一次会话自动应用
```

其本质是：

```text
具体行为 → 原始记录 → 抽象规则/知识 → 相关召回 → 新行为改进
```

## **二、总体架构：三个引擎如何协作**

### **1. 行为观测层：记录事实**

#### **What**

Observation Engine 负责记录 Claude Code 的工具调用，包括：

- 工具名称；
- 调用时间；
- 输入参数；
- 调用前后的行为信息；
- 会话生命周期信息。

数据以 JSONL 形式保存。

#### **Why**

如果没有稳定、完整的原始数据，后续的模式提炼只能依赖模型主观判断，容易出现：

- 触发遗漏；
- 样本不完整；
- 规则来源不可靠；
- 无法复盘行为链路。

因此，观测层的首要目标不是理解，而是确保“发生过的关键行为可被记录”。

#### **How**

系统使用 Claude Code 原生 Hook，而不是依赖 Skill。

主要 Hook 包括：

- **PreToolUse**：工具执行前记录意图，当前重点覆盖 Bash；
- **PostToolUse**：工具执行后记录结果，匹配所有工具；
- **Stop Hook**：会话结束时触发分析和提炼流程；
- **SessionStart Hook**：新会话开始时注入相关记忆。

核心设计是：

```text
PreToolUse：记录将要做什么
PostToolUse：记录实际做了什么
Stop：分析本次会话
SessionStart：恢复历史知识
```

## **三、为什么 Hook 优于 Skill**

### **Skill 的问题**

早期方案依赖模型主动调用学习 Skill，但这种方式存在根本缺陷：

- 模型可能忘记调用；
- 不同会话中的触发率不稳定；
- 模型无法保证覆盖所有工具调用；
- 学习行为本身会占用额外上下文；
- 采集结果受模型状态影响。

### **Hook 的改进**

Hook 位于工具生命周期的系统级回调点，具备更强的确定性：

- 工具调用后自动触发；
- 不依赖模型是否“想起来”；
- 可以统一采集所有工具；
- 更适合构建稳定的数据管道。

第一性原理上，这是把“依赖智能体自觉执行”的流程，改造成“由系统机制强制执行”的流程。

```text
Skill：模型决定是否记录
Hook：系统确保一定记录
```

## **四、数据管理：如何避免观测数据无限膨胀**

### **What：数据会产生什么问题**

如果每次工具调用都被记录，长期运行后会出现：

- 文件不断增大；
- 检索速度下降；
- 分析成本升高；
- 重复信息占用空间；
- 旧信息影响当前判断。

### **Why：为什么不能永久保留全部原始记录**

原始观测数据的价值通常随时间下降，而存储、分析和检索成本持续上升。因此，系统需要区分：

- **原始事实**：适合短期保留；
- **抽象规则**：适合长期保留；
- **项目知识**：根据重要性和时效性保留。

### **How：分层生命周期管理**

系统采用多级防膨胀机制：

#### **观测数据**

当主文件超过以下任一条件时自动归档：

- 5MB；
- 8000 行。

归档按月份分片，主文件只保留最近 30 天数据。

#### **Instinct 规则**

规则根据置信度管理：

- 新规则初始置信度为 0.5；
- 每次重复验证增加 0.05；
- 最高为 0.9；
- 长期未触发减少 0.05；
- 低于 0.55 后标记为 deprecated。

#### **原始记忆**

按照记忆类型设置 TTL，通常为 60 至 90 天。

#### **聚合规则**

- `MEMORY.md` 超过 160 行时按优先级裁剪；
- `auto-evolved.md` 每次会话结束时覆盖重写；
- 相似规则合并，避免重复保存。

核心原则是：

```text
原始数据短期保存
抽象规则长期保存
低价值内容自动淘汰
```

## **五、模式提炼层：如何从行为中获得规则**

### **What：Instinct Engine 做什么**

Instinct Engine 在会话结束后分析观测数据，将重复行为提炼为原子化规则。

Instinct 不是完整历史，而是可以直接指导未来行为的最小规则单元，例如：

```text
触发条件：执行某类 CLI 操作前
行动规则：先确认工具已安装且认证有效
```

### **Why：为什么不能直接保存完整会话**

完整会话包含大量低价值内容：

- 重复对话；
- 临时思路；
- 已失效的上下文；
- 与未来任务无关的工具调用；
- 具体但不可迁移的细节。

直接保存会导致记忆库膨胀，也会让模型难以判断哪些内容真正重要。

因此需要从“发生了什么”进一步提炼为“以后应该怎么做”。

## **六、两条模式提炼路径**

### **路径 A：统计模式检测**

#### **What**

使用规则检测器识别高频工具调用序列和重复行为。

例如：

```text
检查状态 → 修改文件 → 运行测试 → 查看结果
```

#### **Why**

统计方法适合处理：

- 高频模式；
- 明确序列；
- 重复操作；
- 可形式化的行为。

它不依赖模型，速度快，结果稳定，成本低。

#### **How**

检测到模式后，创建或更新对应 Instinct：

```text
首次发现：confidence = 0.5
再次验证：confidence += 0.05
上限：0.9
长期未触发：confidence -= 0.05
低于 0.55：deprecated
```

### **路径 B：AI 语义分析**

#### **What**

将观测摘要交给 Claude 进行语义分析，识别复杂或隐含的行为规律。

#### **Why**

统计方法只能发现“出现频率高”的模式，但无法充分理解：

- 为什么用户反复采取某种操作；
- 某个错误背后的原因；
- 项目约束与行为之间的关系；
- 不连续但语义相关的行为。

#### **How**

系统先压缩观测数据，再调用本地 Claude CLI 进行语义分析，生成候选规则。

### **两条路径的分工**

| 路径 | 优势 | 适用场景 |
|---|---|---|
| 统计检测 | 快速、稳定、低成本 | 高频、明确、可形式化的行为 |
| AI 分析 | 语义理解强 | 隐含、复杂、跨步骤的规律 |

二者结合可以实现：

```text
统计方法负责可靠性
AI 方法负责理解力
```

## **七、Instinct 的原子化设计**

### **What：什么是原子规则**

每条 Instinct 只包含一个核心关系：

```text
一个触发条件 + 一个行动建议
```

例如：

```text
当修改数据库模型后，先执行迁移检查。
```

### **Why：为什么必须原子化**

如果一条规则包含太多行为，就会出现：

- 触发条件不清晰；
- 规则难以验证；
- 置信度无法准确计算；
- 规则难以去重；
- 后续聚合容易失控。

原子规则可以独立完成：

- 统计；
- 验证；
- 衰减；
- 去重；
- 聚类；
- 注入。

因此系统采取：

```text
先记录小规则
再根据数量和相似度进行抽象
```

这比一开始就生成“大而全”的规范更稳定。

## **八、语义去重与规则聚合**

### **What：为什么需要去重**

长期运行会产生大量相似规则，例如：

- 执行命令前确认环境；
- CLI 操作前检查工具；
- 运行脚本前验证依赖。

如果不去重，规则会：

- 重复占用上下文；
- 增加模型判断成本；
- 形成冲突或重复提醒；
- 降低规则库可维护性。

### **How：Jaccard 相似度加 Union-Find**

系统提取 Instinct 中的英文技术关键词，并计算两个规则的 Jaccard 相似度：

$$
J(A,B)=\frac{|A\cap B|}{|A\cup B|}
$$

当相似度达到阈值时，将规则归为同一组。Union-Find 用于高效维护这些相似规则集合。

### **Why：为什么使用英文技术关键词**

用户可能使用中文或英文描述同一个技术行为，但工具名、命令名、框架名和技术术语通常保持英文形式。

因此，只提取英文技术关键词，可以在一定程度上实现跨语言去重，同时降低自然语言差异带来的影响。

### **Domain 聚合**

去重后，规则按照领域分组，例如：

```text
workflow
testing
git
debugging
tooling
```

只有同一领域至少有两条规则时，才生成对应的 Evolved Skill。

这样可以避免单条规则过早被抽象为复杂技能。

---

## **九、Evolved Skill 与自动规则注入**

### **What**

同一领域的多个高置信度 Instinct 会被合并成 Evolved Skill，例如：

```text
workflow（7 条规则）
        ↓
evolved-workflow.md
```

多个领域的聚合规则随后被精简并写入：

```text
~/.claude/rules/auto-evolved.md
```

### **Why**

Instinct 适合表达原子行为，但模型执行时更需要结构化、集中化的工作规范。

因此形成两层结构：

```text
Instinct：细粒度事实
Evolved Skill：可直接执行的领域规则
```

### **How**

每次会话结束后：

1. 更新单条 Instinct；
2. 进行相似规则去重；
3. 按 domain 聚类；
4. 生成 Evolved Skill；
5. 合并为 `auto-evolved.md`；
6. 覆盖旧版本。

Claude Code 启动时会自动加载 `~/.claude/rules/` 下的 Markdown 文件，从而实现跨会话注入。

## **十、记忆层：行为记忆与知识记忆分离**

### **What：为什么要有两套记忆系统**

文章将记忆划分为两个维度：

| 记忆系统 | 主要记录 | 解决的问题 |
|---|---|---|
| Instinct 系统 | 用户行为、偏好、工作模式 | 以后应该如何做 |
| Memory 系统 | Bug、技术决策、项目背景 | 已经知道了什么 |

### **Why：为什么不能混在一起**

行为模式和知识事实的性质不同：

- 行为模式需要置信度演化；
- 技术知识需要语义检索；
- 用户习惯可能长期稳定；
- Bug 解决方案可能只适用于某个项目；
- 项目背景需要根据当前目录筛选。

混在一起会导致：

- 召回结果不准确；
- 不同类型信息权重混乱；
- 生命周期无法分别管理；
- 规则与事实相互污染。

### **How：双系统协作**

```text
Instinct：自动发现行为规则
Memory：保存重要项目知识
Rules：注入稳定规范
Vector DB：召回相关记忆
```

二者相互独立，但共同影响下一次会话。

## **十一、Memory 的结构化存储**

### **What**

每条记忆以独立 Markdown 文件保存，并使用 YAML frontmatter 描述元数据。

通常包含：

- 记忆类型；
- 创建时间；
- 更新时间；
- 项目或领域；
- 重要程度；
- 标签；
- 正文内容。

### **Why**

使用独立文件而不是单一大文件，主要是为了：

- 便于增删改；
- 支持类型管理；
- 方便生成向量；
- 支持 TTL；
- 避免全文文件持续膨胀；
- 便于人工检查与迁移。

Markdown 负责可读性，frontmatter 负责机器处理。

## **十二、记忆召回链路**

### **阶段一：SessionStart 自动触发**

#### **What**

每次新会话开始时，SessionStart Hook 自动运行记忆注入脚本。

#### **Why**

如果等用户提问后再加载记忆，模型的第一轮响应可能已经缺少必要背景。

自动注入可以确保：

```text
第一条用户消息到达前，相关上下文已经准备完成
```

### **阶段二：构造查询**

系统使用以下信息构造查询：

- 当前工作目录 `$PWD`；
- 最近 3 条 Git commit message。

#### **Why**

这些信息能够以较低成本表达当前工作上下文：

- 工作目录反映项目边界；
- Commit message 反映近期开发主题；
- 不需要用户重复说明项目背景。

### **阶段三：向量检索**

系统将查询向量与记忆库中的向量进行余弦相似度比较，召回 Top-5 记忆。

余弦相似度为：

$$
\cos(\theta)=\frac{A\cdot B}{\|A\|\|B\|}
$$

#### **Why：为什么使用 Top-5**

召回全部记忆会重新造成上下文膨胀；只召回一条又可能遗漏关键背景。

Top-5 是在相关性与上下文成本之间的折中。

### **阶段四：结构化注入**

召回结果以 Markdown 形式加入 Claude 的系统提示，并附带类型标签，例如：

```text
## 项目记忆（自动注入，请优先参考）
```

#### **Why：为什么需要类型标签**

不同类型的记忆应具有不同权重：

- 约束类记忆：优先遵守；
- Bug 记忆：用于避免重复错误；
- 背景类记忆：用于理解项目；
- 偏好类记忆：用于调整输出方式。

结构化标签能帮助模型区分记忆来源和使用方式。

## **十三、Embedding 的作用与选型**

### **What：Embedding 解决什么问题**

Embedding 将文本转换成高维向量，使语义相近的内容在向量空间中更接近。

例如：

```text
查询：不要自动提交代码
记忆：等用户确认后再 commit
```

虽然两者字面词汇差异较大，但语义相似度较高。

### **Why：为什么不用传统关键词搜索**

关键词搜索只能匹配字面文本，容易漏掉：

- 同义表达；
- 不同语言表达；
- 不同句式；
- 间接描述；
- 概念相近但用词不同的内容。

### **How：本地 Embedding + Qdrant**

文章使用本地轻量 Embedding 模型和 Qdrant 向量库。

选择本地方案的原因包括：

- 记忆内容可能包含项目路径；
- 可能包含函数名、技术决策和代码上下文；
- 不希望将这些信息上传第三方；
- 本地模型可以降低隐私风险；
- 在 Apple M 系列芯片上推理速度约为每条 10ms。

文章提到的模型是 `nomic-embed-text`。

### **为什么不使用 Claude Embedding API**

文章给出的原因是：

- Claude 当前没有独立的 Embedding API；
- 将记忆内容发送到云端存在隐私风险；
- 本地模型足以满足实时写入需求。

## **十四、完整数据流**

一次工具调用最终影响下一次会话的过程如下：

```text
1. 用户提出任务
2. Claude Code 调用工具
3. PreToolUse 记录执行前意图
4. 工具实际执行
5. PostToolUse 记录执行结果
6. 观测数据写入 JSONL
7. 会话结束
8. Stop Hook 启动分析
9. 统计检测器识别高频模式
10. Claude 进行语义分析
11. 生成或更新 Instinct
12. 更新置信度
13. 相似规则去重
14. 按领域生成 Evolved Skill
15. 更新规则文件和记忆索引
16. 下一次会话启动
17. SessionStart 构造当前项目查询
18. 向量检索 Top-5 记忆
19. 自动注入规则和项目知识
20. 新行为再次被观测
```

这构成完整闭环：

```text
Observe → Analyze → Abstract → Store → Retrieve → Apply → Observe
```

## **十五、实际收益及其原因**

### **1. 冷启动时间从约 10 分钟降至约 30 秒**

#### **原因**

系统不再要求用户手动解释：

- 项目背景；
- 技术栈；
- 编码规范；
- 常见限制；
- 历史问题。

SessionStart Hook 会提前注入相关知识，使模型从第一轮响应开始就具备项目上下文。

### **2. Token 消耗降低约 78%**

#### **原因**

原方案是每次把完整 `CLAUDE.md` 或大量背景复制进 Prompt。

改进后：

- 只召回相关记忆；
- 使用 Top-5 限制上下文规模；
- 规则文件持续压缩；
- 过期内容自动淘汰；
- 相似规则自动合并。

本质上是从“全量加载”转为“按需加载”。

### **3. 重复错误率下降约 80%**

#### **原因**

系统不只是记住“执行了什么”，还会提炼：

- 发生了什么错误；
- 错误为什么发生；
- 哪个前置检查可以避免；
- 下次遇到相似场景应采取什么行动。

这让错误经验转化成前置规则。

例如：

```text
错误经验：CLI 未安装或认证失效导致任务中断
改进规则：执行 CLI 前先检查安装状态和认证状态
```

### **4. 知识产生复利效应**

随着会话增加：

```text
更多行为数据
   ↓
更多可靠规则
   ↓
更少重复解释和错误
   ↓
更多有效开发行为
   ↓
继续产生高质量数据
```

但这种复利成立的前提是系统具备：

- 置信度机制；
- 去重机制；
- 过期淘汰；
- 精准召回；
- 自动注入。

否则，记忆越多，噪声也会越多。

---

## **十六、从第一性原理提炼出的设计原则**

### **1. 先保证数据可靠，再追求智能**

没有稳定观测，就没有可靠学习。因此使用 Hook 确保采集覆盖率，而不是依赖模型主动执行。

### **2. 事实与规则分离**

原始观测说明“发生了什么”，Instinct 说明“应该怎么做”，Memory 说明“已经知道什么”。不同层次不能混为一谈。

### **3. 原子化优于过早抽象**

先积累小规则，再进行去重和聚合，避免一开始生成难以验证的复杂规范。

### **4. 规则必须可以演化**

规则不是永久正确的。重复触发增强置信度，长期不使用则衰减，最终淘汰。

### **5. 相关性优于完整性**

上下文不是越多越好。只注入与当前项目和任务相关的记忆，才能降低 Token 成本并减少干扰。

### **6. 自动化优于人工维护**

SessionStart、Stop、PreToolUse 和 PostToolUse 将记录、分析、召回和注入全部接入生命周期，减少人工维护成本。

### **7. 隐私边界必须前置设计**

观测数据和记忆可能包含代码路径、函数名及项目结构，因此优先采用本地存储、本地向量化和本地检索。

## **十七、方案的本质抽象**

这套系统并不是简单地给 Claude Code 增加一个记忆文件，而是建立了一个分层学习系统：

```text
L0：工具调用事实
L1：行为观测记录
L2：原子化行为规则
L3：领域级工作规范
L4：项目知识记忆
L5：当前会话的相关上下文
```

每一层解决不同问题：

| 层级 | 解决的问题 |
|---|---|
| 事实层 | 到底发生了什么 |
| 观测层 | 如何完整记录 |
| 规则层 | 哪些行为值得复用 |
| 聚合层 | 如何形成可执行规范 |
| 记忆层 | 哪些知识需要长期保存 |
| 注入层 | 当前任务应该使用什么 |

最终目标不是让模型“记住更多”，而是让模型：

```text
更少重复提问
更少重复犯错
更快理解项目
更准确遵循个人习惯
```

这也是该方案相比简单追加历史聊天记录的根本改进。
