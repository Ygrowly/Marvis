### **这篇文章的核心结论是：Agent 项目的竞争力不在于技术名词数量，而在于能否证明“真实问题—合理设计—工程效果—可验证结果”形成闭环。**

文章本质上是一套 Agent 工程师的项目评审与面试方法论。它要求你从“我用了什么技术”转向“为什么需要这个系统、为什么这样设计、怎样证明有效、哪里可以更简单”。

## **一、总框架：Agent 项目的第一性原理**

### **1. 定义：什么才是有价值的 Agent 项目**

一个项目的合理性可以抽象为：

$$
项目价值 = 真实问题强度 \times 现有方案不足 \times 技术方案增益
$$

只有同时满足以下条件，项目才值得使用复杂的 Agent 架构：

- 用户确实存在持续、复杂或高价值需求；
- 直接使用 ChatGPT、豆包、Claude 等通用模型无法稳定解决；
- Agent 能通过规划、工具调用、记忆、检索或环境操作获得额外收益；
- 这种收益可以用指标或真实体验证明。

如果只是把 RAG、GraphRAG、多 Agent、Redis、Neo4j 和微调堆在一个普通问答场景中，技术复杂度不会自动转化为项目价值。

### **2. 机理：为什么“堆技术”容易被识破**

面试官会沿着四个问题追问：

1. 为什么有这个项目？
2. 为什么选这个技术？
3. 如果去掉这个技术，效果会怎样？
4. 你如何证明它有效？

培训项目或开源项目改造通常只能回答“怎么实现”，无法回答“为什么这样实现”。因此一旦被追问选型、边界、替代方案和评估方法，项目就会暴露出缺乏真实思考的问题。

### **3. 边界：什么时候不该使用 Agent**

以下场景通常不需要 Agent：

- 单轮问答；
- 固定模板生成；
- 简单分类；
- 单次数据库查询；
- 普通知识库检索；
- 规则明确、步骤固定的自动化任务。

这类场景优先选择：

- 普通 LLM 调用；
- Function Calling；
- 固定 Workflow；
- 传统后端服务；
- SQL、grep、搜索或规则引擎。

只有当任务需要多步决策、动态选择工具、处理不确定环境或持续交互时，Agent 才具有合理性。

### **4. 方法：项目立项的四步验证**

写项目之前先回答：

#### **What：解决什么问题**

不要从“我要用 LangGraph”开始，而要从用户任务开始，例如：

- 多来源调研与交叉验证；
- 多模态内容生产；
- 跨系统业务操作；
- 需要持续记忆的复杂工作流；
- 需要根据环境反馈动态调整的任务。

#### **Why：为什么现有方案不够**

必须明确现有方案的具体不足：

- 信息来源太多，人工整理成本高；
- 任务步骤不固定；
- 需要跨多个工具或系统；
- 需要持续记忆用户状态；
- 普通问答无法保证结构化输出或执行结果。

#### **How：Agent 如何带来增益**

说明 Agent 的核心能力：

- 自主规划；
- 工具选择；
- 任务拆解；
- 结果验证；
- 失败重试；
- 记忆调用；
- 跨系统执行。

#### **Proof：如何证明有效**

至少建立：

- 正确率；
- 完成率；
- 延迟；
- 成本；
- 工具调用成功率；
- 人工节省时间；
- 与单 Agent、固定 Workflow 或人工方案的对比。

## **二、架构选择：单 Agent、Workflow 还是 Multi-Agent**

### **1. 定义区别**

#### **单 Agent**

一个模型通过工具调用完成任务，适合职责较多但上下文规模可控的场景。

#### **Workflow**

流程由代码预先确定，节点按固定顺序或固定路由执行。

例如：

```text
意图识别 → Text2SQL / RAG / 图谱 → 结果汇总
```

这通常是 Workflow，而不是严格意义上的 Multi-Agent。

#### **Multi-Agent**

多个具有相对自主性的 Agent 之间能够：

- 互相通信；
- 互相调用；
- 根据中间结果重新规划；
- 发起追问；
- 协作解决未预先完全确定的任务。

### **2. 为什么行业从复杂编排回归单 Agent**

单 Agent + 工具 + 良好上下文工程，通常具备：

- 更低延迟；
- 更低成本；
- 更少状态传递；
- 更少路由错误；
- 更简单的调试与部署；
- 更强的全局上下文理解。

复杂 Multi-Agent 的主要问题是：

- 每增加一步就增加调用延迟；
- 历史上下文被重复传递；
- Token 成本持续上升；
- 路由错误会导致后续全部错误；
- 系统状态和异常路径更难调试。

### **3. 什么时候适合拆分多个 Agent**

满足以下条件时才考虑拆分：

- 子任务职责明显不同；
- 子任务可以独立优化；
- 上下文隔离能够显著提升效果；
- 子任务可以并行；
- 不同任务需要不同模型或工具；
- 失败定位和重放具有实际价值。

### **4. 推荐的决策方法**

先设计最简单版本：

```text
单模型 + 工具调用
```

如果出现以下问题，再逐步拆分：

```text
上下文过大
    ↓
职责冲突
    ↓
工具选择混乱
    ↓
单 Agent 难以评估
    ↓
拆分为 Workflow 或 Multi-Agent
```

拆分后必须证明收益，而不是只证明“可以拆”。

## **三、技术选型：每个组件都必须有替代方案**

### **1. 向量数据库**

#### **What**

用于存储向量并进行相似度检索。

#### **Why**

RAG 或 Memory 需要根据语义相似度寻找相关内容。

#### **主要选择**

| 方案 | 特点 | 适用场景 |
|---|---|---|
| PostgreSQL + pgvector | 统一存储、运维简单 | 中小型项目、已有 PG |
| ChromaDB | 嵌入式、使用简单 | 原型、个人项目 |
| Milvus | 分布式、工业级 | 大规模向量检索 |
| Qdrant | 轻量、服务化 | 中小规模生产系统 |
| Pinecone | 托管服务 | 不想自行运维 |

#### **选型原则**

不要只说“数据量大用 Milvus，小用 ChromaDB”。应同时比较：

- 数据规模；
- 查询延迟；
- 并发量；
- 部署方式；
- 运维成本；
- 生态与监控；
- 是否需要与关系数据统一管理；
- 是否需要混合检索。

对于个人项目或中小规模业务，PostgreSQL + pgvector 往往比单独部署 Milvus 更合理，因为它减少了一套基础设施。

### **2. Redis**

#### **正确定位**

Redis 适合：

- 缓存；
- 分布式锁；
- 限流；
- 会话状态；
- 临时 checkpoint；
- 跨服务状态同步。

#### **不适合的设计**

不能把长期记忆仅仅作为带 TTL 的缓存数据。原因是：

- 用户记忆属于持久资产；
- TTL 到期意味着数据被删除；
- 过期记忆通常应该被归档、降权或衰减，而不是直接丢失；
- Redis 的 TTL 解决的是缓存生命周期，不是知识生命周期。

#### **改进设计**

```text
长期记忆：PostgreSQL / 向量库 / 图数据库
临时状态：Redis
记忆过期：降权、归档、人工确认或删除
```

### **3. PostgreSQL 与 MySQL**

PostgreSQL 的优势不只是“功能更多”，而是能够在一个系统中统一处理：

- 关系数据；
- JSONB；
- 向量检索；
- 地理空间数据；
- 时序数据；
- 复杂查询；
- 事务一致性。

因此新项目应先考虑：

```text
PostgreSQL + pgvector
```

再判断是否确实需要独立引入 Milvus、Elasticsearch 或其他数据库。

### **4. Neo4j**

Neo4j 适合表达：

- 实体；
- 关系；
- 路径；
- 多跳关联；
- 图遍历；
- 知识图谱。

它不应被混淆为：

- Redis 的替代品；
- Agent 状态存储；
- 普通缓存；
- 所有关系数据的默认存储。

Agent 状态与知识图谱是两种不同的数据：

```text
Agent 状态：当前任务进度、checkpoint、会话状态
知识图谱：实体、关系、路径、事实
```

## **四、模型设计：为什么不能所有 Agent 都使用同一个模型**

### **1. 核心原则**

模型应该根据任务职责分级：

| 任务 | 模型要求 |
|---|---|
| 意图识别 | 小模型、低延迟、低成本 |
| 简单抽取 | 小模型或专用模型 |
| 长文本摘要 | 长上下文模型 |
| 复杂规划 | 强推理模型 |
| 多模态理解 | 支持视觉或音频的模型 |
| 最终汇总 | 语言表达和推理能力较强的模型 |

### **2. 模型分级的收益**

- 降低平均调用成本；
- 降低简单任务延迟；
- 让强模型集中处理关键环节；
- 支持不同模态和不同能力要求；
- 更容易定位效果问题。

### **3. 如何设计**

```text
轻量模型：分类、路由、过滤、摘要
中等模型：工具调用、信息抽取、普通回答
强模型：复杂规划、冲突处理、最终决策
```

不能因为系统是 Multi-Agent，就机械地给每个 Agent 配不同模型。关键是任务复杂度和性能要求，而不是模型数量。

## **五、评估体系：任何“90% 准确率”都必须可复现**

### **1. What：评估什么**

不能只报准确率，还需要根据任务选择：

- Accuracy；
- Precision；
- Recall；
- F1；
- 任务完成率；
- 工具调用成功率；
- 事实正确率；
- 人工评分；
- 延迟与成本。

### **2. Why：为什么不能只说测试了 200 个问题**

“构造了 200 个问题”不能证明评估有效，因为不知道：

- 问题是否覆盖真实分布；
- 是否包含边界案例；
- 是否存在数据泄漏；
- 类别是否平衡；
- 是否测试了失败情况；
- 是否进行了多轮回归。

### **3. How：测试集设计**

建议覆盖：

```text
常见意图
边界意图
相似意图
模糊表达
未知意图
冲突信息
恶意或异常输入
工具失败
模型拒答
```

同时划分：

```text
训练集
验证集
测试集
回归集
```

### **4. 工程闭环**

```text
构造数据集
    ↓
运行评估
    ↓
发现失败样本
    ↓
修改 Prompt / 工具 / 路由
    ↓
自动回归
    ↓
比较新旧版本
```

可使用 LangSmith、Braintrust、Promptfoo 等工具辅助建立评估流水线。

## **六、上下文工程：不是“做了上下文管理”就够了**

### **1. 定义**

上下文工程是对模型在每一轮调用时看到的信息进行系统设计，包括：

- 系统指令；
- 用户资料；
- 长期记忆；
- 任务状态；
- 工具描述；
- 历史消息；
- 当前问题；
- 外部检索结果。

### **2. 推荐分层**

```text
系统规则
    ↓
稳定的用户资料
    ↓
长期记忆
    ↓
任务规则与工具说明
    ↓
当前任务状态
    ↓
历史对话摘要
    ↓
最近若干轮对话
    ↓
当前问题
```

### **3. 为什么要这样排序**

最稳定的内容应放在前面，变化频繁的内容放在后面，原因是：

- 有利于 Prefix Caching；
- 减少上下文重复计算；
- 降低 Token 成本；
- 避免频繁更新破坏缓存前缀。

### **4. 上下文压缩策略**

当上下文过长时，不应简单删除最近内容，而应分层处理：

- 删除已经消费过的工具原文；
- 将旧对话压缩成摘要；
- 文件内容只保留相关片段或 diff；
- 使用工具按需读取完整内容；
- 保留关键约束、决策和未完成任务；
- 对不同类型的信息设置不同保留周期。

### **5. 上下文工程的评估指标**

可以评估：

- 长上下文任务完成率；
- 关键信息召回率；
- 摘要后任务准确率；
- Token 数；
- 缓存命中率；
- 压缩前后延迟；
- 错误信息丢失率。

## **七、Memory 设计：重点不是“存储”，而是“判断什么值得记住”**

### **1. 记忆类型**

#### **事实型**

例如姓名、长期所在地、职业。通常高置信度、长期有效。

#### **偏好型**

例如喜欢吃辣、偏好某种写作风格。需要考虑持续性和置信度。

#### **推导型**

例如“用户可能经常加班”。这类信息可能由历史推断得出，不一定应直接写入长期记忆。

#### **任务型**

例如当前项目目标、待处理事项、临时约束。通常属于会话或任务记忆。

### **2. 短期偏好与长期偏好的区分**

“今天想吃辣”与“我长期喜欢吃辣”不能等价处理。

可以使用以下升级机制：

```text
单次表达
    ↓
会话级记忆
    ↓
多次重复
    ↓
跨时间持续出现
    ↓
长期偏好
```

判断因素包括：

- 出现次数；
- 时间跨度；
- 表达明确程度；
- 是否用户主动要求记住；
- 是否与历史信息冲突；
- 是否具有稳定性。

### **3. 记忆写入触发**

可以采用三类触发：

#### **显式触发**

用户说“请记住……”。

优点是准确，缺点是依赖用户主动操作。

#### **隐式触发**

模型检测到用户陈述了稳定事实或偏好。

优点是自然，缺点是容易误记。

#### **异步触发**

会话结束后，使用低成本模型进行抽取和判断。

优点是减少实时延迟，缺点是记忆更新不即时。

### **4. 记忆冲突处理**

当出现：

```text
我喜欢吃辣
我不能吃辣
```

不能简单覆盖旧值，应保留：

- 内容；
- 来源；
- 时间；
- 置信度；
- 使用场景；
- 是否为当前状态；
- 与其他记忆的关系。

最终以时间、场景和置信度共同决定当前有效信息。

### **5. 记忆生命周期**

记忆不应只有“存在”和“删除”两个状态，可设计为：

```text
候选记忆
    ↓
短期记忆
    ↓
长期记忆
    ↓
低置信度 / 低频使用
    ↓
归档
    ↓
删除
```

遗忘曲线可以用于降权，但不应机械地决定删除。

## **八、Skills、MCP、Function Calling 与 CLI**

### **1. Function Calling**

解决“模型如何调用一个具体能力”的问题。

```text
模型 → 函数参数 → 后端执行 → 返回结果
```

例如天气查询、数据库查询、发送消息。

### **2. MCP**

解决“模型如何标准化连接工具和数据源”的问题。

MCP Server 可以暴露多个工具或资源，例如：

- GitHub；
- Asana；
- 文件系统；
- 数据库；
- 浏览器。

### **3. Skills**

解决“模型如何按照一套方法完成某类任务”的问题。

Skill 通常包含：

- `SKILL.md`；
- 操作步骤；
- 约束；
- 示例；
- 模板；
- 辅助资源。

它不是单个工具，而是任务方法论或 SOP。

### **4. CLI**

让 Agent 通过命令行操作真实环境，例如：

- 文件系统；
- 代码仓库；
- 部署系统；
- 消息系统；
- 自动化任务。

### **5. 四者关系**

```text
Function Calling：一个可执行能力
MCP：工具和数据源的标准连接方式
Skill：完成一类任务的方法
CLI：操作真实环境的入口
```

Skills 与 MCP 是互补关系：

```text
MCP 提供“有什么能力”
Skill 提供“如何正确使用这些能力”
```

### **6. Progressive Disclosure**

不能把所有 Skill 和工具的完整描述一次性塞进上下文。应分层加载：

```text
第一层：名称 + 描述
    ↓
模型判断是否相关
    ↓
按需读取完整 Skill
    ↓
调用工具执行任务
```

这样可以减少：

- 上下文长度；
- 工具选择混乱；
- 错误调用；
- Token 成本。

当工具数量继续增加时，可以通过工具搜索机制动态加载相关工具定义。

## **九、成本控制：从“少调用”转向可计算的工程方案**

Agent 成本可以近似表示为：

$$
总成本 = \sum_{i=1}^{n}(输入 Token_i + 输出 Token_i) \times 单价_i
$$

而多步 Agent 的输入 Token 往往会重复携带历史上下文，因此成本会随着步骤增加而快速上升。

### **1. Prefix Caching**

让稳定内容位于前缀：

```text
系统提示词 → 稳定记忆 → 工具定义 → 历史摘要 → 当前输入
```

记忆或工具定义频繁变化会导致缓存失效，因此需要控制更新频率。

### **2. 模型分级**

简单任务使用便宜模型，复杂任务使用强模型。

### **3. 减少 Agent Step**

- 能一次完成就不要拆分；
- 合并高度相关的工具；
- 避免无意义的规划步骤；
- 尽量并行执行独立任务；
- 限制重复验证。

### **4. 上下文剪枝**

- 删除已消费的工具返回值；
- 大文件使用按需读取；
- 旧消息使用摘要；
- 只保留决策相关信息；
- 对重复内容去重。

### **5. 重试控制**

必须设计：

- 最大重试次数；
- 指数退避；
- 错误分类；
- 熔断；
- 预算上限；
- 人工接管；
- 幂等操作。

否则一个持续失败的 Agent 可能造成大量重复调用和费用失控。

## **十、AI Coding：核心不是“会用 Claude Code”，而是会设计开发系统**

### **1. 低水平用法**

```text
遇到问题 → 直接问模型 → 复制代码 → 出错后继续问
```

问题在于：

- 模型重复探索；
- 不理解项目约束；
- 修改范围不可控；
- 难以验证；
- 代码质量依赖运气。

### **2. 高水平用法**

建立项目级上下文系统：

```text
项目文档树
    ↓
AGENTS.md / CLAUDE.md
    ↓
代码规范与架构约束
    ↓
Skills
    ↓
自动化测试与评估
    ↓
可重放的修改流程
```

### **3. 文档树的作用**

项目索引应说明：

- 目录结构；
- 核心模块；
- 数据流；
- 依赖关系；
- 启动方式；
- 测试方式；
- 常见错误；
- 修改边界。

这样可以减少 Agent 的重复探索和错误修改。

### **4. Skill 的作用**

把框架最佳实践和项目操作规范沉淀为可复用知识，例如：

- PostgreSQL 规范；
- FastAPI 规范；
- 测试流程；
- 部署流程；
- 数据迁移流程；
- 安全检查流程。

### **5. 开发闭环**

```text
明确需求
    ↓
让 Agent 先分析，不立即写代码
    ↓
形成修改计划
    ↓
小范围实现
    ↓
运行测试
    ↓
检查 diff
    ↓
记录失败原因
    ↓
更新项目文档和 Skill
```

真正的差异化不在于“用了哪个 AI 编程工具”，而在于能否让工具持续、稳定地产出高质量结果。

## **十一、RAG 的边界：不要为了 RAG 而 RAG**

### **1. 传统 RAG 的基本假设**

```text
上下文窗口小
    ↓
文档切片
    ↓
向量化
    ↓
查询时召回相关片段
    ↓
交给模型回答
```

### **2. RAG 的主要风险**

- 切片丢失上下文；
- 向量召回不准确；
- 索引维护复杂；
- 文档更新不及时；
- 语义相似不等于任务相关；
- 多跳问题难以完整召回。

### **3. Agent + 工具的替代方式**

在代码库等结构化环境中，可以让 Agent 使用：

- grep；
- glob；
- find；
- read；
- 文件差异；
- 目录索引。

这种方式由 Agent 主动探索，通常比预先构建向量索引更可控。

### **4. RAG 的适用边界**

RAG 仍适合：

- 大规模文档语义检索；
- 需要跨文档召回；
- 查询模式较稳定；
- 文档无法通过简单文件操作定位；
- 需要混合关键词与语义检索；
- 需要权限过滤或结构化索引。

设计时必须比较：

```text
RAG
vs
Agent + grep / search / read
vs
数据库查询
vs
固定 API
```

选择成本最低、效果最稳定的方案。

## **十二、上线与可观测性：项目必须从 Demo 进入真实系统**

### **1. 为什么上线重要**

上线后才会暴露：

- 延迟；
- 并发；
- 超时；
- 工具失败；
- 数据一致性；
- 权限问题；
- 用户误操作；
- 成本失控；
- 模型输出不稳定。

因此上线本身就是工程能力的证明。

### **2. 最低生产化要求**

至少应具备：

- 可访问 Demo；
- 错误处理；
- 日志；
- 调用链追踪；
- 超时控制；
- 重试策略；
- 配额限制；
- 基础权限；
- 评估数据；
- 部署文档。

### **3. 可观测性设计**

每次任务应记录：

```text
请求 ID
用户 ID
任务类型
模型版本
Prompt 版本
工具调用序列
输入输出 Token
耗时
错误类型
重试次数
最终结果
```

这样才能回答：

- 哪个节点最慢？
- 哪个工具最容易失败？
- 哪类问题最容易路由错误？
- 哪个模型成本最高？
- Prompt 修改后是否变好？
- 能否重放一次失败任务？

## **十三、求职者的证据闭环**

可以用“母题驱动的证据闭环”准备每个项目。

### **母题一：为什么做**

证据：

- 用户场景；
- 痛点；
- 现有方案；
- 失败案例；
- 项目目标。

### **母题二：为什么这样设计**

证据：

- 候选方案；
- 技术对比；
- 取舍；
- 约束；
- 实验结果。

### **母题三：如何证明有效**

证据：

- 数据集；
- 指标；
- Baseline；
- 回归测试；
- 线上反馈；
- 成本和延迟。

### **母题四：哪里失败过**

证据：

- 失败样例；
- 根因；
- 修复过程；
- 修复前后指标；
- 仍然存在的边界。

### **母题五：如何继续改进**

证据：

- 架构简化；
- 模型分级；
- 上下文剪枝；
- 缓存；
- 评估自动化；
- 观测和重放。

每个技术点都应形成：

```text
问题 → 假设 → 方案 → 实验 → 结果 → 局限 → 改进
```

这比背诵技术定义更能证明项目真实且深入。

## **十四、最终的项目设计模板**

一个完整 Agent 项目可以按以下结构设计：

### **1. 问题层**

- 目标用户是谁；
- 高频任务是什么；
- 现有方案哪里失败；
- 为什么值得自动化。

### **2. 能力层**

- 是否需要多步规划；
- 是否需要工具调用；
- 是否需要长期记忆；
- 是否需要外部知识；
- 是否需要环境反馈。

### **3. 架构层**

- 单 Agent、Workflow 还是 Multi-Agent；
- 每个节点职责是什么；
- 为什么不能更简单；
- 哪些步骤可并行；
- 哪些步骤需要人工确认。

### **4. 数据层**

- 关系数据存哪里；
- 向量数据存哪里；
- 图数据存哪里；
- 临时状态存哪里；
- 数据如何归档和删除。

### **5. 模型层**

- 每个任务使用什么模型；
- 为什么选择该模型；
- 如何控制成本；
- 如何处理模型失败；
- 如何进行版本管理。

### **6. 上下文与记忆层**

- 上下文如何分层；
- 哪些信息长期保留；
- 哪些信息短期保留；
- 如何防止冲突；
- 如何进行压缩和缓存。

### **7. 评估层**

- 测试集如何构建；
- 指标如何选择；
- Baseline 是什么；
- 如何自动回归；
- 如何验证线上效果。

### **8. 生产层**

- 如何部署；
- 如何监控；
- 如何限流；
- 如何重试；
- 如何重放失败任务；
- 如何估算每次任务成本。

## **十五、最简洁的判断标准**

评价一个 Agent 项目，可以连续追问：

```text
它解决了什么真实问题？
为什么普通模型或传统程序不够？
为什么必须使用 Agent？
为什么选择这个架构？
为什么选择这些组件？
如果删掉某个组件会怎样？
如何证明效果？
遇到失败时怎么处理？
上线后如何控制成本和风险？
```

如果这些问题都能用真实案例、对比实验和工程数据回答，项目就具备可信度。若只能回答“用了 LangGraph、RAG、Redis、Neo4j 和微调”，但无法解释必要性、边界和效果，那么项目只是技术名词集合。
