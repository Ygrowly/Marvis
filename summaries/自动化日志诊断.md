
### **核心结论**

这篇文章的本质，是把“人工调试 BUG”改造成一个由 **MCP 提供数据能力、Skill 固化诊断流程、AI 执行分析与代码定位** 的自动化闭环。它解决的不是单次日志查询，而是将重复、固定、跨系统的排障经验，转化为可复用的工程能力。

## 一、问题本质：为什么需要自动化日志诊断

### 1. 原始问题

传统后端排障通常包含以下步骤：

1. 获取 `traceId` 或异常描述。
2. 打开日志平台，设置环境和时间范围。
3. 搜索日志并处理分页。
4. 从大量日志中识别关键节点。
5. 根据类名、方法名进入代码仓库。
6. 结合请求参数、调用链和 SQL 判断根因。
7. 修改代码并验证。

这些步骤的共同特征是：

- 流程相对固定；
- 数据来源明确；
- 诊断对象通常是日志、代码和 SQL；
- 但需要在多个工具之间反复切换；
- 结果依赖个人经验，容易遗漏信息。

因此，问题不是“工程师不会查日志”，而是：

> 人工正在执行一套高度结构化、可重复、但交互成本很高的流程。

### 2. 第一性原理拆解

一个 BUG 诊断任务可以抽象为：

$$
诊断结果 = 日志数据 + 代码上下文 + 分析流程 + 证据验证
$$

其中：

- **日志数据**：实际发生了什么；
- **代码上下文**：系统为什么这样执行；
- **分析流程**：先查什么、如何关联、如何排除；
- **证据验证**：根因是否能被日志、代码或 SQL 共同证明。

传统方式的问题在于，这四部分被分散在不同工具中，依靠人手动串联。

## 二、方案总览：MCP 与 Skill 如何协同

### 1. MCP 是什么：解决“数据从哪里来”

MCP，即 Model Context Protocol，是一种标准化的工具调用协议。

在本文方案中，日志平台通过 MCP 暴露日志查询、字段获取、鉴权等能力，Claude Code 可以直接调用这些工具获取实时日志。

MCP 的核心作用是：

> 把外部系统的动态能力转换成 AI 可以调用的工具。

没有 MCP 时，AI 只能分析用户复制进来的静态日志；有了 MCP，AI 才能根据环境、时间范围和查询条件主动拉取日志。

### 2. Skill 是什么：解决“应该怎么做”

Skill 是运行在 Claude Code 中的自定义操作规范，通常通过 Markdown 描述执行流程。

它不是重新训练模型，而是给 AI 一份可执行的 SOP，包括：

- 必须先做什么；
- 哪些数据必须拉全；
- 何时需要跨服务查询；
- 如何识别关键日志；
- 如何关联代码；
- 什么情况下不能提前下结论。

Skill 的核心作用是：

> 将工程师的排障经验，转化为稳定、可复用、可约束的执行流程。

### 3. 两者的关系

| 组成 | 解决的问题 | 类比 |
|---|---|---|
| MCP | AI 如何访问外部数据和系统 | 手和工具 |
| Skill | AI 如何按规范完成任务 | 操作手册 |
| AI | 如何理解上下文并进行推理 | 执行者 |
| 日志与代码 | 诊断所需的事实材料 | 证据 |

只有 MCP，AI 可能“查得到但不会系统分析”；只有 Skill，AI 可能“知道流程但没有真实数据”。

完整闭环是：

```text
用户提出问题
    ↓
Skill 解析环境、分支和诉求
    ↓
MCP 获取 Token
    ↓
MCP 拉取日志
    ↓
分页补全数据
    ↓
识别调用链和关键节点
    ↓
提取请求参数、DTO、SQL
    ↓
关联代码
    ↓
建立根因证据链
    ↓
输出修复方案
```

## 三、Skill 的工作机理

### 1. 输入结构

命令格式为：

```text
/log-diagnosis {环境} {代码分支} {诉求描述}
```

例如：

```text
/log-diagnosis T1 feature/your-branch trace_id: "your-trace" 为什么最终没有返回数据
```

输入包含三类信息：

- **环境**：决定查询哪个日志系统；
- **代码分支**：决定使用哪份代码上下文；
- **诉求描述**：说明诊断目标，通常包含 `traceId` 或告警信息。

### 2. 内部执行流程

Skill 需要把自然语言问题转化为结构化诊断任务：

```text
问题描述
→ 提取 traceId 或关键词
→ 推断查询时间范围
→ 检查鉴权状态
→ 调用日志 MCP
→ 自动分页
→ 提取关键字段
→ 还原调用链
→ 关联代码
→ 验证根因
→ 形成结论
```

关键点在于，AI 不是只执行一次搜索，而是持续执行多步工具调用。

### 3. 为什么必须固化顺序

诊断过程具有依赖关系：

- 没有日志，无法判断实际执行路径；
- 没有完整日志，可能漏掉异常节点；
- 没有请求参数，无法理解 SQL 条件；
- 没有实际 SQL，容易只根据代码表面推测；
- 没有代码定位，无法给出可执行修复方案。

因此，Skill 中的顺序不是形式要求，而是由问题的因果结构决定的。

## 四、核心能力及其设计原因

### 1. Token 自动管理

日志平台需要 `secretKey` 和 `accessToken`。

设计上：

- `secretKey` 由人工申请并配置；
- `accessToken` 由 AI 自动获取；
- 过期后自动刷新；
- `accessTokenExpireAt` 记录过期时间。

#### 为什么这样设计

`secretKey` 属于长期凭证，适合人工配置；`accessToken` 属于短期凭证，不应要求开发者频繁维护。

其原则是：

> 人工只管理不可替代的长期权限，系统自动管理可刷新状态。

### 2. 分页全量拉取

日志平台通常不会一次返回所有结果。Skill 要求自动分页，最多拉取 20 页，不能只看第一页就下结论。

#### 为什么必须全量拉取

如果只拿到部分日志，可能出现：

- 只看到请求，没有看到异常；
- 只看到上游调用，没有看到下游结果；
- 只看到 SQL 执行，没有看到返回数量；
- 错过关键错误或超时日志。

因此：

```text
部分日志 ≠ 完整事实
```

分页不是实现细节，而是诊断可信度的前提。

### 3. 跨服务分析

一个请求通常会经过多个服务。Skill 会根据日志中的上下游标识，继续拉取关联服务日志。

#### 为什么不能只查当前服务

单服务日志可能只能说明：

- 请求已经发出；
- 调用已经返回；
- 结果为空。

但真正的根因可能发生在：

- 下游服务参数转换；
- 数据库查询；
- RPC 调用；
- 消息消费；
- 外部依赖。

因此需要沿调用链追踪，而不是围绕单个应用孤立分析。

### 4. 代码联动

日志中的类名、方法名、Mapper、SQL 等信息，直接用于代码搜索。

#### 为什么要把日志和代码连接起来

日志只能说明“发生了什么”，代码才能解释“为什么这样发生”。

完整诊断需要建立：

```text
日志节点
→ 对应方法
→ 对应业务逻辑
→ 对应 SQL 或外部调用
→ 对应错误结果
```

这使输出从“可能是某处有问题”升级为“某个文件、某段逻辑导致了该结果”。

## 五、queryString 的设计原则

文章强调，时间范围只能通过 `start/end` 参数控制，不应写进 `queryString`。

这体现了查询条件的职责分离：

- `start/end`：控制检索范围；
- `queryString`：描述日志内容条件。

这样设计的好处是：

1. 时间逻辑统一；
2. 避免自然语言时间表达造成歧义；
3. 便于自动推断和复用；
4. 减少查询语法错误；
5. 便于 MCP 工具标准化处理。

可抽象为：

```text
查询 = 时间范围约束 + 内容条件
```

而不是把所有条件混在一段字符串中。

## 六、安装与配置结构

### 1. MCP 配置

日志平台 MCP 可按环境安装。Claude Code 和 Cursor 都可以接入。

安装后需要确认 MCP 连接状态正常，确保 AI 能调用日志工具。

### 2. Skill 配置

项目中需要放置 `log-diagnosis` Skill 目录。

Claude Code 通常使用：

```text
your-project/
└── .claude/
    └── skills/
        └── log-diagnosis/
```

Skill 文件描述具体的诊断步骤、工具调用规则和输出要求。

### 3. `.diagnosis/config.json`

配置文件的核心字段包括：

| 字段 | 来源 | 作用 |
|---|---|---|
| `secretKey` | 人工申请 | 获取日志平台权限 |
| `accessToken` | AI 自动获取 | 调用日志接口 |
| `accessTokenExpireAt` | 自动填充 | 判断 Token 是否过期 |
| `fields` | 日志工具获取 | 描述可查询字段 |

配置设计遵循“最小人工输入”原则：用户只需提供长期密钥，其余运行时信息自动维护。

## 七、实战案例的证据闭环

案例问题是：测试环境中的搜索接口没有返回数据。

### 1. 现象

用户提供：

- 环境：T1；
- 代码分支；
- `traceId`；
- 诉求：为什么最终没有返回数据。

### 2. 第一步：锁定请求

AI 根据 `traceId` 推断日志时间范围，并自动查询完整日志。

结果：

- 自动刷新过期 Token；
- 分页拉取 73 条日志；
- 获得完整请求链路。

### 3. 第二步：定位数据丢失层级

AI 识别出：

```text
resultList is empty
```

进一步判断：

- 业务层确实执行完成；
- DB 查询返回空结果；
- 问题更可能位于数据库查询条件，而不是接口组装逻辑。

这里完成了第一轮归因：

```text
接口无数据
→ 不是返回组装问题
→ 是查询结果为空
→ 继续检查 SQL
```

### 4. 第三步：提取 DTO

AI 从日志中提取 `toSearchDTO` 的组装结果，获得实际传入查询层的条件。

这是重要的中间证据，因为请求入参不一定等于最终查询条件，中间可能发生：

- 默认值填充；
- 字段转换；
- 条件合并；
- 空值处理；
- 类型转换。

### 5. 第四步：分析实际执行 SQL

AI 进一步读取 ORM 打印的真实 SQL，而不是只看 Mapper 源码。

发现其他字段的条件处理方式是：

```sql
字段 IS NULL OR 字段 = ''
```

而 `customer_tag` 只判断：

```sql
customer_tag IS NULL
```

### 6. 第五步：建立根因链

数据库中现有数据的 `customer_tag` 存储为空字符串，表示“未配置”。

但 SQL 将空字符串当成有效值处理，没有把它解释为“不限制”，导致数据被过滤。

完整证据链为：

```text
业务语义：空字符串代表未配置
    ↓
数据事实：数据库中该字段为 ''
    ↓
代码事实：只判断 IS NULL
    ↓
SQL 事实：'' 未被放宽匹配
    ↓
查询结果：所有记录被过滤
    ↓
最终现象：接口返回空数据
```

### 7. 第六步：定位修复位置

AI 在 MyBatis Mapper XML 中找到对应条件，修复方向是使 `customer_tag` 与其他同类字段保持一致，同时处理：

- `NULL`；
- 空字符串；
- 有效查询值。

这里的关键不是简单“加一个条件”，而是恢复同类字段之间的一致业务语义。

## 八、为什么这个 BUG 容易被忽略

这个问题具有三个隐蔽特征：

### 1. SQL 语法合法

SQL 可以正常执行，不会抛出语法错误。

### 2. 单字段逻辑表面合理

`IS NULL` 本身没有明显错误，开发者容易默认它已经覆盖了“未配置”。

### 3. 错误来自横向不一致

真正的问题不是某个条件完全错误，而是：

```text
其他字段：NULL + 空字符串
customer_tag：仅 NULL
```

这类问题属于“同类逻辑不一致”，人工排查容易受局部代码影响，AI 更适合做结构化横向比较。

## 九、从第一性原理看，方案为什么有效

### 1. 它减少了无价值的人工搬运

人工最耗时的部分通常不是最终判断，而是：

- 复制日志；
- 设置查询条件；
- 翻页；
- 查找类名；
- 切换 IDE；
- 对照 SQL；
- 重复执行搜索。

自动化后，工程师可以把精力集中在高价值判断上。

### 2. 它把动态数据接入推理过程

静态代码分析无法回答：

- 这次请求实际走了哪条路径；
- 最终传入了什么参数；
- 实际执行了什么 SQL；
- 哪个下游服务返回了异常结果。

MCP 让 AI 获得运行时事实，避免仅凭代码猜测。

### 3. 它把经验转化为约束

优秀工程师的排障能力往往体现为隐性流程，例如：

- 先用 `traceId`；
- 先确定时间范围；
- 日志必须拉完；
- 先看调用链；
- 再看 DTO；
- 最后看真实 SQL。

Skill 将这些经验显式化，使排障过程不再完全依赖个人记忆。

### 4. 它形成了可验证的证据链

高质量诊断不能只给出“可能原因”，而要连接：

```text
现象 → 运行时日志 → 中间参数 → 实际 SQL → 源码 → 修复方案
```

证据越接近实际执行结果，结论越可靠。

## 十、边界与风险

### 1. MCP 只能提供数据，不保证结论正确

日志查询能力不等于诊断能力。AI 仍可能：

- 误读日志；
- 忽略隐含业务规则；
- 将相关性误判为因果性；
- 错误选择代码分支。

因此，关键修复仍需人工验证。

### 2. 日志质量决定诊断上限

如果缺少以下信息，诊断能力会明显下降：

- `traceId`；
- 请求参数；
- 关键业务节点；
- SQL 日志；
- 上下游关联标识；
- 统一字段格式。

AI 无法从不存在的日志中还原事实。

### 3. 全量分页带来成本

分页拉取更完整，但也会增加：

- Token 消耗；
- 查询耗时；
- 日志平台压力；
- 上下文噪声。

更好的设计应当是：

```text
默认保证完整性
必要时进行分层摘要和重点筛选
```

不能为了节省 Token 而直接牺牲关键证据。

### 4. 凭证安全必须单独治理

`secretKey` 属于敏感凭证，应避免：

- 提交到代码仓库；
- 写入公开配置；
- 出现在普通日志；
- 被模型输出；
- 在团队间无控制复制。

实际使用中应配合权限最小化、密钥轮换和脱敏机制。

### 5. 代码修改与诊断应适当隔离

自动定位问题并不等于自动修改生产代码。更稳妥的流程是：

```text
AI 诊断
→ 输出证据和修复建议
→ 人工确认
→ AI 修改代码
→ 测试验证
→ 发布
```

## 十一、可进一步改进的方案

### 1. 将 Skill 从“流程说明”升级为“状态机”

当前流程可以进一步形式化：

```text
INIT
→ AUTHENTICATED
→ LOGS_DISCOVERED
→ LOGS_COMPLETED
→ TRACE_RECONSTRUCTED
→ DTO_EXTRACTED
→ SQL_ANALYZED
→ CODE_LOCATED
→ ROOT_CAUSE_CONFIRMED
→ RECOMMENDATION_READY
```

每个状态都设置进入条件和退出条件，避免 AI 跳步。

### 2. 增加证据等级

可以将诊断结论分为：

- **事实**：日志直接记录；
- **强推断**：多个日志和代码证据一致；
- **待验证假设**：目前缺少关键证据。

例如：

```text
事实：SQL 返回 0 条记录。
强推断：customer_tag 空字符串条件导致数据被过滤。
待验证：修复后是否会引入其他查询场景变化。
```

这样可以降低“猜测被包装成结论”的风险。

### 3. 增加自动对比能力

针对本文这类 BUG，可以让 Skill 自动执行横向比较：

- 同类字段的空值处理；
- 相邻 Mapper 条件；
- 不同环境 SQL；
- 修复前后查询结果；
- 同一接口不同请求的执行路径。

这会强化 AI 擅长的“结构化差异发现”。

### 4. 引入诊断回归测试

每次发现一个真实 BUG，都可以沉淀为测试样例：

```text
输入：特定请求参数
期望：customer_tag 为空时不限制查询
验证：SQL 条件和返回结果符合预期
```

这样 Skill 不只是排障工具，也可以逐渐成为故障知识库和回归测试生成器。

### 5. 建立标准化日志契约

日志字段可以统一为：

- 请求标识；
- 服务名；
- 方法名；
- 入参摘要；
- 出参摘要；
- SQL 模板；
- SQL 实参；
- 返回数量；
- 错误码；
- 上下游关系；
- 时间戳。

日志越结构化，AI 越容易准确解析，跨服务分析也越稳定。

## 十二、可迁移的方法论

这套方案不局限于日志诊断。凡是满足以下条件的工作，都适合采用 Skill + MCP：

1. 步骤较固定；
2. 数据来源明确；
3. 工具之间需要联动；
4. 输出结果可验证；
5. 人工重复操作比例高。

可迁移场景包括：

- 代码审查；
- 性能问题分析；
- 告警巡检；
- 数据质量排查；
- 发布故障回溯；
- 线上异常复盘；
- 依赖服务健康检查。

抽象模板如下：

```text
外部系统 MCP
    ↓
动态获取事实
    ↓
Skill 固化操作流程
    ↓
AI 进行跨数据源分析
    ↓
输出带证据的结论
    ↓
人工确认与验证
```

## 十三、用“框架学习法”压缩记忆

### 定义

- **MCP**：让 AI 调用外部系统。
- **Skill**：让 AI 按固定 SOP 执行。
- **日志诊断 Skill**：让 AI 自动完成日志查询、链路还原、代码定位和根因分析。

### 机理

```text
MCP 提供事实
Skill 提供流程
AI 提供推理
代码和测试提供验证
```

### 边界

- 没有日志，无法还原运行时事实；
- 没有代码上下文，难以定位修复点；
- 没有业务规则，可能误判语义；
- 没有人工验证，不应直接视为最终结论。

### 方法

```text
优先 traceId
→ 自动确定时间
→ 鉴权并全量分页
→ 还原跨服务链路
→ 提取 DTO
→ 分析真实 SQL
→ 关联源码
→ 对比同类逻辑
→ 输出证据链和修复方案
```

## 十四、母题驱动的证据闭环

这篇文章可以围绕一个母题理解：

> 如何把个人工程经验，转化为 AI 可执行、可复用、可验证的系统能力？

对应的证据闭环是：

```text
人工排障耗时
→ 流程具有固定结构
→ MCP 提供动态日志
→ Skill 固化诊断规范
→ AI 自动执行跨系统分析
→ 真实案例发现 SQL 根因
→ 方案可迁移到其他工程场景
```

最终可将文章压缩为一句话：

> **用 MCP 连接真实运行数据，用 Skill 固化排障流程，用 AI 完成证据关联，最终把重复性的人工调试升级为可复用的工程化诊断能力。**
