# 项目全貌与产品定位

## 模块定位

本模块回答三个面试起点：项目为谁服务、解决什么问题、为什么不是普通 Text-to-SQL。

## 一句话结论

> 数驭穹图是面向中小企业业务团队的可信 NL2BI 数据分析与协作平台，把多源数据、业务语义和权限组织成可查询资产，让业务人员通过自然语言获得可验证结果，并在 Univer 中协作和持续复用。

## 第一性原理

业务人员真正需要的不是 SQL，而是能够支持决策的可信结果。由此推导：

1. 数据分散，需要统一入口；
2. Schema 不能表达正式业务口径，需要语义资产；
3. LLM 是概率系统，不能成为权限和事实源；
4. SQL 能执行不代表结果正确，需要验证和证据；
5. 一次性回答价值有限，需要沉淀、刷新和协作。

## 用户与痛点

| 用户 | 需求 |
|---|---|
| 运营、财务、销售 | 不写 SQL 完成临时分析 |
| 管理者 | 查看统一口径结果并继续追问 |
| 数据管理员 | 接入数据、维护指标和权限 |
| 数据分析师 | 治理复杂口径、处理失败案例 |

传统链路是：

```text
业务人员提需求
→ 数据分析师确认口径
→ 找表、写 SQL、核数
→ 制作报表
→ 截图或文件交付
→ 问题变化后重新排期
```

数驭穹图将其改造成：

```mermaid
flowchart LR
    A["多源数据"] --> B["语义与权限"]
    B --> C["可信问数"]
    C --> D["表格、图表、报告"]
    D --> E["Univer 协作"]
    E --> A
```

## 产品闭环

1. 数据管理员接入数据库、文件、飞书和 Univer 表格；
2. 选定数据默认同步到轻量湖仓，实时数据可受控只读；
3. 数据管理员与业务负责人维护指标、维度和关联关系；
4. 用户自然语言提问，系统澄清歧义；
5. 系统生成 AnalysisIntent、SemQL 和受控 SQL；
6. 查询通过权限、安全、成本和结果校验；
7. 表格或图表绑定查询证据；
8. 结果进入 Univer、报告和看板，继续刷新与复用。

## 钢人比较

### 数据分析师

人工最擅长复杂建模、未知问题和正式经营分析。平台不取代数据分析师，而是减少重复取数；数据人员治理一次，业务人员反复使用。

### 传统 BI

传统 BI 在固定指标和稳定看板上更成熟。数驭穹图补充临时自然语言分析，并把高价值临时结果沉淀为长期资产。

### 裸 Text-to-SQL

直接生成 SQL 原型简单、自由度高，但容易选错表、口径错误、越权或产生慢查询。数驭穹图牺牲部分无限自由，换取可治理和可证明。

## 逆向检查

即使 SQL 执行成功，仍可能：

- 选错销售额口径；
- 把关闭门店计入数量；
- JOIN 导致金额翻倍；
- 读取无权字段；
- 图表数字由模型改写；
- 用旧数据回答“当前”。

因此项目壁垒不是模型写 SQL，而是语义、权限、验证、证据和评测闭环。

## 边际决策

最低可用版本先支持一个高频业务域、少量已确权指标和只读分析，不急于接入所有数据源或建设完整办公套件。优先级是：

> 核心链路可信度 > 业务域数量 > 展示功能数量

> 中小企业的数据分散在数据库、文件、飞书和人工表格中。业务人员想分析经营数据时，通常依赖数据分析师确认口径、写 SQL 和制作报表，沟通链路长，结果也难以复用。数驭穹图把企业选定数据同步到轻量湖仓，实时场景也支持受控只读连接；再通过语义资产定义指标、维度和关联关系。用户提问后，系统依次完成权限检查、歧义澄清、领域路由、Schema Linking、AnalysisIntent、SemQL、SQL 安全执行、结果验证和证据绑定，最后生成表格、图表或报告。结果可以进入 Univer，区分系统计算区和人工协作区，也可以发布为新的数据源。因此它不是简单 Text-to-SQL，而是从数据接入到可信分析和持续协作的完整闭环。

## 高频追问

### 为什么叫 NL2BI，而不是 NL2SQL？

SQL 只是查询表达。NL2BI还要解决语义、权限、执行安全、结果完整性、可视化、证据和长期交付。

### 为什么聚焦中小企业？

中小企业数据源多但数据团队有限，适合轻量底座和自助分析；项目不复制大型数仓，而是治理选定的高价值分析数据。

### 核心技术壁垒是什么？

高质量语义资产、确定性执行护栏、结果 Provenance 和可归因评测，而不是单一模型。

## 恢复脚本

> 数据分散 → 语义确权 → 可信问数 → 证据结果 → Univer 资产
