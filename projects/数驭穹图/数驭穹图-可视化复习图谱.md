# 数驭穹图 · 可视化复习图谱

> 版本：v1.0（基于《数驭穹图-项目学习与面试手册》00–17，以及“定位、数据和语义”专项补充）  
> 用途：建立项目全貌、闭卷画图、专项复习、模拟面试、追加新知识。  
> 项目主线：**多源数据接入 → 语义确权 → 可信问数 → 结果证明 → Univer 协作 → 持续数据资产。**

## 0. 怎么使用这套图

### 三种复习模式

| 时间 | 看哪些图 | 训练目标 |
|---|---|---|
| 2 分钟 | 图 01、图 24、图 26 | 恢复项目定义、黄金案例和面试顺序 |
| 15 分钟 | 图 01、05、07、11、15、16、18、24 | 恢复数据、语义、问数、安全、可信和案例 |
| 45 分钟 | 按图 01～22 顺序闭卷重画 | 承受连续技术追问并完成故障迁移 |

### 新知识如何加入

新增知识先判断它属于哪一类，再放入对应图，而不是继续堆成长文：

```text
新知识
├─ 业务对象/边界      → 图 02～04
├─ 数据状态/同步      → 图 05～10
├─ 指标/Schema/JOIN   → 图 11、12
├─ Intent/SemQL/SQL   → 图 13～15
├─ 权限/性能/证据     → 图 16～18
├─ 协作/Agent/Context → 图 19～21
├─ Eval/部署/故障     → 图 22、23
└─ 面试追问/案例      → 图 24～26
```

每次新增都标记证据等级：

- `E1`：已有代码、测试、日志、真实交付或生产记录；
- `E2`：固定数据集回放、离线评测、压测或模拟结果；
- `E3`：设计方案或待实现目标，不能说成已上线成果。

### 钢人化比较

| 方案 | 最强优势 | 主要局限 | 数驭穹图的关系 |
|---|---|---|---|
| 数据分析师 | 复杂建模、未知问题、正式分析 | 重复取数沟通成本高 | 治理一次，高频复用 |
| 传统 BI | 固定指标和稳定看板成熟 | 临时问题响应慢 | 补充开放式问数 |
| 裸 Text-to-SQL | 原型短、自由度高 | 口径、权限、结果难证明 | 加语义、护栏、证据和协作 |
| 全量数仓 | 治理强、规模能力成熟 | 中小企业建设成本高 | 只治理高价值数据集 |

# 第三层：数据接入、同步与轻量湖仓

## 图 06｜SNAPSHOT 与 LIVE_READ 决策树

```mermaid
flowchart TD
    A["准备接入一个数据集"] --> B{"是否要求接近实时？"}
    B -->|否| C["选择 SNAPSHOT"]
    B -->|是| D{"是否有只读副本或分析库？"}
    D -->|有| E["选择受控 LIVE_READ"]
    D -->|没有| F{"是否为小范围低成本查询？"}
    F -->|是| G["生产主库受限只读"]
    F -->|否| H["拒绝实时查询或转 SNAPSHOT"]

    C --> I["支持跨源 JOIN、复现和隔离"]
    E --> J["更高新鲜度、更严格预算"]
    G --> K["索引明确、超时、并发和取消"]

    L["快照数据＋实时数据"] --> M{"中间结果是否有界？"}
    M -->|是| N["源端过滤聚合后在 DuckDB 汇合"]
    M -->|否| O["先同步或转异步，不做大规模实时联邦 JOIN"]
```

核心取舍：

| 模式 | 得到什么 | 付出什么 |
|---|---|---|
| SNAPSHOT | 生产隔离、跨源分析、版本复现 | 同步延迟、存储和维护 |
| LIVE_READ | 数据更新及时、少复制 | 依赖源端性能、跨源能力弱 |

## 图 07｜首次快照、CDC 与发布主线

```mermaid
flowchart TD
    A["连接与只读权限检查"] --> B["选择表、字段、范围和主键"]
    B --> C["建立一致性快照 S0"]
    C --> D["记录日志起点 P0"]
    D --> E["按稳定主键 Keyset 分片分页"]
    E --> F["限速写入 Staging Parquet"]
    F --> G["持久化文件后提交 Checkpoint"]
    G --> H{"所有分片完成？"}
    H -->|否| E
    H -->|是| I["应用 P0 之后 CDC"]
    I --> J["追平目标位点"]
    J --> K["完整性、Schema、新鲜度和质量校验"]
    K -->|通过| L["原子切换 Manifest 指针"]
    K -->|失败| M["新版本 INVALID，旧版本继续服务"]
```

为什么需要 `S0 + P0`：

```text
S0 保证全量分页看到同一个数据库状态；
P0 保证快照期间发生的变化随后能够连续补上；
两者共同避免“全量结束、增量开始”之间出现不可解释的数据空洞。
```

## 图 08｜增量事件的“至少一次输入、效果一次”

```mermaid
flowchart TD
    A["CDC / updated_at 事件"] --> B["生成事件身份"]
    B --> C{"幂等键已处理？"}
    C -->|是| D["跳过重复事件"]
    C -->|否| E{"源版本是否更新？"}
    E -->|更旧| F["忽略或进入异常队列"]
    E -->|更新| G{"操作类型"}
    G -->|INSERT / UPDATE| H["写增量 Parquet / upsert"]
    G -->|DELETE| I["写 tombstone"]
    H --> J["更新消费位点"]
    I --> J
    J --> K["周期 Compaction"]
    K --> L["形成新的可查询版本"]

    M["日志断档或被清理"] --> N["标记 STALE / INVALID"]
    N --> O["重新快照"]
```

事件身份不能只使用业务主键：同一订单可以发生多次合法更新。更合理的是：

```text
source_id + log_partition + log_position + event_index
```

## 图 09｜轻量湖仓式分析层

```mermaid
flowchart TD
    A["授权业务数据"] --> B["Connector Worker"]
    B --> C["Staging Parquet"]
    C --> D["校验与 Manifest"]
    D --> E["Published Parquet"]
    E --> F["DuckDB Query Worker"]
    F --> G["Result Artifact"]

    H["PostgreSQL 控制面"] --> B
    H --> D
    H --> F
    H --> I["租户、ACL、Schema、任务、版本、审计"]

    J["Delta 与 tombstone"] --> K["Compaction"]
    K --> E
```

组件职责：

| 组件 | 做什么 | 不做什么 |
|---|---|---|
| PostgreSQL | 元数据、权限、任务、版本、语义、审计 | 不保存大规模分析事实 |
| R2/Parquet | 列式数据、版本文件、Artifact | 不负责业务权限判断 |
| DuckDB Worker | 读取授权文件执行 OLAP | 不作为完整多租户安全边界 |
| Manifest | 定义某一已发布版本的文件集合 | 不替代数据质量验证 |

严格表述：当前是“轻量湖仓式分析层”，没有声称具备 Iceberg/Delta 的完整表级 ACID、Schema Evolution 和 Time Travel。

## 图 10｜数据集状态机

```mermaid
stateDiagram-v2
    [*] --> Configuring
    Configuring --> Syncing: 配置通过
    Syncing --> Candidate: 数据写入完成
    Syncing --> SyncFailed: 中断或断档
    SyncFailed --> Syncing: Checkpoint 恢复
    Candidate --> Validating
    Validating --> Published: 全部校验通过
    Validating --> Invalid: 完整性或质量失败
    Published --> Stale: 新鲜度超限
    Published --> Deprecated: 主动下线
    Stale --> Syncing: 补数或重快照
    Invalid --> Syncing: 修复后重建
```

必须记住：

> `SYNC SUCCESS` 只证明搬运任务完成；`PUBLISHED` 才证明这个版本经过完整性、Schema、新鲜度、权限和业务质量门禁，可以进入正式问数。

## 图 15｜NL2SemQL2SQL 与错误归因


允许有限修复：方言、拼写、类型转换、语法。  
禁止绕过：权限拒绝、口径歧义、非法 JOIN、过期数据、成本超限。

# 第六层：权限、安全、性能与可信结果

## 图 16｜五层安全边界

```mermaid
flowchart TD
    A["身份、JWT、租户、AI 配额"] --> B["只发现授权数据集与 Tool"]
    B --> C["Tool Schema、枚举和组合 Validator"]
    C --> D["服务端注入 tenant_id 和权限上下文"]
    D --> E["SQL AST、表列函数白名单、只读事务"]
    E --> F["时间、扫描、超时、并发、行数和取消"]
    F --> G["隔离 Worker 或客户只读副本"]
    G --> H["结果脱敏与敏感信息检查"]
    H --> I["分享、刷新和回写时重新鉴权"]
    I --> J["审计与 Evidence"]
```

关键原则：

- Tool Call 和模型输出都是不可信输入；
- 模型不能填写或删除 `tenant_id`；
- 权限依赖不可用时 `FAILED_CLOSED`；
- 只读不等于安全，慢 `SELECT` 仍可能抢占 CPU、IO、连接和内存。

# 第九层：黄金案例与模拟面试

## 图 24｜“门店数＋平均盈利率”端到端案例

```mermaid
flowchart TD
    A["负责人：有多少门店？今年平均盈利率？"] --> B["鉴权：可查看哪些区域和门店"]
    B --> C["澄清门店、今年、利润、平均方式"]
    C --> D["路由门店经营域"]
    D --> E["加载门店、收入、成本、日历语义"]
    E --> F["AnalysisIntent"]
    F --> G["SemQL：active_store_count＋weighted_profit_margin"]
    G --> H["收入先聚合到门店＋时间"]
    G --> I["成本先聚合到门店＋时间"]
    H --> J["同粒度 JOIN 门店主数据"]
    I --> J
    J --> K["AST、租户、分区、JOIN、EXPLAIN、预算"]
    K --> L["DuckDB 隔离执行"]
    L --> M["门店数、总分、单位、完整性互核"]
    M --> N["绑定 call_id、hash、快照、语义版本"]
    N --> O["表格 / 图表"]
    O --> P["Univer 系统区＋人工区"]
```

关键公式：

```text
经营总盘口径：整体盈利率 = SUM(利润) / SUM(收入)
典型门店口径：简单平均 = AVG(各门店利润 / 各门店收入)
```

两个最高风险：

| 风险 | 发现 | 止血 | 修复与预防 |
|---|---|---|---|
| 平均盈利率口径错误 | Intent 聚合方式为空或冲突 | 不执行，有限澄清 | 指标卡固化公式和适用场景；加入大小店悬殊用例 |
| 收入、成本明细直接 JOIN 放大 | JOIN 前后行数与总额异常 | 阻断结果和图表 | 两边先聚合到共同粒度；知识卡记录基数 |

其他边界：

- 某门店缺成本：报告可计算门店数和缺失门店，不能把缺失成本当零；
- 当天同步未完成：使用最后完整业务日或明确 `STALE/PARTIAL`；
- Live Read 成本过高：缩小范围、转快照或异步，不把复杂 SQL 打到主库。

## 最终总恢复脚本

> **散：** 数据分散，通过授权快照或受控实时只读进入系统。  
> **义：** Schema 不等于业务，指标、粒度和 JOIN 必须人工确权并版本化。  
> **问：** 问题经 Intent、澄清、路由、Linking、SemQL 变成受控 SQL。  
> **证：** 权限、预算、结果验证和 Evidence 共同证明答案可信。  
> **产：** 结果进入 Univer 协作，审核后再次成为可刷新数据资产。
