01主干：它是什么 → 它怎么活着 → 怎么把它用坏 → 哪些活不该派给它正本 wiki/topics/Redis/

四段即依赖：单线程是前提（R1）→ 自己先活着（R2）→ 再谈怎么用（R3）→ 最后划边界（R4/R5）。慢命令、丢数据、DB 被打穿，三段失败分开归因。
主干叙事（一段读完）：Redis 的一条线是「它是什么 → 它怎么活着 → 怎么把它用坏 → 哪些活不该派给它」。 是什么：内存比磁盘快 5 个数量级，所以命令执行敢单线程（代价：慢命令卡全局；6.0 后只是网络 IO 多线程）；五种结构的差别 = 形状 + 有无分数，ZSet 用跳表管排名、哈希表管查分 —— 跳表 vs B+ 树是设计域之争，不是快慢（B+ 树的优势在磁盘，内存里用不上）。 怎么活着：过期删除（惰性 + 定期抽样）由 TTL 决定、内存淘汰（8+2 种，近似 LRU 抽 5 个）由内存决定，两件事别混；持久化没有优劣只有更怕哪个 —— 怕丢选 AOF（everysec 最多丢 1s）、怕恢复慢选 RDB，bgsave 的写时复制会拉高内存峰值。 怎么用坏：先定权威（DB），强一致不可能（没有共同事务）；Cache Aside 先写 DB 再删缓存、必须配 TTL 或对账兜底；穿透 / 击穿 / 雪崩的共同点是缓存没接住的流量全部倒向 DB。 不该派的活：参与判断的数据进缓存，是把「慢」升级成「错」；大 key 的 DEL 同步阻塞全局，热 key 加节点摊不开。
读法：蓝线主线；橙字判据与数字；紫框事故与失效；绿横幅是三个项目的落点。三段失败分开归因：慢命令查结构与大 key、丢数据查持久化与主从、DB 被打穿查三类事故与回源放大。

R2 数据怎么不丢断电 / 过期 / 满内存三件事分开：过期删除（惰性 + 定期抽样）由 TTL 决定，内存淘汰（8+2 种、近似 LRU 抽 5 个）由内存决定；RDB 与 AOF 没有优劣只有更怕哪个（everysec 最多丢 1s）；bgsave 写时复制拉高内存峰值；主从切换丢的是没同步那段10–13未使用 —— 判据：所有「不丢」手段都是拿一致性、内存或性能换的，没有免费的
R3 缓存一致性和 DB 怎么不出事先定权威（DB）→ 强一致不可能（无共同事务）→ Cache Aside：先写 DB 再删缓存（删比更新好），必须配 TTL 或对账兜底；穿透防不存在（布隆 / 空值）、击穿防热 key 过期（互斥 / 逻辑过期）、雪崩防同时失效（错峰 TTL + 限流降级）14–16、18、20EnergyOps：Outbox 把「删缓存」变成事务内事实（PG 提交与 Redis 删除不可能同一事务）；数驭穹图：权限数据可缓存但必须有即时失效路径；RuleArena：限流 / 短期去重可放 Redis，最终裁决必须 DB
R4 大 key / 热 key怎么发现、怎么拆结构性根源 = 单线程 + key 归属单分片：大 key 的 DEL 同步阻塞全局（200 万 field ≈ 200ms → UNLINK / HSCAN 分批）；热 key 加节点摊不开（一个 key 只属于一个分片）——读热复制打散、写热聚合 / 队列 / 换结构17未使用 —— 判据：普通高负载水平扩展能解，热 key 不能（违背「请求均匀分布」的前提）
R5 什么不该放缓存与权威的边界正确问法是「权威来源在哪、参不参与判断」：参与判断的数据进缓存 = 把「慢」升级成「错」（余额 + TTL = 60 秒窗口里照样做错决定）；缓存挂了回源放大 1/(1−命中率)；Redis 持久化是尽力而为，不能当数据库21–24RuleArena：Redis 256–512MB 只做队列 / 限流 / lease，权威状态在 PG；数驭穹图：行级权限不作缓存值、召回前重新求值；EnergyOps：缓存放元数据不放业务事实

      05要能现场算出来的数正本 母题卡「一、教材」推导

      每个数都要带推导，只报结果是会被追问倒的。
      内存 vs 磁盘
      100ns / 10ms
      差 5 个数量级——这是「命令执行敢单线程」的前提；单线程换来简单，代价是慢命令卡全局。
      HyperLogLog
      1 亿 UV ≈ 十几 KB
      用「接受误差」换「固定的小内存」——用精度换空间的典型取舍。
      AOF everysec
      最多丢 1 秒
      5000 QPS 写入时最坏丢约 5000 条命令——用「最多丢 1s」换回一整个数量级的吞吐。
      近似 LRU
      抽样 5 个
      精确 LRU 要全量链表、每次访问挪节点；随机采样 5 个挑最久没用——又是用近似换开销。
      DEL 大 key
      ≈ 200 ms
      200 万 field × 100ns 的同步释放，整个实例阻塞——用 UNLINK 或 HSCAN 分批。
      热 key 集中
      3 万 vs 1 万
      10 分片扛 10 万 QPS、单 key 3 万：单分片 3 倍超载；加节点摊不开，key 不跨分片。
      回源放大
      95% → 20 倍
      1/(1−0.95)=20：缓存全挂时 DB 面对的流量倍数——限流降级必须提前设计。
      击穿的账
      10 万 vs 5000
      热 key 10 万 QPS 过期瞬间全部未命中，DB 上限 5000——互斥重建只放一个请求回源。
      死 key 的账
      99% 没被访问
      100 万 key 只有 1% 被访问过：99% 是纯负债——占内存、拖慢淘汰、还稀释命中率。

      06八句最容易说错的话正本 母题卡「二、自测」纠错题原话

      说对前半句没用，后半句才是判据。
      ✗「跳表比 B+ 树快」✓ 不是快慢问题：B+ 树为磁盘 IO 设计，优势在内存里用不上；跳表实现更简单、范围查询更自然。
      ✗「单线程所以没有并发问题」✓ 单条命令原子，命令组合不原子（GET 完再 SET 之间会插队）——用 INCR / Lua / SET NX 这类原子操作。
      ✗「Redis 什么都能缓存」✓ 参与判断的数据不进缓存：TTL 只给「最多旧多久」的上限，60 秒窗口里的错误决定照样发生。
      ✗「先删缓存再写 DB，保证一致」✓ 更糟：中间的读会把旧值写回缓存长期保留；Cache Aside 是先写 DB 再删，还要配 TTL / 对账。
      ✗「缓存和 DB 可以用事务保证强一致」✓ 两个独立系统没有共同事务；目标是最终一致 + 可容忍的不一致窗口。
      ✗「大 key 的问题就是占内存」✓ 还有 DEL 同步阻塞全局（200 万 field ≈200ms）、网络往返、迁移卡顿——UNLINK / 分批删。
      ✗「集群加节点就能解决热 key」✓ 一个 key 只属于一个分片，压力不会摊开；读热复制打散，写热要聚合 / 队列 / 换结构。
      ✗「缓存挂了大不了回源」✓ 回源放大 1/(1−命中率)：95% 命中 → 20 倍流量；限流降级必须提前设计。
