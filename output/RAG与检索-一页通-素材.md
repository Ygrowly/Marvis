- **锚点**：`projects/数驭穹图/`
- 用在哪：**把 Schema / 指标口径 / 样例查询视作不同知识类型**，关键词 + 向量混合召回表、字段和业务术语；**权限过滤先于 Schema Linking**
- 解决什么问题：**Top-K Schema 召回率 81% → 95% 的提升是靠什么拿到的？**——这条是本模块最值得在面试里讲的证据
- 踩过的坑：**砍掉的检索结果是「外置」不是「丢弃」**——大结果写 Artifact（Hot/Warm/Cold 三级生命周期），**上下文里只留口径摘要、聚合统计和 artifact_id**。需要下钻时按 id 取回。**说成「为了省 token 把数据扔了」就错了：扔的是常驻，不是数据。**
- 决策与取舍：**权限必须在检索前生效，因为「进上下文」就等于「已经泄露」**——模型说不说只是概率问题，不是控制手段；而且未授权内容还会挤占预算、可能进日志和缓存。**「让模型别说」是概率保证，「检索前过滤」才是权限控制**（[[母题-G2-向量与关键词的混合检索]] 5.1 的三条理由）。

- **补充（G3 / G5 的真实落点，一手证据在项目 md 里）**：候选 Schema 走「精确匹配 + 知识卡 + 关键词 + 向量」混合召回，再按**权限、粒度、场景适用性、更新时间、JOIN 关系**重排，只把少量相关 Schema 交给生成（`05-领域路由与Schema-Linking.md`）；失败的归因按**「召回缺失 ≠ 重排错误」**分两段看，各自对应不同的修复动作（`数驭穹图-可视化复习图谱.md`）。Top-K Schema 召回 **81% → 95%** 是用 150 条问题集量出来的（`数驭穹图项目说明.md`，必须带「Schema」两个字）。

### 5.2 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**条款按"条件 / 例外 / 生效时间"结构化切分**；召回规则后用**确定性状态模型验证**

### 5.3 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**运维文档、设备数据和实时状态不混成一个索引**；实时事实走 Tool / 数据库，静态说明走 RAG
- 解决什么问题：**故障建议要引用日志 / 指标 Artifact 和操作手册**——"证据"有两种形态
- 踩过的坑：**把运维文档和设备实时状态混进同一个索引**——检索出来的「当前负荷」其实是**上次同步时的**，而模型会把它当作当下事实引用。**过期的实时数据比没有更危险**，因为它带着「这是事实」的外观。
- 决策与取舍：**证据有两种形态，不能混**——**日志/指标是运行时产生的、会变**，走 Artifact 引用（绑定运行 id）；**操作手册是静态的**，走 RAG。混在一个索引里会让「引用」失去意义：**你分不清引的是哪一次运行的日志**（[[母题-G4-引用绑定与证据可追溯]] 的可追溯性）。

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：检索单元必须同时满足两个互相矛盾的需求：
  - 把"一块文档"当成检索单元，它要同时做到：
  - 这两个需求方向相反，所以"切多大"这个问题的正确答案不是某个数字，而是"承认它们矛盾、然后想办法解耦"。
- 2. 两端各坏在哪：
  - 单个块的意思甚至可能是反的。 小块的"高召回率"只说明它容易被匹配到，不说明它能独立支撑一个答案。
  - 另外两个代价：块数暴涨（索引与检索成本上升）、重叠切分时重复召回（挤占上下文预算）。
  - 块越大，单块的相似度信号越弱——关键内容不是"没被切到"，是被淹没在噪声里排不进 Top-K。
- 3. 候选方案一：解耦——小块召回、大块返回【事实】：
  - 得物那篇文章把它叫 Child-Parent，总结成一句很准的话：
  - 这个方案的通用价值在于：它把"检索用的表示"和"喂给模型的表示"拆成了两份。 只要这两者可以不同，矛盾就消失了——这也是后面所有 RAG 优化的同一个套路（重排用小块、生成用大块；索引用补过上下文的块、展示用原文）。
- 4. 候选方案二：不改粒度，改"块自己知不知道自己在说什么"：
  - Contextual Retrieval 的做法：切块之后，先让模型给每块补一句"它在全文里是什么位置、指代谁"（约 50–100 token），再把补过上下文的块拿去做向量和 BM25 索引。
  - 用约 12.5% 的索引体积，换 49% 的检索失败率下降。 这笔账很划算，而且它不需要改切分策略——是在现有切法上加一层。
  - 一次性成本：Anthropic 给过一个测算——用 prompt caching 做上下文增强，一次性成本约 $1.02 每百万文档 token（前提是缓存复用参考文档，否则要为每个块都重传全文）。
- 5. 三种切分策略的适用【事实】：
  - 得物文章里的一句总结可以当通用判据：
  - 这句话的落点是：切分策略的唯一验收标准是"在你的目标问题上召回率是多少"，而不是"是否符合某个最佳实践"。所以切分是一个需要 Eval 才能定的事（母题-G5-RAG评测与幻觉率）。

### G2 向量与关键词的混合检索

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：两路检索的盲区正好互补：
  - 得物文章给的那个反例最直观：
  - 所以"用哪个"这个问题的正确答案是"两个都用"——不是因为混合更先进，是因为它们的盲区不重叠。而两者都覆盖不到的（比如需要多跳推理的关系），才是 GraphRAG 要解决的问题（见第 5 节）。
- 2. 向量这一路的基础：相似度怎么量：
  - 为什么是余弦而不是别的——因为 Embedding 模型在训练时就是用余弦相似度优化的。
  - 维度不是"越大越好"的调优项——它由模型决定，换模型就换维度，整个索引必须重建。
  - 这也是"Embedding 版本"必须进版本管理的原因：新旧向量混在同一个索引里是不可比的，所以换模型 = 全量重嵌入 + 双写切换（母题-G6-知识更新与增量索引）。
- 3. 为什么必须用 ANN：算力账：
  - 单次查询 1.5 秒，这在任何在线系统里都不可接受。 而这是单条的代价——并发一来直接崩。
  - ANN（近似最近邻）不是"精度优化"，是"算力逼出来的"：牺牲一点召回精度，换数量级的性能提升。这是所有 ANN 算法共同的设计取舍。
  - 回顾跳表（母题-R1-Redis数据结构与选型）：有序链表加多级索引，上层稀疏、下层稠密，查找时从上层快速跳。
- 4. 两路怎么合：RRF：
  - 量纲不可比 → 加权求和需要调参，而且换个数据集就失效。
  - doc_B 略胜——它一路第一、另一路第十，却输给了"两路都在前列"的 doc_B。
  - 这就是 RRF 的设计意图：奖励"多路共识"，而不是"单路极端强"。 只在一路出现、另一路没出现的文档，自然排后面。
- 5. 融合之外的几件事：
  - 为什么必须在召回前：
  - 还要测的场景（这些都是真实事故形态）：跨租户、已撤权、共享链接、继承权限、删除传播、缓存污染。
  - Filter 有一个反直觉的坑：过滤会缩小候选集，可能把正确答案滤掉（比如 ACL 配置错了、或者时间字段本身标错）。所以过滤条件本身也要进评测——不能只测"过滤生效了没有"，还要测"过滤有没有误伤"。
- 6. 边界与常见误解：
  - 读成一句话："用哪一路"不是先进性问题，是"你的查询里有多少是专有编码、有多少是自然语言"——所以要按查询类型分桶评测来定，而不是拍脑袋。

### G3 重排与召回质量

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：召回和精排的优化目标本来就不一样：
  - 两个阶段的约束不同，所以"用同一个模型做一件事"必然有一头不划算：用贵的方法做召回 → 全量算不动；用便宜的方法做精排 → 排不准。两级漏斗不是工程习惯，是被约束逼出来的。
- 2. 双塔 vs 交叉编码器：本质差别是"能不能预计算"【推导】：
  - 为什么双塔"不够准"：
  - 双塔的信息损失来自"编码时看不到对方"——这是一个结构性的损失，不是模型不够大。所以它必须靠交叉编码器补回来，而不是靠换一个更好的双塔。
  - 交叉编码器不能用于召回，不是因为慢，是因为"不能预计算"：文档向量无法离线算好，每次查询都要对全量重算一遍——这才是它只能用在"已经缩小过的候选集"上的根本原因。
- 3. 重排的代价：延迟随候选数线性增长【推导】：
  - 重排会主导整条链路的延迟——它是"数量级更大"的那一项。
  - 所以"重排多少条"是一个必须算的成本决策：
  - 分档启用也是常见做法：重排提高质量但增加延迟与成本，应通过 Eval 判断是否只在难题启用（archive/study-courses/03 的结论）——简单查询（精确编号、单跳事实）不需要重排，难题才需要。
- 4. 重排的收益：两个口径别混【推导】：

### G6 知识更新与增量索引

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：索引是派生数据，源变了它就必须变：
  - 索引（向量 + 倒排 + 元数据）不是事实来源，它只是源文档的派生视图。 这直接推出一件事：
  - 新增最容易（多加一份），删除最难——因为删除要找全所有派生物，而派生物是散开的（一个文档切成 N 个块，每块有向量、倒排项、元数据）。
- 2. 为什么值得做增量【推导】：
  - 增量的收益是数量级的——尤其在嵌入调用要花钱的时候（母题-C6-成本与长上下文截断 的成本口径）。
  - 但增量不是免费的，它换来两个新问题：
  - 所以"全量重建"不是笨办法，是"数据量小、更新频率低"时的正确选择——它的简单性是真实的收益。判断该不该上增量，看的是"重建一次要多久、多久需要重建一次"，不是技术先进性。
- 3. 删除：为什么它比新增难得多【推导】：
  - 删除必须按文档 ID 反查它切出来的全部块：
  - 新增漏了只是"少了一条"，删除漏了是"多了一条不该在的"——后者的性质完全不同。
  - 所以删除需要一张反查表：doc_id → [chunk_id...]。这张表本身也是索引的一部分，也要维护、也要能容错。这也是为什么"删除传播"在 archive/study-courses/03 里被单独列为一步。
- 3.5 删除同样要清"索引之外"的派生物【推导】：
  - 第 3 节只清了索引内的三处（向量 / 倒排 / 元数据），但派生物不止在索引里——源文档的派生物是两层：
  - 删除传播的定义是"源没了，它的所有派生物都不能留"——缓存也是派生物，所以删除同样必须清缓存。否则：
  - 但删除比撤权更难清，难在反查方向：
- 4. 撤权：要清的地方比删除还多【推导】：
  - 撤权时，内容没变，变的是"谁能看"——所以要清的不只是索引：
  - 第 ④ 条是关键：缓存会绕过 ACL 过滤（母题-G2-向量与关键词的混合检索 里"权限必须在召回前生效"讲的是主链路，缓存是绕开主链路的另一条路）。
  - 所以缓存必须按租户 / 权限分区——它不是优化，是权限模型的一部分。
- 5. 新鲜度：必须可观测【事实】：
  - archive/study-courses/03 的要求（这一节可以直接背）：
  - 第 ② 条是最该盯的指标：
  - 为什么它必须是"指标"而不是"约数"：因为它决定"回答能不能引用刚改过的规则"——如果业务承诺"规则改了 10 分钟内生效"，那滞后指标超过 10 分钟就是故障。
- 6. 双写 / 影子索引再切换【事实】：
  - 直接原地覆盖索引有两个问题：
  - 正确做法是双写 / 影子索引：
  - 这和 母题-M4-索引代价与大表变更 的"影子表方案（pt-osc / gh-ost）"是同一个模式：
- 7. 边界与常见误解：
  - 读成一句话：增量省的是成本，删除与撤权保的是正确性——前者做不好是慢，后者做不好是事故。
