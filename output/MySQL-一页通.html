01主干：怎么存 → 怎么读得快 → 怎么写得稳 → 业务怎么落地正本 wiki/topics/MySQL/

七条主线压成四段：存（M1–M5）→ 读（M6–M7）→ 写得稳（M8–M13）→ 治理与落地（M14–M17）。三段失败必须能分开归因。
主干叙事（一段读完）：这一模块的一条线是「怎么存 → 怎么读得快 → 怎么写得稳与恢复 → 业务怎么落地」。 存：引擎与主键是被「并发写 + 不能丢」逼出来的 —— InnoDB、自增主键（UUID 让扇出 1170→390，总页数约翻倍、缓存减半）；但树矮只保证定位便宜，真实成本 = 扫描行数 + 回表次数，索引设计全部围绕少扫 / 少回 / 少排。 读：一条 SQL 走五层，五层里只有优化器在做决定 —— 慢的第一嫌疑人是它估算错了（一次可放大 50 倍），先查统计信息再动手；有时全表扫是优化器的正确决定。 写得稳：A 靠 undo、D 靠 redo、I 靠锁 + MVCC，C 是结果不是机制；RR 的快照读靠 ReadView、当前读靠 next-key lock；崩溃恢复先 redo 再 undo（顺序不能反），redo 与 binlog 分属两个组件，靠 2PC 捆成原子。 拖垮系统的是长事务：它按住全库的 undo 回收边界（只读也按）和锁 —— 分批同时治锁、undo、主从延迟、数据增长四个问题。 落地：先报冲突频率再选乐观 / 悲观锁（高冲突乐观 N² vs N）；排行榜把计算内建进 ZSet（O(logN)），防超卖把判断下推进原子操作 —— 同一条原理的两个应用。
读法：蓝线是主线；橙框是执行与优化（数字账最密的一层）；紫框是并发与恢复（面试最容易被追问的一层）；绿框是治理；绿线是治理回灌。读慢先问优化器、写挂先问锁与日志、拖垮全库先问长事务——三段失败分开归因。

M1 B+ 树为什么不用别的树唯一指标是「定位一行几次 IO」：16KB 页 → 扇出 ≈1170 → 2000 万行 3 层 3 次 IO；哈希不支持范围、红黑树扇出小 IO 多；「矮」只省定位，回表才是大头1未使用 —— 原理题不挂项目，别编
M2 最左前缀联合索引怎么设计索引按字典序连续存放，缺最左列 = 满足条件的行散落在每段里、无连续区间可扫；顺序不同扫描量差 30 倍；范围列后的列失「缩小扫描」不失「过滤」（ICP 省回表不省扫描）11、13EnergyOps：索引按「等值在前、时间范围在后」设计（device_id, energy_type, stat_date）
M3 回表 / 覆盖为什么覆盖索引快二级索引叶子 = 索引列 + 主键 → 命中后回聚簇树取整行，回表次数随命中行数线性涨；覆盖索引 = 索引自己答完（Using index）；真实成本 = 扫描行数 + 回表次数10、12EnergyOps：先修范围与 JOIN 再建联合索引——判断一条 SQL 看回表，不只看 EXPLAIN 的 rows
M4 索引代价 / DDL加索引为什么能搞挂库索引是读的快照、写的负债：每次写维护 N 棵 B+ 树；大表 DDL 的危险是「不可控的等待」（MDL 排队被并发放大）；影子表（pt-osc / gh-ost）= 新建 + 双写 + 验证 + 切换14、15未使用 —— 判据记牢：没有查询在用的索引是纯负债，只在写入时收费
M5 引擎 / 主键 / 类型表怎么建才不埋雷「并发写 + 不丢数据」逼出 InnoDB（MyISAM 叶子存地址、无事务）；主键 UUID(36B) → 扇出 1170→390、总页数约翻倍、缓存减半；char 只用于长度真固定的字段2–9未使用 —— 代价讲不出 = 没选过：引擎 / 主键 / 类型都在回答「写入顺不顺、以后改不改得动」
M6 SQL 执行五层一条 SQL 怎么走、慢在哪连接器 → 分析器 → 优化器 → 执行器 → 引擎层，五层里只有优化器在做决定 → SQL 慢第一嫌疑人是估算错（一次可放大 50 倍）；查询缓存死于「以表为粒度失效」16、17EnergyOps：慢的根因不是单条 SQL，是先展开归属与事实再过滤园区——先修范围与 JOIN，不是先换库
M7 慢查询优化优化手段怎么归类一切手段归三类：少扫（最左前缀 / 避开大偏移）· 少回（覆盖 / ICP）· 少排（索引序匹配 ORDER BY）；先分清「写法问题」还是「成本判断」——有时全表扫是优化器的正确决定18–23EnergyOps：修范围与 JOIN → 联合索引 → 消 N+1 → 最后才缓存（P95 20.4s→2.8s，待验证口径，先说口径）
M8 隔离级别 / ACID并发为什么不会乱并发只有两种冲突关系；隔离谱系单调 RU→RC→RR→串行化；ACID 有分工：A 靠 undo、D 靠 redo、I 靠锁+MVCC，C 是结果不是机制；MVCC 把读摘出冲突（1%）24、25RuleArena：权威状态在同一个事务内提交——事务边界即业务边界（A 的范围）
M9 MVCC读为什么不用加锁读看旧版本：undo 版本链 + ReadView 判可见性；RC/RR 只差生成时机（每语句 / 首次快照）；旧版本回收由最老 ReadView 决定——一个长事务就能让全库回收停摆26、27未使用 —— 机制题；但「回收边界」这条直接连到 M13 长事务与 PG 的 idle in transaction
M10 锁与死锁锁什么时候会变大锁的可寻址对象只有索引项——条件无索引可用时锁全表（1 条 → 100 万条，差 6 个数量级）；RR 默认 Next-Key = 间隙 + 记录（防插入 + 护已有）；死锁 = 顺序不一致成环28–30RuleArena：条件更新替代 SELECT … FOR UPDATE，避开 RR 下 next-key lock 的范围放大
M11 三日志 / 2PC断电为什么不丢WAL：随机页写 → 顺序日志写（机械盘差 2–3 个数量级）；redo 环形 + checkpoint 推进；binlog 管复制与回档（Row 主流）；redo+binlog 分属两组件 → 2PC 捆成原子31–35数驭穹图：接入 MySQL 源优先用 Binlog（CDC 的前提）；「双一」才是断电不丢的配置
M12 崩溃恢复重启后数据怎么回来崩溃瞬间事务三态、各有日志痕迹：先 redo 重放（幂等：做前判是否做过）再 undo 回滚——顺序反了会丢已提交；prepare 态由 2PC 裁决36、37未使用 —— 恢复时长能算：≈ checkpoint 落后的 redo 量 ÷ 重放速度
M13 长事务它凭什么拖垮全库按住两样东西：全库 undo 回收边界（由最老 ReadView 决定，只读也按）+ 锁——两条独立链；外部系统的响应时间绑进事务 = 事故；分批同时治四个问题38RuleArena：事务只包数据库操作、Checkpoint 不当业务事实——动作与 Checkpoint 间永远有崩溃窗口
M14 主从复制延迟为什么是结构性的复制的是 binlog 变更流不是数据页 → 主写 > 从放则延迟累积（结构如此，不是故障）；并行度按库 → WRITESET；无主键表 Row 回放拖慢从库；半同步治丢不治旧39、40数驭穹图：SNAPSHOT / LIVE_READ 按新鲜度选访问模式——「哪些读可以旧」是业务决策
M15 数据增长数据大了先做什么「8000 万行」先定位症状（慢 / 大 / 贵）再动手；五步按复杂度递增：索引 → 冷热分离（量降 1/10、树高 4→3）→ 归档 → 读写分离 → 分库分表（最难回头）41–43EnergyOps：Raw → 可信聚合 → hourly → daily 分层，热查询不打冷数据；数驭穹图：快照 + 位点 + 校验换生产隔离
M16 乐观 vs 悲观冲突频率决定选型先报冲突频率再谈机制：乐观 = 期望值进 WHERE（CAS），高冲突时总工作量 N² vs 悲观 N（p→1 发散）；影响行数 0 是业务分支：读权威快照 → 判定，不无脑重试44RuleArena：version 条件更新 + UNIQUE(run_id, action_type, idempotency_key) 兜底——理由是权威性，不是「低频写」
M17 排行榜 / 防超卖场景题怎么拿分第一动作是澄清（榜单范围 / 更新频率 / 历史榜 / 防作弊——9.9 没问的四个）；MySQL O(N) vs ZSet O(logN) 随榜单长度拉开；防超卖 = 判断下推进原子操作45、46RuleArena：资金正确性靠数据库唯一约束兜底，不靠内存锁或 Redis 锁；「榜单挂了不能影响主链路」是底线

      05要能现场算出来的数正本 母题卡「一、教材」推导

      每个数都要带推导，只报结果是会被追问倒的。
      一张 B+ 树多高
      2000 万 = 3 次 IO
      16KB 页，非叶 14B/条 → 扇出 1170；1170² × 16 ≈ 2000 万行，定位一行 3 次 IO；小表根页即叶（高 1）。
      UUID 主键的账
      扇出 1170 → 390
      36B+6B=42B/条；二级索引每条也带主键 → 总页数约翻倍，buffer pool 能装的页减半——读跟着变慢。
      索引顺序的账
      30 倍
      同样的字段、同样的条件，只是列顺序不同，扫描量差约 30 倍——字段顺序不是风格问题，是成本问题。
      深分页的账
      10 万倍
      LIMIT 1000000,20 的扫描与回表量 = 偏移量，线性涨：第 100 万页是第 1 页的 10 万倍；解法方向是把「翻页」变成「按上次位置继续」。
      串行化的代价
      1% → 19%
      MVCC 把读摘出冲突（冲突面 ≈1%）；串行化把读也拉回排队（≈19%）——把 MVCC 挣来的并发又还回去。
      锁的膨胀
      1 条 → 100 万条
      同样是「更新 pending 任务」：走唯一索引锁 1 条；条件无索引可用时锁全表 100 万条——差 6 个数量级。
      长事务的账
      72 ms
      一个「什么都没干」的只读事务按住回收边界，别人读那一行要沿 undo 链回溯、慢 72ms——链是别人造成的。
      乐观锁发散
      p=0.9 → 10 次
      期望尝试次数 E=1/(1−p)：0.05→1.05、0.9→10；N 个并发写同一行总工作量 N² vs N——高冲突差 N 倍。
      榜单内存
      1/100
      2000 万 DAU 全量 vs 每关只存 Top 1000（1000 关）→ 内存差 100 倍；头部精确 O(logN)、长尾近似 O(1)。

      06八句最容易说错的话正本 母题卡「二、自测」纠错题原话

      说对前半句没用，后半句才是判据。
      ✗「B+ 树因为矮所以快」✓ 矮只保证「定位到索引项」便宜；要取整行还得回表（二级索引场景），那才是大头。
      ✗「树高 3 层，所以这条查询一定快」✓ 树高对任何查询都一样，解释不了差异；差异在扫了多少行、回了多少次表。
      ✗「RR 已经完全解决了幻读」✓ 快照读靠 MVCC、当前读靠间隙锁，各不幻读；混用时仍会「看起来像幻读」。
      ✗「RR 下普通 SELECT 也会加锁」✓ 普通 SELECT 是快照读，不加锁；只有当前读（FOR UPDATE / 写条件）才加锁。
      ✗「有 redo 就不需要 binlog 了」✓ 职责不同：redo 只服务崩溃恢复、用完即弃；binlog 服务复制与时间点恢复，必须长期保留。
      ✗「重放和回滚谁先谁后无所谓」✓ 必须先 redo 重放再 undo 回滚；反过来会在「已提交但页未落盘」时丢掉已提交数据。
      ✗「长事务危险就是持锁久」✓ 它还按住全库的 undo 回收边界——只读长事务照样拖慢别人（72ms 那条链）。
      ✗「乐观锁比悲观锁先进，尽量用乐观」✓ 没有冲突频率就没有选型：高冲突时乐观 N²、悲观 N——差 N 倍；影响行数 0 是业务分支。
