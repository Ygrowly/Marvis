## 5 · 项目映射（检索表「项目证据」列的来源）

### 5.1 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**缓存加速读取**（园区/表/指标的元数据）；**写路径用 Outbox 而不是"提交完顺手删 Redis"**
- 解决什么问题：**缓存是派生数据，DB 才是权威** —— 这条定位决定了"不一致时以谁为准"
- 踩过的坑：**把聚合结果当缓存读**——缓存里该放的是**元数据**（园区/表/指标定义），不是**业务事实**（用量、账单）。元数据陈旧最多是查询慢一点；业务事实陈旧会让**页面和月账单出现两套数字**，而结算必须只有一个权威口径
- 决策与取舍：**为什么用 Outbox 而不是「提交完顺手删 Redis」**——因为 **PG 提交与 Redis 删除不可能构成同一个 ACID 事务**。先删缓存再提交，提交失败就留下脏缓存；先提交再删，删除失败就留下更久的脏缓存。**Outbox 把「删除」变成事务内可提交的一条事实**，再由异步消费者执行，失败可重试、可审计

- 对应母题：【R3】

### 5.2 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**权限与语义层的缓存**（口径、指标、粒度这类读多写少的数据）；**限流与短期去重**
- 解决什么问题：**权限相关的数据能不能缓存？** —— 能，但**必须有明确的失效路径**（权限变了要能立刻失效，否则是安全问题不是性能问题）
- 踩过的坑：**权限数据一进缓存，撤权就不再是即时的**——TTL 没到期前，已经失去权限的人照样能命中。**这是安全问题，不是性能问题**，不能用「缓存总会过期」搪塞
- 决策与取舍：**分界线是「陈旧的后果是慢还是错」**。口径、粒度、常用指标这类，陈旧几分钟只是体验问题 → 可缓存；**行级权限、租户归属、字段可见性一秒都不能陈旧** → 所以它们**不作为缓存值**，而是作为**召回前的过滤条件每次重新求值**（[[母题-G2-向量与关键词的混合检索]] 的「权限必须在召回前生效」在缓存侧的同一件事）

- 对应母题：【R3】

### 5.3 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**短期去重 / 限流 / lease 归属**（`study/09` 明确写了"Redis 用 Cache Aside、限流或短期去重，但不把缓存当最终事实"）
- 解决什么问题：**动作有副作用，所以 Redis 只能做"辅助判断"，不能做"最终裁决"** —— 最终裁决必须是 DB 的约束或条件更新
- 踩过的坑：**用 Redis 判断「这笔动作做过没有」**——Redis 重启、主从切换、或单纯的过期，都会让同一个幂等键被判成「没做过」→ **重复执行副作用**。而超时重投在 Agent 场景里是常态，不是异常
- 决策与取舍：**区别在「丢了会怎样」**。**短期状态**（限流计数、去重窗口、Worker lease）丢了最多是多做一次检查，可恢复、可重来 → 放 Redis 划算；**任务状态与幂等判断**丢了就不知道「做过没有」，这是**正确性问题** → 必须落 PG 的唯一约束（[[母题-P19-唯一约束与UPSERT]]）。**Redis 只能做辅助判断，不能做最终裁决**

- 对应母题：【R3】

### R2 Redis 的数据怎么不丢

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：先把三件「数据消失」的事拆开：
  - 为什么必须分开？因为触发源不同：前者由数据自己的属性（有没有设 TTL、到没到期）决定；后者由实例的状态（内存够不够）决定。一个 key 完全没用过期时间，也可能被淘汰；一个设了 TTL 的 key，也可能在被淘汰前就自然过期。
- 2. 持久化：RDB 与 AOF：
  - 这两条路线没有优劣，只有你更怕哪个：怕丢数据选 AOF，怕恢复慢 / 文件大选 RDB。生产上通常两个都开——RDB 做冷备份和快速恢复，AOF 保证最多丢 1 秒（4.0 之后还有混合持久化：RDB 全量 + 后续 AOF 增量，写在同一个文件里）。
  - 所以生产上选 everysec 不是因为"不重要的数据可以丢"，而是用"最多丢 1 秒"换回整整 1 个数量级的吞吐。
  - 这是 RDB 最容易被忽略的代价：快照期间写越多，内存涨得越多。如果实例已经接近 maxmemory，一次 bgsave 就可能触发淘汰甚至 OOM。这也是为什么大实例上要留出余量（常见做法是让 maxmemory 不超过物理内存的一半到 2/3）。
- 3. 过期删除：惰性 + 定期：
  - 定期删除用的是"抽样"而不是"全扫"——它接受"有些过期 key 暂时没被清掉"，换"主线程永远不会被清理工作长时间占住"。
- 4. 内存淘汰：8 种策略：
  - 注意 ttl 只有 volatile- 版——没有 allkeys-ttl（"所有 key 里挑最快过期的"没有意义，因为没设 TTL 的 key 没有"最快过期"这个属性）。这也是为什么是 1 + 4 + 3 而不是 1 + 5 + 5。
  - 面试时怎么答：先把经典的 8 种列全（这是标准答案），再补一句"较新版本还加了 lrm（只按修改时间算，读不算），所以现在是 10 种"——既答到点上，又显示你不是背的旧资料。
  - ：它随机采样 N 个 key（默认 5），淘汰其中"最久没用"的那个。为什么不做精确 LRU？——精确 LRU 要维护一条全量链表，每次访问都要移动节点，内存和操作开销都上来了。又是同一个思路：用近似的抽样，换掉一个 O(n) 或重开销的结构。
- 5. 复制与集群：它们为什么也不能保证「不丢」：
  - 很多"Redis 丢数据"的真实原因不是持久化没配，而是这里——持久化保证的是"同一台机器重启能恢复"，故障转移走的是另一条路，那条路上没同步的部分就丢了。
- 6. 边界与常见误解：
  - 把这张表读成一句话：Redis 的所有"不丢"手段都是用一致性、内存或性能换来的，没有一个能同时做到"快、省、不丢"。
**自测 cue**：
