01主干：一次 Run 从头到尾正本 wiki/topics/Agent运行时与工具/

分层走一遍：入口 → 循环体 → 六道闸 → 出口 → Eval 闭环回灌。循环体只有四步，工程的分量全在闸和出口上。
主干叙事（一段读完）：一次 Run 从入口开始 —— 先确认是不是真的需要 Agent（步骤能穷举就用 Workflow），再带着目标、版本和七种预算进入循环体。 循环体只有四步：组装 Context（它是 State 的投影，不是副本）→ 模型决策（给答案还是调工具）→ 校验并执行 → 记录 Step（版本 / 幂等键 / 耗时 / 错误码）； 复杂度要放在能被单独测试的边界组件里，而不是塞进 Prompt。每转一圈都在积累风险，所以每个读写动作都要先过六道闸：工具契约、幂等与重试、检查点与恢复、压缩与记忆、沙箱与权限、编排与计划。 出口只有三个：结果通过验证（模型说 done 不算）、七种预算里某一个先到、或连续无进展（比步数耗尽更准的停止信号）；走到出口时必须落一个结构化的终止原因 —— 它不是日志字段，是 Eval 的输入。 最后 Eval 沿五层归因（目标 → 计划 → 工具 → 副作用 → 终止）回到起点，去调预算、裁工具、改提示、调阈值；这条绿色的回灌线，才是这个模块真正闭环的地方。
读法：蓝线是正常路径；橙线是每圈必过的六道闸（扇出 → 汇入）；紫线是循环回边与汇入 Eval；绿线是闭环回灌。六道闸不是可选优化——每一道对应一类事故，且都能被单独测试；提示里堆规则做不到这一点。

      05要能现场算出来的数正本 八张母题卡「一、教材」推导

      每个数都要带推导，只报结果是会被追问倒的。
      失控一次多少钱
      50 步 ≈ $15.9
      每步新增 2.5K token，历史每轮重发 → 2.5K×(50×51/2)＝3.19M，按 $5/MTok 输入算。并发一来是乘出来的。
      无进展检测的价值
      $15.9 → $1.14
      第 10 步卡住、连续 3 步无进展就停 → 第 13 步收工（约 1/14）。比调小 max_steps 更准：卡住和认真干活长得很像。
      压缩能省多少
      3.19M → 1.49M
      50 步每 20 步压一次（压到 10K）：不压缩是整段平方，压缩是分段平方，任务越长省得越多。
      多 Agent 的代价
      1× / 4× / 15×
      对话 / 单 agent / 多 agent，换来 +90.2%；token 用量单独解释 80% 的性能方差 —— 买的不是「更聪明」。
      effort 不分档
      浪费可达 24×
      简单查找实际要 1 agent×5 次调用，按复杂研究配置跑是 10×12＝120 次。分档写进 prompt：1 / 2–4 / >10 个。
      先查 vs 直接重试
      50 : 1
      P(已执行)＝50%、事故代价 100 → 直接重试期望损失 50，查询成本 1。超时＝不知道做没做成，不是没做成。
      重试放大
      3×3×3 = 27×
      客户端×网关×服务各重试 3 次。真实事故：队列积压 8 万，副本 20→100 反而更糟。只让一层重试。
      checkpoint 的收益
      45 步 vs 5 步 = 69×
      重做代价是平方累计的（2,587.5K vs 37.5K）。代价是存储：50 步×50KB＝2.5MB/run，1 万 run/天 ≈ 25GB/天 → 按业务节点存，不按步存。
      能确定化就别交给模型
      19.7% → 52%+
      10 项检查全用 Judge（85% 准）全对率仅 0.85¹⁰≈19.7%；60% 确定化后升到 52%+。优先级：确定性测试 > 工具/权威状态 > 多源交叉 > Judge > 人工。

      06八句最容易说错的话正本 母题卡「二、自测」Q4/Q5 纠错题原文

      这正是教材里 Q4/Q5 让你纠错的那类原话。说对前半句没用，后半句才是判据。
      ✗「循环是 while，模型返回 done 就结束」✓ 只有结果通过验证才算（completed_verified）。模型说 done 是它的判断，不是事实。
      ✗「我们设了 max_steps = 50，所以不会失控」✓ 预算是七种（步数/token/时间/工具次数/单工具配额/重试/产物），先到先停 —— 要算清哪个先生效。
      ✗「所有 API 都封装成工具，80 个，覆盖很全」✓ More tools don't always lead to better outcomes。重叠／含糊会让 agent 分不清，且描述每轮都占上下文。
      ✗「用 ToolCallID 做幂等键最自然」✓ 重试会换 ID → 约束永远失效。判据：同一业务意图重试时这个键会不会变？
      ✗「超时了就重试三次，很安全」✓ 超时＝不知道做没做成。先按业务键查权威状态（期望损失 50 vs 成本 1）；三层重试还会放大 27 倍。
      ✗「每一步状态都存进数据库了，恢复没问题」✓ 只存消息历史＝没有「哪些写操作真的发生了」；恢复时也不能直接把旧上下文加载回来继续跑。
      ✗「每个动作都弹窗让人确认，权限很安全」✓ 审批疲劳：50 次里从第 20 次起就不看了。用边界替代确认（沙箱减 84%，且更安全）。
      ✗「多 Agent 比单 Agent 强很多，能拆就拆」✓ 买的是多花 token＋并行（token 单独解释 80% 方差），代价 15×；先问任务价值够不够高、能不能并行拆。
