> 我是做 **AI 应用与 Agent 工程**的，Python 后端打底；差异化在让 Agent 在真实业务里**数据可信、执行受控、结果可被证明**。三个项目分别证明这三件事。

## 一、金山 EnergyOps —— 锚点：可治理性（业务 Agent 受控执行）

### 一句话定位
> 我在金山做了一个园区能耗智能运营平台：把 604 台参差的水电表读数变成三本可信的账（用能/异常/结算），并给行政、财务一个受权限和人工确认约束的对话式 Agent 入口。**我负责的是让这个业务 Agent 跑得安全、可回测、能持续变好。**

### 60–90s 全貌（口语）
> 问题：园区原来只有同方平台的原始累计读数，质量差、不能直接用；告警一天几十条真问题被淹没；月度水电分摊靠行政在 Excel 里手工对账。
> 我做的平台做四件事：① 把原始读数经过 7 类质量判定和分层聚合，变成可信用能账——可信聚合完整率从 96.8% 提到 99.7%；② 把异常识别和通知拆开，先判候选、再判要不要打扰人，告警量降 43%，研判从 18 分钟降到 6 分钟；③ 月度结算走三道质量门，行政确认、财务核验之后才出正式分发版，能审计；④ 在 WPS Comate 里给行政一个自然语言入口。
> Agent 是入口不是外壳：它的写操作全部按 R0/R1/R2 分级，高风险必须先预览再确认，越权在工具执行前被 Hook 拦掉。真正让它"生产化"的是最后一块——维修工单的处置信号自动回流评测，指南写得好不好直接体现为二次派单率，业务运转本身就在喂数据飞轮。

### 我的负责模块
- **主责①：Agent 运行时治理（Hook 链 + 风险分级 + 可插拔策略）** —— 能讲三层：
  1. 机制：Before/After Tool + Before Model 三个插桩点，分别管越权、上下文膨胀、过程失忆；R0/R1/R2 是 Hook 上的策略配置，不是独立机制。
  2. 取舍：治理策略可插拔，业务只声明"哪个能力什么风险级要不要确认"，核心 Loop 不随业务改；借鉴 Harness 的扩展点思路而非照搬。
  3. 边界与失败：R2 未确认直接阻断；`NEEDS_CONFIRMATION`/`PARTIAL`/`TOOL_TIMEOUT` 等失败语义分级返回。
- **主责②：评测分层 + 无标注数据飞轮（工单信号自动回流）** —— 能讲：
  1. 六层评测：数据层→Tool Contract→任务结果→过程质量→风险安全→效率体验；风险安全是 P0 硬门禁，不走平均分豁免。
  2. 版本与回测：评测集、Rubric、模型/Prompt/工具统一版本号，发布前在固定版本组合回测。
  3. 回流不靠人工标注：指南采纳率/一次关单率自动留痕，归因用确定性规则+LLM Judge，人工只复核争议样本。
- **支撑：数据可信底座与结算**（分层聚合、7 类质量、幂等回补、抄表底稿与自动采集交叉核对）——讲业务真实度和对账即可。
- **明确不抢**：结算财务口径（与财务团队对齐）、Comate 宿主底层、产品入口设计。

### 必被追问（指向文档）
- 结算为什么用人工抄表底稿、和自动聚合什么关系 → §0 口径说明 / §4.5 / §7.4（先讲"口径唯一，自动只做核对"）。
- R 分级怎么定、为什么 Hook 能拦越权 → §6.4（80 条用例拦截 100%，口径在 §14.3）。
- 数据飞轮数据从哪来、要不要人工标注 → §8.4 / §14.3。
- 5.8 万/日怎么算、96.8→99.7 的口径 → 量化口径文件（604×24×4≈5.8 万，15 分钟采集周期；有效区间 ÷ 应产生区间）。

### 补课清单
- 能写出：一个 Hook 拦截 R2 未确认操作的伪代码/实现思路；任务状态外置的字段与恢复流程。
- 能讲清：四层 vs 七层分层的一致性（统一说"分层聚合，中间含标准化与月结快照"）。

## 二、数驭穹图（深圳慧泽致远）—— 锚点：可归因性（让问数结果可信）

### 一句话定位
> 我在慧泽致远做一个面向中小企业的 AI 数据分析产品：业务人员用自然语言问数，而不是等数据团队写 SQL。**我负责的是"可信"这条链——语义层统一口径、契约先行的六阶段链路、五层安全、证据绑定与端到端血缘——让"SQL 能执行"不等于"业务答案正确"。**

### 60–90s 全貌（口语）
> 问题：中小企业业务人员想用数据，但被"找数据同学→写 SQL→等排期"卡住；更麻烦的是同一个"销售额"在不同行业口径完全不同，AI 直接写 SQL 很可能答非所问。
> 平台的思路分四层：① 语义层，把每个行业的指标口径、别名、合法关联沉淀成 Domain Pack，先统一业务口径再谈查询；② 链路，把自然语言问数拆成六阶段——意图路由→域内检索→分析计划(SemQL)→SQL 生成校验→受控执行→证据绑定解释，阶段拆开才能归因；③ 安全，五层边界+信任分级，查询只读、走 AST 审查，危险语句拦截 100%、正常误拦控制在 2.7%；④ 沉淀，结果绑定 Provenance、带端到端血缘回写成可编辑表格和看板，随源更新——每次问数都不是终点，是资产。一个不懂 SQL 的运营把周报从 40 分钟压到 12 分钟。

### 我的负责模块
- **主责①：语义层与领域路由（Domain Pack + NL2SemQL2SQL + SDD 契约先行）** —— 三层：
  1. 机制：意图路由→域内混合检索→AnalysisIntent 草稿→澄清确认→固化 SemQL→生成 SQL；AnalysisIntent 是"意图级契约草稿"，SemQL 是固化后的计划，同一意图两级产物不重复建模。
  2. 取舍：SDD——能力先有 Schema 契约、中间产物先定义字段、输出先过 AST，失败才能归因到"违反哪条契约"而非模型随机；为什么不让模型从自然语言直接跳 SQL（可独立验证业务理解 vs SQL 实现）。
  3. 边界：口径歧义必须澄清，模型不自行决定口径；澄清选项由 Domain Pack 枚举而非模型生成。
- **主责②：安全执行与可信保障（五层安全 + 信任分级 + 证据绑定/血缘）** —— 三层：
  1. 机制：入口→能力→调用→执行→输出五层；调用层把模型输出当不可信输入，tenant 由服务端注入；执行层只读受限账号 + AST 审查 + 成本预估拒绝。
  2. 取舍：信任分级——自有副本可操作度最高、客户生产库只读直查；行级权限在 DuckDB 就地查询按"本地执行+平台侧最终裁剪"，直查才 push-down，两条路径看到同一行列集合。
  3. 边界：权限撤销对下次查询即时生效；分享快照按当前权限校验；证据绑定失败降级为占位块。
- **支撑：轻量湖仓**（Parquet 副本 + DuckDB + 查询路由 + 生产库保护 + 输入沙箱化 + 能力动态注册）。
- **明确不抢**：评测体系（归 RuleArena 主线）、前端表格引擎本身、市场与销售定位。

### 必被追问（指向文档）
- 查询成功率 78→91 / 拦截 100% / 召回 81→95 的口径 → §13.3（150 条评测集、300 条对抗、150 条正常等）。
- 五层安全 vs 五层可信保障是不是一回事 → §13.3 末行（执行侧 vs 结果侧）。
- 慢 SQL 拖垮客户生产库怎么办 → §4.11（副本优先/EXPLAIN 拒绝/熔断降级/独立配额）。
- 案例里销售额口径和退款归因会不会重复计算 → §12.1 口径注（支付金额 + 退款作为漏损项正交）。
- 权限撤销后副本/快照/看板旧版怎么收敛 → §4.11 权限撤销与就地过滤。

### 补课清单
- 能写出：六阶段中某一阶段的关键数据结构（AnalysisIntent→SemQL 的字段与校验）；SQL AST 审查的几条关键规则；行列权限在返回前裁剪的实现思路。
- 能讲清：为什么 6 类源、Domain Pack 3 套 65 指标 120 别名这些数字的来源与含义。

## 三、RuleArena（个人项目）—— 锚点：可证明性（让 Agent 行为可被证明）

### 一句话定位
> RuleArena 是我的个人项目：一个面向电商规则变更的 AI 对抗验证与发布门禁平台。**我负责的是"评测与门禁"这套底层方法论——把自然语言规则变成可执行契约，让受控 Agent 去搜人没想到的动作组合，再用确定性 Oracle 证明它是否真的会造成资金异常。**核心不是追模型上限，是让 Agent 的业务行为可被证明。

### 60–90s 全貌（口语）
> 电商里很多事故不是单条规则错，而是订单/优惠券/积分/退款在特殊顺序下组合出错；单测只覆盖你想到的路径，LLM 审文档只能给风险提示。RuleArena 的做法：先把自然语言规则编译成严格 RuleSpec，歧义必须人工确认冻结；再用 BFS 基线和几个隔离策略去搜动作序列，先在参考模拟器快速剪枝，晋升到独立 Sandbox 用真实 HTTP API 重放；模型只负责提议动作，漏洞成不成立由确定性 Oracle 按价值守恒、幂等这些不变量判。确认的问题压成 1-minimal 反例进回归，修复后旧反例必须消失。整套东西用 24 个开发/隐藏 Case 做消融，hidden 集连运行时都读不到，防止针对考纲训练。

### 我的负责模块
- **主责①：评测与门禁体系（双集隔离 + 消融 + 发布 Gate + 反例回归）** —— 三层：
  1. 机制：development 16 / hidden 8 双集，hidden 由 Evaluation 维护、Runtime 不可读；Random/BFS/Single/Multi 在归一化预算下消融；P0 反例 100% 回归。
  2. 取舍：为什么用"规则+确定性评分 + hidden 隔离"，而不是让 Agent 自测或只看 development 成绩（防过拟合）；预算公平——不同策略用同一归一化预算比。
  3. 边界：门禁承诺的是"预算内未发现"，不是"规则安全"；平台 24-Case 指标证明机制可信度，单条规则门禁 = 域回归 + 专项重放 + 未发现声明，分层不混淆。
- **主责②：Agent Runtime 与副作用控制（Workflow/FSM、幂等、checkpoint、预算）** —— 三层：
  1. 机制：显式状态机主流程；写动作带幂等键 + Receipt + `ACTION_UNKNOWN`（超时后查询权威状态防重复副作用）；Agent 只提议不写库。
  2. 取舍：为什么主流程用 Workflow/FSM 而不是 LangGraph 自由编排；PostgreSQL 当权威状态、Redis 只做队列，避免事实源漂移。
  3. 边界：Checkpoint 恢复的是 Run 状态；`COMPLETED` 只表示结束，Outcome 可能是未发现/歧义/失败，严格分离。
- **主责③：Oracle 三角（防自证）** —— 裁决以冻结 RuleSpec 为基准，每步重读权威状态而非信任 Receipt；Simulator 只是近似剪枝不产出确认；A2A/MCP 只作接入映射层（TargetAdapter），裁决与执行仍隔离。
- **明确不抢**：产品与市场定位（§7 谈资，不进"我做的模块"）；被测真实企业系统（MVP 是独立 Sandbox，诚实分层）。

### 必被追问（指向文档）
- 24 Case 过拟合吗 / 75% 剩下 25% 怎么办 → §14 追问表（双集隔离、hidden、下界证据）。
- Oracle 会不会自证 → §2 原则二/四 + §3 分工段（RuleSpec 为基准、重读权威状态、独立部署）。
- Simulator 会不会滤掉真 bug / 晋升靠什么 → §3 分工段（保真抽样对照 + 确定性启发排序，不信 confidence）。
- 多 Agent 到底用没用 / MCP/A2A 呢 → §14 追问表新增两行（隔离策略、克制用法、接入映射层）。
- 哪些是真跑出来的 → 先答"文档里口径标注了设计目标 vs 实测；我在 development 集上跑出的是 X，hidden 是评审口径"。

### 补课清单（最重要，因为它最像"你能独立交付的证明"）
- 面试前把**实际跑出来的 Run/指标清单**钉死：24 Case 各属于什么缺陷类型、dev 集发现率、是否已有可复现的 BenchmarkRun；凡是没跑的，一律按"设计目标"讲。
- 能写出：Oracle 一条不变量（如退款后积分守恒）的判定逻辑；幂等键 + Receipt + `ACTION_UNKNOWN` 的状态流。
- 公开 repo + README（至少）——个人项目没有链接，说服力折半。

## 四、三项目关系（每个项目收尾都可引）

> EnergyOps 证明我在**业务落地层**做 Agent 治理（Hook、风险分级、质量门禁、数据飞轮）；数驭穹图证明**数据侧基建**（语义层、湖仓、安全、血缘）；RuleArena 证明**评测与验证方法论**（不变量、Oracle、消融、门禁）。三个都指向同一个判断：**Agent 生产化的瓶颈在可靠性工程，不在模型**——这也是我投 Agent 岗位的原因。

## 五、防"重复感"提醒（跨项目连讲时）

三个项目共享一串词（Hook/Eval/Oracle/状态机/幂等/证据绑定/回流），含义分层不同，主动区分：
- **Oracle**：数驭穹图 = 结果正确性的确定性评分；RuleArena = 业务不变量裁决。先说清再说用。
- **评测**：EnergyOps = 业务信号回流、数据从哪来；RuleArena = 评测怎么设计（双集/消融/门禁）。别在两个项目里重复同一段。
- **Eval/门禁**：EnergyOps 是"发布前回测业务能力"，RuleArena 是"发布门禁证明规则没被绕坏"。场景不同，讲场景不讲名词。
