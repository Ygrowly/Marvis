### 5.1 EnergyOps（金山园区能耗 · PostgreSQL）

**锚点**：`projects/EnergyOps/03-query-and-performance.md`（四层事实表：原始 → 可信聚合区间 → hourly → daily；联合索引；`EXPLAIN ANALYZE`；消除重复 join）、`02-aggregation-and-recovery.md`（15 分钟窗口、幂等与补数）

- **用在哪**：604 台电表 15 分钟一次的累计读数采集与治理落库；查询链路按粒度命中 daily / hourly 事实表，不回到 Raw 现算差分。
- **解决什么问题**：原查询慢的根因不是单条 SQL，而是**先展开设备归属和大量事实、再过滤园区**——既产生大量中间行，又可能重复 JOIN，还叠加应用层 `N+1` 和现算差分；接口 P95 二十多秒。
- **踩过的坑**：① 归属关系未限制有效期 → 历史设备套用当前归属，同一设备被重复统计；② N+1（先查 100 台设备，再循环查每台 30 天用量 = 1+100 次往返）；③ 晚到数据重算后数据库已是新值，Redis 仍返回旧结果（缓存陈旧）。
- **决策与取舍**：没有换 OLAP、也没有全量上缓存，而是按顺序来——**先修范围与 JOIN 逻辑 → 再建联合索引 → 再选正确聚合层 → 消除 N+1 → 最后才上缓存/预聚合**。索引按「等值条件在前、时间范围在后」，如 `(device_id, energy_type, stat_date)`；事实表合法冗余园区快照时也可考虑 `(campus_id, energy_type, stat_date)`，最终以选择性和执行计划为准。缓存一致性用「事务内写 CacheInvalidation Outbox → 提交 → 异步 worker 幂等删缓存」，或把聚合版本放进缓存键——因为「PG 提交」和「Redis 删除」不可能构成同一个 ACID 事务。
- **对应母题**：M2、M3、M6、M7、M15
- **口径提醒**：`P95 20.4s → 2.8s` 属**待验证数字**（手册未关联原始报告）。面试必须自带口径：查询范围、样本数、并发、硬件、缓存冷热、统计窗口、P95 算法。**报数字前先说口径，比被追问出来安全。**

### 5.2 数驭穹图（企业问数 · PG 存元数据，接入 MySQL 数据源）

**锚点**：`projects/数驭穹图/02-数据接入与轻量湖仓.md`、`07-权限安全与生产隔离.md`、`08-查询性能与成本控制.md`

- **用在哪**：PostgreSQL 保存租户、数据目录、Schema、同步任务与文件索引；对象存储按租户/数据集/分区存 Parquet；DuckDB 读 Parquet 做分析。接入客户源库时——**MySQL 优先用 Binlog，PostgreSQL 优先用逻辑复制 / WAL**。
- **解决什么问题**：既要拿到真实数据，又不能把未知 SQL 的风险转嫁给客户生产库。所以分两种访问模式：`SNAPSHOT`（同步到租户隔离的轻量湖仓，可跨源 JOIN、可复现）与 `LIVE_READ`（只读副本 / 分析库，新鲜度高但依赖源端性能）。**这是 MySQL 模块里「CDC / 增量同步」的真实落地场景。**
- **踩过的坑**：① 多租户数据源方言差异（同一个查询在不同源上行为不同）；② 只读账号的权限边界——必须有只读事务、允许表清单、超时、扫描量、并发、行数和取消能力；客户只有生产主库时默认不开放复杂即席查询；③ **删除行没有 tombstone 就会静默漏数**，所以发布前必须校验行数、主键重复、字段类型、分区完整性、Schema 漂移、同步位点和新鲜度，关键校验失败就停在 `INVALID` / `STALE`，不得进入正式问数。
- **决策与取舍**：第一版只做**可恢复快照 + `updated_at` / 递增主键轮询**，不上完整 CDC。理由：CDC 要求源端开启 binlog/逻辑复制并承担权限与稳定性风险，而分析场景容忍分钟级新鲜度；用「快照 + 位点 + 校验」换来的生产隔离与可复现性更值。升级条件：出现真实的秒级新鲜度需求。
- **对应母题**：M7、M14、M15

### 5.3 RuleArena（规则竞技场 · PostgreSQL）

**锚点**：`projects/RuleArena/04-idempotency-and-recovery.md`（条件更新、Checkpoint、Worker 重启恢复）、`03-executable-world-and-oracle.md`（PG 事务、Sandbox 副本环境）

- **用在哪**：PostgreSQL 是所有权威状态的落点——AttackRun / StrategyStep / ActionReceipt / Ledger / BusinessEvent 在同一事务内提交；沙箱用**数据库副本**重放高风险操作组合。
- **解决什么问题**：Worker 随时可能崩、队列按「至少一次投递」设计，而退款 / 发券这类**有副作用**的动作绝不能执行两次。要回答的是：**请求结果未知时，怎么避免重复副作用、并让任务恢复到可判断状态。**
- **踩过的坑**：① 沙箱若直接在生产库上重放，长事务 + 锁等待 + 高风险组合会把生产拖下水 → 必须用副本；② 曾把 **ToolCallID 当成幂等键**——模型重新规划、Worker 重启、超时重发都会产生不同的 ToolCallID，业务幂等键必须基于业务身份构造（`run_id + action_type + target_id + 参数 + 规则版本 + 逻辑步骤`）。
- **决策与取舍**：用**条件更新（乐观并发）+ 唯一约束**，不用 `SELECT ... FOR UPDATE`：

  ```sql
  UPDATE orders
  SET refunded_amount = refunded_amount + :amount,
      version = version + 1
  WHERE id = :id
    AND version = :expected_version
    AND refunded_amount + :amount <= paid_amount;
  ```

  影响行数为 0 → 说明版本冲突或超额，读出权威 Snapshot 后返回冲突，**不盲目重试业务动作**。为什么优先条件更新而不是悲观锁：项目文档 `04 §15` 给的是**「MVP 优先业务唯一键 + 条件更新」**，`Q7` 给的是**「锁可以降低竞争，但不能成为资金正确性的唯一保证」**——**理由是权威性，不是「低频写」**；而且文档 `04 §12` 同时给了**「锁定订单行 **或** 乐观版本条件更新」**，所以别说成「完全不用锁」。正确性最终靠数据库唯一约束 `UNIQUE(run_id, action_type, idempotency_key)` 兜底，而不是靠内存锁或 Redis 锁。Checkpoint 只存 frontier / 预算 / 版本元组，**不存业务结论**——因为「动作」与「Checkpoint」之间永远存在崩溃窗口，不存在完美保存顺序。
- **对应母题**：M7、M10、M16、M17

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：真正的约束是磁盘 IO，不是比较速度：

  - 索引结构的设计目标 = 让定位一条记录所需的 IO 次数最少。
- 3. 逐个淘汰（统一指标：定位一行需要几次 IO）：
  - 所以哈希在 InnoDB 里只作为内部优化存在（自适应哈希索引，加速热点等值查询），不是用户可选的主索引类型。
  - 但这不等于"红黑树差"——它有个隐含前提：假设节点分散在不同页。把整棵树放进内存，红黑树就够了（Redis 的 ZSet 用跳表正是这个道理）。
  - ：范围查询本身只需要向右；但 ORDER BY ... DESC 这类反向扫描、以及部分优化器路径需要向左。双向的代价只是每个叶子多 6 字节，换来的是与扫描方向无关。
- 4. 量化验证（把结论算出来，而不是背下来）：

### M3 聚簇索引与回表

**判据**：（待补：母题卡缺「通过判据」）

- 2. 两种索引的叶子装什么：

### M6 一条 SQL 的执行链路

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：五层链路，每层一句话：
  - 这五层里只有一层在"做决定"——优化器。连接器和分析器是固定动作，执行器只是照计划执行，引擎层负责"怎么取"。所以"SQL 慢"的第一嫌疑人永远是"优化器做错了决定"。 而它做错的原因通常只有一个：估算不准（这条直接连到 母题-M7-慢查询与SQL优化手段）。
- 2. 查询缓存为什么被移除【推导】：
  - "查一次缓存白拿"的收益 < "每次更新都要清一堆缓存"的成本。 这就是它被移除的量化理由。

- 4. 怎么判断是"哪一层"慢：
  - EXPLAIN 的字段与三种慢源的对应关系（M7 展开）：
  - 怎么判断"优化器选错了"：看 key（实际用的索引）与 rows（估算扫描行数）——估算行数和实际差很远时，就是统计信息/选择性出了问题。
- 5. 边界与常见误解：
  - 读成一句话：先用 rows 估算 vs 实际 的差距判断"是不是优化器的问题"，再用三种慢源判断"是哪一类问题"——顺序不能反。

### M16 乐观锁与悲观锁

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：它们是对冲突概率的两种假设：
  - "哪个更好"这个问题本身就是错的——没有冲突概率，选型就是空谈。
  - 所以回答的第一句话永远是"冲突频率"，第二句才是机制。 这正是 9.9 那次缺的东西。
- 2. 悲观锁：先拿锁，再操作【事实】：
  - 实现上的一个坑：SELECT ... FOR UPDATE 在 RR 下会带出 next-key lock，锁范围可能比预期大（母题-M10-锁与死锁）——这正是"悲观锁代价"的具体体现。
- 3. 乐观锁：不加锁，提交时校验【事实】：
  - 核心是"期望值进 WHERE"：用 version、用状态、用时间戳都行，本质是 CAS 思想。version 字段的好处是自带 ABA 防护（下一节）。
- 4. ABA 问题：CAS 的固有缺陷【推导】：
  - CAS 只比较"值是否相等"，不比较"中间有没有变过"：
  - 什么时候有害、什么时候无害：
  - 解法：版本号 / 时间戳一起比——Java 里 AtomicStampedReference（带 stamp）；数据库里 version 字段本质就是"自带 ABA 防护的 CAS"。
- 5. 判据：两条成本曲线的交点（本题的落点）：
  - 为什么要画曲线而不是背结论——因为两种方案的成本函数形状完全不同：
  - 这就是"高冲突时乐观锁崩掉"的数学表达——它不是"慢一点"，是在 p→1 时成本发散。
  - 高冲突时乐观锁的总工作量是 N²，悲观锁是 N——差一个 N 倍。 10 个并发就差 10 倍，100 个并发差 100 倍。
- 6. 选了乐观锁，就必须把重试当成方案的一部分【推导】：

### M17 排行榜与防超卖

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：场景题的第一动作是澄清，不是给方案：
  - 9.9 那次丢分的一半在"没问够"——另一半才是技术。技术选型（MySQL vs Redis）反而是这张卡里最容易的部分。
  - 9.9 的澄清对照（复盘里的 ✅/❌ 清单）：问了排名依据、展示字段、规模；没问榜单范围、更新频率、历史榜、防作弊——把这张清单背下来，下次第一分钟就不会空白。
- 2. 排行榜选型：为什么必须是 Redis ZSet：
  - 这不是"Redis 快一点"，是数量级的差别——而且它随榜单长度增长：MySQL 是 O(N)，Redis 是 O(logN)。所以榜单越大，差距越大。
  - 这样做避免了两级排序（先按分数排、同分再按时间排）——一次比较就定出唯一顺序。
  - Redis 的 score 是 IEEE 754 双精度浮点，只有 2⁵³ 以内的整数能被精确表示。
- 3. 2000 万 DAU 下的工程问题（答到这层才像服务端）：
  - "只存 Top N"是内存控制的关键手段，量级上直接差 100 倍。
  - 这是把 O(logN) 的精确查询留给头部、用 O(1) 的近似服务长尾的取舍。 "花更少的代价满足绝大多数人的真实需求"是这类题的通用解法，值得单独背。
- 4. 游戏特性（乐元素面试官最想听的）：
  - "防作弊没提"是 9.9 那次被明确点名的缺口——游戏公司的场景题里这是必答项。
- 5. 防超卖三条路：
  - 为什么能防超卖：判断和写入在一条语句里原子完成——不存在"查到还剩 1，两个人都扣"的窗口。
  - 这和 母题-M16-乐观锁与悲观锁 的条件更新、母题-P18-乐观并发控制 是同一个原理：把判断下推到数据库的原子操作里，而不是在应用层先查后写。
  - 判据：强一致（钱）→ 数据库原子更新；高并发（秒杀、体力）→ Redis 前置 + DB 兜底。
- 6. 指标与降级【事实】：
  - "排行榜挂了不能影响游戏本体"是这一题的底线判断——依赖服务的可用性必须低于主链路，这条原则可以迁移到任何"附加功能"上。
- 7. 边界与常见误解：
  - 读成一句话：排行榜的答案是"把计算内建进数据结构"（ZSet 的排名是结构自带的，不是查出来的）；防超卖的答案是"把判断下推进原子操作"——两者是同一条原理的两个应用。
