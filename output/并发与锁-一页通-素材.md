**三条线的关系**：一是"要不要付这个代价"，二是"付了之后怎么付得少"，三是"把范围从一台机器扩到多台"。**顺序就是决策顺序**——先判断要不要，再决定多大，最后才考虑跨机。

**这三条线共享同一个前提**：**并发控制的目标不是"不出错"，而是"出错的方式可以接受"。** 乐观锁接受"重试"，CAS 接受"失败重来"，分布式锁接受"锁可能失效所以要再校验一次"——**每种方案都是在给"出错"定价，而不是消灭它**。

### 5.1 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**"用条件更新代替加锁"的活教材**——任务表用**窗口业务键 + 唯一约束 + 条件抢占 + 租约版本**来避免多个 Worker 抢同一个窗口（`02-aggregation-and-recovery.md`）。**这不是悲观锁，是"带期望版本的条件更新"**——正是 L1 说的乐观并发控制，只不过不用版本号字段，而用"租约版本"。
- 解决什么问题：**多个 Worker 同时扫到同一个缺口窗口时，只能有一个真的干活**。做法是把"抢"变成一条带条件的 UPDATE：`WHERE 状态 = 待处理 AND 租约版本 = 我看到的那个`——**改到 0 行就说明别人先拿到了，我退让**。**一个原子 UPDATE 就完成了加锁、判断和推进三件事**。
- 踩过的坑：**租约版本只挡住了本地数据库的旧写，撤不回旧 Worker 已经发出的外部调用**（`07-task-lifecycle-and-delivery.md`）——这正是 L3 的核心结论：**任何"锁"都保护不了已经离开进程的副作用**，那要靠幂等键与权威状态查询。
- 决策与取舍：**并发度是"受控"出来的**——受控并发 + 并发配额，而不是让所有任务自由抢。**"先限制并发，再考虑锁"这个顺序**就是本卡第 0 节的判据。

- 对应母题：【L1、L3】

### 5.2 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**并发配额代替锁**——按租户限制并发和队列、给查询设超时、扫描量、行数与取消能力（`07-权限安全与生产隔离.md`、`08-查询性能与成本控制.md`）。**这里根本没有"锁"，而是"限流 + 排队"**。
- 解决什么问题：**保护源库**。多个租户的查询同时打到只读副本上，靠**配额**把它们隔开，而不是靠锁——因为**这些请求之间没有共享状态要保护，只是争资源**。
- 踩过的坑：**"无依赖子查询可以并发，但写回顺序必须确定"**——同一个问题在 L2 里的形态是"**并发度可以放开，但要保序的地方必须显式串起来**"。
- 决策与取舍：**"争资源"和"争状态"要分开处理**——争资源用配额（限流），争状态才用锁或条件更新。**把这两件事混在一起是设计里常见的错**。

- 对应母题：【L2、L3】

### 5.3 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**"不用锁，用幂等"的主证据**——`04-idempotency-and-recovery.md` §9 明确：接受队列至少一次投递与 Worker 随时崩溃，靠**稳定幂等键 + 同一事务里的唯一约束**保证业务副作用只生效一次；`08-capacity-cost-and-facts.md` 给 Redis 只配 256~512MB，**队列与限流用 Redis，但权威状态在 PostgreSQL**。
- 解决什么问题：**多 Worker 并行跑规则审查时，同一个动作不会被两个 Worker 各执行一次**。做法不是"抢锁"，而是**"谁先写进唯一约束谁生效，另一个读到冲突就当自己已经做过"**。**这比分布式锁简单、也更强壮**——因为不依赖锁服务可用。
- 踩过的坑：**超时后不许换 key 重试**（不然幂等键失效）；**不能拿 ToolCallID 当幂等键**（它每次调用都变）。
- 决策与取舍：**"能幂等就不用锁"**。锁要引入一个额外的可用性依赖（锁服务），幂等只依赖自己的数据库——**这是 L3 最后一条追问的答案：能用幂等解决的，不要用锁。**

- 对应母题：【L1、L3】

### L3 分布式锁：三种实现、三大失效场景与 fencing token

**判据**：（待补：母题卡缺「通过判据」）

- 2. 三种实现：各自解决什么、代价是什么：
  - Redis 做锁的核心是一条原子命令：
  - 三个必须做对的地方：
