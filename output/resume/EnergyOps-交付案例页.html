交付案例 · Delivery Case

EnergyOps — 园区能耗智能运营平台 把质量参差的表计读数，变成一张能直接交给财务的月度结算单

这不是一个「加了大模型的能耗看板」。它是一个交付问题：客户手里已经有读数，但没有人能拿它出账；工程的目标不是把模型做聪明，是让行政和财务敢签字。

角色：数据链路 + Agent 操作模块（主导设计与实现） 范围：约 604 台智能水电表 周期：15 分钟 / 次 规模：日均约 5.8 万条读数 客户：园区行政 · 财务 · 设备运营
客户拿到的（交付起点）
既有采集平台的累计读数 —— 解决"设备有没有上报"，不解决"这张表能不能出账"
客户要的（最小价值单位）
一张带计算说明、规则版本与差异检查的月度结算单
交付形态
日常操作走办公协作平台里的对话入口；规则配置、结算复核、审计追溯保留 Web 界面
我负责 / 不对齐的部分
数据模型、工具拆分、Hook 链治理、安全分级由我主导；结算财务口径与财务团队对齐

01初始问题与缺失信息交付从"缺什么"开始，不是从"做什么"开始

进场时手上有的和没有的，必须分开列——因为客户以为他要的是功能，实际缺的是判断依据。

已经有的没有的（真正的缺口）
约 604 台智能水电表的持续上报 园区自己的数据治理层 —— 读数质量好不好，没人说得清
累计读数（设备"此刻的刻度"） 区间用量（业务真正要的"这个月用了多少"）
一批显式阈值规则 规则是否可信、改之前会命中多少 —— 没有准入环节，规则只能靠"试"
Excel 里的分摊算法（在财务手上） 可追溯的计算过程 —— 出了差异只能人工倒推
三个各有痛点的部门 统一口径 —— 页面一个数、导出一个数、财务又一个数
缺失信息里最关键的一条：没有人一开始就说得清「这个月的费用到底以哪个数为准」。这条不问清楚，后面所有自动化都是白做 —— 它后来变成了整个结算设计的事实源。

02发现阶段：我问了什么需求转译 —— 每句话都落成一条设计约束

这几句是交付工作的核心动作：客户不会用工程语言提需求，他只会讲他现在的麻烦。转译的工作是把它变成可验证的约束。

这个月的费用，以哪个数出账？
抄表底稿（行政确认过的）为准；自动采集的数只能用来核对。
→ 约束：自动采集不得生成正式账；它只产出一份「差异 / 缺失 / 疑似漏抄」清单。同一月份不允许出现两套结算数字。
缺数的那几天，你们平时怎么补？
不补。估算出来的用量财务不认。
→ 约束：缺失一律标为"不可判定"并进异常账，不进正式用量与费用；确实当月修不了的，走显式的结转说明路径并标注"待下期"，不得静默通过。
一天给你们几十条告警，你们会看吗？
不会，真问题反而被淹没。
→ 约束：把「数据偏离」和「打扰业务人员」拆成两层 ——异常候选 ≠ 业务告警，中间再加一层"为什么可疑"的判断。
出账这一步，谁签字才算数？
行政先确认说明版，财务再核验。
→ 约束：结算设三道质量门（事实源门 / 预演门 / 责任门），任一门失败都不能生成正式分发版 —— 这就是"共建验收标准"落到代码里的样子。
为什么不做一个独立的系统和 App？
行政和财务的一天本来就在文档和表格里；多一个登录就多一层不用的理由。
→ 约束：入口长在客户已有的工作流里。越简单的操作越收敛到对话，越需要精确控制的操作越保留界面。

03架构与关键取舍选了 A，意味着放弃了 B —— 每条都写清为什么不选 B

交付时选了放弃了什么，为什么不
分层数据模型 raw → interval → hourly → daily，配 7 类质量状态与可信白名单，只有可信区间能进聚合层 直接「本次读数 − 上次读数」。累计值会被重置、回退、换倍率、乱序补写打断 —— 那样做等于把数据错误直接翻译成虚假用量和费用。
缺失就标"不可判定"，不估算 行业做建筑能耗数据质量普遍走 VEE 流程，估算补缺是标准动作。我们反过来：补出来的数会进正式账单，而账单是要收钱的。
约 30 个业务工具收敛为 6 类能力包，按 R0 只读 / R1 可回滚 / R2 高风险写入分级，Before Tool Hook 在调用前校验参数、权限与确认状态 给模型一个数据库连接或一段自由 SQL。模型输出的参数始终是不可信输入，它不理解操作的真实代价 —— 对它来说"查一下"和"发布账单"只是两个工具名。
治理规则做成挂在 Hook 上的可插拔策略：业务只声明"哪个能力、什么风险级、要不要确认" 把权限规则写进 Prompt。Prompt 适合表达意图，不适合充当安全边界；而且新增一类治理规则就得改核心 Agent Loop，客户每加一条业务规则都要动运行框架。
长结果外置为 Artifact，只回传口径摘要 + 关键样例 + 句柄；读侧失败降级、写侧失败阻断 把读数明细和导出文件全塞进上下文。Token 容量会截断，模型可能基于不完整数据给出看似合理但错误的结论；成本还会随结果规模线性膨胀。
Agent 只做入口与编排，不做自主设备控制 让大模型直接控空调照明。2023–2026 年 66 篇同行评议研究的综述结论是没有一篇跑到可持续的生产部署，当前证据支持 LLM 停在语义层与工作流层。

Agent 入口横切在上面这条链上 —— Hook 链治理（Before / After Tool）与 R0 / R1 / R2 风险分级约束它只能选择已注册的能力，不能绕过后端权限，也不能直接改业务状态。
结算的事实源是行政确认过的当月抄表底稿；自动采集只在这条链上做交叉核对，输出差异清单，不充当另一套结算来源。

04集成与约束交付现场的真实条件，往往比技术选型更决定架构

  • 对接的是别人的平台，没有源码也没有写权限 —— 只能读。所以质量治理必须建在自己这一侧：原始读数不可覆盖，只允许追加修正版本，重算产生新的处理版本。
  • 凭据不落在 Agent 侧。Agent 不持有采集平台和数据库的真实凭据，由后端连接器管理，执行环境只拿到受限的业务能力。
  • Agent 宿主是客户已有的产品，入口形态不完全由我们决定。应对方式是把任务状态外置到系统：长耗时导出与结算任务在用户关掉页面后继续跑，回来能恢复进度 —— 不依赖宿主会话活着。
  • 结算口径不由工程单方面定义。财务是这道口径的最终裁判，工程负责把它变成可执行、可审计的检查项。这条是「与业务方共建验收标准」的具体含义。
  • 权限按角色收窄。维修 / 物业协作人员只能收工单、回传处理结果，不直接操作核心数据；设备、组织与结算数据按角色授权。
  • 明确写在纸上的"不做"：不替代采集平台的物理接入、不控设备、不做维修派工与排班 SLA、不替代财务记账开票、不做碳核算与 ISO 50001 认证。划清边界不是免责，是让客户知道该信哪部分。

06可复用组件下次交付能直接搬走的部分

治理层

Hook 链 + 风险分级策略层

Before / After Tool 两个切面挂可插拔策略，业务只声明「哪个能力、什么风险级、要不要确认」。换一个业务域，核心 Agent Loop 不用改。

数据层

7 类质量状态 + 可信白名单

任何「累计值 → 区间增量」的场景都适用（电表水表燃气表、里程、库存流水）。核心是把"不可判定"当成一个正常状态，而不是当成一个错误。

运营层

异常三层分离：基线 → 候选 → 通知

把"发现异常"和"打扰人"解耦。告警疲劳不是靠调阈值解决的，是靠把中间那层判断显式建出来解决的。

流程层

三道质量门：事实源 → 预演 → 责任

任何需要人工签字、且错了要担责的自动化流程都能套：先定谁签字，再定自动化到哪一步停。

07边界与技术反思还有什么是没做到的

最贵的一条经验：先定「谁签字」，再定自动化到什么程度。
三道质量门看起来是个技术设计，其实是从客户那句「估算出来的数财务不认」倒推出来的。自动化程度不只看技术能力，还要看这个动作离"产生真金白银的后果"有多远。越接近生产写入，就越要往可验证、可审计那边让一步。
  • 系统边界本身就是交付物的一部分。把"不做什么"写清楚（不派工、不排班、不算 SLA、不做碳核算），客户反而更敢用 —— 他知道了该信哪部分、以及不会被越权代劳。
  • Agent 只停在语义层和工作流层是刻意的选择，不是能力不足。它负责理解意图、组织证据、解释结果；用量、费用、状态迁移和高风险写入全部由确定性程序控制。核心原则一句话：能由代码确定性保证的，不交给模型自行决定。
  • 还没做到的（如实列出）：维修工单的回流信号已经在跑（行动指南是否被采纳、是否一次关单、建议与真实根因是否一致），但这些信号还没积累到能稳定支撑"哪类设备的指南写得不好"的结论；结算的结转说明路径还需要更多月份的实际案例来验证它够不够用。
  • 如果重做一次：会更早把「口径归属」这件事写进需求收集的第一轮 —— 它决定了事实源、决定了哪一层不能自动化、也决定了验收标准长什么样。技术选型反而是后面才需要拍板的。
