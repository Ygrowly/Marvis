## 2. 方向 ①：AI 应用 / Agent 工程（研发-工程序列）

### 2.1 岗位要什么（字节 2027 校招官方口径）

字节招聘官方对 2027 届「AI Agent 开发工程师」的解读是：**重点关注候选人对 Agent 运行机制和工程落地的理解，而不只是是否做过简单 Demo。部分团队会提前布置 Agent 相关作业。**

官方列出的职位要求要点：

- 熟悉 Agent 常见范式架构：**Plan & Execute、ReAct、Workflow**，并能结合模型原理做**稳定性、成本与效果优化**；
- 业务理解能力强，能**梳理业务边界并匹配最适合的 Agent 工作流范式**；
- 了解行业常见模型优缺点，并**了解如何系统科学地评测以帮助模型选型**；
- Golang / Python / TypeScript 优先；
- 模型原理（CNN / RNN / Transformer 结构、推理架构）与二次训练方法（SFT / LoRA-SFT / DPO）**列为"了解优先"**。

### 2.2 官方给出的三道面试真题与素材映射

| 官方真题 | 本人现成素材 |
|---|---|
| 用户定义了几百个 Skill，导致 Skill 召回准确率下降，你怎么解决？（考分层召回、上下文感知、召回路由、query 优化） | 数驭穹图**领域路由 + 混合检索**，Top-K Schema 召回 81%→95%；3 套 Domain Pack（65 指标 + 120 术语别名 + 表关联约束）——同构问题 |
| 结构化输出要求符合 JSON Schema，但约 10% 请求"解析失败/字段缺失"，如何把失败率降到 1% 以下？（考上下文、提示优化、二次模型校验、链路兜底） | LLM 与上下文簇 **C2 结构化输出**；EnergyOps 的工具契约与 Before/After Tool Hook 校验链 |
| Agent 运行中经常出现幻觉，如何排查？（考模型输出、上下文拼接、Skill 召回多环节） | LLM 与上下文簇 **C4 幻觉成因** + **C1 上下文组装与预算**；数驭穹图"SQL 能执行 ≠ 业务答案正确"的六阶段可归因链路 |

### 2.3 缺口与处理

**缺口**：模型训练层（Pre-Norm / Post-Norm、SFT 与 RL 的分工）——这是"大模型应用算法工程师"的考题，不是 Agent 岗的硬要求。字节在 Agent 岗 JD 里把 SFT / LoRA-SFT / DPO 写成"**了解优先**"。

**处理**：不补、不写。改为一句话取舍回答——"我三个项目都验证过同一件事：**在应用层可控的地方（契约、门禁、评测）把不确定性收掉，比在模型层追效果更划算**"。这是真实的，也是他 19–21 分项目表达能撑住的。

### 4.3 这个方向到底要什么（合并五份 JD 的公共要求）

1. **评测集与基准构建**：评测集的**生产、接入、管理、版本化**；样本分层与标注流程的质量控制；benchmark 覆盖**多轮交互与长短上下文**；防数据污染
2. **评测指标体系设计**：把"非确定性"量化——幻觉率、指令遵循度、输出稳定性、任务成功率、工具调用正确性、成对对比、评分量表、分级指标体系
3. **自动化评测基建**：**LLM-as-a-Judge**（含交叉验证、偏差检测、校准）、规则校验、pytest 批量回归、**CI/CD 质量门禁**、评测平台（"推动评测工程化与无人化"）
4. **可观测与缺陷定界**：Trace 全链路、从生成日志与链路追踪快速定位根因、**区分"工程 bug"与"模型效果缺陷"**、Bad Case 库
5. **Agentic 专项**：工具调用正确性（对的工具 / 对的参数 / 对的时机）、**动作安全**（权限校验、受限操作被阻断）、**恢复行为**（工具报错或超时后不空转、不编造结果）
6. **工程能力**：精通 Python + pytest；熟悉至少 **2 种主流评测框架**（RAGAS / DeepEval / TruLens / promptfoo / AgentBench）；了解学术 Benchmark（SWE-bench / WebArena / GAIA / ToolBench）
7. **统计学**：实验设计、置信区间、显著性检验、评分者一致性（rater reliability）、**离线评测指标与线上业务指标对齐**
8. **门槛与软要求**：学历看序列（见 4.1）；重视逻辑思维、缺陷定界、跨团队推动问题闭环；**"能把模糊业务需求转化为清晰、可量化、可执行的评测方案"**

### 6.2 四个方向的语言体系（写之前先答这句话）

### 7.2 维护红线（事实不变、表达自由）

1. **只改母版** `刘宇广-AI应用开发-2027届.html`，改完跑 `python make_variants.py`（重新派生 3 个变体）→ `python check_layout.py --all --export`（重导 + 双尺校验）。
   **直接改变体没有意义**——下次派生会覆盖它。这就是「编辑入口恒为 1」这条红线的执行方式
2. **数字只能出自 `刘宇广-简历量化指标口径.md`**，四个版本必须完全一致。`make_variants.py` 会断言四份的数字集合与母版逐项相同，改到事实就当场报错
3. **事实层与表达层分开管**
   - **事实层不可变**：数字、口径、可验证主张，四个方向必须一致，且**只在母版里改**
   - **表达层自由**：可以改措辞与动词、换强调面、改 bullet 的详略与取舍（**允许裁剪、允许新增技能行**）、改技能行标签与顺序
   - **为什么推翻旧规则**：初版写的是「不允许某版有某版没有的 bullet、四份 bullet 文本必须完全相同」。那条规则把"不许分叉事实"错误地实现成了"不许改写法"，而真实风险从来不是措辞不同，是**数字和主张对不上**。不同岗位看的东西不同，同一件事本来就该有不同的讲法

   四条断言（`make_variants.py` 里执行，违反直接报错、不写出文件）：
   - a. 变体里出现的每个数字都必须在母版里出现过——**不许凭空造数**
   - b. 每条改写后的 bullet，其数字必须是**它所改自的那一条**的子集——**不许跨条搬运数字**（最隐蔽的一类编造）
   - c. 母版是变体的数字超集：**裁剪允许，编造不允许**
   - d. 每个方向必须保留自己那几条**核心事实锚点**（② 的「¥1920 / Delta Debugging」、③ 的「pass^3 = 1/14 / Release Gate / 双评测集」、④ 的「P95 20.4s→2.8s / 口径一票否决」）——**防裁剪过头把该方向的头号证据裁掉**
4. **每份导出后必须过 `check_layout.py` 的两道尺子**（底部余量 + 文本完整性）。魔方模板的 `.page{overflow:hidden}` 会静默裁掉溢出内容，页面看起来完全正常——见 7.6
5. **不建模板引擎 / 生成器。** `make_variants.py` 不是生成器：它的全部输入是母版既有的 16 条 bullet 与 3 行技能，产出是这些既有事实的重新组织（改讲法、换顺序、裁剪），**不产生任何新事实**；价值在于**把「不许编造」这条红线变成可执行的断言**。真正的红线是「别用搭工具替代投递」，不是「不许有脚本」

### 7.5 一个必须记住的工程坑（2026-09-20）

给 JS 数组**追加**元素时，若原数组最后一行没有尾逗号，直接在末尾插新行会写出：

```js
['D','Grab'],           ← 正常
['D','Grab']            ← 没有逗号
/* 注释 */
['A','字节跳动',...],   ← 新追加
```

JS 会把 `['D','Grab'][...]['A',...]` 解析成**成员访问**（计算属性里用逗号运算符）——**语法完全合法、`node --check` 全绿**，但整个数组少一条真实元素、多出一个 `undefined` 元素，页面打开就是白屏。此类错误只有真执行才暴露，所以台账的校验必须是 `output/check_ledger.js` 而不是 `--check`。

### 7.6 另一类坑：版面静默裁切（2026-09-20 发现并修复）

**母版从 2026-09-15 起就少了一整行内容，而所有既有检查都显示正常。**

- **现象**：`刘宇广-AI应用开发-2027届.pdf` 的第 3 行技能（`工程交付与 AI Coding：Git、pytest、CI/CD、Docker Compose、Nginx；分层评测体系、归一化预算消融、Bad Case 回归集；Claude Code / Codex 重度使用…；CET-6，能流畅阅读英文技术文档`）**完全没进 PDF**，整整 2 行、150 字。
- **原因**：`.page { height: 297mm; overflow: hidden }`。内容比页面高 20.3pt，被直接裁掉——**页面看起来完全正常**。
- **为什么没被发现**：`check_layout.py` 当时只量「末行底部到页底的余量」，报的是「✓ 未溢出（余量 +2.3pt）」。**被裁的字不在 PDF 文本层里，余量尺子原理上量不到它**——这是一条假绿灯。
- **影响面**：这份 PDF 是 2026-09-15 → 09-20 之间的投递正本。丢掉的内容里有 **CET-6**，而它恰是五大行 / 央国企网申的硬性指标项；另有 `Git / pytest / CI/CD / Docker Compose / Nginx` 与 `分层评测体系 / Bad Case 回归集`（③ 方向刚统计出的高重合素材）。
- **修复**：按《简历版面规划》§2 压缩顺序的第 ② 条（收紧段间距与列表间距，单处 0.4–0.6pt，**不碰字号与行高**）累计回收 ≈35pt → 四份成品余量一律 **+9.0pt**。同时给 `check_layout.py` 补上第 2 道尺子，并在已知有问题的母版上验证过它确实能抓出那 150 个字（1 处、零假阳性）。
- **教训**：**「底部还有余量」不等于「内容都在」。** 这两件事必须分别证明。同理，任何「固定高度 + overflow:hidden」的成品（简历、一页纸作战卡、PPT 模板）都适用这条。

**附：142pt 是测量值，不是规定值**（按本库「数字的性质」纪律标注）

- **含义**：岗位名行（`.hd .id .role`）的可用宽度 = 联系方式网格首个图标起点 228.3pt − 岗位行起点 86.3pt = **142pt**（`.hd .id` 固定 160pt、左内边距 18pt，13.5pt 字号 `nowrap`，超出的字会压到联系方式上）

## 9. 2026-09-28 决策记录（三条，主人确认后落地）

### 9.1 BOSS 在线简历改「融合版」

**决策**：在线简历的自我评价从「①方向纯净版」改成**融合版**，四方向的 HR 看了都不扣分。

**判据是三个渠道的分工**：

| 渠道 | 可见范围 | 职责 |
|---|---|---|
| 在线简历 | **全员可见**（HR 沟通前第一关，参与 ES 关键词匹配） | 被搜到 + 不扣分 |
| 打招呼语 | 单会话可见 | 方向精准（已备四段） |
| 附件 PDF | 沟通后可见 | 按 JD 发对应方向（已备四份） |

在线简历是唯一全员可见的东西，它需要的是**兼容**不是锋利。融合的办法是把四个方向都认的那一层提到最前：**可验证 · 可回滚 · 可评测**——评测岗看到验证、交付岗看到回滚与交付、后端岗看到可评测的工程底盘、①方向全收。`MCP / Capability Bundle / Hook` 这类黑话全部撤（HR 看不懂，技术面能从实习描述里找到）。**期望职位仍只填 ①**，平台字段填多个会被降权，这条不变。

> **融合 ≠ 四段各抄一句拼盘**。拼盘的结果是每个方向的 HR 都觉得不对口。

### 9.2 AI 全栈 / 全栈工程师：可以投，不单开第五方向
