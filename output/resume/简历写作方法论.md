# 简历写作方法论（唯一正本）

> 本文回答两个问题：**简历到底应该怎么写、写什么是合适的。** 不受页数、渠道、版面限制——一页附件版、BOSS 在线版、网申版只是同一套内容在不同约束下的投影（版面与渠道规则见同目录 `简历版面规划.md`）。
> 收编来源：简历焚诀（雾行）· MIT/Harvard 指南 · contrib-skill 证据链 · ASu-skills 酥化公式与主张—证据账本 · wiki/thinking/简历写法.md（原始讨论）· 阿酥两轮复盘（2026-09-09 四问点评 + 2026-09-10 七条改写法则）。
> 配套文件（同目录）：`刘宇广-Agent开发工程师-2027届.pdf`（正本）、`刘宇广-BOSS直聘在线简历.md`、`刘宇广-简历量化指标口径.md`、`简历版面规划.md`。面试侧追问链在 `wiki/interview/简历逐句作战地图.md`。

## 0. 第一性原理：简历的功能是生成面试，不是记录历史

1. **简历不是你的历史档案，是你埋给面试官的问题清单。** HR 用 10 秒扫描决定是否细读，细读后决定问什么。你写下的每一句，都在划定面试的范围——写什么，就被问什么。所以简历的最高策略是：**把面试引向你真正擅长、真正做过的方向。**
2. **核心检验句（每条内容都要过一遍）：**

> 「面试官顺着这句话问为什么、怎么实现、怎么验证，我能不能拿出一个真实例子？」

能，就值得保留；只能继续抛术语，就改写或删除。**不要复制别人的资历密度，要复制他留下技术追问入口的方式。**

3. **三条事实底线（所有规则的前提）：**
   - 没做过的，不写；
   - 做过但没测量的，写「设计目标 / 已实现」，不写数字；
   - 测量过的，带口径写（见 §4）。
   - 最差的做法不是没有数字，而是没有数据却补一个「效率提升 40%」。

## 1. 写什么：内容分层与四句话骨架

### 1.1 简历的原子单位 = 主张 + 证据

- 每条内容都是一个主张，每个主张必须有证据支撑。主张先定档再动笔（责任分级四档）：**参与 < 负责模块 < 主导方案或交付 < 项目负责人（/独立项目）**。
- 「主导」只有能讲清决策、交付和结果时才允许用；「独立设计实现」只绑定确实独立的部分。
- **项目全貌 ≠ 个人贡献**：全貌负责说明为什么做、为谁做、系统做到哪里；个人贡献负责说明你遇到什么问题、做了什么决策、如何实现、结果如何验证。团队项目（课程、实验室、比赛）尤其不能整段只写「我们实现了」——面试官需要知道**你拿走哪一块**。

### 1.2 项目贡献的「设计范围 / 实现范围」分离

- 「负责方案设计」和「亲自实现某模块」是两件事，分开写：

> 负责执行框架升级方案设计，并独立实现其中的并发控制与取消模块。

- 项目影响力（star 数、名企背书）只能作背景，**不能代替个人贡献**。「参与知名开源项目，主导架构升级」是无效句——主导的边界是什么？挑一个关键改动讲清旧问题、备选方案、最终选择、自己写的部分、上线后发生了什么，能讲出失败案例和取舍，比复述架构图更能证明参与深度。

### 1.3 每个核心项目先写成四句话

写 bullet 之前，先把项目压成四句话（压不出来说明还没想清）：

| 层 | 回答什么 | 反面 |
|---|---|---|
| 项目背景 | 给谁用，解决什么问题 | 产品说明书式罗列 |
| 个人职责 | 你负责哪一块 | 「我们」实现了什么 |
| 关键设计 | 你解决过的最重要技术难点，**以及为什么这样选** | 五个只解释定义的名词 |
| 验证结果 | 如何证明这个实现有效 | 把「设计上支持」写成「已经验证」 |

### 1.4 结构组织：问题先行，能力主题串联

**先交代项目解决什么问题，再用能力主题串起具体实现和结果**——不是把技术、实现、问题、成果分开罗列成四堆。读者路径永远是：这是什么问题 → 你怎么设计 → 结果如何证明。技术名词只在这条路径上出现，不单独成列。

### 1.5 项目名不大众化

EnergyOps / 数驭穹图 / RuleArena 这类有辨识度的名字直接用，不退化成「xx 管理系统」——名字本身就是追问入口。

## 2. 七条改写法则：从「看起来厉害」到「经得起追问」

### 法则一：把「做了哪些功能」改成「解决了什么问题」

- 弱：`开发多 Agent 平台，支持任务拆解、并行执行、沙箱管理和结果汇总。`（产品说明，换一个参与者也能写）
- 强：`针对长任务执行中主 Agent 上下文膨胀的问题，将子任务放入独立上下文执行，仅回传结果摘要与产物位置，并保留完整执行记录用于失败排查。`
- 判断标准：改写后留下了明确的**面试入口**（怎么拆任务？摘要遗漏信息怎么办？什么时候读完整记录？）。学别人的机制细节不是照抄机制，而是把「为什么做」补到「做了什么」前面。

### 法则二：把「整个项目很厉害」改成「我的贡献在哪里」

见 §1.2。补充：写「主导/owner」等于邀请面试官按负责人的标准追问全部细节——身份撑不住时，简历写得越满，落差越大。

### 法则三：把「用了复杂技术」改成「做过一个有理由的取舍」

- 弱：`采用 DAG、Redis、消息队列和多 Agent 调度架构。`
- 强：`将模型生成的任务计划转换为 DAG，由程序校验依赖并调度执行，避免直接按模型输出启动存在依赖冲突的任务。`
- 一个能讲透的设计 > 五个只能解释定义的名词。**别为了写简历硬加技术**：简单队列够用，就把「为什么够用」讲清楚——这本身就是取舍能力的证明。

### 法则四：没有提升百分比，也能写出结果

- 有真实测量，用句式：`在固定【模型/预算/基线】下，使用【实际任务数】个任务对比改造前后表现，【指标】由【实际值】提升至【实际值】。`
- 没有可靠对比实验，写**验证过的能力**：`补充超时、重复回报与进程重启等异常场景测试，验证任务状态恢复与重复结果拦截。`（前提是确实测过）
- 结果不一定是增长百分比，**一个明确通过验收的能力就是结果**。
- 量化四类（无业务百分比时的替代）：业务结果（省时/降本/减人工）、系统规模（设备/数据/接口/规则数）、质量结果（通过率/覆盖率/一致性）、交付范围（模块/数据源/流程数）。

### 法则五：指标先检查分母，避免主动挖坑

- 不同统计窗口、不同用户集合的数据**不要挤在一起**让面试官自己猜（典型坑：累计注册 2000+、付费 200+、转化率 38% 三个数并列）。只确认累计就只写累计；转化率是试用口径就写明「在【时间段】内，试用用户付费转化率约 38%」。
- 性能/提效指标同理：「耗时下降」必须说清是模型生成、接口响应，还是包含人工修改的完整交付时间；提效对比要说清是初稿还是最终验收、失败任务算不算。

### 法则六：技术用词准确，别把自己写进不会的方向

- 「注入上下文」≠「微调」≠「训练」。只是把 Schema/DSL 放进上下文，就写注入；只有真正更新过模型参数，才写训练/微调，并准备解释数据、方法与评估。
- 措辞的每个高级词都会改变面试官的追问方向。**用词不是越高级越好，而是把面试引向你真正擅长的方向。**

### 法则七：一个项目不要写成技术汇报

- 逐项罗列机制链路（11 层 Middleware 全展开、多条执行链路逐项列）会让重点被稀释，读不出「最难最独特的三个贡献」。
- 每条 bullet ≤2 行；一段经历保留 2~5 条最高价值贡献；每条都有机制名 + 数字/验收结果。
- 技术细节的密度要服务于「追问入口」，不是服务于「看起来很努力」。

## 3. Bullet 公式库（按场景选用）

| 公式 | 结构 | 适用 |
|---|---|---|
| STAR | 背景（可省）→ 动作 → 结果（必有数字或验收能力） | 通用底座 |
| 酥化公式 | 动作 → 系统能力 → 业务价值 → 结果证据 → 个人边界 | 实习经历主公式 |
| 阿酥句式 | 针对【问题】→【机制/设计】→【保留/验证/边界】 | 有明确工程问题的条目 |
| 问题驱动命名 | 「A ≠ B」防混淆句式（如「SQL 能执行 ≠ 业务答案正确」） | 体现设计判断力的条目 |
| 能力主题串联 | 问题一句 → 能力主题 → 具体实现 + 结果 | 项目简介与整段结构（§1.4） |

硬约束：一条 ≤2 行；机制名加粗；每条至少一个数字或一个明确验收能力；每段经历里加粗的词互相不重复。

## 4. 数字与口径规则

1. **口径五要素**：分母、样本集、基线（是否同模型/预算/重试次数）、时间窗口、含不含失败轮次。**能说清三个以上才把数字写上简历；说不清就只写机制。**
2. 相对提升（↓30%）和绝对百分点（78%→91%）是两回事，写清是哪种。
3. 数字是宣言：写上去 = 同意被按这个数字追问基线与统计方式。每个数字都要能在口径文档里说出「怎么算的」。
4. 性能指标必须可复现：固定查询集/固定回放集/两个等长窗口——口径在简历上至少留半句（如「72 条任务评测集」「固定查询集」）。
5. 别人的数字口径（大厂平台基准、开源榜单）不能外推成自己的成果。

## 5. 追问入口设计（把简历当成面试的先手棋）

1. 每条 bullet 主动埋**一个钩子**：面试官愿意往下问的工程线索（一个反直觉的分离、一个有代价的取舍、一个确定性保证）。有钩子的简历让人想问，没钩子的简历只能让人扫过。
2. **钩子必须有追问链答案**：埋钩子之前先确认「为什么这样设计 → 备选方案是什么 → 失败案例是什么」三层能答。写不出答案的钩子不要埋——那不是入口，是陷阱。
3. 主动暴露局限拿回叙事权：先说缺点的人掌握叙事权。在关键贡献上准备一句「这个方案的局限是 X，当时我们用 Y 缓解」，比被问穿体面得多。
4. 经历之间要有**连续性叙事**：从项目 A 到 B 到 C 是一条演进主线（如「数据可信 → 执行可控 → 结果可证」），比一堆互不相关的项目更能形成「持续深入」的印象。这条主线不因微调 JD 关键词而打乱。

## 6. 各模块正误对照

| 模块 | 写 | 不写 |
|---|---|---|
| 个人信息 | 姓名、电话、邮箱、求职岗位；GitHub 有有效内容再放 | 籍贯、政治面貌、冗长自我介绍、空链接 |
| 求职意向 | 每份简历一个方向 | 「后端/算法/产品均可」（系统匹配降权） |
| 教育 | 学校、专业、学历、时间；排名/课程仅在拿得出手时写 | 普通课程罗列、无关证书 |
| 技能 | 分类组织、核心前置、**每个词都能在经历中找到对应项目**；不自我评级 | 「精通/熟练」、进度条、名词堆砌、与项目重复占行 |
| 实习 | 一句项目定位 + role-note（责任档位）+ 2~5 条高价值贡献 | 职责流水账、重复介绍整个产品、全用「参与」 |
| 项目 | 四句话骨架（§1.3）+ bullet | 课程作业式功能列表、把团队成果写成个人成果 |
| 奖项 | 相关、认可度高、能说明结果 | 低价值奖项堆数量 |
| 自我评价 | 每句带证据；责任档位逐句核对，不合并拔高 | 「学习能力强」「认真负责」；两段经历合并成一句超出最低档位的表述 |

## 7. 写作流程与审计

1. **素材层**：逐项目确认「业务背景—产品定位—用户流程—系统边界」+ 个人贡献与证据卡。每个项目逐项确认八件事：①入场时项目什么状态；②团队人数和职责边界；③亲自解决的三个关键问题；④做过哪些方案选择和取舍；⑤关键机制如何运行；⑥最终形成什么结果；⑦有哪些可验证材料；⑧哪些是推测或记不清。
2. **选条层**：按岗位相关性、个人主导度、技术深度、可验证性、项目互补性评分，每项目选 2~3 条最强贡献。
3. **成稿层**：按 §3 公式写 bullet，按 §1.3 四句话定骨架。
4. **审计层**（缺一不可）：
   - 真实性：逐条过主张—证据账本（状态机：已确认 / 待确认 / 已过期 / 不采用）；
   - 追问模拟：每条过核心检验句 + 三层追问（为什么 → 怎么实现 → 怎么验证）；
   - 口径审计：每个数字过口径五要素；
   - 扫描测试：10 秒内能否抓到「最难最独特的三个贡献」；
   - JD 匹配：按投递岗位替换关键词顺序（不改变事实与主线）；
   - ATS：单栏、标准标题、可选中文本 PDF。
5. **版本纪律**：母版素材库（全量事实）→ 投递版（按渠道投影）。投递版每一条都必须能追溯到母版证据，不因版面压力现场编造。

## 8. 证据链（没有代码仓库时怎么建立）

公司项目不上传源代码、内部文档或敏感数据。替代证据按可信度排序：

- 脱敏后的产品截图、架构图、接口文档；测试结果、黄金对账、导出文件；
- 数据规模、规则数量、工具数量、用例数量；部署记录、告警日志、压测报告；
- 需求文档、问题复盘、技术方案；
- **你能稳定回答「为什么这样设计」的完整决策过程**（最终兜底，也是面试主战场）。

「业务背景—产品定位—用户流程—系统边界」只能支撑项目简介，不能直接证明个人贡献和个人技术实现。可以在个人网站做脱敏案例页：背景 + 流程图 + 系统边界 + 个人贡献 + 验证结果 + 技术反思。作品集不是必须展示代码，是展示问题解决能力。

## 9. 样本偷招（学别人的简历学什么）

| 样本 | 偷什么 |
|---|---|
| 牛肉哥（Z.ai 算法实习） | ①经历标题行右侧直接放最硬指标，HR 3 秒看到结果；②bullet=加粗机制名+一句机制+量化增量；③整页无「负责」开头虚句 |
| go-王文杰 | 显式「难点&解决」：难点→方案→效果；教育前置 |
| OnCall Agent 写法 3 | 项目亮点=问题驱动：「问题导致 XX 失败。设计方案，指标降低 60%」 |
| AgentHub-奶龙 | 个人项目 bullet=加粗组件名+实现细节（组件细节是深度证明） |
| 林芮瑭（多模态算法） | **该学的**：工程线索（系统怎么跑的运行描述）、问题—设计—实现—结果结构、经历连续性、留追问入口。**不该学的**：高密度堆术语（11 层 Middleware 全展开）、每项都写 owner、口径不明的业务数据（累计用户与转化率分母不一致、「喂入 Schema 完成模型训练」歧义表述） |

原则：不复制别人的资历密度，只复制他留下技术追问入口的方式。

## 10. 反面清单（出现即改）

- 堆砌不聚焦、空洞不量化（「显著提升」「极大提高」）；
- 无数据却补编造的百分比；把「设计上支持」写成「已经验证」；把计划写成已完成；
- AI 味（「赋能」「抓手」「闭环思维」）与整齐划一的排比句式；
- 「精通」「熟练」自我评级；把 AI 生成代码比例当工程成果（值得写的是如何用 Spec、测试、评审控制 AI 交付质量）；
- 项目影响力（star/名企）当个人能力；团队成果写成个人成果；
- 不同口径的数据挤在同一行；高级术语把自己写进不会的方向；
- 为了量化而量化——**有效结果比数字形式重要**，一个明确通过验收的能力就是结果。

## 11. 一句话总检

> 写完每一条，问：**「面试官顺着这句话问为什么、怎么实现、怎么验证，我能不能拿出一个真实例子？」** 能——且这个方向正是你想被问的——就保留；不能，就改写或删除。

## 附录 A：阿酥四问 × 本简历对照（2026-09-09/10 审计记录）

> 样本：林芮瑭简历（DeerFlow 2.0、多模型接力、轨迹评估）。核心判断：「容易获得关注，也容易被深挖」——经历和技术细节给面试，个人贡献边界 + 指标口径决定能不能活着走出追问。
