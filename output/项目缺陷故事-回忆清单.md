# 项目缺陷故事回忆清单

> **用途**：补齐两份项目说明里空着的「执行中打出来的真实缺陷」一节（`projects/EnergyOps/EnergyOps-项目说明.md` §0.6、`projects/数驭穹图/数驭穹图项目说明.md` §0.6）。
> **为什么值得花时间**：模板里这一节标着「比上面的数字值钱」——因为**数字证明你做过，缺陷故事证明你想过**。RuleArena 那四个缺陷现在是那条主线最有力的部分。
>
> **规则**：**只写你真实经历过的**。想不起来的就写「无」——**空着比编造安全**。编造的细节经不起追问，而且会连累那组真数字的可信度。

---

## 怎么用这份清单

下面的每一条，都是**从你自己写的手册里反推出来的**——如果你当初专门设计了某个防御机制，通常是因为**撞过对应的事**，或者见过别人撞过。对着条目回忆：

1. 碰到过 → 写下来（现象 / 怎么发现 / 为什么漏掉 / 怎么修 / 补了什么）
2. 没碰到过 → 写「无」，或者写「没碰到，但设计时就是防它」
3. 想起来一半 → 先写下确定的部分，不确定的标「待确认」

## EnergyOps

### 候选 1 · 幂等与回补
**你的手册里写着**：「如果 Hourly 已更新但任务状态没有更新，恢复时可能重复执行；如果 Daily 已更新而 Hourly 事务回滚，则上下游版本不一致。」（`02-aggregation-and-recovery.md`）

→ 回忆方向：
- 有没有过一次**服务重启/补数之后数字不对**？
- 有没有发现过**同一窗口跑了两遍**，或者反过来说好的窗口没跑？
- 当时是怎么发现的——对账？用户说数字不对？还是自己盯任务状态？

### 候选 2 · 外部副作用不可回滚
**你的手册里写着**：「外部短信无法被数据库事务回滚，所以超时必须进入 result_unknown，并依赖外部幂等或状态查询。」（`04-anomaly-alarm-incident.md`）

→ 回忆方向：
- 有没有过一次**通知发重了**，或者**该发的没发出去**？
- 有没有一次告警推送失败，导致**真问题被漏掉**？

### 候选 3 · 告警误报/漏报
**你的手册里写着告警三层分离 + 指纹去重 + dry-run 准入**，告警量降了 43%。

→ 回忆方向：
- 改造**之前**那几十条告警里，有没有特别典型的**误报**案例？后来发现根因是什么？
- 有没有反过来——**去重/静默之后漏掉了真问题**？如果有，后来怎么补救的？

### 候选 4 · 性能优化改坏了语义
**你做了查询重构，P95 从 20.4s 降到 2.8s。**

→ 回忆方向：
- 优化过程中有没有出现过**快了但算错了**？（这正是你自己在 `08` 手册里写的风险：性能优化最容易悄悄改语义）
- 有没有哪次改动被**回归测试或对账**拦下来过？

### 候选 5 · 数据质量判定出错
**你定义了 7 类质量状态 + 可信白名单。**

→ 回忆方向：
- 有没有过**白名单误杀**好数据、或者**漏放**坏数据的情况？
- 有没有某类跳变被误判，后来发现是设备侧的合理变化？

## 数驭穹图

### 候选 1 · 权限
**你的手册里强调**：权限在所有边界持续生效、`tenant_id` 服务端注入、权限过滤下推到检索层，还有「防住注入 ≠ 安全」。

→ 回忆方向：
- 有没有一次**权限相关的漏洞**被自己测出来？（比如副本、快照、看板这些衍生路径上权限没跟着走）
- 权限撤销之后，旧资产还在用旧权限——有没有碰到过？

### 候选 2 · 口径歧义
**你的核心命题就是「SQL 能执行 ≠ 业务答案正确」。**

→ 回忆方向：
- 有没有一次**SQL 跑对了但答案是错的**？具体是哪个指标？（这正是你整个产品的起点——如果真发生过，这就是最好的故事）
- 有没有客户/业务方说「这个数不对」，查下来发现是**两边口径不一致**？

### 候选 3 · 证据绑定
**你要求图表必须绑定 call_id + query_fingerprint + result_hash，否则降级。**

→ 回忆方向：
- 有没有一次**图表显示的数和查询结果对不上**？（比如模型在解释里补写了一个数）
- 有没有一次结果被模型「润色」过，导致和真实查询有偏差？

### 候选 4 · 上下文与 Token
**你把 Token 从 18.4K 压到 3.6K，靠的是大结果外置 + 只回传摘要。**

→ 回忆方向：
- 压缩上下文之后，有没有出现模型**因为看不到明细而答错**的情况？
- 有没有一次大结果把上下文撑爆，导致回答被截断或漏掉关键信息？

### 候选 5 · 六阶段归因
**你把链路拆成六阶段，就是为了让错误可归因。**

→ 回忆方向：
- Bad Case 定位从 30 分钟降到 8 分钟——**改造前那个 30 分钟**是什么样的？有没有一个具体案例让你下决心拆链路？
- 有没有一次失败**跨了两个阶段**，当时怎么判断主要责任在哪一环？

## 写完之后的下一步

填好的内容需要合并回两份项目说明的 §0.6。合并时注意：

1. **一条故事 200–400 字**，控制在一屏内；
2. **五要素齐全**（现象 / 怎么发现 / 为什么漏掉 / 怎么修 / 补了什么防复发）——其中**「为什么漏掉」最关键**，它证明你真的复盘过；
3. **不要写成「加强了检查」这种空话**——写具体改在哪一层；
4. 填完告诉我，我帮你合并进正本，并同步到面试话术与量化口径。
