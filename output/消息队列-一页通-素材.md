**三条线的关系**：一是"别丢"，二是"别重复、别乱序"，三是"容量和可用性不够时怎么办"。**顺序就是排查顺序**——线上出问题先问丢了没，再问重复没，最后问扛不住了吗。

**这三条线共享同一个前提**（第 1 节会量化它）：**跨进程通信没有"恰好一次"这回事**。所以 MQ 的全部设计都是"用至少一次 + 幂等去逼近恰好一次"，而不是真的实现恰好一次。

### 5.1 EnergyOps（金山园区能耗）

- **锚点**：`projects/EnergyOps/`
- 用在哪：**这是"什么时候不该上 MQ"的活教材。** 当前规模（约 604 台设备）用的是 **PostgreSQL 任务表 + APScheduler + 批处理 + 受控并发**，项目里**明确决定不引入消息队列与流处理**，并写下了升级条件（表计到万级 / 分钟写入持续高峰 / 补数大量堆积 / 单机无法在窗口内完成）。长耗时导出、规则回放与结算才走队列 + 并发配额限流（[[母题-Q1-消息为什么会丢怎么才不丢]] 的前提节）。
- 解决什么问题：**通知这类外部副作用不能进数据库事务**——短信发出去了没法回滚。所以 Alarm 与 Notification Outbox 在**同一个本地事务**里落库，通知 Worker 再拿业务幂等键去调外部平台；调用超时标记 `result_unknown`，**不直接重试，先查外部权威状态**或用同一幂等键重试。这就是"本地消息表 / Outbox"这条路线在没有 MQ 时的真实形态。
- 踩过的坑：**① 超时被当成失败**——超时表示结果未知，直接重试会重复发短信；**② 租约版本只防住了本地数据库的旧写，撤不回旧 Worker 已经发出的外部调用**——所以外部调用必须用稳定幂等键 + 恢复前先查权威状态；**③ Checkpoint 被当成"业务完成证明"**——它只是恢复线索（[[母题-A4-长任务状态与Checkpoint]]）。
- 决策与取舍：**先用数据库任务表换掉 MQ，等升级条件出现再说**。这笔账划得来是因为：当前吞吐离 MQ 的收益门槛还远，而引入 MQ 的**三笔代价（可用性、复杂度、一致性）立刻要付**。**"不上 MQ"不是保守，是算了账**（[[母题-Q1-消息为什么会丢怎么才不丢]]）。

- 对应母题：【Q1、Q2】

### 5.2 数驭穹图（企业问数）

- **锚点**：`projects/数驭穹图/`
- 用在哪：**队列在这里只承担"限流与排队"一个职责**——按租户限制并发和队列、给查询设超时/扫描量/行数配额，超预算时**拒绝、缩小范围或转异步**（`08-查询性能与成本控制.md`）。不承担解耦，也不承担削峰。
- 解决什么问题：**保护源库不被慢 SQL 打穿**。SQL 执行是不确定的（数据倾斜、统计信息过期都会让它变慢），所以必须有硬超时、取消和租户配额——**这是"队列最小的用法"：不为削峰，只为排队**。
- 踩过的坑：**无依赖子查询可以并发，但写回顺序必须确定**——这是 Q2 说的"局部串行"在非 MQ 场景里的同一个问题。
- 决策与取舍：**异步是预算超支后的降级动作，不是默认路径**——默认同步返回，超预算才转异步。**"什么时候把同步改成异步"是产品问题，不是技术偏好**。

- 对应母题：【Q1、Q2】

### 5.3 RuleArena（规则竞技场）

- **锚点**：`projects/RuleArena/`
- 用在哪：**这是本卡的主证据。** 架构是 **PostgreSQL 存权威状态 + Redis/ARQ 负责队列、限流与短期进度**（`06-architecture-and-scenarios.md`）；`04-idempotency-and-recovery.md` §9 直接叫「Worker、队列与至少一次投递」，并有一节专答「Q5：消息队列能保证 exactly-once 吗」。Worker 跑一条规则审查是长任务，进程随时可能崩。
- 解决什么问题：**"队列可以丢或重投，业务正确性必须落在可恢复的权威数据库里"**——这一句就是 Q2 的全部答案。系统**接受至少一次投递和进程随时崩溃**，靠不重复的业务副作用把这个前提吃掉：同一数据库事务里完成聚合更新、账本、BusinessEvent 和 ActionReceipt，用唯一约束保证同一动作只生效一次。
- 踩过的坑：**① 不能拿 ToolCallID 当幂等键**——它每次调用都变，重试时对不上；正确的是按「run + 动作 + 目标 + 参数 + 规则版本 + 逻辑步骤」构造**稳定幂等键**（这是 Q2 里"幂等键怎么选"的原题）；**② Worker 超时后不许换 key 直接重试**——先查 Receipt，已完成就继续，明确失败才按错误类型决定重试，仍无法确认就记 `ACTION_UNKNOWN` 并停下（这就是"超时 ≠ 失败"）。
- 决策与取舍：**不提前引入 Kafka / Outbox**，升级条件是"出现真实的跨服务事件投递需求"（`04` §9 末尾）。当前用 `%RETRY%` 式的重投 + 权威状态查询就够了。**队列选 Redis/ARQ 而不是 RabbitMQ/Kafka，理由是 MVP 阶段要的是"能异步跑、能查状态"，不是"高吞吐 + 丰富特性"**（这条取舍正是 Q3 选型节的判据）。

- 对应母题：【Q1、Q2、Q3】

### Q1 消息为什么会丢，要它不丢三段各要做对什么

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：MQ 先在回答"为什么值得引入"，再回答"怎么不丢"：
  - 所以"要不要上 MQ"不是技术偏好，是算账。projects/EnergyOps 就是一本活教材：当前规模（约 604 台设备）明确不上 MQ，用 PostgreSQL 任务表 + APScheduler 就够，只在表计到万级、单机跑不完窗口时才考虑引入。
  - 所有主流 MQ 都只承诺 至少一次（at-least-once） 投递。原因很硬：
  - 于是业界的一致选择是：框架保证"至少一次、宁重勿丢"，把去重的责任交给业务层（这正是 母题-Q2-重复与乱序 的全部内容）。所以本卡"不丢"的目标是"已确认的消息绝不丢"，而不是"绝不重复"。
- 2. 三段接力：一条消息的一生：
  - "消息会丢"只能发生在三个位置，没有第四个：
  - 还有一个反直觉的点：Kafka 3.0 起 acks 的默认值已经是 all（因为幂等生产者默认开启，而幂等要求 acks=all）；老版本默认是 1。所以"默认 acks=1、要改成 all"这个说法在现在的 Kafka 上已经过期了，但很多资料还在讲。
  - 两者必须同时设置：一个是"容器"，一个是"内容"。但即使都设了也不是 100% 安全——消息先写进操作系统的页缓存，再由内核异步刷盘，这个窗口里断电仍然会丢。要做到极致可靠，得配合发布者确认（publisher confirm），即 Broker 确认已经真正落盘/复制成功后才回 ack 给生产者。
- 3. 量化：把确认加严到哪一档算出来：
  - 这两条就是 min.insync.replicas 的全部意义：
  - "不丢"的定义是：生产者收到成功 ack 的消息，永远不会消失。 所以线上看到"MQ 写入报错"，第一反应应该是"它在保护数据"，而不是"MQ 坏了"——这个判断方向反了，排查就会走歪。
  - 这就是经典的"可用性 vs 一致性"二选一，官方 Design 文档把它讲得很直白：*If, on the other hand, a non-in-sync replica comes back to life and we allow it to become leader, then its 
- 4. 边界与常见误解：
  - 是所有在 ISR 里的副本。ISR 只剩一个时 acks=all 照样成功（官方 Design 原文），所以必须配 min.insync.replicas | | "acks 默认是 1"
  - 那是旧版本。Kafka 3.0 起默认已是 all（因为幂等生产者默认开启，而幂等要求 acks=all） | | "配了 min.insync.replicas 就安全了"
  - 它只在 acks=all 时生效。配了 acks=1 的话它一点作用都没有 | | "持久化配了就一定不丢"

- 某 Topic 配 replication.factor = 3、min.insync.replicas = 2、生产者 acks = all、unclean.leader.election.enable = false。

### Q2 消息为什么会重复、会乱序，怎么把它变成"只生效一次"

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：重复和乱序其实是同一个根源：
  - 三处都不可能在框架层杜绝，因为它们的根因是同一个：跨进程通信里"确认"这件事本身可能丢失。 所以所有主流 MQ 的一致选择是——
  - 所以"顺序"和"并行"是同一枚硬币的两面：要顺序就必须在某些地方退回串行。关键判断不是"要不要串行"，而是"串到多细"——这就是第 3 节的量化，也是本卡最重要的一个算式。
- 2. 幂等：把"至少一次"消化成"只生效一次"：
  - 为什么工程上要它：分布式系统里，网络超时、消息重复、请求重试无处不在，你没办法保证一个操作只被执行一次。既然做不到"只执行一次"，就换个目标——不保证只执行一次，但保证执行多次效果一样。
  - 幂等方案看起来有五种，其实它们只是"查重方式"不同，问的都是同一句话：
  - 生产上的常见组合是"Redis 查重 + 数据库唯一约束兜底"：Redis 挡掉绝大多数重复（快），唯一约束挡掉"Redis 查重和写入之间又被重放一次"的极端情况（硬）。只用 Redis 会漏，只用唯一约束会在数据库上多一轮冲突处理。
- 3. 顺序：保序的粒度就是并行的粒度（量化）：
  - 判断依据只有一条：你要的顺序，是"同一个订单内的顺序"，还是"全局的顺序"？
  - 这里有本卡最容易被忽略的一句：即使你把分区加到 100 个拿了 100 倍吞吐，单个订单的处理速度上限仍是单分区那 200 TPS。保序的粒度就是并行的粒度——你要哪个粒度的顺序，就只能拿到那个粒度的并行。
  - 消费端的实现两家不同（这是可以加分的细节）：
- 4. 边界与常见误解：
  - 是必然，不是 bug。框架只保证至少一次，因为"处理"与"记录进度"无法原子化。换个 MQ 不改变这个前提 | | "做幂等就是在框架里开个开关"
  - 幂等是业务层的事。框架能给的只有"至少一次"，去重必须落在你的业务键上 | | "用消息 ID 做幂等键"
  - 必错：重投时 ID 变了，查重永远不命中。要的是稳定业务键（业务键 + 动作 + 目标 + 参数 + 版本），粒度对到"一次动作"而不是"一个业务实体" | | "超时就重试，反正有幂等"
**自测 cue**：
- 某个订单消息的处理逻辑，单条耗时 5ms（其中大部分是数据库写入）。目标吞吐 2000 条/秒，且同一个订单的消息必须有序。
- 消费端要做幂等查重。方案是每条消息先 GET 一次 Redis 判断是否处理过，命中就跳过。
- 生产者配置 max.in.flight.requests.per.connection = 5、retries 开启、enable.idempotence = false。

### Q3 消息积压了怎么办，MQ 自己挂了为什么能不停服

**判据**：（待补：母题卡缺「通过判据」）

- 1. 前提：这一节在回答两个不同的问题：
  - 先分清这一点很重要，因为在面试和线上都常见一个错误动作：把积压当成"MQ 坏了"，或者把宕机当成"消费慢了"。前者会让你去加机器，后者会让你去重启——两个动作都不对症。
  - 消积压的净速度就是 λ 和 μ 的差，而消费能力有天花板——这个天花板不是"你能买多少台机器"，而是分区数（第 3 节量化）。记住这个天花板，它决定了积压是一个"能算出来"的问题。
- 2. 积压：先查根因，再谈扩容（顺序不能反）：
  - 处理顺序必须是"根因 → 容量"：如果消费变慢是因为"代码里多了一次慢查询"，那加消费者只是让更多线程一起去撞那个慢查询（还会把下游数据库打得更死）。先修根因，再看要不要扩容——这个顺序反了会放大故障。
  - 所以"加消费者"这个动作有一个硬天花板。越过它的唯一办法是先把分区数加上去（Kafka 里可以给 Topic 增加分区；RocketMQ 可以加队列）。但加分区有代价：
  - RocketMQ 的应急手段更"野"一点：海量积压时会用临时 Topic 嫁接——写一个只做转发、不做业务处理的搬运程序，把积压消息转到一个队列数多几十倍的新 Topic，再部署对应数量的消费者快速清掉。关键是"不处理业务"，否则搬运速度和消费速度一样慢，等于没搬。
- 3. 高可用：三板斧与"MQ 挂了怎么办"：
  - 所有 MQ 的高可用都在做同一件事，只是分三层：
  - 三层是递进关系：有备份不能自动切，等于没有；能自动切但客户端不知道新地址，等于没有。回答"MQ 怎么高可用"时按这三层说，就不会漏。
  - 这就是"可用性 vs 一致性"在 MQ 里的落点。注意它和积压、和"消费者慢"完全不是一回事——它是"副本层面"的取舍。
- 4. 量化：把积压和可用性都算出来：
  - 判断依据是"消费速率该由谁控制"：
- 5. 边界与常见误解：
  - 会撞天花板：消费者数超过分区数后多出来的全闲置。顺序是"先查根因 → 再加分区 → 再加消费者" | | "消费者多开几个就能更快消费同一个队列"
  - 同一分区/队列同一时刻只能被一个消费者消费。消费能力上限 = 分区数 × 单消费者速率 | | "加分区没代价"
  - 有：要数据迁移，且可能改变 Key 的哈希分布、影响顺序语义。分区数应在设计期估算 | | "积压了先重置 offset 跳过"
**自测 cue**：
- 某 Topic 积压 1000 万条，上游生产速率稳定在 2000 条/秒。单个消费者处理能力 500 条/秒。当前有 20 个消费者，但该 Topic 只有 10 个分区。
- 某 Topic 配 replication.factor = 3。运维发现其中一个分区的 ISR 从 3 缩到了 1（另两个副本的 Broker 失联）。
- 某服务的写路径是"先写数据库 → 再发 MQ 通知下游"。某天 MQ 集群全挂 30 分钟。
