# AI 工程负责人型的核心架构

开发闭环：
```
1. Intake：需求进入
2. Context Pack：构造上下文包
3. Plan：方案与风险
4. Task Router：复杂度路由
5. Execute：小任务执行
6. Observe：测试/日志/报错/用户反馈
7. Replan：必要时重排任务
8. Verify：质量门禁
9. Review：AI + 人类审查
10. Ship：提交/部署/回滚策略
11. Reflect：沉淀规则、测试、记忆
```

> 我用 AI 构建一个带计划、执行、观测、重规划、验证和沉淀的工程闭环。


我现在不会把 AI Coding 理解成简单的“让模型写代码”，而是把它作为一个工程闭环来管理。

我的流程一般是 10 步：

第一，需求进入后先做需求建模，不直接写代码。我会让 AI 帮我拆用户目标、系统边界、未知问题和风险等级。

第二，构造 Context Pack，只给当前任务需要的架构、文件、业务不变量和测试命令，避免把所有历史都塞进去。

第三，复杂任务先 plan，要求 AI 给多个方案和取舍，而不是直接给所谓最佳方案。

第四，用复杂度路由决定流程。小 bug 直接修，中等功能拆任务，高风险变更必须先设计评审。

第五，把方案拆成 Codex 可执行的小任务，每个任务都有 allowed files、forbidden changes、verification 和 done when。

第六，执行时让 Codex 采用 ReAct 式小循环：读代码、改动、跑测试、观察反馈。

第七，如果发现新依赖、测试连续失败、需要改未授权文件、scope 扩大，就停止执行并 replan。

第八，完成后不只看能不能跑，而是走质量门禁：单测、集成测试、lint、type check、diff scope、边界条件。

第九，review 分层做，包括需求一致性、架构一致性、正确性、测试覆盖、安全和可观测性。

第十，把重复踩坑沉淀到 AGENTS.md、memory-bank、测试用例或开发规范里，让下一次 AI 执行更稳定。

在金山能源 MCP 项目里，比如做危险模式或 MCP 工具暴露，我会特别控制权限、审计、数据口径和 Comate-facing tool description，避免 AI 为了完成任务误改统计逻辑或暴露内部字段。

## 1. Intake

重点：**先让 AI 把问题讲清楚，而不是马上回答。**

```
我会给你业务需求和现有项目背景。你的任务不是直接设计最终方案，而是先帮我做需求澄清和任务建模。

请输出：
1. 这个需求真正要解决的问题
2. 涉及的用户角色
3. 现有系统可能受影响的模块
4. 必须确认的未知问题
5. 风险点
6. 初步任务复杂度：小修复 / 简单增强 / 中等功能 / 系统改造

暂时不要写实现方案。
```

```
我会给你一个真实业务需求。你先不要写方案，也不要写代码。
请先完成需求建模：

1. 用户是谁
2. 目标行为是什么
3. 当前系统相关模块
4. 输入/输出
5. 不变量
6. 必须保留的兼容行为
7. 未知问题
8. 风险等级
9. 初步复杂度：L0/L1/L2/L3/L4
```

## 2. Context Pack

```
Context Pack:
1. 需求摘要
2. 当前架构
3. 相关文件
4. 禁止修改项
5. 关键业务不变量
6. 测试命令
7. 历史决策
8. 当前问题/报错
```

为了让 agent 少猜、少跑偏、输出更容易 review。


## 3. Plan,拆成小 patch

```
请把这个方案拆成 4-6 个可以独立提交的开发任务。

每个任务包含：
1. 目标
2. 允许修改的文件
3. 禁止修改的文件或行为
4. 验收标准
5. 需要运行的测试
6. 完成后必须汇报的信息

注意：每个任务应该能在一个独立 diff 中完成，不要把多个不相关改动混在一起。
```

```
基于上面的 Context Pack，给出 3 个方案：

方案 A：最小改动
方案 B：推荐工程方案
方案 C：长期可扩展方案

每个方案必须包含：
1. 架构设计
2. 改动文件
3. 数据结构/配置变更
4. 风险
5. 回滚方式
6. 测试策略
7. 不选择它的理由

最后给推荐方案，并说明推荐条件。
```

**工程判断：**
面试官问“如果重做项目，你会怎么优化”，你就不能只说“根据需求优化”，而要从模块边界、状态机、prompt/tool 解耦、观测、重试、幂等、RAG/schema linking 鲁棒性这些维度展开。

## 4. 自适应拆分：不要所有任务都一个流程

**复杂度路由器**

|等级|类型|例子|AI 流程|
|---|---|---|---|
|L0|文案/注释/小配置|改 tool description|直接执行 + diff review|
|L1|单点 bug|某接口参数映射错误|先复现，再修，再测|
|L2|小功能|新增一个 MCP 查询工具|plan → execute → test → review|
|L3|跨模块功能|危险模式、权限、审计|design doc → task split → 多 patch → gate|
|L4|高风险系统改造|数据口径、迁移、权限默认策略|人工设计评审 → 分支/灰度/回滚/观测|

## 复杂度打分

你可以按 5 个维度判断：

```
Scope：会改几个模块？Risk：是否涉及数据、权限、生产配置？Ambiguity：需求是否明确？Verifiability：能不能自动测试？Blast Radius：出错影响范围多大？
```

判断规则：

```
单文件 + 可测试 + 无业务风险 = L1多文件 + 有新行为 + 可测试 = L2跨模块 + 权限/数据/用户体验 = L3生产数据/迁移/安全默认策略 = L4
```

Anthropic 的 orchestrator-workers 正适合“子任务数量和涉及文件无法提前确定”的复杂编码任务；
而 evaluator-optimizer 适合有明确评价标准、需要迭代提高质量的任务。

## 5. Replan：什么时候必须重规划

**不要让 agent 自由 replan，要有触发条件。**

Replan 触发器
出现以下情况，必须停下来 replan：

```
1. 连续两次测试失败，且失败原因不同2. Codex 需要修改未授权文件3. 新发现一个旧逻辑依赖，原计划没覆盖4. 需求解释出现歧义5. diff 明显超过原任务范围6. 需要新增依赖、改 schema、改配置7. 涉及权限、安全、数据口径8. 修 bug 时发现根因和原判断不一致9. 性能退化或兼容性风险出现10. AI 开始通过改测试来让测试通过
```

你的 replan prompt：

```
暂停执行，进入 Replan。请基于当前观察重新评估：1. 原计划哪一条失效了？2. 新发现了什么事实？3. 是否需要缩小/扩大 scope？4. 是否需要新增任务？5. 哪些已完成工作可以保留？6. 哪些改动需要回滚？7. 新的最小可行计划是什么？8. 是否需要人工确认？不要继续写代码，先输出 Replan 报告。
```

Agent是一个要被观测和控制的执行系统。
生产系统需要 guardrails 和 human-in-the-loop 保持可预测。

```
- 不允许修改哪些模块  
- 不允许改变哪些行为

- 日志/审计要求

- 需要运行哪些测试

- 行为满足什么条件

```


## 7. 代码质量，有指标体系


## 高质量代码的四层定义

### 1）局部代码质量

```
- 命名清楚- 函数单一职责- 类型明确- 错误处理完整- 边界条件覆盖- 无重复逻辑- 无隐藏副作用
```

### 2）架构质量

```
- 模块边界清晰- 依赖方向合理- 业务逻辑和基础设施解耦- tool / prompt / policy / config 分离- 状态流转可追踪- 可扩展但不过度设计
```

### 3）交付质量

```
- 单元测试- 集成测试- 回归测试- lint/type check- CI 通过- diff scope 可控- PR 可 review
```

### 4）线上质量

```
- 错误率- 500 比例- 回滚率- 变更失败率- 平均恢复时间- 日志/trace/metrics 完整- 告警有效
```


我会从四层看代码质量：
第一层是局部可读性和边界处理；
第二层是架构边界，比如 prompt、tool、policy、config 是否解耦；
第三层是交付质量，比如测试覆盖、CI、review 可读性；
第四层是线上质量，比如错误率、回滚率、变更失败率和恢复时间。

AI Coding 下我尤其关注 diff scope、测试是否被 AI 篡改、是否引入隐性行为变化，以及是否把项目约定沉淀到 AGENTS.md / rules 里。


## 8. AI Review

**多角色 review**。

## Review 分层

```
Reviewer A：需求一致性- 是否满足原需求？- 是否 scope creep？- 是否漏掉用户场景？Reviewer B：架构一致性- 是否破坏模块边界？- 是否绕过既有抽象？- 是否引入不必要依赖？Reviewer C：代码质量- 边界条件- 异常处理- 命名和复杂度- 重复逻辑Reviewer D：测试和可观测- 是否有测试？- 测试是否覆盖核心风险？- 是否有日志/trace/metrics？- 告警是否能发现失败？Reviewer E：安全和权限- 是否最小权限？- 是否需要审计？- 是否可能误操作生产数据？
```

一个很实用的 review prompt：

```
请作为严格代码审查者，基于原始需求、计划和 diff 进行 review。按 5 个维度审查：1. Requirement fit：是否满足需求，有无 scope creep2. Architecture fit：是否符合现有架构和模块边界3. Correctness：边界条件、异常处理、并发、幂等4. Verification：测试、lint、type check、手工验证是否充分5. Risk：权限、数据、性能、兼容性、可观测性风险输出：- Blocking issues- Non-blocking issues- Missing tests- Suggested improvements- Final verdict: approve / request changes / replan
```
