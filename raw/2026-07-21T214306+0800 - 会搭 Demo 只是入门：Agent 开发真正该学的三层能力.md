封面

Hello 大家好，我是 Perfecto，目前在宠物行业 SaaS 公司做 Platform 和 Infra，最近半年主要在折腾内部 Agent、落地企业内部的 AI 基础设施和 Agent 工具链。

过去几个月，隔一阵就会有人来问我：Agent 开发到底应该怎么学？前几天一位读者朋友又来找我，我顺手给他发了几篇文章，还推荐他用 Teach Skill <sup>[1]</sup> 围绕真实目标建立一套学习过程。我突然间有点心虚：文章发了一堆，但如果让我用一篇文章把“先学什么、哪些东西先别学、学到什么程度才算真的会”讲清楚，我自己的公众号里居然没有。

其实自己的知识库里几乎每天都在频繁的更新，只是写给自己的内容风格语气会比较随意，一旦想到要发出来，我就忍不住开始挑这句话准不准确、那个判断会不会误导人，最后越改越不想发。工作里天天接触 Agent，时间久了，反而容易忘记自己刚开始时也被这些问题困扰过。和读者聊完，才觉得有必要把它们重新讲清楚。最近加入羽哥（冴羽 <sup>[2]</sup> ）的知识星球做嘉宾，他又催了几次。再拖下去就有点说不过去了，恭敬不如从命。

但这篇文章呢，我不准备再把 Agent Engineering 名词讲解一遍，也不劝谁应该去转型。只想回答一个更实际的问题：一个已经会开发的人，想把 Agent 变成自己的能力，到底应该学什么、怎么学，以及哪些东西暂时别急着学。

**Agent 开发仍然是软件工程，只不过系统里多了一个会自主决策、输出又不完全确定的执行者。**

最近看到 DeepSeek Agent Harness 团队的招聘页 <sup>[3]</sup> ，Harness 团队把使命直接写成了一个公式：

> Model + Harness = Agent

Model 是那个基于输入预测并生成输出的模型。Harness 是模型外面那整套让它能工作的工程：Prompt、Context、Tool、Loop、State、Memory、权限、恢复、Eval 和 Observability。

**对绝大多数不训练基础模型的应用开发者来说，Agent 开发主要是在开发 Harness。**

我们平时高强度使用 Claude Code 和 Codex，还会遇到两层不同边界的 Harness。为了方便说清楚，我暂且叫它们“产品级 Harness”和“环境级 Harness”，这不是一个已经统一的行业分类。

Claude Code、Codex <sup>[4]</sup> 本身是产品级 Harness，模型厂商用它把裸模型变成会读仓库、跑 Shell、调工具、继续决策的 Agent。当通用 Agent 进入一家公司或一个具体项目，外面还需要环境级 Harness：全局宪法和 `AGENTS.md` <sup>[5]</sup> / `CLAUDE.md` 定义规则，Memory、Checkpoint 和 Handoff <sup>[6]</sup> 保存状态，Skill 和 MCP 提供能力，Goal 和 Spec 定义完成，Hooks、权限、Lint、Test 和 Eval 负责拦截与验证。

**第一层约束模型如何行动，第二层约束 Agent 在真实环境里如何交付。**

模型决定能力上限，Harness 决定这份能力能不能被稳定使用。这也决定了后面的学习主线。

Model + Harness = Agent

如果只盯着模型，你会觉得换一个更强的模型，Agent 就好了；如果只盯着 Prompt，你会不停修改措辞，希望把每一种异常都写进提示词；如果只盯着框架，你会在 LangGraph、AutoGen、CrewAI 和下一个新名字之间来回迁移。它们都有用，但都不是主线。

我觉得真正的学习主线可以分为三个层次：

| 层次 | 你在解决什么 | 学到什么算过关 |
| --- | --- | --- |
| 让 Agent 跑起来 | 模型如何决定、调用工具并继续行动 | 不依赖重框架，能写出并解释最小 Loop |
| 让 Agent 获得能力 | 如何接工具、知识、记忆，必要时协作 | 知道每种能力解决什么问题，也知道它新增了什么故障面 |
| 让 Agent 对结果负责 | 如何处理权限、状态、副作用、投递、评估与恢复 | 不只知道“模型说了什么”，还能回答“系统到底做成了没有” |

后面的名词再多，都可以放回这三层里。先有主干，再往上挂知识，不容易乱。

Agent 开发的三层学习主线

## 一、先让 Agent 跑起来：看清那个 Loop

很多人的第一个 Agent，是从一个框架 Quick Start 开始的。几十行代码，模型能调用天气 API，控制台里刷出几段“思考”和工具结果，看起来很像那么回事。

这当然算入门，但容易产生一个错觉：以为 Agent 就是 `LLM + Tools` ，剩下的只是继续加工具。

把框架拆掉以后，一个最小 Agent 实际上在重复这几件事：

```
接收目标
  ↓
组装当前上下文
  ↓
模型决定：回答、调用工具，还是停止
  ↓
执行工具并取得结果
  ↓
把结果写回状态，再次交给模型
  ↺
```

写成一句话就是：

> Model → Context → Decide → Tool → Feedback → Loop

Prompt 当然重要，它负责告诉模型这次要做什么。模型还要根据中间结果继续决定下一步，Runtime 再把决定变成行动，整个过程反复运行，直到满足终止条件。一次模型调用走到这里，才有了 Agent 的样子。

这也解释了 Workflow 和 Agent 的区别。一个“先分类，再查库，再总结”的固定流程，即使每一步都调用 LLM，也仍然更接近 Workflow；如果下一步做什么由模型根据当前状态动态决定，它才更接近 Agent。不是哪个名字更高级，而是两者的工程代价不同：固定流程更容易预测、测试和恢复，Agent 更灵活，同时也更难证明它会走到哪里。

实际开发里，我反而会优先问：这件事真的需要 Agent 吗？如果路径可以提前写死，用 Workflow 往往更便宜、更稳定。只有任务无法完整枚举步骤、需要根据环境反馈临场决策时，自主 Loop 才开始产生价值。

### 这个 Loop 里要学什么

模型接口。别把模型响应当成一段字符串，这是我自己踩过的坑。模型一次返回可能同时包含正文、tool call 和厂商定义的 reasoning / thinking item；它有时只是 summary，并不是原始思维链。OpenAI Responses API <sup>[7]</sup> 、Anthropic Tool Use <sup>[8]</sup> 、Gemini Thought Signatures <sup>[9]</sup> 的格式也不一样，流式输出时还可能交错到达。比较稳妥的做法是保留厂商原始响应，再统一转成 `reasoning_summary` 、 `text` 、 `tool_call` 、 `tool_result` 、 `completed` 、 `failed` 这类内部事件；UI 只根据内部事件展示，下一轮还需要的 call ID 或 signature 也原样保存。这样换厂商、换模型时，业务逻辑和界面不用跟着重写。

Prompt。先把模型理解成一个根据输入预测并生成输出的生成器。你给它 system instruction、用户问题、例子、工具描述和上下文，它根据这些内容预测接下来最可能生成什么。所以 Prompt 不是发给确定性函数的命令，而是在提高模型做对的概率；目标、边界、可用工具和完成条件仍然要写清楚，但绝对不能违反的业务规则，还得交给 Schema 校验、权限、状态和停止条件来保底。

Context。模型本身没有你的应用状态。系统指令、用户目标、历史对话、工具结果、检索材料和记忆，最后都要进入有限的上下文窗口。放得太多，信息会互相干扰；放得太少，模型又没有足够的信息做判断。每一步该加载什么、裁掉什么、压缩什么，都是 Context Engineering 要处理的问题。

Tool Use。模型决定调用什么，Runtime 真正执行。Schema 怎么写、参数怎么校验、错误怎么返回、结果要不要裁剪，都会改变下一轮决策。工具对人类好用，不等于对模型好用；含糊的函数名、巨大的返回值、无法区分的错误，都会把复杂度重新扔回模型。

State。当前做到哪一步、已经调用过什么、外部世界是否被改变，不能只存在聊天记录里。聊天记录是给模型看的上下文，状态是系统恢复和判断的依据，这两件事不要混在一起。

Stopping Condition。最大步数只是最后一根保险丝，不是完整的停止设计。任务成功、需要用户补充信息、工具连续失败、预算耗尽、风险操作等待确认，都可能是合法的停止原因。Agent 会行动，也必须知道什么时候不该继续行动。

第一阶段最值得做的练习，不是跟着教程再搭一个聊天机器人，而是不用 Agent 框架，自己写一个很小的 ReAct + Tool Use Agent。

语言不用为了学 Agent 重选。如果你已经熟悉 Python 或 TypeScript，就用熟悉的；两者差不多时，我更推荐 TypeScript + Node.js 作为第一个练习。类型系统能逼着你看清不同 response item，Zod/JSON Schema 写工具参数也顺手，后面接 Web UI、MCP 和 Skills 不需要换栈。主要方向是数据、RAG 和 Eval 的读者，用 Python 同样合理。

这个练习可以只做三件事： `search_docs` 查本地文档， `read_doc` 读取正文， `finish` 明确交付结果。直接调用一家模型的官方 SDK，自己维护 messages 和 state；最多循环八步；打印每个原始 response item；处理工具参数校验、工具报错、超时和五种停止原因。然后故意把一个工具弄坏，再观察 Agent 会不会重试、换路或停下来。

阅读顺序也很重要。我建议先自己写出第一版，再对照三份材料：先读 ReAct 原始论文 <sup>[10]</sup> 看“推理—行动—观察”的原型；再读 Anthropic 的 Building effective agents <sup>[11]</sup> 看最小组合模式；最后直接看 Pi 的 `agent-loop.ts` <sup>[12]</sup> 。Pi 这一个文件里能看到 tool call 检测、顺序/并行执行、结果回填、stop reason、steering 和 follow-up，比再看十篇“如何调用天气 API”更接近真实 Harness。

如果你能画出一次任务从输入到结束的完整 Loop，并指出每一步由模型决定还是由代码决定，这一层就算过了。做不到的话，换再多框架也只是把不理解的部分包起来。

## 二、再让 Agent 获得能力：每接一个系统，也接进来一套复杂度

最小 Loop 跑起来以后，下一步通常是加能力：让它查资料、读文件、调用业务 API、记住用户偏好，或者让几个 Agent 分工。

这一步很容易让人兴奋。每多接一个工具，Demo 都明显更“聪明”。但我后来越来越在意另一面： **Agent 获得的每一种能力，都会同时带来一个新的故障面。**

它能读知识库，就会读到过期、越权或互相矛盾的资料；它能写数据，就会遇到重复执行和部分成功；它有长期记忆，就会记错、记多、记住不该记的东西；它能调用其他 Agent，就会有路由、身份、协议和责任边界。

所以这一层不能只学“怎么接”，还要学“接进来以后怎么判断它工作正常”。

### Tools 和 Skills：先把能力做成模型能用的接口

Function Calling 解决的是“模型怎样表达一次工具调用”。MCP 解决的是“模型应用怎样用统一协议连接外部工具和数据”。Skills 更像能力包：除了工具，还可以包含说明、流程、参考资料和脚本，并且按需加载。

这几个概念不是互斥选型，它们常常处在不同层次。

协议字段用到时查文档就行，练习时多花点时间在工具设计上：

- • 名字和描述能不能让模型区分两个相似工具；
- • 参数能不能在执行前被确定性校验；
- • 返回结果有没有保留下一步决策所需的信息；
- • 失败时能不能区分“可以重试”“需要换方案”“必须问用户”；
- • 读操作和有副作用的写操作是不是同一种授权方式。

工具少的时候，这些问题不明显。工具一多，全部 Schema 塞进 Context 既占 Token，又增加误选。 **给模型的能力集合也需要做信息架构。** 渐进加载、Tool Search 和按任务暴露工具，都是在控制一次任务里模型到底能看到哪些工具。具体产品叫什么，用到时再查。

想把 Skills 学明白，我会直接看 Anthropic 官方 Skills 仓库 <sup>[13]</sup> ，而不是只读一篇概念介绍。先看最小 template，再看 `skill-creator/SKILL.md` <sup>[14]</sup> 怎样组织触发描述、主流程、references、scripts 和 eval。然后把刚才那个 Tool Agent 的一段稳定流程封成自己的 Skill：什么时候触发、需要读取什么、怎样验证完成。亲手写过一次，才会理解 Skill 不是“收藏 Prompt 的文件夹”，而是可加载、可执行、可验证的能力模块。

### RAG：它是 Agent 的外部知识系统，不是一个“搜一下”的小功能

RAG <sup>[15]</sup> 经常被放在 Agent 教程的一小节里：切块、Embedding、向量检索、把结果塞给模型，结束。这样能跑，但会让人严重低估它。

完整的 RAG 至少有自己的链路：

```
数据加载 → 清洗与切分 → 建索引 → 查询改写 → 检索
       → 过滤/重排 → 生成 → 引用与反馈
```

每一段都可能让最终答案变差。回答错了，可能是资料根本没入库，可能是 chunk 切坏了，可能是权限过滤后没有候选，可能是召回了但排序靠后，也可能证据已经给对了，生成模型却没有忠实使用。

这就是为什么 **Agent 有一套 Eval 和 Observability，RAG 也有一套，不能互相代替。**

RAG 更关心检索是否召回了正确证据、无关内容占了多少、回答是否忠于证据；Agent 更关心任务是否完成、工具是否选对、路径是否合理、有没有产生错误副作用、花了多少时间和成本。两者会共享上下文、权限、日志和成本基础设施，但“Agent 最后答对了几道题”不能告诉你 Retrieval 到底好不好。

小模型加垂直领域 RAG，在特定任务上完全有机会打赢通用大模型。这个判断需要几个条件：数据质量足够高，权限和时效已经处理，检索链路单独做过评估，双方还要在同一组真实任务上比较。少一个条件，都容易把一次偶然命中写成架构结论。

学 RAG 时，可以从二三十条带标准答案和标准证据的查询开始。每次失败都判断是 Retrieval 错，还是 Generation 错。把这两类错误分开以后，后面的调优才有方向。

如果需要一个能动手的入口，可以跟着 `langchain-ai/rag-from-scratch` <sup>[16]</sup> 把 query transformation、routing、indexing、retrieval 和 generation 逐段跑一遍；但不要停在 notebook 成功运行。紧接着用 Ragas <sup>[17]</sup> 给同一批查询加上 Context Precision、Context Recall、Faithfulness 和 Response Relevancy。前一份材料教你把链路拆开，后一份逼你回答每一段到底有没有变好。

### Memory：不是把历史聊天全塞回去

Memory 解决的是跨轮次、跨会话甚至跨任务的连续性。它至少涉及写入、读取、更新、冲突、遗忘和权限。

“用户今天说想吃辣，要不要记？”这个问题没有统一答案。临时意图、稳定偏好、明确事实、系统推断，生命周期不一样。把它们都存成一行向量，后面只会得到一个非常自信、但不知道什么应该作废的 Agent。

更麻烦的是，记忆一旦参与行动，就不只是体验问题。Agent 记错了用户身份、项目环境或默认收件人，可能直接把动作执行到错误对象上。所以长期记忆最好带来源、时间、作用域和置信度；有冲突时保留证据，让系统知道为什么覆盖，而不是偷偷改掉一行文本。

这里要刻意区分：Context 是这一次模型调用能看到什么，Memory 是哪些信息能够跨调用保存，State 是任务当前进行到哪里。三者可能使用相同的存储介质，但不承担同一种职责。

### Multi-Agent：不要照着人类组织架构画系统

我也踩过这个坑。

有一次我给五个 Agent 设计了一个最简单的站会。原本的规则很克制：每个 Agent 汇报一次，加一条汇总，预期六条消息结束。第一次真实运行，频道里出现了二十三条消息。Agent 互相 @，一条回复触发下一条回复；有人把工具调用的 JSON 原样发进群；还有 Agent 在没有可靠依据时编出了“自己昨天做了什么”。

单看每个 Agent 的 Prompt，好像都说得过去。问题出在交互协议：谁可以唤醒谁，什么消息算任务，什么时候沉默，谁拥有终止权，都没有被系统性定义。后来把它改成独立触发、禁止互相 @、每个 Agent 只允许发一条，反而立刻安静了。

这件事让我对“多 Agent 更像一个团队”一直比较警惕。人类天然受到时间、技能和身体的限制，所以需要按岗位分工；Agent 可以横跨多个角色，给它复制五个身份，不会自动得到五倍能力，却一定会得到更多通信、状态和故障组合。

多 Agent 当然有适合的地方：任务可以真正并行、上下文需要隔离、不同子任务需要不同模型或权限、单个 Agent 的上下文已经成为瓶颈。但它应该是被约束推出来的架构，不是因为组织架构图看起来很完整。

Multi-Agent 通信时的失控膨胀

到这里，可以用一个问题检查自己：每增加一种能力，你能不能同时说出它新增的状态、权限和评估对象？如果只能描述“接上以后能做什么”，还没有描述“坏了怎么知道”，这一层只完成了一半。

## 三、让 Agent 对结果负责：生产系统不接受“它看起来完成了”

Demo 最容易给人一个错觉：界面里出现了一段不错的最终答案，任务就成功了。

真实系统里，模型生成了 Final Output，只能证明 Runtime 走到了某个节点。用户有没有收到、外部动作有没有发生、发生了几次、当前还能不能恢复，是另外几组问题。

我最近处理过一个接入 IM 渠道的 Agent。一个看起来很小的问题，很快把整条生产链路都扯了出来：Agent 任务已经成功，消息投递失败了，算成功还是失败？投递请求超时，无法确认对方到底收没收到，能不能直接重发？任务中断后恢复，是从模型继续推理，还是把最后一个动作重新执行？如果那个动作是发消息、建工单、改数据，重复执行会发生什么？

这些都不是 Prompt 能解决的问题。

投递、身份、幂等和恢复放在一起看，已经是一套 Agent 的生产运行环境。

### 先把“运行结果”和“投递结果”拆开

对一个接入 IM 的 Agent，至少存在两类 Outcome：

- • Run Outcome：Agent 是否完成推理与工具执行，是否产生了最终结果；
- • Delivery Outcome：消息是否通过渠道发送给用户。

于是会出现几种都合理的组合：Run 成功但 Delivery 失败；Run 失败但失败通知成功送达；分段消息只送到一部分；请求超时，只能标记为 `unknown` ，因为系统无法确认远端是否已收到。

如果把它们压成一个 `success: true/false` ，后面几乎无法正确重试。你不知道应该重新运行整个 Agent，还是只补发消息；也不知道用户没收到，是模型没产出，还是渠道没送达。

**“任务做完”和“用户收到结果”是两件事。** 这是传统分布式系统里的老问题，只是在 Agent 场景里更容易被一段自然语言输出遮住。

任务状态与投递状态的差异

### 权限要分清用户身份和应用身份

生产里的 Agent 一旦执行操作，马上会遇到身份问题。

有些能力必须使用用户级权限。例如只读取当前用户有权看的文档，或者以用户身份更新他自己的数据。这类操作的授权范围应该跟着用户走，Agent 不能因为自己是系统应用，就越过用户边界。

另一些能力来自 Agent 自身的应用身份。例如查询经过脱敏的系统日志、调用内部搜索服务、发送应用通知。它们不代表某个用户，而代表这个应用被平台授予的能力。

飞书、Slack 或其他企业系统的细节不完全一样，但这个心智模型很稳定：

```
用户身份：Agent 代谁行动？
应用身份：这个 Agent 自己被允许做什么？
```

二者混在一起，常见结果不是“权限不足”，而是权限过大：用户本来只能看自己的数据，Agent 却拿应用身份查到了全局数据；或者一个用户诱导 Agent 把另一个用户的上下文带进当前会话。

权限设计不能只做到 API 鉴权。工具暴露、检索过滤、Memory 作用域、日志脱敏、执行审批，都要沿用同一套身份边界。读操作和写操作也不该只有“允许/不允许”两档：只读、可逆写、不可逆写、需要用户确认、必须人工审批，可以是不同等级。

### 重试之前，先问这个动作有没有副作用

外部 API 超时，最顺手的写法是指数退避重试。对查询通常没问题，对“发一条消息”“创建一张工单”“给用户退款”就未必。

超时只说明调用方没有拿到确定结果，不代表远端没有执行。这个时候直接重试，可能把一件事做两遍。于是生产 Agent 需要的不只是 Retry，还包括：

- • 幂等键：同一个逻辑动作重复请求，远端只执行一次；
- • Checkpoint：明确记录哪些步骤已经提交；
- • 去重：同一个终止事件不能产生第二份结果；
- • 补偿：无法回滚时，定义反向动作或人工处理路径；
- • `unknown` 状态：承认系统暂时不知道，而不是用“失败”掩盖不确定性。

我很喜欢 `unknown` 这个状态。工程师容易本能地追求枚举完整，好像所有事都必须被归到成功或失败。但分布式系统里，诚实表达“不知道是否发生”比武断地重试更安全。Agent 会让这种不确定性叠加：模型决策不确定，网络结果也不确定，必须把两者分开记录。

### 状态与恢复：继续任务，不等于重放动作

长任务一定会中断：进程重启、模型超时、工具失败、用户临时取消、预算用完。恢复时最危险的实现，是把之前的对话重新喂给模型，然后说“请继续”。

模型可能不知道哪些外部动作已经真正提交，也可能因为上下文被压缩而重新做一次。一个可靠的恢复点，应该至少知道：当前状态、已完成动作、待确认动作、外部资源标识、剩余预算，以及上次为什么停。

这里也要区分两种 Retry：

- • Continuation Retry：从已确认的状态继续完成后续任务；
- • Attempt Replay：把某一次外部调用重新执行。

前者不必重复已经成功的副作用，后者必须满足幂等或经过明确确认。名字可以不同，这条边界不能模糊。

### 当 Agent 开始同时服务很多人

包括不少“从零实现一个 Claude Code”之类的教程，都会为了讲清核心 Loop，先默认一个很简单的世界：只有一个用户、一条 Session、一个进程，工具也都可信。状态先放在内存里，Token 写进环境变量，任务中断了就重新跑一遍。本地演示这么做没什么问题，接进企业系统以后，这些假设很快就不成立了。

最先碰到的是多租户隔离。用户 A 的 Context、Memory、文件、工具结果和凭据，不能被用户 B 的任务看到。只在 API 入口校验一次身份还不够， `tenant_id` 、 `user_id` 、 `session_id` 和 `run_id` 要一直传到 Retrieval、Memory、工具调用、日志和 Sandbox。中间任何一层把身份丢了，后面都可能拿应用级权限访问原本不属于这个用户的数据。

Agent 的并发也有点特别。一次任务可能跑几分钟甚至更久，中间大量时间都在等模型、工具、用户确认或外部事件；同一个用户还可能同时启动多个 Run。长任务的生命周期不能依附于一条 HTTP 连接。连接断开以后任务是否继续、进程重启以后从哪里恢复、积压时怎样限制并发，都需要 Queue、异步执行、Checkpoint 和背压来回答。版本发布也会带来新问题：跑到一半的 Session 继续使用旧版本，还是切到新版本？已经执行过的外部动作，不能跟着版本切换一起重放。

这时几个边界要画清楚。Runtime 承载 Agent 自己的 Loop、Session、生命周期和扩缩容；Sandbox 承载模型生成的代码、Shell、浏览器和其他高风险执行。Model Gateway 负责模型路由、Fallback、费用和调用观测；Tool Gateway 管 Agent 能看到哪些工具、以谁的身份调用，以及参数和内容是否满足策略。前面讲了用户身份和应用身份，生产平台还会增加 Agent / Workload Identity，用来证明是哪一个 Agent、哪次部署、哪个环境在申请这份凭据。Demo 里这些东西可以挤在一个进程里，生产设计里至少要把职责分开。

### Eval 和 Observability：没有证据，就只能靠感觉调 Prompt

我见过一份十四万字的 Agent 技术蓝图，结构很完整，概念也几乎都覆盖了，但最关键的评估部分仍然只是框架。这样的文档很容易给人一种“系统已经想清楚了”的感觉，实际上只要拿一组真实 case 跑一遍，架构很可能就会开始重写。

Agent 系统很难只靠静态设计推演出来。错误会沿着多轮工具调用传播；同一个输入可能走不同路径；输出文字看起来合理，外部状态却已经错了。没有真实任务和可验证结果，很多“最佳实践”只是在纸面上互相兼容。

Eval 要先回答“什么叫成功”。一个客服 Agent 的成功，可能同时包括：问题解决、政策没有违反、该升级时确实升级、没有破坏用户数据。只评最终文本不够，还要按任务选择过程和环境检查：工具选对没有、参数对不对、数据库最终状态是什么、有没有多做一次副作用。

Observability 回答另一件事：这一次为什么成，为什么败。至少要能串起模型调用、工具调用、状态变化、权限身份、投递尝试、延迟和成本。日志不是越多越好，关键是一次 Run 能沿着同一个 ID 找到因果链。

我的建议是，不要等 Agent “做完了”再补 Eval。项目刚开始就攒一小组真实任务，哪怕只有二十条。每改一次 Prompt、工具或模型都跑一遍。它不需要一开始就很自动化，但必须能留下 baseline，能区分这次是真的变好，还是刚好换了一组顺手的例子。

这一块值得直接精读 Anthropic 的 Demystifying evals for AI agents <sup>[22]</sup> 。它最有价值的不是列了几个 grader，而是把 task、trial、transcript、outcome 和 grader 分开：Agent 可能走出不同路径，所以既要看最终环境状态，也要按风险决定是否检查过程。想把 Eval 真跑起来，可以再看 UK AI Security Institute 开源的 Inspect <sup>[23]</sup> ；不一定要采用它，但它的 dataset、solver、scorer、sandbox 分层很适合作为设计参照。

### 安全、隔离和成本

当 Agent 只能聊天时，错误答案的影响相对有限；当它可以读邮件、查文档、执行代码、写业务系统时，外部内容就可能反过来影响它的行为。Prompt Injection 的危险不只是“模型被骗了”，而是不可信内容借 Agent 已经拥有的权限执行了动作。

因此安全不能只靠 System Prompt 里的一句“不要听从外部指令”。工具最小权限、读写隔离、沙箱、危险动作审批、敏感数据不进入无关上下文，这些仍然是 Runtime 的职责。系统应该假设模型有一天会判断错，然后限制判断错时能造成的损失。

成本也一样。模型调用次数、上下文大小、工具返回体、失败重试、并行 Agent 数量都会放大成本。最有效的优化通常不是到处省几个 token，而是减少无意义的 Loop、让工具一次返回真正需要的信息、避免把所有历史都反复塞回去，并用更便宜的模型处理边界清晰的子任务。

如果你现在能回答下面四个问题，这一层才算真正开始：任务成功但消息没送达，系统怎么记？一个超时的写操作能不能重试？Agent 当前是以谁的身份行动，这个身份会不会在中途丢掉？版本升级以后，拿什么证明它没有退化？

## 四、那到底应该怎么学

也有读者问我，想买课程来学习，某林、某光，或者掘金小册、极客时间，到底该买谁的。这个问题我想分情况来回答。如果你是 0 经验、知识体系还没搭起来，跟着一门结构完整的课程学一遍挺好的。毕竟说实话，有些课程对于专业人士来说可能缺乏深度，但是广度实打实的还可以，花几百块钱，有人帮你排好顺序，手把手带一遍，内容量大管饱，也不亏嘛。

如果已经做过几年软件开发，手头又刚好有 Agent 的开发需求，我不太建议买课。试着从这个需求开始，找一手资料（怎么找一手资料就看 Tw93 写的 在 AI 时代，我是如何深入学习一个技术领域的 <sup>[24]</sup> ）， 在电脑上 clone 几个知名的开源项目，结合 AI 去理解设计理念，碰到问题再去补概念。很多课程覆盖得很广虽然挺好，但也容易让人学完以后知道很多名词，回到项目里还是不知道该从哪里下手——因为没遇到过真实问题，缺乏应用场景也无法深刻记忆。

对已经会开发的人，学习路线可以沿着真实项目展开。系统暴露什么问题，就补什么能力。

### 从一个自己熟悉的真实问题开始

我不太认同“我要转型做 Agent 工程师”作为起点。Agent 很可能会变成大多数工程师都会使用的一种能力，就像云、搜索、数据分析，不一定需要先换一个身份。

更有效的问题是：你手上有什么真实任务，过去因为步骤不固定、信息分散或人工成本太高而做不好？Agent 能不能在其中承担一段决策与执行？

如果你做前端，可以做浏览器操作或带 UI 状态的 Agent；做后端，可以从内部运维、工单或数据处理切入；熟悉某个行业，就让 Agent 解决这个行业里外人不知道的细节。模型能补实现速度，但不会凭空补领域判断。你对问题越熟，越知道什么叫真正完成。

### 用一个真实项目，把三层各走一遍

我会把学习过程归纳成四个阶段：

写出最小 Loop。直接调用模型 API，只接两三个工具。自己保存状态、处理错误、定义停止条件。目标不是功能多，而是能解释控制权在模型和代码之间怎样流动。

接入一种真正有价值的能力。可以是业务 API、RAG、Memory 或浏览器，但一次只选一种。给它准备一组真实任务，记录没接之前和接入之后的变化。不要同时堆五个系统，否则失败时根本不知道是谁造成的。

故意把它弄坏。让工具超时，让检索返回冲突证据，让权限不足，让任务中途重启，让同一个终止事件到达两次。真实学习发生在反馈里：你以为系统会怎样，实际发生了什么，两者之间的差距是什么。

把失败变成 Eval。每修一个有代表性的 case，就把它留进测试集。等这组真实失败逐步稳定了，再扩模型、框架、RAG、Memory 或 Multi-Agent。

这也是为什么我不太建议一开始沉迷“最佳 Agent 项目清单”。抄一个完整项目，往往只能练到代码复现；从自己熟悉的问题出发，你才会真的遇到完成标准、异常路径和权限边界。

### 面对新名词，先翻译，再判断值不值得学

Agent 领域时不时就会冒出一个新名词、新概念。我现在倒不太会因为名字多就先反感，它们至少在帮行业建立共同语言。新的实践里确实出现了新能力和新范式，自然需要新的抽象层把它们说清楚。

话说回来，从第一性原理出发，很多 Agent Engineering 问题并不神秘，它们仍然是软件工程问题在 Agent 时代的新表现。大部分底层规律没变，只是系统里多了概率性、自主决策、有限 Context 和自然语言接口这几个新变量。

如果你对软件工程的知识体系已经比较熟悉，掌握 Agent 开发的速度大概会比自己想象得快。因为你不是从零开始，而是把已经熟悉的控制流、运行时、状态机、数据库、权限、测试和可观测性，重新放到一个会自主决策、但不完全稳定的执行者周围。

| Agent 工程概念 | 对应的软件工程抽象 | Agent 时代新增的问题 |
| --- | --- | --- |
| Prompt Engineering | 任务规格 / API Contract | 执行者是概率性的，写清楚也不等于必然执行 |
| Loop Engineering | 控制流 / Retry / 递归 | 下一步由模型决定，还要管预算、收敛和停止 |
| Harness Engineering | Runtime / OS | 把 Context、Tool、权限、状态和验证组成可运行系统 |
| Context Engineering | Working Set / Cache / GC | Context 有限，要决定什么时候加载、裁剪和压缩 |
| Tool Call | API / SDK 设计 | 接口不只要对人好用，还要让模型选对、传对、读得懂错误 |
| State | 状态机 / Checkpoint / 事务 | 要知道任务做到哪、哪些副作用已提交，以及如何恢复与回滚 |
| Memory | 持久化 / 数据库 | 跨 Session 保存可复用信息，还要处理作用域、冲突、遗忘和污染 |
| Retrieval | 搜索 / 索引 / 查询优化 | RAG 有自己的构建、Eval 和 Observability，不是接个向量库就完了 |
| Eval / Verifier | 断言 / 单元测试 / 类型系统 | 同一任务可能走不同路径，要同时看过程、结果和多次稳定性 |
| Policy / Guardrail / Sandbox | 鉴权 / 最小权限 / 异常处理 / 隔离 | 概率性执行者能操作真实系统，必须限制做错时的影响面 |
| Observability | Log / Trace / Profiling | 要能还原模型决策、工具调用、状态变化和投递结果的完整因果链 |

遇到新概念时，我会先拿这张表找它对应的已有抽象，再看模型的新特性带来了哪些变化。新的名词可以帮助行业建立共识，也常常对应新的能力和实践；底层的软件工程规律并没有因此失效。

我判断要不要投入，主要看两件事： **离生产力有多近，知识保鲜期有多长。**

|  | 离生产力近 | 离生产力远 |
| --- | --- | --- |
| 保鲜期长 | 深入学习 | 保持地图感 |
| 保鲜期短 | 需要时上手 | 暂时跳过 |

Loop、Context、Tool、State、Eval、权限与可靠性都在左上角：它们离实际产出近，也不会因为某个框架改 API 就失效。框架细节离生产力近，但保鲜期短，用到时学即可。模型跑分、融资新闻、没有真实约束支撑的新概念，离你的问题很远，就不要因为所有人都在讨论而焦虑。

### 学习资料怎么选

这篇文章没有再给大家塞一份大而全的课程目录。下面这些资料我基本都认真看过，也尽量在前文说清楚了该看什么、怎么练。资料不用囤很多，顺序比数量重要。我愿意直接推荐的，可以分成三组：

| 用途 | 推荐 | 怎么用 |
| --- | --- | --- |
| 建立 Agent 心智模型 | Building effective agents <sup>[11]</sup> + ReAct <sup>[10]</sup> | 先看简单模式和 Loop 原型，不急着选框架 |
| 读真实源码 | Pi `agent-loop.ts` <sup>[12]</sup> + Anthropic Skills <sup>[13]</sup> | 前者看 Runtime，后者看能力如何封装和渐进加载 |
| 建立反馈系统 | Anthropic Agent Evals <sup>[22]</sup> + Ragas <sup>[17]</sup> | 分清 Agent Eval 与 RAG Eval，各自准备测试集 |

Agent 不会是大家最后一个需要重新学习的技术。以前英文文档难啃，很多经验也很难摸到，跟着课程走确实省事。现在 AI 能帮忙翻译、解释、出题和 review，网上又有大量一手文档、深度文章和开源项目，自己学一门新技术的门槛已经低了很多。

如果想让 AI 带着自己学，我比较推荐 Teach <sup>[1]</sup> 。它会先问清楚你为什么学，再用一手资料、短课、检索练习和即时反馈一点点往前推。学过的内容需要能回忆、能动手、能得到反馈。如果只是想把一组一手资料整理成知识地图，可以用 Learn <sup>[25]</sup> 做前置整理。

AI 很适合做一对一的学习搭档，但资料还是要自己选。把官方文档、源码和手头的真实项目给它，让它解释、出题、反问和 review。读完一个概念以后，合上资料，用自己的项目回答三个问题：它在解决哪种失败？不做会怎样？我怎么验证实现没有问题？三个问题答不上来，就回去再看一遍、再动手试一次。

**会搭 Demo 是入门，能解释失败是理解，能让它在真实环境里持续工作，才是 Agent 开发。**
