# Grep beats LSP? Why coding agents ignore your fancier tools

> 原文：https://www.agentconnect.md/blog/grep-beat-lsp-harness/
> 作者：Pengcheng Xu（AgentConnect）　发布于：2026-08-12　翻译日期：2026-09-05
> 标签：agent-harness / tool-use / ACP / engineering

为什么编码 Agent 会忽略一个能返回更精确结果的检索接口？

我在一个小型研究中对比了基于 `grep` 的词法搜索与基于 LSP 的语义导航。我原本期望语义导航能减少噪音、节省 token。结果恰恰相反：Agent 往往坚持用 `grep`。而当我强制它们优先走语义路径时，任务成功率有时反而下降。

这是一个「LLM 友好性」（LLM-friendliness）的问题。一个工具并不会仅仅因为结果精确就对模型友好。它必须返回足以支撑下一步动作的上下文，并以模型能直接使用的界面形态和输出格式呈现这些上下文。熟悉度可能也有影响：模型也许在训练中就学过类似的动作路径。界面属性是可以直接评估的；训练支持则是一个与这些结果一致的假说，本研究并未证明它。

这个结论并不是一个针对 LSP 的普遍性反驳。LSP 协议包含远超代码导航的能力，而本研究只测试了其中很小的一个子集。真正指向的是一个更广泛的工程问题：模型并不是孤立地使用工具。它是通过一个 harness（执行框架）来使用工具的——这个 harness 定义了可用动作、它们的名称、输入参数，以及返回给模型的上下文。

在这篇文章中，我将描述代码检索如何同时影响「找代码」和「改代码」两类任务，为什么 `grep` 在某些条件下有优势，以及这对 Agent 平台意味着什么。

> **图 1：Agent 能力 = 模型 × 原生 harness**
> 模型与其熟悉的工具循环构成了同一个能力面。

## 对比两种代码检索接口

我对比了 Agent 获取代码上下文的两种方式。`grep` 做的是词法搜索：找到匹配的文本。被测的 LSP 工具做的是语义导航——通过引用、定义和文档符号进行跳转，因此它们能区分一个真正的函数调用和注释里出现的同一个词。

试点覆盖了三个 Claude 模型、多个 Python 和 TypeScript 仓库，以及多种任务类型。我只在两种方式都成功完成任务时才测量 token 用量。这是为了排除一个常见的评测错误：一次失败的运行可能仅仅因为提前停止而显得「高效」。

在简单的代码定位任务上，当两个工具都可用时，三个模型选择语义工具的比例仅为 0% 到 6%。在该组中，强制「语义优先」使成功率从 100% 降到了 89%。

「引用完备性」任务（找齐所有调用方）产生了不同的结果。当被要求找出每一个调用者时，模型选择语义导航的比例为 45% 到 57%。LSP 路径通过剔除误匹配达到了 1.00 的精确率，而 `grep` 只有 0.76。但两者的召回率都停在 0.66 附近——语义导航并没有找到更多真实调用。剩余的瓶颈在于 Agent 工作的彻底程度，而不是检索精确率。对更强的模型来说，精确率的提升还伴随着更高的 token 消耗，而非节省。

> **模型并不是盲目偏爱 grep——它按任务路由**
>
> 在 grep 与 LSP 同时可用、Agent 自由选择时，语义（LSP）工具调用占比：
> Opus 4.8（蓝）、Sonnet 4.6（品红）、Haiku 4.5（绿）。
>
> 同样的模型、同样的自由选择——路由随任务翻转。在定位和重命名任务上，Agent 几乎总是伸手拿 grep；在引用型工作上，它会有一半的时间主动选择 LSP。动作分布是随任务形状变化的，不是盲目的习惯。

代码库本身也很重要。在一个干净的 TypeScript 仓库上，LSP 导航没有带来 F1 提升，反而多用了 16% 的 token。而在一个嘈杂的 TypeScript 仓库上，它把 F1 提升了 0.246，且少用了 12% 的 token。真正有用的预测指标是词法噪音，而不是语言是否具有强静态类型。

> **代码库噪音决定语义导航的价值**
>
> 引用完备性任务上语义检索带来的准确率增益（ΔF1 = LSP − grep）。柱色编码该仓库上 grep 的嘈杂程度；prec = grep 在该仓库上的精确率。
>
> 同一种语言的两个仓库，结论相反。在干净的 remeda 上 LSP 一无所获——grep 已经能正确解析所有引用，语义检索纯属开销。在嘈杂的 hono 上它带来了 +0.246 F1。预测指标是 grep 精确率在该代码库上的退化程度，而不是语言是否静态类型化。

这些结果是有条件的，而不是一刀切的。Agent 并非「总是用 grep」：它们的路由随任务而变，LSP 导航的价值也随仓库而变。

被测的 LSP 工具最初只返回一个位置：文件路径、行号和列号。Agent 随后必须打开文件才能查看代码。相比之下，`grep` 通常立即返回匹配行本身：`src/auth.ts:42: return validateToken(token)`。

我把语义导航的响应改为以类似形态附带源码文本。语义后端和引用集合完全不变；唯一变化的是返回给模型的信息。重命名任务的 Pass@1 从 0.67 升到 0.83，而每个 episode 中的后续文件读取次数从 15.2 降到 3.2。

> **返回源码上下文改进了语义导航**
>
> 多文件重命名，Opus 4.8，pyright（预热索引）。两个 LSP 组使用相同的语义后端——只有输出形态不同。
> 图例：grep（蓝）、LSP—仅位置（品红）、LSP+内联上下文（绿）。
>
> 只返回位置会迫使 Agent 逐一去读取现场；内联返回该行则不必。给每条引用附上 ±2 行源码，把后续文件读取从 15.2 砍到 3.2——低于 grep 自身的 4.3——并将 pass@1 从 0.67 提到 0.83。检索后端从未改变；改变的只是返回内容的形态。

这个结果印证了 Anthropic 在《Writing effective tools for agents》中强调的原则：工具是给非确定性 Agent 用的接口，因此工具返回的上下文本身就是设计的一部分。一个语义上完全正确的工具，如果每个结果都需要额外好几步动作才能解读，仍然会造成糟糕的 Agent 工作流。

输出形态的改变并不能证明「后训练数据」就是改进的成因。它也可能仅仅因为每个响应里包含了更多有用信息。不过，这个结果与一个更广泛的假说一致：模型学到的是具体的动作模式，而不是抽象意义上的「工具使用」。一个熟悉的循环——提示、工具调用、可读的结果、下一步动作——本身可能就是实践中观察到的那部分能力。

## 为什么词法搜索会有优势

界面熟悉度只是解释的一部分。对于某些任务，词法搜索还拥有真实的结构性优势。

语义引用只是文本匹配的一种。一次重命名可能还需要更新注释、文档字符串、配置或字符串。`find_references` 按设计不会返回这些，而 `grep` 可以。

> `semantic references ⊂ textual occurrences`

对于全文本范围的修改，即使模型在 LSP 导航上受过完美训练，`grep` 也可能是更好的检索工具。

由此，我们对观察到的行为有了两种解释：

1. **结构性的：** 某些任务需要文本级的完备性，而受测的语义导航方法不提供这一点。
2. **分布性的：** 模型可能对熟悉工具及其结果形态有更多的训练实践。

第一种解释直接来自工具检索的内容。第二种是与路由和输出格式结果相一致的假说，但本研究并未操纵训练数据，因此无法证明它。

> **图：grep 胜出背后的结构性原因与分布性原因**
> 结构解释了 grep 什么时候更好；分布解释了为什么熟悉的路径仍然会赢。

## Harness 是系统的一部分

在本文中，harness 指的是模型周围的运行时：放进上下文的指令、可用的工具、它们的输入 schema、结果与错误的形态，以及决定模型下一步看到什么的循环。

这个外围系统会实质性改变行为。Anthropic 关于长时运行 Agent 有效 harness 的工作在更长的时间尺度上展示了同样的道理：单靠模型不足以跨会话可靠地推进。环境配置、进度工件和验证例程都会影响 Agent 能完成什么。

同样的原则也适用于单个工具循环之内。当后训练数据包含 Agent 轨迹时，harness 定义了这些样例中的提示、工具调用、结果和恢复路径。一个通过反复使用 `read`、`grep`、`edit` 和 `bash` 训练出来的模型，可能学到了依赖这些接口的策略。把同一个模型迁移到不同的工具层，可能会改变它的有效能力。

> `agent capability = model × harness`

这就是为什么模型在某个基准上的成绩并不总是能原封不动地迁移到另一个运行时。支持同一个模型，不一定等于复现同一个 Agent。工具选择、函数签名、输出格式和错误行为，都会影响模型遵循的策略。

这些发现并不意味着团队应该回避 LSP、MCP 或新的 Agent 技能。本研究在嘈杂代码中观察到 LSP 导航带来的明确精确率增益，而且一个小小的响应格式改动就消除了大部分后续读取。实际的教训是：要把新的检索接口当作完整 Agent 循环的一部分来评估。

我的建议是：以原生工具面为起点，然后在新增能力时应用以下检查：

1. **在同等准确率下测试真实任务。** 如果成功率同时下降了，就不要为更低的 token 用量庆祝。
2. **测量 Agent 是否真的调用它。** 可用不等于采纳。
3. **返回足以支撑下一个决策的上下文。** `path:line:content` 这样的结果可能比一个裸的位置对象更好用。
4. **保留原生回退路径。** 语义搜索和词法搜索解决的是不同的问题。
5. **按任务和代码库路由。** 嘈杂的仓库可能受益于语义导航；全文本范围的搜索可能仍然需要 `grep`。
6. **在关键处强化新轨迹。** 一段提示词可以介绍一个工具，但未必能建立起使用它的可靠策略。

正如 Anthropic 在《Building effective agents》中指出的，成功的 Agent 系统往往依赖简单、可组合的模式。更多的工具不会自动产生更强的 Agent；工具必须是可区分、可理解、并在模型工作流内真正有用的。

## 结论

本研究说明了为什么「更好的检索」无法脱离完整的 Agent 系统来评估。一个接口可以更精确却消耗更多 token；可以返回正确的位置却制造不必要的读取；而输出形态的一个小改动，就能让同样的语义结果对模型好用得多。

对构建 Agent 平台的团队来说，含义很直接：把模型和 harness 放在一起评估。保留那些已经支撑可靠行为的接口，并在真实任务上验证改动，而不是想当然地认为更高级的抽象会有帮助。

完整的实验设置、任务定义和结果，见论文《Does a Language Server Save Tokens for Coding Agents?》。

这也是 AgentConnect 背后的产品原则：用开放协议连接 Agent，同时让每个模型与其原生运行时和工具循环保持一体。

> **译者附注**：这是一项初步试点研究——任务集较小、仓库不多、只有三个 Claude 模型、每个实验格 2-3 次 rollout。作者只测试了通过引用、定义和文档符号进行的 LSP 导航，未测试 `textDocument/rename`、诊断或 code actions。一个支持重命名的 LSP 在 grep 表现最好的重构类任务上可能有不同表现。编辑任务是局部性的，并非标准 SWE-bench 分数。这些发现是有用的信号，而不是对所有模型、工具和代码库的最终定论。
