# 飞书知识生长

把飞书 Wiki 当作“当前最佳解释”，把多维表格 Base 当作“工作流、关系和历史”。使用 `lark-cli`，不依赖 Hermes。

## 开始前

1. 读取 `references/system-model.md` 和 `references/patch-protocol.md`。
2. 从环境变量 `FEISHU_KG_CONFIG` 读取配置路径；未设置时使用：
   - Windows：`$env:USERPROFILE\.knowledge-growth\config.json`
   - macOS/Linux：`~/.knowledge-growth/config.json`
3. 配置不存在或缺少资源 ID 时，读取 `references/feishu-schema.md` 和 `references/lark-cli-contract.md`，提出运行 `scripts/bootstrap.ps1`。默认只预演；获得用户确认后才使用 `-Apply`。
4. 写飞书前运行 `lark-cli whoami`。默认显式使用 `--as user --format json`。不得索取或记录 App Secret。若出现 `hermes context detected but lark-cli is not bound to it`，本 Skill 不执行 `config bind`；读取 `references/lark-cli-contract.md` 的“Hermes 上下文误判”，让用户确认后再处理持久环境变量。
5. 若缺少原文、转写或可访问链接，说明信息边界；可以先收件，但不得编造内容分析。

## 选择模式

根据请求选择一条主路径；不要一次跑完整套系统。

| 用户意图 | 模式 | 必读文件 | 默认产物 |
|---|---|---|---|
| “先存一下”“以后看” | `capture` | `references/dialog-protocol.md` | 来源记录 |
| “帮我分析/总结/融合” | `fuse` | `references/dialog-protocol.md` + 对应路线 | 补丁草稿 + 最小行动 |
| “为什么火/有什么启发” | `fuse:learning` | `references/route-learning.md` | 产品/内容知识补丁 |
| JD、面经、项目学习、能力欠缺 | `fuse:capability` | `references/route-capability.md` | 聚合要求 + 能力缺口 + 证据行动 |
| 生活问题、拖延、反复模式 | `fuse:growth` | `references/route-growth.md` | 暂定机制 + 行为实验/决策协议 |
| “处理收件箱” | `inbox` | 三条路线按记录加载 | 分批补丁草稿 |
| “确认/应用这个补丁” | `apply` | `references/lark-cli-contract.md` | Wiki 局部更新 + 状态变更 |
| “初始化首页/模型入口” | `setup-content` | `references/wiki-templates.md` + `references/lark-cli-contract.md` | 可直接使用的 Wiki 入口页 |

路线不清楚时，先按主要输出判断：理解世界走 learning，建立可证明能力走 capability，改变自身重复行为走 growth。跨路线内容只设一条主路线，其他作为关联。

## 核心闭环

### 1. 收件

- 保留来源、链接、原文/转述、时间和用户触发点；原始材料不可覆盖。
- 先查“内容指纹”或规范化链接；重复内容优先补充已有记录，不制造副本。
- 明确“仅暂存”时止于收件，不强迫分析。
- 无法读取平台内容时，请用户提供分享链接、文字、截图或转写；可以记录“待补原文”。

### 2. 找连接

- 从标题、关键词、当前目标和用户触发点提取 3–8 个检索词。
- 在“知识节点、目标、成长缺口”中寻找最相关记录。优先当前阶段和高影响缺口。
- 若没有真实匹配，声明“暂未找到已有节点”，不要伪造连接。
- 新内容只有在改变结论、边界、证据、行动或结构时才算知识增量。

### 3. AI 先压缩

先给用户一个可批判的草案，而不是把总结工作全部丢给用户：

1. 一句话结论。
2. 关键机制与证据。
3. 与已有知识的连接、重复、矛盾或缺口。
4. 对当前目标的边际价值。
5. 建议的知识补丁和一个最小验证行动。

事实、来源观点、AI 推断和用户判断必须分开标注。对热点、生活心理机制和未来结果使用假设语言。

### 4. 获取关键用户输出

遵循 `references/dialog-protocol.md`：通常最多问 3 个问题，只问会改变补丁或行动的问题。优先让用户完成以下任一项：

- 用自己的话指出它连接或修正了什么；
- 选择真正改变其决策的一条结论；
- 承诺一个小到可执行的验证动作。

用户时间少时允许 30 秒答案。不得用漫长苏格拉底式盘问阻断收件。

### 5. 生成补丁草稿

- 严格使用 `references/patch-protocol.md` 的字段和判定规则。
- 先生成待确认预览，再写“知识补丁”表为 `草稿` 或 `待确认`。
- 重复且无新增量时输出 `NoOp`，把来源关联到已有节点即可。
- 补丁只陈述本次增量，不重写整篇知识。

### 6. 应用与验证

以下变更必须在本轮获得用户明确确认后才应用：

- 修改 Wiki 中的当前结论；
- 写入或强化“自我模型”；
- 修正、合并、拆分、废弃节点；
- 批量应用多个补丁。

获得确认后：读取最新 Wiki 内容，做最小局部修改，再读回验证；随后把补丁标为 `已应用`。若 Wiki 更新失败，补丁保留 `已批准`，不得伪报已应用。

### 7. 关闭循环

- 有可检验假设时，创建“行动与验证”记录。
- 有当前能力差距时，创建或更新“成长缺口”，优先复用同一缺口。
- 最终只报告：更新了什么、为何值得、用户下一步、何时验证。

## 批处理规则

- 每批最多处理 5 条来源，先按“当前目标相关性 × 影响 × 时效性 ÷ 处理成本”排序。
- 相似材料先聚类，再生成一份融合补丁；不得逐篇制造同义节点。
- 遇到矛盾证据，不用多数票抹平；记录各自适用条件和需要验证的分歧。
- 高置信重复内容可以自动标为“仅归档”；Canonical Wiki 仍需确认后更新。

## 安全与质量边界

- 来源记录近似不可变；补丁只追加；知识节点只能通过补丁演化。
- 单个生活事件不能推出稳定人格；自我模型默认是“待验证模式”，并设置复查时间。
- 不把内容长度、点赞量、出现频率等同于真确性。热点分析区分可观察信号与机制假设。
- 不因系统完整性创建空节点、无行动缺口或低价值标签。
- 删除、权限变更、owner 转移、空间删除不属于本 Skill 的常规流程。
- CLI 返回 `ok:false` 时按错误 `hint` 修复一次；权限、身份或 scope 问题停止并告知用户，不反复猜参数。

## 输出约定

交互输出保持短而可确认：

1. `AI 判断`：结论、机制、证据边界。
2. `连接`：已有节点/目标/缺口。
3. `补丁预览`：操作、增量、合并后结论、边界。
4. `你的关键输入`：0–3 个问题。
5. `下一步`：一个最小行动或明确 `NoOp`。

用户只要求收件时，只返回记录标题、状态和待处理原因。
