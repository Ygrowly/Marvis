## 3. 标准回答

### 3.1 知识题：标准答案（八股补牢）

#### A19 · Linux 命令

**面试官真正想听**：不是命令清单，而是「线上出问题你怎么排查」。

**参考回答（60 秒）**：
> 「我常用的分四类。查文件是 `ls`、`find`、`grep -rn`，看日志用 `tail -f` 和 `less`；查进程用 `ps aux`、`top`、`kill`，后台跑服务用 `nohup` 和 `systemctl`；查网络用 `ss -lntp`、`curl`、`lsof -i:端口`；看资源用 `df -h`、`du -sh`、`free -m`。
> 真出故障我按一条线走：先看 `top` 确认是 CPU 高还是内存高，CPU 高就 `ps` 定位到进程再往下看线程栈；磁盘满就 `df` 加 `du` 一层层找大文件；端口不通就用 `ss` 和 `curl` 确认是没监听还是被防火墙挡了。我在金山做采集任务时，定时任务重跑导致数据重复，就是靠 `ps` 加日志时间戳定位到两个 worker 实例同时跑的。」

**补齐清单**：`awk` / `sed` / `sort | uniq -c` / `xargs` / 管道组合；`iostat`、`vmstat`、`dmesg`（了解即可）。

#### A20 · Redis 数据结构

**标准答案**：
> 「基础五种：**String**（计数、分布式锁、缓存单值）、**Hash**（对象属性，比如购物车 `key=user:1, field=sku`）、**List**（队列、栈、消息流，`LPUSH/RPOP`）、**Set**（去重、交集并集，共同好友、抽奖）、**ZSet**（有序集合，排行榜、延迟队列——score 存时间戳，用 `ZRANGEBYSCORE` 捞到期任务）。
> 另外还有几种扩展类型：**Bitmap**（签到、日活打点）、**HyperLogLog**（UV 去重计数，误差约 0.81%）、**Geo**（附近的人）、**Stream**（消息队列，支持消费组）。

#### A21 · 乐观锁 vs 悲观锁

**标准答案**：
> 「区别在**对冲突的假设不同**。
> **悲观锁**假定冲突一定发生，所以访问数据前先加锁：数据库里是 `SELECT ... FOR UPDATE`，Java 里是 `synchronized` 或 `ReentrantLock`，拿到锁才能改，其他事务阻塞等待。适合写多、冲突频繁、临界区长的场景，代价是锁开销和死锁风险。
> **乐观锁**假定冲突很少，不加锁直接改，只在提交时校验有没有被别人改过：常见做法是加 `version` 字段，`UPDATE t SET val=?, version=version+1 WHERE id=? AND version=?`，**影响行数为 0 就说明冲突了**，重试或返回失败；CPU 层面就是 CAS。适合读多写少。要注意 **ABA 问题**——值被改回原样会骗过 CAS，Java 用 `AtomicStampedReference` 加版本号解决。

#### B15 · SSE 是什么，是长连接吗

**这是本场唯一一处明确的概念性错误，必须修正。**

#### B16 · 句子翻转（单词不翻转）

**面试官真正想听**：能不能在 10 分钟内写出可运行代码，并处理好边界（多空格）。

**思路**（你最后说对了思路，但没落地成代码）：整体反转 → 逐单词反转回来，空格原样保留。

**参考实现（Python，保留多余空格）**：
```python
def reverse_words(s: str) -> str:
    chars = list(s)
    n = len(chars)
    chars.reverse()                      # 1. 整体反转
    i = 0
    while i < n:
        if chars[i] == ' ':
            i += 1
            continue
        j = i
        while j < n and chars[j] != ' ': # 2. 找到单词区间 [i, j)
            j += 1
        chars[i:j] = chars[i:j][::-1]    # 3. 单词内部反转回来
        i = j
    return ''.join(chars)
```
- 复杂度：时间 O(n)，空间 O(n)（字符串不可变语言必需）。
- 边界：`''`、全空格、首尾空格、连续多空格都能原样保留。

**被追问的 5 个空格**：你答「split 应该会处理多余空格」，被纠正「应该保留」。正确的区分是——
- `s.split()`：**无参数**时会折叠连续空白并去掉首尾，多个空格变成一个；
- `s.split(' ')`：按单个空格切，**保留空串**，**首尾空格也不会丢**——`' a '.split(' ')` 得到 `['', 'a', '']`，`' '.join(...)` 能原样还原成 `' a '`（`'a  b'` 同理，实测可完整往返）。
- 所以要严格保留空格，用上面的双反转最直接；也可以用正则 `re.findall(r'\S+|\s+')` 把「单词块」和「空格块」分别捕获再反转拼接。

**Java 版（岗位主力语言，必须准备）**：
```java
public static String reverseWords(String s) {
    char[] a = s.toCharArray();
    int n = a.length;
    reverse(a, 0, n);
    int i = 0;
    while (i < n) {
        if (a[i] == ' ') { i++; continue; }
        int j = i;
        while (j < n && a[j] != ' ') j++;
        reverse(a, i, j);
        i = j;
    }
    return new String(a);
}
private static void reverse(char[] a, int l, int r) {
    for (int i = l, j = r - 1; i < j; i++, j--) {
        char t = a[i]; a[i] = a[j]; a[j] = t;
    }
}
```

**第二步 · 规模估算**
2000 万 DAU；假设关卡数在千级量级。**不可能给每一关存全量用户排名**——所以采用「**每关只存 Top N + 玩家个人最佳 + 名次近似**」。

**第三步 · 存储与读写路径**
- **主体用 Redis ZSet**：`key = lb:{levelId}`，`member = playerId`，`score = 复合分数`。
  同分按时间早的优先 → 构造复合 score：`score = 分数 × 10^10 + (MAX_TS − 通关时间戳)`，分数越高越大、同分时时间越早越大。
  **⚠️ 这个写法有个必须自己先交代的边界**：**ZSet 的 score 是 double（IEEE 754）**，整数精确范围只到 `2^53 ≈ 9.007×10^15`。`分数 × 10^10` 一旦超过这个量级，**低位（时间戳那部分）会被舍入**——实测 `分数 = 100 万` 时 `10^16` 量级的复合值已经差 1，同分排序不保证严格正确。
  **所以要么先算清分数的上界**，要么**别用复合 score**：改成 `score = 分数`，同分时间用 `member` 里拼一个零填充的时间戳（`f"{MAX_TS - ts:010d}:{playerId}"`），把时间维度交给字典序、把数值维度留给分数。**面试里主动说出这一句，比被追问出来强得多。**
- **写**：通关上报 → 服务端校验合法性 → `ZADD`；
- **查自己名次**：`ZREVRANK`（O(logN)）；
- **查榜单**：`ZREVRANGE 0 99`（Top 100）。
- **裁剪**：每关只保留 Top N，`ZCARD` 判断后**用 `ZREMRANGEBYRANK key 0 -(N+1)` 删掉【分数最低】的那批**——这是控制内存的关键。
  **注意方向别写反**：`ZREMRANGEBYRANK` 里 **rank 0 是分数【最低】的元素，-1 才是最高分**（官方口径）。所以写成 `ZREMRANGEBYRANK key N -1` 删掉的正好是**榜首那批**，榜单会被砍成"最低分的 N 个人"。

**第四步 · 2000 万 DAU 下的工程问题（答到这层才像服务端）**
1. **热点 key**：热门关卡集中在少数 key，按「关卡 + 区服 / 分片」拆分，或本地缓存 + 异步刷新榜单（Top 100 允许 1 分钟延迟）。
2. **写入削峰**：通关上报是尖峰写，走消息队列异步落榜，前端先返回「计算中」。
3. **名次不必实时精确**：非头部玩家的名次可用「分数段桶计数」近似（比如每 100 分一个桶，统计人数累加估算名次），把 O(logN) 的精确查询留给头部。
4. **持久化**：Redis 只做热层，冷数据定时落 DB；Redis 挂了可从 DB 重建，或降级为「榜单维护中」。
5. **内存控制**：估算 `关卡数 × TopN × (member + score + 跳表指针开销)`，按 Top 100 计算量级，超出就降到 Top 50 或只做周榜。

**第五步 · 游戏特性（这是乐元素面试官最想听的部分）**
- **防作弊**：消消乐是弱联网玩法，客户端上报的分数必须校验——步数下限、最短通关时长、关键操作日志回放；异常分数进人工审核队列，不直接入榜。
- **弱联网容错**：离线通关的成绩本地缓存，联网后补报，用玩家 ID + 关卡 ID + 通关时间戳做**幂等**，避免重复提交刷榜。
- **活动榜**：面试官反问时明确说「先活动吧，活动这块」——所以补充一句：活动榜是**有时效的**，用带过期时间的 key（`EXPIRE`），活动结束自动清理，不用手动下线。

**第六步 · 指标与降级**
- 指标：写入 QPS、查榜接口 P99、Redis 内存占用、裁剪任务耗时。
- 降级：Redis 不可用时返回 DB 快照或直接返回「榜单维护中」，绝不让排行榜拖垮主玩法。

> 这题的完整框架挂在 [[场景设计题库-十道母题]]，建议把「排行榜」作为第 11 道母题补进去。
