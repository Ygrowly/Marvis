# 11 简历证据边界与项目模拟面试

> 优先级：P0｜作用：把前十个模块压缩成可信、可追问、可迁移的面试能力。

## 1. 模块定位

本模块不增加新设计，而是统一项目介绍、简历数字、参与边界、失败案例、技术取舍和模拟面试方式。

## 2. 一句话结论

面试中先讲支付业务链和确定性事实，再讲 Agent、证据契约与 Eval；所有模拟结果必须说明场景、分母、版本和证据等级。

## 3. 第一性原理

面试官真正判断的是：你是否理解用户问题，系统是否正确，你为何这样设计，以及结果能否自证。技术名词越多，不代表项目越可信。最危险的是把设计目标、简历母稿数字和模拟结果说成真实生产结果。

## 4. 核心业务对象

面试事实包应包含：

| 层次 | 必须准备的内容 |
|---|---|
| 背景 | Ovanta 支付/订单/权益与出海电商问题意识 |
| 产品 | 用户、痛点、主线、系统边界 |
| 技术 | 九阶段、Intent、损失、Harness、Evidence、Eval |
| 证据 | 代码、测试、回放、评测报告和待验证数字 |
| 取舍 | 人工/BI/Workflow/单 Agent/多 Agent 的条件 |
| 复盘 | 一个失败、一个优化、一个下一步 |

## 5. 正常业务与技术流程

五分钟项目讲解顺序：

```text
真实问题来源
→ 为什么监控和日志仍有断层
→ 九阶段与 Purchase Intent
→ 确定性异常和损失账本
→ Incident + 七类只读工具
→ 单 Agent Harness + Hypothesis Ledger
→ Evidence 契约 + 人工复核
→ 故障注入 + Ground Truth Eval
→ 模拟数据边界与下一步
```

不要按 FastAPI、DuckDB、Agent、Eval 的技术栈顺序介绍。

## 6. 关键问题和故障场景

- 项目介绍从“我用了 Agent”开始，业务问题不清楚。
- 被问损失如何计算时只回答模型归因。
- 无法解释 Purchase Intent、对象集合和重复计损。
- 把 Harness 说成普通 Tool Calling，或把单 Agent 说成多 Agent。
- 给出 F1、MAE、延迟，却说不出数据集、分母和对照版本。
- 把模拟故障说成真实线上事故。
- 只讲成功，没有失败语义、取舍和下一步。

## 7. 解决方案、优化与长期预防

每个数字建立证据卡：指标定义、分母、样本集、基线版本、候选版本、命令/报告、E1/E2/E3。没有实际产物时，使用“设计目标”“简历母稿口径”“待验证”，不得背成结果。

当前简历母稿包含以下数字，但在进入正式口述前必须逐项核验：

| 母稿表述 | 当前使用方式 |
|---|---|
| 100 个黄金场景、单场景 10 万 Intent/80 万事件 | 待场景清单和生成报告核验 |
| 阶段定位 72% → 93% | 待评测脚本与版本报告核验 |
| 根因 F1 0.61 → 0.87 | 待多标签定义、样本和报告核验 |
| 重复损失 12.4% → 1.6% | 待集合去重测试核验 |
| Loss MAE 18.6% → 6.8% | 待损失标签和计算报告核验 |
| 无依据结论 14.2% → 2.5% | 待 Evidence 评分规则核验 |
| 工具中位调用 11 → 6、Token -36% | 待 Trace 与成本报告核验 |
| pass^3 67% → 91% | 待重复运行明细核验 |
| 断线/重启恢复、回归耗时 | 待演练日志和命令核验 |

核验前可讲系统机制，不能把这些数字作为事实证明。

## 8. 钢人比较

面试时先承认强替代方案：人工排查具有业务直觉，PSP 看板数据最近，固定 Workflow 更稳定，One-shot 更便宜。然后说明 PayTrace 适用条件：跨系统、多根因、重复调查、需要证据和版本回归。不要通过贬低传统方案证明 Agent。

## 9. 逆向检查

即使项目介绍流畅，面试官仍可能沿以下链路击穿：数据从哪来 → 分母是什么 → 状态谁权威 → 如何发现异常 → 损失怎么算 → Agent 为什么需要 → 工具失败怎么办 → Evidence 如何证明 → 指标如何评 → 你实际做了什么。

回答任何数字前先问自己：它是实现事实、模拟评测、设计目标，还是简历草稿？

## 10. 边际决策

当前求职阶段优先做到：90 秒介绍、黄金案例、七个核心母题、数字核验。暂不继续扩展项目功能。一次模拟面试只修最关键三个断点；修完立刻重答，并在第 1、3、7 天复训。

## 11. 面试标准回答

### 20 秒

PayTrace 是我做的支付转化异常诊断 Agent。系统先按 Purchase Intent 和九阶段漏斗确定性计算损失，再由 Harness 编排七类只读工具调查，结论必须绑定 Evidence，并通过故障注入和隔离 Ground Truth 做回归验证。

### 60～90 秒

这个项目来源于我在 Ovanta 支付、订单和权益链路，以及出海电商场景中看到的问题：传统看板能发现支付率下降，日志能看到单次错误，但业务团队仍难判断损失在哪个阶段、影响多少真实购买意图、有哪些并发根因。PayTrace 先用 Purchase Intent 解决取消重下单的重复统计，再统一九阶段事件，由确定性代码定位异常和计算损失。随后单诊断 Agent 在 Harness 约束下调用七类只读工具，Hypothesis Ledger 管理待验证和已否定假设，每条 Claim 必须绑定可复算 Evidence，证据不足就保留 UNKNOWN。项目使用模拟数据、故障注入和隔离 Ground Truth 做 Response 与 Trajectory Eval，因此能验证系统机制和版本相对表现，但不能替代真实商户生产验证。

### 五分钟深度版本

沿本文件第 5 节主线展开，并用黄金案例贯穿：需求稳定 → 认证与回写阶段异常 → 损失账本 → 两个根因假设 → 七类工具取证 → Evidence 去重 → 人工复核 → Ground Truth Eval。最后补一个取舍和一个下一步。

## 12. 高频追问

**问：这个项目最难的点是什么？** 不是接模型，而是建立可信边界：用 Purchase Intent 和损失账本保证数值不重复，用 Harness 控制调查，用 Evidence 契约阻断无依据结论，再用 Ground Truth 证明版本变化。

**问：为什么不是 RAG？** 核心证据来自结构化订单、支付事件、配置和指标，不是文档检索。未来可以用 Case Memory 辅助，但不能替代实时事实工具。

**问：为什么不做多 Agent？** 当前调查共享同一 Incident、工具和证据，单 Agent 更易保证一致性和 Eval；没有证据证明拆分收益前不增加协作复杂度。

**问：你如何计算损失？** 固定观察窗口和基线，以有效 Purchase Intent 完成数为主口径，用确定性集合去重和守恒，Agent 不参与数值计算。

**问：Agent 错了怎么办？** 工具与权限由 Hook 控制，Claim 必须通过证据门禁；证据不足返回 PARTIAL/UNKNOWN，最终高风险动作由人工负责。

**问：如何证明有效？** 使用固定生成器、故障注入和隔离 Ground Truth，同时评最终报告和调查轨迹；具体提升数字只有在评测产物核验后才使用。

**问：项目最大的局限？** 模拟数据不能覆盖真实渠道分布和组织流程，也不能证明线上收益；下一步应优先接入脱敏真实事件做 Shadow 诊断，而非扩展更多 Agent。

## 13. 最短恢复脚本

> 真实痛点 → Intent 九阶段 → 确定性损失 → 单 Agent 工具 → Evidence → GT Eval → 边界

## 14. 闭卷自测

1. 用 20 秒定义 PayTrace。
2. 用 90 秒讲完整项目。
3. 画出黄金案例的正常与异常链路。
4. 解释为什么损失不能交给 LLM。
5. 解释 Harness 与普通 Tool Calling 的区别。
6. 解释 UNKNOWN 为什么是正确输出。
7. 解释 pass@k 与 pass^k。
8. 选择一个简历数字，说明完整证据口径。
9. 讲一个钢人替代方案和选择条件。
10. 讲项目局限和最有价值的下一步。
